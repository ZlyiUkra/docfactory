# Оновлення корпусу — як провести апдейт

Корпус примірника — тека `instances/<домен>/corpus/`: локальна копія документації звичайними текстовими файлами.
Оригінали живуть на офіційних сайтах — яких саме, каже `sources.json` примірника; для ecmascript це tc39.es,
ecma-international.org, unicode.org і rfc-editor.org — і час від часу змінюються: tc39 перезбирає ECMA-262,
Unicode випускає нові редакції звітів, у видання вклинюються нові глави. Копія сама про це не дізнається, тож
апдейт запускають руками. Цей довідник веде його від «чи щось змінилося?» до «сервер відповідає по свіжому
корпусу» — і з Qdrant, і без нього.

Чотири слова, якими тут усе сказано:

- **нагорі** — на офіційних сайтах із `sources.json`: там оригінал, у `corpus/` — наша копія;
- **паспорт** — файл `corpus/index.json`, опис копії: для кожного документа адреса, дата завантаження і
  контрольна сума тексту. За сумами звірка відрізняє «змінилося» від «те саме»;
- **пошук по словах** — типовий спосіб пошуку сервера: знаходить розділ за збігом слів, працює прямо по
  текстових файлах і нічого не потребує;
- **пошук за змістом** — необов'язковий другий спосіб: кожен фрагмент тексту лежить у базі Qdrant числовим
  відбитком (вектором), тож розділ знаходиться й тоді, коли запит сказаний іншими словами. Змінився текст —
  відбитки змінених фрагментів треба порахувати наново; саме це зветься «дорахувати вектори».

Усі кроки біжать з кореня `docfactory/` через `./df <домен> <крок>`; приклади нижче — для примірника `ecmascript`.
Для `react` є власний довідник, [instances/react/UPDATE.md](instances/react/UPDATE.md): там регулярна перевірка сайтів
документації і перехід на нову версію React без втрати тексту попередньої.
Сервер зупиняти заздалегідь не треба: перезапуск — останній крок, і лише він.

```
check ──────► refresh [id…] ──────► manifest ──────► vectors ──────► перезапуск serve
звірка         завантаження           паспорт          вектори         сервер перечитує
з джерелами;   лише зміненого;        index.json;      лише в режимі   корпус на старті
нічого не пише білий список           без мережі       «за змістом»
```

| # | Крок | Команда | Мережа | Пише | Коли потрібен |
|---|------|---------|:------:|------|---------------|
| 1 | Звірка | `./df ecmascript check [--deep]` | так | нічого | завжди, з нього все починається |
| 2 | Завантаження | `./df ecmascript refresh [id…]` | так | `corpus/*.txt` | коли звірка щось показала |
| 3 | Паспорт | `./df ecmascript manifest` | ні | `corpus/index.json` | одразу після refresh |
| 4 | Вектори | `./df ecmascript vectors` | ні¹ | колекцію Qdrant | лише якщо ввімкнено пошук за змістом |
| 5 | Перезапуск | Ctrl+C і знову `./df ecmascript serve` | — | — | завжди: корпус читається на старті |
| 6 | Перевірки | `./df ecmascript smoke` | ні | нічого | завжди після оновлення: числа й цілі в `checks.json` |

¹ Docker локально; перший запуск ще довантажує модель векторів.

## Крок 1 — `check`: що змінилося нагорі

```
./df ecmascript check                    # швидка звірка
./df ecmascript check --deep             # повна: ще й глави ECMA-262 і тіла документів
./df ecmascript check --deep ecma262     # лише названі джерела; решта цього разу не питається
```

Нічого не пише й не змінює — лише питає кожне джерело з `sources.json` і порівнює з тим, що лежить у `corpus/`:

- `+ новий` — документ з'явився нагорі, у корпусі його ще немає;
- `~ змінився` — вміст розійшовся з нашим;
- `сироти` — файл є в `corpus/`, а нагорі за джерелом його вже немає (див. «Особливі випадки»).

Вміст звіряється сумою тексту без шапки, тож перезавантаження того самого тексту за зміну не рахується. Ціна
звірки в різних джерел різна, і `check` це враховує:

- **ECMA-402** приходить однією сторінкою — зміст звіряється завжди, це одне звернення;
- **PDF, RFC і звіти Unicode** питаються умовним запитом «чи змінилося після нашої дати»: сервер відповідає `304`
  без тіла. Відповів `200` — без `--deep` це чесно друкується як «новіше за нашу дату, звірити тіло: --deep»;
- **ECMA-262** дешево не звіряється: tc39 перезбирає видання на кожен запит, тож єдиний чесний сигнал — сума
  тексту глави, а для неї главу треба завантажити. Без `--deep` глави 262 пропускаються (підсумок скаже, скільки),
  з `--deep` — завантажуються й звіряються всі.
- **Сайти документації** (джерела `react`) звіряються так само, як 262: одна адреса джерела не описує сотні
  сторінок, тож без `--deep` документи лише перелічуються, а з `--deep` кожен завантажується — з паузою
  `pause_sec` між зверненнями, тобто годинами. Тому глибоку звірку там обмежують іменами джерел.
- **Заморожені джерела** (`"frozen": true` у `sources.json` — знімок на закріпленому тезі чи коміті) не питаються
  зовсім: їхній вміст змінитися не може. Назвіть id — і звірка спитає й їх.

З іменами (`check [--deep] <id…>`) звіряються лише названі джерела; файли решти не стають ні сиротами, ні
«невідомими», а підсумок каже, скільки їх лишилося без звірки. Невідомий id — відмова з поясненням, а не мовчазний
нуль.

Підсумковий рядок — весь результат одним поглядом:

```
── Без змін 68, змінилося 2, нових 1, сиріт 0, збоїв 0 ──
```

Код виходу — `0`, якщо всі джерела відповіли, `1` при збоях: зручно для автоматизації. «Змінилося» в коді виходу
не відбивається — рішення про завантаження лишається за людиною.

## Крок 2 — `refresh`: завантажити зміни

```
./df ecmascript list                     # репетиція: що завантажилося б, без запису
./df ecmascript refresh ecma402          # точково: одне джерело
./df ecmascript refresh 27-memory-model.txt uts35-3-numbers   # точково: документи впереміш
./df ecmascript refresh                  # без імен: перезавантажити ВЕСЬ корпус наново
./df ecmascript refresh --missing        # лише відсутні файли; жодного наявного не перезаписує
```

Іменем може бути `id` джерела з `sources.json`, ім'я файла в `corpus/` або id документа з паспорта — у глав
видань він несе префікс джерела (`ecma262/scope`, `ecma402/intl-object`), бо голі назви перших глав в обох
виданнях однакові, і без префікса одне ім'я означало б два документи. Нові документи записуються завжди; наявні
перезаписуються лише названі — а без імен усі, тож `refresh` без аргументів — це повне перезавантаження корпусу,
не «докачати змінене». Економний шлях: `check` → `refresh <лише те, що змінилося>`.

`--missing` — протилежний край: пише лише файли, яких у `corpus/` ще немає, і не перезаписує жодного наявного. Так
докачується те, що з'явилося нагорі або не завантажилося минулого разу через збій. З іменами джерел
(`refresh --missing ecma402`) питаються лише названі. Заморожені джерела (`"frozen": true`) і `refresh`, і
`refresh --missing` пропускають, доки їх не назвати.

Тягнути можна тільки задеклароване: дозволені адреси виводяться з `url` записів `sources.json`, усе поза цим
переліком оновлювач відхиляє — хоч би команда прийшла з отруєного документа. Керування джерелами — редагуванням
самого файла: додали запис — джерело з'явилось, прибрали — зникло (файли його при цьому лишаються в `corpus/` і
спливуть у `check` як сироти).

Повний `refresh` — це багато звернень до чужих серверів (між ними навмисна пауза: типово секунда, а поле
`pause_sec` у `config.json` примірника задає свою — у `react` це 5 секунд), але **не** повний перерахунок векторів:
незмінений текст дає ту саму суму, і крок 4 його не чіпає. На відповіді 429 («забагато») і 503 оновлювач чекає й
пробує знову, тричі, а тоді рахує збій і йде далі.

Перерваний повний `refresh` наново не починають: `refresh <id джерела, на якому зупинилося>` перезапише лише це
джерело, а решту допише — вже завантажені файли інших джерел лишаться як є. Якщо переписувати не треба нічого,
досить `refresh --missing`: він допише все відсутнє.

## Крок 3 — `manifest`: оновити паспорт

```
./df ecmascript manifest
```

Паспорт `corpus/index.json` — це опис корпусу: для кожного документа ім'я файла, стійкий ідентифікатор, адреса,
дата завантаження і сума тексту. Саме з цими сумами порівнює `check`, і після `refresh` паспорт сам **не**
оновлюється: пропустіть цей крок — і наступна звірка показуватиме щойно завантажені документи як «змінився».
Тому правило просте: був `refresh` — одразу за ним `manifest`. Крок безкоштовний, без мережі.

## З Qdrant чи без — два способи пошуку

Сервер шукає двома способами, і апдейт від цього відрізняється рівно одним кроком:

| | По словах (BM25) | За змістом (+ Qdrant) |
|---|---|---|
| Що потрібно | нічого: текстові файли поруч | Docker; контейнер `agent0826-qdrant`, модель `bge-small` |
| Якість | запит мусить вживати слова шуканого розділу | парафраз теж знаходить («how to find out the type of a value» → `Object.prototype.toString`) |
| Апдейт | кроки 1–3 і перезапуск | ті самі кроки **плюс** `vectors` |

Рішення «з Qdrant чи без» — не частина апдейту: воно ухвалюється один раз, лежить у `out/mode.json`, і сервер його
лише читає. Якщо записано `vectors`, при старті сервер сам піднімає контейнер і гріє модель у фоні — після
перезавантаження машини нічого руками робити не треба. Передумати можна будь-коли, в обидва боки:

```
./df ecmascript setup                    # діалог: одне питання, y/n/q
./df ecmascript vectors                  # без питань: увімкнути, підняти Qdrant, залити колекцію
./df ecmascript setup --no-vectors       # без питань: вимкнути (контейнер лишається жити)
./df ecmascript setup --stop             # вимкнути й зупинити контейнер
./df ecmascript status                   # що вирішено і що зараз працює
```

Жодна з цих команд нічого не видаляє: ані колекції, ані том, ані контейнер. Контейнер один на всі примірники
(колекція в кожного своя — в `ecmascript` це `docs-ecmascript`), тож `--stop` забирає базу й у сусідів — вони
чесно скажуть про це в своєму виводі й перейдуть на пошук по словах.

## Крок 4 — `vectors`: дорахувати вектори

```
./df ecmascript vectors                  # дорахувати лише нове й змінене
./df ecmascript vectors --refill         # перерахувати все наново, поверх тих самих номерів
./df ecmascript status                   # скільки лишилося: нових N, змінених M, незмінних K
```

Крок інкрементальний, і на це можна покластися:

- **Номер точки стійкий** — виводиться з ідентифікатора фрагмента, а не з позиції в списку. Правка документа в
  середині набору не збиває номери решти: оновиться лише фрагмент, чия сума змінилася.
- **Рахується лише потрібне.** Перед рахунком фрагменти розкладаються на нові / змінені / незмінні; незмінні не
  чіпаються. Після повного `refresh`, де реально змінилося два документи, рахуватимуться хвилини, не десятки.
- **Перерваний запуск не пропадає.** Заливання йде пачками з друком поступу; що Qdrant уже прийняв — лишається.
  Наступний запуск побачить залите як «сума та сама» і продовжить з решти.
- **Нічого не видаляється.** Нові точки дописуються, змінені перезаписуються на своїх номерах.

Дві ситуації, коли `vectors` поводиться інакше, ніж зазвичай:

- **«Жодну точку не впізнано».** У колекції є точки, але ні одна не відповідає поточним фрагментам — стара схема
  номерів або чужий корпус. Доливати не можна (старі точки лишилися б дублями), тож команда відмовляється і друкує
  рецепт: знести колекцію (`curl -X DELETE …` — команду вона показує сама) і залити наново.
- **Зайві точки.** Точки, чий текст із документів зник (наприклад, після видалення сиріт). Пошук їх не віддає, бо
  їхніх фрагментів немає в наборі; фізично прибрати можна лише знесенням колекції — і це робить людина, не команда.

## Крок 5 — перезапуск сервера

Корпус сервер читає один раз, на старті. Тому останній крок — у терміналі, де живе `serve`: Ctrl+C і знову

```
./df ecmascript serve
```

Старт — близько 5 секунд (збирається індекс по словах). У режимі «за змістом» ще ~7 секунд у фоні гріється модель;
ці секунди нікого не тримають — сервер уже відповідає, поки що по словах, а поле `search` у кожній відповіді каже,
який спосіб відпрацював. Claude Code перепід'єднається сам за тією ж адресою — у `.mcp.json` нічого міняти не
треба, порт не змінився.

Перевірити, що все зійшлося:

```
./df ecmascript status                   # у режимі vectors: «усі вектори на місці й актуальні»
./df ecmascript smoke                    # перевірки сервера, ~15 с
```

## Крок 6 — звірити перевірки: `smoke` і `quality`

Оновлений корпус — інші фрагменти, а дві речі в `checks.json` примірника тримають їхні числа й номери навмисно, а
не читають з корпусу. Після оновлення їх треба звірити руками, інакше сюрприз прийде пізніше — червоним smoke або
заміром, що мовчки міряє дев'ять запитів замість десяти.

**`checks.json`, поле `expected_passages`.** Smoke звіряє кількість фрагментів індексу з цим числом і при
розбіжності падає на першій же перевірці. Це навмисно: зміна кількості мусить бути побачена, а не прийнята мовчки.
Якщо `./df ecmascript smoke` після оновлення червоніє рядком «індекс зібрано при завантаженні модуля», порівняйте
число з виводу з очікуваним. Різниця пояснюється завантаженими главами — впишіть нове число в `expected_passages`
і дату в `expected_note` поруч; не пояснюється — шукайте, який розділ загубився: наступний рядок smoke називає
втрачені. Кількість може й не змінитися: змінений текст глави — це ті самі фрагменти з іншими сумами, і тоді
правити нічого.

**`checks.json`, поле `quality`.** Замір якості тримає десять запитів і для кожного розділ, який має знайтися. Номери розділів ECMA-262 між редакціями зсуваються, і ціль, якої в корпусі більше немає, не влучає жодним
способом — замір міряє дев'ять запитів, а каже про десять. Ціль із «−» в усіх трьох стовпцях `--show` підозріла;
чи існує розділ узагалі, каже grep по файлу глави:

```
./df ecmascript quality --show           # «−» в усіх стовпцях — ціль варто перевірити
grep -n "^7.2.15 " instances/ecmascript/corpus/07-*.txt   # порожньо — розділу немає
```

Ціль, якої немає, замініть на номер того самого розділу в новій редакції — його назва в корпусі та сама. У
`react` ціль — не номер, а ім'я документа й шлях заголовків (`reference-react-usestate#reference`): сайт між
редакціями перейменовує заголовки так само, як tc39 зсуває номери.

## Крок 7 — відновити уточнення відповідей

Якість відповіді тримається не лише на корпусі, а й на двох речах поруч із ним, підігнаних під попередній
корпус: промптах примірника (`prompts/search.txt` — опис пошуку для моделі, `prompts/agent.txt` — промпт власного
агента) і другій десятці заміру. Будь-яке оновлення корпусу — нові версії, нова лінія, нове джерело, інша
розкладка сайту — може тихо зсунути те, що модель отримує на ті самі питання. Тому після кожного оновлення цикл
уточнень проходять наново, а не вважають зробленим раз і назавжди.

Дві десятки заміру — два різні питання:

- **`quality`** — десять питань своїми словами, повз промпт: найгірший випадок. Міряє сам пошук.
- **`quality_model`** — ті самі теми так, як їх поставить модель за промптом: назвами документації, з версією (третій
  елемент запису) і, де треба, з фреймворком чи SDK. Міряє те, що сервер віддасть моделі насправді. Саме ця
  десятка показує, чи промпт ще веде туди, куди треба.

**Порядок.**

1. Прогнати замір на свіжих векторах: `./df <домен> quality --show`. Він друкує обидві десятки і для кожного
   запиту — що саме знайшлося.
2. Порівняти з попереднім результатом. Останні числа записано в README примірника (абзац «Замір `quality`») і в
   повідомленнях комітів «<домен>: промпт …» та «<домен>: десятка «як модель» …» (`git log --grep`).
3. Звірити лінію за замовчуванням з тим, чим користуються. Коли питання не каже версії, промпт веде модель у
   «поточну лінію» — ту, що вписана в `search.txt` і `agent.txt`. Правильна вона тоді, коли на ній сидить
   більшість проєктів, а це не завжди найновіша: реєстр npm віддає завантаження кожної версії за тиждень.

   ```
   curl -s https://api.npmjs.org/versions/<пакет>/last-week | python3 -c "
   import json,sys,collections; d=json.load(sys.stdin)['downloads']; t=sum(d.values()); c=collections.Counter()
   for v,n in d.items(): c['pre' if '-' in v else v.split('.')[0]]+=n
   print(*(f'{k}: {100*n/t:.1f}%' for k,n in c.most_common(5)), sep='\n')"
   ```

   Пакет для заміру: astro — `astro`, nestjs — `@nestjs/core`, react — `react`, react-router — `react-router`,
   tanstack-query — `@tanstack/react-query` (до v4 — `react-query`), react-hook-form — `react-hook-form`. Ім'я з
   областю в адресі кодується: `@` — `%40`, `/` — `%2F` (`…/versions/%40nestjs%2Fcore/last-week`), інакше API
   відповідає помилкою.

   У clerk лінія — не номер пакета, а покоління SDK (Core), тож мажорні версії зводяться до ліній за таблицею.
   Міряється `@clerk/nextjs`, найпоширеніший із SDK; відповідність — за гайдами оновлення й датами релізів npm
   (7.0.0 вийшов 03.03.2026, у день запису журналу змін про Core 3, і в реєстрі має мітку `canary-core3`):

   | `@clerk/nextjs` | Лінія |
   |-----------------|-------|
   | 7.x | `core-3` |
   | 5.x–6.x | `core-2` (гайд оновлення до v6 лежить у гілці `core-2`) |
   | до 4.x | `core-1` |

   Замір 26.09.2026: `core-3` — 59%, `core-2` — 39% (6.x — 36,7%, 5.x — 2,1%), `core-1` — 1%. Коли вийде Core 4,
   у таблицю дописується мажорна версія, з якої вона почалася.

   Для supabase (версій немає) пункт не застосовується. Для ecmascript — теж, але з відкритим питанням нижче.

   Замір лише показує числа, нічого не змінює. Чи міняти лінію за замовчуванням — вирішує той, хто проводить
   оновлення: коли найпопулярніша лінія — не та, що в промпті, або дві лінії ділять користувачів майже порівну
   (тоді доречніше правило «спитай версію проєкту»). Рішення й числа записати в README примірника.
4. Ціль, що не влучила жодним способом, спершу перевірити на існування: сторінку могли перейменувати чи
   перенести. Така ціль замінюється на нове ім'я тієї самої сторінки. Ціль добирається з документації, а не з
   видачі: ціль, дописана під те, що пошук знайшов, робить замір зеленим і порожнім.
5. Промах у `quality_model`, коли ціль на місці, — це робота для промпту. Подивитися, що зайняло місця замість
   цілі, і назвати причину. Досі траплялися:
   - **поточна лінія змінилася** — промпт і далі велить шукати з `version` старої лінії. Замінити лінію в
     `search.txt` (абзац про те, з якої версії шукати) і `agent.txt`, а в `quality_model` — там, де питання про
     поточну поведінку;
   - **новий шум займає видачу** — блог, сторінки помилок, журнал змін, десятки редакцій старого README. У
     `search.txt` дописується правило: з якою `version` шукати, яким словом назвати запит, що робити, коли вся
     видача — такий шум (шукати ще раз назвою гайду);
   - **модель описує своїми словами** замість назви можливості — правило «пиши запит назвою, як її називає
     документація» з прикладами саме цього примірника.
6. Після кожної правки промпту — знову `quality`. Правка, що не підняла `quality_model` або опустила іншу ціль,
   відкочується. Промпт не підганяють під десятку: правило мусить бути правдою про документацію, а не про ці
   десять запитів.
7. Записати нові числа в README примірника й закомітити окремо від корпусу: «<домен>: промпт …» з числами до й
   після в тексті коміту. Сервер перечитує промпти на старті, тож потім — перезапуск `serve`.

**Ecmascript: база — завжди ECMA-262, жива чернетка.** Пункт 3 міряє популярність лінії пакета, а для
специфікації такого сигналу немає: пакета npm немає, а «яку редакцію читають найчастіше» — питання без сенсу.
Рішення (26.09.2026): лінії за замовчуванням тут немає й не буде — база завжди ECMA-262 у тому вигляді, в якому
її тримає tc39 (`https://tc39.es/ecma262/multipage/`, джерело `ecma262`). Нове, що tc39 вносить у специфікацію,
потрапляє в корпус звичайним оновленням (`check` → `refresh`), без правки `sources.json`. Підтримка можливостей у
браузерах і Node (дані сумісності на кшталт MDN browser-compat-data) до примірника не входить; якщо колись
знадобиться — це окреме джерело й окреме рішення.

Що в кожному примірнику означає «поточна лінія» і які правила промпту вже є — в його `UPDATE.md`, розділ
«Уточнення відповідей після оновлення». Власного `UPDATE.md` не має лише `ecmascript`: його промпт лінії не
фіксує (редакція специфікації одна), `quality_model` шукає без `version`, а головне правило промпту — називати
номер розділу; після нової редакції ECMA-262 цілі обох десяток звіряють за кроком 6, бо номери розділів зсуваються. Власного `UPDATE.md` не має лише `ecmascript`: його промпт лінії не

## Особливі випадки

**Сироти в `corpus/`.** `check` знайшов файли, яких нагорі за джерелом уже немає, — і лише називає їх: «нічого не
видалено — що з ними робити, вирішувати вам». Якщо документ справді втратив право жити в корпусі — видаліть файл
руками, оновіть паспорт (`manifest`) і, в режимі за змістом, дайте `status` показати його точки як «зайві».
Важлива межа: сиротою файл називається лише тоді, коли його джерело *відповіло* і файла в переліку не було. Файли
джерела, якого не вдалося спитати (тайм-аут, збій мережі), `check` показує окремо, під заголовком «Невідомо», — це
не сироти, видаляти їх не можна: чи існують вони нагорі, цей прогін просто не дізнався. Повторіть звірку, коли
джерело оживе.

**Зсув глав ECMA-262.** Ім'я файла глави несе позицію в змісті видання (`22-text-processing.txt` — двадцять
друга за порядком). Вклиниться нова глава раніше — всі наступні файли дістануть інші імена, хоча самі документи не
змінилися. `check` це впізнає і підказує біля сироти: «ймовірно зсув: те саме, що новий …». Ідентифікатори
фрагментів позиції не містять, тож вектори через зсув не перераховуються — оновиться лише те, що змінилося
насправді. Після такого `refresh` старі файли з колишніми іменами лишаться сиротами — видаліть їх і оновіть
паспорт.

**Docker не відповідає.** Не аварія: `vectors` чесно скаже, запише пошук по словах, і сервер працюватиме по
словах над найповнішим корпусом, який є. Коли Docker повернеться — `./df ecmascript vectors`, і все на місці.

## Шпаргалка

Без Qdrant (пошук по словах):

```
./df ecmascript check --deep             # що змінилося; --deep звіряє і глави 262
./df ecmascript refresh <id…>            # завантажити змінене (або без імен — усе наново)
./df ecmascript manifest                 # оновити паспорт
# Ctrl+C у терміналі з serve, і знову:
./df ecmascript serve
./df ecmascript smoke                    # червоний expected_passages — див. Крок 6
```

З Qdrant (пошук за змістом) — усе те саме плюс один крок перед перезапуском:

```
./df ecmascript check --deep
./df ecmascript refresh <id…>
./df ecmascript manifest
./df ecmascript vectors                  # дорахує лише нове й змінене
./df ecmascript status                   # «усі вектори на місці й актуальні — рахувати нічого»
# Ctrl+C у терміналі з serve, і знову:
./df ecmascript serve
./df ecmascript smoke                    # червоний expected_passages — див. Крок 6
```
