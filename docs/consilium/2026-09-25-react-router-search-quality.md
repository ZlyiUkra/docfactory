# Якість пошуку в примірнику react-router

## Узгоджена пропозиція

Примірник react-router знаходить потрібний розділ гірше за інші: на десяти контрольних питаннях по словах 6,
за змістом 6, разом 5. Мета — підняти результат найдешевшими засобами і не витрачати дні на те, що замір не
підтверджує. Робимо два кроки. Спершу прибираємо з довідника API тисячі однакових фрагментів — атрибути DOM, які
генератор розгортає в кожному інтерфейсі посилань і форм. Потім даємо пошуку за змістом бачити назву документа й
шлях заголовків, а не лише текст розділу: обидва справжні промахи мають заголовки, дослівно схожі на питання,
яких пошук за змістом сьогодні не бачить.

## Межі та обмеження

- Етап B (гігієна довідника): з документів TypeDoc вилучаються члени, оголошені в node_modules. Критерій —
  походження («Defined in node_modules»), не успадкування: члени SharedFormProps (action, method, encType)
  успадковані, але оголошені в packages/ і власної сторінки не мають. Прийнята втрата — п'ять членів опцій
  cookie, що теж лежать у node_modules.
- Етап A (контекст у пошуку): поле `passage_context` у config.json примірника. Вектори рахуються в пробну
  колекцію; відкат — один рядок конфігу, без перерахунку.
- Правило рішення для A, зафіксоване до заміру: поле лишається, якщо «разом» росте хоч на 1 і жоден стовпець
  не падає нижче базових 6/6. `fusion_depth` дописується лише за плато на сітці глибин, не за одним значенням.
- Спільний код не змінюється. Жоден крок нічого не видаляє.

## Зауваження, що вціліли

- [підтверджено] `fusion_depth` на нинішньому індексі нічого не дає; fuse 20 дає регрес 5→4 (три незалежні
  заміри).
- [підтверджено] Лексична половина `passage_context` у топ-5 дає +0; векторна — «разом» 5→6 (питання про
  browserHistory стає першим), за змістом питання про spinner просідає 4→9.
- [підтверджено] Члени TypeDoc з node_modules у топ-30 жодного з десяти питань не трапляються: етап B — гігієна
  (−16 % індексу), не якість.
- [підтверджено] Питання «loader runs on the server» і «spinner» трьома кроками не рятуються: плато — 7 із 10;
  8/10 не ціль.
- [підтверджено] Будь-яке нове звернення до GitHub мусить бути оголошене в `within`; локальний клон іде повз
  білий список.

## Позначене допитувачем

- [слабке] «Відкидати успадковані члени» — знищує єдину копію тексту SharedFormProps; замінено на критерій
  походження. Рішення користувача: прийняв заміну.
- [слабке] «Блок-перелік членів — магніт пошуку по словах» — замір не підтвердив, відкликано. Рішення
  користувача: не входить у роботу.
- [слабке] «passage_context дасть 7–8» — оптимістична оцінка без повного перерахунку. Рішення користувача:
  вирішує замір.
- [суперечить performance] Приріст від зведення переїжджених сторінок: +1 (два заміри) проти +2 (один). Рішення
  користувача: етап відкладено.

## Свідомо не робимо

- Етап C — зведення переїжджених сторінок в одне ім'я (compare API в `within`, повне перезавантаження, нові id,
  прибирання старих файлів): очікуваний +1, пів дня роботи. Відкладено за ціною часу й ресурсу.
- Злиття дрібних розділів і нижча вага experimental/nightly: виміряний нуль.
- Сильніша модель векторів, розширення цілей quality, планка 8/10.

## Маршрут виконання

- Рекомендація ради: direct-verified — зміна компактна, рішення записані у вердикті, відкат дешевий.
- Доступність speckit: не підключений.
- Рішення користувача: direct-verified; порядок B, потім A; C відкладено.
- Verification-список: після B — `smoke` з новим `expected_passages`, `quality` не нижче базового; після A —
  `quality` у пробній колекції і сітка `fusion_depth` 5–30 з набором влучань; перед комітом — `smoke`.
