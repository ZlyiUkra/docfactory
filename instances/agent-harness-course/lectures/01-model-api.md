# Лекція 1. Як програма викликає мовну модель

Лекція 0 пояснила, що модель лише пише текст, а все інше робить програма навколо неї. Ця лекція показує першу частину
такої програми: код, який надсилає запит моделі й розбирає її відповідь. У курсі цей код зібрано в одному файлі,
`harness/llm.py`. Читання займе близько 40 хвилин, а наприкінці ти напишеш подібний файл для власного агента.

**Після лекції ти зможеш пояснити:**

- що входить у запит до моделі й що повертається у відповіді;
- як один файл ховає різницю між провайдерами від решти агента;
- як порахувати ціну запиту й чому завдання на 30 кроків коштує так дорого;
- навіщо потрібен потоковий режим і як влаштований формат SSE;
- які помилки варто повторювати, які не варто й чому.

## Звідки береться проблема

Уяви, що ти написав агента для моделі Anthropic. Через місяць ти хочеш спробувати дешевшу модель іншого провайдера або
безкоштовну модель на власному комп'ютері. Виявляється, що той самий зміст там треба надсилати інакше: системний
промпт лежить в іншому місці, результат інструмента має інший формат, а кількість токенів називається іншим словом.
Якщо такі деталі розкидано по всьому коду агента, то заміна провайдера означає правки в десятках місць.

Є ще дві незручності. По-перше, кожен запуск зі справжньою моделлю коштує грошей, а модель щоразу відповідає трохи
інакше, тому тест, який очікує конкретну відповідь, то проходитиме, то ні. По-друге, провайдер іноді дає збій. Якщо в
завданні на 30 кроків 29-й запит отримає тимчасову помилку, а програма її не обробляє, то завдання обірветься, хоча за
попередні кроки вже заплачено.

Розв'язок такий: усе, що програма знає про провайдерів, зібрано в одному файлі, а решта коду звертається до нього
через один метод. На React це схоже на окремий модуль `api.ts`: компонент не знає адреси сервера, а в тестах цей
модуль легко замінити підробленим.

```text
        цикл агента (модуль 2), уроки, тести
                       |
                       |  complete(system, messages, tools, max_tokens)  ->  Reply
                       v
   +------------------ LLM ------------------+
   |                   |                     |
ScriptedLLM     OpenAICompatLLM         AnthropicLLM
записані        запит на                запит на
відповіді,      /chat/completions       /v1/messages
без мережі
```

`LLM` — це базовий клас, тобто спільний опис методів. Три класи під ним мають ті самі методи, тому цикл працює з
будь-яким із них і не знає, з яким саме. Заміну провайдера й тести без мережі файл уже забезпечує, а повтори після
збоїв курс залишив тобі як практику. Розбір читання до модуля 1 пояснює цей файл рядок за рядком, а лекція зосереджена
на механізмі.

## Що лежить у запиті

Звернення до моделі — це звичайний HTTP-запит POST із JSON у тілі. Провайдер описує, куди й що надсилати, у своєму
**API** (application programming interface, тобто домовленість про те, як одна програма звертається до іншої). На
JavaScript запит до Anthropic виглядав би так:

```js
await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: { "content-type": "application/json", "x-api-key": API_KEY, "anthropic-version": "2023-06-01" },
  body: JSON.stringify({
    model: MODEL_ID,
    max_tokens: 1024,
    system: "Відповідай одним реченням.",
    messages: [{ role: "user", content: "Що таке харнес?" }],
  }),
});
```

Курс виділяє чотири поля тіла запиту:

| Поле | Що це | Що зламається |
|------|-------|---------------|
| `system` | Системний промпт: роль і правила. Автор курсу називає його найвагомішим текстом для моделі | Правила, записані лише у звичайному повідомленні, модель може виконувати гірше |
| `messages` | Історія. Кожне повідомлення має роль: `user` (людина), `assistant` (модель) або `tool` (результат інструмента) | Деякі провайдери повертають помилку, якщо дві однакові ролі йдуть поспіль |
| `max_tokens` | Найбільша кількість токенів у відповіді моделі. Запит це поле не обмежує | Замале значення обріже відповідь, навіть посеред виклику інструмента |
| `tools` | Описи інструментів у форматі JSON Schema, тобто стандартному описі будови JSON (модуль 2) | Модель не зрозуміє, як викликати інструмент |

## Що лежить у відповіді

Відповідь містить текст, виклики інструментів, лічильники токенів і причину зупинки. Скорочені відповіді двох
провайдерів з однаковим змістом (числа умовні), спершу Anthropic, потім OpenAI:

```json
{ "content": [{ "type": "text", "text": "Харнес — це код навколо моделі." }],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 31, "output_tokens": 12 } }
```

```json
{ "choices": [{ "message": { "role": "assistant", "content": "Харнес — це код навколо моделі." },
                "finish_reason": "stop" }],
  "usage": { "prompt_tokens": 31, "completion_tokens": 12 } }
```

Поле `usage` («використання») містить справжню кількість токенів: **вхідних** (те, що ти надіслав) і **вихідних** (те,
що написала модель). За цими числами провайдер виставляє рахунок. **Причина зупинки** (stop reason) пояснює, чому
модель перестала писати:

| Що сталося | Anthropic, `stop_reason` | OpenAI, `finish_reason` |
|------------|--------------------------|-------------------------|
| Модель закінчила сама | `end_turn` | `stop` |
| Модель дійшла до межі `max_tokens` | `max_tokens` | `length` |
| Модель просить виконати інструмент | `tool_use` | `tool_calls` |

Зверни увагу на другий рядок таблиці. Обрізана відповідь приходить зі статусом HTTP 200, тому `response.ok` у
JavaScript дав би `true`. Дізнатися про обрізання можна лише з причини зупинки.

## Один формат усередині й переклад для кожного провайдера

Це головна ідея модуля. Усередині агента є один **нейтральний формат**, тобто формат, який не належить жодному
провайдеру. Цикл агента працює лише з ним. Перед відправкою метод `_to_wire` перекладає історію у формат конкретного
API (wire, буквально «дріт», тут означає «те, що йде мережею»). Коли приходить відповідь, метод `complete` перекладає
її в об'єкт `Reply`:

```python
# harness/llm.py
@dataclass
class ToolCall:
    id: str
    name: str
    arguments: dict


@dataclass
class Reply:
    text: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    input_tokens: int = 0
    output_tokens: int = 0
    stop_reason: str = "end"
```

`@dataclass` просить Python самому створити конструктор із цих полів. `ToolCall` описує один виклик інструмента: номер
`id`, за яким потім знаходять результат, назву й аргументи. `Reply` описує всю відповідь, і код поза `llm.py` читає
лише ці поля.

**Приклад із конкретними даними.** Людина питає: «Скільки буде 20+22 і 3+4?». Модель просить виконати інструмент `add`
двічі. Після виконання історія в нейтральному форматі виглядає так:

```python
messages = [
    {"role": "user", "content": "Скільки буде 20+22 і 3+4?"},
    {"role": "assistant", "content": "", "tool_calls": [
        {"id": "c1", "name": "add", "arguments": {"a": 20, "b": 22}},
        {"id": "c2", "name": "add", "arguments": {"a": 3, "b": 4}},
    ]},
    {"role": "tool", "tool_call_id": "c1", "content": "42"},
    {"role": "tool", "tool_call_id": "c2", "content": "7"},
]
```

Для OpenAI `_to_wire` додає системний промпт на початок і загортає виклики. Результати лишаються окремими
повідомленнями:

```json
[
  { "role": "system", "content": "Ти калькулятор." },
  { "role": "user", "content": "Скільки буде 20+22 і 3+4?" },
  { "role": "assistant", "content": null, "tool_calls": [
    { "id": "c1", "type": "function", "function": { "name": "add", "arguments": "{\"a\": 20, \"b\": 22}" } },
    { "id": "c2", "type": "function", "function": { "name": "add", "arguments": "{\"a\": 3, \"b\": 4}" } }
  ] },
  { "role": "tool", "tool_call_id": "c1", "content": "42" },
  { "role": "tool", "tool_call_id": "c2", "content": "7" }
]
```

Для Anthropic системний промпт іде окремим полем `system` поруч із `messages`, а обидва результати склеєно в одне
повідомлення `user`:

```json
[
  { "role": "user", "content": "Скільки буде 20+22 і 3+4?" },
  { "role": "assistant", "content": [
    { "type": "tool_use", "id": "c1", "name": "add", "input": { "a": 20, "b": 22 } },
    { "type": "tool_use", "id": "c2", "name": "add", "input": { "a": 3, "b": 4 } }
  ] },
  { "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "c1", "content": "42" },
    { "type": "tool_result", "tool_use_id": "c2", "content": "7" }
  ] }
]
```

Ось що саме файл `llm.py` ховає від решти коду:

| Що | Формат курсу | OpenAI | Anthropic |
|----|--------------|--------|-----------|
| Системний промпт | окремий аргумент | перше повідомлення з роллю `system` | окреме поле `system` |
| Виклик інструмента | `tool_calls` | `tool_calls`, усередині `function` | блок `tool_use` у `content` |
| Аргументи виклику | словник | рядок із JSON | готовий об'єкт `input` |
| Результат інструмента | роль `tool` | роль `tool` | блок `tool_result` у повідомленні `user` |
| Опис інструмента | `parameters` | `parameters`, загорнуто у `function` | `input_schema` |
| Токени | `input_tokens`, `output_tokens` | `prompt_tokens`, `completion_tokens` | `input_tokens`, `output_tokens` |
| Ключ у заголовку | немає | `authorization: Bearer ...` | `x-api-key` і `anthropic-version` |

Той самий шлях покроково для Anthropic, числа токенів умовні:

| Крок | Хто діє | Що відбувається | Що змінюється |
|------|---------|-----------------|---------------|
| 1 | Цикл агента | Викликає `llm.complete(system, messages, tools)` | у `messages` поки лише запитання |
| 2 | `_to_wire`, потім `_post` | Перекладають історію й надсилають запит POST | з'являється тіло запиту |
| 3 | Провайдер | Повертає два блоки `tool_use` і `stop_reason: tool_use` | нічого |
| 4 | `complete` | Складає `Reply("", [ToolCall("c1", ...), ToolCall("c2", ...)], 40, 30, "tool_use")` | цикл отримує `Reply` |
| 5 | Цикл агента | Викликає `reply.as_message()` і дописує результат в історію | +1 повідомлення `assistant` |
| 6 | Цикл агента | Виконує `add` двічі й дописує результати | +2 повідомлення `tool` |
| 7 | `_to_wire` | Під час наступного запиту склеює результати | у запиті 3 повідомлення, в історії 4 |

**Навіщо склеювати.** Усі результати одного кроку відповідають на одне повідомлення моделі, тому код кладе їх в одне
повідомлення `user`, і ролі чергуються правильно. Крім того, Anthropic вимагає, щоб результати йшли одразу після
повідомлення з викликами, і повертає помилку 400, якщо результату немає. Тому в модулі 2 цикл додає результат на кожен
виклик, навіть якщо інструмент завершився помилкою.

## Сценарна модель: тести без мережі

Клас `ScriptedLLM` не звертається до мережі, а повертає наперед записані відповіді. Такий клас можна назвати
**сценарною моделлю** (англійською mock, підроблений об'єкт). У тестах React те саме робить підміна `fetch`. Кожен
виклик клас записує в поле `calls`, тому тест може перевірити, що саме модель «бачила». Коли записані відповіді
закінчилися, клас видає помилку `LLMError`, і тест одразу показує, що цикл зробив зайвий виклик.

Цей прийом варто перенести до себе першим, бо завдяки йому цикл, компакцію й дозволи можна перевіряти безкоштовно,
швидко й з однаковим результатом. Сценарна модель не перевірить двох речей: чи вибере справжня модель правильний
інструмент і чи прийме справжній провайдер твій запит.

## Що робить урок

Запусти урок командою `python3 examples/01_hello_llm.py`. Без ключа він працює на сценарній моделі й робить три речі:
один звичайний виклик, один виклик у потоковому режимі й підрахунок ціни першого виклику. Вивід нижче ми отримали з
коду уроку, а не із запуску, тому звір його зі своїм:

```text
Провайдер: scripted

Ответ: Харнес — это всё, что окружает модель: цикл, инструменты, контекст, память и интерфейс.
Токены: вход 31, выход 21

Стрим: Модель — двигатель. Харнес — машина вокруг него: руль, колёса, тормоза и навигатор.

Стоимость первого вызова ≈ $0.000408
Заметь: каждый следующий вызов платит за ВСЮ историю заново — поэтому контекст надо беречь.
```

Числа токенів тут не справжні. Сценарна модель оцінила їх функцією `approx_tokens`, яка ділить кількість символів на 4
і відкидає остачу. Системний промпт уроку має 69 символів і дає 17 токенів, повідомлення людини, записане як JSON, має
57 символів і дає 14 токенів, разом на вході 31. Записана відповідь має 87 символів і дає 21 токен на виході.

## Скільки коштує запит

Ціну рахує формула з уроку. Провайдери вказують ціну за мільйон токенів, а `1e6` у коді означає 1 000 000:

```python
# examples/01_hello_llm.py
price_in, price_out = 3.0, 15.0
cost = r.input_tokens / 1e6 * price_in + r.output_tokens / 1e6 * price_out
```

Тут $3 і $15 — умовні ціни для прикладу, а справжні треба дивитися на сторінці провайдера. Для уроку виходить таке: 31
/ 1 000 000 × 3 + 21 / 1 000 000 × 15 = 0,000093 + 0,000315 = **$0,000408**.

**Ціна — це метрика, про яку часто забувають.** Лекція 0 показала, що кожен запит містить усю історію. Приклад курсу:
завдання на 30 кроків, історія 20 000 токенів. Для простоти вважатимемо, що довжина історії не змінюється, а кожна
відповідь має 200 токенів.

| Що | Токенів за завдання | Ціна за умовними тарифами |
|----|---------------------|---------------------------|
| Вхідні | 30 × 20 000 = 600 000 | 0,6 × $3 = $1,80 |
| Вихідні | 30 × 200 = 6 000 | 0,006 × $15 = $0,09 |

Вихідний токен тут у п'ять разів дорожчий за вхідний, але основні гроші йдуть на вхідні токени, бо ту саму історію
надсилають 30 разів. Звідси три способи заощадити: **кешування промптів**, **компакція**, тобто заміна старої історії
коротким зведенням (модуль 3), і **дешевші моделі** для простих підзавдань (модуль 5).

**Кешування промптів** (prompt caching) працює так: провайдер запам'ятовує незмінний початок запиту, який називають
**префіксом**, і наступний запит із таким самим початком коштує набагато дешевше. В Anthropic станом на листопад 2026
року запис у кеш, який живе 5 хвилин, коштує 1,25 ціни звичайного вхідного токена, а читання зазвичай 0,1 ціни. Для
деяких моделей читання ще дешевше, тому перевір сторінку `Prompt caching` у примірнику `anthropic-api`.

Порахуймо найкращий випадок, коли вся історія незмінна. Перший запит записує 20 000 токенів за $3,75 за мільйон, тобто
$0,075. Решта 29 запитів читають 580 000 токенів за $0,30 за мільйон, тобто $0,174. Разом близько $0,25 замість $1,80,
тобто економія близько 86 %. Насправді вона буде меншою: історія росте, тому кожен новий шматок записується за вищою
ціною, кеш зникає після 5 хвилин без використання, а замалий префікс не кешується взагалі.

## Потоковий режим і SSE

Без потокового режиму програма чекає, поки модель допише відповідь повністю, і весь цей час людина бачить порожній
екран. У **потоковому режимі** (streaming, у курсі «стриминг») провайдер надсилає відповідь частинами, щойно вони
з'являються. Автор курсу наголошує, що цей режим потрібен не для швидкості, а для зручності людини: вона бачить, що
агент працює. Раніше з'являться лише перші слова, а повна відповідь не прийде раніше.

Частини передаються у форматі **SSE** (Server-Sent Events, «події, які надсилає сервер»). Це звичайна HTTP-відповідь,
яка довго не закривається. Сервер дописує до неї текстові рядки, кожна подія починається з `data:`, а події розділені
порожнім рядком. У браузері такий формат читає `EventSource`, але він уміє лише GET. Тут потрібен POST із тілом, тому
програма читає відповідь сама, як у JavaScript через `fetch` і `getReader`. Так виглядає потік у форматі OpenAI,
приклад узято з тесту курсу:

```text
data: {"choices": [{"delta": {"content": "При"}}]}

data: {"choices": [{"delta": {"content": "вет"}}]}

data: [DONE]
```

Метод `stream_text` перебирає такий потік рядок за рядком, пропускає рядки без `data:`, зупиняється на `[DONE]`, а
текст кожної події віддає через `yield`. Слово `yield` передає один шматок тому, хто перебирає функцію, і призупиняє
її до наступного шматка, як `function*` у JavaScript. Рядок за рядком цей метод пояснює розбір читання.

`stream_text` вміє менше за `complete`: він не приймає інструментів і не читає `usage`. Тому цикл агента користується
лише `complete`, а урок рахує ціну лише першого виклику: для потокового виклику код не знає кількості токенів.

## Помилки: що можна повторювати

Усі HTTP-запити в курсі проходять через одну функцію:

```python
# harness/llm.py
def _post(url: str, headers: dict, body: dict, timeout: int = 120):
    req = urllib.request.Request(url, data=json.dumps(body).encode(), method="POST",
                                 headers={"content-type": "application/json", **headers})
    try:
        return urllib.request.urlopen(req, timeout=timeout)
    except urllib.error.HTTPError as e:
        detail = e.read().decode(errors="replace")[:500]
        raise LLMError(f"HTTP {e.code} от {url}: {detail}") from e
```

Перша інструкція готує запит: перетворює тіло на JSON, потім на байти, і додає заголовки. Функція `urlopen` надсилає
запит і повертає відповідь. На відміну від `fetch`, вона сама видає помилку, якщо код відповіді 4xx чи 5xx. Блок
`except` читає перші 500 символів відповіді сервера й видає помилку `LLMError`.

Повторів тут немає: перша ж помилка зупиняє всю роботу, бо цикл `run_agent` не перехоплює `LLMError`. Повтор ти
допишеш сам, і головне в ньому — вибрати, що повторювати. Запитай себе: чи може наступна спроба дати інший результат?

| Код відповіді | Що означає | Чи повторювати | Що робити |
|---------------|------------|----------------|-----------|
| 400 | Сам запит неправильний, наприклад на виклик інструмента немає результату | ні | виправити запит |
| 401, 403, 404 | Ключ хибний, немає прав або такої моделі не існує | ні | перевірити ключ, `LLM_BASE_URL` і назву моделі |
| 413 | Запит завеликий | ні | скоротити історію (модуль 3) |
| 429 | Перевищено межу запитів або токенів за хвилину | так | зачекати й повторити |
| 5xx, зокрема 529 в Anthropic | Збій або перевантаження в провайдера | так | зачекати й повторити |

Помилку 400 марно повторювати, бо провайдер отримає ті самі байти й дасть ту саму відповідь. Натомість 429 і 5xx
описують тимчасовий стан сервера, який за кілька секунд може змінитися.

**Як робити паузу.** Пауза між спробами має рости, щоб не навантажувати сервер, якому вже важко. Такий спосіб
називають **експоненційною затримкою** (exponential backoff): кожна пауза вдвічі більша за попередню. До неї додають
**випадкову добавку** (jitter, у курсі «джиттер»). Вона потрібна ось чому: якщо сто клієнтів отримали помилку в ту
саму мить і всі чекають рівно 1 секунду, то сервер отримає сто запитів одночасно знову, а з випадковою добавкою ці
запити надійдуть у різний час. Паузи можуть бути такими: 1,37 с, 2,81 с, 4,12 с, 8,55 с, а після п'ятої невдалої
спроби код видає `LLMError`.

Кількість спроб має бути обмеженою. В Anthropic є випадок помилки 429, коли вичерпано місячну межу витрат: заголовка
`retry-after` у відповіді немає, і повтори не допоможуть, доки доступ не відновиться. Якщо сервер усе ж надіслав
`retry-after`, зачекай саме стільки, скільки вказано в цьому заголовку.

## Вибір провайдера: змінні оточення

Код агента не повинен знати назву моделі чи ключ. **Ключ** — це секретний рядок, за яким провайдер визначає, кому
виставити рахунок. Функція `from_env` читає обидва значення зі **змінних оточення**, тобто значень, які задаються поза
програмою. У Node це `process.env`. Завдяки цьому ключ не потрапляє в код і в git.

```bash
LLM_PROVIDER=anthropic LLM_MODEL=<id моделі> LLM_API_KEY=... python3 examples/01_hello_llm.py
LLM_PROVIDER=openai LLM_BASE_URL=http://localhost:11434/v1 LLM_MODEL=<модель в Ollama> python3 examples/01_hello_llm.py
```

Назва `openai` тут означає формат, а не компанію: у другому рядку працює Ollama на твоєму комп'ютері, і ключ їй не
потрібен. Якщо `LLM_PROVIDER` не задано, `from_env` повертає сценарну модель, яку отримала аргументом.

## Типові хибні уявлення

**«Код 200 означає, що відповідь повна».** Код 200 каже лише, що запит оброблено. Відповідь, обрізана межею
`max_tokens`, теж приходить із кодом 200. Про обрізання каже тільки причина зупинки.

**«Потоковий режим робить модель швидшою».** Модель пише з тією самою швидкістю, а людина лише раніше бачить перші
слова.

**«`approx_tokens` покаже, що російський текст дорожчий».** Ця функція рахує лише символи. Запитання «Что такое
агентный харнес?» (26 символів) і «What is an agent harness?» (25 символів) вона оцінить однаково, по 6 токенів.
Різницю покаже лише `usage` справжнього провайдера, тому порівняти мови на сценарній моделі неможливо.

**«OpenAI-сумісний означає, що все працює однаково».** Сумісний сервер приймає той самий формат запиту, але його
можливості можуть бути меншими. Автор курсу попереджає, що маленькі локальні моделі помітно гірше викликають
інструменти.

## Практика: твій власний `llm.py`

**1. Запусти урок на двох провайдерах,** наприклад на хмарній моделі й на локальній через Ollama. Ключ задавай лише
змінною оточення й нікуди не вставляй його значення.

**2. Напиши `llm.py` з порожнього файла.** Закрий файл курсу й пиши в такому порядку, бо кожен крок спирається на
попередній:

1. Опиши нейтральний формат: `ToolCall`, `Reply` і метод `as_message`.
2. Напиши базовий клас і `ScriptedLLM` разом із першим тестом, який перевіряє відповідь і запис у `calls`.
3. Напиши один справжній провайдер: `_post`, `_to_wire`, `complete`.
4. Напиши другий провайдер і перевір, що той самий код викликає обидва.
5. Додай `from_env`. Ключ і назва моделі мають надходити лише зі змінних оточення.

**3. Порівняй мови.** Надішли той самий запит російською та англійською. Для кожної мови запиши кількість символів,
поля `usage`, ціну й кількість символів на токен. Можеш додати й українську: лекція 0 обіцяла, що ти виміряєш її сам.

**4. Допиши повтор.** Це завдання курсу. Повторюй лише 429 і 5xx, збільшуй паузу вдвічі, додавай випадкову добавку й
обмеж кількість спроб. Спершу спробуй сам, а потім порівняй свій код із варіантом нижче.

<details><summary>Один із можливих варіантів</summary>

Треба додати `import random` і `import time`. Цей варіант ще не враховує `retry-after` і мережеві збої: це наступні
кроки.

```python
def _post(url: str, headers: dict, body: dict, timeout: int = 120, attempts: int = 5):
    req = urllib.request.Request(url, data=json.dumps(body).encode(), method="POST",
                                 headers={"content-type": "application/json", **headers})
    for attempt in range(attempts):
        try:
            return urllib.request.urlopen(req, timeout=timeout)
        except urllib.error.HTTPError as e:
            detail = e.read().decode(errors="replace")[:500]
            can_retry = e.code == 429 or e.code >= 500
            if not can_retry or attempt == attempts - 1:
                raise LLMError(f"HTTP {e.code} от {url}: {detail}") from e
            time.sleep(2 ** attempt + random.random())
```

</details>

## Межі коду курсу

Код курсу навчальний, тому деяких речей у ньому немає. Ось що варто знати й перевірити.

**Повторів немає.** Функція `_post` видає `LLMError` уже на першій відповіді з кодом 429 чи 5xx, а цикл цю помилку не
перехоплює. Курс сам просить дописати повтори: 429 і 5xx так, 400 ні, із затримкою, що подвоюється, і випадковою
добавкою. Перевір так: запусти локальний сервер, який двічі відповідає 429, а потім 200, і подивись, що твій код
робить дві паузи й отримує відповідь. Врахуй ще одне: якщо сервер не відповів зовсім (наприклад, Ollama не запущена),
вийде інша помилка, `URLError`, і її теж треба обробити окремо.

**Кешування промпта лише згадане в тексті курсу, а в коді його немає.** У `llm.py` немає поля `cache_control`, яке
вмикає кеш в Anthropic. Подивись сторінки про кешування в `anthropic-api` і оціни, скільки воно заощадить на тих 600
тисячах токенів: найкращий випадок ми порахували вище, а тепер порахуй для історії, яка росте. Якщо ввімкнеш кеш,
зміни й підрахунок ціни, бо в Anthropic поле `input_tokens` не містить токенів із кешу. Вони приходять окремо в полях
`cache_creation_input_tokens` і `cache_read_input_tokens`.

**`approx_tokens` — лише приблизна оцінка.** Її власний опис попереджає, що для російського тексту вона занижає
результат приблизно в 1,5–2 рази. Справжнє число приходить лише в полі `usage` відповіді. Перевір сам: порівняй оцінку
з `usage` для одного російського запиту. Це важливо для модуля 3, бо там ця оцінка вирішує, коли скорочувати історію.

**Причину зупинки ніхто не читає.** Поле `Reply.stop_reason` зберігає значення провайдера без перекладу, тому в ньому
може бути `end_turn`, `stop` або `end`. Цикл `run_agent` це поле не перевіряє. Якщо відповідь без виклику інструмента
обрізано межею `max_tokens`, цикл вважатиме завдання виконаним. У своєму агенті зведи значення до спільних слів і
реагуй на обрізання.

**`stream_text` бачить лише текст.** Він не читає токени, хоча провайдери вміють їх надсилати. Крім того, після коду
200 Anthropic може надіслати в потоці подію `error`, а код курсу її пропускає. Людина побачить відповідь, що раптом
закінчилася без пояснень.

**Блоки міркувань втрачаються.** Нові моделі Anthropic міркують перед відповіддю й повертають окремі блоки `thinking`.
Код курсу бере лише блоки `text` і `tool_use`, а документація Anthropic вимагає повертати блоки міркувань разом із
результатами інструментів. Якщо в модулі 2 побачиш помилку 400 про `thinking`, почни пошук звідси.

## Перевір себе

Спершу дай відповідь сам, а потім розгортай пояснення.

**1. Що станеться, якщо `max_tokens` замало, а модель саме пише виклик інструмента?**

<details><summary>Відповідь</summary>

Відповідь обірветься посеред аргументів. У клієнті для OpenAI обрізаний JSON не вдасться розібрати, тому код покладе
сирий рядок в аргумент `__invalid_json__`. Потім `validate_args` поверне текст помилки, і модель отримає його як
результат інструмента. Модель спробує ще раз, але з тією самою межею може обірватися знову, і так аж до межі кроків
`max_steps`. Причина зупинки при цьому буде `length`, але цикл її не читає. Допоможе більше значення `max_tokens`, а
виявити проблему можна перевіркою причини зупинки.

</details>

**2. Чому помилку 400 не можна повторювати?**

<details><summary>Відповідь</summary>

Код 400 означає, що неправильний сам запит. Повтор надішле ті самі байти й отримає ту саму відповідь, лише витратить
час. Треба виправити запит, наприклад додати пропущений результат інструмента.

</details>

**3. Ти переходиш з Anthropic на локальну модель через Ollama. Що доведеться змінити в циклі агента й чому?**

<details><summary>Відповідь</summary>

Нічого. Цикл викликає лише `complete` і читає лише `Reply`. Зміняться змінні оточення: `LLM_PROVIDER=openai`,
`LLM_BASE_URL` і `LLM_MODEL`. Уся різниця у форматах лежить усередині класів `OpenAICompatLLM` і `AnthropicLLM`.
Якість відповідей при цьому може змінитися, бо модель інша.

</details>

**4. У `usage` прийшло 12 000 вхідних і 800 вихідних токенів, а ціни становлять $3 і $15 за мільйон. Скільки коштує
запит?**

<details><summary>Відповідь</summary>

12 000 / 1 000 000 × 3 = $0,036 за вхід і 800 / 1 000 000 × 15 = $0,012 за вихід. Разом $0,048.

</details>

**5. Навіщо потрібен потоковий режим і як влаштований SSE?**

<details><summary>Відповідь</summary>

Він потрібен для зручності людини: вона бачить перші слова раніше й розуміє, що агент працює. Повна відповідь не
приходить швидше. SSE — це HTTP-відповідь, яка довго не закривається: сервер дописує до неї рядки `data: ...`,
розділені порожнім рядком, а програма читає їх один за одним і розбирає JSON у кожному.

</details>

**6. Які з цих відповідей твій повтор має повторювати: 400, 401, 429, 503? Навіщо потрібна випадкова добавка?**

<details><summary>Відповідь</summary>

Лише 429 і 503, бо вони описують тимчасовий стан сервера. Коди 400 і 401 означають помилку в запиті чи ключі, і повтор
нічого не змінить. Випадкова добавка потрібна, щоб клієнти, які отримали помилку одночасно, не надіслали новий запит
теж одночасно.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| API | домовленість про те, як одна програма звертається до іншої; тут адреса й формат запитів до провайдера |
| `usage` | лічильники вхідних і вихідних токенів у відповіді провайдера |
| причина зупинки, `stop_reason` | чому модель перестала писати: закінчила, дійшла до межі чи просить інструмент |
| нейтральний формат | внутрішній формат повідомлень, який не належить жодному провайдеру |
| сценарна модель, mock | підроблена модель із наперед записаними відповідями |
| кешування промптів, prompt caching | дешевша повторна обробка незмінного початку запиту |
| потоковий режим, streaming | відповідь частинами, щойно вони з'являються |
| SSE, Server-Sent Events | формат передавання подій сервера в довгій HTTP-відповіді |
| експоненційна затримка, exponential backoff | повтор із паузою, яка щоразу подвоюється |
| випадкова добавка, jitter | випадкова частка паузи, через яку повтори різних клієнтів надходять у різний час |
