**Схема в тексті модуля.** Курс показує обмін повідомленнями діаграмою послідовності. На ній четверо учасників:
«Пользователь» (людина), «Харнес», «Модель» та «Инструменты». Послідовність така:

1. Людина дає харнесу завдання.
2. Поки у відповіді є виклики інструментів, повторюється таке: харнес надсилає моделі системний промпт, історію й

   інструмент, отримує результат чи текст помилки й дописує його в історію.
3. Коли викликів більше немає, харнес віддає людині фінальну відповідь.

### Початок файла: опис та імпорти

```python
"""Агентный цикл — сердце любого харнеса.

    while True:
        ответ = модель(система, история, инструменты)
        если в ответе нет вызовов инструментов → готово
        выполнить инструменты → добавить результаты в историю → повторить

Всё остальное в харнесе (компакция, память, субагенты, UI) — обвязка вокруг этих 5 строк.
"""
from __future__ import annotations

import json
import time
from dataclasses import dataclass, field
from typing import Callable

from .llm import LLM, Reply
from .tools import Tool, validate_args
```

- **Рядок у потрійних лапках** на початку файла називають docstring. Це вбудований опис модуля, приблизно те саме, що
  коментар JSDoc на початку файла. Він каже, що цикл складається з кількох рядків псевдокоду, а все інше в харнесі
  лише доповнює його.
- **`from __future__ import annotations`** змінює роботу анотацій типів: Python більше не обчислює їх під час запуску,
  а зберігає як текст. У TypeScript типи теж не існують під час виконання, тому ідея схожа. Завдяки цьому можна писати
  сучасні записи на кшталт `list[Tool] | None`, не турбуючись про порядок оголошень. Наслідок цього рядка ти побачиш у
  `tools.py`, де для читання типів потрібна окрема функція.
- **`import json`** підключає модуль зі стандартної бібліотеки. Функція `json.dumps` тут виконує роботу
  `JSON.stringify`.
- **`import time`** підключає модуль часу. Функція `time.time()` повертає секунди як дробове число, тобто приблизно
  `Date.now() / 1000`.
- **`from dataclasses import dataclass, field`** означає те саме, що `import { dataclass, field } from "dataclasses"`.
- **`from .llm import LLM, Reply`** має крапку на початку, і вона означає «з цієї самої теки». У JavaScript це
  `from "./llm"`. Класи `LLM` і `Reply` описано в модулі 1: `LLM` є спільним інтерфейсом до провайдера, а `Reply` є
  відповіддю моделі.

### Клас `Usage`

```python
@dataclass
class Usage:
    input_tokens: int = 0
    output_tokens: int = 0
    model_calls: int = 0
    tool_calls: int = 0

    def add(self, r: Reply):
        self.input_tokens += r.input_tokens
        self.output_tokens += r.output_tokens
        self.model_calls += 1

    def cost(self, usd_per_mtok_in: float, usd_per_mtok_out: float) -> float:
        return self.input_tokens / 1e6 * usd_per_mtok_in + self.output_tokens / 1e6 * usd_per_mtok_out
```

Клас рахує, скільки коштував один запуск `run_agent`.

- **`@dataclass`** є декоратором, тобто записом із `@`, який отримує клас чи функцію й змінює їх. Цей декоратор читає
  перелік полів класу й сам створює конструктор, текстове подання для друку й порівняння. У TypeScript найближче до
  цього `class Usage { constructor(public inputTokens = 0, public outputTokens = 0) {} }`. Тому `Usage()` створює
  об'єкт із чотирма нулями.
- **`input_tokens: int = 0`** оголошує поле: назва, тип і типове значення.
- **`def add(self, r: Reply):`** оголошує метод. Параметр `self` означає те саме, що `this` у JavaScript, але в Python
  його пишуть у підписі явно, а під час виклику `usage.add(reply)` Python підставляє його сам. Метод додає токени з
  однієї відповіді й рахує виклик моделі.
- Поле `tool_calls` цей метод не змінює. Його збільшує сам цикл, бо в одній відповіді може бути кілька викликів, і
  рахувати їх зручно там, де їх виконують.
- **`cost`** рахує ціну. Запис `1e6` є числом 1 000 000, а скорочення `mtok` означає мільйон токенів, бо провайдери
  вказують ціну саме за мільйон. Наприклад, повний прогін з лекції дав 611 вхідних і 113 вихідних токенів за оцінкою.
  За умовних цін 3 і 15 доларів за мільйон вийде 611 / 1 000 000 × 3 + 113 / 1 000 000 × 15, тобто приблизно 0,0035
  долара.

### Клас `RunResult`

```python
@dataclass
class RunResult:
    text: str
    messages: list[dict]
    usage: Usage
    steps: int
    stopped_by: str  # "done" | "max_steps" | "terminated"
    tool_log: list[dict] = field(default_factory=list)
```

Цей клас описує, що повертає цикл: підсумковий текст, усю історію, витрати, кількість кроків, причину завершення й
журнал викликів.

- **`list[dict]`** означає список словників. Словник (`dict`) у Python приблизно відповідає звичайному об'єкту
  JavaScript. У TypeScript цей тип виглядав би як `Record<string, any>[]`.
- **`stopped_by: str`** має коментар із трьома значеннями. У TypeScript тут був би тип-об'єднання
  `"done" | "max_steps" | "terminated"`, а в Python це лише домовленість, і мова її не перевіряє.
- **`field(default_factory=list)`** каже: кожному новому об'єкту створи власний порожній список. Запис
  `tool_log: list = []` тут не підійшов би, бо в Python типове значення поля обчислюється один раз, і один список став
  би спільним для всіх об'єктів. Декоратор `@dataclass` навіть забороняє такий запис і видає помилку.
- Поле з типовим значенням стоїть останнім, бо в Python поля без типового значення не можуть іти після полів, які його
  мають. Це таке саме правило, як для параметрів функції.

### Функція `default_events`

```python
def default_events(kind: str, data: dict):
    if kind == "tool_call":
        print(f"  🔧 {data['name']}({json.dumps(data['arguments'], ensure_ascii=False)[:120]})")
    elif kind == "tool_result":
        preview = data["content"].replace("\n", " ")[:120]
        print(f"  ↳ {preview}")
    elif kind == "assistant" and data["text"]:
        print(f"🤖 {data['text']}")
```

Цикл повідомляє про кожну подію через функцію `on_event`, а ця функція є її типовим значенням і друкує події в
термінал. Так цикл не залежить від способу показу: вебінтерфейс передасть свою функцію, а тести передають порожню
`lambda k, d: None`, щоб нічого не друкувати. Запис `lambda k, d: None` означає те саме, що `(k, d) => null` у
JavaScript.

- **`f"…{вираз}…"`** називають f-рядком. Це те саме, що шаблонний рядок `` `…${вираз}…` `` у JavaScript.
- **`ensure_ascii=False`** залишає кирилицю як є. Без нього `json.dumps` замінив би кожну кириличну літеру на запис на
  кшталт `а`.
- **`[:120]`** бере перші 120 символів, як `.slice(0, 120)` у JavaScript. Якщо рядок коротший, помилки не буде.
  Обрізання стосується лише друку: в історію і журнал іде повний текст.
- **`.replace("\n", " ")`** замінює всі переноси рядків на пропуски, щоб результат зайняв один рядок термінала. Зверни
  увагу на різницю: у Python `replace` замінює всі входження, а в JavaScript `replace` із рядком замінює лише перше.
- **`elif`** є скороченням від `else if`.
- **`and data["text"]`** не дає надрукувати порожній текст, бо порожній рядок у Python хибний, як і в JavaScript. Тому
  на кроці 2 прогону з лекції немає рядка з текстом моделі.

### Функція `ask_in_terminal`

```python
def ask_in_terminal(t: Tool, args: dict) -> bool:
    ans = input(f"⚠️  Агент хочет вызвать {t.name}({json.dumps(args, ensure_ascii=False)[:200]}). Разрешить? [y/N] ")
    return ans.strip().lower() in {"y", "yes", "д", "да"}
```

Ця функція питає людину, чи можна виконати небезпечний інструмент. Вона є типовим значенням параметра `approve` у
`run_agent`.

- **`input(…)`** друкує запитання й зупиняє програму, доки людина не введе рядок. Найближче в Node.js є
  `readline.question`, але `input` не асинхронний.
- **`.strip().lower()`** відповідає `.trim().toLowerCase()`.
- **`{"y", "yes", "д", "да"}`** є множиною (set), а `x in множина` перевіряє, чи є там значення. У JavaScript це
  `new Set([...]).has(x)`.
- **`[y/N]`**: велика літера за домовленістю показує типову відповідь. Дозволом вважаються лише чотири слова, а все
  інше, зокрема порожній Enter, означає відмову. Це безпечний вибір: помилка в написанні дає заборону, а не дозвіл.

**Крайній випадок.** Якщо програма працює без термінала, наприклад на сервері, виклик `input` викине `EOFError`.
Функція `_execute` цього винятку не перехоплює, бо виклик `approve` стоїть поза її блоком `try`. Тому на сервері
потрібно передавати власну функцію `approve`.

### Функція `run_agent`: підпис

```python
def run_agent(
    llm: LLM,
    system: str,
    messages: list[dict],
    tools: list[Tool] | None = None,
    *,
    max_steps: int = 20,
    on_event: Callable[[str, dict], None] = default_events,
    approve: Callable[[Tool, dict], bool] = ask_in_terminal,
    client_handler: Callable[[Tool, dict], str] | None = None,
    before_model_call: Callable[[list[dict]], list[dict]] | None = None,
    max_tokens: int = 1024,
) -> RunResult:
    """Запускает цикл. messages изменяется на месте — это и есть транскрипт.

    before_model_call — хук перед каждым вызовом модели (сюда подключают компакцию).
    client_handler   — исполнитель client_side-инструментов (вопрос человеку, UI-квиз).
    """
```

- **`list[Tool] | None`** означає те саме, що `Tool[] | null` у TypeScript. Значення `None` у Python є відповідником
  `null`.
- **Зірочка `*`** ділить параметри на дві групи. Усі параметри після неї можна передавати лише за назвою:
  `run_agent(llm, s, m, t, max_steps=10)`. У TypeScript подібне роблять об'єктом налаштувань:
  `runAgent(llm, s, m, t, { maxSteps: 10 })`. Завдяки цьому виклик легко читати, і параметри не можна переплутати за
  порядком.
- **`Callable[[str, dict], None]`** описує функцію. У TypeScript це `(kind: string, data: object) => void`.
- **`max_steps`** обмежує кількість кроків циклу, а **`max_tokens`** обмежує довжину однієї відповіді моделі. Назви
  схожі, але це різні обмеження.
- **`approve`** вирішує, чи можна виконати небезпечний інструмент. Тести передають сюди `lambda t, a: False`, щоб
  завжди відмовляти.
- **`client_handler`** виконує інструменти, які працюють поза програмою агента, наприклад запитання до людини чи
  вікторину в інтерфейсі.
- **`before_model_call`** є хуком, який викликається перед кожним зверненням до моделі. Сюди модуль 3 підключить
  компакцію.

Опис функції каже головне про `messages`: цикл змінює цей список на місці, і цей список є транскриптом, тобто повним
записом розмови. Той, хто викликав функцію, бачить зміни у своєму списку, навіть якщо функція не повернула результату
через виняток.

### Функція `run_agent`: підготовка

```python
    tools = tools or []
    by_name = {t.name: t for t in tools}
    usage, tool_log = Usage(), []
```

- **`tools or []`** означає: якщо `tools` порожнє чи `None`, візьми порожній список. У JavaScript це `tools || []`.
- **`{t.name: t for t in tools}`** називають словниковим виразом (dict comprehension). Він будує словник «назва →
  інструмент». У JavaScript це `Object.fromEntries(tools.map(t => [t.name, t]))`. Такий словник потрібен, щоб за
  назвою з відповіді моделі швидко знайти інструмент.
- **`usage, tool_log = Usage(), []`** присвоює два значення за раз. У JavaScript це
  `const [usage, toolLog] = [new Usage(), []]`. Зверни увагу, що об'єкт створюється викликом класу без слова `new`.

Важливий наслідок: `usage` і `tool_log` є локальними змінними. Якщо функція завершиться винятком, вони пропадуть, бо
вона не встигне повернути їх у `RunResult`.

### Функція `run_agent`: виклик моделі

```python
    for step in range(1, max_steps + 1):
        if before_model_call:
            messages[:] = before_model_call(messages)

        reply = llm.complete(system, messages, [t.schema() for t in tools] or None, max_tokens)
        usage.add(reply)
        messages.append(reply.as_message())
        on_event("assistant", {"text": reply.text, "step": step})

        if not reply.tool_calls:
            return RunResult(reply.text, messages, usage, step, "done", tool_log)
```

- **`for step in range(1, max_steps + 1)`** перебирає числа від 1 до `max_steps` включно, бо верхня межа в `range` не
  входить. У JavaScript це `for (let step = 1; step <= maxSteps; step++)`.
- **`if before_model_call:`** перевіряє, чи передано хук. Значення `None` хибне, тому без хука рядок нижче не
  виконається.
- **`messages[:] = …`** замінює вміст того самого списку. Запис `messages[:]` означає «усі елементи списку». Різницю
  показує такий приклад:

  ```python
  a = [1, 2]
  b = a          # b і a вказують на той самий список
  a[:] = [9]     # змінюємо вміст списку
  print(b)       # [9]: b бачить зміну
  a = [7]        # a тепер вказує на новий список
  print(b)       # [9]: b про це не знає
  ```

  Якби в коді стояло `messages = before_model_call(messages)`, той, хто викликав `run_agent`, після компакції лишився
  б зі старою довгою історією.
- **`llm.complete(…)`** надсилає запит провайдеру й повертає об'єкт `Reply`. Модель отримує чотири речі: системний
  промпт, історію, схеми інструментів і обмеження довжини. Цей виклик не стоїть у `try`, тому будь-яка його помилка
  виходить із `run_agent` назовні.
- **`[t.schema() for t in tools]`** називають списковим виразом (list comprehension). У JavaScript це
  `tools.map(t => t.schema())`.
- **`… or None`**: порожній список у Python хибний, тому без інструментів передається `None`. Тут є відмінність від
  JavaScript, де порожній масив істинний і `[] || null` повертає `[]`. Обидва провайдери курсу додають поле `tools` у
  запит лише тоді, коли воно непорожнє.
- **`usage.add(reply)`** додає витрати цієї відповіді до лічильника.
- **`messages.append(…)`** дописує елемент у кінець списку, як `push` у JavaScript. Метод `as_message` перетворює
  `Reply` на словник `{"role": "assistant", "content": текст}` і додає поле `tool_calls`, лише якщо виклики є. Цей
  рядок стоїть до виконання інструментів, і чому це важливо, пояснює лекція 2.
- **`on_event("assistant", …)`** повідомляє про нову відповідь. Типова функція надрукує її текст.
- **`if not reply.tool_calls:`** перевіряє, чи порожній список викликів. Тут знову відмінність від JavaScript:
  `not []` у Python дає `True`, тоді як `![]` у JavaScript дає `false`, і там довелося б перевіряти `.length`.
- **`return RunResult(…)`** завершує роботу. Аргументи йдуть у порядку полів класу: `text`, `messages`, `usage`,
  `steps`, `stopped_by`, `tool_log`.

**Спробуй передбачити.** Модель повернула `Reply("")` без тексту й без викликів. Що поверне `run_agent`?

<details><summary>Відповідь</summary>

`RunResult` зі `stopped_by="done"` і порожнім `text`. Цикл перевіряє лише наявність викликів, тому порожня відповідь
теж вважається нормальним завершенням. У своєму агенті такий випадок варто обробити окремо.

</details>

### Функція `run_agent`: виконання викликів

```python
        # Модель может попросить несколько инструментов сразу. На КАЖДЫЙ вызов
        # обязательно должен быть ответ, иначе следующий запрос к API упадёт.
        terminate = False
        for call in reply.tool_calls:
            on_event("tool_call", {"name": call.name, "arguments": call.arguments})
            started = time.time()
            content = _execute(call.name, call.arguments, by_name, approve, client_handler)
            usage.tool_calls += 1
            tool_log.append({"name": call.name, "arguments": call.arguments, "result": content,
                             "ms": round((time.time() - started) * 1000)})
            messages.append({"role": "tool", "tool_call_id": call.id, "content": content})
            on_event("tool_result", {"name": call.name, "content": content})
            t = by_name.get(call.name)
            if t and t.terminates and not content.startswith(("ОШИБКА", "ОТКАЗАНО")):
                terminate = True

        if terminate:  # например, probe_done: ход переходит к другому агенту
            return RunResult(reply.text, messages, usage, step, "terminated", tool_log)
```

Коментар на початку повторює перше правило циклу: кожен виклик має отримати відповідь.

- **`for call in reply.tool_calls`** перебирає виклики по одному, як `for (const call of …)` у JavaScript. Кожен
  `call` є об'єктом `ToolCall` із модуля 1 і має поля `id`, `name` та `arguments`. Виконання йде по черзі, і наступний
  виклик чекає завершення попереднього.
- **`started = time.time()`** запам'ятовує час початку. Рядок `round((time.time() - started) * 1000)` дає тривалість у
  цілих мілісекундах. Сюди входить і час, поки людина думала над дозволом, бо запитання стоїть усередині `_execute`.
- **`content = _execute(…)`** завжди дає текст, тому далі цикл працює однаково для успіху й для невдачі.
- **`usage.tool_calls += 1`** рахує всі виклики, зокрема невдалі й заборонені. Вони теж коштували кроку.
- **`tool_log.append({…})`** записує траєкторію: назву, аргументи, результат і час. Це п'яте правило циклу.
- **`messages.append({"role": "tool", …})`** дописує результат в історію. Поле `tool_call_id` містить той самий номер,
  що й виклик.
- **`by_name.get(call.name)`** шукає інструмент ще раз, бо `_execute` повернула лише текст. Метод `.get` повертає
  `None`, якщо ключа немає. Запис `by_name[call.name]` у такому разі викинув би виняток `KeyError`, бо словник Python
  поводиться інакше, ніж об'єкт JavaScript, який повернув би `undefined`.
- **`content.startswith(("ОШИБКА", "ОТКАЗАНО"))`** приймає кортеж (tuple, незмінний список у круглих дужках) і
  повертає `True`, якщо текст починається з будь-якого з цих слів. У JavaScript це
  `["ОШИБКА", "ОТКАЗАНО"].some(p => content.startsWith(p))`. Так цикл відрізняє успіх від невдачі, і слабке місце
  такого підходу описано в лекції серед меж коду.
- **`terminate = True`** лише запам'ятовує рішення, а цикл `for` іде далі. Вихід стоїть уже після нього, тому
  результати отримають усі виклики кроку.
- **`RunResult(reply.text, …, "terminated", …)`** повертає текст, який модель написала поруч із викликом, а не
  результат інструмента. Часто цей текст порожній. Результат завершального інструмента треба брати з `tool_log` чи
  `messages`.

Назва `probe_done` у коментарі належить інструменту з `examples/capstone/mini_tutor.py`. Там один агент заміряє знання
учня, викликає цей інструмент і передає роботу іншому агентові.

**Спробуй передбачити.** Модель в одній відповіді попросила інструмент `handoff` із `terminates=True` і за ним
інструмент `add`. Чи виконається `add`? Чим закінчиться `run_agent`?

<details><summary>Відповідь</summary>

`add` виконається, бо `terminate = True` не перериває цикл `for`. В історії будуть обидва результати, а функція
поверне `stopped_by="terminated"`.

</details>

### Функція `run_agent`: кінець циклу

```python
    return RunResult("(остановлено: превышен лимит шагов)", messages, usage, max_steps, "max_steps", tool_log)
```

Цей рядок виконується, коли `for` пройшов усі кроки. Текст не від моделі, його записано в коді: «зупинено, перевищено
обмеження кроків». Людина не отримає відповіді на своє запитання, зате знатиме, що сталося.

**Спробуй передбачити.** Модель щоразу просить інструмент, а `max_steps=3`. Скільки разів викличуть модель? Чи
побачить вона результат третього виклику? А що буде, якщо передати `max_steps=0`?

<details><summary>Відповідь</summary>

Модель викличуть тричі. Результат третього виклику буде в історії, але модель його не побачить, бо наступного кроку
немає. Якщо `max_steps=0`, цикл не виконається жодного разу: модель не викличуть узагалі, а функція одразу поверне
`stopped_by="max_steps"`.

</details>

### Функція `_execute`

```python
def _execute(name, args, by_name, approve, client_handler) -> str:
    t = by_name.get(name)
    if t is None:
        return f"ОШИБКА: инструмента '{name}' нет. Доступны: {sorted(by_name)}"
    err = validate_args(t, args)
    if err:
        return f"ОШИБКА валидации: {err}"
    if t.needs_approval and not approve(t, args):
        return "ОТКАЗАНО пользователем. Не повторяй этот вызов; предложи альтернативу или спроси, что делать."
    if t.client_side:
        if client_handler is None:
            return "ОШИБКА: нет клиента для этого инструмента"
        return client_handler(t, args)
    try:
        out = t.fn(**args)
        return out if isinstance(out, str) else json.dumps(out, ensure_ascii=False)
    except Exception as e:  # ошибка инструмента → текст для модели, а не падение харнеса
        return f"ОШИБКА выполнения {name}: {type(e).__name__}: {e}"
```

Функція виконує один виклик і завжди повертає рядок. Підкреслення на початку назви є домовленістю, яка каже «це
внутрішня функція». Мова цього не забороняє, бо приватних функцій у модулях Python немає.

- **`if t is None`** перевіряє, чи знайдено інструмент. Оператор `is` порівнює об'єкти за тотожністю, і для `None`
  пишуть саме так. У JavaScript це `t === null`.
- **`sorted(by_name)`**: перебір словника дає його ключі, тому результатом буде відсортований список назв. Завдяки
  цьому помилка підказує моделі, що вона може викликати. У f-рядку список надрукується у форматі Python:
  `['calculator', 'now']`.
- **`err = validate_args(t, args)`** повертає текст помилки або `None`. Значення `None` хибне, тому `if err:` спрацює
  лише при помилці.
- **`t.needs_approval and not approve(t, args)`**: оператор `and` не обчислює праву частину, якщо ліва хибна, як `&&`
  у JavaScript. Тому людину питають лише про інструменти з прапорцем.
- **Текст відмови** адресований моделі: не повторюй, запропонуй інше або спитай. Ця фраза запобігає зацикленню після
  відмови, про яке пише й `docs/debugging.md`.
- **`if t.client_side:`** віддає виконання функції `client_handler`. Якщо її не передали, модель отримає текст про це,
  а не виняток. Перевірка дозволу стоїть вище, тому клієнтський інструмент теж може вимагати згоди людини.
- **`t.fn(**args)`** викликає функцію інструмента. Дві зірочки розгортають словник у іменовані аргументи:
  `fn(**{"path": "a.txt"})` означає `fn(path="a.txt")`. Прямого відповідника в JavaScript немає. Найближче до цього
  виклик функції, яка приймає об'єкт і розбирає його в підписі. Якщо передати назву, якої немає в підписі, Python
  викине `TypeError`, і саме тому `validate_args` спершу перевіряє назви.
- **`out if isinstance(out, str) else json.dumps(…)`** є умовним виразом, як
  `typeof out === "string" ? out : JSON.stringify(out)`. Запис читається в іншому порядку: спершу значення, потім
  умова. Модель працює з текстом, тому будь-який результат перетворюється на рядок. Якщо перетворення не вдасться,
  блок `except` теж це перехопить.
- **`except Exception as e`** відповідає `catch (e)`. Він перехоплює звичайні помилки, але не `KeyboardInterrupt`,
  який виникає при натисканні `Ctrl+C`. Завдяки цьому людина завжди може зупинити програму.
- **`type(e).__name__`** дає назву класу винятку, як `e.constructor.name` у JavaScript. Модель бачить, наприклад,
  `PermissionError` і розуміє тип проблеми.

**Що стоїть поза `try`.** Блок `try` охоплює лише виклик функції інструмента. Виклики `validate_args`, `approve` і
`client_handler` стоять поза ним, і їхній виняток вийде з `run_agent` назовні. На той момент виклик моделі вже
дописаний в історію, а результату ще немає. У коді є ще один такий випадок: `OpenAICompatLLM` розбирає аргументи через
`json.loads`, а модель могла написати там масив замість об'єкта. Для інструмента без обов'язкових параметрів
`validate_args` дійде до `args.items()` і викине `AttributeError`.

**Спробуй передбачити.** Модель викликала `read_file` з аргументом `{"path": 5}`. Чи запуститься функція `read_file`?
Що отримає модель?

`ОШИБКА валидации: аргумент 'path' должен быть string, получено int`.

### Початок файла

```python
"""Инструменты агента: описание (JSON Schema) + функция + политика безопасности."""
from __future__ import annotations

import inspect
import typing
from dataclasses import dataclass, field
from pathlib import Path
from typing import Callable

_PY_TO_JSON = {str: "string", int: "integer", float: "number", bool: "boolean", list: "array", dict: "object"}
```

Перший рядок називає три частини інструмента: опис, функцію й правила безпеки.

- **`inspect`** дозволяє програмі читати підпис функції під час роботи. У JavaScript такої можливості майже немає: там
  є лише `fn.length` і текст функції.
- **`typing`** дає інструменти для роботи з типами.
- **`Path`** подає шлях до файла як об'єкт і замінює `path.join` та частину `fs` із Node.js.
- **`_PY_TO_JSON`** є словником, де ключі не рядки, а самі типи Python. Ключем може бути майже будь-який незмінний
  об'єкт, як у `Map` у JavaScript. Цей словник перекладає тип параметра функції на мову JSON Schema.

### Клас `Tool` і метод `schema`

```python
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict
    fn: Callable[..., str]
    needs_approval: bool = False      # спросить человека перед запуском
    client_side: bool = False         # выполняется не сервером, а «клиентом» (UI / человек)
    terminates: bool = False          # успешный вызов завершает цикл (передача хода, финальный отчёт)
    tags: set[str] = field(default_factory=set)

    def schema(self) -> dict:
        """То, что уходит в модель. Сама функция модели не видна никогда."""
        return {"name": self.name, "description": self.description, "parameters": self.parameters}
```

| Поле | Що воно означає |
|------|-----------------|
| `name` | Назва, за якою модель просить інструмент |
| `description` | Опис для моделі. Від нього залежить, чи покличе вона інструмент вчасно |
| `parameters` | Опис аргументів у форматі JSON Schema |
| `fn` | Справжня функція. Запис `Callable[..., str]` означає «функція з будь-якими аргументами, яка повертає рядок» |
| `needs_approval` | Чи питати дозволу в людини перед запуском |
| `client_side` | Чи виконує інструмент хтось поза програмою агента |
| `terminates` | Чи завершує успішний виклик весь цикл |
| `tags` | Набір міток. У `loop.py` та `tools.py` ніщо їх не читає, тому поле поки нічого не змінює |

Метод `schema` визначає межу між моделлю й програмою. Модель отримує лише три поля. Вона не бачить ні функції, ні
прапорців, тому не може про них домовитися чи обійти їх. Формат цього словника не залежить від провайдера:
`AnthropicLLM` перейменовує `parameters` на `input_schema`, а `OpenAICompatLLM` загортає все в
`{"type": "function", "function": …}`.

### Декоратор `tool`

```python
def tool(description: str, *, needs_approval: bool = False, client_side: bool = False,
         terminates: bool = False, params: dict[str, str] | None = None) -> Callable[[Callable], Tool]:
    """Декоратор: строит JSON Schema из сигнатуры функции.

        @tool("Сложить два числа", params={"a": "первое", "b": "второе"})
        def add(a: float, b: float) -> str: ...
    """
    params = params or {}

    def wrap(fn: Callable) -> Tool:
        sig = inspect.signature(fn)
        hints = typing.get_type_hints(fn)
        props, required = {}, []
        for name, p in sig.parameters.items():
            t = hints.get(name, str)
            origin = typing.get_origin(t) or t
            prop = {"type": _PY_TO_JSON.get(origin, "string")}
            if name in params:
                prop["description"] = params[name]
            props[name] = prop
            if p.default is inspect.Parameter.empty:
                required.append(name)
        schema = {"type": "object", "properties": props, "required": required}
        return Tool(fn.__name__, description, schema, fn, needs_approval, client_side, terminates)

    return wrap
```

Цей код здається складним, бо функції тут вкладені одна в одну. Подивимося на нього окремими частинами.

**Як працює декоратор.** Запис

```python
@tool("Сложить два числа")
def add(a: float, b: float) -> str: ...
```

означає те саме, що:

```python
def add(a: float, b: float) -> str: ...
add = tool("Сложить два числа")(add)
```

Тобто `tool("…")` запам'ятовує опис і налаштування та повертає функцію `wrap`. Функція `wrap` отримує `add`, а її
результат записується під назвою `add`. Після цього `add` є об'єктом `Tool`, а не функцією, тому `add(1, 2)` не
спрацює: справжня функція лежить у полі `add.fn`. У JavaScript декоратора для звичайних функцій немає, а найближчий
запис такий: `const add = tool("…")((a, b) => …)`.

**Рядок за рядком.**

- **`params = params or {}`** підставляє порожній словник, якщо описів параметрів не передали.
- **`inspect.signature(fn)`** читає підпис функції. Результат містить назви параметрів і їхні типові значення.
- **`typing.get_type_hints(fn)`** повертає типи параметрів у вигляді справжніх типів. Цей виклик потрібен через
  `from __future__ import annotations`: анотації зберігаються як текст, і функція перетворює текст `"float"` на тип
  `float`.
- **`props, required = {}, []`** створює порожній словник описів і порожній список обов'язкових параметрів.
- **`for name, p in sig.parameters.items():`** перебирає пари «ключ і значення», як
  `for (const [name, p] of Object.entries(params))` у JavaScript.
- **`t = hints.get(name, str)`** бере тип параметра. Другий аргумент `.get` є значенням на випадок, коли ключа немає:
  параметр без анотації вважається рядком.
- **`typing.get_origin(t) or t`** дістає основу складеного типу. Для `list[str]` результатом буде `list`. Для простого
  `str` функція поверне `None`, тому спрацює `or t`, і лишиться `str`.
- **`_PY_TO_JSON.get(origin, "string")`** перекладає тип. Будь-який невідомий тип стає рядком `"string"`.
- **`if name in params:`** додає опис параметра, якщо він є. Оператор `in` для словника перевіряє ключі.
- **`if p.default is inspect.Parameter.empty:`** перевіряє, чи має параметр типове значення. `Parameter.empty` є
  спеціальним об'єктом-позначкою «значення немає». Звичайний `None` тут не підійшов би, бо `None` сам може бути
  типовим значенням. Параметр без типового значення стає обов'язковим.
- **`schema = {…}`** складає опис аргументів у форматі JSON Schema. Запис `"type": "object"` каже, що аргументи є
  об'єктом, `properties` описує кожне поле, а `required` перелічує обов'язкові.
- **`Tool(fn.__name__, …)`** створює об'єкт. `fn.__name__` дає назву функції, тому назва функції в Python і є назвою,
  яку бачить модель. Якщо перейменуєш функцію, зміниться й те, що читає модель.

**Приклад на конкретній функції.** Візьмемо вигаданий інструмент:

```python
@tool("Найти заметки", params={"query": "что искать"})
def search(query: str, labels: list[str], limit: int = 5) -> str: ...
```

Цикл `for` пройде три параметри:

1. `query`: тип `str`, у схемі `"string"`, опис є, типового значення немає, тому параметр обов'язковий.
2. `labels`: тип `list[str]`, основа `list`, у схемі `"array"`, тип елементів у схему не потрапляє, типового значення
   немає, тому параметр обов'язковий.
3. `limit`: тип `int`, у схемі `"integer"`, опису немає, типове значення є, тому параметр необов'язковий.

Результат:

```json
{ "type": "object",
  "properties": {
    "query": { "type": "string", "description": "что искать" },
    "labels": { "type": "array" },
    "limit": { "type": "integer" } },
  "required": ["query", "labels"] }
```

**Крайній випадок.** Для параметра `limit: int | None = None` основою буде тип-об'єднання, якого немає в
`_PY_TO_JSON`. Тому схема скаже `"string"`, і `validate_args` відхилить число, яке надішле модель. Якщо пишеш
необов'язковий параметр, давай йому простий тип і звичайне типове значення: `limit: int = 5`.

**Спробуй передбачити.** Що поверне `tool("Текущие дата и время")` для функції `def now() -> str` без параметрів?

<details><summary>Відповідь</summary>

Об'єкт `Tool` із назвою `now`, цим описом і схемою `{"type": "object", "properties": {}, "required": []}`. У циклі
`for` немає жодного параметра, тому `props` і `required` лишаються порожніми.

</details>

### Функція `validate_args`

```python
def validate_args(t: Tool, args: dict) -> str | None:
    """Минимальная валидация. Возвращает текст ошибки — его увидит модель и исправится."""
    if "__invalid_json__" in args:
        return f"аргументы не являются валидным JSON: {args['__invalid_json__']!r}"
    props = t.parameters.get("properties", {})
    for r in t.parameters.get("required", []):
        if r not in args:
            return f"нет обязательного аргумента '{r}'"
    for k, v in args.items():
        if k not in props:
            return f"неизвестный аргумент '{k}'. Допустимые: {sorted(props)}"
        want = props[k].get("type")
        ok = {"string": isinstance(v, str), "integer": isinstance(v, int) and not isinstance(v, bool),
              "number": isinstance(v, (int, float)) and not isinstance(v, bool),
              "boolean": isinstance(v, bool), "array": isinstance(v, list),
              "object": isinstance(v, dict)}.get(want, True)
        if not ok:
            return f"аргумент '{k}' должен быть {want}, получено {type(v).__name__}"
    return None
```

Функція не викидає винятків, а повертає текст помилки, бо цей текст побачить модель. Вона повертає першу знайдену
помилку й на цьому зупиняється.

- **`"__invalid_json__" in args`** перевіряє спеціальний ключ. Його додає `OpenAICompatLLM` з модуля 1, коли не може
  розібрати рядок аргументів як JSON. Так трапляється, зокрема, коли `max_tokens` обриває відповідь посеред виклику.
- **`{…!r}`** у f-рядку друкує значення у форматі Python, із лапками навколо рядка, як `JSON.stringify` для рядка в
  JavaScript. Завдяки цьому модель точно бачить, що саме вона написала.
- **`t.parameters.get("properties", {})`** бере опис полів і не викидає виняток, якщо його немає.
- **Перший `for`** шукає пропущені обов'язкові аргументи.
- **Другий `for`** перевіряє кожен наявний аргумент: спершу чи є така назва, потім чи підходить тип. Він зупиняє
  вигадані параметри, а модель отримує список допустимих назв.
- **`{…}.get(want, True)`** є прийомом замість довгого `if`. Код будує словник «назва типу → чи підходить значення» й
  бере з нього потрібний запис. Значення `True` наприкінці означає: якщо схема вказує невідомий тип, перевірка
  пропускає значення.
- **`isinstance(v, int) and not isinstance(v, bool)`**: у Python тип `bool` є підвидом `int`, тому
  `isinstance(True, int)` дає `True`. Без другої частини модель могла б надіслати `true` там, де чекають число, і
  перевірка його пропустила б. У JavaScript такої проблеми немає, бо `typeof true` дає `"boolean"`.
- **`"number"`** приймає і `int`, і `float`, бо в JSON це той самий тип числа.
- **`type(v).__name__`** дає назву типу значення, яку зрозуміє модель: `str`, `int`, `list`.

**Межа цієї функції.** Функція дивиться лише на верхній рівень. Для `{"items": ["а", "б"]}` вона побачить, що `items`
є списком, і на цьому закінчить, хоча всередині мали бути числа. Ще вона перевіряє лише форму даних, а не зміст: шлях
`../../etc/passwd` є правильним рядком.

**Спробуй передбачити.** Інструмент `add(a: int, b: int)`. Модель надіслала `{"a": 1, "b": 2, "c": 3}`, потім
`{"a": 1}`, потім `{"a": 1, "b": true}`. Що скаже `validate_args` у кожному випадку?

<details><summary>Відповідь</summary>

У першому випадку: `неизвестный аргумент 'c'. Допустимые: ['a', 'b']`. У другому: `нет обязательного аргумента 'b'`. У
третьому: `аргумент 'b' должен быть integer, получено bool`.

</details>

### Клас `Workspace`: конструктор і `resolve`

```python
class Workspace:
    """Все пути — только внутри root. Классическая защита от '../../etc/passwd'."""

    def __init__(self, root: str | Path):
        self.root = Path(root).resolve()
        self.root.mkdir(parents=True, exist_ok=True)

    def resolve(self, rel: str) -> Path:
        p = (self.root / rel).resolve()
        if p != self.root and self.root not in p.parents:
            raise PermissionError(f"путь '{rel}' выходит за пределы рабочей папки")
        return p
```

Клас обмежує роботу з файлами однією текою. Модель може попросити будь-який шлях, зокрема `../../etc/passwd` (дві теки
вгору й далі до системного файла), тому перевірка стоїть у коді.

- **`__init__`** є конструктором, як `constructor` у JavaScript. Цей клас написано без `@dataclass`, тому конструктор
  записаний вручну.
- **`Path(root).resolve()`** перетворює шлях на абсолютний і прибирає всі `..`.
- **`mkdir(parents=True, exist_ok=True)`** створює теку разом із батьківськими й не скаржиться, якщо вона вже існує. У
  Node.js це `fs.mkdirSync(dir, { recursive: true })`.
- **`self.root / rel`** використовує оператор `/`, який для `Path` склеює шляхи, як `path.join`. Клас `Path` визначає
  власну поведінку цього оператора. Якщо `rel` є абсолютним шляхом, наприклад `/etc/passwd`, він повністю замінює
  `root`.
- **`.resolve()`** ще раз обчислює справжній шлях. Він прибирає `..` і переходить за символічними посиланнями
  (symlink, файл-посилання на інший файл). Тому посилання всередині теки, яке веде назовні, теж виявиться.
- **`p != self.root and self.root not in p.parents`** перевіряє, чи `root` є предком `p`. `p.parents` містить усі
  батьківські теки шляху. Саму теку `root` теж дозволено. Порівняння рядків через `startswith` тут було б помилкою: шлях
  `/work/agent-evil` починається з `/work/agent`, хоча лежить поза текою.
- **`raise PermissionError(…)`** викидає виняток, як `throw` у JavaScript. Цей виняток перехопить `_execute`, і модель
  отримає текст.

**Спробуй передбачити.** Нехай `root` дорівнює `/work`. Що буде для шляхів `notes/a.txt`, `notes/../a.txt`,
`../secret.txt`, `/etc/passwd`?

<details><summary>Відповідь</summary>

Перші два шляхи пройдуть: вони дадуть `/work/notes/a.txt` і `/work/a.txt`. Два останні викинуть `PermissionError`:
перший дасть `/secret.txt`, а другий через абсолютний шлях дасть `/etc/passwd`, і обидва лежать поза `/work`.

</details>

### Метод `Workspace.tools` і його інструменти

```python
    def tools(self) -> list[Tool]:
        ws = self

        @tool("Прочитать текстовый файл из рабочей папки", params={"path": "относительный путь"})
        def read_file(path: str) -> str:
            p = ws.resolve(path)
            if not p.exists():
                return f"файл '{path}' не найден. Есть: {[x.name for x in ws.root.iterdir()]}"
            text = p.read_text(encoding="utf-8", errors="replace")
            return text if len(text) < 20_000 else text[:20_000] + "\n…[обрезано]"

        @tool("Список файлов в рабочей папке")
        def list_files() -> str:
            return "\n".join(sorted(str(p.relative_to(ws.root)) for p in ws.root.rglob("*") if p.is_file())) or "(пусто)"

        @tool("Записать текстовый файл в рабочую папку (перезапишет существующий)",
              needs_approval=True, params={"path": "относительный путь", "content": "содержимое"})
        def write_file(path: str, content: str) -> str:
            p = ws.resolve(path)
            p.parent.mkdir(parents=True, exist_ok=True)
            p.write_text(content, encoding="utf-8")
            return f"записано {len(content)} символов в {path}"

        return [read_file, list_files, write_file]
```

Метод створює три інструменти, прив'язані до конкретної теки.

- **`ws = self`** дає внутрішнім функціям доступ до об'єкта через замикання, як у JavaScript. Функції тут вкладені, а
  не оголошені методами класу, і на це є причина: у методу в підписі був би параметр `self`, і декоратор записав би
  його в схему як аргумент для моделі.

**Інструмент `read_file`.**

- Шлях спершу проходить `ws.resolve`. Вихід за межі теки викине виняток, і `_execute` перетворить його на текст.
- Якщо файла немає, функція повертає звичайний текст зі списком наявних файлів. Це та сама порада з модуля: «Файл не
  найден. Есть: a.txt, b.txt». Вираз `[x.name for x in ws.root.iterdir()]` перелічує лише верхній рівень теки, зокрема
  й вкладені теки. Цей текст не починається зі слова `ОШИБКА`, тому для циклу він виглядає як успішний результат.
- **`errors="replace"`** каже: байти, які не вдається прочитати як UTF-8, заміни спеціальним символом, а не викидай
  виняток. Завдяки цьому читання двійкового файла не дасть помилки, хоч і дасть нерозбірливий текст.
- **`text if len(text) < 20_000 else text[:20_000] + "\n…[обрезано]"`** є умовним виразом, який обмежує результат 20
  000 символів. Запис `20_000` є таким самим числом, як `20000`, і JavaScript теж дозволяє так писати. Позначка
  наприкінці каже моделі, що це не весь файл. Функція не має параметра, щоб прочитати решту, тому модель не зможе
  дістатися кінця великого файла. У своєму агенті можеш додати параметри початку й довжини.
- Якщо `path` вказує на теку, `read_text` викине `IsADirectoryError`, і модель отримає його як текст.

**Інструмент `list_files`.**

- **`ws.root.rglob("*")`** перебирає всі файли й теки на будь-якій глибині.
- **`str(p.relative_to(ws.root)) for p in … if p.is_file()`** називають генераторним виразом. Він схожий на списковий
  вираз із фільтром, тільки значення створює по одному. У JavaScript результат нагадує
  `[...items].filter(p => p.isFile()).map(p => relative(root, p))`.
- **`"\n".join(…)`** склеює рядки, як `.join("\n")` у JavaScript, але метод викликається на роздільнику.
- **`… or "(пусто)"`**: порожній рядок хибний, тому для порожньої теки модель отримає зрозуміле слово, а не порожній
  результат.

**Інструмент `write_file`.**

- **`needs_approval=True`** змушує питати людину, бо запис може знищити дані. Читання такого дозволу не вимагає.
- **Опис** прямо каже, що файл буде перезаписано. Це приклад того, як опис попереджає модель про наслідки.
- **`p.parent.mkdir(…)`** створює потрібні теки.
- **Рядок результату** каже, скільки символів записано, щоб модель мала підтвердження.

Останній рядок методу повертає список із трьох об'єктів `Tool`, бо після декоратора ці назви вказують уже на них.

### Як ці частини використовує урок

План просить запустити `examples/02_agent_loop.py`, і в цьому файлі є калькулятор, якого немає в `harness/`. Ось його
код:

```python
_OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
        ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg}


def _safe_eval(node):
    # НИКОГДА не делай eval() на строке от модели. Разбираем AST сами.
    if isinstance(node, ast.Expression):
        return _safe_eval(node.body)
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    if isinstance(node, ast.BinOp) and type(node.op) in _OPS:
        return _OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _OPS:
        return _OPS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("допустимы только числа и + - * / **")


@tool("Вычислить арифметическое выражение. Используй для ЛЮБЫХ расчётов, не считай в уме.",
      params={"expression": "например '(12.5 * 4) / 3'"})
def calculator(expression: str) -> str:
    return str(_safe_eval(ast.parse(expression, mode="eval")))
```

- **`_OPS`** є словником «вид операції → функція, яка її виконує». Модуль `operator` містить звичайні операції у
  вигляді функцій: `operator.add(2, 3)` дає 5. `ast.USub` означає унарний мінус, тобто `-5`.
- **`ast.parse(expression, mode="eval")`** розбирає текст на дерево й нічого не виконує. Слово `eval` тут означає лише
  режим «один вираз», і це не функція `eval`.
- **`_safe_eval`** викликає сама себе для кожної частини дерева, тобто працює рекурсивно. Для `2 + 3 * 4` вона отримає
  вузол додавання, обчислить ліву частину (2), для правої знову викличе себе й отримає 12, а потім додасть.
- **`isinstance(node.value, (int, float))`** перевіряє, що константа є числом. Другий аргумент може бути кортежем
  типів. Рядок `'abc'` теж є вузлом `Constant`, але цю перевірку не пройде.
- **`_OPS[type(node.op)](…)`** дістає зі словника функцію за типом операції й одразу її викликає.
- **`raise ValueError`** спрацює на будь-якому іншому вузлі: виклику функції, зверненні до змінної, порівнянні. Це і є
  список дозволеного: усе, що не назване явно, заборонене.

Калькулятор теж має слабке місце. Оператор `**` дозволено без обмежень, тому вираз `9**9**9` обчислюватиметься дуже
довго й займе багато пам'яті. Цикл курсу не має обмеження часу на виконання інструмента, і `_execute` такого не
перерве.

**Решта уроку.**

- **`ws = Workspace(Path(__file__).parent / "_workspace")`** створює робочу теку поруч із файлом уроку, а наступний
  рядок записує туди `budget.txt`. Запис відбувається під час кожного запуску, тому файл щоразу повертається до
  початкового стану.
- **`tools = [calculator, now, *ws.tools()]`** складає список. Одна зірочка в списку означає те саме, що `...` у
  JavaScript.
- **`mock = ScriptedLLM([...])`** створює сценарну модель із чотирма записаними відповідями, а
  `from_env(fallback=mock)` вибирає цю модель, якщо не задано змінної оточення `LLM_PROVIDER`.
- **Системний промпт** каже: спершу збери дані інструментами, а числа бери лише з калькулятора. Це підсилює опис
  інструмента.
- **`run_agent(llm, system, messages, tools, max_steps=10)`** запускає цикл. Параметр `approve` не передано, тому на
  справжній моделі виклик `write_file` спитає дозволу в терміналі.

**Спробуй передбачити.** План просить перед запуском записати, що виведе програма зі сценарною моделлю. Спирайся на
таблицю прогону в лекції й на функцію `default_events`.

**Де читати:**
[`docs/debugging.md`](https://github.com/justxor/agent-harness-course/blob/0c90ce7bbeef858426abfeeacacbdb438921c078/docs/debugging.md),
69 рядків, російською.

**Що це за текст.** Це пам'ятка автора курсу про налагодження агентів, побудована за принципом «ознака, причина, що
зробити». Її не обов'язково вчити: достатньо прочитати раз і повертатися, коли агент поводиться дивно. Частина записів
стосується наступних модулів, і це нормально: ти вже знатимеш, де шукати.

**Золоте правило.** Перш ніж міняти промпт, подивись **траєкторію**: що модель насправді бачила й що вона викликала.
Автор курсу оцінює, що 80 % випадків, коли «модель тупит», насправді означають, що «харнес прислал не то». Тобто
модель працює нормально, а програма надіслала їй неправильні дані.

У коді курсу для цього є три джерела:

| Де дивитися | Що там є |
|-------------|----------|
| `result.tool_log` | Кожен виклик інструмента: назва, аргументи, результат, час |
| `result.messages` | Уся історія розмови |
| `ScriptedLLM.calls` | Те, що сценарна модель отримала в кожному виклику: системний промпт, історію й схеми |

### Розділ «Запросы к API падают»

Цей розділ про відповіді провайдера з кодом помилки.

| Що бачиш | Причина | Що зробити |
|----------|---------|------------|
| `400` зі словами `tool_use` чи `tool_call_id` | На виклик немає результату, або є результат без виклику | Функція `repair_dangling_tool_calls` з модуля 3 допише штучний результат. Перевір, що компакція не розділяє виклик і його результат |
| `400` про чергування ролей | Два повідомлення `user` чи `assistant` підряд, а частина провайдерів цього не приймає | Склеювати такі повідомлення. Після зведення вставляти коротку перехідну репліку, яку курс називає «шов». Про це буде в модулі 3 |
| `401` або `403` | Неправильний ключ, чужий провайдер чи адреса | Перевір `LLM_PROVIDER`, `LLM_BASE_URL` і чи ключ належить цьому сервісу |
| `404` про модель | Застаріла назва моделі або помилка в ній | Звір назву зі сторінкою моделей провайдера |
| `429` | Перевищено обмеження запитів чи токенів за хвилину | Повторювати із зростаючою паузою й випадковою добавкою (backoff із jitter), слухатися заголовка `retry-after` і робити менше одночасних запитів. Це практика модуля 1 |
| `413` або «контекст завеликий» | Історія не вміщається | Компакція й обрізання результатів інструментів |
| Відповідь обривається посеред JSON | `max_tokens` замалий | Збільшити його й дивитися на `stop_reason` |

Останній рядок пов'язаний із першою межею коду з лекції: `run_agent` причини зупинки не перевіряє.

### Розділ «Агент не вызывает инструмент»

Чотири причини, чому модель не користується інструментом:

- Модель узагалі не підтримує виклику інструментів. Таке трапляється передусім із локальними моделями, тому варто
  подивитися їхню картку, тобто опис можливостей.
- Опис не каже, **коли** викликати інструмент. Додай формулювання на кшталт «Используй для любых…».
- Інструментів забагато або вони схожі. Об'єднай їх.
- Системний промпт суперечить сам собі: наприклад, «відповідай одразу» й «спершу перевір».

### Розділ «Агент вызывает не то / с неправильными аргументами»

- Назви параметрів незрозумілі, наприклад `q` замість `query`. Перейменуй і додай опис та приклад.
- Тип не вказано або вказано неправильно. Харнес поверне помилку перевірки, і варто подивитися, чи модель виправиться
  з другої спроби.
- Модель вигадує значення, наприклад номер замовлення чи шлях. Дай їй інструмент, який їх перелічує: `list_files` чи
  `search_orders`.

### Розділ «Агент зацикливается»

- Текст помилки нічого не пояснює, наприклад лише `error`, тому модель пробує те саме. Пиши в помилці, **що** не так і
  **що** спробувати.
- Інструмент повертає те саме на різні запити.
- Немає обмеження кроків. Постав `max_steps` і записуй у журнал, коли воно спрацьовує.
- Після відмови модель повторює виклик. Текст відмови має прямо казати: не повторюй, запропонуй інше.

### Розділ «Агент „забывает“»

- Спрацювала компакція, і зведення втратило факт. Покращ промпт зведення або зберігай важливе в нотатках чи пам'яті.
  Про це модулі 3 і 4.
- Факт був у результаті інструмента, який ти обрізав.
- Довга сесія без компакції призводить до явища, яке курс називає **context rot** (буквально «гниття контексту»):
  модель гірше знаходить важливе посеред довгого контексту.

### Розділ «Агент выдумывает»

- Немає інструмента, який дав би правильну відповідь, тому модель заповнює прогалину вигадкою. Дай їй інструмент або
  дозволь казати «не знаю».
- У промпті немає правила, що числа можна брати лише з інструментів.
- Перевіряй замірами з чіткою умовою, наприклад: «відповідь містить значення, яке повернув інструмент». Курс називає
  такі заміри детермінованими, бо сама перевірка не залежить від випадку: для однакової відповіді вона щоразу дає
  однаковий висновок. Докладно про це йдеться в модулі 7.

### Розділ «Результаты нестабильны»

- Це нормально, бо модель щоразу відповідає трохи інакше. Міряй частку успіхів за 5–10 прогонів.
- Зменш свободу агента: менше інструментів, чіткіша умова завершення, явний план.
- Якщо потрібна повна повторюваність, пиши тести на `ScriptedLLM`, а не на справжній моделі.

### Розділ «Дорого»

- Порахуй витрати: кількість кроків помножити на розмір контексту. Зазвичай причина в довгих результатах інструментів
  і відсутності компакції.
- **Prompt caching** (кешування промпта) дозволяє платити менше за незмінний початок запиту, тобто за системний промпт
  і схеми інструментів. У коді курсу цього немає.
- Використовуй дешевшу модель для субагентів і витягання даних, а сильну лише для головного рішення. Про субагентів
  ідеться в модулі 5.

### Розділ «Чек-лист перед тем, как винить модель»

Перш ніж звинувачувати модель, перевір п'ять речей: чи бачив ти повний запит, який пішов до моделі; чи каже опис
кожного інструмента, коли його викликати; чи пояснюють помилки, що виправити; чи є обмеження кроків і запис
траєкторії; чи прогнав ти завдання п'ять разів, а не один. Цей перелік варто скопіювати у свій `JOURNAL.md`.

## Стаття «Writing effective tools for agents»

**Де читати:** [сайт Anthropic](https://www.anthropic.com/research/writing-tools-for-agents), англійською.

**Що це за текст.** Автор статті Ken Aizawa працює в компанії Anthropic, над текстом працювали також колеги, а
опубліковано його у вересні 2025 року. Автори розповідають, чого навчилися, коли покращували інструменти для власних
агентів. У тексті часто згадується **Model Context Protocol** (MCP), про який уже йшлося в модулі 0. Це спільний
спосіб під'єднати зовнішні інструменти до агента. **Сервером MCP** називають окрему програму, яка надає такі
інструменти. У статті часто згадується власний агент компанії для написання коду, а приклади стосуються її моделей,
проте більшість порад не прив'язана до конкретного агента.

**Головна думка статті.** Інструмент не є звичайною функцією для іншого програміста. Це домовленість між
передбачуваним кодом і непередбачуваним агентом. Тому інструменти треба проєктувати саме для агентів і перевіряти
замірами на реалістичних завданнях, а не вгадувати, що спрацює.

**Якщо часу мало,** прочитай `What is a tool?` і всі п'ять підрозділів `Principles for writing effective tools`.
Розділ `Running an evaluation` стане особливо корисним у модулі 7.

### Вступ

Автори ставлять питання: якщо агент може мати сотні інструментів, як зробити їх справді ефективними? Далі текст
ділиться на дві частини. Перша частина описує процес: зробити перший варіант, виміряти його й покращувати разом з
агентом. Друга частина дає п'ять принципів: які інструменти робити, як групувати назви, що повертати, як економити
токени й як писати описи.

### Розділ `What is a tool?`

Автори починають з поділу на два типи систем. **Детермінована** система (deterministic) на однакові вхідні дані завжди
дає однаковий результат. **Недетермінована** система (non-deterministic) може щоразу відповідати інакше, і агент
належить саме до таких.

Звичайна функція `getWeather("NYC")` щоразу робить те саме. Але коли людина питає агента, чи брати парасольку, агент
може викликати інструмент погоди, відповісти із загальних знань або спершу уточнити місто. Інколи він може вигадати
відповідь (hallucinate) чи неправильно зрозуміти інструмент.

Звідси висновок: не пиши інструменти так, як пишеш API для інших програмістів. Вони читають документацію один раз і
викликають функцію завжди однаково, а агент щоразу вирішує заново. Автори додають спостереження: інструменти, зручні
для агента (ergonomic), зазвичай виявляються зрозумілими й для людини.

### Розділ `How to write tools`

Це вступ до процесу, який складається з трьох етапів і повторюється: швидко зробити перший варіант і спробувати його,
провести заміри, а потім разом з агентом аналізувати результати й покращувати інструменти. Ці етапи повторюють, доки
агент не працюватиме добре на справжніх завданнях.

### Підрозділ `Building a prototype`

Важко заздалегідь вгадати, які інструменти виявляться зручними, тому спершу зроби швидкий перший варіант (prototype).
Якщо пишеш його за допомогою агента, дай йому документацію бібліотек, які використовує інструмент. На сайтах
документації для цього часто є файл `llms.txt`, тобто текст документації, підготовлений спеціально для мовних моделей.

Спробувати інструмент можна трьома способами: загорнути його в локальний сервер MCP, загорнути в розширення
настільного застосунку (Desktop extension, DXT) або передати прямо у виклику API. Спробуй інструмент сам, знайди
незручні місця й збери відгуки людей, які ним користуються.

**Для твого агента.** У курсі інструменти є звичайними функціями Python, тому під'єднувати нічого не треба. Але
сценарна модель опису не читає, тому пробувати якість опису можна лише на справжній моделі.

### Підрозділ `Running an evaluation`

**Заміри** (evaluation, скорочено eval) означають, що ти запускаєш агента на наборі завдань і рахуєш, як часто він
справляється. У статті є два графіки для внутрішніх інструментів компанії, які працюють зі Slack (сервіс для
спілкування команди) та Asana (сервіс для керування завданнями). Вони порівнюють інструменти, написані людьми, з
версіями, які покращив агент, на завданнях, відкладених окремо (held-out test set). Такі завдання не використовували
під час покращення, тому результат показує, чи стало краще насправді.

Далі розділ має три частини.

### Частина `Generating evaluation tasks`

Завдання для заміру мають бути схожими на справжню роботу й спиратися на реалістичні дані. Автори застерігають від
надто простих навчальних середовищ. Сильне завдання може вимагати багатьох викликів, навіть десятків.

| Слабке завдання | Сильне завдання | У чому різниця |
|-----------------|-----------------|----------------|
| Призначити зустріч із jane@acme.corp наступного тижня | Призначити зустріч із Джейн наступного тижня щодо проєкту Acme Corp, додати нотатки з минулої наради й забронювати кімнату | Сильне завдання вимагає самостійно знайти людину, нотатки й кімнату |
| Знайти в журналі платежів `purchase_complete` і `customer_id=9182` | Клієнт 9182 повідомив про потрійне списання за одну покупку. Знайти записи в журналі й з'ясувати, чи постраждали інші клієнти | У слабкому завданні запит уже написано за агента |
| Знайти заявку на скасування від клієнта 45892 | Надійшла заявка на скасування від Sarah Chen. Підготувати пропозицію: чому людина йде, що могло б її втримати й які є ризики | Сильне завдання вимагає зібрати дані й зробити висновки |

До кожного завдання потрібна перевірна відповідь або очікуваний результат. Перевірка може бути простим порівнянням
рядків, а може доручатися іншій моделі як суддя. Не роби перевірку надто суворою: правильну відповідь не можна
відхиляти через формат чи пунктуацію.

Можна також вказати, які інструменти агент мав би викликати, щоб побачити, чи розуміє він їхнє призначення. Але не
перестарайся: до правильного результату часто веде кілька шляхів.

### Частина `Running the evaluation`

Автори радять запускати заміри програмно, через прямі виклики API, у простих циклах `while`, по одному циклу на
завдання. Це саме те, що робить `run_agent`, тому в модулі 7 ти використаєш власний цикл.

У системному промпті такого агента варто попросити виводити не лише відповідь, а й міркування та відгук про
інструменти. Якщо модель пише міркування перед викликом, вона часто працює краще. Цей прийом називають chain of
thought (CoT), тобто міркування вголос крок за кроком. Деякі моделі мають для цього окремий режим роздумів між
викликами (interleaved thinking). Головна користь тут у тому, що видно, чому агент викликав чи не викликав певний
інструмент.

Окрім частки правильних відповідей, збирай такі числа: час виконання викликів і завдань, кількість викликів, кількість
токенів і кількість помилок інструментів. У циклі курсу ці дані вже є: `tool_log` містить назви й час, а `usage`
містить токени. Якщо видно, що агент постійно викликає три інструменти поспіль, їх можна об'єднати в один.

### Частина `Analyzing results`

Агенти добре помічають проблеми: суперечливі описи, неефективні інструменти, незрозумілі схеми. Але автори
застерігають: те, чого агент не сказав, часто важливіше за те, що він написав. Тому читай не лише міркування, а й
сирий запис викликів і результатів. Агент сам може не знати, що вибрав поганий шлях.

| Що видно в числах | Що це може означати |
|-------------------|---------------------|
| Багато зайвих повторних викликів | Потрібно змінити розмір сторінки результатів чи обмеження токенів |
| Багато помилок через неправильні параметри | Опис чи приклади інструмента незрозумілі |

Приклад зі статті: коли компанія запустила інструмент вебпошуку, модель безпідставно дописувала до запиту число
`2025`. Це псувало результати пошуку, і допомогло покращення опису інструмента.

### Підрозділ `Collaborating with agents`

Результати можна проаналізувати за допомогою самого агента: склей записи всіх прогонів і дай їх агентові для написання
коду. Він знайде закономірності й перепише багато інструментів одразу, зберігаючи узгодженість описів і коду. Автори
кажуть, що більшість порад цієї статті отримано саме так.

Щоб не підігнати інструменти під конкретні завдання (overfitting), вони перевіряли результат на відкладених завданнях.
Ця перевірка показала, що покращення дає приріст навіть порівняно з ретельно зробленими інструментами, які написали
дослідники вручну або згенерувала модель.

**Для твого агента.** Спробуй це в малому: дай агентові, яким користуєшся, запис кількох прогонів і попроси знайти
суперечності в описах. Перевір пропозиції повторним запуском, а не на слово.

### Розділ `Principles for writing effective tools`

Далі йдуть п'ять принципів, кожен в окремому підрозділі. Вони випливають із результатів замірів, описаних вище.

### Принцип `Choosing the right tools for agents`

Більше інструментів не означає кращий результат. Типова помилка полягає в тому, щоб зробити окремий інструмент для
кожної дії наявного API.

Автори пояснюють це словом **affordances**: це те, що певна річ дозволяє зробити й як вона показує цю можливість.
Агент сприймає інструменти не так, як звичайна програма. Звичайна програма може недорого перебрати мільйон записів, бо
пам'ять дешева. Агент має обмежений контекст, і кожен прочитаний запис займає в ньому місце.

Приклад: пошук контакту в адресній книзі. Інструмент `list_contacts`, який повертає всі контакти, змушує модель читати
їх один за одним. Людина так не шукає: вона одразу відкриває потрібну літеру. Тому краще зробити `search_contacts`.

Один інструмент може виконувати кілька операцій за раз:

| Замість цього | Краще це | Чому |
|---------------|----------|------|
| `list_users`, `list_events`, `create_event` | `schedule_event`, який сам знаходить вільний час і створює подію | Модель не читає зайвих списків |
| `read_logs` | `search_logs`, який повертає лише потрібні рядки й трохи тексту навколо них | Журнали великі, а потрібна мала частина |
| `get_customer_by_id`, `list_transactions`, `list_notes` | `get_customer_context`, який збирає потрібне про клієнта одразу | Три виклики замінено одним |

Кожен інструмент повинен мати ясне й окреме призначення. Перевірка проста: чи поділила б людина завдання так само,
маючи ті самі можливості?

**Для твого агента.** Інструмент `list_files` з курсу є саме таким «перелічити все». Для маленької теки це нормально,
а для великого проєкту він займе багато контексту. Інструмент `grep` із практики належить до кращого типу.

### Принцип `Namespacing your tools`

**Простір назв** (namespace) означає спільний префікс для пов'язаних інструментів. Агенти можуть отримати доступ до
десятків серверів і сотень інструментів, зокрема чужих. Коли інструменти перетинаються, агент плутається.

Групувати можна за сервісом (`asana_search`, `jira_search`) і за ресурсом (`asana_projects_search`,
`asana_users_search`). Автори виміряли, що вибір між префіксом і суфіксом помітно впливає на результат, причому вплив
різний для різних моделей. Тому вибирай схему назв за власними замірами.

Автори називають чотири типові помилки агента: викликає не той інструмент, викликає правильний інструмент із
неправильними параметрами, викликає замало інструментів або неправильно розуміє результат. Вдало вибрані інструменти
зменшують ризик усіх чотирьох, бо описів у контексті менше, а більшу частину роботи виконує сам інструмент.

### Принцип `Returning meaningful context from your tools`

Повертай лише те, що справді впливає на наступний крок. Технічні поля на кшталт `uuid`, `256px_image_url` чи
`mime_type` агентові зазвичай не потрібні. Поля `name`, `image_url` та `file_type` набагато корисніші.

Агент краще працює зі зрозумілими назвами, ніж із випадковими ідентифікаторами. Автори пишуть, що заміна довгих
випадкових номерів на зрозумілі назви чи навіть на прості порядкові номери помітно зменшила кількість вигаданих
відповідей під час пошуку.

Інколи технічний номер усе ж потрібен для наступного виклику: наприклад, `search_user(name='jane')` дає результат, а
для `send_message(id=12345)` потрібен номер. Розв'язок такий: додай параметр `response_format`, який приймає
`"concise"` (коротко) або `"detailed"` (докладно). Значення такого параметра обмежені переліком, який називають
`enum`. Сама ідея нагадує GraphQL, де клієнт вибирає потрібні поля. У прикладі статті докладна відповідь зі Slack
займала 206 токенів, а коротка 72, тобто приблизно третину. Докладна відповідь містить номери на кшталт `thread_ts`,
потрібні для подальших викликів.

Формат результату (XML, JSON чи Markdown) теж впливає на якість, і найкращого для всіх випадків немає. Це знову
вирішують заміри.

### Принцип `Optimizing tool responses for token efficiency`

Важлива не лише якість результату, а й обсяг. Для всього, що може зайняти багато контексту, автори радять поєднувати
чотири прийоми й давати розумні типові значення:

- посторінковий вивід (pagination), коли результати видають частинами;
- вибір діапазону (range selection), наприклад рядки з 100 до 200;
- фільтрування (filtering);
- обрізання (truncation).

Для прикладу: у власному агенті компанії для написання коду результат інструмента за замовчуванням обмежено 25 000
токенів.

Якщо обрізаєш результат, підкажи агентові, що робити далі, наприклад кілька вузьких пошуків замість одного широкого.
Те саме стосується помилок: текст має конкретно пояснювати, що виправити, а не показувати незрозумілий код чи стек
викликів. У статті є зображення з двома варіантами помилки, а суть така: погана помилка не каже, що робити, а добра
наводить приклад правильного формату.

**Для твого агента.** Функція `read_file` обрізає результат і пише `…[обрезано]`, а повідомлення `validate_args`
кажуть, що виправити. Це приклади цього принципу. Проте `read_file` не дає способу прочитати решту, тому варто додати
параметр для цього.

### Принцип `Prompt-engineering your tool descriptions`

Автори називають це одним із найдієвіших способів покращити інструменти, бо описи завантажуються в контекст і напряму
впливають на поведінку моделі. Тому **prompt engineering** (ретельне написання тексту для моделі) стосується й описів.

Описуй інструмент так, як новому колезі в команді. Подумай, що ти знаєш неявно, і напиши це прямо: особливі формати
запитів, значення вузьких термінів, зв'язки між даними. Очікувані вхідні й вихідні дані описуй точно й перевіряй за
суворим описом даних (strict data models). Назви параметрів мають бути однозначні: не `user`, а `user_id`.

Автори наводять приклад: одна з моделей Anthropic досягла найкращого на той час результату в наборі завдань SWE-bench
Verified (справжні завдання програмування для вимірювання агентів) після того, як компанія точно відшліфувала описи
інструментів. Кількість помилок помітно зменшилася.

Наприкінці автори радять почитати довідку компанії про визначення інструментів. Для серверів MCP вони згадують
анотації інструментів: позначки, які показують, чи інструмент звертається до зовнішнього світу (open-world access) чи
робить незворотні зміни. У коді курсу подібну роль виконує прапорець `needs_approval`.

### Розділ `Looking ahead`

Автори підсумовують. Ефективні інструменти мають чотири риси: вони ясно визначені, ощадливо використовують контекст
агента, поєднуються між собою в різних завданнях і дозволяють агентові природно розв'язувати справжні завдання.
Механізми взаємодії змінюватимуться, бо розвиваються й протокол MCP, і самі моделі. Проте підхід, побудований на
вимірюванні, збережеться.

### Що взяти у свого агента

- Пиши в кожному описі, коли викликати інструмент, і використовуй однозначні назви параметрів.
- Став на початку лише кілька інструментів, а не окремий на кожну дію.
- Роби так, щоб результат і помилка підказували наступний крок.
- Обрізай великий результат, повідомляй про обрізання й давай спосіб дістати решту.
- Перевіряй зміни замірами на реалістичних завданнях і читай сирий запис викликів.

### Запитання до статті

**1. Чому інструмент не можна писати так само, як API для іншого програміста?**

<details><summary>Відповідь</summary>

Програміст читає документацію, а потім викликає функцію завжди однаково. Агент щоразу вирішує заново, чи викликати
інструмент, і може помилитися чи вибрати інше. Крім того, його контекст обмежений, тому кожен зайвий результат йому
заважає й коштує токенів.

</details>

**2. Агент часто викликає той самий пошук із трохи різними словами. Що це може означати, і що спробувати?**

<details><summary>Відповідь</summary>

Стаття пов'язує багато зайвих викликів із невдалим розміром сторінки результатів чи обмеженням токенів. Спробуй
змінити ці параметри, покращити опис і подивитися в запису прогону, що саме повертав інструмент. Посібник
`docs/debugging.md` додає ще одну причину: інструмент може повертати те саме на різні запити.

</details>

**3. Навіщо параметр `response_format`, якщо можна завжди повертати все?**

<details><summary>Відповідь</summary>

Повна відповідь займає більше контексту: у прикладі статті 206 токенів проти 72. Але інколи номери з повної відповіді
потрібні для наступного виклику. Параметр дозволяє агентові вибрати коротку відповідь для читання й повну для
подальшої роботи.

</details>

**4. Чому заміри мають ґрунтуватися на складних завданнях, а не на простих?**

<details><summary>Відповідь</summary>

Просте завдання на кшталт «знайди цей запис» часто вже диктує агентові виклик і не показує, чи він розуміє
інструменти. Складне завдання вимагає самостійно вибрати й поєднати кілька інструментів, а саме це й відбувається на
справжній роботі.

</details>
