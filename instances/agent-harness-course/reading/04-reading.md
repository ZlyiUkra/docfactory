**Уточнення про «одного писателя».** Документ `docs/vision.md` LearnHarness називає конвеєр єдиним компонентом, що
пише в граф. Конвеєр має три етапи: модель-витягувач дістає твердження з тексту, модель-аудитор звіряє їх із наявним
графом через інструменти лише для читання, а звичайний код-об'єднувач дописує результат у журнали. Документ
`docs/architecture.md` уточнює: цей конвеєр є основним шляхом побудови графа, але видалення вузла чи сесії та
спрощення ланцюжків теж змінюють файли графа. Той самий документ каже, що правило «один записувач на сховище» (one
writer per store) не перевіряє автоматичний лінтер. Тому принцип варто розуміти так: нові знання в граф додає лише
один компонент, і це домовленість у коді, а не автоматичний контроль.

### Початок файла

```python
from __future__ import annotations

import hashlib
import json
import os
import re
import time
from pathlib import Path

from .llm import LLM
```

Перший рядок просить Python не обчислювати підказки типів під час запуску. Як і типи в TypeScript, вони лишаються для
читача й перевірних інструментів і на роботу програми не впливають.

Далі йдуть модулі стандартної бібліотеки, тобто ті, що входять до самого Python:

| Модуль | Для чого тут | Що схоже в JavaScript |
|--------|--------------|------------------------|
| `hashlib` | хеш SHA-256 | `crypto.createHash` у Node |
| `json` | `json.dumps` і `json.loads` | `JSON.stringify` і `JSON.parse` |
| `os` | `os.replace` | `fs.renameSync` у Node |
| `re` | регулярні вирази | вбудований `RegExp` |
| `time` | поточний час | `Date.now()`, але `time.time()` дає секунди, а не мілісекунди |
| `pathlib.Path` | шляхи до файлів як об'єкти | модуль `path` разом із `fs` |

`from .llm import LLM` бере клас `LLM` із сусіднього файла. Крапка означає «цей самий пакет», як `./llm` в імпорті
JavaScript.

### Клас `SessionStore`

```python
class SessionStore:
    """Сессия = JSON-файл. Сохраняем ДО вызова модели (write-ahead): если процесс упадёт
    посреди ответа, сообщение пользователя не потеряется, а сессию можно продолжить."""
```

Рядок у потрійних лапках одразу під заголовком називається **docstring**, це опис класу, схожий на коментар JSDoc. Сам
клас лише читає й записує файли. Запис наперед робить не він, а той, хто викликає `save` до звернення до моделі. Отже,
якщо викликати `save` пізніше, клас не заперечуватиме й нічого не попередить.

### `SessionStore.__init__`

```python
def __init__(self, root: str | Path):
    self.root = Path(root)
    self.root.mkdir(parents=True, exist_ok=True)
```

`__init__` — це конструктор, аналог `constructor` у класі JavaScript. `self` — це той самий об'єкт, що `this`, але в
Python його явно пишуть першим параметром кожного методу. Запис `str | Path` означає те саме, що в TypeScript: можна
передати рядок або об'єкт шляху.

`Path(root)` перетворює обидва випадки на об'єкт шляху. `mkdir(parents=True, exist_ok=True)` створює теку разом із
батьківськими, як `fs.mkdirSync(root, { recursive: true })`. Назви параметрів тут пишуть під час виклику, це
називається іменованими аргументами. Без `exist_ok=True` другий запуск програми завершився б помилкою, бо тека вже
існує.

### `SessionStore.path`

```python
def path(self, sid: str) -> Path:
    if not re.fullmatch(r"[\w-]+", sid):
        raise ValueError("недопустимый id сессии")
    return self.root / f"{sid}.json"
```

Метод перетворює ідентифікатор сесії на шлях до файла, але спершу перевіряє його. Перевірка потрібна тому, що
ідентифікатор може прийти ззовні. Без неї значення `../evil` вивело б запис за межі теки сесій. Таку атаку називають
**path traversal**, тобто вихід за межі дозволеної теки, і тест курсу `test_session_store_rejects_bad_id` перевіряє
саме цей випадок.

- `-> Path` вказує тип результату, як `: Path` у TypeScript.
- `if not ...` відповідає `if (!...)`: слово `not` заперечує умову.
- `r"..."` означає рядок, у якому зворотна коса риска не має особливого значення. Для регулярних виразів це зручно.
- `re.fullmatch` вимагає, щоб шаблон збігся з усім рядком, як `/^...$/` у JavaScript.
- `[\w-]+` означає одну чи більше літер, цифр, підкреслень або дефісів. На відміну від JavaScript, у Python `\w`
  приймає літери будь-якої абетки.
- `raise` кидає виняток, як `throw`.
- `self.root / f"{sid}.json"` склеює шлях. Об'єкти `Path` перевизначають оператор `/`, тому це аналог `path.join`.
  Запис `f"..."` називається **f-рядком** і працює як шаблонний рядок `` `${sid}.json` ``.

**Спробуй передбачити.** Що станеться для `path("сесія_1")`, `path("a.b")` і `path("../evil")`?

<details><summary>Відповідь</summary>

`сесія_1` підходить, бо кирилиця входить до `\w`, а підкреслення теж. `a.b` і `../evil` викличуть `ValueError`, бо
крапка й коса риска не входять до шаблону.

</details>

### `SessionStore.load`

```python
def load(self, sid: str) -> dict:
    p = self.path(sid)
    if not p.exists():
        return {"id": sid, "created": time.time(), "messages": []}
    return json.loads(p.read_text(encoding="utf-8"))
```

Метод повертає `dict`. У Python **словник** (`dict`) відповідає звичайному об'єкту JavaScript, який використовують як
набір ключів і значень.

Якщо файла немає, метод повертає нову порожню сесію, але на диск нічого не пише. Файл з'явиться під час першого
`save`. Якщо файл є, `read_text` читає його як рядок, а `json.loads` розбирає.

Тут немає `try`: якщо файл зіпсовано, програма впаде з винятком `JSONDecodeError`. У цьому важлива відмінність від
журналу. Журнал складається з багатьох незалежних рядків, тому один рядок можна пропустити. Сесія складається з одного
документа, тому пропустити частину неможливо, а тихо почати порожню сесію було б гірше. Атомарний запис і робить так,
щоб падіння програми такого файла не залишало.

### `SessionStore.save`

```python
def save(self, session: dict) -> None:
    p = self.path(session["id"])
    tmp = p.with_suffix(".tmp")
    tmp.write_text(json.dumps(session, ensure_ascii=False, indent=1), encoding="utf-8")
    os.replace(tmp, p)  # атомарно: либо старая версия, либо новая, никогда — половина
```

Ідею метода пояснює лекція, а тут розберемо кожен рядок.

- `-> None` означає, що метод нічого не повертає, як `: void` у TypeScript.
- `session["id"]` бере ідентифікатор із самої сесії. Шлях проходить ту саму перевірку, що й під час читання.
- `p.with_suffix(".tmp")` міняє розширення: `sessions/s1.json` стає `sessions/s1.tmp`.
- `json.dumps(session, ensure_ascii=False, indent=1)` перетворює сесію на рядок. `ensure_ascii=False` лишає кирилицю
  читабельною, бо інакше кожна літера стала б записом на кшталт `П`. `indent=1` додає переноси й відступ в один
  пробіл, щоб файл могла прочитати людина.
- `write_text` відкриває файл, пише весь рядок і закриває файл.
- `os.replace(tmp, p)` ставить тимчасовий файл на місце основного. Якщо основний існує, його буде замінено.

**Чому тимчасовий файл лежить поруч, а не в системній теці.** Документація Python попереджає, що `os.replace` може не
спрацювати, якщо файли лежать на різних файлових системах. Одна тека такий випадок виключає.

**Крайні випадки.**

- Назва тимчасового файла стала, тому два процеси, що пишуть ту саму сесію, працюватимуть з одним `s1.tmp`. Дані
  можуть змішатися, а другий `os.replace` може не знайти файла, який перший уже перемістив. Тому одну сесію має писати
  один процес.
- Кожне збереження перетворює на рядок і записує всю сесію. Для одного збереження на крок цього досить, але витрати
  ростуть разом із довжиною розмови.
- `fsync` немає, тому під час вимкнення живлення дані можуть не дійти до диска. Ескіз виправлення є нижче.

**Спробуй передбачити.** Програма впала між `write_text` і `os.replace`. Що лежить у теці, що поверне `load("s1")` і
що поверне `list()`?

<details><summary>Відповідь</summary>

У теці лежать старий `s1.json` і повний новий `s1.tmp`. `load` читає лише `s1.json`, тому поверне стару версію.
`list()` поверне `["s1"]`, бо шукає лише файли `*.json`. Наступний `save` перезапише `s1.tmp`, тому прибирати його
окремо не потрібно.

</details>

### `SessionStore.list`

```python
def list(self) -> list[str]:
    return sorted(p.stem for p in self.root.glob("*.json"))
```

Метод повертає ідентифікатори всіх збережених сесій. `glob("*.json")` знаходить файли за шаблоном, а `p.stem` дає
назву файла без розширення.

Вираз `p.stem for p in ...` у дужках називається **генераторним виразом**. Він схожий на `.map(p => p.stem)`, але
значення обчислює по одному, коли їх просять, а не наперед. `sorted` забирає їх і повертає відсортований список.

Метод має таку саму назву, як вбудований тип `list`. Конфлікту немає, бо викликають його через об'єкт:
`sessions.list()`.

### Клас `Ledger` і його `__init__`

```python
class Ledger:
    """Только дописываем. Чтение терпит битые строки (обрыв записи при падении).
    Всё «текущее состояние» вычисляется из журнала при чтении."""

    def __init__(self, path: str | Path):
        self.path = Path(path)
        self.path.parent.mkdir(parents=True, exist_ok=True)
```

Клас нічого не знає про факти: він приймає будь-який словник і повертає список словників. Завдяки цьому той самий
журнал можна використати для будь-яких подій.

`self.path.parent` — це тека, у якій лежатиме файл. Конструктор створює лише теку. Сам файл з'явиться під час першого
`append`.

### `Ledger.append`

```python
def append(self, record: dict) -> None:
    with self.path.open("a", encoding="utf-8") as f:
        f.write(json.dumps({"ts": time.time(), **record}, ensure_ascii=False) + "\n")
```

**`with ... as f`** відкриває файл і гарантує, що він закриється, навіть якщо всередині станеться виняток. У
JavaScript це відповідає блоку `try { ... } finally { f.close() }`. Під час закриття дані з буфера Python переходять
до операційної системи.

**Режим `"a"`** (від append) означає, що запис іде в кінець файла, а наявний вміст лишається недоторканим. Якщо файла
ще немає, Python його створить.

**`{"ts": time.time(), **record}`** будує новий словник. `**record` розгортає ключі й значення, як `...record` в
об'єкті JavaScript. Пізніший ключ перемагає, тому якщо `record` містить власне `ts`, запишеться воно.

**`+ "\n"`** завершує рядок. Завдяки цьому кожен запис займає один рядок файла. Перенос усередині тексту факта цьому
не заважає, бо `json.dumps` записує його як два символи `\n`.

Метод нічого не читає, тому запис дешевий. Цим же пояснюється його слабке місце: він не знає, чи закінчився попередній
рядок.

**Спробуй передбачити.** Файл закінчується на обірваному записі `{"op": "add", "id": "2", "te`. Викликаємо
`append({"op": "add", "id": "3", "text": "c"})`. Скільки записів поверне `read`, якщо до цього файл мав один цілий
рядок?

<details><summary>Відповідь</summary>

Один, бо новий запис пишеться одразу за `"te`, і два записи стають одним непридатним рядком. Цього не змінює навіть
випадок, коли обірвався лише сам перенос: два цілих об'єкти JSON в одному рядку `json.loads` теж відхилить.

</details>

### `Ledger.read`

```python
def read(self) -> list[dict]:
    if not self.path.exists():
        return []
    out = []
    for line in self.path.read_text(encoding="utf-8").splitlines():
        try:
            out.append(json.loads(line))
        except json.JSONDecodeError:
            continue  # битая строка — пропускаем, не угадываем
    return out
```

- `-> list[dict]` означає список словників, як `Record<string, unknown>[]` у TypeScript.
- Якщо файла немає, журнал вважається порожнім. Це не помилка, бо нова програма ще нічого не записала.
- `read_text` читає весь файл у пам'ять, а `splitlines` ділить його на рядки. Цикл `for ... in` відповідає `for...of`.
- `try`/`except` відповідає `try`/`catch`. Метод перехоплює лише `JSONDecodeError`, тобто помилку розбору, а всі інші
  винятки йдуть далі. Це правильно: помилка доступу до диска не має виглядати як порожній журнал.
- `continue` переходить до наступного рядка. Тут він стоїть останнім у циклі, тому поведінку не змінює, зате показує
  намір: рядок свідомо пропущено.

**Спробуй передбачити.** Посеред журналу стоїть порожній рядок. Що зробить `read`?

<details><summary>Відповідь</summary>

Пропустить його, бо `json.loads("")` кидає `JSONDecodeError`. Саме тому працює один зі способів виправлення
склеювання: писати перенос на початку кожного запису.

</details>

**Слабкі місця, про які курс не пише.** Перевірити їх можна короткими дослідами зі стандартною бібліотекою.

1. **Обрив посеред літери.** Кирилична літера займає у файлі два байти. Якщо файл закінчується першим із них,
   `read_text` кидає `UnicodeDecodeError`. Це відбувається ще до циклу, поза блоком `try`, і цей виняток не є
   `JSONDecodeError`. Тому журнал не читається взагалі, а разом із ним не працюють `facts()`, `add` і `recall`. Тест
   курсу цього не бачить, бо обриває запис на латинських літерах.
2. **Символи, які `splitlines` вважає кінцем рядка.** Він ділить текст не лише за `\n`, а й за символами на кшталт
   `U+2028`, що трапляються в тексті з вебсторінок. Код `json.dumps` з `ensure_ascii=False` таких символів не екранує,
   тому вони потрапляють у файл як є. Запис розпадається на дві частини, кожна непридатна, і факт мовчки зникає.
3. **Рядок, який є правильним JSON, але не об'єктом.** Рядок `123` розбереться успішно, і `read` поверне число. Тоді
   `facts()` впаде на виклику `r.get`. Обрив такого рядка не дасть, бо кожен запис починається з `{`, але ручна правка
   файла може.

### `EXTRACT_PROMPT` і `SAVE_FACTS_SCHEMA`

```python
EXTRACT_PROMPT = """Извлеки из текста устойчивые факты о пользователе и его задаче,
которые пригодятся в будущих сессиях (предпочтения, решения, контекст проекта).
Не включай разовые детали. Каждый факт — одно самостоятельное утверждение.
Вызови инструмент save_facts."""

SAVE_FACTS_SCHEMA = {
    "name": "save_facts",
    "description": "Сохранить список фактов",
    "parameters": {"type": "object", "required": ["facts"],
                   "properties": {"facts": {"type": "array", "items": {"type": "string"}}}},
}
```

Великими літерами в Python позначають сталі значення, це домовленість. Потрійні лапки дають рядок на кілька рядків, як
зворотні лапки в JavaScript.

Промпт просить три речі. Брати лише сталі факти: уподобання, рішення, контекст проєкту. Не брати разових деталей:
«зараз падає тест» через тиждень нікому не потрібно. Формулювати кожен факт самостійним твердженням, бо його
читатимуть без контексту розмови.

Схема має той самий формат, що `Tool.schema()` із модуля 2: назва, опис і параметри у форматі JSON Schema. Тут єдиний
обов'язковий параметр `facts` має бути масивом рядків. Функції за цим описом немає, бо інструмент служить лише для
того, щоб отримати від моделі структурований список, а не текст, який довелося б розбирати.

### `_norm`

```python
def _norm(s: str) -> str:
    return re.sub(r"\W+", " ", s.lower()).strip()
```

Підкреслення на початку назви за домовленістю означає «внутрішня функція, не для використання ззовні». Мова цього не
забороняє.

Вираз читається зсередини назовні:

1. `s.lower()` переводить текст у нижній регістр.
2. `re.sub(r"\W+", " ", ...)` замінює кожну послідовність символів, які не є літерою, цифрою чи підкресленням, одним
   пробілом. `\W` протилежне `\w`.
3. `.strip()` прибирає пробіли з обох кінців.

| Вхід | Результат |
|------|-----------|
| `"Любить каву"` | `"любить каву"` |
| `"  ЛЮБИТЬ   КАВУ "` | `"любить каву"` |
| `"Пише на C++"` | `"пише на c"` |
| `"Node.js"` | `"node js"` |
| `"!!!"` | порожній рядок |

### `fact_id`

```python
def fact_id(text: str) -> str:
    return "f_" + hashlib.sha256(_norm(text).encode()).hexdigest()[:12]
```

`.encode()` перетворює рядок на байти в кодуванні UTF-8, бо SHA-256 працює з байтами. `hexdigest()` дає результат як
рядок із 64 шістнадцяткових символів. `[:12]` бере перші 12 символів. Такий запис називається **зрізом** (slice) і
відповідає `.slice(0, 12)`. Дванадцять символів дають близько 281 трильйона можливих значень, а цього досить для
фактів однієї людини. Префікс `f_` показує в журналі, що це ідентифікатор факта.

Ідентифікатор обчислюється з тексту, тому йому не потрібен лічильник чи база даних: той самий текст дасть той самий
результат у будь-якому процесі й після будь-якого перезапуску.

**Крайні випадки.** `"Пише на C++"` і `"Пише на C#"` дають той самий `f_2670ad79eb29`, бо після `_norm` обидва тексти
стають `пише на c`. Факти без жодної літери, наприклад `"!!!"` і `"???"`, теж збігаються, бо хешується порожній рядок.

### Клас `FactMemory` і його `__init__`

```python
class FactMemory:
    def __init__(self, ledger: Ledger):
        self.ledger = ledger
```

Клас отримує готовий журнал через конструктор, а не створює його сам. Завдяки цьому тест може передати журнал у
тимчасовій теці. Журнал не знає про факти, а `FactMemory` знає лише про факти, тому кожен із них можна змінювати
окремо.

### `FactMemory.facts`

```python
def facts(self) -> dict[str, str]:
    """Текущее состояние = свёртка журнала (add / forget)."""
    state: dict[str, str] = {}
    for r in self.ledger.read():
        if r.get("op") == "add":
            state[r["id"]] = r["text"]
        elif r.get("op") == "forget":
            state.pop(r["id"], None)
    return state
```

Те саме мовою TypeScript:

```ts
const facts = (log: Rec[]) =>
  log.reduce<Record<string, string>>((state, r) => {
    if (r.op === "add") state[r.id] = r.text;
    else if (r.op === "forget") delete state[r.id];
    return state;
  }, {});
```

- `state: dict[str, str] = {}` створює порожній словник і зазначає тип: ключі й значення є рядками.
- `r.get("op")` повертає значення або `None`, якщо ключа немає. `None` відповідає `null` у JavaScript. Тому рядок без
  `op` не викличе помилки.
- `state[r["id"]] = r["text"]` додає факт. Квадратні дужки в Python поводяться суворіше, ніж у JavaScript: якщо ключа
  `id` немає, буде виняток `KeyError`, а не `undefined`.
- `state.pop(r["id"], None)` прибирає ключ, як `delete`. Другий аргумент потрібен, щоб забування неіснуючого факта не
  викликало помилки.

Записи з невідомим значенням `op` нічого не роблять. Завдяки цьому стара версія програми зможе прочитати журнал, у
якому нова версія вже пише інші типи подій. Поле `source` стан не використовує: воно потрібне, щоб потім можна було
знайти в журналі, звідки взявся факт.

**Спробуй передбачити.** Факт додали, забули, а потім додали знову. Що покаже `facts()`?

<details><summary>Відповідь</summary>

Факт буде в стані, бо згортка застосує `add`, `forget`, `add` у такому порядку. Словник Python пам'ятає порядок
додавання, тому факт опиниться в кінці.

</details>

### `FactMemory.add`

```python
def add(self, text: str, source: str) -> bool:
    fid = fact_id(text)
    if fid in self.facts():
        return False  # дедупликация по нормализованному тексту
    self.ledger.append({"op": "add", "id": fid, "text": text, "source": source})
    return True
```

`fid in self.facts()` перевіряє, чи є такий ключ у словнику, як `map.has(fid)`. Метод повертає `False`, якщо факт уже
є, і `True`, якщо записав новий. Завдяки цьому `extract` знає, що саме додалося.

У журнал іде оригінальний текст, а не нормалізований, бо людина й модель мають бачити нормальне речення. Якщо пізніше
додати той самий факт іншим написанням, лишиться перший варіант.

Дедуплікація перевіряє поточний стан, а не всю історію. Тому забутий факт можна додати знову.

Є дві ціни. Кожен виклик читає весь журнал, тому додати 1000 фактів поспіль означає розібрати 500 500 рядків. Між
перевіркою й записом немає блокування, тому два процеси можуть дописати той самий факт двічі. Згортка цього не
помітить, бо словник тримає за одним ключем одне значення.

### `FactMemory.forget`

```python
def forget(self, fid: str) -> None:
    self.ledger.append({"op": "forget", "id": fid})
```

Один рядок, але три наслідки. Метод приймає ідентифікатор, а не текст, тому його треба отримати з ключів `facts()` або
через `fact_id(text)`. Метод не перевіряє, чи факт існує. Текст факта лишається у файлі в попередньому рядку, тому для
справжнього видалення особистих даних журнал доведеться переписати окремою дією.

### `FactMemory.extract`

```python
def extract(self, llm: LLM, text: str, source: str) -> list[str]:
    r = llm.complete(EXTRACT_PROMPT, [{"role": "user", "content": text}], [SAVE_FACTS_SCHEMA], 600)
    added = []
    for c in r.tool_calls:
        if c.name == "save_facts":
            for f in c.arguments.get("facts", []):
                if isinstance(f, str) and f.strip() and self.add(f.strip(), source):
                    added.append(f.strip())
    return added
```

**Перший рядок** — виклик моделі. Аргументи йдуть у такому порядку: системний промпт, повідомлення, інструменти,
найбільша кількість токенів у відповіді (метод `complete` у `harness/llm.py`). Головна історія сюди не потрапляє:
модель бачить лише переданий текст.

**`for c in r.tool_calls`** перебирає виклики інструментів у відповіді моделі. Кожен такий виклик має `name` і
`arguments`. Модель могла викликати `save_facts` кілька разів, і цикл це врахує.

**Внутрішня умова** використовує те, що `and` зупиняється на першому хибному значенні, як `&&` у JavaScript:

1. `isinstance(f, str)` перевіряє, що це рядок, як `typeof f === "string"`. Модель могла надіслати число.
2. `f.strip()` дає порожній рядок для тексту з одних пробілів, а порожній рядок вважається хибним.
3. `self.add(...)` записує факт і повертає `True`, лише якщо він новий. Запис стоїть в умові навмисно: у `added`
   потраплять лише справді нові факти.

**Крайні випадки.**

- Код не змушує модель викликати інструмент: `tool_choice` у `harness/llm.py` не передається. Якщо модель відповість
  текстом, метод тихо поверне порожній список.
- Обмеження в 600 токенів може обрізати відповідь. Для провайдерів, сумісних з OpenAI, хибний JSON стає
  `{"__invalid_json__": ...}`, `get("facts", [])` дає порожній список, і знову все минає тихо.
- Метод не проходить через `_execute` і `validate_args` із модуля 2, тому схему ніхто не перевіряє.

**Спробуй передбачити.** Модель надіслала `{"facts": "Любить каву"}`, тобто рядок замість масиву. Що запишеться?

<details><summary>Відповідь</summary>

Цикл `for` над рядком перебирає його літери, а кожна літера проходить `isinstance(f, str)`. Пробіл відсіє `f.strip()`,
і в журнал запишуться десять фактів, кожен з однієї літери. Тому після такого виклику варто перевіряти, що значення
справді є списком.

</details>

### `FactMemory.recall`

```python
def recall(self, query: str, k: int = 5) -> list[str]:
    """Простейший поиск по пересечению слов. В продакшене — эмбеддинги + BM25."""
    q = set(_norm(query).split())
    scored = []
    for text in self.facts().values():
        words = set(_norm(text).split())
        score = len(q & words) / (len(words) ** 0.5 or 1)
        if score > 0:
            scored.append((score, text))
    return [t for _, t in sorted(scored, reverse=True)[:k]]
```

- `k: int = 5` — це параметр зі значенням за замовчуванням, як у JavaScript.
- `.split()` без аргументів ділить текст за пробілами. `set(...)` прибирає повтори, як `new Set(...)`.
- `self.facts().values()` дає тексти фактів, як `Object.values`.
- `q & words` — перетин двох множин, тобто спільні слова. У JavaScript для цього довелося б писати `filter`.
- `len(words) ** 0.5` — квадратний корінь: `**` означає степінь. Ділення зменшує оцінку довгих фактів, бо в них
  випадковий збіг слова ймовірніший.
- `or 1` рятує від ділення на нуль. Python `or` повертає перше істинне значення, як `||`. Для факта без слів корінь
  дає нуль, а нуль хибний, тому дільником стане 1.
- `(score, text)` — це **кортеж** (tuple), тобто незмінний список, тут із двох значень. `sorted` порівнює кортежі
  поелементно: спершу за оцінкою, а за рівної оцінки за текстом. `reverse=True` дає найбільші спочатку.
- `[:k]` бере перші `k` результатів.
- `[t for _, t in ...]` — **списковий вираз** (list comprehension), аналог `.map(([_, t]) => t)`. Він розгортає кожен
  кортеж на дві змінні, а `_` за домовленістю означає «це значення не потрібне».

**Спробуй передбачити.** Є факти `Пише бекенд на Go`, `Обирає PostgreSQL, а не MongoDB`,
`Робить сервіс бронювання переговорних кімнат`. Що поверне `recall("go postgresql")`? А
`recall("яку базу даних обрати")`?

<details><summary>Відповідь</summary>

Перший запит поверне два факти: `Пише бекенд на Go` з оцінкою 1 / √4 = 0,5 і `Обирає PostgreSQL, а не MongoDB` з
оцінкою 1 / √5 ≈ 0,45. Другий поверне порожній список: слова «базу» й «даних» у фактах немає, а «обрати» й «обирає»
для коду різні слова. Для української мови, де слова змінюють закінчення, це головна слабкість такого пошуку.

</details>

Короткі слова на кшталт `на`, `а`, `не` теж рахуються, тому запит «на чому ми зупинилися» знайде всі факти зі словом
`на`.

### Ескізи виправлень

Це наш код, а не код курсу. Він ілюструє межі, описані в лекції. Ескізи `append` і `read` ми перевірили окремим
дослідом, а хуки випробуй у власному агенті.

**Збереження після кожного кроку.** `run_agent` змінює список `messages` на місці: навіть рядок `messages[:] = ...`
замінює вміст того самого списку, а не створює новий. Тому `s["messages"]` завжди містить актуальну історію, і хуку
досить викликати `save`.

```python
s = sessions.load("s1")
s["messages"].append({"role": "user", "content": task})

def save_before_call(messages):
    sessions.save(s)
    return messages

run_agent(llm, system, s["messages"], tools, before_model_call=save_before_call)
sessions.save(s)
```

Перший виклик хука і є записом наперед, тому окремий `save` перед `run_agent` не потрібен. Останній `save` потрібен,
бо після останньої відповіді моделі хук уже не спрацює. Хук тут один на все, тому компакцію з модуля 3 і збереження
доведеться об'єднати в одній функції.

Цей хук зберігає лише цілісні стани, де кожен виклик має результат. Якщо програма впаде під час виконання інструмента,
сліду цього виклику у файлі не буде, і модель може повторити дію, не знаючи про це. Подія `on_event` дає інший
варіант:

```python
from harness.loop import default_events

def save_on_event(kind, data):
    default_events(kind, data)                    # лишити звичайний друк у термінал
    if kind in ("assistant", "tool_result"):      # після відповіді моделі й після кожного результату
        sessions.save(s)
```

Цю функцію передають параметром `on_event=save_on_event`. Подія `"assistant"` спрацьовує одразу після відповіді моделі
й до виконання інструментів, тому у файлі лишиться виклик без результату. Для такого файла й існує
`repair_dangling_tool_calls`: модель побачить `INTERRUPTED` і знатиме, що результат невідомий.

**Запис, що переживає вимкнення живлення.**

```python
with tmp.open("w", encoding="utf-8") as f:
    f.write(json.dumps(session, ensure_ascii=False, indent=1))
    f.flush()              # із буфера Python до операційної системи
    os.fsync(f.fileno())   # з кешу операційної системи на диск
os.replace(tmp, p)
```

На Linux для повної гарантії треба ще викликати `fsync` для самої теки, бо перейменування теж спершу лежить у кеші.
Ціна `fsync` у тому, що кожен запис чекає на диск.

**Тест на склеювання.** Цей тест можна додати до `StateTests` у `tests/test_harness.py`. На коді курсу він не пройде,
бо `read` поверне лише `["1"]`:

```python
def test_append_after_torn_record(self):
    lg = Ledger(self.tmp / "l.jsonl")
    lg.append({"op": "add", "id": "1", "text": "a"})
    with lg.path.open("a") as f:
        f.write('{"op": "add", "id": "2", "te')     # обірваний запис, як у тесті курсу
    lg.append({"op": "add", "id": "3", "text": "c"})
    self.assertEqual([r["id"] for r in lg.read()], ["1", "3"])
```

**`append`, що перевіряє кінець файла.** Режим `"a+b"` дозволяє дописувати й читати байти, а `b"\n"` — це один байт
переносу. `seek` пересуває позицію читання й у цьому режимі повертає її нове значення. Запис у режимі дописування все
одно йде в кінець файла.

```python
def append(self, record: dict) -> None:
    line = json.dumps({"ts": time.time(), **record}, ensure_ascii=False) + "\n"
    with self.path.open("a+b") as f:
        if f.seek(0, os.SEEK_END) > 0:          # файл не порожній
            f.seek(-1, os.SEEK_END)
            if f.read(1) != b"\n":              # попередній запис обірвано
                f.write(b"\n")
        f.write(line.encode("utf-8"))
```

**`read`, стійкий до обох слабких місць.** `errors="replace"` замінює биті байти спеціальним символом, рядок доходить
до `json.loads` і пропускається, бо лапка в ньому не закрита. `split("\n")` ділить рядки лише за переносом.

```python
for line in self.path.read_text(encoding="utf-8", errors="replace").split("\n"):
```

### Урок `examples/04_memory.py`

**Де читати:**
[`examples/04_memory.py`](https://github.com/justxor/agent-harness-course/blob/0c90ce7bbeef858426abfeeacacbdb438921c078/examples/04_memory.py),
70 рядків. Він показує всі три класи разом. Запускай без ключа API: за замовчуванням `from_env` використовує
заготовлену модель `ScriptedLLM`.

```python
sessions = SessionStore(DATA / "sessions")
memory = FactMemory(Ledger(DATA / "facts.jsonl"))
```

Обидва сховища лежать у теці `examples/_data`. Команда `python3 examples/04_memory.py --reset` видаляє цю теку, щоб
почати спочатку. Функція `scripted` підмінює модель: якщо серед інструментів є `save_facts`, вона повертає три
заготовлені факти, а якщо в системному промпті є «Что ты знаешь», повертає відповідь про пам'ять. Отже, факти нічого
не витягують із тексту: у цьому режимі вони записані в уроці наперед.

Далі урок дивиться, чи є вже факти (`known = memory.facts()`), і йде однією з двох гілок.

**Перший запуск: пам'яті немає.** Програма читає чи створює сесію `s1`, дописує повідомлення, робить `sessions.save`,
викликає модель, дописує відповідь, знову робить `sessions.save`, а потім викликає `memory.extract` для першого
повідомлення. Вивід приблизно такий:

```text
— Сессия 1: памяти нет —
🤖 Отлично: Go + PostgreSQL — хороший выбор для бронирований, транзакции и exclusion-constraint защитят от двойных броней.

Извлечённые факты (сохранены в facts.jsonl):
  • Пользователь пишет бэкенд на Go
  • Пользователь предпочитает PostgreSQL, а не MongoDB
  • Проект пользователя — сервис бронирования переговорок

Запусти скрипт ещё раз — начнётся новая сессия с этой памятью.
```

**Другий запуск: пам'ять є.** Програма шукає факти через `memory.recall("база данных проект бронирования Go")`,
вставляє знайдені в системний промпт і викликає модель лише з новим повідомленням. Вивід приблизно такий:

```text
— Сессия 2: память есть —
В системный промпт подмешано:
- Проект пользователя — сервис бронирования переговорок
- Пользователь пишет бэкенд на Go
(Факт про PostgreSQL не нашёлся: в запросе «база данных», а в факте «PostgreSQL». Поиск по словам не видит синонимов — для этого нужны эмбеддинги, см. урок 4.4.)

🤖 Помню: ты пишешь на Go, любишь PostgreSQL и делаешь сервис бронирования переговорок. Продолжим со схемой БД?

Сессии на диске: ['s1']  ·  фактов в памяти: 3
Сырой журнал: …/examples/_data/facts.jsonl
```

**На що звернути увагу.**

- Заготовлена відповідь згадує PostgreSQL, хоча цього факта в промпті немає. Це записаний наперед рядок, а справжня
  модель так не відповіла б. Перевір це, запустивши урок зі справжньою моделлю.
- Повідомлення згадує «урок 4.4». У тексті модуля такої нумерації немає, ідеться про абзац «Поиск по памяти».
- Другий запуск не завантажує транскрипт `s1`. Він працює лише з фактами, і нова сесія теж не зберігається, тому на
  диску лишається один файл. Отже, урок показує довготривалу пам'ять, а продовження сесії після падіння не показує.
- Якщо перший запуск упаде до кінця витягу, фактів не буде, тому наступний запуск знову піде першою гілкою і допише те
  саме повідомлення до `s1` вдруге.
- Урок не використовує `run_agent`, тому збереження після кожного кроку доведеться писати тобі.

### Що взяти у свого агента

- Викликай збереження сесії до кожного звернення до моделі й перевіряй це заготовленою моделлю, яка падає.
- Пиши продовження сесії за останнім повідомленням файла й не дописуй повідомлення людини вдруге.
- Виправ `append` і `read` у своїй копії журналу, бо твої факти будуть кириличними.
- Додай перевірку типів до витягу фактів: список, рядки, непорожні значення.

## Стаття «Factor 5: Unify execution state»

**Де читати:** [Factor 5 у репозиторії 12-Factor
Agents](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-05-unify-execution-state.md),
англійською. Повна назва правила: «Unify execution state and business state», тобто «об'єднай стан виконання й
бізнес-стан».

**Що це за текст.** Одне з дванадцяти правил про інженерію агентів, про які йшлося в модулі 0. Текст дуже короткий,
тому читай його повністю.

**Головна думка.** Системи часто зберігають окремо дані роботи й службові відомості про те, на якому вона кроці. В
агента службові відомості часто можна обчислити з історії розмови, тому два сховища можна замінити одним.

### Вступ: `execution state` і `business state`

Автор розрізняє два види стану. Слово «business» тут може ввести в оману, бо йдеться не про замовлення чи клієнтів у
твоїй базі даних.

| Термін у статті | Що це означає | Приклади зі статті |
|-----------------|---------------|--------------------|
| execution state, стан виконання | де саме зараз перебуває робота | поточний крок, наступний крок, чи чекаємо на щось, скільки було повторів |
| business state, бізнес-стан | що вже сталося в роботі агента | список повідомлень, виклики інструментів і їхні результати |

Автор не стверджує, що поділ завжди шкодить. Він каже, що поділ додає складності, яка буває виправданою, але часто
зайва, і що рішення лишається за тобою. Заклик звучить так: якщо можеш, спрощуй і об'єднуй.

### `In reality, you can engineer your application...`

Тут головне твердження: застосунок можна побудувати так, щоб весь стан виконання виводився з **context window**, тобто
з контексту, який модель отримує в запиті. Поточний крок і статус очікування часто є лише метаданими про те, що вже
сталося.

Подивись на це через код курсу. Поля «поточний крок» у файлі сесії немає, але таблиця в лекції показує, що останнє
повідомлення його замінює: якщо там `user`, відповідь не прийшла; якщо `assistant` без викликів, робота закінчена.

### `You may have things that can't go in the context window`

Є дані, яким у контексті не місце: автор називає ідентифікатори сесій і паролі. Їх варто тримати окремо, але таких
даних має бути якомога менше. Посилання на Factor 3 нагадує, що ти сам вирішуєш, що саме піде до моделі, тому історія
й запит не мусять збігатися повністю. У коді курсу так і є: поля `id` і `created` лежать у файлі сесії, а до моделі
йде лише `messages`.

### `This approach has several benefits`

Слово **thread** у цьому списку означає послідовність подій однієї роботи агента, тобто ту саму історію.

| Перевага | Що це означає | Як це виглядає в коді курсу |
|----------|---------------|-----------------------------|
| Simplicity | Одне джерело правди для всього стану | один файл сесії |
| Serialization | Історію легко перетворити на текст і назад | `json.dumps` і `json.loads` у `SessionStore` |
| Debugging | Уся історія видна в одному місці | відкрий `s1.json` і читай |
| Flexibility | Новий вид стану додається новим типом події | `add` і `forget` у журналі: згортка ігнорує невідомі типи |
| Recovery | Продовжити з будь-якої точки можна, завантаживши історію | `sessions.load`, а потім виклик моделі |
| Forking | Можна розгалузити роботу, скопіювавши частину історії в новий стан | взяти `messages[:k]` у нову сесію й спробувати інший шлях |
| Human Interfaces and Observability | Історію легко показати людині | кілька рядків коду перетворять її на markdown чи вебсторінку |

### Що взяти у свого агента

- Перш ніж додавати поле на кшталт `current_step`, перевір, чи не можна його обчислити з історії.
- Зберігай окремо лише те, чого моделі показувати не можна.
- Врахуй, що лічильник кроків і підрахунок токенів усередині `run_agent` в історії не лежать. Після перезапуску вони
  почнуться з нуля, тому кількість кроків можна обчислювати за кількістю повідомлень `assistant`.

### Запитання до статті

**1. Що таке `business state` у цій статті? Чи це дані твого застосунку, наприклад замовлення?**

<details><summary>Відповідь</summary>

Ні. Автор називає так історію роботи агента: повідомлення, виклики інструментів і їхні результати.

</details>

**2. Агент чекає на відповідь людини. Як зрозуміти це з історії, без окремого поля статусу?**

<details><summary>Відповідь</summary>

Подивитися на останнє повідомлення. Якщо це відповідь `assistant` без викликів інструментів чи виклик інструмента із
запитанням до людини без результату, агент чекає на людину.

</details>

**3. Що варто зберігати поза історією?**

<details><summary>Відповідь</summary>

Те, що не має потрапити до моделі: секрети, службові ідентифікатори. Автор радить тримати таких даних якомога менше.

</details>

## Стаття «Factor 12: Stateless reducer»

**Де читати:** [Factor 12 у репозиторії 12-Factor
Agents](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-12-stateless-reducer.md), англійською.
Повна назва правила: «Make your agent a stateless reducer», тобто «зроби свого агента редьюсером без стану».

**Що це за текст.** Тут одне речення й два малюнки. Автор сам пише, що це правило додано здебільшого заради розваги,
тому не шукай у ньому докладної інструкції. Весь зміст лежить у малюнках.

**Головна думка.** На агента можна дивитися як на функцію, яка отримує контекст і повертає новий контекст, а між
викликами нічого не зберігає в собі.

### Перший малюнок

Малюнок показує замкнуте коло. Зліва вгорі лежить `Context`, тобто кілька подій. Вони потрапляють у блок
`Determine Next Step`, де модель вирішує, що робити далі. Далі стрілки розходяться на кілька гілок під підписом
`Handle Next Step`, тобто на обробники різних рішень, а біля останньої стоїть `whatever you want`: тут може бути
будь-який твій код. Результат стає `New Context`, у якому подій більше, і коло починається знову.

У коді курсу це той самий цикл `run_agent` із модуля 2.

### Другий малюнок

Це знімок допису автора в соціальній мережі. Він починає з думки, що агент у певному сенсі є циклом `for`, і запитує,
як це сказати мовою Lisp, мови функціонального програмування. Відповідь така: «an AI Agent is a foldL where the
accumulator is a context window, and the reducer is an LLM DetermineNextStep + a switch statement on how to handle
it».

Ти знаєш усі ці поняття з `Array.prototype.reduce` і Redux, хоча слова інші:

| Вираз у дописі | Що це означає | Що це в JavaScript | Що це в `run_agent` |
|----------------|---------------|--------------------|---------------------|
| foldL | Згортка зліва направо | метод `reduce` | цикл `for step in range(...)` |
| accumulator | Значення, яке переходить із кроку в крок | перший аргумент функції в `reduce` | список `messages` |
| reducer | Функція «стан і подія дають новий стан» | редьюсер у `useReducer` | тіло циклу |
| LLM DetermineNextStep | Модель вирішує наступний крок | немає аналога | `llm.complete` |
| switch statement | Вибір обробника за рішенням моделі | `switch (action.type)` | `if not reply.tool_calls` і `_execute` |

### Наскільки код курсу відповідає цій картині

Близько, але є три відмінності, і вони корисні для розуміння:

- `run_agent` змінює список `messages` на місці, а редьюсер у Redux мусить повертати новий об'єкт.
- Інструменти роблять справжні дії: пишуть файли чи надсилають листи. Тому повторний прохід історії в агенті не можна
  запускати так само вільно, як у Redux DevTools.
- Лічильник `step` і підрахунок `usage` живуть усередині функції, поза `messages`. Після перезапуску вони починаються
  спочатку.

Модуль 0 казав, що стану не має модель. Тут ідеться про агента: увесь стан лежить у списку, який йому передають. Тому
після падіння досить завантажити файл і викликати функцію знову, а для перевірки досить передати заготовлену історію й
подивитися на результат. Найчистіший приклад такої згортки в цьому модулі — не `run_agent`, а `FactMemory.facts`.

### Що взяти у свого агента

- Тримай увесь стан розмови в даних, які можна зберегти у файл, а не в змінних усередині функцій.
- Перевіряй агента так: передай заготовлену історію, подивись на наступний крок.

### Запитання до статті

**1. Що в `run_agent` виконує роль акумулятора?**

<details><summary>Відповідь</summary>

Список `messages`: він переходить із кроку в крок і наприкінці містить результат усієї роботи.

</details>

**2. Чому після падіння не можна сліпо пройти всю історію заново, як у Redux DevTools?**

<details><summary>Відповідь</summary>

Бо дії інструментів справжні. Повторне виконання надішле лист удруге. Тому програма завантажує збережену історію й
продовжує з кінця, а не виконує її спочатку.

</details>

**3. Чим згортка в `FactMemory.facts` чистіша за `run_agent`?**

<details><summary>Відповідь</summary>

Вона нічого не робить назовні: читає записи й обчислює словник. Той самий журнал завжди дасть той самий результат,
тому її можна запускати скільки завгодно разів.

</details>

## Сторінка Memory tool

**Де читати:** [сторінка `Memory tool`](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool) у
документації API Anthropic, англійською; ту саму сторінку знайде сервер MCP `anthropic-api-docs`. Її можна читати
вибірково: розділи `How it works`, `Tool commands` (лише назви команд), `Security considerations` і
`Multisession software development pattern`. Приклади коду багатьма мовами пропусти.

**Що це.** Готовий інструмент, який компанія Anthropic описала для своїх моделей. Модель створює, читає, змінює й
видаляє файли пам'яті в теці `/memories`, а файли переживають кінець розмови. У запиті досить вказати
`{"type": "memory_20250818", "name": "memory"}` у полі `tools`, опис параметрів додавати не треба.

**Хто виконує.** Твоя програма. Сторінка називає це **client-side**, тобто виконання на твоєму боці. Модель лише
просить операцію, а твій код виконує її й повертає результат як звичайний результат інструмента. Це той самий принцип
із лекції 0: модель не робить нічого сама. Шлях `/memories` є лише префіксом, який твій код перетворює на справжнє
сховище: теку на диску чи записи в базі даних.

**Команди.**

| Команда | Що робить |
|---------|-----------|
| `view` | показує вміст теки або файла з номерами рядків |
| `create` | створює файл |
| `str_replace` | замінює текст у файлі |
| `insert` | вставляє текст після вказаного рядка |
| `delete` | видаляє файл чи теку |
| `rename` | перейменовує чи переміщує |

**Вказівка в промпті.** Якщо інструмент увімкнено, API сам додає до системного промпта вказівку: спершу переглянути
теку пам'яті, а в процесі роботи записувати туди прогрес. Там є вираз `ASSUME INTERRUPTION`: контекст може бути
скинуто будь-якої миті, тому незаписаний прогрес можна втратити. Це та сама думка, що й у записі наперед.

**Безпека.** За кожну операцію відповідає твій код, тому сторінка перелічує обов'язки:

- перевіряти кожен шлях, бо `/memories/../../secrets.env` вийде за межі теки. Це та сама проблема, яку
  `SessionStore.path` розв'язує регулярним виразом;
- обмежувати розмір файлів і кількість символів, які повертає `view`;
- час від часу видаляти файли, до яких давно не зверталися;
- не покладатися лише на модель щодо чутливих даних і прибирати їх перед записом.

**Пам'ять і компакція.** Сторінка радить поєднувати їх для довгих завдань: компакція тримає контекст малим, а пам'ять
зберігає те, що має пережити стискання.

**Схема для багатьох сесій.** Перша сесія створює файли пам'яті до початку роботи: журнал прогресу й перелік завдань.
Кожна наступна сесія починає з їхнього читання, а перед завершенням оновлює журнал. Завдання вважається виконаним лише
після перевірки від початку до кінця, інакше журнал прогресу стане неточним.

**Порівняння з кодом курсу.**

| | `FactMemory` у курсі | `Memory tool` |
|-|----------------------|---------------|
| Хто вирішує, що запам'ятати | окремий виклик моделі після розмови | головна модель під час роботи |
| Формат | журнал JSONL, один рядок на подію | файли, які модель пише як хоче |
| Зміна даних | лише дописування, історія ціла | файл змінюється на місці, історії немає |
| Видалення | `forget`, текст лишається в журналі | `delete` прибирає файл, якщо так реалізує твій код |
| Як пам'ять доходить до моделі | програма вставляє її в промпт | модель читає сама, виклик за викликом |
| Ризик | витяг пропустить важливе | модель захаращує теку зайвими файлами |

Отже, `Memory tool` належить до другого варіанта з головного рішення модуля: модель шукає сама й платить за це
кроками. Інструмент `remember(fact)` із практики належить до того самого варіанта, бо модель сама вирішує, що
запам'ятати.

**Запитання.** Чому сторінка так наполягає на перевірці шляхів, якщо шляхи пише модель, а не зловмисник?

<details><summary>Відповідь</summary>

Модель можна обдурити: текст, який вона прочитала, може містити вказівку записати чи прочитати файл поза пам'яттю.
Докладно про такі атаки йдеться в модулі 6. Крім того, модель може помилитися й без чужого втручання. Гарантію дає
лише перевірка в коді.

</details>
