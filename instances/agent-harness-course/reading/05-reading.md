### Потоки й черга для того, хто знає асинхронність із JavaScript

У цьому файлі немає ні `async`, ні `await`, тому спершу треба зрозуміти іншу модель.

**Як це працює в JavaScript.** Твій код виконується в одному потоці. Коли функція доходить до `await fetch(...)`, вона
призупиняється, а цикл подій (event loop) виконує інші функції. Між двома `await` ніхто не може втрутитися, тому `n++`
завжди виконується цілком.

**Як у `jobs.py`.** Файл використовує **потоки виконання** (англійською threads). Потік — це окрема послідовність дій
усередині однієї програми. Кожен потік виконує звичайний послідовний код і сам чекає на мережу чи таймер. Поки один
потік чекає, інші працюють. Головна відмінність: перемикання між потоками від тебе не залежить і може статися
будь-якої миті, навіть посеред `self._n += 1`. Тому спільні дані доводиться захищати. Не плутай потік виконання зі
стрімом (stream), який українською теж часто називають потоком.

| Що потрібно | JavaScript | Python у `jobs.py` |
|-------------|------------|--------------------|
| Запустити роботу у фоні | викликати `async`-функцію без `await` | `threading.Thread(target=run, daemon=True).start()` |
| Дочекатися результату | `await promise`: функція призупиняється | `inbox.get(timeout=...)`: цей потік стоїть, а інші працюють |
| Передати результат | `resolve(value)` | `inbox.put(message)` |
| Захистити лічильник | нічого не потрібно | `with self._lock:` |
| Не тримати процес через фонову роботу | `timer.unref()` у Node.js | `daemon=True` |
| Помилка у фоні | відхилений `Promise` | виняток у потоці: друкується в терміналі, а решта програми про нього не дізнається |
| Скасувати роботу | `AbortController` і його `signal` | вбудованого способу немає, потрібен власний прапорець |

**Чи справді потоки працюють одночасно.** У звичайній збірці Python код Python у будь-яку мить виконує лише один
потік. Це обмеження називається GIL (global interpreter lock, глобальне блокування інтерпретатора). Але потік, який
чекає на мережу чи `time.sleep`, це блокування відпускає. Субагент майже весь час чекає на відповідь моделі, тому три
субагенти справді чекають одночасно, а програма завершує роботу приблизно за час одного. Для важких обчислень потоки
не дали б такого виграшу.

**Навіщо черга.** `queue.Queue` — це черга за правилом «першим прийшов, першим вийшов», якою безпечно користуватися з
кількох потоків. Вона вміє те, чого не вміє звичайний список: метод `get` зупиняє потік, доки в черзі щось не
з'явиться. Так фоновий потік передає результат головному, і жоден із них не працює зі спільними даними безпосередньо.

Ось уся ідея в мінімальному вигляді. Це наш приклад, а не код курсу:

```python
import queue, threading, time

q = queue.Queue()

def worker():
    time.sleep(1)
    q.put("готово")

threading.Thread(target=worker, daemon=True).start()
print("чекаю")
print(q.get(timeout=5))
```

Те саме на JavaScript:

```js
const result = new Promise(resolve => setTimeout(() => resolve("готово"), 1000));
console.log("чекаю");
console.log(await result);
```

**Спробуй передбачити:** що станеться, якщо в прикладі на Python замінити `q.get(timeout=5)` на `q.get_nowait()`?

<details><summary>Відповідь</summary>

Виникне виняток `queue.Empty`. Потік `worker` ще спить, тому черга порожня, а `get_nowait` не чекає. Саме цей виняток
перехоплює `collect`.

</details>

### Початок файла: опис та імпорти

```python
from __future__ import annotations

import queue
import threading
import time
from dataclasses import dataclass, field
from typing import Callable
```

Перед імпортами стоїть опис файла, тобто рядок у потрійних лапках (docstring). У ньому записано п'ять кроків схеми, і
варто звірити їх зі схемою з лекції.

- `from __future__ import annotations` вимикає обчислення анотацій типів під час виконання. Як і в TypeScript, типи
  тут лишаються підказками для людей та інструментів перевірки.
- `queue`, `threading` і `time` входять до самого Python, тому код не має сторонніх залежностей.
- `dataclass` і `field` потрібні для класу `Job`, а `Callable` описує тип функції.

### Клас `Job`

```python
@dataclass
class Job:
    id: str
    kind: str
    input: dict
    status: str = "running"   # running | done | error
    result: str = ""
    started: float = field(default_factory=time.time)
```

Це запис про одне завдання.

- `@dataclass` — **декоратор**, тобто функція, яка отримує клас і змінює його. Цей декоратор створює конструктор за
  переліком полів. Поля без значень за замовчуванням ідуть першими, тому `Job(jid, kind, inp)` заповнює `id`, `kind`
  та `input` за порядком. У TypeScript це схоже на клас із `constructor(public id: string, ...)`.
- `id` має вигляд `job_1`, а `kind` називає вид роботи, наприклад `research`. `input` зберігає вхідні дані.
- `status` — звичайний рядок. Коментар перелічує три можливі значення: у TypeScript тут був би тип `"running" | "done"
  | "error"`, а Python цього не перевіряє.
- `field(default_factory=time.time)` викликає `time.time` для кожного нового об'єкта. Тут є пастка для того, хто
  прийшов із JavaScript. У класі JS вираз `started = Date.now()` обчислюється для кожного об'єкта окремо. У Python
  запис `started: float = time.time()` обчислився б один раз під час створення класу, і всі завдання отримали б
  однаковий час. Зверни увагу: `time.time` передано без дужок, тобто передано саму функцію. Вона повертає секунди, а
  `Date.now()` повертає мілісекунди.

Поля `input` і `started` ніхто не читає ні в цьому файлі, ні в уроці. Вони знадобляться для відновлення: за `input`
завдання можна запустити знову, а за `started` помітити завдання, яке працює підозріло довго.

### `JobRunner.__init__`

```python
class JobRunner:
    def __init__(self):
        self.jobs: dict[str, Job] = {}
        self.inbox: "queue.Queue[dict]" = queue.Queue()   # steer-сообщения для главного агента
        self.delivered: set[str] = set()                   # exactly-once
        self._n = 0
        self._lock = threading.Lock()
```

`__init__` — це конструктор, а `self` відповідає `this`, тільки записується явно.

- `jobs` — словник «номер → завдання», у JavaScript це `Map<string, Job>`.
- `inbox` — вхідна черга. Лапки в анотації не впливають на виконання: це та сама підказка для людей та інструментів.
- `delivered` — множина вже доставлених ідентифікаторів, у JavaScript `new Set()`. Пишеться `set()`, бо `{}` у Python
  створює порожній словник.
- `_n` — лічильник завдань. Підкреслення на початку імені є лише домовленістю «це внутрішнє», і Python нічого не
  забороняє.
- `_lock` — **замок** (англійською lock): об'єкт, який дозволяє лише одному потокові за раз виконувати певний шматок
  коду.

**Що зламається.** Усі п'ять полів зберігаються лише в пам'яті об'єкта. Коли програма завершується, вони зникають.
Саме тут починається головна межа цього коду, яку описано в лекції: черга, завдання, множина й лічильник не
переживають перезапуску.

### `JobRunner.spawn`

Цей метод запускає завдання. Розглянемо його трьома частинами.

```python
    def spawn(self, kind: str, inp: dict, work: Callable[[dict], str]) -> str:
        with self._lock:
            self._n += 1
            jid = f"job_{self._n}"
        job = self.jobs[jid] = Job(jid, kind, inp)
```

- `work: Callable[[dict], str]` — функція, яка приймає словник і повертає рядок. У TypeScript це `(inp: Dict) =>
  string`. `JobRunner` нічого не знає про агентів, тому може виконати будь-яку таку функцію, а `-> str` означає, що
  `spawn` повертає рядок.
- `with self._lock:` бере замок на час відступленого блока й віддає його після виходу з блока, навіть якщо виникла
  помилка. Це коротший запис такої схеми: взяти замок, `try`, у `finally` віддати.
- **Навіщо замок.** `self._n += 1` складається з трьох дій: прочитати, додати, записати. Якщо два потоки прочитають
  число 4, обидва запишуть 5, отримають номер `job_5` і однаковий `steer_job_5`. Тоді результат другого завдання буде
  відкинуто як дублікат. В уроці `spawn` викликає лише головний потік, тому замок є запобіжником на випадок, коли
  завдання запускатиме сам субагент.
- `f"job_{self._n}"` — **f-рядок**, у JavaScript це `` `job_${n}` ``.
- `job = self.jobs[jid] = Job(...)` створює один об'єкт і записує його в обидва місця: у локальну змінну й у словник.

```python
        def run():
            try:
                job.result, job.status = work(inp), "done"
            except Exception as e:
                job.result, job.status = f"{type(e).__name__}: {e}", "error"
            # детерминированный id → повторная доставка распознаётся и отбрасывается
            self.inbox.put({"steer_id": f"steer_{jid}", "job": jid, "kind": kind,
                            "status": job.status, "result": job.result})
```

Функція `run` оголошена всередині `spawn` і бачить його змінні `job`, `work`, `inp`, `jid`, `kind`. Це таке саме
замикання, як у JavaScript.

- `job.result, job.status = work(inp), "done"` — присвоєння кількох значень, у JavaScript `[job.result, job.status] =
  [work(inp), "done"]`. Спершу обчислюється вся права частина, і `work(inp)` може тривати кілька хвилин. Потім
  значення присвоюються зліва направо: спершу результат, потім статус. Тому той, хто побачить статус `done`, побачить
  і готовий результат.
- Якщо `work` викине помилку, жодне поле не зміниться, і виконання перейде до `except`.
- `except Exception as e` перехоплює помилки, а `type(e).__name__` дає назву їхнього класу. Наприклад, результатом
  може стати рядок `LLMError: HTTP 429 ...`. Помилка стає звичайним результатом, бо головний агент мусить дізнатися,
  що обіцяного результату не буде.
- **Що зламається без `try`.** Необроблений виняток завершує лише цей потік і друкується в терміналі. Повідомлення не
  потрапляє в чергу, статус назавжди лишається `running`, а `collect` чекає до кінця свого часу.
- **Крайній випадок.** `Exception` не охоплює `SystemExit`. Якщо всередині `work` викликати `sys.exit()`, потік
  завершиться мовчки, статус лишиться `running`, а повідомлення не буде. У JavaScript `catch (e)` перехоплює все, а
  тут ні.
- `self.inbox.put(...)` стоїть після обох гілок, тому повідомлення надходить і після успіху, і після помилки. Черга не
  має обмеження розміру, тому `put` не чекає.
- `f"steer_{jid}"` — це той самий детермінований ідентифікатор: завдання `job_1` завжди дає `steer_job_1`.

**Зверни увагу на порядок.** Статус змінюється на рядку 44, а повідомлення кладеться в чергу на рядку 48. Текст курсу
обіцяє протилежне: статус мав би змінюватися після збереження ходу. Про наслідок цього порядку йдеться наприкінці
цього розділу.

```python
        threading.Thread(target=run, daemon=True).start()
        return jid
```

- `target=run` передає саму функцію, без дужок. Якби написати `target=run()`, вся робота виконалася б тут, у головному
  потоці, і фону не було б.
- `.start()` запускає новий потік. Метод `.run()` виконав би функцію в поточному потоці, тому їх важливо не плутати.
- `daemon=True` робить потік **демоном**: програма не чекатиме його під час завершення, і він обірветься разом із нею.
  Без цього параметра програма чекала б кінця роботи, навіть коли головний код закінчився. Аналогія з Node.js: це
  схоже на `timer.unref()`, де таймер теж не тримає процес живим.
- `return jid` виконується відразу після старту потоку. Завдяки цьому інструмент `research` миттєво відповідає
  підтвердженням.

**Спробуй передбачити:** що виведе цей код?

```python
r = JobRunner()

def broken(inp):
    raise ValueError("сломалось")

r.spawn("k", {}, broken)
print(r.collect(timeout=2))
```

<details><summary>Відповідь</summary>

Список з одним словником: `steer_id` дорівнює `steer_job_1`, `job` дорівнює `job_1`, `kind` дорівнює `k`, `status`
дорівнює `error`, а `result` дорівнює `ValueError: сломалось`. Помилка стала звичайним результатом. `collect`
завершується одразу після повідомлення, бо завдань зі статусом `running` більше немає.

</details>

### `JobRunner.collect`

```python
    def collect(self, timeout: float = 0.0) -> list[dict]:
        """Забрать готовые результаты. Дубликаты (тот же steer_id) отбрасываются."""
        out = []
        deadline = time.time() + timeout
        while True:
            remaining = max(0.0, deadline - time.time())
            try:
                msg = self.inbox.get(timeout=remaining) if remaining else self.inbox.get_nowait()
            except queue.Empty:
                break
            if msg["steer_id"] in self.delivered:
                continue
            self.delivered.add(msg["steer_id"])
            out.append(msg)
            if timeout and not self.pending():
                break
        return out
```

Цей метод має два режими. Без `timeout` він забирає все, що вже є, і не чекає. Із `timeout` він чекає, поки завдання
не закінчаться або не вийде час.

- `deadline` — момент у часі, коли треба припинити чекати. Він рахується один раз, а `remaining` перераховується на
  кожному кроці. Тому весь виклик чекає не довше за `timeout`, скільки б повідомлень не прийшло. Якби кожен `get`
  отримував повний `timeout`, очікування могло б тривати значно довше.
- `max(0.0, ...)` не дає значенню стати від'ємним, коли час уже вийшов.
- `A if умова else B` — це запис `умова ? A : B` із JavaScript. Значення `0.0` хибне, як `0` у JavaScript.
- `self.inbox.get(timeout=remaining)` зупиняє **цей потік** щонайбільше на `remaining` секунд. Інші потоки працюють
  далі, зокрема потоки субагентів. Якщо за цей час нічого не з'явилося, виникає виняток `queue.Empty`.
- `self.inbox.get_nowait()` забирає повідомлення негайно або одразу викидає той самий виняток.
- `except queue.Empty: break` використовує виняток як звичайний сигнал «у черзі порожньо». Для Python це поширений
  спосіб, хоча в JavaScript ти б перевіряв значення.
- `if msg["steer_id"] in self.delivered: continue` — це і є відкидання дублікатів. Оператор `in` для множини
  відповідає `delivered.has(id)`.
- `self.delivered.add(...)` позначає результат доставленим. Насправді він лише виданий тому, хто викликав `collect`: в
  історію він ще не потрапив. Якщо програма впаде тут, результат зникне.
- `if timeout and not self.pending(): break` завершує очікування, коли робіт більше немає. Без цього рядка
  `collect(timeout=5)` завжди чекав би всі 5 секунд.
- `return out` повертає весь список наприкінці, а не по одному повідомленню. Тому той, хто викликав `collect`,
  обробить результати лише після того, як очікування закінчиться.

Ось як поводиться метод у різних випадках:

| Виклик | Що відбувається | Результат |
|--------|-----------------|-----------|
| `collect()`, черга порожня | `get_nowait` одразу викидає `queue.Empty` | одразу `[]` |
| `collect()`, у черзі два повідомлення | забирає обидва, потім `queue.Empty` | одразу два повідомлення |
| `collect(timeout=5)`, завдання завершується за 1 с | `get` чекає 1 с, потім `pending()` порожній | одне повідомлення приблизно через 1 с |
| `collect(timeout=5)`, завдання триває 60 с | час виходить, `queue.Empty` | `[]` через 5 с, а результат прийде пізніше й чекатиме наступного виклику |
| `collect(timeout=5)`, жодне завдання не запущено | перевірка `pending()` стоїть лише після отриманого повідомлення | `[]` лише через 5 с |
| `collect(timeout=5)`, у черзі лише дублікат і немає робіт | `continue` пропускає перевірку `pending()` | `[]` лише через 5 с |

**Спробуй передбачити.** Це тест `test_jobs_exactly_once` із `tests/test_harness.py`, лише з `print` замість
перевірок. Запис `lambda inp: "готово"` — це функція з одного виразу, у JavaScript `inp => "готово"`. Запис
`dict(got[0])` робить копію словника, у JavaScript `{...got[0]}`.

```python

r.inbox.put(dict(got[0]))

```

`steer_id`, тому другий `collect` її відкидає. Зверни увагу, чого цей тест не перевіряє: перезапуску. Обидва виклики
працюють з одним об'єктом у пам'яті.

</details>

### `JobRunner.pending`

```python
    def pending(self) -> list[str]:
        return [j.id for j in self.jobs.values() if j.status == "running"]
```

Це **списковий вираз**: він будує новий список за одним рядком. У JavaScript те саме виглядало б так:
`[...jobs.values()].filter(j => j.status === "running").map(j => j.id)`. У Python спершу пишуть, що взяти (`j.id`),
потім звідки (`for j in ...`), а потім умову (`if ...`). Метод повертає номери завдань, які ще працюють.

**Крайній випадок.** Замок захищає лише лічильник. Якщо один потік проходить словник у `pending`, а інший додає
завдання через `spawn`, Python може викинути `RuntimeError`, бо словник змінив розмір під час перебору. В уроці
`spawn` і `pending` викликає один потік, тому це не проявляється. Якщо субагенти почнуть запускати власні завдання,
захисти замком і словник.

### `steer_message`

```python
def steer_message(s: dict) -> dict:
    """Результат фоновой задачи как user-сообщение для главного агента."""
    return {"role": "user", "steer_id": s["steer_id"],
            "content": f"[ФОНОВАЯ ЗАДАЧА {s['job']} ({s['kind']}) завершена со статусом {s['status']}]\n{s['result']}"}
```

Ця функція не належить до класу й нічого не змінює: вона перетворює повідомлення з черги на повідомлення для історії.
Наприклад, для `job_1` поле `content` почнеться так:

```text
[ФОНОВАЯ ЗАДАЧА job_1 (research) завершена со статусом done]
Итог: при 429 делай экспоненциальный backoff с джиттером, ...
```

- `"role": "user"` потрібна, бо у форматі API немає окремої ролі для фонового результату. Роль `tool` не підходить, бо
  вона вимагає ідентифікатора виклику, а на виклик `research` уже дано відповідь у вигляді підтвердження.
- Мітка в квадратних дужках показує моделі, що це не репліка людини. У власному агенті пиши її своєю мовою.
- `"steer_id"` — додаткове поле. До провайдера воно не доходить: функції `_to_wire` у `harness/llm.py` копіюють для
  такого повідомлення лише роль і текст (рядки 152 і 222). Воно лишається в локальній історії, а `SessionStore.save`
  зберігає його у файлі. Завдяки цьому після перезапуску можна перевірити, чи результат уже в історії. Лекція пояснює,
  як цим скористатися.
- Усередині f-рядка, написаного в подвійних лапках, ключі записано в одинарних лапках: `s['job']`. Python до версії
  3.12 не дозволяє тут використати той самий вид лапок.
- `s['result']` вставляється цілком. Функція не скорочує довгий текст.

### Урок `examples/05_subagents.py`: як це працює разом

**Субагент.**

```python
def research_subagent(inp: dict) -> str:
    @tool("Поиск по базе знаний", params={"query": "запрос"})
    def search(query: str) -> str:
        time.sleep(0.5)  # имитация медленного веба
        return {"rate limit": "Anthropic и OpenAI ограничивают RPM и TPM; при 429 — экспоненциальный backoff.",
                "retry": "Повторять только идемпотентные запросы; учитывать заголовок retry-after."}.get(query, "ничего")
```

Інструмент `search` створюється заново під час кожного запуску субагента. Декоратор `@tool` ти бачив у модулі 2: він
робить із функції інструмент з описом. Запис `.get(query, "ничего")` у JavaScript виглядав би як `obj[query] ??
"ничего"`. Далі йде сценарій моделі:

```python
    sub_llm = ScriptedLLM([
        Reply("", [ToolCall("s1", "search", {"query": "rate limit"}), ToolCall("s2", "search", {"query": "retry"})]),
        Reply("Итог: при 429 делай экспоненциальный backoff с джиттером, уважай retry-after, "
              "повторяй только идемпотентные запросы; лимиты бывают по запросам и по токенам."),
    ])
```

Перша відповідь просить два пошуки, друга містить підсумок. `run_agent` виконує виклики по черзі (рядок 99
`harness/loop.py`), тому два пошуки займають 1 секунду, а не 0,5. Паралельними є лише субагенти, а не інструменти
всередині одного субагента.

Після цього викликається `run_agent`, а функція повертає `res.text`. Цей виклик пояснено в лекції.

**Інструмент головного агента.**

```python
@tool("Запустить фоновое исследование. Возвращает id задачи сразу; результат придёт позже отдельным сообщением.",
      params={"question": "что исследовать"})
def research(question: str) -> str:
    jid = runner.spawn("research", {"question": question}, research_subagent)
    return f"Принято: {jid}. Продолжай работу, результат придёт сам."
```

Опис інструмента й текст підтвердження важливі для моделі: вони кажуть, що чекати не треба. Без цього модель могла б
вирішити, що дослідження не дало результату. `research_subagent` передано без дужок, тобто передано саму функцію, а
викличе її потік.

**Перший хід і пробудження.**

```python
t0 = time.time()
run_agent(main_llm, system, messages, [research])
print(f"\n⏱  Пользователь получил первый ответ через {time.time() - t0:.2f} c; в фоне: {runner.pending()}")

for s in runner.collect(timeout=5):
    print(f"\n📬 Доставлено {s['steer_id']} (exactly-once)")
    messages.append(steer_message(s))
    run_agent(main_llm, system, messages, [research])
```

`run_agent` змінює список `messages` на місці, тому другий виклик продовжує ту саму історію. `:.2f` означає два знаки
після коми. Кожен отриманий результат запускає окремий хід. Якщо результатів три, буде три ходи.

**Перевірка дубліката.** Останні два рядки кладуть у чергу повідомлення з `steer_job_1` вручну й показують, що
`collect` його відкидає.

**Вивід.** Він випливає з коду й виглядає приблизно так:

```text
🤖 Запущу исследование в фоне, а пока отвечу на то, что знаю.
  🔧 research({"question": "Как правильно обрабатывать rate limit у LLM API?"})
  ↳ Принято: job_1. Продолжай работу, результат придёт сам.
🤖 Пока идёт поиск: сначала логируй каждый 429 и заголовки ответа — это пригодится. Детали скоро.

⏱  Пользователь получил первый ответ через 0.00 c; в фоне: ['job_1']

📬 Доставлено steer_job_1 (exactly-once)
🤖 Пришли результаты исследования: добавь backoff с джиттером и учитывай retry-after. Код-ревью: твой цикл повторяет и POST-запросы на оплату — так нельзя, они не идемпотентны.

Повторная доставка steer_job_1 → получено 0 сообщений (дубль отброшен)
```

Час 0.00 с виходить через те, що `ScriptedLLM` відповідає миттєво: зі справжньою моделлю це будуть секунди. Усі тексти
моделі записані наперед, зокрема зауваження про POST-запити. Цей урок показує механізм доставки, а не якість
відповідей.

### Що ще видно з коду

Лекція описує межі, названі в плані. Ось ще п'ять, які випливають із читання коду й знадобляться в практиці.

**1. Ніхто не перевіряє, що головний агент вільний.** Опис файла каже, що харнес будить агента, тобто запускає новий
хід, коли той вільний. Але `JobRunner` нічого не знає про ходи. В уроці правильний порядок дає лише те, що рядок із
`collect` стоїть після `run_agent`. Програма при цьому стоїть у `collect` до 5 секунд, тому не чекає модель, а харнес
усе одно чекає. У справжньому застосунку потрібен цикл, який обробляє і повідомлення людини, і чергу, і не запускає
другий хід, доки не закінчився перший.

**2. `pending()` може спорожніти раніше, ніж результат потрапить у чергу.** Причина в порядку рядків 44 і 48.
Припустимо, працюють два завдання:

| Момент | Потік `job_2` | Головний потік у `collect(timeout=5)` |
|--------|---------------|---------------------------------------|
| 1 | виконує рядок 44: статус `done` | отримує результат `job_1` |
| 2 | ще не дійшов до рядка 48 | `pending()` порожній, цикл завершується, повертається лише `job_1` |
| 3 | виконує рядок 48: повідомлення в черзі | урок більше не викликає `collect`, тому результат `job_2` так і лежить у черзі |

Результат не зник, але його ніхто не забере. Така помилка трапляється рідко й залежить від випадкового порядку
потоків, тому її називають **станом гонитви** (англійською race condition). Для трьох паралельних досліджень у
практиці викликай `collect` ще раз наприкінці. Можна також завершувати очікування за іншою умовою:
`len(self.delivered) == len(self.jobs)`, тобто коли доставлено все, що запущено. Переносити зміну статусу за `put` не
варто: тоді `collect` іноді бачив би вже доставлене завдання як незавершене й чекав би до кінця свого часу.

**3. Токени субагента ніде не враховано.** `run_agent` повертає `RunResult` із полем `usage`, але `research_subagent`
бере лише `res.text`, а в `Job` немає поля для токенів. Тому `JobRunner` показує лише результат, а справжньої вартості
не показує. Збережи `res.usage` окремо, інакше порівняння в практиці буде неповним.

**4. Причину зупинки субагента ніхто не перевіряє.** Якщо субагент вичерпав `max_steps`, `run_agent` повертає текст
«(остановлено: превышен лимит шагов)». `research_subagent` передасть його далі, а `run` запише статус `done`. Головний
агент отримає «успішний» результат без змісту. Перевіряй `res.stopped_by` і в разі потреби викидай виняток.

**5. Текст субагента приходить із роллю `user`.** Якщо субагент читав чужі сторінки, у його підсумок могли потрапити
сторонні інструкції, а головний агент отримає їх від імені людини. `steer_message` не використовує функцію
`as_untrusted` із `harness/context.py`, яка позначає такий текст як дані. Докладно про цю загрозу йдеться в модулі 6.

### `Benefits of a multi-agent system`

Дослідження важко передбачити наперед: кожна знахідка змінює наступний крок. Саме тому тут потрібен агент, а не
записаний у коді порядок дій. Це та сама межа між агентом і воркфлоу, що й у лекції 0.

Далі автори пояснюють, навіщо кілька агентів. Вони пишуть: «The essence of search is compression». Суть пошуку полягає
в стисненні: треба витягти головне з величезного обсягу тексту. Субагенти роблять це паралельно, кожен у своєму
контексті, і передають головному агентові лише найважливіше. Окремі промпти й інструменти також зменшують залежність
від шляху: знахідка одного субагента не впливає на те, куди піде інший.

**Числа, які варто запам'ятати.**

| Що виміряно | Результат |
|-------------|-----------|
| Система з кількох агентів проти одного агента на внутрішньому вимірюванні | на 90,2 % краще |
| Що пояснює різницю в результатах на тесті BrowseComp (пошук важкодоступної інформації) | три чинники пояснюють 95 %, а сама кількість токенів 80 %. Два інші чинники: кількість викликів інструментів і вибір моделі |
| Витрати агента порівняно зі звичайним чатом | приблизно вчетверо більше токенів |
| Витрати системи з кількох агентів порівняно зі звичайним чатом | приблизно в 15 разів більше токенів |

Приклад успіху: знайти всіх членів рад директорів ІТ-компаній з індексу S&P 500. Один агент не впорався через
повільний послідовний пошук, а система з кількох агентів поділила завдання на частини. Автори називають такі запити
**breadth-first**, тобто «спершу вшир»: багато незалежних напрямів, а не один глибокий.

**Несподіваний висновок.** Система добре працює здебільшого тому, що витрачає достатньо токенів. Кращий результат
можна отримати й іншим способом: автори повідомляють, що перехід на новішу модель дав більший приріст, ніж подвоєння
бюджету токенів на старій.

**Коли не підходить.** Коли всім агентам потрібен спільний контекст, коли між їхніми частинами багато залежностей і
коли результат не вартий витрат. Більшість завдань із кодом, за словами авторів, має менше незалежних частин, ніж
дослідження, а агенти поки що погано узгоджують дії між собою під час роботи.

### `Architecture overview for Research`

Тут описано порядок роботи:

1. Запит людини отримує головний агент `LeadResearcher`. Він обмірковує підхід і зберігає план у зовнішню пам'ять, бо
   за перевищення 200 000 токенів контекст обрізається, а план треба зберегти.
2. Він створює субагентів зі своїми завданнями. На схемі їх два, але кількість може бути будь-якою.
3. Кожен субагент сам шукає в інтернеті й оцінює результати. **Interleaved thinking** означає, що модель міркує між
   результатами інструментів.
4. Головний агент читає підсумки й вирішує, чи потрібне ще дослідження. Якщо так, він створює нових субагентів або
   змінює план.
5. Коли інформації вистачає, окремий агент `CitationAgent` знаходить у документах місця, на які спирається кожне
   твердження, і додає посилання.

Стаття також порівнює цей підхід із **RAG** (Retrieval Augmented Generation): там програма один раз знаходить уривки,
схожі на запит, і відповідає за ними. Тут пошук багатокроковий і змінюється залежно від знахідок.

Порівняй із кодом курсу: `research` відповідає другому кроку, а `collect` і новий хід — четвертому. Зовнішньої пам'яті
для плану, повторних субагентів і окремого агента для посилань у курсі немає.

### `Prompt engineering and evaluations for research agents`

Ранні агенти запускали 50 субагентів для простих запитань, нескінченно шукали джерела, яких не існує, і заважали одне
одному зайвими повідомленнями. Кожним агентом керує промпт, тому автори виправляли це передусім промптами й
сформулювали вісім принципів.

| Принцип | Що він означає | Що взяти собі |
|---------|----------------|---------------|
| `Think like your agents` | Запускай агента з тими самими промптами й інструментами й дивися на кожен крок. Так видно, що він шукає зайве чи вибирає не той інструмент | Читай історію кожного запуску |
| `Teach the orchestrator how to delegate` | Субагентові потрібні мета, формат результату, вказівка щодо інструментів і джерел, межі завдання. Коротке «дослідь нестачу напівпровідників» призвело до того, що один субагент вивчав кризу 2021 року, а два інші повторювали одне одного про 2025 рік | Запиши ці чотири частини в опис `research` |
| `Scale effort to query complexity` | Для факту вистачає одного агента й 3–10 викликів, для порівняння потрібно 2–4 субагенти по 10–15 викликів, а для складного дослідження понад 10 субагентів | Додай ці межі в промпт |
| `Tool design and selection are critical` | Опис інструмента важить не менше за інтерфейс для людини. Агент, який шукає в інтернеті те, що є лише в Slack, не знайде нічого | Давай кожному інструменту окреме призначення |
| `Let agents improve themselves` | Нові моделі Anthropic самі знаходять причини невдач. Агент для перевірки інструментів випробовував поганий опис десятки разів і переписував його, і час виконання завдань наступними агентами скоротився на 40 % | Давай моделі промпт разом із прикладом збою |
| `Start wide, then narrow down` | Агенти схильні до довгих вузьких запитів, які дають мало результатів. Краще почати з короткого широкого запиту, а потім звужувати | Запиши це в промпт субагента |
| `Guide the thinking process` | Режим **extended thinking** дає моделі окремо написати міркування. Головний агент планує в ньому, а субагенти оцінюють результати | Подивись, чи твій провайдер має такий режим |
| `Parallel tool calling transforms speed and performance` | Головний агент запускає 3–5 субагентів одночасно, а кожен субагент викликає 3 і більше інструментів одночасно. Для складних досліджень це скоротило час на величину до 90 % | У курсі паралельні лише субагенти, а `run_agent` виконує інструменти по черзі |

Наприкінці розділу автори кажуть, що вчили агентів не жорстких правил, а евристик: як поділити завдання, оцінити
джерело, змінити пошук, вибрати глибину чи ширину. Водночас вони поставили явні обмеження, щоб агенти не працювали без
кінця.

### `Effective evaluation of agents`

Цей розділ готує до модуля 7. Звичайна перевірка чекає, що програма пройде той самий шлях. Агенти можуть прийти до
правильної відповіді різними шляхами, тому перевіряти треба результат і розумність процесу, а не конкретні кроки.

- **Починай одразу з малого набору.** На початку зміни дають великий ефект: правка промпта може підняти успіх із 30 %
  до 80 %, і це видно на кількох прикладах. Автори почали з приблизно 20 запитів.
- **Модель як суддя** (`LLM-as-judge`). Текст дослідження важко перевірити кодом, тому його оцінює інша модель за
  критеріями: точність фактів, точність посилань, повнота, якість джерел, ефективність інструментів. Найкраще
  спрацював один виклик, який видає оцінки від 0,0 до 1,0 і висновок «так чи ні», а не кілька окремих суддів.
- **Людина помічає те, чого не бачать автоматичні перевірки.** Люди-випробувачі виявили, що агенти обирають сайти,
  створені заради пошукової видачі (SEO-оптимізовані «ферми контенту»), а не авторитетні, але менш помітні джерела.
- **Несподівана поведінка.** Мала зміна в головному агенті може непередбачувано змінити поведінку субагентів. Тому
  промпти мають описувати поділ роботи й межі витрат, а не лише суворі вказівки.

### `Production reliability and engineering challenges`

Цей розділ найближчий до коду модуля.

| Назва підрозділу | Що там сказано | Як це стосується курсу |
|------------------|----------------|------------------------|
| `Agents are stateful and errors compound` | Агент працює довго й накопичує стан, тому дрібний збій може зіпсувати все. Починати спочатку дорого, тому система продовжує з місця збою. Також корисно повідомити моделі, що інструмент не працює, і дати їй пристосуватися | Модуль 4 і завдання з `Ledger` у цьому модулі |
| `Debugging benefits from new approaches` | Той самий запит дає різну поведінку, тому потрібне докладне трасування. Автори стежать за загальними закономірностями рішень агентів, не читаючи вмісту розмов, щоб берегти приватність | Модуль 7 |
| `Deployment needs careful coordination` | Під час оновлення агенти можуть бути посеред роботи. **Rainbow deployments** означає, що стара й нова версії працюють поруч, а трафік переходить поступово | У курсі такого немає |
| `Synchronous execution creates bottlenecks` | На момент написання головний агент чекав, доки завершиться вся група субагентів. Це спрощує узгодження, але не дозволяє ні скеровувати субагентів, ні узгоджувати їх між собою. Асинхронне виконання дало б більше паралельності, але ускладнює узгодження результатів, стану й помилок | Саме цю складність показує ack-and-steer |

Останній рядок важливо зрозуміти правильно. Курс показує фонову роботу, яку ця система на момент написання ще не мала,
але це не означає, що фон завжди кращий. Автори свідомо почали з простішого синхронного варіанта.

### `Conclusion`

Автори кажуть, що перехід від прототипу до надійного продукту часто забирає більшу частину роботи, бо в агентах дрібна
помилка може змінити весь подальший шлях. Наприкінці є діаграма найчастіших застосувань Research: найбільше запитів
стосується розробки програм для спеціальних галузей (10 %) і професійного контенту (8 %).

### `Appendix`

Три поради наприкінці статті:

- **`End-state evaluation of agents that mutate state over many turns`.** Якщо агент змінює дані, оцінюй кінцевий
  стан, а не кожен крок. Для складних робіт постав кілька контрольних точок.
- **`Long-horizon conversation management`.** У розмовах на сотні ходів агенти підсумовують завершений етап і
  зберігають головне у зовнішній пам'яті. Коли контекст закінчується, вони запускають нових субагентів і передають їм
  потрібне. Це поєднання модулів 3, 4 і 5.
- **`Subagent output to a filesystem to minimize the ‘game of telephone’`.** Назва натякає на гру «зіпсований
  телефон»: кожна передача тексту через іншого агента щось губить. Тому субагент може записати великий результат у
  файл і повернути лише посилання. Так зберігається точність і менше токенів витрачається на копіювання.

**2. Що пішло не так, коли головний агент давав короткі завдання?**

<details><summary>Відповідь</summary>

Субагенти неправильно розуміли завдання або повторювали роботу одне одного. У прикладі зі статті два субагенти
досліджували те саме, поки третій вивчав інший період. Виправлення: мета, формат результату, вказівка щодо
інструментів і межі завдання.

</details>

**3. Чи запускає описана система субагентів так само, як код курсу?**

<details><summary>Відповідь</summary>

Ні. Там на момент написання головний агент чекав завершення групи субагентів. Код курсу не змушує головного агента
чекати: той отримує підтвердження, а результат приходить окремим ходом.

</details>

**4. Навіщо записувати результат субагента у файл?**

<details><summary>Відповідь</summary>

Кожна передача через іншого агента може щось загубити, а копіювання великого тексту через історію коштує токенів. Файл
зберігає результат точно, а головний агент отримує лише коротке посилання.

</details>

## Стаття «Factor 10: Small, focused agents»

**Де читати:** [розділ у 12-Factor
Agents](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-10-small-focused-agents.md),
англійською. Це дуже короткий текст.

**Що це за текст.** Це десяте з дванадцяти правил збірки 12-Factor Agents, яку ти бачив у модулі 0. Воно стосується
розміру агента.

**Головна думка.** Не будуй одного великого агента на всі випадки. Роби малих агентів, кожен із яких добре виконує
одну справу, а навколо них нехай лишається звичайний передбачуваний код.

### `10. Small, Focused Agents`

Автор пояснює причину так: що більше й складніше завдання, то більше кроків воно потребує, отже, тим довший контекст.
У статті виділено таке речення: «As context grows, LLMs are more likely to get lost or lose focus». Воно означає, що з
ростом контексту модель частіше відхиляється від завдання. Тому автор радить обмежувати агента 3–10 кроками,
щонайбільше 20.

Вираз **mostly deterministic system** означає систему, яка здебільшого складається зі звичайного передбачуваного коду,
а агенти є лише її окремими частинами. **Monolithic agent** означає одного великого агента, який намагається робити
все.

У статті названо п'ять переваг:

| Назва | Що це означає |
|-------|---------------|
| Manageable Context | Менший контекст, тому модель працює краще |
| Clear Responsibilities | Кожен агент має чітке призначення |
| Better Reliability | Менше шансів заплутатися в складній роботі |
| Easier Testing | Вузьку функцію легше перевірити |
| Improved Debugging | Легше знайти й виправити причину збою |

### `What if LLMs get smarter?`

Чи потрібне це правило, якщо моделі навчаться виконувати 100 кроків? Автор відповідає, що потрібне. Моделі справді
можуть опанувати більшу частину роботи, але малі агенти дають результат уже сьогодні, а межі агента можна поступово
розширювати, не втрачаючи якості. Абревіатуру **DAG** (схема кроків без циклів) ми пояснили в розборі до модуля 0.

Наприкінці є думка команди NotebookLM: найкращі результати з'являються біля самої межі можливостей моделі. Автор
додає: де б не проходила ця межа, успіх залежить від того, чи можеш ти стабільно працювати саме біля неї, а для цього
потрібна інженерна дисципліна. Слово **moat** («рів навколо замку») у цьому контексті означає перевагу, яку важко
скопіювати конкурентам.

### Як це пов'язано із субагентами

Правило ширше за субагентів: воно стосується кожного агента в системі. Субагент є одним зі способів його виконати, бо
замість одного запуску на 40 кроків ти отримуєш головного агента на кілька кроків і субагента на 10. У коді курсу
стандартне значення `max_steps` у `run_agent` дорівнює 20, тобто збігається з верхньою межею автора.

### Що взяти у свого агента

- Порахуй кроки типових завдань свого агента. Якщо їх регулярно більше 20, подумай, що можна виділити.
- Спершу постав вузьку межу, а розширюй її лише тоді, коли заміри показують, що якість не падає.

### Запитання до статті

**1. Чому довгий контекст шкодить, навіть якщо він вміщується в модель?**

<details><summary>Відповідь</summary>

Автор каже, що з ростом контексту модель частіше відхиляється від завдання. Тому важливий не лише ліміт токенів, а й
те, скільки матеріалу модель мусить утримувати одночасно.

</details>

**2. Чи означає це правило, що кожну частину треба робити субагентом?**

<details><summary>Відповідь</summary>

Ні. Правило каже, що агенти мають бути малими частинами системи, яка здебільшого складається зі звичайного коду. Часто
частину роботи краще виконати кодом узагалі без агента.

</details>

**3. Що зміниться, якщо моделі стануть кращими?**

<details><summary>Відповідь</summary>

Межі агента можна буде поступово розширювати. Правило не забороняє цього, а радить рости лише так, щоб якість не
падала.

</details>

## LearnHarness: docs/architecture.md

**Де читати:**
[`docs/architecture.md`](https://github.com/amosblomqvist/learnharness/blob/v0.4.1/docs/architecture.md) версії 0.4.1,
розділ `5. Background work and delivery`, англійською. Потім [розділ 6 розбору LearnHarness у
курсі](https://github.com/justxor/agent-harness-course/blob/0c90ce7bbeef858426abfeeacacbdb438921c078/docs/learnharness-case-study.md),
російською.

**Що це за текст.** LearnHarness — застосунок із відкритим кодом від іншого автора, у якому агенти ведуть уроки. Цей
документ описує, як застосунок влаштований зараз. Код проєкту поширюється за ліцензією AGPL-3.0, тому тут лише
наведено назви файлів і функцій і пояснено ідеї своїми словами. Сам проєкт написаний на TypeScript. Тому для тебе він
навіть зрозуміліший за Python: фонове завдання там є `async`-функцією `runJob`, яку викликають без `await`, без
окремих потоків.

### Розділ `5. Background work and delivery`

**Перший абзац.** Застосунок має чотири види фонової роботи: дослідника (researcher), читача PDF, збирача демонстрацій
і виконавця малюнків. Усі їх запускає `src/agent/subagents/runner.ts`. Важливий порядок: інструмент спершу зберігає
завдання разом із вхідними даними, потім повертає підтвердження і лише тоді запускає роботу. У коді курсу вхідні дані
на диск не потрапляють узагалі.

**Головне речення розділу: `Worker completion is not session delivery`.** Кінець роботи ще не означає, що результат
доставлено в розмову. **Worker** означає виконавця фонової роботи, а **session** тут означає розмову з людиною.
Виконавець зберігає свій кінцевий стан разом із записом «результат ще треба доставити», і вже потім ставить результат
у чергу. Робота може закінчитися, а результат ще довго чекатиме, поки людина не відповість на незакриті запитання
уроку.

**Два способи доставки.** `src/server/jobs.ts` веде реєстр у пам'яті процесу:

| Назва | Коли | Що відбувається |
|-------|------|-----------------|
| `Live run` | Хід саме триває | Результат потрапляє в чергу скерування бібліотеки Pi, на якій працюють розмови LearnHarness. Бібліотека вставляє його лише на дозволених межах, ніколи між викликом інструмента та його результатом. Це те саме правило, що й у лекції |
| `Idle wake` | Ходу немає | Програма чекає, поки одночасно виконано чотири умови: немає поточного ходу, немає запитання без відповіді, розмову не поставлено на паузу, а людина погодилася на фонову роботу. Потім вона запускає звичайний новий хід із результатами |

Код курсу має лише другий спосіб, причому в спрощеному вигляді.

**Що відбувається, коли запуск не вдався.** Відповідь HTTP 409 означає конфлікт: людина вже почала свій хід. Тоді
програма чекає й пробує знову. Якщо людина не погодилася на фонову роботу, результат лишається в черзі. Інші невдалі
запуски тихо чекають наступного ходу людини чи перезапуску, бо нескінченних повторів за таймером автори не хотіли.

**Що вважається доставкою.** Автори чітко кажуть: доставку підтверджує **маркер у збереженій розмові**, а не успішна
відповідь HTTP і не те, що текст уже з'явився на екрані. Саме так можна виконати обіцянку тексту курсу про збереження
ходу. **Reconciliation** (звірка) не дає доставити результат знову, якщо маркер уже збережений, а подальші дії не
вдалися.

**Відновлення.** Після перезапуску програма відновлює всі відомі зобов'язання щодо доставки, а незавершені роботи може
запустити знову зі збережених вхідних даних. Старі записи без поля про доставку повторно не доставляються, бо програма
не може знати, чи вони вже доставлені. Видалення розмови скасовує її зобов'язання.

**Застереження наприкінці.** Автори прямо кажуть, що це узгодження в межах одного процесу над файлами JSON, а не черга
з транзакціями й не гарантія рівно одного виконання в провайдера. Це варто запам'ятати: документ прямо називає межі
своєї гарантії. Також вони попереджають, що повідомлення, які людина пише під час ходу, зберігаються лише в пам'яті й
не мають такого самого відновлення.

### Порівняння з кодом курсу

| Питання | `harness/jobs.py` | LearnHarness 0.4.1 |
|---------|-------------------|--------------------|
| Головна функція | `JobRunner.spawn` | `createJobRunner` і `runJob` у `src/agent/subagents/runner.ts` |
| Як іде фонова робота | потік | `async`-функція без `await` |
| Де зберігається завдання | словник `jobs` у пам'яті | файли `jobs/*.json`, код у `src/store/jobs.ts` |
| Коли зберігаються вхідні дані | ніколи | до запуску, функція `dispatch` у `src/agent/tools/jobs.ts` |
| Що, якщо той самий виклик виконано двічі | запуститься друге завдання | `dispatch` шукає наявне завдання за ідентифікатором виклику |
| Стан завдання | одне поле `status` | `status` описує роботу, а `delivery` описує доставку |
| Що вважається доставкою | `collect` видав результат | маркер у збереженій розмові |
| Ідентифікатор | `steer_job_1` | те саме правило: `steer_` і номер завдання |
| Способи доставки | лише новий хід після завершення | `Live run` і `Idle wake` |
| Відновлення | немає | `restorePendingDeliveries` і `recoverStaleJobs` у `src/server/jobs.ts` |
| Скасування | немає | `abortJob`: сигнал у кожен виклик моделі, а також окреме повідомлення про скасування |
| Облік токенів | немає | поле `usage` запису завдання, яке оновлюється після кожного виклику моделі |
| Помилка роботи | текст і статус `error` | окрема форма результату, яка доставляється так само |

**Де що читати в коді.** `createJobRunner` показує лише виконання, а функція `finishJob` усередині нього — порядок
збереження результату. Доставка й відновлення лежать у `src/server/jobs.ts`, а опис протоколу — у коментарі `THE ASYNC
PROTOCOL` у `src/core/contracts/jobs.ts`. Тому завдання з плану «порівняй із `createJobRunner`» варто виконувати разом
із цими двома файлами.

### Розділ 6 розбору LearnHarness у курсі

Цей розділ російською коротко переказує той самий механізм. Зіставимо його з кодом версії 0.4.1:

| Що написано в розборі | Що це означає й що варто перевірити |
|-----------------------|-------------------------------------|
| «Инструменты `research`, `demo`, `visual` отвечают сразу» | Інструменти одразу відповідають, а урок триває. У версії 0.4.1 додано ще читача PDF |
| «steer-сообщение — user-сообщение с текстом для модели и полным артефактом для UI» | Модель отримує текст, а інтерфейс отримує повний результат, наприклад демонстрацію |
| «Конвейер пробуждения: очередь на чат» | Окрема черга на кожну розмову. Новий хід починається, коли немає поточного ходу й незакритого запитання |
| «При `409` — backoff 500 → 1000 → 2000 → 5000 мс» | Повтор зі зростаючою затримкою. Значення збігаються з `RETRY_BACKOFF_MS` у `src/server/jobs.ts` |
| «статус задачи меняется только после сохранения хода» | **У версії 0.4.1 уже не так.** `finishJob` записує статус `done` одразу, а окреме поле `delivery` лишається `pending`, поки маркер не збережено |
| «Зависшие задачи (> 15 мин) восстанавливаются после падения» | **У версії 0.4.1 уже не так.** `recoverStaleJobs` дивиться не на вік запису, а на те, чи виконується завдання в цьому процесі. Коментар у коді пояснює, що перевірка за віком запускала другу копію завдання, яке працювало довго, але ще не зупинилося |
| «Субагенты проверяют, а не выдают с первого раза» | Демонстрацію запускають у браузері без вікна, а малюнок показують моделі, яка вміє дивитися на зображення |

Отже, текст курсу описує загальну ідею правильно, але дві деталі відстають від версії 0.4.1. Для тебе важливіша нова
модель із двома станами, бо вона чіткіше розділяє дві різні речі: роботу завершено й результат доставлено.

### Що взяти у свого агента

- Зберігай завдання й вхідні дані до запуску роботи, а не після.
- Роздільно зберігай стан роботи й стан доставки.
- Вважай результат доставленим лише тоді, коли він є у збереженій історії.
- Перед запуском завдання перевір, чи такий виклик уже не створив його.
- Запиши в документації, що саме гарантує твій код, а що ні.
