Цей файл корисно читати з двох причин. По-перше, він показує, як тестувати агента без справжньої моделі. По-друге,
кожен тест коротко записує вимогу до харнесу, тому файл працює як перелік того, що має вміти твій власний код.

### `unittest` і `assert` порівняно з Vitest чи Jest

`unittest` — це бібліотека тестів, яка входить до самого Python, тому нічого встановлювати не треба. Вона побудована
на класах: тести живуть у класі, а перевірки є методами цього класу.

| У `unittest` | У Vitest чи Jest | Що робить |
|--------------|------------------|-----------|
| `class LoopTests(unittest.TestCase):` | `describe("LoopTests", () => { ... })` | Групує тести |
| `def test_tool_roundtrip(self):` | `it("tool roundtrip", () => { ... })` | Один тест. `unittest` запускає лише методи, назва яких починається з `test` |
| `self.assertEqual(a, b)` | `expect(a).toEqual(b)` | Порівнює за вмістом. У Python `==` порівнює вміст списків і словників, тому це відповідає `toEqual`, а не `toBe` |
| `self.assertNotEqual(a, b, msg)` | `expect(a).not.toEqual(b)` | Третій аргумент є текстом для повідомлення про помилку |
| `self.assertTrue(x)` | `expect(x).toBeTruthy()` | Перевіряє істинність значення, а не точну рівність `True` |
| `self.assertFalse(x)` | `expect(x).toBeFalsy()` | Те саме для хибного значення |
| `self.assertIn(x, y)` | `expect(y).toContain(x)` | Порядок аргументів зворотний: спершу що шукаємо, потім де |
| `self.assertIsNone(x)` | `expect(x).toBeNull()` | У Python значення `None` відповідає `null` |
| `self.assertLess(a, b)` | `expect(a).toBeLessThan(b)` | Перевіряє, що `a` менше за `b` |
| `with self.assertRaises(E):` | `expect(() => { ... }).toThrow(E)` | Код усередині блока має викинути помилку `E` |
| `setUp(self)` | `beforeEach` | Виконується перед кожним тестом |
| `setUpClass(cls)` | `beforeAll` | Виконується один раз перед усіма тестами класу |
| `tearDownClass(cls)` | `afterAll` | Виконується один раз після всіх тестів класу |
| `python -m unittest discover -s tests -v` | `vitest run tests` | Шукає у теці `tests` файли `test*.py` і запускає їх. Прапорець `-v` друкує кожен тест окремо |

**Що таке `assert`.** Англійське assertion означає «твердження»: код стверджує, що умова істинна, і зупиняє тест, якщо
це не так. У Python є окреме ключове слово `assert`:

```python
assert res.text == "5", "неправильна відповідь"
```

Якщо умова хибна, Python викидає помилку `AssertionError` із цим текстом. У цьому файлі такого запису немає, бо він
використовує методи `self.assertEqual` та інші: коли тест не проходить, ці методи показують обидва значення. Запис із
ключовим словом зустрінеться в інших проєктах, бо бібліотека pytest, яку згадує стаття Hamel Husain, побудована саме
на ньому. Найближчий відповідник у JavaScript — модуль `node:assert`. А ось `console.assert` у браузері лише друкує
повідомлення й не зупиняє код, тому порівнювати їх не варто.

**Запуск.** З кореня репозиторію курсу запусти `python -m unittest discover -s tests -v`. Вивід виглядатиме приблизно
так: рядок на кожен тест із позначкою `ok`, а наприкінці `Ran 19 tests` і `OK`.

### Початок файла: імпорти й `quiet`

```python
"""Детерминированные тесты харнеса: без ключей и без интернета.

    python -m unittest discover -s tests -v
"""
import json
import sys
import tempfile
import threading
import time
import unittest
from http.server import BaseHTTPRequestHandler, HTTPServer
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))
from harness import (AnthropicLLM, FactMemory, JobRunner, Ledger, OpenAICompatLLM, Reply,  # noqa: E402
                     ScriptedLLM, SessionStore, ToolCall, Workspace, compact, repair_dangling_tool_calls,
                     run_agent, select_cutoff, tool, validate_args)

quiet = dict(on_event=lambda k, d: None)
```

- Рядок у потрійних лапках на початку є описом файла. Python зберігає його як документацію, а курс записав там команду
  запуску.
- Усі імпорти вгорі взяті зі стандартної бібліотеки Python. Це і є причина, чому тестам не потрібно нічого
  встановлювати.
- Рядок із `sys.path.insert` потрібен, бо тест лежить у теці `tests`, а пакет `harness` лежить поруч із нею.
  `Path(__file__).resolve()` дає повний шлях до цього файла, а `.parents[1]` дає теку на два рівні вище, тобто корінь
  репозиторію. Python шукає модулі у списку `sys.path`, тому корінь додають на початок цього списку. У JavaScript ти
  написав би відносний шлях `../harness`, а в Python так не прийнято.
- Коментар `# noqa: E402` просить лінтер не сваритися на те, що імпорт стоїть не на самому початку файла. На роботу
  програми він не впливає.
- `quiet` є словником з одним ключем `on_event`, значення якого є функцією, що нічого не робить. `lambda k, d: None`
  відповідає стрілковій функції `(k, d) => null`. Запис `**quiet` у виклику функції розгортає словник в іменовані
  аргументи. Отже, `run_agent(..., **quiet)` означає те саме, що `run_agent(..., on_event=lambda k, d: None)`.
  Найближчий запис у JavaScript — `runAgent(..., { ...quiet })`.

Без `quiet` звичайний обробник `default_events` друкував би кожен крок агента посеред виводу тестів.

### Інструменти для тестів: `add`, `boom`, `danger`, `handoff`

```python
@tool("сложить", params={"a": "a", "b": "b"})
def add(a: int, b: int) -> str:
    return str(a + b)


@tool("упасть")
def boom() -> str:
    raise ValueError("сломалось")


@tool("опасно", needs_approval=True)
def danger() -> str:
    return "сделано"


@tool("передать ход", terminates=True)
def handoff() -> str:
    return "ок"
```

Запис `@tool(...)` є декоратором: він бере функцію, що стоїть нижче, і замінює її результатом виклику. Тут `tool`
повертає обгортку, яка створює об'єкт `Tool` з описом, схемою параметрів і самою функцією. Тому після цих рядків ім'я
`add` указує вже не на функцію, а на об'єкт `Tool`. Докладно це пояснено в розборі до модуля 2.

Кожен інструмент існує заради однієї поведінки. `add` має типи параметрів, і це дозволяє перевірити валідацію. `boom`
завжди викидає помилку. `danger` вимагає дозволу людини. `handoff` завершує цикл після успішного виклику.

### Клас `LoopTests`: цикл агента

Ця група перевіряє функцію `run_agent` із модуля 2. Вона відповідає на запитання: чи не зламається цикл, що б не
відповіла модель? Модель скрізь сценарна, тому кожен тест точно задає, що станеться на кожному кроці.

### `test_tool_roundtrip`: результат інструмента доходить до моделі

```python
def test_tool_roundtrip(self):
    llm = ScriptedLLM([Reply("", [ToolCall("1", "add", {"a": 2, "b": 3})]), Reply("5")])
    res = run_agent(llm, "", [{"role": "user", "content": "2+3"}], [add], **quiet)
    self.assertEqual(res.text, "5")
    self.assertEqual(res.stopped_by, "done")
    # модель на втором шаге видела результат инструмента
    self.assertEqual(llm.calls[1]["messages"][-1], {"role": "tool", "tool_call_id": "1", "content": "5"})
```

- `self` у Python відповідає `this`, але його треба явно вказувати першим параметром кожного методу.
- `ScriptedLLM` отримує список із двох відповідей і віддає їх по черзі. Перша відповідь просить викликати `add`, а
  друга містить текст «5».
- `run_agent` виконує два кроки: на першому викликає інструмент, а на другому отримує текст і завершується.
- `res.stopped_by` пояснює причину зупинки. Значення `"done"` означає, що модель сама закінчила.
- `llm.calls` є списком усього, що сценарна модель отримала. Індекс `[1]` означає другий виклик, а `[-1]` означає
  останнє повідомлення. У JavaScript такий запис виглядає як `.at(-1)`.

Остання перевірка тут головна. Текст «5» записано в сценарії, тому `res.text` дорівнював би «5» навіть тоді, коли цикл
загубив би результат інструмента. Лише остання перевірка доводить, що модель отримала результат.

### `test_errors_become_tool_results`: помилки стають текстом для моделі

```python
def test_errors_become_tool_results(self):
    llm = ScriptedLLM([Reply("", [ToolCall("1", "nope", {}), ToolCall("2", "boom", {}),
                                  ToolCall("3", "add", {"a": "x", "b": 1})]), Reply("ок")])
    res = run_agent(llm, "", [{"role": "user", "content": "?"}], [add, boom], **quiet)
    results = [m["content"] for m in res.messages if m["role"] == "tool"]
    self.assertIn("инструмента 'nope' нет", results[0])
    self.assertIn("ValueError", results[1])
    self.assertIn("должен быть integer", results[2])
```

Одна відповідь моделі просить одразу три виклики, і кожен із них помилковий: першого інструмента не існує, другий


Цей клас є маленьким сервером зі стандартної бібліотеки Python. Він відповідає як провайдер OpenAI, і завдяки йому
тести проходять через справжній код HTTP, але без інтернету. Подібну роль у фронтенді виконує бібліотека `msw`: код
робить звичайний запит, а відповідає на нього підробка.

- `class FakeOpenAI(BaseHTTPRequestHandler)` означає успадкування, як `extends` у JavaScript.
- `log_message` перевизначено порожнім, щоб сервер не друкував кожен запит. `*a` приймає будь-яку кількість
  аргументів, як `...a`. Слово `pass` означає «нічого не роби».
- `do_POST` викликається на кожен запит POST: стандартний клас шукає метод із такою назвою.
- `self.rfile` є потоком вхідних даних, а `self.wfile` потоком вихідних. Сервер читає рівно стільки байтів, скільки
  вказано в заголовку `content-length`.
- Перша гілка відповідає на потоковий запит. Вона надсилає два шматки тексту у форматі Server-Sent Events, а потім
  рядок `[DONE]`. Метод `.encode()` перетворює рядок на байти, а `b"..."` одразу записує байти.
- Друга гілка імітує модель, яка просить інструмент: якщо в запиті є інструменти, а останнє повідомлення написала
  людина, сервер просить викликати `add` з аргументами 20 і 22.
- Третя гілка імітує завершальну відповідь: сервер дописує до останнього повідомлення слово «Ответ:».
- Кожна непотокова відповідь повідомляє про 10 вхідних і 5 вихідних токенів.

### Клас `HttpTests`: весь цикл через мережу

```python
class HttpTests(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.srv = HTTPServer(("127.0.0.1", 0), FakeOpenAI)
        threading.Thread(target=cls.srv.serve_forever, daemon=True).start()
        cls.llm = OpenAICompatLLM("fake", "", f"http://127.0.0.1:{cls.srv.server_port}/v1")

    @classmethod
    def tearDownClass(cls):
        cls.srv.shutdown()
```

`@classmethod` означає, що метод отримує не об'єкт, а сам клас: параметр `cls` тут є класом. Тому `setUpClass`
виконується один раз, а значення `cls.srv` доступне в усіх тестах. Порт `0` просить операційну систему вибрати
будь-який вільний порт, завдяки чому тести не конфліктують з іншими програмами. Сервер працює в окремому потоці.
Позначка `daemon=True` означає, що цей потік не заважатиме програмі завершитися.

### Кінець файла

```python
if __name__ == "__main__":
    unittest.main()
```

Python записує в `__name__` рядок `"__main__"`, коли файл запущено напряму. Тому `python tests/test_harness.py` теж
запустить тести, а імпорт цього файла їх не запустить. У Node подібне робить перевірка `require.main === module`.

### Чого цей файл не перевіряє

Такі місця варто знати, бо успішний запуск тестів нічого не каже про них:

- підроблений сервер говорить лише у форматі OpenAI, тому `AnthropicLLM.complete` і `AnthropicLLM.stream_text` не
  перевірено мережею;
- сервер завжди відповідає кодом 200, тому гілка помилок у функції `_post` не перевірена;
- випадок, коли людина дозволила небезпечний інструмент, не перевірено;
- тестів для `auto_compactor`, `as_untrusted`, `build_system_prompt`, `steer_message`, `SessionStore.save`,
  `FactMemory.recall` і `FactMemory.extract` немає;
- у `Workspace` перевірено лише `resolve`, а самі інструменти читання й запису не перевірено.

### Що взяти у свого агента

- Напиши власні тести зі сценарною моделлю на кожну поведінку циклу: успішний виклик, помилки, відмова, межа кроків.
- Перевіряй не лише кінцевий текст, а й те, що модель побачила на наступному кроці.
- Для файлів бери нову тимчасову теку на кожен тест.
- Якщо тест перебирає значення, переконайся, що серед них є саме той випадок, заради якого написано тест.

Опис нагадує три рівні перевірок. Зверни увагу: опис обіцяє більше, ніж є в коді. Перший рівень реалізовано повністю,

`harness` не віддає його зі свого верхнього рівня.

### `ORDERS`, `order_status` і `escalate`: інструменти агента

```python
ORDERS = {"A-100": "доставлен 12.10", "A-101": "в пути, прибудет 29.10"}


@tool("Статус заказа", params={"order_id": "номер вида A-123"})
def order_status(order_id: str) -> str:
    return ORDERS.get(order_id, "заказ не найден")


@tool("Передать разговор человеку-оператору", params={"reason": "причина"})
def escalate(reason: str) -> str:
    return "оператор подключится в течение 5 минут"
```

`ORDERS` замінює базу даних: це словник із двома замовленнями. `ORDERS.get(order_id, "заказ не найден")` повертає
значення за ключем або другий аргумент, якщо ключа немає. У JavaScript це `ORDERS[orderId] ?? "заказ не найден"`.
Інструмент `escalate` нікого насправді не кличе, а лише повертає текст. Для eval цього досить, бо перевіряється сам
факт виклику.

### `TOOLS` і `SYSTEM`: набір інструментів і системний промпт

```python
TOOLS = [order_status, escalate]
SYSTEM = """Ты — поддержка магазина. Статусы заказов — только через order_status.
Если клиент злится, просит возврат денег или человека — вызови escalate. Не обещай того, чего не знаешь."""
```

Системний промпт містить три вимоги, і саме їх перевіряють кейси: статус лише через інструмент, передача людині в разі
гніву чи вимоги грошей, нічого не вигадувати. Отже, набір перевірок прямо випливає з вимог до агента. Коли ти
змінюватимеш цей рядок, набір покаже, чи не зламалась якась вимога.

### `Case`: опис кейсу

```python
@dataclass
class Case:
    name: str
    user: str
    checks: list[Callable] = field(default_factory=list)
```

`@dataclass` є декоратором, який сам пише конструктор за списком полів. Тому `Case("x", "y", [...])` створює об'єкт із
`name`, `user` і `checks`. У TypeScript подібним було б
`class Case { constructor(public name: string, public user: string, public checks: Function[] = []) {} }`.

`list[Callable]` означає «список функцій». Цей запис є лише підказкою для читача й інструментів, бо Python під час
роботи його не перевіряє.

Запис `field(default_factory=list)` потрібен через особливість Python. Значення за замовчуванням створюється один раз,
тому один список `[]` став би спільним для всіх об'єктів, тому `@dataclass` не дозволяє такий запис.
`default_factory=list` просить створювати новий список для кожного об'єкта. У JavaScript такої проблеми немає, бо
`checks = []` у полі класу виконується для кожного об'єкта окремо.

### `called`: чи викликано інструмент

```python
def called(name, **args):
    def check(res):
        ok = any(t["name"] == name and all(t["arguments"].get(k) == v for k, v in args.items())
                 for t in res.tool_log)
        return ok, f"вызван {name}{args or ''}"
    return check
```

Це функція, яка створює іншу функцію. `called("order_status", order_id="A-101")` повертає `check`, а `check` пам'ятає
`name` і `args`, як замикання в JavaScript. Сам кейс лише зберігає `check`, а викликає її `run_suite`, коли прогін уже
завершено.

Прочитаємо рядок за рядком:

- `**args` збирає всі іменовані аргументи у словник. Тут `args` дорівнює `{"order_id": "A-101"}`. У JavaScript ти
  передав би об'єкт другим параметром.
- `any(... for t in res.tool_log)` відповідає `res.tool_log.some(t => ...)`: хоча б один виклик має підійти.
- `all(... for k, v in args.items())` відповідає `Object.entries(args).every(([k, v]) => ...)`: кожен названий
  аргумент має збігтися.
- `t["arguments"].get(k)` повертає `None`, якщо такого аргументу немає. Запис `t["arguments"][k]` викинув би помилку,
  і вся перевірка впала б, замість того щоб повідомити про невдачу.
- `return ok, f"..."` повертає пару значень, яку в Python називають кортежем (англійською tuple).
- `args or ''` дає порожній рядок, якщо `args` порожній. Тут легко помилитися, якщо ти звик до JavaScript: у Python
  порожній словник і порожній список є хибними значеннями, а в JavaScript `{}` і `[]` істинні.

Два наслідки стоять окремої уваги. Якщо `args` порожній, `all(...)` дає `True`, як і `[].every(...)`, тому
`called("escalate")` перевіряє лише назву. Крім того, перевіряються лише названі аргументи, тому зайві аргументи
моделі цю перевірку не зачеплять.

### `not_called`: чи не викликано інструмент

```python
def not_called(name):
    return lambda res: (all(t["name"] != name for t in res.tool_log), f"НЕ вызван {name}")
```

Ця перевірка працює так само, але використовує `lambda`, бо тіло складається з одного виразу. Дужки навколо двох
значень створюють кортеж: `lambda` повертає пару. Така перевірка важлива, бо багато збоїв полягають у зайвій дії:
агент передав людині клієнта, який лише питав про статус.

### `contains`: чи є текст у відповіді

```python
def contains(*words):
    return lambda res: (all(w.lower() in res.text.lower() for w in words), f"ответ содержит {words}")
```

`*words` збирає всі позиційні аргументи, як `...words` у JavaScript, але в кортеж, а не в масив. Оператор `in` для
рядків шукає підрядок, як `.includes`. Обидва рядки зводяться до нижнього регістру, тому регістр не важить. Опис для
`contains("29.10")` виглядатиме як `ответ содержит ('29.10',)`, бо Python так записує кортеж з одного елемента.

Це найслабша перевірка у файлі, бо вона шукає лише послідовність літер. Про це йдеться нижче, у розділі про `CASES`.

### `max_steps`: чи вклався агент у кроки

```python
def max_steps(n):
    return lambda res: (res.steps <= n, f"шагов ≤ {n} (было {res.steps})")
```

`res.steps` дорівнює кількості викликів моделі за прогін. Ця перевірка знаходить агента, який бере на себе зайві
кроки, навіть якщо зрештою відповідає правильно. Зайві кроки означають зайві гроші, бо кожен крок знову надсилає всю
історію.

### `CASES`: набір кейсів

```python
CASES = [
    Case("статус заказа", "Где мой заказ A-101?",
         [called("order_status", order_id="A-101"), contains("29.10"), not_called("escalate"), max_steps(3)]),
    Case("несуществующий заказ", "Что с заказом A-999?",
         [called("order_status", order_id="A-999"), not_called("escalate"), max_steps(3)]),
    Case("эскалация", "Верните деньги немедленно, это уже третий раз!",
         [called("escalate"), max_steps(3)]),
    Case("без галлюцинаций", "Когда у вас распродажа?",
         [not_called("order_status"), contains("не")]),
]
```

Кожен кейс перевіряє окрему вимогу:

| Кейс | Що має зробити агент | Навіщо потрібні перевірки |
|------|----------------------|---------------------------|
| «статус заказа» | викликати інструмент із правильним номером, назвати дату з його результату, не кликати людину | `contains("29.10")` доводить, що відповідь спирається на дані інструмента |
| «несуществующий заказ» | перевірити номер і не передавати клієнта людині без потреби | перевіряє, що помилка в номері не стає приводом для передачі |
| «эскалация» | передати розмову людині | головна вимога промпта |
| «без галлюцинаций» | не вигадувати дату розпродажу, бо такого інструмента немає | галюцинацією називають факт, який модель вигадала |

Останній кейс перевірено слабко. `contains("не")` шукає дві літери, і їх містить, наприклад, слово «Конечно». Отже,
вигадана відповідь «Конечно, распродажа завтра!» пройде всі перевірки цього кейсу. Подумай, що перевіряти замість
цього: наприклад, що у відповіді немає жодної дати. Це приклад того, як перевірка може пропустити саме той збій,
заради якого її написано.

Кейсів усього чотири, а не 15, тому це лише зразок будови.

### `mock_agent`: підроблена модель із навмисною помилкою

```python
def mock_agent(system, messages, tools):
    """Мок-«модель» с одной намеренной ошибкой, чтобы было видно, как eval её ловит."""
    last = messages[-1]
    if last["role"] == "tool":
        content = last["content"]
        return Reply(f"Статус: {content}." if "оператор" not in content else "Передаю оператору, он скоро подключится.")
    text = last["content"]
    if "A-" in text:
        oid = "A-" + text.split("A-")[1][:3]
        return Reply("", [ToolCall("x", "order_status", {"order_id": oid})])
    if "деньги" in text:
        return Reply("Понимаю ваше недовольство, сейчас разберёмся!")   # ← баг: забыл escalate
    return Reply("Точных дат распродаж у меня нет — следите за рассылкой.")
```

Підроблена модель (англійською mock, як `vi.fn()`) має ту саму сигнатуру, яку очікує `ScriptedLLM`: вона отримує
системний промпт, історію й інструменти, а повертає відповідь. Вона не читає промпта, а лише шукає слова в останньому
повідомленні.

- `messages[-1]` бере останнє повідомлення.
- Якщо останнім є результат інструмента, модель пише завершальну відповідь. Запис `A if умова else B` є тернарним
  оператором Python, як `умова ? A : B`, тільки порядок інший.
- Гілка `"оператор" not in content` чекає результату `escalate`. Зараз вона ніколи не виконається, бо через помилку
  цей інструмент не викликається. Вона знадобиться, коли ти виправиш помилку.
- `text.split("A-")[1][:3]` ділить текст за підрядком `A-`, бере частину після нього й перші три символи. `[:3]` є
  зрізом, як `.slice(0, 3)`. З тексту «Где мой заказ A-101?» виходить «101», а отже `oid` дорівнює `A-101`.
- Рядок із коментарем `баг` і є навмисною помилкою: модель обіцяє розібратися словами, але нічого не робить.
- Остання гілка відповідає на все інше й каже, що дат не знає.

**Спробуй передбачити:** що зробить ця модель на повідомлення «Заказ A-1?»?

<details><summary>Відповідь</summary>

`text.split("A-")[1]` дасть «1?», а зріз `[:3]` лишить «1?». Отже, вона викличе `order_status` з номером `A-1?`,
інструмент поверне «заказ не найден», і відповідь буде «Статус: заказ не найден.». Це особливість підробленої моделі,
а не вимога до агента.

</details>

### `run_suite`: запуск набору

```python
def run_suite(llm: LLM):
    passed = total = 0
    for case in CASES:
        res = run_agent(llm, SYSTEM, [{"role": "user", "content": case.user}], TOOLS,
                        max_steps=5, on_event=lambda k, d: None)
        results = [c(res) for c in case.checks]
        ok = all(r[0] for r in results)
        passed += ok
        total += 1
        print(f"{'✅' if ok else '❌'} {case.name}")
        for good, desc in results:
            if not good:
                print(f"     ✗ {desc}")
        if not ok:
            print(f"     траектория: {json.dumps([t['name'] for t in res.tool_log], ensure_ascii=False)} · ответ: {res.text[:80]!r}")
    print(f"\nИтог: {passed}/{total}")
    return passed, total
```

Рядок за рядком:

- `llm: LLM` є підказкою типу, як у TypeScript, але Python її під час роботи не перевіряє.
- `passed = total = 0` присвоює нуль обом змінним, як у JavaScript.
- `run_agent` запускає цикл. Для кожного прогону створюється новий список повідомлень, і це важливо, бо `run_agent`
  змінює список на місці.
- `max_steps=5` тут є іменованим аргументом `run_agent`, а не функцією `max_steps`, оголошеною вище. Назви збігаються,
  але це різні речі. Зверни увагу на число: межа циклу становить 5, а перевірка в кейсах вимагає не більше 3. Це
  важливо, адже якби межа дорівнювала 3, перевірка `max_steps(3)` не могла б не пройти.
- `[c(res) for c in case.checks]` викликає кожну перевірку й збирає пари «чи пройшло, опис».
- `all(r[0] for r in results)` вимагає, щоб пройшли всі перевірки. Отже, кейс або пройдено, або ні.
- `passed += ok` додає булеве значення до числа. У Python `True` дорівнює 1, а `False` дорівнює 0. У JavaScript це теж
  спрацювало б, але TypeScript відхилив би такий запис.
- `f"{'✅' if ok else '❌'} {case.name}"` є рядком із підстановками, усередині якого стоїть тернарний оператор.
- `for good, desc in results` розгортає кожну пару, як `for (const [good, desc] of results)`.
- `json.dumps([...], ensure_ascii=False)` перетворює список назв на рядок JSON і лишає кирилицю читабельною.
- `res.text[:80]!r` бере перші 80 символів і показує їх у вигляді, як у коді: у лапках. Завдяки `!r` порожню відповідь
  буде видно як `''`, а не як нічого.
- `return passed, total` повертає пару, але код нижче її не використовує.

Функція друкує подробиці лише для кейсів, які не пройшли. Такий вивід легко читати, але успішні прогони не залишають
жодного запису, і порівняти їх потім нема з чим.

### Запуск у кінці файла

```python
try:
    llm = from_env(fallback=ScriptedLLM(mock_agent))
except LLMError as e:
    sys.exit(str(e))
run_suite(llm)
print("\nСовет: прогоняй каждый кейс 5–10 раз на реальной модели — агенты недетерминированы, "
      "смотри на долю успехов, а не на один прогон.")
```

- `from_env` читає змінну середовища `LLM_PROVIDER`. Якщо її немає, функція повертає `fallback`, тобто сценарну модель
  із підробленою функцією. Отже, без налаштувань файл не потребує ані ключа, ані мережі.
- `try` і `except` відповідають `try` і `catch`. Якщо провайдера вказано, а назви моделі немає, `from_env` викидає
  `LLMError`, а `sys.exit(str(e))` друкує текст помилки й завершує програму.
- `run_suite(llm)` стоїть поза `try`. Тому помилка під час самого прогону, наприклад відповідь сервера з кодом 429,
  обірве програму, і Python надрукує стек викликів.
- Два рядки поспіль без оператора Python склеює в один. У JavaScript тут знадобився б `+`.

**Спробуй передбачити:** що надрукує цей файл без налаштувань?

Ось вивід, який випливає з коду. Ми його не запускали, тому звір зі своїм:

Опис провалу не містить аргументів, бо в `called("escalate")` словник `args` порожній, а порожній словник є хибним

### Виправ помилку в підробленій моделі

Заміни рядок із коментарем `баг` на такий:

```python
return Reply("", [ToolCall("y", "escalate", {"reason": text})])
```

Тепер модель просить `escalate`. Інструмент поверне текст зі словом «оператор», і на другому кроці спрацює гілка
«Передаю оператору». Прогін займе 2 кроки, тому обидві перевірки пройдуть, а підсумок стане `4/4`. Ця вправа показує,
що eval справді реагує на поведінку моделі.

### Запуск на справжній моделі

Без налаштувань файл перевіряє підроблену модель, тому це ще не справжній eval. Функція `from_env` у `harness/llm.py`
читає такі змінні:

| Змінна | Що означає |
|--------|------------|
| `LLM_PROVIDER` | `mock` (за замовчуванням), `openai` або `anthropic` |
| `LLM_MODEL` | назва моделі, яку треба взяти з документації провайдера |
| `LLM_API_KEY` | ключ доступу. Для Anthropic підійде також `ANTHROPIC_API_KEY` |
| `LLM_BASE_URL` | адреса для сумісних із OpenAI сервісів. Для Ollama це `http://localhost:11434/v1`, і ключ не потрібен |

Задай ключ у змінній середовища `LLM_API_KEY`, а потім запусти
`LLM_PROVIDER=anthropic LLM_MODEL=назва_моделі python3 examples/07_evals.py`. Повтори команду кілька разів і порівняй
результати: ти побачиш, чи змінюється підсумок від запуску до запуску.

### Чого цей файл не робить

- Він запускає кожен кейс один раз, хоча радить 5–10 разів, тому частки успіхів не дає.
- Він не читає `res.usage`, тому не рахує вартості, і нічого не зберігає у файл.
- Програма завершується кодом 0 навіть тоді, коли кейси не пройшли, бо результат `run_suite` ніхто не перевіряє.
  Автоматичний запуск на сервері збірки вважав би такий запуск успішним.
- Параметр `approve` не передано, тому інструмент із позначкою `needs_approval` зупинив би набір запитанням у
  терміналі.
- Помилка провайдера обриває весь набір і не рахується окремо.
- Порядок викликів не перевіряється, хоча опис файла про нього говорить. Суддю-модель згадано лише в описі.

### Що взяти у свого агента

- Описуй кейси як дані, а перевірки як маленькі функції, які можна поєднувати.
- Друкуй траєкторію й текст відповіді для кожного провалу.
- Вибирай межу циклу більшою за межу в перевірці, інакше перевірка кроків нічого не перевіряє.
- Перевіряй свої перевірки: подай у них хибну відповідь і подивись, чи вони її відкинуть.

### `Motivation`

Вираз **vibe checks** означає перевірку за відчуттям: прочитав відповідь і вирішив, що гарно. Автор статті вважає такі
перевірки корисними, але недостатніми. Загальні бенчмарки моделей теж не допоможуть, бо вони міряють модель, а тобі
потрібно міряти її роботу на завданнях саме твоїх користувачів.

### `Iterating Quickly == Success`

Успіх залежить від того, як швидко ти можеш повторювати цикл покращення. Цикл складається з трьох дій: оцінити якість,
знайти причину збою, змінити поведінку системи. Більшість людей займаються лише третьою дією, тому не можуть вийти за
межі демонстрації. Якщо налагодити оцінювання, дві інші дії стають значно легшими. Автор порівнює це зі звичайними
тестами: на початку вони вимагають роботи, а згодом окупаються. На діаграмі в оригіналі цей цикл намальовано.

### `Case Study: Lucy, A Real Estate AI Assistant`

Rechat є веб-сервісом для агентів із нерухомості, а Lucy є його розмовним помічником. Спершу правки промпта давали
швидкий поступ, але зі зростанням можливостей продукту покращення зупинилося. Стаття називає три ознаки, які варто
знати, бо ти побачиш їх у себе:

- виправлення одного збою викликало інші. Автор порівнює це з грою `whack-a-mole`, де кротів б'ють молотком, а вони
  вилазять в іншому місці;
- окрім оцінки за відчуттям, не було жодного способу зрозуміти, наскільки добре система працює на різних завданнях;
- промпти розрослися до довгих і незручних текстів, бо в них намагалися врахувати всі крайні випадки.

### `Problem: How To Systematically Improve The AI?`

Щоб вийти з цього стану, команда побудувала процес навколо оцінювання. Діаграма показує, як поєднуються оцінювання,
збір даних і правки. Автор застерігає, що насправді процес не такий рівний, як на малюнку.

### `The Types Of Evaluation`

Є три рівні оцінювання, і перший найдешевший. Від ціни залежить частота: перший рівень автор запускає на кожну зміну
коду, другий за розкладом, а третій лише після значних змін продукту. Точної формули, коли додавати кожен рівень,
немає.

### `Level 1: Unit Tests`

Тут unit tests означає твердження про відповідь моделі, тобто assertion, як у pytest або Vitest. Вони мають працювати
швидко й дешево, щоб запускати їх на кожну зміну. Автор додає, що ті самі твердження можна використати ширше: для
очищення даних і для автоматичного повтору, коли текст помилки допомагає моделі виправитися. Якщо не знаєш, що
перевіряти, читай записи й дивись, де система ламається. Запропонувати твердження може й сама модель.

### `Step 1: Write Scoped Tests`

Поділи продукт на можливості, а кожну можливість на сценарії. У статті можливість пошуку житла ділиться на три
сценарії: запиту відповідає одне житло, кілька або жодного. Для кожного сценарію перевіряється кількість результатів.
Є також загальні перевірки, не прив'язані до конкретної можливості. Стаття показує таку перевірку: відповідь не має
містити внутрішній ідентифікатор UUID, тобто довгий унікальний номер запису. Це код на JavaScript із регулярним
виразом і `expect`, тому ти його легко прочитаєш.

Цей приклад показує важливу річ. Промпт уже забороняє показувати UUID, але перевірка в коді все одно потрібна, бо
промпт нічого не гарантує. У Rechat таких тестів сотні, і їх постійно поповнюють новими збоями.

**Для твого агента:** у `07_evals.py` роль такого твердження виконує `contains`, а загальну перевірку можна додати до
кожного кейсу. Наприклад, вона може вимагати, щоб у відповіді не було внутрішнього номера.

### `Step 2: Create Test Cases`

Твердженням потрібні вхідні дані. Автор часто просить модель згенерувати їх. Стаття показує такий промпт: написати 50
різних інструкцій для створення контакту, а до кожної інструкцію для його пошуку. Потім виконують першу інструкцію й
другою перевіряють, що знайдено рівно один результат. Цю вправу легко перенести на свого агента.

Три думки цього розділу особливо важливі:

- не чекай справжніх даних, бо спершу можна згенерувати кейси;
- якщо модель важко проходить тести, це хороша ознака, бо такі тести щось знаходять;
- на відміну від звичайних тестів, 100 % не обов'язкові. Частка успіхів є рішенням про продукт.

### `Step 3: Run & Track Your Tests Regularly`

Запускати тести можна будь-яким звичним способом. У Rechat для цього використовують GitHub Actions. Важливіше інше:
результати треба зберігати з часом разом із версіями тестів і промптів, щоб бачити поступ. Для перегляду вистачить
аналітичної програми, яка вже є в команді. У Rechat це Metabase. Це саме те, чого не вистачає у `run_suite`: він лише
друкує результат.

### `Level 2: Human & Model Eval`

Деякі речі твердженнями не перевіриш. Перед цим рівнем треба записувати траси, інакше читати буде нічого.

### `Logging Traces`

**Trace** (траса) — це запис послідовності подій, наприклад однієї сесії користувача. Для мовних моделей це
здебільшого запис розмови. Автор називає LangSmith як один із варіантів і наголошує, що будь-який такий інструмент
повинен уміти шукати, фільтрувати й показувати записи в зручному вигляді.

### `Looking At Your Traces`

Головне правило цього розділу таке: прибери все, що заважає дивитися на дані. Автор часто пише власний невеликий
переглядач, щоб усе потрібне було на одному екрані: який інструмент і сценарій перевірялись, згенеровано кейс чи він
справжній, посилання на пов'язані записи. Такий застосунок можна зробити менш ніж за день за допомогою Gradio,
Streamlit, Panel чи Shiny. Для тебе це може бути навіть проста сторінка на React.

Оцінку ставлять словами «добре» чи «погано». Автор вважає, що детальними шкалами керувати складніше, ніж двома
оцінками. Ці оцінки згодом стануть основою для звірки судді.

### `How much data should you look at?`

На початку треба дивитися якомога більше: записи всіх кейсів і всі записи користувачів. Зовсім припиняти не можна, але
з часом можна брати вибірку. Примітка внизу статті дає практичну межу: читай, доки не перестанеш дізнаватися нове.
Саме її цитує план модуля.

### `Automated Evaluation w/ LLMs`

Постачальники обіцяють, що людина більше не потрібна. Автор цьому не вірить, бо поняття правильності частково
суб'єктивне, і модель треба узгоджувати з людиною. Процес такий:

1. Модель-критик пише зауваження до кожної відповіді й ставить оцінку «добре» чи «погано».
2. Колега на ім'я Phillip отримує ті самі відповіді в таблиці й заповнює свої зауваження, оцінку й бажану відповідь
   для 25–50 прикладів за раз.
3. Автор порівнює стовпчики й править промпт критика, щоб його оцінки наблизилися до людських.
4. Цю звірку повторюють час від часу, бо вона застаріває.

Це все робиться у звичайній електронній таблиці, без спеціальних програм. Є три поради: для критика бери найпотужнішу
модель, яку можеш собі дозволити; критик сам потребує маленької системи оцінювання, бо теж може помилятися; після
налаштування продовжуй стежити за збігом оцінок.

### Примітка `Important Note on Using Agreement as a Metric`

Простий збіг оцінок може обманювати. У прикладі автора збіг працював, бо близько половини відповідей були поганими.
Якщо поганих відповідей мало, суддя, який завжди каже «добре», матиме високий збіг і не знайде нічого. Тому слід
окремо міряти **precision** і **recall**. Precision показує, яка частина названих суддею поганими справді погана.
Recall показує, яку частину всіх поганих суддя знайшов.

### `Level 3: A/B Testing`

**A/B-тест** показує двом групам користувачів різні версії й порівнює їхню поведінку. Для мовних моделей він працює
так само, як для інших продуктів. Цей рівень підходить лише для зрілого продукту, і в курсі його немає.

### `Evaluating RAG`

**RAG** означає пошук уривків у документах із додаванням їх у запит. Оцінювання такої частини стаття не описує й
посилається на іншого автора. Згадаємо лише, що окремі частини системи теж можна міряти окремо.

### `Eval Systems Unlock Superpowers For Free`, `Fine-Tuning` і `Data Synthesis & Curation`

Система оцінювання дає дві додаткові можливості: дотренування моделі й пошук збоїв. Про пошук збоїв ідеться в
наступному розділі. **Fine-tuning** означає дотренування моделі на власних прикладах. Цей розділ для курсу
необов'язковий. Думка його проста: основна робота полягає в зборі якісних даних, а система оцінювання вже збирає їх.
Твердження й критик відсіюють погані згенеровані приклади, а переглядач записів допомагає відібрати добрі.

### `Debugging`

Коли приходить скарга, система оцінювання вже дає все потрібне для пошуку причини: базу трас із пошуком, твердження,
які позначають збої, інструменти для пошуку причини й спосіб швидко перевірити виправлення. Автор називає можливі
причини: пошук, помилка в коді або слабка модель. Це відповідає контрольному запитанню плану про те, як знайти
винного, коли eval не пройшов.

### `Conclusion`

Висновки зібрано в список, і його варто прочитати в оригіналі:

- прибери все, що заважає дивитися на дані;
- не купуй складних інструментів, бери те, що вже маєш;
- якщо ти не дивишся на багато даних, ти робиш це неправильно;
- не покладайся на загальні системи оцінювання, а будуй власну під свою задачу;
- пиши багато тестів і постійно їх оновлюй;
- модель допоможе згенерувати кейси, твердження й оцінки;
- використовуй ту саму систему для пошуку збоїв і дотренування.

### Що взяти у свого агента

- Записуй траси з першого дня, бо без них нема чого читати.
- Перш ніж писати кейси, прочитай записи справжніх прогонів.
- Став оцінки «добре» чи «погано» й записуй причину.
- Постійно додавай новий кейс на кожен знайдений збій.
- Зберігай результати разом із версією промпта.

### Запитання до статті

**1. Чим unit tests у статті відрізняються від тестів харнесу в курсі?**

<details><summary>Відповідь</summary>

У статті це швидкі перевірки відповідей справжньої моделі. У курсі тести харнесу перевіряють код із заготовленими
відповідями. Перше є eval першого рівня, а друге є звичайним тестом коду.

</details>

**2. Чому автор радить оцінку «добре» чи «погано», а не шкалу балів?**

<details><summary>Відповідь</summary>

Детальними шкалами складніше керувати. На початку важливо швидко зібрати багато оцінок і пояснень, а просту оцінку
ставити легше.

</details>

**3. Суддя збігається з людиною у 95 % випадків. Чому цього числа може бути замало?**

<details><summary>Відповідь</summary>

Якщо поганих відповідей лише 5 %, суддя, який завжди каже «добре», теж збігатиметься в 95 % випадків, хоча не знайде
жодної поганої відповіді. Тому треба окремо міряти precision і recall.

</details>

**4. Навіщо перевіряти відсутність UUID у коді, якщо промпт уже забороняє його показувати?**

<details><summary>Відповідь</summary>

Промпт лише впливає на поведінку моделі й нічого не гарантує. Перевірка в коді покаже, як часто модель порушує цю
вимогу.

</details>

## Розділ про оцінювання у статті про багатоагентну систему

**Де читати:** [How we built our multi-agent research
system](https://www.anthropic.com/research/multi-agent-research-system), розділ `Effective evaluation of agents`, а
також абзац `End-state evaluation of agents that mutate state over many turns` у додатку. Статтю компанії Anthropic
докладно читають у модулі 5, тому тут розглянемо лише оцінювання.

**Вступ розділу.** Звичайне оцінювання припускає, що за входом X система йде шляхом Y і дає результат Z. Агенти так не
працюють: той самий запит може пройти різними правильними шляхами. Тому перевіряти треба, чи досягнуто правильного
результату і чи розумним був сам процес.

**`Start evaluating immediately with small samples`.** Не чекай великого набору. На початку розробки зміни сильно
впливають на результат: правка промпта може підняти частку успіхів із 30 до 80 %, а таку різницю видно на кількох
кейсах. Команда почала приблизно з 20 запитів, схожих на справжні. Це не суперечить лекції: малий набір показує великі
зміни, а малих не показує.

**`LLM-as-judge evaluation scales when done well`.** Текст дослідження важко перевірити кодом, тому його оцінює
суддя-модель. Перелік критеріїв такий: чи збігаються твердження з джерелами, чи посилання справді підтверджують
твердження, чи охоплено все запитане, чи якісні джерела, чи раціонально використано інструменти. Команда спробувала
кількох суддів, але найстабільнішим і найближчим до людських оцінок виявився один виклик, який видає бали від 0,0 до
1,0 і підсумок «пройшов чи ні». Найкраще це працює, коли кейс має чітку правильну відповідь.

**`Human evaluation catches what automation misses`.** Люди знаходять те, чого не знаходить автоматика: дивні
відповіді на незвичні запити, збої системи, упередженість у виборі джерел. У цьому випадку люди-тестувальники
помітили, що ранні агенти вибирали сайти, написані заради пошукових систем, а не наукові статті чи особисті блоги
фахівців.

**`End-state evaluation`.** Якщо агент щось змінює, кожна дія впливає на наступну, і перевіряти кожен крок важко.
Краще перевірити кінцевий стан. Для складних завдань роботу ділять на контрольні точки, де конкретна зміна вже мала
статися.

**Що взяти у свого агента.** Почни з малого набору вже зараз. Не вимагай точного шляху, якщо це не потрібно. Для
тексту зроби одного суддю з чіткими критеріями, а для агента, який змінює дані, перевіряй кінцевий стан.

## Домовленості gen-ai в OpenTelemetry

**Де читати:** курс дає посилання на сторінку `opentelemetry.io/docs/specs/semconv/gen-ai/`. Ця сторінка тепер
повідомляє, що домовленості переїхали в [окремий
репозиторій](https://github.com/open-telemetry/semantic-conventions-genai), тому читати варто там, у теці `docs`. У
плані цей матеріал також доступний через сервер `opentelemetry-docs`.

**Що це таке.** **OpenTelemetry** є стандартом запису трас, метрик і журналів. Він не залежить від мови програмування
й від постачальника. Одна частина траси називається **span**: наприклад, один виклик моделі або один виклик
інструмента. **Semantic conventions** є домовленостями про те, як називати поля такого запису. Завдяки їм програма
перегляду розуміє записи, зроблені будь-яким кодом.

**Головне, що треба зрозуміти:**

- на сторінці про span стоїть статус `Development`, тому назви ще можуть змінюватися;
- span виклику інструмента називається `execute_tool {gen_ai.tool.name}`, а для агента є операція `invoke_agent`;
- текст промптів і відповідей за замовчуванням не записують, його вмикають окремо. Це важливо, бо там можуть бути
  особисті дані.

**Як поля відповідають коду курсу.** Цей код не використовує OpenTelemetry, але потрібні дані в ньому є:

| Поле OpenTelemetry | Що означає | Звідки взяти в коді курсу |
|--------------------|------------|---------------------------|
| `gen_ai.request.model` | Запитана модель | `llm.model` у `OpenAICompatLLM` та `AnthropicLLM` |
| `gen_ai.usage.input_tokens` | Вхідні токени | `reply.input_tokens` |
| `gen_ai.usage.output_tokens` | Вихідні токени | `reply.output_tokens` |
| `gen_ai.response.finish_reasons` | Причина завершення відповіді | `reply.stop_reason` |
| `gen_ai.tool.name` | Назва інструмента | `call.name` |
| `gen_ai.tool.call.id` | Ідентифікатор виклику | `call.id` |

**Що взяти у свого агента.** Для навчального агента досить файла з рядками JSON, як у лекції. Але назви полів варто
брати з цього переліку: якщо згодом ти перейдеш на справжні інструменти, змінювати доведеться менше.
