### Рядки 1–18: опис файла й імпорти

```python
"""Финальный проект: мини-репетитор по мотивам LearnHarness.
...
"""
import json
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parents[2]))
from harness import FactMemory, Ledger, Reply, ScriptedLLM, ToolCall, from_env, run_agent, tool  # noqa: E402
from harness.llm import LLMError  # noqa: E402
```

**Рядок у потрійних лапках** на початку файла називається docstring. Це опис модуля, який можна прочитати з програми.
У JavaScript найближчий аналог — коментар JSDoc на початку файла, але docstring є справжнім значенням, а не
коментарем. Він містить чотири фази: `probe` (замір), `plan` (план), `teach` (навчання), `graph` (журнал знань).

**`import json`** підключає стандартний модуль, а **`from pathlib import Path`** бере з модуля одну назву. Це схоже на
`import { Path } from "pathlib"`.

**`sys.path.insert(0, ...)`** вирішує конкретну проблему. Python шукає модулі в теках зі списку `sys.path`. Файл
лежить у `examples/capstone/`, а пакет `harness` лежить у корені проєкту, тому без цього рядка імпорт не спрацює.
`Path(__file__)` — шлях до цього файла, `resolve()` робить його повним, а `.parents[2]` піднімається на дві теки
вгору: `parents[0]` це `capstone`, `parents[1]` це `examples`, `parents[2]` це корінь. У Node.js таке зазвичай
вирішують відносним імпортом чи налаштуванням шляхів.

**`# noqa: E402`** — коментар для лінтера. Правило E402 вимагає, щоб імпорти стояли на початку файла, а тут вони
стоять після `sys.path.insert` навмисно.

Імпортовані назви тобі знайомі: `run_agent` і `tool` із модуля 2, `from_env`, `ScriptedLLM`, `Reply` і `ToolCall` із
модуля 1, `Ledger` і `FactMemory` із модуля 4.

### Рядки 20–24: налаштування й спільний стан

```python
DEMO = "--demo" in sys.argv or len([a for a in sys.argv[1:] if not a.startswith("--")]) == 0
GOAL = next((a for a in sys.argv[1:] if not a.startswith("--")), "Хочу понять, почему HTTPS безопасен")
DATA = Path(__file__).parent / "_data"
knowledge = FactMemory(Ledger(DATA / "knowledge.jsonl"))
state = {"phase": "probe", "assessment": None, "plan": None, "quiz_log": []}
```

**`sys.argv`** є списком аргументів командного рядка, а `sys.argv[1:]` бере всі елементи, крім першого, бо перший
містить назву програми. Це те саме, що `process.argv.slice(2)` у Node.js, тільки там першим стоїть ще й шлях до
`node`.

**`[a for a in ... if not a.startswith("--")]`** називається списковим виразом (list comprehension). У JavaScript це
`args.filter(a => !a.startsWith("--"))`. Вираз залишає аргументи, що не є прапорцями.

**`DEMO`** стає істинним у двох випадках: є прапорець `--demo` або немає жодного аргументу, який не є прапорцем. Тому
запуск без аргументів теж є демонстрацією.

**`GOAL`** використовує вираз із круглими дужками, який називається генераторним. Він не будує список одразу, а видає
значення по одному. Функція `next` бере перше значення, а якщо значень немає, повертає другий аргумент. У JavaScript
це `args.find(a => !a.startsWith("--")) ?? "Хочу понять..."`.

**`Path(__file__).parent / "_data"`** будує шлях: об'єкт `Path` перевизначає оператор `/`. Це те саме, що
`path.join(__dirname, "_data")`.

**`knowledge`** створюється під час завантаження файла, і конструктор `Ledger` одразу створює теку `_data`, якщо її
немає. Сам файл журналу з'явиться під час першого запису.

**`state`** є звичайним словником (`dict`), подібним до об'єкта в JavaScript. `None` відповідає `null`. Цей словник є
глобальним станом модуля, і всі функції нижче читають його й змінюють. Для одного запуску це зручно, але для evals, де
запусків багато, його доведеться скидати.

**Спробуй передбачити:** що буде в `DEMO` і `GOAL` після команди `python3 mini_tutor.py --verbose "Як працює DNS"`?

<details><summary>Відповідь</summary>

`DEMO` дорівнює `False`: прапорця `--demo` немає, а список аргументів без прапорців має один елемент. `GOAL` дорівнює
«Як працює DNS», бо `--verbose` починається з `--` і пропускається.

</details>

### Рядки 31–36: декоратор `@tool` і функція `quiz`

```python
@tool("Задать ученику вопрос с вариантами ответа. Ответ и уверенность ученика вернутся результатом.",
      client_side=True,
      params={"question": "вопрос", "options": "варианты ответа", "correct": "индекс правильного (с 0)",
              "plan_node": "id узла плана, который проверяется (или 'probe')"})
def quiz(question: str, options: list, correct: int, plan_node: str) -> str:
    raise RuntimeError("client-side: выполняется не здесь")
```

**Декоратор** `@tool(...)` є коротким записом такого виклику:
`quiz = tool("...", client_side=True, params={...})(quiz)`. Функцію передають у `tool`, а результат записують під тією
самою назвою. У JavaScript це функція вищого порядку: `const quiz = tool("...", options)(function quiz(...) {...})`.
Важливий наслідок: після цих рядків назва `quiz` позначає вже не функцію, а об'єкт класу `Tool`. Саме тому в `main`
список `[quiz, probe_done]` передає об'єкти з описами.

**Позначення типів** `question: str`, `options: list`, `-> str` схожі на TypeScript, але Python не перевіряє їх під
час виконання. Тут вони мають іншу роль: `tool` читає їх і будує схему JSON, яку побачить модель. Для `quiz` схема
виходить такою:

```json
{"name": "quiz",
 "description": "Задать ученику вопрос с вариантами ответа. ...",
 "parameters": {"type": "object",
   "properties": {"question": {"type": "string", "description": "вопрос"},
                  "options": {"type": "array", "description": "варианты ответа"},
                  "correct": {"type": "integer", "description": "индекс правильного (с 0)"},
                  "plan_node": {"type": "string", "description": "id узла плана, который проверяется (или 'probe')"}},
   "required": ["question", "options", "correct", "plan_node"]}}
```

Зверни увагу, що `options` описано лише як `array` без опису елементів. Тому `validate_args` не помітить, якщо
елементи не є рядками.

**Параметр `client_side=True`** каже циклу, що функцію не треба викликати. У `harness/loop.py` функція `_execute`
бачить цю позначку й передає аргументи в `client_handler`. Тіло функції `quiz` ніколи не виконується, а рядок
`raise RuntimeError` є запобіжником на випадок, якщо хтось викличе її напряму. `raise` відповідає `throw` у
JavaScript.

### Рядки 39–43: `probe_done`

```python
@tool("Завершить замер: записать, что ученик уже знает и чего нет.", terminates=True,
      params={"knows": "что уже понимает", "gaps": "пробелы", "goal": "цель ученика своими словами"})
def probe_done(knows: list, gaps: list, goal: str) -> str:
    state.update(phase="plan", assessment={"knows": knows, "gaps": gaps, "goal": goal})
    return "Замер сохранён. Передаю учителю."
```

**`terminates=True`** каже циклу зупинитися після успішного виклику. **`state.update(phase="plan", assessment=...)`**
змінює кілька полів словника й відповідає `Object.assign(state, {phase: "plan", assessment: {...}})`. Запис
`phase="plan"` називається іменованим аргументом. У JavaScript такого немає, і найближчий аналог — об'єкт параметрів.

Оцінка має три поля: що людина вже розуміє, чого не розуміє і як модель сформулювала її мету. Рядок результату модель
фактично не використає: цикл зупиниться, а вчитель почне з порожньою історією.

**Що зламається без цього.** Якщо прибрати `terminates=True`, цикл викличе модель ще раз, і замірник може продовжити
ставити запитання. Якщо прибрати `state.update`, вчитель не отримає оцінки, а `main` завершить програму перевіркою
`phase`.

### Рядки 46–59: `plan_init`

```python
@tool("Один раз создать план урока: граф зависимостей. edges — пары [от, к]: 'от' нужно понять раньше 'к'.",
      params={"nodes": "список объектов {id, title}", "edges": "список пар [from_id, to_id]"})
def plan_init(nodes: list, edges: list) -> str:
    if state["plan"]:
        return "ОШИБКА: план уже создан, он неизменяем. Прогресс отслеживается по квизам."
    ids = {n.get("id") for n in nodes}
    bad = [e for e in edges if len(e) != 2 or e[0] not in ids or e[1] not in ids]
    if bad:
        return f"ОШИБКА: рёбра ссылаются на несуществующие узлы: {bad}"
    order = topo_sort(ids, edges)
    if order is None:
        return "ОШИБКА: в плане есть цикл — это должен быть ациклический граф (DAG). Исправь и вызови снова."
    state.update(plan={"nodes": nodes, "edges": edges, "order": order}, phase="teach")
    return "План принят. Порядок обучения: " + " → ".join(order)
```

Цю функцію варто прочитати як послідовність перевірок. Кожна в разі помилки повертає текст, який починається з
«ОШИБКА», і модель прочитає цей текст як результат інструмента.

1. **`if state["plan"]:`** перевіряє, чи план уже існує. У Python `None` є хибним значенням, а непорожній словник
   істинним. Повторний виклик отримує відмову, тому план незмінний.
2. **`ids = {n.get("id") for n in nodes}`** будує множину назв вузлів. Фігурні дужки без двокрапки дають множину
   (`set`). У JavaScript це `new Set(nodes.map(n => n.id))`. Метод `.get("id")` повертає `None`, якщо ключа немає,
   тоді як `n["id"]` викинув би помилку `KeyError`.
3. **`bad = [...]`** збирає ребра з помилками: ребро не є парою, або один із його кінців не є відомим вузлом. Оператор
   `or` зупиняється на першому істинному значенні, тому для порожнього ребра `e[0]` не читається.
4. **`f"...{bad}"`** називається f-рядком і відповідає шаблонному рядку в JavaScript.
5. **`topo_sort`** повертає порядок або `None` за наявності циклу.
6. **`state.update(...)`** зберігає план і змінює фазу. Поле `order` зберігає обчислений порядок, а `edges` лишаються
   як вихідні дані.
7. **`" → ".join(order)`** з'єднує елементи рядком. У JavaScript це `order.join(" → ")`, тобто порядок запису
   протилежний.

Якщо код кидає виняток, його перехоплює `_execute` і перетворює на текст для моделі. Наприклад, якщо елемент `nodes` є
рядком, `.get` викине `AttributeError`, і модель отримає «ОШИБКА выполнения plan_init: AttributeError...».

**Що зламається без цього.** Без перевірки циклів план із циклом мовчки потрапив би в `state`, а `order` лишився б
неповним. Без перевірки ребер `topo_sort` викинув би `KeyError` на невідомому вузлі, і модель отримала б менш
зрозумілу помилку.

**Спробуй передбачити:** модель викликає `plan_init(nodes=[{"id": 1}, {"id": 2}], edges=[[1, 2]])`. Що станеться? А що
буде на другому виклику з правильними рядками?

<details><summary>Відповідь</summary>

Перевірки ребер і циклу пройдуть, бо числа так само є в множині. Рядок `state.update` збереже план. Потім
`" → ".join(order)` кине `TypeError`, бо `join` вміє лише рядки. `_execute` перетворить виняток на «ОШИБКА
выполнения», хоча план уже збережено. Наступна спроба з рядками отримає «план уже создан», і модель лишиться з планом
із числами. Цього не сталося б, якби `state.update` стояв після побудови тексту.

</details>

### Рядки 62–66: `record_knowledge`

```python
@tool("Записать в журнал знаний утверждения, которые ученик понял на этом уроке.",
      params={"claims": "самостоятельные утверждения, по одному на пункт"})
def record_knowledge(claims: list) -> str:
    added = [c for c in claims if isinstance(c, str) and knowledge.add(c, source=GOAL)]
    return f"Записано новых утверждений: {len(added)} (дубликаты пропущены)"
```

**`isinstance(c, str)`** перевіряє тип під час виконання, як `typeof c === "string"`. Це потрібно, бо схема каже лише
`array`. Оператор `and` зупиняється на першому хибному значенні, тому `knowledge.add` викликається лише для рядків.

Це списковий вираз із побічною дією: `knowledge.add` пише у файл і водночас повертає, чи було твердження новим. Він
виконує фільтрацію й запис за один прохід, що коротко, але потребує уваги під час читання. `source=GOAL` зберігає мету
уроку як джерело твердження.

**Що зламається без цього.** Без `isinstance` елемент, що не є рядком, викине виняток у `_norm`. Без перевірки
дублікатів кожен запуск дописував би ті самі твердження, і журнал ріс би без користі.

Метод `FactMemory.add` у `harness/memory.py` робить таке: `fact_id` приводить текст до нижнього регістру, замінює
розділові знаки пробілами й обчислює хеш SHA-256, тобто короткий відбиток змісту. Якщо такий ідентифікатор уже є серед
`self.facts()`, він повертає `False`. Тому твердження, що відрізняються лише регістром чи комою, вважаються
однаковими, а твердження, переписане іншими словами, вважається новим.

### Рядки 69–82: `topo_sort`

```python
def topo_sort(ids, edges):
    indeg = {i: 0 for i in ids}
    for a, b in edges:
        indeg[b] += 1
    ready, order = sorted(i for i, d in indeg.items() if d == 0), []
    while ready:
        n = ready.pop(0)
        order.append(n)
        for a, b in edges:
            if a == n:
                indeg[b] -= 1
                if indeg[b] == 0:
                    ready.append(b)
    return order if len(order) == len(ids) else None
```

Цей спосіб називають алгоритмом Кана (Kahn's algorithm). Покроковий приклад із числами є в лекції 9, а тут розберемо
запис.

- **`indeg = {i: 0 for i in ids}`** будує словник (dictionary comprehension). Кожному вузлу відповідає 0. Назва
  означає in-degree, тобто кількість стрілок, що входять у вузол. У JavaScript:
  `Object.fromEntries([...ids].map(i => [i, 0]))`.
- **`for a, b in edges:`** розкладає кожну пару на дві змінні. У JavaScript це `for (const [a, b] of edges)`.
- **`indeg.items()`** видає пари «ключ, значення», як `Object.entries`.
- **`ready, order = sorted(...), []`** виконує два присвоєння в одному рядку. `sorted` повертає новий відсортований
  список. Тому вузли на старті йдуть за абеткою, і порядок не залежить від випадкового порядку множини.
- **`while ready:`** працює, доки список непорожній, бо порожній список є хибним значенням. Запис `ready.pop(0)`
  прибирає перший елемент, як `shift()` у JavaScript, а `order.append(n)` відповідає `push`.
- **Внутрішній цикл** проходить усі ребра, що виходять із `n`. Для 3–5 вузлів повний перегляд цілком прийнятний.
- **Останній рядок** є умовним виразом, як `cond ? order : null`. Якщо не всі вузли потрапили в порядок, значить, є
  цикл.

Новий вузол додається в кінець `ready`, тому алфавітним є лише стартовий порядок. Перевірки «план починається з
прогалини» через це треба писати обережно. Про це йдеться в останньому запитанні лекції 9.

**Спробуй передбачити:** що поверне `topo_sort({"a", "b", "c"}, [["a", "b"], ["a", "b"], ["b", "c"]])`, де одне ребро
повторюється?

<details><summary>Відповідь</summary>

`["a", "b", "c"]`. Вузол `b` матиме `indeg` 2, але обидва ребра від `a` зменшать його по одному разу, тому він дійде
до нуля. Повторення не ламає функцію.

</details>

Цю функцію передано в `run_agent` параметром `client_handler`. Цикл викликає її з об'єктом інструмента `t` та
аргументами моделі `args`. Тут `t` не використовується, але сигнатуру задає цикл. Аргументи вже пройшли

- **`enumerate(...)`** видає пари з номером і значенням. У JavaScript: `options.forEach((o, i) => ...)`.
- **`choice, conf = next(AUTO_ANSWERS, (args["correct"], 3))`** бере наступну пару. Другий аргумент `next` спрацює,
  коли список вичерпано: тоді учень завжди відповідає правильно з упевненістю 3. Без цього значення ітератор викинув
  би `StopIteration`.
- **`thinking`** містить вигадане міркування учня. Для неправильної відповіді воно завжди одне й те саме, бо записане
  під конкретне запитання сценарію.
- **`input(...)`** показує рядок і блокує програму, доки людина не введе текст. Таке блокування неможливе в браузері,
  тому вебінтерфейс потребує іншої будови.
- **`int(input(...) or -1)`** обробляє порожнє введення. Порожній рядок є хибним значенням, тому `or` поверне `-1`, як

- **`ok = choice == args["correct"]`** є головною перевіркою.
- **`state["quiz_log"].append(...)`** записує лише вузол і результат. Упевненість і міркування сюди не потрапляють.
- **`json.dumps(..., ensure_ascii=False)`** перетворює об'єкт на рядок, як `JSON.stringify`. Параметр лишає кирилицю
  як є, а не замінює кожну літеру записом `\uXXXX`. Так рядок коротший і читабельний.

Результат інструмента має бути рядком, тому модель отримує рядок JSON і читає в ньому чотири поля.

### Рядки 135–148: `demo_prober`

```python
def demo_prober(system, messages, tools):
    n_quiz = sum(1 for m in messages if m["role"] == "tool")
    if n_quiz == 0:
        return Reply("Сначала пара вопросов, чтобы понять, откуда начать.", [ToolCall("p1", "quiz", {
            "question": "Что делает шифрование?", "options": ["Сжимает данные", "Делает данные нечитаемыми без ключа", "Ускоряет сеть"],
            "correct": 1, "plan_node": "probe"})])
    if n_quiz == 1:
        return Reply("", [ToolCall("p2", "quiz", {...})])
    return Reply("", [ToolCall("p3", "probe_done", {...})])
```

Тут і в наступному розділі `{...}` і `...` позначають скорочені дані. Замість справжньої моделі тут працює функція.
`ScriptedLLM` приймає або список відповідей, або функцію. Її сигнатура збігається з тим, що передає
`ScriptedLLM.complete`: системний промпт, повідомлення й інструменти.

**`sum(1 for m in messages if ...)`** рахує елементи, як `messages.filter(...).length`. Функція дивиться на кількість
результатів інструментів в історії, тому відповідь залежить від того, що вже сталося. Цикл надсилає всю історію
щоразу, тож сценарій без внутрішнього стану може визначити, на якому він кроці.

**`Reply`** і **`ToolCall`** є класами з `harness/llm.py`, оголошеними декоратором `@dataclass`. Він сам створює
конструктор із полів. У TypeScript це схоже на клас із властивостями в параметрах конструктора. Тому
`ToolCall("p1", "quiz", {...})` заповнює поля `id`, `name`, `arguments`, а `Reply("текст", [виклики])` заповнює `text`
і `tool_calls`.

**`from_env(fallback=...)`** читає змінну оточення `LLM_PROVIDER`. Якщо її немає, повертає `fallback`, тобто сценарій.
Якщо її вказано, створює справжнього клієнта й нехтує сценарієм. Клієнтів два, бо кожен сценарій свій. Зі справжньою
моделлю обидва звертаються до однієї моделі, бо `from_env` читає ті самі змінні. Якщо хочеш дешевшу модель для
замірника, змінювати доведеться тут.

**`try ... except LLMError as e`** відповідає `try ... catch`. `from_env` кидає `LLMError`, якщо вказано провайдера
без моделі. **`sys.exit(str(e))`** виводить текст у потік помилок і завершує програму з кодом 1, тому людина бачить
зрозуміле повідомлення, а не стек викликів.

**Перший `run_agent`** отримує замірника: промпт із підставленою метою, історію з одного повідомлення, два

міг написати текст або вичерпати кроки. `sys.exit` завершує програму.

**Другий `msgs`** є новим списком. Старий список більше ніхто не використовує, тому вся переписка зникає. Оцінка йде в
системний промпт через `json.dumps`.

**Другий `run_agent`** отримує вчителя з іншим набором інструментів і межею у 25 кроків. Завершується він, коли модель

стоїть поза функціями, виконається й під час імпорту: буде створено теку `_data`, а `DEMO` обчислиться з аргументів
тієї програми, яка виконує імпорт. Для тестів це незручно.

### Як усе працює разом із циклом

`_execute` у `harness/loop.py` обробляє кожен виклик у такому порядку:

1. Чи є такий інструмент? Якщо ні, модель отримує «ОШИБКА: инструмента ... нет».
2. Чи правильні аргументи (`validate_args`)? Якщо ні, модель отримує «ОШИБКА валидации».
3. Чи потрібен дозвіл (`needs_approval`)? У цьому файлі такого немає.
4. Чи це клієнтський інструмент? Якщо так, виклик іде в `client`.
5. Інакше виконується сама функція, а виняток перетворюється на текст для моделі.

Цикл запобігає винятку лише на кроці 5. Тому неправильні аргументи й помилка в `plan_init` стають повідомленням для
моделі, а помилка в `client` завершує програму.
