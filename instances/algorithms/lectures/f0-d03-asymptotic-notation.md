# Лекція. День 3. Асимптотика: O, Θ і Ω

Ця лекція вчить мови, якою порівнюють швидкість алгоритмів: позначень `O`, `Θ` і `Ω`. Читання займе близько 55 хвилин.
Під кожним прикладом коду стоїть справжній вивід, який програма надрукувала в Node 24.22.

Учора ви рахували кроки сортування вставками і отримали громіздкі вирази на кшталт `a·n² + b·n + c`. Наприкінці лекції
ми домовилися лишати з такого виразу лише `n²` і писати `Θ(n²)`. Сьогодні з'ясуємо, що саме означає цей запис, чому
так можна робити і де таке спрощення обманює.

**Після лекції ви зможете пояснити:**

- що означає «функція росте не швидше за `n²`» і як це записують через `O`;
- чим `O`, `Ω` і `Θ` відрізняються одне від одного і як довести кожне з них, знайшовши сталі `c` і `n₀`;
- чому «найгірший випадок» і «`O`» — різні речі, і як правильно сказати про сортування вставками;
- як спростити вираз до порядку росту і де прості правила дають хибну відповідь;
- як знайти приховані цикли в коді, який виглядає як один цикл;
- що мають на увазі на співбесіді, коли кажуть «O від n квадрат».

## Один цикл, який виявився квадратичним

На перевірці коду колега показує функцію, яка прибирає з масиву повтори і зберігає порядок першої появи:

```ts
// src/dedupe.ts
export function dedupeWithIncludes(xs: readonly number[]): number[] {
  const result: number[] = [];
  for (const x of xs) {
    if (!result.includes(x)) {   // includes переглядає result від початку
      result.push(x);
    }
  }
  return result;
}
```

«Тут один цикл, отже час лінійний», — каже колега. На тестах із тисячею елементів функція працює менше мілісекунди, і
перевірку пропускають. Через місяць ту саму функцію викликають для 100 000 записів, і сторінка висне на п'ять секунд.

Помилка в слові «один». Метод `includes` сам перебирає масив `result` від початку, поки не знайде шукане значення або
не дійде до кінця. Якщо повторів немає, `result` росте з кожним проходом, і `includes` на проході з номером `k`
перевіряє `k` елементів. Разом виходить `0 + 1 + … + (n − 1) = n(n − 1) / 2` перевірок, та сама сума, що й учора в
сортуванні вставками. Цикл у коді один, а квадратична кількість кроків є.

Ось інша версія тієї самої функції. Вона запам'ятовує вже бачені значення в множині `Set`, яка перевіряє наявність
елемента, не переглядаючи всі елементи. Як `Set` це робить, план пояснить у фазі 1, у дні про хеш-таблиці.

```ts
export function dedupeWithSet(xs: readonly number[]): number[] {
  const seen = new Set<number>();
  const result: number[] = [];
  for (const x of xs) {
    if (!seen.has(x)) {          // has у Set не переглядає всі елементи
      seen.add(x);
      result.push(x);
    }
  }
  return result;
}
```

Програма виміряла обидві функції на масивах без повторів, тобто в найгіршому для них випадку. Кожне число — медіана
п'яти запусків. **Медіана** — це середнє за порядком значення: з п'яти вимірів, розставлених за зростанням, береться
третій. Медіана менше залежить від одного випадково довгого запуску, ніж звичайне середнє.

```
n = 1000: includes 0.59 мс, Set 0.21 мс
n = 10000: includes 49.22 мс, Set 0.97 мс
n = 100000: includes 4939.71 мс, Set 10.13 мс
```

Подивіться не на самі мілісекунди, а на те, як вони змінюються. Коли `n` зростає вдесятеро, час версії з `includes`
зростає приблизно в сто разів, бо `10² = 100`. Час версії з `Set` зростає приблизно вдесятеро. Саме це відношення і
передає асимптотика: версія з `includes` має порядок росту `Θ(n²)`, а версія з `Set` у середньому `Θ(n)`. На тисячі
елементів різниця непомітна, на ста тисячах вона в п'ятсот разів.

Ця лекція вчить бачити таке відношення до запуску, читаючи код.

## Що відбувається, коли вхід подвоюється

Найпростіший спосіб відчути порядок росту — спитати, як зміниться кількість кроків, якщо вхід стане вдвічі більшим.
Програма порахувала значення кількох функцій для `n = 1000` і `n = 2000`:

| Функція | При `n = 1000` | При `n = 2000` | У скільки разів зросла |
|---------|----------------|----------------|------------------------|
| `log₂ n` | ≈ 9,97 | ≈ 10,97 | на 1, тобто в 1,1 раза |
| `n` | 1000 | 2000 | у 2 рази |
| `n log₂ n` | ≈ 9 966 | ≈ 21 932 | трохи більше ніж у 2 рази |
| `n²` | 1 000 000 | 4 000 000 | у 4 рази |
| `n³` | 10⁹ | 8 · 10⁹ | у 8 разів |
| `2ⁿ` | `2¹⁰⁰⁰` | `2²⁰⁰⁰` | у `2¹⁰⁰⁰` разів |

Звідси правило, яке варто тримати в голові:

- **логарифм** при подвоєнні входу зростає лише на сталу величину;
- **лінійна** функція подвоюється;
- **квадратична** зростає вчетверо, **кубічна** — увосьмеро;
- **експоненційна** при подвоєнні входу підноситься до квадрата, а при збільшенні входу на одиницю вже подвоюється.

Тепер подивіться на дві функції `3n² + 20n` і `n²`. При подвоєнні `n` обидві зростають майже вчетверо. Сталий множник
3 і доданок `20n` не змінюють відповіді на запитання «що буде з більшим входом». Тому порядок росту відкидає і
множники, і молодші доданки. Але щоб таке відкидання було чесним, потрібне точне означення.

## Позначення `O`: верхня межа

Неформально `f(n) = O(g(n))` означає: «`f` росте не швидше за `g`, якщо не зважати на сталий множник і на малі `n`».
Формально CLRS дає таке означення.

> `f(n) = O(g(n))`, якщо існують додатні сталі `c` і `n₀` такі, що `0 ≤ f(n) ≤ c · g(n)` для всіх `n ≥ n₀`.

Розберемо кожну частину.

- **`c`** — сталий множник. Він дозволяє не зважати на те, що `f` може бути в кілька разів більшою за `g`. Важливо, що
  `c` не залежить від `n`: це одне число на всі `n`.
- **`n₀`** — поріг. Нерівність мусить виконуватися лише для `n`, не менших за поріг. Що відбувається на малих `n`,
  неважливо.
- **`0 ≤ f(n)`** — вимога, щоб функція була невід'ємною для досить великих `n`. Кількість кроків і так завжди
  невід'ємна, тому для нас ця частина виконується сама.
- Слово **«існують»** означає: щоб довести `f(n) = O(g(n))`, досить знайти **одну** пару чисел `c` і `n₀`, для якої
  нерівність правдива.

### Приклад: `4n² + 100n + 500 = O(n²)`

Цей приклад CLRS показує, що молодші доданки можна відкинути, навіть якщо їхні множники набагато більші за множник
старшого доданка. Треба знайти `c` і `n₀` такі, що `4n² + 100n + 500 ≤ c · n²` для всіх `n ≥ n₀`.

Поділимо обидві частини на `n²`:

```
4 + 100/n + 500/n² ≤ c
```

Ліва частина зменшується, коли `n` росте, бо `100/n` і `500/n²` стають меншими. Тому досить, щоб нерівність
виконувалася при `n = n₀`: для більших `n` ліва частина лише менша. Програма порахувала ліву частину для трьох
порогів:

| `n₀` | `4 + 100/n₀ + 500/n₀²` | Яке `c` підходить |
|------|------------------------|--------------------|
| 1 | 4 + 100 + 500 = 604 | `c = 604` |
| 10 | 4 + 10 + 5 = 19 | `c = 19` |
| 100 | 4 + 1 + 0,05 = 5,05 | `c = 5,05` |

Підходить будь-який рядок таблиці: кожен дає пару `c` і `n₀`, для якої означення виконується. Чим більший поріг, тим
ближче `c` до 4, тобто до множника старшого доданка. Це і є точний зміст слів «молодші доданки неважливі для великих
`n`».

### Протилежний приклад: `n³ − 100n²` не є `O(n²)`

Тут множник при `n²` великий і від'ємний, і здається, що він «стримує» куб. Припустімо, що `n³ − 100n² ≤ c · n²` для
всіх `n ≥ n₀`. Поділимо на `n²`:

```
n − 100 ≤ c
```

Яке б `c` ми не вибрали, при `n > c + 100` нерівність порушується. Отже, потрібних `c` і `n₀` не існує, і `n³ − 100n²`
не є `O(n²)`. Так доводять, що `O` **не** виконується: показують, що для будь-якого `c` нерівність ламається на
якомусь великому `n`.

### `O` — це межа зверху, і вона не мусить бути точною

`7n³ + 100n² − 20n + 6` є `O(n³)`, але також `O(n⁴)`, `O(n⁵)` і `O(2ⁿ)`. Усі ці записи правдиві, бо функція справді
росте не швидше за кожну з них. Тому сам по собі запис «`O(n²)`» каже лише «не гірше за квадратичне». Він не каже, що
функція квадратична. Через це на `O` не можна спиратися, коли треба сказати, що алгоритм **повільний**.

## Позначення `Ω`: нижня межа

`Ω` — дзеркальне відображення `O`. Неформально `f(n) = Ω(g(n))` означає «`f` росте не повільніше за `g`».

> `f(n) = Ω(g(n))`, якщо існують додатні сталі `c` і `n₀` такі, що `0 ≤ c · g(n) ≤ f(n)` для всіх `n ≥ n₀`.

Приклад CLRS: `4n² + 100n + 500 = Ω(n²)`. Ділимо на `n²` і отримуємо `4 + 100/n + 500/n² ≥ c`. Ліва частина завжди
більша за 4, тому підходить `c = 4` і будь-яке `n₀`.

Цікавіший приклад: `n²/100 − 100n − 500 = Ω(n²)`. Молодші доданки тепер від'ємні й великі. Після ділення на `n²`:

```
1/100 − 100/n − 500/n² ≥ c
```

Для малих `n` ліва частина від'ємна, а `c` мусить бути додатним. Програма порахувала: при `n = 10 004` ліва частина ще
від'ємна, а при `n = 10 005` уже додатна, хоч і крихітна, близько `2,5 · 10⁻⁹`. При `n = 100 000` вона близько 0,009.
Отже, підходить, наприклад, пара `n₀ = 100 000`, `c = 0,008`. Чим більший поріг, тим ближче можна взяти `c` до
`1/100`. Цей приклад показує, навіщо означенню поріг `n₀`: без нього від'ємні молодші доданки зіпсували б нерівність
на малих `n`.

## Позначення `Θ`: точна оцінка

`Θ` поєднує обидві межі.

> `f(n) = Θ(g(n))`, якщо існують додатні сталі `c₁`, `c₂` і `n₀` такі, що `0 ≤ c₁ · g(n) ≤ f(n) ≤ c₂ · g(n)` для всіх
> `n ≥ n₀`.

Тобто після порогу `f` затиснута між двома копіями `g`, помноженими на різні сталі. CLRS формулює це як теорему 3.1:
`f(n) = Θ(g(n))` тоді й лише тоді, коли одночасно `f(n) = O(g(n))` і `f(n) = Ω(g(n))`. На практиці так і доводять `Θ`:
окремо верхню межу, окремо нижню.

Приклад: `3n² + 20n = Θ(n²)` зі сталими `c₁ = 3`, `c₂ = 4`, `n₀ = 20`. Ліва нерівність `3n² ≤ 3n² + 20n` правдива
завжди. Права `3n² + 20n ≤ 4n²` рівносильна `20n ≤ n²`, тобто `n ≥ 20`. Таблиця показує, як функція лягає між межами:

| `n` | `3n²` | `3n² + 20n` | `4n²` | Між межами? |
|-----|-------|-------------|-------|-------------|
| 10 | 300 | 500 | 400 | ні, вища за `4n²` |
| 20 | 1 200 | 1 600 | 1 600 | так, торкається верхньої |
| 40 | 4 800 | 5 600 | 6 400 | так |
| 100 | 30 000 | 32 000 | 40 000 | так |

При `n = 10` функція вища за верхню межу, і це дозволено: поріг `n₀ = 20` каже, що малі `n` не рахуються.

### Порівняння з числами

CLRS пропонує тримати в голові аналогію з порівнянням чисел `a` і `b`. Вона допомагає запам'ятати, але це лише
аналогія: функції порівнюють з точністю до сталого множника і лише для великих `n`.

| Запис | Як для чисел | Зміст |
|-------|--------------|-------|
| `f = O(g)` | `a ≤ b` | росте не швидше |
| `f = Ω(g)` | `a ≥ b` | росте не повільніше |
| `f = Θ(g)` | `a = b` | росте так само |
| `f = o(g)` | `a < b` | росте строго повільніше |
| `f = ω(g)` | `a > b` | росте строго швидше |

Два останні рядки — «мале o» і «мале омега». Вони означають, що відношення `f(n) / g(n)` прямує до нуля або до
нескінченності. Наприклад, `2n = o(n²)`, бо `2n / n² = 2/n` прямує до нуля, але `2n² ≠ o(n²)`, бо відношення дорівнює
2. Ці позначення трапляються в книжках рідше, і сьогодні досить їх упізнавати.

Одна властивість чисел на функції не переноситься: будь-які два числа можна порівняти, а дві функції — не завжди. CLRS
наводить приклад `n` і `n^(1 + sin n)`: показник другої функції коливається між 0 і 2, тож вона то обганяє `n`, то
відстає від неї, і жодне з `O` чи `Ω` не виконується. Для часу роботи справжніх алгоритмів такі функції майже не
трапляються.

## Випадок і межа — дві різні осі

Найпоширеніша плутанина — вважати, що `O` означає найгірший випадок, `Ω` — найкращий, а `Θ` — середній. Це не так.
Випадок відповідає на запитання «**на якому вході**»: на найгіршому, найкращому чи на типовому. Позначення відповідає
на запитання «**наскільки точно** ми знаємо кількість кроків на цьому вході»: зверху, знизу чи з обох боків. Ці
запитання незалежні, і будь-яке позначення можна вжити для будь-якого випадку.

Для сортування вставками CLRS наводить такі правильні й неправильні твердження:

| Твердження | Правильне? | Чому |
|------------|------------|------|
| Найгірший час — `Θ(n²)` | так | найточніше з правильних |
| Найгірший час — `O(n²)` або `Ω(n²)` | так | правдиві, але кожне каже лише половину |
| Найкращий час — `Θ(n)` | так | на відсортованому масиві |
| Час роботи — `O(n²)` | так | на будь-якому вході не більше за квадратичний |
| Час роботи — `Ω(n)` | так | на будь-якому вході не менше за лінійний |
| Час роботи — `Θ(n²)` | **ні** | на відсортованому масиві час лінійний, а не квадратичний |
| Час роботи — `Θ(n)` | **ні** | на зворотному масиві час квадратичний |

Фраза «час роботи» без слова «випадок» означає твердження про **всі** входи. Тому про сортування вставками без
уточнення можна сказати лише `O(n²)` і `Ω(n)`. Про сортування злиттям, яке план розбирає у фазі 1, можна сказати
просто «`Θ(n lg n)`», бо воно працює однаково на всіх входах.

### Як доводять `Θ(n²)` для найгіршого випадку без сум

CLRS у розділі 3.1 повертається до сортування вставками і доводить оцінку найгіршого випадку двома простими
міркуваннями, не рахуючи точних сум.

**Верхня межа.** Зовнішній цикл робить `n − 1` проходів. Внутрішній на кожному проході робить не більше `i − 1 < n`
кроків. Отже, кроків внутрішнього циклу не більше `(n − 1)(n − 1) < n²`, і час `O(n²)` на будь-якому вході.

**Нижня межа.** Поділимо масив на три третини і візьмемо вхід, у якому найбільші `n/3` значень стоять у першій
третині. Після сортування кожне з них мусить опинитися в останній третині. Сортування вставками переносить значення
праворуч лише зсувами на одну позицію, тому кожне з цих `n/3` значень пройде через усі `n/3` позицій середньої
третини. Це щонайменше `(n/3) · (n/3) = n²/9` зсувів, тобто `Ω(n²)` для цього входу.

Обидві межі разом дають найгірший час `Θ(n²)`. Зверніть увагу, що нижня межа найгіршого випадку потребує лише
**одного** поганого входу для кожного великого `n`, а верхня межа мусить виконуватися для **всіх** входів.

## Як говорять на співбесіді

Книжка Beyond Cracking the Coding Interview прямо попереджає: на співбесідах і в більшості коду слово «`O`» вживають у
значенні точної оцінки найгіршого випадку. Коли кажуть «пошук у масиві — це `O(n)`», мають на увазі «у найгіршому
випадку рівно лінійний», тобто `Θ(n)` для найгіршого випадку. Автори визнають, що з погляду підручника це неточність,
і пишуть, що так роблять усі.

Висновок для вас такий. Знайте різницю між `O`, `Ω` і `Θ`, бо без неї не прочитати CLRS і не довести нижню межу. На
співбесіді кажіть «`O`» так, як це прийнято, але називайте найменшу правдиву верхню межу: відповідь «сортування
вставками — `O(n³)`» формально правдива, але її сприймуть як помилку. Якщо найкращий і найгірший випадки різні,
назвіть обидва.

## Як спрощувати вираз до порядку росту

BCtCI зводить спрощення до двох правил.

**Правило 1. Відкиньте сталі доданки й сталі множники.** `3n + 5n + 32 = 8n + 32`, і після відкидання лишається `n`,
тобто `O(n)`. Від'ємні сталі теж відкидаються: `n − 1 = O(n)`. Множник `1/2` теж: `n/2 = O(n)`. Але показник степеня
не є множником: двійку в `n²` відкинути не можна, бо `n² = n · n`, а не `2 · n`.

**Правило 2. Відкиньте доданки, які ростуть повільніше за найшвидший.** `n² + n · (2n + 2) = 3n² + 2n`, і лишається
`n²`.

Щоб застосувати друге правило, треба знати, який доданок росте швидше. Ось порядок найчастіших класів, від повільного
до швидкого. Кожен наступний для великих `n` обганяє попередній, хоч би які сталі множники в нього були.

| Клас | Назва | Приклад алгоритму |
|------|-------|-------------------|
| `1` | сталий | взяти елемент масиву за номером |
| `log n` | логарифмічний | бінарний пошук |
| `√n` | корінь | перевірка, чи `n` просте, перебором дільників до `√n` |
| `n` | лінійний | знайти найбільше в масиві |
| `n log n` | лінійно-логарифмічний | сортування злиттям |
| `n²` | квадратичний | сортування вставками в найгіршому випадку |
| `n³` | кубічний | звичайне множення двох матриць `n × n` |
| `2ⁿ` | експоненційний | перебір усіх підмножин |
| `n!` | факторіальний | перебір усіх перестановок |

### Де прості правила обманюють

**Основа логарифма неважлива, а основа степеня важлива.** `log₂ n` і `log₁₀ n` відрізняються лише сталим множником:
`log₂ n = log₁₀ n / log₁₀ 2 ≈ 3,32 · log₁₀ n`. Тому пишуть просто `O(log n)`. А от `4ⁿ` і `2ⁿ` — різні класи, хоча
здається, що 4 — лише «сталий множник» більше за 2. Насправді `4ⁿ = (2ⁿ)²`, і відношення `4ⁿ / 2ⁿ = 2ⁿ` росте без меж:
1024 при `n = 10`, понад мільйон при `n = 20`, понад мільярд при `n = 30`. MCS називає цю пастку «експоненційним
фіаско».

**Не можна додавати `O(1)` як числа.** MCS наводить хибне доведення того, що `1 + 2 + … + n = O(n)`: «кожне число `i`
— стала, отже `O(1)`, а `n` доданків по `O(1)` дають `O(n)`». Помилка в тому, що `i` тут не стала: воно пробігає
значення аж до `n`, тобто залежить від `n`. Насправді сума дорівнює `n(n + 1) / 2`, і це `Θ(n²)`. Правило звідси:
`O(1)` означає «обмежене числом, яке не залежить від `n`», і кожен доданок треба перевіряти саме на це.

**Знак `=` у записі `f = O(g)` не є рівністю.** CLRS означує `O(g(n))` як **множину** функцій, а запис `f(n) =
O(g(n))` означає «`f` належить цій множині». Тому читати його можна лише зліва направо. MCS показує, до чого веде
читання справа наліво: «`2n = O(n)` і `n = O(n)`, отже `n = O(n) = 2n`, отже `n = 2n`». Ніколи не пишіть `O(…) = f`.

**Кілька змінних не зливаються в одну.** Якщо функція отримує два масиви довжин `a` і `b`, час `O(a + b)` не можна
спростити до `O(a)`, бо невідомо, який масив більший. BCtCI радить давати змінним імена за змістом: не `n` і `m`, які
легко переплутати, а `n1` і `n2` або `rows` і `cols`. Окрема пастка — квадратна матриця `n × n`: обхід усіх клітинок
робить `n²` кроків, і назвати його «лінійним» правильно лише щодо розміру матриці, а не щодо `n`.

## Як читати цикли

Більшість оцінок для ітеративного коду складається з кількох прийомів. Нижче кожен показано на числах, які порахувала
програма.

**Послідовні цикли додаються.** Якщо один цикл іде по масиву, а після нього другий іде по тому самому масиву, разом `n
+ n = 2n`, тобто `Θ(n)`. Два проходи не дають квадрата.

**Вкладені цикли множаться, якщо внутрішній не залежить від зовнішнього.** Цикл по `n` усередині циклу по `n` дає
`n²`.

**Якщо внутрішній залежить від зовнішнього, рахуйте суму.** Внутрішній цикл від `i + 1` до `n` робить `n − 1`, потім
`n − 2` і так далі кроків. Разом `n(n − 1) / 2`, тобто вдвічі менше за `n²`, але порядок той самий, `Θ(n²)`.

**Цикл, який множить або ділить лічильник, логарифмічний.** Цикл `for (let i = 1; i < 1000; i *= 2)` робить 10
проходів: `i` пробігає 1, 2, 4, …, 512. Кількість проходів — це скільки разів треба подвоїти 1, щоб дійти до `n`,
тобто близько `log₂ n`.

**Спадна геометрична сума обмежена першим доданком.** BCtCI розбирає цикл, де зовнішній лічильник щоразу ділиться
навпіл, а внутрішній цикл робить стільки кроків, скільки зараз зовнішній лічильник. Для `n = 1000` програма
порахувала: зовнішніх проходів 10, а внутрішніх кроків разом `1000 + 500 + 250 + … + 1 = 1994`. Для мільйона — 20
зовнішніх проходів і 1 999 993 внутрішніх кроки. Сума `n + n/2 + n/4 + …` ніколи не досягає `2n`, тому весь алгоритм
лінійний, хоча зовнішній цикл логарифмічний, а внутрішній на першому проході лінійний.

**Вбудовані методи теж мають ціну.** Саме цей прийом зламав функцію з початку лекції. У JavaScript метод `includes`,
`indexOf`, `slice`, розгортання `[...xs]` і `join` перебирають масив, тобто кожен виклик коштує до `n` кроків. Один
такий виклик усередині циклу по `n` робить код квадратичним. BCtCI називає звичку рахувати лише видимі цикли
небезпечною: за словами книжки, вона дає правильну відповідь приблизно так само часто, як хибну.

**Ранній вихід змінює випадок, а не межу.** Функція, яка шукає в масиві від'ємне число і повертає `true` при першій
знахідці, у найкращому випадку робить один крок, а в найгіршому, коли від'ємних немає, — `n` кроків. Її найгірший час
`Θ(n)`, найкращий `Θ(1)`.

### Пам'ять

Ті самі позначення описують і пам'ять. BCtCI розрізняє пам'ять вхідних даних, яка існувала до виклику функції, і
**додаткову пам'ять**, яку функція виділяє сама. Коли на співбесіді питають про пам'ять, мають на увазі додаткову.
Обидві функції `dedupe` з початку лекції потребують `Θ(n)` додаткової пам'яті на масив результату, а версія з `Set` ще
стільки ж на множину. Сортування вставками сортує на місці і потребує `Θ(1)` додаткової пам'яті: кількох змінних,
незалежно від `n`.

## Скільки триватиме обчислення

Порядок росту дозволяє оцінити час на більшому вході за одним виміром. Нехай алгоритм `Θ(n²)` обробляє 10 000
елементів за 2 секунди. Скільки він працюватиме на 40 000? Вхід зріс учетверо, отже кількість кроків зросте приблизно
в `4² = 16` разів, і час буде близько 32 секунд. Для алгоритму `Θ(n log n)` вхід учетверо більший дав би трохи більше
ніж учетверо довший час.

Ця оцінка наближена з двох причин. Перша: `Θ` гарантує лише, що функція лежить між `c₁ · g` і `c₂ · g`, тож відношення
часів може відхилятися від 16. MCS у виносці підкреслює, що відношення точно наближається до очікуваного лише тоді,
коли відношення `f / g` прямує до сталої. Друга: справжній комп'ютер не є моделлю RAM, і великий вхід може не
вміститися в кеш процесора, про що день 7. Але для рішення «чи встигне програма» такої оцінки зазвичай досить.

## Типові хибні уявлення

**«`O(n²)` означає, що алгоритм квадратичний».** `O` дає лише верхню межу. Лінійний алгоритм теж є `O(n²)`. Щоб
сказати «рівно квадратичний», потрібне `Θ(n²)`.

**«Алгоритм `O(n log n)` швидший за алгоритм `O(n²)`».** CLRS відповідає: можливо, а можливо, ні. Якщо другий
насправді `Θ(n)`, він швидший. Порівнювати можна лише точні оцінки, а навіть точні оцінки обіцяють перевагу лише для
досить великих `n`.

**«`O` — це найгірший випадок, `Ω` — найкращий».** Випадок і межа — незалежні речі. Найгірший випадок можна оцінити і
зверху, і знизу.

**«`O(1)` — це швидко».** `O(1)` означає лише, що час не залежить від `n`. Стала може бути великою: операція, яка
завжди робить мільйон кроків, — теж `O(1)`, і для масиву з десяти елементів вона повільніша за лінійний прохід.

**«Асимптотично швидший алгоритм завжди кращий».** MCS наводить множення матриць: існує спосіб, який робить близько
`n^2,55` операцій замість звичайних `n³`, але на практиці його майже не використовують, бо він виграє лише на матрицях
непрактичного розміру. Асимптотика порівнює алгоритми на великих входах, а які входи великі для вас, вирішують дані.

**«Один цикл — лінійний час».** Цикл з `includes` усередині квадратичний. Рахуйте кроки, а не цикли.

## Перевірте себе

**1. Чи правдиве `2n + 10 = O(n²)`? А `2n + 10 = Θ(n²)`?**

<details><summary>Відповідь</summary>

Перше правдиве: `2n + 10 ≤ 12 · n²` для всіх `n ≥ 1`, бо `2n ≤ 2n²` і `10 ≤ 10n²`. Отже, `c = 12`, `n₀ = 1`. Друге
хибне: `Θ(n²)` вимагає ще й нижньої межі `c · n² ≤ 2n + 10`, а після ділення на `n²` ліва частина стала, тоді як
права, `2/n + 10/n²`, прямує до нуля. Для будь-якого додатного `c` нерівність порушиться при великому `n`.

</details>

**2. Знайдіть сталі `c` і `n₀`, які доводять `5n² + 40n = O(n²)`.**

<details><summary>Відповідь</summary>

Ділимо на `n²`: `5 + 40/n ≤ c`. Ліва частина спадає з ростом `n`. При `n₀ = 1` вона дорівнює 45, отже підходить `c =
45`. При `n₀ = 40` вона дорівнює 6, отже підходить `c = 6`. Обидві пари правильні, бо означення вимагає лише, щоб
існувала одна.

</details>

**3. Колега пише в документації: «Сортування вставками працює за `Θ(n²)`». Що не так і як виправити?**

<details><summary>Відповідь</summary>

Без слова «випадок» твердження стосується всіх входів, а на відсортованому масиві сортування вставками робить `n − 1`
порівнянь, тобто працює за `Θ(n)`. Правильно: «у найгіршому випадку `Θ(n²)`, у найкращому `Θ(n)`», або для всіх входів
одразу: «`O(n²)`».

</details>

**4. Чи правдиве `4ⁿ = O(2ⁿ)`? А `log₄ n = O(log₂ n)`?**

<details><summary>Відповідь</summary>

Перше хибне. `4ⁿ / 2ⁿ = 2ⁿ`, і це відношення росте без меж, тож жодне стале `c` не підходить. Друге правдиве: `log₄ n
= log₂ n / log₂ 4 = log₂ n / 2`, тобто це той самий логарифм, помножений на `1/2`. Основа логарифма дає лише сталий
множник, а основа степеня змінює клас.

</details>

**5. Який найгірший час у цієї функції?**

```ts
function countCommon(a: readonly number[], b: readonly number[]): number {
  let count = 0;
  for (const x of a) {
    if (b.includes(x)) count++;
  }
  return count;
}
```

<details><summary>Відповідь</summary>

Позначимо довжину `a` через `na`, а довжину `b` через `nb`. Цикл робить `na` проходів, а `includes` у кожному
переглядає до `nb` елементів. У найгіршому випадку, коли спільних елементів немає, виходить `na · nb` перевірок, тобто
`Θ(na · nb)`. Спростити до `Θ(n²)` не можна, доки невідомо, як пов'язані довжини. Якщо вони однакові й дорівнюють `n`,
тоді `Θ(n²)`.

</details>

**6. Алгоритм `Θ(n²)` обробляє 10 000 записів за 2 секунди. Скільки приблизно він працюватиме на 30 000 записів? А
алгоритм `Θ(n³)`, який на 10 000 записів теж працює 2 секунди?**

<details><summary>Відповідь</summary>

Вхід зріс утричі. Для `Θ(n²)` кроків стане приблизно в `3² = 9` разів більше, тобто близько 18 секунд. Для `Θ(n³)` — у
`3³ = 27` разів більше, близько 54 секунд. Обидві оцінки наближені: `Θ` не фіксує сталих точно, і на великих даних
може вплинути пам'ять.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| асимптотика | поведінка функції, коли її аргумент `n` росте необмежено |
| порядок росту | клас функції після відкидання сталих множників і молодших доданків |
| `O(g)`, «о велике» | множина функцій, які після деякого порогу не більші за `c · g` для деякої сталої `c`: верхня межа |
| `Ω(g)`, «омега велике» | множина функцій, які після порогу не менші за `c · g`: нижня межа |
| `Θ(g)`, «тета» | множина функцій, затиснутих між `c₁ · g` і `c₂ · g`: точна оцінка |
| `o(g)`, `ω(g)` | «мале о» і «мале омега»: функція росте строго повільніше або строго швидше за `g` |
| поріг `n₀` | число, починаючи з якого нерівність мусить виконуватися |
| стала | число, яке не залежить від `n` |
| молодший доданок | доданок, який росте повільніше за старший |
| точна межа | межа, яка відрізняється від функції не більше ніж у сталу кількість разів, тобто `Θ` |
| випадок | вибір входу, для якого рахують кроки: найгірший, найкращий, середній |
| медіана | середнє за порядком значення серед вимірів |
| додаткова пам'ять | пам'ять, яку функція виділяє сама, без пам'яті вхідних даних |
| логарифмічний, лінійний, квадратичний, експоненційний | класи `log n`, `n`, `n²`, `2ⁿ` |
| `Set` | вбудована множина JavaScript: зберігає значення без повторів і швидко перевіряє наявність |
| `includes` | метод масиву JavaScript, який перебирає елементи, поки не знайде шукане |
