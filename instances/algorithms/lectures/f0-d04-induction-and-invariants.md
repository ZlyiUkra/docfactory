# Лекція. День 4. Доказ індукцією й інваріант циклу

Ця лекція вчить доводити, що алгоритм правильний для всіх входів, а не лише для тих, що потрапили в тести. Читання
займе близько 60 хвилин. Під кожним прикладом коду стоїть справжній вивід, який програма надрукувала в Node 24.22, а
тести запускалися у Vitest 5.1.

У лекції дня 1 ви бачили твердження, яке лишається правдивим на кожному проході циклу селянського множення, і
обіцянку, що день 4 покаже, як доводити такі твердження строго. Сьогодні ця обіцянка виконується. Інструмент один, і
він має дві назви: коли доводять твердження про всі натуральні числа, його називають **індукцією**, а коли доводять
правильність циклу — **інваріантом циклу**.

**Після лекції ви зможете пояснити:**

- чому тести не доводять правильності, а доведення доводить;
- з яких двох частин складається доведення індукцією і чому без будь-якої з них воно нічого не варте;
- чим звичайна індукція відрізняється від сильної і чому ця різниця лише в зручності;
- що таке інваріант циклу і які три речі про нього треба показати;
- як довести, що цикл узагалі закінчиться;
- як перевіряти інваріант у коді під час тестів, не сповільнюючи звичайну роботу.

## Пошук, який зависав

Розробник пише функцію пошуку в упорядкованому масиві. Функція повертає першу позицію, де значення не менше за
`target`. Ідея відома: дивимося на середній елемент і відкидаємо половину масиву, у якій відповіді точно немає. Цей
прийом називається **бінарним пошуком**, і план розбирає його у фазі 1. Ось перша версія, до якої розробник додав
лічильник кроків, щоб функція не зависла назавжди:

```ts
// Перша позиція в упорядкованому масиві, де значення не менше за target.
// У функції є помилка; лічильник кроків не дає їй зависнути назавжди.
function firstAtLeastBroken(xs: readonly number[], target: number): number | string {
  let lo = 0;
  let hi = xs.length;
  let steps = 0;
  while (lo < hi) {
    if (++steps > 100) return `зависла: lo = ${lo}, hi = ${hi}`;
    const mid = Math.floor((lo + hi) / 2);
    if (xs[mid]! < target) lo = mid;
    else hi = mid;
  }
  return lo;
}

const xs = [10, 20, 30, 40, 50, 60, 70, 80];
for (const target of [10, 30, 50, 15, 85]) {
  console.log(`target = ${target}: ${firstAtLeastBroken(xs, target)}`);
}
```

Знак оклику в `xs[mid]!` каже TypeScript: «я знаю, що елемент існує». Без нього налаштування
`noUncheckedIndexedAccess` вважало б, що `xs[mid]` може бути `undefined`.

Вивід:

```
target = 10: 0
target = 30: зависла: lo = 1, hi = 2
target = 50: зависла: lo = 3, hi = 4
target = 15: зависла: lo = 0, hi = 1
target = 85: зависла: lo = 7, hi = 8
```

Розробник перевірив функцію на першому елементі масиву і на порожньому масиві. Обидва тести пройшли, бо в обох
випадках гілка `lo = mid` не виконується жодного разу. На всіх інших входах функція зависає, і завжди тоді, коли `hi`
більше за `lo` рівно на одиницю.

Чому саме так, ви зможете пояснити наприкінці лекції, і пояснення займе три рядки. Воно спирається на ту частину
доведення, про яку найчастіше забувають. Спершу треба зрозуміти, як доведення взагалі влаштоване.

## Чому тести не доводять

Тест перевіряє один вхід. Входів у будь-якої цікавої задачі нескінченно багато, а тестів скінченна кількість. Тому
скільки б тестів не пройшло, лишаються входи, яких ніхто не перевіряв. Пошук вище пройшов два тести і зламався на всіх
інших входах.

Доведення — це міркування, яке однаково годиться для **кожного** входу. Курс MIT 6.006 пояснює, чому для алгоритмів
доведення майже завжди індукційне: програма має скінченний розмір, а входи як завгодно великі. Тому алгоритм, який
обробляє великі входи, мусить містити цикл або рекурсію, а про цикл і рекурсію міркують індукцією.

Тести від цього не стають марними. Вони ловлять помилки в записі алгоритму: одруківки, плутанину з номерами, забуту
гілку. Доведення каже, що алгоритм правильний, а тести перевіряють, що код відповідає алгоритму.

## Індукція

### Черга по цукерки

MCS пояснює індукцію такою історією. Професорка приносить на лекцію мішок цукерок, ставить студентів у чергу і
оголошує два правила:

1. перший у черзі отримує цукерку;
2. якщо студент отримав цукерку, то наступний за ним теж отримує цукерку.

Чи отримає цукерку сімнадцятий студент? Перший отримує за першим правилом. Тоді другий отримує за другим правилом,
застосованим до першого. Третій — за другим правилом, застосованим до другого. Після шістнадцяти застосувань другого
правила цукерку отримує сімнадцятий. Те саме міркування доходить до будь-якого студента, хоч би як далеко він стояв.

Тепер замінимо «студент з номером `n` отримав цукерку» на будь-яке твердження `P(n)` про число `n`. **Принцип
індукції** каже: якщо `P(0)` правдиве, і для кожного `n` з `P(n)` випливає `P(n + 1)`, то `P(n)` правдиве для всіх
`n`.

Доведення індукцією складається з двох частин:

- **база**: показати, що `P(0)` правдиве (або `P(1)`, якщо твердження про числа від одиниці);
- **крок індукції**: узяти довільне `n`, **припустити**, що `P(n)` правдиве, і вивести з цього `P(n + 1)`.

Припущення в кроці називають **гіпотезою індукції**. Воно не є коловим міркуванням: ми не припускаємо того, що
доводимо. Ми доводимо умовне твердження «якщо `P(n)`, то `P(n + 1)`», а перший ланцюжок у цьому ряду запускає база.

### Приклад: сума степенів двійки

Доведемо, що для кожного `k ≥ 0`

```
1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1
```

Ця формула знадобиться в день 8, коли динамічний масив копіюватиме елементи щоразу, як подвоюється. Спершу перевіримо
її на малих `k`, щоб побачити, що саме доводимо:

| `k` | Сума | `2ᵏ⁺¹ − 1` |
|-----|------|------------|
| 0 | 1 | 1 |
| 1 | 1 + 2 = 3 | 3 |
| 2 | 3 + 4 = 7 | 7 |
| 3 | 7 + 8 = 15 | 15 |
| 4 | 15 + 16 = 31 | 31 |

Таблиця переконує, але не доводить: вона перевірила п'ять значень `k`, а їх нескінченно багато. Ось доведення.

**Твердження `P(k)`:** `1 + 2 + … + 2ᵏ = 2ᵏ⁺¹ − 1`.

**База, `k = 0`.** Ліва частина — один доданок `2⁰ = 1`. Права — `2¹ − 1 = 1`. Рівні.

**Крок.** Візьмемо довільне `k ≥ 0` і припустимо, що `P(k)` правдиве. Сума для `k + 1` — це сума для `k` плюс ще один
доданок `2ᵏ⁺¹`. За гіпотезою індукції сума для `k` дорівнює `2ᵏ⁺¹ − 1`. Отже:

```
1 + 2 + … + 2ᵏ + 2ᵏ⁺¹ = (2ᵏ⁺¹ − 1) + 2ᵏ⁺¹ = 2 · 2ᵏ⁺¹ − 1 = 2ᵏ⁺² − 1
```

Це і є `P(k + 1)`. За принципом індукції `P(k)` правдиве для всіх `k ≥ 0`.

Подивіться, як працює крок. Сума для `k + 1` містить у собі суму для `k`. Гіпотеза дозволяє замінити цю меншу суму
готовою відповіддю, а решта — алгебра. Майже кожен крок індукції влаштований так: велику задачу розбивають на меншу
задачу того самого виду і невеликий залишок.

### Шаблон доведення

MCS радить записувати кожне доведення індукцією за одним шаблоном з п'яти частин:

1. сказати, що доведення ведеться індукцією;
2. явно записати твердження `P(n)`, яке доводиться, тобто гіпотезу індукції;
3. довести базу;
4. довести крок: припустити `P(n)` для довільного `n` і вивести `P(n + 1)`;
5. зробити висновок, що `P(n)` правдиве для всіх `n`.

Друга частина найважливіша. MCS пише, що незаписана гіпотеза — найчастіша причина заплутаних доведень у студентів.
Якщо ви не можете записати `P(n)` одним реченням, ви ще не знаєте, що доводите.

### Що буває, коли крок не працює для всіх `n`

MCS наводить навмисно хибне «доведення», що всі коні однієї масті. Твердження `P(n)`: у будь-якій групі з `n` коней
усі коні однієї масті. База `n = 1` правдива: один кінь однієї масті сам із собою. Крок: візьмемо групу з `n + 1`
коня. Перші `n` коней однієї масті за гіпотезою, останні `n` теж. Обидві підгрупи мають спільних коней посередині,
тому всі `n + 1` однієї масті.

Висновок хибний, отже, у доведенні є помилка. Вона в кроці від `n = 1` до `n = 2`. Група з двох коней ділиться на
підгрупи «перший кінь» і «другий кінь», і в цих підгрупах немає спільного коня. Крок працює для `n ≥ 2`, але не для `n
= 1`, і ланцюжок рветься на першій же ланці. Звідси правило: крок мусить працювати для **кожного** `n`, починаючи з
бази. Перевіряйте найменші `n` окремо.

### Сильна індукція

Інколи для доведення `P(n)` недостатньо знати `P(n − 1)`, а потрібне твердження для якогось іншого меншого числа.
**Сильна індукція** дозволяє в кроці припустити, що твердження правдиве для **всіх** менших чисел, а не лише для
попереднього. Erickson записує кожне доведення саме так: «нехай `n` — довільне число; припустимо, що `P(k)` правдиве
для всіх `k < n`; доведемо `P(n)`». Тоді база — це ті випадки, у яких доводять `P(n)`, не спираючись на припущення.

Приклад. Скільки цифр у двійковому записі числа `n`? Рекурсивна функція відповідає так: якщо `n = 1`, одна цифра;
інакше відкинемо останню цифру, тобто поділимо `n` навпіл з округленням униз, і додамо одиницю.

```ts
// Скільки двійкових цифр у записі додатного цілого n.
function bits(n: number): number {
  if (n === 1) return 1;                       // базовий випадок: запис "1"
  return 1 + bits(Math.floor(n / 2));          // відкидаємо останню цифру
}
```

Твердження: `bits(n) = ⌊log₂ n⌋ + 1` для кожного `n ≥ 1`. Звичайна індукція тут незручна: `bits(n)` спирається на
`bits(⌊n/2⌋)`, а не на `bits(n − 1)`. Тому беремо сильну.

**Доведення.** Нехай `n ≥ 1` довільне, і припустимо, що `bits(k) = ⌊log₂ k⌋ + 1` для всіх `1 ≤ k < n`.

- **Якщо `n = 1`**, функція повертає 1, а `⌊log₂ 1⌋ + 1 = 0 + 1 = 1`.
- **Якщо `n ≥ 2`**, то `1 ≤ ⌊n/2⌋ < n`, тому гіпотеза годиться для `k = ⌊n/2⌋`, і `bits(n) = 2 + ⌊log₂ ⌊n/2⌋⌋`.
  Лишилося показати, що `⌊log₂ ⌊n/2⌋⌋ = ⌊log₂ n⌋ − 1`. Для парного `n` маємо `⌊n/2⌋ = n/2` і `log₂(n/2) = log₂ n − 1`.
  Для непарного `n` маємо `⌊n/2⌋ = (n − 1)/2`, а непарне `n ≥ 3` не є степенем двійки, тому між `n − 1` і `n` немає
  жодного степеня двійки, і `⌊log₂(n − 1)⌋ = ⌊log₂ n⌋`.

В обох випадках `bits(n) = ⌊log₂ n⌋ + 1`. Це теорема 9 з конспекту Erickson про індукцію, і саме ця формула стоїть за
поправкою з розбору читання дня 1: двійковий пошук у масиві зі 128 елементів робить до `⌊log₂ 128⌋ + 1 = 8` перевірок.

Програма звірила обидві частини рівності:

```
розбіжностей серед n від 1 до 1 000 000: 0
bits(1) = 1, bits(2) = 2, bits(3) = 2, bits(4) = 3, bits(7) = 3, bits(8) = 4, bits(1000) = 10
```

Мільйон збігів — це добра перевірка, що формулу записано без одруківки. Доведенням вона не є: доведення вище накриває
і мільйон перший випадок, і всі наступні.

**Сильна індукція не сильніша.** MCS показує, що будь-яке доведення сильною індукцією механічно переписується на
звичайну: досить узяти за `Q(n)` твердження «`P(k)` для всіх `k ≤ n`». Erickson іде далі й радить узагалі не
розрізняти види індукції. Різниця лише в тому, що сильна індукція чесно каже читачеві, на які менші випадки спирається
крок.

### Індукція і рекурсія — те саме

Порівняйте функцію `bits` і доведення її правильності.

| Функція | Доведення |
|---------|-----------|
| базовий випадок `n === 1` повертає відповідь без рекурсії | база доводиться без гіпотези |
| рекурсивний виклик `bits(⌊n/2⌋)` для меншого аргументу | гіпотеза індукції для меншого `k` |
| з відповіді на меншу задачу збирається відповідь на більшу | з `P(k)` виводиться `P(n)` |
| рекурсія закінчується, бо аргумент зменшується до 1 | індукція спирається на те, що менші числа колись дійдуть до бази |

Erickson пише, що добре написане доведення індукцією дуже схоже на добре написану рекурсивну програму, і програмістам
вигідно тримати в голові один шаблон замість двох. Завтрашня лекція про рекурсію спирається саме на цю схожість.

## Інваріант циклу

Цикл — це та сама рекурсія, записана інакше: кожен прохід розв'язує задачу на крок далі. Тому і правильність циклу
доводять індукцією, де `n` — номер проходу. Твердження, яке доводять, CLRS називає **інваріантом циклу**: це
твердження про змінні, правдиве перед кожною перевіркою умови циклу.

Щоб інваріант доводив правильність, треба показати три речі.

| Частина | Що показати | Відповідник в індукції |
|---------|-------------|------------------------|
| **Ініціалізація** | інваріант правдивий перед першим проходом | база |
| **Збереження** | якщо інваріант правдивий перед проходом, то правдивий і після нього | крок |
| **Завершення** | цикл закінчується, і інваріант разом з умовою виходу дає потрібну відповідь | висновок |

Третя частина складається з двох окремих запитань. Перше: **чи закінчиться** цикл? Для циклу `for i = 1 to n`
відповідь очевидна, бо `i` росте до `n`. Для циклу `while` очевидної відповіді немає, і її треба довести. Друге: **що
каже** інваріант у момент виходу? Ця частина пов'язує інваріант з відповіддю.

Щоб довести, що цикл `while` закінчиться, шукають **міру прогресу**: ціле число, яке не може бути від'ємним і строго
зменшується на кожному проході. Невід'ємне ціле число не може зменшуватися вічно, тому проходів скінченна кількість.
Для циклу з лічильником, що зростає до `n`, міра — `n − i`.

### Приклад 1: селянське множення

Повернімося до функції з лекції дня 1. Вона перемножує невід'ємні цілі `x₀` і `y₀`; змінні `x` і `y` починають з цих
значень і змінюються на кожному проході.

```ts
export function peasantMultiply(x: number, y: number): number {
  let prod = 0;
  while (x > 0) {
    if (x % 2 === 1) {
      prod = prod + y;
    }
    x = Math.floor(x / 2);
    y = y + y;
  }
  return prod;
}
```

**Інваріант:** перед кожною перевіркою умови `x > 0` правдиве `prod + x · y = x₀ · y₀`.

**Ініціалізація.** Перед першою перевіркою `prod = 0`, `x = x₀`, `y = y₀`. Тоді `0 + x₀ · y₀ = x₀ · y₀`.

**Збереження.** Нехай перед проходом `prod + x · y = x₀ · y₀`. Позначимо нові значення змінних штрихом.

- Якщо `x` парне, то `x = 2 · ⌊x/2⌋`. Прохід робить `prod′ = prod`, `x′ = ⌊x/2⌋`, `y′ = 2y`. Тоді `prod′ + x′ · y′ =
  prod + ⌊x/2⌋ · 2y = prod + x · y = x₀ · y₀`.
- Якщо `x` непарне, то `x = 2 · ⌊x/2⌋ + 1`. Прохід робить `prod′ = prod + y`, `x′ = ⌊x/2⌋`, `y′ = 2y`. Тоді `prod′ +
  x′ · y′ = prod + y + ⌊x/2⌋ · 2y = prod + (2 · ⌊x/2⌋ + 1) · y = prod + x · y = x₀ · y₀`.

В обох випадках інваріант правдивий і після проходу.

**Завершення.** Міра прогресу — саме `x`. Воно ціле, невід'ємне, і на кожному проході, де `x > 0`, строго зменшується,
бо `⌊x/2⌋ < x`. Отже, цикл закінчиться. У момент виходу умова `x > 0` хибна, тобто `x = 0`. Інваріант тоді каже `prod
+ 0 · y = x₀ · y₀`, тобто `prod = x₀ · y₀`. Функція повертає `prod`, отже, повертає правильну відповідь.

Зверніть увагу, що ініціалізацію перевіряли на конкретних початкових значеннях, а збереження — для **довільного**
проходу, не дивлячись, який він за ліком. Саме тому доведення годиться для будь-яких `x₀` і `y₀`.

### Приклад 2: алгоритм Евкліда

**Найбільший спільний дільник** двох чисел, скорочено НСД, — найбільше число, на яке діляться обидва без остачі.
Наприклад, НСД(12, 18) = 6. Алгоритм Евкліда, відомий понад дві тисячі років, знаходить його так: поки друге число не
нуль, замінити пару `(a, b)` парою `(b, a mod b)`, де `a mod b` — остача від ділення `a` на `b`. Коли друге число
стало нулем, перше і є відповіддю.

Ось хід алгоритму для пари `(1071, 462)`:

```ts
let a = 1071;
let b = 462;
console.log(`a = ${a}, b = ${b}`);
while (b !== 0) {
  [a, b] = [b, a % b];
  console.log(`a = ${a}, b = ${b}`);
}
console.log(`НСД = ${a}`);
```

Запис `[a, b] = [b, a % b]` — **деструктуроване присвоєння**: праворуч створюється масив із двох нових значень,
обчислених зі старих `a` і `b`, а потім його елементи записуються в `a` і `b`. Тому обидві змінні отримують нові
значення одночасно, і жодне старе значення не губиться.

Вивід:

```
a = 1071, b = 462
a = 462, b = 147
a = 147, b = 21
a = 21, b = 0
НСД = 21
```

Перевірка: `1071 = 21 · 51` і `462 = 21 · 22`, а числа 51 і 22 спільних дільників, крім 1, не мають.

Доведення спирається на один факт: **НСД(a, b) = НСД(b, a mod b)** для `b > 0`. Чому так? Нехай `a = q · b + r`, де `r
= a mod b`. Якщо число `d` ділить і `a`, і `b`, то воно ділить і `r = a − q · b`. Навпаки, якщо `d` ділить `b` і `r`,
то воно ділить і `a = q · b + r`. Отже, спільні дільники пари `(a, b)` і пари `(b, r)` — ті самі числа, а значить, і
найбільший з них той самий.

**Інваріант:** перед кожною перевіркою умови `b !== 0` правдиве `НСД(a, b) = НСД(a₀, b₀)`.

**Ініціалізація.** На початку `a = a₀`, `b = b₀`, і рівність очевидна.

**Збереження.** Прохід замінює `(a, b)` на `(b, a mod b)`, а за фактом вище НСД від цього не змінюється.

**Завершення.** Міра прогресу — `b`. Воно ціле й невід'ємне, бо остача від ділення невід'ємна. На кожному проході нове
`b` дорівнює `a mod b`, а остача завжди менша за дільник, тому `b` строго зменшується. Отже, цикл закінчиться. У
момент виходу `b = 0`, і інваріант каже `НСД(a, 0) = НСД(a₀, b₀)`. Найбільше число, яке ділить `a` і 0, — це саме `a`,
бо 0 ділиться на будь-яке число. Отже, функція повертає НСД(a₀, b₀).

### Приклад 3: сортування вставками

CLRS доводить правильність сортування вставками тим самим способом, і розбір читання дня 2 переказує це доведення
таблицею. Інваріант зовнішнього циклу: перед проходом з номером `i` частина масиву від першого елемента до елемента `i
− 1` складається з тих самих елементів, що стояли там на початку, але відсортованих.

Зверніть увагу на слова «з тих самих елементів». Без них інваріант був би неповним. Функція, яка просто записує в
масив числа `1, 2, 3, …`, теж дає відсортовану частину на кожному кроці, але це не сортування вхідного масиву. Обидві
половини інваріанта потрібні: «відсортовано» каже про порядок, «ті самі елементи» каже, що нічого не загубили і не
вигадали.

CLRS також чесно зауважує, що строге доведення збереження потребує окремого інваріанта для внутрішнього циклу `while`,
і книжка свідомо обмежується неформальним міркуванням. Сформулювати цей внутрішній інваріант — частина сьогоднішньої
практики.

## Чому пошук зависав

Тепер повернімося до функції з початку лекції. Запишемо для неї інваріант. Нехай масив `xs` упорядкований.

**Інваріант:** перед кожною перевіркою умови `lo < hi` усі позиції ліворуч від `lo` містять значення, менші за
`target`, а всі позиції від `hi` до кінця містять значення, не менші за `target`.

Ініціалізація правдива: на початку `lo = 0`, і ліворуч нічого немає, а `hi = xs.length`, і від `hi` до кінця теж
нічого немає. Збереження теж правдиве. Якщо `xs[mid] < target`, то через упорядкованість і всі позиції до `mid`
включно менші за `target`, тому присвоєння `lo = mid` нічого не порушує. Якщо `xs[mid] ≥ target`, то всі позиції від
`mid` не менші, і присвоєння `hi = mid` теж нічого не порушує.

Ламається третя частина: **завершення**. Природна міра прогресу тут — `hi − lo`, розмір ділянки, де ще може бути
відповідь. Коли `hi = lo + 1`, середина `mid = ⌊(2·lo + 1)/2⌋ = lo`. Якщо при цьому `xs[mid] < target`, присвоєння `lo
= mid` не змінює нічого, міра не зменшується, і цикл крутиться вічно. Саме це показав вивід: функція завжди зависала з
`hi = lo + 1`.

Інваріант не тільки пояснює помилку, а й підказує, де шукати виправлення: присвоєння в першій гілці мусить зсувати
`lo` так, щоб міра `hi − lo` зменшувалася на кожному проході, і при цьому інваріант лишався правдивим. Як саме, —
запитання 5 в кінці лекції, а повністю бінарний пошук план розбирає у фазі 1, день 3.

## Перевірка інваріанта в коді

Доведення пишуть на папері, але інваріант корисно перевіряти й у коді, під час тестів. Якщо одруківка порушить
інваріант, тест упаде саме в тому проході, де це сталося, з поясненням, яке твердження зламалося. Без перевірки тест
побачив би лише неправильну відповідь наприкінці.

Проблема в тому, що перевірка інваріанта буває дорогою. Для алгоритму Евкліда найпростіша перевірка рахує НСД
повільним перебором дільників, а це в багато разів довше за сам алгоритм. Тому перевірку вмикають лише в тестах.

```ts
// src/invariant.ts
// Перемикач дорогих перевірок. У звичайній роботі вимкнений, тест вмикає його сам.
export const checks = { enabled: false };

// Кидає помилку з поясненням, якщо умова хибна.
export function invariant(condition: boolean, message: string): asserts condition {
  if (!condition) {
    throw new Error(`Порушено інваріант: ${message}`);
  }
}
```

- `checks` — об'єкт з одним полем. Об'єкт, а не змінна, потрібен тому, що інший модуль може змінити поле імпортованого
  об'єкта, але не може переприсвоїти імпортовану змінну.
- `asserts condition` у типі результату — позначка TypeScript: після виклику `invariant(x !== undefined, …)`
  компілятор знає, що `x` не `undefined`, бо інакше функція кинула б помилку.

Ось алгоритм Евкліда з перевіркою:

```ts
// src/gcd.ts
import { checks, invariant } from "./invariant.ts";

// Повільний, але очевидно правильний НСД: перебирає дільники від більшого до меншого.
export function slowGcd(a: number, b: number): number {
  for (let d = Math.max(a, b); d > 1; d--) {
    if (a % d === 0 && b % d === 0) return d;
  }
  return Math.max(a, b) === 0 ? 0 : 1;
}

// Найбільший спільний дільник невід'ємних цілих a0 і b0 за алгоритмом Евкліда.
export function gcd(a0: number, b0: number): number {
  let a = a0;
  let b = b0;
  while (b !== 0) {
    if (checks.enabled) {
      invariant(slowGcd(a, b) === slowGcd(a0, b0), `НСД(${a}, ${b}) = НСД(${a0}, ${b0})`);
    }
    [a, b] = [b, a % b];
  }
  return a;
}
```

Чому перевірка стоїть усередині `if (checks.enabled)`, хоча можна було б перевіряти перемикач у самій функції
`invariant`? JavaScript обчислює аргументи **до** виклику функції. Якби `if` не було, обидва виклики `slowGcd`
виконувалися б на кожному проході завжди, а `invariant` лише вирішувала б, чи кидати помилку. Повільна частина
працювала б і в звичайній роботі.

Тест вмикає перевірку один раз перед усіма тестами файлу:

```ts
// src/gcd.test.ts
import { beforeAll, describe, expect, test } from "vitest";
import { checks } from "./invariant.ts";
import { gcd } from "./gcd.ts";

beforeAll(() => {
  checks.enabled = true;                       // у тестах інваріант перевіряється
});

describe("gcd", () => {
  test("приклад з таблиці", () => {
    expect(gcd(1071, 462)).toBe(21);
  });
  test("один з аргументів нуль", () => {
    expect(gcd(12, 0)).toBe(12);
    expect(gcd(0, 12)).toBe(12);
  });
  test("взаємно прості числа", () => {
    expect(gcd(35, 64)).toBe(1);
  });
});
```

`beforeAll` — функція Vitest, яка виконує передану їй функцію один раз перед першим тестом файлу. Вивід `npx vitest
run --reporter=verbose`:

```
 ✓ src/gcd.test.ts > gcd > приклад з таблиці 2ms
 ✓ src/gcd.test.ts > gcd > один з аргументів нуль 0ms
 ✓ src/gcd.test.ts > gcd > взаємно прості числа 0ms
 Test Files  1 passed (1)
      Tests  3 passed (3)
```

А тепер зробимо одруківку, яку легко зробити насправді: напишемо ділення `a / b` замість остачі `a % b`. Ввімкнемо
перевірку і викличемо `gcdWithTypo(1071, 462)`. Вивід:

```
Порушено інваріант: НСД(462, 2.3181818181818183) = НСД(1071, 462)
```

Повідомлення каже, що саме зламалося і на яких значеннях: після першого проходу друге число стало дробовим, і НСД
нової пари вже не дорівнює НСД початкової.

## Як це звучить на співбесіді

Доведень на співбесіді майже не просять, але інваріант допомагає саме там, де найчастіше помиляються: у бінарному
пошуку, двох вказівниках, ковзному вікні, розбитті масиву. Корисна звичка — перед тим як писати цикл, сказати вголос,
що правдиве на кожному проході.

| Ситуація | Що сказати |
|----------|-----------|
| починаєте цикл з двома межами | «Інваріант: усе ліворуч від `lo` менше за ціль, усе від `hi` — не менше. Відповідь між ними» |
| інтерв'юер питає, чому цикл закінчиться | «На кожному проході `hi − lo` строго зменшується, а воно не може бути від'ємним» |
| інтерв'юер питає, чому відповідь правильна | «Коли цикл закінчився, `lo = hi`, і інваріант каже, що `lo` — перша позиція, яка не менша за ціль» |
| питають про рекурсивну функцію | «Базовий випадок правильний. Якщо виклики для менших входів правильні, то з них правильно збирається відповідь» |

Така розмова показує, що ви не вгадуєте межі циклу методом спроб, а знаєте, чому вони саме такі.

## Типові хибні уявлення

**«Інваріант правдивий завжди».** Інваріант правдивий у певній точці: перед кожною перевіркою умови циклу. Усередині
проходу він може тимчасово порушуватися. У сортуванні вставками під час зсувів у масиві стоять дві копії одного
значення, а сам `key` лежить окремо, і лише рядок 8 знову робить масив перестановкою початкового.

**«База — формальність».** Без бази ланцюжок не має першої ланки. Крок «якщо `P(n)`, то `P(n + 1)`» буває правдивим
для хибного твердження: для твердження «`n = n + 1`» крок формально правильний, бо з `n = n + 1` випливає `n + 1 = n +
2`, але бази немає, і твердження хибне для всіх `n`.

**«Індукція — це перевірка багатьох випадків».** Індукція перевіряє лише базу, а все інше виводить міркуванням про
довільне `n`. Мільйон перевірених значень `bits(n)` — це тест, а не індукція.

**«У кроці індукції ми припускаємо те, що доводимо».** Ми припускаємо твердження для меншого числа і виводимо його для
наступного. Колового міркування тут немає, бо ланцюжок починається з бази, яку доведено без жодних припущень.

**«Якщо інваріант зберігається, цикл правильний».** Ще треба довести, що цикл закінчиться, і що інваріант на виході
дає відповідь. Зламаний пошук з початку лекції має правильний і збережений інваріант, але вічно крутиться.

**«Корисний інваріант — той, який правдивий завжди».** Твердження «масив складається з тих самих елементів» правдиве
на кожному кроці сортування вставками, але на виході не каже, що масив відсортований. Інваріант має бути досить
сильним, щоб разом з умовою виходу дати відповідь.

## Практика

Практика дня описана в плані, у рядку «Зробити» дня 4. Тут вона розписана по кроках. Готових інваріантів для
`insertionSort` і готового доведення формули суми тут немає: лекція показала спосіб на інших прикладах.

**1. Інваріант зовнішнього циклу `insertionSort`.** Запишіть його в коментарі над циклом своїми словами, з номерами
позицій так, як їх нумерує ваш код, тобто з нуля. Перевірте, що в ньому дві половини: про порядок і про ті самі
елементи. Потім подумайте над внутрішнім циклом: що правдиве про частину масиву між `j + 1` і `i` перед кожною
перевіркою його умови?

**2. Перевірка в тестах.** Додайте в `insertionSort` перевірку інваріанта, яка працює лише тоді, коли `checks.enabled`
дорівнює `true`, і ввімкніть її в тестах через `beforeAll`. Навідні запитання:

- Як перевірити, що частина масиву відсортована, одним проходом?
- Як перевірити, що частина складається з тих самих елементів, що на початку? Підказка: відсортована копія початкової
  частини має збігатися з поточною частиною.
- Скільки коштує ваша перевірка на одному проході? Скільки разом на весь масив довжиною 1000? Чи не стала функція в
  тестах помітно повільнішою, і чи це прийнятно?

Щоб переконатися, що перевірка справді працює, тимчасово внесіть у функцію одруківку, наприклад `>=` замість `>` чи `j
> 0` замість `j >= 0`, і подивіться, чи впаде тест з повідомленням про інваріант. Потім одруківку приберіть.

**3. Доведення.** Доведіть індукцією, що `1 + 2 + … + n = n(n + 1) / 2`. Запишіть доведення за шаблоном MCS з п'яти
частин у `JOURNAL.md` або окремому файлі. Спершу явно запишіть `P(n)`. Яка база: `n = 0` чи `n = 1`? Що означає сума
нуля доданків?

**4. Журнал.** Один рядок у `JOURNAL.md`: що стало зрозумілим і що ні.

## Перевірте себе

**1. Доведіть індукцією, що `1 + 3 + 5 + … + (2n − 1) = n²` для всіх `n ≥ 1`.**

<details><summary>Відповідь</summary>

`P(n)`: сума перших `n` непарних чисел дорівнює `n²`. База `n = 1`: ліворуч 1, праворуч `1² = 1`. Крок: припустимо
`P(n)`. Сума перших `n + 1` непарних чисел дорівнює сумі перших `n` плюс наступне непарне `2n + 1`. За гіпотезою це
`n² + 2n + 1 = (n + 1)²`, тобто `P(n + 1)`. За принципом індукції `P(n)` правдиве для всіх `n ≥ 1`.

</details>

**2. Яка помилка в «доведенні», що всі коні однієї масті?**

<details><summary>Відповідь</summary>

Крок від `n = 1` до `n = 2` не працює. Для групи з двох коней підгрупи «усі, крім останнього» і «усі, крім першого»
складаються з одного коня кожна і не мають спільного коня, тому з того, що кожна підгрупа однієї масті, нічого не
випливає. Для `n ≥ 2` крок правильний, але ланцюжок рветься на першій ланці, і всі наступні висновки безпідставні.

</details>

**3. Інваріант для лінійного пошуку: функція перебирає масив зліва направо і повертає номер першого елемента, рівного
`target`, або `-1`, якщо такого немає. Сформулюйте інваріант і покажіть завершення.**

<details><summary>Відповідь</summary>

Інваріант: перед перевіркою умови з номером `i` серед елементів з номерами від 0 до `i − 1` немає `target`.
Ініціалізація: при `i = 0` ця частина порожня. Збереження: якщо `xs[i]` дорівнює `target`, функція повертає `i`, і це
перша поява, бо раніше `target` не було; інакше частина до `i` включно теж без `target`, і `i` збільшується.
Завершення: міра `n − i` зменшується на кожному проході. Якщо цикл дійшов до `i = n`, інваріант каже, що `target`
немає ніде, і `-1` правильне.

</details>

**4. Чому в алгоритмі Евкліда цикл закінчиться для будь-яких невід'ємних цілих `a₀` і `b₀`?**

<details><summary>Відповідь</summary>

Міра прогресу — `b`. Воно ціле й невід'ємне. На кожному проході нове `b` дорівнює `a mod b`, а остача від ділення на
`b` строго менша за `b`. Невід'ємне ціле число не може строго зменшуватися нескінченно, тому проходів скінченна
кількість.

</details>

**5. Як виправити зламаний пошук з початку лекції, щоб інваріант зберігався, а міра `hi − lo` строго зменшувалася?**

<details><summary>Відповідь</summary>

У першій гілці писати `lo = mid + 1`. Це не порушує інваріанта: якщо `xs[mid] < target`, то позиція `mid` теж належить
до тих, де значення менше за ціль, тож межа може пройти й за неї. А міра тепер зменшується завжди: `mid` лежить між
`lo` і `hi − 1`, тому і `lo = mid + 1`, і `hi = mid` роблять ділянку `[lo, hi)` строго меншою.

</details>

**6. Навіщо дорогу перевірку інваріанта загортати в `if (checks.enabled)`, а не перевіряти перемикач усередині
`invariant`?**

<details><summary>Відповідь</summary>

Аргументи функції обчислюються до її виклику. Вираз `slowGcd(a, b) === slowGcd(a0, b0)` виконувався б на кожному
проході навіть тоді, коли перевірки вимкнені, і функція `invariant` лише вирішувала б, чи кидати помилку. Умова `if`
ззовні не дає дорогому виразу обчислюватися взагалі.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| доведення | міркування, яке показує, що твердження правдиве для всіх входів |
| індукція | спосіб довести твердження для всіх натуральних чисел: база плюс крок |
| база індукції | доведення твердження для найменшого числа |
| крок індукції | доведення, що з твердження для `n` випливає твердження для `n + 1` |
| гіпотеза індукції | припущення в кроці, що твердження правдиве для `n` або для всіх менших чисел |
| сильна індукція | індукція, у кроці якої припускають твердження для всіх менших чисел |
| інваріант циклу | твердження про змінні, правдиве перед кожною перевіркою умови циклу |
| ініціалізація, збереження, завершення | три частини доведення через інваріант |
| міра прогресу | невід'ємне ціле число, яке строго зменшується на кожному проході й тому гарантує завершення |
| НСД | найбільший спільний дільник: найбільше число, на яке діляться обидва числа |
| `a mod b`, `a % b` | остача від ділення `a` на `b` |
| деструктуроване присвоєння | запис `[a, b] = [b, a % b]`, що записує кілька значень одночасно |
| `asserts condition` | позначка TypeScript: після виклику функції умова вважається правдивою |
| `beforeAll` | функція Vitest, що виконується один раз перед тестами файлу |
| бінарний пошук | пошук в упорядкованому масиві, який щоразу відкидає половину ділянки |
