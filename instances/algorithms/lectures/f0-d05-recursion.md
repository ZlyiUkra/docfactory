# Лекція. День 5. Рекурсія

Ця лекція вчить писати рекурсивні функції і довіряти їм, не розгортаючи подумки всі виклики. Читання займе близько 55
хвилин. Під кожним прикладом коду стоїть справжній вивід, який програма надрукувала в Node 24.22.

Учора ви бачили, що доведення індукцією і рекурсивна функція влаштовані однаково: база відповідає базовому випадку, а
гіпотеза індукції — рекурсивному виклику. Сьогодні цю схожість використаємо в протилежний бік: щоб написати рекурсивну
функцію, досить продумати один крок, а решту довірити рекурсивному виклику, так само як крок індукції довіряє
гіпотезі.

**Після лекції ви зможете пояснити:**

- коли рекурсія природніша за цикл і чому для деяких даних цикл узагалі не годиться;
- з яких частин складається правильна рекурсивна функція і чому вона закінчується;
- що відбувається в пам'яті під час рекурсивних викликів і звідки береться помилка переповнення стеку;
- скільки викликів зробить рекурсивна функція і чому деякі з них повторюються мільйони разів;
- як переписати рекурсію на цикл із власним стеком, коли вхід дуже глибокий;
- які помилки в рекурсивному коді трапляються найчастіше.

## Гілка коментарів

Уявіть сторінку обговорення. Під дописом є коментарі, на коментар можна відповісти, на відповідь теж, і так без
обмеження глибини. Над обговоренням треба показати «8 коментарів». Як їх порахувати?

Дані виглядають так:

```ts
// Коментар може мати відповіді, а кожна відповідь — свої відповіді, без обмеження глибини.
export type Comment = { text: string; replies: Comment[] };
```

Тип `Comment` посилається сам на себе: поле `replies` — масив коментарів. Таке означення називають
**самопосилальним**. Якби глибина була відома, скажімо, не більше трьох рівнів, можна було б написати три вкладені
цикли. Але глибина наперед невідома, тому жодна фіксована кількість циклів не годиться.

Ось розв'язок, який повторює будову даних:

```ts
// Скільки коментарів у гілці разом з її коренем.
export function countComments(comment: Comment): number {
  let total = 1;                               // сам коментар
  for (const reply of comment.replies) {
    total += countComments(reply);             // кожну відповідь рахує рекурсивний виклик
  }
  return total;
}
```

Функція, яка викликає саму себе, називається **рекурсивною**. Перевіримо на гілці з восьми коментарів: допис, три
відповіді на нього, одна відповідь на першу відповідь, дві на третю, і ще одна на одну з них.

```
рекурсивно: 8
```

Як думати про таку функцію? Не треба простежувати, що відбувається на кожному рівні. Досить двох міркувань: коментар
без відповідей функція рахує правильно, бо цикл не виконується і повертається 1; а для коментаря з відповідями функція
правильна, **якщо** правильні виклики для відповідей, бо загальна кількість — це сам коментар плюс кількості в кожній
відповіді. Це і є індукція з учорашньої лекції, тільки за розміром гілки замість числа.

## Спрости й делегуй

Erickson описує рекурсію як особливий вид **зведення**, тобто розв'язання задачі через уміння розв'язувати іншу
задачу. Правило таке:

- якщо екземпляр задачі можна розв'язати прямо, розв'яжіть прямо;
- інакше зведіть його до одного чи кількох **простіших екземплярів тієї самої задачі**.

Щоб самопосилання не плутало, Erickson пропонує уявити, що простіші екземпляри розв'язує хтось інший. Він називає
цього когось **Феєю рекурсії** і жартома додає, що математики знають її під іншим ім'ям: гіпотеза індукції. Ваша
робота — лише спростити задачу і зібрати відповідь з відповідей Феї. Як Фея розв'язує простіші екземпляри, вас не
стосується.

Ця сама думка є в книжці How to Design Programs. Там рекурсивний виклик у шаблоні функції називають «природною
рекурсією», а в примітці на полях порівнюють з доведенням індукцією: довіра до рекурсивного виклику — це використання
гіпотези індукції в кроці доведення. Шаблон функції для самопосилальних даних HtDP будує прямо з означення даних: по
одній гілці на кожен варіант даних і по одному рекурсивному виклику на кожне самопосилання. У `Comment` самопосилання
одне, поле `replies`, тому і рекурсивний виклик один, усередині циклу по цьому полю.

Erickson додає одну технічну умову: послідовність спрощень не може бути нескінченною. Рекурсивні виклики мусять
зрештою дійти до **базового випадку**, який розв'язується без рекурсії. Найпростіший спосіб це забезпечити — кожен
рекурсивний виклик робити на **строго меншому** вході. Це та сама міра прогресу, що й для циклів у день 4: гілка
відповіді менша за гілку, яка її містить, тож рекурсія закінчиться.

### Чотири запитання до рекурсивної функції

| Запитання | Для `countComments` |
|-----------|---------------------|
| Який вхід розв'язується прямо? | коментар без відповідей: відповідь 1, рекурсії немає |
| До яких менших екземплярів зводиться задача? | до гілок кожної відповіді |
| Як зібрати відповідь з відповідей на менші екземпляри? | додати 1 за сам коментар до суми відповідей на гілки |
| Чому виклики закінчаться? | кожна гілка відповіді містить строго менше коментарів, а гілка без відповідей рекурсії не викликає |

### Вежі Ханоя

Erickson показує, як «спрости й делегуй» розв'язує задачу, яка вручну здається заплутаною. Є три стрижні й `n` дисків
різного розміру, нанизаних на перший стрижень від найбільшого внизу до найменшого вгорі. Треба перенести всі диски на
інший стрижень, переносячи за раз один диск і ніколи не кладучи більший диск на менший.

Порада Erickson: думайте лише про **найбільший** диск. Щоб його перенести, усі менші диски мусять лежати на запасному
стрижні. Отже, спершу перенести `n − 1` менших дисків на запасний стрижень, потім перенести найбільший на цільовий,
потім перенести `n − 1` менших із запасного на цільовий. Два перенесення `n − 1` дисків — це та сама задача меншого
розміру, і її розв'язує Фея рекурсії. Як саме, вас не стосується. Erickson підкреслює це великими літерами: на цьому
місці треба зупинитися.

Лишається базовий випадок. Erickson помічає, що міркування припускає, що найбільший диск існує, тобто `n ≥ 1`. Для `n
= 0` нічого переносити не треба, і це найпростіший базовий випадок.

Ось хід для трьох дисків, які переносять зі стрижня A на стрижень C через B. Перші три ходи переносять два менші диски
на B, четвертий переносить найбільший на C, останні три переносять два менші з B на C:

| Хід | Що переноситься | Звідки → куди |
|-----|-----------------|---------------|
| 1 | найменший | A → C |
| 2 | середній | A → B |
| 3 | найменший | C → B |
| 4 | найбільший | A → C |
| 5 | найменший | B → A |
| 6 | середній | B → C |
| 7 | найменший | A → C |

Код цієї функції і доведення того, скільки ходів вона робить, — практика дня. Таблиця показує, чому важко розгортати
рекурсію подумки: уже для трьох дисків ходів сім, для чотирьох — п'ятнадцять, і стежити за ними без помилки складно.
Доводити правильність рекурсивної функції простіше, ніж простежувати її.

## Що відбувається в пам'яті

Щоб зрозуміти, де рекурсія ламається, треба знати, як виконуються виклики функцій.

Коли функція `f` викликає функцію `g`, виконання `f` призупиняється на середині. Комп'ютер мусить пам'ятати, куди
повернутися після `g`, і значення всіх локальних змінних `f`, щоб продовжити з того самого місця. Ці дані зберігаються
в області пам'яті, яку називають **стеком викликів**. На кожен виклик до стеку додається **кадр**: блок пам'яті з
параметрами, локальними змінними й адресою повернення. Коли функція повертає результат, її кадр знімається з вершини
стеку, і виконання продовжується в кадрі під ним.

Стек викликів працює за правилом «останнім прийшов, першим пішов»: знімається завжди той кадр, який додали останнім.
Таку структуру даних називають **стеком**, і план розбирає її у фазі 1. Grokking пояснює стек на прикладі стосу
листочків зі справами: новий листочок кладуть зверху, і читають завжди верхній.

Рекурсивні виклики для стеку нічим не відрізняються від звичайних. Кожен виклик має власний кадр і власні копії
змінних. Ось факторіал, який друкує, коли виклик починається і коли закінчується. **Факторіал** числа `n`,
позначається `n!`, — добуток усіх чисел від 1 до `n`: `4! = 1 · 2 · 3 · 4 = 24`.

```ts
// Факторіал, який друкує, коли виклик починається і коли повертає результат.
function factorial(n: number, depth = 0): number {
  const pad = "  ".repeat(depth);
  console.log(`${pad}factorial(${n}) почався`);
  const result = n === 1 ? 1 : n * factorial(n - 1, depth + 1);
  console.log(`${pad}factorial(${n}) повертає ${result}`);
  return result;
}
factorial(4);
```

Параметр `depth = 0` має **значення за замовчуванням**: якщо його не передати, він дорівнює 0. Він потрібен лише для
відступу в друку.

Вивід:

```
factorial(4) почався
  factorial(3) почався
    factorial(2) почався
      factorial(1) почався
      factorial(1) повертає 1
    factorial(2) повертає 2
  factorial(3) повертає 6
factorial(4) повертає 24
```

Відступ показує висоту стеку. На найглибшому місці в стеку лежать чотири кадри: `factorial(4)`, `factorial(3)`,
`factorial(2)` і `factorial(1)`. Перші три чекають, поки повернеться виклик над ними. Множення `n * …` у кожному кадрі
виконується вже **після** повернення, тому результати збираються знизу вгору: 1, потім 2, потім 6, потім 24.

### Переповнення стеку

Для стеку викликів програма заздалегідь резервує обмежений обсяг пам'яті. Якщо вкладених викликів стає забагато, місце
закінчується, і рушій JavaScript кидає помилку. Це **переповнення стеку**, англійською stack overflow; на честь цієї
помилки названо відомий сайт запитань і відповідей.

Повернімося до коментарів. Побудуємо гілку, де кожен коментар — відповідь на попередній, глибиною 100 000, і порахуємо
її обома способами: рекурсивною функцією і функцією без рекурсії, яку покажемо нижче.

```
рекурсивно: RangeError — Maximum call stack size exceeded
ітеративно: 100000
```

`RangeError` з повідомленням «Maximum call stack size exceeded» — саме так JavaScript повідомляє про переповнення
стеку.

Наскільки глибоко може зайти рекурсія? Програма знайшла найбільшу глибину, на якій три різні функції ще не падали:

```
depthOf: 9765
depthTail: 9276
depthHeavy: 6835
```

Функція `depthOf(n)` найпростіша: `n === 0 ? 0 : 1 + depthOf(n - 1)`. Функція `depthHeavy` робить те саме, але має
шість додаткових локальних змінних, тому її кадр більший, і в той самий стек їх уміщується менше. Звідси правило: межа
глибини в Node — кілька тисяч, близько десяти тисяч для найпростіших функцій, і вона залежить від розміру кадру. У
Python межа задана явно і за замовчуванням дорівнює 1000 викликів; це повертає функція `sys.getrecursionlimit()`.

Що означає `depthTail`, пояснює наступний розділ.

### Хвостова рекурсія в JavaScript не рятує

Виклик стоїть у **хвостовій позиції**, якщо після нього функції нічого не лишається зробити, крім як повернути його
результат. У `1 + depthOf(n - 1)` виклик не хвостовий: після повернення ще треба додати 1. У функції `depthTail(n,
acc)`, яка повертає `n === 0 ? acc : depthTail(n - 1, acc + 1)`, виклик хвостовий: накопичене значення передається
вперед у параметрі `acc`, і після повернення робити нічого не треба. Таку рекурсію називають **хвостовою**.

Кадр функції з хвостовим викликом більше не потрібен, тому мова може його звільнити, і тоді хвостова рекурсія не росте
в стеку. Специфікація ECMAScript з редакції ES2015 цього вимагає: у суворому режимі виклик у хвостовій позиції мусить
звільняти ресурси поточного кадру. Розділ «PrepareForTailCall» специфікації пояснює це словами «Discard all resources
associated with the current execution context». Але рушій V8, на якому працюють Node і Chrome, цю вимогу не виконує.
Вимір вище це показує: хвостова версія впала на глибині 9 276, навіть трохи раніше за звичайну, бо в неї на один
параметр більше. Grokking обережно каже, що хвостову рекурсію підтримують «лише деякі мови». Для JavaScript у Node
практичний висновок один: глибоку рекурсію хвостова форма не врятує.

### Рекурсія без рекурсії: власний стек

Якщо вхід може бути глибоким, рекурсію переписують на цикл, а стек викликів замінюють власним масивом, у якому лежить
усе, що ще треба обробити. Grokking описує саме ці два способи на прикладі пошуку ключа в коробках, вкладених у
коробки: можна тримати купу коробок, які ще треба переглянути, а можна відкривати коробку і для вкладених коробок
викликати той самий пошук. У рекурсивному способі купи немає, бо її роль грає стек викликів.

```ts
// Те саме без рекурсії: власний стек замість стеку викликів.
export function countCommentsIterative(root: Comment): number {
  const pending: Comment[] = [root];           // коментарі, які ще треба переглянути
  let total = 0;
  while (pending.length > 0) {
    const comment = pending.pop()!;
    total += 1;
    for (const reply of comment.replies) pending.push(reply);
  }
  return total;
}
```

Масив `pending` — це «купа коробок». `pop` знімає останній доданий елемент, `push` додає в кінець, тому масив працює
як стек. Знак `!` після `pop()` каже TypeScript, що масив не порожній, бо це перевірила умова циклу. Масив живе в
звичайній пам'яті, а не в обмеженому стеку викликів, тому гілку глибиною 100 000 ця функція порахувала без помилки.

Ціна такого перепису — читабельність. Рекурсивна версія повторює будову даних рядок у рядок, а в ітеративній ту саму
будову доводиться відновлювати вручну. Тому рекурсію пишуть там, де глибина помірна, а власний стек — там, де вхід
приходить ззовні і може бути як завгодно глибоким.

## Скільки коштує рекурсія

### Пам'ять — це глибина

Кожен кадр займає сталу пам'ять, а в стеку одночасно лежать лише кадри від поточного виклику до кореня. Тому додаткова
пам'ять рекурсії дорівнює її **найбільшій глибині**, помноженій на розмір кадру, а не загальній кількості викликів.
Bae показує це на функції, яка друкує числа від `n` до 1: вона робить `n` вкладених викликів і займає `Θ(n)` пам'яті,
хоча власних змінних, крім `n`, не має. BCtCI наголошує: на співбесіді пам'ять стеку викликів теж треба рахувати.

### Час — це кількість викликів

Час рекурсивної функції — сума роботи всіх викликів. Виклики зручно уявляти **деревом викликів**: кожен виклик —
вузол, а виклики, які він робить, — його нащадки. Дерево — це картинка для аналізу, а не структура в пам'яті: у
пам'яті в кожен момент лежить лише одна гілка від кореня до поточного виклику.

Найвідоміший приклад, де дерево викликів вибухає, — числа Фібоначчі. За означенням `F(0) = 0`, `F(1) = 1`, а кожне
наступне — сума двох попередніх. Пряма рекурсивна функція повторює означення:

```ts
function fib(n: number): number {
  return n <= 1 ? n : fib(n - 1) + fib(n - 2);
}
```

Програма порахувала, скільки разів ця функція викликається:

```
fib(6): викликів 25 fib(6)×1 fib(5)×1 fib(4)×2 fib(3)×3 fib(2)×5 fib(1)×8 fib(0)×5
fib(10) = 55, викликів 177
fib(20) = 6765, викликів 21891
fib(30) = 832040, викликів 2692537
```

Перший рядок показує, звідки береться вибух: `fib(2)` обчислюється п'ять разів, `fib(1)` — вісім. Одна й та сама менша
задача розв'язується знову і знову, бо два рекурсивні виклики не знають про роботу одне одного. Кількість викликів
росте приблизно в 1,6 раза з кожним `n`, тобто експоненційно. Для `n = 30` це понад два з половиною мільйони викликів,
щоб отримати число, яке цикл обчислює за 30 кроків. Запам'ятовування вже обчислених значень, яке називають
**мемоізацією**, прибирає повтори; план розбирає його у фазі 4, у дні про динамічне програмування.

Протилежний приклад — швидке піднесення до степеня. Для парного `p` маємо `aᵖ = (a^(p/2))²`, тобто одним рекурсивним
викликом задача зменшується вдвічі:

```ts
let calls = 0;
// a у степені p для цілого p ≥ 0: парний степінь ділимо навпіл.
function power(a: bigint, p: number): bigint {
  calls++;
  if (p === 0) return 1n;
  if (p % 2 === 0) {
    const half = power(a, p / 2);
    return half * half;
  }
  return a * power(a, p - 1);
}
```

Тип `bigint` і літерал `1n` потрібні, бо `2¹⁰⁰⁰` не вміщується точно в `number`. Вивід для `a = 2n`:

```
2^10: цифр 4, викликів 6
2^64: цифр 20, викликів 8
2^1000: цифр 302, викликів 16
2^1000000: цифр 301030, викликів 27
```

Для степеня мільйон досить 27 викликів, бо щонайменше кожен другий виклик ділить `p` навпіл, а `log₂ 1 000 000 ≈ 20`.
Зверніть увагу на змінну `half`: результат рекурсивного виклику зберігається і використовується двічі. Якби написати
`power(a, p / 2) * power(a, p / 2)`, виклик розгалужувався б на два, і вся економія зникла б.

Як точно рахувати час рекурсивних функцій через рівняння на кшталт `T(n) = 2T(n/2) + n`, пояснює завтрашня лекція.

## Типові помилки

BCtCI перелічує помилки, які найчастіше роблять у рекурсивному коді. Ось вони на прикладах JavaScript.

**Забутий або неправильний базовий випадок.** Факторіал з базою `n === 1`, викликаний для 0, піде в `factorial(−1)`,
`factorial(−2)` і далі, поки не переповнить стек. Правило BCtCI: кожен допустимий вхід має однозначно належати або до
базового випадку, або до рекурсивного. Для факторіала база `n === 0` з відповіддю 1 накриває і 0, і всі додатні числа.

**Немає прогресу.** Рекурсивний виклик із тим самим або більшим входом не наближає до бази. Типовий приклад —
`countdown(n - 2)` з базою `n === 0`: для непарного `n` значення перестрибне через 0 і піде в від'ємні числа.

**Зайві копії.** Перевірка, чи є рядок паліндромом, може на кожному кроці відрізати перший і останній символи через
`s.slice(1, -1)`. Але `slice` створює новий рядок, і копіювання коштує стільки, скільки символів у копії. Програма
порахувала скопійовані символи для рядка з 5000 літер:

```
true скопійовано символів: 6247500
```

Це `4998 + 4996 + … + 2`, близько `n² / 4`. Рекурсія з `n/2` викликів стала квадратичною через копії. BCtCI радить
**передавати номери, а не копії**: функція `isPalindrome(s, lo, hi)` порівнює `s[lo]` і `s[hi]` і викликає себе з `lo
+ 1` і `hi − 1`, не створюючи нових рядків. Та сама пастка чатує на `xs.slice(1)` у рекурсивній обробці масиву.

**Неправильно зібрані результати.** Якщо рекурсивних викликів кілька, їхні відповіді треба поєднати так, як вимагає
задача: скласти, перемножити, вибрати найбільшу. Найчастіше помилка видна на прикладі з двох-трьох елементів.

**Забутий `return`.** Рекурсивний виклик обчислили, але його результат не повернули. JavaScript у такому разі мовчки
поверне `undefined`. TypeScript допомагає, якщо тип результату записано явно. Для функції

```ts
function sumTo(n: number): number {
  if (n === 0) {
    return 0;
  } else {
    n + sumTo(n - 1);
  }
}
```

компілятор каже:

```
error TS2366: Function lacks ending return statement and return type does not include 'undefined'.
```

Тобто «функція не має завершального `return`, а тип результату не включає `undefined`». Без явного типу `: number`
TypeScript вивів би тип `number | undefined` і нічого б не сказав, а Node надрукував би `undefined`.

## Як це звучить на співбесіді

BCtCI пише, що рекурсія на співбесідах рідко буває окремою темою, але лежить в основі задач про дерева, графи, перебір
із поверненням і динамічне програмування.

| Ситуація | Що сказати чи зробити |
|----------|-----------------------|
| дані вкладені на невідому глибину: дерево, вкладені масиви, JSON | «Структура самопосилальна, тому рекурсія повторить її будову» |
| задача має самопосилальне означення | записати означення як базовий і рекурсивний випадки |
| вхід може бути дуже глибоким | «Глибина може дійти до десятків тисяч, рекурсія переповнить стек; я напишу цикл із власним стеком або принаймні попереджаю про ризик» |
| питають про пам'ять рекурсивного рішення | «Додаткова пам'ять — глибина рекурсії, бо кожен кадр лежить у стеку, поки не повернеться» |
| питають про час рекурсивного рішення | оцінити кількість вузлів дерева викликів і роботу в кожному; для дерева з розгалуженням `b` і глибиною `d` вузлів не більше `bᵈ`, з точністю до сталого множника |
| у рішенні повторюються ті самі виклики | «Тут перекриваються підзадачі, мемоізація прибере повтори» |

Останні два рядки BCtCI зводить до прийому, який автори називають методом BAD: розгалуження, глибина і додаткова
робота вузла. Метод дає правильну верхню межу, але не завжди точну. Точніші способи — завтра.

## Типові хибні уявлення

**«Щоб зрозуміти рекурсивну функцію, треба простежити всі виклики».** Простежувати корисно на прикладі з двох-трьох
кроків, щоб побачити механіку. Для розуміння правильності досить перевірити базовий випадок і один крок, довіряючи
меншим викликам. Повне простеження для `hanoi(4)` — це п'ятнадцять ходів, і думка губиться.

**«Рекурсія повільніша за цикл, тому її треба уникати».** Виклик функції трохи дорожчий за прохід циклу, але сталий
множник рідко вирішує. Вирішує кількість викликів. `fib` повільна не через рекурсію, а через повтори: та сама функція
з мемоізацією робить лінійну кількість викликів.

**«Хвостова рекурсія не займає стеку».** Так каже специфікація ECMAScript, але Node і Chrome цього не виконують.
Хвостова функція впала на тій самій глибині, що й звичайна.

**«Рекурсія не займає пам'яті, якщо функція не створює масивів».** Кожен незавершений виклик займає кадр у стеку.
Рекурсія глибиною `n` займає `Θ(n)` пам'яті, навіть якщо в ній лише одна числова змінна.

**«Базовий випадок — це завжди найменший вхід 0 чи 1».** Базових випадків може бути кілька, і вони визначаються тим,
куди не дотягується рекурсивний крок. У Фібоначчі їх два, бо крок заглядає на два числа назад.

**«Дерево викликів лежить у пам'яті цілком».** У пам'яті в кожен момент лише одна гілка: від кореня до поточного
виклику. Дерево — інструмент для підрахунку часу.

## Практика

Практика дня описана в плані, у рядку «Зробити» дня 5. Тут вона розписана по кроках. Готової функції `hanoi` і
готового доведення тут немає: лекція показала спосіб думати і хід для трьох дисків.

**1. Функція `hanoi(n)`.** Файл `src/hanoi.ts`. Функція повертає масив ходів. Спершу вирішіть, як описати один хід
типом TypeScript: наприклад, об'єкт із полями «звідки» і «куди». Навідні запитання:

- Скільки параметрів потрібно рекурсивній функції, щоб пам'ятати, звідки, куди і через який стрижень переносити?
  Підказка: зовнішня функція `hanoi(n)` може викликати допоміжну функцію з більшою кількістю параметрів.
- Який базовий випадок ви виберете: `n === 0` чи `n === 1`? Що повертає кожен з них?
- Як зібрати ходи: повертати нові масиви й склеювати їх, чи додавати ходи в один спільний масив? Що скаже BCtCI про
  копії?

Тест: результат для `n = 3` збігається з таблицею лекції, і жоден хід не кладе більший диск на менший. Як перевірити

## Перевірте себе

**1. Яка помилка в цій функції і що станеться при виклику `countdown(5)`?**

```ts
function countdown(n: number): void {
  if (n === 0) return;
  console.log(n);
  countdown(n - 2);
}
```

<details><summary>Відповідь</summary>

Немає прогресу до бази для непарних `n`. Від 5 функція дійде до 3, 1, −1, −3 і далі, перестрибнувши через 0, і зрештою
кине `RangeError: Maximum call stack size exceeded`. Виправлення: база `n <= 0`, тоді і парні, і непарні `n`
закінчуються.

</details>

**2. Скільки кадрів лежить у стеку на найглибшому місці під час виклику `factorial(4)` з лекції? А скільки разів
викликається функція загалом?**

<details><summary>Відповідь</summary>

Чотири кадри: `factorial(4)`, `factorial(3)`, `factorial(2)`, `factorial(1)`. Викликів теж чотири, бо кожен виклик
робить не більше одного рекурсивного. Для функцій з кількома рекурсивними викликами ці числа розходяться: `fib(6)`
робить 25 викликів, а найбільша глибина стеку лише 6.

</details>

**3. Чому `power(a, p / 2) * power(a, p / 2)` замість збереження результату в `half` робить функцію набагато
повільнішою?**

<details><summary>Відповідь</summary>

Кожен виклик для парного `p` розгалужується на два однакові виклики. Глибина лишається близько `log₂ p`, але кількість
викликів подвоюється на кожному рівні, і разом їх стає порядку `2^(log₂ p) = p`. Швидке піднесення до степеня
перетворюється на звичайне, з лінійною кількістю множень. Збережений `half` лишає по одному виклику на рівень.

</details>

**4. Чому рекурсивна функція, яка перевіряє паліндром через `s.slice(1, -1)`, квадратична, хоча робить лише `n/2`
викликів?**

<details><summary>Відповідь</summary>

Кожен виклик створює копію середини рядка, а копіювання коштує стільки кроків, скільки символів у копії: `n − 2`,
потім `n − 4` і так далі. Сума `(n − 2) + (n − 4) + … ≈ n²/4`, тобто `Θ(n²)`. Для 5000 символів програма нарахувала
понад шість мільйонів скопійованих символів. Версія з номерами `lo` і `hi` не копіює нічого і працює за `Θ(n)`.

</details>

**5. Скільки додаткової пам'яті займає `countComments` для гілки з `n` коментарів, і від чого це залежить?**

<details><summary>Відповідь</summary>

Від найбільшої глибини гілки, а не від кількості коментарів. Якщо всі `n` коментарів — прямі відповіді на допис,
глибина 2, і пам'ять стеку стала. Якщо кожен коментар — відповідь на попередній, глибина `n`, і пам'ять `Θ(n)`; саме
на такій гілці глибиною 100 000 рекурсивна версія впала.

</details>

**6. Що спільного між базовим випадком рекурсивної функції і базою доведення індукцією?**

<details><summary>Відповідь</summary>

Обидва розв'язуються прямо, без звернення до меншого випадку, і обидва запускають ланцюжок. У доведенні база дає перше
правдиве твердження, з якого крок виводить наступні. У функції базовий випадок повертає першу відповідь, з якої
повернення рекурсивних викликів збирають решту. Без бази доведення нічого не доводить, а функція не закінчується.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| рекурсія, рекурсивна функція | функція, яка викликає саму себе для меншого входу |
| базовий випадок | вхід, на якому функція відповідає прямо, без рекурсивного виклику |
| рекурсивний випадок | вхід, на якому функція зводить задачу до менших екземплярів і викликає себе |
| самопосилальне означення | означення типу чи поняття, що посилається саме на себе, як `Comment` з полем `replies` |
| зведення | розв'язання задачі через уміння розв'язувати іншу задачу |
| стек викликів | область пам'яті, де лежать кадри всіх незавершених викликів |
| кадр | блок пам'яті одного виклику: параметри, локальні змінні, адреса повернення |
| переповнення стеку | помилка, коли незавершених викликів більше, ніж уміщує стек; у JavaScript — `RangeError` |
| хвостовий виклик | виклик, після якого функція лише повертає його результат |
| хвостова рекурсія | рекурсія, де рекурсивний виклик хвостовий |
| дерево викликів | картинка, де кожен виклик — вузол, а виклики, які він робить, — його нащадки |
| мемоізація | запам'ятовування вже обчислених результатів, щоб не обчислювати їх знову |
| факторіал, `n!` | добуток чисел від 1 до `n` |
| паліндром | рядок, який читається однаково зліва направо і справа наліво |
| `bigint` | тип JavaScript для цілих чисел будь-якої довжини, літерали з `n` наприкінці |
| значення за замовчуванням | значення параметра, якщо його не передали під час виклику |
