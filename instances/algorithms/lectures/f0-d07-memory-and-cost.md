# Лекція. День 7. Пам'ять комп'ютера і справжня ціна кроку

Ця лекція пояснює, чому однакова кількість кроків може займати дуже різний час. Читання займе близько 50 хвилин. Усі
виміри в лекції зроблено в Node 24.22 на процесорі Intel Core i7-9700K. На вашому комп'ютері числа будуть інші, але
відношення між ними будуть схожими, і саме відношення тут важливі.

Шість днів план рахував кроки в моделі RAM, де кожне звернення до пам'яті коштує однаково. Ця модель дала мову для
порівняння алгоритмів, і вона нікуди не дінеться. Але CLRS у розділі 2.2 чесно попереджав: модель не враховує кешів.
Сьогодні подивимося, що саме вона не враховує, наскільки це важить і коли через це змінюється вибір структури даних.

**Після лекції ви зможете пояснити:**

- як масив і зв'язний список лежать у пам'яті і чому елемент масиву знаходиться одним обчисленням;
- що таке ієрархія пам'яті, кеш і рядок кешу;
- чому прохід масивом підряд найшвидший, а стрибки по пам'яті повільні, навіть якщо кроків стільки ж;
- як JavaScript розміщує в пам'яті масиви чисел, типізовані масиви й об'єкти;
- як правильно вимірювати час і які помилки роблять у вимірах найчастіше;
- коли модель RAM дає правильну відповідь, а коли вводить в оману.

## Та сама сума, у вісім разів довша

Візьмемо матрицю `2048 × 2048` дробових чисел і порахуємо суму всіх її елементів двома способами: спершу рядок за
рядком, потім стовпчик за стовпчиком. Обидва способи роблять рівно `2048² = 4 194 304` додавання і читають кожен
елемент рівно один раз. У моделі RAM вони однакові.

Матрицю збережено в одному масиві `Float64Array`, рядок за рядком: спершу всі 2048 чисел першого рядка, потім усі
числа другого, і так далі. Елемент з рядка `r` і стовпця `c` лежить на позиції `r * n + c`.

```ts
// Сума матриці n × n, збереженої в одному масиві рядок за рядком.
const n = 2048;
const m = new Float64Array(n * n);                           // 2048 · 2048 · 8 байтів = 32 МБ
for (let i = 0; i < m.length; i++) m[i] = i % 7;

function byRows(): number {
  let s = 0;
  for (let r = 0; r < n; r++)
    for (let c = 0; c < n; c++) s += m[r * n + c]!;          // сусідні адреси
  return s;
}
function byColumns(): number {
  let s = 0;
  for (let c = 0; c < n; c++)
    for (let r = 0; r < n; r++) s += m[r * n + c]!;          // стрибок на n · 8 байтів
  return s;
}
```

Кожну функцію виміряно п'ять разів, і надруковано медіану. Вивід:

```
по рядках: медіана 7.4 мс, сума 12582907
по стовпцях: медіана 60.8 мс, сума 12582907
```

Суми однакові, тобто обидві функції зробили те саме. А час відрізняється у вісім разів. Різниця між функціями лише в
порядку, у якому вони звертаються до пам'яті: перша читає числа, що лежать поруч, друга щоразу стрибає на 2048 чисел,
тобто на 16 КБ уперед. Щоб пояснити, чому порядок так важить, треба знати, як влаштована пам'ять.

## Як лежать дані в пам'яті

### Пам'ять — це пронумеровані комірки

Grokking пояснює пам'ять як величезну шафу з шухлядами. Кожна шухляда має номер, тобто **адресу**, і вміщує одне
значення. Щоб щось зберегти, програма просить у комп'ютера місце і отримує адресу. Насправді комірка — це один байт, а
число займає кілька сусідніх байтів: `Float64Array` зберігає кожне число у 8 байтах, `Int32Array` — у 4.

### Масив: усе поруч

**Масив** займає один суцільний шматок пам'яті, і його елементи лежать один за одним. Якщо масив починається з адреси
`A`, а кожен елемент займає `s` байтів, то елемент з номером `i` лежить за адресою `A + i · s`. Цю адресу процесор
обчислює одним множенням і одним додаванням, хоч би яким великим був масив. Тому доступ за номером коштує `Θ(1)`.
Grokking називає це **довільним доступом**: можна одразу перейти до будь-якого елемента.

Звідси й нумерація з нуля: перший елемент лежить за адресою `A + 0 · s`, тобто на самому початку масиву.

Ціна суцільного шматка — вставка. Щоб вставити елемент у середину, усі елементи після нього треба зсунути на одну
позицію, а якщо місця немає, переїхати в більший шматок і скопіювати все. Як робити це дешево в середньому, пояснює
завтрашня лекція про динамічний масив.

### Зв'язний список: кожен вузол окремо

**Зв'язний список** зберігає кожен елемент в окремому **вузлі**, а кожен вузол містить, крім значення, адресу
наступного вузла. Таку адресу, збережену як значення, називають **вказівником**. Вузли можуть лежати будь-де в
пам'яті. Grokking порівнює це з полюванням за скарбом: на першому місці написано, де шукати друге, на другому — де
третє.

Вставити вузол у відоме місце списку легко: треба лише змінити один вказівник. Але щоб дійти до елемента з номером
`i`, треба пройти `i` вказівників від початку, бо адресу `i`-го вузла неможливо обчислити. Такий доступ називають
**послідовним**.

Курс MIT 6.006 і Grokking зводять порівняння в таблиці. Ось їхнє спільне зведення, де `Θ` — найгірший випадок однієї
операції. Рядок про вставку в середину взято з Grokking: MIT рахує туди й пошук місця вставки, і тоді для списку
виходить `Θ(n)`.

| Операція | Масив | Зв'язний список |
|----------|-------|-----------------|
| прочитати чи змінити елемент з номером `i` | `Θ(1)` | `Θ(i)`, до `Θ(n)` |
| вставити чи видалити на початку | `Θ(n)` | `Θ(1)` |
| вставити чи видалити в середині | `Θ(n)` | `Θ(1)`, якщо вузол уже знайдено |
| пройти всі елементи | `Θ(n)` | `Θ(n)` |

Останній рядок — головний для сьогоднішнього дня. Обидві структури проходять усі елементи за `Θ(n)`, і модель RAM
вважає їх однаковими. Практика дня перевіряє, чи однакові вони насправді.

## Ієрархія пам'яті

### Чому пам'ять повільна

Процесор виконує прості операції за частки наносекунди, а основна пам'ять, **оперативна пам'ять**, віддає дані за
десятки наносекунд. Якби процесор щоразу чекав на оперативну пам'ять, він би здебільшого простоював. Тому між
процесором і оперативною пам'яттю стоять кілька рівнів **кешу**: невеликої, але швидкої пам'яті всередині процесора,
де лежать копії нещодавно використаних даних.

Рівні кешу нумерують від найближчого до процесора. Чим ближче рівень, тим він швидший і менший. Розміри кешів свого
процесора в Linux і WSL показує команда `getconf -a`. Для процесора, на якому зроблено виміри лекції:

```
LEVEL1_DCACHE_SIZE                 32768
LEVEL1_DCACHE_LINESIZE             64
LEVEL2_CACHE_SIZE                  262144
LEVEL2_CACHE_LINESIZE              64
LEVEL3_CACHE_SIZE                  12582912
LEVEL3_CACHE_LINESIZE              64
```

Тобто кеш першого рівня для даних — 32 КБ, другого — 256 КБ, третього — 12 МБ. Матриця з початку лекції займає 32 МБ і
в жоден кеш цілком не вміщується. algorithmica показує цю ієрархію вимірами: коли масив перестає вміщуватися в
черговий рівень кешу, швидкість його обробки падає сходинкою.

### Рядок кешу

Другий рядок виводу, `LINESIZE 64`, важить не менше за розміри. Процесор переносить дані між пам'яттю і кешем не по
одному байту і не по одному числу, а **рядками кешу** по 64 байти. algorithmica формулює це так: уся пам'ять поділена
на блоки по 64 байти, і коли ви просите хоч один байт, разом з ним приходять і всі його 63 сусіди, потрібні вони вам
чи ні.

Звідси пояснення першого виміру. У 64 байтах уміщується вісім чисел `Float64`.

- **Прохід по рядках** читає числа підряд. Перше число рядка кешу змушує завантажити його з пам'яті, а наступні сім
  уже лежать у кеші. Крім того, процесор помічає, що програма йде підряд, і заздалегідь підвантажує наступні рядки
  кешу. Це називають **попередньою вибіркою**.
- **Прохід по стовпцях** стрибає на 16 КБ між сусідніми зверненнями. Кожне звернення потрапляє в інший рядок кешу, з
  якого використовується одне число з восьми. Поки програма повернеться до сусіднього стовпця, цей рядок кешу вже
  витіснено іншими даними, бо стовпець з 2048 рядків кешу займає 128 КБ.

Отже, обидві функції читають однакову кількість чисел, але функція по стовпцях завантажує з пам'яті у вісім разів
більше рядків кешу. Вісім разів різниці в часі — не збіг.

### Рахувати рядки кешу, а не звернення

algorithmica показує цю думку ще одним дослідом, і його легко повторити на JavaScript. Цикл збільшує кожен `step`-ий
елемент масиву `Int32Array`. З кроком 1 він торкається кожного елемента, з кроком 16 — кожного шістнадцятого, тобто
робить у 16 разів менше роботи.

```ts
// Збільшує кожен step-ий елемент масиву: на кроці 16 роботи в 16 разів менше.
function touch(a: Int32Array, step: number): void {
  for (let i = 0; i < a.length; i += step) a[i]! += 1;
}
```

Програма повторювала цикл так, щоб загальний обсяг пройденої пам'яті був однаковим, і вимірювала медіану семи запусків
для маленького масиву, що вміщується в кеш другого рівня, і для великого, що не вміщується в жоден кеш:

```
масив 64 КБ: крок 1 — 84.6 мс, крок 16 — 5.4 мс, відношення 15.5
масив 65536 КБ: крок 1 — 119.3 мс, крок 16 — 31.9 мс, відношення 3.7
```

Для маленького масиву в 16 разів менша робота дала в 15,5 раза менший час, як і обіцяє модель RAM. Для великого масиву
та сама в 16 разів менша робота дала виграш лише в 3,7 раза. Причина та сама: 16 чисел `Int32` займають рівно 64
байти, тож цикл із кроком 16 торкається одного числа в кожному рядку кешу. Обидва цикли завантажують з оперативної
пам'яті **ті самі рядки кешу**, і для великого масиву саме це завантаження займає більшу частину часу. У досліді
algorithmica, написаному на C++, графіки двох циклів для великих масивів майже зливаються. У JavaScript кожен крок
циклу дорожчий, тому різниця лишилася, але від шістнадцятикратної вона впала до чотирикратної.

Практичний урок algorithmica: для алгоритмів, які впираються в пам'ять, рахуйте кількість рядків кешу, яких торкається
алгоритм, а не лише кількість читань і записів.

### Затримка і пропускна здатність

algorithmica розрізняє дві характеристики пам'яті.

- **Затримка** — час від запиту до приходу даних.
- **Пропускна здатність** — скільки даних пам'ять віддає за секунду.

Коли програма читає масив підряд, процесор знає наступні адреси заздалегідь, посилає багато запитів одночасно, і
затримки перекриваються. Швидкість тоді обмежує пропускна здатність. Коли ж наступну адресу можна дізнатися лише з
щойно прочитаних даних, як у зв'язному списку, кожен запит мусить чекати попереднього, і швидкість обмежує затримка.
Цей шаблон algorithmica називає **гонитвою за вказівниками** і пише, що він у багато разів повільніший за лінійний
прохід і дуже поширений у структурах даних, написаних мовами високого рівня з великою кількістю об'єктів і посилань на
них.

## Що це означає для JavaScript

У JavaScript немає явних адрес, але рушій V8 усе одно розміщує дані в пам'яті, і від цього залежить швидкість.

**Типізовані масиви.** `Int32Array`, `Float64Array` та інші, за MDN, — це подання масиву поверх буфера двійкових
даних. Елементи лежать у буфері підряд, кожен фіксованого розміру. Це найближчий у JavaScript аналог масиву з
підручника.

**Звичайні масиви чисел.** V8 відстежує, які значення лежать у масиві, і вибирає під них представлення, яке блог V8
називає **видом елементів**. Масив малих цілих чисел має вид `PACKED_SMI_ELEMENTS`, масив дробових —
`PACKED_DOUBLE_ELEMENTS`, масив довільних значень — `PACKED_ELEMENTS`. Блог описує їх як дедалі загальніші
представлення: дробові числа загальніші за малі цілі, а довільні значення загальніші за дробові. Масив з одних чисел,
який ніколи не отримував рядків чи об'єктів, лишається в одному з числових видів. Переходи між видами йдуть лише в бік
загальнішого: масив, у який один раз поклали рядок, уже не стане масивом чисел. Якщо в масиві з'явилася «дірка»,
наприклад через `new Array(n)` без заповнення, він назавжди стає «дірявим», `HOLEY`, і доступ до нього трохи дорожчий.

**Об'єкти.** Кожен об'єкт, наприклад вузол списку `{ value, next }`, V8 розміщує в купі окремо, а масив об'єктів
зберігає лише посилання на них. Блог V8 про прибирання сміття описує дві речі, важливі для вимірів. Перше: нові
об'єкти розміщуються за наступною вільною адресою, тобто об'єкти, створені один за одним, лежать у пам'яті поруч.
Друге: коли прибиральник сміття переносить живі об'єкти, він складає їх суцільним шматком. Тому зв'язний список, вузли
якого створено в порядку проходу, у JavaScript може лежати в пам'яті майже як масив, і його прохід буде не таким
повільним, як очікує теорія. Розкидати вузли по пам'яті можна, створивши їх у випадковому порядку.

## Як правильно вимірювати

Учорашні виміри дня 2 і цього дня спираються на кілька правил. Без них числа виходять випадковими.

| Правило | Чому |
|---------|------|
| Запускайте вимір кілька разів і беріть медіану. | Перший запуск включає підготовку коду рушієм, а інші програми на комп'ютері заважають випадково. Медіана менше залежить від одного невдалого запуску. |
| Використовуйте результат обчислення, наприклад друкуйте суму. | Рушій може викинути обчислення, результат якого нікуди не йде, і ви виміряєте порожній цикл. |
| Готуйте дані до початку виміру. | Інакше в час потрапить створення масиву. |
| Порівнюйте на однакових даних і однакових розмірах. | Інакше різниця може бути в даних, а не в способі. |
| Дивіться на відношення, а не на мілісекунди. | Мілісекунди залежать від комп'ютера, відношення переносяться. |
| Пробуйте кілька розмірів, зокрема більші за кеш. | Ефекти пам'яті видно лише тоді, коли дані не вміщуються в кеш. |

`performance.now()` повертає час у мілісекундах з дробовою частиною, тому ним можна міряти інтервали коротші за
мілісекунду. Але для дуже коротких операцій точніше повторити операцію багато разів і поділити.

## Коли модель RAM помиляється і чи варто її викидати

Модель RAM не помиляється в **порядку росту**. Обидва проходи матриці лінійні за кількістю елементів, і подвоєння
матриці подвоїть час обох. Помиляється вона в **сталому множнику**: він залежить від порядку звернень і може
відрізнятися в десятки разів. CLRS пише, що аналіз у моделі RAM зазвичай добре передбачає справжній час, і це правда,
коли порівнюють алгоритми з різним порядком росту. Коли ж порядок однаковий, вирішує стала, і тоді вирішує пам'ять.

Де це змінює вибір у цьому плані:

| Порівняння | Що каже модель RAM | Що каже пам'ять |
|------------|--------------------|-----------------|
| прохід масивом і списком | обидва `Θ(n)` | масив швидший у рази, бо читає підряд |
| бінарне дерево пошуку і відсортований масив для пошуку | обидва `Θ(log n)` | масив зазвичай швидший; фаза 2 |
| B-дерево і двійкове дерево | B-дерево не краще асимптотично | B-дерево торкається набагато менше блоків пам'яті чи диска; фаза 2, день 7 |
| хеш-таблиця з ланцюжками і з відкритою адресацією | обидві `Θ(1)` в середньому | відкрита адресація читає сусідні комірки; фаза 1, день 4 |

## Як це звучить на співбесіді

Класичне запитання «масив чи зв'язний список?» має відповідь у два шари. Перший — таблиця операцій: що швидше
асимптотично. Другий — пам'ять: прохід масивом швидший через кеш, а список має додаткову пам'ять на вказівник у
кожному вузлі. Grokking підсумовує: масиви використовують частіше, крім окремих випадків.

| Запитання | Що сказати |
|-----------|-----------|
| «Чому масив швидший за список, якщо обидва проходять за `O(n)`?» | «Елементи масиву лежать поруч, процесор читає їх рядками кешу і заздалегідь. Вузли списку розкидані, і кожен перехід за вказівником чекає на пам'ять» |
| «Коли список кращий?» | «Коли часто вставляють і видаляють у відомому місці, і немає довільного доступу. Наприклад, у кеші LRU з хеш-таблицею» |
| «Як обійти матрицю швидше?» | «У тому порядку, у якому вона лежить у пам'яті: рядок за рядком для звичайного зберігання» |
| «Чи має сенс асимптотично гірший алгоритм?» | «На малих даних, які вміщуються в кеш, або коли він читає пам'ять підряд — так. Тому бібліотеки досортовують короткі шматки вставками» |

## Типові хибні уявлення

**«Однакова асимптотика — однаковий час».** Два проходи матриці мають однакову асимптотику і різняться у вісім разів.
Асимптотика порівнює ріст, а не сталу.

**«Менше операцій — завжди швидше».** Цикл із кроком 16 робить у 16 разів менше збільшень, а на великому масиві виграв
лише в 3,7 раза. Важить, скільки даних прочитано з пам'яті.

**«Зв'язний список у JavaScript завжди повільний».** Якщо вузли створено підряд, V8 розмістить їх поруч, і список
поводиться майже як масив. Повільним його робить розкиданість вузлів у пам'яті, а не сама ідея списку.

**«Одного виміру досить».** Перший запуск включає підготовку коду, а випадкові фонові задачі можуть подвоїти час.
Беріть медіану кількох запусків.

**«Модель RAM неправильна, тому асимптотика марна».** Асимптотика правильно каже, як росте час. Вона не каже, яка
стала, і для цього потрібні виміри. Обидва інструменти потрібні разом.

**«Кеш — деталь заліза, програміста вона не стосується».** Порядок звернень до пам'яті вибирає програміст: обхід
матриці, вибір масиву чи списку, розміщення об'єктів.

## Практика

Практика дня описана в плані, у рядку «Зробити» дня 7. Тут вона розписана по кроках. Коду вимірів тут немає: лекція
показала прийоми на інших дослідах, а результат практики — ваш власний вимір.

**1. Дані.** Створіть масив з 10 мільйонів чисел і зв'язний список з тих самих чисел у тому самому порядку. Опишіть
вузол типом TypeScript. Навідні запитання:

- Скільки пам'яті займе масив з 10 мільйонів чисел? А список, якщо кожен вузол займає кілька десятків байтів? Якщо
  Node завершиться помилкою нестачі пам'яті, зменште розмір до 2–5 мільйонів і запишіть у журнал, з яким розміром
  працювали.
- Чим відрізняється масив, створений `Array.from({ length: n }, …)`, від `new Array(n)`, заповненого потім у циклі?
  Який вид елементів матиме кожен за блогом V8?

**2. Виміри.** Виміряйте час суми елементів масиву і списку по п'ять разів через `performance.now()` і візьміть
медіану. До запуску запишіть передбачення: у скільки разів список буде повільнішим?

**3. Перемішаний порядок.** Створіть масив номерів від 0 до `n − 1`, перемішайте його і пройдіть основний масив у
порядку цих номерів. Порівняйте з проходом підряд. Як перемішати масив так, щоб кожна перестановка була однаково
ймовірною? Пошукайте алгоритм Фішера–Єйтса.

**4. Розкиданий список.** Якщо список з кроку 2 виявився повільнішим за масив менше, ніж ви чекали, згадайте розділ
лекції про те, як V8 розміщує об'єкти. Побудуйте другий список з тими самими значеннями в тому самому порядку проходу,
але створюйте його вузли в перемішаному порядку, а потім зв'яжіть вказівниками. Виміряйте і його.

**5. Журнал вимірів.** Запишіть у `MEASUREMENTS.md` медіани і відношення до проходу масивом підряд, а також процесор,
на якому міряли, і розмір даних. Поясніть одним реченням кожне відношення словами «рядок кешу», «попередня вибірка» чи
«гонитва за вказівниками».

**6. Журнал.** Один рядок у `JOURNAL.md`: що стало зрозумілим і що ні.

## Перевірте себе

**1. Масив `Float64Array` починається з адреси 1000. За якою адресою лежить елемент з номером 5? А в `Int32Array` з
тим самим початком?**

<details><summary>Відповідь</summary>

`Float64` займає 8 байтів, тому елемент 5 лежить за адресою `1000 + 5 · 8 = 1040`. `Int32` займає 4 байти, тому `1000
+ 5 · 4 = 1020`. В обох випадках адреса обчислюється одним множенням і одним додаванням, тобто за `Θ(1)`.

</details>

**2. Скільки чисел `Float64` і скільки чисел `Int32` вміщує один рядок кешу у 64 байти?**

<details><summary>Відповідь</summary>

`64 / 8 = 8` чисел `Float64` і `64 / 4 = 16` чисел `Int32`. Тому в досліді з кроком саме крок 16 для `Int32Array`
торкається рівно одного числа в кожному рядку кешу.

</details>

**3. Чому прохід матриці по стовпцях повільніший, хоча кількість додавань та сама?**

<details><summary>Відповідь</summary>

Матриця лежить у пам'яті рядок за рядком. Сусідні елементи стовпця віддалені на `2048 · 8 = 16 384` байти, тому кожне
звернення потрапляє в новий рядок кешу, з якого використовується одне число з восьми. Поки програма дійде до
сусіднього стовпця, цей рядок кешу вже витіснено. Прохід по рядках використовує всі вісім чисел кожного завантаженого
рядка, і процесор підвантажує наступні рядки заздалегідь.

</details>

**4. Чим затримка пам'яті відрізняється від пропускної здатності, і яка з них обмежує прохід зв'язним списком?**

<details><summary>Відповідь</summary>

Затримка — час від запиту до відповіді, пропускна здатність — скільки даних пам'ять віддає за секунду. Прохід масивом
підряд обмежує пропускна здатність, бо запити відомі заздалегідь і йдуть паралельно. Прохід списком обмежує затримка:
адресу наступного вузла можна дізнатися, лише дочекавшись поточного, тому запити йдуть строго один за одним.

</details>

**5. Чому список у JavaScript, вузли якого створено підряд, може бути майже таким швидким, як масив?**

<details><summary>Відповідь</summary>

V8 розміщує нові об'єкти за наступною вільною адресою, тож вузли, створені один за одним, лежать у пам'яті поруч.
Прохід таким списком читає пам'ять майже підряд, і кеш та попередня вибірка працюють, як для масиву. Гонитва за
вказівниками стає дорогою, коли вузли розкидано по пам'яті.

</details>

**6. Алгоритм A робить `n` звернень до пам'яті підряд, алгоритм B — `n/4` звернень у випадкові місця великого масиву.
Модель RAM каже, що B у чотири рази швидший. Чи так буде насправді?**

<details><summary>Відповідь</summary>

Найімовірніше, ні. A використовує кожен завантажений рядок кешу повністю і читає наперед, тож на рядок кешу з 8 чи 16
чисел припадає одне завантаження. B на кожне звернення завантажує новий рядок кешу і чекає повну затримку пам'яті.
Якщо масив більший за кеш, B може виявитися повільнішим за A, хоча звернень у нього вчетверо менше. Правило
algorithmica: рахуйте рядки кешу, а не звернення.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| адреса | номер комірки пам'яті |
| довільний доступ | можливість одразу перейти до елемента з будь-яким номером |
| послідовний доступ | доступ, за якого до елемента доходять, проходячи всі попередні |
| вузол | окремий блок зв'язного списку зі значенням і вказівником на наступний вузол |
| вказівник | адреса іншого об'єкта, збережена як значення |
| оперативна пам'ять | основна пам'ять комп'ютера, велика і порівняно повільна |
| кеш | маленька швидка пам'ять у процесорі з копіями нещодавно використаних даних |
| рівні кешу L1, L2, L3 | рівні кешу від найближчого до процесора, найшвидшого й найменшого, до найдальшого |
| рядок кешу | блок пам'яті, яким дані переносяться в кеш; найчастіше 64 байти |
| попередня вибірка | завантаження даних у кеш наперед, коли процесор передбачає наступні адреси |
| затримка | час від запиту даних до їхнього приходу |
| пропускна здатність | обсяг даних, який пам'ять віддає за одиницю часу |
| гонитва за вказівниками | прохід, де кожну наступну адресу видно лише з щойно прочитаних даних |
| `Int32Array`, `Float64Array` | типізовані масиви JavaScript: числа фіксованого розміру, що лежать підряд у буфері |
| вид елементів | внутрішнє представлення масиву у V8, залежне від того, які значення в ньому лежать |
| медіана | середнє за порядком значення серед вимірів |
