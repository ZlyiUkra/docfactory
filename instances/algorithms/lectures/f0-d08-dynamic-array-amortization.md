# Лекція. День 8. Динамічний масив і амортизація

Ця лекція пояснює, як масив, що займає суцільний шматок пам'яті, може дешево рости, і вводить амортизований аналіз —
спосіб рахувати вартість послідовності операцій, а не однієї. Читання займе близько 55 хвилин. Під прикладами коду
стоїть справжній вивід з Node 24.22.

Учора ви бачили, що масив швидкий завдяки тому, що лежить суцільно, а вставка в нього дорога з тієї самої причини:
коли місце закінчилося, треба переїхати в більший шматок і скопіювати все. Проте `push` у JavaScript, `append` у
Python і `append` для зрізу в Go працюють швидко. Сьогодні з'ясуємо, як це можливо і що саме означають слова «у
середньому `O(1)`» у документації.

**Після лекції ви зможете пояснити:**

- як влаштований динамічний масив і чим місткість відрізняється від розміру;
- чому подвоєння місткості дає сталу вартість вставки в середньому, а збільшення на сталу кількість місць — ні;
- що таке амортизована вартість і чим вона відрізняється від середньої за випадковими входами;
- три способи амортизованого аналізу: сумування, податки й потенціал;
- чому масив треба стискати не тоді, коли він наполовину порожній, а пізніше;
- де в коді на JavaScript і React квадратичний час ховається за «незмінним» додаванням елемента.

## Список, який будували тридцять секунд

Розробник на React пише функцію, яка збирає список рядків таблиці з відповіді сервера. Він звик не змінювати масиви на
місці, бо React порівнює стан за посиланням, і тому додає елемент так:

```ts
// Додавання в кінець двома способами: новий масив щоразу і push.
function withSpread(n: number): number[] {
  let items: number[] = [];
  for (let i = 0; i < n; i++) items = [...items, i];   // копія всього масиву на кожному кроці
  return items;
}
function withPush(n: number): number[] {
  const items: number[] = [];
  for (let i = 0; i < n; i++) items.push(i);
  return items;
}
```

Запис `[...items, i]` створює **новий** масив: розгортання `...items` копіює в нього всі наявні елементи, а потім
додається `i`. Програма виміряла обидві функції, медіана п'яти запусків:

```
n = 10000: розгортання 136.4 мс, push 0.09 мс
n = 20000: розгортання 1409.4 мс, push 0.28 мс
n = 40000: розгортання 7377.5 мс, push 0.53 мс
```

Для 40 000 рядків перша функція працює понад сім секунд, друга — пів мілісекунди. Причина проста. На кроці з номером
`k` розгортання копіює `k` елементів, тож разом `0 + 1 + … + (n − 1) = n(n − 1)/2` копій: для 40 000 це близько 800
мільйонів. Це знову сума з дня 2. Час першої функції при подвоєнні `n` зростає більше ніж учетверо, бо до квадратичної
кількості копій додається ще й робота прибиральника сміття, який звільняє всі ці проміжні масиви.

Незмінність тут не винна: досить зібрати масив через `push` у локальній змінній і лише потім один раз передати його в
стан. Але звідки береться швидкість `push`? Адже масив лежить суцільно, і рано чи пізно місце теж закінчується.

## Динамічний масив

**Динамічний масив** тримає елементи у звичайному масиві фіксованого розміру, але виділяє його із запасом. Тому він
має дві величини:

- **розмір** — скільки елементів у ньому зараз лежить;
- **місткість** — скільки комірок виділено.

Поки розмір менший за місткість, вставка в кінець — це запис у наступну вільну комірку і збільшення розміру на 1,
тобто кілька кроків. Коли розмір дорівнює місткості, масив **переїжджає**: виділяє новий, більший масив, копіює туди
всі елементи і лише потім вставляє новий. Переїзд коштує стільки кроків, скільки елементів копіюється.

Grokking пояснює ту саму ідею як «тримати місця» в кінотеатрі: попросити більше місць, ніж треба, щоб друзі, які
прийдуть пізніше, сіли поруч. Головне запитання — **на скільки** збільшувати місткість при переїзді.

### Два правила росту

Розглянемо `n` вставок у порожній масив з місткістю 1 і порахуємо лише копіювання при переїздах, бо запис нового
елемента коштує один крок і разом дає `n`.

**Множити місткість на сталу, наприклад подвоювати.** Переїзди відбуваються, коли розмір дорівнює 1, 2, 4, 8 і так
далі. Кожен переїзд копіює стільки елементів, скільки зараз є. Для `n = 2ᵏ⁺¹` вставок копій:

```
1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1 < n
```

Цю суму ви довели індукцією в лекції дня 4. Отже, копій менше, ніж вставок, і в середньому на одну вставку припадає
менше одного копіювання.

**Додавати сталу кількість місць, наприклад `c`.** Переїзди відбуваються, коли розмір дорівнює `c`, `2c`, `3c`, …
Копій разом `c + 2c + 3c + …`, і для `n` вставок це приблизно `c · (n/c)² / 2 = n²/(2c)`. Сума квадратична: стала `c`
лише ділить її, але не змінює порядку росту.

Програма порахувала копії для мільйона вставок при чотирьох правилах росту:

```
×2     скопійовано       1048575, на одну вставку 1.05
×1.5   скопійовано       2099753, на одну вставку 2.10
+1000  скопійовано     499501000, на одну вставку 499.50
+1     скопійовано  499999500000, на одну вставку 499999.50
```

Обидва правила з множенням дають кілька копій на вставку, хоч би яким великим був масив. Правила з додаванням дають
сотні й сотні тисяч копій на вставку, і з ростом масиву ця кількість тільки росте. Навіть щедрий запас у тисячу місць
не рятує: він лише відкладає квадрат.

Множник 1,5 копіює вдвічі більше, ніж 2, але й тримає менше порожнього місця: після переїзду масив заповнений на дві
третини, а не наполовину. Курс MIT 6.006 підкреслює, що годиться будь-який сталий множник, більший за 1. Різні мови
вибирають різний. У рецитації MIT наведено формулу запасу зі старших джерел CPython: близько однієї восьмої розміру
плюс кілька місць. Вимір у Python 3.14 показує саме такий ріст: місткість списку змінюється як 4, 8, 16, 24, 32, 40,
52, 64, 76, 92, 108, 128, тобто для великих списків приблизно на восьму частину.

## Амортизована вартість

Окрема вставка в динамічний масив з подвоєнням може коштувати `Θ(n)`: це та вставка, яка спричинила переїзд. Чи
означає це, що `n` вставок коштують `Θ(n²)`? Ні: ми щойно порахували, що разом вони коштують `Θ(n)`. Оцінка «найгірша
операція, помножена на кількість операцій» тут правдива, але дуже груба.

CLRS пояснює потрібне поняття на прикладі спортзалу. Абонемент коштує 60 доларів на місяць плюс 3 долари за кожне
відвідування. Якщо ви ходили щодня всі 30 днів листопада, ви заплатили `60 + 3 · 30 = 150` доларів, тобто в середньому
5 доларів за день. Місячний платіж «розкладено» на дні по 2 долари. Так само дорогий переїзд можна розкласти на дешеві
вставки, які йому передували.

**Амортизована вартість** операції — це така вартість, що для **будь-якої** послідовності операцій сума амортизованих
вартостей не менша за справжню сумарну вартість. Курс MIT каже коротко: операція має амортизовану вартість `T(n)`,
якщо будь-які `k` операцій разом коштують не більше `k · T(n)`. Для вставки в динамічний масив з подвоєнням
амортизована вартість `O(1)`.

Головне, чим амортизована вартість **не** є: вона не є середньою за випадковими входами, як середній випадок
сортування вставками з дня 2. CLRS і Erickson обидва наголошують: імовірності тут немає. Амортизована оцінка — це
**гарантія для найгіршої послідовності операцій**. Ніякий вхід, ніяка послідовність вставок не змусить `n` вставок
коштувати більше за `O(n)`.

## Три способи амортизованого аналізу

Erickson і CLRS описують ті самі три способи. Покажемо їх на прикладі, який не є динамічним масивом, — на **двійковому
лічильнику**. Лічильник зберігає число бітами, і операція «збільшити на 1» перегортає біти: усі одиниці праворуч
стають нулями, а перший нуль стає одиницею. Наприклад, `0111 + 1 = 1000` змінює чотири біти.

Окреме збільшення може змінити багато бітів: для числа з `k` одиниць у кінці — `k + 1` бітів. Але здебільшого
змінюється один-два. Програма порахувала зміни бітів за `n` збільшень, починаючи з нуля:

```ts
// Двійковий лічильник: скільки бітів змінюється за n збільшень, починаючи з нуля.
function countFlips(n: number): { total: number; worst: number } {
  const bits: number[] = [];
  let total = 0, worst = 0;
  for (let step = 0; step < n; step++) {
    let i = 0, flips = 0;
    while (bits[i] === 1) { bits[i] = 0; i++; flips++; }   // переноси: одиниці стають нулями
    bits[i] = 1; flips++;                                 // перший нуль стає одиницею
    total += flips;
    worst = Math.max(worst, flips);
  }
  return { total, worst };
}
```

Масив `bits` зберігає біти від молодшого: `bits[0]` — одиниці, `bits[1]` — двійки. Порожні комірки масиву дорівнюють
`undefined`, і умова `bits[i] === 1` для них хибна, тож вони поводяться як нулі. Вивід:

```
n = 16: усього змін 31, у середньому 1.938, найбільше за раз 5
n = 1000: усього змін 1994, у середньому 1.994, найбільше за раз 10
n = 1024: усього змін 2047, у середньому 1.999, найбільше за раз 11
n = 1000000: усього змін 1999993, у середньому 2.000, найбільше за раз 20
```

Окрема операція доходить до 20 змін, але в середньому їх менше двох. Ось три способи це довести.

### Сумування

Порахувати загальну вартість будь-якої послідовності з `n` операцій і поділити на `n`. CLRS називає це **агрегатним
аналізом**. Для лічильника: молодший біт змінюється при кожному збільшенні, тобто `n` разів; наступний — через раз,
`⌊n/2⌋` разів; наступний — `⌊n/4⌋` разів. Разом

```
n + ⌊n/2⌋ + ⌊n/4⌋ + … < n + n/2 + n/4 + … = 2n
```

Отже, амортизована вартість збільшення менша за 2. Erickson дає і точну формулу: `2n` мінус кількість одиниць у
двійковому записі `n`. Для `n = 1000`, у якого шість одиниць, це `2000 − 6 = 1994`, як і надрукувала програма.

### Податки

Цей спосіб CLRS називає **методом обліку**, а Erickson — **податками**. Кожна операція платить фіксовану суму. Частина
суми одразу оплачує роботу операції, а решта лишається **кредитом**, прив'язаним до певної частини структури, щоб
оплатити майбутню дорогу роботу. Треба лише показати, що кредиту ніколи не бракує.

Для лічильника: кожне збільшення платить 2 долари. Один долар оплачує перетворення нуля на одиницю, яке трапляється
рівно один раз за збільшення. Другий долар лягає на цю одиницю як кредит. Коли пізніше ця одиниця стане нулем, вона
заплатить за себе своїм доларом. Отже, кожне перетворення одиниці на нуль уже оплачене, і 2 долари за збільшення
покривають усе.

Для динамічного масиву з подвоєнням CLRS бере 3 долари за вставку: один оплачує запис нового елемента, другий лягає на
цей елемент, щоб оплатити його копіювання при наступному переїзді, а третій лягає на один зі «старих» елементів, які
були в масиві одразу після попереднього переїзду, і в яких власного кредиту вже немає. Коли масив заповниться, у
кожного елемента буде по долару на переїзд. Звідси амортизована вартість вставки — не більше 3.

### Потенціал

Найзагальніший спосіб. Вводять **потенціал** — число `Φ`, яке залежить від стану всієї структури, дорівнює нулю на
початку і ніколи не стає від'ємним. Амортизована вартість операції — це її справжня вартість плюс зміна потенціалу:

```
амортизована = справжня + (Φ після − Φ до)
```

Якщо скласти амортизовані вартості всіх операцій, зміни потенціалу скорочуються, і лишається справжня сума плюс `Φ`
наприкінці мінус `Φ` на початку. Оскільки `Φ` на початку нуль, а наприкінці невід'ємний, сума амортизованих вартостей
не менша за справжню. Потенціал — це накопичений кредит, тільки записаний однією формулою для всієї структури.

Для лічильника потенціал — кількість одиниць у ньому. Збільшення, яке перетворює `t` одиниць на нулі і один нуль на
одиницю, має справжню вартість `t + 1`, а потенціал змінюється на `1 − t`. Амортизована вартість `(t + 1) + (1 − t) =
2`, хоч би яким було `t`.

Erickson дає пораду щодо вибору потенціалу: добрий потенціал трохи росте на дешевих операціях і сильно падає на
дорогих. Загального рецепта, як його знайти, немає, крім спроб.

## Стискання: чому не наполовину

Якщо з динамічного масиву видаляють багато елементів, він займає багато порожньої пам'яті, і його варто стиснути.
Здається природним стискати вдвічі, щойно масив заповнений менше ніж наполовину, — симетрично до подвоєння. CLRS
показує, чому це погана ідея.

Нехай масив щойно заповнився повністю. Тепер чергуємо операції: вставка, видалення, видалення, вставка, вставка,
видалення, видалення і так далі. Перша вставка подвоює масив, і він стає заповненим трохи більше ніж наполовину. Два
видалення роблять його заповненим менше ніж наполовину, і він стискається. Дві вставки знову його переповнюють. Кожна
пара операцій спричиняє переїзд вартістю `Θ(n)`, тобто `n` операцій коштують `Θ(n²)`.

Програма промоделювала саме таку послідовність з 4000 операцій для масиву з 512 елементів і порахувала копії:

```
стискати нижче 1/2: 1023000 копій за 4000 операцій
стискати нижче 1/4: 512 копій за 4000 операцій
```

Вихід, який пропонують і CLRS, і MIT 6.006, — стискати вдвічі, лише коли масив заповнений менше ніж на **чверть**.
Після переїзду в будь-який бік масив заповнений рівно наполовину, і до наступного переїзду треба зробити `Θ(n)`
операцій, які його й оплатять. Порожньої пам'яті тоді не більше трьох чвертей, тобто вона обмежена сталою частиною.

## Амортизація в мовах програмування

| Операція | Вартість | Чому |
|----------|----------|------|
| `push`, `pop` у кінці масиву JavaScript | амортизовано `O(1)` | динамічний масив |
| `shift`, `unshift` | до `O(n)` | специфікація ECMA-262 описує `shift` як перенесення кожного наступного елемента на позицію ліворуч |
| `[...items, x]`, `items.concat([x])` | `O(n)` | створюється новий масив і копіюються всі елементи |
| `splice(i, 0, x)` у середині | `O(n)` | треба зсунути всі елементи після `i` |
| `append` у Python, `append` для зрізу Go | амортизовано `O(1)` | динамічний масив з множником росту |

Курс MIT формулює правило для Python: `append` і `pop` амортизовано `O(1)`, а решта операцій можуть бути `O(n)`. Для
JavaScript воно таке саме.

| «Яка складність `push`?» | «Амортизовано `O(1)`. Окремий `push` може коштувати `O(n)`, коли масив переїжджає, але будь-які `n` вставок разом коштують `O(n)`» |
| «Чому місткість подвоюють, а не збільшують на 100?» | «Зі сталим додатком копій за `n` вставок квадратична кількість, з множником — лінійна: сума геометричної прогресії менша за подвоєний останній член» |
| «Амортизовано — це в середньому?» | «Середнє за послідовністю операцій, а не за випадковими входами. Це гарантія для найгіршої послідовності» |
| «Коли амортизація не годиться?» | «Коли важить кожна окрема операція: у системах реального часу чи в інтерфейсі, де одна довга пауза помітна. Тоді потрібна оцінка найгіршої операції» |
| «Як ви додаєте елементи в стан React у циклі?» | «Збираю в локальний масив через `push`, а в стан передаю один раз. Розгортання на кожному кроці квадратичне» |

BCtCI додає: після цієї глави книжка всюди вживає амортизований аналіз для структур даних, тож на співбесіді варто
впевнено пояснювати, чому `append` — `O(1)` амортизовано, а не просто `O(1)`.

## Типові хибні уявлення

**«Амортизовано `O(1)` означає, що кожна операція швидка».** Окрема операція може бути `Θ(n)`. Амортизація обіцяє
лише, що дорогі операції рідкісні настільки, що разом з дешевими дають лінійну суму.

**«Амортизована вартість — це середня за випадковими входами».** Імовірності тут немає. Оцінка правдива для найгіршої
послідовності операцій, яку можна підібрати.

**«Великий сталий запас вирішує проблему».** Запас у тисячу місць робить вставки в 1000 разів дешевшими за запас в
одне місце, але квадратична сума лишається квадратичною: для мільйона вставок — пів мільярда копій.

**«Стискати треба симетрично до росту, наполовину».** Тоді операції біля межі переїжджають щоразу, і амортизована
вартість стає `Θ(n)`. Межа стискання мусить бути нижчою, наприклад одна чверть.

**«Незмінні оновлення в JavaScript безкоштовні».** Кожне `[...items, x]` копіює весь масив. У циклі це квадратичний
час.

**«Амортизований аналіз потрібен лише для масивів».** Ті самі способи пояснюють двійковий лічильник, хеш-таблиці з
переїздом, об'єднання множин і splay-дерева, до яких план ще дійде.

## Практика

Практика дня описана в плані, у рядку «Зробити» дня 8. Тут вона розписана по кроках. Класу `DynamicArray` тут немає:
лекція пояснила механізм і порахувала копії для інших правил росту, а клас і ваші числа — ваша частина роботи.

**1. Клас `DynamicArray<T>`.** Файл `src/dynamic-array.ts`. Методи `push(x)`, `get(i)`, `set(i, x)`, поле чи метод для
розміру і лічильник скопійованих елементів. Навідні запитання:

- Щоб модель була чесною, внутрішнє сховище має бути масивом **фіксованого** розміру. Як створити масив заданої
  довжини і ніколи не викликати для нього `push`? Що за MDN робить `new Array(n)` і яким за блогом V8 буде вид
  елементів такого масиву? Чи не зручніше для чисел узяти типізований масив?
- Що мають робити `get` і `set` для номера поза межами розміру, а не місткості? Зверніться до лекції дня 1 про рішення
  для недопустимого входу.
- Як передати правило росту в конструктор, щоб тим самим класом перевірити і подвоєння, і ріст на 10 місць?
- Яка початкова місткість? Чи важить вона для результату?

**2. Тести.** Порожній масив, один елемент, `get` після переїзду повертає ті самі значення, `set` поза межами
поводиться за вашим рішенням.

**3. Виміри.** Додайте 1024 елементи з подвоєнням і з ростом на 10 місць і запишіть обидві суми копій у
`MEASUREMENTS.md`. До запуску передбачте суму для подвоєння формулою з лекції, а для росту на 10 — сумою арифметичної
прогресії. Скільки разів переїжджав масив у кожному випадку?

**4. Пояснення.** Одним-двома реченнями в журналі вимірів поясніть різницю сумою геометричної прогресії і сумою
арифметичної.

**5. Журнал.** Один рядок у `JOURNAL.md`: що стало зрозумілим і що ні. Це останній день фази 0, тому перегляньте

## Перевірте себе

**1. Динамічний масив з подвоєнням починає з місткості 1. Скільки переїздів і скільки копій буде за 100 вставок?**

<details><summary>Відповідь</summary>

Переїзди відбуваються, коли розмір дорівнює 1, 2, 4, 8, 16, 32 і 64: сім переїздів. Копій `1 + 2 + 4 + 8 + 16 + 32 +
64 = 127`. Після останнього переїзду місткість 128, і решта вставок до 100 переїздів не потребує.

</details>

**2. Чому двійковий лічильник за `n` збільшень змінює менше `2n` бітів, хоча окреме збільшення може змінити `log₂ n`
бітів?**

<details><summary>Відповідь</summary>

Біт з номером `i` змінюється раз на `2ⁱ` збільшень: молодший щоразу, наступний через раз і так далі. Разом `n + n/2 +
n/4 + … < 2n`. Дорогі збільшення, що змінюють багато бітів, трапляються рідко: збільшення, яке змінює `k` бітів, буває
лише раз на `2ᵏ⁻¹` збільшень.

</details>

**3. Чим амортизована вартість відрізняється від середньої вартості з дня 2, де сортування вставками на випадковому
масиві робило близько `n²/4` порівнянь?**

<details><summary>Відповідь</summary>

Середній випадок дня 2 — середнє за випадковими входами: для конкретного невдалого входу, наприклад зворотного масиву,
сортування робить удвічі більше. Амортизована вартість — гарантія для будь-якої послідовності операцій: немає такої
послідовності `n` вставок у динамічний масив з подвоєнням, яка коштувала б більше за `O(n)`. Імовірність в амортизації
не бере участі.

</details>

**4. Динамічний масив росте множенням на 3. Скільки копій буде за `n` вставок, і яка амортизована вартість?**

<details><summary>Відповідь</summary>

Переїзди при розмірах 1, 3, 9, 27, …, і сума копій `1 + 3 + 9 + … + 3ᵏ = (3ᵏ⁺¹ − 1)/2`. Найбільший доданок `3ᵏ` не
перевищує `n`, тож сума менша за `1,5n`. Амортизована вартість `O(1)`. Ціна — більше порожнього місця: одразу після
переїзду масив заповнений лише на третину.

</details>

**5. Чому стискання при заповненні менше ніж наполовину може зробити операції дорогими, а при заповненні менше ніж на
чверть — ні?**

<details><summary>Відповідь</summary>

При межі в половину масив після переїзду в будь-який бік стоїть прямо на межі іншого переїзду: одна-дві операції
повертають його назад, і кожна пара операцій коштує `Θ(n)`. При межі в чверть після будь-якого переїзду масив
заповнений наполовину, і до наступного переїзду треба `Θ(n)` вставок або видалень, які разом оплачують копіювання.
Тоді амортизована вартість стала.

</details>

**6. Знайдіть квадратичний час у цьому коді і перепишіть його лінійно, не змінюючи масив `rows` ззовні.**

```ts
function addTotals(rows: readonly number[][]): number[][] {
  let result: number[][] = [];
  for (const row of rows) {
    const total = row.reduce((sum, x) => sum + x, 0);
    result = [...result, [...row, total]];
  }
  return result;
}
```

<details><summary>Відповідь</summary>

`result = [...result, …]` копіює весь накопичений результат на кожному рядку: `0 + 1 + … + (n − 1)` копій рядків,
тобто `Θ(n²)` для `n` рядків. Копія `[...row, total]` теж копіює, але лише один рядок і лише раз, тож разом вона дає
лінійну кількість роботи від загального обсягу даних. Виправлення: оголосити `const result: number[][] = []` і робити
`result.push([...row, total])`. Масив `rows` і його рядки при цьому не змінюються, бо `push` змінює лише новий масив
`result`, який функція сама створила.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| динамічний масив | масив, що виділяє місце із запасом і переїжджає в більший, коли запас вичерпано |
| розмір | кількість елементів, що зараз лежать у масиві |
| місткість | кількість виділених комірок |
| переїзд | виділення нового масиву і копіювання туди всіх елементів |
| множник росту | у скільки разів збільшується місткість при переїзді |
| амортизована вартість | вартість, сума якої для будь-якої послідовності операцій не менша за справжню сумарну вартість |
| агрегатний аналіз, сумування | загальна вартість `n` операцій, поділена на `n` |
| метод обліку, податки | кожна операція платить фіксовану суму, а надлишок зберігається як кредит на майбутні дорогі операції |
| кредит | заздалегідь оплачена робота, прив'язана до частини структури |
| потенціал | число, що залежить від стану всієї структури: накопичений кредит, записаний формулою |
| двійковий лічильник | число, збережене бітами, з операцією «збільшити на 1» |
| коефіцієнт заповнення | відношення розміру до місткості |
| розгортання `...` | запис JavaScript, що копіює елементи масиву в новий масив |
