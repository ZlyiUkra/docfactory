# Лекція. Фаза 1, день 2. Стеки й черги

Ця лекція пояснює дві найпростіші структури, що визначають порядок обробки: стек, який віддає останнє додане, і чергу,
яка віддає найдавніше. Читання займе близько 50 хвилин. Під прикладами коду стоїть справжній вивід з Node 24.22.

Учора ви бачили, що однозв'язний список із головою і хвостом уже вміє бути і стеком, і чергою. Сьогодні з'ясуємо, як
зробити те саме на масиві, чому для стека це очевидно, а для черги ні, і що насправді коштує `shift` у JavaScript.

**Після лекції ви зможете пояснити:**

- що таке стек і черга як інтерфейси і чим інтерфейс відрізняється від реалізації;
- чому порядок обробки впливає на найдовше очікування, хоча середнє лишається тим самим;
- чому стек на масиві очевидний, а черга на масиві з `shift` стає квадратичною;
- як кільцевий буфер робить чергу на масиві сталою за часом і де в ньому ховаються помилки;
- чому остача від ділення від'ємного числа в JavaScript від'ємна і де це ламає код;
- як черга з двох стеків отримує амортизовано сталу вартість.

## Черга, яка повільнішала сама собою

Розробник пише обробник завдань: завдання приходять, лягають у кінець масиву через `push` і забираються з початку
через `shift`. На тестах з кількома сотнями завдань усе летить, а на справжньому навантаженні обробник раптом
повільнішає в десятки разів. Програма нижче вимірює, скільки коштує одна пара `push` + `shift`, коли в черзі вже
стоїть `n` завдань:

```ts
// Ціна однієї пари push + shift залежно від довжини черги. Медіана п'яти запусків по 20 000 пар.
for (const n of [1_000, 8_000, 15_000, 16_000, 17_000, 32_000, 64_000]) {
  const ms: number[] = [];
  for (let r = 0; r < 5; r++) {
    const q: number[] = [];
    for (let i = 0; i < n; i++) q.push(i);
    let sum = 0;
    const t0 = performance.now();
    for (let i = 0; i < 20_000; i++) { q.push(i); sum += q.shift()!; }
    ms.push(performance.now() - t0);
    if (sum < 0) console.log(sum);
  }
  console.log(`довжина ${String(n).padStart(6)}: ${(median(ms) * 1e6 / 20_000).toFixed(0).padStart(6)} нс на пару`);
}
```

```
довжина   1000:    123 нс на пару
довжина   8000:    417 нс на пару
довжина  15000:   1750 нс на пару
довжина  16000:   1967 нс на пару
довжина  17000:   2095 нс на пару
довжина  32000:   5061 нс на пару
довжина  64000:  12488 нс на пару
```

Перевірка `if (sum < 0)` ніколи не спрацьовує. Вона потрібна лише для того, щоб рушій не викинув обчислення суми як
непотрібне. Функція `median` та сама, що в лекціях фази 0.

Від 16 000 до 64 000 довжина зросла вчетверо, і ціна пари теж зросла приблизно вчетверо. Отже, один `shift` коштує
`Θ(n)`. Специфікація ECMA-262 описує `shift` саме так: забрати перший елемент і зсунути кожен наступний на одну
позицію ліворуч. Процесор зсуває пам'ять дуже швидко, близько 0,2 наносекунди на елемент, тому на коротких чергах
цього не видно. Через це помилка й пережила тести.

Коли черга спершу наповнюється, а потім спорожнюється, кожен `shift` зсуває все, що лишилося, і разом виходить
квадратична кількість зсувів. Друга програма робить `n` разів `push`, а потім `n` разів `shift`:

```ts
// Черга на масиві: спершу n разів push, потім n разів shift. Медіана п'яти запусків.
for (const n of [10_000, 20_000, 50_000, 100_000, 200_000]) {
  const t = time(() => {
    const q: number[] = [];
    for (let i = 0; i < n; i++) q.push(i);
    let sum = 0;
    while (q.length > 0) sum += q.shift()!;
    if (sum < 0) console.log(sum);
  });
  console.log(`n = ${n}: усе push, потім усе shift ${t.toFixed(1)} мс`);
}
```

```
n = 10000: усе push, потім усе shift 2.5 мс
n = 20000: усе push, потім усе shift 30.0 мс
n = 50000: усе push, потім усе shift 215.9 мс
n = 100000: усе push, потім усе shift 940.5 мс
n = 200000: усе push, потім усе shift 4380.6 мс
```

Для 200 000 завдань чотири з половиною секунди йде на те, що мало б займати мілісекунди. До кінця лекції ви знатимете
два способи це виправити.

## Інтерфейс і реалізація

Стек і черга — це насамперед **інтерфейси**, тобто домовленості про те, які операції є і що вони роблять. Як саме
елементи лежать у пам'яті, вирішує **реалізація**, і одна домовленість може мати кілька реалізацій.

**Стек** віддає останній доданий елемент. Цей порядок називають LIFO, від англійського «last in, first out»: останнім
прийшов — першим пішов. Операції стека — `push` (покласти нагору) і `pop` (зняти верхній). Часто є ще `peek`
(подивитися на верхній, не знімаючи) і `size`. CLRS порівнює стек зі стопкою тарілок у їдальні: доступна лише верхня.

**Черга** віддає найдавніший елемент. Цей порядок називають FIFO, «first in, first out»: першим прийшов — першим
пішов. Додавання в кінець черги називають `enqueue`, вилучення з початку — `dequeue`. У JavaScript ті самі дії роблять
`push` і `shift`, у Python — `append` і `popleft`.

Skiena називає обидві структури **контейнерами**: вони зберігають і віддають елементи незалежно від їхнього вмісту, а
порядок залежить лише від порядку додавання. Цим вони відрізняються від словників, де елемент шукають за ключем.

Де ці порядки трапляються в програмах:

- стек викликів функцій з лекції дня 5 фази 0 — це стек: функція, викликана останньою, закінчується першою;
- кнопка «назад» у браузері і скасування дії в редакторі — стек;
- черга завдань і черга мікрозавдань у циклі подій JavaScript — черги: MDN пише, що завдання і мікрозавдання ставлять
  у чергу і виконують у свій час, а цикл подій виконує мікрозавдання, доки їхня черга не спорожніє;
- пошук у ширину, до якого план дійде у фазі 3, обходить граф саме чергою, а пошук у глибину — стеком.

### Чесність черги

Skiena зауважує, що порядок обробки не змінює середнього очікування, але змінює найдовше. Розберемо приклад. Сервер
обробляє одне завдання за хвилину. У момент 0 приходять завдання A і B, а далі щохвилини приходить ще одне: C у момент
1, D у момент 2, E у момент 3.

| Хвилина | Є на початку хвилини (FIFO) | Обробляється (FIFO) | Є на початку хвилини (LIFO) | Обробляється (LIFO) |
|---------|----------------|---------------------|----------------|---------------------|
| 0 | A, B | A | A, B | B |
| 1 | B, C | B | A, C | C |
| 2 | C, D | C | A, D | D |
| 3 | D, E | D | A, E | E |
| 4 | E | E | A | A |

З чергою кожне завдання, крім A, чекає 1 хвилину: разом 4 хвилини, найдовше очікування — 1 хвилина. Зі стеком B, C, D
і E не чекають зовсім, а A чекає 4 хвилини. Разом знову 4 хвилини, але найдовше очікування вчетверо більше. Якби нові
завдання приходили без кінця, A не дочекалося б ніколи. Саме тому там, де важить справедливість, ставлять чергу.

## Стек на масиві

Стек на динамічному масиві з учорашньої лекції фази 0 нічого не вимагає: `push` додає в кінець, `pop` знімає з кінця,
обидві операції коштують амортизовано `O(1)`. CLRS показує той самий стек на масиві фіксованого розміру з номером
верхнього елемента `S.top`. Тоді стек може **переповнитися** (overflow), коли масив скінчився, і **спустошитися**
(underflow), коли з порожнього стека знімають елемент.

У JavaScript окремий клас стека зазвичай не пишуть: звичайний масив з `push` і `pop` уже є стеком. BCtCI радить на
співбесіді так і робити, назвавши змінну `stack`.

Ось задача, яку стек розв'язує природно. У **зворотному польському записі** операція стоїть після своїх операндів: `3
4 + 2 *` означає `(3 + 4) * 2`. Дужки не потрібні, бо порядок обчислення задає сам запис. Обчислюють такий вираз
стеком: число кладуть у стек, а операція знімає два верхні числа і кладе результат.

```ts
// Обчислення виразу в зворотному польському записі: операнди йдуть перед операцією.
export function evalRpn(tokens: string[]): number {
  const stack: number[] = [];
  for (const t of tokens) {
    if (t === "+" || t === "-" || t === "*" || t === "/") {
      const right = stack.pop();          // верхнє число — правий операнд
      const left = stack.pop();
      if (left === undefined || right === undefined) throw new Error(`бракує операндів для ${t}`);
      stack.push(t === "+" ? left + right : t === "-" ? left - right : t === "*" ? left * right : left / right);
    } else {
      stack.push(Number(t));
    }
  }
  if (stack.length !== 1) throw new Error(`після обчислення в стеку ${stack.length} чисел`);
  return stack[0]!;
}
console.log(evalRpn("3 4 + 2 *".split(" ")));      // (3 + 4) * 2
console.log(evalRpn("5 1 2 + 4 * + 3 -".split(" ")));   // 5 + (1 + 2) * 4 - 3
try { evalRpn("1 +".split(" ")); } catch (e) { console.log((e as Error).message); }
try { evalRpn("1 2".split(" ")); } catch (e) { console.log((e as Error).message); }
```

```
14
14
бракує операндів для +
після обчислення в стеку 2 чисел
```

Простежимо другий вираз:

| Лексема | Стек після неї |
|---------|----------------|
| 5 | 5 |
| 1 | 5 1 |
| 2 | 5 1 2 |
| + | 5 3 |
| 4 | 5 3 4 |
| * | 5 12 |
| + | 17 |
| 3 | 17 3 |
| - | 14 |

Дві перевірки в коді відповідають двом помилкам, які BCtCI називає найчастішими в задачах на стеки й черги. Перша —
знімати з порожнього стека, не перевіривши, чи він порожній. Друга — забути про елементи, що лишилися в стеку після
циклу. Метод `pop` у JavaScript на порожньому масиві не кидає помилку, а повертає `undefined`, тому перевірку треба
писати самому. Порядок `right`, потім `left` теж важливий: для `-` і `/` переставлені операнди дають інший результат.

Перевірка дужок з практики дня влаштована схоже: відкривна дужка лягає в стек, а закривна має збігтися з верхньою.

## Черга на масиві

З чергою складніше, бо вона працює з обома кінцями. Якщо додавати в кінець масиву, то забирати доведеться з початку, і
кожне вилучення зсуває всі елементи. Якщо додавати на початок, зсуває вже кожна вставка. Ви бачили ціну цього вище.

### Номер голови замість зсуву

Morin пропонує спершу уявити нескінченний масив. Тоді черга — це номер голови `j` і кількість елементів `n`, а
елементи лежать у комірках від `j` до `j + n − 1`. Щоб забрати елемент, досить збільшити `j` на одиницю: нічого не
зсувається.

```ts
// Черга без зсувів: номер голови замість shift. Масив лише росте.
class IndexQueue<T> {
  private items: T[] = [];
  private head = 0;                         // номер першого елемента черги в масиві
  push(x: T): void { this.items.push(x); }
  shift(): T | undefined {
    if (this.head === this.items.length) return undefined;
    return this.items[this.head++];         // нічого не зсуваємо, лише рухаємо номер голови
  }
  get size(): number { return this.items.length - this.head; }
  get slots(): number { return this.items.length; }
}
```

Той самий вимір, що на початку лекції:

```
довжина 1000: 83 нс на пару, у черзі 1000, комірок у масиві 21000
довжина 64000: 29 нс на пару, у черзі 64000, комірок у масиві 84000
```

Ціна пари більше не залежить від довжини черги. Але подивіться на останній стовпець: у черзі 1000 елементів, а масив
тримає 21 000 комірок. Комірки перед головою вже нікому не потрібні, але масив їх не звільняє. Програма, що місяцями
обробляє події, з такою чергою з'їсть усю пам'ять. Нескінченного масиву немає.

### Кільцевий буфер

Вихід — масив сталої довжини, по якому номер іде по колу. Коли номер доходить до кінця масиву, він повертається на
початок. Morin порівнює це з годинником: 10 година плюс 5 годин — це 3 година, бо після 12 лічба починається знову.
Так працює **остача від ділення**: `(10 + 5) % 12 = 3`. Масив, по якому ходять по колу, називають **кільцевим
буфером**.

Черга на кільцевому буфері зберігає три числа: номер голови `head`, кількість елементів `size` і довжину масиву
`capacity`. Елемент з номером `k` у черзі лежить у комірці `(head + k) % capacity`. Новий елемент лягає в комірку
`(head + size) % capacity`, а вилучення збільшує `head` на одиницю по колу.

Простежимо масив на 4 комірки. Крапка позначає порожню комірку, квадратні дужки — голову:

| Операція | Комірки 0 1 2 3 | `head` | `size` |
|----------|-----------------|--------|--------|
| порожня черга | `. . . .` | 0 | 0 |
| додати a, b, c | `[a] b c .` | 0 | 3 |
| забрати (a) | `. [b] c .` | 1 | 2 |
| забрати (b) | `. . [c] .` | 2 | 1 |
| додати d | `. . [c] d` | 2 | 2 |
| додати e | `e . [c] d` | 2 | 3 |
| додати f | `e f [c] d` | 2 | 4 |

Елемент `e` ліг у комірку `(2 + 2) % 4 = 0`, тобто перейшов через кінець масиву. Черга `c, d, e, f` лежить у масиві
так: `e f c d`. Тепер масив повний. Коли прийде наступний елемент, черга має вирости.

**Головна пастка росту.** Новий масив удвічі довший, але копіювати старий масив комірку в комірку не можна: черга `c,
d, e, f` лежить як `e f c d`, і після простого копіювання голова на комірці 2 показувала б на `c`, за ним ішли б `d`,
порожні комірки 4–7 і лише потім, після переходу через кінець нового масиву, `e` і `f`. Елементи треба копіювати в
порядку черги: від голови, `size` штук, кожен з комірки `(head + k) % capacity`. Після цього голова стоїть на комірці
0. Morin робить саме так. Тест, що перевіряє перехід через кінець масиву і ріст у такий момент, ловить цю помилку
одразу.

Ріст удвічі коштує те саме, що в динамічного масиву вчора: амортизовано `O(1)` на операцію. CLRS показує простіший
варіант без росту: масив фіксованого розміру, і черга вміщує на один елемент менше, ніж комірок. Так CLRS розрізняє
порожню і повну чергу за двома номерами, головою і хвостом, без лічильника.

### Остача від ділення від'ємного числа

У деки, тобто черги з двома відкритими кінцями, голова іноді рухається назад: `head − 1`. У JavaScript це несподівано
ламається:

```ts
// Остача від ділення від'ємного числа в JavaScript.
const capacity = 8;
const head = 0;
console.log((head - 1) % capacity);                    // крок назад від комірки 0
console.log((head - 1 + capacity) % capacity);
console.log(((head - 1) % capacity + capacity) % capacity);
```

```
-1
7
7
```

Оператор `%` у JavaScript бере знак від діленого, тому `−1 % 8` дорівнює `−1`, а не `7`. Комірки з номером `−1` у
масиві немає, і запис `items[-1] = x` створить у масиві властивість з назвою `"-1"`, а не заповнить останню комірку.
Morin визначає `mod` інакше: результат завжди від `0` до `m − 1`. Щоб отримати такий результат у JavaScript, до
від'ємного числа додають довжину масиву перед діленням. Python і Go тут різні: у Python `-1 % 8` дорівнює `7`, а в Go
`-1 % 8` дорівнює `-1`, як у JavaScript.

## Черга з двох стеків

Є ще одна реалізація черги, у якій немає ні зсувів, ні кільця. Беруть два стеки. Перший, `inbox`, приймає нові
елементи. Другий, `outbox`, віддає їх. Коли `outbox` порожній, а треба щось віддати, увесь `inbox` перекладають в
`outbox` по одному елементу. Перекладання перевертає порядок, тож найдавніший елемент опиняється нагорі `outbox`.

```ts
// Черга з двох стеків: inbox приймає, outbox віддає. Рахуємо, скільки разів елементи перекладали.
class TwoStackQueue<T> {
  private inbox: T[] = [];
  private outbox: T[] = [];
  moved = 0;                                // скільки елементів переклали з inbox в outbox
  worst = 0;                                // найбільше перекладань за одну операцію
  push(x: T): void { this.inbox.push(x); }
  shift(): T | undefined {
    if (this.outbox.length === 0) {
      const k = this.inbox.length;
      while (this.inbox.length > 0) this.outbox.push(this.inbox.pop()!);   // порядок перевертається
      this.moved += k;
      this.worst = Math.max(this.worst, k);
    }
    return this.outbox.pop();
  }
}
```

Програма виконала мільйон випадкових операцій: з імовірністю 0,55 — `push`, інакше — `shift`. Вона перевіряла, що
елементи виходять у порядку надходження:

```
push 558615, shift 441377, порядок FIFO збережено: true
перекладено 523270, тобто 0.94 на один push; найдовше перекладання 109794
```

Одна операція переклала майже 110 тисяч елементів, тобто окремий `shift` може коштувати `Θ(n)`. Але разом за мільйон
операцій перекладено менше елементів, ніж їх надійшло. Це не випадковість, а гарантія: кожен елемент кладуть в `inbox`
один раз, перекладають один раз і знімають з `outbox` один раз. Отже, на кожен елемент припадає не більше трьох дій зі
стеками, хоч би якою була послідовність операцій. Це амортизована оцінка з лекції дня 8 фази 0, отримана методом
податків: кожен `push` заздалегідь платить за майбутнє перекладання свого елемента.

Цю конструкцію просить придумати вправа в розділі 10.1 CLRS. Morin у розділі `DualArrayDeque` будує з двох стеків іншу
структуру, деку. Там стеки стоять спиною один до одного і щоразу, коли один стає більш ніж утричі більшим за інший,
елементи розподіляються між ними порівну.

## Стеки й черги в мовах

| Мова | Стек | Черга |
|------|------|-------|
| JavaScript | масив: `push`, `pop` | вбудованої немає; `shift` коштує `Θ(n)`, тому чергу пишуть самі |
| Python | список: `append`, `pop` | `collections.deque`: `append`, `popleft` |
| Go | зріз: `append` і `s[:len(s)-1]` | зріз з `q[1:]` або `container/list` |

BCtCI у примітці до глави про стеки й черги пише, що в JavaScript справи гірші, ніж у Python, бо вбудованої черги
немає зовсім. Чергу Go на зрізі план розбере в день 13, коли перекладатиме структури фази на Go.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Чим стек відрізняється від черги? | Стек віддає останнє додане (LIFO), черга — найдавніше (FIFO). |
| Чому не можна робити чергу масивом з `shift`? | `shift` зсуває всі елементи і коштує `Θ(n)`; черга з `n` елементів стає квадратичною. |
| Як зробити чергу на масиві за `O(1)`? | Кільцевий буфер: номер голови і розмір, номери йдуть по колу через остачу від ділення, при заповненні масив подвоюється з копіюванням у порядку черги. |
| Як зробити чергу з двох стеків і скільки це коштує? | Один стек приймає, другий віддає, перекладання — коли другий порожній. Окрема операція до `Θ(n)`, амортизовано `O(1)`. |
| Які помилки найчастіші? | Зняти з порожнього стека без перевірки і забути про елементи, що лишилися після циклу. |
| Де стек трапляється сам собою? | Виклики функцій, рекурсія, «назад» у браузері, скасування дій, перевірка дужок, обчислення виразів. |

## Типові помилки

**Вважати `shift` дешевим, бо `push` дешевий.** На коротких масивах різниці не видно, і помилка проходить тести. На
черзі з десятків тисяч елементів вона стає квадратичною.

**Копіювати кільцевий буфер при рості комірка в комірку.** Черга, що перейшла через кінець масиву, після такого
копіювання розривається порожніми комірками.

**Брати остачу від від'ємного числа без поправки.** У JavaScript `−1 % 8` дорівнює `−1`.

**Знімати з порожнього стека.** У JavaScript `pop` поверне `undefined` без помилки, і `undefined` піде в обчислення
далі. TypeScript з `strict` підкаже, що тип результату `T | undefined`, якщо не глушити його знаком `!`.

**Думати, що номер голови без кільця — розв'язок.** Він прибирає зсуви, але масив росте без меж.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: стек показано на польському записі, а кільцевий буфер —
таблицею без коду.

**1. `RingQueue<T>`.** Методи `push`, `shift`, `peek` і `size`. Почніть з місткості 4. Коли масив повний, створіть
удвічі довший і скопіюйте елементи в порядку черги. Перш ніж писати ріст, намалюйте на папері масив на 4 комірки з
чергою, що перейшла через кінець, і випишіть, куди потрапить кожен елемент у новому масиві.

**2. Перевірка дужок.** Функція `isBalanced(s)` для дужок `()`, `[]` і `{}`, решта символів не враховується. Відкривна
дужка лягає в стек, закривна має відповідати верхній. Подумайте, що функція має повернути для `"(]"`, `")("` і `"(("`,
і яку з двох найчастіших помилок ловить кожен із цих рядків.

**3. Тести.** Для `RingQueue` — порожня черга, один елемент, перехід голови через кінець буфера, ріст у момент, коли
черга вже перейшла через кінець, і порядок FIFO після росту. Для дужок — порожній рядок, вкладені дужки різних видів,
перехрещені дужки `"([)]"`.

**4. Вимір.** До запуску передбачте, у скільки разів `RingQueue` буде швидша за масив з `shift` на 100 000 операцій
`push`, а потім 100 000 `shift`. Виміряйте і запишіть обидва числа в `MEASUREMENTS.md`.

## Перевірте себе

**1. Що буде в стеку і в черзі після операцій `push 1`, `push 2`, `push 3`, вилучення, `push 4`, вилучення?**

<details><summary>Відповідь</summary>

Стек: після трьох `push` у ньому `1 2 3`, вилучення знімає 3, `push 4` дає `1 2 4`, вилучення знімає 4. Лишається `1
2`. Черга: вилучення забирає 1, `push 4` дає `2 3 4`, вилучення забирає 2. Лишається `3 4`.

</details>

**2. Кільцевий буфер на 8 комірок, `head = 6`, `size = 3`. У які комірки лягли елементи черги, і куди ляже
наступний?**

<details><summary>Відповідь</summary>

Елементи лежать у комірках `6`, `7` і `(6 + 2) % 8 = 0`. Наступний ляже в комірку `(6 + 3) % 8 = 1`.

</details>

**3. Чому в черзі CLRS на масиві з `n` комірок поміщається лише `n − 1` елемент?**

<details><summary>Відповідь</summary>

CLRS зберігає лише два номери: голову і комірку, куди ляже наступний елемент, без лічильника. Порожня черга — це `head
= tail`. Якби в масив можна було покласти `n` елементів, після заповнення `tail` пройшов би повне коло і знову
дорівнював би `head`, і повну чергу не можна було б відрізнити від порожньої. Тому одна комірка завжди лишається
вільною. Лічильник `size`, як у Morin, прибирає цю проблему.

</details>

**4. У черзі з двох стеків `inbox` містить 1, 2, 3 (3 нагорі), `outbox` порожній. Що повертає `shift` і що лежить у
стеках після нього?**

<details><summary>Відповідь</summary>

`outbox` порожній, тому `inbox` перекладається: знімається 3, потім 2, потім 1, і в `outbox` вони лягають так, що 1
опиняється нагорі. `shift` знімає 1 і повертає його. Після цього `inbox` порожній, а в `outbox` лежать 3 внизу і 2
нагорі. Наступні два `shift` повернуть 2 і 3 без жодного перекладання.

</details>

**5. Чи може в черзі з двох стеків кожна операція коштувати `Θ(n)`?**

<details><summary>Відповідь</summary>

Ні. Перекладання спорожнює `inbox`, і кожен елемент перекладається лише раз за все життя в черзі. Дорогий `shift`, що
переклав `k` елементів, після себе лишає `k` дешевих: ці елементи виходять з `outbox` без перекладань. Тому за `m`
операцій сумарна вартість `O(m)`, хоча окремі операції бувають дорогими.

</details>

**6. Знайдіть помилку в функції, що повертає останні `k` повідомлень чату, і оцініть її час для `n` повідомлень.**

```ts
function lastK(messages: string[], k: number): string[] {
  const window: string[] = [];
  for (const m of messages) {
    window.push(m);
    if (window.length > k) window.shift();
  }
  return window;
}
```

<details><summary>Відповідь</summary>

Функція правильна за результатом, але кожен `shift` зсуває `k` елементів, тож час `Θ(n · k)`. Для мільйона повідомлень
і `k = 50 000` це десятки мільярдів зсувів. Виправлення без жодної структури: `messages.slice(-k)` копіює лише останні
`k` елементів за `Θ(k)`. Якщо повідомлення надходять потоком і масиву всіх повідомлень немає, потрібна кільцева черга
місткістю `k`. Зверніть увагу: з `k = 0` функція повертає порожній масив, а `messages.slice(-0)` — увесь масив, бо
`-0` дорівнює `0`.

</details>
