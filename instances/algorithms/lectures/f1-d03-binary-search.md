# Лекція. Фаза 1, день 3. Бінарний пошук

Ця лекція пояснює бінарний пошук: як знайти потрібне місце у відсортованих даних, перевіривши лише логарифмічну частку
елементів, і як писати його так, щоб не помилитися на одиницю. Читання займе близько 55 хвилин. Під прикладами коду
стоїть справжній вивід з Node 24.22.

У лекції дня 4 фази 0 ви вже бачили функцію пошуку, яка зависала, коли `hi` перевищувало `lo` рівно на одиницю, і
інваріант, що пояснив чому. Сьогодні з'ясуємо, скільки кроків робить бінарний пошук і звідки береться логарифм, чому
задачу краще ставити як пошук межі, а не елемента, і як той самий прийом шукає відповідь там, де масиву немає зовсім.

**Після лекції ви зможете пояснити:**

- чому бінарному пошуку для мільйона елементів досить 20 кроків і звідки формула `⌈log₂(n + 1)⌉`;
- чим пошук елемента відрізняється від пошуку межі і чому другий надійніший;
- який інваріант тримає пошук межі і як з нього випливають усі межі циклу;
- як обчислювати середину, щоб не отримати дробовий номер чи від'ємне число;
- що таке пошук за відповіддю і як він знаходить найменше значення, для якого умова правдива;
- чому в пошуку на дійсних числах умова «ширина менша за ε» може ніколи не справдитися.

## Двадцять запитань

Skiena починає з дитячої гри «двадцять запитань»: один гравець задумує слово, другий ставить запитання, на які можна
відповісти «так» чи «ні». Якщо за двадцять запитань слово не вгадано, виграє перший. У другого є виграшна стратегія:
розгорнути словник посередині, взяти слово звідти і запитати, чи задумане слово стоїть у словнику раніше. Кожна
відповідь відкидає половину слів. Словник має від 50 до 200 тисяч слів, а після 18 поділів навпіл від 200 тисяч
лишається одне слово.

BCtCI розповідає справжню історію. У журналіста Тома Віппла вкрали велосипед зі стоянки під камерою. Поліція сказала,
що не має людей переглядати багато годин запису. Журналіст пояснив, що переглядати все не треба: перемотати на
середину запису і подивитися, чи велосипед ще там. Якщо там, крадіжка сталася в другій половині, якщо ні — у першій. І
так далі.

Обидві історії про одне: якщо дані впорядковані так, що одна перевірка каже, з якого боку відповідь, кожна перевірка
відкидає половину. Це і є **бінарний пошук**.

## Класичний пошук і кількість кроків

Найвідоміший запис шукає число у відсортованому масиві. Пошук тримає ділянку `[lo, hi]`, де ще може бути відповідь,
дивиться на середину і або знаходить число, або відкидає половину ділянки разом із серединою:

```ts
// Класичний бінарний пошук: межі включно, три результати порівняння. Рахуємо ітерації циклу.
export function classicSearch(xs: readonly number[], target: number): { index: number; steps: number } {
  let lo = 0, hi = xs.length - 1, steps = 0;
  while (lo <= hi) {
    steps++;
    const mid = lo + Math.floor((hi - lo) / 2);
    const v = xs[mid]!;
    if (v === target) return { index: mid, steps };
    if (v < target) lo = mid + 1;       // відповідь, якщо вона є, праворуч від mid
    else hi = mid - 1;                  // відповідь, якщо вона є, ліворуч від mid
  }
  return { index: -1, steps };
}

const n = 1_000_000;
const xs = Array.from({ length: n }, (_, i) => 2 * i);   // парні числа 0, 2, …, 1 999 998
let worstFound = 0, worstMissing = 0;
for (let i = 0; i < n; i++) {
  worstFound = Math.max(worstFound, classicSearch(xs, 2 * i).steps);
  worstMissing = Math.max(worstMissing, classicSearch(xs, 2 * i + 1).steps);
}
console.log(`n = ${n}: найбільше ітерацій для наявного ${worstFound}, для відсутнього ${worstMissing}`);
console.log(`лінійний пошук для відсутнього: ${n} порівнянь`);
```

```
n = 1000000: найбільше ітерацій для наявного 20, для відсутнього 20
лінійний пошук для відсутнього: 1000000 порівнянь
```

Програма перебрала всі мільйон наявних чисел і всі мільйон відсутніх і для жодного не зробила більше 20 ітерацій.
Лінійний пошук, щоб переконатися, що числа немає, перевіряє всі мільйон елементів.

**Звідки 20.** Після першої ітерації від ділянки з `n` елементів лишається не більше `⌊n/2⌋`: середина відкинута, а з
двох половин більша має `⌊n/2⌋` елементів. Після `k` ітерацій лишається не більше `⌊n/2ᵏ⌋`. Цикл точно закінчиться,
коли ділянка стане порожньою. Тож найбільша кількість ітерацій — це найменше `k`, для якого `2ᵏ > n`, тобто `⌊log₂ n⌋
+ 1`. Цю саму кількість записують як `⌈log₂(n + 1)⌉`. Для `n = 1 000 000` маємо `2¹⁹ = 524 288 ≤ n < 2²⁰ = 1 048 576`,
отже, 20 ітерацій. У лекції дня 4 фази 0 ви довели сильною індукцією, що число `n` має `⌊log₂ n⌋ + 1` двійкових цифр.
Це не збіг: кожна відповідь «ліворуч чи праворуч» схожа на вибір однієї двійкової цифри номера, і цифр потрібно
стільки ж.

**Чому логарифм — це так мало.** Подвоєння масиву додає лише одну ітерацію. Мільярд елементів — 30 ітерацій, усі
адреси 64-бітного комп'ютера — не більше 64.

## Чого класичний пошук не вміє

Той самий код на масиві з повторами:

```ts
const dup = [1, 2, 2, 2, 2, 2, 3];
console.log(`у [${dup}] число 2 знайдено на позиції ${classicSearch(dup, 2).index}`);
```

```
у [1,2,2,2,2,2,3] число 2 знайдено на позиції 3
```

Пошук знайшов двійку, але не першу і не останню, а ту, що випадково опинилася посередині. А задачі зазвичай потребують
саме першої чи останньої: скільки разів трапляється число, куди вставити нове значення, щоб масив лишився
відсортованим, з якого запису почати діапазон дат. Коли числа немає, класичний пошук повертає `−1` і губить інформацію
про те, де воно мало б стояти.

Skiena показує, як виправити це для підрахунку повторів: прибрати перевірку рівності, щоб пошук не зупинявся на першій
знайденій копії, а доходив до межі блоку однакових чисел.

## Пошук межі

BCtCI радить для всіх задач на бінарний пошук один рецепт: шукати не елемент, а **межу**. Уявіть, що кожна позиція
масиву має ярлик «до» чи «після», і всі «до» стоять лівіше за всі «після». Тоді задача — знайти, де ярлики змінюються.

Ярлик дає **предикат** — функція, яка для позиції повертає `true` чи `false`. Предикат має бути **монотонним**: якщо
він правдивий на позиції `i`, то правдивий і на всіх наступних. Наприклад, для пошуку першої позиції, де значення не
менше за 2, у масиві `[1, 2, 2, 2, 2, 2, 3]` предикат `xs[i] >= 2` дає:

```
позиція:   0     1     2     3     4     5     6
значення:  1     2     2     2     2     2     3
предикат:  false true  true  true  true  true  true
                 ▲
                 межа: перша позиція, де предикат правдивий
```

Одна правильна функція «перша позиція, де предикат правдивий» розв'язує купу задач, бо змінюється лише предикат:

| Задача | Предикат | Що повертати |
|--------|----------|--------------|
| перша позиція, де `xs[i] ≥ x` | `xs[i] >= x` | межу; це місце вставки `x` |
| перша позиція, де `xs[i] > x` | `xs[i] > x` | межу; різниця з попереднім рядком — кількість копій `x` |
| чи є `x` у масиві | `xs[i] >= x` | `true`, якщо межа в межах масиву і `xs[межа] === x` |
| останній запис не пізніше дати `d` | `dates[i] > d` | межу мінус один |

### Інваріант пошуку межі

Функція з лекції дня 4 фази 0 вже була пошуком межі для предиката «значення не менше за `target`». Її інваріант
переноситься на будь-який монотонний предикат дослівно:

**Інваріант:** перед кожною перевіркою умови циклу всі позиції ліворуч від `lo` мають предикат `false`, а всі позиції
від `hi` до кінця ділянки — `true`. Межа лежить десь у `[lo, hi]`.

З інваріанта випливає весь код, тому запам'ятовувати межі циклу не треба:

- **Початок.** `lo` — перша позиція ділянки, `hi` — позиція одразу за останньою. Ліворуч від `lo` і праворуч від `hi`
  поки нічого немає, тож інваріант правдивий. Межа може виявитися і за останньою позицією, якщо предикат ніде не
  правдивий; тому `hi`, а не `hi − 1`.
- **Умова циклу.** Поки `lo < hi`, межа ще не визначена: між ними є позиції без ярлика.
- **Крок.** Беремо `mid` з `[lo, hi)`. Якщо предикат на `mid` хибний, то хибний і на всіх позиціях до `mid`, отже,
  `lo` можна перенести за `mid`, на `mid + 1`. Якщо правдивий, то й на всіх після, і `hi` можна перенести на `mid`.
- **Прогрес.** Оскільки `lo ≤ mid < hi`, обидва переходи строго зменшують `hi − lo`. Саме цієї частини бракувало
  зламаній функції з фази 0, де писали `lo = mid`.
- **Кінець.** Коли `lo = hi`, ліворуч усе `false`, а з `hi` усе `true`. Отже, `lo` — це межа.

Простежимо пошук межі для `xs[i] >= 2` у масиві `[1, 2, 2, 2, 2, 2, 3]`:

| `lo` | `hi` | `mid` | `xs[mid]` | Предикат | Що робимо |
|------|------|-------|-----------|----------|-----------|
| 0 | 7 | 3 | 2 | true | `hi = 3` |
| 0 | 3 | 1 | 2 | true | `hi = 1` |
| 0 | 1 | 0 | 1 | false | `lo = 1` |
| 1 | 1 | — | — | — | `lo = hi`, межа 1 |

Предикат викликано тричі, і результат — перша двійка, позиція 1. Функцію `firstTrue(lo, hi, pred)`, що робить це для
будь-якого предиката, ви напишете в практиці.

BCtCI записує той самий рецепт трохи інакше: `l` і `r` стоять на двох відомих позиціях з різними ярликами, крайові
випадки перевіряють перед циклом, а цикл іде, поки `r − l > 1`. Стаття cp-algorithms робить так само, ставлячи `l =
−1` і `r = n` на уявні позиції за межами масиву. Обидва записи тримають той самий інваріант: позиції ліворуч від межі
мають ярлик «до», праворуч — «після». Записи відрізняються лише тим, чи межі включено в ділянку. Важливо вибрати один
запис і в кожному рядку коду пам'ятати, що означають `lo` і `hi`.

### Скільки викликів предиката

Пошук межі на ділянці з `n` позицій має `n + 1` можливих відповідей: межа може стояти перед кожною позицією або за
останньою. Кожен виклик предиката ділить можливі відповіді на дві частини і залишає не більшу за половину. Тому
потрібно `⌈log₂(n + 1)⌉` викликів, і для мільйона це знову 20. Пошук межі не зупиняється рано, навіть якщо випадково
влучив у шукане число. BCtCI зауважує, що це не біда: нас цікавить найгірший випадок, а він той самий.

## Середина ділянки

Обчислити середину можна кількома способами, і два з них ламаються:

```ts
// Три способи обчислити середину ділянки.
const xs = [10, 20, 30, 40];
let lo = 1, hi = 2;
const mid = (lo + hi) / 2;                    // без округлення
console.log(mid, xs[mid]);

lo = 1_500_000_000; hi = 2_000_000_000;       // номери в масиві на диску чи в базі
console.log((lo + hi) >> 1);                  // зсув працює з 32-бітними цілими
console.log(lo + Math.floor((hi - lo) / 2));
```

```
1.5 undefined
-397483648
1750000000
```

**Ділення без округлення.** У JavaScript `/` завжди дає дробове число. Елемента з номером `1.5` немає, і `xs[1.5]`
повертає `undefined`. Порівняння `undefined < target` дає `false`, тож код не падає, а тихо йде не в той бік.
TypeScript тут не допомагає: номер масиву має тип `number`, і дробовий номер проходить перевірку типів.

**Зсув і переповнення.** Запис `(lo + hi) >> 1` часто трапляється в коді, бо зсув на один біт праворуч ділить на два і
відкидає дробову частину. Але оператори зсуву в JavaScript спершу перетворюють число на 32-бітне ціле зі знаком. Сума
`3 500 000 000` у 32 біти не вміщується, перетворення перекидає її у від'ємне число, і середина стає від'ємною. У
мовах з цілими фіксованого розміру, як Java чи Go, переповнюється вже саме додавання `lo + hi`. Стаття cp-algorithms
згадує, що така помилка дев'ять років жила в бібліотеці Java.

**Правильний запис.** `lo + Math.floor((hi - lo) / 2)` не додає двох великих чисел і завжди дає ціле між `lo` і `hi −
1`, коли `lo < hi`.

## Пошук за відповіддю

Предикату не обов'язково дивитися в масив. Досить, щоб він був монотонним на проміжку цілих чисел. Тоді бінарний пошук
знаходить найменше значення, для якого умова правдива, навіть якщо значень мільярди і жодне з них не записане. Цей
прийом BCtCI називає **guess-and-check**, «вгадай і перевір», а cp-algorithms — пошуком за відповіддю.

Приклад з BCtCI: тест проходив на всіх комітах до якогось моменту, а потім почав падати. Предикат «тест падає на
коміті `i`» монотонний: хибний до певного коміту і правдивий після. Перший коміт, де він правдивий, і є коміт, що
зламав тест. Серед тисячі комітів пошук запустить тест не більше `⌈log₂ 1001⌉ = 10` разів.

Інший приклад, ближчий до інтерфейсів. Заголовок треба обрізати так, щоб він разом із трикрапкою вміщувався в ширину
`W` пікселів. Ширина префікса з `k` символів зростає разом з `k`, бо кожен символ має додатну ширину. Тому предикат
«префікс довжини `k` з трикрапкою ширший за `W`» монотонний, і перша довжина, де він правдивий, мінус один — найдовший
префікс, що вміщується. Для заголовка в 200 символів досить 8 вимірів ширини замість двохсот.

Ціна прийому: кожен виклик предиката може бути дорогим. BCtCI нагадує врахувати його вартість: якщо предикат працює за
`Θ(n)`, а значень `S`, пошук коштує `Θ(n log S)`.

**Коли межі невідомі.** Буває, що верхньої межі немає: масив читають через функцію `fetch(i)` і довжина невідома, або
відповідь може бути будь-яким додатним числом. Тоді спершу перевіряють позиції 1, 2, 4, 8, … , доки предикат не стане
правдивим, а потім шукають межу між останніми двома. Skiena називає це **одностороннім бінарним пошуком**, BCtCI —
**експоненційним пошуком**. Якщо межа стоїть на позиції `p`, усе разом займає не більше `2⌈log₂ p⌉` перевірок, хоч би
яким великим був масив.

## Пошук на дійсних числах

Якщо невідоме — дійсне число, ділити відрізок навпіл можна без кінця, і треба вирішити, коли зупинитися. Програма
шукає корінь рівняння `x³ = y` з двома умовами зупинки: коли ширина відрізка менша за `10⁻⁹` і після рівно 100 кроків:

```ts
// Пошук кореня рівняння x³ = y діленням відрізка навпіл, з двома умовами зупинки.
function cubeRoot(y: number, stop: (lo: number, hi: number, iter: number) => boolean): { x: number; iter: number } {
  let lo = 0, hi = Math.max(1, y), iter = 0;
  while (!stop(lo, hi, iter)) {
    const mid = (lo + hi) / 2;
    if (mid * mid * mid < y) lo = mid; else hi = mid;
    iter++;
  }
  return { x: lo, iter };
}
const byWidth = (lo: number, hi: number, iter: number) => hi - lo < 1e-9 || iter > 10_000;   // запобіжник
const byCount = (_lo: number, _hi: number, iter: number) => iter === 100;

for (const y of [27, 1e30]) {
  const a = cubeRoot(y, byWidth), b = cubeRoot(y, byCount);
  console.log(`y = ${y}: за шириною ${a.x} після ${a.iter} кроків; за кількістю ${b.x} після ${b.iter} кроків`);
}
```

```
y = 27: за шириною 2.9999999995634425 після 35 кроків; за кількістю 2.9999999999999996 після 100 кроків
y = 1e+30: за шириною 9999999999.999998 після 10001 кроків; за кількістю 9999999999.77731 після 100 кроків
```

Тут `lo = mid` без `+ 1` правильне: на дійсних числах немає «наступного» значення, і відрізок усе одно звужується
вдвічі, поки число з плаваючою комою може вмістити середину.

Для `y = 27` обидві умови спрацювали. Для `y = 10³⁰` сталося дві різні неприємності.

**Умова за шириною не справдилася ніколи.** Корінь дорівнює `10¹⁰`, а сусідні числа типу `number` біля `10¹⁰` стоять
на відстані приблизно `2 · 10⁻⁶`. Ширина відрізка не може стати меншою за цю відстань, тим паче меншою за `10⁻⁹`. Без
запобіжника на 10 000 кроків цикл крутився б вічно: середина збігається з `lo` чи `hi`, і відрізок перестає
звужуватися.

**Ста кроків не вистачило.** Пошук стартував з відрізка завдовжки `10³⁰`. Після 100 поділів його ширина `10³⁰ / 2¹⁰⁰ ≈
0,8`, тож відповідь хибить у третьому знаку після коми. Кількість кроків треба рахувати від початкової ширини: щоб
дійти до точності `ε`, потрібно `log₂((hi − lo)/ε)` кроків, тут близько 130.

Надійна зупинка — коли середина вже не лежить строго між `lo` і `hi`. Тоді досягнуто найкращої можливої точності чисел
з плаваючою комою, хоч би яким великим був корінь.

## Бінарний пошук у мовах

| Мова | Функція | Що повертає |
|------|---------|-------------|
| JavaScript | вбудованої немає | `indexOf` і `includes` шукають лінійно |
| Python | `bisect.bisect_left(a, x)`, `bisect.bisect_right(a, x)` | місце вставки: перше `≥ x` і перше `> x` |
| Go | `sort.Search(n, f)` | найменший `i` з `[0, n)`, де `f(i)` правдива, або `n`, якщо такого немає |
| Go | `slices.BinarySearch(s, target)` | перша позиція, де `target` знайдено чи мав би стояти, і чи знайдено |

Документація Go описує `sort.Search` майже словами цієї лекції: функція вимагає, щоб `f` була хибною на якомусь
префіксі і правдивою на решті, і повертає перший правдивий номер. Документація окремо попереджає, що «не знайдено» тут
означає `n`, а не `−1`, як у `strings.Index`.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Скільки кроків робить бінарний пошук? | `⌈log₂(n + 1)⌉` у найгіршому випадку: для мільйона 20, для мільярда 30. |
| Що потрібно від даних? | Монотонний предикат: хибний на префіксі, правдивий на решті. Відсортований масив дає його для будь-якого порогу. |
| Як знайти першу і останню копію числа? | Два пошуки межі: перше `≥ x` і перше `> x`; кількість копій — різниця. |
| Як обчислювати середину? | `lo + Math.floor((hi - lo) / 2)`: без дробів і без переповнення. |
| Що таке пошук за відповіддю? | Бінарний пошук по можливих значеннях відповіді з предикатом «чи годиться це значення». |
| Як шукати, якщо довжина невідома? | Подвоювати верхню межу, доки предикат не стане правдивим, потім звичайний пошук. |

## Типові помилки

**Змішати два записи меж.** Почати з `hi = xs.length` для напіввідкритої ділянки, а цикл написати як `lo <= hi` для
закритої. Тоді пошук читає `xs[xs.length]`. Виберіть один запис і виведіть усе з інваріанта.

**Писати `lo = mid` у пошуку на цілих.** Коли `hi = lo + 1`, середина дорівнює `lo`, і цикл зависає. Це помилка з дня
4 фази 0.

**Обчислювати середину як `(lo + hi) / 2` або `(lo + hi) >> 1`.** Перше дає дробовий номер, друге ламається на сумах
понад `2³¹ − 1`.

**Застосовувати пошук до немонотонного предиката.** На невідсортованому масиві бінарний пошук не падає, а повертає
довільну позицію. Тести з маленькими масивами можуть цього не помітити.

**Зупиняти пошук на дійсних числах лише за шириною відрізка.** Для великих значень ширина ніколи не стане меншою за
відстань між сусідніми числами з плаваючою комою.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: інваріант і трасування пошуку межі показано на прикладі, а
функцію ви пишете самі.

**1. `firstTrue(lo, hi, pred)`.** Повертає першу позицію з `[lo, hi)`, де `pred` правдивий, або `hi`, якщо такої
немає. Перш ніж писати, запишіть у коментарі інваріант і для кожного рядка коду перевірте, що він його зберігає.

**2. Через `firstTrue`** напишіть `lowerBound(xs, x)` і цілочисельний квадратний корінь `isqrt(n)`: найбільше ціле
`r`, для якого `r² ≤ n`. Подумайте, який предикат дає `isqrt` і яку верхню межу пошуку взяти, щоб `n = 0` і `n = 1`
теж працювали.

**3. Лічильник.** Порахуйте кількість викликів `pred` для масиву з мільйона елементів на кількох `x`: менших за всі,
більших за всі і посередині. Перед запуском передбачте найбільше число.

**4. Тести.** Порожній масив, масив без шуканого елемента, масив з повторами, масив з одного елемента, `x` менше за
всі елементи і більше за всі. Для `isqrt` — 0, 1, 15, 16, 17 і `2⁵³ − 1`. Для останнього подумайте, чи не
переповниться `mid * mid` точність `number`.

**5. Журнал.** Один рядок у `JOURNAL.md`: що стало зрозумілим і що ні. Запишіть числа з пункту 3 у `MEASUREMENTS.md`.

## Перевірте себе

**1. Скільки ітерацій у найгіршому випадку зробить класичний пошук на масиві з 1000 елементів? А з 1024?**

<details><summary>Відповідь</summary>

`⌊log₂ n⌋ + 1`. Для 1000: `2⁹ = 512 ≤ 1000 < 1024`, отже, `9 + 1 = 10`. Для 1024: `log₂ 1024 = 10`, отже, 11. Масив з
1024 елементів потребує на одну ітерацію більше, бо після десяти поділів від нього може лишитися один елемент, який ще
треба перевірити.

</details>

**2. Масив `[3, 5, 5, 5, 8, 9]`. Що повернуть пошуки межі для предикатів `xs[i] >= 5`, `xs[i] > 5` і `xs[i] >= 10`?**

<details><summary>Відповідь</summary>

`xs[i] >= 5` правдивий з позиції 1, тож межа 1. `xs[i] > 5` правдивий з позиції 4, тож межа 4. Різниця `4 − 1 = 3` —
кількість п'ятірок. `xs[i] >= 10` ніде не правдивий, тож межа 6, тобто довжина масиву: десятку треба вставити в
кінець.

</details>

**3. Чому в пошуку межі на цілих `hi = mid`, а не `hi = mid − 1`?**

<details><summary>Відповідь</summary>

Предикат на `mid` правдивий, і `mid` сам може виявитися межею: першою правдивою позицією. Інваріант каже, що з `hi`
усе правдиве, і `hi = mid` це зберігає. Запис `hi = mid − 1` відкинув би `mid` і порушив би інваріант, якщо `mid` саме
межа.

</details>

**4. Чому `(lo + hi) >> 1` у JavaScript дає від'ємне число для `lo = 1 500 000 000` і `hi = 2 000 000 000`, хоча `lo +
hi` — звичайне число без переповнення?**

<details><summary>Відповідь</summary>

Сума `3 500 000 000` справді точна. Але оператор `>>` спершу перетворює число на 32-бітне ціле зі знаком, а такі цілі
вміщують лише до `2³¹ − 1 = 2 147 483 647`. Перетворення бере остачу за модулем `2³²` і трактує старший біт як знак:
`3 500 000 000 − 4 294 967 296 = −794 967 296`. Зсув ділить це на два з округленням униз: `−397 483 648`.

</details>

**5. Чому пошук за відповіддю не годиться для задачі «знайти найменше `k`, при якому функція `f(k)` дорівнює 0», якщо
`f` то спадає, то зростає?**

<details><summary>Відповідь</summary>

Бінарному пошуку потрібен монотонний предикат: з якогось місця і до кінця правдивий. Предикат `f(k) = 0` для такої
функції може бути правдивим у кількох розрізнених точках, і одна перевірка посередині не каже, з якого боку шукати.
Laaksonen показує, як бути з функцією, що спершу зростає, а потім спадає: шукати не нуль, а межу предиката `f(x) < f(x
+ 1)`, тобто вершину. І це працює лише тоді, коли сусідні значення ніколи не рівні.

</details>

**6. Предикат у пошуку за відповіддю працює за `Θ(n)`, а відповідь лежить між 1 і 10⁹. Скільки коштує пошук, і коли
краще перебрати всі значення по черзі?**

<details><summary>Відповідь</summary>

Пошук викличе предикат `⌈log₂(10⁹ + 1)⌉ = 30` разів, разом `Θ(30n)`. Перебір значень по черзі коштує `Θ(n)` на кожне
значення до першого правдивого. Він дешевший лише тоді, коли відповідь гарантовано менша за 30, тобто менша за
логарифм проміжку. Якщо відповідь зазвичай мала, а проміжок величезний, допомагає експоненційний пошук: він знайде
відповідь `p` за `2⌈log₂ p⌉` викликів.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| бінарний пошук | пошук, що щоразу відкидає половину ділянки, де може бути відповідь |
| ділянка пошуку | позиції, де відповідь ще може бути: `[lo, hi]` чи `[lo, hi)` залежно від запису |
| предикат | функція, що повертає `true` чи `false` |
| монотонний предикат | предикат, що лишається правдивим на всіх позиціях після першої правдивої |
| межа | перша позиція, де монотонний предикат правдивий |
| місце вставки, lower bound | перша позиція, де значення не менше за шукане |
| upper bound | перша позиція, де значення більше за шукане |
| пошук за відповіддю, guess-and-check | бінарний пошук по можливих значеннях відповіді з предикатом «чи годиться» |
| експоненційний, односторонній пошук | подвоєння верхньої межі, доки предикат не стане правдивим, а потім бінарний пошук |
