# Лекція. Фаза 1, день 4. Хеш-таблиці: ланцюжки й відкрита адресація

Ця лекція пояснює хеш-таблицю: структуру, яка знаходить запис за ключем у середньому за сталий час, хоч би скільки
записів у ній лежало. Читання займе близько 55 хвилин. Під прикладами коду стоїть справжній вивід з Node 24.22.

Учора бінарний пошук знаходив ключ за `log₂ n` кроків, але вимагав відсортованих даних. Сьогодні з'ясуємо, як обійтися
без сортування і без логарифма, що за це доводиться платити, і що відбувається всередині `Map` і `Set`, якими ви
користуєтеся щодня.

**Після лекції ви зможете пояснити:**

- як хеш-функція перетворює ключ на номер комірки і чому колізії неминучі;
- як працюють ланцюжки і відкрита адресація з лінійним зондуванням;
- що таке коефіцієнт заповнення і як він визначає середню кількість порівнянь;
- чому лінійне зондування різко гіршає, коли таблиця заповнена на 90 %;
- чому з таблиці з відкритою адресацією не можна видаляти, просто звільняючи комірку;
- що специфікація JavaScript обіцяє про `Map` і чим `Map` відрізняється від звичайного об'єкта як словника.

## Пошук, що забирав сім секунд

Розробник отримує з сервера масив користувачів і масив ідентифікаторів, для яких треба показати імена. Найпростіший
код шукає кожного користувача методом `find`. Програма нижче порівнює його з `Map`, побудованою один раз:

```ts
// Пошук користувача за id: перебір масиву методом find і Map.
type User = { id: string; name: string };
for (const n of [10_000, 20_000, 40_000]) {
  const users: User[] = Array.from({ length: n }, (_, i) => ({ id: `u${i}`, name: `Name ${i}` }));
  const ids = users.map((u) => u.id).reverse();       // шукаємо кожного користувача по разу

  let t0 = performance.now();
  let found = 0;
  for (const id of ids) if (users.find((u) => u.id === id)) found++;
  const tFind = performance.now() - t0;

  t0 = performance.now();
  const byId = new Map(users.map((u) => [u.id, u] as const));   // побудова теж входить у час
  for (const id of ids) if (byId.get(id)) found++;
  const tMap = performance.now() - t0;

  console.log(`n = ${n}: find ${tFind.toFixed(0)} мс, Map ${tMap.toFixed(2)} мс (знайдено ${found / 2})`);
}
```

```
n = 10000: find 568 мс, Map 4.24 мс (знайдено 10000)
n = 20000: find 1808 мс, Map 6.56 мс (знайдено 20000)
n = 40000: find 7137 мс, Map 18.52 мс (знайдено 40000)
```

Кожен `find` перебирає масив до потрібного користувача, у середньому половину масиву. `n` пошуків разом дають близько
`n²/2` порівнянь, і час росте вчетверо, коли `n` подвоюється. `Map` будується за один прохід і потім знаходить кожного
користувача за кілька кроків, тому її час росте лише лінійно, разом з побудовою. Для 40 000 користувачів різниця майже
в чотириста разів.

Як `Map` знаходить ключ, не перебираючи і не сортуючи? Відповідь — хеш-таблиця.

## Від масиву за номером до хеш-таблиці

Почнемо з найпростішого випадку, який курс MIT 6.006 називає **масивом прямого доступу**. Якщо ключі — цілі числа від
0 до `u − 1`, запис з ключем `k` можна покласти просто в комірку `k` масиву. Тоді пошук, вставка і видалення коштують
один крок у найгіршому випадку. Біда в пам'яті: масив займає `u` комірок, хоч би скільки ключів у ньому лежало. MIT
рахує, що для імен з десяти латинських літер знадобилося б `26¹⁰` комірок, і навіть по одному біту на комірку це 17,6
терабайта.

**Хеш-таблиця** бере масив розумного розміру `m` і перетворює ключ на номер комірки спеціальною функцією. Цю функцію
називають **хеш-функцією** `h`, а її результат `h(k)` — **хешем** ключа. Хеш-функція має бути детермінованою: той
самий ключ завжди дає ту саму комірку. Інакше записане неможливо було б знайти.

Ось проста хеш-функція рядка і таблиця з 8 комірок:

```ts
// Куди потрапляють ключі в таблиці з 8 комірок: поліноміальний хеш рядка і остача від ділення.
function hash(s: string): number {
  let h = 0;
  for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) >>> 0;   // >>> 0 тримає 32 біти без знака
  return h;
}
const m = 8;
const keys = ["kyiv", "lviv", "odesa", "dnipro", "kharkiv", "poltava", "sumy", "rivne", "lutsk", "uzhhorod"];
const slots: string[][] = Array.from({ length: m }, () => []);
for (const k of keys) slots[hash(k) % m]!.push(k);
slots.forEach((s, i) => console.log(`комірка ${i}: ${s.join(", ") || "—"}`));
```

```
комірка 0: —
комірка 1: —
комірка 2: kharkiv
комірка 3: kyiv, lutsk
комірка 4: —
комірка 5: poltava, uzhhorod
комірка 6: odesa, dnipro, sumy, rivne
комірка 7: lviv
```

Функція множить накопичене значення на 31 і додає код наступного символу. Оператор `>>> 0` перетворює результат на
32-бітне число без знака, щоб воно не росло без меж. Як вибирати хеш-функцію і чому саме так, план розбирає завтра.
Сьогодні важливо інше: десять ключів лягли у вісім комірок нерівно. Три комірки порожні, а в комірку 6 потрапили
чотири ключі.

Два різні ключі з однією коміркою — це **колізія**. Колізій не уникнути: ключів, які можна придумати, набагато більше,
ніж комірок, тож за принципом Діріхле якісь два ключі мусять потрапити в одну комірку. Навіть коли ключів менше, ніж
комірок, колізії з'являються дуже рано. Це парадокс днів народження, до якого план дійде завтра. Тому кожна
хеш-таблиця мусить вміти з колізіями жити. Способів два.

## Ланцюжки

У способі **ланцюжків** кожна комірка тримає список усіх ключів, що в неї потрапили. Щоб знайти ключ, обчислюють його
комірку і перебирають її список. Щоб вставити, додають ключ у список. CLRS кладе новий елемент на початок списку
процедурою з розділу 10.2, тож вставка коштує `O(1)`, якщо заздалегідь відомо, що такого ключа ще немає. Інакше спершу
доводиться шукати.

Таблиця з прикладу вище з ланцюжками виглядала б так:

```
0: —
1: —
2: kharkiv
3: lutsk → kyiv
4: —
5: uzhhorod → poltava
6: rivne → sumy → dnipro → odesa
7: lviv
```

Пошук `odesa` перевіряє чотири ключі в комірці 6, а пошук `kharkiv` — один. Найгірший випадок жахливий: якщо всі ключі
потрапили в одну комірку, таблиця стає одним довгим списком, і пошук коштує `Θ(n)`. Хеш-таблицями користуються не
заради найгіршого випадку, а заради середнього.

### Коефіцієнт заповнення

**Коефіцієнт заповнення** `α = n/m` — це середня кількість ключів на комірку. У прикладі `α = 10/8 = 1,25`.

CLRS аналізує ланцюжки за припущенням, що хеш-функція поводиться як випадкова: кожен ключ однаково ймовірно потрапляє
в будь-яку комірку, незалежно від інших. Тоді середня довжина списку дорівнює `α`, і книжка доводить дві теореми:

- **невдалий пошук**, коли ключа немає, перевіряє в середньому `α` ключів, бо проходить увесь список;
- **вдалий пошук** перевіряє в середньому `1 + α/2 − α/(2n)` ключів, тобто приблизно `1 + α/2`: сам шуканий ключ плюс
  половину тих, що лежать у списку перед ним.

Обидві оцінки — `Θ(1 + α)`. Отже, поки `α` обмежене сталою, пошук у середньому сталий. Для цього таблицю роблять так
само, як динамічний масив з дня 8 фази 0: коли `α` перевищує поріг, виділяють удвічі більший масив і **перехешовують**
усі ключі, тобто обчислюють для кожного нову комірку. Окремий перехеш коштує `Θ(n)`, але амортизовано він додає до
кожної вставки сталу вартість. Morin тримає `n ≤ m`, тобто `α ≤ 1`.

## Відкрита адресація

У **відкритій адресації** ключі лежать прямо в масиві, по одному на комірку, без списків. Якщо комірка ключа зайнята,
ключ кладуть в іншу за правилом, яке залежить від ключа і номера спроби. Послідовність комірок, які перевіряють для
ключа, називають **послідовністю зондування**. Пошук іде тією самою послідовністю і зупиняється, коли знайшов ключ або
натрапив на порожню комірку: якби ключ був у таблиці, вставка поклала б його саме туди.

Найпростіше правило — **лінійне зондування**: якщо комірка `h(k)` зайнята, пробувати `h(k) + 1`, потім `h(k) + 2` і
так далі, повертаючись після кінця масиву на початок. Покладемо в таблицю з 8 комірок ключі з комірки 6 прикладу вище:

| Вставка | Пробує комірки | Лягає в | Таблиця 0 … 7 |
|---------|----------------|---------|---------------|
| odesa | 6 | 6 | `. . . . . . odesa .` |
| dnipro | 6, 7 | 7 | `. . . . . . odesa dnipro` |
| sumy | 6, 7, 0 | 0 | `sumy . . . . . odesa dnipro` |
| rivne | 6, 7, 0, 1 | 1 | `sumy rivne . . . . odesa dnipro` |

Відкрита адресація не тримає посилань, тож ту саму пам'ять можна віддати на більше комірок. Посилання на вузли списку
теж не треба розіменовувати, а сусідні комірки лежать поруч, що добре для кешу процесора з лекції дня 7 фази 0. Ціна —
таблиця може заповнитися: `α` ніколи не перевищує 1, і довго до одиниці доходити не можна.

### Злипання

Зверніть увагу: чотири ключі утворили суцільний **шматок** зайнятих комірок 6, 7, 0, 1, що переходить через кінець
масиву. Будь-який новий ключ, чий хеш потрапить у комірки 6, 7, 0, 1 або 2, ляже в комірку 2 і подовжить шматок.
Шматок довжини `k` ловить новий ключ з імовірністю `(k + 1)/m`, тож що довший шматок, то швидше він росте. Sedgewick
називає це **кластеризацією**, і саме вона робить лінійне зондування гіршим за ідеальну відкриту адресацію.

Кнут у 1962 році вивів середню кількість зондувань для лінійного зондування за припущення про випадкову хеш-функцію.
Sedgewick наводить її як твердження M: приблизно `½(1 + 1/(1 − α))` для вдалого пошуку і `½(1 + 1/(1 − α)²)` для
невдалого. CLRS для порівняння аналізує ідеальну схему, у якій послідовність зондування кожного ключа — випадкова
перестановка всіх комірок: там невдалий пошук робить не більше `1/(1 − α)` зондувань, а вдалий — не більше `(1/α) ·
ln(1/(1 − α))`. Ось ці формули в числах:

| `α` | Ланцюжки, вдалий | Ланцюжки, невдалий | Ідеальна схема, вдалий | Ідеальна схема, невдалий | Лінійне, вдалий | Лінійне, невдалий |
|-----|------------------|--------------------|------------------------|--------------------------|-----------------|-------------------|
| 0,25 | 1,12 | 0,25 | 1,15 | 1,3 | 1,2 | 1,4 |
| 0,5 | 1,25 | 0,5 | 1,39 | 2,0 | 1,5 | 2,5 |
| 0,75 | 1,38 | 0,75 | 1,85 | 4,0 | 2,5 | 8,5 |
| 0,9 | 1,45 | 0,9 | 2,56 | 10,0 | 5,5 | 50,5 |
| 0,99 | 1,50 | 0,99 | 4,65 | 100,0 | 50,5 | 5000,5 |

Для ланцюжків рахуються порівняння з ключами в списку, для відкритої адресації — зондування, тобто перевірені комірки.
Поки таблиця заповнена наполовину, усі схеми роблять один-два кроки. Біля `α = 0,9` лінійне зондування на невдалому
пошуку вже робить п'ятдесят кроків, а біля `0,99` — тисячі. Тому таблиці з лінійним зондуванням ростуть рано:
Sedgewick тримає `α` не більше половини, Morin — так само, рахуючи разом із видаленими комірками. Практика дня
перевірить ці числа вимірами.

## Видалення з відкритої адреси

З ланцюжків ключ видаляють так само, як вузол зі списку. З відкритою адресацією все складніше. Повернімося до таблиці
з чотирма ключами і видалимо `dnipro`, просто звільнивши комірку 7:

| Крок | Таблиця 0 … 7 | Що відбувається |
|------|---------------|-----------------|
| до видалення | `sumy rivne . . . . odesa dnipro` | — |
| звільнили комірку 7 | `sumy rivne . . . . odesa .` | — |
| шукаємо `sumy` | | комірка 6 — `odesa`, не те; комірка 7 порожня — пошук зупиняється: «ключа немає» |

Ключ `sumy` лежить у комірці 0, але пошук до нього не доходить. Коли `sumy` вставляли, комірка 7 була зайнята, тому
він пішов далі. Порожня комірка на його шляху тепер бреше, що далі шукати марно.

Виправлення, яке дають CLRS і Morin, — **позначка видалення** (її ще називають надгробком, tombstone). Замість
звільнення в комірку кладуть особливе значення `DELETED`. Пошук проходить повз нього, як повз зайняту комірку, а
вставка може покласти туди новий ключ. Ціна: позначки займають місце, і пошук через них іде так само довго, як через
справжні ключі. Тому Morin рахує окремо кількість ключів `n` і кількість непорожніх комірок `q`, разом з позначками, і
перебудовує таблицю, коли `q` росте. Перебудова кладе лише живі ключі й позбавляється позначок. Sedgewick для
лінійного зондування обходиться без позначок: після видалення він заново вставляє всі ключі, що стоять у шматку
праворуч від звільненої комірки.

## Ланцюжки чи відкрита адресація

| | Ланцюжки | Відкрита адресація з лінійним зондуванням |
|---|----------|-------------------------------------------|
| де лежать ключі | у списках поза масивом | у самому масиві |
| найбільше `α` | будь-яке, але для швидкості тримають біля 1 | менше 1, на практиці не більше ½ |
| коли гіршає | плавно, пропорційно `α` | різко біля `α → 1` через злипання |
| видалення | просте | потрібні позначки або перевставка |
| пам'ять на ключ | ключ плюс посилання і вузол списку | лише ключ, але з запасом порожніх комірок |
| кеш процесора | вузли розкидано по пам'яті | сусідні комірки поруч |

CLRS зауважує, що коли ключі доводиться видаляти, частіше вибирають ланцюжки. Відкрита адресація натомість не витрачає
пам'ять на посилання і краще працює з кешем процесора. Обидва способи дають `O(1)` у середньому, якщо `α` обмежене і
хеш-функція добре розкидає ключі.

## `Map`, `Set` і об'єкти в JavaScript

Специфікація ECMA-262 не каже, як влаштовано `Map`, але ставить умову. Розділ 24.1 редакції ES2026 вимагає, щоб `Map`
була реалізована «хеш-таблицями або іншими механізмами, що в середньому дають час доступу, сублінійний від кількості
елементів». Для `Set` у розділі 24.2 вимога та сама. Тобто специфікація гарантує середню, а не найгіршу оцінку, і
хеш-таблицю називає першим варіантом.

Звичайний об'єкт теж можна вживати як словник, але він розрізняє ключі інакше:

```ts
// Як Map і звичайний об'єкт розрізняють ключі.
const obj: Record<string, string> = {};
obj[1] = "число";
obj["1"] = "рядок";
console.log(Object.keys(obj), obj[1]);

const map = new Map<unknown, string>();
map.set(1, "число").set("1", "рядок");
console.log(map.size, map.get(1), map.get("1"));

map.set(NaN, "не число");
console.log(map.get(NaN), [NaN].indexOf(NaN));       // Map знаходить NaN, а строга рівність — ні

const a = { id: 1 }, b = { id: 1 };
map.set(a, "об'єкт a");
console.log(map.get(a), map.get(b));                  // ключ-об'єкт порівнюється за тотожністю
console.log([...map.keys()]);                         // порядок додавання
```

```
[ '1' ] рядок
2 число рядок
не число -1
об'єкт a undefined
[ 1, '1', NaN, { id: 1 } ]
```

Об'єкт перетворює ключ `1` на рядок `"1"`, тож другий запис затер перший. `Map` зберігає ключі такими, як їх дали, і
порівнює їх за правилом **SameValueZero** зі специфікації: воно схоже на `===`, але вважає `NaN` рівним `NaN`. Тому
`map.get(NaN)` знаходить запис, хоча `indexOf`, що порівнює строго, не знаходить `NaN` навіть у масиві з ним. Цікава
деталь: перша версія цього прикладу містила вираз `NaN === NaN`, і TypeScript відмовився його компілювати з помилкою
TS2845 «This condition will always return 'false'».

Два об'єкти `{ id: 1 }` з однаковим вмістом для `Map` — різні ключі: об'єкти порівнюються за тотожністю, тобто за тим,
чи це той самий об'єкт у пам'яті. Щоб шукати за вмістом, ключ треба перетворити на рядок чи число, як `u.id` у
прикладі з початку лекції. Обхід `Map` іде в порядку додавання ключів, а не в порядку комірок, і це теж вимога
специфікації: опис `Map.prototype.forEach` у розділі 24.1.3.5 каже «in key insertion order». Хеш-таблиця сама такого
порядку не дає, тож реалізації зберігають його окремо.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Скільки коштує пошук у хеш-таблиці? | `O(1)` у середньому за доброї хеш-функції і обмеженого `α`; `Θ(n)` у найгіршому випадку. |
| Що таке колізія і чому вона неминуча? | Два ключі в одній комірці. Можливих ключів більше, ніж комірок. |
| Ланцюжки чи відкрита адресація? | Ланцюжки простіші й плавно гіршають з `α`; відкрита адресація економить посилання і краща для кешу, але потребує `α` помітно менше 1 і обережного видалення. |
| Що таке коефіцієнт заповнення і навіщо перехешування? | `α = n/m`. Коли `α` перевищує поріг, масив подвоюють і переносять усі ключі; амортизовано це `O(1)` на вставку. |
| Чому не можна просто звільнити комірку при видаленні у відкритій адресації? | Пошуки ключів, що лежать далі в тому самому шматку, зупиняться на порожній комірці. |
| Чим `Map` краща за об'єкт як словник? | Ключі будь-якого типу без перетворення на рядок, `size`, порядок додавання, без конфлікту з полями прототипу. |

## Типові помилки

**Шукати в масиві методом `find` у циклі.** Кожен пошук лінійний, і разом виходить квадрат. Побудуйте `Map` один раз.

**Вважати `O(1)` хеш-таблиці гарантією.** Це середнє за припущення про добру хеш-функцію. Погана функція чи навмисно
підібрані ключі роблять пошук лінійним. Про це наступний день.

**Звільняти комірку при видаленні у відкритій адресації.** Потрібна позначка видалення або перевставка шматка.

**Доводити таблицю з лінійним зондуванням до 90 % заповнення.** Невдалий пошук там робить у середньому п'ятдесят
кроків.

**Використовувати об'єкти як ключі `Map`, очікуючи порівняння за вмістом.** Два однакові на вигляд об'єкти — різні
ключі.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: ланцюжки й лінійне зондування показано таблицями, а класи ви
пишете самі.

**1. `ChainedHashMap<V>` і `LinearProbingMap<V>`** для рядкових ключів з методами `set`, `get`, `has` і `size`. Хеш
рядка візьміть з лекції. Таблиця з ланцюжками може тримати в комірці звичайний масив пар. Для лінійного зондування
передбачте, що робить пошук, коли таблиця повністю заповнена.

**2. Лічильник порівнянь.** Кожна таблиця рахує, скільки разів пошук порівняв шуканий ключ з ключем у таблиці.

**3. Вимір.** Не вмикаючи перехешування, створіть таблиці з такою кількістю комірок, щоб після 100 000 вставок `α`
дорівнювало 0,5 і 0,9. Виміряйте середню кількість порівнянь для вдалих пошуків усіх 100 000 ключів і для 100 000
невдалих. До запуску випишіть з таблиці лекції, що має вийти. Запишіть передбачення й виміри поруч у
`MEASUREMENTS.md`.

**4. Видалення.** Додайте `delete` у `LinearProbingMap` з позначкою видалення. Напишіть тест, що відтворює сценарій з
лекції: два ключі з однією коміркою, видалення першого, пошук другого.

**5. Журнал.** Один рядок у `JOURNAL.md`: що стало зрозумілим і що ні.

## Перевірте себе

**1. Таблиця з ланцюжками має 1000 комірок і 3000 ключів. Скільки ключів у середньому перевірить невдалий пошук і
скільки — вдалий?**

<details><summary>Відповідь</summary>

`α = 3`. Невдалий пошук проходить увесь список комірки, у середньому `α = 3` ключі. Вдалий перевіряє приблизно `1 +
α/2 = 2,5` ключа. Обидва числа сталі, хоч і більші, ніж при `α = 1`.

</details>

**2. У таблиці з 8 комірок і лінійним зондуванням зайняті комірки 2, 3, 4 і 6. Яка ймовірність, що новий ключ ляже в
комірку 5, якщо хеш випадковий?**

<details><summary>Відповідь</summary>

Ключ ляже в комірку 5, якщо його хеш — 2, 3, 4 або 5: з комірок 2, 3 і 4 він зсунеться вперед до першої вільної, тобто
до 5. Це 4 комірки з 8, ймовірність `1/2`. Після цього шматок 2–6 стане суцільним шматком довжини 5. Порожня комірка 5
мала вдвічі більший шанс заповнитися, ніж комірка 7, яку ловлять хеші 6 і 7, і вчетверо більший, ніж комірка 0, яку
ловить лише хеш 0. Це і є злипання.

</details>

**3. Чому для лінійного зондування таблиця з `α = 0,9` гірша, ніж таблиця з ланцюжками з `α = 0,9`, хоча в обох
однаково ключів і комірок?**

<details><summary>Відповідь</summary>

У ланцюжках ключі різних комірок не заважають один одному: кожен список має в середньому `0,9` ключа. У лінійному
зондуванні ключ, що не помістився у свою комірку, займає чужу, і шматки зайнятих комірок зростають і зливаються. Пошук
мусить пройти шматок до кінця, а при `α = 0,9` шматки довгі. Формула Кнута дає 50,5 зондування на невдалий пошук проти
0,9 порівняння в ланцюжках.

</details>

**4. У таблиці з відкритою адресацією вставили 1000 ключів, потім видалили 900 з позначками і вставили ще 100 нових.
Чому пошук став повільнішим, ніж у свіжій таблиці з тими самими 200 ключами?**

<details><summary>Відповідь</summary>

Позначки видалення займають комірки так само, як ключі, з погляду пошуку: він проходить повз них і не зупиняється.
Нові ключі можуть лягти на місце деяких позначок, але решта лишається, і таблиця поводиться, ніби заповнена набагато
більше, ніж `200/m`. Тому Morin рахує всі непорожні комірки `q` і перебудовує таблицю, коли їх стає забагато.
Перебудова переносить лише живі ключі.

</details>

**5. Що надрукує код і чому?**

```ts
const seen = new Set<number[]>();
seen.add([1, 2]);
console.log(seen.has([1, 2]));
```

<details><summary>Відповідь</summary>

`false`. Масив — об'єкт, і `Set` порівнює об'єкти за тотожністю. Літерал `[1, 2]` у другому рядку створює новий масив,
не той, що лежить у множині. Щоб перевіряти пари за вмістом, ключ перетворюють на рядок, наприклад `"1,2"`, або на
число, якщо пари обмежені.

</details>

**6. Чому таблицю з ланцюжками подвоюють, коли `α` перевищує поріг, а не збільшують на 1000 комірок?**

<details><summary>Відповідь</summary>

Перехешування переносить усі `n` ключів, тобто коштує `Θ(n)`. Подвоєння робить такі перенесення рідкісними: між двома
перехешуваннями відбувається стільки ж вставок, скільки ключів уже є, і загальна вартість лишається `O(n)` на `n`
вставок, як у динамічному масиві з дня 8 фази 0. Збільшення на сталу кількість комірок перехешовує кожні 1000 вставок,
і сума перенесень стає квадратичною.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| масив прямого доступу | масив, де запис з цілим ключем `k` лежить у комірці `k` |
| хеш-функція | детермінована функція, що перетворює ключ на номер комірки |
| хеш | результат хеш-функції для ключа |
| колізія | два різні ключі з однаковою коміркою |
| ланцюжки | спосіб жити з колізіями: кожна комірка тримає список своїх ключів |
| відкрита адресація | спосіб жити з колізіями: ключ кладуть в іншу комірку масиву за правилом |
| послідовність зондування | порядок комірок, які перевіряють для ключа у відкритій адресації |
| лінійне зондування | правило «наступна комірка, потім ще наступна» |
| коефіцієнт заповнення `α` | кількість ключів на комірку, `n/m` |
| перехешування | перенесення всіх ключів у більший масив з новими номерами комірок |
| злипання, кластеризація | утворення довгих суцільних шматків зайнятих комірок при лінійному зондуванні |
| позначка видалення, tombstone | особливе значення в комірці видаленого ключа, повз яке пошук іде далі |
| SameValueZero | правило рівності ключів `Map` і `Set`: як `===`, але `NaN` рівне `NaN` |
