# Лекція. Фаза 1, день 5. Хеш-функції, атаки і хешування в мовах

Ця лекція пояснює, від чого залежить обіцянка «хеш-таблиця шукає за `O(1)`»: від хеш-функції. Читання займе близько 55
хвилин. Під прикладами коду стоїть справжній вивід з Node 24.22 і Python 3.14.

Учора ви бачили, що середня кількість порівнянь у хеш-таблиці залежить лише від коефіцієнта заповнення `α`. Але всі
формули спиралися на припущення, що хеш-функція розкидає ключі як випадкові. Сьогодні з'ясуємо, що буває, коли це
припущення не виконується, як зловмисник цим користується, і чому Python, Go та інші мови щоразу перемішують хеш
випадковим числом.

**Після лекції ви зможете пояснити:**

- чому колізії з'являються набагато раніше, ніж заповнюється таблиця, і що таке парадокс днів народження;
- чим добра хеш-функція відрізняється від поганої і чому остача від ділення на степінь двійки небезпечна;
- як хешують рядки поліномом і навіщо остача від ділення на просте число;
- що таке універсальне хешування і що саме воно гарантує;
- як атака на хеш-таблицю робить сервер квадратичним і як випадкове зерно цьому запобігає;
- чому порядок обходу множини в Python змінюється від запуску до запуску.

## Десять тисяч ключів, що поклали сервер

Сервер приймає від користувачів запити з числовими ідентифікаторами і складає їх у хеш-таблицю з 1024 комірок з
ланцюжками. Хеш-функція найпростіша: `k mod 1024`. Програма нижче рахує, скільки порівнянь коштує вставка 10 000
ключів. Саму таблицю будувати не треба: досить знати довжину списку кожної комірки, бо вставка, що перевіряє, чи ключа
ще немає, порівнює новий ключ з усім списком.

```ts
// Скільки порівнянь коштує вставка n ключів у таблицю з ланцюжками, якщо ключі підібрано проти хеш-функції.
// Таблицю не будуємо: досить знати довжину списку кожної комірки.
function cost(keys: number[], m: number, h: (k: number) => number): { compares: number; longest: number } {
  const len = new Array<number>(m).fill(0);
  let compares = 0;
  for (const k of keys) {
    const s = h(k);
    compares += len[s]!;          // вставка спершу перевіряє, чи ключа ще немає: порівнює з усім списком
    len[s]!++;
  }
  return { compares, longest: Math.max(...len) };
}
const m = 1024, n = 10_000;
const randomKeys = Array.from({ length: n }, () => Math.floor(Math.random() * 2 ** 30));
const evilKeys = Array.from({ length: n }, (_, i) => i * m);            // усі кратні 1024
const alignedKeys = Array.from({ length: n }, (_, i) => i * 64);        // кратні 64, як вирівняні адреси
```

Для випадкових ключів, для ключів, кратних 1024, і для ключів, кратних 64, з функцією `k mod m` виходить:

```
випадкові    k mod m:    49137 порівнянь, найдовший список    21
кратні 1024  k mod m: 49995000 порівнянь, найдовший список 10000
кратні 64    k mod m:  3120000 порівнянь, найдовший список   625
```

Випадкові ключі дають близько `n²/(2m) ≈ 48 800` порівнянь, як обіцяє вчорашній аналіз: у середньому кожен список має
`α ≈ 10` ключів. Ключі, кратні 1024, усі мають остачу 0 і всі лягають в одну комірку. Таблиця стає одним списком, і
вставка коштує `0 + 1 + … + 9999 = 49 995 000` порівнянь, у тисячу разів більше. Користувачеві, що хоче покласти
сервер, досить надіслати такі ключі.

Третій рядок показує пастку, яка трапляється й без зловмисника. Ключі, кратні 64, мають шість нульових молодших бітів.
Остача від ділення на `1024 = 2¹⁰` бере лише десять молодших бітів, і з них шість завжди нульові. Тому ключі
потрапляють лише в 16 комірок з 1024, по 625 ключів у кожну. Так поводяться, наприклад, адреси в пам'яті, вирівняні на
64 байти.

Обидві проблеми мають один корінь: хеш-функція фіксована і відома, а дані не випадкові. Erickson пише це великими
літерами: «Input data is not random! So good hash functions must be random!»

## Колізії приходять рано

Навіть ідеально випадкова хеш-функція дає колізії раніше, ніж здається. Skiena пояснює це **парадоксом днів
народження**: скільки людей має бути в кімнаті, щоб двоє з них найімовірніше мали день народження в один день?

Порахуємо ймовірність, що `n` ключів у таблиці з `m` комірок не мають жодної колізії. Перший ключ лягає будь-куди.
Другий має не влучити в зайняту комірку: ймовірність `(m − 1)/m`. Третій — `(m − 2)/m`, і так далі. Ключі незалежні,
тож ймовірності перемножуються:

```ts
// Парадокс днів народження: імовірність, що n ключів у m комірках не мають жодної колізії.
function noCollision(n: number, m: number): number {
  let p = 1;
  for (let i = 0; i < n; i++) p *= (m - i) / m;   // (i + 1)-й ключ має влучити в одну з m − i вільних комірок
  return p;
}
for (const n of [10, 23, 30, 50]) console.log(`m = 365, n = ${n}: без колізій ${(noCollision(n, 365) * 100).toFixed(1)} %`);
for (const n of [20, 40, 80]) console.log(`m = 1024, n = ${n}: без колізій ${(noCollision(n, 1024) * 100).toFixed(1)} %`);
```

```
m = 365, n = 10: без колізій 88.3 %
m = 365, n = 23: без колізій 49.3 %
m = 365, n = 30: без колізій 29.4 %
m = 365, n = 50: без колізій 3.0 %
m = 1024, n = 20: без колізій 83.0 %
m = 1024, n = 40: без колізій 46.2 %
m = 1024, n = 80: без колізій 4.2 %
```

У кімнаті з 23 людей імовірність збігу днів народження вже більша за половину, а з 50 людей збіг майже гарантований.
Таблиця з 1024 комірок, заповнена лише на 4 % сорока ключами, найімовірніше вже має колізію. Skiena робить висновок:
колізії починаються, коли `n` порядку `√m`. Щоб їх уникнути зовсім, потрібна таблиця розміру порядку `n²`. Тому
колізії не намагаються усунути, а роблять так, щоб їх було мало і вони були розкидані рівномірно.

## Яка хеш-функція добра

Morin формулює дві вимоги:

1. **Рівні ключі мають однаковий хеш.** Інакше записаний ключ неможливо знайти.
2. **Різні ключі мають однаковий хеш рідко**, з ймовірністю близькою до `1/m`.

Перша вимога пояснює, чому хеш-функція мусить бути детермінованою і чому, перевизначаючи рівність, треба перевизначити
й хеш. Друга — головна, і з нею найбільше складнощів.

**Метод ділення** `h(k) = k mod m` — найпростіша функція. Ви бачили, що з `m = 2ᵈ` вона бере лише `d` молодших бітів
ключа. Тому підручники радять брати `m` простим числом, далеким від степенів двійки. Erickson вважає і це недостатнім:
навіть з простим `m` ключі `x` і `x + am` для будь-якого цілого `a` колізують гарантовано. «Why would anyone use a
hash function where they know certain pairs of keys always collide?»

**Мультиплікативний метод** множить ключ на велике непарне число і бере старші біти молодшої половини добутку. CLRS
показує його варіант «multiply-shift», що на комп'ютері займає три інструкції: множення, віднімання і зсув. Morin і
Erickson аналізують той самий метод під назвою мультиплікативного хешування. Множення перемішує біти: старші біти
результату залежать від усіх бітів ключа, тому ключі, кратні 64, уже не злипаються.

## Хеш рядка

Рядок — це послідовність чисел, кодів символів. Найпоширеніший спосіб перетворити її на одне число — **поліноміальний
хеш**: рядок `s₀ s₁ … s_{L−1}` вважають числом у системі числення з основою `B`:

```
h(s) = (s₀ · B^(L−1) + s₁ · B^(L−2) + … + s_{L−1}) mod p
```

Обчислюють його **схемою Горнера**, як у вчорашньому прикладі з `h * 31 + code`: накопичене значення множать на `B` і
додають наступний символ. Щоб число не росло без меж, на кожному кроці беруть остачу від ділення на `p`. Sedgewick
пояснює, що так рядок фактично вважають величезним числом і ділять його на `p`, не обчислюючи самого числа.

**Чому `p` просте.** Поліном степеня `L − 1` за модулем простого числа має не більше `L − 1` коренів. Morin спирається
саме на це у своїй теоремі 5.4: два різні рядки дають однаковий хеш лише тоді, коли основа `B` виявилася коренем
полінома, утвореного різницею рядків. Якщо `B` вибрати випадково з `0 … p − 1`, ймовірність такого збігу не більша за
`(L − 1)/p`. Для `p` близько двох мільярдів і рядків до тисячі символів це менше однієї мільйонної.

**Хеш рядка не безкоштовний.** BCtCI нагадує, що хешування рядка довжини `L` коштує `Θ(L)`. Операції з `Map` для
довгих рядкових ключів сталі лише за кількістю ключів, але не за довжиною кожного.

Той самий поліноміальний хеш план використає у фазі 4 для пошуку підрядка алгоритмом Рабіна–Карпа: там хеш вікна
перераховують за сталий час, коли вікно зсувається на один символ.

## Випадковість замість удачі

Будь-яка фіксована хеш-функція має погані набори ключів: якщо ключів можливо набагато більше, ніж комірок, то за
принципом Діріхле знайдеться щонайменше `|U|/m` ключів з однаковим хешем. Erickson підкреслює: якщо дані прийдуть саме
з такого набору, випадково чи навмисно, програма зупиниться.

Вихід — вибирати хеш-функцію випадково, коли таблицю створюють. Набір функцій, з якого вибирають, називають
**родиною**. Родина **універсальна**, якщо для будь-яких двох різних ключів ймовірність, що випадково вибрана функція
дасть їм однаковий хеш, не більша за `1/m`. Важливо, що випадкова тут функція, а не ключі: ключі може вибирати хоч
зловмисник, але він не знає, яку функцію вибрано.

Класична універсальна родина з CLRS і Erickson:

```
h_ab(k) = ((a · k + b) mod p) mod m,
```

де `p` — просте число, більше за всі ключі, `a` вибирають випадково з `1 … p − 1`, а `b` — з `0 … p − 1`. Числа `a` і
`b` Erickson називає **сіллю** (salt), а в документації мов частіше пишуть **зерно** (seed).

Чому це допомагає. Довжина списку, у який потрапляє ключ `x`, — це кількість інших ключів з тим самим хешем. Для
кожного з них ймовірність збігу не більша за `1/m`. Отже, очікувана довжина не більша за `1 + (n − 1)/m`, тобто `O(1 +
α)`, для **будь-якого** набору ключів. CLRS формулює це як наслідок 11.3: з універсальним хешуванням і ланцюжками
будь-яка послідовність `s` операцій, серед яких `O(m)` вставок, займає в середньому `Θ(s)`.

Перевіримо на тих самих ключах. Програма вибирає `a` і `b` випадково і рахує той самий підсумок:

```ts
// Універсальна родина ((a·k + b) mod p) mod m з випадковими a і b; BigInt, бо a·k не вміщується в 2^53.
const p = 2_147_483_647n;                                             // просте число 2^31 − 1
const a = BigInt(1 + Math.floor(Math.random() * (2 ** 31 - 2)));
const b = BigInt(Math.floor(Math.random() * (2 ** 31 - 1)));
const universal = (k: number) => Number(((a * BigInt(k) + b) % p) % BigInt(m));
```

```
випадкові    універсальна:  49119 порівнянь, найдовший список 21
кратні 1024  універсальна:  44101 порівнянь, найдовший список 11
кратні 64    універсальна:  44292 порівнянь, найдовший список 13
```

Тип `BigInt` тут потрібен, бо добуток `a · k` сягає `2⁶²`, а звичайне число в JavaScript точно тримає цілі лише до
`2⁵³`. Без `BigInt` молодші біти добутку загубилися б, і остача була б неправильною.

Ключі, кратні 1024, які щойно поклали таблицю, тепер розсипалися так само, як випадкові. Другий запуск програми вибрав
інші `a` і `b` і дав для тих самих ключів 44 006 і 46 956 порівнянь: числа трохи інші, бо інша функція, але порядок
той самий.

**Де має бути зерно.** Зерно мусить змінювати те, які ключі колізують, а не лише значення хешу. Якщо в поліноміальному
хеші рядка додати випадкове число до результату чи взяти його початковим значенням, два рядки однакової довжини, що
колізували без зерна, колізуватимуть і з ним: випадкова добавка однакова для обох. Morin робить випадковою саму основу
полінома, і тоді колізії стають справді випадковими. Пам'ятайте про це в практиці.

## Атаки і зерно в мовах

Те, що ви бачили на початку лекції, — не теоретична загроза. Документація Python пояснює, навіщо хеш рядків
перемішується: «This is intended to provide protection against a denial-of-service caused by carefully chosen inputs
that exploit the worst case performance of a dict insertion, O(n²) complexity». Вона посилається на попередження
oCERT-2011-003, після якого мови масово ввели зерно. Блог Go про генератор ChaCha8Rand пише, що середовище виконання
Go вибирає нове випадкове зерно для **кожної** мапи, бо зловмисник, який знає хеш-функцію, «can prepare input that
drives the map into quadratic behavior».

У Python це видно одразу. Два запуски підряд друкують різні хеші того самого рядка, а зі змінною `PYTHONHASHSEED=0`
зерно фіксоване, і хеші однакові:

```
$ python3 -c "print(hash('kyiv'))"
-2807234426761048197
$ python3 -c "print(hash('kyiv'))"
4071417764126542762
$ PYTHONHASHSEED=0 python3 -c "print(hash('kyiv'))"
4881871996127621372
$ PYTHONHASHSEED=0 python3 -c "print(hash('kyiv'))"
4881871996127621372
```

Наслідок, який документація теж згадує: від зерна залежить порядок обходу множини. Ось та сама множина з трьома
різними зернами:

```
$ PYTHONHASHSEED=1 python3 -c "print(list({'kyiv','lviv','odesa','sumy'}))"
['odesa', 'lviv', 'sumy', 'kyiv']
$ PYTHONHASHSEED=2 python3 -c "print(list({'kyiv','lviv','odesa','sumy'}))"
['lviv', 'kyiv', 'sumy', 'odesa']
$ PYTHONHASHSEED=3 python3 -c "print(list({'kyiv','lviv','odesa','sumy'}))"
['odesa', 'sumy', 'lviv', 'kyiv']
```

Python ніколи не обіцяв порядку множин, і код, що на нього покладається, ламається між запусками. BCtCI попереджає про
те саме: порядок обходу множин і мап у більшості мов близький до випадкового. Go навмисно починає обхід мапи з
випадкового місця: примітки до випуску Go 1.3 пояснюють, що так роблять, «to keep code from depending on map iteration
order». JavaScript тут виняток: специфікація вимагає, щоб `Map` і `Set` обходилися в порядку додавання, незалежно від
хешів, як ви бачили вчора.

## Ідеальне хешування

Коли набір ключів відомий наперед і не змінюється, як ключові слова мови програмування, можна гарантувати пошук за
сталий час у найгіршому випадку. Skiena і Erickson описують двоярусну схему. Перший ярус — таблиця з `n` комірок.
Кожна комірка, у яку потрапило `nᵢ` ключів, отримує власну таблицю розміру порядку `nᵢ²`. За парадоксом днів
народження в таблиці квадратичного розміру колізії малоймовірні, а якщо вони все ж трапилися, другий ярус
перебудовують з іншою функцією. Erickson доводить, що сума `Σ nᵢ²` в середньому менша за `3n`, тож разом пам'ять
лишається лінійною.

| Питання | Коротка відповідь |
|---------|-------------------|
| Чому `O(1)` хеш-таблиці не гарантія? | Це середнє за доброї хеш-функції. Фіксовану функцію можна атакувати ключами з однаковим хешем, і операції стають `Θ(n)`. |
| Що таке парадокс днів народження і до чого він тут? | Колізії з'являються вже при `n ≈ √m` ключах: 23 людини з 365 днів. Тому таблиці не уникають колізій, а розподіляють їх. |
| Що таке універсальне хешування? | Випадковий вибір функції з родини, де будь-які два ключі колізують з ймовірністю не більше `1/m`; очікуваний пошук `O(1 + α)` для будь-яких ключів. |
| Як хешують рядки? | Поліноміально: кожен символ множать на степінь основи і беруть остачу від простого числа, обчислюючи схемою Горнера. |
| Чому порядок обходу `set` у Python змінюється? | Хеш рядків перемішується випадковим зерном при кожному запуску, а порядок обходу залежить від хешів. |
| Скільки коштує хешування рядка? | `Θ(L)` для рядка довжини `L`, тож для довгих ключів операції з мапою не сталі. |

## Типові помилки

**Брати `k mod 2ᵈ`, коли молодші біти ключів погано перемішані.** Ключі, кратні 64, займуть лише кожну 64-ту комірку.

**Додавати зерно до результату хешу.** Ключі, що колізували без зерна, колізують і з ним.

**Покладатися на порядок обходу множини чи мапи.** У Python він змінюється між запусками, у Go — між обходами. Порядок
додавання гарантують лише `Map` і `Set` у JavaScript.

**Перевизначити рівність без хешу.** Два рівні об'єкти з різними хешами потраплять у різні комірки, і таблиця не
знайде те, що в ній лежить.

**Множити великі числа в хеш-функції звичайним `number`.** Добуток понад `2⁵³` втрачає молодші біти. Беріть `BigInt`,
`Math.imul` для 32-бітного множення або тримайте множники досить малими.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: атаку показано на числових ключах, а рядки ви підбираєте
самі.

**1. Поліноміальний хеш рядка** `polyHash(s, base, p)` за модулем простого числа `p`. Подумайте, як не вийти за межі
точних цілих: якщо `p` близько `2³¹`, чи вміщується добуток накопиченого значення на основу в `2⁵³`?

**2. Атака.** Для таблиці з 1024 комірок і фіксованої основи підберіть 1000 різних рядків, які потрапляють в одну
комірку. Підказка: є два шляхи. Перший — перебирати випадкові рядки й залишати ті, що влучили в потрібну комірку;
оцініть, скільки рядків доведеться перебрати. Другий — знайти дві короткі пари символів з однаковим хешем і подумати,
що буде, якщо складати з них довші рядки. Запишіть, скільки часу забрав кожен шлях.

**3. Зерно.** Зробіть основу полінома випадковою, вибраною при створенні таблиці, і перевірте, що ті самі 1000 рядків
розсипаються по комірках. Порахуйте найдовший ланцюжок і середню довжину непорожнього ланцюжка.

**4. Пастка степеня двійки.** Візьміть 1000 ключів, кратних 64, і порівняйте найдовший ланцюжок для `k mod 1024`, `k
mod 1021` і мультиплікативного хешу з розділу 11.3 CLRS.

**5. Журнал.** Один рядок у `JOURNAL.md` і числа з пунктів 2–4 у `MEASUREMENTS.md`. Поясніть одним реченням, чому
різниця між пунктами 2 і 3 важлива для сервера, що приймає ключі від користувачів.

## Перевірте себе

**1. У таблиці 1 000 000 комірок. Приблизно скільки ключів треба покласти, щоб колізія стала ймовірнішою, ніж її
відсутність?**

<details><summary>Відповідь</summary>

Колізії починаються при `n` порядку `√m`. Точніше, ймовірність без колізій приблизно `e^(−n²/(2m))`, і вона падає до
половини при `n ≈ √(2m · ln 2) ≈ 1,18√m`. Для мільйона комірок це близько 1180 ключів, хоча таблиця заповнена лише на
0,1 %. Для 365 днів формула дає `1,18 · 19,1 ≈ 22,5`, тобто ті самі 23 людини.

</details>

**2. Чому функція `k mod 1021` краща за `k mod 1024` для ключів, кратних 64, але все одно погана проти зловмисника?**

<details><summary>Відповідь</summary>

1021 — просте число, і `gcd(64, 1021) = 1`, тож послідовність `0, 64, 128, …` за модулем 1021 обходить усі комірки, а
не кожну 64-ту. Але функція фіксована й відома, і ключі `x`, `x + 1021`, `x + 2042`, … завжди колізують. Зловмиснику
досить надіслати їх, щоб отримати один довгий ланцюжок.

</details>

**3. Чому універсальна родина вимагає випадкового `a`, а не випадкових ключів?**

<details><summary>Відповідь</summary>

Ключі вибирає не таблиця, а той, хто нею користується, і вони можуть бути будь-якими, зокрема найгіршими. Аналіз
універсального хешування не робить жодних припущень про ключі: ймовірність береться лише за вибором функції. Тому
оцінка `O(1 + α)` правдива для кожного набору ключів, якщо зловмисник не знає, яку функцію вибрано.

</details>

**4. У поліноміальному хеші рядків зерно `s` додали так: `h = (s + polyHash(str)) mod p`. Чи захищає це від атаки з
практики?**

<details><summary>Відповідь</summary>

Ні. Якщо без зерна два рядки мали однаковий `polyHash`, то з зерном обидва отримують `s + той самий хеш`, тобто знову
однаковий. Зерно лише зсуває всі хеші на одне число, а колізії лишаються тими самими. Щоб колізії змінювалися від
зерна, воно має впливати на те, як символи змішуються, наприклад бути основою полінома.

</details>

**5. Чому програма, що в тестах друкує `list(my_set)` і порівнює з очікуваним списком, може падати не щоразу?**

<details><summary>Відповідь</summary>

Порядок обходу множини в Python залежить від хешів, а хеші рядків перемішуються випадковим зерном при кожному запуску
інтерпретатора. Тому тест бачить різний порядок у різних запусках і проходить лише тоді, коли порядок випадково
збігся. Порівнювати треба множини (`set(...) == {...}`) або відсортовані списки.

</details>

**6. Хеш-таблиця з ланцюжками й універсальною функцією має `n = m`. Скільки в середньому ключів у найдовшому
ланцюжку?**

<details><summary>Відповідь</summary>

Не стала кількість. Erickson попереджає, що оцінка `Θ(1 + α)` стосується очікуваної довжини ланцюжка конкретного
ключа, а не найдовшого ланцюжка. Навіть з ідеально випадковою функцією при `α = 1` очікувана довжина найдовшого
ланцюжка — `Θ(log n / log log n)`. Моделювання з мільйоном ключів у мільйоні комірок тричі дало найдовший ланцюжок з 9
або 10 ключів. У вимірі лекції з 10 000 ключів і 1024 комірками найдовший ланцюжок мав 21 ключ при середньому близько
10.

</details>

| парадокс днів народження | спостереження, що колізії з'являються вже при `n ≈ √m` ключах |
