# Лекція. Фаза 1, день 7. Сортування злиттям

Ця лекція пояснює сортування злиттям, перше сортування цього плану, що працює за `Θ(n log n)`, і прийом «розділяй і
володарюй», на якому воно побудоване. Читання займе близько 50 хвилин. Під прикладами коду стоїть справжній вивід з
Node 24.22.

Учора ви бачили, що прості сортування на випадкових даних роблять близько `n²/4` порівнянь. Сьогодні з'ясуємо, як
зменшити це до `n log₂ n`, звідки береться логарифм, чому сортування злиттям стабільне і чим воно платить за
швидкість.

**Після лекції ви зможете пояснити:**

- що таке прийом «розділяй і володарюй» і з яких трьох кроків він складається;
- як злиття двох відсортованих масивів робить не більше `n − 1` порівнянь і чому воно стабільне;
- чому сортування злиттям робить не більше `n log₂ n − n + 1` порівнянь, використовуючи дерево рекурсії;
- навіщо сортуванню злиттям додатковий масив і чому його виділяють один раз, а не на кожному рівні;
- де сортування злиттям трапляється на практиці: у бібліотеках мов, у зовнішньому сортуванні, у зв'язних списках.

## Від `n²` до `n log n`

Програма нижче нічого не сортує. Вона рахує за рекурентними співвідношеннями, скільки порівнянь потрібно сортуванню
злиттям у найкращому і найгіршому випадку, і ставить поруч середню кількість порівнянь сортування вставками, `n(n −
1)/4`. Звідки ці співвідношення, з'ясуємо далі в лекції.

```ts
// Передбачення кількості порівнянь сортування злиттям за рекурентним співвідношенням,
// у найгіршому і найкращому випадку, поруч із середнім числом для сортування вставками.
const worst = new Map<number, number>(), best = new Map<number, number>();
function W(n: number): number {          // кожне злиття робить n − 1 порівняння
  if (n <= 1) return 0;
  if (!worst.has(n)) worst.set(n, W(Math.ceil(n / 2)) + W(Math.floor(n / 2)) + n - 1);
  return worst.get(n)!;
}
function B(n: number): number {          // найкраще злиття порівнює лише коротшу половину
  if (n <= 1) return 0;
  if (!best.has(n)) best.set(n, B(Math.ceil(n / 2)) + B(Math.floor(n / 2)) + Math.floor(n / 2));
  return best.get(n)!;
}
for (const n of [1000, 1024, 2000, 4000, 8000]) {
  const lg = Math.log2(n);
  console.log(`n = ${String(n).padStart(4)}: злиття від ${String(B(n)).padStart(6)} до ${String(W(n)).padStart(6)}` +
    ` (n·log₂n − n + 1 = ${(n * lg - n + 1).toFixed(0).padStart(6)}); вставки в середньому ${(n * (n - 1) / 4).toFixed(0).padStart(8)}`);
}
```

Мапи `worst` і `best` запам'ятовують уже обчислені значення, щоб рекурсія не рахувала те саме багато разів. Вивід:

```
n = 1000: злиття від   4932 до   8977 (n·log₂n − n + 1 =   8967); вставки в середньому   249750
n = 1024: злиття від   5120 до   9217 (n·log₂n − n + 1 =   9217); вставки в середньому   261888
n = 2000: злиття від  10864 до  19953 (n·log₂n − n + 1 =  19933); вставки в середньому   999500
n = 4000: злиття від  23728 до  43905 (n·log₂n − n + 1 =  43864); вставки в середньому  3999000
n = 8000: злиття від  51456 до  95809 (n·log₂n − n + 1 =  95727); вставки в середньому 15998000
```

На восьми тисячах елементів сортування злиттям робить не більше 96 тисяч порівнянь навіть у найгіршому випадку, а
сортування вставками в середньому — 16 мільйонів. Коли `n` подвоюється, кількість порівнянь злиття росте трохи більше
ніж удвічі, а вставок — учетверо. Erickson нагадує, що сортування злиттям — один з перших алгоритмів для комп'ютерів
загального призначення: Джон фон Нейман розробив його в 1945 році для EDVAC.

## Розділяй і володарюй

CLRS описує прийом **«розділяй і володарюй»** трьома кроками:

1. **Розділити** задачу на кілька менших задач того самого виду.
2. **Володарювати**: розв'язати менші задачі рекурсивно, а зовсім малі — напряму.
3. **Поєднати** розв'язки менших задач у розв'язок цілої.

Для сортування злиттям ці кроки такі:

1. Розділити масив навпіл.
2. Відсортувати кожну половину рекурсивно. Масив з одного елемента вже відсортований, і на ньому рекурсія зупиняється.
3. Злити дві відсортовані половини в один відсортований масив.

Erickson підкреслює: перший крок тривіальний, другий робить «Recursion Fairy», тобто рекурсивний виклик, якому досить
довіряти, як у лекції дня 5 фази 0. Уся справжня робота — у злитті.

Приклад Erickson з літерами `S O R T I N G E X A M P L`:

```
вхід:                S O R T I N G E X A M P L
розділити:           S O R T I N   G E X A M P L
ліва відсортована:   I N O R S T   G E X A M P L
права відсортована:  I N O R S T   A E G L M P X
злити:               A E G I L M N O P R S T X
```

## Злиття

CLRS пояснює злиття картами. Дві стопки карт лежать на столі сорочкою донизу, кожна відсортована, найменша карта
згори. Щоразу беремо меншу з двох верхніх карт і кладемо у вихідну стопку. Коли одна стопка закінчилася, решту другої
перекладаємо цілком, нічого не порівнюючи.

Ось злиття двох відсортованих масивів у новий масив. Таке злиття корисне й саме по собі: так зливають дві стрічки
подій, відсортовані за часом, чи дві сторінки відповіді сервера.

```ts
// Злиття двох відсортованих масивів у новий, з лічильником порівнянь.
// Стабільність: при рівних ключах першим іде елемент з лівого масиву.
export function mergeSorted<T>(left: readonly T[], right: readonly T[], key: (x: T) => number): { out: T[]; compares: number } {
  const out: T[] = [];
  let i = 0, j = 0, compares = 0;
  while (i < left.length && j < right.length) {
    compares++;
    if (key(left[i]!) <= key(right[j]!)) out.push(left[i++]!);   // <= : рівний ключ — спершу лівий
    else out.push(right[j++]!);
  }
  while (i < left.length) out.push(left[i++]!);                    // одна з частин скінчилася:
  while (j < right.length) out.push(right[j++]!);                  // решту другої дописуємо без порівнянь
  return { out, compares };
}

const id = (x: number) => x;
for (const [a, b] of [[[1, 2, 3], [4, 5, 6]], [[1, 3, 5], [2, 4, 6]], [[4, 5, 6], [1, 2, 3]], [[1, 2, 6], [3, 4, 5]]]) {
  const r = mergeSorted(a!, b!, id);
  console.log(`[${a}] + [${b}] → [${r.out}], порівнянь ${r.compares}`);
}
```

```
[1,2,3] + [4,5,6] → [1,2,3,4,5,6], порівнянь 3
[1,3,5] + [2,4,6] → [1,2,3,4,5,6], порівнянь 5
[4,5,6] + [1,2,3] → [1,2,3,4,5,6], порівнянь 3
[1,2,6] + [3,4,5] → [1,2,3,4,5,6], порівнянь 5
```

**Скільки порівнянь.** Кожне порівняння відправляє один елемент у вихідний масив. Після останнього порівняння одна з
частин порожня, а в другій лишається щонайменше один елемент, який іде без порівняння. Тому порівнянь не більше `n −
1`, де `n` — сума довжин. Найменше порівнянь буває, коли одна частина цілком менша за другу: тоді порівнюється лише
коротша частина, як у першому і третьому рядках. Найбільше — коли елементи частин чергуються, як у другому рядку, або
коли найбільший елемент стоїть в одній частині, а решта перемішана, як у четвертому.

**Чому злиття стабільне.** Умова `<=` означає: якщо ключі рівні, першим іде елемент з лівої частини. А ліва частина в
сортуванні — це елементи, що у вхідному масиві стояли лівіше. Отже, рівні елементи зберігають порядок:

```ts
type Event = { at: number; source: string };
const feedA: Event[] = [{ at: 1, source: "A1" }, { at: 3, source: "A3" }, { at: 3, source: "A3'" }];
const feedB: Event[] = [{ at: 2, source: "B2" }, { at: 3, source: "B3" }];
console.log(mergeSorted(feedA, feedB, (e) => e.at).out.map((e) => e.source).join(" "));
```

```
A1 B2 A3 A3' B3
```

Три події з часом 3 вийшли в порядку «спершу обидві з лівої стрічки, потім з правої». Якби в умові стояло `<`, при
рівних ключах першим ішов би елемент з правої частини, і сортування стало б нестабільним. Саме таку умову, `A[i] <
A[j]`, має процедура `Merge` у книжці Erickson; розбір читання про це попереджає.

## Чому `n log n`

Нехай `C(n)` — найбільша кількість порівнянь для масиву з `n` елементів. Масив з одного елемента не потребує
порівнянь, а більший сортується двома рекурсивними викликами і одним злиттям:

```
C(1) = 0,    C(n) = C(⌈n/2⌉) + C(⌊n/2⌋) + n − 1.
```

Це рекурентне співвідношення з дня 6 фази 0, і найпростіше розв'язати його **деревом рекурсії**. Нехай `n = 2ᵏ`. На
верхньому рівні одне злиття `n` елементів. На наступному — два злиття по `n/2`. На рівні `i` — `2ⁱ` злиттів по `n/2ⁱ`
елементів. Кожен елемент на кожному рівні бере участь рівно в одному злитті.

```
рівень 0:  [            n             ]               злиття: не більше n − 1 порівнянь
рівень 1:  [    n/2    ] [    n/2    ]                 2 злиття: не більше n − 2
рівень 2:  [n/4] [n/4] [n/4] [n/4]                     4 злиття: не більше n − 4
   …
рівень k−1: 2ᵏ⁻¹ злиттів по 2 елементи                 не більше n − 2ᵏ⁻¹
рівень k:  n масивів з одного елемента                 порівнянь немає
```

Skiena рахує саме так: на рівні `i` не більше `n − 2ⁱ` порівнянь. Рівнів зі злиттями `k = log₂ n`. Сума:

```
(n − 1) + (n − 2) + (n − 4) + … + (n − 2ᵏ⁻¹) = k·n − (2ᵏ − 1) = n log₂ n − n + 1.
```

Для `n = 1024` це `1024 · 10 − 1024 + 1 = 9217`, і програма на початку лекції дала те саме число. Для `n`, що не є
степенем двійки, рівнів `⌈log₂ n⌉`, і формула дає наближену оцінку: у таблиці для 1000 рекурентне співвідношення дає
8977, а формула — 8967.

**Найкращий випадок.** Якщо кожне злиття порівнює лише коротшу половину, на кожному рівні виходить `n/2` порівнянь, і
разом `(n/2) log₂ n`. Так буває, наприклад, на вже відсортованому масиві. Sedgewick формулює обидві межі як твердження
F: сортування злиттям робить від `½ n log₂ n` до `n log₂ n` порівнянь для будь-якого масиву. Квадратичного випадку тут
немає зовсім, на відміну від сортування вставками і, як ви побачите завтра, quicksort.

Головна думка дерева: кожен рівень коштує `Θ(n)`, а рівнів `Θ(log n)`. Erickson називає це випадком «усі рівні
однакові». CLRS малює те саме дерево для часу: кожен з `log₂ n` рівнів коштує `c·n`, і разом `c·n log₂ n + c·n = Θ(n
log n)`.

**Нижня межа.** Sedgewick доводить у твердженні I, що жодне сортування порівняннями не може гарантувати менше ніж
`log₂(n!) ≈ n log₂ n` порівнянь, і робить висновок (твердження J), що сортування злиттям асимптотично оптимальне. Цю
межу план докладно розбере в день 11.

## Пам'ять: один додатковий масив

Злиття не можна зробити на місці простим способом. Skiena пояснює на прикладі: якщо зливати `{4, 5, 6}` і `{1, 2, 3}`,
що лежать поруч в одному масиві, і писати результат туди ж, то перші ж записи затруть елементи лівої половини раніше,
ніж їх прочитають. Тому злиття пише результат у **допоміжний масив**, а потім результат повертається на місце. CLRS
копіює обидві половини в масиви `L` і `R` і зливає назад, Sedgewick копіює ділянку в масив `aux`.

Тут ховається пастка з плану. Найпростіший запис сортування злиттям на JavaScript створює нові масиви на кожному
виклику: `slice` для половин і новий масив для злиття. Асимптотика від цього не змінюється, бо на кожному рівні
копіюється `n` елементів, тобто разом `n log₂ n` копіювань, стільки ж, скільки злиття й так переміщує. Але кожен
виклик ще й виділяє пам'ять під нові масиви: дві половини і результат злиття. Для мільйона елементів це кілька
мільйонів маленьких масивів, і прибиральник сміття мусить їх звільнити. Тому правильна реалізація виділяє **один**
допоміжний масив розміру `n` на початку і передає його в усі рекурсивні виклики. Sedgewick робить саме так. Це перший
пункт практики.

Глибина рекурсії тут не проблема: `⌈log₂ n⌉` рівнів, для мільйона елементів — 20 вкладених викликів. Переповнення
стека з лекції дня 5 фази 0 сортуванню злиттям не загрожує.

## Варіанти й покращення

**Знизу вгору.** Erickson зауважує, що фон Нейман і Голдстайн описали не рекурсивний варіант, а той, що тепер
називають сортуванням злиттям **знизу вгору**. Спершу зливають сусідні пари елементів, потім пари пар, потім четвірки,
і так далі, без рекурсії. Sedgewick (твердження H) показує, що для `n`, яке є степенем двійки, обидва варіанти роблять
ті самі порівняння, лише в іншому порядку.

**Три покращення Sedgewick.**

- Короткі шматки, наприклад до 15 елементів, сортувати вставками: на них вставки швидші, як ви бачили вчора. CLRS
  пропонує те саме в задачі 2-1.
- Перед злиттям перевірити, чи останній елемент лівої половини не більший за перший елемент правої. Якщо так, половини
  вже стоять у правильному порядку, і зливати не треба. Тоді на відсортованому масиві все сортування стає лінійним.
- Уникнути копіювання в допоміжний масив, міняючи ролі масивів на кожному рівні рекурсії.

**Зв'язні списки.** Skiena називає сортування злиттям чудовим для зв'язних списків: воно не потребує доступу за
номером, а два відсортовані списки можна злити, лише переставляючи посилання, без жодного допоміжного масиву.

**Зовнішнє сортування.** Коли дані не вміщуються в пам'ять, їх сортують шматками, записують відсортовані шматки на
диск і потім зливають, читаючи кожен шматок послідовно. Послідовне читання — найдешевший спосіб працювати з диском, і
злиття читає саме так.

**Бібліотеки.** Документація Python пояснює, що стабільність `sort` дозволяє сортувати за кількома ключами кількома
проходами, і додає: «The Timsort algorithm used in Python does multiple sorts efficiently because it can take
advantage of any ordering already present in a dataset». Блог V8 «Getting things sorted in V8» описує Timsort, який з
версії 7.0 стоїть і за `Array.prototype.sort`, як «adaptive stable Mergesort variant». Він іде по масиву зліва направо
і шукає вже відсортовані ділянки. Надто короткі ділянки подовжує сортуванням вставками, а потім зливає ділянки між
собою. Тому вже відсортований масив стає однією ділянкою і сортується за `O(n)`, а найгірший випадок лишається `O(n
log n)`.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Скільки коштує сортування злиттям? | `Θ(n log n)` завжди: від `½ n log₂ n` до `n log₂ n` порівнянь; найгіршого квадратичного випадку немає. |
| Скільки пам'яті? | `Θ(n)` на допоміжний масив плюс `Θ(log n)` на стек рекурсії. |
| Чи стабільне? | Так, якщо при рівних ключах злиття бере елемент з лівої частини. |
| Скільки порівнянь робить злиття двох масивів загальною довжиною `n`? | Від довжини коротшого до `n − 1`. |
| Чим краще за quicksort? | Гарантований `n log n`, стабільність, послідовний доступ для списків і зовнішнього сортування. Гірше — додаткова пам'ять. |
| Як злити `k` відсортованих масивів? | Попарно, як рівні сортування злиттям, або купою з дня 10: `O(n log k)`. |

## Типові помилки

**Писати в умові злиття `<` замість `<=`.** Сортування стає нестабільним, і помилку не видно на числах, лише на
записах з однаковими ключами.

**Виділяти нові масиви на кожному виклику.** Асимптотика та сама, але більшість часу йде на виділення пам'яті.

**Забувати дописати залишок однієї з частин.** Після основного циклу одна з частин ще не порожня, і без двох
завершальних циклів її елементи губляться.

**Ділити масив так, що одна частина порожня.** Якщо середину для ділянки з двох елементів обчислити неправильно,
рекурсія викликає себе на тій самій ділянці і ніколи не закінчується. Перевірте, що обидві половини непорожні для
будь-якої ділянки з двох і більше елементів.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: показано лише злиття двох окремих масивів, а сортування з
одним допоміжним масивом ви пишете самі.

**1. `mergeSort(xs)`** з одним допоміжним масивом на весь виклик і з лічильником порівнянь. Рекурсивна функція отримує
масив, допоміжний масив і межі ділянки. Подумайте, де саме копіювати в допоміжний масив і звідки зливати назад.

**2. Перевірка `n = 1024`.** На випадковому масиві з 1024 чисел порівнянь має бути не більше 9217. На відсортованому
масиві — передбачте до запуску, скільки буде, і перевірте.

**3. Ріст.** Запустіть `mergeSort` і `insertionSort` з дня 2 фази 0 на випадкових масивах з `n = 1000, 2000, 4000,
8000` і запишіть кількість порівнянь. У скільки разів росте кожне число, коли `n` подвоюється?

**4. Стабільність.** Тест на записах з однаковими ключами: після сортування за ключем записи з рівним ключем стоять у
вхідному порядку. Перевірте, що тест падає, якщо в злитті замінити `<=` на `<`.

**5. Журнал.** Один рядок у `JOURNAL.md` і числа з пунктів 2–3 у `MEASUREMENTS.md`.

## Перевірте себе

**1. Скільки порівнянь зробить злиття `[1, 4, 9]` і `[2, 3, 10, 11]`?**

<details><summary>Відповідь</summary>

Порівняння: 1 з 2 — бере 1; 4 з 2 — бере 2; 4 з 3 — бере 3; 4 з 10 — бере 4; 9 з 10 — бере 9. Ліва частина порожня, і
10, 11 ідуть без порівнянь. Разом 5 порівнянь, а довжина `n = 7`, тож це менше за `n − 1 = 6`.

</details>

**2. Скільки рівнів має дерево рекурсії сортування злиттям для `n = 1000` і скільки — для мільйона?**

<details><summary>Відповідь</summary>

Рівнів зі злиттями `⌈log₂ n⌉`: для 1000 це 10, бо `2⁹ = 512 < 1000 ≤ 1024 = 2¹⁰`; для мільйона — 20, бо `2¹⁹ = 524 288
< 1 000 000 ≤ 2²⁰`. Разом з нижнім рівнем масивів з одного елемента — 11 і 21 рівень. Стільки ж і найбільша глибина
рекурсії.

</details>

**3. Чому злиття двох відсортованих половин не можна робити на місці простим записом результату в той самий масив?**

<details><summary>Відповідь</summary>

Результат пишеться з початку ділянки, а там лежать елементи лівої половини, які ще не прочитано. Якщо найменші
елементи лежать у правій половині, як у прикладі Skiena `{4, 5, 6}` і `{1, 2, 3}`, то перший же запис 1 на місце 4
знищить 4 раніше, ніж злиття його прочитає. Тому спершу ділянку копіюють у допоміжний масив і зливають з нього.

</details>

**4. Сортування злиттям на масиві з мільйона однакових чисел. Скільки порівнянь і чи зміниться порядок записів?**

<details><summary>Відповідь</summary>

З умовою `<=` кожне злиття бере всі елементи лівої частини першими: кожен лівий елемент порівнюється з першим правим і
йде у вихід. Після того як ліва частина скінчилася, права йде без порівнянь. Тож кожне злиття порівнює лише довжину
лівої частини, разом близько `(n/2) log₂ n ≈ 10` мільйонів порівнянь. Порядок записів не змінюється, бо сортування
стабільне.

</details>

**5. Чому сортування злиттям підходить для зв'язних списків краще, ніж для масивів?**

<details><summary>Відповідь</summary>

Злиття читає обидва вхідні шматки послідовно, від початку до кінця, і ніколи не потребує доступу за номером, а саме
цього список не вміє робити швидко. До того ж зливати списки можна, переставляючи посилання вузлів, тож допоміжний
масив розміру `n` не потрібен. Для масиву ж злиття без додаткової пам'яті складне.

</details>

**6. Що зміниться в кількості порівнянь, якщо перед кожним злиттям перевіряти, чи останній елемент лівої половини не
більший за перший елемент правої?**

<details><summary>Відповідь</summary>

Кожна перевірка — одне порівняння на виклик, тож на випадковому масиві порівнянь стане трохи більше: близько `n`
додаткових. Зате на відсортованому масиві жодне злиття не виконується, і сортування робить лише ці перевірки, тобто `n
− 1` порівняння замість `(n/2) log₂ n`. Для частково відсортованих даних, що часто трапляються на практиці, це великий
виграш.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| розділяй і володарюй | прийом: розділити задачу на менші того самого виду, розв'язати їх рекурсивно і поєднати розв'язки |
| злиття | об'єднання двох відсортованих послідовностей в одну відсортовану |
| допоміжний масив | масив, куди злиття пише результат, щоб не затерти непрочитані елементи |
| дерево рекурсії | рисунок усіх рекурсивних викликів з вартістю кожного; сума по рівнях дає загальну вартість |
| сортування злиттям знизу вгору | варіант без рекурсії: зливають пари, потім пари пар і так далі |
| зовнішнє сортування | сортування даних, що не вміщуються в пам'ять, шматками з подальшим злиттям |
| Timsort | сортування злиттям, що використовує вже впорядковані ділянки входу; стоїть у Python і V8 |
