# Лекція. Фаза 1, день 9. Випадковість і аналіз quicksort

Ця лекція пояснює, як випадковий вибір опорного елемента рятує quicksort від поганих входів, і доводить, що в
середньому він робить `Θ(n log n)` порівнянь. Читання займе близько 60 хвилин. Під прикладами коду стоїть справжній
вивід з Node 24.22.

Учора ви бачили, що quicksort з опорним першим елементом стає квадратичним саме на відсортованих даних, які в житті
трапляються постійно. Сьогодні з'ясуємо, що змінює випадковість, як рахувати середнє, не перебираючи всіх
перестановок, і що робити з масивами, де багато однакових значень.

**Після лекції ви зможете пояснити:**

- чим «середній випадок за випадковими входами» відрізняється від «очікуваного часу випадкового алгоритму»;
- що таке індикаторна випадкова величина і лінійність сподівання і чому разом вони рахують середні майже без зусиль;
- чому `i`-тий і `j`-тий за величиною елементи порівнюються з імовірністю `2/(j − i + 1)`;
- як із цих імовірностей виходить `2(n + 1)Hₙ − 4n ≈ 1,39 n log₂ n` порівнянь;
- чому масив з однакових значень ламає quicksort навіть з випадковим опорним і як допомагає розбиття на три частини;
- які дві поширені помилки з `Math.random` дають нерівномірну випадковість.

## Поганий вхід чи погане везіння

У quicksort з опорним першим елементом є конкретні погані входи: відсортований масив, зворотний масив. Хто знає
алгоритм, може такий вхід подати. Skiena формулює, що насправді обіцяє середня оцінка вчорашньої лекції: «Quicksort
runs in Θ(n log n) time, with high probability, if you give it randomly ordered data to sort». Тобто якщо самі дані
випадкові.

Але дані рідко випадкові. Тому випадковість переносять із даних в алгоритм. Є два способи:

- перемішати масив перед сортуванням, як робить Sedgewick;
- на кожному кроці вибирати опорний елемент випадково з ділянки, як робить CLRS: вибраний елемент міняють з останнім і
  далі розбивають як звичайно.

Тепер погана поведінка залежить не від входу, а лише від того, які випадкові числа випали. Skiena каже: «There is no
longer a well-defined "worst-case" input», і формулює нову обіцянку: «Randomized quicksort runs in Θ(n log n) time on
any input, with high probability». Найгірший випадок `n²/2` нікуди не зник, але тепер його не може підготувати
зловмисник, і він вимагає неймовірного невезіння.

Варто розрізняти два «середні»:

| | Середній випадок | Очікуваний час випадкового алгоритму |
|---|------------------|--------------------------------------|
| що випадкове | вхідні дані | вибір усередині алгоритму |
| для якого входу оцінка | у середньому по всіх входах | для **кожного** входу |
| чи є погані входи | так, конкретні | ні, лише невдалі випадкові вибори |
| приклад | сортування вставками в середньому `n²/4` | випадковий quicksort `≈ 1,39 n log₂ n` |

Випадковий quicksort завжди дає правильну відповідь, випадковий лише час. Такі алгоритми називають алгоритмами
**Лас-Вегаса**.

## Як рахувати середнє: індикаторні величини

Щоб порахувати середню кількість порівнянь, не треба перебирати всі `n!` порядків. CLRS і MCS дають прийом, що
розв'язує такі задачі майже механічно.

**Випадкова величина** — це число, що залежить від випадкового результату: кількість гербів у кидках монети, кількість
порівнянь у запуску сортування. MCS підкреслює, що назва вводить в оману: це не змінна, а функція від результату.

**Індикаторна випадкова величина** події `A` дорівнює 1, якщо подія сталася, і 0, якщо ні. Її **сподівання**, тобто
середнє значення, дорівнює ймовірності події: `E[I{A}] = 1 · Pr{A} + 0 · Pr{не A} = Pr{A}`.

**Лінійність сподівання**: сподівання суми дорівнює сумі сподівань, `E[X + Y] = E[X] + E[Y]`. MCS підкреслює головне:
«no independence is required». Величини можуть як завгодно залежати одна від одної, а рівність лишається правдивою.

Разом прийом такий: представити величину, яку рахуємо, сумою індикаторів, порахувати ймовірність кожної події і
скласти ймовірності.

Дві класичні задачі з читання. **Капелюхи** (MCS): `n` гостей здали капелюхи, а після вечері кожен отримав випадковий.
Скільки в середньому отримають свій? Індикатор `Gᵢ` — «`i`-тий гість отримав свій капелюх», його ймовірність `1/n`.
Сума `n` таких імовірностей — 1, хоч би скільки гостей. **Найм** (CLRS): кандидати приходять у випадковому порядку, і
ви наймаєте кожного, хто кращий за всіх попередніх. Індикатор «найняли `i`-того» має ймовірність `1/i`, бо `i`-тий
найкращий серед перших `i` з імовірністю `1/i`. Середня кількість наймів — `1 + 1/2 + … + 1/n = Hₙ ≈ ln n`.

Перевіримо обидві відповіді моделюванням:

```ts
// Індикаторні величини на двох задачах: капелюхи (нерухомі точки перестановки) і найм кращого кандидата.
function shuffle<T>(xs: T[]): T[] {                       // перемішування Фішера–Єйтса
  for (let i = xs.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));        // випадковий номер з 0 … i включно
    [xs[i], xs[j]] = [xs[j]!, xs[i]!];
  }
  return xs;
}
const trials = 100_000;
for (const n of [10, 1000]) {
  let ownHats = 0, hires = 0;
  for (let t = 0; t < trials; t++) {
    const p = shuffle(Array.from({ length: n }, (_, i) => i));
    let best = -1;
    for (let i = 0; i < n; i++) {
      if (p[i] === i) ownHats++;                          // i-й гість отримав свій капелюх
      if (p[i]! > best) { best = p[i]!; hires++; }        // i-й кандидат кращий за всіх попередніх
    }
  }
  let h = 0; for (let k = 1; k <= n; k++) h += 1 / k;
  console.log(`n = ${n}: свій капелюх у середньому ${(ownHats / trials).toFixed(3)}; наймів ${(hires / trials).toFixed(3)}, H(n) = ${h.toFixed(3)}`);
}
```

```
n = 10: свій капелюх у середньому 1.004; наймів 2.927, H(n) = 2.929
n = 1000: свій капелюх у середньому 0.999; наймів 7.478, H(n) = 7.485
```

Ні в одній із задач не знадобився розподіл усієї величини: скільки перестановок мають рівно 3 нерухомі точки, ніхто не
рахував. Досить імовірності кожної окремої події.

## Скільки порівнянь робить випадковий quicksort

CLRS рахує тим самим прийомом. Позначимо елементи за зростанням `z₁ < z₂ < … < zₙ`, усі різні. Нехай `Xᵢⱼ` — індикатор
події «`zᵢ` і `zⱼ` порівнювалися».

**Кожна пара порівнюється щонайбільше один раз.** Розбиття порівнює елементи лише з опорним, а опорний після розбиття
стоїть на своєму місці і в рекурсію не потрапляє. Тому загальна кількість порівнянь — це просто `X = Σ Xᵢⱼ` по всіх
парах `i < j`, і за лінійністю `E[X] = Σ Pr{zᵢ і zⱼ порівнювалися}`.

**Коли пара порівнюється.** Розгляньмо елементи між ними за величиною: `zᵢ, zᵢ₊₁, …, zⱼ`, усього `j − i + 1`
елементів. Поки опорним не вибрано жодного з них, усі вони лежать в одній ділянці, бо кожне розбиття кидає їх разом в
один бік. Перший опорний з цієї групи вирішує долю пари:

- якщо це `zᵢ` чи `zⱼ`, він порівнюється з усіма елементами ділянки, зокрема з другим елементом пари;
- якщо це будь-який елемент між ними, `zᵢ` іде ліворуч, а `zⱼ` праворуч, і вони більше ніколи не зустрінуться.

Опорний вибирається випадково, тож кожен з `j − i + 1` елементів групи однаково ймовірно стане першим. Сприятливих
варіантів два, отже

```
Pr{zᵢ і zⱼ порівнювалися} = 2 / (j − i + 1).
```

Сусіди за величиною (`j = i + 1`) порівнюються завжди: інакше ніхто не дізнався б, хто з них менший. Найменший і
найбільший елементи порівнюються лише тоді, коли один з них стане найпершим опорним усього масиву.

Перевіримо формулу моделюванням. Нам не потрібен сам quicksort: досить змоделювати порядок, у якому елементи стають
опорними. Для цього кожному елементу дають випадковий «пріоритет», і менший пріоритет означає «став опорним раніше»:

```ts
// Імовірність, що quicksort з випадковим опорним порівняє i-й і j-й за величиною елементи.
// Достатньо змоделювати порядок, у якому елементи стають опорними: випадкова перестановка «пріоритетів».
// Пара порівнюється тоді й лише тоді, коли першим опорним серед i, i+1, …, j стає i або j.
const n = 100, trials = 200_000;
const pairs: [number, number][] = [[1, 2], [1, 10], [40, 60], [1, 100]];
const hits = pairs.map(() => 0);
const prio = new Float64Array(n + 1);
for (let t = 0; t < trials; t++) {
  for (let k = 1; k <= n; k++) prio[k] = Math.random();   // менший пріоритет — раніше став опорним
  pairs.forEach(([i, j], idx) => {
    let first = i;
    for (let k = i + 1; k <= j; k++) if (prio[k]! < prio[first]!) first = k;
    if (first === i || first === j) hits[idx]!++;
  });
}
pairs.forEach(([i, j], idx) =>
  console.log(`пара (${i}, ${j}): виміряно ${(hits[idx]! / trials).toFixed(4)}, формула 2/(j − i + 1) = ${(2 / (j - i + 1)).toFixed(4)}`));

// Сума ймовірностей по всіх парах — очікувана кількість порівнянь.
for (const m of [100, 2000]) {
  let sum = 0;
  for (let i = 1; i < m; i++) for (let j = i + 1; j <= m; j++) sum += 2 / (j - i + 1);
  let h = 0; for (let k = 1; k <= m; k++) h += 1 / k;
  console.log(`n = ${m}: сума 2/(j − i + 1) = ${sum.toFixed(1)}, 2(n + 1)H(n) − 4n = ${(2 * (m + 1) * h - 4 * m).toFixed(1)}`);
}
```

```
пара (1, 2): виміряно 1.0000, формула 2/(j − i + 1) = 1.0000
пара (1, 10): виміряно 0.2001, формула 2/(j − i + 1) = 0.2000
пара (40, 60): виміряно 0.0953, формула 2/(j − i + 1) = 0.0952
пара (1, 100): виміряно 0.0204, формула 2/(j − i + 1) = 0.0200
n = 100: сума 2/(j − i + 1) = 647.9, 2(n + 1)H(n) − 4n = 647.9
n = 2000: сума 2/(j − i + 1) = 24729.8, 2(n + 1)H(n) − 4n = 24729.8
```

Ймовірність залежить лише від відстані `j − i` між елементами за величиною, а не від їхнього положення в масиві: пари
`(1, 10)` і `(40, 60)` мають відстань 9 і 20 і поводяться відповідно.

**Сума.** Пар з відстанню `d = j − i` рівно `n − d`. Тому

```
E[X] = Σ_{d=1}^{n−1} (n − d) · 2/(d + 1) ≤ 2n · (1/2 + 1/3 + … + 1/n) < 2n Hₙ = O(n log n).
```

Точне значення — `2(n + 1)Hₙ − 4n`, те саме число, що вчорашня таблиця дала для середнього випадку детермінованого
quicksort на випадковому вході: для `n = 2000` це 24 730. Це не збіг: випадковий вибір опорного на будь-якому вході
поводиться так само, як детермінований вибір на випадковому вході. Різниця в тому, що тепер ця оцінка правдива для
відсортованого масиву теж.

CLRS доводить меншу оцінку тим самим шляхом і робить висновок: очікуваний час випадкового quicksort на масиві з різних
елементів — `O(n lg n)`, а разом з найкращим випадком `Ω(n lg n)` — `Θ(n lg n)`.

## Наскільки результат розкиданий

Середнє ще не все: може, половина запусків швидкі, а половина повільні? Sedgewick повідомляє, що стандартне відхилення
кількості порівнянь — близько `0,65n`. Для `n = 2000` це близько 1300 на тлі середнього 24 730, тобто кілька
відсотків. І навіть груба нерівність Чебишова дає для мільйона елементів імовірність перевищити середнє вдесятеро
меншу за `0,00001`.

Skiena пояснює це інтуїтивно. Назвемо опорний елемент **досить добрим**, якщо він лежить у середній половині значень,
між `n/4`-тим і `3n/4`-тим. Випадковий опорний досить добрий з імовірністю 1/2. Досить добрий залишає не більше `3n/4`
елементів у більшій частині, тож після `log_{4/3} n` досить добрих виборів ділянки стають одиничними. А поганий вибір
лише марнує один рівень, не зіпсувавши нічого. Тому дерево рекурсії має висоту `O(log n)` з великою ймовірністю.
Skiena додає, що середня висота такого дерева — `2 ln n ≈ 1,386 lg n`, лише на 39 % більше за ідеально збалансоване.

Практика дня перевірить це на ваших числах: сто запусків на відсортованому масиві і найбільше відхилення від медіани.

## Однакові значення

CLRS прямо оговорює, що аналіз вище припускає різні елементи (задача 7-2 розглядає інший випадок). Масив з самих
однакових чисел ламає quicksort навіть з випадковим опорним: хоч би який елемент вибрано, розбиття Ломуто відправить
усі інші в одну частину, бо всі вони «не більші за опорний». Ділянка зменшується на один елемент за рівень, і час
знову `n²/2`.

Виправлення — **розбиття на три частини**: менші за опорний, рівні йому і більші. Рівні вже стоять на місцях, і в
рекурсію йдуть лише крайні частини. Масив з однакових чисел сортується за один прохід. Sedgewick описує це як задачу
**голландського прапора**, яку популяризував Дейкстра: розкласти кульки трьох кольорів так, щоб вийшли три смуги.
Розбиття тримає три межі: `lt`, `i`, `gt`.

```
 lo         lt         i              gt         hi
 [  < v ... ][  = v ... ][ ще не бачені ][  > v ... ]
```

Вказівник `i` іде зліва направо, і для кожного елемента є три випадки. Менший за `v` — міняється з елементом на `lt`,
обидва вказівники зсуваються. Рівний `v` — просто зсувається `i`. Більший за `v` — міняється з елементом на `gt`, `gt`
зсувається ліворуч, а `i` лишається на місці, бо елемент, що прийшов з `gt`, ще не бачений.

Простежимо масив `[2, 1, 2, 3, 2, 1]` з опорним `v = 2`:

| Крок | `lt` | `i` | `gt` | Масив | Що зроблено |
|------|------|-----|------|-------|-------------|
| 0 | 0 | 0 | 5 | `2 1 2 3 2 1` | — |
| 1 | 0 | 1 | 5 | `2 1 2 3 2 1` | `a[0] = 2 = v`: `i++` |
| 2 | 1 | 2 | 5 | `1 2 2 3 2 1` | `a[1] = 1 < v`: обмін `a[0] ↔ a[1]`, `lt++`, `i++` |
| 3 | 1 | 3 | 5 | `1 2 2 3 2 1` | `a[2] = 2 = v`: `i++` |
| 4 | 1 | 3 | 4 | `1 2 2 1 2 3` | `a[3] = 3 > v`: обмін `a[3] ↔ a[5]`, `gt--` |
| 5 | 2 | 4 | 4 | `1 1 2 2 2 3` | `a[3] = 1 < v`: обмін `a[1] ↔ a[3]`, `lt++`, `i++` |
| 6 | 2 | 5 | 4 | `1 1 2 2 2 3` | `a[4] = 2 = v`: `i++`; тепер `i > gt`, кінець |

Менші стоять на позиціях 0–1, рівні — 2–4, більший — 5. У рекурсію йдуть лише `[1, 1]` і `[3]`. Код ви напишете в
практиці.

## Випадковість у JavaScript

Випадкові алгоритми потребують рівномірної випадковості, і в JavaScript легко зробити її нерівномірною. Програма нижче
показує дві поширені помилки:

```ts
// Дві поширені помилки з випадковістю: номер через Math.round і перемішування через sort.
const trials = 600_000;

// 1. Випадкове ціле від 1 до 6 включно.
const viaRound = new Array<number>(7).fill(0), viaFloor = new Array<number>(7).fill(0);
for (let t = 0; t < trials; t++) {
  viaRound[1 + Math.round(Math.random() * 5)]!++;          // неправильно
  viaFloor[1 + Math.floor(Math.random() * 6)]!++;          // правильно
}
console.log("Math.round:", viaRound.slice(1).map((c) => (c / trials * 100).toFixed(1) + "%").join(" "));
console.log("Math.floor:", viaFloor.slice(1).map((c) => (c / trials * 100).toFixed(1) + "%").join(" "));

// 2. Перемішування масиву [0..9]: де опиняється елемент 0.
function fisherYates(xs: number[]): number[] {
  for (let i = xs.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [xs[i], xs[j]] = [xs[j]!, xs[i]!];
  }
  return xs;
}
const n = 10, runs = 100_000;
const bySort = new Array<number>(n).fill(0), byFY = new Array<number>(n).fill(0);
for (let t = 0; t < runs; t++) {
  const a = Array.from({ length: n }, (_, i) => i).sort(() => Math.random() - 0.5);
  bySort[a.indexOf(0)]!++;
  byFY[fisherYates(Array.from({ length: n }, (_, i) => i)).indexOf(0)]!++;
}
console.log("sort з випадковим компаратором, де опинився 0:", bySort.map((c) => (c / runs * 100).toFixed(0) + "%").join(" "));
console.log("Фішер–Єйтс, де опинився 0:                   ", byFY.map((c) => (c / runs * 100).toFixed(0) + "%").join(" "));
```

```
Math.round: 9.9% 20.0% 20.1% 20.0% 20.0% 10.0%
Math.floor: 16.7% 16.6% 16.6% 16.7% 16.7% 16.7%
sort з випадковим компаратором, де опинився 0: 19% 14% 9% 7% 7% 7% 8% 8% 9% 10%
Фішер–Єйтс, де опинився 0:                    10% 10% 10% 10% 10% 10% 10% 10% 10% 10%
```

**`Math.round` замість `Math.floor`.** `Math.random() * 5` дає число від 0 до 5. Округлення дає 1 для чисел від 0,5 до
1,5, а 0 — лише для чисел від 0 до 0,5. Тому крайні значення випадають удвічі рідше. MDN попереджає про це прямо:
`Math.round` дає «a non-uniform distribution». Правильно — `Math.floor(Math.random() * k)`, що дає числа від 0 до `k −
1` з однаковою ймовірністю.

**Перемішування через `sort` з випадковим компаратором.** Компаратор, що повертає випадковий знак, порушує вимоги MDN
з учорашнього розбору читання: він не стабільний і не транзитивний. Сортування з таким компаратором не дає рівномірної
перестановки: нуль лишився на першому місці майже вдвічі частіше, ніж мав би. Правильний спосіб — алгоритм
**Фішера–Єйтса**: для кожної позиції з кінця вибрати випадковий елемент серед ще не поставлених і поміняти. Кожна з
`n!` перестановок виходить з однаковою ймовірністю.

Ще одна річ, яку варто знати: MDN нагадує, що `Math.random()` — не криптографічно надійний генератор. Для quicksort це
неважливо, але для токенів, паролів і всього, що має бути непередбачуваним для зловмисника, потрібен
`crypto.getRandomValues()`.

## Чи можна обдурити випадковий quicksort

Примітки до глави 7 CLRS згадують роботу Макілроя, що будує «killer adversary»: вхід, на якому практично будь-яка
реалізація quicksort працює `Θ(n²)`. Він працює проти реалізацій, де опорний вибирається передбачувано, зокрема
«медіаною з трьох». Справжня випадковість, яку зловмисник не бачить, від цього захищає.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Навіщо випадковий опорний? | Щоб не було конкретних поганих входів: очікуваний час `Θ(n log n)` для будь-якого масиву з різних елементів. |
| Як довести `Θ(n log n)`? | Індикатор на кожну пару; пара `zᵢ, zⱼ` порівнюється з імовірністю `2/(j − i + 1)`; сума дає `2(n + 1)Hₙ − 4n`. |
| Що таке лінійність сподівання? | Сподівання суми дорівнює сумі сподівань, навіть для залежних величин. |
| Чи допомагає випадковий опорний на однакових значеннях? | Ні; потрібне розбиття на три частини. |
| Як правильно перемішати масив? | Фішер–Єйтс; не `sort` з випадковим компаратором. |
| Чим алгоритм Лас-Вегаса відрізняється від Монте-Карло? | Лас-Вегас завжди правильний, випадковий лише час; Монте-Карло має обмежений час, але може помилитися. |

## Типові помилки

**Плутати середній випадок і очікуваний час.** Перший — середнє по входах, і погані входи існують. Другий — середнє по
випадкових виборах для кожного входу.

**Вважати, що випадковий опорний розв'язує все.** Масив з однакових значень лишається квадратичним без розбиття на три
частини.

**Брати `Math.round` для випадкового номера.** Крайні номери випадають удвічі рідше.

**Перемішувати через `sort(() => Math.random() - 0.5)`.** Перестановки виходять нерівноймовірними.

**Вибирати випадковий номер з неправильного проміжку.** Опорний має вибиратися з усієї поточної ділянки `lo … hi`
включно, а не з `0 … n − 1` чи з `lo … hi − 1`.

## Перевірте себе

**1. Яка ймовірність, що випадковий quicksort порівняє найменший і найбільший елементи масиву з 1000 різних чисел?**

<details><summary>Відповідь</summary>

`i = 1`, `j = 1000`, тож `2/(j − i + 1) = 2/1000 = 0,002`. Вони порівнюються лише тоді, коли найпершим опорним усього
масиву стане один з них. Будь-який інший перший опорний відправить їх у різні частини.

</details>

**2. Чому кожна пара елементів порівнюється не більше одного разу?**

<details><summary>Відповідь</summary>

Розбиття порівнює елементи лише з опорним. Щоб пара порівнялася, один з її елементів мусить бути опорним. Після
розбиття опорний стоїть на своєму місці і в жодну рекурсію не потрапляє, тож більше ні з чим не порівнюється. Тому
другого порівняння тієї самої пари бути не може.

</details>

**3. Скільки в середньому гостей отримають свій капелюх, якщо гостей мільйон? Чому відповідь не залежить від `n`?**

<details><summary>Відповідь</summary>

Один. Кожен з `n` гостей отримує свій капелюх з імовірністю `1/n`, і за лінійністю сподівання сума `n` таких
імовірностей — `n · 1/n = 1`. Лінійність не вимагає незалежності, хоча події тут залежні: якщо `n − 1` гостей отримали
свої, останній теж отримав свій.

</details>

**4. Розбиття на три частини на масиві з `n` елементів, де всього `k` різних значень. Чому кількість порівнянь
залежить від `k`, а не від `n log n`?**

<details><summary>Відповідь</summary>

Кожне розбиття ставить на місце не один елемент, а всі, рівні опорному. Після цього рівні в рекурсію не йдуть. Тож
кожне значення бере участь в опорному розбитті лише раз, і рекурсія має не більше `k` розбиттів з непорожньою
середньою частиною на шляху до кожного значення. Sedgewick оцінює кількість порівнянь через ентропію `H` частот
значень; коли значень мало, `H` мале, і сортування майже лінійне. Для `k = 1` вистачає одного проходу.

</details>

**5. Чому вираз `lo + Math.floor(Math.random() * (hi - lo))` дає неправильний опорний?**

<details><summary>Відповідь</summary>

`Math.random()` дає числа з `[0, 1)`, тож `Math.floor(Math.random() * (hi − lo))` дає від 0 до `hi − lo − 1`, і номер
виходить від `lo` до `hi − 1`. Останній елемент ділянки ніколи не стане опорним. Щоб `hi` теж міг випасти, множити
треба на `hi − lo + 1`.

</details>

**6. За оцінкою Sedgewick стандартне відхилення порівнянь — близько `0,65n`. У скільки разів воно менше за середнє для
`n = 10⁶`?**

<details><summary>Відповідь</summary>

Середнє `≈ 2n ln n ≈ 2 · 10⁶ · 13,8 ≈ 2,76 · 10⁷`, відхилення `≈ 6,5 · 10⁵`. Відношення близько 42: відхилення
становить близько 2,4 % середнього. З ростом `n` середнє росте як `n ln n`, а відхилення — як `n`, тож відносний
розкид спадає, і час випадкового quicksort стає дедалі передбачуванішим.

</details>
