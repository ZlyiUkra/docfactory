# Лекція. Фаза 1, день 11. Нижня межа і сортування без порівнянь

Ця лекція доводить, що жодне сортування порівняннями не може бути швидшим за `n log n` у найгіршому випадку, і
показує, як обійти цю межу, коли ключі — невеликі цілі числа. Читання займе близько 50 хвилин. Під прикладами коду
стоїть справжній вивід з Node 24.22.

За останні дні ви бачили три сортування за `n log n`: злиттям, quicksort і купою. Природне питання: чи можна ще
швидше? Сьогодні з'ясуємо, що порівняннями — ні, і чому, а потім подивимося на сортування, які взагалі не порівнюють
елементи і тому працюють за лінійний час.

**Після лекції ви зможете пояснити:**

- що таке модель обчислень і чому нижня межа завжди стосується конкретної моделі;
- як дерево рішень описує будь-яке сортування порівняннями і чому його висота не менша за `log₂(n!)`;
- чому `log₂(n!) = Θ(n log n)` і скільки порівнянь мінімально потрібно для 10 елементів;
- як сортування підрахунком сортує за `Θ(n + k)`, не порівнюючи елементи;
- чому порозрядне сортування йде від молодшого розряду і чому кожен прохід мусить бути стабільним;
- коли сортування без порівнянь справді швидше, а коли ні.

## Скільки запитань треба поставити

Erickson відкриває конспект про нижні межі сценою з «Різдвяної пісні» Діккенса: гра «так і ні», де загадали дядька
Скруджа. Це та сама гра, що «двадцять запитань» з лекції про бінарний пошук. Якщо можливих відповідей `N`, а кожне
запитання має два варіанти відповіді, то запитань потрібно щонайменше `⌈log₂ N⌉`: кожна відповідь щонайбільше вдвічі
зменшує кількість можливостей.

Сортування — та сама гра. Масив з `n` різних елементів може стояти в будь-якому з `n!` порядків. Алгоритм має
з'ясувати, у якому саме, і щоб відповісти правильно, мусить відрізнити кожен порядок від кожного. Порівняння `aᵢ ≤ aⱼ`
— запитання з двома відповідями.

## Модель обчислень

Нижню межу не можна довести «для всіх алгоритмів узагалі», бо Erickson нагадує: «there is no formal definition of the
phrase "all algorithms"». Треба спершу сказати, які дії алгоритм може виконувати і що вважаємо кроком. Це називають
**моделлю обчислень**.

**Модель порівнянь**: алгоритм дізнається про елементи лише порівнюючи їх парами. Він не може дивитися на біти числа,
брати його як номер масиву чи рахувати хеш. CLRS підкреслює: сортування порівняннями «may not inspect the values of
the elements or gain order information about them in any other way». У цій моделі працюють усі сортування, які ви
бачили: вставками, вибором, злиттям, quicksort, купою. Erickson додає, що вони трактують два входи однаково, якщо
порівняння дають однакові результати: важать не значення, а лише їхній порядок.

## Дерево рішень

Будь-яке сортування порівняннями для фіксованого `n` можна намалювати **деревом рішень**. Кожен внутрішній вузол —
порівняння `aᵢ ≤ aⱼ`. Ліве піддерево — що робить алгоритм, якщо відповідь «так», праве — якщо «ні». Кожен лист —
відповідь, тобто порядок елементів. Запуск алгоритму на конкретному вході — шлях від кореня до листа.

CLRS малює дерево сортування вставками для трьох елементів:

```
                        a1 ≤ a2 ?
                  так /           \ ні
               a2 ≤ a3 ?           a1 ≤ a3 ?
            так /     \ ні      так /     \ ні
       ⟨1,2,3⟩     a1 ≤ a3 ?  ⟨2,1,3⟩     a2 ≤ a3 ?
               так /     \ ні          так /     \ ні
            ⟨1,3,2⟩    ⟨3,1,2⟩      ⟨2,3,1⟩    ⟨3,2,1⟩
```

Лист `⟨3, 1, 2⟩` означає «`a₃ ≤ a₁ ≤ a₂`». CLRS простежує вхід `⟨6, 8, 5⟩`: `6 ≤ 8` — так; `8 ≤ 5` — ні; `6 ≤ 5` — ні;
лист `⟨3, 1, 2⟩`, тобто `5, 6, 8`. Листків шість, по одному на кожен з `3! = 6` порядків, а найдовший шлях має три
порівняння.

**Найгірша кількість порівнянь дорівнює висоті дерева**: найдовший шлях від кореня до листа. Отже, щоб довести нижню
межу для всіх сортувань порівняннями, досить довести нижню межу висоти для всіх дерев, що правильно сортують.

**Доведення.** Правильне сортування мусить уміти видати кожен з `n!` порядків, тож дерево має щонайменше `n!` листків.
Двійкове дерево висоти `h` має не більше `2ʰ` листків. Тому `n! ≤ 2ʰ`, і

```
h ≥ log₂(n!).
```

Це теорема 8.1 CLRS. Вона стосується **будь-якого** сортування порівняннями, навіть ще не придуманого.

## Скільки це

Програма рахує `log₂(n!)` для кількох `n` і порівнює з наближенням за формулою Стірлінга:

```ts
// Нижня межа сортування порівняннями: дерево рішень має щонайменше n! листків, тож висоту не меншу за log₂(n!).
function log2Factorial(n: number): number {
  let s = 0;
  for (let k = 2; k <= n; k++) s += Math.log2(k);
  return s;
}
for (const n of [3, 4, 5, 10, 12, 100, 1_000_000]) {
  const lb = log2Factorial(n);
  const approx = n * Math.log2(n) - n * Math.log2(Math.E);           // з формули Стірлінга
  console.log(`n = ${n}: log₂(n!) = ${lb.toFixed(2)}, найменша висота дерева ${Math.ceil(lb)};` +
    ` n·log₂n − n·log₂e = ${approx.toFixed(2)}`);
}
```

```
n = 3: log₂(n!) = 2.58, найменша висота дерева 3; n·log₂n − n·log₂e = 0.43
n = 4: log₂(n!) = 4.58, найменша висота дерева 5; n·log₂n − n·log₂e = 2.23
n = 5: log₂(n!) = 6.91, найменша висота дерева 7; n·log₂n − n·log₂e = 4.40
n = 10: log₂(n!) = 21.79, найменша висота дерева 22; n·log₂n − n·log₂e = 18.79
n = 12: log₂(n!) = 28.84, найменша висота дерева 29; n·log₂n − n·log₂e = 25.71
n = 100: log₂(n!) = 524.76, найменша висота дерева 525; n·log₂n − n·log₂e = 520.12
n = 1000000: log₂(n!) = 18488884.82, найменша висота дерева 18488885; n·log₂n − n·log₂e = 18488873.53
```

Логарифм суми — сума логарифмів, тож `log₂(n!) = log₂ 2 + log₂ 3 + … + log₂ n`; так програма його й рахує, не
обчислюючи величезного `n!`.

Для 10 елементів будь-яке сортування порівняннями мусить у найгіршому випадку зробити щонайменше 22 порівняння. Для
трьох — 3, і дерево вставок вище цю межу досягає.

**Чому `log₂(n!) = Θ(n log n)`.** Зверху: `n! ≤ nⁿ`, тож `log₂(n!) ≤ n log₂ n`. Знизу MIT дає простий аргумент:
половина множників `n!` не менша за `n/2`, тож `n! ≥ (n/2)^(n/2)` і `log₂(n!) ≥ (n/2) log₂(n/2) = Ω(n log n)`.
Erickson бере формулу Стірлінга `n! > (n/e)ⁿ`, звідки `log₂(n!) > n log₂ n − n log₂ e`. Останній стовпець програми
показує, що вже для мільйона елементів це наближення відрізняється від точного значення лише на 11.

**Наслідок.** Сортування злиттям і купою роблять `O(n log n)` порівнянь у найгіршому випадку, тож вони **асимптотично
оптимальні** в моделі порівнянь: CLRS формулює це як наслідок 8.2. Злиття близьке до межі навіть за сталою: `n log₂ n
− n + 1` проти `log₂(n!) ≈ n log₂ n − 1,44n`.

## Межа стосується моделі

Erickson ставить провокаційне запитання: хеш-таблиця знаходить ключ за `O(1)` в середньому, а нижня межа пошуку `Ω(log
n)`. Суперечність? Ні: обчислення хешу — запитання з `m` відповідями, а не з двома, і модель порівнянь його не
дозволяє. Erickson підсумовує: «choosing the right model of computation is absolutely crucial». Нижня межа сортування
`Ω(n log n)` правдива лише для алгоритмів, що порівнюють. Якщо дозволити використовувати значення ключа як номер
масиву, межа зникає.

## Сортування підрахунком

**Сортування підрахунком** працює для цілих ключів від 0 до `k − 1`. Воно не порівнює елементи зовсім:

1. Порахувати, скільки разів трапляється кожен ключ: масив лічильників `c` довжини `k`.
2. Перетворити лічильники на **накопичені суми**: тепер `c[v]` — кількість елементів з ключем, не більшим за `v`.
   Отже, останній елемент з ключем `v` має стати на місце `c[v] − 1`.
3. Пройти вхід **з кінця** і класти кожен елемент на місце `c[його ключ] − 1`, зменшуючи лічильник.

Простежимо масив `[3, 1, 0, 3, 1]` з ключами від 0 до 3:

| Крок | Лічильники `c[0..3]` | Вихід |
|------|----------------------|-------|
| підрахунок | `1 2 0 2` | — |
| накопичені суми | `1 3 3 5` | — |
| `a[4] = 1` → місце `3 − 1 = 2` | `1 2 3 5` | `. . 1 . .` |
| `a[3] = 3` → місце `5 − 1 = 4` | `1 2 3 4` | `. . 1 . 3` |
| `a[2] = 0` → місце `1 − 1 = 0` | `0 2 3 4` | `0 . 1 . 3` |
| `a[1] = 1` → місце `2 − 1 = 1` | `0 1 3 4` | `0 1 1 . 3` |
| `a[0] = 3` → місце `4 − 1 = 3` | `0 1 3 3` | `0 1 1 3 3` |

**Час `Θ(n + k)`**: два проходи по входу і два по лічильниках. Якщо `k = O(n)`, це лінійно. CLRS пояснює, чому межа
`Ω(n log n)` тут не діє: «no comparisons between input elements occur anywhere in the code». Morin формулює те саме
інакше: присвоєння `c[a[i]] = …` має `k` різних результатів залежно від `a[i]`, тож дерево рішень такого алгоритму вже
не двійкове.

**Стабільність.** Прохід з кінця робить сортування стабільним: з двох однакових ключів правіший у вході кладеться
першим, на більше місце, тож у виході він теж правіший. Подивіться на одиниці в трасуванні: `a[4]` стала на місце 2, а
`a[1]` — на місце 1. Вправа 8.2-3 CLRS питає, що буде, якщо йти з початку: сортування лишиться правильним, але
перестане бути стабільним. Навіщо стабільність тут, якщо сортуються числа? Бо на практиці сортують записи за ключем, і
бо від неї залежить порозрядне сортування.

**Коли не годиться.** Якщо ключі — 32-бітні числа, `k = 2³²`, і масив лічильників займає 16 ГБ. MIT показує той самий
підхід як сортування масивом прямого доступу і зауважує, що час `Θ(u)` годиться лише тоді, коли `u = Θ(n)`.

## Порозрядне сортування

CLRS починає з історії: порозрядне сортування робили механічні сортувальники перфокарт, які сьогодні стоять лише в
музеях. Машина розкладала карти на 10 стопок за однією цифрою, а оператор збирав стопки по порядку.

Ідея: представити кожен ключ як кілька **розрядів** і відсортувати стабільним сортуванням за кожним розрядом, **від
молодшого до старшого**. Простежимо шість тризначних чисел:

| Вхід | Після сортування за одиницями | Після сортування за десятками | Після сортування за сотнями |
|------|-------------------------------|-------------------------------|-----------------------------|
| 329 | 72**0** | 7**2**0 | **3**29 |
| 457 | 43**6** | 3**2**9 | **4**36 |
| 657 | 45**7** | 4**3**6 | **4**57 |
| 839 | 65**7** | 8**3**9 | **6**57 |
| 436 | 32**9** | 4**5**7 | **7**20 |
| 720 | 83**9** | 6**5**7 | **8**39 |

Чому це працює. Після сортування за десятками числа впорядковані за останніми двома цифрами: за десятками, а при
однакових десятках — за одиницями, бо стабільне сортування не переставило те, що вже впорядкував попередній прохід.
Подивіться на 329 і 720 у третьому стовпці: обидва мають десятки 2, і 720 стоїть першим, бо `20 < 29`. Індукцією за
кількістю проходів після останнього прохіду числа впорядковані за всіма розрядами.

**Без стабільності все ламається.** Якби сортування за сотнями поставило 457 перед 436 (обидва мають сотні 4),
результат був би неправильним, хоча за сотнями все впорядковано. Це пастка з плану: один нестабільний прохід знищує
порядок, створений усіма попередніми.

**Чому від молодшого.** CLRS пояснює: якщо сортувати від старшого розряду, кожну з 10 стопок доводиться сортувати
окремо далі, і з'являється багато проміжних стопок. Від молодшого розряду щоразу сортують усю колоду цілком, а
стабільність зберігає зроблене.

**Скільки коштує.** Якщо ключі мають `d` розрядів по `k` значень, кожен прохід підрахунком коштує `Θ(n + k)`, а разом
`Θ(d(n + k))` (лема 8.3 CLRS). Для `b`-бітних чисел, розбитих на розряди по `r` бітів, проходів `b/r`, а значень у
розряді `2^r`, тож час `Θ((b/r)(n + 2^r))` (лема 8.4). Наприклад, 32-бітне число — це чотири розряди по 8 бітів, і
кожен прохід підрахунком використовує 256 лічильників. За формулою для `n = 10⁷`:

| Бітів у розряді `r` | Проходів | `(b/r)(n + 2^r)` |
|---------------------|----------|------------------|
| 4 | 8 | 80 000 128 |
| 8 | 4 | 40 001 024 |
| 11 | 3 | 29 096 867 |
| 16 | 2 | 20 131 072 |

Що більший розряд, то менше проходів, поки `2^r` малий порівняно з `n`. CLRS доводить, що найкраще `r ≈ log₂ n`. Але
формула не враховує кеш: масив з 65 536 лічильників уже не вміщується в найшвидший кеш процесора, і на практиці часто
беруть 8 бітів.

MIT описує той самий алгоритм через кортежі: ключ менший за `n^c` — це `c`-значне число в системі числення з основою
`n`, і сортування кортежів підрахунком за кожним розрядом займає `O(cn)`. Якщо `c` стале, сортування лінійне.

## Чи справді швидше

Лінійна асимптотика не гарантує виграшу. CLRS попереджає: кожен прохід порозрядного сортування довший, ніж прохід
quicksort, quicksort краще використовує кеш, а порозрядне сортування з підрахунком потребує допоміжного масиву. Що
швидше, залежить від реалізації, машини й даних.

У JavaScript є ще одна обставина. Програма нижче сортує мільйон випадкових 32-бітних беззнакових чисел звичайним
масивом з компаратором і типізованим масивом `Uint32Array` без компаратора:

```ts
// Сортування мільйона 32-бітних беззнакових чисел: звичайний масив з компаратором і Uint32Array.
function median(xs: number[]): number { const s = [...xs].sort((a, b) => a - b); return s[Math.floor(s.length / 2)]!; }
const n = 1_000_000;
const source = new Uint32Array(n);
for (let i = 0; i < n; i++) source[i] = Math.floor(Math.random() * 2 ** 32);

const tArray: number[] = [], tTyped: number[] = [];
for (let r = 0; r < 5; r++) {
  const a = Array.from(source);
  let t0 = performance.now();
  a.sort((x, y) => x - y);
  tArray.push(performance.now() - t0);

  const b = source.slice();
  t0 = performance.now();
  b.sort();                                   // без компаратора: числовий порядок
  tTyped.push(performance.now() - t0);
}
console.log(`Array з компаратором: ${median(tArray).toFixed(0)} мс; Uint32Array без компаратора: ${median(tTyped).toFixed(0)} мс`);
```

```
Array з компаратором: 1240 мс; Uint32Array без компаратора: 64 мс
```

Різниця майже в двадцять разів, і причина не в алгоритмі, а в тому, що компаратор — функція JavaScript, яку рушій
викликає мільйони разів, а типізований масив сортується без жодного такого виклику. MDN підтверджує: якщо компаратор
не передано, елементи типізованого масиву «are sorted according to numeric value», на відміну від звичайного масиву,
де вони порівнювалися б як рядки. Тож у практиці дня чесне порівняння — ваш `radixSort` проти обох варіантів.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Чи можна сортувати порівняннями швидше за `n log n`? | Ні в найгіршому випадку: дерево рішень має `n!` листків і висоту щонайменше `log₂(n!) = Θ(n log n)`. |
| Як тоді сортування підрахунком лінійне? | Воно не порівнює елементи, а бере ключ як номер масиву; модель порівнянь до нього не застосовна. |
| Скільки коштує сортування підрахунком? | `Θ(n + k)` часу і `Θ(n + k)` пам'яті, де `k` — кількість можливих ключів. |
| Чому порозрядне сортування від молодшого розряду? | Щоб щоразу сортувати весь масив; стабільність зберігає порядок за молодшими розрядами. |
| Що буде з нестабільним проходом? | Порядок, створений попередніми проходами, зруйнується, і результат буде неправильним. |
| Коли сортування без порівнянь не годиться? | Коли ключі не цілі, коли діапазон величезний, коли пам'яті обмаль. |

## Типові помилки

**Вважати, що `Ω(n log n)` — межа для будь-якого сортування.** Лише для сортувань порівняннями.

**Йти в сортуванні підрахунком з початку входу.** Результат правильний, але нестабільний, і порозрядне сортування на
ньому ламається.

**Сортувати порозрядно від старшого розряду цілим масивом.** Старші проходи перемішують те, що впорядкували молодші, і
результат упорядкований лише за останнім проходом.

**Брати сортування підрахунком для великого діапазону.** Лічильники на `2³²` значень займають гігабайти.

**Порівнювати швидкість з `Array.prototype.sort` з компаратором і робити висновок про алгоритм.** Частина різниці —
ціна викликів компаратора, а не асимптотика.

## Практика

Працюйте в тому самому проєкті. Відповіді в лекції немає: обидва сортування показано таблицями, а код ви пишете самі.

**1. `countingSort`** для чисел від 0 до 255. Порахуйте до запуску `log₂(10!)` вручну чи калькулятором і
переконайтеся, що отримали 21,8.

**2. `radixSort`** для `Uint32Array` у чотири проходи по 8 бітів. Розряд з номером `p` — це `(x >>> (8 * p)) & 255`.
Подумайте, чому тут `>>>`, а не `>>`, і що станеться з числами більшими за `2³¹`. Використайте два масиви і міняйте
їхні ролі після кожного проходу, як радить CLRS.

**3. Вимір.** Порівняйте час на 10 мільйонах випадкових чисел: ваш `radixSort`, `Array.prototype.sort` з компаратором
і `Uint32Array.prototype.sort` без компаратора. Перед запуском передбачте порядок.

**4. Стабільність.** Навмисно зробіть один прохід нестабільним, ідучи з початку, і знайдіть найменший вхід, на якому
результат стає неправильним.

## Перевірте себе

**1. Скільки листків щонайменше має дерево рішень для сортування 5 елементів, і яка найменша можлива висота?**

<details><summary>Відповідь</summary>

Листків щонайменше `5! = 120`. Двійкове дерево висоти `h` має не більше `2ʰ` листків, а `2⁶ = 64 < 120 ≤ 128 = 2⁷`,
тож висота щонайменше 7. Будь-яке сортування 5 елементів порівняннями мусить у найгіршому випадку зробити 7 порівнянь.

</details>

**2. Чому хеш-таблиця шукає за `O(1)`, хоча нижня межа пошуку `Ω(log n)`?**

<details><summary>Відповідь</summary>

Нижня межа доведена для моделі, де кожне запитання має сталу кількість відповідей, наприклад два для порівняння.
Обчислення хешу і звернення до комірки — це запитання з `m` відповідями, бо воно одразу вибирає одну з `m` комірок.
Хеш-таблиця працює поза моделлю, тож межа на неї не поширюється.

</details>

**3. Відсортуйте підрахунком `[2, 0, 2, 1, 0]`. Яким буде масив лічильників після накопичення, і на яке місце стане
останній елемент входу?**

<details><summary>Відповідь</summary>

Підрахунок: нулів 2, одиниць 1, двійок 2 — `c = [2, 1, 2]`. Накопичені суми — `[2, 3, 5]`. Останній елемент входу
`a[4] = 0` стає на місце `c[0] − 1 = 1`, а `c[0]` стає 1. Перший нуль `a[1]` пізніше стане на місце 0, тож нулі
збережуть вхідний порядок. Результат `[0, 0, 1, 2, 2]`.

</details>

**4. Відсортуйте порозрядно `[31, 13, 22, 12, 21]`. Що вийде після першого проходу?**

<details><summary>Відповідь</summary>

Перший прохід — за одиницями, стабільно. Одиниці: 1, 3, 2, 2, 1. Порядок: спершу з одиницею 1 у вхідному порядку — 31,
21; потім з 2 — 22, 12; потім з 3 — 13. Отже, `[31, 21, 22, 12, 13]`. Другий прохід за десятками: 1 — 12, 13; 2 — 21,
22; 3 — 31. Результат `[12, 13, 21, 22, 31]`.

</details>

**5. Чому в порозрядному сортуванні 32-бітних чисел розряди по 16 бітів формально кращі, а на практиці часто беруть по
8?**

<details><summary>Відповідь</summary>

За формулою CLRS для `n = 10⁷` розряди по 16 бітів дають два проходи і близько 20 мільйонів кроків, а по 8 — чотири
проходи і близько 40 мільйонів. Але при 16 бітах масив лічильників має 65 536 комірок, і звернення до нього в
випадковому порядку частіше промахуються повз швидкий кеш. 256 лічильників завжди в кеші. Модель RAM, у якій виведено
формулу, кешу не бачить.

</details>

**6. Сортування злиттям робить у найгіршому випадку `n log₂ n − n + 1` порівнянь. Наскільки це далеко від межі
`log₂(n!)` для `n = 10⁶`?**

<details><summary>Відповідь</summary>

`n log₂ n − n + 1 ≈ 10⁶ · 19,93 − 10⁶ ≈ 18,93 · 10⁶`, а `log₂(n!) ≈ 18,49 · 10⁶` з програми лекції. Різниця близько
2,4 %. Сортування злиттям майже досягає межі навіть за сталою, а не лише за порядком росту.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| модель обчислень | домовленість, які дії дозволено алгоритму і що вважати кроком |
| модель порівнянь | модель, де алгоритм дізнається про елементи лише порівнюючи їх парами |
| дерево рішень | дерево, де вузли — запитання до входу, а листи — відповіді алгоритму |
| нижня межа | оцінка, швидше за яку не може працювати жоден алгоритм у даній моделі |
| асимптотично оптимальний | алгоритм, чий час збігається з нижньою межею з точністю до сталого множника |
| сортування підрахунком | сортування цілих ключів через лічильники і накопичені суми за `Θ(n + k)` |
| накопичена сума | для кожного значення — кількість елементів, не більших за нього |
| порозрядне сортування | сортування ключів стабільними проходами за розрядами від молодшого до старшого |
| розряд | частина ключа: десяткова цифра, байт чи група бітів |
| `>>>` | беззнаковий зсув праворуч у JavaScript: заповнює звільнені біти нулями |
