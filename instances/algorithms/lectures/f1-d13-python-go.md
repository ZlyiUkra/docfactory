## Python: `heapq`

Модуль `heapq` — не клас, а набір функцій, що працюють зі звичайним списком. Документація описує ту саму властивість
купи, що в дні 10, з нумерацією з нуля: `heap[k] <= heap[2*k+1]` і `heap[k] <= heap[2*k+2]`, а найменший елемент —
`heap[0]`.

```python
# Купа в Python: модуль heapq працює зі звичайним списком.
import heapq

xs = [5, 1, 4, 2, 3]
heapq.heapify(xs)                       # перетворює список на мінімальну купу на місці, за лінійний час
print("купа:", xs, "найменший:", xs[0])
heapq.heappush(xs, 0)
print("pop:", [heapq.heappop(xs) for _ in range(3)], "лишилось:", xs)

# Максимальна купа: з Python 3.14 є окремі функції, раніше — лише від'ємні ключі.
ys = [5, 1, 4, 2, 3]
heapq.heapify_max(ys)
print("максимальна купа:", ys)
print("найбільший:", heapq.heappop_max(ys))
neg = [-y for y in [5, 1, 4, 2, 3]]
heapq.heapify(neg)
print("через від'ємні:", -heapq.heappop(neg))

# Топ-k без повного сортування.
print("3 найменші:", heapq.nsmallest(3, [9, 4, 7, 1, 8, 2]))
```

```
купа: [1, 2, 4, 5, 3] найменший: 1
pop: [0, 1, 2] лишилось: [3, 5, 4]
максимальна купа: [5, 3, 4, 2, 1]
найбільший: 5
через від'ємні: 5
3 найменші: [1, 2, 4]
```

**Максимальна купа.** До Python 3.13 включно в `heapq` була лише мінімальна купа, і максимум отримували, кладучи в
купу від'ємні ключі: найбільше число стає найменшим від'ємним. Багато підручників досі пишуть так. Але в Python
3.14 документація «What's new» повідомляє: модуль «has improved support for working with max-heaps» — з'явилися
`heapify_max`, `heappush_max`, `heappop_max`, `heapreplace_max` і `heappushpop_max`. Якщо код має працювати на
старіших версіях, прийом з від'ємними ключами лишається.

**`nsmallest` і `nlargest`.** Документація радить їх для малих `n` порівняно з кількістю елементів; для великих швидше
відсортувати, а для `n = 1` — взяти `min` чи `max`. Посібник з сортування пояснює чому: ці функції роблять один прохід
і тримають у пам'яті лише `n` елементів, тобто це той самий прийом обмеженої купи, що в дні 10.

### Пріоритетна черга на `heapq`

Записи пріоритетної черги — кортежі `(пріоритет, завдання)`. Python порівнює кортежі поелементно, і коли пріоритети
рівні, переходить до другого елемента. Якщо завдання не вміють порівнюватися, черга падає:

```python
# Пріоритетна черга із записами (пріоритет, завдання): рівні пріоритети ламають порівняння.
pq = []
heapq.heappush(pq, (1, {"task": "звіт"}))
try:
    heapq.heappush(pq, (1, {"task": "лист"}))
except TypeError as e:
    print("TypeError:", e)

# Рішення з документації: лічильник як другий елемент кортежу.
from itertools import count
pq, order = [], count()
for prio, task in [(2, "звіт"), (1, "лист"), (2, "код"), (1, "дзвінок")]:
    heapq.heappush(pq, (prio, next(order), {"task": task}))
print("порядок:", [heapq.heappop(pq)[2]["task"] for _ in range(4)])
```

```
TypeError: '<' not supported between instances of 'dict' and 'dict'
порядок: ['лист', 'дзвінок', 'звіт', 'код']
```

Документація `heapq` у розділі «Priority Queue Implementation Notes» дає саме це рішення: трійка `(пріоритет,
лічильник, завдання)`. Лічильник розв'язує дві проблеми одразу: завдання ніколи не порівнюються, бо лічильники різні,
і завдання з рівним пріоритетом виходять у порядку додавання, тобто черга стає стабільною. Для зміни пріоритету та
сама документація радить не шукати запис у купі, а позначити його видаленим і додати новий — ліниве видалення з
розбору читання дня 10.

### Чим `heapq` відрізняється від `MinHeap`

| | Ваш `MinHeap<T>` | `heapq` |
|---|------------------|---------|
| форма | клас з даними і методами | функції над звичайним списком |
| порядок | компаратор у конструкторі | природне порівняння елементів; ключ кладуть у кортеж |
| захист властивості | масив прихований у класі | список відкритий: `append` чи присвоєння ламають купу |
| максимальна купа | інший компаратор | окремі функції з 3.14, раніше від'ємні ключі |
| рівні пріоритети | залежить від компаратора | кортежі порівнюють наступний елемент; потрібен лічильник |

## Python: `bisect` і сортування

`bisect` — бінарний пошук межі з дня 3. `bisect_left(a, x)` повертає першу позицію, де елемент не менший за `x`,
`bisect_right` — першу, де більший. `insort` вставляє, зберігаючи відсортованість, але вставка в список — зсув, тож
`O(n)`. З Python 3.10 є параметр `key`:

```python
# bisect і стабільне сортування в Python.
import bisect

xs = [3, 5, 5, 5, 8, 9]
print("bisect_left(5):", bisect.bisect_left(xs, 5), "bisect_right(5):", bisect.bisect_right(xs, 5))
print("кількість п'ятірок:", bisect.bisect_right(xs, 5) - bisect.bisect_left(xs, 5))
bisect.insort(xs, 7)
print("після insort(7):", xs)

events = [(30, "c"), (10, "a"), (20, "b")]
events.sort()                                     # кортежі порівнюються поелементно
times = [t for t, _ in events]
print("перша подія не раніше 15:", events[bisect.bisect_left(times, 15)])
print("те саме через key:", events[bisect.bisect_left(events, 15, key=lambda e: e[0])])

people = [("Олег", "Львів"), ("Анна", "Київ"), ("Ірина", "Львів"), ("Богдан", "Київ")]
by_name = sorted(people, key=lambda p: p[0])
by_city = sorted(by_name, key=lambda p: p[1])     # sorted стабільне: порядок за іменем зберігається в місті
print(by_city)
```

```
bisect_left(5): 1 bisect_right(5): 4
кількість п'ятірок: 3
після insort(7): [3, 5, 5, 5, 7, 8, 9]
перша подія не раніше 15: (20, 'b')
те саме через key: (20, 'b')
[('Анна', 'Київ'), ('Богдан', 'Київ'), ('Ірина', 'Львів'), ('Олег', 'Львів')]
```

Різниця `bisect_right − bisect_left` — кількість копій, як у таблиці лекції дня 3. Параметр `key` у `bisect`
застосовується до елементів списку, а не до `x`: шукане значення 15 передають уже як ключ.

**Сортування.** Документація гарантує, що `list.sort` і `sorted` стабільні, і показує той самий прийом кількох
проходів, що лекція дня 6: спершу за другорядним ключем, потім за головним. Вона ж пояснює, що Timsort, яким сортує
Python, робить кілька проходів ефективно, бо використовує вже наявний порядок. Замість компаратора Python бере функцію
`key`, що обчислюється один раз на елемент, — той самий прийом «sorting with map» з MDN, тільки вбудований.

Зверніть увагу на порядок імен: Python порівнює рядки за номерами символів Юнікоду, як JavaScript. Тут це не завадило,
бо в кожному місті імена випадково стоять правильно, але `sorted(["Ірина", "Анна"])` поставить «Ірина» першою: літера
`І` має менший номер, ніж `А`. Для абетки потрібна локаль.

## Go: `container/heap`

Пакет `container/heap` не дає готової купи. Він дає функції `heap.Init`, `heap.Push`, `heap.Pop`, `heap.Fix` і
`heap.Remove`, що працюють з будь-яким типом, який реалізує інтерфейс `heap.Interface`. Цей інтерфейс складається з
трьох методів `sort.Interface` — `Len`, `Less`, `Swap` — і ще двох, `Push` і `Pop`. Разом п'ять методів, як каже план.

```go
// Купа в Go: тип реалізує heap.Interface, а операції викликають через функції пакета heap.
package main

import (
	"container/heap"
	"fmt"
)

type IntHeap []int

func (h IntHeap) Len() int           { return len(h) }
func (h IntHeap) Less(i, j int) bool { return h[i] < h[j] } // мінімальна купа
func (h IntHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *IntHeap) Push(x any)        { *h = append(*h, x.(int)) } // викликає пакет heap, не ми
func (h *IntHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1] // пакет heap уже переставив найменший у кінець
	*h = old[:n-1]
	return x
}

func main() {
	h := &IntHeap{5, 1, 4, 2, 3}
	heap.Init(h) // побудова купи за O(n)
	heap.Push(h, 0)
	fmt.Println("найменший:", (*h)[0])
	for h.Len() > 0 {
		fmt.Print(heap.Pop(h), " ")
	}
	fmt.Println()

	h2 := &IntHeap{5, 1, 4}
	heap.Init(h2)
	fmt.Println("h2.Pop() напряму:", h2.Pop(), "— це останній елемент масиву, а не найменший")
}
```

```
найменший: 0
0 1 2 3 4 5 
h2.Pop() напряму: 4 — це останній елемент масиву, а не найменший
```

**Хто що робить.** Методи `Push` і `Pop` вашого типу лише додають елемент у кінець зрізу і забирають з кінця. Підйом і
опускання виконують функції пакета: `heap.Push` викликає ваш `Push`, а потім піднімає новий елемент; `heap.Pop` міняє
корінь з останнім, опускає новий корінь, а потім викликає ваш `Pop`, щоб забрати останній — колишній найменший.
Документація попереджає: «Push and Pop in this interface are for package heap's implementation to call. To add and
remove things from the heap, use heap.Push and heap.Pop». Останній рядок виводу показує, що буває, якщо забути:
`h2.Pop()` напряму повернув 4 — останній елемент масиву купи `[1, 5, 4]`, а не найменший.

**Максимальна купа і пріоритети.** Порядок задає `Less`. Документація пакета радить для пріоритетної черги з більшим
пріоритетом першим реалізувати `Less` через від'ємний пріоритет чи обернене порівняння. Функція `heap.Fix(h, i)`
відновлює купу після зміни значення елемента на місці `i` за `O(log n)` — це `INCREASE-KEY` з CLRS. Щоб знати `i`,
приклад `PriorityQueue` у документації зберігає в кожному елементі його поточний номер і оновлює його в `Swap`.

Складність, за документацією: `heap.Init` — `O(n)`, `heap.Push` і `heap.Pop` — `O(log n)`.

## Go: сортування і бінарний пошук

| Функція | Стабільна | Примітка документації |
|---------|-----------|-----------------------|
| `sort.Slice(x, less)` | ні | «equal elements may be reversed from their original order» |
| `sort.SliceStable(x, less)` | так | «keeping equal elements in their original order» |
| `slices.Sort(x)` | — | для впорядковуваних типів, рівні елементи нерозрізненні |
| `slices.SortFunc(x, cmp)` | ні | «This sort is not guaranteed to be stable» |
| `slices.SortStableFunc(x, cmp)` | так | «keeping the original order of equal elements» |

Документація `sort.Slice` додає, що новіший `slices.SortFunc` у багатьох випадках зручніший і швидший. Компаратор
`slices.SortFunc` повертає число, як у JavaScript, а `less` у `sort.Slice` — булеве значення «менше». Обидва мусять
задавати порядок без суперечностей: документація `slices` називає це строгим слабким порядком. З примітками до випуску
Go 1.19 ви знайомі з розбору дня 8: сортування в пакеті `sort` переписано на pattern-defeating quicksort, а quicksort
нестабільний.

**Бінарний пошук.** `sort.Search(n, f)` з дня 3 — це ваш `firstTrue`: найменший `i`, де `f(i)` правдива, або `n`.
`slices.BinarySearch` зручніший для відсортованого зрізу: він повертає позицію і ознаку, чи знайдено.

## Go: зрізи й мапи

Програма нижче показує дві речі, що прямо стосуються фази: як росте зріз і в якому порядку обходиться мапа.

```go
// Ріст місткості зрізу в Go і порядок обходу мапи.
package main

import (
	"fmt"
	"slices"
)

func main() {
	var s []int
	last := -1
	caps := []int{}
	for i := 0; i < 2000; i++ {
		s = append(s, i)
		if cap(s) != last {
			last = cap(s)
			caps = append(caps, last)
		}
	}
	fmt.Println("місткості:", caps)

	m := map[string]int{"kyiv": 1, "lviv": 2, "odesa": 3, "sumy": 4, "rivne": 5}
	for r := 0; r < 3; r++ {
		keys := []string{}
		for k := range m {
			keys = append(keys, k)
		}
		fmt.Println("обхід мапи:", keys)
	}

	xs := []int{9, 3, 7, 1}
	slices.Sort(xs)
	i, found := slices.BinarySearch(xs, 7)
	j, found2 := slices.BinarySearch(xs, 4)
	fmt.Println(xs, "7 на місці", i, found, "; 4 мало б стати на місце", j, found2)
}
```

```
місткості: [1 2 4 8 16 32 64 128 256 512 848 1280 1792 2560]
обхід мапи: [kyiv lviv odesa sumy rivne]
обхід мапи: [odesa sumy rivne kyiv lviv]
обхід мапи: [odesa sumy rivne kyiv lviv]
[1 3 7 9] 7 на місці 2 true ; 4 мало б стати на місце 2 false
```

**Ріст зрізу.** Поки зріз малий, місткість подвоюється, а після 512 росте повільніше: у 1,66, 1,5, 1,4 рази. Це той
самий динамічний масив з дня 8 фази 0 з множником, що зменшується. Go 101 пише, що місткість нового зрізу «compiler
dependent», і для стандартного компілятора при малій місткості вона щонайменше подвоюється. Амортизований `O(1)` на
`append` зберігається, бо множник лишається більшим за 1.

**Обхід мапи.** Обходи тієї самої незмінної мапи дали різні порядки: перший не збігся з двома наступними, а попередній
запуск тієї самої програми дав три різні порядки з трьох. Go 101 нагадує, що за специфікацією порядок не визначений,
«kind-of randomized», а з розбору читання дня 5 ви знаєте, що примітки до Go 1.3 пояснюють навіщо: щоб код не
покладався на порядок обходу. Якщо порядок потрібен, ключі збирають у зріз і сортують.

Останній рядок показує `slices.BinarySearch`: число 7 знайдено на місці 2, а для відсутнього 4 повернуто місце 2, куди
його треба вставити, щоб зріз лишився відсортованим, і `false`.

| Як зробити максимальну купу в Python? | З 3.14 — `heapify_max`, `heappush_max`, `heappop_max`; на старіших версіях — від'ємні ключі. |
| Скільки методів треба реалізувати для `container/heap`? | П'ять: `Len`, `Less`, `Swap`, `Push`, `Pop`; а викликати — `heap.Push` і `heap.Pop`. |
| Чи стабільний `sort.Slice` у Go? | Ні; стабільні `sort.SliceStable` і `slices.SortStableFunc`. |
| Чи можна покладатися на порядок обходу мапи в Go чи множини в Python? | Ні: у Go він навмисно змінюється, у Python залежить від хешів із випадковим зерном. |
| Як знайти позицію вставки у відсортований список? | Python — `bisect.bisect_left`, Go — `sort.Search` чи `slices.BinarySearch`. |

## Типові помилки

**Викликати `h.Push` і `h.Pop` у Go напряму.** Купа не піднімає і не опускає елементи, і `Pop` повертає останній
елемент масиву.

**Класти в `heapq` пари `(пріоритет, обʼєкт)` без лічильника.** На рівних пріоритетах Python порівнює об'єкти і може
впасти з `TypeError` або повернути їх у непередбачуваному порядку.

**Змінювати список, що є купою, звичайними методами.** `append` чи присвоєння за номером ламають властивість купи;
після цього треба знову викликати `heapify`.

**Брати `sort.Slice` для сортування за кількома ключами кількома проходами.** Нестабільне сортування зламає порядок
попереднього проходу; потрібен `sort.SliceStable` або один компаратор з кількома ключами.

**Вважати, що максимальної купи в `heapq` немає.** Це правда до Python 3.13 і неправда з 3.14. Перевіряйте
документацію своєї версії.

## Перевірте себе

**1. Що надрукує код і чому?**

```python
import heapq
h = []
for x in [3, 1, 2]:
    h.append(x)
print(heapq.heappop(h))
```

<details><summary>Відповідь</summary>

`3`. `heappop` вважає, що список уже купа, і забирає `h[0]`, тобто 3. `append` не відновлює властивість купи. Треба
було або класти через `heappush`, або викликати `heapify(h)` перед першим `heappop`.

</details>

**2. Чому в документації `heapq` рекомендовано трійку `(пріоритет, лічильник, завдання)`, а не пару?**

<details><summary>Відповідь</summary>

Кортежі порівнюються поелементно, тож на рівних пріоритетах Python порівнює наступний елемент. Без лічильника це
завдання, які можуть не підтримувати порівняння, і тоді буде `TypeError`. Лічильник завжди різний, тож до завдань
справа не доходить, а рівні пріоритети виходять у порядку додавання.

</details>

**3. Що повертає `bisect.bisect_left([1, 3, 3, 5], 3)` і `bisect.bisect_right([1, 3, 3, 5], 3)`?**

<details><summary>Відповідь</summary>

1 і 3. Перша позиція, де елемент не менший за 3, — 1; перша, де більший, — 3. Різниця 2 — кількість трійок. Це
`lowerBound` і upper bound з дня 3.

</details>

**4. Чому в `container/heap` метод `Pop` вашого типу забирає останній елемент, а не перший?**

<details><summary>Відповідь</summary>

Перед викликом вашого `Pop` функція `heap.Pop` уже поміняла корінь з останнім елементом і опустила новий корінь.
Найменший тепер стоїть у кінці зрізу, і забрати його звідти — дешево: зріз коротшає без зсуву. Ваш метод лише відрізає
кінець і повертає його.

</details>

**5. Чому місткість зрізу в Go після 512 росте повільніше, ніж удвічі, і чи не ламає це амортизований `O(1)`?**

<details><summary>Відповідь</summary>

Подвоєння великих зрізів марнує багато пам'яті: після переїзду половина місткості порожня. Менший множник тримає менше
порожнього місця ціною частіших переїздів. Амортизована оцінка з дня 8 фази 0 тримається для будь-якого сталого
множника, більшого за 1: сума копій — геометрична прогресія, обмежена сталою, помноженою на кількість елементів.

</details>

**6. Програма на Go друкує ключі мапи, і тест порівнює вивід з еталонним рядком. Чому тест проходить не завжди і як
виправити?**

<details><summary>Відповідь</summary>

Порядок обходу мапи в Go не визначений і навмисно змінюється між обходами, тож рядок щоразу інший. Виправлення —
зібрати ключі в зріз, відсортувати `slices.Sort` і друкувати відсортовані. Те саме з множинами в Python, де порядок
залежить від хешів із випадковим зерном.

</details>
