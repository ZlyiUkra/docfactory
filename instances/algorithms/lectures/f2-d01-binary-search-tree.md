# Лекція. Фаза 2, день 1. Двійкове дерево пошуку

Ця лекція пояснює двійкове дерево пошуку: структуру, яка тримає ключі впорядкованими і дозволяє і швидко шукати, і
швидко вставляти. Читання займе близько 55 хвилин. Під прикладами коду стоїть справжній вивід з Node 24.22.

У фазі 1 ви бачили два способи тримати ключі. Хеш-таблиця шукає за сталий час, але нічого не знає про порядок ключів.
Відсортований масив знає порядок і шукає бінарним пошуком, але вставка в нього коштує лінійний час. Сьогодні з'ясуємо,
як отримати обидві переваги одразу, чому все залежить від висоти дерева, і чому просте дерево пошуку на відсортованих
даних перетворюється на повільний список.

**Після лекції ви зможете пояснити:**

- чого не вміє хеш-таблиця і навіщо для цього дерево;
- що таке властивість дерева пошуку і чому з неї випливає, що симетричний обхід видає ключі відсортованими;
- як працюють пошук, вставка, мінімум і наступний за величиною ключ і чому кожна з цих операцій коштує стільки, яка
  висота дерева;
- як видалити вузол з двома дітьми і чому при цьому легко зіпсувати дерево;
- чому дерево з перемішаних ключів має висоту близько двадцяти на тисячу вузлів, а з відсортованих — 999;
- чому рекурсивний код на перекошеному дереві падає з переповненням стека.

## Чого не вміє хеш-таблиця

Уявіть журнал замовлень інтернет-магазину. Кожне замовлення має номер, і за номером його треба швидко знаходити. Із
цим упорається хеш-таблиця. Але менеджер просить ще й таке: показати всі замовлення з номерами від 1000 до 1200,
знайти перше замовлення після номера 5321, назвати десяте за величиною. Хеш-таблиця розкладає ключі по комірках за
хешем, і сусідні номери опиняються в різних кінцях таблиці. Тому на кожне таке питання їй доведеться переглянути всі
ключі.

Курс MIT 6.006 зводить це в таблицю. Він розглядає набір операцій над множиною ключів: побудувати, знайти, вставити,
видалити, знайти найменший і найбільший, знайти попередній і наступний за величиною. Час операцій у різних структур
такий:

| Структура | Знайти | Вставити, видалити | Найменший, найбільший | Попередній, наступний |
|-----------|--------|--------------------|-----------------------|-----------------------|
| відсортований масив | `O(log n)` | `O(n)` | `O(1)` | `O(log n)` |
| хеш-таблиця | `O(1)` очікувано | `O(1)` очікувано й амортизовано | `O(n)` | `O(n)` |
| мета | `O(log n)` | `O(log n)` | `O(log n)` | `O(log n)` |

Жодна з двох структур не досягає мети. Sedgewick формулює задачу так: треба поєднати гнучку вставку зв'язаного списку
з ефективним пошуком відсортованого масиву. Він показує, що для цього досить дати вузлу два посилання замість одного.
Так виходить **двійкове дерево пошуку** (binary search tree, скорочено BST). Sedgewick називає його одним із
найфундаментальніших алгоритмів у інформатиці.

## Вузол і властивість дерева пошуку

**Двійкове дерево** складається з вузлів. Кожен вузол має два посилання: на **ліву дитину** і на **праву дитину**.
Будь-яке з них може бути порожнім. На кожен вузол, крім одного, вказує рівно один інший вузол, його **батько**. Вузол
без батька називають **коренем**, а вузол без дітей — **листом**. Ліва дитина разом з усіма своїми нащадками утворює
**ліве піддерево** вузла, права — **праве піддерево**.

У дереві пошуку кожен вузол тримає ще й **ключ**, за яким шукають, і **значення**, яке за ключем зберігають. CLRS
додає до вузла ще посилання на батька, бо деякі операції ходять угору. Sedgewick обходиться без нього.

Ключі в дереві розкладено за одним правилом, яке називають **властивістю дерева пошуку**: усі ключі лівого піддерева
вузла менші за ключ вузла, а всі ключі правого піддерева — більші. Правило діє для кожного вузла, а не лише для
кореня. Ось дерево з рисунка 12.2 CLRS, на якому ми розбиратимемо всі операції:

```
                15
             /      \
           6          18
         /   \       /   \
        3     7     17    20
       / \     \
      2   4     13
               /
              9
```

Перевірте правило на вузлі 6. Його ліве піддерево — ключі 2, 3, 4, і всі вони менші за 6. Праве піддерево — ключі 7,
13, 9, і всі вони більші за 6. Але ще й усі ці шість ключів менші за 15, бо лежать у лівому піддереві кореня.

**Однакові ключі.** Sedgewick будує таблицю символів, у якій ключ трапляється не більше разу, тому вимагає строгих
нерівностей. Якщо ключ уже є, вставка просто замінює значення. CLRS допускає однакові ключі і пише нестрогі
нерівності: ліворуч ключі «не більші», праворуч — «не менші». Обидва варіанти правильні. Помилка виникає тоді, коли
пошук і вставка в одній програмі домовляються про різне.

**Одну множину можуть зберігати різні дерева.** CLRS показує на рисунку 12.1 два дерева з тими самими шістьма ключами.
Одне має висоту 2, а друге — 4. Форма дерева залежить від того, в якому порядку ключі вставляли. Нижче ви побачите, що
від форми залежить і швидкість.

## Пошук

Пошук іде від кореня вниз. У кожному вузлі він порівнює шуканий ключ з ключем вузла. Якщо ключі рівні, пошук
закінчено. Якщо шуканий менший, то за властивістю дерева він може лежати лише в лівому піддереві, і пошук іде ліворуч.
Якщо більший — праворуч. Якщо посилання, куди треба йти, порожнє, ключа в дереві немає.

```ts
// Дерево з рисунка лекції, зібране вручну: вузол — ключ і два посилання.
type Node = { key: number; left: Node | null; right: Node | null };
const leaf = (key: number): Node => ({ key, left: null, right: null });
const node = (key: number, left: Node | null, right: Node | null): Node => ({ key, left, right });

const root = node(15,
  node(6, node(3, leaf(2), leaf(4)), node(7, null, node(13, leaf(9), null))),
  node(18, leaf(17), leaf(20)));

// Пошук: від кореня ліворуч, якщо шуканий менший, праворуч, якщо більший.
function find(root: Node | null, key: number): string[] {
  const path: string[] = [];
  let x = root;
  while (x !== null) {
    path.push(String(x.key));
    if (key === x.key) return [...path, "знайдено"];
    x = key < x.key ? x.left : x.right;     // половина дерева відкидається одним порівнянням
  }
  return [...path, "немає"];
}

for (const k of [13, 17, 8, 21]) console.log(`шукаємо ${k}: ${find(root, k).join(" → ")}`);

// Симетричний обхід: ліве піддерево, сам вузол, праве піддерево.
const inOrder = (x: Node | null): number[] => (x === null ? [] : [...inOrder(x.left), x.key, ...inOrder(x.right)]);
console.log("симетричний обхід:", inOrder(root).join(" "));
```

```
шукаємо 13: 15 → 6 → 7 → 13 → знайдено
шукаємо 17: 15 → 18 → 17 → знайдено
шукаємо 8: 15 → 6 → 7 → 13 → 9 → немає
шукаємо 21: 15 → 18 → 20 → немає
симетричний обхід: 2 3 4 6 7 9 13 15 17 18 20
```

Перший рядок повторює шлях, який CLRS показує на рисунку 12.2: від 15 до 13 через 6 і 7. Пошук 8 дійшов до вузла 9.
Вісім менше за дев'ять, тож треба йти ліворуч, а ліве посилання вузла 9 порожнє. Отже, вісімки в дереві немає.

**Скільки це коштує.** Пошук проходить один шлях від кореня вниз і в кожному вузлі робить одне-два порівняння.
Найдовший шлях від кореня вниз називають **висотою дерева** і позначають `h`. Тому пошук коштує `O(h)`. Це схоже на
бінарний пошук з дня 3 фази 1: там кожне порівняння відкидало половину масиву, тут — одне з двох піддерев. Різниця в
тому, що бінарний пошук завжди ділить навпіл, а дерево ділить так, як воно склалося. Якщо одне піддерево майже
порожнє, а друге майже все, порівняння відкидає майже нічого.

## Симетричний обхід

Останній рядок виводу показує ключі за зростанням. Функція `inOrder` спершу обходить ліве піддерево, потім видає ключ
вузла, потім обходить праве піддерево. Такий порядок називають **симетричним обходом** (inorder traversal). CLRS
пояснює назву тим, що ключ кореня друкується між ключами двох піддерев. Якщо корінь друкувати першим, обхід називають
**прямим** (preorder), а якщо останнім — **зворотним** (postorder).

**Чому ключі виходять відсортованими.** Доведемо індукцією за розміром дерева. Порожнє дерево не видає нічого, і це
правильно. Нехай для менших дерев твердження вже доведено. Тоді обхід лівого піддерева видає його ключі за зростанням,
і всі вони менші за ключ кореня. Далі йде ключ кореня. Потім обхід правого піддерева видає його ключі за зростанням, і
всі вони більші за ключ кореня. Разом виходить зростаюча послідовність усіх ключів.

**Скільки це коштує.** CLRS доводить, що обхід дерева з `n` вузлів коштує `Θ(n)`: функція викликає себе рівно двічі
для кожного вузла, і кожен виклик без урахування вкладених робить сталу роботу. Отже, дерево пошуку вміє віддати всі
ключі відсортованими за лінійний час. Хеш-таблиця так не вміє: їй довелося б сортувати за `n log n`.

## Мінімум і наступний за величиною

**Мінімум.** Найменший ключ лежить у найлівішому вузлі. Від кореня треба йти ліворуч, доки ліве посилання не стане
порожнім. CLRS обґрунтовує це так. Якщо вузол не має лівого піддерева, то всі ключі його правого піддерева більші за
нього, і найменший — він сам. Якщо ліве піддерево є, то найменший лежить саме там. У нашому дереві шлях до мінімуму —
15, 6, 3, 2. Максимум симетричний: треба йти праворуч до 20.

**Наступний за величиною.** CLRS називає цю операцію successor. Наступний — це вузол, який симетричний обхід видає
одразу після даного. Його можна знайти, не порівнюючи ключів, лише за формою дерева. Є два випадки:

1. **Вузол має праве піддерево.** Тоді наступний — найменший вузол правого піддерева, тобто найлівіший у ньому. Для
   вузла 15 праве піддерево починається з 18, і найлівіший вузол там 17. Отже, після 15 іде 17.
2. **Правого піддерева немає.** Тоді наступний — найближчий предок, для якого наш вузол лежить у лівому піддереві.
   Треба йти вгору, доки ми піднімаємося з правої дитини, і зупинитися, щойно піднялися з лівої. Для вузла 13 підйом
   іде так: 13 — права дитина 7, 7 — права дитина 6, 6 — ліва дитина 15. Отже, після 13 іде 15.

Якщо підйом дійшов до кореня і жодного разу не піднявся з лівої дитини, наступного немає. Так буде для вузла 20,
найбільшого в дереві. Другий випадок потребує посилання на батька. Без нього наступний шукають під час спуску від
кореня: щоразу, коли пошук повертає ліворуч, поточний вузол запам'ятовують як кандидата.

Обидві операції проходять один шлях униз або один шлях угору, тож коштують `O(h)`. CLRS зводить це в теорему: пошук,
мінімум, максимум, наступний і попередній працюють за `O(h)` на дереві висоти `h`.

**Що ще дає порядок.** Sedgewick будує на дереві ще кілька операцій. `floor(k)` — найбільший ключ, не більший за `k`;
`ceiling(k)` — найменший, не менший. `keys(lo, hi)` віддає всі ключі з проміжку і пропускає піддерева, де їх не може
бути. Якщо в кожному вузлі зберігати розмір його піддерева, з'являються `rank(k)` — скільки ключів менші за `k` — і
`select(i)` — ключ з номером `i` за зростанням. Пошук `select` працює так само, як вибір `k`-го елемента з дня 12 фази
1: порівнює `i` з розміром лівого піддерева і йде ліворуч або праворуч. Курс MIT називає таке додаткове поле в вузлі
**доповненням** дерева (augmentation).

## Вставка

Вставка — це пошук, який не знайшов ключа. Пошук закінчується на порожньому посиланні, і саме туди ставлять новий
вузол. Решта дерева не змінюється. Вставимо 8 у наше дерево:

| Вузол | Порівняння | Куди далі |
|-------|------------|-----------|
| 15 | `8 < 15` | ліворуч, до 6 |
| 6 | `8 > 6` | праворуч, до 7 |
| 7 | `8 > 7` | праворуч, до 13 |
| 13 | `8 < 13` | ліворуч, до 9 |
| 9 | `8 < 9` | ліве посилання порожнє: 8 стає лівою дитиною 9 |

Новий вузол завжди стає листом. Sedgewick помічає наслідок: корінь — це перший вставлений ключ, а кожен ключ лягає під
тими, що прийшли раніше. Тому форму дерева повністю визначає порядок вставок. CLRS додає у вправі 12.3-2 ще один
наслідок: пошук ключа потім пройде ті самі вузли, що й вставка, і ще сам вузол.

Вставку пишуть двома способами. CLRS спускається циклом і тримає «хвостове» посилання на батька поточного вузла. Коли
цикл доходить до порожнього посилання, цей батько вже відомий, і йому призначають нову дитину. Sedgewick пише
рекурсію, яка повертає корінь піддерева, а батько присвоює результат своєму посиланню: `x.left = put(x.left, key)`.
Майже всі ці присвоєння нічого не міняють, бо посилання вказувало на той самий вузол. Але так код не мусить окремо
пам'ятати батька, і той самий прийом знадобиться в збалансованих деревах, де вузли переставляються.

## Видалення

Видалення найскладніше. CLRS розбирає три випадки. Розглянемо кожен на нашому дереві.

**Лист.** Його просто відрізають: батько отримує порожнє посилання замість нього. Видалимо 4:

```
до:      3              після:      3
        / \                        /
       2   4                      2
```

**Вузол з однією дитиною.** Дитина піднімається на його місце: батько отримує посилання на неї. Видалимо 7, у якого
лише права дитина 13:

```
до:        6            після:      6
          / \                      / \
         3   7                    3   13
              \                       /
               13                    9
              /
             9
```

Властивість дерева не порушилась: усе піддерево 13 лежало праворуч від 6 і лишилося праворуч від 6.

**Вузол з двома дітьми.** Тут проблема: у батька є місце лише для одного посилання, а дітей дві. Sedgewick називає
розв'язок **видаленням Гіббарда**, яке Т. Гіббард запропонував у 1962 році. Вузол замінюють його наступним за
величиною. Наступний лежить у правому піддереві і є там найлівішим, тож лівої дитини не має. Тому його легко вийняти з
його місця за першими двома випадками і поставити на місце видаленого. Порядок не порушується, бо між видаленим ключем
і наступним інших ключів немає.

Видалимо корінь 15. Його наступний — 17, ліва дитина 18. Вузол 17 виймають (він лист), а потім ставлять у корінь:

```
до:          15                     після:       17
          /      \                            /      \
        6          18                       6          18
      /   \       /   \                   /   \          \
     3     7     17    20                3     7          20
    / \     \                           / \     \
   2   4     13                        2   4     13
            /                                   /
           9                                   9
```

Якщо наступний — сама права дитина видаленого, виймати нічого не треба: вона просто піднімається і забирає ліве
піддерево видаленого. Так буде при видаленні 6: його наступний — 7, права дитина, і 7 стає на місце 6 з лівим
піддеревом 3, 2, 4.

**Переміщувати вузол чи копіювати ключ.** План описує простіший варіант: скопіювати ключ і значення наступного у
вузол, що видаляється, а видалити вузол наступного. Так робили перші два видання CLRS. У четвертому виданні автори
пояснюють, чому від цього відмовилися. Якщо інші частини програми тримають посилання на вузли дерева, то після
копіювання видаленим виявиться не той вузол, який просили видалити. Хтось може лишитися з посиланням на вузол, якого
вже немає в дереві. Тому CLRS переміщує сам вузол наступного. Для навчального дерева, яке нікому не віддає посилань на
свої вузли, обидва варіанти дають правильний результат.

**Несиметричність.** Sedgewick помічає, що вибір наступного, а не попереднього, довільний. У вправі 3.2.42 він
пропонує перевірити гіпотезу, яку сам називає дещо неочікуваною: якщо довго чергувати випадкові видалення і вставки,
дерево перекошується, і середній шлях росте пропорційно `√n`. На практиці він радить вибирати навмання між попереднім
і наступним.

Видалення теж проходить один шлях від кореня вниз до вузла і, можливо, далі до його наступного. Тому воно коштує
`O(h)`.

## Висота вирішує все

Усі операції цієї лекції коштують `O(h)`. Sedgewick формулює це твердженням E: у дереві пошуку всі операції в
найгіршому випадку коштують час, пропорційний висоті дерева. Отже, усе питання в тому, якою буде висота.

**Як рахувати висоту.** CLRS, Sedgewick і курс MIT рахують висоту в ребрах: дерево з одного вузла має висоту 0. BCtCI
рахує рівні, тобто вузли на найдовшому шляху, і в нього таке дерево має висоту 1. План, лекція і практика рахують у
ребрах, як CLRS.

**Вимір.** Програма вставляє тисячу ключів двома способами і міряє висоту. Щоб не писати окремий обхід, вона
користується тим, що вузли після вставки не рухаються. Глибина вузла — кількість ребер від кореня до нього. Тоді
висота дерева дорівнює найбільшій глибині, а глибину нового вузла вставка рахує сама під час спуску.

```ts
// Вставка без жодного балансування. Вона повертає глибину нового вузла: скільки ребер від кореня.
// Вузли після вставки не рухаються, тому висота дерева — найбільша з глибин, які повернули вставки.
type Node = { key: number; left: Node | null; right: Node | null };

class KeyTree {
  root: Node | null = null;
  insert(key: number): number {
    const fresh: Node = { key, left: null, right: null };
    if (this.root === null) { this.root = fresh; return 0; }
    let x = this.root, depth = 1;
    for (;;) {
      if (key < x.key) {
        if (x.left === null) { x.left = fresh; return depth; }   // батько отримує посилання
        x = x.left;
      } else {
        if (x.right === null) { x.right = fresh; return depth; }
        x = x.right;
      }
      depth++;
    }
  }
}

function shuffle(xs: number[]): number[] {          // Фішер–Єйтс з дня 9 фази 1
  for (let i = xs.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [xs[i], xs[j]] = [xs[j]!, xs[i]!];
  }
  return xs;
}

function build(keys: number[]): { height: number; avgDepth: number } {
  const t = new KeyTree();
  let height = 0, sumDepth = 0;
  for (const k of keys) {
    const d = t.insert(k);
    height = Math.max(height, d);
    sumDepth += d;
  }
  return { height, avgDepth: sumDepth / keys.length };
}

const n = 1000;
const sorted = Array.from({ length: n }, (_, i) => i + 1);
console.log("по порядку 1…1000:", build(sorted));

const trials = 1000;
let minH = Infinity, maxH = 0, sumH = 0;
for (let t = 0; t < trials; t++) {
  const { height } = build(shuffle([...sorted]));
  minH = Math.min(minH, height); maxH = Math.max(maxH, height); sumH += height;
}
console.log(`перемішані, ${trials} спроб: висота від ${minH} до ${maxH}, у середньому ${(sumH / trials).toFixed(1)}`);
console.log(`для порівняння: ⌊log₂ ${n}⌋ = ${Math.floor(Math.log2(n))}`);
```

```
по порядку 1…1000: { height: 999, avgDepth: 499.5 }
перемішані, 1000 спроб: висота від 16 до 29, у середньому 21.1
для порівняння: ⌊log₂ 1000⌋ = 9
```

Перемішування випадкове, тож у вашому запуску числа другого рядка будуть трохи інші.

**Відсортовані ключі.** Кожен новий ключ більший за всі попередні. Пошук місця для нього щоразу йде праворуч до самого
низу, і новий вузол стає правою дитиною останнього. Дерево вироджується в ланцюжок, по суті у зв'язаний список з дня 1
фази 1. Висота 999, середня глибина 499,5, і пошук коштує лінійний час. Те саме дасть зворотний порядок, а також
порядок «за зростанням через один». CLRS у вступі до глави 12 каже про це прямо: для повного дерева операції коштують
`Θ(lg n)`, а для ланцюжка з `n` вузлів — `Θ(n)`.

**Перемішані ключі.** Висота в середньому 21, і за тисячу спроб жодного разу не перевищила 29. Це вдвічі більше за
найменшу можливу висоту 9, але в тридцять із лишком разів менше за 999.

### Звідки береться логарифм

Sedgewick пояснює це спорідненістю з quicksort. Перший вставлений ключ стає коренем і ділить решту ключів на менші й
більші, точно як опорний елемент у quicksort. Далі кожне піддерево будується так само, як quicksort рекурсивно сортує
свої половини. Якщо ключі йдуть у випадковому порядку, корінь — випадковий ключ, тобто випадковий опорний з дня 9 фази
1. CLRS у задачі 12-3 доводить ту саму схожість і пропонує описати quicksort, який робить рівно ті самі порівняння, що
   й вставки в дерево.

З цієї схожості Sedgewick виводить твердження C і D: влучний пошук, промах і вставка в дереві з `n` випадкових ключів
роблять у середньому близько `2 ln n ≈ 1,39 log₂ n` порівнянь. У вправі 3.2.35 він уточнює формулу до `1,39 log₂ n −
1,85`. Перевіримо. Пошук вузла на глибині `d` робить `d + 1` порівнянь, тож середня кількість порівнянь — це одиниця
плюс середня глибина:

```ts
// Скільки порівнянь у середньому коштує влучний пошук у дереві з випадкових ключів.
// Пошук вузла на глибині d робить d + 1 порівнянь, тому середнє — 1 + середня глибина.
type Node = { key: number; left: Node | null; right: Node | null };
function insert(root: Node | null, key: number): { root: Node; depth: number } {
  const fresh: Node = { key, left: null, right: null };
  if (root === null) return { root: fresh, depth: 0 };
  let x = root, depth = 1;
  for (;;) {
    const next = key < x.key ? x.left : x.right;
    if (next === null) { if (key < x.key) x.left = fresh; else x.right = fresh; return { root, depth }; }
    x = next; depth++;
  }
}
function shuffle(xs: number[]): number[] {
  for (let i = xs.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [xs[i], xs[j]] = [xs[j]!, xs[i]!];
  }
  return xs;
}
for (const n of [1_000, 10_000, 100_000, 1_000_000]) {
  let root: Node | null = null, sum = 0, height = 0;
  for (const k of shuffle(Array.from({ length: n }, (_, i) => i))) {
    const r = insert(root, k); root = r.root; sum += r.depth; height = Math.max(height, r.depth);
  }
  const lg = Math.log2(n);
  console.log(`n = ${n}: порівнянь ${(1 + sum / n).toFixed(1)} (формула 1,39·lg n − 1,85 = ${(1.39 * lg - 1.85).toFixed(1)}),` +
    ` висота ${height} (2,99·lg n = ${(2.99 * lg).toFixed(1)})`);
}
```

```
n = 1000: порівнянь 11.7 (формула 1,39·lg n − 1,85 = 12.0), висота 23 (2,99·lg n = 29.8)
n = 10000: порівнянь 15.4 (формула 1,39·lg n − 1,85 = 16.6), висота 29 (2,99·lg n = 39.7)
n = 100000: порівнянь 21.1 (формула 1,39·lg n − 1,85 = 21.2), висота 38 (2,99·lg n = 49.7)
n = 1000000: порівнянь 26.3 (формула 1,39·lg n − 1,85 = 25.9), висота 49 (2,99·lg n = 59.6)
```

Кожен рядок — одне дерево з випадкових ключів, тому числа трохи стрибають, і у вашому запуску вони будуть інші. Але
середня кількість порівнянь іде за формулою: на мільйоні ключів пошук робить близько 26 порівнянь. Бінарний пошук у
відсортованому масиві зробив би близько 20. Sedgewick оцінює цю різницю в 39 % і вважає її прийнятною ціною за те, що
вставка теж логарифмічна.

**Висота і середня глибина — різні речі.** Середня глибина враховує і короткі шляхи, а висота — лише найдовший.
Sedgewick пише, що середню висоту дерева з випадкових ключів довів логарифмічною Дж. Робсон у 1979 році, а Л. Деврой
показав, що для великих `n` вона наближається до `2,99 log₂ n`. На наших розмірах висота помітно нижча за цю межу, бо
формула описує поведінку при дуже великих `n`.

### Чому не можна просто перемішати

У quicksort ми самі перемішували вхід, і погані випадки ставали неймовірними. Sedgewick звертає увагу, що з деревом
так не вийде. Порядок вставок вибирає не дерево, а програма, яка ним користується. А відсортовані ключі на практиці
трапляються постійно: номери замовлень, що ростуть, час подій, рядки, прочитані з уже відсортованого файлу. Тому решта
фази шукає дерева, висота яких лишається логарифмічною за будь-якого порядку вставок.

## Рекурсія на довгому шляху

Рекурсивний код дерева робить стільки вкладених викликів, яка глибина вузла, до якого він спускається. На
збалансованому дереві це кілька десятків. На ланцюжку — тисячі. Рушій JavaScript відводить на стек викликів обмежену
пам'ять:

```ts
// Рекурсивна вставка в стилі Sedgewick: функція повертає корінь піддерева, і батько переприсвоює посилання.
// На відсортованих ключах дерево стає ланцюжком, і глибина рекурсії дорівнює кількості вузлів.
type Node = { key: number; left: Node | null; right: Node | null };
function put(x: Node | null, key: number): Node {
  if (x === null) return { key, left: null, right: null };
  if (key < x.key) x.left = put(x.left, key);
  else if (key > x.key) x.right = put(x.right, key);
  return x;
}
for (const n of [1_000, 10_000, 100_000]) {
  let root: Node | null = null;
  try {
    for (let k = 0; k < n; k++) root = put(root, k);
    console.log(`n = ${n}: вставлено всі`);
  } catch (e) {
    console.log(`n = ${n}: ${(e as Error).name}: ${(e as Error).message}`);
  }
}
```

```
n = 1000: вставлено всі
n = 10000: вставлено всі
n = 100000: RangeError: Maximum call stack size exceeded
```

Десять тисяч відсортованих ключів рекурсія ще витримала, а сто тисяч — ні. Помилка вилетіла не на першій вставці, а
тоді, коли ланцюжок став задовгим. Sedgewick у розділі запитань і відповідей зважує обидва стилі. Рекурсію легше
перевірити, цикл трохи швидший, а на незбалансованому дереві глибина стека викликів може стати проблемою. BCtCI радить
на співбесіді прямо сказати про це: якщо в умові сказано, що дерево збалансоване, рекурсія безпечна; якщо ні, варто
спитати про найбільшу висоту.

## Дерева в мовах

У JavaScript упорядкованого словника немає. `Map` і `Set` обходять ключі в порядку вставки, а не за зростанням, а
специфікація ECMAScript вимагає від них лише доступу, швидшого за лінійний, і згадує хеш-таблиці як один зі способів
цього досягти. Тому «наступний за величиною» чи «всі ключі від 10 до 20» у JavaScript доводиться писати самому.

BCtCI радить на співбесіді таке. Якщо в обраній мові немає дерева-словника, скажіть про це інтерв'юеру і спитайте, чи
можна вважати, що такий клас є. Зазвичай дозволяють, бо писати збалансоване дерево з нуля довго. Що є в Python і Go,
план розбере в день 11 цієї фази.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Чим дерево пошуку краще за хеш-таблицю? | Воно тримає порядок: мінімум, наступний за величиною, проміжок ключів, `k`-й за величиною. |
| Скільки коштують операції? | `O(h)`. На збалансованому дереві `O(log n)`, на ланцюжку `O(n)`. |
| Як перевірити, що дерево — дерево пошуку? | Симетричний обхід має йти за зростанням, або кожен вузол перевіряють проти меж, успадкованих від предків. |
| Де наступний за величиною ключ? | Найлівіший у правому піддереві; якщо його немає — найближчий предок, до якого піднялися з лівої дитини. |
| Як видалити вузол з двома дітьми? | Замінити його наступним за величиною: той лежить у правому піддереві і не має лівої дитини. |
| Яка висота дерева з `n` випадкових ключів? | У середньому логарифмічна; пошук робить близько `1,39 log₂ n` порівнянь. Відсортовані ключі дають висоту `n − 1`. |

## Типові помилки

**Забувати оновлювати посилання батька під час видалення.** Це пастка дня з плану. Якщо «видалити» вузол,
переприсвоївши лише локальну змінну, дерево не зміниться:

```ts
// Помилка з плану: «видалити» вузол, переприсвоївши локальну змінну. Батько про це не дізнається.
type Node = { key: number; left: Node | null; right: Node | null };
const leaf = (key: number): Node => ({ key, left: null, right: null });
const root: Node = { key: 15, left: { key: 6, left: leaf(3), right: { key: 7, left: null, right: leaf(13) } }, right: leaf(18) };

const inOrder = (x: Node | null): number[] => (x === null ? [] : [...inOrder(x.left), x.key, ...inOrder(x.right)]);

function deleteWrong(root: Node, key: number): void {
  let x: Node | null = root;
  while (x !== null && x.key !== key) x = key < x.key ? x.left : x.right;
  if (x !== null) x = x.right;            // вузол 7 «замінено» дитиною, але лише в змінній x
}
deleteWrong(root, 7);
console.log("після deleteWrong(7):", inOrder(root).join(" "));
```

```
після deleteWrong(7): 3 6 7 13 15 18
```

Сімка лишилася в дереві, бо вузол 6 і далі вказує на неї. Змінна `x` — лише копія посилання. Змінити дерево можна
тільки через поле батька: `parent.right = ...`, або через корінь дерева, якщо видаляють корінь.

**Перевіряти властивість дерева лише між батьком і дітьми.** Дерево, в якому корінь 10 має ліву дитину 5, а та — праву
дитину 12, проходить таку перевірку: `5 < 10` і `12 > 5`. Але 12 лежить у лівому піддереві кореня 10, і пошук 12 піде
праворуч від кореня і не знайде його. Правильна перевірка передає кожному вузлу межі від усіх предків або дивиться, чи
симетричний обхід іде за зростанням.

**Домовлятися про однакові ключі по-різному в пошуку і вставці.** Якщо вставка кладе рівний ключ праворуч, а пошук
чекає його ліворуч, рівні ключі губляться.

**Забувати корінь як особливий випадок.** Видалення кореня і вставка в порожнє дерево змінюють саме посилання на
корінь, а не поле якогось батька.

**Писати рекурсію без думки про висоту.** На перекошеному дереві з сотні тисяч вузлів вона падає з `RangeError`.

порожнє. Ключ 5 стає правою дитиною 4. Пошук 5 потім пройде ті самі вузли 15, 6, 3, 4 і ще сам вузол 5.

</details>

**3. Чому в дереві з лекції після 9 іде 13, а після 4 — 6?**

<details><summary>Відповідь</summary>

Вузол 9 не має правого піддерева, тож треба піднятися. Вузол 9 — ліва дитина 13, і вже перший підйом іде з лівої
дитини: наступний — 13. Вузол 4 теж не має правого піддерева. Він права дитина 3, тож підйом продовжується; 3 — ліва
дитина 6, і на цьому підйом закінчується: наступний — 6.

</details>

**4. Видаліть з дерева лекції вузол 6. Як виглядатиме ліве піддерево кореня?**

<details><summary>Відповідь</summary>

У 6 дві дитини. Наступний за 6 — найлівіший у правому піддереві, тобто 7, і він сам права дитина 6. Тому 7
піднімається на місце 6 і забирає ліве піддерево 3 з дітьми 2 і 4. Права дитина 7, вузол 13 з дитиною 9, лишається
правою дитиною 7. Ліве піддерево кореня: 7, під ним ліворуч 3 з 2 і 4, праворуч 13 з 9.

</details>

**5. Чому дерево з відсортованих ключів має висоту `n − 1`, а дерево з перемішаних — логарифмічну?**

<details><summary>Відповідь</summary>

У відсортованому порядку кожен новий ключ більший за всі, тож спускається праворуч до самого низу і стає правою
дитиною попереднього. Виходить ланцюжок з `n` вузлів і `n − 1` ребер. У перемішаному порядку корінь — випадковий ключ,
і він ділить решту на дві частини випадкового розміру, як випадковий опорний у quicksort. Кожне піддерево будується
так само. Тому глибини ведуть себе як глибина рекурсії рандомізованого quicksort, тобто логарифмічно.

</details>

**6. CLRS питає у вправі 12.1-2: чи можна властивістю мінімальної купи надрукувати ключі за зростанням за `O(n)`, як
симетричним обходом дерева пошуку?**

<details><summary>Відповідь</summary>

Ні. Купа порівнює батька лише з дітьми, а про порядок між лівим і правим піддеревом не каже нічого. Якби за `O(n)`
можна було і збудувати купу, і надрукувати її відсортованою, вийшло б сортування порівняннями за `O(n)`. А день 11
фази 1 довів, що сортування порівняннями потребує `Ω(n log n)`. Дерево пошуку не суперечить цьому: Sedgewick у вправі
3.2.24 просить довести, що жоден алгоритм порівнянь не збудує дерево пошуку менш ніж за `log₂(n!) ≈ n log₂ n`
порівнянь.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| двійкове дерево | вузли, у кожного з яких не більше двох дітей і рівно один батько, крім кореня |
| корінь | єдиний вузол без батька |
| лист | вузол без дітей |
| двійкове дерево пошуку | двійкове дерево, де ключі лівого піддерева менші за ключ вузла, а правого — більші |
| глибина вузла | кількість ребер від кореня до вузла |
| висота дерева | найбільша глибина вузла; у ребрах, тож дерево з одного вузла має висоту 0 |
| симетричний обхід | обхід «ліве піддерево, вузол, праве піддерево»; у дереві пошуку видає ключі за зростанням |
| наступний за величиною, successor | вузол, що йде після даного в симетричному обході |
| видалення Гіббарда | видалення вузла з двома дітьми заміною на наступний за величиною |
| доповнення дерева | додаткове поле у вузлі, наприклад розмір піддерева, яке підтримують під час змін |
