Жодна з трьох мов не має в стандартній бібліотеці дерева, яке тримає ключі за порядком і вставляє за `O(log n)`. Це

«Performance Notes» модуля `bisect` вона згадує пакет Sorted Collections.

## Python: відсортований список з `bisect`

`bisect.insort(a, x)` вставляє `x` у відсортований список так, щоб він лишився відсортованим. Документація пояснює, що
функція спершу знаходить місце бінарним пошуком, а потім викликає звичайне `insert` списку. Розділ «Performance Notes»
підсумовує: функції `insort` коштують `O(n)`, бо логарифмічний пошук місця тоне в лінійному кроці вставки.

Чому ж на практиці цей підхід часто досить швидкий? Вставка в список зсуває хвіст списку одним копіюванням пам'яті
всередині інтерпретатора, написаного на C. Таке копіювання дуже швидке, і поки список не надто великий, воно обганяє
дерево з вузлами-об'єктами Python, де кожен крок спуску — окремий виклик і окреме звернення до пам'яті.

Програма нижче вставляє випадкові ключі частинами і міряє середній час однієї вставки в кожній частині.

```python
# Скільки коштує «впорядкована множина» на списку з bisect: вставка 400 тисяч випадкових ключів частинами.
import bisect
import random
import time

random.seed(1)  # стале зерно лише для того, щоб повторювались ключі; час однаково залежить від машини
xs: list[int] = []
done = 0
for target in (50_000, 100_000, 200_000, 400_000):
    start = time.perf_counter()
    while done < target:
        bisect.insort(xs, random.randrange(10**12))
        done += 1
    batch = target // 2 if target > 50_000 else target
    per_insert = (time.perf_counter() - start) / batch * 1e6
    print(f"size {target:>9,}: last {batch:>7,} inserts took {per_insert:5.2f} µs each")

i = bisect.bisect_left(xs, 500_000_000_000)
print("first key >= 5e11:", xs[i], " keys below it:", i)
```

```
size    50,000: last  50,000 inserts took  4.59 µs each
size   100,000: last  50,000 inserts took 12.89 µs each
size   200,000: last 100,000 inserts took 22.89 µs each
size   400,000: last 200,000 inserts took 43.38 µs each
first key >= 5e11: 500000723332  keys below it: 199805
```

Що видно:

- **Час вставки росте разом з розміром списку.** Від 50 до 400 тисяч елементів він виріс з 4,6 до 43 мікросекунд,
  майже в десять разів, приблизно як розмір. Це і є `O(n)` з документації.
- **Але абсолютні числа малі.** 43 мікросекунди на вставку — це понад 20 тисяч вставок за секунду навіть у списку з
  400 тисяч елементів. Для багатьох програм цього досить.
- **Пошук лишається швидким.** `bisect_left` знайшов перший ключ, не менший за `5 · 10¹¹`, і заодно сказав, скільки
  ключів менші за нього, 199 805. Це запит «ранг», який у дереві потребував би лічильника розмірів у вузлах.

Числа часу залежать від машини, тож у вас вони будуть іншими, але зріст буде тим самим. Ваше завдання в практиці —
знайти розмір, з якого ваше `LLRB` на Python обганяє список з `bisect`.

## Go: узагальнена структура через `cmp.Ordered`

Go з версії 1.18 має дженерики, тобто типи і функції з параметрами типів. Пакет `cmp`, що з'явився в Go 1.21, визначає
обмеження `cmp.Ordered`: так позначають усі типи, для яких працюють оператори `<`, `<=`, `>` і `>=`. Це цілі числа,
числа з рухомою комою і рядки, а також власні типи на їхній основі, позначені знаком `~`.

Пакет `slices` дає дві потрібні функції. `slices.BinarySearch` шукає значення у відсортованому зрізі і повертає
позицію та ознаку «знайдено». `slices.Insert` вставляє значення на позицію і зсуває хвіст; документація пише, що це
`O(len(s) + len(v))`. Разом вони дають ту саму впорядковану множину, що й `bisect` у Python, але для будь-якого
впорядкованого типу.

```go
// Впорядкована множина на відсортованому зрізі для будь-якого типу з cmp.Ordered.
package main

import (
	"cmp"
	"fmt"
	"slices"
)

type SortedSet[T cmp.Ordered] struct {
	items []T
}

// Add шукає місце двійковим пошуком і вставляє туди; вставка зсуває хвіст зрізу, тож O(n).
func (s *SortedSet[T]) Add(v T) bool {
	i, found := slices.BinarySearch(s.items, v)
	if found {
		return false
	}
	s.items = slices.Insert(s.items, i, v)
	return true
}

func (s *SortedSet[T]) Has(v T) bool {
	_, found := slices.BinarySearch(s.items, v)
	return found
}

func main() {
	var nums SortedSet[int]
	for _, v := range []int{42, 7, 19, 7, 3} {
		nums.Add(v)
	}
	fmt.Println(nums.items, nums.Has(19), nums.Has(20))

	var words SortedSet[string]
	for _, w := range []string{"pear", "apple", "fig"} {
		words.Add(w)
	}
	fmt.Println(words.items)
}
```

```
[3 7 19 42] true false
[apple fig pear]
```

Що видно:

- **Один код працює для двох типів.** `SortedSet[int]` і `SortedSet[string]` — це той самий код, і компілятор
  перевірив, що обидва типи задовольняють `cmp.Ordered`.
- **Повтор відкинуто.** Сімку додали двічі, а в множині вона одна, бо `BinarySearch` повернув `found = true`.
- **Рядки впорядковано за байтами.** `apple`, `fig`, `pear` стоять за абеткою лише тому, що це латиниця. Для кирилиці
  діє те саме застереження, що й у фазі 1: порядок за номерами символів, а не за правилами мови.

### Коли `cmp.Ordered` не годиться

Обмеження `cmp.Ordered` пускає лише типи з операторами порівняння. Структура таких операторів не має.

```go
// Структура не задовольняє cmp.Ordered: для неї немає операторів < і >.
package main

import "cmp"

type SortedSet[T cmp.Ordered] struct{ items []T }

type Point struct{ X, Y int }

func main() {
	var s SortedSet[Point]
	_ = s
}
```

```
# badkey
./main.go:11:18: Point does not satisfy cmp.Ordered (Point missing in ~int | ~int8 | ~int16 | ~int32 | ~int64 | ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr | ~float32 | ~float64 | ~string)
```

Компілятор пояснює причину: тип `Point` не входить у перелік типів, з яких складається `cmp.Ordered`. Learning Go
розв'язує цю проблему інакше. У главі 8 Bodner будує узагальнене дерево, яке приймає не обмеження, а функцію
порівняння: `type OrderableFunc[T any] func(t1, t2 T) int`. Тип `Tree[T any]` зберігає цю функцію і передає її вузлам.
Для чисел підходить готова `cmp.Compare[int]`, а для структури ви пишете свою, наприклад порівняння спершу за `X`,
потім за `Y`.

Два підходи — це обмін зручності на гнучкість. `cmp.Ordered` не потребує жодної функції, але працює лише для простих
типів. Функція порівняння працює для будь-якого типу, але її треба передати при створенні дерева. Пункт 3 практики
просить перший варіант; другий корисний, коли ключ — запис з кількох полів.

## Пастка: порядок вставки — не порядок ключів

Словник Python і `Map` JavaScript повертають ключі в тому порядку, у якому їх додавали. Документація Python пише про
перегляди словника: ключі і значення обходяться в порядку вставки. Через це їх легко прийняти за впорядковані
структури.

```python
# Словник пам'ятає порядок вставки, а не порядок ключів.
prices = {"pear": 3, "apple": 5, "fig": 2}
print(list(prices))          # порядок, у якому ключі додавали
print(sorted(prices))        # порядок ключів
```

```
['pear', 'apple', 'fig']
['apple', 'fig', 'pear']
```

```ts
// Map у JavaScript так само пам'ятає порядок вставки.
const prices = new Map([["pear", 3], ["apple", 5], ["fig", 2]]);
console.log([...prices.keys()]);
console.log([...prices.keys()].sort());
```

```
[ 'pear', 'apple', 'fig' ]
[ 'apple', 'fig', 'pear' ]
```

Обидві мови повернули `pear`, `apple`, `fig` — порядок, у якому ключі вставляли. Порядок ключів — `apple`, `fig`,
`pear` — дав лише явний `sorted` чи `sort`, а сортування коштує `O(n log n)` при кожному запиті. Запити «найменший
ключ», «наступний після `x`», «всі ключі від `a` до `b`» словник не вміє. Їх уміють дерева цієї фази і відсортований
список з `bisect`.

У Go ситуація ще жорсткіша: документація пише, що порядок обходу `map` у циклі `range` не визначений і може
відрізнятися від одного обходу до іншого.

## Типові помилки

**Вважати `dict` чи `Map` впорядкованими.** Це пастка дня. Вони пам'ятають порядок вставки, а не порядок ключів.

**Покладатися на порядок обходу `map` у Go.** Він не визначений. Тести, що порівнюють результат з очікуваним списком,
падатимуть випадково.

**Забути, що `slices.Insert` повертає новий зріз.** Як і `append`, вона може виділити новий масив. Без присвоєння
`s.items = slices.Insert(...)` вставка загубиться.

**Переносити рекурсію без зміни.** Python обмежує глибину рекурсії, за замовчуванням близько тисячі викликів. Для
збалансованих дерев це не важить, бо висота логарифмічна, але `UnionFind` без рангу з дня 10 на Python упаде так само,
як упав у Node.

**Вимірювати час однієї вставки.** Один виклик займає мікросекунди, і похибка таймера більша за сам вимір. Міряйте
тисячі вставок і діліть.

## Перевірте себе

**1. Чому `bisect.insort` коштує `O(n)`, хоча використовує бінарний пошук?**

<details><summary>Відповідь</summary>

Бінарний пошук знаходить місце за `O(log n)`, але потім `insert` зсуває всі елементи після цього місця на одну
позицію. Зсув у середньому зачіпає половину списку, тож вставка коштує `O(n)`. Документація `bisect` пише саме це:
логарифмічний пошук тоне в лінійній вставці.

</details>

**2. Вставка в список з 400 тисяч елементів займає 43 мікросекунди. Скільки приблизно займе вставка в список з 4
мільйонів?**

<details><summary>Відповідь</summary>

Близько 430 мікросекунд, бо час росте лінійно з розміром списку. Мільйон таких вставок займе кілька хвилин, і тут
дерево з `O(log n)` на вставку стає помітно вигіднішим.

</details>

**3. Чому `SortedSet[Point]` не компілюється, а дерево з Learning Go для `Point` працюватиме?**

<details><summary>Відповідь</summary>

`cmp.Ordered` вимагає, щоб тип був числом чи рядком або типом на їхній основі, бо код використовує оператор `<`.
Структура таких операторів не має. Дерево Learning Go не використовує операторів, воно викликає передану функцію
порівняння, а таку функцію можна написати для будь-якого типу.

</details>

**4. Колега каже: «Мені потрібні ключі за порядком, візьму `dict`, він з Python 3.7 впорядкований». Що не так?**

<details><summary>Відповідь</summary>

Словник пам'ятає порядок, у якому ключі додавали, а не порядок самих ключів. Якщо ключі приходять не за зростанням,
обхід словника поверне їх не за зростанням. Для порядку ключів потрібні `sorted` при кожному запиті, відсортований
список з `bisect` або дерево.

</details>

**5. Що повертає `slices.BinarySearch`, коли значення немає в зрізі, і навіщо це потрібно?**

<details><summary>Відповідь</summary>

Позицію, на якій значення мало б стояти, і `false`. Саме цю позицію передають у `slices.Insert`, щоб вставити значення
і не зламати відсортованість. Один пошук відповідає і на «чи є», і на «куди вставити».

</details>

**6. Чому в Python відсортований список часто швидший за дерево, хоча асимптотично гірший?**

<details><summary>Відповідь</summary>

Сталі множники різні. Зсув хвоста списку — одне копіювання пам'яті в C, дуже швидке для кожного байта. Спуск деревом з
вузлів-об'єктів Python — десятки кроків інтерпретатора, кожен з викликом методу і зверненням до розкиданих у пам'яті
об'єктів. Поки `n` не дуже велике, лінійна, але швидка операція обганяє логарифмічну, але повільну.

</details>
