## Python: черга

Список Python уміє забирати перший елемент методом `pop(0)`. Але документація модуля `collections` попереджає: списки
оптимізовано для операцій, що не змінюють їхньої довжини, а `pop(0)` і `insert(0, v)` коштують `O(n)`, бо змінюють і
розмір, і розташування даних у пам'яті. Підручник Python у розділі «Using Lists as Queues» каже те саме простіше:
вставляти й забирати на початку списку повільно, бо всі інші елементи треба зсунути на одне місце. Це та сама пастка,
що `shift` у JavaScript з дня 2.

Для черги документація радить `collections.deque`. Дека, тобто двобічна черга, додає й забирає елементи з обох кінців
приблизно за `O(1)`.

Програма нижче кладе в чергу `n` чисел і забирає їх усі з голови двома способами.

```python
# Черга на списку проти collections.deque: покласти n чисел і забрати їх усі з голови.
import time
from collections import deque


def drain_list(n):
    q = list(range(n))
    start = time.perf_counter()
    while q:
        q.pop(0)  # список зсуває всі елементи, що лишилися, на одне місце
    return (time.perf_counter() - start) * 1000


def drain_deque(n):
    q = deque(range(n))
    start = time.perf_counter()
    while q:
        q.popleft()  # дека просто пересуває свій початок
    return (time.perf_counter() - start) * 1000


for n in (50_000, 100_000, 200_000, 400_000):
    print(f"n={n:>7,}  list.pop(0): {drain_list(n):8.1f} ms   deque.popleft(): {drain_deque(n):5.1f} ms")
```

```
n= 50,000  list.pop(0):    212.6 ms   deque.popleft():   1.5 ms
n=100,000  list.pop(0):    846.4 ms   deque.popleft():   3.0 ms
n=200,000  list.pop(0):   3508.3 ms   deque.popleft():   5.8 ms
n=400,000  list.pop(0):  15257.6 ms   deque.popleft():  11.7 ms
```

Що видно:

- **Час списку росте квадратично.** Черга щоразу вдвічі довша, а час щоразу приблизно вчетверо більший: 0,2 секунди,
  0,8, 3,5 і 15. Кожен із `n` викликів `pop(0)` зсуває в середньому `n / 2` елементів.
- **Час деки росте лінійно.** Черга вдвічі довша, і час удвічі більший: 1,5, 3,0, 5,8 і 11,7 мілісекунди.
- **Різниця на 400 тисячах елементів — понад тисячу разів.** Якщо зріст лишиться таким самим, черга з мільйона
  елементів на списку забере щонайменше півтори хвилини, а на деці близько 30 мілісекунд.

Числа часу залежать від машини, але зріст буде тим самим. Практичний висновок: у Python черга для пошуку в ширину — це
завжди `deque` з методами `append` і `popleft`.

Одне застереження з тієї самої сторінки документації: доступ до елемента деки за номером швидкий лише біля кінців, а в
середині коштує `O(n)`. Дека — це черга, а не масив.

## Python: граф

Якщо вершини мають довільні назви, граф зберігають у словнику: ключ — вершина, значення — список її сусідів. Сторінка
модуля `collections` показує для цього `defaultdict(list)`. Такий словник сам створює порожній список, коли до нього
звертаються з ключем, якого ще немає. Тому ребро додають одним рядком, без перевірки, чи вершина вже є.

Якщо вершини пронумеровано від `0` до `n − 1`, досить списку списків: `graph[v]` — список сусідів вершини `v`.

Обидва способи мають по одній помилці, на якій спотикаються майже всі. Програма нижче показує обидві.

```python
# Граф як словник списків. defaultdict сам створює порожній список для вершини, якої ще немає.
from collections import defaultdict

edges = [("a", "b"), ("a", "c"), ("b", "d")]


def build():
    graph = defaultdict(list)
    for u, v in edges:
        graph[u].append(v)  # для нової вершини u список з'являється сам
    return graph


graph = build()
print(dict(graph))
print("d" in graph, len(graph))
print(graph["d"])  # читання вершини, якої немає серед ключів, додає її у словник
print("d" in graph, len(graph))

graph = build()
try:
    for v in graph:
        for u in graph[v]:
            neighbors = graph[u]  # лише читання, але для вершини c воно змінює словник
except RuntimeError as error:
    print("RuntimeError:", error)

graph = build()
for v in graph:
    for u in graph[v]:
        neighbors = graph.get(u, [])  # get нічого не створює
print(len(graph))

# Пронумеровані вершини: список списків. Множення списку копіює посилання, а не списки.
wrong = [[]] * 3
wrong[0].append("x")
print(wrong)
right = [[] for _ in range(3)]
right[0].append("x")
print(right)
```

```
{'a': ['b', 'c'], 'b': ['d']}
False 2
[]
True 3
RuntimeError: dictionary changed size during iteration
2
[['x'], ['x'], ['x']]
[['x'], [], []]
```

Що видно:

- **Читання створює вершину.** Вершини `d` не було серед ключів: з неї не виходить жодного ребра. Після `graph["d"]`
  вона там з'явилася, і розмір словника зріс з 2 до 3. Документація пояснює чому: коли ключа немає, `defaultdict`
  викликає свою функцію, у нас `list`, вставляє результат у словник і лише тоді повертає його.
- **Через це падає обхід.** Цикл `for v in graph` обходить словник, а читання `graph[u]` для вершини `c` всередині
  циклу додає новий ключ. Python зупиняє обхід з `RuntimeError`. Документація словника попереджає: якщо під час обходу
  додавати чи видаляти записи, обхід може впасти або пропустити частину записів.
- **Ліки — `get`.** Метод `get` нічого не створює: документація `defaultdict` окремо каже, що функція для відсутніх
  ключів викликається лише для звертання у квадратних дужках. Після третього циклу в словнику, як і було, 2 ключі.
- **`[[]] * 3` — це один список тричі.** Сусіда додали вершині 0, а він з'явився в усіх трьох. Документація пояснює:
  множення списку копіює не вкладені списки, а посилання на той самий список. Правильний запис — `[[] for _ in
  range(3)]`: він створює три окремі списки.

## Python: межа рекурсії

Пошук у глибину природно пишеться рекурсією, і глибина рекурсії дорівнює довжині найдовшого шляху, яким пошук
спустився. У дні 3 рекурсивний пошук у Node впав на ланцюжку з 10 000 вершин. У Python межа нижча, і вона задана
числом.

Документація модуля `sys` описує дві функції. `sys.getrecursionlimit()` повертає найбільшу дозволену глибину стека
інтерпретатора. `sys.setrecursionlimit(limit)` її змінює. Межа існує, щоб нескінченна рекурсія не переповнила стек
самого інтерпретатора, написаного на C, і не обвалила Python цілком. Коли межу перевищено, Python кидає виняток
`RecursionError`.

Програма нижче проходить ланцюжок вершин рекурсією і циклом.

```python
# Межа рекурсії Python: пройти ланцюжок вершин рекурсією і циклом.
import sys


def length_recursive(v, next_of):
    if next_of[v] is None:
        return 1
    return 1 + length_recursive(next_of[v], next_of)  # кожна вершина ланцюжка — ще один вкладений виклик


def length_loop(v, next_of):
    count = 1
    while next_of[v] is not None:
        v = next_of[v]
        count += 1
    return count


def chain(n):  # вершина i веде до i + 1, остання нікуди не веде
    return list(range(1, n)) + [None]


def try_recursive(n):
    try:
        return length_recursive(0, chain(n))
    except RecursionError as error:
        return f"RecursionError: {error}"


print("limit:", sys.getrecursionlimit())
for n in (900, 1_000, 10_000):
    print(f"recursive n={n:>6,}:", try_recursive(n))
print(f"loop      n={1_000_000:,}:", length_loop(0, chain(1_000_000)))

sys.setrecursionlimit(20_000)
print("limit:", sys.getrecursionlimit())
print(f"recursive n={10_000:>6,}:", try_recursive(10_000))
```

```
limit: 1000
recursive n=   900: 900
recursive n= 1,000: RecursionError: maximum recursion depth exceeded
recursive n=10,000: RecursionError: maximum recursion depth exceeded
loop      n=1,000,000: 1000000
limit: 20000
recursive n=10,000: 10000
```

Що видно:

- **Межа за замовчуванням — 1000.** Ланцюжок з 900 вершин пройдено, а з 1000 уже ні.
- **Ланцюжок з 1000 вершин не вмістився в межу 1000.** Межа рахує всі вкладені виклики, а не лише виклики нашої
  функції. Поки працює рекурсія, на стеку вже лежать сама програма і функція `try_recursive`. Тому для рекурсії
  лишається трохи менше ніж 1000 рівнів.
- **Цикл проходить мільйон вершин.** Він не займає стек викликів зовсім.
- **Межу можна підняти.** Після `sys.setrecursionlimit(20_000)` ланцюжок з 10 000 вершин пройдено рекурсією.

Чому ж не піднімати межу завжди? Документація відповідає: найвища можлива межа залежить від платформи, і надто висока
межа може призвести до аварійного завершення. Межа — це запобіжник, а не налаштування швидкості. Розмір графа ви
зазвичай не контролюєте, тому надійний спосіб один: пошук у глибину з явним стеком, як у дні 3. Він упирається лише в
обсяг пам'яті.

## Go: черга на зрізі

У Go немає готової черги, і вона не потрібна. Черга — це зріз: додають у кінець через `append`, а голову забирають
одним із двох способів.

```go
// Черга на зрізі в Go: два способи забрати елемент з голови.
package main

import (
	"fmt"
	"time"
)

func main() {
	const n = 10_000_000

	// Спосіб 1: зріз не змінюється, вперед рухається номер голови.
	q := make([]int, 0, 16)
	start := time.Now()
	sum := 0
	for i := 0; i < n; i++ {
		q = append(q, i)
	}
	for head := 0; head < len(q); head++ {
		sum += q[head]
	}
	fmt.Println("head index:", sum, time.Since(start).Round(time.Millisecond))

	// Спосіб 2: після кожного читання зріз починається на один елемент далі.
	q = make([]int, 0, 16)
	start = time.Now()
	sum = 0
	for i := 0; i < n; i++ {
		q = append(q, i)
	}
	for len(q) > 0 {
		sum += q[0]
		q = q[1:] // елементи ніхто не зсуває: змінюється лише початок зрізу
	}
	fmt.Println("q = q[1:] :", sum, time.Since(start).Round(time.Millisecond))

	// Що відбувається з довжиною і місткістю, коли зріз починають далі.
	s := []int{10, 20, 30, 40}
	fmt.Println(len(s), cap(s), s)
	s = s[1:]
	fmt.Println(len(s), cap(s), s)
}
```

```
head index: 49999995000000 189ms
q = q[1:] : 49999995000000 255ms
4 4 [10 20 30 40]
3 3 [20 30 40]
```

Що видно:

- **Обидва способи швидкі.** Десять мільйонів елементів пройшли через чергу за частки секунди. В іншому запуску тієї
  самої програми другий спосіб був швидшим за перший: 110 мілісекунд проти 153. Різниця між ними — це шум вимірювання.
  Порівняйте з Python, де список витратив 15 секунд на 400 тисяч елементів.
- **`q = q[1:]` нічого не зсуває.** Стаття Go 101 пояснює, що зріз — це три числа: адреса першого елемента, довжина і
  місткість. Вираз `q[1:]` створює новий зріз, який дивиться на ту саму пам'ять, починаючи з наступного елемента. Тому
  в Go немає пастки `list.pop(0)`.
- **Місткість зменшується разом з довжиною.** Після `s = s[1:]` довжина й місткість стали 3 замість 4. Місце першого
  елемента цей зріз уже не використає. Go 101 називає це «kind-of memory leaking»: пам'ять лишається зайнятою, доки
  хоч один зріз дивиться на цей шматок.

Для пошуку в ширину це не страшно. Кожна вершина потрапляє в чергу один раз, тому за весь час у чергу покладуть не
більше ніж `V` елементів. Обирайте той спосіб, який вам легше читати.

## Go: граф

Граф у Go зберігають так само, як у Python: мапа зрізів `map[int][]int` для довільних вершин або зріз зрізів `[][]int`
для вершин від `0` до `n − 1`. Обидва дають сусідів вершини за `O(1)`. Але Go 101 застерігає: доступ до елемента мапи
зазвичай у кілька разів повільніший, ніж до елемента зрізу. Програма нижче міряє, у скільки саме.

```go
// Граф у Go двома способами: зріз зрізів і мапа зрізів. Мільйон вершин, з кожної виходить п'ять ребер.
package main

import (
	"fmt"
	"time"
)

const n = 1_000_000

// Сусіди вершини v: п'ять вершин, розкиданих по всьому графу.
func neighbor(v, k int) int { return (v*31 + k*200_003) % n }

func main() {
	start := time.Now()
	asSlice := make([][]int, n)
	for v := 0; v < n; v++ {
		for k := 1; k <= 5; k++ {
			asSlice[v] = append(asSlice[v], neighbor(v, k))
		}
	}
	buildSlice := time.Since(start)

	start = time.Now()
	asMap := make(map[int][]int)
	for v := 0; v < n; v++ {
		for k := 1; k <= 5; k++ {
			asMap[v] = append(asMap[v], neighbor(v, k))
		}
	}
	buildMap := time.Since(start)

	// Обхід: для кожної вершини подивитися на список сусідів кожного її сусіда.
	start = time.Now()
	total := 0
	for v := 0; v < n; v++ {
		for _, u := range asSlice[v] {
			total += len(asSlice[u])
		}
	}
	scanSlice := time.Since(start)

	start = time.Now()
	totalMap := 0
	for v := 0; v < n; v++ {
		for _, u := range asMap[v] {
			totalMap += len(asMap[u])
		}
	}
	scanMap := time.Since(start)

	ms := func(d time.Duration) string { return d.Round(time.Millisecond).String() }
	fmt.Println("[][]int       build", ms(buildSlice), " scan", ms(scanSlice), " total", total)
	fmt.Println("map[int][]int build", ms(buildMap), " scan", ms(scanMap), " total", totalMap)
}
```

```
[][]int       build 131ms  scan 48ms  total 25000000
map[int][]int build 516ms  scan 529ms  total 25000000
```

Що видно:

- **Відповідь однакова.** Обидва обходи нарахували 25 мільйонів, тож графи ті самі.
- **Обхід мапи повільніший в 11 разів.** 529 мілісекунд проти 48. Кожне звертання до мапи рахує хеш ключа і шукає його
  в таблиці, а звертання до зрізу — це одне додавання до адреси.
- **Побудова мапи повільніша вчетверо.** 516 мілісекунд проти 131.

Практичний висновок: якщо вершини можна пронумерувати підряд, нумеруйте і беріть зріз зрізів. Мапа потрібна, коли
вершини — рядки або рідкісні великі номери. Навіть тоді часто вигідніше один раз перевести назви в номери окремою
мапою, а сам граф тримати у зрізі.

## Go: глибока рекурсія

У Go стек не має малого сталого розміру. Кожна горутина, тобто легкий потік виконання Go, починає з малого стека, і
середовище виконання збільшує його, коли він заповнюється. Програма нижче проходить ланцюжок рекурсією, як програма
для Python вище.

```go
// Глибока рекурсія в Go: пройти ланцюжок вершин рекурсією.
package main

import "fmt"

// next[v] — наступна вершина ланцюжка, -1 означає кінець.
func length(v int, next []int) int {
	if next[v] == -1 {
		return 1
	}
	return 1 + length(next[v], next)
}

func chain(n int) []int {
	next := make([]int, n)
	for i := range next {
		next[i] = i + 1
	}
	next[n-1] = -1
	return next
}

func main() {
	for _, n := range []int{10_000, 1_000_000, 10_000_000, 100_000_000} {
		fmt.Println("recursive n =", n, "->", length(0, chain(n)))
	}
}
```

```
recursive n = 10000 -> 10000
recursive n = 1000000 -> 1000000
recursive n = 10000000 -> 10000000
runtime: goroutine stack exceeds 1000000000-byte limit
fatal error: stack overflow
```

Вивід тут скорочено: між двома останніми рядками Go друкує рядок з адресами стека, а після них довгий перелік
викликів.

Що видно:

- **Десять мільйонів вкладених викликів пройшли.** Це в десять тисяч разів глибше за межу Python.
- **Межа все ж є.** На ста мільйонах програма зупинилася з повідомленням, що стек перевищив мільярд байтів.
  Документація пакета `runtime/debug` називає це число: стек однієї горутини може зайняти щонайбільше 1 ГБ на
  64-бітних системах, і цю межу змінює функція `SetMaxStack`.
- **Це аварія, а не помилка.** Програма не повертає значення помилки, яке можна перевірити: вона завершується.
  Документація так і каже: якщо горутина перевищує межу, програма аварійно завершується.

Практичний висновок: рекурсивний пошук у глибину в Go безпечний, навіть коли глибина сягає сотень тисяч вершин. Явний
стек потрібен лише на справді величезних графах.

## Купа для Дейкстри і сортування для Крускала

Ці два інструменти ви вже знаєте з фази 1, тому тут лише те, що важить для перекладу.

**Купа в Python.** У `heapq` кладуть кортежі `(відстань, вершина)`. Підручник Python пояснює, що кортежі порівнюються
по черзі: спершу перші елементи, а якщо вони рівні, то другі. Отже, купа впорядкує записи за відстанню. Змінити
відстань запису, що вже лежить у купі, `heapq` не вміє. Документація в розділі «Priority Queue Implementation Notes»
радить позначити старий запис вилученим і додати новий. Варіант Дейкстри із застарілими записами з дня 6 робить саме
це: кладе нову пару і пропускає стару, коли та вийде з купи.

**Купа в Go.** Пакет `container/heap` вимагає від вашого типу п'ять методів. Приклад `PriorityQueue` в документації
пакета зберігає в кожному записі його номер у купі і після зміни пріоритету викликає `heap.Fix`. Це справжнє зменшення
ключа, якого немає в Python. Годяться обидва шляхи: застарілі записи простіші, а `heap.Fix` тримає купу меншою.
Зверніть увагу, що приклад документації порівнює через `>`, бо першим віддає найбільший пріоритет. Для Дейкстри
потрібне `<` за відстанню.

**Сортування ребер.** У Python ребра зручно тримати кортежами `(вага, u, v)`: тоді `edges.sort()` упорядкує їх за
вагою без жодної функції порівняння. У Go беруть `slices.SortFunc` з функцією, що порівнює ваги через `cmp.Compare`.
Документація попереджає, що це сортування не гарантує стабільності. Тому ребра рівної ваги в трьох мовах можуть стати
в різному порядку, і Крускал може взяти різні ребра. З дня 9 ви знаєте, що це не помилка: мінімальних кістякових дерев
буває кілька, а вага в усіх однакова.

## Пастка: `list.pop(0)` як черга

Пошук у ширину з `list.pop(0)` дає правильні відстані і проходить усі тести. Помилку видно лише на годиннику. На
графі, де в черзі одночасно лежить багато вершин, кожне `pop(0)` зсуває всю чергу, і алгоритм з `O(V + E)` стає
квадратичним. Вивід у розділі «Python: черга» показує масштаб: 15 секунд замість 12 мілісекунд на 400 тисячах
елементів.

Впізнати цю помилку можна так: подвойте граф і подивіться на час. Якщо час зріс удвічі, усе гаразд. Якщо вчетверо,
шукайте `pop(0)`, `insert(0, …)` або `del q[0]`.

## Для співбесіди

| Питання | Коротка відповідь |
|---------|-------------------|
| Чим робити чергу в Python? | `collections.deque`: `append` і `popleft` за `O(1)`. |
| Чому не `list.pop(0)`? | Воно зсуває всі елементи, `O(n)` на виклик; пошук у ширину стає квадратичним. |
| Як зберігати граф у Python? | `defaultdict(list)` для довільних вершин, список списків для пронумерованих. |
| Яка межа рекурсії в Python? | 1000 вкладених викликів за замовчуванням; перевищення кидає `RecursionError`. |
| Що робити з глибокою рекурсією? | Переписати на явний стек, а не піднімати межу. |
| Чи має Go пастку `pop(0)`? | Ні: `q = q[1:]` лише пересуває початок зрізу. |
| Мапа чи зріз для графа в Go? | Зріз зрізів, якщо вершини пронумеровано; у вимірі лекції обхід мапи повільніший в 11 разів. |
| Чи має Go межу рекурсії? | Стек росте сам до 1 ГБ; перевищення — аварійне завершення. |
| Як змінити пріоритет у купі? | Python: новий запис і пропуск застарілого; Go: так само або `heap.Fix` з номером запису. |

## Типові помилки

**`list.pop(0)` як черга.** Це пастка дня: відповіді правильні, а час квадратичний.

**`[[]] * n` для списку суміжності.** Усі вершини отримують той самий список сусідів.

**Читати `defaultdict` для перевірки.** Звертання `graph[v]` до вершини, якої немає, додає її у словник, а під час
обходу словника ще й обвалює цикл. Для читання беріть `get`.

**Піднімати межу рекурсії замість явного стека.** На більшому графі програма впаде знову, і цього разу, можливо, без
винятку.

**Мапа для пронумерованих вершин у Go.** Вона працює, але в рази повільніше за зріз зрізів.

**Порівнювати набори ребер Крускала між мовами.** Порядок ребер рівної ваги після сортування в мовах різний.
Порівнюйте суму ваг і кількість ребер.

**Викликати методи `Push` і `Pop` свого типу напряму.** Це помилка з дня 13 фази 1: порядок купи підтримують лише
функції `heap.Push` і `heap.Pop`.

## Перевірте себе

**1. Пошук у ширину на Python з `list.pop(0)` витратив на чергу 1 секунду для графа зі 100 000 вершин. Скільки він
витратить для 400 000 вершин, якщо черга росте разом із графом?**

<details><summary>Відповідь</summary>

Близько 16 секунд. Час черги на списку росте квадратично: граф учетверо більший, тому час більший у 16 разів. З
`deque` час зріс би лише вчетверо.

</details>

**2. Межа рекурсії 1000, ланцюжок має рівно 1000 вершин. Чому рекурсія все одно впала?**

<details><summary>Відповідь</summary>

Межа рахує всі вкладені виклики на стеку, а не лише виклики рекурсивної функції. До початку рекурсії на стеку вже були
сама програма і функція, яка рекурсію запустила. Разом з тисячею рекурсивних викликів це більше за 1000.

</details>

**3. Що надрукує цей код?**

```python
graph = [[]] * 3
graph[0].append(1)
print(graph)
```

<details><summary>Відповідь</summary>

`[[1], [1], [1]]`. Множення створило список із трьох посилань на один і той самий вкладений список. Сусіда додали в
нього один раз, а видно його через усі три посилання. Програма лекції показала те саме з рядком `"x"`.

</details>

**4. Що надрукує цей код на Go і чому?**

```go
s := []int{1, 2, 3}
t := s[1:]
t[0] = 9
fmt.Println(s, t)
```

<details><summary>Відповідь</summary>

`[1 9 3] [9 3]`. Зріз `t` дивиться на ту саму пам'ять, що й `s`, починаючи з другого елемента. Запис у `t[0]` змінює
`s[1]`. З тієї самої причини `q = q[1:]` у черзі нічого не копіює.

</details>

**5. Доступ до елемента мапи і до елемента зрізу в Go коштує `O(1)`. Чому ж обхід графа в мапі був повільніший в 11
разів?**

<details><summary>Відповідь</summary>

`O(1)` каже лише, що час не росте з розміром. Сама стала різна. Для зрізу це одне додавання до адреси. Для мапи треба
порахувати хеш ключа, знайти потрібну комірку таблиці і порівняти ключі. Крім того, сусідні елементи зрізу лежать у
пам'яті поруч, а записи мапи розкидані.

</details>

**6. Крускал на Python і на Go повернув різні набори ребер для того самого графа. Це помилка перекладу?**

<details><summary>Відповідь</summary>

Не обов'язково. Якщо в графі є ребра рівної ваги, сортування в різних мовах може поставити їх у різному порядку, і
Крускал візьме різні ребра. Перевірте суму ваг і кількість ребер: якщо вони збігаються, обидва дерева мінімальні. Якщо
суми різні, тоді це помилка.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| дека | двобічна черга: додає і забирає з обох кінців за `O(1)`; у Python це `collections.deque` |
| `defaultdict` | словник Python, який сам створює значення для ключа, якого ще немає |
| межа рекурсії | найбільша дозволена кількість вкладених викликів; у Python за замовчуванням 1000 |
| `RecursionError` | виняток Python, коли межу рекурсії перевищено |
| зріз | у Go — адреса першого елемента, довжина і місткість; кілька зрізів можуть дивитися на ту саму пам'ять |
| горутина | легкий потік виконання в Go зі стеком, що росте сам |
