# Лекція. Фаза 4, день 1. Розділяй і володарюй: множення Карацуби

У школі всіх учать множити числа в стовпчик. Цей спосіб здається єдиним можливим: кожну цифру одного числа треба
помножити на кожну цифру другого, і пропустити жодну пару начебто не можна. Так думав і Андрій Колмогоров, один з
найсильніших математиків двадцятого століття. Книжка Erickson розповідає, що він привселюдно припустив: швидшого
способу множення немає. У 1960 році Колмогоров зібрав у Московському університеті семінар про це припущення. Приблизно
за тиждень 23-річний студент Анатолій Карацуба приніс йому спосіб, який множить швидше. Сьогодні ви розберете цей
спосіб і прийом, на якому він стоїть. Читання займе близько 45 хвилин. Під кожним прикладом коду стоїть справжній
вивід з Node 24.22.

**Після лекції ви зможете пояснити:**

- з яких трьох кроків складається прийом «розділяй і володарюй»;
- чому поділ числа навпіл сам собою нічого не пришвидшує;
- як Карацуба обходиться трьома добутками половин замість чотирьох;
- чому заміна чотирьох добутків на три змінює показник степеня, а не лише стале число;
- як та сама ідея працює для матриць в алгоритмі Штрассена;
- чому рекурсію не доводять до самого дна.

## Прийом «розділяй і володарюй»

Ви вже бачили цей прийом у фазі 1. Сортування злиттям з дня 7 ділить масив навпіл, сортує кожну половину тим самим
способом і зливає дві відсортовані половини в одну. Швидке сортування з дня 8 робить схоже. Erickson описує спільну
схему трьома кроками:

1. **Поділити.** Задачу ділять на кілька менших задач того самого виду. Менші задачі мають бути незалежними одна від
   одної.
2. **Доручити.** Кожну меншу задачу розв'язує той самий алгоритм, тобто рекурсивний виклик.
3. **Зібрати.** З відповідей на менші задачі складають відповідь на всю задачу.

Прийом називають «розділяй і володарюй», англійською divide and conquer. Erickson додає до схеми ще одне правило: коли
задача стає меншою за певний сталий розмір, рекурсію припиняють і розв'язують задачу напряму. Цей найменший випадок
називають базою рекурсії.

Час такого алгоритму записують рівнянням, яке ви розв'язували у фазі 0, у день 6. Конспект MIT 6.046J дає загальний
вигляд: `T(n) = a·T(n/b) + робота на збирання`. Тут `a` — це кількість менших задач, а `n/b` — розмір кожної з них.
Для сортування злиттям `a = 2` і `b = 2`, а збирання коштує `n` кроків, тому `T(n) = 2T(n/2) + n`, і це дає `n log n`.

У сортуванні прийом дав виграш завдяки дешевому збиранню. Сьогодні ви побачите іншу його силу. Якщо зменшити число
`a`, тобто кількість рекурсивних викликів, зміниться показник степеня в оцінці часу.

## Скільки коштує множення в стовпчик

Візьмемо два числа, 1234 і 5678. У стовпчик їх множать так: число 1234 множать окремо на кожну цифру числа 5678, а
чотири проміжні результати додають зі зсувом. Кожну з чотирьох цифр першого числа доводиться помножити на кожну з
чотирьох цифр другого. Разом це 4 · 4 = 16 множень цифр.

Для двох чисел по `n` цифр множень цифр буде `n · n`, тобто `n²`. Додавань теж близько `n²`, тому весь час
пропорційний `n²`. Для чисел з 1024 цифр це 1 048 576 множень цифр.

У цій лекції ми рахуємо саме множення цифр. Ця кількість не залежить від комп'ютера і від мови, тому її можна
порівнювати точно. Числа такої довжини трапляються і в справжніх програмах: у JavaScript для них є вбудований тип
`BigInt`, який зберігає цілі числа довільної довжини.

## Перша спроба: поділити число навпіл

Спробуймо застосувати прийом. Число 1234 можна записати як 12 · 100 + 34, а число 5678 — як 56 · 100 + 78. Позначимо
половини буквами: `a = 12`, `b = 34`, `c = 56`, `d = 78`. Тоді добуток розкладається на чотири менші добутки:

```
1234 · 5678 = (a·100 + b) · (c·100 + d)
            = a·c·10000 + (a·d + b·c)·100 + b·d
```

Порахуємо з числами:

| Добуток | Значення |
|---------|----------|
| `a·c` = 12 · 56 | 672 |
| `a·d` = 12 · 78 | 936 |
| `b·c` = 34 · 56 | 1904 |
| `b·d` = 34 · 78 | 2652 |

Середній доданок дорівнює 936 + 1904 = 2840. Разом виходить 6 720 000 + 284 000 + 2652 = 7 006 652. Це правильна
відповідь.

Множення на 100 і на 10 000 тут не є справжнім множенням. Щоб помножити число на степінь десятки, досить дописати до
нього нулі. Тому вся справжня робота — це чотири добутки половин і кілька додавань.

Для чисел по `n` цифр половини мають по `n/2` цифр, і формула та сама, лише замість 100 стоїть 10 у степені `n/2`.
Алгоритм виходить такий: поділити обидва числа навпіл, чотири рази викликати себе для половин, скласти відповідь
зсувами і додаваннями. Додавання і зсуви коштують порядку `n` кроків. Час описує рівняння `T(n) = 4T(n/2) + n`.

Ось цей алгоритм у коді. Число тут записано масивом цифр, бо звичайний тип `number` точно зберігає цілі числа лише
приблизно до 16 десяткових цифр.

```ts
// Число записано масивом цифр, і молодша цифра стоїть першою: 1234 — це [4, 3, 2, 1].
// Так розряд цифри збігається з її індексом у масиві.
type Digits = number[];

let digitMultiplications = 0; // скільки разів програма перемножила дві цифри

// Додавання в стовпчик: іде від молодшої цифри і переносить десяток у наступний розряд.
function add(x: Digits, y: Digits): Digits {
  const result: Digits = [];
  let carry = 0;
  for (let i = 0; i < Math.max(x.length, y.length) || carry > 0; i += 1) {
    const sum = (x[i] ?? 0) + (y[i] ?? 0) + carry;
    result.push(sum % 10);
    carry = Math.floor(sum / 10);
  }
  return result;
}

// Множення на 10 у степені k: дописати k нулів з молодшого боку. Жодного множення цифр тут немає.
function shift(x: Digits, k: number): Digits {
  return [...new Array<number>(k).fill(0), ...x];
}

// Множення поділом навпіл із чотирма добутками половин.
// Обидва числа мають однакову довжину n, і n є степенем двійки.
function splitMultiply(x: Digits, y: Digits): Digits {
  const n = x.length;
  if (n === 1) {
    digitMultiplications += 1;
    const product = x[0] * y[0]; // найбільше 9 · 9 = 81, тобто дві цифри
    return [product % 10, Math.floor(product / 10)];
  }
  const m = n / 2;
  const b = x.slice(0, m); // молодша половина x
  const a = x.slice(m); //    старша половина x, тобто x = a · 10^m + b
  const d = y.slice(0, m);
  const c = y.slice(m); //    y = c · 10^m + d
  const ac = splitMultiply(a, c);
  const ad = splitMultiply(a, d);
  const bc = splitMultiply(b, c);
  const bd = splitMultiply(b, d);
  // x · y = ac · 10^(2m) + (ad + bc) · 10^m + bd
  return add(add(shift(ac, 2 * m), shift(add(ad, bc), m)), bd);
}

// Перевірка через BigInt: вбудований тип цілих чисел довільної довжини.
function toBigInt(x: Digits): bigint {
  return BigInt([...x].reverse().join(''));
}

// Генератор mulberry32: з одного початкового числа щоразу виходить та сама послідовність.
let state = 2026;
function random(): number {
  state = (state + 0x6d2b79f5) | 0;
  let t = Math.imul(state ^ (state >>> 15), 1 | state);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}
function randomDigits(n: number): Digits {
  return Array.from({ length: n }, () => Math.floor(random() * 10));
}

const small = splitMultiply([4, 3, 2, 1], [8, 7, 6, 5]);
console.log('1234 · 5678 =', toBigInt(small), 'множень цифр:', digitMultiplications);

for (const n of [4, 16, 64, 256]) {
  const x = randomDigits(n);
  const y = randomDigits(n);
  digitMultiplications = 0;
  const product = splitMultiply(x, y);
  const correct = toBigInt(product) === toBigInt(x) * toBigInt(y);
  console.log(`n=${n}: множень цифр ${digitMultiplications}, n·n = ${n * n}, збігається з BigInt: ${correct}`);
}
```

```
1234 · 5678 = 7006652n множень цифр: 16
n=4: множень цифр 16, n·n = 16, збігається з BigInt: true
n=16: множень цифр 256, n·n = 256, збігається з BigInt: true
n=64: множень цифр 4096, n·n = 4096, збігається з BigInt: true
n=256: множень цифр 65536, n·n = 65536, збігається з BigInt: true
```

Що видно у виводі.

**Відповіді правильні.** Кожен добуток збігся з тим, що порахував вбудований тип `BigInt`. Отже, формула з чотирма
добутками працює для чисел будь-якої довжини, яка є степенем двійки.

**Множень цифр рівно `n · n`.** Для 256 цифр лічильник показав 65 536, і це точно 256 · 256. Алгоритм зробив стільки ж
множень цифр, скільки множення в стовпчик.

Причина проста. Рекурсія спускається, доки в числах не лишиться по одній цифрі. На кожному рівні кожна задача породжує
чотири менші. Після першого поділу задач 4, після другого 16, і так далі. Число з `n` цифр можна ділити навпіл `log₂
n` разів, тому на дні опиняється 4 у степені `log₂ n` задач, а це рівно `n²`. Erickson підсумовує: цей алгоритм
множить кожну цифру одного числа на кожну цифру другого, так само як шкільний спосіб.

**Практичний висновок:** поділ задачі на частини сам собою нічого не пришвидшує. Якщо частин стільки, що на дні
рекурсії лежить та сама кількість дрібних кроків, ви отримали той самий алгоритм, записаний складніше. Перш ніж писати
рекурсивний алгоритм, запишіть його рівняння і подивіться, що воно дає.

## Ідея Карацуби: три добутки замість чотирьох

Подивіться ще раз на формулу. Добутки `a·d` і `b·c` нам окремо не потрібні. Потрібна лише їхня сума `a·d + b·c`.
Карацуба помітив, що цю суму можна отримати одним множенням, якщо вже відомі `a·c` і `b·d`.

Перемножимо суми половин:

```
(a + b) · (c + d) = a·c + a·d + b·c + b·d
```

У правій частині стоять усі чотири добутки разом. Два крайні, `a·c` і `b·d`, ми однаково рахуємо. Якщо відняти їх,
залишиться саме те, що потрібно:

```
a·d + b·c = (a + b)·(c + d) − a·c − b·d
```

Порахуємо на тих самих числах:

| Крок | Обчислення | Значення |
|------|------------|----------|
| перший добуток | `a·c` = 12 · 56 | 672 |
| другий добуток | `b·d` = 34 · 78 | 2652 |
| суми половин | `a + b` = 46, `c + d` = 134 | |
| третій добуток | 46 · 134 | 6164 |
| середній доданок | 6164 − 672 − 2652 | 2840 |

Середній доданок вийшов 2840, той самий, що й раніше з двох добутків. Далі все як у першій спробі: 6 720 000 + 284 000
+ 2652 = 7 006 652.

Множень стало три замість чотирьох. За це заплачено двома додаваннями і двома відніманнями. Додавання і віднімання
чисел з `n` цифр коштують порядку `n` кроків, а множення в стовпчик коштує `n²`, тому обмін вигідний.

Наступний приклад робить один такий крок на готових числах типу `BigInt` і рахує, скільки множень цифр зробить
рекурсія з чотирма і з трьома добутками. Самого алгоритму Карацуби для масивів цифр тут немає: його ви напишете в
практиці.

```ts
// Один крок ідеї Карацуби на готових числах: три добутки замість чотирьох.
function threeProducts(x: bigint, y: bigint, m: number): bigint {
  const power = 10n ** BigInt(m);
  const a = x / power; // старша половина x
  const b = x % power; // молодша половина x
  const c = y / power;
  const d = y % power;
  const ac = a * c; //                       перший добуток
  const bd = b * d; //                       другий добуток
  const mixed = (a + b) * (c + d); //        третій добуток: ac + ad + bc + bd
  const middle = mixed - ac - bd; //         лишається ad + bc, і множити для цього не довелося
  console.log(`ac=${ac}, bd=${bd}, (a+b)(c+d)=${a + b}·${c + d}=${mixed}, ad+bc=${middle}`);
  return ac * power * power + middle * power + bd;
}
console.log('три добутки:', threeProducts(1234n, 5678n, 2), 'BigInt:', 1234n * 5678n);

// Скільки множень цифр зробить рекурсія, яка ділить число навпіл до однієї цифри.
function leaves(branches: number, n: number): number {
  return n === 1 ? 1 : branches * leaves(branches, n / 2);
}
for (const n of [2, 4, 16, 64, 256, 1024]) {
  const four = leaves(4, n);
  const three = leaves(3, n);
  console.log(`n=${n}: чотири добутки ${four}, три добутки ${three}, різниця у ${(four / three).toFixed(1)} раза`);
}
```

```
ac=672, bd=2652, (a+b)(c+d)=46·134=6164, ad+bc=2840
три добутки: 7006652n BigInt: 7006652n
n=2: чотири добутки 4, три добутки 3, різниця у 1.3 раза
n=4: чотири добутки 16, три добутки 9, різниця у 1.8 раза
n=16: чотири добутки 256, три добутки 81, різниця у 3.2 раза
n=64: чотири добутки 4096, три добутки 729, різниця у 5.6 раза
n=256: чотири добутки 65536, три добутки 6561, різниця у 10.0 раза
n=1024: чотири добутки 1048576, три добутки 59049, різниця у 17.8 раза
```

Що видно у виводі.

**Три добутки дають ту саму відповідь.** Перші два рядки повторюють таблицю вище, і результат збігається зі звичайним
множенням `BigInt`.

**Виграш росте разом з довжиною числа.** Для чисел з 4 цифр три добутки дають 9 множень проти 16, тобто менше ніж
удвічі. Для 1024 цифр це 59 049 проти 1 048 576, майже у 18 разів. Якби новий спосіб був швидшим лише у стале число
разів, різниця не росла б.

**Практичний висновок:** числа останнього рядка — це ті самі числа, які план просить отримати в практиці. Ваш
лічильник у множенні в стовпчик має показати 1 048 576, а в алгоритмі Карацуби, що ділить до однієї цифри, — 59 049.

### Сума половин може бути довшою за половину

У прикладі є деталь, яку легко пропустити. Половини мали по дві цифри, а сума `c + d = 134` має три. Сума двох чисел
по `m` цифр може мати `m + 1` цифру. Тоді третій добуток множить числа, довші за половину, і рекурсія вже не ділить
задачу рівно навпіл. Kleinberg і Tardos кажуть про це прямо: на оцінку часу зайвий розряд не впливає. Але на точне
число у вашому лічильнику він вплине.

Є три способи з цим упоратися, і вибір за вами:

- Дозволити сумам бути на цифру довшими і акуратно обробити цей випадок. Тоді лічильник не мусить дорівнювати рівно
  59 049.
- Множити різниці замість сум. Erickson наводить тотожність `a·c + b·d − (a − b)·(c − d) = a·d + b·c` і пояснює, що
  різниці `a − b` і `c − d` мають не більше `m` цифр. Тоді доведеться стежити за знаком різниці. Erickson пише, що сам
  Карацуба множив суми, а спрощення з різницями належить Дональду Кнуту.
- Не переносити десятки всередині рекурсії. Тоді в одній позиції масиву тимчасово може стояти число, більше за 9, а
  всі перенесення робляться один раз наприкінці. Довжини половин при цьому не змінюються.

## Чому три замість чотирьох змінює показник степеня

Час алгоритму Карацуби описує рівняння `T(n) = 3T(n/2) + n`. Розв'яжемо його деревом рекурсії для `n = 1024`, як у
фазі 0.

На верхньому рівні одна задача розміру 1024. На наступному три задачі розміру 512. Далі дев'ять задач розміру 256. На
рівні з номером `i` задач 3 у степені `i`, а розмір кожної дорівнює 1024, поділеному на 2 у степені `i`. Робота на
збирання в одній задачі пропорційна її розміру. Тому робота цілого рівня дорівнює добутку кількості задач на їхній
розмір.

| Рівень | Задач | Розмір однієї | Робота рівня |
|--------|-------|---------------|--------------|
| 0 | 1 | 1024 | 1024 |
| 1 | 3 | 512 | 1536 |
| 2 | 9 | 256 | 2304 |
| 3 | 27 | 128 | 3456 |
| … | … | … | … |
| 10 | 59 049 | 1 | 59 049 |

Кожен наступний рівень коштує у півтора раза більше за попередній, бо задач стає втричі більше, а кожна вдвічі менша.
Коли кожен рівень у стале число разів дорожчий за попередній, майже вся робота зосереджена на останньому. Сума всіх
рівнів над останнім тут дорівнює 116 050, а останній рівень коштує 59 049. Разом це менше, ніж потроєна робота
останнього рівня. Отже, час алгоритму пропорційний кількості задач на дні.

Задач на дні 3 у степені `log₂ n`. Це число можна записати інакше: `n` у степені `log₂ 3`. Обидва записи дають для `n
= 1024` те саме число 59 049. Оскільки `log₂ 3 ≈ 1,585`, час алгоритму Карацуби становить `Θ(n^1,585)`.

Тепер порівняймо три рівняння, які відрізняються лише кількістю рекурсивних викликів.

| Рівняння | Робота наступного рівня | Розв'язок | Де трапляється |
|----------|-------------------------|-----------|----------------|
| `T(n) = 2T(n/2) + n` | та сама | `n log n` | сортування злиттям |
| `T(n) = 3T(n/2) + n` | у 1,5 раза більша | `n^1,585` | алгоритм Карацуби |
| `T(n) = 4T(n/2) + n` | удвічі більша | `n²` | поділ на чотири добутки |

Кількість викликів стоїть у показнику степеня: розв'язком є `n` у степені `log₂ a`, де `a` — кількість викликів. Тому
один зекономлений виклик змінює не стале число перед формулою, а саму швидкість зростання. Головна теорема з дня 6
фази 0 каже те саме: вона порівнює роботу на збирання `n` з числом `n` у степені `log₂ a`, і коли друге більше,
перемагає воно.

Ще один спосіб відчути різницю. Якщо подвоїти довжину чисел, множення в стовпчик стане дорожчим у 4 рази, а алгоритм
Карацуби — у 3 рази.

## Та сама ідея для матриць: алгоритм Штрассена

Ідея «менше рекурсивних викликів ціною додавань» працює не лише для чисел. Найвідоміший другий приклад — множення
матриць.

Матриця — це прямокутна таблиця чисел. Добуток двох квадратних матриць розміру `n` — це теж матриця розміру `n`. Число
в рядку `i` і стовпці `j` добутку отримують так: беруть рядок `i` першої матриці і стовпець `j` другої, перемножують
їх числа попарно і додають. Приклад для розміру 2:

```
| 1 2 |   | 5 6 |   | 1·5 + 2·7   1·6 + 2·8 |   | 19 22 |
| 3 4 | · | 7 8 | = | 3·5 + 4·7   3·6 + 4·8 | = | 43 50 |
```

Тут вісім множень чисел. Для матриць розміру `n` множень `n³`: у відповіді `n²` чисел, і на кожне йде `n` множень.

Якщо поділити кожну матрицю на чотири чверті, добуток виражається через вісім добутків чвертей за тією самою формулою,
що й у прикладі 2 на 2. Рівняння `T(n) = 8T(n/2) + n²` дає `n³`, тобто нічого не змінюється. Це та сама історія, що з
чотирма добутками половин числа.

CLRS розповідає, що багато математиків вважали швидше множення матриць неможливим, доки 1969 року Фолькер Штрассен не
опублікував спосіб обійтися сімома добутками чвертей замість восьми. Сім добутків складаються із сум і різниць
чвертей. Перевіримо формули з CLRS на прикладі вище, де чверті — це окремі числа: `a11 = 1`, `a12 = 2`, `a21 = 3`,
`a22 = 4`, `b11 = 5`, `b12 = 6`, `b21 = 7`, `b22 = 8`.

| Добуток | Формула | Значення |
|---------|---------|----------|
| `p1` | `a11 · (b12 − b22)` = 1 · (−2) | −2 |
| `p2` | `(a11 + a12) · b22` = 3 · 8 | 24 |
| `p3` | `(a21 + a22) · b11` = 7 · 5 | 35 |
| `p4` | `a22 · (b21 − b11)` = 4 · 2 | 8 |
| `p5` | `(a11 + a22) · (b11 + b22)` = 5 · 13 | 65 |
| `p6` | `(a12 − a22) · (b21 + b22)` = (−2) · 15 | −30 |
| `p7` | `(a11 − a21) · (b11 + b12)` = (−2) · 11 | −22 |

Відповідь складається із самих додавань і віднімань:

- верхнє ліве число: `p5 + p4 − p2 + p6` = 65 + 8 − 24 − 30 = 19;
- верхнє праве: `p1 + p2` = −2 + 24 = 22;
- нижнє ліве: `p3 + p4` = 35 + 8 = 43;
- нижнє праве: `p5 + p1 − p3 − p7` = 65 − 2 − 35 + 22 = 50.

Вийшла та сама матриця, і множень було сім. Рівняння `T(n) = 7T(n/2) + n²` дає `n` у степені `log₂ 7`, тобто приблизно
`n^2,81`. CLRS описує суть так: дерево рекурсії стає менш гіллястим, і це окупає додаткові додавання.

Наступна програма множить випадкові матриці двома способами і рахує множення чисел. У функції `strassen` є параметр
`cutoff`. Коли матриця стає не більшою за це число, функція припиняє рекурсію і множить за означенням.

```ts
type Matrix = number[][];

let scalarMultiplications = 0; // скільки разів програма перемножила два числа з матриць

// Множення за означенням: три вкладені цикли, n · n · n множень чисел.
function multiplyDirect(a: Matrix, b: Matrix): Matrix {
  const n = a.length;
  const c: Matrix = Array.from({ length: n }, () => new Array<number>(n).fill(0));
  for (let i = 0; i < n; i += 1) {
    for (let k = 0; k < n; k += 1) {
      const aik = a[i][k];
      for (let j = 0; j < n; j += 1) {
        c[i][j] += aik * b[k][j];
      }
    }
  }
  scalarMultiplications += n * n * n;
  return c;
}

// Сума або різниця двох матриць однакового розміру: sign дорівнює 1 або -1.
function combine(a: Matrix, b: Matrix, sign: number): Matrix {
  return a.map((row, i) => row.map((value, j) => value + sign * b[i][j]));
}

// Чверть матриці: квадрат розміру h, верхній лівий кут якого стоїть у рядку row і стовпці col.
function quarter(a: Matrix, row: number, col: number, h: number): Matrix {
  return a.slice(row, row + h).map((line) => line.slice(col, col + h));
}

// Алгоритм Штрассена. Розмір n є степенем двійки.
// Коли матриця не більша за cutoff, функція множить її за означенням.
function strassen(a: Matrix, b: Matrix, cutoff: number): Matrix {
  const n = a.length;
  if (n <= cutoff) {
    return multiplyDirect(a, b);
  }
  const h = n / 2;
  const a11 = quarter(a, 0, 0, h);
  const a12 = quarter(a, 0, h, h);
  const a21 = quarter(a, h, 0, h);
  const a22 = quarter(a, h, h, h);
  const b11 = quarter(b, 0, 0, h);
  const b12 = quarter(b, 0, h, h);
  const b21 = quarter(b, h, 0, h);
  const b22 = quarter(b, h, h, h);
  // Сім добутків матриць половинного розміру замість восьми. Формули взято з CLRS, розділ 4.2.
  const p1 = strassen(a11, combine(b12, b22, -1), cutoff);
  const p2 = strassen(combine(a11, a12, 1), b22, cutoff);
  const p3 = strassen(combine(a21, a22, 1), b11, cutoff);
  const p4 = strassen(a22, combine(b21, b11, -1), cutoff);
  const p5 = strassen(combine(a11, a22, 1), combine(b11, b22, 1), cutoff);
  const p6 = strassen(combine(a12, a22, -1), combine(b21, b22, 1), cutoff);
  const p7 = strassen(combine(a11, a21, -1), combine(b11, b12, 1), cutoff);
  // Чотири чверті відповіді складаються із семи добутків самими додаваннями і відніманнями.
  const c11 = combine(combine(combine(p5, p4, 1), p2, -1), p6, 1);
  const c12 = combine(p1, p2, 1);
  const c21 = combine(p3, p4, 1);
  const c22 = combine(combine(combine(p5, p1, 1), p3, -1), p7, -1);
  const top = c11.map((row, i) => [...row, ...c12[i]]);
  const bottom = c21.map((row, i) => [...row, ...c22[i]]);
  return [...top, ...bottom];
}

let state = 2026;
function random(): number {
  state = (state + 0x6d2b79f5) | 0;
  let t = Math.imul(state ^ (state >>> 15), 1 | state);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}
function randomMatrix(n: number): Matrix {
  return Array.from({ length: n }, () => Array.from({ length: n }, () => Math.floor(random() * 10)));
}
function same(a: Matrix, b: Matrix): boolean {
  return a.every((row, i) => row.every((value, j) => value === b[i][j]));
}

function measure(n: number, cutoffs: number[]): void {
  const a = randomMatrix(n);
  const b = randomMatrix(n);
  scalarMultiplications = 0;
  let start = performance.now();
  const expected = multiplyDirect(a, b);
  let ms = performance.now() - start;
  console.log(`n=${n}, за означенням: множень ${scalarMultiplications}, ${ms.toFixed(0)} мс`);
  for (const cutoff of cutoffs) {
    scalarMultiplications = 0;
    start = performance.now();
    const product = strassen(a, b, cutoff);
    ms = performance.now() - start;
    console.log(
      `n=${n}, Штрассен, поріг ${cutoff}: множень ${scalarMultiplications}, ${ms.toFixed(0)} мс, ` +
        `відповідь та сама: ${same(product, expected)}`,
    );
  }
}

measure(256, [1, 4, 16, 64]);
measure(512, [32, 128]);
```

**Відповіді однакові.** Усі варіанти алгоритму Штрассена дали ту саму матрицю, що й множення за означенням.

**З порогом 1 множень утричі менше.** Рекурсія до матриць 1 на 1 зробила 5 764 801 множення. Це 7 у восьмому степені,
бо матрицю розміру 256 можна поділити навпіл вісім разів. Множення за означенням зробило 16 777 216, тобто у 2,9 раза
більше.

**З порогом 1 програма у 138 разів повільніша.** Вона працювала 6368 мс проти 46 мс. Менша кількість множень не дала
меншого часу. Про причину йдеться в наступному розділі.

**Що вищий поріг, то більше множень і менше часу.** З порогом 64 множень 12 845 056, а час 53 мс. Для матриць розміру
512 з порогом 128 алгоритм Штрассена лише зрівнявся з множенням за означенням: 356 мс проти 363 мс.

**Практичний висновок:** числа часу на вашій машині будуть іншими, а кількості множень збіжаться до одиниці. У цій
простій реалізації мовою TypeScript алгоритм Штрассена на матрицях до 512 не дає помітного виграшу в часі. Його
перевага в показнику степеня починає працювати лише на великих розмірах і лише разом з порогом.

## Пастка: ділити до самого дна

Кількість множень чесно показує, як росте час на великих входах. Але вона мовчить про ціну всього іншого. Подивіться,
що робить функція `strassen` на кожному рівні, крім семи рекурсивних викликів:

- вирізає вісім чвертей, і кожна чверть є новим масивом;
- обчислює десять сум і різниць чвертей, і кожна теж є новим масивом;
- складає відповідь ще вісьмома додаваннями і відніманнями;
- склеює чотири чверті відповіді в одну матрицю.

CLRS підсумовує те саме числами: 7 множень чвертей і 18 додавань чвертей на кожному рівні. Для великої матриці ця
робота мала поруч із множенням. Для матриці 2 на 2 усе навпаки: замість восьми множень чисел програма створює десятки
маленьких масивів і робить сім викликів функції. Вимір показує, що ця додаткова робота коштує набагато більше за
множення, які вона замінює.

З порогом 1 саме на таких крихітних матрицях проходить майже вся робота, бо їх найбільше: на дні рекурсії лежить
5 764 801 задача. Тому програма виходить у 138 разів повільнішою.

Вихід — зупиняти рекурсію раніше. Коли задача стає меншою за певний розмір, алгоритм перемикається на простий спосіб:
для матриць на множення за означенням, для чисел на множення в стовпчик. Цей розмір називають порогом. Поріг не змінює
показника степеня, бо він є сталим числом, але сильно змінює справжній час.

З алгоритмом Карацуби те саме. Якщо ділити числа до однієї цифри, лічильник покаже гарне число 59 049, а час вийде
гіршим, ніж у множення в стовпчик: так було і в перевірці, зробленій для цієї лекції. Де саме лежить поріг, залежить
від мови, машини і способу запису чисел. Його не вгадують, а вимірюють. Це останній пункт сьогоднішньої практики.

## Що було після Карацуби

Erickson коротко розповідає продовження. Число можна ділити не на дві частини, а на `k` частин, і тоді вистачає `2k −
1` добутків замість `k²`. Такі алгоритми придумав Андрій Тоом, а спростив Стівен Кук. Арнольд Шенгаґе і Фолькер
Штрассен у 1971 році опублікували алгоритм на основі швидкого перетворення Фур'є з часом `O(n log n log log n)`. У
2019 році Девід Гарві і Йоріс ван дер Гувен опублікували алгоритм з часом `O(n log n)`.

Erickson додає до цього застереження, яке повторює пастку дня. Алгоритм Шенгаґе і Штрассена стає найшвидшим на
практиці для чисел, довших приблизно за 75 000 цифр. Найновіші алгоритми були б швидшими на практиці лише для чисел, у
яких цифр більше, ніж частинок у Всесвіті.

## Як упізнати задачу на цей прийом

З цієї фази ви ведете файл `PATTERNS.md`. Сьогодні в ньому з'являється перший запис. Ось ознаки, які варто туди
перенести своїми словами.

- **Задача ділиться на менші задачі того самого виду.** Половина масиву є масивом, половина числа є числом, чверть
  матриці є матрицею.
- **Менші задачі незалежні.** Відповідь для лівої половини не потрібна, щоб порахувати праву. Якщо менші задачі
  перетинаються і повторюються, це вже інший прийом, динамічне програмування, і до нього ви дійдете в день 4.
- **Відповіді легко зібрати.** Збирання має коштувати менше, ніж розв'язання цілої задачі напряму.
- **Простий розв'язок уже поліноміальний, а хочеться швидше.** Розділяй і володарюй зазвичай знижує `n²` до `n log n`
  або зменшує показник степеня.

Порядок роботи завжди однаковий. Спершу запишіть рівняння: скільки менших задач, якого вони розміру і скільки коштує
збирання. Потім розв'яжіть його деревом рекурсії або головною теоремою. Лише після цього пишіть код. Якщо рівняння дає
той самий час, що й простий розв'язок, шукайте, як зменшити кількість менших задач або здешевити збирання.

Приклади, які ви вже знаєте: сортування злиттям, швидке сортування і вибір `k`-го елемента з фази 1. Конспект MIT
6.046J розбирає цим прийомом ще дві задачі: опуклу оболонку точок і пошук медіани.

## Типові помилки

**Вважати, що поділ сам собою пришвидшує.** Чотири добутки половин дають рівно `n²` множень цифр. Виграш дає лише
менша кількість рекурсивних викликів або дешевше збирання.

**Забути, що сума половин може бути довшою за половину.** У прикладі лекції 56 + 78 = 134. Код, який чекає на рівно
`m` цифр, може загубити старшу цифру і дати неправильний добуток без жодної помилки під час запуску.

**Переплутати зсуви.** Добуток старших половин зсувають на `2m` позицій, а середній доданок на `m`, де `m` — довжина
молодшої половини. Коли довжина числа непарна, `2m` не дорівнює `n`.

**Ділити до однієї цифри в робочому коді.** Це пастка дня. Така версія годиться, щоб перевірити лічильник, але працює
повільніше за множення в стовпчик.

**Судити про швидкість лише за кількістю множень.** Алгоритм Штрассена з порогом 1 зробив утричі менше множень і
працював у 138 разів довше.

**Перевіряти відповідь через тип `number`.** Число з 1024 цифр у нього не вміщується. Для перевірки потрібен `BigInt`.
Документація MDN попереджає, що `BigInt` і `number` не можна змішувати в одній операції: вираз `2n / 2` кидає
`TypeError`.

**Тестувати лише на числах, довжина яких є степенем двійки.** Алгоритм, який мовчки вважає довжину парною, зламається
на числі з 1000 цифр.

## Практика

Працюйте в проєкті `algo-lab`. Лекція показала поділ на чотири добутки для масивів цифр і один крок ідеї Карацуби на
готових числах. Множення в стовпчик і сам алгоритм Карацуби для масивів цифр ви пишете самі.

**1. Множення в стовпчик.** Функція отримує два числа, записані масивами цифр, і повертає їхній добуток у тому самому
записі. Лічильник рахує множення цифр.

**2. Алгоритм Карацуби.** Функція ділить числа навпіл до однієї цифри і робить три рекурсивні виклики. Лічильник той
самий. Спершу вирішіть, як ви впораєтеся із сумою половин, довшою за половину: три способи описано в лекції.

**3. Прогноз і запуск.** Перемножте два випадкові числа по 1024 цифри обома способами. До запуску запишіть, які два
числа покажуть лічильники. Перевірте обидві відповіді через `BigInt`.

**4. Тести.** Добуток 1234 · 5678 дорівнює 7 006 652. Множення на нуль дає нуль. Число з самих дев'яток, помножене на
себе, перевіряє перенесення. Сто випадкових пар чисел різної довжини збігаються з `BigInt`.

**5. Поріг.** Додайте в алгоритм Карацуби параметр порогу: нижче нього функція множить у стовпчик. Виміряйте час для
порогів 1, 2, 4, 8, 16, 32, 64 і 128 на числах з 1024 цифр і порівняйте з множенням у стовпчик. Кожен вимір повторіть
кілька разів і беріть найменший час. До запуску запишіть, який поріг, на вашу думку, виявиться найкращим.

**6. Записи.** Один рядок у `JOURNAL.md`, таблиця часу з пункту 5 у `MEASUREMENTS.md` і перший запис у `PATTERNS.md`:
ознаки задачі на «розділяй і володарюй», порядок роботи і приклади, які ви знаєте.

**Як перевірити себе.** У стовпчик виходить 1 048 576 множень цифр. Алгоритм Карацуби, що ділить до однієї цифри,
робить 59 049, тобто 3 у десятому степені. Обидві відповіді збігаються з `BigInt`. Версія з порогом 1 повільніша за
множення в стовпчик, а з вдало підібраним порогом швидша.

## Перевірте себе

**1. Алгоритм ділить задачу розміру `n` на чотири задачі розміру `n/2` і збирає відповідь за `n` кроків. Чому він не
швидший за `n²`?**

<details><summary>Відповідь</summary>

Його час описує рівняння `T(n) = 4T(n/2) + n`. На кожному рівні задач стає вчетверо більше, а кожна вдвічі менша, тому
робота рівня подвоюється. Майже вся робота лежить на дні, де задач 4 у степені `log₂ n`, тобто `n²`. Для множення
чисел це означає, що кожна цифра одного числа все одно множиться на кожну цифру другого.

</details>

**2. Перемножте 23 і 41 способом Карацуби, поділивши кожне число на дві цифри.**

<details><summary>Відповідь</summary>

Половини: `a = 2`, `b = 3`, `c = 4`, `d = 1`. Перший добуток `a·c = 8`. Другий добуток `b·d = 3`. Третій добуток `(a +
b)·(c + d) = 5 · 5 = 25`. Середній доданок: 25 − 8 − 3 = 14. Відповідь: 8 · 100 + 14 · 10 + 3 = 943. Перевірка: 23 ·
41 = 943.

</details>

**3. Скільки множень цифр зробить алгоритм Карацуби, що ділить до однієї цифри, на числах з 4096 цифр? У скільки разів
це менше, ніж у стовпчик?**

<details><summary>Відповідь</summary>

Число 4096 дорівнює 2 у дванадцятому степені, тому поділів навпіл дванадцять. На дні лежить 3 у дванадцятому степені
задач, тобто 531 441 множення цифр. У стовпчик виходить 4096 · 4096 = 16 777 216. Різниця приблизно у 31,6 раза. Для
1024 цифр різниця була у 17,8 раза: виграш росте з довжиною.

</details>

**4. Число ділять на три частини, і вистачає п'яти добутків третин. Запишіть рівняння і розв'язок.**

<details><summary>Відповідь</summary>

Рівняння `T(n) = 5T(n/3) + n`. Задач на кожному рівні стає вп'ятеро більше, а кожна втричі менша, тому робота рівня
росте у 5/3 раза і перемагає дно. На дні лежить 5 у степені `log₃ n` задач, тобто `n` у степені `log₃ 5`, приблизно
`n^1,465`. Це краще за `n^1,585` в алгоритмі Карацуби. Це алгоритм з родини Тоома і Кука, про яку згадує Erickson: `k`
частин і `2k − 1` добутків, тут `k = 3`.

</details>

**5. Алгоритм Штрассена з порогом 1 зробив у 2,9 раза менше множень, ніж множення за означенням, але працював у 138
разів довше. Чому?**

<details><summary>Відповідь</summary>

Лічильник рахує лише множення чисел. Крім них, на кожному рівні функція вирізає вісім чвертей, робить десять додавань
для співмножників і ще вісім для відповіді, і все це створює нові масиви. На матрицях 2 на 2 ця робота набагато
дорожча за вісім множень чисел, які вона замінює. З порогом 1 саме таких крихітних задач найбільше, тому вони й
визначають час.

</details>

**6. Ваші числа мають по 1000 цифр, а алгоритм написано для довжини, яка є степенем двійки. Що можна зробити?**

<details><summary>Відповідь</summary>

Є два шляхи. Перший: доповнити обидва числа нулями зі старшого боку до 1024 цифр. Добуток від цього не зміниться, а
зайва робота невелика. Другий: ділити число на нерівні частини. Erickson у своєму записі алгоритму бере за довжину
молодшої половини `n/2`, заокруглене вгору, і тоді довжина може бути будь-якою. У цьому разі зсуви роблять на `m` і на
`2m` позицій, де `m` — довжина молодшої половини.

</details>

|-------|------------|
| розділяй і володарюй | прийом: поділити задачу на менші того самого виду, розв'язати їх рекурсивно, зібрати відповідь |

| алгоритм Штрассена | множення матриць сімома добутками чвертей замість восьми |
