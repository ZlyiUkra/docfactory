# Лекція. Фаза 4, день 3. Коди Хаффмана

У 1951 році Девід Хаффман був аспірантом у MIT і слухав курс Роберта Фано. Фано дав студентам задачу: як записати
текст нулями й одиницями якомога коротше. Хаффман узявся розв'язати її замість іспиту. Він не знав, що задача
відкрита: Фано і Клод Шеннон самі пробували її розв'язати і не змогли. Після кількох місяців марних спроб Хаффман
здався, вирішив таки складати іспит і вже викидав чернетки у смітник, коли розв'язок раптом склався. Цю історію
розповідає книжка Erickson. Розв'язок Хаффмана вміщується в одне речення, а його доказ повторює аргумент обміну з
учорашнього дня. Сьогодні ви розберете і сам алгоритм, і причину, чому він дає найкращий можливий код. Читання займе
близько 45 хвилин. Під кожним прикладом коду стоїть справжній вивід з Node 24.22.

**Після лекції ви зможете пояснити:**

- чому текст можна записати коротше, ніж по 8 бітів на символ;
- що таке код без префіксів і навіщо він потрібен;
- чому код без префіксів — це двійкове дерево;
- як алгоритм Хаффмана будує дерево знизу вгору;
- чому спроба будувати дерево згори вниз не дає найкращого коду;
- як аргумент обміну доводить, що код Хаффмана найкращий.

## Скільки бітів займає текст

Комп'ютер зберігає текст нулями й одиницями. Одну таку цифру називають бітом. Книжка Grokking Algorithms показує це на
файлі з одним словом `tilt`: файл займає 4 байти, по одному байту на літеру, а байт — це 8 бітів. Разом 32 біти. У
кодуванні, яке бере книжка, кожна літера має код рівно з 8 бітів, і таких кодів 256.

Але слову `tilt` не потрібні 256 різних літер. У ньому лише три: `t`, `i` та `l`. Щоб розрізнити три літери, досить
двох бітів на кожну: `t = 00`, `i = 01`, `l = 10`. Тоді слово займе 8 бітів замість 32.

Можна ще коротше. Літера `t` трапляється у слові двічі, а інші по одному разу. Дамо їй код з одного біта: `t = 1`, `i
= 00`, `l = 01`. Слово запишеться як `1 00 01 1`, і це 6 бітів.

У цьому вся ідея стиснення, яку реалізує код Хаффмана: частим символам дати короткі коди, а рідкісним довгі. Код, у
якому всі символи мають однакову довжину, називають кодом сталої довжини. Код, у якому довжини різні, називають кодом
змінної довжини.

## Код без префіксів

Код змінної довжини має небезпеку, якої не має код сталої довжини. Коли всі коди мають по 8 бітів, рядок бітів просто
ріжуть на шматки по 8. Коли довжини різні, незрозуміло, де закінчується один код і починається наступний.

Kleinberg і Tardos показують це на азбуці Морзе. Морзе дав частим літерам короткі коди: `e` — це крапка, `t` — тире,
`a` — крапка і тире. Запишемо крапку нулем, а тире одиницею: `e = 0`, `t = 1`, `a = 01`. Тоді рядок `0101` можна
прочитати як `eta`, як `aa`, як `etet` і як `aet`. Телеграфісти розв'язували цю проблему паузами між літерами. Але
пауза — це третій знак, а в нас є лише нулі й одиниці.

Причина плутанини в тому, що код літери `e` є початком коду літери `a`. Початок рядка називають префіксом. Якщо жоден
код не є префіксом іншого, плутанини не буде: читаючи біти зліва направо, ми впізнаємо код символу в ту саму мить,
коли він закінчився, бо довшого коду з таким початком немає. Такий код називають кодом без префіксів. Erickson
попереджає про плутанину в назвах: англійською його називають і prefix-free code, і просто prefix code.

Наступна програма перевіряє, чи є код кодом без префіксів, і рахує, скількома способами можна прочитати рядок бітів.
Самого розшифрування тут немає: його ви напишете в практиці.

```ts
// Код — це таблиця: кожному символу відповідає рядок з нулів та одиниць.
type Code = Record<string, string>;

// Код без префіксів: жоден код символу не є початком коду іншого символу.
function isPrefixFree(code: Code): boolean {
  const words = Object.values(code);
  return words.every((word, i) => words.every((other, j) => i === j || !other.startsWith(word)));
}

// Скількома способами рядок бітів можна розрізати на коди символів.
// Функція пробує кожен код як початок рядка і рахує способи розрізати решту.
function countReadings(code: Code, bits: string): number {
  if (bits === '') {
    return 1; // рядок розрізано до кінця: знайдено один спосіб
  }
  let count = 0;
  for (const word of Object.values(code)) {
    if (bits.startsWith(word)) {
      count += countReadings(code, bits.slice(word.length));
    }
  }
  return count;
}

// Закодувати текст: записати коди його символів один за одним.
const encode = (code: Code, text: string): string => [...text].map((symbol) => code[symbol]).join('');

// Скільки бітів займе текст, у якому кожен символ трапляється задану кількість разів.
function totalBits(code: Code, counts: Record<string, number>): number {
  return Object.keys(counts).reduce((sum, symbol) => sum + counts[symbol] * code[symbol].length, 0);
}

const morse: Code = { e: '0', t: '1', a: '01' }; //                             три літери з азбуки Морзе
const fixed: Code = { a: '000', b: '001', c: '010', d: '011', e: '100' }; //    усі коди однакової довжини
const first: Code = { a: '11', b: '01', c: '001', d: '10', e: '000' }; //       код γ1 з книжки Kleinberg і Tardos
const second: Code = { a: '11', b: '10', c: '01', d: '001', e: '000' }; //      код γ2 звідти ж

console.log('Морзе: без префіксів', isPrefixFree(morse), '| способів прочитати 0101:', countReadings(morse, '0101'));

const message = encode(first, 'cecab');
console.log('cecab кодом γ1:', message);
console.log('γ1: без префіксів', isPrefixFree(first), '| способів прочитати:', countReadings(first, message));

// На кожні 100 символів тексту: a трапляється 32 рази, b 25, c 20, d 18, e 5.
const counts = { a: 32, b: 25, c: 20, d: 18, e: 5 };
for (const [name, code] of [['3 біти на символ', fixed], ['γ1', first], ['γ2', second]] as [string, Code][]) {
  console.log(`${name}: ${totalBits(code, counts)} бітів на 100 символів, без префіксів ${isPrefixFree(code)}`);
}
```

γ1: без префіксів true | способів прочитати: 1

Що видно у виводі.

**Три літери Морзе не є кодом без префіксів, і рядок `0101` читається чотирма способами.** Це ті самі чотири
прочитання, які називають Kleinberg і Tardos.

**Код γ1 є кодом без префіксів, і закодоване слово читається рівно одним способом.** Рядок `0010000011101` збігається
з тим, що наведено в книжці.

**Код сталої довжини теж є кодом без префіксів.** Коди однакової довжини не можуть бути початком один одного.

**Три коди дають різну довжину тексту.** Якщо на кожні 100 символів літера `a` трапляється 32 рази, `b` 25, `c` 20,
`d` 18 та `e` 5, то код по 3 біти на символ дає 300 бітів, код γ1 дає 225, а код γ2 дає 223.

**Практичний висновок:** серед кодів без префіксів є кращі й гірші, і різниця залежить від того, наскільки довжини
кодів узгоджені з частотами символів. Задача дня: для заданих частот знайти код без префіксів, який дає найменшу
загальну кількість бітів. Такий код називають оптимальним.

## Код без префіксів — це дерево

Код без префіксів зручно малювати двійковим деревом. Символи лежать у листках. Щоб дізнатися код символу, йдуть від
кореня до його листка і записують 0 за кожен крок ліворуч та 1 за кожен крок праворуч.

Ось дерево для коду `t = 1`, `i = 00`, `l = 01` зі слова `tilt`:

```
        корінь
       0/    \1
      вузол    t
    0/    \1
    i      l
```

З малюнка видно три речі.

**Чому префіксів немає.** Код одного символу був би початком коду іншого лише тоді, коли б перший символ лежав на
шляху від кореня до другого. Але символи лежать тільки в листках, а шлях до листка не проходить через інші листки.

**Що таке довжина коду.** Довжина коду символу дорівнює глибині його листка, тобто кількості кроків від кореня.

**Як розшифровувати.** Починаємо в корені й читаємо біти по одному: 0 веде ліворуч, 1 праворуч. Дійшовши до листка,
записуємо його символ і повертаємося в корінь.

Тепер задачу можна сказати точно. Кожен символ має частоту: скільки разів він трапляється в тексті. Загальна кількість
бітів дорівнює сумі добутків «частота символу на глибину його листка» за всіма символами. Цю суму називають вартістю
дерева. Треба знайти дерево з найменшою вартістю.

Erickson і CLRS окремо зауважують, що це дерево не є деревом пошуку з фази 2: порядок символів у листках не має
жодного значення.

Одна властивість оптимального дерева очевидна одразу. У ньому немає вузла з однією дитиною. Якби такий вузол був, його
можна було б викинути і підняти дитину на його місце: усі коди під ним стали б на біт коротшими. Дерево, де кожен
вузол, крім листків, має рівно двох дітей, називають повним.

## Перша спроба: ділити згори вниз

Як побудувати дерево з малою вартістю? Перша думка — будувати від кореня. Частим символам потрібні листки ближче до
кореня. Тож поділимо всі символи на дві групи з приблизно однаковими сумами частот. Перша група піде в ліве піддерево,
друга в праве, і кожну групу поділимо далі так само.

Саме так робили Шеннон і Фано, і коди, побудовані таким способом, називають кодами Шеннона і Фано. Kleinberg і Tardos
пишуть, що обидва знали про недолік цього способу, але не бачили, як знайти найкращий код без повного перебору.

Наступна програма будує код поділом згори вниз для прикладу з попереднього розділу. Поруч вона рахує вартість способу,
який придумав Хаффман. Його суть описано в наступному розділі, а тут потрібне лише число для порівняння.

```ts
type Code = Record<string, string>;
type Counts = Record<string, number>;

const sum = (symbols: string[], counts: Counts): number => symbols.reduce((total, s) => total + counts[s], 0);

// Спроба згори вниз. Символи ділимо на дві групи з якомога ближчими сумами частот.
// Перша група отримує біт 0, друга біт 1, і кожну групу ділимо далі так само.
function splitFromTop(symbols: string[], counts: Counts, prefix = '', code: Code = {}): Code {
  if (symbols.length === 1) {
    code[symbols[0]] = prefix;
    return code;
  }
  const total = sum(symbols, counts);
  let bestLeft: string[] = [];
  let bestGap = Infinity;
  // Перебираємо всі способи вибрати першу групу. Номер mask задає групу своїми бітами.
  // Останній символ завжди лишається в другій групі, тому обидві групи непорожні.
  for (let mask = 1; mask < 1 << (symbols.length - 1); mask += 1) {
    const left = symbols.filter((_, i) => (mask >> i) & 1);
    const gap = Math.abs(total - 2 * sum(left, counts)); // різниця між сумами двох груп
    if (gap < bestGap) {
      bestGap = gap;
      bestLeft = left;
    }
  }
  const right = symbols.filter((s) => !bestLeft.includes(s));
  splitFromTop(bestLeft, counts, `${prefix}0`, code);
  splitFromTop(right, counts, `${prefix}1`, code);
  return code;
}

function totalBits(code: Code, counts: Counts): number {
  return Object.keys(counts).reduce((total, symbol) => total + counts[symbol] * code[symbol].length, 0);
}

// Вартість злиття знизу: щоразу беремо дві найменші частоти, додаємо їх
// і кладемо суму назад. Сума всіх таких додавань дорівнює кількості бітів у коді Хаффмана.
// Дерева й таблиці кодів ця функція не будує: вона рахує лише число.
function mergeCost(counts: Counts, log = false): number {
  const queue = Object.values(counts);
  let cost = 0;
  while (queue.length > 1) {
    queue.sort((a, b) => a - b);
    const x = queue.shift() as number;
    const y = queue.shift() as number;
    if (log) {
      console.log(`  зливаємо ${x} і ${y} у ${x + y}`);
    }
    cost += x + y;
    queue.push(x + y);
  }
  return cost;
}

const example: Counts = { a: 32, b: 25, c: 20, d: 18, e: 5 };
const fromTop = splitFromTop(Object.keys(example), example);
console.log('поділ згори:', fromTop, '→', totalBits(fromTop, example), 'бітів на 100 символів');
console.log('злиття знизу:');
console.log('  разом', mergeCost(example, true), 'бітів на 100 символів');

// Генератор mulberry32: з одного початкового числа щоразу виходить та сама послідовність.
let state = 2026;
function random(): number {
  state = (state + 0x6d2b79f5) | 0;
  let t = Math.imul(state ^ (state >>> 15), 1 | state);
  t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
}

// 2000 випадкових алфавітів: від 3 до 8 символів, частоти від 1 до 50.
let worse = 0;
let better = 0;
let largestLoss = 0;
for (let test = 0; test < 2000; test += 1) {
  const size = 3 + Math.floor(random() * 6);
  const counts: Counts = {};
  for (let i = 0; i < size; i += 1) {
    counts[String.fromCharCode(97 + i)] = 1 + Math.floor(random() * 50);
  }
  const top = totalBits(splitFromTop(Object.keys(counts), counts), counts);
  const bottom = mergeCost(counts);
  if (top > bottom) {
    worse += 1;
    largestLoss = Math.max(largestLoss, (top - bottom) / bottom);
  }
  if (top < bottom) {
    better += 1;
  }
}
console.log(`поділ згори гірший у ${worse} випадках із 2000, кращий у ${better}`);
console.log(`найбільший програш: ${(largestLoss * 100).toFixed(1)} відсотка`);
```

злиття знизу:
  зливаємо 5 і 18 у 23
  зливаємо 20 і 23 у 43
  зливаємо 25 і 32 у 57
  зливаємо 43 і 57 у 100

Що видно у виводі.

**Поділ згори дав 225 бітів.** Програма знайшла ідеальний поділ навпіл: `a` та `d` разом мають 50, і решта три символи
теж 50. Далі `b` має 25, а `c` та `e` разом 25. Кожен поділ ідеально рівний, а код вийшов не найкращим. Це той самий
код γ1 з книжки Kleinberg і Tardos.

**Злиття знизу дало 223 біти.** Це вартість коду γ2.

**На випадкових алфавітах поділ згори програв у 1054 випадках із 2000 і не виграв жодного разу.** Найбільший програш
становив 23,9 відсотка.

**Практичний висновок:** це вчорашня пастка в чистому вигляді. Правило «діли навпіл якомога рівніше» звучить розумно,
і над ним працювали засновники теорії інформації. Воно правильне майже в половині випадків і неправильне в решті.
Порівняння на випадкових входах показує це за секунду.

Чому поділ згори помиляється? Він починає з найважливішого рішення, з поділу біля кореня, і приймає його, майже нічого
не знаючи про те, що вийде внизу. У прикладі ідеально рівний поділ посадив символ `d` з частотою 18 на глибину 2,
поруч з `a`, а символ `c` з частотою 20 опинився на глибині 3.

## Алгоритм Хаффмана: будувати знизу вгору

Хаффман розвернув задачу. Замість вирішувати, що буде біля кореня, він спершу вирішує, що буде на самому дні. Erickson
записує алгоритм одним реченням: злити два найрідкісніші символи в один і повторити.

Докладніше це виглядає так.

1. Кожен символ стає окремим деревом з одного листка. Вага дерева дорівнює частоті символу.
2. Беремо два дерева з найменшими вагами.
3. Робимо їх дітьми нового вузла. Вага нового дерева дорівнює сумі двох ваг.
4. Повторюємо кроки 2 і 3, доки не лишиться одне дерево.

Виконаємо алгоритм на прикладі з CLRS. У файлі зі 100 000 символів шість різних літер. Частоти подано в тисячах: `a` —
45, `b` — 13, `c` — 12, `d` — 16, `e` — 9, `f` — 5.

| Крок | Дерева перед кроком, за зростанням ваги | Що зливаємо | Нова вага |
|------|------------------------------------------|-------------|-----------|
| 1 | `f` 5, `e` 9, `c` 12, `b` 13, `d` 16, `a` 45 | `f` та `e` | 14 |
| 2 | `c` 12, `b` 13, дерево 14, `d` 16, `a` 45 | `c` та `b` | 25 |
| 3 | дерево 14, `d` 16, дерево 25, `a` 45 | дерево 14 і `d` | 30 |
| 4 | дерево 25, дерево 30, `a` 45 | дерево 25 і дерево 30 | 55 |
| 5 | `a` 45, дерево 55 | `a` і дерево 55 | 100 |

Шість символів потребують п'яти злиттів. Вийшло таке дерево, і біля кожного вузла написано його вагу:

```
              100
            0/   \1
          a 45    55
               0/    \1
              25      30
            0/  \1  0/  \1
          c 12 b 13 14   d 16
                  0/  \1
                 f 5   e 9
```

Коди читаємо з дерева: `a = 0`, `c = 100`, `b = 101`, `d = 111`, `f = 1100`, `e = 1101`. Найчастіша літера отримала
один біт, дві найрідкісніші по чотири.

Порахуємо вартість: 45 · 1 + 13 · 3 + 12 · 3 + 16 · 3 + 9 · 4 + 5 · 4 = 224. Частоти подано в тисячах, тому файл займе
224 000 бітів. Код сталої довжини потребує 3 бітів на кожну з шести літер, тобто 300 000 бітів. Виграш становить
близько 25 відсотків. CLRS пише, що залежно від даних типовим є виграш від 20 до 90 відсотків.

### Вартість дорівнює сумі злиттів

Складіть нові ваги з правого стовпця таблиці: 14 + 25 + 30 + 55 + 100 = 224. Вийшла та сама вартість. Це не збіг.
Кожне злиття опускає всі символи обох дерев на один рівень глибше, тобто додає кожному з них один біт. Вага нового
дерева — це якраз сума частот усіх символів у ньому. Тому кожне злиття додає до вартості рівно свою нову вагу.

Саме так рахує функція `mergeCost` з програми вище. Вона не будує ні дерева, ні кодів, а лише складає ваги злиттів. Ця
функція знадобиться вам у практиці як незалежна перевірка: кількість бітів вашого закодованого тексту має дорівнювати
числу, яке вона повертає для тих самих частот.

### Скільки це коштує

Алгоритму постійно потрібні два найменші елементи, і він постійно додає нові. Це робота для пріоритетної черги з дня
10 фази 1. Для `n` різних символів алгоритм робить `n − 1` злиття, і кожне злиття — це два діставання найменшого й
одна вставка. З купою кожна така дія коштує `O(log n)`, тому весь алгоритм працює за `O(n log n)`.

Тут `n` — це кількість різних символів, а не довжина тексту. Щоб порахувати частоти, текст треба пройти один раз, і це
коштує часу, пропорційного його довжині.

Функція `mergeCost` з лекції навмисно обходиться без купи і щоразу сортує весь масив. Для кількох символів це не має
значення, але у вашому розв'язку має стояти купа.

### Кодів Хаффмана багато, вартість одна

Коли дві ваги рівні, алгоритм може взяти будь-яку. Крім того, байдуже, яке з двох дерев стане лівою дитиною, а яке
правою. Тому для одного тексту існує багато різних кодів Хаффмана. Erickson підкреслює: коди окремих символів у них
можуть відрізнятися навіть довжиною, але загальна довжина закодованого тексту однакова для всіх.

## Чому алгоритм Хаффмана дає найкращий код

Доказ складається з двох частин, і обидві ви бачили вчора: властивість жадібного вибору й оптимальна підструктура.

### Частина перша: два найрідкісніші символи можна посадити найглибше і поруч

Почнемо з простого спостереження. В оптимальному дереві рідкісний символ не може лежати вище за частий. Якби лежав, їх
можна було б поміняти місцями і зекономити.

Перевіримо на числах. Візьмемо дерево з прикладу і поміняємо місцями `a` з частотою 45 та `f` з частотою 5. Тепер `f`
лежить на глибині 1, а `a` на глибині 4. Вартість: 5 · 1 + 13 · 3 + 12 · 3 + 16 · 3 + 9 · 4 + 45 · 4 = 344. Обмін
назад повертає 224. Різниця дорівнює 120, і це добуток різниці глибин на різницю частот: (4 − 1) · (45 − 5).

Загальне правило таке. Якщо поміняти місцями два листки, вартість зміниться на добуток різниці їхніх глибин на різницю
їхніх частот. Якщо глибший листок при цьому отримує рідкісніший символ, вартість не зростає.

Тепер саме твердження, яке CLRS називає лемою про властивість жадібного вибору, а Erickson доводить так. Візьмемо
будь-яке оптимальне дерево. Воно повне, тому на найбільшій глибині є два листки, які мають спільного батька. Якщо в
цих листках лежать не два найрідкісніші символи, поміняємо: найрідкісніший символ з тим, що лежить у першому листку, а
другий за рідкісністю з тим, що лежить у другому. Обидва обміни опускають рідкісніший символ глибше, тому вартість не
зростає. Дерево було оптимальним, отже, і нове дерево оптимальне.

Висновок: існує оптимальне дерево, у якому два найрідкісніші символи лежать найглибше і мають спільного батька. Саме
такими їх робить перше злиття Хаффмана. Це аргумент обміну за схемою з учорашньої лекції: узяли оптимальний розв'язок
і замінили в ньому вибір на жадібний, нічого не втративши.

### Частина друга: після злиття лишається менша задача того самого виду

Після першого злиття два найрідкісніші символи можна вважати одним новим символом, частота якого дорівнює сумі двох
частот. Лишається та сама задача, але символів на один менше.

Зв'язок між двома задачами точний. Якщо в дереві для меншої задачі замінити листок нового символу на вузол з двома
дітьми, обидва символи опиняться на рівень глибше, ніж був новий символ. Тому вартість зросте рівно на суму їхніх
частот.

Перевіримо на прикладі. Після злиття `f` та `e` маємо п'ять символів: `a` 45, `b` 13, `c` 12, `d` 16 і новий символ з
частотою 14 на глибині 3. Вартість цього меншого дерева: 45 · 1 + 13 · 3 + 12 · 3 + 16 · 3 + 14 · 3 = 210. Вартість
повного дерева дорівнює 210 + 14 = 224.

Різниця між двома вартостями — стале число, яке не залежить від форми дерева. Тому найкраще дерево для меншої задачі
дає найкраще дерево для більшої. А меншу задачу алгоритм розв'язує так само, і так до двох символів, де відповідь
очевидна: одному 0, другому 1. Це індукція за кількістю символів.

Kleinberg і Tardos описують, чим цей жадібний алгоритм незвичний. Зливаючи два символи, алгоритм ще не знає, які коди
вони отримають. Він лише вирішує, що вони матимуть спільного батька, і цього досить, щоб задача стала меншою.

## Пастка: текст з одного різного символу

Що зробить алгоритм з текстом `aaaa`? У ньому один різний символ, тому на початку є одне дерево з одного листка.
Зливати нічого, і алгоритм одразу зупиняється. Корінь дерева — це і є листок. Шлях від кореня до нього має нуль
кроків, тому код символу — порожній рядок.

Закодований текст теж виходить порожнім: нуль бітів. Функція `mergeCost` для такого тексту повертає 0. Розкодувати
порожній рядок назад неможливо, бо з нього не видно, скільки було літер: чотири чи чотири тисячі.

Розв'язок, який не розглядає цей випадок окремо, може повернути порожній текст замість оригіналу або зациклитися в
розкодуванні. Є щонайменше два способи впоратися, і вибір за вами:

- дати єдиному символу код з одного біта, тобто розглянути цей випадок окремо;
- зберігати разом із закодованим текстом кількість символів оригіналу.

Поруч лежить ще один крайній випадок: порожній текст, у якому символів немає взагалі.

## Чого код Хаффмана не вміє

Код Хаффмана оптимальний серед кодів, які дають кожному символу свій незмінний код. Kleinberg і Tardos показують, що
це не означає найкращого стиснення взагалі, на двох прикладах.

**Дуже нерівні частоти.** Чорно-біле зображення з мільйона точок, з яких тисяча чорні, а решта білі. Символів два,
тому кожен отримує код з одного біта, і стиснення немає зовсім, хоча зображення майже порожнє.

**Частоти, які змінюються.** У першій половині тексту трапляються лише `a` та `b`, у другій лише `c` та `d`. Загалом
усі чотири символи однаково часті, тому кожен отримає два біти. А якби посередині можна було змінити код, вистачило б
одного біта на символ.

Є ще практична деталь. Щоб розкодувати текст, одержувач мусить знати дерево або таблицю кодів. Тому їх треба зберегти
разом із закодованим текстом, і вони теж займають місце. Для короткого тексту таблиця може з'їсти весь виграш.

## Що дописати в PATTERNS.md

Нового прийому сьогодні немає: код Хаффмана — це жадібний алгоритм, і він іде третім прикладом у вчорашній запис. Але
він додає до запису дві речі.

- **Жадібний крок може зменшувати задачу, а не вибирати елемент відповіді.** Учора жадібне правило вибирало заявку,
  яка входить у відповідь. Сьогодні воно зливає два елементи в один, і лишається менша задача того самого виду.
- **Ознака пріоритетної черги.** Якщо алгоритм раз у раз потребує найменшого елемента і водночас додає нові, йому
  потрібна купа.

Запишіть туди й застереження: поділ згори вниз, найрівніший на кожному кроці, не дає найкращого коду.

## Типові помилки

**Забути текст з одного різного символу.** Це пастка дня. Тест на рядку `aaaa` знаходить її одразу.

**Рахувати розмір закодованого тексту в символах `0` та `1`.** Якщо зберігати біти рядком із символів `0` та `1`,
кожен такий символ сам займає щонайменше байт. Для підрахунку це зручно, але порівнювати треба кількість бітів, тобто
довжину цього рядка, з кількістю бітів оригіналу.

**Не вирішити, що таке символ.** Літера українського тексту в кодуванні UTF-8 займає два байти, а латинська один. Якщо
ви кодуєте літери, порівняння з «8 бітами на символ» буде нечесним для українського тексту. Якщо ви кодуєте байти,
порівняння точне. Вирішіть це до того, як писати код.

**Порівнювати свою таблицю кодів з таблицею з книжки.** Кодів Хаффмана багато. Порівнювати треба загальну кількість
бітів.

**Сортувати масив заново після кожного злиття.** Так робить функція `mergeCost` у лекції, і це працює, але повільніше
за купу. Практика просить купу.

**Класти в купу лише частоти.** Алгоритму потрібні дерева: з купи має діставатися вузол, у якому є і вага, і діти або
символ.

**Вважати, що рівний поділ згори кращий, бо він «збалансований».** Програма лекції показала: ідеально рівні поділи
дали 225 бітів проти 223.

**Вважати дерево кодів деревом пошуку.** Символи в листках не впорядковані, і шукати символ спуском від кореня в ньому
не можна. Для кодування потрібна окрема таблиця «символ — код».

## Практика

Працюйте в проєкті `algo-lab`. Лекція показала перевірку коду на префікси, поділ згори вниз і підрахунок вартості
злиттів. Дерево Хаффмана, таблицю кодів, кодування і розкодування ви пишете самі.

**1. Функція `huffman(text)`.** Вона рахує частоти символів, будує дерево на вашій купі `MinHeap` з дня 10 фази 1 і
повертає таблицю кодів. Спершу вирішіть, що у вас символ: літера чи байт.

**2. Кодування і розкодування.** Функція кодування перетворює текст на рядок бітів. Функція розкодування отримує біти
та дерево або таблицю і повертає текст.

**3. Справжній текст.** Візьміть текст глави книжки. Закодуйте його, розкодуйте і перевірте, що результат збігається з
оригіналом. До запуску запишіть, скільки бітів на символ ви очікуєте.

**4. Порівняння.** Порахуйте, скільки бітів на символ вийшло, і порівняйте з 8 бітами. Перевірте, що загальна
кількість бітів дорівнює тому, що повертає функція `mergeCost` з лекції для тих самих частот.

**5. Тести.** Слово `tilt` кодується 6 бітами. Текст із частотами прикладу CLRS, де `a` трапляється 45 разів, `b` 13,
`c` 12, `d` 16, `e` 9 та `f` 5, кодується 224 бітами. Текст з одного різного символу розкодовується правильно.
Порожній текст не ламає програму. Сто випадкових коротких текстів після кодування і розкодування збігаються з
оригіналом. Кожна побудована таблиця є кодом без префіксів.

**6. Записи.** Один рядок у `JOURNAL.md`. Відношення кількості бітів до 8 бітів на символ — у `MEASUREMENTS.md`.
Доповнення до запису про жадібні алгоритми — у `PATTERNS.md`.

**Як перевірити себе.** Розкодований текст збігається з оригіналом побайтно. Закодований текст займає помітно менше 8
бітів на символ. Для орієнтиру: у перевірці, зробленій для цієї лекції, англійський текст на 35 тисяч символів дав
4,61 біта на символ.

## Перевірте себе

**1. Код: `a = 1`, `b = 10`, `c = 01`. Знайдіть рядок бітів, який читається двома способами.**

порахуйте кількість бітів.**

<details><summary>Відповідь</summary>

Перше злиття: `c` та `d`, вага 2. Друге: це дерево і `b`, вага 4. Третє: дерево з вагою 4 та `a`, вага 9. Літера `a`
лежить на глибині 1, `b` на глибині 2, `c` та `d` на глибині 3. Кількість бітів: 5 · 1 + 2 · 2 + 1 · 3 + 1 · 3 = 15.
Сума ваг злиттів дає те саме: 2 + 4 + 9 = 15. Код сталої довжини з двох бітів на символ дав би 18.

</details>

**3. Чому сума ваг усіх злиттів дорівнює кількості бітів закодованого тексту?**

<details><summary>Відповідь</summary>

Кожне злиття ставить над двома деревами новий вузол, тому всі символи обох дерев стають на один рівень глибшими, і код
кожного з них довшає на один біт. Вага нового вузла — це сума частот цих символів, тобто саме стільки бітів додало це
злиття до всього тексту. Символ на глибині `k` брав участь у `k` злиттях, і його частота увійшла в суму `k` разів.

</details>

**4. Частоти восьми символів — перші вісім чисел Фібоначчі: 1, 1, 2, 3, 5, 8, 13, 21. Яку форму має дерево Хаффмана і
скільки бітів займе текст?**

<details><summary>Відповідь</summary>

Злиття йдуть так: 1 + 1 = 2, далі 2 + 2 = 4, потім 4 + 3 = 7, 7 + 5 = 12, 12 + 8 = 20, 20 + 13 = 33 і 33 + 21 = 54.
Щоразу щойно злите дерево виявляється одним із двох найлегших, тому дерево росте ланцюжком: на кожному рівні один
листок і одне піддерево. Глибини символів від найчастішого до найрідкісніших: 1, 2, 3, 4, 5, 6, 7 і 7. Кількість бітів
дорівнює сумі ваг злиттів: 2 + 4 + 7 + 12 + 20 + 33 + 54 = 132. У тексті 54 символи, тож виходить близько 2,44 біта на
символ проти 3 бітів у коді сталої довжини.

</details>

**5. Усі вісім символів тексту трапляються однаково часто. Що дасть код Хаффмана?**

<details><summary>Відповідь</summary>

Нічого кращого за код сталої довжини. Алгоритм зіллє символи парами, потім пари парами, і вийде дерево, де всі вісім
листків лежать на глибині 3. Кожен символ отримає 3 біти, як і в коді сталої довжини. Код Хаффмана виграє лише тоді,
коли частоти нерівні.

</details>

**6. Програма кодує і розкодовує всі тестові тексти правильно, але на рядку `zzzz` розкодування повертає порожній
рядок. У чому причина?**

<details><summary>Відповідь</summary>

У тексті один різний символ. Дерево складається з одного листка, який водночас є коренем, тому шлях до нього порожній
і код символу — порожній рядок. Закодований текст має нуль бітів, і розкодуванню нема чого читати. Цей випадок треба
розглянути окремо: наприклад, дати єдиному символу код з одного біта або зберігати кількість символів оригіналу.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| біт | одна двійкова цифра, 0 або 1 |
| код сталої довжини | код, у якому всі символи мають коди однакової довжини |
| код змінної довжини | код, у якому довжини кодів різних символів різні |
| префікс | початок рядка |
| код без префіксів | код, у якому жоден код символу не є початком коду іншого |
| частота символу | скільки разів символ трапляється в тексті |
| вартість дерева | сума добутків частоти кожного символу на глибину його листка; кількість бітів закодованого тексту |
| оптимальний код | код без префіксів з найменшою вартістю для заданих частот |
| повне двійкове дерево | дерево, де кожен вузол, крім листків, має рівно двох дітей |
| код Хаффмана | код, побудований злиттям двох найрідкісніших символів знизу вгору |
| код Шеннона і Фано | код, побудований поділом символів на дві групи згори вниз; не завжди оптимальний |
