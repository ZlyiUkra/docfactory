### `Binary search`

Розділ починається з пошуку прізвища на літеру K у телефонній книзі. Ніхто не гортає книгу з першої сторінки: всі
відкривають десь посередині, бо прізвища впорядковано. Так автор підводить до **двійкового пошуку** (binary search):
алгоритму, який шукає елемент у впорядкованому списку й щоразу відкидає половину ще не перевірених елементів.

Далі гра «вгадай число від 1 до 100». Хто вгадує по черзі, 1, 2, 3, …, може витратити до 100 спроб. Автор називає це
**простим пошуком** (simple search). Хто починає з 50, а потім ділить залишок навпіл, вгадає не більше ніж за 7 спроб.

Потім словник із 240 000 слів: простий пошук робить до 240 000 кроків, двійковий — 18. Число 18 з'являється так: стільки
разів 240 000 можна поділити навпіл, поки не залишиться одне слово.

**`Logarithms`.** Врізка пояснює логарифм. `log₁₀ 100` питає, скільки десяток треба перемножити, щоб отримати 100; відповідь
2. Логарифм — дія, обернена до піднесення до степеня. Важливе домовлення книжки: коли вона пише `log`, мається на увазі
`log₂`, логарифм за основою 2. Так само домовляються CLRS і більшість книжок про алгоритми, тільки CLRS пише `lg`.

**Примітка про впорядкованість.** Двійковий пошук працює лише на впорядкованому списку. Якщо список не впорядкований, то з
того, що середній елемент менший за шуканий, не випливає, що шуканий праворуч, і алгоритм відкине ту половину, де елемент
лежить насправді.

### Код `binary_search` на Python

Книжка записує двійковий пошук мовою Python. Python — запасна мова цього курсу, тому ось ця функція рядок за рядком з
поясненням, як те саме виглядає в TypeScript.

| Рядок Python | Що він робить | Як це записують у TypeScript |
|--------------|---------------|------------------------------|
| `def binary_search(arr, item):` | Оголошує функцію з двома параметрами. Двокрапка відкриває тіло. | `function binarySearch(arr: number[], item: number)` і фігурна дужка |
| `low = 0` | Ліва межа частини масиву, де ще може бути `item`. | `let low = 0;` |
| `high = len(arr) - 1` | Права межа. `len(arr)` — довжина масиву. | `let high = arr.length - 1;` |
| `while low <= high:` | Повторювати, поки частина непорожня. | `while (low <= high) {` |
| `mid = (low + high) // 2` | Середина. `//` — ділення з округленням униз. | `const mid = Math.floor((low + high) / 2);` |
| `guess = arr[mid]` | Елемент посередині. | `const guess = arr[mid];` |
| `if guess == item: return mid` | Знайшли: повернути номер. | `if (guess === item) return mid;` |
| `elif guess > item: high = mid - 1` | Середній більший: шуканий лівіше, праву межу зсуваємо. `elif` означає `else if`. | `else if (guess > item) high = mid - 1;` |
| `else: low = mid + 1` | Середній менший: шуканий правіше. | `else low = mid + 1;` |
| `return None` | Не знайшли. `None` у Python відповідає `null` чи `undefined`. | `return undefined;` |

У Python немає фігурних дужок: тіло циклу чи умови визначається відступом. Тому в книжці відступи — частина коду, а не
оформлення. У тексті, який повертає сервер, відступи загубилися, і рядки коду злилися з підписами до малюнків на кшталт «Found
the item» чи «The guess was too high». Код зручніше читати в PDF.

Наприкінці книжка перевіряє функцію: `binary_search([1, 3, 5, 7, 9], 3)` дає `1`, бо номери в масиві починаються з нуля, а
`binary_search([1, 3, 5, 7, 9], -1)` дає `None`.

### Тонке місце: скільки перевірок робить двійковий пошук насправді

Книжка каже, що двійковому пошуку потрібно `log₂ n` кроків. Вправа 1.1 питає, скільки кроків у найгіршому випадку на
впорядкованому списку з 128 імен, і в додатку з відповідями стоїть 7, бо `log₂ 128 = 7`. Перевірмо це на самому коді книжки.
Ось функція `binary_search` з книжки, у яку додано лічильник перевірок. Вона перебирає всі можливі шукані значення: ті, що є
в списку, і ті, що потрапляють між елементами або за межі списку.

```python
def binary_search(arr, item):
    low = 0
    high = len(arr) - 1
    checks = 0                    # додано: скільки елементів перевірено
    while low <= high:
        mid = (low + high) // 2
        guess = arr[mid]
        checks += 1
        if guess == item:
            return mid, checks
        elif guess > item:
            high = mid - 1
        else:
            low = mid + 1
    return None, checks

for n in (100, 128, 256):
    arr = list(range(n))          # список 0, 1, …, n - 1
    worst = max(binary_search(arr, t / 2)[1] for t in range(-1, 2 * n + 1))
    print(n, worst, binary_search(arr, n - 1), binary_search(arr, n))
```

Вивід, отриманий у Python 3.14:

```
100 7 (99, 7) (None, 7)
128 8 (127, 8) (None, 8)
256 9 (255, 9) (None, 9)
```

У кожному рядку спершу йде `n`, потім найбільша кількість перевірок, далі результат пошуку останнього елемента й результат
пошуку значення, якого в списку немає. Для 128 елементів найгірший випадок — 8 перевірок, а не 7. Так буває, наприклад, коли
шукають останній елемент списку.

Звідки різниця. `log₂ 128 = 7` — це кількість поділів навпіл, після яких зі 128 елементів лишається один: 128, 64, 32, 16, 8,
4, 2, 1. Але код перевіряє елемент **перед** кожним поділом, а потім ще раз перевіряє той один, що лишився. Тому точна
кількість перевірок у найгіршому випадку — `⌊log₂ n⌋ + 1`, тобто ціла частина логарифма плюс один. Для 100 елементів
`log₂ 100 ≈ 6,64`, і обидва способи дають 7, тому в прикладі з числом від 1 до 100 книжка не помиляється.

Для оцінок на кшталт `O(log n)`, про які йдеться далі, різниця в одну перевірку не важить. Але в рядках «Перевірити себе»
цього плану числа точні, тому рахуйте перевірки так, як їх робить код, а не за формулою з книжки.

### `Big O notation`

**Історія Боба.** Боб пише для NASA програму, яка допоможе ракеті вибрати місце посадки на Місяць, і вибирає між простим і
двійковим пошуком. На 100 елементах простий пошук займає 100 мс, двійковий — 7 мс. Боб вирішує, що двійковий пошук у 15
разів швидший, і для мільярда елементів очікує 450 мс простого пошуку. Насправді простий пошук на мільярді елементів займе
мільярд мілісекунд, тобто понад 11 днів, а двійковий — 30 мс. На мільярді двійковий пошук швидший не в 15, а приблизно в 33
мільйони разів. Висновок книжки: треба знати не те, скільки триває алгоритм, а те, як цей час росте разом із розміром
входу.

**Що таке `O`.** Запис `O(n)` читають «О від ен». Книжка пояснює його так: це кількість операцій, яку алгоритм робить на
вході розміру `n`, у найгіршому випадку. Секунд у ньому немає. Строге визначення `O`, через сталі множники, дає день 3
плану; тут достатньо інтуїції.

**`Visualizing different Big O run times`.** Треба намалювати сітку з 16 клітинок. Перший спосіб — малювати клітинки по
одній, 16 операцій, тобто `O(n)`. Другий — скласти аркуш навпіл чотири рази й розгорнути: кожне складання подвоює кількість
клітинок, тому 16 клітинок виходять за 4 операції, тобто `O(log n)`.

**`Big O establishes a worst-case run time`.** Якщо простим пошуком шукати людину, чиє ім'я стоїть першим у телефонній
книзі, пошук закінчиться за один крок. Але простий пошук усе одно `O(n)`: оцінка описує **найгірший випадок**, найбільшу
кількість кроків для входу цього розміру. Книжка обіцяє в главі 4 повернутися до **середнього випадку**, кількості кроків
на типовому вході.

**`Some common Big O run times`.** П'ять часів роботи від найшвидшого до найповільнішого:

| Запис | Як називають | Приклад із книжки |
|-------|--------------|-------------------|
| `O(log n)` | логарифмічний час | двійковий пошук |
| `O(n)` | лінійний час | простий пошук |
| `O(n · log n)` | — | швидке сортування, глава 4 |
| `O(n²)` | квадратичний час | сортування вибором, глава 2 |
| `O(n!)` | факторіальний час | перебір маршрутів комівояжера |

Далі книжка рахує, скільки часу піде на сітку з 16 і з 1024 клітинок, якщо виконувати 10 операцій на секунду. Таблиця з
відповіддю в книжці намальована, і в тексті сервера її немає. Ось ті самі числа, пораховані за правилом книжки: кількість
операцій поділено на 10.

| Час роботи | 16 клітинок | 1024 клітинки |
|------------|-------------|---------------|
| `O(log n)` | 0,4 с | 1 с |
| `O(n)` | 1,6 с | 102,4 с, близько 1,7 хвилини |
| `O(n · log n)` | 6,4 с | 1024 с, близько 17 хвилин |
| `O(n²)` | 25,6 с | 104 858 с, близько 1,2 доби |
| `O(n!)` | близько 66 тисяч років | число років із 2632 цифр |

Книжка сама попереджає, що це спрощення: насправді час роботи в записі `O` не перетворюється на кількість операцій так
точно. Але порядок чисел показує головне: різниця між рядками росте з розміром задачі.

**`The traveling salesperson`.** Комівояжер має об'їхати п'ять міст найкоротшим маршрутом. Якщо перебрати всі порядки
міст, їх буде `5! = 120`, для шести міст 720, для семи 5040. **Факторіал** `n!` — добуток `1 · 2 · … · n`. Для 100 міст
перебір неможливий. Книжка каже, що швидкого алгоритму для цієї задачі не знає ніхто, а багато дослідників вважають, що його
не існує. Тому шукають наближений розв'язок, про це глава 10 книжки й фаза 5 плану.

### `0.2 Multiplication`

Розділ показує, що алгоритми множення існують тисячі років, і на них видно, що «елементарний крок» залежить від того, хто
виконує алгоритм.

**`Lattice Multiplication`.** Множення «ґраткою» — це по суті шкільне множення стовпчиком. Числа записано масивами цифр, а
добуток — це сума всіх добутків пар цифр `X[i] · Y[j] · 10^(i+j)`. Елементарні операції алгоритму — додавання і множення двох
однозначних чисел; останнє виконують за таблицею множення. Для `m`-значного й `n`-значного числа потрібно `m · n` множень
цифр, тому час роботи `O(mn)`. Рисунок 0.1 показує множення `934 × 314 = 293 276` з італійського підручника 1478 року.

**`Duplation and Mediation`.** Це селянське множення, яке лекція простежує на прикладі `123 × 456 = 56 088`. Рисунок 0.3 книжки
— та сама таблиця. Головне в розділі:

- алгоритм зводить множення до чотирьох простіших дій: перевірка парності, додавання, **дуплація** (подвоєння) і **медіація**
  (ділення навпіл з округленням униз);
- правильність випливає з тотожності, яку лекція записує трьома рядками. Erickson пише, що ця тотожність **і є** алгоритмом,
  а цикл у псевдокоді лише ховає рекурсивну природу алгоритму. Що таке рекурсія, пояснює день 5;
- алгоритм робить `O(log x)` операцій. Якщо перед початком поміняти аргументи місцями так, щоб `x` був меншим, операцій
  буде `O(log min{x, y})`, тобто логарифм меншого з чисел;
- у двійковій системі числення селянське множення і множення ґраткою — той самий алгоритм.

**`Compass and Straightedge`.** Грецькі геометри «множили» відрізки за допомогою циркуля й лінійки. Елементарні операції тут
інші: провести пряму через дві точки, провести коло, знайти точки перетину. Алгоритм Евкліда з рисунка 0.4 будує відрізок
довжини `|AC| · |AD| / |AB|`. Erickson звертає увагу на дві речі. Евклід спершу визначає допоміжну операцію `RightAngle`,
тобто, як сказали б програмісти, пише підпрограму. І в ідеальній геометрії кожна побудова виконується за сталий час, тому
алгоритм працює за `O(1)`. Ця думка важлива: **модель обчислень**, тобто домовленість про те, які кроки вважаються
елементарними і скільки коштує кожен, визначає, якою вийде оцінка.

### `0.3 Congressional Apportionment`

Конституція США вимагає розподілити 435 місць у Палаті представників між 50 штатами пропорційно населенню, і кожен штат
отримує хоча б одне місце. Дробових депутатів не буває, тому потрібен алгоритм округлення. З 1941 року закон використовує
метод **Гантінгтона — Гілла**:

1. кожен штат спершу отримує одне місце;
2. кожне наступне місце дістається штату з найбільшим **пріоритетом** `P / √(r(r + 1))`, де `P` — населення штату, а `r` —
   скільки місць він уже має.

Ось маленький приклад, порахований за цим правилом, якого в книжці немає. Три штати мають населення 100, 60 і 40 одиниць,
розподіляємо 5 місць. Спершу кожен штат отримує одне місце, лишається два.

| Крок | Пріоритет A (100) | Пріоритет B (60) | Пріоритет C (40) | Хто отримує місце |
|------|-------------------|------------------|------------------|-------------------|
| 1 | 100 / √2 ≈ 70,71 | 60 / √2 ≈ 42,43 | 40 / √2 ≈ 28,28 | A, тепер у нього 2 |
| 2 | 100 / √6 ≈ 40,82 | 42,43 | 28,28 | B, тепер у нього 2 |

Результат: A — 2, B — 2, C — 1. Точно пропорційний розподіл був би 2,5, 1,5 і 1, і алгоритм його округлив.

Псевдокод `ApportionCongress` тримає штати в **пріоритетній черзі**. Це структура даних, яка вміє додати елемент із
пріоритетом (`Insert`) і забрати елемент з найбільшим пріоритетом (`ExtractMax`). Пріоритетну чергу план вивчає у фазі 1,
день 10. Erickson наголошує: відповідь алгоритму, а отже і його правильність, не залежить від того, як влаштовано чергу, а
від цього залежить лише швидкість. У тексті сервера коментар і цикл кажуть про «`n − R`» місць, що лишилися. За змістом
їх `R − n`, бо всього місць `R`, а `n` вже роздано. Так і записано в оцінці часу в розділі 0.6.

Наприкінці розділу згадано методи д'Ондта і Сент-Лаге, якими розподіляють місця між партіями в багатьох парламентах. Вони
відрізняються лише формулою пріоритету: `P / (r + 1)` і `P / (2r + 1)`.

### `0.4 A Bad Example`

«Алгоритм» Стіва Мартіна: отримайте мільйон доларів, а коли податковий інспектор спитає, чому ви не платили податків,
скажіть «я забув». Перший крок не елементарний для більшості людей, тому вся інструкція не є алгоритмом. Водночас вона є
прикладом **зведення**: вона зводить важку задачу до «легшої», «отримати мільйон». Erickson обіцяє, що зведення
зустрічатимуться в книжці постійно.

### `0.5 Describing Algorithms`

Найважливіший розділ дня для вправи.

**Чотири частини опису.** Що (точна специфікація задачі), Як (точний опис алгоритму), Чому (доведення правильності), Як
швидко (аналіз часу роботи). Розробляти їх можна в будь-якому порядку, але подавати краще окремо.

**Для кого писати.** Erickson радить писати для «компетентного, але скептичного програміста, який не такий кмітливий, як
ви», наприклад для себе самого шість місяців тому. Той, хто читатиме опис пізніше, не матиме вашої інтуїції. Не матиме її і
компілятор. Головна думка розділу, яку автор виділяє курсивом: основна робота того, хто створює алгоритми, — навчити інших
людей, як і чому алгоритм працює. Правильний і швидкий код автор називає важливою, але другою за значенням метою.

**`Specifying the Problem`.** Задачі приходять звичайною мовою і про реальні речі. Їх треба переказати мовою математичних
об'єктів: чисел, масивів, списків, графів, дерев. Треба знайти приховані припущення й записати їх. Приклад Erickson: у пісні
«n пляшок пива» `n` завжди ціле невід'ємне. Специфікація має бути достатньою, щоб інший міг використати алгоритм як
**чорну скриньку**: описати тип і зміст кожного параметра і те, як вихід залежить від входу. Водночас специфікація має
приховувати все, що для використання не потрібне. Наприкінці розділу Erickson порівнює алгоритми з 0.2: множення ґраткою і
селянське множення розв'язують одну задачу, бо їхні входи й виходи — масиви цифр. А геометричне множення Евкліда розв'язує
іншу задачу, бо його входи й вихід — відрізки.

**`Describing the Algorithm`.** Програма — конкретне втілення алгоритму, але алгоритм не програма. Код погано підходить для
розповіді, а звичайний текст — для точності. Тому Erickson радить поєднання псевдокоду і структурованої мови: псевдокод дає
будову, а окремі кроки можна писати формулою чи словами, як зрозуміліше. Добрий опис має містити все, що потрібно, щоб
задати алгоритм, довести його правильність і оцінити час, і нічого зайвого.

**Правило про повторення.** На початку документа `Analyzing Algorithms` стоїть кінець розділу 0.5 з правилом, яке автор
називає особливо шкідливою звичкою: ніколи не описуйте повторення словами «спочатку зробіть це, потім те, і так далі» чи
«повторюйте, поки…». Якщо в алгоритмі є цикл, запишіть цикл і поясніть, що відбувається на довільному проході. Якщо
алгоритм рекурсивний, запишіть рекурсію і поясніть кожен випадок.

### `0.6 Analyzing Algorithms`

**`Correctness`.** Книжка вимагає алгоритмів, правильних **завжди**, для всіх входів, і вимагає це **доводити**. Інтуїція й
кілька тестів доведенням не є, а «очевидне» надто часто означає «хибне». Доведення правильності зазвичай спираються на
індукцію, і автор пише, що без неї з книжкою буде важко. Індукцію план вивчає в день 4.

**`Running Time`.** Скільки часу займає пісня `BottlesOfBeer(n)`? Це залежить від співака й техніки, але пісня для `2n`
пляшок завжди вдвічі довша, ніж для `n`. Тому час оцінюють через ріст: `Θ(n)`. Запис `Θ` означає «росте рівно так, з
точністю до сталого множника», його пояснює день 3. Час можна рахувати, вибравши одну дію, яка повторюється, наприклад
скільки разів у пісні звучить слово «beer»: рівно `3n + 3` рази.

Пісня «Дванадцять днів Різдва», `NDaysOfChristmas`, має квадратичний час. Її псевдокод — два вкладені цикли: зовнішній по
днях, внутрішній по подарунках, які співак перелічує в куплеті цього дня. Назви подарунків звучать `1 + 2 + … + n = n(n +
1) / 2` рази. Для 12 днів це 78. А подарунків за перші `n` днів отримано `n(n + 1)(n + 2) / 6`. Для 12 днів це 364,
приблизно по одному на кожен день року. Розрахунок для `n = 12` зроблено для розбору, у книжці лише формули.

Для рекурсивних алгоритмів час зручніше записувати **рекурентним співвідношенням**, тобто формулою, яка виражає час через
час для меншого входу. Для селянського множення кількість операцій `T(x, y)` задовольняє `T(x, y) ≤ T(⌊x/2⌋, 2y) + 2` і
`T(0, y) = 0`, звідки `T(x, y) = O(log x)`. Як розв'язувати такі співвідношення, пояснює день 6.

**Час залежить від структури даних.** Метод Гантінгтона — Гілла працює за `O(N + RI + (R − n)E)`, де `N`, `I` і `E` — час
створення черги, вставки й вилучення максимуму. Продовження лежить на початку документа `Exercises`. Якщо реалізувати чергу
невпорядкованим масивом, вийде `O(Rn)`, а якщо двійковою купою — `O(R log n)`. Той самий алгоритм із різною структурою
даних має різний час.

**Інші ресурси.** Крім часу, рахують пам'ять, кількість підкидань монети, промахів кешу чи повідомлень між процесами, і
рахують їх тими самими методами. Наприклад, множення ґраткою двох `n`-значних чисел потребує `O(n²)` пам'яті, якщо записати
всі часткові добутки, і лише `O(n)`, якщо додавати їх одразу.

### `What kinds of problems are solved by algorithms?`

CLRS наводить приклади з реального життя, кожен з посиланням на главу книжки. Проєкт «Геном людини» використовує динамічне
програмування для порівняння послідовностей ДНК (глава 14, у плані фаза 4). Інтернет потребує пошуку маршрутів для даних
(глава 22) і пошукових систем (глави 11 і 32). Електронна комерція спирається на криптографію з відкритим ключем (глава 31).
Нафтова компанія, політик і авіакомпанія розподіляють обмежені ресурси, і ці задачі розв'язує лінійне програмування (глава
29).

Далі йдуть конкретні задачі:

- найкоротший маршрут на карті доріг, яку моделюють **графом**, тобто набором вершин-перехресть і ребер-доріг (глава 22, у
  плані фаза 3);
- порядок деталей механізму, у якому кожна деталь іде перед тими, що її використовують. Можливих порядків `n!`, тому
  перебрати їх не можна. Це **топологічне сортування** (глава 20, у плані фаза 3);
- лікар порівнює знімок пухлини з відомими випадками за допомогою кластеризації (глава 33);
- стиснення текстового файла кодом Хаффмана, у якому частіші символи отримують коротші коди (глава 15, у плані фаза 4).

Ці задачі мають дві спільні риси. По-перше, у них дуже багато можливих розв'язків, і майже всі не годяться, тому знайти
правильний чи найкращий без перебору всіх — справжня складність. По-друге, вони мають практичне застосування. CLRS додає,
що не кожна задача має очевидну множину можливих розв'язків, і наводить приклад: дискретне перетворення Фур'є, яке
перетворює сигнал на набір частот (глава 30).

### `Data structures`, `Technique`, `Hard problems`

- **Структура даних** — спосіб зберігати й упорядкувати дані так, щоб полегшити доступ до них і їх зміну. Жодна структура не
  підходить для всього, тому треба знати сильні й слабкі сторони кількох. Вправа 1.1-3 просить саме це.
- **Техніка.** Книжку можна використовувати як збірник готових рецептів, але колись трапиться задача, для якої готового
  алгоритму немає. Тому книжка вчить способів розробки й аналізу: «розділяй і володарюй» (глави 2 і 4), динамічне
  програмування (глава 14), амортизований аналіз (глава 16).
- **Важкі задачі.** Для деяких задач не відомо жодного алгоритму, що працює за розумний час. Найвідомішу групу таких задач
  називають **NP-повними** (глава 34). Про них відомо три речі. Ніхто не знайшов для них швидкого алгоритму, але й не довів,
  що його немає. Якщо швидкий алгоритм знайдеться для однієї з них, він буде для всіх. І багато з них дуже схожі на задачі,
  які розв'язуються швидко. Якщо задача NP-повна, краще шукати **наближений алгоритм**, який дає добрий, але не обов'язково
  найкращий розв'язок. Приклад — задача комівояжера про маршрут вантажівки з доставками.

### `Alternative computing models`

Тактова частота процесорів більше не росте так, як колись, бо чипи перегріваються. Тому процесори мають кілька **ядер**, і
алгоритми треба розробляти з урахуванням паралельності (глава 26). Ще одна модель — **онлайн-алгоритми**, які отримують вхід
частинами з часом і мусять діяти, не знаючи майбутнього: планувальник завдань у дата-центрі, маршрутизація в інтернеті,
сортування пацієнтів у приймальному відділенні (глава 27).

### Вправи 1.1-1 – 1.1-6

Усі шість вправ просять приклади з власного досвіду: де потрібне сортування, які ще міри ефективності є крім швидкості,
чим схожі й чим відрізняються задачі найкоротшого шляху й комівояжера. Для розробника інтерфейсів добрі відповіді на 1.1-2
— пам'ять, кількість запитів до мережі, розмір бандла й енергія батареї телефона.

## CLRS — `1.2 Algorithms as a technology`

**Де читати:** розділ 1.2 того самого PDF, документ `1.2 Algorithms as a technology`.

**Якщо часу мало,** прочитайте підрозділ `Efficiency` з порівнянням двох комп'ютерів.

**Якби комп'ютери були нескінченно швидкими.** Розділ починає з питання: чи варто було б тоді вивчати алгоритми? Так, бо
однаково треба знати, що спосіб розв'язання зупиняється з правильною відповіддю. Але тоді годився б будь-який правильний
спосіб, і вибирали б найпростіший. Комп'ютери не нескінченно швидкі, а пам'ять не безкоштовна, тому час і пам'ять — ресурси,
які треба витрачати ощадливо.

### `Efficiency`

Сортування вставками займає час, приблизно рівний `c₁ n²`, а сортування злиттям — `c₂ n lg n`, де `c₁` і `c₂` — сталі, які
не залежать від `n`, а `lg n` — це `log₂ n`. Зазвичай `c₁ < c₂`, тобто на малих масивах сортування вставками швидше. Але
порівнювати треба множники `n` і `lg n`: для `n = 1000` маємо `lg n ≈ 10`, а для мільйона — лише близько 20. Тому хоч би
наскільки `c₁` був меншим за `c₂`, існує **точка перетину**, після якої сортування злиттям швидше.

Далі приклад із двома комп'ютерами. Формули з розрахунком у книжці набрано окремими рядками, і в тексті сервера вони
зникли: там стоїть «computer A takes while computer B takes». Ось ці розрахунки, перераховані для розбору:

| | Комп'ютер A | Комп'ютер B |
|---|---|---|
| Швидкість | 10¹⁰ інструкцій на секунду | 10⁷ інструкцій на секунду, у 1000 разів повільніше |
| Алгоритм | сортування вставками, `2n²` інструкцій | сортування злиттям, `50 n lg n` інструкцій |
| 10 мільйонів чисел | `2 · (10⁷)² / 10¹⁰ = 20 000` с, понад 5,5 години | `50 · 10⁷ · lg 10⁷ / 10⁷ ≈ 1 163` с, менше 20 хвилин |
| 100 мільйонів чисел | понад 23 дні | менше 4 годин |

Висновок книжки: комп'ютер B працює більш ніж у 17 разів швидше, хоч його програму написано посередньою мовою з поганим
компілятором. Перевага сортування злиттям росте разом із розміром задачі.

### `Algorithms and other technologies`

Алгоритми — така сама технологія, як швидке залізо: продуктивність системи залежить від обох. Навіть застосунок, у якому
немає «алгоритмічної» частини, спирається на алгоритми: їх використовували, щоб спроєктувати процесор, графічний інтерфейс,
мережеву маршрутизацію і компілятор.

Про машинне навчання CLRS пише, що воно саме є набором алгоритмів. Його успіхи стосуються головно задач, для яких люди не
знають правильного алгоритму, як-от розпізнавання зображень чи переклад. Для задач, які люди розуміють добре, а таких
більшість у книжці, спеціально розроблені алгоритми зазвичай працюють краще. Наука про дані теж спирається на алгоритми
книжки. Розділ закінчується думкою, що міцна основа в алгоритмах відрізняє справді вмілого програміста.

## Запитання до читання

**1. Чому Grokking каже, що двійковий пошук на 128 елементах робить 7 кроків, а код книжки робить до 8 перевірок?**

<details><summary>Відповідь</summary>

Книжка рахує, скільки разів 128 можна поділити навпіл до одного елемента: `log₂ 128 = 7`. Код перевіряє середній елемент
перед кожним поділом, а потім ще перевіряє той один, що лишився. Тому точна кількість перевірок у найгіршому випадку
`⌊log₂ n⌋ + 1 = 8`. Для оцінки `O(log n)` різниця не важить, а для точного підрахунку кроків важить.

</details>

**2. Що спільного в «алгоритмі» Стіва Мартіна і в методі Гантінгтона — Гілла, і чим вони відрізняються?**

<details><summary>Відповідь</summary>

Обидва зводять задачу до іншої: Мартін — до «отримати мільйон», Гантінгтон — Гілл — до операцій пріоритетної черги. Різниця
в тому, що операції черги елементарні й добре відомі, а «отримати мільйон» механічно виконати неможливо. Тому перше —
алгоритм, а друге — ні.

</details>

**3. Чому алгоритм Евкліда з циркулем і лінійкою працює за `O(1)`, а множення ґраткою — за `O(mn)`? Хіба множити відрізки
швидше, ніж числа?**

<details><summary>Відповідь</summary>

Ці оцінки отримано в різних моделях обчислень. В ідеальній геометрії кожна побудова за визначенням коштує сталий час, і
побудов сталу кількість. Множення ґраткою рахує операції з окремими цифрами, а їх `m · n`. Оцінка залежить від того, які
кроки вважаються елементарними, тому порівнювати їх напряму не можна.

</details>

**4. Що спільного між правилом Erickson «ніколи не описуйте повторення словами "і так далі"» і вимогою формулювати задачу
для всіх входів, а не на прикладі?**

<details><summary>Відповідь</summary>

Обидва правила про одне: опис має покривати всі випадки, а не перші кілька. «І так далі» описує перші проходи циклу й мовчить
про довільний. Специфікація, написана на прикладах, мовчить про входи, яких у прикладах не було, і порожній масив —
найчастіший із них.

</details>

**5. Вправа CLRS 1.2-2: для яких `n` сортування вставками з `8n²` кроків швидше за сортування злиттям із `64 n lg n`?**

<details><summary>Відповідь</summary>

Нерівність `8n² < 64 n lg n` після ділення на `8n` стає `n < 8 lg n`. Вона правдива для `2 ≤ n ≤ 43`: для `n = 43`
маємо `8 · lg 43 ≈ 43,4`, а для `n = 44` маємо `8 · lg 44 ≈ 43,7 < 44`. Для `n = 1` сортування злиттям за цією формулою
робить 0 кроків, бо `lg 1 = 0`, а вставками 8, тому вставки не швидші. Перевірено перебором `n` від 1 до 99.

</details>

**6. Вправа CLRS 1.2-3: за якого найменшого `n` алгоритм зі `100n²` кроків швидший за алгоритм із `2ⁿ` кроків?**

<details><summary>Відповідь</summary>

За `n = 15`: `100 · 15² = 22 500`, а `2¹⁵ = 32 768`. Для `n = 14` маємо `100 · 14² = 19 600` і `2¹⁴ = 16 384`, тобто
алгоритм із `2ⁿ` ще швидший. Від `n = 15` і далі `2ⁿ` росте швидше, і різниця лише збільшується.

</details>
