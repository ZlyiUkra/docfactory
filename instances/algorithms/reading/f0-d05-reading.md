### Вступ і `Recursion`

Глава починається з історії: у бабусі на горищі валіза, ключ від неї в коробці, у коробці інші коробки, і так далі. Як
знайти ключ? Книжка дає два алгоритми.

| Перший алгоритм | Другий алгоритм |
|-----------------|-----------------|
| Скласти купу коробок, які треба переглянути. | Переглянути коробку. |
| Узяти коробку з купи і переглянути її. | Якщо в ній коробка, перейти до кроку 1 для цієї коробки. |
| Якщо в ній коробка, додати її до купи. | Якщо в ній ключ, готово. |
| Якщо в ній ключ, готово. Інакше повторити. | |

Перший алгоритм — цикл із власною купою, другий — рекурсія. На сервері код обох алгоритмів і малюнки не збереглися,
вони є в PDF. Лекція показує ту саму пару на коментарях: `countCommentsIterative` з масивом `pending` відповідає
першому алгоритму, а `countComments` — другому.

### `Base case and recursive case`

Функція `countdown(i)` друкує `i` і викликає себе з `i − 1`. Без умови зупинки вона рахує 3, 2, 1, 0, −1, −2 і далі
без кінця, і книжка радить перервати її клавішами Ctrl-C. Звідси дві частини кожної рекурсивної функції: **рекурсивний
випадок**, де функція викликає себе, і **базовий випадок**, де не викликає.

Код Python і його відповідник на TypeScript:

| Python з книжки | TypeScript |
|-----------------|------------|
| `def countdown(i):` | `function countdown(i: number): void {` |
| `print(i)` | `console.log(i);` |
| `if i <= 1: return` | `if (i <= 1) return;` |
| `else: countdown(i-1)` | `countdown(i - 1);` |

Python позначає блоки відступами, а не фігурними дужками, і не пише крапок з комою.

Одна неточність у книжці стосується Python. Книжка пише, що рекурсія без бази «runs forever». У Python так не буде:
інтерпретатор зупинить її через тисячу вкладених викликів помилкою `RecursionError`, бо в Python межа глибини дорівнює
1000. Для `countdown` книжка, мабуть, мала на увазі, що зупинитися вона сама не здатна. Вправа 3.2 якраз про це.

### `The stack` і `The call stack`

**Стек** пояснено на листочках для справ на барбекю: новий кладуть зверху, читають і знімають лише верхній. Дві дії
мають назви **push** (покласти) і **pop** (зняти й прочитати). Ця сама структура в пам'яті, яка зберігає виклики
функцій, називається **стеком викликів**.

Приклад книжки з трьома функціями:

```python
def greet(name):
    print("hello, " + name + "!")
    greet2(name)
    print("getting ready to say bye...")
    bye()
```

`greet` вітається, викликає `greet2`, потім `bye`. Покроково: виклик `greet("maggie")` отримує в пам'яті «коробку», де
лежить `name = "maggie"`. Виклик `greet2` кладе зверху другу коробку. Коли `greet2` повертається, її коробка
знімається, і `greet` продовжує з місця, де зупинилася. Головна думка розділу: **коли одна функція викликає іншу,
перша призупиняється на середині**, а її змінні лишаються в стеку.

### `The call stack with recursion`

| Python з книжки | TypeScript |
|-----------------|------------|
| `def fact(x):` | `function fact(x: number): number {` |
| `if x == 1: return 1` | `if (x === 1) return 1;` |
| `else: return x * fact(x-1)` | `return x * fact(x - 1);` |

`==` у Python відповідає `===` у JavaScript, бо Python не перетворює типи під час порівняння. Книжка простежує
`fact(3)` малюнками стеку. Важливе спостереження: кожен виклик `fact` має **власну копію `x`**, і до чужої копії
доступу немає. Лекція показує те саме виводом функції `factorial` з відступами.

Наприкінці книжка повертається до коробок: у рекурсивному способі купи коробок немає, бо **купу зберігає стек**. Це
зручно, але кожен виклик займає пам'ять. Якщо стек занадто високий, книжка пропонує два виходи: переписати код на цикл
або скористатися **хвостовою рекурсією**, яку «підтримують лише деякі мови». Node до таких мов не належить: лекція
показує, що хвостова функція падає на тій самій глибині, що й звичайна.

| Що написано | Що це означає |

**Неточність у прикладі `countDownToZero`.** Текст каже, що базовий випадок — «коли `n` менше або дорівнює 0». У коді
стоїть `if (n < 0) return;`, тобто базовий випадок — від'ємне `n`, а 0 ще друкується і веде до виклику з −1. Код
працює правильно, друкує числа від 12 до 0, але текст його неточно описує.

### Фібоначчі: три версії

| Версія | Що робить | Що сказати |
|--------|-----------|------------|

### `Pascal's Triangle`

Трикутник Паскаля: кожне число — сума двох чисел над ним. Функція `pascalTriangle(row, col)` повертає 1, коли `col ==
0`, і 0, коли `row == 0`, а інакше — суму двох викликів для рядка вище. Текст при цьому каже про базовий випадок «коли
стовпчик дорівнює 1», а код перевіряє 0. Розбіжність знову між текстом і кодом. Зверніть увагу, що ця функція, як і
`getNthFibo`, має два рекурсивні виклики і обчислює ті самі значення багато разів.

### `Big-O for Recursion`

Цей розділ — уже тема завтрашнього дня. Дві неточності варто знати заздалегідь.

**Перебільшена картинка викликів.** Bae малює дерево викликів `getNthFibo(6)` так, ніби на кожному рівні викликів
удвічі більше: 16 викликів для `F(1)` і 32 для `F(0)`. Програма лекції порахувала справжні числа: `F(1)` викликається
8 разів, `F(0)` — 5 разів, а всього викликів 25. Картинка Bae — груба верхня межа, а не підрахунок. Висновок «час
експоненційний» від цього не змінюється, але основа експоненти не 2, а близько 1,618.

**Умова головної теореми.** Bae пише її для `T(n) = aT(n/b) + O(nᶜ)` з умовами `a ≥ 1` і `b ≥ 1`. Для `b = 1` вираз
`n/b = n` не зменшує задачу, і теорема не має сенсу: потрібно `b > 1`, як у CLRS. День 6 розбирає головну теорему
точно.

### Вступ і механіка

Рекурсивна функція викликає себе, поки не дійде до базового випадку. Книжка пише, що окремих задач на рекурсію на
співбесідах небагато, але вона лежить в основі задач про дерева, графи, перебір із поверненням і динамічне
програмування. Потім стоять поруч дві функції факторіала мовою Python: циклом і рекурсією.

### `The Call Stack & Stack Overflow`

| Що написано | Що це означає |
|-------------|---------------|
| Коли `main()` викликає `foo()`, комп'ютер запам'ятовує, куди повернутися. Однієї адреси мало, бо `foo()` може викликати ще щось. | Адреси повернення всіх вкладених викликів лежать у стеку викликів. |
| **Stack frame** — блок пам'яті з адресою повернення і параметрами виклику. | Кадр. |
| Стек викликів, як і структура даних «стек», працює за правилом LIFO: last in, first out. | Останнім прийшов, першим пішов. |
| Програма заздалегідь резервує під стек фіксований обсяг. Межа може бути в тисячах чи десятках тисяч кадрів. Python за замовчуванням має межу близько 1000. | Лекція виміряла Node: близько 9 800 кадрів для найпростішої функції. |
| Через ризик переповнення рекурсію в робочому коді іноді уникають. На співбесіді варто принаймні сказати інтерв'юеру про цей ризик. | Це показує, що ви знаєте обмеження інструмента. |

### `The Call Tree` і задача 33.1 «Robot Instructions»

Рядок інструкцій для робота складається з `L`, `R` і `2`. Цифра 2 означає: виконати всі інструкції після неї, а потім
ще раз усі інструкції після наступного за нею символу. Програма розбору перевірила приклади книжки:

| Вхід | Вихід |
|------|-------|
| `"LL"` | `"LL"` |
| `"2LR"` | `"LRR"` |
| `"2L"` | `"L"` |
| `"22LR"` | `"LRRLR"` |
| `"LL2R2L"` | `"LLRLL"` |

Рекурсивний розв'язок: порожній рядок дає порожню відповідь; якщо перший символ 2, склеїти відповіді для рядка без
першого символу і для рядка без перших двох; інакше перший символ плюс відповідь для решти. Тут функція викликає себе
**двічі**, і виклики зручно малювати **деревом викликів**. Книжка підкреслює, що дерево викликів — інструмент для
розуміння, а не структура в пам'яті.

### `Common Mistakes`

П'ять помилок. Лекція розбирає їх на прикладах JavaScript.

| Помилка | Приклад книжки |
|---------|----------------|
| забутий чи неправильний базовий випадок | `factorial_rec(0)` без бази для 0 іде в −1, −2 і падає. Правило: кожен допустимий вхід мусить однозначно бути або базовим, або рекурсивним |
| немає прогресу | гілка для невідомої інструкції викликає `moves(seq)` з тим самим рядком |
| зайві копії | зрізи `seq[1:]` у Python копіюють рядок; краще передавати номер позиції |
| неправильно зібрані результати | з двох рекурсивних відповідей не завжди очевидно, скласти їх чи перемножити |
| забутий `return` | рекурсивний бінарний пошук, де результат рекурсивного виклику не повернули, повертає `None` для всього, крім середнього елемента |

Ідея «**Pass Indices, Not Copies**»: посилатися на позиції в оригінальному масиві чи рядку замість зрізів. Лекція
показує, що для перевірки паліндрома з `slice` на 5000 символах це шість мільйонів скопійованих символів проти нуля.

### `Implementation Choices` і задача 33.2 «Nested Array Sum»

Книжка обговорює три вибори стилю: допоміжна функція з додатковими параметрами чи ні; повертати значення чи дописувати
в зовнішню змінну; перевіряти аргументи **до** рекурсивного виклику (eager) чи **на вході** в нього (lazy). Задача про
суму вкладеного масиву показує останній вибір. Програма розбору перевірила відповіді: `[1, [2, 3], [4, [5]], 6]` дає
21, `[[[[1]], 2]]` дає 3, а порожній масив дає 0. Книжка навмисно лишає відповідь для порожнього масиву знаком
питання: вирішити, що повертати для порожнього входу, мусите ви, як у лекції дня 1.

Коли взагалі писати рекурсію? Книжка відповідає: там, де вона природна, тобто в деревах, графах, переборі й
мемоізації. Шукати найбільше в масиві рекурсією не варто. Якщо глибина може дійти до десятків тисяч, рекурсії краще
уникнути або принаймні сказати про ризик.

### `Big O Analysis` і метод BAD

Час рекурсивного алгоритму — сума роботи всіх вузлів дерева викликів. Перше запитання: скільки вузлів має дерево? Для
дерева з глибиною `d` і найбільшим розгалуженням `b` вузлів не більше `1 + b + b² + … + b^(d−1)`, тобто `O(bᵈ)`.
Помноживши на додаткову роботу одного вузла `A`, отримують межу `O(bᵈ · A)`. Книжка називає цей прийом **BAD method**:
Branching factor, Additional work, Depth.

| Що написано | Що це означає |
|-------------|---------------|
| Для «Robot Instructions» межа `O(2ⁿ)`, але неточна: не всі листки на найбільшій глибині. Насправді вузлів близько `O(1,618ⁿ)`. | Програма розбору порахувала вузли для `"22222R"`: 33, а не `2⁷ = 128`. Число 1,618 — та сама основа, що для Фібоначчі. |
| Межа може бути неточною з трьох причин: не всі листки на найбільшій глибині; не всі вузли мають найбільше розгалуження; не всі вузли роблять однакову роботу. | Метод дає правильну верхню межу, але не обов'язково найменшу. |
| Для співбесід такої межі зазвичай досить. Якщо підозрюєте, що вона неточна, скажіть чому. | Час відомих алгоритмів, як сортування злиттям, варто просто пам'ятати. |

Задачі на метод BAD з відповідями книжки: якщо цифр 2 не більше п'яти, вузлів на кожному рівні не більше `2⁵ = 32`, і
час лінійний; якщо додати інструкцію 3 з трьома викликами, межа `O(3ⁿ)`; якщо додати інструкцію, яка дописує `n`
символів, межа `O(2ⁿ · n)`.

### `Merge Sort Analysis`

Для сортування злиттям метод BAD дає `O(2^(log n) · n) = O(n²)`, і це груба переоцінка: лише корінь зливає масиви
довжиною `n`, а вузли біля листків зливають крихітні масиви. Якщо скласти роботу по рівнях, кожен рівень робить `n`
кроків, а рівнів `log₂ n`, тож разом `O(n log n)`. Книжка каже, що такого аналізу на співбесідах не чекають, а головну
теорему радить узагалі не вчити, бо «багато інтерв'юерів самі її не знають». План іде іншим шляхом: день 6 розбирає і
дерево рекурсії, і головну теорему, бо без них не прочитати CLRS.

### `Space Analysis`

Пам'ять стеку викликів — додаткова пам'ять функції, і вона дорівнює `O(найбільшої глибини)`, а не кількості вузлів
дерева викликів. Приклад книжки: рекурсивне обертання масиву на місці, `reverse_rec(arr, i, j)`, міняє місцями крайні
елементи і викликає себе для `i + 1` і `j − 1`. Здається, що додаткова пам'ять `O(1)`, бо масив обертається на місці.
Насправді глибина рекурсії `n/2`, тому пам'ять `O(n)`, і на великому масиві функція переповнить стек. Тут краще цикл.

### `Recurrence Relations`, мемоізація і задачі

| Частина | Що в ній |
|---------|----------|
| задача 33.3 «Powers Mod M» | обчислити `aᵖ mod m`, не створюючи великих проміжних чисел. Розв'язок — швидке піднесення до степеня: для парного `p` маємо `aᵖ = a^(p/2) · a^(p/2)`, і остача береться на кожному кроці. Час `O(log p)`. Лекція показує ту саму ідею з `bigint` |
| `Memoization` | зберігати обчислені значення в словнику і не рахувати їх удруге. Фібоначчі з мемоізацією — лінійний. Детально — фаза 4 |
| задачі про плитки | кількість способів укласти підлогу `1 × n` плитками `1 × 1` і `2 × 1` задовольняє те саме співвідношення, що Фібоначчі; для `n = 4` способів 5. Для підлоги `3 × n` співвідношення `t(n) = t(n − 1) + t(n − 3)`, і для `n = 6` способів 6. Обидва числа програма розбору перевірила |
| задача 33.4 «Lego Castle» | замок з `n` поверхів — два замки з `n − 1` поверхів і дах. Програма розбору перевірила кількості блоків: 1, 5, 17, 49, 129 |
| задача 33.5 «Laminal Arrays» | «розділяй і володарюй»: найкраща сума серед половин масиву і всього масиву. Для `[3, −9, 2, 4, −1, 5, 5, −4]` відповідь 6, частина `[2, 4]` |

### `Key Takeaways`

Розуміння рекурсії спирається на стек викликів і дерево викликів. Ознаки, що задачу варто розв'язувати рекурсією: дані
самопосилальні або вкладені; умова містить самопосилальне означення; хочеться написати кількість вкладених циклів, яка
залежить від входу; задача пов'язана з сортуванням злиттям чи швидким сортуванням.

## Запитання до читання

**1. Вправа 3.1 Grokking. Що можна сказати про програму лише за стеком викликів, у якому зверху `greet2` з `name =
"maggie"`, а під ним `greet` з тим самим `name`?**

<details><summary>Відповідь</summary>

Що `greet` викликала `greet2` і зараз призупинена на середині, чекаючи, поки `greet2` поверне керування. Що в обох
викликах змінна `name` дорівнює `"maggie"`. Що зараз виконується саме `greet2`, бо її кадр зверху. Чого стек не каже:
що `greet` вже встигла зробити і що зробить після повернення.

</details>

**2. Вправа 3.2 Grokking. Що станеться зі стеком, якщо рекурсивна функція ніколи не доходить до бази?**

<details><summary>Відповідь</summary>

Кожен виклик додає кадр, і жоден не знімається, бо жоден виклик не повертається. Стек росте, поки не закінчиться
відведена йому пам'ять, і тоді програма падає з помилкою переповнення стеку. У Node це `RangeError: Maximum call stack
size exceeded`, у Python — `RecursionError` після тисячі викликів. Функція «не працює вічно», а аварійно зупиняється.

</details>

**3. Чому Erickson радить зупинитися словами «NO!! STOP!!» саме тоді, коли хочеться з'ясувати, як перенести `n − 1`
дисків?**

<details><summary>Відповідь</summary>

Бо ця задача — той самий екземпляр меншого розміру, і її розв'язує рекурсивний виклик. Спроба розібратися, як саме,
повертає до розгортання рекурсії подумки, яке для великих `n` неможливе. Правильність тримається на довірі: якщо
функція правильна для `n − 1`, і крок правильно використовує два такі виклики та одне перенесення, вона правильна і
для `n`. Це крок індукції.

</details>

**4. Bae пише, що хвостова версія Фібоначчі займає `O(n)` пам'яті. Чи так само це було б у мові з оптимізацією
хвостових викликів?**

<details><summary>Відповідь</summary>

Ні. У мові, яка звільняє кадр перед хвостовим викликом, у стеку одночасно лежав би лише один кадр, і пам'ять була б
`O(1)`. Специфікація ECMAScript такої оптимізації вимагає, але Node і Chrome її не виконують, тому для JavaScript у
Node оцінка Bae правильна.

</details>

**5. BCtCI каже, що рекурсивне обертання масиву на місці займає `O(n)` пам'яті. Звідки вона, якщо нових масивів не
створюється?**

<details><summary>Відповідь</summary>

Зі стеку викликів. Функція викликає себе `n/2` разів вкладено, і всі кадри лежать у стеку одночасно, поки не дійде до
бази. Кожен кадр займає сталу пам'ять, тож разом `Θ(n)`. Ітеративна версія з двома номерами займає `Θ(1)`.

</details>

**6. Чому метод BAD дав для «Robot Instructions» межу `O(2ⁿ)`, а для `"22222R"` вузлів лише 33?**

<details><summary>Відповідь</summary>

Метод BAD рахує так, ніби кожен вузол розгалужується на два і всі листки лежать на найбільшій глибині. Насправді гілка
`moves(seq[2:])` пропускає два символи, тому одна з двох гілок щоразу коротша, і дерево нерівне. Його розмір росте як
числа Фібоначчі, тобто приблизно в 1,618 раза на кожен символ, а не в 2. Межа `O(2ⁿ)` правильна, але неточна.

</details>
