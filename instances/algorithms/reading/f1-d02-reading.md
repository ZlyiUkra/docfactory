### 10.1.3: стеки й черги

```
STACK-EMPTY(S)                PUSH(S, x)                       POP(S)
1  if S.top == 0              1  if S.top == S.size            1  if STACK-EMPTY(S)
2      return TRUE            2      error "overflow"          2      error "underflow"
3  else return FALSE          3  else S.top = S.top + 1        3  else S.top = S.top − 1
                              4      S[S.top] = x              4      return S[S.top + 1]

ENQUEUE(Q, x)                         DEQUEUE(Q)
1  Q[Q.tail] = x                      1  x = Q[Q.head]
2  if Q.tail == Q.size                2  if Q.head == Q.size
3      Q.tail = 1                     3      Q.head = 1
4  else Q.tail = Q.tail + 1           4  else Q.head = Q.head + 1
                                      5  return x
```

| Що написано | Що це означає |
|-------------|---------------|
| Стек і черга — динамічні множини, у яких операція видалення сама визначає, який елемент видалити. У стеку — останній вставлений (LIFO), у черзі — той, що пробув найдовше (FIFO). | Визначення з лекції. |
| Стек на масиві `S[1 : n]` з атрибутами `S.top` і `S.size`. Стек займає `S[1 : S.top]`, дно — `S[1]`, верх — `S[S.top]`. | Масив фіксованого розміру, тому можливе переповнення. |
| Рисунок 10.2(c): після `POP` елемент 3 ще лежить у масиві, але вже не в стеку. | Стек визначає `S.top`, а не вміст комірок. |
| Черга на масиві `Q[1 : n]` вміщує не більше `n − 1` елементів. `Q.head` — голова, `Q.tail` — комірка, куди ляже наступний. Номери йдуть по колу: після `n` іде `1`. | Кільцевий буфер з лекції, нумерація з 1. |
| Черга порожня, коли `Q.head = Q.tail`. Повна, коли `Q.head = Q.tail + 1` або `Q.head = 1` і `Q.tail = Q.size`. | Обидві умови кажуть одне: `tail` стоїть одразу перед `head` по колу. Одна комірка лишається порожньою, щоб повну чергу можна було відрізнити від порожньої. |
| У `ENQUEUE` і `DEQUEUE` перевірки переповнення й спустошення пропущено, їх просить дописати вправа 10.1-5. Кожна операція `O(1)`. | — |

### 2.1 `ArrayStack`

| Що написано | Що це означає |
|-------------|---------------|
| `ArrayStack` реалізує інтерфейс списку на масиві `a`, який Morin називає **backing array**. Масив майже завжди більший, ніж треба, тому окремо зберігають кількість елементів `n`. | Розмір і місткість з лекції дня 8 фази 0. |
| `add(i, x)` зсуває `a[i..n−1]` праворуч і кладе `x` в `a[i]`; `remove(i)` зсуває ліворуч. Без урахування росту обидві коштують `O(n − i)`. | Біля кінця масиву дешево, біля початку дорого. Тому стек на масиві дешевий: він працює лише з кінцем. |
| `remove` стискає масив, коли `length(a) ≥ 3n`. `resize()` завжди створює масив довжини `max(1, 2n)`. | Після стискання масив заповнений наполовину. Поріг утричі, а не вдвічі, рятує від стрибків туди-сюди, як правило чверті в CLRS. |
| Лема 2.1: для будь-якої послідовності `m ≥ 1` операцій `add` і `remove`, починаючи з порожнього `ArrayStack`, усі виклики `resize()` разом коштують `O(m)`. | Амортизований аналіз. |

Доказ леми на сервері втратив формули. Відновлені вони такі. Між двома викликами `resize()` відбувається не менше
`nᵢ/2 − 1` операцій, де `nᵢ` — кількість елементів під час `i`-того виклику. Якщо викликів було `r`, то

```
Σ (nᵢ/2 − 1) ≤ m,   тобто   Σ nᵢ ≤ 2m + 2r,
```

а весь час на `resize()` дорівнює `Σ O(nᵢ) ≤ O(m + r) = O(m)`, бо `r ≤ m`.

Залишається показати, що між викликами справді стільки операцій. Якщо `resize()` викликав `add`, масив повний:
`length(a) = nᵢ`. Після попереднього виклику в масиві було не більше `length(a)/2 = nᵢ/2` елементів, отже, з того часу
відбулося щонайменше `nᵢ/2` додавань. Якщо `resize()` викликав `remove`, то `nᵢ ≤ length(a)/3`, а після попереднього
виклику елементів було не менше `length(a)/2 − 1`. Тоді видалень було щонайменше

```
length(a)/2 − 1 − length(a)/3 = length(a)/6 − 1 = (length(a)/3)/2 − 1 ≥ nᵢ/2 − 1.
```

Мінус одиниця враховує особливий випадок `n = 0`, `length(a) = 1`.

### 2.3 `ArrayQueue`

| Що написано | Що це означає |
|-------------|---------------|
| `ArrayStack` — поганий вибір для черги: одна з двох операцій мусить працювати з початком масиву, тобто з `i = 0`, і коштує пропорційно `n`. | Саме це показує вимір `shift` у лекції. |
| З нескінченним масивом черга була б простою: номер `j` наступного елемента на вилучення і кількість `n`. Елементи в `a[j..j + n − 1]`. | Черга з номером голови з лекції. |
| `ArrayQueue` імітує нескінченний масив скінченним і **модульною арифметикою**. Приклад з годинником: `10 + 5 = 15 ≡ 3 (mod 12)`. | Запис `≡ 3 (mod 12)` читається «дає остачу 3 при діленні на 12». |
| `a mod m` — єдине ціле `r` від `0` до `m − 1` таке, що `a = r + km` для деякого цілого `k`. У C, C++ і Java це оператор `%`. | Увага: `%` у цих мовах, як і в JavaScript, для від'ємного `a` дає від'ємний результат, тобто не збігається з цим визначенням. Лекція показує, як це виправити. |
| Елементи черги лежать у `a[j mod length(a)]`, `a[(j + 1) mod length(a)]`, …, `a[(j + n − 1) mod length(a)]`. | Кільцевий буфер. |
| `add(x)`: якщо `n + 1 > length(a)`, викликати `resize()`; покласти `x` у `a[(j + n) mod length(a)]`; збільшити `n`. | — |
| `remove()`: взяти `a[j]`, `j ← (j + 1) mod length(a)`, зменшити `n`, стиснути масив, якщо `length(a) ≥ 3n`. | — |
| `resize()` копіює `a[(j + k) mod length(a)]` у `b[k]` для `k` від 0 до `n − 1` і ставить `j ← 0`. | Копіювання в порядку черги, про яке попереджає лекція. |
| Теорема 2.2: без урахування `resize()` обидві операції `O(1)`; будь-яка послідовність `m` операцій витрачає на `resize()` разом `O(m)`. | — |

### 2.5 `DualArrayDeque`

| Що написано | Що це означає |
|-------------|---------------|
| `DualArrayDeque` будує деку з двох `ArrayStack`, `front` і `back`, поставлених спиною один до одного. Асимптотично вона не краща за `ArrayDeque`, але показує, як скласти складнішу структуру з простіших. | Не плутайте з чергою з двох стеків: тут обидва кінці відкриті. |
| `front` зберігає елементи з номерами `0 … front.size() − 1` у зворотному порядку, `back` — решту у звичайному. | Тому елемент з номером `i < front.size()` лежить у `front` на позиції `front.size() − i − 1`. |
| `balance()` стежить, щоб `3 · front.size() ≥ back.size()` і `3 · back.size() ≥ front.size()`, якщо елементів хоча б два. Коли умова порушується, елементи розподіляються порівну: `⌊n/2⌋` у `front` і `⌈n/2⌉` у `back`. | Переважування коштує `O(n)`, але трапляється рідко. |
| Без урахування `balance()` вартість `add(i, x)` — `O(1 + i)` при `i < n/4`, `O(n)` при `n/4 ≤ i < 3n/4` і `O(1 + n − i)` при `i ≥ 3n/4`, тобто разом `O(1 + min{i, n − i})`. | Біля обох кінців дешево. |
| Лема 2.2: `balance()` на будь-якій послідовності `m` операцій разом коштує `O(m)`. Доказ іде **методом потенціалу** з потенціалом `Φ = |front.size() − back.size()|`. | Метод потенціалу з лекції дня 8 фази 0. |

Доказ леми 2.2 на сервері з розсипаними дробами. Одразу після переважування `Φ₀ = |⌊n/2⌋ − ⌈n/2⌉| ≤ 1`. Кожна операція
без переважування змінює `Φ` не більше ніж на 1. Перед наступним переважуванням, якщо `3 · front.size() <
back.size()`, маємо

```
n = front.size() + back.size() < back.size()/3 + back.size() = (4/3) · back.size(),
Φ₁ = back.size() − front.size() > back.size() − back.size()/3 = (2/3) · back.size() > (2/3) · (3/4) · n = n/2.
```

Потенціал виріс від 1 до понад `n/2`, а кожна операція додає не більше 1. Отже, між двома переважуваннями відбулося не
менше `n/2 − 1` операцій, і вони оплачують переважування, як у лемі 2.1.

**Дрібна розбіжність у тексті.** Код `add(i, x)` викликає `front.add(front.size() − i, x)`, а аналіз нижче пише
`front.add(front.size() − i − 1, x)`. Правильний код: щоб новий елемент став номером `i` у списку, у перевернутому
`front` він має лягти на позицію `front.size() − i`. На оцінку `O(i + 1)` ця одиниця не впливає.

|-------------|---------------|
| Стек — як тубус чипсів: верхня чипсина покладена останньою і береться першою. Черга — як черга в магазині. | — |
| Крім `push` і `pop`, у стеків і черг часто є `peek`, що повертає елемент без вилучення. Усі операції можна зробити за сталий час (таблиця 1). | Сталий час у найгіршому випадку — для реалізації на списку. На динамічному масиві `push` сталий амортизовано. |
| Головний недолік стеків і черг порівняно з динамічним масивом — немає доступу за номером. | — |
| Стек на динамічному масиві: `push` — `append`, `pop` — зняти останній; на порожньому стеку `pop` і `peek` кидають `IndexError`. Стек на списку — у задачі 34.3. | На співбесіді звичайно беруть масив і називають змінну `stack`. |
| Примітка 3: у Python черга — `collections.deque` з `append` і `popleft`. «JavaScript has it worse», бо вбудованої черги немає зовсім. | Звідси практика дня. |

### Задачі

| Задача | Прийом |
|--------|--------|
| 32.1: стиснути масив, щоразу зливаючи першу ліворуч пару однакових сусідів у їхню суму | стек: кожне нове число може запустити ланцюжок злиттів з верхом стека |
| 32.2: те саме для блоків з `k` однакових чисел | у стеку лежать пари «число, скільки разів підряд»; книжка називає це **piggybacking**, «підвезти додаткові дані» |
| 32.3: лічильник глядачів за вікно часу | окрема черга на кожен тип глядача; старі записи вилучаються з голови, поки виходять за вікно |
| 32.4: поточна адреса після дій «go» і «back» | стек історії, `back` знімає, але не останню адресу |
| 32.5: те саме з «forward» | другий стек для адрес, з яких повернулися; дія «go» його очищає |
| 32.6: найбільше число збалансованих частин | висота графіка дужок: нова частина починається, коли висота повертається до 0 |
| 32.7: перевірка дужок кількох видів | стек відкритих дужок; розв'язок — готова практика дня |
| 32.8: найдовша збалансована підпослідовність | закривні дужки, що опускають графік нижче нуля, і відкривні, що лишилися в стеку наприкінці, видаляються |

У прикладі до задачі 32.2 розпізнавання зіпсувало проміжний крок: замість `[1, 2, 9, 2, 4]` має бути `[1, 9, 9, 9,
4]`. Три трійки злилися в 9, а потім три дев'ятки — у 27, звідки відповідь `[1, 27, 4]`.

В задачі 32.3 книжка обговорює покращення: зберігати в черзі не кожного глядача, а пари «момент, кількість». Тоді
нових глядачів того самого моменту треба дописувати до останньої пари, а старі пари вилучати з голови, тобто потрібен
доступ до обох кінців — дека.

### `Balanced Parentheses`

| Що написано | Що це означає |
|-------------|---------------|
| Рядок з `(` і `)` збалансований, якщо кожна відкривна має відповідну закривну, і те, що між ними, теж збалансоване. | `"(()())()"` — так, `")("` і `"(()"` — ні. |
| Стек підходить, бо дужки закриваються в порядку LIFO: у `"(())"` перша закривна відповідає другій відкривній. | — |
| **Reframe as plot heights**: рядок — графік, що йде вгору на `(` і вниз на `)`. Рядок збалансований, якщо графік ніколи не опускається нижче нуля і закінчується на нулі. | Для одного виду дужок стек не потрібен, досить лічильника висоти. Коли видів кілька, лічильника мало, бо треба пам'ятати, яка саме дужка відкрита. |
| Розв'язок 32.7 кладе в стек не відкривну дужку, а відповідну їй закривну. Тоді закривна з рядка просто порівнюється з верхом стека. | Дрібний прийом, що спрощує код. |
| Найчастіші помилки: знімати з порожнього стека чи черги без перевірки і забути про елементи, що лишилися після циклу. | Ті самі дві перевірки, що в коді польського запису в лекції. |
| **Recipe 1. Dangling bracket stack**: відкривні в стек, закривну звірити з верхом, після циклу перевірити, що стек порожній. | Рецепт залишає два питання. Перше на сервері загубилося, друге — що робити з символами, які не є дужками. |

### `Key Takeaways`

| Що написано | Що це означає |
|-------------|---------------|
| Для стека найпростіше — динамічний масив. | — |
| Для черг і дек найпростіше — зв'язний список. «A common mistake to avoid is using an array to implement a queue.» | Ідеться про наївну чергу на масиві з вилученням з початку. Кільцевий буфер з Morin і CLRS — теж масив, але без цієї проблеми; на співбесіді його довше писати, тому книжка радить список. |
| Стеки і черги — прості з погляду складності: усі операції сталі. | — |
| Ознаки задачі на стек: перетворення справа наліво, скасування й повтор дій, збалансовані дужки. | — |

Дві співбесіди з глави варто подивитися онлайн: обчислення виразу в зворотному польському записі, як у лекції, і
обчислення звичайного виразу з пріоритетами операцій. В обох кандидати помічають, що порядок операцій керується
стеком.

## Перевірте себе

**1. Skiena радить стек, коли порядок обробки не важливий. Чому саме стек, а не черга?**

<details><summary>Відповідь</summary>

Обидва контейнери дають сталий час операцій, але стек простіше реалізувати: досить масиву, що росте з одного кінця.
Черга вимагає або кільцевого буфера, або списку, або двох стеків. Коли порядок не важливий, справедливість черги не
потрібна, а простота стека дешевша.

</details>

**2. Черга CLRS на масиві `Q[1 : 6]`, спершу порожня. Виконайте `ENQUEUE 4`, `ENQUEUE 1`, `ENQUEUE 3`, `DEQUEUE`,
`ENQUEUE 8`, `DEQUEUE`. Що повернуть вилучення і які значення матимуть `Q.head` і `Q.tail`?**

<details><summary>Відповідь</summary>

На початку `Q.head = Q.tail = 1`. Три вставки кладуть 4, 1, 3 у комірки 1, 2, 3, і `Q.tail = 4`. Перше вилучення
повертає 4, `Q.head = 2`. Вставка 8 кладе її в комірку 4, `Q.tail = 5`. Друге вилучення повертає 1, `Q.head = 3`.
Наприкінці в черзі 3 і 8, `Q.head = 3`, `Q.tail = 5`. Це вправа 10.1-4.

</details>

**3. Чому `ArrayStack` Morin стискає масив, коли `length(a) ≥ 3n`, а не коли `length(a) ≥ 2n`?**

<details><summary>Відповідь</summary>

Після `resize()` масив має довжину `2n`, тобто заповнений рівно наполовину. Якби стискання спрацьовувало вже при
`length(a) ≥ 2n`, одне видалення одразу після росту знову викликало б `resize()`, а наступна вставка — ріст. Поріг у
три рази лишає між станом після `resize()` і порогом стискання запас у сталу частку `n` операцій, які й оплачують
копіювання. Це та сама думка, що правило чверті в CLRS 16.4.

</details>

**4. У `DualArrayDeque` `front` містить 2 елементи, `back` — 7. Чи буде переважування і якими стануть розміри?**

<details><summary>Відповідь</summary>

Умова переважування — `3 · front.size() < back.size()`: `3 · 2 = 6 < 7`, отже, так. Усього `n = 9` елементів, `front`
отримає `⌊9/2⌋ = 4`, `back` — `⌈9/2⌉ = 5`.

</details>

**5. Чому для одного виду дужок BCtCI обходиться лічильником висоти, а для кількох видів потрібен стек?**

<details><summary>Відповідь</summary>

Для одного виду кожна закривна дужка підходить до будь-якої відкритої, тож досить знати, скільки дужок відкрито: це і
є висота графіка. Коли видів кілька, закривна дужка мусить відповідати саме останній відкритій. Рядок `"([)]"` має
правильну кількість кожного виду, але `)` закриває `(`, поки відкрита `[`. Щоб це помітити, треба пам'ятати порядок
відкритих дужок, а цей порядок — стек.

</details>

**6. BCtCI називає реалізацію черги на масиві поширеною помилкою, а Morin і CLRS роблять чергу саме на масиві. Хто
правий?**

<details><summary>Відповідь</summary>

Обидва, бо йдеться про різні масиви. BCtCI застерігає від масиву, з якого вилучають початок зсувом, як `shift` у
JavaScript чи `pop(0)` у Python: кожне вилучення коштує `Θ(n)`. Morin і CLRS не зсувають нічого: номер голови йде по
колу, і обидві операції сталі. На співбесіді список чи `deque` швидше написати без помилок, а в бібліотечному коді
кільцевий буфер дає меншу пам'ять і швидший прохід.

</details>
