### 5.1–5.3: навіщо випадковість

| Що написано | Що це означає |
|-------------|---------------|
| Хеш-функція — будь-яка функція `h : U → {0, …, m − 1}`. Якщо `u = m`, годиться `h(x) = x`, і це звичайний масив. | Масив прямого доступу з учорашньої лекції. |
| Для будь-якої фіксованої функції знайдеться щонайменше `|U|/m` елементів з однаковим хешем. Якщо дані прийдуть звідти, «our code will come to a grinding halt». Erickson додає, що це справжня загроза для маршрутизаторів інтернету. | Атака з лекції. |
| «Input data is not random! So good hash functions must be random!» | Головна думка конспекту. |
| Метод ділення `x mod m` Erickson називає «utterly stupid»: навіть з простим `m` пари `x` і `x + am` колізують завжди. | В оригіналі написано «low-order bits of m», але мається на увазі «of x»: з `m = 2ᵈ` функція бере молодші біти ключа. |
| Ідеально випадкова функція — «теоретична фантазія»: щоб обчислювати її, довелося б записувати вже видані значення в окрему структуру з доступом за ключем, «which is exactly what hash tables are for!» | Тому шукають родини, у яких випадковості рівно стільки, скільки потрібно для оцінок. |
| **Uniform**: кожна комірка однаково ймовірна для кожного ключа. Сама по собі ця властивість марна: родина сталих функцій `const_a(x) = a` рівномірна, але «utterly useless». | Важить не рівномірність, а колізії. |
| **Universal**: `Pr[h(x) = h(y)] ≤ 1/m` для всіх `x ≠ y`. **Near-universal**: `≤ 2/m`. **k-uniform**: будь-які `k` різних ключів потрапляють у будь-які задані `k` комірок з ймовірністю `1/mᵏ`. | Ці самі властивості CLRS 11.3.3 називає universal, ε-universal і d-independent. |

### 5.4 Chaining

| Що написано | Що це означає |
|-------------|---------------|
| `𝓁(x)` — довжина списку `T[h(x)]`, а `C_{x,y}` дорівнює 1, коли `x` і `y` колізують. Тоді `𝓁(x) = Σ_y C_{x,y}`. | Довжина списку — сума індикаторних величин. |
| З універсальною родиною `E[C_{x,y}] = 1/m`, тож `E[𝓁(x)] = n/m = α`. З майже універсальною — не більше `2α`. Невдалий пошук займає `Θ(1 + α)`. | Та сама оцінка, що в CLRS, але без припущення про ідеальну функцію. |
| Якщо всередині кожної комірки тримати не список, а збалансоване дерево, пошук — `O(1 + log α)`. | Дерева — фаза 2. |
| **Caveat Lector!** Очікувана довжина списку стала, але очікуваний найдовший список — ні: навіть з ідеальною функцією при `α = 1` він `Θ(log n / log log n)`. | Запитання 6 лекції. Моделювання з мільйоном ключів дало 9–10. |
| «When several individual items are distributed independently and uniformly at random, the overall distribution of those items is almost never uniform in the traditional sense!» | Рівномірна випадковість не дає рівного розподілу. |

### 5.5 Multiplicative Hashing

| Що написано | Що це означає |
|-------------|---------------|
| Функцію задає параметр `a`, **сіль**, вибраний випадково при створенні таблиці. | Зерно з лекції. |
| `mult^p_a(x) = (a·x mod p) mod m` з простим `p > |U|`. Родина майже універсальна. Лема 1: кожне ненульове `a` має єдиний обернений за модулем `p`. | Обернене існує, бо `p` просте. |
| `h_{a,b}(x) = ((a·x + b) mod p) mod m` — **справді універсальна** родина з `p(p − 1)` функцій (теорема 1). Для будь-яких `r ≠ s` система `ax + b ≡ r`, `ay + b ≡ s` має єдиний розв'язок `(a, b)` з `a ≠ 0`. | Та сама родина, що в CLRS і в лекції. |
| Точна ймовірність колізії `(p − p mod m)(p − (m − p mod m)) / (m p (p − 1))`, строго менша за `1/m`. Для `p = 5`, `m = 3` це `1/5 < 1/3`, і таблиця всіх 20 функцій це підтверджує. | Таблиця на сервері розсипалася на цифри. |
| **Binary multiplicative hashing** для `U = [2ʷ]` і `m = 2^𝓁`: `mult^b_a(x) = ⌊(a·x mod 2ʷ) / 2^(w−𝓁)⌋` з непарним `a`. Це старші `𝓁` бітів молодшої половини добутку; у C — одне множення й один зсув. Родина майже універсальна. | Те саме, що multiply-shift у CLRS і мультиплікативне хешування в Morin. |

Решту конспекту можна прочитати пізніше: 5.6 оцінює найдовший список моделлю «кульки в кошиках», 5.7 описує ідеальне
хешування з вторинними таблицями розміру `2nⱼ²`, 5.8–5.10 — відкриту адресацію, лінійне і **двійкове зондування**
`hᵢ(x) = h(x) ⊕ i`, де `⊕` — виключне «або». Двійкове зондування Erickson пропонує як варіант лінійного, що трохи
краще працює з кешем і простіше аналізується.

### 11.3.2–11.3.4 Random і universal hashing

| Що написано | Що це означає |
|-------------|---------------|
| Зловмисник, що знає функцію, вибере `n` ключів з однаковим хешем. Єдиний дієвий захист — вибирати функцію випадково, незалежно від ключів. | Як вибір опорного елемента в quicksort, до якого план дійде в день 9. |
| Родина ℋ **універсальна**, якщо для будь-яких різних `k₁`, `k₂` кількість функцій з `h(k₁) = h(k₂)` не більша за `|ℋ|/m`. | Ймовірність колізії не більша за `1/m`. |
| Наслідок 11.3: з універсальним хешуванням і ланцюжками будь-яка послідовність `s` операцій, серед яких `n = O(m)` вставок, займає в середньому `Θ(s)`. | Доказ — теорема 11.2 з заміною ймовірності `1/m` на «не більше `1/m`». |
| Властивості родин: uniform, universal, ε-universal, d-independent. | Erickson називає d-independent словом k-uniform. |

Відновлені формули (11.3) і (11.4):

```
h_ab(k) = ((a·k + b) mod p) mod m,                       (11.3)
ℋ_pm = { h_ab : a ∈ ℤ*_p, b ∈ ℤ_p },                       (11.4)
```

де `ℤ_p = {0, 1, …, p − 1}`, а `ℤ*_p = {1, …, p − 1}`. Родина має `p(p − 1)` функцій. Приклад книжки: `p = 17`, `m =
6`, `h₃,₄(8) = ((3 · 8 + 4) mod 17) mod 6 = 11 mod 6 = 5`.

**Доказ універсальності** на сервері втратив одну оцінку. Для різних ключів значення `r₁ = (ak₁ + b) mod p` і `r₂ =
(ak₂ + b) mod p` різні, бо `p` просте і `a ≠ 0`. Пари `(a, b)` і пари `(r₁, r₂)` з `r₁ ≠ r₂` відповідають одна одній
взаємно однозначно, тож `(r₁, r₂)` — випадкова пара різних чисел. Серед `p − 1` можливих `r₂` число таких, що `r₂ ≡ r₁
(mod m)`, не більше `⌈p/m⌉ − 1 ≤ (p − 1)/m`. Звідси ймовірність колізії не більша за `1/m`.

Формула (11.5), теж загублена, задає родину multiply-shift з непарними `a`: `ℋ = { h_a : a непарне, 1 ≤ a < 2ʷ }`.
Теорема 11.5: ця родина 2/m-універсальна. CLRS радить на практиці саме її, бо швидкість важить більше, ніж удвічі
гірша оцінка ймовірності.

## Перевірте себе

**1. Erickson називає родину сталих функцій рівномірною, але марною. Яку властивість вона має, а якої не має?**

<details><summary>Відповідь</summary>

Якщо вибрати `a` випадково, кожен ключ потрапляє в кожну комірку з ймовірністю `1/m`, тож родина рівномірна. Але будь-
які два ключі потрапляють в одну комірку з ймовірністю 1, бо функція стала. Отже, вона не універсальна, і всі ключі
таблиці опиняться в одному списку. Для швидкості важить імовірність колізії пари, а не рівномірність окремого ключа.

</details>

**2. Обчисліть `h₃,₄(8)` для `p = 17`, `m = 6` з CLRS і поясніть, навіщо остача від `p` перед остачею від `m`.**

<details><summary>Відповідь</summary>

`3 · 8 + 4 = 28`, `28 mod 17 = 11`, `11 mod 6 = 5`. Остача від простого `p` робить відображення `k ↦ (ak + b) mod p`
взаємно однозначним на `ℤ_p`: різні ключі дають різні `r`, і пара `(r₁, r₂)` поводиться як випадкова пара різних
чисел. Лише після цього остача від `m` групує `p` значень у `m` комірок майже порівну. Без проміжного `mod p` лінійна
функція `ak + b` за модулем `m` мала б ті самі проблеми, що й метод ділення.

</details>

**3. Перевірте приклад CLRS з multiply-shift: чому `h_a(123456) = 67` при `ℓ = 14` і `w = 32`?**

<details><summary>Відповідь</summary>

`k·a = 327 706 022 297 664 = 76300 · 2³² + 17 612 864`. Остача від `2³²` — молодше слово `r₀ = 17 612 864`. Зсув
праворуч на `w − ℓ = 18` бітів лишає 14 старших бітів цього слова: `⌊17 612 864 / 2¹⁸⌋ = ⌊67,19⌋ = 67`.

</details>

**4. Навіщо Morin додає до полінома маркер `(p − 1)z^r`?**

<details><summary>Відповідь</summary>

Без маркера рядок `x₀ … x_{r−1}` і той самий рядок з дописаним нулем дали б однаковий поліном, бо доданок `0 · z^r`
нічого не змінює. Маркер `p − 1` відрізняється від будь-якого символу, бо символи не перевищують `p − 2`, і стоїть на
позиції, що залежить від довжини. Тому рядки різної довжини завжди дають різні поліноми, і теорема 5.4 обмежує
ймовірність їхньої колізії.

</details>

**5. У рисунку 11.6 CLRS після видалення 43 ключ 92 переїжджає з комірки 6 у комірку 5. Чому він не переїжджає в
комірку 3, звільнену першою?**

<details><summary>Відповідь</summary>

Коли 43 видалили, процедура йде праворуч від комірки 3 і першим знаходить ключ 93 у комірці 5. Для нього `g(93, 3) =
0` менше за `g(93, 5) = 2`, тож 93 переїжджає в комірку 3, і порожньою стає комірка 5. Далі процедура шукає кандидата
вже для комірки 5. Ключ 92 з домашньою коміркою 2 стоїть у комірці 6: `g(92, 5) = 3 < g(92, 6) = 4`, тож він
переїжджає в комірку 5. Комірка 3 на той момент уже зайнята ключем 93.

</details>

**6. BCtCI радить не змінювати масив, який уже лежить у множині як ключ. Що саме зламається в Python і що в
JavaScript?**

<details><summary>Відповідь</summary>

Python просто не дозволить покласти список у множину, бо список змінюваний і не має хешу; треба брати кортеж. У мовах,
що дозволяють змінювані ключі з хешем за вмістом, ключ лежить у комірці, обчисленій за старим вмістом. Після зміни
пошук обчислить нову комірку і не знайде його. У JavaScript `Set` порівнює масиви за тотожністю, тож зміна вмісту
нічого не ламає, але й знайти масив за вмістом не можна взагалі: потрібен той самий об'єкт.

</details>
