## Python — `heapq` — Heap queue algorithm

**Де читати:** сторінка модуля в довіднику бібліотеки. На сервері вона розбита на частини; версії 3.14 і 3.15 вже
містять опис максимальних куп.

| Що написано | Що це означає |
|-------------|---------------|
| Модуль реалізує «heap queue algorithm, also known as the priority queue algorithm». | Купа як реалізація пріоритетної черги, день 10. |
| Мінімальні купи — дерева, де кожен батько не більший за дітей; це **heap invariant**. У списку: `heap[k] <= heap[2*k+1]` і `heap[k] <= heap[2*k+2]`, «Elements are counted from zero». Найменший — `heap[0]`. | Формули з нумерацією з нуля, як у TypeScript. |
| Максимальні купи — навпаки: `maxheap[2*k+1] <= maxheap[k]`, найбільший — `maxheap[0]`. Список, відсортований за спаданням, — максимальна купа. | Новий текст 3.14. |
| `heappush`, `heappop`, `heapify` («in-place, in linear time»), `heappushpop`, `heapreplace`. | Побудова за лінійний час — алгоритм Флойда з дня 10. |
| `merge(*iterables, key=None, reverse=False)` зливає кілька відсортованих входів в один відсортований вихід ітератором, не завантажуючи все в пам'ять. | Готове злиття `k` потоків. |
| `nlargest` і `nsmallest`: рівносильні `sorted(iterable, key=key)[:n]`; найкращі для малих `n`; для великих швидше `sorted`, для `n == 1` — `min` і `max`. | — |
| **Priority Queue Implementation Notes**: чотири проблеми — стабільність при рівних пріоритетах; порівняння кортежів ламається, якщо завдання не порівнювані; зміна пріоритету; видалення завдання. | — |
| Рішення перших двох — запис з трьох елементів: пріоритет, лічильник, завдання. Лічильник робить рівні пріоритети стабільними і не дає дійти до порівняння завдань. Альтернатива — клас-обгортка `PrioritizedItem` з `@dataclass(order=True)`, де поле завдання не бере участі в порівнянні. | Приклад з `TypeError` у лекції. |
| Рішення двох останніх — словник «завдання → запис» і позначка видалення: старий запис позначають як видалений, а новий з іншим пріоритетом додають. | Ліниве видалення з розбору BCtCI в день 10. |

## Python — `bisect` — Array bisection algorithm

**Де читати:** сторінка модуля в довіднику бібліотеки.

| Що написано | Що це означає |
|-------------|---------------|
| Модуль підтримує список у відсортованому стані без пересортування після кожної вставки. Функції шукають **місце вставки**, а не конкретне значення, тому «never call an `object.__eq__` method», лише `__lt__`. | Пошук межі з дня 3: предикат «менший за `x`». |
| `bisect_left(a, x, lo=0, hi=len(a), *, key=None)`: якщо `x` уже є, місце вставки — ліворуч від усіх копій. Повернене `ip` ділить список так, що `all(elem < x for elem in a[lo : ip])` і `all(elem >= x for elem in a[ip : hi])`. | Інваріант пошуку межі, записаний як умова результату. |
| `bisect_right` — праворуч від усіх копій. | — |
| Параметр `key` додано в Python 3.10; у `bisect_left` він «not applied to the `x` value», щоб можна було шукати записи за ключем. | Тому в лекції передаємо 15, а не подію. |
| `insort_left` спершу шукає місце, потім викликає `list.insert`; тут `key` застосовується і до `x`. «The O(log n) search is dominated by the slow O(n) insertion step». | Вставка в список — зсув, як у дні 2. |
| Функції модуля не потокобезпечні. | — |

## Python — `Sorting Techniques`

| Розділ | Що там головне |
|--------|----------------|
| Sorting Basics | `sorted()` повертає новий список, `list.sort()` сортує на місці і повертає `None`. |
| Key Functions | Параметр `key` — функція одного аргументу, що обчислюється рівно раз на елемент. |

| Decorate-Sort-Undecorate | Старий прийом, він же Schwartzian transform: доповнити елементи ключами, відсортувати, прибрати ключі. Тепер його робить параметр `key`. |
| Comparison Functions | Компаратори в стилі C перетворюють на ключ функцією `functools.cmp_to_key`. |
| Partial Sorts | `min` і `max` — один прохід; `heapq.nsmallest` і `nlargest` — один прохід з `n` елементами в пам'яті; `heappush` і `heappop` — для пріоритетних черг. |

Стабільні кілька проходів — той самий прийом, що в лекції дня 6, а параметр `key` — той самий прийом, що «sorting with

## Go — `package container/heap`

**Де читати:** сторінка пакета в документації стандартної бібліотеки разом з двома прикладами: `IntHeap` і
`PriorityQueue`.

| Що написано | Що це означає |
|-------------|---------------|
| Купа — дерево, де кожен вузол — найменший у своєму піддереві; найменший — у корені, на місці 0. | — |
| Для пріоритетної черги з найвищим пріоритетом першим реалізують `Less` з «(negative) priority». | Максимальна купа через порядок. |
| `type Interface interface { sort.Interface; Push(x any); Pop() any }`. Інваріант: `!h.Less(j, i)` для `j` від `2*i+1` до `2*i+2`. | П'ять методів. |
| «Push and Pop in this interface are for package heap's implementation to call. To add and remove things from the heap, use heap.Push and heap.Pop». | Пастка з лекції: `h.Pop()` напряму повертає останній елемент, а не найменший. |
| `Init` — `O(n)`, можна викликати знову, коли властивість зламано. `Push`, `Pop` — `O(log n)`. | — |
| `Fix(h, i)` відновлює купу після зміни елемента на місці `i`; це дешевше, ніж `Remove` і `Push`. `Remove(h, i)` видаляє елемент на місці `i`. | `INCREASE-KEY` з CLRS. |
| Приклад `PriorityQueue`: кожен `Item` має поле `index`, яке «is maintained by the heap.Interface methods»: `Swap` оновлює номери обох елементів, `Push` записує номер нового. Метод `update` змінює пріоритет і викликає `heap.Fix(pq, item.index)`. | Індексована черга Sedgewick. |

## Go — `package sort` і `package slices`

**Де читати:** описи функцій сортування і пошуку.

| Функція | Що написано |
|---------|-------------|
| `sort.Sort(data)` | `O(n log n)` викликів `Less` і `Swap`; «The sort is not guaranteed to be stable». |
| `sort.Stable(data)` | Зберігає порядок рівних; `O(n log n)` викликів `Less`, але `O(n log n · log n)` викликів `Swap`. |
| `sort.Slice(x, less)` | Нестабільний: «equal elements may be reversed from their original order». Радить новіший `slices.SortFunc`. |
| `sort.SliceStable(x, less)` | Стабільний. Приклад сортує людей спершу за іменем, потім стабільно за віком. |
| `sort.Search(n, f)` | Найменший `i` з `[0, n)`, де `f(i)` правдива, або `n`; «not found» — це `n`, а не `−1`. |
| `slices.SortFunc(x, cmp)` | Нестабільний; `cmp` повертає від'ємне, нуль чи додатне і мусить задавати строгий слабкий порядок. |
| `slices.SortStableFunc(x, cmp)` | Стабільний; приклад зберігає порядок двох Alice з різним віком. |
| `slices.BinarySearch(x, target)` | Найраніша позиція, де `target` знайдено чи мав би стояти, і ознака, чи знайдено. |

Ціна стабільності в `sort.Stable` видна з кількості обмінів: зайвий множник `log n`. Тому нестабільне сортування —
вибір за замовчуванням, а стабільне просять явно.

## Перевірте себе

**1. Чому `heapq.heapify` працює за лінійний час, а `n` викликів `heappush` — ні?**

<details><summary>Відповідь</summary>

`heapify` будує купу знизу вгору, опускаючи вузли від останнього батька до кореня, і загальна робота обмежена сумою
висот вузлів, меншою за `n`, як у лекції дня 10. `n` вставок піднімають кожен новий елемент на глибину до `log n`, і в
найгіршому випадку сума глибин — `Θ(n log n)`.

</details>

**2. Документація `bisect_left` описує результат умовою на два зрізи. Перепишіть її словами пошуку межі з дня 3.**

<details><summary>Відповідь</summary>

Предикат «елемент не менший за `x`» монотонний на відсортованому списку: хибний на префіксі і правдивий на решті.
`bisect_left` повертає межу — першу позицію, де він правдивий. Умова документації каже саме це: усі елементи ліворуч
від `ip` менші за `x` (предикат хибний), а всі від `ip` — не менші (предикат правдивий).

</details>

**3. Чому в `insort_left` функцію `key` застосовують до `x`, а в `bisect_left` — ні?**

<details><summary>Відповідь</summary>

`bisect_left` шукає місце для значення, яке ви передаєте вже як ключ: наприклад, час 15, щоб знайти першу подію не
раніше нього. `insort_left` вставляє в список сам запис, тож мусить спершу обчислити його ключ, щоб знайти місце, а
потім вставити запис цілим. Документація формулює це як «applied to x for the search step but not for the insertion
step».

</details>

**4. Навіщо в прикладі `PriorityQueue` Go поле `index` і чому його оновлює `Swap`?**

<details><summary>Відповідь</summary>

Щоб змінити пріоритет елемента і викликати `heap.Fix`, треба знати, де цей елемент зараз лежить у купі. Елементи
переміщуються лише обмінами, а всі обміни робить метод `Swap`, тож саме там і оновлюють номери обох переставлених
елементів. `Push` записує номер нового елемента, `Pop` позначає вилучений номером −1.

</details>

**5. Чому `sort.Stable` робить `O(n log n · log n)` обмінів, а не `O(n log n)`?**

<details><summary>Відповідь</summary>

`sort.Stable` отримує лише `sort.Interface`, тобто методи `Len`, `Less` і `Swap`. Скопіювати елемент у допоміжний
масив через цей інтерфейс неможливо, тож стабільно переставляти елементи доводиться лише обмінами сусідніх ділянок, а
це дорожче, ніж копіювання в сортуванні злиттям з дня 7. Документація прямо називає оцінку `O(n log n · log n)`
обмінів і радить `slices.SortStableFunc`, який працює зі зрізом напряму і часто швидший.

</details>

**6. Функція повертає `big[:3]` з великого зрізу, а великий зріз більше ніде не використовується. Що каже Go 101 про
пам'ять?**

<details><summary>Відповідь</summary>

Підзріз ділить базовий масив з великим зрізом, тож поки маленький зріз досяжний, весь великий базовий масив лишається
в пам'яті. Go 101 називає це «kind-of memory leaking». Якщо потрібні лише три елементи, їх варто скопіювати в новий
зріз, наприклад `slices.Clone(big[:3])`, і тоді великий масив звільниться.

</details>
