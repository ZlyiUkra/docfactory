# alpine — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Alpine.js за офіційною документацією всіх його версій — від 0.1
(2019) до поточної 3.x — разом із CSP-збіркою `@alpinejs/csp`: її кодом і тестами на кожному релізі 3.x, нотатками
релізів і історією версій ядра, CSP-збірки й плагінів у реєстрі npm. Код спільний і лежить у `../../engine/`,
`../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо CSP-збірка окремо

Alpine виконує вирази з атрибутів (`x-on:click="count++"`) через `new Function`, і політика Content-Security-Policy без
`'unsafe-eval'` це забороняє. CSP-збірка — та сама Alpine, у якій вирази обчислює власний код замість `new Function`.
Що саме він приймає, залежить від версії, і різниця велика:

- **до 3.13.3** пакета в npm не було, збірку будували з вихідного коду; обчислювач умів лише назву властивості
  (`x-on:click="increment"`), без операторів і викликів;
- **3.13.3** — перша публікація `@alpinejs/csp`; **3.14.1** — вкладені властивості (`user.name`);
- **3.15.0** — збірку переписано навколо власного розбирача виразів `parser.js`: літерали, оператори, присвоєння,
  виклики методів; **3.15.1** — доступ до глобальних об'єктів за замовчуванням вимкнено;
- **3.15.2–3.17.3** — виправлення розбирача: присвоєння властивостям, скорочене обчислення `&&` і `||`,
  Unicode-escape у рядках, зарезервовані слова як імена властивостей, запуск у пісочниці iframe.

Сайт описує збірку однією сторінкою «CSP», і вона за кодом не встигає: перелік «що не підтримується» досі називає
присвоєння властивості (`user.name = 'John'`). Тести розбирача кажуть інакше: у 3.15.0–3.15.1 таке присвоєння
працювало, у 3.15.2–3.15.11 тест «should not handle property assignment» вимагав помилки, а з 3.15.12 тест «should
handle scope property assignment» знову перевіряє його як робоче — крім властивостей DOM-об'єктів («should block DOM
node property assignment»). Тож у корпусі поруч зі сторінкою — сам код збірки й тести, поділені на випадки: кожен
тест несе версії, у яких він був, і відповідає на «з якої версії це працює» точніше за текст сайту.

Разом 704 документи; фрагментів в індексі — 2 043 (`expected_passages` у `checks.json`). 87 документів власних
фрагментів не дають: їхні розділи дослівно ті самі, що в сусідніх редакціях, і злилися з ними разом із версіями.

Редакцій коду небагато: `parser.js` — 7 (3.15.0–3.17.4), тести розбирача — 5, обчислювач — 6, точка входу — 6.

Замір `quality` на першому корпусі: по словах 8 із 10, за змістом 7, разом 7; десятка «як модель» — 10 із 10.
Промахи першої десятки (переказ питання своїми словами):

- **«share data between components that are far apart»** — пошук приносить сторінки `x-data` і `$dispatch`, а не
  `Alpine.store`: у переказі немає слова «store».
- **«run setup code when a component starts»** — першими стоять розділи `x-init` старого README 2.x і
  `init()`-функції `Alpine.data`; останнє — теж правильна відповідь, але ціль — сторінка `x-init` 3.x.
- **«hide markup until the library has finished initializing»** — по словах `x-cloak` знаходиться, а за змістом
  першими стоять нотатки релізів, тож злиття сторінку губить.

Ціль запиту про вирази під CSP — уся сторінка «CSP»: вона вся про це питання, і перший замір з вужчою ціллю (розділи
«What's supported») давав 6 із 10 при правильній видачі. Поле `max_per_doc` заміряно 0/1/2/3: разом 6, 5, 5, 6 на
десятці до цієї правки, «як модель» 10 скрізь — поле не ввімкнене.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Перелік усіх знімків лежить саме
  тут, у полі `tags` джерел `alpine-docs` і `alpine-csp-code`: оновлювач не питає в GitHub, які теги існують.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df alpine <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація всіх версій | дерево кожного знімка через GitHub API, текст — `raw.githubusercontent.com` | `ghdocs-history` |
| код і тести CSP-збірки | те саме, файли за виразами `include` | `ghcode-history`, новий |
| нотатки релізів | GitHub API | `ghreleases` |
| реєстр npm | registry.npmjs.org, одне звернення на пакет | `npm-versions` |

Читач `ghcode-history` додано разом із цим примірником (`engine/readers/ghcodehistory.py`). `ghcode` бере дерево
одного тегу, а `ghdocs-history` бере багато тегів, але читає кожен файл як markdown. Новий читач робить для коду те,
що `ghdocs-history` для документації: одна пара «шлях, вміст» — один документ з усіма версіями, де файл був саме
таким. З полем `outline` файл JavaScript ділиться на розділи: тести — за `describe`, `it` і `test`, код — за класами,
функціями й методами (`Parser.parseAssignment()`). Без цього тести розбирача були б одним фрагментом на 32 тисячі
символів, з якого вектор бачить лише початок.

Особливості, які варто знати:

- **Сайт — не першоджерело.** alpinejs.dev збирається з теки `packages/docs/src/en` репозиторію. Тож текст береться
  прямо зі знімка, а адреса в шапці документа — blob на GitHub саме тієї версії: сайт показує лише поточну редакцію.
  Платних компонентів сайту (`/component/…`) тут немає.
- **Де лежала документація.** 0.x–2.x — уся документація в кореневому `README.md` (переклади `README.ja.md` та інші
  не беруться); у README 2.x директиви стоять підрозділами розділу «Community Projects», тож ключі розділів там
  виглядають як `readme#community-projects/x-spread`. З 3.0 — сторінки сайту: `directives/`, `magics/`, `globals/`,
  `plugins/`, `essentials/`, `advanced/` і посібник `upgrade-guide.md`.
- **Знімки без тегів.** 3.0.0–3.0.5 тегів не мають: їх заміняють коміти, на яких `package.json` ядра несе цю
  версію (3.0.0, 3.0.1, 3.0.4, 3.0.5); для 3.0.2 і 3.0.3 такого коміту немає. `2.x` — гілка: після 2.8.2 у ній ще 53
  коміти з правками README. Безіменні теги `v`, `v0.2` і `v2` не випуски й не беруться.
- **Одна версія на все.** Ядро, CSP-збірка й плагіни виходять разом під спільним тегом `vX.Y.Z`, тож фільтр
  `version: "3.15"` однаково лишає сторінки сайту, код збірки й тести лінії 3.15.
- **Що з коду не взято.** HTML-сторінки, на яких Cypress запускає тести CSP, і `packages/csp/package.json` — 38
  редакцій, що відрізнялися лише номером версії; залежності кожної версії є в документах реєстру npm.
- **README пакетів у npm порожні** (у всіх, крім застарілого `@alpinejs/trap`), тож читач `npm-readme` не
  потрібен: реєстр дає лише версії, дати, мітки й залежності.
- **Редакції того самого файла зливаються (`revision_suffix`)**: ім'я документа несе хеш вмісту, і без поля незмінний
  розділ двох редакцій лишався б двома фрагментами.

## Межі, про які треба пам'ятати

Livewire, htmx, Vue і самої специфікації Content-Security-Policy тут немає (CSP як стандарт — у примірниках
`webstandards` і `owasp`). Опція `allowGlobals` згадана лише в нотатці релізу 3.15.1: на сторінці CSP її немає. Гілку
`main` після 3.17.4 (підняття версії до 3.17.5 без тегу) не взято: знімки — лише релізи.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/alpine-corpus-2026-10-10.tar.gz` (0,9 МБ, 704 тексти і паспорт;
перед видаленням розпакований окремо й звірений із диском — нуль розбіжностей). В історії git текстів немає ніде.
Архів лежить лише на цій машині.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/alpine-corpus-2026-10-10.tar.gz -C instances/alpine
./df alpine smoke
```

**Як знову винести** — після оновлення, коли `vectors` і `smoke` пройшли (вони ж збирають свіжий кеш):

```
ls -l instances/alpine/index/passages.json       # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/alpine-corpus-РРРР-ММ-ДД.tar.gz -C instances/alpine corpus
find instances/alpine/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/alpine/index/passages.json > instances/alpine/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти» і «Як повернути тексти».

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»): звірка індексу з документами і звірка паспорта з файлами.

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/alpine/index/passages.json.gz`,
далі `./df alpine vectors` заллє колекцію Qdrant (~2 хвилини).

## Установка venv

```
cd instances/alpine
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df alpine sources --why   # перелік джерел і білий список
./df alpine refresh         # завантажити все задеклароване (~20 хвилин)
./df alpine manifest        # оновити паспорт
./df alpine setup           # Qdrant чи пошук лише по словах
./df alpine vectors         # залити корпус у docs-alpine (~2 хвилини)
./df alpine smoke           # перевірки
```

Перші ~5 хвилин `refresh` журнал мовчить, а `corpus/` порожній: читач проходить дерево кожного з 166 знімків і лише
потім починає писати файли; код CSP-збірки — ще ~95 дерев. Без токена GitHub перелік ішов би годинними вікнами по 60
звернень.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df alpine serve          # порт 8815
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8815/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user alpine-docs http://127.0.0.1:8815/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `alpine-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
