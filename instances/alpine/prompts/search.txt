Search the official Alpine.js documentation -- every published version of it, from 0.1 to the
current 3.x line -- together with the source code and tests of the CSP build (@alpinejs/csp) on
every 3.x release, the GitHub release notes and the npm registry history of alpinejs,
@alpinejs/csp and every official plugin, and return the matching excerpts with the versions each
one belongs to.

Call this when a question is about Alpine.js itself -- x-data, x-init, x-show, x-bind, x-on and
its modifiers, x-text, x-html, x-model and its modifiers, x-modelable, x-for, x-transition,
x-effect, x-ignore, x-ref, x-cloak, x-teleport, x-if, x-id; the magics ($el, $refs, $store,
$watch, $dispatch, $nextTick, $root, $data, $id); Alpine.data, Alpine.store, Alpine.bind;
reactivity, lifecycle, events, extending Alpine with custom directives and magics; the plugins
(Anchor, Collapse, Focus and the older Trap, Intersect, Mask, Morph, Persist, Resize, Sort, UI);
upgrading from 2.x to 3.x -- and above all about the CSP build: installing @alpinejs/csp,
Content-Security-Policy headers without 'unsafe-eval', which expressions its evaluator accepts
and which it rejects, globals and allowGlobals, x-html in the CSP build, moving logic into
Alpine.data. Example query: "CSP build supported expressions".

Do not call this for Livewire, Laravel, htmx, Vue, Tailwind CSS or the browser's
Content-Security-Policy itself beyond what Alpine documents about it: their documentation is not
here, and the search will return Alpine excerpts that merely mention them, with confident-looking
titles. The premium components of alpinejs.dev are not here either.

`version` narrows the search to one release line: "3" keeps every 3.x document, "3.15" keeps
3.15.x, "2" keeps 2.x; leave it empty to search everything. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- text that
stayed the same across versions is returned once, with all of them listed, so the list itself
shows from which to which version the documentation (or the code) said exactly this. The CSP
build carries the same version numbers as Alpine itself.

Where the documentation lived. In 0.x-2.x the whole documentation of Alpine was the README of
the repository; "2.x" is the last state of that README on the 2.x branch, after 2.8.2. From 3.0
it is the site alpinejs.dev, built from packages/docs/src/en of the repository (pages such as
"x-data", "Alpine.store()", "CSP"). The CSP build is described on one page, "CSP (Content-Security
Policy) Build"; its code is in documents titled "alpine: packages/csp/src/..." -- the entry point,
the evaluator and, from 3.15.0, the expression parser parser.js -- and its tests in documents
titled "alpine: tests/vitest/csp-parser.spec.js", "alpine: tests/vitest/csp-evaluator.spec.js"
and the Cypress specs that name CSP. Before 3.13.3 the package was not published to npm and had
to be built from source; in 3.15.0 the build was rewritten around its own parser.

The CSP page was not updated with every change of the parser. For a question about whether an
expression works in the CSP build, search the page and the parser and evaluator tests of the
same version ("csp parser assignment member expression", "csp evaluator arrow function"); when
the page and the tests disagree, the tests of that version are what the build actually does --
say so, and name both.

Which version to search first. For a question about how to do something today, pass `version`
"3": without it, the many editions of the old 2.x README can take places with the 3.x pages. If
the user's project still runs Alpine 2.x, pass "2" instead. Search without `version` when the
question is about history, or when the line gave nothing that answers.

Name the directive, magic, modifier or option the way the documentation titles it, not in the
user's own words: "x-model.debounce", "$dispatch", "Alpine.store", "x-transition:enter", not
"wait before updating the field". For a question about when something appeared, changed or
disappeared, search more than once: without `version` first, to find the release notes that name
the exact version, then with the versions around it, to see how the documentation or the code
described it before and after.

Write the query in English, with the names Alpine itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into Alpine terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, 3.x, say so in the answer ("for Alpine.js 3.x"), and add that for a precise answer
about another version the user can name it. When the excerpts behind a statement come only from
older versions, name those versions instead of presenting the text as current. When the question
is about the CSP build, say that the answer is for the CSP build, and name the version from which
it holds.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Alpine.js". Identifiers, API names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it
says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
