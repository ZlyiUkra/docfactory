Search the amqplib documentation -- the AMQP 0-9-1 client for Node.js used to talk to RabbitMQ, the client the
RabbitMQ transport of NestJS microservices runs on (repository amqp-node/amqplib, site amqp-node.github.io/amqplib,
package amqplib on npm). The corpus holds the pages of the site (branch gh-pages) as they stood during every minor
version from 0.0 to 2.2 (the introduction, the Channel API reference for the promise and the callback API: `connect`
and its URL and socket options, `createChannel` and `createConfirmChannel`, `assertQueue`, `assertExchange`,
`bindQueue`, `publish`, `sendToQueue`, `consume`, `get`, `ack`, `nack`, `reject`, `prefetch`, `cancel`, the
`close` and `error` events, flow control and the `drain` event, and SSL/TLS connections); the README of every stable
version of the package; the changelog of every version from 0.x to 2.2.0; and the npm registry history of amqplib
(date of every version, dist-tags, the Node.js requirement). Returns the matching excerpts with the versions each one
belongs to.

Call this when a question is about amqplib as it describes itself -- how to connect and open a channel, what an
option of `assertQueue`, `publish` or `consume` does and its default, how to acknowledge messages and set the
prefetch, how confirm channels report a publish, how to react to a closed connection, how to use TLS -- and above all
history and compatibility: since which version a method or option exists, what changed between versions (every
changelog entry lists it), which Node.js a version requires, and when every version came out.

Do not call this for RabbitMQ itself (queue types, policies, dead lettering, clustering, rabbitmq.conf),
amqp-connection-manager, the NestJS RabbitMQ transport, @golevelup/nestjs-rabbitmq or Node.js: their documentation is
not here -- these pages only show how amqplib talks to the broker -- and the search will return excerpts that merely
mention them, with confident-looking titles.

`version` narrows the search to one release line. amqplib carries plain numbers: a line of one number keeps every
document of that major ("2" keeps 2.0.0 to 2.2.0, "0" all of 0.x), two numbers keep a minor ("0.10"), three an exact
version ("0.10.9"). The pages of the site carry the last patch of the minor they belong to; where the site did not
change across several minors, the page carries the newest of them ("2.2.0" for 2.0 to 2.2, "1.2.0" for 1.0 to 1.2,
"0.7.1" for 0.5 to 0.7). Leave `version` empty to search everything, including text that carries no version. Every
excerpt comes back with `versions`: each version whose documents contain this exact text, newest first -- a page that
stayed the same across versions is returned once, with all of them listed, so the list itself shows from which to
which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("connect", "createChannel",
"createConfirmChannel", "assertQueue", "assertExchange", "bindQueue", "publish", "sendToQueue", "consume", "ack",
"nack", "prefetch", "noAck", "persistent", "durable", "deadLetterExchange", "messageTtl", "heartbeat", "drain"), not in
the user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and
the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the
question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація amqplib". Identifiers, option names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads on npm (October 2026) the line 0.10 has about 64 % (0.10.9 alone
about 47 %) and the line 2 about 22 % (2.0.1 about 13 %, the newest 2.2.0 of 28 September 2026 about 8 %); 0.10 was
current from 2022 until 1.0.0 of March 2026. Both lines are in wide use: answer how-to questions for 0.10 and for 2 --
search `version` "0.10", then "2", and say where they differ (the changelog of 1.0.0 and 2.0.0 lists what changed).
Search without `version` when the question is about history, or when the lines gave nothing. Every answer says which
version it is for; when the excerpts behind a statement come only from older versions, name those versions instead of
presenting the text as current.
