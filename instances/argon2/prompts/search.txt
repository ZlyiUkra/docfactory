Search the Argon2 password hashing documentation for Node.js -- the README, TypeScript
declarations and GitHub release notes of every stable version of the npm package `argon2`
(node-argon2, native bindings to the reference C implementation) and its GitHub wiki (Options,
Migrating from another hash function); the README, TypeScript declarations, changelog and
release notes of every stable version of `@node-rs/argon2` (Rust bindings, prebuilt for every
platform, no node-gyp); the npm registry history of both packages; and the reference
implementation P-H-C/phc-winner-argon2 (its README at every release, its changelog and the
Argon2 specification, version 1.3, by the designers of the algorithm) -- and return the
matching excerpts with the versions each one belongs to.

Call this when a question is about these packages or the algorithm as they describe it --
hash(), verify(), needsRehash(), hashRaw(), hashSync()/verifySync() of @node-rs/argon2, the
options (type / algorithm: argon2d, argon2i, argon2id; memoryCost, timeCost, parallelism,
hashLength / outputLen, salt, secret, associatedData, version, raw), the encoded hash string
($argon2id$v=19$m=...,t=...,p=...), defaults per version, building the native module
(node-gyp, prebuilt binaries, Alpine/musl, ARM), migrating stored bcrypt hashes, the C library
and command-line utility (argon2 -id -t -m -p -l), the memory-hard design, Argon2d vs Argon2i
vs Argon2id, tradeoff attacks, recommended parameters of the specification -- and above all
history and compatibility: since which version an option or function exists, what changed
between versions, which versions run on which Node.js (the `engines` field of every version is
written in the npm registry documents: argon2 0.6 Node 4, 0.17 Node 6, 0.20 Node 8, 0.26.1 Node
10, 0.28.0 Node 12, 0.28.7 Node 14, 0.40.1 and newer Node 16.17; @node-rs/argon2 Node 10).
Example query: "engine changed node".

Do not call this for bcrypt, scrypt, PBKDF2, the node:crypto module (crypto.argon2 since Node
24.7), RFC 9106, the OWASP password storage guidance, NestJS, Passport or any framework: their
documentation is not here, and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line, and it applies to both packages at once:
argon2 lines are 0.x ("0.45" keeps every 0.45.x document of argon2), @node-rs/argon2 lines are
1.x and 2.x ("2" keeps every 2.x document of @node-rs/argon2), releases of the reference
implementation are dates ("20190702"). Leave it empty to search everything, including the wiki,
the changelog of the reference implementation and the specification, which carry no version.
Every excerpt comes back with `versions`: each version whose documents contain this exact text,
newest first -- text that stayed the same across versions is returned once, with all of them
listed, so the list itself shows from which to which version the documentation said exactly
this.

Write the query in English, with the names the documentation itself uses ("memoryCost",
"timeCost", "parallelism", "needsRehash", "argon2id", "hashLength", "outputLen"), not in the
user's own words. Everything here is English -- the excerpts, the word index and the meaning
index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into the terms of the
documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version.
Every point names the package, the version and the document it rests on; a point the excerpts do
not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian
engineer writes, not as a translation from English: plain technical prose, and the Ukrainian
word wherever one exists -- "уривок", not "ексерпт"; "хешування", "сіль", "застарілий". Never
call this set of documents "корпус" -- say "документація argon2". Identifiers, option names,
package names and titles stay in English, spelled exactly as the documentation spells them.
Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut,
read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which package and version to search first. The two packages do the same job with different
APIs; when the user did not say which one they use, answer for `argon2` (the more widely used),
mention that `@node-rs/argon2` exists, and say so. For `argon2`, the most downloaded versions are
0.44.0 and 0.45.1 almost equally: pass `version` "0.45" for how things are done today and
answer for both 0.44 and 0.45 when they differ. For `@node-rs/argon2`, pass "2". Search without
`version` when the question is about history, about the algorithm or its parameters (the
specification and the wiki carry no version), or when the line gave nothing. Every answer says
which package and version it is for; when the excerpts behind a statement come only from older
versions, name those versions instead of presenting the text as current. argon2 1.0.0-alpha.1
(npm tag `next`, Node 24.7 and newer) is a pre-release: only the registry lists it.
