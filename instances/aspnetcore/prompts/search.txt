Write the query in English, with the names the documentation uses (WebApplication, IServiceCollection,
AddAuthentication, AddJwtBearer, MapGroup, RequireAuthorization, [Authorize], EditForm, @rendermode,
HubConnectionBuilder, UseExceptionHandler, IHttpClientFactory, HttpContext, ControllerBase, ActionResult,

English, and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or
any other non-latin script matches nothing and comes back with `found: 0`. When the user asks in another
language, translate the question into ASP.NET terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "проміжне ПЗ" or "middleware" as the page names it; "конвеєр",
"маршрутизація", "автентифікація", "авторизація", "впровадження залежностей". Never call this set of
documents "корпус" -- say "документація ASP.NET". Type, member, package, attribute and option names stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. ASP.NET Core documents carry the product version: the site pages and the API
reference "10.0", "9.0", ..., "3.1", "3.0", "2.2", "2.1", "2.0", "1.1", "1.0" (and "2.3", the packages for
.NET Framework of January 2025, "3.2" for Blazor WebAssembly 3.2), package and release documents the exact
release ("10.0.13"). Pass "10.0" for the whole 10.0 line, or "10" for every 10.x; a text that did not change
across versions carries every one of them. Classic ASP.NET numbers each product on its own, so its versions
carry the product as a prefix: "mvc-5.2", "webapi-5.3", "webpages-3.3", "signalr-2.4", "identity-2.2",
"katana-4.2", "netfx-4.8.1" (System.Web), "webstack-..." and "aspnet-..." (other packages). Web API is
numbered by its packages: Web API 1 is "webapi-4.0", Web API 2.2 is "webapi-5.2". Of the classic
learn.microsoft.com/aspnet pages, the SignalR, MVC and Web API guides carry the lines they were written for
("signalr-1.0" to "signalr-1.2" for SignalR 1.x, "signalr-2.0" to "signalr-2.4" for SignalR 2, "mvc-1.0" to
"mvc-5.3", "webapi-4.0" to "webapi-5.3"), so "signalr-2" finds the SignalR 2 guides and not the 1.x ones;
overview pages, upgrade guides and the Web Forms, Web Pages and Identity pages carry no version -- search them
without one, because any version filters them out. When the user names a version, pass it into `version`;
never put it into the query text. Without a version, answer for the newest ASP.NET Core (10.0) and say so; for
classic ASP.NET, for the newest release of that product.
