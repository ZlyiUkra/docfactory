# Оновлення корпусу astro

Три різні роботи, які легко переплутати: звичайне оновлення поточної документації, вихід нової лінії і збирання
примірника з нуля. Порядок усередині кожної важливіший за самі команди, тому кроки пронумеровані.

Головне правило: **знімок лінії робиться на коміті дня її виходу, а не «колись потім».** Репозиторій
`withastro/docs` тримає всю історію, тож фізично знімок можна зробити й через рік — цим Astro відрізняється від
доменів, де сайт показує лише поточну версію. Але «можна» не означає «вийде саме те»: за місяць після виходу лінії
в документацію вже влиті правки наступної, і коміт, узятий навмання, дасть суміш двох ліній. Тому дата береться з
тега `astro@X.Y.0`, а коміт — останній на цю дату.

Друге правило: **імена документів зводяться самі, руками їх не чіпають ніколи.** До лінії 2.0 глави лежали в
`src/pages/en/`, з 2.1 — у `src/content/docs/en/`. Поле `root` у джерелі велить знімати саме цей префікс, тож в
обох випадках ім'я документа починається з `en/`, і та сама сторінка сусідніх ліній зливається у видачі в один
уривок із переліком версій. Якщо `root` помилитися, зовні нічого не зламається — просто однаковий текст
перестане зливатися, і на питання «з якої лінії це так» пошук відповість десятком копій замість одного рядка.

Третє правило: **нічого не видаляється.** Сторінка, яку прибрали в сьомій лінії, лишається в корпусі під своєю
версією: питання «як це працювало в третій» не має ламатися через те, що главу з сайту зняли. Ані `refresh`, ані
`vectors`, ані `manifest` нічого не стирають самі.

Четверте: **токен GitHub потрібен лише для збирання.** Він лежить рядком `GITHUB_TOKEN=…` у `.env` цієї теки,
читається тільки звідти й іде тільки на `api.github.com` — подробиці в [README.md](README.md). Для оновлення
каталогів чи однієї лінії він не обов'язковий; для збирання з нуля без нього доведеться розкладати роботу на
годинні вікна.

## 1. Звичайне оновлення

Раз на кілька тижнів, або коли в релізах щось помітне.

```
./df astro refresh astro-current astro-releases astro-blog astro-case-studies
./df astro refresh astro-integrations astro-themes astro-showcase
./df astro manifest
./df astro vectors
./df astro smoke
# Ctrl+C у терміналі з serve, і знову: ./df astro serve
```

Перший рядок бере поточну документацію з гілки `main`, нові релізи й нові записи блогу. Другий — каталоги: вони
живуть власним життям, версії не несуть і міняються частіше за документацію (теми додають щотижня, вітрина росте
постійно). Обидва рядки безпечні: `refresh` переписує лише те, що змінилося, решту лишає як є.

Заморожені знімки цими командами не зачіпаються взагалі — оновлювач їх навіть не питає, і це навмисно: коміт
закріплений, отже текст незмінний, отже звертатися до мережі нема за чим.

Перезапуск `serve` — не формальність: корпус сервер читає один раз, на старті, тож поки старий процес живий,
клієнт бачить стару копію, хоч би що лежало в `corpus/`. Адреса при цьому не міняється, тож ані `.mcp.json`, ані
сесію Claude Code чіпати не треба — він перепід'єднається сам.

Якщо `smoke` скаржиться на число фрагментів — це не поломка, а наслідок того, що документація підросла. Нове число
записують у `checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Вийшла нова лінія

Astro випускає мінорну лінію раз на кілька тижнів, мажорну — раз на рік із гаком. Для корпусу різниці немає:
знімок робиться однаково.

**Крок 1. Взяти дату виходу.** Дата — це дата тега `astro@X.Y.0` у `withastro/astro`. Її видно на сторінці релізів,
але надійніше взяти з самого репозиторію, щоб не гадати про часові пояси.

**Крок 2. Знайти коміт документації на цю дату.** Через API це одне звернення, але зручніше й дешевше — клоном без
файлів, бо ліміту він не витрачає:

```
git clone --bare --filter=blob:none https://github.com/withastro/docs.git /tmp/docs.git
git -C /tmp/docs.git rev-list -1 --before=РРРР-ММ-ДДT23:59:59 HEAD
```

**Крок 3. Оголосити джерело.** У `sources.json` додається запис на зразок сусідніх: `id` виду `astro-7.4`,
`reader` — `ghdocs-mdx`, `version` — `7.4`, `frozen: true`, `folders` і `root` — `src/content/docs`, `within` —
префікс `raw.githubusercontent.com` із тим самим SHA. SHA пишеться повністю: коротка форма колись стане
неоднозначною.

**Крок 4. Перевірити оголошення й перелік.**

```
./df astro sources --why
./df astro list astro-7.4
```

Перелік має показати кількість глав, близьку до попередньої лінії. Якщо їх удесятеро менше — помилилися текою;
якщо нуль — читач узагалі нічого не знайшов, і далі йти не можна.

**Крок 5. Завантажити й перевірити.**

```
./df astro refresh astro-7.4
./df astro manifest
./df astro vectors
./df astro smoke
```

Поточну гілку `main` оновлювати окремо не треба — вона й так у першому рядку звичайного оновлення, і після виходу
лінії показує вже її текст.

## 3. Збирання з нуля

Робота на ніч: документації в корпусі понад двадцять тисяч документів, і при паузі в секунду це близько восьми
годин.

**Крок 1. Токен.** Без нього 60 звернень до API на годину, а знімків вісімдесят із гаком, і кожен коштує одне
звернення. Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки.

**Крок 2. Каталоги окремо.** Вони не залежать ні від API, ні від токена, і збираються за чверть години:

```
./df astro refresh astro-integrations astro-themes astro-showcase
```

**Крок 3. Усе інше одним прогоном.** Заморожені знімки треба назвати поіменно — оновлювач їх сам не питає:

```
IDS=$(grep -o '"id": "astro-[0-9.]*"' instances/astro/sources.json | cut -d'"' -f4)
nohup ./df astro refresh $IDS > /tmp/astro-refresh.log 2>&1 &
```

**Крок 4. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються, добереться
лише відсутнє.

**Крок 5. Паспорт, вектори, перевірки.**

```
./df astro manifest
./df astro setup
./df astro vectors
./df astro smoke
./df astro quality
./df astro serve
```

Останній рядок — окремий термінал, і його лишають жити; під'єднання до Claude Code описане в
[README.md](README.md), розділ «Спосіб Б».

## Що робити, коли щось не так

**`збій: HTTP 403` на `api.github.com`.** Вичерпано ліміт звернень. З токеном це майже неможливо; без нього —
зачекайте до початку наступної години й повторіть із `--missing`.

**`збій: HTTP 429` на `raw.githubusercontent.com`.** Занадто часті звернення до CDN. Підніміть `pause_sec` у
`config.json` і повторіть із `--missing`; перекачувати вже записане не доведеться.

**`у теках … немає жодного дозволеного .md або .mdx`.** Читач не знайшов глав: або тека названа не та (до 2.1 це
`src/pages/en`, потім `src/content/docs/en`), або коміт узято з часів, коли англійської документації ще не було.
Лінії до 0.23 саме такі, і знімків для них немає навмисно.

**`GitHub обрізав дерево`.** Репозиторій виріс настільки, що API віддає перелік файлів неповним. Читач у цьому разі
відмовляється працювати, і це правильно: неповний перелік тихо дав би корпус із дірками.

**Каталог тем чи вітрини став порожнім.** Змінилася розмітка сайту: читач `astro-catalog` бере вміст `<main>` і
відкидає розділи, названі в `skip_sections`. Якщо на сайті перейменували заголовки, у корпус поїде або шум, або
нічого. Перевіряється очима, одним документом: `head -20 corpus/astro-themes--page-001.txt`.

**Пошук відповідає десятком однакових уривків різних ліній.** Зламалося зведення імен — найімовірніше в новому
джерелі помилилися полем `root`. Текст при цьому цілий, перекачувати нічого не треба: виправте `root` і повторіть
`refresh` цього джерела.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df astro quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія — 7.** `prompts/search.txt` (абзац про те, з якої версії шукати) і `prompts/agent.txt` велять на
  питання «як зараз» шукати з `version "7"`; у `checks.json` `quality_model` дев'ять записів із десяти стоять на
  "7". Нова лінія — заміна в усіх трьох місцях (розділ «2. Вийшла нова лінія» вище).
- **Правила промпту, що вже є:** спершу лінія 7, без версії — лише історія, анонси й каталоги; «що є для задачі» — у
  каталогах, «як це працює» — у документації; на видачу зі сторінок помилок — шукати ще раз назвою гайду; кожна
  відповідь каже, для якої версії вона, а без названої версії — відповідає для 7.x і пропонує назвати свою.
- **Останній результат:** `quality_model` 8 із 10 після правила про лінію 7 (коміт «astro: промпт веде спершу в
  лінію 7»); перша десятка — у README, абзац «Замір `quality`».
