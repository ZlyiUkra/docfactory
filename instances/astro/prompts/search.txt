Search the official Astro documentation -- every release line of it, from 1 to the
current 7 -- together with the release notes of every Astro release, the Astro blog,
the case studies, and the catalogs of integrations, themes and showcase sites. Every
excerpt comes back with the version it belongs to.

Call this when a question is about Astro itself: components and the `.astro` syntax,
pages and routing, layouts, content collections, islands and partial hydration,
`client:` directives, server-side rendering and adapters, actions, sessions,
middleware, endpoints, image and font handling, view transitions, environment
variables, configuration, the CLI, upgrading between lines. Call it above all when the
question is about a particular version: how a thing was configured in that line, what
changed between lines, what was deprecated or removed and what replaced it, and what
breaks on upgrade. Example query: "content collections defineCollection schema
loader".

Do not call this for React, Vue, Svelte, Solid, Preact or Alpine internals, for Vite,
Tailwind, Starlight, Node.js, Cloudflare, Netlify or Vercel themselves, or for any
third-party package: their documentation is not here. Astro chapters mention those
names constantly, so a search will return confident-looking excerpts that describe
only Astro's own integration layer and nothing about the tool itself.

`version` narrows the search to one release line: "5" keeps every 5.x document, "2"
keeps 2.x, and so on; leave it empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first.
Text that stayed identical across lines is returned once with all of them listed, so
the list itself shows from which line to which line the documentation said exactly
this -- and a short list is itself the answer to "when did this change".

What is here, and what is not. Documentation is present for lines 1 through 7, each
taken from the documentation repository as it stood on the release day of that line;
line 7 is the current text. Line 1 is the smallest -- 72 chapters against roughly 420
today -- and everything before it is gone: Astro had no stable release and no
documentation site worth the name. Release notes cover every `astro@` release. The
blog, the case studies and the three catalogs carry no version at all, by intent: an
announcement of 5.0 speaks about the lines before it too.

The catalogs answer a different kind of question than the documentation does.
Integrations are grouped by category -- adapters, loaders, frameworks, css+ui,
performance+seo, analytics, accessibility and so on -- and each entry carries its
description, its npm and repository addresses and its download count. Themes come as
catalog pages with the name, the description, the author and whether the theme is free
or paid. The showcase is a list of real sites built with Astro. When the question is
"what exists for X", search the catalogs; when it is "how does X work", search the
documentation.

For a question about when something appeared or changed, search more than once:
without `version` first, to find the release note that announced it, then with the
lines around it, to see how the documentation described it before and after.

Write the query in English, with the names Astro itself uses (getStaticPaths,
defineCollection, client:visible, Astro.props, output: "server", adapter, prerender).
Everything here is English -- the excerpts, the word index and the meaning index alike
-- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing and comes back with
`found: 0`. When the user asks in another language, translate the question into Astro
terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the
words of the query had to appear in the text, so a query phrased differently from the
documentation may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in. When the question is about a version, answer
point by point: which line the answer holds for; how it is configured there, with the
exact option and directive names; what differs in the neighbouring lines; and what
breaks or needs changing on upgrade. Every point names the version and the document it
rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from
English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація Astro". Identifiers, directives, option names
and titles stay in English, spelled exactly as the documentation spells them. Build
the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3; `version` is optional, see above. Excerpt text is cut at 600 characters -- pass the
`id` of an excerpt to `read_section` to get the whole thing.
