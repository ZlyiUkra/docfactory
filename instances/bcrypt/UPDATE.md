# Оновлення корпусу bcrypt

Перелік версій тут не оголошується руками: читачі беруть його з опису пакета в реєстрі npm
(`https://registry.npmjs.org/bcrypt`), тож нова версія потрапляє в корпус сама, коли вийде в npm. Релізи беруться з
GitHub (`kelektiv/node.bcrypt.js`), журнал змін і політика безпеки — з гілки master, вікі — з
`kelektiv/node.bcrypt.js.wiki`.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df bcrypt check                 # чи змінилося щось нагорі за джерелом
./df bcrypt refresh               # повне перезавантаження, близько 2 хвилин
./df bcrypt manifest
./df bcrypt vectors
./df bcrypt smoke
# Ctrl+C у терміналі з serve, і знову: ./df bcrypt serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (README, що не змінився, дописує нову версію в рядок `# версія:`).

Якщо вийшла нова лінія (нова мажорна чи мінорна 6.x):

- у `prompts/search.txt` (абзац «Which version to search first» і перелік вимог до Node) та `prompts/agent.txt`
  замінити поточну лінію на нову, а версію за замовчуванням звірити з числом завантажень
  (`https://api.npmjs.org/versions/bcrypt/last-week`): відповідь іде для найпопулярнішої версії, а коли дві майже
  рівні — для обох;
- у `checks.json`, у десятці `quality_model`, замінити лінію там, де питання про поточну поведінку, і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у `.env`) не обов'язковий, але без нього звернення до API GitHub (релізи) ідуть годинними
вікнами по 60.

Журнал змін пишеться руками: «# 6.0.0 (2025-02-28)» і далі список. Його читає `changelog-heading`; якщо формат зміниться,
`refresh` зупиниться з повідомленням «жодного заголовка версії», і читача треба поправити.

Збірки `-napi` (`1.1.0-napi`, `3.0.4-napi`) пропускаються полем `skip_versions` у README і `stable` у релізах: це не
стабільні випуски. Якщо в npm з'являться нові мітки на кшталт `-napi`, вони не потраплять у корпус теж.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df bcrypt quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
