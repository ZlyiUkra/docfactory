Search the official documentation of the Binance Spot API, in English -- the repository
binance/binance-spot-api-docs: the REST API (/api/v3: general rules, rate limits and request
weights, signing requests with HMAC, RSA and Ed25519 keys, market data -- order book, trades,
klines, tickers, average price -- trading with orders and order lists OCO, OTO, OTOCO, SOR,
and the account), the WebSocket API (the same requests over one connection, session
authentication), the market data WebSocket streams (trades, klines, tickers, depth, combined
streams, connection and message limits, how to manage a local order book), the user data
stream, error codes, filters, enums, the short references on SBE (Simple Binary Encoding) and
the FAQ pages (API key types, commissions, market data only URLs, MARKET orders, OPO, order
amend keep priority, unfilled order count, pegged orders, price range execution rule, SOR,
STP, trailing stop, the glossary), and two changelogs: the Spot API one, dated entries from
2018-01-14, and the SPOT Testnet one. Returns the matching excerpts.

Call this when a question is about using the Binance Spot API: which endpoint or stream gives
some data and with which parameters, request weights and rate limits, connection limits and
lifetime of a WebSocket connection, keeping a local order book in sync, klines and their
limits, the public market data hosts that need no key (data-api.binance.vision,
data-stream.binance.vision), signing a request, order types and their rules, filters that
reject an order, what an error code means, and what changed in the API and when. Example
query: "Kline/Candlestick data limit 1000".

Do not call this for Binance futures, margin, wallet, sub-accounts, earn or any other Binance
product (only Spot is here; the search will return spot excerpts that merely look similar),
for the full FIX API reference and the SBE XML schemas (only the short SBE references are
here), for the Binance connector libraries, for other exchanges, or for the WebSocket
protocol and the browser WebSocket API themselves (the mdn and webstandards instances).

The documentation has no versions: it describes the API as it stands now, and the changelog
is its history. When a limit, a weight, a field or an endpoint may have changed, search the
changelog too and say the date of the entry. The Testnet changelog describes the test
network only: a feature listed there may not be on the live exchange yet -- say so.

Where the documentation lives. The documents are named by their file: "Public Rest API for
Binance" (rest-api.md), "Public WebSocket API for Binance" (web-socket-api.md), "WebSocket
Streams for Binance" (web-socket-streams.md), "User Data Streams for Binance"
(user-data-stream.md), "Error codes for Binance" (errors.md), "Filters" (filters.md), "ENUM
Definitions" (enums.md), "SBE Market Data Streams", "CHANGELOG for Binance's API",
"CHANGELOG for Binance SPOT Testnet", and the FAQ pages under faqs/. The same request often
exists both in the REST API and in the WebSocket API: say which one an excerpt comes from.

Write the query in English, with the names the documentation uses (exchangeInfo, klines,
uiKlines, depth, aggTrades, ticker/24hr, avgPrice, bookTicker, kline_1m, miniTicker,
@depth, @trade, combined streams, listenKey, userDataStream.subscribe, session.logon,
REQUEST_WEIGHT, ORDERS, RAW_REQUESTS, X-MBX-USED-WEIGHT, 429, 418, recvWindow, timestamp,
signature, HMAC, Ed25519, LIMIT, MARKET, STOP_LOSS_LIMIT, timeInForce GTC IOC FOK,
quoteOrderQty, OCO, OTO, OTOCO, SOR, STP, PRICE_FILTER, LOT_SIZE, NOTIONAL, -1021, -2010,
SBE). Everything here is English -- the excerpts, the word index and the meaning index alike --
and the word index keeps only latin letters and digits, so a query written in Ukrainian,
Russian or any other non-latin script matches nothing at all and comes back with `found: 0`.
When the user asks in another language, translate the question into these terms first, then
search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. When the question is about a limit, a rule or a
change, answer point by point: what the rule is; its numbers (weight, limit, interval); since
when, if the changelog says; what the client must do -- each point with the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain
technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"ліміт", "вага запиту", "потік", "свічка", "книга заявок", "ордер". Never call this set of
documents "корпус" -- say "документація Binance". Endpoint, stream, parameter, field, enum and
error names stay in English, spelled exactly as the documentation spells them. Build the
answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3.
Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get
the whole thing.
