Search the official documentation of Biome -- the toolchain for web projects from biomejs: a
formatter, a linter, an assist with source actions, a CLI, a language server for editors and
GritQL plugins, for JavaScript, TypeScript, JSX, JSON, CSS, GraphQL, HTML and Markdown -- and
return the matching excerpts with the versions each one belongs to. Here: the documentation site
biomejs.dev as it stood when each stable Biome release from 0.1.2 to 2.5.15 came out -- getting
started, installation and the standalone executable, configuring Biome (biome.json and biome.jsonc,
nested configurations, extends, overrides, files.includes and ignoring files, VCS integration, big
projects and monorepos), the CLI reference (check, lint, format, ci, init, migrate, search, rage,
explain, start, lsp-proxy, every flag), the configuration reference, the environment variables,
the diagnostics, suppression comments, the linter (rule groups, domains, severity, safe and unsafe
fixes) and the page of every lint rule and assist action -- its summary (since which version, the
diagnostic category, whether it is recommended, its fix and default severity, the ESLint or
other rule it comes from), how to configure it, the description, invalid and valid examples with
the diagnostic Biome prints, and its options -- the rule lists and rule sources of every language,
the formatter, its options philosophy and the differences with Prettier, language support,
migrating from ESLint and Prettier, upgrading to Biome 2, editors (VS Code, Zed, IntelliJ, the
language server), continuous integration, git hooks, GritQL and linter plugins, the internals
(architecture, philosophy, versioning) and the blog with the release posts; the changelog of every
stable release, Biome 1.0.0-1.9.4 and 2.0.0-2.5.15; and the npm version table of @biomejs/biome.

Call this when a question is about Biome itself -- a lint rule (noUnusedVariables,
useExhaustiveDependencies, noExplicitAny), what it reports, its options and fix, how to enable,
disable or change the severity of a rule or a group, a biome.json key and its default
(formatter.indentStyle, javascript.formatter.quoteStyle, linter.rules.recommended,
files.includes, assist.actions.source.organizeImports), a CLI command or flag, suppression
comments (biome-ignore), formatting differences with Prettier, migrating from ESLint or Prettier
(biome migrate eslint), editor setup, CI, and above all history: since which version something
exists, what changed, what was renamed or removed.
Example query: "noUnusedVariables ignoreRestSiblings".

Do not call this for ESLint, Prettier, typescript-eslint, dprint, oxlint or Rome beyond the pages
that compare or migrate from them, the JavaScript, TypeScript or CSS languages themselves, Node.js,
npm or other package managers, VS Code or other editors themselves, or any framework (React, Vue,
Svelte, Astro, Next.js): their documentation is not here, and the search will return Biome
excerpts that merely mention them, with confident-looking titles.

Only stable releases are here: the nightly builds and the 2.0.0 betas are not documented.

Versions. `version` narrows the search to the documents of one release line: "2.5" keeps every
2.5.x document, "1.9" every 1.9.x, "2.0" every 2.0.x. Each document of the site carries the Biome
releases whose site showed the page exactly so. Without `version` a page found in several releases
comes back once, in its newest edition. Every excerpt comes back with `versions`: each version
whose documents contain this exact text, newest first. Changelogs carry the version of their
release. Biome 2.0 changed a lot -- rules moved between groups, organizeImports became an assist
action, files.ignore and files.include became files.includes, the configuration of the linter
and formatter changed -- so for Biome 1 search with `version` "1.9".

Name the rule, option, configuration key or command the way the documentation titles it, not in
the user's own words: "noUnusedVariables", "useExhaustiveDependencies options",
"formatter indentStyle", "javascript formatter quoteStyle", "files includes", "biome check write",
"biome-ignore suppression comment", "organizeImports", "biome migrate eslint", not "how do I stop
Biome complaining about unused vars". Rule pages are titled with the rule name in camelCase
(noUnusedVariables (JavaScript)): search for the rule name itself. A rule name alone also matches
every changelog line that mentions it: add the plain word of the topic ("noUnusedVariables
options", "useImportType fix"). For a how-to question a guide often shows it better than the
reference: search for it as well ("configure biome ignore files", "continuous integration").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the changelog or release post that names the exact version, then
with the versions around it, to see the documentation of that time.

Write the query in English, with the names Biome itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate
the question into Biome terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
two most downloaded stable lines: Biome 2 (2.5.15) and Biome 1 (1.9.4) -- and, when the excerpts
show that a rule, option or command appeared in a later release than the user may have, or
differs between the two lines, say since which one. Add that for a precise answer about another
version the user can name it. When the excerpts behind a statement come only from older versions,
name those versions instead of presenting the text as current. Command examples are shown for
every package manager, each under its own label (npm:, pnpm:, yarn:, bun:, deno:): give the one
the user asked about, and when the user did not say, the npm one with a note that the others
exist.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
and how it stands now -- recommended, deprecated, or removed and replaced by what. Every point
names the version and the document it rests on; a point the excerpts do not support is left out,
not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "правило лінтера", not "лінт-рул"; "застарілий", not "депрекейтнутий".
Never call this set of documents "корпус" -- say "документація Biome". Identifiers, rules,
options and titles stay in English, spelled exactly as the documentation spells them. Build the
answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
