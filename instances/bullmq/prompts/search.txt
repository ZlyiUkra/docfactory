Search the BullMQ documentation, in English: BullMQ is the Redis-backed job and message queue for Node.js
(Queue, Worker, Job, FlowProducer, QueueEvents; delayed, repeatable and prioritized jobs, retries with backoff,
rate limiting, concurrency, sandboxed processors, flows with parent and child jobs, deduplication, telemetry),
with the ports BullMQ Python, Elixir, Rust, PHP and .NET and the commercial BullMQ Pro (groups, batches,
observables). The set also holds the predecessor Bull (versions 0.1 to 4.16), the dashboards Bull Board and
Arena, and the NestJS modules @nestjs/bullmq and @nestjs/bull. For every stable release it holds: the site
docs.bullmq.io (guide, patterns, BullMQ Pro, the Bull section, the port sections, the changelogs of every
major), README and CHANGELOG, the source code src/ with the Lua scripts of the queue, the tests of the last
release of each minor line, the code of each port, the GitHub release notes; for Bull: README, REFERENCE.md,
PATTERNS.md, MIGRATION.md, CHANGELOG, lib/ and tests, @types/bull; for Bull Board: README, the site
website/docs, the README of every @bull-board package and example, the code of all packages including the
React UI, the examples; for Arena and the NestJS modules: README and code. Returns the matching excerpts
with the versions each one belongs to.

Call this when a question is about BullMQ or Bull: how to add a job and its options (delay, attempts,
backoff, priority, jobId, removeOnComplete, lifo), how a Worker processes jobs (concurrency, lock duration,
stalled jobs, rate limiter, sandboxed processors), repeatable jobs and job schedulers, flows and
parent-child jobs, events (QueueEvents, worker events), retries and failures, pausing, cleaning and
draining, how the Lua scripts move jobs between states, what BullMQ Pro groups and batches do, how a port
(Python, Elixir, Rust, PHP, .NET) differs, how to migrate from Bull to BullMQ, what changed between versions,
how to mount Bull Board or Arena on Express, Fastify, Koa, Hapi, NestJS, Hono, H3, Elysia or Next.js, how
@nestjs/bullmq registers queues and processors. Example query: "Worker concurrency".

Do not call this for the Redis server itself (commands, redis.conf, persistence, Cluster: the redis instance),
for the clients ioredis and node-redis (their own instances), for the NestJS Queues chapter itself (the nestjs
instance), or for other queue systems (Bee-Queue, Agenda, RabbitMQ, Kafka, SQS).

Write the query in English, with the names BullMQ uses (Worker, Queue.add, FlowProducer, QueueEvents,
removeOnComplete, backoff, limiter, JobScheduler, sandboxed processor). Everything here is English, and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing and comes back with `found: 0`. When the user asks in another language,
translate the question into BullMQ terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий"; "черга", "задача", "воркер" (так
каже і документація). Never call this set of documents "корпус" -- say "документація BullMQ". Class, option,
method and event names stay in English, spelled exactly as the documentation spells them. Build the answer
out of the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before
describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. When the user names a version, search that line; otherwise answer for the newest
BullMQ release and say so. Put a version only into `version`, never into the query text: "5" keeps every 5.x,
"5.34" keeps 5.34.x. Every document carries the releases in which it was exactly so. Versions are per product:
a Bull document is marked by Bull versions (4.16.5), a Bull Board document by Bull Board versions (9.10.4), a
port by the port's versions, so name the product in the query when the version matters ("Bull Board 6
fastify"). Documents are named by product and path: "bullmq-docs-guide-workers", "bullmq-readme",
"bull-reference", "bull-board-docs-queue-adapters-bullmq", "src-classes-worker-ts", "nestjs-bull-readme".
