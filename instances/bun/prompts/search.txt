Search the Bun documentation and return the matching excerpts with the versions each one belongs to.
What is here: the bun.com/docs documentation (the runtime: running files, TypeScript and JSX, `bunfig.toml`,
environment variables, the module resolver, Node.js compatibility, Web APIs, HTTP server `Bun.serve`, WebSockets,
files `Bun.file` and `Bun.write`, child processes `Bun.spawn`, `bun:sqlite`, SQL, Redis, S3, FFI, workers, shell
`Bun.$`; the package manager: `bun install`, `bun add`, lockfile, workspaces, catalogs, patching, `bunx`; the bundler
`bun build`, plugins, macros, executables `bun build --compile`, HTML and CSS; the test runner `bun test`, mocks,
snapshots, coverage; `bun lint` and its rules; and the guides) as it stood at every stable patch release 1.0.0–1.4.4 and
the last patch of every minor 0.1–0.8; the API reference from the type files of `packages/bun-types` at the same
releases; the GitHub release notes of every stable version; the npm registry records of `bun`, `bun-types` and
`@types/bun`; the tags of the Docker image `oven/bun` on Docker Hub (versions, variants, floating tags,
architectures); and every post of the bun.com blog, including the release post of each version.

Call this when a question is about Bun: running and configuring it, its CLI commands and flags, its APIs (`Bun.*`,
`bun:sqlite`, `bun:test`, `bun:ffi`), Node.js and npm compatibility and moving a Node.js project to Bun, installing
packages and workspaces, bundling and single-file executables, testing, Docker images, and history: since which
version a flag, API or behaviour exists, what changed in a release.

Do not call this for Node.js itself, Deno, browsers in general, frameworks (Elysia, Hono, Next.js) beyond how Bun
runs them, or JavaScript and TypeScript language questions: their documentation is not here, and the search will
return Bun excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "1" keeps every 1.x document, "1.2" one minor with all its
patches, "1.2.5" one patch; 0.x minors are "0.8" and the like. The blog carries no version; Docker image documents
carry the minor line ("1.4"). Leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first, so the list itself shows from which to which version
the documentation said exactly this.

Write the query in English, with the names Bun itself uses ("bun install", "bunfig.toml", "Bun.serve routes",
"Bun.file", "bun:sqlite", "bun test mock", "bun build --compile", "workspaces catalog", "node:fs compatibility",
"Bun.$ shell"), not in the user's own words. Everything here is English -- the excerpts, the word index and the
meaning index alike -- and the word index keeps only latin letters and digits, so a query written in Ukrainian,
Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into Bun terms first, then search.

Answer in the language the user wrote in. When the question is about the history of a flag, API or behaviour,
answer point by point: since which version it exists; what changed in later versions; what prompted the change, if
the excerpts say so; and how it stands now. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація Bun". Identifiers, command names, flags, keys and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.
