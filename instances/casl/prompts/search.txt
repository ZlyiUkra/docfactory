Search the CASL documentation -- the isomorphic JavaScript authorization library that restricts what a user may do
with which subjects and fields, with conditions written in the MongoDB query language (attribute based access
control; monorepo stalniy/casl, site casl.js.org). The corpus holds the pages of the site v4 to v7, taken from the
tags of @casl/ability 4.0.8 to 7.0.2: the guide (Introduction, Installation, Define Rules with defineAbility,
AbilityBuilder and JSON objects, Conditions in Depth with the supported operators, Restricting fields access with
field patterns, TypeScript Support, Subject type detection with the `subject` helper), the advanced pages (Customize
Ability with custom operators and matchers, Ability to database query, Ability inheritance, Cache abilities,
Debugging and testing, Define Action Aliases, TypeScript inference), the cookbook (roles with predefined permissions,
roles with persisted permissions, claim based authorization, cache rules, a less confusing can API) and the API
reference of @casl/ability and @casl/ability/extra (PureAbility and Ability, AbilityBuilder, ForbiddenError,
createAliasResolver, subject, rulesToQuery, rulesToAST, rulesToFields, permittedFieldsOf, packRules, unpackRules);
the old Jekyll site of v1 to v3 (Roles and Abilities, Define Abilities, Check Abilities, Database Integration,
Storing abilities, Error Handling); the README of every stable version of @casl/ability, @casl/react (Can,
AbilityContext, useAbility), @casl/vue (abilitiesPlugin, provideAbility, useAbility, Can), @casl/angular
(AbilityModule, AbilityService, the able pipes, signals), @casl/aurelia, @casl/mongoose (accessibleBy,
accessibleRecordsPlugin, accessibleFieldsPlugin), @casl/prisma (createPrismaAbility, accessibleBy, PrismaQuery,
Subjects) and of the old package `casl` (0.2.0 to 1.1.0); the changelog of every package; the example applications of
stalniy/casl-examples (hello-world, express-blog, fastify-prisma-blog, fastify-ucast-sql-blog, react-blog,
react-todo, vue-blog, vue-todo, angular-todo); and the npm registry history of every package (date of every version,
dependencies, peer dependencies). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about CASL as it describes itself -- how to define rules (defineAbility, AbilityBuilder,
createMongoAbility, JSON rules), how `can` and `cannot` combine and in which order inverted rules win, conditions and
their operators, fields and field patterns, subject type detection, checking with `ability.can` and
`ForbiddenError.from(ability).throwUnlessCan`, turning rules into a database query (accessibleBy for Mongoose and
Prisma, rulesToQuery, rulesToCondition), restricting fields with permittedFieldsOf, storing and sending rules to the
client with packRules, updating rules after login, TypeScript types (MongoAbility, InferSubjects, MongoQuery), the
React, Vue and Angular bindings -- and above all history and compatibility: since which version a function or option
exists, what changed between versions, which versions require which React, Vue, Angular, Mongoose or Prisma, and when
every version came out.

Do not call this for React, Vue, Angular, Aurelia, Mongoose, Prisma, MongoDB, Express or NestJS themselves (routing,
components, schemas, queries, guards): their documentation is not here -- the pages of CASL and the examples only show
how CASL is wired into them -- and the search will return excerpts that merely mention them, with confident-looking
titles.

`version` narrows the search to one release line. @casl/ability and the old package `casl` carry bare numbers (lines
0 and 1 are the old package `casl`, lines 2 to 7 are @casl/ability; the pages of the site carry the version of the
@casl/ability tag they were taken from), the other packages carry the name of the package in front: "react-5",
"vue-2", "angular-9", "aurelia-1", "mongoose-8", "prisma-2". A line keeps every document of that major ("6" keeps
6.0.0 to 6.8.1), adding a minor keeps that minor ("6.7", "react-5.0"), three numbers an exact version ("6.8.1").
Leave `version` empty to search everything, including text that carries no version. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- a page that stayed the same across
versions is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("defineAbility", "AbilityBuilder",
"createMongoAbility", "PureAbility", "ForbiddenError", "subject", "permittedFieldsOf", "packRules",
"accessibleBy", "accessibleRecordsPlugin", "createPrismaAbility", "useAbility", "AbilityModule", "InferSubjects"),
not in the user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike --
and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer point by point:
 since which version it exists; what changed in later versions; what prompted the change, if the excerpts say
so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація CASL". Identifiers, method names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads the line 6 of @casl/ability leads with about 70 % (6.8.1 of April
2026 is its last version), the line 7 -- the newest, 7.0.0 of May 2026 and 7.0.2 of October 2026 -- has about 26 % and
the line 5 about 3 %. Pass `version` "6" for how things are done today, and mention 7 when the user is on it or it differs (the changelog
7.0.0 says what changed: PureAbility renamed to Ability without default options, rulesToQuery replaced with
rulesToCondition, getDefaultErrorMessage removed, readonly rules). For the bindings: @casl/react
lines 5 (about 43 %) and 7 (about 29 %) are close -- answer for both; @casl/vue line 2 (about 63 %); @casl/angular
line 9 (about 52 %); @casl/mongoose line 8 (about 48 %); @casl/prisma lines 2 (about 55 %) and 1 (about 45 %) --
answer for both. Search without `version` when the question is about history, or when the line gave nothing. Every
answer says which version it is for; when the excerpts behind a statement come only from older versions, name those
versions instead of presenting the text as current.
