# certbot — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Certbot — клієнт ACME від EFF, який отримує й поновлює
безкоштовні сертифікати Let's Encrypt і сам налаштовує Apache та nginx, — за документацією всіх його стабільних версій:
сайтом eff-certbot.readthedocs.io у стані на кожен реліз, сторінками плагінів DNS, журналом змін і реєстром PyPI
certbot, acme та всіх офіційних плагінів. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Скільки цього

Усього 133 стабільні версії Certbot (0.6.0–5.8.0) — ті, що є на PyPI під назвою `certbot`. До 0.6.0 той самий проєкт
виходив як `letsencrypt` (0.1–0.5); з тих часів у корпусі лише журнал змін. Передрелізи (`0.6.0.dev0`) не беруться.

| Шар | Документів | Версій | Звідки |
|-----|-----------:|-------:|--------|
| Сайт: кожен неповторний текст сторінки один раз, з усіма версіями | 362 | 0.6.0–5.8.0 | теги репозиторію `certbot/certbot` |
| Сторінки 14 плагінів DNS | 85 | 0.15.0–5.8.0 | ті самі теги |
| Журнал змін, по документу на версію | 142 | 0.1.1–5.8.0 | `certbot/CHANGELOG.md` гілки main |
| Реєстр PyPI 18 проєктів: огляд і лінії, з вимогою до Python і залежностями | 122 | усі стабільні | pypi.org |
| Опис проєкту certbot на PyPI (README) | 29 | 0.6.0–5.8.0 | pypi.org |

Разом 740 документів; фрагментів в індексі — 3337 (`expected_passages` у `checks.json`).

Замір `quality` на першому корпусі: по словах 4 із 10, за змістом 8, разом 7; десятка «як модель» — 10 із 10.
`max_per_doc` заміряно від 0 до 3: 1 програє (5 і 8 із 10), 2 і 3 — нарівні з 0, тож поле не задано.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df certbot <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| сайт | репозиторій `certbot/certbot`, тег `vX.Y.Z` кожної версії; тека `docs/` до 1.0, далі `certbot/docs/` | `ghdocs-history` з `sphinx` |
| плагіни DNS | ті самі теги: опис модуля `certbot_dns_*/__init__.py` кожного плагіна | `ghdocs-history` з `sphinx` |
| журнал змін | `certbot/CHANGELOG.md` гілки main | `changelog-dated` |
| реєстр PyPI | `pypi.org/pypi/<проєкт>/json` і опис кожної версії | `pypi-versions`, новий |

Сайт Certbot збирає Sphinx із файлів reStructuredText (`.rst`) репозиторію, а Read the Docs тримає лише дві його
версії — `latest` і `stable`. Тому сайт кожної версії береться з тегу git: це той самий текст, з якого Read the Docs
будував сторінки. Що додано у фабрику разом із цим примірником:

- **Читач `pypi-versions`** (`engine/readers/pypiversions.py`) — те саме, що `npm-versions`, для реєстру PyPI: дата
  кожної версії, позначка yanked (відкликана версія), вимога до Python (`requires_python`) і залежності з межами
  (`requires_dist`), а в документі лінії — що змінилося відносно попередньої версії. З `readme: true` — ще й опис
  проєкту в кожній неповторній редакції.
- **Поле `sphinx` читача `ghdocs-history`** (розбір у `engine/readers/_sphinx.py`): ролі `:ref:` і `:doc:` стають
  словами посилання, `toctree` і `automodule` зникають, підпис `:caption:` стоїть над прикладом коду, проста таблиця
  (таблиця параметрів кожного плагіна DNS) — пунктами «параметр — опис», підстановки `|назва|` розгорнуто. Файл
  `.py` дає документ з опису модуля — саме його показує сайт плагіна на Read the Docs, — а `cli-help.txt` (вивід
  `certbot --help all`) — розділ на кожну групу параметрів.
- **`changelog-dated`** приймає місяць і день однією цифрою: у журналі Certbot є «## 0.28.0 - 2018-11-7».

Особливості корпусу:

- **Документ — неповторний текст.** Версії, де сторінка не змінилася, ділять один документ; у рядку `# версія:` стоять
  усі. Ключ сторінки однаковий у `docs/` і `certbot/docs/` (`slug_rewrite` у `config.json`), тож редакції однієї
  сторінки до й після 1.0 зливаються.
- **Плагіни DNS** — cloudflare, cloudxns, digitalocean, dnsimple, dnsmadeeasy, gehirn, google, linode, luadns, nsone,
  ovh, rfc2136, route53, sakuracloud. Перші з'явилися в 0.15; gehirn, linode, ovh і sakuracloud — пізніше;
  `certbot-dns-cloudxns` прибрано в 2.0, його сторінки є до 1.32.
- **Вимога до Python і залежності** записані в документах реєстру PyPI кожного проєкту: «certbot on PyPI: versions
  5.x» тощо. Для старих версій, чий опис PyPI залежностей не знає, так і написано.
- **Довідника API немає.** Сторінки `api/` сайту Sphinx генерує з коду Python (autodoc), у файлах `.rst` їхнього тексту
  немає; він потрібен лише авторам плагінів.
- **Посилання** ведуть на файл у репозиторії на тезі версії, а не на Read the Docs: старих версій сайту там немає.

## Межі, про які треба пам'ятати

Сайту Let's Encrypt (letsencrypt.org: ліміти, ланцюжки довіри, протокол) тут немає — він є в примірнику
`kubernetes` (джерело `letsencrypt-docs`). Немає й RFC 8555 (ACME), документації Apache, nginx (є примірник `nginx`)
і провайдерів DNS, сторонніх плагінів, сайту certbot.eff.org з інструкціями під кожну систему (його сторінки
складає застосунок, а не текст у репозиторії) і коду самого Certbot.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/certbot-corpus-2026-10-09.tar.gz` (740 текстів і паспорт). В історії
git текстів немає ніде. Архів лежить лише на цій машині.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/certbot-corpus-2026-10-09.tar.gz -C instances/certbot
./df certbot smoke
```

**Як знову винести** — після оновлення, коли `vectors` і `smoke` пройшли (вони ж збирають свіжий кеш):

```
ls -l instances/certbot/index/passages.json       # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/certbot-corpus-РРРР-ММ-ДД.tar.gz -C instances/certbot corpus
find instances/certbot/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/certbot/index/passages.json > instances/certbot/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти» і «Як повернути тексти».

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/certbot/index/passages.json.gz`,
далі `./df certbot vectors` заллє колекцію Qdrant.

## Установка venv

```
cd instances/certbot
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df certbot sources --why   # перелік джерел і білий список
./df certbot refresh         # завантажити все задеклароване (близько 25 хвилин)
./df certbot manifest        # оновити паспорт
./df certbot setup           # Qdrant чи пошук лише по словах
./df certbot vectors         # залити корпус у docs-certbot
./df certbot smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df certbot serve          # порт 8811
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8811/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user certbot-docs http://127.0.0.1:8811/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `certbot-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
