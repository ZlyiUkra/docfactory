# Оновлення корпусу class-transformer

Перелік версій тут не оголошується руками: читач README і реєстру бере його з опису пакета в реєстрі npm
(`https://registry.npmjs.org/class-transformer`), тож нова версія потрапляє в корпус сама, коли вийде в npm. Журнал змін береться з гілки develop
репозиторію `typestack/class-transformer`; релізів GitHub у корпусі немає — їхні нотатки порожні. Єдине, що оголошено руками, — теги теки `docs`
(поле `tags` у `sources.json`, джерело `class-transformer-docs`): нову версію туди дописують зверху.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df class-transformer check                 # чи змінилося щось нагорі за джерелом
./df class-transformer refresh               # повне перезавантаження, близько хвилини
./df class-transformer manifest
./df class-transformer vectors
./df class-transformer smoke
# Ctrl+C у терміналі з serve, і знову: ./df class-transformer serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (README, що не змінився, дописує нову версію в рядок `# версія:`).

Якщо вийшла нова лінія (нова мінорна 0.x чи перша 1.0):

- додати тег у `tags` джерела `class-transformer-docs` (`"v0.6.0": "0.6.0"`);
- у `prompts/search.txt` (абзац «Which version to search first» і перелік ліній) та `prompts/agent.txt` замінити
  поточну лінію на нову, а версію за замовчуванням звірити з числом завантажень
  (`https://api.npmjs.org/versions/class-transformer/last-week`): відповідь іде для найпопулярнішої лінії, а коли дві
  майже рівні — для обох; на 20.10.2026 це 0.5.1 (97 %);
- у `checks.json`, у десятках `quality` і `quality_model`, замінити лінію там, де питання про поточну поведінку, і звірити
  цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) не обов'язковий, але без нього звернення до API GitHub (релізи, дерева
тегів) ідуть годинними вікнами по 60.

Журнал змін пишеться руками і нерівно: «### [0.5.1][v0.5.1] [BREAKING CHANGE] - 2021-11-22», «### [0.3.1][v0.3.1] - 2020-07-29»,
«### 0.1.10».
Його читає `changelog-regex` за виразом `heading` у `sources.json`; якщо формат зміниться, `refresh` зупиниться з
повідомленням «жодного заголовка запису», і вираз треба поправити.

Передрелізи (`0.1.0-beta.N`) пропускаються полем `skip_versions` у README. Записи журналу 0.0.x (до першої публікації в npm)
пропускаються полем `skip` джерела `class-transformer-changelog`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df class-transformer quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
