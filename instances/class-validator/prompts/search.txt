Search the class-validator documentation -- the README of every stable version of the npm package
`class-validator` (decorator-based validation of classes for TypeScript and JavaScript, from the
TypeStack organisation), the pages of its `docs` folder on GitHub, the changelog and the GitHub release
notes, and the npm registry history of the package -- and return the matching excerpts with the
versions each one belongs to.

Call this when a question is about class-validator as it describes itself -- validate(),
validateOrReject(), validateSync(), the ValidationError object (target, property, value, constraints,
children, contexts), the validator options (skipMissingProperties, whitelist, forbidNonWhitelisted,
forbidUnknownValues, groups, always, strictGroups, stopAtFirstError, dismissDefaultMessages,
validationError, enableDebugMessages), the validation decorators (@IsString, @IsNumber, @IsInt,
@IsEmail, @IsUUID, @IsDate, @IsEnum, @IsArray, @IsOptional, @IsDefined, @IsNotEmpty, @Length, @Min,
@Max, @Matches, @IsStrongPassword and the rest of the decorator tables), nested validation
(@ValidateNested, @ValidatePromise, arrays, Maps and Sets through `each: true`), conditional validation
(@ValidateIf, the `validateIf` option), validation groups, custom messages and the `$property`, `$value`
and `$constraint1` tokens, custom validators (@ValidatorConstraint, ValidatorConstraintInterface,
registerDecorator, ValidateBy, async validators), inheriting decorators, `useContainer` and dependency
injection into validators, the manual `Validator` class and the standalone functions (isEmail, isNotIn,
isBoolean ...), the metadata storage, the requirement for `reflect-metadata`, `experimentalDecorators`
and `emitDecoratorMetadata` -- and above all history and compatibility: since which version a decorator
or option exists, what changed between versions, what the breaking changes were (0.9.0, 0.12.0 with its
removal of the methods of the Validator class, 0.14.0 with `forbidUnknownValues` on by default, 0.15.1
with the options argument of @IsIBAN), which version of validator.js stands behind a release, and when
every version came out. The dependencies of every version (validator, libphonenumber-js,
@types/validator) are written in the npm registry documents.

Do not call this for class-transformer (plainToInstance, @Type, @Transform, @Expose), for the NestJS
ValidationPipe, for validator.js itself, Joi, Zod, Yup, ajv or any other validation library, nor for
TypeScript decorators in general: their documentation is not here, and the search will return excerpts
that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. The package is numbered 0.x: the lines are 0.3, 0.4,
0.5, 0.6, 0.7, 0.8, 0.9, 0.10, 0.11, 0.12, 0.13, 0.14 and 0.15 (44 stable versions, 0.3.0 to 0.15.1).
"0.14" keeps every 0.14.x document, "0.14.4" one exact version. There was never a 1.0. The versions 0.10.0-rc,
0.12.0-rc and the 0.12.0-refactor builds are not stable releases: only the registry lists them. The version
0.15.0 has a GitHub tag and release but was never published to npm; 0.15.1 followed at once. Leave
`version` empty to search everything, including text that carries no version. Every excerpt comes
back with `versions`: each version whose documents contain this exact text, newest first -- text that
stayed the same across versions is returned once, with all of them listed, so the list itself shows
from which to which version the documentation said exactly this.

To find which decorator checks a given kind of value (an e-mail, a URL, a phone number, a UUID, a date, the
size of an array ...) search for "validation decorators" together with the decorator names: the README section
"Validation decorators" holds the tables of all of them (common, type, number, date, string, array, object and
other decorators).

Write the query in English, with the names the documentation itself uses ("ValidateNested",
"forbidUnknownValues", "whitelist", "registerDecorator", "ValidatorConstraint", "validateSync",
"useContainer"), not in the user's own words. Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into the terms of the
documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support,
answer point by point: since which version it exists; what changed in later versions; what prompted
the change, if the excerpts say so; and how it stands in the current version. Every point names the
version and the document it rests on; a point the excerpts do not support is left out, not guessed. When
that language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from English:
plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"валідація", "декоратор", "застарілий". Never call this set of documents "корпус" -- say "документація
class-validator". Identifiers, decorator names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to
`read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses may
miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase had a
chance.

Which version to search first. By weekly downloads the line 0.14 leads (0.14.4 about 32 %, 0.14.3 about
17 %, 0.14.1 about 10 %, 0.14.2 about 8 %, 0.14.0 about 5 %: together about 72 %), and 0.15.1, the newest
version, has about 25 %. Pass `version` "0.14" for how things are done today, and say what 0.15 adds or
changes when it differs (the `validateIf` option on every validator, the options argument of @IsIBAN that
breaks existing calls, the new @IsISO31661Numeric and @IsISO6391, more UUID versions). Search without
`version` when the question is about history, or when the line gave nothing. Every answer says which
version it is for; when the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current.
