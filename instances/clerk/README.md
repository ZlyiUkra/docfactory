# clerk — примірник фабрики docfactory

Сьомий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Clerk (автентифікація й керування
користувачами) за його офіційною документацією — поточною лінією Core 3 і двома архівними, Core 2 та Core 1, —
за довідниками Backend, Frontend і Platform API, журналом змін і блогом. Код спільний і лежить у `../../engine/`
(завантаження корпусу), `../../server/` (сервер, агент, шари) та `../../common/` (пошук); ця тека тримає самі дані
домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо архівні лінії

«Core» — так Clerk називає покоління своїх SDK: усі пакети переходять на нову лінію разом, і з кожною змінюється
API — імена хуків і пропсів, middleware, імена пакетів. Номер лінії з номером версії пакета не збігається: за
гайдами оновлення, Core 2 — це `@clerk/nextjs` від 5.0.0, `@clerk/clerk-react` від 5, `@clerk/clerk-expo`,
`@clerk/backend` і `@clerk/fastify` від 1; Core 3 до того ж перейменовує `@clerk/clerk-react` на `@clerk/react` і
`@clerk/clerk-expo` на `@clerk/expo`. Лінію свого проєкту найпростіше впізнати за назвою й мажорною версією пакета
в `package.json`.

Сайт тримає документацію всіх трьох ліній (перемикач «Core 3 / Core 2 / Core 1» угорі), бо проєкти на старих
лініях живуть роками. Для такого проєкту поточна документація шкодить: вона радить код, якого в його версії SDK ще
немає. Тому корпус тримає всі три лінії, а фільтр `version` пошуку відбирає потрібну.

Разом 4 121 документ, 22 МБ; фрагментів в індексі — 30 579 (`expected_passages` у `checks.json`).

**Чому фрагментів утричі більше, ніж у `react-router`.** Сторінки Core 3 лежать окремо на кожен SDK: 2 487 адрес
на 803 різні сторінки. Однакові розділи варіантів зливаються в один фрагмент, але розділи з кодом у кожного SDK
свої, і лишаються окремими. Звідси й час заливки векторів — близько півтори години на процесорі.

Замір `quality` на першому корпусі: по словах 8 із 10, за змістом 7, разом 7. Промахи не порожні: на питання
«ID і стан сесії в компоненті React» пошук за змістом приносить розділ блогу про `useUser` замість довідника
`useAuth()`, а на «захист від ботів при реєстрації» — огляд безпеки й custom flow з bot sign-up protection замість
гайду `bot-protection`. `passage_context` увімкнено з самого початку, `fusion_depth` не задано.

**Хвіст «Sitemap».** Кожна markdown-сторінка clerk.com закінчується посиланням «Overview of all docs pages» під
заголовком «## Sitemap» — 2 487 фрагментів без змісту, що траплялися у видачі. Читач `llms-heading` зрізає цей
хвіст так само, як `llms` робить це для react.dev. Замір після цього той самий, 8/7/7: ті два промахи від хвоста
не залежали. Старі точки `#sitemap` із колекції `docs-clerk` прибрано точково, за списком сиріт, який друкує
`vectors`; решту колекції не чіпали.

**Варіанти SDK займають одне місце (`variant_pattern` у `config.json`).** Розбір промахів показав, що сторінка Core 3
у 10–12 варіантах забирала кілька місць видачі з п'яти: на питання про `useAuth()` у React перше місце довідника
дістав варіант Astro, другий — Chrome Extension, а варіант React випав. Поле `variant_pattern` каже серверу, що
`docs-astro-…` і `docs-react-…` — та сама сторінка: у видачі від неї лишається одне місце, а якщо запит називає
SDK («…in a React component», «…in Next.js»), місце дістається варіанту саме цього SDK. Як запит називає SDK — поле
`variant_aliases`. Ім'я варіанта в ключі згортання заміняється «*», а не вирізається, тож сторінка Core 2 з тим
самим шляхом (`reference-hooks-use-auth`) лишається у видачі окремо. Замір після цього: по словах 8, за змістом 7,
разом 8 — питання про `useAuth()` тепер влучає. Поле є лише в цьому примірнику; видача решти перевірена
дослівно до і після зміни й не змінилася.

**Промпт веде модель у документацію, а не в блог.** Замір `quality` шукає без фільтра версії, і там блог із
журналом змін змагаються з документацією на рівних: на «захист від ботів при реєстрації» перше місце бере огляд
безпеки, а далі — запис блогу про reCAPTCHA, хоча в Clerk є вбудований захист. Тому `prompts/search.txt` велить
моделі на питання «як зробити зараз» шукати спершу з `version: "core-3"` і називати SDK у запиті. Так обидва
питання-промахи заміру влучають першим місцем: гайд `bot-protection` і довідник `useAuth()` для React. На сам
замір це не впливає — він промпту не читає.

## Що в цій теці

- `corpus/` — документація Clerk звичайними текстовими файлами; поруч `index.json` — паспорт, тобто опис копії:
  адреса, дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями до сайтів і профіль домену: ім'я
  сервера, імена інструментів, домени, посилання на які лишаються у відповідях.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу, див. нижче);
  `.mcp.json` — запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df clerk <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| Core 3, поточна лінія | `clerk.com/docs/llms.txt`, текст кожної сторінки — її markdown-двійник із «.md» | `llms-heading` |
| Core 2 і Core 1 | гілки `core-2` і `core-1` репозиторію `clerk/clerk-docs` | `clerk-mdx` |
| Backend, Frontend, Platform API | специфікації OpenAPI, з яких сайт рендерить довідники | `openapi` |
| журнал змін і блог | `clerk.com/changelog/llms.txt`, `clerk.com/blog/llms.txt` | `llms-heading` |

Читач `clerk-mdx` додано разом із цим примірником окремим модулем (`engine/readers/clerkmdx.py`). З чинних читачів
змінено один: `llms-heading` зрізає хвіст «Sitemap» (див. вище); для nestjs і supabase від цього нічого не
змінилося, бо в їхніх сторінках такого хвоста немає.

Особливості, які варто знати:

- **Архіви — з репозиторію, а не з сайту.** Сторінки `/docs/core-2/…` і `/docs/core-1/…` на сайті є, але
  `robots.txt` clerk.com закриває їх від автоматичного обходу. Той самий текст лежить у публічному репозиторії
  документації, по гілці на лінію, звідки його й беремо.
- **Вставки розгортаються.** Сторінка Core 2 у репозиторії не самодостатня: кроки quickstart-ів лежать окремими
  фрагментами (`<Include src="_partials/…" />`), а таблиці параметрів хуків — у згенерованому довіднику
  (`<Typedoc src="…" />`, тека `clerk-typedoc/`). Читач вставляє їх на місце, інакше в корпус лягли б сторінки з
  дірами. У Core 1 вставок немає.
- **Форма ліній різна.** Core 3 — сторінки такими, як їх віддає сайт: сторінка, що має варіанти для кількох SDK,
  лежить окремим документом на кожен SDK (`/docs/nextjs/…`, `/docs/vue/…`). Core 2 і Core 1 — одна сторінка на
  всі SDK, а блок, призначений лише деяким, починається рядком «SDK: nextjs, react» (або «SDK, except: …»).
  Сторінка для одного SDK відкривається таким рядком одразу під назвою. Промпт велить моделі звіряти цей рядок,
  перш ніж подавати код як спосіб для конкретного SDK.
- **Заголовки з відступом.** У MDX крок усередині `<Steps>` пишеться з відступом («  ## Install …»), і для MDX це
  заголовок, а для markdown ні. Читач зсуває такі заголовки до лівого краю, інакше quickstart ліг би в корпус одним
  розділом.
- **Версія — мітка лінії.** `core-3`, `core-2`, `core-1`; фільтр `version: "core-2"` відбирає рівно архів Core 2.
  Довідники API, журнал змін і блог лінії не мають і знаходяться лише пошуком без фільтра.
- **Адреса в шапці архівного документа** — файл на GitHub у своїй гілці, а не сторінка сайту: саме цей текст і
  завантажено, і за цією адресою його можна звірити.

## Межі, про які треба пам'ятати

Community SDK (Angular, Svelte, SolidJS, Rust, Flutter та інші) живуть поза clerk.com, у своїх репозиторіях, — їх
тут немає. Сторінки C#, Java, PHP і Python на сайті — посилання на GitHub тих SDK, тож їх теж немає. Документації
самих фреймворків (Next.js, Expo, React) тут немає — лише згадки про них у тексті Clerk.

## Токен GitHub

Перелік файлів гілки — одне звернення до GitHub API на гілку, тож для цього примірника токен не обов'язковий:
анонімних 60 звернень на годину вистачає з запасом. Він лежить у `.env` рядком `GITHUB_TOKEN=…` на випадок частих
повторних прогонів. Читається лише звідси й іде лише на `api.github.com` — подробиці в
[README примірника astro](../astro/README.md#токен-github). Тексти файлів ліміту не витрачають: вони йдуть із
`raw.githubusercontent.com`.

## Установка venv

Єдиний крок, що робиться зсередини цієї теки, — і після нього треба повернутися в корінь. Активувати venv не
потрібно ані зараз, ані потім: `df` сам викликає `.venv/bin/python` примірника на кожному кроці.

```
cd instances/clerk
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # за потреби впишіть ANTHROPIC_API_KEY (крок ask) і GITHUB_TOKEN
cd ../..                      # назад у корінь фабрики: усі кроки df — тільки звідти
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, цей розділ пропускається — потрібен лише `vectors`, якщо колекції ще немає.

```
./df clerk sources --why   # перелік джерел і білий список
./df clerk refresh         # завантажити все задеклароване (~1,5 години)
./df clerk manifest        # оновити паспорт
./df clerk setup           # Qdrant чи пошук лише по словах
./df clerk vectors         # залити корпус у docs-clerk (~1,5 години)
./df clerk smoke           # перевірки
```

Порядок оновлення корпусу — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба
перезапустити: корпус сервер читає один раз, на старті.

## Спосіб А — власний захищений агент (усі чотири шари)

```
./df clerk tools                                        # $0: під'єднання, перелік інструментів
./df clerk ask "How do I protect routes in Core 2 with Next.js?"   # платно
```

Клієнт тут — наш код, тож працюють усі чотири шари: вхідний фільтр над запитом, правила перед кожним викликом
інструмента, список дозволених інструментів і вихідний фільтр разом із guardrail. Крок `ask` потребує
`ANTHROPIC_API_KEY` у `.env`; `tools` не потребує нічого.

## Спосіб Б — сервер під Claude Code (HTTP)

**1. Підняти сервер** (окремий термінал, з кореня фабрики `docfactory/`), і лишити його жити:

```
./df clerk serve                  # HTTP-сервер на порту з config.json (8766)
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8766/mcp`.

**2. Додати сервер у Claude Code**: відкрити теку `instances/clerk/` як проєкт (Claude Code побачить `.mcp.json`
і запропонує сервер `clerk-docs`), або командою:

```
claude mcp add --transport http --scope user clerk-docs http://127.0.0.1:8766/mcp
```

**3. Перевірити.** У сесії Claude Code — `/mcp`: має бути `clerk-docs` і два інструменти `search_docs`,
`read_section`.

Решта — зупинка сервера, scope запису, Claude Desktop під Windows, що робити з «address already in use» — так
само, як у [README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http),
змінюються лише ім'я й порт.
