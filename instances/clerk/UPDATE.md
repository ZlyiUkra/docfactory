# Оновлення корпусу clerk

Три різні частини корпусу старіють по-різному, тож і оновлюються різними командами.

| Частина | Джерела | Як часто змінюється |
|---------|---------|---------------------|
| поточна лінія Core 3 | `docs-core3` | щотижня: документацію правлять постійно |
| довідники API, changelog, блог | `api-backend`, `api-frontend`, `api-platform`, `changelog`, `blog` | з кожним релізом і записом |
| архіви Core 2 і Core 1 | `docs-core2`, `docs-core1` | рідко: гілки `core-2` і `core-1` ще отримують виправлення, але нового там не пишуть |

Головне правило: **нічого не видаляється.** Сторінку, яку прибрали з сайту, корпус тримає як була: питання «як це
було» не має ламатися через те, що главу зняли. Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають
самі; зайвий файл у `corpus/` прибирає лише власник, руками.

## 1. Звичайне оновлення

```
./df clerk check                                  # що змінилося нагорі
./df clerk refresh docs-core3 api-backend api-frontend api-platform changelog blog
./df clerk manifest
./df clerk vectors
./df clerk smoke
# Ctrl+C у терміналі з serve, і знову: ./df clerk serve
```

`refresh` із назвами джерел перезаписує всі їхні документи, а нові сторінки докачує. Близько години при паузі в
секунду: майже весь час іде на 2,5 тисячі сторінок Core 3.

Нова сторінка в `llms.txt` сайту з'являється в корпусі сама: перелік сторінок читач бере з `llms.txt` на кожному
прогоні, а `within` дозволяє все під `/docs/`. Так само з новими записами changelog і блогу.

## 2. Архіви

```
./df clerk refresh docs-core2 docs-core1
./df clerk manifest
./df clerk vectors
```

Близько двадцяти хвилин. Перелік файлів гілки — одне звернення до GitHub API на гілку, тексти — з
`raw.githubusercontent.com`, ліміту не витрачають.

## 3. Коли вийде Core 4

Лінія, що зараз поточна, переїде в архів. Кроки:

1. Перевірити, що в репозиторії `clerk/clerk-docs` з'явилася гілка `core-3`:
   `git ls-remote --heads https://github.com/clerk/clerk-docs.git core-3`.
2. У `sources.json` додати джерело `docs-core3-archive` за зразком `docs-core2` (читач `clerk-mdx`, гілка
   `core-3`, версія `core-3`), а у `docs-core3` змінити `version` на `core-4`.
3. Документи Core 3 з сайту (`docs-core3--*.txt`) лишаться в `corpus/` з версією `core-3` у шапці, поруч із
   новими. Чи прибирати їх на користь архівних з гілки — рішення власника: це дві копії тієї самої лінії різної
   форми (на SDK окремо і на всі SDK разом).
4. `refresh`, `manifest`, `vectors`, `smoke`, як вище. Нове число фрагментів записати в `checks.json`.

## Якщо прогін урвався

Повторіть його з `--missing`: уже записані файли не перекачуються, добереться лише відсутнє.

```
./df clerk refresh --missing
```

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df clerk quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія — `core-3`.** Промпти велять на питання «як зараз» шукати з `version "core-3"` і з назвою SDK у
  запиті; у `quality_model` сім записів на `core-3`, один на `core-1`. Коли вийде Core 4 — заміна в
  `prompts/search.txt`, `prompts/agent.txt` і `quality_model` (розділ «3. Коли вийде Core 4» вище).
- **Правила промпту, що вже є:** спершу `core-3` і назва SDK; без фільтра — ендпоінти API, анонси, історія; код з
  архівних ліній — лише для SDK з рядка «SDK:» уривка; запис блогу — як запис блогу, а не офіційний спосіб.
- **Останній результат** — у README, абзаци «Замір `quality`» і «Промпт веде модель у документацію».
