> **Experimental:** This feature is experimental and may change or be removed without notice. If you run into any issues, please reach out to our support team.

Clerk offers the ability to override the strings for all of the elements in each of the Clerk components. This allows you to provide localization for your users or change the wording to suit your brand.

## `@clerk/localizations`

The `@clerk/localizations` package contains predefined localizations for the Clerk components.

### Usage

> The localizations will only update the text in the Clerk components used in your application. The hosted Clerk Account Portal will remain in English.

To get started, install the `@clerk/localizations` package.

```npm
npm install @clerk/localizations
```

Once the `@clerk/localizations` package is installed, you can import the localizations you need by removing the "-" from the locale. You can then pass the localization to the `localization` prop.

To apply a localization, pass the `appearance` prop to the  component. The `appearance` prop accepts the property `localization`, which can be set to the imported localization.

In the following example, the fr-FR locale is imported as `frFR` and applied to all Clerk components.

```tsx
// fr-FR locale is imported as frFR
import { frFR } from '@clerk/localizations'

<ClerkProvider localization={frFR}>
  {/* ... */}
</ClerkProvider>
```

### Bundle size

Each localization lives in its own module and the `@clerk/localizations` package is tree-shakeable, so bundlers with tree-shaking enabled — the default for modern production builds — include only the localizations you import, not every supported language.

> Development builds typically skip tree-shaking, so a bundle analyzer or your browser's network tab may show every language while running your app locally.

To guarantee that only a single language is included, regardless of bundler configuration, import the localization directly from its subpath. The subpath is the language tag, as shown in the Languages table.

```ts
// Imports only the fr-FR localization
import { frFR } from '@clerk/localizations/fr-FR'
```

> In Next.js apps, importing a localization in a Server Component, such as the root layout where `<ClerkProvider>` is typically rendered, keeps the localization strings out of your client-side JavaScript bundles entirely. The strings are sent as part of the server-rendered payload instead.

### Lazy-load localizations

If your app offers multiple languages and selects one at runtime, statically importing every language includes all of them in your bundle, even though each user only needs one. Instead, use a dynamic import with the localization's subpath so that only the selected language is loaded. In client-side code, bundlers split each language into its own chunk and the browser downloads only the selected one. In a Server Component, the import runs on the server instead, and only the selected localization is sent to the browser as part of the server-rendered payload.

The following example lazy-loads the localization for the user's active locale. Call `loadLocalization()` from an async context, such as a Server Component or your app's setup code, and pass the result to the `localization` prop.

```ts
const localizations = {
  'en-US': () => import('@clerk/localizations/en-US').then((mod) => mod.enUS),
  'fr-FR': () => import('@clerk/localizations/fr-FR').then((mod) => mod.frFR),
  'de-DE': () => import('@clerk/localizations/de-DE').then((mod) => mod.deDE),
}

async function loadLocalization(locale: keyof typeof localizations) {
  return localizations[locale]()
}
```

## Adding or updating a localization

Clerk's localizations are customer-sourced and we encourage customers to add or update localizations. To do so, follow these steps:

1. Fork the https://github.com/clerk/javascript/ repo.
2. Clone it locally to edit it.
3. Review Clerk's Contributing guide.
4. If you are updating an existing localization locate the file in `packages/localizations/src`
5. If you are adding a new language, copy the `en-US.ts` file and name it according to your language. The naming is the abbreviated language-region. For example, for French in Canada, it would be `fr-CA.ts.`
6. Go through the file and edit the entries.
7. If you are adding a new localization, add the language to the `packages/localizations/src/index.ts` file.
8. Commit your changes to git and push them to your fork. Create a Pull Request from your fork to Clerk's repo against the `main` branch. We will review and either approve or ask for updates.

## Custom localizations

You can also provide your own localizations for the Clerk components. This is useful if you want to provide limited or quick localization for a language Clerk doesn't currently support, adjust the wording to match your brand, or customize default error messages.

First, you need to find the key for the element that you want to customize. To find the key for your translation, open up Clerk's English localization file. Search the file for the term that you want to customize.

For example, say you want to change the text of the "Continue" button on the `<SignIn />` component to say "LETS GO!". In this case, you'd search for "Continue". The first result that comes up is `formButtonPrimary`, which is the key for the "Continue" button.

Now that you know the key, you can pass it to the `localization` prop and set the value to the text you want to display. In this case, you'd set the value to "LETS GO!", as shown in the following example.

```tsx
// Set your customizations in a `localization` object
const localization = {
  formButtonPrimary: 'LETS GO!',
}

<ClerkProvider localization={localization}>
  {/* ... */}
</ClerkProvider>
```

### Pass multiple keys

You can also customize multiple entries by passing multiple keys. The following example updates the "to continue to" subtitles on the `<SignUp />` component to say "to access" instead.

```tsx
const localization = {
  signUp: {
    start: {
      subtitle: 'to access {{applicationName}}',
    },
    emailCode: {
      subtitle: 'to access {{applicationName}}',
    },
  },
}

<ClerkProvider localization={localization}>
  {/* ... */}
</ClerkProvider>
```

### Customize error messages

You can customize Clerk's default error messages by targeting the `unstable__errors` key. This key lets you define specific error keys for different error types and assign them custom message strings. You can find the full list of error keys in the English localization file. Search for the `unstable__errors` object to find the keys you can customize.

The following example updates the `not_allowed_access` error message. This message appears when a user tries to sign in with an email domain that isn't allowed to access your application.

```tsx
const localization = {
  unstable__errors: {
  not_allowed_access:
    'Send us an email if you want your corporate email domain allowlisted for access',
  },
}

<ClerkProvider localization={localization}>
  {/* ... */}
</ClerkProvider>
```

### Pipe syntax and modifiers

Clerk localization strings support a small template language. Some values will use `{{ variable | modifier(...args) }}` to pass a runtime value through one or more named formatters. Here's what each part means:

- `variable` — the runtime value (for example, a `Date` passed as `date`).
- `|` — the pipe operator; it passes the value to the modifier on its right.
- `modifier(...)` — a named formatter with optional arguments (for example, the `timeString` formatter with the `'en-US'` locale as an argument).

For example: `"Yesterday at {{ date | timeString('en-US') }}"` would take the `date` and apply the `timeString` formatter with the `'en-US'` locale to get the time string in English, like `'12:00 PM'`.

#### Chaining pipes

You can chain pipes so each step receives the result of the previous one.

For example: `{{ date | weekday('en-US','long') | titleize }}` would take the `date` and apply the `weekday` formatter with the `'en-US'` locale and `'long'` style ('Monday' instead of 'Mon') to get a long English weekday name. Then, `titleize` would ensure the long English weekday name is properly capitalized. This is useful because some locales return lowercase weekday names while others capitalize them, so the final output would consistently be something like `'Monday'` rather than `'Mon'` or `'monday'`.
