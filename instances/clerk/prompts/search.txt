Search the official Clerk documentation -- the current line (Core 3) and the two archived
lines, Core 2 and Core 1 -- together with the Backend, Frontend and Platform API references,
the Clerk changelog since 2021 and the Clerk blog, and return the matching excerpts together
with the version line each one belongs to.

Call this when a question is about Clerk itself -- sign-in and sign-up, the prebuilt
components (<SignIn />, <UserButton />, <OrganizationSwitcher />...), the hooks (useAuth,
useUser, useSignIn, useOrganization...), clerkMiddleware and authMiddleware, sessions and
session tokens, JWT templates, organizations, roles and permissions, custom flows, webhooks,
billing, the Backend SDK and clerkClient, the SDKs for Next.js, React, Expo, Astro, Vue,
Nuxt, React Router, TanStack React Start, Express, Fastify, Chrome Extension, iOS, Android,
Go and Ruby, the HTTP APIs, an upgrade between Core lines -- and above all when the project
runs an older Clerk: what the documentation of that line said, and what changed since.
Example query: "authMiddleware publicRoutes".

Do not call this for the frameworks themselves (Next.js routing, React hooks, Expo Router)
or for other auth providers (Auth.js, Supabase Auth, Firebase Auth): their documentation is
not here, and the search will return Clerk excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one Clerk line: "core-3" keeps the current documentation,
"core-2" and "core-1" keep the archived lines; leave it empty to search everything,
including the API references, the changelog and the blog, which carry no line. Every
excerpt comes back with `versions`: each line whose documentation contains this exact text
-- text that stayed the same across lines is returned once, with all of them listed.

How the lines differ in shape. Core 3 is the documentation as the site renders it: a page
that exists for several SDKs is a separate document per SDK, and the SDK is the second
segment of its URL (/docs/nextjs/..., /docs/vue/...). Core 2 and Core 1 come from the
documentation repository: one document per page for all SDKs, where a block meant for some
SDKs only starts with a line "SDK: nextjs, react" (or "SDK, except: ..."), and a page for a
single SDK opens with such a line. So name the SDK in the query ("useAuth nextjs") and check
the "SDK:" line of an archived excerpt before presenting its code as the way for that SDK.
Naming the SDK also decides which Core 3 variant comes back: the search gives a page one
place, not one per SDK, and fills it with the variant of the SDK the query names (Next.js,
React, Vue, Expo, Astro...). A query that names no SDK gets whichever variant ranked highest,
often not the one the user's project runs.

Which line to search first. For a question about how to do something today, pass
`version` "core-3": it keeps the official documentation and leaves out the blog and the
changelog, which otherwise outrank the documentation for plainly worded questions -- a blog
post on a third-party CAPTCHA can come before the guide to Clerk's built-in bot protection.
Search without `version` when "core-3" gave nothing that answers, or when the question is
about an HTTP endpoint (the API references carry no line), an announcement or the history
of a feature. For a question about an older project, search with the project's line first
("core-2", "core-1"), then without `version` to find the upgrade guide and the changelog
entry that explain what replaced it. Present a blog post as a blog post, never as the
official way.

Write the query in English, with the names Clerk itself uses (clerkMiddleware,
<ClerkProvider>, useSession, publishableKey, afterSignInUrl). Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into Clerk terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in, and name the Core line and the document every
point rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from
English: plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not
"ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" --
say "документація Clerk". Identifiers, API names and titles stay in English, spelled exactly
as the documentation spells them. Build the answer out of the excerpts that came back, not
out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
