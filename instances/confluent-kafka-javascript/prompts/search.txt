Search the documentation of the Confluent JavaScript Client for Apache Kafka -- the package
@confluentinc/kafka-javascript, Confluent's client for Node.js built on the librdkafka C library, with a promisified
API compatible with KafkaJS and a callback API compatible with node-rdkafka (repository
confluentinc/confluent-kafka-javascript, guide on docs.confluent.io). The corpus holds the client guide of
docs.confluent.io for the versions 1.0 to 1.11 (installation, choosing between the promisified and the callback API,
producer, consumer, admin client, transactions, rebalancing, committing offsets, configuration); the migration page
from KafkaJS and from node-rdkafka; the documents of the repository taken from the tag of every minor version from 0.2
to 1.11 (INTRODUCTION.md with the full description of both APIs, MIGRATION.md with every KafkaJS option and method that
behaves differently, QUICKSTART.md, CONTRIBUTING.md, the README of the Schema Registry client); the README of every
stable version of the package; the configuration properties of the librdkafka bundled in every version
(`deps/librdkafka/CONFIGURATION.md`: every property with its range, default, importance and description); the
changelog of every version from 0.1 to 1.11; and the npm registry history of the package (date of every version,
dist-tags, the Node.js requirement). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about this client as it describes itself -- how to create a producer or a consumer with
the promisified API (`new Kafka().producer()`, `consumer.run({ eachMessage })`) or the callback API
(`Producer`, `KafkaConsumer`), what a configuration property does and its default (`bootstrap.servers`,
`enable.auto.commit`, `auto.offset.reset`, `linger.ms`, `acks`, `enable.idempotence`), how the `kafkaJS` block of the
configuration maps to librdkafka properties, what differs from KafkaJS when migrating, how transactions, rebalance
callbacks and manual commits work -- and above all history and compatibility: since which version a feature exists,
what changed between versions (every changelog entry lists enhancements and fixes and the librdkafka version it
ships), which Node.js a version requires, and when every version came out.

Do not call this for Apache Kafka itself (broker and topic configuration, replication, the protocol, KRaft), KafkaJS
as its own library, node-rdkafka, Confluent Cloud and Confluent Platform, ksqlDB or Kafka Connect, nor for the
librdkafka C API: their documentation is not here -- these pages only show how this client uses them -- and the search
will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. The client carries plain numbers: a line of one number keeps every
document of that major ("1" keeps 1.0.0 to 1.11.0), two numbers keep a minor ("1.10"), three an exact version
("1.10.1"); the documents of the repository carry the version of the tag they were taken from (the last patch of every
minor), the guide of docs.confluent.io the versions of the site that showed this text. Leave `version` empty to search
everything, including text that carries no version. Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first -- a page that stayed the same across versions is returned once, with
all of them listed, so the list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("promisified API", "callback API",
"kafkaJS", "eachMessage", "eachBatch", "KafkaConsumer", "HighLevelProducer", "rebalance_cb", "enable.auto.commit",
"auto.offset.reset", "bootstrap.servers", "linger.ms", "enable.idempotence", "transactional.id", "commitOffsets",
"librdkafka", "migration from KafkaJS"), not in the user's own words. Everything here is English -- the excerpts, the
word index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query written
in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the
user asks in another language, translate the question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація клієнта Confluent". Identifiers, property names and titles stay in English, spelled exactly as
the documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt
was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads on npm (October 2026) 1.10.0 leads with about 22 % and 1.10.x
with about 31 %; 1.9.x has about 20 %, 1.8.2 about 13 %, 1.3.2 about 12 %; 1.11.0 of 7 October 2026 is the newest.
Answer how-to questions for 1.10: search `version` "1.10", and when the question touches what is new, search "1.11"
too and say where they differ. Search without `version` when the question is about history, or when the line gave
nothing. Every answer says which version it is for; when the excerpts behind a statement come only from older
versions, name those versions instead of presenting the text as current.
