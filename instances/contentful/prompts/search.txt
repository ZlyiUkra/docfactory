Search the documentation of Contentful -- the API-first headless content platform (the developer documentation of
contentful.com, the repositories of the official Contentful SDKs and tools on GitHub, the npm registry). The corpus
holds the pages of contentful.com/developers/docs as they stand now: the concepts (the data model of spaces,
environments and environment aliases, content types, entries, assets, locales, links and references, external
references, rich text, the sync API, images, the deployment pipeline); the API reference -- the Content Delivery API
(CDA), the Content Preview API (CPA), the Content Management API (CMA), the GraphQL Content API, the Images API, the
User Management and SCIM APIs, authentication, API basics, rate limits and technical limits; the extensibility pages
(the App Framework, app definitions, app locations, app actions and app events, functions, the App SDK, UI
extensions, webhooks and their filters, OAuth); the SDK pages (JavaScript, .NET, Java, Android, iOS, PHP and others);
the tutorials (the CLI, content preview, live preview, migrations, scripting, general guides); Compose, Experiences
(Studio) and Personalization (Ninetailed). It also holds the README and documentation files of the official
repositories at the last tag of every minor -- contentful.js (the `contentful` delivery client, 0.0–11.12),
contentful-management.js (the management client, 0.0–12.19), contentful-cli (with the reference of every command),
contentful-migration, contentful-import, contentful-export, rich-text (`@contentful/rich-text-types` and the React,
HTML and plain-text renderers, from-markdown), the App SDK (`@contentful/app-sdk`, formerly
contentful-ui-extensions-sdk), live-preview (`@contentful/live-preview`, `@contentful/content-source-maps`), the
Experiences SDK (`@contentful/experiences-sdk-react`), create-contentful-app (with app-scripts, react-apps-toolkit
and node-apps-toolkit) and the Contentful MCP server; the GitHub releases of these repositories; and the npm registry
entry of twenty of their packages with release dates. Returns the matching excerpts with the versions each one
belongs to.

Call this when a question is about Contentful as it describes itself -- how to model content (content types, fields,
validations, references, rich text), how to query entries and assets through the CDA or GraphQL (search parameters,
`include` and linked entries, locales, `select`, ordering, pagination, the sync API), how to write content through the
CMA (create, update with `X-Contentful-Version`, publish, archive, bulk actions, releases, scheduled actions, tags,
environments and aliases), how to authenticate (delivery, preview and management tokens), what the rate and technical
limits are, how to build an app with the App Framework and the App SDK, how to set up webhooks, how to use the
JavaScript SDKs (`createClient`, `getEntries`, `withAllLocales`, `withoutLinkResolution`, the plain client of
contentful-management), how to render rich text in React or HTML, how to script migrations and import or export a
space with the CLI, how to set up live preview -- and history: since which version an SDK function or option exists,
what changed between major versions (the MIGRATION files and the releases list it).

Do not call this for Next.js, React, Gatsby, GraphQL, Node.js or TypeScript as their own projects: their documentation
is not here -- these pages only show how Contentful is used with them -- and the search will return excerpts that
merely mention them, with confident-looking titles. The Help Center of contentful.com (the web app for editors) and
the Forma 36 design system are not here either; neither are the pages of the developer documentation that the site
did not link from any other page.

`version` narrows the search to one release line of a package: a line of one number keeps every document of that
major ("11" keeps 11.x), two numbers keep a minor ("10.6"), three an exact version ("11.5.25"). Mind that every
package has its own numbering -- 11 is a line of `contentful`, of `contentful-management` and of
`contentful-cli`-era tools alike -- so name the package in the query along with the version. The pages of the site
carry no version: they describe the platform as it is today. Every excerpt comes back with `versions`: each version
whose documents contain this exact text, newest first.

Write the query in English, with the names the documentation itself uses ("space", "environment", "environment
alias", "content type", "entry", "asset", "locale", "Link", "include", "sys.id", "fields", "Rich Text", "sync",
"Content Delivery API", "Content Preview API", "Content Management API", "GraphQL", "Images API", "X-Contentful-Version",
"webhook", "App Framework", "app definition", "app action", "function", "createClient", "getEntries",
"withAllLocales", "withoutLinkResolution", "documentToReactComponents", "documentToHtmlString", "contentful space
export", "migration", "live preview", "content source maps"), not in the user's own words. Everything here is English
-- the excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters and digits,
so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into the terms of the documentation first,
then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація Contentful". Identifiers, parameters and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
