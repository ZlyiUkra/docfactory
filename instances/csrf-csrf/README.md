# csrf-csrf — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про `csrf-csrf` — пакет npm для захисту застосунків Express від CSRF
(Cross-Site Request Forgery, підробка міжсайтового запиту) за схемою підписаного Double Submit Cookie (репозиторій
Psifi-Solutions/csrf-csrf) — за документацією всіх його стабільних версій: README кожної версії (сайту пакет не має,
README і є документацією), FAQ, посібник переходу між мажорами, журнал змін, приклади репозиторію та історія версій у
реєстрі npm. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані
домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

CSRF — атака, коли чужий сайт змушує браузер користувача надіслати запит на ваш сервер разом із cookie сесії. Захист —
токен, якого чужий сайт не знає. `csrf-csrf` робить це без зберігання токенів на сервері: токен — HMAC від
ідентифікатора сесії (`getSessionIdentifier`), секрету (`getSecret`) і випадкового значення; одна копія лежить у cookie
(`__Host-psifi.x-csrf-token`), другу клієнт шле в заголовку `x-csrf-token`, і `doubleCsrfProtection` порівнює їх на
кожному запиті, крім `GET`, `HEAD` і `OPTIONS`. Колишній `csurf` застарів, документація NestJS радить саме цей пакет.
У плані NestJS (фулстек-родина) це захист форм і запитів з cookie-автентифікацією.

За чотири мажорні лінії API мінявся: у 4.0 `generateToken` став `generateCsrfToken`, `getTokenFromRequest` —
`getCsrfTokenFromRequest`, `delimiter` — `csrfTokenDelimiter`, `getSessionIdentifier` став обов'язковим, `signed`
вилучено, а формат токена змінився. Що саме і як оновитися без розлогінювання всіх — у UPGRADING.md, що мінялося в
кожній версії 3.x–4.x — у журналі змін, дата кожної версії — у реєстрі npm. Усе це в одному місці, з номером версії
біля кожного уривка.

Разом 48 документів; фрагментів в індексі — 235 (`expected_passages` у `checks.json`). Замір `quality`: по словах 7 із
10, за змістом 7, разом 7, «як модель» 10 із 10. Перша десятка нижча: README один на всі теми, і три питання своїми
словами (дати браузеру токен, прив'язати токен до сесії, отримати токен у React) потрапляють не в той розділ, що в цілі;
друга десятка — назвами документації — влучає всюди.

Чому README береться і з tarball кожної версії, і з гілки main. Tarball — точно те, що отримує `npm install`, і питання
про 3.x дістає текст 3.x. Але README 4.0.3 у прикладах налаштування пише опції через «=» замість «:» (код не
компілюється); у main це виправлено вже після випуску, тож виправлений текст стоїть окремим документом.

Заголовки README записано тегами HTML (`<h2>`, `<h3>`), а не «##»: без поля `html_headings` у `sources.json` README
лишався б одним безіменним розділом на 15 частин, і пошук не міг би назвати, з якого розділу уривок.

Релізів на GitHub репозиторій не публікує, а журнал змін починається з 3.0.0: що мінялося в 1.x–2.x, видно лише з
README цих версій і реєстру. Тегів для 4.0.1–4.0.3 у репозиторії немає.

Чого немає. Документації Express, express-session, cookie-parser, helmet, cors і NestJS: README, FAQ і приклади лише
показують, як `csrf-csrf` під'єднується до них. Коду й типів пакета: README описує кожну опцію й функцію. Сусіднього
пакета `csrf-sync` того ж автора (схема Synchronizer Token) — вирішено не брати.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа. Самих
  текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише
  для завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df csrf-csrf <крок>`.

## Версії

Версія — номер випуску. Фільтр `version` бере мажор (`"4"`), мінор (`"3.2"`) або точну версію (`"3.2.2"`). Без
названої версії промпт велить шукати для лінії 4 — на неї за тиждень до 24.10.2026 припадало близько 76 % завантажень
(4.0.3, найновіша, від 27.05.2025, сама — 75 %), на лінію 3 близько 22 % (3.2.2 — 13 %), на лінію 2 близько 2 %; де
3.x відрізняється (UPGRADING.md, журнал 4.0.0), модель згадує й її. FAQ, UPGRADING.md, SECURITY.md, README гілки main
і приклади мають версію 4.0.3: вони описують поточну лінію. README, що не змінився між версіями, — один документ з
усіма ними, тож перелік версій уривка сам показує, відколи й доки документація казала саме це.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/csrf-csrf-corpus-2026-10-24.tar.gz` (48 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском) і в копії на Windows-диску
`C:\Distr\csrf-csrf-corpus-2026-10-24.tar.gz` (звірено за SHA-256). В історії git текстів немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/csrf-csrf/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/csrf-csrf-corpus-РРРР-ММ-ДД.tar.gz -C instances/csrf-csrf corpus raw
find instances/csrf-csrf/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/csrf-csrf/raw
gzip -9 -c instances/csrf-csrf/index/passages.json > instances/csrf-csrf/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/csrf-csrf-corpus-2026-10-24.tar.gz -C instances/csrf-csrf
./df csrf-csrf smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/csrf-csrf/index/passages.json.gz`,
далі `./df csrf-csrf vectors` заллє колекцію Qdrant (секунди на відеокарті, менше хвилини на процесорі).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df csrf-csrf …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md, розділ
«Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df csrf-csrf sources --why   # перелік джерел і білий список
./df csrf-csrf refresh         # завантажити все задеклароване (близько хвилини)
./df csrf-csrf manifest        # оновити паспорт
./df csrf-csrf setup           # Qdrant чи пошук лише по словах
./df csrf-csrf vectors         # залити корпус у docs-csrf-csrf
./df csrf-csrf smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df csrf-csrf serve          # порт 8881
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8881/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user csrf-csrf-docs http://127.0.0.1:8881/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `csrf-csrf-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у [README
примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
