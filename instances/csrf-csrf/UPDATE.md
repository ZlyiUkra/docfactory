# Оновлення корпусу csrf-csrf

Перелік версій тут не оголошується руками: читачі README і реєстру беруть його з опису пакета в реєстрі npm
(`https://registry.npmjs.org/csrf-csrf`), тож нова версія потрапляє в корпус сама, коли вийде. README гілки main, FAQ,
UPGRADING.md, SECURITY.md, журнал змін і приклади беруться з гілки `main` репозиторію `Psifi-Solutions/csrf-csrf`:
оновлення підхоплює їхню поточну редакцію.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df csrf-csrf check                 # чи змінилося щось нагорі за джерелом
./df csrf-csrf refresh               # повне перезавантаження, близько хвилини
./df csrf-csrf manifest
./df csrf-csrf vectors
./df csrf-csrf smoke
# Ctrl+C у терміналі з serve, і знову: ./df csrf-csrf serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (README, що не змінився, дописує нову версію в рядок `# версія:`).

Документи з гілки main (README main, FAQ, UPGRADING.md, SECURITY.md, приклади) мають версію, записану в `sources.json`
полем `version` (і ключем `tags` для README main): з новою версією пакета її міняють там на нову.

Якщо вийшла нова мажорна лінія (5.0):

- у `prompts/search.txt` (абзац «Which version to search first» і перелік ліній) та `prompts/agent.txt` замінити
  поточну лінію на нову, а версію за замовчуванням звірити з числом завантажень
  (`https://api.npmjs.org/versions/csrf-csrf/last-week`): відповідь іде для найпопулярнішої лінії, а коли дві майже
  рівні — для обох; на 24.10.2026 лінія 4 мала 76 %, лінія 3 — 22 %, лінія 2 — 2 %;
- у `checks.json`, у десятках `quality` і `quality_model`, замінити лінію там, де питання про поточну поведінку, і звірити
  цілі (ціль «що ламає оновлення» показує на UPGRADING.md і запис журналу X.0.0).

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) не обов'язковий: звернень до API GitHub тут два — дерево гілки main
для README і для прикладів.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df csrf-csrf quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
