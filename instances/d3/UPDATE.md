# Оновлення корпусу d3

Перелік версій тут не оголошується руками: знімки сайту (`docs`, читач `ghsite-dated-vue`), README і `API.md`
(`npm-readme-*`, `npm-api-d3`) та реєстр (`npm-*`) беруть версії з опису пакетів у реєстрі npm, тож новий реліз d3 чи
модуля потрапляє туди сам, а релізи GitHub (`releases-*`) і зошити Observable (`observable`) читаються з API щоразу
заново. Передрелізи не беруться (`only` у знімку, `skip_versions: "-"` у README, `ghreleases-stable` — без дефіса в
номері).

Руками оголошено:

- **Новий модуль D3** — три джерела за зразком наявних: `npm-readme-d3-<ім'я>`, `npm-d3-<ім'я>`,
  `releases-d3-<ім'я>`, з префіксом версії `d3-<ім'я>-`. Сторінки модуля на d3js.org `docs` підхопить сам (тека
  `docs/`).
- **Зошити поза збірками.** Поле `notebooks` джерела `observable` — зошити, на які посилається d3js.org, але яких немає
  в жодній збірці `@d3`. Нова збірка `@d3` підхоплюється сама.
- **Закріплені джерела** (`api-reference-3x`, `changes`) стоять на коміті й оновлюються лише заміною SHA в адресі й
  `within` та названим `refresh`. Довідник 3.x більше не змінюється; `CHANGES.md` дописують лише з новим мажором.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df d3 refresh docs npm-readme-d3 npm-api-d3 npm-d3 releases-d3   # і джерела модуля, що змінився
./df d3 refresh observable       # зошити Observable — коли галерея поповнилася
./df d3 refresh --missing        # джерела, яких не названо, лише докачуються
./df d3 manifest
./df d3 vectors
./df d3 smoke
# Ctrl+C у терміналі з serve, і знову: ./df d3 serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінна сторінка дописує нову версію в рядок `# версія:`). Документи редакцій, яких
у новому прогоні вже немає, лишаються в теці — їх переносять в окрему теку поза корпусом руками, перш ніж рахувати
вектори. Сховище сирого `raw/` повертається з архіву разом із текстами, тож після правки читача тексти
перебудовуються без мережі: `./df d3 build <id>`.

Якщо змінилася найпоширеніша лінія (на 29.10.2026 — 7.9, близько 95 % завантажень d3):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінію за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"7.9"` там, де питання про поточну поведінку, і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у `.env`) потрібен для історії комітів і дерева сайту та релізів 43 репозиторіїв.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df d3 quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Останній результат — у README, розділ «Скільки цього».
