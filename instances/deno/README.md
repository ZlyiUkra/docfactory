# deno — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Deno за його документацією: сайт docs.deno.com (Runtime, конфігурація
`deno.json`, дозволи, TypeScript, сумісність із Node.js і npm, перехід з Node.js, довідник CLI, тести, лінтер, форматер,
робочі простори, Web API, Deno KV, Deno Deploy, Subhosting, Sandbox, правила лінтера, посібники й приклади) на кожну
мінорну 1.37–2.9, старий посібник 1.0–1.36, довідник API з файлів типів `lib.deno.*.d.ts` кожної мінорної 1.0–2.9,
журнал змін і релізи, запис npm пакета `deno`, усі дописи блогу deno.com, документація реєстру JSR і стандартна
бібліотека `@std/*`. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі
дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

Deno — середовище виконання JavaScript і TypeScript від автора Node.js, яке розглядають як альтернативу Node: TypeScript
без збирання, дозволи замість повного доступу за замовчуванням, вбудовані тести, лінтер, форматер і `deno compile`, а з
2.0 — сумісність із `package.json`, `node_modules` і пакетами npm. Примірник `nodejs` описує сам Node; тут — Deno з
усією його історією версій, щоб порівнювати й переносити проєкт, знаючи, з якої версії що працює.

Разом 6 727 записів паспорта. В індексі 30 557 фрагментів (`expected_passages` у `checks.json`). Замір `quality`:
по словах 3 із 10, за змістом 4, разом 4, «як модель» 10 із 10. Перша десятка своїми словами низька: сайт тримає кожну
тему в кількох місцях і в кількох редакціях (посібник 1.x, сайт 1.37–1.46, перебудований сайт 2.x, посібники в
`examples/tutorials`), а блог описує ті самі можливості в нотатках до випусків. Запити назвами документації знаходять
ціль усі.

**Нестабільні пакети `@std`.** Дванадцять пакетів стандартної бібліотеки ще не мають жодної версії 1.0: `cache`, `cbor`,
`datetime`, `dotenv`, `ini`, `io`, `log`, `math`, `random`, `tar`, `webgpu`, `xml`. Вони тут на кожну свою мінорну 0.x
(`datetime`, `dotenv`, `io` — 0.196–0.225, `log` — 0.196–0.224, `ini` — 0.209–0.225, `webgpu` — 0.209–0.224, решта — одна
чи дві мінорні), і кожен їхній документ під шапкою несе рядок «Unstable package (0.x) … Нестабільний пакет» — правило
`redact` у `config.json` вставляє його за міткою версії `std-<пакет>-0.N`. Стабільні пакети беруться лише від 1.0: їхні
0.x — передрелізна історія, яку ніхто не просив.

Чого немає:

- Передрелізів (`2.0.0-rc.*`), канарних збірок і нічних версій.
- Згенерованих сторінок довідника docs.deno.com/api: замість них — самі файли типів, з яких сайт їх генерує.
- Старої монолітної стандартної бібліотеки `deno.land/std@0.x` до появи JSR (до 0.196) і сторонніх модулів `deno.land/x`.
- Fresh та інших фреймворків — це окремі продукти.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа. Самих
  текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого підіймається сервер. У git лежить стиснений `passages.json.gz`; розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки будується корпус. Він же білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише
  для завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df deno <крок>`.

**Знімки сайту.** Версійних тегів у `denoland/docs` немає. Знімок мінорної — останній коміт main перед виходом
наступної мінорної (дата `x.y.0` — з релізів GitHub), для 2.9 — стан main на 31.10.2026. Коміти записано в `tags`
джерела `site`. До вересня 2023 посібник жив у `denoland/manual` (теги на кожен патч), до 1.12 — у теці `docs/` самого
Deno. Сайт двічі міняв будову (Docusaurus 1.37–1.46: `runtime/manual/…`; Lume з 2.0: `runtime/fundamentals/…`,
`runtime/reference/…`; з 2.8 тести — `runtime/test/…`), тож та сама тема в різних редакціях має різні імена сторінок.

**Довідник API.** Читач `ghcode-history-dts` зроблено для цього примірника: у `lib.deno.ns.d.ts` весь простір `Deno` —
один блок `declare namespace Deno { … }`, і спільний `ghcode-history-ts` дав би кілька розділів на двісті тисяч символів.
Тут розділ — кожне оголошення з повною назвою (`## function Deno.readFile`, `## interface Deno.ServeOptions`), член
інтерфейсу чи класу — підрозділ (`### Deno.Kv.atomic()`), сигнатури перевантаження зливаються в один розділ.

**Стандартна бібліотека.** До 0.224 бібліотека мала одну спільну версію (теги `0.N.P`), далі кожен пакет нумерується
окремо і виходить з тегу `release-РРРР.ММ.ДД`; який тег дав яку версію — з `Releases.md` бібліотеки. Беруться файли
пакета без тестів, бенчмарків і службових `_*.ts`: опис JSDoc у них і є тим, що показує jsr.io.

## Версії

Deno — без префікса: `version: "2"` бере всі документи 2.x (сайт, типи API, журнали, релізи, npm), `"2.9"` чи `"1.46"`
— одну мінорну. Сайт JSR і блог версії не мають. Пакети стандартної бібліотеки — з префіксом пакета, щоб нумерації не
змішувалися з Deno: `"std-fs-1.0"`, `"std-http-1.0"`, нестабільні — `"std-datetime-0.225"`. Журнал випусків `@std` —
`std-РРРР.ММ.ДД`.

Без версії поточна документація стоїть попереду: поле `demote` у `config.json` опускає на п'ять місць документи епохи
1.x (посібники `manual-…`, сайт 1.37–1.46 `site-runtime-manual-…` і `site-kv-manual-…`). З `version` вони знаходяться
як і раніше, бо фільтр лишає саме їх.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку. У `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant. Відповіді ті самі до символа, бо кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/deno-corpus-2026-10-31.tar.gz` (6 727 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів архів розпаковано окремо й звірено з диском) і в копії на Windows
`C:\Distr\deno-corpus-2026-10-31.tar.gz` (звірено за SHA-256). В історії git текстів немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/deno/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/deno-corpus-РРРР-ММ-ДД.tar.gz -C instances/deno corpus raw
find instances/deno/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/deno/raw
gzip -9 -c instances/deno/index/passages.json > instances/deno/index/passages.json.gz
```

Після цього закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Тексти й сховище видаляють лише тоді,
коли архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із текстами повертається сховище сирого:

```
tar -xzf ~/archives/docfactory/deno-corpus-2026-10-31.tar.gz -C instances/deno
./df deno smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Їхні
перевірки `smoke` чесно пропускає з позначкою «корпус в архіві».

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/deno/index/passages.json.gz`.
Далі `./df deno vectors` заллє колекцію Qdrant: менше хвилини на відеокарті, довше на процесорі.

## Установка venv

Власний venv цьому примірнику не потрібен: `./df deno …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як збудувати його один раз і як `df` обирає між ними — у кореневому README, розділ
«Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df deno sources --why   # перелік джерел і білий список
./df deno refresh         # завантажити все задеклароване (близько години: 2 383 тексти сайту й 160 тегів @std)
./df deno manifest        # оновити паспорт
./df deno setup           # Qdrant чи пошук лише по словах
./df deno vectors         # залити корпус у docs-deno
./df deno smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити його працювати:

```
cd ~/Projects/docfactory
./df deno serve          # порт 8938
```

Сервер готовий, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8938/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user deno-docs http://127.0.0.1:8938/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування. Вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell або додати сервер кнопкою «Add server» у вікні
`/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` має показати `deno-docs` і два інструменти: `search_docs` і `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта (scope запису, «address already in use») — так само, як у [README
примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
