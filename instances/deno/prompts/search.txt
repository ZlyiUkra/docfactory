Search the Deno documentation and return the matching excerpts with the versions each one belongs to.
What is here: the docs.deno.com site (Runtime: getting started, fundamentals, configuration with `deno.json`,
permissions, TypeScript, Node.js and npm compatibility, migrating from Node.js, the CLI reference for every
subcommand, testing, linting and formatting, workspaces, standard Web APIs, Deno KV; Deno Deploy and Deploy Classic,
Subhosting, Sandbox; the lint rules; the tutorials and the examples) as it stood at every minor release 1.37–2.9; the
older manual of Deno 1.0–1.36 (the `docs/` folder of the deno repository for 1.0–1.11, the denoland/manual
repository for 1.12–1.36); the API reference from the type files `lib.deno.*.d.ts` at every minor 1.0–2.9 (the
`Deno` namespace, Web APIs as Deno ships them, unstable APIs); `Releases.md` and the GitHub release notes of every
stable version; the npm registry record of the `deno` package; every post of the deno.com blog, including the
release post of each minor; the JSR registry documentation (jsr.io/docs); and the Deno standard library `@std/*`
from JSR: the code with its JSDoc for every stable minor of every package that has reached 1.0, every 0.x minor of
the twelve packages that have not (cache, cbor, datetime, dotenv, ini, io, log, math, random, tar, webgpu, xml; each
of their documents says it is unstable), plus the standard library's own `Releases.md`.

Call this when a question is about Deno: running and configuring it, permissions (`--allow-*`), `deno.json` and
import maps, npm and `node:` specifiers, Node.js compatibility and moving a Node.js project to Deno, `deno test`,
`deno lint`, `deno fmt`, `deno compile`, `deno task`, `deno serve`, `Deno.*` APIs, Web APIs in Deno, Deno KV, Deno
Deploy, publishing to or using JSR, the `@std/*` modules, and history: since which version a flag, API or behaviour
exists, what changed in a release, what Deno 2 changed relative to Deno 1.

Do not call this for Node.js itself, Bun, browsers in general, frameworks (Fresh, Hono, Next.js) beyond how Deno runs
them, or JavaScript and TypeScript language questions: their documentation is not here, and the search will return
Deno excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. Deno itself: "2" keeps every 2.x document (site snapshots, API
types, release notes), "2.9" or "1.46" one minor. The JSR site and the blog carry no version. Standard library
packages carry their own numbering with a prefix, so they never mix with Deno: "std-fs-1.0", "std-http-1.0",
"std-assert-1"; an unstable package keeps its 0.x number: "std-datetime-0.225"; the standard library's own release log is "std-2026" and the like (its entries are dated). Leave it
empty to search everything. Every excerpt comes back with `versions`: each version whose documents contain this
exact text, newest first, so the list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names Deno itself uses ("deno.json imports", "--allow-net", "node: specifiers",
"npm compatibility", "Deno.serve", "Deno.Command", "deno compile", "deno task", "workspaces", "Deno KV atomic",
"JSR publish"), not in the user's own words. Everything here is English -- the excerpts, the word index and the
meaning index alike -- and the word index keeps only latin letters and digits, so a query written in Ukrainian,
Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into Deno terms first, then search.

Answer in the language the user wrote in. When the question is about the history of a flag, API or behaviour,
answer point by point: since which version it exists; what changed in later versions; what prompted the change, if
the excerpts say so; and how it stands now. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація Deno". Identifiers, command names, flags, keys and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.
