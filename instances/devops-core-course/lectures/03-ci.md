# Лекція 3. Конвеєр CI і чужий код у ньому

У лабораторній 3 перевірка, збірка й публікація образу виконуватимуться самі на кожну зміну. Лекція пояснює, як
влаштований такий конвеєр на GitHub Actions, а головну увагу приділяє **ланцюгу постачання**: чужому коду, якому ти
довіряєш свої секрети. Читання займе близько 30 хвилин.

Основи GitHub Actions для образів є також у [плані Docker](../../docker/LEARNING.md), фаза 4, день 4.

**Після лекції ти зможеш пояснити:**

- чому однакові кроки на кожну зміну прибирають суперечку «у мене працює»;
- чому тег дії можна підмінити, а повний хеш коміту ні, і чого хеш усе ж не вирішує;
- що дає `permissions:` і чому `GITHUB_TOKEN` не потребує ротації;
- чому зелена позначка нічого не блокує, а обов'язкова перевірка блокує;
- чому фільтр шляхів і обов'язкові перевірки можуть зупинити злиття.

## Звідки береться проблема

П'ятеро розробників три тижні працюють кожен у своїй гілці. У п'ятницю всі зливають зміни в основну гілку. Конфлікти
розв'язують кілька годин, а основна гілка лишається зламаною цілий тиждень. Перевірку й публікацію людина робить
вручну, тому хтось колись забуде запустити тести.

**Безперервна інтеграція**, CI (Continuous Integration), розв'язує це так: кожна зміна часто потрапляє у спільну гілку
й щоразу автоматично проходить той самий набір кроків. Машину для цього створює сервіс, тому на результат не впливає
те, що встановлено на твоєму ноутбуці.

Курс розрізняє три близькі поняття:

| Назва | Що відбувається автоматично | Хто вирішує про випуск |
|-------|-----------------------------|------------------------|
| Continuous Integration | Збірка й тести на кожну зміну | Випуску ще немає |
| Continuous Delivery | Кожна успішна зміна готова до випуску | Людина натискає кнопку |
| Continuous Deployment | Кожна успішна зміна одразу йде у випуск | Ніхто, усе робить конвеєр |

Лабораторна 3 дає лише першу частину й публікацію образу. Випуск у кластер прийде в лабораторній 13.

## Будова конвеєра

**Робочий процес** (workflow) — це файл YAML у теці `.github/workflows/`. У ньому описано, коли запускатися й що
робити. Подивимося на приклад для бібліотеки на Node.js, бо твій файл лабораторна просить написати самостійно.

```yaml
name: Library checks
on:
  pull_request:
  push:
    branches: [master]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-24.04
    strategy:
      matrix:
        node: [22, 24]
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test
```

| Частина | Що означає |
|---------|------------|
| `on:` | Події, на які запускається робочий процес |
| `permissions:` | Що дозволено токену цього запуску |
| `jobs:` | Завдання. Кожне отримує окрему чисту машину, тому файли самі між завданнями не передаються |
| `runs-on:` | Який образ машини використовувати. Таку машину називають **виконавцем** (runner) |
| `strategy.matrix` | Повторює завдання для кожного значення: тут для двох версій Node.js |
| `steps:` | Кроки всередині завдання |
| `uses:` | Запускає **дію** (action): готовий код із чужого або твого репозиторію |
| `run:` | Запускає команду оболонки |

За замовчуванням завдання працюють паралельно. Слово `needs:` змушує одне завдання чекати на успіх іншого. Без нього
образ опублікується навіть тоді, коли тести впали.

## Головне: дія є чужим кодом поруч із твоїми секретами

Рядок `uses: some/action@v4` виглядає як налаштування. Насправді він наказує завантажити чужий код і виконати його на
машині, де є твій код, токен і, можливо, секрети. Тому **закріплене в цьому рядку і є твоєю поверхнею атаки**:
переліком місць, через які зловмисник може дістатися до секретів.

```text
посилання          що це                   чи можна підмінити
@main              гілка                   змінюється з кожним комітом
@v4                рухомий тег             автор регулярно переносить його
@v4.2.2            тег із точним виглядом  можна перенести так само
@11bd719…c9af683   повний хеш коміту       ні: хеш обчислено з вмісту
```

Тег у git є лише назвою, що вказує на коміт, і власник репозиторію може перенести її на інший коміт. Хеш коміту,
навпаки, обчислено з самого вмісту, тому інший вміст матиме інший хеш.

**Випадок 1.** У березні 2025 року зламали дію `tj-actions/changed-files`, якою користувалися понад 23 000
репозиторіїв. Ось що сталося за [оповіщенням GitHub](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3):

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | Зловмисник | Отримав доступ і переніс теги дії на свій коміт, зокрема теги з точним виглядом, такі як `v44.5.1` |
| 2 | Твій конвеєр | Запускається як завжди. Рядок `uses` не змінився, тому ніхто нічого не помітив |
| 3 | Шкідливий код | Читає пам'ять процесу виконавця й дістає звідти секрети |
| 4 | Шкідливий код | Друкує секрети в журнал запуску у вигляді base64 |
| 5 | Будь-хто | У публічному репозиторії читає цей журнал |

**Випадок 2.** У березні 2026 року атака дійшла до самого сканера Trivy. За [оповіщенням
проєкту](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23) зловмисники випустили
зловмисний `v0.69.4`, а також перенесли 76 із 77 тегів дії `trivy-action` і всі теги `setup-trivy`. Пізніше на Docker
Hub з'явилися зловмисні образи `v0.69.5` і `v0.69.6`. Цей випадок показує, чому перелік «надійних» інструментів не
замінює закріплення: інструмент, який мав шукати вразливості, сам став шляхом атаки.

**Чого хеш не вирішує.** Є дві межі. Перша: те саме оповіщення каже, що старий хеш `trivy-action` дає чистий код самої
дії, але ця дія всередині завантажувала `setup-trivy` за тегом. Отже, хеш захищає лише те, що ти назвав прямо. Друга:
хеш ніколи не отримає виправлень сам, тому потрібен інструмент оновлення на зразок Dependabot, а кожне оновлення варто
переглядати.

**Практичне правило курсу:** дії самого GitHub можна закріплювати тегом основної версії, наприклад `@v4`, а чужі й
ризиковані дії закріплюють повним хешем із коментарем про версію. [Документація
GitHub](https://docs.github.com/en/actions/reference/security/secure-use) суворіша: вона радить хеш загалом, а тег
лише тоді, коли ти довіряєш автору.

## `permissions:` і `GITHUB_TOKEN`

На початку кожного завдання GitHub створює `GITHUB_TOKEN`: тимчасовий токен із правами на цей репозиторій. Він зникає,
коли завдання закінчується, а на машинах GitHub не пізніше ніж за 6 годин. Тому його не треба ротувати: немає
довготривалого значення, яке треба міняти. Цей захист обмежений: під час роботи завдання токен лишається дійсним, а
шкідлива дія може його вкрасти й використати.

Саме тому важливе `permissions:`. Токен має лише те, що дозволено. Правило плану таке: **читання за замовчуванням,
запис у реєстр лише тому завданню, яке публікує**. Шкідлива дія в завданні з тестами тоді не зможе опублікувати образ.

## Перевірка має блокувати

Зелена позначка лише повідомляє результат. Щоб червоний конвеєр реально забороняв злиття, у налаштуваннях гілки
вмикають **обов'язкові перевірки** (required status checks). На цьому етапі виникають дві пастки, а [документація
GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)
описує обидві.

**Покроковий приклад.** Нехай робочий процес має фільтр `paths`, завдання `test` і завдання публікації з умовою «не
запускати на заявці». Обидва завдання обов'язкові.

| Подія | Чи стартував робочий процес | `test` | Публікація | Чи можна злити |
|-------|-----------------------------|--------|------------|----------------|
| Заявка зі зміною коду, тести зелені | так | успіх | пропущена, звітує Success | так |
| Заявка зі зміною коду, тести червоні | так | помилка | пропущена через `needs` | ні, і це правильно |
| Заявка лише зі зміною документації | ні, відсік фільтр `paths` | немає звіту | немає звіту | **ні: перевірки чекають вічно** |
| Коміт в основну гілку | так | успіх | виконується | заявки вже немає |

Перша пастка в першому рядку: пропущене завдання вважається успішним. Отже, обов'язкова перевірка публікації на заявці
нічого не доводить, а блокує лише тести. Друга пастка в третьому рядку: робочий процес не запустився, тому його
перевірки лишаються в стані `Pending`, а заявка не зливається. Лабораторна вимагає і фільтр шляхів, і обов'язкові
перевірки, тому заявка лише з текстом застрягне. Побач цю поведінку й обери, що для тебе важливіше.

## Запуски з копій репозиторію

Лабораторна вимагає не публікувати образ на заявках із чужих копій. Вона пояснює це тим, що заявка з копії може
використати твій `GITHUB_TOKEN`. За [довідником
GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) це не зовсім так: токен
для заявки з копії отримує лише читання, якщо власник не ввімкнув окремо передавання токена із записом. Секрети такому
запуску також не передаються.

Заборона все одно потрібна: образ із незлитого коду не повинен потрапляти в реєстр. Поруч лежить найнебезпечніший
варіант: подія `pull_request_target` виконується з правами основного репозиторію, тому документація радить уникати її
без потреби.

## Сканування й теги

**Сканер у конвеєрі.** Лекція 2 пояснила код виходу. Тут він працює за призначенням: крок сканера повертає помилку,
завдання червоніє, завдання публікації не запускається. Лабораторна 3 сканує файлову систему, тому бачить залежності
твого застосунку, а не пакети базового образу. Тому повного сканування образу з лабораторної 2 цей крок не замінює.

**Теги образу.** Лабораторна пропонує `docker/metadata-action`, яка будує теги за описом. Тут є важлива деталь із
[README дії](https://github.com/docker/metadata-action): кожен тип тега прив'язаний до події. Тег `type=semver`
з'являється лише на коміті з тегом git, а `type=schedule` лише під час запуску за розкладом. Якщо робочий процес
стартує лише на звичайний коміт у гілку, такі рядки не дадуть нічого. Перевір у журналі кроку, які теги насправді
вийшли.

## Типові хибні уявлення

**«Я закріпив `@v4.2.2`, отже, версія незмінна».** Це лише тег, хоч і схожий на точну версію. У випадку `tj-actions`
перенесли й теги такого вигляду.

**«GitHub помітить, що тег перенесено, і зупинить запуск».** GitHub не порівнює тег із учорашнім значенням. Конвеєр
виконає те, на що тег указує зараз.

**«Зелений значок означає, що зламаний код не злиють».** Значок лише показує останній результат. Злиття блокують лише
обов'язкові перевірки в налаштуваннях гілки.

## Практика

Усе нижче вимагає лабораторна. Скелети заповнюй сам.

1. Напиши тести на три випадки: шлях `/`, шлях `/health` і неіснуючий шлях. Перевір, що тест падає, якщо зламати
   застосунок.
2. Напиши завдання тестів із матрицею версій Python, кешем і лінтером.
3. Додай публікацію, яка чекає на тести й не публікує із заявок, а також Trivy, що її зупиняє.
4. Увімкни обов'язкові перевірки й відкрий заявку з навмисно зламаним тестом: злиття має бути заблоковано.

## Межі курсу

**Версії дій уже змінилися.** Курс закріплює версії станом на травень 2026 року. [За оголошенням
GitHub](https://github.blog/changelog/2026-09-23-deprecation-of-node-20-on-github-actions-runners/) Node 24 став
стандартним 16 червня 2026 року, а Node 20 мали прибрати 23 вересня. Курс сам пише, що `actions/checkout@v4` працює на
Node 20. Перед роботою перевір актуальну основну версію в README кожної дії. Важливо зрозуміти правило закріплення, а
не запам'ятати числа.

**Конвеєр лабораторної не перевіряє образ після публікації.** Він сканує залежності до збірки, а не сам зібраний
образ. Новий пакет у базовому образі цей конвеєр не побачить.

## Перевір себе

**1. Чому `runs-on: ubuntu-latest` є ризиком, хоча нічого не ламає сьогодні?**

<details><summary>Відповідь</summary>

Мітка рухома: GitHub переносить її на нову версію системи за власним розкладом. Завтра той самий файл запуститься на
іншій системі з іншими версіями програм, тому конвеєр може впасти без змін у коді, а вчорашній результат неможливо
відтворити.

</details>

**2. Дія закріплена тегом `@v4`, а її автора зламали. Що станеться з твоїм наступним запуском, і що змінив би хеш?**

<details><summary>Відповідь</summary>

Зловмисник переносить тег на свій коміт, а твій наступний запуск виконає шкідливий код поруч із токеном і секретами.
Хеш указує на конкретний вміст, тому твій запуск виконав би старий чистий код і не залежав би від нового вмісту тега.
Хеш не захищає, лише якщо дія сама завантажує інші дії за тегами.

</details>

**3. Чому `GITHUB_TOKEN` не треба ротувати, але його все одно обмежують?**

<details><summary>Відповідь</summary>

Він створюється для одного завдання й зникає з його завершенням, тому немає довготривалого значення для заміни. Проте
під час роботи завдання він дійсний, і шкідлива дія може його використати. Тому завданню дають лише потрібні дозволи.

</details>

**4. Обов'язкове завдання пропущено умовою `if`. Чи заблокує воно злиття? А якщо весь робочий процес відсік фільтр
`paths`?**

<details><summary>Відповідь</summary>

Пропущене завдання звітує про успіх, тому не блокує. Якщо робочий процес відсік фільтр шляхів, звіту немає зовсім,
тому перевірка лишається в стані очікування, а злиття заблоковано.

</details>

**5. У конвеєрі немає `needs:` між тестами й публікацією. Що станеться, коли тест упаде?**

<details><summary>Відповідь</summary>

Завдання стартують паралельно, тому образ опублікується, хоча тести червоні. Без `needs:` результат тестів не впливає
на публікацію.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| робочий процес (workflow) | файл YAML, що описує конвеєр |
| завдання (job) | частина робочого процесу на окремій чистій машині |
| дія (action) | готовий код, який запускають через `uses:` |
| ланцюг постачання | увесь чужий код і всі сервіси, від яких залежить твоя програма |
| поверхня атаки | усі місця, через які можна дістатися до системи |
| `GITHUB_TOKEN` | тимчасовий токен, що живе одне завдання |
| обов'язкова перевірка | перевірка, без якої гілку не можна злити |
