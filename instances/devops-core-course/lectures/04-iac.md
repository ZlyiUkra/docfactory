# Лекція 4. Інфраструктура як код: Terraform, OpenTofu, Pulumi

Ця лекція пояснює, як описати сервер файлом у git і навіщо інструментові окрема пам'ять, яку називають станом. Читання
займе близько 35 хвилин. Для Terraform, OpenTofu й Pulumi у фабриці ще немає примірника, тому факти про них звірено з
офіційною документацією 2 листопада 2026 року.

**Після лекції ти зможеш пояснити:**

- що таке стан і чому `plan` порівнює три джерела, а не два;
- що станеться, якщо файл стану зникне, і чому результат залежить від об'єкта;
- чому стан не кладуть у git, а `.terraform.lock.hcl` кладуть;
- що блокування стану вміє, а чого не вміє;
- чим Pulumi повторює механізм Terraform і де OpenTofu з Terraform не збігається.

## Звідки береться проблема

Уяви, що тобі потрібен сервер. Ти заходиш на сайт хмарного провайдера, натискаєш у вебконсолі два десятки кнопок і
відкриваєш порт. Через місяць потрібен такий самий сервер, а ти вже не пам'ятаєш, що вибирав. Тим часом колега вручну
поміняв налаштування на першому сервері й нікому не сказав.

З цього виростають три біди:

- **Сервер-сніжинка** (snowflake server): його неможливо відтворити, бо ніде не записано, як його зроблено.
- **Дрейф** (drift): реальність розійшлася з тим, що всі вважають правдою.
- **Одна людина знає все** (англійською bus factor 1): якщо вона звільниться, ніхто не знає, що й навіщо налаштовано.

**Інфраструктура як код** (Infrastructure as Code, IaC) розв'язує їх так: сервери й мережі описують текстовими файлами
в git, а окрема програма приводить реальність у відповідність до файлів. Зміни проходять той самий шлях, що й код
застосунку: гілка, перегляд, злиття. Тому з історії git видно, хто що змінив, а новий сервер створюється запуском
команди.

## Кілька слів про хмару

Докладно SSH і мережу пояснює [план Linux](../../linux/LEARNING.md) у фазі 5, а контейнери для локальної дороги
лабораторної пояснює [план Docker](../../docker/LEARNING.md). Для цієї лекції досить такого:

| Слово | Що це |
|-------|-------|
| віртуальна машина (VM, instance) | комп'ютер, який хмара виділяє тобі й до якого ти під'єднуєшся по мережі |
| образ (image, в AWS це AMI) | готовий знімок системи, з якого стартує машина |
| група безпеки (security group, firewall) | правила хмари: з яких адрес і на які порти можна зайти |
| `/32` у записі адреси | позначка «рівно одна адреса», наприклад `203.0.113.7/32` |
| провайдер (provider) | у Terraform це плагін, який уміє розмовляти з API конкретної хмари |

## Описувати результат, а не кроки

Можна написати скрипт на bash: «створи машину, відкрий порт». Це **імперативний** підхід: ти перелічуєш кроки. Якщо
запустити скрипт удруге, він створить другу машину, бо про першу не знає.

Terraform працює **декларативно**: ти описуєш, що має існувати, а він обчислює, що для цього зробити. Другий запуск
без змін у коді нічого не робить. Цю властивість називають **ідемпотентністю**.

Аналогія для розробника на React: компонент описує, яким має бути інтерфейс, а React обчислює різницю й оновлює
сторінку. Код Terraform відповідає компоненту, а `plan` відповідає обчисленню різниці. Аналогія закінчується на файлі
стану: у React немає окремого файла, який треба берегти.

## З чого складається опис

Terraform читає файли `.tf`, написані мовою **HCL** (HashiCorp Configuration Language). Ось приклад на іншому об'єкті,
ніж у лабораторній. Він створює файл на твоєму диску, тому працює без хмари й без грошей.

```hcl
terraform {
  required_version = ">= 1.10"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

variable "greeting" {
  type    = string
  default = "hello"
}

resource "local_file" "note" {
  filename = "${path.module}/note.txt"
  content  = var.greeting
}

output "note_path" {
  value = local_file.note.filename
}
```

Розберемо блоки:

- `terraform { … }` налаштовує сам інструмент: якою версією його можна запускати і які плагіни потрібні.
  `hashicorp/local` означає плагін `local` від видавця `hashicorp`.
- `~> 2.5` дозволяє збільшуватися лише найправішій вказаній частині версії: підійде `2.6`, але не `3.0`.
- `variable` оголошує вхідне значення. Типи: `string`, `number`, `bool`, `list`, `map`, `set`, `object`, `tuple`. Типу
  `int` немає. Значення можна передати через `terraform.tfvars`, параметр `-var` або змінну оточення з префіксом
  `TF_VAR_`. Без значення Terraform спитає його перед планом.
- `resource` описує об'єкт, яким Terraform керує. Два слова після нього означають тип і твоє локальне ім'я. Разом вони
  дають адресу `local_file.note`, яка потрапляє в стан.
- `output` показує значення після `apply`.

Є ще два блоки. `data` лише **читає** наявний об'єкт, наприклад знаходить найновіший образ за фільтром. `provider`
налаштовує плагін, наприклад регіон. Паролі й ключі в нього не пишуть, бо файл потрапить у git: плагіни читають їх зі
змінних оточення чи з профілю.

**Файл `.terraform.lock.hcl`.** Команда `init` записує в нього точну версію кожного плагіна й контрольні суми, і
наступний `init` вибере ту саму версію, навіть якщо вийшла новіша. Це аналог `package-lock.json`: файл комітять, щоб
уся команда отримала однакові плагіни. Версії модулів він не фіксує.

## Життєвий цикл

| Команда | Що робить | Чи звертається до хмари | Що змінює |
|---------|-----------|-------------------------|-----------|
| `terraform fmt` | вирівнює оформлення | ні | твої файли |
| `terraform init` | завантажує плагіни, налаштовує сховище стану | лише до реєстру й сховища стану | теку `.terraform/`, файл версій |
| `terraform validate` | перевіряє синтаксис і внутрішню узгодженість | ні | нічого |
| `terraform plan` | обчислює різницю | так, читає | нічого в хмарі |
| `terraform apply` | виконує різницю | так | хмару й стан |
| `terraform destroy` | видаляє все, що записано в стані | так | хмару й стан |

`validate` не перевірить, чи існує в хмарі такий тип машини, бо до хмари не звертається.

У `plan -out=файл` дві пастки. Якщо передати збережений план у `apply`, Terraform **не спитає підтвердження**, бо
вважає передачу файла згодою, тому читати план треба раніше. Крім того, файл плану містить значення змінних і чутливі
дані без приховування, тому в git йому не місце.

## Стан: окрема пам'ять інструмента

У коді є адреса `local_file.note`, а в хмарі тисячі об'єктів. Який із них твій? За назвою чи тегами не вийде:
документація Terraform пояснює, що ранні прототипи пробували теги й відмовилися, бо теги підтримують не всі об'єкти й
не всі хмари.

Тому Terraform веде власний запис, **стан** (state): файл JSON, типово `terraform.tfstate`, де кожній адресі
відповідає ідентифікатор реального об'єкта. У ньому також є копія атрибутів об'єктів і залежності між ними. Залежності
потрібні, щоб видаляти об'єкти в правильному порядку.

```text
   код (.tf)            стан (tfstate)             реальність (API хмари)
  що має бути     яка адреса який ідентифікатор     що є насправді
       |                     |                            ^
       |                     +---- за ідентифікаторами ---+
       v                     v
                   +------------------+
                   |  terraform plan  | ---> різниця, яку читаєш ти
                   +------------------+
```

Спочатку Terraform за ідентифікаторами зі стану питає в хмари, що зараз із цими об'єктами. Потім порівнює результат із
кодом, і все, що не збігається, стає пропозицією змін.

| Позначка в плані | Що станеться |
|------------------|--------------|
| `+` | створить |
| `~` | змінить на місці |
| `-` | видалить, дані об'єкта зникнуть |
| `-/+` | видалить і створить замість нього; для бази даних це катастрофа |
| `+/-` | спершу створить заміну, потім видалить старий |
| `<=` | прочитає блок `data`, нічого не змінює |

### Покроковий приклад

Візьмемо `note.txt` із прикладу вище. Рядки плану наведено скорочено.

| Крок | Що ти зробив | Що в стані | Що покаже `plan` |
|------|--------------|------------|------------------|
| 1 | написав код, виконав `init` | порожньо | `Plan: 1 to add, 0 to change, 0 to destroy.` |
| 2 | виконав `apply` | `local_file.note` з ідентифікатором | `No changes. Your infrastructure matches the configuration.` |
| 3 | вручну видалив `note.txt` | запис лишився | файла немає, знову `1 to add` |
| 4 | відновив файл, змінив `greeting` у коді | старий вміст | `-/+`: `1 to add, 0 to change, 1 to destroy`, бо цей ресурс не змінюється на місці |
| 5 | видалив блок `resource` з коду | запис лишився | `0 to add, 0 to change, 1 to destroy` |

Крок 5 важливий: прибравши блок, ти **не забуваєш** про об'єкт. Terraform бачить запис без відповідника в коді й
пропонує видалити реальний об'єкт. Документація формулює це правилом: знищуються ресурси, які є в стані, але яких
немає в конфігурації.

### Що станеться, якщо стан зникне

Машини не зникають, бо стан лише запис про них. Але Terraform перестає про них знати, кожен рядок коду здається йому
новим, і план показує лише `+`. Подальше залежить від об'єкта:

| Об'єкт | Що зробить `apply` | Наслідок |
|--------|--------------------|----------|
| машина, ім'я якої не мусить бути унікальним | створить другу | перша працює далі поза керуванням, за неї можуть брати гроші |
| об'єкт з унікальною назвою, наприклад група безпеки AWS в одній мережі | отримає помилку від хмари | `apply` падає тут, а залежне від нього не створюється |
| наш `local_file`, де ключем є шлях до файла | перезапише файл | дубліката не буде |

Якщо в коді є група безпеки з фіксованою назвою, у лабораторній ти побачиш другий випадок раніше за перший. Зв'язок
відновлює **імпорт**: команда `terraform import` або блок `import` кажуть Terraform, що адреса з коду відповідає
такому-то ідентифікатору.

## Дрейф

Хтось відкрив порт вручну у вебконсолі. У коді порту немає, тому наступний `plan` запропонує його закрити. Звідси
правило: зміни вносять лише через код. Параметр `-detailed-exitcode` змушує `plan` повертати код виходу: `0` означає
відсутність змін, `1` означає помилку, `2` означає, що зміни є. Запустивши таку команду щоночі в CI, можна дізнаватися
про дрейф автоматично.

## Стан є секретом

Документація каже прямо: стан лежить у файлі відкритим текстом разом із секретними значеннями. Перевірити це можна без
хмари: плагін `hashicorp/random` має ресурс `random_password`, який генерує пароль. У виводі `plan` пароль прихований,
а в `terraform.tfstate` його видно. Те саме робить `sensitive = true` у змінної чи виводу: значення зникає з журналу
команд, але в стані й плані лишається.

| Файл | У git? | Чому |
|------|--------|------|
| `*.tf` | так | це і є опис |
| `.terraform.lock.hcl` | так | уся команда отримає ті самі плагіни |
| `terraform.tfstate`, `*.tfstate.backup` | ні | можуть містити секрети |
| `.terraform/` | ні | завантажені плагіни, `init` створить їх знову |
| `*.tfvars` | ні | у них часто лежать приватні значення |
| збережений план | ні | чутливі дані в ньому не приховано |

У новіших версіях є й інші шляхи. Terraform має ефемерні значення (ephemeral) і аргументи лише для запису
(write-only), які не потрапляють у стан. OpenTofu з версії 1.7 уміє шифрувати файли стану й плану, але це треба
налаштувати самому.

## Стан є спільним

Покажемо, як втрачається запис, коли спільний стан є, а блокування немає:

| Крок | Хто | Що робить | Стан у сховищі |
|------|-----|-----------|----------------|
| 1 | Аня | читає стан із 5 об'єктами | 5 |
| 2 | Борис | читає той самий стан | 5 |
| 3 | Аня | створює об'єкт А, записує стан | 5 + А |
| 4 | Борис | створює об'єкт Б, записує свою копію | 5 + Б |

Об'єкт А існує в хмарі, але запису про нього вже немає. **Блокування** (state locking) не дає цьому статися: перед
кожною операцією, яка може записати стан, Terraform бере замок, і другий учасник отримає повідомлення про блокування.
Це відбувається автоматично, але лише там, де сховище підтримує блокування.

Сховище стану називають **бекендом** (backend). Типовий бекенд `local` блокує файл засобами операційної системи, тому
дві команди на одній машині не заважатимуть одна одній. Але дві людини на різних ноутбуках мають два окремі файли, і
жоден замок тут не допоможе: спільний стан потребує спільного сховища.

| Бекенд | Як блокує | Що ще знати |
|--------|-----------|-------------|
| `s3` | файл `<key>.tflock`, параметр `use_lockfile = true` | блокування через DynamoDB у Terraform оголошено застарілим |
| `gcs` | вбудоване | аргументу `encrypt` немає |
| `oci` (Oracle) | об'єкт-замок у тому самому сховищі | потрібні `bucket` і `namespace` |

Для всіх трьох документація наполегливо радить увімкнути **версії об'єктів** у сховищі, щоб зіпсований стан можна було
повернути. Наявний стан переносить `terraform init -migrate-state`, а успіх доводить наступний `plan` без змін.

## Pulumi: той самий механізм, інша мова

Pulumi теж має бажаний стан, файл стану й порівняння, але опис ти пишеш мовою програмування: Python, TypeScript, Go,
C#, Java або YAML.

Програма на Python **не створює** ресурс у рядку, де його оголошено, а лише реєструє намір. Мовний хост запускає
програму, рушій (engine) порівнює зареєстроване зі станом, а плагін провайдера звертається до API хмари. Ресурси зі
стану, яких програма більше не реєструє, потрапляють на видалення. Отже, цикл у Python лише будує список бажаного, а
різниця обчислюється так само, як у Terraform.

```python
import pulumi
import pulumi_random as random

pet = random.RandomPet("pet", length=2)        # лише реєстрація наміру
greeting = pet.id.apply(lambda name: f"hello, {name}")
pulumi.export("greeting", greeting)
```

`lambda name: …` є стрілковою функцією `name => …`, а `f"hello, {name}"` є шаблонним рядком. Перший аргумент `"pet"` є
логічним іменем у стані, яке грає роль адреси `local_file.note`.

**Що таке `Output`.** `pet.id` не є рядком, бо ім'я з'явиться лише після створення ресурсу. Аналогія: `Output` схожий
на `Promise`, а `.apply(…)` схожий на `.then(…)`. Функція всередині `apply` отримає звичайний рядок, а результат знову
буде `Output`.

**Стек** (stack) є окремим екземпляром програми, наприклад `dev`. Його налаштування лежать у `Pulumi.<стек>.yaml`.
Ключі без двокрапки належать проєкту, а `aws:region` належить провайдеру AWS. Метод `pulumi.Config().require` зупинить
роботу помилкою, якщо значення не задано.

**Де лежить стан.** За замовчуванням у Pulumi Cloud. Команда `pulumi login --local` переносить його в `~/.pulumi`,
тобто за межі репозиторію, і за резервні копії тоді відповідаєш ти.

**Секрети.** Зашифровано лише те, що позначено секретом, наприклад через `pulumi config set --secret`. Звичайні
значення конфігурації документація прямо називає відкритим текстом. Читати секрет треба через `require_secret`, бо
звичайний `require` може загубити позначку. З локальним сховищем ключ шифрування даєш ти: парольну фразу вводять
вручну або кладуть у `PULUMI_CONFIG_PASSPHRASE`.

**Відмінність про дрейф.** Terraform перед планом опитує реальні об'єкти. Pulumi порівнює програму із записаним
станом, тому ручна зміна може лишитися непоміченою, доки ти не додаси `--refresh` до `pulumi preview` чи `pulumi up`
або не виконаєш `pulumi refresh --preview-only`.

## Порівняння

Той самий нешкідливий цикл у HCL і в Python:

```hcl
resource "local_file" "env" {
  for_each = toset(["dev", "staging", "prod"])
  filename = "${path.module}/${each.key}.txt"
  content  = "environment: ${each.key}"
}
```

```python
import pulumi_local as local

for env in ["dev", "staging", "prod"]:
    local.File(f"env-{env}", filename=f"{env}.txt", content=f"environment: {env}")
```

| Що порівнюємо | Terraform | OpenTofu | Pulumi |
|---------------|-----------|----------|--------|
| ліцензія | BSL 1.1 | MPL 2.0 | Apache 2.0 |
| мова опису | HCL | HCL, також файли `.tofu` | Python, TypeScript, Go, C#, Java, YAML |
| стан за замовчуванням | локальний файл | локальний файл | Pulumi Cloud |
| секрети в стані | відкритим текстом, крім ефемерних значень | відкритим текстом, якщо не ввімкнено шифрування | зашифровано позначене секретом |
| вбудовані тести | `terraform test` | `tofu test` | бібліотеки тестів твоєї мови |
| опитування хмари перед планом | так | так | лише з `--refresh` |

Далі наша оцінка, а не факт із документації. В HCL легко прочитати чужий файл, бо мова обмежена, але важко писати
складні перетворення даних і власні функції. У Pulumi легко писати цикли, умови й тести, але важче гарантувати
передбачуваність: програма може читати мережу чи час, і той самий код дасть різний план. Ще Pulumi потребує середовища
мови із залежностями. Навіть сторінка порівняння на сайті Pulumi визнає, що в Terraform більша спільнота готових
модулів.

## OpenTofu: чому існує і де не збігається

10 серпня 2023 року HashiCorp змінила ліцензію своїх продуктів із відкритої MPL 2.0 на BSL 1.1: код лишився доступним,
але його заборонено використовувати в продукті, що конкурує з HashiCorp. Компанії, чий бізнес тримався на Terraform,
створили відгалуження (fork), і 20 вересня 2023 року Linux Foundation оголосила про проєкт OpenTofu.

Команда `tofu` приймає ті самі підкоманди, а документація каже, що більшість коду Terraform працює без змін. Саме
«більшість». Ось відмінності, які стосуються цієї лабораторної:

- **Інший реєстр.** Плагіни за замовчуванням приходять із `registry.opentofu.org`.
- **`required_version`.** З версії 1.12 OpenTofu перевіряє цей аргумент лише у файлах `.tofu`, а у файлах `.tf`
  ігнорує, вважаючи, що він написаний для Terraform. Старіші версії перевіряли його завжди.
- **Файли.** Якщо поруч лежать `foo.tf` і `foo.tofu`, OpenTofu читає лише другий.
- **DynamoDB.** OpenTofu не планує оголошувати це блокування застарілим.

## Як це лягає на лабораторну

**`user_data` і cloud-init.** `user_data` є текстом, який ти передаєш машині під час створення. Усередині машини його
читає програма **cloud-init**: скрипт вона виконує один раз на екземпляр машини, досить пізно під час завантаження.
Тому `apply` завершується, коли хмара створила машину, а не коли скрипт відпрацював, і зелений `apply` нічого не
доводить про скрипт. Саме тому курс вимагає зайти на машину й побачити результат. Зміна `user_data` не запустить
скрипт на вже працюючій машині.

**Правила групи безпеки в AWS.** AWS дає новій групі правило «весь вихідний трафік дозволено». Terraform його прибирає
й вимагає описати явно, інакше машина нічого не завантажить із мережі.

**Oracle Cloud.** Цю дорогу плану курс у таблиці хмар не перелічує, але просить лише безкоштовну хмару, тому свій
вибір опиши у звіті. Подробиці є в розборі читання й у примірнику `oracle-cloud`.

## Типові хибні уявлення

**«Стан є резервною копією машини».** Стан містить запис про машину, але не вміст її диска. Якщо машина зникне, він
дасть змогу лише створити нову за кодом.

**«Видалю блок із коду, і Terraform забуде про об'єкт».** Навпаки: наступний `apply` видалить реальний об'єкт. Забути
без видалення допомагає окрема команда `terraform state rm`.

**«`sensitive = true` шифрує значення».** Ця позначка лише прибирає значення з виводу команд.

**«Pulumi шифрує все сам».** Він шифрує лише те, що позначено секретом.

**«OpenTofu є повною копією Terraform».** Проєкти розходяться: інший реєстр, інші правила `required_version`, власне
шифрування стану.

## Практика

Спершу пройди приклад із `local_file` без хмари. Перед кожною командою скажи вголос, що покаже план, а потім порівняй.
Перевір п'ять кроків таблиці й видалення стану, а ще додай `random_password` і знайди пароль у `terraform.tfstate`.
Потім виконуй лабораторну. На питання про другий прогін правильна відповідь завжди «змін немає», а все інше є приводом
розібратися.

## Межі лабораторної

Лабораторна вчить життєвого циклу на одній машині. Модулі, кілька середовищ і запуск `apply` у CI лишаються за її
межами, а налаштування програм усередині машини прийде в лабораторних 5 і 6 з Ansible.

## Перевір себе

Спершу відповідай сам, уголос або письмово, і лише потім розгортай пояснення.

**1. Ти видалив файл стану й запустив `plan`. Що він покаже, і що станеться після `apply`?**

<details><summary>Відповідь</summary>

План покаже лише створення, а реальні машини працюють далі. Після `apply` машина без унікальної назви з'явиться
вдруге, а перша лишиться поза керуванням. Об'єкт із фіксованою унікальною назвою дасть помилку хмари. Зв'язок
відновлює імпорт.

</details>

**2. Чому `terraform destroy` не потрібен після кожної лабораторної, якщо машина безкоштовна, і коли він усе ж
потрібен?**

<details><summary>Відповідь</summary>

Лабораторні 5 і 6 продовжують працювати з цією машиною, а гроші за неї не йдуть. `destroy` потрібен, коли машин стало
дві, коли закінчуються безкоштовний період чи кредити або коли машина більше не потрібна, наприклад, коли в
лабораторній 9 її замінить k3d. Ще він корисний як перевірка: якщо після нього код знову створює робочу машину, опис
справді повний.

</details>

**3. Що справді важко зробити в HCL і легко в Pulumi, а що навпаки?**

<details><summary>Відповідь</summary>

В HCL важко писати складну логіку й перевіряти її модульними тестами, а в Pulumi це звичайний код. Зате в Pulumi важче
прочитати чужу програму з першого погляду й гарантувати передбачуваність, а ще потрібне середовище мови. Власна
відповідь із лабораторної цінніша за цю: курс просить порівняти на твоєму досвіді.

</details>

**4. Хтось вручну відкрив порт. Що покаже наступний запуск у Terraform і в Pulumi?**

<details><summary>Відповідь</summary>

`terraform plan` опитає реальні об'єкти й запропонує прибрати зміну. `pulumi preview` порівняє програму із записаним
станом і може сказати, що змін немає, доки не додати `--refresh`.

</details>

**5. Два інженери на різних ноутбуках запускають `apply` з локальним станом. Чи врятує їх блокування бекенду
`local`?**

<details><summary>Відповідь</summary>

Ні. Він блокує файл на одній машині, а в кожного свій файл. Кожен бачить лише свої записи, тому вони створюватимуть
дублікати. Потрібен спільний бекенд із блокуванням.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| IaC | сервери й мережі описано файлами в git, а інструмент приводить реальність до опису |
| ідемпотентність | повторний запуск нічого не змінює, якщо все вже як треба |
| HCL | мова конфігурацій Terraform і OpenTofu |
| ресурс (resource) | об'єкт, яким інструмент керує |
| стан (state) | запис, який адресі з коду зіставляє реальний об'єкт |
| бекенд (backend) | місце, де зберігається стан |
| блокування (state locking) | замок, що не дає двом операціям писати стан одночасно |
| дрейф (drift) | реальність розійшлася з описом |
| імпорт (import) | додавання наявного об'єкта до стану |
| cloud-init | програма в образі, що виконує `user_data` під час завантаження |
| стек (stack) | окремий екземпляр програми Pulumi зі своїм станом і налаштуваннями |
