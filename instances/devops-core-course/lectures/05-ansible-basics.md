# Лекція 5. Ansible: налаштування машини описом бажаного стану

Лабораторна 4 створила машину: у неї є адреса й відкриті порти, але всередині порожньо. Ця лекція пояснює, як
інструмент Ansible налаштовує те, що всередині, і чому результат можна перевірити одним числом. Читання займе близько
40 хвилин. Програмувати тут ще нічого не треба, а всі приклади взято на іншому об'єкті, ніж у лабораторній: ми
налаштовуємо сервер кешу Redis, а лабораторна просить Docker і твій сервіс.

**Після лекції ти зможеш пояснити:**

- чим опис бажаного стану відрізняється від скрипта команд і що ламається у скрипта при другому запуску;
- як одне завдання Ansible проходить шлях від твого комп'ютера до сервера без встановленого там агента;
- чому другий запуск плейбука має показати `changed=0` і що означає інше число;
- навіщо потрібен обробник (handler) і коли він не спрацює;
- що саме захищає Ansible Vault і чого він не захищає.

## Звідки береться проблема

Уяви, що тобі дали порожній сервер Ubuntu, і на ньому має працювати Redis, налаштований на обмеження пам'яті. Перше,
що спадає на думку, це скрипт із командами:

```bash
#!/bin/bash
apt-get update
apt-get install -y redis-server
echo "maxmemory 256mb" >> /etc/redis/redis.conf
systemctl restart redis-server
```

Першого разу скрипт спрацює. Проблеми починаються потім:

- **Другий запуск псує файл.** Оператор `>>` дописує рядок у кінець файла, тому після десяти запусків у конфігурації
  буде десять однакових рядків.
- **Другий запуск зачіпає службу.** Команда `systemctl restart` виконується щоразу, тому всі з'єднання з Redis
  обриваються навіть тоді, коли нічого не змінилося.
- **Скрипт не знає, що вже зроблено.** Він записує кроки, а не результат. Якщо хтось руками змінив файл, скрипт цього
  не помітить.
- **Сервери поступово розходяться.** На одному сервері скрипт запускали тричі, на другому ще й правили файл руками.
  Коли другий сервер ламається, ніхто не може сказати, чим він відрізняється від першого.

Останнє явище вже знайоме з лабораторної 4: те, що є насправді, розійшлося з описом, і це називається **дрейфом**
(drift).

Ansible розв'язує проблему іншим способом запису. Ти описуєш не кроки, а те, що має бути правдою: пакет встановлено,
файл має такий вміст, служба працює. Перед дією інструмент сам перевіряє, чи це вже так.

**Де проходить межа між інструментами.** Лабораторна 4 створює машину, лабораторна 5 налаштовує те, що всередині.
Обидва інструменти лежать у git, але відповідають на різні запитання:

| Інструмент | Запитання, на яке він відповідає | Приклад |
|------------|----------------------------------|---------|
| Terraform, Pulumi | Які машини й мережі мають існувати? | «Є віртуальна машина з такою адресою» |
| Ansible | Що налаштовано всередині машини? | «Встановлено Docker, служба працює» |
| Docker | Як запаковано застосунок? | «Образ містить сервіс і його бібліотеки» |
| Kubernetes | Скільки копій застосунку працює і що робити зі збоєм? | «Працює три копії, упалу копію замінити» |

Докладно про образи є в плані Docker цієї лінії, а про кластер у плані Kubernetes. Для цієї лекції досить пам'ятати,
що **образ контейнера** — це запакований застосунок, який запускають на машині.

## Як Ansible дістається до машини

У Ansible є дві ролі машин:

- **Керівний вузол** (control node): комп'ютер, на якому ти запускаєш Ansible. Це твій ноутбук або машина CI.
- **Керовані вузли** (managed nodes): сервери, які налаштовують.

На керованому вузлі не працює жодна постійна програма Ansible. Інструменти старшого покоління вимагали встановити на
кожен сервер **агента**, тобто фонову програму, яку теж треба оновлювати. Ansible натомість під'єднується звичайним
SSH у момент запуску. Тому кажуть, що він **без агента** (agentless) і працює **за моделлю проштовхування** (push):
дію починає керівний вузол, коли ти запускаєш команду, а сервери самі нічого не запитують.

Шлях одного завдання виглядає так:

```text
 Керівний вузол                                 Керований вузол
 --------------                                 ---------------
 1. читає інвентар: які сервери
 2. відкриває SSH  ---------------------------> приймає з'єднання
 3. копіює маленьку програму-модуль  ---------> тимчасовий файл
                                                4. запускає модуль своїм Python
                                                   модуль перевіряє стан і за
                                                   потреби змінює його
 5. отримує JSON  <---------------------------- {"changed": true, ...}
 6. друкує ok або changed                       тимчасовий файл прибрано
```

З цієї схеми випливають дві вимоги. На сервері має бути **Python**, бо модуль написано цією мовою, і на Ubuntu він уже
є. А ще мусить працювати **SSH**: якщо немає доступу, Ansible нічого не зробить.

Версії важливі. Курс фіксує `ansible-core 2.21`. Таблиця підтримки в документації Ansible вимагає для цієї версії
Python 3.12–3.14 на керівному вузлі й Python 3.9–3.14 на керованому. Лабораторна згадує «3.11+», але це застаріло:
Python 3.11 перестав бути прийнятним для керівного вузла ще у версії 2.20.

**Що означають три схожі назви.** Від 2021 року проєкт поділено на частини:

| Назва | Що це | Чи потрібне в лабораторній |
|-------|-------|----------------------------|
| `ansible-core` | Сам рушій і вбудовані модулі (`ansible.builtin.*`) | так, версія 2.21 |
| колекція (collection) | Окремий пакет із додатковими модулями, наприклад `community.docker`. Встановлюється командою `ansible-galaxy collection install` | так |
| `ansible` | Великий набір: `ansible-core` плюс багато колекцій разом | ні, лабораторна ставить `ansible-core` |

Звідси береться **FQCN** (Fully Qualified Collection Name, повна назва модуля): `ansible.builtin.apt` означає колекцію
`ansible.builtin` і модуль `apt`. Коли кілька колекцій містять модуль із тією самою короткою назвою, лише повна назва
однозначно каже, який із них потрібен. Тому лабораторна вимагає її скрізь, а лінтер `ansible-lint` (програма, що
перевіряє текст плейбуків без запуску) скаржиться на короткі назви.

## Інвентар, плейбук, завдання

**Інвентар** (inventory) — це перелік серверів, поділених на групи. Формат може бути INI або YAML:

```ini
[cache]
redis1 ansible_host=203.0.113.10
redis2 ansible_host=203.0.113.11

[cache:vars]
ansible_user=admin
```

Ім'я `redis1` — це назва сервера всередині Ansible, а `ansible_host` каже, куди насправді під'єднуватися. Адреса
`203.0.113.x` призначена для прикладів і в інтернеті не існує. Група `all` існує завжди й містить усі сервери.

**Завдання** (task) — один виклик модуля з параметрами. **Плейбук** (playbook) — файл YAML зі списком **плеїв**
(play), а плей каже, на яких серверах виконати які завдання:

```yaml
- name: Налаштувати сервери кешу
  hosts: cache
  become: true
  tasks:
    - name: Встановити Redis
      ansible.builtin.apt:
        name: redis-server
        state: present

    - name: Служба працює й стартує разом із системою
      ansible.builtin.service:
        name: redis-server
        state: started
        enabled: true
```

Рядок за рядком:

- `hosts: cache` вибирає групу з інвентаря.
- `become: true` означає, що після входу через SSH Ansible підвищить права, типово через `sudo`, бо встановлювати
  пакети може лише `root`. Для цього `sudo` має працювати без пароля, або пароль треба передати окремо.
- `state: present` означає «пакет має бути встановлено», а не «встанови пакет». Різниця в цих словах і є темою
  наступного розділу.

**Факти** (facts) — дані про сервер, які Ansible збирає на початку плею: дистрибутив, його кодове ім'я, обсяг пам'яті.
За збір відповідає окреме приховане завдання, тому в підсумку завжди є на одне `ok` більше, ніж ти написав. Читай їх
через словник `ansible_facts`, наприклад `ansible_facts['hostname']`. Старий запис без словника (`ansible_hostname`),
який трапляється й у лабораторній, поки працює, але документація версії 2.20 оголосила його застарілим: зараз він дає
попередження, а у версії 2.24 його типово вимкнуть.

**Де лежать змінні груп.** Змінні для групи кладуть у теку `group_vars/`. Документація каже, що Ansible шукає цю теку
поруч із файлом інвентаря й поруч із файлом плейбука. Запам'ятай це правило: воно ще знадобиться, коли ти побачиш
дерево тек лабораторної.

## Механізм ідемпотентності

**Ідемпотентність** (idempotency) означає, що повторний запуск дії нічого не змінює, якщо потрібний стан уже є.
Механізм складається з двох кроків усередині кожного модуля:

1. Модуль перевіряє, як є зараз.
2. Якщо стан уже правильний, модуль нічого не робить і повертає `changed: false`. Якщо ні, він робить зміну й повертає
   `changed: true`.

Ansible показує перше як `ok`, а друге як `changed`.

| Модуль | Що перевіряє перед дією |
|--------|-------------------------|
| `ansible.builtin.apt` зі `state: present` | чи встановлено пакет |
| `ansible.builtin.service` зі `state: started` | чи вже працює служба |
| `ansible.builtin.file` зі `state: directory` | чи існує тека і чи такі в неї права |
| `ansible.builtin.template` | чи збігається файл, створений із шаблона Jinja2, із файлом на сервері |
| `ansible.builtin.command`, `ansible.builtin.shell` | нічого: модуль не знає, що робить твоя команда |

**Покроковий приклад із числами.** Додамо до плейбука завдання, яке створює конфігурацію з шаблона, і обробник
перезапуску (про нього нижче). Разом із прихованим збором фактів отримуємо чотири завдання й один обробник. Числа
наведено приблизно так, як вони склалися б у такому плейбуку.

| Запуск | Що було на сервері | Збір фактів | `apt` | `template` | `service` | Обробник | Підсумок |
|--------|--------------------|-------------|-------|------------|-----------|----------|----------|
| 1 | порожній сервер | ok | changed | changed | ok | changed | `ok=5 changed=3` |
| 2 | усе вже правильно | ok | ok | ok | ok | не запускався | `ok=4 changed=0` |
| 3 | хтось руками змінив файл | ok | ok | changed | ok | changed | `ok=5 changed=2` |
| 4 | файл знову правильний | ok | ok | ok | ok | не запускався | `ok=4 changed=0` |

Зверни увагу на чотири речі:

- **Число `ok` у підсумку містить і `changed`.** Це кількість завдань, які завершилися без помилки. Тому `ok=5
  changed=3` не означає вісім завдань.
- **Служба на першому запуску показує `ok`,** бо на Ubuntu пакет сам запускає службу під час встановлення. Модуль
  бачить, що стан уже правильний.
- **Запуск 3 виправив дрейф.** Шаблон помітив чужу правку й повернув файл до опису.
- **Запуск 2 є приймальним тестом.** Якщо все описано правильно, другий запуск поспіль дає `changed=0`.

Звідси й правило лабораторної: перший прогін дає `changed=N`, другий обов'язково `changed=0`. Ненульове значення
означає одне з двох: або роль повідомляє про зміну, якої не було, або вона справді щоразу щось змінює.

**Що найчастіше ламає цей тест:**

| Причина | Чому ламає | Що робити |
|---------|------------|-----------|
| `shell:` або `command:` | Модуль не вміє перевіряти стан і без додаткових вказівок завжди повідомляє `changed` | Спершу пошукати справжній модуль, інакше дати вказівки (нижче) |
| `state: latest` | Пакет оновлюється щоразу, коли вийшла нова версія, тож результат залежить від дати запуску | `state: present`, якщо немає окремої причини оновлюватися |
| Час чи випадкове значення в шаблоні | Створений файл щоразу інший | Прибрати таке значення з шаблона |
| `apt` лише з `update_cache`, без пакета й без `cache_valid_time` | Завдання повідомляє про зміну щоразу, коли список пакетів справді оновився | Вказати, скільки секунд список вважається свіжим |
| `file` зі `state: touch` | Модуль щоразу ставить новий час зміни файла | Обрати спосіб, який не змінює файл, коли той уже є |

**Як змусити команду говорити правду.** Коли модуля справді немає, є дві вказівки. Вони стосуються і `command`, і
`shell`:

```yaml
- name: Одноразово створити базу кешу
  ansible.builtin.command: /usr/local/bin/init-cache
  args:
    creates: /var/lib/cache/.ready
```

Параметр `creates` каже: якщо такий файл уже є, команду не запускати. Тоді другий прогін покаже `ok`. Якщо команда
нічого не створює, а ти лише хочеш щось дізнатися, допоможе `changed_when`:

```yaml
- name: Дізнатися версію Redis
  ansible.builtin.command: redis-server --version
  register: redis_version
  changed_when: false
```

Тут `register` зберігає результат команди у змінну, а `changed_when: false` каже, що команда нічого не змінює. Такий
рядок пиши обдумано: якщо команда насправді щось змінює, ти приховаєш це від самого себе, і обробник теж не спрацює.

**Сухий запуск.** Прапорець `--check` просить модулі лише передбачити зміни, нічого не роблячи, а `--diff` показує, що
саме зміниться у файлах. Модуль `command` у такому режимі пропускається, якщо ти не вказав `creates` чи `removes`. А
ще `--check` спирається на те, що вже є на сервері: якщо попереднє завдання лише передбачило встановлення пакета,
наступне може не знайти службу.

## Обробники: перезапуск лише тоді, коли є причина

Після зміни конфігурації Redis службу треба перезапустити, бо вона читає файл лише під час старту. Але перезапускати
її щоразу не можна, бо це обриває всі з'єднання. Потрібна дія, яка виконується лише за умови, що інше завдання справді
щось змінило. Це і є **обробник** (handler):

```yaml
# roles/redis/tasks/main.yml
- name: Створити конфігурацію
  ansible.builtin.template:
    src: redis.conf.j2
    dest: /etc/redis/redis.conf
    mode: "0640"
  notify: Перезапустити Redis

# roles/redis/handlers/main.yml
- name: Перезапустити Redis
  ansible.builtin.service:
    name: redis-server
    state: restarted
```

Спочатку `notify` лише робить позначку «обробник потрібен», і лише якщо завдання повернуло `changed`. Сам обробник
виконається пізніше:

```text
завдання 1 (changed) ---> позначка: «Перезапустити Redis»
завдання 2 (ok)      ---> позначки немає
завдання 3 (changed) ---> та сама позначка, вдруге не додається
кінець завдань плею  ---> обробник виконується один раз
```

Деталі з документації, які варто знати:

- **Один раз і наприкінці.** Скільки б завдань не надіслало сповіщення, обробник запуститься один раз, типово після
  всіх завдань плею. Якщо потрібно раніше, є завдання `ansible.builtin.meta: flush_handlers`.
- **Обробник запускає лише `changed`.** Тому `changed_when` на завданні напряму впливає на те, чи спрацює обробник.
- **Якщо наступне завдання впало.** Типово обробник на цьому сервері вже не запуститься, хоча конфігурація вже
  змінена. Наступний запуск плейбука побачить правильний файл і сповіщення не надішле, тому служба лишиться зі старими
  налаштуваннями. Цю ситуацію розв'язує `--force-handlers` або налаштування `force_handlers`.
- **Модуль `service` зі `state: restarted`** за документацією перезапускає службу завжди. Сам по собі такий рядок не
  ідемпотентний, і саме тому він живе в обробнику.

## Ролі й змінні

Коли завдань стає багато, один файл плейбука незручний: його не перевикористаєш в іншому проєкті. **Роль** (role) — це
тека з домовленими підтеками, яка збирає все потрібне для однієї задачі:

```text
roles/redis/
├── tasks/main.yml      завдання, основна робота
├── handlers/main.yml   обробники
├── defaults/main.yml   змінні, які користувач може перевизначити
├── vars/main.yml       змінні, які не варто перевизначати
├── templates/          шаблони Jinja2 для модуля template
├── files/              файли, які копіюють без змін
└── meta/main.yml       залежності від інших ролей
```

Потрібні лише ті підтеки, якими ти користуєшся. Тоді плейбук стає коротким: він лише каже, які ролі застосувати до
яких серверів.

**Хто перемагає, коли змінну задано двічі.** Повний перелік у документації має 22 рівні. Для початку досить цього
порядку, від найслабшого до найсильнішого:

| Рівень | Де задано | Для чого |
|--------|-----------|----------|
| слабкий | `defaults/main.yml` ролі | Значення, які легко перевизначити |
| | `group_vars/`, потім `host_vars/` | Значення для групи чи одного сервера |
| | `vars:` у плеї | Значення для одного плею |
| | `vars/main.yml` ролі | Значення, які роль вважає сталими |
| | `vars:` на блоці чи завданні | Значення лише для цього місця |
| найсильніший | `-e` у командному рядку | Завжди перемагає |

## Ansible Vault: секрети у git

Твоїй ролі потрібен пароль до реєстру образів, а всі файли ролі лежать у git. Записати пароль відкритим текстом не
можна: він залишиться в історії комітів назавжди. **Ansible Vault** розв'язує це так: файл зі змінними шифрується, і в
git потрапляє лише зашифрований текст.

```text
У git                              Поза git
-----                              --------
group_vars/.../vault.yml           пароль Vault
$ANSIBLE_VAULT;1.1;AES256          (файл із правами 600 у .gitignore
6134653938...                       або секрет CI)
```

Перший рядок зашифрованого файла завжди має такий вигляд. `1.1` — це версія формату, а `AES256` — алгоритм шифрування.
Цей рядок і є доказом шифрування, який просить лабораторна.

Коли плейбук читає такий файл, Ansible просить пароль Vault. Є два способи його передати: ввести щоразу
(`--ask-vault-pass`) або вказати файл із паролем (`--vault-password-file` чи налаштування `vault_password_file`).

**Чого Vault не захищає.** Документація каже прямо, що шифрування захищає лише дані в спокої (data at rest). Після
розшифрування відповідальність за секрет лежить на авторі плейбука. Є три місця, де секрет потрапляє назовні:

- **Вивід завдання.** Для цього існує `no_log: true`: завдання не показує своїх значень. Документація попереджає, що
  це не поширюється на налагоджувальний вивід.
- **Файли на сервері.** Якщо шаблон вставив секрет у файл, той файл лежить на сервері відкритим текстом, тому важливо,
  хто може його читати.
- **Вивід `--diff`.** Прапорець показує зміни файла, а у файлі може бути секрет.

У лабораторній 11 ти побачиш інший підхід: окреме сховище секретів OpenBao, до якого програма звертається під час
роботи.

## Типові хибні уявлення

**«Ansible замінює Terraform».** Ні, це різні шари. Terraform створює машину, а Ansible налаштовує вже наявну.

**«`shell:` у плейбуку — це те саме, що модуль, лише коротше».** Модуль перевіряє стан і звітує про зміну, а `shell`
виконує команду наосліп і без додаткових вказівок завжди каже `changed`. Обробник на такому завданні спрацьовуватиме
щоразу.

**«`changed=0` означає, що плейбук нічого не перевіряв».** Навпаки: кожен модуль перевірив стан і побачив, що все вже
правильно.

**«Зашифрований файл робить секрет безпечним усюди».** Шифрування стосується лише файла в git. Під час роботи значення
розшифроване, і його треба окремо захищати від логів та сторонніх очей.

**«Обробник запускається одразу після `notify`».** Він запускається наприкінці плею. Якщо між сповіщенням і цим
моментом завдання зламалося, обробник типово не спрацює на цьому сервері.

## Практика

Цю послідовність ти пройдеш у лабораторній 5 на власних ролях. Перед кожним запуском скажи вголос, яке число очікуєш,
бо так видно, де закінчується розуміння.

1. Запусти плейбук на порожній машині й запиши `changed`.
2. Одразу запусти вдруге. Очікуване значення: `changed=0`. Якщо ні, знайди завдання за словом `changed` у виводі:
   прапорець `-vvv` показує, що саме повернув модуль.
3. Зайди на сервер, зміни файл, яким керує шаблон, і запусти плейбук втретє. Передбач, скільки завдань покаже
   `changed` і чи спрацює обробник.

## Межі лабораторної

Лабораторна написана станом на травень 2026 року, а деякі її твердження розходяться з документацією. Докладна таблиця
є в [розборі читання](../reading/05-reading.md). Ось що варто перевірити наперед, бо воно зупинить роботу:

- **Дерево тек і `group_vars`.** Лабораторна кладе `group_vars/` поруч із `inventory/` і `playbooks/`, а не всередину
  котроїсь із них. За правилом вище такі змінні можуть не завантажитися. Перевір це командою `ansible-inventory --host
  <ім'я>`.
- **Версія Python.** На керівному вузлі потрібен Python 3.12 або новіший, інакше `pip` не знайде `ansible-core` 2.21.
- **Модуль `pip` на Ubuntu 24.04.** Такий Python позначено як керований системою (стандарт PEP 668), тому модуль без
  спеціальних параметрів відмовиться ставити пакет.
- **Бібліотека Python на сервері.** Сторінки модулів `community.docker` кажуть, що самого Docker SDK вони не
  використовують: їм потрібна бібліотека `requests`.
- **WSL і диск `/mnt/c`.** Ansible не читає `ansible.cfg` із теки, куди можуть писати всі. Тримай копію курсу у
  файловій системі Linux.

## Перевір себе

**1. Завдання викликає `shell: curl … | sh`. Що покаже другий прогін, і як це виправити, не прибираючи команду?**

<details><summary>Відповідь</summary>

Другий прогін покаже `changed` на цьому завданні, бо модуль `shell` нічого не знає про результат команди, а команда
виконається знову. Параметр `creates` не дасть команді запуститися, якщо файл, який вона створює, уже є. Вираз
`changed_when` описує, за якої умови вважати, що зміна справді сталася. Перше зазвичай краще, бо команда взагалі не
запускається вдруге. Ще краще пошукати модуль, який знає стан.

</details>

**2. Чому перезапуск служби винесено в обробник, а не записано звичайним завданням після шаблона?**

<details><summary>Відповідь</summary>

Звичайне завдання зі `state: restarted` перезапускало б службу при кожному запуску плейбука: це обривало б з'єднання,
і кожен прогін показував би `changed`. Обробник виконується лише тоді, коли шаблон справді змінив файл, і лише один
раз за плей.

</details>

**3. Шаблон змінив файл, потім наступне завдання впало. Що буде зі службою і що покаже наступний запуск?**

<details><summary>Відповідь</summary>

Типово обробник на цьому сервері не запуститься, тому служба працюватиме зі старими налаштуваннями, хоча файл уже
новий. Наступний запуск побачить правильний файл, шаблон покаже `ok`, і сповіщення не буде. Щоб цього уникнути, є
`--force-handlers` або налаштування `force_handlers`.

</details>

**4. У файлі зі змінними зашифровано пароль. Чи досить цього, щоб пароль не потрапив у лог CI?**

<details><summary>Відповідь</summary>

Ні. Vault захищає лише файл у спокої. Коли завдання використовує пароль, його значення розшифроване, і Ansible може
надрукувати параметри. Для цього потрібен `no_log: true` на завданні. Обережним треба бути також із налагоджувальним
виводом і прапорцем `--diff`.

</details>

**5. У `defaults/main.yml` ролі стоїть `redis_maxmemory: 256mb`, а у `group_vars` для групи стоїть `512mb`. Який
результат, і що зміниться, якщо додати `-e redis_maxmemory=1gb`?**

<details><summary>Відповідь</summary>

Без `-e` переможе `512mb`, бо `defaults` ролі слабші за `group_vars`. З `-e` переможе `1gb`, бо параметр командного
рядка завжди найсильніший. Значення, передане так, є рядком, і це має значення для булевих змінних: про це в лекції 6.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| керівний вузол (control node) | Комп'ютер, де запускають Ansible |
| керований вузол (managed node) | Сервер, який налаштовують |
| інвентар (inventory) | Перелік серверів і груп |
| завдання (task) | Один виклик модуля з параметрами |
| плей (play) | Частина плейбука: які сервери й які завдання |
| плейбук (playbook) | Файл YAML з одним чи кількома плеями |
| модуль (module) | Програма, яку Ansible запускає на сервері; вона перевіряє й змінює стан |
| колекція (collection) | Пакет із додатковими модулями |
| FQCN | Повна назва модуля разом із колекцією |
| факти (facts) | Дані про сервер, які Ansible збирає на початку плею |
| ідемпотентність (idempotency) | Повторний запуск нічого не змінює, якщо стан уже правильний |
| обробник (handler) | Завдання, що запускається лише після сповіщення від завдання зі статусом `changed` |
| роль (role) | Тека з домовленою будовою для однієї задачі |
| Ansible Vault | Шифрування файлів зі змінними |
