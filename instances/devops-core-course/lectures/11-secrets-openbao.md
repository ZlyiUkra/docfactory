# Лекція 11. Секрети: де їм лежати й як довести, що доступ обмежено

Ця лекція пояснює, чому об'єкт `Secret` сам по собі нічого не приховує, від чого захищає шифрування сховища, навіщо
окреме сховище секретів і чому політику доводять відмовою. Читання займе близько 40 хвилин. Програмувати поки нічого
не треба. Про `Secret` як об'єкт кластера є день 2 фази 2 у [плані Kubernetes](../../kubernetes/LEARNING.md), а про
права доступу RBAC там же день 6. Тут нагадано лише потрібне.

**Після лекції ти зможеш пояснити:**

- чим кодування base64 відрізняється від шифрування і чому людина з правом читання бачить пароль;
- від якої загрози захищає шифрування сховища кластера, а від якої ні;
- де фізично лишається значення, передане через `--set`;
- як улаштовано OpenBao: механізми секретів, автентифікація, політики;
- чому перевірка «читання працює» нічого не доводить про політику;
- чим агент-ін'єктор відрізняється від External Secrets Operator і що ти втрачаєш із кожним вибором.

## Звідки береться проблема

Застосунку потрібен пароль до бази даних. Найлегше вписати його в `values.yaml` і закомітити. Файл потрапить у кожну
копію репозиторію й у всю історію. Видалення рядка наступним комітом пароля не прибере.

Курс розбирає п'ять справжніх випадків. Спільна риса: це не складні атаки, а секрет не в тому місці.

| Рік | Хто | Де лежав секрет | Що сталося |
|-----|-----|-----------------|------------|
| 2014 | Code Spaces | доступ до керування AWS | стерто дані й резервні копії, компанія закрилася |
| 2016 | Uber | ключі AWS у приватному репозиторії | витік даних 57 мільйонів користувачів |
| 2022 | Dropbox | ключі в репозиторіях, викрадених через фішинг | викрадено 130 репозиторіїв |
| 2022 | Toyota | ключ у коді, викладеному на GitHub підрядником | доступ відкритий майже п'ять років |
| 2025 | tj-actions/changed-files | секрети запусків GitHub Actions | скомпрометована дія виводила їх у журнали |

## Що таке об'єкт `Secret`

`Secret` — це об'єкт кластера для чутливих даних. Значення в полі `data` записано в **base64**, і вважати це захистом
не можна. Кодування перетворює байти на текст, і обернути його може будь-хто без ключа. Шифрування, навпаки, без ключа
не обернеш. Base64 потрібен тому, що об'єкти передаються як JSON або YAML, а значенням може бути двійковий файл,
наприклад ключ TLS.

**Пастка кінця рядка.** Команда `echo` додає символ нового рядка, і він теж кодується.

| Команда | Результат | Що всередині |
|---------|-----------|--------------|
| `echo -n 'kvitka' \| base64` | `a3ZpdGth` | 6 байтів |
| `echo 'kvitka' \| base64` | `a3ZpdGthCg==` | 7 байтів, останній є новим рядком |

Застосунок порівнює пароль байт за байтом, тому зайвий символ означає відмову у вході. Значення в `stringData`
кодувати не треба: Kubernetes об'єднує його з `data` сам, і при збігу ключів перемагає `stringData`.

**Типи.** Поле `type` визначає потрібні ключі. За документацією `kubernetes.io/tls` вимагає `tls.crt` і `tls.key`,
`kubernetes.io/dockerconfigjson` вимагає `.dockerconfigjson` із правильним JSON, а `Opaque` нічого не перевіряє. Є ще
`kubernetes.io/basic-auth`, якого лабораторна не згадує.

## Хто насправді бачить секрет

Документація попереджає: типово секрети лежать у сховищі кластера незашифрованими. Є й менш помітне правило: **кожен,
хто може створити под у просторі імен, може прочитати будь-який секрет цього простору**, бо досить підключити секрет
до свого пода. Це стосується й права створювати `Deployment`.

| Де лежить значення | Хто його бачить | Що захищає |
|--------------------|-----------------|------------|
| git | усі, хто клонував | не класти туди; сканери |
| журнал CI, історія оболонки | усі, хто читає журнали | передавати змінною або файлом, а не аргументом |
| API кластера | хто має `get secrets` чи може створити под | права RBAC, окремі простори імен |
| запис випуску Helm | хто читає секрети в цьому просторі | RBAC; значення не передавати через Helm |
| сховище кластера, резервні копії | хто дістав диск | шифрування сховища |
| запущений под | хто може виконати `exec` | RBAC, файл замість змінної |

## Шифрування сховища

Сервер API може шифрувати об'єкти перед записом. Це задає перелік `providers` у файлі `EncryptionConfiguration`.
Документація описує правило так: **перший** постачальник шифрує все нове, а при читанні постачальники пробуються за
порядком.

```text
Запис:   kubectl apply -> API -> перший постачальник шифрує -> сховище
Читання: сховище -> API пробує постачальників -> розшифрований об'єкт -> кому дозволяє RBAC
```

- **`identity`** нічого не шифрує. Якщо він перший, шифрування вимкнено, навіть коли далі є ключ. Лекція курсу пише
  «останній», а точніше: не перший.
- **Старі дані лишаються незашифрованими**, доки їх не перезапишуть. Документація дає команду `kubectl get secrets
  --all-namespaces -o json | kubectl replace -f -`.
- **Захист не діє на шляху через API**, бо сервер розшифровує об'єкт раніше, ніж віддати його.

Контрольне запитання: **чим шифрування etcd не допомагає проти людини з `kubectl get secret`?** Вона не читає диск, а
звертається до сервера API. Він сам розшифровує значення й перевіряє лише її права. Вона отримає base64, який
обертається без ключа. Шифрування захищає від того, хто вкрав диск чи резервну копію. Від людини з правами захищає
RBAC, а від витоку в git чи журнали — окреме сховище й дисципліна.

| Постачальник | Оцінка документації | Де ключ |
|--------------|---------------------|---------|
| `identity` | захисту немає | ключа немає |
| `aescbc` | слабкий, не рекомендований через атаку padding oracle | файл на вузлі керування |
| `aesgcm` | лише за автоматичної зміни ключів: кожні 200 000 записів | файл на вузлі керування |
| `secretbox` | сильний | файл на вузлі керування |
| `kms` v1 | застарів із 1.28, типово вимкнений із 1.29 | зовнішня служба |
| `kms` v2 | найсильніший, стабільний із 1.29 | зовнішня служба |

**Навіщо KMS.** Той, хто заволодів вузлом керування, дістане файл із локальним ключем. **KMS** (Key Management
Service, служба керування ключами) застосовує **конвертне шифрування**: дані шифрує робочий ключ (DEK), а його шифрує
головний (KEK), який не покидає зовнішню службу. Приклад на слайді 8 курсу не має поля `apiVersion`, а це означає
застарілу першу версію.

**Що в k3d.** Документація k3s каже: типове сховище одного сервера — SQLite, а не etcd. Логіка та сама, бо вона
стосується сервера API. Прапорець `--secrets-encryption` вмикає шифрування під час запуску сервера. Лабораторна цього
не просить, а вимагає пояснення своїми словами.

## Секрет у чарті

План такий: шаблон у чарті, заглушка у `values.yaml`, справжнє значення лише під час встановлення. Шаблон використовує
`stringData`, бо інакше значення довелося б кодувати самому, а двічі закодований пароль не спрацює.

```text
values.yaml у git: ЗАГЛУШКА  --  helm upgrade --set password=$PASS  -->  Secret у кластері  -->  envFrom у поді
```

**Що заглушка не розв'язує.** Значення лежить в об'єкті `Secret` і в **записі випуску Helm**: документація каже прямо,
що значення `--set` зберігаються в `Secret`. Також воно може лишитись в історії оболонки й журналах CI.

**Наступне оновлення.** Якщо `helm upgrade` отримав інші значення, але не цей `--set`, у секрет повернеться заглушка.
Перевіряй `helm get values`.

**Змінні застигають.** Значення зі `envFrom` фіксується на старті контейнера, тому зміна секрету не змінить запущений
под. Докладніше в лекції 12.

**CI.** Значення зберігається в секретах сховища, передається в крок як змінна оточення, а команда читає її зі
змінної. GitHub намагається приховувати такі значення в журналах, але це не гарантія, і випадок tj-actions це показав.

## OpenBao

HashiCorp Vault був відкритим сервером секретів. У серпні 2023 року компанія змінила ліцензію на BSL 1.1, яка обмежує
конкурентне комерційне використання. Linux Foundation створив відгалуження OpenBao з ліцензією MPL-2.0. Команди й
шляхи API збереглися, тому інструкції для Vault майже завжди допомагають.

OpenBao зберігає секрети, видає їх за політикою й веде журнал доступу. Застосунок доводить, хто він, і отримує лише
дозволене.

```text
клієнт --> автентифікація --> токен + політики --> механізм секретів --> зашифроване сховище
```

| Поняття | Що це | Приклади |
|---------|-------|----------|
| **Механізм секретів** (secrets engine) | де лежать або як генеруються секрети | `kv`, `database`, `pki` |
| **Метод автентифікації** (auth method) | як клієнт доводить, хто він | токен, `kubernetes`, AppRole |
| **Політика** (policy) | перелік шляхів і дозволених дій | читання одного шляху |
| **Токен** (token) | пропуск із політиками й строком дії | результат входу |

Звичайний сервер спершу **запечатаний** (sealed): він не може прочитати власні дані, доки не отримає ключ. **Режим
розробки** (`-dev`) за документацією OpenBao розпечатаний одразу, зберігає дані лише в пам'яті, слухає
`127.0.0.1:8200` без TLS і **вже має механізм KV v2 за шляхом `secret/`**.

Останнє створює пастку: завдання пропонує увімкнути механізм за шляхом `secret`, а цей шлях уже зайнятий, тому команда
відмовить. Можна вибрати інший шлях, і тоді він має бути в усіх командах і в політиці. Поточні шляхи покаже `bao
secrets list`.

**Контракт змінних.** Клієнт `bao` читає `BAO_ADDR` (адреса) і `BAO_TOKEN` (токен). У реальному встановленні токен
стане короткоживучим і прийде від методу автентифікації.

## Шляхи KV v2: логічний і справжній

Механізм **KV v2** зберігає версії значень. Для цього його API має префікси: значення лежить за `data/`, а метадані за
`metadata/`. Команда `bao kv put` приховує це від тебе, а політика — ні.

Приклад: механізм підключено за шляхом `team`, секрет називається `billing/api`.

| Хто | Яким шляхом користується |
|-----|---------------------------|
| ти в команді `bao kv get team/billing/api` | логічний: `team/billing/api` |
| сервер обробляє запит | справжній: `team/data/billing/api` |
| **політика** | мусить назвати справжній |
| шаблон агента-ін'єктора | справжній |
| ESO у полі `remoteRef.key`, якщо `path` уже вказує механізм | відносно механізму: `billing/api` |

Останній рядок відрізняється від твердження лабораторної, що та сама пастка є в ESO. Приклади документації ESO пишуть
ключ без `data/`, а версію задають окремим полем `version`.

Політика з логічним шляхом не дасть жодного доступу: запит піде на інший шлях і отримає відмову. Лабораторна називає
це головною причиною, чому «правильна» політика заважає читати.

## Політика й доказ відмовою

**Політика** — це перелік шляхів і дій. Документація каже: все заборонено, якщо не дозволено явно. Дії прив'язані до
методів HTTP.

| Дія | Метод HTTP | Що дає |
|-----|------------|--------|
| `read` | GET | читати значення |
| `create`, `update` | POST, PUT | створити новий або змінити наявний |
| `patch` | PATCH | змінити частину |
| `delete` | DELETE | видалити |
| `list` | LIST | показати назви |
| `sudo` | | доступ до захищених шляхів |
| `deny` | | заборонити, навіть якщо щось інше дозволяє |

Коли кілька правил підходять, діє найточніше: точний шлях сильніший за шаблон `*`. Вбудована політика `default` за
замовчуванням додається до кожного нового токена. Тому в переліку політик свого токена ти побачиш і її.

Приклад для вигаданого секрету команди. Це не відповідь лабораторної: у ній інші дія і шлях.

```hcl
path "team/data/billing/*" {
  capabilities = ["create", "update", "read"]
}
```

**Чому читання нічого не доводить.** Уяви, що ти написав занадто широку політику: дозволив усе. Перевірка «читання
працює» пройде. Перевірка з кореневим токеном теж пройде, бо кореневий токен обходить будь-які політики. Обмеження
можна довести лише спробою того, що заборонено.

**Покроковий приклад.** Правильний порядок перевірки на вигаданій політиці, яка дозволяє лише читання:

| Крок | Який токен | Дія | Очікуваний результат | Що це доводить |
|------|------------|-----|----------------------|----------------|
| 1 | кореневий | записати значення | успіх | дані існують |
| 2 | кореневий | створити обмежений токен | токен | токен отримано |
| 3 | обмежений | `bao token lookup` | перелік політик: `default` і твоя | ти справді під обмеженим токеном |
| 4 | обмежений | прочитати значення | успіх | потрібний доступ є |
| 5 | обмежений | записати значення | `permission denied` | зайвого доступу немає |

Крок 3 лабораторна не вимагає, але він виключає прикрий випадок: якщо змінна токена порожня, команда може використати
збережений раніше кореневий токен, і запис пройде. Тоді результат виглядатиме як помилка політики, а причина буде
зовсім інша.

## Доставка в под

Основні завдання лабораторної виконуються на локальному сервері, без зв'язку з кластером. Подальший крок, доставку
значення в под, винесено в бонус. Вибір між двома варіантами і є реальним рішенням.

**Автентифікація пода.** Кожен под може мати токен свого **облікового запису служби** (ServiceAccount). Це підписаний
JWT. Поду не потрібен пароль до OpenBao:

| Крок | Хто | Що робить |
|------|-----|-----------|
| 1 | под | надсилає OpenBao свій JWT і назву ролі |
| 2 | OpenBao | питає у Kubernetes через TokenReview API, чи дійсний цей токен |
| 3 | OpenBao | перевіряє, що роль дозволяє саме цей обліковий запис і простір імен |
| 4 | OpenBao | видає власний токен із політиками ролі |
| 5 | под | читає дозволений секрет |

**Агент-ін'єктор** працює через **змінюючий вебхук допуску** (mutating admission webhook): коли кластер отримує новий
под, він спершу надсилає його опис програмі ін'єктора, а та дописує контейнери. Тому твій файл має один контейнер, а
запущений под три. Початковий контейнер отримує секрет до старту застосунку, а супровідний оновлює його під час
роботи. Застосунок читає файл із `/vault/secrets/`.

**External Secrets Operator (ESO)** — контролер, який читає об'єкт `ExternalSecret`, забирає значення із зовнішнього
сховища й створює звичайний `Secret`. Застосунок нічого не знає про OpenBao.

```text
ін'єктор:  OpenBao --> агент у поді --> файл у пам'яті пода --> застосунок
ESO:       OpenBao --> контролер --> Secret у сховищі кластера --> envFrom --> застосунок
```

| Запитання | Ін'єктор | ESO |
|-----------|----------|-----|
| Де лежить значення в кластері | лише в поді | знову в об'єкті `Secret`, тобто й у сховищі кластера |
| Що робить застосунок | читає файл | читає звичайну змінну чи файл |
| Що коштує | супровідний контейнер у кожному поді | один контролер |
| Як оновлюється | агент оновлює файл, а застосунок ще має його перечитати | за `refreshInterval`, а змінні застигають до перезапуску |
| Коли краще | тимчасові паролі, короткий строк життя | багато подів читають кілька сталих секретів |

Контрольне запитання: **що вибереш для свого сервісу, і що втрачаєш разом із цим вибором?** Правильної відповіді одним
словом немає. Якщо вибираєш ін'єктор, платиш контейнером у кожному поді й змінюєш застосунок так, щоб він читав файл.
Якщо вибираєш ESO, значення знову лежить у сховищі кластера, отже, діють усі попередні застереження, плюс затримка
оновлення.

## Інші шляхи

Не кожна команда готова тримати сервер секретів.

- **SOPS** шифрує значення всередині файла, і такий файл можна класти в git. Розшифровує його конвеєр.
- **Sealed Secrets** шифрує значення відкритим ключем контролера в кластері, і лише цей кластер може розшифрувати. Для
  нього є окремий примірник `sealed-secrets`.

Обидва не дають окремого журналу доступу й центрального оновлення, зате не потребують окремого сервера. Третій шар —
**сканери** (`gitleaks`, `trufflehog`): вони перевіряють коміти й ловлять людські помилки до того, як вони потраплять
на сервер.

## Типові хибні уявлення

**«Видалити секрет із git наступним комітом досить».** Значення лишилось в історії та в кожній копії. Такий секрет
вважай скомпрометованим і заміни.

**«`kubectl describe` не показує значення, отже, воно приховане».** `get -o yaml` віддає все тому, хто має право.

**«Команда `bao kv get` спрацювала, отже, політика правильна».** Це доводить лише наявність доступу. Обмеження
доводить відмова.

## Практика

**Спершу скажи:** «збери примірник OpenBao й External Secrets Operator». Їх ще немає у фабриці, а без них лишається
тільки текст курсу. Потім роби [лабораторну
11](https://github.com/inno-devops-labs/DevOps-Core-Course/blob/master/labs/lab11.md):

1. Перед розкодуванням власного секрету скажи, що побачиш. Потім виконай і запиши результат.
2. Після встановлення чарту подивись `helm get values` і поясни, де ще лежить твоє значення.
3. Перед написанням політики випиши логічний і справжній шлях для свого секрету.
4. Перед спробою запису передбач точне слово у відмові. Якщо запис пройшов, спершу подивись `bao token lookup`, а вже
   потім змінюй політику.
5. Перед бонусом порівняй варіанти за таблицею вище для застосунку, який хотів би запустити.

Не клади справжній пароль у жоден файл: у цій лабораторній достатньо вигаданого значення.

## Перевір себе

**1. Чим шифрування etcd не допомагає проти людини з `kubectl get secret`?**

<details><summary>Відповідь</summary>

Сервер API сам розшифровує значення перед видачею й перевіряє лише права цієї людини. Шифрування захищає від того, хто
дістав диск або резервну копію. Від людини з правом читання захищає RBAC.

</details>

**2. Що вибереш для свого сервісу, ін'єктор чи ESO, і що втрачаєш разом із цим вибором?**

<details><summary>Відповідь</summary>

Обґрунтуй власний випадок. З ін'єктором значення не лежить у сховищі кластера, але кожен под має додатковий контейнер,
а застосунок має читати файл. З ESO застосунок не змінюється, контролер один, але значення лежить у звичайному
`Secret`, а оновлення приходить із затримкою.

</details>

**3. Людина не має права `get secrets`, але може створювати `Deployment` у цьому просторі. Чи може вона прочитати
секрет?**

<details><summary>Відповідь</summary>

Так. Вона створить под, підключить до нього секрет і прочитає значення з пода. Документація каже про це прямо, тому
право створювати поди теж є правом читання секретів цього простору.

</details>

**4. Політика каже `path "team/billing/api"`, механізм KV v2 підключено за шляхом `team`. Чому токен отримує відмову
при читанні?**

<details><summary>Відповідь</summary>

Справжній шлях читання в KV v2 містить `data/`: `team/data/billing/api`. Названий у політиці шлях не збігається із
запитом, а все не дозволене явно заборонено.

</details>

**5. У переліку `EncryptionConfiguration` спершу стоїть `identity`, потім `aescbc`. Чи зашифровані нові секрети?**

<details><summary>Відповідь</summary>

Ні. Новий запис виконує перший постачальник, а він нічого не шифрує. `aescbc` тут лише зможе прочитати значення,
зашифровані раніше.

</details>

**6. Після `helm upgrade` без `--set secret.dbPassword` застосунок перестав входити в базу. Що сталося?**

<details><summary>Відповідь</summary>

Якщо ти передав інші значення, значення з минулого `--set` не перенеслись, тож у секреті опинилася заглушка. Перевір
`helm get values` і порівняй із попередньою ревізією. Застосунок побачить нове значення після перезапуску, бо змінні
застигають при старті.

</details>

**7. Перевірка показала, що запис із обмеженим токеном теж пройшов. Що перевірити першим?**

<details><summary>Відповідь</summary>

Який токен насправді використано: `bao token lookup`. Якщо там кореневий токен, змінна порожня або не застосувалась.
Якщо токен обмежений, подивись політики: найімовірніше, правило містить зайву дію або занадто широкий шлях.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| base64 | кодування байтів у текст; обертається без ключа |
| шифрування сховища (encryption at rest) | сервер API шифрує об'єкти перед записом |
| KMS, DEK, KEK | зовнішня служба ключів; робочий ключ даних; головний ключ |
| RBAC | правила, хто які дії може виконувати через API кластера |
| OpenBao, KV v2 | відкритий сервер секретів; його механізм пар із версіями |
| запечатування (seal) | стан, у якому сервер не може прочитати власні дані |
| ServiceAccount | обліковий запис служби: ідентичність пода |
| ін'єктор, ESO | вебхук, що додає контейнери агента; контролер, що створює `Secret` із зовнішнього сховища |
