# Лекція 13. GitOps: кластер сам приводить себе до стану з git

Ця лекція пояснює, як розгортання перестає бути командою, яку хтось запускає, і стає станом, який кластер підтримує
сам. Читання займе близько 45 хвилин, а саму лабораторну ти виконуватимеш протягом тижня.

**Після лекції ти зможеш пояснити:**

- чим модель pull (кластер сам забирає зміни) відрізняється від моделі push (хтось заходить у кластер ззовні);
- чим звірка відрізняється від синхронізації і чому застосунок може бути `Synced` і водночас `Degraded`;
- що окремо дозволяють `automated`, `selfHeal` і `prune`;
- які ресурси Argo CD вважає своїми і чому створений вручну ресурс він не видалить;
- як `ApplicationSet` робить шість застосунків з одного шаблону і чому умовну політику доводиться писати через
  `templatePatch`.

Лекція спирається на поняття з [плану Kubernetes](../../kubernetes/LEARNING.md): `Deployment` (об'єкт, який підтримує
потрібну кількість подів), простір імен (namespace), контролер (програма в кластері, яка приводить реальність до
опису) і чарт Helm (набір шаблонів маніфестів).

## Звідки береться проблема

Уяви, що сервіс уже працює в кластері, а оновлюєш ти його командою `helm upgrade` зі свого ноутбука або з конвеєра CI.
О третій ночі сервіс падає, і черговий виправляє змінну середовища через `kubectl edit`. Сервіс ожив, а чарт у git
залишився старим. Через тиждень хтось запускає `helm upgrade`, і нічне виправлення мовчки зникає.

У цій історії є три окремі проблеми:

1. **Права.** Конвеєр CI мусить мати файл доступу до кластера з широкими правами, і кожен витік такого файла відкриває
   весь кластер.
2. **Розбіжність.** Реальність розійшлася з описом, і ніщо їх не порівнює. Таку розбіжність називають **дрейфом**
   (drift).
3. **Слід.** Відповідь на запитання «хто збільшив кількість реплік до 12?» лежить в історії чиєїсь оболонки.

GitOps розв'язує всі три проблеми однією зміною: програму, яка застосовує зміни, переносять усередину кластера й
доручають їй стежити за git.

## Що таке GitOps

**GitOps** — це спосіб керувати системою, за якого бажаний стан описано в git, а програма-агент сама його забирає й
постійно звіряє з реальністю. Робоча група OpenGitOps сформулювала [чотири принципи](https://opengitops.dev/):

| Принцип | Що він означає на практиці |
|---------|----------------------------|
| Declarative (декларативний) | Ти описуєш, яким має бути результат, а не які команди виконати |
| Versioned and Immutable (із версіями й незмінний) | Усю історію бажаного стану збережено, тому для кожного коміту відомо, що мало працювати |
| Pulled Automatically (забирається автоматично) | Програми-агенти самі забирають опис із джерела |
| Continuously Reconciled (постійно звіряється) | Агенти постійно дивляться на справжній стан і намагаються застосувати бажаний |

Напрям руху змінюється так:

```text
PUSH (як було)
  git --> конвеєр CI --(файл доступу, kubectl або helm)--> кластер

PULL (GitOps)
  git <--(агент сам читає git)-- агент усередині кластера --> API кластера
```

| Що порівнюємо | Push | Pull |
|---------------|------|------|
| Де лежать права на кластер | у CI й на ноутбуках | лише всередині кластера |
| Хто помічає дрейф | ніхто | агент, постійно |
| Де шукати, хто що змінив | журнали CI | історія git |
| Як відновити кластер | заново запустити конвеєри | встановити агента й указати йому на git |
| Що блокує розгортання | недоступний CI | недоступний git |

CI при цьому лишається: конвеєр далі збирає образ і перевіряє код, але до кластера більше не звертається. Git також
відновлює лише конфігурацію, а не дані, тому резервні копії томів і баз лишаються окремою справою.

## З чого складається Argo CD

**Argo CD** — це той самий агент: набір програм, які працюють у просторі імен `argocd`. Ти описуєш завдання для нього
власним ресурсом кластера (custom resource, тобто новий вид об'єктів, який Argo CD додає до Kubernetes).

| Складова | Що робить |
|----------|-----------|
| `argocd-server` | Обслуговує вебінтерфейс, команду `argocd` і API, перевіряє права, приймає вебхуки від git |
| `argocd-repo-server` | Тримає копію репозиторію й перетворює чарти на готові маніфести |
| `argocd-application-controller` | Порівнює бажаний стан зі справжнім і за потреби застосовує зміни. Це і є цикл звірки |
| `argocd-applicationset-controller` | Створює об'єкти `Application` із шаблону |
| `argocd-redis` | Кешує результати, щоб не обчислювати їх щоразу заново |
| `argocd-notifications-controller` | Надсилає сповіщення про події |
| `argocd-dex-server` | Посередник для входу через зовнішні облікові записи |

**Важливий наслідок для тих, хто вивчав Helm.** Argo CD [використовує Helm лише як механізм
шаблонів](https://argo-cd.readthedocs.io/en/stable/faq/): він виконує `helm template` і сам застосовує результат
замість `helm install`. Тому `helm ls` не покаже твій застосунок, а `helm rollback` тут не працює. Історію й відкат
веде сам Argo CD. Назва релізу Helm за замовчуванням збігається з назвою `Application`.

## Application: запис «що куди»

`Application` каже Argo CD: візьми цю теку з цього репозиторію на цій версії й поклади в цей простір імен цього
кластера. Ось приклад для вигаданого сервісу `wiki`. Це не відповідь до лабораторної, там значення будуть інші.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: wiki-test                  # назва самого запису
  namespace: argocd                # запис завжди лежить у просторі імен Argo CD
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://example.org/acme/wiki.git
    targetRevision: trunk          # гілка, тег або коміт
    path: deploy/wiki              # тека чарту в репозиторії
    helm:
      valueFiles:
        - values-test.yaml
  destination:
    server: https://kubernetes.default.svc   # той самий кластер, де працює Argo CD
    namespace: wiki-test           # сюди потрапить сам сервіс
```

Тут легко помилитися в трьох місцях:

- **Простори імен два.** `metadata.namespace` каже, де лежить запис, а `spec.destination.namespace` каже, куди
  потраплять поди. Запис завжди лежить в `argocd`, а сервіс ніколи туди не потрапляє.
- **Фіналізатор вирішує долю сервісу під час видалення.** Фіналізатор (finalizer) — це позначка, яка не дає Kubernetes
  видалити об'єкт, доки контролер не виконає свою роботу. З цим фіналізатором видалення `Application` прибирає й усе,
  чим вона керує. Без нього запис зникне, а `Deployment` і `Service` працюватимуть далі вже без нагляду.
- **`targetRevision` має існувати й містити теку `path`.** Якщо чарт лежить у гілці, якої Argo CD не читає, він не
  знайде теки й покаже помилку.

## Звірка й синхронізація: дві різні дії

Argo CD тримає два описи: **бажаний стан** (target state, те, що виходить із файлів у git) і **живий стан** (live
state, те, що справді є в кластері). З ними виконують дві різні дії:

- **Звірка** (refresh) лише порівнює бажаний стан із живим і записує результат. У кластері нічого не змінюється.
- **Синхронізація** (sync) застосовує зміни, щоб живий стан став бажаним.

Результати записано у двох незалежних полях:

| Поле | Значення | Про що воно |
|------|----------|-------------|
| Стан синхронізації | `Synced`, `OutOfSync`, `Unknown` | Чи збігається кластер із git |
| Стан здоров'я | `Healthy`, `Progressing`, `Degraded`, `Suspended`, `Missing` | Чи працює те, що запущено |

Тому можливі й такі поєднання. `Synced` і `Degraded` означає, що кластер точно виконав git, але в git описано образ,
який падає. `OutOfSync` і `Healthy` означає, що сервіс працює, але не так, як описано.

**Коли відбувається звірка.** Тут є дві різні події, і курс їх часто об'єднує:

- **Зміна в git.** Argo CD [опитує репозиторій приблизно кожні три
  хвилини](https://argo-cd.readthedocs.io/en/stable/faq/): 120 секунд плюс випадкова добавка до 60 секунд. Вебхук від
  git або кнопка `REFRESH` прискорюють це.
- **Зміна в кластері.** Контролер не чекає трьох хвилин: [застосунок оновлюється щоразу, коли змінюється ресурс, що
  йому належить](https://argo-cd.readthedocs.io/en/stable/operator-manual/reconcile/). Тому `OutOfSync` після `kubectl
  edit` зазвичай видно майже одразу.

Отже, «три хвилини» стосуються нових комітів, а для самовідновлення це лише верхня межа.

## Покроковий приклад

Візьмемо `wiki-test` з автоматичною синхронізацією. У git записано 2 репліки, у кластері працює 2.

| Крок | Хто діє | Що відбувається | Що показує Argo CD |
|------|---------|-----------------|--------------------|
| 1 | Ти | Комітиш 3 репліки у файл значень. Кластер не змінюється | Поки що `Synced`: нового коміту ще не бачили |
| 2 | Контролер | Не пізніше ніж за три хвилини бачить коміт: у git 3, у кластері 2 | `OutOfSync` |
| 3 | Контролер | `automated` дозволяє синхронізацію цього коміту, і він застосовує зміну | `Synced`, спершу `Progressing`, потім `Healthy` |
| 4 | Людина | Виконує `kubectl scale --replicas=1` | Майже одразу `OutOfSync`: у git 3, у кластері 1 |
| 5а | Контролер без `selfHeal` | Нічого не робить: цей коміт уже синхронізовано | Лишається `OutOfSync`, працює 1 репліка |
| 5б | Контролер із `selfHeal` | Застосовує git знову | `Synced`, знову 3 репліки |
| 6 | Людина | Створює вручну `Secret` на ім'я `wiki-token` у тому самому просторі імен | Нічого не змінюється: цей об'єкт не належить застосунку |
| 7 | Ти | Видаляєш із чарту шаблон `ConfigMap` і комітиш | `OutOfSync`: об'єкт є в кластері, але його немає в git |
| 8а | Контролер без `prune` | Не видаляє `ConfigMap` | Лишається `OutOfSync` |
| 8б | Контролер із `prune` | Видаляє `ConfigMap`, а `wiki-token` не чіпає | `Synced` |

Зверни увагу на кроки 6 і 8б: прибирання стосується лише того, що Argo CD сам вважає своїм.

## Три окремі дозволи

Блок `syncPolicy.automated` складається з трьох незалежних рішень, і кожне вирішує своє запитання.

| Налаштування | На яке запитання відповідає | Чого не робить |
|--------------|-----------------------------|----------------|
| `automated` | Чи застосовувати новий стан із git без людини? | Не реагує на ручні зміни в кластері й нічого не видаляє |
| `selfHeal` | Чи скасовувати ручні зміни в кластері? | Не лікує падіння застосунку, якщо git описує зламаний образ |
| `prune` | Чи видаляти те, що зникло з git? | Не чіпає ресурсів, які не належать застосунку |

Без блока `automated` синхронізацію запускає людина кнопкою `SYNC` або командою `argocd app sync`. [Правила
автоматичного режиму](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/) такі:

- Синхронізація запускається лише тоді, коли застосунок `OutOfSync`.
- На кожне поєднання коміту й параметрів припадає одна спроба. Якщо вона провалилася, повтору за тим самим комітом не
  буде, окрім випадку з увімкненим `selfHeal`. Тоді спроба повториться після паузи, яка за замовчуванням становить 5
  секунд.
- Відкат командою неможливий, поки ввімкнено автоматичний режим. Відкат у такому застосунку робиться новим комітом.
- Є запобіжник: якщо після побудови чарту не лишилося жодного ресурсу, автоматичне прибирання нічого не видалить. Поле
  `allowEmpty` скасовує цей запобіжник. Прочитай документацію й вирішуй сам, що записати в лабораторній.

**Чому dev автоматично, а prod вручну.** У dev помилка коштує кілька хвилин, а швидкий зворотний зв'язок дає більше
користі. У prod людина має подивитися на різницю перед застосуванням. З тієї самої причини prod не прив'язують до
рухомої гілки: версія змінювалася б після будь-якого злиття, а тег чи гілка випуску зупиняє цей рух.

## Що саме видаляє prune

Argo CD порівнює не весь кластер, а лише ресурси, які вважає своїми. Щоб їх розрізняти, він під час синхронізації
ставить на кожен ресурс позначку. Починаючи з версії 3.0, [за замовчуванням це
анотація](https://argo-cd.readthedocs.io/en/release-3.4/user-guide/resource_tracking/)
`argocd.argoproj.io/tracking-id`. Її значення має такий вигляд:

```text
wiki-test:apps/Deployment:wiki-test/wiki-test-web
```

Тут записано назву застосунку, групу й вид об'єкта, простір імен і назву самого об'єкта. З цього випливає кілька
наслідків:

- **Створений вручну ресурс не має цієї анотації, тому Argo CD його не відстежує.** Такий ресурс не потрапляє до
  застосунку, не робить його `OutOfSync`, і `prune` його не видаляє. `selfHeal` теж його не прибере.
- **Побачити такі ресурси можна окремо.** Функція [Orphaned
  Resources](https://argo-cd.readthedocs.io/en/stable/user-guide/orphaned-resources/) вмикається в налаштуваннях
  проєкту й попереджає про ресурси поза застосунками.

**Коли `prune` справді небезпечний.** Небезпека в тому, що видаляється об'єкт, який Argo CD уже відстежував:

- Секрет колись лежав у git і був синхронізований, а потім його прибрали з git. Він має анотацію, тому буде видалений.
- Ти змінив `path` на іншу непорожню теку. Усе, що застосунок відстежував зі старої теки, зникне. Неіснуюча тека
  видалення не спричинить: Argo CD не зможе побудувати маніфести й покаже помилку.
- Ти створив об'єкт вручну, а потім об'єкт із тим самим видом, простором імен і назвою з'явився в git. Синхронізація
  застосує опис до наявного об'єкта, і відтоді він уже відстежується.
- У git лежить `Namespace`, і його прибрали. Сам `prune` видалить лише цей об'єкт, але Kubernetes разом із простором
  імен видаляє все в ньому, також і створене вручну.

Анотація `argocd.argoproj.io/sync-options: Prune=false` захищає окремий об'єкт навіть за ввімкненого `prune`.

## Що бачить порівняння

Є ще одна межа, яку лабораторна не згадує. За замовчуванням Argo CD використовує [стратегію
Legacy](https://argo-cd.readthedocs.io/en/stable/user-guide/diff-strategies/): тристороннє порівняння живого стану,
бажаного стану й останньої застосованої конфігурації. [Код
порівняння](https://github.com/argoproj/gitops-engine/blob/master/pkg/diff/diff.go) будує зміни, які треба внести, а
поле, якого немає ні в git, ні в останній застосованій конфігурації, до цих змін не потрапляє.

Висновок: **нова мітка, якої чарт не задає, найімовірніше не дасть `OutOfSync`, і `selfHeal` її не скасує**, адже він
спрацьовує лише на `OutOfSync`. Зміна значення мітки, яку чарт записує сам, видна як дрейф. У документації окремого
речення про це немає, тому висновок зроблено з читання коду порівняння, а на справжньому кластері його тут не
перевіряли. Перед кроком 4.4 лабораторної подивись самостійно, що покаже `argocd app diff`.

## ApplicationSet: один шаблон замість шести файлів

Коли сервісів три, а середовищ два, тобі потрібно шість `Application`, які збігаються майже повністю. Курс вводить
третій сервіс `health` саме для цього: на одному чи двох застосунках шаблон не дає користі. Цей маленький сервіс
докладніше показано в розборі читання.

`ApplicationSet` складається з двох частин: **генератора**, який видає набори параметрів, і **шаблону**, який
перетворює кожен набір на `Application`. Є багато генераторів, а лабораторній потрібні два:

- **List** отримує записаний вручну перелік елементів, і кожен елемент містить пари ключ і значення.
- **Matrix** поєднує результати [рівно двох дочірніх
  генераторів](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Matrix/) кожен із
  кожним. Він завершиться помилкою, якщо обидва дочірні генератори видадуть той самий ключ із різними значеннями.

Наприклад, два сервіси `wiki` і `forum` та два середовища `test` і `live` дадуть 2 × 2 = 4 набори параметрів, а отже,
чотири застосунки.

**Два рушії шаблонів.** За замовчуванням працює fasttemplate, який лише підставляє рядки: `{{name}}`. Поле
`goTemplate: true` вмикає шаблони мови Go із записом `{{.name}}`, умовами та функціями. Документація радить додавати
`goTemplateOptions: ["missingkey=error"]`, щоб помилка в назві параметра зупиняла генерацію, а не давала порожній
рядок.

**Головна пастка.** [Шаблони Go застосовуються лише до окремих рядкових
полів](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/GoTemplate/). Документація прямо
перелічує, чого робити не можна: шаблонізувати об'єктні поля на кшталт `syncPolicy` і логічні значення, а також
розтягувати `if` через кілька полів. Тому вставити умову прямо в поле `template`, як підказує коментар у лабораторній,
не вийде: `template` є структурованим YAML, а не текстом. Для цього існує окреме поле
[`templatePatch`](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/applicationset/Template/). Воно
містить текстовий шаблон, а результат накладається на `template`. Ось приклад з іншим полем, де частина застосунків
отримує анотацію:

```yaml
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - list:
        elements:
          - { name: wiki,  tier: "gold" }
          - { name: forum, tier: "basic" }
  template:
    metadata:
      name: '{{ .name }}'
    spec:
      project: default
      # source і destination записано тут, як в окремому Application
  templatePatch: |
    {{- if eq .tier "gold" }}
    metadata:
      annotations:
        acme.example/oncall: "true"
    {{- end }}
```

Чому тут `eq`, а не `if .tier`? Значення в List є рядками, а в шаблоні Go непорожній рядок вважається істиною, тому
рядок `"false"` спрацював би як істина. Документація радить `templatePatch` лише для довірених параметрів.

**Що станеться під час видалення.** [Видалення `ApplicationSet` видаляє всі створені ним
`Application`](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Application-Deletion/), а через
фіналізатор і їхні ресурси. Одна команда `kubectl delete` прибере всі шість сервісів. Поле
`syncPolicy.preserveResourcesOnDeletion` захищає від цього.

Контролер `ApplicationSet` також приводить створені застосунки до шаблону, тому постійні зміни треба вносити в шаблон.

## Хвилі, хуки й застосунок застосунків

Хвилі синхронізації й хуки задають порядок застосування, а застосунок застосунків керує самими записами `Application`.
Вони потрібні лише для бонусу й лекції курсу, тому їх пояснює розбір читання.

## Секрети в GitOps

Git має бути джерелом правди, але секрет там лежати не може, бо історія git не забуває нічого. Документація Argo CD
[радить заповнювати секрети вже в цільовому
кластері](https://argo-cd.readthedocs.io/en/stable/operator-manual/secret-management/), щоб Argo CD не мав із ними
справи. У лабораторній 11 External Secrets Operator читає значення з OpenBao, а в git лежить лише посилання.
Інструмент `sealed-secrets` кладе в git зашифрований об'єкт, який розшифровує контролер у кластері.

## Типові хибні уявлення

**«`prune` видалить мій створений вручну `Secret`».** Не видалить, бо такий об'єкт не має анотації відстеження й не
належить застосунку. Текст курсу тут помиляється. Секрет зникне, лише якщо раніше потрапив у застосунок через git або
лежав у просторі імен, який видалили.

**«Без `selfHeal` кластер не звіряється з git».** Звірка працює завжди, і `OutOfSync` буде видно. `selfHeal` вирішує
лише, чи скасовувати розбіжність автоматично.

**«`selfHeal` рятує від падіння застосунку».** Ні. Перезапуск пода виконує Kubernetes, а `selfHeal` повертає
конфігурацію з git. Якщо в git записано образ, що падає, застосунок буде `Synced` і `Degraded`.

## Практика

Виконуй завдання лабораторної по порядку й перед кожним запуском записуй передбачення в `JOURNAL.md`.

1. **Встановлення.** Передбач, скільки подів буде в `argocd`, якщо нічого не вимикати.
2. **Три застосунки dev без автоматичного режиму.** Передбач стан до першої синхронізації.
3. **Шлях через git.** Зміни значення в чарті й не запускай `kubectl apply`. Перевір, що значення не перекриває інший
   файл значень.
4. **Dev і prod.** Запиши своїми словами, чому політики різні. Заради цього й існує завдання.
5. **`ApplicationSet`.** Вибери шлях для різної політики, поясни вибір і переконайся, що застосунків рівно шість.
6. **Самовідновлення.** Видали навантаження, зміни мітку й зафіксуй час. Додатково створи власний тестовий `ConfigMap`
   у `dev`, запусти синхронізацію та переконайся, що він лишився на місці.

Докладний розбір кожного завдання є в [розборі читання](../reading/13-reading.md).

## Де курс розходиться з документацією

Ці межі тексту курсу звірено з документацією Argo CD.

| Що каже курс | Що насправді |
|--------------|--------------|
| `prune` видалить ресурс, застосований вручну | Невідстежуваний ресурс не прибирається. Перевір тестовим `ConfigMap` |
| Умову можна вставити прямо в `template` | Умову над `syncPolicy` пишуть у `templatePatch` |
| Argo CD відмовиться прийняти `Application` із такою самою назвою | [Код контролера](https://github.com/argoproj/argo-cd/blob/master/applicationset/controllers/applicationset_controller.go) перезаписує наявний запис і стає його власником. Попереднє видалення запису з фіналізатором ще й видаляє сервіс |
| Зміна мітки завжди показує дрейф | Нова мітка поза чартом, найімовірніше, не видна. Перевір через `argocd app diff` |

Решту дрібніших розходжень перелічує розбір читання.

## Перевір себе

Спершу відповідай сам, а потім розгортай пояснення.

**1. Ти зробив `kubectl edit` у продакшні під час аварії. Що станеться невдовзі з увімкненим `selfHeal`, і що ти
робитимеш?**

<details><summary>Відповідь</summary>

Зміна поля, описаного в git, дасть `OutOfSync`, і контролер поверне значення з git, зазвичай за лічені секунди, тому
сервіс знову зламається. Виправлення треба внести в git. Якщо потрібен час, тимчасово вимкни самовідновлення для цього
застосунку. Якщо його створено з `ApplicationSet`, зміну треба робити в шаблоні, інакше контролер її перезапише.

</details>

**2. Чому `prune` небезпечніший за `selfHeal`?**

<details><summary>Відповідь</summary>

`selfHeal` повертає конфігурацію, а наслідки такої помилки зазвичай можна виправити наступним комітом. `prune` видаляє
об'єкти, а разом із ними можуть зникнути дані, наприклад у томі. Видалення може запустити одна зміна в git, тому
невдале перейменування чи перенесення теки знищує відстежувані ресурси. Втім, ресурсів поза застосунком він не чіпає.

</details>

**3. Ти створив `Secret` командою `kubectl apply` у просторі імен, яким керує застосунок із `prune: true`. Що
станеться під час синхронізації?**

<details><summary>Відповідь</summary>

Нічого. У нього немає анотації відстеження, тому застосунок його не вважає своїм, не показує `OutOfSync` і не видаляє.
Проблема тут інша: секрет не описано в git, тож у новому кластері його не буде.

</details>

**4. Чому `{{- if eq .autoSync "true" }}automated: {}{{- end }}` не можна вставити в поле `template`?**

<details><summary>Відповідь</summary>

Шаблони застосовуються окремо до кожного рядкового поля, а `template` є структурованим YAML. Умова між полями не
утворює коректний YAML і не належить жодному рядковому полю. Умовну структуру пишуть у `templatePatch` за ввімкненого
`goTemplate`.

</details>

**5. Що відновить новий кластер після встановлення Argo CD і застосування твоїх описів, а чого не відновить?**

<details><summary>Відповідь</summary>

Він відновить усю конфігурацію, що описана в git: `Deployment`, `Service`, чарти й налаштування. Він не відновить дані
в томах і базах, а також секрети, якщо вони не описані так, щоб їх можна було створити знову, наприклад із зовнішнього
сховища.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| GitOps | агент у кластері сам забирає бажаний стан із git і постійно звіряє з ним реальність |
| бажаний і живий стан (target, live) | те, що виходить із git, і те, що справді є в кластері |
| дрейф (drift) | реальність розійшлася з описом |
| звірка (refresh) | порівняння бажаного й живого стану без змін у кластері |
| синхронізація (sync) | застосування змін, щоб живий стан став бажаним |
| `selfHeal`, `prune` | самовідновлення і прибирання відстежуваних ресурсів, яких немає в git |
| анотація відстеження (`tracking-id`) | позначка, за якою Argo CD знає, що ресурс належить застосунку |
