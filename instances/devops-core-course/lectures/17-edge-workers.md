# Лекція 17. Код без контейнера: Cloudflare Workers проти кластера

У лабораторних 9–16 ти запускав сервіс у кластері Kubernetes: образ контейнера, поди, служби, томи. Ця лекція показує
протилежний кінець шкали, де немає ні образу, ні вузла, ні вибору регіону. Вона пояснює, що стоїть за цією простотою й
чого за неї доводиться позбутися. Читання займе близько 30 хвилин. Загальну карту варіантів розгортання дає лекція 16
цього плану, а тут лише те, що потрібно для лабораторної 17.

**Після лекції ти зможеш пояснити:**

- чим ізолят V8 відрізняється від контейнера і чому він запускається за мілісекунди;
- чому твій сервіс із лабораторних 1–12 не можна перенести на Workers без переписування;
- чому лічильник у Workers KV може втрачати значення і яке сховище вибрати замість нього;
- чому після `wrangler kv key put` дані можуть опинитися зовсім не там, де їх читає твій Worker;
- як скласти таблицю порівняння з кластером так, щоб її цифри справді можна було порівнювати.

## Звідки береться запитання

Уяви сервіс, який приймає сповіщення від стороннього сервера двісті разів на день. Одна обробка триває кілька
мілісекунд. Якщо розгорнути його в кластері, тобі потрібні вузол, що працює цілодобово, образ контейнера, маніфести,
контролер вхідного трафіку й людина, яка оновлює все це. Майже весь час цей вузол нічого не робить, але гроші за нього
йдуть.

Лекція 16 курсу називає це податком Kubernetes: кластер дає контроль, а за контроль платять роботою й простоєм. Звідси
запитання: що зміниться, якщо платформа сама запускатиме твій код лише на час запиту?

Нагадаю два слова з кластера, бо далі вони потрібні. **Под** — це один або кілька контейнерів, які кластер запускає
разом на одному вузлі. **Вузол** — машина, на якій працюють поди. Якщо план Kubernetes ще не пройдено, почни з його
[частини A](../../kubernetes/LEARNING.md): там те саме пояснено докладно.

## Що таке ізолят V8

**V8** — це програма, яка виконує JavaScript. Вона працює всередині браузера Chrome і всередині Node.js. **Ізолят**
(англійською isolate) — це відокремлена ділянка пам'яті V8 разом із власним станом виконання: код в одному ізоляті не
бачить змінних коду в іншому, хоча обидва живуть в одному процесі операційної системи.

На цьому побудовано **Cloudflare Workers**. На сервері Cloudflare вже працює процес `workerd`, у якому завантажений
V8. Коли приходить запит до твого коду, `workerd` створює для нього ізолят у цьому готовому процесі. Твій код
називають **Worker**.

```text
  Контейнер у кластері                   Ізолят у Workers

  +----------------------+               +-----------------------------------+
  | твій код             |               | процес workerd (уже працює)       |
  | Python і бібліотеки  |               |                                   |
  | файли образу         |               |  +---------+ +---------+ +------+ |
  +----------------------+               |  | Worker  | | Worker  | | ...  | |
  | ядро Linux вузла     |               |  | клієнта | | клієнта | |      | |
  +----------------------+               |  | A       | | B       | |      | |
                                         |  +---------+ +---------+ +------+ |
  межа ізоляції: засоби ядра             |                                   |
                                         |  межа ізоляції: сам V8            |
                                         +-----------------------------------+
```

Звідси випливають цифри. Контейнеру треба отримати образ, створити простори імен, запустити інтерпретатор і
завантажити застосунок. Ізоляту все це не потрібно, бо інтерпретатор уже працює.

| Твердження | Звідки воно |
|------------|-------------|
| Ізолят запускається приблизно за 5 мс | стаття Cloudflare 2018 року |
| Node-функція без коду в Lambda займає 35 МБ, а ізолят близько 3 МБ, бо середовище виконання спільне | та сама стаття |
| Ізолят стартує приблизно у сто разів швидше за процес Node і споживає на порядок менше пам'яті | документація Cloudflare, сторінка `How Workers works` |
| Один екземпляр середовища виконує сотні або тисячі ізолятів | та сама сторінка |
| Один ізолят може використати не більше 128 МБ | документація Cloudflare, сторінка лімітів |

Курс пише «менше 5 мс» і «близько 3 МБ» як задокументовані сталі. Насправді це оцінки з давньої статті, а чинна
документація наводить лише порівняння «у сто разів» і «на порядок». Користуйся цими числами як порядком величини, а не
як точним значенням.

**Чому холодного старту майже не видно.** Холодний старт — це затримка першого запиту, коли коду ще немає в пам'яті.
Перед запитом клієнт встановлює захищене з'єднання TLS, а на цьому етапі він уже передає назву сайту. Cloudflare
бачить цю назву й завантажує потрібний Worker, поки з'єднання ще встановлюється. За даними Cloudflare, для адрес рівня
всього сайту завантаження закінчується раніше, ніж приходить сам запит.

**Де саме виконується код.** У Cloudflare є сотні майданчиків у різних містах, їх називають **точками присутності**
(англійською point of presence, PoP). Курс пише про 330+, а сторінка мережі Cloudflare зараз показує 348 міст. Одна
IP-адреса доступна з усіх цих майданчиків, і мережа веде запит до найближчого (такий спосіб називають anycast).
Команда `wrangler deploy` публікує код одразу в усій мережі, тому регіон вибирати не треба. Трилітерний код
майданчика, який обробив запит, лежить у `request.cf.colo`.

## Що зникає разом із контейнером

Простота має ціну, і таблиця нижче важливіша за цифри швидкості. Її третій стовпець відповідає на контрольне запитання
плану.

| У контейнері | У Worker | Що це означає для твого сервісу |
|--------------|----------|---------------------------------|
| Програма слухає порт | Немає порту: платформа викликає функцію `fetch` | `app.run(...)` і `PORT` з лабораторної 1 втрачають зміст |
| Будь-який виконуваний файл | За словами Cloudflare, ізолят не може виконати довільний скомпільований код; мова — JavaScript, TypeScript, Python або те, що компілюється у WebAssembly | Бібліотеки з нативним кодом можуть не запрацювати |
| Один довгоживучий процес | Ізолят може зникнути будь-якої миті, а запити можуть потрапляти до різних екземплярів | `START_TIME` і час роботи з лабораторної 1 більше нічого не вимірюють |
| Постійний том | Постійної файлової системи немає. Є лише віртуальна файлова система в пам'яті: каталог `/tmp` окремий для кожного запиту | Файл лічильника в `DATA_DIR` з лабораторної 12 не збережеться |
| Лічильники в пам'яті процесу | Пам'ять окрема в кожному ізоляті | `/metrics` із лабораторної 8 показував би випадкові частини справжніх чисел |
| Журнали йдуть у stdout, а їх забирає Alloy | Журнали видає сама платформа | Конфігурація Loki й Alloy з лабораторної 7 тут не працює |
| Процесор обмежуєш сам | 10 мс процесорного часу на запит у безплатному плані; у платному за замовчуванням 30 с, максимум 5 хв | Важка обробка не вкладеться в безплатний ліміт |

**Приклад: чому глобальна змінна не лічильник.** Припустімо, ти написав у Worker `let visits = 0` на верхньому рівні
файла й збільшуєш її під час кожного запиту. Локально вона зростає гарно: 1, 2, 3. У справжній мережі буває так:

| Запит | Де обробили | Значення у відповіді | Чому |
|-------|-------------|----------------------|------|
| 1 | Варшава, ізолят 1 | 1 | ізолят щойно створено |
| 2 | Варшава, ізолят 1 | 2 | ізолят ще живий |
| 3 | Франкфурт, ізолят 2 | 1 | маршрут змінився, а в цьому ізоляті своя змінна |
| 4 | Варшава, ізолят 3 | 1 | платформа прибрала ізолят 1 і створила новий |

Документація прямо радить не зберігати змінний стан у глобальній області. Стан має лежати в окремому сховищі, і про
нього далі.

Python не закритий повністю: є Python Workers, а документація наводить FastAPI як приклад підтримуваної залежності.
Проте бібліотеки мають бути суто на Python або мати збірку для WebAssembly, а сказане в таблиці про порт, стан і файли
лишається в силі. Лабораторна пропонує писати JavaScript.

## Як виглядає Worker

Ти вже знаєш цю модель із браузера: `Request` і `Response` у Worker — ті самі об'єкти, що й у `fetch` на фронтенді.
Лабораторна 17 дає таку форму (`labs/lab17.md`, завдання 1.3):

```javascript
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
```

Рядок за рядком:

1. `export default { ... }` — модуль віддає платформі один об'єкт. Сервера ти не створюєш і порт не відкриваєш.
2. `async fetch(request, env, ctx)` — платформа викликає цю функцію на кожен запит. `request` — вхідний запит, `env` —
   усе, що підключено до Worker ззовні, `ctx` дає службові можливості, наприклад `ctx.waitUntil`, що дозволяє
   завершити фонову роботу вже після відповіді (до 30 с).
3. `new URL(request.url)` — у `request.url` лежить повна адреса рядком, а `URL` розбирає її, щоб дістати шлях із
   `url.pathname`. Вбудованого маршрутизатора немає, тому маршрути ти перебираєш сам.

Ось приклад на іншому об'єкті, не з лабораторної: Worker віддає час і вітання з конфігурації.

```javascript
export default {
  async fetch(request, env) {
    const { pathname } = new URL(request.url);
    if (pathname === "/time") {
      return Response.json({ now: new Date().toISOString(), hello: env.GREETING });
    }
    return Response.json({ error: "not found" }, { status: 404 });
  },
};
```

`Response.json` сам ставить заголовок `Content-Type: application/json`. 

**Дата сумісності.** Конфігурація Worker містить поле `compatibility_date`. Це не дата випуску твого коду, а спосіб
сказати платформі: «поводься так, як поводилася на цю дату». Коли Cloudflare змінює поведінку середовища, нова
поведінка вмикається прапорцем із власною датою, а дата сумісності вмикає всі прапорці до себе включно. Старі дати
підтримуються завжди, тому твій код не зламається сам. Дата оновлюється лише тоді, коли ти сам її зміниш.

Це має прямий наслідок для цієї лабораторної. Починаючи з дати `2026-08-04`, сумісність із Node.js (`nodejs_compat`)
увімкнена за замовчуванням. Лабораторна радить поставити сьогоднішню дату й водночас каже, що `Buffer` і `process`
недоступні за замовчуванням. Для свіжої дати це вже неправда, тому в рефлексії пиши те, що побачив сам.

## Прив'язки: конфігурація, секрети, стан

**Прив'язка** (англійською binding) — це запис у конфігурації, завдяки якому в `env` з'являється готовий об'єкт:
значення чи клієнт до сховища. Рядків підключення, адрес і паролів у коді немає.

| Прив'язка | Що це | Узгодженість | Для чого |
|-----------|-------|--------------|----------|
| `vars` | Звичайний текст чи JSON у конфігурації | — | Назва застосунку, рівень журналу. Значення видно в конфігурації й на панелі керування, тому секрети сюди не кладуть |
| секрет | Зашифроване значення, яке після запису ніхто не може прочитати через `wrangler` чи панель | — | Токени, ключі |
| KV | Сховище «ключ — значення» | кінцева | Багато читань і рідкі записи: конфігурація, прапорці |
| D1 | База SQLite | усі записи йдуть на один основний екземпляр; копії для читання оновлюються асинхронно | Реляційні дані |
| R2 | Сховище файлів, сумісне з S3, без плати за вихідний трафік | сильна для кожного об'єкта | Файли, резервні копії |
| Durable Object | Особливий Worker зі своїм сховищем, має унікальну назву | сильна | Те, що треба координувати: чат, лічильник, обмеження частоти запитів |

**Кінцева узгодженість** (англійською eventual consistency) означає: після запису інші читачі рано чи пізно побачать
нове значення, але не обов'язково відразу. Документація KV каже, що в інших майданчиках зміна може з'явитися за 60
секунд або пізніше. Навіть у тому самому майданчику негайна видимість не гарантована.

**Чому лічильник у KV втрачає значення.** KV не має атомарного збільшення. Лічильник складається з двох окремих дій:
прочитати й записати. Нехай значення дорівнює 5, а два запити приходять майже одночасно.

| Крок | Хто діє | Що робить | Що в KV |
|------|---------|-----------|---------|
| 1 | Запит A, Варшава | читає `5` | 5 |
| 2 | Запит B, Франкфурт | читає `5` | 5 |
| 3 | Запит A | рахує 6 і записує | 6 |
| 4 | Запит B | рахує 6 і записує | 6 |
| 5 | Два відвідування сталися, а значення зросло на 1 | | 6 |

Є ще одне обмеження: не більше одного запису на секунду в той самий ключ, а в безплатному плані не більше 1000 записів
на день. Документація прямо каже, що KV не годиться там, де потрібні атомарні операції, і радить для цього Durable
Objects.

Отже, лічильник у лабораторній — навчальний приклад, щоб побачити сховище в дії. Три послідовні запити від однієї
людини покажуть очікуване значення, але це не робить KV правильним вибором для справжнього лічильника. Лекція й
лабораторна курсу пишуть, що KV годиться для лічильників. Вважай це спрощенням і скажи про це у своєму звіті.

## Два світи даних: локальний і справжній

Команда `wrangler dev` запускає твій код у процесі `workerd` на твоїй машині. Цей режим працює так із Wrangler 3, хоча
лабораторна приписує цю зміну четвертій версії. Четверта версія зробила інше: команди `wrangler kv key`,
`wrangler r2 object` та подібні теж стали за замовчуванням працювати локально, а до справжнього сховища їх веде
параметр `--remote`.

```text
          твоя машина                          мережа Cloudflare
  +---------------------------+            +---------------------------+
  | wrangler dev              |            | розгорнутий Worker        |
  |   KV: локальна копія      |            |   KV: справжній простір   |
  |   секрети: .dev.vars      |            |   секрети: secret put     |
  +---------------------------+            +---------------------------+
               ^                                        ^
               |                                        |
     wrangler kv key put                  wrangler kv key put --remote
```

Звідси типова розгубленість. Ти запускаєш `wrangler kv key put` без параметра, бачиш підтвердження, відкриваєш
розгорнутий Worker, а там старе значення. Обидва сховища справжні, але це два різні сховища. Те саме із секретами:
`wrangler secret put` працює лише для розгорнутого Worker, а локальний запуск читає файл `.dev.vars` або `.env`. Якщо
є `.dev.vars`, файл `.env` ігнорується. Обидва файли мають бути в `.gitignore`.

`request.cf` теж показує різне. Значення `colo` із локального запуску нічого не доводить, тому в лабораторній доказом
маршрутизації є лише відповідь справжньої мережі. Якщо ти під VPN, побачиш майданчик поруч із виходом VPN, а не поруч
із тобою.

## Версії й відкат

У Workers **версія** — це завантажений код разом із конфігурацією, а **розгортання** вказує, яка версія зараз
обслуговує запити. Це нагадує `Deployment` і `ReplicaSet` у кластері, але без подів.

Є дві неочікувані деталі:

1. `wrangler secret put` створює нову версію й одразу її розгортає. Отже, у списку розгортань будуть записи, у яких
   змінився лише секрет.
2. `wrangler rollback` без номера повертає версію, завантажену перед останньою. Якщо останньою дією був `secret put`,
   відкат поверне не той код, на який ти розраховував. Номер версії можна вказати явно.

Відкат не чіпає під'єднаних ресурсів. Лічильник у KV не повернеться назад, і старий код працюватиме з новими даними.
Якщо формат даних змінився, старий код може зламатися. Той самий ризик є в кластері: `kubectl rollout undo` не
відкочує базу даних.

## Як порівнювати, щоб цифри щось значили

Завдання 3.3 — головне в лабораторній. Воно просить таблицю з власними вимірами, і саме тут найлегше отримати
переконливі, але непорівнювані числа.

| Рядок таблиці | Що вимірює кластер | Що вимірює Worker | Чому ці числа не збігаються за змістом |
|---------------|--------------------|-------------------|---------------------------------------|
| Холодний старт | Від `Pending` до `Ready` і першої відповіді `200` | `time curl` | У k3d образ уже імпортовано, тому завантаження з реєстру немає. У `curl` до Worker входять DNS, TLS і шлях мережею, а сам холодний старт ти примусово викликати не можеш |
| Затримка | Запит із ноутбука до локального кластера | Запит із ноутбука до майданчика Cloudflare | Кластер на твоїй машині майже напевно виграє, бо мережі немає. Географію цей вимір не перевіряє |
| Пам'ять | `requests.memory`, тобто те, що ти попросив | Оцінка з документації | Одне — резервування, інше — чужа оцінка |
| Вартість | Вузол на місяць, навіть за нульового трафіку | Плата за запити й процесор | Для порівняння потрібні дві точки: нульовий трафік і конкретне навантаження |

Тому біля кожного числа запиши, чим і звідки його виміряно, а якщо воно не твоє, то звідки взято. 

**Приклад розрахунку вартості.** Нехай сервіс отримує 12 мільйонів запитів на місяць, і кожен витрачає 5 мс процесора.
Ціни взято зі сторінки тарифів Cloudflare.

| Складова | Включено в $5 | Твоє споживання | Понад включене | Доплата |
|----------|---------------|-----------------|----------------|---------|
| Запити | 10 млн | 12 млн | 2 млн | 2 × $0,30 = $0,60 |
| Процесор | 30 млн мс | 12 млн × 5 мс = 60 млн мс | 30 млн мс | 30 × $0,02 = $0,60 |
| Разом | | | | $5 + $0,60 + $0,60 = $6,20 |

Час очікування, наприклад відповіді зовнішнього сервера, не оплачується, бо рахують лише процесорний час. Плати за
вихідний трафік теж немає. Безплатний план дає 100 000 запитів на день, і після вичерпання запити отримують помилку
1027.

Лекція 16 курсу додає ще одне застереження: якщо база даних лежить в одному місці, кожен запит усе одно їде до неї, і
перевага близькості до користувача зникає.

## Порівняльна таблиця

| Питання | Кластер (лабораторні 9–16) | Workers (лабораторна 17) |
|---------|----------------------------|-------------------------|
| Стан | Томи, бази, будь-що | Лише прив'язки: KV, D1, R2, Durable Objects |
| Спостереження | Prometheus, Loki, Grafana, які ти налаштовуєш сам | Журнали й показники, які дає сама платформа |
| Залежність від постачальника | Маніфести переносяться на інший кластер | `env`, KV і `wrangler` існують лише тут |

Жоден стовпець не кращий загалом. Лабораторна радить спершу назвати навантаження, а вже потім вибирати середовище.

## Типові хибні уявлення

- **«Worker — це маленький контейнер».** Ні. Контейнер має власну файлову систему й може виконати будь-яку програму
  для свого ядра. Worker — це функція всередині спільного процесу, і межу безпеки тримає V8, а не ядро Linux.
- **«У Workers немає файлової системи».** Так казали давно. Зараз із сумісністю Node.js доступний модуль `node:fs` із
  віртуальною файловою системою в пам'яті. Але записане в `/tmp` існує лише в межах одного запиту, тож зберігати там
  нічого не можна. Точне формулювання: немає постійної файлової системи.
- **«Запит не може тривати довше 30 секунд».** Лабораторна пише так, але чинна сторінка лімітів каже інакше: для
  HTTP-запитів немає жорсткого обмеження на загальний час, поки клієнт не відключився. Обмежено процесорний час: 10 мс
  безплатно, до 5 хв у платному плані.
- **«Якщо локально все працює, то і в мережі теж».** Код виконує той самий `workerd`, але дані, секрети й `request.cf`
  інші. Глобальна змінна, яка локально рахує правильно, у мережі ламається.
- **«KV — це база даних, тільки швидка».** KV призначено для частих читань і рідких записів. Запис може бути не видно
  хвилину, а одночасні записи перетирають один одного.

## Практика

Це план роботи, а не відповідь на завдання. Перед кожним кроком запиши, що очікуєш побачити.

1. **Передбач таблицю.** До запуску заповни олівцем рядки таблиці 3.3 своїми припущеннями. Після вимірів порівняй: де
   ти помилився, там і було непорозуміння.
2. **Випиши, що зламається.** Перелічи всі особливості свого сервісу з лабораторних 1, 7, 8 і 12, які залежать від
   порту, файлів чи пам'яті процесу. Це готова відповідь на контрольне запитання.
3. **Перевір два світи.** Запиши значення в KV без параметра `--remote` і подивись, що покаже розгорнутий Worker.
   Поясни результат своїми словами.
4. **Запиши в журнал** один рядок: що виявилося не таким, як ти очікував.

Лабораторна дозволяє пройти без облікового запису Cloudflare, якщо докладно описати прогалину, але повні бали за
завдання 3 і бонус потребують справжнього розгортання. У деяких мережах служби Cloudflare обмежено; курс радить тоді
використовувати VPN у режимі повного тунелю, бо за часткового тунелю Node.js може йти повз нього.

## Перевір себе

**1. Що завадить тобі перенести свій сервіс на Workers без переписування?** Назви щонайменше п'ять причин, посилаючись
на власні лабораторні.

<details><summary>Відповідь</summary>

Запуск через порт (`app.run`, `PORT` з лабораторної 1) не має сенсу, бо платформа сама викликає `fetch`. `START_TIME`
і час роботи нічого не значать, бо ізолят не живе довго, а запити йдуть до різних екземплярів. Ім'я машини й дані
платформи з `/` теж втрачають зміст. Файл лічильника в `DATA_DIR` (лабораторна 12) не збережеться, треба інше сховище.
Лічильники `prometheus_client` у пам'яті (лабораторна 8) розпадуться на окремі ізоляти. Журнали в stdout для Alloy
(лабораторна 7) замінюються журналами платформи. Сам код на Flask чи FastAPI треба або переписати на JavaScript, або
переносити через Python Workers із їхніми обмеженнями. Dockerfile і чарт Helm тут узагалі не використовуються.

</details>

**2. Ти зробив три послідовні запити до `/counter` і отримав 1, 2, 3. Чи доводить це, що лічильник правильний?**

<details><summary>Відповідь</summary>

Ні. Це доводить лише, що читання й запис працюють за відсутності одночасних запитів. За двох одночасних запитів обидва
прочитають одне значення, і одне збільшення загубиться. Крім того, частіше ніж один запис за секунду в той самий ключ
обмежено, а зміна може стати видимою в інших майданчиках через хвилину.

</details>

**3. Ти виконав `wrangler kv key put` і бачиш успіх, але розгорнутий Worker показує старе значення. Що сталося?**

<details><summary>Відповідь</summary>

У Wrangler 4 команди сховищ за замовчуванням працюють із локальним сховищем. Значення потрапило в локальну копію, а
розгорнутий Worker читає справжній простір імен KV. Щоб писати в мережу, потрібен параметр `--remote`.

</details>

**4. Чому `wrangler rollback` може повернути не той код, якого ти чекав, і чи повернеться значення лічильника?**

<details><summary>Відповідь</summary>

Без номера відкат іде до версії, завантаженої перед останньою, а `wrangler secret put` теж створює версію. Отже,
«попередньою» може бути версія з тим самим кодом і іншим секретом. Лічильник не повернеться, бо відкат не змінює
під'єднаних ресурсів.

</details>

## Словничок лекції

| Термін | Що означає |
|--------|-----------|
| ізолят (isolate) | Відокремлена ділянка пам'яті V8 із власним станом всередині спільного процесу |
| `workerd` | Програма, що виконує Workers, і в мережі Cloudflare, і локально |
| холодний старт (cold start) | Затримка першого запиту, коли код ще не завантажено |
| прив'язка (binding) | Запис у конфігурації, завдяки якому в `env` з'являється значення чи клієнт сховища |
| кінцева узгодженість (eventual consistency) | Нове значення рано чи пізно побачать усі, але не обов'язково відразу |
| дата сумісності (compatibility date) | Дата, чию поведінку середовища ти закріплюєш за своїм Worker |
