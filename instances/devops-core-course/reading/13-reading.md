# Розбір читання до лабораторної 13

Цей файл пояснює, що саме написано в лекції 13 і лабораторній 13 курсу. [Лекція 13 цього
плану](../lectures/13-gitops.md) розповідає про саму тему, а цей розбір допомагає прочитати чужий текст: показує, де
що шукати, що означають незнайомі слова й де текст курсу не збігається з документацією.

Курс написано англійською, а в репозиторії курсу немає ліцензії. Тому розбір лише переказує своїми словами, а значень
`YOUR-TASK` не заповнює. У лабораторній 13 порожні місця позначено саме так, а не `___`. Читай у такому порядку:

1. лекцію 13 цього плану;
2. лекцію 13 курсу (близько 40 хвилин);
3. лабораторну 13 курсу, спершу цілком, а потім по завданнях.

### Слайди 1–2: вступ і результати навчання

Слайд 1 каже, де ми зупинилися: сервіс працює в кластері, а розгортає його людина командою `helm upgrade`. GitOps
переносить цю роль усередину кластера. Слайд 2 перелічує шість речей, які ти маєш уміти після лекції, і фіксує версії:
Argo CD 3.4 і Kubernetes 1.36.

Дати випусків збігаються з [графіком Argo
CD](https://argo-cd.readthedocs.io/en/stable/developer-guide/release-process-and-cadence/): версію 3.4 заплановано на
5 травня 2026 року, а версію 3.2 на листопад 2025 року. Підтримку отримують лише три найновіші мінорні версії, тому
вихід 3.2 справді завершив підтримку лінії 2.x. Зверни увагу, що зараз поточною стала лінія 3.5, а за графіком 3
листопада 2026 року має вийти 3.6. Тому сторінки документації зі словом `stable` описують новішу версію, ніж
лабораторна. Для 3.4 у адресі стоїть `release-3.4`.

### Слайд 3: чому pull кращий за push

Курс називає чотири причини: файл доступу до кластера в CI, дрейф після ручного `kubectl edit`, відсутність сліду змін
і складне відновлення. Перші три докладно пояснено в лекції плану. Вираз `Hot take` означає навмисно гостру думку
автора курсу: GitOps є не інструментом, а зміною напряму керування, бо кластер сам звертається до git.

Твердження, що до кластера ніхто не звертається ззовні, стосується самого розгортання. Вебінтерфейс і API Argo CD
існують, а вебхуки від git надходять саме до `argocd-server`, якщо ти їх налаштуєш.

### Слайд 4: чотири принципи OpenGitOps

Переказ принципів у курсі відповідає [сайту OpenGitOps](https://opengitops.dev/). Вираз `Litmus test` означає швидку
перевірку, але сформульовано її заплутано: курс питає, чи розійдеться кластер із git, якщо прибрати агента. Зміст
такий: якщо лише агент утримує кластер у стані з git, у тебе справді є постійна звірка, а без нього YAML у git лише
лежить як документ.

### Слайд 5: push і pull поруч

Таблиця порівняння збігається з таблицею в лекції плану. Рядок про дрейф каже «кожні 3 хвилини», але ця цифра
стосується опитування git, а не помічання змін у кластері. Рядок `What blocks deploy` нагадує про ціну: якщо git
недоступний, нове розгортання не відбудеться, хоча запущений сервіс далі працює.

### Слайд 6: інші інструменти

Таблиця називає Argo CD, Flux, Rancher Fleet, Codefresh і Jenkins X, а курс пояснює, чому вибрав Argo CD: він
поширений, має наочний вебінтерфейс і зручні ресурси `Application` та `ApplicationSet`. Запам'ятати варто лише Flux,
бо для нього є окремий сервер документації `flux-docs`.

### Слайд 7: будова Argo CD

Курс описує складові так само, як
[документація](https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/). Незнайомі вирази: `Stateless`
означає, що програма не зберігає власних даних, тому її копії взаємозамінні; `sharding` означає поділ роботи між
кількома копіями контролера; `OIDC broker` означає посередника для входу через зовнішню систему облікових записів.
Думка про Redis така: якщо втратити кеш, Argo CD обчислить усе заново, тобто працюватиме повільніше, але без помилок.

### Слайд 8: ресурс Application

Це той самий об'єкт, що в лекції плану. Курс підкреслює три речі: гілка рухається, а коміт є точною вказівкою; без
фіналізатора видалення `Application` лишає ресурси працювати; відсутність блока `automated` означає ручну
синхронізацію. Усі три твердження збігаються з документацією.

### Слайд 9: стани

Таблиці станів пояснює лекція плану. `Orthogonal` тут означає «незалежні одне від одного». Рядок `Unknown` курс
пояснює як недоступний репозиторій або ще не виконану перевірку. Твердження про новий фільтр у версії 3.4 тут не
перевірено, і для лабораторної він не потрібен.

### Слайд 10: політики синхронізації

Цей слайд важливий для завдання 3.

| Що написано в курсі | Що це означає |
|---------------------|---------------|
| `allowEmpty` | За замовчуванням автоматичне прибирання не залишить застосунок зовсім порожнім. Поле дозволяє такий результат |
| `ServerSideApply=true` | Argo CD застосовує зміни на боці сервера API й відстежує, яка програма якими полями керує. [Документація](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/) наводить такі причини: завеликий об'єкт для анотації або часткове змінення чужого об'єкта |
| `PruneLast=true` | Видалення виконується наприкінці, коли решта ресурсів уже здорова |
| `ApplyOutOfSyncOnly=true` | Застосовуються лише ресурси з розбіжностями |
| `retry` і `backoff` | Повтори після невдалої синхронізації зі зростанням паузи між ними |
| `orphan` у рядку про `prune` | Тут це ресурс, який зник із git, але лишився в кластері. У документації слово orphaned означає інше: ресурс, що не належить жодному застосунку |

Порада для prod збігається з логікою лабораторної: ручна синхронізація дає людині подивитися на зміну перед
застосуванням.

### Слайд 11: хвилі й хуки

Хвилі задають порядок анотацією: менші числа йдуть раніше. Хуки — це ресурси, зазвичай `Job`, які виконуються на
певному етапі. Курс правильно називає їхні види й політику `HookSucceeded`. Варто додати, що
[порядок визначається спершу фазою, потім хвилею](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-waves/).
Наприклад, застосунок із хуком `PreSync` спершу виконує хук, а вже потім хвилю `-1`.

### Слайд 12: застосунок застосунків

Задача слайда така: `Application` керує сервісами, а хто керує самими `Application`? Відповідь: ще один `Application`,
який вказує на теку з маніфестами. Слово `Bootstrap` означає початковий запуск системи, а `seed` — перший об'єкт, із
якого виростає решта. Завдання лабораторної цього не вимагають.

### Слайди 13–15: три сервіси, ApplicationSet, генератори

Слайд 13 пояснює, навіщо потрібен третій сервіс. Вираз `Pedagogical point` означає навчальну мету: на шести
застосунках із 3 × 2 користь від шаблону стає помітною. Твердження «менше трьох — іграшка» є оцінкою автора курсу, а
не обмеженням інструмента.

Приклад на слайді 14 показує матрицю двох списків. Зверни увагу на дрібницю: список середовищ задає ключ `autoSync`,
але шаблон нижче його не використовує, тому всі шість застосунків будуть з ручною синхронізацією. Це лише приклад
форми, а не повний розв'язок.

Таблиця на слайді 15 перелічує генератори:

| Генератор | Що він перебирає |
|-----------|------------------|
| List | записаний у файлі перелік |
| Cluster | кластери, зареєстровані в Argo CD |
| Git (Directory і File) | теки або файли в репозиторії |
| Matrix | усі поєднання двох інших генераторів |
| Merge | об'єднання результатів із перезаписом окремих значень |
| SCM Provider | репозиторії організації на GitHub чи GitLab |
| Pull Request | відкриті запити на злиття для тимчасових середовищ |
| Cluster Decision | кластери, які вибрала зовнішня логіка |
| Plugin | результат твого власного сервісу |

### Слайд 16: проєкти й права

`AppProject` обмежує застосунки: з яких репозиторіїв брати маніфести, у які простори імен класти й які види ресурсів
дозволено. `RBAC` означає доступ за ролями. Проєкт `default` дозволяє все. У лабораторній використовується саме він,
але в робочій системі так не роблять. Саме в налаштуваннях проєкту вмикають згадане в лекції плану попередження про
ресурси поза застосунками.

### Слайд 17: секрети

Таблиця зіставляє три підходи: Sealed Secrets (у git лежить зашифрований об'єкт), External Secrets Operator (у git
лежить посилання на значення в сховищі) і SOPS (у git лежать зашифровані файли, а Argo CD розшифровує їх під час
побудови маніфестів). Третій підхід [документація Argo CD не
радить](https://argo-cd.readthedocs.io/en/stable/operator-manual/secret-management/), бо Argo CD тоді отримує доступ
до секретів, а побудовані маніфести лежать у кеші Redis відкритим текстом. Курс цього застереження не дає.

### Слайд 18: кілька кластерів

Один Argo CD може керувати багатьма кластерами. Команда `argocd cluster add` створює `Secret` із даними для доступу.
`Hub-and-spoke` означає схему «центр і промені», а `federated` — окремий Argo CD у кожному кластері. Речення з виразом
`Argo CD Argocd in each cluster` містить помилку друку. Сама лабораторна в основних завданнях кілька кластерів
забороняє.

### Слайд 19: спостереження за самим Argo CD

Argo CD віддає метрики Prometheus, і слайд перелічує їхні назви та пороги сповіщень. Для лабораторної це
необов'язково, але пороги корисні: тривалий `OutOfSync` в автоматичному застосунку свідчить, що щось застрягло. Назву
кожної метрики перевіряй у документації, перш ніж писати за нею сповіщення.

### Слайд 20: відновлення після аварії

Послідовність така: новий кластер, встановлення Argo CD, застосування кореневого опису. Найважливіше в цьому слайді —
застереження в кінці: GitOps відновлює конфігурацію, а не стан. Дані томів і баз потребують власних резервних копій.

### Слайд 21: типові помилки

Цей слайд читай критично.

| Пункт курсу | Що з ним не так або що варто знати |
|-------------|------------------------------------|
| 1. `kubectl apply` у просторі імен Argo CD буде скасовано за 3 хвилини | Правда лише для ресурсів, які застосунок відстежує, причому зазвичай набагато швидше. Новий об'єкт, створений вручну, лишиться |
| 2. `prune: true` під час першого встановлення видаляє все, чого не бачить | Перебільшено. Прибирається лише відстежуване. На першому встановленні застосунок ще нічого не відстежує. Обережність потрібна пізніше, під час зміни `path` |
| 3. `HEAD` у prod | Правильно: версія змінюється разом із гілкою |
| 4. Секрети у відкритому вигляді в git | Правильно |
| 5. Один застосунок на все | Правильно: втрачається окремий стан і окрема синхронізація |
| 6. Код і маніфести разом | Це рекомендація курсу. Лабораторна для простоти тримає все в одній копії репозиторію |
| 7. Забутий фіналізатор | Правильно |
| 8. `selfHeal` разом із HPA | Правильно. Поле `ignoreDifferences` описує [документація](https://argo-cd.readthedocs.io/en/stable/user-guide/diffing/) |

### Слайди 22–24 і ресурси

Слайд 22 наводить історію та числа поширення: опитування CNCF і Codefresh. Ці числа тут не перевірено, і для
лабораторної вони не потрібні. Слайд 23 підсумовує лекцію. Слайд 24 переказує наступну тему (Argo Rollouts) і

## Лабораторна 13 курсу

**Де читати:** [`labs/lab13.md`](https://github.com/inno-devops-labs/DevOps-Core-Course/blob/master/labs/lab13.md).
Оцінка: 10 балів за основні завдання і 2 бонусні.

### Вступні розділи

**Overview** ставить мету: зробити git єдиним джерелом правди й перестати запускати `helm upgrade` з ноутбука.
Обмеження `Scope` забороняє Argo Rollouts, кілька кластерів і вхід через зовнішню систему, хоча бонусний варіант C
потім просить саме другий кластер. Вважай цей варіант окремим винятком.

**Project State** перелічує, що має бути готове: кластер k3d із попередніх лабораторних, чарт основного сервісу з
двома файлами значень і сервіс `echo`. Якщо план Kubernetes ще не пройдено, спершу виконай лабораторні 9 і 10 курсу,
бо без них немає що розгортати.

**The Three Services** зіставляє три сервіси. `app-python` є твоїм власним кодом і збирається у твоєму CI. `echo` і
`health` є готовими образами на портах 8081 і 8082, тому збирати їх заборонено: у чарті вказуй готовий образ.
Міні-чарти для них пишеш сам.

**Setup** просить перевірити кластер і підключити репозиторій чартів. Там же перелічено файли, які ти створиш: файл
значень, шість маніфестів `Application` і один маніфест `ApplicationSet`.

**Перевірка перед початком.** Курс здає роботу через гілку `lab13`, а приклади коду показують `main`. Твоя копія може
мати основну гілку `master`, бо запит на злиття в кінці лабораторної спрямовано саме туди. Argo CD читає лише те, що
вже відправлено у вказану гілку, тому чарт, який лежить лише локально або в іншій гілці, він не знайде. Спершу з'ясуй,
яку гілку читатимуть твої застосунки.

### Завдання 1. Встановлення Argo CD 3.4 (2 бали)

**Що вимагає.** Вибрати версію чарту `argo/argo-cd`, у якої поле `appVersion` належить до лінії 3.4. Написати власний
файл значень. Відкрити вебінтерфейс і встановити команду `argocd` тієї самої лінії.

**Незнайомі слова.**

| Вираз | Що це означає |
|-------|---------------|
| `chart version` і `appVersion` | Версія самого пакета чарту й версія програми в ньому. Вони нумеруються незалежно, і це різниця, яку треба описати у звіті |
| `server.service.type` | Як дістатися до `argocd-server`. За замовчуванням у чарті це `ClusterIP`, тобто лише зсередини кластера. Вибір обґрунтуй у звіті |
| `server.insecure` | Чи віддавати вебінтерфейс через звичайний HTTP замість HTTPS |
| `resources` | Запити й ліміти процесора та пам'яті. У чарті для контролера і `repoServer` вони порожні за замовчуванням |

**На чому спотикаються.**

- Команда `head -5` у вимогах до доказу покаже лише верхні рядки, а вгорі зараз стоять новіші версії: [основна гілка
  чарту](https://github.com/argoproj/argo-helm/blob/main/charts/argo-cd/Chart.yaml) вже містить лінію 3.5. Твій рядок
  3.4 може не потрапити в ці п'ять. Покажи у звіті рядок, який справді вибрав.
- Лабораторна згадує «попередній випуск 3.3.x», але версія 3.3 є звичайним випуском. Вимога лишається тією самою:
  потрібна саме лінія 3.4.
- Курс каже, що TLS завершується на `port-forward`. Це неточно: `kubectl port-forward` лише передає байти. Якщо сервер
  працює без TLS, з'єднання між твоєю командою й подом іде звичайним HTTP через цей тунель. Команда `argocd login`
  може вимагати окремих прапорців для такого сервера, дивись `argocd login --help`.
- Курс чекає щонайменше шість подів і каже, що Dex з'являється лише після ввімкнення. У значеннях чарту [`dex.enabled`
  за замовчуванням увімкнено](https://github.com/argoproj/argo-helm/blob/main/charts/argo-cd/values.yaml). Тому без
  зміни значень подів буде сім. Лабораторна не використовує входу через зовнішню систему, тому ти можеш вирішити, чи
  він потрібен.
- Початковий пароль лежить у `Secret` закодованим у base64, а отже, його треба розкодувати.
  [Документація](https://argo-cd.readthedocs.io/en/stable/getting_started/) також описує команду CLI для цього й
  радить видалити цей `Secret` після зміни пароля.

**Доказ.** Вивід пошуку чартів із вибраним рядком, список подів у стані `Running`, вивід `argocd version` з однаковою
лінією 3.4 у клієнта й сервера, повний файл значень, по одному реченню про обидва вибори.

### Завдання 2. Три застосунки dev (3 бали)

**Що вимагає.** Написати вручну три `Application` для dev без автоматичного режиму, виконати перше розгортання
командою й довести шлях від коміту до кластера.

**2.1–2.2.** Основний сервіс бере чарт із лабораторної 10. Для `echo` і `health` ти пишеш міні-чарти. Курс підказує,
що досить трьох файлів. Лабораторна лишає порожні назву, фіналізатор, адресу репозиторію, версію, теку, файли значень,
простір імен і опцію створення простору імен. Форму показує [приклад у лекції плану](../lectures/13-gitops.md), а
значення твої.

**2.3. Перше розгортання.** Курс каже, що без `automated` нічого не було звірено. Насправді звірка відбулась, і саме
тому ти бачиш `OutOfSync`. Не виконано лише синхронізацію. Для кожного застосунку запускаєш її вручну, і після цього
стан має стати `Synced` і `Healthy`.

**2.4. Шлях через git.** Зміни значення, закоміть, відправ і не запускай `kubectl apply`. Тут є дві пастки. Перша:
курс пропонує змінити значення у `values.yaml`, але значення накладаються шарами, і файл `values-dev.yaml` може
перекрити твою зміну. Тоді Argo CD нічого не побачить, бо результат побудови не змінився. Друга: кнопка `REFRESH` лише
прискорює звірку, а застосувати зміну мусиш синхронізацією, бо `automated` ще немає.

**Важлива підготовка до завдання 4.** У версії 3 Argo CD відстежує ресурси через анотацію й [більше не додає
мітку](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/upgrading/2.14-3.0/)
`app.kubernetes.io/instance`. Завдання 4.4 вибирає ресурси саме цією міткою. Тому в міні-чартах її маєш записати сам.
Назва релізу Helm за замовчуванням [дорівнює назві
`Application`](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/), тому значення збігатиметься з назвою
застосунку.

Міні-чарти варто перевірити за портами: `echo` слухає 8081, `health` слухає 8082, а обидва мають шлях `/healthz` для
проб.

**Доказ.** Три маніфести, таблиця трьох застосунків зі станом `Synced` і `Healthy`, шість ресурсів у просторі імен
`dev`, хеш коміту й історія застосунку, де видно синхронізацію цього коміту.

### Завдання 3. Dev автоматично, prod вручну (3 бали)

**Що вимагає.** Для кожного чарту зробити два файли значень, які справді відрізняються щонайменше двома параметрами.
Перевести dev в автоматичний режим. Додати три застосунки prod без блока `automated`, які вказують на тег або гілку
випуску.

**Незнайомі слова.** `image tag pin` означає запис точного тега образу, а `release/*` — гілки випуску. `delta` означає
різницю між файлами значень.

**На чому спотикаються.**

- Тег для prod має вказувати на коміт, де вже є всі чарти й файли `values-prod.yaml`. Якщо створити тег раніше, Argo
  CD не знайде теки чи файла й покаже помилку.
- Курс називає `ServerSideApply` обов'язковим для співіснування з HPA. Документація цього не стверджує. У лабораторній
  опцію вимагає сама форма завдання, а HPA тут немає.
- Застосунки prod лишаються `OutOfSync`, доки ти не запустиш синхронізацію. Це їхня правильна поведінка, а не помилка.

**Письмова частина 3.3.** Курс прямо каже, що справжня навичка тут — вибір політики. Потрібно 4–6 речень про три речі:

1. Чому `prune` і `selfHeal` прийнятні для dev, але ризиковані для prod. Подумай про ціну помилки й про те, що зміна
   застосовується без перегляду людиною.
2. Чому `targetRevision` на основну гілку зводить нанівець процес випуску.
3. Що станеться, якщо ввімкнути `prune` із хибним `path`, і як від цього захиститися. Пиши точно. Неіснуюча тека дасть
   помилку й нічого не видалить, а інша непорожня тека призведе до видалення всього відстежуваного зі старої. Порожній
   результат зупиняє запобіжник, якщо його не вимкнено через `allowEmpty`.

**Доказ.** Таблиця відмінностей між dev і prod, шість маніфестів, шість рядків зі станом `Synced` і `Healthy`,
письмова частина.

### Завдання 4. ApplicationSet (2 бали)

**Що вимагає.** Замінити шість файлів одним `ApplicationSet` із матрицею двох списків. Довести самовідновлення двома
сценаріями.

**4.2. Вибір шляху для різної політики.** Лабораторна пропонує два шляхи, і курс тут потребує уточнення.

- **Шлях (a), Go-шаблони.** Коментар у скелеті показує умову прямо в `template`. Так зробити не вийде, бо [шаблони
  діють лише на окремі рядкові
  поля](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/GoTemplate/), а умовну структуру
  пишуть у [`templatePatch`](https://argo-cd.readthedocs.io/en/release-3.4/operator-manual/applicationset/Template/).
  Як воно працює, показано в лекції плану на іншому полі. Документація цієї сторінки містить приклад, близький до
  твоєї задачі, тому прочитай його.
- **Шлях (b), два `ApplicationSet`.** Без умов, але критерії прийняття говорять про один `ApplicationSet` і про шість
  рядків від `all-apps`, хоча окремий рядок критеріїв дозволяє і два. Якщо вибереш цей шлях, поясни його у звіті.

Інші деталі:

- Запис заповнювача залежить від рушія: `{{svc}}` у fasttemplate і `{{.svc}}` у Go-шаблонах.
- Значення `"true"` і `"false"` у списку є рядками, тому порівнюй їх через `eq`. Непорожній рядок у виразі `if` завжди
  істинний.
- Різну версію для dev і prod зручно задати ключем у списку середовищ. Цю пораду дає сама лабораторна.
- Розділ типових проблем каже шукати помилки шаблонів у журналі `controller`. Шукай у журналі
  `argocd-applicationset-controller`, бо шаблони обробляє саме він.

**4.3. Заміна файлів.** Спершу застосовуєш `ApplicationSet`, переконуєшся, що застосунків рівно шість, а потім
прибираєш шість файлів через `git rm`. Врахуй дві речі:

- Застосунки створено командою `kubectl apply`, тому видалення файлів із git саме по собі нічого в кластері не змінює.
- Курс каже, що Argo CD відмовиться взяти застосунок із такою самою назвою і його треба спершу видалити. У [коді
  контролера](https://github.com/argoproj/argo-cd/blob/master/applicationset/controllers/applicationset_controller.go)
  наявний запис перезаписується, а `ApplicationSet` стає його власником, і відмови для запису без власника там немає.
  Видалення ж запису з фіналізатором [прибере й сам
  сервіс](https://argo-cd.readthedocs.io/en/stable/user-guide/app_deletion/), а застосунок prod після цього чекатиме
  ручної синхронізації. Тому спершу застосуй `ApplicationSet` і подивись поле `ownerReferences` у запису. Видаляй щось
  лише тоді, коли ти справді побачив відмову.

**4.4. Самовідновлення.** Курс просить два сценарії.

1. **Видалити `Deployment`.** Вибір за міткою спрацює, лише якщо чарт її записує, як сказано вище. Контролер помітить
   зміну й відновить об'єкт, зазвичай швидше ніж за три хвилини. Кнопка `REFRESH` зазвичай не знадобиться, а час
   зафіксуй.
2. **Змінити мітку.** Команда в лабораторній додає нову мітку `owner`. Як пояснено в [лекції
   плану](../lectures/13-gitops.md), нову мітку, якої чарт не задає, стандартне порівняння, найімовірніше, не
   побачить, тому `OutOfSync` може й не з'явитися. Спершу подивись `argocd app diff`. Якщо різниці немає, запиши це у
   звіт як окреме спостереження, а для доказу змін значення мітки, яку записує сам чарт у `metadata.labels` цього
   `Deployment`. Мітки в `spec.selector` не чіпай.

У письмовій частині поясни різницю двох рівнів. Самовідновлення Kubernetes означає, що `ReplicaSet` створює новий под
замість зниклого. Самовідновлення Argo CD означає, що контролер повертає об'єкт до опису в git. Жоден із них не
виправить падіння через зламаний образ, якщо цей образ описано в git.

**Доказ.** Повний `applicationset.yaml`, примітка про вибраний шлях, шість рядків зі станом `Synced` і `Healthy`,
обидва сценарії із часом, одне речення про різницю двох рівнів.

### Бонус: один із трьох варіантів (2 бали)

**Варіант A. Сповіщення.** Потрібно налаштувати у `argocd-notifications-cm` тригер, шаблон і службу вебхука, а
застосунок [підписати анотацією](https://argo-cd.readthedocs.io/en/stable/operator-manual/notifications/). Контролер
сповіщень у чарті ввімкнено за замовчуванням. Адреса вебхука має бути досяжна з кластера. Анотацію на застосунку,
створеному через `ApplicationSet`, став у шаблоні, бо контролер `ApplicationSet` приводить анотації до шаблону. Збій
можна викликати неіснуючим тегом образу.

**Варіант B. Хвилі й хук.** Порядок: `Namespace` і `ConfigMap` у хвилі `-1`, `Deployment` у хвилі 0, `Service` у хвилі
1, а `Job` як хук `PreSync` з автоматичним видаленням після успіху. Подумай про три речі. Фаза важливіша за хвилю,
тому хук виконається раніше, ніж з'явиться `Namespace` із хвилі `-1`. `Job` після видалення не покаже журналів, а
критерії просять саме їх, тому знімай журнал під час виконання. `Namespace` у git означає, що його прибирання разом із
`prune` видалить усе в ньому.

**Варіант C. Другий кластер.** Другий кластер k3d реєструється в Argo CD, а `ApplicationSet` із генератором Cluster
розгортає лише `health` на кластери з міткою. Є пастка: [вибір за міткою не збігається з локальним
кластером](https://argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Generators-Cluster/), бо він за
замовчуванням не має `Secret`. Тому «два кластери × один сервіс» вийде лише за окремого налаштування. Контролер у
подах також має дістатися адреси API другого кластера, а адреса з твого файлу kubeconfig на ноутбуці може бути
недосяжною зсередини контейнера. Перевір це першим.

Для будь-якого варіанта потрібні абзац про рішення, опис зміни й один справжній доказ із командного рядка.

### Здача, критерії й типові проблеми

**How to Submit.** Гілка `lab13`, тека `k8s/argocd/` і звіт `docs/LAB13.md`, два запити на злиття: у репозиторій курсу
й у власну копію. **Acceptance Criteria** і **Rubric** повторюють завдання. Вони корисні як контрольний перелік перед
здачею.

**Common Pitfalls.** Цей розділ варто прочитати, але частина пунктів неточна.

| Пункт курсу | Оцінка |
|-------------|--------|
| `install.yaml` не застосовується з першого разу | Для шляху через Helm неважливо. [Документація](https://argo-cd.readthedocs.io/en/stable/getting_started/) пояснює потребу в `--server-side` інакше: деякі CRD завеликі для анотації |
| **`prune` видаляє застосований вручну `Secret`** | **Неправильно.** Argo CD не відстежує створені вручну ресурси, тому `prune` їх не чіпає й не позначає для видалення. Секрет зникне, лише якщо мав анотацію відстеження, тобто раніше надійшов із git, або лежав у видаленому просторі імен. Порада тримати секрети поза git через лабораторну 11 лишається правильною, але з іншої причини: у новому кластері секрета, створеного вручну, не буде |
| `selfHeal` приховує справжні помилки | Правильно за змістом. Виправлення має бути в git. Число «кожні 3 хвилини» є лише верхньою межею, а реакція зазвичай швидша |
| Права доступу до приватного репозиторію | За змістом правильно. Назва `argocd-repo-creds` лише приклад: [`Secret` визначається міткою](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/) `argocd.argoproj.io/secret-type` |
| fasttemplate і `goTemplate` | Правильно щодо різниці записів. Умову над `syncPolicy` пиши в `templatePatch` |
| Забутий фіналізатор | Правильно |
| `targetRevision: main` на prod | Правильно |

**Tools worth knowing.** Команди `argocd app diff` і `argocd app history` знадобляться одразу. Перша показує різницю
перед синхронізацією, друга показує докази для завдання 2. Команда `rollback` [не працює за ввімкненого автоматичного
режиму](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/), тому в dev відкат означає новий коміт.

**Looking Ahead.** Лабораторна 14 замінить `Deployment` на `Rollout`, лабораторна 15 додасть `StatefulSet`,
лабораторна 16 збиратиме метрики `health` і `echo`. Тому не викидай міні-чарти після здачі.

**Що ще врахувати щодо версій.** Лабораторна поєднує Argo CD 3.4 із Kubernetes 1.36, а [таблиця перевірених
версій](https://argo-cd.readthedocs.io/en/stable/operator-manual/tested-kubernetes-versions/) для 3.4 закінчується на
1.35. Вимогу лабораторної щодо 3.4 виконуй, але пам'ятай про це, якщо бачиш незрозумілу поведінку.

## Сервіс health у plumbing

**Де читати:**
[`plumbing/health/`](https://github.com/inno-devops-labs/DevOps-Core-Course/tree/master/plumbing/health). Це близько
80 рядків мовою Go в `main.go`, короткий `README.md` і `Dockerfile`. Редагувати нічого не треба. Читай лише заради
того, щоб правильно написати міні-чарт.

| Шлях | Що повертає | Для чого тобі |
|------|-------------|---------------|
| `GET /` | JSON зі службою, версією, назвою хоста й лічильником запитів | Побачити, який под відповів |
| `GET /healthz` | `ok` із кодом 200 | Проби готовності й життєздатності |
| `GET /metrics` | Лічильник запитів і час роботи у форматі Prometheus | Знадобиться в лабораторній 16 |

Порт і версія беруться зі змінних середовища, а якщо їх не задано, діють значення за замовчуванням:

```go
port := os.Getenv("PORT")
if port == "" {
	port = "8082"
}
```

Перший рядок читає змінну середовища так само, як `process.env.PORT` у JavaScript, але в Go відсутня змінна дає
порожній рядок, а не `undefined`. Тому код порівнює значення з `""`. Отже, якщо в міні-чарті ти задаси змінну `PORT`,
той самий номер мусить бути в `containerPort` і в пробах.

`Dockerfile` збирає програму на основі `golang:1.24`, а запускає на мінімальному образі
`distroless/static-debian12:nonroot`. Такий образ не має оболонки, тому `kubectl exec ... sh` у цьому поді не спрацює.
Програма запускається від імені користувача без прав адміністратора, тому образ не конфліктуватиме з налаштуваннями
безпеки пода, які забороняють root.
