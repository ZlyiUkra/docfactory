# Docker — план вивчення

План для того, хто пройшов план Linux цієї лінії (або вже впевнено адмініструє машину Linux) і хоче пакувати й
запускати застосунки в контейнерах так, як це роблять у продакшні. Ціль — не «вміти `docker run`», а самому
зробити образ, за який не соромно: маленький, без root, з перевіркою стану, що збирається за хвилину з кешу під дві
архітектури, публікується з CI разом із переліком залежностей і запускається в `compose` з базою, мережею, томами й
секретами, — і розуміти, що при цьому відбувається на машині.

Це другий план лінії віртуалізації застосунків: Linux → Docker → Kubernetes. З плану Linux ви знаєте, що контейнер —
процес у просторах імен з лімітами cgroups і коренем на overlayfs (фаза 7 там). Тут — інструмент, який збирає це за
вас, і вся практика навколо нього. Kubernetes наступного плану запускає ті самі образи, тож усе, що тут про образи,
сигнали, перевірки стану й ліміти, перейде туди без змін.

**Обов'язкового сертифіката для Docker немає.** Сертифікат Docker Certified Associate (DCA) існує, його видає
Mirantis, але в лінію він не входить. Місце Docker у лінії — між факультативним LFCS і обов'язковими CKAD та CKA: CKAD
питає образи й контейнери як уже відомі (розділ програми «Application Design and Build»: визначити, зібрати й
змінити образ контейнера). Дні, на які спирається CKAD, позначено **[CKAD]**.

Лінія незалежна від родини React → NestJS → Next.js. Дотик один: фулстек-плани теж збирають образи й запускають
`compose`; хто пройшов цей план, ті дні проходить швидше.

Усього — сорок два навчальні дні по півтори-дві години. П'ять днів на тиждень дають близько двох місяців.

## Порядок трьох планів

| Етап | План | Сертифікат | Що виходить наприкінці |
|------|------|------------|------------------------|
| 1 | Linux | LFCS — факультатив | дві власні машини (Ubuntu і Rocky Linux), налаштовані з нуля; контейнер, зібраний руками з namespaces і cgroups |
| 2 | Docker — цей план | — | образи власного застосунку, `compose` з базою й секретами, збірка під amd64 і arm64 з CI, реєстр, SBOM |
| 3 | Kubernetes | CKAD, потім CKA — обов'язково | застосунок у кластері; далі — сам кластер: kubeadm, оновлення, резервні копії etcd, мережа й сховища |

## З чого почати

**Машина.** Головна машина `ubu` з плану Linux (Ubuntu Server 24.04). Docker Engine ставиться на неї з офіційного
репозиторію Docker, а не з пакета Ubuntu `docker.io`: у дистрибутиві версія старіша, а документація описує
офіційну. Для фази 4 потрібна друга архітектура — її дає емуляція QEMU на тій самій машині. Docker Desktop не
потрібен: план вчить рушій, а не настільний застосунок.

**Наскрізний проєкт.** Один застосунок на три частини, який росте через усі фази: статичний фронт за nginx, API на
мові, яку ви знаєте (Node.js, Python чи Go), і PostgreSQL. Підійде будь-що з записами в базі: нотатки, список задач.
Свій код із фулстек-планів годиться так само. До кінця плану в нього з'являться Dockerfile на кожну частину,
`compose.yaml` для розробки й для продакшну, конвеєр CI, що публікує образи в GitHub Container Registry (GHCR), і
сторінка в README «як це запустити з нуля».

**Який сервер документації запустити.** З кореня фабрики: `./df docker serve`. Корпус — документація
docs.docker.com, нотатки релізів Engine 27–29 і релізи moby, compose та buildx; назви глав у плані (у `такому
вигляді`) — назви документів корпусу. Документація сайту має лише поточну версію; версії продуктів — у нотатках
релізів («Engine 29» — `version: "29"`).

**Репозиторій.** Той самий `infra-notes`, що в плані Linux, тека `docker/`, або репозиторій самого застосунку з
текою `deploy/`. У README — відповіді на контрольні питання, журнал вимірів (розмір образу, час збірки з кешем і
без) і чекбокси днів `- [ ] Ф0 Д1. Встановлення`.

## Як користуватися планом

У кожного дня сім рядків — як у плані Linux: **Навіщо**, **Що це**, **Читати**, **Сервери MCP**, **Зробити**,
**Перевірити себе**, **Пастка**. День — одиниця умовна; небезпечний не пропущений день, а пропущена вправа.

**Сервери MCP.** Імена — як у Claude Code: сервер примірника `x` зветься `x-docs` (`react-docs`, `mdn-docs`,
`webstandards-docs`). Під заголовком кожної фази — усі сервери фази разом: їх варто підняти до її початку (`./df
<примірник> serve` з кореня фабрики) і додати в Claude Code командою з README примірника. Сервер відповідає з тих
самих глав, що названі в рядку «Читати», і дає адресу джерела, за якою відповідь можна перевірити. «Жодного» — джерела
дня поза фабрикою; чого бракує — у [карті навчання](../../docs/learning-map.md).

**Журнал вимірів.** З фази 1 у README живе таблиця: дата, що змінили, розмір образу (`docker image ls`), час
холодної збірки і збірки з кешем, кількість шарів. Кожна вправа-замір дає число в таблицю. «Образ став менший» без
числа — враження.

## Словник

- **Образ (image).** Незмінний набір шарів файлової системи плюс конфігурація запуску (команда, змінні, користувач,
  порти). Те, з чого створюють контейнер. Шари спільні між образами: базовий образ на диску лежить один раз.
- **Контейнер.** Запущений (або зупинений) екземпляр образу: процес у власних просторах імен з верхнім шаром для
  записів. Видалили контейнер — зник і цей шар.
- **Реєстр і репозиторій.** Реєстр — сервер образів (Docker Hub, GHCR). Репозиторій — набір версій одного образу в
  ньому (`ghcr.io/ви/api`). Тег (`:1.4.0`) — рухома мітка, дайджест (`@sha256:…`) — незмінний відбиток.
- **Dockerfile.** Рецепт образу: кожна інструкція (`FROM`, `RUN`, `COPY`) дає крок збірки, а більшість — шар.
- **Контекст збірки.** Файли, які клієнт передає збирачеві: усе, що доступне `COPY`. `.dockerignore` його звужує.
- **BuildKit і buildx.** BuildKit — сучасний збирач образів (типовий давно); buildx — команда `docker buildx`, що
  керує ним: кілька архітектур, кеш у реєстрі, віддалені збирачі.
- **Том (volume) і bind-монтування.** Том — тека, якою керує Docker і яка переживає контейнер; bind — тека
  господаря, змонтована всередину. Перший — для даних, другий — для коду під час розробки.
- **Мережа bridge.** Типова мережа контейнерів: програмний міст на господарі (фаза 5 плану Linux) з NAT назовні.
  У власній мережі контейнери знаходять одне одного за іменем.
- **Публікація порту.** Правило DNAT, яке Docker пише в брандмауер господаря: порт машини веде в порт контейнера.
- **Compose.** Опис кількох контейнерів, їхніх мереж і томів одним файлом `compose.yaml` і команда `docker compose`,
  що піднімає їх разом.
- **Healthcheck.** Команда, якою Docker перевіряє, чи застосунок у контейнері справді працює, а не просто процес
  живий.
- **SBOM і attestation.** SBOM — перелік усього, що всередині образу (пакети й версії); attestation — підписане
  твердження про образ (SBOM, походження збірки), що лежить поруч із ним у реєстрі.

## П'ять пасток, які переживають будь-який рівень

- **`latest` — не версія.** Тег рухається; сьогоднішній `postgres:latest` завтра інший. У продакшні — конкретний тег
  або дайджест.
- **Опублікований порт обходить ufw.** Docker пише свої правила раніше за правила ufw, і `-p 5432:5432` відкриває
  базу всьому інтернету, хоч `ufw status` каже «deny». Публікуйте на `127.0.0.1:` або не публікуйте зовсім (фаза 2,
  день 4).
- **Дані в контейнері зникають.** Усе, що записано не в том, зникає разом із контейнером. База без тому живе до
  першого `docker compose down`.
- **Секрет у шарі лишається назавжди.** `COPY .env` чи `ARG TOKEN` — і секрет у шарах образу, навіть якщо наступна
  інструкція його видалила. Для секретів збірки — `--secret`, для запуску — змінні чи файли секретів.
- **PID 1 не отримує сигнал.** Shell-форма `CMD npm start` робить PID 1 оболонку, яка не передає `SIGTERM`
  застосунку: `docker stop` чекає 10 секунд і вбиває. Exec-форма `CMD ["node", "server.js"]` — і застосунок
  завершується чисто.

# Фаза 0. Робоче місце й перший контейнер — 5 днів

**Сервери MCP фази:** `docker-docs`.

### День 1. Встановлення

- **Навіщо.** Рушій з офіційного репозиторію — те, що описує документація і що стоїть на серверах.
- **Що це.** Docker Engine — служба `dockerd` плюс клієнт `docker` і плагіни `buildx` та `compose`. Ставиться з
  репозиторію Docker (ключ у `/etc/apt/keyrings/`, джерело з `signed-by` — фаза 3, день 6 плану Linux). Після
  встановлення — група `docker` (дає права root на машині — свідомо!), автозапуск служби, перевірка.
- **Читати:** `Install Docker Engine on Ubuntu`; `Linux post-installation steps for Docker Engine`; `Docker
  Engine`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) видалити пакети `docker.io` і `containerd`, якщо стоять; 2) поставити Engine, `buildx` і
  `compose` з репозиторію Docker; 3) додати себе в групу `docker` і зрозуміти, що це означає; 4) `docker run
  hello-world`.
- **Перевірити себе:** `docker version` показує Engine 29.x на клієнті й сервері; `docker info` — `Storage Driver`
  чи `containerd image store`; `systemctl is-enabled docker` — `enabled`.
- **Пастка:** вважати групу `docker` безпечною заміною sudo. Хто в ній, той root: `docker run -v /:/host` дає повний
  доступ до файлової системи господаря.

### День 2. Образ, контейнер, реєстр

- **Навіщо.** Три слова, на яких тримається решта плану. Без чіткої різниці між ними команди плутаються.
- **Що це.** `docker pull` бере образ з реєстру, `docker run` створює з образу контейнер і запускає його, `docker ps
  -a` — контейнери, зокрема зупинені, `docker image ls` — образи. Ім'я образу — `реєстр/репозиторій:тег`; без
  реєстру — Docker Hub, без тегу — `latest`.
- **Читати:** `What is a container?`; `What is an image?`; `What is a registry?`; `docker container run`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) запустити `nginx` у фоні з іменем і портом; 2) запустити ще два контейнери з того самого образу —
  подивитися, скільки місця займають образ і контейнери (`docker system df`); 3) зупинити, запустити знову,
  видалити; 4) знайти образ за дайджестом і запустити саме його.
- **Перевірити себе:** `docker ps -a` порожній після кроку 3, а образ лишився; ви пояснюєте, чому три контейнери
  одного образу майже не займають місця.
- **Пастка:** `docker run` замість `docker start` для зупиненого контейнера — щоразу новий контейнер, і десятки
  мертвих лежать у `docker ps -a`. `--rm` для разових запусків.

### День 3. Життя контейнера

- **Навіщо.** Діагностика контейнера — щоденна робота: подивитися журнал, зайти всередину, з'ясувати, чому він
  перезапускається.
- **Що це.** `docker logs -f`, `docker exec -it контейнер sh`, `docker inspect` (усе про контейнер у JSON, `--format`
  для одного поля), `docker stats`, `docker top`, `docker cp`. Стани: created, running, paused, exited; код виходу —
  у `inspect`. Контейнер живе, поки живе його PID 1.
- **Читати:** `Running containers`; `View container logs`; `docker container exec`; `docker inspect`; `Format command
  and log output`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) контейнер, що завершується з кодом 3, — знайти код і останні рядки журналу; 2) зайти в nginx і
  змінити сторінку; 3) знайти PID контейнера на господарі й порівняти з `ps` всередині (зв'язок з фазою 7 плану
  Linux); 4) вивести IP-адреси всіх контейнерів одним `docker inspect --format`.
- **Перевірити себе:** `docker inspect -f '{{.State.ExitCode}}' контейнер` — 3; PID на господарі — звичайний процес у
  `ps -ef`.
- **Пастка:** правити файли всередині контейнера й вважати це налаштуванням. Новий контейнер з того самого образу —
  без ваших правок; зміни — в образ або в том.

### День 4. Змінні, команди й точки входу

- **Навіщо.** Той самий образ має запускатися в різних середовищах з різними налаштуваннями — без перезбирання.
- **Що це.** `-e КЛЮЧ=значення` і `--env-file`; `CMD` — типова команда, яку перекриває хвіст `docker run`;
  `ENTRYPOINT` — постійна частина, до якої хвіст дописується аргументами (`--entrypoint` перекриває). Exec-форма
  (JSON-масив) проти shell-форми — від неї залежить, хто PID 1.
- **Читати:** `Set environment variables within your container's environment`; у `Dockerfile reference` — розділи
  про `CMD`, `ENTRYPOINT` і їхню взаємодію (таблиця «Understand how CMD and ENTRYPOINT interact»).
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) запустити `postgres` з паролем і базою через змінні; 2) перекрити команду образу `alpine` хвостом
  `run`; 3) з'ясувати `ENTRYPOINT` і `CMD` образу `postgres` через `inspect` і пояснити, як вони складаються.
- **Перевірити себе:** `docker exec` у postgres і `psql -U користувач -d база -c 'select 1'` — 1.
- **Пастка:** пароль у `-e` видно в `docker inspect` і в історії оболонки. Для справжніх секретів — файли (фаза 3,
  день 6).

### День 5. Прибирання й місце на диску

- **Навіщо.** Docker на сервері тихо з'їдає диск: старі образи, кеш збірки, мертві контейнери, томи без власника.
- **Що це.** `docker system df` — хто скільки займає; `docker container prune`, `image prune` (`-a` — і невживані,
  не лише безіменні), `volume prune`, `builder prune`, `system prune`. Журнали контейнерів за замовчуванням ростуть
  без меж (фаза 5).
- **Читати:** `docker system df`; `docker system prune`; `docker image prune`; `Build garbage collection`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) набрати мотлоху (кілька збірок, зупинені контейнери, том) і подивитися `system df -v`;
  2) прибрати все, крім томів; 3) налаштувати автоматичне прибирання кешу збірки за розміром.
- **Перевірити себе:** `docker system df` після кроку 2 — RECLAIMABLE близько нуля для образів і контейнерів.
- **Пастка:** `docker system prune --volumes` на сервері з базою в іменованому томі без контейнера в цю мить — і бази
  більше немає. Томи прибирають лише руками й поіменно.

# Фаза 1. Образи й Dockerfile — 9 днів

**Сервери MCP фази:** `docker-docs`.

Головна фаза плану й головне, що з Docker питає CKAD: зібрати образ, змінити його, зробити маленьким і безпечним.

### День 1. Перший Dockerfile [CKAD]

- **Навіщо.** Образ власного застосунку — перший крок до будь-якого розгортання.
- **Що це.** `FROM` — база, `WORKDIR`, `COPY`, `RUN` — команда під час збирання, `ENV`, `EXPOSE` (лише документація
  порту), `USER`, `CMD`. `docker build -t ім'я:тег .` — `.` тут контекст збірки, а не місце Dockerfile.
- **Читати:** `Dockerfile overview`; `Writing a Dockerfile`; `Build, tag, and publish an image`; `docker buildx
  build` (вона стоїть за `docker build`).
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) Dockerfile для API наскрізного проєкту в один етап; 2) зібрати, запустити, відкрити в браузері;
  3) записати в журнал розмір образу й час збірки.
- **Перевірити себе:** `curl localhost:порт/health` відповідає з контейнера; рядок у журналі вимірів.
- **Пастка:** `COPY . .` першою інструкцією після `FROM` — будь-яка зміна коду ламає кеш установлення залежностей
  (день 3).

### День 2. Контекст і `.dockerignore`

- **Навіщо.** Контекст — усе, що бачить збирач. Без `.dockerignore` у нього летять `node_modules`, `.git` і `.env` —
  повільно й небезпечно.
- **Що це.** Клієнт передає контекст збирачеві перед збиранням; `COPY` бачить лише його. `.dockerignore` — шаблони
  того, що не передавати. Контекстом може бути й віддалений репозиторій git чи архів.
- **Читати:** `Build context`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) покласти в теку проєкту `.env` з «секретом» і переконатися, що `COPY . .` заносить його в образ
  (`docker run … cat .env`); 2) `.dockerignore`, після якого `.env`, `.git` і залежності не потрапляють у контекст;
  3) порівняти розмір контексту в виводі збирача до й після.
- **Перевірити себе:** `docker run --rm образ ls -a` не показує `.env` і `.git`.
- **Пастка:** вважати `.dockerignore` захистом від секретів у будь-якому разі — він не допоможе, якщо секрет
  копіюється явним `COPY .env .` або лежить у теці, яку ви копіюєте цілком.

### День 3. Шари й кеш [CKAD]

- **Навіщо.** Збірка за 10 секунд замість 3 хвилин — порядок інструкцій, а не потужніший сервер.
- **Що це.** Кожна інструкція — крок із ключем кешу; зміна кроку інвалідує всі наступні. Тому спершу копіюють лише
  файли залежностей (`package.json`, `package-lock.json`), ставлять залежності, а вже потім — код. `RUN
  --mount=type=cache` тримає кеш менеджера пакетів між збірками. `docker image history` показує шари й розміри.
- **Читати:** `Understanding the image layers`; `Docker build cache`; `Build cache invalidation`; `Optimize cache
  usage in builds`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) переставити інструкції так, щоб зміна коду не перевстановлювала залежності; 2) кеш менеджера
  пакетів через `--mount=type=cache`; 3) виміряти збірку після зміни одного файла коду — до й після.
- **Перевірити себе:** у виводі збірки після зміни коду крок встановлення залежностей — `CACHED`; час — у журналі.
- **Пастка:** `RUN apt-get update` окремим кроком від `apt-get install` — кешований `update` місяцями тримає старий
  перелік пакетів. В одному `RUN`, разом.

### День 4. Багатоетапна збірка [CKAD]

- **Навіщо.** Компілятор, dev-залежності й вихідний код не потрібні в образі, який працює в продакшні.
- **Що це.** Кілька `FROM … AS етап` в одному Dockerfile: етап збирання ставить усе й компілює, фінальний етап
  копіює лише результат (`COPY --from=build`). `--target` збирає лише до вказаного етапу — зручно для тестів.
- **Читати:** `Multi-stage builds`; `Building best practices` — розділ про багатоетапну збірку.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) фронт: етап збирання на Node, фінальний — `nginx` зі статикою; 2) API: етап збирання й фінальний
  етап лише з production-залежностями; 3) етап `test` і `docker build --target test`.
- **Перевірити себе:** розмір фінального образу фронту — десятки мегабайт, а не сотні; цифри до й після — у журналі.
- **Пастка:** копіювати у фінальний етап усю теку збирання — разом із dev-залежностями повертається все, від чого
  тікали.

### День 5. База образу

- **Навіщо.** База — більша частина розміру й більша частина вразливостей образу.
- **Що це.** Повні образи дистрибутивів (`debian`, `ubuntu`), «slim»-варіанти, `alpine` (musl замість glibc —
  бувають несумісності), distroless і Docker Hardened Images (лише застосунок і рантайм, без оболонки), `scratch`
  (нічого — для статичних бінарників). Офіційні образи Docker Hub і закріплення бази дайджестом.
- **Читати:** `Base images`; `Docker Official Images`; `Building best practices` — розділ про вибір бази.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) зібрати API на трьох базах (повна, slim, alpine або distroless) і записати розміри; 2) закріпити
  базу дайджестом; 3) для distroless — пояснити, як тепер налагоджувати без оболонки (окремий етап з
  оболонкою через `--target`, або сусідній контейнер у тих самих просторах: `docker run -it --pid container:api
  --network container:api busybox`).
- **Перевірити себе:** три рядки в журналі вимірів; `FROM` з `@sha256:`.
- **Пастка:** `alpine` для застосунку з нативними модулями під glibc — збирається, а падає під час запуску з
  загадковою помилкою завантажувача.

### День 6. Користувач, сигнали, healthcheck [CKAD]

- **Навіщо.** Три речі, які відрізняють «працює в мене» від образу для продакшну — і які Kubernetes перевірить.
- **Що це.** `USER` — не root: процес усередині з UID 0 — root і на господарі, якщо контейнер втече. Exec-форма
  `CMD` — щоб застосунок отримав `SIGTERM` і завершився чисто; `--init` чи `tini` — коли застосунок сам не збирає
  зомбі. `HEALTHCHECK` — команда перевірки стану з інтервалом і кількістю спроб; стан видно в `docker ps`.
- **Читати:** у `Dockerfile reference` — розділи `USER`, `HEALTHCHECK`, `STOPSIGNAL`; `Run multiple processes in a
  container` — чому один процес на контейнер.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) API від користувача з UID 10001; 2) застосунок, що на `SIGTERM` закриває з'єднання й пише в журнал
  «shutdown»; 3) `HEALTHCHECK` на `/health`; 4) порівняти час `docker stop` для shell- і exec-форми `CMD`.
- **Перевірити себе:** `docker exec api id` — не 0; `docker ps` — `(healthy)`; `docker stop api` — менше секунди й
  рядок «shutdown» у журналі.
- **Пастка:** `HEALTHCHECK` з `curl`, якого в мінімальному образі немає, — контейнер вічно `unhealthy`, хоч
  застосунок здоровий.

### День 7. Аргументи, змінні й секрети збірки

- **Навіщо.** Одна збірка — різні версії, і жодного токена в шарах.
- **Що це.** `ARG` — параметр збірки (`--build-arg`), видимий лише під час збирання; `ENV` — змінна, що лишається в
  образі. Секрет збірки (`RUN --mount=type=secret`) — файл, доступний одному кроку й не записаний у шар; SSH-агент
  (`--mount=type=ssh`) — для приватних репозиторіїв. Перевірки збірки (`docker build --check`) ловлять секрети в
  `ARG` і `ENV`.
- **Читати:** `Build variables`; `Build secrets`; `Build checks`; `SecretsUsedInArgOrEnv`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) версія застосунку через `ARG` у мітку образу й змінну; 2) приватний реєстр пакетів з токеном через
  `--secret`; 3) спершу «погано» — через `ARG` — і знайти токен у `docker image history`; 4) `docker build --check`.
- **Перевірити себе:** `docker image history --no-trunc` правильного образу не містить токена; `--check` без
  попереджень.
- **Пастка:** `ARG` вважається безпечним, бо «не лишається в образі». Значення `ARG`, використане в `RUN`, видно в
  історії шарів.

### День 8. Мітки й метадані

- **Навіщо.** Через пів року треба знати, з якого коміту зібрано образ, що крутиться в продакшні.
- **Що це.** `LABEL` і стандартні анотації OCI (`org.opencontainers.image.source`, `.revision`, `.version`);
  `docker inspect` і `buildx imagetools inspect` їх показують; GHCR за міткою `source` прив'язує образ до
  репозиторію.
- **Читати:** `Docker object labels`; `Annotations`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** мітки OCI з версією й комітом (через `ARG` з дня 7) на всіх трьох образах проєкту.
- **Перевірити себе:** `docker inspect -f '{{json .Config.Labels}}' api` — коміт, версія, джерело.
- **Пастка:** мітка з датою збірки «зараз» робить кожну збірку унікальною — і ламає відтворюваність і кеш шару з
  міткою.

### День 9. Найкращі практики разом

- **Навіщо.** Підсумок фази: образи проєкту, які не соромно показати на співбесіді.
- **Що це.** Перелік з `Building best practices` як чек-лист: мінімальна база, багатоетапна збірка, `.dockerignore`,
  кеш, один процес, не root, закріплені версії, `HEALTHCHECK`, без секретів у шарах.
- **Читати:** `Building best practices` повністю.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** пройти чек-лист по трьох образах проєкту і виправити все, що не так; у журнал — розміри й час
  збірки «на початку фази» і «тепер».
- **Перевірити себе:** `docker build --check` по всіх трьох — чисто; таблиця «до і після».
- **Пастка:** `RUN chmod -R` чи `chown -R` окремим кроком — копія всіх файлів у новому шарі, і образ удвічі
  більший. `COPY --chown` / `--chmod` одразу.

# Фаза 2. Дані й мережа — 6 днів

**Сервери MCP фази:** `docker-docs`.

### День 1. Томи

- **Навіщо.** База, завантажені файли, черги — усе, що має пережити контейнер.
- **Що це.** Іменований том (`-v pgdata:/var/lib/postgresql/data` чи `--mount type=volume`) — живе окремо від
  контейнера, ним керує Docker (`docker volume ls`, `inspect`). Резервна копія тому — через тимчасовий контейнер з
  `tar`. Нові томи заповнюються вмістом теки образу.
- **Читати:** `Volumes`; `docker volume create`; `docker volume inspect`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) PostgreSQL з іменованим томом; записати дані, видалити контейнер, підняти новий — дані на місці;
  2) резервна копія тому в архів і відновлення в новий том; 3) з'ясувати, де том лежить на диску господаря.
- **Перевірити себе:** дані пережили видалення контейнера; з відновленого тому база стартує з тими самими рядками.
- **Пастка:** `docker run --rm` з базою і анонімним томом — `--rm` видаляє і анонімний том разом із контейнером.

### День 2. Bind-монтування і tmpfs

- **Навіщо.** Код під час розробки — з диска господаря, без перезбирання; тимчасові файли — у пам'ять.
- **Що це.** Bind (`-v $(pwd)/src:/app/src` чи `--mount type=bind`) — тека господаря всередині, з правами
  господаря; `:ro` — лише читання. tmpfs — тека в пам'яті, зникає з контейнером. Права файлів bind: UID усередині і
  зовні ті самі числа.
- **Читати:** `Bind mounts`; `tmpfs mounts`; `Sharing local files with containers`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) API в режимі розробки з кодом через bind і автоперезапуском; 2) конфіг nginx через bind `:ro`;
  3) контейнер з UID 10001 пише в bind-теку, що належить вашому користувачу, — отримати відмову і виправити правами
  теки, а не root-ом.
- **Перевірити себе:** зміна файла на господарі видна в застосунку без перезбирання; запис у `:ro` — «Read-only file
  system».
- **Пастка:** bind поверх теки, де образ тримав залежності (`/app` цілком), — вони зникають під теками господаря, і
  застосунок не знаходить модулі.

### День 3. Мережі

- **Навіщо.** Контейнери проєкту мають бачити одне одного за іменем і не бачити чужих.
- **Що це.** Типова мережа `bridge` — без DNS за іменами; власна мережа bridge (`docker network create`) — з
  вбудованим DNS: контейнер `db` доступний як `db`. Драйвери: `host` (мережа господаря, без ізоляції), `none`,
  `macvlan`/`ipvlan` (адреса в мережі господаря), `overlay` (Swarm). Контейнер може бути в кількох мережах.
- **Читати:** `Networking overview`; `Bridge network driver`; `Network drivers`; `Host network driver`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) мережа `app`, у ній `db` і `api`; API підключається до бази за іменем `db`; 2) контейнер у
  типовій мережі не бачить `db` за іменем; 3) знайти міст мережі `app` на господарі (`ip link`, `bridge link`).
- **Перевірити себе:** `docker exec api getent hosts db` повертає адресу; з контейнера поза мережею — нічого.
- **Пастка:** підключатися між контейнерами за IP з `docker inspect` — після перезапуску адреса інша. Лише імена.

### День 4. Порти й брандмауер

- **Навіщо.** Найчастіша діра в безпеці Docker: опублікований порт, якого ніхто не збирався відкривати.
- **Що це.** `-p 8080:80` пише правило DNAT у netfilter господаря — у власні ланцюги Docker, які спрацьовують раніше
  за правила ufw чи firewalld. `-p 127.0.0.1:8080:80` — лише локально. Власні обмеження — в ланцюг `DOCKER-USER`.
  У Engine 29 є і бекенд nftables, але він експериментальний.
- **Читати:** `Port publishing and mapping`; `Packet filtering and firewalls`; `Docker with iptables`; `Docker with
  nftables`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) `ufw default deny incoming`, опублікувати `-p 5432:5432` і з машини `rocky` підключитися до бази;
  2) переопублікувати на `127.0.0.1`; 3) правило в `DOCKER-USER`, що пускає порт лише з `10.10.0.0/24`; 4) знайти
  правило DNAT Docker у `nft list ruleset`.
- **Перевірити себе:** після кроку 2 з `rocky` — тайм-аут; з `ubu` — підключення є.
- **Пастка:** вимкнути керування брандмауером Docker (`"iptables": false`), щоб «ufw працював», — і контейнери
  втрачають вихід в інтернет та публікацію портів. Правильний шлях — `127.0.0.1` і `DOCKER-USER`.

### День 5. IPv6 і DNS

- **Навіщо.** Сервер з IPv6 і контейнери без нього — частий сюрприз; DNS усередині контейнера — частий підозрюваний.
- **Що це.** Мережа з `--ipv6` і підмережею; контейнери отримують адреси IPv6. DNS контейнера у власній мережі —
  вбудований сервер Docker (`127.0.0.11`), що пересилає зовнішні імена на DNS господаря; `--dns` перекриває.
- **Читати:** `Use IPv6 networking`; у `Networking overview` — розділ про DNS.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) мережа з IPv6 (`fd00:20::/64`), пінг між контейнерами по IPv6; 2) подивитися `/etc/resolv.conf` у
  контейнері типової й власної мережі і пояснити різницю.
- **Перевірити себе:** `docker exec api ping -6 -c1 db` — відповідь.
- **Пастка:** в Ubuntu `/etc/resolv.conf` господаря вказує на `127.0.0.53` (фаза 5 плану Linux) — контейнер у типовій
  мережі не може до нього достукатися, і Docker підставляє справжні сервери. Ручне копіювання resolv.conf ламає це.

### День 6. Обмеження ресурсів

- **Навіщо.** Один контейнер не має права з'їсти всю пам'ять машини. Те саме, що `resources.limits` у Kubernetes.
- **Що це.** `--memory`, `--memory-reservation`, `--cpus`, `--pids-limit` — під капотом cgroup v2 (фаза 7 плану
  Linux). Перевищення пам'яті — OOM-kill усередині контейнера; `docker inspect` покаже `OOMKilled: true`.
  `docker update` змінює ліміти на ходу.
- **Читати:** `Resource constraints`; `docker container update`; `Runtime metrics`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) API з `--memory 256m --cpus 0.5`; 2) навантажити пам'ять і дочекатися OOM; 3) знайти cgroup
  контейнера на господарі й порівняти `memory.max` з лімітом.
- **Перевірити себе:** `docker inspect -f '{{.State.OOMKilled}}' api` — `true`; `memory.max` — 268435456.
- **Пастка:** ліміт пам'яті без розуміння рантайму: JVM чи Node зі старих версій не бачать ліміту cgroup і
  розганяють купу понад нього — OOM без помилки в журналі застосунку.

# Фаза 3. Compose — 7 днів

**Сервери MCP фази:** `docker-docs`.

Увесь проєкт однією командою. Compose — і щоденний інструмент розробки, і цілком придатний спосіб запуску на
одній машині.

### День 1. Перший compose.yaml

- **Навіщо.** Три контейнери, мережа й том — руками це десять команд і їхній порядок; у Compose — один файл.
- **Що це.** `compose.yaml`: `services` (образ або `build`, порти, змінні, томи), `networks`, `volumes`. `docker
  compose up -d`, `ps`, `logs -f`, `down` (без `-v` томи лишаються). Ім'я проєкту — ім'я теки або `-p`; від нього
  залежать імена контейнерів, мереж і томів. Мережа проєкту створюється сама, і сервіси бачать одне одного за
  іменами.
- **Читати:** `What is Docker Compose?`; `How Compose works`; `Compose file reference`; `Define services in Docker
  Compose`; `docker compose up`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** `compose.yaml` наскрізного проєкту: `web`, `api`, `db` з томом; `api` збирається з Dockerfile фази 1.
- **Перевірити себе:** `docker compose up -d` з нуля піднімає все; сторінка відкривається й читає дані з бази;
  `docker compose down && docker compose up -d` — дані на місці.
- **Пастка:** старий формат з `version: "3.8"` і команда `docker-compose` через дефіс — це Compose v1, якого давно
  немає. Поле `version` сучасний Compose ігнорує, а команда — `docker compose`.

### День 2. Порядок запуску й перевірки стану

- **Навіщо.** API стартує раніше за базу й падає — класика першого `compose up`.
- **Що це.** `depends_on` лише впорядковує запуск; з `condition: service_healthy` — чекає, доки залежність стане
  здоровою за своїм `healthcheck`. `service_completed_successfully` — для одноразових задач (міграції). `restart:` —
  політика перезапуску.
- **Читати:** `Control startup and shutdown order in Compose`; у `Compose file reference` — `healthcheck`,
  `depends_on`, `restart`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) `healthcheck` для `db` (`pg_isready`) і `api`; 2) `api` чекає здорову базу; 3) сервіс `migrate`,
  що запускає міграції й завершується, а `api` чекає його успішного кінця.
- **Перевірити себе:** `docker compose up` з нуля стартує без жодного перезапуску `api`; `docker compose ps` —
  усі `healthy`, `migrate` — `exited (0)`.
- **Пастка:** `depends_on` без умови вважається очікуванням готовності — він чекає лише запуску контейнера, а не
  того, що база приймає з'єднання.

### День 3. Змінні й інтерполяція

- **Навіщо.** Один `compose.yaml` для розробки, тестів і сервера — різниця лише в змінних.
- **Що це.** `${VAR}` і `${VAR:-типове}` в файлі підставляються з оточення й файла `.env` поруч; `environment:` і
  `env_file:` передають змінні в контейнер — це дві різні речі. Порядок пріоритетів змінних. `docker compose config`
  показує файл після підстановок.
- **Читати:** `Environment variables in Compose`; `Set, use, and manage variables in a Compose file with
  interpolation`; `Environment variables precedence in Docker Compose`; `Best practices for working with
  environment variables in Docker Compose`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) тег образів і порт — через змінні з типовими значеннями; 2) `.env` для розробки, не в git;
  3) з'ясувати через `docker compose config`, яке значення перемогло, коли змінна задана і в оболонці, і в `.env`.
- **Перевірити себе:** `TAG=1.2.3 docker compose config | grep image` показує 1.2.3.
- **Пастка:** вважати, що `.env` поруч із `compose.yaml` потрапляє в контейнери. Він лише для підстановок у файлі;
  у контейнер змінна йде через `environment` чи `env_file`.

### День 4. Розробка: watch, профілі, кілька файлів

- **Навіщо.** Зручна розробка без ручних перезапусків і без копії файла на кожне середовище.
- **Що це.** `develop.watch` + `docker compose watch` — синхронізація файлів у контейнер чи перезбирання при змінах;
  `profiles` — сервіси, що піднімаються лише на прохання (адмінка бази, засоби налагодження); кілька файлів
  (`-f compose.yaml -f compose.prod.yaml`) зливаються; `include` — підключити чужий compose-файл.
- **Читати:** `Use Compose Watch`; `Using profiles with Compose`; `Merge Compose files`; `Use multiple Compose files`;
  `Include`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) watch для API: зміна коду синхронізується, зміна залежностей — перезбирає; 2) профіль `tools` з
  pgAdmin; 3) `compose.prod.yaml`, що прибирає bind-монтування й публікацію бази.
- **Перевірити себе:** `docker compose -f compose.yaml -f compose.prod.yaml config` — без bind і без порту бази.
- **Пастка:** у злитті файлів списки (`ports`, `volumes`) додаються, а не замінюються — прибрати опублікований порт
  другим файлом звичайним записом не вийде (`!reset`/`!override`).

### День 5. Мережі й томи в Compose

- **Навіщо.** Фронт не повинен бачити базу; дані бази — в іменованому томі з передбачуваним іменем.
- **Що це.** Кілька мереж: `front` (web і api) і `back` (api і db), `internal: true` — без виходу назовні. Томи
  проєкту, зовнішні томи (`external: true`), що переживають `down -v`.
- **Читати:** `Networking in Compose`; `Define and manage networks in Docker Compose`; `Define and manage volumes in
  Docker Compose`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) розділити мережі так, щоб `web` не мав маршруту до `db`; 2) мережа `back` — internal; 3) том бази —
  external, створений руками.
- **Перевірити себе:** `docker compose exec web getent hosts db` — нічого; `docker compose down -v` не чіпає
  зовнішній том.
- **Пастка:** `docker compose down -v` на сервері — видаляє томи проєкту, тобто базу. На сервері — без `-v`, а
  справжні дані — у зовнішньому томі.

### День 6. Секрети

- **Навіщо.** Пароль бази не повинен бути видимим у `docker inspect`, журналі збирання чи змінних процесу.
- **Що це.** `secrets:` верхнього рівня (з файла чи змінної оточення) і `secrets:` сервісу — файл у
  `/run/secrets/ім'я`. Офіційні образи (postgres) читають `*_FILE`-змінні; свій застосунок читає файл сам.
- **Читати:** `Manage secrets securely in Docker Compose`; `Secrets` (у довіднику Compose).
- **Сервери MCP:** `docker-docs`.
- **Зробити:** пароль бази — секретом з файла, `POSTGRES_PASSWORD_FILE` для бази і читання файла в API.
- **Перевірити себе:** `docker inspect` контейнерів не містить пароля; `docker compose exec api cat
  /run/secrets/db_password` — є.
- **Пастка:** файл секрету в git. Секрети — поза репозиторієм (або зашифровані — SOPS у плані Kubernetes).

### День 7. Compose на сервері

- **Навіщо.** Для невеликого проєкту одна машина з Compose — цілком чесний продакшн, і саме так ви деплоїте до
  Kubernetes.
- **Що це.** Окремий продакшн-файл: образи з реєстру за тегом (без `build`), `restart: unless-stopped`, ліміти
  ресурсів (`deploy.resources`), журнали з ротацією, без bind-монтувань коду; оновлення — `docker compose pull && up
  -d`. Docker-контекст дає керувати віддаленою машиною зі свого терміналу по SSH.
- **Читати:** `Use Compose in production`; `Docker contexts`; у `Compose Deploy Specification` — `resources`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) контекст `rocky` по SSH; 2) підняти проєкт на `rocky` з вашого терміналу продакшн-файлом;
  3) оновити один сервіс на новий тег без простою інших.
- **Перевірити себе:** `docker --context rocky compose ps` — усе `healthy`; після оновлення — новий тег в `docker
  compose images`.
- **Пастка:** `docker compose up -d` на сервері з `build:` у файлі — збирання на продакшн-машині, різні образи на
  різних серверах. Сервер лише тягне готові образи.

# Фаза 4. Кілька архітектур, реєстри, CI, ланцюг постачання — 6 днів

**Сервери MCP фази:** `docker-docs`.

### День 1. Реєстр і теги

- **Навіщо.** Образ, якого немає в реєстрі, не потрапить на сервер і в кластер.
- **Що це.** `docker login`, `docker tag`, `docker push`. Docker Hub (ліміти завантажень для анонімних і безкоштовних
  користувачів), GHCR (`ghcr.io/власник/образ`, токен GitHub з правом пакетів). Схема тегів: версія semver,
  короткий коміт, `latest` лише як зручність. Дайджест — незмінний.
- **Читати:** `Build, tag, and publish an image`; `Docker Hub usage and limits`; `Docker Hub pull usage and limits`;
  `docker image push`; `docker login`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) опублікувати три образи проєкту в GHCR з тегами версії й коміту; 2) на `rocky` стягнути образ за
  дайджестом; 3) з'ясувати свій поточний ліміт завантажень Docker Hub.
- **Перевірити себе:** `docker buildx imagetools inspect ghcr.io/…/api:1.0.0` — той самий дайджест, що локально.
- **Пастка:** пароль облікового запису замість токена доступу в `docker login` на сервері — і він лежить відкритим
  текстом у `~/.docker/config.json`.

### День 2. Збірка під кілька архітектур

- **Навіщо.** Сервери на ARM (Graviton, Ampere — зокрема безкоштовна машина Oracle) дешевші; образ лише під amd64 на
  них не запуститься.
- **Що це.** Образ для кількох платформ — індекс (manifest list) з образом під кожну архітектуру. `docker buildx
  build --platform linux/amd64,linux/arm64 --push`. Чужу архітектуру будують через емуляцію QEMU (повільно) або
  крос-компіляцією в етапі збирання (`BUILDPLATFORM`, `TARGETPLATFORM`). Будівник `docker-container` потрібен для
  кількох платформ, якщо не ввімкнено containerd image store.
- **Читати:** `Multi-platform builds`; `Builders`; `Build drivers`; `Docker container driver`; `docker buildx
  create`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) емуляція QEMU на `ubu` і збірка API під обидві платформи; 2) порівняти час з крос-компіляцією для
  Go чи з нативною збіркою залежностей; 3) запустити arm64-образ на amd64 машині через емуляцію.
- **Перевірити себе:** `docker buildx imagetools inspect` показує дві платформи; `docker run --platform
  linux/arm64 … uname -m` — `aarch64`.
- **Пастка:** `RUN npm install` з нативними модулями під емуляцією триває в десять разів довше й часом падає;
  такі кроки виносять у крос-збірку чи на нативного збирача.

### День 3. Кеш збірки поза машиною

- **Навіщо.** У CI кожна збірка починається на чистій машині — без зовнішнього кешу це щоразу холодна збірка.
- **Що це.** Бекенди кешу: `inline` (у самому образі), `registry` (окремий образ кешу), `gha` (кеш GitHub Actions),
  `local`. `--cache-to type=registry,ref=…,mode=max` зберігає і проміжні етапи.
- **Читати:** `Cache storage backends`; `Registry cache`; `GitHub Actions cache`; `Inline cache`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** збірка з `--cache-from` і `--cache-to` у реєстр; виміряти другу збірку на чистому будівнику.
- **Перевірити себе:** друга збірка з порожнього будівника бере шари з кешу реєстру — число в журналі.
- **Пастка:** `mode=min` (типовий) не кешує проміжні етапи багатоетапної збірки — кеш є, а встановлення
  залежностей щоразу заново.

### День 4. CI на GitHub Actions

- **Навіщо.** Образи для продакшну збирає не ноутбук, а конвеєр — однаково щоразу й з історією.
- **Що це.** Офіційні дії Docker: `setup-qemu`, `setup-buildx`, `login`, `metadata` (теги й мітки з git),
  `build-push`.
  Збірка на кожен PR (без публікації), публікація — на тег.
- **Читати:** `Introduction to GitHub Actions with Docker`; `Docker Build GitHub Actions`; `Manage tags and labels
  with GitHub Actions`; `Multi-platform image with GitHub Actions`; `Cache management with GitHub Actions`; `Test
  before push with GitHub Actions`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** workflow: на PR — збірка й тести без публікації; на тег `v*` — образи під дві платформи з тегами з
  `metadata` у GHCR, кеш `gha`.
- **Перевірити себе:** тег `v1.1.0` у репозиторії дає образи `1.1.0`, `1.1` і `sha-…` у GHCR під дві платформи.
- **Пастка:** токен із правом запису в пакети, доступний workflow з PR з форків. Публікація — лише на тег і лише з
  власного репозиторію.

### День 5. SBOM і походження

- **Навіщо.** Питання «чи є в нас вразлива версія openssl» має відповідатися за хвилину, без розбирання образів.
- **Що це.** Attestations: SBOM (перелік пакетів образу) і provenance (як і з чого зібрано), що лежать у реєстрі
  поруч з образом. `--sbom=true --provenance=mode=max`. Сканування образу на вразливості — Docker Scout чи Trivy.
- **Читати:** `Build attestations`; `SBOM attestations`; `Provenance attestations`; `Add SBOM and provenance
  attestations with GitHub Actions`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) SBOM і provenance в CI; 2) прочитати SBOM з реєстру через `imagetools inspect --format`;
  3) просканувати образ і виправити хоч одну вразливість зміною бази.
- **Перевірити себе:** `docker buildx imagetools inspect ghcr.io/…/api:1.1.0 --format '{{json .SBOM}}'` повертає
  перелік пакетів.
- **Пастка:** сканувати лише в момент збирання. Нові CVE з'являються щодня для старих образів — сканування за
  розкладом.

### День 6. Відтворювані збірки й політики

- **Навіщо.** Та сама ревізія коду — той самий образ: інакше незрозуміло, що саме перевіряли тести.
- **Що це.** Закріплені бази (дайджест), закріплені залежності (lock-файли), `SOURCE_DATE_EPOCH` для часу у файлах;
  політики збирання buildx — перевірки, що база з довіреного джерела.
- **Читати:** `Reproducible builds with GitHub Actions`; `Introduction to build policies`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** зібрати той самий коміт двічі з різницею в годину і порівняти дайджести; домогтися однакових.
- **Перевірити себе:** два однакові дайджести в журналі.
- **Пастка:** `apt-get install` без версій у Dockerfile — дві збірки одного коміту в різні дні дають різні образи.

# Фаза 5. Експлуатація й безпека рушія — 6 днів

**Сервери MCP фази:** `docker-docs`.

### День 1. Налаштування рушія

- **Навіщо.** Типові налаштування `dockerd` годяться для ноутбука; на сервері — журнали без меж і мережі, що
  перетинаються з офісними.
- **Що це.** `/etc/docker/daemon.json`: `log-driver` і `log-opts` (ротація), `default-address-pools` (діапазони
  мереж), `live-restore`, `features`, `registry-mirrors`. Після зміни — перезапуск служби. Проксі для рушія —
  через `systemctl edit docker` (фаза 3 плану Linux).
- **Читати:** `Docker daemon configuration overview`; `dockerd` (довідник опцій); `Daemon proxy configuration`;
  `Live restore`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) `daemon.json` з ротацією журналів, власним пулом адрес і `live-restore`; 2) перезапустити `docker`
  і переконатися, що контейнери пережили перезапуск рушія.
- **Перевірити себе:** `docker info` показує ваш драйвер журналів і `Live Restore Enabled: true`.
- **Пастка:** синтаксична помилка в `daemon.json` — рушій не стартує взагалі. Перед перезапуском —
  `dockerd --validate --config-file /etc/docker/daemon.json`.

### День 2. Журнали

- **Навіщо.** Журнал контейнера без ротації — найчастіша причина повного диска на сервері з Docker.
- **Що це.** Драйвери: `json-file` (типовий, без меж!), `local` (стиснений, з ротацією), `journald` (у журнал
  systemd — фаза 3 плану Linux), віддалені (fluentd, syslog, хмарні). `docker logs` працює з `local`, `json-file` і
  `journald`.
- **Читати:** `Configure logging drivers`; `Local file logging driver`; `JSON File logging driver`; `Journald logging
  driver`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) переключити рушій на `local` з лімітом; 2) один контейнер — у `journald`, знайти його записи через
  `journalctl CONTAINER_NAME=…`; 3) переконатися, що нові налаштування не діють на старі контейнери.
- **Перевірити себе:** `docker inspect -f '{{.HostConfig.LogConfig}}'` нового контейнера — ваш драйвер.
- **Пастка:** змінити драйвер у `daemon.json` і чекати, що ротація з'явиться в працюючих контейнерів. Діє лише на
  нові — старі треба перестворити.

### День 3. Автозапуск і відновлення

- **Навіщо.** Після перезавантаження сервера все має піднятися саме — і в правильному порядку.
- **Що це.** Політики перезапуску: `no`, `on-failure[:N]`, `always`, `unless-stopped`; різниця між двома останніми
  після ручної зупинки. Контейнер як служба systemd — альтернатива (фаза 6 плану Linux, Quadlet для Podman).
- **Читати:** `Start containers automatically`; `docker container update` (зміна політики).
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) проєкт з `unless-stopped`; 2) перезавантажити машину — усе піднялося; 3) зупинити руками один
  контейнер, перезавантажити — він лишився зупиненим.
- **Перевірити себе:** після кроку 2 `docker compose ps` — усе `healthy` без вашого втручання.
- **Пастка:** `restart: always` для контейнера, що падає на старті, — вічний цикл перезапусків, що з'їдає процесор і
  журнал. `on-failure` з межею або перевірка стану.

### День 4. Безпека рушія й контейнерів

- **Навіщо.** Контейнер — не віртуальна машина: ядро спільне, і помилка в налаштуваннях дає root на господарі.
- **Що це.** Захист шарами: не root усередині (`USER`), `--cap-drop ALL` + потрібні можливості, `--read-only` з
  tmpfs для записів, `--security-opt no-new-privileges`, типові профілі seccomp і AppArmor (фаза 6 плану Linux),
  ніколи `--privileged` і не монтувати `/var/run/docker.sock` у контейнер.
- **Читати:** `Docker Engine security`; `Seccomp security profiles for Docker`; `AppArmor security profiles for
  Docker`; `Antivirus software and Docker`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** API з `--read-only`, `--cap-drop ALL`, `no-new-privileges` і tmpfs для `/tmp`; переконатися, що
  працює; спробувати з контейнера змінити час машини чи змонтувати файлову систему — відмова.
- **Перевірити себе:** `docker inspect` показує `ReadonlyRootfs: true` і порожній перелік можливостей; спроби кроку —
  «Operation not permitted».
- **Пастка:** змонтувати `docker.sock` у контейнер «для моніторингу» — це повний root на господарі для всього, що
  в контейнері.

### День 5. Rootless і простір користувачів

- **Навіщо.** Навіть втеча з контейнера не повинна давати root на машині.
- **Що це.** Rootless-режим — сам рушій працює від звичайного користувача (обмеження: порти нижче 1024, деякі
  драйвери мереж і сховищ). `userns-remap` — root контейнера відображається на непривілейованого користувача
  господаря (несумісний з containerd image store).
- **Читати:** `Rootless mode`; `Isolate containers with a user namespace`; `containerd image store with Docker
  Engine` — розділ про обмеження.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** 1) rootless-рушій для окремого користувача на `rocky`; 2) запустити проєкт у ньому; 3) з'ясувати, яким
  UID на господарі працює «root» контейнера.
- **Перевірити себе:** `ps -o user,cmd -C nginx` на господарі — ваш користувач, а не root.
- **Пастка:** rootless і порт 80 — «permission denied». Або порт вище 1024 з проксі, або
  `net.ipv4.ip_unprivileged_port_start` (параметр ядра з фази 3 плану Linux).

### День 6. Діагностика рушія

- **Навіщо.** Рушій не стартує, контейнер не бачить мережу, диск закінчився — і треба знайти причину за хвилини.
- **Що це.** `journalctl -u docker`, `dockerd --debug`, `docker info` (попередження внизу), `docker system events`,
  `docker system df`; мережа — `nsenter` у простір контейнера (фаза 7 плану Linux); сховище — `containerd image store`
  чи overlay2.
- **Читати:** `Troubleshooting the Docker daemon`; `docker system events`; `docker system info`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** три поломки самому собі й знайти кожну: зламаний `daemon.json`, перетин пулу адрес Docker з
  мережею машини, контейнер без DNS.
- **Перевірити себе:** для кожної поломки — команда, що показала причину, у журналі.
- **Пастка:** `docker system prune -a` як ліки від усього — проблема мережі чи DNS не зникне, а образи доведеться
  тягнути знову.

# Фаза 6. Міст до Kubernetes — 3 дні

**Сервери MCP фази:** `docker-docs`, `kubernetes-docs`.

### День 1. Що з Docker переходить у Kubernetes

- **Навіщо.** Kubernetes не запускає Docker: він запускає образи через containerd. Треба знати, що з вашої роботи
  переходить, а що ні.
- **Що це.** Переходить: образ (той самий, з реєстру), команда й аргументи, змінні, порти, `USER`, сигнали, ліміти
  ресурсів. Не переходить: `HEALTHCHECK` (у Kubernetes — проби в маніфесті), `depends_on` (застосунок мусить сам
  чекати залежність), томи й мережі Compose, політики перезапуску. Рантайм кластера — containerd з CRI, і `crictl`
  замість `docker`.
- **Читати:** `containerd image store with Docker Engine`; `Alternative container runtimes`; документація
  Kubernetes про контейнерні рантайми — у примірнику `kubernetes`.
- **Сервери MCP:** `docker-docs`, `kubernetes-docs`.
- **Зробити:** таблиця в README: кожен рядок вашого `compose.yaml` → як це буде в Kubernetes (або «не переходить»).
- **Перевірити себе:** у таблиці немає рядка без відповіді.
- **Пастка:** покладатися в застосунку на `depends_on` — у Kubernetes порядку запуску подів немає, і застосунок має
  сам повторювати підключення до бази.

### День 2. Образ, готовий до кластера [CKAD]

- **Навіщо.** CKAD вимагає змінити образ і запустити його в поді; кластер вимагає від образу те, що Compose
  пробачав.
- **Що це.** Завершення за `SIGTERM` за кілька секунд, без стану на диску контейнера, конфіг через змінні, журнал у
  stdout, не root з числовим UID (`runAsNonRoot` перевіряє число, не ім'я), ендпоінти `/healthz` і `/readyz` окремо.
- **Читати:** `Building best practices` — ще раз; `Run multiple processes in a container`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** привести образи проєкту до переліку: числовий UID, два ендпоінти здоров'я, журнали лише в stdout,
  чисте завершення за `SIGTERM` менш ніж за 5 секунд.
- **Перевірити себе:** `docker run --user 10001 … ` працює; `docker stop -t 5` — завершення без `KILL` у
  `docker events`.
- **Пастка:** `USER app` іменем — Kubernetes з `runAsNonRoot: true` відмовить запускати, бо за іменем не може
  перевірити, що це не root.

### День 3. Compose → маніфести

- **Навіщо.** Перший погляд на маніфести Kubernetes з власного, знайомого `compose.yaml`.
- **Що це.** Compose Bridge перетворює `compose.yaml` на маніфести Kubernetes (Deployment, Service, PVC); результат
  — чернетка, а не продакшн, але добре показує відповідність понять.
- **Читати:** `Overview of Compose Bridge`; `Use the default Compose Bridge transformation`; `docker compose bridge
  convert`.
- **Сервери MCP:** `docker-docs`.
- **Зробити:** перетворити `compose.yaml` проєкту й прочитати кожен згенерований маніфест: що з чого вийшло і що
  загубилося (перевірки стану, секрети, порядок).
- **Перевірити себе:** у README — перелік того, що перетворення загубило, — з ним ви починаєте план Kubernetes.
- **Пастка:** вважати згенеровані маніфести готовими до продакшну — без проб, лімітів і секретів вони лише стартова
  точка.

# Застереження про документацію

У корпусі цього примірника — **лише Docker**: docs.docker.com (Engine, збірка, Compose, Docker Hub, безпека,
посібники, довідники Dockerfile, compose-файлу й командного рядка), нотатки релізів Engine 27–29 і релізи moby,
compose та buildx. Docker Desktop, Docker AI, Scout як продукт і інші платні продукти не взято. Про інші бібліотеки
й інструменти сервер `docker-docs` відмовить або поверне лише уривки, де їх згадано. Для яких із них у фабриці є
власний примірник, а для яких його ще немає, — у підрозділі «Документація у фабриці» нижче; там же — що беруть із
сайтів самих інструментів.

**Версія.** Документація сайту одна — поточна; на 04.10.2026 це Engine 29. Нотатки релізів кажуть, з якої версії що
з'явилося: containerd image store типовий з Engine 29 на нових установках, бекенд nftables з 29.0 —
експериментальний. Статті й відповіді в інтернеті часто описують Compose v1 (`docker-compose`, поле `version`) і
класичний збирач без BuildKit — звіряйте з корпусом.
