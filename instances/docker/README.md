# docker — примірник фабрики docfactory

Двадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Docker — Engine, Dockerfile,
збирання образів (BuildKit, buildx, bake), Compose, Docker Hub і CLI — за офіційною документацією docs.docker.com і
нотатками релізів Engine, Compose і Buildx. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

Docker — інструмент, який бекенд-розробник бачить щодня, і саме в ньому найлегше впевнено помилитися: прапорець
`COPY --chown` чи `--link`, синтаксис `--mount=type=cache` у `RUN`, ключ `healthcheck` і умова `service_healthy` у
`depends_on`, різниця між `-p 8080:80` і `EXPOSE`, `docker-compose` (Compose 1, Python) проти `docker compose`
(плагін). Відповідь з пам'яті тут часто застаріла на кілька років; відповідь із документації — ні.

Документація на docs.docker.com одна — чинна, без версій: старих редакцій сайт не тримає. Версії живуть лише в
нотатках релізів, і там вони є: що змінилося в Engine 27–29, у кожному релізі Compose і Buildx.

Разом 1 264 документи; фрагментів в індексі — 10 111 (`expected_passages` у `checks.json`). Фрагменти —
це шматки документів між заголовками, по яких іде пошук.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без назв команд і інструкцій) — по
словах 7 із 10, за змістом 6, разом 7; друга, «як модель» (назви інструкцій, команд і ключів, як велить промпт), —
10 із 10. Промахи першої десятки — питання, де своїх слів документація не вживає: «set the owner of files» не
знаходить `COPY --chown`, «reachable from the host on a chosen number» — публікацію портів, «leave files out of what
is sent to the builder» за змістом — `.dockerignore`. Тому промпт велить писати запит назвами самої документації.

**Версія у відповіді.** Документація без версії — це завжди чинна редакція, і відповідь «як зробити» спирається на
неї. Коли питання про версії — що змінилося, з якого релізу, що застаріло, — відповідь називає продукт і реліз:
номери в Engine (`29.x`), Compose (`5.x`) і Buildx (`0.x`) свої.

## Що в цій теці

- `corpus/` — документи звичайними текстовими файлами; поруч `index.json` — паспорт: адреса, дата завантаження й
  сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df docker <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| посібники, довідники, CLI, гайди | sitemap.xml docs.docker.com, текст — markdown-двійник сторінки | `sitemap-md-meta` |
| нотатки релізів Engine 27–29 | markdown-двійник сторінки лінії, поділений на версії | `changelog` |
| релізи Engine на GitHub | moby/moby, лише теги `docker-v…` | `ghreleases-tagged` |
| релізи Compose і Buildx | docker/compose, docker/buildx | `ghreleases` |

Нових читачів немає. Сайт docs.docker.com (Hugo) віддає кожну сторінку ще й markdown-ом — та сама адреса з «.md»
(«markdown-двійник»): шорткоди там уже розгорнуті, вкладки й вставки підставлені, а довідник CLI, який у репозиторії
docker/docs лежить YAML-ом, — готовою сторінкою з описом, таблицею опцій і прикладами. Тому джерело — сам сайт, а не
репозиторій: з репозиторію довелося б писати власний розбір Hugo і переклад YAML у текст.

Особливості, які варто знати:

- **Сайтмап один, джерел дев'ять.** Кожне джерело-сайт бере зі спільного sitemap.xml лише свій розділ (поле
  `within`), а кореневу сторінку розділу (`/engine/` → `engine.md`) — окремим рядком того ж поля: вона лежить поруч
  із текою, а не в ній.
- **Сторінки-заглушки пропущено** (поле `skip`). Нотатки релізів Compose і Build та Dockerfile frontend на сайті
  лише ведуть на GitHub, і їхній markdown — сам заголовок без тексту; сторінки окремих версій Engine API
  (`/reference/api/engine/version/v1.40` … `v1.56`) — обгортки інтерактивної специфікації; коренева сторінка
  Get started і глосарій — markdown без тексту (сайт будує їх із даних). Короткі псевдоніми CLI (`docker run`,
  `docker ps`, `docker build`, `exec`, `images`, `info`, `pull`, `push`) markdown-двійника не мають (404): їхній
  текст лежить на сторінках повних команд (`docker container run`, `docker buildx build`…). Нотатки релізів Engine
  пропущено в посібнику Engine, бо вони йдуть окремими джерелами, поділені на версії.
- **Нотатки релізів Engine 27 і 28 поділені на мінорні версії** (`## 27.5`, а патчі `27.5.1` — підрозділи
  всередині), 29 — на патчі (`## 29.8.2`). Тож мітка документа — `27.5` чи `29.8.2`; фільтр `"29"` бере всю лінію.
- **Релізи Engine на GitHub — лише з 29.0.** Відтоді moby/moby позначає їх тегами `docker-v…`; старіші теги `v…`
  не взято — ті самі версії описують нотатки релізів на сайті. Номери Compose і Buildx свої: `"5"` — Compose 5.x,
  `"2"` — Compose 2.x, `"0.37"` — Buildx 0.37.
- **Лише англійською.**

## Межі, про які треба пам'ятати

Тут немає Docker Desktop, Docker AI (Model Runner, Gordon, MCP Toolkit, sandboxes), Docker Hardened Images, Scout,
Extensions, Build Cloud, Testcontainers, керування підпискою й обліковими записами, а також команд CLI цих
продуктів (`docker mcp`, `docker model`, `docker scout`, `docker dhi`, `docker desktop`, `docker pass`,
`docker offload`). Немає й специфікації Engine API за версіями (OpenAPI v1.40…v1.56): її YAML потребує PyYAML,
якого в цьому примірнику немає, а сторінки Engine API про SDK і історію версій API є. Нотатки релізів Engine
старіших за 27 не взято. Kubernetes, containerd і runc окремо — поза примірником.

## Установка venv

```
cd instances/docker
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

Токен GitHub тут необов'язковий: релізи трьох репозиторіїв — близько півтора десятка звернень до GitHub API, а без
токена їх дозволено 60 на годину.

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df docker sources --why   # перелік джерел і білий список
./df docker refresh         # завантажити все задеклароване (~20 хвилин)
./df docker manifest        # оновити паспорт
./df docker setup           # Qdrant чи пошук лише по словах
./df docker vectors         # залити корпус у docs-docker (~50 хвилин)
./df docker smoke           # перевірки
```

Довгі кроки з Claude Code запускають окремим процесом (`setsid nohup …`), інакше фонову задачу обірве оболонка
через 30 хвилин. Обірваний `refresh` продовжується з `--missing`: уже записане він не тягне вдруге.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df docker serve           # порт 8780
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8780/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user docker-docs http://127.0.0.1:8780/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `docker-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df docker setup --vectors      # з Qdrant: потрібен Docker
./df docker setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

**4. Перевірка, сервер, клієнт.**

```
./df docker smoke           # усі перевірки мають бути ok
./df docker serve           # порт 8780, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
