# Оновлення корпусу docker

Дві різні роботи: звичайне оновлення (змінилася документація, вийшли нові релізи Engine, Compose чи Buildx) і нова
мажорна лінія Engine. Порядок усередині кожної важливіший за самі команди.

Головне правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Сторінка, що зникла з docs.docker.com, лишається в `corpus/`; прибрати — рішення людини.

## 1. Звичайне оновлення

Документація на сайті одна — чинна, тож її сторінки змінюються на місці, без нових версій. Перелік сторінок
кожного розділу береться з sitemap.xml при кожному прогоні: нові сторінки підхоплюються самі. Нові релізи Compose,
Buildx і Engine на GitHub і нові версії на сторінці нотаток релізів Engine — теж.

```
./df docker check                  # що змінилося нагорі, нічого не записує
./df docker refresh                # повний — DOCS_REFRESH_TIME
./df docker manifest
./df docker vectors
./df docker smoke
# Ctrl+C у терміналі з serve, і знову: ./df docker serve
```

Тут потрібен саме повний `refresh`, а не `--missing`: змінені сторінки лежать під тими самими іменами файлів, і
`--missing` їх не торкнеться. `--missing` — лише щоб продовжити обірваний прогін. З Claude Code довгі кроки
запускати окремим процесом (`setsid nohup …`), інакше оболонка обірве їх через 30 хвилин.

Якщо `refresh` скаржиться «тіло куце (0 символів)» на якусь сторінку — це нова заглушка, що лише веде деінде
(зазвичай на GitHub). Таку адресу додають у поле `skip` її джерела в `sources.json` і запускають `refresh` знову.

Корпус комітити логічними частинами до ~700 файлів: документація, довідник CLI, нотатки й релізи.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Нова мажорна лінія Engine

Нотатки релізів Engine лежать на сайті сторінкою на лінію (`/engine/release-notes/29/`). Нова лінія (наприклад,
30) — новий запис у `sources.json` за зразком `engine-release-notes-29`: `url` — `…/release-notes/30.md`, `cite` —
та сама адреса без «.md» з косою рискою, `title` і `note` — з новим номером. Релізи на GitHub (`releases-moby`,
теги `docker-v…`) нову лінію підхоплюють самі.

Потім `refresh` лише нового джерела (`./df docker refresh engine-release-notes-30`), `manifest`, `vectors`,
`smoke`, як у розділі 1, рядок у таблиці README і номер лінії в `prompts/search.txt` та `prompts/loaded.txt`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df docker quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Версій у документації немає.** `prompts/search.txt` і `prompts/agent.txt` велять шукати без `version`, а
  `version` — лише для нотаток релізів; тож і `quality_model` у `checks.json` іде без версії.
- **Правила промпту, що вже є:** запит — назвами інструкцій, команд, прапорців і ключів англійською; номери версій —
  свої в Engine, Compose і Buildx; кожна відповідь каже продукт, а для питань про версії — реліз; текст лише з rc чи
  beta міг не вийти релізом.
- **Останній результат:** у README, абзац «Замір `quality`».
