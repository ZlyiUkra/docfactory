Search the official Docker documentation at docs.docker.com: Get started; Docker Engine
(installation on every Linux distribution, running and managing containers, networking --
bridge, host, overlay, macvlan, port publishing --, storage -- volumes, bind mounts, tmpfs,
storage drivers --, logging, daemon configuration, rootless mode, security, resource
constraints, swarm, plugins, deprecated features); Docker Build (Dockerfile best practices,
multi-stage builds, build context and .dockerignore, BuildKit, buildx builders and drivers,
multi-platform images, cache and cache backends, exporters, secrets and SSH, attestations,
bake, CI); Docker Compose (how it works, environment variables and interpolation, profiles,
startup order with depends_on and healthcheck, watch, multiple Compose files, production);
Docker Hub; account and organization security; the full Dockerfile reference, the Compose
file reference, the build checks, the CLI reference of every docker, docker buildx and
docker compose command and of dockerd, and the language and task guides. Also the Docker
Engine release notes for 27.x, 28.x and 29.x and the GitHub release notes of Docker Engine
(moby/moby), Docker Compose and Docker Buildx. Returns the matching excerpts with the
versions each one belongs to.

Call this when a question is about Docker -- writing a Dockerfile (FROM, RUN, COPY and ADD
with --chown, --chmod, --from and --link, ARG, ENV, ENTRYPOINT and CMD, HEALTHCHECK, USER),
building images, docker build and docker buildx build, multi-platform builds, the build
cache, running containers (docker run -p, -v, --network, --restart, -e), volumes and
networks, the daemon and daemon.json, compose.yaml and docker compose commands, Docker Hub
-- and when it is about Docker versions: what changed in an Engine, Compose or Buildx
release, since which release a flag or behaviour exists, what was deprecated or removed.
Example query: "COPY --chown".

Do not call this for Docker Desktop, Docker AI and Model Runner, Docker Hardened Images,
Scout, Extensions or Testcontainers, for Kubernetes, Podman, containerd or runc on their own,
or for the images of particular applications on Docker Hub: their documentation is not here,
and the search will return Docker excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line, and it applies only to release notes:
the documentation on docs.docker.com is a single current edition and carries no version, so
a search with `version` never returns it. "29" keeps Docker Engine 29.x, "28" Engine 28.x,
"5" Compose 5.x, "2" Compose 2.x, "0.37" Buildx 0.37 -- every product has its own numbers,
and the title of every excerpt names its product, so read it. Leave `version` empty for
everything else. Excerpts of release notes come back with `versions`: the release the text
belongs to.

Where the documentation lives. Documents are named by their path on docs.docker.com
(engine/network/port-publishing, build/building/multi-stage, compose/how-tos/startup-order,
reference/dockerfile, reference/compose-file/services, reference/cli/docker/container/run,
reference/cli/docker/buildx/build). The Dockerfile reference is one long document with a
section per instruction; the Compose file reference has a document per top-level element.
Engine release notes are titled "Docker Engine release notes: <version>"; GitHub releases by
product and tag.

Write the query in English, with the names the documentation uses (Dockerfile instructions,
command names, flags such as --platform or --mount=type=cache, Compose keys such as
depends_on, healthcheck, develop.watch). Everything here is English -- the excerpts, the
word index and the meaning index alike -- and the word index keeps only latin letters and
digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into Docker terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which product it is about, and for a question about versions which
release. When the excerpts behind a statement come only from release notes of older
releases, name those releases instead of presenting the text as current. A text found only
in an rc or beta release may never have shipped: say so.

Answer in the language the user wrote in. When the question is about a feature's history or
compatibility, answer point by point: which product and since which release; what changed in
later releases; and how it stands now in the documentation. Every point names the release or
the document it rests on; a point the excerpts do not support is left out, not guessed. When
that language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from
English: plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not
"ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" --
say "документація Docker". Identifiers, instructions, commands, flags and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
