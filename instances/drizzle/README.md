# drizzle — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Drizzle — ORM для TypeScript від drizzle-team (PostgreSQL, MySQL,
SQLite, SingleStore) разом із CLI міграцій drizzle-kit, Drizzle Studio, генератором тестових даних drizzle-seed і
генераторами схем валідації (drizzle-zod, drizzle-typebox, drizzle-valibot, drizzle-arktype). Джерела — сайт
orm.drizzle.team (репозиторій drizzle-team/drizzle-orm-docs), монорепозиторій drizzle-team/drizzle-orm і реєстр npm,
лише англійською й лише стабільні версії. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`;
ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

План Next.js бере Drizzle як легшу альтернативу Prisma там, де застосунок говорить із PostgreSQL. Drizzle рухається
швидко: за 2024–2025 роки змінилися команди й конфігурація drizzle-kit (0.21 прибрав префікси діалектів у командах),
з'явилися `$count`, ідентичні колонки, генеровані колонки, кеш запитів, drizzle-seed і нова версія drizzle-zod; а з
грудня 2025 команда готує 1.0 з іншим API зв'язків. Тож потрібен текст документації тієї версії, з якою працюєш, а не
пам'ять моделі.

**Що є що.** **ORM** — бібліотека, що описує таблиці кодом TypeScript і складає з цього типізовані запити SQL.
**Схема** — файл із таблицями (`pgTable`, `mysqlTable`, `sqliteTable`), колонками й зв'язками; з неї Drizzle виводить
типи рядків (`$inferSelect`, `$inferInsert`). **Діалект** — вид бази (PostgreSQL, MySQL, SQLite, SingleStore);
**драйвер** — бібліотека з'єднання з нею (node-postgres, postgres.js, Neon, mysql2, better-sqlite3, libSQL…), і в
кожного свій `drizzle()` з власними параметрами. **drizzle-kit** — CLI, що порівнює схему з базою: `generate` пише
файли міграцій SQL, `migrate` їх застосовує, `push` змінює базу одразу, без файлів (для прототипів), `pull` читає
наявну базу в схему, `studio` відкриває **Drizzle Studio** — переглядач даних у браузері. **Relational Queries**
(`db.query`) — API вибірки з вкладеними зв'язками (`with`) поверх оголошених `relations()`.

У яких фазах і днях планів навчання він потрібен — див. [../../docs/learning-map.md](../../docs/learning-map.md).

«як модель» (назви функцій, команд і опцій, як велить промпт), — 10 із 10. Перший замір дав 7 із 10, і причин було
три. Посібники й сторінки «Get started» повторюють той самий крок у кожній вкладці драйвера власним заголовком («Push
your changes to the database» чотири рази на сторінці), і одна така сторінка займала всю видачу на `drizzle-kit
push`: `max_per_doc` 1 віддає сторінці одне місце. Запит «drizzle-kit generate migrations» знаходив кроки «Generate
migrations» десятка сторінок «Get started»; промпт велить шукати команду назвою її сторінки, і запит «drizzle-kit
generate» знаходить її першою. Сама назва функції («pgEnum») збігається з кожним рядком журналу змін, що її згадує;
промпт тепер радить додавати слово теми («pgEnum enum»). Ціль питання про `db.query` з `with` доповнено сторінкою
Relational Queries цілком: уся вона про цей API. `fusion_depth` 10 тримає 10 із 10, але забирає одне влучання першої
десятки, 15 — забирає одне «як модель», тож не ввімкнений.

## Що в цій теці

- `corpus/` — лише паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа (тексти — в архіві,
  див. нижче).
- `index/passages.json.gz` — стиснений кеш фрагментів, з якого підіймається сервер.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями, спільний ключ сторінок трьох
  розкладок сайту (`slug_rewrite`), `max_per_doc`, глибина лінії версій і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (дерева комітів і тегів, релізи); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df drizzle <крок>`.

Особливості, які варто знати:

- **Сайт описує 1.0 RC.** 02.12.2025 у `main` злили документацію бети 1.0: діалекти MSSQL і CockroachDB, нове API
  зв'язків, команди встановлення `drizzle-orm@rc`. Примірник бере лише стабільні версії, тож знімки сайту

  наступниця вийшла теж після нього. Нового в 0.45.x — дрібні виправлення, драйвер Netlify DB і виправлення
  екранування в `sql.identifier()`, і це дають журнали змін.
- **Історія сайту — з грудня 2023.** Раніший сайт (на Nextra) у git-історії репозиторію не зберігся, тож перший знімок
  — 0.29.1. Документацію 0.17–0.29.0 дає монорепозиторій: тоді повний довідник pg-core, mysql-core і sqlite-core жив у
  README модулів `drizzle-orm/src`.
- **Три розкладки сайту.** До 0.33 (вересень 2024) — тека `src/content/documentation` (з теками `docs/`, `kit-docs/`)

  `documentation/docs`; з 0.36 (кінець жовтня 2024) — `src/content/docs`. Поле `slug_rewrite` у `config.json` дає
  сторінці спільний ключ у всіх трьох: стара редакція не займає у видачі місця нової, однаковий текст зливається в
  один фрагмент. Правила виведено зіставленням назв сторінок; спільних ключів між різними джерелами немає.
- **Компоненти сайту.** Сторінки — MDX для Astro. Поле `astro_mdx` (модуль `_astromdx`) розкриває спільні шматки MDX
  (кроки «Get started» кожного драйвера з підставленими назвами пакетів і змінних), підписує вкладки діалектів і
  файлів («PostgreSQL:», «MySQL:», «schema.ts:»), робить із `<Npm>` і `<Npx>` рядки `npm i …` і `npx …`, з позначок
  підтримки — рядок «Supported: … Not supported: …», і знімає роздільники `## ---`. Псевдонім `@mdx/` сайт переносив
  із `src/components/markdown` у `src/mdx`, тож він шукається в обох теках. Анонси й сторінка-вітрина компонентів
  (`migrate/components`) не беруться.
- **Журнали змін.** Тека `changelogs/` тримає файл на кожну версію кожного пакета, зокрема старих окремих
  drizzle-orm-pg, drizzle-orm-mysql і drizzle-orm-sqlite (2022). Файл починається одразу з розділу, тож назву
  документа дає шлях: «drizzle-kit 0.31.4 release notes». Ті самі тексти стоять у релізах GitHub, тож релізи

## Версії у відповіді

Фільтр `version` бере лінію drizzle-orm: `"0.45"` — усе 0.45.x, `"0.30"` — усе 0.30.x. Глибина лінії — два числа
(`version_line_depth` 2). Інші пакети мають власну нумерацію й мітку: `"drizzle-kit-0.31"`, `"drizzle-zod-0.8"`,
`"drizzle-seed-0.3"` тощо; голе `"0.31"` drizzle-kit не бере. Без фільтра сторінка, що є в кількох версіях,
показується один раз — найновішою редакцією. Журнали змін мають версію свого випуску.

Без названої версії промпт велить відповідати для найпопулярніших стабільних за завантаженнями npm (тиждень до
13.10.2026): drizzle-orm 0.45 (0.45.2 — 14,7 млн) і drizzle-kit 0.31 (0.31.10 — 10,8 млн). 1.0.0-rc.4 має понад
мільйон завантажень на тиждень, але це передреліз, і його документації тут немає.

## Сховище сирого

Під час оновлення примірник тримає ще й сирі відповіді — у теці `raw/`, поза git (сховище ввімкнене за
замовчуванням). Правка читача тоді не вимагає нового завантаження: `./df drizzle build` збирає тексти зі сховища без
мережі. Попередні версії файлів не видаляються, а переїжджають у `raw/_old/<день>/`. Між оновленнями сховище, як і
тексти, лежить лише в архіві: серверу воно не потрібне. Устрій — у [../../UPDATE.md](../../UPDATE.md), розділ про
`refresh`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/drizzle-corpus-2026-10-13.tar.gz` (1 404 тексти, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском). В історії git текстів немає ніде.
Архів лежить лише на цій машині. Сховище `raw/` після звірки теж видалено з диска.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/drizzle/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/drizzle-corpus-РРРР-ММ-ДД.tar.gz -C instances/drizzle corpus raw
find instances/drizzle/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/drizzle/raw
gzip -9 -c instances/drizzle/index/passages.json > instances/drizzle/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/drizzle-corpus-РРРР-ММ-ДД.tar.gz -C instances/drizzle
./df drizzle smoke
```

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/drizzle/index/passages.json.gz`, далі
`./df drizzle vectors` заллє колекцію Qdrant (близько 12 хвилин).

## Установка venv

```
cd instances/drizzle
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # ANTHROPIC_API_KEY — для кроку ask; GITHUB_TOKEN — для репозиторіїв
cd ../..
```

## Збирання корпусу

```
./df drizzle sources --why   # перелік джерел і білий список
./df drizzle refresh         # завантажити все задеклароване (~17 хвилин: ~170 дерев, ~1 800 файлів, пауза 0,3 с)
./df drizzle build           # перезібрати тексти зі сховища сирого, без мережі (після правки читача)
./df drizzle manifest        # оновити паспорт
./df drizzle setup           # Qdrant чи пошук лише по словах
./df drizzle vectors         # залити корпус у docs-drizzle (~12 хвилин)
./df drizzle smoke           # перевірки
```

Як оновлювати після нових версій — у [UPDATE.md](UPDATE.md).

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df drizzle serve       # порт 8830
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8830/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user drizzle-docs http://127.0.0.1:8830/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт. Інший
шлях — запис `.mcp.json` цієї теки: Claude Code, відкритий у ній, побачить сервер сам.

**3. Перевірити.** `/mcp` — має бути `drizzle-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію Claude
Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і «Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Якщо порт 8830 зайнятий, `serve` падає з «address already in use»: значить,
сервер уже піднято в іншому терміналі. Решта — scope запису — так само, як у
[README примірника nestjs](../nestjs/README.md#спосіб-б--сервер-під-claude-code-http).
