# Оновлення корпусу drizzle

Дві різні роботи: звичайне оновлення, коли вийшли нові стабільні версії пакетів Drizzle, і збирання з нуля. Порядок
усередині кожної важливіший за самі команди.

Головне правило: **оновлювач тягне лише оголошене.** Дерева й файли репозиторіїв — лише тих комітів і тегів, що
перелічені в полі `tags` джерел, і лише в межах `within`; релізи — лише з адреси джерела `releases-drizzle-kit`; версії —
з реєстру npm. Нова версія сама в документацію не потрапить, доки її тег (чи коміт сайту) не дописано в `tags`.

Друге правило: **лише стабільні версії.** У `tags` — тільки стабільні випуски, без бет і RC (`1.0.0-beta.22`,
`1.0.0-rc.4`) і без збірок гілок з хешем (`1.0.0-beta.1-867d080`); поле `skip_versions` джерел `npm-*` і поле `exclude`
джерела `changelogs` відкидають усе з дефісом за номером.

Третє правило: **версія сайту — стан гілки перед наступною версією.** Сайт (репозиторій drizzle-team/drizzle-orm-docs,
гілка `main`) тегів не має. Для кожної стабільної версії drizzle-orm у `tags` джерела `site` стоїть повний SHA вершини
гілки (за ланцюжком перших батьків) перед публікацією наступної стабільної версії. Але з 02.12.2025 (коміт злиття
`60a3e192`, «Beta (#626)») сайт описує 1.0 RC, тож межа знімків — останній коміт перед злиттям, `11695b74`
(19.11.2025): кожна нова версія 0.45.x дописується до його ключа.

Четверте правило: **нова версія змінює й старі документи.** Документ сторінки — неповторна редакція, а в рядку
`# версія:` стоять усі версії, де вона була саме такою. Тож після нових комітів джерела перезаписуються цілком
(`refresh site repo`), а не докачуються (`--missing`).

П'яте правило: **нічого не видаляється.** Ані `refresh`, ані `build`, ані `manifest` нічого не стирають самі;
`vectors` прибирає лише точки власної колекції, чиїх фрагментів у корпусі вже немає. Редакції сторінок, що після
правки читача дістали нове ім'я, лишаються в `corpus/` старими файлами — їх переносять убік вручну.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти й сховище сирого розпаковують, а після неї —
пакують і виносять знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшла нова стабільна версія 0.x

**Крок 1. Знайти версію.** Стабільні версії й час публікації — у реєстрі npm
(`https://registry.npmjs.org/drizzle-orm`, поле `time`), теги — на `https://github.com/drizzle-team/drizzle-orm/tags`
(drizzle-orm — голий номер `0.45.5`, drizzle-kit — `drizzle-kit@0.31.12`).

**Крок 2. Сайт.** Поки `main` описує 1.0, нова версія 0.45.x дописується до ключа `11695b74…` джерела `site`:
`"11695b74b84979f2ba9641009608d38fe0efbbe8": "0.45.5, 0.45.4, …"`.

**Крок 3. Тег монорепозиторію.** `"0.45.5": "0.45.5"` — на початок поля `tags` джерела `repo`.

**Крок 4. Журнали змін.** У джерелі `changelogs` ключ поля `tags` — коміт `main` монорепозиторію; його замінюють на
новий (`https://api.github.com/repos/drizzle-team/drizzle-orm/commits/main`, поле `sha`), щоб тека `changelogs/`
містила файли нових версій.

**Крок 5. Завантажити.**

```
./df drizzle sources --why
./df drizzle refresh site repo changelogs npm-drizzle-orm npm-drizzle-kit npm-drizzle-zod npm-drizzle-typebox npm-drizzle-valibot npm-drizzle-arktype npm-drizzle-seed npm-eslint-plugin-drizzle npm-drizzle-graphql npm-drizzle-prisma-generator npm-expo-drizzle-studio-plugin npm-drizzle-team-studio readme-drizzle-graphql readme-drizzle-prisma-generator readme-expo-drizzle-studio-plugin readme-drizzle-team-studio
./df drizzle manifest
./df drizzle vectors
./df drizzle smoke
# Ctrl+C у терміналі з serve, і знову: ./df drizzle serve
```

Названий `refresh` інших джерел не чіпає зовсім. Джерело `releases-drizzle-kit` застигле: репозиторій
drizzle-kit-mirror архівний.

**Крок 6. Промпти.** Версії за замовчуванням (найпопулярніші за завантаженнями npm:
`https://api.npmjs.org/versions/drizzle-orm/last-week`) записано в `prompts/search.txt` (абзац «Every answer says
which version…») і `prompts/agent.txt`; межі версій — ще й у `prompts/loaded.txt`, `prompts/read.txt` і
`prompts/agent.txt` («від 0.29.1 до 0.45.4»).

## 2. Вийшов стабільний Drizzle 1.0

Тоді `main` сайту знову описує стабільну версію. Нове джерело `site-1` робиться за зразком `site` з ключами-комітами
`main` для версій 1.x (від виходу 1.0.0), id обох джерел іде в одну родину поля `families` у `config.json`, а в
`slug_rewrite` — правила, що зводять нові шляхи сторінок (з 1.0 сторінки розійшлися по теках діалектів: `pg/`, `mysql/`,
`sqlite/`, `mssql/`, `cockroach/`, `singlestore/`) до спільного ключа `src-content-docs-…`. Правильність ключів
перевіряють в `index/passages.json`: ключ розділу (`slug` і `section`) мусить бути спільним лише для джерел однієї
родини. Нові компоненти сайту (рядки `<…>` у текстах, `{props.…}`) — правка модуля `engine/readers/_astromdx.py`;
лінія версій у промптах і README — «1.0».

## 3. Сайт змінив розмітку

Якщо в тексті з'явилися службові рядки MDX (теги компонентів `<…>`, `{props.…}`, рядки `import`), правиться модуль
`engine/readers/_astromdx.py`. Правка читача не вимагає нового завантаження: `./df drizzle build site` збирає тексти
зі сховища сирого. Виняток — вставка файла, якого читач досі не брав: його в сховищі ще немає, тож потрібен `refresh`
джерела.

Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти й сховище (README, розділ «Архівний
режим»), а в git ідуть лише паспорт і кеш. Старий архів видаляють, коли новий звірено з диском.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 4. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки: без нього ~170 дерев ішли б годинними вікнами по
60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
PYTHONUNBUFFERED=1 setsid nohup ./df drizzle refresh > refresh.log 2>&1 < /dev/null &
```

Близько 17 хвилин: дерево кожного коміту сайту й тегу монорепозиторію через API GitHub і кожен неповторний файл
(сторінка, шматок MDX, README) один раз із raw.githubusercontent.com, з паузою 0,3 с. Обірваний прогін продовжують
`./df drizzle refresh <джерело, де зупинився>`, далі `refresh --missing`.

**Крок 3.** `manifest`, `vectors` (~12 хвилин), `smoke`, `quality`; далі — архів і винесення текстів.

Очікуваних збоїв `refresh` немає.
