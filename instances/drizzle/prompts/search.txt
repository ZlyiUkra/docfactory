Search the official documentation of Drizzle -- the TypeScript ORM for PostgreSQL, MySQL, SQLite
and SingleStore from drizzle-team, with its migrations CLI drizzle-kit -- and return the matching
excerpts with the versions each one belongs to. Here: the documentation site orm.drizzle.team as
it stood while each stable drizzle-orm release from 0.29.1 to 0.45.4 was the newest -- get
started with every driver and database (node-postgres, postgres.js, Neon, Vercel Postgres,
Supabase, Xata, PGlite, Nile, Gel, MySQL2, PlanetScale, TiDB, SQLite, libSQL and Turso, Cloudflare
D1 and Durable Objects, Bun, Expo SQLite, OP SQLite, SingleStore), schema declaration, column
types of every dialect, indexes and constraints, relations, sequences, views, schemas, Row-Level
Security, the select, insert, update, delete, joins, set operations, $count and query utilities,
the Relational Queries API (db.query), the sql template operator, transactions, batch,
dynamic queries, read replicas, caching, custom types, migrations and every drizzle-kit command
(generate, migrate, push, pull, check, up, studio, export) with drizzle.config.ts, Drizzle Studio,
drizzle-seed, drizzle-zod, drizzle-typebox, drizzle-valibot, drizzle-arktype, drizzle-graphql,
the ESLint plugin, the Prisma extension, guides, tutorials and the release posts; the markdown of
the drizzle-team/drizzle-orm repository at every stable tag from 0.17.0 (the package READMEs, and
before 0.29 the full pg-core and mysql-core documentation that lived there); the changelog of every
stable release of every package; the release notes of drizzle-kit 0.17.0-0.23.1; and the npm
version table of every Drizzle package.

Call this when a question is about Drizzle itself -- defining tables (pgTable, mysqlTable,
sqliteTable), column types and their modes, defaults, $onUpdate, generated and identity columns,
enums, indexes, primary and foreign keys, relations() and the db.query API with `with`, filters
and operators (eq, and, or, inArray, like, sql``), select fields, joins, subqueries, CTEs ($with),
aggregations, upserts (onConflictDoUpdate, onDuplicateKeyUpdate), returning, prepared statements
and placeholders, transactions and savepoints, type inference ($inferSelect, $inferInsert),
logging, the drizzle() connection options of a driver, drizzle-kit commands, flags and
drizzle.config.ts keys, migration files and the migrate() function, Drizzle Studio, seeding,
schema validators generated from tables, and above all history: since which version something
exists, what changed, what was renamed or removed.
Example query: "select partial select".

Do not call this for Prisma, TypeORM, Kysely, Knex, MikroORM or Sequelize beyond the pages that
compare or integrate them, the SQL language and the database servers themselves (PostgreSQL,
MySQL, SQLite), the drivers' own APIs (pg, mysql2, better-sqlite3), Zod, Valibot or TypeBox
themselves, Next.js, NestJS or any web framework, or hosting providers: their documentation is not
here, and the search will return Drizzle excerpts that merely mention them, with confident-looking
titles.

Only stable releases are here. Drizzle 1.0 (the 1.0.0-beta and 1.0.0-rc releases: Relational
Queries v2 with defineRelations, MSSQL and CockroachDB, drizzle-kit up for the v3 migration folder)
is not documented here: since December 2025 the live site describes 1.0 RC, and this
documentation stops at its last stable state. A question about 1.0 gets the answer that it is
not in this documentation.

Versions. `version` narrows the search to the documents of one release line of drizzle-orm:
"0.45" keeps every 0.45.x document, "0.30" every 0.30.x. The site has no versions of its own: each
of its documents carries the drizzle-orm versions during whose time the page read exactly so.
Every other package has its own numbering and its own label: "drizzle-kit-0.31" keeps drizzle-kit
0.31.x, "drizzle-zod-0.8" keeps drizzle-zod 0.8.x (also drizzle-typebox-, drizzle-valibot-,
drizzle-arktype-, drizzle-seed-, eslint-plugin-drizzle-, drizzle-graphql-); a bare "0.31" never
returns drizzle-kit. Without `version` a page found in several releases comes back once, in its
newest edition. Every excerpt comes back with `versions`: each version whose documents contain
this exact text, newest first. Changelogs carry the version of their release.

Name the function, method, column type, option, command or config key the way the documentation
titles it, not in the user's own words: "onConflictDoUpdate upsert", "relations one many",
"db.query findMany with", "pgEnum", "drizzle-kit push strict", "drizzle.config.ts schemaFilter",
"migrate() migrationsFolder", "createInsertSchema drizzle-zod", "$inferSelect", not "how do I
update a row if it already exists". For a how-to question a guide often shows it better than the
reference: search for it as well ("upsert guide", "timestamps default value guide").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the changelog or release post that names the exact version, then
with the versions around it, to see the documentation of that time.

Write the query in English, with the names Drizzle itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate
the question into Drizzle terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
most downloaded stable releases: drizzle-orm 0.45 (0.45.2) and drizzle-kit 0.31 (0.31.10) -- and,
when the excerpts show that a function, option or command appeared in a later release than the
user may have, say since which one. Add that for a precise answer about another version the user
can name it. When the excerpts behind a statement come only from older versions, name those
versions instead of presenting the text as current. Many pages show the same example for every
dialect, each under its own label (PostgreSQL:, MySQL:, SQLite:, SingleStore:): give the one the
user asked about, and when the user did not say, the PostgreSQL one with a note that the others
exist; "Supported: … Not supported: …" lines say which dialects have a feature.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
and how it stands now -- recommended, deprecated, or removed and replaced by what. Every point
names the version and the document it rests on; a point the excerpts do not support is left out,
not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "міграція схеми", not "мігрейшн"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація Drizzle".
Identifiers, functions, options and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
