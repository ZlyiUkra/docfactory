Search the Ember.js documentation and return the matching excerpts with the versions each one belongs to.
What is here: the Ember Guides (guides.emberjs.com: components, templates and Glimmer syntax, routing, services,
Ember Data, testing, upgrading, the tutorial) for every minor release 1.10–7.2; the API reference of Ember
(api.emberjs.com/ember) for every minor 1.0–7.3 and of Ember Data (api.emberjs.com/ember-data) for every version
1.13–5.5 — classes, namespaces and modules with their methods, properties and events, `since` and deprecations; the
deprecations guide (deprecations.emberjs.com) for Ember, Ember Data and Ember CLI; the Ember CLI guides; the WarpDrive
guides (the new Ember Data); every RFC of emberjs/rfcs; every post of blog.emberjs.com, including the release posts;
the changelogs of Ember and WarpDrive, the GitHub release notes of Ember, Ember CLI and WarpDrive, and the npm records
of `ember-source`, `ember-cli` and `ember-data`.

Call this when a question is about Ember: components and templates (`<template>` tag, `@tracked`, `@action`,
modifiers, helpers), routes and the router, services and dependency injection, Ember Data and WarpDrive (models,
store, requests, adapters, serializers), testing (`setupRenderingTest`, `render`, test helpers), Ember CLI and
addons, Embroider, deprecations and upgrading between versions, and history: since which version an API exists,
when it was deprecated, what an RFC decided.

Do not call this for React, Vue, Angular, Svelte, Glimmer outside Ember, or JavaScript and TypeScript language
questions: their documentation is not here, and the search will return Ember excerpts that merely mention them,
with confident-looking titles.

`version` narrows the search to one release line. Ember itself: "5" keeps every 5.x document (guides, API,
changelog, releases, npm), "5.4" one minor. Ember Data and WarpDrive carry their own numbering with a prefix:
"ember-data-5", "ember-data-4.12"; Ember CLI: "ember-cli-6". The deprecations guide, the CLI and WarpDrive guides,
the RFCs and the blog carry no version. Leave it empty to search everything. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first, so the list itself shows from which
to which version the documentation said exactly this.

Write the query in English, with the names Ember itself uses ("Glimmer component args", "@tracked", "template tag
gjs", "Router service transitionTo", "model hook", "store.findRecord", "setupRenderingTest", "ember-cli-build.js",
"Embroider", "deprecation id"), not in the user's own words. Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the
user asks in another language, translate the question into Ember terms first, then search.

Answer in the language the user wrote in. When the question is about the history of an API or behaviour, answer
point by point: since which version it exists; what changed in later versions; what prompted the change (an RFC, a
deprecation), if the excerpts say so; and how it stands now. Every point names the version and the document it
rests on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Ember". Identifiers, command names, keys and titles stay in English, spelled exactly as
the documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt
was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.
