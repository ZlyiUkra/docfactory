Search the documentation of ESLint, in English: the docs folder of the eslint/eslint repository
on the last release of every minor line of ESLint 8, 9 and 10 and of every older major from 0 to
7 -- using ESLint (the flat config eslint.config.js with files, ignores, extends,
languageOptions, linterOptions and plugins, the legacy .eslintrc config, configuring rules,
plugins, parsers, processors and languages, the command line, caching, formatters, bulk
suppressions, troubleshooting, the migration guides between majors), extending ESLint (custom
rules, plugins, parsers, language plugins, formatters, shareable configs), integrating it (the
Node.js API, Linter) and the reference of every core rule with examples of correct and
incorrect code; the eslint.org blog with the announcement of every release; the README of
every stable version of eslint; its GitHub release notes; the npm registry lists of eslint and
@eslint/js. Next to it: the README and CHANGELOG of eslint-plugin-react-hooks; typescript-eslint
(getting started, typed linting, shared configs, the parser and every @typescript-eslint rule),
eslint-plugin-react (every react/ rule) and eslint-plugin-jsx-a11y (every jsx-a11y/ rule) on the
last release of every major, with their changelogs, release notes and registry lists. Returns
the matching excerpts with the versions each one belongs to.

Call this when a question is about linting JavaScript or TypeScript with ESLint: what a rule
reports and its options, setting up or migrating eslint.config.js, defineConfig and
globalIgnores, sharing a config, writing a rule or a plugin, eslint-disable comments, the
recommended presets of the plugins, rules-of-hooks and exhaustive-deps, typed linting with
projectService, React and accessibility rules -- and above all when it is about versions: since
which version a rule or option exists, what changed between majors, which Node.js versions a
release needs. Example query: "no-unused-vars caughtErrors".

Do not call this for Prettier, Biome, Oxlint, stylelint, the TypeScript compiler itself, or
for React and the web platform: their documentation is not here, and the search will return
ESLint excerpts that merely mention them, with confident-looking titles. The page of each
eslint-plugin-react-hooks rule (purity, refs, set-state-in-effect...) lives on react.dev and
is not here either; the README and CHANGELOG of that plugin are.

`version` narrows the search to one minor line: "9.39" keeps ESLint 9.39.x. The plugins have
their own numbers -- typescript-eslint "8.71", eslint-plugin-react "7.37", eslint-plugin-jsx-a11y
"6.10", eslint-plugin-react-hooks "7.1" -- and the same number may belong to ESLint as well, so
read the title of every excerpt: it names its package. Blog posts carry the version "blog".
Leave `version` empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which
to which version the documentation said exactly this.

Which version to search first. For a question about how to do something today, pass the line
of the user's project or the most downloaded line -- "9.39" in the week the documentation was
collected: without it, the many editions of the same page, which differ by a line or two, fill
every place with older text. Search without `version` for history and migrations. For "since
which version", the rule pages say when a rule was added, and the release notes and the blog
name the version that introduced a feature.

Where the documentation lives. Core pages are named by their path (docs-src-use-configure-
configuration-files, docs-src-rules-no-unused-vars, docs-src-use-migrate-to-9-0-0,
docs-src-extend-custom-rules; before 8.x docs-user-guide-... and docs-rules-...); the plugins'
pages by their own paths, with the package in the title. README documents, release notes and
registry documents are titled by package.

Write the query in English, with the names the documentation uses (eslint.config.js,
defineConfig, languageOptions, globals, ignores, extends, rules, no-unused-vars, eqeqeq,
rules-of-hooks, exhaustive-deps, recommended-latest, @typescript-eslint/no-explicit-any,
projectService, react/jsx-key, jsx-a11y/alt-text). Everything here is English -- the excerpts,
the word index and the meaning index alike -- and the word index keeps only latin letters and
digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
at all and comes back with `found: 0`. When the user asks in another language, translate the
question into ESLint terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. Every answer says which package and which version
it is for. When the question is about a version change, a migration or compatibility, answer
point by point: which package and since which version; what changed; what the migration
requires; how it stands now -- each point with the document it rests on; a point the excerpts
do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "правило", "налаштування", not
"конфіга"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" --
say "документація ESLint". Identifiers, rule names, option names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that
came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
