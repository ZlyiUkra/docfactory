# expo — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Expo — фреймворк і платформу для застосунків на React Native — за
офіційною документацією всіх стабільних SDK, від SDK 23 (листопад 2017) до поточного: довідник модулів кожного SDK
разом з API, довідник `app.json`, посібники docs.expo.dev у стані на кінець кожного SDK (Expo Router, EAS, Expo Modules
API, config plugins, tutorial), приклади застосунків, шаблони create-expo-app, журнал змін, дописи про випуск SDK і
історія пакета в реєстрі npm. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека
тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

Сам React Native — ядро, компоненти, Turbo Native Modules і Fabric — має власний примірник
[`react-native`](../react-native/README.md).

## Навіщо вся історія

**SDK** (Software Development Kit) — набір модулів Expo, випущених разом під одним номером; номер SDK збігається з
мажорною версією пакета `expo`, і кожен SDK прив'язаний до певної версії React Native. За вісім років Expo змінився
докорінно: класичне збирання (`expo build`) поступилося EAS Build, «керований» і «голий» робочі процеси —
development builds і `prebuild` (нативні теки генеруються з конфігурації), `expo-av` — `expo-video` і `expo-audio`,
старий API файлової системи — новим, а модулі переписано на Expo Modules API. Старі SDK досі живуть: за тиждень SDK 57
завантажують ~53 % від усіх завантажень пакета, SDK 54 — 21 %, SDK 55 — 9 %, SDK 56 — 7 %. Питання часто звучить «як
це було в моєму SDK», і відповідь дає лише документація саме того SDK. Тож корпус — не одна редакція сайту, а вся його
історія, і кожен документ несе свої SDK.

Разом 7 701 документ; фрагментів в індексі — 35 632 (`expected_passages` у `checks.json`). 1 647 документів власних
фрагментів не дають: їхні розділи дослівно ті самі, що в інших редакціях, і злилися з ними.

SDK з документацією 35: 23–57. Довідник кожного SDK — від 81 сторінки (SDK 33–34) до 246 (SDK 57), посібників на SDK
— від 105 до 452. Бета SDK 58 і `unversioned` документації не дають, поки npm не перенесе на них мітку `latest`.

**Замір `quality`** на першому корпусі: по словах 6 із 10, за змістом 5, разом 6; десятка «як модель» — 10 із 10.
Перша десятка — переказ питання своїми словами, і промахи такі:

- **Власний нативний view.** «show my own native platform widget inside the app screen»: слово «widget» в Expo —
  віджети домашнього екрана, і обидва способи приносять сторінку `sdk-widgets`; `modules-native-view-tutorial` за
  змістом лише 29-та.
- **Сховище токена.** «keep the login token encrypted on the device»: сторінка SecureStore за змістом 11-та — слів
  «login» і «token» у ній немає, а «device tokens» зі сторінок про підпис застосунку тягнуть угору чуже.
- **Оновлення без перевірки магазину.** «ship a JavaScript fix to users without a new store review»: слово «review»
  приносить модуль StoreReview, а EAS Update за змістом аж 59-та.
- **Профілі збирання.** «different build settings for testers and for the store release»: перші місця беруть уроки
  збирання для внутрішнього розповсюдження, `eas.json` за змістом 35-та.

Ці промахи — межа малої моделі векторів, а не розмітки: перебір 48 поєднань полів `fusion_depth` (0–16),
`max_per_doc` (0–3) і `title_match` не підняв першу десятку жодного разу, а `title_match` ще й знижує «за змістом» до
4. Жодне з цих полів не ввімкнене.

Десятка «як модель» — запити назвами модулів, API, опцій і понять, як велить промпт, з `version "57"`, а один —
`Audio.Sound createAsync` з `version "50"`. На першому замірі вона дала 8 із 10. На «app.json ios bundleIdentifier»
довідника `app.json` не було серед п'яти: увесь він був одним розділом на 35 тис. символів. Тепер читач робить розділ
на кожну властивість верхнього рівня, як якорі на сайті, і `config-app#properties/ios` третій. На «EAS Update channel
runtimeVersion» першими стояли `eas-update-override` і `eas-update-channel-surfing` — сторінки саме про канал і
версію середовища; знаюча людина прийняла б їх як відповідь, і їх дописано в ціль.

Поле `max_per_doc` заміряно 0/1/2/3: перша десятка 6/6/6/6 разом, «як модель» 10/10/10/10 — поле не ввімкнене.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df expo <крок>`.

Примірник додав два читачі (`expo-sdk-history`, `expo-guides-history`) і спільний помічник `_typedocjson`, що робить
з JSON TypeDoc текст розділу API. `ghexamples` дістав поле `folder` (тека прикладів; порожня — корінь репозиторію),
`changelog-dated` — довге тире в заголовку версії («## 57.0.0 — 2026-07-08»), а `html-pages` — поле `follow: false`:
документами стають лише задані сторінки, без посилань з них (допис про випуск посилається на сусідні дописи, і без
поля кожен із них потрапив би в корпус ще раз — з чужим SDK).

Особливості, які варто знати:

- **API модулів у сторінках немає.** Сторінка ставить `<APISection packageName="expo-camera" />`, а сайт малює розділ
  із JSON, згенерованого TypeDoc з коду пакета того самого SDK. Тут цей JSON стає текстом: кожен компонент, хук,
  метод, клас, тип і enum — підрозділ `### Назва` із сигнатурою, параметрами, платформами й типовими значеннями. Так
  само довідник `app.json` розгортається з JSON Schema, а `eas.json` — зі схем EAS. Дані TypeDoc сайт має з SDK
  ~41; у старших SDK API написано просто в сторінках.
- **Сторінка з даними — окремий документ на кожен SDK.** Однаковий текст сторінки з різним API — різні тексти, тож
  сторінки `sdk/` і `config/` у SDK з даними не зливаються між SDK у документ; однакові розділи все одно зливаються
  у фрагменти корпусу. Ім'я такого документа несе два хвости — суму тексту сторінки й суму даних
  (`sdk-camera-1a2b3c4d-5e6f70`), і `slug_rewrite` у `config.json` зрізає обидва: слаг `sdk-camera` той самий в усіх
  SDK, тож за ним шукають і на ньому стоять цілі `quality`.
- **Посібники версії не мають**, але змінюються з кожним SDK. Тут вони — у стані на кінець кожного SDK (для
  найновішого — вершина гілки); незмінна сторінка — один документ з усіма SDK, де вона була такою. До SDK ~37
  посібники жили в теці версії, і для тих SDK вони приходять разом із довідником.
- **Теки старих SDK сайт прибирає.** На гілці лежать лише SDK 54–58; кожна прибрана тека береться зі знімка перед
  комітом, що її видалив, з тим самим кроком назад, що й у `react-native`, якщо коміт лишив у теці залишок.
- **SDK 58 — бета** (мітка `next` у npm), `unversioned` — документація в розробці: не беруться. Реєстр публікує бету
  без суфікса («58.0.0»), тож джерело `expo-npm` відкидає її явно, виразом `^58\.` у `skip_versions`. Так само не
  беруться японський переклад (`ja/`) і тека `react-native/` старих SDK — копія документації React Native.
- **Дописи про випуск** є на expo.dev лише з SDK 50; старші анонси жили в блозі на Medium і в корпус не входять.

## Межі, про які треба пам'ятати

Ядра React Native, React Navigation, Reanimated та інших бібліотек спільноти тут немає — лише те, що про них пише
документація Expo; для React Native є примірник `react-native`. Документація SDK до 23 (2017) у репозиторії не
збереглася. Посилання документів прибраних SDK і старих редакцій посібників ведуть на GitHub, бо сайт їх уже не
показує. Відео й інтерактивні приклади Snack у тексті лишаються лише підписом чи кодом.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/expo-corpus-2026-10-11.tar.gz` (7 701 текст і паспорт; перед
видаленням розпакований окремо й звірений із диском — нуль розбіжностей). В історії git текстів немає ніде. Архів
лежить лише на цій машині.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/expo-corpus-2026-10-11.tar.gz -C instances/expo
./df expo smoke
```

**Як знову винести** — після оновлення, коли `vectors` і `smoke` пройшли (вони ж збирають свіжий кеш):

```
ls -l instances/expo/index/passages.json       # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/expo-corpus-РРРР-ММ-ДД.tar.gz -C instances/expo corpus
find instances/expo/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/expo/index/passages.json > instances/expo/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти» і «Як повернути тексти».

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»): звірка індексу з документами і звірка паспорта з файлами.

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/expo/index/passages.json.gz`, далі
`./df expo vectors` заллє колекцію Qdrant.

## Установка venv

```
cd instances/expo
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df expo sources --why   # перелік джерел і білий список
./df expo refresh         # завантажити все задеклароване (~2.5 години)
./df expo manifest        # оновити паспорт
./df expo setup           # Qdrant чи пошук лише по словах
./df expo vectors         # залити корпус у docs-expo
./df expo smoke           # перевірки
```

Перші ~5 хвилин `refresh` журнал мовчить, а `corpus/` порожній: читачі проходять коміти й знімки теки `docs/`
репозиторію expo/expo і лише потім починають писати файли. Без токена GitHub перелік ішов би годинними вікнами по 60
звернень.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df expo serve          # порт 8819
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8819/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user expo-docs http://127.0.0.1:8819/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `expo-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
