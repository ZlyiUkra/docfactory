# Оновлення корпусу expo

Дві різні роботи: звичайне оновлення, коли вийшов новий SDK, і збирання з нуля. Порядок усередині кожної важливіший за
самі команди.

Головне правило: **SDK приходять самі, з реєстру npm.** Обидва читачі сайту беруть перелік SDK з
https://registry.npmjs.org/expo: SDK — мажорна версія пакета `expo`, найновіший стабільний — мажор мітки `latest`.
Читач `expo-sdk-history` шукає теку `docs/pages/versions/vNN.0.0` кожного SDK у репозиторії expo/expo — на вершині
гілки, а якщо теку вже прибрано — зі знімка перед комітом, що її видалив. Читач `expo-guides-history` бере стан
посібників на кінець кожного SDK. Новий SDK з'являється в корпусі сам, щойно npm перенесе на нього мітку `latest`.
Журнал змін, дописи про випуск і реєстр npm так само читають актуальний стан; руками дописують лише допис про
випуск нового SDK, гілку шаблонів і межу бети в реєстрі npm (крок 2).

Друге правило: **новий SDK змінює й старі документи.** Документ — неповторний текст сторінки, а в рядку `# версія:`
стоять усі SDK, де сторінка була саме такою. Тож після нового SDK корпус перезаписують цілком (`refresh` без
`--missing`): інакше старі тексти не дізнаються, що дожили до нового SDK, і фільтр `version` їх не знайде. Посібники
найновішого SDK — вершина гілки, тож правка сайту змінює корпус і без нового SDK.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі; лише
`vectors` прибирає з колекції Qdrant точки, чиїх фрагментів більше немає в корпусі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшов новий SDK

**Крок 1. Чи змінилася розкладка сайту.** Сайт тримає теки SDK у `docs/pages/versions/vNN.0.0`, дані API — у
`docs/public/static/data/vNN.0.0`, схеми — у `docs/public/static/schemas/vNN.0.0`. Якщо сайт перенесе їх, у переліку
нового SDK не з'явиться жодної сторінки або розділи API лишаться порожніми: тоді треба поправити шаблони `_FOLDERS` і
`_DATA` у `engine/readers/expodocs.py`. Нові компоненти MDX, чий зміст лежить у властивостях, без правки читача
губитимуть текст — їх видно в корпусі як рядки без змісту на місці прикладу чи таблиці.

**Крок 2. Допис про випуск і шаблони.** Допис про випуск нового SDK (expo.dev/changelog/sdk-NN) — нове джерело
`expo-release-sdk-NN` за зразком `expo-release-sdk-57` (з полями `follow: false` і `end`), його id — у родину
`expo-release` у `config.json`. Шаблони create-expo-app беруться з гілки `sdk-NN`: замінити гілку в `url`, `version` і
`title` джерела `expo-templates`, так само `version` і `title` джерела `expo-examples`. Реєстр npm публікує бету
наступного SDK без суфікса («58.0.0» під міткою `next`), тож джерело `expo-npm` відкидає її виразом `^58\.` у
`skip_versions`: коли SDK 58 стане `latest`, вираз замінюють на `^59\.`.

**Крок 3. SDK за замовчуванням.** `prompts/search.txt` (абзаци «Which SDK to search first» і «Every answer says which
SDK it is for») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "57"`. SDK вибирають за
завантаженнями з npm за тиждень, а не за номером:

```
curl -s https://api.npmjs.org/versions/expo/last-week
```

Поки SDK 57 завантажують найбільше, він лишається основним; коли інший SDK його випередить — замінити номер у
промптах і в десятці `quality_model` у `checks.json`.

**Крок 4. Завантажити.**

```
./df expo sources --why
./df expo refresh
./df expo manifest
./df expo vectors
./df expo smoke
# Ctrl+C у терміналі з serve, і знову: ./df expo serve
```

## 2. Особливі SDK

- **SDK 23–~32** — теки версій лежали в `docs/versions/`, а не в `docs/pages/versions/`; читач шукає обидва місця і
  бере те, де тека жила пізніше. Документації SDK до 23 у репозиторії немає.
- **SDK до ~37** — посібники жили в теці версії (`guides/`, `workflow/`); для них окремого знімка посібників немає.
- **SDK з даними TypeDoc** — сторінки `sdk/` і `config/` стають окремим документом на кожен SDK (поле `scan` джерела
  `expo-sdk`), бо їхній текст залежить від файлів даних.
- **Бета наступного SDK** (мітка `next`) і `unversioned` не беруться, поки npm не перенесе `latest`. Читачі сайту
  дивляться на мітку `latest` самі, а для `expo-npm` межу ставить вираз у `skip_versions` (крок 2 вище).

## 3. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік ~70 комітів і ~60 знімків теки
`docs/` іде годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df expo refresh > instances/expo/out/refresh.log 2>&1 &
```

Перші ~5 хвилин журнал мовчить, а `corpus/` порожній: читачі проходять коміти й знімки теки `docs/`. Стан видно за
кількістю файлів: `ls instances/expo/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df expo quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Що це означає тут:

- **Поточний SDK — 57.** Що міняти, коли інший SDK стане найпопулярнішим, — крок 3 розділу «1. Вийшов новий SDK»
  вище.
- **Правила промпту, що вже є:** спершу SDK 57; запит — назвою модуля, API, опції чи поняття, а не описом; питання
  про історію — журнал змін і допис про випуск SDK; кожна відповідь каже, для якого SDK вона, а без названого SDK —
  відповідає для SDK 57 і пропонує назвати свій.
- **Останній результат** — у README, абзац «Замір `quality`».
