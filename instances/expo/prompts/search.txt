Search the official documentation of Expo, the framework and platform for React Native apps --
the site docs.expo.dev for every stable SDK from SDK 23 (2017) to the current one: the reference of
every Expo SDK module with its API (methods, components, hooks, props, types, config plugin
options, permissions), the app.json reference, and the guides as they stood at the end of each
SDK (Expo Router, EAS Build, Submit, Update and Workflows, the Expo Modules API for writing your
own native modules and views in Swift and Kotlin, config plugins, development builds, push
notifications, the tutorial); plus the example apps of expo/examples, the create-expo-app
templates, the change log, the SDK release posts and the npm registry history of the expo
package. Return the matching excerpts with the SDK versions each one belongs to.

Call this when a question is about Expo itself -- creating and running a project
(create-expo-app, Expo Go, development builds, prebuild and Continuous Native Generation), app
configuration (app.json, app.config.js, eas.json), Expo Router (file-based routes, layouts,
stacks, tabs, links, typed routes, API routes, server rendering), SDK modules (expo-camera,
expo-image, expo-file-system, expo-sqlite, expo-notifications, expo-location, expo-av,
expo-video, expo-audio, expo-secure-store, expo-updates, expo-auth-session, expo-font,
expo-splash-screen, expo-sensors, expo-media-library and the others), permissions, EAS Build
profiles and credentials, app signing, submitting to the App Store and Google Play, EAS Update
channels and runtime versions, and native code -- the Expo Modules API (Module definition, Name,
Function, AsyncFunction, Events, Property, View, Prop, shared objects, lifecycle listeners,
AppDelegate subscribers, autolinking, create-expo-module), config plugins and mods, adding a
third-party native library. Example query: "Expo Modules API native view tutorial".

Do not call this for React Native core (View, FlatList, StyleSheet, Turbo Native Modules,
Fabric), React Navigation, Reanimated or other community libraries, nor for React itself, beyond
what the Expo documentation says about them: their own documentation is not here, and the search
will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one SDK: "57" keeps the SDK 57 documents (and the 57.x change
log and npm versions), "5" keeps SDK 5 only (not 50-59); leave it empty to search everything.
Every excerpt comes back with `versions`: each SDK whose documents contain this exact text,
newest first -- text that stayed the same across SDKs is returned once, with all of them listed,
so the list itself shows from which to which SDK the documentation said exactly this.

Where the documentation lives. Module reference pages are titled as on the site ("Camera",
"FileSystem", "Notifications", "SQLite") and end with the API section: one "### Name" entry per
component, hook, method, class, type and enum, with signatures, parameters, platforms and
defaults. "app.json / app.config.js" lists every app config property. Guides keep their site
titles ("Tutorial: Create a native module", "Module API Reference", "Introduction to Expo
Router", "Configure EAS Build with eas.json"); up to about SDK 37 the guides lived inside each
SDK's folder, later they are versioned by the state they had at the end of each SDK. Examples are
titled "Example: with-camera", templates "Example: expo-template-default", change-log entries
"Expo Changelog: 57.0.0 - ...", release posts by their headline ("Expo SDK 57").

Which SDK to search first. For a question about how to do something today, pass `version` "57"
-- the most downloaded SDK on npm when this documentation was built (SDK 58 was still in beta):
without it, the many editions of older pages can take places with the current ones. If the
user's project runs another SDK, pass that SDK instead -- modules, configuration and workflows
changed a lot: classic builds (expo build) gave way to EAS Build, the managed and bare workflows
to development builds and prebuild, expo-av to expo-video and expo-audio, the old file system
API to the new one, and modules were rewritten on the Expo Modules API. Search without `version`
when the question is about history, or when the SDK gave nothing that answers.

Name the module, API, option or concept the way the documentation titles it, not in the user's
own words: "Expo Modules API", "AsyncFunction", "config plugin withAndroidManifest",
"useCameraPermissions", "eas.json build profile", "runtimeVersion policy", "expo-router Stack",
not "how to call my Swift code". For a question about when something appeared, changed or
disappeared, search more than once: without `version` first, to find the change-log entry or
release post that names the exact SDK, then with the SDKs around it, to see how the
documentation described it before and after.

Write the query in English, with the names Expo itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into Expo terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which SDK it is for. When the user did not name one, answer for the default,
Expo SDK 57, say so in the answer ("for Expo SDK 57"), and add that for a precise answer about
another SDK the user can name it. When the excerpts behind a statement come only from older SDKs,
name those SDKs instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which SDK it exists and which release introduced it; what
changed in later SDKs; what prompted the change, if the excerpts say so; and how it stands in the
current SDK -- recommended, deprecated, or removed and replaced by what. Every point names the SDK
and the document it rests on; a point the excerpts do not support is left out, not guessed. When
that language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from
English: plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not
"ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація Expo". Identifiers, API names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
