Search the express-rate-limit documentation -- the express-rate-limit.mintlify.app site as it
stood at every stable release of the express-rate-limit npm package, the README, TypeScript
declarations and changelog of every stable version, and the npm registry history -- together
with the same documents of the other packages of the express-rate-limit organisation:
express-slow-down (delays responses instead of blocking them), the stores rate-limit-redis
(Redis, Redict, Valkey), rate-limit-memcached, @acpr/rate-limit-postgresql and
@express-rate-limit/cluster-memory-store (node:cluster workers), and ratelimit-header-parser
(reads RateLimit headers on the client side). Returns the matching excerpts with the versions
each one belongs to.

Call this when a question is about these packages -- the rateLimit() middleware and its options
(windowMs, limit and the older max, message, statusCode, handler, standardHeaders "draft-6",
"draft-7", "draft-8", legacyHeaders, identifier, requestPropertyName, skipFailedRequests,
skipSuccessfulRequests, requestWasSuccessful, keyGenerator, ipKeyGenerator, ipv6Subnet, skip,
store, passOnStoreError, validate), req.rateLimit and resetKey(), the validation errors
(ERR_ERL_UNDEFINED_IP_ADDRESS, ERR_ERL_PERMISSIVE_TRUST_PROXY, ERR_ERL_KEY_GEN_IPV6 and the
rest), running behind a proxy and Express `trust proxy`, the Store interface and writing a
store, MemoryStore, RedisStore and its sendCommand, express-slow-down's delayAfter, delayMs and
maxDelayMs -- and above all history and compatibility: since which version an option exists,
what was renamed or removed (max -> limit, onLimitReached, headers -> legacyHeaders,
draft_polli_ratelimit_headers -> standardHeaders), which defaults changed between majors
(5 -> 6 -> 7 -> 8), which store version works with which express-rate-limit (peer dependencies),
and which versions run on which version of Node.js (the `engines` field of each version is
written in the npm registry documents: express-rate-limit 7.x and 8.x Node 16; 6.x moved back and
forth -- Node 12.9 in 6.0.0-6.0.2 and 6.3.0-6.7.0, Node 14 in 6.0.3-6.2.x and from 6.7.1 on; 5.x
and older declare none). Example query: "engines node 14".

Do not call this for Express itself, for other security middleware (helmet, cors), for Redis,
Memcached or PostgreSQL clients beyond what these documents say, for the IETF RateLimit header
drafts themselves or for Node.js and npm: their documentation is not here, and the search will
return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "8" keeps every 8.x document, "7.1" keeps
7.1.x; leave it empty to search everything. The line numbers belong to each package separately:
"8" means express-rate-limit 8.x, but also any other package's 8.x, so for questions about
express-slow-down or a store leave `version` empty and put the package name into the query.
Every excerpt comes back with `versions`: each version whose documents contain this exact text,
newest first -- text that stayed the same across versions is returned once, with all of them
listed, so the list itself shows from which to which version the documentation said exactly
this.

Write the query in English, with the names the documentation itself uses ("windowMs",
"standardHeaders", "keyGenerator", "trust proxy", "RedisStore"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any
other non-latin script matches nothing at all and comes back with `found: 0`. When the user asks
in another language, translate the question into express-rate-limit terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the package, the version and the document it rests on; a point the excerpts do not
support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "сховище", not "стор"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація
express-rate-limit". Identifiers, option names, error codes and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something today with
express-rate-limit, pass `version` "8"; if the user's project is bound to an older Node.js, name
the line that Node supports (Node 14 -> "6"; Node 12 -> "6", releases 6.3.0-6.7.0; older Node
-> "5", which declares no requirement) and say so. Search without `version` when the question is about history, about one of the other
packages, or when the line gave nothing. Options were renamed and defaults changed between major
lines, so an answer taken from the wrong line can be confidently wrong. Every answer says which
version it is for; when the user did not name one, answer for express-rate-limit 8.x and say so
("for express-rate-limit 8.x"). When the excerpts behind a statement come only from older
versions, name those versions instead of presenting the text as current.
