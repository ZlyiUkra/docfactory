# Оновлення корпусу fabricjs

README (`npm-readme-*`) і реєстр (`npm-*`) беруть версії з опису пакетів у реєстрі npm, тож новий реліз fabric чи
fabricjs-react потрапляє туди сам. Журнал змін (`changelog`) і релізи GitHub (`releases`) читаються щоразу заново з
гілки `master` і з API. Довідник API (`api`) бере перелік сторінок із сайтмапу сайту, тож нова сторінка класу
з'являється сама. Передрелізи README і релізів не беруться (`skip_versions: "-"` у README, `"stable": true` і `skip`
у релізах).

Руками оголошено:

- **Посібник, код прикладів, код демонстрацій, README пакетів** (`guides`, `guides-code`, `demos-code`,
  `packages`): поле `tags` тримає один рядок «SHA коміту → версія». Тека сайту є лише в гілці `master`, у тегах
  релізів її немає, тому знімок — це коміт гілки `master`, а його мітка — остання на той день версія fabric з реєстру
  npm (`"ab604137…": "7.4.0"`). Щоб оновити, беруть SHA найновішого коміту
  (`git ls-remote https://github.com/fabricjs/fabric.js master`) і мітку `latest` пакета fabric, і замінюють рядок у
  всіх чотирьох джерелах. Старий рядок не лишають: два знімки під різними мітками видавали б учорашній текст за
  документацію старої версії.
- **Адреси сторінок посібника** (поле `site` джерела `guides`): кожна сторінка має власний рядок «файл → адреса на
  fabricjs.com». Після оновлення адреси звіряють із `https://www.fabricjs.com/sitemap-0.xml`: нова сторінка потребує
  нового рядка, інакше в цитаті стоятиме адреса файла на GitHub.
- **Мітка довідника API** (`api`, поле `version`): сайт показує довідник лише поточної версії, тому мітку міняють
  разом із міткою посібника.
- **Старий сайт** (`api-5`, `demos-5`): перелік сторінок fabric5.fabricjs.com записано в `pages`. Сайт заморожено,
  і оновлювати його не треба; мітка `5.5.2` — остання версія лінії 5.
- **Новий пакет чи обгортка** — нові джерела `npm-readme`, `npm-versions` і, якщо є релізи, `ghreleases` за зразком
  fabricjs-react, з власним префіксом версії.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df fabricjs refresh npm-readme-fabric npm-fabric changelog releases   # або джерела fabricjs-react
./df fabricjs refresh --missing    # джерела, яких не названо, лише докачуються
./df fabricjs manifest
./df fabricjs vectors
./df fabricjs smoke
# Ctrl+C у терміналі з serve, і знову: ./df fabricjs serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі README стоять усі версії, де текст був таким, тож
новий реліз змінює й старі документи (незмінний README дописує нову версію в рядок `# версія:`).

Тег нового релізу перевіряють оком: репозиторій пише його трьома цифрами поспіль (`v740`), і поле `tag_version`
джерела `releases` виводить із нього 7.4.0. Тег версії з двозначним числом (скажімо, 7.10.0) цей вираз не розбере
правильно — тоді вираз у `tag_version` доведеться доповнити.

## Оновився сайт

```
./df fabricjs refresh guides guides-code demos-code packages api   # після заміни SHA і міток у sources.json
./df fabricjs manifest
./df fabricjs vectors
./df fabricjs smoke
```

Ім'я файла сторінки посібника містить початок хеша її тексту, тому змінена сторінка лягає новим файлом поруч зі
старим. Файли попереднього знімка, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш
ніж рахувати вектори: інакше пошук знаходив би обидві редакції сторінки. Сторінки довідника API хеша в імені не мають
і перезаписуються на місці. Сховище сирого `raw/` повертається з архіву разом із текстами, тож після правки читача
тексти перебудовуються без мережі: `./df fabricjs build <id>`.

Довідник API читається з `https://www.fabricjs.com/sitemap-0.xml`: адреса без `www` відповідає перенаправленням, а
оновлювач не йде за перенаправленням на адресу, якої в `sources.json` немає.

Якщо змінилися найпоширеніші лінії (на 18.11.2026 — Fabric.js 7, близько 61 % завантажень; Fabric.js 6 — 18 %;
Fabric.js 5 — 14 %):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінії за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"7"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторію і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df fabricjs quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
