Search the documentation of Flux -- the GitOps toolkit for Kubernetes from the CNCF (site fluxcd.io, repositories
fluxcd/flux2, fluxcd/website and the controllers) and of what is used together with it: Flagger (progressive
delivery: canary, A/B and blue/green releases), Flux Operator (controlplaneio-fluxcd/flux-operator, with its Helm
charts) and the Terraform provider for Flux (fluxcd/terraform-provider-flux). The corpus holds every page of the
fluxcd.io site as it stood in the branch of every minor of Flux 2, 2.0 to 2.10, together with the blog: installation
and bootstrap (`flux bootstrap` for GitHub, GitLab, Gitea, Bitbucket, plain Git), the concepts, the guides (repository
structure, Helm releases, Kustomize, image update automation, notifications, webhook receivers, Mozilla SOPS and other
secret management, multi-tenancy, sharding, monitoring, OCI artifacts), the cheatsheets, the migration guides (Flux v1
to v2, API versions), the use cases, the security and the release notes and supported releases. Because the site
pulls the CRD specifications from the controllers at build time, the corpus holds them from the controllers' own
repositories at the last tag of every minor (versions written "source-controller-1.10.1"): source-controller
(GitRepository, OCIRepository, HelmRepository, HelmChart, Bucket), kustomize-controller (Kustomization),
helm-controller (HelmRelease), notification-controller (Provider, Alert, Receiver), image-reflector-controller
(ImageRepository, ImagePolicy), image-automation-controller (ImageUpdateAutomation) and source-watcher, with their API
references, README and CHANGELOG. It also holds the documentation of Flux 0.x from the flux2 repository (the early
minors, with the `flux` CLI reference), the stable GitHub releases of Flux, and the documentation, README and releases
of Flagger (versions "flagger-1.45.0"), Flux Operator (versions "flux-operator-0.62.0") and terraform-provider-flux
(versions "terraform-1.10.0"). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about Flux as it describes itself -- how to bootstrap Flux into a cluster, how to point
it at a Git repository, an OCI artifact or a Helm repository, how to reconcile Kustomizations and HelmReleases, order
them with `dependsOn`, substitute variables, decrypt secrets with SOPS, send alerts and receive webhooks, update
image tags in Git automatically, set up multi-tenancy, run canary releases with Flagger, install Flux with Flux
Operator or Terraform -- and history: since which version a field, flag or API version exists, what changed between
versions (the release notes, the changelogs and the migration guides list it).

Do not call this for Kubernetes, Helm, Kustomize, SOPS, Terraform, Argo CD or the Git hosting services as their own
projects: their documentation is not here -- these pages only show how Flux is used with them -- and the search will
return excerpts that merely mention them, with confident-looking titles. The Go source code is not here either; nor
is Flux v1 (fluxcd/flux), archived in 2022.

`version` narrows the search to one release line: a line of one number keeps every document of that major of Flux
("2" keeps 2.x), two numbers keep a minor ("2.6"), three an exact version ("2.10.0"); the controllers, Flagger, Flux
Operator and the Terraform provider carry a prefix ("kustomize-controller-1", "helm-controller-1.4", "flagger-1",
"flux-operator-0", "terraform-1"), so a bare number keeps only Flux itself. Pages unchanged across versions carry all
of them. Every excerpt comes back with `versions`: each version whose documents contain this exact text, newest
first.

Write the query in English, with the names the documentation itself uses ("GitRepository",
"OCIRepository", "HelmRepository", "HelmChart", "Bucket", "Kustomization", "HelmRelease", "dependsOn",
"prune", "healthChecks", "postBuild", "substituteFrom", "decryption", "sops", "interval", "suspend", "Provider",
"Alert", "Receiver", "ImageRepository", "ImagePolicy", "ImageUpdateAutomation", "flux bootstrap github",
"flux reconcile", "multi-tenancy", "Canary", "analysis", "FluxInstance", "ResourceSet", "flux_bootstrap_git"), not in the
user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the
question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація Flux". Identifiers, parameters and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. Flux supports its newest minors (2.10.0 is the newest); answer for 2.x: search
without `version` first, then with "2" if 0.x pages crowd the results; when the user names their version, search
that line. A CRD question is answered from the controller's own specification -- the newest line of the controller
(for example "kustomize-controller-1") unless the user's API version is older. Every answer says which version it is
for.
