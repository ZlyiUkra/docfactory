# foundry — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про Foundry — набір інструментів на Rust від foundry-rs для
смартконтрактів Ethereum: forge (збирання, тести, фазинг- та інваріантні тести, форки, покриття, газ, скрипти
Solidity, розгортання й верифікація, лінтер, форматер), cast (виклики, транзакції, гаманці, ABI з командного рядка),
anvil (локальний вузол) і chisel (REPL Solidity), а ще читкоди, стандартна бібліотека forge-std і налаштування
`foundry.toml`. Джерела — сайт getfoundry.sh (Foundry Book, репозиторій foundry-rs/book), репозиторії
foundry-rs/foundry і foundry-rs/forge-std на GitHub і реєстр npm, лише англійською. Код спільний і лежить у
`../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо

Факультатив «крипта» планів React, NestJS і Next.js закінчується смартконтрактом: його пишуть, тестують і розгортають
Foundry, а застосунок читає через Viem і Wagmi. Foundry змінюється щомісяця: у 1.0 змінилися налаштування компілятора
за замовчуванням і поведінка `vm.expectRevert`, зникли тести `testFail`; у 1.3 з'явилися лінтер `forge lint` і фазинг
інваріантів за покриттям, у 1.8 — символьні тести; кожен випуск додає читкоди й ключі `foundry.toml`. Тож потрібен
текст документації версії, з якою працюєш, а не пам'ять моделі.

**Що є що.** **forge** — збирає й тестує контракти, запускає скрипти Solidity й розгортає. **cast** — звертається до
мережі з командного рядка: читає стан, надсилає транзакції, кодує й розкодовує ABI. **anvil** — локальний вузол
Ethereum для розробки й тестів, уміє «відгалужувати» (fork) стан справжньої мережі. **chisel** — інтерактивна консоль
Solidity. **Читкод** (cheatcode) — функція спеціальної адреси `vm`, доступна лише в тестах і скриптах: підмінити
відправника (`vm.prank`), час (`vm.warp`), баланс (`vm.deal`), очікувати відмову (`vm.expectRevert`) чи подію
(`vm.expectEmit`). **forge-std** — стандартна бібліотека тестів: контракти `Test` і `Script`, перевірки, помічники
(`deal` для токенів ERC-20, `bound`, `makeAddr`) і інтерфейс усіх читкодів `Vm.sol`. **foundryup** — встановлювач:
ставить найновішу стабільну версію, нічну — лише з `--install nightly`.

У яких фазах і днях планів навчання він потрібен — див. [../../docs/learning-map.md](../../docs/learning-map.md).

Разом 4 424 документи; фрагментів в індексі — 13 822 (`expected_passages` у `checks.json`). Фрагменти — це шматки
документів між заголовками, по яких іде пошук. Документ сторінки — неповторна редакція: сторінка разом із тим, що вона
вставляє, і в рядку `# версія:` стоять усі версії, де вона була саме такою. Однаковий текст різних версій лягає одним
фрагментом з усіма цими версіями, тож 999 редакцій часів mdBook додають лише 1 127 фрагментів.

Замір `quality`: перша десятка (питання своїми словами, без версії) — по словах 8 із 10, за змістом 8, разом 7; друга,
«як модель» (назви читкодів, команд, прапорців і ключів, як велить промпт), — 10 із 10. Перший замір дав 8 із 10:
сторінка з однією назвою лежала в трьох періодах сайту за трьома різними шляхами, і стара редакція займала місце нової
(див. «Особливості»). До двох цілей додано справжні відповіді, яких бракувало: питання «`deal` для балансу ERC-20 зі
`stdCheats`» прийняло ще розділ «ERC20 token deals» сторінки читкоду `deal` і сам `StdCheats.deal` у коді forge-std;
питання «посунути час блоку вперед у тесті» — ще помічник forge-std `skip`. `max_per_doc` 1 піднімає першу десятку по
словах із 6 до 8 і нічого не забирає, тож увімкнений; `fusion_depth` 10 і 20 нічого не міняє.

## Що в цій теці

- `corpus/` — лише паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа (тексти — в архіві,
  див. нижче).
- `index/passages.json.gz` — стиснений кеш фрагментів, з якого підіймається сервер.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями, спільний ключ сторінок трьох періодів
  сайту (`slug_rewrite`), родина джерел сайту (`families`), `max_per_doc`, глибина лінії версій і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (дерева комітів і тегів, релізи); `.mcp.json` — запис
  HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df foundry <крок>`.

**Сайт не має версій.** Foundry Book — одна жива гілка без тегів. Версію сторінці дає день виходу: для кожної
стабільної версії Foundry береться останній коміт книжки перед публікацією її релізу, а для 1.8.5 — стан сайту на
день збирання (12.10.2026). Так сторінка, змінена в березні 2026, належить 1.7.0 і новішим. 1.3.3 і 1.3.4 вийшли на
тому самому коміті книжки. Для теперішнього періоду в шапці документа стоїть адреса сторінки getfoundry.sh; для двох
старших — файл на GitHub на тому коміті, бо сайту того часу вже немає. Посилання у відповідях ведуть на getfoundry.sh,
github.com і registry.npmjs.org.

Особливості, які варто знати:

- **Три періоди сайту.** До травня 2025 книжка збиралася mdBook із теки `src/`, з 29.05.2025 — Vocs із теки
  `vocs/docs`, з 03.02.2026 — Vocs із кореня (`src/pages`). Сторінки за ці роки переїжджали: `cheatcodes/deal.md`
  стала `reference/cheatcodes/deal.mdx`, `reference/forge/forge-script.md` і `forge/reference/forge-script.mdx` —
  `reference/forge/script.mdx`. Поле `slug_rewrite` у `config.json` дає їм спільний ключ, а родина `book` поля
  `families` зводить три джерела в одне: стара редакція не займає у видачі місця нової, а однаковий текст зливається в
  один фрагмент.
- **Вставки mdBook.** Сторінки довідника CLI вставляють спільні шматки опцій (`{{#include common-options.md}}`),
  посібники — код прикладів із теки `projects/` (з областю між `ANCHOR: назва` і `ANCHOR_END: назва`) і записаний вивід
  команд. Поле `mdbook` читача `ghdocs-history` (модуль `_mdbook`) їх розкриває; самі шматки опцій і зміст `SUMMARY.md`
  окремими документами не беруться.
- **Вставки Vocs.** Код прикладів, `foundry.toml` і записаний вивід команд (`~/snippets/output/…`) вставляються в
  блоки коду рядком `// [!include …]`; модуль `_vocs` їх розкриває і знімає кольори терміналу з виводу. Одна вставка
  в сторінці про читкоди періоду 1.2.2–1.5.1 має помилку в самому джерелі (`:output}]`) і лишається рядком.
- **Код forge-std ділиться на розділи.** `Vm.sol` — 178 тисяч символів, інтерфейс усіх читкодів з описами NatSpec.
  Поле `outline` читача `ghcode-history` ділить файл Solidity на контракти, групи читкодів (`// ======== Environment
  ========`) і члени разом з описом над ними, а `max_file` пускає такий великий файл. Згенеровані `console.sol`,
  `console2.sol` і `safeconsole.sol` (тисячі перевантажень `console.log`) не беруться.
- **Дві нумерації.** forge-std має свої версії (1.8.0 вийшла 2024 року, Foundry 1.8.0 — 2026), тож документи
  forge-std мають мітку «forge-std-1.17.0», а сторінки довідника forge-std на сайті — назву «forge-std: `deal`», бо
  поруч є однойменні сторінки читкодів.
- **Пропущені версії.** 1.6.0 вийшла лише як 1.6.0-rc1; у 1.8.2 є тег, але релізу немає. Обидві не беруться, як і
  нічні збірки, передрелізи `-rc` і теги `stable`, `rc`. До 0.3.0 (19.12.2024) стабільних версій не було зовсім.
- **npm відстає.** Пакети `@foundry-rs/*` виходять з 2025 року паралельно з foundryup; версій 1.8.x у реєстрі немає,
  останній стабільний випуск там — 1.7.1.

## Версії у відповіді

Фільтр `version` бере лінію: `"1.8"` — усе 1.8.x, `"1"` — усе 1.x, `"0.3"` — першу стабільну версію; для forge-std —
`"forge-std-1.17"`, `"forge-std-1"`. Голе `"1.8"` forge-std не бере. Без фільтра сторінка, що є в кількох версіях,
показується один раз — найновішою редакцією. Нотатки релізів мають версію свого релізу. Глибина лінії — два числа
(`version_line_depth` 2), тож перелік завантаженого називає лінії 0.3, 1.0 … 1.8.

Без названої версії промпт велить відповідати для найновішої стабільної, Foundry 1.8 (1.8.5): саме її ставить
foundryup. Завантаження npm тут нічого не кажуть — Foundry ставлять здебільшого не з npm.

## Сховище сирого

Під час оновлення примірник тримає ще й сирі відповіді — у теці `raw/`, поза git (сховище ввімкнене за
замовчуванням). Правка читача тоді не вимагає нового завантаження: `./df foundry build` збирає тексти зі сховища без
мережі. Попередні версії файлів не видаляються, а переїжджають у `raw/_old/<день>/`. Між оновленнями сховище, як і
тексти, лежить лише в архіві: серверу воно не потрібне. Устрій — у [../../UPDATE.md](../../UPDATE.md), розділ про
`refresh`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/foundry-corpus-2026-10-13.tar.gz` (4 424 тексти, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском). В історії git текстів немає ніде.
Архів лежить лише на цій машині. Сховище `raw/` після звірки теж видалено з диска.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/foundry/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/foundry-corpus-РРРР-ММ-ДД.tar.gz -C instances/foundry corpus raw
find instances/foundry/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/foundry/raw
gzip -9 -c instances/foundry/index/passages.json > instances/foundry/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/foundry-corpus-РРРР-ММ-ДД.tar.gz -C instances/foundry
./df foundry smoke
```

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/foundry/index/passages.json.gz`, далі
`./df foundry vectors` заллє колекцію Qdrant (близько години).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df foundry …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище». Свій `.env` примірник тримає в `instances/foundry/.env` (`cp .env.example .env`;
для кроку `ask` потрібен `ANTHROPIC_API_KEY`); `GITHUB_TOKEN`, якого немає в цьому `.env`, береться з кореневого.

## Збирання корпусу

```
./df foundry sources --why   # перелік джерел і білий список
./df foundry refresh         # завантажити все задеклароване (~1 година: ~150 дерев, ~5 100 файлів, пауза 0,3 с)
./df foundry build           # перезібрати тексти зі сховища сирого, без мережі (після правки читача)
./df foundry manifest        # оновити паспорт
./df foundry setup           # Qdrant чи пошук лише по словах
./df foundry vectors         # залити корпус у docs-foundry (~1 година)
./df foundry smoke           # перевірки
```

Як оновлювати після нових версій — у [UPDATE.md](UPDATE.md).

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df foundry serve       # порт 8829
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8829/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user foundry-docs http://127.0.0.1:8829/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт. Інший
шлях — запис `.mcp.json` цієї теки: Claude Code, відкритий у ній, побачить сервер сам.

**3. Перевірити.** `/mcp` — має бути `foundry-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію Claude
Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і «Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Якщо порт 8829 зайнятий, `serve` падає з «address already in use»: значить,
сервер уже піднято в іншому терміналі. Решта — scope запису — так само, як у
[README примірника nestjs](../nestjs/README.md#спосіб-б--сервер-під-claude-code-http).
