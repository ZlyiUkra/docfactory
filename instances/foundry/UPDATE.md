# Оновлення корпусу foundry

Дві різні роботи: звичайне оновлення, коли вийшли нові версії Foundry чи forge-std, і збирання з нуля. Порядок
усередині кожної важливіший за самі команди.

Головне правило: **оновлювач тягне лише оголошене.** Дерева й файли репозиторіїв — лише тих комітів і тегів, що
перелічені в полі `tags` джерел, і лише в межах `within`; релізи — лише з адрес джерел `releases-*`; версії — з реєстру
npm. Нова версія сама в документацію не потрапить, доки її тег (чи коміт книжки) не дописано в `tags`.

Друге правило: **лише стабільні версії.** У `tags` — тільки стабільні випуски, без нічних збірок (`nightly-…`) і без
передрелізів (`-rc1`); читач `ghreleases-stable` і поле `skip_versions` джерел `npm-*` відкидають усе з дефісом за
номером.

Третє правило: **версія сайту — день виходу.** Foundry Book (репозиторій foundry-rs/book) тегів не має. Для кожної
стабільної версії Foundry в `tags` джерела сайту стоїть повний SHA останнього коміту книжки перед публікацією її
релізу. Виняток один: 1.8.5 узято зі стану сайту на день збирання примірника (12.10.2026, коміт `eb5b8f17`).

Четверте правило: **нова версія змінює й старі документи.** Документ сторінки — неповторна редакція, а в рядку
`# версія:` стоять усі версії, де вона була саме такою. Тож після нових комітів джерело сайту перезаписується цілком
(`refresh book-3`), а не докачується (`--missing`).

П'яте правило: **нічого не видаляється.** Ані `refresh`, ані `build`, ані `manifest` нічого не стирають самі;
`vectors` прибирає лише точки власної колекції, чиїх фрагментів у корпусі вже немає. Редакції сторінок, що після
правки читача дістали нове ім'я, лишаються в `corpus/` старими файлами — їх переносять убік вручну.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти й сховище сирого розпаковують, а після неї —
пакують і виносять знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшла нова версія Foundry

**Крок 1. Знайти реліз.** Стабільні релізи — на `https://github.com/foundry-rs/foundry/releases` (тег `v1.9.0`, без
`-rc` і без `nightly-`), час публікації — поле `published_at` релізу в API
(`https://api.github.com/repos/foundry-rs/foundry/releases/tags/v1.9.0`). Тег без релізу (як `v1.8.2`) не береться.

**Крок 2. Коміт книжки.** Останній коміт гілки `master` репозиторію foundry-rs/book перед `published_at`:

```
git -C book.git rev-list -1 --before=2026-11-02T12:00:00Z master    # у голому клоні foundry-rs/book
```

або `https://api.github.com/repos/foundry-rs/book/commits?sha=master&until=2026-11-02T12:00:00Z&per_page=1`. Повний SHA
— на початок поля `tags` джерела `book-3` (від найновішого): `"<sha>": "1.9.0"`. Якщо дві версії вийшли на тому самому
коміті, ключ один, а версії — через кому: `"<sha>": "1.9.1, 1.9.0"`.

**Крок 3. Тег репозиторію.** `"v1.9.0": "1.9.0"` — на початок поля `tags` джерела `repo`.

**Крок 4. Нова версія forge-std** (теги на `https://github.com/foundry-rs/forge-std/tags`): `"v1.18.0":
"forge-std-1.18.0"` — на початок полів `tags` джерел `forge-std-docs` і `forge-std-src`. Мітка «forge-std-» не дає
змішати лінії forge-std і Foundry у фільтрі версії.

**Крок 5. Завантажити.**

```
./df foundry sources --why
./df foundry refresh book-3 repo releases-foundry forge-std-docs forge-std-src releases-forge-std npm-forge npm-cast npm-anvil npm-chisel
./df foundry manifest
./df foundry vectors
./df foundry smoke
# Ctrl+C у терміналі з serve, і знову: ./df foundry serve
```

Названий `refresh` інших джерел не чіпає зовсім. Джерела `book-2` і `book-1` застиглі: ці періоди сайту закінчилися.
Перезбирання `book-3` перепитує в GitHub кожну сторінку й вставку («чи змінилася»), близько 25 хвилин.

**Крок 6. Промпти.** Версію за замовчуванням (найновіша стабільна) записано в `prompts/search.txt` (абзац «Every answer
says which version…») і `prompts/agent.txt`; лінії й межі версій — ще й у `prompts/loaded.txt` і `prompts/agent.txt`
(«від 0.3.0 до 1.8.5»).

**Крок 7. Сайт знову переїхав.** Якщо сторінки книжки опинилися в іншій теці (як 2025 року `src/` → `vocs/docs/pages`,
а 2026 — `vocs/docs/pages` → `src/pages`), нове джерело `book-4` робиться за зразком `book-3`, його id дописується в
родину `book` поля `families` у `config.json`, а в `slug_rewrite` — правило, що зводить новий шлях сторінок до спільного
ключа `src-…`. Правильність ключів видно зі скану спільних ключів кешу фрагментів (див. NEW-INSTANCE.md).

**Крок 8. Сайт змінив розмітку.** Якщо в тексті з'явилися службові рядки Vocs (`:::`, `// [!include`, теги компонентів
`<…/>`) чи кольори терміналу, правиться модуль `engine/readers/_vocs.py`. Правка читача не вимагає нового
завантаження: `./df foundry build book-3` збирає тексти зі сховища сирого. Виняток — вставка файла, якого читач досі
не брав: його в сховищі ще немає, тож потрібен `refresh` джерела.

Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти й сховище (README, розділ «Архівний
режим»), а в git ідуть лише паспорт і кеш. Старий архів видаляють, коли новий звірено з диском.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки: без нього ~150 дерев і ~10 сторінок релізів ішли б
годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
PYTHONUNBUFFERED=1 setsid nohup ./df foundry refresh > refresh.log 2>&1 < /dev/null &
```

Близько години: дерево кожного коміту й тегу через API GitHub і кожен неповторний файл (сторінка, вставка, файл коду)
один раз із raw.githubusercontent.com, з паузою 0,3 с. Обірваний прогін продовжують `./df foundry refresh <джерело, де
зупинився>`, далі `refresh --missing`.

**Крок 3.** `manifest`, `vectors` (~1 година), `smoke`, `quality`; далі — архів і винесення текстів.

Очікуваних збоїв `refresh` немає.
