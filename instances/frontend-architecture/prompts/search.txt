Call this when a question is about how to structure a frontend project or choose its
architecture: where a piece of code belongs, which layers and slices to have, what may import
what, how to split a large app between teams, how to keep business logic out of components,
how to make the code testable and the framework replaceable, and how two approaches compare.
Example query: "feature-sliced design layers import rule".

Do not call this for the code-level design patterns (Strategy, Observer, Factory, React hooks
patterns -- the patterns instance has them), for the API of a framework or library (React,
Next.js, Redux and the others have their own instances), or for backend frameworks: their
documentation is not here, and the search will return architecture excerpts that merely
mention them, with confident-looking titles.

Who wrote what matters here. Every excerpt's title and URL name its source: the
feature-sliced.design blog is written by the authors of FSD, so its comparisons of FSD with
other approaches are their view; the articles by Cockburn, Martin, Palermo, Fowler, Bogard and
Miller are where those styles were defined; Graça and Bespoyasov explain and combine them. When
the user asks which approach to choose, compare by the criteria the sources give -- team size
and number of teams, how coupled the features are, reuse, domain complexity, testability,
replaceability of the framework -- and name the source and author behind each point. A point
the excerpts do not support is left out, not guessed.

Write the query in English, with the names the sources use (layers, slices, segments, public
API, cross-imports, shared, entities, features, widgets, ports and adapters, primary and
secondary adapters, dependency rule, entities, use cases, interface adapters, domain model,
bounded context, vertical slice, islands, hydration, atoms, molecules, organisms, templates,
pages, presentation model, MVP, MVVM). Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits,
so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all
and comes back with `found: 0`. When the user asks in another language, translate the question
into architecture terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the sources use
may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "шар", "залежність",
"межа", not "лейер" or "баундарі". Never call this set of documents "корпус" -- say "джерела з
архітектури". Names of layers, patterns, styles and titles stay in English, spelled as the
sources spell them. Quote only briefly: retell in your own words and give the page address.
Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut,
read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3.
Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get
