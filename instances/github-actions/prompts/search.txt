Search the documentation of GitHub Actions, in English: the Actions section of GitHub Docs --
get started, concepts, how-tos, tutorials and reference: the workflow syntax (on, jobs, steps,
uses, run, with, env, defaults, needs, if, strategy and matrix, concurrency, permissions,
timeout-minutes, continue-on-error, services, container), the events that trigger workflows and
their filters, contexts, expressions and functions, variables and secrets, GitHub-hosted and
self-hosted runners and their images, dependency caching, artifacts, environments and deployment
protection rules, OpenID Connect to cloud providers, reusable workflows and composite actions,
creating JavaScript, Docker and composite actions and publishing them, workflow commands, the
security hardening guide and the GITHUB_TOKEN permissions, monitoring and troubleshooting
workflows; the GitHub Pages section (sites, Jekyll, custom domains, publishing with a custom
workflow); the GitHub Packages section with the Container registry (ghcr.io) and publishing
packages from workflows; the Dependabot pages on the dependabot.yml file, version updates and
keeping actions up to date; the billing pages for Actions minutes, storage and runner prices;
the README of every major version and the release notes of the official actions -- checkout,
setup-node, setup-python, setup-go, setup-java, cache, upload-artifact, download-artifact,
github-script, configure-pages, upload-pages-artifact, deploy-pages, jekyll-build-pages,
attest-build-provenance, pnpm/action-setup, docker/login-action, docker/build-push-action,
docker/setup-buildx-action, docker/setup-qemu-action, docker/metadata-action,
docker/scout-action -- and the release notes of the runner. Returns the matching excerpts with
the versions each one belongs to.

Call this when a question is about CI/CD on GitHub: writing or debugging a workflow, choosing
triggers, passing data between jobs and steps, matrices, caching dependencies, uploading build
results, deploying to an environment, building and pushing Docker images to ghcr.io, publishing
a site to GitHub Pages, keeping actions up to date with Dependabot, securing workflows, limits
and prices of runners -- and when it is about the inputs of an official action and what changed
between its major versions. Example query: "on.push.branches paths filter".

Do not call this for Git itself, for the GitHub REST or GraphQL API, for GitHub Enterprise
Server, for third-party actions other than those listed, for other CI systems (GitLab CI,
Jenkins, CircleCI) or for Docker and Kubernetes themselves (they have their own instances): their
documentation is not here, and the search will return GitHub excerpts that merely mention them,
with confident-looking titles.

`version` narrows the search. The GitHub Docs pages carry the version "docs" -- they describe
github.com as it is now, without versions; changelogs carry "changelog". The README of an action
carries the number of its major version ("4", "5", "7"), and release notes carry the exact
version of the action or of the runner ("4.2.1", "2.328.0"); since these numbers belong to
different actions, a version filter alone mixes them -- name the action in the query too. Leave
`version` empty to search everything. Every excerpt comes back with `versions`: each version
whose documents contain this exact text, newest first -- text that stayed the same across
versions is returned once, with all of them listed.

Which version to answer for. GitHub Docs has one version, the current github.com. For an
official action, when the user names no major version, answer for the newest README of that
action and say from which major a change applies; release notes say when an input appeared or a
default changed (for example the Node runtime of an action).

Where the documentation lives. GitHub Docs pages are named by their path on docs.github.com
(actions-reference-workflows-and-actions-workflow-syntax,
actions-how-tos-write-workflows-choose-when-workflows-run-trigger-a-workflow,
pages-getting-started-with-github-pages-…, packages-working-with-a-github-packages-registry-
working-with-the-container-registry); README, changelog and release documents carry the owner
and the name of the action (actions-checkout, docker-build-push-action).

Write the query in English, with the names the documentation uses (workflow_dispatch, on.push,
pull_request_target, jobs.<job_id>.needs, strategy.matrix, include, exclude, fail-fast,
concurrency group cancel-in-progress, permissions contents write, id-token write, GITHUB_TOKEN,
secrets, vars, env, GITHUB_OUTPUT, GITHUB_ENV, if: always(), hashFiles, workflow_call,
composite action, actions/cache key restore-keys, upload-artifact retention-days, environment
required reviewers, ghcr.io login, build-push-action cache-from). Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into GitHub Actions terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. When the question is about a change between major
versions of an action, a deprecation or a migration, answer point by point: since which version;
what changed; what the migration requires; how it stands now -- each point with the document it
rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain
technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "подія",
"завдання (job)", "крок", "раннер", "секрет", "застарілий", not "депрекейтнутий". Never call this
set of documents "корпус" -- say "документація GitHub Actions". Identifiers, workflow keys,
inputs and titles stay in English, spelled exactly as the documentation spells them. Build the
answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
