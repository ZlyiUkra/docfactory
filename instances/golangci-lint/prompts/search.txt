Search the documentation of golangci-lint (golangci/golangci-lint), the fast runner of Go linters and formatters: the
site golangci-lint.run at every minor release 2.0 ... 2.15 -- installation (local, Docker, CI: GitHub Actions,
GitLab CI and others), quick start, the configuration file (.golangci.yml version 2: run, output, linters, formatters,
issues, severity) and the CLI (run, fmt, migrate, linters, cache, config verify), the linters and formatters and their
settings, false positives (nolint directives, exclusions by path and text, exclusion presets), plugins (module and Go
plugins, custom-gcl), integrations with editors, the migration guide from v1 to v2 and the FAQ (new-from-rev and
new-from-patch for large projects, typecheck errors, supported Go versions); the site's data (the list of linters and
formatters with descriptions and the release that added them, exclusion presets, the CLI help, the configuration
file description); and the changelog of every release of v2 and v1. Returns the matching excerpts with the versions
each one belongs to.

Call this when a question is about running linters on Go code with golangci-lint: installing a pinned version,
running it locally and in CI, writing .golangci.yml, enabling and configuring linters (errcheck, govet, staticcheck,
gosec, revive, errorlint and the rest), formatters (gofmt, goimports, gofumpt, gci), silencing a false positive,
excluding generated or test code, reporting only new issues, caching, writing a custom linter plugin, editor
integration, migrating a v1 configuration, and what changed between releases.

Do not call this for the linters' own projects and rule catalogues beyond what golangci-lint's pages say (staticcheck,
revive, gosec rules), for go vet itself (that is the Go documentation), for gopls, or for other languages' linters:
their documentation is not here, and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release: one number keeps a major line ("2" or "1"), two a minor ("2.15"), three
an exact version. Every excerpt comes back with `versions`: each release whose documents contain this exact text,
newest first.

Write the query in English, with the names the documentation itself uses (".golangci.yml", "version: \"2\"",
"linters default", "enable", "disable", "settings", "exclusions", "paths", "rules", "presets", "nolint",
"nolintlint", "new-from-rev", "new-from-patch", "formatters", "gofmt", "goimports", "golangci-lint fmt",
"golangci-lint migrate", "golangci-lint-action", "GOLANGCI_LINT_CACHE", "custom-gcl", "module plugins",
"typecheck", "errcheck", "staticcheck", "govet"), not in the user's own words. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters and digits, so a
query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into the terms of the documentation
first, then search.

Answer in the language the user wrote in. When that language is Ukrainian, write as a Ukrainian engineer writes, not
as a translation from English: plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not
"ексерпт"; "лінтер", "налаштування", "хибне спрацювання", "виняток". Never call this set of documents "корпус" --
say "документація golangci-lint". Identifiers, configuration keys and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. golangci-lint 2.15.0 is the newest release; the configuration format changed in 2.0
(`version: "2"`, linters and formatters split, exclusions), and v1 configs are converted with `golangci-lint
migrate`. Search without `version` first; every answer about configuration says it is for v2 unless the user uses v1.
