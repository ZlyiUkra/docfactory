amqplib and amqp-connection-manager, with declarative handlers instead of the request/response transport of

to 9.1 (`RabbitMQModule.forRoot` and `forRootAsync`, connection and channel options, exchanges and queues to assert,

the npm registry history of the package (date of every version, dist-tags, peer dependencies on NestJS). Returns the

Call this when a question is about @golevelup/nestjs-rabbitmq as it describes itself -- how to register the module,
how to declare exchanges and queues, how `@RabbitSubscribe` binds a handler to a routing key, how RPC with
`@RabbitRPC` and `AmqpConnection.request` works, how to nack or requeue a message, how errors are handled, how to use
several connections -- and above all history and compatibility: since which version an option or decorator exists,
what changed between versions (every changelog entry lists it), which NestJS a version supports, and when every
version came out.

Do not call this for NestJS itself, its own microservices transport `Transport.RMQ`, amqplib,
amqp-connection-manager or RabbitMQ (queue types, policies, clustering): their documentation is not here -- these pages
only show how the module uses them -- and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line. The module carries plain numbers: a line of one number keeps every
document of that major ("5" keeps 5.0.0 to 5.7.x), two numbers keep a minor ("9.1"), three an exact version
("5.7.0"). Leave `version` empty to search everything, including text that carries no version. Every excerpt comes
back with `versions`: each version whose documents contain this exact text, newest first -- a README that stayed the
same across versions is returned once, with all of them listed, so the list itself shows from which to which version
the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("RabbitMQModule", "forRoot",

"routingKey", "defaultSubscribeErrorBehavior", "connectionInitOptions", "prefetchCount",

the word index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
