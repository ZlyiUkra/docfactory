# gvisor — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про gVisor — «ядро застосунку» для контейнерів: воно перехоплює
системні виклики програми й виконує їх саме, у просторі користувача, ядром, написаним на Go (Sentry), тож програма
майже не торкається ядра господаря. Запускає gVisor `runsc` — середовище виконання OCI, яке Docker, containerd, CRI-O
і Kubernetes викликають замість звичного `runc`. Документація — сторінки gvisor.dev/docs із теки `g3doc` репозиторію
google/gvisor і кореневі файли репозиторію для кожного випуску 20190304.1–20261012.0; прапорці й підкоманди `runsc` з
коду тих самих випусків; сторінки gvisor.dev поза документацією (таблиці системних викликів, сумісність застосунків,
історія вразливостей, блог); архівний сайт 2019–2020 і архівний gvisor-containerd-shim; нотатки релізів; пакет `runsc`
в APT і довідник netstack — мережевого стека gVisor як бібліотеки Go — на pkg.go.dev. Код спільний і лежить у
`../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

Слова, що трапляються нижче:

- **Sentry** — ядро gVisor на Go, що виконує системні виклики програми; **Gofer** — окремий процес, через який Sentry
  дістає файли господаря, а **directfs** — режим, де Sentry відкриває їх сам, без Gofer;
- **платформа** — спосіб, яким gVisor перехоплює системні виклики: `systrap` (на seccomp, типова), `kvm` (апаратна
  віртуалізація), `ptrace` (стара);
- **shim containerd** — посередник між containerd і `runsc` (`containerd-shim-runsc-v1`);
- **RuntimeClass** — об'єкт Kubernetes, що вибирає для пода середовище виконання (так GKE Sandbox і вмикає gVisor);
- **`g3doc`** — тека документації в репозиторії, з якої Jekyll збирає gvisor.dev/docs;
- **псевдоверсія** — версія модуля Go без тегу: `0.0.0-<час>-<коміт>`.

## Навіщо окремий примірник

gVisor випускається щотижня: тег `release-РРРРММДД.N` і є стабільним випуском, семантичних версій немає. На машинах
стоять дуже різні випуски — `apt-get install runsc` ставить лише останній, а образи вузлів і кластери живуть місяцями.
Між випусками міняються прапорці `runsc` і їхні типові значення: до 20230605.0 типова платформа — `ptrace`, з
20230621.0 — `systrap`; з'являються `--overlay2`, `--directfs`, `--nvproxy`, а вилучені переносять у
`flags_graveyard.go`. Окремої довідки з прапорців немає взагалі: їх описано лише в коді `runsc/config` — полями
структури `Config` з коментарями й реєстрацією з типовим значенням і підказкою. Тож відповідь «що робить
`--overlay2=root:self` у випуску 20240916.0» береться з коду й сторінок саме того випуску, а не з пам'яті. Сайт
gvisor.dev показує лише поточний стан; архівний сайт 2019–2020 і архівний shim кажуть, як gVisor ставили тоді.
Docker, Kubernetes і ядро Linux мають власні примірники (`docker`, `kubernetes`, `linux`); тут — те, як вони
запускають gVisor і що gVisor реалізує з Linux.

## Що в цій теці

- `corpus/` — паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа. Самих текстів тут немає:
  корпус в архіві.
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`.
- `sources.json` — звідки корпус будується (8 джерел), і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — токен GitHub і, для кроку `ask`, ключ Anthropic; `.mcp.json` — запис HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики через `./df gvisor <крок>`.

| пакет `runsc` в APT | `apt-packages` (новий) |
| netstack на pkg.go.dev | `pkgsite` (новий) |

Особливості:

- **Сайтмап із голими шляхами.** gvisor.dev зібрано Jekyll без `site.url`, і `sitemap.xml` пише
  `<loc>/blog/2023/06/27/directfs/</loc>` — шлях, а не адресу. `sitemap-html` порівнює `<loc>` з `within` як рядок, і
  жодна сторінка не проходила; `sitemap-html-rel` спершу робить з кожного `<loc>` повну адресу відносно самого
  сайтмапа. Сторінки `/docs/` бере джерело `g3doc` з репозиторію; із `/docs/` тут лише дві таблиці системних
  викликів — їх сайт генерує з `runsc`, у `g3doc` їх немає.
- **Залишки Jekyll у `g3doc`.** Майже кожна сторінка починається рядком `[TOC]` (місце змісту на сайті), сторінка
  продуктивності вставляє графіки тегом Liquid `{% include graph.html … %}`, розірваним на два рядки, а приклади
  команд Docker ховають дужки шаблону Go в `{% raw %}…{% endraw %}`. `ghdocs-history-jekyll` прибирає `[TOC]` і
  позначки `raw`, а графік робить рядком «Graph: <назва>». Це тонка обгортка над `ghdocs-history`: текст сторінки
  чиститься до розбору, а сам спільний читач, на якому стоять звірені примірники, не змінено.
- **Шапки TOML архівного сайту.** Сайт Hugo 2019–2020 пише шапку сторінки в TOML (`+++ / title = "Installation" /
  +++`), якої `ghdocs-history` не знає: назвою ставало ім'я файла, а `title = …` лягало першим абзацом.
  `ghdocs-history-toml` перетворює шапку на YAML і підставляє вставки на кшталт `{{< required_linux >}}` значеннями з
  `config.toml` того самого знімка — інакше речення про потрібну версію ядра Linux втрачало саме номер. Назви
  документів позначено «gvisor.dev 2020», щоб не плутати їх із чинними сторінками.
- **Одна родина з трьох джерел.** `slug_rewrite` дає сторінкам архівного сайту ключі їхніх наступниць у `g3doc`
  (посібник користувача, посібник з архітектури, туторіали, сумісність), двом дописам блогу 2020 року — ключі тих
  самих дописів на чинному сайті, а двом сторінкам, що переїхали всередині `g3doc` (`checkpoint_restore.md` з кореня в
  `user_guide/`, `docker-in-gvisor.md` у `tutorials/`), — ключі нових місць. Запис `families`
  `{"gvisor-docs": ["g3doc", "website-2020", "site"]}`: стара редакція не забирає місця у видачі в чинної.
- **Адреси.** Документ `g3doc` цитує сторінку gvisor.dev лише тоді, коли файл є в найновішому тезі й сайт його
  показує: поле `site` перелічує такі файли поіменно. Сторінки, що переїхали чи зникли (`g3doc/checkpoint_restore.md`
  2019 року, `user_guide/docker-in-gvisor.md`), і файли, яких сайт не показує (кореневий README, ADOPTERS,
  MAINTAINERS, пропозиції, README прикладів), ведуть на blob GitHub свого тегу, а не на мертву адресу сайту.
- **Прапорці в коді.** `ghcode-history` з `outline: ["go"]` ділить файл Go за оголошеннями верхнього рівня разом із
  коментарем над ними: структура `Config`, функція `RegisterFlags`, кожна підкоманда з `Usage()` і `SetFlags`.
  Внутрішні підкоманди `boot` і `gofer` (процеси пісочниці, які `runsc` запускає сам), допоміжні файли `runsc/cmd`,
  тести й `_unsafe.go` не взято.
- **Netstack з pkg.go.dev.** Документація мережевого стека існує лише як коментарі коду, які показує pkg.go.dev.
  `pkgsite` бере сторінку `pkg/tcpip`, кожен підпакет із її розділу «Directories» (без `internal`, допоміжних пакетів
  тестів і `faketime`) і окремо `pkg/buffer`; функції й типи — розділами з оголошенням, методи — підрозділами, приклади
  — усередині розділу своєї функції. Між зверненнями — пауза 1,5 с: pkg.go.dev пригальмовує частих клієнтів відповіддю
  429. Тегованих версій модуль Go не має, тож версія — псевдоверсія гілки `go` на день збирання.
- **APT.** Офіційний репозиторій тримає лише останній `runsc`; `apt-packages` робить з індексу `Packages` один документ
  із розділом на кожну архітектуру: версія, розмір, шлях до `.deb`, контрольні суми. Пакетів npm чи PyPI gVisor не має.
- **Мітки версій.** Випуск gVisor — дата тегу без «release-»: `20261012.0`. Лінія — перша частина мітки
  (`version_line_depth: 1`), тобто сама дата: `version: "20261012"` бере всі 20261012.N, а рік чи місяць (`"2026"`,
  `"202610"`) і префікс `release-` не дають нічого — модель про це попереджено в описі інструмента. Архівний shim —
  `containerd-shim-0.0.4` (`"containerd-shim-0"` — усі чотири), щоб фільтр не змішував його з випусками gVisor.
  Сторінки gvisor.dev поза `g3doc` і архівний сайт версій не мають, netstack несе псевдоверсію: їх шукають без версії,
  бо будь-яка дата випуску їх відсікає. Без названої версії — найновіша, 20261012.0.

## Межі, про які треба пам'ятати

- Структура `Config` (`config.go`) і функція `RegisterFlags` (`flags.go`) — оголошення по 16–20 КБ, поділені за
  довжиною, тож питання про один прапорець зазвичай приходить на сторінку посібника, де його вживають, а не на рядок
  коду. Типове значення варто дочитати через `read_section` цілим фрагментом.
- Таблиці системних викликів amd64 і arm64 — кожна одним довгим розділом, поділеним за довжиною: фрагмент про виклик
  несе й сусідні рядки таблиці.
- `--nvproxy` у `flags.go` позначено LEGACY: підтримка GPU вмикається сама, коли в специфікації OCI є пристрої NVIDIA.
  Сторінка посібника про GPU досі каже, що прапорець потрібен.
- Тексти pkg.go.dev зберігають анотації gVisor `+stateify savable` у коментарях типів.
- Нотатки релізів GitHub є лише з 20260817.0; раніші зміни видно тільки з порівняння редакцій сторінок і коду.
- Netstack — лише чинна псевдоверсія, без історії; APT — лише останній випуск.
- У тегах 2019 року `g3doc` тримає лише `checkpoint_restore.md` (з 20190722.1 ще README); повна документація — з
  20200518.0, а до того її дає архівний сайт.
- Документації Docker, containerd, Kubernetes і самого ядра Linux (man системних викликів, seccomp, KVM, cgroups) тут
  немає: Docker — у примірнику `docker`, Kubernetes і containerd у кластері — у `kubernetes`, ядро — у `linux`.

## Архівний режим: сервер без корпусу

Корпус в архіві від самого початку: у `corpus/` лежить лише паспорт, а сервер підіймається з кешу фрагментів і
колекції Qdrant; відповіді ті самі до символа. `smoke` дав 221 пройдену перевірку з корпусом і 219 в архівному режимі
(дві звірки з файлами пропускаються), провалів — нуль.

**Де тексти.** В архіві `~/archives/docfactory/gvisor-corpus-2026-10-18.tar.gz` (49 МБ: 1 219 текстів, паспорт і
сховище сирого `raw/`; перед видаленням розпакований окремо й звірений з диском через `diff -r` — нуль розбіжностей).
Лише на цій машині. У git — паспорт `corpus/index.json` і кеш `index/passages.json.gz`.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
tar -czf ~/archives/docfactory/gvisor-corpus-РРРР-ММ-ДД.tar.gz -C instances/gvisor corpus raw
find instances/gvisor/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/gvisor/raw
gzip -9 -c instances/gvisor/index/passages.json > instances/gvisor/index/passages.json.gz
```

**Як повернути тексти** — перед будь-яким оновленням:

```
tar -xzf ~/archives/docfactory/gvisor-corpus-2026-10-18.tar.gz -C instances/gvisor
./df gvisor smoke
```

**Оновлення.** Новий випуск дописують першим рядком у `tags` джерел `g3doc` і `runsc-flags`
(«"release-РРРРММДД.N": "РРРРММДД.N"»). Сайт (нові дописи блогу ловить вираз `match`), релізи, APT і netstack
підхоплюються самі; архівний сайт і shim більше не змінюються. Далі `./df gvisor list`, `refresh`, `manifest`,
`vectors`, `smoke`, `quality`. Перший повний `refresh` мережею тривав 11 хвилин, `vectors` — 13.

## Установка venv

Власний venv цьому примірнику не потрібен: `./df gvisor …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище». Свій `.env` примірник тримає в `instances/gvisor/.env` (`cp .env.example .env`;
для кроку `ask` потрібен `ANTHROPIC_API_KEY`); `GITHUB_TOKEN`, якого немає в цьому `.env`, береться з кореневого.

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають. Для роботи сервера збирати нічого не
треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df gvisor sources --why      # перелік джерел і білий список
./df gvisor refresh            # завантажити все задеклароване
./df gvisor manifest           # оновити паспорт
./df gvisor setup              # Qdrant чи пошук лише по словах
./df gvisor vectors            # залити корпус у docs-gvisor
./df gvisor smoke              # перевірки
```

Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df gvisor serve             # порт 8859
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8859/mcp`. Якщо порт зайнятий,
сервер скаже про це й вийде: значить, `serve` цього примірника вже десь запущений; хто тримає порт, покаже
`ss -ltnp | grep 8859`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user gvisor-docs http://127.0.0.1:8859/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Замість запису на рівні користувача можна відкрити Claude Code у цій теці:
`.mcp.json` тут уже називає сервер.

**3. Перевірити.** `/mcp` — має бути `gvisor-docs` і два інструменти `search_docs`, `read_section`. Якщо там
«failed / not connected» — майже завжди сервер не піднятий (крок 1) або адреса не збігається з полем `port` у
`config.json`.

Зупинка — Ctrl+C у терміналі сервера.
