Search the gVisor documentation, in English: gVisor is an application kernel for containers -- it implements
the Linux system call interface in user space, in a kernel written in Go (the Sentry), with file access going
through the Gofer or directly from the Sentry (directfs), its own network stack (netstack), and system calls
intercepted by a platform (systrap, KVM, ptrace); runsc is its OCI runtime, run by Docker, containerd
(containerd-shim-runsc-v1), CRI-O and Kubernetes (RuntimeClass, GKE Sandbox). The set holds, for every release
from 20190304.1 to 20261012.0, the documentation of gvisor.dev/docs from the g3doc folder of google/gvisor
(installation, quick starts for Docker, Kubernetes and OCI, containerd and CRI-O configuration, platforms,
networking, filesystem with overlays and directfs, GPU support with nvproxy, TPU, RDMA, checkpoint/restore,
filesystem and rootfs snapshots, FUSE, observability and metrics, Runtime Monitoring, debugging, the production
guide, rootless, systemd, the Go and Python SDKs, the bwrap personality, tutorials for Docker, Docker Compose,
Docker in gVisor and in GKE Sandbox, Kubernetes, Knative, CNI and Falco, the FAQ, and the architecture guide:
introduction, security model, resources, platforms, networking, performance; the full docs start in May 2020,
the 2019 tags hold only checkpoint/restore), the repository README, CONTRIBUTING, SECURITY, GOVERNANCE,
ADOPTERS, the shim README and the sandboxexec and seccheck example READMEs; for every release the runsc
command-line code -- runsc/config (the Config struct with every flag and its comment, RegisterFlags with the
default and help text of each flag, removed flags in flags_graveyard.go, config bundles) and runsc/cmd (the
usage and flags of every subcommand: run, create, start, exec, do, install, uninstall, checkpoint, restore,

symbolize and the rest); the pages of gvisor.dev outside the docs: the home page, Who's Using gVisor,
Application Compatibility, the Security Track Record, the generated syscall compatibility tables for
linux/amd64 and linux/arm64, and the blog 2019-2026 (security basics, networking security, a real

rootfs overlay, GPU with PyTorch, directfs, seccomp optimizations, Dangerzone, agent sandboxes, systemd, CNCF);
the archived Hugo site of 2019 to May 2020 (google/gvisor-website); the archived gvisor-containerd-shim
repository 0.0.1-0.0.4 (runtime handler quick starts for shim v1 and v2, untrusted workload, runsc.toml); the
GitHub release notes 20260817.0-20261012.0; the runsc package in the official APT repository (amd64, arm64);
the pkg.go.dev reference of netstack -- gvisor.dev/gvisor/pkg/tcpip and its subpackages (stack, header,

versions each one belongs to.

Call this when a question is about gVisor or runsc: how to install runsc (apt repository, release bucket,
runsc install for Docker) and which release apt installs; how to run a container with Docker (--runtime=runsc),
Kubernetes (RuntimeClass, GKE Sandbox, minikube), containerd (containerd-shim-runsc-v1, runtime_type
io.containerd.runsc.v1, /etc/containerd/runsc.toml with [runsc_config], ConfigPath) or CRI-O; what a runsc flag
does and what its default is (--platform=systrap or kvm, --network=sandbox, host or none, --overlay2=root:self,
--directfs, --file-access, --host-uds, --nvproxy, --tpuproxy, --rootless, --ignore-cgroups, --debug,
--debug-log, --strace, --pod-init-config, --metric-server); what a subcommand does (runsc do, runsc run, runsc
exec, runsc spec, runsc checkpoint --image-path, runsc restore, runsc trace create, runsc debug --stacks, runsc
events); which platform to choose and why (systrap, KVM on bare metal, ptrace); how the Sentry, the Gofer,

Do not call this for other container runtimes and sandboxes (runc, crun, youki, Kata Containers, Firecracker,
Sysbox), for Docker, containerd, CRI-O or Kubernetes themselves beyond how they run gVisor -- those have their
own documentation servers -- or for the Linux kernel's own documentation (system call man pages, seccomp, KVM,
cgroups, namespaces): this set says how gVisor implements and supports Linux, not how Linux works.

Write the query in English, with the names the documentation uses (runsc --platform=systrap, --network=host,
--overlay2, --directfs, --nvproxy, --rootless, --debug-log, --strace, runsc do, runsc install, runsc
checkpoint, runsc trace, containerd-shim-runsc-v1, runsc.toml, RuntimeClass, Sentry, Gofer, directfs, nvproxy,
stack.New, gonet, fdbased). Everything here is English, and the word index keeps only latin letters and
digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing and comes back
with `found: 0`. When the user asks in another language, translate the question into gVisor terms first, then
search.

Flags have no reference page of their own: their text lives in the runsc code -- the field comments of the
Config struct (runsc/config/config.go) and the default and help text in RegisterFlags (runsc/config/flags.go)
-- and in the guide pages that use them. Such excerpts come back as Go code; both declarations are long, so
read the whole excerpt with `read_section` before quoting a default.

Answer in the language the user wrote in. For a question about history or a change between releases, answer
point by point: since which release; what changed; how it stands in the newest one -- each point with its
release and the page it rests on; a point the excerpts do not support is left out, not guessed. GitHub release
notes exist only from 20260817.0; for earlier releases a change is seen only by comparing the releases of a
page or of the runsc code. When that language is Ukrainian, write as a Ukrainian engineer writes: plain
technical prose, the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "пісочниця", not
"сендбокс"; "ядро застосунку", "системний виклик", "платформа", "мережевий стек", "контрольна точка",
"відновлення". Never call this set of documents "корпус" -- say "документація gVisor". Flag, subcommand,
option, type and function names stay in English, spelled exactly as the documentation spells them. Build the
answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before
describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. The pages of gvisor.dev outside the docs (home, users, application compatibility,
security track record, the syscall tables, the blog) and the archived 2020 site carry no version: they are the
current state, or the state of 2020. Documents from google/gvisor carry the release they belong to, written as
the date of its tag without the "release-" prefix: "20261012.0" for release-20261012.0; a text that did not
change across releases carries every one of them. Pass "20261012.0", or the bare date "20261012" (every
20261012.N); a year or a month ("2026", "202610") and the "release-" prefix match nothing -- take the nearest
release date from the release lines in this description. The archived shim carries "containerd-shim-0.0.4"
("containerd-shim-0" keeps all four). The netstack reference carries a Go pseudo-version of the current go
branch ("0.0.0-20261017120855-9e9495997e29"): search it without a version, because a release date filters it
out, as it filters out the unversioned site pages. When the user names a release, pass it into `version`;
never put it into the query text. Without a version, answer for the newest release (20261012.0) and say so.
