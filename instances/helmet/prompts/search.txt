Search the Helmet documentation -- the helmetjs.github.io site as it stood at every stable
release of the helmet npm package, the README, SECURITY.md, CONTRIBUTING.md, TypeScript
declarations and changelog of every stable version, and the npm registry history -- and return
the matching excerpts with the versions each one belongs to. Helmet sets HTTP response headers
for Node.js apps (Express, Connect and others): Content-Security-Policy, Strict-Transport-
Security, Cross-Origin-Opener-Policy, Cross-Origin-Embedder-Policy, Cross-Origin-Resource-Policy,
Referrer-Policy, X-Content-Type-Options, X-DNS-Prefetch-Control, X-Download-Options,
X-Frame-Options, X-Permitted-Cross-Domain-Policies, X-Powered-By, X-XSS-Protection,
Origin-Agent-Cluster, and in old versions Expect-CT, Public-Key-Pins (hpkp), nocache and
Feature-Policy.

Call this when a question is about Helmet itself -- the helmet() function and its options
(contentSecurityPolicy, useDefaults, directives, reportOnly, nonce through a function value,
strictTransportSecurity maxAge/includeSubDomains/preload, referrerPolicy, xFrameOptions,
crossOriginEmbedderPolicy, xXssProtection and its removal, hidePoweredBy), the individual
middleware functions (helmet.contentSecurityPolicy() and so on), turning one header off with
`false`, defaults per version, using Helmet without Express, the FAQ (conditional options, a
CSP nonce example, upgrading from 3 to 4, "you might not need Helmet") -- and above all history
and compatibility: since which version a header or option exists, which defaults changed
between majors (3 -> 4 -> 5 -> 6 -> 7 -> 8), what was removed (hpkp, nocache, expect-ct,
feature-policy), and which versions run on which version of Node.js (the `engines` field of
each version is written in the npm registry documents: 3.x Node 4, 4.x Node 10, 5.x Node 12,
6.x Node 14, 7.x Node 16, 8.x Node 18). Example query: "engines node 16".

Do not call this for Express itself, for other security middleware (cors, csurf, express-rate-
limit), for the meaning of the headers beyond what the Helmet documentation says (MDN, the
specifications) or for Node.js and npm: their documentation is not here, and the search will
return Helmet excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "8" keeps every 8.x document, "7.1" keeps
7.1.x; leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which
to which version the documentation said exactly this.

Write the query in English, with the names Helmet itself uses ("contentSecurityPolicy", "useDefaults",
"strictTransportSecurity", "xFrameOptions", "hidePoweredBy"), not in the user's own words. Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into Helmet terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Helmet". Identifiers, option names, header names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts
that came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something today, pass `version`
"8"; if the user's project is bound to an older Node.js, name the line that Node supports
(Node 16 -> "7", Node 14 -> "6", Node 12 -> "5", Node 10 -> "4") and say so. Search without
`version` when the question is about history, or when the line gave nothing. The defaults changed
with almost every major line, so an answer taken from the wrong line can be confidently wrong.
Every answer says which version it is for; when the user did not name one, answer for 8.x and say
so ("for Helmet 8.x"). When the excerpts behind a statement come only from older versions, name
those versions instead of presenting the text as current.
