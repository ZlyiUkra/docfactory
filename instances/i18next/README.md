# i18next — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про i18next за офіційною документацією всіх його стабільних версій —
від 0.0.1 (2012) до поточної 26.x: сайт у стані на день кожного релізу, журнал змін, нотатки релізів GitHub, README
кожної версії й історія версій у реєстрі npm. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Три епохи сайту

Документація i18next за чотирнадцять років тричі переїжджала, і кожна епоха — окреме джерело:

| Версії | Де жив сайт | Що там |
|--------|-------------|--------|
| 0.0.1–1.10.6 | гілка `gh-pages` репозиторію `i18next/i18next` (тоді домен i18next.com, тепер i18next.github.io/i18next) | ініціалізація, можливості, jQuery, шаблони, нотатки релізів; з 09.2012 — ще й сторінки версії для Node.js |
| 2.0.0–8.2.1 | репозиторій `i18next/i18next.com` (сайт на Gatsby, тепер позначений застарілим) | API, опції, екосистема, перехід між версіями, формат JSON, власні плагіни |
| 8.3.0–26.x | репозиторій `i18next/i18next-gitbook`, з якого GitBook збирає нинішній www.i18next.com | огляд, функція `t`, принципи, «як зробити», TypeScript, посібник переходу |

Знімок версії — вершина гілки сайту на мить перед виходом наступної версії тієї ж лінії: тоді документація саме цю
версію й описувала. Для найновішої версії знімок — сьогоднішній стан. Документ — неповторна пара «шлях, вміст»:
сторінка, що не мінялася через сто релізів, лежить один раз, а в рядку `# версія:` — усі ці релізи.

**0.x–1.x у npm — інший пакет.** Під ім'ям `i18next` до 2.0.0 у npm виходила версія для Node.js (репозиторій
`i18next-node`, тепер застарілий); браузерна версія 1.x у npm під цим ім'ям не виходила. Тому фільтр `version: "1"`
лишає сайт 1.x (обидві половини: браузер і Node.js), журнал змін i18next-node і записи 1.x журналу i18next, де
описано браузерну версію. Перехід 1.11 → 2.0 описано в посібнику переходу нинішнього сайту.

Разом 1915 документів; фрагментів в індексі — 3 140 (`expected_passages` у `checks.json`). 280 документів власних
фрагментів не дають: їхні розділи дослівно ті самі, що в сусідніх редакціях, і злилися з ними разом із версіями.

Замір `quality` на першому корпусі: по словах 6 із 10, за змістом 5, разом 5; десятка «як модель» — 10 із 10.
Промахи першої десятки (переказ питання своїми словами, без назви опції):

- **«insert a user name into a translated sentence»** — першим стоїть розділ «insert values into your translation»
  сайту 1.x: його слова збігаються з переказом дослівно, а сторінка Interpolation нинішнього сайту так не каже.
- **«use another language when a key is missing in the current one»** — слова «missing» і «key» ведуть до опцій
  розділу «Missing keys» (`saveMissing`), а не до сторінки Fallback.
- **«reference one translation from inside another one»** і **«get a list of strings back instead of a single
  text»** — сторінки Nesting та Objects and Arrays цими словами не говорять; «list» до того ж веде до формату `List`.
- **«switch the app to another language at runtime»** — за змістом знаходиться `changeLanguage` старого сайту 2.x–8.x,
  а не розділ нинішньої сторінки API.

Поле `max_per_doc` заміряно 0/1/2/3: разом 5 скрізь, по словах 6/6/7/6, «як модель» 10/8/10/10 — поле не ввімкнене.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Версії сайт бере з реєстру npm
  сам, а репозиторії кожної епохи перелічено в полі `eras`.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df i18next <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| сайт 2.x–26.x | версії — реєстр npm; історія гілки й дерево кожного знімка — GitHub API; текст — `raw.githubusercontent.com` | `ghsite-dated` |
| сайт 1.x | те саме, сторінки — зібраний HTML | `ghsite-dated-html`, новий |
| журнали змін | один файл на журнал | `changelog-v` |
| нотатки релізів | GitHub API | `ghreleases` |
| реєстр npm | registry.npmjs.org, одне звернення | `npm-versions` |
| README версій | `gitHead` кожної версії з реєстру | `npm-readme` |

Читач `ghsite-dated-html` додано разом із цим примірником (`engine/readers/ghdatedhtml.py`). Він бере знімки так само,
як `ghsite-dated`, але читає готові `.html`: джерело сайту 1.x на гілці мінялося (спершу markdown, потім шаблони
Jade), і спільний для всіх епох лише зібраний HTML. Поля `start` і `end` відрізають шапку з меню й підвал.

Особливості, які варто знати:

- **Адреса в шапці документа — blob на GitHub** саме того коміту, з якого взято знімок: сайт показує лише поточну
  редакцію, а GitBook і зовсім не зберігає старих.
- **Блоки GitBook** (`{% hint %}`, `{% tabs %}`, `{% code %}`) пропускаються, а їхній вміст лишається: приклади
  JavaScript і TypeScript на сторінках стоять поруч, кожен зі своєю мовою блоку коду.
- **Сторінки, що переїхали.** У перші дні GitBook (травень 2017) сторінки лежали в корені (`api.md`, `plurals.md`), а
  потім переїхали в теки (`overview/api.md`). Поле `slug_rewrite` у `config.json` дає старим редакціям ключ нових
  (`api` → `overview-api`), тож однакові розділи зливаються в один фрагмент.
- **Що зі старого сайту 2.x–8.x не взято.** Інтерактивні приклади `translate/*` і таблиця суфіксів множини —
  компоненти React, чий зміст складався в браузері з коду й файлів перекладів; їхній текст — обривки, а не
  документація. Самі можливості (інтерполяція, вкладення, контекст, множина) описано на сторінках API й опцій того
  самого сайту.
- **Альфи й бети 2.0.0** у реєстрі є, але не беруться жодним джерелом: корпус — лише стабільні версії.
- **Редакції того самого файла зливаються (`revision_suffix`)**: ім'я документа несе хеш вмісту, і без поля незмінний
  розділ двох редакцій лишався б двома фрагментами.

## Межі, про які треба пам'ятати

Тут лише сам i18next. Документації react-i18next, next-i18next, бекендів (`i18next-http-backend` та інших), детекторів
мови, `i18next-cli` і locize немає: сайт i18next лише згадує їх і посилається. Код і типи TypeScript пакета не взято —
лише документацію; що каже сторінка TypeScript, те й є.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/i18next-corpus-2026-10-10.tar.gz` (2,0 МБ, 1915 текстів і паспорт;
перед видаленням розпакований окремо й звірений із диском — нуль розбіжностей). В історії git текстів немає ніде.
Архів лежить лише на цій машині.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/i18next-corpus-2026-10-10.tar.gz -C instances/i18next
./df i18next smoke
```

**Як знову винести** — після оновлення, коли `vectors` і `smoke` пройшли (вони ж збирають свіжий кеш):

```
ls -l instances/i18next/index/passages.json       # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/i18next-corpus-РРРР-ММ-ДД.tar.gz -C instances/i18next corpus
find instances/i18next/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/i18next/index/passages.json > instances/i18next/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти» і «Як повернути тексти».

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»): звірка індексу з документами і звірка паспорта з файлами.

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/i18next/index/passages.json.gz`,
далі `./df i18next vectors` заллє колекцію Qdrant (~5 хвилин).

## Установка venv

```
cd instances/i18next
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df i18next sources --why   # перелік джерел і білий список
./df i18next refresh         # завантажити все задеклароване (~45 хвилин)
./df i18next manifest        # оновити паспорт
./df i18next setup           # Qdrant чи пошук лише по словах
./df i18next vectors         # залити корпус у docs-i18next (~5 хвилин)
./df i18next smoke           # перевірки
```

Перші ~7 хвилин `refresh` журнал мовчить, а `corpus/` порожній: читач проходить історію гілок і дерево кожного з
кількох сотень знімків і лише потім починає писати файли. README кожної версії теж читаються ще до запису: щоб звести
однакові тексти, їх треба прочитати (~10 хвилин). Без токена GitHub перелік ішов би годинними вікнами по 60 звернень.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df i18next serve          # порт 8816
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8816/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user i18next-docs http://127.0.0.1:8816/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `i18next-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
