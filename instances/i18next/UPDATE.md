# Оновлення корпусу i18next

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи i18next, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версії приходять самі, джерела — ні.** Перелік версій сайти беруть з реєстру npm
(`registry.npmjs.org/i18next`, `registry.npmjs.org/react-i18next`) на кожному прогоні, тож нову версію вписувати
нікуди не треба: `refresh` сам зробить знімок сайту на її день, а журнали змін, релізи, реєстр і README всіх пакетів
підхоплять її так само. Натомість репозиторії, з яких береться сайт, оголошено руками (поле `eras` джерел
`i18next-site`, `i18next-site-v1`, `react-i18next-site`, `i18next-vue-site` і `i18next-vue-site-vue2`): якщо сайт
переїде в інший репозиторій, оновлювач туди не піде, доки нову епоху не вписано. Так вимагає білий список. Так само
руками оголошено й самі пакети: новий пакет організації в корпус не потрапить, доки для нього немає джерел (крок 2а).

Друге правило: **нова версія змінює й старі документи.** Документ сайту — неповторний текст сторінки, а в рядку
`# версія:` стоять усі версії, у знімку яких сторінка була саме такою. Тож після нових релізів корпус перезаписується
цілком (`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version`
їх не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Завантажити.**

```
./df i18next sources --why
./df i18next refresh
./df i18next manifest
./df i18next vectors
./df i18next smoke
# Ctrl+C у терміналі з serve, і знову: ./df i18next serve
```

`refresh` без назв — повне перезавантаження: спершу перелік (історія гілок і дерево кожного знімка), потім файли.
Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти (README, розділ «Архівний режим»), а
в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

**Крок 2. Якщо вийшла нова мажорна лінія** (i18next 27.0; для супутніх пакетів — див. нижче):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзаци «Which version to search first» і «Every answer
  says which version») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "26"` — інакше модель
  і далі шукатиме в старій лінії, а нова документація у видачу не потрапить;
- лінію за замовчуванням обирають за завантаженнями npm (`api.npmjs.org/versions/i18next/last-week`): нова мажорна
  лінія стає нею не в день виходу, а коли її ставлять частіше за попередню;
- у `checks.json`, у десятці `quality_model`, замінити `"26"` на нову лінію там, де питання про поточну поведінку.

У супутнього пакета лінія за замовчуванням своя (react-i18next 17, next-i18next 15, i18next-http-backend 3,
i18next-browser-languagedetector 8, i18next-cli 1 — за завантаженнями npm на 10.10.2026). Коли найпоширенішою стає
інша, її міняють у `prompts/search.txt` (абзаци «Which version to search first» і «Every answer says which version»),
у `prompts/agent.txt` і в шести останніх запитах `quality_model`.

**Крок 2а. Новий супутній пакет.** Тими самими шарами, що й сусідні: журнал змін (`changelog-heading` чи інший читач
за форматом заголовків, `name_prefix` — назва пакета), реєстр (`npm-versions`, `name_prefix`, `skip_versions: "-"`),
README кожної версії (`npm-readme` з `{gitHead}`), нотатки релізів, якщо пакет їх пише (`ghreleases`, `name_prefix`).
Далі — назва пакета в переліках `prompts/search.txt`, `prompts/loaded.txt` і `prompts/agent.txt` («Call it as well…» і
«Do not call this…»), рядок у таблиці «Супутні пакети» README і запит у `quality_model`.

**Крок 3. Якщо сайт переїхав.** www.i18next.com збирає GitBook із репозиторію `i18next/i18next-gitbook`. Якщо сайт
перенесуть в інший репозиторій чи теку, остання епоха в `eras` джерела `i18next-site` дістає поле `before` (мить
переїзду), а нова епоха з новим `repo` і `include` дописується після неї; нові адреси — у `within`.

## 2. Особливі місця

- **0.x–1.x у npm — інший пакет.** Під ім'ям `i18next` до 2.0.0 виходила версія для Node.js (репозиторій
  `i18next-node`, тепер застарілий). Тому для 0.x–1.x README не береться (він лише посилався на сайт), журнал змін —
  окремий (`i18next-node-changelog`), а сайт — гілка gh-pages репозиторію i18next (`i18next-site-v1`).
- **Старі епохи сайту не змінюються.** Гілку gh-pages узято до 12.12.2015 (сайт тоді переїхав на нову адресу), а
  репозиторій i18next.com — до 20.05.2017 (перша правка GitBook). Пізніші коміти цих гілок — дрібні правки посилань
  у вже покинутих сайтах, і в корпус вони не потрапляють навмисно.
- **Альфи й бети 2.0.0** у реєстрі є, але не беруться жодним джерелом: корпус — лише стабільні версії.
- **Сайт react-i18next — з 4.1.0.** Репозиторій `react-i18next-gitbook` має порожній шаблонний коміт 2016 року, а
  справжній сайт — з 30.05.2017. Поле `only` джерела `react-i18next-site` тому відкидає 0.x–3.x і 4.0.0: без нього
  ці версії дістали б шаблон GitBook замість документації. Тека `legacy-v9` належить лише лінії 9 (`line_marker`).
- **Журнал i18next-cli** пише заголовок версії двома видами (`## [1.56.11](<адреса>) - дата` до 1.56.11, голий номер
  далі); бере обидва читач `changelog-bracket`. Якщо `refresh` пише записів менше, ніж версій у реєстрі, — формат
  змінився втретє.
- **next-i18next.** Журнал змін — з 11.0.0, старше — лише в нотатках релізів; TROUBLESHOOT.md — з 12.x (версії без
  файла `npm-readme` пропускає й називає в журналі прогону). Сайт next.i18next.com — демонстраційний застосунок, не
  документація.
- **i18next-vue** тримає документацію на двох гілках: `docs` для Vue 3 (2.x–5.x) і `vue-2-docs` для Vue 2 (1.x).
  Якщо вийде нова мажорна лінія для Vue 2 чи гілку перейменують, міняють поле `only` чи `branch` відповідного джерела.
- **i18next-parser** тримає частину документації в теці `docs/` (`migration.md`, `examples.md`): це окремі джерела
  `i18next-parser-migration` і `i18next-parser-examples`. Пакет позначено застарілим, репозиторій — в архіві.
- **Версії без `gitHead`.** У кількох пакетів (scanner, parser, conv, ng-i18next, icu, i18next-client) реєстр не
  записав коміт для частини версій; поле `tag` джерела README каже, яким тегом його замінити (`v{version}` чи
  `{version}`). У bs-react-i18next єдина версія без коміту й тегів, і README береться з гілки `master`.

## 3. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік кількох сотень дерев іде
годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df i18next refresh > instances/i18next/out/refresh.log 2>&1 &
```

Перші ~7 хвилин журнал мовчить, а `corpus/` порожній: читач проходить історію гілок і дерево кожного знімка. Стан
видно за кількістю файлів: `ls instances/i18next/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df i18next quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія — 26** (супутні пакети — свої лінії). Що міняти з новою мажорною лінією — крок 2 розділу «1. Вийшли
  нові релізи» вище.
- **Правила промпту, що вже є:** спершу лінія 26; запит — назвою опції, методу чи поняття, а не описом; питання про
  історію — по пунктах, з версією й документом при кожному; кожна відповідь каже, для якої версії вона, а без
  названої версії — відповідає для 26.x і пропонує назвати свою.
- **Останній результат** — у README, абзац «Замір `quality`».
