Search the official i18next documentation -- the site www.i18next.com on every stable release
from 2.0.0 to the current 26.x line, the older i18next.com site of 2.x-8.x and the 1.x site --
together with the CHANGELOG of i18next and of the old i18next-node, the GitHub release notes, the
README of every version and the npm registry history of the i18next package; and the same for five
companion packages: react-i18next (the site react.i18next.com on every release from 4.1.0, its
CHANGELOG, README and npm history), next-i18next, i18next-http-backend,
i18next-browser-languagedetector and i18next-cli (README of every stable version, CHANGELOG, npm
history; next-i18next also its GitHub release notes and TROUBLESHOOT.md). Return the matching
excerpts with the versions each one belongs to.

Call this when a question is about i18next itself -- init and its configuration options,
i18next.t and its options, interpolation (escaping, nesting of values, formatting, the built-in
Formatter and Intl), plurals and the plural suffixes (_one, _other, _zero, the JSON v4 format),
context, nesting ($t()), objects and arrays (returnObjects), namespaces, fallback languages and
fallback namespaces, translation resolution, keySeparator and nsSeparator, the instance API
(use, init, changeLanguage, language and languages, loadNamespaces, loadLanguages, reloadResources,
getFixedT, exists, addResourceBundle and the rest of the resource API, events, createInstance,
cloneInstance), plugins (backends, language detectors, post processors, formatters, loggers,
3rdParty modules) and writing your own, caching and backend fallback, the JSON format versions,
TypeScript (CustomTypeOptions, resources typing, the selector API of t), extracting translations,
and the migration guide between major versions. Example query: "interpolation escapeValue".

Call it as well for the five companion packages: react-i18next (useTranslation, withTranslation,
the Translation render prop, Trans and IcuTrans, I18nextProvider, initReactI18next, Suspense and
useSuspense, SSR with useSSR, testing, TypeScript, migrating v9 to v10); next-i18next
(next-i18next.config.js, appWithTranslation, serverSideTranslations, getStaticProps and
getServerSideProps, the App Router support of 16.x, troubleshooting); i18next-http-backend
(loadPath, addPath, parse, request, crossDomain, reloadInterval); i18next-browser-languagedetector
(order, lookupQuerystring, lookupCookie, lookupLocalStorage, caches, convertDetectedLanguage,
custom detectors); i18next-cli (init, extract, types, sync, lint, status, rename-key, the
i18next.config file, plugins).

Do not call this for any other package of the ecosystem -- i18next-fs-backend,
i18next-http-middleware, i18next-icu, i18next-resources-to-backend, the chained or localStorage
backends, i18next-parser, i18next-scanner, locize, vue-i18next -- nor for next-intl, react-intl or
FormatJS, beyond what the documentation here says about them: their own documentation is not
here, and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "26" keeps every 26.x document, "25.10" keeps
25.10.x, "1" keeps 1.x; leave it empty to search everything. The filter knows only numbers, not
packages: every package has its own numbering, so "15" keeps i18next 15.x, react-i18next 15.x and
next-i18next 15.x alike -- read the document titles, which name the package. Every excerpt
comes back with `versions`: each version whose documents contain this exact text, newest first --
text that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lived. From 8.3 (May 2017) to today it is www.i18next.com, built by
GitBook from the repository i18next/i18next-gitbook: pages titled by their path, such as
"overview/configuration-options", "translation-function/plurals", "misc/migration-guide". For
2.x-8.2 it is the older site of the repository i18next/i18next.com: pages titled "docs/api",
"docs/options", "docs/migration", "translate/interpolation" and similar. The npm package i18next
of 0.x-1.x was the Node.js version (i18next-node); its documentation is the 1.x site, kept on the
gh-pages branch of i18next/i18next, with pages for the browser version ("pages/doc_init",
"pages/doc_features") and for Node.js ("node/pages/doc_init"), and its changes are in the
i18next-node Changelog. The i18next Changelog itself covers the browser version 0.9-1.11.2 and
then the single package from 2.0.0 on.

The companion packages. react-i18next has its own site from 4.1.0 (May 2017), react.i18next.com,
built from i18next/react-i18next-gitbook: pages titled by their path, such as
"latest/usetranslation-hook", "latest/trans-component", "guides/quick-start"; pages under
"legacy-v9" describe 9.x only; before 4.1.0 the README was the whole documentation. The other four
packages are documented by their README alone, kept once per distinct text with every version it
shipped with ("next-i18next README", "i18next-cli README"), next to their changelogs ("i18next-cli
Changelog: 1.75.2") and the npm registry history of each.

Which version to search first. For a question about how to do something today with i18next
itself, pass `version` "26": without it, the many editions of older pages can take places with the
current ones. If the user's project runs another line, pass that line instead -- 25 and 23 are
still widely installed. For a companion package, put its name in the query ("react-i18next Trans
component", "next-i18next serverSideTranslations") and pass that package's line if the user named
one; the lines installed most today are react-i18next 17, next-i18next 15, i18next-http-backend 3,
i18next-browser-languagedetector 8 and i18next-cli 1. Search without `version` when the question
is about history, or when the line gave nothing that answers.

Name the option, method or concept the way the documentation titles it, not in the user's own
words: "fallbackLng", "returnObjects", "keySeparator", "changeLanguage", "plural suffix",
"compatibilityJSON", not "what happens when a word is missing". For a question about when
something appeared, changed or disappeared, search more than once: without `version` first, to
find the changelog entry or migration-guide section that names the exact version, then with the
versions around it, to see how the documentation described it before and after.

Write the query in English, with the names i18next itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into i18next terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line -- i18next 26.x, react-i18next 17.x, next-i18next 15.x, i18next-http-backend 3.x,
i18next-browser-languagedetector 8.x, i18next-cli 1.x -- say so in the answer ("for i18next 26.x
and react-i18next 17.x"), and add that for a precise answer about another version the user can
name it. When the excerpts behind a statement come only from
older versions, name those versions instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація i18next" (or the package's name). Identifiers, API names and
titles stay in English, spelled exactly as the documentation spells them. Build the answer out of
the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before
describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
