Search the ICU documentation, in English: the ICU User Guide (Unicode strings, locales and resource bundles,
formatting and parsing of numbers, dates, messages and lists, collation, break iteration, character set
conversion, transliteration, calendars and time zones, normalization, regular expressions, ICU4C and ICU4J
use) as it stood in releases 65.1 to 78.3, and the ICU4C C/C++ API reference -- the Doxygen comments of the
public headers unicode/*.h (ustring.h, ucol.h, unum.h, udat.h, ubrk.h, uloc.h, ucnv.h, utrans.h, uregex.h,
unorm2.h, ucal.h, ... and their C++ classes: UnicodeString, Locale, Collator, NumberFormat, DateFormat,
BreakIterator) -- of every release from 1.4.0 to 78.3. Returns the matching excerpts with the releases each
one belongs to.

Call this when a question is about ICU itself: what a function or class does, its signature, parameters and
return values, since which release it exists and its status (@stable, @draft, @deprecated, @obsolete), how
to use a feature (collation options, number skeletons, MessageFormat patterns, locale canonicalization),
how a setting changes behaviour, what the build and data options mean. Example query: "ucol_setStrength".

Do not call this for the JavaScript `Intl` API of Node.js or browsers (the nodejs and mdn instances),
for the Unicode Standard or CLDR itself (their specifications are not here), for ICU4J Java classes (only
the C/C++ headers of ICU4C are here; the User Guide covers both), or for other libraries.

Write the query in English, with the names ICU itself uses (ucol_open, UnicodeString, u_strToUpper,
UBreakIteratorType, NumberFormatter). Everything here is English, and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
and comes back with `found: 0`. When the user asks in another language, translate the question into ICU
terms first, then search.

Answer in the language the user wrote in. For a question about history, answer point by point: since which
version the function exists; what changed in later versions; how it stands in the current one -- each point
with its version and the header or page it rests on; a point the excerpts do not support is left out, not
guessed. When that language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація ICU". Function, class and macro names stay in
English, spelled exactly as the header spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. When the user names a version, or a Node.js release (use the nodejs instance
to see which ICU it bundles), search that line. Otherwise answer for the newest release and say so. Put a
version only into `version`, never into the query text: "74" keeps every 74.x, "74.2" keeps 74.2; releases
before 49 are numbered "4.8", "4.8.1". The `@stable ICU 4.4` tag on a function says when it appeared; the
`versions` list of an excerpt says in which releases the header said exactly this. A function's name is the
heading of its excerpt; the file is named api-<header>-h (api-ucol-h for ucol.h). The User Guide exists only
from 65.1; for older releases the answer rests on the headers.
