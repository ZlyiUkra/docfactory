# Оновлення корпусу iron-session

Перелік версій тут не оголошується руками: читачі пакетів беруть його з опису пакета в реєстрі npm
(`https://registry.npmjs.org/iron-session`, `…/next-iron-session`, `…/iron-webcrypto`), тож нова версія потрапляє в
корпус сама, коли вийде в npm. Журнали змін беруться з гілки `main` репозиторіїв `vvo/iron-session` і
`brc-dd/iron-webcrypto`, нотатки релізів — з API релізів `vvo/iron-session`.

Руками оголошено лише теги репозиторію `vvo/iron-session`: поле `tags` джерел `iron-session-examples` (приклади) і
`iron-session-security` (`SECURITY.md`). Новий стабільний тег дописують у обидва переліки першим рядком, у вигляді
`"v9.1.0": "9.1.0"`.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df iron-session check                 # чи змінилося щось нагорі за джерелом
./df iron-session refresh               # повне перезавантаження, близько 7 хвилин
./df iron-session manifest
./df iron-session vectors
./df iron-session smoke
# Ctrl+C у терміналі з serve, і знову: ./df iron-session serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (README, що не змінився, дописує нову версію в рядок `# версія:`).

Якщо вийшла нова мажорна лінія:

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінію за
  замовчуванням: вона — найпопулярніша за завантаженнями npm (на 13.10.2026 — 8.x, 56 %; друга — 6.x, 40 %; 9.x —
  4 %), і де дві лінії близькі, відповідь дається для обох;
- у `checks.json`, у десятці `quality_model`, замінити `"8"` там, де питання про поточну поведінку, і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у `.env`) потрібен для дерев тегів (55 звернень) і релізів: без нього вистачає годинного
вікна в 60 звернень лише впритул.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df iron-session quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
