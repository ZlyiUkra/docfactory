# jose — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про jose — пакет npm, який реалізує стандарти JOSE: JSON Web Token
(JWT), підпис (JWS), шифрування (JWE), ключі (JWK) і набори ключів (JWKS) на Web Crypto API — у Node.js, браузерах,
Deno, Bun, Cloudflare Workers та інших середовищах edge. Документація — усіх стабільних версій бібліотеки panva/jose
разом із її першою назвою @panva/jose. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`;
ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

jose стоїть усередині багатьох бібліотек: next-auth 4 бере jose 4, `@auth/core` і better-auth — jose 6, openid-client
— теж jose. Документація Next.js (глава `How to implement authentication`) будує сесію саме на jose: функція там
зветься `encrypt`, але всередині — підпис (`SignJWT`, `jwtVerify`), а не шифрування (`EncryptJWT`, `jwtDecrypt`).
Сайту документації в jose немає: довідник лежить у теці `docs/` репозиторію, і API змінювався з кожною мажорною
лінією. Тут — усі версії поруч, тож на питання «як це в моїй версії» є відповідь саме для неї.

| жовтень 2021 | jose | 4.0–4.15 | усе — з кореня `jose` замість підшляхів; `importJWK`, `exportJWK`, `calculateJwkThumbprint` |
| жовтень 2023 | jose | 5.0–5.10 | `Uint8Array` замість `Buffer`, PBES2 лише з явним дозволом, без Node.js, що вийшли з підтримки; довідник за модулями `jwt/`, `jws/`, `jwe/`, `jwk/`, `jwks/`, `key/`, `util/`, `types/` |
| лютий 2025 | jose | 6.0–6.2 | без `KeyLike` (лише `CryptoKey`, `KeyObject`, `Uint8Array`), `createRemoteJWKSet` на `fetch`, без Node 18 |

Завантаження за тиждень (13.10.2026): 6.x — 64 %, 5.x — 22 %, 4.x — 13 %, решта — менше відсотка.

Разом 7 301 документ. Однакові розділи редакцій у кеші зливаються в один фрагмент з усіма версіями, тож фрагментів в
індексі — 8 413 із 3 378 документів (`expected_passages` у `checks.json`). Ще 13 записів журналу в оригіналі порожні
(лише заголовок версії) і не записуються; для дев'яти з них опис є в нотатках релізів.

Чому 3.x так багато: кожна сторінка довідника 3.x несе рядок імпорту для Deno з номером версії
(`deno.land/x/jose@v3.20.4/…`), тож кожен реліз дає нову редакцію кожної сторінки. Злиття однакових розділів у кеші
прибирає ці повтори з видачі.

Замір `quality` на першому корпусі: по словах 4 із 10, за змістом 4, разом 5; десятка «як модель» — 10 із 10. Цілі
питань своїми словами охоплюють і довідник 1.x–2.x (`docs/README.md`: `JWT.verify`, `JWK.asKey`, `JWT.decode`) — це
відповіді для тих версій. Промах «як модель» на «6.0.0 BREAKING CHANGES» розібрано до кореня: числа в тексті запиту
тягнули документи реєстру npm, де перелічено всі релізи; промпт тепер велить класти номер версії лише в параметр
`version`, і запит «BREAKING CHANGES» з `version` "6" знаходить запис журналу 6.0.0 першим. `max_per_doc` заміряно: 1
знижує першу десятку до 3, 2 — до 4; лишено 0.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df jose <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| тека `docs/` | дерева тегів `panva/jose`, тексти з raw.githubusercontent.com; 3.x — окремим джерелом `jose-docs-3` | `ghdocs-history-typedoc`, новий |
| `README.md`, `SECURITY.md` | ті самі теги, лише файли кореня | `ghdocs-history-typedoc` |
| журнал змін | `CHANGELOG.md` гілки main | `changelog-conventional` |
| нотатки релізів | API релізів `panva/jose`, поле `skip` лишає 35 | `ghreleases` |
| реєстр npm | registry.npmjs.org, одне звернення на пакет | `npm-versions` |

Читач `ghdocs-history-typedoc` додано разом із цим примірником (`engine/readers/ghtypedoc.py`). Він бере
документацію так само, як `ghdocs-history`, і доробляє готовий текст довідника TypeDoc:

- **Підзаголовки членів стають підписами** (поле `inline_titles`): «Parameters», «Returns», «Type Parameters»,
  «Call Signature» та інші. Окремими розділами вони давали фрагменти з одного рядка, а опис методу відривався від
  його параметрів.
- **Однакові службові розділи вирізаються** (поле `drop_titles`): «💗 Help the project» на кожній сторінці 5.x–6.x,
  «Sponsor» і «Support» (прохання підтримати автора), «Table of contents» у 3.x, «Defined in» у 3.x (файл і рядок
  коду, що зсуваються з кожним релізом і не дали б розділам злитися між редакціями).

Особливості корпусу:

- **Три вигляди довідника.** 0.9–2.x — один великий `docs/README.md`; 3.x–4.x — TypeDoc у теках `classes/`,
  `functions/`, `interfaces/`, `modules/`; 5.x–6.x — за модулями. Та сама сторінка (`jwtVerify`) у старому й новому
  вигляді має різні імена документів; фільтр версії розводить їх сам.
- **Нотатки релізів — лише ті, що доповнюють журнал.** 222 з 257 повторюють `CHANGELOG.md` слово в слово (звірено
  13.10.2026); беруться 35: латки старших ліній, випущені з гілок поза main (2.0.7, 3.20.4, 4.15.x), і релізи з
  довшим описом (5.9.0, 4.12.0 тощо).
- **Вимога до Node (`engines`)** записана в документах реєстру npm лише для 1.x–2.x (`>=10.13.0`); з 3.x поля немає,
  а відмова від Node 18 — у журналі змін 6.0.0.
- **Документ — неповторний текст.** Версії, де файл не змінився, ділять один документ; у рядку `# версія:` стоять усі.

## Межі, про які треба пам'ятати

Текстів RFC (JWT, JWS, JWE, JWK, JWA) тут немає — вони в примірнику `webstandards`; немає й клієнтів OAuth та
OpenID Connect (openid-client), бібліотек автентифікації, що беруть jose всередину (Auth.js, Better Auth, Clerk,
iron-session — для них є свої примірники `auth`, `clerk`, `iron-session`), Next.js і модуля `crypto` Node.js. Код
бібліотеки (`src/`), тести, `CONTRIBUTING.md` і `CODE_OF_CONDUCT.md` не входять. Чужа бібліотека jose 0.1–0.3 (2015)
— лише рядком реєстру.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/jose-corpus-2026-10-13.tar.gz` (7 301 текст, паспорт і сховище сирого
`raw/`; перед видаленням текстів розпакований окремо й звірений із диском). В історії git текстів немає ніде. Архів
лежить лише на цій машині. Сховище `raw/` після звірки теж видалено з диска.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/jose/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/jose-corpus-РРРР-ММ-ДД.tar.gz -C instances/jose corpus raw
find instances/jose/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/jose/raw
gzip -9 -c instances/jose/index/passages.json > instances/jose/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/jose-corpus-2026-10-13.tar.gz -C instances/jose
./df jose smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/jose/index/passages.json.gz`, далі
`./df jose vectors` заллє колекцію Qdrant (близько 20 хвилин на процесорі).

## Установка venv

```
cd instances/jose
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df jose sources --why                  # перелік джерел і білий список
./df jose refresh jose-docs-3            # 3.x, близько 1 год 45 хв — можна паралельно з наступним
./df jose refresh jose-docs              # решта тегів, близько 1 год
./df jose refresh jose-repo jose-changelog jose-releases jose-npm panva-jose-npm
./df jose manifest                       # оновити паспорт
./df jose setup                          # Qdrant чи пошук лише по словах
./df jose vectors                        # залити корпус у docs-jose
./df jose smoke                          # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df jose serve          # порт 8834
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8834/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user jose-docs http://127.0.0.1:8834/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `jose-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
