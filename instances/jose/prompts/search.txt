Search the jose documentation -- the README, SECURITY.md and the whole docs/ folder of the
panva/jose repository at every stable release tag (v0.9.0 to v6.x, the first ones published as
@panva/jose), the changelog, the GitHub release notes that add to it, and the npm registry history
-- and return the matching excerpts with the versions each one belongs to. jose implements JOSE:
JSON Web Tokens (JWT), JSON Web Signature (JWS), JSON Web Encryption (JWE), JSON Web Key (JWK),
JSON Web Key Set (JWKS) and the key utilities around them, on the Web Crypto API -- in Node.js,
browsers, Deno, Bun, Cloudflare Workers and other edge runtimes (from 3.x; 1.x-2.x ran on Node
only, with an API of its own: JWK.asKey, JWS.sign, JWT.verify).

Call this when a question is about jose itself -- SignJWT and jwtVerify (setProtectedHeader,
setIssuedAt, setExpirationTime, setIssuer, setAudience, the verify options issuer, audience,
algorithms, clockTolerance, maxTokenAge, requiredClaims), EncryptJWT and jwtDecrypt, UnsecuredJWT,
CompactSign / compactVerify, FlattenedSign, GeneralSign, CompactEncrypt / compactDecrypt,
createRemoteJWKSet and createLocalJWKSet (verifying tokens of an identity provider), importJWK,
importSPKI, importPKCS8, importX509, exportJWK, generateKeyPair, generateSecret,
calculateJwkThumbprint, decodeJwt, decodeProtectedHeader, base64url, the error classes
(JWTExpired, JWTClaimValidationFailed, JWSSignatureVerificationFailed, JOSEAlgNotAllowed ...) and
their codes, the supported algorithms (HS256, RS256, PS256, ES256, EdDSA, Ed25519, RSA-OAEP,
ECDH-ES, A256GCM, dir ...) and runtimes -- and above all history and compatibility: since which
version a function, option or algorithm exists, what was renamed or removed between majors
(1 -> 2 -> 3 -> 4 -> 5 -> 6), which versions run on which Node.js (the `engines` field of each
version is written in the npm registry documents). Example query: "jwtVerify audience issuer".

Do not call this for JWT as a standard beyond what the jose documentation says (the RFCs), for
OAuth 2.0 and OpenID Connect clients, for authentication libraries (Auth.js, Better Auth, Clerk,
iron-session) that use jose inside, for Next.js or for Node.js crypto itself: their documentation
is not here, and the search will return jose excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line: "6" keeps every 6.x document, "4.15" keeps
4.15.x; leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which
to which version the documentation said exactly this.

Write the query in English, with the names jose itself uses ("jwtVerify", "SignJWT",
"createRemoteJWKSet", "importPKCS8", "JWTExpired"), not in the user's own words. Everything here is
English -- the excerpts, the word index and the meaning index alike -- and the word index keeps
only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into jose terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація jose". Identifiers, option names, algorithm names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts
that came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something, pass `version` "6" --
the most downloaded line. If the user names a version, or their code shows one (JWK.asKey,
JWS.sign, JWT.verify -> 1.x-2.x; the KeyLike type -> 3.x-5.x, it is gone in 6.x), search that
line. Put a version only into `version`, never into the query text: numbers in the query match
the npm registry documents, which list every release, instead of the text you need. For what a
major line changed or removed, search "BREAKING CHANGES" with `version` set to that line. Search
without `version` when the question is about history, or when the line gave nothing. The API changed with every major line, so an answer taken
from the wrong line can be confidently wrong. Every answer says which version it is for; when the
user did not name one, answer for 6.x and say so ("for jose 6.x"). When the excerpts behind a
statement come only from older versions, name those versions instead of presenting the text as
current.
