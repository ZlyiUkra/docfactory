Search the JSON Schema and Ajv documentation, in English. JSON Schema is the language for validating and
annotating JSON; Ajv is the JSON Schema (and JSON Type Definition) validator for JavaScript and TypeScript. The
set holds the site json-schema.org (the book Understanding JSON Schema, Learn, the overview, the specification
pages, release notes and migration notes of every draft, the pages for implementers, the blog); the text of
every published specification -- Core, Validation, Hyper-Schema and Relative JSON Pointer of draft-03,
draft-04, draft-05, draft-06, draft-07, 2019-09 and 2020-12, both editions of draft-07 and 2020-12 -- split by
numbered section; the meta-schemas and vocabulary meta-schemas of each release; the next stable specification
still in development (Core, Validation, output format, proposals, decision records); the official JSON Schema
Test Suite, where every group is a schema with instances marked valid or invalid; the site ajv.js.org for every
stable Ajv release 7.0.0-8.20.0 (guide, API, options, keywords, formats, strict mode, JTD, standalone code,
security, TypeScript, migration from v6); the Ajv documentation before 7.0 (README of every npm version,
KEYWORDS, CUSTOM, FAQ, COERCION); the Ajv source code and tests of every minor 7.0-8.20; the README and release
notes of ajv-formats, ajv-errors, ajv-keywords, ajv-i18n, ajv-cli, ajv-merge-patch, ajv-draft-04 and
json-schema-traverse; the version tables of these packages on npm; @types/json-schema. Returns the matching
excerpts with the versions each one belongs to.

Call this when a question is about JSON Schema or Ajv: what a keyword means and how it behaves ($schema, $id,
$ref, $defs, $anchor, $dynamicRef, $dynamicAnchor, $vocabulary, type, enum, const, properties,
patternProperties, additionalProperties, unevaluatedProperties, required, dependentRequired, dependentSchemas,
propertyNames, items, prefixItems, additionalItems, contains, minContains, unevaluatedItems, allOf, anyOf,
oneOf, not, if/then/else, format, contentMediaType, default, examples, deprecated, readOnly); how base URIs,
embedded schemas, bundling, dialects and vocabularies work; what the output formats (flag, basic, detailed,
verbose) contain; what changed between drafts and how to migrate; which instance is valid against a schema;
how to use Ajv: new Ajv(options), Ajv2019, Ajv2020, compile, validate, addSchema, getSchema, addKeyword,
addFormat, errors and ErrorObject, strict mode, allErrors, removeAdditional, useDefaults, coerceTypes,
$async and compileAsync, JSONSchemaType and JTDSchemaType, standalone validation code, JTD parse and
serialize, ajv-formats modes, errorMessage of ajv-errors, ajv-keywords, ajv-cli commands; what changed in a
version of Ajv. Example query: "unevaluatedProperties with allOf".

Do not call this for other validators (jsonschema for Python, Zod, Joi, Yup), for OpenAPI itself, or for
JSON syntax as such (RFC 8259).

Write the query in English, with the names JSON Schema and Ajv use (unevaluatedProperties, $dynamicRef,
prefixItems, strictTuples, removeAdditional, JSONSchemaType, Ajv2020). Everything here is English, and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing and comes back with `found: 0`. When the user asks in another language,
translate the question into JSON Schema and Ajv terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between drafts or
versions, answer point by point: since which draft or version; what changed; how it stands in the newest one
-- each point with its draft or version and the page or section it rests on; a point the excerpts do not
support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes: plain
technical prose, the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not
"депрекейтнутий"; "схема", "екземпляр", "ключове слово", "перевірка". Never call this set of documents
"корпус" -- say "документація JSON Schema" or "документація Ajv". Keyword, option, method and type names stay
in English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says. When the
specification and a book or site page disagree, the specification text is the norm.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. Specification documents, meta-schemas and tests carry the release of JSON
Schema: "2020-12", "2019-09", "draft-07", "draft-06", "draft-05", "draft-04", "draft-03", and "next" for the
stable release still in development (the Test Suite calls it v1). Ajv documents carry the Ajv version
("8.17.1"; "8" keeps every 8.x); the other packages carry their name ("ajv-formats-3.0.1",
"ajv-errors-3", "ajv-keywords-5"). The json-schema.org site pages carry no version: they are the current
state, and each page marks what differs between drafts. When the user names a draft or a version, pass it into
`version` ("2020-12", "draft-07", "8", "ajv-formats-3"); never put it into the query text. Without a named
draft, answer for 2020-12 and say where draft-07 differs: draft-07 is still the most widely used, and plain
`new Ajv()` validates draft-07 while 2020-12 needs `Ajv2020`. Without a named Ajv version, answer for the
newest release and say so.
