# Оновлення корпусу konva

README (`npm-readme-*`) і реєстр (`npm-*`) беруть версії з опису пакетів у реєстрі npm, тож новий реліз konva,
react-konva чи react-konva-utils потрапляє туди сам. Журнал змін (`changelog-konva`), нотатки випусків
(`release-notes-react-konva`) і релізи GitHub (`releases-*`) читаються щоразу заново з гілки `master` і з API.
Передрелізи не беруться (`skip_versions: "-"` у README, `"stable": true` у релізах).

Руками оголошено:

- **Сайт** (`site`): поле `tags` тримає один рядок «SHA коміту → версія». Репозиторій `konvajs/site` тегів не
  ставить, тому знімок сайту — це коміт гілки `master`, а його мітка — остання на той день версія konva з реєстру npm
  (`"dc0f3676…": "10.9.1"`). Щоб оновити сайт, беруть SHA найновішого коміту
  (`git ls-remote https://github.com/konvajs/site master`) і мітку `latest` пакета konva, і замінюють рядок. Старий
  рядок не лишають: сайт описує лише поточну Konva, і два знімки під різними мітками видавали б учорашній текст за
  документацію старої версії.
- **Приклади** (`site-svelte-demos`, `site-react-demos`): той самий SHA стоїть в адресі дерева (`url`) і та сама
  мітка — у полі `version`. Їх міняють разом із `site`.
- **Адреси сторінок** (поле `site` джерела `site`): сторінка, чию адресу задає `slug` шапки, а не ім'я файла, має
  власний рядок. Після оновлення адреси звіряють із `https://konvajs.org/sitemap.xml`: нова стаття в `content/docs/posts`
  з іменем файла, відмінним від `slug`, потребує нового рядка.
- **Таблиця сумісності react-konva** (`react-konva-docs`): поле `tags` — останній тег react-konva
  (`"v19.3.2": "react-konva-19.3.2"`); з новим релізом рядок замінюють.
- **Нова обгортка** (якщо знадобляться `vue-konva`, `svelte-konva` чи `ng2-konva`) — нові джерела `npm-readme`,
  `npm-versions` і `ghreleases` за зразком react-konva, з власним префіксом версії.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df konva refresh npm-readme-konva npm-konva changelog-konva releases-konva   # або джерела react-konva
./df konva refresh --missing    # джерела, яких не названо, лише докачуються
./df konva manifest
./df konva vectors
./df konva smoke
# Ctrl+C у терміналі з serve, і знову: ./df konva serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі README стоять усі версії, де текст був таким, тож
новий реліз змінює й старі документи (незмінний README дописує нову версію в рядок `# версія:`).

## Оновився сайт

```
./df konva refresh site site-svelte-demos site-react-demos   # після заміни SHA і мітки в sources.json
./df konva manifest
./df konva vectors
./df konva smoke
```

Ім'я файла сторінки містить початок хеша її тексту (`site--content-docs-shapes-arc-1ea5e66c.txt`), тому змінена
сторінка лягає новим файлом поруч зі старим. Файли попереднього знімка, яких новий прогін не записав, переносять в
окрему теку поза корпусом руками, перш ніж рахувати вектори: інакше пошук знаходив би обидві редакції сторінки.
Сховище сирого `raw/` повертається з архіву разом із текстами, тож після правки читача тексти перебудовуються без
мережі: `./df konva build <id>`.

Якщо змінилися найпоширеніші лінії (на 17.11.2026 — Konva 10, близько 64 % завантажень; react-konva 19, близько 61 %):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінії за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"10"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторіїв і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df konva quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Останній результат — у README, розділ «Скільки цього».
