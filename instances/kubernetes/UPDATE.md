# Оновлення корпусу kubernetes

Три різні роботи: звичайне оновлення (вийшли патчі й нові лінії), нова лінія Kubernetes і новий інструмент поруч.
Порядок усередині кожної важливіший за самі команди.

**Спершу — повернути тексти.** Корпус примірника в архіві з самого початку: у `corpus/` лежить лише паспорт, а
`refresh` і `manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї —
пакують і виносять знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

Головне правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Сторінка, що зникла з документації, чи реліз, прибраний з GitHub, лишається в `corpus/`; прибрати — рішення людини.

## 1. Звичайне оновлення

Нові патчі Kubernetes (журнал змін і розклад релізів), нові релізи інструментів і правки документації на живих
гілках (`main` сайту, `release-1.N` ліній, що ще підтримуються, `main` Gateway API) підхоплюються самі: перелік
документів складається обходом оголошених гілок.

```
./df kubernetes sources --why
./df kubernetes check             # що нового й що осиротіло
./df kubernetes refresh --missing # лише нове
./df kubernetes manifest
./df kubernetes vectors
./df kubernetes smoke
# Ctrl+C у терміналі з serve, і знову: ./df kubernetes serve
```

**Чому `--missing` тут достатньо.** Документ сторінки — пара «сторінка, гілка»: ім'я файла складене зі шляху,
вмісту й гілки, а версія в шапці — версія гілки, і вона не росте з новими гілками. Змінилася сторінка на `main` —
з'явилося нове ім'я, `--missing` його докачає. Попередній документ тієї ж сторінки стає сиротою: `check` друкує
його як «зник», а прибирає людина (інакше та сама сторінка лежатиме двома редакціями з однією версією).

**Чого `--missing` не бачить.** Приклад YAML, врізка чи сторінка feature gate змінилася, а сама сторінка, що їх
показує, — ні: ім'я документа те саме, і `--missing` його не перезапише. Раз на лінію (після виходу нової версії
Kubernetes) варто перезібрати живі гілки повністю: `./df kubernetes refresh k8s-docs` (без `--missing`, кілька
годин). Журнали змін, розклад і релізи інструментів дешеві — їх можна оновлювати повністю завжди:

```
./df kubernetes refresh k8s-changelog k8s-releases gateway-releases k3s-releases traefik-releases   # і решта *-releases
```

З Claude Code довгі кроки запускати окремим процесом (`setsid nohup …`), інакше оболонка обірве їх через 30 хвилин;
поступ обходу видно в лозі рядком «пройдено N із M гілок».

Корпус комітити не треба (архівний режим): після `vectors` і `smoke` комітять паспорт `corpus/index.json` і
стиснений кеш `index/passages.json.gz`.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Нова лінія Kubernetes

Коли виходить 1.38, на сайті з'являється гілка `release-1.37`, а `main` стає 1.38. У `sources.json` джерела
`k8s-docs` (поле `refs`, «гілка → версія», від найновішого):

- `"main": "1.38"` замість `"main": "1.37"`;
- новий рядок `"release-1.37": "1.37"` одразу під ним.

Документи `main` з міткою 1.37 після цього стають сиротами (їхні тексти тепер лежать під `release-1.37` з тією ж
міткою) — `check` їх покаже. Далі — `refresh --missing k8s-docs`, у джерело `k8s-changelog` (поле `files`) —
`CHANGELOG-1.39.md`, коли він з'явиться, і кроки розділу 1. Поточну лінію в `prompts/search.txt` (абзаци «Which
version to search first» і «Every answer says») та `prompts/agent.txt` — на 1.38, у `checks.json` — `quality_model`.

Те саме для інструментів: нова гілка чи тег у `refs` (Traefik `v3.8`, Gateway API `release-1.8`, k3d `v5.10.0`,
Kustomize `kustomize/v5.9.0`, age, metrics-server), нова тека версії в `folders` (cert-manager `content/v1.21-docs`
→ "1.21" і `content/docs` → "1.22"; Helm — нова тека `versioned_docs`).

## 3. Новий інструмент поруч

Беруться лише інструменти, якими план навчання справді користується навколо кластера. Документація — читач
`site-history` за зразком найближчого джерела того самого формату (`hugo`, `mkdocs`, `docusaurus`, `markdown`) з
полем `label` (назва інструмента — префікс назви документа), нотатки релізів — `ghreleases` або `ghreleases-tagged`.
Потім кроки розділу 1, рядок у таблиці README і назва інструмента в `prompts/search.txt` та `prompts/loaded.txt`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df kubernetes quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія:** Kubernetes 1.37. `prompts/search.txt` і `prompts/agent.txt` велять шукати з нею; поточні
  лінії інструментів названо там само.
- **Правила промпту, що вже є:** запит — назвами об'єктів і полів англійською і з назвою інструмента; версія в
  кожного інструмента своя, назва документа каже, чий він; без версії — історія, сумісність і сайти без версій
  (k3s, книга kubectl, SOPS, Let's Encrypt); стан alpha чи beta називати; текст гілки «-dev» міг не вийти релізом.
- **Цілі `quality` в `checks.json` — заготовка:** імена документів записано за шляхами сторінок, але ще не звірено з
  корпусом. Перший замір покаже, які з них назвати інакше.
