Search the official documentation of Kubernetes and of the tools around a Kubernetes cluster
-- every released version: kubernetes.io/docs of every release line from 1.0 to 1.37 (concepts,
tasks, tutorials, setup, reference: the API of every object with its fields, kubectl and its
commands, kubeadm, the flags of kube-apiserver, kubelet and the other components, feature gates
with their stages, the glossary), with the YAML examples of each page inlined; the changelog of
every Kubernetes patch, alpha, beta and rc release from 1.2.0 on; the release schedule (release
dates, patch dates, maintenance mode, end of life); Gateway API (the documentation and the GEPs,
0.1 to 1.7); k3s (docs.k3s.io and the release notes of every k3s release); k3d (3.0 to 5.9);
Traefik (1.0 to 3.7: routing, providers -- Kubernetes Ingress, IngressRoute CRD and the Gateway
API provider --, middlewares, TLS and ACME, install configuration); cert-manager (1.0 to 1.21:
Issuer, ClusterIssuer, ACME HTTP-01 and DNS-01 solvers, Certificate, the API reference); Helm
(2, 3 and 4: charts, templates, the helm commands); Kustomize (1.0 to 5.8, with its examples)
and the kubectl book; SOPS; age (README and man pages, 1.0.0 to 1.3.2); metrics-server (0.1 to
0.9: README, FAQ, known issues, the Helm chart); the Let's Encrypt documentation (rate limits,
challenge types, certificate profiles and lifetimes, CAA); and the GitHub release notes of every
tool -- and return the matching excerpts with the versions each one belongs to.

Call this when a question is about running applications on Kubernetes -- Pods, Deployments,
ReplicaSets, StatefulSets, Jobs and CronJobs, Services and cluster DNS, Ingress and the Gateway
API (Gateway, HTTPRoute, GRPCRoute, ReferenceGrant), ConfigMaps and Secrets, volumes, PVC and
StorageClass, resource requests and limits, probes, rollouts and rollbacks, the
HorizontalPodAutoscaler and metrics-server, PodDisruptionBudget, namespaces, RBAC, kubectl,
kubeconfig and contexts, kubeadm and upgrades --, about a light cluster (k3s on a VM, k3d on a
laptop: install, config, bundled Traefik and ServiceLB, local-path storage), about traffic in
(Traefik routers, entrypoints, middlewares, timeouts for WebSockets), about TLS (cert-manager
with Let's Encrypt, staging and production issuers, HTTP-01 through Ingress or Gateway, rate
limits), about packaging (Helm charts and values, Kustomize bases and overlays), about secrets
in git (SOPS with age) -- and above all when it is about versions: since which version a
feature exists and in which state (alpha, beta, stable), what changed between versions, which
API version an object has in a given release, how to upgrade, which version is still supported.
Example query: "HorizontalPodAutoscaler behavior scaleDown stabilizationWindowSeconds".

Do not call this for Docker, Dockerfiles, buildx or container registries (their documentation is
not here), for Prometheus, Grafana, Loki, Argo CD, Flux, Sealed Secrets or service meshes, for
the consoles of cloud providers, or for application frameworks: their documentation is not here,
and the search will return excerpts that merely mention them, with confident-looking titles.

Whose version. Every tool numbers its own versions, and the numbers overlap: "1.36" is
Kubernetes 1.36, but cert-manager and Gateway API have 1.x lines too, and "3" is Helm 3 as well
as Traefik 3. The title says whose document it is: pages of the Kubernetes documentation have no
prefix; the others begin with the tool -- "Traefik: …", "Helm: …", "cert-manager: …",
"Gateway API: …", "Gateway API GEP: …", "k3d: …", "K3s: …", "Kustomize: …", "kubectl book: …",
"SOPS: …", "age: …", "metrics-server: …", "Let's Encrypt: …"; changelogs are "Kubernetes
changelog: v1.37.1", release dates "Kubernetes 1.36 release dates and support", release notes
"Traefik release: …", "K3s release: …" and so on. Put the tool's name in the query.

`version` narrows the search to one release line of whichever tool: "1.37" keeps Kubernetes
1.37 -- its documentation and its changelog entries 1.37.0, 1.37.1 … -- and k3s releases
1.37.x+k3sN; "3.7" keeps Traefik 3.7; "4" keeps Helm 4. Documentation is labelled by release
line ("1.36"), changelogs and release notes by the exact version ("1.36.5", "1.37.0-rc.1"). The
k3s documentation, the kubectl book, SOPS and Let's Encrypt are single, unversioned sites: a
search with `version` never returns them, so search them without it. Leave `version` empty to
search everything. Every excerpt comes back with `versions`: each version whose documents
contain this exact text, newest first -- text that stayed the same across releases is returned
once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Which version to search first. For a question about how to do something today, pass the current
Kubernetes line -- "1.37" -- or the line of the user's cluster (`kubectl version`, the k3s
version): without it, the many editions of the same page, which differ by a line or two, fill
every place with older text. For Traefik, cert-manager, Gateway API, Helm, Kustomize, k3d, age
and metrics-server pass their own current line when the user did not name one -- Traefik "3.7",
cert-manager "1.21", Gateway API "1.6", Helm "4" (or "3" for Helm 3 charts), Kustomize "5.8",
k3d "5.9" -- or search without `version`. Search without `version` for history, for upgrades,
for compatibility and for the unversioned sites.

Feature states. A page of the Kubernetes documentation says the state of a feature in a line
"Feature state: Kubernetes v1.33 [stable]" (or [alpha], [beta], [deprecated]), sometimes with
the feature gate and whether it is enabled by default; the page of each feature gate lists its
stages with versions. An alpha feature is off by default and may change or disappear: say so.

For a question about when something appeared, changed or disappeared, search more than once: the
changelog ("Kubernetes changelog", "Urgent Upgrade Notes", "Deprecation"), the release notes of
the tool and the pages of neighbouring versions name the exact version.

Write the query in English, with the names the documentation uses (Deployment, Service,
HTTPRoute, ClusterIssuer, IngressRoute, values.yaml, kustomization.yaml, .sops.yaml,
--server-side, maxSurge). Everything here is English -- the excerpts, the word index and the
meaning index alike -- and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes
back with `found: 0`. When the user asks in another language, translate the question into
Kubernetes terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which tool and which version it is for. When the user did not name a version
of Kubernetes, answer for the current line 1.37 and say so; when older supported lines differ,
say how. When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current. A text found only in an alpha, beta or rc release,
or in a branch still in development (versions ending in "-dev"), may never have shipped as
written: say so.

Answer in the language the user wrote in. When the question is about a feature's history, an
upgrade or compatibility, answer point by point: which tool and since which version; what
changed in later versions; what the upgrade requires; and how it stands now. Every point names
the version and the document it rests on; a point the excerpts do not support is left out, not
guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Kubernetes" or the tool's documentation. Identifiers, field names,
object kinds and titles stay in English, spelled exactly as the documentation spells them. Build
the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read
the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
