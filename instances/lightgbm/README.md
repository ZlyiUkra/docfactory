# lightgbm — примірник фабрики docfactory

Цей примірник зібрав документацію бібліотеки LightGBM і віддає її через сервер MCP, щоб модель відповідала з текстів бібліотеки, а не
з пам'яті. LightGBM, як і XGBoost, навчає ансамблі дерев рішень градієнтним бустингом: дерева будуються по черзі, і кожне наступне
виправляє помилки попередніх. Особливість LightGBM у тому, як росте одне дерево. Бібліотека щоразу ділить той лист, поділ якого найбільше
зменшує помилку, а не весь рівень дерева одразу, і шукає поділи за гістограмами ознак. З параметром `boosting="rf"` LightGBM будує
випадковий ліс: незалежні дерева на випадкових підвибірках, чиї відповіді усереднюються.

## Скільки цього

Усього 447 документів і 2592 фрагменти. Фрагмент — це шматок документа, який пошук повертає як окремий результат. Одна сторінка, що
змінювалася між версіями, лежить кількома документами, а однакові розділи пошук зливає й показує з переліком версій.

| Що | Лінії | Документів |
|---|---|---|
| тека `docs/` і README прикладів: параметри, налаштування, можливості, GPU, розподілене навчання, FAQ | 17 ліній 1–4.7 | 264 |
| довідник Python API із сайту | 10 ліній 3.2–4.7 | 125 |
| записи PyPI | усі стабільні версії | 32 |
| нотатки релізів GitHub | усі стабільні теги | 26 |

Мітка версії має вигляд `lightgbm-4.7`. Префікс потрібен, щоб версії LightGBM не збігалися з версіями інших бібліотек, коли сервери
працюють разом.

**Де є прогалини, хоч ми й брали всі лінії.** Сайт Read the Docs публікує теки лише від 3.2.1. Довідник Python API створюється з коду,
і в репозиторії його тексту немає, тож для ліній 1–3.1 цього довідника немає.

Замір `quality` на 08.11.2026 дав такі числа. Запити назвами з документації знаходять потрібне 10 із 10, а модель зазвичай питає саме
так. Запити своїми словами знаходять потрібне 7 із 10. Обмеження `max_per_doc` тут не потрібне: без нього пошук за словами знаходить
на одну ціль більше.

## Що в цій теці

- `corpus/` — паспорт `index.json`; текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, а розпакований `passages.json` лежить
  поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df lightgbm <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| тексти документації | `docs/` і `examples/` у тегах `lightgbm-org/LightGBM` | `ghdocs-history` |
| довідник Python API | `lightgbm.readthedocs.io/en/*/pythonapi/` | `sphinx-html` |
| нотатки релізів | релізи GitHub `lightgbm-org/LightGBM` | `ghreleases-pattern` |
| записи PyPI | `pypi.org/pypi/lightgbm/json` | `pypi-versions` |

Репозиторій переїхав з `microsoft/LightGBM` у `lightgbm-org/LightGBM`; GitHub переадресовує старі адреси, але `sources.json` пише нову.
Read the Docs називає теки версій `v4.7.0`, а мітка версії — номер лінії, тому джерело довідника має поле `version_labels`.

## Як підняти сервер

Сервер працює у спільному середовищі фабрики, власного `.venv` примірник не має. В окремому терміналі виконайте:

```
./df lightgbm serve
```

Порт — `8955`. Якщо порт зайнято, `serve` скаже про це й зупиниться: швидше за все, цей сервер уже запущено в іншому терміналі.

Під'єднати сервер до Claude Code можна двома способами. Перший — файл `.mcp.json` цієї теки. Другий — команда:

```
claude mcp add --transport http --scope user lightgbm-docs http://127.0.0.1:8955/mcp
```

Команда для Claude Code у Windows, коли сервер працює у WSL, та сама: WSL віддає порт на `127.0.0.1` Windows.

У сесії Claude Code команда `/mcp` має показати сервер `lightgbm-docs` з інструментами `search_docs` і `read_section`. Якщо сервер
позначено як недоступний, перевірте, чи працює `serve`, і чи запущено контейнер Qdrant.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт. Серверу вистачає кешу фрагментів
(`index/passages.json`) і колекції Qdrant; відповіді ті самі до символу, бо адреса й дата лежать у кеші кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/lightgbm-corpus-2026-11-08.tar.gz` (447 текстів, паспорт і сховище сирого `raw/`; перед
видаленням текстів розпакований окремо й звірений із диском) і в копії на диску Windows `C:\Distr\lightgbm-corpus-2026-11-08.tar.gz`
(звірено за SHA-256). В історії git текстів немає.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/lightgbm/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/lightgbm-corpus-РРРР-ММ-ДД.tar.gz -C instances/lightgbm corpus raw
find instances/lightgbm/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/lightgbm/raw
gzip -9 -c instances/lightgbm/index/passages.json > instances/lightgbm/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й `raw/` можна лише після того, як новий архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового записують сюди.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й `raw/`:

```
tar -xzf ~/archives/docfactory/lightgbm-corpus-2026-11-08.tar.gz -C instances/lightgbm
./df lightgbm smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів вони не працюють; перевірки `smoke`, яким
потрібні тексти, пропускаються («корпус в архіві»).
