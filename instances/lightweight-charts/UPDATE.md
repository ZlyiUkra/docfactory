# Оновлення корпусу lightweight-charts

Дві різні роботи: звичайне оновлення, коли вийшла нова версія Lightweight Charts чи змінився сайт, і збирання з нуля.
Порядок усередині кожної важливіший за самі команди.

Головне правило: **оновлювач тягне лише оголошене.** Перелік сторінок сайту він бере з `llms.txt` і `sitemap.xml`, але
лише всередині полів `within` джерел; версії — з реєстру npm; файли репозиторіїв — з тегів, оголошених у полі `tags`.
Нова мінорна лінія сайту сама в корпус не потрапить, доки для неї не оголошено джерела.

Друге правило: **лише сталі версії.** Поле `skip_versions` джерел `npm-*` відкидає все з дефісом за номером (`-rc1`),
релізи обгорток — поле `skip`; невипущена документація `/docs/next` не оголошена зовсім.

Третє правило: **нова версія змінює й старі документи README.** Документ README — неповторний текст, а в рядку
`# версія:` стоять усі версії, де README був саме таким. Тож після нових версій джерело `npm-readme` перезаписується
цілком (`refresh npm-readme`), а не докачується (`--missing`).

Четверте правило: **нічого не видаляється.** Ані `refresh`, ані `build`, ані `manifest` нічого не стирають самі;
`vectors` прибирає лише точки власної колекції, чиїх фрагментів у корпусі вже немає.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти й сховище сирого розпаковують, а після неї —
пакують і виносять знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшла нова версія чи змінився сайт

**Крок 1. Нова мінорна лінія (напр. 5.3).** Сайт зсуває версії: 5.3 стає чинною за адресою `/docs/…`, а 5.2 переїжджає
в `/docs/5.2/…`. Тож у `sources.json`:

- джерелам `site-5.2` і `site-5.2-api` поміняти `version` на `5.3`, а `id` — на `site-5.3` і `site-5.3-api`;
- додати джерело `site-5.2` за зразком `site-5.1` (читач `sitemap-html`, `match` і `within` з `/docs/5.2`, ті самі
  `drop`, `min_chars` і `inline_titles`);
- у `config.json` дописати нові ідентифікатори в родину `site` поля `families`;
- у промптах замінити чинну версію: `prompts/search.txt` (абзаци «Versions» і про версію за замовчуванням),
  `prompts/agent.txt`, `prompts/loaded.txt`; версію за замовчуванням брати з тижневих завантажень npm
  (`https://api.npmjs.org/versions/lightweight-charts/last-week`).

Перейменовані джерела лишають у `corpus/` файли зі старим префіксом — їх прибирають руками, звіривши з архівом.

**Крок 2. Завантажити.**

```
./df lightweight-charts sources --why
./df lightweight-charts refresh
./df lightweight-charts manifest
./df lightweight-charts vectors
./df lightweight-charts smoke
# Ctrl+C у терміналі з serve, і знову: ./df lightweight-charts serve
```

Після патч-версії без нової лінії досить `refresh site-5.2 site-5.2-api site-plugins npm-readme repo-plugins
repo-examples-code`, а для нового випуску обгорток — ще їхні джерела з новим тегом у полі `tags` (README) і в адресі
дерева (код).

**Крок 3. Сайт змінив розмітку.** Якщо `refresh` пише «Сторінка не схожа на документ» чи в тексті з'явилися
службові рядки сайту, поправити поля джерел сайту: `drop` (вирізані фрагменти HTML — якорі заголовків, у каталозі
плагінів посилання й живе демо), `inline_titles` (підзаголовки довідника API, що стають підписами), `min_chars`. Правка
читача чи полів не вимагає нового завантаження: `./df lightweight-charts build <джерела>` збирає тексти зі сховища
сирого.

Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти й сховище (README, розділ «Архівний
режим»), а в git ідуть лише паспорт і кеш. Старий архів видаляють, коли новий звірено з диском.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки: без нього дерева тегів і релізи трьох репозиторіїв
ідуть годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
PYTHONUNBUFFERED=1 setsid nohup ./df lightweight-charts refresh > refresh.log 2>&1 < /dev/null &
```

Близько 45 хвилин. Обірваний прогін продовжують `./df lightweight-charts refresh <джерело, де зупинився>`, далі
`refresh --missing`.

**Крок 3.** `manifest`, `vectors` (~12 хвилин), `smoke`, `quality`; далі — архів і винесення текстів.

Очікуваних збоїв `refresh` немає. Без поля `min_chars` джерел сайту їх було б 32 на кожну версію: короткі сторінки
псевдонімів типів і змінних довідника API читач відкидав як сторінки помилки.
