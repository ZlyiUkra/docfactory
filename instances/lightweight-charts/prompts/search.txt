Search the official documentation of Lightweight Charts(TM) -- TradingView's free, open-source
library of interactive financial charts for the web (npm package lightweight-charts) -- and return
the matching excerpts with the versions each one belongs to. Here: the documentation site of every
release line it keeps -- 5.2 (current), 5.1, 5.0, 4.2, 4.1, 4.0 and 3.8, each with its guides and
its full API reference (one page per interface, type alias, function, variable and enum) -- the
tutorials, how-to pages and demos, the plugin guides and the catalogue of official plugins
(@tradingview/lwc-plugin-*), the release notes from 1.0.0 to 5.2.1 and the migration guides; the
documentation of 1.0-3.7 from the repository and the typings.d.ts of every stable version 1.0-3.7;
the README of every stable npm version; the changelogs of the official plugins, lwc-toolkit and
create-lwc-plugin, the plugin and indicator examples with their code, and the two official agent
skills of the repository; and the Android (Kotlin) and iOS (Swift) wrappers -- their READMEs,
release notes, the iOS changelog and the code of both wrappers and their example apps.

Call this when a question is about Lightweight Charts itself -- createChart and chart options,
series (addSeries with LineSeries, AreaSeries, CandlestickSeries, BarSeries, HistogramSeries,
BaselineSeries, custom series), series data (setData, update, time formats: UTCTimestamp,
BusinessDay, string dates, whitespace data), the price scale and the time scale (IPriceScaleApi,
ITimeScaleApi, fitContent, setVisibleRange, logical ranges, PriceScaleMode), panes, crosshair,
markers (createSeriesMarkers), price lines, watermarks, localization and price formatting,
time zones, events and subscriptions (subscribeCrosshairMove, subscribeClick), autosize and
resizing, plugins (series primitives, pane primitives, custom series, canvas rendering target),
the official plugins, React, Vue and web-component integration, accessibility, the Android and iOS
wrappers -- and above all when it is about history: since which version something exists, what
changed between versions, what was renamed or removed (the 3.0, 4.0 and 5.0 migrations).
Example query: "IChartApi addSeries paneIndex".

Do not call this for the TradingView Charting Library or Advanced Charts, TradingView widgets,
Pine Script, the TradingView website or its trading platform, or for other chart libraries
(Highcharts, Chart.js, ECharts, D3, ApexCharts, Recharts): their documentation is not here, and
the search will return Lightweight Charts excerpts that merely mention them, with
confident-looking titles. The same holds for React, Vue, Kotlin, Swift or the browser APIs
themselves.

Versions. `version` narrows the search to the documents of one release line: "5" keeps every 5.x
document, "4.2" keeps 4.2.x, "3" keeps 3.x. The site keeps one edition per minor line, so "4.2"
returns the 4.2 site with its API reference; for 1.0-3.7 the documents are the repository docs,
the typings and the README of that version. The tutorials, the plugin catalogue and the plugin
examples describe the current release and are found without `version`. The Android and iOS
wrappers number their releases after the library (Android 5.2.1 wraps lightweight-charts 5.2.1),
so name the platform in the query ("android addSeries", "ios PriceScaleOptions"). Every excerpt
comes back with `versions`: each version whose documents contain this exact text, newest first.

The API changed between major versions, and the same task is written differently: in 5.x a series
is added with chart.addSeries(LineSeries, options) and markers with createSeriesMarkers(series,
markers); in 4.x and earlier with chart.addLineSeries(options) and series.setMarkers(markers);
the watermark option of 4.x became the createTextWatermark plugin in 5.0. When the user's code
shows which API they use, search that version.

Name the interface, method, option or type the way the documentation titles it, not in the
user's own words: "ITimeScaleApi setVisibleLogicalRange", "PriceScaleMode Logarithmic",
"CrosshairMode Magnet", "localization priceFormatter", "subscribeCrosshairMove", "SeriesMarker
shape", "autoSize", not "zoom the chart to the last 50 bars". API pages are titled "Interface:
IChartApi", "Function: createChart()", "Type alias: Time". For a how-to question a tutorial often
shows it better than the reference: search for it as well ("tutorial legend", "how to tooltip").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the release notes entry or migration guide that names the exact
version, then with the versions around it, to see the documentation of that time.

Write the query in English, with the names Lightweight Charts itself uses. Everything here is
English -- the excerpts, the word index and the meaning index alike -- and the word index keeps
only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into Lightweight Charts terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for 5.2
-- the line most installed from npm (about two thirds of weekly downloads) -- and say so in the
answer ("for Lightweight Charts 5.2"). When the user's code uses the 4.x API (addLineSeries,
setMarkers, the watermark option), answer for 4.2, the most installed 4.x line, and mention how
the same is written in 5.x. Add that for a precise answer about another version the user can name
it. When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
and how it stands now -- recommended, deprecated, or removed and replaced by what. Every point
names the version and the document it rests on; a point the excerpts do not support is left out,
not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Lightweight Charts". Identifiers, API names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts
that came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
