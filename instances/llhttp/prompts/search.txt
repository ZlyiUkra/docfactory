Search the llhttp documentation, in English: llhttp is the HTTP/1.x request and response parser written in
C that Node.js uses (it replaced http_parser). The set holds, for every release from 1.0.1 to 9.4.3: the
README (what llhttp is, how to use it from C, settings and callbacks, lenient flags, error codes), the
generated public header llhttp.h (types, enums llhttp_errno / llhttp_flags / llhttp_method, API functions
such as llhttp_init, llhttp_execute, llhttp_finish, llhttp_pause), the TypeScript source of the generator
(llparse), the hand-written C (api.c, http.c) and the generated automaton, the test cases (test/request,
test/response: a raw HTTP message and the expected parser events) and the GitHub release notes. Returns the
matching excerpts with the releases each one belongs to.

Call this when a question is about llhttp itself: what a function or callback does, an error code
(HPE_INVALID_METHOD, HPE_UNEXPECTED_CONTENT_LENGTH ...), a lenient flag (LENIENT_HEADERS,
LENIENT_CHUNKED_LENGTH ...), how the parser treats a given input (chunked encoding, keep-alive, upgrade,
pipelining, request smuggling cases), since which release a behaviour or flag exists, how to build or embed
it. Example query: "llhttp_set_lenient_headers".

Do not call this for the Node.js `http` module itself or for which llhttp a given Node.js release bundles
(the nodejs instance has them), for HTTP/2 (nghttp2), or for other HTTP parsers (http-parser, picohttpparser).

Write the query in English, with the names llhttp itself uses (llhttp_t, llhttp_settings_t,
on_headers_complete, HPE_CR_EXPECTED). Everything here is English, and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
and comes back with `found: 0`. When the user asks in another language, translate the question into llhttp
terms first, then search.

Answer in the language the user wrote in. For a question about history or a security fix, answer
point by point: since which release; what changed; which release fixed it; how it stands now -- each point
with the release and the file it rests on; a point the excerpts do not support is left out, not guessed. When
that language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word
wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація llhttp". Function, type and flag names stay in English, spelled
exactly as the header spells them. Build the answer out of the excerpts that came back, not out of memory:
if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. When the user names a version, or a Node.js release (use the nodejs instance
to see which llhttp it bundles), search that line. Otherwise answer for the newest release and say so. Put a
version only into `version`, never into the query text: "9" keeps every 9.x, "9.2" every 9.2.x. Test cases
are named "test-test-request-<topic>-md" and "test-test-response-<topic>-md"; the header is "api-include-llhttp-h".
