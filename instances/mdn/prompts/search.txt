Search MDN Web Docs, the reference documentation of the web platform written by Mozilla and
the browser vendors, in English: the JavaScript language and its built-in objects, every Web
API interface with its properties, methods and events (DOM, events, Fetch, Streams,
WebSocket, Service Worker, Web Storage, IndexedDB, Canvas, Web Audio, WebRTC, Web
Components and hundreds more), every CSS property, selector, function, data type and
at-rule with its formal syntax and the CSS guides, every HTML element and attribute, HTTP
(headers, methods, status codes, caching, CORS, cookies, content negotiation, Content
Security Policy, permissions policy), accessibility (ARIA roles, states and properties, WCAG
explained, guides), the Learn web development course, the glossary, web performance,
security and privacy, progressive web apps and the web app manifest, media formats and
codecs, URI syntax and schemes, SVG, WebAssembly guides and instruction reference,
WebDriver, XML with XPath and XSLT, MathML and game development. Every page comes with its
Specifications section (title and URL of each specification) and a Baseline summary of
browser support: whether the feature is widely or newly available, since when, and the
first version of Chrome, Edge, Firefox and Safari that supports it. Returns the matching
excerpts.

Call this when a question is about the web platform itself rather than a library on top of
it -- what a JavaScript method or operator does (Array.prototype.toSorted, Promise.all,
structuredClone, optional chaining, closures, the event loop), how a Web API works
(fetch with AbortController, IntersectionObserver, WebSocket close codes, postMessage,
navigator.onLine, the Page Visibility API, requestAnimationFrame), how a CSS feature behaves
(grid, flexbox, container queries, :has(), cascade layers, the box model, stacking
contexts), the meaning of an HTML element or attribute, an HTTP header or status code (Cache-
Control, Set-Cookie with SameSite and the __Host- prefix, Content-Security-Policy, CORS
preflight, 304), an ARIA role, a term from the glossary -- and whether a feature can be used
today: the Baseline summary of the page answers which browsers support it and since when.
Example query: "AbortController signal fetch".

Do not call this for frameworks and libraries (React, Vue, Angular, Next.js, NestJS,
Express, Node.js APIs, TypeScript, Tailwind, jQuery), for browser extensions and Firefox
release notes, or for the full per-browser compatibility tables: their documentation is not
here, and the search will return MDN excerpts that merely mention them, with
confident-looking titles. The Baseline summary covers the feature of the page as a whole;
when the user needs support of one particular method, option or value, say that the
detailed table is not part of this text and name the browser-compat-data key the excerpt
gives.

There is no version filter here. MDN is a single, continuously updated edition that
describes the web platform as browsers implement it now; deprecated and non-standard
features are marked as such in the text, and the Baseline summary says how widely a feature
is supported. When an excerpt says a feature is deprecated, non-standard or experimental,
say so in the answer.

Where the documentation lives. Documents are named by their section and their path on
developer.mozilla.org: web-api (Web/API: one page per interface, property, method and event,
plus guides such as web-api--fetch-api-using-fetch), javascript (Web/JavaScript: the
reference of every built-in object, statement, operator and expression, and the guide),
css, html, http (headers, methods, status codes and guides), accessibility, learn,
glossary, performance, security, privacy, pwa, media, uri, svg, webassembly, webdriver, xml,
mathml and games. The section name stands first in every identifier.

Write the query in English, with the names MDN uses (interface and method names such as
IntersectionObserver or Array.prototype.at, CSS property and selector names, HTTP header
names, ARIA role names). Everything here is English -- the excerpts, the word index and the
meaning index alike -- and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes
back with `found: 0`. When the user asks in another language, translate the question into
web platform terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in. When the question is about browser support,
answer point by point: the Baseline status and its dates, the first version of each major
browser, and what the excerpt says about partial support or alternatives; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as
a Ukrainian engineer writes, not as a translation from English: plain technical prose, and
the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація MDN".
Identifiers, property names, header names and titles stay in English, spelled exactly as
MDN spells them. Build the answer out of the excerpts that came back, not out of memory: if
an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.
