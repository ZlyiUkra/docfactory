# mikro-orm — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про MikroORM — ORM для TypeScript і Node.js (репозиторій
mikro-orm/mikro-orm, сайт mikro-orm.io) — і його модуль NestJS @mikro-orm/nestjs за документацією всіх стабільних
версій: сайт з тегу кожної мінорної версії, README кожної версії, журнали змін, релізи модуля NestJS та історія версій у
реєстрі npm. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані
домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

MikroORM — ORM на патернах Data Mapper, Unit of Work та Identity Map: сутності — звичайні класи (декоратори,
`defineEntity` чи `EntitySchema`), `EntityManager` пам'ятає кожну завантажену сутність і сам вирішує, що записати під
час `flush`, а контекст розгалужують на кожен запит (`em.fork`, `RequestContext`). Драйвери — PostgreSQL, MySQL,
MariaDB, SQLite, libSQL, MS SQL Server і MongoDB; поруч міграції, сідери, генератор сутностей. У плані NestJS
(фулстек-родина) MikroORM стоїть у «знати, що існує» як третій шлях до бази поруч з TypeORM і Prisma.

Чинних ліній дві: 6 (близько 56 % завантажень `@mikro-orm/core` за тиждень до 24.10.2026, Node 18.12+) і 7 (близько
36 %; 7.0.0 від 11.03.2026 — лише ESM, Node 22.17+, Kysely замість Knex, декоратори в окремому пакеті). Сайт кожної
мінорної версії, кожен запис журналу змін і дата кожного випуску зібрані в одному місці, з номером версії біля кожного
уривка.

Разом 1109 документів; фрагментів в індексі — 4901 (`expected_passages` у `checks.json`). Замір `quality`: по словах 4
із 10, за змістом 3, разом 5, «як модель» 10 із 10. Перша десятка низька не через версії — однаковий розділ різних
версій пошук і так згортає до найновішого: п'ять питань своїми словами не мають жодного слова з документації («stop two
users from overwriting each other's update» замість optimistic locking, «versioned files» замість migrations, «rows of
another table» замість OneToMany), а модель векторів bge-small цього розриву не долає. Ще одна причина — покроковий
посібник сайту (`guide-00`…`guide-05`) розповідає ті самі теми, що й довідкові сторінки (сідери, soft delete, пакетний
запис), і питання своїми словами часто влучає в нього; там, де посібник дає справжню відповідь, він є в цілі. Заміряно
й не допомогло: `max_per_doc` 1–3 і відсунуті вниз журнали змін (`demote`). Друга десятка — назвами документації, як
шукає модель за промптом, — влучає всюди.

Чому сайт береться з репозиторію, а не з mikro-orm.io. Сайт тримає лише кілька останніх версій (`versions.json`: 7.2,
7.1, 7.0, 6.6, 5.9), а зміст кожної лежить у репозиторії на її тезі: з 3.0 — Docusaurus у `docs/docs`, у 2.x — Jekyll у
корені `docs/`. Береться остання латка кожної мінорної версії від 2.0 до 7.2. Сторінка, що переїхала між теками,
лишається тією самою сторінкою: поле `slug_rewrite` у `config.json` зводить обидва шляхи до одного ключа
(`mikro-orm-entity-manager`). До 2.0 сайту не було — тоді документацією був README.

Чому README лише пакета mikro-orm. З 4.0 пакети `@mikro-orm/*` (core, драйвери, migrations, seeder, cli) несуть той
самий README, тож окремо вони не беруться; реєстр `@mikro-orm/core` узято — за ним рахуються лінії. Модуль
@mikro-orm/nestjs живе в окремому репозиторії: його README (16 КБ) і є документацією модуля; журнал змін узято до 5.1.0,
далі — релізи GitHub.

Чого немає. Документації SQL, PostgreSQL, MySQL, SQLite, MongoDB, Knex, Kysely, TypeScript і NestJS: сторінки MikroORM
лише показують, як ними користуватися. Коду самого ORM і окремих репозиторіїв-прикладів.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа. Самих
  текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями, `slug_rewrite` і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише
  для завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df mikro-orm <крок>`.

## Версії

Версія — номер випуску; сторінки сайту мають версію тегу, з якого взято (остання латка мінорної). Фільтр `version` бере
мажор (`"6"`), мінор (`"5.9"`) або точну версію (`"7.2.5"`); модуль NestJS — з префіксом `nestjs-` (`"nestjs-6"`).
Лінії 6 і 7 обидві чинні, тож на питання «як це зробити зараз» промпт велить шукати для обох і казати, де вони
різняться (сторінка `upgrading-v6-to-v7`). Сторінка, що не змінилася між версіями, — один документ з усіма ними, тож
перелік версій уривка сам показує, відколи й доки документація казала саме це.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/mikro-orm-corpus-2026-10-24.tar.gz` (1217 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском) і в копії на Windows-диску
`C:\Distr\mikro-orm-corpus-2026-10-24.tar.gz` (звірено за SHA-256). В історії git текстів немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/mikro-orm/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/mikro-orm-corpus-РРРР-ММ-ДД.tar.gz -C instances/mikro-orm corpus raw
find instances/mikro-orm/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/mikro-orm/raw
gzip -9 -c instances/mikro-orm/index/passages.json > instances/mikro-orm/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/mikro-orm-corpus-2026-10-24.tar.gz -C instances/mikro-orm
./df mikro-orm smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/mikro-orm/index/passages.json.gz`,
далі `./df mikro-orm vectors` заллє колекцію Qdrant (секунди на відеокарті, кілька хвилин на процесорі).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df mikro-orm …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md, розділ
«Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df mikro-orm sources --why   # перелік джерел і білий список
./df mikro-orm refresh         # завантажити все задеклароване (близько 30 хвилин)
./df mikro-orm manifest        # оновити паспорт
./df mikro-orm setup           # Qdrant чи пошук лише по словах
./df mikro-orm vectors         # залити корпус у docs-mikro-orm
./df mikro-orm smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df mikro-orm serve          # порт 8885
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8885/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user mikro-orm-docs http://127.0.0.1:8885/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `mikro-orm-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у [README
примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
