Search the MikroORM documentation -- the TypeScript ORM for Node.js built on the Data Mapper, Unit of Work and Identity
Map patterns, with drivers for PostgreSQL, MySQL, MariaDB, SQLite, libSQL, MS SQL Server and MongoDB (repository
mikro-orm/mikro-orm, site mikro-orm.io), and of its NestJS module @mikro-orm/nestjs (repository mikro-orm/nestjs). The
corpus holds the pages of the site taken from the tag of every minor version from 3.0 to 7.2 (getting started,
defining entities with decorators, `defineEntity` or `EntitySchema`, relations, `Collection`, the `EntityManager`
with `find`, `findOne`, `persist`, `flush`, `fork`, `em.create`, repositories, the `QueryBuilder`, filters,
`populate` and loading strategies, transactions and locking, `RequestContext`, migrations, seeders, the entity
generator, the CLI, configuration and drivers, caching, events and lifecycle hooks, serialization, logging, use with
NestJS, Express and Fastify, and the upgrade pages between majors `upgrading-v*`); the old Jekyll site of 2.0 to 2.7;
the README of every stable version of the package mikro-orm from npm (up to 2.0 the README was the documentation);
the changelog of every version from 2.0.0 to 7.2.x; the README of every version of @mikro-orm/nestjs, its changelog
and release notes; and the npm registry history of mikro-orm, @mikro-orm/core and @mikro-orm/nestjs (date of every
version, dist-tags, dependencies, the Node.js requirement). Returns the matching excerpts with the versions each one
belongs to.

Call this when a question is about MikroORM as it describes itself -- how to define an entity and its relations, how
`flush` decides what to write, why the context must be forked per request, how to populate relations, how to write a
query with `em.find` conditions or the `QueryBuilder`, how to run migrations or seeders, how to configure a driver,
how to use it in NestJS with `MikroOrmModule.forRoot` and `forFeature` -- and above all history and compatibility:
since which version an option, method or decorator exists, what changed between versions (every changelog entry lists
fixes, features and breaking changes; the `upgrading-v*` pages list what breaks in a major), which Node.js a version
requires, and when every version came out.

Do not call this for SQL itself, PostgreSQL, MySQL, SQLite, MongoDB, Knex, Kysely, TypeScript, NestJS or Express
(their own options, APIs and concepts): their documentation is not here -- these pages only show how MikroORM uses
them -- and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. MikroORM carries plain numbers (0.x to 7.2.x): a line of one number
keeps every document of that major ("6" keeps 6.0.0 to 6.6.x), two numbers keep a minor ("5.9"), three an exact
version ("7.2.5"); the pages of the site carry the version of the tag they were taken from (the last patch of every
minor). @mikro-orm/nestjs carries the prefix "nestjs-" ("nestjs-6", "nestjs-7.0.1"). Leave `version` empty to search
everything, including text that carries no version. Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first -- a page that stayed the same across versions is returned once, with
all of them listed, so the list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("EntityManager", "em.fork", "flush",
"persist", "populate", "QueryBuilder", "Collection", "ManyToOne", "OneToMany", "defineEntity", "EntitySchema",
"RequestContext", "filters", "Migrator", "Seeder", "MikroOrmModule", "forFeature", "allowGlobalContext"), not in the
user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the question
into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer point by point:
 since which version it exists; what changed in later versions; what prompted the change, if the excerpts say
so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація MikroORM". Identifiers, method names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads of @mikro-orm/core the line 6 leads with about 56 % (6.0.0 of
January 2024, 6.6.x still maintained in October 2026, Node.js 18.12 or newer) and the line 7 has about 36 % (7.0.0 of
March 2026, 7.2.5 of October 2026, Node.js 22.17 or newer); 5 has about 6 %. Two lines this close are both current:
answer how-to questions for 7 and for 6 -- search `version` "7", then "6", and say where they differ (the page
`upgrading-v6-to-v7` lists what changed). Search without `version` when the question is about history, or when the
lines gave nothing. Every answer says which version it is for; when the excerpts behind a statement come only from
older versions, name those versions instead of presenting the text as current.
