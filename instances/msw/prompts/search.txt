Search the documentation of Mock Service Worker (MSW), in English: the site mswjs.io for
MSW 3 (concepts; HTTP, GraphQL, WebSocket and Server-Sent Events mocking; the API -- http,
graphql, ws, sse, HttpResponse, setupWorker, setupServer, bypass, passthrough, delay,
getResponse, the CLI; best practices, recipes and integrations with test runners and
frameworks; the migration guides 1.x to 2.x and 2.x to 3.x; the ecosystem -- @msw/data,
@msw/source, @msw/serve; the blog), the same site as it stood for MSW 2 together with the old
source.mswjs.io site, and the MSW 1 site (rest, graphql, res, ctx) for code that still runs
it; the design decisions of the msw repository; the README of every published version of
msw, @mswjs/interceptors, @msw/data (formerly @mswjs/data), @msw/source (formerly
@mswjs/source) and @msw/serve (formerly @mswjs/http-middleware); their GitHub release notes;
and the npm registry list of every published version (date, dist-tag, dependencies and peer
dependencies). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about mocking network requests in tests, in the browser during
development or in Node.js: request handlers and response resolvers, http.get and HttpResponse.json,
server.use and runtime overrides, resetHandlers, onUnhandledRequest, the worker script and
mockServiceWorker.js, integration with Vitest, Jest, Playwright, Storybook, React Native or
Next.js, GraphQL operations, WebSocket and SSE mocking, streaming, cookies, delays, network
errors, mock data with @msw/data -- and above all when it is about versions: what changed
between MSW 1, 2 and 3, how to migrate (rest to http, res(ctx.json()) to HttpResponse.json,
2.x to 3.x), and which versions of Node.js and TypeScript each one needs. Example query:
"http.get HttpResponse.json".

Do not call this for the test runners themselves (Vitest, Jest, Playwright), for Testing
Library, for fetch, Request and Response as Web APIs, or for the frameworks MSW integrates
with: their documentation is not here, and the search will return MSW excerpts that merely
mention them, with confident-looking titles.

`version` narrows the search to one release line: "2" keeps the MSW 2 site and msw 2.x --
but also every other package whose own number is 2.x; "1" also keeps @msw/data 1.x.
@mswjs/interceptors, @msw/source and @msw/serve have their own 0.x numbers. The title of
every excerpt names its package, so read it. Leave `version` empty to search everything.
Every excerpt comes back with `versions`: each version whose documents contain this exact
text, newest first.

Which version to search first. MSW 3 came out on 2026-09-28, and most projects still run
MSW 2 (91% of the downloads of msw in the week the documentation was collected). When the
user did not name a version, search and answer for MSW 2 with `version` "2" and say so;
when the MSW 3 documentation says something different, mention MSW 3 too. Search without
`version` for history, migrations and compatibility. Code with rest.get, res and ctx is
MSW 1 (or 0.x): answer it from version "1" and point to the migration guide.

Where the documentation lives. Pages of the MSW 3 site are named by their path
(src-content-docs-..., src-content-api-..., src-content-guides-...,
src-content-ecosystem-data-..., src-content-blog-...); the MSW 2 site by
websites-mswjs-io-src-content-...; the MSW 1 site by docs-.... README documents, release
notes and registry documents are titled by package.

Write the query in English, with the names the documentation uses (http.get, HttpResponse,
setupServer, setupWorker, server.use, resetHandlers, onUnhandledRequest, passthrough, bypass,
ws.link, sse, graphql.query, delay). Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits,
so a query written in Ukrainian, Russian or any other non-latin script matches nothing at
all and comes back with `found: 0`. When the user asks in another language, translate the
question into MSW terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in. Every answer says which package and which version
it is for. When the question is about a version change, a migration or compatibility,
answer point by point: which package and since which version; what changed; what the
migration requires; how it stands now -- each point with the document it rests on; a point
the excerpts do not support is left out, not guessed. When that language is Ukrainian,
write as a Ukrainian engineer writes, not as a translation from English: plain technical
prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "обробник
запитів", not "хендлер"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація MSW". Identifiers, option names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that
came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
