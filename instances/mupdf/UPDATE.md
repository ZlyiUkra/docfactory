# Оновлення корпусу mupdf

Історія PyPI (`pypi-*`) бере версії з опису пакета в реєстрі, тож новий реліз потрапляє туди сам. Релізи GitHub
(`pymupdf-releases`) читаються щоразу заново з API, журнали змін (`mupdf-changes`, `pymupdf-changes`,
`pymupdf4llm-changes`) — з основної гілки репозиторію. Передрелізи відсіюються.

Руками оголошено:

- **Документація, заголовки, приклади й сторінки man на тегах** (`mupdf-docs`, `mupdf-headers`, `mupdf-examples`,
  `mupdf-man`, `pymupdf-docs`, `pymupdf-samples`): поле `tags` — об'єкт «тег → мітка версії з префіксом», від
  найновішого, по одному тегу на лінію. Коли в лінії виходить новий патч, тег лінії заміняють новішим; коли виходить
  нова лінія, дописують рядок нагорі. У MuPDF лінія — два числа (`1.28`), тег — три (`1.28.6`).
- **Старі макети документації** (`mupdf-docs-src`, `mupdf-html`, `mupdf-txt`, `pymupdf-docs-119`) оголошено на тегах
  закритих ліній, і міняти їх не треба.
- **Книжка** (`mupdf-explored`): адреса PDF на сайті автора. Нова редакція лягає за тією самою адресою; тоді в полі
  `note` джерела й у README міняють дату редакції.
- **Новий пакет PyPI** — джерело `pypi-versions` за зразком наявних, з власним префіксом версії; префікс дописують у
  `prompts/search.txt` і `prompts/agent.txt` та в таблицю README.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описано в README, розділ «Архівний режим».

## Вийшла нова версія MuPDF чи PyMuPDF

```
./df mupdf refresh mupdf-docs mupdf-headers mupdf-examples mupdf-man mupdf-changes   # приклад для MuPDF, після правки tags
./df mupdf refresh --missing    # джерела, яких не названо, лише докачуються
./df mupdf manifest
./df mupdf vectors
./df mupdf smoke
# Ctrl+C у терміналі з serve, і знову: ./df mupdf serve
```

Для PyMuPDF названі джерела — `pymupdf-docs pymupdf-samples pymupdf-changes pymupdf-releases pypi-pymupdf`.

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінний заголовковий файл дописує нову версію в рядок `# версія:`).

Ім'я файла містить початок хеша його вмісту, тому змінена сторінка чи заголовок лягає новим файлом поруч зі старим.
Після заміни тегу в `tags` файли, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш
ніж запускати `manifest`: інакше в корпусі лишиться редакція патча, якого в `tags` уже немає.

Якщо вийшла нова лінія:

- у `prompts/search.txt` (абзаци про `version` і «Which version to search first») та `prompts/agent.txt` замінити
  номер найновішої лінії; коли MuPDF змінить макет документації, додати правило в `slug_rewrite` файла `config.json`,
  щоб нові імена сторінок зводилися до старих;
- у таблиці «Пакети й версії» README оновити версію;
- у `checks.json`, у десятці `quality_model`, замінити мітку лінії й звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторіїв і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального
довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей): `./df mupdf quality --show`, порівняння обох
десяток з попереднім результатом, розбір промахів, правка промптів чи цілей. Головна мета — «як модель» 10 із 10.
