Search the documentation of MuPDF and PyMuPDF and return the matching excerpts with the versions each one belongs to.
MuPDF is the C library by Artifex that reads, renders, converts and edits PDF, XPS, EPUB and other documents, with its
command line tool mutool; PyMuPDF is its Python binding (the package pymupdf, imported as pymupdf, formerly as fitz).

What is here. MuPDF: the documentation of mupdf.readthedocs.io -- the guide (installing, building, Android, Java), the
C API reference (the context, error handling with fz_try, memory, streams, pixmaps, option strings such as the PDF
write options and the structured text options), the C cookbook, a page for every mutool command (draw, convert, clean,
merge, show, extract, info, pages, poster, sign, trace, run, create) and for mupdf-gl; the same documentation as it
was written in the lines 1.22-1.25 and as HTML pages in 1.11-1.21; the header files include/mupdf/fitz/*.h and
include/mupdf/pdf/*.h of every line 1.3-1.28 -- the full C API, where every function, type and macro stands with the
comment that describes it (fz_open_document, fz_new_pixmap_from_page, fz_new_stext_page_from_page, pdf_load_page,
pdf_annot_type, pdf_dict_get); the C examples (example.c, multi-threaded.c); the man pages; the CHANGES file; and the
book "MuPDF Explored" by Robin Watts (2023) about the C API and the internals. PyMuPDF: the documentation of
pymupdf.readthedocs.io for every line 1.16-2.1 -- the tutorial and the basics, a page per class (Document, Page,
Pixmap, Rect, Point, Matrix, Annot, Widget, Link, TextPage, TextWriter, Shape, Font, Story, Archive, DocumentWriter,
Tools) with a section per method and attribute, the recipes (text, images, annotations, drawing, stories, optional
content, low-level interfaces, multiprocessing), the FAQ, the functions and constants, the appendices, PyMuPDF4LLM,
PyMuPDF Pro, PyMuPDF Layout and OCR; the code samples; the change log; the GitHub release notes; and the PyPI
histories of pymupdf, pymupdf4llm, pymupdfpro, pymupdf-layout and pymupdf-fonts with their READMEs.

Call this when a question is about using MuPDF from C, about a mutool command and its options, or about PyMuPDF in
Python: how to open a document and render a page, extract text, words, blocks, tables or images, search, add or read
annotations and form fields, redact, insert text and images, merge and split documents, save with garbage collection,
compression or encryption, convert a document to PDF, Markdown or images, run OCR, write multi-threaded C code with
cloned contexts, handle errors with fz_try and fz_catch, manage reference counts with keep and drop -- and history:
since which version a function, method or parameter exists, what a release changed, what an old name is called now.
Example query: "fz_new_pixmap_from_page_number".

Do not call this for the JavaScript API of MuPDF (the npm package mupdf, MuPDF.js, and the scripts of mutool run): it
is in the pdf-js-docs server together with the other JavaScript PDF libraries. Do not call it for the PDF file format
itself (the ISO 32000 specification), for other PDF tools (the poppler utilities, Ghostscript and qpdf are in the
doc-tools-docs server), for other Python PDF libraries (pypdf, pdfplumber, ReportLab), or for Python and C themselves:
their documentation is not here, and the search will return excerpts that merely mention them, with confident-looking
titles.

`version` narrows the search to one release line of one product. Each product carries its own numbering behind a
prefix, because MuPDF and PyMuPDF share the numbers of the lines 1.16-1.28 and must not mix: "mupdf-1.28",
"mupdf-1.24", "pymupdf-2", "pymupdf-1.28", "pymupdf-1.24", "pymupdf4llm-2", "pymupdfpro-1", "pymupdf-layout-2",
"pymupdf-fonts-1". A longer value narrows further ("mupdf-1.28.6", "pymupdf-1.27.2"). Leave it empty to search every
version at once. Every excerpt comes back with `versions`: each version whose documents contain this exact text,
newest first. The book "MuPDF Explored" carries no version and is found only by a search without `version`.

Which version to search first. When the user names no version, answer for the newest line and say which one: MuPDF
1.28, PyMuPDF 2.1. PyMuPDF 2.0 and 2.1 came out in October and November 2026, so much code in use is still written for
1.2x: when the answer differs between the 2.x and the 1.x lines, give both. Things that changed and are worth checking
before an answer: the import name (`import pymupdf` today, `import fitz` in older code); the method names (camelCase
such as getText and insertImage at first, snake_case such as get_text and insert_image since the renaming finished in
1.18.14; the old names stayed as deprecated aliases through 1.19 and were removed after it -- the page "Deprecated
Names" maps one to the other); in 2.0 the functions of PyMuPDF4LLM moved into the Document class
(Document.to_markdown, Document.to_json, Document.to_text, use_layout). In C, the API is not stable between minor
lines: a function may change its arguments or disappear, so check the header of the line the user builds against.

How the text is laid out. Documents are named by source: mupdf-headers (one document per header file; a section per
group of declarations, titled with what it declares -- "fz_open_document()", "fz_document_drop_fn",
"struct fz_page"), mupdf-docs, mupdf-docs-src and mupdf-html (the documentation in its three layouts), mupdf-man,
mupdf-examples, mupdf-changes, mupdf-explored (a document per chapter of the book), pymupdf-docs (a page per class; a
section per method, titled with the class and the signature -- "Page.get_text(option, *, clip=None, ...)"),
pymupdf-samples, pymupdf-changes, pymupdf-release, pypi-pymupdf.

Write the query in English, with the names the libraries use ("fz_open_document fz_load_page",
"fz_new_stext_page_from_page", "fz_try fz_always fz_catch", "fz_clone_context locks", "mutool draw -r resolution",
"mutool clean garbage", "Page.get_text blocks words", "Document.insert_pdf", "Page.find_tables",
"Page.add_redact_annot apply_redactions", "Document.save garbage deflate", "Pixmap save png", "to_markdown"), not in
the user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and
the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the
question into the terms of the libraries first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a function, method or
option, answer point by point: since which version it exists; what changed in later versions; what prompted the
change, if the excerpts say so; and how it stands in the current version. Every point names the product, the version
and the document it rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set
of documents "корпус" -- say "документація MuPDF і PyMuPDF". Identifiers, option names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
