Search the documentation of nats.js -- the official NATS client for JavaScript and TypeScript on Node.js, Deno, Bun
and browsers, in both of its lines: the package `nats` 2.x and the modular packages `@nats-io/*` 3.x (repositories
nats-io/nats.js and nats-io/nats.deno, the npm registry, the API reference at nats-io.github.io/nats.js). The corpus
holds the README of every stable `nats` version from npm, 0.2 to 2.29; for the line 2 the README, jetstream.md and
services.md of the shared client nats-base-client from the nats.deno tag that goes with each minor, 2.0 to 2.29;
for the line 3 the README of every package -- `@nats-io/nats-core` (connect, publish, subscribe, request, headers,
drain, reconnect and status events), `@nats-io/jetstream` (JetStream manager, streams, consumers, consume, fetch,
next, ordered consumers, publish with acknowledgement and deduplication), `@nats-io/kv`, `@nats-io/obj`,
`@nats-io/services`, `@nats-io/transport-node` -- with migration.md (moving from `nats` 2.x) and runtimes.md, from
every minor 3.0 to 3.4; the TypeDoc API reference of core, jetstream, kv, obj and services for 3.4 (every interface,
option, method and type); the JavaScript and TypeScript examples that docs.nats.io shows on its pages; the npm registry
of every package with its versions and release dates; and the release notes of nats.js 3.x and of nats.deno 1.x.
Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about the JavaScript client as it describes itself -- how to connect with
`connect()` and its options (`servers`, `name`, `token`, `user`, `pass`, `authenticator`, `maxReconnectAttempts`,
`reconnectTimeWait`, `tls`), how to subscribe with an async iterator or a callback, how request-reply and `respond()`
work, how headers are set, how `drain()` and `close()` differ, how to create a stream with `jetstreamManager()`,
consume with `consumer.consume()`, `fetch()` or `next()`, acknowledge with `ack()`, `nak()`, `term()` and
`working()`, publish with `js.publish()` and `msgID`, use `Kvm` and `kv.watch()`, the Object Store, services with
`svcm` -- and above all history and compatibility: since which version an option or a method exists, what was
renamed or removed when the client split into `@nats-io/*` 3.x (migration.md lists it), what changed between versions.

Do not call this for the NATS server itself -- its configuration, clustering, accounts and JWT, how JetStream stores
and replicates data, the protocol and the server release notes: that is the NATS documentation (nats-docs) -- nor for
the NestJS NATS transport, nats.go, nats.py or other clients: their documentation is not here.

`version` narrows the search to one release line. nats.js carries plain numbers: a line of one number keeps every
document of that major ("2" keeps the package `nats` 2.x, "3" the packages `@nats-io/*` 3.x), two numbers keep a minor
("2.29", "3.4"), three an exact version ("3.3.1"). Leave `version` empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first -- a page that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("connect", "ConnectionOptions",
"subscribe", "Subscription", "request", "respond", "headers", "drain", "status", "reconnect", "JetStreamManager",
"jetstreamManager", "streams.add", "consumers.get", "consume", "fetch", "next", "ordered consumer", "ack", "nak",
"term", "working", "PubAck", "msgID", "Kvm", "kv.watch", "Objm", "Svcm", "migration"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps
only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
at all and comes back with `found: 0`. When the user asks in another language, translate the question into the terms
of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація nats.js". Identifiers, options and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By npm downloads in the week before 25 October 2026 two lines are in use side by side:
the package `nats` 2.x (2.29.3, about 666 thousand a week, and the NestJS NATS transport is built on it) and the
packages `@nats-io/*` 3.x (3.4.0; `@nats-io/nats-core` about 367 thousand, `@nats-io/transport-node` about 331
thousand). Answer for both: search `version` "2.29", then "3.4", and say how the two differ -- the API moved between
them (migration.md lists what was renamed, moved into its own package or removed). When the user names a package or a
version, answer for it. Search without `version` when the question is about history, or when the line gave nothing.
Every answer says which version it is for; when the excerpts behind a statement come only from older versions, name
those versions instead of presenting the text as current.
