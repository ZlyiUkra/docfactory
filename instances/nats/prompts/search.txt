Search the NATS documentation -- the open source messaging system nats-server with core NATS publish-subscribe,
request-reply and queue groups, and JetStream persistence with streams, consumers, Key-Value and Object Store (site
docs.nats.io, repositories nats-io/nats.docs.v2, nats-io/nats.docs, nats-io/nats-architecture-and-design and
nats-io/nats-server). The corpus holds the reference of every server version the site keeps, 2.11, 2.12, 2.14 and 2.15
(the server configuration file with a page for every key, JetStream streams and consumers and their configuration and
API, system subjects, monitoring endpoints, the client and cluster protocols, services); the Learn section (subjects
and wildcards, publish-subscribe, request-reply, queue groups, scatter-gather, JetStream acknowledgement and delivery,
mirrors and sources, subject mapping, message TTL, Key-Value, Object Store, services, security with accounts, JWT,
nkeys and the operator mode, clustering, super-clusters, gateways and leaf nodes, deployment, monitoring, backup and
recovery, MQTT and WebSocket); the concepts pages and the upgrade notes to 2.12, 2.14 and 2.15; the tutorials; the old
documentation that docs.nats.io served from GitBook until August 2026 (running a NATS service, the nats CLI and nsc,
developing with the clients, NATS Streaming as legacy); the architecture decision records (ADR) of the NATS team;
and the release notes of every stable nats-server release from 0.5.6 to 2.15.1. Returns the matching excerpts with
the versions each one belongs to.

Call this when a question is about NATS as it describes itself -- how a subject, a wildcard or a queue group behaves,
what a configuration key does and its default (`max_payload`, `max_pending`, `jetstream { store_dir, max_mem }`,
`cluster`, `leafnodes`, `authorization`), how a stream or a consumer is configured (`retention`, `discard`,
`max_age`, `duplicate_window`, `ack_policy`, `ack_wait`, `max_deliver`, `deliver_policy`, `filter_subject`), how
acknowledgements, redelivery and exactly-once publishing work, how to form a cluster or connect leaf nodes, how to
secure a server with accounts and JWT, which monitoring endpoint or system subject to use -- and above all history and
compatibility: since which version a feature exists, what was deprecated or removed, what changed between versions
(the release notes of every version list it), what to check before an upgrade.

Do not call this for the client libraries as their own projects -- nats.js and its packages `nats` and `@nats-io/*`,
nats.go, nats.py, the NestJS NATS transport -- nor for Kubernetes, Docker or Go itself: their documentation is not
here -- these pages only show how NATS is used with them -- and the search will return excerpts that merely mention
them, with confident-looking titles.

`version` narrows the search to one release line. NATS carries plain numbers: a line of one number keeps every
document of that major ("2" keeps 2.x), two numbers keep a minor ("2.14"), three an exact version ("2.12.15"). The
reference pages carry the version of the site they were taken from ("2.15", "2.11"); the release notes carry their
exact version ("2.14.8"). Leave `version` empty to search everything, including the Learn section, the concepts, the
tutorials, the old GitBook documentation and the ADRs, which carry no version. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- a page that stayed the same across
versions is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("subject", "wildcard", "queue group",
"request-reply", "JetStream", "stream", "consumer", "durable consumer", "pull consumer", "ack policy", "ack wait",
"max deliver", "retention policy", "work queue", "interest", "deduplication", "Nats-Msg-Id", "mirror", "source",
"subject mapping", "Key-Value", "Object Store", "leaf node", "gateway", "super-cluster", "account", "JWT", "nkeys",
"nsc", "max_payload", "jetstream store_dir"), not in the user's own words. Everything here is English -- the excerpts,
the word index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`.
When the user asks in another language, translate the question into the terms of the documentation first, then
search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація NATS". Identifiers, configuration keys and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. NATS publishes no download counts per server version, so the line to answer for is the
one the project ships patches for: 2.15 is the newest (2.15.1 of 9 October 2026), and 2.14 is still maintained (2.14.8
of the same day); the site marks 2.12 and 2.11 as unmaintained. Answer how-to questions for 2.15 and say where 2.14
differs: search `version` "2.15", then "2.14". When the question involves an older server, search its line as well
and say what changed (the upgrade notes and the release notes list it). The Learn section and the concepts carry no
version and describe the current server. Search without `version` when the question is about history, or when the
line gave nothing. Every answer says which version it is for; when the excerpts behind a statement come only from
older versions or from the old GitBook documentation, say so instead of presenting the text as current.
