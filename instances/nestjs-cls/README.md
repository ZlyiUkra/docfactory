# nestjs-cls — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про `nestjs-cls` — модуль continuation-local storage (контекст запиту
на `AsyncLocalStorage`, сумісний із впровадженням залежностей NestJS; репозиторій Papooch/nestjs-cls, сайт
papooch.github.io/nestjs-cls) — за документацією всіх його стабільних версій: сторінки сайту на тегах кожної версії
ядра від 3.5.1, README кожної версії (до 3.5.1 README і був документацією), нотатки релізів GitHub та історія версій
у реєстрі npm. Разом із ядром — плагін транзакцій `@nestjs-cls/transactional` і вісім його адаптерів
(`@nestjs-cls/transactional-adapter-prisma`, `-typeorm`, `-drizzle-orm`, `-kysely`, `-knex`, `-mongoose`, `-mongodb`,
`-pg-promise`): README кожної версії, релізи й реєстр npm кожного пакета.
Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний
устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

У NestJS немає вбудованого способу тримати дані «цього запиту» (ідентифікатор запиту, користувача, орендаря, відкриту
транзакцію) так, щоб їх бачив будь-який сервіс без передавання параметром і без REQUEST-scoped провайдерів, які
перестворюють увесь ланцюжок впровадження на кожен запит. `nestjs-cls` робить це через `AsyncLocalStorage`: контекст
відкривають middleware, guard, interceptor, декоратор `@UseCls` або `cls.run`, читають через `ClsService`, а Proxy
Providers заміняють REQUEST-scoped провайдери. Плагін Transactional на цьому ж контексті поширює одну транзакцію бази
через кілька сервісів (`@Transactional`, `TransactionHost`, режими `Propagation`) — для кожної бібліотеки бази свій
адаптер. У плані NestJS (фулстек-родина) це основа фаз про транзакції й контекст запиту.

Бібліотека має сім мажорних ліній за п'ять років, і кожна зміна ламає щось у реєстрації модуля чи в плагінах; посібники
міграції лежать на сайті, нотатки релізів — на GitHub, вимоги до NestJS і Node.js — лише в реєстрі npm. Усе це — в
одному місці й з номером версії біля кожного уривка.

Чому сторінки беруться з тегів, а не з гілки main: сайт не має версій, а документація змінюється від лінії до лінії
(реєстрація плагінів, Proxy Providers, адаптери з'являлися і змінювали API), і без тегів модель відповідала б про одну
лінію. Ключі в полі `tags` — SHA комітів тегів ядра `nestjs-cls@3.5.1` … `nestjs-cls@7.0.1`; тека `docs/docs` з'явилася
на 3.5.1 (24 сторінки) і зросла до 45 на 7.0.1. До 3.5.0 (теги старого виду `vX.Y.Z`) документацією був README
(34 КБ на 3.0.0), і він береться з tarball кожної версії. Сайт один на всі пакети, тож сторінки плагіна й адаптерів
версіонуються ядром; власні версії пакетів несуть лише їхні README, релізи й реєстр — з префіксом у номері
(`transactional-3.2.0`, `adapter-prisma-2.0.1`), бо інакше їхні числа збіглися б із числами ядра.

Чого немає. Коду й тестів: документація відповідає на питання про те, що викликати й що змінилося. Документації
самого NestJS, `AsyncLocalStorage` і бібліотек баз даних за адаптерами (Prisma, TypeORM, Drizzle, Kysely, Knex, Mongoose,
драйвер MongoDB, pg-promise) — вони в інших примірниках фабрики.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише для
  завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df nestjs-cls <крок>`.

## Версії

Версія — номер випуску. Фільтр `version` бере мажор (`"6"`), мінор (`"6.2"`) або точну версію (`"6.2.1"`). Без
названої версії промпт велить шукати для лінії 6 — на неї за тиждень до 22.10.2026 припадало близько 63 % завантажень
(6.2.0 — 22 %, 6.2.1 — 16 %, 6.3.1 — 8 %), на лінію 5 близько 14 %, на лінію 7 (найновіша, 7.0.1 від 24.09.2026)
близько 12 %, на лінію 4 близько 8 %; де 7.x відрізняється (посібник міграції v6x-v7x, реліз 7.0.0), модель згадує й її.
Для плагіна — спершу `"transactional-3"` (близько 80 % завантажень), `"transactional-4"` — коли відрізняється.

Версії плагіна й адаптерів записано з префіксом, бо їхні номери збіглися б із номерами ядра: `"transactional-3"` бере
всі документи плагіна 3.x, `"adapter-prisma-2"` — адаптера Prisma 2.x, а голе `"2"` лишає лише `nestjs-cls` 2.x.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/nestjs-cls-corpus-2026-10-24.tar.gz` (389 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском) і в копії на Windows-диску
`C:\Distr\nestjs-cls-corpus-2026-10-24.tar.gz` (звірено за SHA-256). В історії git текстів немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/nestjs-cls/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/nestjs-cls-corpus-РРРР-ММ-ДД.tar.gz -C instances/nestjs-cls corpus raw
find instances/nestjs-cls/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/nestjs-cls/raw
gzip -9 -c instances/nestjs-cls/index/passages.json > instances/nestjs-cls/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/nestjs-cls-corpus-2026-10-24.tar.gz -C instances/nestjs-cls
./df nestjs-cls smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/nestjs-cls/index/passages.json.gz`,
далі `./df nestjs-cls vectors` заллє колекцію Qdrant (кілька секунд на відеокарті, хвилина на процесорі).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df nestjs-cls …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df nestjs-cls sources --why   # перелік джерел і білий список
./df nestjs-cls refresh         # завантажити все задеклароване (близько 25 хвилин: 35 дерев тегів, ~400 tarball, сторінки релізів)
./df nestjs-cls manifest        # оновити паспорт
./df nestjs-cls setup           # Qdrant чи пошук лише по словах
./df nestjs-cls vectors         # залити корпус у docs-nestjs-cls
./df nestjs-cls smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df nestjs-cls serve          # порт 8879
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8879/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user nestjs-cls-docs http://127.0.0.1:8879/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `nestjs-cls-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
