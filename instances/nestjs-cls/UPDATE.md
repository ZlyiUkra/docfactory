# Оновлення корпусу nestjs-cls

Перелік версій тут не оголошується руками: читачі README і реєстру беруть його з опису кожного пакета в реєстрі npm
(`https://registry.npmjs.org/nestjs-cls`, `…/@nestjs-cls/transactional`, `…/@nestjs-cls/transactional-adapter-*`), тож
нова версія будь-якого з десяти пакетів потрапляє в корпус сама, коли вийде в npm. Релізи беруться з GitHub
(`Papooch/nestjs-cls`, один потік релізів монорепозиторію, кожен пакет — своїм префіксом тегу) і теж підхоплюють нову
версію самі. Руками прив'язано одне: перелік тегів ядра в полі `tags` джерела `cls-docs` (нижче).

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія ядра

Сторінки сайту беруться з теки `docs/docs` репозиторію на тегах ядра `nestjs-cls@X.Y.Z`; ключ у полі `tags` — повний
SHA коміту тегу, значення — версія. Новий тег додають на початок переліку (він іде від найновішого):

```
git ls-remote --tags https://github.com/Papooch/nestjs-cls 'nestjs-cls@7.1.0'   # SHA коміту тегу
```

```json
"tags": { "<sha>": "7.1.0", … }
```

Без цього сторінки сайту нової версії в корпус не потраплять, хоч README, реліз і реєстр підхопляться самі. Теги плагіна
й адаптерів (`@nestjs-cls/transactional@…`) у `tags` не додають: сайт один на всі пакети і версіонується ядром.

```
./df nestjs-cls check                 # чи змінилося щось нагорі за джерелом
./df nestjs-cls refresh               # повне перезавантаження, близько 10 хвилин
./df nestjs-cls manifest
./df nestjs-cls vectors
./df nestjs-cls smoke
# Ctrl+C у терміналі з serve, і знову: ./df nestjs-cls serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (сторінка, що не змінилася, дописує нову версію в рядок `# версія:`).

Якщо вийшла нова мажорна лінія ядра (8.0) або плагіна (transactional-5):

- у `prompts/search.txt` (абзац «Which version to search first» і перелік ліній) та `prompts/agent.txt` замінити
  поточну лінію на нову, а версію за замовчуванням звірити з числом завантажень
  (`https://api.npmjs.org/versions/nestjs-cls/last-week`, для плагіна — `…/@nestjs-cls%2Ftransactional/last-week`):
  відповідь іде для найпопулярнішої лінії, а коли дві майже рівні — для обох; на 24.10.2026 лінія 6 ядра мала 63 %,
  лінія 5 — 14 %, лінія 7 — 12 %, лінія 4 — 8 %; у плагіна лінія 3 — 80 %, лінія 4 — 15 %;
- у `checks.json`, у десятках `quality` і `quality_model`, замінити лінію там, де питання про поточну поведінку, і звірити
  цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

## Вийшла нова версія плагіна чи адаптера

Нічого не прив'язувати: README береться з tarball нової версії, реліз — з потоку релізів за префіксом тегу
(`@nestjs-cls/transactional-adapter-prisma@`), реєстр — з опису пакета. Якщо з'явився новий адаптер (новий пакет
`@nestjs-cls/transactional-adapter-<база>`), йому додають три джерела за зразком наявних (`<база>-readme`,
`<база>-releases`, `<база>-npm`) з власними `version_prefix` «adapter-<база>-» і `name_prefix` для README та реєстру, і
згадують його в `prompts/` та README.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) не обов'язковий, але без нього звернення до API GitHub (35 дерев тегів
і сторінки релізів) ідуть годинними вікнами по 60.

Передрелізи ядра пропускає поле `skip_versions` у README («-» у номері); у релізах монорепозиторію передрелізів немає,
а читач `ghreleases-stable` їх і так не бере.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df nestjs-cls quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
