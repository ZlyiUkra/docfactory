Search the nestjs-cls documentation -- the npm package `nestjs-cls` (a continuation-local storage module, built on
AsyncLocalStorage, that is compatible with the dependency injection of NestJS; repository Papooch/nestjs-cls, site
papooch.github.io/nestjs-cls) -- together with its Transactional plugin `@nestjs-cls/transactional` and the eight
transactional adapters `@nestjs-cls/transactional-adapter-prisma`, `-typeorm`, `-drizzle-orm`, `-kysely`, `-knex`,
`-mongoose`, `-mongodb` and `-pg-promise`. The corpus holds: the pages of the documentation site as they stood at the
tag of every core version from 3.5.1 to 7.0.1 (installation, quick start, how it works, setting up the CLS context with
a middleware, a guard, an interceptor, the @UseCls decorator or cls.run, request id, additional CLS setup, breaking out
of DI, usage outside of a web request, type safety and type inference, proxy providers, the ClsService interface and
the module options, security and compatibility considerations, the plugin API, the Transactional plugin and every
adapter, testing, the migration guides v2→v3 … v6→v7); the README of every stable version of every package (before
3.5.1 the README of `nestjs-cls` was the whole documentation); the GitHub release notes of every package; and the npm
registry history of every package (date of every version, dist-tags, dependencies, peer dependencies, Node.js
requirement). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about nestjs-cls as it describes itself -- ClsModule.forRoot and forRootAsync, the
options `global`, `middleware`, `guard`, `interceptor` (mount, generateId, idGenerator, setup, saveReq, saveRes,
useEnterWith), ClsService (get, set, has, getId, run, runWith, enter, exit, isActive, setIfUndefined), the typed
store ClsStore and the Terminal type, ClsMiddleware, ClsGuard, ClsInterceptor, the decorator @UseCls, cls.run outside
of a request (cron jobs, queue consumers, microservices, websocket gateways, passport strategies), proxy providers
(ClsModule.forFeature, forFeatureAsync, @InjectableProxy, class and factory proxy providers, strict mode), the
Transactional plugin (ClsPluginTransactional, the decorator @Transactional, TransactionHost with tx, withTransaction
and withoutTransaction, the propagation modes Required, RequiresNew, NotSupported, Mandatory, Never and Supports,
several connections with connectionName, enableTransactionProxy, isolation levels of the adapters, writing a custom
adapter), compatibility with REST, GraphQL, websockets and microservices, the plugin API for library authors, testing
with CLS -- and above all history and compatibility: since which version an option, method or adapter exists, what
changed between versions (every major has a migration guide in the documentation and a release note on GitHub), which
versions require which NestJS and Node.js (the peer dependencies and the `engines` field of every version are written
in the npm registry documents), and when every version came out.

Do not call this for the NestJS framework itself (modules, providers, request scope, middleware in general), for
AsyncLocalStorage and the async_hooks module of Node.js, for `cls-hooked` or other CLS libraries, nor for Prisma,
TypeORM, Drizzle, Kysely, Knex, Mongoose, the MongoDB driver or pg-promise beyond their nestjs-cls adapter: their
documentation is not here, and the search will return excerpts that merely mention them, with confident-looking
titles.

`version` narrows the search to one release line. The core package is numbered 0.x to 7.x (73 stable versions, 0.1.0
to 7.0.1): a line of one number keeps every document of that major ("6" keeps 6.0.0 to 6.3.1, "7" keeps 7.0.0 and
7.0.1), two numbers keep a minor ("6.2"), three an exact version ("6.2.1"). The site pages carry the core version of
the tag they were taken from, from 3.5.1 on; before that the documentation is the README of the version. The versions
of the plugin and of the adapters are written with a prefix, because their numbers would otherwise collide with those
of the core: `@nestjs-cls/transactional` has 43 stable versions, "transactional-1.0.1" to "transactional-4.0.1"
("transactional-3" keeps every 3.x document of the plugin); the adapters are "adapter-prisma-1.0.1" to
"adapter-prisma-2.0.1", "adapter-typeorm-1.1.0" to "adapter-typeorm-2.0.1", and likewise "adapter-drizzle-orm-",
"adapter-kysely-", "adapter-knex-", "adapter-mongoose-", "adapter-mongodb-", "adapter-pg-promise-" (every adapter is
at 2.0.1). A bare "2" keeps core 2.x only. Leave `version` empty to search everything, including text that carries no
version. Every excerpt comes back with `versions`: each version whose documents contain this exact text, newest
first -- text that stayed the same across versions is returned once, with all of them listed, so the list itself shows
from which to which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("ClsService", "ClsModule.forRoot",
"ClsMiddleware", "UseCls", "proxy providers", "InjectableProxy", "Transactional", "TransactionHost", "Propagation",
"TransactionalAdapterPrisma", "idGenerator", "setup"), not in the user's own words. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters and digits, so a
query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into the terms of the documentation first,
then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer point by point:
 since which version it exists; what changed in later versions; what prompted the change, if the excerpts say
so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація nestjs-cls". Identifiers, method names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads the core line 6 leads with about 63 % (6.2.0 about 22 %, 6.2.1
about 16 %, 6.3.1 about 8 %), the line 5 follows with about 14 % (5.4.3), the line 7 -- the newest, 7.0.1 of September
2026 -- with about 12 % and the line 4 with about 8 %. Pass `version` "6" for how things are done today, and mention 7
when it differs (the migration guide v6x-v7x and the release note nestjs-cls@7.0.0 say what changed) and 5 or 4 when
the user is on them. For the Transactional plugin the line "transactional-3" leads with about 80 % and
"transactional-4" has about 15 %: search "transactional-3" first and mention 4 when it differs. Search without `version`
when the question is about history, or when the line gave nothing. Every answer says which version it is for; when the
excerpts behind a statement come only from older versions, name those versions instead of presenting the text as
current.
