# nestjs-pino — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про `nestjs-pino` — логер для NestJS на pino і pino-http з контекстом
запиту в кожному рядку логу (репозиторій iamolegga/nestjs-pino) — за документацією всіх його стабільних версій: README
кожної версії (сайту пакет не має, README і є документацією), нотатки релізів GitHub та історія версій у реєстрі npm.
Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену.
Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

Вбудований `Logger` NestJS пише текст або JSON без зв'язку з запитом: щоб знайти в лозі всі рядки одного запиту, його
ідентифікатор довелося б протягувати параметром. `nestjs-pino` підміняє логер застосунку
(`app.useLogger(app.get(Logger))`) і через pino-http та `AsyncLocalStorage` додає до кожного рядка `req.id` та дані
запиту, сам логує кожну відповідь, дає `PinoLogger` з API pino, `assign` для полів на решту запиту, `runInContext` для
черг і cron, параметр `microservice` для обробників повідомлень і `NativeLogger` — заміну `ConsoleLogger` з тим самим
JSON. У плані NestJS (фулстек-родина) це логи продакшну фази 6.

За шість мажорних ліній змінилося все: у 1.0 параметри переїхали в `pinoHttp`, у 2.0 з'явилася підміна логера через
`useLogger`, 3.0 вимагає pino 8, 4.0 — pino-http 9, 5.0 — NestJS 11.0.8+/12, pino 10, pino-http 11 і Node.js 22.12.
Посібники міграції — у README, що змінилося в кожному релізі — на GitHub, вимоги до NestJS, pino і Node — лише в
реєстрі npm. Усе це в одному місці, з номером версії біля кожного уривка.

`pinoHttp`. Коду й типів пакета: README описує кожен клас і параметр.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа. Самих
  текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише
  для завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df nestjs-pino <крок>`.

## Версії

Версія — номер випуску. Фільтр `version` бере мажор (`"4"`), мінор (`"4.6"`) або точну версію (`"4.6.1"`). Без
названої версії промпт велить шукати для лінії 4 — на неї за тиждень до 24.10.2026 припадало близько 75 % завантажень
(4.6.1 сама — 50 %, 4.4.0 — 9 %, 4.5.0 — 6 %), на лінію 5 (найновіша, 5.3.1 від 02.10.2026) близько 21 %, на лінію 3
близько 3 %; де 5.x відрізняється (розділ Migration v5 у README, релізи 5.0.0–5.3.1), модель згадує й її. README, що
не змінився між версіями, — один документ з усіма ними, тож перелік версій уривка сам показує, відколи й доки
документація казала саме це.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/nestjs-pino-corpus-2026-10-24.tar.gz` (82 тексти, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском) і в копії на Windows-диску
`C:\Distr\nestjs-pino-corpus-2026-10-24.tar.gz` (звірено за SHA-256). В історії git текстів немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/nestjs-pino/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/nestjs-pino-corpus-РРРР-ММ-ДД.tar.gz -C instances/nestjs-pino corpus raw
find instances/nestjs-pino/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/nestjs-pino/raw
gzip -9 -c instances/nestjs-pino/index/passages.json > instances/nestjs-pino/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/nestjs-pino-corpus-2026-10-24.tar.gz -C instances/nestjs-pino
./df nestjs-pino smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/nestjs-pino/index/passages.json.gz`,
далі `./df nestjs-pino vectors` заллє колекцію Qdrant (секунди на відеокарті, менше хвилини на процесорі).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df nestjs-pino …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md, розділ
«Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df nestjs-pino sources --why   # перелік джерел і білий список
./df nestjs-pino refresh         # завантажити все задеклароване (близько 2 хвилин)
./df nestjs-pino manifest        # оновити паспорт
./df nestjs-pino setup           # Qdrant чи пошук лише по словах
./df nestjs-pino vectors         # залити корпус у docs-nestjs-pino
./df nestjs-pino smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df nestjs-pino serve          # порт 8880
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8880/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user nestjs-pino-docs http://127.0.0.1:8880/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `nestjs-pino-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у [README
примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
