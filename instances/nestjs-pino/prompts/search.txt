Search the nestjs-pino documentation -- the npm package `nestjs-pino` (a platform-agnostic logger for NestJS built on
pino and pino-http, with the request context in every log line; repository iamolegga/nestjs-pino). The package has no
documentation site: its README is the documentation, and the corpus holds the README of every stable version from
0.1.0 to 5.3.1 (install, the example with LoggerModule.forRoot and app.useLogger, the two loggers -- the NestJS `Logger`
substitute and `PinoLogger` with `@InjectPinoLogger` and setContext, the drop-in `NativeLogger` with
`nativeLoggerOptions`, the comparison with nest-winston, the configuration -- the `Params` interface with `pinoHttp`,
`forRoutes`, `exclude`, `useExisting`, `renameContext`, `assignResponse`, `microservice` and `nativeLogger`,
synchronous and asynchronous configuration with forRootAsync, asynchronous logging and flushing on shutdown, testing
with `getLoggerToken`, extending `Logger`/`PinoLogger` with `PARAMS_PROVIDER_TOKEN`, `assign` for extra fields,
microservices and hybrid applications with `registerMicroserviceLogging`, `MicroserviceParams` and `getRpcInfo`,
`runInContext` for queue processors, cron jobs and scripts, `PinoLogger.root` for changing pino params at runtime,
`LoggerErrorInterceptor`, the migration guides to v1, v2 and v5, the FAQ with the mapping of pino levels to NestJS
methods); the GitHub release notes of every version from 2.0.1 to 5.3.1; and the npm registry history (date of every
version, dist-tags, dependencies, peer dependencies on pino, pino-http, @nestjs/common and @nestjs/core, the Node.js
requirement). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about nestjs-pino as it describes itself -- LoggerModule.forRoot and forRootAsync, the
`Params` fields, `Logger` versus `PinoLogger` versus `NativeLogger`, `@InjectPinoLogger`, `assign`, `runInContext`,
`PinoLogger.root`, `LoggerErrorInterceptor`, `getLoggerToken`, `PARAMS_PROVIDER_TOKEN`, the `microservice` parameter
and its `MicroserviceParams`, `registerMicroserviceLogging`, `getRpcInfo`, `useExisting` with the Fastify adapter,
`bufferLogs` and `app.flushLogs`, the double-logging trap of importing the bare LoggerModule, `LazyModuleLoader`, the
level mapping (trace → verbose, info → log) -- and above all history and compatibility: since which version a
parameter, class or method exists, what changed between versions (every major has a migration section in the README
and a release note on GitHub), which versions require which NestJS, pino, pino-http and Node.js (the compatibility
table of the README, and the peer dependencies and the `engines` field of every version in the npm registry
documents), and when every version came out.

Do not call this for pino itself (the options `level`, `redact`, `serializers`, `transport`, `customLevels`,
`pino.destination`, child loggers), for pino-http (`autoLogging`, `genReqId`, `customProps`, `customLogLevel`,
`customSuccessMessage`, `quietReqLogger`), for pino-pretty, nor for the NestJS framework in general (modules,
middleware, `ConsoleLogger`, the `LoggerService` interface, microservice transports): their documentation is not here
-- the README only says which of their options go into the `pinoHttp` field -- and the search will return excerpts
that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. The package is numbered 0.x to 5.x (57 stable versions, 0.1.0 to
5.3.1): a line of one number keeps every document of that major ("4" keeps 4.0.0 to 4.6.1, "5" keeps 5.0.0 to
5.3.1), two numbers keep a minor ("4.6"), three an exact version ("4.6.1"). Leave `version` empty to search
everything, including text that carries no version. Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first -- a README that stayed the same across versions is returned once,
with all of them listed, so the list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("LoggerModule.forRoot", "pinoHttp",
"PinoLogger", "InjectPinoLogger", "NativeLogger", "assign", "assignResponse", "runInContext", "useExisting",
"renameContext", "LoggerErrorInterceptor", "getLoggerToken", "microservice", "getRpcInfo"), not in the user's own
words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate the question into
the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer point by point:

so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація nestjs-pino". Identifiers, method names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads the line 4 leads with about 75 % (4.6.1 alone about 50 %, 4.4.0
about 9 %, 4.5.0 about 6 %), the line 5 -- the newest, 5.3.1 of October 2026 -- has about 21 % and the line 3 about
3 %. Pass `version` "4" for how things are done today, and mention 5 when it differs (the migration section v5 of the
README and the release notes 5.0.0 to 5.3.1 say what changed: NestJS 11.0.8+ or 12.0.2+, pino 10, pino-http 11,
Node.js 22.12, the `dist/` exports map, `runInContext`, the `microservice` parameter, NativeLogger matching the
NestJS 12.1.1 ConsoleLogger) and 3 when the user is on it. Search without `version` when the question is about
history, or when the line gave nothing. Every answer says which version it is for; when the excerpts behind a
statement come only from older versions, name those versions instead of presenting the text as current.
