# Оновлення корпусу nestjs

Три різні роботи, які легко переплутати: звичайне оновлення поточної лінії, вихід нової мажорної лінії і збирання
примірника з нуля. Порядок усередині кожної важливіший за самі команди, тому кроки пронумеровані.

Головне правило, з якого випливає все інше: **знімок робиться ПЕРШИМ, до підняття живого джерела.** Сайт NestJS
тримає лише поточну лінію. Щойно вийде наступна, попередня зникне з сайту назавжди, і взяти її буде нізвідки,
окрім історії репозиторію. Тому черговість не косметична.

Друге правило: **імена документів зводяться самі, руками їх не чіпають ніколи.** У репозиторії сайту файли звуться
по-старому (`sql.md`, `unit-testing.md`, `dependency-injection.md`), а сторінки живуть за адресами
`techniques/database`, `fundamentals/testing`, `fundamentals/custom-providers`. Поле `route_map` у джерелі велить
читачеві побудувати таблицю відповідності з модулів маршрутизації Angular **того самого коміту**, на якому стоїть
знімок. Коміт закріплений, отже таблиця відтворюється точно, отже повне перекачування корпусу дасть ті самі імена
файлів. Переназивати нічого не доведеться ні зараз, ні після повного знесення бази.

Що робить читач, коли не певен, і чому це важливо: кореневого модуля маршрутів немає — відмова; не розібралося
жодної пари «адреса — компонент» (Angular змінив синтаксис) — відмова; дві сторінки зводяться на одну адресу —
відмова. Сторінка з кількома адресами лишається під іменем файлу. Незведене ім'я нічого не псує, воно лише не
зіллється з сусідньою версією. Вгадане — псує, бо дає хибну відповідь на питання «з якої версії це так».

Третє правило: **нічого не видаляється.** Якщо сторінка зникла з сайту, її текст лишається в корпусі під своєю
версією. Питання «як це було в дев'ятій» не має ламатися через те, що у дванадцятій главу прибрали. Ані
`refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

## 1. Звичайне оновлення поточної лінії

Раз на кілька тижнів, або коли в релізах щось помітне.

```
./df nestjs check                      # що нагорі змінилося за паспортом
./df nestjs refresh nestjs-12          # перечитати живий сайт
./df nestjs refresh nestjs-releases    # дотягнути нові релізи
./df nestjs manifest                   # оновити паспорт
./df nestjs vectors                    # дорахувати лише змінені фрагменти
./df nestjs smoke                      # звірити, що нічого не поїхало
```

`check` на заморожених джерелах (`nestjs-6` … `nestjs-11`) мусить мовчати завжди. Якщо він щось про них каже, це
означає, що хтось переписав історію репозиторію. Це привід розбиратися, а не оновлювати.

Після `refresh` число фрагментів зазвичай змінюється, і `smoke` про це скаже. Тоді треба оновити
`expected_passages` у `checks.json` і в полі `expected_note` записати, коли й чому число знято.

## 2. Вийшла нова мажорна лінія

Скажімо, вийшла 13. Кроки строго в цьому порядку.

**Крок 1. Знайти коміт репозиторію сайту на день виходу 13.0.0.**

```
curl -s "https://api.github.com/repos/nestjs/docs.nestjs.com/commits?until=РРРР-ММ-ДДT23:59:59Z&per_page=1" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d[0]['sha'], d[0]['commit']['committer']['date'][:10])"
```

Дату виходу беруть з релізів `nestjs/nest`. Знімок робиться **на день виходу нової** лінії: саме тоді сайт ще
показує стару, і це останній момент, коли її можна взяти.

**Крок 2. Заморозити попередню лінію.** У `sources.json` додати джерело `nestjs-12` за зразком інших знімків:
читач `ghdocs-heading`, `frozen: true`, `folders: ["content"]`, `recursive: true`, `root: "content"`,
`route_map: true`, у `within` — дві теки того ж коміту:
`https://raw.githubusercontent.com/nestjs/docs.nestjs.com/<SHA>/content/` і `…/<SHA>/src/app/` (друга потрібна
читачеві, щоб прочитати модулі маршрутизації), у `version` — `"12"`.

**Крок 3. Аж тепер підняти живе джерело.** У джерелі, що читає сайт, змінити `id` на `nestjs-13` і `version` на
`"13"`. Заодно звірити `within`: за рік у документації могла з'явитися нова тека верхнього рівня або нова сторінка
в корені, а білий список перелічує їх поіменно. Перевірити так:

```
curl -s https://docs.nestjs.com/llms.txt | grep -oE 'https://docs\.nestjs\.com/[^)]+\.md' \
  | sed 's|https://docs.nestjs.com/||' | awk -F/ 'NF>1{print $1"/"} NF==1{print $0}' | sort -u
```

Кожен рядок із скісною рискою мусить бути в `within` як тека, кожен файл — як окрема сторінка. Чого немає в
списку, те не завантажиться, і `list` покаже менше сторінок, ніж є насправді.

**Крок 4. Завантажити обидва.**

```
./df nestjs sources --why
./df nestjs list nestjs-12             # знімок: перелік має збігтися з числом сторінок тієї лінії
./df nestjs refresh nestjs-12
./df nestjs refresh nestjs-13
./df nestjs manifest
```

**Крок 5. Вектори й перевірки.**

```
./df nestjs vectors
./df nestjs smoke
./df nestjs quality
```

Оновити `expected_passages` у `checks.json`, а в `README.md` дописати нову лінію в таблицю джерел.

## 3. Збирання з нуля

Якщо примірник треба відтворити повністю. Усі команди з кореня `docfactory/`.

**Крок 1. Тека і venv.** Єдиний крок зсередини теки примірника.

```
mkdir -p instances/nestjs/prompts
cp instances/react/requirements.txt instances/react/.gitignore instances/react/.env.example instances/nestjs/
cd instances/nestjs
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cd ../..
```

Якщо системний `python3` іде без модуля `venv`, беруть інтерпретатор, у якого він є, наприклад
`/шлях/до/miniconda3/bin/python3 -m venv .venv`. На все подальше це не впливає: venv самодостатній.

**Крок 2. `config.json`.** Порт 8762, колекція `docs-nestjs`, `sections: "markdown"`, `versions: true`,
інструменти `search_docs` і `read_section`, `answer_hosts` — `docs.nestjs.com`, `nestjs.com`, `github.com`.
`.mcp.json` — запис HTTP-сервера на тому самому порту.

**Крок 3. `sources.json`.** Вісім джерел: живий сайт, шість заморожених знімків і релізи. SHA комітів записані в
самому файлі, у полі `url` кожного знімка, тож відтворення не потребує повторного пошуку.

**Крок 4. Перевірити оголошення й пробний перелік.**

```
./df nestjs sources --why
./df nestjs list nestjs-6              # найменший знімок: 73 сторінки, один виклик GitHub API
```

**Крок 5. Завантажити.** Двома командами, і це не примха. `refresh` без імен свідомо не питає заморожених джерел:
знімок на закріпленому коміті не міняється, тож щоразу його перечитувати нема сенсу. Але при збиранні з нуля його
ще немає, і назвати його доводиться явно.

```
./df nestjs refresh                                                           # живий сайт і релізи
./df nestjs refresh nestjs-11 nestjs-10 nestjs-9 nestjs-8 nestjs-7 nestjs-6   # знімки, поіменно
./df nestjs manifest
```

Часу це займає близько години: приблизно 850 файлів при паузі `pause_sec: 5`, тобто одинадцять файлів за хвилину.
Ліміт GitHub API без ключа — 60 звернень на годину, і його витрачають лише сім викликів (шість дерев і сторінки
релізів); файли тягнуться з `raw.githubusercontent.com`, який до ліміту не рахується.

**Крок 6. Промпти.** П'ять файлів у `prompts/`: `search.txt`, `read.txt`, `loaded.txt`, `agent.txt`,
`refusal.txt`. Копіювати з `react` не можна — вони називають React.

**Крок 7. `checks.json`.** Пишеться після корпусу, бо потребує справжнього числа фрагментів і справжніх id.

**Крок 8. Вектори, перевірки, сервер.**

```
./df nestjs setup
./df nestjs vectors
./df nestjs smoke
./df nestjs protocol
./df nestjs quality
./df nestjs serve
```

## Що робити, коли щось не так

**`refresh` каже «Сторінка не схожа на документ: немає назви».** Сайт змінив формат: або з'явилася шапка YAML,
або зник заголовок на початку файлу. Читачі `llms-heading` і `ghdocs-heading` беруть назву саме з першого
заголовка, і це їхня єдина відмінність від `llms` та `ghdocs`.

**`list` показує менше сторінок, ніж є на сайті.** Білий список `within` не покриває нову теку чи нову сторінку
кореня. Перелік перевіряють командою з кроку 3 розділу 2.

**`list` мовчить про заморожені джерела.** Так і має бути: без імені джерела їх не питають. Щоб звернутися до
знімка, його `id` називають явно — `./df nestjs list nestjs-8`.

**Вичерпано ліміт GitHub API.** Чекають до скидання (`curl -s https://api.github.com/rate_limit`) і продовжують
`./df nestjs refresh --missing`, який пише лише відсутні файли.

**`refresh` каже «у модулях маршрутизації не розібралося жодної пари».** Angular змінив спосіб опису маршрутів:
замість `component:` тепер, скажімо, `loadComponent:`. Треба дописати ще один зразок у `_ROUTE` і `_IMPORT`
модуля `engine/readers/mdheading.py`. Доти крок падає, і це навмисно: тихо неправильні імена гірші за зупинку.

**`refresh` каже «адреса X належить і A, і B».** Дві сторінки репозиторію зводяться на одну адресу сайту. Це або
справжній конфлікт у маршрутах, або зміна їхньої структури. Розбиратися треба руками; читач у такому разі не
зводить нічого.

**Сервер при старті каже, що в колекції більше точок, ніж фрагментів.** Після того, як частина фрагментів злилася
чи зникла, у Qdrant лишаються сироти. Пошук їх не показує. Прибрати можна лише знесенням колекції з повним
перерахунком, і це рішення людини: жоден крок фабрики нічого не видаляє сам.
