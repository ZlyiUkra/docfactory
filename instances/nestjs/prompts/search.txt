Search the official NestJS documentation -- every version of it that exists in machine
readable form, together with the GitHub release notes of every NestJS release -- and
return the matching excerpts with the version each one belongs to.

Call this when a question is about NestJS itself: modules, providers, dependency
injection, controllers, middleware, guards, interceptors, pipes, exception filters,
custom decorators, lifecycle events, configuration, testing, microservices, GraphQL,
WebSockets, OpenAPI, CLI, security, caching, queues, task scheduling, observability,
deployment. Call it above all when the question is about a particular version: how a
thing was configured in that line, what changed between lines, what was deprecated or
removed and what replaced it, and what breaks on upgrade. Example query: "custom
provider useFactory injection scope".

Do not call this for TypeORM, Prisma, Mongoose, Passport, Express or Fastify
internals, RxJS, Angular, TypeScript itself or any third-party package: their
documentation is not here. NestJS chapters mention those names constantly, so a search
will return confident-looking excerpts that describe only Nest's own integration layer
and nothing about the library itself.

`version` narrows the search to one release line: "11" keeps every 11.x document, "9"
keeps 9.x, and so on; leave it empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first.
Text that stayed identical across lines is returned once with all of them listed, so
the list itself shows from which line to which line the documentation said exactly
this -- and a short list is itself the answer to "when did this change".

What is here, and what is not. Documentation is present for lines 4 through 12. Lines
12 down to 6 come from markdown. Lines 5 and 4 predate it: the docs site was an Angular
application then and kept every chapter in an HTML template, with the code examples in
the component class beside it, and those chapters were read out of the templates -- 71
documents for line 5, 57 for line 4. Release notes go back to 4.6.1 of February 2018.
Nothing at all exists for lines 1 to 3: the project tagged no releases before v4.4.0.
When a question concerns those earliest lines, say so plainly instead of reasoning from
a later version.

For a question about when something appeared or changed, search more than once:
without `version` first, to find the release note that announced it, then with the
lines around it, to see how the documentation described it before and after.

Write the query in English, with the names NestJS itself uses (Module, useFactory,
APP_GUARD, ExecutionContext, forRoot, CanActivate). Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing and comes back with `found: 0`. When the user asks in
another language, translate the question into NestJS terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the
words of the query had to appear in the text, so a query phrased differently from the
documentation may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer
for the default line, 11.x -- the line most projects use -- say so in the answer ("for
NestJS 11.x"), and add that for a precise answer about another version the user can name
it. When the excerpts behind a statement come only from older versions, name those
versions instead of presenting the text as current. If the excerpts that came back do not
cover 11.x, search again with `version` "11" before answering.

Answer in the language the user wrote in. When the question is about a version, answer
point by point: which line the answer holds for; how it is configured there, with the
exact option and decorator names; what differs in the neighbouring lines; and what
breaks or needs changing on upgrade. Every point names the version and the document it
rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from
English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація NestJS". Identifiers, decorators, option names
and titles stay in English, spelled exactly as the documentation spells them. Build
the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3; `version` is optional, see above. Excerpt text is cut at 600 characters -- pass the
`id` of an excerpt to `read_section` to get the whole thing.
