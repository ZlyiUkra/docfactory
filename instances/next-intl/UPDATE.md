# Оновлення корпусу next-intl

Руками оголошено лише теги репозиторію `amannn/next-intl`: поле `tags` джерела `next-intl-site`. Новий стабільний тег
дописують першим рядком, у вигляді `"v4.15.0": "4.15.0"`. README чотирьох пакетів і реєстр беруться з опису пакетів
у реєстрі npm (`https://registry.npmjs.org/next-intl`, `…/use-intl`, `…/icu-minify`,
`…/next-intl-swc-plugin-extractor`), журнал змін — з `CHANGELOG.md` гілки `main`, тож нові версії там з'являються
самі.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df next-intl check                 # чи змінилося щось нагорі за джерелом
./df next-intl refresh               # повне перезавантаження, близько 35 хвилин
./df next-intl manifest
./df next-intl vectors
./df next-intl smoke
# Ctrl+C у терміналі з serve, і знову: ./df next-intl serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий тег змінює й старі
документи.

Якщо сайт додасть новий компонент, що несе текст (як вкладки `Tabs` чи назва файла блоку коду), чи знову
перенесе теку документації, — правка в `engine/readers/ghnextintl.py` чи в полях `folders`/`exclude` джерела, далі
`./df next-intl build next-intl-site` без мережі. Після правки читача — звірити заголовки записаних сторінок з
оригіналами (практика з [NEW-INSTANCE.md](../../NEW-INSTANCE.md)).

Якщо вийшла нова мажорна лінія:

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінію за
  замовчуванням: вона — найпопулярніша за завантаженнями npm (на 13.10.2026 — 4.x, 93,6 %);
- у `checks.json`, у десятці `quality_model`, замінити `"4"` там, де питання про поточну поведінку, і звірити цілі
  (ціль «зміни мажорної версії» — допис блогу про новий мажор).

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у `.env`) потрібен для дерев 250 тегів.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df next-intl quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
