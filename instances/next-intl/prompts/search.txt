Search the next-intl documentation -- the next-intl.dev site (docs and blog) as it stood at every
stable release from 1.2.0 on, taken from the amannn/next-intl repository; the README of every
stable version of next-intl, of use-intl (its core without Next.js), of icu-minify and of
next-intl-swc-plugin-extractor; the changelog of every release; and the npm registry history of all
four packages -- and return the matching excerpts with the versions each one belongs to. next-intl
is the internationalization (i18n) library for Next.js: messages in ICU format, formatting of dates,
times, numbers and lists, locale-based routing with middleware (proxy in Next.js 16) and navigation
APIs, for the App Router (Server and Client Components) and the Pages Router.

Call this when a question is about next-intl or use-intl itself -- useTranslations, getTranslations,
useFormatter, getFormatter, useLocale, useNow, useTimeZone, useMessages, NextIntlClientProvider,
IntlProvider, getRequestConfig (i18n/request.ts), createNextIntlPlugin, defineRouting,
createMiddleware, createNavigation (Link, redirect, usePathname, useRouter, getPathname),
setRequestLocale, hasLocale, localePrefix, localeDetection, pathnames, domains, rich text
(t.rich, t.markup, t.raw, t.has), plurals and select in ICU messages, typed messages with
AppConfig, error handling (onError, getMessageFallback), metadata, route handlers, server actions,
testing, Storybook, useExtracted and message extraction, precompilation with icu-minify -- and above
all history and compatibility: since which version an API exists, what changed between 2.x, 3.x and
4.x, which Next.js and React versions each release supports (the peer dependencies of each version
are written in the npm registry documents). Example query: "useTranslations rich text".

Do not call this for Next.js itself (routing, middleware, generateMetadata), for React, for the
Intl API of JavaScript, for the ICU message syntax specification or for i18next and react-intl:
their documentation is not here, and the search will return next-intl excerpts that merely mention
them, with confident-looking titles.

`version` narrows the search to one release line: "4" keeps every 4.x document, "3.26" keeps
3.26.x; leave it empty to search everything. Every excerpt comes back with `versions`: each version
whose documents contain this exact text, newest first -- text that stayed the same across versions
is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names next-intl itself uses ("getRequestConfig", "defineRouting",
"createNavigation", "NextIntlClientProvider", "setRequestLocale"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any
other non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into next-intl terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація next-intl". Identifiers, option names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something, pass `version` "4" --
almost every install is on 4.x. If the user names a version, or their code shows one
(createSharedPathnamesNavigation, createLocalizedPathnamesNavigation, unstable_setRequestLocale,
`locale` instead of `requestLocale` in getRequestConfig -> 3.x; NextIntlProvider,
next-intl/client -> 2.x), search that line. Put a version only into `version`, never into the
query text: numbers in the query match the npm registry documents and changelog entries, which list
every release, instead of the text you need. For what changed in a major version, search
"announcement upgrade now" with `version` set to that major: every major release (3.0, 4.0) is
announced in a blog post titled "next-intl X.0" that lists the changes and ends in an "Upgrade now"
section, while the changelog entry of X.0.0 only links to it. Search without `version` when the
question is about history, or when the line gave nothing. Every answer says which version it is for; when the user
did not name one, answer for 4.x and say so ("for next-intl 4.x"). When the excerpts behind a
statement come only from older versions, name those versions instead of presenting the text as
current.
