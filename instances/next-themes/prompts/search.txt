Search the next-themes documentation -- the README of every stable version of the next-themes
npm package (0.0.2 to 0.4.6), the TypeScript declarations shipped in the package, the GitHub
release notes of 0.2.0-0.4.6, the example apps of every stable version and the npm registry
history -- and return the matching excerpts with the versions each one belongs to. next-themes
switches the theme of a React app -- light, dark, the system preference or any number of custom
themes -- by setting a class or a data attribute on the html element, remembers the choice in
localStorage, and injects a small script so the page does not flash the wrong theme on load. It
works with the Next.js App Router and Pages Router and with any React app.

Call this when a question is about next-themes itself -- ThemeProvider and its props
(attribute: class or data-*, several attributes at once, defaultTheme, enableSystem,
enableColorScheme, disableTransitionOnChange, storageKey, themes, forcedTheme, value, nonce,
scriptProps), useTheme and what it returns (theme, setTheme, resolvedTheme, systemTheme,
forcedTheme, themes), where to put the provider in app/layout and pages/_app, a theme toggle
button, avoiding the hydration mismatch (mounted check, suppressHydrationWarning on html, dynamic
import with ssr false, theme-dependent images), the flash of the wrong theme and the injected
script, more than light and dark, a page forced to one theme, Tailwind CSS dark mode with the
class strategy or a custom selector, styled-components and CSS-in-JS, Content Security Policy,
Cloudflare Rocket Loader, the FAQ -- and above all history and compatibility: since which version
a prop exists, what each release changed, which React and Next.js versions a release accepts (the
peerDependencies of each version are written in the npm registry documents). Example query:
"useTheme resolvedTheme".

Do not call this for Next.js itself, for React, for Tailwind CSS, for CSS in general or for
other theming and UI libraries (shadcn/ui, Radix, MUI, Chakra): their documentation is not here,
and the search will return next-themes excerpts that merely mention them, with confident-looking
titles.

`version` narrows the search to one release line: "0.4" keeps every 0.4.x document, "0.3" keeps
0.3.0; leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which
to which version the documentation said exactly this.

Write the query in English, with the names next-themes itself uses ("ThemeProvider",
"resolvedTheme", "disableTransitionOnChange", "forcedTheme", "suppressHydrationWarning"), not in
the user's own words. Everything here is English -- the excerpts, the word index and the meaning
index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into next-themes
terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація next-themes". Identifiers, prop names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it
says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something, pass `version` "0.4"
-- the most downloaded line (about four in five installs); 0.3.0 comes second. If the user names
a version, or their code shows one, search that line. Put a version only into `version`, never
into the query text: numbers in the query match the npm registry documents, which list every
release, instead of the text you need. Search without `version` when the question is about
history, or when the line gave nothing. Every answer says which version it is for; when the user
did not name one, answer for 0.4.x and say so ("for next-themes 0.4.x"). When the excerpts behind
a statement come only from older versions, name those versions instead of presenting the text as
current.
