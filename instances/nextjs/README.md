# nextjs — примірник фабрики docfactory

Дев'ятнадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Next.js за офіційною
документацією всіх версій — обох роутерів, App Router і Pages Router, — поясненнями помилок, README кожної версії
пакета `next` і дев'яти пакетів поруч, нотатками релізів, реєстром версій npm, блогом nextjs.org, прикладами з
репозиторію, шаблонами з галереї Vercel і сторінкою showcase. Код спільний і лежить у `../../engine/`,
`../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо

Next.js за десять років змінив шістнадцять мажорних версій і один раз — самий спосіб писати застосунок: з 13.4 поруч
із Pages Router (`pages/`, `getServerSideProps`, `_app`) стоїть App Router (`app/`, серверні компоненти, `layout`,
Server Actions), і майже кожна сторінка документації відтоді існує двічі, з різним кодом і різними порадами. А
всередині App Router так само рухається кешування: `fetch` з кешем за замовчуванням у 13–14, без нього у 15,
`use cache` і Cache Components у 16; `middleware` у 16 став `proxy`. Відповідь «як це зробити» залежить і від
версії, і від роутера.

Тому тут документація кожного тегу, а не лише поточна: текст, що не змінювався між версіями, лежить один раз із
переліком усіх версій, де він був таким, а сторінки двох роутерів — окремі документи з підписом роутера в назві.
Для питань «що з чим сумісне» (Next.js 16 і React 19, Node, TypeScript) — реєстр npm з peer-залежностями кожної
версії; для «коли це з'явилося й навіщо» — блог і нотатки релізів.

Разом 15 332 документи з 3 935 тегів репозиторію; фрагментів в індексі — 60 882 (`expected_passages` у
`checks.json`). Фрагменти — це шматки документів між заголовками, по яких іде пошук; однаковий текст різних версій
зливається в один з усіма версіями.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 5 із 10, за
змістом 6, разом 7; друга, «як модель» (назви API, з `version: "16"`, як велить промпт), — 10 із 10. Час одного
запиту — 151 мс по словах і 24 мс за змістом. Що показали промахи:

- **Без версії та сама тема лежить під кількома адресами.** Сторінка про зображення за роки побувала в
  `docs/api-reference/next/image`, `docs/app/building-your-application/optimizing/images` і
  `docs/app/getting-started/images`; усі вони — правильна відповідь на питання без версії, тому цілями першої
  десятки є сторінки всіх версій. Із цілями лише поточної лінії було 1, 3 і 1.
- **Два промахи — не порожні.** На «назву й опис сторінки для пошуковиків» приходять глосарій (`Metadata`) і розділ
  «Metadata and SEO» з production-checklist, а не довідка `generateMetadata`; на розмите «малі порції даних, які
  браузер шле з кожним запитом» — Route Handlers, а не `cookies`. Обидва запити навмисне не називають API.
- **Друга десятка влучає щоразу**, бо `version: "16"` лишає одну редакцію кожної сторінки, а назва API стоїть у
  заголовку.

**Версія й роутер у відповіді.** Кожна відповідь каже, якої версії й котрого роутера вона стосується; без названої
версії — для поточної лінії 16, без названого роутера — для App Router (типовий для нових проєктів з 13.4). Текст,
знайдений лише в canary, beta чи rc, міг так і не вийти релізом — відповідь каже про це.

## Два роутери

З тегу v13.4.5 тека `docs/` поділена на `01-app/` і `02-pages/`, але сторінки Pages Router там здебільшого —
заглушки на кілька рядків із полем `source: app/…`: текст лежить у файлі App Router, а відмінності розмічені
блоками `<AppOnly>` і `<PagesOnly>`. Сайт збирає з цього дві різні сторінки. Читач `nextdocs-history` робить те
саме:

- для сторінки App Router лишає спільний текст і блоки `<AppOnly>`, блоки `<PagesOnly>` викидає;
- для заглушки Pages Router бере файл, на який вона вказує, і лишає спільний текст і блоки `<PagesOnly>`;
- назву документа починає з «App Router: » або «Pages Router: »;
- на спільних сторінках (поза `app/` і `pages/`) обидва блоки лишаються, кожен із підписом роутера.

Звірено із сайтом: на сторінці компонента `Image` заголовки обох варіантів збігаються з markdown-двійниками
nextjs.org — 57 із 57.

## Мітки версій і canary

Документ має мітку кожної версії, на тегу якої його текст був саме таким. Релізи й передрелізи (`-beta`, `-rc`,
`-preview`) — точна версія: `16.3.8`, `15.0.0-rc.1`. Фільтр `"16"` бере всю лінію, `"16.3"` — мінорну.

Canary — інакше: усі збірки одного циклу мають **одну мітку без номера** — `16.4.0-canary` для
`v16.4.0-canary.0 … v16.4.0-canary.55`. Із 3 935 тегів виходить 562 мітки. Причина — в сервері: з кожним уривком
він віддає повний перелік його версій, а canary виходить по кілька на тиждень; з окремою міткою на кожну незмінний
абзац ніс би тисячі версій, і відповідь пошуку не влізла б у ліміт клієнта. Текст кожної canary в корпусі є; її
точний номер, дата і зміни — у нотатках релізів і реєстрі npm.

Блог, шаблони й showcase міток версій не мають: з фільтром `version` їх не видно, шукати їх треба без нього.
Приклади мають мітку `16.3.8` — версію тегу, з якого знято теку `examples/`.

## Що в цій теці

- `corpus/` — документи звичайними текстовими файлами; поруч `index.json` — паспорт: адреса, дата завантаження й
  сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df nextjs <крок>`.

| Що | Джерело | Читач |
|----|---------|-------|
| документація й пояснення помилок | теки `docs/` і `errors/` vercel/next.js на кожному тегу | `nextdocs-history` |
| нотатки релізів | GitHub API | `ghreleases` |
| приклади | тека `examples/` на тегу v16.3.8 | `ghexamples` |
| README пакетів | тег релізу на GitHub | `npm-readme` |

| блог | sitemap nextjs.org, markdown-двійник кожного запису | `sitemap-md-meta` |
| шаблони | sitemap vercel.com, markdown-двійник кожної сторінки шаблону | `sitemap-md-meta` |
| showcase | сторінка nextjs.org/showcase | `html-list` |

Нових читачів два, обидва — окремі модулі, спільні читачі не чіпано:

- **`nextdocs-history`** (`engine/readers/nextdocs.py`) — історія теки документації на тегах, як `ghdocs-history`,
  плюс те, чого той не вміє: два роутери з одного файла (розділ вище), номери порядку в шляхах
  (`01-app/03-api-reference` → `app/api-reference`, інакше перенумерована тека стала б «новою» сторінкою), ім'я
  файла з огорожі коду (`filename="app/page.tsx"`) окремим рядком перед кодом, багаторядкові теги JSX із
  властивостями. Дерево тегу читається не цілим: корінь — на кожен тег, піддерево теки — раз на хеш; інакше обхід
  чотирьох тисяч тегів монорепозиторію тривав би добу.
- **`sitemap-md-meta`** (`engine/readers/mdmeta.py`) — сторінки, чия шапка YAML є частиною змісту: дата запису блогу
  (`publishedAt`) іде в назву, адреси репозиторію й демо шаблону — першими рядками тексту; спільний для всіх сторінок
  хвіст («Related Templates») відрізається.

Особливості, які варто знати:

- **Документація починається з 9.1.7.** Раніше теки `docs/` не було: для 1.0–9.1 документацією був README пакета
  `next`, тому він узятий на кожній версії тих ліній разом із canary. Пояснення помилок — із 5.x.
- **Теги до 7.0.3 — без `v`** (`7.0.2`, `6.1.2`); мітка версії від цього не залежить.
- **Нотатки релізів — усі, з canary**: 3 878 записів. Саме в них точний номер і зміни кожної canary.
- **Приклади — один знімок**, а не історія: тека `examples/` на v16.3.8, 233 приклади. Назва документа — «Example: …».
- **Шаблони — це код спільноти.** У галереї Vercel поруч стоять шаблони команди Next.js і сторонніх авторів; опис і
  README шаблону — не рекомендація документації, і промпт велить казати про це. Сторінка мітки блогу
  (`/blog/tag/…`) записом не є й пропускається полем `skip`.
- **Showcase — слабке джерело.** Перелік сайтів сторінка довантажує скриптом; у розмітці лишаються назви кількох
  компаній, категорії й рекламний текст — шість фрагментів.
- **Лише офіційне й лише англійською.**

## Межі, про які треба пам'ятати

Тут немає документації самого React (окремий примірник `react`), платформи Vercel (звідти лише галерея шаблонів),
Turborepo і Turbopack як окремих інструментів, бібліотек навколо (Auth.js, Prisma, SWR) та курсу nextjs.org/learn.
Issues і GitHub Discussions свідомо не взято: це рецепти окремих проблем, а не документація.

**Відома вада: питання про реєстр npm.** Оглядовий документ реєстру пакета `next` несе перелік усіх 3 968 версій, і
сервер віддає його з кожним уривком цього документа. Відповідь пошуку з таким уривком сягає 147 тисяч символів і
може не влізти в ліміт клієнта; звичайні запити по документації дають 4–18 тисяч. Обхід — питати про версії з
фільтром лінії (`version: "16"`) і меншим `k`. Виправлення — у спільному коді (читач `npm-versions` або сервер), і
воно чекає окремого рішення.

## Установка venv

```
cd instances/nextjs
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt

```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df nextjs sources --why   # перелік джерел і білий список
./df nextjs refresh         # завантажити все задеклароване (~8 годин)
./df nextjs manifest        # оновити паспорт
./df nextjs setup           # Qdrant чи пошук лише по словах
./df nextjs vectors         # залити корпус у docs-nextjs (~2,5 години)
./df nextjs smoke           # перевірки
```

`refresh` найдовший у фабриці: джерело `next-docs` спершу три з половиною години обходить дерева 3 935 тегів (у лозі
— рядок «пройдено N із M тегів» кожні 250) і лише потім чотири з половиною години пише 10 386 документів. Решта
джерел разом — близько двох годин, тому їх варто пускати другим процесом:

```
./df nextjs refresh --missing next-docs
./df nextjs refresh --missing next-releases next-examples readme-next npm-next next-blog next-templates   # і решта id
```

Із Claude Code довгі кроки треба запускати окремим процесом (`setsid nohup …`), інакше фонову задачу обірве оболонка.
Обірваний `refresh` продовжується з `--missing`: уже записане він не тягне вдруге, але обхід тегів `next-docs`
повторює. Імена джерел без `--missing` прогін не звужують.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df nextjs serve           # порт 8779
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8779/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user nextjs-docs http://127.0.0.1:8779/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `nextjs-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Досить отримати репозиторій зі свіжими комітами (`git clone` або `git pull` після того, як їх

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
