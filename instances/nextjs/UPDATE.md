# Оновлення корпусу nextjs

Три різні роботи: звичайне оновлення (вийшли нові релізи й canary), новий знімок прикладів і новий пакет поруч.
Порядок усередині кожної важливіший за самі команди.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `refresh` і `manifest`
працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять знову; обидві
дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

Головне правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Сторінка, що зникла з документації, шаблон, прибраний з галереї, чи версія, прибрана з реєстру, лишається в
`corpus/`; прибрати — рішення людини.

## 1. Звичайне оновлення

**Крок 1. Нові теги.** Документація й пояснення помилок беруться з тегів, перелічених у полі `tags` джерела
`next-docs` у `sources.json` («тег → версія», від найновішого). Новий реліз — новий рядок нагорі цього поля:
`"v16.4.0": "16.4.0"`. Передрелізи (`-beta`, `-rc`, `-preview`) — так само, з точною версією.

Canary — інакше: усі збірки одного циклу мають **одну мітку без номера**, `"v16.5.0-canary.3": "16.5.0-canary"`.
Причина — в сервері: з кожним уривком він віддає повний перелік його версій, а canary виходить по кілька на
тиждень; з окремою міткою на кожну незмінний абзац ніс би тисячі версій, і одна відповідь пошуку не влізла б у
ліміт клієнта. Текст кожної canary в корпусі є; її точний номер, дата і зміни — у нотатках релізів і реєстрі npm.

Нотатки релізів, README, реєстр npm, блог і шаблони нове підхоплюють самі.

**Крок 2. Завантаження й решта.**

```
./df nextjs sources --why
./df nextjs refresh --missing     # лише нове
./df nextjs manifest
./df nextjs vectors
./df nextjs smoke
# Ctrl+C у терміналі з serve, і знову: ./df nextjs serve
```

`--missing` докачує документи, яких ще немає, і не чіпає наявних. Але перелік джерела `next-docs` складається
обходом усіх тегів — це кілька годин навіть тоді, коли нових документів десяток: на кожен тег читається корінь
дерева, а піддерево теки — раз на хеш. Тому `refresh` варто запускати двома процесами, які одне одному не заважають:

```
./df nextjs refresh --missing next-docs
./df nextjs refresh --missing next-releases readme-next npm-next next-blog next-templates   # і решта id
```

Повний `refresh` (без `--missing`) потрібен, коли змінився перелік версій уже наявного тексту: документ пам'ятає
всі версії, де текст був таким, і з новим тегом цей перелік росте. З Claude Code довгі кроки запускати окремим
процесом (`setsid nohup …`), інакше оболонка обірве їх через 30 хвилин; поступ `next-docs` видно в лозі рядком
«пройдено N із M тегів».

Корпус комітити логічними частинами до ~700 файлів: документація — порціями, нотатки релізів — порціями, приклади,
README, реєстр npm, блог, шаблони.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Новий знімок прикладів

Приклади (`next-examples`) — один знімок теки `examples/` на тегу релізу: у `url` і `version` джерела стоїть
`v16.3.8`. З новою мажорною версією — новий тег у `url`, нова версія у `version`, і `./df nextjs refresh
next-examples` (без `--missing`: наявні документи мають оновитися). Приклад, прибраний з репозиторію, лишається в
`corpus/` зі старою версією.

## 3. Новий пакет поруч із next

Беруться лише пакети з `packages/` репозиторію vercel/next.js. Джерел два:

**README** — `npm-readme` за зразком `readme-mdx`: опис пакета в реєстрі, шаблон адреси README з `{ref}` (коміт
публікації або тег `v{version}`), `skip_versions` з `-canary`. README береться, лише якщо він є документацією для
користувача пакета, а не нотатками для розробників Next.js (так не взято `@next/swc`).

**Реєстр** — `npm-versions` за зразком `npm-mdx`.

Потім `refresh --missing`, `manifest`, `vectors`, `smoke`, як у розділі 1, рядок у таблиці пакетів README і назва
пакета в `prompts/search.txt` та `prompts/loaded.txt`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df nextjs quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія:** Next.js 16. `prompts/search.txt` (абзац «Which version to search first») і `prompts/agent.txt`
  велять шукати з нею; нова мажорна версія — правка цих двох абзаців і `quality_model` у `checks.json`.
- **Правила промпту, що вже є:** запит — назвами API англійською і з назвою роутера; без версії — історія,
  міграції, сумісність, блог і шаблони (вони версії не мають); canary — мітка циклу; кожна відповідь каже роутер і
  версію; без названого роутера — App Router; код шаблону спільноти — не рекомендація документації.
- **Останній результат:** у README, абзац «Замір `quality`».
