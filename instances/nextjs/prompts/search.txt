Search the official documentation of Next.js -- every released version: the docs folder of
vercel/next.js (nextjs.org/docs: App Router and Pages Router -- getting started, guides, the
API reference of components, functions, file conventions, directives, next.config.js options
and the CLI --, architecture and community; and, before 13.4, the single documentation of the
Pages era: basic features, routing, API routes, API reference, advanced features, migrating)
on every tag from 9.1.7 to 16.x, including canary, beta, rc and preview builds; the error
explanations (nextjs.org/docs/messages) from 5.x; the README of every version of the `next`
package -- for 1.0 to 9.1 the README was the whole documentation -- and of create-next-app,
@next/mdx, @next/bundle-analyzer, @next/third-parties, @next/font, @next/codemod,
@next/playwright, @next/routing and next-rspack; the GitHub release notes of every release
and every canary build; the npm registry list of every published version of these packages
and of @next/env, @next/eslint-plugin-next, @next/plugin-storybook and eslint-config-next
(date, dist-tag, dependencies and peer dependencies); the nextjs.org blog
(release announcements, with dates); the official examples of the repository (the examples
folder at 16.3.8: README and code, file by file); the Next.js templates of the Vercel gallery
(description, README, repository, demo) and the showcase page; and return the matching
excerpts with the versions each one belongs to.

Call this when a question is about Next.js -- the App Router (layouts, pages, routing, route
handlers, Server and Client Components, data fetching, caching and revalidation, `use cache`,
Server Actions, metadata, proxy and middleware, error and loading files, parallel and
intercepting routes), the Pages Router (getStaticProps, getServerSideProps, getStaticPaths,
API routes, _app, _document), next/image, next/link, next/font, next/script, next.config.js,
Turbopack, environment variables, internationalization, deploying and self-hosting, an error
message of Next.js ("why this error occurred"), a starter template -- and above all when it is
about versions: since which version something exists, what changed between versions, how to
migrate (Pages Router to App Router, 12 to 13 to 14 to 15 to 16, the codemods), and which
versions of Next.js, React, Node and TypeScript work together -- the peer dependencies of
each version answer that. Example query: "generateMetadata app router".

Do not call this for React itself, for the Vercel platform (its documentation is not here,
only the template gallery), for Turborepo, for authentication and data libraries (Auth.js,
Prisma, SWR), or for other frameworks (Remix, Astro, Nuxt): their documentation is not here,
and the search will return Next.js excerpts that merely mention them, with confident-looking
titles.

Two routers. Since 13.4 every page of the documentation exists twice: titles begin with
"App Router:" or "Pages Router:", and the two texts differ in code and in advice. Say the
router in the query ("app router", "pages router"). When the user did not say which one the
project uses, answer for the App Router -- the default for new projects since 13.4 -- and say
so; a project with a `pages/` directory and getServerSideProps is on the Pages Router. Before
13.4 there is one documentation, without a prefix, and it describes what is now the Pages
Router.

`version` narrows the search to one release line: "16" keeps Next.js 16.x, "15.3" keeps
15.3.x. All packages of the repository are released together and share the numbers. Canary
builds of one cycle share one label -- "16.1.0-canary" stands for every 16.1.0-canary.N --
so the documentation of a canary is found under its cycle; the exact canary number, its date
and its changes are in the release notes and in the registry documents. The blog, the
templates and the showcase carry no version: a search with `version` never returns them, so
search them without it. Leave `version` empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first -- text
that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lives. Documents are named by their path in the repository without
the ordering numbers: docs/app/getting-started/..., docs/app/guides/...,
docs/app/api-reference/functions/generate-metadata, docs/pages/api-reference/...,
errors/<name>. From 9.1 to 13.4 the paths are docs/basic-features/...,
docs/api-reference/next/image, docs/api-routes/..., docs/advanced-features/...,
docs/migrating/.... Before 9.1 the README is the documentation (titles "next README").
Upgrade guides are docs/app/guides/upgrading/... (earlier
docs/app/building-your-application/upgrading/..., docs/upgrading). Release notes are titled
"Next.js release", blog posts "Blog: ... (date)", templates "Template: ...", examples
"Example: with-..." -- an example is one document, each file of it a section named by its
path, and it carries the version 16.3.8 only.

Which version to search first. For a question about how to do something today, pass the
current line -- "16" -- or the line of the user's project: without it, the many editions of
the same page, which differ by a line or two, fill every place with older text. Search without
`version` for history, for migrations, for compatibility, for the blog and for templates.

For a question about when something appeared, changed or disappeared, search more than
once: the blog announcements, the release notes and the upgrade guides name the exact
version; then search the lines before and after it to see how the documentation described it.
For a question about which versions work together, read the peer dependencies in the registry
document of the package.

Write the query in English, with the names the documentation uses (generateMetadata,
revalidatePath, use cache, getServerSideProps, next.config.js, route handlers, middleware).
Everything here is English -- the excerpts, the word index and the meaning index alike -- and
the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian
or any other non-latin script matches nothing at all and comes back with `found: 0`. When the
user asks in another language, translate the question into Next.js terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which router and which version it is for. When the user did not name a
version, answer for the most downloaded line of `next` on npm and say so; when two lines are
both in wide use, give both. When the excerpts behind a statement come only from older
versions, name those versions instead of presenting the text as current. A text found only in
canary, beta, rc or preview builds may never have shipped in a release: say so. A template
from the gallery may be written by the community and for an older Next.js: say whose it is
when the page says so, and do not present its code as the documented way.

Answer in the language the user wrote in. When the question is about a feature's history,
a migration or compatibility, answer point by point: which router and since which version;
what changed in later versions; what the migration requires; and how it stands now. Every
point names the version and the document it rests on; a point the excerpts do not support is
left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes,
not as a translation from English: plain technical prose, and the Ukrainian word wherever one
exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація Next.js". Identifiers, option names and titles stay
in English, spelled exactly as the documentation spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
