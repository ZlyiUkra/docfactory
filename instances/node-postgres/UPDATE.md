# Оновлення корпусу node-postgres

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи pg чи його пакетів, і збирання з нуля. Порядок усередині
кожної важливіший за самі команди.

Головне правило: **перелік версій бере реєстр npm.** Тут немає поля `tags`, яке треба дописувати руками: сайт
(`np-site`) робить знімок на кожну стабільну версію pg з реєстру, README (`np-readme-*`) — на кожну стабільну версію
свого пакета, типи (`np-types-pg`) — на кожну версію `@types/pg`. Новий реліз потрапляє в корпус сам, щойно джерело
перечитано. Білий список від цього не слабшає: тягнуться лише адреси з полів `within`.

Друге правило: **нова версія змінює й старі документи.** Документ — неповторний текст сторінки, а в рядку `# версія:`
стоять усі версії, де сторінка була саме такою. Тож після нових релізів джерела перезаписуються цілком (`refresh`),
а не докачуються (`--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version`
їх не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Перевірити, чи не переїхала документація.** Сайт зараз будується з теки `docs/pages/` монорепозиторію
`brianc/node-postgres` — друга епоха джерела `np-site`. Якщо сайт перейшов на інший рушій чи теку, у джерело
додається нова епоха з полем `before` у попередньої (так зроблено з `node-postgres-docs` → `docs/pages/`), а в
`config.json` — правило `slug_rewrite`, що зводить нові шляхи сторінок до тих самих імен.

**Крок 2. Новий пакет монорепозиторію** (теки `packages/*`) — додати `np-readme-<пакет>` і `np-npm-<пакет>` за
зразком сусідніх. Журнал змін спільний, його читач бере новий пакет сам.

**Крок 3. Завантажити.**

```
./df node-postgres sources --why
./df node-postgres refresh
./df node-postgres manifest
./df node-postgres vectors
./df node-postgres smoke
# Ctrl+C у терміналі з serve, і знову: ./df node-postgres serve
```

`refresh` без назв — повне перезавантаження: спершу перелік комітів обох репозиторіїв сайту, дерева знімків і README
кожної версії кожного пакета, далі файли. Корпус не комітиться: після оновлення пишуть новий архів і знову виносять
тексти (README, розділ «Архівний режим»), а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік комітів і дерев іде годинними
вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df node-postgres refresh > instances/node-postgres/out/refresh.log 2>&1 &
```

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df node-postgres quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка
промпту, знову замір. Що це означає тут:

- **Поточна лінія — pg 8.** Коли вийде pg 9, у `prompts/search.txt` (абзац «Which version to search first») і
  `prompts/agent.txt` замінити "8" на нову лінію, а в `checks.json`, у десятці `quality_model`, — версію тих записів,
  що питають про поточну поведінку.
- **Правила промпту, що вже є:** спершу лінія 8; запит — назвою класу, методу чи опції, а не описом; для «як
  зробити» — шукати й сторінку можливостей чи посібник; супутні пакети мають власні номери; кожна відповідь каже,
  для якої версії вона.
- **Останній результат** — у README, абзац «Замір `quality`».
