Search the official node-postgres documentation -- the pg package for Node.js and its companions,
every stable version of them -- and return the matching excerpts with the versions each one belongs
to. Here are the node-postgres.com site as it stood at every stable release of pg since 2019, the
README of every stable release of pg, pg-pool, pg-cursor, pg-query-stream, pg-connection-string,
pg-native, pg-protocol, pg-types, pg-copy-streams and pg-format, the changelog of the monorepo, the
FAQ and Extras pages of the GitHub wiki, the @types/pg type definitions from DefinitelyTyped and the
npm registry history of all eleven packages.

Call this when a question is about using PostgreSQL from Node.js with node-postgres -- Client and
Pool and their options (connectionString, host, port, user, password, database, ssl, max,
idleTimeoutMillis, connectionTimeoutMillis, statement_timeout, query_timeout, application_name),
client.connect and client.end, pool.query, pool.connect and client.release, events (error, connect,
acquire, remove, notification, notice), queries with parameters, prepared statements, row mode,
query config objects, Result (rows, fields, rowCount, command), transactions, type parsing
(types.setTypeParser, pg-types), SSL, the native bindings (pg-native), cursors (pg-cursor),
streaming results (pg-query-stream), COPY streams (pg-copy-streams), connection strings
(pg-connection-string), escaping identifiers and literals (escapeIdentifier, escapeLiteral,
pg-format), ESM, pipelining, the TypeScript types of @types/pg, an upgrade between major versions --
and above all when it is about history: since which version something exists, what changed between
versions, what was renamed or removed and what replaced it. Example query: "pool.query
idleTimeoutMillis".

Do not call this for PostgreSQL itself (SQL syntax, indexes, server settings, replication), for
Node.js, or for ORMs and query builders built on top of pg (Prisma, TypeORM, Knex, Drizzle,
Sequelize): their documentation is not here, and the search will return node-postgres excerpts
that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "8" keeps every 8.x document, "7" every 7.x,
"8.11" keeps 8.11.x; leave it empty to search everything. Every excerpt comes back with `versions`:
each version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which to
which version the documentation said exactly this. The site pages carry the versions of pg. The
companion packages number their releases on their own (pg-pool 3.x, pg-cursor 2.x,
pg-query-stream 4.x, pg-connection-string 2.x, pg-native 3.x, pg-protocol 1.x, pg-types 2.x and
4.x, pg-copy-streams 7.x, pg-format 1.x, @types/pg 8.x): their README, changelog entries and type
documents carry that package's own version, so a `version` filter keeps them too when the number
matches, and drops them when it does not.

Where the documentation lived. Until mid-2019 the documentation of pg was a GitHub wiki whose API
pages no longer exist; for pg 7.10 and earlier there are only the README and the changelog. From
July 2019 to October 2022 the site was built from the separate repository node-postgres-docs (pages
like "content/api/1-pool"), and since then from docs/pages/ of the monorepo ("apis/pool",
"features/queries", "guides/upgrading"); the same page in both places is one document with the
versions of both. The changelog lists only major and minor releases, with headings like
"pg@8.11.0" or "pg-pool@3.0.0"; entries from before the monorepo are pg ("v6.2.0"). The upgrade
guide ("guides/upgrading") and the announcements page describe what changed in pg 8 and 7.

Which version to search first. For a question about how to do something today, pass `version`
"8": pg 8.x is what almost every project runs. If the user's project still runs an older pg, pass
its line instead. Search without `version` when the question is about history or about a
companion package whose number differs from pg's, or when the line gave nothing that answers.

Name the class, method or option the way the documentation titles it, not in the user's own words:
"pool.query", "client.release", "idleTimeoutMillis", "connectionTimeoutMillis",
"types.setTypeParser", "ssl rejectUnauthorized", "QueryStream", "copyFrom", not "close idle
connections after a while". When the question is how to do something, a feature page or a guide
often shows it better than the API page: search for it as well ("transactions", "pool sizing",
"async express").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the changelog entry and the README that name the exact version,
then with the versions around it, to see how the documentation described it before and after.

Write the query in English, with the names node-postgres itself uses. Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate
the question into node-postgres terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses may
miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase had a
chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, pg 8.x, say so in the answer ("for node-postgres 8.x"), and add that for a precise
answer about another version the user can name it. When the excerpts behind a statement come only
from older versions, name those versions instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація node-postgres". Identifiers, API names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it
says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
