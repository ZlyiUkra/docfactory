Search the node-redis documentation, in English: node-redis is the official Redis client for Node.js (the npm
package `redis` with `@redis/client`, `@redis/json`, `@redis/search`, `@redis/time-series`, `@redis/bloom`,
`@redis/entraid`) -- createClient and its options, the command methods with typed arguments and replies,
multi/exec transactions and WATCH, pipelining, pub/sub, SCAN iterators, cluster and Sentinel clients, the
connection pool, RESP2 and RESP3, client-side caching, Lua scripts and functions, Entra ID authentication,
OpenTelemetry metrics. The set holds, for every stable release from 0.3.5 to 6.3.0: the README (in 0.x-3.x the
whole API reference), the guides in docs/ (client configuration, clustering, Sentinel, pub/sub, transactions,
pool, scan iterators, programmability, client-side caching, RESP, FAQ, the migration guides v3 to v4, v4 to v5,
v5 to v6), the changelog, SUPPORTED_REDIS_VERSIONS, the examples and doctests, the source code of the client
(one file per command with its argument and reply types, the client, socket, cluster, Sentinel, pool, pub/sub,
multi -- for 4.x to 6.x the API reference is this code), the source of the modules json, search, time-series,
bloom, graph and entraid, the tests of the last release of each minor line, the GitHub release notes, the
README of every package from npm (also the old @node-redis/* names) and the community typings @types/redis for
redis 2 and 3. Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about node-redis: how to connect (createClient, url, socket options, TLS,
reconnectStrategy, username and password, database), what a command method is called and what it returns
(client.hSet, client.sendCommand, HGETALL reply shape), how multi/exec, WATCH, pipelining, pub/sub (subscribe,
pSubscribe, sSubscribe), scanIterator, the cluster client (createCluster, nodeAddressMap), Sentinel, the pool
or RESP3 work, what an error means (ClientClosedError, DisconnectsClientError, WatchError), what changed
between versions (3 to 4, 4 to 5, 5 to 6, legacyMode), how the JSON, search, time series or bloom modules are
called. Example query: "createClient".

Do not call this for the Redis server itself (commands, redis.conf, persistence, replication: the redis
instance), for ioredis (its own instance), for BullMQ or other queue libraries, or for frameworks that wrap
node-redis beyond what the node-redis documents say.

Write the query in English, with the names node-redis uses (createClient, reconnectStrategy, sendCommand,
scanIterator, legacyMode, RESP, pSubscribe, createCluster). Everything here is English, and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing and comes back with `found: 0`. When the user asks in another language, translate the
question into node-redis terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий"; "підключення", "опція", "подія".
Never call this set of documents "корпус" -- say "документація node-redis". Option, method, event and class
names stay in English, spelled exactly as the documentation spells them. Build the answer out of the excerpts
that came back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. When the user names a version, search that line; otherwise answer for the newest
release and say so. Put a version only into `version`, never into the query text: "4" keeps every 4.x, "4.7"
keeps 4.7.x, "5.1.0" one release. Every document carries the releases of `redis` in which it was exactly so;
the versions of @redis/client 1.x correspond to redis 4.x. The README is "readme", a guide is named after its
file ("docs-clustering", "docs-v4-to-v5"), the changelog "changelog"; the source is named by its path
("src-packages-client-lib-client-index-ts", "src-packages-client-lib-commands-hset-ts").
