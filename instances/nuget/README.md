# nuget — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про NuGet, менеджер пакетів .NET: клієнтські інструменти (`nuget.exe`,
`dotnet nuget`, відновлення й пакування через `dotnet`, вікна пакетів у Visual Studio), `PackageReference` і
`packages.config`, `nuget.config` і джерела пакетів (зіставлення джерел, облікові дані, підпис і довірені
підписувачі), централізоване керування версіями, блокування версій і аудит, діапазони версій і цільові платформи,
створення й публікацію пакетів (`.nuspec`, властивості пакування MSBuild, nuget.org), помилки й попередження `NU…`,
протокол сервера V3 (Server API) і клієнтські бібліотеки `NuGet.*`. Документація англійською: сторінки
learn.microsoft.com/nuget з репозиторію документації, README і `docs/` репозиторію NuGet.Client на кожному стабільному
випуску 4.0.0–7.9.0, його код і тести на останньому випуску кожної мажорної лінії, специфікації дизайну NuGet/Home,
документація й релізи NuGetGallery, 52 пакети власника `nuget` на nuget.org з кожною стабільною версією та довідник
API з XML-документації цих пакетів для кожної мінорної лінії. Код спільний і лежить у `../../engine/`, `../../server/`
та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

Менеджер пакетів .NET не описує жоден інший примірник: `dotnet` знає про нього лише як про команди `dotnet restore`,
`dotnet pack` і `dotnet nuget`, `aspnetcore`, `entityframework`, `testcontainers-dotnet` і `dotnet-testing` — як про
пакети своїх бібліотек. Формат пакета, `nuget.config`, зіставлення джерел, `Directory.Packages.props`,
`packages.lock.json`, NuGet Audit, протокол V3 і бібліотеки, на яких стоять `dotnet restore` та Visual Studio, лежать
тут. Звернувшись до цього примірника з версією, дістаєш усе для відповіді саме на ній: нотатки випуску, тип і член API
тієї лінії, пакет із залежностями, код і тест випуску й специфікацію, з якої функція починалась.

## Що в цій теці

- `corpus/` — паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа. Самих текстів тут
  немає: корпус в архіві.
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`.
- `sources.json` — звідки корпус будується (60 джерел), і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, профіль домену, родини джерел-версій (`families`:
  `client-api` — 28 ліній довідника клієнтських бібліотек, `vs-api` — 20 ліній NuGet.VisualStudio), `fusion_depth: 40`
  і `max_per_doc: 3`.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — токен GitHub і, для кроку `ask`, ключ Anthropic; `.mcp.json` — запис HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики через `./df nuget <крок>`.

Особливості:

- **Версії**: клієнт, його бібліотеки й репозиторій нумеруються разом, тож версія — випуск NuGet (`7.9.0`, `6.14.3`),

  нумеровані датою), `packagesourcemapper-1.0` і `verifymicrosoftpackage-1.0`.
- **Сайт без тегів.** Репозиторій документації тегів не має, тож його сторінки взято в чинному стані; лише нотатки
  випусків дістали версію. Фільтр старої лінії сторінки посібників ховає, тож промпт велить шукати і з версією, і без
  неї.
- **Версія за замовчуванням** — найпопулярніша за завантаженнями на nuget.org: клієнт `nuget.exe` (NuGet.CommandLine)
  7.6.0 (61,6 млн), далі 7.3.0 (45,6 млн) і 7.9.0 (41,2 млн); бібліотеки NuGet.Packaging і NuGet.Protocol — 6.11.0
  (27,5 і 27,3 млн). 7.9.0 — найновіший стабільний випуск, і промпт каже, чим він відрізняється, але за замовчуванням
  не є.
- **Коміт випуску NuGet.Client.** Теги збірок чотиричленні (`7.9.0.83`), і найвищий не завжди є випуском (з 56
  звірених версій 11 розійшлися). Коміт випуску — поле `repository commit` у nuspec пакета NuGet.Packaging цього
  випуску (NuGet.Commands, NuGet.CommandLine); для 5.7.2 і 6.0.2 його немає в публічному репозиторії, для 4.0–5.10
  nuspec його не несе — там тег збірки (4.0.0, 4.1.0, 4.2.0 — `-rtm-…`). Версії, випущені з одного коміту, ділять ключ
  у `tags`.
- **Довідник API** — з найновішої версії кожної мінорної лінії, без таблиць ресурсів (`Strings`, `Resources`,
  `NuGetResources`, `AnalysisResources`, `SR` — 395 документів) і без вкомпільованих `System.*`, `Microsoft.*`,
  `JetBrains.*`. Пакети NuGet.* 6.5–6.11 і NuGet.VisualStudio 17.5–17.11 вийшли без XML-документації: довідника цих
  ліній немає, і промпт велить відповідати про їхні типи за 6.4 чи 6.12. Пакети без XML зовсім (NuGet.Core,
  NuGet.Server, NuGet.Build, NuGet.Bootstrapper, NuGet.Localization, NuGet.Mcp.Server…) довідника не дають, але мають
  огляд, лінії й README.
- **Пакети власника `nuget`.** Перелік дає пошук `owner:nuget` на nuget.org: 54 пакети, з них 52 взято;
  `PoliteCaptcha` і `NuGet.Services.Build` — інших продуктів, їх не взято. П'ять платформних пакетів
  `NuGet.Mcp.Server.<rid>` узято (вони майже дублюють опис головного).
- **Код і тести** — на останньому випуску кожного мажору (4.9.7, 5.11.7, 6.14.3, 7.9.0); незмінний член сусідніх
  мажорів — один фрагмент. Сторінки `src/**/README.md` не беруться: README пакетів вже в `nuget-package`.
- **Скан кешу фрагментів** не знаходить жодного ключа розділу, спільного для джерел різних родин. Спершу знайшов два:
  README Gallery і `mcp/README.md` Home називались однаково (`readme`). `ghdocs` не має `name_prefix`, тому обидва
  файли взято через `ghdocs-history` з порожньою версією в `tags` і власним `name_prefix`.
- **Дотюнінг якості.** Перший замір — «як модель» 8 із 10, своїми словами 1. Замір одним процесом із завантаженим
  індексом показав: `FrameworkReducer.GetNearest` у довіднику API — 33-й і по словах, і за змістом, а перед ним понад
  тридцять методів тестового класу `FrameworkReducerTests`; `demote` нічого не міняє, бо переставляє лише в межах
  глибини `k`×6 = 30. `fusion_depth: 40` впускає сторінку в список, `max_per_doc: 3` не дає одному файлові тестів
  зайняти всі місця — разом 10 із 10 без `demote`. Ціль `VersionRange.Satisfies` виявилась лише в редакції 1.0.7
  (`SimpleVersion`): члени пізніших ліній коментарів не мають і документами не стали — ціль замінено на
  `VersionRange.Parse`, що є в 7.9.0. Половину запитів своїми словами переписано словами документації, без назв API
  (так велить схема заміру), і до двох цілей додано специфікації Home, що описують ту саму функцію (централізоване
  керування версіями, зіставлення джерел).
- **Запити `quality`** записано так, як їх ставить людина своїми словами. Промахи своїми словами (по всіх трьох
  стовпцях): централізоване керування версіями (знаходяться сторінки про цільові платформи, `project.json` і Visual
  Studio), «з якого випуску відновлення саме відкидає пакети, що вже є в цільовій платформі» (знаходяться сторінки про
  розв'язання залежностей, помилки `NU51xx` і нотатки інших випусків) і залежності NuGet.Protocol 6.11 (знаходяться
  специфікації про .NET Framework й пакування, а не документ лінії пакета); назвами документації знаходяться всі три.

## Межі, про які треба пам'ятати

- Усе англійською.
- Лише стабільні випуски: передрелізи NuGet, нотатки передрелізів і NuGet.Client до 4.0 (теги 3.x, `-VSIX`,
  `3.5.0-rtm`) не взято. Документація learn.microsoft.com — у стані на 15.10.2026 (нотатки 7.10 вже є, а 7.10 на
  nuget.org ще немає).
- Не взято нічого поза трьома групами: блог NuGet, документацію Visual Studio про NuGet, інші репозиторії NuGet
  (NuGet.Jobs, NuGet.Services.*, NuGet.Insights тощо), політики nuget.org поза тими, що лежать у репозиторії
  документації (`docs/nuget-org/policies/`, `docs/policies/` — їх узято), `CONTRIBUTING.md`, `SECURITY.md` і
  `.agents/skills` NuGet.Client, `meta/` і політики NuGet/Home (Privacy-Policy, Terms-Of-Use, Issue-Triage-Policy).
- Із пакетів власника `nuget` не взято `PoliteCaptcha` (бібліотека CAPTCHA, не NuGet) і `NuGet.Services.Build` (збірка
  внутрішніх сервісів nuget.org); взято всі п'ять `NuGet.Mcp.Server.<rid>`.
- Сім записів релізів GitHub (NuGet.Client — 2, NuGet/Home — 5, 2015–2016 роки, VS 2013/2015) майже порожні: тег, дата
  й посилання на нотатки. Їх лишено, бо релізи входять до обсягу.
- Документацію NuGetGallery (8 файлів про Azure Search, листи, фронтенд, розгортання) і 41 реліз розгортань nuget.org
  взято, хоч вони про сервіс, а не про клієнт NuGet.
- Довідник API з XML не перелічує успадкованих членів і не має прикладів, яких немає в самому XML; для 6.5–6.11 його
  немає зовсім.

## Родина .NET: піднімати разом

Цей примірник — частина родини .NET: платформа, мова, веб, дані, тестування й менеджер пакетів Microsoft. Питання про
C# впирається в бібліотеку класів, про EF — у SQL Server, про тест із базою — у Testcontainers, про пакет — у NuGet.
Тому примірники родини піднімають у Claude Code разом, а `.mcp.json` цієї теки перелічує всі вісім серверів:
підключивши будь-який із них, Claude Code бачить решту.

розділі «Родини примірників» кореневого [README](../../README.md).

## Архівний режим: сервер без корпусу

Корпус в архіві від самого початку: у `corpus/` лежить лише паспорт, а сервер підіймається з кешу фрагментів і
колекції Qdrant; відповіді ті самі до символа.

**Де тексти.** В архіві `~/archives/docfactory/nuget-corpus-2026-10-19.tar.gz` (160 МБ; 30 366 текстів, паспорт і
сховище сирого `raw/`, 43 134 файли; перед видаленням розпакований окремо й звірений з диском `diff -r` — нуль
розбіжностей). Лише на цій машині.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:


## Установка venv

Власний venv цьому примірнику не потрібен: `./df nuget …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище». Свій `.env` примірник тримає в `instances/nuget/.env` (`cp .env.example .env`;
для кроку `ask` потрібен `ANTHROPIC_API_KEY`); `GITHUB_TOKEN`, якого немає в цьому `.env`, береться з кореневого.

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають. Для роботи сервера збирати нічого не треба
— потрібен лише `vectors`, якщо колекції ще немає.

```
./df nuget sources --why   # перелік джерел і білий список
./df nuget refresh         # завантажити задеклароване (код — краще з клона, див. вище)
./df nuget manifest        # оновити паспорт
./df nuget setup           # Qdrant чи пошук лише по словах
./df nuget vectors         # залити корпус у docs-nuget (близько двох хвилин на відеокарті)
./df nuget smoke           # перевірки
```

Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df nuget serve          # порт 8869
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8869/mcp`; індекс по словах
збирається з кешу кілька десятків секунд. Якщо порт зайнятий, сервер скаже про це й вийде: значить, `serve` цього
примірника вже десь запущений; хто тримає порт, покаже `ss -ltnp | grep 8869`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user nuget-docs http://127.0.0.1:8869/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Можна й не реєструвати глобально: `.mcp.json` цієї теки вже містить запис
сервера для сесії, відкритої тут.

**3. Перевірити.** `/mcp` — має бути `nuget-docs` і два інструменти `search_docs`, `read_section`. Якщо `/mcp` показує
`failed`, сервер не запущено або запущено з іншим портом.

Зупинка — Ctrl+C у терміналі сервера.
