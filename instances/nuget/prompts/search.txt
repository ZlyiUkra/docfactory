Search the documentation of NuGet, the package manager of .NET, in English: the client tools (nuget.exe, `dotnet
nuget`, `dotnet restore`/`dotnet pack`/`dotnet add package`, the Package Manager UI and Console in Visual Studio),
package references (PackageReference, packages.config, PackageDownload, the lock file packages.lock.json,
project.assets.json), nuget.config and package sources (credentials, package source mapping, audit sources,
signing and trusted signers), Central Package Management (Directory.Packages.props), NuGet Audit and the
vulnerability warnings, restore and dependency resolution, package versioning and version ranges, target
frameworks, authoring packages (the .nuspec, the MSBuild pack properties, symbol packages, signing), the
NU-numbered errors and warnings, publishing to nuget.org (API keys, trusted publishing, deprecation, ID prefix
reservation), the server protocol of NuGet V3 (service index, search, autocomplete, registrations, package base
address, publish, catalog, vulnerability info), and the NuGet client libraries (NuGet.Versioning,
NuGet.Frameworks, NuGet.Packaging, NuGet.Protocol, NuGet.Configuration, NuGet.Common, NuGet.ProjectModel,
NuGet.Commands, NuGet.Resolver, NuGet.CommandLine, NuGet.Build.Tasks and the rest of the packages the NuGet
team owns on nuget.org). The set holds: every page of learn.microsoft.com/nuget as of 15 October 2026 (guides,
reference, concepts, the Server API section, nuget.org, the FAQ, the release notes of the client from 1.1 to
7.10); the README and docs/ of the NuGet.Client repository at every stable release 4.0.0-7.9.0, and its source
code and tests (split into types and members) at the last release of every major line (4.9.7, 5.11.7, 6.14.3,
7.9.0); the design specifications of the NuGet/Home repository (accepted and implemented, with the MCP server
README); the README, docs/ and release notes of NuGetGallery, the code of nuget.org; the 52 NuGet packages owned
by the NuGet team with every stable version, its date, dependencies and README; and the API reference from the XML
documentation of those packages for the newest release of every minor line that shipped it. Returns the matching
excerpts with the versions each one belongs to.

Call this when a question is about using or building on NuGet: how to install, restore, update, pack, push, sign
or audit packages; what a setting means (ManagePackageVersionsCentrally, RestorePackagesWithLockFile,
RestoreLockedMode, NuGetAudit, NuGetAuditMode, packageSourceMapping, trustedSigners, PackageVersion,
VersionOverride, PrivateAssets, IncludeAssets, PackageReadmeFile, PackageLicenseExpression); what an error or
warning means and how to fix it (NU1100, NU1101, NU1103, NU1202, NU1605, NU1608, NU1701, NU1903, NU5100); how
NuGet picks a version or a target framework (floating versions, lowest applicable version, nearest framework,
fallback frameworks); which HTTP request a V3 feed answers (PackageBaseAddress, RegistrationsBaseUrl,
SearchQueryService, PackagePublish); what a type or member of the client libraries does, with its parameters,
return value and exceptions (NuGetVersion, VersionRange, NuGetFramework, FrameworkReducer, PackageArchiveReader,
PackageBuilder, SourceRepository, PackageSource, Settings, LockFileFormat, PackageSpec); how the client is built
(restore, project types, the plugin protocol, the credential providers); what a design specification proposed;
which NuGet package and version to reference; what changed between releases of NuGet.
Example query: "PackageReference Include Version".

Do not call this for other parts of .NET or other tools -- the C# language, the base class library, ASP.NET
Core, MSBuild beyond the NuGet properties and targets, the dotnet CLI beyond its restore, pack, push and nuget
commands, Visual Studio beyond its NuGet windows, other package managers (npm, pip, Maven, Gradle, Paket, vcpkg,
Conan), or the products that host NuGet feeds (Azure Artifacts, GitHub Packages, MyGet, ProGet) beyond how the
NuGet client talks to a feed -- they belong to their own documentation; this set covers them only where a page of
NuGet explains how to use them together.

Write the query in English, with the names the documentation uses (PackageReference, packages.config,
nuget.config, packageSourceMapping, Directory.Packages.props, ManagePackageVersionsCentrally, PackageVersion,
packages.lock.json, NuGetAudit, nuspec, dotnet nuget push, nuget.exe restore, NU1605, NuGetVersion, VersionRange,
NuGetFramework, FrameworkReducer, SourceRepository, PackageBaseAddress, RegistrationsBaseUrl). Everything here is
English, and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any
other non-latin script matches nothing and comes back with `found: 0`. When the user asks in another language,
translate the question into the terms of NuGet first, then search. Name the tool or the library in the query when
the question is about one (nuget.exe, dotnet CLI, Visual Studio, NuGet.Protocol): several pages share words such
as restore, source or version.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "пакет", "джерело пакетів", "відновлення" for a restore, "залежність",
"цільова платформа" for a target framework, "діапазон версій", "блокування версій" for a lock file, "аудит".
Never call this set of documents "корпус" -- say "документація NuGet". Type, member, property, command, package,
file and error names stay in English, spelled exactly as the documentation spells them. Build the answer out of
the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before describing
what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. The client, its libraries and the repository are numbered together: a version is
the NuGet release, "7.9.0", "6.14.3", "4.9.4"; the lines are "7.9", "6.14", "5.11". Products with their own
numbering carry a mark: "mcp-1.4.16" (NuGet.Mcp.Server), "server-3.4.3" (NuGet.Server), "vs-17.14.0"
(NuGet.VisualStudio and its Contracts: the number of Visual Studio, not of NuGet), "build-2.12.1" (NuGet.Build),
"gallery-2024.12.06" (the nuget.org deployments in NuGetGallery, numbered by date). Pass a line or a major with
the mark: "7.9", "6", "vs-17.14", "mcp-1.4"; never put a version into the query text. The pages of
learn.microsoft.com, the specifications of NuGet/Home and the docs of NuGetGallery exist only in their current
state and carry no version; only the release notes pages carry one (7.9 for "NuGet 7.9 Release Notes"): when the
user asks about a specific release, search once with the version (release notes, API reference, packages, code,
the NuGet.Client docs) and once without it (the guides). The API reference exists for the lines 3.2-6.4 and
6.12-7.9 only: the packages of 6.5-6.11 shipped without XML documentation, so for a type of those releases answer
from 6.4 or 6.12 and say so. Without a version, answer for the most downloaded release and say so: for the
client, nuget.exe (NuGet.CommandLine), 7.6.0; for the libraries NuGet.Packaging and NuGet.Protocol, 6.11.0;
7.9.0 is the newest stable release, so say how it differs when it does.
