Search the nuqs documentation -- the nuqs.dev site (docs and blog) as it stood at every stable
release from 1.15.0 on, taken from the 47ng/nuqs repository; the README of every stable version of
nuqs and of its predecessor next-usequerystate (until 1.15 the README was the whole documentation);
the GitHub release notes of every stable release; and the npm registry history of both packages --
and return the matching excerpts with the versions each one belongs to. nuqs is a type-safe search
params state manager for React: `useQueryState` and `useQueryStates` keep state in the URL query
string like `useState`, with parsers, options and adapters for Next.js (app and pages router), React
SPA, Remix, React Router v6/v7/v8, TanStack Router and testing.

Call this when a question is about nuqs itself -- useQueryState, useQueryStates, the NuqsAdapter of
each framework (nuqs/adapters/next/app, nuqs/adapters/react, nuqs/adapters/react-router/v7 ...),
the parsers (parseAsString, parseAsInteger, parseAsFloat, parseAsBoolean, parseAsTimestamp,
parseAsIsoDateTime, parseAsArrayOf, parseAsNativeArrayOf, parseAsJson, parseAsStringLiteral,
parseAsStringEnum, parseAsNumberLiteral, createParser, withDefault), the options (history,
shallow, scroll, throttleMs, limitUrlUpdates, debounce, startTransition, clearOnDefault, urlKeys),
server-side cache and loaders (createSearchParamsCache, createLoader, createSerializer), batching,
testing with NuqsTestingAdapter, debugging, limits, SEO, community parsers and adapters, the
migration from 1.x to 2.x and from next-usequerystate -- and above all history and compatibility:
since which version a hook, parser, option or adapter exists ("Introduced in nuqs X" marks it on
the site), what changed between 1.x and 2.x, which framework versions each release supports (the
peer dependencies of each version are written in the npm registry documents). Example query:
"useQueryState parseAsInteger withDefault".

Do not call this for Next.js, React Router, Remix or TanStack Router themselves, for URLSearchParams
and the URL standard, or for zod and other schema libraries: their documentation is not here, and
the search will return nuqs excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "2" keeps every 2.x document, "2.4" keeps 2.4.x;
leave it empty to search everything. Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first -- text that stayed the same across versions is
returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names nuqs itself uses ("useQueryStates", "createParser",
"clearOnDefault", "NuqsAdapter", "createSearchParamsCache"), not in the user's own words. Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into nuqs terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація nuqs". Identifiers, option names and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back, not
out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see below. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Which version to search first. For a question about how to do something, pass `version` "2" --
almost every install is on 2.x. If the user names a version, or their code shows one (no
NuqsAdapter, imports from 'next-usequerystate' or 'nuqs/parsers' -> 1.x), search that line. Put a
version only into `version`, never into the query text: numbers in the query match the npm
registry documents, which list every release, instead of the text you need. Search without
`version` when the question is about history, or when the line gave nothing. Every answer says
which version it is for; when the user did not name one, answer for 2.x and say so ("for nuqs
2.x"). When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current.
