Call this when a question is about GPUs in containers through the NVIDIA stack: how to install the toolkit
(the apt or dnf repository, which packages, pinning NVIDIA_CONTAINER_TOOLKIT_VERSION) and which versions the
repository holds; how to configure Docker (sudo nvidia-ctk runtime configure --runtime=docker, daemon.json,
--gpus, --runtime=nvidia, rootless mode), containerd (--runtime=containerd, nvidia runtime class,
--set-as-default, drop-in config), CRI-O or Podman; what a flag of nvidia-ctk, nvidia-cdi-hook or the
installer does and what its default is (--runtime, --config, --config-mode, --drop-in-config,
--nvidia-set-as-default, --cdi.enabled, --output, --format, --mode, --device-name-strategy,
--library-search-path, --driver-root, --dev-root); how to generate and use a CDI specification (nvidia-ctk
cdi generate --output=/etc/cdi/nvidia.yaml, nvidia.com/gpu=all, nvidia-cdi-refresh.service, docker run
--device nvidia.com/gpu=all, podman); what an environment variable does (NVIDIA_VISIBLE_DEVICES,
NVIDIA_DRIVER_CAPABILITIES, NVIDIA_REQUIRE_CUDA, NVIDIA_DISABLE_REQUIRE, NVIDIA_MIG_CONFIG_DEVICES,
NVIDIA_GPU_MEMORY_LIMIT); what a config.toml option does (accept-nvidia-visible-devices-envvar-when-unprivileged,
nvidia-container-cli.no-cgroups, nvidia-container-runtime.mode, nvidia-container-runtime.runtimes,
nvidia-container-runtime-hook.path, features); how the components fit together (runtime, hook, CLI,
libnvidia-container, which package to install); how to troubleshoot (debug logs, "Failed to initialize
NVML", SELinux, lost GPUs after systemctl daemon-reload, cgroups); what changed in a release and since which
release a feature, flag or hook exists; what the CDI specification says (cdiVersion, kind, devices,
containerEdits, deviceNodes, mounts, hooks, env, spec directories /etc/cdi and /var/run/cdi, what each spec
version added); how nvidia-docker2 and the old nvidia-container-runtime package relate to today's toolkit; how
nvidia-container-cli is used; how the nvcdi Go API works (nvcdi.New, WithMode, GetSpec). Example query:
"nvidia-ctk runtime configure containerd".

Do not call this for Docker, containerd, CRI-O, Podman or Kubernetes themselves beyond how they run NVIDIA
GPUs -- those have their own documentation servers --, for the NVIDIA GPU Operator, the NVIDIA device plugin,
DCGM or MIG management beyond what the toolkit says about them, for CUDA programming, the NVIDIA driver
installation itself or nvidia-smi, for other GPU vendors (AMD ROCm, Intel), or for gVisor's nvproxy: this set
says how the NVIDIA Container Toolkit exposes GPUs to containers.

Write the query in English, with the names the documentation uses (nvidia-ctk runtime configure, nvidia-ctk
cdi generate, nvidia-cdi-hook update-ldcache, nvidia-container-runtime, nvidia-container-runtime-hook,
nvidia-container-cli, nvidia-cdi-refresh, config.toml, NVIDIA_VISIBLE_DEVICES, NVIDIA_DRIVER_CAPABILITIES, CDI,
containerEdits, nvidia-docker2, nvcdi). Everything here is English, and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing and comes
back with `found: 0`. When the user asks in another language, translate the question into NVIDIA Container
Toolkit terms first, then search.

Flags have no reference page of their own: their text lives in the command code -- the Flags list of each
cli.Command, with the flag name, usage and default -- and in the guide pages that use them. Such excerpts come
back as Go code: a default is often a constant defined elsewhere in the same file, so read the whole excerpt
with `read_section`, and search the constant's name, before quoting a default.

Answer in the language the user wrote in. For a question about history or a change between releases, answer
point by point: since which release; what changed; how it stands in the newest one -- each point with its
release and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "середовище виконання", "хук", "специфікація", "пристрій", "драйвер",
"змінна середовища". Never call this set of documents "корпус" -- say "документація NVIDIA Container Toolkit".
Command, flag, option, variable, type and function names stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. The toolkit and libnvidia-container share one numbering (unified releases):
"1.20.1"; the site, the repository documents, the command code, the changelog, the release notes, the APT
versions and the pkg.go.dev reference all carry it. Pass a full version ("1.17.8") or a line ("1.17" keeps
every 1.17.x); the leading "v" of a tag matches nothing. Three other products carry their own label:
"nvidia-docker-2.14.0" (the archived nvidia-docker and the nvidia-docker2 package), "nvidia-container-runtime-3.14.0"
(the archived runtime and its package) and "cdi-1.1.1" (tags of the CDI specification repository; the
specification version itself, cdiVersion "1.1.0" and so on, is written inside the text). The site exists from
1.6.0: older toolkit releases have only repository documents and code. When the user names a release, pass it
into `version`; never put it into the query text. Without a version, answer for the newest release (1.20.1)
and say so.
