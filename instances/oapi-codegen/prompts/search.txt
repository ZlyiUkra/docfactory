Search the documentation of oapi-codegen (github.com/oapi-codegen/oapi-codegen), the generator of Go code from
OpenAPI 3 documents, together with the libraries its code depends on: the README of oapi-codegen and its docs/ pages
(configuration, servers for net/http, chi, echo, gin, fiber, gorilla and iris, the x-go-* extensions, schema merging)
and the README of every example, at every minor release 1.0 ... 2.8; its GitHub release notes; the code of the
examples (OpenAPI documents, generator configuration and the hand-written server implementations next to the
generated code); github.com/oapi-codegen/runtime (parameter binding, strictmiddleware, the types Date, Email, UUID,
File) on pkg.go.dev 1.0 ... 1.8; github.com/oapi-codegen/nethttp-middleware (OapiRequestValidator, Options,
ErrorHandler, MultiErrorHandler) -- README and pkg.go.dev 1.0 ... 1.3; and kin-openapi (github.com/getkin/kin-openapi)
-- its README at every minor release (loading and validating a document, validating HTTP requests and responses with
openapi3filter, custom formats, custom error messages, the list of breaking API changes) and the pkg.go.dev reference
of openapi3, openapi3filter, routers and openapi3gen for the latest twelve releases. Returns the matching excerpts
with the versions each one belongs to.

Call this when a question is about generating Go code from an OpenAPI document: the generator configuration file
(package, output, generate: models, std-http-server, chi-server, strict-server, client, embedded-spec;
output-options; import-mapping; compatibility), what the strict server interface and its response types look like,
how the generated server is mounted under a base URL, the x-go-type, x-go-name, x-oapi-codegen-extra-tags and
x-go-type-skip-optional-pointer extensions, nullable and optional fields, the generated client, validating requests
against the document with nethttp-middleware and kin-openapi (openapi3filter.ValidateRequest, AuthenticationFunc,
MultiError, SchemaError, ValidateResponse), loading a document with openapi3.NewLoader, and what changed between
releases.

Do not call this for the OpenAPI specification itself (that is the specification text), for JSON Schema, for other
generators (ogen, go-swagger, openapi-generator), for routers and frameworks beyond the pages that show how to mount
generated code on them, or for generating TypeScript clients: their documentation is not here, and the search will
return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release: one number keeps a major line ("2"), two a minor ("2.4"), three an exact
version. oapi-codegen, runtime, nethttp-middleware and kin-openapi have their own version numbers: kin-openapi
versions are 0.N ("0.152"), runtime 1.N, nethttp-middleware 1.N, oapi-codegen 1.N and 2.N -- so "1.5" may match
several of them. Every excerpt comes back with `versions`: each release whose documents contain this exact text,
newest first.

Write the query in English, with the names the documentation itself uses ("strict-server", "std-http-server",
"StrictServerInterface", "NewStrictHandler", "HandlerWithOptions", "StdHTTPServerOptions", "BaseURL",
"embedded-spec", "GetSwagger", "output-options", "x-go-type", "x-go-name", "x-oapi-codegen-extra-tags",
"nullable", "OapiRequestValidator", "OapiRequestValidatorWithOptions", "ErrorHandler", "SilenceServersWarning",
"openapi3filter", "ValidateRequest", "ValidateResponse", "AuthenticationFunc", "MultiError", "SchemaError",
"openapi3.NewLoader", "Validate", "go tool oapi-codegen", "go:generate"), not in the user's own words. Everything here
is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes
back with `found: 0`. When the user asks in another language, translate the question into the terms of the
documentation first, then search.

Answer in the language the user wrote in. When that language is Ukrainian, write as a Ukrainian engineer writes, not
as a translation from English: plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not
"ексерпт"; "генератор", "згенерований код", "перевірка запиту", "документ OpenAPI". Never call this set of documents
"корпус" -- say "документація oapi-codegen" (or kin-openapi). Identifiers, configuration keys and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back, not
out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. oapi-codegen 2.8.1 is the newest release (its module path is
github.com/oapi-codegen/oapi-codegen/v2; 1.x lived at github.com/deepmap/oapi-codegen), runtime 1.8.0,
nethttp-middleware 1.3.1, kin-openapi 0.152.0. Search without `version` first; when the user names a version, search
that release. Every answer says which library and which release it is for.
