Search the documentation of openapi-typescript and its family (repository openapi-ts/openapi-typescript, site
openapi-ts.dev): openapi-typescript turns an OpenAPI 3.0 / 3.1 schema (YAML or JSON, local file or URL) into
TypeScript types with zero runtime -- `paths`, `components`, `operations`, `webhooks` --; openapi-fetch is a typed
fetch client built on those types; openapi-react-query wraps it in TanStack Query hooks; swr-openapi wraps it in SWR
hooks; openapi-typescript-helpers holds the shared helper types; openapi-metadata builds an OpenAPI document from
decorators. The corpus holds the pages of the site taken from the tag of every minor version of openapi-typescript
from 6.2 to 7.13 (introduction, CLI with its flags and `redocly.yaml`, the Node API with `openapiTS` and `astToString`,
transform and postTransform, advanced use and recipes, examples, the migration guide to 7.x, the openapi-fetch pages --
API, middleware and auth, testing, examples -- and the openapi-react-query pages); the README of every stable version
of all six packages from npm (up to openapi-typescript 6.2.4 the README was the whole documentation); the changelogs
of openapi-typescript (0.1.0 to 7.13.0), openapi-fetch, openapi-react-query and openapi-typescript-helpers; the old
site and the release notes of swr-openapi from its former repository htunnicliff/swr-openapi, and the release notes
of swr-openapi 5.x-6.x and openapi-metadata in the monorepo; the sample projects of openapi-fetch (Next.js,
SvelteKit, Vue 3); and the npm registry history of all six packages (date of every version, dist-tags,
dependencies). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about these packages as they describe themselves -- how to generate types from a schema,
which CLI flag or `openapiTS` option does what (`--enum`, `--alphabetize`, `--immutable`, `--additional-properties`,
`--path-params-as-types`, `--root-types`, `--export-type`, `--default-non-nullable`, `--array-length`), how to
transform a schema type (`Date` instead of `string`, `Blob` for binary), how to call an endpoint with openapi-fetch
(`createClient`, `GET`, `POST`, `params.path`, `params.query`, `body`, `parseAs`, `querySerializer`,
`bodySerializer`), how to add middleware or auth (`onRequest`, `onResponse`, `onError`, `client.use`), how to use
`createQueryHook`/`useQuery`/`useMutation`/`queryOptions` of openapi-react-query or the hooks of swr-openapi -- and
above all history and compatibility: since which version a flag, option or function exists, what changed between
versions (every changelog entry lists major, minor and patch changes with their PR), what broke in 7.0 of
openapi-typescript or in a 0.x minor of openapi-fetch, and when every version came out.

Do not call this for OpenAPI itself, TypeScript, TanStack Query, SWR, Redocly, Next.js, SvelteKit or Vue (their own
options, APIs and concepts): their documentation is not here -- these pages only show how the packages use them --
and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. openapi-typescript carries plain numbers (0.1.0 to 7.13.0); the other
packages carry a prefix: "fetch-" for openapi-fetch (fetch-0.0.1 to fetch-0.17.0), "react-query-" for
openapi-react-query, "swr-" for swr-openapi, "helpers-" for openapi-typescript-helpers, "metadata-" for
openapi-metadata. A line of one number keeps every document of that major ("7" keeps 7.0.0 to 7.13.0), two numbers
keep a minor ("fetch-0.13"), three an exact version ("7.13.0"). The pages of the site -- the openapi-fetch and
openapi-react-query pages among them -- carry the version of the openapi-typescript tag they were taken from (the last
patch of every minor). Leave `version` empty to search everything, including text that carries no version. Every
excerpt comes back with `versions`: each version whose documents contain this exact text, newest first -- a page that
stayed the same across versions is returned once, with all of them listed, so the list itself shows from which to
which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("openapiTS", "astToString", "transform",
"postTransform", "createClient", "client.use", "onRequest", "querySerializer", "parseAs", "paths", "components",
"operations", "useQuery", "useSuspenseQuery", "--enum", "--root-types", "redocly.yaml"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at
all and comes back with `found: 0`. When the user asks in another language, translate the question into the terms of
the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer point by point:
 since which version it exists; what changed in later versions; what prompted the change, if the excerpts say
so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація openapi-typescript". Identifiers, method names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads openapi-typescript 7 leads with about 94 % (7.0.0 of June 2024,
7.13.0 of February 2026; Redocly parses the schema since 7.0), 6 has about 4 %. openapi-fetch is still 0.x: 0.17 has
about 46 %, 0.14 about 23 %, 0.13 about 16 %; openapi-react-query 0.5 has about 93 %; swr-openapi 5 nearly all. Pass
`version` "7" for how openapi-typescript works today, "fetch-0.17" for openapi-fetch, and mention 6.x when the user is
on it or it differs (the migration guide to 7.x says what changed). Search without `version` when the question is
about history, or when the line gave nothing. Every answer says which version it is for; when the excerpts behind a
statement come only from older versions, name those versions instead of presenting the text as current.
