Call this when a question is about OpenTelemetry: how to set up the Node.js or browser SDK (NodeSDK, register,
instrumentation.ts in Next.js), what a span processor, sampler, propagator, resource or exporter does, which
environment variable sets what (OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_SERVICE_NAME), what an attribute is called in
the semantic conventions and since when, how OTLP encodes a field, how to configure a Collector pipeline or a
component (otlpreceiver, batchprocessor, memory_limiter, k8sattributes, prometheusexporter), what changed
between versions and how to migrate (SDK 1.x to 2.x, semconv HTTP stabilization), whether an instrumentation
exists for a library. Example query: "BatchSpanProcessor maxExportBatchSize scheduledDelayMillis".

Do not call this for Jaeger, Prometheus, Grafana or a vendor backend beyond what OpenTelemetry says about them,
for Next.js itself (nextjs-docs) or NestJS itself (nestjs-docs).

Write the query in English, with the names OpenTelemetry uses (TracerProvider, NodeSDK, getNodeAutoInstrumentations,
SpanKind, ParentBased, W3CTraceContextPropagator, OTLPTraceExporter, service.name, http.request.method, receivers,
pipelines). Everything here is English, and the word index keeps only latin letters and digits, so a query
written in Ukrainian, Russian or any other non-latin script matches nothing and comes back with `found: 0`. When
the user asks in another language, translate the question into OpenTelemetry terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий"; "траса", "спан", "метрика", "журнал
подій", "атрибут". Never call this set of documents "корпус" -- say "документація OpenTelemetry". Names of
classes, methods, options, attributes and environment variables stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt
was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. When the user names a version, search that line; otherwise answer for the
JavaScript SDK 2.x (the stable packages most installed today) and say when 1.x differs. Put a version only into
`version`, never into the query text. Every product carries its own prefix so that numbers are never mixed:
the stable JS SDK has bare numbers ("2", "2.12", "1.30"), the rest are labelled -- "api-1.9", "experimental-0.223"
(sdk-node, OTLP exporters, logs, instrumentation), "semantic-conventions-1.43" (the JS constants package),
"spec-1.61", "semconv-1.44", "proto-1.11", "collector-0.163" (core and contrib), "configuration-1.2", "opamp-0.20",
"vercel-otel-2.1", each js-contrib package by its name ("instrumentation-express-0.71", "auto-instrumentations-
node-0.81", "contrib-0.24" before 2021), npm tables "npm-sdk-node-0.223". The site pages carry no version: they
show the current state. Documents are named after their file: site pages "site-content-en-docs-…", the
specification "spec-specification-…", semantic conventions "semconv-docs-…", Collector READMEs
"collector-contrib-receiver-…", JS code "js-packages-…-src-…", contrib "js-contrib-packages-instrumentation-…".
