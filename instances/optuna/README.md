# optuna — примірник фабрики docfactory

Цей примірник зібрав документацію Optuna, її пакета інтеграцій optuna-integration і веб-панелі optuna-dashboard та віддає її
через сервер MCP, щоб модель відповідала з текстів бібліотек, а не з пам'яті.

Optuna — бібліотека для Python, яка сама підбирає параметри моделі. Користувач пише функцію `objective`. Ця функція бере в
об'єкта `trial` значення параметрів (`trial.suggest_float("eta", 1e-3, 0.3, log=True)`), навчає з ними модель і повертає оцінку.
Optuna викликає функцію багато разів, і кожен виклик називається спробою (trial). Семплер (`TPESampler` та інші) вирішує, які
значення спробувати наступними, з огляду на результати попередніх спроб. Прунер (`MedianPruner` та інші) зупиняє спробу ще під
час навчання, якщо проміжний результат уже гірший за інші. Усі спроби разом зберігає об'єкт `Study`. Його можна записати в базу
даних і продовжити пізніше.

- **optuna-integration** містить готові зв'язки Optuna з іншими бібліотеками. Для XGBoost і LightGBM тут є колбеки обрізання
  (`XGBoostPruningCallback`, `LightGBMPruningCallback`), які передають Optuna проміжну оцінку після кожної ітерації бустингу, і
  `LightGBMTuner`, що підбирає параметри LightGBM по черзі. До версії 3.2 ці класи жили в самій Optuna (`optuna.integration`).
- **optuna-dashboard** — веб-панель. Вона показує спроби з бази даних Study на графіках: як покращувалася оцінка, які значення
  параметрів пробувалися, які параметри важать найбільше.

## Скільки цього

Усього 2 497 документів і 6 457 фрагментів. Фрагмент — це шматок документа, який пошук повертає як окремий результат. Сторінка з
однаковим текстом у кількох лініях лежить одним документом із переліком цих ліній.

| Що | Версії | Документів |
|---|---|---|
| сайт optuna.readthedocs.io: встановлення, посібник (ключові можливості й рецепти), довідник API зі сторінкою кожного класу й функції, FAQ | останній патч кожної мінорної лінії 0.19–5.0 (36 ліній) | 2 143 |
| сайт optuna-integration.readthedocs.io: довідник кожної інтеграції | останній патч кожної мінорної лінії 3.2–5.0 (15 ліній) | 136 |
| сайт optuna-dashboard.readthedocs.io: початок роботи, налаштування, довідник API, розширення для VS Code і JupyterLab | стабільна версія 0.21 | 31 |
| нотатки релізів GitHub трьох пакетів | усі стабільні теги | 49 + 17 + 43 |
| записи PyPI трьох пакетів з README | усі стабільні версії | 40 + 16 + 22 |

Мітки версій мають вигляд `optuna-5.0`, `optuna-integration-4.0` і `optuna-dashboard-0.21`. Префікси потрібні, щоб номери трьох
пакетів не змішувалися між собою й з версіями інших бібліотек.

**Де є прогалини, хоч ми й брали всі лінії.**

- Read the Docs має теки Optuna лише від v0.19.0. Про лінії 0.0–0.18 є тільки записи PyPI і релізи.
- Теки v3.1.1 і v3.0.6 Read the Docs називає активними, але їхні сторінки відповідають «404», бо збірки цих патчів на сайті немає.
  Тому лінію 3.1 взято з v3.1.0, а лінію 3.0 — з v3.0.5.
- optuna-dashboard на Read the Docs має лише стабільну версію і гілку розробки. Про старіші версії панелі є тільки релізи й записи
  PyPI.
- Сторінки `_modules/` (вихідний код, на який ведуть посилання «[source]») не взято: це код, а не документація.

Замір `quality` на 09.11.2026 дав такі числа. Запити назвами з документації знаходять потрібне 10 із 10, а модель зазвичай питає саме
так. Запити своїми словами знаходять потрібне 6 із 10.

## Що в цій теці

- `corpus/` — паспорт `index.json`; текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, а розпакований `passages.json` лежить
  поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df optuna <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| сайт Optuna | `optuna.readthedocs.io/en/v*/` | `sphinx-html` |
| сайт optuna-integration | `optuna-integration.readthedocs.io/en/v*/` | `sphinx-html` |
| сайт optuna-dashboard | `optuna-dashboard.readthedocs.io/en/stable/` | `sphinx-html` |
| нотатки релізів | релізи GitHub `optuna/optuna`, `optuna/optuna-integration`, `optuna/optuna-dashboard` | `ghreleases-pattern` |
| записи PyPI | `pypi.org/pypi/<пакет>/json` | `pypi-versions` |

**Чому сайт обходиться посторінково.** Read the Docs віддає для кожної версії архів `htmlzip`, але в ньому вся документація
зібрана в одну сторінку (збирач Sphinx `singlehtml`). Із такого архіву вийшов би один документ на версію без поділу на сторінки,
тому сайт обходиться сторінка за сторінкою.

**Чому обхід довгий.** Read the Docs обмежує, скільки запитів можна зробити за певний проміжок часу. Під час першого збирання три
процеси з паузою в секунду працювали без відмов, а шість процесів за кілька хвилин отримали відповідь «429 Too Many Requests».
Після цього сайт відмовляв навіть двом процесам, тоді як один процес із паузою в секунду пройшов решту без жодної відмови. Тому
оновлювати сайт треба одним процесом. Близько 5 700 сторінок трьох сайтів займають так приблизно дві години.

## Як підняти сервер

Сервер працює у спільному середовищі фабрики, власного `.venv` примірник не має. В окремому терміналі виконайте:

```
./df optuna serve
```

Порт — `8967`. Якщо порт зайнято, `serve` скаже про це й зупиниться: швидше за все, цей сервер уже запущено в іншому терміналі.

Під'єднати сервер до Claude Code можна двома способами. Перший — файл `.mcp.json` цієї теки. Другий — команда:

```
claude mcp add --transport http --scope user optuna-docs http://127.0.0.1:8967/mcp
```

Команда для Claude Code у Windows, коли сервер працює у WSL, та сама: WSL віддає порт на `127.0.0.1` Windows.

У сесії Claude Code команда `/mcp` має показати сервер `optuna-docs` з інструментами `search_docs` і `read_section`. Якщо сервер
позначено як недоступний, перевірте, чи працює `serve`, і чи запущено контейнер Qdrant.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт. Серверу вистачає кешу фрагментів
(`index/passages.json`) і колекції Qdrant; відповіді ті самі до символу, бо адреса й дата лежать у кеші кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/optuna-corpus-2026-11-09.tar.gz` (2 497 текстів, паспорт і сховище сирого `raw/`;
перед видаленням текстів розпакований окремо й звірений із диском) і в копії на диску Windows
`C:\Distr\optuna-corpus-2026-11-09.tar.gz` (звірено за SHA-256). В історії git текстів немає.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/optuna/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/optuna-corpus-РРРР-ММ-ДД.tar.gz -C instances/optuna corpus raw
find instances/optuna/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/optuna/raw
gzip -9 -c instances/optuna/index/passages.json > instances/optuna/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й `raw/` можна лише після того, як новий архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового записують сюди.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й `raw/`:

```
tar -xzf ~/archives/docfactory/optuna-corpus-2026-11-09.tar.gz -C instances/optuna
./df optuna smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів вони не працюють; перевірки `smoke`, яким
потрібні тексти, пропускаються («корпус в архіві»).
