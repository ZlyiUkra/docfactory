# Оновлення корпусу optuna

Корпус живе нагорі: три сайти на Read the Docs (Optuna, optuna-integration, optuna-dashboard), релізи GitHub трьох репозиторіїв і
реєстр PyPI. Теки вже вийшлих версій на сайтах не змінюються, а нова лінія потребує правки `sources.json`.

Правило: **нічого не видаляється.** Ані `refresh`, ані `manifest` нічого не видаляють. Лише `vectors` прибирає точки своєї колекції,
чиїх фрагментів у корпусі вже немає.

**Спершу — повернути тексти.** Корпус примірника в архіві, а `check`, `refresh` і `manifest` читають файли. Тому перед роботою нижче
тексти розпаковують, а після неї виносять знову: обидві дії описано в
[README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

```
./df optuna refresh <id джерела>   # лише те, що змінилося
./df optuna manifest
./df optuna vectors
./df optuna smoke
# Ctrl+C у терміналі з serve, і знову: ./df optuna serve
```

Що міняти, коли вийшов новий випуск:

- **Нова лінія Optuna чи optuna-integration (наприклад 5.1):** у поле `versions` відповідного джерела записати теку першою
  (`"v5.1.0"`), а в `version_labels` — що вона означає лінію (`"v5.1.0": "5.1"`). Новий патч наявної лінії замінює в обох полях
  попередній патч цієї лінії. Перед записом перевірити, що стартова сторінка теки відповідає «200»: Read the Docs буває називає
  активною версію, збірки якої немає (так було з v3.1.1 і v3.0.6).
- **optuna-dashboard:** у `version_labels` джерела `optuna-dashboard-docs` замінити мітку теки `stable` на нову лінію.
- Релізи GitHub і PyPI підтягуються самі.

**Лише один процес.** Read the Docs відповідає «429», коли запитів забагато. Сайти оновлюють одним процесом `refresh` з паузою в
секунду (`pause_sec: 1.0`), без паралельних блоків. Обхід звертається до кожної сторінки, навіть коли вона вже є в сховищі сирого
(сайт відповідає «304 Not Modified», і це теж звернення), тому повне оновлення трьох сайтів триває близько двох годин; запускають
його у фоні (`setsid nohup … &`). Якщо «429» усе ж прийшло, процес зупиняють, чекають кілька хвилин і продовжують з того джерела, де
він зупинився.

Якщо `smoke` скаржиться на число фрагментів, корпус підріс: нове число записують в `expected_passages`, а в `expected_note` — коли й
чому його знято.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу треба виконати `./df optuna quality --show`, переглянути запити зі знаком «-» і перевірити, чи справді
відповідь змінилася. Ціль розширюють лише тоді, коли знайдена сторінка справді відповідає на запит.
