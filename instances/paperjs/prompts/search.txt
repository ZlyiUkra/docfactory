Call this when a question is about Paper.js: setting up a canvas with paper.setup() or PaperScript, creating
paths, segments and curves, predefined shapes (Path.Circle, Path.Rectangle, Path.Line), points, sizes,
rectangles and vector math, colors, gradients, strokes and fills, groups, layers and the project hierarchy,
symbols, rasters and pixels, text items, transforming items (position, rotate, scale, matrix), hit testing,
boolean operations on paths (unite, intersect, subtract, exclude, divide), path intersections, smoothing,
simplifying and flattening, mouse tools and keyboard events, animation with onFrame and tweens, importing and
exporting SVG and JSON, running Paper.js in Node.js or a worker -- and history: since which version a class,
method or option exists, what a release changed.

Do not call this for the browser Canvas API or SVG themselves (CanvasRenderingContext2D, getContext, SVG elements) --
they are in the mdn-docs server, and what the SVG specification requires is in the svg-docs server -- nor for Konva
(the konva-docs server), PixiJS (the pixijs-docs server), Fabric.js (the fabricjs-docs server), SVG.js (the svgjs-docs
server), D3 (the d3-docs server), other drawing libraries, React, or JavaScript and TypeScript language questions:
their documentation is not here, and the search will return Paper.js excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line. Paper.js has no 1.0, so a line is two numbers: "0.12" keeps
every 0.12.x document (the tutorials, the API reference of 0.12.18 and 0.12.20, README, changelog, releases),
"0.17" the same for 0.17, "0.12.18" one exact version; leave it empty to search everything. The other packages
carry a prefix so they never mix with paper: "paper-jsdom-0.12", "paper-jsdom-canvas-0.12", "types-paper-0.12".
Every excerpt comes back with `versions`: each version whose documents contain this exact text, newest first,
so the list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names Paper.js itself uses ("Path.Circle center radius", "segments
handleIn handleOut", "onMouseDrag event.delta", "hitTest tolerance", "unite intersect subtract", "exportSVG
asString", "onFrame event.delta", "Raster getPixel", "view.onResize"), not in the user's own words. Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
at all and comes back with `found: 0`. When the user asks in another language, translate the question into
Paper.js terms first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a class, method
or option, answer point by point: since which version it exists; what changed in later versions; what prompted
the change, if the excerpts say so; and how it stands in the current version. Every point names the version and
the document it rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and
the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація Paper.js". Identifiers, option names and titles stay
in English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. In the week to 18 November 2026 version 0.12.18 carried about 69% of the
downloads of paper and the whole 0.12 line more than 80%; 0.17.0 and 0.16.0 carried about 5% each. The lines
0.13 to 0.17 all came out between 19 October and 3 November 2026 and mostly add things on top of 0.12: text
along a path and inside a shape (PathText, AreaText, TextRange, TextStory, from 0.15), hosted projects
(HostItem, from 0.14), live effects, stroke profiles, pattern colors and path offsetting (from 0.17). So search
with `version` "0.12" for a question about how to do something, and say the answer is for Paper.js 0.12; if the
user names a newer version or asks for one of the newer features, search "0.17" (or the line they named).
Search without `version` when the question is about history or when the line gave nothing. In the API
reference a member inherited from a parent class is described on the parent's page only: Path and
CompoundPath inherit from PathItem and Item, Group, Layer, Shape, Raster and the text items from Item; the
section "Inherited members" at the end of a page names the parents. So for `position`, `rotate()`, `fillColor`
or `onMouseDown` of a Path, look at Item. PaperScript and plain JavaScript differ: operators on points
(`point1 + point2`) and the global handlers (`onMouseDown`, `onFrame`) work only in PaperScript; say which of
the two an example is written in.
