# Оновлення корпусу partysocket

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи partysocket, і збирання з нуля. Порядок усередині
кожної важливіший за самі команди.

Головне правило: **версії приходять самі, з реєстру npm — окрім коду.** Сайт docs.partykit.io тегів не має, тож читач
`ghsite-dated` бере перелік версій і їхні дати з https://registry.npmjs.org/partysocket і на кожну стабільну версію
робить знімок гілки `main` репозиторію partykit/partykit — вершину гілки перед виходом наступної версії тієї ж лінії.
README, журнал змін і реєстр npm так само читають актуальний перелік. Руками дописують лише теги коду (крок 1).

Друге правило: **нова версія змінює й старі документи.** Документ — неповторний текст сторінки чи файла коду, а в
рядку `# версія:` стоять усі версії, де він був саме таким. Тож після нового релізу корпус перезаписують цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх не
знайде. Для найновішої версії знімок сайту — сьогоднішній стан гілки, тож навіть без нового релізу правка сайту
змінює корпус.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Теги коду.** Код і тести беруть два джерела з полем `tags` — об'єктом «тег або коміт → версія», від
найновішого: `partysocket-code-cf` (репозиторій cloudflare/partykit, версії 1.1.1, 1.1.3 і новіші) і
`partysocket-code-pk` (partykit/partykit, 0.0.2–1.1.0 і 1.1.2; пакет звідти переїхав, і нових версій там не буде).
Кожну нову версію дописують на початок `tags` джерела `partysocket-code-cf`: `"partysocket@1.4.0": "1.4.0"`. Якщо
тегу немає (так було з 1.1.4–1.1.6), ключем стає коміт `gitHead` версії з реєстру npm. Теги, без жодного звернення до
API:

```
git ls-remote --tags https://github.com/cloudflare/partykit.git 'partysocket@*' | grep -v '\^{}' | sed 's#.*refs/tags/##'
```

Коміт версії без тегу: `curl -s https://registry.npmjs.org/partysocket/1.1.4 | python3 -c "import json,sys;
print(json.load(sys.stdin)['gitHead'])"`.

**Крок 2. Чи не з'явилося нової сторінки про PartySocket.** Джерело `partykit-site` бере не весь сайт, а чотирнадцять
сторінок, де згадано PartySocket (поле `include` епохи). Нова сторінка з клієнтом не потрапить у корпус сама:
перевірити, чи згадує її `partysocket`, і дописати шлях у `include`. Якщо сторінку перенесли на інший шлях, старий
лишають (він дає старі редакції), новий дописують, а в `config.json` — правило `slug_rewrite`, що зводить нове ім'я до
старого ключа (так зведено `tutorial/2-adding-realtime-cursors` → `tutorials/…`). Хостинг PartyKit закривається
23.10.2026; якщо репозиторій сайту перестане оновлюватися, знімки новіших версій просто повторюватимуть останній
стан — правок це не потребує.

**Крок 3. Якщо вийшла нова мажорна лінія** (2.0):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзаци «Which version to search first» і «Every answer
  says which version it is for») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "1"` —
  інакше модель і далі шукатиме в старій лінії, а нова документація у видачу не потрапить;
- лінію за замовчуванням вибирають за завантаженнями з npm за тиждень, а не за номером: поки 1.x завантажують більше,
  вона лишається основною;
- у `checks.json`, у десятці `quality_model`, замінити `"1"` на нову лінію там, де питання про поточну поведінку.

**Крок 4. Завантажити.**

```
./df partysocket sources --why
./df partysocket refresh
./df partysocket manifest
./df partysocket vectors
./df partysocket smoke
./df partysocket quality
# Ctrl+C у терміналі з serve, і знову: ./df partysocket serve
```

`smoke` порівнює число фрагментів з `expected_passages` у `checks.json`; після оновлення число зміниться — вписати
нове разом із датою в `expected_note`, а в README — у таблицю «Скільки цього». `quality` порівняти з попереднім
заміром (README): «як модель» має лишитися 10 із 10.

**Крок 5. Винести тексти в архів** — як у README, розділ «Архівний режим»: новий архів під новою датою, звірка з
диском, видалення текстів і попереднього архіву, нове ім'я архіву в README.

## 2. Збирання з нуля

На новій машині чи після втрати корпусу (venv — спільний, з кореня, власний не потрібен: розділ «Спільне середовище»
кореневого README.md):

```
cd instances/partysocket
cp .env.example .env          # GITHUB_TOKEN обов'язково: без нього GitHub дає 60 звернень на годину
cd ../..
./df partysocket refresh      # ~15 хвилин
./df partysocket manifest
./df partysocket setup
./df partysocket vectors
./df partysocket smoke
```

Без токена GitHub `refresh` не впорається: лише перелік комітів сайту й дерева 49 знімків для сайту та 49 для коду —
понад сотню звернень до API.
