Search the official documentation of PartySocket, the reconnecting WebSocket client of PartyKit
and PartyServer (npm package partysocket) -- the pages of docs.partykit.io that cover it on every
stable release from 0.0.3 to the current 1.x line, the README of every stable version from 0.0.2
on, the CHANGELOG of the package, the npm registry history of the partysocket package, and the
source code and tests of the package on every stable release. Return the matching excerpts with
the versions each one belongs to.

Call this when a question is about PartySocket itself -- the PartySocket class and its options
(host, room, party, prefix, basePath, path, id, query, protocol, protocols, startClosed), the
reconnecting WebSocket underneath (ReconnectingWebSocket: the default export of partysocket/ws,
also exported as WebSocket from partysocket) and its options and defaults (maxRetries,
maxReconnectionDelay, minReconnectionDelay, reconnectionDelayGrowFactor, minUptime,
connectionTimeout, maxEnqueuedMessages, startClosed, debug, debugLogger, WebSocket,
shouldReconnectOnClose), reconnect(), close(), send() and the message buffer
(drainQueuedMessages), updateProperties(), the URL and protocols providers, readyState,
retryCount, shouldReconnect, roomUrl, events (open, message, close, error), PartySocket.fetch for
HTTP requests to a party, the React hooks (usePartySocket from partysocket/react, useWebSocket
from partysocket/use-ws; enabled, transferEnqueuedMessages, onOpen, onMessage, onClose, onError),
React Native and Node.js usage, the EventTarget polyfill, and how a client authenticates, connects
to several parties, and is rate-limited by a PartyKit or PartyServer server. Example query:
"maxRetries default".

Do not call this for Socket.IO, the ws package, the browser WebSocket API in general, Cloudflare
Durable Objects, or the internals of PartyKit and PartyServer servers beyond what these pages show
next to the client: their own documentation is not here, and the search will return excerpts that
merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "1" keeps every 1.x document, "1.1" keeps
1.1.x, "1.3" keeps 1.3.x, "0" keeps 0.0.x; leave it empty to search everything. Every excerpt
comes back with `versions`: each version whose documents contain this exact text, newest first --
text that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lives. The page titled "PartySocket (Client API)
(reference/partysocket-api)" is the reference on docs.partykit.io; the other site pages are
titled by their heading and path -- "Authentication (guides/authentication)", "Responding to HTTP
requests (guides/responding-to-http-requests)", "Migrate to PartyServer
(guides/migrate-to-partyserver)". The site page was last changed in January 2024 and the README
in June 2025, so the options added later (shouldReconnectOnClose, drainQueuedMessages,
transferEnqueuedMessages, basePath, send() returning a boolean, useWebSocket) are described only in
the CHANGELOG, titled "partysocket changelog: 1.2.0", and in the code. The code is titled by
repository and path -- "partykit: packages/partysocket/src/ws.ts" (ReconnectingWebSocket and its
Options), ".../src/index.ts" (PartySocket), ".../src/react.ts", ".../src/use-socket.ts" (the
hooks) and ".../src/tests/*.test.ts" (the tests); a section of the code is one class, method,
type or test, headed by its name, such as "ReconnectingWebSocket.send()" or "type Options". The
package moved from the repository partykit/partykit to cloudflare/partykit in March 2025 (1.1.1,
1.1.3 and later); both are covered.

Which version to search first. For a question about how to do something today, pass `version` "1":
without it, the editions of older 0.0.x pages and code can take places with the current ones. If
the user's project pins an older version, pass that line instead -- before 0.0.12 there was no
PartySocket.fetch, before 0.0.17 no updateProperties, before 0.0.23 `host` did not default to
window.location.host; 1.0.0 was a stable cut with no API change; 1.1.0 renamed the old `prefix` to
`basePath` and added a new `prefix`; 1.2.0 made close() dispatch its close event at once and
send() return a boolean. Search without `version` when the question is about history, or when the
line gave nothing that answers.

Name the class, option, method or hook the way the documentation and the code name them, not in
the user's own words: "maxRetries", "minUptime", "maxEnqueuedMessages", "updateProperties",
"usePartySocket", "PartySocket.fetch", not "how to stop it reconnecting". For what an option means
and what it defaults to, add the word "default" to its name -- "maxRetries default", "minUptime
default": a bare option name brings first the tests that set it, while "default" brings the table
of default values in the reference and the DEFAULT constant in the code. For a question about when
something appeared, changed or disappeared, search more than once: without `version` first, to
find the CHANGELOG entry that names the exact version, then with the versions around it, to see
how the documentation and the code described it before and after. For a question about exact
behaviour or a default value, search the code and its tests as well as the pages: the code is what
the package actually does.

Write the query in English, with the names PartySocket itself uses. Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into PartySocket terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, partysocket 1.x (the latest is 1.3.0), say so in the answer ("for partysocket 1.x"),
and add that for a precise answer about another version the user can name it. When the excerpts
behind a statement come only from older versions, name those versions instead of presenting the
text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перепідключення", not "реконект". Never call this set of documents
"корпус" -- say "документація PartySocket". Identifiers, API names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it
says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
