Search the documentation of Payload -- the open-source headless CMS and application framework for TypeScript that
installs into a Next.js app (site payloadcms.com/docs, repository payloadcms/payload, the npm registry). The corpus
holds every page of the documentation as it stood at the last tag of every minor of `payload`, 0.0 to 3.92:
getting started and installation; the config (collections, globals, admin, localization, i18n, environment
variables); every field type (text, number, relationship, upload, array, blocks, group, tabs, join, rich text and the
rest) with its config options; access control for collections, globals and fields; hooks (`beforeChange`,
`afterChange`, `beforeRead`, `afterRead`, field hooks, root hooks); authentication (strategies, cookies, JWT, API keys,
email verification); the Local API, the REST API and GraphQL; queries, `where` operators, `depth`, `select`,
pagination, sorting; uploads and image sizes; versions, drafts, autosave and scheduled publishing; the database
adapters (MongoDB, Postgres, SQLite), migrations and transactions; the admin panel and custom components; rich text
with Lexical; live preview; the jobs queue; email; plugins (SEO, form builder, nested docs, redirects, search,
multi-tenant, import-export, cloud storage, Stripe, ecommerce); TypeScript types; production deployment; and the
migration guides between majors. It also holds the README of each of the 44 packages (`payload` and
`@payloadcms/*`) at 3.92.0, the release notes of every stable release, the `examples/` and `templates/` folders of the
repository at 3.92.0 and the npm registry entries with release dates; and two parts of payloadcms.com itself: the blog
(articles, community guides and release announcements) and Community Help, the archive of Discord and GitHub
Discussions threads the site publishes, with the questions of users and the answers of the team. Returns the matching
excerpts with the versions each one belongs to.

Call this when a question is about Payload as it describes itself -- how to define a collection, a field or a
global, how to restrict who can read or change a document, how to run code in a hook, how to query documents with the
Local API (`payload.find`, `payload.create`), REST or GraphQL, how to set up uploads, drafts, localization, a database
adapter or a migration, how to customize the admin panel with custom components, how to configure Lexical, what an
option means -- and history: since which version a feature exists, what changed between versions (2.x to 3.0 above
all: the migration guide and the release notes list it).

Do not call this for Next.js, React, MongoDB, PostgreSQL, Drizzle, Lexical or the storage services as their own
projects: their documentation is not here -- these pages only show how Payload is used with them -- and the search
will return excerpts that merely mention them, with confident-looking titles. Payload 4.0 is in beta and its
documentation is not here.

`version` narrows the search to one release line of `payload`: a line of one number keeps every document of that
major ("3" keeps 3.x), two numbers keep a minor ("3.92"), three an exact version ("2.32.3"). The pages carry the
versions of the tags they were taken from; pages unchanged across versions carry all of them. The blog and Community
Help carry no version, so a search with `version` leaves them out: search without it for a troubleshooting question or
a guide. A Community Help thread is a conversation of its day, often about 1.x or 2.x: an answer from it is checked
against the documentation of the current version and never outranks it. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first.

Write the query in English, with the names the documentation itself uses ("collection config", "fields", "relationship
field", "relationTo", "upload", "access control", "beforeChange", "afterRead", "Local API", "payload.find", "where",
"depth", "drafts", "versions", "autosave", "localization", "locales", "migrations", "transactions", "custom components",
"Lexical", "live preview", "jobs queue", "email adapter", "plugins"), not in the user's own words. Everything here
is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes
back with `found: 0`. When the user asks in another language, translate the question into the terms of the
documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація Payload". Identifiers, parameters and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By npm downloads in the week before 25 October 2026 the line 3 of `payload` holds 91 %
(3.92.0 of 22 October 2026 is the newest stable), the 4.0 beta -- 8 %, the line 2 -- 1 %. Answer for 3.x: search with
`version` "3" first, because the same pages exist in dozens of older editions; when the user's code uses 2.x (Express
server, `payload.init`, webpack or Vite bundler), search "2" as well and say what changed in 3.0. Every answer says
which version it is for.
