# pdf-js — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про роботу з PDF у JavaScript і TypeScript. В одному місці лежить
документація 23 пакетів npm і сторінки Puppeteer про PDF: посібники, довідники API, приклади коду, README стабільних
версій, журнали змін, релізи й історія версій із реєстру npm. Усе лише англійською. Код спільний і лежить у
`../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо один примірник на багато бібліотек

Однієї бібліотеки «для PDF» у JavaScript немає. Одна вміє показати файл на сторінці, інша — створити новий, третя —
змінити наявний, четверта — надрукувати вебсторінку в PDF. Тому питання зазвичай починається із задачі («як заповнити
форму в PDF»), а не з назви бібліотеки. Один пошук по всіх бібліотеках одразу показує, яка з них це вміє і як її
викликати.

| Задача | Бібліотеки в цьому примірнику |
|--------|--------------------------------|
| Показати PDF на сторінці, прочитати його, витягти текст у браузері | PDF.js (`pdfjs-dist`), `react-pdf`, `@react-pdf-viewer/core` |
| Змінити наявний PDF: сторінки, злиття, форми, шрифти, зображення | `pdf-lib`, `@cantoo/pdf-lib`, `@pdf-lib/fontkit`, `pdf-merger-js` |
| Створити PDF з коду | jsPDF з `jspdf-autotable`, PDFKit, pdfmake, `@react-pdf/renderer`, pdfme |
| Перетворити HTML на PDF | Puppeteer (`Page.pdf()`), `html2pdf.js` |
| Витягти текст і дані на сервері | `pdf-parse`, `unpdf`, `pdf2json`, `pdf.js-extract` |
| Показ, анотації, затирання тексту, перетворення одним рушієм | MuPDF.js (пакет `mupdf`) |
| Перетворити сторінки на зображення | `pdf-to-img`, `pdf2pic`, `node-poppler` |
| Підписати PDF цифровим підписом | `@signpdf/signpdf` |

Ця сама карта записана в описі інструмента пошуку, тож модель знає, якими назвами шукати.

**Що є що.** **Worker** — окремий потік, у якому PDF.js розбирає файл, щоб не гальмувати сторінку; його треба
підключити окремо, і це найчастіше питання про `react-pdf`. **Форма** (AcroForm) — поля, які користувач заповнює в
PDF. **Сплющити форму** (flatten) — перетворити заповнені поля на звичайний текст сторінки. **Затирання** (redaction)
— вилучення тексту з файла так, щоб його не можна було відновити. **Відгалуження** (fork) — копія чужого проєкту, яку
далі розвивають інші люди.

## Звідки документація

- **Посібники — з репозиторіїв, на тегах версій.** Сайти PDFKit, pdfmake, pdfme, pdf-parse, `@react-pdf/renderer`,
  MuPDF.js і Puppeteer збираються з файлів у репозиторії. Читач бере ці файли на останньому тегу кожної лінії, тож
  видно, що документація казала в кожній версії. Незмінена сторінка кількох версій — один документ з усіма цими
  версіями.
- **Довідник API PDF.js — з файла типів пакета.** Сайт PDF.js показує довідник лише для поточної збірки. Те саме
  лежить у пакеті npm кожної версії: файл `types/src/display/api.d.ts` з описами JSDoc. Його взято з останньої версії
  кожної мажорної лінії 2–6; розділ пошуку — одне оголошення («function getDocument», «class PDFPageProxy»).
- **Довідник API pdf-lib — з репозиторію сайту.** Сторінки pdf-lib.js.org лежать у репозиторії `Hopding/pdf-lib-docs`:
  сторінка на клас, розділ на метод.
- **Довідник API jsPDF — сторінки JSDoc із теки `docs`.** З кожної сторінки знято меню з переліком усіх методів і
  рядки «Source: файл, рядок N», бо вони мінялися з кожною версією й не несли змісту.
- **Довідник MuPDF.js розбирає власний читач.** У документації MuPDF кожен метод записано директивою Sphinx (`..
  method:: PDFPage.prototype.applyRedactions(...)`), а не заголовком. Спільний читач лишав би підпис методу звичайним
  рядком, і сторінка на 134 методи ділилася б на п'ять розділів. Читач `ghdocs-history-jsdomain` робить кожен метод
  окремим розділом.
- **README — головна документація багатьох пакетів.** У `pdf-lib`, `react-pdf`, `unpdf`, `jspdf-autotable` і всіх
  дрібних пакетів окремого сайту немає, і все написано в README. Реєстр npm віддає README лише найновішої версії, тому
  README кожної версії читається з репозиторію на коміті її публікації, а де це неможливо — з самого пакета.
- **Приклади коду.** З PDF.js і pdfmake взято теку `examples`. У `@react-pdf/renderer` сторінка документації показує
  приклад окремим компонентом, а сам код лежить поруч у файлі `.usage.jsx`; ці файли взято окремим джерелом.
- **Вікі.** Узято сторінки вікі PDF.js (питання й відповіді, опції переглядача, підключення до сайту), `react-pdf`
  (питання, рецепти, посібники переходу між мажорними версіями) і PDFKit.

## Межі, про які треба пам'ятати

- Довідник API PDF.js узято лише з останньої версії кожної мажорної лінії, а не кожної мінорної: пакет однієї версії
  важить близько 10 МБ. Що змінилося між мінорними версіями, кажуть релізи.
- Довідник API pdf-lib один, для версії 1.17.1. Окремого довідника `@cantoo/pdf-lib` немає: є його README і журнал
  змін.
- У `@react-pdf-viewer/core` відкритої документації в репозиторії немає: сайт react-pdf-viewer.dev збирається не з
  нього. Є лише журнали змін із прикладами коду.
- У `@pdfme/generator` README порожній, тому взято README і документацію всього проєкту pdfme.
- З Puppeteer узято лише сторінки про PDF. Решти його документації тут немає; Playwright має власний примірник
  `playwright`.
- Старий посібник PDFKit ліній до 0.10 (файли `.coffee.md`) не береться.
- Файли прикладів pdfmake з вбудованими зображеннями (понад 40 000 байтів) не беруться.
- П'ять сторінок вікі pdfmake не взято: у них лише рядок «сторінку перенесено в документацію».
- У документації pdfmake лишилися службові позначки шаблону сайту виду `{{% alert %}}` навколо приміток.
- Передрелізи не беруться.
- Самого формату PDF (специфікація ISO 32000) тут немає. Утиліти poppler і Ghostscript — у примірнику `doc-tools`.
  PyMuPDF, бібліотека MuPDF мовою C і утиліта `mutool` — у примірнику `mupdf`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/pdf-js-corpus-2026-11-20.tar.gz` (тексти, паспорт і сховище сирого
`raw/`; перед видаленням текстів розпакований окремо й звірений із диском), копія —
`C:\Distr\pdf-js-corpus-2026-11-20.tar.gz` (`/mnt/c/Distr/…` з WSL), SHA-256 обох звірено. В історії git текстів немає
ніде. Архів важить близько 250 МБ: у сховищі сирого лежать пакети npm, з яких бралися README і файли типів.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/pdf-js/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/pdf-js-corpus-РРРР-ММ-ДД.tar.gz -C instances/pdf-js corpus raw
find instances/pdf-js/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/pdf-js/raw
gzip -9 -c instances/pdf-js/index/passages.json > instances/pdf-js/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Новий архів копіюють у `C:\Distr` і звіряють за SHA-256 (`tools/mirror-archives.sh --apply`),
і лише тоді видаляють попередній з обох місць, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/pdf-js-corpus-2026-11-20.tar.gz -C instances/pdf-js
./df pdf-js smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/pdf-js/index/passages.json.gz`, далі
`./df pdf-js vectors` заллє колекцію Qdrant.

## Установка venv

Власний venv цьому примірнику не потрібен: `./df pdf-js …` бере спільне середовище з кореня репозиторію (`.venvs/cpu`
або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md, розділ «Спільне
середовище». Свій `.env` примірник тримає в `instances/pdf-js/.env` (`cp .env.example .env`; для кроку `ask` потрібен
`ANTHROPIC_API_KEY`); `GITHUB_TOKEN`, якого немає в цьому `.env`, береться з кореневого.

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df pdf-js sources --why    # перелік джерел і білий список
./df pdf-js refresh          # усе: близько пів години мережею
./df pdf-js manifest         # оновити паспорт
./df pdf-js setup            # Qdrant чи пошук лише по словах
./df pdf-js vectors          # залити корпус у docs-pdf-js
./df pdf-js smoke            # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df pdf-js serve   # порт 8997
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8997/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user pdf-js-docs http://127.0.0.1:8997/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `pdf-js-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у [README
примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
