# Оновлення корпусу pdf-js

README пакетів (`*-readme`) і реєстр (`npm-*`) беруть версії з опису пакета в реєстрі npm, тож новий реліз потрапляє
туди сам. Релізи GitHub (`*-releases`) читаються щоразу заново з API, журнали змін (`*-changelog`) — з основної гілки
репозиторію. Передрелізи не беруться.

Руками оголошено:

- **Документація на тегах** (`pdfjs-site`, `pdfjs-readme`, `pdfjs-examples`, `jspdf-api`, `pdfkit-docs`,
  `pdfmake-examples`, `pdfparse-docs`, `mupdf-reference`, `mupdf-guide`, `puppeteer-pdf`, `pdfme-docs`,
  `pdfme-readme`): поле `tags` — об'єкт «тег → мітка версії з префіксом пакета», від найновішого, по одному тегу на
  лінію. Нову версію тієї самої лінії ставлять замість старої, нову лінію дописують першим рядком.
- **Довідник API PDF.js** (`pdfjs-api`): поле `skip_versions` — вираз, що пропускає всі версії, крім названих. Нову
  версію дописують у перелік у дужках.
- **Документація на коміті** (`pdflib-api`, `pdfmake-docs`, `pdfmake-docs-01`, `renderer-docs-v1` …
  `renderer-docs-v4`, `renderer-usage`, `signpdf-repo`, `viewer-changelogs`, перший рядок `tags` у `mupdf-guide`):
  ключ у `tags` — хеш коміту, бо ці репозиторії тегів не ставлять. Щоб узяти свіжий стан, хеш замінюють на поточний
  (`git ls-remote <адреса> HEAD`).
- **Сторінки вікі** (`pdfjs-wiki-*`, `reactpdf-wiki-*`, `pdfkit-wiki-*`): кожна сторінка — окреме джерело з полем
  `version`, де стоїть найновіша версія пакета на день збирання. Нову сторінку, наприклад посібник переходу
  `react-pdf` на наступну мажорну версію, дописують окремим джерелом.
- **Новий пакет** — джерела README і `npm-versions` за зразком наявних, з власним префіксом версії; префікс дописують
  у `prompts/search.txt` і `prompts/agent.txt`, а пакет — у карту задач там само й у таблиці README.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія пакета

```
./df pdf-js refresh pdfkit-docs pdfkit-readme pdfkit-changelog npm-pdfkit   # приклад для PDFKit, після правки tags
./df pdf-js refresh --missing    # джерела, яких не названо, лише докачуються
./df pdf-js manifest
./df pdf-js vectors
./df pdf-js smoke
# Ctrl+C у терміналі з serve, і знову: ./df pdf-js serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінна сторінка дописує нову версію в рядок `# версія:`).

Ім'я файла сторінки містить початок хеша її тексту, тому змінена сторінка лягає новим файлом поруч зі старим. Після
заміни тегу в `tags` файли, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш ніж
рахувати вектори: інакше пошук знаходив би сторінку версії, якої в переліку вже немає. Сховище сирого `raw/`
повертається з архіву разом із текстами, тож після правки читача тексти перебудовуються без мережі: `./df pdf-js build
<id>`.

Якщо вийшла нова мажорна версія однієї з бібліотек:

- у `prompts/search.txt` (абзаци про `version` і «Which version to search first») та `prompts/agent.txt` замінити
  номер лінії й дописати, що нова лінія ламає, якщо це сказано в її посібнику переходу;
- у таблиці пакетів README оновити версію;
- у `checks.json`, у десятці `quality_model`, замінити мітку лінії й звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторіїв і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального
довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей): `./df pdf-js quality --show`, порівняння обох
десяток з попереднім результатом, розбір промахів, правка промпту, знову замір. Останній результат — у README, розділ
«Скільки цього».
