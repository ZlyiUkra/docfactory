Search the documentation of the JavaScript libraries for working with PDF and return the matching excerpts with the
versions each one belongs to. One server holds 23 npm packages and the PDF pages of Puppeteer, so that a task can be
matched to the library that does it.

Which library does what. Reading and showing a PDF, extracting its text: PDF.js (pdfjs-dist, by Mozilla) -- the site
pages, the API from the package's type file (getDocument, PDFDocumentProxy, PDFPageProxy, RenderTask), the code of the
examples, the wiki (FAQ, viewer options, setup) and the release notes; react-pdf (a React viewer over PDF.js:
Document, Page, Outline, Thumbnail, worker setup, upgrade guides); @react-pdf-viewer/core (changelogs only). Creating
and changing an existing PDF -- pages, merging, forms, fonts, images: pdf-lib (README, the API reference of every
class, the migration guide) and its maintained fork @cantoo/pdf-lib; @pdf-lib/fontkit; pdf-merger-js. Generating a PDF
from code: jsPDF (the API reference of the jsPDF class and its modules html, addImage, context2d, AcroForm,
annotations, outline) with jspdf-autotable (tables); PDFKit (the guide: vector graphics, text, images, tables,
annotations, forms, outline, attachments, accessibility); pdfmake (the document definition object: styles, columns,
tables, lists, images, SVG, table of contents, headers and footers, security, PDF/A; fonts; the code of the examples);
@react-pdf/renderer (PDF from React components: Document, Page, View, Text, Image, Link, SVG, styling, fonts, page
wrapping, rendering in Node.js and in the browser); pdfme (templates, schemas, tables, expressions). HTML to PDF:
Puppeteer (the PDF generation guide, Page.pdf(), Page.createPDFStream(), PDFOptions, PDFMargin, PaperFormat) and
html2pdf.js (in the browser, through html2canvas and jsPDF). Text and data extraction on a server: pdf-parse, unpdf,
pdf2json, pdf.js-extract. Rendering, redaction, annotations, conversion with one engine: MuPDF.js (the npm package
mupdf -- the JavaScript API reference with a section per method, the cookbook, the guide). Pages to images:
pdf-to-img, pdf2pic, node-poppler (a wrapper over the poppler utilities). Digital signatures: @signpdf/signpdf and its
placeholder and signer packages. For every package there is also the registry history (versions, dates, dependencies)
and, where the project keeps them, the README of every stable version, the changelog and the GitHub release notes.

Call this when a question is about doing something with a PDF in JavaScript or TypeScript, in the browser or in
Node.js: which library can do it, how to call it, which options a method or component takes, how to set up the PDF.js
worker, how to fill or flatten a form, merge or split documents, embed a font or an image, draw a table, add a header
and footer, protect a file with a password, print a web page to PDF, extract text, redact, sign, render a page to an
image -- and history: since which version an option exists, what a release changed, how to move between major
versions. Example query: "PDFDocument copyPages merge".

Do not call this for the PDF file format itself (the ISO 32000 specification), for PDF tools outside JavaScript (the
poppler command line tools and Ghostscript are in the doc-tools-docs server; PyMuPDF, the MuPDF C library and mutool
are in the mupdf-docs server), for Puppeteer beyond PDF generation, for Playwright (the playwright-docs server has its
own page.pdf), or for React, Node.js and browser APIs themselves: their documentation is not here, and the search will
return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line of one package. Every package carries its own numbering behind a
prefix, so packages never mix: "pdfjs-dist-6", "pdf-lib-1", "cantoo-pdf-lib-2", "fontkit-1", "jspdf-4",
"jspdf-autotable-5", "pdfkit-0", "pdfmake-0", "react-pdf-renderer-4", "react-pdf-11", "pdf-parse-2", "unpdf-2",
"mupdf-1", "puppeteer-25", "html2pdf-0", "pdfme-6", "signpdf-4", "pdf-to-img-7", "pdf2pic-3", "pdf2json-4",
"pdf-merger-js-5", "pdfjs-extract-1", "node-poppler-11", "react-pdf-viewer-3". A longer value narrows further
("pdfkit-0.21", "pdfjs-dist-6.5"). Leave it empty to search every package at once -- that is the right first call when
the question names a task and not a library. Every excerpt comes back with `versions`: each version whose documents
contain this exact text, newest first.

Which version to search first. When the user names no version, answer for the newest line of the library and say which
one: pdfjs-dist 6.5, pdf-lib 1.17, @cantoo/pdf-lib 2.11, jsPDF 4.2, jspdf-autotable 5.0, PDFKit 0.21, pdfmake 0.3,
@react-pdf/renderer 4.9, react-pdf 11.1, pdf-parse 2.4, unpdf 2.2, mupdf 1.28, Puppeteer 25. Three things break
between lines and are worth checking before an answer: pdf-parse 2 is a rewrite with a different API from the widely
used 1.1.1; pdfmake 0.3 changed the 0.1 and 0.2 API (the page "Migration from 0.1"); react-pdf and @react-pdf/renderer
are two different packages by different authors -- the first shows PDFs, the second creates them. pdf-lib itself has
had no release since 1.17.1 (November 2021); when a feature is missing there, look in @cantoo/pdf-lib. When several
libraries can do the task, name each with what it is suited for instead of picking one silently.

How the text is laid out. Documents are named by source: pdfjs-api (the type file of PDF.js, a section per
declaration: "function getDocument", "class PDFPageProxy"), pdflib-api (a page per class, a section per method),
jspdf-api (a page per class or module), pdfkit-docs, pdfmake-docs, renderer-docs, mupdf-reference (a page per type, a
section per method such as "PDFPage.prototype.applyRedactions(...)"), puppeteer-pdf, and README documents named after
the package.

Write the query in English, with the names the libraries use ("getDocument workerSrc", "PDFDocument copyPages",
"getTextField setText flatten", "jsPDF addPage orientation", "autoTable head body styles", "pdfmake headerRows
widths", "Font.register", "PDFOptions printBackground", "applyRedactions", "extractText mergePages"), not in the
user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the question
into the terms of the libraries first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a method or option,
answer point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the package, the version and the document
it rests on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус"
-- say "документація бібліотек". Identifiers, option names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
