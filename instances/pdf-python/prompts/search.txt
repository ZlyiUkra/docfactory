Search the documentation of the Python libraries for working with PDF files and return the matching excerpts with the
versions each one belongs to. This server answers "which Python library does this with a PDF and how": reading and
changing existing files, extracting text and tables, creating new files from code or from HTML, rendering pages to
images, filling forms and signing.

What is here, by task. Read and change a PDF: pypdf (the site of the last release of every major line 3-7, the
package code of the lines 1-7, the change log) and its old name PyPDF2 (the site of the lines 1.28, 2.12 and 3.0);
pikepdf, built on qpdf (the site of 10.18, the docs folder of the major lines 1-9, the code with the `_core.pyi`
signatures); pdfrw; the command line tool pdfly. Extract text and tables: pdfplumber (the README, which is its whole
documentation, of the lines 0.5-0.11), pdfminer.six (the site, the docs of 2019-2025, the code of 2016-2026), Camelot
(the site of 2.1, the docs of 0.7-2.0), tabula-py (the site of 2.5-2.11, the docs of 1.4-2.4), pdftotext. Create a
PDF: ReportLab (the User Guide chapters from docs.reportlab.com, installation, the "What's new" pages of 2.2-5.1, the
User Guide source and the package code of 3.5-5.1), fpdf2 (the docs folder of 2.2-2.9 from which its site is built,
the code docstrings of 2.0-2.9), borb (README, the examples book, the code of 2.1 and 3.0), svglib (SVG to a ReportLab
drawing). HTML to PDF: WeasyPrint (the site of every version 52-70 and of 0.42, the docs of 43-51, the code of nine
versions), xhtml2pdf (the site of 0.2.28, the docs of 0.2.8-0.2.17), pdfkit (the wkhtmltopdf wrapper). Render pages to
images: pypdfium2 (the site of the lines 5 and 4, the README of 1-5), pdf2image (the site of 1.17, the README of
1.5-1.17). Forms: PyPDFForm (the docs folder of the major lines 1-6). Digital signatures: pyHanko (the site of 0.38,
the guides of 0.5-0.37, the code of eight lines). Conversion: pdf2docx (PDF to Word), img2pdf (images to PDF). Each
library also has its change log or GitHub release notes and its PyPI history with the README.

Call this when a question is about doing something with a PDF in Python: how to merge, split, rotate, crop, encrypt
or decrypt pages; how to extract text with layout, words with coordinates, or tables into a DataFrame; how to draw
text, tables, images and charts into a new PDF; how to turn HTML and CSS into a PDF and which CSS is supported; how
to render a page to PNG; how to fill or create form fields; how to sign a PDF or validate a signature; what the
parameters of a function are and what their defaults are -- and history: since which version a parameter exists,
what a release changed, what an old name is called now. Example query: "PdfWriter append pages merge".

Do not call this for PyMuPDF and MuPDF (they are in the mupdf-docs server), for OCRmyPDF and Tesseract (the
tesseract-docs server), for PDF libraries of JavaScript (pdf-js-docs), for the command line tools poppler,
Ghostscript and qpdf themselves (doc-tools-docs), for the PDF specification, or for document parsers built on machine
learning (Docling, Marker, Unstructured): their documentation is not here, and the search will return excerpts that
merely mention them, with confident-looking titles.

`version` narrows the search to one release line of one library. Each library carries its own numbering behind a
prefix: "pypdf-7.1", "pypdf-5", "pypdf2-3.0", "pypdf2-1.28", "pdfplumber-0.11", "pdfminer-20260107", "reportlab-5.1",
"reportlab-4.4", "fpdf2-2.9", "pikepdf-10.18", "weasyprint-70", "weasyprint-52", "borb-3.0", "pypdfium2-5.15",
"camelot-2.1", "tabula-2.11", "pdf2image-1.17", "xhtml2pdf-0.2", "pyhanko-0.38", "pypdfform-6.2", "pdfly-0.7",
"pdf2docx-0.5", "pdfkit-1.0", "pdfrw-0.4", "svglib-2.4", "pdftotext-3.0", "img2pdf-0.6", "fpdf-1.7". A longer value
narrows further ("pypdf-6.21.4"). Leave it empty to search every version of every library at once. Every excerpt
comes back with `versions`: each version whose documents contain this exact text, newest first. The pages of
docs.reportlab.com and the borb examples book carry no version and are found only by a search without `version`.

Which version to search first. When the user names no library, search without `version` and compare what comes
back; when the user names a library but no version, answer for its newest line and say so. Weekly downloads from
PyPI in November 2026, to tell the widely used from the rare: pypdf 51.6 million, pypdfium2 30.4, ReportLab 24.0,
pdfminer.six 19.5, pdfplumber 16.5, WeasyPrint 11.2, fpdf2 7.0, pdf2image 6.2, pikepdf 3.7, PyPDF2 3.5, Camelot 1.6,
pyHanko 1.4, svglib 1.4, pdfkit 1.1 million; xhtml2pdf 933 thousand, img2pdf 911, pdfrw 872, tabula-py 467, fpdf 411,
pdf2docx 363, borb 173, pdftotext 41, PyPDFForm 41 thousand; pdfly about 500. PyPI gives no reliable figures by
version of a package. Names that changed, with the release that did it -- check them before an answer: PyPDF2 1.28
and 2.0 renamed `PdfFileReader`, `PdfFileWriter` and `PdfFileMerger` to `PdfReader`, `PdfWriter` and `PdfMerger`, and
PyPDF2 3.0.0 removed the old names; pypdf 3.1.0 (23 December 2022) is PyPDF2 3.0.0 under the name `pypdf`, and PyPDF2
receives no more updates; pypdf 5.0.0 removed `PdfMerger` (use `PdfWriter`). fpdf2 2.5.2 deprecated the parameter `ln`
of `cell()` and `multi_cell()` in favour of `new_x` and `new_y`; the package `fpdf` (PyFPDF 1.7.2) is the abandoned
predecessor of `fpdf2` and both import as `fpdf`. WeasyPrint 53 replaced Cairo with its own PDF generator. ReportLab
4.0 made `rlPyCairo` the default backend for bitmap output in place of `_renderPM`.

How the text is laid out. Documents are named by library and source: "<library>-site" (the rendered documentation
site: guides and the API reference), "<library>-docs" and "<library>-readme" (the same pages or the README at older
tags), "<library>-code" (the package code at tags, one section per class and function, for checking signatures and
defaults), "<library>-changelog", "<library>-release", "pypi-<package>". Libraries whose reference lives in
docstrings (fpdf2, pdfplumber, PyPDFForm, borb, pdfrw) are answered from the "-code" documents.

Write the query in English, with the names the libraries use ("PdfReader extract_text", "PdfWriter append encrypt",
"extract_table table_settings vertical_strategy", "LAParams char_margin line_margin", "read_pdf flavor lattice",
"SimpleDocTemplate Paragraph Table TableStyle", "canvas drawString setFont", "FPDF multi_cell new_x new_y",
"write_html", "HTML write_pdf stylesheets", "@page margin size", "render to_pil scale", "convert_from_path dpi
poppler_path", "PdfWrapper fill", "signers PdfSigner sign_pdf", "pikepdf Pdf open save linearize"), not in the user's
own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word
index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the question
into the terms of the library first, then search.

Answer in the language the user wrote in. When the question is which library to choose, name the candidates the
excerpts support, what each one does and does not do, and its licence when the excerpts state it. When the question
is about the history of a function or parameter, answer point by point: since which version it exists; what changed
in later versions; and how it stands in the current version. Every point names the library, the version and the
document it rests on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian,
write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian
word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація бібліотек PDF для Python". Identifiers, parameter names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back, not
out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
