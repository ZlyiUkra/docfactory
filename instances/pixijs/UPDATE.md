# Оновлення корпусу pixijs

README (`npm-readme-*`) і реєстр (`npm-*`) беруть версії з опису пакетів у реєстрі npm, тож новий реліз будь-якого з
одинадцяти пакетів потрапляє туди сам, а релізи GitHub (`releases-*`) читаються з API щоразу заново. Передрелізи не
беруться (`skip_versions: "-"` у README, `"stable": true` у релізах).

Руками оголошено:

- **Посібник PixiJS 8** (`guides`): поле `tags` — останній тег кожної мінорної, найновіший першим
  (`"v8.23.0": "8.23.0"`). Нова мінорна — новий рядок на початку; новий латковий реліз тієї самої мінорної — заміна
  тегу в її рядку. Нова сторінка посібника потребує рядка в полі `site` з її адресою на pixijs.com: адреси звіряють
  із `https://pixijs.com/sitemap.xml`.
- **Приклади й настанови** (`examples`, `skills`): той самий перелік тегів, що в `guides`, але лише від 8.17 і 8.20.
- **Довідник API 8** (`api-8`): адреси сторінок стоять у полі `within` поіменно, з номером версії в кожній
  (`…/v8.23.0/docs/scene.Sprite.html.md`). Для нової версії перелік складають заново з `https://pixijs.com/llms.txt`:
  беруть посилання, де в імені файла є крапка після назви розділу (`scene.Sprite`), а сторінки посібника
  (`scene.html.md`, `core-concepts-1.html.md`) пропускають. Поле `version` міняють на нову версію. Файли старої версії
  переносять в окрему теку поза корпусом, перш ніж рахувати вектори: в іменах документів стоїть номер версії, і поруч
  лягли б два довідники.
- **Довідники старих ліній** (`api-7`, `api-6`, `api-5`, `api-5-namespaces`, `api-4`): лінії закриті, їх не
  оновлюють. Якщо вийде латка, міняють номер версії в адресах і в полі `version`.
- **Знімки без тегів** (`guides-site`, `guides-7`, `examples-7`, `tutorials-*`, `blog`, `react-docs`, `react-docs-7`):
  поле `tags` тримає рядок «SHA коміту → версія». Новий SHA дає `git ls-remote https://github.com/pixijs/pixijs.com
  main` (для Pixi React — `pixijs/pixi-react`), мітку — `latest` пакета в реєстрі npm. Старий рядок не лишають.
- **PixiJS 3D** (`pixi3d`): номер версії стоїть в адресі в `within` (`3d.pixijs.download/v0.1.0/docs/`) і в полі
  `version` (`3d-0.1.0`); нову версію називає `https://pixijs.com/3d/llms.txt`.
- **Документація додатків** (`layout-docs`, `devtools-docs`): поле `tags` — останній тег репозиторію.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

Джерела незалежні, тому їх оновлюють блоками в окремих терміналах — так удвічі швидше, ніж одним прогоном:

```
./df pixijs refresh guides skills examples                      # блок 1: основний репозиторій
./df pixijs refresh api-8                                       # блок 2: довідник API
./df pixijs refresh npm-readme-pixi npm-pixi releases-pixi      # блок 3: пакет і релізи
./df pixijs refresh --missing    # після блоків: джерела, яких не названо, лише докачуються
./df pixijs manifest
./df pixijs vectors
./df pixijs smoke
# Ctrl+C у терміналі з serve, і знову: ./df pixijs serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінна сторінка дописує нову версію в рядок `# версія:`). Документи редакцій, яких у
новому прогоні вже немає, лишаються в теці — їх переносять в окрему теку поза корпусом руками, перш ніж рахувати
вектори. Сховище сирого `raw/` повертається з архіву разом із текстами, тож після правки читача тексти перебудовуються
без мережі: `./df pixijs build <id>`.

Якщо змінилися найпоширеніші лінії (на 18.11.2026 — PixiJS 8, близько 76 % завантажень; `@pixi/react` 8, близько 84 %):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінії за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"8"` і `"react-8"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторіїв і сторінок релізів: без нього API
GitHub дає 60 звернень на годину, а одних релізів тут десять репозиторіїв.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df pixijs quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Останній результат — у README, розділ «Скільки цього».
