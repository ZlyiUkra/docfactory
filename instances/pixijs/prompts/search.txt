Search the PixiJS documentation and return the matching excerpts with the versions each one belongs to.
What is here: the PixiJS 8 guides of pixijs.com at the last release of every minor line 8.10 to 8.23 -- getting
started, concepts (architecture, scene graph, render loop, render groups, render layers, environments, garbage
collection, performance tips), components (Application, renderers, Assets with bundles, manifests and background
loading, scene objects: Container, Sprite, Graphics, Text, BitmapText, HTMLText, SplitText, Mesh,
ParticleContainer, NineSliceSprite, TilingSprite; textures, filters, events and interaction, accessibility, color,
math, ticker), the migration guides v5 to v8; the API reference of PixiJS 8.23.0, one page per class, interface
and function; the API reference of the last release of the older lines 7.4.3, 6.5.10, 5.3.12 and 4.8.9, one
page per class and namespace (PIXI.Sprite, PIXI.Container, PIXI.Graphics, PIXI.Loader, PIXI.utils…); the code of
the official examples of PixiJS 8.17 to 8.23 and of PixiJS 7; the pixijs.com tutorials with the text and the
code of every step; the PixiJS 7 guides; the blog; the official PixiJS skills written for AI assistants (how to
do a task properly and what to avoid); Pixi React -- the documentation of @pixi/react 8 and 7 (react.pixijs.io:
Application, pixi components, custom components, extend, hooks useApplication, useExtend, useTick, TypeScript;
in 7: Stage, Sprite, Container, Graphics, Text, hooks, react-spring); PixiJS 3D 0.1.0 (open beta): guides and
API reference; the add-on packages @pixi/ui, @pixi/sound, @pixi/layout (with its documentation), @pixi/devtools
(with its documentation), @pixi/tilemap, @pixi/particle-emitter, @pixi/gif and pixi-viewport; the README of
every stable version and the npm registry history (versions, dates, peer dependencies) of pixi.js, @pixi/react,
@inlet/react-pixi (the name of Pixi React before 2023) and the add-ons; the GitHub release notes of all of them.

Call this when a question is about PixiJS: creating an Application and its renderer (WebGL, WebGPU, canvas),
the scene graph (Container, addChild, zIndex, masks, render groups), sprites and textures, loading with Assets,
drawing with Graphics, text, meshes and shaders, filters, pointer events and interaction, the ticker and
animation, performance and memory, migrating between major versions -- about Pixi React: the Application
component, extend, pixi components in JSX, hooks, refs -- about PixiJS 3D, and about the add-ons: UI components,
sound, flexbox layout, devtools, tilemaps, particles, GIFs, a zoomable viewport -- and history: since which
version a class or option exists, what changed in a release.

Do not call this for the browser Canvas API, WebGL or WebGPU themselves (CanvasRenderingContext2D,
WebGLRenderingContext, GPUDevice) -- they are in the mdn-docs server -- nor for React itself, for three.js (the
threejs-docs server), for Konva (the konva-docs server), for Phaser, Fabric.js or other libraries, for Spine and
other third-party plugins, or for JavaScript or TypeScript language questions: their documentation is not here,
and the search will return PixiJS excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "8" keeps every PixiJS 8.x document, "8.23" every 8.23.x, "7"
the guides, examples, API reference, README and release notes of PixiJS 7, "6", "5" and "4" the same for the
older lines; leave it empty to search everything. Everything that is not pixi.js itself carries its own
numbering with a prefix, so it never mixes with the PixiJS lines: "react-8" and "react-7" (@pixi/react; "react-6"
and lower is @inlet/react-pixi), "3d-0.1" (PixiJS 3D), "ui-2", "sound-6", "layout-3", "devtools-2", "tilemap-5",
"particle-emitter-5", "gif-3", "viewport-7". Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names PixiJS itself uses ("Application init", "Assets.load", "Sprite
anchor", "Graphics fill stroke", "Container addChild zIndex", "eventMode pointerdown", "Ticker add", "useTick",
"extend"), not in the user's own words. For the old lines the classes live in the PIXI namespace: write
"PIXI.Sprite", "PIXI.Loader". Everything here is English -- the excerpts, the word index and the meaning index
alike -- and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any
other non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into PixiJS terms first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a class, method
or option, answer point by point: since which version it exists; what changed in later versions; what prompted
the change, if the excerpts say so; and how it stands in the current version. Every point names the version and
the document it rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and
the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація PixiJS". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. PixiJS 8 carries about 76% of the weekly downloads, PixiJS 7 about 13%, PixiJS 6
about 9%; @pixi/react 8 about 84%. PixiJS 8 changed the API deeply (async `app.init`, single `pixi.js` import,
new Graphics API, Assets instead of Loader), so code for 7 and for 8 is not interchangeable. Search with
`version` "8" for a question about how to do something, and "react-8" when it is about Pixi React; if the user
names an older PixiJS or the code uses the `PIXI.` namespace, the Loader or `new Application({...})` without
`init`, search that line ("7", "6", "5", "4"). Search without `version` when the question is about history or
when the line gave nothing. Every answer says which version it is for; when the user did not name one, answer
for PixiJS 8.23 and @pixi/react 8.0 and say so. When the excerpts behind a statement come only from older
versions, name those versions instead of presenting the text as current.
