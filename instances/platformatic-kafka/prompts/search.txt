Search the documentation of @platformatic/kafka -- a modern Apache Kafka client for Node.js written in pure TypeScript
by Platformatic, with a producer, a consumer that returns message streams, an admin client, transactions, metrics and
diagnostics channels (repository platformatic/kafka, package @platformatic/kafka on npm). The corpus holds the `docs/`
of the repository taken from the tag of every minor version from 0.1 to 2.14 (base client options: bootstrap brokers,
SASL and TLS, timeouts, retries, metadata; the producer with `send`, idempotence, acks, compression, partitioners and
serializers; the consumer with `consume`, message streams, offsets and commits, consumer groups and rebalancing,
deserializers; the admin client; transactions; metrics; diagnostics channels; the supported KIPs; Confluent Schema
Registry; troubleshooting); the README of every stable version of the package; the release notes of GitHub for every
stable version; and the npm registry history of the package (date of every version, dist-tags, the Node.js
requirement). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about @platformatic/kafka as it describes itself -- how to create a `Producer`,
`Consumer` or `Admin`, what an option and its default are, how a `MessagesStream` is consumed and how offsets are
committed, how serializers and deserializers work, how to run a transaction, which diagnostics channels and metrics
exist, which KIPs are supported -- and above all history and compatibility: since which version an option or method
exists, what changed between versions (every release note lists the merged changes, the README of every version shows
the API of that version), which Node.js a version requires, and when every version came out.

Do not call this for Apache Kafka itself (broker and topic configuration, replication, the protocol, KRaft), KafkaJS,
the Confluent client @confluentinc/kafka-javascript, node-rdkafka, the Platformatic application server, Watt or
Node.js: their documentation is not here -- these pages only show how this client talks to them -- and the search will
return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. The client carries plain numbers: a line of one number keeps every
document of that major ("1" keeps 1.0.0 to 1.35.0), two numbers keep a minor ("2.11"), three an exact version
("2.12.1"); the pages of `docs/` carry the version of the tag they were taken from (the last patch of every minor).
Leave `version` empty to search everything, including text that carries no version. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- a page that stayed the same across
versions is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("Producer", "Consumer", "Admin",
"MessagesStream", "consume", "send", "commit", "autocommit", "groupId", "serializers", "deserializers",
"stringSerializers", "idempotent", "acks", "compression", "transactions", "diagnostic channels", "metrics",
"bootstrapBrokers", "sasl"), not in the user's own words. Everything here is English -- the excerpts, the word index
and the meaning index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the user
asks in another language, translate the question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація @platformatic/kafka". Identifiers, option names and titles stay in English, spelled exactly as
the documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt
was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads on npm (October 2026) 2.11.0 leads with about 34 %, 2.9.0 has
about 21 %, 2.14.0 -- the newest, of 7 October 2026 -- about 14 % and 2.2.3 about 14 %; the line 2 holds almost all of
them, and 1.35.0 is kept under the dist-tag `v-1.x`. Answer how-to questions for 2.11: search `version` "2.11", and
when the question touches what is new, search "2.14" too and say where they differ. Search without `version` when
the question is about history, or when the line gave nothing. Every answer says which version it is for; when the
excerpts behind a statement come only from older versions, name those versions instead of presenting the text as
current.
