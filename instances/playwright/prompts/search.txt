Search the documentation of Playwright, in English: the docs folder of the microsoft/playwright
repository on the last release of every minor line from 0.10 to 1.63 -- the guides (locators,
assertions and auto-waiting, actionability, network and route, authentication, tracing,
screenshots and videos, emulation, frames, dialogs, downloads, clock, accessibility testing,
ARIA snapshots, CI and Docker), Playwright Test (configuration, fixtures, projects,
parallelism and sharding, retries, reporters, annotations, visual comparisons, component
testing, the UI mode, codegen, test agents) and the API reference with one file per class
(class-page, class-locator, class-browsercontext, class-locatorassertions...) where every
member says since which version it exists, plus the JavaScript release notes; the site
playwright.dev for Node.js as of the current stable release, with JavaScript and TypeScript
examples only; the Playwright MCP server and the Playwright CLI for agents; the README of every
stable version of playwright, @playwright/mcp and @playwright/cli; their GitHub release notes;
and the npm registry list of every published version of playwright, @playwright/test,
@playwright/mcp and @playwright/cli. Returns the matching excerpts with the versions each one
belongs to.

Call this when a question is about end-to-end and browser testing with Playwright: page.goto,
getByRole and the other locators, expect(locator).toBeVisible and the web-first assertions,
auto-waiting and actionability, page.route and network mocking, storageState and
authentication, test.describe, fixtures, playwright.config, projects, webServer, trace viewer,
toHaveScreenshot, codegen, debugging, running on CI and in Docker, component tests -- and
above all when it is about versions: since which version a method or option exists, what
changed between versions, and which browsers and Node.js versions a release needs. Example
query: "toHaveScreenshot maxDiffPixels".

Do not call this for the test runners and libraries used next to Playwright (Jest, Vitest,
Testing Library, MSW), for Selenium, Cypress or Puppeteer, for the browsers' own DevTools
Protocol, or for the web platform itself: their documentation is not here, and the search
will return Playwright excerpts that merely mention them, with confident-looking titles.

The repository docs are written once for every language Playwright supports: a shared page
may carry Python, Java and C# examples next to the JavaScript one, and some sections apply to
one language only. The pages made only for those languages are not here. Answer with the
JavaScript or TypeScript form; when only another language's example came back, look for the
JavaScript one or say that the excerpt shows another language.

`version` narrows the search to one minor line: "1.63" keeps Playwright 1.63.x. @playwright/mcp
(0.0.x) and @playwright/cli (0.1.x) have their own numbers. The title of every excerpt names its
package, so read it. Leave `version` empty to search everything. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- text that
stayed the same across versions is returned once, with all of them listed, so the list itself
shows from which to which version the documentation said exactly this.

Which version to search first. For a question about how to do something today, pass the line
of the user's project or the most downloaded line -- "1.63" in the week the documentation was
collected: without it, the many editions of the same page, which differ by a line or two, fill
every place with older text. Search without `version` for history and migrations. For "since
which version", the API reference states it next to each member, and the release notes name
the version that introduced a feature.

Where the documentation lives. Repository pages are named by their path (docs-src-locators,
docs-src-test-assertions-js, docs-src-api-class-page, docs-src-test-configuration-js,
docs-src-release-notes-js); site pages by their path in nodejs/versioned_docs/version-stable;
MCP and CLI pages by mcp-... and agent-cli-.... README documents, release notes and registry
documents are titled by package.

Write the query in English, with the names the documentation uses (page.getByRole,
locator.click, expect(locator).toHaveText, page.route, browserContext.storageState,
test.use, testInfo, defineConfig, webServer, fullyParallel, toHaveScreenshot). Everything here
is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into Playwright terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. Every answer says which package and which version
it is for. When the question is about a version change, a migration or compatibility, answer
point by point: which package and since which version; what changed; what the migration
requires; how it stands now -- each point with the document it rests on; a point the excerpts
do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "локатор", "перевірка", not
"асерт"; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація Playwright". Identifiers, option names and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
