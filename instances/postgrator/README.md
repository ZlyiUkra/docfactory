# postgrator — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про postgrator — бібліотеку міграцій SQL для Node.js (PostgreSQL,
MySQL, SQL Server, SQLite) — за документацією всіх його 65 версій npm, від 0.0.1 (2012) до 8.0.0 (2024). Код спільний
і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій
фабрики — у [../../README.md](../../README.md).

## Навіщо вся історія

Окремого сайту документації в postgrator немає: документація — це README, типи й приклади самого пакета. Вони
міняються з кожною мажорною лінією: у 2.x–3.x підключення до бази описувала рядок з'єднання й `driver`, з 4.0 —
`execQuery`, а вимога до Node стрибала разом із лініями (3.x — Node 6, 4.x — 10, 5.x — 12, 6.x–7.x — 14, 8.x — 20).
Проєкт на старому Node не може взяти 8.x, тож питання звучить «яка версія працює на моєму Node» і «як це було в
моїй лінії». Відповідь дає лише документація саме тієї версії, тож корпус — усі 65 версій, а не остання.

for Node 10»), де відповідь живе в документі реєстру npm чи у `Breaking` журналу змін під іншими словами.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df postgrator <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| README усіх версій | tarball `registry.npmjs.org/postgrator/-/postgrator-X.tgz` | `npm-tarball-files`, новий |
| типи `postgrator.d.ts` | той самий tarball | `npm-tarball-files`, новий |
| приклади | дерево репозиторію на коміті `gitHead` версії, текст — `raw.githubusercontent.com` | `npm-githead-files`, новий |
| журнал змін | `CHANGELOG.md` гілки master | `changelog` |
| реєстр npm | registry.npmjs.org, одне звернення | `npm-versions` |

Читачі `npm-tarball-files` і `npm-githead-files` додано разом із цим примірником (`engine/readers/npmpackage.py`).
Особливості, які варто знати:

- **Чому tarball, а не репозиторій.** Для 16 версій 0.x (2012–2014) реєстр не записав `gitHead`, а тегів у
  репозиторії немає (найстаріший тег — v2.10.2). README цих версій є лише в пакеті. Тому README й типи беруться з
  tarball кожної версії — це точно те, що отримує `npm install`, — а не з коміту.
- **Приклади — з репозиторію.** Тека `examples/` у пакет не потрапляє (`.npmignore`), тож її беруть із репозиторію
  на коміті версії. Приклади з'являються у версіях 5.0.0 і новіших; коміти, яких уже немає в репозиторії (GitHub
  відповідає 422), пропускаються з повідомленням у журналі.
- **Документ — неповторний текст.** Версії, де файл не змінився, ділять один документ; у рядку `# версія:` стоять усі.
  `revision_suffix` у `config.json` зводить редакції README до спільного ключа розділу, тож однаковий розділ двох
  редакцій — один фрагмент.
- **Типи є з 3.6.0.** Раніше `postgrator.d.ts` у пакеті не було.
- **Вимога до Node (`engines`)** записана в документах реєстру npm: рядок кожної версії, де вона змінилася відносно
  попередньої. Для версій до 3.0.0 поля `engines` у пакеті немає.
- **Усі 65 версій стабільні**, передрелізів і міток canary немає.

## Межі, про які треба пам'ятати

Документації драйверів (`pg`, `mysql2`, `tedious`, `sqlite3`), SQL і Node.js тут немає, як і інших інструментів
міграцій (knex, Flyway, node-pg-migrate). Журнал змін на master неповний для найстарших версій: до 2.0.0 записів
немає, а для 41 версії з 65 запис є. Код бібліотеки (`lib/`) не входить — лише документація.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/postgrator-corpus-2026-10-09.tar.gz` (104 тексти і паспорт). В історії
git текстів немає ніде. Архів лежить лише на цій машині.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/postgrator-corpus-2026-10-09.tar.gz -C instances/postgrator
./df postgrator smoke
```

**Як знову винести** — після оновлення, коли `vectors` і `smoke` пройшли (вони ж збирають свіжий кеш):

```
ls -l instances/postgrator/index/passages.json       # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/postgrator-corpus-РРРР-ММ-ДД.tar.gz -C instances/postgrator corpus
find instances/postgrator/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/postgrator/index/passages.json > instances/postgrator/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти» і «Як повернути тексти».

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/postgrator/index/passages.json.gz`,
далі `./df postgrator vectors` заллє колекцію Qdrant (близько хвилини).

## Установка venv

```
cd instances/postgrator
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df postgrator sources --why   # перелік джерел і білий список
./df postgrator refresh         # завантажити все задеклароване (хвилини)
./df postgrator manifest        # оновити паспорт
./df postgrator setup           # Qdrant чи пошук лише по словах
./df postgrator vectors         # залити корпус у docs-postgrator
./df postgrator smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df postgrator serve          # порт 8806
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8806/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user postgrator-docs http://127.0.0.1:8806/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `postgrator-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
