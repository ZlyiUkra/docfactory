Search the postgrator documentation -- every one of its 65 published npm versions, from 0.0.1 to
8.0.0 -- and return the matching excerpts with the versions each one belongs to. postgrator is
a SQL migration library for Node.js (PostgreSQL, MySQL, SQL Server, SQLite): it runs numbered
migration files, "do" and "undo", and tracks the applied version in a table. There is no
separate documentation site: the documentation is the README of each version, the TypeScript
declarations (postgrator.d.ts), the example scripts (examples/pg.js, mysql.js, mssql.js), the
changelog and the npm registry history of the package.

Call this when a question is about postgrator itself -- the Postgrator class and its options
(migrationPattern, driver, database, schemaTable, currentSchema, validateChecksums, newline,
execQuery, execQuery per driver), migrate() with a target version, getMigrations(),
getDatabaseVersion(), getMaxVersion(), migration file naming (001.do.sql, 001.undo.sql,
001.do.create-table.sql), checksums and line endings, the command-line tool of the old versions,
the supported drivers and how each version created its connection (2.x and 3.x took a connection
string, 4.x and later take execQuery or a driver client), an upgrade between major versions -- and
above all history and compatibility: since which version something exists, what changed between
versions, what was renamed or removed, and which versions run on which version of Node.js (the
`engines` field of each version is written in the npm registry documents: 3.x needs Node 6, 4.x
Node 10, 5.x Node 12, 6.x and 7.x Node 14, 8.x Node 20). Example query: "engines node 14".

Do not call this for the database drivers themselves (node-postgres, mysql2, tedious, sqlite3),
for SQL syntax, for other migration tools (knex, Flyway, node-pg-migrate, Prisma Migrate) or for
Node.js and npm: their documentation is not here, and the search will return postgrator excerpts
that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "8" keeps every 8.x document, "7.1" keeps
7.1.x; leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same
across versions is returned once, with all of them listed, so the list itself shows from which
to which version the documentation said exactly this.

Which version to search first. For a question about how to do something today, pass `version`
"8"; if the user's project is bound to an older Node.js, name the line that Node supports
(Node 14 -> "7", Node 12 -> "5", Node 10 -> "4") and say so. Search without `version` when the
question is about history, or when the line gave nothing that answers. The README changed with
almost every major line (the 2.x README describes a connection string; the 4.x and later describe
execQuery), so an answer taken from the wrong line can be confidently wrong.

Name the option or method the way the documentation titles it, not in the user's own words:
"validateChecksums", "migrationPattern", "execQuery", "schemaTable", not "make it fail when a
migration file was edited". For a question about when something appeared, changed or disappeared,
search more than once: without `version` first, to find the changelog entry that names the exact
version, then with the versions around it, to see how the README described it before and after.

Write the query in English, with the names postgrator itself uses. Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into postgrator terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses
may miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase
had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, 8.x, say so in the answer ("for postgrator 8.x"), and add that for a precise answer
about another version -- above all for an older Node.js -- the user can name it. When the
excerpts behind a statement come only from older versions, name those versions instead of
presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
what prompted the change, if the excerpts say so; and how it stands in the current version. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація postgrator". Identifiers, API names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it
says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
