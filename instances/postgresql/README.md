# postgresql — примірник фабрики docfactory

Тридцять другий примірник фабрики: захищений MCP-сервер, що відповідає на питання про PostgreSQL — мову SQL і її
розширення в PostgreSQL, індекси, транзакції й рівні ізоляції, продуктивність і `EXPLAIN`, налаштування сервера,
автентифікацію й ролі, резервне копіювання, реплікацію, обслуговування й `VACUUM`, PL/pgSQL, довідник команд і програм
(`psql`, `pg_dump`, `pg_restore`). Тут офіційна документація кожного мажору від 9.0 до 19 разом із нотатками релізів.
Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний
устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

PostgreSQL — база даних фулстек-планів (NestJS, Next.js) і задуму переписати проєкт на Express із власною базою.
Поведінка залежить від версії сервера: `MERGE` з'явився в 15, `recovery.conf` зник у 12, `scram-sha-256` став типовим
паролем у 14, а на роботі трапляються сервери і 9.6, і 18. Тому тут усі мажори від 9.0, і відповідь завжди каже, для
якої версії вона.

У яких фазах і днях планів навчання він потрібен — див. [../../docs/learning-map.md](../../docs/learning-map.md).

## Скільки цього

Одиниця корпусу — неповторний файл сирців: файл, що не мінявся між гілками, — це один документ з усіма своїми
версіями. Так 17 гілок по 300–450 файлів дають 3 620 документів, а не шість тисяч.

Число в рядку — скільки документів несуть цю версію; документ без змін рахується в кожній. Що новіша версія, то менше
в неї власних документів: більшість її глав лишилася такою, як у сусідніх.

Разом 3 620 документів; фрагментів в індексі — 30 609 (`expected_passages` у `checks.json`). Фрагменти — це шматки
документів між заголовками, по яких іде пошук; однаковий текст різних версій зливається в один з усіма версіями.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами) — по словах 5 із 10, за змістом 7, разом 7;
друга, «як модель» (назви команд і параметрів, з версією «18», як велить промпт), — 10 із 10.

**Версія у відповіді.** Перший рядок відповіді каже, для якої версії PostgreSQL вона. Без названої версії — 18 (на день
збирання остання стабільна; Docker Hub не дає статистики завантажень за тегами, тож найпопулярнішу виміряти нема чим),
і відповідь прямо каже, що версію взято за замовчуванням, та підказує `SELECT version();` або `SHOW server_version;`.
Фільтр `version` — мажор: «18», «17» … «10», а до 10 — двоцифровий: «9.6», «9.0».

## Що в цій теці

- `corpus/` — лише паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа (тексти — в архіві,
  див. нижче).
- `index/passages.json.gz` — стиснений кеш фрагментів, з якого підіймається сервер.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df postgresql <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| уся документація: посібник, довідник SQL-команд і програм, розширення `contrib`, нотатки релізів | `doc/src/sgml` репозиторію postgres/postgres, гілки `REL9_0_STABLE` … `REL_19_STABLE` | `pg-sgml` |

Білий список — два хости: `api.github.com` (перелік файлів гілки) і `raw.githubusercontent.com` (самі файли).

Особливості, які варто знати:

- **DocBook, а не markdown.** Документацію PostgreSQL пишуть у DocBook: до 10 включно — SGML (скорочені кінцеві теги,
  атрибути без лапок), з 11 — XML. Для цього в фабриці новий читач `pg-sgml`: він читає розмітку потоком тегів, без
  дерева, тож той самий код бере і SGML 9.x, і XML 11+. Параметри конфігурації (`work_mem`, `shared_buffers`…) стають
  окремими заголовками, тож пошук знаходить сам параметр, а не всю главу.
- **Посилання — на сайт.** Сайт www.postgresql.org/docs збирається з тих самих сирців, тому сайт не читається, а
  джерелом документа записано його сторінку: `https://www.postgresql.org/docs/ВЕРСІЯ/id.html`, де `id` — ідентифікатор
  кореневого елемента файла (поле `site` джерела). Документ з кількома версіями несе адресу найновішої; модель за
  промптом ставить в адресу версію, для якої відповідь. 11 файлів, корінь яких не стає окремою сторінкою сайту
  (наприклад `dfunc`), лишилися з посиланням на GitHub.
- **Нотатки релізів** кожної гілки лежать у ній самій: у 18 — `release-18` з усіма 18.x. Гілки 9.x несуть ще й нотатки
  всіх давніших релізів аж до 7.x і 8.x — як історію змін; документації самих 7.x і 8.x тут немає.
- **Службові файли збирання** (`filelist`, `allfiles`, `postgres`, `version`, `standalone-*`, `legal`) не беруться:
  це оголошення сутностей і склад книги, а не текст.
- **19** на день збирання ще не вийшов: у його нотатках релізу дата «2026-??-??, AS OF 2026-09-14». Документація
  гілки — те, що буде в релізі, якщо до нього нічого не зміниться.
- **Посилання «§» на коміти** в нотатках релізів (`&commit_baseurl;…`) викинуто: для пошуку це шум.

## Межі, про які треба пам'ятати

Тут немає документації драйверів і ORM (node-postgres, Prisma, TypeORM, Drizzle), розширень поза `contrib` (PostGIS,
TimescaleDB, pgvector), керованих сервісів (Supabase — окремий примірник `supabase`, RDS, Neon), операторів Kubernetes і
пулерів (PgBouncer). Wiki postgresql.org і розсилки свідомо не взято.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку, як у express: у `corpus/` лежить лише паспорт `index.json`, а сервер
підіймається з кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає
повний текст кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/postgresql-corpus-2026-10-06.tar.gz` (20 МБ, 3 620 текстів і паспорт;
перед видаленням розпакований окремо й звірений із диском — нуль розбіжностей). В історії git текстів немає ніде. Архів
лежить лише на цій машині.

**Зайві точки — прибрати на першому ж оновленні.** У колекції `docs-postgresql` 30 855 точок на 30 609 фрагментів:
246 лишилися від нотаток релізів 12–19 у тому вигляді, який вони мали до того, як читач почав викидати посилання «§»
на коміти. Пошук їх не показує, на відповіді вони не впливають. Прибрати їх можна лише знесенням колекції й новим
`vectors` (близько години) — це треба зробити разом із першим оновленням документації PostgreSQL, а не окремо.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/postgresql/index/passages.json      # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/postgresql-corpus-РРРР-ММ-ДД.tar.gz -C instances/postgresql corpus
find instances/postgresql/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/postgresql/index/passages.json > instances/postgresql/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/postgresql-corpus-РРРР-ММ-ДД.tar.gz -C instances/postgresql
./df postgresql smoke
```

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/postgresql/index/passages.json.gz`,
далі `./df postgresql vectors` заллє колекцію Qdrant (близько години).

## Установка venv

```
cd instances/postgresql
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

```
./df postgresql sources --why   # перелік джерел і білий список
./df postgresql refresh         # завантажити все задеклароване (~1,5 години)
./df postgresql manifest        # оновити паспорт
./df postgresql setup           # Qdrant чи пошук лише по словах
./df postgresql vectors         # залити корпус у docs-postgresql (~1,5 години)
./df postgresql smoke           # перевірки
```

`refresh` спершу читає дерево файлів кожної з 17 гілок (17 звернень до GitHub API), а потім по одному сирому файлу на
кожен неповторний вміст — 3,6 тисячі звернень до `raw.githubusercontent.com`. Без `GITHUB_TOKEN` у `.env` анонімного
ліміту GitHub API вистачає, але токен однаково радять для надійності. Обірваний `refresh` продовжується з `--missing`.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df postgresql serve           # порт 8792
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8792/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user postgresql-docs http://127.0.0.1:8792/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `postgresql-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
