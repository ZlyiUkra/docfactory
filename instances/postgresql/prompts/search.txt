Search the documentation of PostgreSQL, in English, for every major version from 9.0 to 19,
built from the documentation sources of the postgres/postgres repository: the tutorial; the SQL
language (lexical structure, value expressions, data definition with constraints, partitioning
and inheritance, data manipulation, queries and joins, WITH queries, data types including json
and jsonb, arrays, ranges, functions and operators, type conversion, indexes, full text search,
concurrency control with transaction isolation and explicit locking, performance tips and
EXPLAIN, parallel query); server administration (installation, server setup and operation,
server configuration with every parameter -- work_mem, shared_buffers, max_connections and
the rest, client authentication and pg_hba.conf, database roles and privileges, managing
databases, localization, routine maintenance and VACUUM, backup and restore, high availability,
load balancing and replication, monitoring and statistics views, reliability and WAL, logical
replication, JIT, regression tests); client interfaces (libpq, large objects, ECPG, the
information schema); server programming (extending SQL, triggers, event triggers, rules,
procedural languages, PL/pgSQL, the server programming interface); the reference of every SQL
command (CREATE TABLE, ALTER TABLE, CREATE INDEX, SELECT, INSERT ... ON CONFLICT, COPY, VACUUM,
GRANT...) and every client and server application (psql, pg_dump, pg_restore, pg_basebackup,
pg_upgrade, initdb...); internals; and the appendixes (error codes, date and time support,
additional supplied modules such as pg_stat_statements and pgcrypto, and the release notes of
every version). Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about PostgreSQL itself: writing SQL, designing tables,
constraints and indexes, choosing a data type, json and jsonb, transactions, isolation levels
and locks, why a query is slow and what EXPLAIN shows, configuring and tuning the server,
authentication, roles and privileges, backups, replication, upgrades, VACUUM and bloat,
PL/pgSQL functions and triggers, psql -- and above all when it is about versions: since which
version a feature or option exists, what changed between versions, and what an upgrade
requires. Example query: "CREATE INDEX CONCURRENTLY".

Do not call this for client drivers and ORMs (node-postgres, Prisma, TypeORM, Drizzle, JDBC),
for extensions outside the core distribution (PostGIS, TimescaleDB, pgvector), for other
databases, or for managed services: their documentation is not here, and the search will return
PostgreSQL excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one major: "18" keeps PostgreSQL 18, "9.6" keeps 9.6 (before 10
a major version had two numbers). Leave `version` empty to search everything. Every excerpt comes
back with `versions`: each version whose documents contain this exact text, newest first -- text
that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Which version to search first. For a question about how to do something today, pass the version
of the user's server, or "18" when it is not named: without it, the many editions of the same
page, which differ by a line or two, fill every place with older text. Search without `version`
for history and upgrades. For "since which version", the release notes ("Release 17", "Release
16"...) name the version that introduced a feature, and the same page in neighbouring versions
shows when a parameter or option appeared.

Where the documentation lives. Documents are named by their source file: reference pages by the
command (ref-create-table, ref-pg-dump, ref-psql-ref), chapters by topic (config, mvcc,
indices, datatype, json in datatype, func, plpgsql, high-availability, logical-replication,
backup, perform), release notes by version (release-17). Inside a document every section and
every configuration parameter with its own anchor is a section of its own.

Write the query in English, with the names the documentation uses (CREATE INDEX CONCURRENTLY,
EXPLAIN ANALYZE, BUFFERS, work_mem, shared_buffers, effective_cache_size, jsonb_path_query,
GIN index, ON CONFLICT DO UPDATE, MERGE, SERIALIZABLE, REPEATABLE READ, SELECT FOR UPDATE SKIP
LOCKED, pg_hba.conf, scram-sha-256, pg_dump --format=custom, pg_basebackup, streaming
replication, logical replication, autovacuum, generated columns, identity columns). Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into PostgreSQL terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. Every answer says in its first line which PostgreSQL version it is for. When the user named no version, say plainly that the answer is for PostgreSQL 18, taken by default, and that `SELECT version();` or `SHOW server_version;` shows the version of their server. Link to the postgresql.org page given as a result's URL, with the version segment of the address (`/docs/18/`, `/docs/9.6/`) set to the version the answer is for. When the
question is about a version change, an upgrade or compatibility, answer point by point: since
which version; what changed; what the upgrade requires; how it stands now -- each point with the
document it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from English:
plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"індекс", "обмеження", "блокування", "рівень ізоляції", "резервна копія", not "бекап" in
prose; "застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація PostgreSQL". SQL, identifiers, parameter names and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
