Search the official documentation of Prisma -- the TypeScript and Node.js ORM (Prisma schema,
Prisma Client, Prisma Migrate and the prisma CLI) for PostgreSQL, MySQL, MariaDB, SQLite, SQL
Server, CockroachDB and MongoDB, with the Prisma data platform around it -- and return the matching
excerpts with the versions each one belongs to. Here: the documentation site prisma.io/docs as it
stood while each stable Prisma release from 2.0.0 to 7.10.0 was the newest -- getting started and
quickstarts for every database, the Prisma schema language (models, fields, attributes such as
@id, @unique, @default, @relation, @@index, @map, enums, composite types, views, multi-file
schema), relations, Prisma Client queries (findUnique, findMany, create, update, upsert, delete,
createMany, select, include, omit, filtering and sorting, pagination, aggregation, groupBy,
transactions and $transaction, raw SQL with $queryRaw and TypedSQL, client extensions with
$extends, middleware, logging, error codes), the generators prisma-client-js and prisma-client,
driver adapters, Prisma Migrate (migrate dev, deploy, reset, resolve, diff, baselining, shadow
database), db push, db pull, db seed, every CLI command and flag, prisma.config.ts, environment
variables, connection URLs, deployment guides, upgrade guides between major versions, Prisma
Postgres, Accelerate, Optimize, Pulse, Prisma Studio, the Console, and guides for frameworks such
as Next.js, NestJS and Nuxt; the markdown of the prisma/prisma repository at every stable tag
(the README of every package); the release notes of every stable release; and the npm version
table of the CLI, Prisma Client, the driver adapters and the extensions.

Call this when a question is about Prisma itself -- a schema attribute or field type and how it
maps to each database, a Prisma Client method, its arguments and its result type, nested writes,
relation queries, transactions, raw queries, extensions, the generated types, a CLI command and
its flags, a migration workflow, a prisma.config.ts key, a driver adapter, an error code (P2002,
P1001), an Accelerate or Prisma Postgres setting, and above all history: since which version
something exists, what changed between versions, what was renamed, deprecated or removed, and
how to upgrade from one major version to the next.
Example query: "findMany select".

Do not call this for Drizzle, TypeORM, Sequelize, MikroORM, Kysely or Knex beyond the pages that
compare Prisma with them or migrate from them, the SQL language and the database servers
themselves (PostgreSQL, MySQL, SQLite, SQL Server, MongoDB), the drivers' own APIs (pg, mysql2,
better-sqlite3), Next.js, NestJS or any web framework beyond their Prisma guides, or hosting
providers: their documentation is not here, and the search will return Prisma excerpts that
merely mention them, with confident-looking titles.

Only stable releases are here. Prisma ORM 8 (the 8.0.0 release candidates) and Prisma Next are
not documented here: since 25 August 2026 the live site describes Prisma ORM 8, and this
documentation stops at its last stable state, Prisma 7.10.0. Prisma 1 (the GraphQL server with
prisma.yml and the Prisma 1 client) is not here either. A question about them gets the answer that
they are not in this documentation.

Versions. `version` narrows the search to the documents of one release line: "7" keeps every 7.x
document, "6" every 6.x, "5" every 5.x. The site has no versions of its own: each of its documents
carries the Prisma versions during whose time the page read exactly so. Packages with their own
numbering carry a label: "extension-accelerate-2" keeps @prisma/extension-accelerate 2.x (also
extension-read-replicas-, extension-optimize-, ppg-, studio-core-); a bare "2" never returns them.
Without `version` a page found in several releases comes back once, in its newest edition. Every
excerpt comes back with `versions`: each version whose documents contain this exact text, newest
first. Release notes carry the version of their release.

Name the method, attribute, option, command or config key the way the documentation titles it,
not in the user's own words: "findUniqueOrThrow", "upsert", "@default autoincrement",
"@relation onDelete referential actions", "$transaction interactive transactions",
"$extends query component", "createMany skipDuplicates", "prisma migrate dev", "prisma db push",
"prisma.config.ts migrations seed", "driverAdapters adapter-pg", "omit fields", not "how do I
update a row if it already exists". A command is searched by its full name as the page titles it
("prisma migrate deploy", "prisma generate"). A method name alone also matches every release note
and example that merely mentions it: add the plain word the documentation titles its topic with
("upsert CRUD", "select fields", "Json field filtering"). For a how-to question a guide often
shows it better than the reference: search for it as well ("seeding guide", "deploy to Vercel
guide", "upgrade to Prisma 7").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the release notes or the upgrade guide that names the exact
version, then with the versions around it, to see the documentation of that time.

Write the query in English, with the names Prisma itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate
the question into Prisma terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
two most downloaded stable lines, which are close: Prisma 7 (7.10.0) and Prisma 6 (6.19.3) -- and
where they differ (the prisma-client generator and its output path, driver adapters,
prisma.config.ts, removed options), give both. When the excerpts show that a method, option or
command appeared in a later release than the user may have, say since which one. Add that for a
precise answer about another version the user can name it. When the excerpts behind a statement
come only from older versions, name those versions instead of presenting the text as current.
Many pages show the same example for several databases or languages, each under its own label
("PostgreSQL:", "MongoDB:", "TypeScript, PostgreSQL:"): give the one the user asked about, and
when the user did not say, the PostgreSQL one with a note that the others exist. A line
"File `schema.prisma`:" names the file the code below it belongs to; "Output:" introduces what a
command prints.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
and how it stands now -- recommended, deprecated, or removed and replaced by what. Every point
names the version and the document it rests on; a point the excerpts do not support is left out,
not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "міграція схеми", not "мігрейшн"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація Prisma".
Identifiers, methods, options and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
