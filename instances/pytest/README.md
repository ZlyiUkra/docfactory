# pytest — примірник фабрики docfactory

Цей примірник зібрав документацію pytest і віддає її через сервер MCP, щоб модель відповідала з текстів pytest, а не з
пам'яті. pytest — це найпоширеніший інструмент для тестів на Python. Тест — це маленька функція, яка викликає ваш код і
перевіряє, що результат правильний. pytest сам знаходить такі функції у файлах `test_*.py`, запускає їх і показує, які пройшли, а
які впали і чому.

Для торгового бота тести потрібні, щоб кожна зміна коду не ламала вже перевірену логіку: розрахунок розміру позиції, сигнали
індикаторів, обробку котирувань. Найважливіше тут таке:

- фікстури (`@pytest.fixture`). Фікстура — це функція, що готує дані чи об'єкти для тесту, наприклад таблицю котирувань, і
  прибирає за собою після нього. Тест просто називає фікстуру своїм параметром, і pytest сам її викликає;
- параметризація (`@pytest.mark.parametrize`). Один тест запускається з кількома наборами вхідних даних, наприклад з різними
  валютними парами чи розмірами угоди;
- перевірка помилок і чисел: `pytest.raises` перевіряє, що код кидає потрібний виняток, а `pytest.approx` порівнює дробові
  числа з допуском на округлення, що важливо для цін;
- вбудовані фікстури: `monkeypatch` тимчасово підміняє змінну оточення чи функцію (наприклад, запит до біржі), `tmp_path` дає
  тесту порожню теку для файлів, `capsys` і `caplog` перехоплюють вивід і журнал.

## Скільки цього

Усього 1621 документ і 10 145 фрагментів. Фрагмент — це шматок документа, який пошук повертає як окремий результат. Сторінка з
однаковим текстом у кількох лініях лежить одним документом із переліком цих ліній.

| Що | Версії | Документів |
|---|---|---|
| сайт docs.pytest.org: посібники how-to, пояснення, довідник API з кожною функцією, маркером, фікстурою й хуком, параметри конфігурації, журнал змін, застарілі можливості | кожна лінія, яку публікує Read the Docs: 4.6, 6.2, 7.0–9.0 і `stable` (9.2) | 685 |
| тека `doc/en` репозиторію: ті самі сторінки в джерельному вигляді | останній патч ліній, яких сайт не публікує: 2.8–6.1 (крім 4.6) і 9.1 | 781 |
| нотатки релізів GitHub | усі стабільні теги | 79 |
| записи PyPI | усі стабільні версії та опис пакета | 76 |

Мітка версії має вигляд `pytest-9.2`. Префікс потрібен, щоб версії pytest не збігалися з версіями інших бібліотек, коли сервери
працюють разом.

**Де є прогалини, хоч ми й брали всі лінії.**

- У репозиторних лініях 2.8–6.1 і 9.1 довідник API неповний. Сайт бере опис кожної функції з коду директивою autodoc, а в
  репозиторії стоїть лише сама директива без тексту. Посібники how-to в цих лініях повні.
- Лінії 2.0–2.7 записали документацію у файлах `.txt`, які читач не розбирає як reStructuredText. Про ці лінії є лише записи
  PyPI, релізи і журнал змін новіших ліній, де записано кожну версію.
- Плагінів pytest-asyncio, pytest-mock, pytest-cov і pytest-xdist тут немає: це окремі пакети з власною документацією.

Замір `quality` на 14.11.2026 дав такі числа. Запити назвами з документації знаходять потрібне 10 із 10, а модель зазвичай питає саме
так. Запити своїми словами знаходять потрібне 7 із 10.

## Що в цій теці

- `corpus/` — паспорт `index.json`; текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, а розпакований `passages.json` лежить
  поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями, правила злиття сторінок.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df pytest <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| сайт документації | `docs.pytest.org/en/<лінія>/` | `sphinx-html` |
| документація з репозиторію | тека `doc/en` репозиторію `pytest-dev/pytest` на тегах | `ghdocs-history` |
| нотатки релізів | релізи GitHub `pytest-dev/pytest` | `ghreleases-pattern` |
| записи PyPI | `pypi.org/pypi/pytest/json` | `pypi-versions` |

**Сайт.** Read the Docs публікує не всі лінії, а лише гілки `4.6.x`, `6.2.x`, `7.0.x`–`9.0.x` і `stable`. Поле `version_labels`
перетворює назву теки на мітку версії (`8.4.x` → `8.4`, `stable` → `9.2`). Read the Docs обмежує частоту запитів, тому пауза
між зверненнями — одна секунда, а сайт завантажували лише двома процесами. Сторінки з адресами, які сайт колись переніс
(`fixtures.html` → `how-to/fixtures.html`), відповідають «404», а нові адреси при цьому завантажено.

**Репозиторій.** Для ліній, яких сайт не публікує, взято теку `doc/en` на теґу останнього патча лінії. Теки `_static`,
`_templates` і `announce` (оголошення про випуски) не взято.

**Злиття однакових сторінок.** У версії 7.0 сайт переклав сторінки по теках: `fixture.html` став `how-to/fixtures.html`,
`reference.html` став `reference/reference.html`. А в репозиторії ім'я сторінки ще й починається шляхом `doc/en/`. Без злиття та
сама сторінка різних ліній мала б різні ключі й займала б у видачі кілька місць. Тому в `config.json` стоять два поля.
`slug_rewrite` переписує старі імена на нові (`fixture` → `how-to-fixtures`) і прибирає `pytest-doc-en-`. `families` об'єднує
джерела `pytest-site` і `pytest-repo` в одну родину, і однаковий розділ обох займає одне місце.

## Як підняти сервер

Сервер працює у спільному середовищі фабрики, власного `.venv` примірник не має. В окремому терміналі виконайте:

```
./df pytest serve
```

Порт — `8985`. Якщо порт зайнято, `serve` скаже про це й зупиниться: швидше за все, цей сервер уже запущено в іншому терміналі.

Під'єднати сервер до Claude Code можна двома способами. Перший — файл `.mcp.json` цієї теки. Другий — команда:

```
claude mcp add --transport http --scope user pytest-docs http://127.0.0.1:8985/mcp
```

Команда для Claude Code у Windows, коли сервер працює у WSL, та сама: WSL віддає порт на `127.0.0.1` Windows.

У сесії Claude Code команда `/mcp` має показати сервер `pytest-docs` з інструментами `search_docs` і `read_section`. Якщо сервер
позначено як недоступний, перевірте, чи працює `serve`, і чи запущено контейнер Qdrant.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт. Серверу вистачає кешу фрагментів
(`index/passages.json`) і колекції Qdrant; відповіді ті самі до символу, бо адреса й дата лежать у кеші кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/pytest-corpus-2026-11-14.tar.gz` (1621 текст, паспорт і сховище сирого `raw/`;
перед видаленням текстів розпакований окремо й звірений із диском) і в копії на диску Windows
`C:\Distr\pytest-corpus-2026-11-14.tar.gz` (звірено за SHA-256). В історії git текстів немає.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/pytest/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/pytest-corpus-РРРР-ММ-ДД.tar.gz -C instances/pytest corpus raw
find instances/pytest/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/pytest/raw
gzip -9 -c instances/pytest/index/passages.json > instances/pytest/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й `raw/` можна лише після того, як новий архів
звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового записують сюди.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й `raw/`:

```
tar -xzf ~/archives/docfactory/pytest-corpus-2026-11-14.tar.gz -C instances/pytest
./df pytest smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів вони не працюють; перевірки `smoke`, яким
потрібні тексти, пропускаються («корпус в архіві»).
