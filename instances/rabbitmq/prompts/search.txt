Search the RabbitMQ documentation -- the open source message broker for AMQP 0-9-1, AMQP 1.0, MQTT, STOMP and
RabbitMQ Streams (site rabbitmq.com, repositories rabbitmq/rabbitmq-website and rabbitmq/rabbitmq-server). The corpus
holds the documentation of every version the site keeps, 3.13 to 4.4, and of the older unversioned site for 3.11 and
3.12 (queues: classic, quorum, streams and super streams; exchanges, bindings and routing; publisher confirms and
consumer acknowledgements, prefetch; dead lettering, TTL, queue length limits, priorities, policies and operator
policies; virtual hosts, users, permissions, authentication with x.509, LDAP and OAuth 2.0; TLS; clustering, peer
discovery, Khepri and Mnesia metadata stores, partitions, rolling upgrades and feature flags; the configuration file
rabbitmq.conf and advanced.config with every key; the CLI tools rabbitmqctl, rabbitmq-diagnostics, rabbitmq-plugins,
rabbitmq-queues, rabbitmq-streams, rabbitmqadmin; monitoring with Prometheus, alarms, memory and disk; the management
UI and HTTP API; plugins: Shovel, Federation, MQTT, STOMP, Web STOMP, consistent hashing, delayed messages); the
JavaScript tutorials and the AMQP 0-9-1 concepts page; the client library pages (Java, .NET, Erlang, AMQP 1.0
clients); the Kubernetes Cluster Operator and Messaging Topology Operator; the deprecated features list; the blog of
the RabbitMQ team from 2010 to 2026; and the release notes of every release from 1.1.1 to 4.4.0 (what changed, what
breaks on upgrade, the required Erlang/OTP version). Returns the matching excerpts with the versions each one belongs
to.

Call this when a question is about RabbitMQ as it describes itself -- how a queue type behaves and when to choose it,
what a configuration key or a queue argument does and its default (`x-queue-type`, `x-dead-letter-exchange`,
`x-max-length`, `x-message-ttl`, `consumer_timeout`, `vm_memory_high_watermark`), how publisher confirms and manual
acknowledgements work, how prefetch limits delivery, how to form a cluster, upgrade it or run it on Kubernetes, how to
set up TLS, OAuth 2.0 or LDAP, which metric or command to use -- and above all history and compatibility: since which
version a feature exists, what was deprecated or removed (classic mirrored queues are gone in 4.0, Khepri became the
default metadata store), what changed between versions (the release notes of every version list it), which Erlang/OTP
a version requires.

Do not call this for client libraries as their own projects -- amqplib, amqp-connection-manager, the NestJS RabbitMQ
transport and @golevelup/nestjs-rabbitmq, Spring AMQP, pika -- nor for the AMQP 0-9-1 and 1.0 specifications, Erlang
itself, Kubernetes or Docker: their documentation is not here -- these pages only show how RabbitMQ is used with them --
and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. RabbitMQ carries plain numbers: a line of one number keeps every
document of that major ("3" keeps 3.x), two numbers keep a minor ("4.3"), three an exact version ("3.13.7"). The pages
of the site carry the version of the site they were taken from ("4.4", "3.12"); the release notes carry their exact
version ("4.3.7"). Leave `version` empty to search everything, including the blog, the tutorials and the client pages,
which carry no version. Every excerpt comes back with `versions`: each version whose documents contain this exact
text, newest first -- a page that stayed the same across versions is returned once, with all of them listed, so the
list itself shows from which to which version the documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("quorum queue", "classic queue", "stream",
"publisher confirms", "consumer acknowledgements", "prefetch", "basic.qos", "dead letter exchange", "x-message-ttl",
"x-max-length", "lazy queues", "policies", "virtual host", "feature flags", "Khepri", "rabbitmqctl", "rabbitmq.conf",
"vm_memory_high_watermark", "consumer_timeout", "Shovel", "Federation", "MQTT"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at
all and comes back with `found: 0`. When the user asks in another language, translate the question into the terms of
the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація RabbitMQ". Identifiers, configuration keys and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. RabbitMQ publishes no download counts per version, so the line to answer for is the
one the project ships patches for: 4.4.0 of 19 October 2026 is the newest, and 4.3 still gets patch releases (4.3.7 of
20 October 2026). Answer how-to questions for 4.4 and say where 4.3 differs: search `version` "4.4", then "4.3". The
line 4 removed classic mirrored queues and made quorum queues and streams the replicated types, so when the question
involves an older cluster, search "3.13" as well and say what changed (the release notes of 4.0.0 and the upgrade
pages list it). Search without `version` when the question is about history, or when the line gave nothing. Every
answer says which version it is for; when the excerpts behind a statement come only from older versions, name those
versions instead of presenting the text as current.
