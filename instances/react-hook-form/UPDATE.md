# Оновлення корпусу react-hook-form

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версії приходять із npm, а теги — руками.** Сайт документації версійних тегів не має, тож
перелік версій для `rhf-site` і `rhf-readme` береться з реєстру npm на кожному прогоні: новий реліз потрапляє в
корпус сам. Інакше з `rhf-api` (TypeScript-сигнатури): там, як у `react-router`, оновлювач бере рівно теги з поля
`tags` у `sources.json`, і новий тег треба дописати.

Друге правило: **новий реліз змінює й старі документи.** Документ — неповторний текст файла, а в рядку `# версія:`
стоять усі версії, де файл був саме таким. До того ж знімок попередньої версії лінії береться на мить перед
новим релізом, тож і він зсувається. Тому `rhf-site`, `rhf-readme` і `rhf-api` перезаписуються цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх
не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Документ, що після нового релізу вже нікому не належить (скажімо, знімок останньої версії лінії до правки),
лишається в `corpus/`; прибрати його — рішення людини.

## 1. Вийшли нові релізи

**Крок 1. Дописати теги для `rhf-api`.** Список, без жодного звернення до API:

```
git ls-remote --tags https://github.com/react-hook-form/react-hook-form.git | grep -v '\^{}' \
  | sed 's#.*refs/tags/##' | sort -V | tail
```

Кожен новий тег дописується на початок поля `tags` джерела `rhf-api` парою «тег → версія»
(`"v7.90.0": "7.90.0"`). Перелік іде від найновішого.

**Крок 2. Якщо вийшла нова мажорна лінія** (скажімо, 8.0.0 як реліз, а не beta):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзац «Which version to search first» і приклади
  `version` у ньому) та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "7"`;
- у `checks.json`, у десятці `quality_model`, замінити `"7"` на нову лінію там, де питання про поточну поведінку.

**Крок 3. Якщо сайт позначив документацію старої лінії теками** (як колись `V5/` і `v6/`): нічого робити не
треба, поле `line_marker` джерела `rhf-site` розпізнає будь-яку теку `V<номер>` чи `v<номер>`. Якщо ж сайт почне
тримати стару лінію в окремій гілці чи на піддомені — це нове джерело, його треба описати в `sources.json`.

**Крок 4. Завантажити.**

```
./df react-hook-form sources --why
./df react-hook-form refresh
./df react-hook-form manifest
./df react-hook-form vectors
./df react-hook-form smoke
# Ctrl+C у терміналі з serve, і знову: ./df react-hook-form serve
```

`refresh` без назв — повне перезавантаження. Названі джерела (`refresh rhf-site`) нічого не скорочують у переліку:
оновлювач однаково складає перелік усіх джерел, а пише лише названі. Корпус комітити частинами до ~700 файлів.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік знімків сайту (сотні дерев)
іде годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном.**

```
nohup ./df react-hook-form refresh > /tmp/react-hook-form-refresh.log 2>&1 &
```

Перші ~35 хвилин журнал мовчить, а `corpus/` порожній: читачі проходять дерево знімку на кожну версію npm, дерево
кожного тегу для сигнатур і README кожної з 1100 версій, і лише потім починають писати файли. Стан видно за
кількістю файлів: `ls instances/react-hook-form/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.
