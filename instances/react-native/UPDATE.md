# Оновлення корпусу react-native

Дві різні роботи: звичайне оновлення, коли вийшли нові версії React Native, і збирання з нуля. Порядок усередині
кожної важливіший за самі команди.

Головне правило: **версії приходять самі, з реєстру npm.** Читач `docusaurus-versions` бере перелік мінорних ліній з
https://registry.npmjs.org/react-native і для кожної шукає теку `website/versioned_docs/version-0.X` репозиторію
react/react-native-website: на вершині гілки, а якщо теку вже прибрано — зі знімка перед комітом, що її видалив.
Нова мінорна версія з'являється в корпусі сама, щойно сайт зріже її теку. Релізи, журнали змін і реєстр npm так само
читають актуальний перелік. Руками нічого дописувати не треба, окрім нового файла журналу змін (крок 2).

Друге правило: **нова версія змінює й старі документи.** Документ — неповторний текст сторінки, а в рядку
`# версія:` стоять усі версії, де сторінка була саме такою. Тож після нової версії корпус перезаписують цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх не
знайде. Правки сайту в теках чинних версій теж змінюють корпус і без нового релізу.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі; лише
`vectors` прибирає з колекції Qdrant точки, чиїх фрагментів більше немає в корпусі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові версії

**Крок 1. Чи змінилася розкладка сайту.** Сайт тримає теки версій у `website/versioned_docs/version-0.X`, а меню
Docusaurus 1 — у `website/versioned_sidebars/`. Якщо сайт перенесе теки (новий Docusaurus, інша структура), у переліку
нових версій не з'явиться жодної сторінки сайту: тоді треба поправити шаблон `folder` джерела `rn-site`.

**Крок 2. Новий файл журналу змін.** Журнал змін React Native розбито за лініями: `CHANGELOG-0.5x.md`,
`CHANGELOG-0.6x.md`, `CHANGELOG-0.7x.md` і кореневий `CHANGELOG.md` для 0.80+. Коли лінія 0.8x закриється і
репозиторій винесе її в `CHANGELOG-0.8x.md`, у `sources.json` треба додати джерело за зразком `rn-changelog-07x` і
вписати його id у родину `rn-changelog` у `config.json`.

**Крок 3. Лінія за замовчуванням.** `prompts/search.txt` (абзаци «Which version to search first» і «Every answer
says which version it is for») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "0.86"`. Лінію
вибирають за завантаженнями з npm за тиждень, а не за номером:

```
curl -s https://api.npmjs.org/versions/react-native/last-week
```

Поки 0.86 завантажують найбільше, вона лишається основною; коли інша лінія її випередить — замінити номер у промптах і
в десятці `quality_model` у `checks.json`.

**Крок 4. Завантажити.**

```
./df react-native sources --why
./df react-native refresh
./df react-native manifest
./df react-native vectors
./df react-native smoke
# Ctrl+C у терміналі з serve, і знову: ./df react-native serve
```

## 2. Особливі версії

- **0.1–0.4** — до сайту reactnative.dev документація лежала в теці `docs/` самого репозиторію; джерело
  `rn-site-early` бере її з останнього тегу кожної лінії. Нових версій там не буде.
- **0.5–0.59** — Docusaurus 1: тека версії тримала лише змінені сторінки, решту читач добирає зі старших тек за меню
  версії (поле `v1_until` джерела `rn-site` — мить переходу сайту на Docusaurus 2).
- **0.69** — архівний коміт 2023 року лишив у теці один файл; читач бачить залишок і бере теку з попереднього знімка.
- **Заглушка 1000.0.0 і нічні збірки `0.0.0-…`** у реєстрі — не версії React Native, їх відкидають `only` і
  `skip_versions`.

## 3. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік ~80 комітів, дерев знімків і
сторінок релізів іде годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df react-native refresh > instances/react-native/out/refresh.log 2>&1 &
```

Перші ~2 хвилини журнал мовчить, а `corpus/` порожній: читач проходить коміти й дерева сайту. Стан видно за
кількістю файлів: `ls instances/react-native/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df react-native quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка
промпту, знову замір. Що це означає тут:

- **Поточна лінія — 0.86.** Що міняти, коли інша лінія стане найпопулярнішою, — крок 3 розділу «1. Вийшли нові
  версії» вище.
- **Правила промпту, що вже є:** спершу лінія 0.86; запит — назвою компонента, API, пропса чи поняття, а не описом;
  питання про історію — журнал змін і допис у блозі про реліз; кожна відповідь каже, для якої версії вона, а без
  названої версії — відповідає для 0.86 і пропонує назвати свою.
- **Останній результат** — у README, абзац «Замір `quality`».
