# react-router — примірник фабрики docfactory

Шостий примірник фабрики: захищений MCP-сервер, що відповідає на питання про React Router за офіційною
документацією всіх його версій — від 0.x (2014) до поточної 8.4, разом з кожним pre-release, nightly й
experimental-збіркою, — за довідником API, журналами змін і нотатками релізів. Код спільний і лежить у
`../../engine/` (завантаження корпусу), `../../server/` (сервер, агент, шари) та `../../common/` (пошук); ця тека
тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

Здебільшого його запускають у парі з `react` (порт 8761), але React Router — окрема бібліотека з власною історією,
і в одному корпусі з React він лише заважав би: `Route`, `Link` чи `redirect` у видачі React були б шумом, а
питання про роутер тонули б серед хуків React.

Історія в роутера бурхлива. Вісім мажорних ліній, і майже кожна переписувала API: `Router.run` і `RouteHandler` у
0.x, `browserHistory` в 1–3, компоненти `<Route>` усередині `<Switch>` у 4–5, `<Routes>` і хуки в 6, дата-роутери з
6.4, злиття з Remix і framework mode у 7. Тому питання про нього рідко «що робить `useNavigate`» — частіше «як це
було в моїй версії», «коли з'явилося» і «на що замінили». Відповідь дає лише документація саме тієї версії, тож
корпус тут — не одна редакція сайту, а вся історія репозиторію, і кожен документ несе свої версії.

## Що в цій теці

- `corpus/` — документація React Router звичайними текстовими файлами; поруч `index.json` — паспорт, тобто опис
  копії: адреса, дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Перелік усіх 820 тегів
  лежить саме тут, у полі `tags` джерела `rr-docs`: оновлювач не питає в GitHub, які теги існують, а бере рівно
  оголошені.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями до сайтів і профіль домену: ім'я
  сервера, імена інструментів, домени, посилання на які лишаються у відповідях.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу, див. нижче);
  `.mcp.json` — запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df react-router <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація всіх версій | дерево кожного тегу через GitHub API, текст — `raw.githubusercontent.com` | `ghdocs-history` |
| довідник API | обхід посилань від `modules.html` у межах `/v8/` і `/v7/` | `typedoc` |
| нотатки релізів і журнал пакета | `CHANGELOG.md` гілок main і v6, `packages/react-router/CHANGELOG.md` | `changelog-v` |
| релізи | GitHub API, відбір за префіксом тегу | `ghreleases-tagged` |

Три читачі додано разом із цим примірником, окремими модулями (`engine/readers/ghhistory.py`,
`engine/readers/typedoc.py`, `engine/readers/changelogv.py`). Чинні читачі не змінено жодним рядком.

Особливості, які варто знати:

- **Сайт — не першоджерело.** reactrouter.com збирає сторінки з теки `docs/` репозиторію на тезі і віддає їх
  markdown-ом за адресою `…/<версія>/<сторінка>.md` — для будь-якого тегу, не лише для тих трьох ліній, що в
  перемикачі версій. Тож текст береться прямо з тегу: той самий, але без обходу сайту. v5.reactrouter.com і
  посилання «v3.x» — застосунки, зібрані з тих самих файлів репозиторію.
- **Де лежала документація.** 0.x — `doc/` і `docs/`; 1.x–3.x — `docs/` і `upgrade-guides/`; 4.x–5.x —
  `packages/react-router{,-dom,-native}/docs`; 6.x–8.x — `docs/`; 4.x–6.x — ще й кореневий `FAQ.md`. Читач бере
  всі ці теки з кожного тегу; на тезі, де теки немає, вона просто нічого не дає.
- **Nightly й experimental позначені міткою, а не номером.** Їхні теги — `v0.0.0-experimental-004e483a8`,
  номер 0.0.0 при тексті ліній 6–8. З таким номером фільтр `version: "0"` змішав би їх зі справжньою лінією 0.x
  2014 року. Тому версією в них стоїть `experimental` чи `nightly`; фільтр за цими словами збирає всі такі збірки
  разом, а конкретну збірку видно з адреси в шапці документа. Це 407 тегів із 820; нових текстів вони додали
  небагато, бо здебільшого повторюють сусідні релізи.
- **Адреса в шапці — найновіший тег.** Документ, що був однаковим у 6.4.0–6.30.6, посилається на blob у
  6.30.6, а всі версії, де він був таким, перелічені в рядку `# версія:`. Перевагу мають стабільні релізи й
  pre-release: nightly й experimental стоять у переліку тегів останніми.
- **Сторінки без тексту записані, але фрагментів не дають.** Рубрики меню сайту (`index.md` з самою шапкою
  «title: Guides») і заготовки старих версій (файл із самим заголовком «# IndexLink») — теж частина історії:
  документ є, а порожнього тексту корпус не ділить.
- **Старі заголовки-підкреслення.** Документація до 4.x пише заголовки як «Назва» з рядком `===` чи `---` під
  нею; читач перетворює їх на `#`/`##`, інакше документ не ділився б на розділи. Назва документа — поле `title`
  шапки YAML, або заголовок першого рядка, або ім'я файла: у 0.x сторінка `Route.md` починається одразу текстом, і
  сайт тоді називав її за файлом.
- **Довідник API є лише для 7.18.4 і 8.4.0.** api.reactrouter.com тримає по одному виданню на лінію; для 6.x і
  старших такого довідника немає взагалі (там API описано в самій документації). Версію видання видно з посилань
  «Defined in»: вони ведуть на коміт тегу `react-router@8.4.0` і `react-router@7.18.4`. `sitemap.xml` обох видань
  перелічує адреси `/dev/`, тому перелік будується обходом посилань.
- **Нотатки релізів у двох місцях.** З 6.4 GitHub Releases містять лише посилання на журнал змін, тож повні
  нотатки — у `CHANGELOG.md` (v7+ у main, v6 — у гілці v6). До 6.4 журналу в репозиторії не вели, і нотатки
  релізів GitHub — єдине джерело.

## Межі, про які треба пам'ятати

Документації React, Remix до його злиття з React Router 7, Next.js, TanStack Router та інших бібліотек тут немає —
лише згадки про них у тексті роутера. Для React поруч є окремий примірник `react`. Nightly й experimental — не
релізи: текст, що є лише в них, міг так і не вийти, і промпт велить моделі казати про це прямо.

## Токен GitHub

Перелік файлів кожного з 820 тегів — одне звернення до GitHub API на тег. Анонімний ліміт — 60 звернень на
годину, тож без токена лише перелік розтягнувся б на чотирнадцять годин. Токен кладеться рядком `GITHUB_TOKEN=…`
у `.env` цієї теки; досить найвужчого (fine-grained з `Public repositories (read-only)` або класичний без scope).
Читається він лише звідси й іде лише на `api.github.com` — подробиці в
[README примірника astro](../astro/README.md#токен-github).

Тексти файлів ліміту не витрачають — вони йдуть із `raw.githubusercontent.com`. Збирання з нуля при паузі в
секунду — близько двох годин: 23 хвилини на перелік тегів, година з чвертю на 2 857 файлів, чверть години на
довідник API.

## Установка venv

Єдиний крок, що робиться зсередини цієї теки, — і після нього треба повернутися в корінь. Активувати venv не
потрібно ані зараз, ані потім: `df` сам викликає `.venv/bin/python` примірника на кожному кроці.

```
cd instances/react-router
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..                      # назад у корінь фабрики: усі кроки df — тільки звідти
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, цей розділ пропускається — потрібен лише `vectors`, якщо колекції ще немає.

```
./df react-router sources --why   # перелік джерел і білий список
./df react-router refresh         # завантажити все задеклароване (~2 години)
./df react-router manifest        # оновити паспорт
./df react-router setup           # Qdrant чи пошук лише по словах
./df react-router vectors         # залити корпус у docs-react-router
./df react-router smoke           # перевірки
```

Порядок оновлення корпусу — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба
перезапустити: корпус сервер читає один раз, на старті.

## Спосіб А — власний захищений агент (усі чотири шари)

```
./df react-router tools                      # $0: під'єднання, перелік інструментів
./df react-router ask "How did route matching change between v5 and v6?"   # платно
```

Клієнт тут — наш код, тож працюють усі чотири шари: вхідний фільтр над запитом, правила перед кожним викликом
інструмента, список дозволених інструментів і вихідний фільтр разом із guardrail — окремим викликом дешевої моделі,
що перевіряє готову відповідь. Крок `ask` потребує `ANTHROPIC_API_KEY` у `.env`; `tools` не потребує нічого.

## Спосіб Б — сервер під Claude Code (HTTP)

З HTTP-транспортом сервер — окремий процес: його тримають запущеним, а Claude Code під'єднується до нього за
адресою. Тому підйом і інтеграція йдуть у такому порядку.

**1. Підняти сервер** (окремий термінал, з кореня фабрики `docfactory/`), і лишити його жити:

```
./df react-router serve                  # HTTP-сервер на порту з config.json (8765)
```

На старті сервер друкує, скільки фрагментів проіндексовано, і адресу `http://127.0.0.1:8765/mcp`. Готовий він
тоді, коли надрукував цей рядок, не раніше. Qdrant знайде сам; для самого під'єднання Docker не потрібен.

**2. Додати сервер у Claude Code** — одним зі способів:

- відкрити теку `instances/react-router/` як проєкт у Claude Code: він побачить `.mcp.json` цієї теки й
  запропонує сервер `react-router-docs` (адреса `http://127.0.0.1:8765/mcp`), який треба підтвердити;
- або командою: `claude mcp add --transport http --scope user react-router-docs http://127.0.0.1:8765/mcp`.
  Прапорець `--scope user` робить сервер видимим у всіх проєктах, а не лише в тій теці, з якої додали. Саме це
  потрібно, щоб сервером користувався проєкт, у якому працюють з роутером.

**3. Перевірити під'єднання.** У сесії Claude Code — команда `/mcp`: має бути `react-router-docs` і два
інструменти `search_docs`, `read_section`. Поза сесією той самий перелік дає `claude mcp list`.

**4. Користуватися.** Розмова з Claude Code лишається вільною: він сам кличе інструменти, коли питання стосується
React Router, і не кличе, коли ні. Запит усередину пишеться англійськими іменами роутера (індекс англійський), а
відповідь — мовою питання. Разом із цим сервером зазвичай тримають і `react-docs` (порт `8761`): у обох
однакові імена інструментів, але різні імена серверів, тож Claude Code бачить їх окремо, і кожен відповідає за
свою бібліотеку.

Клієнтів у сервера може бути скільки завгодно одночасно — друге вікно VS Code, інша тека, Claude Desktop; другий
раз `serve` для цього не запускають. Докладно про scope запису (local, project, user) і про Claude Desktop під
Windows при сервері у WSL — у [README примірника nestjs](../nestjs/README.md#спосіб-б--сервер-під-claude-code-http):
там усе те саме, змінюються лише ім'я й порт.

З іншого комп'ютера в мережі сервер недоступний, і це навмисно: він слухає `127.0.0.1`, а не `0.0.0.0`, і
автентифікації не має.

**5. Зупинити сервер.** У терміналі, де він живе, — Ctrl+C. Якщо термінал загублено, знайдіть процес за портом
і зупиніть його за номером:

```
ss -ltnp | grep 8765                     # покаже pid=NNNN процесу, що тримає порт
kill NNNN                                # м'яка зупинка: сервер закриває сесії й виходить
```

Зупиняти за іменем (`pkill -f spec_mcp`) не варто: під шаблон потрапляють сервери інших примірників.

**Якщо щось не так.** `[Errno 98] address already in use` — порт уже зайнятий, майже завжди попереднім, забутим
`serve`; хто саме тримає порт, покаже `ss -ltnp | grep 8765`, і той процес треба зупинити. `/mcp` показує
`react-router-docs` як «failed / not connected» — майже завжди сервер не піднятий (крок 1) або порт інший; звірте
адресу `http://127.0.0.1:8765/mcp` з полем `port` у `config.json`.
