# Оновлення корпусу react-router

Дві різні роботи: звичайне оновлення, коли в репозиторії з'явилися нові теги, і збирання примірника з нуля.
Порядок усередині кожної важливіший за самі команди, тому кроки пронумеровані.

Головне правило: **перелік тегів оголошується руками.** Оновлювач не питає в GitHub, які теги існують: він бере
рівно ті, що перелічені в полі `tags` джерела `rr-docs` у `sources.json`. Так вимагає білий список — тягнеться
лише задеклароване, — і так видно, що саме в корпусі. Новий реліз сам у корпус не потрапить, доки його тег не
вписано.

Друге правило: **новий тег змінює й старі документи.** Документ тут — неповторний текст файла, а в рядку
`# версія:` стоять усі теги, де файл був саме таким. Якщо 8.4.1 не змінив сторінку `useNavigate`, нового
документа не буде, але в наявного додасться версія 8.4.1. Тому після нових тегів `rr-docs` перезаписується
цілком (`refresh rr-docs`), а не докачується (`--missing`): з `--missing` нові тексти з'являться, а старі так і
не дізнаються, що дожили до нової версії, і фільтр `version: "8.4.1"` їх не знайде.

Третє правило: **нічого не видаляється.** Сторінку, яку прибрали з документації, корпус тримає під її старими
версіями: питання «як це було в 5.x» не має ламатися через те, що главу давно зняли. Ані `refresh`, ані
`vectors`, ані `manifest` нічого не стирають самі.

## 1. Вийшли нові релізи

**Крок 1. Дописати теги.** У `sources.json`, у поле `tags` джерела `rr-docs`, додається пара «тег → версія» на
кожен новий тег. Порядок має значення: перелік іде від найновішого, і адреса в шапці документа береться з
першого тегу, де файл був таким. Стабільні релізи й pre-release — угорі, у порядку версій; nightly й
experimental — наприкінці. Версія — номер без префікса (`react-router@8.5.0` → `8.5.0`); для nightly й
experimental — слово `nightly` чи `experimental`, бо номер 0.0.0 у їхніх тегах нічого не каже.

Список тегів репозиторію, без жодного звернення до API:

```
git ls-remote --tags https://github.com/remix-run/react-router.git | grep -v '\^{}' | sed 's#.*refs/tags/##' \
  | grep -E '^(react-router@|v)[0-9]'
```

**Крок 2. Якщо вийшла нова мажорна лінія** — перевірити, чи з'явилося видання довідника
`api.reactrouter.com/v9/`, і оголосити його так само, як `rr-api-8`. Версію видання видно з посилань «Defined in»
на будь-якій сторінці: вони ведуть на коміт, і `git tag --points-at <коміт>` у клоні назве тег. Коли видання
`/v8/` перезбирають на новому релізі лінії, поле `version` джерела `rr-api-8` оновлюється тим самим способом.

**Крок 3. Перевірити оголошення.**

```
./df react-router sources --why
```

**Крок 4. Завантажити.**

```
./df react-router refresh rr-docs rr-api-8 rr-api-7 rr-changelog rr-changelog-v6 rr-changelog-pkg rr-releases rr-releases-v
./df react-router manifest
./df react-router vectors
./df react-router smoke
# Ctrl+C у терміналі з serve, і знову: ./df react-router serve
```

Це повне перезавантаження, близько двох годин; інакше не можна з причини, описаної в другому правилі. Якщо
змінилися лише нотатки релізів, досить `refresh rr-changelog rr-changelog-pkg rr-releases`.

Якщо `smoke` скаржиться на число фрагментів — це не поломка, а наслідок того, що документація підросла. Нове число
записують у `checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік 820 тегів іде годинними
вікнами по 60 звернень.

**Крок 2. Усе одним прогоном.**

```
nohup ./df react-router refresh > /tmp/react-router-refresh.log 2>&1 &
```

Перші ~25 хвилин журнал мовчить, а `corpus/` порожній: читач складає перелік, проходячи дерево кожного з 820
тегів, і лише потім починає писати файли. Стан видно за кількістю файлів: `ls instances/react-router/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються, добереться
лише відсутнє. При збиранні з нуля це безпечно: список тегів не змінювався, тож і версії в записаних документах
правильні.

**Крок 4. Паспорт, вектори, перевірки.**

```
./df react-router manifest
./df react-router setup
./df react-router vectors
./df react-router smoke
./df react-router quality
./df react-router serve
```

Останній рядок — окремий термінал, і його лишають жити; під'єднання до Claude Code описане в
[README.md](README.md), розділ «Спосіб Б».

## Що робити, коли щось не так

**`збій: HTTP 403` на `api.github.com`.** Вичерпано ліміт звернень. З токеном це майже неможливо; без нього —
зачекайте до початку наступної години й повторіть.

**`збій: HTTP 429` на `raw.githubusercontent.com`.** Занадто часті звернення до CDN. Підніміть `pause_sec` у
`config.json` і повторіть із `--missing`.

**`GitHub обрізав дерево`.** Репозиторій виріс настільки, що API віддає перелік файлів тегу неповним. Читач тоді
відмовляється працювати, і це правильно: неповний перелік тихо дав би корпус із дірками. Сьогодні в дереві тегу
близько півтори тисячі записів, до межі далеко.

**`ім'я документа … уже зайняте іншою сторінкою`** (довідник API). Дві сторінки TypeDoc звелися до одного імені
файла навіть із крапкою в імені. Файл не записується, щоб один документ не затер другий; читач треба поправити.

**Фільтр за новою версією нічого не знаходить, хоча тег вписано.** Найімовірніше, після нових тегів `rr-docs`
докачали з `--missing`, а не перезаписали: нові версії є лише в нових документах. Повторіть `refresh rr-docs`.
