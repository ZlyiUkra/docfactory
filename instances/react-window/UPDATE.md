# Оновлення корпусу react-window

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи react-window чи його супутніх пакетів, і збирання з нуля.
Порядок усередині кожної важливіший за самі команди.

Головне правило: **перелік версій оголошується руками.** Оновлювач не питає в GitHub, які теги існують: він бере рівно
ті, що перелічені в полі `tags` джерел `rw-readme`, `rw-site-v1` і `rw-site-v2` у `sources.json`. Так вимагає білий
список, і так видно, що саме в корпусі. Новий реліз сам у корпус не потрапить, доки його не вписано.

Друге правило: **нова версія змінює й старі документи.** Документ — неповторний текст сторінки, а в рядку `# версія:`
стоять усі версії, де сторінка була саме такою. Тож після нових версій ці три джерела перезаписуються цілком
(`refresh rw-readme rw-site-v2`), а не докачуються (`--missing`): інакше старі тексти не дізнаються, що дожили до
нової версії, і фільтр `version` їх не знайде. Так само `types-react-window`: версії @types/react-window
зіставляються з комітами DefinitelyTyped щоразу заново.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Дописати версії.** Стабільні версії react-window і їхні теги, без жодного звернення до API:

```
git ls-remote --tags https://github.com/bvaughn/react-window.git | grep -v '\^{}' | sed 's#.*refs/tags/##' \
  | grep -E '^[0-9]+\.[0-9]+\.[0-9]+$' | sort -V | tail
```

Кожна нова версія дописується на початок поля `tags` джерела `rw-readme` і джерела своєї лінії (`rw-site-v2` для
2.x) парою «тег → версія» (`"2.3.4": "2.3.4"`). Перелік іде від найновішого. Альфи (`2.2.5-alpha.1`) не беруться.
Версія, що вийшла в npm без тегу, вписується комітом із поля `gitHead` реєстру
(`curl -s https://registry.npmjs.org/react-window | jq -r '.versions["X.Y.Z"].gitHead'`) — так у корпусі
стоять 1.2.3, 1.8.7 і 1.8.8.

Журнали змін (`rw-changelog`, `ril-changelog`, `ras-changelog`), релізи GitHub, README супутніх пакетів
(`npm-readme` сам бере всі версії з реєстру) і документи реєстру npm нових записів не потребують: вони читають
свої джерела цілком.

**Крок 2. Якщо вийшла нова мажорна лінія** (скажімо, 3.0):

- з'ясувати, чи сайт лишився тим самим (`src/routes.ts`, теки `public/generated/`): читач `react-window-site-v2`
  знає дві епохи сайту 2.x — `code-snippets` і `js-docs` до 2.2.3, `examples` і `docs` з 2.2.4. Нова епоха —
  привід перевірити читача на одному тезі, перш ніж качати все;
- у промптах замінити лінії: `prompts/search.txt` (абзаци «Where the documentation lived» і «Which version to
  search first») та `prompts/agent.txt` велять шукати в лініях "1" і "2";
- у `checks.json`, у десятці `quality_model`, звірити лінії й цілі з новими шляхами.

**Крок 3. Завантажити.**

```
./df react-window sources --why
./df react-window refresh
./df react-window manifest
./df react-window vectors
./df react-window smoke
# Ctrl+C у терміналі з serve, і знову: ./df react-window serve
```

`refresh` без назв — повне перезавантаження, кілька хвилин: спершу перелік дерев кожної версії, далі файли.
Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти (README, розділ «Архівний режим»),
а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік дерев іде годинними вікнами
по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df react-window refresh > instances/react-window/out/refresh.log 2>&1 &
```

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df react-window quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка
промпту, знову замір. Що це означає тут:

- **Дві лінії з різним API.** 1.x (FixedSizeList, VariableSizeList, FixedSizeGrid, VariableSizeGrid) досі має
  найбільше завантажень, 2.x (List, Grid) — поточна. Промпт велить без названої версії відповідати для обох.
- **Правила промпту, що вже є:** запит — назвою компонента, властивості чи методу, а не описом; для «як зробити» —
  шукати й сторінку прикладу; кожна відповідь каже, для якої версії вона.
- **Останній результат** — у README, абзац «Замір `quality`».
