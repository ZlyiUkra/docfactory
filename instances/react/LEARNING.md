# React — план вивчення

План для того, хто вже пише на React на рівні мідла і хоче вийти на роботу фулстеком, — і водночас повний шлях
для того, хто React тільки починає. Він перший у родині з трьох планів: React → NestJS → Next.js. Через усі три
проходить один проєкт: тут це SPA на Vite, у плані NestJS ([../nestjs/LEARNING.md](../nestjs/LEARNING.md)) він
отримує власний бекенд, у плані Next.js ([../nextjs/LEARNING.md](../nextjs/LEARNING.md)) переїжджає на Next.js і
зшивається з NestJS. Плани проходять по черзі, не паралельно. Кожен день пояснений від знайомого до нового: що
ви вже робите руками, що за цим стоїть і як це перевірити числом або спостереженням.

Шляхів два. **Шлях мідла** — тридцять один день за контрольними питаннями: перший викот застосунку в інтернет у
перший же день, живі ціни з біржі через WebSocket посередині й власний кластер Kubernetes наприкінці; він описаний
нижче, перед фазами. **Повний шлях** — шістдесят сім навчальних днів по півтори-дві години, від мови й браузера до
продакшну в кластері. П'ять днів на тиждень (два лишаються на те, щоб доганяти пропущене) дають трохи більше трьох
місяців повного шляху або трохи більше шести тижнів шляху мідла. Окремо стоїть **факультатив «крипта»** — п'ять
днів, ще тиждень: графік свічок, книга заявок, гаманець і транзакція на тестовій мережі. Для роботи фулстеком він
не потрібен.

| Фаза | Тема | Днів |
|------|------|------|
| 0 | База, якої React не дає: JS, TypeScript, браузер, інструменти | 12 |
| 1 | Ядро React — розділ Learn | 20 |
| 2 | Як React працює зсередини: заміри, рендер, конкурентність, компілятор | 8 |
| 3 | Екосистема: маршрути, серверний стан, живі дані, форми, глобальний стан, тести | 15 |
| 4 | Сервер: SSR, стрімінг, серверні компоненти | 3 |
| 5 | Продакшн: збірка, безпека, метрики, CI, викот у кластер Kubernetes | 9 |
| Факультатив | Крипта: свічки, книга заявок, гаманець, транзакція | 5 |

## Порядок трьох планів

Три плани — React, NestJS і Next.js — одна родина з одним наскрізним проєктом. Вчать їх по черзі, не паралельно:
кожен наступний спирається на зроблене в попередньому. Порядок такий.

| Етап | План і частина | Днів | Що виходить наприкінці |
|------|----------------|------|------------------------|
| 1 | React — шлях мідла | 31 | SPA в інтернеті з першого дня, живі ціни з біржі, тести, CI; власний кластер k3s і SPA в ньому як под |
| 2 | NestJS — фази 0–6 | 75 | власний бекенд для SPA: API, база, вхід і права, тести; локально — `docker compose`, на продакшні — поди в тому самому кластері |
| 3 | NestJS — фаза 7, живі дані й демо-мінімум | 8 | SPA бере ціни вже з власного сервера через WebSocket, з входом; у кластері — дві репліки; демо-мінімум для клієнта: власне ім'я, гостьовий вхід, нагляд ззовні, перевірена копія |
| 4 | Next.js — фази 0–8 | 84 | SPA переїхала на Next.js і зшита з NestJS, живі дані в Next.js; под Next.js замінив под SPA |
| 5 | Next.js — фаза 9, Kubernetes глибше і демо | 8 | викот з CI, оновлення без простою, резервні копії; демо для клієнта оновлене під Next.js |
| 6* | Факультатив «крипта»: React → NestJS → Next.js | 5 + 4 + 3 | графік свічок, книга заявок, гаманець, вхід гаманцем, власний токен |

\* кожен блок факультативу — після основної частини свого плану.

**Решта плану React** (дні повного шляху поза шляхом мідла) — не окремий етап: її добирають між етапами, коли
контрольне питання показало прогалину або проєкт дійшов до теми. **Факультатив** не потрібен для роботи фулстеком;
кожен його блок можна брати одразу після основної частини свого плану, але не раніше. Вступ до крипти — поняття,
інструменти, правила безпеки — лише в плані React, на початку факультативу; плани NestJS і Next.js на нього
посилаються. **Продакшн один на всю родину:** кластер k3s на безкоштовній машині Oracle Cloud з'являється наприкінці
шляху мідла React, і кожен план викочує в нього свою частину — поди, а не архіви на хостинг. Бекенд до фази 6 плану
NestJS живе на PaaS (Render, Railway чи Fly.io), далі — у кластері. **Модель токена** одна на всю родину:
access-токен у пам'яті, refresh-токен у куці `HttpOnly` з ротацією. Її власник — план NestJS, фаза 4; інші плани
беруть звідти.

## З чого почати

Цей план — перший у родині, тож його перший день — перший день усіх трьох планів. Він іде не на React, а на
робоче місце: коли інструменти стоять, кожен наступний день починається з вправи, а не з налаштувань. Займає це
один вечір.

**1. Система.** На Windows — WSL 2 з Ubuntu: усі команди плану написані для bash, фабрика документації працює лише
з-під Linux, а кластер у фазі 5 керується звідти ж. На Linux і macOS нічого додатково не треба. Проєкт тримайте у
файловій системі Linux (`~/projects/…`), а не на диску Windows (`/mnt/c/…`): через межу двох систем npm і Vite
працюють у рази повільніше.

**2. Інструменти.** Node.js поточної LTS-лінії — через менеджер версій (nvm або fnm), щоб наступні плани могли
перемкнути версію одним рядком. Git з вашим іменем і поштою (`git config --global user.name …`). Редактор із
підтримкою ESLint і Prettier. Chrome з розширенням React Developer Tools — у ньому ж DevTools і Lighthouse, якими
робляться всі заміри. Docker, `kubectl` і k3d зараз не ставте: вони потрібні з фази 5, дня 7, і там встановлюються з
поясненням кожного кроку. Обліковий запис Oracle Cloud для сервера заведіть за тиждень до фази 5, дня 8: перевірка
картки буває з відмовами (розділ «Що треба мати до викоту» у фазі 5).

**3. Сервери документації.** Фабрика, в якій лежить цей план, — і є довідник. З її кореня `./df react serve`
запускає сервер документації React; його підключають у клієнт MCP (налаштування — файл `.mcp.json` у теці
примірника, `instances/react/`). Інші примірники запускаються так само, `./df <назва> serve`, — але не всі одразу:
кожен сервер — окремий процес у пам'яті, тож тримайте піднятими лише ті, до яких дійшла фаза.

| Примірник | Коли потрібен |
|-----------|---------------|
| `react` | увесь план |
| `typescript` | фаза 0, дні 9–10; фаза 1, день 6 |
| `vite` | фаза 0, дні 11–12; фаза 1, день 20; фаза 5 |
| `eslint` | фаза 0, день 11; фаза 1, день 19; фаза 2, день 4 |
| `react-router` | фаза 3, дні 1–2 і 13; фаза 5, день 1 |
| `tanstack-query` | фаза 3, дні 3–8 і 13; факультатив |
| `react-hook-form`, `zod` | фаза 3, день 10 |
| `zustand`, `redux`, `tailwind` | за потребою: глобальний стан — фаза 3, день 11; стилі — фаза 0, день 11 |

Питання до сервера ставлять із версією: «у React 19.3», «у React Router 7», «у TanStack Query 5». Корпус тримає
багато версій, і без версії відповідь може прийти з глави для старої лінії.

**4. Репозиторій проєкту.** Публічний репозиторій на GitHub — це майбутнє портфоліо, тож заводьте його одразу, а
не «коли буде що показати». Сам застосунок з'явиться у фазі 0, день 11 (новачок) або в перший день шляху мідла;
README — сьогодні, ось скелет:

```markdown
# Назва проєкту

Жива версія: (адреса з'явиться в перший день шляху мідла)

## Відповіді на контрольні питання

## Журнал вимірів

| Дата | Що змінили | LCP | INP | CLS | JS, КБ gzip |
|------|------------|-----|-----|-----|-------------|

## Пройдені дні

- [ ] Шлях мідла, день 1 — контрольні питання; фаза 1, день 20
- [ ] Шлях мідла, день 2 — фаза 1, день 6
- [ ] Шлях мідла, день 3 — фаза 1, день 16
- [ ] …

## Рішення
```

**5. Відмітки днів.** Один рядок-чекбокс на день, як у скелеті; GitHub малює їх галочками. Галочка ставиться, коли
зійшлося «Перевірити себе», а не коли глава прочитана. День, що розтягнувся на два вечори, — все одно один рядок.
Чекбокси, журнал вимірів і розділ «Рішення» на співбесіді показують системну роботу краще за будь-які слова.

**6. Перша вправа.** Мідл — контрольні питання письмово (розділ про шлях мідла нижче), потім шлях мідла, день 1.
Новачок — фаза 0, день 1.

**Готово, якщо:** `node -v` показує LTS-лінію; клієнт MCP на питання «що повертає `useSyncExternalStore` у 19.3»
відповідає з посиланням на главу корпусу; репозиторій із README лежить на GitHub.

## Як користуватися планом

**Як влаштований день.** У кожного дня сім рядків. **Навіщо** — яку задачу тема розв'язує. **Що це** — пояснення
простими словами, від того, що ви вже знаєте, до нового. **Читати** — глави документації. **Сервери MCP** — які
сервери документації фабрики про це питати. **Зробити** — вправа по кроках. **Перевірити себе** — що має вийти, якщо
все правильно: число, рядок у лозі, поведінка на екрані. **Пастка** — помилка, яку на цьому місці роблять майже всі.
Дні викоту у фазі 5 мають усередині ще й короткі файли — Dockerfile і маніфести, — де кожен рядок пояснено.

**Сервери MCP.** Імена — як у Claude Code: сервер примірника `x` зветься `x-docs` (`react-docs`, `mdn-docs`,
`webstandards-docs`). Під заголовком кожної фази — усі сервери фази разом: їх варто підняти до її початку (`./df
<примірник> serve` з кореня фабрики) і додати в Claude Code командою з README примірника. Сервер відповідає з тих
самих глав, що названі в рядку «Читати», і дає адресу джерела, за якою відповідь можна перевірити. «Жодного» — джерела
дня поза фабрикою; чого бракує — у [карті навчання](../../docs/learning-map.md).

**Один наскрізний проєкт.** Не десяток навчальних застосунків, а один, який росте через усі фази й переходить у
плани NestJS і Next.js. Добре працює будь-що зі списками, формами, входом і публічною частиною: трекер задач із
публічними дошками, каталог з адмінкою, журнал витрат із кабінетом. Списки покажуть ключі й продуктивність, форми —
стан і валідацію, вхід — модель токенів, яку далі доробить бекенд. З фази 3 у проєкті є ще й модуль «список
монет»: користувач веде власний список криптопар (такі самі записи з власником, як і решта), а екран показує їхні
живі ціни з публічного ринкового стріму біржі Binance — без ключа й реєстрації. На ньому вчаться WebSocket і
швидкі оновлення; у плані NestJS ціни підуть уже через власний сервер.

**День — одиниця умовна.** Якщо тема не вляглася за день, беріть другий. Небезпечний не пропущений день, а
пропущена вправа: без неї тема лишається прочитаною, а не вивченою.

**Журнал вимірів.** З кінця фази 1 (фаза 1, день 20; на шляху мідла — перший день) у README проєкту живе таблиця:
дата, що змінили, LCP, INP, CLS, розмір JavaScript у КБ після gzip. Кожна вправа-замір у плані називає інструмент і
число, яке треба записати. Умови лабораторного заміру однакові щоразу: продакшн-збірка (`vite build` і
`vite preview` або викочена адреса), Lighthouse у режимі mobile, три прогони, у журнал іде медіана. Без журналу
«стало швидше» — це враження, а на співбесіді питають число. Що означають LCP, INP і CLS, пояснює словник нижче.

**Документація під рукою.** Цей примірник фабрики — і є довідник: `./df react serve` з кореня, далі питання до
MCP-сервера замість пошуку в гуглі. Корпус тримає документацію всіх версій React від 0.3 до 19.3 разом із
CHANGELOG, нотатками релізів і блогом, тож відповідь приходить із зазначенням версії. Для бібліотек екосистеми
підняті власні примірники — `react-router`, `tanstack-query`, `react-hook-form`, `zod`, `zustand`, `redux`,
`tailwind`, `vite`, `typescript`; вони запускаються так само: `./df <назва> serve`. Назви глав у плані
(у бектиках) — точні назви документів корпусу, їх можна питати дослівно. Якщо назва двозначна, поруч
словами сказано, яка саме: «`Installation` (Learn)» і «`Installation` (React Compiler)». Те, чого в корпусах немає,
позначено «поза корпусом» або «порада з практики».

**Версія.** Вчіть на React 19, останній патч лінії 19.3 (анонс у блозі React від 09.09.2026). Усе в плані — про
сучасний React із функціональними компонентами й хуками; класові компоненти трапляються рівно раз — у дні про межі
помилок, бо інакше межу помилок і досі не написати.

**Чому SPA на Vite, а не фреймворк.** Глава `Creating a React App` радить починати з фреймворку (Next.js, React
Router у режимі фреймворку тощо). План свідомо йде іншим шляхом, який документація описує поруч, у главі
`Build a React app from Scratch`: Vite з шаблоном `react-ts`, а маршрути, дані й розділення коду ви додаєте самі.
Так видно кожен механізм окремо, а фреймворк чекає на вас у плані Next.js. Розділ цієї глави «Step 2: Build Common
Application Patterns» — маршрутизація, отримання даних, розділення коду, продуктивність — це карта фаз 3 і 5.

## Словник: слова, без яких план не читається

- **Рендер і коміт.** Рендер — React викликає ваші функції-компоненти й отримує опис інтерфейсу. Коміт — React
  записує різницю в DOM. Малює пікселі вже браузер, після коміту. Три різні події в часі.
- **Стан і пропси.** Пропси — те, що компонент отримав від батька, лише для читання. Стан — пам'ять компонента
  між рендерами; змінюється тільки через функцію `set`, і кожна зміна просить новий рендер.
- **Знімок стану.** У кожному рендері стан — константа. Обробник події бачить значення того рендеру, в якому його
  створено, а не «поточне».
- **Чистий компонент.** Однакові пропси й стан — однаковий результат, і жодних змін зовнішнього світу під час
  рендеру. React на цьому будує все, від `<StrictMode>` до компілятора.
- **Ефект.** Код, що синхронізує компонент із чимось **зовнішнім**: мережа, підписка, віджет не на React. Не
  «зробити після рендеру».
- **Ключ (`key`).** Ідентичність елемента списку. За ним React вирішує, чий стан кому належить після зміни списку.
- **Ref.** Скринька для значення, яке живе між рендерами, але не викликає рендер при зміні; часто — посилання на
  DOM-вузол.
- **Контекст.** Спосіб передати значення вглиб дерева без пропсів на кожному рівні. Не менеджер стану.
- **Перехід (transition).** Оновлення, позначене як нетермінове: React може перервати його заради введення.
- **`<Suspense>` і межа помилок.** Перший показує заглушку, доки щось усередині чекає (код чи дані). Друга показує
  запасний екран, якщо щось усередині впало під час рендеру.
- **Мемоізація.** Запам'ятати результат і не рахувати вдруге, якщо входи не змінилися: `memo`, `useMemo`,
  `useCallback`. **React Compiler** робить це автоматично на збірці.
- **Серверний стан.** Дані, що належать серверу й у браузері лише кешуються: список задач, профіль. Протилежність —
  клієнтський стан: відкрите меню, введений текст.
- **Лоадер.** Функція маршруту, яка вантажить дані до того, як компонент сторінки відрендерився.
- **WebSocket.** Одне довге з'єднання між браузером і сервером, яким обидва боки шлють повідомлення будь-коли.
  Починається як звичайний HTTP-запит із проханням перейти на інший протокол (`Upgrade`), далі це вже не HTTP.
  Протилежність — запит-відповідь, де говорить лише той, хто спитав.
- **Зовнішній стор.** Дані, що живуть поза React — у звичайному модулі зі списком підписників. Компоненти читають
  їх через `useSyncExternalStore` і перемальовуються, лише коли стор повідомив про зміну.
- **SSR і гідратація.** SSR — HTML малюється на сервері. Гідратація — React у браузері «оживляє» цей HTML,
  навішує обробники на готову розмітку.
- **Серверний компонент (RSC).** Компонент, що виконується заздалегідь в окремому середовищі (на збірці чи на
  сервері) і свій код у браузер не шле. **Server Function** — функція на сервері, яку клієнт викликає мережею; до
  вересня 2024 усі вони звалися Server Actions.
- **Бандл і чанк.** Бандл — JavaScript, зібраний для браузера. Чанк — окремий файл бандла, що вантажиться, коли
  потрібен.
- **LCP, INP, CLS.** Три метрики швидкості сторінки (Core Web Vitals). LCP — коли з'явився найбільший видимий
  елемент. INP — наскільки швидко сторінка відповідає на клацання й набір тексту. CLS — наскільки «стрибає» макет.
- **Образ і контейнер.** Образ — застосунок, запакований разом з усім, що потрібно для запуску: тут це nginx і
  зібрана тека `dist`. Контейнер — запущений образ. Той самий образ однаково працює на вашому ноутбуці й на сервері.
- **Kubernetes, кластер, под.** Kubernetes — система, що запускає контейнери на машинах і стежить, щоб їх було
  стільки, скільки описано. Кластер — машини під її керуванням (у плані — одна). Под — найменша одиниця запуску:
  один контейнер або кілька разом. Поди руками не створюють: описують **Deployment** («хочу дві копії такого
  образу»), і Kubernetes сам підтримує цей стан — упав под, піднімає новий.
- **Маніфест.** Файл YAML з описом бажаного стану: Deployment, Service, маршрут. `kubectl apply -f файл` надсилає
  його в кластер, і кластер доводить себе до описаного.

### Контрольні питання

Відповідайте письмово, у README проєкту, у перший день шляху — до того, як відкрити документацію. Якщо відповідь

треба пройти цілком, понад тридцять один базовий.

- **Фаза 0.** Чому `items.push(x)` у стані не перемальовує екран? Як замикання робить «застаріле» значення в
  `setTimeout`? Що відбувається в браузері між зміною стилю й пікселями на екрані? Чим `unknown` відрізняється від
  `any`?
- **Фаза 1.** Чому `key` за індексом масиву ламає список із видаленням? Чому два поспіль `setCount(count + 1)`

  хоч його й хочеться написати? Як типізувати `children` і обробник події поля вводу?

- **Фаза 3.** Чому `useEffect` плюс `fetch` — водоспад запитів і гонки? Що робить лоадер маршруту? Чим `staleTime`

  чого вона принципово не тестує?

## П'ять пасток, які переживають будь-який рівень

- **Стан іммутабельний.** `items.push(x)` не перемальовує нічого: React порівнює посилання, а воно не змінилося.
  Це не примха бібліотеки, а наслідок того, як працює порівняння, — перший день фази 0 про це.
- **Рендер — не малювання.** Виклик компонента, запис різниці в DOM і пікселі на екрані — три різні події в часі.
  Половина питань «чому воно не оновилося» — це сплутані фази.
- **Ефект — не «зробити після рендеру».** Ефект синхронізує компонент із чимось зовнішнім. Якщо синхронізувати
  нічого, ефект не потрібен — про це є ціла глава, `You Might Not Need an Effect`.
- **Дані беруть до рендеру, а не після.** `useEffect` плюс `fetch` у кожному компоненті — це запити по черзі:
  батько завантажився, відрендерив дитину, дитина пішла по своє. Документація прямо радить вантажити дані в лоадерах
  маршрутів або на сервері (`Build a React app from Scratch`, розділ «Data Fetching»).
- **Клієнт нічого не захищає.** Захищений маршрут, схована кнопка, «секретна» змінна `VITE_*` — усе це видно
  будь-кому, хто відкрив інструменти браузера. Дані закриває бекенд; у фронтенді — лише зручність.

## Блок A. Мова — дні 1–5

### День 1. Значення й посилання

- **Навіщо.** React вирішує, чи змінився стан, порівнянням посилань. Без цього дня «чому не оновилося» — лотерея.
- **Що це.** Число чи рядок копіюються значенням. Об'єкт і масив — посиланням: дві змінні можуть вказувати на
  той самий об'єкт, і зміна через одну видна через іншу. `===` для об'єктів порівнює посилання, а не вміст, тож
  два однакові на вигляд об'єкти не рівні. Розгортання `{ ...user }` робить нову обгортку, але лише на один рівень:
  вкладені об'єкти спільні. Глибоку копію дає `structuredClone`. React порівнює стан через `Object.is` — по суті
  той самий `===`.
- **Читати:** у примірнику `mdn` — `Object.is()`, `Spread syntax (...)`, `Window: structuredClone() method`; у
  примірнику `webstandards` — `HTML Standard: 2.7 Safe passing of structured data`.
- **Сервери MCP:** `mdn-docs`, `webstandards-docs`.
- **Зробити:** 1) функція `addItem(list, item)`, що повертає новий масив і не чіпає вхідний; 2) `console.log`
  порівнянь `===` до й після; 3) змінити `user.address.city`, розгорнувши два рівні; 4) показати, що після
  `{ ...user }` поле `address` спільне з оригіналом.
- **Перевірити себе:** ви передбачили результат п'яти порівнянь `===` до запуску, і всі п'ять збіглися.
- **Пастка:** вважати розгортання глибокою копією. Зміна вкладеного об'єкта в «копії» — це зміна оригіналу.

### День 2. Масиви й об'єкти функційно

- **Навіщо.** Кожне оновлення списку в стані React — перетворення масиву без мутації.
- **Що це.** `map`, `filter`, `reduce`, `find`, `some` повертають нове й не чіпають вхідне. `sort`, `reverse`,
  `splice` і `push` змінюють масив на місці. Для них є немутуючі пари: `toSorted`, `toReversed`, `toSpliced`, `with`.
- **Читати:** у примірнику `mdn` — `Array`, розділ про копіювальні й мутуючі методи; `Object.freeze()`.
- **Сервери MCP:** `mdn-docs`.
- **Зробити:** 1) список із тисячі об'єктів-задач; 2) `Object.freeze` на масиві й кожному елементі; 3) набір
  перетворень: відфільтрувати, відсортувати за датою, перейменувати одне поле, порахувати суму.
- **Перевірити себе:** у суворому режимі модуля жодне перетворення не кинуло `TypeError` — отже, жодне не мутувало
  заморожені дані.
- **Пастка:** `items.sort()` змінює масив і повертає той самий масив. У стані React це тиха помилка: посилання не
  змінилося, екран не оновився.

### День 3. Функції та замикання

- **Навіщо.** **Головний день фази.** Увесь клас помилок «застарілого стану» з хуками — це замикання.
- **Що це.** Функція пам'ятає змінні з того місця, де її створили, а не з того, де її викликали. Обробник, створений
  у першому рендері, бачить значення першого рендеру назавжди. `let` у циклі створює нову змінну на кожен оберт,
  `var` — одну на всіх.
- **Читати:** у примірнику `mdn` — `Closures`, `let`.
- **Сервери MCP:** `mdn-docs`.
- **Зробити:** 1) лічильник на замиканні; 2) кнопка, що через три секунди показує значення змінної, яку ви
  встигли змінити тричі; 3) цикл із `setTimeout` на `var` і на `let`.
- **Перевірити себе:** ви пояснюєте, яке значення покаже кожен `setTimeout` і чому, до того як запустили.
- **Пастка:** думати, що функція читає «поточне» значення змінної. Вона читає ту змінну, яку бачила при створенні,
  — у React це прямо описано в главі `State as a Snapshot`, до якої ви дійдете у фазі 1.

### День 4. Модулі й пакети

- **Навіщо.** Проєкт на React — це сотні модулів і десятки пакетів. Треба розуміти, звідки що береться.
- **Що це.** ESM: `import` і `export`, іменований і типовий експорт. `package.json` описує залежності; `^19.3.0`
  дозволяє будь-яку 19.x не нижче 19.3.0, `~19.3.0` — лише 19.3.x. Файл блокування (`package-lock.json`) фіксує
  точні версії всього дерева; `npm ci` ставить рівно їх. `npx` запускає пакет, не встановлюючи його в проєкт.
- **Читати:** у примірнику `mdn` — `JavaScript modules`; у примірнику `nodejs` — `package.json` (розділи dependencies,
  devDependencies), `package-lock.json`, `npm-ci`, `npx`, посібник `About semantic versioning` (`^` і `~`).
- **Сервери MCP:** `mdn-docs`, `nodejs-docs`.
- **Зробити:** 1) розбити код днів 1–3 на модулі; 2) підключити одну зовнішню бібліотеку; 3) `npm ls` і
  знайти її залежності.
- **Перевірити себе:** ви кажете, яку версію поставить `npm install` для `^19.3.0` і чим `npm ci` відрізняється.
- **Пастка:** не комітити файл блокування. Тоді у вас і на CI стоять різні версії, і «у мене працює» стає правдою
  лише у вас.

### День 5. Асинхронність

- **Навіщо.** Будь-які дані в React приходять асинхронно, і порядок їх приходу — джерело половини гонок.
- **Що це.** Проміс — значення, яке буде. `async`/`await` — синтаксис поверх промісів. `Promise.all` чекає всіх
  паралельно і падає з першою помилкою; `Promise.allSettled` чекає всіх і повертає кожен результат. `await` у циклі
  для незалежних запитів виконує їх по черзі.
- **Читати:** у примірнику `mdn` — `Using promises`, `async function`, `Promise.all()`, `Promise.allSettled()`; у
  примірнику `webstandards` — `HTML Standard: 8 Web application APIs` (розділ 8.1.7 Event loops: задачі й
  мікрозадачі).
- **Сервери MCP:** `mdn-docs`, `webstandards-docs`.
- **Зробити:** 1) три фейкові запити із затримками 300, 500 і 700 мс; 2) послідовно через `await`;
  3) паралельно через `Promise.all`; 4) час кожного варіанта через `performance.now()`.
- **Перевірити себе:** два числа: близько 1500 мс і близько 700 мс.
- **Пастка:** `await` у циклі для незалежних запитів. Це той самий водоспад, що й `useEffect` плюс `fetch` у
  вкладених компонентах, — до нього план повернеться у фазі 3.

## Блок B. Мережа й браузер — дні 6–8

### День 6. Мережа

- **Навіщо.** Пошуковий рядок, що шле запит на кожну літеру, — класична гонка відповідей.
- **Що це.** `fetch` повертає відповідь навіть на 404 і 500: проміс відхиляється лише при мережевій помилці, тож
  статус перевіряють через `res.ok`. Тіло читається один раз (`res.json()`). `AbortController` скасовує запит:
  його сигнал передають у `fetch`, а `abort()` обриває запит, що ще летить.
- **Читати:** у примірнику `mdn` — `Using the Fetch API`, `Response: ok property`, `AbortController`; у примірнику
  `webstandards` — `DOM Standard: 3 Aborting ongoing activities`, `Fetch Standard: 5 Fetch API`.
- **Сервери MCP:** `mdn-docs`, `webstandards-docs`.
- **Зробити:** 1) поле пошуку, що на кожну літеру питає публічний API; 2) кожна нова літера скасовує попередній
  запит; 3) у вкладці «Мережа» ввімкнути повільну мережу й набрати слово швидко.
- **Перевірити себе:** у вкладці «Мережа» скасовані запити позначені як скасовані, а на екрані завжди результат
  останнього введення, навіть якщо попередня відповідь прийшла пізніше.
- **Пастка:** не перевірити `res.ok` — і показати сторінку помилки сервера як дані.

### День 7. DOM і події

- **Навіщо.** React навішує обробники за вас, але події живуть за правилами браузера.
- **Що це.** DOM — дерево вузлів. Атрибут — те, що в HTML; властивість — те, що в об'єкті вузла (`value` поля
  вводу змінюється, атрибут `value` — ні). Подія спливає від цілі вгору до кореня; делегування — один обробник на
  батькові замість сотні на дітях. `event.target` — де клацнули, `event.currentTarget` — чий обробник працює.
  `preventDefault` скасовує дію браузера (відправлення форми), `stopPropagation` — спливання.
- **Читати:** у примірнику `mdn` — `Introduction to events`, `Event bubbling`, `Event: preventDefault() method`; у
  примірнику `webstandards` — `DOM Standard: 2 Events`.
- **Сервери MCP:** `mdn-docs`, `webstandards-docs`.
- **Зробити:** список на сто елементів без React з одним обробником на батьківському `<ul>`, що видаляє елемент,
  по якому клацнули.
- **Перевірити себе:** в інструментах розробника на вкладці слухачів подій — один обробник, а не сто.
- **Пастка:** плутати `target` і `currentTarget`: клацнули по іконці всередині кнопки — і `target` уже іконка.

### День 8. Як браузер малює

- **Навіщо.** Метрики INP і CLS, до яких ви дійдете, — про те, скільки браузер рахує й перемальовує.
- **Що це.** Після зміни DOM браузер рахує стилі, компонування (де що стоїть), малювання й композицію шарів.
  Прочитати `offsetHeight` після запису стилю — змусити браузер перерахувати компонування негайно (примусове
  перекомпонування); у циклі це дуже дорого. Анімація `transform` і `opacity` обходиться без компонування.
- **Читати:** у примірнику `mdn` — `Populating the page: how browsers work`, `Window: requestAnimationFrame() method`;
  у примірнику `webstandards` — `HTML Standard: 8 Web application APIs` (розділ 8.1.7.3 Processing model, крок «update
  the rendering»); у примірнику `webdev` — `Avoid large, complex layouts and layout thrashing`, `Stick to
  Compositor-Only Properties and Manage Layer Count`.
- **Сервери MCP:** `mdn-docs`, `webstandards-docs`, `webdev-docs`.
- **Зробити:** 1) сторінка, що в циклі на тисячу елементів по черзі читає `offsetHeight` і пише `style.height`;
  2) записати профіль у вкладці «Продуктивність»; 3) переписати: спершу всі читання, потім усі записи;
  4) записати профіль знову.
- **Перевірити себе:** два числа — тривалість задачі до й після, і попередження про примусове перекомпонування
  зникли з профілю.
- **Пастка:** анімувати `top` і `left` замість `transform` — кожен кадр перераховує компонування.

## Блок C. TypeScript та інструменти — дні 9–12

### День 9. TypeScript: основи

- **Навіщо.** У фазі 1 ви типізуватимете пропси, стан і події. Без основ TypeScript кожна помилка типів у React
  виглядатиме як помилка React.
- **Що це.** Тип описує форму значення. `type` і `interface` для об'єктів майже рівноцінні. Об'єднання `A | B` —
  «одне з», звуження (`typeof`, `in`, перевірка поля) — спосіб довести компілятору, яке саме. Розрізнюване
  об'єднання — найкорисніший прийом для React: `{ status: 'loading' } | { status: 'success'; data: T } |
  { status: 'error'; error: string }`. `unknown` — «не знаю, що це, перевір»; `any` — «вимкни перевірку».
- **Читати:** у примірнику `typescript` — `The Basics (handbook-v2/Basics)`,
  `Everyday Types (handbook-v2/Everyday Types)`, `Narrowing (handbook-v2/Narrowing)`.
- **Сервери MCP:** `typescript-docs`.
- **Зробити:** 1) типізувати код днів 1–6 без жодного `any`; 2) відповідь `fetch` прочитати як `unknown` і
  звузити до свого типу; 3) стан запиту описати розрізнюваним об'єднанням.
- **Перевірити себе:** `tsc --noEmit` з `strict: true` без помилок, пошук `any` по коду нічого не знаходить;
  звертання до `data` у гілці `loading` — помилка компіляції.
- **Пастка:** `as MyType`, «щоб зникла помилка». Це не перевірка, а обіцянка компілятору, яку ніхто не
  перевіряє: дані з мережі як були неперевірені, так і лишилися.

### День 10. TypeScript: дженерики

- **Навіщо.** `useState<T>`, `useRef<T>`, хук запиту, що повертає `T`, — усе це дженерики.
- **Що це.** Параметр типу — «тип, який підставлять потім»: `function first<T>(list: T[]): T | undefined`.
  Обмеження `K extends keyof T` дозволяє лише ключі об'єкта. Службові типи `Partial`, `Pick`, `Omit`, `Record`
  будують нові типи зі старих.
- **Читати:** у примірнику `typescript` — `Generics (handbook-v2/Type Manipulation/Generics)`,
  `Keyof Type Operator (handbook-v2/Type Manipulation/Keyof Type Operator)`,
  `Utility Types (reference/Utility Types)`.
- **Сервери MCP:** `typescript-docs`.
- **Зробити:** 1) типізоване сховище `Store<T>` з методами `get`, `set`, `subscribe`; 2) функція
  `pick<T, K extends keyof T>(obj: T, keys: K[])`; 3) тип форми редагування як `Partial<Omit<Task, 'id'>>`.
- **Перевірити себе:** `pick(task, ['titel'])` з помилкою в назві ключа не компілюється.
- **Пастка:** дженерик там, де вистачає одного конкретного типу: код важче читати, а користі немає.

### День 11. Проєкт: Vite, лінт, TypeScript

- **Навіщо.** Звідси починається наскрізний проєкт. Інструменти, налаштовані сьогодні, ловитимуть помилки весь план.
- **Що це.** Vite — збирач і сервер розробки: у розробці віддає модулі браузеру майже як є і підміняє змінений
  модуль без перезавантаження (гаряча заміна), для продакшну збирає бандл. Проєкт створюється шаблоном `react-ts`
  — так радить глава `Build a React app from Scratch`. `eslint-plugin-react-hooks` — офіційні правила React для
  ESLint: правила хуків, повнота залежностей ефектів і діагностика React Compiler навіть без самого компілятора.
  Prettier форматує код; `tsconfig` з `strict: true` вмикає всі суворі перевірки.
- **Читати:** `Build a React app from Scratch` (крок 1 — Vite; крок 2 прогляньте як карту фаз 3 і 5),
  `Editor Setup`, `eslint-plugin-react-hooks`; у примірнику `vite` — `Getting Started`, `Features`; у примірнику
  `eslint` — `Configuration Files` (файл `eslint.config.js`, який створив шаблон) і README
  `` `eslint-plugin-react-hooks` `` (пресети `recommended` і `recommended-latest`). Якщо проєкт буде на Tailwind — у
  примірнику `tailwind` глава `Get started with Tailwind CSS`, розділ «Installing Tailwind CSS as a Vite plugin».
- **Сервери MCP:** `react-docs`, `vite-docs`, `eslint-docs`, `tailwind-docs`.
- **Зробити:** 1) `npm create vite@latest my-app -- --template react-ts`; 2) `git init` і перший коміт;
  3) переконатися, що лінт має пресет `recommended` з `eslint-plugin-react-hooks`; 4) свідомо викликати хук
  усередині `if` і запустити лінт; 5) змінити текст у компоненті з лічильником, не перезавантажуючи сторінку.
- **Перевірити себе:** лінт падає на правилі `rules-of-hooks`; після правки тексту лічильник зберіг значення —
  гаряча заміна спрацювала.
- **Пастка:** брати старий туторіал на Create React App. Документація відповідає прямо: «Create React App has been
  deprecated» («`Installation` (Learn)», розділ «Should I use Create React App?»).

### День 12. Інструменти браузера

- **Навіщо.** Усі заміри плану робляться тут. Треба вміти читати те, що бачите.
- **Що це.** Вкладка «Мережа»: водоспад запитів, розмір переданого й розпакованого, час до першого байта.
  «Продуктивність»: запис профілю, довгі задачі, уповільнення процесора в чотири рази (так ваш ноутбук
  імітує середній телефон). Карти коду (source maps) показують у налагоджувачі ваш код замість зібраного.
  Lighthouse — лабораторний аудит сторінки.
- **Читати:** у примірнику `vite` — `Why Vite` (чому в розробці модулі вантажаться окремо); документацію Chrome
  DevTools про вкладки «Network» і «Performance» (поза корпусом).
- **Сервери MCP:** `vite-docs`.
- **Зробити:** 1) відкрити проєкт у `npm run dev`, записати кількість запитів і переданий обсяг; 2) те саме на
  `npm run build && npx vite preview`; 3) поставити точку зупину у своєму компоненті в зібраній версії.
- **Перевірити себе:** дві пари чисел (запити, КБ) для розробки й збірки, і ви пояснюєте, чому в розробці запитів
  у рази більше.
- **Пастка:** міряти швидкість у режимі розробки. Він повільніший навмисно і нічого не каже про продакшн.

**Критерій завершення фази:** ви можете пояснити, чому зміна поля в об'єкті не помічається порівнянням і що
відбувається в браузері між кліком і новим кадром на екрані.

## Блок A. Компоненти й розмітка — дні 1–6

### День 1. Компоненти й модулі

- **Навіщо.** Компонент — одиниця всього в React, а розкладання по файлах — перше рішення в проєкті.
- **Що це.** Компонент — функція з великої літери, що повертає розмітку. Компоненти вкладаються один в одного, як
  теги. Оголошувати компонент **усередині** іншого не можна: на кожному рендері батька це буде новий тип, і React
  знищить стан дитини.
- **Читати:** `Your First Component`, `Importing and Exporting Components`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) шапка, список і картка — три файли; 2) зібрати їх на одному екрані; 3) свідомо оголосити
  компонент із полем вводу всередині батька, набрати текст і змусити батька перемалюватися.
- **Перевірити себе:** у кроці 3 введений текст зникає, лінт скаржиться на правило `static-components`, і ви
  пояснюєте чому.
- **Пастка:** компонент із малої літери. React сприйме `<card />` як невідомий HTML-тег.

### День 2. JSX

- **Навіщо.** JSX — не HTML, і його відмінності ламають розмітку в найнесподіваніших місцях.
- **Що це.** JSX компілюється у виклики функцій, що створюють об'єкти-описи елементів. Звідси правила: один
  кореневий елемент (або фрагмент `<>…</>`), закриті теги, `className`, атрибути в camelCase, `style` — об'єкт.
  У фігурних дужках — будь-який вираз JavaScript. Текст у дужках React **екранує сам**: рядок
  `<script>alert(1)</script>` з'явиться на екрані як текст, а не виконається. Це головний захист від XSS
  (впровадження чужого скрипту через дані).
- **Читати:** `Writing Markup with JSX`, `JavaScript in JSX with Curly Braces`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) розмітка з обчисленнями, умовами й підстановкою стилів; 2) у вкладці «Мережа» в режимі розробки
  відкрити свій зібраний модуль і знайти, у що перетворився JSX; 3) вставити рядок
  `<img src=x onerror=alert(1)>` у JSX через `{}`.
- **Перевірити себе:** у модулі видно виклики `jsxDEV(…)` на місці ваших тегів; рядок із кроку 3 показаний як
  текст, і жодного `alert`.
- **Пастка:** `dangerouslySetInnerHTML` з даними користувача. Документація попереджає: «If the HTML inside isn't
  trusted (for example, if it's based on user data), you risk introducing an XSS vulnerability»
  (`Common components (e.g. <div>)`, розділ Props). Якщо без нього ніяк — лише після очищення бібліотекою на
  кшталт DOMPurify (поза корпусом). Друга дірка — адреси з даних: `href` з `javascript:` виконує код, тому
  посилання з даних пропускайте, лише якщо вони починаються з `http:` або `https:` (у корпусі — блог React,
  «React v16.9.0 and the Roadmap Update», розділ «Deprecating `javascript:` URLs»).

### День 3. Пропси й умовний рендер

- **Навіщо.** Більшість компонентів — це функція від пропсів, без жодного стану.
- **Що це.** Пропси — аргументи компонента, лише для читання. `children` — те, що вкладено між тегами.
  Умовний рендер — звичайний JavaScript: `if`, тернарний оператор, `&&`. Розрізнюване об'єднання з фази 0 тут
  працює повністю: компонент за полем `status` малює одну з трьох гілок, і TypeScript не пустить у неіснуючу.
- **Читати:** `Passing Props to a Component`, `Conditional Rendering`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** картка, що виглядає по-різному для трьох станів даних — завантаження, помилка, дані, — без жодного
  стану всередині; три картки поруч з різними пропсами.
- **Перевірити себе:** спроба прочитати `data` у гілці помилки не компілюється; три картки показують три стани.
- **Пастка:** `{count && <Badge />}` при `count === 0` малює на екрані «0». Умова має бути булевою: `count > 0`.

### День 4. Списки й ключі

- **Навіщо.** Ключі — тема, яку питають на кожній співбесіді, і помилка, що проявляється лише в певних сценаріях.
- **Що це.** Список малюють через `map`. Ключ каже React, який елемент який: після видалення чи перестановки React
  за ключем знаходить, чий стан і чий DOM кому належить. Індекс масиву ключем не годиться, якщо список змінює
  порядок чи склад: ключі «з'їжджають» на сусідні елементи.
- **Читати:** `Rendering Lists`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) список рядків, у кожному поле вводу; 2) ключ — індекс; набрати текст у трьох полях і видалити
  другий рядок; 3) ключ — `id`; повторити.
- **Перевірити себе:** з індексом текст після видалення «переїжджає» в чужий рядок, з `id` — ні; ви пояснюєте це
  словами «стан належить позиції з ключем».
- **Пастка:** `key={Math.random()}`. Кожен рендер — нові ключі: React знищує й створює кожен рядок наново, стан і
  фокус губляться.

### День 5. Чистота й дерево

- **Навіщо.** На чистоті компонентів стоїть усе: `<StrictMode>`, конкурентний рендер, компілятор.
- **Що це.** Чистий компонент не змінює під час рендеру нічого, що існувало до нього: не пише в зовнішні змінні,
  не мутує пропси, не ходить у мережу. Зміни — в обробниках подій або, в крайньому разі, в ефектах. `<StrictMode>`
  у розробці викликає компоненти двічі, щоб нечистота стала помітною. Дерево рендеру (хто кого малює) і дерево
  модулів (хто кого імпортує) — різні дерева, і обидва корисно бачити.
- **Читати:** `Keeping Components Pure`, `Understanding Your UI as a Tree`, `<StrictMode>`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) компонент, що під час рендеру дописує рядок у зовнішній масив; 2) обгорнути застосунок у
  `<StrictMode>` і подивитися на результат; 3) полагодити.
- **Перевірити себе:** у кроці 2 рядків удвічі більше, ніж компонентів; після кроку 3 — стільки ж, і з
  `<StrictMode>`, і без нього.
- **Пастка:** вимкнути `<StrictMode>`, «бо він усе дублює». Він не створює помилку, а показує ту, що вже є.

### День 6. TypeScript у React

- **Навіщо.** На роботі React пишуть на TypeScript, і питання «як це типізувати» виникає щодня.
- **Що це.** Пропси описують інтерфейсом або типом. `children` — `React.ReactNode`: усе, що можна намалювати.
  Події — `React.ChangeEvent<HTMLInputElement>`, `React.FormEvent<HTMLFormElement>`. Хуки виводять тип із
  початкового значення, тому `useState(null)` назавжди лишиться `null` — потрібне явне `useState<User | null>(null)`.
  `useReducer` найкраще типізується розрізнюваним об'єднанням дій. `useRef<HTMLInputElement>(null)` — посилання на
  DOM. Контекст без розумного типового значення створюють як `createContext<T | null>(null)` плюс хук, що кидає
  помилку, якщо провайдера немає.
- **Читати:** `Using TypeScript` — зокрема розділи «Example Hooks» і «Useful Types».
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) типізувати всі компоненти днів 1–5; 2) обробник поля вводу й відправлення форми з точними
  типами подій; 3) контекст поточного користувача з хуком `useCurrentUser`, що кидає помилку без провайдера.
- **Перевірити себе:** `tsc --noEmit` без помилок, пошук `any` нічого не знаходить; передати неіснуючий проп —
  помилка компіляції.
- **Пастка:** `useState(null)` без типу. Компілятор не дасть записати туди користувача, і рука тягнеться до `any`.

## Блок B. Стан — дні 7–14

### День 7. Події й стан

- **Навіщо.** Стан — те, що робить інтерфейс живим. І перше місце, де інтуїція з JavaScript підводить.
- **Що це.** Обробник передають, а не викликають: `onClick={handleClick}`. Обробники передають пропсами вниз
  (`onSelect`), щоб дитина повідомляла батькові. `useState` дає значення й функцію `set`; звичайна змінна між
  рендерами не живе. Стан належить конкретному екземпляру компонента: два однакові компоненти мають окремий стан.
- **Читати:** `Responding to Events`, `State: A Component's Memory`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) форма з кількома полями на `useState`; 2) дитина повідомляє батькові про вибір через проп
  `onSelect`; 3) два екземпляри тієї самої форми поруч.
- **Перевірити себе:** введене в одну форму не з'являється в іншій.
- **Пастка:** `onClick={handleClick()}` — функція виконується під час рендеру, а не при клацанні.

### День 8. Рендер, коміт і знімок стану

- **Навіщо.** Звідси відповіді на два найчастіші питання співбесіди: «чим рендер відрізняється від коміту» і
  «чому стан у обробнику старий».
- **Що це.** Рендер запускається першим показом або зміною стану. React викликає компонент, порівнює результат із
  попереднім і в коміті записує в DOM лише різницю. Стан у рендері — знімок: `set` не змінює змінну зараз, а
  просить новий рендер з новим значенням. Кілька `set` в одному обробнику React складає в чергу й робить один
  рендер. Функція-оновлювач `setCount(c => c + 1)` отримує результат попереднього оновлення в черзі.
- **Читати:** `Render and Commit`, `State as a Snapshot`, `Queueing a Series of State Updates`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) обробник, що викликає `set` і одразу читає стан; 2) три `setCount(count + 1)` поспіль;
  3) три `setCount(c => c + 1)`; 4) `setTimeout` з `alert(count)` після зміни.
- **Перевірити себе:** до клацання ви записали очікування — 1, 3 і старе значення в `alert`, — і всі три збіглися.
- **Пастка:** чекати, що після `set` змінна вже нова. Нове значення буде лише в наступному рендері.

### День 9. Об'єкти й масиви в стані

- **Навіщо.** Це день 1 і день 2 фази 0, застосовані до стану, — і найчастіше джерело «не оновлюється».
- **Що це.** Стан, що є об'єктом чи масивом, не змінюють, а замінюють: нова копія з потрібною зміною. Для
  вкладених об'єктів копіюють кожен рівень на шляху до зміни. Глави показують, як додати, видалити, замінити,
  вставити й відсортувати без мутації, і де допомагає Immer.
- **Читати:** `Updating Objects in State`, `Updating Arrays in State`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) редагування `user.address.city` у стані; 2) список задач: додати, видалити, перейменувати,
  вставити в середину, відсортувати; 3) у розробці заморожувати новий стан функцією глибокого `Object.freeze`.
- **Перевірити себе:** жодна операція не кинула `TypeError`, і кожна оновила екран.
- **Пастка:** `[...items].sort()` правильно, `items.sort()` — ні; другий варіант тихо мутує стан і не дає рендеру.

### День 10. Стан як набір станів екрана

- **Навіщо.** Різниця між мідлом і джуном — у тому, як описано стан, а не в тому, скільки хуків знає людина.
- **Що це.** Декларативний інтерфейс описують станами, а не діями: «порожньо», «набирає», «надсилається», «успіх»,
  «помилка». Спершу перелічують візуальні стани, потім — що їх перемикає, потім — мінімальний стан, з якого вони
  виводяться. `Thinking in React` показує той самий підхід на всьому екрані: розбити на компоненти, знайти
  мінімальний стан, вирішити, де він живе.
- **Читати:** `Reacting to Input with State`, `Thinking in React`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) для форми з проєкту виписати всі візуальні стани; 2) намалювати їх усі поруч на одному
  службовому екрані, передаючи стан пропсом; 3) звести стан до одного поля `status` з розрізнюваним об'єднанням.
- **Перевірити себе:** службовий екран показує п'ять станів; комбінація «надсилається й помилка» неможлива за
  типом.
- **Пастка:** п'ять булевих `isLoading`, `isError`, `isSuccess`… — дають 32 комбінації, з яких можливі п'ять.

### День 11. Структура стану

- **Навіщо.** Зайвий стан — джерело розсинхронізацій, які шукають днями.
- **Що це.** Правила: не дублювати (те, що можна обчислити з наявного, не зберігають), не суперечити (два поля,
  що мусять змінюватися разом, — одне поле), не вкладати глибоко (плоска структура з ідентифікаторами).
  Обраний елемент зберігають як `selectedId`, а не копією об'єкта.
- **Читати:** `Choosing the State Structure`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) знайти в проєкті стан, що обчислюється з іншого, і прибрати його; 2) обраний елемент
  перевести на `selectedId`; 3) перейменувати обраний елемент у списку.
- **Перевірити себе:** кількість `useState` у проєкті зменшилася (запишіть два числа); після перейменування в
  списку панель обраного показує нову назву без додаткового коду.
- **Пастка:** `useState(props.value)` — стан ініціалізується один раз, і зміна пропса його вже не оновить.

### День 12. Спільний стан і скидання стану

- **Навіщо.** Два компоненти мусять бачити те саме, а форма мусить очищатися при зміні сутності.
- **Що це.** Спільний стан піднімають до найближчого спільного батька й передають униз пропсами. Стан у React живе
  не в компоненті, а в позиції в дереві: той самий компонент на тому самому місці зберігає стан, навіть якщо
  пропси інші. Інший `key` на тій самій позиції — інший екземпляр із чистим станом.
- **Читати:** `Sharing State Between Components`, `Preserving and Resetting State`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) два синхронізовані компоненти через спільного батька; 2) форма редагування сутності, де перехід
  на іншу сутність має скидати введене, — через `key={entity.id}`, без ефекту.
- **Перевірити себе:** перемикання між сутностями очищає форму; у коді форми немає `useEffect`.
- **Пастка:** скидати форму ефектом `useEffect(() => setText(''), [id])`. Один кадр показує старий текст, і
  рендерів удвічі більше.

### День 13. Редюсер

- **Навіщо.** Коли один обробник міняє п'ять полів стану, логіку краще зібрати в одному місці.
- **Що це.** Редюсер — чиста функція `(стан, дія) → новий стан`. Компонент лише надсилає дії (`dispatch`), а що з
  ними робити, вирішує редюсер. Його можна тестувати без React, просто викликом.
- **Читати:** `Extracting State Logic into a Reducer`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) перевести складну форму з кількох `useState` на `useReducer` з типізованим об'єднанням дій;
  2) три перевірки редюсера звичайним викликом функції з `console.assert`.
- **Перевірити себе:** перевірки проходять без рендеру будь-якого компонента; неіснуючий тип дії не компілюється.
- **Пастка:** запит у мережу чи `Date.now()` усередині редюсера. Він має бути чистим, як компонент.

### День 14. Контекст

- **Навіщо.** Тема, поточний користувач, мова — значення, які потрібні глибоко в дереві.
- **Що це.** Контекст передає значення всім нащадкам провайдера без пропсів на кожному рівні. Будь-яка зміна
  значення контексту перемальовує всіх, хто його читає, — вибіркової підписки немає. Тому контекст — механізм
  передачі, а не менеджер стану. Редюсер плюс контекст — спосіб дати глибоким компонентам і стан, і `dispatch`.
- **Читати:** `Passing Data Deeply with Context`, `Scaling Up with Reducer and Context`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) тема через контекст; 2) у `React Developer Tools` увімкнути підсвічування перемальовувань;
  3) перемкнути тему і подивитися, що підсвітилося.
- **Перевірити себе:** ви називаєте кожен підсвічений компонент і причину його рендеру.
- **Пастка:** один великий контекст «для всього». Зміна будь-якого поля перемальовує всіх споживачів.

## Блок C. Ref, ефекти й перший викот — дні 15–20

### День 15. Ref

- **Навіщо.** Фокус, прокручування, ідентифікатор таймера — те, що не має перемальовувати екран.
- **Що це.** `useRef` дає об'єкт `{ current }`, що живе між рендерами; зміна `current` рендер не викликає. Ref на
  DOM-вузол дає доступ до `focus()`, `scrollIntoView()`. У React 19 `ref` — звичайний проп, і для передачі ref
  дочірньому компоненту `forwardRef` більше не потрібен.
- **Читати:** `Referencing Values with Refs`, `Manipulating the DOM with Refs`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) фокус на полі після відкриття форми; 2) прокручування до нового елемента списку; 3) секундомір
  з ідентифікатором інтервалу в ref; 4) лічильник кліків у ref поруч із лічильником у стані.
- **Перевірити себе:** лічильник у ref збільшується (видно в `console.log`), але екран не оновлюється, доки не
  зміниться стан.
- **Пастка:** читати чи писати `ref.current` під час рендеру. Лінт (правило `refs`) про це скаже.

### День 16. Синхронізація ефектами

- **Навіщо.** Ефект — найпотужніший і найнебезпечніший інструмент React.
- **Що це.** Ефект запускається після коміту й синхронізує компонент із зовнішньою системою: підключитися,
  підписатися, запустити віджет. Функція прибирання відключає те, що підключив ефект. У розробці `<StrictMode>`
  монтує компонент двічі — підключити, відключити, підключити, — щоб перевірити, що прибирання є. Запит у мережу в
  ефекті потребує прибирання (прапорець `ignore` або `AbortController`), інакше старі відповіді перетирають нові.
- **Читати:** `Synchronizing with Effects`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) ефект, що «підключається» до кімнати чату (лог `connect`/`disconnect`); 2) прибирання;
  3) запит у мережу з `AbortController` і прибиранням; 4) порівняти лог у розробці й у `vite preview`.
- **Перевірити себе:** у розробці в лозі `connect, disconnect, connect`, у збірці — один `connect`; швидке
  перемикання кімнат не показує чужих даних.
- **Пастка:** вимкнути `<StrictMode>`, щоб ефект не спрацьовував двічі. Подвійний запуск показує відсутнє
  прибирання, а не створює проблему.

### День 17. Коли ефект не потрібен

- **Навіщо.** **Головний день фази.** Зайві ефекти — найдорожча звичка в React-коді: зайві рендери, мерехтіння,
  ланцюги оновлень.
- **Що це.** Ефект не потрібен, щоб перетворити дані для рендеру (обчисліть під час рендеру), щоб відреагувати на
  дію користувача (це робота обробника), щоб скинути стан при зміні пропса (`key`), щоб обчислити одне поле стану
  з іншого (не зберігайте похідне). Ефект потрібен лише для синхронізації із зовнішньою системою.
- **Читати:** `You Might Not Need an Effect`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) порахувати `useEffect` у проєкті; 2) прибрати щонайменше три: похідне значення — в обчислення,
  реакцію на клік — в обробник, скидання — в `key`; 3) запустити лінт.
- **Перевірити себе:** два числа ефектів до й після; поведінка не змінилася; лінт без попереджень
  `set-state-in-effect`.
- **Пастка:** ланцюг ефектів, де кожен ставить стан, на який реагує наступний. Кожна ланка — зайвий рендер.

### День 18. Життєвий цикл ефекту й події поза ним

- **Навіщо.** «Ефект перепідключається, коли не треба» — типова скарга. Причина — неправильна модель у голові.
- **Що це.** У ефекту немає «монтування» й «розмонтування», є лише «почати синхронізацію» і «зупинити». Він
  перезапускається, коли змінилося реактивне значення, яке він читає (пропс, стан, усе обчислене з них). Логіку,
  яка має читати свіже значення, але не перезапускати ефект (наприклад, тему сповіщення), виносять у функцію
  `useEffectEvent`.
- **Читати:** `Lifecycle of Reactive Effects`, `Separating Events from Effects`; довідка `useEffectEvent`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) вибір кімнати чату й перемикач теми сповіщень; 2) ефект підключення читає і кімнату, і тему;
  3) винести показ сповіщення з темою в `useEffectEvent`.
- **Перевірити себе:** у лозі зміна кімнати дає перепідключення, зміна теми — ні.
- **Пастка:** думати категоріями «при монтуванні». Ефект синхронізується з тим, що читає, а не з часом життя
  компонента.

### День 19. Залежності ефекту й власні хуки

- **Навіщо.** Залежності, які «прибирають» коментарем для лінта, — бомба уповільненої дії.
- **Що це.** Залежності не обирають, а описують: це все реактивне, що ефект читає. Щоб залежність зникла, треба
  змінити код — перенести об'єкт чи функцію всередину ефекту, прочитати значення через оновлювач стану, винести
  нереактивне в `useEffectEvent`. Власний хук — функція з префіксом `use`, що ділиться **логікою**, а не станом:
  кожен виклик має свій стан.
- **Читати:** `Removing Effect Dependencies`, `Reusing Logic with Custom Hooks`; у примірнику `eslint` — README
  `` `eslint-plugin-react-hooks` ``: як правило `exhaustive-deps` перевіряє залежності власних хуків.
- **Сервери MCP:** `react-docs`, `eslint-docs`.
- **Зробити:** 1) знайти ефект з об'єктом чи функцією в залежностях і прибрати їх, змінивши код; 2) винести
  повторювану логіку у власні хуки `useOnlineStatus` і `useDebouncedValue` з типами.
- **Перевірити себе:** пошук `eslint-disable` по проєкту нічого не знаходить; два компоненти з тим самим хуком
  мають незалежні значення.
- **Пастка:** вимкнути правило `exhaustive-deps` для рядка. Ефект почне читати застарілі значення — день 3 фази 0
  в дії.

### День 20. Збірка, перший викот і журнал вимірів

- **Навіщо.** Застосунок, якого немає в інтернеті, не існує ні для роботодавця, ні для замірів. Перший викот —
  справа тридцяти хвилин, і робиться він рано, а не «коли буде готово».
- **Що це.** `vite build` складає теку `dist`: `index.html` і файли в `assets/` з хешем вмісту в імені. Статичний
  хостинг просто роздає цю теку — сервер не потрібен. Звіт `vite build` друкує розмір кожного файла й розмір після
  gzip — це і є число «JS-бандл» для журналу. `vite preview` запускає зібране локально.
- **Читати:** у примірнику `vite` — `Building for Production`, `static-deploy` (розділи про Netlify, Vercel чи
  Cloudflare — оберіть один хостинг з безкоштовним планом).
- **Сервери MCP:** `vite-docs`.
- **Зробити:** 1) `npm run build` і подивитися на `dist`; 2) `npx vite preview`; 3) викотити `dist` на обраний
  хостинг; 4) Lighthouse в режимі mobile на викоченій адресі, три прогони; 5) завести в README журнал вимірів:
  дата, «перший викот», LCP і CLS (медіана), INP — прочерк (його перший замір у фазі 2, день 5), КБ gzip
  головного JS-файла зі звіту збірки.
- **Перевірити себе:** адреса відкривається з телефона; у журналі перший рядок із числами.
- **Пастка:** вважати, що все в збірці приватне. Усе з `dist` — і кожна змінна `VITE_*` у ньому — публічне;
  секретів у фронтенд-збірці не буває. До цього план повернеться у фазі 5, день 2.

**Критерій завершення фази:** ви можете сказати, чому компонент перемалювався, не вгадуючи, а дивлячись на код;
застосунок живе в інтернеті, і в журналі вимірів є перший рядок.

# Фаза 2. Як React працює зсередини — 8 днів

**Сервери MCP фази:** `react-docs`, `eslint-docs`, `webdev-docs`.

Фаза, після якої зникає слово «магія». Головне правило: жодна оптимізація без заміру до неї. Міряйте на
продакшн-збірці або на спеціальній збірці для профілювання, з уповільненням процесора в чотири рази, — режим
розробки повільніший навмисно, а `<StrictMode>` у ньому рендерить усе двічі. Кожен замір іде в журнал вимірів.

### День 1. Профайлер

- **Навіщо.** «Повільно» — не діагноз. Профайлер називає компонент і мілісекунди.
- **Що це.** `React Developer Tools` записує профіль: кожен коміт, які компоненти рендерились і скільки часу.
  `<Profiler>` робить те саме з коду: колбек `onRender` отримує `actualDuration` — скільки зайняв рендер піддерева.
  У продакшн-збірці профілювання вимкнене; для замірів є окрема збірка для профілювання — `react-dom/profiling`
  замість `react-dom/client`, підставлена псевдонімом у збирачі.
- **Читати:** `React Developer Tools`, `<Profiler>`, `React Performance tracks` (розділ «Using profiling builds»).
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) окремий режим збірки (`vite build --mode profile`), де `resolve.alias` підміняє
  `react-dom/client` на `react-dom/profiling`; 2) `<Profiler>` навколо головного екрана з виводом `actualDuration`;
  3) записати профіль однієї дії з уповільненням процесора 4×.
- **Перевірити себе:** у журналі рядок: найдорожчий компонент, його `actualDuration` у мс, кількість комітів на
  одну дію.
- **Пастка:** профілювати в режимі розробки. Числа будуть у кілька разів більші й покажуть не те.

### День 2. Узгодження дерева

- **Навіщо.** «Чому стан дитини зник» і «чому не зник, хоча мав» — це узгодження.
- **Що це.** Після рендеру React порівнює нове дерево зі старим. Той самий тип на тій самій позиції — React
  оновлює наявний екземпляр і зберігає стан. Інший тип — знищує все піддерево разом зі станом і будує наново.
  У списках позицію замінює ключ. Звідси й правило дня 1 фази 1: компонент, оголошений усередині іншого, — щоразу
  новий тип.
- **Читати:** `Preserving and Resetting State` (знову, під кутом алгоритму); `Reconciliation` — легасі-документація
  до React 18 включно, у новій документації окремої глави немає, але правила типу й ключа ті самі.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) обгортку дочірнього компонента з полем вводу умовно міняти між `<div>` і `<section>`;
  2) `isEditing ? <Form /> : <Form />` з різними пропсами; 3) той самий випадок, але з різними `key`;
  4) записати передбачення до кожного кроку.
- **Перевірити себе:** для чотирьох змін дерева ваші передбачення «стан виживе / не виживе» збіглися з поведінкою.
- **Пастка:** очікувати, що дві гілки тернарного оператора з тим самим компонентом — різні екземпляри. Для React
  це та сама позиція й той самий тип.

### День 3. Пакетування оновлень

- **Навіщо.** Кількість рендерів — перше, що питають про продуктивність.
- **Що це.** Усі `set` в одному обробнику React складає в один рендер. З React 18 те саме відбувається й у
  `setTimeout`, промісах і нативних подіях — автоматичне пакетування. `flushSync` змушує React застосувати
  оновлення негайно, наприклад щоб прокрутити до щойно доданого елемента, — і платить за це зайвим комітом.
- **Читати:** `Queueing a Series of State Updates` (розділ «React batches state updates»), `flushSync`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) три `set` у обробнику кліку, у `setTimeout` і після `await`; 2) порахувати коміти через
  `onRender` у `<Profiler>`; 3) прокручування до нового елемента списку з `flushSync` і без.
- **Перевірити себе:** таблиця в журналі: три випадки — по одному коміту; з `flushSync` — два, а без нього
  прокручування не доходить до нового елемента.
- **Пастка:** `flushSync` усюди, «щоб стан оновився одразу». Він ламає пакетування і робить застосунок повільнішим.

### День 4. Мемоізація і React Compiler — один замір

- **Навіщо.** «Коли `useMemo` справді допомагає» — питання співбесіди, на яке відповідають числами.
- **Що це.** `memo` пропускає рендер компонента, якщо пропси не змінилися. `useMemo` запам'ятовує результат
  обчислення, `useCallback` — саму функцію, щоб посилання не змінювалося. Документація радить міряти:
  `console.time` навколо обчислення; якщо набігає близько 1 мс чи більше, мемоізація має сенс (`useMemo`, розділ
  «How to tell if a calculation is expensive?»). React Compiler мемоізує автоматично на збірці, і він уже не
  експеримент: «React Compiler is now stable and has been tested extensively in production» («`Introduction`
  (React Compiler)», розділ «Is it safe to use?»). У новому коді документація радить покладатися на компілятор, а
  `useMemo` і `useCallback` лишати там, де потрібен точний контроль. Наявну ручну мемоізацію не прибирати: «removing
  it can change compilation output». Компілятор працює лише з кодом, що дотримується `Rules of React`; де правила
  порушено, він компонент пропускає, а `eslint-plugin-react-hooks` показує де.
- **Читати:** `memo`, `useMemo`, `useCallback`, «`Introduction` (React Compiler)», «`Installation` (React
  Compiler)» (розділи «Basic Setup › Vite» і «Check React DevTools»), `Rules of React`, `eslint-plugin-react-hooks`;
  у примірнику `eslint` — CHANGELOG плагіна: з якої версії в ньому правила компілятора.
- **Сервери MCP:** `react-docs`, `eslint-docs`.
- **Зробити:** один і той самий екран — список на дві тисячі елементів із фільтром і лічильником в іншому кутку —
  у трьох гілках: 1) без мемоізації; 2) з ручними `memo`, `useMemo`, `useCallback`; 3) без ручної мемоізації, з
  увімкненим компілятором. Для кожної на збірці для профілювання: скільки елементів списку рендериться на клік
  лічильника, тривалість коміту, `console.time` фільтра.
- **Перевірити себе:** три рядки в журналі; у гілці 3 компоненти мають у `React Developer Tools` позначку
  «Memo ✨»; ви можете назвати місце, де мемоізація не дала нічого, і чому.
- **Пастка:** `memo` на компоненті, якому передають новий об'єкт чи функцію в кожному рендері, — порівняння
  завжди «змінилося», і `memo` лише додає роботи. Друга пастка — масово видаляти `useMemo`, увімкнувши компілятор.

### День 5. `useTransition` і перший замір INP

- **Навіщо.** Поле фільтра, що «замерзає» на кожній літері, — найпомітніше гальмо для користувача, і саме його
  міряє INP.
- **Що це.** Оновлення бувають термінові (введення в поле) і нетермінові (перемалювати важкий список). Обгорнуте
  в `startTransition` оновлення React рендерить у фоні й може перервати заради нового введення. `isPending`
  каже, що перехід ще триває.
- **Читати:** `useTransition` — зокрема розділ «Troubleshooting › Updating an input in a Transition doesn't work»;
  `startTransition`; у примірнику `webdev` — `Interaction to Next Paint (INP)`, README `web-vitals` (функція `onINP`).
- **Сервери MCP:** `react-docs`, `webdev-docs`.
- **Зробити:** 1) штучно повільний список (кожен рядок рахує щось 1 мс) із фільтром; 2) уповільнення
  процесора 4×, набрати слово; 3) INP взаємодії — у вкладці «Продуктивність» (живі метрики) або через `onINP` з
  бібліотеки web-vitals; 4) оновлення списку — в перехід, поле лишається терміновим; 5) заміряти знову.
- **Перевірити себе:** два числа INP у журналі, до й після; поле вводу відгукується одразу. Пороги «добре» й
  «погано» для INP публікує web.dev: у примірнику `webdev` — `Interaction to Next Paint (INP)` (розділ «What is a
  good INP score?»), а як їх вивели — `How the Core Web Vitals metrics thresholds were defined`.
- **Пастка:** загорнути в перехід стан самого поля вводу. Контрольоване поле перестає встигати за набором.

### День 6. `useDeferredValue`

- **Навіщо.** Той самий результат, коли сеттера у вас немає: значення прийшло пропсом.
- **Що це.** `useDeferredValue(value)` повертає «відстаючу» копію значення: спершу React рендерить зі старою,
  потім у фоні — з новою. Працює, лише якщо повільна частина вміє пропускати рендер з тими самими пропсами:
  документація загортає її в `memo` (з компілятором це відбувається само). Різниця між `value` і відкладеним
  значенням — ознака «дані застаріли», її показують напівпрозорістю.
- **Читати:** `useDeferredValue` (розділ «Deferring re-rendering for a part of the UI»).
- **Сервери MCP:** `react-docs`.
- **Зробити:** той самий список із дня 5 через `useDeferredValue`; напівпрозорість, доки значення відстає; INP.
- **Перевірити себе:** третє число INP у журналі; ви кажете, коли брати перехід (ви володієте сеттером), а коли
  відкладене значення (значення приходить ззовні).
- **Пастка:** відкласти значення, але не мемоізувати повільний компонент. Він усе одно рендериться з кожною
  літерою, і виграшу немає.

### День 7. Віртуалізація довгих списків

- **Навіщо.** Десять тисяч рядків у DOM гальмують будь-який браузер, хоч скільки мемоізуйте.
- **Що це.** Віртуалізація малює лише видимі рядки плюс невеликий запас, а решту заміщує порожнім місцем
  потрібної висоти. Кількість DOM-вузлів перестає залежати від довжини списку.
- **Читати:** `Optimizing Performance`, розділ «Virtualize Long Lists» — легасі-документація React 16–18, у новій
  документації його немає; документацію react-window або TanStack Virtual (поза корпусом); у примірнику `webdev` —
  `How large DOM sizes affect interactivity, and what you can do about it`.
- **Сервери MCP:** `react-docs`, `webdev-docs`.
- **Зробити:** 1) список на 10 000 рядків; 2) кількість вузлів: `document.querySelectorAll('*').length`; 3) INP
  набору у фільтр (як у дні 5); 4) віртуалізувати; 5) заміряти обидва числа знову.
- **Перевірити себе:** дві пари чисел у журналі — вузли й INP до й після.
- **Пастка:** віртуалізувати список на п'ятдесят рядків. Складність є, виграшу немає, а пошук `Ctrl+F` браузера
  перестає знаходити невидимі рядки.

### День 8. `<Suspense>` і межі помилок

- **Навіщо.** Що бачить користувач, поки код чи дані вантажаться, і коли щось упало, — частина інтерфейсу, а не
  випадковість.
- **Що це.** `<Suspense>` показує заглушку, доки щось усередині «чекає»: лінивий компонент (`lazy`) або дані з
  бібліотеки, що вміє чекати разом із Suspense. Межа помилок ловить помилки **рендеру** нащадків і показує запасний
  екран. Пишеться вона досі класом (`static getDerivedStateFromError`, `componentDidCatch`) — це єдине місце плану,
  де потрібен клас. Помилок в обробниках подій і в асинхронному коді межа не ловить. Опції `createRoot` —
  `onCaughtError` і `onUncaughtError` — точка, куди підключають збирач помилок (сам збір, Sentry, — у плані
  Next.js, фаза 7, день 9).
- **Читати:** `<Suspense>`, `lazy`, `Component` (розділ «Catching rendering errors with an Error Boundary»),
  `createRoot` (розділ «Error logging in production»); поза корпусом — документація Sentry для React.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) важкий компонент через `lazy` під `<Suspense>`; 2) межа помилок навколо; 3) кинути помилку в
  рендері; 4) кинути помилку в `onClick`; 5) у `createRoot` передати `onCaughtError`, що пише помилку й
  `componentStack` у консоль.
- **Перевірити себе:** крок 3 показує запасний екран, крок 4 — ні; у консолі є стек компонентів із кроку 3.
- **Пастка:** вважати, що межа помилок ловить усе. Помилку в обробнику ловлять `try/catch` у самому обробнику.

**Критерій завершення фази:** на питання «чому повільно» ви відповідаєте назвою компонента й числом з профайлера,
а не здогадом; у журналі є INP.

## Блок A. Маршрути й серверний стан — дні 1–5

### День 1. Маршрути

- **Навіщо.** Три екрани без маршрутизатора — це вже незручно; тридцять — неможливо.
- **Що це.** React Router має три режими: декларативний (лише маршрути), даних (маршрути плюс лоадери й дії) і

  Захищений маршрут — лоадер, що перенаправляє на вхід, якщо сесії немає.
- **Читати:** у примірнику `react-router` — `Picking a Mode`; у розділі Data Mode — `Installation`, `Routing`,
  `Navigating`. Питайте з версією з вашого `package.json`: примірник тримає лінії 7 і 8.
- **Сервери MCP:** `react-router-docs`.
- **Зробити:** 1) три екрани зі спільним каркасом і сторінкою 404; 2) сторінка сутності за `:id`; 3) приватна
  зона з фейковим входом; 4) викотити й оновити сторінку на адресі `/items/2`.
- **Перевірити себе:** у `vite preview` оновлення на `/items/2` працює; на хостингу з фази 1 — спершу 404. Полагодити
  правилом «усі адреси віддають `index.html`» (`Single Page App (SPA)`, крок «Direct all URLs to index.html»;
  синтаксис правила — у документації хостингу, поза корпусом). Після цього глибоке посилання відкривається.
- **Пастка:** вважати захищений маршрут захистом. Він лише ховає екран; дані без входу не має віддавати бекенд.

### День 2. Лоадери й дії маршруту

- **Навіщо.** Дані до рендеру замість водоспаду після рендеру.
- **Що це.** Лоадер — функція маршруту, яку маршрутизатор викликає **до** рендеру сторінки; лоадери вкладених
  маршрутів запускаються паралельно. Компонент читає результат через `useLoaderData`. Дія (`action`) обробляє
  відправлення `<Form>` маршрутизатора й після неї лоадери перезапускаються самі. `useNavigation` каже, що
  перехід триває.
- **Читати:** у розділі Data Mode примірника `react-router` — `Data Loading`, `Actions`, `Pending UI`.
- **Сервери MCP:** `react-router-docs`.
- **Зробити:** 1) батьківський і дочірній екрани, кожен вантажить своє в `useEffect` (затримка API — 500 мс);
  2) у вкладці «Мережа» з уповільненою мережею — водоспад; 3) переписати на лоадери; 4) час до появи вмісту — до
  й після.
- **Перевірити себе:** два числа в журналі; на водоспаді у «Мережі» запити тепер ідуть паралельно.
- **Пастка:** лоадер є, а компонент ще й сам вантажить те саме в ефекті — подвійний запит.

### День 3. Серверний стан: TanStack Query

- **Навіщо.** `useEffect` плюс `fetch` — це гонки відповідей, подвійні запити, відсутність кешу й повторів. Усе
  це вже написано в бібліотеці.
- **Що це.** TanStack Query тримає кеш серверних даних за ключем запиту. `useQuery({ queryKey, queryFn })` дає
  дані, стан завантаження й помилки. `staleTime` — скільки дані вважаються свіжими (свіжі не перезапитуються);
  `gcTime` — скільки невикористані дані лежать у пам'яті. За замовчуванням дані застарівають одразу й
  перезапитуються при поверненні на вкладку — це описано в `Important Defaults`.
- **Читати:** у примірнику `tanstack-query` (фреймворк React) — `Overview`, `Quick Start`, `Queries`,
  `Query Keys`, `Important Defaults`, `Devtools`.
- **Сервери MCP:** `tanstack-query-docs`.
- **Зробити:** 1) перевести всі завантаження поза лоадерами на `useQuery`; 2) підключити Devtools; 3) поставити
  `staleTime` 30 с для списку; 4) піти з екрана й повернутися.
- **Перевірити себе:** у «Мережі» повернення в межах 30 с — нуль запитів, після — один, а екран показує дані
  одразу.
- **Пастка:** копіювати `data` з `useQuery` у `useState`. Копія перестає оновлюватися разом із кешем.

### День 4. Лоадер плюс кеш

- **Навіщо.** Лоадер дає «до рендеру», TanStack Query — кеш і повтори. Разом — найкраще з обох.
- **Що це.** Лоадер не вантажить сам, а просить кеш: `queryClient.ensureQueryData(...)` — повернути з кешу або
  завантажити. Компонент читає ті самі дані через `useQuery` з тим самим ключем. Після зміни даних
  `invalidateQueries` позначає записи застарілими, і активні запити оновлюються.
- **Читати:** у примірнику `tanstack-query` — `Prefetching & Router Integration`, `Query Invalidation` і
  `Example: react/react-router`. Це приклад із репозиторію TanStack Query, а не документація React Router: звідти
  беріть зв'язку «лоадер — `ensureQueryData` — `useQuery`».
- **Сервери MCP:** `tanstack-query-docs`.
- **Зробити:** 1) спільні функції опису запиту (ключ і `queryFn`) для лоадера й компонента; 2) два екрани, що
  показують ті самі дані; 3) кнопка, що викликає `invalidateQueries`.
- **Перевірити себе:** перший візит — один запит, повторний у межах `staleTime` — нуль, після інвалідації — один.
- **Пастка:** різні ключі в лоадері й у компоненті. Виходить два записи кешу й подвійний запит.

### День 5. Мутації й оптимістичні оновлення

- **Навіщо.** Лайк, що з'являється через секунду, здається поламаним.
- **Що це.** `useMutation` надсилає зміну й дає стан відправлення. Після успіху — `invalidateQueries`, щоб список
  оновився. Оптимістичне оновлення малює результат одразу й відкочує його при помилці. У самому React є хук
  `useOptimistic` для того самого в межах одного компонента.
- **Читати:** у примірнику `tanstack-query` — `Mutations`, `Optimistic Updates`; `useOptimistic`.
- **Сервери MCP:** `react-docs`, `tanstack-query-docs`.
- **Зробити:** 1) лайк через `useMutation` з оптимістичним оновленням кешу; 2) фейковий API, що падає кожен
  третій раз; 3) повідомлення про помилку й відкат.
- **Перевірити себе:** третій клік — лайк з'явився й зник із повідомленням; після успіху список збігається з
  сервером.
- **Пастка:** оптимістичне оновлення без відкату й без інвалідації в `onSettled` — екран розходиться з сервером.

## Блок B. Живі дані — дні 6–8

Досі дані приходили на запит: попросили — отримали. Ціни на біржі змінюються кілька разів на секунду, і питати
сервер щосекунди — марна витрата мережі й батареї. Три дні блоку дають проєкту модуль «список монет»: користувач
веде власний список криптопар — записи з власником, через той самий фейковий API і TanStack Query, що й решта
записів, — а екран показує їхні живі ціни. Джерело — ринкові ендпойнти Binance лише для даних: стрім
`wss://data-stream.binance.vision` і REST `https://data-api.binance.vision` (у примірнику `binance-spot` —
`Market Data Only URLs`). Ключ і реєстрація не потрібні, ціни приходять рядками. Про CORS документація нічого не каже,
тож запит REST із браузера перевірте першого ж дня.

Правила з документації Binance (у примірнику `binance-spot` — `WebSocket Streams for Binance`, розділи «General WSS
information» і «WebSocket Limits»), на 08.10.2026: з'єднання з `stream.binance.com` живе не довше 24 годин, далі
сервер його закриває (про `data-stream.binance.vision` окремо не сказано — розраховуйте на те саме); сервер шле ping
кожні 20 секунд, і браузер відповідає на нього сам; клієнт може надіслати не більше 5 повідомлень на секунду на одне
з'єднання; з однієї адреси — не більше 300 нових з'єднань за 5 хвилин. За перевищення 5 повідомлень на секунду
з'єднання розривають, а адресу, яку розривають раз у раз, можуть заблокувати; що буває після 300 з'єднань,
документація не пише. **Першого ж дня перевірте, що стрім відповідає з вашої мережі:** Binance обмежує доступ із
деяких країн, а про `*.binance.vision` документація в цьому сенсі нічого не каже. Якщо не відповідає — запасне джерело
Kraken WS v2, `wss://ws.kraken.com/v2`: там підписка окремим повідомленням, а ціни приходять числами JSON, тож їх
треба одразу перетворювати на рядки. У плані NestJS, фаза 7, з'єднання з біржею переїде на ваш сервер, а SPA слухатиме
вже його, — тому тримайте адресу й розбір повідомлень біржі в одному модулі, щоб потім замінити лише його.

### День 6. WebSocket у браузері

- **Навіщо.** Ціна, що оновлюється лише після перезавантаження сторінки, нікому не потрібна. Живі дані в браузері
  — це WebSocket, і на співбесіді питають, як він відкривається, закривається й обривається.
- **Що це.** `new WebSocket(url)` починає з'єднання: браузер шле звичайний HTTP-запит із заголовком `Upgrade`, сервер
  відповідає статусом 101, і далі тим самим з'єднанням в обидва боки ходять повідомлення. Подій чотири: `open` — можна
  слати; `message` — прийшло повідомлення, текст у `event.data`; `error` — щось пішло не так, але подробиць браузер
  свідомо не дає; `close` — з'єднання закрите, з кодом і причиною. Коди варто знати: 1000 — нормальне закриття; 1001 —
  сторона йде (вкладку закрили, сервер перезапускається); 1006 — з'єднання обірвалося без закриття, наприклад зникла
  мережа. 1006 браузер ставить сам, надіслати його не можна; `close()` приймає лише 1000 і 3000–4999, а 3000–3999
  реєструються в IANA, тож власні коди застосунку — 4000–4999. Для React з'єднання — та сама «зовнішня система», що й
  кімната чату в главах про ефекти: відкрити в ефекті, закрити в прибиранні, залежність — те, до чого підключаєтесь
  (тут — список пар). Binance складає кілька потоків в одне з'єднання адресою
  `/stream?streams=btcusdt@miniTicker/ethusdt@miniTicker` і загортає кожне повідомлення в `{ stream, data }`; потік
  `@miniTicker` шле зведення по парі раз на секунду.
- **Читати:** `Synchronizing with Effects` (розділ «Subscribing to events»), `Lifecycle of Reactive Effects`; у
  примірнику `mdn` — `WebSocket`, `CloseEvent`; у примірнику `binance-spot` — `WebSocket Streams for Binance` (розділи
  «General WSS information», «WebSocket Limits», «Individual Symbol Mini Ticker Stream»); у
  примірнику `webstandards` — `WebSockets Standard: 3 The WebSocket interface`, `WebSockets Standard: 6 The CloseEvent
  interface`, `RFC 6455 The WebSocket Protocol: 7 Closing the Connection`.
- **Сервери MCP:** `react-docs`, `mdn-docs`, `webstandards-docs`, `binance-spot-docs`.
- **Зробити:** 1) модуль «список монет»: додати, видалити й перейменувати пару (`BTCUSDT`, `ETHUSDT`…) через фейковий
  API і `useQuery`, як інші записи; 2) компонент, що в ефекті відкриває одне з'єднання на весь список (адреса — з
  відсортованих пар у нижньому регістрі; кожну пару з даних користувача перед цим перевірити виразом
  `^[A-Z0-9]{5,20}$`, інакше чужий рядок допише в адресу власні потоки) і пише в лог `open`, кожне двадцяте
  повідомлення і `close` з кодом; 3) прибирання — `ws.close(1000, 'list changed')`; 4) додати пару в список; 5)
  вимкнути мережу комп'ютера (Wi-Fi чи кабель) на хвилину.
- **Перевірити себе:** у вкладці «Мережа», фільтр «WS», — одне з'єднання зі статусом 101, а в його повідомленнях
  приблизно по повідомленню на секунду на кожну пару; після кроку 4 старе з'єднання закрите з кодом 1000 і відкрите
  нове; після кроку 5 у лозі `close` з кодом 1006 — браузер помічає обрив не миттєво, іноді за десятки секунд, — і
  жодного відновлення: його дасть наступний день.
- **Пастка:** відкривати з'єднання в рендері або в обробнику без закриття. Після кожного переходу між сторінками
  лишається ще одне живе з'єднання, а Binance рахує нові з'єднання з вашої адреси, ліміт — 300 за п'ять хвилин; що
  буває після нього, документація не пише, тож доводити до нього не варто.

### День 7. Стор поза React і перепідключення

- **Навіщо.** Ціну BTC показують і список, і шапка, і картка пари. Три компоненти — три з'єднання й три різні
  «поточні» ціни. А з'єднання, що обірвалося й не піднялося, мовчки показує старі числа як живі.
- **Що це.** З'єднання виносять із компонентів у звичайний модуль — стор. Він тримає одне з'єднання, останню ціну по
  кожній парі й список підписників. `subscribe(listener)` додає підписника й повертає функцію відписки; перший
  підписник відкриває з'єднання, останній, що пішов, — закриває, але не одразу, а через 1–2 секунди: `<StrictMode>` і
  перехід між сторінками відписують і тут же підписують знову, і без затримки з'єднання щоразу рвалося б і
  відкривалося наново. `getSnapshot()` повертає поточний знімок — і той самий об'єкт, доки нічого не змінилося: React
  порівнює знімки через `Object.is`. Компонент читає стор через `useSyncExternalStore(subscribe, getSnapshot)`, а хук
  `usePrice(symbol)` повертає запис лише своєї пари: якщо змінилася ціна ETH, рядок BTC отримує той самий об'єкт і не
  перемальовується. Перепідключення — з експоненційною затримкою і джитером: спроба номер n чекає випадковий час від
  нуля до `min(30 с, 1 с × 2^n)`. Випадковість потрібна, щоб тисячі клієнтів після збою біржі не повернулися в одну й
  ту саму секунду; стеля — щоб не чекати годину. Після стабільного з'єднання лічильник спроб скидається. Стан
  з'єднання теж живе в сторі: «з'єднуюсь», «на зв'язку», «перепідключаюсь через N с», «немає мережі» (події `online` і
  `offline` на `window` — підказка, а не гарантія). Binance закриває з'єднання з `stream.binance.com` через 24 години
  (розраховуйте на те саме й для `data-stream.binance.vision`), тож перепідключення — не рідкісна аварія, а щоденна
  подія.
- **Читати:** `useSyncExternalStore` (розділи «Subscribing to an external store», «Subscribing to a browser API»,
  «Extracting the logic to a custom Hook» і обидва розділи Troubleshooting), `Reusing Logic with Custom Hooks`; у
  примірнику `mdn` — `Navigator: onLine property`, `Page Visibility API`; блог AWS Architecture — «Exponential Backoff
  And Jitter» (поза корпусом); у примірнику `binance-spot` — `WebSocket Streams for Binance` (розділ «General WSS
  information»).
- **Сервери MCP:** `react-docs`, `mdn-docs`, `binance-spot-docs`.
- **Зробити:** 1) модуль `priceStore` з `subscribe`, `getSnapshot`, станом з'єднання й незмінними записами;
  2) хуки `usePrice(symbol)` і `useConnectionStatus()`; 3) перепідключення з повним джитером і стелею, кожна
  затримка — у лог; 4) індикатор стану в шапці; 5) ціна BTC у списку й у шапці одночасно; 6) службова функція,
  що закриває сокет стору кодом 4000, — викликати її з консолі п'ять разів поспіль, не чекаючи відновлення.
- **Перевірити себе:** у «Мережі» одне з'єднання на два компоненти; лог кроку 6 показує п'ять різних затримок, що
  загалом ростуть і не перевищують стелі; профайлер під час потоку показує рендери лише рядків, ціна яких
  змінилася; індикатор проходить «перепідключаюсь» → «на зв'язку».
- **Пастка:** `getSnapshot`, що щоразу повертає новий об'єкт (`return { ...prices }`). React бачить «зміну» на
  кожному виклику й падає з помилкою «The result of getSnapshot should be cached» або йде в нескінченні рендери.
  Друга пастка — `subscribe`, оголошена всередині компонента: React відписується й підписується заново на кожному
  рендері.

### День 8. Сотні повідомлень на секунду

- **Навіщо.** Потік угод по BTC — десятки повідомлень на секунду, по кількох парах — сотні. Рендер на кожне
  повідомлення з'їдає процесор, і поле фільтра поруч починає гальмувати: INP росте, хоча користувач «нічого не
  робить».
- **Що це.** Екран оновлюється не частіше за кадр — близько 60 разів на секунду, — тож усе, що прийшло між
  кадрами, можна застосувати разом. Повідомлення складають у буфер — `Map` «пара → останнє значення», де нове
  перетирає старе, — а `requestAnimationFrame` раз на кадр переносить буфер у стор і один раз повідомляє
  підписників. У фоновій вкладці кадрів немає, і буфер просто тримає останнє значення по кожній парі: пам'ять не
  росте. Рядок списку бере запис лише своєї пари (день 7) і загорнутий у `memo` або скомпільований React
  Compiler, тож перемальовуються лише змінені рядки. Свічки — дані іншої природи: закрита свічка більше не
  змінюється, і в неї є історія. Історію дає REST `GET /api/v3/klines?symbol=BTCUSDT&interval=1m&limit=60` (ціни
  рядками, щонайбільше 1000 свічок за запит) через `useQuery` зі `staleTime: Infinity`. Потік `@kline_1m` кожні 2
  секунди шле поточну свічку з прапорцем `x` — «свічка закрита». Свічка, що ще формується, живе в сторі; закрита
  дописується в кеш через `queryClient.setQueryData` — раз на хвилину, а не на кожне повідомлення. Після
  перепідключення історію перезапитують (`invalidateQueries`): поки з'єднання не було, свічки закривалися без вас.
- **Читати:** `<Profiler>`, `React Performance tracks`, `memo`; у примірнику `mdn` — `Window: requestAnimationFrame()
  method`; у примірнику `tanstack-query` — `Updates from Mutation Responses` (той самий `setQueryData`, лише джерело
  інше), `QueryClient` (метод `setQueryData`), `Important Defaults`; блог TkDodo — «Using WebSockets with React Query»
  (поза корпусом); у примірнику `webdev` — `Optimize input delay` (затримка перед обробником, поки головний потік
  зайнятий іншою роботою); у примірнику `binance-spot` — `Public Rest API for Binance` (розділ «Kline/Candlestick
  data»), `WebSocket Streams for Binance` (розділи «Trade Streams», «Kline/Candlestick Streams for UTC»).
- **Сервери MCP:** `react-docs`, `mdn-docs`, `tanstack-query-docs`, `webdev-docs`, `binance-spot-docs`.
- **Зробити:** 1) перевести список на потік `@trade` для п'яти пар; 2) на збірці для профілювання з уповільненням
  процесора 4× заміряти за десять секунд кількість повідомлень і комітів (`<Profiler>`) і INP набору в поле фільтра
  поруч; 3) буфер і скидання раз на кадр; 4) заміряти знову; 5) таблиця останніх шістдесяти хвилинних свічок: історія
  через REST, закриті свічки зі стріму через `setQueryData`, поточна — зі стору; 6) вимкнути мережу на хвилину й
  увімкнути.
- **Перевірити себе:** у журналі два рядки, до й після: повідомлень за десять секунд, комітів на 100 повідомлень і INP
  — потік нерівний, тож порівнюють коміти на 100 повідомлень, а не голі коміти (або запишіть потік у файл і
  відтворюйте його однаково); після кроку 3 комітів не більше, ніж кадрів; у «Мережі» таблиця свічок росте на рядок
  щохвилини без жодного нового REST-запиту, а після кроку 6 — рівно один перезапит історії.
- **Пастка:** класти кожне повідомлення потоку в кеш TanStack Query через `setQueryData`. Кожен виклик будить
  усіх спостерігачів ключа, Devtools захлинається, а виграшу перед стором немає. Кеш — для рідкісних подій
  (закрита свічка), стор — для частих (ціна).

## Блок C. Форми й глобальний стан — дні 9–11

### День 9. Форми в React 19

- **Навіщо.** Проста форма в React 19 обходиться без жодного `useState`.
- **Що це.** Контрольоване поле — значення в стані React; неконтрольоване — значення в DOM, читається при
  відправленні. `<form action={fn}>` у React 19 приймає функцію, що отримує `FormData`. `useActionState` тримає
  результат останньої відправки (наприклад, текст помилки) і стан `isPending`. `useFormStatus` дає стан
  відправлення батьківської форми — для кнопки «Зберегти», винесеної в окремий компонент.
- **Читати:** `<form>`, `<input>`, `useActionState`, `useFormStatus`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** форма входу: `<form action>`, помилка через `useActionState`, кнопка в окремому компоненті з
  `useFormStatus`, що блокується під час відправлення.
- **Перевірити себе:** у компоненті форми нуль `useState`; подвійне клацання не надсилає форму двічі.
- **Пастка:** викликати `useFormStatus` у тому ж компоненті, що малює `<form>`. Він бачить лише батьківську форму,
  і `pending` ніколи не стане `true` — це прямо сказано в довідці.

### День 10. React Hook Form і zod

- **Навіщо.** Форма на десять полів із перевіркою під час набору — щоденна робота, і схема перевірки має бути
  одна для фронту й бекенду.
- **Що це.** zod описує схему даних і виводить з неї тип (`z.infer`). React Hook Form тримає поля
  неконтрольованими й не перемальовує всю форму на кожну літеру; схема підключається резолвером. Помилку з сервера
  для конкретного поля ставить `setError`. Схему кладуть в окремий модуль: у плані NestJS, фаза 2, день 1, та сама
  схема стане валідацією бекенду — NestJS 12 приймає схеми zod через Standard Schema.
- **Читати:** у примірнику `react-hook-form` — `Get Started (content/get-started)` (розділ «Schema Validation»),
  `useForm (content/docs/useform)`, `setError (content/docs/useform/seterror)`; у примірнику `zod` — `Basic usage`,
  `Defining schemas`; у примірнику `webdev` — `Learn Forms: Help users enter the right data in forms` (як повідомити
  правила перевірки й показати зрозумілу помилку).
- **Сервери MCP:** `react-hook-form-docs`, `zod-docs`, `webdev-docs`.
- **Зробити:** 1) схема сутності на десять полів в окремому модулі; 2) форма на React Hook Form із резолвером;
  3) тип форми лише з `z.infer`; 4) імітувати відповідь сервера «ця назва вже зайнята» і показати її біля поля
  через `setError`.
- **Перевірити себе:** зміна правила в схемі змінює і тип, і перевірку; профайлер показує, що набір в одному полі
  не рендерить усю форму.
- **Пастка:** дві схеми — для клієнта й для сервера. Вони розійдуться за тиждень.

### День 11. Глобальний стан

- **Навіщо.** «Беремо Redux» — часто рішення, прийняте до того, як з'ясували, що глобального в застосунку майже
  нічого.
- **Що це.** Стан буває серверний (кеш TanStack Query), в адресі (фільтри, сторінка — `searchParams`), формовий
  (React Hook Form), локальний (`useState`) і справді глобальний клієнтський (тема, налаштування інтерфейсу,
  кошик). Лише останній потребує сховища. Zustand — маленьке сховище з селекторами: компонент перемальовується,
  лише коли змінилося те, що він вибрав. Redux Toolkit — те саме з суворішою структурою, частий у великих
  командах. Обидва під капотом спираються на `useSyncExternalStore` — той самий механізм, що й стор цін із дня 7.
- **Читати:** у примірнику `zustand` — `Introduction`, `Comparison`; у примірнику `redux` —
  `Why Redux Toolkit is How To Use Redux Today`; `useSyncExternalStore`.
- **Сервери MCP:** `react-docs`, `zustand-docs`, `redux-docs`.
- **Зробити:** 1) таблиця в README: увесь стан проєкту за п'ятьма категоріями; 2) лише справді глобальне — у
  Zustand із селекторами; 3) профайлер: змінити тему.
- **Перевірити себе:** у таблиці по кожній категорії число; профайлер показує рендер лише підписаних компонентів.
- **Пастка:** класти серверні дані в Zustand чи Redux. Виходить другий кеш, який доводиться синхронізувати руками.

## Блок D. Тести й доступність — дні 12–15

### День 12. Тести компонентів

### День 13. Тести з мережею

### День 15. Доступність

  `label` і `aria-describedby`.
- **Читати:** `useId`; `Common components (e.g. <div>)` (атрибути `aria-*` і `role`); у примірнику `mdn` —

# Фаза 4. Сервер: SSR, стрімінг, серверні компоненти — 3 дні

**Сервери MCP фази:** `react-docs`.

Тут React перестає бути тільки браузерним. Фаза коротка навмисно: вона дає механізми самого React, які є в
корпусі, а їхню найпоширенішу реалізацію — Next.js — вчить окремий план. Фаза 0 плану Next.js спирається саме на
ці три дні.

### День 1. SSR і гідратація

- **Навіщо.** SPA приходить у браузер порожнім HTML. Пошуковик, прев'ю посилання в месенджері й повільний телефон
  бачать порожню сторінку, доки не виконався JavaScript.
- **Що це.** Серверний рендер (SSR) викликає ті самі компоненти на сервері й віддає готовий HTML. У браузері
  `hydrateRoot` «оживляє» його: React ще раз рендерить дерево, звіряє з наявною розміткою і навішує обробники.
  Якщо сервер і браузер намалювали різне (`Date.now()`, `Math.random()`, `window` у рендері), React повідомляє про
  розбіжність гідратації.
- **Читати:** `hydrateRoot`, `renderToString`, `Server React DOM APIs`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) «Переглянути код сторінки» свого SPA — порожній `<div id="root">`; 2) найпростіший сервер на
  `node:http`, що віддає один компонент через `renderToString`; 3) клієнтський `hydrateRoot` для нього; 4) вивести
  в рендері поточний час.
- **Перевірити себе:** у коді сторінки з кроку 2 є вміст; у кроці 4 консоль показує розбіжність гідратації, і ви
  її полагодили, перенісши час у ефект.
- **Пастка:** вважати SSR «швидшим». Зміст з'являється раніше, але сторінка не реагує на клацання, доки не
  завершилася гідратація.

### День 2. Стрімінг на сервері

- **Навіщо.** Без стрімінгу сервер чекає найповільніший запит, перш ніж надіслати хоч байт.
- **Що це.** `renderToPipeableStream` шле HTML частинами: спершу оболонку (усе над межами `<Suspense>`), потім
  кожен шматок у міру готовності, з маленьким скриптом, що ставить його на місце заглушки. `prerender` малює
  сторінку заздалегідь, на збірці. Стрімінг ламає будь-яка проміжна ланка, що збирає відповідь цілком (проксі з
  буферизацією).
- **Читати:** `renderToPipeableStream` (розділи «Specifying what goes into the shell» і «Streaming more content as
  it loads»), `<Suspense>`, `prerender`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) сервер дня 1 переписати на `renderToPipeableStream`; 2) блок із затримкою даних 2 с під
  `<Suspense>`; 3) `curl -N` на сервер.
- **Перевірити себе:** у терміналі два шматки відповіді з інтервалом близько двох секунд.
- **Пастка:** одна межа `<Suspense>` над усією сторінкою. Тоді оболонка порожня, і все чекає найповільнішого.

### День 3. Серверні компоненти, межа клієнта, Server Functions

- **Навіщо.** «Чим серверний компонент відрізняється від SSR» — питання, яке ставлять постійно й плутають усі.
- **Що це.** Серверний компонент виконується заздалегідь в окремому середовищі: «Server Components can run once at
  build time on your CI server, or they can be run for each request using a web server» (`Server Components`).
  Його код у браузер не їде взагалі; він може бути `async` і читати базу, але не має стану й обробників.
  `'use client'` позначає модуль, з якого починається клієнтська частина; пропси через цю межу проходять мережею
  і мусять серіалізуватися. `'use server'` позначає Server Functions — функції на сервері, які клієнт викликає
  мережею; до вересня 2024 усі вони звалися Server Actions. Кожна Server Function — публічний ендпойнт: «Always
  treat arguments to Server Functions as untrusted input and authorize any mutations» (`use server`, розділ
  Caveats). Вразливості React, оголошені в грудні 2025, стосуються саме серверних компонентів; SPA на Vite їх не
  зачіпають: «If your app does not use a framework, bundler, or bundler plugin that supports React Server
  Components, your app is not affected by this vulnerability» (блог React у корпусі, «Critical Security
  Vulnerability in React Server Components», 03.12.2025, і «Denial of Service and Source Code Exposure in React
  Server Components», 11.12.2025).
- **Читати:** `Server Components`, `use client` (зокрема розділ «Serializable types returned by Server
  Components»), `use server`, `Server Functions`.
- **Сервери MCP:** `react-docs`.
- **Зробити:** 1) пів сторінки своїми словами: чим серверний компонент відрізняється від SSR; 2) таблиця з восьми
  значень — рядок, `Date`, функція, екземпляр класу, проміс, `Map`, JSX, `Symbol` — що з них можна передати через
  межу `'use client'`, і звірити з довідкою.
- **Перевірити себе:** у тексті є обидві тези: SSR малює HTML із **будь-яких** компонентів і потім шле їхній код у
  браузер; серверний компонент свого коду в браузер не шле зовсім. Таблиця збіглася з довідкою.
- **Пастка:** «серверний компонент = SSR». Друга пастка — вважати Server Function внутрішньою функцією: її може
  викликати будь-хто з будь-якими аргументами.

**Критерій завершення фази:** ви пояснюєте на одному прикладі, що виконалося на збірці, що — на сервері під час
запиту, а що — в браузері, і що з цього потрапило в бандл.

**Далі — Next.js.** Фреймворки складають ці механізми в готовий застосунок. Як це робить Next.js — план Next.js, з
фази 0 (дні про те, де виконується код, і про серверний React) і далі. Питання «Next.js як єдиний бекенд чи поруч
окремий NestJS» — план Next.js, фаза 8, день 1: там воно вирішується, коли обидва вміння вже є.

### День 2. Оточення й безпека фронтенду

- **Навіщо.** Фронтенд атакують не через сервер, а через браузер: чужий скрипт у сторінці читає все, що бачить
  ваш код.
- **Що це.** Змінні `VITE_*` вшиваються в бандл під час збірки — **секретів у фронтенд-збірці не існує**, будь-хто
  прочитає їх у вкладці «Джерела». Захист від XSS — екранування JSX (фаза 1, день 2), `dangerouslySetInnerHTML`
  лише після очищення, адреси з даних — лише `http(s):`. Токени — за моделлю родини, яку будує план NestJS у фазі
  про авторизацію: короткий access-токен приходить у тілі відповіді й живе лише в пам'яті SPA; refresh-токен — у
  куці `HttpOnly` (JavaScript її не бачить), сервер обмінює його на новий при кожному оновленні. `localStorage` для
  токенів — ні: будь-який XSS його читає. Захищений маршрут — зручність, дані закриває бекенд.
- **Читати:** у примірнику `vite` — `Env Variables and Modes`; `Common components (e.g. <div>)` (проп
  `dangerouslySetInnerHTML`); у примірнику `owasp` — `Cross Site Scripting Prevention Cheat Sheet` (розділи Framework
  Security, HTML Sanitization) і чернетка `React Security Cheat Sheet` (`dangerouslySetInnerHTML`, перевірка адрес,
  токени в куках `HttpOnly`, секрети в змінних оточення).
- **Сервери MCP:** `react-docs`, `vite-docs`, `owasp-docs`.
- **Зробити:** 1) `VITE_SECRET=abc123`, зібрати й знайти рядок `abc123` у `dist` пошуком; 2) пошук по коду
  `dangerouslySetInnerHTML` і `localStorage` — кожне входження обґрунтувати або прибрати; 3) функція `safeUrl`,
  що пропускає лише `http:` і `https:`, — на всі `href` з даних.
- **Перевірити себе:** пошук у кроці 1 знаходить значення — доказ для README; у коді жодного токена в
  `localStorage` і жодного неочищеного HTML.
- **Пастка:** «сховати» ключ стороннього API у змінну оточення фронтенду. Запит із ключем іде через ваш бекенд.

### День 6. Викот статики як слід

- **Навіщо.** Після кожного викоту частина користувачів сидить на старій вкладці зі старим кодом. Кеш вирішує, чи
  вони це помітять.
- **Що це.** Файли в `assets/` мають хеш в імені — новий вміст, нове ім'я, тому їх кешують на рік:
  `Cache-Control: public, max-age=31536000, immutable`. `index.html` посилається на поточні імена, тож його не
  кешують (`no-cache`): кожен візит перевіряє, чи не з'явилася нова версія. Карти коду в публічний доступ не
  викладають — їх віддають збирачу помилок. Заголовки безпеки й політику CSP віддає той, хто роздає SPA: на
  статичному хостингу — файл заголовків хостингу (поза корпусом), у кластері — nginx з образу (дні 7 і 9); які
  саме заголовки — план NestJS, фаза 4, день 12.
  Стара вкладка після викоту просить чанк, якого вже немає, — це помилка завантаження, яку ловить межа помилок і
  пропонує оновити сторінку.
- **Читати:** у примірнику `vite` — `static-deploy`, `Build Options` (опція `build.sourcemap`); у примірнику
  `webstandards` — `RFC 9111 HTTP Caching: 5 Field Definitions` (розділ 5.2 Cache-Control); у примірнику `webdev` —
  `Prevent unnecessary network requests with the HTTP Cache` (хеш в імені файла плюс `immutable`, для HTML —
  `no-cache`).
- **Сервери MCP:** `vite-docs`, `webstandards-docs`, `webdev-docs`.
- **Зробити:** 1) правила кешу для `index.html` і `assets/`; 2) `curl -I` обох; 3) карти коду — `hidden` або
  вимкнені; 4) відкрити вкладку, викотити нову версію, перейти на лінивий маршрут у старій вкладці.
- **Перевірити себе:** `curl -I` показує два різні `Cache-Control`; запит до `.map` дає 404; стара вкладка
  показує «вийшла нова версія, оновіть сторінку», а не білий екран.
- **Пастка:** довгий кеш на `index.html`. Користувачі тижнями сидять на старій версії, а виправлення «не
  доходить».

## Блок B. Викот у кластер Kubernetes — дні 7–9

Статичний хостинг із фази 1 — швидкий старт, але він уміє лише роздавати файли. Бекенд із базою й живими цінами
туди не покладеш, а родині потрібен один продакшн на всі три плани. Цей блок його будує: SPA пакується в образ
Docker, запускається подами в Kubernetes — спершу на вашому комп'ютері, потім на безкоштовному сервері в хмарі, —
за HTTPS і з відкатом версії. Далі в цей самий кластер план NestJS (фаза 6, дні 8–9) додасть бекенд, базу й Redis і
поставить SPA та API під одне ім'я і зробить перше демо для клієнта (фаза 7, день 8), а план Next.js замінить под
SPA подом Next.js (фаза 7) і оновить демо під Next.js (фаза 9).

Docker має примірник `docker`; Kubernetes, k3s, k3d, Traefik, cert-manager і Let's Encrypt — примірник `kubernetes`;
кожен день називає глави. Документації Oracle Cloud у фабриці немає — джерело її офіційний сайт. Факти про
безкоштовний хостинг тут — на 02.10.2026. Безкоштовні тарифи змінюються, буває й без оголошення, тож перед днем 8
звірте їх зі сторінкою Oracle «Always Free Resources».

### Що треба мати до викоту

**Знання.** Термінал Linux: файли, права, `sudo`, правка файла в `nano` чи `vim` через SSH. SSH-ключі: пара
«приватний — публічний»; публічний кладуть на сервер, приватний не покидає вашої машини, і вхід на сервер — лише
ключем, без пароля. DNS і TLS на рівні понять: ім'я перетворюється на IP-адресу записом A; сертифікат доводить
браузеру, що сервер справді володіє цим ім'ям, а видає його центр сертифікації — тут безкоштовний Let's Encrypt.
YAML: вкладеність задають відступи пробілами (не табуляцією), `-` починає елемент списку, `---` розділяє кілька
документів в одному файлі. Усе це — на рівні «читаю й розумію», не «знаю напам'ять»: кожну команду дні пояснюють.

**Облікові записи.** GitHub — для реєстру образів GHCR: на 02.10.2026 зберігання й трафік образів там безкоштовні,
і GitHub обіцяє попередити за місяць до змін. Oracle Cloud — для безкоштовного сервера; обліковий запис заведіть
**за тиждень до дня 8**: перевірка картки буває з відмовами й повторними спробами. Потрібна звичайна кредитна
картка (з неї нічого не списують, доки обліковий запис не переведено на оплату); віртуальні й передплачені, за
відгуками користувачів, не приймають, а антифрод часом відхиляє і звичайні. Регіон, обраний при реєстрації
(домашній), змінити не можна, і безкоштовні ресурси створюються лише в ньому — беріть не найпопулярніший, там менше
шансів упертися в брак вільних машин. Саму машину раніше дня 8 не створюйте — причина в наступному абзаці.

**Коли машину заберуть.** Правило Oracle «Reclamation of Idle Compute Instances»: машину A1 вважають бездіяльною,
якщо за 7 днів одночасно процесор (95-й перцентиль), мережа й пам'ять нижче 20 %. Між кінцем шляху мідла й планом
NestJS, фаза 6, день 8, — близько п'ятнадцяти тижнів, і кластер з одним маленьким подом SPA за цей час, імовірно,
заберуть. Це нормально, якщо є рецепт: кожна команда днів 8 і 9 записується у файл `infra/README.md` вашого
репозиторію — «від порожньої машини до робочого кластера», без токенів і ключів. Перед планом NestJS, фаза 6,
день 8, і перед планом Next.js, фаза 7, день 12, кластер за потреби піднімають заново за цим файлом.

**Без хмари.** Якщо Oracle не пустив або вільних машин так і не з'явилося, усі дні з кластером — і тут, і в
наступних планах — робляться на k3d з дня 7 тими самими маніфестами: ім'я `app.localhost` замість sslip.io і без
Let's Encrypt (кластер створюють із пробросом порту, `k3d cluster create learn -p "80:80@loadbalancer"`). Хмара
потрібна лише для публічної адреси й демо. Kubernetes від DigitalOcean на кредиті для нових користувачів (за
сторонніми джерелами на 02.10.2026 — $200 на 60 днів, із карткою) бережуть на місяць демо в плані Next.js, фаза 9,
— у цьому плані його не витрачають.

**На своєму комп'ютері.** Docker Engine всередині WSL (Docker Desktop не потрібен), `kubectl` і k3d — їх ставить
день 7; Helm — день 9. Пам'ять WSL обмежте у файлі `%UserProfile%\.wslconfig`, розділ `[wsl2]`, рядок `memory=`
(наприклад, половина пам'яті машини), і перезапустіть WSL командою `wsl --shutdown` з Windows: інакше під збіркою
образів WSL забирає все, що дадуть, і гальмує Windows.

**Що з попередніх днів.** Збірка `vite build` без помилок і без секретів у `VITE_*` (фаза 5, день 2); маршрути з
правилом «усі адреси віддають `index.html`» (фаза 3, день 1); правила кешу `index.html` проти `assets/` (фаза 5,
день 6 — на шляху мідла прочитайте хоча б його «Що це»).

### День 7. Образ і под на своєму комп'ютері

- **Навіщо.** Кластер запускає не теку `dist`, а образи. Перш ніж розбиратися з помилками на сервері, образ і
  маніфести треба побачити працюючими локально, де зламане лагодиться за хвилину і нічого не коштує.
- **Що це.** Образ збирається за рецептом — Dockerfile. Кожна інструкція дає шар, шари кешуються, тож порядок має
  значення: спершу те, що змінюється рідко (залежності), потім те, що часто (код). Збірка у два етапи: перший має
  Node і збирає `dist`, другий — лише nginx і готові файли. Node, `node_modules` і вихідний код у фінальний образ не
  потрапляють, і він важить десятки мегабайт замість сотень.

  ```dockerfile
  FROM --platform=$BUILDPLATFORM node:lts-alpine AS build
  WORKDIR /app
  COPY package.json package-lock.json ./
  RUN npm ci
  COPY . .
  RUN npm run build

  FROM nginx:stable-alpine
  COPY nginx.conf /etc/nginx/conf.d/default.conf
  COPY --from=build /app/dist /usr/share/nginx/html
  ```

  Рядок за рядком. `FROM … AS build` — почати етап з офіційного образу Node і назвати його `build`.
  `--platform=$BUILDPLATFORM` — виконувати цей етап на архітектурі вашої машини, навіть коли фінальний образ
  потрібен для іншої: результат етапу — статичні файли, однакові для будь-якого процесора, а `npm ci` під
  емуляцією чужого процесора йшов би в рази довше. `WORKDIR` — тека всередині образу, де виконуються наступні
  команди. Перший `COPY` бере лише `package.json` і файл блокування, `RUN npm ci` ставить за ними залежності: доки ці
  два файли не змінилися, Docker бере шар із кешу й залежності вдруге не ставить. `COPY . .` копіює решту коду,
  `RUN npm run build` збирає `dist`. Другий `FROM` починає новий, чистий етап з nginx; у ньому немає жодного `RUN`,
  тож емуляція чужого процесора не знадобиться зовсім. Наступний `COPY` кладе ваш конфіг nginx на місце
  стандартного, `COPY --from=build` бере з першого етапу лише теку `dist`. Теги `lts-alpine` і `stable-alpine`
  плаваючі — для навчання зручно, у робочому проєкті фіксують точну версію.

  Поруч лежать `.dockerignore` — що не копіювати в образ (`node_modules`, `dist`, `.git`, `.env*`), — і
  `nginx.conf`:

  ```nginx
  server {
    listen 80;
    root /usr/share/nginx/html;

    location /assets/ {
      add_header Cache-Control "public, max-age=31536000, immutable";
      try_files $uri =404;
    }
    location ~ \.map$ {
      return 404;
    }
    location / {
      add_header Cache-Control "no-cache";
      try_files $uri /index.html;
    }
  }
  ```

  `listen 80` — порт усередині контейнера. `root` — звідки брати файли. Блок `/assets/` — файли з хешем в імені:
  кеш на рік, а відсутній файл — чесний 404, не `index.html`, інакше стара вкладка отримає HTML замість чанка й
  упаде незрозуміло. Блок `\.map$` не віддає карти коду (фаза 5, день 6). Блок `/` — усе інше: `index.html` без
  кешу, а адреса, якої немає серед файлів (`/items/2`), отримує `index.html` — те саме правило SPA, що й на хостингу
  у фазі 3, день 1.

  У Kubernetes образ потрапляє через маніфести. Deployment описує, які поди тримати:

  ```yaml
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: spa
    namespace: app
  spec:
    replicas: 2
    selector:
      matchLabels:
        app: spa
    template:
      metadata:
        labels:
          app: spa
      spec:
        containers:
          - name: spa
            image: spa:0.1.0
            ports:
              - containerPort: 80
            readinessProbe:
              httpGet:
                path: /
                port: 80
            resources:
              requests:
                cpu: 10m
                memory: 32Mi
              limits:
                memory: 64Mi
  ```

  `apiVersion` і `kind` — що це за об'єкт і з якої групи API. `metadata.name` — ім'я, за яким його знайде `kubectl`;
  `metadata.namespace` — простір імен, окрема «тека» кластера. Уся родина живе в просторі `app`: тут з'являються
  `spa`, план NestJS додасть `api`, `db` і `redis`, план Next.js — `web-next`. `replicas: 2` — тримати дві копії:
  впала одна — друга відповідає, доки Kubernetes піднімає заміну. `selector.matchLabels` — за якою міткою Deployment
  впізнає «свої» поди, а `template.metadata.labels` ставить цю мітку кожному новому поду; ці дві мітки мусять
  збігатися. `template.spec.containers` — що запускати в поді: ім'я контейнера, образ із тегом, порт. `readinessProbe`
  — Kubernetes сам робить `GET /` у под і шле туди трафік, лише коли той відповідає успішно. `resources.requests` —
  скільки процесора (`10m` — сота частка ядра) і пам'яті резервувати під под; `limits.memory` — стеля, вище якої
  контейнер буде вбито. Service дає подам одне стабільне ім'я й адресу всередині кластера — поди приходять і йдуть,
  Service лишається:

  ```yaml
  apiVersion: v1
  kind: Service
  metadata:
    name: spa
    namespace: app
  spec:
    selector:
      app: spa
    ports:
      - port: 80
        targetPort: 80
  ```

  `selector` — трафік іде на всі поди з міткою `app: spa`; `port` — порт самого Service, `targetPort` — порт
  контейнера. k3d запускає справжній кластер k3s у контейнерах Docker на вашому комп'ютері — той самий дистрибутив,
  що буде на сервері, тож маніфести завтра не зміняться.
- **Читати:** у примірнику `docker` — `Multi-stage builds`, `Dockerfile reference`, `Multi-platform builds`; у
  примірнику `kubernetes` — `Deployments`, `Service`, `Configure Liveness, Readiness and Startup Probes`,
  `k3d: Overview`, `k3d: k3d cluster create`; у примірнику `vite` — `static-deploy`; у примірнику `nginx` — `Serve
  Static Content`, `Module ngx_http_core_module` (директиви `location`, `root`, `try_files`), `Module
  ngx_http_headers_module` (директива `add_header`).
- **Сервери MCP:** `docker-docs`, `kubernetes-docs`, `vite-docs`, `nginx-docs`.
- **Зробити:** 1) Docker Engine у WSL за інструкцією для Ubuntu з docs.docker.com, далі `sudo usermod -aG docker
  $USER` (запускати `docker` без `sudo`), перезайти в WSL і `docker run hello-world`; 2) `Dockerfile`, `.dockerignore`
  і `nginx.conf` у корені проєкту, як вище; 3) `docker build -t spa:0.1.0 .` — зібрати образ з тегом, крапка — «рецепт
  і файли беремо з поточної теки»; `docker images spa` — розмір у журнал; 4) `docker run --rm -p 8080:80 spa:0.1.0` —
  запустити контейнер, прокинувши порт 8080 вашої машини на порт 80 контейнера (`--rm` прибере контейнер після
  зупинки); відкрити `http://localhost:8080/items/2` і перевірити `curl -I` для `/` і для файла з `assets/`; 5)
  мультиархітектурна збірка: `docker buildx create --use` створює збирач, що вміє кілька платформ (збирач за
  замовчуванням arm64 не вміє), а `docker buildx build --platform linux/amd64,linux/arm64 -t spa:multi .` збирає для
  обох — без `--push` результат лишається в кеші збирача, це лише перевірка, що збирається; якщо вона падає з «exec
  format error» — `docker run --privileged --rm tonistiigi/binfmt --install arm64` і повторити (після `wsl --shutdown`
  — знову); 6) поставити `kubectl` (сторінка «Install Tools» на kubernetes.io) і k3d (скрипт установки з його
  документації), `k3d cluster create learn`, `kubectl get nodes`; 7) `k3d image import spa:0.1.0 -c learn` — покласти
  образ у кластер без реєстру; 8) `kubectl create namespace app`, маніфести в теку `k8s/`, `kubectl apply -f k8s/` —
  надіслати всі файли теки; щоб не дописувати `-n app` до кожної команди, `kubectl config set-context --current
  --namespace app`; 9) `kubectl get pods -w` (стежити за подами наживо, вихід — `Ctrl+C`), потім `kubectl port-forward
  svc/spa 8081:80` і відкрити `http://localhost:8081`; 10) `kubectl delete pod <ім'я одного з подів>` і знову `kubectl
  get pods`; 11) наприкінці дня `k3d cluster stop learn` — кластер не займає пам'ять, поки ви не вчитеся.
- **Перевірити себе:** розмір образу — десятки мегабайт (у журнал); `curl -I` на порт 8080 показує `no-cache` для
  `/` і `immutable` для файла з `assets/`; `kubectl get pods` показує два поди `Running` з `READY 1/1`; після
  кроку 10 за кілька секунд з'являється под із новим іменем — Deployment доводить кількість назад до двох.
- **Пастка:** тег `latest` або образ без тегу. Для `latest` Kubernetes за замовчуванням щоразу тягне образ із
  реєстру, не знаходить вашого локального `spa` на Docker Hub і показує `ErrImagePull`; а на сервері `latest` не
  каже, яка версія зараз працює і на що відкочуватися. Тег — завжди версія: `0.1.0`, `0.2.0` або хеш коміту.

### День 8. Сервер: Oracle Cloud, k3s і SPA за HTTP

- **Навіщо.** Кластер на ноутбуці зникає, щойно ноутбук закрили. Продакшн родини — машина в хмарі, що працює
  цілодобово, і до кінця вечора на ній відкривається ваша SPA за власною адресою: поки що по HTTP, HTTPS додасть
  день 9.
- **Що це.** Безкоштовна машина Oracle Cloud Always Free на 02.10.2026: Ampere A1 — разом 2 OCPU і 12 ГБ пам'яті
  (з 15.06.2026; старі інструкції пишуть «4 і 24» — для безкоштовного облікового запису це вже неправда), процесор
  arm64, тож образи мусять бути мультиархітектурні (день 7); дисків — до 200 ГБ на всі машини. Бездіяльну машину
  Oracle забирає (розділ «Що треба мати до викоту»), а при створенні A1 у популярних регіонах буває «Out of host
  capacity» — вільних машин немає, і лишається пробувати пізніше або в іншій зоні доступності. Доступ до сервера:
  порт 22 відкритий, але вхід лише ключем — паролі й вхід під `root` вимкнені. API кластера (порт 6443) назовні не
  відкривається ніколи: `kubectl` з вашого комп'ютера ходить до нього тунелем SSH. k3s — Kubernetes в одному
  файлі, розрахований на маленькі машини; разом із ним ставляться Traefik (приймає вхідний трафік) і ServiceLB
  (відкриває порти 80 і 443 прямо на адресі машини, без платного балансувальника). Встановлення — одна команда на
  сервері:

  ```bash
  curl -sfL https://get.k3s.io | sh -s - --secrets-encryption
  ```

  `curl -sfL` завантажує скрипт установки (тихо, з падінням на помилці HTTP, ідучи за перенаправленнями),
  `| sh -s -` виконує його й передає йому решту рядка як аргументи. `--secrets-encryption` — необов'язковий, але
  дешевий: k3s шифрує Secret у своєму сховищі на диску машини. Доступ із WSL:

  ```bash
  umask 077
  ssh ubuntu@203.0.113.10 'sudo cat /etc/rancher/k3s/k3s.yaml' > ~/.kube/oracle.yaml
  ssh -N -L 6443:127.0.0.1:6443 ubuntu@203.0.113.10
  ```

  `umask 077` — нові файли в цьому терміналі може читати лише ваш користувач: у kubeconfig лежить повний
  адміністраторський ключ кластера. Друга команда виконує на сервері `sudo cat` і пише вивід одразу у файл на
  вашому комп'ютері — проміжної копії на сервері не лишається. Адреса сервера у файлі — `https://127.0.0.1:6443`, і
  такою вона й лишається: третя команда (в окремому терміналі) тримає тунель — `-L` пересилає ваш локальний порт
  6443 на порт 6443 самого сервера, `-N` — нічого не виконувати, лише тримати тунель. Далі в терміналі для сервера
  `export KUBECONFIG=~/.kube/oracle.yaml`. Вхідний трафік описують через **Gateway API** — новий стандарт
  Kubernetes на зміну Ingress; популярний ingress-nginx у березні 2026 знято з підтримки, тож його не вчать.
  Gateway — «вхідні двері»: порти, протоколи, імена, сертифікати; HTTPRoute — «яка адреса до якого Service».
  Traefik у k3s ставиться чартом Helm (Helm — менеджер пакетів Kubernetes; чарт — пакет із шаблонів маніфестів), а
  його налаштування змінюють об'єктом HelmChartConfig:

  ```yaml
  apiVersion: helm.cattle.io/v1
  kind: HelmChartConfig
  metadata:
    name: traefik
    namespace: kube-system
  spec:
    valuesContent: |-
      providers:
        kubernetesGateway:
          enabled: true
  ```

  `name: traefik` і `namespace: kube-system` мусять бути саме такі — так k3s знає, до якого вбудованого чарта
  застосувати зміну. `valuesContent` — значення чарта текстом YAML (`|-` означає «далі багаторядковий текст»);
  `providers.kubernetesGateway.enabled` вмикає в Traefik підтримку Gateway API. Цей об'єкт на всю родину один:
  план NestJS доповнить його у фазі 6, день 9, і у фазі 7, день 6, — тримайте файл у `k8s/` і дописуйте його, а не
  створюйте другий. Ворота поки що з одним слухачем:

  ```yaml
  apiVersion: gateway.networking.k8s.io/v1
  kind: Gateway
  metadata:
    name: web
    namespace: app
  spec:
    gatewayClassName: traefik
    listeners:
      - name: http
        protocol: HTTP
        port: 8000
  ```

  `gatewayClassName` — яка реалізація обслуговує ці ворота; точне ім'я класу покаже `kubectl get gatewayclass`.
  Слухач `http` з портом 8000 — не помилка: у Traefik порт слухача — це внутрішній порт його точки входу, а назовні
  він відкритий як 80 (звірте в примірнику `kubernetes` — `Traefik: Traefik Kubernetes Gateway API Documentation`
  для лінії Traefik 3). HTTPRoute `spa` —
  той самий, що буде до кінця родини, лише сьогодні він чіпляється до слухача `http`:

  ```yaml
  apiVersion: gateway.networking.k8s.io/v1
  kind: HTTPRoute
  metadata:
    name: spa
    namespace: app
  spec:
    parentRefs:
      - name: web
        sectionName: http
    hostnames:
      - app.203-0-113-10.sslip.io
    rules:
      - backendRefs:
          - name: spa
            port: 80
  ```

  `parentRefs` — до яких воріт і до якого слухача (`sectionName`) чіпляється маршрут. `hostnames` — для якого
  імені. `rules.backendRefs` — куди слати запит: Service `spa`, порт 80; правило без умов ловить усі шляхи. Ім'я без
  купівлі домену дає **sslip.io**: `app.203-0-113-10.sslip.io` саме перетворюється на адресу `203.0.113.10`
  (підставте адресу своєї машини). Але sslip.io не входить у Public Suffix List (перевірено 02.10.2026), тож для
  браузера всі `*.sslip.io` — один сайт: чужа сторінка на sslip.io може підкинути вашому застосунку куку з
  `Domain=sslip.io` і обійти захист `SameSite`. Тому sslip.io — лише для навчальних днів; до першого справжнього
  користувача й до демо — власний домен (близько $10 на рік, за сторонніми джерелами) або безкоштовний піддомен
  DuckDNS (`duckdns.org` у списку є, і кожен піддомен — окремий сайт). Образ на сервер їде через реєстр GHCR:
  ім'я `ghcr.io/<логін>/spa:0.1.0`. Вхід — класичним токеном доступу GitHub лише з правом `write:packages` і з
  терміном дії. Пакет за замовчуванням приватний, і так його й лишають: образ бекенду в плані NestJS лежатиме там
  само. Щоб кластер міг стягнути приватний образ, йому дають окремий токен лише з правом `read:packages`,
  покладений у Secret типу `docker-registry` з ім'ям `ghcr`:

  ```bash
  kubectl create secret docker-registry ghcr -n app \
    --docker-server=ghcr.io --docker-username=<логін> --docker-password=<токен read:packages>
  ```

  `docker-registry` — тип Secret для входу в реєстр; `ghcr` — ім'я, яким на нього посилатимуться всі Deployment
  родини; `-n app` — простір імен; решта — адреса реєстру, логін і токен. У Deployment поруч із `containers`
  з'являються два рядки — `imagePullSecrets:` і під ним `- name: ghcr`: «тягни образи з цим входом». Secret
  створюють командою, а не файлом у репозиторії: токен у git — уже не секрет; пробіл на початку рядка команди — і
  bash в Ubuntu не запише її в історію.
- **Читати:** у примірнику `kubernetes` — `K3s: Quick-Start Guide`, `K3s: Networking Services` (розділ про Traefik і
  HelmChartConfig), `K3s: Secrets Encryption`, `Gateway API`,
  `Traefik: Traefik Kubernetes Gateway API Documentation`; поза корпусом — документація Oracle Cloud: «Always Free
  Resources», «Creating an Instance»; документація GitHub: «Working with the Container registry»; сайт Public Suffix
  List.
- **Сервери MCP:** `kubernetes-docs`.
- **Зробити:** 1) у WSL `ssh-keygen -t ed25519` — пара ключів, публічна половина в `~/.ssh/id_ed25519.pub`;
  2) у консолі Oracle створити машину: форма VM.Standard.A1.Flex, 2 OCPU, 12 ГБ, образ Ubuntu для arm64

### День 9. HTTPS, нова версія й відкат

- **Навіщо.** Сайт по HTTP браузер позначає «Не захищено», а кука з прапорцем `Secure` по ньому не ходить зовсім.
  Друга половина дня — навичка, яку питають на кожній співбесіді про DevOps: викотити нову версію без простою й
  відкотити погану однією командою.
- **Що це.** **cert-manager** сам отримує й поновлює сертифікати Let's Encrypt: ClusterIssuer каже, де і як їх
  брати, а перевірка HTTP-01 — це Let's Encrypt просить файл за адресою `http://<ім'я>/.well-known/acme-challenge/…`,
  і cert-manager тимчасово його віддає власним маршрутом. Встановлення з WSL:

  ```bash
  helm repo add jetstack https://charts.jetstack.io
  helm upgrade --install cert-manager jetstack/cert-manager \
    --namespace cert-manager --create-namespace \
    --set crds.enabled=true --set config.gatewayAPI.enabled=true
  ```

  `helm repo add` — підключити сховище чартів cert-manager. `helm upgrade --install` — поставити, а якщо вже
  стоїть — оновити: ту саму команду можна повторювати, тому вона й іде в `infra/README.md`. `--namespace` і
  `--create-namespace` — окремий простір імен для cert-manager. `crds.enabled=true` — поставити разом із чартом
  власні типи об'єктів cert-manager (Certificate, ClusterIssuer); `config.gatewayAPI.enabled=true` — увімкнути
  роботу з Gateway API (для cert-manager 1.15 і новіших; точні імена параметрів звірте в примірнику `kubernetes` —
  `cert-manager: Annotated Gateway resource`). CRD Gateway API мусять бути в кластері **до** встановлення
  cert-manager: він перевіряє їх на старті. Якщо поставили в іншому порядку — `kubectl rollout restart deployment
  cert-manager -n cert-manager`. Видавець:

  ```yaml
  apiVersion: cert-manager.io/v1
  kind: ClusterIssuer
  metadata:
    name: letsencrypt-staging
  spec:
    acme:
      server: https://acme-staging-v02.api.letsencrypt.org/directory
      email: you@example.com
      privateKeySecretRef:
        name: letsencrypt-staging-key
      solvers:
        - http01:
            gatewayHTTPRoute:
              parentRefs:
                - name: web
                  namespace: app
                  kind: Gateway
  ```

  `server` — адреса тестового (staging) сервера Let's Encrypt: його сертифікатам браузер не довіряє, зате ліміти
  в нього щедрі. `email` — куди писатимуть про сертифікати, що закінчуються. `privateKeySecretRef` — Secret, де
  cert-manager тримає ключ вашого облікового запису в Let's Encrypt. `solvers.http01.gatewayHTTPRoute` — проходити
  перевірку HTTP-01 тимчасовим HTTPRoute, причепленим до воріт `web`. Другий видавець, `letsencrypt-prod`, —
  копія з адресою `https://acme-v02.api.letsencrypt.org/directory` і своїм ім'ям ключа. Ворота отримують анотацію
  й другого слухача:

  ```yaml
  metadata:
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-staging
  spec:
    listeners:
      - name: https
        protocol: HTTPS
        port: 8443
        hostname: app.203-0-113-10.sslip.io
        tls:
          mode: Terminate
          certificateRefs:
            - name: app-tls
  ```

  Анотація просить cert-manager отримати сертифікат для кожного слухача з ім'ям і TLS через вказаний
  ClusterIssuer. Порт 8443 — внутрішній порт точки входу Traefik, назовні це 443. `hostname` — для якого імені цей
  слухач. `tls.mode: Terminate` — HTTPS закінчується тут, далі в под іде звичайний HTTP; `certificateRefs` — у
  якому Secret лежить сертифікат (його створить cert-manager). Слухач `http` лишається на місці. HTTPRoute `spa`
  переходить на `sectionName: https` і лишається там до кінця родини — плани NestJS і Next.js, доповнюючи маршрут,
  цей рядок зберігають. Слухач `http` дістається другому маршруту, `spa-redirect`, з тим самим `hostnames` і з
  фільтром замість `backendRefs`:

  ```yaml
    rules:
      - filters:
          - type: RequestRedirect
            requestRedirect:
              scheme: https
              statusCode: 301
  ```

  Він відповідає на будь-який запит по HTTP перенаправленням на ту саму адресу з `https`. Перевірки Let's Encrypt
  не постраждають: тимчасовий маршрут cert-manager має точний шлях, а точний шлях у Gateway API важить більше за
  маршрут без умов. Нова версія — це зміна тегу в Deployment. Kubernetes оновлює поди поступово: з двома репліками і
  стандартними налаштуваннями він спершу створює один новий под, чекає, доки той пройде перевірку готовності, і лише
  потім гасить старий. Новий под не готовий — старі продовжують працювати, і користувачі нічого не помічають.
  `kubectl rollout status` стежить за оновленням, `kubectl rollout history` показує ревізії, `kubectl rollout undo`
  повертає попередню. Анотація `kubernetes.io/change-cause` на Deployment робить історію читабельною: замість
  порожньої колонки — ваш опис версії.
- **Читати:** у примірнику `kubernetes` — `cert-manager: Helm`, `cert-manager: HTTP01`,
  `cert-manager: Annotated Gateway resource`, `Let's Encrypt: Rate Limits`, `Let's Encrypt: Staging Environment`,
  `Deployments` (розділи «Updating a Deployment» і «Rolling Back a Deployment»),
  `Gateway API: HTTP path redirects and rewrites`; у примірнику `vite` — `static-deploy`.
- **Сервери MCP:** `kubernetes-docs`, `vite-docs`.
- **Зробити:** 1) Helm у WSL (сторінка «Installing Helm» його документації), cert-manager командою вище, `kubectl
  get pods -n cert-manager` — усі `Running`; 2) обидва ClusterIssuer — `kubectl apply -f`; 3) у Gateway — анотація
  з `letsencrypt-staging` і слухач `https`, застосувати, `kubectl get certificate -w` — дочекатися `READY True`;
  4) HTTPRoute `spa` перевести на `sectionName: https`, додати `spa-redirect`, застосувати; `curl -kI
  https://<адреса>/` (`-k` — бо staging-сертифікат недовірений); 5) змінити анотацію на `letsencrypt-prod`,
  застосувати й знову дочекатися `READY True`; 6) відкрити адресу з телефона; 7) змінити помітний текст на
  головній, зібрати й відправити `0.2.0`, змінити тег у `k8s/`, застосувати, `kubectl annotate deployment/spa
  kubernetes.io/change-cause="0.2.0: новий заголовок"`, `kubectl rollout status deployment/spa`; 8) в окремому
  терміналі цикл `while true; do curl -s -o /dev/null -w '%{http_code}\n' https://<адреса>/; sleep 1; done`;
  9) зламати `nginx.conf` (зайва дужка), зібрати й викотити `0.3.0` — `rollout status` зависне, вихід `Ctrl+C`;
  10) `kubectl get pods`, потім `kubectl rollout undo deployment/spa` і `kubectl rollout history deployment/spa`;
  11) повернути в `k8s/` тег, що реально працює, і закомітити; 12) Lighthouse mobile на новій адресі — рядок
  журналу «кластер»; 13) усі команди дня — в `infra/README.md`.
- **Перевірити себе:** `kubectl get certificate` — `READY True`; `curl -I https://<адреса>/` — `200` з
  `cache-control: no-cache` і без попереджень про сертифікат, `curl -I http://<адреса>/` — `301` на `https`; після
  кроку 9 один новий под у `CrashLoopBackOff`, два старі `Running`, а цикл із кроку 8 весь час друкує лише `200`;
  після кроку 10 сайт знову показує `0.2.0`, а в історії видно ревізії з вашими описами; журнал має рядок, де видно
  різницю між статичним хостингом і кластером.
- **Пастка:** відкотитися через `kubectl rollout undo` і забути про репозиторій. У кластері працює `0.2.0`, а в
  `k8s/` лишився зламаний `0.3.0` — і наступний `kubectl apply -f k8s/` старанно повертає поломку. Джерело правди —
  файли в git; відкат командою — лише швидка допомога, після якої виправляють файл. Друга пастка — одразу брати
  бойовий сервер Let's Encrypt: на 02.10.2026 ліміт — 5 сертифікатів на той самий набір імен за 7 днів і 5 невдалих
  перевірок на ім'я за годину; вичерпали — тиждень без HTTPS. Спершу staging.

**Критерій завершення фази:** злиття в головну гілку саме перевіряє застосунок; SPA працює у власному кластері за
HTTPS, нова версія викочується без простою, а погана відкочується однією командою; журнал вимірів показує числами,
що стало краще і завдяки чому.

## Поняття простими словами

- **Блокчейн.** Журнал записів, який лише дописується і копія якого лежить у тисяч незалежних учасників. Змінити
  старий запис не можна непомітно: усі копії розійдуться з вашою. Довіра тримається не на одній компанії, а на
  тому, що більшість учасників дотримується тих самих правил.
- **Блок.** Порція записів журналу, що додається за раз. Кожен блок містить хеш попереднього, тож вони зчеплені в
  ланцюг: змінити один — означає перерахувати всі наступні.
- **Приватний ключ і сід-фраза.** Приватний ключ — секретне число, яким підписують транзакції; хто має ключ, той
  розпоряджається коштами, і відновити вкрадене нікому не під силу. Сід-фраза — 12 або 24 слова, з яких
  виводиться вся низка ключів гаманця. Це одне й те саме за силою: сід-фраза = усі ключі разом.
- **Адреса.** Публічний ідентифікатор рахунку, `0x` і 40 шістнадцяткових символів, отриманий із ключа. Адресу
  можна давати будь-кому — як номер рахунку.
- **Гаманець.** Програма, що зберігає ключі й підписує ними, — розширення браузера на кшталт MetaMask. Монет у
  гаманці немає: вони записані в блокчейні за адресою, а гаманець лише тримає ключ до них.
- **Транзакція.** Підписане повідомлення «з адреси A на адресу B, стільки-то, з такими даними». Потрапляє в блок не
  миттєво: спершу чекає в черзі, потім її включають у блок, потім над нею наростають наступні блоки —
  підтвердження.
- **Газ.** Плата мережі за виконання транзакції. Кількість газу залежить від роботи (простий переказ — 21 000
  одиниць), ціна одиниці — від завантаженості мережі; в Ethereum вона складається з базової плати й чайових
  валідатору.
- **Nonce транзакції.** Лічильник транзакцій адреси: 0, 1, 2… Задає порядок і не дає повторити ту саму транзакцію
  вдруге. Не плутати з nonce входу гаманцем у плані NestJS — там це одноразовий рядок сервера.
- **Тестова мережа.** Копія мережі з монетами, що нічого не варті; їх роздають безкоштовно сервіси-«крани».
  Локальний ланцюг — те саме на вашому комп'ютері: миттєві блоки, десять готових рахунків із тестовими монетами.
- **Смарт-контракт.** Програма, що лежить у блокчейні за власною адресою. Читати з нього безкоштовно, змінювати
  його стан — лише транзакцією з газом.
- **ERC-20 і ERC-721.** Стандартні інтерфейси контрактів. ERC-20 — взаємозамінний токен (кожна одиниця рівна
  іншій): `balanceOf`, `transfer`, `approve`, `decimals`. ERC-721 — невзаємозамінний (NFT): кожен токен унікальний,
  має власника (`ownerOf`).
- **Стейблкоїн.** Токен, прив'язаний до долара чи іншої валюти, як USDC чи USDT; на біржі в парі `BTCUSDT` друга
  половина — саме він.
- **RPC-вузол.** Сервер, через який застосунок читає блокчейн і надсилає транзакції: запити JSON-RPC на кшталт
  `eth_getBalance`. Свій вузол тримати не обов'язково — є публічні й комерційні з безкоштовними лімітами.
- **Біржа проти блокчейну.** Централізована біржа (Binance, Kraken) — це звичайна база даних компанії: угоди між
  користувачами записуються в неї, а в блокчейн потрапляють лише заведення й виведення коштів. Тому ринкові дані
  біржі (свічки, книга заявок) — це не блокчейн, а API компанії.
- **Книга заявок.** Список заявок на купівлю (bids) і продаж (asks) за різними цінами з обсягами. Угода стається,
  коли ціни зустрічаються.
- **Свічка (OHLCV).** Зведення за проміжок часу: ціна відкриття (open), найвища (high), найнижча (low), закриття
  (close) і обсяг (volume). Графік свічок — головний графік трейдера.
- **Спред.** Різниця між найдешевшою пропозицією на продаж і найдорожчою на купівлю. Малий спред — ліквідний ринок.
- **Прослизання.** Різниця між ціною, яку ви бачили, і ціною, за якою заявка виконалася: велика заявка «з'їдає»
  кілька рівнів книги, і кожен наступний дорожчий.

## Правила безпеки

- **Приватний ключ і сід-фраза ніколи не потрапляють** у код, репозиторій, `.env` фронтенду, лог, скриншот чи
  чат. Застосунок їх ніколи не просить: підписує гаманець. Сайт, що просить сід-фразу, — шахрайський без винятків.
- **Для вправ — окремий профіль браузера з окремим гаманцем**, у якому ніколи не було справжніх коштів. Ключі
  рахунків Anvil однакові в усіх і опубліковані — будь-що, надіслане на них у справжній мережі, зникне за хвилини.
- **Лише локальний ланцюг і тестова мережа.** Жодна вправа не потребує справжньої мережі.
- **Ключі API бірж, якщо колись знадобляться, — лише на читання**, без права виведення, з прив'язкою до IP, і лише
  на сервері: у фронтенд-збірці секретів не існує (фаза 5, день 2).
- **Читайте, що підписуєте.** `approve` і `setApprovalForAll` дають контракту право витрачати ваші токени — часто
  без ліміту; саме так спустошують гаманці через фішингові сайти. Незнайомі токени, що «самі прийшли», і адреси,
  схожі на ваші першими й останніми символами, — типові пастки.

## Гроші — ніколи не `float`

Число JavaScript — двійкове з плаваючою комою: `0.1 + 0.2` дає `0.30000000000000004`, а цілі понад 2^53 втрачають
точність. Для грошей це неприйнятно. Правила родини:

- **Ціни з біржі — рядки**, і такими їх тримають від мережі до екрана; Binance так їх і шле. Арифметика —
  бібліотекою десяткових чисел (decimal.js чи big.js), показ — `Intl.NumberFormat`.
- **Суми в блокчейні — `bigint`** у найменших одиницях: 1 ETH = 10^18 wei. `parseEther('0.5')` перетворює рядок на
  `bigint`, `formatEther` — назад, лише для показу. Токени ERC-20 мають власне `decimals`, звідси `parseUnits` і
  `formatUnits`.
- **У базі — `NUMERIC`**, а не `REAL` чи `DOUBLE PRECISION`; `BIGINT` для wei замалий. Це вже план NestJS,
  факультатив, день К1.
- `Number(x)` і `parseFloat(x)` дозволені лише на межі з бібліотекою, що приймає тільки числа (графік у дні К2), і
  ніколи — в обчисленнях.

## Порядок трьох блоків

1. **React, дні К1–К5** — ринкові дані, графік, книга заявок, гаманець, транзакція. Після шляху мідла плану React.
2. **NestJS, дні К1–К4** — гроші й свічки в базі, сповіщення про ціну, вхід гаманцем (SIWE), читання блокчейну.
   Після фаз 0–7 плану NestJS.
3. **Next.js, дні К1–К3** — портфель за адресою на сервері, власний токен ERC-20 на тестовій мережі, вхід гаманцем
   через BFF і демо клієнту. Після фаз 0–9 плану Next.js.

Кожен блок можна брати одразу після основної частини свого плану, але не раніше: він спирається на її код.

## Дні факультативу — К1–К5

### День К1. Свічки й книга заявок через REST

- **Навіщо.** Перш ніж малювати графік і книгу заявок, треба побачити, з чого вони складаються, і навчитися рахувати
  гроші без похибок.
- **Що це.** Ринкові ендпойнти Binance лише для даних (`https://data-api.binance.vision`) працюють без ключа й
  дозволяють запити з браузера. `GET /api/v3/klines?symbol=BTCUSDT&interval=1m&limit=500` повертає масив свічок,
  кожна — масив із 12 полів: час відкриття в мілісекундах, open, high, low, close, обсяг і далі; ціни — рядки.
  Щонайбільше 1000 свічок за запит; старіші — сторінками через `endTime` (кінець попередньої сторінки мінус одна
  мілісекунда). `GET /api/v3/depth?symbol=BTCUSDT&limit=100` — знімок книги заявок: `bids` і `asks` як пари
  «ціна, обсяг», рядками, і `lastUpdateId`. Кожен запит має «вагу», ліміт ваги — на хвилину з вашої адреси;
  використану вагу показує заголовок `x-mbx-used-weight-1m`. Спред — найнижча ціна в `asks` мінус найвища в `bids`.
  Прослизання для купівлі обсягу X — пройти `asks` знизу вгору, поки не набрано X, і порівняти середню ціну з
  найкращою.
- **Читати:** у примірнику `tanstack-query` — `Infinite Queries`, `Query Keys`; у примірнику `binance-spot` —
  `Public Rest API for Binance` (розділи «General API Information», «IP Limits», «Kline/Candlestick data», «Order
  book»), `Market Data Only URLs`; документація decimal.js (поза корпусом).
- **Сервери MCP:** `tanstack-query-docs`, `binance-spot-docs`.
- **Зробити:** 1) `useQuery` для 500 хвилинних свічок BTCUSDT і таблиця з них; 2) `useInfiniteQuery` з кнопкою
  «старіші»; 3) знімок книги на 20 рівнів з обох боків; 4) спред і прослизання для купівлі 0,5 і 5 BTC — через
  decimal.js; 5) те саме для порівняння через `parseFloat` у консоль.
- **Перевірити себе:** після трьох натискань «старіші» в таблиці 2000 свічок без пропусків і дублів за часом; у
  вкладці «Мережа» видно заголовок ваги, що росте з кожним запитом; спред через decimal.js — точне число без хвостів,
  а варіант із `parseFloat` хоча б раз показує хвіст на кшталт `…0000001`.
- **Пастка:** `limit` понад 1000 чи цикл «вантажимо всю історію одразу». Більше 1000 свічок за запит документація не
  дає, а цикл витрачає вагу, і якщо після відповіді 429 не зупинитися, адресу блокують автоматично (статус 418).
  Беріть сторінками й лише те, що видно на екрані.

### День К2. Графік свічок

- **Навіщо.** Таблиця з 2000 рядків — не інтерфейс. Графік свічок — головний екран будь-якого крипто-застосунку, і
  на ньому видно, як React живе поруч із віджетом, що малює сам.
- **Що це.** TradingView lightweight-charts 5.2.1 малює на canvas і про React нічого не знає — це «віджет не на
  React» з глави про ефекти. Графік створюють в ефекті на `div` з ref (`createChart(element, options)`) і знищують у
  прибиранні (`chart.remove()`); серію свічок додає `chart.addSeries(CandlestickSeries, options)`. Історію задає
  `series.setData(bars)`, живу свічку — `series.update(bar)`: вона або оновлює останню, або додає нову. Час у
  бібліотеці — у секундах, у Binance — у мілісекундах; ціни бібліотека бере числами, тож перетворення рядка на
  число стоїть лише тут, на самій межі з графіком. Живі оновлення йдуть зі стору фази 3 прямо в `series.update`, в
  обхід стану React: графік оновлюється, а React не рендерить нічого. Ліцензія Apache-2.0 вимагає зазначити
  авторство TradingView з посиланням на їхній сайт; у версії 5 це робить логотип на графіку, увімкнений за
  замовчуванням.
- **Читати:** `Synchronizing with Effects` (розділ «Controlling non-React widgets»), `useRef`; документація
  lightweight-charts — «Getting started», «Series», розділ про авторство (поза корпусом); у примірнику `binance-spot`
  — `WebSocket Streams for Binance` (розділ «Kline/Candlestick Streams for UTC»).
- **Сервери MCP:** `react-docs`, `binance-spot-docs`.
- **Зробити:** 1) компонент `CandleChart` з `createChart` в ефекті й `chart.remove()` у прибиранні; 2) історія з
  дня К1 через `setData`; 3) живі свічки з потоку `@kline_1m` через `update`; 4) перемикач інтервалу 1m / 15m / 1h
  (новий ключ запиту, новий потік); 5) записати профіль React за хвилину живого графіка.
- **Перевірити себе:** у розробці зі `<StrictMode>` на сторінці один графік, а не два; остання свічка рухається кожні
  2 секунди і закривається щохвилини; профайлер React за хвилину живих оновлень показує нуль комітів від графіка;
  логотип TradingView на місці.
- **Пастка:** `setData` на кожне повідомлення потоку. Бібліотека перебудовує всю серію, процесор гуде, а
  прокручування графіка скидається. Історія — `setData` один раз, далі — лише `update`.

### День К3. Книга заявок наживо

- **Навіщо.** Книга заявок — найвибагливіша до швидкості частина торгового інтерфейсу: сотні змін на секунду, і
  одна пропущена зміна тихо псує все, що показано далі.
- **Що це.** Потік `<пара>@depth@100ms` шле не книгу, а зміни: «на ціні X тепер обсяг Y» (нуль — рівень зник). Щоб
  з них вийшла правильна книга, Binance описує процедуру синхронізації: відкрити потік і буферизувати зміни;
  узяти знімок через REST; відкинути зміни, старші за `lastUpdateId` знімка; далі застосовувати по черзі, стежачи,
  щоб кожна наступна зміна продовжувала попередню без дірки в номерах (`U` і `u`). Дірка — книга вже неправильна,
  і синхронізація починається з нуля. Процедуру уточнювали, тож звіряйте кроки з поточною документацією, розділ
  «How to manage a local order book correctly». Сама книга живе поза React — у `Map` «ціна-рядок → обсяг» для кожного
  боку, а на екран раз на кадр (фаза 3, день 8) іде лише верх: 20 найкращих рівнів. Ключ — рядок ціни рівно таким,
  як прислала біржа: `"0.1"` і `"0.10000000"` для `Map` — різні ключі.
- **Читати:** `useSyncExternalStore`; у примірнику `mdn` — `Window: requestAnimationFrame() method`; у примірнику
  `binance-spot` — `WebSocket Streams for Binance` (розділи «Diff. Depth Stream», «How to manage a local order book
  correctly», «Individual Symbol Book Ticker Streams»).
- **Сервери MCP:** `react-docs`, `mdn-docs`, `binance-spot-docs`.
- **Зробити:** 1) модуль `orderBook` з буфером, знімком і застосуванням змін за процедурою; 2) виявлення дірки й
  повторна синхронізація з записом у лог; 3) екран: 20 рівнів з кожного боку, спред, смужки обсягу; 4) поруч —
  потік `@bookTicker`, що шле лише найкращу ціну купівлі й продажу; 5) вимкнути мережу на хвилину й увімкнути.
- **Перевірити себе:** найкращі ціни вашої книги збігаються з `@bookTicker` (незалежна перевірка); після кроку 5 у
  лозі одна повторна синхронізація, і збіг відновився; комітів React не більше, ніж кадрів.
- **Пастка:** застосовувати зміни до знімка без перевірки номерів. Книга виглядає живою, але після першої ж
  пропущеної зміни в ній висять рівні, яких на біржі давно немає, — і помітити це оком неможливо.

### День К4. Гаманець: підключення й баланс

- **Навіщо.** Підключити гаманець — перший крок будь-якого застосунку, що працює з блокчейном, і перша зустріч із
  `bigint` у грошах.
- **Що це.** wagmi 3 — хуки React для гаманця, побудовані на viem і на TanStack Query, тож кеш, стани
  завантаження й повтори вже знайомі; `WagmiProvider` загортається в `QueryClientProvider`. Конфіг
  `createConfig` перелічує мережі, з'єднувачі й транспорти (адреси RPC). З'єднувач `injected` говорить із
  гаманцем-розширенням, що вбудувався в сторінку, — без готових вікон вибору: RainbowKit і ConnectKit поки що лише
  для wagmi 2. Хуки: `useConnect` і `useDisconnect` — підключення, `useConnection` — адреса й мережа (у wagmi 2 він
  звався `useAccount`), `useBalance` — баланс як `bigint` у wei. Мережа для вправ — спершу **локальний ланцюг Anvil**
  з Foundry: `anvil` запускає вузол на `http://127.0.0.1:8545` з ідентифікатором ланцюга 31337 і десятьма рахунками
  по 10 000 тестових ETH. Тестова мережа — лише налаштуванням у конфігу. Яка саме: Ethereum Foundation оголошувала
  завершення Sepolia на 30.09.2026 і заміну їй, а на 02.10.2026 Sepolia ще працює — тож **перед днем перевірте в
  блозі Ethereum Foundation, яка тестова мережа зараз актуальна**, і лише тоді шукайте для неї кран.
- **Читати:** у примірнику `tanstack-query` — `QueryClientProvider`; документація wagmi — «Getting Started»,
  «Connect Wallet», «Migrate from v2 to v3» (поза корпусом); документація viem — «Units» (поза корпусом); Foundry
  Book — «Anvil» (поза корпусом).
- **Сервери MCP:** `tanstack-query-docs`.
- **Зробити:** 1) Foundry через `foundryup` у WSL, `anvil` в окремому терміналі; 2) у окремому профілі браузера —
  гаманець, мережа «localhost 8545» з ідентифікатором 31337, імпорт одного тестового рахунку Anvil; 3) конфіг wagmi з
  ланцюгом `foundry` і з'єднувачем `injected`; 4) кнопки «підключити» і «відключити», адреса скорочено, мережа,
  баланс через `formatEther`; 5) баланс іншої адреси Anvil — через `useBalance` з параметром `address`, без
  підключення; 6) у консоль — `formatEther(balance - 1n)` і `(Number(balance) - 1) / 1e18`.
- **Перевірити себе:** баланс — рівно `10000` ETH; після перезавантаження сторінки гаманець підключається знову без
  клацання; пошук по репозиторію й по вкладці «Мережа» не знаходить жодного ключа; у кроці 6 `formatEther` показує
  `9999.999999999999999999`, а варіант із `Number` — рівно `10000`: один wei загубився.
- **Пастка:** `Number(balance)`. 10 000 ETH — це 10^22 wei, далеко за межею точних цілих JavaScript (близько 9 ×
  10^15): для довільного балансу молодші розряди вже вигадані; рівно 10^22 — щасливий виняток, а мінус один wei вже
  губиться. Сума в блокчейні — завжди `bigint`, а рядок — лише для показу.

### День К5. Транзакція: газ, nonce, статуси

- **Навіщо.** Відправити транзакцію — найнебезпечніше місце будь-якого крипто-інтерфейсу: користувач платить газ,
  чекає, і кожен стан між «натиснув» і «готово» треба показати чесно.
- **Що це.** Шлях транзакції: застосунок готує її (`to`, `value` у wei) → гаманець показує, що підписати, і
  користувач погоджується або відхиляє → підписана транзакція отримує хеш і чекає в черзі → потрапляє в блок і
  отримує квитанцію (receipt) зі статусом `success` або `reverted` → над нею наростають підтвердження. Хеш — не
  успіх: транзакція з хешем ще може впасти. У wagmi `useSendTransaction` віддає хеш, а
  `useWaitForTransactionReceipt({ hash })` чекає квитанцію. Плата — використаний газ, помножений на фактичну ціну
  газу; обидва числа є в квитанції. Nonce адреси росте на одиницю з кожною транзакцією. Відхилення в гаманці — не
  збій, а звичайний результат: стандартний код помилки 4001, «користувач відмовився». Anvil за замовчуванням
  включає транзакцію в блок миттєво; `anvil --block-time 12` робить блок раз на 12 секунд — так видно очікування.
- **Читати:** у примірнику `zod` — `Defining schemas`; документація wagmi — «Send Transaction» (поза корпусом);
  документація viem — «sendTransaction», «waitForTransactionReceipt» (поза корпусом); ethereum.org — «Transactions»,
  «Gas and fees» (поза корпусом).
- **Сервери MCP:** `zod-docs`.
- **Зробити:** 1) форма «адреса й сума» зі схемою zod: адреса перевіряється `isAddress` з viem, сума — рядком,
  `parseEther` лише після перевірки; 2) відправка через `useSendTransaction`, стани «чекаємо підпису», «в черзі»,
  «у блоці», «впала», «відхилено»; 3) перезапустити `anvil --block-time 12` і пройти всі стани; 4) відхилити
  транзакцію в гаманці; 5) nonce адреси до й після; 6) баланс відправника до й після, плата з квитанції.
- **Перевірити себе:** різниця балансів відправника дорівнює сумі плюс платі з точністю до wei — перевірка на
  `bigint`, а не «приблизно»; nonce виріс на одиницю за кожну успішну транзакцію; відхилення показане як
  «відхилено», а не як помилка.
- **Пастка:** показати «Готово», щойно прийшов хеш. Транзакція ще в черзі, ще може впасти, а користувач уже пішов.
  Успіх — лише квитанція зі статусом `success`. Друга пастка — перезапустити `anvil` і не скинути історію рахунку в
  гаманці: гаманець пам'ятає старий nonce, і нові транзакції відкидаються з помилкою nonce.

# Що далі

План React закінчується застосунком, який живе у власному кластері, показує живі ціни з біржі, але записи бере з
фейкового API. Зшивання з бекендом — не окрема фаза тут, а частина плану NestJS
([../nestjs/LEARNING.md](../nestjs/LEARNING.md)), де кожна вправа має і фронт-бік:

- **Контракт.** NestJS видає документ OpenAPI, з нього генерується типізований клієнт, і SPA переходить на нього
  — жодного ручного типу відповіді (план NestJS, фаза 2, день 7).
- **Помилки.** Помилка валідації з бекенду приходить за шляхом поля, і форма з фази 3, дня 10 підсвічує конкретне
  поле через `setError` (план NestJS, фаза 2, день 8).
- **Токени й проксі.** У розробці SPA ходить в API через проксі Vite (`server.proxy`, у примірнику `vite` —
  `Server Options`): одне походження, CORS не потрібен (план NestJS, фаза 0, день 11). Модель токенів із фази 5,
  дня 2 реалізується наскрізь: вхід, мовчазне оновлення, вихід (план NestJS, фаза 4, дні 6–9).
- **Усе разом.** Локально — SPA, бекенд, база й міграції однією командою `docker compose`, з образом SPA з фази 5,
  дня 7 (план NestJS, фаза 6, день 2). На продакшні — той самий кластер із фази 5: бекенд, база й Redis стають
  подами поруч зі SPA, а SPA й API — одним іменем (план NestJS, фаза 6, дні 8–9).
- **Живі дані.** Ціни йдуть уже не з біржі напряму, а з власного сервера через WebSocket, з входом і правами; у
  SPA змінюється лише модуль джерела з фази 3, дня 6, стор і швидкі оновлення лишаються (план NestJS, фаза 7).

Після NestJS — план Next.js ([../nextjs/LEARNING.md](../nextjs/LEARNING.md)): у фазі 6, день 5 цей самий SPA
переїжджає на Next.js, у фазі 7 под Next.js замінює под SPA в кластері, фаза 8 зшиває Next.js з NestJS і
повертає живі дані (дні 6–7), а фаза 9 оновлює під Next.js демо для клієнта, зроблене в плані NestJS (фаза 7,
день 8).

# Під працевлаштування

**Портфоліо.** Один застосунок, доведений до кінця фази 5, вартий більше, ніж п'ять недороблених. З репозиторію має
бути видно: типізацію без `any`, дані в лоадерах і кеші, живі ціни через WebSocket із перепідключенням і замірами до й
після, форми з однією схемою, тести трьох рівнів, доступність, CI, Dockerfile і маніфести Kubernetes у репозиторії,

# Застереження про документацію

У корпусі цього примірника — **лише сама React**, зате всіх версій від 0.3 до 19.3 разом із CHANGELOG, нотатками
релізів і блогом, включно з оголошеннями про вразливості. Про інші бібліотеки й інструменти сервер `react-docs`
відмовить або поверне лише уривки, де їх згадано. Для яких із них у фабриці є власний примірник, а для яких його ще
немає, — у підрозділі «Документація у фабриці» (розділ «Екосистема»); там же — що беруть із сайтів самих
інструментів.

**Дати.** Усе, що в плані про безкоштовні тарифи, ліміти бірж, версії пакетів факультативу й стан тестових мереж,
сказано на 02.10.2026. Ці речі змінюються швидше за документацію React: перед днем, що на них спирається,
перевірте першоджерело.

**Легасі-глави.** `Reconciliation` і `Optimizing Performance` — документація до React 18 включно; у новій
документації окремих глав немає. План посилається на них свідомо й щоразу каже, що саме звідти брати. Сервер
повертає їх із версіями — дивіться на них.

**Приклади з інших примірників.** `Example: react/react-router` — приклад із репозиторію TanStack Query, а не
рекомендація React Router; беріть з нього зв'язку лоадера з кешем, а не все підряд.

**Безпека.** Оголошення про вразливості виходять у блозі React і є в корпусі. Перед кожним оновленням React
питайте сервер про свіжі оголошення для вашої лінії й перевіряйте, чи вони стосуються вашої збірки: SPA на Vite і
застосунок із серверними компонентами зачіпають різні оголошення.
