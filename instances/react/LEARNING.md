# React — план вивчення

План для того, хто вже пише на React на рівні мідла і хоче вийти на роботу фулстеком, — і водночас повний шлях
для того, хто React тільки починає. Він перший у родині з трьох планів: React → NestJS → Next.js. Через усі три
проходить один проєкт: тут це SPA на Vite, у плані NestJS ([../nestjs/LEARNING.md](../nestjs/LEARNING.md)) він
отримує власний бекенд, у плані Next.js ([../nextjs/LEARNING.md](../nextjs/LEARNING.md)) переїжджає на Next.js і
зшивається з NestJS. Плани проходять по черзі, не паралельно. Кожен день пояснений від знайомого до нового: що
ви вже робите руками, що за цим стоїть і як це перевірити числом або спостереженням.

Шляхів два. **Шлях мідла** — двадцять п'ять днів за контрольними питаннями, з першим викотом застосунку в
інтернет у перший же день; він описаний нижче, перед повним шляхом. **Повний шлях** — шістдесят один навчальний
день по півтори-дві години, від мови й браузера до продакшну. П'ять днів на тиждень (два лишаються на те, щоб
доганяти пропущене) дають близько трьох місяців повного шляху або п'ять тижнів шляху мідла.

| Фаза | Тема | Днів |
|------|------|------|
| 0 | База, якої React не дає: JS, TypeScript, браузер, інструменти | 12 |
| 1 | Ядро React — розділ Learn | 20 |
| 2 | Як React працює зсередини: заміри, рендер, конкурентність, компілятор | 8 |
| 3 | Екосистема: маршрути, серверний стан, форми, глобальний стан, тести | 12 |
| 4 | Сервер: SSR, стрімінг, серверні компоненти | 3 |
| 5 | Продакшн: збірка, безпека, метрики, CI, викот | 6 |

## Як користуватися планом

**Як влаштований день.** У кожного дня шість рядків. **Навіщо** — яку задачу тема розв'язує. **Що це** —
пояснення простими словами, від того, що ви вже знаєте, до нового. **Читати** — глави документації. **Зробити** —
вправа по кроках. **Перевірити себе** — що має вийти, якщо все правильно: число, рядок у лозі, поведінка на
екрані. **Пастка** — помилка, яку на цьому місці роблять майже всі.

**Один наскрізний проєкт.** Не десяток навчальних застосунків, а один, який росте через усі фази й переходить у
плани NestJS і Next.js. Добре працює будь-що зі списками, формами, входом і публічною частиною: трекер задач із
публічними дошками, каталог з адмінкою, журнал витрат із кабінетом. Списки покажуть ключі й продуктивність, форми —
стан і валідацію, вхід — модель токенів, яку далі доробить бекенд.

**День — одиниця умовна.** Якщо тема не вляглася за день, беріть другий. Небезпечний не пропущений день, а
пропущена вправа: без неї тема лишається прочитаною, а не вивченою.

**Журнал вимірів.** З кінця фази 1 (фаза 1, день 20; на шляху мідла — перший день) у README проєкту живе таблиця:
дата, що змінили, LCP, INP, CLS, розмір JavaScript у КБ після gzip. Кожна вправа-замір у плані називає інструмент і
число, яке треба записати. Умови лабораторного заміру однакові щоразу: продакшн-збірка (`vite build` і
`vite preview` або викочена адреса), Lighthouse у режимі mobile, три прогони, у журнал іде медіана. Без журналу
«стало швидше» — це враження, а на співбесіді питають число. Що означають LCP, INP і CLS, пояснює словник нижче.

**Документація під рукою.** Цей примірник фабрики — і є довідник: `./df react serve` з кореня, далі питання до
MCP-сервера замість пошуку в гуглі. Корпус тримає документацію всіх версій React від 0.3 до 19.3 разом із
CHANGELOG, нотатками релізів і блогом, тож відповідь приходить із зазначенням версії. Для бібліотек екосистеми
підняті власні примірники — `react-router`, `tanstack-query`, `react-hook-form`, `zod`, `zustand`, `redux`,
`tailwind`, `vite`, `typescript`; вони запускаються так само: `./df <назва> serve`. Назви глав у плані
(у бектиках) — точні назви документів корпусу, їх можна питати дослівно. Якщо назва двозначна, поруч
словами сказано, яка саме: «`Installation` (Learn)» і «`Installation` (React Compiler)». Те, чого в корпусах немає,
позначено «поза корпусом» або «порада з практики».

**Версія.** Вчіть на React 19, останній патч лінії 19.3 (анонс у блозі React від 09.09.2026). Усе в плані — про
сучасний React із функціональними компонентами й хуками; класові компоненти трапляються рівно раз — у дні про межі
помилок, бо інакше межу помилок і досі не написати.

**Чому SPA на Vite, а не фреймворк.** Глава `Creating a React App` радить починати з фреймворку (Next.js, React
Router у режимі фреймворку тощо). План свідомо йде іншим шляхом, який документація описує поруч, у главі
`Build a React app from Scratch`: Vite з шаблоном `react-ts`, а маршрути, дані й розділення коду ви додаєте самі.
Так видно кожен механізм окремо, а фреймворк чекає на вас у плані Next.js. Розділ цієї глави «Step 2: Build Common
Application Patterns» — маршрутизація, отримання даних, розділення коду, продуктивність — це карта фаз 3 і 5.

## Якщо ви вже пишете на React: шлях мідла

План написаний від нуля, але мідлу не варто читати його поспіль. Шлях мідла — це базові двадцять п'ять днів, які
мідл зазвичай пропускає на роботі: TypeScript у React, ефекти, заміри, дані до рендеру, тести, безпека, метрики.
Решту фаз ви проходите вправами, без читання, — якщо впевнено відповіли на контрольні питання.

### Контрольні питання

Відповідайте письмово, у README проєкту, у перший день шляху — до того, як відкрити документацію. Якщо відповідь
упевнена — фазу можна пройти вправами. Кожне питання, на яке відповідь не впевнена, — це день повного шляху, який
треба пройти цілком, понад двадцять п'ять базових.

- **Фаза 0.** Чому `items.push(x)` у стані не перемальовує екран? Як замикання робить «застаріле» значення в
  `setTimeout`? Що відбувається в браузері між зміною стилю й пікселями на екрані? Чим `unknown` відрізняється від
  `any`?
- **Фаза 1.** Чому `key` за індексом масиву ламає список із видаленням? Чому два поспіль `setCount(count + 1)`
  дають плюс один, а не плюс два? Як скинути стан форми при зміні сутності без ефекту? Коли ефект **не** потрібен,
  хоч його й хочеться написати? Як типізувати `children` і обробник події поля вводу?
- **Фаза 2.** Чим рендер відрізняється від коміту? Як довести числом, що `useMemo` щось дав, і що змінив React
  Compiler? Що дає `useTransition`, чого не дає `setTimeout`? Яку помилку межа помилок не зловить?
- **Фаза 3.** Чому `useEffect` плюс `fetch` — водоспад запитів і гонки? Що робить лоадер маршруту? Чим `staleTime`
  відрізняється від `gcTime`? Що тестує React Testing Library і чого вона принципово не тестує?
- **Фаза 4.** Чим серверний компонент відрізняється від SSR? Що можна передати через межу `'use client'`? Чому
  Server Function — публічний ендпойнт?
- **Фаза 5.** Чому секретів у фронтенд-збірці не існує? Чим міряють LCP, INP і CLS і що кожна означає? Чому
  `index.html` не кешують, а файли з хешем в імені кешують на рік?

### Двадцять п'ять днів

Порядок важливий: перший день дає працюючий застосунок в інтернеті й перший рядок журналу, останній — CI, що
стереже все зроблене.

- **День 1** — контрольні питання письмово, потім фаза 1, день 20: збірка, викот на статичний хостинг (перші
  тридцять хвилин дня) і перший рядок журналу вимірів;
- **дні 2–6** — фаза 1, дні 6, 16, 17, 18 і 19: TypeScript у React і чотири дні про ефекти;
- **дні 7–9** — фаза 2, дні 1, 4 і 5: профайлер, мемоізація з компілятором одним заміром, `useTransition` і INP;
- **дні 10–19** — фаза 3, дні 1–7 і 9–11: маршрути, лоадери, TanStack Query, мутації, форми React 19, React Hook
  Form із zod, три рівні тестів;
- **дні 20–21** — фаза 4, дні 1 і 3: SSR і гідратація, серверні компоненти й межа клієнта (на них спирається
  фаза 0 плану Next.js);
- **дні 22–25** — фаза 5, дні 1, 2, 3 і 5: розділення коду, оточення й безпека, метрики, CI.

Після двадцять п'ятого дня — план NestJS. Решту днів цього плану (віртуалізація, доступність, ресурси сторінки,
кеш-заголовки статики) добирайте, коли проєкт до них дійде або коли контрольне питання показало прогалину.

### Карта пропусків: що звідси закриває дні інших планів

- Фаза 3, дні 9–11 — тести: план Next.js тестує клієнтські компоненти так само й додає лише те, чого тут немає.

## Словник: слова, без яких план не читається

- **Рендер і коміт.** Рендер — React викликає ваші функції-компоненти й отримує опис інтерфейсу. Коміт — React
  записує різницю в DOM. Малює пікселі вже браузер, після коміту. Три різні події в часі.
- **Стан і пропси.** Пропси — те, що компонент отримав від батька, лише для читання. Стан — пам'ять компонента
  між рендерами; змінюється тільки через функцію `set`, і кожна зміна просить новий рендер.
- **Знімок стану.** У кожному рендері стан — константа. Обробник події бачить значення того рендеру, в якому його
  створено, а не «поточне».
- **Чистий компонент.** Однакові пропси й стан — однаковий результат, і жодних змін зовнішнього світу під час
  рендеру. React на цьому будує все, від `<StrictMode>` до компілятора.
- **Ефект.** Код, що синхронізує компонент із чимось **зовнішнім**: мережа, підписка, віджет не на React. Не
  «зробити після рендеру».
- **Ключ (`key`).** Ідентичність елемента списку. За ним React вирішує, чий стан кому належить після зміни списку.
- **Ref.** Скринька для значення, яке живе між рендерами, але не викликає рендер при зміні; часто — посилання на
  DOM-вузол.
- **Контекст.** Спосіб передати значення вглиб дерева без пропсів на кожному рівні. Не менеджер стану.
- **Перехід (transition).** Оновлення, позначене як нетермінове: React може перервати його заради введення.
- **`<Suspense>` і межа помилок.** Перший показує заглушку, доки щось усередині чекає (код чи дані). Друга показує
  запасний екран, якщо щось усередині впало під час рендеру.
- **Мемоізація.** Запам'ятати результат і не рахувати вдруге, якщо входи не змінилися: `memo`, `useMemo`,
  `useCallback`. **React Compiler** робить це автоматично на збірці.
- **Серверний стан.** Дані, що належать серверу й у браузері лише кешуються: список задач, профіль. Протилежність —
  клієнтський стан: відкрите меню, введений текст.
- **Лоадер.** Функція маршруту, яка вантажить дані до того, як компонент сторінки відрендерився.
- **SSR і гідратація.** SSR — HTML малюється на сервері. Гідратація — React у браузері «оживляє» цей HTML,
  навішує обробники на готову розмітку.
- **Серверний компонент (RSC).** Компонент, що виконується заздалегідь в окремому середовищі (на збірці чи на
  сервері) і свій код у браузер не шле. **Server Function** — функція на сервері, яку клієнт викликає мережею; до
  вересня 2024 усі вони звалися Server Actions.
- **Бандл і чанк.** Бандл — JavaScript, зібраний для браузера. Чанк — окремий файл бандла, що вантажиться, коли
  потрібен.
- **LCP, INP, CLS.** Три метрики швидкості сторінки (Core Web Vitals). LCP — коли з'явився найбільший видимий
  елемент. INP — наскільки швидко сторінка відповідає на клацання й набір тексту. CLS — наскільки «стрибає» макет.

## П'ять пасток, які переживають будь-який рівень

- **Стан іммутабельний.** `items.push(x)` не перемальовує нічого: React порівнює посилання, а воно не змінилося.
  Це не примха бібліотеки, а наслідок того, як працює порівняння, — перший день фази 0 про це.
- **Рендер — не малювання.** Виклик компонента, запис різниці в DOM і пікселі на екрані — три різні події в часі.
  Половина питань «чому воно не оновилося» — це сплутані фази.
- **Ефект — не «зробити після рендеру».** Ефект синхронізує компонент із чимось зовнішнім. Якщо синхронізувати
  нічого, ефект не потрібен — про це є ціла глава, `You Might Not Need an Effect`.
- **Дані беруть до рендеру, а не після.** `useEffect` плюс `fetch` у кожному компоненті — це запити по черзі:
  батько завантажився, відрендерив дитину, дитина пішла по своє. Документація прямо радить вантажити дані в лоадерах
  маршрутів або на сервері (`Build a React app from Scratch`, розділ «Data Fetching»).
- **Клієнт нічого не захищає.** Захищений маршрут, схована кнопка, «секретна» змінна `VITE_*` — усе це видно
  будь-кому, хто відкрив інструменти браузера. Дані закриває бекенд; у фронтенді — лише зручність.

## Екосистема: бібліотеки, які треба знати

React — бібліотека інтерфейсу: маршрутів, кешу даних, форм, тестів і збірки в ньому немає, це беруть поруч. «Є
примірник» означає, що у фабриці для бібліотеки піднято власний сервер документації, і питати треба його. Позначка
«Ф3 Д1» — фаза 3, день 1 цього плану.

**Треба знати** — без цього не обходиться жоден робочий проєкт.

| Бібліотека | Навіщо вона з React | Де в плані |
|------------|---------------------|------------|
| Vite | збірка, сервер розробки з гарячою заміною, проксі до API | Ф0 Д11, Ф1 Д20, Ф5 Д1–2; є примірник `vite` |
| TypeScript | типи пропсів, стану, подій, відповідей сервера | Ф0 Д9–10, Ф1 Д6; є примірник `typescript` |
| React Router (режим даних) | маршрути, лоадери, дії, розділення коду за маршрутами | Ф3 Д1–2, Ф5 Д1; є примірник `react-router` |
| TanStack Query | серверний стан: кеш, повтори, інвалідація, оптимістичні оновлення | Ф3 Д3–5; є примірник `tanstack-query` |
| React Hook Form + zod | великі форми з однією схемою перевірки для фронту й бекенду | Ф3 Д7; є примірники `react-hook-form`, `zod` |
| Vitest + React Testing Library | швидкі тести компонентів за поведінкою (поза корпусом) | Ф3 Д9–10 |
| ESLint з `eslint-plugin-react-hooks` | правила хуків і діагностика компілятора | Ф0 Д11, Ф2 Д4 |
| Tailwind CSS | стилі класами в розмітці; підключається плагіном Vite | Ф0 Д11; план Next.js Ф1 Д10; є примірник `tailwind` |

**Варто знати** — трапляється в більшості проєктів, вчиться за день, коли знадобилося.

| Бібліотека | Навіщо | Де в плані |

# Фаза 0. База, якої React не дає — 12 днів

React — бібліотека поверх мови й браузера. Усе, що тут, документація React вважає відомим і не пояснює; саме на
цих речах, а не на хуках, застрягає більшість новачків. Джерела — MDN і примірник `typescript` цієї фабрики;
корпус React з'являється наприкінці фази, у дні про інструменти.

### День 1. Значення й посилання

- **Навіщо.** React вирішує, чи змінився стан, порівнянням посилань. Без цього дня «чому не оновилося» — лотерея.
- **Що це.** Число чи рядок копіюються значенням. Об'єкт і масив — посиланням: дві змінні можуть вказувати на
  той самий об'єкт, і зміна через одну видна через іншу. `===` для об'єктів порівнює посилання, а не вміст, тож
  два однакові на вигляд об'єкти не рівні. Розгортання `{ ...user }` робить нову обгортку, але лише на один рівень:
  вкладені об'єкти спільні. Глибоку копію дає `structuredClone`. React порівнює стан через `Object.is` — по суті
  той самий `===`.
- **Читати:** MDN — «Object.is()», «Spread syntax», «structuredClone()».
- **Зробити:** 1) функція `addItem(list, item)`, що повертає новий масив і не чіпає вхідний; 2) `console.log`
  порівнянь `===` до й після; 3) змінити `user.address.city`, розгорнувши два рівні; 4) показати, що після
  `{ ...user }` поле `address` спільне з оригіналом.
- **Перевірити себе:** ви передбачили результат п'яти порівнянь `===` до запуску, і всі п'ять збіглися.
- **Пастка:** вважати розгортання глибокою копією. Зміна вкладеного об'єкта в «копії» — це зміна оригіналу.

### День 2. Масиви й об'єкти функційно

- **Навіщо.** Кожне оновлення списку в стані React — перетворення масиву без мутації.
- **Що це.** `map`, `filter`, `reduce`, `find`, `some` повертають нове й не чіпають вхідне. `sort`, `reverse`,
  `splice` і `push` змінюють масив на місці. Для них є немутуючі пари: `toSorted`, `toReversed`, `toSpliced`, `with`.
- **Читати:** MDN — «Array», розділ про копіювальні й мутуючі методи; «Object.freeze()».
- **Зробити:** 1) список із тисячі об'єктів-задач; 2) `Object.freeze` на масиві й кожному елементі; 3) набір
  перетворень: відфільтрувати, відсортувати за датою, перейменувати одне поле, порахувати суму.
- **Перевірити себе:** у суворому режимі модуля жодне перетворення не кинуло `TypeError` — отже, жодне не мутувало
  заморожені дані.
- **Пастка:** `items.sort()` змінює масив і повертає той самий масив. У стані React це тиха помилка: посилання не
  змінилося, екран не оновився.

### День 3. Функції та замикання

- **Навіщо.** **Головний день фази.** Увесь клас помилок «застарілого стану» з хуками — це замикання.
- **Що це.** Функція пам'ятає змінні з того місця, де її створили, а не з того, де її викликали. Обробник, створений
  у першому рендері, бачить значення першого рендеру назавжди. `let` у циклі створює нову змінну на кожен оберт,
  `var` — одну на всіх.
- **Читати:** MDN — «Closures», «let».
- **Зробити:** 1) лічильник на замиканні; 2) кнопка, що через три секунди показує значення змінної, яку ви
  встигли змінити тричі; 3) цикл із `setTimeout` на `var` і на `let`.
- **Перевірити себе:** ви пояснюєте, яке значення покаже кожен `setTimeout` і чому, до того як запустили.
- **Пастка:** думати, що функція читає «поточне» значення змінної. Вона читає ту змінну, яку бачила при створенні,
  — у React це прямо описано в главі `State as a Snapshot`, до якої ви дійдете у фазі 1.

### День 4. Модулі й пакети

- **Навіщо.** Проєкт на React — це сотні модулів і десятки пакетів. Треба розуміти, звідки що береться.
- **Що це.** ESM: `import` і `export`, іменований і типовий експорт. `package.json` описує залежності; `^19.3.0`
  дозволяє будь-яку 19.x не нижче 19.3.0, `~19.3.0` — лише 19.3.x. Файл блокування (`package-lock.json`) фіксує
  точні версії всього дерева; `npm ci` ставить рівно їх. `npx` запускає пакет, не встановлюючи його в проєкт.
- **Читати:** MDN — «JavaScript modules»; документацію npm — «package.json», «npm ci» (поза корпусом).
- **Зробити:** 1) розбити код днів 1–3 на модулі; 2) підключити одну зовнішню бібліотеку; 3) `npm ls` і
  знайти її залежності.
- **Перевірити себе:** ви кажете, яку версію поставить `npm install` для `^19.3.0` і чим `npm ci` відрізняється.
- **Пастка:** не комітити файл блокування. Тоді у вас і на CI стоять різні версії, і «у мене працює» стає правдою
  лише у вас.

### День 5. Асинхронність

- **Навіщо.** Будь-які дані в React приходять асинхронно, і порядок їх приходу — джерело половини гонок.
- **Що це.** Проміс — значення, яке буде. `async`/`await` — синтаксис поверх промісів. `Promise.all` чекає всіх
  паралельно і падає з першою помилкою; `Promise.allSettled` чекає всіх і повертає кожен результат. `await` у циклі
  для незалежних запитів виконує їх по черзі.
- **Читати:** MDN — «Using promises», «async function», «Promise.all()», «Promise.allSettled()».
- **Зробити:** 1) три фейкові запити із затримками 300, 500 і 700 мс; 2) послідовно через `await`;
  3) паралельно через `Promise.all`; 4) час кожного варіанта через `performance.now()`.
- **Перевірити себе:** два числа: близько 1500 мс і близько 700 мс.
- **Пастка:** `await` у циклі для незалежних запитів. Це той самий водоспад, що й `useEffect` плюс `fetch` у
  вкладених компонентах, — до нього план повернеться у фазі 3.

### День 6. Мережа

- **Навіщо.** Пошуковий рядок, що шле запит на кожну літеру, — класична гонка відповідей.
- **Що це.** `fetch` повертає відповідь навіть на 404 і 500: проміс відхиляється лише при мережевій помилці, тож
  статус перевіряють через `res.ok`. Тіло читається один раз (`res.json()`). `AbortController` скасовує запит:
  його сигнал передають у `fetch`, а `abort()` обриває запит, що ще летить.
- **Читати:** MDN — «Using the Fetch API», «Response.ok», «AbortController».
- **Зробити:** 1) поле пошуку, що на кожну літеру питає публічний API; 2) кожна нова літера скасовує попередній
  запит; 3) у вкладці «Мережа» ввімкнути повільну мережу й набрати слово швидко.
- **Перевірити себе:** у вкладці «Мережа» скасовані запити позначені як скасовані, а на екрані завжди результат
  останнього введення, навіть якщо попередня відповідь прийшла пізніше.
- **Пастка:** не перевірити `res.ok` — і показати сторінку помилки сервера як дані.

### День 7. DOM і події

- **Навіщо.** React навішує обробники за вас, але події живуть за правилами браузера.
- **Що це.** DOM — дерево вузлів. Атрибут — те, що в HTML; властивість — те, що в об'єкті вузла (`value` поля
  вводу змінюється, атрибут `value` — ні). Подія спливає від цілі вгору до кореня; делегування — один обробник на
  батькові замість сотні на дітях. `event.target` — де клацнули, `event.currentTarget` — чий обробник працює.
  `preventDefault` скасовує дію браузера (відправлення форми), `stopPropagation` — спливання.
- **Читати:** MDN — «Introduction to events», «Event bubbling», «Event.preventDefault()».
- **Зробити:** список на сто елементів без React з одним обробником на батьківському `<ul>`, що видаляє елемент,
  по якому клацнули.
- **Перевірити себе:** в інструментах розробника на вкладці слухачів подій — один обробник, а не сто.
- **Пастка:** плутати `target` і `currentTarget`: клацнули по іконці всередині кнопки — і `target` уже іконка.

### День 8. Як браузер малює

- **Навіщо.** Метрики INP і CLS, до яких ви дійдете, — про те, скільки браузер рахує й перемальовує.
- **Що це.** Після зміни DOM браузер рахує стилі, компонування (де що стоїть), малювання й композицію шарів.
  Прочитати `offsetHeight` після запису стилю — змусити браузер перерахувати компонування негайно (примусове
  перекомпонування); у циклі це дуже дорого. Анімація `transform` і `opacity` обходиться без компонування.
- **Читати:** MDN — «Populating the page: how browsers work», «Window.requestAnimationFrame()».
- **Зробити:** 1) сторінка, що в циклі на тисячу елементів по черзі читає `offsetHeight` і пише `style.height`;
  2) записати профіль у вкладці «Продуктивність»; 3) переписати: спершу всі читання, потім усі записи;
  4) записати профіль знову.
- **Перевірити себе:** два числа — тривалість задачі до й після, і попередження про примусове перекомпонування
  зникли з профілю.
- **Пастка:** анімувати `top` і `left` замість `transform` — кожен кадр перераховує компонування.

### День 9. TypeScript: основи

- **Навіщо.** У фазі 1 ви типізуватимете пропси, стан і події. Без основ TypeScript кожна помилка типів у React
  виглядатиме як помилка React.
- **Що це.** Тип описує форму значення. `type` і `interface` для об'єктів майже рівноцінні. Об'єднання `A | B` —
  «одне з», звуження (`typeof`, `in`, перевірка поля) — спосіб довести компілятору, яке саме. Розрізнюване
  об'єднання — найкорисніший прийом для React: `{ status: 'loading' } | { status: 'success'; data: T } |
  { status: 'error'; error: string }`. `unknown` — «не знаю, що це, перевір»; `any` — «вимкни перевірку».
- **Читати:** у примірнику `typescript` — `The Basics (handbook-v2/Basics)`,
  `Everyday Types (handbook-v2/Everyday Types)`, `Narrowing (handbook-v2/Narrowing)`.
- **Зробити:** 1) типізувати код днів 1–6 без жодного `any`; 2) відповідь `fetch` прочитати як `unknown` і
  звузити до свого типу; 3) стан запиту описати розрізнюваним об'єднанням.
- **Перевірити себе:** `tsc --noEmit` з `strict: true` без помилок, пошук `any` по коду нічого не знаходить;
  звертання до `data` у гілці `loading` — помилка компіляції.
- **Пастка:** `as MyType`, «щоб зникла помилка». Це не перевірка, а обіцянка компілятору, яку ніхто не
  перевіряє: дані з мережі як були неперевірені, так і лишилися.

### День 10. TypeScript: дженерики

- **Навіщо.** `useState<T>`, `useRef<T>`, хук запиту, що повертає `T`, — усе це дженерики.
- **Що це.** Параметр типу — «тип, який підставлять потім»: `function first<T>(list: T[]): T | undefined`.
  Обмеження `K extends keyof T` дозволяє лише ключі об'єкта. Службові типи `Partial`, `Pick`, `Omit`, `Record`
  будують нові типи зі старих.
- **Читати:** у примірнику `typescript` — `Generics (handbook-v2/Type Manipulation/Generics)`,
  `Keyof Type Operator (handbook-v2/Type Manipulation/Keyof Type Operator)`,
  `Utility Types (reference/Utility Types)`.
- **Зробити:** 1) типізоване сховище `Store<T>` з методами `get`, `set`, `subscribe`; 2) функція
  `pick<T, K extends keyof T>(obj: T, keys: K[])`; 3) тип форми редагування як `Partial<Omit<Task, 'id'>>`.
- **Перевірити себе:** `pick(task, ['titel'])` з помилкою в назві ключа не компілюється.
- **Пастка:** дженерик там, де вистачає одного конкретного типу: код важче читати, а користі немає.

### День 11. Проєкт: Vite, лінт, TypeScript

- **Навіщо.** Звідси починається наскрізний проєкт. Інструменти, налаштовані сьогодні, ловитимуть помилки весь план.
- **Що це.** Vite — збирач і сервер розробки: у розробці віддає модулі браузеру майже як є і підміняє змінений
  модуль без перезавантаження (гаряча заміна), для продакшну збирає бандл. Проєкт створюється шаблоном `react-ts`
  — так радить глава `Build a React app from Scratch`. `eslint-plugin-react-hooks` — офіційні правила React для
  ESLint: правила хуків, повнота залежностей ефектів і діагностика React Compiler навіть без самого компілятора.
  Prettier форматує код; `tsconfig` з `strict: true` вмикає всі суворі перевірки.
- **Читати:** `Build a React app from Scratch` (крок 1 — Vite; крок 2 прогляньте як карту фаз 3 і 5),
  `Editor Setup`, `eslint-plugin-react-hooks`; у примірнику `vite` — `Getting Started`, `Features`. Якщо проєкт
  буде на Tailwind — у примірнику `tailwind` глава `Get started with Tailwind CSS`, розділ «Installing Tailwind
  CSS as a Vite plugin».
- **Зробити:** 1) `npm create vite@latest my-app -- --template react-ts`; 2) `git init` і перший коміт;
  3) переконатися, що лінт має пресет `recommended` з `eslint-plugin-react-hooks`; 4) свідомо викликати хук
  усередині `if` і запустити лінт; 5) змінити текст у компоненті з лічильником, не перезавантажуючи сторінку.
- **Перевірити себе:** лінт падає на правилі `rules-of-hooks`; після правки тексту лічильник зберіг значення —
  гаряча заміна спрацювала.
- **Пастка:** брати старий туторіал на Create React App. Документація відповідає прямо: «Create React App has been
  deprecated» («`Installation` (Learn)», розділ «Should I use Create React App?»).

### День 12. Інструменти браузера

- **Навіщо.** Усі заміри плану робляться тут. Треба вміти читати те, що бачите.
- **Що це.** Вкладка «Мережа»: водоспад запитів, розмір переданого й розпакованого, час до першого байта.
  «Продуктивність»: запис профілю, довгі задачі, уповільнення процесора в чотири рази (так ваш ноутбук
  імітує середній телефон). Карти коду (source maps) показують у налагоджувачі ваш код замість зібраного.
  Lighthouse — лабораторний аудит сторінки.
- **Читати:** у примірнику `vite` — `Why Vite` (чому в розробці модулі вантажаться окремо); документацію Chrome
  DevTools про вкладки «Network» і «Performance» (поза корпусом).
- **Зробити:** 1) відкрити проєкт у `npm run dev`, записати кількість запитів і переданий обсяг; 2) те саме на
  `npm run build && npx vite preview`; 3) поставити точку зупину у своєму компоненті в зібраній версії.
- **Перевірити себе:** дві пари чисел (запити, КБ) для розробки й збірки, і ви пояснюєте, чому в розробці запитів
  у рази більше.
- **Пастка:** міряти швидкість у режимі розробки. Він повільніший навмисно і нічого не каже про продакшн.

**Критерій завершення фази:** ви можете пояснити, чому зміна поля в об'єкті не помічається порівнянням і що
відбувається в браузері між кліком і новим кадром на екрані.

# Фаза 1. Ядро React — 20 днів

Розділ Learn на react.dev у порядку самої документації: вона вибудувана правильно, і скорочувати її — найпоширеніша
помилка самоучок. Глави `Quick Start` і `Tutorial: Tic-Tac-Toe` — для тих, хто бачить React уперше; мідлу їх
можна пропустити. Усе пишеться в проєкті з фази 0, дня 11, на TypeScript із першого дня; день 6 — окремо про типи
в React.

### День 1. Компоненти й модулі

- **Навіщо.** Компонент — одиниця всього в React, а розкладання по файлах — перше рішення в проєкті.
- **Що це.** Компонент — функція з великої літери, що повертає розмітку. Компоненти вкладаються один в одного, як
  теги. Оголошувати компонент **усередині** іншого не можна: на кожному рендері батька це буде новий тип, і React
  знищить стан дитини.
- **Читати:** `Your First Component`, `Importing and Exporting Components`.
- **Зробити:** 1) шапка, список і картка — три файли; 2) зібрати їх на одному екрані; 3) свідомо оголосити
  компонент із полем вводу всередині батька, набрати текст і змусити батька перемалюватися.
- **Перевірити себе:** у кроці 3 введений текст зникає, лінт скаржиться на правило `static-components`, і ви
  пояснюєте чому.
- **Пастка:** компонент із малої літери. React сприйме `<card />` як невідомий HTML-тег.

### День 2. JSX

- **Навіщо.** JSX — не HTML, і його відмінності ламають розмітку в найнесподіваніших місцях.
- **Що це.** JSX компілюється у виклики функцій, що створюють об'єкти-описи елементів. Звідси правила: один
  кореневий елемент (або фрагмент `<>…</>`), закриті теги, `className`, атрибути в camelCase, `style` — об'єкт.
  У фігурних дужках — будь-який вираз JavaScript. Текст у дужках React **екранує сам**: рядок
  `<script>alert(1)</script>` з'явиться на екрані як текст, а не виконається. Це головний захист від XSS
  (впровадження чужого скрипту через дані).
- **Читати:** `Writing Markup with JSX`, `JavaScript in JSX with Curly Braces`.
- **Зробити:** 1) розмітка з обчисленнями, умовами й підстановкою стилів; 2) у вкладці «Мережа» в режимі розробки
  відкрити свій зібраний модуль і знайти, у що перетворився JSX; 3) вставити рядок
  `<img src=x onerror=alert(1)>` у JSX через `{}`.
- **Перевірити себе:** у модулі видно виклики `jsxDEV(…)` на місці ваших тегів; рядок із кроку 3 показаний як
  текст, і жодного `alert`.
- **Пастка:** `dangerouslySetInnerHTML` з даними користувача. Документація попереджає: «If the HTML inside isn't
  trusted (for example, if it's based on user data), you risk introducing an XSS vulnerability»
  (`Common components (e.g. <div>)`, розділ Props). Якщо без нього ніяк — лише після очищення бібліотекою на
  кшталт DOMPurify (поза корпусом). Друга дірка — адреси з даних: `href` з `javascript:` виконує код, тому
  посилання з даних пропускайте, лише якщо вони починаються з `http:` або `https:` (у корпусі — блог React,
  «React v16.9.0 and the Roadmap Update», розділ «Deprecating `javascript:` URLs»).

### День 3. Пропси й умовний рендер

- **Навіщо.** Більшість компонентів — це функція від пропсів, без жодного стану.
- **Що це.** Пропси — аргументи компонента, лише для читання. `children` — те, що вкладено між тегами.
  Умовний рендер — звичайний JavaScript: `if`, тернарний оператор, `&&`. Розрізнюване об'єднання з фази 0 тут
  працює повністю: компонент за полем `status` малює одну з трьох гілок, і TypeScript не пустить у неіснуючу.
- **Читати:** `Passing Props to a Component`, `Conditional Rendering`.
- **Зробити:** картка, що виглядає по-різному для трьох станів даних — завантаження, помилка, дані, — без жодного
  стану всередині; три картки поруч з різними пропсами.
- **Перевірити себе:** спроба прочитати `data` у гілці помилки не компілюється; три картки показують три стани.
- **Пастка:** `{count && <Badge />}` при `count === 0` малює на екрані «0». Умова має бути булевою: `count > 0`.

### День 4. Списки й ключі

- **Навіщо.** Ключі — тема, яку питають на кожній співбесіді, і помилка, що проявляється лише в певних сценаріях.
- **Що це.** Список малюють через `map`. Ключ каже React, який елемент який: після видалення чи перестановки React
  за ключем знаходить, чий стан і чий DOM кому належить. Індекс масиву ключем не годиться, якщо список змінює
  порядок чи склад: ключі «з'їжджають» на сусідні елементи.
- **Читати:** `Rendering Lists`.
- **Зробити:** 1) список рядків, у кожному поле вводу; 2) ключ — індекс; набрати текст у трьох полях і видалити
  другий рядок; 3) ключ — `id`; повторити.
- **Перевірити себе:** з індексом текст після видалення «переїжджає» в чужий рядок, з `id` — ні; ви пояснюєте це
  словами «стан належить позиції з ключем».
- **Пастка:** `key={Math.random()}`. Кожен рендер — нові ключі: React знищує й створює кожен рядок наново, стан і
  фокус губляться.

### День 5. Чистота й дерево

- **Навіщо.** На чистоті компонентів стоїть усе: `<StrictMode>`, конкурентний рендер, компілятор.
- **Що це.** Чистий компонент не змінює під час рендеру нічого, що існувало до нього: не пише в зовнішні змінні,
  не мутує пропси, не ходить у мережу. Зміни — в обробниках подій або, в крайньому разі, в ефектах. `<StrictMode>`
  у розробці викликає компоненти двічі, щоб нечистота стала помітною. Дерево рендеру (хто кого малює) і дерево
  модулів (хто кого імпортує) — різні дерева, і обидва корисно бачити.
- **Читати:** `Keeping Components Pure`, `Understanding Your UI as a Tree`, `<StrictMode>`.
- **Зробити:** 1) компонент, що під час рендеру дописує рядок у зовнішній масив; 2) обгорнути застосунок у
  `<StrictMode>` і подивитися на результат; 3) полагодити.
- **Перевірити себе:** у кроці 2 рядків удвічі більше, ніж компонентів; після кроку 3 — стільки ж, і з
  `<StrictMode>`, і без нього.
- **Пастка:** вимкнути `<StrictMode>`, «бо він усе дублює». Він не створює помилку, а показує ту, що вже є.

### День 6. TypeScript у React

- **Навіщо.** На роботі React пишуть на TypeScript, і питання «як це типізувати» виникає щодня.
- **Що це.** Пропси описують інтерфейсом або типом. `children` — `React.ReactNode`: усе, що можна намалювати.
  Події — `React.ChangeEvent<HTMLInputElement>`, `React.FormEvent<HTMLFormElement>`. Хуки виводять тип із
  початкового значення, тому `useState(null)` назавжди лишиться `null` — потрібне явне `useState<User | null>(null)`.
  `useReducer` найкраще типізується розрізнюваним об'єднанням дій. `useRef<HTMLInputElement>(null)` — посилання на
  DOM. Контекст без розумного типового значення створюють як `createContext<T | null>(null)` плюс хук, що кидає
  помилку, якщо провайдера немає.
- **Читати:** `Using TypeScript` — зокрема розділи «Example Hooks» і «Useful Types».
- **Зробити:** 1) типізувати всі компоненти днів 1–5; 2) обробник поля вводу й відправлення форми з точними
  типами подій; 3) контекст поточного користувача з хуком `useCurrentUser`, що кидає помилку без провайдера.
- **Перевірити себе:** `tsc --noEmit` без помилок, пошук `any` нічого не знаходить; передати неіснуючий проп —
  помилка компіляції.
- **Пастка:** `useState(null)` без типу. Компілятор не дасть записати туди користувача, і рука тягнеться до `any`.

### День 7. Події й стан

- **Навіщо.** Стан — те, що робить інтерфейс живим. І перше місце, де інтуїція з JavaScript підводить.
- **Що це.** Обробник передають, а не викликають: `onClick={handleClick}`. Обробники передають пропсами вниз
  (`onSelect`), щоб дитина повідомляла батькові. `useState` дає значення й функцію `set`; звичайна змінна між
  рендерами не живе. Стан належить конкретному екземпляру компонента: два однакові компоненти мають окремий стан.
- **Читати:** `Responding to Events`, `State: A Component's Memory`.
- **Зробити:** 1) форма з кількома полями на `useState`; 2) дитина повідомляє батькові про вибір через проп
  `onSelect`; 3) два екземпляри тієї самої форми поруч.
- **Перевірити себе:** введене в одну форму не з'являється в іншій.
- **Пастка:** `onClick={handleClick()}` — функція виконується під час рендеру, а не при клацанні.

### День 8. Рендер, коміт і знімок стану

- **Навіщо.** Звідси відповіді на два найчастіші питання співбесіди: «чим рендер відрізняється від коміту» і
  «чому стан у обробнику старий».
- **Що це.** Рендер запускається першим показом або зміною стану. React викликає компонент, порівнює результат із
  попереднім і в коміті записує в DOM лише різницю. Стан у рендері — знімок: `set` не змінює змінну зараз, а
  просить новий рендер з новим значенням. Кілька `set` в одному обробнику React складає в чергу й робить один
  рендер. Функція-оновлювач `setCount(c => c + 1)` отримує результат попереднього оновлення в черзі.
- **Читати:** `Render and Commit`, `State as a Snapshot`, `Queueing a Series of State Updates`.
- **Зробити:** 1) обробник, що викликає `set` і одразу читає стан; 2) три `setCount(count + 1)` поспіль;
  3) три `setCount(c => c + 1)`; 4) `setTimeout` з `alert(count)` після зміни.
- **Перевірити себе:** до клацання ви записали очікування — 1, 3 і старе значення в `alert`, — і всі три збіглися.
- **Пастка:** чекати, що після `set` змінна вже нова. Нове значення буде лише в наступному рендері.

### День 9. Об'єкти й масиви в стані

- **Навіщо.** Це день 1 і день 2 фази 0, застосовані до стану, — і найчастіше джерело «не оновлюється».
- **Що це.** Стан, що є об'єктом чи масивом, не змінюють, а замінюють: нова копія з потрібною зміною. Для
  вкладених об'єктів копіюють кожен рівень на шляху до зміни. Глави показують, як додати, видалити, замінити,
  вставити й відсортувати без мутації, і де допомагає Immer.
- **Читати:** `Updating Objects in State`, `Updating Arrays in State`.
- **Зробити:** 1) редагування `user.address.city` у стані; 2) список задач: додати, видалити, перейменувати,
  вставити в середину, відсортувати; 3) у розробці заморожувати новий стан функцією глибокого `Object.freeze`.
- **Перевірити себе:** жодна операція не кинула `TypeError`, і кожна оновила екран.
- **Пастка:** `[...items].sort()` правильно, `items.sort()` — ні; другий варіант тихо мутує стан і не дає рендеру.

### День 10. Стан як набір станів екрана

- **Навіщо.** Різниця між мідлом і джуном — у тому, як описано стан, а не в тому, скільки хуків знає людина.
- **Що це.** Декларативний інтерфейс описують станами, а не діями: «порожньо», «набирає», «надсилається», «успіх»,
  «помилка». Спершу перелічують візуальні стани, потім — що їх перемикає, потім — мінімальний стан, з якого вони
  виводяться. `Thinking in React` показує той самий підхід на всьому екрані: розбити на компоненти, знайти
  мінімальний стан, вирішити, де він живе.
- **Читати:** `Reacting to Input with State`, `Thinking in React`.
- **Зробити:** 1) для форми з проєкту виписати всі візуальні стани; 2) намалювати їх усі поруч на одному
  службовому екрані, передаючи стан пропсом; 3) звести стан до одного поля `status` з розрізнюваним об'єднанням.
- **Перевірити себе:** службовий екран показує п'ять станів; комбінація «надсилається й помилка» неможлива за
  типом.
- **Пастка:** п'ять булевих `isLoading`, `isError`, `isSuccess`… — дають 32 комбінації, з яких можливі п'ять.

### День 11. Структура стану

- **Навіщо.** Зайвий стан — джерело розсинхронізацій, які шукають днями.
- **Що це.** Правила: не дублювати (те, що можна обчислити з наявного, не зберігають), не суперечити (два поля,
  що мусять змінюватися разом, — одне поле), не вкладати глибоко (плоска структура з ідентифікаторами).
  Обраний елемент зберігають як `selectedId`, а не копією об'єкта.
- **Читати:** `Choosing the State Structure`.
- **Зробити:** 1) знайти в проєкті стан, що обчислюється з іншого, і прибрати його; 2) обраний елемент
  перевести на `selectedId`; 3) перейменувати обраний елемент у списку.
- **Перевірити себе:** кількість `useState` у проєкті зменшилася (запишіть два числа); після перейменування в
  списку панель обраного показує нову назву без додаткового коду.
- **Пастка:** `useState(props.value)` — стан ініціалізується один раз, і зміна пропса його вже не оновить.

### День 12. Спільний стан і скидання стану

- **Навіщо.** Два компоненти мусять бачити те саме, а форма мусить очищатися при зміні сутності.
- **Що це.** Спільний стан піднімають до найближчого спільного батька й передають униз пропсами. Стан у React живе
  не в компоненті, а в позиції в дереві: той самий компонент на тому самому місці зберігає стан, навіть якщо
  пропси інші. Інший `key` на тій самій позиції — інший екземпляр із чистим станом.
- **Читати:** `Sharing State Between Components`, `Preserving and Resetting State`.
- **Зробити:** 1) два синхронізовані компоненти через спільного батька; 2) форма редагування сутності, де перехід
  на іншу сутність має скидати введене, — через `key={entity.id}`, без ефекту.
- **Перевірити себе:** перемикання між сутностями очищає форму; у коді форми немає `useEffect`.
- **Пастка:** скидати форму ефектом `useEffect(() => setText(''), [id])`. Один кадр показує старий текст, і
  рендерів удвічі більше.

### День 13. Редюсер

- **Навіщо.** Коли один обробник міняє п'ять полів стану, логіку краще зібрати в одному місці.
- **Що це.** Редюсер — чиста функція `(стан, дія) → новий стан`. Компонент лише надсилає дії (`dispatch`), а що з
  ними робити, вирішує редюсер. Його можна тестувати без React, просто викликом.
- **Читати:** `Extracting State Logic into a Reducer`.
- **Зробити:** 1) перевести складну форму з кількох `useState` на `useReducer` з типізованим об'єднанням дій;
  2) три перевірки редюсера звичайним викликом функції з `console.assert`.
- **Перевірити себе:** перевірки проходять без рендеру будь-якого компонента; неіснуючий тип дії не компілюється.
- **Пастка:** запит у мережу чи `Date.now()` усередині редюсера. Він має бути чистим, як компонент.

### День 14. Контекст

- **Навіщо.** Тема, поточний користувач, мова — значення, які потрібні глибоко в дереві.
- **Що це.** Контекст передає значення всім нащадкам провайдера без пропсів на кожному рівні. Будь-яка зміна
  значення контексту перемальовує всіх, хто його читає, — вибіркової підписки немає. Тому контекст — механізм
  передачі, а не менеджер стану. Редюсер плюс контекст — спосіб дати глибоким компонентам і стан, і `dispatch`.
- **Читати:** `Passing Data Deeply with Context`, `Scaling Up with Reducer and Context`.
- **Зробити:** 1) тема через контекст; 2) у `React Developer Tools` увімкнути підсвічування перемальовувань;
  3) перемкнути тему і подивитися, що підсвітилося.
- **Перевірити себе:** ви називаєте кожен підсвічений компонент і причину його рендеру.
- **Пастка:** один великий контекст «для всього». Зміна будь-якого поля перемальовує всіх споживачів.

### День 15. Ref

- **Навіщо.** Фокус, прокручування, ідентифікатор таймера — те, що не має перемальовувати екран.
- **Що це.** `useRef` дає об'єкт `{ current }`, що живе між рендерами; зміна `current` рендер не викликає. Ref на
  DOM-вузол дає доступ до `focus()`, `scrollIntoView()`. У React 19 `ref` — звичайний проп, і для передачі ref
  дочірньому компоненту `forwardRef` більше не потрібен.
- **Читати:** `Referencing Values with Refs`, `Manipulating the DOM with Refs`.
- **Зробити:** 1) фокус на полі після відкриття форми; 2) прокручування до нового елемента списку; 3) секундомір
  з ідентифікатором інтервалу в ref; 4) лічильник кліків у ref поруч із лічильником у стані.
- **Перевірити себе:** лічильник у ref збільшується (видно в `console.log`), але екран не оновлюється, доки не
  зміниться стан.
- **Пастка:** читати чи писати `ref.current` під час рендеру. Лінт (правило `refs`) про це скаже.

### День 16. Синхронізація ефектами

- **Навіщо.** Ефект — найпотужніший і найнебезпечніший інструмент React.
- **Що це.** Ефект запускається після коміту й синхронізує компонент із зовнішньою системою: підключитися,
  підписатися, запустити віджет. Функція прибирання відключає те, що підключив ефект. У розробці `<StrictMode>`
  монтує компонент двічі — підключити, відключити, підключити, — щоб перевірити, що прибирання є. Запит у мережу в
  ефекті потребує прибирання (прапорець `ignore` або `AbortController`), інакше старі відповіді перетирають нові.
- **Читати:** `Synchronizing with Effects`.
- **Зробити:** 1) ефект, що «підключається» до кімнати чату (лог `connect`/`disconnect`); 2) прибирання;
  3) запит у мережу з `AbortController` і прибиранням; 4) порівняти лог у розробці й у `vite preview`.
- **Перевірити себе:** у розробці в лозі `connect, disconnect, connect`, у збірці — один `connect`; швидке
  перемикання кімнат не показує чужих даних.
- **Пастка:** вимкнути `<StrictMode>`, щоб ефект не спрацьовував двічі. Подвійний запуск показує відсутнє
  прибирання, а не створює проблему.

### День 17. Коли ефект не потрібен

- **Навіщо.** **Головний день фази.** Зайві ефекти — найдорожча звичка в React-коді: зайві рендери, мерехтіння,
  ланцюги оновлень.
- **Що це.** Ефект не потрібен, щоб перетворити дані для рендеру (обчисліть під час рендеру), щоб відреагувати на
  дію користувача (це робота обробника), щоб скинути стан при зміні пропса (`key`), щоб обчислити одне поле стану
  з іншого (не зберігайте похідне). Ефект потрібен лише для синхронізації із зовнішньою системою.
- **Читати:** `You Might Not Need an Effect`.
- **Зробити:** 1) порахувати `useEffect` у проєкті; 2) прибрати щонайменше три: похідне значення — в обчислення,
  реакцію на клік — в обробник, скидання — в `key`; 3) запустити лінт.
- **Перевірити себе:** два числа ефектів до й після; поведінка не змінилася; лінт без попереджень
  `set-state-in-effect`.
- **Пастка:** ланцюг ефектів, де кожен ставить стан, на який реагує наступний. Кожна ланка — зайвий рендер.

### День 18. Життєвий цикл ефекту й події поза ним

- **Навіщо.** «Ефект перепідключається, коли не треба» — типова скарга. Причина — неправильна модель у голові.
- **Що це.** У ефекту немає «монтування» й «розмонтування», є лише «почати синхронізацію» і «зупинити». Він
  перезапускається, коли змінилося реактивне значення, яке він читає (пропс, стан, усе обчислене з них). Логіку,
  яка має читати свіже значення, але не перезапускати ефект (наприклад, тему сповіщення), виносять у функцію
  `useEffectEvent`.
- **Читати:** `Lifecycle of Reactive Effects`, `Separating Events from Effects`; довідка `useEffectEvent`.
- **Зробити:** 1) вибір кімнати чату й перемикач теми сповіщень; 2) ефект підключення читає і кімнату, і тему;
  3) винести показ сповіщення з темою в `useEffectEvent`.
- **Перевірити себе:** у лозі зміна кімнати дає перепідключення, зміна теми — ні.
- **Пастка:** думати категоріями «при монтуванні». Ефект синхронізується з тим, що читає, а не з часом життя
  компонента.

### День 19. Залежності ефекту й власні хуки

- **Навіщо.** Залежності, які «прибирають» коментарем для лінта, — бомба уповільненої дії.
- **Що це.** Залежності не обирають, а описують: це все реактивне, що ефект читає. Щоб залежність зникла, треба
  змінити код — перенести об'єкт чи функцію всередину ефекту, прочитати значення через оновлювач стану, винести
  нереактивне в `useEffectEvent`. Власний хук — функція з префіксом `use`, що ділиться **логікою**, а не станом:
  кожен виклик має свій стан.
- **Читати:** `Removing Effect Dependencies`, `Reusing Logic with Custom Hooks`.
- **Зробити:** 1) знайти ефект з об'єктом чи функцією в залежностях і прибрати їх, змінивши код; 2) винести
  повторювану логіку у власні хуки `useOnlineStatus` і `useDebouncedValue` з типами.
- **Перевірити себе:** пошук `eslint-disable` по проєкту нічого не знаходить; два компоненти з тим самим хуком
  мають незалежні значення.
- **Пастка:** вимкнути правило `exhaustive-deps` для рядка. Ефект почне читати застарілі значення — день 3 фази 0
  в дії.

### День 20. Збірка, перший викот і журнал вимірів

- **Навіщо.** Застосунок, якого немає в інтернеті, не існує ні для роботодавця, ні для замірів. Перший викот —
  справа тридцяти хвилин, і робиться він рано, а не «коли буде готово».
- **Що це.** `vite build` складає теку `dist`: `index.html` і файли в `assets/` з хешем вмісту в імені. Статичний
  хостинг просто роздає цю теку — сервер не потрібен. Звіт `vite build` друкує розмір кожного файла й розмір після
  gzip — це і є число «JS-бандл» для журналу. `vite preview` запускає зібране локально.
- **Читати:** у примірнику `vite` — `Building for Production`, `static-deploy` (розділи про Netlify, Vercel чи
  Cloudflare — оберіть один хостинг з безкоштовним планом).
- **Зробити:** 1) `npm run build` і подивитися на `dist`; 2) `npx vite preview`; 3) викотити `dist` на обраний
  хостинг; 4) Lighthouse в режимі mobile на викоченій адресі, три прогони; 5) завести в README журнал вимірів:
  дата, «перший викот», LCP і CLS (медіана), INP — прочерк (його перший замір у фазі 2, день 5), КБ gzip
  головного JS-файла зі звіту збірки.
- **Перевірити себе:** адреса відкривається з телефона; у журналі перший рядок із числами.
- **Пастка:** вважати, що все в збірці приватне. Усе з `dist` — і кожна змінна `VITE_*` у ньому — публічне;
  секретів у фронтенд-збірці не буває. До цього план повернеться у фазі 5, день 2.

**Критерій завершення фази:** ви можете сказати, чому компонент перемалювався, не вгадуючи, а дивлячись на код;
застосунок живе в інтернеті, і в журналі вимірів є перший рядок.

# Фаза 2. Як React працює зсередини — 8 днів

Фаза, після якої зникає слово «магія». Головне правило: жодна оптимізація без заміру до неї. Міряйте на
продакшн-збірці або на спеціальній збірці для профілювання, з уповільненням процесора в чотири рази, — режим
розробки повільніший навмисно, а `<StrictMode>` у ньому рендерить усе двічі. Кожен замір іде в журнал вимірів.

### День 1. Профайлер

- **Навіщо.** «Повільно» — не діагноз. Профайлер називає компонент і мілісекунди.
- **Що це.** `React Developer Tools` записує профіль: кожен коміт, які компоненти рендерились і скільки часу.
  `<Profiler>` робить те саме з коду: колбек `onRender` отримує `actualDuration` — скільки зайняв рендер піддерева.
  У продакшн-збірці профілювання вимкнене; для замірів є окрема збірка для профілювання — `react-dom/profiling`
  замість `react-dom/client`, підставлена псевдонімом у збирачі.
- **Читати:** `React Developer Tools`, `<Profiler>`, `React Performance tracks` (розділ «Using profiling builds»).
- **Зробити:** 1) окремий режим збірки (`vite build --mode profile`), де `resolve.alias` підміняє
  `react-dom/client` на `react-dom/profiling`; 2) `<Profiler>` навколо головного екрана з виводом `actualDuration`;
  3) записати профіль однієї дії з уповільненням процесора 4×.
- **Перевірити себе:** у журналі рядок: найдорожчий компонент, його `actualDuration` у мс, кількість комітів на
  одну дію.
- **Пастка:** профілювати в режимі розробки. Числа будуть у кілька разів більші й покажуть не те.

### День 2. Узгодження дерева

- **Навіщо.** «Чому стан дитини зник» і «чому не зник, хоча мав» — це узгодження.
- **Що це.** Після рендеру React порівнює нове дерево зі старим. Той самий тип на тій самій позиції — React
  оновлює наявний екземпляр і зберігає стан. Інший тип — знищує все піддерево разом зі станом і будує наново.
  У списках позицію замінює ключ. Звідси й правило дня 1 фази 1: компонент, оголошений усередині іншого, — щоразу
  новий тип.
- **Читати:** `Preserving and Resetting State` (знову, під кутом алгоритму); `Reconciliation` — легасі-документація
  до React 18 включно, у новій документації окремої глави немає, але правила типу й ключа ті самі.
- **Зробити:** 1) обгортку дочірнього компонента з полем вводу умовно міняти між `<div>` і `<section>`;
  2) `isEditing ? <Form /> : <Form />` з різними пропсами; 3) той самий випадок, але з різними `key`;
  4) записати передбачення до кожного кроку.
- **Перевірити себе:** для чотирьох змін дерева ваші передбачення «стан виживе / не виживе» збіглися з поведінкою.
- **Пастка:** очікувати, що дві гілки тернарного оператора з тим самим компонентом — різні екземпляри. Для React
  це та сама позиція й той самий тип.

### День 3. Пакетування оновлень

- **Навіщо.** Кількість рендерів — перше, що питають про продуктивність.
- **Що це.** Усі `set` в одному обробнику React складає в один рендер. З React 18 те саме відбувається й у
  `setTimeout`, промісах і нативних подіях — автоматичне пакетування. `flushSync` змушує React застосувати
  оновлення негайно, наприклад щоб прокрутити до щойно доданого елемента, — і платить за це зайвим комітом.
- **Читати:** `Queueing a Series of State Updates` (розділ «React batches state updates»), `flushSync`.
- **Зробити:** 1) три `set` у обробнику кліку, у `setTimeout` і після `await`; 2) порахувати коміти через
  `onRender` у `<Profiler>`; 3) прокручування до нового елемента списку з `flushSync` і без.
- **Перевірити себе:** таблиця в журналі: три випадки — по одному коміту; з `flushSync` — два, а без нього
  прокручування не доходить до нового елемента.
- **Пастка:** `flushSync` усюди, «щоб стан оновився одразу». Він ламає пакетування і робить застосунок повільнішим.

### День 4. Мемоізація і React Compiler — один замір

- **Навіщо.** «Коли `useMemo` справді допомагає» — питання співбесіди, на яке відповідають числами.
- **Що це.** `memo` пропускає рендер компонента, якщо пропси не змінилися. `useMemo` запам'ятовує результат
  обчислення, `useCallback` — саму функцію, щоб посилання не змінювалося. Документація радить міряти:
  `console.time` навколо обчислення; якщо набігає близько 1 мс чи більше, мемоізація має сенс (`useMemo`, розділ
  «How to tell if a calculation is expensive?»). React Compiler мемоізує автоматично на збірці, і він уже не
  експеримент: «React Compiler is now stable and has been tested extensively in production» («`Introduction`
  (React Compiler)», розділ «Is it safe to use?»). У новому коді документація радить покладатися на компілятор, а
  `useMemo` і `useCallback` лишати там, де потрібен точний контроль. Наявну ручну мемоізацію не прибирати: «removing
  it can change compilation output». Компілятор працює лише з кодом, що дотримується `Rules of React`; де правила
  порушено, він компонент пропускає, а `eslint-plugin-react-hooks` показує де.
- **Читати:** `memo`, `useMemo`, `useCallback`, «`Introduction` (React Compiler)», «`Installation` (React
  Compiler)» (розділи «Basic Setup › Vite» і «Check React DevTools»), `Rules of React`, `eslint-plugin-react-hooks`.
- **Зробити:** один і той самий екран — список на дві тисячі елементів із фільтром і лічильником в іншому кутку —
  у трьох гілках: 1) без мемоізації; 2) з ручними `memo`, `useMemo`, `useCallback`; 3) без ручної мемоізації, з
  увімкненим компілятором. Для кожної на збірці для профілювання: скільки елементів списку рендериться на клік
  лічильника, тривалість коміту, `console.time` фільтра.
- **Перевірити себе:** три рядки в журналі; у гілці 3 компоненти мають у `React Developer Tools` позначку
  «Memo ✨»; ви можете назвати місце, де мемоізація не дала нічого, і чому.
- **Пастка:** `memo` на компоненті, якому передають новий об'єкт чи функцію в кожному рендері, — порівняння
  завжди «змінилося», і `memo` лише додає роботи. Друга пастка — масово видаляти `useMemo`, увімкнувши компілятор.

### День 5. `useTransition` і перший замір INP

- **Навіщо.** Поле фільтра, що «замерзає» на кожній літері, — найпомітніше гальмо для користувача, і саме його
  міряє INP.
- **Що це.** Оновлення бувають термінові (введення в поле) і нетермінові (перемалювати важкий список). Обгорнуте
  в `startTransition` оновлення React рендерить у фоні й може перервати заради нового введення. `isPending`
  каже, що перехід ще триває.
- **Читати:** `useTransition` — зокрема розділ «Troubleshooting › Updating an input in a Transition doesn't work»;
  `startTransition`.
- **Зробити:** 1) штучно повільний список (кожен рядок рахує щось 1 мс) із фільтром; 2) уповільнення
  процесора 4×, набрати слово; 3) INP взаємодії — у вкладці «Продуктивність» (живі метрики) або через `onINP` з
  бібліотеки web-vitals (поза корпусом); 4) оновлення списку — в перехід, поле лишається терміновим; 5) заміряти
  знову.
- **Перевірити себе:** два числа INP у журналі, до й після; поле вводу відгукується одразу. Пороги «добре» й
  «погано» для INP публікує web.dev (поза корпусом).
- **Пастка:** загорнути в перехід стан самого поля вводу. Контрольоване поле перестає встигати за набором.

### День 6. `useDeferredValue`

- **Навіщо.** Той самий результат, коли сеттера у вас немає: значення прийшло пропсом.
- **Що це.** `useDeferredValue(value)` повертає «відстаючу» копію значення: спершу React рендерить зі старою,
  потім у фоні — з новою. Працює, лише якщо повільна частина вміє пропускати рендер з тими самими пропсами:
  документація загортає її в `memo` (з компілятором це відбувається само). Різниця між `value` і відкладеним
  значенням — ознака «дані застаріли», її показують напівпрозорістю.
- **Читати:** `useDeferredValue` (розділ «Deferring re-rendering for a part of the UI»).
- **Зробити:** той самий список із дня 5 через `useDeferredValue`; напівпрозорість, доки значення відстає; INP.
- **Перевірити себе:** третє число INP у журналі; ви кажете, коли брати перехід (ви володієте сеттером), а коли
  відкладене значення (значення приходить ззовні).
- **Пастка:** відкласти значення, але не мемоізувати повільний компонент. Він усе одно рендериться з кожною
  літерою, і виграшу немає.

### День 7. Віртуалізація довгих списків

- **Навіщо.** Десять тисяч рядків у DOM гальмують будь-який браузер, хоч скільки мемоізуйте.
- **Що це.** Віртуалізація малює лише видимі рядки плюс невеликий запас, а решту заміщує порожнім місцем
  потрібної висоти. Кількість DOM-вузлів перестає залежати від довжини списку.
- **Читати:** `Optimizing Performance`, розділ «Virtualize Long Lists» — легасі-документація React 16–18, у новій
  документації його немає; документацію react-window або TanStack Virtual (поза корпусом).
- **Зробити:** 1) список на 10 000 рядків; 2) кількість вузлів: `document.querySelectorAll('*').length`; 3) INP
  набору у фільтр (як у дні 5); 4) віртуалізувати; 5) заміряти обидва числа знову.
- **Перевірити себе:** дві пари чисел у журналі — вузли й INP до й після.
- **Пастка:** віртуалізувати список на п'ятдесят рядків. Складність є, виграшу немає, а пошук `Ctrl+F` браузера
  перестає знаходити невидимі рядки.

### День 8. `<Suspense>` і межі помилок

- **Навіщо.** Що бачить користувач, поки код чи дані вантажаться, і коли щось упало, — частина інтерфейсу, а не
  випадковість.
- **Що це.** `<Suspense>` показує заглушку, доки щось усередині «чекає»: лінивий компонент (`lazy`) або дані з
  бібліотеки, що вміє чекати разом із Suspense. Межа помилок ловить помилки **рендеру** нащадків і показує запасний
  екран. Пишеться вона досі класом (`static getDerivedStateFromError`, `componentDidCatch`) — це єдине місце плану,
  де потрібен клас. Помилок в обробниках подій і в асинхронному коді межа не ловить. Опції `createRoot` —
  `onCaughtError` і `onUncaughtError` — точка, куди підключають збирач помилок (сам збір, Sentry, — у плані
  Next.js, фаза 7, день 9).
- **Читати:** `<Suspense>`, `lazy`, `Component` (розділ «Catching rendering errors with an Error Boundary»),
  `createRoot` (розділ «Error logging in production»).
- **Зробити:** 1) важкий компонент через `lazy` під `<Suspense>`; 2) межа помилок навколо; 3) кинути помилку в
  рендері; 4) кинути помилку в `onClick`; 5) у `createRoot` передати `onCaughtError`, що пише помилку й
  `componentStack` у консоль.
- **Перевірити себе:** крок 3 показує запасний екран, крок 4 — ні; у консолі є стек компонентів із кроку 3.
- **Пастка:** вважати, що межа помилок ловить усе. Помилку в обробнику ловлять `try/catch` у самому обробнику.

**Критерій завершення фази:** на питання «чому повільно» ви відповідаєте назвою компонента й числом з профайлера,
а не здогадом; у журналі є INP.

# Фаза 3. Екосистема — 12 днів

React не має нічого з цього в коробці. Документація сама каже, що брати: глава `Build a React app from Scratch`,
крок 2 — маршрути, дані, розділення коду. Про дані там пряма порада: «fetching data directly in components can
lead to slower loading times due to network request waterfalls, so we recommend prefetching data in router loaders
or on the server as much as possible!» (розділ «Data Fetching»). Тому план вчить лоадери React Router у режимі
даних і кеш TanStack Query поверх них. Для кожної бібліотеки фази у фабриці є примірник — назви глав нижче з нього.

### День 1. Маршрути

- **Навіщо.** Три екрани без маршрутизатора — це вже незручно; тридцять — неможливо.
- **Що це.** React Router має три режими: декларативний (лише маршрути), даних (маршрути плюс лоадери й дії) і
  фреймворку (повний фреймворк зі збіркою). План бере **режим даних**: `createBrowserRouter` з деревом маршрутів,
  вкладені маршрути зі спільним каркасом через `<Outlet>`, індексний маршрут, параметри шляху, сторінка 404.
  Захищений маршрут — лоадер, що перенаправляє на вхід, якщо сесії немає.
- **Читати:** у примірнику `react-router` — `Picking a Mode`; у розділі Data Mode — `Installation`, `Routing`,
  `Navigating`. Питайте з версією з вашого `package.json`: примірник тримає лінії 7 і 8.
- **Зробити:** 1) три екрани зі спільним каркасом і сторінкою 404; 2) сторінка сутності за `:id`; 3) приватна
  зона з фейковим входом; 4) викотити й оновити сторінку на адресі `/items/2`.
- **Перевірити себе:** у `vite preview` оновлення на `/items/2` працює; на хостингу з фази 1 — спершу 404. Полагодити
  правилом «усі адреси віддають `index.html`» (`Single Page App (SPA)`, крок «Direct all URLs to index.html»;
  синтаксис правила — у документації хостингу, поза корпусом). Після цього глибоке посилання відкривається.
- **Пастка:** вважати захищений маршрут захистом. Він лише ховає екран; дані без входу не має віддавати бекенд.

### День 2. Лоадери й дії маршруту

- **Навіщо.** Дані до рендеру замість водоспаду після рендеру.
- **Що це.** Лоадер — функція маршруту, яку маршрутизатор викликає **до** рендеру сторінки; лоадери вкладених
  маршрутів запускаються паралельно. Компонент читає результат через `useLoaderData`. Дія (`action`) обробляє
  відправлення `<Form>` маршрутизатора й після неї лоадери перезапускаються самі. `useNavigation` каже, що
  перехід триває.
- **Читати:** у розділі Data Mode примірника `react-router` — `Data Loading`, `Actions`, `Pending UI`.
- **Зробити:** 1) батьківський і дочірній екрани, кожен вантажить своє в `useEffect` (затримка API — 500 мс);
  2) у вкладці «Мережа» з уповільненою мережею — водоспад; 3) переписати на лоадери; 4) час до появи вмісту — до
  й після.
- **Перевірити себе:** два числа в журналі; на водоспаді у «Мережі» запити тепер ідуть паралельно.
- **Пастка:** лоадер є, а компонент ще й сам вантажить те саме в ефекті — подвійний запит.

### День 3. Серверний стан: TanStack Query

- **Навіщо.** `useEffect` плюс `fetch` — це гонки відповідей, подвійні запити, відсутність кешу й повторів. Усе
  це вже написано в бібліотеці.
- **Що це.** TanStack Query тримає кеш серверних даних за ключем запиту. `useQuery({ queryKey, queryFn })` дає
  дані, стан завантаження й помилки. `staleTime` — скільки дані вважаються свіжими (свіжі не перезапитуються);
  `gcTime` — скільки невикористані дані лежать у пам'яті. За замовчуванням дані застарівають одразу й
  перезапитуються при поверненні на вкладку — це описано в `Important Defaults`.
- **Читати:** у примірнику `tanstack-query` (фреймворк React) — `Overview`, `Quick Start`, `Queries`,
  `Query Keys`, `Important Defaults`, `Devtools`.
- **Зробити:** 1) перевести всі завантаження поза лоадерами на `useQuery`; 2) підключити Devtools; 3) поставити
  `staleTime` 30 с для списку; 4) піти з екрана й повернутися.
- **Перевірити себе:** у «Мережі» повернення в межах 30 с — нуль запитів, після — один, а екран показує дані
  одразу.
- **Пастка:** копіювати `data` з `useQuery` у `useState`. Копія перестає оновлюватися разом із кешем.

### День 4. Лоадер плюс кеш

- **Навіщо.** Лоадер дає «до рендеру», TanStack Query — кеш і повтори. Разом — найкраще з обох.
- **Що це.** Лоадер не вантажить сам, а просить кеш: `queryClient.ensureQueryData(...)` — повернути з кешу або
  завантажити. Компонент читає ті самі дані через `useQuery` з тим самим ключем. Після зміни даних
  `invalidateQueries` позначає записи застарілими, і активні запити оновлюються.
- **Читати:** у примірнику `tanstack-query` — `Prefetching & Router Integration`, `Query Invalidation` і
  `Example: react/react-router`. Це приклад із репозиторію TanStack Query, а не документація React Router: звідти
  беріть зв'язку «лоадер — `ensureQueryData` — `useQuery`».
- **Зробити:** 1) спільні функції опису запиту (ключ і `queryFn`) для лоадера й компонента; 2) два екрани, що
  показують ті самі дані; 3) кнопка, що викликає `invalidateQueries`.
- **Перевірити себе:** перший візит — один запит, повторний у межах `staleTime` — нуль, після інвалідації — один.
- **Пастка:** різні ключі в лоадері й у компоненті. Виходить два записи кешу й подвійний запит.

### День 5. Мутації й оптимістичні оновлення

- **Навіщо.** Лайк, що з'являється через секунду, здається поламаним.
- **Що це.** `useMutation` надсилає зміну й дає стан відправлення. Після успіху — `invalidateQueries`, щоб список
  оновився. Оптимістичне оновлення малює результат одразу й відкочує його при помилці. У самому React є хук
  `useOptimistic` для того самого в межах одного компонента.
- **Читати:** у примірнику `tanstack-query` — `Mutations`, `Optimistic Updates`; `useOptimistic`.
- **Зробити:** 1) лайк через `useMutation` з оптимістичним оновленням кешу; 2) фейковий API, що падає кожен
  третій раз; 3) повідомлення про помилку й відкат.
- **Перевірити себе:** третій клік — лайк з'явився й зник із повідомленням; після успіху список збігається з
  сервером.
- **Пастка:** оптимістичне оновлення без відкату й без інвалідації в `onSettled` — екран розходиться з сервером.

### День 6. Форми в React 19

- **Навіщо.** Проста форма в React 19 обходиться без жодного `useState`.
- **Що це.** Контрольоване поле — значення в стані React; неконтрольоване — значення в DOM, читається при
  відправленні. `<form action={fn}>` у React 19 приймає функцію, що отримує `FormData`. `useActionState` тримає
  результат останньої відправки (наприклад, текст помилки) і стан `isPending`. `useFormStatus` дає стан
  відправлення батьківської форми — для кнопки «Зберегти», винесеної в окремий компонент.
- **Читати:** `<form>`, `<input>`, `useActionState`, `useFormStatus`.
- **Зробити:** форма входу: `<form action>`, помилка через `useActionState`, кнопка в окремому компоненті з
  `useFormStatus`, що блокується під час відправлення.
- **Перевірити себе:** у компоненті форми нуль `useState`; подвійне клацання не надсилає форму двічі.
- **Пастка:** викликати `useFormStatus` у тому ж компоненті, що малює `<form>`. Він бачить лише батьківську форму,
  і `pending` ніколи не стане `true` — це прямо сказано в довідці.

### День 7. React Hook Form і zod

- **Навіщо.** Форма на десять полів із перевіркою під час набору — щоденна робота, і схема перевірки має бути
  одна для фронту й бекенду.
- **Що це.** zod описує схему даних і виводить з неї тип (`z.infer`). React Hook Form тримає поля
  неконтрольованими й не перемальовує всю форму на кожну літеру; схема підключається резолвером. Помилку з сервера
  для конкретного поля ставить `setError`. Схему кладуть в окремий модуль: у плані NestJS, у фазі про робочий API,
  та сама схема стане валідацією бекенду — NestJS 12 приймає схеми zod через Standard Schema.
- **Читати:** у примірнику `react-hook-form` — `Get Started (content/get-started)` (розділ «Schema Validation»),
  `useForm (content/docs/useform)`, `setError (content/docs/useform/seterror)`; у примірнику `zod` — `Basic usage`,
  `Defining schemas`.
- **Зробити:** 1) схема сутності на десять полів в окремому модулі; 2) форма на React Hook Form із резолвером;
  3) тип форми лише з `z.infer`; 4) імітувати відповідь сервера «ця назва вже зайнята» і показати її біля поля
  через `setError`.
- **Перевірити себе:** зміна правила в схемі змінює і тип, і перевірку; профайлер показує, що набір в одному полі
  не рендерить усю форму.
- **Пастка:** дві схеми — для клієнта й для сервера. Вони розійдуться за тиждень.

### День 8. Глобальний стан

- **Навіщо.** «Беремо Redux» — часто рішення, прийняте до того, як з'ясували, що глобального в застосунку майже
  нічого.
- **Що це.** Стан буває серверний (кеш TanStack Query), в адресі (фільтри, сторінка — `searchParams`), формовий
  (React Hook Form), локальний (`useState`) і справді глобальний клієнтський (тема, налаштування інтерфейсу,
  кошик). Лише останній потребує сховища. Zustand — маленьке сховище з селекторами: компонент перемальовується,
  лише коли змінилося те, що він вибрав. Redux Toolkit — те саме з суворішою структурою, частий у великих
  командах. Обидва під капотом спираються на `useSyncExternalStore`.
- **Читати:** у примірнику `zustand` — `Introduction`, `Comparison`; у примірнику `redux` —
  `Why Redux Toolkit is How To Use Redux Today`; `useSyncExternalStore`.
- **Зробити:** 1) таблиця в README: увесь стан проєкту за п'ятьма категоріями; 2) лише справді глобальне — у
  Zustand із селекторами; 3) профайлер: змінити тему.
- **Перевірити себе:** у таблиці по кожній категорії число; профайлер показує рендер лише підписаних компонентів.
- **Пастка:** класти серверні дані в Zustand чи Redux. Виходить другий кеш, який доводиться синхронізувати руками.

### День 9. Тести компонентів

- **Навіщо.** Портфоліо без тестів на співбесіді коштує вдвічі менше, а рефакторинг без них — лотерея.
- **Що це.** Vitest запускає тести (той самий конфіг, що й Vite). React Testing Library рендерить компонент і
  шукає елементи так, як їх бачить користувач: за роллю й доступною назвою — `getByRole('button', { name:
  'Зберегти' })`. Тест перевіряє поведінку (що на екрані після дії), а не реалізацію (стан, внутрішні функції).
  Пошук за ролями заодно перевіряє доступність. `act` — обгортка, що дає React завершити оновлення до перевірок;
  бібліотека викликає його сама.
- **Читати:** `act`; документацію Vitest і React Testing Library, зокрема «Which query should I use?» (поза
  корпусом).
- **Зробити:** 1) налаштувати Vitest з jsdom; 2) тест форми: заповнити, надіслати, побачити помилку валідації;
  3) перейменувати CSS-клас кнопки; 4) змінити текст кнопки.
- **Перевірити себе:** після кроку 3 тест зелений, після кроку 4 — червоний: текст кнопки — контракт із
  користувачем, клас — ні.
- **Пастка:** `getByTestId` усюди. Тест проходить, навіть коли кнопка недоступна з клавіатури чи без назви.

### День 10. Тести з мережею

- **Навіщо.** Більшість екранів вантажить дані; тест має пройти завантаження, помилку й успіх.
- **Що це.** MSW перехоплює запити на рівні мережі й віддає підготовлені відповіді — код застосунку не знає, що
  його тестують. Асинхронні перевірки — через `findBy…`, що чекає появи. Для TanStack Query кожен тест отримує
  свій `QueryClient` з вимкненими повторами. Маршрути з лоадерами тестують через тестовий маршрутизатор.
- **Читати:** у примірнику `tanstack-query` — `Testing` (фреймворк React); у примірнику `react-router` — `Testing`
  (розділ Data Mode); документацію MSW (поза корпусом).
- **Зробити:** три тести одного екрана: завантаження, помилка сервера, успіх — через обробники MSW.
- **Перевірити себе:** три тести зелені; прибрати показ помилки в компоненті — тест помилки червоний.
- **Пастка:** один `QueryClient` на всі тести. Кеш протікає з тесту в тест, а три повтори за замовчуванням роблять
  тест помилки повільним.

### День 11. Наскрізні тести

- **Навіщо.** Лише наскрізний тест перевіряє застосунок так, як його бачить користувач: справжній браузер,
  справжня збірка.
- **Що це.** Playwright відкриває браузер і проходить сценарій. Перевірки Playwright самі чекають, доки
  елемент з'явиться. Трасування показує кожен крок з екраном і мережею — так розбирають падіння на CI.
- **Читати:** документацію Playwright, розділи про першочергові перевірки й трасування (поза корпусом).
- **Зробити:** 1) сценарій «вхід, створення запису, запис у списку, вихід» проти `vite preview`; 2) зламати
  маршрут сторінки створення; 3) відкрити трасування падіння.
- **Перевірити себе:** тест зелений на збірці; після кроку 2 — червоний, і трасування показує крок, де зламалося.
- **Пастка:** `waitForTimeout(2000)` замість перевірки, що чекає сама. Тест стає і повільним, і нестабільним.

### День 12. Доступність

- **Навіщо.** Інтерфейс, яким не користуються з клавіатури чи з екранним читачем, — бракований. І на співбесіді
  це питають усе частіше.
- **Що це.** Семантика: кнопка — `<button>`, посилання — `<a>`, поле — з `<label>`. Клавіатура: усе доступне
  через Tab, Enter, Esc; фокус видно. Після переходу на інший екран фокус переходить на заголовок нової сторінки.
  `aria-` атрибути — лише там, де семантики HTML забракло. `useId` дає стабільні ідентифікатори для зв'язку
  `label` і `aria-describedby`.
- **Читати:** `useId`; `Common components (e.g. <div>)` (атрибути `aria-*` і `role`); MDN — «Accessibility»;
  розширення axe DevTools (поза корпусом).
- **Зробити:** 1) пройти весь застосунок без миші; 2) axe DevTools на трьох головних екранах; 3) полагодити
  знайдене; 4) повторити.
- **Перевірити себе:** два числа проблем axe до й після; кожна дія застосунку доступна з клавіатури.
- **Пастка:** `<div onClick>` замість `<button>`. Його немає в порядку Tab, і екранний читач не знає, що це кнопка.

**Критерій завершення фази:** дані вантажаться до рендеру й живуть у кеші, жодного `useEffect` плюс `fetch` у
проєкті; тести трьох рівнів зелені й падають, коли ламається поведінка.

# Фаза 4. Сервер: SSR, стрімінг, серверні компоненти — 3 дні

Тут React перестає бути тільки браузерним. Фаза коротка навмисно: вона дає механізми самого React, які є в
корпусі, а їхню найпоширенішу реалізацію — Next.js — вчить окремий план. Фаза 0 плану Next.js спирається саме на
ці три дні.

### День 1. SSR і гідратація

- **Навіщо.** SPA приходить у браузер порожнім HTML. Пошуковик, прев'ю посилання в месенджері й повільний телефон
  бачать порожню сторінку, доки не виконався JavaScript.
- **Що це.** Серверний рендер (SSR) викликає ті самі компоненти на сервері й віддає готовий HTML. У браузері
  `hydrateRoot` «оживляє» його: React ще раз рендерить дерево, звіряє з наявною розміткою і навішує обробники.
  Якщо сервер і браузер намалювали різне (`Date.now()`, `Math.random()`, `window` у рендері), React повідомляє про
  розбіжність гідратації.
- **Читати:** `hydrateRoot`, `renderToString`, `Server React DOM APIs`.
- **Зробити:** 1) «Переглянути код сторінки» свого SPA — порожній `<div id="root">`; 2) найпростіший сервер на
  `node:http`, що віддає один компонент через `renderToString`; 3) клієнтський `hydrateRoot` для нього; 4) вивести
  в рендері поточний час.
- **Перевірити себе:** у коді сторінки з кроку 2 є вміст; у кроці 4 консоль показує розбіжність гідратації, і ви
  її полагодили, перенісши час у ефект.
- **Пастка:** вважати SSR «швидшим». Зміст з'являється раніше, але сторінка не реагує на клацання, доки не
  завершилася гідратація.

### День 2. Стрімінг на сервері

- **Навіщо.** Без стрімінгу сервер чекає найповільніший запит, перш ніж надіслати хоч байт.
- **Що це.** `renderToPipeableStream` шле HTML частинами: спершу оболонку (усе над межами `<Suspense>`), потім
  кожен шматок у міру готовності, з маленьким скриптом, що ставить його на місце заглушки. `prerender` малює
  сторінку заздалегідь, на збірці. Стрімінг ламає будь-яка проміжна ланка, що збирає відповідь цілком (проксі з
  буферизацією).
- **Читати:** `renderToPipeableStream` (розділи «Specifying what goes into the shell» і «Streaming more content as
  it loads»), `<Suspense>`, `prerender`.
- **Зробити:** 1) сервер дня 1 переписати на `renderToPipeableStream`; 2) блок із затримкою даних 2 с під
  `<Suspense>`; 3) `curl -N` на сервер.
- **Перевірити себе:** у терміналі два шматки відповіді з інтервалом близько двох секунд.
- **Пастка:** одна межа `<Suspense>` над усією сторінкою. Тоді оболонка порожня, і все чекає найповільнішого.

### День 3. Серверні компоненти, межа клієнта, Server Functions

- **Навіщо.** «Чим серверний компонент відрізняється від SSR» — питання, яке ставлять постійно й плутають усі.
- **Що це.** Серверний компонент виконується заздалегідь в окремому середовищі: «Server Components can run once at
  build time on your CI server, or they can be run for each request using a web server» (`Server Components`).
  Його код у браузер не їде взагалі; він може бути `async` і читати базу, але не має стану й обробників.
  `'use client'` позначає модуль, з якого починається клієнтська частина; пропси через цю межу проходять мережею
  і мусять серіалізуватися. `'use server'` позначає Server Functions — функції на сервері, які клієнт викликає
  мережею; до вересня 2024 усі вони звалися Server Actions. Кожна Server Function — публічний ендпойнт: «Always
  treat arguments to Server Functions as untrusted input and authorize any mutations» (`use server`, розділ
  Caveats). Вразливості React, оголошені в грудні 2025, стосуються саме серверних компонентів; SPA на Vite їх не
  зачіпають: «If your app does not use a framework, bundler, or bundler plugin that supports React Server
  Components, your app is not affected by this vulnerability» (блог React у корпусі, «Critical Security
  Vulnerability in React Server Components», 03.12.2025, і «Denial of Service and Source Code Exposure in React
  Server Components», 11.12.2025).
- **Читати:** `Server Components`, `use client` (зокрема розділ «Serializable types returned by Server
  Components»), `use server`, `Server Functions`.
- **Зробити:** 1) пів сторінки своїми словами: чим серверний компонент відрізняється від SSR; 2) таблиця з восьми
  значень — рядок, `Date`, функція, екземпляр класу, проміс, `Map`, JSX, `Symbol` — що з них можна передати через
  межу `'use client'`, і звірити з довідкою.
- **Перевірити себе:** у тексті є обидві тези: SSR малює HTML із **будь-яких** компонентів і потім шле їхній код у
  браузер; серверний компонент свого коду в браузер не шле зовсім. Таблиця збіглася з довідкою.
- **Пастка:** «серверний компонент = SSR». Друга пастка — вважати Server Function внутрішньою функцією: її може
  викликати будь-хто з будь-якими аргументами.

**Критерій завершення фази:** ви пояснюєте на одному прикладі, що виконалося на збірці, що — на сервері під час
запиту, а що — в браузері, і що з цього потрапило в бандл.

**Далі — Next.js.** Фреймворки складають ці механізми в готовий застосунок. Як це робить Next.js — план Next.js, з
фази 0 (дні про те, де виконується код, і про серверний React) і далі. Питання «Next.js як єдиний бекенд чи поруч
окремий NestJS» — план Next.js, фаза 8, день 1: там воно вирішується, коли обидва вміння вже є.

# Фаза 5. Продакшн: збірка, безпека, метрики, CI, викот — 6 днів

Застосунок уже в інтернеті з фази 1. Тут він стає легшим, безпечнішим, вимірюваним і викочується сам. Docker для
SPA, nginx перед нею і збір помилок тут не вчаться: образ і nginx — у плані NestJS (фаза про продакшн), збір
помилок — у плані Next.js (фаза 7, день 9).

### День 1. Розділення коду

- **Навіщо.** Користувач, що відкрив головну, не мусить вантажити код адмінки.
- **Що це.** Збирач кладе в окремий чанк усе, що імпортовано динамічно (`import()`). На рівні компонента це
  `lazy` під `<Suspense>`; на рівні маршруту в режимі даних React Router — властивість `lazy` маршруту: код
  маршруту й дані лоадера вантажаться паралельно, а не по черзі. Розділення за маршрутами — найдешевший виграш.
- **Читати:** у примірнику `vite` — `Building for Production`; у примірнику `react-router` — `Route Object`
  (розділ Data Mode, властивість `lazy`); `lazy`; `Build a React app from Scratch`, розділ «Code-splitting».
- **Зробити:** 1) записати розмір головного чанка (КБ gzip) зі звіту `vite build`; 2) винести маршрути в `lazy`;
  3) зібрати й записати знову; 4) за бажанням — карта бандла `rollup-plugin-visualizer` (поза корпусом;
  перевірте сумісність з вашою версією Vite).
- **Перевірити себе:** два числа в журналі; у «Мережі» чанк маршруту вантажиться лише при переході на нього.
- **Пастка:** лінивий компонент, що вантажить свої дані лише після свого коду, — водоспад «код, потім дані»,
  про який попереджає та сама глава.

### День 2. Оточення й безпека фронтенду

- **Навіщо.** Фронтенд атакують не через сервер, а через браузер: чужий скрипт у сторінці читає все, що бачить
  ваш код.
- **Що це.** Змінні `VITE_*` вшиваються в бандл під час збірки — **секретів у фронтенд-збірці не існує**, будь-хто
  прочитає їх у вкладці «Джерела». Захист від XSS — екранування JSX (фаза 1, день 2), `dangerouslySetInnerHTML`
  лише після очищення, адреси з даних — лише `http(s):`. Токени — за моделлю родини, яку будує план NestJS у фазі
  про авторизацію: короткий access-токен приходить у тілі відповіді й живе лише в пам'яті SPA; refresh-токен — у
  куці `HttpOnly` (JavaScript її не бачить), сервер обмінює його на новий при кожному оновленні. `localStorage` для
  токенів — ні: будь-який XSS його читає. Захищений маршрут — зручність, дані закриває бекенд.
- **Читати:** у примірнику `vite` — `Env Variables and Modes`; `Common components (e.g. <div>)` (проп
  `dangerouslySetInnerHTML`).
- **Зробити:** 1) `VITE_SECRET=abc123`, зібрати й знайти рядок `abc123` у `dist` пошуком; 2) пошук по коду
  `dangerouslySetInnerHTML` і `localStorage` — кожне входження обґрунтувати або прибрати; 3) функція `safeUrl`,
  що пропускає лише `http:` і `https:`, — на всі `href` з даних.
- **Перевірити себе:** пошук у кроці 1 знаходить значення — доказ для README; у коді жодного токена в
  `localStorage` і жодного неочищеного HTML.
- **Пастка:** «сховати» ключ стороннього API у змінну оточення фронтенду. Запит із ключем іде через ваш бекенд.

### День 3. Метрики

- **Навіщо.** «Сайт швидкий» на співбесіді не рахується. Рахується «LCP був 3,1 с, став 1,8 с, ось що я зробив».
- **Що це.** LCP — коли намальований найбільший видимий елемент. INP — одна з найдовших затримок між дією
  користувача й наступним кадром за весь візит. CLS — сума несподіваних зсувів макета. Лабораторно (Lighthouse,
  вкладка «Продуктивність») міряють на своєму комп'ютері в контрольованих умовах; польові дані збирають у справжніх
  користувачів бібліотекою web-vitals. Lighthouse не міряє INP — він не клацає; для INP потрібна взаємодія.
- **Читати:** web.dev — «Web Vitals», «LCP», «INP», «CLS»; документацію web-vitals (поза корпусом).
- **Зробити:** 1) повний рядок журналу для двох головних сторінок: Lighthouse mobile, три прогони, медіана LCP і
  CLS; INP — ваша типова дія з уповільненням процесора 4×; КБ gzip; 2) `onLCP`, `onINP`, `onCLS` з web-vitals —
  у консоль на викоченій версії.
- **Перевірити себе:** два повні рядки журналу; лабораторні й польові числа з консолі одного порядку, а
  розбіжність ви пояснюєте.
- **Пастка:** Lighthouse у режимі desktop на швидкому ноутбуці. Числа гарні, а користувачі сидять із телефонів.

### День 4. Зображення, шрифти й підказки браузеру

- **Навіщо.** Найбільший елемент сторінки — зазвичай зображення, а найчастіша причина стрибків макета —
  зображення без розмірів і шрифти, що підміняються.
- **Що це.** `width` і `height` на `<img>` резервують місце до завантаження — CLS падає. `fetchpriority="high"` на
  зображенні LCP і `loading="lazy"` на тих, що нижче першого екрана. `font-display: swap` показує текст одразу
  запасним шрифтом. React 19 уміє підказувати браузеру ресурси з будь-якого компонента: `preload`, `preconnect`,
  `prefetchDNS`, і сам піднімає `<link>` та `<title>` у `<head>`.
- **Читати:** `preload`, `preconnect`, `prefetchDNS`, `<link>`; MDN — «HTMLImageElement.fetchPriority»,
  «font-display».
- **Зробити:** 1) розміри всім зображенням; 2) `fetchpriority="high"` на зображенні LCP; 3) `preconnect` до
  домену зображень чи API; 4) шрифт з `font-display: swap` і `preload`; 5) Lighthouse до й після.
- **Перевірити себе:** дві пари чисел LCP і CLS у журналі.
- **Пастка:** `loading="lazy"` на зображенні LCP. Браузер навмисно вантажить його пізніше, і LCP росте.

### День 5. CI

- **Навіщо.** Кожна зміна має сама перевіритися, перш ніж потрапить у головну гілку.
- **Що це.** GitHub Actions запускає на кожен запит на злиття: лінт, `tsc --noEmit`, тести Vitest, збірку,
  Playwright проти `vite preview`. Кеш залежностей між запусками прискорює все. Dependabot або Renovate щотижня
  пропонують оновлення залежностей — латки безпеки приходять самі.
- **Читати:** документацію GitHub Actions і Dependabot (поза корпусом); у примірнику `vite` — `Command Line
  Interface`.
- **Зробити:** 1) робочий процес із п'ятьма кроками; 2) захист головної гілки: злиття лише із зеленим CI;
  3) запит на злиття з навмисно червоним тестом; 4) бот оновлень.
- **Перевірити себе:** червоний запит не зливається; у журналі — два числа: тривалість першого запуску й
  повторного, з кешем.
- **Пастка:** ганяти Playwright проти сервера розробки. Він поводиться не так, як збірка, і тест бреше.

### День 6. Викот статики як слід

- **Навіщо.** Після кожного викоту частина користувачів сидить на старій вкладці зі старим кодом. Кеш вирішує, чи
  вони це помітять.
- **Що це.** Файли в `assets/` мають хеш в імені — новий вміст, нове ім'я, тому їх кешують на рік:
  `Cache-Control: public, max-age=31536000, immutable`. `index.html` посилається на поточні імена, тож його не
  кешують (`no-cache`): кожен візит перевіряє, чи не з'явилася нова версія. Карти коду в публічний доступ не
  викладають — їх віддають збирачу помилок. Заголовки безпеки й політику CSP для SPA в продакшні віддає nginx — це
  робиться в плані NestJS, фаза про продакшн; на статичному хостингу — файл заголовків хостингу (поза корпусом).
  Стара вкладка після викоту просить чанк, якого вже немає, — це помилка завантаження, яку ловить межа помилок і
  пропонує оновити сторінку.
- **Читати:** у примірнику `vite` — `static-deploy`, `Build Options` (опція `build.sourcemap`).
- **Зробити:** 1) правила кешу для `index.html` і `assets/`; 2) `curl -I` обох; 3) карти коду — `hidden` або
  вимкнені; 4) відкрити вкладку, викотити нову версію, перейти на лінивий маршрут у старій вкладці.
- **Перевірити себе:** `curl -I` показує два різні `Cache-Control`; запит до `.map` дає 404; стара вкладка
  показує «вийшла нова версія, оновіть сторінку», а не білий екран.
- **Пастка:** довгий кеш на `index.html`. Користувачі тижнями сидять на старій версії, а виправлення «не
  доходить».

**Критерій завершення фази:** злиття в головну гілку саме перевіряє й викочує застосунок; журнал вимірів
показує числами, що стало краще і завдяки чому.

# Що далі: SPA отримує бекенд

План React закінчується застосунком, який живе в інтернеті, але бере дані з фейкового API. Зшивання з бекендом —
не окрема фаза тут, а частина плану NestJS ([../nestjs/LEARNING.md](../nestjs/LEARNING.md)), де кожна вправа має
і фронт-бік:

- **Контракт.** NestJS видає документ OpenAPI, з нього генерується типізований клієнт, і SPA переходить на нього
  — жодного ручного типу відповіді (план NestJS, фаза про робочий API).
- **Помилки.** Помилка валідації з бекенду приходить за шляхом поля, і форма з фази 3, дня 7 підсвічує конкретне
  поле через `setError` (там само).
- **Токени й проксі.** У розробці SPA ходить в API через проксі Vite (`server.proxy`, у примірнику `vite` —
  `Server Options`): одне походження, CORS не потрібен. Модель токенів із фази 5, дня 2 реалізується наскрізь:
  вхід, мовчазне оновлення, вихід (план NestJS, фаза про авторизацію).
- **Усе разом.** SPA за nginx, бекенд, база й міграції однією командою `docker compose` (план NestJS, фаза про
  продакшн).

Після NestJS — план Next.js ([../nextjs/LEARNING.md](../nextjs/LEARNING.md)): у фазі 6, день 5 цей самий SPA
переїжджає на Next.js, а фаза 8 зшиває Next.js з NestJS.

# Під працевлаштування

**Портфоліо.** Один застосунок, доведений до кінця фази 5, вартий більше, ніж п'ять недороблених. З репозиторію
має бути видно: типізацію без `any`, дані в лоадерах і кеші, форми з однією схемою, тести трьох рівнів,
доступність, CI, журнал вимірів і README з адресою живої версії, описом запуску та одним абзацом про ухвалені

# Застереження про документацію

У корпусі цього примірника — **лише сама React**, зате всіх версій від 0.3 до 19.3 разом із CHANGELOG, нотатками
релізів і блогом, включно з оголошеннями про вразливості. Для React Router, TanStack Query, React Hook Form, zod,
Zustand, Redux Toolkit, Tailwind, Vite і TypeScript у фабриці є власні примірники — питайте їх, а не цей.
Vitest, React Testing Library, MSW, Playwright, web-vitals, react-window, TanStack Virtual, GitHub Actions і
хостинги в жодному корпусі фабрики немає: для них — сайти самих інструментів.

**Легасі-глави.** `Reconciliation` і `Optimizing Performance` — документація до React 18 включно; у новій
документації окремих глав немає. План посилається на них свідомо й щоразу каже, що саме звідти брати. Сервер
повертає їх із версіями — дивіться на них.

**Приклади з інших примірників.** `Example: react/react-router` — приклад із репозиторію TanStack Query, а не
рекомендація React Router; беріть з нього зв'язку лоадера з кешем, а не все підряд.

**Безпека.** Оголошення про вразливості виходять у блозі React і є в корпусі. Перед кожним оновленням React
питайте сервер про свіжі оголошення для вашої лінії й перевіряйте, чи вони стосуються вашої збірки: SPA на Vite і
застосунок із серверними компонентами зачіпають різні оголошення.
