# React — план вивчення

План від нуля до рівня, на якому React перестає підкидати сюрпризи: від мови й браузера, через ядро бібліотеки та
її внутрішній устрій, до екосистеми, сервера, збірки й викоту. Порядок тем визначений тим, що ламається в
реальних проєктах і що питають на співбесідах, а не структурою сайту документації.

Усього — сімдесят чотири навчальні дні по півтори-дві години. П'ять днів на тиждень (два лишаються на те, щоб
доганяти пропущене) дають близько чотирьох місяців.

| Фаза | Тема | Днів |
|------|------|------|
| 0 | База, якої React не дає: JS, TypeScript, браузер, інструменти | 12 |
| 1 | Ядро React — розділ `Learn` цілком | 18 |
| 2 | Як React працює зсередини: рендер, конкурентність, компілятор | 8 |
| 3 | Екосистема: маршрути, серверний стан, форми, тести | 12 |
| 4 | Сервер: SSR, React Server Components, Next.js | 10 |
| 5 | Продакшн: збірка, продуктивність, Docker, викот | 9 |
| 6 | Зшивання з бекендом | 5 |

## Як користуватися планом

**Один наскрізний проєкт.** Не десяток навчальних застосунків, а один, який росте через усі фази. Добре працює
будь-що зі списками, формами й авторизацією: саме там проявляються всі механізми React.

**День — одиниця умовна.** Якщо тема не вляглася за день, беріть другий. Небезпечний не пропущений день, а
пропущена вправа: без неї тема лишається прочитаною, а не вивченою.

**Документація під рукою.** Цей примірник фабрики — і є довідник: `./df react serve` з кореня, далі питання до
MCP-сервера замість пошуку в гуглі. Корпус тримає документацію всіх версій React від 0.3 до 19.3, тож відповідь
приходить із зазначенням версії — а це саме те, чого не дає жодна стаття. Назви глав у плані — назви документів
корпусу, їх можна питати дослівно.

**Версія.** Вчіть на 19.x. Усе, що написано в цьому плані, стосується сучасного React із хуками; класові
компоненти згадані рівно раз і лише тому, що ви побачите їх у старому коді на роботі.

## Якщо ви вже пишете на React

План написаний від нуля, але мідлу не варто читати його поспіль. Робіть інакше: по кожній фазі спершу дайте
відповідь на контрольні питання нижче, і якщо відповідь впевнена — фазу можна пройти вправами, без читання.

- **Фаза 0.** Чому мутація масиву не викликає перемальовування? Що таке замикання і як воно робить «застарілий
  стан» в ефекті? Що відбувається в браузері між зміною стилю й пікселями на екрані?
- **Фаза 1.** Чому `key` за індексом масиву ламає список із видаленням? Чому два поспіль `setCount(count + 1)`
  дають плюс один, а не плюс два? Коли ефект **не** потрібен, хоч його й хочеться написати?
- **Фаза 2.** Чим рендер відрізняється від коміту? Що саме робить `useMemo` і чому він майже завжди зайвий? Що
  дає `useTransition`, чого не дає `setTimeout`?
- **Фаза 3.** Чому `useEffect` плюс `fetch` — поганий спосіб брати дані з сервера? Що тестує React Testing
  Library і чого вона принципово не тестує?
- **Фаза 4.** Де проходить межа `use client` і що станеться, якщо її посунути?

Кожне питання, на яке відповідь не впевнена, — це день, який треба пройти повністю.

## Три пастки, які переживають будь-який рівень

- **Стан іммутабельний.** `arr.push(x)` не перемальовує нічого: React порівнює посилання, а воно не змінилося.
  Це не примха бібліотеки, а наслідок того, як працює порівняння — перший день фази 0 про це.
- **Рендер — не малювання.** Виклик компонента, обчислення різниці й запис у DOM — три різні події в часі.
  Половина питань «чому воно не оновилося» — це сплутані фази.
- **Ефект — не «зробити після рендеру».** Ефект синхронізує компонент із чимось **зовнішнім**. Якщо
  синхронізувати нічого, ефект не потрібен — про це є ціла глава, і половина проєктів її не прочитала.

# Фаза 0. База, якої React не дає — 12 днів

React — бібліотека поверх мови й браузера. Усе, що тут, документація React вважає відомим і не пояснює; саме на
цих речах, а не на хуках, застрягає більшість новачків. Джерела — MDN і TypeScript Handbook, корпусу React тут
ще немає.

- **День 1 — значення й посилання.** Копія проти посилання, `spread`, `structuredClone`, чому `===` для двох
  однакових об'єктів — хибність. *Вправа:* функція, що додає елемент у масив, не змінюючи вхідний; довести
  порівнянням посилань. Це фундамент усього стану React.
- **День 2 — масиви й об'єкти функційно.** `map`, `filter`, `reduce`, `find`, `some`, сортування без мутації.
  *Вправа:* набір перетворень над списком об'єктів, жодної мутації вхідних даних.
- **День 3 — функції та замикання.** Область видимості, замикання, чому функція пам'ятає значення з моменту
  створення. *Вправа:* лічильник на замиканні й свідомо «застаріле» значення в `setTimeout`. **Головний день
  фази:** увесь клас помилок із хуками — це замикання.
- **День 4 — модулі й пакети.** ESM, іменований та типовий експорт, `package.json`, семантичне версіювання,
  `npm` проти `npx`. *Вправа:* розбити свій навчальний код на модулі й підключити одну зовнішню бібліотеку.
- **День 5 — асинхронність.** Промиси, `async`/`await`, обробка помилок, `Promise.all`, черга мікрозадач.
  *Вправа:* три запити послідовно й паралельно з вимірюванням часу.
- **День 6 — мережа.** `fetch`, статуси, JSON, заголовки, `AbortController`. *Вправа:* запит, який скасовується
  при швидкій зміні пошукового рядка, — те саме ви робитимете в React ефектом із прибиранням.
- **День 7 — DOM і події.** Дерево, атрибути проти властивостей, спливання подій, делегування,
  `preventDefault`. *Вправа:* список із делегуванням на батьківському елементі, без React.
- **День 8 — як браузер малює.** Стилі, компонування, малювання, композиція; чому читання `offsetHeight` після
  запису стилю дороге. *Вправа:* сторінка, що гальмує від перекомпонування, і її полагодження.
- **День 9 — TypeScript: основи.** Типи проти інтерфейсів, об'єднання, звуження, `unknown` проти `any`.
  *Вправа:* типізувати вчорашній код без жодного `any`.
- **День 10 — TypeScript: дженерики.** Параметри типу, обмеження, службові типи `Partial`, `Pick`, `Omit`.
  *Вправа:* типізоване сховище `Store<T>`.
- **День 11 — інструменти.** Vite, режим розробки й гаряча заміна модулів, ESLint, Prettier, `tsconfig`.
  *Вправа:* порожній проєкт із нуля, без шаблону-стартера, з робочим лінтом.
- **День 12 — інструменти браузера.** Вкладки «Мережа» та «Продуктивність», карти коду, профіль запису.
  *Вправа:* заміряти час завантаження власної сторінки й пояснити кожен запит у переліку.

**Критерій завершення фази:** ви можете пояснити, чому зміна поля в об'єкті не помічається порівнянням, і що
відбувається в браузері між подією кліку й новим кадром на екрані.

# Фаза 1. Ядро React — 18 днів

Розділ `Learn` на react.dev цілком, у порядку самої документації: вона вибудувана правильно, і скорочувати її —
найпоширеніша помилка самоучок. Проєкт створюйте через `Installation` і `Creating a React App`.

## Описати інтерфейс — дні 1–5

- **День 1 — `Your First Component`, `Importing and Exporting Components`.** *Вправа:* три компоненти у трьох
  файлах, зібрані в один екран.
- **День 2 — `Writing Markup with JSX`, `JavaScript in JSX with Curly Braces`.** *Вправа:* розмітка з
  обчисленнями, умовами й підстановкою стилів; звірити, у що JSX перетворюється насправді.
- **День 3 — `Passing Props to a Component`, `Conditional Rendering`.** *Вправа:* картка, що виглядає по-різному
  для трьох станів даних, без жодного стану всередині.
- **День 4 — `Rendering Lists`.** Ключі: навіщо, чому не індекс. *Вправа:* список із видаленням посередині, де
  ключ за індексом ламає вміст полів вводу, — побачити це на власні очі й полагодити.
- **День 5 — `Keeping Components Pure`, `Understanding Your UI as a Tree`.** *Вправа:* знайти у власному коді
  побічний ефект під час рендеру й прибрати його.

## Додати взаємодію — дні 6–9

- **День 6 — `Responding to Events`, `State: A Component's Memory`.** *Вправа:* форма з кількома полями на
  `useState`.
- **День 7 — `Render and Commit`, `State as a Snapshot`.** *Вправа:* обробник, що читає стан після `set`, і
  пояснення, чому там старе значення.
- **День 8 — `Queueing a Series of State Updates`.** *Вправа:* три `setCount(count + 1)` поспіль проти
  `setCount(c => c + 1)`; пояснити різницю словами.
- **День 9 — `Updating Objects in State`, `Updating Arrays in State`.** *Вправа:* редагування вкладеного об'єкта
  в стані без жодної мутації.

## Керувати станом — дні 10–14

- **День 10 — `Reacting to Input with State`, `Thinking in React`.** *Вправа:* описати екран як набір станів,
  а не набір дій.
- **День 11 — `Choosing the State Structure`.** Похідні дані не зберігають. *Вправа:* знайти в коді стан, який
  обчислюється з іншого, і прибрати його.
- **День 12 — `Sharing State Between Components`.** Підняття стану. *Вправа:* два компоненти, синхронізовані
  через спільного батька.
- **День 13 — `Preserving and Resetting State`.** Стан живе за позицією в дереві. *Вправа:* форма, яку треба
  скинути при зміні сутності, — через `key`, а не через ефект.
- **День 14 — `Extracting State Logic into a Reducer`.** *Вправа:* перевести складну форму з кількох `useState`
  на редюсер.

## Контекст і аварійні виходи — дні 15–18

- **День 15 — `Passing Data Deeply with Context`, `Scaling Up with Reducer and Context`.** *Вправа:* тема або
  поточний користувач через контекст; пояснити, чому контекст не є заміною менеджеру стану.
- **День 16 — `Referencing Values with Refs`, `Manipulating the DOM with Refs`.** *Вправа:* фокус на полі та
  прокручування до елемента.
- **День 17 — `Synchronizing with Effects`, `You Might Not Need an Effect`.** *Вправа:* викинути з власного коду
  щонайменше один ефект, замінивши його обчисленням під час рендеру або обробником події. **Головна глава всього
  розділу:** зайві ефекти — найдорожча звичка в React-коді.
- **День 18 — `Lifecycle of Reactive Effects`, `Separating Events from Effects`, `Removing Effect
  Dependencies`, `Reusing Logic with Custom Hooks`.** *Вправа:* ефект із прибиранням (підписка або скасування
  запиту), винесений у власний хук; пояснити, навіщо `StrictMode` викликає його двічі.

**Критерій завершення фази:** ви можете сказати, чому компонент перемалювався, не вгадуючи, а дивлячись на код.

# Фаза 2. Як React працює зсередини — 8 днів

Фаза, після якої зникає слово «магія». Тут же — вимірювання: жодна оптимізація не робиться без заміру до неї.

- **День 1 — `React Developer Tools`.** Дерево компонентів, підсвічення перемальовувань, профіль.
  *Вправа:* записати профіль власного екрана й знайти найдорожчий компонент.
- **День 2 — узгодження дерева.** Як React зіставляє старе дерево з новим, чому тип елемента й ключ вирішують
  усе. *Вправа:* змінити тип обгортки й побачити, як стан дитини зникає.
- **День 3 — пакетування оновлень.** Кілька `set` в одному обробнику дають один рендер; `flushSync` і його
  ціна. *Вправа:* відтворити обидва випадки й порахувати рендери.
- **День 4 — мемоізація.** `memo`, `useMemo`, `useCallback`. *Вправа:* заміряти екран, додати мемоізацію,
  заміряти знову — і чесно визнати, якщо різниці немає. Саме так це питають на співбесіді.
- **День 5 — `useTransition`.** Термінові й нетермінові оновлення. *Вправа:* важкий список із фільтром, де
  введення лишається чуйним.
- **День 6 — `useDeferredValue`.** Чим відрізняється від переходу. *Вправа:* той самий список, але іншим
  інструментом; пояснити, коли який.
- **День 7 — `<Suspense>` і межі помилок.** Що межа ловить, а що ні; запасний вміст. *Вправа:* лінивий
  компонент через `lazy` під `Suspense` плюс межа помилок навколо.
- **День 8 — `React Compiler`.** Глави `React Compiler → Introduction` та `Installation`. Що він мемоізує за
  вас і чому це не привід прибирати всю мемоізацію завтра. *Вправа:* увімкнути на навчальному проєкті й
  подивитися на різницю в профілі.

# Фаза 3. Екосистема — 12 днів

React не має нічого з цього в коробці, і в корпусі цього примірника документації сторонніх бібліотек немає:
читайте їхні власні сайти. Але вибір бібліотек — половина роботи фронтендера, тому фаза обов'язкова.

- **День 1 — маршрутизація.** React Router: маршрути, посилання, параметри шляху. *Вправа:* три екрани й
  навігація між ними.
- **День 2 — вкладені маршрути.** Спільні каркаси, індексні маршрути, сторінка 404, захищений маршрут.
  *Вправа:* приватна зона, куди не пускає без «входу» (поки фейкового).
- **День 3 — серверний стан.** Чому `useEffect` плюс `fetch` — антипатерн: гонки, подвійні запити, відсутність
  кешу. TanStack Query: запит, стани завантаження й помилки. *Вправа:* перевести всі свої завантаження на неї.
- **День 4 — кеш.** Ключі запитів, застарілі дані, повторне отримання, інвалідація. *Вправа:* два екрани, що
  показують ті самі дані з одного кешу.
- **День 5 — мутації.** Відправлення змін, інвалідація після успіху, оптимістичне оновлення; хук `useOptimistic`
  у самому React. *Вправа:* лайк, що малюється миттєво й відкочується при помилці.
- **День 6 — форми.** Контрольовані проти неконтрольованих, компонент `<form>` у React 19, `useActionState` і
  `useFormStatus`. *Вправа:* форма з індикатором відправлення без жодного `useState`.
- **День 7 — форми серйозно.** React Hook Form і схема перевірки (zod). *Вправа:* форма на десять полів із
  валідацією, де перевірка описана один раз і працює на обох боках.
- **День 8 — глобальний стан.** Коли контексту вже не вистачає; Zustand або Redux Toolkit. *Вправа:* винести
  справді глобальне (користувач, тема) і переконатися, що решта глобальною не була.
- **День 9 — стилі.** CSS-модулі, Tailwind, CSS-in-JS: чим платять за кожен. *Вправа:* один компонент трьома
  способами й висновок для себе.
- **День 10 — тестування.** React Testing Library: тестувати поведінку, а не реалізацію; ролі та доступні імена
  замість класів. *Вправа:* тест форми, який не зламається від перейменування класу.
- **День 11 — тести з мережею.** Підміна запитів через MSW, асинхронні очікування, `act` і звідки береться його
  попередження. *Вправа:* тест екрана із завантаженням, помилкою й успіхом.
- **День 12 — доступність.** Семантика, клавіатура, фокус, `aria-` там, де семантики не вистачило.
  *Вправа:* пройти власний застосунок без миші.

# Фаза 4. Сервер: SSR, RSC, Next.js — 10 днів

Тут React перестає бути тільки браузерним. Перші п'ять днів — механізми в самому React (вони є в корпусі), далі
Next.js як їхня найпоширеніша реалізація (його документації в корпусі немає).

- **День 1 — навіщо сервер.** Порожній HTML і перший змістовний кадр, SEO, швидкість. Гідратація:
  `hydrateRoot`. *Вправа:* подивитися на HTML свого SPA до виконання JS.
- **День 2 — рендер на сервері.** `react-dom/server`: `renderToString` проти `renderToPipeableStream`, стрімінг
  розмітки. *Вправа:* найпростіший сервер, що віддає готовий HTML.
- **День 3 — `Server Components`.** Компонент, який виконується на сервері й не їде в бандл. Чим він принципово
  відрізняється від SSR. *Вправа:* сформулювати різницю письмово — її питають постійно й плутають усі.
- **День 4 — межа клієнта.** Директиви `use client` і `use server`, що можна передавати через межу.
  *Вправа:* свідомо посунути межу вгору й подивитися, як росте бандл.
- **День 5 — `Server Functions` і `use`.** Виклик серверного коду з клієнта; читання проміса через `use`.
- **День 6 — Next.js: каркас.** App Router, вкладені каркаси, файли `loading` і `error`, параметри маршруту.
- **День 7 — Next.js: дані.** Отримання даних у серверних компонентах, кешування, ревалідація, динамічний проти
  статичного рендеру. *Вправа:* сторінка, що оновлює дані за розкладом, і сторінка, що завжди свіжа.
- **День 8 — Next.js: дії.** Серверні дії у формах, перевірка вводу на сервері, перенаправлення після успіху.
- **День 9 — Next.js: сторінкові дрібниці.** Метадані й SEO, оптимізація зображень і шрифтів, обробка 404.
- **День 10 — архітектурне рішення.** Next як самостійний бекенд проти зв'язки Next плюс окремий бекенд на
  NestJS. Критерії: складність домену, команда, фонові задачі, черги. *Вправа:* вибрати для свого проєкту й
  записати обґрунтування — це питання ставлять на кожній співбесіді рівня мідл і вище.

# Фаза 5. Продакшн: збірка, продуктивність, Docker, викот — 9 днів

- **День 1 — збірка.** Що робить Vite у продакшн-режимі: бандл, хешовані імена, розділення коду. `lazy` плюс
  `Suspense` на рівні маршрутів. *Вправа:* екрани вантажаться окремими файлами.
- **День 2 — розмір бандла.** Аналізатор, струшування дерева, чому імпорт бібліотеки цілком її не струшує.
  *Вправа:* знайти найбільшу залежність і замінити або відкласти її.
- **День 3 — оточення.** Режими збірки, змінні `VITE_*`. **Секретів у фронтенд-збірці не існує:** усе, що
  потрапило в бандл, читає будь-хто. *Вправа:* знайти в бандлі власну змінну пошуком по тексту.
- **День 4 — метрики.** LCP, CLS, INP: що кожна означає і чим міряється — лабораторно (Lighthouse) і на живих
  користувачах. *Вправа:* заміряти свій застосунок і записати три числа до оптимізації.
- **День 5 — завантаження ресурсів.** `preload`, `preconnect`, пріоритети, зображення потрібного розміру,
  підключення шрифтів без стрибка тексту. *Вправа:* покращити LCP і показати різницю числами.
- **День 6 — Docker для SPA.** Багатоетапний образ: збірка в Node, роздача статики через nginx, запуск не від
  root, `.dockerignore`. *Вправа:* образ, менший за сто мегабайтів.
- **День 7 — Docker для Next.js.** Чому образ інший: сервер лишається жити; режим standalone, змінні часу
  збірки проти змінних часу запуску. *Вправа:* той самий застосунок двома образами.
- **День 8 — CI.** GitHub Actions: лінт, типи, тести, збірка образу, кеш залежностей. *Вправа:* збірка падає,
  якщо впав хоча б один тест.
- **День 9 — викот і спостереження.** Статичний хостинг проти серверного, збір помилок і карти коду до нього.
  *Вправа:* зламати щось навмисно й знайти помилку у звіті зі стектрейсом по вихідному коду.

# Фаза 6. Зшивання з бекендом — 5 днів

Фінальна фаза, спільна з планом NestJS ([../nestjs/LEARNING.md](../nestjs/LEARNING.md)). Саме вона перетворює два
окремі вміння на фулстек.

- **День 1 — контракт.** Генерація типів і клієнта з OpenAPI-документа бекенду. *Вправа:* прибрати всі ручні
  типи відповідей — хай їх дає бекенд.
- **День 2 — авторизація наскрізь.** Кука `httpOnly` проти токена в пам'яті, оновлення токена, захищені
  маршрути, вихід. *Вправа:* повний цикл від логіну до протухання.
- **День 3 — CORS і проксі.** Чому в розробці все через проксі, а в продакшні — через спільний домен або
  налаштований CORS. *Вправа:* підняти обидва варіанти й порівняти заголовки.
- **День 4 — помилки наскрізно.** Єдиний формат помилки бекенду, його розкладання на повідомлення форми й
  сповіщення. *Вправа:* помилка валідації з сервера підсвічує конкретне поле.
- **День 5 — усе разом.** `docker-compose`: фронтенд, бекенд, база, міграції — однією командою на чистій
  машині. *Вправа:* клонувати власний репозиторій у порожню теку й підняти застосунок з нуля.

# Під працевлаштування

**Портфоліо.** Один застосунок, доведений до шостої фази, вартий більше, ніж п'ять недороблених. З репозиторію
має бути видно: типізацію без `any`, тести, роботу з серверним станом, доступність, Docker, CI, README з описом
запуску й одним абзацом про ухвалені рішення.

**Питання, які ставлять майже завжди** — і глава, де лежить відповідь:

| Питання | Де відповідь |
|---------|--------------|
| Чому не можна брати індекс масиву за `key` | `Rendering Lists` |
| Чим рендер відрізняється від коміту | `Render and Commit` |
| Чому стан у обробнику «старий» | `State as a Snapshot` |
| Коли ефект не потрібен, хоч і хочеться | `You Might Not Need an Effect` |
| Навіщо `StrictMode` викликає ефект двічі | `Synchronizing with Effects` |
| Коли `useMemo` справді допомагає | фаза 2, день 4 — з власними замірами |
| Чим `useTransition` відрізняється від `useDeferredValue` | `useTransition`, `useDeferredValue` |
| Чим серверний компонент відрізняється від SSR | `Server Components` |
| Чому `useEffect` плюс `fetch` — поганий спосіб брати дані | фаза 3, день 3 |
| Що таке LCP і як ви його покращували | фаза 5, дні 4–5 |

**Ваша фора.** Фронтендер, який розуміє бекенд, на ринку коштує дорожче за того, хто вміє лише малювати екрани.
Питання про CORS, формат помилок API, місце зберігання токена й `docker-compose` — ви відповідаєте на них з обох
боків одразу.

# Застереження про документацію

У корпусі цього примірника — **лише сама React**, зате всіх версій від 0.3 до 19.3 разом із CHANGELOG і нотатками
релізів. React Router, TanStack Query, React Hook Form, zod, Zustand, Redux Toolkit, Tailwind, Vite, Next.js,
Testing Library, MSW, Playwright — їх тут немає, і питати про них сервер марно: він чесно відмовить. Це навмисно:
межа корпусу збігається з межею бібліотеки. Для всього іншого — сайти самих бібліотек.

Окремо про Next.js: він розвивається швидше за React і має власні версії. Усе, що в плані стосується App Router,
серверних дій і кешування, звіряйте з його поточною документацією — саме там найчастіше застаріває будь-який
навчальний матеріал, включно з цим.
