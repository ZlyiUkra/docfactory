# react — примірник фабрики docfactory

Другий примірник фабрики: захищений MCP-сервер, що відповідає на питання про React за офіційною документацією всіх
його версій — від першого публічного релізу 0.3 (травень 2013) до поточної 19.3. Код спільний і лежить у
`../../engine/` (завантаження корпусу), `../../server/` (сервер, агент, шари) та `../../common/` (пошук); ця тека
тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

Питання про React рідко звучить «що робить `useEffect`» — частіше «з якої версії це є, що з ним змінювалося і чи
так ще можна писати». Відповідь на таке питання не лежить на одній сторінці: її складають документація версії, в
якій можливість з'явилася, запис CHANGELOG і нотатки релізу, анонс у блозі й нинішня документація. Тому корпус тут —
не одна редакція сайту, а всі, і кожен документ несе свою версію.

## Що в цій теці

- `corpus/` — документація React усіх версій звичайними текстовими файлами; поруч `index.json` — паспорт, тобто
  опис копії: адреса, дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями до сайтів і профіль домену: ім'я
  сервера, імена інструментів, домени, посилання на які лишаються у відповідях.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`); `.mcp.json` — запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df react <крок>`.

П'ять особливостей, які варто знати:

- **Проміжні лінії — знімки репозиторію сайту.** Сайти тримають лише останній стан кожної мажорної версії, тож
  документація 16.1–16.13, 18.0–18.1 і 19.0–19.2 береться з історії репозиторіїв, з яких ці сайти збиралися: стан на
  кінець дня виходу `.0` кожної лінії. Коміт записаний у `sources.json` повним SHA — знімок відтворюється байт у байт,
  а білий список дозволяє рівно файли цього коміту. У старих сторінках частина прикладів коду вбудовувалася з окремих
  файлів (`embed:…`), і в знімку на їхньому місці лишається лише посилання.
- **15-та версія береться з GitHub.** 15.react.dev перенаправляє на react-legacy.netlify.app, а там `robots.txt`
  забороняє автоматичне завантаження всього сайту. Та сама документація лежала в репозиторії React (тека `docs/`)
  до переїзду на окремий сайт, тож для 15.x і всіх 0.x вона береться звідти — з тегу кожної лінії.
- **Меню 18.2.0 — зі сторінки `hooks-intro.html`.** `legacy.reactjs.org/docs/getting-started.html` тепер
  перенаправляє на react.dev/learn; решта сторінок і їхні `page-data.json` живі.
- **Сторінки поза меню архівних сайтів — поіменно.** Застарілий `legacy-context`, Concurrent Mode на 16 і 17,
  сторінки попереджень `warnings/*` на сайтах живі, але з меню прибрані, а мапи сайту Gatsby-архіви не мають. Такі
  сторінки перелічені в полі `pages` джерела; знайдено їх звіркою зі знімками тих самих ліній у репозиторії. Нову
  сторінку поза меню `check` сам не помітить — лише вручну доданою в `pages`.
- **Блог не дублюється.** Записи з 21.12.2020 і новіші є на react.dev, тож з архіву legacy беруться лише старші
  (поле `before` у `sources.json`).

Переклади документації не беруться: індекс англійський.

## Версії у відповідях

Кожен документ несе рядок шапки `# версія: 18.3.1`. Документація сусідніх версій часто повторює одна одну дослівно,
і такий повтор не викидається, а зливається: фрагмент лишається один, а в полі `versions` перелічено всі версії, в
документах яких цей текст стоїть саме так, від найновішої. Сам перелік уже відповідає на питання «від якої до якої
версії документація казала саме це». Адреса й назва фрагмента — з найновішої з цих версій.

Пошук (`search_docs`) приймає необов'язковий `version` — лінію версій: `"18"` лишає всі 18.x, `"16.8"` — 16.8.x,
`"0.14"` — 0.14.x. Записи блогу версії не мають і приходять лише з пошуку без фільтра. Невідома версія дає не
мовчазний нуль, а перелік ліній, які є.

Опис інструмента велить моделі на питання про історію можливості відповідати по пунктах: з якої версії вона є і
який реліз її приніс; що змінювалося далі; чим зміну було викликано, якщо документи це кажуть; як вона підтримується
в поточній версії. Кожен пункт називає версію й документ, а пункт, якого знайдені уривки не підтверджують, не
пишеться.

## Установка venv

Єдиний крок, що робиться зсередини цієї теки, — і після нього треба повернутися в корінь. Активувати venv не
потрібно ані зараз, ані потім: `df` сам викликає `.venv/bin/python` примірника на кожному кроці.

```
cd instances/react
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть свій ANTHROPIC_API_KEY, якщо потрібен крок ask
cd ../..                      # назад у корінь фабрики: усі кроки df — тільки звідти
```

`python3` тут — той, що 3.10 або новіший і з модулем `venv`; якщо системний без нього, підійде будь-який інший.

## Спосіб А — власний захищений агент (усі чотири шари)

```
./df react tools                         # $0: під'єднання, перелік інструментів
./df react ask "Since which version does React have useId, and is it still recommended?"   # платно
```

Клієнт тут — наш код, тож працюють усі чотири шари: вхідний фільтр над запитом, правила перед кожним викликом
інструмента, список дозволених інструментів і вихідний фільтр разом із guardrail — окремим викликом дешевої моделі,
що перевіряє готову відповідь.

## Спосіб Б — сервер під Claude Code (HTTP)

**1. Підняти сервер** (окремий термінал, з кореня фабрики `docfactory/`), і лишити його жити:

```
./df react serve                         # HTTP-сервер на порту з config.json (8761)
```

**2. Додати сервер у Claude Code** — одним зі способів:

- відкрити теку `instances/react/` як проєкт у Claude Code: він побачить `.mcp.json` цієї теки й запропонує сервер
  `react-docs` (адреса `http://127.0.0.1:8761/mcp`), який треба підтвердити;
- або командою: `claude mcp add --transport http --scope user react-docs http://127.0.0.1:8761/mcp`. Прапорець
  `--scope user` робить сервер видимим у всіх проєктах, а не лише в тій теці, з якої додали.

**3. Перевірити під'єднання.** У сесії Claude Code — команда `/mcp`: має бути `react-docs` і два інструменти
`search_docs`, `read_section`. Поза сесією той самий перелік дає `claude mcp list`.

**4. Користуватися.** Розмова з Claude Code лишається вільною: він сам кличе інструменти, коли питання стосується
React, і не кличе, коли ні. Запит усередину пишеться англійськими іменами React (індекс англійський), а відповідь —
мовою питання.

**5. Зупинити сервер.** У терміналі, де він живе, — Ctrl+C. Якщо термінал загублено, знайдіть процес за портом
і зупиніть його за номером:

```
ss -ltnp | grep 8761                     # покаже pid=NNNN процесу, що тримає порт
kill NNNN                                # м'яка зупинка: сервер закриває сесії й виходить
```

`kill -9` не потрібен — сервер виходить на TERM. А от зупиняти за іменем (`pkill -f spec_mcp`) не варто: під
шаблон потрапляють сервери інших примірників, а іноді й сама оболонка, з якої ви це запустили.

**Якщо щось не так.** `[Errno 98] address already in use` — порт уже зайнятий, майже завжди попереднім, забутим
`serve`; хто саме тримає порт, покаже `ss -ltnp | grep 8761`, і той процес треба зупинити. `/mcp` показує
`react-docs` як «failed / not connected» — майже завжди сервер не піднятий (крок 1) або порт інший; звірте адресу
`http://127.0.0.1:8761/mcp` з полем `port` у `config.json`.

Сервери всіх чотирьох примірників тримаються під'єднаними одночасно: порти й колекції в них різні — 8760
`ecma-spec`, 8761 `react-docs`, 8762 `nestjs-docs`, 8763 `astro-docs`. Однакові імена інструментів не заважають:
Claude Code розводить їх сам, тобто `search_docs` сервера `react-docs` і `search_docs` сервера `astro-docs` для
нього різні інструменти.

## Пошук за змістом

Типово сервер шукає по словах (BM25), і запит тоді мусить вживати слова шуканого розділу. Документація React — проза,
і питають її своїми словами: «як не перерендерювати дочірній компонент» мало що дасть по словах, а за змістом
приведе до `memo`. Тому для цього примірника пошук за змістом радимо:

```
./df react vectors                       # підняти Qdrant і залити колекцію docs-react
./df react status                        # стан бази
```

Фрагментів тут у кілька разів більше, ніж в ecmascript, тож перший рахунок векторів займає години CPU, а не
хвилини; перерваний запуск не пропадає, а далі рахується лише нове й змінене.

## Оновлення корпусу

Покроковий порядок для цього примірника — у [UPDATE.md](UPDATE.md): регулярна перевірка, нові й змінені документи,
докачування недотягнутого, перехід на нову версію React без втрати тексту попередньої, ліміт GitHub і повний аудит.
Коротко:

```
./df react check                         # переліки всіх незаморожених джерел: що з'явилося, що зникло
./df react check --deep react-19 react-blog react-changelog react-releases react-versions   # тексти живих джерел
./df react refresh --missing             # докачати відсутнє, нічого не перезаписуючи
./df react refresh <файл…>               # перезаписати змінене — поіменно
./df react manifest                      # перегенерувати паспорт
./df react vectors                       # дорахувати вектори — якщо ввімкнено пошук за змістом
```

Після цього — перезапуск `./df react serve`. Що тут інакше, ніж в ecmascript:

- **Заморожені знімки не питаються.** 37 джерел — документація на закріпленому тезі чи коміті (`"frozen": true` у
  `sources.json`). Їхній вміст змінитися не може, тож `check` і `refresh` звертаються до них, лише коли id названо в
  команді.
- **`check` без `--deep` звіряє лише переліки.** Чесний сигнал зміни тексту — сума, для якої сторінку треба
  завантажити, тож тексти звіряє `--deep`, і лише в названих джерелах.
- **Повільно навмисно.** Між будь-якими двома зверненнями — 5 секунд (`pause_sec` у `config.json`): звірка текстів
  живих джерел триває ~20 хвилин, `refresh` без імен — години. На відповіді 429 і 503 оновлювач чекає й пробує знову.
- **Ліміт GitHub.** Без ключа GitHub дозволяє 60 звернень до свого API на годину. Звичайна перевірка витрачає два
  (сторінки релізів), кожне назване заморожене джерело — ще одне. Файли з raw.githubusercontent.com під цей ліміт не
  підпадають.
- **Сироти не видаляються.** Сторінка, яку прибрали з сайту, — факт історії, і її файл лишається в корпусі.
- **Перерваний чи недотягнутий `refresh` не починають наново.** `./df react refresh --missing` докачає всі відсутні
  файли, не чіпаючи вже завантаженого; для замороженого джерела — з його id.

Загальний порядок апдейту фабрики — у [../../UPDATE.md](../../UPDATE.md).

## Межа захисту, коротко

Спосіб А дає повний захист — усі чотири шари навколо агента. Спосіб Б дає серверну оборону (розтяжка санітара плюс
вузький перелік інструментів), а клієнтські шари — відповідальність Claude Code. Посилання у відповідях агента
лишаються лише на react.dev, reactjs.org і github.com (поле `answer_hosts`).

І межа самого корпусу: документація каже, як React задуманий і описаний у кожній версії, а не як поводиться конкретна
збірка. Next.js, React Native, Redux та інших проєктів на React тут немає — лише згадки про них у самій документації.
