# react — як перевіряти й оновлювати корпус

Загальний порядок апдейту будь-якого примірника — звірка, завантаження, паспорт, вектори, перезапуск, перевірки —
описаний у [../../UPDATE.md](../../UPDATE.md) і тут не повторюється. Цей довідник — про те, чим відрізняється React.

Корпус `react` тримає не одну редакцію документації, а всю її історію: від першого публічного коміту до поточної
версії. Звідси головне правило кожного оновлення — **нічого з уже зібраного не втратити**. Нагорі сторінку можуть
переписати, розділ застарілого API — прибрати, сайт — перевести на нову мажорну версію, а корпус мусить і далі знати,
як це було описано раніше. Кожен розділ нижче каже, що саме робити, щоб так і лишилося.

## Словник

- **нагорі** — офіційні сайти й репозиторії, записані в `sources.json`; у `corpus/` — наша копія.
- **живе джерело** — те, що змінюється постійно: поточна документація react.dev, його блог, `CHANGELOG.md`, релізи на
  GitHub і сторінка версій.
- **архівне джерело** — сайт старої мажорної версії: 18.react.dev, legacy.reactjs.org, 17.reactjs.org, 16.reactjs.org
  та архів старого блогу. Офіційно ці сайти не оновлюються, але це лише обіцянка: сторінку там можуть виправити або
  прибрати. Тому архівні звіряються так само, як живі, тільки рідше.
- **заморожене джерело** — запис із `"frozen": true`: знімок документації на закріпленому тезі (`v15.6.2`) чи
  повному SHA коміту. Змінитися він не може за визначенням: тег і коміт назавжди вказують на ті самі байти. Тому
  `check` і `refresh` такого джерела не питають, доки його id не назвати в команді явно.
- **знімок** — документація на момент виходу версії, взята з історії репозиторію, з якого збирався сайт.
- **сирота** — файл у `corpus/`, якого нагорі за його джерелом уже немає.
- **шапка** — перші рядки кожного документа з `#`: назва, адреса, дата завантаження і `# версія:`.

## Регулярна перевірка

Коли: раз на місяць і обов'язково тоді, коли в блозі React з'явився анонс нового релізу. Нічого з цього не пише в
корпус.

```
git status instances/react/corpus        # 0. корпус закомічений: переписаним текстам є куди відкотитися
./df react check                         # 1. переліки всіх незаморожених джерел: ~2 хв, 2 звернення до GitHub API
./df react check --deep react-19 react-blog react-changelog react-releases react-versions
                                         # 2. тексти живих джерел: ~20 хв
```

Раз на пів року — ще й тексти архівних:

```
./df react check --deep react-18 react-18-legacy react-17 react-16 react-blog-legacy     # ~45 хв
```

Що робить кожен крок:

0. **`git status`.** `refresh` перезаписує файл новим текстом, і попередній лишається лише в історії git. Якщо в
   корпусі є незакомічені зміни, їх спершу треба закомітити, інакше перший же перезапис зітре їх безслідно.
1. **`check` без імен** питає кожне незаморожене джерело, що в нього є зараз, і порівнює з файлами. Показує нові
   документи й сироти, але не тексти: одна адреса сайту не описує сотні його сторінок, і щоб порівняти текст, сторінку
   треба завантажити.
2. **`check --deep` з іменами** завантажує й порівнює тексти **лише названих** джерел; решта цього разу не
   питається, і підсумок скаже, скільки файлів лишилося без звірки. Порівнюється сума тексту без шапки, тож
   повторне завантаження того самого тексту зміною не вважається.

Вивід зручно зберегти: `./df react check 2>&1 | tee instances/react/out/check-$(date +%F).log`. Тека `out/` у git не
потрапляє.

## Як читати вивід

| Рядок | Що означає | Що робити |
|---|---|---|
| `── Заморожених джерел не питаю: 37 ──` | норма: знімки не звіряються | нічого |
| `+ новий: react-19--reference-react-….txt` | нова сторінка, пост, версія CHANGELOG чи реліз — або документ, який минулого разу не дотягнули | «Звичайне оновлення» |
| `+ новий: react-changelog--19.4.0.txt` чи `react-releases--v20.0.0.txt` з новою мінорною чи мажорною версією | вийшла нова версія React | спершу «Нова версія React», потім решта |
| `~ змінився: …` | текст нагорі розійшовся з нашим (лише з `--deep`) | «Звичайне оновлення», поіменно |
| `── Сироти … ──` | нагорі сторінки вже немає | нічого: у цьому примірнику сироти не видаляються, див. нижче |
| `── Невідомо … ──` | джерело не відповіло, тож про свої файли думки не має | повторити звірку пізніше |
| `не вдалось спитати джерело: … HTTP 403` або `429` на api.github.com | вичерпано ліміт GitHub API | «Ліміт GitHub API» |
| `не вдалось спитати джерело: …` з іншою причиною | сайт недоступний або змінив розмітку | повторити; не минає — читача треба правити |

## Звичайне оновлення: нові й змінені документи

```
git status instances/react/corpus                       # чисто — можна починати
./df react refresh --missing                            # нові документи всіх незаморожених; наявних не чіпає
./df react refresh react-19--reference-react-useeffect.txt react-blog--2026-10-01-react-labs.txt
                                                        # змінені — поіменно, як їх назвав check
./df react manifest                                     # паспорт: без нього наступний check покаже все як змінене
./df react vectors                                      # вектори лише нового й зміненого
# Ctrl+C у терміналі з serve, і знову: ./df react serve
./df react smoke                                        # число фрагментів — ../../UPDATE.md, крок 6
git add instances/react/corpus && git commit            # новий стан корпусу — в історію
```

Правила:

- **Змінене — завжди поіменно.** `refresh` без імен перекачує всі незаморожені джерела (~1300 документів, близько
  двох годин), а `refresh react-19` — усі 178 сторінок react.dev. Обидва варіанти перезапишуть і те, що не
  змінилося. Ім'ям може бути ім'я файла (`react-19--learn.txt`) або id документа (`react-19/learn`).
- **`--missing` нічого не перезаписує.** Він пише лише файли, яких у `corpus/` немає, тож безпечний завжди. З
  іменами джерел (`refresh --missing react-blog`) питає лише названі.
- **Попередній текст зміненої сторінки лишається в git.** Сервер шукає лише в поточному корпусі, а колишнє
  формулювання дістається з історії:

  ```
  git log -p -- instances/react/corpus/react-19--reference-react-useeffect.txt    # як змінювався текст
  git show <коміт>:instances/react/corpus/react-19--reference-react-useeffect.txt # текст на тому коміті
  ```

  Для правок усередині однієї версії цього досить: це та сама документація, виправлена. Перехід на нову версію —
  інша справа, і для нього є окремий розділ.

## Недотягнуте: збої завантаження

Сторінка може не завантажитися: сайт на хвилину впав, GitHub вичерпав ліміт, читач не впізнав розмітку. Механізм
цього не губить:

1. Під час `refresh` такий документ друкується рядком `збій:` і не записується. Наявний файл, якщо він був,
   лишається як був.
2. Відсутній файл наступний `check` покаже як `+ новий`: для звірки «не дотягнули» і «з'явилося» — те саме.
3. `./df react refresh --missing` докачає всі відсутні документи незаморожених джерел, нічого не перезаписуючи.
4. Для замороженого джерела його треба назвати: `./df react check react-15.3` покаже, чого бракує, а
   `./df react refresh --missing react-15.3` докачає.

Якщо той самий документ дає `збій` знову й знову з причиною «немає назви» чи «тіло куце», повтор не допоможе: сторінка
має незвичну форму, і правити треба читача в `engine/readers/`. Після виправлення — `refresh <ім'я документа>`.

Знайти всі збої в збереженому виводі: `grep 'збій' instances/react/out/refresh-….log`. Перше слово рядка — ім'я
файла, і його можна одразу підставити в `refresh`.

## Нова версія React

Сигнали: `check` показує `+ новий` з новою версією в `react-changelog` чи `react-releases`, у блозі — анонс, а
`check --deep` — `~ змінився` на сторінці версій.

**Порядок тут головне.** `react-19` — це «поточна документація react.dev», і наступне його оновлення перезапише
текст 19.3 текстом нової версії. Щоб 19.3 не зникла з корпусу, спершу її стан закріплюється замороженим знімком, і
лише потім живе джерело переходить на нову версію. Навпаки не можна: перезаписаний текст повернеться хіба з git, а
сервер його там не бачить.

Зайвого шуму знімок у відповідях не додає: однаковий текст сторінки в 19.3 і 19.4 не дублюється, фрагмент лишається
один, а в полі `versions` у нього стоять обидві версії. Знімок коштує місця на диску, а не якості пошуку.

### Нова мінорна версія (наприклад, 19.3 → 19.4)

1. **Корпус закомічений:** `git status instances/react/corpus` чистий.
2. **Дата виходу попередньої мінорної.** Вона стоїть у назві документа CHANGELOG, наприклад, у рядку шапки
   `instances/react/corpus/react-changelog--19.3.0.txt`: «React CHANGELOG: 19.3.0 (…)». Знімки всіх попередніх ліній
   узято на кінець дня виходу `.0` — так само робиться і цей.
3. **SHA коміту репозиторію сайту на кінець цього дня.** Одне звернення до GitHub API, вручну, поза `df`:

   ```
   curl -s "https://api.github.com/repos/reactjs/react.dev/commits?sha=main&until=РРРР-ММ-ДДT23:59:59Z&per_page=1" \
     | grep -m1 '"sha"'
   ```

   Той самий коміт видно й у браузері: `https://github.com/reactjs/react.dev/commits/main/?until=РРРР-ММ-ДД` —
   найверхній у списку. Потрібен повний SHA, усі 40 символів.
4. **Запис знімка в `sources.json`** — поруч із `react-19.2`, за його зразком; змінюються SHA (двічі), версія, дата
   й тексти:

   ```json
   {
     "id": "react-19.3",
     "url": "https://api.github.com/repos/reactjs/react.dev/git/trees/<SHA>?recursive=1",
     "reader": "ghdocs",
     "version": "19.3.0",
     "frozen": true,
     "root": "src/content",
     "recursive": true,
     "folders": ["src/content/learn", "src/content/reference"],
     "within": ["https://raw.githubusercontent.com/reactjs/react.dev/<SHA>/src/content/"],
     "title": "React 19.3 documentation (react.dev repository, РРРР-ММ-ДД)",
     "added": "<сьогодні>",
     "note": "Проміжний знімок: Learn і Reference на кінець дня виходу 19.3.0."
   }
   ```

5. **Завантажити знімок:** `./df react refresh react-19.3` — близько 180 документів, ~15 хв, одне звернення до GitHub
   API. Заморожене джерело тут назване, тож воно питається. Перевірити, що збоїв немає, а якщо є — розділ
   «Недотягнуте».
6. **Лише тепер — живе джерело.** У записі `react-19` поміняти `version` на `19.4` і в `title` — «React 19.4
   documentation (react.dev)».
7. **Перезаписати react.dev повністю:** `./df react refresh react-19` (~15 хв). Саме повністю, а не лише змінене:
   версія записана в шапці кожного документа, а звірка шапки не бачить. Без повного перезапису незмінені сторінки
   лишилися б підписаними «19.3», і на питання «як зараз» пошук відповідав би старою версією.
8. **Решта нового:** `./df react refresh --missing` (нові записи CHANGELOG, релізи, пости) і
   `./df react refresh react-versions` (сторінка версій змінилася).
9. **Тексти, що називають версії,** — вручну:
   - `prompts/loaded.txt`: «react.dev (19.3)» і перелік проміжних ліній «19.0-19.2»;
   - `README.md` цього примірника: вступ («до поточної 19.3») і таблиця «Звідки документація»;
   - `checks.json`: кількість фрагментів і цілі перевірок, якщо вони стосуються версій.
10. **Далі як завжди:** `manifest`, `vectors`, перезапуск `serve`, `smoke`, коміт.

### Нова мажорна версія (наприклад, 19 → 20)

Досі react.dev щоразу переходив на нову мажорну, а документацію попередньої переносив на архівний піддомен: так
з'явився 18.react.dev. Кроки 1–5 мінорної — ті самі: знімок останньої мінорної лінії 19.x на кінець дня її виходу.
Далі інакше:

6. **Знайти архів 19 і з'ясувати, як він зібраний.** Адресу архіву дає https://react.dev/versions. Чи віддає архів
   markdown, показує `curl -sI https://19.react.dev/llms.txt`:
   - `200` — читач `llms`, як у react.dev;
   - немає, але сторінки мають `__NEXT_DATA__` — читач `nextdata`, як у `react-18`;
   - ні те, ні те — потрібен новий читач, і це окрема робота **до** оновлення. Поки її не зроблено, живе джерело не
     чіпати: воно тримає останній текст 19.
7. **Новий запис `react-20`** — поточна документація: копія нинішнього запису `react-19` з `"id": "react-20"`,
   `"version": "20.0"`, новою назвою і тими самими `url` та `within` react.dev.
8. **Запис `react-19` переходить на архів:** `url`, `reader` і `within` — адреси архіву за зразком `react-18`,
   `version` — остання 19.x.y з CHANGELOG, назва — з архівною адресою. Id лишається `react-19`: імена файлів ті самі,
   тож незмінений текст не стає сиротою, а лише отримує остаточну версію лінії.
9. **Завантажити обидва:** `./df react refresh react-19 react-20` (~30 хв). Архів перезаписує файли `react-19--*`,
   react.dev пишеться в нові `react-20--*`. Сироти `react-19--*` — сторінки, яких в архіві немає, — лишаються.
10. **Тексти** — як у п. 9 мінорної. Ще `answer_hosts` у `config.json`, якщо архів переїхав на новий домен, а в
    `README.md` цього примірника — рядок таблиці для архіву.
11. **Далі як завжди:** `refresh --missing`, `refresh react-versions`, `manifest`, `vectors`, перезапуск `serve`,
    `smoke`, коміт.

### Пре-релізи і Canary

Окремих дій не потрібно. Пре-релізи приходять у `react-releases` як `+ новий`. Сторінки можливостей, доступних лише в
Canary, react.dev публікує разом зі стабільними, з позначкою «Canary» в тексті, тож вони приходять як нові документи
`react-19`.

## Сироти в React не видаляються

Сторінку з react.dev прибирають, коли API застаріває, перейменовується або переїжджає. Для історії це факт, а файл
сироти — єдине місце, де лишився її текст. У шапці він несе версію, при якій його завантажено, тож пошук і далі
відповість, як це було описано тоді.

Тому в цьому примірнику сироти не видаляються ніколи. Навіть дубль після перейменування сторінки шкоди не робить:
однаковий текст у пошуку зливається в один фрагмент. `check` щоразу друкуватиме таких сиріт — це очікувано. Команди
фабрики самі нічого не видаляють: ні `check`, ні `refresh`, ні `vectors`.

## Коли змінився читач

Якщо поправили читача в `engine/readers/`, уже завантажені документи лишаються зібраними старим кодом. Перезібрати
їх — `refresh` з іменами джерел цього читача. Для заморожених джерел теж, назвавши їх; не більше двадцяти за годину
через ліміт GitHub. Перезбирання зачіпає лише розбір: вміст знімка той самий, змінюється тільки те, як його прочитано.

## Ліміт GitHub API

- Без ключа GitHub дозволяє 60 звернень до свого API на годину з однієї IP-адреси. Ліміт скидається щогодини.
- Через API йдуть: перелік кожного знімка на GitHub (дерево тегу чи коміту) — 1 звернення; релізи — 2 сторінки;
  перший коміт — 1. Самі тексти беруться з raw.githubusercontent.com і під ліміт не підпадають.
- Звичайна перевірка (`check` без імен) — 2 звернення. Кожне назване заморожене джерело — ще одне: усі 37 разом з
  іншою роботою за одну годину не вмістяться, тож їх ділять на дві години.
- Скільки лишилося: `curl -s https://api.github.com/rate_limit` — поле `core.remaining`; `core.reset` — час скидання
  в секундах Unix.
- Вичерпаний ліміт GitHub віддає як `HTTP 403` або `429`. На `429` оновлювач сам чекає й повторює; на `403` рахує
  збій джерела й іде далі. В обох випадках досить дочекатися скидання й повторити ту саму команду; для `refresh`
  краще з `--missing`, щоб не перекачувати вже записане.

## Повний аудит корпусу

Раз на рік або після великої правки читачів варто перевірити, що заморожені знімки зібрані повністю. Звірка
переліку показує відсутні файли як `+ новий`, а тексти знімків не завантажує. Дві команди — у різні години, через
ліміт GitHub:

```
./df react check react-0.3 react-0.4 react-0.5 react-0.8 react-0.9 react-0.10 react-0.11 react-0.12 react-0.13 \
  react-0.14 react-15.0 react-15.1 react-15.2 react-15.3 react-15.4 react-15.5 react-15.6 react-16.0 \
  react-initial-commit
./df react check react-16.1 react-16.2 react-16.3 react-16.4 react-16.5 react-16.6 react-16.7 react-16.8 react-16.9 \
  react-16.10 react-16.11 react-16.12 react-16.13 react-18.0 react-18.1 react-19.0 react-19.1 react-19.2
```

Показав `+ новий` — `./df react refresh --missing <ті самі id>`, теж у межах ліміту.

Окремо — архівні сайти на Gatsby (`react-18-legacy`, `react-17`, `react-16`). Їхній перелік — меню сайту плюс поле
`pages`: сторінки, живі на сайті, але прибрані з меню (`legacy-context`, `warnings/*`, Concurrent Mode). Мапи сайту
там немає, тож нову сторінку поза меню `check` не помітить. Знаходиться вона звіркою імен: сторінки знімка тієї самої
лінії (`react-18.1` для `react-18-legacy`, `react-16.13` і `react-18.0` для `react-17`, `react-16.13` для
`react-16`), яких немає на сайті, перевіряються на сайті адресою
`https://<сайт>/page-data/<тека>/<сторінка>.html/page-data.json`. Відповіла `200` — адреса сторінки додається в
`pages`, далі `refresh --missing <id сайту>`. Відповіла `404` — сторінку з сайту прибрано, і її текст лишається лише в
знімку.
