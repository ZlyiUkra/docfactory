# Лекція. День 3. Функції та замикання

Ця лекція пояснює механізм, на якому тримається більша частина роботи з React: як функція знаходить змінні, коли її
викликають. Читання займе близько 40 хвилин. Кожен приклад на JavaScript запущено на Node 24, а під ним наведено
справжній вивід. Приклади навмисно інші, ніж у теорії й завданнях дня: механізм той самий, а завдання лишаються за
вами.

**Після лекції ви зможете пояснити:**

- чому функція читає змінну іншої функції, яка вже завершилася;
- чому функція шукає змінні там, де її створили, а не там, де її викликали;
- чому функція бачить зміну змінної, зроблену після створення функції, і коли такої зміни не може бути;
- чому в циклі з `var` усі функції бачать те саме число, а в циклі з `let` кожна бачить своє;
- чому обробник у React бачить значення того виклику компонента, у якому його створили, і що робити, коли потрібне
  найновіше значення.

## Кнопка, яка бачить минуле

Уявіть сторінку замовлення в інтернет-крамниці. Покупець вибрав доставку до Києва й натиснув «Замовити». Кнопка чекає
три секунди, щоб покупець міг передумати, і за цей час він перемикає місто на Львів. Куди піде замовлення?

У типовому коді на React воно піде до Києва. Функція, яка спрацює через три секунди, прочитає місто, вибране в мить
натискання, хоча на екрані вже написано «Львів». Для такої кнопки це зрозуміла поведінка, бо покупець натискав, коли
бачив Київ.

Тепер інша частина тієї самої сторінки: годинник, який щосекунди додає одиницю до числа на екрані. Такий самий код тут
дає помилку. Число доходить до 1 і далі не росте, бо щосекунди функція бере те саме старе число 0 і додає до нього
одиницю.

Обидва випадки визначає правило самої мови JavaScript. Без нього залишається вгадувати: то «функція прочитає поточне
значення», то «функція запам'ятала старе значення». Обидві фрази неточні. Далі в нас з'явиться правило з двох
запитань, за яким результат можна передбачити до запуску.

## Функція — це значення

Число можна покласти в змінну, передати іншій функції й повернути з функції. З функцією в JavaScript можна робити те
саме:

```js
function double(n) {
  return n * 2;
}
const square = (n) => n * n;

console.log(typeof double, typeof double(4));

function applyTwice(f, x) {
  return f(f(x));
}
console.log(applyTwice(square, 3));
```

```text
function number
81
```

Пройдемо код по порядку:

- `function double(n) { ... }` — це **оголошення функції**. Воно створює функцію й водночас змінну `double`, яка на
  неї вказує.
- `const square = (n) => n * n` — це **стрілкова функція**, або просто стрілка. Якщо після `=>` стоїть вираз без
  фігурних дужок, функція повертає значення цього виразу. Є ще запис `const f = function (n) { ... }`, який працює так
  само для всього, про що йдеться в лекції.
- `typeof double` дає `function`, а `typeof double(4)` дає `number`. Ім'я без дужок означає саму функцію, а дужки її
  викликають. Тому `setTimeout(f, 100)` передає таймеру функцію, а `setTimeout(f(), 100)` викликає її негайно й
  передає таймеру результат.
- `applyTwice(square, 3)` передає функцію `square` без дужок. Усередині вона викликається двічі: спершу 3 × 3 = 9,
  потім 9 × 9 = 81. Функцію, яку передають іншій функції, щоб та викликала її пізніше, називають **колбеком**
  (англійською callback, «зворотний виклик»). Обробник натискання і функція в таймері є колбеками.

Ще одна річ знадобиться далі. **Параметр**, тобто `n` у `double(n)`, є звичайною змінною, яку JavaScript створює
заново при кожному виклику.

## Де функція шукає змінну

Функція може лежати всередині іншої функції:

```js
const city = "Київ";

function order() {
  const item = "чай";

  function label() {
    const qty = 2;
    return qty + " × " + item + ", доставка: " + city;
  }

  return label();
}

console.log(order());
console.log(typeof item, typeof qty);
```

```text
2 × чай, доставка: Київ
undefined undefined
```

Функція `label` прочитала три імена, хоча оголошене в ній лише одне: `qty` лежить у ній самій, `item` у функції
навколо неї, а `city` у файлі. Другий рядок виводу показує зворотний бік: поза функцією `order` її змінних не видно.
Оператор `typeof` для неоголошеного імені повертає рядок `undefined` і не кидає помилки, тому ним зручно це
перевіряти.

Частину коду, у якій ім'я доступне, називають **областю видимості**. Внутрішній код бачить зовнішні імена, а зовнішній
код не бачить внутрішніх. Область видимості створює функція, а для `let` і `const` її створює ще й блок, тобто пара
фігурних дужок.

Тепер головне запитання: коли функцію викликають з іншого місця, де вона шукає зовнішні імена?

```js
const currency = "грн";

function price(n) {
  return n + " " + currency;
}

function foreignShop() {
  const currency = "EUR";
  return price(5);
}

console.log(foreignShop());
```

```text
5 грн
```

Функцію `price` викликано зсередини `foreignShop`, де є власна змінна `currency` зі значенням `EUR`. Проте `price` її
не бачить, бо створена на верхньому рівні файла й шукає `currency` там. Місце виклику на пошук не впливає.

Таке правило називають **лексичною областю видимості**. Слово «лексична» означає «визначена текстом програми»: щоб
дізнатися, яку змінну бачить функція, досить подивитися, куди вона вкладена в коді. Якби пошук залежав від місця
виклику, функцію не можна було б зрозуміти окремо від решти програми.

## Механізм: створення, виклик, пошук, завершення

Нам потрібне одне нове слово. **Оточення** — це таблиця «ім'я → змінна», яка існує під час роботи програми й
відповідає одній області видимості. Кожне оточення має посилання на зовнішнє оточення. Специфікація мови називає таку
таблицю Environment Record, а MDN пише lexical environment. Усе далі складається з чотирьох дій.

**Створення функції.** Коли виконання доходить до коду функції, JavaScript створює об'єкт функції й записує в нього
посилання на оточення, яке діє саме зараз. У специфікації це внутрішнє поле називається `[[Environment]]`. Подвійні
дужки означають, що поле існує лише в описі мови, а з коду його не прочитати. Записується посилання на оточення, а не
копія змінних.

**Виклик функції.** JavaScript створює нове оточення й кладе туди параметри та змінні цього виклику. Зовнішнім для
нового оточення стає те, яке записане в полі `[[Environment]]` функції. Оточення того, хто викликав, не бере участі, і
саме тому `price` не побачила `EUR`. Звідси також випливає, що кожен виклик має власні змінні.

**Пошук імені.** Коли код читає ім'я, JavaScript шукає його в поточному оточенні, потім у зовнішньому, потім у
зовнішньому для зовнішнього. Пошук зупиняється на першому знайденому імені, тому внутрішня змінна приховує зовнішню з
тим самим ім'ям. Це називають **затіненням**. Якщо імені немає ніде, читання кидає `ReferenceError`.

**Завершення виклику.** Коли функція повернула результат, її оточення не знищується автоматично. Воно залишається,
доки на нього хтось посилається, наприклад функція, створена під час цього виклику. Коли посилань більше немає,
пам'ять звільняє **збирач сміття**, тобто частина рушія, яка прибирає недосяжні дані. **Рушій** — це програма, яка
виконує JavaScript.

Тепер можна дати означення. **Замикання** — це функція разом із оточенням, у якому її створили. Воно не потребує
особливого синтаксису й виникає при кожному створенні функції. Функція `price` теж є замиканням, просто різницю
помітно лише тоді, коли функція переживає виклик, який її створив, або читає змінну, яка змінюється.

Оточення є моделлю зі специфікації. Рушій може зберігати дані в пам'яті інакше, якщо програма не здатна помітити
різниці.

## Приклад із числами: два податки

Функція `makeTax` приймає відсоток і повертає функцію, яка додає цей податок до ціни. Функцію, яка створює й повертає
інші функції, називають **фабрикою функцій**.

```js
function makeTax(percent) {
  return function (price) {
    return price + (price * percent) / 100;
  };
}

const withVat = makeTax(20);
const withLowVat = makeTax(7);

console.log(withVat(100));
console.log(withLowVat(100));
```

```text
120
107
```

| Крок | Що відбувається | Що змінюється |
|------|-----------------|---------------|
| 1 | Викликано `makeTax(20)` | Створено оточення А: `percent = 20`. Нова функція запам'ятала А |
| 2 | `makeTax` завершилась | Функція лежить у `withVat`, тому оточення А живе |
| 3 | Викликано `makeTax(7)` | Створено оточення Б: `percent = 7`. Друга функція запам'ятала Б і лежить у `withLowVat` |
| 4 | Викликано `withVat(100)` | Створено оточення В: `price = 100`, зовнішнє для нього — А |
| 5 | Пошук імен | `price` знайдено у В, `percent` у В немає, а в А є 20. Результат: 100 + 20 = 120 |
| 6 | Викликано `withLowVat(100)` | Створено оточення Г: `price = 100`, зовнішнє — Б. Результат: 100 + 7 = 107 |

Оточення В і Г ніхто не тримає, тому після своїх викликів вони стають недосяжними. Оточення А й Б живуть, доки живуть
функції:

```text
файл:          makeTax, withVat, withLowVat
                  ^                   ^
                  | зовнішнє          | зовнішнє
оточення А:   percent = 20     оточення Б:   percent = 7
                  ^                   ^
                  | запам'ятала       | запам'ятала
функція в withVat              функція в withLowVat
```

Текст обох функцій той самий, а оточення різні, і саме оточення дають дві різні поведінки.

## Кілька функцій на одне оточення: гаманець

Функції можуть і змінювати змінну з оточення. Якщо кілька функцій створено під час одного виклику, у них спільне
оточення:

```js
function makeWallet(start) {
  let balance = start;
  return {
    pay(sum) {
      if (sum > balance) return "бракує коштів";
      balance = balance - sum;
      return "сплачено";
    },
    left() {
      return balance;
    },
  };
}

const mine = makeWallet(100);
const yours = makeWallet(500);

console.log(mine.pay(30), mine.left(), yours.left());
console.log(mine.pay(200), mine.left());
console.log(mine.balance);
```

```text
сплачено 70 500
бракує коштів 70
undefined
```

Запис `pay(sum) { ... }` усередині об'єкта створює властивість `pay`, значенням якої є функція. Два виклики
`makeWallet` створили два оточення зі своїми змінними `balance`, тому витрата з `mine` не вплинула на `yours`. Функції
`pay` і `left` гаманця `mine` мають одне оточення, тому `left` прочитала 70, яке записала `pay`. Останній рядок дає
`undefined`, бо `balance` лежить в оточенні, а не в об'єкті. Змінити суму в обхід перевірки в `pay` неможливо, тобто
замикання дало функціям приватні дані.

## Функція тримає змінну, а не значення

Ось найкоротший приклад головної думки цього дня:

```js
let city = "Київ";
const whereTo = () => city;

console.log(whereTo());
city = "Львів";
console.log(whereTo());
```

```text
Київ
Львів
```

Функція `whereTo` не зберегла рядок «Київ», коли її створили. Вона зберегла посилання на оточення, де лежить змінна
`city`, а значення читає при кожному виклику. Тепер маємо обіцяне правило. Щоб передбачити, що побачить функція, дайте
відповідь на два запитання:

1. **Яку саме змінну вона читає?** Подивіться, де функцію створили, і пройдіть назовні до першого оголошення цього
   імені. Якщо цей код виконувався кілька разів, з'ясуйте, під час якого виконання функцію створили.
2. **Що лежить у цій змінній у мить виклику функції?** Подивіться, хто й коли записує в цю змінну.

**Коли функцію викликає таймер.** Таймер викликає функцію пізніше, ніж її створили:

```js
let city = "Київ";

setTimeout(() => {
  console.log("таймер читає:", city);
}, 10);

city = "Львів";
console.log("код дійшов до кінця");
```

```text
код дійшов до кінця
таймер читає: Львів
```

Виклик `setTimeout(f, ms)` не зупиняє програму й не викликає `f` сам. Він просить середовище, тобто браузер або Node,
викликати `f` не раніше ніж через `ms` мілісекунд, і одразу повертає керування. Коли час минув, середовище ставить
виклик у чергу завдань. JavaScript не перериває поточний код: наступне завдання починається лише тоді, коли поточне
дійшло до кінця. Тому затримка 0 означає «після всього, що вже виконується», а не «зараз». Докладно про чергу йдеться
в дні 5. За нашими двома запитаннями: функція читає єдину змінну `city`, а в мить спрацювання в ній уже «Львів».

**Коли змінна щоразу нова.** Функція бачить незмінне значення лише тоді, коли в її змінну більше ніхто не пише. Цього
найпростіше досягти, якщо кожне значення отримує власну змінну:

```js
function remember(value) {
  return () => value;
}

let city = "Київ";
const first = remember(city);
city = "Львів";

console.log(first(), city);
```

```text
Київ Львів
```

Виклик `remember` створює нову змінну `value` і копіює туди значення, яке передали. Далі `value` і `city` не
пов'язані. Функція `first` читає `value`, а туди більше ніхто не пише. Саме таку поведінку називають **знімком**. Це
не окремий механізм мови, а наслідок того, що нову змінну ніхто не змінює.

**Коли в змінній об'єкт.** Тут знімок має межу, яку пояснює перший день: у змінній лежить посилання на об'єкт, а не
сам об'єкт.

```js
function remember(value) {
  return () => value;
}

const order = { city: "Київ" };
const snapshot = remember(order);

order.city = "Львів";
console.log(snapshot().city);
```

```text
Львів
```

Змінна `value` вказує на той самий об'єкт, а сам об'єкт змінено через іншу змінну. Тому React просить замінювати
об'єкти в стані новими: інакше старий знімок перестане бути знімком.

## Цикл: скільки змінних створено

Цикл працює за тим самим правилом, а різниця лише в кількості створених змінних. Зробимо кнопки ліфта: кожен прохід
циклу додає до масиву функцію, яка каже, куди їхати.

```js
const buttons = [];
for (var floor = 1; floor <= 3; floor++) {
  buttons.push(() => "їдемо на поверх " + floor);
}
console.log(buttons[0]());
console.log(buttons[2]());
console.log("floor після циклу:", floor);
```

```text
їдемо на поверх 4
їдемо на поверх 4
floor після циклу: 4
```

Ключове слово `var` оголошує змінну на всю функцію або на весь файл, а блоки для нього нічого не значать. Тому змінна
`floor` одна, і всі три функції тримають те саме оточення. Цикл зупиняється, коли `floor` дорівнює 4, а функції
викликано вже після циклу. Заміна одного слова змінює результат:

```js
const buttons = [];
for (let floor = 1; floor <= 3; floor++) {
  buttons.push(() => "їдемо на поверх " + floor);
}
console.log(buttons[0]());
console.log(buttons[2]());
console.log("floor після циклу:", typeof floor);
```

```text
їдемо на поверх 1
їдемо на поверх 3
floor після циклу: undefined
```

Цикл `for` обробляє `let` у своєму заголовку особливо: кожен прохід отримує власне оточення зі своєю змінною.

| Момент | Що робить JavaScript | `floor` |
|--------|----------------------|---------|
| Початок циклу | Створює змінну в початковому оточенні | 1 |
| Перед першою перевіркою | Створює оточення проходу й копіює туди значення | 1 |
| Перший прохід | Тіло: функція запам'ятала це оточення | 1 |
| Кінець проходу | Створює нове оточення й копіює туди значення | 1 |
| Перед другим проходом | `floor++` змінює змінну вже нового оточення | 2 |
| Останній прохід завершено | Нове оточення, копія, `floor++`, перевірка `4 <= 3` хибна | 4 |

Головне тут те, що `floor++` виконується вже після копіювання, тому не торкається змінної попереднього проходу. Звідси
два випадки, де легко помилитися:

```js
const outside = [];
let shared = 1;
for (; shared <= 2; shared++) {
  outside.push(() => shared);
}
console.log("let поза заголовком:", outside.map((f) => f()));

const changed = [];
for (let i = 0; i < 3; i++) {
  changed.push(() => i);
  i++;
}
console.log("зміна в тілі циклу:", changed.map((f) => f()));
```

```text
let поза заголовком: [ 3, 3 ]
зміна в тілі циклу: [ 1, 3 ]
```

Особлива обробка стосується лише заголовка `for`. Змінна `shared` оголошена перед циклом, тому вона одна, як із `var`.
У другому циклі функція тримає змінну проходу, а не число на початку проходу. У першому проході `i` спершу 0, а потім
тіло записало в ту саму змінну 1, тому функція читає 1. Копія 1 переходить далі, `i++` робить її 2, а тіло другого
проходу записує 3.

## Типові хибні уявлення

**«Замикання виникає лише тоді, коли функцію повертають із іншої функції».** Кожна функція запам'ятовує своє оточення
при створенні. Повернення лише робить це помітним.

**«Функція запам'ятовує значення змінної на момент створення».** Вона запам'ятовує оточення, а значення читає в мить
виклику, як показала функція `whereTo`.

**«Функція завжди читає поточне значення».** Ця фраза пропускає запитання, яку саме змінну читає функція. Якщо
викликів було багато, змінних теж багато, і функція читає свою.

**«`const` робить знімок».** `const` лише забороняє записати в змінну нове значення. Об'єкт у ній можна змінити, і
функція це побачить.

## Як це проявиться в React

**Компонент** у React є звичайною функцією, яка повертає опис інтерфейсу. **Рендер** означає, що React викликав цю
функцію. Стан зберігається всередині самого React, а кожен виклик компонента отримує поточне значення у власну нову
змінну.

Цей механізм можна відтворити без React. Нижче дуже спрощена модель: стан лежить у змінній `stored` поза компонентом,
а `setStored` записує нове значення й одразу викликає компонент знову. Справжній React складніший, зокрема об'єднує
кілька оновлень в один рендер, але на замикання це не впливає.

```js
let stored = 0;
let screen;

function setStored(next) {
  stored = typeof next === "function" ? next(stored) : next;
  render();
}

function Cart() {
  const qty = stored;
  return {
    text: "у кошику " + qty,
    add: () => setStored(qty + 1),
    addSafely: () => setStored((previous) => previous + 1),
    showLater: () => setTimeout(() => console.log("таймер показав", qty), 10),
  };
}

function render() {
  screen = Cart();
  console.log(screen.text);
}

render();
const firstScreen = screen;

firstScreen.showLater();
screen.add();
screen.add();

firstScreen.add();
firstScreen.add();

firstScreen.addSafely();
firstScreen.addSafely();
```

```text
у кошику 0
у кошику 1
у кошику 2
у кошику 1
у кошику 1
у кошику 2
у кошику 3
таймер показав 0
```

Кожен виклик `Cart` створює нову змінну `qty` і нові функції, які її тримають. Змінна `firstScreen` зберігає результат
першого рендеру, тобто імітує обробник, який ще живий після нових рендерів.

| Дія | `qty` у функції | Запис у `stored` | Вивід |
|-----|-----------------|------------------|-------|
| Перший рендер | 0 | 0 | у кошику 0 |
| `firstScreen.showLater()` | 0 | поставлено таймер | немає |
| Два виклики `screen.add()` на найновішому екрані | 0, потім 1 | 1, потім 2 | у кошику 1, у кошику 2 |
| Два виклики старого `firstScreen.add()` | 0 і 0 | 1 і 1, кошик зменшився | у кошику 1, двічі |
| Два виклики старого `firstScreen.addSafely()` | не читає | 2, потім 3 | у кошику 2, у кошику 3 |
| Таймер спрацював | 0 | без змін | таймер показав 0 |

Старий обробник читає змінну свого рендеру, і нові рендери на неї не впливають. Обробник `addSafely` не читає старої
змінної, бо передає функцію: її викликає той, хто зберігає стан, і передає туди найновіше значення.

У справжньому React це виглядає так. Такий код потребує браузера або його імітації. Його поведінку описують глава
[`State as a Snapshot`](https://react.dev/learn/state-as-a-snapshot) і [довідка
`useState`](https://react.dev/reference/react/useState). Нижче наведено й наш запуск, а самі ви запустите цей код у
фазі 1:

```jsx
function Cart() {
  const [qty, setQty] = useState(0);

  function handleAddLater() {
    setTimeout(() => {
      setQty(qty + 1);
    }, 3000);
  }

  return <button onClick={handleAddLater}>Додати пізніше (зараз {qty})</button>;
}
```

Рядок з `useState` дає дві змінні цього рендеру: значення стану `qty` і функцію `setQty`, яка просить React про новий
рендер. Сама змінна `qty` після виклику `setQty` не змінюється. Якщо натиснути кнопку тричі за три секунди, усі три
таймери створено в тому самому рендері. Усі вони читають 0 і просять записати 1, тому на екрані буде 1, а не 3.

Перевіримо це запуском на React 19.3. Програма Vitest виконує файли, ім'я яких закінчується на `.test.tsx`, а перший
рядок файла просить її працювати в jsdom, тобто в імітації браузера всередині Node. Усі приклади React нижче лежать в
одному такому файлі, а компонент `Cart` стоїть у ньому одразу після імпортів. Функція `test` оголошує один дослід,
`render` малює компонент, а `fireEvent.click` клацає кнопку. Функція `act` просить React виконати всі оновлення стану,
які виникнуть, поки дослід чекає.

```tsx
// @vitest-environment jsdom
import { useEffect, useState } from "react";
import { act, fireEvent, render, screen } from "@testing-library/react";
import { test } from "vitest";

const wait = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

test("Cart: три клацання, поки таймери чекають", async () => {
  render(<Cart />); // перший рендер: qty дорівнює 0
  const button = screen.getByRole("button");
  console.log("до клацань:", button.textContent);

  // Між клацаннями стан не змінюється, тому всі три таймери створено в тому самому рендері.
  fireEvent.click(button);
  fireEvent.click(button);
  fireEvent.click(button);

  await act(() => wait(3100)); // чекаємо, доки спрацюють усі три таймери
  console.log("через три секунди:", button.textContent);
});
```

Команда `npx vitest run файл.test.tsx -t Cart --disable-console-intercept` запускає лише цей дослід. Тут і далі показано
те, що надрукував `console.log`, без службових рядків Vitest:

```text
до клацань: Додати пізніше (зараз 0)
через три секунди: Додати пізніше (зараз 1)
```

Перший рядок показує перший рендер. Другий рядок показує стан після всіх трьох таймерів: кожен таймер прочитав `qty`,
де лежить 0, і попросив записати 1. Отже, три клацання не означають трьох додавань, якщо нове значення обчислено зі
змінної рендеру.

Тепер замініть у функції `handleAddLater` рядок `setQty(qty + 1)` на `setQty((previous) => previous + 1)` і запустіть
той самий дослід:

```text
до клацань: Додати пізніше (зараз 0)
через три секунди: Додати пізніше (зараз 3)
```

Другий рядок змінився, бо таймери більше не читають `qty`. React передає кожній такій функції найновіше значення:
спершу 0, потім 1, потім 2. Якщо нове значення стану обчислюється зі старого, передавайте в `setQty` функцію.

Замовлення з початку лекції працює за тим самим правилом, але там стара змінна якраз потрібна. Цей дослід лежить у тому
самому файлі. Компонент зберігає місто в стані, а кнопка «Замовити» через три секунди друкує місто:

```tsx
function Order() {
  const [city, setCity] = useState("Київ");

  function handleOrder() {
    // Стрілка тримає змінну city того рендеру, у якому покупець натиснув кнопку.
    setTimeout(() => console.log("замовлення піде до:", city), 3000);
  }

  return (
    <>
      <p>Місто: {city}</p>
      <button onClick={handleOrder}>Замовити</button>
      <button onClick={() => setCity("Львів")}>Перемкнути на Львів</button>
    </>
  );
}

test("Order: покупець передумав після натискання", async () => {
  render(<Order />);
  fireEvent.click(screen.getByText("Замовити")); // таймер створено, поки city дорівнює "Київ"
  fireEvent.click(screen.getByText("Перемкнути на Львів")); // новий рендер із новою змінною city
  console.log("на екрані:", screen.getByText(/Місто/).textContent);
  await act(() => wait(3100));
});
```

```text
на екрані: Місто: Львів
замовлення піде до: Київ
```

Перший рядок надрукував дослід одразу після клацань, і на екрані вже Львів. Другий рядок надрукував таймер через три
секунди: він прочитав змінну `city` рендеру, у якому покупець натиснув «Замовити», а там лежить Київ. Новий рендер
створив нову змінну `city`, а старої ніхто не змінював. Тому для такої кнопки нічого особливого писати не треба:
обробник сам візьме те місто, яке покупець бачив у мить натискання.

| Що потрібно | Що взяти | Чому це працює |
|-------------|----------|----------------|
| Значення на мить дії, як із замовленням на Київ | Нічого особливого | Змінна рендеру не зміниться |
| Нове значення, обчислене зі старого | `setQty((previous) => previous + 1)` | React викликає цю функцію й передає в неї найновіше значення |
| Найновіше значення в таймері чи іншому старому колбеку | `useRef` | Ця функція React повертає той самий об'єкт `{ current }` у кожному рендері, тому всі замикання бачать один об'єкт |

Є й межа цієї проблеми. Документація `useState` пояснює, що React встигає оновити стан між навмисними діями
користувача, тому звичайний обробник натискання не бачить старого значення на початку наступного клацання. Значення зі
старого рендеру, яке читає функція, що пережила цей рендер, називають **застарілим станом**. Він виникає в таймерах, у
коді після очікування мережі та в ефектах.

Годинник із початку лекції є саме таким випадком. **Ефект** — це функція, яку React викликає після рендеру. Ефект із
порожнім масивом залежностей запускається один раз і ставить таймер, що повторюється. Функція таймера створена під час
першого рендеру, тому щосекунди читає 0. Таку помилку описує глава [`Removing Effect
Dependencies`](https://react.dev/learn/removing-effect-dependencies).

Ось такий годинник. Він лежить у тому самому тестовому файлі, а дослід чекає три з половиною секунди, щоб таймер
спрацював тричі:

```tsx
function Clock() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log("таймер читає:", seconds); // це змінна seconds першого рендеру
      setSeconds(seconds + 1);
    }, 1000);
    return () => clearInterval(id); // зупиняє таймер, коли компонент зникає зі сторінки
  }, []);

  return <p>Секунд: {seconds}</p>;
}

test("Clock: три спрацювання таймера", async () => {
  render(<Clock />);
  await act(() => wait(3500));
  console.log("на екрані:", screen.getByText(/Секунд/).textContent);
});
```

```text
таймер читає: 0
таймер читає: 0
таймер читає: 0
на екрані: Секунд: 1
```

Три однакові рядки показують, що таймер щоразу читає ту саму стару змінну. Він тричі попросив записати 1, тому на екрані
лишилася одиниця. Тепер замініть у таймері `setSeconds(seconds + 1)` на `setSeconds((previous) => previous + 1)` і
запустіть той самий дослід:

```text
таймер читає: 0
таймер читає: 0
таймер читає: 0
на екрані: Секунд: 3
```

Таймер і далі друкує 0, бо змінна лишилася старою, але для обчислення вона більше не потрібна, і на екрані вже 3. Отже,
у таймері, який живе довше за один рендер, обчислюйте нове значення через функцію, передану в `setSeconds`.

## Перевірте себе

Спершу дайте відповідь самі, уголос або письмово, і лише потім розгортайте пояснення.

**1. Функція `report` створена на верхньому рівні файла й читає `limit`. Її викликають із функції, де оголошено власну
змінну `limit`. Яку змінну прочитає `report`?**

<details><summary>Відповідь</summary>

Змінну з верхнього рівня файла, а якщо там її немає, читання кине `ReferenceError`. Нове оточення виклику отримує як
зовнішнє те оточення, яке функція запам'ятала при створенні. Оточення того, хто викликав, у пошуку не бере участі.

</details>

**2. Чому в прикладі з податками змінна `percent` живе після завершення `makeTax`, а змінна `price` після завершення
`withVat(100)` уже не потрібна?**

<details><summary>Відповідь</summary>

На оточення з `percent` посилається функція, яка лежить у змінній `withVat`. Під час виклику `withVat(100)` не
створено жодної функції, тому на оточення з `price` ніхто не посилається, і збирач сміття може його прибрати.

</details>

**3. Є рядки: `let price = 10; setTimeout(() => console.log(price), 0); price = 20;`. Що надрукує таймер і чому?**

<details><summary>Відповідь</summary>

Таймер надрукує 20. Змінна одна, а функція таймера виконається лише після всього поточного коду, коли в змінній уже
лежить 20. Числа 10 функція не зберігала.

</details>

**4. У циклі `for (let i = 0; i < 2; i++)` в тілі створюється функція, яка читає `i`. Функції викликають після циклу.
Що вони повернуть і що зміниться, якщо оголосити `let i` перед циклом?**

<details><summary>Відповідь</summary>

Функції повернуть 0 і 1, бо кожен прохід має власне оточення. Якщо оголосити `let i` перед циклом, змінна буде одна, і
обидві функції повернуть 2, тобто значення, на якому цикл зупинився.

</details>

**5. Функція `remember(order)` отримала об'єкт і повернула стрілку, яка його віддає. Потім код виконав `order.city =
"Львів"`. Чи є ця стрілка знімком старого міста?**

<details><summary>Відповідь</summary>

Ні. Параметр тримає посилання на той самий об'єкт, а об'єкт змінено, тому стрілка покаже Львів. Знімок був би
справжнім, якби код замість зміни створив новий об'єкт.

</details>

**6. У компоненті React таймер в обробнику викликає `setQty(qty + 1)`. Користувач клацнув тричі, поки таймери чекали.
Чому на екрані 1, а не 3, і яка зміна дасть 3?**

<details><summary>Відповідь</summary>

Усі три таймери створені в тому самому рендері й читають ту саму змінну `qty`, де лежить 0, тому всі просять записати 1.
Запис `setQty((previous) => previous + 1)` дасть 3, бо функція отримує найновіше значення від React.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| область видимості (scope) | частина коду, де ім'я доступне |
| оточення (lexical environment, Environment Record) | таблиця «ім'я → змінна» з посиланням на зовнішню таблицю |
| замикання (closure) | функція разом із оточенням, у якому її створили |
| збирач сміття (garbage collector) | частина рушія, яка звільняє пам'ять від недосяжних даних |
| знімок (snapshot) | значення у змінній, у яку більше ніхто не записує |
| рендер | виклик компонента React |
| застарілий стан (stale state) | значення зі старого рендеру, яке читає функція, що пережила цей рендер |
