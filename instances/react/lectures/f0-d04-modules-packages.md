# Лекція. День 4. Модулі й пакети

Ця лекція пояснює дві речі, на яких тримається кожен проєкт на React: як файли проєкту бачать один одного і як у
проєкт потрапляє чужий код. Читання займе близько 30 хвилин. Усі приклади запущено на Node 24 і npm 11, а вивід під
ними справжній. Те, що відбувається лише в браузері, описано за документацією, і поруч сказано, де ви це побачите.

Кілька слів, без яких лекцію не прочитати. **Node** (повна назва Node.js) — це програма, яка виконує JavaScript поза
браузером, просто на комп'ютері. **npm** — це програма, яка приходить разом із Node і встановлює в проєкт чужий код.
Докладно про npm розповідає розділ про пакети. Обидві програми запускають у **терміналі**: це програма, у якій
людина вводить команди текстом, а комп'ютер виконує їх і друкує відповідь. У блоках виводу цієї лекції рядок, що
починається знаком `$`, показує команду, яку ввели в терміналі, а рядки під ним показують те, що надрукувала програма.

**Після лекції ви зможете пояснити:**

- яку проблему розв'язують модулі й чим іменований експорт відрізняється від типового;
- у якому порядку виконуються файли проєкту і чому кожен виконується лише один раз;
- як за рядком у лапках після `from` знаходять файл або пакет;
- що лежить у `package.json`, у теці `node_modules` і у файлі `package-lock.json`;
- як прочитати записи `^4.17.0` і `~4.17.0` і яку версію поставить npm;
- чим відрізняються команди `npm install`, `npm update`, `npm ci` і `npx`.

## Дві проблеми великого проєкту

Уявіть сайт магазину. Код каталогу й кошика виріс до кількох тисяч рядків, тому його поділили на два файли. Сторінку
сайту описує файл HTML, і в ньому стоять **теги**: позначки в кутових дужках, які кажуть браузеру, що показати чи що
завантажити. Тег `<script src="catalog.js">` просить браузер завантажити файл `catalog.js` і виконати його, а тег
`<script src="cart.js">` робить те саме з файлом `cart.js`. Файл, підключений таким тегом, називають **звичайним
скриптом** (англійською classic script). Усі звичайні скрипти сторінки оголошують свої імена в одному спільному
просторі: ім'я, яке оголосив один скрипт, бачать усі інші скрипти сторінки.

**Перша проблема: імена спільні.** Припустімо, обидва файли оголосили функцію `format`. Браузер нічого не скаже:
другий файл просто замінить функцію першого, і каталог почне викликати чужий код. До того ж ніде не записано, який
файл від якого залежить. Про це нагадує лише порядок тегів, і переставлені теги ламають сторінку.

**Друга проблема: чужий код.** Магазину потрібні готові бібліотеки для дат і форм. **Бібліотекою** називають готовий
код, який написали інші люди, щоб ним могли користуватися різні програми. Якщо скопіювати файл бібліотеки до себе,
стає незрозуміло, яка це версія, тобто який це випуск бібліотеки, як її оновити й що робити, якщо вона сама потребує
ще двох бібліотек.

Першу проблему розв'язують модулі, а другу розв'язують пакети. **Пакетом** називають бібліотеку чи інструмент,
оформлені так, щоб їх могла встановити програма npm. Докладно про пакети йдеться нижче, а спершу розберемо модулі.

## Модуль: файл, який сам вирішує, що показати назовні

**Модуль** — це файл, імена якого належать лише йому. Змінна чи функція модуля не видна іншим файлам, доки сам модуль
не дозволить. Дозвіл записує слово `export`, а файл, якому потрібне це ім'я, бере його словом `import`.

```js
// файл prices.js
const VAT_RATE = 0.2;

function roundToCents(amount) {
  return Math.round(amount * 100) / 100;
}

export function withVat(amount) {
  return roundToCents(amount * (1 + VAT_RATE));
}

// файл main.js
import { withVat } from "./prices.js";

console.log(withVat(99.99));
console.log(typeof VAT_RATE);
```

```text
$ node main.js
119.99
undefined
```

Команда `node main.js` просить Node виконати файл `main.js`. Подивимося на кожну частину:

- `const VAT_RATE` і `function roundToCents` стоять без `export`, тому це внутрішня справа файла `prices.js`.
- `export function withVat` дозволяє іншим файлам узяти цю функцію. Усередині вона вільно користується внутрішніми
  іменами.
- `import { withVat } from "./prices.js"` просить із файла `prices.js` саме цю функцію. Рядок у лапках називають
  **вказівником модуля** (англійською module specifier): він каже, де шукати файл.
- `typeof VAT_RATE` дає `undefined`, бо в `main.js` такого імені немає. Інший файл може мати власну константу з тим
  самим іменем, і конфлікту не буде.

### Форми запису

Експорт із власним іменем називають **іменованим**. Файл може мати скільки завгодно таких експортів.

| Запис | Що він робить |
|-------|---------------|
| `export function f() {}` | експортує функцію прямо там, де її оголошено |
| `export { f, g };` | перелічує експорти одним рядком, зазвичай наприкінці файла |
| `import { f } from "./x.js";` | бере експорт `f` |
| `import { f as area } from "./x.js";` | бере експорт `f` і називає його в цьому файлі `area` |
| `import * as x from "./x.js";` | збирає всі експорти в один об'єкт `x` |
| `export { f } from "./x.js";` | передає чужий експорт далі, нічого не оголошуючи у своєму файлі |

Запис з `as` потрібен, коли два модулі експортують однакові імена. У прикладі нижче обидва файли експортують функцію
`area`, а файл `main.js` бере обидві без `as`:

```js
// файл circle.js
export function area(radius) {
  return Math.round(3.14 * radius * radius);
}

// файл square.js
export function area(side) {
  return side * side;
}

// файл main.js
import { area } from "./circle.js";
import { area } from "./square.js"; // друге оголошення того самого імені
console.log(area(2));
```

```text
$ node main.js
SyntaxError: Identifier 'area' has already been declared
```

Перед цим рядком Node друкує шлях до файла й рядок коду, а після нього друкує **стек викликів**, тобто список
функцій, які викликали одна одну до місця помилки. Тут і далі в лекції показано лише рядок із помилкою.
`SyntaxError` — це помилка, яку рушій кидає, коли код записано не за правилами мови. Рушій помічає таку помилку ще
тоді, коли читає файл, тому не виконує з нього жодного рядка. Саме тому число на екрані не з'явилося: Node відмовився
виконувати файл `main.js`, бо другий `import` оголошує ім'я `area` вдруге. Щоб файл запрацював, дайте кожному імпорту
власне ім'я:

```js
// файл main.js
import { area as circleArea } from "./circle.js";
import { area as squareArea } from "./square.js";
console.log(circleArea(2), squareArea(2));
```

```text
$ node main.js
13 4
```

Тепер `circleArea(2)` дає 13, а `squareArea(2)` дає 4, тобто кожне ім'я веде до функції зі свого файла. Отже, коли
два модулі експортують однакове ім'я, змінювати самі модулі не треба, достатньо перейменувати імпорт у своєму файлі.

Запис `export { f } from` часто стоїть у файлі `index.js`, який збирає експорти цілої теки. Такий файл нічого не
обчислює, а лише передає чужі імена далі, наприклад `export { area as circleArea } from "./circle.js"`.

### Типовий експорт

Часто файл існує заради однієї головної речі. Для цього є **типовий експорт** (англійською default export), який
записують `export default`. У файлі він може бути лише один, а той, хто імпортує, сам вибирає йому ім'я й не ставить
фігурних дужок. Це не окремий механізм мови, а звичайний іменований експорт з іменем `default`, і запуск це показує:

```js
// файл title.js
export default function title(text) {
  return text.toUpperCase();
}
export const SEPARATOR = " | ";

// файл main.js
import makeTitle, { SEPARATOR } from "./title.js";
import { default as sameFunction } from "./title.js";
import * as everything from "./title.js";

console.log(makeTitle("каса") + SEPARATOR + "відкрито");
console.log(makeTitle === sameFunction);
console.log(Object.keys(everything));
```

```text
$ node main.js
КАСА | відкрито
true
[ 'SEPARATOR', 'default' ]
```

Рядок `true` означає, що `makeTitle` і `sameFunction` є тією самою функцією, а об'єкт `everything` містить поле
`default`.

### Що саме приходить через `import`

Рядок `import` не копіює значення. **MDN** — це великий онлайн-довідник з JavaScript і технологій браузера, на який
спирається ця лекція. MDN називає імпортовані імена поданнями лише для читання (read-only views): ім'я у вашому файлі
показує змінну іншого файла, а присвоїти їй нове значення може лише модуль, який її експортує. Теорія дня показує це
на лічильнику. Тут важливий інший наслідок: об'єкт, який експортував модуль, один на всю програму.

```js
// файл settings.js
export const settings = { currency: "грн" };

// файл admin.js
import { settings } from "./settings.js";
export function switchToEuro() {
  settings.currency = "євро";
}

// файл shop.js
import { settings } from "./settings.js";
export function priceLabel(amount) {
  return amount + " " + settings.currency;
}

// файл main.js
import { switchToEuro } from "./admin.js";
import { priceLabel } from "./shop.js";
console.log(priceLabel(100));
switchToEuro();
console.log(priceLabel(100));
```

```text
$ node main.js
100 грн
100 євро
```

Файл `shop.js` нічого не змінював, а його результат змінився, бо `admin.js` і `shop.js` мають посилання на той самий
об'єкт, як дві змінні в дні 1.

## Як завантажується програма з модулів

Рядок `import` спрацьовує не тоді, коли до нього доходить виконання. Завантаження проходить три етапи, які описує
специфікація мови ECMAScript у розділі 16.2.1:

1. **Завантаження.** Рушій (програма, яка виконує JavaScript) читає головний файл, нічого в ньому не виконуючи,
   знаходить рядки `import`, читає названі там файли й так далі. Виходить **граф модулів**: схема того, який файл від
   якого залежить. Файл, який інший файл імпортує, називають **залежністю** цього файла.
2. **Зв'язування.** Рушій створює імена й зв'язує кожен `import` з відповідним `export`. Якщо експорту немає, помилка
   виникає саме тут, коли жоден рядок вашого коду ще не виконано.
3. **Виконання.** Кожен файл виконується після тих файлів, від яких залежить, і лише один раз, скільки б файлів його
   не імпортували.

Покроковий приклад: `main.js` бере функції з `format.js` і `tax.js`, а ті обидва беруть валюту з `config.js`.

```js
// файл config.js
console.log("виконується config.js");
export const CURRENCY = "грн";

// файл format.js
import { CURRENCY } from "./config.js";
console.log("виконується format.js");
export function formatPrice(amount) {
  return amount + " " + CURRENCY;
}

// файл tax.js
import { CURRENCY } from "./config.js";
console.log("виконується tax.js, валюта вже відома:", CURRENCY);
export const VAT_RATE = 0.2;

// файл main.js
console.log("виконується main.js");
import { formatPrice } from "./format.js";
import { VAT_RATE } from "./tax.js";
console.log(formatPrice(100 * (1 + VAT_RATE)));
```

```text
$ node main.js
виконується config.js
виконується format.js
виконується tax.js, валюта вже відома: грн
виконується main.js
120 грн
```

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | рушій читає `main.js` | знайдено два `import`, код не виконується |
| 2 | рушій читає `format.js` і `tax.js` | знайдено ще `config.js`, граф повний |
| 3 | рушій зв'язує імена | кожен `import` знайшов свій `export` |
| 4 | виконується `config.js` | він ні від чого не залежить, тому друкує першим |
| 5 | виконується `format.js` | його залежність уже готова |
| 6 | виконується `tax.js` | файл `config.js` повторно не виконується |
| 7 | виконується `main.js` | усі залежності готові, тому він друкує останнім |

Рядок `console.log("виконується main.js")` стоїть вище за `import`, а друкується після всіх залежностей. MDN називає
це підняттям (hoisting) оголошень імпорту. Цим словом MDN описує дві речі: імпортовані імена доступні в усьому файлі,
навіть вище за рядок `import`, а імпортовані файли виконуються раніше за решту коду модуля.

**Чому `import` не можна поставити в `if`.** Перші два етапи відбуваються до виконання, тому рушій мусить знати список
імпортів, не запускаючи код. Рядок `import { a } from "./a.js"` усередині `if` дає `SyntaxError`. Для завантаження за
умовою існує **динамічний імпорт**: вираз `import("./report.js")` виконується як звичайний виклик і повертає
**проміс**, тобто об'єкт, який представляє результат роботи, що ще не завершилася. Коли завантаження закінчиться,
результатом цього проміса стане об'єкт з експортами файла `report.js`. Докладно проміс і `await` пояснює день 5, а тут
`await` просто чекає завершення завантаження.

```js
// файл report.js
console.log("report.js завантажено");
export function buildReport() {
  return "звіт готовий";
}

// файл good.js
console.log("сторінка відкрита");
const needReport = true;
if (needReport) {
  const module = await import("./report.js");
  console.log(module.buildReport());
}
```

```text
$ node good.js
сторінка відкрита
report.js завантажено
звіт готовий
```

Наперед відомий список імпортів дає ще одну перевагу. **Бандлер** (англійською bundler) — це програма, яка читає
модулі проєкту й записує їхній код у кілька файлів, готових для браузера. Цю роботу називають **збиранням**, а файли,
які вийшли, називають **збіркою**. Прикладом бандлера є Vite, з яким ви працюватимете в проєктах на React. Бандлер
бачить, які експорти ніхто не імпортує, і може не включати їх у збірку. MDN називає таке прибирання невикористаного
коду tree shaking.

Щоб перевірити це, створимо в порожній теці три файли. `main.js` бере лише одну з двох функцій файла `prices.js`, а
кожна функція містить власну позначку, яку легко знайти в результаті збирання. Файл `index.html` є сторінкою, яку
відкриває браузер. Атрибут `type="module"` у тегу `<script>` каже браузеру, що файл `main.js` є модулем: без цього
атрибута рядок `import` у ньому дав би помилку.

```js
// файл prices.js
export function withVat(amount) {
  return "vat-label: " + amount * 1.2;
}
export function withDiscount(amount) {
  return "discount-label: " + amount * 0.9;
}

// файл main.js
import { withVat } from "./prices.js"; // функцію withDiscount ніхто не імпортує
console.log(withVat(100));

// файл index.html
<script type="module" src="/main.js"></script>
```

Далі йдуть команди для термінала, кожна в окремому рядку. Рядок, що починається знаком `#`, є коментарем: термінал
його не виконує, а вам він пояснює наступну команду. Слова після назви команди, які починаються з дефіса чи двох
дефісів, як `-y` чи `--silent`, називають **прапорцями** (англійською options або flags). Прапорець змінює поведінку
команди. Ці команди ставлять Vite у проєкт і запускають збирання. Що саме роблять `npm init`, `npm install --save-dev`
і `npx`, докладно пояснюють розділи про пакети й про `npx` нижче.

```bash
# npm init -y створює package.json, а запис > /dev/null прибирає друк цього файла на екран.
npm init -y > /dev/null
# Прапорець --silent прибирає підсумок npm.
npm install --save-dev vite --silent
# vite build кладе зібраний код у теку dist/assets, а --logLevel silent прибирає його звіт.
npx vite build --logLevel silent
# grep -o шукає обидві позначки у зібраному файлі й друкує лише те, що знайшов.
grep -o "vat-label\|discount-label" dist/assets/*.js
```

```text
vat-label
```

Команда `grep` знайшла тільки позначку функції `withVat`. Тексту функції `withDiscount` у зібраному файлі немає, бо її
ніхто не імпортував. Отже, у цьому випадку експорт, яким ніхто не користується, не збільшив файл для браузера.

**Циклічні імпорти.** Якщо `a.js` імпортує `b.js`, а `b.js` імпортує `a.js`, виникає цикл. Помилка з'являється, лише
коли `b.js` під час виконання одразу читає константу з `a.js`, який ще не виконувався. Ось такий випадок:

```js
// файл a.js
import { b } from "./b.js";
export const a = "значення a";
console.log("a.js бачить:", b);

// файл b.js
import { a } from "./a.js";
console.log("b.js бачить:", a); // читає a до того, як a.js почав виконуватися
export const b = "значення b";
```

```text
$ node a.js
ReferenceError: Cannot access 'a' before initialization
```

Ви запустили `a.js`, але першим виконується його залежність `b.js`. Файл `a.js` ще не дійшов до рядка `export const
a`, тому рядок `console.log` у файлі `b.js` падає з цією помилкою, і жоден файл нічого не друкує. MDN радить виносити
спільний код у третій файл, тоді цикл зникає.

## Як за рядком у лапках знаходять файл

Рядок у лапках після `from` буває двох видів. **Відносний вказівник** починається з `./` або `../` і описує шлях до
файла від того файла, у якому стоїть `import`. **Голий вказівник** (англійською bare specifier) — це назва пакета без
шляху, наприклад `"react"`. Node, браузер і Vite знаходять файл за цими вказівниками по-різному. Браузер отримує
кожен файл від **сервера**, тобто програми, яка за адресою файла віддає браузеру його вміст. **Карта імпортів**
(англійською import map) — це запис у тегу `<script type="importmap">` на сторінці, який каже браузеру, за якою
адресою шукати модуль із певною назвою. Тека `node_modules` у проєкті містить пакети, які встановив npm. Таблиця
порівнює всі три способи:

| Вид вказівника | Приклад | Node | Браузер без бандлера | Vite |
|----------------|---------|------|----------------------|------|
| Відносний | `"./prices.js"` | шукає від поточного файла, розширення обов'язкове | запитує в сервера точну адресу | шукає від поточного файла, розширення можна пропустити |
| Голий | `"react"` | шукає пакет у `node_modules` | `TypeError`, якщо немає карти імпортів | переписує на справжню адресу |

Щоб побачити, як Node шукає пакет за голим вказівником, створимо пакет руками, без npm. Для Node пакет — це просто
тека з файлом `package.json`. Цей файл записано у форматі JSON, тобто текстом, який виглядає майже так само, як об'єкт
у JavaScript. Він описує пакет: його назву, версію та інші налаштування.

```js
// файл package.json
{ "type": "module" }

// файл node_modules/tiny-price/package.json
{
  "name": "tiny-price",
  "version": "1.2.0",
  "type": "module",
  "exports": { ".": "./lib/index.js" }
}

// файл node_modules/tiny-price/lib/index.js
export function withVat(amount) {
  return Math.round(amount * 120) / 100;
}

// файл node_modules/tiny-price/lib/secret.js
export const SECRET = 1;

// файл src/deep/main.js
import { withVat } from "tiny-price";
console.log(withVat(50));

// файл src/inner.js
import { SECRET } from "tiny-price/lib/secret.js";
console.log(SECRET);
```

```text
$ node src/deep/main.js
60
$ node src/inner.js
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/secret.js' is not defined by "exports" in .../node_modules/tiny-price/package.json imported from .../src/inner.js
```

Node шукає теку `node_modules/tiny-price` поруч із файлом, що імпортує, а якщо її немає, піднімається на теку вище й
повторює пошук аж до кореня диска, тобто до найвищої теки, у якій лежать усі інші. Тому файл у `src/deep/` знайшов
пакет у теці проєкту. Далі Node читає `package.json` пакета. Поле `exports` перелічує, що пакет дозволяє імпортувати
ззовні, а запис `"."` означає імпорт за самою назвою пакета. Усе інше закрите, тому другий запуск падає, хоча файл
`secret.js` існує.

**Браузер** працює з адресами й не знає, де лежить ваша `node_modules`. Якщо підключити модуль тегом `<script
type="module">` без бандлера й написати `from "react"`, у консолі браузера з'явиться `TypeError`. **Консоллю**
браузера називають панель інструментів розробника, у якій браузер показує помилки сторінки й те, що друкує
`console.log`. **Vite** під час розробки, тобто поки ви пишете код і дивитеся результат у браузері, заздалегідь
збирає пакети, від яких залежить проєкт, і переписує голий імпорт на адресу на кшталт
`/node_modules/.vite/deps/my-dep.js?v=…`. Він також дописує пропущені розширення, тому у проєкті на Vite працює `from
"./helper"`, а в Node той самий рядок дає `ERR_MODULE_NOT_FOUND`.

**Як Node вирішує, що файл є модулем.** Файл `.mjs` завжди модуль, а `.cjs` завжди старий формат модулів **CommonJS**,
у якому замість `import` пишуть `require`. Для файла `.js` вирішує поле `type` у найближчому `package.json`. Якщо поля
немає, Node 24 дивиться на код: файл із рядком `import` чи `export` запускається як модуль, а без них запускається як
CommonJS. Документація Node радить завжди писати `type` явно.

## Пакети: як чужий код потрапляє у проєкт

**npm** — це дві речі під однією назвою: **реєстр**, тобто велике онлайн-сховище пакетів, і програма для термінала,
яка приходить разом із Node. Файл `package.json` у корені проєкту, тобто в його головній теці, перелічує пакети,
потрібні проєкту. Такі пакети називають **залежностями** проєкту (англійською dependencies): проєкт залежить від них
так само, як файл залежить від модуля, який імпортує. Ось головні поля цього файла:

| Поле | Навіщо воно |
|------|-------------|
| `private` | значення `true` не дає випадково опублікувати проєкт у реєстрі |
| `type` | читає Node, а не npm: як розуміти файли `.js` |
| `scripts` | короткі назви команд: `npm run dev` запустить те, що записано в `dev` |
| `dependencies` | пакети, потрібні програмі під час роботи |
| `devDependencies` | інструменти для розробки: тести, збирання, перевірка коду |

Команда `npm install debug` дізнається в реєстрі доступні версії, обирає найновішу, завантажує **архів** пакета, тобто
один файл, у якому упаковано всі файли пакета, розпаковує його в `node_modules`, дописує пакет у `package.json` і
записує результат у `package-lock.json`. Про файл `package-lock.json` докладно розповідає розділ про файл блокування.
Те саме відбувається з пакетами, від яких залежить `debug`. Така залежність залежності називається **транзитивною**.
Команда `npm install --save-dev semver` кладе пакет у `devDependencies`, а прапорець `--omit=dev` просить npm не
ставити пакети з цього розділу. Спробуйте це в новій порожній теці:

```bash
# npm init -y створює package.json, а запис > /dev/null прибирає друк цього файла на екран.
npm init -y > /dev/null
# Прапорець --silent прибирає підсумок npm, щоб лишилися тільки наші перевірки.
npm install debug --silent
npm install --save-dev semver --silent
# ls -1 друкує вміст теки, по одній назві в рядку.
ls -1 node_modules
# npm ci ставить пакети заново, а --omit=dev пропускає devDependencies.
npm ci --omit=dev --silent
ls -1 node_modules
```

```text
debug
ms
semver
debug
ms
```

Перші три рядки надрукував перший `ls`. Пакет `debug` ви поставили самі, пакет `ms` npm поставив, бо від нього
залежить `debug`, а `semver` записано в `devDependencies`. Останні два рядки надрукував другий `ls`, і `semver` серед
них уже немає. Отже, запис у `devDependencies` підходить для інструментів розробки: на машину, де запускають `npm ci
--omit=dev`, вони не потраплять.

Тека `node_modules` містить усе **дерево залежностей**, тобто пакети проєкту разом із їхніми залежностями,
залежностями тих залежностей і так далі. Двом пакетам у цьому дереві можуть бути потрібні різні версії того самого
третього пакета. Запис `debug@2.6.9` означає пакет `debug` версії 2.6.9. Приклад: `debug@2.6.9` вимагає рівно
`ms@2.0.0`, а проєкт сам просить `ms@2.1.3`. Створіть такий проєкт у теці `two-ms`. Команда `mkdir` створює нову
теку, а команда `cd` переходить у неї, тому наступні команди працюють уже в цій теці:

```bash
mkdir two-ms && cd two-ms
npm init -y > /dev/null
npm install debug@2.6.9 ms@2.1.3 --silent
# npm ls --all малює все дерево пакетів.
npm ls --all
# node -p друкує значення виразу: тут це версія з package.json пакета у вказаній теці.
node -p "require('./node_modules/ms/package.json').version"
node -p "require('./node_modules/debug/node_modules/ms/package.json').version"
```

```text
two-ms@1.0.0 .../two-ms
├─┬ debug@2.6.9
│ └── ms@2.0.0
└── ms@2.1.3

2.1.3
2.0.0
```

Перший рядок називає сам проєкт і теку, де він лежить, тому на вашій машині шлях буде інший. Дерево показує дві версії
`ms`. Останні два рядки підтверджують, що на диску версія `2.1.3` лежить у `node_modules/ms`, а версія `2.0.0` лежить
у `node_modules/debug/node_modules/ms`. Коли `debug` імпортує `ms`, пошук починається з найближчої `node_modules`,
тому `debug` отримує свою версію. Отже, два пакети у вашому проєкті можуть користуватися різними версіями третього
пакета, і вони не заважають одна одній.

**git** — це програма, яка зберігає історію змін файлів проєкту. Завдяки цій історії можна повернутися до попередньої
версії коду й поділитися кодом з колегами. **Закомітити** файл означає записати його поточний стан в історію git.
Теку `node_modules` не комітять у git: вона велика, а відтворити її можна однією командою.

## Версії: що означають три числа

Версія записана трьома числами за правилами **семантичного версіонування** (англійською semantic versioning, коротко
semver): `MAJOR.MINOR.PATCH`, тобто мажорне, мінорне й виправне число. Виправлення помилки підвищує останнє число.
Нова можливість зі збереженням сумісності підвищує середнє число. Зміна, яка ламає старий код, підвищує перше число.
Це домовленість між людьми, а не перевірка: автор може помилитися й зламати щось у виправній версії.

У `package.json` зазвичай стоїть не версія, а **діапазон**. Перевірити діапазон можна пакетом `semver`, на якому
побудовано npm. Команда `npx`, про яку докладно сказано нижче в цій лекції, запускає цей пакет, не встановлюючи його у
ваш проєкт. Після прапорця `-r` стоїть діапазон, далі стоять версії для перевірки, а друкує команда лише ті версії,
що підходять:

```text
$ npx --yes semver -r "^4.17.0" 4.16.9 4.17.0 4.21.2 5.0.0
4.17.0
4.21.2
$ npx --yes semver -r "~4.17.0" 4.16.9 4.17.0 4.17.21 4.18.0
4.17.0
4.17.21
$ npx --yes semver -r "^0.4.2" 0.4.1 0.4.2 0.4.9 0.5.0
0.4.2
0.4.9
$ npx --yes semver -r "^19.0.0" 19.0.0 19.1.0 20.0.0-rc.1 19.2.0-canary.1
19.0.0
19.1.0
```

Таблиця збирає ці самі відповіді й додає до кожної значення запису:

| Діапазон | Перевірені версії | Підходять | Значення запису |
|----------|-------------------|-----------|-----------------|
| `^4.17.0` | 4.16.9, 4.17.0, 4.21.2, 5.0.0 | 4.17.0, 4.21.2 | від 4.17.0 до 5.0.0, не включно |
| `~4.17.0` | 4.16.9, 4.17.0, 4.17.21, 4.18.0 | 4.17.0, 4.17.21 | від 4.17.0 до 4.18.0, не включно |
| `^0.4.2` | 0.4.1, 0.4.2, 0.4.9, 0.5.0 | 0.4.2, 0.4.9 | від 0.4.2 до 0.5.0, не включно |
| `^19.0.0` | 19.0.0, 19.1.0, 20.0.0-rc.1, 19.2.0-canary.1 | 19.0.0, 19.1.0 | версії з дефісом не підходять |

Дашок `^` не дозволяє міняти найлівіше ненульове число: для `^4.17.0` це 4, а для `^0.4.2` це 4 у другій позиції.
Тильда `~` дозволяє змінювати лише останнє число. Версії з дефісом є **передрелізами**, тобто пробними випусками
перед стабільною версією, і звичайний діапазон їх не бере. Коли у проєкті немає файла блокування, про який розповідає
наступний розділ, `npm install` бере найновішу версію, яка підходить під діапазон.

## Файл блокування: покроковий приклад

Діапазон дає різні результати на різних машинах. **Файл блокування** `package-lock.json` записує точну версію кожного
пакета всього дерева. Англійською такий файл називають lockfile, бо він закріплює, тобто блокує, вибрані версії.
Простежимо за цим на справжньому пакеті `ms`, у якого є версії 2.1.1 і 2.1.3. Щоб показати, що відбувається з
часом, ми поставили стару версію й записали діапазон `^2.1.1`, ніби новішої версії тоді ще не було. Команда `npm
install ms@2.1.1` записує цей діапазон у `package.json` сама.

Створіть порожню теку й покладіть у неї маленький файл `show.mjs`. Він друкує версію пакета `ms` у трьох місцях, щоб
після кожної команди було видно, що змінилося. Модуль `node:fs` вбудований у Node і працює з файлами на диску. Його
функція `readFileSync` читає файл і повертає його вміст, а `JSON.parse` перетворює цей текст на об'єкт.

```js
// файл show.mjs
import { readFileSync } from "node:fs";

// Читає JSON-файл із теки, у якій запущено команду.
const read = (file) => JSON.parse(readFileSync(file, "utf8"));

const range = read("package.json").dependencies.ms;
const locked = read("package-lock.json").packages["node_modules/ms"].version;
const installed = read("node_modules/ms/package.json").version;
console.log(`діапазон ${range}, блокування ${locked}, встановлено ${installed}`);
```

Команди нижче проходять через чотири місця: теку розробниці, теку колеги, сервер збирання й нову теку без файла
блокування. **Сервером збирання** називають окремий комп'ютер, який сам встановлює залежності, збирає проєкт і
запускає тести, щойно хтось пропонує зміну в коді. Англійською такий підхід називають continuous integration, коротко
CI.

```bash
# Розробниця ставить стару версію. Прапорець --silent прибирає підсумок npm.
mkdir developer && cd developer
npm init -y > /dev/null
npm install ms@2.1.1 --silent
node ../show.mjs

# Колега отримує package.json і файл блокування, але без node_modules, і запускає npm install.
mkdir ../colleague && cp package.json package-lock.json ../colleague && cd ../colleague
npm install --silent
node ../show.mjs

# Сервер збирання ставить ті самі два файли командою npm ci.
npm ci --silent
node ../show.mjs

# Нова тека отримує лише package.json, без файла блокування.
mkdir ../no-lock && cp package.json ../no-lock && cd ../no-lock
npm install --silent
node ../show.mjs

# Колега у своїй теці свідомо оновлює пакет у межах діапазону.
cd ../colleague
npm update --silent
node ../show.mjs
cd ..
```

```text
діапазон ^2.1.1, блокування 2.1.1, встановлено 2.1.1
діапазон ^2.1.1, блокування 2.1.1, встановлено 2.1.1
діапазон ^2.1.1, блокування 2.1.1, встановлено 2.1.1
діапазон ^2.1.1, блокування 2.1.3, встановлено 2.1.3
діапазон ^2.1.1, блокування 2.1.3, встановлено 2.1.3
```

Кожен запуск `show.mjs` надрукував один рядок, тому рядки виводу йдуть у тому самому порядку, що й рядки цієї таблиці:

| Крок | Команда | `package.json` | Файл блокування | Встановлено |
|------|---------|----------------|-----------------|-------------|
| 1 | розробниця ставить пакет | `^2.1.1` | `2.1.1` | `2.1.1` |
| 2 | колега отримує копію проєкту без `node_modules`: `npm install` | `^2.1.1` | `2.1.1` | `2.1.1` |
| 3 | сервер збирання: `npm ci` | `^2.1.1` | `2.1.1` | `2.1.1` |
| 4 | нова тека без файла блокування: `npm install` | `^2.1.1` | створено заново: `2.1.3` | `2.1.3` |
| 5 | свідоме оновлення: `npm update` | `^2.1.1` | `2.1.3` | `2.1.3` |

Випадок без файла блокування і є пасткою цього дня: та сама команда з тим самим `package.json` дала іншу версію. Коли
файл блокування є, `npm install` лишає записану версію, доки вона підходить під діапазон. Отже, файл блокування треба
комітити разом із `package.json`. У теці `developer` запис про пакет у файлі `package-lock.json` виглядає так:

```json
"node_modules/ms": {
  "version": "2.1.1",
  "resolved": "https://registry.npmjs.org/ms/-/ms-2.1.1.tgz",
  "integrity": "sha512-tgp+dl5cGk28utYktBsrFqA7HKgrhgPsg6Z/EfhWI4gl1Hwq8B/GmY/0oXZ6nF8hDVesS/FpnYaD/kOWhYQvyg==",
  "license": "MIT"
}
```

Поле `resolved` є адресою архіву, а `integrity` є **хешем**, тобто коротким значенням, обчисленим із вмісту архіву.
Щоб побачити, навіщо потрібен хеш, змінимо одну літеру цього значення й запустимо `npm ci`. Команди виконуються в тій
самій теці, що лежить над `developer`:

```bash
# Нова тека отримує копію обох файлів розробниці.
mkdir tampered && cp developer/package.json developer/package-lock.json tampered && cd tampered
# sed замінює у файлі блокування маленьку літеру t на початку хеша на велику T.
sed -i 's/sha512-tgp/sha512-Tgp/' package-lock.json
npm ci
# ls -A показує вміст теки разом із прихованими файлами.
ls -A
cd ..
```

```text
npm error code EINTEGRITY
npm error sha512-Tgp+dl5cGk28utYktBsrFqA7HKgrhgPsg6Z/EfhWI4gl1Hwq8B/GmY/0oXZ6nF8hDVesS/FpnYaD/kOWhYQvyg== integrity checksum failed when using sha512: wanted sha512-Tgp+dl5cGk28utYktBsrFqA7HKgrhgPsg6Z/EfhWI4gl1Hwq8B/GmY/0oXZ6nF8hDVesS/FpnYaD/kOWhYQvyg== but got sha512-tgp+dl5cGk28utYktBsrFqA7HKgrhgPsg6Z/EfhWI4gl1Hwq8B/GmY/0oXZ6nF8hDVesS/FpnYaD/kOWhYQvyg==. (3028 bytes)
package-lock.json
package.json
```

Команда `npm ci` друкує ще попередження й шлях до журналу, тобто файла, у який npm записує подробиці своєї роботи. Тут
показано лише рядки з помилкою. Після слова `wanted` стоїть значення з файла блокування, а після `got` стоїть
значення, яке npm обчислив із завантаженого архіву. Вони різняться однією літерою, тому npm зупинився. Останні два
рядки надрукував `ls -A`, і теки `node_modules` серед них немає. Отже, якщо вміст архіву не збігається із записаним
хешем, цей пакет не потрапить у ваш проєкт.

**Чим відрізняється `npm ci`.** Команда вимагає готовий файл блокування. Вона не вміє додати один окремий пакет, а
встановлює всі залежності проєкту разом. Перед встановленням вона видаляє `node_modules` і ніколи нічого не записує в
`package.json` і у файл блокування. Якщо вони розходяться, вона зупиняється. Ось випадок, де в `package.json` підняли
діапазон до `^2.1.3`, а файл блокування лишився старий:

```bash
mkdir range && cp developer/package.json developer/package-lock.json range && cd range
# npm pkg set змінює запис у package.json, а файл блокування не чіпає.
npm pkg set dependencies.ms=^2.1.3
npm ci
```

```text
npm error code EUSAGE
npm error Invalid: lock file's ms@2.1.1 does not satisfy ms@2.1.3
```

Команда `npm ci` друкує ще довгу довідку, тут показано лише код помилки й причину. Причина каже, що файл блокування
записав `ms@2.1.1`, а ця версія не підходить під новий діапазон. Звичайний `npm install` у цій самій ситуації мовчки
оновлює файл блокування:

```bash
npm install --silent
node ../show.mjs
cd ..
```

```text
діапазон ^2.1.3, блокування 2.1.3, встановлено 2.1.3
```

Сервер збирання має перевіряти саме той код, який ви закомітили. Тому на ньому запускають `npm ci`, який ніколи не
змінює файл блокування, а не `npm install`, який може змінити цей файл мовчки.

| Команда | Коли її запускають | Міняє `package.json` | Міняє файл блокування |
|---------|--------------------|----------------------|-----------------------|
| `npm install пакет` | додати пакет | так | так |
| `npm install` | поставити залежності у себе | ні | лише якщо є розбіжність чи файла немає |
| `npm update` | оновити в межах діапазонів | ні | так |
| `npm ci` | чисте встановлення на іншій машині | ніколи | ніколи |

## npx: запустити команду з пакета

Деякі пакети дають команду для термінала. Пакет описує її в полі `bin` свого `package.json`, а npm під час
встановлення створює в теці `node_modules/.bin` посилання на файл команди всередині пакета. Це посилання на файл на
диску, і воно не має нічого спільного з посиланнями на об'єкти з дня 1. Коли ви вводите назву команди, система шукає
програму з такою назвою в кількох теках зі списку, який англійською називають PATH. Команда `npm run` додає до цього
списку теку `node_modules/.bin`, тому в `scripts` можна писати просто `vite`.

Команда `npx` шукає пакет у два кроки. Спершу вона дивиться у ваш проєкт. Якщо пакета там немає, вона питає дозволу,
завантажує його в **кеш** npm і запускає звідти. Кешем називають окрему теку поза проєктом, де npm зберігає
завантажені пакети, щоб наступного разу взяти їх звідти. Прапорець `--yes` відповідає на запитання «так» наперед.
Спробуйте це в новій порожній теці:

```bash
npm init -y > /dev/null
# Пакета cowsay у проєкті немає, тому npx завантажує його в кеш і запускає.
npx --yes cowsay "привіт"
# ls -A показує вміст теки разом із прихованими файлами.
ls -A
# npm pkg get друкує розділ dependencies з package.json.
npm pkg get dependencies
```

```text
 ________
< привіт >
 --------
        \   ^__^
         \  (oo)\_______
            (__)\       )\/\
                ||----w |
                ||     ||
package.json
{}
```

Малюнок надрукував пакет `cowsay`, отже команда спрацювала. Рядок `package.json` надрукував `ls -A`: крім цього файла,
у теці нічого немає, тобто теки `node_modules` не з'явилося. Запис `{}` означає, що розділ `dependencies` порожній.
Отже, `npx` підходить для разового запуску, а ваш проєкт від такого запуску не змінюється. Пам'ятайте, що `npx`
виконує чужий код на вашій машині, і одруківка в назві може запустити зовсім інший пакет. Команда `npm create
vite@latest` влаштована схоже: `npm create` є іншою назвою `npm init`, а `npm init foo` запускає `npm exec
create-foo`. Команда `npm exec` робить те саме, що й `npx`: сама `npx` усередині користується `npm exec`. Запис
`@latest` просить версію, яку автори пакета позначили як найновішу, і саме її `npm install` бере, коли версію не
вказано.

## Типові хибні уявлення

**«`^4.17.0` означає найновішу версію пакета».** Діапазон має верхню межу, тому `5.0.0` під нього не підходить. За
наявності файла блокування `npm install` не візьме навіть новішу `4.x`, доки ви не запустите `npm update`.

**«Файл блокування потрібен лише на сервері».** Лише він дає всім те саме дерево. Якщо його не комітити, ваші версії й
версії колеги розійдуться непомітно.

**«`devDependencies` не потрапляють у збірку застосунку».** Цей розділ керує встановленням, а не збиранням. Бандлер
кладе в результат те, що імпортовано. Щоб перевірити це, створимо в порожній теці два файли, а пакет `ms` запишемо в
`devDependencies` і імпортуємо в коді:

```js
// файл main.js
import ms from "ms";
console.log(ms("2 days"));

// файл index.html
<script type="module" src="/main.js"></script>
```

```bash
npm init -y > /dev/null
npm install --save-dev ms vite --silent
# Розділ dependencies порожній, бо обидва пакети лежать у devDependencies.
npm pkg get dependencies
npx vite build --logLevel silent
# Цей текст помилки є лише в коді пакета ms, а наш файл main.js його не містить.
grep -o "val is not a non-empty string" dist/assets/*.js
```

```text
{}
val is not a non-empty string
```

Запис `{}` показує, що пакет `ms` не записано в `dependencies`. Другий рядок показує, що код пакета все одно опинився
в зібраному файлі. Отже, розділ у `package.json` не вирішує, чи потрапить пакет у збірку: для цього важить лише те, що
ваш код його імпортує.

## Як це проявиться в React

React ви почнете вивчати у фазі 1, тому спершу кілька слів, без яких цей розділ не прочитати. **Компонент** React — це
функція, яка повертає опис частини сторінки, наприклад кнопки чи картки товару. React сам викликає функцію компонента,
щоб отримати цей опис, і кожен такий виклик називає **рендером**. Функції React, назви яких починаються з `use`,
називають **хуками**. Хук можна викликати лише всередині компонента, на його верхньому рівні, тобто не в умові й не в
циклі. Хук `useState` додає компоненту стан, тобто дані, які компонент пам'ятає між оновленнями екрана, як пояснював
день 1. Файл із розширенням `.jsx` містить код JavaScript разом із розміткою, схожою на HTML. Браузер такої розмітки
не розуміє, тому Vite перетворює її на звичайний JavaScript, перш ніж віддати код браузеру. Файл із розширенням `.css`
описує вигляд сторінки мовою **CSS**: шрифти, кольори, розміри й відступи.

```jsx
import { useState } from "react";
import Button from "./Button.jsx";
import "./App.css";
```

Запис `from "react"` є голим вказівником, а `useState` є іменованим експортом. Запис `from "./Button.jsx"` є відносним
шляхом і бере типовий експорт: зазвичай так оформлюють компонент, який займає цілий файл. Запис `import "./App.css"`
працює лише завдяки бандлеру: Vite додає стилі на сторінку, а мова JavaScript такого не передбачає.

**Завантаження за потреби.** Функція React `lazy` приймає функцію з динамічним імпортом і завантажує код компонента,
коли той знадобиться. Документація вимагає, щоб компонент був типовим експортом, бо `lazy` читає поле `.default`
результату.

**Змінна поза компонентом спільна.** Змінна на верхньому рівні модуля, тобто оголошена поза будь-якою функцією,
існує, доки відкрита сторінка. Її бачать усі копії компонента, тобто всі місця на сторінці, де показано цей
компонент. Зміна такої змінної під час рендеру робить результат непередбачуваним, і глава `Keeping Components Pure`
документації React показує це на лічильнику гостей.

**Дві копії React.** Пакет `react-dom` містить ту частину React, яка працює в браузері, зокрема показує компоненти на
сторінці. Хуки працюють, лише якщо `react` у вашому коді й `react` усередині `react-dom` є тим самим модулем. Коли
пакет помилково приносить власну копію, з'являється помилка про неправильний виклик хука, а команда `npm ls react`
показує більше однієї версії. Щоб такого не сталося, бібліотеки описують React у розділі `peerDependencies`. Цей запис
означає: «я працюю поруч із React, який уже стоїть у проєкті, власної копії мені не треба». Зараз `react-dom` версії
19.3.1 вимагає саме так, і реєстр npm показує цей запис за такою командою:

```text
$ npm view react-dom@19.3.1 peerDependencies
{ react: '^19.3.1' }
```

Отже, у вашому проєкті має стояти `react`, версія якого підходить під діапазон `^19.3.1`.

## Перевірте себе

Спершу дайте відповідь самостійно, уголос або письмово, і лише потім розгортайте пояснення.

**1. `main.js` імпортує `x.js` і `y.js`, а обидва вони імпортують `z.js`. У якому порядку виконаються файли, якщо
кожен друкує своє ім'я?**

<details><summary>Відповідь</summary>

`z.js`, `x.js`, `y.js`, `main.js`. Кожен файл виконується після своїх залежностей. Файл `z.js` виконується один раз,
хоча його імпортують двічі, а `main.js` виконується останнім, навіть якщо його перший рядок стоїть вище за `import`.

</details>

**2. Чому `import { a } from "./a.js"` не можна поставити в `if`, а `await import("./a.js")` можна?**

<details><summary>Відповідь</summary>

Рядок `import` рушій обробляє до виконання коду, щоб побудувати граф модулів і зв'язати імена, тому результат умови ще
не відомий. Вираз `import()` є звичайним викликом: він запускає завантаження, коли до нього дійшов код, і повертає
проміс.

</details>

**3. У `package.json` стоїть `"date-lib": "~2.3.1"`. Які з версій 2.3.0, 2.3.1, 2.3.9, 2.4.0, 3.0.0 підходять? Що
зміниться для `^2.3.1`?**

<details><summary>Відповідь</summary>

Під `~2.3.1` підходять 2.3.1 і 2.3.9. Під `^2.3.1` підходять 2.3.1, 2.3.9 і 2.4.0. Версія 2.3.0 нижча за початок
діапазону, а 3.0.0 має інше мажорне число.

</details>

**4. Колега вручну змінив діапазон у `package.json`, і новий діапазон не включає версію з файла блокування. Що зробить
`npm install`, а що `npm ci`?**

<details><summary>Відповідь</summary>

`npm install` вибере версію, яка підходить, і оновить файл блокування. `npm ci` зупиниться з помилкою `EUSAGE` і
нічого не встановить, бо ця команда ніколи не змінює файл блокування.

</details>

**5. Чому `from "./helper"` працює у проєкті на Vite, але падає в `node main.js`? Чому `from "react"` не запрацює в
браузері без інструментів?**

<details><summary>Відповідь</summary>

Vite дописує пропущене розширення, а Node для відносних шляхів вимагає повну назву файла. Браузер працює з адресами й
не шукає в `node_modules`, тому голу назву він без карти імпортів не розпізнає. Vite переписує її на справжню адресу.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| модуль | файл із власними іменами, які видно ззовні лише через `export` |
| типовий експорт | один експорт на файл з іменем `default`, ім'я в іншому файлі вибирають самі |
| голий вказівник | вказівник без шляху, назва пакета: `"react"` |
| діапазон версій | запис на кшталт `^4.17.0`, який описує, які версії підходять |
| файл блокування | `package-lock.json`, точні версії всього дерева пакетів |
| Node | програма, яка виконує JavaScript поза браузером |
| npm | реєстр пакетів і програма, яка встановлює пакети в проєкт |
| термінал | програма, у якій людина вводить команди текстом, а комп'ютер виконує їх |
| прапорець | слово з дефісом після назви команди, яке змінює її поведінку |
| тег | позначка в кутових дужках у файлі HTML, яка каже браузеру, що показати чи завантажити |
| бібліотека | готовий код, який написали інші люди, щоб ним користувалися різні програми |
| пакет | бібліотека чи інструмент, оформлені так, щоб їх могла встановити програма npm |
| залежність | файл чи пакет, без якого інший файл чи проєкт не працює |
| дерево залежностей | пакети проєкту разом із їхніми залежностями, залежностями тих залежностей і так далі |
| стек викликів | список функцій, які викликали одна одну до місця помилки |
| `SyntaxError` | помилка, яку рушій кидає, коли код записано не за правилами мови |
| MDN | великий онлайн-довідник з JavaScript і технологій браузера |
| проміс | об'єкт, який представляє результат роботи, що ще не завершилася |
| бандлер | програма, яка записує код модулів у кілька файлів, готових для браузера |
| збирання | робота бандлера, після якої з'являються файли для браузера |
| збірка | файли, які вийшли після збирання |
| відносний вказівник | вказівник, який починається з `./` або `../` і описує шлях до файла |
| сервер | програма, яка за адресою файла віддає браузеру його вміст |
| карта імпортів | запис у тегу `<script type="importmap">`, який каже браузеру, де шукати модуль за назвою |
| консоль браузера | панель інструментів розробника, де браузер показує помилки й те, що друкує `console.log` |
| архів | один файл, у якому упаковано багато інших файлів |
| git | програма, яка зберігає історію змін файлів проєкту |
| закомітити | записати поточний стан файлів в історію git |

| кеш npm | тека поза проєктом, де npm зберігає завантажені пакети |
| компонент | функція React, яка повертає опис частини сторінки |
| рендер | один виклик компонента, під час якого React отримує опис частини сторінки |
| хук | функція React, назва якої починається з `use` і яку викликають лише на верхньому рівні компонента |
