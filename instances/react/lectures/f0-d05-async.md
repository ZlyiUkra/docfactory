# Лекція. День 5. Асинхронність

Ця лекція пояснює, чому JavaScript не чекає на мережу, що таке проміс і як працюють `async` та `await`. Читання займе
близько 30 хвилин. Усі приклади запущено на Node 24, а вивід під ними справжній. Числа часу округлено, бо від запуску
до запуску вони трохи різняться. Браузерні подробиці описано за документацією.

**Після лекції ви зможете пояснити:**

- чому програма має один потік виконання і що таке цикл подій;
- чим задача відрізняється від мікрозадачі;
- у яких станах буває проміс і що повертає `then`;
- що насправді роблять `async` і `await`;
- чому запит іде в мережу вже в ту мить, коли ви викликаєте функцію, і чому `Promise.all` не запускає запитів, а лише
  чекає, поки завершаться вже запущені;
- коли використовувати `Promise.all`, `Promise.allSettled`, `Promise.race` і `Promise.any`;
- як виникає гонка відповідей на екрані й як її уникнути.

## Ситуація: сторінка, яка не може чекати

Уявіть сторінку каталогу. Користувач вводить текст, програма запитує сервер, і відповідь приходить через 400
мілісекунд. Якби програма просто стояла й чекала, сторінка всі ці 400 мілісекунд не реагувала б на клавіші. Причина в
тому, що код JavaScript сторінки виконується в одному **потоці**: у кожну мить рушій (програма, яка виконує
JavaScript) робить лише одну справу.

Наступний код просить таймер спрацювати через 100 мс, а потім займає потік циклом на 500 мс:

```js
const start = performance.now();
setTimeout(() => {
  console.log("таймер спрацював через", Math.round(performance.now() - start), "мс");
}, 100);

while (performance.now() - start < 500) {
  // нічого не робимо, лише займаємо єдиний потік
}
console.log("цикл закінчився через", Math.round(performance.now() - start), "мс");
```

```text
цикл закінчився через 500 мс
таймер спрацював через 503 мс
```

Таймер просили на 100 мс, а спрацював він після 500 мс. Отже, поки код виконується, нічого іншого статися не може.
Звідси правило, на якому побудовано все інше: довгу роботу треба віддавати назовні й не чекати на неї в потоці.
Мережу, таймери й читання файлів виконує браузер або Node поза вашим кодом. Вашому коду лишається сказати, що зробити,
коли результат буде готовий.

## Цикл подій: хто вирішує, що виконувати далі

**Цикл подій** (англійською event loop) — це механізм, який раз за разом вибирає, що виконати наступним. Він працює з
двома видами черг:

- **Задача** (task) — це окрема порція роботи: спрацював таймер, користувач клацнув мишею, прийшли дані. Задачі лежать
  у чергах задач.
- **Мікрозадача** (microtask) — це маленька робота, яку треба виконати одразу після поточного коду. Сюди потрапляють
  функції з `then`, продовження `async`-функцій після `await` і функції з `queueMicrotask`.

**Що саме є задачею.** Специфікація HTML описує, що браузер ставить у черги задач, а довідник MDN додає до цього запуск
самої програми. Кожен рядок нижче стає окремою задачею:

| Що сталося | Приклад |
|---|---|
| почала виконуватися програма | браузер запускає завантажений скрипт |
| спрацював таймер | `setTimeout`, `setInterval` |
| користувач щось зробив | клацання мишею, натискання клавіші |
| прийшли дані з мережі | браузер отримав відповідь на `fetch` |
| надійшло повідомлення | `postMessage`, `MessageChannel` |
| браузер відреагував на зміну документа чи переходить на іншу сторінку | вставлений елемент, перехід за посиланням |
| браузер оновлює екран | усередині цієї роботи викликаються функції з `requestAnimationFrame` |

**Що саме є мікрозадачею.** Перелік значно коротший, і в браузері його легко запам'ятати:

| Що ставить мікрозадачу | Приклад |
|---|---|
| проміс, що виконався | функції з `then`, `catch`, `finally` |
| `await` | продовження `async`-функції після `await` |
| пряме прохання | `queueMicrotask(функція)` |
| спостереження за документом | функція, передана в `MutationObserver` |

Перевірмо це кодом. Програма нижче нічого корисного не робить: кожен її рядок лише ставить одну функцію в чергу й друкує
своє ім'я, щоб ми побачили, у якому порядку браузер виконує різні види роботи. На сторінці є кнопка й порожній блок:

```html
<button id="button">Кнопка</button>
<div id="box"></div>
```

```js
const button = document.querySelector("#button");
const box = document.querySelector("#box");

// Обробник клацання: виконається, коли кнопку клацнуть.
button.addEventListener("click", () => console.log("обробник click"));

// Спостерігач: браузер викличе цю функцію мікрозадачею після зміни атрибута блока.
const observer = new MutationObserver(() => console.log("MutationObserver"));
observer.observe(box, { attributes: true });

console.log("синхронний код: початок");

// Задача: таймер.
setTimeout(() => console.log("setTimeout"), 0);

// Задача: повідомлення між двома кінцями каналу.
const channel = new MessageChannel();
channel.port1.onmessage = () => console.log("MessageChannel");
channel.port2.postMessage("привіт");

// Мікрозадача: пряме прохання.
queueMicrotask(() => console.log("queueMicrotask"));

// Мікрозадача: функція з then.
Promise.resolve().then(() => console.log("then"));

// Мікрозадача: продовження async-функції після await.
async function run() {
  await null;
  console.log("після await");
}
run();

// Зміна атрибута: саме тут спостерігач ставить свою мікрозадачу.
box.setAttribute("data-state", "new");

// Клацання з коду: обробник виконується прямо тут, а не в черзі.
button.click();
console.log("одразу після button.click()");

console.log("синхронний код: кінець");
```

Запуск у браузері Chrome 157 без вікна надрукував таке:

```text
синхронний код: початок
обробник click
одразу після button.click()
синхронний код: кінець
queueMicrotask
then
після await
MutationObserver
setTimeout
MessageChannel
```

Цей вивід читається трьома частинами:

| Рядки виводу | Що це за робота | Чому саме тут |
|---|---|---|
| від `синхронний код: початок` до `синхронний код: кінець` | поточна задача, тобто сам скрипт | вона виконується до кінця, і ніщо її не перериває |
| від `queueMicrotask` до `MutationObserver` | мікрозадачі | вони виконуються одразу після скрипта, у тому порядку, у якому їх поставили. Спостерігач останній, бо `setAttribute` стоїть у коді після решти |
| `setTimeout`, `MessageChannel` | задачі | кожна чекає, поки мікрозадачі закінчаться. Це дві різні черги задач, тому специфікація не обіцяє, яка з них буде першою |

Практичний висновок такий. Код у `then` чи після `await` завжди виконається раніше за `setTimeout(функція, 0)`, поставлений у
тому самому скрипті, бо черга мікрозадач спорожніє раніше, ніж браузер візьме наступну задачу. Тому `setTimeout` із нулем не
означає «одразу»: він означає «після всіх мікрозадач, коли дійде черга».

Цей запуск показує ще чотири речі, які часто плутають:

- **Клацання з коду не є задачею.** Справжнє клацання користувача приходить задачею, а виклик `button.click()` запускає
  обробник одразу, посеред поточного коду. Тому рядок `обробник click` стоїть перед рядком `одразу після button.click()`.
- **`setTimeout` із нулем не стає мікрозадачею.** Він усе одно ставить задачу, тому всі мікрозадачі виконуються раніше.
- **Запит `fetch` дає і задачу, і мікрозадачу.** Прихід відповіді є задачею. Вона виконує проміс, а ваша функція з `then`
  уже є мікрозадачею.
- **`requestAnimationFrame` не є мікрозадачею.** Браузер викликає таку функцію під час оновлення екрана. За специфікацією
  це частина задачі оновлення екрана, тому рядка цього виклику немає в запуску вище: браузер без вікна за час досліду його
  не викликав.

У Node черги влаштовано інакше. Задачами там є `setTimeout`, `setImmediate` і готове читання файла. Функції з
`process.nextTick` лежать в окремій черзі, яка не входить до мікрозадач. Node виконує її перед мікрозадачами, якщо код
запущено як файл CommonJS. У модулі ES порядок інший: у нашому запуску спершу пройшли мікрозадачі, а потім `process.nextTick`.

Цикл працює так: він бере одну задачу й виконує її до кінця, потім виконує всі мікрозадачі, включно з тими, що
з'явилися під час цього виконання, і лише потім бере наступну задачу. Ніхто не може перервати код посередині, тому між
двома рядками функції без `await` інший код не змінить жодної змінної.

Покроковий приклад показує, що мікрозадачі виконуються після кожної задачі, а не лише один раз:

```js
console.log("старт");

setTimeout(() => {
  console.log("таймер 1");
  Promise.resolve().then(() => console.log("мікрозадача всередині таймера 1"));
}, 0);

setTimeout(() => console.log("таймер 2"), 0);

Promise.resolve().then(() => {
  console.log("мікрозадача А");
  queueMicrotask(() => console.log("мікрозадача Б, поставлена з А"));
});

console.log("кінець файла");
```

```text
старт
кінець файла
мікрозадача А
мікрозадача Б, поставлена з А
таймер 1
мікрозадача всередині таймера 1
таймер 2
```

| Крок | Що виконується | Черга задач після кроку | Черга мікрозадач після кроку |
|------|----------------|-------------------------|------------------------------|
| 1 | Код файла від початку до кінця | таймер 1, таймер 2 | А |
| 2 | Мікрозадача А ставить Б | таймер 1, таймер 2 | Б |
| 3 | Мікрозадача Б | таймер 1, таймер 2 | порожньо |
| 4 | Задача «таймер 1» ставить нову мікрозадачу | таймер 2 | всередині таймера 1 |
| 5 | Мікрозадача всередині таймера 1 | таймер 2 | порожньо |
| 6 | Задача «таймер 2» | порожньо | порожньо |

Рядок `мікрозадача всередині таймера 1` стоїть перед рядком `таймер 2`, хоча другий таймер чекав у черзі раніше.
Причина в тому, що черга мікрозадач спорожніла перед тим, як цикл узяв наступну задачу.

Звідси й небезпека: якщо мікрозадачі весь час створюють нові мікрозадачі, цикл не дійде до наступної задачі. Ми
поставили таймер із затримкою 0 і 300 мс запускали мікрозадачі одну за одною, і таймер спрацював лише через 303 мс. У
браузері оновлення сторінки теж окрема задача, тому така програма на цей час заморозить екран.

## Проміс: об'єкт, який представляє майбутній результат

**Проміс** (англійською promise, «обіцянка») — це об'єкт, який представляє результат роботи, що ще не завершилася.
Його повертає функція замість самого результату. Проміс перебуває в одному з трьох станів:

| Стан | Що він означає | Куди веде |
|------|----------------|-----------|
| очікує (pending) | результату ще немає | може стати одним із двох наступних |
| виконано (fulfilled) | робота вдалася, є значення | кінцевий стан |
| відхилено (rejected) | робота не вдалася, є причина, зазвичай об'єкт `Error` | кінцевий стан |

Проміс, який став виконаним або відхиленим, називають **завершеним** (settled). Більше він не змінюється.

```js
console.log("до конструктора");
const order = new Promise((resolve) => {
  console.log("функція всередині конструктора працює одразу");
  setTimeout(() => resolve("замовлення № 41"), 100);
});
console.log("після конструктора", order);

order.then((value) => {
  console.log("значення:", value);
  console.log("після виконання", order);
});
```

```text
до конструктора
функція всередині конструктора працює одразу
після конструктора Promise { <pending> }
значення: замовлення № 41
після виконання Promise { 'замовлення № 41' }
```

Подивимося на кожен рядок:

- `new Promise(функція)` створює проміс і одразу викликає передану функцію. Отже, робота починається в момент
  створення.
- `resolve` — це функція, яку дає конструктор. Її виклик робить проміс виконаним із переданим значенням. Є й друга
  функція `reject`, яка робить проміс відхиленим.
- `order.then(функція)` просить викликати функцію зі значенням, коли воно буде. Сам рядок нічого не чекає: код іде
  далі.

### Що повертає `then`

Метод `then` повертає **новий проміс**. Його результатом стає те, що поверне передана функція. Так будують ланцюжки:

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

later(100, 5)
  .then((n) => n * 2)
  .then((n) => later(100, n + 1))
  .then((n) => {
    console.log("результат ланцюжка:", n);
  });
```

```text
результат ланцюжка: 11
```

Функція `later` повертає проміс, який через `ms` мілісекунд виконується значенням `value`. Перший `then` отримує 5 і
повертає 10. Другий `then` повертає не число, а проміс, і ланцюжок чекає на нього ще 100 мс. Третій отримує вже готове
11.

Якщо забути `return`, ланцюжок не дізнається про внутрішню роботу. MDN називає такий проміс **плавучим** (floating),
бо за ним ніхто не стежить:

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

later(10, "користувач")
  .then((user) => {
    later(50, user + " і його замовлення");
  })
  .then((orders) => {
    console.log("наступний then отримав:", orders);
  });
```

```text
наступний then отримав: undefined
```

### Як рухаються помилки

Відхилений проміс пропускає всі `then` до найближчого `catch`. Виняток, кинутий усередині `then`, теж відхиляє проміс.
Після `catch` ланцюжок продовжує працювати зі значенням, яке той повернув:

```js
const refuse = () => Promise.reject(new Error("сервер не відповів"));

refuse()
  .then(() => console.log("цей then пропущено"))
  .catch((error) => {
    console.log("catch:", error.message);
    return "значення за замовчуванням";
  })
  .then((value) => console.log("після catch:", value));
```

```text
catch: сервер не відповів
після catch: значення за замовчуванням
```

Якщо помилку не перехопив ніхто, вона стає **необробленим відхиленням** (unhandled rejection). Node друкує її й
завершує процес із кодом 1.
Браузер пише в консолі `Uncaught (in promise)` і запускає подію `unhandledrejection`, а сторінка працює далі.

## `async` і `await`: той самий проміс іншим записом

Ланцюжки `then` важко читати, коли кроків багато. Слова `async` і `await` дозволяють записати те саме як звичайний
код. Під ними ті самі проміси:

- Функція зі словом `async` **завжди повертає проміс**. Значення з `return` стає значенням проміса, а виняток
  усередині функції робить проміс відхиленим.
- Слово `await` усередині такої функції призупиняє лише цю функцію, доки проміс не завершиться. Решта програми працює
  далі. Якщо проміс виконано, `await` дає його значення. Якщо відхилено, `await` кидає виняток у цьому місці, і
  звичайний `try…catch` його ловить.

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));
const refuseLater = (ms, text) =>
  new Promise((_, reject) => setTimeout(() => reject(new Error(text)), ms));

async function loadRate() {
  try {
    return await refuseLater(50, "курс недоступний");
  } catch (error) {
    console.log("перехоплено:", error.message);
    return await later(50, 41.5);
  } finally {
    console.log("finally виконується в будь-якому разі");
  }
}

console.log("курс:", await loadRate());
```

```text
перехоплено: курс недоступний
finally виконується в будь-якому разі
курс: 41.5
```

Функція `refuseLater` повертає проміс, який через `ms` мілісекунд відхиляється. Рядок `await loadRate()` наприкінці
стоїть поза будь-якою функцією: **`await` на верхньому рівні** дозволений лише в модулях.

Тіло `async`-функції виконується одразу й синхронно до першого `await`, а решта стає мікрозадачею, коли проміс
завершиться. Теорія дня показує це докладно.

**Без `await` ви отримуєте проміс, а не значення.** Це найчастіша помилка новачка:

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

const total = later(10, 42);
console.log(total + 1);

const list = later(10, ["чай"]);
try {
  list.map((x) => x);
} catch (error) {
  console.log(error.name + ":", error.message);
}
```

```text
[object Promise]1
TypeError: list.map is not a function
```

**`return` без `await` у `try`.** Якщо написати `return refuseLater(...)` без `await`, функція вийде з `try` раніше,
ніж проміс відхилиться, і `catch` цієї функції помилку не побачить. Отже, усередині `try` пишіть `return await`.

## Разом чи по черзі: запит починається в момент виклику

Важлива думка цього дня така: `await` і `Promise.all` нічого не запускають. Запит починається тоді, коли ви
**викликали функцію**, яка його створює. Простежимо за цим із часовими позначками:

```js
const start = performance.now();
const now = () => Math.round((performance.now() - start) / 50) * 50;

function load(name, ms) {
  console.log(now(), "мс: старт", name);
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log(now(), "мс: готово", name);
      resolve(name);
    }, ms);
  });
}

const stock = load("залишки", 200);
const price = load("ціна", 400);
console.log(now(), "мс: обидва запити вже йдуть, Promise.all ще не викликано");

const result = await Promise.all([stock, price]);
console.log(now(), "мс:", result);
```

```text
0 мс: старт залишки
0 мс: старт ціна
0 мс: обидва запити вже йдуть, Promise.all ще не викликано
200 мс: готово залишки
400 мс: готово ціна
400 мс: [ 'залишки', 'ціна' ]
```

| Запис | Коли стартує другий запит | Загальний час |
|-------|---------------------------|---------------|
| `const a = await load("залишки", 200);` і далі `const b = await load("ціна", 400);` | після відповіді на перший | 200 + 400 = 600 мс |
| `load` викликано двічі, потім `await Promise.all([stock, price])` | одразу | більший із двох: 400 мс |

Перший запис виклав незалежні запити в чергу, і другий запит даремно чекає на перший. Це називають **водоспадом**
(waterfall).

**Коли послідовний запис правильний.** Якщо наступний запит залежить від відповіді попереднього, чекати треба.
Наприклад, сервер віддає товари сторінками, і адресу наступної сторінки ви дізнаєтеся лише з відповіді:

```js
const PAGES = {
  start: { items: ["чай", "кава"], next: "p2" },
  p2: { items: ["какао"], next: null },
};
const getPage = (id) =>
  new Promise((resolve) => setTimeout(() => resolve(PAGES[id]), 100));

const all = [];
let pageId = "start";
while (pageId !== null) {
  const page = await getPage(pageId);
  all.push(...page.items);
  pageId = page.next;
}
console.log(all);
```

```text
[ 'чай', 'кава', 'какао' ]
```

Тут `await` у циклі не помилка, бо інакше ніяк. Запитання, яке все вирішує: чи потрібна другому запиту відповідь
першого?

**«Разом» не означає «паралельно» в розумінні процесора.** Мережу чи таймер обслуговують поза вашим кодом, тому
чекання справді відбувається одночасно. Обчислення виконує той самий один потік, і `async` тут не допомагає:

```js
function busy(ms) {
  const start = performance.now();
  while (performance.now() - start < ms) {}
}

async function heavy() {
  busy(300);
}

const started = performance.now();
await Promise.all([heavy(), heavy()]);
console.log(Math.round((performance.now() - started) / 100) * 100, "мс");
```

```text
600 мс
```

Для справді паралельних обчислень у браузері існують окремі потоки, Web Workers, але ця тема виходить за межі дня.

## Чотири способи чекати на кілька промісів

| Метод | Коли завершується | Що дає | Коли брати |
|-------|-------------------|--------|------------|
| `Promise.all` | усі виконано, або перше відхилення | масив значень у порядку передачі | потрібні всі результати, без одного немає сенсу |
| `Promise.allSettled` | усі завершилися | масив об'єктів зі `status` і `value` чи `reason` | кожен результат цікавий окремо |
| `Promise.race` | перший завершений, будь-який | значення чи причину першого | обмеження за часом |
| `Promise.any` | перший виконаний | значення першого вдалого | кілька запасних джерел |

Масив `Promise.all` завжди йде в порядку передачі, а не в порядку приходу відповідей:

```js
const started = performance.now();
const at = () => Math.round((performance.now() - started) / 100) * 100;
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

const results = await Promise.all(
  [300, 100, 200].map(async (ms) => {
    const value = await later(ms, ms);
    console.log(at(), "мс: прийшла відповідь", value);
    return value;
  }),
);
console.log(at(), "мс: масив", results);
```

```text
100 мс: прийшла відповідь 100
200 мс: прийшла відповідь 200
300 мс: прийшла відповідь 300
300 мс: масив [ 300, 100, 200 ]
```

Відхилення `Promise.all` **не скасовує решту роботи**. Запити продовжуються, а їхні результати просто нікому не
потрібні. Промісу нема чим скасувати роботу, і MDN пропонує для цього `AbortController`, про який розповість день 6.
Ми перевірили це так: `Promise.all` відхилився на 50 мс, а таймер на 150 мс усе одно спрацював пізніше.

**Пастка з масивом.** Запис `[await slow, await fast]` виглядає безпечно, але він небезпечний, якщо швидкий проміс
відхиляється раніше:

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));
const refuseLater = (ms, text) =>
  new Promise((_, reject) => setTimeout(() => reject(new Error(text)), ms));

async function bad() {
  const slow = later(100, "повільний");
  const fast = refuseLater(10, "швидка помилка");
  return [await slow, await fast];
}

try {
  await bad();
} catch (error) {
  console.log("перехоплено:", error.message);
}
```

```text
Error: швидка помилка
```

Рядок `перехоплено` не надруковано, а процес завершився з кодом 1. На 10-й мілісекунді `fast` уже відхилено, а на
нього ще ніхто не чекає, бо код стоїть на `await slow`. Node вважає таке відхилення необробленим. Метод `Promise.all`
не має цієї проблеми, бо підписується на всі проміси одразу.

## Гонка відповідей

**Гонка** (англійською race condition) виникає тоді, коли результат залежить від порядку подій, яким ви не керуєте.
Мережа не обіцяє, що відповіді прийдуть у тому порядку, у якому пішли запити.

Приклад із числами. Користувач вводить у пошук «к», а через 50 мс дописує «а». Запит «к» складний і займає 500 мс, а
запит «ка» займає 100 мс.

| Час | Подія | Що на екрані |
|-----|-------|--------------|
| 0 мс | пішов запит «к» | порожньо |
| 50 мс | пішов запит «ка» | порожньо |
| 150 мс | прийшла відповідь «ка» | результати для «ка» |
| 500 мс | прийшла відповідь «к» | результати для «к» — це застарілий результат |

```js
const DELAYS = { к: 500, ка: 100 };
const search = (text) =>
  new Promise((resolve) =>
    setTimeout(() => resolve("результати для «" + text + "»"), DELAYS[text]),
  );

let screen = "порожньо";

async function onInput(text) {
  const result = await search(text);
  screen = result;
  console.log("на екрані:", screen);
}

onInput("к");
setTimeout(() => onInput("ка"), 50);
```

```text
на екрані: результати для «ка»
на екрані: результати для «к»
```

У полі пошуку написано «ка», а на екрані лишилися результати для «к». Найпростіший захист такий: пам'ятати номер
останнього запиту й ігнорувати відповідь, якщо він уже не останній.

```js
const DELAYS = { к: 500, ка: 100 };
const search = (text) =>
  new Promise((resolve) =>
    setTimeout(() => resolve("результати для «" + text + "»"), DELAYS[text]),
  );

let screen = "порожньо";
let lastRequest = 0;

async function onInput(text) {
  lastRequest += 1;
  const thisRequest = lastRequest;
  const result = await search(text);
  if (thisRequest !== lastRequest) {
    console.log("відкинуто застарілу відповідь:", result);
    return;
  }
  screen = result;
  console.log("на екрані:", screen);
}

onInput("к");
setTimeout(() => onInput("ка"), 50);
```

```text
на екрані: результати для «ка»
відкинуто застарілу відповідь: результати для «к»
```

Константа `thisRequest` — замикання з дня 3: кожен виклик `onInput` має власну. Змінна `lastRequest` спільна, тому
після `await` функція бачить її найновіше значення.

## Типові хибні уявлення

**«`Promise.all` запускає запити».** Запити вже запущено, коли ви викликали функції в масиві. `Promise.all` лише чекає
на готові проміси.

**«`async` переносить код у фоновий потік».** Функція виконується в тому самому потоці. Важке обчислення в ній
заморожує сторінку так само, як у звичайній функції.

**«`await` зупиняє всю програму».** Призупиняється лише поточна функція. Тому під час `await` інший код може змінити
спільні змінні, і після `await` значення можуть бути вже інші.

**«`setTimeout(f, 0)` виконується негайно».** Спершу мають закінчитися поточний код і всі мікрозадачі. Сама затримка
теж означає мінімум, а не точний час: таймер може спрацювати пізніше, а в неактивних вкладках браузер навмисно рідшає
таймери.

**«Відхилений `Promise.all` зупинив решту запитів».** Запити продовжуються. Скасування треба робити окремо.

**«`forEach` з `async` дочекається всіх».** `forEach` ігнорує проміси, які повертає функція. Теорія дня показує це на
прикладі.

## Як це проявиться в React

**Функцію ефекту не роблять `async`.** Функція, яку ви передаєте в `useEffect`, може повернути лише функцію очищення,
а `async`-функція повертає проміс. Тому документація оголошує `async`-функцію всередині ефекту й одразу її викликає.

**Гонка й прапорець `ignore`.** Коли `userId` змінюється з `Alice` на `Bob`, відповідь про Alice може прийти пізніше.
Документація React розв'язує це так само, як номер запиту вище: ефект створює змінну `ignore`, функція очищення
встановлює її в `true`, а після `await` код перевіряє її перед записом у стан. Глава називається `Synchronizing with
Effects`, а до самих ефектів ви дійдете у фазі 1.

**Водоспад у дереві компонентів.** Батьківський компонент завантажує дані, рендериться, і лише тоді дочірній компонент
починає свій запит. Документація React називає це мережевим водоспадом: на повільній мережі це значно довше, ніж
завантажувати все разом. План повернеться до цього у фазі 3.

**Значення після `await` може бути застарілим.** Функція-обробник бачить стан свого рендеру (замикання з дня 3), тому
після `await` вона бачить старе значення, навіть якщо стан уже змінився. Стан рендеру поводиться як константа `seen` у
прикладі без React, а новий стан схожий на змінну `price`:

```js
const later = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

let price = 100;
async function logPriceLater() {
  const seen = price;
  await later(50);
  console.log("запам'ятали на старті:", seen, "зараз у змінній:", price);
}
logPriceLater();
price = 120;
```

```text
запам'ятали на старті: 100 зараз у змінній: 120
```

**Часткове завантаження.** Якщо сторінка показує незалежні блоки, `Promise.allSettled` дає показати те, що прийшло, а
замість решти показати повідомлення про помилку. `Promise.all` забрав би всі результати через один збій.

## Перевірте себе

Спершу дайте відповідь самостійно, уголос або письмово, і лише потім розгортайте пояснення.

**1. Що надрукує цей код і чому: `setTimeout(() => console.log("а"), 0); Promise.resolve().then(() =>
console.log("б")); console.log("в");`?**

<details><summary>Відповідь</summary>

`в`, `б`, `а`. Спершу до кінця виконується поточний код. Потім виконуються всі мікрозадачі, серед яких функція з
`then`. Таймер є окремою задачею, тому він виконується останнім, хоча його затримка дорівнює 0.

</details>

**2. Функція `async function f() { return 5; }`. Що лежить у `const x = f()`? Як дістати 5?**

<details><summary>Відповідь</summary>

У `x` лежить проміс, який уже виконано значенням 5. Дістати число можна через `await f()` або `f().then(...)`.

</details>

**3. Два незалежні запити тривають 200 і 900 мс. Скільки часу займе запис із двома `await` поспіль і скільки займе
`Promise.all`?**

<details><summary>Відповідь</summary>

Близько 1100 мс і близько 900 мс. У першому записі другий запит стартує після відповіді першого. У другому обидва
стартують одразу, а `Promise.all` чекає найдовшого.

</details>

**4. `await` у циклі завжди помилка?**

<details><summary>Відповідь</summary>

Ні. Він правильний, коли наступний запит залежить від відповіді попереднього, наприклад коли адреса наступної сторінки
приходить у відповіді. Помилкою він стає для незалежних запитів, бо вони даремно чекають один одного.

</details>

**5. `Promise.all` отримав три проміси, другий відхилився через 50 мс. Що станеться з першим і третім?**

<details><summary>Відповідь</summary>

`Promise.all` одразу стане відхиленим із причиною другого проміса, але перший і третій продовжать роботу, бо проміс
нічого не скасовує. Їхні результати просто нікому не потрібні. Відхилення цих двох, якщо воно станеться пізніше,
необробленим не вважатиметься.

</details>

**6. Чому в полі пошуку може бути «ка», а на екрані результати для «к»? Як цього уникнути?**

<details><summary>Відповідь</summary>

Відповіді можуть прийти не в тому порядку, у якому пішли запити, і пізніша відповідь на старий запит перезаписує новий
результат. Треба позначати кожен запит і відкидати відповідь, якщо запит уже не останній. Можна також скасовувати
старий запит через `AbortController`.

</details>

**7. Чому важка функція, позначена `async`, усе одно заморожує сторінку?**

<details><summary>Відповідь</summary>

Слово `async` лише загортає результат у проміс. Тіло функції виконується в тому самому потоці, а поки потік зайнятий,
цикл подій не може взяти ні клацання миші, ні оновлення екрана.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| потік | одна послідовність виконання: у кожну мить виконується один рядок коду |
| цикл подій | механізм, який вибирає наступну задачу й запускає мікрозадачі |
| задача | окрема порція роботи: таймер, клацання, прихід даних |
| мікрозадача | робота, яка виконується одразу після поточного коду, перед наступною задачею |
| проміс | об'єкт, що представляє результат незавершеної роботи |
| виконано, відхилено, завершено | fulfilled, rejected, settled: стани проміса |
| плавучий проміс | проміс, за яким ніхто не стежить, бо його не повернули й не дочекалися |
| необроблене відхилення | відхилений проміс, якому ніхто не поставив обробника помилки |
| водоспад | незалежні запити, що даремно чекають один одного |
| гонка | результат залежить від порядку подій, яким ви не керуєте |
