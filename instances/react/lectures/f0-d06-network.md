# Лекція. День 6. Мережа

Ця лекція пояснює, що відбувається між сторінкою й сервером, коли код викликає `fetch`. Вона розбирає три запитання,
які найчастіше дивують новачків: чому відповідь 404 не є помилкою для `fetch`, чому тіло відповіді можна прочитати
лише раз і чому на екрані може лишитися відповідь на старий запит. Читання займе близько 35 хвилин. Приклади можна
запускати в Node 24, браузер для них не потрібен.

**Після лекції ви зможете пояснити:**

- з яких частин складаються запит і відповідь і що означають групи статусів;
- чому в коді з `fetch` стоять два `await` і що чекає кожен із них;
- у яких випадках проміс від `fetch` відхиляється, а в яких виконується;
- чому тіло відповіді читається один раз;
- як працюють `AbortController` і `AbortSignal` і чого скасування не робить;
- що таке гонка відповідей і як її прибрати двома способами.

## Ситуація: прогноз не для того міста

Уявіть сторінку прогнозу погоди зі списком міст. Людина вибирає Львів, потім одразу передумує й вибирає Одесу.
Заголовок на сторінці каже «Одеса», а цифри під ним належать Львову. Код нібито правильний: на кожну зміну міста він
робить запит і малює те, що прийшло. У розробника на швидкому домашньому інтернеті ця помилка ніколи не з'являється, а
в користувача в метро з'являється щодня.

Тепер друга ситуація на тій самій сторінці. Сервер перевантажений і відповідає сторінкою HTML із текстом про помилку.
Код не показує повідомлення про збій, а падає з дивним текстом про неправильний символ `<` у JSON.

Обидві проблеми походять не з мови JavaScript, а з того, як влаштовано обмін даними в мережі. Тому почнемо з нього.

## Що таке запит і відповідь

Браузер і сервер — дві окремі програми, часто на різних континентах. Вони домовилися про спільні правила розмови, і ці
правила називаються **HTTP**. Розмова завжди однакова: браузер надсилає один запит і отримує одну відповідь.

**Запит** складається з таких частин:

- **метод** каже, що клієнт хоче зробити: `GET` просить дані, а `POST` надсилає дані на обробку;
- **адреса** каже, про що йдеться, наприклад `/weather?city=lviv`;
- **заголовки** — це пари «назва й значення» зі службовими відомостями, наприклад `Accept: application/json`;
- **тіло** містить дані, які надсилає клієнт. У запиту `GET` тіла немає, тому параметри записують в адресу.

**Відповідь** має подібну будову:

- **статус** — це тризначне число, яким сервер коротко каже, чим скінчилася справа;
- **заголовки** описують відповідь, наприклад `Content-Type: application/json` каже, що в тілі лежить JSON;
- **тіло** містить самі дані: текст JSON, сторінку HTML, байти картинки.

Перша цифра статусу називає групу:

| Група | Що означає | Приклади |
|-------|------------|----------|
| 2xx | Сервер зробив те, про що просили | 200 готово, 204 готово, але тіла немає |
| 3xx | Те, що шукаєте, лежить деінде | 302 адреса тимчасово інша |
| 4xx | Сервер вважає, що помилився клієнт | 404 такого немає, 401 не назвали себе |
| 5xx | Сервер визнає, що помилився сам | 500 внутрішня помилка, 503 перевантажено |

Статус 404 — це повноцінна, успішна з погляду мережі розмова. Клієнт надіслав запит, сервер його отримав і
відповів: «такого немає». Саме тому `fetch` не вважає такий
результат своєю помилкою. Його робота — провести розмову, а оцінювати її зміст мусить ваш код.

## Два `await`: заголовки приходять раніше за тіло

Відповідь не приходить одним шматком. Спершу з мережі надходять статус і заголовки, а тіло може йти ще довго. Для
великого файла різниця становить хвилини. Тому в коді з `fetch` є два очікування, і вони чекають різного.

Перевіримо це. Для прикладів лекції ми написали маленький вигаданий сервер прогнозу погоди `weather-server.mjs`, його
код не важливий. Адреса `/slow-body` одразу надсилає статус і заголовки, а тіло дописує через 200 мс.

```js
import { start } from "./weather-server.mjs";
const { server, base } = await start();

const t0 = performance.now();
const at = () => Math.round((performance.now() - t0) / 50) * 50;   // час, округлений до 50 мс

const res = await fetch(base + "/slow-body");
console.log(at(), "мс: fetch виконався, статус", res.status, "bodyUsed:", res.bodyUsed);

const data = await res.json();
console.log(at(), "мс: тіло прочитано", data, "bodyUsed:", res.bodyUsed);

server.close();
```

```text
0 мс: fetch виконався, статус 200 bodyUsed: false
200 мс: тіло прочитано { city: 'Львів', temp: 7 } bodyUsed: true
```

Розберемо ключові рядки:

- `await fetch(...)` чекає лише статусу й заголовків. Результат — об'єкт `Response`, тобто опис відповіді. На цю мить
  тіла в пам'яті програми ще немає.
- `await res.json()` чекає, доки дійде все тіло, а потім розбирає його як JSON. Метод `json()` не може повернути дані
  одразу, бо їх ще не надіслали. Саме тому він теж повертає проміс.
- `res.bodyUsed` спершу дорівнює `false`, а після читання `true`. Це поле каже, чи тіло вже хтось почав читати.

**Що з цього випливає.** Статус можна перевірити раніше, ніж дійде тіло, тож не треба завантажувати велику сторінку
помилки, щоб дізнатися про помилку. Є й неприємний наслідок: успіх першого `await` нічого не обіцяє другому, бо
з'єднання може обірватися на середині тіла. Адреса `/cut` нашого сервера надсилає статус 200, половину тексту, а потім
обриває з'єднання. Перший `await` дає `ok` рівне `true`, а `await cut.text()` падає з `TypeError: terminated`. Текст
задає Node, у браузері він буде інший. Тому `try` має охоплювати обидва `await`, а не лише перший.

## Коли проміс від `fetch` відхиляється

Тепер можна точно сказати, що означає успіх `fetch`: клієнт отримав статус і заголовки. Усе, що заважає їх отримати,
дає відхилення проміса. Стандарт Fetch у цьому місці каже коротко: якщо відповідь є мережевою помилкою, проміс
відхиляється з `TypeError`.

| Що сталося | Проміс від `fetch` | `e.name` чи `res.ok` |
|------------|--------------------|----------------------|
| Сервер відповів 200 | виконується | `res.ok` дорівнює `true` |
| Сервер відповів 204 без тіла | виконується | `res.ok` дорівнює `true` |
| Сервер відповів 404 або 500 | виконується | `res.ok` дорівнює `false` |
| Сервер перенаправив на іншу адресу | виконується відповіддю з нової адреси | залежить від нової відповіді |
| На порту ніхто не слухає, немає інтернету | відхиляється | `TypeError` |
| Адресу неможливо розібрати | відхиляється | `TypeError` |
| Браузер заборонив читати чужий сервер (про це нижче) | відхиляється | `TypeError` |
| Викликано `abort()` | відхиляється | `AbortError`, якщо не задано іншої причини |

Запустимо крайні випадки, які найчастіше дивують:

```js
const empty = await fetch(base + "/no-content");
console.log("204: ok =", empty.ok, "| body =", empty.body);
try {
  await empty.json();
} catch (e) {
  console.log("204, json() →", e.name + ":", e.message);
}

const moved = await fetch(base + "/old");
console.log("302: status =", moved.status, "| redirected =", moved.redirected,
  "| url закінчується на", new URL(moved.url).pathname);
```

```text
204: ok = true | body = null
204, json() → SyntaxError: Unexpected end of JSON input
302: status = 200 | redirected = true | url закінчується на /new
```

Тут видно дві пастки:

- **Статус 204.** Поле `ok` дорівнює `true`, але тіла немає, тому `json()` падає. Перевірка `res.ok` каже лише про
  статус і нічого не каже про вміст. Якщо сервер на видалення запису відповідає 204, читати JSON не треба.
- **Перенаправлення.** Статусу 302 ваш код не побачить. `fetch` сам переходить на нову адресу, а в `res.status` лежить
  статус уже другої відповіді. Про перехід кажуть поля `res.redirected` і `res.url`.

**Не спирайтеся на текст помилки.** Рядок `fetch failed`, який ви бачили в теорії дня, написав Node. Браузери пишуть
інші слова, і вони різні в різних браузерах. Стандарт задає лише тип `TypeError`. Тому помилки розрізняють за
`e.name`, а не за `e.message`.

**Заборона браузера.** Браузер за замовчуванням не дає сторінці читати відповідь з іншого **джерела**, тобто з іншого
поєднання протоколу, домену й порту. Це правило захищає людину: чужа сторінка не може прочитати її пошту, навіть якщо
людина ввійшла в пошту в сусідній вкладці. Сервер може дозволити таке читання заголовком
`Access-Control-Allow-Origin`, а весь механізм називається **CORS**. Якщо дозволу немає, код отримає лише `TypeError`
без пояснень. Причину браузер пише в консоль. У Node цього правила немає, а сервер дня віддає сторінку й дані з одного
джерела, тож сьогодні ви цього не зустрінете.

## Тіло відповіді — це потік

Чому тіло не можна прочитати двічі? Причина в тому, як воно зберігається, а точніше в тому, що воно не зберігається.

Тіло відповіді — це **потік**: байти надходять із мережі частинами, і `fetch` не складає їх про запас. Хто читає, той
забирає байти собі. Це логічно: файл на 2 ГБ можна записати на диск частинами, не тримаючи його в пам'яті. Плата за
таку економію одна: прочитане назад не повертається.

Потік можна прочитати власноруч через поле `res.body`. Адреса `/chunks` надсилає три шматки тексту з паузами:

```js
const res = await fetch(base + "/chunks");
const decoder = new TextDecoder();
let count = 0;
for await (const bytes of res.body) {     // кожен bytes — масив байтів Uint8Array
  count += 1;
  console.log("шматок", count + ":", bytes.length, "байтів:", decoder.decode(bytes));
}
console.log("bodyUsed:", res.bodyUsed);
try {
  res.clone();
} catch (e) {
  console.log("clone() після читання →", e.name + ":", e.message);
}
```

```text
шматок 1: 13 байтів: перший 
шматок 2: 13 байтів: другий 
шматок 3: 12 байтів: третій
bodyUsed: true
clone() після читання → TypeError: Response.clone: Body has already been consumed.
```

Цикл `for await` бере з потоку наступний шматок, коли той надійде. Шматок займає 13 байтів на слово з шести літер і
пробілу, бо українська літера в кодуванні UTF-8 займає два байти. `TextDecoder` перетворює байти на текст. У прикладі
межі шматків збіглися з межами слів, а в справжньому потоці межа може пройти посередині літери, тому для такого
читання декодер викликають із параметром `{ stream: true }`. `res.clone()` падає, бо копію можна зробити лише до
першого читання.

Методи `json()`, `text()` і `blob()` роблять те саме, що цей цикл: читають потік до кінця, а потім перетворюють
результат. Звідси правило: прочитайте тіло один раз, збережіть результат у змінну й далі працюйте зі змінною. Копія
через `clone()` потрібна рідко, зокрема коли одну відповідь треба і показати, і покласти в кеш.

Ще одна деталь: `json()` не дивиться ні на статус, ні на заголовок `Content-Type`. Він читає всі байти й намагається
розібрати їх як JSON. Звідси й дивний текст про символ `<` у ситуації з перевантаженим сервером на початку лекції.
Сторінка HTML починається з `<`, а JSON так починатися не може. Якщо перевірити `res.ok` до розбору, то статус 503
стане зрозумілою подією, про яку можна сказати людині, а не збоєм розбору.

## `AbortController` і `AbortSignal`: як зупинити роботу

Іноді результат роботи більше не потрібен: людина пішла зі сторінки або вибрала інше місто. JavaScript не може
примусово зупинити чужу асинхронну функцію. Він може лише попросити, а функція мусить сама вміти слухати таке
прохання. Для цього стандарт DOM описує пару об'єктів.

- **`AbortController`** — це об'єкт, що лишається в того, хто вирішує скасувати. Він має метод `abort()`.
- **`AbortSignal`** — це об'єкт, який лежить у полі `controller.signal` і який віддають виконавцю. Сигнал дозволяє
  лише дізнатися, чи було скасування: поле `aborted`, поле `reason` з причиною і подія `abort`.

Поділ на два об'єкти зроблено навмисно. Виконавець отримує сигнал і може почути прохання, але не може скасувати роботу
сам і не може скасувати її для інших виконавців, які отримали той самий сигнал.

Механізм не прив'язаний до мережі. Покажемо це на функції очікування, яка взагалі не робить запитів, зате виконує те,
що стандарт DOM радить будь-якій функції зі скасуванням.

```js
function wait(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal.aborted) return reject(signal.reason);        // скасовано ще до початку
    const timer = setTimeout(resolve, ms, "дочекалися");
    signal.addEventListener("abort", () => {                 // скасовано під час очікування
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}

const first = new AbortController();
const promise = wait(1000, first.signal);
first.abort(new Error("Користувач закрив вікно"));
first.abort(new Error("Друга причина"));                     // другий виклик нічого не змінить
await promise.catch((e) => console.log("очікування →", e.name + ":", e.message));
console.log("причина в сигналі:", first.signal.reason.message);

const second = new AbortController();
second.abort();                                              // без причини
console.log("типова причина:", second.signal.reason.name);
await wait(1000, second.signal).catch((e) => console.log("новий виклик →", e.name));

```

```text
очікування → Error: Користувач закрив вікно
причина в сигналі: Користувач закрив вікно
типова причина: AbortError
новий виклик → AbortError
```

З цього виводу видно чотири правила:

1. Причину можна передати в `abort(причина)`, і проміс відхилиться саме нею. Тому в такому разі `e.name` уже не
   дорівнює `AbortError`. Код, який упізнає скасування лише за цим іменем, власної причини не впізнає.
2. Другий виклик `abort()` нічого не робить. Стандарт прямо починає алгоритм скасування з перевірки, чи сигнал уже
   скасовано.
3. Без причини браузер або Node створює помилку з іменем `AbortError`.
4. Скасований сигнал лишається скасованим назавжди, тому кожній новій роботі потрібен новий контролер.

Функція `fetch` поводиться так само, як `wait`, але ще ламає потік тіла. Це важливо, бо скасування діє й після
виконання проміса `fetch`. Якщо заголовки вже прийшли, а тіло ще ні, то читання тіла відхилиться:

```js
const controller = new AbortController();
const res = await fetch(base + "/slow-body", { signal: controller.signal });
console.log("fetch уже виконався, статус", res.status);

controller.abort();                        // скасовуємо між заголовками й тілом
try {
  await res.json();
} catch (e) {
  console.log("читання тіла →", e.name + ":", e.message);
}
```

```text
fetch уже виконався, статус 200
читання тіла → AbortError: This operation was aborted
```

### Чого скасування не робить

`abort()` зупиняє очікування у вашій програмі, і браузер чи Node обриває передачу даних. Але він не відкочує того, що
сервер уже зробив. Ми написали вигаданий сервер оплати, який працює 100 мс, а наприкінці збільшує лічильник платежів.
Клієнт надсилає `POST` і викликає `abort()` через 20 мс:

```text
клієнт: AbortError
сервер: платіж проведено, усього 1
наприкінці на сервері платежів: 1
```

Клієнт вважає, що запит скасовано, а гроші списано. Для пошуку це не має значення, бо читання нічого не змінює. Для
запитів, що змінюють дані, скасування не є способом «передумати»: відмінити операцію може лише окремий запит до
сервера.

### Готові сигнали: таймер і поєднання

`AbortSignal.timeout(100)` дає сигнал, який спрацює сам через 100 мс, і помилка матиме ім'я `TimeoutError`.
`AbortSignal.any([...])` дає сигнал, що спрацьовує разом із першим спрацьованим зі списку. Якщо поєднати контролер і
таймер, код зможе розрізнити дві історії для людини: `TimeoutError` означає «сервер довго не відповідає», а
`AbortError` означає «ви самі скасували».

## Гонка відповідей із числами

Повернімося до Львова й Одеси. **Гонка** (англійською race condition) — це ситуація, у якій результат залежить від
того, яка з незалежних дій закінчиться першою. Два запити не зобов'язані повернутися в тому порядку, в якому пішли: у
них можуть бути різні шляхи, різне навантаження й різний обсяг роботи на сервері.

Наш сервер відповідає про Львів через 400 мс, а про Одесу через 100 мс. Людина вибирає Львів у момент 0, а Одесу в
момент 50 мс.

| Час | Хто діє | Що відбувається | На екрані |
|-----|---------|-----------------|-----------|
| 0 мс | Код | Запит про Львів пішов | порожньо |
| 50 мс | Код | Запит про Одесу пішов | порожньо |
| 150 мс | Мережа | Прийшла Одеса (50 + 100) | Одеса |
| 400 мс | Мережа | Прийшов Львів (0 + 400) | Львів |

Остання відповідь перемагає, хоч її запит був старшим. Код без захисту дає такий вивід:

```text
без перевірки:
  прийшла відповідь: odesa → на екрані odesa
  прийшла відповідь: lviv → на екрані lviv
  користувач вибрав odesa, на екрані lviv
```

Є два способи це прибрати, і вони вирішують різне.

**Спосіб перший: скасувати старий запит.** Перед новим запитом код викликає `abort()` на контролері попереднього й
створює новий контролер. Стара відповідь не дійде зовсім. Саме цей спосіб просить план дня, і його код є в теорії та в
завданні.

**Спосіб другий: викинути застарілу відповідь.** Запити йдуть до кінця, але код порівнює, чи відповідь ще актуальна.
Найпростіша перевірка використовує номер запиту:

```js
let lastId = 0;
async function showLatest(city) {
  lastId += 1;
  const id = lastId;               // цей запит запам'ятав свій номер
  const res = await fetch(base + "/weather?city=" + city);
  const data = await res.json();
  if (id !== lastId) {
    console.log("  прийшла відповідь:", data.city, "→ застаріла, викинуто");
    return;
  }
  screen = data.city;
  console.log("  прийшла відповідь:", data.city, "→ на екрані", screen);
}
```

```text
з номером запиту:
  прийшла відповідь: odesa → на екрані odesa
  прийшла відповідь: lviv → застаріла, викинуто
  користувач вибрав odesa, на екрані odesa
```

Змінна `lastId` живе поза функцією й спільна для всіх викликів, а `id` своя в кожному виклику. Коли відповідь
приходить, `id` старого запиту вже не збігається з `lastId`. Це те саме замикання, яке ви розбирали в дні 3.

Скасування економить трафік, бо очікування припиняється, але потребує окремої обробки `AbortError` і працює лише з
функціями, що приймають сигнал. Перевірка актуальності не потребує обробки помилок і працює з будь-яким промісом, зате
стара відповідь завантажується до кінця. Ці способи не заважають один одному, тому їх можна поєднувати.

## Що ви побачите у вкладці «Мережа»

Вкладка Network в інструментах розробника Chrome показує кожен запит окремим рядком. Цей опис спирається на
документацію Chrome, а не на запуск у браузері.

| Де дивитися | Що там |
|-------------|--------|
| Стовпець Status | статус відповіді, а також `(failed)` і `CORS error`, якщо запит не вдався |
| Рядок запиту, вкладка Response | тіло, яке прислав сервер, тож видно сторінку HTML замість JSON |
| Список Throttling | штучне сповільнення мережі, щоб побачити гонку на своєму комп'ютері |

На швидкому каналі гонку майже не видно. Сповільнення розтягує час так, що різниця між запитами стає помітною.

## Типові хибні уявлення

**«Якщо `await fetch` не кинув помилку, запит успішний».** Це означає лише, що прийшли статус і заголовки. Статус може
бути 500, а тіло може обірватися пізніше.

**«`res.ok` означає, що в тілі є дані».** Поле `ok` каже лише, що статус від 200 до 299. За статусу 204 тіла немає, а
сервер може прислати 200 і зламаний JSON.

**«`abort()` скасовує операцію на сервері».** Він зупиняє очікування на вашому боці. Те, що сервер уже зробив,
лишається зробленим.

**«Один контролер можна використовувати для всіх запитів».** Після першого `abort()` його сигнал скасований назавжди,
і кожен наступний `fetch` із ним одразу відхиляється. Один спільний контролер має сенс, лише коли треба разом
скасувати всі запити групи.


## Як це проявиться в React

У React ці самі правила стоять у місці, яке називається **ефектом**. Ефект — це функція, яку React запускає після
оновлення екрана, а `useEffect` — спосіб її оголосити. Функцію, яку ефект повертає, React викликає перед наступним
запуском ефекта з новими даними й коли компонент зникає. У цій функції прибирання зручно скасовувати запит.

Ось частина компонента, який показує прогноз. Ми запустили її в React 19 в імітації браузера jsdom з увімкненим
режимом `StrictMode`.

```js
useEffect(() => {
  const controller = new AbortController();
  fetch(base + "/weather?city=" + city, { signal: controller.signal })
    .then((res) => res.json())
    .then(setData)
    .catch((e) => { if (e.name !== "AbortError") throw e; console.log("запит скасовано:", city); });
  return () => controller.abort();
}, [city]);
```

```text
запит скасовано: lviv
сервер отримав /weather?city=lviv
на екрані: lviv
```

Рядок `запит скасовано` з'явився, хоч місто ніхто не змінював. У режимі розробки `StrictMode` спеціально запускає
ефект двічі, із прибиранням між запусками, щоб знайти код, який погано прибирає за собою. Перший запит скасовано
одразу, другий дійшов до сервера. Тому у вкладці «Мережа» в режимі розробки можна побачити скасований запит, і це не
помилка.

Що ще ви зустрінете:

- Сторінка `useEffect` у документації React показує для тієї самої гонки другий спосіб: прапорець `ignore`, який
  функція прибирання ставить у `true`. Це той самий підхід, що й перевірка номера запиту.
- Документація React радить для завантаження даних готові бібліотеки, наприклад TanStack Query, бо вони вже розв'язали
  гонки, кеш і повторні спроби. Щоб ними користуватися й розуміти їхні помилки, потрібні саме ці знання.

## Перевірте себе

Спершу дайте відповідь самі, вголос або письмово, і лише потім розгортайте наші пояснення.

**1. Сервер відповів статусом 503. Що зробить `await fetch(url)` і чому?**

<details><summary>Відповідь</summary>

Поверне об'єкт `Response` зі `status` 503 і `ok` рівним `false`. Розмова відбулася: клієнт отримав статус і заголовки.
Проміс відхиляється лише тоді, коли відповіді немає зовсім, наприклад немає зв'язку.

</details>

**2. Сервер відповідає 204 на видалення. Код робить `if (res.ok) return await res.json()`. Що станеться?**

<details><summary>Відповідь</summary>

`res.ok` дорівнює `true`, бо 204 входить у діапазон від 200 до 299, але тіла немає. `res.json()` відхилиться із
`SyntaxError: Unexpected end of JSON input`. Для такої відповіді тіло читати не треба.

</details>

**3. Чому `res.text()` після `res.json()` падає, хоч дані вже є в змінній?**

<details><summary>Відповідь</summary>

Тіло є потоком: байти надходять і забираються тим, хто читає, а `fetch` не тримає їх про запас. Дані є лише в змінній,
куди їх поклав перший читач, а метод читає з відповіді. Щоб читати двічі, копію роблять до першого читання через
`res.clone()`.

</details>

**4. Людина натиснула «Скасувати» на запиті `POST`, який створює замовлення. Код отримав `AbortError`. Чи створено
замовлення?**

<details><summary>Відповідь</summary>

Невідомо. `abort()` зупинив очікування на боці клієнта, але сервер міг уже встигнути отримати запит і виконати його.
Щоб дізнатися правду, треба окремо спитати сервер. Тому скасування безпечне для запитів на читання й не гарантує
нічого для запитів, що змінюють дані.

</details>

**5. Запити пішли в порядку А, Б, В, а відповіді прийшли Б, В, А. Що буде на екрані без захисту, зі скасуванням і з
перевіркою номера запиту?**

<details><summary>Відповідь</summary>

Вважаймо, що всі три запити пішли раніше, ніж прийшла перша відповідь. Без захисту лишиться А, бо ця відповідь прийшла
останньою. Зі скасуванням запит В скасує запит Б, а той раніше скасував запит А, тому дійде лише відповідь В. З
перевіркою номера відповіді А і Б дійдуть до коду, але будуть викинуті, тож результат теж В.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| HTTP | правила обміну даними між клієнтом і сервером: один запит, одна відповідь |
| статус | тризначне число у відповіді, яке коротко каже, чим скінчилася справа |
| тіло | дані запиту чи відповіді; у `fetch` воно є потоком байтів |
| `res.ok` | `true`, коли статус від 200 до 299 |
| потік | дані, що надходять частинами й забираються тим, хто читає |
| джерело (origin) | поєднання протоколу, домену й порту |
| CORS | механізм, яким сервер дозволяє сторінці з іншого джерела читати відповідь |
| `AbortController` | об'єкт із методом `abort()`, який лишається в того, хто скасовує |
| `AbortSignal` | об'єкт, який отримує виконавець, щоб дізнатися про скасування |
| `AbortError` | ім'я помилки при скасуванні без власної причини |
| гонка | результат залежить від того, що закінчиться першим |
