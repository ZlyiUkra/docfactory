# Лекція. День 6. Мережа

Ця лекція пояснює, що відбувається між сторінкою й сервером, коли код викликає `fetch`. Вона розбирає три запитання,
які найчастіше дивують новачків: чому відповідь 404 не є помилкою для `fetch`, чому тіло відповіді можна прочитати
лише раз і чому на екрані може лишитися відповідь на старий запит. Читання займе близько 45 хвилин. Приклади можна
запускати в Node 24, браузер для них не потрібен.

**Після лекції ви зможете пояснити:**

- з яких частин складаються запит і відповідь і що означають групи статусів;
- чому в коді з `fetch` стоять два `await` і що чекає кожен із них;
- у яких випадках проміс від `fetch` відхиляється, а в яких виконується;
- чому тіло відповіді читається один раз;
- як працюють `AbortController` і `AbortSignal` і чого скасування не робить;
- що таке гонка відповідей і як її прибрати двома способами.

## Ситуація: прогноз не для того міста

Уявіть сторінку прогнозу погоди зі списком міст. Людина вибирає Львів, потім одразу передумує й вибирає Одесу.
Заголовок на сторінці каже «Одеса», а цифри під ним належать Львову. Код нібито правильний: на кожну зміну міста він
робить запит і малює те, що прийшло. У розробника на швидкому домашньому інтернеті ця помилка ніколи не з'являється, а
в користувача в метро з'являється щодня.

Тепер друга ситуація на тій самій сторінці. Сервер перевантажений і відповідає сторінкою HTML із текстом про помилку.
Код не показує повідомлення про збій, а падає з дивним текстом про неправильний символ `<` у JSON.

Обидві проблеми походять не з мови JavaScript, а з того, як влаштовано обмін даними в мережі. Тому почнемо з нього.

## Що таке запит і відповідь

Браузер і сервер — дві окремі програми, часто на різних континентах. Вони домовилися про спільні правила розмови, і ці
правила називаються **HTTP**. Розмова завжди однакова: браузер надсилає один запит і отримує одну відповідь.

**Запит** складається з таких частин:

- **метод** каже, що клієнт хоче зробити: `GET` просить дані, а `POST` надсилає дані на обробку;
- **адреса** каже, про що йдеться, наприклад `/weather?city=lviv`. Частина після знака `?` містить **параметри**,
  тобто пари «назва=значення». Тут параметр `city` зі значенням `lviv` каже серверу, про яке місто питають;
- **заголовки** — це пари «назва й значення» зі службовими відомостями. Наприклад, заголовок
  `Accept: application/json` каже серверу, що клієнт хоче отримати дані у форматі JSON;
- **тіло** містить дані, які надсилає клієнт. У запиту `GET` тіла немає, тому все, що треба передати, записують в
  адресу як параметри.

**Відповідь** має подібну будову:

- **статус** — це тризначне число, яким сервер коротко каже, чим скінчилася справа;
- **заголовки** описують відповідь, наприклад `Content-Type: application/json` каже, що в тілі лежить JSON;
- **тіло** містить самі дані: текст JSON, сторінку HTML, байти картинки.

Статуси поділено на групи за першою цифрою. Запис `2xx` означає «будь-яке число від 200 до 299», і так само для
решти груп:

| Група | Що означає | Приклади |
|-------|------------|----------|
| 2xx | Сервер зробив те, про що просили | 200 готово, 204 готово, але тіла немає |
| 3xx | Те, що шукаєте, лежить деінде | 302 адреса тимчасово інша |
| 4xx | Сервер вважає, що помилився клієнт | 404 такого немає, 401 клієнт не підтвердив, хто він |
| 5xx | Сервер визнає, що помилився сам | 500 внутрішня помилка, 503 перевантажено |

Статус 404 — це повноцінна, успішна з погляду мережі розмова. Клієнт надіслав запит, сервер його отримав і відповів:
«такого немає». Саме тому `fetch` не вважає такий результат своєю помилкою. Його робота — провести розмову, а
оцінювати її зміст мусить ваш код.

## Два `await`: заголовки приходять раніше за тіло

Відповідь не приходить одним шматком. Спершу з мережі надходять статус і заголовки, а тіло може йти ще довго. Для
великого файла різниця становить хвилини. Тому в коді з `fetch` є два очікування, і вони чекають різного.

Перевіримо це. Для прикладів лекції ми написали маленький вигаданий сервер прогнозу погоди. Збережіть його код у файл
`weather-server.mjs`. Вивчати цей код рядок за рядком не треба: кожна гілка `if` описує одну адресу, а коментар поруч
каже, що сервер робить, коли хтось просить цю адресу.

Кілька слів, щоб коментарі читалися. Функція `createServer` із вбудованого модуля Node `node:http` створює сервер і
викликає функцію `handle` на кожен запит, що прийшов. Перший аргумент `req` описує цей запит, і з нього сервер бере
адресу. Другий аргумент `res` — це відповідь, яку сервер заповнює: `writeHead` задає статус і заголовки, `write`
надсилає шматок тіла, `end` надсилає останній шматок і закриває відповідь, а `destroy` обриває з'єднання, не
закінчивши відповідь.

```js
// weather-server.mjs: вигаданий сервер прогнозу погоди
import { createServer } from "node:http";

const pause = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
const JSON_TYPE = { "Content-Type": "application/json" };

async function handle(req, res) {
  const { pathname, searchParams } = new URL(req.url, "http://localhost");

  if (pathname === "/slow-body") {          // статус і заголовки одразу, тіло через 200 мс
    res.writeHead(200, JSON_TYPE);
    res.flushHeaders();
    await pause(200);
    res.end(JSON.stringify({ city: "Львів", temp: 7 }));
  } else if (pathname === "/cut") {         // статус 200, половина тексту, потім обрив з'єднання
    res.writeHead(200, { "Content-Type": "text/plain" });
    res.write("половина тек");
    await pause(50);
    res.destroy();
  } else if (pathname === "/no-content") {  // статус 204, тіла немає
    res.writeHead(204).end();
  } else if (pathname === "/old") {         // статус 302: дані лежать за адресою /new
    res.writeHead(302, { Location: "/new" }).end();
  } else if (pathname === "/new") {
    res.writeHead(200, JSON_TYPE).end(JSON.stringify({ moved: true }));
  } else if (pathname === "/chunks") {      // три шматки тексту з паузами між ними
    for (const word of ["перший ", "другий ", "третій"]) {
      res.write(word);
      await pause(50);
    }
    res.end();
  } else if (pathname === "/busy") {        // статус 503 і сторінка HTML замість JSON
    res.writeHead(503, { "Content-Type": "text/html" });
    res.end("<!doctype html><h1>Сервер перевантажено</h1>");
  } else if (pathname === "/weather") {     // про Львів відповідає через 400 мс, про інші міста через 100 мс
    const city = searchParams.get("city");
    await pause(city === "lviv" ? 400 : 100);
    res.writeHead(200, JSON_TYPE).end(JSON.stringify({ city, temp: 7 }));
  } else {
    res.writeHead(404).end();
  }
}

// Запускає сервер і повертає його разом із початком адреси. Порт 0 просить систему вибрати вільний порт.
export function start() {
  const server = createServer(handle);
  return new Promise((resolve) => {
    server.listen(0, "127.0.0.1", () => {
      resolve({ server, base: "http://127.0.0.1:" + server.address().port });
    });
  });
}
```

Перший приклад збережіть поруч у файл `example.mjs` і запустіть командою `node example.mjs`. Він просить адресу
`/slow-body`, яка одразу надсилає статус і заголовки, а тіло дописує через 200 мс.

```js
import { start } from "./weather-server.mjs";
const { server, base } = await start();

const t0 = performance.now();
const at = () => Math.round((performance.now() - t0) / 50) * 50;   // час, округлений до 50 мс

const res = await fetch(base + "/slow-body");
console.log(at(), "мс: fetch виконався, статус", res.status, "bodyUsed:", res.bodyUsed);

const data = await res.json();
console.log(at(), "мс: тіло прочитано", data, "bodyUsed:", res.bodyUsed);

server.close();
```

```text
0 мс: fetch виконався, статус 200 bodyUsed: false
200 мс: тіло прочитано { city: 'Львів', temp: 7 } bodyUsed: true
```

Розберемо ключові рядки:

- `await fetch(...)` чекає лише статусу й заголовків. Результат — об'єкт `Response`, тобто опис відповіді. На цю мить
  тіла в пам'яті програми ще немає.
- `await res.json()` чекає, доки дійде все тіло, а потім розбирає його як JSON. Метод `json()` не може повернути дані
  одразу, бо їх ще не надіслали. Саме тому він теж повертає проміс.
- `res.bodyUsed` спершу дорівнює `false`, а після читання `true`. Це поле каже, чи тіло вже хтось почав читати.
- Функція `at` округлює час до 50 мс. Точне число мілісекунд щоразу трохи інше, а округлене число однакове в кожному
  запуску, тому ваш вивід збіжеться з нашим.

**Що з цього випливає.** Статус можна перевірити раніше, ніж дійде тіло, тож не треба завантажувати велику сторінку
помилки, щоб дізнатися про помилку. Є й неприємний наслідок: успіх першого `await` нічого не обіцяє другому, бо
з'єднання може обірватися на середині тіла. Адреса `/cut` нашого сервера надсилає статус 200, половину тексту, а потім
обриває з'єднання. Цей приклад і всі наступні, що звертаються до `base`, запускаються так само, як перший: на початку
файла стоять рядки з `import` і `await start()`, а в кінці `server.close()`. Щоб не повторювати їх, ми показуємо лише
середину.

```js
const cut = await fetch(base + "/cut");
console.log("перший await: ok =", cut.ok);
try {
  await cut.text();                         // тут з'єднання обірветься
} catch (e) {
  console.log("другий await →", e.name + ":", e.message);
}
```

```text
перший await: ok = true
другий await → TypeError: terminated
```

Перший рядок надрукував код після `await fetch`: статус і заголовки прийшли, тому `ok` дорівнює `true`. Другий рядок
надрукував блок `catch`, бо читання тіла не дійшло до кінця. Текст `terminated` задає Node, у браузері він буде інший.
Тому `try` має охоплювати обидва `await`, а не лише перший.

## Коли проміс від `fetch` відхиляється

Тепер можна точно сказати, що означає успіх `fetch`: клієнт отримав статус і заголовки. Усе, що заважає їх отримати,
дає відхилення проміса. Стандарт Fetch описує це так. Коли справжньої відповіді отримати не вдалося, браузер замість
неї створює особливу відповідь, яку стандарт називає **мережевою помилкою** (network error): у неї статус 0, немає
заголовків і немає тіла. Далі стандарт каже коротко: якщо відповідь є мережевою помилкою, проміс від `fetch`
відхиляється з `TypeError`. Тому всі випадки «відповіді немає» виглядають для вашого коду однаково. Виняток лише один:
скасування, про яке йдеться далі в лекції, відхиляє проміс власною помилкою.

Ось два такі випадки. Сервер тут не потрібен, тому цей приклад запускайте окремим файлом, без рядків із `start()`:

```js
try {
  await fetch("http://127.0.0.1:1/");       // на порту 1 ніхто не слухає
} catch (e) {
  console.log("порожній порт →", e.name + ":", e.message);
}
try {
  await fetch("http://");                   // адресу неможливо розібрати
} catch (e) {
  console.log("погана адреса →", e.name + ":", e.message);
}
```

```text
порожній порт → TypeError: fetch failed
погана адреса → TypeError: Failed to parse URL from http://
```

Обидва рядки надрукували блоки `catch`, і в обох `e.name` дорівнює `TypeError`. Таблиця нижче збирає всі випадки
разом. Частину з них ми вже запустили, решту запустимо або пояснимо далі в лекції.

| Що сталося | Проміс від `fetch` | `e.name` чи `res.ok` |
|------------|--------------------|----------------------|
| Сервер відповів 200 | виконується | `res.ok` дорівнює `true` |
| Сервер відповів 204 без тіла | виконується | `res.ok` дорівнює `true` |
| Сервер відповів 404 або 500 | виконується | `res.ok` дорівнює `false` |
| Сервер перенаправив на іншу адресу | виконується відповіддю з нової адреси | залежить від нової відповіді |
| На порту ніхто не слухає, немає інтернету | відхиляється | `TypeError` |
| Адресу неможливо розібрати | відхиляється | `TypeError` |
| Браузер заборонив читати чужий сервер (про це нижче) | відхиляється | `TypeError` |
| Викликано `abort()` | відхиляється | `AbortError`, якщо не задано іншої причини |

Запустимо крайні випадки, які найчастіше дивують:

```js
const empty = await fetch(base + "/no-content");
console.log("204: ok =", empty.ok, "| body =", empty.body);
try {
  await empty.json();
} catch (e) {
  console.log("204, json() →", e.name + ":", e.message);
}

const moved = await fetch(base + "/old");
console.log("302: status =", moved.status, "| redirected =", moved.redirected,
  "| url закінчується на", new URL(moved.url).pathname);
```

```text
204: ok = true | body = null
204, json() → SyntaxError: Unexpected end of JSON input
302: status = 200 | redirected = true | url закінчується на /new
```

Тут видно дві пастки:

- **Статус 204.** Поле `ok` дорівнює `true`, але тіла немає, тому `json()` падає. Метод `json()` спершу збирає тіло в
  рядок, а тут рядок порожній. Порожній рядок не є записом JSON, і розбір закінчується помилкою `SyntaxError`: «JSON
  несподівано закінчився». Перевірка `res.ok` каже лише про статус і нічого не каже про вміст. Якщо сервер на
  видалення запису відповідає 204, читати JSON не треба.
- **Перенаправлення.** Статусу 302 ваш код не побачить. `fetch` сам переходить на нову адресу, а в `res.status` лежить
  статус уже другої відповіді. Про перехід кажуть поля `res.redirected` і `res.url`.

**Не спирайтеся на текст помилки.** Рядки `fetch failed` і `Failed to parse URL` з першого досліду цього розділу
написав Node. Браузери пишуть інші слова, і вони різні в різних браузерах. Стандарт задає лише тип `TypeError`. Тому
помилки розрізняють за `e.name`, а не за `e.message`.

**Заборона браузера.** Браузер за замовчуванням не дає сторінці читати відповідь з іншого **джерела**, тобто з іншого
поєднання протоколу, домену й порту. Адреси `https://mail.example` і `https://shop.example` належать різним джерелам,
бо в них різні домени. Це правило захищає людину. Сторінка може попросити браузер додати до запиту дані входу людини,
наприклад cookie, тобто маленький запис, за яким сервер пошти впізнає людину, що вже ввійшла. Без правила про
джерела чужа сторінка зробила б запит до пошти з входом людини й прочитала б її листи. Сервер може сам дозволити
таке читання заголовком `Access-Control-Allow-Origin`, а весь механізм називається **CORS** (Cross-Origin Resource
Sharing, спільний доступ до ресурсів з різних джерел).

Якщо дозволу немає, код отримає лише `TypeError` без пояснень. MDN пише, що подробиці навмисно не показують коду
сторінки з міркувань безпеки: інакше чужа сторінка могла б з тексту помилки дізнатися щось про сервер, читати який
їй заборонено. Справжню причину браузер пише в консоль інструментів розробника, яку бачить лише людина за
комп'ютером. У Node цього правила немає, бо там немає ні сторінки з чужого сайту, ні входу людини, які треба
захищати. У браузері ж пам'ятайте, що різні порти теж дають різні джерела. Якщо сторінка прийшла з
`http://localhost:5173`, а дані вона просить у `http://localhost:3000`, то без дозволу від сервера даних запит
відхилиться саме так, хоч обидва сервери працюють на вашому комп'ютері.

## Тіло відповіді — це потік

Чому тіло не можна прочитати двічі? Причина в тому, як воно зберігається, а точніше в тому, що воно не зберігається.

Спершу два поняття, без яких цей розділ не прочитати. Комп'ютер зберігає й пересилає все, зокрема текст, як
послідовність **байтів**, тобто чисел від 0 до 255. Щоб записати текст байтами, потрібне правило, яке каже, які байти
відповідають якій літері. Таке правило називають **кодуванням**, і в мережі майже завжди вживають кодування
**UTF-8**. У ньому латинська літера, цифра чи пробіл займають один байт, а українська літера займає два байти.

Тіло відповіді — це **потік**: байти надходять із мережі частинами, і `fetch` не складає їх про запас. Коли код читає
шматок, `fetch` віддає його й більше не зберігає в себе. Так зроблено навмисно. Якщо `fetch` не тримає копії, то файл
на 2 ГБ можна записувати на диск шматок за шматком, і в пам'яті одночасно лежить лише один шматок, а не всі 2 ГБ.
Плата за таку економію одна: прочитаного повторно не прочитаєш, бо його ніде не збережено.

Потік можна прочитати власноруч через поле `res.body`. Для цього є цикл `for await...of`. Звичайний цикл
`for...of` перебирає елементи, які вже лежать у масиві. Цикл `for await...of` перед кожним кроком чекає, як `await`,
доки надійде наступний шматок, а коли потік закінчився, цикл закінчується теж. Писати його можна там само, де
дозволено `await`, тобто в функції з `async` або на верхньому рівні модуля. Адреса `/chunks` надсилає три шматки
тексту з паузами:

```js
const res = await fetch(base + "/chunks");
const decoder = new TextDecoder();
let count = 0;
for await (const bytes of res.body) {     // кожен bytes — масив байтів Uint8Array
  count += 1;
  console.log("шматок", count + ":", bytes.length, "байтів:", decoder.decode(bytes));
}
console.log("bodyUsed:", res.bodyUsed);
try {
  res.clone();
} catch (e) {
  console.log("clone() після читання →", e.name + ":", e.message);
}
```

```text
шматок 1: 13 байтів: перший 
шматок 2: 13 байтів: другий 
шматок 3: 12 байтів: третій
bodyUsed: true
clone() після читання → TypeError: Response.clone: Body has already been consumed.
```

Розберемо вивід:

- Цикл зробив три кроки, бо сервер надіслав три шматки з паузами. Кожен шматок приходить як `Uint8Array`, тобто масив,
  у якому лежать байти.
- Шматок «перший » займає 13 байтів: шість українських літер по два байти й пробіл в один байт. Шматок «третій» без
  пробілу займає 12 байтів.
- Об'єкт `TextDecoder` перетворює байти на текст за правилами UTF-8, і його метод `decode` повертає рядок.
- Після циклу `bodyUsed` дорівнює `true`, а `res.clone()` падає з `TypeError`. Копію відповіді можна зробити лише до
  першого читання, бо після нього прочитаних байтів уже ніде немає.

У цьому досліді межі шматків збіглися з межами слів, але мережа такого не обіцяє. Межа може пройти посередині літери,
і тоді половина її байтів прийде в одному шматку, а половина в наступному. Подивімося, що тоді зробить декодер. Об'єкт
`TextEncoder` робить зворотну роботу: перетворює текст на байти UTF-8. Метод `slice` вирізає частину масиву байтів.

```js
const bytes = new TextEncoder().encode("Київ");  // текст → байти UTF-8
console.log(bytes.length, "байтів:", bytes.join(" "));

const head = bytes.slice(0, 3);                  // «К» і перший байт «и»
const tail = bytes.slice(3);                     // другий байт «и», потім «ї» і «в»

const plain = new TextDecoder();
console.log("без stream:", plain.decode(head) + plain.decode(tail));

const streaming = new TextDecoder();
console.log("зі stream:", streaming.decode(head, { stream: true }) + streaming.decode(tail));
```

```text
8 байтів: 208 154 208 184 209 151 208 178
без stream: К��їв
зі stream: Київ
```

Слово з чотирьох літер займає вісім байтів, по два на літеру. Ми розрізали масив після третього байта, тобто
посередині літери «и». Перший декодер отримав кожну половину окремо. Половина літери не є жодною літерою, тому декодер
замість кожної з двох половин поставив знак заміни `�`. Другому декодеру параметр `{ stream: true }` каже, що
за цим шматком надійдуть ще. Тому декодер не поспішає: незакінчену літеру він відкладає, а коли надходить наступний
шматок, складає її з другою половиною. Звідси правило: якщо ви декодуєте потік шматками, передавайте
`{ stream: true }` у кожен виклик, крім останнього.

Методи `json()` і `text()` роблять те саме, що цей цикл: читають потік до кінця, а потім перетворюють
результат. Звідси правило: прочитайте тіло один раз, збережіть результат у змінну й далі працюйте зі змінною. Копія
через `clone()` потрібна рідко, зокрема коли одну відповідь треба і показати, і покласти в **кеш**, тобто сховище
збережених відповідей, з якого програма наступного разу бере відповідь, не питаючи сервер.

Ще одна деталь: `json()` не дивиться ні на статус, ні на заголовок `Content-Type`. Він читає всі байти й намагається
розібрати їх як JSON. Адреса `/busy` нашого сервера поводиться як перевантажений сервер із початку лекції: відповідає
статусом 503 і сторінкою HTML.

```js
const res = await fetch(base + "/busy");
console.log("статус", res.status, "| ok =", res.ok, "| тип:", res.headers.get("Content-Type"));
try {
  await res.json();                         // розбираємо, не глянувши на статус
} catch (e) {
  console.log("json() →", e.name + ":", e.message);
}
```

```text
статус 503 | ok = false | тип: text/html
json() → SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON
```

Перший рядок показує, що все потрібне для розуміння вже було в руках до читання тіла: статус 503, `ok` дорівнює
`false`, а заголовок `Content-Type` каже, що прийшла сторінка HTML. Метод `res.headers.get` повертає значення
заголовка за його назвою. Другий рядок надрукував `catch`. Метод `json()` дійшов до першого символу `<`, з якого
починається сторінка HTML, а запис JSON так починатися не може. Саме цей дивний текст і бачила людина в ситуації на
початку лекції. Якщо перевірити `res.ok` до розбору, то статус 503 стане зрозумілою подією, про яку можна сказати
людині, а не збоєм розбору.

## `AbortController` і `AbortSignal`: як зупинити роботу

Іноді результат роботи більше не потрібен: людина пішла зі сторінки або вибрала інше місто. JavaScript не може
примусово зупинити чужу асинхронну функцію. Він може лише попросити, а функція мусить сама вміти слухати таке
прохання. Для цього стандарт DOM описує пару об'єктів.

- **`AbortController`** — це об'єкт, що лишається в того, хто вирішує скасувати. Він має метод `abort()`.
- **`AbortSignal`** — це об'єкт, який лежить у полі `controller.signal` і який віддають виконавцю. Сигнал дозволяє
  лише дізнатися, чи було скасування: поле `aborted`, поле `reason` з причиною і подія `abort`.

Поділ на два об'єкти зроблено навмисно. Виконавець отримує сигнал і може почути прохання, але не може скасувати роботу
сам і не може скасувати її для інших виконавців, які отримали той самий сигнал.

Механізм не прив'язаний до мережі. Покажемо це на функції очікування, яка взагалі не робить запитів. Стандарт DOM дає
пораду кожному, хто пише функцію зі скасуванням, і ця функція виконує її: якщо сигнал уже скасовано на старті,
одразу відхилити проміс; інакше слухати скасування під час роботи; в обох випадках відхиляти проміс причиною з
`signal.reason`.

У коді є три записи, яких ви ще не бачили:

- `signal.addEventListener("abort", f)` просить сигнал викликати функцію `f`, коли станеться **подія** `abort`, тобто
  коли хтось викличе `abort()` на контролері. Події докладно розбирає день 7, а сьогодні досить знати, що
  `addEventListener` записує функцію, яку треба викликати пізніше.
- Параметр `{ once: true }` каже: викликати цю функцію щонайбільше один раз, а потім забути про неї.
- `setTimeout(resolve, ms, "дочекалися")` передає третій аргумент у функцію `resolve`, коли таймер спрацює. Отже,
  проміс виконається рядком `"дочекалися"`.

Ще одна дрібниця: у першому рядку стоїть `return reject(...)`. Слово `return` тут потрібне, щоб функція одразу
вийшла й не запускала таймера для роботи, яку вже скасовано.

```js
function wait(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal.aborted) return reject(signal.reason);        // скасовано ще до початку
    const timer = setTimeout(resolve, ms, "дочекалися");
    signal.addEventListener("abort", () => {                 // скасовано під час очікування
      clearTimeout(timer);
      reject(signal.reason);
    }, { once: true });
  });
}

const first = new AbortController();
const promise = wait(1000, first.signal);
first.abort(new Error("Користувач закрив вікно"));
first.abort(new Error("Друга причина"));                     // другий виклик нічого не змінить
await promise.catch((e) => console.log("очікування →", e.name + ":", e.message));
console.log("причина в сигналі:", first.signal.reason.message);

const second = new AbortController();
second.abort();                                              // без причини
console.log("типова причина:", second.signal.reason.name);
await wait(1000, second.signal).catch((e) => console.log("новий виклик →", e.name));

```

```text
очікування → Error: Користувач закрив вікно
причина в сигналі: Користувач закрив вікно
типова причина: AbortError
новий виклик → AbortError
```

З цього виводу видно чотири правила:

1. Причину можна передати в `abort(причина)`, і проміс відхилиться саме нею. Тому в такому разі `e.name` уже не
   дорівнює `AbortError`. Код, який упізнає скасування лише за цим іменем, власної причини не впізнає.
2. Другий виклик `abort()` нічого не робить. Стандарт прямо починає алгоритм скасування з перевірки, чи сигнал уже
   скасовано.
3. Без причини браузер або Node сам створює причину. Це помилка типу `DOMException`, тобто вбудованого типу помилок
   браузерних API, і її поле `name` дорівнює `AbortError`.
4. Скасований сигнал лишається скасованим назавжди. Новий виклик `wait` зі старим сигналом відхилився одразу, бо
   спрацювала перевірка `signal.aborted` на початку функції. Тому кожній новій роботі потрібен новий контролер.

Функція `fetch` поводиться так само, як `wait`, але робить ще одну річ: на скасування вона обриває й потік тіла. Це
важливо, бо скасування діє й після того, як проміс від `fetch` уже виконався. Якщо заголовки вже прийшли, а тіло ще
ні, то читання тіла відхилиться:

```js
const controller = new AbortController();
const res = await fetch(base + "/slow-body", { signal: controller.signal });
console.log("fetch уже виконався, статус", res.status);

controller.abort();                        // скасовуємо між заголовками й тілом
try {
  await res.json();
} catch (e) {
  console.log("читання тіла →", e.name + ":", e.message);
}
```

```text
fetch уже виконався, статус 200
читання тіла → AbortError: This operation was aborted
```

### Чого скасування не робить

`abort()` зупиняє очікування у вашій програмі, і браузер чи Node обриває передачу даних. Але виклик `abort()` не
відкочує того, що сервер уже зробив. Ми написали вигаданий сервер оплати, який працює 100 мс, а наприкінці збільшує
лічильник платежів. Клієнт надсилає `POST` і викликає `abort()` через 20 мс. Цей приклад має власний сервер, тому його
код показано цілком.

```js
import { createServer } from "node:http";

const pause = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

let payments = 0;                                // лічильник платежів на сервері
const server = createServer(async (req, res) => {
  await pause(100);                              // сервер працює 100 мс
  payments += 1;                                 // і лише тепер проводить платіж
  console.log("сервер: платіж проведено, усього", payments);
  res.end("готово");
});
await new Promise((resolve) => server.listen(0, "127.0.0.1", resolve));
const base = "http://127.0.0.1:" + server.address().port;

const controller = new AbortController();
setTimeout(() => controller.abort(), 20);        // клієнт передумує через 20 мс
try {
  await fetch(base + "/pay", { method: "POST", signal: controller.signal });
} catch (e) {
  console.log("клієнт:", e.name);
}

await pause(200);                                // даємо серверу час закінчити роботу
console.log("наприкінці на сервері платежів:", payments);
server.close();
```

```text
клієнт: AbortError
сервер: платіж проведено, усього 1
наприкінці на сервері платежів: 1
```

Перший рядок надрукував клієнт одразу після скасування, близько двадцятої мілісекунди. Другий рядок надрукував
сервер пізніше. Запит до сервера
дійшов ще до скасування, і сервер почав роботу. Коли клієнт скасував запит, Node на боці клієнта закрив з'єднання,
але код сервера не стежить за з'єднанням, тому довів роботу до кінця. Навіть стеження не врятувало б у всіх
випадках. Якби клієнт скасував запит пізніше, наприклад на 150-й мілісекунді, сервер на цю мить уже провів би платіж.
Третій рядок показує лічильник на сервері після того, як обидва закінчили.

Клієнт вважає, що запит скасовано, а гроші списано. Для пошуку це не має значення, бо читання нічого не змінює. Для
запитів, що змінюють дані, скасування не є способом «передумати»: відмінити операцію може лише окремий запит до
сервера.

### Готові сигнали: таймер і поєднання

Для двох частих випадків контролер писати не треба, бо готовий сигнал дає сам `AbortSignal`:

- `AbortSignal.timeout(100)` повертає сигнал, який скасується сам через 100 мс. Його причина — помилка
  `DOMException` з ім'ям `TimeoutError`.
- `AbortSignal.any([a, b])` повертає сигнал, який скасується тоді, коли скасується перший зі списку, і з його
  причиною.

Запустимо обидва на адресі `/weather?city=lviv`, яка відповідає через 400 мс:

```js
async function load(signal) {
  try {
    const res = await fetch(base + "/weather?city=lviv", { signal });  // сервер відповідає через 400 мс
    console.log("прийшло:", (await res.json()).city);
  } catch (e) {
    console.log("помилка:", e.name);
  }
}

await load(AbortSignal.timeout(100));            // чекаємо не довше 100 мс

const controller = new AbortController();
setTimeout(() => controller.abort(), 50);        // людина натискає «Скасувати» через 50 мс
await load(AbortSignal.any([controller.signal, AbortSignal.timeout(1000)]));

await load(AbortSignal.timeout(1000));           // часу досить
```

```text
помилка: TimeoutError
помилка: AbortError
прийшло: lviv
```

Перший виклик чекав не довше 100 мс, а сервер відповідає через 400 мс, тому спрацював таймер і прийшла помилка
`TimeoutError`. У другому виклику сигнал поєднує кнопку людини й таймер на секунду. Людина натиснула кнопку на 50-й
мілісекунді, раніше за таймер, тому прийшла причина від контролера, тобто `AbortError`. У третьому виклику секунди
вистачило, і відповідь дійшла. Отже, за `e.name` код розрізняє дві історії для людини: `TimeoutError` означає
«сервер довго не відповідає», а `AbortError` означає «ви самі скасували».

## Гонка відповідей із числами

Повернімося до Львова й Одеси. Що таке **гонка** і як її прибирає номер запиту, ви вже бачили в лекції дня 5, розділ
«Гонка відповідей». Там відповіді імітував `setTimeout`, а тепер ту саму гонку дасть справжній `fetch`. Два запити не
зобов'язані повернутися в тому порядку, в якому пішли: у них можуть бути різні шляхи, різне навантаження й різний
обсяг роботи на сервері.

Наш сервер відповідає про Львів через 400 мс, а про Одесу через 100 мс. Людина вибирає Львів у момент 0, а Одесу в
момент 50 мс.

| Час | Хто діє | Що відбувається | На екрані |
|-----|---------|-----------------|-----------|
| 0 мс | Код | Запит про Львів пішов | порожньо |
| 50 мс | Код | Запит про Одесу пішов | порожньо |
| 150 мс | Мережа | Прийшла Одеса (50 + 100) | Одеса |
| 400 мс | Мережа | Прийшов Львів (0 + 400) | Львів |

Остання відповідь перемагає, хоч її запит був старшим. У коді нижче змінна `screen` стоїть замість екрана, а функція
`userPicksTwoCities` повторює дії людини, яка вибирає два міста з перервою в 50 мс. Параметр `show` цієї функції —
інша функція, яка робить запит і показує відповідь. Далі ми запустимо ті самі дії людини ще раз з іншою функцією
`show`.

```js
const pause = (ms) => new Promise((resolve) => setTimeout(resolve, ms));
let screen = "порожньо";                     // те, що зараз бачить людина

async function showAny(city) {
  const res = await fetch(base + "/weather?city=" + city);
  const data = await res.json();
  screen = data.city;                        // без захисту: малюємо все, що прийшло
  console.log("  прийшла відповідь:", data.city, "→ на екрані", screen);
}

async function userPicksTwoCities(show) {
  const lviv = show("lviv");                 // момент 0: людина вибрала Львів
  await pause(50);
  const odesa = show("odesa");               // момент 50 мс: людина вибрала Одесу
  await Promise.all([lviv, odesa]);          // чекаємо обидві відповіді
  console.log("  користувач вибрав odesa, на екрані", screen);
}

console.log("без перевірки:");
await userPicksTwoCities(showAny);
```

```text
без перевірки:
  прийшла відповідь: odesa → на екрані odesa
  прийшла відповідь: lviv → на екрані lviv
  користувач вибрав odesa, на екрані lviv
```

Перший рядок відповіді належить Одесі, бо її сервер відповідає швидше. Другий рядок належить Львову, і саме він
перезаписав `screen`. Останній рядок показує наслідок: людина вибрала Одесу, а бачить Львів. Отже, код, який малює
все, що прийшло, покаже старе місто щоразу, коли відповідь на старий запит прийде останньою.

Є два способи це прибрати, і вони вирішують різне.

**Спосіб перший: скасувати старий запит.** Перед новим запитом код викликає `abort()` на контролері попереднього й
створює новий контролер. Проміс старого запиту відхиляється з `AbortError`, тому код, який мав би намалювати його
відповідь, не виконується зовсім, а помилку `AbortError` код ловить і нічого не показує. Саме цей спосіб просить план
дня. Його ви напишете самі в завданні, тому повного коду тут немає, а як скасування виглядає в React, показано в
розділі «Як це проявиться в React» нижче.

**Спосіб другий: викинути застарілу відповідь.** Запити йдуть до кінця, але код порівнює, чи відповідь ще актуальна.
Це номер запиту з лекції дня 5, тепер зі справжнім `fetch`. Допишіть цей код у той самий файл, після попереднього
досліду:

```js
let lastId = 0;
async function showLatest(city) {
  lastId += 1;
  const id = lastId;               // цей запит запам'ятав свій номер
  const res = await fetch(base + "/weather?city=" + city);
  const data = await res.json();
  if (id !== lastId) {
    console.log("  прийшла відповідь:", data.city, "→ застаріла, викинуто");
    return;
  }
  screen = data.city;
  console.log("  прийшла відповідь:", data.city, "→ на екрані", screen);
}

console.log("з номером запиту:");
await userPicksTwoCities(showLatest);
```

```text
з номером запиту:
  прийшла відповідь: odesa → на екрані odesa
  прийшла відповідь: lviv → застаріла, викинуто
  користувач вибрав odesa, на екрані odesa
```

Запит про Одесу пішов другим і отримав номер 2, тому його відповідь пройшла перевірку. Запит про Львів має номер 1, а
`lastId` на час його відповіді вже дорівнює 2, тому відповідь викинуто. Чому кожен виклик пам'ятає свій номер,
пояснено в лекції дня 5, розділ «Гонка відповідей».

Скасування економить трафік, бо Node чи браузер обриває передачу тіла, яке ще не дійшло. Зате воно потребує окремої
обробки `AbortError` і працює лише з функціями, що приймають сигнал. Перевірка актуальності не потребує обробки
помилок і працює з будь-яким промісом, зате стара відповідь завантажується до кінця. Ці способи не заважають один
одному, тому їх можна поєднувати.

## Що ви побачите у вкладці «Мережа»

Вкладка Network в інструментах розробника Chrome показує кожен запит окремим рядком. Цей опис спирається на
документацію Chrome, а не на запуск у браузері.

| Де дивитися | Що там |
|-------------|--------|
| Стовпець Status | статус відповіді, а також `(failed)` і `CORS error`, якщо запит не вдався |
| Рядок запиту, вкладка Response | тіло, яке прислав сервер, тож видно сторінку HTML замість JSON |
| Список Throttling | штучне сповільнення мережі, щоб побачити гонку на своєму комп'ютері |

На швидкому каналі гонку майже не видно. Сповільнення розтягує час так, що різниця між запитами стає помітною.

Запит, скасований через `abort()`, теж лишається рядком у списку, і в стовпці Status він позначений як скасований:
у Chrome там стоїть напис `(canceled)`. Цей напис ми не перевіряли ні запуском, ні документацією. Саме за такими
рядками в завданні дня ви побачите, що кожна нова літера справді скасовує попередній запит.

## Типові хибні уявлення

**«Якщо `await fetch` не кинув помилку, запит успішний».** Це означає лише, що прийшли статус і заголовки. Статус може
бути 500, а тіло може обірватися пізніше.

**«`res.ok` означає, що в тілі є дані».** Поле `ok` каже лише, що статус від 200 до 299. За статусу 204 тіла немає, а
сервер може прислати 200 і зламаний JSON.

**«`abort()` скасовує операцію на сервері».** Він зупиняє очікування на вашому боці. Те, що сервер уже зробив,
лишається зробленим.

**«Один контролер можна використовувати для всіх запитів».** Після першого `abort()` його сигнал скасований назавжди,
і кожен наступний `fetch` із ним одразу відхиляється. Один спільний контролер має сенс, лише коли треба разом
скасувати всі запити групи.

## Як це проявиться в React

У React запити зазвичай роблять в **ефекті**, тобто у функції, яку компонент передає в `useEffect`. Що таке ефект і
**функція очищення**, яку ефект повертає, пояснено в лекції дня 5, розділ «Як це проявиться в React». Нагадаємо
головне: функцію очищення React викликає перед наступним запуском ефекту з новими даними й тоді, коли компонент
зникає з екрана. Тому функція очищення — зручне місце, щоб скасувати запит, відповідь на який уже не потрібна.

Ось компонент, який показує прогноз, разом із тестом, що його запускає. Компонент обгорнуто в `StrictMode`. Це
вбудований компонент React, який у режимі розробки вмикає додаткові перевірки, щоб помилки знаходилися раніше. Ми
запустили цей код у React 19 в імітації браузера jsdom. Тест запускає програма Vitest командою `npx vitest run`. Для
цього в проєкті мають стояти пакети `react`, `@testing-library/react`, `vitest` і `jsdom`, а файл тесту має лежати
поруч із `weather-server.mjs`. Ці пакети ви поставите в день 11, тому сьогодні досить прочитати код і вивід.

```jsx
// @vitest-environment jsdom
import { StrictMode, useEffect, useState } from "react";
import { render, screen } from "@testing-library/react";
import { test } from "vitest";
import { start } from "./weather-server.mjs";

const { server, base } = await start();
server.on("request", (req) => console.log("сервер отримав", req.url));

function Forecast({ city }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    fetch(base + "/weather?city=" + city, { signal: controller.signal })
      .then((res) => res.json())
      .then(setData)
      .catch((e) => { if (e.name !== "AbortError") throw e; console.log("запит скасовано:", city); });
    return () => controller.abort();
  }, [city]);

  return <p>{data ? "на екрані: " + data.city : "завантаження"}</p>;
}

test("прогноз у StrictMode", async () => {
  render(<StrictMode><Forecast city="lviv" /></StrictMode>);
  const shown = await screen.findByText(/на екрані/);    // чекаємо, доки з'явиться відповідь
  console.log(shown.textContent);
  server.close();
});
```

```text
запит скасовано: lviv
сервер отримав /weather?city=lviv
на екрані: lviv
```

Розберемо ключові рядки компонента:

- Ефект створює власний контролер на кожен запуск і передає його сигнал у `fetch`.
- Функція очищення `() => controller.abort()` скасовує запит саме цього запуску ефекту.
- `.then(setData)` передає розібрані дані прямо у функцію `setData`, яка записує їх у стан компонента.
- Блок `.catch` перевіряє ім'я помилки. Скасування — очікувана подія, тому для `AbortError` він лише друкує рядок.
  Будь-яку іншу помилку він кидає далі словом `throw`, щоб справжній збій не зник непомітно.

Перший рядок виводу надрукував блок `catch`, другий надрукував сервер, а третій надрукував тест, коли прогноз
з'явився на екрані.

Рядок `запит скасовано` з'явився, хоч місто ніхто не змінював. У режимі розробки `StrictMode` спеціально запускає
ефект двічі, а між запусками викликає функцію очищення. Так він шукає ефекти, чия функція очищення не зупиняє того,
що ефект запустив. Перший запуск ефекту почав запит, функція очищення одразу його скасувала, і він так і не дійшов до
сервера. Другий запуск почав новий запит, і сервер отримав лише його. Тому у вкладці «Мережа» в режимі розробки
можна побачити скасований запит, і це не помилка.

Що ще ви зустрінете:

- Сторінка `useEffect` у документації React показує для тієї самої гонки другий спосіб: прапорець `ignore`, який
  функція очищення ставить у `true`. Його розібрано в лекції дня 5, розділ «Як це проявиться в React», і це той самий
  підхід, що й перевірка номера запиту.
- Документація React радить для завантаження даних готові бібліотеки, наприклад TanStack Query, бо в них уже
  розв'язано гонки, кеш і повторні спроби запиту після збою. Але щоб зрозуміти, що бібліотека робить за вас і чому
  вона повідомила про помилку, потрібні саме знання цієї лекції: статус проти відхилення, одноразове тіло й
  скасування.

## Перевірте себе

Спершу дайте відповідь самі, вголос або письмово, і лише потім розгортайте наші пояснення.

**1. Сервер відповів статусом 503. Що зробить `await fetch(url)` і чому?**

<details><summary>Відповідь</summary>

Поверне об'єкт `Response` зі `status` 503 і `ok` рівним `false`. Розмова відбулася: клієнт отримав статус і заголовки.
Проміс відхиляється лише тоді, коли відповіді немає зовсім, наприклад немає зв'язку.

</details>

**2. Сервер відповідає 204 на видалення. Код робить `if (res.ok) return await res.json()`. Що станеться?**

<details><summary>Відповідь</summary>

`res.ok` дорівнює `true`, бо 204 входить у діапазон від 200 до 299, але тіла немає. `res.json()` відхилиться із
`SyntaxError: Unexpected end of JSON input`. Для такої відповіді тіло читати не треба.

</details>

**3. Чому `res.text()` після `res.json()` падає, хоч дані вже є в змінній?**

<details><summary>Відповідь</summary>

Тіло є потоком: байти надходять і забираються тим, хто читає, а `fetch` не тримає їх про запас. Дані є лише в змінній,
куди їх поклав перший читач, а метод читає з відповіді. Щоб читати двічі, копію роблять до першого читання через
`res.clone()`.

</details>

**4. Людина натиснула «Скасувати» на запиті `POST`, який створює замовлення. Код отримав `AbortError`. Чи створено
замовлення?**

<details><summary>Відповідь</summary>

Невідомо. `abort()` зупинив очікування на боці клієнта, але сервер міг уже встигнути отримати запит і виконати його.
Щоб дізнатися правду, треба окремо спитати сервер. Тому скасування безпечне для запитів на читання й не гарантує
нічого для запитів, що змінюють дані.

</details>

**5. Запити пішли в порядку А, Б, В, а відповіді прийшли Б, В, А. Що буде на екрані без захисту, зі скасуванням і з
перевіркою номера запиту?**

<details><summary>Відповідь</summary>

Вважаймо, що всі три запити пішли раніше, ніж прийшла перша відповідь. Без захисту лишиться А, бо ця відповідь прийшла
останньою. Зі скасуванням запит В скасує запит Б, а той раніше скасував запит А, тому дійде лише відповідь В. З
перевіркою номера відповіді А і Б дійдуть до коду, але будуть викинуті, тож результат теж В.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| HTTP | правила обміну даними між клієнтом і сервером: один запит, одна відповідь |
| статус | тризначне число у відповіді, яке коротко каже, чим скінчилася справа |
| тіло | дані запиту чи відповіді; у `fetch` воно є потоком байтів |
| `res.ok` | `true`, коли статус від 200 до 299 |
| мережева помилка | особлива відповідь зі статусом 0, якою стандарт Fetch позначає «відповіді немає»; через неї `fetch` відхиляється з `TypeError` |
| байт | число від 0 до 255; текст і будь-які дані пересилаються послідовністю байтів |
| UTF-8 | кодування, тобто правило запису тексту байтами; українська літера в ньому займає два байти |
| потік | дані, що надходять частинами й забираються тим, хто читає |
| `for await...of` | цикл, який перед кожним кроком чекає наступного шматка потоку |
| джерело (origin) | поєднання протоколу, домену й порту |
| CORS | механізм, яким сервер дозволяє сторінці з іншого джерела читати відповідь |
| `AbortController` | об'єкт із методом `abort()`, який лишається в того, хто скасовує |
| `AbortSignal` | об'єкт, який отримує виконавець, щоб дізнатися про скасування |
| `AbortError` | ім'я помилки при скасуванні без власної причини |
| `TimeoutError` | ім'я помилки, коли спрацював сигнал від `AbortSignal.timeout` |
| гонка | результат залежить від того, що закінчиться першим |
