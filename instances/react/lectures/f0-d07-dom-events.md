# Лекція. День 7. DOM і події

Ця лекція пояснює, у якому вигляді сторінка існує всередині браузера і як браузер повідомляє код про дії людини.
Читання займе близько 35 хвилин. Приклади призначені для консолі браузера. Їхній вивід ми отримали в jsdom, тобто в
імітації браузера для Node, і звірили з браузером Chrome. У вашій консолі він може виглядати трохи інакше, а теги й
значення будуть ті самі. Деякі приклади пишуть `await` просто в коді, поза функцією `async`. Консоль Chrome це
дозволяє, тому такі приклади можна вставляти в неї як є.

**Після лекції ви зможете пояснити:**

- що таке дерево DOM і чому у `<ul>` із двома пунктами п'ять дітей;
- чим атрибут відрізняється від властивості;
- яким шляхом проходить подія й у якому порядку працюють обробники;
- чому `currentTarget` після `await` дорівнює `null`;
- чим скасування дії браузера відрізняється від зупинки події;
- чому делегування зручне і де воно не працює;
- де справжні обробники в застосунку на React.

## Ситуація: сердечко, яке відкриває картку

Уявіть каталог товарів. На кожній картці висить функція, яку браузер викликає при клацанні, і ця функція відкриває
сторінку товару: клацнули по картці, і сторінка відкрилася. У картці є кнопка із сердечком, яка додає товар в обране.
Людина клацає по сердечку, товар додається, а сторінка товару відкривається теж. Хтось виправляє це викликом
`preventDefault()`, і нічого не змінюється. Хтось інший додає в функцію картки перевірку
`event.target.tagName === "BUTTON"`, тобто питає «чи клацнули саме по кнопці?». Ця перевірка то спрацьовує, то ні:
якщо клацнути по самому малюнку сердечка, то `target` виявляється не кнопкою. Що таке `preventDefault()` і `target`,
пояснено нижче.

Щоб такі випадки перестали бути загадкою, треба знати дві речі: як влаштована сторінка в браузері й яким шляхом
проходить подія.

## Сторінка як дерево об'єктів

Коли браузер отримує HTML, він читає цей текст і будує в пам'яті об'єкти. Кожен об'єкт пов'язаний із батьком і дітьми,
тому разом вони утворюють дерево. Це дерево і є **DOM** (Document Object Model, об'єктна модель документа). JavaScript
працює лише з цими об'єктами, а не з текстом HTML. Після побудови дерева вихідний текст браузеру вже не потрібен.

Кожен об'єкт дерева називають **вузлом**. Найважливіші види вузлів:

- **елемент** відповідає тегу, наприклад `<li>`;
- **текстовий вузол** містить текст між тегами;
- **документ** є коренем дерева, він доступний як `document`.

Текстові вузли дають перший сюрприз. Пробіли й переноси рядків між тегами теж є текстом. Перевіримо це кодом, у якому
трапляються кілька нових записів:

- `document.createElement("ul")` створює новий елемент `<ul>`. Цей елемент поки лежить лише в пам'яті й на сторінці
  не з'являється.
- Запис рядка в поле `innerHTML` просить браузер прочитати цей рядок як HTML і зробити з нього дітей елемента.
- `childNodes` — це список усіх дітей вузла, `children` — це список лише дітей-елементів.
- `firstChild` повертає першу дитину будь-якого виду, а `firstElementChild` повертає першу дитину-елемент.
- `nodeName` — це назва вузла. Для елемента це назва тегу великими літерами, наприклад `LI`, а для текстового вузла
  це рядок `#text`.

```js
const list = document.createElement("ul");
list.innerHTML = `
  <li>Чай</li>
  <li>Кава</li>
`;
console.log("childNodes:", list.childNodes.length, "| children:", list.children.length);
console.log("перший вузол:", list.firstChild.nodeName, "| перший елемент:", list.firstElementChild.nodeName);

const box = document.createElement("div");
box.innerHTML = "<table><tr><td>1</td></tr></table>";
console.log(box.innerHTML);
```

```text
childNodes: 5 | children: 2
перший вузол: #text | перший елемент: LI
<table><tbody><tr><td>1</td></tr></tbody></table>
```

Розберемо вивід:

- `childNodes` містить усіх дітей: перенос рядка, `<li>`, перенос рядка, `<li>`, перенос рядка. Це п'ять вузлів.
  `children` містить лише елементи, тому їх два. У прикладному коді майже завжди потрібне `children`.
- `firstChild` повертає текстовий вузол із переносом рядка, а не перший пункт. Це стара пастка: код чекає елемент,
  звертається до поля, яке є лише в елемента, і падає. Ось як це виглядає, якщо додати клас першому пункту:

```js
const list = document.createElement("ul");
list.innerHTML = `
  <li>Чай</li>
  <li>Кава</li>
`;
list.firstElementChild.classList.add("first");   // перший елемент: усе гаразд
console.log("клас першого пункту:", list.firstElementChild.className);
list.firstChild.classList.add("first");          // перший вузол — це текст
```

```text
клас першого пункту: first
Uncaught TypeError: Cannot read properties of undefined (reading 'add')
```

Поле `classList`, тобто список класів елемента, є лише в елементів. У текстового вузла його немає, тому
`list.firstChild.classList` дає `undefined`, а виклик `.add` на `undefined` кидає помилку.

Повернімося до першого прикладу. Останній рядок його виводу показує, що браузер виправляє HTML під час читання. Ми
не писали `<tbody>`, а в дереві він є. Правила читання HTML кажуть, що рядки таблиці `<tr>` лежать усередині розділу
`<tbody>`, тому браузер сам додав пропущений тег. Отже, дерево DOM не завжди збігається з написаним текстом. В
інструментах розробника, на вкладці Elements (у Chrome вона відкривається клавішею F12), ви бачите саме дерево, а не
текст, який надіслав сервер.

### Що відбувається із заміною `innerHTML`

Запис у `innerHTML` просить браузер прочитати рядок як HTML і створити нові вузли замість старих. Тому запис
`panel.innerHTML += "..."` не дописує текст, хоч так і виглядає. Він читає старий HTML у рядок, додає до нього новий
шматок і створює все заново.

Перевіримо це кодом. У ньому знову трапляються нові записи:

- `document.body` — це елемент `<body>` сторінки.
- `document.querySelector("#panel")` знаходить на сторінці перший елемент, що підходить під селектор CSS. Селектор
  `#panel` означає «елемент з `id="panel"`».
- `addEventListener("click", функція)` просить браузер викликати функцію, коли по кнопці клацнуть. Докладно цей метод
  розібрано нижче, у розділі «Що таке подія і як її слухати».
- `click()` імітує клацання мишею по елементу, тому браузер викликає ті самі функції, що й при справжньому клацанні.
- `value` — це текст, який зараз стоїть у полі вводу.
- `JSON.stringify` тут потрібен лише для того, щоб порожній рядок у виводі було видно як `""`.

```js
document.body.innerHTML = `<div id="panel"><input id="name"><button id="save">Зберегти</button></div>`;
const panel = document.querySelector("#panel");
const oldButton = document.querySelector("#save");
oldButton.addEventListener("click", () => console.log("збережено"));
document.querySelector("#name").value = "Оксана";    // людина вже надрукувала ім'я

panel.innerHTML += "<p>Підказка</p>";                // дописуємо один абзац

const newButton = document.querySelector("#save");
console.log("та сама кнопка?", newButton === oldButton);
newButton.click();
console.log("що в полі:", JSON.stringify(document.querySelector("#name").value));
```

```text
та сама кнопка? false
що в полі: ""
```

Рядка `збережено` немає: обробник залишився на старому об'єкті, якого вже немає на сторінці. Надрукований текст теж
зник, бо браузер створив нове поле з розмітки, а в розмітці тексту `Оксана` не було.

Щоб дописати без цієї шкоди, існують методи `append` і `insertAdjacentHTML`. Вони додають нові вузли поруч зі старими
й не чіпають наявних. Метод `append(вузол)` додає готовий вузол у кінець елемента. Метод
`insertAdjacentHTML(місце, рядок)` читає рядок як HTML і вставляє отримані вузли в указане місце, а місце
`"beforeend"` означає «усередині елемента, після всіх його дітей». Замінимо в тому самому коді рядок із `+=`:

```js
document.body.innerHTML = `<div id="panel"><input id="name"><button id="save">Зберегти</button></div>`;
const panel = document.querySelector("#panel");
const oldButton = document.querySelector("#save");
oldButton.addEventListener("click", () => console.log("збережено"));
document.querySelector("#name").value = "Оксана";

panel.insertAdjacentHTML("beforeend", "<p>Підказка</p>");   // дописуємо в кінець панелі

const newButton = document.querySelector("#save");
console.log("та сама кнопка?", newButton === oldButton);
newButton.click();
console.log("що в полі:", JSON.stringify(document.querySelector("#name").value));
console.log("абзаців у панелі:", panel.querySelectorAll("p").length);
```

```text
та сама кнопка? true
збережено
що в полі: "Оксана"
абзаців у панелі: 1
```

Тепер кнопка та сама, її обробник спрацював, текст у полі лишився, а абзац додався.

Є й небезпека іншого роду. Рядок, записаний в `innerHTML`, стає справжньою розміткою, тому рядок від користувача може
містити теги, які виконають чужий код. Браузер не виконує тег `<script>`, вставлений через `innerHTML`, але є інші
шляхи. Довідник MDN наводить такий: картинка з неіснуючою адресою й атрибутом `onerror`. Браузер не може завантажити
картинку й виконує код з атрибута `onerror`. Поле `textContent` поводиться інакше: воно записує рядок як звичайний
текст, і теги в ньому лишаються просто символами `<` і `>`. Порівняємо обидва поля на тому самому рядку:

```js
const nameFromUser = `<img src="nope" onerror="console.log('виконано чужий код')">`;
document.body.innerHTML = `<p id="as-html"></p><p id="as-text"></p>`;

document.querySelector("#as-text").textContent = nameFromUser;   // рядок стає текстом
console.log("textContent: усередині абзацу елементів", document.querySelector("#as-text").children.length);

document.querySelector("#as-html").innerHTML = nameFromUser;     // рядок стає розміткою
console.log("innerHTML: усередині абзацу елементів", document.querySelector("#as-html").children.length);
await new Promise((r) => setTimeout(r, 100));                    // даємо браузеру спробувати завантажити картинку
```

```text
textContent: усередині абзацу елементів 0
innerHTML: усередині абзацу елементів 1
виконано чужий код
```

Через `textContent` рядок став текстом, і елементів в абзаці немає. Через `innerHTML` рядок став елементом `<img>`,
і код з його атрибута виконався. Замість `console.log` там міг стояти код, який краде дані людини. Тому для звичайного
тексту користуйтеся `textContent`. Цей вивід отримано в Chrome без вікна. Останнього рядка в jsdom немає, бо jsdom
без окремого налаштування не завантажує картинок.

## Атрибут і властивість

**Атрибут** — це запис у розмітці: `href="/about"` у тегу. **Властивість** — це поле JavaScript-об'єкта вузла:
`link.href`. Атрибути вузол зберігає так, як їх записано в розмітці. Для більшості стандартних атрибутів у вузла є
властивість із тією самою чи схожою назвою, і стандарт HTML описує для кожної такої пари, як властивість пов'язана з
атрибутом. Цей зв'язок називають **відображенням** (англійською reflection). У різних пар він різний, і саме тут
трапляються помилки.

Для роботи з атрибутами є три методи. `getAttribute("href")` повертає текст атрибута так, як його записано в
розмітці. `setAttribute("href", "/new")` записує атрибут. `hasAttribute("checked")` відповідає, чи є такий атрибут у
вузла взагалі.

Подивимося, чим відрізняються ці зв'язки. Приклад запущено на сторінці з адресою `https://shop.example/`. На іншій
сторінці початок повної адреси в першому рядку виводу буде іншим:

```js
document.body.innerHTML = `
  <a id="more" class="link big" href="/about">Докладніше</a>
  <input id="agree" type="checkbox" checked>
  <button id="send" disabled>Надіслати</button>`;
const link = document.querySelector("#more");
const box = document.querySelector("#agree");
const button = document.querySelector("#send");

console.log("атрибут href:", link.getAttribute("href"), "| властивість href:", link.href);
console.log("атрибут class:", link.getAttribute("class"), "| властивість className:", link.className);

box.checked = false;                         // так робить користувач, коли знімає прапорець
console.log("checked:", box.checked, "| атрибут є:", box.hasAttribute("checked"));

button.disabled = false;
console.log("disabled:", button.disabled, "| атрибут є:", button.hasAttribute("disabled"));
```

```text
атрибут href: /about | властивість href: https://shop.example/about
атрибут class: link big | властивість className: link big
checked: false | атрибут є: true
disabled: false | атрибут є: false
```

Розберемо вивід рядок за рядком.

Перший рядок показує пару `href`. Атрибут містить те, що написано в розмітці, тобто `/about`. Властивість `link.href`
читає цей атрибут і доповнює його адресою сторінки, тому повертає повну адресу `https://shop.example/about`. Отже,
атрибут містить написане, а властивість містить обчислене.

Другий рядок показує пару `class` і `className`. Тут обидві сторони дають те саме значення, просто під різними
назвами. Властивість назвали інакше, бо `class` — зарезервоване слово JavaScript, і в давніх версіях мови його не
можна було взяти за ім'я поля.

Третій рядок показує прапорець. Ми зняли його через властивість, і властивість `checked` стала `false`. Атрибут
`checked` при цьому лишився в розмітці. Причина в тому, що атрибут `checked` означає «з якого стану починати», а
властивість `checked` означає «який стан зараз». Зміна поточного стану не переписує початковий.

Четвертий рядок показує кнопку. Властивість `disabled = false` прибрала атрибут `disabled` з розмітки, бо ця пара
пов'язана напряму: властивість додає чи прибирає атрибут. Для такого атрибута має значення лише те, чи він є. Текст у
ньому не важливий, тому навіть `disabled="false"` вимикає кнопку.

Поле вводу поводиться так само, як прапорець: атрибут `value` задає початковий текст, а властивість `value` містить
поточний. Є ще одна тонкість. Поки поле ніхто не змінював, нове значення атрибута одразу з'являється й у полі. Щойно
текст поля змінили, браузер запам'ятовує, що поле вже змінене, і далі не бере значення з атрибута. Стандарт HTML
називає цю позначку dirty value flag, а для прапорця — dirty checkedness flag. Позначку ставить і людина, яка
друкує в полі, і код, який записує властивість. Подивимося на це разом з атрибутами `data-*`. Так називають власні
атрибути, ім'я яких починається з `data-`. Код читає їх через властивість `dataset`, у якій ім'я записано без `data-`,
а дефіс замінено великою літерою: `data-in-stock` читається як `dataset.inStock`.

```js
document.body.innerHTML = `
  <input id="city" value="Київ">
  <li id="item" data-id="7" data-in-stock="yes">Чай</li>`;
const city = document.querySelector("#city");
const item = document.querySelector("#item");

city.setAttribute("value", "Одеса");          // поле ще ніхто не чіпав
console.log("1) властивість:", city.value, "| атрибут:", city.getAttribute("value"));
city.value = "Львів";                         // так поле змінюється, коли людина друкує
console.log("2) властивість:", city.value, "| атрибут:", city.getAttribute("value"));
city.setAttribute("value", "Харків");         // поле вже змінене
console.log("3) властивість:", city.value, "| атрибут:", city.getAttribute("value"));

console.log("dataset.id:", item.dataset.id, "| тип:", typeof item.dataset.id);
console.log("dataset.inStock:", item.dataset.inStock);
```

```text
1) властивість: Одеса | атрибут: Одеса
2) властивість: Львів | атрибут: Одеса
3) властивість: Львів | атрибут: Харків
dataset.id: 7 | тип: string
dataset.inStock: yes
```

Перший рядок показує поле, яке ще ніхто не змінював: новий атрибут одразу змінив і текст поля. Другий рядок показує,
що запис властивості змінив текст поля, а атрибут лишився `Одеса`. Третій рядок показує, що після зміни поля новий
атрибут `Харків` уже не потрапив у поле. Останні два рядки показують `dataset`: у розмітці стояло число `7`, а
повернувся рядок, бо атрибут завжди є текстом. Щоб порахувати з таким значенням, його спершу перетворюють на число,
наприклад `Number(item.dataset.id)`.

Підсумуємо пари в таблиці:

| Пара | Як пов'язані | Що варто пам'ятати |
|------|--------------|-------------------|
| `href` | властивість читає атрибут і дає повну адресу | атрибут містить написане, властивість містить обчислене |
| `class` і `className` | одне значення під різними назвами | слово `class` колись не можна було використати для імені поля |
| `checked` і `value` поля | атрибут задає лише початкове значення | поточний стан лежить у властивості |
| `disabled` | властивість додає чи прибирає атрибут | значення має лише наявність атрибута, текст у ньому не важливий |
| `data-*` і `dataset` | одне значення, завжди рядок | число `7` повернеться як рядок `"7"` |

Головна пара для інтерфейсів — третя. Коли ви хочете знати, що зараз вибрала чи надрукувала людина, читайте
властивість `checked` чи `value`, а не атрибут.

## Що таке подія і як її слухати

Що таке подія й обробник, пояснено в лекції дня 5, розділ «Цикл подій: хто вирішує, що виконувати далі». Тут нам
потрібно інше: що саме браузер передає обробнику. Коли щось стається, браузер створює **об'єкт події** й передає його
вузлу, з яким це сталося. Об'єкт містить назву події (`type`), вузол, де все сталося (`target`), і подробиці,
наприклад координати миші. Браузер викликає кожен обробник і передає йому цей об'єкт першим аргументом. Обробник
також називають **слухачем** (англійською listener).

Обробник додають через `addEventListener(назва, функція, параметри)`. Третій аргумент необов'язковий: це об'єкт із
параметрами, наприклад `{ once: true }`. Цей метод має кілька особливостей, яких не видно з першого погляду:

```js
document.body.innerHTML = `<button id="buy">Купити</button>`;
const buy = document.querySelector("#buy");
const log = () => console.log("  той самий обробник");

buy.addEventListener("click", log);
buy.addEventListener("click", log);                   // та сама функція: другий запис ігнорується
buy.addEventListener("click", () => console.log("  другий обробник, один раз"), { once: true });
const stopper = new AbortController();
buy.addEventListener("click", () => console.log("  третій обробник, до abort"), { signal: stopper.signal });

console.log("перше клацання:");
buy.click();
stopper.abort();
console.log("друге клацання:");
buy.click();
```

```text
перше клацання:
  той самий обробник
  другий обробник, один раз
  третій обробник, до abort
друге клацання:
  той самий обробник
```

Рядок за рядком:

- Та сама функція на тому самому вузлі й для тієї самої події реєструється один раз, тому другий виклик нічого не
  додає. Дві однакові на вигляд стрілкові функції є різними об'єктами, тому вони додадуться обидві.
- На одному вузлі обробники працюють у порядку додавання.
- Параметр `once` прибирає обробник після першого виклику.
- Параметр `signal` приймає той самий сигнал, що й `fetch` у дні 6 (див. лекцію дня 6, розділ «`AbortController` і
  `AbortSignal`: як зупинити роботу»): виклик `abort()` прибирає обробник. Якщо передати один сигнал кільком
  обробникам, один виклик `abort()` прибере їх усі.

Прибрати обробник можна й методом `removeEventListener(назва, функція)`. Браузер шукає в списку обробників вузла ту
саму функцію, тобто той самий об'єкт, а не функцію з таким самим текстом. Тому стрілкову функцію, записану просто в
дужках виклику, прибрати не вийде: посилання на неї ніде не збережено, а новий запис створює новий об'єкт.

```js
document.body.innerHTML = `<button id="buy">Купити</button>`;
const buy = document.querySelector("#buy");
const named = () => console.log("  обробник з ім'ям");

buy.addEventListener("click", named);
buy.addEventListener("click", () => console.log("  стрілкова функція"));

buy.removeEventListener("click", named);                                // той самий об'єкт функції
buy.removeEventListener("click", () => console.log("  стрілкова функція")); // новий об'єкт, такий самий на вигляд
buy.click();
```

```text
  стрілкова функція
```

Обробник `named` зник, бо в `removeEventListener` ми передали той самий об'єкт. Стрілкова функція лишилася, бо другий
виклик `removeEventListener` отримав інший об'єкт, хоч і з таким самим текстом.

## Шлях події

Найважливіше: подія не залишається там, де виникла. Браузер проводить її шляхом через усіх предків. Порядок такий:

1. **Побудова шляху.** Вузол, де виникла подія, називають **ціллю**. Ще до першого обробника браузер запам'ятовує
   список: ціль, батько цілі, його батько й так далі до `document` і вікна. Вікно — це об'єкт `window`, який стоїть
   над документом і представляє вкладку браузера. Стандарт DOM описує цей порядок у своєму алгоритмі, за яким браузер
   розсилає подію (англійською dispatch).
2. **Занурення** (capture). Подія йде від вікна вниз до цілі. За замовчуванням обробники цю фазу пропускають. Щоб
   спрацювати тут, обробник додають із параметром `{ capture: true }`.
3. **Ціль.** Подія дійшла до вузла, де все сталося.
4. **Спливання** (bubbling). Подія йде від цілі назад угору.
5. **Дія браузера.** Якщо подію не скасовано, браузер виконує свою звичайну дію.

Подивимося на весь шлях у каталозі. Символ сердечка `<b>` лежить у кнопці, кнопка в картці, картка в секції. На
кожному вузлі висить по два обробники: для занурення (`↓`) і для спливання (`↑`).

Кожен обробник друкує два поля об'єкта події. Поле `eventPhase` каже, у якій фазі шляху подія зараз. Поле
`currentTarget` вказує на вузол, чий обробник працює в цю мить. Поле `target` упродовж усього шляху вказує на ціль, а
`currentTarget` змінюється від вузла до вузла. Функція `say` отримує ім'я і повертає обробник, який це ім'я
пам'ятає. Так працює замикання з лекції дня 3. Метод `padEnd(8)` доповнює ім'я пробілами до восьми символів, щоб
колонки у виводі стояли рівно. Метод `document.getElementById(id)` знаходить елемент за його `id`, як
`querySelector("#" + id)`.

```js
document.body.innerHTML = `
  <section id="catalog">
    <article id="card">
      <button id="like"><b id="heart">♥</b></button>
    </article>
  </section>`;
const say = (name) => (event) =>
  console.log(name.padEnd(8), "фаза", event.eventPhase, "| currentTarget:", event.currentTarget.id);

for (const id of ["catalog", "card", "like", "heart"]) {
  const node = document.getElementById(id);
  node.addEventListener("click", say(id + " ↓"), { capture: true });
  node.addEventListener("click", say(id + " ↑"));
}
document.getElementById("heart").click();
```

```text
catalog ↓ фаза 1 | currentTarget: catalog
card ↓   фаза 1 | currentTarget: card
like ↓   фаза 1 | currentTarget: like
heart ↓  фаза 2 | currentTarget: heart
heart ↑  фаза 2 | currentTarget: heart
like ↑   фаза 3 | currentTarget: like
card ↑   фаза 3 | currentTarget: card
catalog ↑ фаза 3 | currentTarget: catalog
```

Число в кожному рядку — це поле `event.eventPhase`: 1 означає занурення, 2 означає, що подія дійшла до цілі, а 3
означає спливання. Перші три рядки показують рух згори вниз через секцію, картку й кнопку. Потім спрацювали обидва
обробники на символі `heart`, бо він і є ціллю: на цілі працюють і обробники занурення, і обробники спливання,
причому спершу обробники занурення. Останні три рядки показують той самий шлях у зворотному порядку.

Тепер можна пояснити ситуацію зі сердечком. Людина клацнула по символу `♥`. Ціллю стала не кнопка, а `<b>` усередині
неї, бо подія виникає на найглибшому вузлі під курсором. Далі подія спливла через кнопку до картки. Обробник кнопки
додав товар в обране, а потім обробник картки теж отримав клацання й відкрив сторінку товару. Він не знає, що
клацання вже обробила кнопка: для нього це звичайне клацання всередині картки.

Перевірка `event.target.tagName === "BUTTON"` спрацьовує не завжди, бо `target` залежить від того, куди саме влучив
курсор. Клацання по краю кнопки дає `target`, що дорівнює кнопці, а клацання по символу дає `target`, що дорівнює
`<b>`.

Виклик `preventDefault()` не допоміг, бо він не зупиняє подію. Він лише просить браузер не виконувати власну дію,
наприклад перехід за посиланням (про це розповідає розділ «Дія браузера й `preventDefault`» нижче). Сторінку товару
відкриває не браузер, а обробник картки, і цей обробник однаково отримує подію.

Допомагає метод `closest(селектор)`. Він перевіряє сам вузол, потім його батька, потім батька батька й повертає
перший вузол, що підходить під селектор, або `null`, якщо такого немає. Обробник картки викликає
`event.target.closest("button")`. Якщо результат не `null`, ціль лежить усередині кнопки чи сама є кнопкою, і тоді
обробник картки нічого не робить:

```js
document.body.innerHTML = `
  <article id="card">
    <h3>Чайник</h3>
    <button id="like"><b id="heart">♥</b></button>
  </article>`;
const card = document.querySelector("#card");
card.addEventListener("click", (event) => {
  if (event.target.closest("button")) return;   // клацання прийшло з кнопки: сторінку товару не відкриваємо
  console.log("відкриваємо сторінку товару");
});
document.querySelector("#like").addEventListener("click", () => console.log("додано в обране"));

console.log("клацання по символу:");
document.querySelector("#heart").click();
console.log("клацання по назві:");
document.querySelector("h3").click();
```

```text
клацання по символу:
додано в обране
клацання по назві:
відкриваємо сторінку товару
```

Клацання по символу дійшло до картки, але `closest` знайшов кнопку, і обробник картки нічого не зробив. Клацання по
назві товару не має кнопки серед предків, тому сторінка товару відкрилася.

Можна також викликати `stopPropagation()` в обробнику кнопки. Цей метод зупиняє подію, і вона не піде вище. Але це має
ціну: подія не дійде й до інших обробників вище. Наприклад, код аналітики часто слухає всі клацання на `document`, а
випадне меню часто закривається обробником на `document`, коли людина клацає будь-де поза меню. Після
`stopPropagation()` на кнопці аналітика цього клацання не порахує, а відкрите меню не закриється.

### Крайні випадки шляху

**Шлях не змінюється після старту.** Браузер будує список один раз. Якщо обробник прибере вузол зі сторінки, подія все
одно пройде далі старим списком. У коді нижче `card.remove()` виймає картку з документа разом з усім, що в ній лежить.
Метод `catalog.contains(вузол)` відповідає, чи лежить вузол усередині секції.

```js
document.body.innerHTML = `
  <section id="catalog"><article id="card"><button id="remove">Прибрати</button></article></section>`;
const catalog = document.querySelector("#catalog");
const card = document.querySelector("#card");
const button = document.querySelector("#remove");

button.addEventListener("click", () => {
  card.remove();                                       // картки вже немає в документі
  console.log("кнопка: картку прибрано");
});
catalog.addEventListener("click", (event) => {
  console.log("catalog бачить клацання, target:", event.target.id);
  console.log("catalog.contains(target):", catalog.contains(event.target));
  console.log("target.closest('#card'):", event.target.closest("#card")?.id);
  console.log("target.closest('#catalog'):", event.target.closest("#catalog"));
});
button.click();
```

```text
кнопка: картку прибрано
catalog бачить клацання, target: remove
catalog.contains(target): false
target.closest('#card'): card
target.closest('#catalog'): null
```

Секція почула клацання, бо вона була в списку, складеному до першого обробника. Водночас ціль уже не лежить усередині
секції, тому `contains` відповідає `false`. Метод `closest` іде лише за поточними батьками. Кнопка досі лежить у
картці, бо картку вийняли разом із кнопкою, тому `closest` знаходить картку. Секції серед поточних предків кнопки вже
немає, тому `closest("#catalog")` дає `null`. Отже, якщо нижчий обробник змінює дерево, вищий обробник не може
вважати дерево незмінним.

**`currentTarget` існує лише під час обробки.** Коли подія пройшла свій шлях, браузер записує в це поле `null`.
`await` віддає керування, тому код після нього працює вже пізніше (див. лекцію дня 5, розділ «`async` і `await`: той
самий проміс іншим записом»):

```js
document.body.innerHTML = `<button id="save"><b id="icon">✓</b></button>`;
const button = document.querySelector("#save");
button.addEventListener("click", async (event) => {
  console.log("до await: target =", event.target.id, "| currentTarget =", event.currentTarget.id);
  await new Promise((r) => setTimeout(r, 10));  // очікування, наприклад запит у мережу
  console.log("після await: target =", event.target.id, "| currentTarget =", event.currentTarget?.id ?? null);
});
document.querySelector("#icon").click();
```

```text
до await: target = icon | currentTarget = save
після await: target = icon | currentTarget = null
```

Поле `target` лишається. Поле `currentTarget` дорівнює `null`. Якщо вузол знадобиться після очікування, збережіть його
в змінну до `await`.

Зовсім коротке очікування може дати інший результат. У коді нижче очікування замінено на `await Promise.resolve()`.
Проміс `Promise.resolve()` уже виконаний, тому чекати йому нічого, і продовження функції стає мікрозадачею. Рядка з
`click()` у коді немає: після запуску клацніть по кнопці мишею.

```js
document.body.innerHTML = `<button id="save"><b id="icon">✓</b></button>`;
const button = document.querySelector("#save");
button.addEventListener("click", async (event) => {
  console.log("до await: target =", event.target.id, "| currentTarget =", event.currentTarget.id);
  await Promise.resolve();                      // проміс уже виконаний: чекати нічого
  console.log("після await: target =", event.target.id, "| currentTarget =", event.currentTarget?.id ?? null);
});
```

Клацання мишею по символу `✓` дало такий вивід. Ми отримали його в Chrome без вікна, де клацання мишею надіслали
через інструменти розробника. Цей спосіб дає справжнє клацання, як від людини:

```text
до await: target = icon | currentTarget = save
після await: target = icon | currentTarget = save
```

Другий рядок показує, що поле `currentTarget` ще не очищене. Причина в тому, коли браузер виконує мікрозадачі. Як
пояснює лекція дня 5, розділ «Цикл подій: хто вирішує, що виконувати далі», мікрозадачі виконуються одразу після
поточного коду, щойно жодна функція JavaScript більше не працює. Справжнє клацання приходить окремою задачею, і
обробники викликає сам браузер. Коли наш обробник дійшов до `await` і повернув керування, жодного іншого коду
JavaScript уже не працює. Тому браузер виконує мікрозадачу одразу, ще до того, як подія піде далі шляхом, і
`currentTarget` у цю мить ще вказує на кнопку.

Якщо додати в кінець цього коду рядок `document.querySelector("#icon").click();`, вивід стане таким самим, як у
попередньому прикладі з таймером: після `await` поле дорівнює `null`. Виклик `click()` із коду працює інакше, бо
подію розсилає наш скрипт, і цей скрипт ще не завершився. Мікрозадача чекає, поки закінчиться весь скрипт. На той
час подія вже пройшла шлях, і поле дорівнює `null`. На таку різницю не варто покладатися, тому правило лишається те
саме: зберігайте вузол у змінну до `await`.

**Не всі події спливають.** Прапорець `event.bubbles` каже, чи спливає подія. Візьмемо фокус. Поле має **фокус**,
коли саме воно отримує натискання клавіш: людина клацнула в поле, і курсор блимає в ньому. Коли поле отримує фокус,
браузер надсилає йому дві події: спершу `focus`, а потім `focusin`. Різниця між ними одна: `focus` не спливає, а
`focusin` спливає. Перевіримо це на формі з полем. Метод `field.focus()` передає фокус полю з коду, так само як
клацання мишею. На формі висять три обробники, а четвертий висить на самому полі й друкує прапорець:

```js
document.body.innerHTML = `<form id="order"><input id="field"></form>`;
const form = document.querySelector("#order");
const field = document.querySelector("#field");

form.addEventListener("focus", () => console.log("focus на формі, спливання"));
form.addEventListener("focus", () => console.log("focus на формі, занурення"), { capture: true });
form.addEventListener("focusin", () => console.log("focusin на формі, спливання"));
field.addEventListener("focus", (event) => console.log("event.bubbles у focus:", event.bubbles));

field.focus();
```

```text
focus на формі, занурення
event.bubbles у focus: false
focusin на формі, спливання
```

Якщо ви запускаєте код у консолі й вивід порожній, клацніть мишею по полю на сторінці. Поки ви друкуєте в консолі,
натискання клавіш отримує консоль, а не сторінка, тобто фокус має не сторінка. Тоді браузер може не надіслати події
фокуса. Клацання по полю передає фокус сторінці й полю, і браузер надсилає ті самі події. Цю поведінку консолі ми
запуском не перевіряли, бо в Chrome без вікна консолі немає.

Рядка `focus на формі, спливання` у виводі немає, бо `focus` не спливає, і звичайний обробник на формі не спрацював.
Обробник `focusin` спрацював, бо ця подія спливає. Обробник `focus` із параметром `{ capture: true }` теж спрацював,
бо занурення проходить незалежно від `bubbles`. Отже, щоб на формі дізнатися про фокус у будь-якому її полі, потрібен
`focusin` або обробник із `capture`.

**Є два способи зупинити подію.** `stopPropagation()` зупиняє рух до наступних вузлів, але інші обробники на поточному
вузлі ще спрацюють. `stopImmediatePropagation()` зупиняє ще й їх. У коді нижче перший обробник кнопки викликає один
із цих методів. Змінна `stop` містить назву методу, а запис `event[stop]()` викликає метод із такою назвою:

```js
document.body.innerHTML = `<div id="card"><button id="like">♥</button></div>`;
const card = document.querySelector("#card");
const like = document.querySelector("#like");
card.addEventListener("click", () => console.log("  обробник картки"));

let stop = "stopPropagation";
like.addEventListener("click", (event) => { console.log("  перший обробник кнопки"); event[stop](); });
like.addEventListener("click", () => console.log("  другий обробник кнопки"));

console.log("stopPropagation:");
like.click();
stop = "stopImmediatePropagation";
console.log("stopImmediatePropagation:");
like.click();
```

```text
stopPropagation:
  перший обробник кнопки
  другий обробник кнопки
stopImmediatePropagation:
  перший обробник кнопки
```

Після `stopPropagation()` другий обробник кнопки спрацював, бо він висить на тому самому вузлі, а обробник картки не
спрацював, бо картка стоїть далі на шляху. Після `stopImmediatePropagation()` не спрацював навіть другий обробник
кнопки.

## Дія браузера й `preventDefault`

Для багатьох подій браузер має власну реакцію. Клацання по посиланню веде за адресою, клацання по кнопці в формі
надсилає форму, клацання по прапорцю перемикає його. Метод `preventDefault()` просить цього не робити. Він працює не
завжди, а за двох умов.

Перша умова: подія має бути **скасовною**. Про це каже прапорець `event.cancelable`. Наприклад, подія `click`
скасовна, а `focus` ні: фокус уже перейшов, і скасовувати нічого.

Друга умова: обробник не має бути зареєстрований з параметром `{ passive: true }`. Цей параметр потрібен для
прокручування. Коли людина крутить колесо миші, браузер мав би чекати, поки закінчаться обробники події `wheel`, бо
котрийсь із них може скасувати прокручування. Повільний обробник тоді затримує прокручування, і сторінка смикається.
Параметр `passive: true` — це обіцянка обробника не скасовувати дію. Браузер вірить їй і прокручує сторінку одразу, а
виклик `preventDefault()` у такому обробнику нічого не робить.

Дія браузера виконується після всього шляху події. Звідси наслідок, який дивує: скасувати перехід може не лише
обробник на посиланні, а й будь-який його предок.

Перевіримо це на посиланні з адресою `#orders`. Поле `location.hash` містить частину адреси сторінки після знака `#`.
Перехід за таким посиланням лише змінює цю частину адреси й не перезавантажує сторінку, тому вивід у консолі не
зникне. Після кожного клацання код чекає 20 мілісекунд функцією `tick`, щоб браузер устиг змінити адресу.

```js
document.body.innerHTML = `<nav id="menu"><a id="go" href="#orders">Замовлення</a></nav>`;
const menu = document.querySelector("#menu");
const go = document.querySelector("#go");
const tick = () => new Promise((r) => setTimeout(r, 20));

go.click();
await tick();
console.log("без скасування адреса:", location.hash);
location.hash = "";
await tick();

menu.addEventListener("click", (event) => event.preventDefault());   // скасовує БАТЬКО
go.click();
await tick();
console.log("зі скасуванням на батькові адреса:", JSON.stringify(location.hash));
```

```text
без скасування адреса: #orders
зі скасуванням на батькові адреса: ""
```

Перший рядок показує звичайний перехід: обробників ще немає, тому браузер записав в адресу `#orders`. Другий рядок
показує, що обробник на `<nav>` скасував перехід, хоч сам `<nav>` не є посиланням. Отже, коли посилання перестало
працювати, шукайте `preventDefault()` не лише на самому посиланні, а й на всіх його предках.

**Виняток: прапорець.** У прапорця частина дії відбувається ще до шляху події. Стандарт HTML описує це так: перед
розсиланням клацання браузер уже перемикає `checked`, а якщо подію скасовано, після шляху повертає попередній стан.
Тому обробник клацання бачить новий стан, навіть якщо той потім буде скасовано:

```js
document.body.innerHTML = `<input id="agree" type="checkbox">`;
const agree = document.querySelector("#agree");
let cancel = false;
agree.addEventListener("click", (event) => {
  console.log("  в обробнику checked =", agree.checked);
  if (cancel) event.preventDefault();
});

console.log("без скасування:");
agree.click();
console.log("  після події checked =", agree.checked);
cancel = true;
console.log("зі скасуванням:");
agree.click();
console.log("  після події checked =", agree.checked);
```

```text
без скасування:
  в обробнику checked = true
  після події checked = true
зі скасуванням:
  в обробнику checked = false
  після події checked = true
```

Перше клацання ввімкнуло прапорець, і обробник уже бачив `true`. Друге клацання браузер спершу перемкнув на `false`,
тому обробник побачив `false`. Обробник скасував подію, і після шляху браузер повернув `true`. Отже, в обробнику
клацання прапорця `checked` показує стан, який буде, якщо подію ніхто не скасує.

**Пастка з кнопкою у формі.** Тег `<button>` без атрибута `type` усередині форми надсилає форму. Перед надсиланням
браузер розсилає формі подію `submit`, а поле `event.submitter` цієї події вказує на кнопку, яка надіслала форму.
Перевіримо це на двох кнопках:

```js
document.body.innerHTML = `
  <form id="order">
    <button id="plain">Без type</button>
    <button id="safe" type="button">Не надсилає</button>
  </form>`;
const form = document.querySelector("#order");
form.addEventListener("submit", (event) => {
  event.preventDefault();                      // щоб браузер не пішов на нову адресу й вивід не зник
  console.log("  подія submit, її викликала кнопка:", event.submitter.id);
});

console.log('клацання по кнопці з type="button":');
document.querySelector("#safe").click();
console.log("клацання по кнопці без type:");
document.querySelector("#plain").click();
```

```text
клацання по кнопці з type="button":
клацання по кнопці без type:
  подія submit, її викликала кнопка: plain
```

Клацання по кнопці без `type` викликало подію `submit`, а клацання по кнопці з `type="button"` не викликало нічого.
Без `preventDefault()` на події `submit` браузер надіслав би форму. У нашої форми немає атрибута `action`, тобто
адреси, куди надсилати, тому браузер надіслав би її на адресу поточної сторінки й завантажив би сторінку заново. Тоді
зник би і вивід, і все, що людина встигла ввести. Тому кнопки, що не надсилають форму, завжди отримують
`type="button"`.

## Делегування

**Делегування** означає один обробник на спільному предку замість окремого обробника на кожному дочірньому елементі.
Воно можливе завдяки спливанню. Покажемо його на панелі інструментів текстового редактора. Завдання дня робить таке
для списку, тому там ваш код буде іншим.

```js
document.body.innerHTML = `
  <div id="toolbar">
    <button data-action="bold"><b>Ж</b></button>
    <button data-action="italic"><i>К</i></button>
    <span id="hint">Виберіть дію</span>
  </div>`;
const toolbar = document.querySelector("#toolbar");
toolbar.addEventListener("click", (event) => {
  const button = event.target.closest("[data-action]");
  if (!button || !toolbar.contains(button)) return;     // клацнули повз кнопки
  console.log("дія:", button.dataset.action, "| target:", event.target.tagName);
});
toolbar.querySelector("b").click();
toolbar.querySelector('[data-action="italic"]').click();
toolbar.querySelector("#hint").click();
toolbar.insertAdjacentHTML("beforeend", `<button data-action="link">URL</button>`);
toolbar.querySelector('[data-action="link"]').click();
```

```text
дія: bold | target: B
дія: italic | target: BUTTON
дія: link | target: BUTTON
```

Розберемо тіло обробника:

- `event.target` — найглибший вузол під курсором. Це може бути символ усередині кнопки.
- `closest("[data-action]")` перевіряє сам вузол, потім його предків і повертає перший вузол з атрибутом
  `data-action` або `null`. Селектор у квадратних дужках означає «елемент, у якого є такий атрибут».
- Перевірка `!button` обробляє клацання по підказці: третє клацання нічого не надрукувало.
- Перевірка `toolbar.contains(button)` потрібна, коли вся панель лежить усередині іншого елемента з атрибутом
  `data-action`. Метод `closest` іде вгору без меж, тому для клацання по підказці він пройшов би повз панель і
  знайшов би цей зовнішній елемент. Без перевірки обробник панелі виконав би чужу дію.
- Кнопка `link` додана вже після реєстрації обробника, і він її однаково бачить. Це найважливіша перевага делегування.

Делегування також економить пам'ять, бо замість сотні функцій зберігається одна, але для сторінки зі ста кнопками
ця економія невелика. Важливіша причина інша: не треба стежити за обробниками, коли елементи з'являються й зникають.

Межі в делегування теж є. Подію, що не спливає, як `focus`, обробник на предку почує лише під час занурення, тобто
з параметром `{ capture: true }`. Якщо нижчий обробник зупинив спливання викликом `stopPropagation()`, звичайний
обробник на предку не почує нічого.

## Типові хибні уявлення

**«`event.target` — це елемент, на який я повісив обробник».** Це `currentTarget`. Поле `target` вказує, де подія
виникла, і це може бути глибокий нащадок.

**«`preventDefault()` зупиняє подію».** Він скасовує лише дію браузера. Шлях події продовжується, тому обробники вище
спрацюють.

**«`stopPropagation()` скасовує перехід за посиланням».** Навпаки, перехід відбудеться, бо дію браузера ніхто не
скасовував.

**«Атрибут і властивість — це те саме».** Для `id` майже так. Для `checked` і `value` це різні речі, а `href` має
різний вміст.

**«`innerHTML +=` дописує текст».** Запис створює всі вузли заново, і стара кнопка втрачає обробники.

## Як це проявиться в React

Коли ви пишете `onClick` у React, це не `addEventListener` на вашому вузлі. Починаючи з версії 17, React реєструє
обробники на **корені**, тобто на вузлі, куди змонтовано застосунок. Там він ловить події, що спливли, і сам викликає
ваші функції за деревом компонентів. Це те саме делегування.

Приклади цього розділу використовують React, тому консоль браузера для них не підійде. Проєкт React ви створите в
дні 11. У ньому можна замінити вміст файла `src/main.tsx` кодом прикладу й побачити вивід у консолі браузера. Зараз
достатньо прочитати код і вивід.

Код написано мовою TypeScript із JSX, як і приклади React у попередніх днях. Запис `type: string` після імені
параметра, як і `ms: number` у лекції дня 3, позначає тип параметра. Трапляються й позначки TypeScript, яких ще не
було. Запис `as Element` каже TypeScript, що значення є елементом. Знак `!` після виразу
каже, що значення точно не `null`. Запис `querySelector<HTMLElement>` уточнює, який саме елемент поверне пошук. Ці
позначки лише допомагають перевірці типів і не змінюють того, що код робить, тому їх можна поки пропускати. Типи
пояснить день 9.

Спершу порахуємо слухачі на корені. Код нижче підміняє метод `addEventListener` на майбутньому корені: замість
справжнього методу в поле записано нашу функцію, яка спершу запам'ятовує назву події та фазу, а потім викликає
справжній метод. Так ми бачимо кожну реєстрацію, яку зробить React. Метод `bind(container)` прив'язує справжній
метод до вузла, щоб його можна було викликати окремо від вузла. Потім код просить React створити корінь:

```tsx
import { createRoot } from "react-dom/client";

const container = document.createElement("div");
const registered: string[] = [];
const realAdd = container.addEventListener.bind(container);

// Запам'ятовуємо назву кожної події й фазу, а тоді реєструємо обробник як зазвичай.
container.addEventListener = (
  type: string,
  listener: EventListenerOrEventListenerObject,
  options?: boolean | AddEventListenerOptions,
) => {
  const capture = options === true || (typeof options === "object" && options.capture === true);
  registered.push(type + (capture ? " занурення" : " спливання"));
  realAdd(type, listener, options);
};

createRoot(container);                         // компонент ще не показано, а слухачі вже є
console.log("слухачів на корені:", registered.length);
console.log(registered.filter((name) => name.startsWith("click ")).join(" | "));
```

```text
слухачів на корені: 142
click спливання | click занурення
```

Перший рядок показує, що React зареєстрував 142 слухачі ще до показу першого компонента. Другий рядок показує, що
подія `click` має два слухачі: для занурення й для спливання. Отже, на корені висить не один обробник на весь
застосунок, а окремий обробник майже для кожного типу події.

Тепер зберемо ту саму картку з кнопкою, додамо справжні обробники через `addEventListener` і клацнемо по символу.
Обробник React друкує три поля, а `nativeEvent` є справжньою подією браузера:

```tsx
import type { MouseEvent } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";

document.body.innerHTML = `<div id="root"></div>`;

const report = (name: string) => (e: MouseEvent) => {
  const target = e.target as Element;                    // де виникла подія
  const own = e.currentTarget as Element;                // ваш елемент, чий onClick зараз працює
  const real = e.nativeEvent.currentTarget as Element;   // де зараз стоїть справжня подія браузера
  console.log(name, "target", target.tagName, "| currentTarget", own.tagName, "| nativeEvent.currentTarget", real.id);
};

function Card() {
  return (
    <article onClick={report("article")}>
      <button id="like" onClick={report("button")}><b id="heart">♥</b></button>
    </article>
  );
}

// flushSync просить React показати компонент одразу, щоб наступні рядки вже знайшли кнопку.
flushSync(() => createRoot(document.querySelector("#root")!).render(<Card />));

// Це справжні обробники браузера, React про них нічого не знає.
document.querySelector("#like")!.addEventListener("click", () => console.log("справжній обробник на кнопці"));
document.addEventListener("click", () => console.log("справжній обробник на document"));

document.querySelector<HTMLElement>("#heart")!.click();
```

```text
справжній обробник на кнопці
button target B | currentTarget BUTTON | nativeEvent.currentTarget root
article target B | currentTarget ARTICLE | nativeEvent.currentTarget root
справжній обробник на document
```

Порядок пояснює шлях події. Справжній обробник на кнопці спрацював першим, бо подія ще не дійшла до кореня. Коли подія
дійшла, React викликав обробники кнопки й картки. Поле `currentTarget` у React показує ваш елемент, а справжня подія в
цю мить стоїть на корені. `document` лежить вище за корінь, тому він спрацював останнім.

Такий порядок має кілька наслідків.

**Зупинка в обробнику React.** `e.stopPropagation()` у React зупиняє рух по дереву компонентів і справжню подію теж.
Щоб це побачити, замініть у прикладі вище рядок кнопки на такий:

```tsx
      <button id="like" onClick={(e) => { report("button")(e); e.stopPropagation(); }}><b id="heart">♥</b></button>
```

```text
справжній обробник на кнопці
button target B | currentTarget BUTTON | nativeEvent.currentTarget root
```

Рядка `article` немає, тому `onClick` на батьку не спрацював. Рядка `document` теж немає. Причина в тому, коли
працює обробник React. Він працює всередині справжнього обробника на корені, поки справжня подія стоїть на корені.
Метод `e.stopPropagation()` об'єкта React зупиняє обхід компонентів і викликає `stopPropagation()` справжньої події.
Тому справжня подія не пішла від кореня вище, до `document`. Справжній обробник на кнопці лежить нижче кореня, тому
він устиг спрацювати раніше, ще до зупинки.

**Зупинка у справжньому обробнику.** Справжній `stopPropagation()` на вузлі нижче кореня не дає події дійти до кореня,
тому не спрацює жоден `onClick`. Щоб це побачити, поверніть рядок кнопки й замініть у тому самому прикладі справжній
обробник на кнопці:

```tsx
document.querySelector("#like")!.addEventListener("click", (event) => {
  console.log("справжній обробник зупинив подію");
  event.stopPropagation();
});
```

```text
справжній обробник зупинив подію
```

У виводі лише один рядок: React не дізнався про клацання взагалі. Таке трапляється, коли сторонній код сам додає
обробники на вузли. Тому, якщо `onClick` раптом перестав працювати, перевірте справжні обробники на вузлах нижче
кореня.

**`currentTarget` після `await`.** `e.currentTarget` після `await` дорівнює `null` і в React:

```tsx
import type { MouseEvent } from "react";
import { flushSync } from "react-dom";
import { createRoot } from "react-dom/client";

document.body.innerHTML = `<div id="root"></div>`;

function SaveButton() {
  const save = async (e: MouseEvent<HTMLButtonElement>) => {
    console.log("до await:", e.currentTarget.tagName);
    await new Promise((r) => setTimeout(r, 10));
    console.log("після await:", e.currentTarget);
  };
  return <button id="save" onClick={save}>Зберегти</button>;
}

flushSync(() => createRoot(document.querySelector("#root")!).render(<SaveButton />));
document.querySelector<HTMLElement>("#save")!.click();
```

```text
до await: BUTTON
після await: null
```

Рядок після `await` друкує `null`, тому читання `e.currentTarget.dataset` у цьому місці впаде. Вузол зберігають у
змінну до `await`, так само як у коді без React.

**Інші події.** Частина подій поводиться інакше, ніж у браузері. Документація React каже, що `onFocus` і `onBlur`
спливають, а `onScroll` не спливає. Причину видно в слухачах на корені. Візьмемо перший приклад цього розділу й
замінимо в ньому останній рядок, щоб надрукувати слухачі подій фокуса й прокручування:

```tsx
console.log(registered.filter((name) => /^(focus|blur|focusin|focusout|scroll) /.test(name)).join(" | "));
```

```text
слухачів на корені: 142
scroll занурення | focusin спливання | focusin занурення | focusout спливання | focusout занурення
```

Слухачів `focus` і `blur` на корені немає. Подія `blur` приходить, коли поле втрачає фокус, і вона, як `focus`, не
спливає. Замість цих двох подій React слухає `focusin` і `focusout`. Подія `focusout` — це спливна пара для
`blur`, так само як `focusin` — спливна пара для `focus`. Тому `onFocus` на батьківському елементі спрацює, коли
фокус отримає будь-яке поле всередині нього. Подія `scroll` у браузері не спливає, і `onScroll` у React поводиться
так само.

**Атрибути й властивості.** Проп `value` робить поле **керованим**. Після кожного рендеру React записує у властивість
`value` значення зі стану. Людина друкує літеру, браузер змінює властивість, але React одразу повертає туди значення
зі стану. Тому без `onChange`, який оновлює стан, поле не зміниться під руками людини. Проп `defaultValue` задає лише
початкове значення, як атрибут `value` у розмітці. Це ті самі атрибут і властивість, тільки під іншими назвами. Той
самий поділ є між `checked` і `defaultChecked`.

**Заміна `innerHTML`.** React змінює в DOM лише те, що справді відрізняється між двома рендерами, тому незмінені вузли
лишаються, а текст у полі не зникає.

## Перевірте себе

Спершу дайте відповідь самі, вголос або письмово, і лише потім розгортайте наші пояснення.

**1. У `<ul>` два `<li>`, між тегами є перенос рядка. Чому `childNodes.length` дорівнює 5, а `children.length`
дорівнює 2?**

<details><summary>Відповідь</summary>

Перенос рядка між тегами є текстовим вузлом. `childNodes` містить три текстові вузли й два елементи, а `children`
містить лише елементи.

</details>

**2. Обробник висить на `<article>`, людина клацнула по `<b>` усередині кнопки. Що буде в `target` і
`currentTarget`?**

<details><summary>Відповідь</summary>

`target` — `<b>`, бо там виникла подія. `currentTarget` — `<article>`, бо там висить обробник, що зараз працює.

</details>

**3. Обробник клацання є і на `<a>`, і на `<nav>` над ним. `<nav>` викликає `preventDefault()`. Чи буде перехід? Чи
спрацює обробник на `<a>`?**

<details><summary>Відповідь</summary>

Переходу не буде, бо браузер виконує дію після всього шляху події й бачить скасування. Обробник на `<a>` спрацює,
причому раніше, бо він нижче на шляху спливання.

</details>

**4. Обробник кнопки робить `await`, а потім читає `event.currentTarget.dataset.id` і падає. Чому й що зробити?**

<details><summary>Відповідь</summary>

Після `await` подія вже закінчила шлях, тому браузер очистив `currentTarget`, і там лежить `null`. Вузол треба
зберегти в змінну до `await`.

</details>

**5. Людина надрукувала текст у полі, а потім код виконав `form.innerHTML += "<p>підказка</p>"`. Що станеться?**

<details><summary>Відповідь</summary>

Усе, що всередині форми, створиться заново. Поле стане новим вузлом із порожнім значенням, а обробники на старих
вузлах зникнуть. Потрібно використовувати `append` чи `insertAdjacentHTML`.

</details>

**6. У React `e.stopPropagation()` викликано в обробнику кнопки. Чи спрацює `onClick` батька й обробник на `document`,
доданий через `addEventListener`?**

<details><summary>Відповідь</summary>

У нашому досліді не спрацював жоден. React зупинив рух по дереву компонентів і зупинив справжню подію на корені, тому
вона не піднялася до `document`.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| DOM | дерево об'єктів, яким браузер представляє сторінку |
| вузол | один об'єкт дерева DOM: елемент, текст чи документ |
| атрибут | запис у розмітці, доступний через `getAttribute` |
| властивість | поле JavaScript-об'єкта вузла |
| відображення | правило стандарту HTML, яке пов'язує властивість з атрибутом |
| фокус | стан поля, яке зараз отримує натискання клавіш |
| ціль, `target` | вузол, де виникла подія |
| `currentTarget` | вузол, на якому висить обробник, що зараз працює |
| занурення | перша фаза шляху: від вікна вниз до цілі |
| спливання | остання фаза шляху: від цілі вгору |
| дія браузера | власна реакція браузера на подію, наприклад перехід за посиланням |
| делегування | один обробник на предку для подій з усіх дітей |
