# Лекція. День 9. TypeScript: основи

Ця лекція пояснює з самого початку, що таке TypeScript, хто й коли перевіряє типи і чому дані з мережі все одно треба
перевіряти власним кодом. Вона спирається лише на JavaScript із попередніх днів. Читання займе близько 30 хвилин.
Вивід кожної команди наведено таким, яким він був насправді. Лише коли програма падає, Node друкує ще шлях до файла,
рядок коду з позначкою місця й перелік викликів, і ці рядки тут пропущено.

**Після лекції ви зможете пояснити:**

- хто перевіряє типи, коли це відбувається і чому файл із помилкою типу все одно запускається;
- що таке об'єднання типів і як звичайний `if` доводить компілятору, яке значення перед ним;
- чому кілька варіантів зі спільним полем кращі за один об'єкт із необов'язковими полями;
- чим відрізняються `any`, `unknown` і `as`, і чому відповідь сервера не можна просто назвати потрібним типом;
- чому помилка типів у React виглядає як помилка React, хоча React тут ні до чого.

## Помилка, яку JavaScript не вважає помилкою

Уявіть інтернет-магазин. Функція додає до суми замовлення вартість доставки. Суму програма бере з поля форми, а поле
форми завжди віддає рядок, навіть коли людина ввела цифри.

Файл `order.js`:

```js
function totalWithDelivery(order, delivery) {
  return order.total + delivery;
}

console.log(totalWithDelivery({ total: "100" }, 50));
console.log(totalWithDelivery({ totl: 100 }, 50));
```

```text
$ node order.js
10050
NaN
```

Програма не впала жодного разу, хоча обидві відповіді неправильні. У першому виклику оператор `+` побачив рядок і
склеїв `"100"` із `50`. У другому виклику в назві поля є описка, читання неіснуючого поля дало `undefined`, а
`undefined + 50` дає `NaN`, тобто «не число».

JavaScript дізнається про значення лише тоді, коли виконує рядок, і навіть тоді не знає, чого ви хотіли. Такі помилки
знаходить покупець. Щоб знаходити їх раніше, потрібна програма, яка прочитає код до запуску й порівняє те, що функція
очікує, з тим, що їй дають.

## Що додає TypeScript

**TypeScript** — це JavaScript, до якого можна дописувати описи значень. Такий опис називається **типом**: він каже,
яке значення може бути в цьому місці. Наприклад, `number` означає «будь-яке число», а `{ total: number }` означає
«об'єкт, у якому є поле `total` із числом».

Описи читає програма `tsc`. Її називають **компілятором**, бо вона вміє ще й перетворювати файл `.ts` на файл `.js`.
Сьогодні нам потрібна лише перша її робота: прочитати код, порівняти значення з описами й повідомити про розбіжності.

Програма `tsc` входить до пакета `typescript`. До першої команди цей пакет треба встановити в теку вашого проєкту
командою `npm i -D typescript`. Якщо в теці ще немає файла `package.json`, спершу створіть його командою
`npm init -y`. Запис `npm i` є коротким ім'ям `npm install`, а `-D` є коротким ім'ям `--save-dev`: пакет потрапляє в
розділ `devDependencies`, тобто в інструменти розробки (див. лекцію дня 4, розділ «Пакети: як чужий код потрапляє у
проєкт»). Компілятор потрібен лише вам, поки ви пишете код, а програмі під час роботи він не потрібен.

Після встановлення команда `npx tsc --version` друкує номер версії компілятора. Приклади цієї лекції перевірено
версією 7.0.2, найновішою стабільною в реєстрі npm на день написання:

```text
$ npm init -y > /dev/null
$ npm i -D typescript

added 2 packages, and audited 3 packages in 2s

found 0 vulnerabilities
$ npx tsc --version
Version 7.0.2
```

Пакетів додано два, бо версія 7 складається з пакета `typescript` і ще одного пакета з готовою програмою для вашої
операційної системи. Npm сам вибирає потрібний.

Команда `npx tsc` шукає програму `tsc` серед пакетів, встановлених у теку проєкту. Якщо пакета `typescript` там немає,
`npx` питає, чи завантажити з реєстру npm інший пакет:

```text
$ npx tsc --version
Need to install the following packages:
tsc@2.0.4
Ok to proceed? (y)
```

Пакет `tsc` не є компілятором TypeScript. Це стара покинута публікація, і після запуску вона лише друкує рядок
`This is not the tsc command you are looking for`, тобто «це не та команда `tsc`, яку ви шукаєте». Тому на це
запитання відповідайте `n` і встановіть пакет `typescript`.

Тепер той самий код із типами. Перший рядок `type Order = { total: number };` дає типу назву `Order`, щоб далі не
переписувати опис щоразу. Слово `type` тут означає «оголошую назву типу», і докладніше про нього йдеться нижче, у
розділі «Як записують типи». Запис `order: Order` після назви параметра називається **анотацією**: він каже, якого
типу цей параметр. Запис `: number` після дужок задає тип результату.

Файл `order.ts`:

```ts
type Order = { total: number };

function totalWithDelivery(order: Order, delivery: number): number {
  return order.total + delivery;
}

console.log(totalWithDelivery({ total: "100" }, 50));
console.log(totalWithDelivery({ totl: 100 }, 50));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false order.ts
order.ts(7,33): error TS2322: Type 'string' is not assignable to type 'number'.
order.ts(8,33): error TS2561: Object literal may only specify known properties, but 'totl' does not exist in type 'Order'. Did you mean to write 'total'?
$ echo $?
1
```

Запис `order.ts(7,33)` означає «файл, рядок 7, символ 33 у цьому рядку». `TS2322` — номер помилки, за яким її легко
шукати. Перше повідомлення перекладається так: «тип `string` не можна присвоїти типу `number`». Слова `not assignable`
означають, що значення одного типу не можна покласти туди, де обіцяно інший.

Друге повідомлення каже: «об'єктний літерал може називати лише відомі поля, а поля `totl` у типі `Order` немає; може,
ви хотіли написати `total`?». **Об'єктним літералом** називають об'єкт, записаний прямо в коді у фігурних дужках, як
`{ totl: 100 }` тут. Компілятор не лише знайшов описку, а й запропонував правильну назву поля.

Команда `echo $?` друкує код, з яким завершилася попередня команда. Код 0 означає успіх, а будь-який інший код означає
невдачу. Тут `tsc` завершився з кодом 1, бо знайшов помилки.

Тепер про прапорці команди:

- `--noEmit` просить лише перевірити код і не створювати файла `.js`.
- `--strict` вмикає всі суворі перевірки. Починаючи з TypeScript 6.0, вони увімкнені й без прапорця. Тут прапорець
  стоїть, щоб у команді було видно, з якими налаштуваннями зроблено перевірку.
- `--target es2022` називає видання стандарту JavaScript, для якого компілятор готує код. Від цього залежить, які
  вбудовані функції він вважає наявними і який новий синтаксис переписав би старішим, якби створював файл `.js`. Без
  прапорця TypeScript 7.0 бере видання es2025. На приклади цієї лекції вибір видання не впливає: без `--strict` і
  `--target` вони дають той самий вивід.
- `--pretty false` друкує помилки простим текстом, без кольорів і рамок.

У справжньому проєкті ці налаштування записують один раз у файл `tsconfig.json`, і тоді запускають просто `npx tsc`.
Сьогодні такого файла в теці немає, тому прапорці стоять у команді. Якщо `tsconfig.json` у теці є, а ви назвете файл
у команді, TypeScript 6.0 і новіші зупиняються з помилкою:

```text
$ npx tsc --noEmit --pretty false order.ts
error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Use '--ignoreConfig' to skip this error.
```

Повідомлення попереджає, що з файлом у команді налаштування з `tsconfig.json` не застосуються. Тоді або запускайте
`npx tsc` без назви файла, або додайте `--ignoreConfig`, якщо файл налаштувань справді треба пропустити.

## Перевірка й запуск — дві окремі дії

Тепер запустимо той самий файл із помилками:

```text
$ node order.ts
10050
NaN
```

Node 24 запускає файли `.ts` напряму й типів не перевіряє. Він замінює все, що стосується типів, пробілами, а решту
виконує як звичайний JavaScript. Тому програма видає ті самі неправильні числа, що й без типів. Це називається
**стиранням типів** (у документації Node — type stripping). Пробіли замість простого видалення потрібні для того, щоб
кожен рядок і кожен символ лишилися на своєму місці: тоді номер рядка в повідомленні про помилку збігається з вашим
файлом.

Усі запуски `node` у цій лекції зроблено саме так: файл `.ts` подано Node без попереднього перетворення, а `tsc` лише
перевіряв його. Ця можливість увімкнена в Node 24 без прапорців, від версії 24.3 вона не друкує попереджень, а від
версії 24.12 вважається стабільною. Приклади запущено на Node 24.22.

Стирання має дві межі, про які варто знати заздалегідь. Перша: Node уміє лише стерти типи, тому записи TypeScript,
які треба перетворити на інший код, наприклад `enum`, він без окремого прапорця не запустить. У цій лекції таких
записів немає. Друга: Node не читає файла `tsconfig.json`, тому налаштування з нього на запуск не впливають.

| | `tsc` | `node` |
|--|-------|--------|
| Коли працює | до запуску програми | під час запуску |
| Що робить із типами | порівнює з ними кожне значення в коді | викидає їх, не читаючи |
| Що бачить | лише текст коду | справжні значення, зокрема дані з мережі |
| Помилка типу | друкує її й завершується з кодом 1 | не шукає її й ніяк не реагує |

З цієї таблиці випливають три наслідки, і на них тримається решта лекції.

**Перший: про типи свідчить лише `tsc`.** Те, що `node` запустив файл, нічого не доводить. Типи збігаються тоді, коли
`tsc` нічого не надрукував і завершився з кодом 0.

**Другий: під час роботи програми типів не існує.** Запитати в значення, чи воно `Order`, неможливо, бо слова `Order`
у виконуваному коді вже немає. Перевіряти під час роботи можна лише засобами JavaScript: `typeof`, порівнянням,
оператором `in`. Оператор `in` відповідає, чи є в об'єкті поле з такою назвою (див. лекцію дня 2, розділ «Об'єкти без
мутацій»).

**Третій: `tsc` бачить код, а не дані.** Текст, який надішле сервер завтра, у коді не записаний, тому компілятор
нічого про нього не знає. Цьому присвячено окремий розділ нижче.

## Як записують типи

Спершу найчастіші записи типів. Таблиця показує, як кожен виглядає і яке значення до нього підходить; далі вони
трапляються в прикладах.

| Запис | Що він означає | Значення, яке підходить |
|-------|----------------|-------------------------|
| `string`, `number`, `boolean` | рядок, число, логічне значення | `"Чай"`, `80`, `true` |
| `number[]` | масив чисел | `[80, 150]` |
| `{ name: string; price: number }` | об'єкт із двома полями | `{ name: "Чай", price: 80 }` |
| `{ note?: string }` | поля `note` може не бути | `{}` або `{ note: "Крихке" }` |
| `(price: number) => string` | функція з числа в рядок | `(price) => price + " грн"` |

**Де анотації потрібні.** Компілятор сам визначає тип, коли бачить значення, і це називається **виведенням типу**.
Запис `let price = 80` дає змінній тип `number`, бо в неї покладено число, і наступний рядок `price = "сто"`
компілятор відхилить без жодної анотації. З параметром функції так не вийде: функцію можуть викликати звідки
завгодно з чим завгодно, і всередині функції немає значення, з якого можна вивести тип. Тому `--strict` вимагає для
параметрів анотації.

Файл `inference.ts`:

```ts
let price = 80; // компілятор виводить тип number
price = "сто";

function withVat(amount) {
  return amount * 1.2;
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false inference.ts
inference.ts(2,1): error TS2322: Type 'string' is not assignable to type 'number'.
inference.ts(4,18): error TS7006: Parameter 'amount' implicitly has an 'any' type.
```

Перше повідомлення таке саме, як у `order.ts`: тип `number` компілятор вивів сам. Друге повідомлення перекладається
так: «параметр `amount` неявно має тип `any`». Тип `any` означає «не перевіряти це значення взагалі», докладно про
нього йдеться в розділі «`any`, `unknown` і `as`» нижче. Компілятор не мовчить, а повідомляє, що для параметра без
анотації він вимкнув би перевірку. Звичайна практика така: анотувати параметри й результат функції, а локальні
змінні залишати виведенню.

**`type` і `interface`.** Обидва слова дають типу назву, і для об'єктів вони майже рівноцінні. Той самий опис
замовлення можна записати двома способами. Це два варіанти на вибір, а не один файл: разом в одному файлі вони дали
б помилку про подвійне оголошення.

```ts
// Варіант через type: назва, знак = і опис після нього.
type Order = { total: number };
```

```ts
// Варіант через interface: назва й опис у фігурних дужках, без знака =.
interface Order {
  total: number;
}
```

Відрізняються вони двома речами. Лише `type` може назвати об'єднання, про яке йтиметься далі. Лише `interface` можна
оголосити вдруге з тією самою назвою, і тоді компілятор додає поля другого оголошення до першого. Ось як це виглядає.

Файл `interface.ts`:

```ts
interface Order {
  total: number;
}

interface Order {
  comment?: string;
}

const order: Order = { total: 100, comment: "Крихке" };
console.log(order);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false interface.ts
(tsc нічого не надрукував: помилок немає)
$ node interface.ts
{ total: 100, comment: 'Крихке' }
```

Компілятор прийняв поле `comment`, бо друге оголошення додало його до `Order`. Тепер те саме через `type`.

Файл `dup.ts`:

```ts
type Order = { total: number };
type Order = { comment?: string };
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false dup.ts
dup.ts(1,6): error TS2300: Duplicate identifier 'Order'.
dup.ts(2,6): error TS2300: Duplicate identifier 'Order'.
```

Повідомлення перекладається як «назву `Order` оголошено двічі», і компілятор ставить його біля кожного з двох
оголошень. Отже, `type` назву лише дає, а доповнювати опис уміє тільки `interface`.

Котре з двох слів брати? Сторінка Everyday Types документації TypeScript у розділі про їхні відмінності радить брати
`interface`, доки не знадобиться те, що вміє лише `type`. У реальних проєктах трапляються обидва підходи, тому
вирішує домовленість у проєкті.

**Компілятор порівнює форму, а не назву.** Значення підходить до типу, якщо в ньому є всі потрібні поля потрібних
типів. Об'єкт не мусить бути створений «як `Order`» і не мусить згадувати слово `Order`. Це називається
**структурною типізацією**. Тому змінну, у якій є зайве поле, теж можна передати у функцію: зайве поле функції не
заважає. Виняток стосується об'єктного літерала, написаного прямо там, де очікують тип.

Файл `structural.ts`:

```ts
type Order = { total: number };

function totalWithDelivery(order: Order, delivery: number): number {
  return order.total + delivery;
}

const fromForm = { total: 100, comment: "Подзвонити перед доставкою" };
console.log(totalWithDelivery(fromForm, 50));
console.log(totalWithDelivery({ total: 100, comment: "Подзвонити" }, 50));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false structural.ts
structural.ts(9,45): error TS2353: Object literal may only specify known properties, and 'comment' does not exist in type 'Order'.
$ node structural.ts
150
150
```

Змінну `fromForm` компілятор пропустив, хоча в ній є поле `comment`, якого `Order` не описує. Літерал із тим самим
полем на рядку 9 він відхилив. Причина така. Змінна `fromForm` може знадобитися деінде, де поле `comment` потрібне,
тому зайве поле в ній має сенс. Літерал же існує лише в цьому виклику, і функція поля `comment` ніколи не прочитає.
Отже, зайве поле в літералі нікуди не дійде, і найімовірніше це описка, як `totl` у файлі `order.ts`. Такий захід
називають перевіркою зайвих полів. Запуск надрукував `150` двічі: для JavaScript обидва виклики однакові, а
відрізняються вони лише для компілятора.

## Об'єднання: одне з кількох

Знижку в нашому магазині можна задати числом, можна кодом-рядком, а можна не задати взагалі. Один тип цього не опише.
**Об'єднання** записують через вертикальну риску: `string | number | null` означає «або рядок, або число, або `null`».

Об'єднання приймає будь-який зі своїх варіантів, зате читати з нього дозволено лише те, що є в усіх варіантах.
Компілятор міркує так: значення може виявитися будь-яким варіантом, тому операція має бути допустимою для кожного.

Метод `toString` є і в рядка, і в числа, тому для `string | number` його викликати можна. Метод `toUpperCase` є лише в
рядка, тому такий виклик компілятор не пропускає.

Файл `union.ts`:

```ts
function label(value: string | number): string {
  console.log(value.toString()); // метод є в обох варіантах
  return value.toUpperCase(); // метод є лише в рядка
}

console.log(label(5));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false union.ts
union.ts(3,16): error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
  Property 'toUpperCase' does not exist on type 'number'.
$ node union.ts
5
TypeError: value.toUpperCase is not a function
```

Компілятор поскаржився лише на рядок 3, а рядок 2 пропустив. Рядок із відступом уточнює причину: цього методу немає у
варіанта `number`. Запуск показує, що компілятор мав рацію: `node` надрукував `5` із рядка 2, а на рядку 3 програма
впала, бо функція отримала саме число. Отже, повідомлення про об'єднання вказує на виклик, який справді може впасти в
покупця, тому такий виклик треба спершу захистити перевіркою.

Значення `null` і `undefined` теж стають варіантами об'єднання. З прапорцем `--strict` тип `string` їх не містить,
тому можливу відсутність значення записують прямо: `string | null`.

## Звуження: `if` як доказ для компілятора

Щоб скористатися об'єднанням, треба з'ясувати, який варіант перед нами. Для цього пишуть звичайну перевірку
JavaScript, а компілятор читає її й робить тип вужчим усередині гілки. Це називається **звуженням**, і окремого
синтаксису воно не потребує.

Файл `discount.ts`:

```ts
function discount(code: string | number | null): number {
  if (code === null) {
    return 0;
  }
  if (typeof code === "number") {
    return code;
  }
  return code === "VIP" ? 20 : 5;
}

console.log(discount(null), discount(15), discount("VIP"), discount("WELCOME"));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false discount.ts
(tsc нічого не надрукував: помилок немає)
$ echo $?
0
$ node discount.ts
0 15 20 5
```

Компілятор нічого не виконує. Він читає код зверху вниз і після кожного рядка запам'ятовує, що ще може лежати в
змінній `code`. Простежмо за ним.

На початку функції в `code` може бути будь-що з анотації: рядок, число або `null`. Перший `if` перевіряє
`code === null`. Усередині цієї гілки умова виконалась, тому там у `code` лежить саме `null`. Гілка закінчується
`return`, і функція з неї виходить. Отже, до рядків після першого `if` значення `null` дійти не може, і компілятор
прибирає його з типу: там `code` має тип `string | number`.

Другий `if` перевіряє `typeof code === "number"`. Усередині нього компілятор залишає лише варіант `number`, тому
`return code` повертає число, як і обіцяє тип результату. Ця гілка теж закінчується `return`. На останній рядок
доходить лише те, що не відсіяла жодна перевірка, тобто рядок. Тому порівняння `code === "VIP"` компілятор
перевіряє вже для типу `string`.

Компілятор розуміє кілька видів перевірок. Ось підсумок:

| Перевірка | Що вона доводить | На що зважати |
|-----------|------------------|---------------|
| `typeof x === "string"` | примітивний тип значення | `typeof` не відрізняє `null` від об'єкта |
| `x !== null` | значення не `null` | прибирає цей варіант із типу |
| `"field" in x` | в об'єкті є таке поле | якщо тип об'єкта цього поля не описує, значення в полі має тип `unknown` |
| `if (x)` | значення не є хибним | відкидає ще й `0` та порожній рядок |

Тип `unknown` у третьому рядку означає «значення невідомого типу». Він з'явиться в розділі «`any`, `unknown` і
`as`», і там видно, як `in` працює з ним крок за кроком.

**Пастка з `typeof null`.** У JavaScript `typeof null` дорівнює `"object"`. Причина історична. У першій реалізації
мови кожне значення зберігалося разом із числовою позначкою типу, і в об'єктів ця позначка дорівнювала нулю. Значення
`null` записували як нульову адресу, тому його позначка теж виходила нульовою, і `typeof` називав його об'єктом.
Виправлення цього результату пропонували до стандарту, але відхилили. Компілятор це знає, тому після
`typeof x === "object"` залишає `null` серед можливих варіантів. Прибрати його може лише окрема перевірка
`x !== null`.

**Пастка з `if (x)`.** Значення `0`, `""` і `NaN` теж вважаються хибними. Тому `if (price)` для типу
`number | null` відправляє безкоштовну доставку за нуль гривень у ту саму гілку, що й відсутню ціну.

Файл `free-delivery.ts`:

```ts
function deliveryText(price: number | null): string {
  if (price) {
    return "Доставка " + price + " грн";
  }
  return "Ціну доставки не вказано";
}

console.log(deliveryText(50));
console.log(deliveryText(null));
console.log(deliveryText(0));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false free-delivery.ts
(tsc нічого не надрукував: помилок немає)
$ node free-delivery.ts
Доставка 50 грн
Ціну доставки не вказано
Ціну доставки не вказано
```

Третій рядок виводу неправильний: доставку за нуль гривень програма назвала відсутньою ціною. Компілятор цього не
зупинив, бо з типами тут усе гаразд: після `if (price)` у гілці справді число. Неправильний лише зміст, і його
компілятор не бачить. Щоб нуль пішов у першу гілку, умова має перевіряти саме `null`: `price !== null`.

## Розрізнюване об'єднання: варіанти зі спільним полем

Спершу ще одне поняття. Тип може складатися з одного конкретного значення. Запис `"packing"` як тип означає «лише
рядок `packing`». Це називається **літеральним типом**.

Тепер опишемо доставку посилки, яка буває на трьох етапах. Поки посилку пакують, кур'єра ще немає. Коли її везуть,
кур'єр є. Коли її отримали, відомо, хто підписав. Перший спосіб, який спадає на думку, це один об'єкт із
необов'язковими полями.

Файл `delivery-loose.ts`:

```ts
type Delivery = {
  stage: "packing" | "onTheWay" | "delivered";
  courier?: string;
  signedBy?: string;
};

function courierName(delivery: Delivery): string {
  if (delivery.stage === "onTheWay") {
    return delivery.courier.toUpperCase();
  }
  return "";
}

const nonsense: Delivery = { stage: "packing", signedBy: "Оксана" };
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false delivery-loose.ts
delivery-loose.ts(9,12): error TS18048: 'delivery.courier' is possibly 'undefined'.
```

Повідомлення перекладається так: «`delivery.courier`, можливо, дорівнює `undefined`». Знак `?` у записі `courier?:`
каже, що поля може не бути. Читання відсутнього поля дає `undefined`, а в `undefined` немає методу `toUpperCase`.

У цього опису дві вади. Компілятор не знає зв'язку між `stage` і `courier`, хоча ми його знаємо, тому навіть після
перевірки етапу вимагає довести наявність кур'єра. А останній рядок проходить без помилки, хоча описує неможливу
ситуацію: посилку ще пакують, а хтось уже її підписав.

Другий спосіб описує кожен етап окремим варіантом зі своїми полями. Поле `stage` є в усіх варіантах, але в кожному має
свій літерал. Таке об'єднання називається **розрізнюваним**, бо за спільним полем компілятор розрізняє варіанти.

Файл `delivery.ts`:

```ts
type Delivery =
  | { stage: "packing" }
  | { stage: "onTheWay"; courier: string }
  | { stage: "delivered"; signedBy: string };

function describe(delivery: Delivery): string {
  switch (delivery.stage) {
    case "packing":
      return "Пакуємо";
    case "onTheWay":
      return "Везе " + delivery.courier;
    case "delivered":
      return "Отримав " + delivery.signedBy;
  }
}

console.log(describe({ stage: "onTheWay", courier: "Ігор" }));
console.log(describe({ stage: "delivered", signedBy: "Оксана" }));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false delivery.ts
(tsc нічого не надрукував: помилок немає)
$ node delivery.ts
Везе Ігор
Отримав Оксана
```

Рядок за рядком:

- `switch (delivery.stage)` перевіряє спільне поле. До цього рядка компілятор дозволяє читати лише `stage`, бо лише
  воно є в усіх варіантах.
- Усередині `case "onTheWay"` компілятор уже вибрав варіант із кур'єром, тому `delivery.courier` має тип `string`, а
  не `string | undefined`.
- Гілки `default` немає. Компілятор сам порахував, що три випадки охоплюють усі варіанти, тому не скаржиться, що
  функція може нічого не повернути.

Такий опис не дає записати кілька типових помилок. Запишемо п'ять таких помилок в одному файлі й покажемо його
компілятору.

Файл `delivery-errors.ts`:

```ts
type Delivery =
  | { stage: "packing" }
  | { stage: "onTheWay"; courier: string }
  | { stage: "delivered"; signedBy: string };

// Читаємо поле кур'єра, не перевіривши етап.
function courierName(delivery: Delivery): string {
  return delivery.courier;
}

// У switch немає випадку "delivered".
function describe(delivery: Delivery): string {
  switch (delivery.stage) {
    case "packing":
      return "Пакуємо";
    case "onTheWay":
      return "Везе " + delivery.courier;
  }
}

// Описка в назві етапу: мала літера w.
const typo: Delivery = { stage: "onTheway", courier: "Ігор" };

// Кур'єра забули вказати.
const noCourier: Delivery = { stage: "onTheWay" };

// Посилку ще пакують, а кур'єр уже є.
const tooEarly: Delivery = { stage: "packing", courier: "Ігор" };
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false delivery-errors.ts
delivery-errors.ts(8,19): error TS2339: Property 'courier' does not exist on type 'Delivery'.
  Property 'courier' does not exist on type '{ stage: "packing"; }'.
delivery-errors.ts(12,40): error TS2366: Function lacks ending return statement and return type does not include 'undefined'.
delivery-errors.ts(22,26): error TS2820: Type '"onTheway"' is not assignable to type '"delivered" | "onTheWay" | "packing"'. Did you mean '"onTheWay"'?
delivery-errors.ts(25,7): error TS2322: Type '{ stage: "onTheWay"; }' is not assignable to type 'Delivery'.
  Property 'courier' is missing in type '{ stage: "onTheWay"; }' but required in type '{ stage: "onTheWay"; courier: string; }'.
delivery-errors.ts(28,48): error TS2353: Object literal may only specify known properties, and 'courier' does not exist in type '{ stage: "packing"; }'.
```

Кожній помилці в коді відповідає одне повідомлення, а рядки з відступом уточнюють причину. Розберемо їх по черзі.

- Рядок 8, `return delivery.courier`. Повідомлення каже: «поля `courier` немає в типі `Delivery`», а рядок із
  відступом уточнює, що його немає у варіанті `{ stage: "packing"; }`. Етап ще не перевірено, тому значення може
  виявитися будь-яким варіантом, а читати дозволено лише спільні поля, тобто тільки `stage`.
- Рядок 12, функція `describe` без випадку `"delivered"`. Повідомлення каже: «функції бракує завершального `return`,
  а тип результату не містить `undefined`». Якщо прийде етап `"delivered"`, жоден `case` не спрацює, виконання дійде
  до кінця функції, і функція поверне `undefined`. Тип результату обіцяє рядок, тому компілятор цього не пропускає.
- Рядок 22, описка `"onTheway"`. Повідомлення каже: «тип `"onTheway"` не можна присвоїти типу
  `"delivered" | "onTheWay" | "packing"`», і далі «може, ви мали на увазі `"onTheWay"`?». Тип поля `stage` складається
  лише з трьох літералів, тож будь-який інший рядок не підходить. Порядок варіантів у повідомленні не збігається з
  порядком у коді, бо TypeScript 7.0 упорядковує типи за власним сталим правилом. На зміст це не впливає.
- Рядок 25, `{ stage: "onTheWay" }` без кур'єра. Повідомлення каже: «поля `courier` бракує», і показує варіант, у
  якому воно обов'язкове. Значення `stage` вибрало варіант із кур'єром, тому решту полів компілятор вимагає саме від
  цього варіанта.
- Рядок 28, `{ stage: "packing", courier: "Ігор" }`. Це вже знайома перевірка зайвих полів з розділу «Як записують
  типи»: варіант `packing` поля `courier` не описує, а об'єктний літерал його називає.

Отже, описка, забуте поле чи забутий випадок зупиняють вас ще до запуску, і покупець їх не побачить. Коротко це
формулюють так: неможливі стани не вдасться навіть записати.

**Тип `never`.** Коли всі варіанти вичерпано, у змінній не лишається жодного можливого значення. Для цього існує тип
`never`, «сюди не дійде жодне значення», і покласти в нього можна лише `never`. Тому в гілці `default` часто пишуть
`const rest: never = delivery`. Якщо хтось додасть четвертий етап і забуде про нього в цьому `switch`, компілятор
покаже на цей рядок і назве забутий варіант.

Файл `delivery-never.ts`:

```ts
type Delivery =
  | { stage: "packing" }
  | { stage: "onTheWay"; courier: string }
  | { stage: "delivered"; signedBy: string }
  | { stage: "returned"; reason: string }; // новий етап, для якого немає case

function describe(delivery: Delivery): string {
  switch (delivery.stage) {
    case "packing":
      return "Пакуємо";
    case "onTheWay":
      return "Везе " + delivery.courier;
    case "delivered":
      return "Отримав " + delivery.signedBy;
    default:
      // Сюди доходить лише те, що не обробив жоден case.
      const rest: never = delivery;
      return rest;
  }
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false delivery-never.ts
delivery-never.ts(17,13): error TS2322: Type '{ stage: "returned"; reason: string; }' is not assignable to type 'never'.
```

Компілятор показав на рядок 17 і в лапках назвав варіант `returned`, який ніхто не обробив. Якщо прибрати рядок із
цим варіантом з опису типу, `tsc` не надрукує нічого, бо в гілці `default` не лишиться жодного можливого значення.
Отже, новий етап сам покаже вам кожен `switch` із таким рядком, де про нього забули.

Рядок `return rest` потрібен, бо функція обіцяє повернути рядок. Тип `never` можна покласти в змінну будь-якого
типу: значення, якого не буває, нічому не суперечить. Тому компілятор приймає `rest` як рядок, і повідомлення про
відсутній `return` не з'являється.

## `any`, `unknown` і `as`: що робити з даними ззовні

Тепер повернімося до третього наслідку: `tsc` не бачить даних. Сервер надсилає текст, програма перетворює його на
значення, і лише під час запуску стає відомо, що там насправді. Є три способи сказати про таке значення компілятору, і
лише один із них безпечний.

Нижче кожен спосіб розібрано окремо з прикладом. Таблиця дає їх наперед для порівняння. У ній `Rate` означає тип курсу
валюти з прикладів цього розділу.

| Запис | Що він каже компілятору | Що дозволено зі значенням | Що буде з неправильними даними |
|-------|-------------------------|---------------------------|--------------------------------|
| `any` | не перевіряй взагалі | усе | помилка під час роботи, у покупця |
| `as Rate` | вважай, що це `Rate` | усе, що дозволено для `Rate` | помилка під час роботи, у покупця |
| `unknown` | я не знаю, що це | нічого, доки немає перевірки | ваша перевірка відхиляє їх одразу |

**`any` приходить сам.** Разом із компілятором встановлюються файли з описами типів усього, що вбудоване в JavaScript
і в браузер. Такі файли мають розширення `.d.ts` і містять лише типи без коду. У TypeScript 7.0.2 вони лежать у теці
`node_modules/@typescript/<ваша система>/lib`. Ось два рядки звідти:

```ts
// lib.es5.d.ts, опис JSON.parse
parse(text: string, reviver?: (this: any, key: string, value: any) => any): any;

// lib.dom.d.ts, опис методу json() у відповіді fetch
json(): Promise<any>;
```

Останнє `: any` у першому рядку означає, що результат `JSON.parse` має тип `any`. Запис `Promise<any>` означає
«проміс, який дасть значення типу `any`»: у кутових дужках стоїть тип того, що лежить усередині проміса. Докладно
кутові дужки пояснить лекція дня 10. Отже, навіть без слова `any` у вашому коді значення з мережі вже не
перевіряється.

**`as` — це обіцянка.** Запис `значення as Тип` називається **твердженням типу**. Він нічого не перевіряє й нічого не
перетворює, а лише наказує компілятору вважати значення таким типом. Запис `as Element` із лекції дня 7 був саме
таким твердженням. Припустімо, сервер надіслав курс валюти, але поле `value` прийшло рядком.

Файл `rate-as.ts`:

```ts
type Rate = { currency: string; value: number };

const rate = JSON.parse('{"currency": "EUR", "value": "41.5"}') as Rate;
console.log(rate.value.toFixed(2));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false rate-as.ts
(tsc нічого не надрукував: помилок немає)
$ node rate-as.ts
TypeError: rate.value.toFixed is not a function
```

Компілятор мовчить, бо йому пообіцяли `Rate`, а метод `toFixed` у числа є. Програма падає, бо там рядок. Метод
`toFixed(2)` записує число з двома знаками після коми, а в рядка такого методу немає.

Обіцянку `as` компілятор приймає не завжди. Якщо два типи не мають нічого спільного, він вважає твердження помилкою.

Файл `as-direct.ts`:

```ts
const price = "41.5" as number;
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false as-direct.ts
as-direct.ts(1,15): error TS2352: Conversion of type 'string' to type 'number' may be a mistake because neither type sufficiently overlaps with the other. If this was intentional, convert the expression to 'unknown' first.
```

Повідомлення перекладається так: «перетворення типу `string` на тип `number` може бути помилкою, бо жоден із цих типів
не перетинається з іншим достатньо. Якщо ви зробили це навмисно, спершу перетворіть вираз на `unknown`». Останнє
речення означає запис `"41.5" as unknown as number`, і він з'явиться нижче, у розділі «Типові хибні уявлення».
Рядок ніколи не буває числом, тому таке твердження найімовірніше помилкове. Для `JSON.parse` цей захист не
спрацьовує: результат має тип `any`, а з `any` компілятор дозволяє твердження до будь-якого типу.

**`unknown` вимагає доказів.** Прочитати поле значення цього типу чи покласти його в змінну типу `number` компілятор
не дасть, доки перевірки не звузять тип.

Файл `unknown-read.ts`:

```ts
const data: unknown = JSON.parse('{"currency": "EUR", "value": 41.5}');

console.log(data.value);
const value: number = data;
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false unknown-read.ts
unknown-read.ts(3,13): error TS18046: 'data' is of type 'unknown'.
unknown-read.ts(4,7): error TS2322: Type 'unknown' is not assignable to type 'number'.
```

Значення типу `any` компілятор дозволяє покласти в змінну будь-якого типу, тому анотація `: unknown` приймає результат
`JSON.parse`. Далі змінна `data` має тип `unknown`, і компілятор знову стежить за кожною дією з нею. Перше
повідомлення каже: «`data` має тип `unknown`», тобто читати з нього поле не можна, бо невідомо, чи це взагалі
об'єкт. Друге каже, що невідоме значення не можна покласти туди, де обіцяно число. Дані тут правильні, але компілятор
цього не знає, доки код не перевірив їх сам. Той самий курс валюти з перевіркою.

Файл `rate.ts`:

```ts
type Rate = { currency: string; value: number };

function toRate(data: unknown): Rate {
  if (
    typeof data === "object" &&
    data !== null &&
    "currency" in data &&
    typeof data.currency === "string" &&
    "value" in data &&
    typeof data.value === "number"
  ) {
    return { currency: data.currency, value: data.value };
  }
  throw new Error("Сервер надіслав не курс валюти");
}

for (const text of [
  '{"currency": "EUR", "value": 41.5}',
  '{"currency": "EUR", "value": "41.5"}',
  '{"currency": "EUR"}',
  "null",
  '"EUR"',
]) {
  try {
    console.log(text, "->", toRate(JSON.parse(text)));
  } catch {
    console.log(text, "-> відхилено");
  }
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false rate.ts
(tsc нічого не надрукував: помилок немає)
$ node rate.ts
{"currency": "EUR", "value": 41.5} -> { currency: 'EUR', value: 41.5 }
{"currency": "EUR", "value": "41.5"} -> відхилено
{"currency": "EUR"} -> відхилено
null -> відхилено
"EUR" -> відхилено
```

Цикл подає функції п'ять текстів, і лише перший із них є правильним курсом. Решту функція відхиляє, кидаючи помилку.
Конструкцію `try ... catch` пояснювала лекція дня 1. Тут `catch` записано без `(e)`: так пишуть, коли сам об'єкт
помилки не потрібен, а важливо лише те, що вона сталася.

Компілятор читає ланцюжок умов зліва направо, і після кожної умови тип стає вужчим. Це можна побачити самому за
допомогою типу `never`. Покласти в `never` не можна нічого, тому кожен рядок `const ...: never = ...` у файлі нижче
навмисно неправильний, а компілятор у повідомленні про нього називає тип, який бачить у цьому місці. Той самий
ланцюжок тут записано вкладеними `if`, щоб після кожної умови стояв окремий рядок. Функцію ніхто не викликає, бо її
читає лише `tsc`.

Файл `rate-stages.ts`:

```ts
function stages(data: unknown) {
  if (typeof data === "object") {
    const a: never = data; // який тип має data?
    if (data !== null) {
      const b: never = data; // який тип має data?
      if ("currency" in data) {
        const c: never = data; // який тип має data?
        if (typeof data.currency === "string") {
          const d: never = data.currency; // який тип має поле?
          if ("value" in data) {
            const e: never = data; // який тип має data?
            if (typeof data.value === "number") {
              const f: never = data.value; // який тип має поле?
            }
          }
        }
      }
    }
  }
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false rate-stages.ts
rate-stages.ts(3,11): error TS2322: Type 'object | null' is not assignable to type 'never'.
  Type 'null' is not assignable to type 'never'.
rate-stages.ts(5,13): error TS2322: Type 'object' is not assignable to type 'never'.
rate-stages.ts(7,15): error TS2322: Type 'object & Record<"currency", unknown>' is not assignable to type 'never'.
rate-stages.ts(9,17): error TS2322: Type 'string' is not assignable to type 'never'.
rate-stages.ts(11,19): error TS2322: Type 'object & Record<"currency", unknown> & Record<"value", unknown>' is not assignable to type 'never'.
rate-stages.ts(13,21): error TS2322: Type 'number' is not assignable to type 'never'.
```

Кожне повідомлення відповідає одному навмисно неправильному рядку, а в перших лапках стоїть тип у цьому місці. Перше
повідомлення показує, що після `typeof` у значенні ще може бути `null`. Знак `&` означає «і те, і те», а запис
`Record<"currency", unknown>` означає «об'єкт, у якому є поле `currency` зі значенням типу `unknown`». Отже, оператор
`in` довів лише наявність поля, і перед використанням значення вам потрібна ще перевірка `typeof`.

Типи в таблиці взято з цих повідомлень:

| Умова | Яким став тип `data` | Який текст вона відхиляє |
|-------|----------------------|--------------------------|
| `typeof data === "object"` | `object \| null` | `"EUR"` |
| `data !== null` | `object` | `null` |
| `"currency" in data` | об'єкт із полем `currency` невідомого типу | об'єкт без цього поля |
| `typeof data.currency === "string"` | поле `currency` стало рядком | об'єкт із числом замість назви |
| `"value" in data` | додалося поле `value` невідомого типу | `{"currency": "EUR"}` |
| `typeof data.value === "number"` | поле `value` стало числом | `{"currency": "EUR", "value": "41.5"}` |

Функція будує новий об'єкт, а не повертає `data`, і цьому є причина. Компілятор звузив окремі поля, а сам `data`
лишився типу «об'єкт із полями невідомого типу», тому рядок `return data` він би не пропустив. Звуження стосується
саме виразу `data.currency`: компілятор запам'ятовує, що цей вираз дає рядок, але тип усього об'єкта `data` заради
цього не переписує. Це видно й у файлі `rate-stages.ts`: на рядку 11, уже після перевірки `typeof data.currency`,
поле `currency` у типі `data` усе ще має тип `unknown`. Це легко перевірити й інакше: скопіюйте `rate.ts` у файл
`rate-return.ts` і замініть у копії рядок `return { currency: data.currency, value: data.value };` на
`return data;`.

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false rate-return.ts
rate-return.ts(12,5): error TS2322: Type 'object & Record<"currency", unknown> & Record<"value", unknown>' is not assignable to type 'Rate'.
  Types of property 'currency' are incompatible.
    Type 'unknown' is not assignable to type 'string'.
```

Читайте це повідомлення з найглибшого рядка. Кожен рядок із більшим відступом уточнює попередній: перший каже, що
весь об'єкт не підходить до `Rate`, другий називає поле `currency`, а найглибший називає саму причину. Значення типу
`unknown` не можна покласти в поле типу `string`. Отже, функція перевірки повертає новий об'єкт, зібраний із полів,
які вона вже перевірила.

Таку перевірку ставлять один раз на межі програми, там, де дані заходять ззовні. Після неї решта коду працює зі
справжнім типом і нічого не перевіряє. У фазі 3 (день 10) плану з'явиться бібліотека `zod`, яка будує такі перевірки
з опису.

## Типові хибні уявлення

**«`tsc` не знайшов помилок, отже, дані правильні».** Він перевірив код. Дані з мережі він не бачив, а `as` і `any`
лише приховують це від нього.

**«`as number` перетворить рядок на число».** Перетворення робить лише код, наприклад `Number(text)`.

Файл `as-number.ts`:

```ts
// Спершу as unknown, бо прямий запис "41.5" as number дає помилку TS2352 (файл as-direct.ts вище).
const price = "41.5" as unknown as number;

console.log(typeof price); // що насправді лежить у змінній
console.log(price + 1); // компілятор вважає, що це додавання чисел
console.log(typeof Number("41.5")); // справжнє перетворення
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false as-number.ts
(tsc нічого не надрукував: помилок немає)
$ node as-number.ts
string
41.51
number
```

Значення `"41.5" as unknown as number` після запуску лишається рядком. Тому `typeof` дає `string`, а `+ 1` склеює
рядки й дає `41.51`. Лише виклик `Number` дає справжнє число. Отже, коли вам потрібне число, викликайте перетворення,
а запису `as` не вірте.

**«Можна написати `x instanceof Product`, де `Product` — це `type`».**

Файл `instanceof.ts`:

```ts
type Product = { name: string };

function isProduct(x: unknown): boolean {
  return x instanceof Product; // Product тут є лише типом
}

console.log(isProduct({ name: "Чай" }));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false instanceof.ts
instanceof.ts(4,23): error TS2693: 'Product' only refers to a type, but is being used as a value here.
$ node instanceof.ts
ReferenceError: Product is not defined
```

Компілятор каже, що `Product` є лише типом. Запуск показує те саме з іншого боку: `node` стер опис типу, і назви
`Product` у програмі не лишилося. Під час роботи типів немає, тому перевіряти можна лише значення.

**«`any` зручний, бо не заважає працювати».** Він не заважає лише компілятору. Помилка нікуди не зникає, а переїжджає
до людини, яка користується програмою.

## Як це проявиться в React

У фазі 1 компоненти отримують дані через **пропси**, тобто вхідні параметри компонента, а значення між показами екрана
зберігають через **стан**. Обидва описують типами. Запускати файл нижче зараз не треба, бо React з'явиться пізніше.
Його можна лише перевірити компілятором, і для цього вистачить двох речей.

Перша — пакет `@types/react`. Сам React написано на JavaScript, і типи для нього описано окремо, у пакеті з назвою
`@types/react`. Коли код пише `import { useState } from "react"`, компілятор шукає опис типів цього пакета, зокрема в
теці `node_modules/@types`. Встановлюють його так само, як компілятор: `npm i -D @types/react`. Приклад перевірено з
версією 19.3.0. Сам пакет `react` для перевірки типів не потрібен, бо компілятор нічого не запускає.

Друга — прапорець `--jsx react-jsx`. Файл `.tsx` містить розмітку JSX, знайому з лекцій днів 1–3. Без цього
прапорця компілятор на кожен тег у файлі нижче відповідає `Cannot use JSX unless the '--jsx' flag is provided`,
тобто «JSX не можна вживати без прапорця `--jsx`». Значення `react-jsx` каже, що JSX призначено для React.

Код нижче містить три навмисні помилки. Компонент `Badge` приймає пропси `label` і `count`. Запис
`function Badge({ label, count = 0 }: BadgeProps)` означає, що функція отримує один об'єкт пропсів типу `BadgeProps`
і відразу розкладає його на змінні `label` і `count`, а `count` отримує `0`, якщо поля немає (розкладання об'єкта на
змінні пояснено в лекції дня 2, розділ «Об'єкти без мутацій»). Компонент `Upload` зберігає в стані розрізнюване
об'єднання `UploadState`. Запис `useState<UploadState>` каже, якого типу буде стан.

Файл `upload.tsx`:

```tsx
import { useState } from "react";

type BadgeProps = { label: string; count?: number };

function Badge({ label, count = 0 }: BadgeProps) {
  return <span>{label}: {count}</span>;
}

export const wrong = <Badge label={5} />;

type UploadState =
  | { stage: "idle" }
  | { stage: "sending"; percent: number };

export function Upload() {
  const [upload, setUpload] = useState<UploadState>({ stage: "idle" });

  if (upload.stage === "idle") {
    return <p>{upload.percent}%</p>;
  }
  return <button onClick={() => setUpload({ stage: "sending" })}>Ще раз</button>;
}
```

```text
$ npm i -D @types/react

added 2 packages, and audited 5 packages in 857ms

found 0 vulnerabilities
$ npx tsc --noEmit --strict --target es2022 --jsx react-jsx --pretty false upload.tsx
upload.tsx(9,29): error TS2322: Type 'number' is not assignable to type 'string'.
upload.tsx(19,23): error TS2339: Property 'percent' does not exist on type '{ stage: "idle"; }'.
upload.tsx(21,43): error TS2345: Argument of type '{ stage: "sending"; }' is not assignable to parameter of type 'SetStateAction<UploadState>'.
  Type '{ stage: "sending"; }' is not assignable to type '((prevState: UploadState) => UploadState) | { stage: "sending"; percent: number; }'.
    Property 'percent' is missing in type '{ stage: "sending"; }' but required in type '{ stage: "sending"; percent: number; }'.
```

Кожне повідомлення пояснюється тим, що ви вже знаєте:

- `label={5}` на рядку 9 — це звичайна помилка присвоєння, бо пропси компонента перевіряються так само, як поля
  об'єкта: тип `BadgeProps` обіцяє в `label` рядок, а передано число.
- `upload.percent` у гілці `idle` на рядку 19 — це звуження за полем `stage`. Прочитати поле, якого в цьому варіанті
  немає, компілятор не дасть. Пункт «Перевірити себе» в плані цього дня чекає такої самої помилки, коли код
  звертається до `data` у гілці `loading`.
- `SetStateAction<UploadState>` на рядку 21 означає просту річ: функція зміни стану приймає нове значення або функцію,
  яка його обчислює з попереднього. Тому другий рядок повідомлення перелічує, що тут підійшло б: функцію або об'єкт
  варіанта `sending`. Останнє повідомлення читайте з найглибшого рядка: там названо поле `percent`, якого бракує.

Документація React на сторінці Using TypeScript, у розділі про `useState`, радить саме таку побудову для стану запиту:
об'єднання варіантів зі спільним полем. Кутові дужки в
`useState<UploadState>` пояснить завтрашня лекція.

Побачивши рядок `error TS…`, читайте його як розбіжність двох типів. Помилка самого React виглядає інакше: вона
виникає під час роботи й видна в консолі браузера.

## Перевірте себе

Спершу дайте відповідь самі, уголос або письмово, і лише потім розгортайте пояснення.

**1. `tsc` надрукував помилку, а `node` той самий файл запустив і вивів результат. Хто з них неправий?**

<details><summary>Відповідь</summary>

Обидва праві, бо роблять різну роботу. `tsc` до запуску порівнює значення з типами й знайшов розбіжність. `node` типи
викидає й просто виконує JavaScript. Висновок про типи можна робити лише за виводом `tsc`.

</details>

**2. Значення `x` має тип `number | null`. Який тип у кожній гілці `if (x) { ... } else { ... }` і куди потрапить
`0`?**

<details><summary>Відповідь</summary>

У першій гілці `x` має тип `number`. У другій гілці тип лишається `number | null`, бо хибним може бути і `null`, і
число `0`. Значення `0` потрапить у другу гілку разом із `null`. Щоб їх розрізнити, потрібна умова `x !== null`.

</details>

**3. Чому варіанти доставки не описують одним об'єктом із необов'язковими полями? Назвіть дві причини.**

<details><summary>Відповідь</summary>

Перша: компілятор не знає зв'язку між етапом і полем, тому навіть після перевірки етапу вимагатиме доводити наявність
кур'єра. Друга: спільний об'єкт дозволяє записати неможливі стани, наприклад етап пакування з підписом отримувача.

</details>

**4. Сервер надіслав `{"value": "41.5"}`. Що буде у випадку `JSON.parse(text) as Rate`, а що у випадку перевірки
значення як `unknown`?**

<details><summary>Відповідь</summary>

З `as` компілятор мовчить, бо `as` лише наказує вважати значення типом `Rate` і нічого не перевіряє. Помилка виникне
аж при першому використанні: `rate.value.toFixed` не буде функцією. З `unknown` перевірка відхилить дані й кине
зрозумілу помилку там, де дані зайшли в програму.

</details>

**5. Чому після `"currency" in data` не можна одразу написати `data.currency.toUpperCase()`?**

<details><summary>Відповідь</summary>

Оператор `in` довів лише, що поле існує. Тип значення в ньому лишився `unknown`. Потрібна ще перевірка
`typeof data.currency === "string"`, і лише після неї компілятор дозволить методи рядка.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| тип | опис того, яке значення може бути в цьому місці коду |
| компілятор, `tsc` | програма, яка до запуску порівнює код із типами |
| анотація | запис типу після назви змінної чи параметра, наприклад `order: Order` |
| виведення типу | компілятор сам визначає тип за значенням, як у `let price = 80` |
| стирання типів | під час запуску типи викидаються, і програма про них нічого не знає |
| структурна типізація | значення підходить до типу за набором полів, а не за назвою типу |
| об'єктний літерал | об'єкт, записаний прямо в коді у фігурних дужках |
| перевірка зайвих полів | компілятор відхиляє поле об'єктного літерала, якого немає в очікуваному типі |
| літеральний тип | тип з одного значення, наприклад `"packing"` |
| об'єднання (union) | тип `A \| B`, тобто значення або одного типу, або іншого |
| звуження (narrowing) | перевірка в коді робить тип вужчим усередині гілки |
| розрізнюване об'єднання | варіанти зі спільним полем, у кожному з яких це поле має свій літерал |
| `never` | тип, якому не належить жодне значення |
| `any` | вимикає перевірку для значення |
| `unknown` | значення невідоме, і нічого не можна зробити до перевірки |
| твердження типу, `as` | наказ компілятору вважати значення певним типом, без перевірки |
