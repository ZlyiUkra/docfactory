# Лекція. День 10. TypeScript: дженерики

Ця лекція пояснює, як написати одну функцію чи один тип для багатьох типів даних, не втрачаючи перевірки. Вона
спирається на вчорашню лекцію: типи, об'єднання, звуження, `unknown` і `as`. Читання займе близько 40 хвилин. Вивід
кожної команди наведено таким, яким він був насправді. Лише коли програма падає, Node друкує ще шлях до файла, рядок
коду з позначкою місця й перелік викликів, і ці рядки тут пропущено.

Команди запускайте в теці проєкту, де вчора встановлено пакет `typescript`: без нього `npx tsc` не знайде компілятора.
Як його встановити, що означає кожен прапорець команди `npx tsc` і чому файл `.ts` можна просто подати команді `node`,
пояснює лекція дня 9, розділи «Що додає TypeScript» і «Перевірка й запуск — дві окремі дії». Там само пояснено помилку
`TS5112`: її друкує компілятор, коли в теці лежить файл налаштувань `tsconfig.json`, а команда називає окремий файл.
Якщо такий файл у вас є, додавайте до кожної команди цієї лекції прапорець `--ignoreConfig`.

**Після лекції ви зможете пояснити:**

- яку проблему розв'язує параметр типу і чому кажуть, що він зв'язує вхід із виходом;
- як компілятор добирає параметр типу і коли його треба вказати самому;
- що роблять обмеження `extends`, оператор `keyof` і запис `T[K]`;
- як `Partial`, `Pick`, `Omit` і `Record` будують нові типи зі старих і де вони мовчки підводять;
- коли дженерик не потрібен і чому функція `parse<T>` нічого не гарантує;
- чому `useState(null)` у React не приймає нічого, крім `null`.

## Проблема: одна дія, багато типів

У магазині часто потрібен останній елемент списку: остання ціна, остання назва товару, останнє замовлення. Дія завжди
однакова, а тип елементів різний. Спробуємо записати це тим, що вже знаємо.

Файл `last-bad.ts`:

```ts
function lastNumber(list: number[]): number | undefined {
  return list[list.length - 1];
}
function lastAny(list: any[]): any {
  return list[list.length - 1];
}
function lastUnknown(list: unknown[]): unknown {
  return list[list.length - 1];
}

const a = lastNumber(["Чай"]);

const b = lastAny(["Чай"]);
console.log(b.toFixed(2));

const c = lastUnknown(["Чай"]);
console.log(c.toUpperCase());
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false last-bad.ts
last-bad.ts(11,23): error TS2322: Type 'string' is not assignable to type 'number'.
last-bad.ts(17,13): error TS18046: 'c' is of type 'unknown'.
```

Запис `list[list.length - 1]` читає останній елемент масиву. Якщо масив порожній, такого елемента немає, і читання
дає `undefined`. Тому перша функція обіцяє `number | undefined`, а не просто `number`.

Компілятор знайшов дві помилки, хоча проблемних місць у файлі три. Розберемо три виклики по черзі.

Виклик `lastNumber(["Чай"])` на рядку 11 компілятор зупинив. Функція приймає лише масив чисел, а їй дали масив
рядків, і повідомлення каже: «тип `string` не можна присвоїти типу `number`». Щоб брати останній елемент списку назв,
довелося б написати другу таку саму функцію для рядків, а потім третю для замовлень.

Виклик `lastAny(["Чай"])` і рядок 14 `b.toFixed(2)` компілятор пропустив. Тип `any` вимикає перевірку значення (див.
лекцію дня 9, розділ «`any`, `unknown` і `as`: що робити з даними ззовні»). Тому компілятор не знає, що в `b` лежить
рядок, у якого немає методу `toFixed`. Запуск показує, чим це закінчується:

```text
$ node last-bad.ts
TypeError: b.toFixed is not a function
```

Програма впала на рядку 14 і до рядка 17 не дійшла. Отже, функція з `any` приймає все, але помилку переносить із
перевірки на час роботи програми.

Виклик `lastUnknown(["Чай"])` компілятор пропустив, а рядок 17 `c.toUpperCase()` відхилив. Повідомлення каже: «`c` має
тип `unknown`». Функція оголосила результат типом `unknown`, тобто «невідомо що», і компілятор уже не пов'язує цей
результат із масивом рядків, який ми передали. Тому метод рядка викликати не можна, хоча в `c` справді лежить рядок.
Довелося б спершу перевірити `typeof c === "string"`, хоча ми й так знаємо відповідь.

Підсумок трьох способів:

| Спосіб | Що добре | Що погано |
|--------|----------|-----------|
| `lastNumber` | результат точно число | для рядків доведеться написати другу таку саму функцію |
| `lastAny` | приймає все | перевірку вимкнено: `b.toFixed(2)` пройшов компілятор і впаде під час роботи |
| `lastUnknown` | приймає все й нічого не обіцяє | у масиві були рядки, а на виході компілятор цього вже не знає |

Бракує способу сказати: «тип результату такий самий, як тип елементів, які мені дали, хоч би яким він був».

## Параметр типу

Для цього існує **параметр типу**. Звичайний параметр функції стоїть замість значення, яке передадуть під час виклику.
Параметр типу стоїть замість типу, який компілятор підставить для кожного виклику. Функції й типи з таким параметром
називають **дженериками** (generics, узагальнені типи).

Файл `last.ts`:

```ts
function last<T>(list: T[]): T | undefined {
  return list[list.length - 1];
}

const price = last([80, 150, 42]);
const word = last(["Чай", "Кава"]);

console.log(price?.toFixed(2));
console.log(word?.toUpperCase());
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false last.ts
(tsc нічого не надрукував: помилок немає)
$ node last.ts
42.00
КАВА
```

Рядок за рядком:

- `<T>` після назви функції оголошує параметр типу. Назва довільна. Часто пишуть одну літеру, а посібник TypeScript
  пише `Type`.
- `list: T[]` каже, що параметр є масивом елементів типу `T`.
- `: T | undefined` каже, що результат має той самий тип `T`, а масив може бути порожнім.
- `last([80, 150, 42])`: компілятор бачить масив чисел і підставляє `T = number`. Тому `price` має тип `number |
  undefined`, і метод `toFixed` дозволено.
- `last(["Чай", "Кава"])`: той самий код, але тепер `T = string`. Рядок `word?.toFixed(2)` компілятор відхилив би з
  повідомленням `Property 'toFixed' does not exist on type 'string'`, тобто «тип `string` не має методу
  `toFixed`».
- Запис `?.` знайомий з лекції дня 2, розділ «Як це проявиться в React». Він викликає метод, лише якщо значення не
  дорівнює `undefined` чи `null`, а інакше весь вираз дає `undefined`. Тут він потрібен, бо тип результату містить
  `undefined`, і без `?.` компілятор не дозволив би викликати метод.

Запис `T` зустрічається і у вході, і у виході. Саме це мають на увазі, коли кажуть, що параметр типу **зв'язує вхід із
виходом**. Без цього зв'язку параметр нічого не дає, і до цього ми ще повернемося.

Як і решта типів, `T` існує лише для компілятора. Під час запуску `node` стирає `<T>` разом з іншими типами (див.
лекцію дня 9, розділ «Перевірка й запуск — дві окремі дії») і виконує одну звичайну функцію. Окремих версій для чисел
і рядків не створюється, тому під час роботи `T` дізнатися неможливо.

## Як компілятор добирає `T`

Зазвичай `T` не пишуть, бо компілятор визначає його з аргументів. Ось що він робить у різних випадках. Файл навмисно
містить помилки, щоб побачити результат.

Файл `infer.ts`:

```ts
function last<T>(list: T[]): T | undefined { return list[list.length - 1]; }
function same<T>(a: T, b: T): T[] { return [a, b]; }
function box<T>(value: T) { return { value }; }
function empty<T>(): T[] { return []; }

const mixed: number = last([1, "два"]);
const pair = same(1, "два");
const pairOk = same<number | string>(1, "два");

const none: string = last([]);
const unknownList: string = empty();

let nothing = box(null);
nothing = box(5);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false infer.ts
infer.ts(6,7): error TS2322: Type 'string | number | undefined' is not assignable to type 'number'.
  Type 'undefined' is not assignable to type 'number'.
infer.ts(7,22): error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
infer.ts(10,7): error TS2322: Type 'undefined' is not assignable to type 'string'.
infer.ts(11,7): error TS2322: Type 'unknown[]' is not assignable to type 'string'.
infer.ts(14,1): error TS2322: Type '{ value: number; }' is not assignable to type '{ value: null; }'.
  Types of property 'value' are incompatible.
    Type 'number' is not assignable to type 'null'.
```

Розберемо повідомлення в тому порядку, в якому їх надрукував компілятор.

**Рядок 6, `last([1, "два"])`.** Спершу компілятор визначає тип самого масиву `[1, "два"]`. У масиві є число й рядок,
тому кожен його елемент має тип `string | number`. Параметр функції має тип `T[]`, отже `T` дорівнює типу елемента,
тобто `string | number`. Функція повертає `T | undefined`, і результат має тип `string | number | undefined`. Змінна
`mixed` обіцяє число, тому повідомлення каже, що такий результат туди не підходить. Рядок із відступом називає одну з
причин: `undefined` теж не є числом.

**Рядок 7, `same(1, "два")`.** Тут два окремі аргументи, і кожен із них пропонує свій варіант `T`. Перший аргумент
пропонує `number`, другий пропонує `string`. Об'єднання з двох варіантів компілятор сам не будує: якщо функція має
приймати і числа, і рядки, про це треба сказати явно, як на рядку 8. Він вибирає `number`, тип першого аргументу, і
тоді другий аргумент `"два"` уже не підходить. Тому повідомлення стоїть біля другого аргументу: «аргумент типу
`string` не можна передати в параметр типу `number`». Посібник TypeScript показує такий самий випадок на функції
`combine` у розділі Specifying Type Arguments сторінки More on Functions.

**Рядок 8, `same<number | string>(1, "два")`, помилки не дав.** Тип у кутових дужках у самому виклику задає `T` явно.
Такий тип називають **аргументом типу**, так само як значення в круглих дужках називають аргументом. Коли аргумент
типу вказано, компілятор нічого не виводить, а лише перевіряє, що `1` і `"два"` підходять до `number | string`.

**Рядок 10, `last([])`.** У порожньому масиві немає жодного елемента, тому компілятор дає йому тип `never[]`, тобто
«масив, у якому не може бути жодного значення». Тип `never` пояснено в лекції дня 9, розділ «Розрізнюване об'єднання:
варіанти зі спільним полем». Отже, `T = never`, і функція повертає `never | undefined`. Варіант `never` не містить
жодного значення, тому до об'єднання він нічого не додає, і лишається просто `undefined`. Саме цей тип компілятор і
назвав у повідомленні.

**Рядок 11, `empty()`.** Аргументів немає, тому з них `T` не вивести. Тоді компілятор дивиться ще в одне місце: на тип
змінної, у яку покладуть результат. Змінна обіцяє `string`, а функція повертає масив `T[]`, і жоден `T` не зробить
масив рядком. Компілятор не знайшов жодної підказки й підставив `T = unknown`. Тому повідомлення каже, що `unknown[]`
не можна покласти в `string`.

**Рядки 13 і 14, `box(null)`.** Рядок 13 пройшов: компілятор побачив `null` і підставив `T = null`, тому змінна
`nothing` отримала тип `{ value: null }`. Рядок 14 кладе в неї `{ value: 5 }`, і компілятор відповідає, що
`{ value: number; }` не підходить до `{ value: null; }`. Рядки з відступом читайте з найглибшого (див. лекцію дня 9,
кінець розділу «`any`, `unknown` і `as`: що робити з даними ззовні»): поле `value` має тип `number`, а тип `null` не
приймає чисел. Компілятор бере тип того значення, яке бачить, бо про ваші наміри він нічого не знає.

Тепер про підказку з типу змінної, яку компілятор шукав на рядку 11. Якщо змінна обіцяє масив, підказка спрацьовує.

Файл `infer-context.ts`:

```ts
function empty<T>(): T[] {
  return [];
}

// Аргументів немає, але змінна обіцяє масив рядків.
const names: string[] = empty();
names.push("Чай");
names.push(5);
console.log(names);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false infer-context.ts
infer-context.ts(8,12): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
$ node infer-context.ts
[ 'Чай', 5 ]
```

Анотація `string[]` має ту саму форму, що й `T[]`, тому компілятор підставив `T = string` без кутових дужок. Число на
рядку 8 він відхилив, бо масив `names` обіцяє лише рядки. Запуск надрукував `[ 'Чай', 5 ]`: під час роботи типів
немає, і `push` поклав число в масив. Отже, `T` компілятор бере з аргументів, а коли аргументів немає, з типу місця, у
яке йде результат. Якщо немає ні того, ні іншого, виходить `unknown`.

Підсумок цих випадків:

| Виклик | Яким став `T` | Чому |
|--------|---------------|------|
| `last([1, "два"])` | `string \| number` | `T` дорівнює типу елемента масиву |
| `same(1, "два")` | `number`, і другий аргумент не підходить | кожен аргумент дає свій варіант, і об'єднання компілятор сам не будує |
| `same<number \| string>(1, "два")` | `number \| string` | аргумент типу вказано явно в кутових дужках |
| `last([])` | `never` | у порожньому масиві елементів немає, тому результат дорівнює просто `undefined` |
| `empty()` у змінну `string` | `unknown` | ні аргументів, ні підходящого типу змінної |
| `empty()` у змінну `string[]` | `string` | тип узято з анотації змінної |
| `box(null)` | `null` | компілятор бере те, що бачить, і не знає ваших намірів |

Випадок `box(null)` найважливіший для React. Значення `null` часто означає «поки що нічого», а згодом там з'явиться
об'єкт. Компілятор цього передбачити не може, тому такий випадок вимагає явного аргументу типу. Наприклад, якщо
`Product` означає тип товару `{ id: number; name: string }`, пишуть `box<Product | null>(null)`.

**Вказувати аргументи типу треба для всіх параметрів одразу.** Якщо параметрів типу два, а в дужках указано один,
компілятор не виведе другий сам. Часткового виведення немає. Перевіримо це на функції з двома параметрами типу.

Файл `partial-args.ts`:

```ts
function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

// Указано лише A, а B компілятор мав би добрати сам.
const wrong = pair<number>(1, "два");
// Указано обидва параметри, тому помилки немає.
const right = pair<number, string>(1, "два");
// Не вказано жодного, тому компілятор добирає обидва.
const inferred = pair(1, "два");
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false partial-args.ts
partial-args.ts(6,20): error TS2558: Expected 2 type arguments, but got 1.
```

Тип результату `[A, B]` описує масив рівно з двох елементів: перший має тип `A`, а другий тип `B`. Такий тип
називають **кортежем** (tuple). Він знадобиться в розділі про React, бо `useState` повертає саме кортеж.

Повідомлення перекладається так: «очікувалося 2 аргументи типу, а отримано 1». Компілятор поскаржився лише на рядок
зі змінною `wrong`, бо там указано один параметр із двох. На практиці є два робочі записи: або вкажіть усі параметри,
або не вказуйте жодного й дайте компілятору добрати їх з аргументів.

## Обмеження: `extends`

Усередині функції `T` може виявитися будь-чим, тому компілятор дозволяє лише те, що законно для будь-якого типу.
Припустімо, що треба вибрати з двох значень довше.

Файл `longer.ts`:

```ts
function size<T>(value: T): number {
  return value.length;
}

function longer<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

const text: string = longer("чай", "кава");
const list: number[] = longer([1, 2], [3]);
longer(5, 6);

function longerPlain(a: { length: number }, b: { length: number }) {
  return a.length >= b.length ? a : b;
}
longerPlain("чай", "кава").toUpperCase();
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false longer.ts
longer.ts(2,16): error TS2339: Property 'length' does not exist on type 'T'.
longer.ts(11,8): error TS2345: Argument of type 'number' is not assignable to parameter of type '{ length: number; }'.
longer.ts(16,28): error TS2339: Property 'toUpperCase' does not exist on type '{ length: number; }'.
```

Перше повідомлення стосується функції `size` на рядку 2: «поля `length` немає в типі `T`». Функцію `size` можна
викликати з будь-яким значенням, зокрема з числом, а в числа поля `length` немає. Компілятор перевіряє тіло функції
один раз для всіх можливих `T`, тому не дозволяє читати поле, якого може не бути.

Функція `longer` пояснює компілятору, які `T` вона приймає. Запис `T extends { length: number }` називається
**обмеженням**. Він каже, що `T` може бути будь-яким типом, у якому є числове поле `length`. У JavaScript слово
`extends` пишуть ще в класах, коли один клас будують на основі іншого. Тут воно має інший зміст: «підходить під такий
опис».

Обмеження дає дві речі. Перша: усередині функції стало законним `a.length`, бо кожен дозволений `T` має це поле.
Друга: під час виклику компілятор перевіряє аргументи. Рядки й масиви мають поле `length`, тому виклики на рядках 9 і
10 пройшли, а на рядку 11 компілятор відповів, що число не підходить під опис `{ length: number; }`.

Останній приклад показує, чому не можна просто написати тип параметра `{ length: number }`. Функція `longerPlain`
приймає те саме, що й `longer`, але її результат має тип `{ length: number }`. Компілятор знає про результат лише
поле `length`, тому на рядку 16 відповідає, що методу `toUpperCase` у такого типу немає. Обмеження перевіряє тип, але
не підміняє його описом: `longer("чай", "кава")` має тип `string`, бо `T = string`, а `longer([1, 2], [3])` має тип
`number[]`.

## `keyof` і `T[K]`: доступ за назвою поля

Тепер припустімо, що треба витягти один стовпець зі списку товарів: усі ціни або всі назви. Для цього потрібні два
оператори типів.

**`keyof`** бере об'єктний тип і дає об'єднання назв його полів. Кожна назва в ньому є літеральним типом з лекції
дня 9, розділ «Розрізнюване об'єднання: варіанти зі спільним полем». Для `type Product = { id: number; name: string;
price: number }` запис `keyof Product` означає `"id" | "name" | "price"`.

**`T[K]`** означає тип поля `K` в типі `T`. Цей запис називають **індексованим доступом**. `Product["price"]` дорівнює
`number`, а `Product["name"]` дорівнює `string`. Запис `T[K][]` у функції нижче читається зліва направо: спершу
`T[K]`, тип одного поля, а потім `[]`, масив значень цього типу.

Файл `pluck.ts`:

```ts
type Product = { id: number; name: string; price: number };

function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}

const shelf: Product[] = [
  { id: 1, name: "Чай", price: 80 },
  { id: 2, name: "Кава", price: 150 },
];

const prices = pluck(shelf, "price");
const names = pluck(shelf, "name");
console.log(prices, names);
console.log(prices.reduce((sum, price) => sum + price, 0));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false pluck.ts
(tsc нічого не надрукував: помилок немає)
$ node pluck.ts
[ 80, 150 ] [ 'Чай', 'Кава' ]
230
```

Простежимо, як компілятор обробляє виклик `pluck(shelf, "price")`. Спершу він дивиться на перший аргумент. Змінна
`shelf` має тип `Product[]`, а параметр `items` має тип `T[]`, тому `T = Product`. Тепер обмеження
`K extends keyof T` означає `K extends keyof Product`, тобто `K` може бути лише `"id"`, `"name"` або `"price"`. Далі
компілятор дивиться на другий аргумент, рядок `"price"`. Він підставляє `K = "price"` і перевіряє, що цей літерал
підходить під обмеження. Нарешті компілятор обчислює тип результату `T[K][]`: це `Product["price"][]`, тобто
`number[]`.

Тому на наступних рядках змінна `prices` має тип `number[]`. У виклику `prices.reduce` компілятор знає, що `sum` і
`price` є числами, і додавання перевіряє як додавання чисел. Для `pluck(shelf, "name")` ті самі кроки дають
`K = "name"` і результат `string[]`. Метод `reduce` пояснено в лекції дня 2, розділ «`reduce`: згорнути масив в одне
значення».

Файл нижче показує, що цей опис забороняє.

Файл `pluck-errors.ts`:

```ts
type Product = { id: number; name: string; price: number };

function pluck<T, K extends keyof T>(items: T[], key: K): T[K][] {
  return items.map((item) => item[key]);
}
function pluckLoose<T>(items: T[], key: keyof T) {
  return items.map((item) => item[key]);
}

const shelf: Product[] = [{ id: 1, name: "Чай", price: 80 }];

pluck(shelf, "prise");
const wrong: string[] = pluck(shelf, "price");
const loose: number[] = pluckLoose(shelf, "price");

for (const key of Object.keys(shelf[0])) {
  console.log(shelf[0][key]);
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false pluck-errors.ts
pluck-errors.ts(12,14): error TS2345: Argument of type '"prise"' is not assignable to parameter of type 'keyof Product'.
pluck-errors.ts(13,7): error TS2322: Type 'number[]' is not assignable to type 'string[]'.
  Type 'number' is not assignable to type 'string'.
pluck-errors.ts(14,7): error TS2322: Type '(string | number)[]' is not assignable to type 'number[]'.
  Type 'string | number' is not assignable to type 'number'.
    Type 'string' is not assignable to type 'number'.
pluck-errors.ts(17,15): error TS7053: Element implicitly has an 'any' type because expression of type 'string' can't be used to index type 'Product'.
  No index signature with a parameter of type 'string' was found on type 'Product'.
```

Перші два повідомлення очікувані. На рядку 12 компілятор каже, що літерал `"prise"` не підходить до `keyof Product`:
описку в назві поля зупинено. На рядку 13 він каже, що `number[]` не можна покласти в змінну типу `string[]`: тип
результату точний, і компілятор знає, що ціни є числами. Два інші повідомлення варто розібрати докладніше.

**Навіщо окремий параметр `K`.** Функція `pluckLoose` обходиться без нього, і `key: keyof T` теж не пропустить описку.
Проте тепер тип ключа дорівнює всьому об'єднанню `"id" | "name" | "price"`, і компілятор не знає, яке саме поле
передали. Тому `item[key]` може бути значенням будь-якого з трьох полів, тобто числом або рядком, і результат має тип
`(string | number)[]`. На рядку 14 компілятор відповідає, що такий масив не можна покласти в змінну типу `number[]`.
Саме окремий параметр `K` запам'ятовує, яке поле передали.

**Чому `Object.keys` дає помилку.** Функція `Object.keys` (див. лекцію дня 2, розділ «Масив — це теж об'єкт»)
повертає масив назв полів, і TypeScript описує її результат як `string[]`, а не як `(keyof T)[]`. Тому `key` має тип
`string`, і на рядку 17 компілятор не дозволяє читати `shelf[0][key]`.

Повідомлення каже: «елемент неявно має тип `any`, бо вираз типу `string` не можна вживати як ключ до типу `Product`».
Слово «неявно» тут те саме, що в повідомленні `TS7006` з лекції дня 9, розділ «Як записують типи»: компілятор не може
визначити тип і попереджає, що без перевірки вийшов би `any`. Рядок із відступом згадує **індексну сигнатуру** (index
signature). Так називають запис у типі, який дозволяє будь-яку назву поля певного виду, наприклад `{ [key: string]:
number }`, тобто «за будь-яким рядковим ключем лежить число». У типі `Product` такого запису немає, там описано лише
три конкретні поля, тому довільний рядок не годиться як ключ.

Чому TypeScript не обіцяє, що `Object.keys` поверне лише `"id"`, `"name"` і `"price"`? Причина у структурній типізації
з лекції дня 9, розділ «Як записують типи»: значення підходить до типу, якщо в ньому є потрібні поля, а зайві поля не
заважають.

Файл `keys.ts`:

```ts
type Product = { id: number; name: string; price: number };

const fromForm = { id: 1, name: "Чай", price: 80, comment: "Без цукру" };
const tea: Product = fromForm;

console.log(Object.keys(tea));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false keys.ts
(tsc нічого не надрукував: помилок немає)
$ node keys.ts
[ 'id', 'name', 'price', 'comment' ]
```

Компілятор пропустив `tea: Product`, бо в `fromForm` є всі три поля товару. Проте `Object.keys(tea)` повернув і
четверту назву, `comment`, якої тип `Product` не описує. Отже, якби TypeScript обіцяв для `Object.keys` лише ключі
типу, ця обіцянка була б неправдою.

## Узагальнені типи

Параметр типу може мати не лише функція, а й тип. Ви вже бачили такі типи: `number[]` є скороченням для
`Array<number>`, а `Promise<string>` означає проміс, який дасть рядок. У лекції дня 9 опис методу `json()` мав вигляд
`json(): Promise<any>`. Тепер його можна прочитати точно: `Promise` є узагальненим типом із параметром, а `any` є
аргументом типу, який підставлено замість параметра. Так само `Record<"currency", unknown>` з повідомлень компілятора
в тій лекції є узагальненим типом із двома аргументами, і про `Record` йдеться нижче, у розділі «Службові типи».

Опишемо стек дій для кнопки «Скасувати». **Стеком** називають список, з якого першим забирають елемент, доданий
останнім.

Файл `stack.ts`:

```ts
interface Stack<T> {
  push(item: T): void;
  pop(): T | undefined;
  size(): number;
}

function createStack<T>(): Stack<T> {
  const items: T[] = [];
  return {
    push(item) { items.push(item); },
    pop() { return items.pop(); },
    size() { return items.length; },
  };
}

const undo = createStack<string>();
undo.push("Додано товар");
undo.push("Змінено ціну");
console.log(undo.pop(), undo.size());
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false stack.ts
(tsc нічого не надрукував: помилок немає)
$ node stack.ts
Змінено ціну 1
```

Рядок за рядком:

- `interface Stack<T>` оголошує параметр на всьому типі, тому всі методи говорять про той самий `T`. Написати `Stack`
  без аргументу не можна: компілятор відповість `Generic type 'Stack<T>' requires 1 type argument(s)`, тобто
  «узагальнений тип `Stack<T>` вимагає 1 аргумент типу».
- `push(item: T): void` описує метод, який приймає елемент і нічого не повертає. Тип `void` означає саме це: «функція
  не повертає значення».
- `createStack<T>(): Stack<T>` не має аргументів, тому з аргументів `T` не вивести. Тому виклик пише
  `createStack<string>()` явно. Без цього й без анотації змінної вийшов би `Stack<unknown>`, як у функції `empty` з
  розділу «Як компілятор добирає `T`».
- Масив `items` створено всередині `createStack`, і три методи об'єкта працюють з ним навіть після того, як
  `createStack` завершилася. Це замикання з лекції дня 3, розділ «Кілька функцій на одне оточення: гаманець».
- Об'єкт із методами не повторює типів `item`, бо компілятор бере їх з `Stack<T>`, указаного як тип результату.
- Вивід `Змінено ціну 1` містить два значення: `undo.pop()` забрав і повернув останній доданий запис, а `undo.size()`
  після цього показав, що в стеку лишився один запис.

Перевірмо дві помилки, про які щойно йшлося. Допишіть у кінець файлу `stack.ts` такі рядки:

```ts
// Тип Stack записано без аргументу.
const noArgument: Stack = createStack<string>();

// Виклик без кутових дужок: аргументів немає, тому T нема звідки взяти.
const noType = createStack();
const item: string | undefined = noType.pop();
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false stack.ts
stack.ts(21,19): error TS2314: Generic type 'Stack<T>' requires 1 type argument(s).
stack.ts(25,7): error TS2322: Type 'unknown' is not assignable to type 'string | undefined'.
```

Перше повідомлення стосується запису `Stack` без аргументу. Друге показує, що `noType.pop()` повертає `unknown`, тобто
компілятор підставив `T = unknown`. Отже, коли функція не має аргументів, з яких можна вивести `T`, пишіть тип у
кутових дужках самі або анотуйте змінну, наприклад `const names: Stack<string> = createStack()`. Інакше результат
доведеться перевіряти перед кожним вживанням.

Параметр можна поставити й в об'єднанні з учорашньої лекції. Запис `type Loaded<T> = { status: "ok"; value: T } | {
status: "fail"; reason: string }` описує результат будь-якого завантаження, а `Loaded<number>` і `Loaded<Product[]>`
підставляють конкретний тип.

## Службові типи

TypeScript має вбудовані дженерики, які будують новий тип зі старого. Їх називають **службовими типами** (utility
types). Візьмемо товар.

```ts
type Product = { id: number; name: string; price: number; description: string };
```

| Запис | Що вийде | Для чого |
|-------|----------|----------|
| `Partial<Product>` | усі поля необов'язкові | часткове оновлення |
| `Readonly<Product>` | поля не можна переприсвоїти | значення, яке не можна змінювати |
| `Pick<Product, "name" \| "price">` | лише `name` і `price` | картка товару |
| `Omit<Product, "id">` | усі поля, крім `id` | новий товар, якому сервер ще не дав `id` |
| `Record<"low" \| "high", string>` | об'єкт із ключами `low` і `high`, значення рядки | таблиця підписів |

Їх можна вкладати, і читати такий запис треба зсередини назовні. `Partial<Pick<Product, "name" | "price">>` спершу
лишає два поля, а потім робить їх необов'язковими.

Усередині це звичайні дженерики. Їх оголошено у вбудованому файлі `lib.es5.d.ts`, про який ішлося в лекції дня 9,
розділ «`any`, `unknown` і `as`: що робити з даними ззовні». Ось три оголошення звідти:

```ts
// lib.es5.d.ts, TypeScript 7.0.2
type Partial<T> = {
    [P in keyof T]?: T[P];
};

type Pick<T, K extends keyof T> = {
    [P in K]: T[P];
};

type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

Запис `[P in keyof T]` перебирає назви полів із `keyof T` по одній і для кожної назви `P` створює поле. Тип,
побудований так, називають **зіставленим типом** (mapped type). У `Partial` кожне поле дістає знак `?`, тобто стає
необов'язковим (знак `?` пояснено в лекції дня 9, розділ «Як записують типи»), і зберігає свій тип `T[P]`. `Pick`
перебирає не всі назви, а лише ті, що передали в `K`, і обмеження `K extends keyof T` дозволяє передати тільки
справжні назви полів.

`Omit` має інше обмеження: `K extends keyof any`. Запис `keyof any` означає будь-яку можливу назву поля, тобто рядок,
число або `symbol` (`symbol` є особливим видом значень JavaScript, який теж може бути назвою поля; у цьому плані він
не знадобиться). Отже, `Omit` приймає будь-який рядок, навіть якщо такого поля в `T` немає. Службовий тип `Exclude`
прибирає з об'єднання `keyof T` ті назви, що є в `K`, і `Pick` бере решту полів.

Службові типи мають чотири тихі пастки. Перевіримо їх.

Файл `traps.ts`:

```ts
type Product = { id: number; name: string; price: number };

const typoOmit: Omit<Product, "prise"> = { id: 1, name: "Чай", price: 80 };
const typoPick: Pick<Product, "prise"> = { prise: 1 };

const tea: Product = { id: 1, name: "Чай", price: 80 };
const patch: Partial<Product> = { price: undefined };
const updated: Product = { ...tea, ...patch };
console.log(updated.price);

const prices: Record<string, number> = { tea: 80 };
const coffee: number = prices.coffee;
console.log(coffee);

const frozen: Readonly<Product> = { ...tea };
frozen.price = 100;
console.log(frozen.price);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false traps.ts
traps.ts(4,31): error TS2344: Type '"prise"' does not satisfy the constraint 'keyof Product'.
traps.ts(16,8): error TS2540: Cannot assign to 'price' because it is a read-only property.
$ node traps.ts
undefined
undefined
100
```

- `Omit` не перевіряє назв. Його другий параметр обмежено записом `keyof any`, а не `keyof T`, тому описка `"prise"` у
  третьому рядку пройшла й нічого не прибрала. `Pick` у наступному рядку таку описку зупинив: повідомлення
  `TS2344` каже, що `"prise"` «не задовольняє обмеження `keyof Product`».
- `Partial` дозволяє явне `undefined`. Знак `?` компілятор розуміє як «поля може не бути», і поле зі значенням
  `undefined` він вважає тим самим випадком. Коли три крапки (див. лекцію дня 1, розділ «Що роблять три крапки»)
  копіюють `patch` поверх `tea`, відсутнє поле нічого не змінює, і компілятор вважає, що ціна лишилася від `tea`.
  Проте поле, яке є і дорівнює `undefined`, теж копіюється й затирає ціну. Тому об'єкт `updated` за типом є `Product`,
  а ціна в ньому `undefined`, і компілятор мовчить. Це значення надрукував `console.log(updated.price)` у першому
  рядку виводу. Прапорець `--exactOptionalPropertyTypes` розрізняє ці два випадки, і з ним рядок `patch` дає помилку,
  проте `--strict` цього прапорця не вмикає.
- `Record<string, number>` дорівнює типу з індексною сигнатурою `{ [key: string]: number }` з розділу «`keyof` і
  `T[K]`: доступ за назвою поля». Він обіцяє число за будь-яким рядковим ключем, навіть за неіснуючим. Тому другий
  рядок виводу теж `undefined`: його надрукував `console.log(coffee)`. Прапорець `--noUncheckedIndexedAccess` додає
  `undefined` до типу такого читання, і тоді рядок `coffee` дає помилку, проте `--strict` і його не вмикає.
- `Readonly` існує лише для компілятора. Файл `node` запустив, і рядок із присвоєнням виконався: третій рядок виводу
  `100` є новою ціною. Заморозити об'єкт під час роботи може лише `Object.freeze` (див. лекцію дня 2, розділ
  «`Object.freeze`: як перевірити, що нічого не змінюється»).
- Крім того, `Readonly` і `Partial` діють лише на поля самого об'єкта. Якщо в полі лежить інший об'єкт, наприклад
  розміри коробки `{ size: { weight: 1 } }`, то `Readonly` забороняє замінити `size` цілком, але дозволяє змінити
  `size.weight`, а `Partial` робить необов'язковим поле `size`, але не поле `weight` усередині нього. Так само на один
  рівень діє й `Object.freeze`.

## Коли дженерик не потрібен

Посібник TypeScript дає просте правило: параметр типу виправданий, коли зв'язує принаймні два місця. Якщо він
трапляється лише раз, він нічого не зв'язує.

Візьмемо `function log<T>(value: T): void`. Параметр `T` стоїть лише в типі `value`. Функція приймає будь-яке
значення, і `value: unknown` приймає те саме. Усередині функції з `T` можна робити рівно те, що й з `unknown`, бо `T`
може виявитися будь-чим. Результат від `T` не залежить. Отже, параметр нічого не додає. Так само
`function count<T>(list: T[]): number` повертає число за будь-якого `T`, і досить написати `list: unknown[]`.

Функція `last` з початку лекції інша: `T` стоїть у типі списку й у типі результату, і саме цей зв'язок дає точний тип
`number | undefined` для масиву чисел. Посібник уточнює, що місцем вважається й тип результату, який компілятор
вивів сам. Тому функція `box<T>(value: T)` з розділу «Як компілятор добирає `T`» теж правильна: у коді `T` записано
один раз, але виведений тип результату `{ value: T }` містить його вдруге.

Підсумок:

| Запис | Чи потрібен параметр | Чому |
|-------|---------------------|------|
| `function log<T>(value: T): void` | ні | досить `value: unknown` |
| `function count<T>(list: T[]): number` | ні | досить `list: unknown[]`, бо результат не залежить від типу |
| `function last<T>(list: T[]): T \| undefined` | так | зв'язує елементи з результатом |
| `function parse<T>(text: string): T` | небезпечно | `T` є лише у виході, тому зв'язувати нема з чим |

Зайвий параметр робить код важчим для читання й не дає жодної користі. Саме це план навчання називає пасткою цього
дня. Останній рядок таблиці ще гірший, бо виглядає безпечно, хоча нічого не перевіряє.

Файл `parse.ts`:

```ts
type Rate = { currency: string; value: number };

function parse<T>(text: string): T {
  return JSON.parse(text);
}

const rate = parse<Rate>('{"currency": "EUR", "value": "41.5"}');
console.log(typeof rate.value);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false parse.ts
(tsc нічого не надрукував: помилок немає)
$ node parse.ts
string
```

Вивід `string` показує неправду в типі: за типом `Rate` поле `value` є числом, а в тексті JSON там стоїть рядок
`"41.5"`. Компілятор мовчить, бо `JSON.parse` повертає `any`, а `any` можна покласти куди завгодно. Запис
`parse<Rate>` читається як перевірка, але є тим самим твердженням `as Rate` в іншому записі (див. лекцію дня 9, розділ
«`any`, `unknown` і `as`: що робити з даними ззовні»). Функція `async function getJson<T>(url: string): Promise<T>`,
яка повертає `response.json()`, має ту саму ваду, бо `json()` теж повертає `any`. Такий запис лише записує, якого
вигляду дані ви чекаєте від сервера. Самі дані лишаються неперевіреними, доки їх не перевірить код.

Інколи `as` усередині дженерика виправданий. Компілятор не виконує цикл, тому не знає, які ключі той додасть до
об'єкта. Тип змінної він перевіряє там, де її створено, а там об'єкт ще порожній. Функція `zeros` нижче створює
таблицю лічильників, де кожен лічильник дорівнює нулю. Рядок зі змінною `plain` навмисно записано без `as`, щоб
побачити відповідь компілятора.

Обмеження `K extends string` тут потрібне ще з однієї причини. Без нього компілятор для `["low", "high"]` вивів би
`K = string`, і в типі результату не лишилося б переліку ключів. З обмеженням `extends string` він зберігає точні
літерали. Це видно з такого файла, де кожен рядок `never` навмисно неправильний, щоб компілятор назвав тип результату
(той самий прийом, що й у файлі `rate-stages.ts` лекції дня 9).

Файл `zeros-keys.ts`:

```ts
function keysLoose<K>(keys: K[]): K[] {
  return keys;
}
function keysExact<K extends string>(keys: K[]): K[] {
  return keys;
}

// Кожен рядок навмисно неправильний: повідомлення назве тип результату.
const loose: never = keysLoose(["low", "high"]);
const exact: never = keysExact(["low", "high"]);
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false zeros-keys.ts
zeros-keys.ts(9,7): error TS2322: Type 'string[]' is not assignable to type 'never'.
zeros-keys.ts(10,7): error TS2322: Type '("high" | "low")[]' is not assignable to type 'never'.
```

Без обмеження результат має тип `string[]`, а з обмеженням має тип `("high" | "low")[]`. Порядок `"high" | "low"` не
збігається з порядком у коді з тієї самої причини, що й у лекції дня 9: TypeScript 7.0 упорядковує типи за власним
сталим правилом. Тепер сама функція.

Файл `zeros.ts`:

```ts
function zeros<K extends string>(keys: K[]): Record<K, number> {
  // Без as: компілятор бачить порожній об'єкт, а не об'єкт з усіма ключами K.
  const plain: Record<K, number> = {};

  // З as: автор функції обіцяє, що цикл нижче заповнить усі ключі K.
  const result = {} as Record<K, number>;
  for (const key of keys) {
    result[key] = 0;
  }
  return result;
}

console.log(zeros(["low", "high"]));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false zeros.ts
zeros.ts(3,9): error TS2322: Type '{}' is not assignable to type 'Record<K, number>'.
$ node zeros.ts
{ low: 0, high: 0 }
```

Без `as` компілятор відповів `Type '{}' is not assignable to type 'Record<K, number>'`, і ця відповідь стосується лише
рядка зі змінною `plain`. Рядок із `as` компілятор пропустив, а `node` надрукував таблицю з усіма ключами, тобто цикл
справді виконав обіцянку. Тут обіцянку дає сам автор функції, і вона стосується коду, який він бачить, а не даних зі
світу.

## Типові хибні уявлення

**«`K extends keyof T` не пропустить чужий ключ під час роботи».** Обмеження живе лише в компіляторі. Виклик
`pluck(shelf, "prise" as "price")` компілюється, а `node` друкує `[ undefined, undefined ]`. Щоб побачити це, допишіть
у кінець файлу `pluck.ts` такий рядок:

```ts
// as змушує компілятор вважати описку "prise" правильною назвою "price".
console.log(pluck(shelf, "prise" as "price"));
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false pluck.ts
(tsc нічого не надрукував: помилок немає)
$ node pluck.ts
[ 80, 150 ] [ 'Чай', 'Кава' ]
230
[ undefined, undefined ]
```

Перші два рядки виводу надрукував старий код файлу, а останній надрукував новий рядок. Поля `prise` в об'єктах немає,
тому `item[key]` дає `undefined` для кожного з двох товарів. Отже, обмеження зупиняє описку лише доти, доки компілятор
бачить справжню назву поля. Запис `as` цю перевірку обходить.

Чому твердження `"prise" as "price"` не дало помилки `TS2352`, як `"41.5" as number` у лекції дня 9? Перевіряючи
твердження, компілятор порівнює цільовий тип не з літералом `"prise"`, а з ширшим типом `string`. Літерал `"price"` є
рядком, тому типи перетинаються, і компілятор твердження приймає. Запис `"prise" as 5` він відхилив би з повідомленням
`Conversion of type 'string' to type '5' may be a mistake`: у ньому видно, що компілятор порівнював саме `string`.

**«`Partial` дозволяє покласти в поле що завгодно».** Він дозволяє лише пропустити поле або покласти `undefined`.
Поле, яке є, зберігає свій тип, тому `{ price: "99" }` компілятор відхилить.

Файл `partial-type.ts`:

```ts
type Product = { id: number; name: string; price: number };

// Поле пропущено або дорівнює undefined: це Partial дозволяє.
const empty: Partial<Product> = {};
const cleared: Partial<Product> = { price: undefined };

// Поле є, але тип інший: це Partial не дозволяє.
const wrong: Partial<Product> = { price: "99" };
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false partial-type.ts
partial-type.ts(8,35): error TS2322: Type 'string' is not assignable to type 'number'.
```

Компілятор поскаржився лише на останній рядок. Отже, `Partial` робить поле необов'язковим, але перевірку типу поля не
вимикає: ціну рядком він у код не пропустить.

**«Чим більше параметрів типу, тим гнучкіша функція».** Гнучкість дає зв'язок між типами, а не кількість параметрів.
Посібник радить брати якомога менше параметрів.

## Як це проявиться в React

Хуки React, з якими ви працюватимете у фазі 1, є дженериками. У лекції дня 9 запис `useState<UploadState>` уже
задавав тип стану. Тепер видно, що це звичайний аргумент типу в кутових дужках. Ось як `useState` оголошено в пакеті
описів `@types/react` 19.3.0 (що це за пакет і як його встановити, пояснює лекція дня 9, розділ «Як це проявиться в
React»):

```ts
// @types/react, index.d.ts
type SetStateAction<S> = S | ((prevState: S) => S);
type Dispatch<A> = (value: A) => void;
function useState<S>(initialState: S | (() => S)): [S, Dispatch<SetStateAction<S>>];
```

Прочитаємо це знизу вгору. Функція `useState` має параметр типу `S`, тобто тип стану. Початкове значення має тип `S`
або є функцією, яка повертає `S`. Результат є кортежем із двох елементів. Перший елемент є поточним станом типу `S`.
Другий елемент має тип `Dispatch<SetStateAction<S>>`, тобто є функцією, яка приймає `SetStateAction<S>` і нічого не
повертає. А `SetStateAction<S>` означає «нове значення типу `S` або функцію, яка з попереднього стану обчислює новий»
(це пояснено й у лекції дня 9). Отже, параметр `S` зв'язує три місця: початкове значення, поточний стан і функцію
зміни. Компілятор виводить `S` з початкового значення, і саме з цього беруться всі помилки файла нижче.

Файл нижче містить шість навмисних помилок. Запускати його зараз не треба, бо React з'явиться пізніше, але перевірити
компілятором можна так само, як файл `upload.tsx` у лекції дня 9. Запис `type ReactNode` в імпорті каже, що з пакета
береться лише тип. `ReactNode` означає «будь-що, що React уміє показати»: елемент JSX, рядок, число, `null` тощо.

Файл `hooks.tsx`:

```tsx
import { useState, useRef, type ReactNode } from "react";

type Product = { id: number; name: string };

export function Hooks() {
  const [count, setCount] = useState(0);
  setCount("один");

  const [stuck, setStuck] = useState(null);
  setStuck({ id: 1, name: "Чай" });

  const [chosen, setChosen] = useState<Product | null>(null);
  setChosen({ id: 1, name: "Чай" });
  console.log(chosen.name);

  const [list, setList] = useState([]);
  setList([{ id: 1, name: "Чай" }]);

  const inputRef = useRef<HTMLInputElement>(null);
  inputRef.current.focus();
  return <input ref={inputRef} />;
}

function List<T>(props: { items: T[]; render: (item: T) => ReactNode }) {
  return <ul>{props.items.map((item, i) => <li key={i}>{props.render(item)}</li>)}</ul>;
}

export const row = <List items={[{ id: 1, name: "Чай" }]} render={(p) => p.title} />;
```

```text
$ npx tsc --noEmit --strict --target es2022 --jsx react-jsx --pretty false hooks.tsx
hooks.tsx(7,12): error TS2345: Argument of type 'string' is not assignable to parameter of type 'SetStateAction<number>'.
hooks.tsx(10,14): error TS2353: Object literal may only specify known properties, and 'id' does not exist in type '(prevState: null) => null'.
hooks.tsx(14,15): error TS18047: 'chosen' is possibly 'null'.
hooks.tsx(17,12): error TS2322: Type '{ id: number; name: string; }' is not assignable to type 'never'.
hooks.tsx(20,3): error TS18047: 'inputRef.current' is possibly 'null'.
hooks.tsx(28,76): error TS2339: Property 'title' does not exist on type '{ id: number; name: string; }'.
```

Кожне повідомлення пояснюється тим, що вже розібрано в цій лекції. Розберемо їх по черзі.

- **Рядок 7, `setCount("один")`.** Початкове значення `0` дало `S = number`, тому функція зміни приймає лише
  `SetStateAction<number>`: число або функцію, яка повертає число. Рядок туди не підходить.
- **Рядок 10, `setStuck(...)`.** Початкове значення `null` дало `S = null`, як у `box(null)`. Функція зміни приймає
  `SetStateAction<null>`, тобто `null` або функцію `(prevState: null) => null`. Об'єкт товару не є `null`, тому
  компілятор пробує другий варіант, функцію, і застосовує до об'єктного літерала перевірку зайвих полів (див. лекцію
  дня 9, розділ «Як записують типи»). Через це текст помилки незграбний: «поля `id` немає в типі `(prevState: null) =>
  null`». Справжня причина простіша: у стан, оголошений як `null`, нічого іншого покласти не можна.
- **Рядок 14, `chosen.name`.** Запис `useState<Product | null>(null)` вказує аргумент типу явно, як
  `box<Product | null>(null)`, і рядок 13 `setChosen(...)` проходить. Проте тепер стан може дорівнювати `null`, тому
  читання поля компілятор пропускає лише після перевірки на `null`. Це звуження з лекції дня 9, розділ «Звуження: `if`
  як доказ для компілятора».
- **Рядок 17, `setList(...)`.** Порожній масив `[]` має тип `never[]`, як у `last([])`, тому `S = never[]`. Елемент
  `{ id: 1, name: "Чай" }` не підходить до `never`. Щоб список міг містити товари, пишуть
  `useState<Product[]>([])`.
- **Рядок 20, `inputRef.current.focus()`.** `HTMLInputElement` є типом з описів браузера для елемента `<input>`
  (елементи сторінки як об'єкти пояснено в лекції дня 7, розділ «Сторінка як дерево об'єктів»). Атрибут
  `ref={inputRef}` просить React покласти справжній елемент `<input>` у поле `inputRef.current`, але React робить це
  лише після того, як покаже елемент на сторінці. До того в полі лежить початкове значення `null`. Тому `@types/react`
  для виклику з `null` повертає тип, у якому `current` має тип `HTMLInputElement | null`, і компілятор вимагає
  перевірки. Найкоротший запис такої перевірки: `inputRef.current?.focus()`.
- **Рядок 28, `p.title`.** Компонент теж може бути дженериком. Компілятор вивів `T` з пропса `items`: це
  `{ id: number; name: string }`. Параметр функції `render` має той самий тип `T`, тому `p` отримав тип товару без
  поля `title`. Так параметр типу зв'язує два пропси між собою. Атрибут `key` в `<li key={i}>` потрібен React, щоб
  розрізняти рядки списку (див. лекцію дня 2, розділ «Як це проявиться в React»).

Деякі дані компонент завантажує з сервера. Функцію, яка робить такий запит і повертає відповідь як стан, теж
оформлюють хуком, і в плані її називають хуком запиту. Якщо такий хук повертає `T`, він потрапляє в ту саму пастку, що
й `parse<T>`. Він зручний у вжитку, але відповідь сервера лишається неперевіреною, доки всередині хука немає
перевірки.

Ще одна особливість файлів `.tsx` стосується стрілкових функцій. У звичайній функції параметр типу стоїть після назви,
`function first<T>(...)`, і плутанини немає. У стрілковій функції запис `<T>` стоїть на початку виразу, а у файлі
`.tsx` компілятор читає його як відкривальний тег JSX.

Файл `arrow.tsx`:

```tsx
// Звичайна функція: параметр типу після назви, тут конфлікту з JSX немає.
function first<T>(list: T[]) {
  return list[0];
}

// Стрілкова функція з <T>: компілятор читає <T> як початок тегу JSX.
const second = <T>(list: T[]) => list[1];
```

```text
$ npx tsc --noEmit --strict --target es2022 --jsx react-jsx --pretty false arrow.tsx
arrow.tsx(7,17): error TS17008: JSX element 'T' has no corresponding closing tag.
arrow.tsx(7,32): error TS1382: Unexpected token. Did you mean `{'>'}` or `&gt;`?
arrow.tsx(8,1): error TS1005: '</' expected.
```

Перше повідомлення каже: «елемент JSX `T` не має закривального тегу». Компілятор побачив `<T>` і вирішив, що це тег,
як `<li>`. Далі він сприйняв знак `>` зі стрілки `=>` як звичайний текст усередині тегу, а наприкінці файла так і не
знайшов `</T>`. Функція `first` помилок не дала. Щоб стрілкова функція працювала, після `T` ставлять кому. Тег JSX не
може містити кому після назви, тому компілятор розуміє, що це параметр типу.

Файл `arrow-comma.tsx`:

```tsx
// Кома після T показує, що це параметр типу, а не тег.
const second = <T,>(list: T[]) => list[1];
```

```text
$ npx tsc --noEmit --strict --target es2022 --jsx react-jsx --pretty false arrow-comma.tsx
(tsc нічого не надрукував: помилок немає)
```

## Перевірте себе

Спершу дайте відповідь самі, уголос або письмово, і лише потім розгортайте пояснення.

**1. Чим `function last<T>(list: T[]): T | undefined` краща за `function last(list: unknown[]): unknown`?**

<details><summary>Відповідь</summary>

Обидві приймають будь-який масив, але друга забуває тип елементів, і результат доводиться перевіряти. Перша зв'язує
вхід із виходом: для масиву чисел результат має тип `number | undefined`. Під час роботи вони однакові, різниця існує
лише для компілятора.

</details>

**2. Навіщо у `pluck` два параметри типу, якщо `key: keyof T` теж зупиняє описку?**

<details><summary>Відповідь</summary>

Параметр `K` запам'ятовує конкретне поле. З ним результат має тип `T[K][]`, для `"price"` це `number[]`. Без нього
компілятор знає лише, що ключ є якимось ключем `T`, і результат стає об'єднанням типів усіх полів.

</details>

**3. У `Omit<Product, "prise">` є описка. Що скаже компілятор і чому?**

<details><summary>Відповідь</summary>

Нічого. Другий параметр `Omit` обмежено будь-яким ключем, а не `keyof T`. Описка нічого не прибере, і тип лишиться
повним `Product`. `Pick` має обмеження `K extends keyof T`, тому там компілятор повідомить про помилку.

</details>

**4. Чому `parse<Rate>(text)` не краща за `JSON.parse(text) as Rate`?**

<details><summary>Відповідь</summary>

Обидва записи лише наказують компілятору вважати значення типом `Rate`. Параметр `T` трапляється лише у виході, тому
нічого не зв'язує. Перевірити дані може лише код, який виконується.

</details>

**5. Що потрібно змінити в `useState(null)`, якщо там згодом буде товар, і що зміниться для коду, який читає стан?**

<details><summary>Відповідь</summary>

Написати `useState<Product | null>(null)`. Тоді функція зміни прийме товар, а код, який читає стан, мусить спершу
перевірити значення на `null`, бо інакше компілятор скаже `'chosen' is possibly 'null'`.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| дженерик (generic) | функція або тип із параметром типу |
| параметр типу | ім'я, замість якого компілятор підставляє конкретний тип |
| аргумент типу | конкретний тип у кутових дужках виклику, наприклад `string` у `createStack<string>()` |
| виведення параметра | компілятор визначає `T` з аргументів виклику або з типу місця, куди йде результат |
| кортеж (tuple) | масив зі сталою кількістю елементів, де кожен має свій тип, наприклад `[A, B]` |
| обмеження, `extends` | вимога до параметра типу: чому він має відповідати |
| `keyof T` | об'єднання назв полів типу `T` |
| індексований доступ, `T[K]` | тип поля `K` у типі `T` |
| індексна сигнатура | запис `{ [key: string]: number }`: за будь-яким ключем такого виду лежить значення цього типу |
| `void` | тип результату функції, яка не повертає значення |
| службовий тип (utility type) | вбудований дженерик, який будує новий тип зі старого |
| зіставлений тип (mapped type) | тип, який перебирає ключі й будує поле для кожного |
