# Лекція. День 11. Проєкт: Vite, лінт, TypeScript

Сьогодні починається ваш наскрізний проєкт, тобто застосунок `spa`, який ви будуватимете й доповнюватимете в
наступних фазах плану. Свого коду в ньому поки майже немає. Лекція пояснює, навіщо потрібні п'ять інструментів, які ви
поставите: Vite, TypeScript, ESLint, Prettier і Vitest. Для кожного з них вона показує, яку саме помилку він ловить, а
яку пропускає. Читання займе близько 50 хвилин. Весь вивід нижче справжній: його отримано на Node 24, Vite 8.3,
TypeScript 6.0, ESLint 10 і Vitest 5. Коли проєкт уже буде створено й ви захочете повторити ці запуски, працюйте в
окремій копії: команда `cp -a spa /tmp/spa-lab` робить таку копію в тимчасовій теці. Тоді файли дослідів не
потраплять у ваш перший коміт.

Застереження про версію: у двох попередніх лекціях компілятор мав версію 7, а тут він має версію 6.0. Це обмеження
через ESLint: пакет `typescript-eslint`, через який ESLint читає код TypeScript, працює лише з TypeScript, нижчим за
6.1. Розділ «TypeScript: команда `tsc -b`, файл `tsconfig` і слово `strict`» показує, де це записано.

**Після лекції ви зможете пояснити:**

- чому браузер не може просто відкрити файл `.tsx` і що робить Vite, щоб він зміг;
- чому Vite у розробці не склеює файли, а для продакшну склеює;
- чому сторінка працює, хоча в коді є помилка типу, і хто цю помилку знайде;
- як гаряча заміна оновлює сторінку, не скидаючи стан, і коли цього не виходить;
- чому хук не можна класти в `if`, хоча тест часто проходить;
- яку помилку зловить `tsc`, яку ESLint, яку Vitest, а яку жоден із них.

## Чому браузер не може просто відкрити ваш код

Шаблон `react-ts` створює файл `src/main.tsx`. Це перший файл вашого застосунку:

```tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App.tsx'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

Цей файл запускає весь застосунок. У файлі `index.html` шаблону стоїть порожній елемент `<div id="root"></div>`.
Функція `createRoot` з пакета `react-dom` отримує цей елемент і робить його місцем, куди React показуватиме
застосунок. Метод `render` показує там компонент `App` з файла `App.tsx`. Компонент `StrictMode` обгортає застосунок і
під час розробки вмикає додаткові перевірки (див. лекцію дня 6, розділ «Як це проявиться в React»). Знак оклику після
`getElementById('root')` є записом TypeScript. Метод `getElementById` повертає `null`, якщо елемента з такою назвою
немає, а знак оклику каже компілятору: «тут точно не `null`».

Якщо дати цей файл браузеру без змін, нічого не запрацює, і на це є три окремі причини.

**Перша причина: це не JavaScript.** Браузер виконує лише JavaScript. Теги на кшталт `<StrictMode>` усередині коду
належать до JSX, а знак оклику належить до TypeScript. Браузер зупиниться на першому такому символі з помилкою
синтаксису.

**Друга причина: браузер не знає, де лежить `react`.** Запис `from 'react'` містить назву пакета без шляху, тобто голий
вказівник (див. лекцію дня 4, розділ «Як за рядком у лапках знаходять файл»). Node вміє шукати такі пакети в теці
`node_modules`, а браузер працює лише з адресами й сам ніякої теки на вашому диску не бачить.

**Третя причина: сам React написано в старому форматі модулів.** Ось увесь файл `node_modules/react/index.js`:

```js
'use strict';

if (process.env.NODE_ENV === 'production') {
  module.exports = require('./cjs/react.production.js');
} else {
  module.exports = require('./cjs/react.development.js');
}
```

Це формат CommonJS, у якому Node жив до появи `import` і `export` (див. лекцію дня 4, той самий розділ). Файл вибирає
одну з двох збірок React за змінною `NODE_ENV`, яку Node читає з об'єкта `process.env`. У браузері немає ні `require`,
ні `module`, ні `process`.

Отже, між вашими файлами й браузером мусить стояти програма, яка перетворює код. У лекції дня 4 така програма
називалася бандлером. Vite є бандлером і водночас сервером розробки, тому його називають ширше, інструментом збірки.
Він виконує дві різні роботи:

| | Сервер розробки, `npm run dev` | Збірка, `npm run build` |
|---|---|---|
| Для кого | для вас, поки ви пишете код | для користувачів сайту |
| Коли перетворює файл | у мить, коли браузер його запитав | усі файли наперед, один раз |
| Що отримує браузер | багато окремих модулів | кілька склеєних і стиснутих файлів |

## Робота перша: сервер розробки віддає файли на вимогу

Простежимо за одним показом сторінки.

1. Ви запускаєте `npm run dev`, і Vite запускає сервер за адресою `http://localhost:5173`. Слово `localhost` означає
   ваш власний комп'ютер, а 5173 є номером порту, на якому Vite чекає на запити. Сервер готовий приблизно за 0,2
   секунди, бо він ще не перетворив жодного вашого файла.
2. Ви відкриваєте цю адресу в браузері. Браузер запитує адресу `/` і отримує ваш `index.html`. У ньому стоїть рядок
   `<script type="module" src="/src/main.tsx">`. Атрибут `type="module"` каже браузеру, що скрипт є модулем (див.
   лекцію дня 4, розділ «Як завантажується програма з модулів»).
3. Браузер запитує `/src/main.tsx`. Лише тепер Vite читає цей файл із диска й перетворює його.
4. Браузер читає отриманий код, бачить у ньому `import` і робить новий запит на кожен із них. Так він обходить усі
   файли, від яких залежить сторінка.

Відповідь сервера можна побачити й без браузера. Поки працює `npm run dev`, у другому терміналі програма `curl` запитує
той самий файл, а програма `grep` вибирає з довгої відповіді потрібні шматки. Прапорець `-o` просить друкувати лише
знайдені шматки, а не цілі рядки, бо Vite записує кілька команд в один дуже довгий рядок. Шаблон після `-oE`
перелічує через знак `|` п'ять шматків, які нас цікавлять:

```text
$ curl -s http://localhost:5173/src/main.tsx | grep -oE 'import __vite__cjsImport1[^;]*|const createRoot = [^;]*|import App[^;]*|getElementById\([^)]*\)|_jsxDEV\(App, [^,]*'
const createRoot = __vite__cjsImport1_reactDom_client["createRoot"]
import __vite__cjsImport1_reactDom_client from "/node_modules/.vite/deps/react-dom_client.js?v=a3d26016"
import App from "/src/App.tsx"
getElementById("root")
_jsxDEV(App, {}
```

Ось що стало з кожною незвичною частиною `main.tsx` у відповіді сервера:

| У файлі на диску | У відповіді сервера |
|------------------|---------------------|
| `import { createRoot } from 'react-dom/client'` | `import __vite__cjsImport1_reactDom_client from "/node_modules/.vite/deps/react-dom_client.js?v=a3d26016"` і `const createRoot = __vite__cjsImport1_reactDom_client["createRoot"]` |
| `from './App.tsx'` | `from "/src/App.tsx"` |
| `getElementById('root')!` | `getElementById("root")` |
| `<App />` | виклик функції `_jsxDEV(App, {}, ...)` |

Перша причина зникла, бо знак оклику вирізано, а теги замінено викликами функції `_jsxDEV`. Цю функцію дає пакет
React, а решта її аргументів, яких вивід не показав, каже, у якому рядку файла стояв тег, щоб повідомлення про помилку
вказувало на ваш код. Друга причина зникла, бо голу назву замінено справжньою адресою. Лишається третя, і саме для неї
існує тека `node_modules/.vite/deps`.

**Попереднє пакування.** Під час першого запуску Vite бере кожен пакет, який ви імпортуєте, і склеює його в один модуль
з `import` та `export`. Так зникає CommonJS і зменшується кількість запитів: документація наводить пакет `lodash-es` із
понад 600 внутрішніх модулів, який без пакування породив би понад 600 запитів.

Тепер зрозуміло, звідки взялися два рядки замість одного `import { createRoot }`. Пакет `react-dom` написано в
CommonJS, тому в ньому немає іменованих експортів, а є лише один об'єкт `module.exports`. Vite імпортує цей об'єкт
цілком під службовою назвою `__vite__cjsImport1_reactDom_client` і бере з нього поле `createRoot`. Документація
називає це розумним аналізом імпортів: завдяки йому звичний запис `import { useState } from 'react'` працює й з
пакетами на CommonJS.

Хвіст `?v=a3d26016` в адресі пакета потрібен для кешу браузера. Прапорець `-I` просить `curl` запитати лише заголовки
відповіді (про заголовки див. лекцію дня 6, розділ «Два `await`: заголовки приходять раніше за тіло»), а `grep -i`
шукає рядок без огляду на великі й малі літери:

```text
$ curl -sI "http://localhost:5173/node_modules/.vite/deps/react-dom_client.js?v=a3d26016" | grep -i cache-control
Cache-Control: max-age=31536000,immutable

$ curl -sI http://localhost:5173/src/App.tsx | grep -i cache-control
Cache-Control: no-cache
```

Заголовок `Cache-Control` каже браузеру, як довго можна брати файл зі свого сховища, не питаючи сервер. Для пакета
`max-age=31536000` дозволяє 31 536 000 секунд, тобто рік, а `immutable` каже, що файл за цією адресою ніколи не
зміниться, тому браузер навіть не перепитує. Коли ви поставите іншу версію пакета, Vite змінить хвіст `?v=...`, і
браузер вважатиме нову адресу новим файлом. Ваш власний файл `App.tsx` отримав `no-cache`: браузер може зберегти
його, але перед кожним використанням мусить спитати сервер, чи файл не змінився, бо ви змінюєте його постійно.

**Вимір: що дає робота на вимогу.** Ми зробили окрему копію проєкту, `cp -a spa /tmp/spa-many`, і створили в ній 2000
крихітних файлів `.ts` та один головний файл, який імпортує їх усі. Це робить такий скрипт:

```js
// файл make-many.mjs. Запускайте лише в копії проєкту, бо він замінює src/main.tsx.
import { mkdirSync, writeFileSync } from 'node:fs'

mkdirSync('src/many', { recursive: true })
let imports = ''
let names = ''
for (let i = 0; i < 2000; i++) {
  // Кожен файл крихітний: одна стала з типом, який Vite мусить вирізати.
  writeFileSync(`src/many/m${i}.ts`, `export const v${i}: number = ${i}\n`)
  imports += `import { v${i} } from './many/m${i}.ts'\n`
  names += `v${i}, `
}
writeFileSync('src/main.tsx', `${imports}console.log([${names}].length)\n`)
```

Другий скрипт поводиться як браузер. Сервер розробки Vite говорить із браузером за протоколом HTTP/1.1, а за цим
протоколом браузер тримає до одного сервера не більше шести з'єднань одночасно, і MDN згадує цю межу. Тому скрипт
запитує головний файл, знаходить у відповіді адреси всіх модулів і тримає не більше шести запитів одночасно. Він
обходить модулі двічі й друкує час кожного обходу:

```js
// файл walk.mjs
const server = 'http://localhost:5173'

async function walk() {
  const started = performance.now()
  const main = await (await fetch(`${server}/src/main.tsx`)).text()
  // Відповідь сервера містить адресу кожного модуля: скрипт шукає їх так само, як браузер.
  const paths = [...main.matchAll(/from "(\/src\/many\/[^"]+)"/g)].map((match) => match[1])
  const worker = async () => {
    while (paths.length > 0) await (await fetch(server + paths.pop())).text()
  }
  await Promise.all(Array.from({ length: 6 }, worker))
  return Math.round(performance.now() - started)
}

console.log('перший обхід:', await walk(), 'мс')
console.log('другий обхід:', await walk(), 'мс')
```

Метод `matchAll` знаходить у тексті всі збіги з шаблоном, а `match[1]` бере з кожного збігу частину в круглих дужках,
тобто саму адресу. Виклик `Array.from({ length: 6 }, worker)` шість разів викликає функцію `worker` і збирає шість
промісів, які вона повернула, у масив. Усі шість працівників беруть адреси з одного спільного масиву `paths`: кожен
забирає методом `pop` останню адресу, чекає на відповідь і бере наступну, доки масив не спорожніє. Тому одночасно
триває не більше шести запитів. `Promise.all` чекає, доки закінчать усі шість (див. лекцію дня 5, розділ «Чотири
способи чекати на кілька промісів»).

У теці копії спершу виконайте `node make-many.mjs`, потім `npm run dev`, а в другому терміналі `node walk.mjs`. Коли
скрипт закінчить, зупиніть сервер і виконайте дві останні команди з виводу нижче. Команда `tsc -b` перевіряє типи
всього проєкту, і розділ про TypeScript нижче пояснює її докладно. Вона запам'ятовує результат минулої перевірки, а
прапорець `--force` просить перевірити все заново. Один із наших запусків надрукував:

```text
$ npm run dev
  VITE v8.3.5  ready in 314 ms

$ node walk.mjs
перший обхід: 2484 мс
другий обхід: 519 мс

$ npx vite build | grep built
✓ built in 155ms

$ time npx tsc -b --force

real	0m3.509s
user	0m5.158s
sys	0m0.670s
```

Рядок `ready in` друкує сам Vite: це час запуску сервера. Рядок `built in` теж друкує Vite: це час склеювання. Рядок
`real` друкує команда `time`: це час від початку до кінця перевірки типів за годинником. Рядки `user` і `sys` рахують
лише роботу процесора. Їхня сума більша за `real`, бо програма використовувала кілька ядер процесора одночасно, і час
кожного ядра пораховано окремо. Нас цікавить лише `real`.

Ваші числа будуть іншими, і в нас вони теж змінювалися від запуску до запуску. Таблиця дає округлені значення з кількох
запусків, а запуск сервера на порожньому шаблоні ми виміряли тією самою командою `npm run dev`:

| Дія | Час |
|-----|-----|
| запуск сервера розробки на порожньому шаблоні | 0,2–0,3 секунди |
| запуск сервера розробки на 2000 файлів | 0,2–0,3 секунди |
| перший обхід усіх модулів: кожен файл перетворюється вперше | близько 3 секунд |
| другий обхід усіх модулів: перетворення взято з кешу сервера | менше за секунду |
| склеювання того самого проєкту, `npx vite build` | 0,2–0,4 секунди |
| перевірка типів того самого проєкту, `npx tsc -b --force` | близько 4 секунд |

Перші два рядки майже однакові, бо запуск сервера не залежить від розміру проєкту: сервер нічого не робить наперед.
Перетворення файлів припадає на перший обхід. Другий обхід нічого не перетворює, тому його час показує ціну самих
запитів, і ця ціна більша, ніж уся збірка. Збірка працює всередині однієї програми й не відповідає на 2000 окремих
запитів, тому на цих крихітних файлах вона виявилася швидшою за обхід.

Отже, робота на вимогу не робить перший показ швидшим за збірку. Вона дає інше: браузер отримує лише ті файли, які
сторінка справді запитала, а після збереження одного файла сервер перетворює й надсилає лише цей файл. Розділ про
гарячу заміну показує це запуском. Для вас це означає, що великий проєкт не сповільнить запуск `npm run dev`, а перше
відкриття сторінки після запуску буде повільнішим за наступні, і це нормально. Найдовший рядок таблиці це перевірка
типів, і наступний розділ пояснює, чому Vite її не робить.

## Перетворення лише вирізає типи й нічого не перевіряє

Vite не перевіряє типи, а лише вирізає їх. Node 24 робить із файлом `.ts` те саме (див. лекцію дня 9, розділ
«Перевірка й запуск — дві окремі дії»), тому показати це можна без браузера:

```ts
// файл basket.ts
const basketKopecks: number = 120000
const deliveryKopecks: number = "5000"
console.log("до сплати:", basketKopecks + deliveryKopecks)
```

```text
$ node basket.ts
до сплати: 1200005000

$ npx tsc --noEmit --strict --target esnext --ignoreConfig basket.ts
basket.ts(3,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

Рядок 3 обіцяє число, а дає рядок. Програма, яка лише вирізає типи, прибирає `: number` і запускає те, що лишилося.
Далі JavaScript додає число до рядка, склеює їх і замість 1250 гривень отримує нісенітницю. Компілятор `tsc` знайшов
помилку, нічого не запускаючи. Прапорці команди ті самі, що в лекції дня 9, розділ «Що додає TypeScript»: `--noEmit`
просить лише перевірити, а `--ignoreConfig` потрібен через помилку `TS5112`, бо в теці проєкту лежить `tsconfig.json`.
Новий тут лише `--target esnext`: він називає найновіше видання стандарту JavaScript.

Vite працює так само, як `node` у цьому прикладі. Щоб перетворити один файл, досить прочитати цей файл, а щоб
перевірити типи, треба знати всі файли, від яких він залежить, і це повільно. Тому документація Vite лишає перевірку
двом іншим місцям. Перше місце це редактор коду, який підкреслює помилки типів, поки ви пишете. Друге місце це окрема
команда. У шаблоні ця команда вбудована в збірку:

```json
"build": "tsc -b && vite build"
```

Знак `&&` виконує другу команду, лише якщо перша завершилася без помилок. Тому `npm run dev` покаже сторінку з
помилкою типу, а `npm run build` зупиниться.

## Гаряча заміна: як змінити код, не втративши стан

Уявіть форму на п'ять кроків. На п'ятому кроці ви виправили підпис, і якщо сторінка перезавантажиться, доведеться
знову пройти всі кроки. Гаряча заміна (англійською Hot Module Replacement, HMR) розв'язує цю проблему: браузер отримує
лише новий варіант зміненого файла, а решта сторінки працює далі.

Сервер і браузер спілкуються через WebSocket, тобто постійне з'єднання, яким сервер може надсилати повідомлення сам,
без запиту від браузера. Клієнт цього з'єднання, модуль `/@vite/client`, Vite дописує у вашу сторінку. Ми підключилися
до того самого з'єднання таким скриптом. Другий аргумент `new WebSocket`, рядок `"vite-hmr"`, називає домовленість
про формат повідомлень, яку сервер Vite чекає від свого клієнта:

```js
// файл hmr-watch.mjs
const client = await (await fetch("http://localhost:5173/@vite/client")).text()
// Сервер приймає лише того, хто назве токен, тобто секретний рядок із тексту клієнта.
const token = client.match(/const wsToken = "([^"]+)"/)[1]
const socket = new WebSocket(`ws://localhost:5173/?token=${token}`, "vite-hmr")

// Кожне повідомлення сервера приходить текстом JSON, і скрипт друкує його тип.
socket.onmessage = (event) => {
  const msg = JSON.parse(event.data)
  if (msg.type === "update") {
    console.log("update:", msg.updates.map((u) => `${u.type} ${u.path}`).join(", "))
  } else {
    console.log(msg.type, msg.path ?? "")
  }
}
```

Запустіть `npm run dev`, відкрийте сторінку в браузері, а в другому терміналі виконайте `node hmr-watch.mjs`. Сторінка
мусить бути відкрита, бо про зв'язки між модулями сервер дізнається лише тоді, коли браузер їх запитує. Далі ми клацнули
кнопку лічильника тричі й змінювали файли по одному: у `src/App.tsx` змінили текст заголовка, у `src/App.css` дописали
одне правило, а в кінець `src/main.tsx` та `index.html` дописали коментар. Скрипт надрукував:

```text
connected
update: js-update /src/App.tsx
update: js-update /src/App.css
full-reload *
full-reload /index.html
```

Термінал сервера водночас надрукував:

```text
1:11:39 PM [vite] (client) hmr update /src/App.tsx
1:11:41 PM [vite] (client) hmr update /src/App.css
1:11:43 PM [vite] (client) page reload src/main.tsx
1:11:44 PM [vite] (client) page reload index.html
```

Перший рядок скрипта означає, що з'єднання встановлено. Кожен наступний рядок відповідає одному збереженому
файлу. Повідомлення `update` несе адресу модуля, який браузер має довантажити. Повідомлення `full-reload` просить
перезавантажити сторінку, а зірочка в ньому означає «будь-яку відкриту сторінку». Кнопка лічильника показує, що зробив
браузер: після змін `App.tsx` і `App.css` кнопка далі показувала `Count is 3`, а після змін `main.tsx` та
`index.html` вона показувала `Count is 0`. Ось ті самі результати однією таблицею:

| Що змінили | Повідомлення сервера | Рядок у терміналі | Що робить браузер |
|------------|----------------------|-------------------|-------------------|
| `src/App.tsx` | `update: js-update /src/App.tsx` | `hmr update /src/App.tsx` | довантажує новий модуль, а стан лишається |
| `src/App.css` | `update: js-update /src/App.css` | `hmr update /src/App.css` | замінює стиль на сторінці |
| `src/main.tsx` | `full-reload *` | `page reload src/main.tsx` | перезавантажує сторінку, а стан зникає |
| `index.html` | `full-reload /index.html` | `page reload index.html` | перезавантажує сторінку, а стан зникає |

**Чому файли поводяться по-різному.** Модуль може заявити, що вміє прийняти власне оновлення. У перетвореному
`App.tsx` таку заяву дописав плагін React. Документація називає такий модуль межею гарячої заміни (HMR boundary). Коли
змінюється файл, сервер іде від нього вгору через тих, хто його імпортує, і шукає найближчу межу. Файл `main.tsx`
стоїть на самому верху, нічого не заявляє, і йти далі нікуди, тому лишається повне перезавантаження. Цю заяву видно у
відповіді сервера, поки працює `npm run dev`:

```text
$ curl -s http://localhost:5173/src/App.tsx | grep 'import.meta.hot.accept'
    import.meta.hot.accept((nextExports) => {

$ curl -s http://localhost:5173/src/main.tsx | grep -c 'import.meta.hot.accept'
0
```

Запис `import.meta` дає модулю об'єкт із відомостями про нього самого, наприклад його адресу. Під час розробки Vite
додає до цього об'єкта поле `hot` з функціями гарячої заміни. Виклик `import.meta.hot.accept` і є заявою модуля, що
він приймає власне оновлення. Перша команда знаходить його в `App.tsx`. Друга команда рахує такі рядки в `main.tsx`
(прапорець `-c` просить `grep` надрукувати лише кількість) і отримує нуль.

**Чому стан не зникає.** Для кожного компонента, показаного на сторінці, React тримає власний запис, і в ньому лежать
значення `useState` цього компонента. Ці записи вкладені один в одного так само, як компоненти, тому їх називають
деревом компонентів. Новий модуль містить нову функцію `App`. Частина плагіна під назвою React Refresh просить React
викликати нову функцію замість старої, але дерева компонентів не перебудовує. Стан лежить у дереві, а не у функції,
тому `useState` у новій функції повертає старе значення. Документація Fast Refresh (так називається той самий механізм)
уточнює межі: `useState` і `useRef` зберігають значення, якщо ви не змінили їхніх аргументів і порядку викликів хуків.
Заміна `useState(0)` на `useState(5)` скине стан, і це правильно, бо інакше ви не побачите нового початкового
значення.

**Чому файл має експортувати лише компоненти.** React Refresh замінює компоненти, а що робити зі звичайною функцією,
він не знає. Тому файл, який експортує і те, і те, гаряче не замінюється, і оновлення йде вгору. Шаблон стереже це
правилом лінтера `react-refresh/only-export-components`.

## Робота друга: збірка для користувачів

Окремі модулі не годяться для користувачів, бо про наступний модуль браузер дізнається лише тоді, коли прочитає
попередній, і кожен вкладений `import` означає ще один запит. Тому `vite build` читає `index.html`, проходить усі
імпорти наперед і робить чотири речі.

**Склеює модулі** в один чи кілька файлів, щоб запитів стало мало.

**Викидає те, що ніхто не використовує.** Цей крок називають tree-shaking, буквально «струшування дерева». Що це таке
і чому він можливий лише з `import` та `export`, пояснює лекція дня 4, розділ «Як завантажується програма з модулів».
Тут та сама перевірка позначками повторена в проєкті `spa`, бо той самий файл знадобиться для двох наступних кроків.
Ми додали файл із двома функціями й використали лише першу:

```ts
// файл src/money.ts
export function formatUah(kopecks: number): string {
  return `МАРКЕР-ПОТРІБНИЙ ${kopecks / 100} грн`
}

export function formatUsd(cents: number): string {
  return `МАРКЕР-ЗАЙВИЙ ${cents / 100} дол`
}
```

У `src/main.tsx` ми дописали імпорт першої функції та один її виклик, а другу функцію ніде не згадали:

```tsx
// дописано в src/main.tsx
import { formatUah } from './money.ts'

console.log(formatUah(120000))
```

Команда `npm run build` спершу перевіряє типи, а потім збирає проєкт і друкує, які файли вийшли:

```text
$ npm run build

> tsc -b && vite build

transforming...

rendering chunks...
```

Увесь код застосунку разом із React потрапив в один файл `dist/assets/index-BaJGfhdC.js`. Числа праворуч від назв
показують розмір кожного файла, і що вони означають, ви розберете завтра. Програма `grep -c` рахує в зібраному файлі
рядки з кожним маркером:

```text
$ grep -c 'МАРКЕР-ПОТРІБНИЙ' dist/assets/index-*.js
1

$ grep -c 'МАРКЕР-ЗАЙВИЙ' dist/assets/index-*.js
```

Рядок `МАРКЕР-ПОТРІБНИЙ` у зібраному файлі є, а рядка `МАРКЕР-ЗАЙВИЙ` немає, отже, `formatUsd` до користувача не дійшла.
Для вас це означає, що експортована функція, яку ніхто не імпортує, не збільшує файл, який завантажує користувач.

**Мінімізує код,** тобто переписує його коротше, не змінюючи поведінки. Ось функція `formatUah` у тому самому зібраному
файлі:

```text
$ grep -o 'function [^ ]*{return`МАРКЕР-ПОТРІБНИЙ[^`]*`}' dist/assets/index-*.js
function _(e){return`МАРКЕР-ПОТРІБНИЙ ${e/100} грн`}
```

Назва `formatUah` стала `_`, параметр `kopecks` став `e`, а типи зникли.

**Додає до назви файла відбиток умісту.** Відбиток це короткий рядок, який Vite обчислює з умісту файла: однаковий
уміст завжди дає той самий відбиток, а змінений уміст дає інший. У назві `index-BaJGfhdC.js` відбиток це `BaJGfhdC`.
Ми подивилися назви після `npm run build`. Потім замінили в `main.tsx` виклик на `formatUah(120001)`, знову виконали
`npm run build` і подивилися назви ще раз, а також рядки `index.html`, які підключають ці файли:

```text

$ ls -1 dist/assets/index-*

$ grep 'assets/index-' dist/index.html
    <script type="module" crossorigin src="/assets/index-CTglleNo.js"></script>
    <link rel="stylesheet" crossorigin href="/assets/index-D64VDMd1.css">
```

Вміст JavaScript змінився, і змінилася його назва. Стилі лишилися тими самими, і назва теж лишилася. Зібраний
`index.html` уже посилається на нову назву. Завдяки цьому сервер може дозволити браузеру зберігати такі файли
назавжди тим самим заголовком `immutable`, що й пакети під час розробки. Нова версія завжди матиме нову назву, а
новий `index.html` приведе браузер до неї.

## TypeScript: команда `tsc -b`, файл `tsconfig` і слово `strict`

**Три файли `tsconfig`.** Файл `tsconfig.json` зберігає налаштування компілятора, щоб не писати їх щоразу прапорцями
(див. лекцію дня 9, розділ «Що додає TypeScript»). Шаблон створив три такі файли, бо код проєкту виконують дві різні
програми. Файл `tsconfig.app.json` описує код у `src`, який виконує браузер. Файл `tsconfig.node.json` описує
`vite.config.ts`, який виконує Node. Ось увесь головний файл `tsconfig.json`:

```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}
```

Поле `files` перелічує файли з кодом, і тут цей перелік порожній. Поле `references` містить посилання на два інші
файли налаштувань. Звідси випливає типова помилка:

```text
# у src/wrong.ts написано: export const seats: number = "двадцять"

$ npx tsc --noEmit
(нічого не надруковано, код завершення 0)

$ npx tsc -b
src/wrong.ts(1,14): error TS2322: Type 'string' is not assignable to type 'number'.
(код завершення 2)
```

Без `-b` компілятор прочитав головний файл, не знайшов у ньому жодного файла з кодом і тому не побачив помилок.
Прапорець `-b` є коротким ім'ям `--build`. У цьому режимі компілятор проходить усі посилання з `references` і
перевіряє кожен названий там файл налаштувань разом із його кодом. Результат він записує в теку
`node_modules/.tmp`, і наступного разу перевіряє лише те, що змінилося. Саме цей запам'ятований результат
прапорець `--force` у вимірі вище просив не брати. Тому в цьому проєкті типи перевіряє `tsc -b` чи `npm run build`, а
не проста команда `tsc`.

Код завершення тут 2, а в лекції дня 9 команда `tsc` завершувалася з кодом 1. Причина у версії компілятора: у проєкті
`spa` стоїть TypeScript 6.0, а не 7. Це вимушене обмеження через ESLint. Пакет `typescript-eslint`, через який ESLint
розуміє TypeScript, записує в полі `peerDependencies`, з якими версіями TypeScript він працює (про це поле див. лекцію
дня 4, розділ «Як це проявиться в React»). Ось цей запис для найновішої версії пакета на день написання лекції:

```text
$ npm view typescript-eslint@8.73.0 peerDependencies
{
  eslint: '^8.57.0 || ^9.0.0 || ^10.0.0',
  typescript: '>=4.8.4 <6.1.0'
}
```

Отже, `typescript-eslint` працює з TypeScript від 4.8.4 і нижчим за 6.1, тобто з версією 7 не працює. Програма
`create-vite` знає про це сама. Ми створили той самий шаблон двічі: з прапорцем `--eslint` у теці `spa` і без нього в
теці `spa-default`. Ось рядок `typescript` у файлі `package.json` кожного з двох проєктів:

```text
$ grep '"typescript"' spa/package.json spa-default/package.json
spa/package.json:    "typescript": "~6.0.3",
spa-default/package.json:    "typescript": "~7.0.2",
```

Тильда `~` дозволяє npm змінювати лише останнє число версії (див. лекцію дня 4, розділ «Версії: що означають три
числа»). Тому в `spa` стоятиме TypeScript 6.0.x і ніколи не 6.1, а це якраз діапазон `typescript-eslint`. Коли
`typescript-eslint` запрацює з TypeScript 7, обмеження можна буде зняти. Версія 6.0 повідомляє про знайдені помилки
кодом 2, а версія 7.0 кодом 1. Обидва коди не дорівнюють нулю, тому для команди `npm run build` вони означають одне:
перевірка не пройшла.

**Що вмикає `strict`.** Це один прапорець, який вмикає цілу родину суворих перевірок. Одна з них називається
`strictNullChecks`: вона не дає забути, що значення може бути `undefined` чи `null`. Ось вона на прикладі файла
`found.ts`:

```ts
const shops = [{ city: "Львів", open: true }]
const shop = shops.find((s) => s.city === "Київ")
console.log(shop.open)
```

```text
$ npx tsc --noEmit --strict false --target esnext --ignoreConfig found.ts
(нічого не надруковано)

$ npx tsc --noEmit --strict --target esnext --ignoreConfig found.ts
found.ts(3,13): error TS18048: 'shop' is possibly 'undefined'.

$ node found.ts 2>&1 | grep TypeError
TypeError: Cannot read properties of undefined (reading 'open')
```

Команда `node` друкує повідомлення про помилку разом зі шляхом до файла й довгим переліком викликів. Запис `2>&1`
передає все це в `grep`, а `grep` лишає один рядок. Метод `find` повертає `undefined`, якщо нічого не знайшов.
Перевірка `strictNullChecks` змушує вас врахувати цей випадок, а без неї програма падає вже в користувача.

План згадує рядок `"strict": true`, але в шаблоні його немає, бо від TypeScript 6.0 суворі перевірки увімкнені й без
нього (див. лекцію дня 9, розділ «Що додає TypeScript»).

## ESLint: правила, яких не знає компілятор

Лінтер читає код, не запускаючи його. ESLint перетворює файл на дерево синтаксису, у якому видно, де функція, де
виклик, де умова, і передає це дерево правилам. Ось файл `src/Profile.tsx`, у якому `tsc -b` не знаходить нічого, бо
всі типи тут правильні:

```tsx
import { useEffect, useState } from 'react'

type User = { id: number; name: string }

export function Profile({ user }: { user: User | null }) {
  if (user === null) return <p>Увійдіть</p>
  const [likes, setLikes] = useState(0)
  return <button onClick={() => setLikes(likes + 1)}>{user.name}: {likes}</button>
}

export function Clock({ city }: { city: string }) {
  const [text, setText] = useState('')
  useEffect(() => {
    const timer = setInterval(() => setText(`${city}: ${Date.now()}`), 1000)
    return () => clearInterval(timer)
  }, [])
  return <p>{text}</p>
}

export function Ticket() {
  const code = Math.random()
  return <p>{code}</p>
}
```

ESLint знаходить три проблеми (текст скорочено):

```text
$ npx eslint src/Profile.tsx

                after an early return?                                     react-hooks/rules-of-hooks
16:6   warning  React Hook useEffect has a missing dependency: 'city'. ... react-hooks/exhaustive-deps
21:16  error    Error: Cannot call impure function during render ...       react-hooks/purity
```

Перше число в записі `7:29` це номер рядка у файлі, а друге це номер символу в рядку.

- **`rules-of-hooks`** помітило, що хук стоїть після раннього `return`. Для правила це така сама умова, як `if`
  навколо хука.
- **`exhaustive-deps`** помітило, що ефект читає `city`, а в масиві залежностей її немає. Коли `city` зміниться,
  годинник далі показуватиме стару назву міста, бо ефект не запуститься заново.
- **`purity`** помітило виклик `Math.random()` під час рендеру. Компонент має при тих самих пропсах давати той самий
  результат, а `Math.random()` щоразу дає інший. Це правило прийшло від React Compiler, тобто програми, яка під час
  збірки сама дописує в компоненти оптимізації. Компілятор розраховує, що компоненти дотримуються правил React, і
  разом із ним команда React випустила правила ESLint, які знаходять порушення цих правил. Самого компілятора для цих
  перевірок вмикати не треба: їх запускає пакет `eslint-plugin-react-hooks`.

Слова `error` і `warning` у виводі показують суворість правила, і від неї залежить код завершення лінтера.
Попередження лише друкується, а помилка робить код завершення рівним 1. Цей код потрібен, щоб команда на кшталт
`npm run lint && npm run build` зупинялася на помилці, так само як `&&` зупиняє збірку після `tsc`. Суворість задають
у файлі `eslint.config.js`, який створив шаблон. Пресети в полі `extends` уже задали її для кожного правила, а поле
`rules` дозволяє змінити її для окремого правила. Ось увесь файл, у який ми дописали поле `rules`:

```js
// файл eslint.config.js
import js from '@eslint/js'
import globals from 'globals'
import reactHooks from 'eslint-plugin-react-hooks'
import reactRefresh from 'eslint-plugin-react-refresh'
import tseslint from 'typescript-eslint'
import { defineConfig, globalIgnores } from 'eslint/config'

export default defineConfig([
  globalIgnores(['dist']),
  {
    files: ['**/*.{ts,tsx}'],
    extends: [
      js.configs.recommended,
      tseslint.configs.recommended,
      reactHooks.configs.flat.recommended,
      reactRefresh.configs.vite,
    ],
    languageOptions: {
      globals: globals.browser,
    },
    // Дописано: забута залежність ефекту стає помилкою, а не попередженням.
    rules: {
      'react-hooks/exhaustive-deps': 'error',
    },
  },
])
```

Значення `'off'` вимикає правило, `'warn'` робить його попередженням, а `'error'` робить його помилкою. Замість слів
можна писати числа 0, 1 і 2. Ми поклали компонент `Clock` з файла вище разом із рядком `import` в окремий файл
`src/Clock.tsx` і запустили лінтер двічі: спершу з файлом налаштувань шаблону, а потім із дописаним полем `rules`.
Команда `echo $?` друкує код завершення (див. лекцію дня 9, розділ «Що додає TypeScript»). Шлях до файла й кінець
повідомлення у виводі скорочено:

```text
$ npx eslint src/Clock.tsx; echo $?

0
```

З попередженням лінтер завершився кодом 0, тобто для `&&` перевірка пройшла. Після зміни суворості те саме місце
дало код 1.

**Чому хук не можна класти під умову.** Функція `useState` не отримує імені стану. React знає лише номер виклику:
перед кожним рендером він починає рахувати з нуля, а кожен виклик бере наступну комірку. Візьмемо компонент оформлення
замовлення:

```tsx
// файл src/Checkout.tsx
import { useState } from 'react'

export function Checkout({ gift }: { gift: boolean }) {
  const [city] = useState('Львів')
  let note = ''
  if (gift) [note] = useState('з днем народження')
  const [count] = useState(1)
  return <p>{city} {note} {count}</p>
}
```

Запис `[note] = useState(...)` без `const` кладе перший елемент масиву, який повернув `useState`, в уже оголошену
змінну `note`. Простежимо два рендери. Під час першого рендера `gift` дорівнює `true`, тому виконуються всі три
виклики: місто бере комірку 0, текст привітання бере комірку 1, кількість бере комірку 2. Під час другого рендера
`gift` дорівнює `false`, і виклик усередині `if` не виконується. Місто знову бере комірку 0. Наступним тепер іде
виклик для кількості, і він бере комірку 1, де лежить текст привітання. Комірка 2 лишається без власника. Таблиця
підсумовує ці кроки:

| Виклик | Перший рендер, `gift = true` | Другий рендер, `gift = false` |
|--------|------------------------------|-------------------------------|
| перший | комірка 0, місто | комірка 0, місто |
| другий | комірка 1, текст привітання | комірка 1, але це вже кількість: вона отримала б текст привітання |
| третій | комірка 2, кількість | виклику немає, комірка 2 лишилася без власника |

У цьому випадку React бачить, що хуків стало менше, і зупиняє рендер. Ми перевірили це двома тестами. Тести працюють у
jsdom, тобто в програмі, яка імітує браузерну сторінку всередині Node, і перший рядок файла просить Vitest її увімкнути.
Функція `render` показує компонент уперше, а `rerender` показує його ще раз із новими пропсами, і це другий рендер.

```tsx
// @vitest-environment jsdom
// файл src/Checkout.test.tsx
import { render } from '@testing-library/react'
import { test } from 'vitest'
import { Checkout } from './Checkout'

test('умова не змінилася', () => {
  const { rerender } = render(<Checkout gift={true} />)
  rerender(<Checkout gift={true} />) // другий рендер із тією самою умовою
})

test('умова змінилася', () => {
  const { container, rerender } = render(<Checkout gift={true} />)
  console.log('перший рендер:', container.textContent)
  rerender(<Checkout gift={false} />) // другий рендер: умова стала хибною, і один хук зник
})
```

Ось потрібні рядки виводу, без довгого переліку викликів усередині React:

```text
$ npx vitest run src/Checkout.test.tsx --reporter=verbose

stdout | src/Checkout.test.tsx > умова змінилася
перший рендер: Львів з днем народження 1

 ✓ src/Checkout.test.tsx > умова не змінилася 26ms
 × src/Checkout.test.tsx > умова змінилася 14ms
   → Rendered fewer hooks than expected. This may be caused by an accidental early return statement.

 FAIL  src/Checkout.test.tsx > умова змінилася
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.

      Tests  1 failed | 1 passed (2)
```

Рядок `перший рендер` надрукував `console.log` у другому тесті: перший рендер пройшов, бо всі три хуки були на місці.
Помилку `Rendered fewer hooks` кинув виклик `rerender` із `gift={false}`.

Але React скаржиться лише тоді, коли умова справді змінилася між рендерами. Перший тест позначено `✓`: якщо `gift`
завжди `true`, тест проходить, і помилка чекає на випадок, коли умова зміниться. Лінтер знаходить її одразу, бо читає
код, а не запуск.

**Важливо: `create-vite` має вибір.** Поточний `create-vite` без додаткових прапорців ставить інший лінтер, Oxlint, і
файла `eslint.config.js` не створює. Oxlint теж читає код без запуску, але має власний файл налаштувань
`.oxlintrc.json`, і саме такий файл з'явився в теці `spa-default`, яку ми створили без прапорця. Команда зі сторінки
дня містить `--eslint`, і саме завдяки цьому прапорцю в проєкті з'являється файл `eslint.config.js` з пресетом
`recommended` пакета `eslint-plugin-react-hooks`. Пресетом називають готовий набір правил разом із їхньою суворістю.

## Prettier: форматування окремо від помилок

Prettier не шукає помилок. Він читає код і друкує його заново за єдиними правилами, щоб у команді не сперечатися про
пробіли. Сьогоднішні кроки Prettier не вимагають. Глава `Editor Setup` документації React попереджає: якщо пресет
лінтера містить правила про форматування, вони сперечатимуться з Prettier, і їх варто вимкнути пакетом
`eslint-config-prettier`. У цьому пакеті є й програма, яка перевіряє, чи такі правила є. Ми поставили пакет у копію
проєкту командою `npm i -D eslint-config-prettier` і запустили програму на файлі `src/App.tsx`:

```text
$ npx eslint-config-prettier src/App.tsx
The following rules are enabled but cannot be automatically checked. See:
https://github.com/prettier/eslint-config-prettier#special-rules

- no-unexpected-multiline

Other than that, no rules that are unnecessary or conflict with Prettier were found.
```

Останній рядок каже, що правил, які сперечаються з Prettier, програма не знайшла. Правило `no-unexpected-multiline`
вона лише називає, бо не може перевірити його сама. Воно стосується не вигляду коду, а його змісту: воно ловить
місця, де перенесення рядка схоже на кінець команди, а насправді команда триває на наступному рядку. Отже, пресети
цього шаблону з Prettier не сперечаються, і якщо ви поставите Prettier, `eslint-config-prettier` знадобиться лише
тоді, коли ви додасте пресет із правилами про форматування.

## Vitest: приклади стають перевірками

Рецепт із книжки How to Design Programs, за яким ви пишете функції, вимагає прикладів ще до коду. Останній крок
рецепта перетворює ці приклади на тести, бо так знаходяться помилки. Досі ви перевіряли приклади через `assert`, а
тепер їх запускає Vitest. Він читає той самий `vite.config.ts` і перетворює файли так само, як Vite. Візьмемо
функцію, яка рахує ціну доставки. Коментарі над нею записують перші кроки рецепта: що означають числа, які функція
отримує й повертає, потім запис `deliveryPrice: number -> number`, тобто «отримує число, повертає число», і одне
речення про те, що функція рахує:

```ts
// файл src/delivery.ts
// Гривні: ціле число гривень. Кілограми: число, більше за нуль.

// deliveryPrice: number -> number
// Рахує ціну доставки: до 2 кг включно 70 гривень, а за кожен повний кілограм понад 2 кг ще 15.
export function deliveryPrice(kg: number): number {
  if (kg < 2) return 70
  return 70 + Math.ceil(kg - 2) * 15
}
```

```ts
// файл src/delivery.test.ts
import { expect, test } from 'vitest'
import { deliveryPrice } from './delivery'

test('рівно на межі: 2 кг коштує 70', () => {
  expect(deliveryPrice(2)).toBe(70)
})

test('неповний кілограм не рахується: 3,9 кг коштує 85', () => {
  expect(deliveryPrice(3.9)).toBe(85)
})
```

`test` оголошує один приклад: перший аргумент це назва, другий це функція з перевіркою. `expect(x).toBe(y)` кидає
помилку, якщо `x` не дорівнює `y`. Методи на кшталт `toBe`, які стоять після `expect(...)`, називають матчерами, від
англійського match, «збігатися». У тілі функції ми навмисно написали `Math.ceil` замість `Math.floor`, і Vitest це
знайшов:

```text
$ npx vitest run src/delivery --reporter=verbose
 ✓ src/delivery.test.ts > рівно на межі: 2 кг коштує 70 2ms
 × src/delivery.test.ts > неповний кілограм не рахується: 3,9 кг коштує 85 7ms
   → expected 100 to be 85 // Object.is equality
```

Перший приклад пройшов, бо `Math.ceil(0)` дає 0, і функція повернула 70. У другому прикладі `Math.ceil(1.9)` дає 2, тому
функція повернула 100, а приклад чекав 85. Цю помилку `tsc` не знайде, бо типи правильні, а неправильна лише логіка.
Сам Vitest, як і Vite, вирізає типи й не перевіряє їх.

Матчер `toBe` порівнює так, як `Object.is` (див. лекцію дня 1, розділ «Що порівнює `===`»). З цього випливають дві
пастки, і обидві видно в такому файлі:

```ts
// файл src/compare.test.ts
import { expect, test } from 'vitest'

const order = { city: 'Львів', kg: 3 }

test('toBe: однаковий вміст, але два різні об’єкти', () => {
  expect(order).toBe({ city: 'Львів', kg: 3 })
})

test('toEqual: порівнює вміст', () => {
  expect(order).toEqual({ city: 'Львів', kg: 3 })
})

test('toBe: дробові числа', () => {
  expect(0.1 + 0.2).toBe(0.3)
})

test('toBeCloseTo: дробові числа з допуском', () => {
  expect(0.1 + 0.2).toBeCloseTo(0.3)
})
```

Ось рядки виводу про чотири тести, без докладних звітів про кожну помилку, які Vitest друкує нижче:

```text
$ npx vitest run src/compare --reporter=verbose
 × src/compare.test.ts > toBe: однаковий вміст, але два різні об’єкти 7ms
   → expected { city: 'Львів', kg: 3 } to be { city: 'Львів', kg: 3 } // Object.is equality

If it should pass with deep equality, replace "toBe" with "toStrictEqual"

Expected: { city: 'Львів', kg: 3 }
Received: serializes to the same string

 ✓ src/compare.test.ts > toEqual: порівнює вміст 0ms
 × src/compare.test.ts > toBe: дробові числа 2ms
   → expected 0.30000000000000004 to be 0.3 // Object.is equality
 ✓ src/compare.test.ts > toBeCloseTo: дробові числа з допуском 0ms
```

Перший тест упав, хоча обидва об'єкти виглядають однаково: запис у фігурних дужках щоразу створює новий об'єкт, а
`Object.is` питає, чи це той самий об'єкт. Vitest навіть пише, що вміст збігається (`serializes to the same string`).
Матчер `toEqual` порівнює вміст, тому другий тест пройшов. Vitest радить ще й `toStrictEqual`: він теж порівнює вміст,
але суворіше. Наприклад, для нього `{ a: undefined, b: 2 }` і `{ b: 2 }` різні, а для `toEqual` однакові. Третій
тест упав, бо JavaScript зберігає дробові числа наближено, і сума `0.1 + 0.2` дорівнює 0.30000000000000004. Матчер
`toBeCloseTo` за замовчуванням порівнює лише дві цифри після коми, тому четвертий тест пройшов.

## Хто що ловить

Жоден інструмент не замінює решти.

| Помилка | Сервер Vite | `tsc -b` | ESLint | Vitest |
|---------|-------------|----------|--------|--------|
| рядок там, де обіцяно число | мовчить | `TS2322` | мовчить | лише якщо зламалася поведінка |
| не враховано `undefined` після `find` | мовчить | `TS18048` | мовчить | лише якщо приклад туди дійшов |
| хук під умовою | мовчить | мовчить | `rules-of-hooks` | лише якщо умова змінилася між рендерами |
| забута залежність ефекту | мовчить | мовчить | `exhaustive-deps` | рідко |
| неправильна формула ціни | мовчить | мовчить | мовчить | так, якщо є приклад |

## Чому не Create React App

У старих туторіалах проєкт створює команда `npx create-react-app`. Команда React оголосила цей інструмент застарілим у
лютому 2025 року. Причин дві: у нього немає активних супровідників, а кілька важливих задач він лишає вам. Серед цих
задач маршрути, тобто вибір екрана за адресою в рядку браузера, завантаження даних із сервера й розділення коду, тобто
завантаження частин застосунку лише тоді, коли вони знадобилися. Старий туторіал можна впізнати за пакетом
`react-scripts` і файлом `.eslintrc`. Такі поради не підходять до вашого проєкту, бо в ньому інші команди й інші
файли налаштувань.

## Типові хибні уявлення

**«`npx tsc --noEmit` нічого не надрукував, отже, помилок немає».** У цьому шаблоні головний `tsconfig.json` не
містить файлів, тому команда не перевірила нічого. Потрібен `tsc -b`.

**«Збірка пройшла, отже, лінт чистий».** Команда `npm run build` запускає `tsc` і Vite, а лінтер не запускає. Лінт це
окрема команда `npm run lint`.

**«Тест зелений, отже, правило хуків можна порушити».** Тест перевіряє один конкретний запуск. Правило стосується всіх
можливих рендерів, тому його стереже лінтер.

## Як це проявиться в React

- **Фаза 1, ефекти.** Майже кожна помилка з ефектами спершу виглядатиме як попередження `exhaustive-deps`. Пресет
  `recommended` містить ще правила `set-state-in-effect` і `refs`. Вони стежать за помилками, про які ви дізнаєтеся
  лише у фазі 1, тому спершу лінтер підкаже вам там, де ви ще не знаєте, що так не роблять.
- **Щодня під час роботи.** Гаряча заміна зберігає стан, поки ви правите розмітку. Якщо стан раптом скинувся,
  подивіться в термінал: рядок `page reload` означає, що оновлення не знайшло межі. Тоді перевірте дві речі. Перша: чи
  не змінили ви файл, над яким немає межі, як-от `src/main.tsx`. Друга: чи експортує змінений файл лише компоненти, бо
  інакше оновлення йде від нього вгору й може дійти до `src/main.tsx`.
- **Фаза 3 і фаза 5.** У фазі 3 ви писатимете у Vitest тести компонентів. У фазі 5 команди `tsc -b`, `npm run lint` і
  `vitest run` стануть кроками безперервної перевірки коду (CI).

## Перевірте себе

Спершу дайте відповідь самі, вголос або письмово, і лише потім розгортайте пояснення.

**1. Чому браузер не може виконати `import { useState } from 'react'` без Vite, навіть якщо `react` встановлено?**

<details><summary>Відповідь</summary>

Браузер працює лише з адресами, а `react` є голим вказівником, тобто назвою пакета без шляху. Теки `node_modules`
браузер не бачить. Крім того, сам React розповсюджується у форматі CommonJS, якого браузер не розуміє. Vite замінює
назву адресою `/node_modules/.vite/deps/react.js?v=...` і заздалегідь перепаковує пакет у модуль із `import` та
`export`.

</details>

**2. У файлі є `const age: number = "сорок"`. Що скажуть `npm run dev` і `npm run build`?**

<details><summary>Відповідь</summary>

`npm run dev` не скаже нічого: Vite вирізає `: number`, і браузер отримує рядок. `npm run build` виконує `tsc -b &&
vite build`, тому `tsc` друкує `TS2322` і завершується кодом 2, а `&&` не дає запуститися збірці.

</details>

**3. Ви змінили текст у `App.tsx`, і лічильник зберіг значення. Потім змінили `main.tsx`, і лічильник скинувся.
Чому?**

<details><summary>Відповідь</summary>

`App.tsx` приймає власні оновлення, бо плагін React дописав туди таку заяву. React Refresh викликає нову функцію в
старому дереві, де лежить стан. `main.tsx` нічого не заявляє, а вище за нього нікого немає, тому сервер надсилає
`full-reload`.

</details>

**4. Файл `Cart.tsx` експортує компонент `Cart` і функцію `total`. Що скаже лінтер і що станеться з гарячою заміною?**

<details><summary>Відповідь</summary>

Правило `react-refresh/only-export-components` повідомить про помилку на експорті `total`. React Refresh не вміє
замінювати звичайні функції, тому оновлення цього файла піде вгору й може закінчитися перезавантаженням сторінки.
Виправлення полягає в тому, щоб винести `total` в окремий файл.

</details>

**5. У компоненті три хуки, другий стоїть під умовою. Під час першого рендера умова істинна, під час другого хибна.
Який хук отримає чиє значення і що зробить React?**

<details><summary>Відповідь</summary>

Третій виклик стане другим і візьме комірку 1, тобто значення другого хука. Хуків стало менше, ніж минулого разу, тому
React зупиняє рендер помилкою `Rendered fewer hooks than expected`. Якщо умова не змінюється, React не помітить
нічого, тому це правило стереже лінтер.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| інструмент збірки | програма на кшталт Vite, яка поєднує сервер розробки й бандлер |
| попереднє пакування | склеювання пакета з `node_modules` в один модуль з `import` та `export` перед першим показом сторінки |
| `Cache-Control` | заголовок відповіді, який каже браузеру, як довго можна брати файл зі свого сховища |
| гаряча заміна, HMR | оновлення одного модуля в працюючій сторінці без її перезавантаження |
| межа гарячої заміни | модуль, який заявив викликом `import.meta.hot.accept`, що сам приймає оновлення |
| React Refresh, Fast Refresh | механізм, який замінює компонент, зберігаючи його стан |
| tree-shaking | викидання зі збірки коду, який ніхто не імпортує |
| відбиток умісту | короткий рядок у назві зібраного файла, який змінюється разом із умістом файла |
| режим `tsc -b` | перевірка, яка проходить посилання `references` і запам'ятовує результат |
| лінтер | програма, яка читає код без запуску й шукає порушення правил |
| пресет | готовий набір правил лінтера разом із їхньою суворістю |
| матчер | метод після `expect(...)`, який порівнює значення, наприклад `toBe` чи `toEqual` |
