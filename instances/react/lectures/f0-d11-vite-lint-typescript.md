# Лекція. День 11. Проєкт: Vite, лінт, TypeScript

Сьогодні починається ваш наскрізний проєкт, а свого коду в ньому майже немає. Лекція пояснює, навіщо потрібні п'ять
інструментів, які ви поставите, і яку саме помилку ловить кожен із них. Читання займе близько 45 хвилин. Весь вивід
нижче справжній: його отримано на Node 24, Vite 8.3, TypeScript 6.0, ESLint 10 і Vitest 5.

**Після лекції ви зможете пояснити:**

- чому браузер не може просто відкрити файл `.tsx` і що робить Vite, щоб він зміг;
- чому Vite у розробці не склеює файли, а для продакшну склеює;
- чому сторінка працює, хоча в коді є помилка типу, і хто цю помилку знайде;
- як гаряча заміна оновлює сторінку, не скидаючи стан, і коли цього не виходить;
- чому хук не можна класти в `if`, хоча тест часто проходить;
- яку помилку зловить `tsc`, яку ESLint, яку Vitest, а яку жоден із них.

## Чому браузер не може просто відкрити ваш код

Шаблон `react-ts` створює файл `src/main.tsx`. Це перший файл вашого застосунку:

```tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App.tsx'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

Якщо дати цей файл браузеру без змін, нічого не запрацює, і на це є три окремі причини.

**Перша причина: це не JavaScript.** Браузер виконує лише JavaScript. Теги на кшталт `<StrictMode>` усередині коду
належать до розширення мови, яке називається JSX, а знак оклику після `getElementById('root')` належить до TypeScript.
Браузер зупиниться на першому такому символі з помилкою синтаксису.

**Друга причина: браузер не знає, де лежить `react`.** Запис `from 'react'` містить назву пакета без шляху. Такий
запис називають голим специфікатором (англійською bare specifier). Node вміє шукати такі пакети в теці `node_modules`,
а браузер працює лише з адресами й сам ніякої теки на вашому диску не бачить.

**Третя причина: сам React написано в старому форматі модулів.** Ось увесь файл `node_modules/react/index.js`:

```js
'use strict';

if (process.env.NODE_ENV === 'production') {
  module.exports = require('./cjs/react.production.js');
} else {
  module.exports = require('./cjs/react.development.js');
}
```

Це формат CommonJS, у якому Node жив до появи `import` і `export`. У браузері немає ні `require`, ні `module`, ні
`process`.

Отже, між вашими файлами й браузером мусить стояти програма, яка перекладає код. Цю програму називають інструментом
збірки, і у вашому проєкті це Vite. Він виконує дві різні роботи:

| | Сервер розробки, `npm run dev` | Збірка, `npm run build` |
|---|---|---|
| Для кого | для вас, поки ви пишете код | для користувачів сайту |
| Коли перетворює файл | у мить, коли браузер його запитав | усі файли наперед, один раз |
| Що отримує браузер | багато окремих модулів | кілька склеєних і стиснутих файлів |

## Робота перша: сервер розробки віддає файли на вимогу

Простежимо за одним показом сторінки.

1. Ви запускаєте `npm run dev`. Сервер готовий приблизно за 0,2 секунди, бо він ще не перетворив жодного вашого файла.
2. Браузер запитує адресу `/` і отримує ваш `index.html`. У ньому стоїть рядок `<script type="module"
   src="/src/main.tsx">`. Атрибут `type="module"` каже браузеру, що скрипт є модулем, тобто файлом з `import` та
   `export`.
3. Браузер запитує `/src/main.tsx`. Лише тепер Vite читає цей файл із диска й перетворює його.
4. Браузер читає отриманий код, бачить у ньому `import` і робить новий запит на кожен із них. Так він обходить усі
   файли, від яких залежить сторінка.

Ось що стало з кожною незвичною частиною `main.tsx` у відповіді сервера:

| У файлі на диску | У відповіді сервера |
|------------------|---------------------|
| `from 'react-dom/client'` | `from "/node_modules/.vite/deps/react-dom_client.js?v=f44285fe"` |
| `from './App.tsx'` | `from "/src/App.tsx"` |
| `getElementById('root')!` | `getElementById("root")` |
| `<App />` | виклик функції `_jsxDEV(App, {}, ...)` |

Перша причина зникла, бо типи вирізано, а теги замінено викликами функцій. Друга причина зникла, бо голу назву
замінено справжньою адресою. Лишається третя, і саме для неї існує тека `node_modules/.vite/deps`.

**Попереднє пакування.** Під час першого запуску Vite бере кожен пакет, який ви імпортуєте, і склеює його в один
сучасний модуль. Так зникає CommonJS і зменшується кількість запитів: документація наводить пакет `lodash-es` із понад
600 внутрішніх модулів, який без пакування породив би понад 600 запитів. Ці файли браузер може зберігати цілий рік, а
коли версія пакета змінюється, змінюється хвіст `?v=...` в адресі, і браузер вважає її новим файлом.

**Вимір: що дає робота на вимогу.** Ми створили проєкт із 2000 крихітних файлів `.ts` і одним головним файлом, який
імпортує їх усі. Запити робив скрипт, який, як браузер на HTTP/1.1, тримає не більше шести запитів одночасно. Ваші
числа будуть іншими, важливе тут лише співвідношення.

| Дія | Час |
|-----|-----|
| запуск сервера розробки (порожній шаблон дає 214 мс) | 182 мс |
| усі 2000 модулів, перший обхід, кожен файл перетворюється вперше | 1800 мс |
| усі 2000 модулів, другий обхід, перетворення взято з кешу сервера | 563 мс |
| повна збірка того самого проєкту, `vite build` | 5900–8400 мс |

Запуск не залежить від розміру проєкту, бо сервер нічого не робить наперед. Якби сервер збирав усе наперед, як збірка,
ви чекали б кілька секунд ще до першого показу сторінки.

## Перетворення лише вирізає типи й нічого не перевіряє

Vite не перевіряє типи. Node 24 теж уміє вирізати типи з файла `.ts`, тому показати це можна без браузера:

```ts
// файл basket.ts
const basketKopecks: number = 120000
const deliveryKopecks: number = "5000"
console.log("до сплати:", basketKopecks + deliveryKopecks)
```

```text
$ node basket.ts
до сплати: 1200005000

$ npx tsc --noEmit --strict --target esnext basket.ts
basket.ts(2,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

Рядок 2 обіцяє число, а дає рядок. Програма, яка лише вирізає типи, прибирає `: number` і запускає те, що лишилося.
Далі JavaScript додає число до рядка, склеює їх і замість 1250 гривень отримує нісенітницю. Програма `tsc`, компілятор
TypeScript, знайшов помилку одразу, але нічого не запускав: прапорець `--noEmit` просить лише перевірити.

Vite працює так само, як `node` у цьому прикладі. Щоб перетворити один файл, досить прочитати цей файл, а щоб
перевірити типи, треба знати всі файли, від яких він залежить, і це повільно. Тому документація Vite лишає перевірку
редактору й окремій команді. У шаблоні ця команда вбудована в збірку:

```json
"build": "tsc -b && vite build"
```

Знак `&&` виконує другу команду, лише якщо перша завершилася без помилок. Тому `npm run dev` покаже сторінку з
помилкою типу, а `npm run build` зупиниться.

## Гаряча заміна: як змінити код, не втративши стан

Уявіть форму на п'ять кроків. На п'ятому кроці ви виправили підпис, і якщо сторінка перезавантажиться, доведеться
знову пройти всі кроки. Гаряча заміна (англійською Hot Module Replacement, HMR) розв'язує цю проблему: браузер отримує
лише новий варіант зміненого файла, а решта сторінки працює далі.

Сервер і браузер спілкуються через WebSocket, тобто постійне з'єднання, яким сервер може надсилати повідомлення сам.
Клієнт цього з'єднання, модуль `/@vite/client`, Vite дописує у вашу сторінку. Ми підключилися до того самого з'єднання
скриптом (його код є в розборі читання) і змінювали файли по одному:

| Що змінили | Повідомлення сервера | Рядок у терміналі | Що робить браузер |
|------------|----------------------|-------------------|-------------------|
| `src/App.tsx` | `update: js-update /src/App.tsx` | `hmr update /src/App.tsx` | довантажує новий модуль, а стан лишається |
| `src/App.css` | `update: js-update /src/App.css` | `hmr update /src/App.css` | замінює стиль на сторінці |
| `src/main.tsx` | `full-reload *` | `page reload src/main.tsx` | перезавантажує сторінку, а стан зникає |
| `index.html` | `full-reload /index.html` | `page reload index.html` | перезавантажує сторінку, а стан зникає |

**Чому файли поводяться по-різному.** Модуль може заявити, що вміє прийняти власне оновлення. У перетвореному
`App.tsx` таку заяву дописав плагін React. Документація називає такий модуль межею гарячої заміни (HMR boundary). Коли
змінюється файл, сервер іде від нього вгору через тих, хто його імпортує, і шукає найближчу межу. Файл `main.tsx`
стоїть на самому верху, нічого не заявляє, і йти далі нікуди, тому лишається повне перезавантаження.

**Чому стан не зникає.** Новий модуль містить нову функцію `App`. Частина плагіна під назвою React Refresh просить
React викликати нову функцію замість старої, але дерево компонентів не перебудовує. Стан лежить у цьому дереві, а не у
функції, тому `useState` повертає старе значення. Документація Fast Refresh (так називається той самий механізм)
уточнює межі: `useState` і `useRef` зберігають значення, якщо ви не змінили їхніх аргументів і порядку викликів хуків.
Заміна `useState(0)` на `useState(5)` скине стан, і це правильно, бо інакше ви не побачите нового початкового
значення.

**Чому файл має експортувати лише компоненти.** React Refresh замінює компоненти, а що робити зі звичайною функцією,
він не знає. Тому файл, який експортує і те, і те, гаряче не замінюється, і оновлення йде вгору. Шаблон стереже це
правилом лінтера `react-refresh/only-export-components`.

## Робота друга: збірка для користувачів

Окремі модулі не годяться для користувачів, бо про наступний модуль браузер дізнається лише тоді, коли прочитає
попередній, і кожен вкладений `import` означає ще один запит. Тому `vite build` читає `index.html`, проходить усі
імпорти наперед і робить чотири речі.

**Склеює модулі** в один чи кілька файлів, щоб запитів стало мало.

**Викидає те, що ніхто не використовує.** Цей крок називають tree-shaking, буквально «струшування дерева». Ми додали
файл з двома функціями й використали лише першу:

```ts
// файл src/money.ts
export function formatUah(kopecks: number): string {
  return `МАРКЕР-ПОТРІБНИЙ ${kopecks / 100} грн`
}

export function formatUsd(cents: number): string {
  return `МАРКЕР-ЗАЙВИЙ ${cents / 100} дол`
}
```

Після збірки `grep -c` знаходить у файлі `dist/assets/index-*.js` рядок `МАРКЕР-ПОТРІБНИЙ` один раз, а рядок
`МАРКЕР-ЗАЙВИЙ` жодного разу. Це можливо саме тому, що `import` та `export` записано в коді явно. Vite ще до запуску
бачить, що `formatUsd` ніхто не імпортує. У коді CommonJS такий висновок зробити значно важче, бо `require` можна
викликати як завгодно.

**Мінімізує код,** тобто переписує його коротше, не змінюючи поведінки. Функція `formatUah` у зібраному файлі стала
такою: `` function _(e){return`МАРКЕР-ПОТРІБНИЙ ${e/100} грн`} ``.

**Додає до назви файла відбиток умісту.** Коли ми змінили в `main.tsx` одне число, назви стали такими:

```text
до зміни      dist/assets/index-CsdsIcUz.js    dist/assets/index-D64VDMd1.css
після зміни   dist/assets/index-YmGmGrNu.js    dist/assets/index-D64VDMd1.css
```

Вміст JavaScript змінився, і змінилася його назва. Стилі лишилися тими самими, і назва теж лишилася. Завдяки цьому
сервер може дозволити браузеру зберігати такі файли назавжди: нова версія завжди матиме нову назву, а новий
`index.html` приведе браузер до неї. Що стоїть за числами збірки, ви виміряєте завтра.

## TypeScript: команда `tsc -b`, файл `tsconfig` і слово `strict`

**Три файли `tsconfig`.** Файл `tsconfig.app.json` описує код у `src`, який виконує браузер. Файл `tsconfig.node.json`
описує `vite.config.ts`, який виконує Node. Головний `tsconfig.json` містить лише `"files": []` і посилання на ці два
файли.

Звідси випливає типова помилка:

```text
# у src/wrong.ts написано: export const seats: number = "двадцять"

$ npx tsc --noEmit
(нічого не надруковано, код завершення 0)

$ npx tsc -b
src/wrong.ts(1,14): error TS2322: Type 'string' is not assignable to type 'number'.
(код завершення 2)
```

Без `-b` компілятор прочитав головний файл, не знайшов у ньому жодного файла з кодом і тому не побачив помилок.
Прапорець `-b` просить пройти посилання. Тому в цьому проєкті типи перевіряє `tsc -b` чи `npm run build`, а не проста
команда `tsc`.

**Що вмикає `strict`.** Це один прапорець, який вмикає цілу родину суворих перевірок. Ось одна з них на прикладі:

```ts
const shops = [{ city: "Львів", open: true }]
const shop = shops.find((s) => s.city === "Київ")
console.log(shop.open)
```

```text
$ npx tsc --noEmit --strict false --target esnext found.ts
(нічого не надруковано)

$ npx tsc --noEmit --strict --target esnext found.ts
found.ts(3,13): error TS18048: 'shop' is possibly 'undefined'.

$ node found.ts
TypeError: Cannot read properties of undefined (reading 'open')
```

Метод `find` повертає `undefined`, якщо нічого не знайшов. Перевірка `strictNullChecks` змушує вас врахувати цей
випадок, а без неї програма падає вже в користувача.

План згадує рядок `"strict": true`, але в шаблоні його немає: у TypeScript 6.0 значення `strict` стало `true` за
замовчуванням.

## ESLint: правила, яких не знає компілятор

Лінтер читає код, не запускаючи його. ESLint перетворює файл на дерево синтаксису, у якому видно, де функція, де
виклик, де умова, і передає це дерево правилам. Ось файл, у якому `tsc -b` не знаходить нічого, бо всі типи тут
правильні:

```tsx
import { useEffect, useState } from 'react'

type User = { id: number; name: string }

export function Profile({ user }: { user: User | null }) {
  if (user === null) return <p>Увійдіть</p>
  const [likes, setLikes] = useState(0)
  return <button onClick={() => setLikes(likes + 1)}>{user.name}: {likes}</button>
}

export function Clock({ city }: { city: string }) {
  const [text, setText] = useState('')
  useEffect(() => {
    const timer = setInterval(() => setText(`${city}: ${Date.now()}`), 1000)
    return () => clearInterval(timer)
  }, [])
  return <p>{text}</p>
}

export function Ticket() {
  const code = Math.random()
  return <p>{code}</p>
}
```

ESLint знаходить три проблеми (текст скорочено):

```text
 7:29  error    React Hook "useState" is called conditionally. ... Did you accidentally call a React Hook
                after an early return?                                     react-hooks/rules-of-hooks
16:6   warning  React Hook useEffect has a missing dependency: 'city'.     react-hooks/exhaustive-deps
21:16  error    Cannot call impure function during render                  react-hooks/purity

✖ 3 problems (2 errors, 1 warning)
(код завершення 1)
```

- **`rules-of-hooks`** помітило, що хук стоїть після раннього `return`. Для правила це така сама умова, як `if`
  навколо хука.
- **`exhaustive-deps`** помітило, що ефект читає `city`, а в масиві залежностей її немає. Коли `city` зміниться,
  годинник далі показуватиме стару назву міста, бо ефект не запуститься заново.
- **`purity`** належить до діагностики React Compiler. Компонент має при тих самих пропсах давати той самий результат,
  а `Math.random()` щоразу дає інший. Сам компілятор для цього вмикати не треба.

Число суворості визначає наслідки: `0` вимикає правило, `1` робить його попередженням і не змінює код завершення, `2`
робить його помилкою, і тоді лінтер завершується кодом 1.

**Чому хук не можна класти під умову.** Функція `useState` не отримує імені стану. React знає лише номер виклику:
перед кожним рендером він починає рахувати з нуля, а кожен виклик бере наступну комірку. Візьмемо компонент оформлення
замовлення:

```tsx
export function Checkout({ gift }: { gift: boolean }) {
  const [city] = useState('Львів')
  let note = ''
  if (gift) [note] = useState('з днем народження')
  const [count] = useState(1)
  return <p>{city} {note} {count}</p>
}
```

| Виклик | Перший рендер, `gift = true` | Другий рендер, `gift = false` |
|--------|------------------------------|-------------------------------|
| перший | комірка 0, місто | комірка 0, місто |
| другий | комірка 1, текст привітання | комірка 1, але це вже кількість: вона отримала б текст привітання |
| третій | комірка 2, кількість | виклику немає, комірка 2 лишилася без власника |

У цьому випадку React бачить, що хуків стало менше, і зупиняє рендер. Ми перевірили це в jsdom:

```text
перший рендер: Львів з днем народження 1
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

Але React скаржиться лише тоді, коли умова справді змінилася між рендерами. Якщо `gift` завжди `true`, тест проходить,
і помилка чекає на випадок, коли умова зміниться. Лінтер знаходить її одразу, бо читає код, а не запуск.

**Важливо: `create-vite` має вибір.** Поточний `create-vite` без додаткових прапорців ставить інший лінтер, Oxlint, і
файла `eslint.config.js` не створює. Команда зі сторінки дня містить `--eslint`, і саме завдяки цьому прапорцю в
проєкті з'являється пресет, тобто готовий набір правил, `recommended` пакета `eslint-plugin-react-hooks`.

## Prettier: форматування окремо від помилок

Prettier не шукає помилок. Він читає код і друкує його заново за єдиними правилами, щоб у команді не сперечатися про
пробіли. Сьогоднішні кроки Prettier не вимагають. Якщо ви його поставите, вимкніть у лінтері правила про форматування
пакетом `eslint-config-prettier`, як радить глава `Editor Setup`, інакше два інструменти сперечатимуться.

## Vitest: приклади стають перевірками

Рецепт із книжки How to Design Programs, за яким ви пишете функції, вимагає прикладів ще до коду. Досі ви перевіряли
їх через `assert`, а тепер їх запускає Vitest. Він читає той самий `vite.config.ts` і перетворює файли так само, як
Vite. Візьмемо функцію, яка рахує ціну доставки:

```ts
// файл delivery.ts
// Гривні: ціле число гривень. Кілограми: число, більше за нуль.

// deliveryPrice: number -> number
// Рахує ціну доставки: до 2 кг включно 70 гривень, а за кожен повний кілограм понад 2 кг ще 15.
export function deliveryPrice(kg: number): number {
  if (kg < 2) return 70
  return 70 + Math.ceil(kg - 2) * 15
}
```

```ts
// файл delivery.test.ts
import { expect, test } from 'vitest'
import { deliveryPrice } from './delivery'

test('рівно на межі: 2 кг коштує 70', () => {
  expect(deliveryPrice(2)).toBe(70)
})

test('неповний кілограм не рахується: 3,9 кг коштує 85', () => {
  expect(deliveryPrice(3.9)).toBe(85)
})
```

`test` оголошує один приклад: перший аргумент це назва, другий це функція з перевіркою. `expect(x).toBe(y)` кидає
помилку, якщо `x` не дорівнює `y`. У тілі функції ми навмисно написали `Math.ceil` замість `Math.floor`, і Vitest це
знайшов:

```text
 ✓ delivery.test.ts > рівно на межі: 2 кг коштує 70
 × delivery.test.ts > неповний кілограм не рахується: 3,9 кг коштує 85
   → expected 100 to be 85 // Object.is equality
```

Цю помилку `tsc` не знайде, бо типи правильні, а неправильна лише логіка. Сам Vitest, як і Vite, вирізає типи й не
перевіряє їх. Матчер `toBe` порівнює так, як `Object.is`, тому два однакові за вмістом об'єкти для нього різні, і для
об'єктів існує `toEqual`. З дробовими числами теж обережно: `expect(0.1 + 0.2).toBe(0.3)` падає з текстом `expected
0.30000000000000004 to be 0.3`, і для них існує `toBeCloseTo`.

## Хто що ловить

Жоден інструмент не замінює решти.

| Помилка | Сервер Vite | `tsc -b` | ESLint | Vitest |
|---------|-------------|----------|--------|--------|
| рядок там, де обіцяно число | мовчить | `TS2322` | мовчить | лише якщо зламалася поведінка |
| не враховано `undefined` після `find` | мовчить | `TS18048` | мовчить | лише якщо приклад туди дійшов |
| хук під умовою | мовчить | мовчить | `rules-of-hooks` | лише якщо умова змінилася між рендерами |
| забута залежність ефекту | мовчить | мовчить | `exhaustive-deps` | рідко |
| неправильна формула ціни | мовчить | мовчить | мовчить | так, якщо є приклад |

## Чому не Create React App

У старих туторіалах проєкт створює команда `npx create-react-app`. Команда React оголосила цей інструмент застарілим у
лютому 2025 року: у нього немає активних супровідників, а маршрути, завантаження даних і розділення коду він лишає
вам. Старий туторіал можна впізнати за пакетом `react-scripts` і файлом `.eslintrc`. Такі поради не підходять до
вашого проєкту, бо в ньому інші команди й інші файли налаштувань.

## Типові хибні уявлення

**«`npx tsc --noEmit` нічого не надрукував, отже, помилок немає».** У цьому шаблоні головний `tsconfig.json` не
містить файлів, тому команда не перевірила нічого. Потрібен `tsc -b`.

**«Збірка пройшла, отже, лінт чистий».** Команда `npm run build` запускає `tsc` і Vite, а лінтер не запускає. Лінт це
окрема команда `npm run lint`.

**«Тест зелений, отже, правило хуків можна порушити».** Тест перевіряє один конкретний запуск. Правило стосується всіх
можливих рендерів, тому його стереже лінтер.

## Як це проявиться в React

- **Фаза 1, ефекти.** Майже кожна помилка з ефектами спершу виглядатиме як попередження `exhaustive-deps`. Діагностика
  `set-state-in-effect` і `refs` підкаже вам там, де ви ще не знаєте, що так не роблять.
- **Щодня під час роботи.** Гаряча заміна зберігає стан, поки ви правите розмітку. Якщо стан раптом скинувся,
  подивіться в термінал: рядок `page reload` означає, що оновлення не знайшло межі, найчастіше через експорт не
  компонента.
- **Фаза 3 і фаза 5.** У фазі 3 ви писатимете у Vitest тести компонентів. У фазі 5 команди `tsc -b`, `npm run lint` і
  `vitest run` стануть кроками безперервної перевірки коду (CI).

## Перевірте себе

Спершу дайте відповідь самі, вголос або письмово, і лише потім розгортайте пояснення.

**1. Чому браузер не може виконати `import { useState } from 'react'` без Vite, навіть якщо `react` встановлено?**

<details><summary>Відповідь</summary>

Браузер працює лише з адресами, а `react` є назвою пакета без шляху. Папки `node_modules` браузер не бачить. Крім
того, сам React розповсюджується у форматі CommonJS, якого браузер не розуміє. Vite замінює назву адресою
`/node_modules/.vite/deps/react.js?v=...` і заздалегідь перепаковує пакет у модуль із `import` та `export`.

</details>

**2. У файлі є `const age: number = "сорок"`. Що скажуть `npm run dev` і `npm run build`?**

<details><summary>Відповідь</summary>

`npm run dev` не скаже нічого: Vite вирізає `: number`, і браузер отримує рядок. `npm run build` виконує `tsc -b &&
vite build`, тому `tsc` друкує `TS2322` і завершується кодом 2, а `&&` не дає запуститися збірці.

</details>

**3. Ви змінили текст у `App.tsx`, і лічильник зберіг значення. Потім змінили `main.tsx`, і лічильник скинувся.
Чому?**

<details><summary>Відповідь</summary>

`App.tsx` приймає власні оновлення, бо плагін React дописав туди таку заяву. React Refresh викликає нову функцію в
старому дереві, де лежить стан. `main.tsx` нічого не заявляє, а вище за нього нікого немає, тому сервер надсилає
`full-reload`.

</details>

**4. Файл `Cart.tsx` експортує компонент `Cart` і функцію `total`. Що скаже лінтер і що станеться з гарячою заміною?**

<details><summary>Відповідь</summary>

Правило `react-refresh/only-export-components` повідомить про помилку на експорті `total`. React Refresh не вміє
замінювати звичайні функції, тому оновлення цього файла піде вгору й може закінчитися перезавантаженням сторінки.
Виправлення полягає в тому, щоб винести `total` в окремий файл.

</details>

**5. У компоненті три хуки, другий стоїть під умовою. Під час першого рендера умова істинна, під час другого хибна.
Який хук отримає чиє значення і що зробить React?**

<details><summary>Відповідь</summary>

Третій виклик стане другим і візьме комірку 1, тобто значення другого хука. Хуків стало менше, ніж минулого разу, тому
React зупиняє рендер помилкою `Rendered fewer hooks than expected`. Якщо умова не змінюється, React не помітить
нічого, тому це правило стереже лінтер.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| інструмент збірки | програма, яка перетворює ваш код на те, що розуміє браузер, і готує його для користувачів |
| голий специфікатор | назва пакета в `import` без шляху, наприклад `'react'` |
| CommonJS | старий формат модулів Node з `require` і `module.exports` |
| попереднє пакування | склеювання пакета з `node_modules` в один сучасний модуль перед першим показом сторінки |
| гаряча заміна, HMR | оновлення одного модуля в працюючій сторінці без її перезавантаження |
| React Refresh, Fast Refresh | механізм, який замінює компонент, зберігаючи його стан |
| tree-shaking | викидання зі збірки коду, який ніхто не імпортує |
| лінтер | програма, яка читає код без запуску й шукає порушення правил |
