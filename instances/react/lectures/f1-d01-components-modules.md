# Лекція. Фаза 1, день 1. Компоненти й модулі

З цієї лекції починається сам React. Вона пояснює, що таке компонент, коли React його викликає, як розкласти
компоненти по файлах і чому компонент не можна оголошувати всередині іншого компонента. Читання займе близько 35
хвилин.

Усі приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Приклади
без React запущено на Node 24. Вивід під прикладами справжній. У справжньому браузері приклади не запускалися, тому
те, що стосується браузера, описано за документацією, і поруч сказано, де ви це побачите самі.

**Після лекції ви зможете пояснити:**

- чим компонент відрізняється від елемента, а елемент від вузла DOM;
- у якому порядку React викликає компоненти і куди при цьому йдуть дані;
- чому велика літера в назві змінює значення запису;
- що станеться, якщо переплутати типовий та іменований імпорт, і чому різні інструменти кажуть про це по-різному;
- як React вирішує, оновити компонент чи створити його заново;
- чому компонент, оголошений усередині іншого компонента, втрачає стан, і що робити замість цього.

## Сторінка, яку важко змінювати

Уявіть сторінку погоди. Для кожного міста на ній стоїть такий самий блок:

```html
<section>
  <h2>Львів</h2>
  <p>Вітер: 5 м/с</p>
  <p>Вологість: 62 %</p>
</section>
```

Коли міст стане тридцять, а замовник попросить виділити назву показника жирним, правити доведеться шістдесят рядків. У
лекції «DOM і події» ви будували вузли зі звичайного JavaScript. Повтор можна винести у функцію, але тоді всі подальші
зміни на екрані ви теж описуєте самі: знайти вузол, змінити текст, додати клас. Хотілося б один раз описати блок, дати
йому назву, вживати його як тег з різними даними, а про зміни в DOM не думати. Саме це дає React, і такий блок у ньому
називається компонентом.

## Компонент: функція, яка описує шматок екрана

**Компонент** — це звичайна функція JavaScript, назва якої починається з великої літери і яка повертає опис того, що
показати. Ось компонент для одного показника погоди:

```tsx
type ReadingProps = { label: string; value: string }

function Reading({ label, value }: ReadingProps) {
  return <p>{label}: {value}</p>
}
```

Тип `ReadingProps` описує дані, які компонент отримує. Запис `<p>{label}: {value}</p>` схожий на HTML, але це **JSX**:
запис усередині JavaScript, який описує розмітку, а фігурні дужки вставляють значення змінної. Докладно про JSX
розповість наступний день. Уживають компонент як тег:

```tsx
<Reading label="Вітер" value="5 м/с" />
```

Значення, які батьківський компонент передає дитині в такому тегу, називаються **пропсами** (англійською props). Для
цього запису React викличе `Reading` з одним аргументом, об'єктом усіх пропсів: `{ label: 'Вітер', value: '5 м/с' }`.
Запис `({ label, value }: ReadingProps)` дістає з цього об'єкта два поля, це звичайна деструктуризація.

Компоненти вкладаються один в одного так само, як теги:

```tsx
type StationProps = { city: string; wind: number; humidity: number }

function Station({ city, wind, humidity }: StationProps) {
  return (
    <section>
      <h2>{city}</h2>
      <Reading label="Вітер" value={`${wind} м/с`} />
      <Reading label="Вологість" value={`${humidity} %`} />
    </section>
  )
}

function WeatherPage() {
  return (
    <div>
      <Station city="Львів" wind={5} humidity={62} />
      <Station city="Одеса" wind={9} humidity={71} />
    </div>
  )
}
```

Тепер, щоб виділити назву показника жирним, треба змінити один рядок у `Reading`. `WeatherPage` тут **батько**
компонентів `Station`, а вони його **діти**. Круглі дужки після `return` потрібні, коли розмітка займає кілька рядків.
Чому без них код ламається, показано в розборі читання.

## Три різні речі: компонент, елемент і вузол DOM

Щоб зрозуміти головну помилку дня, ці три речі треба розрізняти. Подивімося, що лежить у змінних:

```tsx
let calls = 0

function Reading({ label, value }: ReadingProps) {
  calls = calls + 1
  return <p>{label}: {value}</p>
}

test('три різні речі', () => {
  const element = <Reading label="Вітер" value="5 м/с" />
  console.log('typeof element:', typeof element)
  console.log('element.type === Reading:', element.type === Reading)
  console.log('element.props:', element.props)
  console.log('викликів Reading до render:', calls)

  const { container } = render(element)
  console.log('викликів Reading після render:', calls)
  console.log('вузол:', container.firstChild?.nodeName, '|', container.innerHTML)
})
```

```text
typeof element: object
element.type === Reading: true
element.props: { label: 'Вітер', value: '5 м/с' }
викликів Reading до render: 0
викликів Reading після render: 1
вузол: P | <p>Вітер: 5 м/с</p>
```

Запис із тегом не викликав функцію. Він лише створив простий об'єкт, у полі `type` якого лежить сама функція
`Reading`, а в полі `props` лежать пропси. Такий об'єкт називають **елементом**. Функцію викликав React, коли `render`
із бібліотеки Testing Library попросив його показати елемент у документі. Лише після цього з'явився вузол DOM.

| Що це | Приклад | Хто створює |
|-------|---------|-------------|
| компонент | функція `Reading` | ви, у коді, один раз |
| елемент | об'єкт із `type` і `props` | запис `<Reading … />`, щоразу, коли він виконується |
| вузол DOM | тег `<p>` у документі | React через DOM браузера |

Звідси випливає правило: компонент уживають як тег і не викликають як функцію. Після виклику `Reading({ … })` у вас у
руках лише елемент із `type: 'p'`, і React не знає, що тут був компонент. Тому він не зможе дати цьому компонентові
власний стан і сам вирішувати, коли його викликати.

## Рендер: хто кого викликає

**Рендером** React називає виклик функції компонента, щоб дізнатися, що показати. Не плутайте це слово з рендерингом у
браузері з лекції «Як браузер малює»: там браузер перетворює сторінку на пікселі. Додамо в кожен компонент прикладу
про погоду по одному `console.log` і виконаємо `render(<WeatherPage />)`:

```text
елемент створено
WeatherPage
  Station Львів
    Reading Вітер
    Reading Вологість
  Station Одеса
    Reading Вітер
    Reading Вологість
```

Сім викликів складаються з однієї сторінки, двох міст і чотирьох показників: для кожного тега React робить окремий
виклик. З виводу видно ще дві речі.

**Порядок задано вкладеністю.** React викликає `WeatherPage` і отримує два елементи `Station`. Далі він викликає
`Station` для Львова й обидва його `Reading`, а вже потім переходить до Одеси. Батько завжди викликається раніше за
дітей, бо діти стають відомі лише з того, що батько повернув.

**Дані йдуть згори вниз.** `Reading` не бачить ні `wind`, ні `Station`, ні `WeatherPage`. Він знає лише те, що батько
передав йому в пропсах. Якщо дитині щось потрібно від батька, батько передає це пропсом.

Одне застереження про перегляд у браузері. Шаблон проєкту загортає застосунок у `<StrictMode>`, а цей компонент у
режимі розробки навмисно викликає кожен компонент двічі, щоб виявити певні помилки. Тому під час `npm run dev` ви
можете побачити кожен `console.log` двічі. У нашому досліді під `<StrictMode>` один `render` теж дав два рядки.
Докладно про це розповідає день 5 цієї фази.

## Велика літера вирішує, що це

Напишемо той самий тег з малої літери:

```tsx
const bad = <reading label="Вітер" value="5 м/с" />
console.log('type з малої:', typeof bad.type, bad.type)
console.log(render(bad).container.innerHTML)
```

```text
type з малої: string reading
<reading label="Вітер" value="5 м/с"></reading>
```

Компілятор JSX дивиться на першу літеру. Запис із малої літери він вважає тегом HTML і кладе в `type` рядок
`'reading'`. Запис із великої літери він вважає змінною з таким іменем і кладе в `type` те, що в ній лежить. Тому
`<section>` працює як тег, а `<Station>` працює як компонент.

Запис із малої літери не зупиняє програму: у документі з'являється невідомий браузеру елемент, а вашого тексту немає.
Попередити про це можуть двоє. React у режимі розробки пише в консоль
`The tag <reading> is unrecognized in this browser`, і під jsdom ми цей рядок побачили. TypeScript не пропускає такий
запис ще до запуску: `error TS2339: Property 'reading' does not exist on type 'JSX.IntrinsicElements'.`

## Файли: компонент у своєму модулі

Коли компонентів стає багато, їх розкладають по файлах. Механізм ви вже знаєте з лекції «Модулі й пакети»: файл
показує назовні лише те, що експортує, а інший файл бере це через `import`. React нічого до цього не додає.

Типовий експорт (`export default function Title`) у файлі може бути один, його беруть без дужок і під будь-яким
іменем: `import Title from './Title'`. Іменованих експортів (`export function Note`) може бути скільки завгодно, їх
беруть у дужках і під тим самим іменем: `import { Note } from './Note'`.

Сторінка React радить типовий експорт, коли файл віддає один компонент, а іменовані, коли компонентів чи значень
кілька. Компонент без `export` лишається приватним для файла. Застосунок починається з **кореневого компонента**: у
шаблоні Vite це `App` у файлі `src/App.tsx`, а файл `src/main.tsx` просить React показати його на сторінці.

Найцікавіше тут те, як поводяться інструменти, коли ви переплутали вид імпорту. Візьмемо такий файл:

```tsx
// файл parts.tsx
export default function Title({ text }: { text: string }) {
  return <h2>{text}</h2>
}
export function Note({ text }: { text: string }) {
  return <p>{text}</p>
}
```

Ось дві помилки й те, що каже про них кожен інструмент. Node ми перевірили на такому самому файлі `.mjs`.

| Запис | `tsc` | Node | Vitest |
|-------|-------|------|--------|
| `import { Title } from './parts'` | `TS2614: … has no exported member 'Title'` | `SyntaxError: … does not provide an export named …` | `Title` дорівнює `undefined`, React пише `Element type is invalid … but got: undefined` |
| `import Note from './parts'` | `TS2322`, лише якщо пропси не збігаються | помилки немає | помилки немає, а `<Note text="Сьогодні дощ" />` показує `<h2>Сьогодні дощ</h2>` |

**Запис `import Note from './parts'` небезпечний.** Ім'я при типовому імпорті довільне, тому змінна `Note` насправді
містить `Title`. Запуск не впаде. Пропси в цих двох компонентів збіглися, тому `tsc` теж мовчить, і помилку знайде
лише приклад, який шукає на сторінці правильний тег.

**Одна помилка виглядає по-різному.** Node зупиняє модуль ще до запуску, бо імпорт зв'язується з експортом під час
завантаження. За специфікацією так само чинить браузер, тому під час `npm run dev` у консолі буде `SyntaxError`, хоча
її текст залежить від браузера. Vitest запускає код через власний завантажувач, який перетворює імпорт на читання поля
об'єкта-модуля, а читання відсутнього поля дає `undefined`. Тому в тестах повідомлення приходить від React. Коли
бачите `got: undefined`, насамперед перевірте рядок `import`.

Тип імпортують окремо, зі словом `type`. Причину пояснює лекція «Проєкт: Vite, лінт, TypeScript».

## Стан: пам'ять компонента

Щоб зрозуміти головну помилку дня, потрібне ще одне поняття. Докладно його вивчає день 7 цієї фази. Ось термостат,
який пам'ятає температуру:

```tsx
function Thermostat() {
  const [degrees, setDegrees] = useState(20)
  return <button onClick={() => setDegrees(degrees + 1)}>Температура: {degrees}</button>
}
```

Локальна змінна функції зникає, коли функція завершилася. Тому значення, яке має дожити до наступного виклику,
зберігає сам React. Таке значення називається **станом**. Виклик `useState(20)` просить React зберегти значення для
цього компонента й повертає пару: поточне значення й функцію, яка його змінює. Число `20` враховується лише під час
першого показу. Такі функції React, назва яких починається з `use`, називають **хуками**. Виклик `setDegrees(21)`
записує нове значення і просить React викликати компонент ще раз, тобто перемалювати його.

React зберігає стан не у функції. Він будує власне дерево компонентів, що зараз на екрані, і прив'язує стан до місця в
цьому дереві. Запис про компонент на конкретному місці разом зі станом і вузлами називають **екземпляром**.

## Як React вирішує: оновити чи створити заново

Після кожного рендеру React порівнює нове дерево елементів зі старим, місце за місцем. На кожному місці він порівнює
старе значення поля `type` з новим через `===`:

| Порівняння `type` | Що робить React | Що зі станом і вузлами |
|-------------------|-----------------|------------------------|
| рівні | оновлює наявний екземпляр новими пропсами | стан і вузли зберігаються |
| різні | **знімає** старий екземпляр і **монтує** новий | старий стан і вузли зникають, новий стан починається з початкового значення |

**Монтувати** означає вперше створити екземпляр і поставити його вузли в документ, а **знімати** означає прибрати їх
звідти разом зі станом.

Для тегів HTML у `type` лежить рядок, і `'div'` завжди дорівнює `'div'`. Для компонентів у `type` лежить функція.
Функції порівнюються за посиланням, як об'єкти в лекції «Значення й посилання». Подивімося на функції, створені в
різних викликах:

```js
function makeInner() {
  function inner() {
    return 42
  }
  return inner
}

const first = makeInner()
const second = makeInner()
console.log(first === second)
console.log(first.toString() === second.toString())
console.log(first() === second())
```

```text
false
true
true
```

Код однаковий, результат однаковий, а функції різні. Кожен виклик `makeInner` виконує оголошення `function inner` і
створює новий об'єкт функції, як пояснювала лекція «Функції та замикання».

## Компонент усередині компонента

Кімната має світло, а термостат оголошено всередині кімнати:

```tsx
function Room() {
  const [lights, setLights] = useState(false)

  function Thermostat() {                       // оголошено всередині Room
    const [degrees, setDegrees] = useState(20)
    console.log('Thermostat:', degrees)
    return <button onClick={() => setDegrees(degrees + 1)}>Температура: {degrees}</button>
  }

  return (
    <div>
      <Thermostat />
      <button onClick={() => setLights(!lights)}>Світло: {lights ? 'так' : 'ні'}</button>
    </div>
  )
}
```

Тест натискає кнопку термостата тричі, а потім кнопку світла. Другий варіант відрізняється лише одним: функцію
`Thermostat` перенесено над `Room`, на рівень файла. Обидва варіанти спершу друкують `Thermostat: 20`, `21`, `22` і
`23`. Після натискання на світло вони розходяться:

```text
Усередині Room:
Thermostat: 20
після світла: Температура: 20
той самий вузол: false | старий у документі: false

Над Room:
Thermostat: 23
після світла: Температура: 23
той самий вузол: true | старий у документі: true
```

Пройдемо перший варіант кроками. Функцію `Thermostat`, створену першим викликом `Room`, позначимо `T1`, а створену
другим викликом позначимо `T2`.

| Подія | Хто викликаний | `type` на місці термостата | Рішення React | `degrees` |
|-------|----------------|----------------------------|---------------|-----------|
| перший показ | `Room`, потім `T1` | `T1` | монтує | 20 |
| три натискання на термостат | щоразу лише `T1`, бо змінився її стан | `T1` | оновлює | 21, 22, 23 |
| натискання на світло | `Room`, бо змінився її стан, потім `T2` | `T2`, а `T1 === T2` дає `false` | знімає `T1` разом із числом 23 і кнопкою, монтує `T2` | 20 |

Поки ви натискаєте термостат, `Room` не викликається і нової функції не створює, тому здається, що все добре. Помилка
проявляється лише тоді, коли перемальовується батько. Кнопка світла не змінювала `degrees`: вона замінила цілий
компонент, і значення зникло разом із ним. У другому варіанті `Thermostat` теж викликано ще раз, бо батько
перемальовує дітей, але `type` лишився тим самим, тому стан збережено. Перемалювати й створити заново — різні речі.

Документація React прямо каже про цей випадок: «This is why you should not nest component function definitions». Вона
попереджає, що такий код повільний і веде до помилок. Повільний він тому, що при кожному рендері батька React видаляє
й будує заново всі вузли під цією дитиною.

### Навіщо так пишуть і як це виправити

Компонент оголошують усередині іншого найчастіше заради зручності: так дитина бачить змінні батька без пропсів. Ось
випадок із найпомітнішим симптомом:

```tsx
function Catalog() {
  const [query, setQuery] = useState('')

  function SearchBox() {                        // хочеться читати query без пропсів
    return <input aria-label="Пошук" value={query} onChange={(e) => setQuery(e.target.value)} />
  }

  return <div><SearchBox /><p>Шукаємо: {query}</p></div>
}
```

Тест набирає `кава`, а в полі лишається лише `к`, і фокус клавіатури стоїть на `BODY`. Перша літера змінила стан
батька, батько створив нову функцію `SearchBox`, а React зняв старе поле разом із фокусом. Решта літер нікуди не
потрапила. У браузері той самий механізм означає, що після кожної літери поле доведеться клацати знову.

Виправлення завжди одне: оголосити компонент на рівні файла, а потрібне від батька передати пропсами. Тоді той самий
тест дає `кава`, і фокус лишається на `INPUT`:

```tsx
type SearchBoxProps = { query: string; onQueryChange: (text: string) => void }

function SearchBox({ query, onQueryChange }: SearchBoxProps) {
  return <input aria-label="Пошук" value={query} onChange={(e) => onQueryChange(e.target.value)} />
}

function Catalog() {
  const [query, setQuery] = useState('')
  return <div><SearchBox query={query} onQueryChange={setQuery} /><p>Шукаємо: {query}</p></div>
}
```

### Хто ловить цю помилку

React під час роботи не кидає помилки й нічого не пише в консоль, бо для нього `<Thermostat />` лише об'єкт, а де
створено функцію з поля `type`, він не перевіряє. Ловить цю помилку лінтер з лекції «Проєкт: Vite, лінт, TypeScript».
Правило `react-hooks/static-components` входить у пресет `recommended`, і ось його вивід для коду з кімнатою,
скорочений:

```text
  18:8  error  Error: Cannot create components during render

Components created during render will reset their state each time they are created. Declare components outside of render.
```

Рядок 18 — це `<Thermostat />`. Лінтер вказує насамперед на місце, де компонент **використано**, а оголошення показує
нижче як друге місце.

### Що всередині компонента оголошувати можна

Заборона стосується тільки функцій, які ви вживаєте як тег. Лінтер не скаржиться на цей код, а тест показує, що стан
термостата зберігся після натискання на світло:

```tsx
function Room() {
  const [lights, setLights] = useState(false)
  function caption() {                          // допоміжна функція: її викликають, а не малюють як тег
    return lights ? 'так' : 'ні'
  }
  return <div><Thermostat /><button onClick={() => setLights(!lights)}>Світло: {caption()}</button></div>
}
```

Функція `caption` і стрілкова функція в `onClick` теж нові при кожному рендері, але вони ніколи не потрапляють у поле
`type`, тому React їх не порівнює.

## Рецепт: компонент проєктують як функцію

З фази 0 ви знаєте рецепт із книжки How to Design Programs. Компонент — це функція, тому рецепт працює без змін. Опис
даних — це тип пропсів, сигнатура — параметр із типом у коді, призначення — речення в коментарі над функцією, заглушка
— `return null`, тобто компонент, який нічого не показує. Приклади пишуть до тіла. Покажемо це на компоненті
`Reading`:

```tsx
// файл Reading.tsx
type ReadingProps = { label: string; value: string }

// Показує один показник погоди абзацом «назва: значення».
export function Reading({ label, value }: ReadingProps) {
  // Є: label — назва показника, value — готовий текст значення.
  return null
}

// файл examples.test.tsx
test('Reading: показує назву й значення', () => {
  render(<Reading label="Вітер" value="5 м/с" />)
  expect(screen.getByText('Вітер: 5 м/с')).toBeInTheDocument()
})
```

Приклад для компонента показує компонент у документі й шукає те, що побачив би користувач. Об'єкт `screen` з
бібліотеки Testing Library шукає по всій сторінці, `getByText` знаходить вузол із таким текстом, а `toBeInTheDocument`
перевіряє, що вузол стоїть у документі. Поки стоїть заглушка, приклад падає:

```text
TestingLibraryElementError: Unable to find an element with the text: Вітер: 5 м/с. …
<body>
  <div />
</body>
```

Цей знімок розмітки під помилкою читайте першим, бо він показує, що насправді є на сторінці. Коли замість
`return null` стоїть розмітка, приклад проходить. Запит `getByRole` і функцію `within` докладно пояснює розбір
читання.

## Типові хибні уявлення

**«Батько перемалювався, отже, діти створилися заново».** Діти справді викликаються ще раз, але React створює
екземпляр заново лише тоді, коли змінився `type`. У варіанті з `Thermostat` над `Room` тіло компонента виконалося, а
число 23 лишилося.

**«Стан зникає, бо `useState` скидається під час рендеру батька».** Хук нічого не скидає. Стан зникає, бо React зняв
екземпляр, якому стан належав. Вузол DOM зникає разом із ним, тому текст у полі без жодного `useState` теж пропаде.

**«Функції всередині компонента оголошувати не можна».** Не можна лише компоненти, тобто функції, які вживають як тег.
Обробники подій і допоміжні функції всередині компонента звичайні й потрібні.

**«Вкладати компоненти не можна».** Вкладати можна й потрібно **вживання**: `<Station>` у розмітці `WeatherPage`.
Заборонено вкладати **оголошення**: `function Station` усередині `function WeatherPage`.

## Як це проявиться далі в React

- **День 4, списки й ключі.** Ключ `key` доповнює порівняння за місцем і типом, коли елементи стоять у списку.
- **День 5, чистота й дерево.** Ви побачите `<StrictMode>` і дізнаєтеся, чому рендер не повинен нічого змінювати
  назовні.
- **День 12, спільний стан і скидання стану.** Правило про місце й тип стане інструментом: ви навмисно скидатимете
  стан.

## Перевірте себе

**1. На сторінці `Station` ужито три рази, а в кожному `Station` по два `Reading`. Скільки викликів зробить React під
час першого показу разом зі сторінкою?**

<details><summary>Відповідь</summary>

Десять: один виклик сторінки, три виклики `Station` і шість викликів `Reading`.

</details>

**2. Файл експортує `export default function Title` і `export function Note`. Що потрапить у змінну після
`import Note from './parts'`?**

<details><summary>Відповідь</summary>

Типовий експорт, тобто `Title`. Ім'я при типовому імпорті довільне, тому помилки під час запуску не буде. Помітити її
можуть `tsc`, якщо пропси не збігаються, або приклад, який шукає на сторінці правильний тег.

</details>

**3. Той самий хибний імпорт `import { Title } from './parts'` у Node дає `SyntaxError`, а у Vitest дає повідомлення
React про `undefined`. Чому?**

<details><summary>Відповідь</summary>

Node зв'язує імпорти з експортами під час завантаження й зупиняється, якщо експорту немає. Vitest перетворює імпорт на
читання поля об'єкта-модуля. Відсутнє поле дає `undefined`, а React отримує `undefined` замість компонента й
повідомляє про це.

</details>

**4. У прикладі з кімнатою натискання на термостат не скидає число, а натискання на світло скидає. Поясніть різницю.**

<details><summary>Відповідь</summary>

Термостат має власний стан, тому після його зміни React викликає лише функцію термостата, і нова функція не
створюється. Кнопка світла змінює стан кімнати, тому React викликає `Room`. Тіло `Room` створює нову функцію
`Thermostat`, і на тому самому місці стоїть інший `type`. React знімає старий екземпляр зі станом і монтує новий.

</details>

**5. Усередині компонента оголошено функцію `formatDate` і її викликають як `{formatDate(day)}`. Це та сама помилка?**

<details><summary>Відповідь</summary>

Ні. Функцію викликано як звичайну, її результат стає частиною розмітки, а в поле `type` вона не потрапляє. React її не
порівнює, і лінтер не скаржиться.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| компонент | функція з великою літерою в назві, яка повертає опис того, що показати |
| проп (prop) | значення, яке батько передає дитині; усі пропси приходять одним об'єктом |
| елемент | простий об'єкт із полями `type` і `props`, який описує, що показати |
| рендер | виклик функції компонента, щоб дізнатися, що показати |
| стан | значення, яке React зберігає для компонента між рендерами |
| хук | функція React із назвою на `use`, наприклад `useState` |
| екземпляр | запис React про компонент на конкретному місці дерева разом зі станом |
