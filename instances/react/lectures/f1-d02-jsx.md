# Лекція. Фаза 1, день 2. JSX

Учора ви писали компоненти, а запис усередині `return` приймали на віру. Ця лекція пояснює, що це за запис, у що він
перетворюється до запуску, звідки беруться його правила і чому він сам захищає сторінку від чужого коду в даних
користувача. Читання займе близько 40 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Перетворення
коду запущено на Node 24 і Vite 8.3. Вивід під прикладами справжній. У справжньому браузері приклади не запускалися,
тому в кожному місці, де йдеться про браузер, сказано, на чому це твердження тримається.

**Після лекції ви зможете пояснити:**

- у що перетворюється тег JSX і хто це робить;
- чому кожне правило JSX є наслідком того, що тег стає викликом функції;
- що можна написати у фігурних дужках, а що не можна, і чому;
- що React показує для рядка, числа, `false`, `null` і об'єкта у фігурних дужках;
- чому рядок із тегами, вставлений через `{}`, не стає розміткою;
- якими трьома способами цей захист можна обійти;
- яку помилку ловить компілятор, яку `tsc`, а яку лише React під час роботи.

## Розмітка, яку не вдалося просто вставити

Ви робите меню кав'ярні, і дизайнер надсилає вам шматок HTML для одного напою:

```html
<dt class="drink" style="color: gray">Лате</dt>
<dd>
  <label for="qty">Кількість</label>
  <input id="qty" readonly value="1">
</dd>
```

Для браузера це правильний HTML. Ви вставляєте його в `return` компонента, і компілятор відмовляє. Ви виправляєте
першу помилку, і він відмовляє знову. Коли код нарешті запускається, React пише в консоль про `class` і `for`, а
сторінка падає через `style`. Якщо дивитися на ці розбіжності як на список, вони здаються примхами. Насправді в них
одна причина, і нижче ми її знайдемо.

Спершу подивимося, навіщо цей запис узагалі потрібен. З лекції «DOM і події» ви знаєте два способи збудувати вузли зі
звичайного JavaScript:

```js
// Перший спосіб: рядок із HTML. Коротко, але рядок drink.name браузер теж прочитає як HTML.
list.innerHTML = `<dt class="drink">${drink.name}</dt>`

// Другий спосіб: окремі виклики. Вміст тут завжди лишається текстом, але коду багато.
const dt = document.createElement('dt')
dt.className = 'drink'
dt.textContent = drink.name
list.append(dt)
```

Перший спосіб зручний і небезпечний, а другий безпечний і довгий. JSX пишеться майже так само коротко, як перший, а
працює так само безпечно, як другий.

## Що відбувається з тегом до запуску

Браузер не розуміє JSX. Тому перед тим, як код потрапить у браузер, його обробляє **компілятор**, тобто програма, яка
перетворює один текст програми на інший. У вашому проєкті це робить Vite функцією `transformWithOxc`. Дамо їй кілька
записів і подивимося на результат:

```js
// файл compile.mjs
import { transformWithOxc } from 'vite'
const source = `
export const row = <li className="drink">{name}: {price} грн</li>
export const pair = <><dt>Кава</dt><dd>25 грн</dd></>
export const badge = <Badge text="Немає" />
export const off = <button disabled>Купити</button>
`
const { code } = await transformWithOxc(source, 'menu.jsx', { jsx: { runtime: 'automatic' } })
console.log(code)
```

```text
$ node compile.mjs
import { jsxs as _jsxs, jsx as _jsx, Fragment as _Fragment } from "react/jsx-runtime";
export const row = /* @__PURE__ */ _jsxs("li", {
	className: "drink",
	children: [
		name,
		": ",
		price,
		" грн"
	]
});
export const pair = /* @__PURE__ */ _jsxs(_Fragment, { children: [/* @__PURE__ */ _jsx("dt", { children: "Кава" }), /* @__PURE__ */ _jsx("dd", { children: "25 грн" })] });
export const badge = /* @__PURE__ */ _jsx(Badge, { text: "Немає" });
export const off = /* @__PURE__ */ _jsx("button", {
	disabled: true,
	children: "Купити"
});
```

Жодного тега не лишилося. Кожен тег став викликом функції, і ось що в цих викликах стоїть.

**Перший аргумент — що показати.** Для тега з малої літери це рядок `"li"`, для тега з великої літери це змінна
`Badge`, а для порожніх дужок `<>…</>` це спеціальне значення `_Fragment`. Про різницю між малою й великою літерою
розповідала лекція «Компоненти й модулі».

**Другий аргумент — об'єкт пропсів.** Атрибути стали полями цього об'єкта. Запис `disabled` без значення став
`disabled: true`.

**Вкладене лежить у полі `children`.** Текст і вирази між тегами стають значенням цього поля, а якщо дітей кілька, то
масивом. Запис `{name}` перенесено як є: у масиві стоїть змінна `name`, а її значення компілятор не знає й не
дізнається, бо значення з'явиться лише під час роботи програми.

**Функції імпортує сам компілятор.** Перший рядок виводу додав він, тому у своїх файлах ви не пишете імпорт для JSX.
Функція `jsx` створює елемент з однією дитиною або без дітей, а `jsxs` створює елемент із кількома дітьми.
Підкреслення в `_jsx` означає лише те, що функцію імпортовано під іншим іменем.

Кожен такий виклик повертає **елемент**, тобто простий об'єкт із полями `type` і `props`, який ви вже бачили в лекції
«Компоненти й модулі». Отже, JSX є виразом JavaScript, як `2 + 2` чи `f(x)`. Його можна покласти в змінну, передати у
функцію або повернути з функції.

### Режим розробки

Сервер розробки просить компілятор про докладніший варіант. Ось той самий тег із параметром `development: true`:

```text
var _jsxFileName = "menu.jsx";
import { jsxDEV as _jsxDEV } from "react/jsx-dev-runtime";
export const off = /* @__PURE__ */ _jsxDEV("button", {
	disabled: true,
	children: "Купити"
}, void 0, false, {
	fileName: _jsxFileName,
	lineNumber: 1,
	columnNumber: 20
}, this);
```

Тепер викликається `jsxDEV`, а після пропсів ідуть службові аргументи. Запис `void 0` дає `undefined`, тобто ключа
немає, а про ключі розповість день 4. Значення `false` каже, що дітей не кілька. Об'єкт із `fileName` і `lineNumber`
вказує, де в коді стояв тег, і завдяки йому повідомлення React показують ваш рядок.

Сьогоднішня практика просить знайти такі виклики у вкладці «Мережа». У браузері ми цього не робили. Ми запитали сервер
розробки тією самою адресою модуля командою `curl`, і відповідь справді містить виклики `_jsxDEV(`. На початку
відповіді стоїть рядок із `createHotContext`, а наприкінці стоїть `$RefreshReg$`. Ці рядки потрібні для гарячої заміни
з лекції «Проєкт: Vite, лінт, TypeScript», а не для JSX. План дня пише `jsxDEV`, а у файлі ви побачите `_jsxDEV`: це
та сама функція під іменем, яке дав їй рядок імпорту.

## Правила випливають із цього

Тепер повернемося до розмітки дизайнера й розберемо кожну розбіжність.

### Один кореневий елемент

Два сусідні теги після `return` стали б двома викликами функцій поруч. Запис `return f() g()` не має сенсу, бо функція
повертає одне значення. Компілятор відмовляє: `Adjacent JSX elements must be wrapped in an enclosing tag`.

Їх можна загорнути в `<div>`, але тоді в документі з'явиться зайвий вузол, а HTML дозволяє не всяку вкладеність. Ось
компонент, який повертає комірку таблиці, загорнуту в `<div>`, усередині рядка `<tr>`. Серед іншого React пише таке:

```text
In HTML, <td> cannot be a child of <div>.
In HTML, <div> cannot be a child of <tr>.
```

Це попередження React ми отримали під jsdom. Для таких випадків існує **фрагмент** `<>…</>`. Він об'єднує елементи в
один виклик, а в документі не лишає нічого:

```tsx
const { container } = render(<><dt>Кава</dt><dd>25 грн</dd></>)
console.log(container.innerHTML, container.children.length)
```

```text
<dt>Кава</dt><dd>25 грн</dd> 2
```

Функція могла б повернути й масив, але елементи масиву потребують ключів, про які розповість день 4.

### Кожен тег закритий

HTML-парсер браузера знає, що `<img>` завжди порожній, а наступний `<li>` закриває попередній. Компілятор JSX не знає
про теги нічого: для нього це просто імена. Він мусить бачити межі кожного тега, щоб скласти виклик, тому запис
`<ul><li>Кава<li>Чай</ul>` дає помилку `Expected corresponding JSX closing tag for 'li'`.

Закрити себе в JSX може будь-який тег. Запис `<div className="fill" />` означає порожній `<div>`. В HTML такий запис
означав би незакритий `<div>`, тому розмітку не можна переносити назад так само механічно. У зворотному напрямку теж є
межа: `<img>` не може мати дітей, і спроба їх передати дає помилку React під час показу: `img is a void element tag
and must neither have children nor use dangerouslySetInnerHTML`.

### Назви атрибутів

Атрибути стають полями об'єкта, а компонент зазвичай читає ці поля в змінні. Назва змінної не може містити дефіс або
бути службовим словом мови. Подивіться, де саме проходить межа:

```js
const props = { class: 'drink', for: 'qty' }
console.log(props.class, props.for)
try { new Function("const { class } = {}") } catch (e) { console.log(e.name + ':', e.message) }
```

```text
drink qty
SyntaxError: Unexpected token 'class'
```

Як поле об'єкта слово `class` дозволене, а як змінна заборонене. Тому компілятор запис `<p class="a" />` пропускає, і
помилку ловлять уже інші інструменти. Назви в JSX повторюють властивості DOM-елементів, про які говорила лекція «DOM і
події», у розділі «Атрибут і властивість»: `element.className`, `element.htmlFor`, `element.readOnly`.

| В HTML | У JSX | Що каже React на запис як в HTML |
|--------|-------|----------------------------------|
| `class` | `className` | `Invalid DOM property class. Did you mean className?` |
| `for` | `htmlFor` | `Invalid DOM property for. Did you mean htmlFor?` |
| `readonly` | `readOnly` | `Invalid DOM property readonly. Did you mean readOnly?` |
| `tabindex` | `tabIndex` | `Invalid DOM property tabindex. Did you mean tabIndex?` |
| `onclick` | `onClick` | `Invalid event handler property onclick. Did you mean onClick?` |
| `aria-label`, `data-id` | так само, з дефісом | нічого не каже |

Записи `aria-*` і `data-*` лишилися з дефісом з історичних причин, і компілятор робить з них поля в лапках:
`"data-id": 7`. Попередження React легко пропустити, бо сторінка з `class` виглядає правильно, а саме попередження
React показує лише раз за запуск. Тому тут важливий `tsc`, який такий запис не пропускає.

### `style` приймає об'єкт

В HTML значення `style` є рядком CSS, а в JSX воно є об'єктом, ключі якого написано в camelCase. Подвійні дужки не є
особливим записом: зовнішні відкривають вираз JavaScript, а внутрішні починають об'єкт. Ось що React робить зі
значеннями:

```tsx
renderToStaticMarkup(<p style={{ width: 75, marginTop: 0, opacity: 0.5, lineHeight: 1.5, fontSize: '1.2rem', backgroundColor: 'teal' }} />)
```

```text
<p style="width:75px;margin-top:0;opacity:0.5;line-height:1.5;font-size:1.2rem;background-color:teal"></p>
```

Число `75` отримало одиницю `px`, бо ширина без одиниці не має сенсу. Число `0` лишилося без неї. Числа `0.5` і `1.5`
теж лишилися без неї, бо `opacity` і `line-height` вимірюються без одиниць. Рядок `'1.2rem'` пройшов як є, а
`backgroundColor` став `background-color`.

Рядок у `style` не просто ігнорується, а зупиняє показ компонента: `The style prop expects a mapping from style
properties to values, not a string`. Компілятор тут не допоможе, бо для нього рядок є звичайним значенням поля.
Документація радить уживати `style` лише для значень, що залежать від даних, а решту оформлювати класами через
`className`.

### Логічні атрибути

Деякі атрибути HTML мають значення лише тим, що вони є, наприклад `disabled`. React приймає для них `true` чи `false`
і вирішує, чи ставити атрибут. Для `aria-*` і `data-*` він цього не робить, а записує значення рядком.

| Запис | Результат |
|-------|-----------|
| `<button disabled>Купити</button>` | `<button disabled="">Купити</button>` |
| `<button disabled={false}>Купити</button>` | `<button>Купити</button>` |
| `<div aria-hidden={false} data-count={0} />` | `<div aria-hidden="false" data-count="0"></div>` |
| `<div title={undefined} />` | `<div></div>` |

До цієї ж теми належить поле вводу зі значенням. Запис `<input value="Кава" />` дає попередження `You provided a value
prop to a form field without an onChange handler`, бо таке поле неможливо змінити. Слово `readOnly` каже React, що так
задумано. Обробники змін ви вивчатимете з дня 7.

### Текст і пробіли

Текст між тегами теж розбирає компілятор, тому знаки синтаксису в ньому не можуть стояти просто так. Запис `<p>1 <
2</p>` дає `Unexpected token`, а запис `<p>2 > 1</p>` дає `Unexpected token. Did you mean {'>'} or &gt;?`. Є два
виходи: написати сутність `&lt;`, яку компілятор перетворить на знак, або взяти знак у дужки як рядок.

Сутність працює лише в тексті JSX. У рядку JavaScript вона лишається набором звичайних знаків:

| Запис | Що побачить людина |
|-------|--------------------|
| `<p>1 &lt; 2</p>` | `1 < 2` |
| `<p>{'1 < 2'}</p>` | `1 < 2` |
| `<p>{'1 &lt; 2'}</p>` | `1 &lt; 2` |

Запис `&lt;` у рядку трапляється, коли сервер присилає вже екранований текст: React покаже його як є, знак у знак.

Пробіли компілятор теж обробляє по-своєму. Він прибирає кінці рядків разом із відступами навколо них, бо інакше
форматування коду потрапляло б на екран. Пробіл усередині рядка він лишає. Ось що виходить для змінних зі значеннями
`'Чорна'` і `'кава'`:

| Запис | Результат |
|-------|-----------|
| `{a}` і `{b}` на двох різних рядках коду | `<p>Чорнакава</p>` |
| `{a} {b}` на одному рядку | `<p>Чорна кава</p>` |
| `{a}{' '}{b}` | `<p>Чорна кава</p>` |
| `Кава` і `з молоком` на двох рядках тексту | `<p>Кава з молоком</p>` |

Випадок із двома виразами на сусідніх рядках коду часто стає несподіванкою, бо вони склеюються без пробілу. Запис `{'
'}` є виразом, значення якого є рядок із пробілом. Такий запис часто ставить програма форматування, коли розмітка не
вміщається в рядок.

## Фігурні дужки: вираз замість значення

Фігурні дужки просять компілятор узяти значення з JavaScript. Між ними стоїть **вираз**, тобто запис, який дає
значення: `name`, `price * 2`, `f(x)`, `` `${a}%` ``, `ok ? 'так' : 'ні'`. Запис, який лише щось робить і значення не
дає, називається **інструкцією**: `if`, `for`, `const`.

Компілятор кладе вираз у поле об'єкта або в масив `children`. Поле об'єкта може містити лише значення, тому запис `{if
(ok) 'так'}` дає `Unexpected token`, і запис `{for (const a of list) { a }}` дає ту саму помилку. Для умови в розмітці
є оператори, які дають значення: `умова ? а : б` та `умова && б`. Складнішу умову пишуть інструкцією `if` перед
`return` і кладуть результат у змінну.

Дужки працюють лише в двох місцях: як текст між тегами й одразу після знака `=` в атрибуті. Запис `<{tag}>` дає
`Unexpected token`. Запис `alt="{name}"` помилки не дає, але лапки означають рядок, і компілятор робить з нього поле
`alt: "{name}"`, тому на сторінку потрапляють самі знаки `{name}`.

### Приклад із числами

Ось компонент, який показує один напій у меню. Функція `finalPrice` рахує ціну зі знижкою.

```tsx
type Drink = { name: string; price: number; discount: number; left: number }

function finalPrice(drink: Drink): number {
  return (drink.price * (100 - drink.discount)) / 100
}

function DrinkRow({ drink }: { drink: Drink }) {
  return (
    <>
      <dt style={{ color: drink.left > 0 ? 'black' : 'gray', fontSize: 18 }}>
        {drink.name}
      </dt>
      <dd title={`Залишилось: ${drink.left}`}>
        {finalPrice(drink)} грн
        {drink.discount > 0 && <b> −{drink.discount}%</b>}
      </dd>
    </>
  )
}
```

Простежимо вирази для напою `{ name: 'Лате', price: 80, discount: 25, left: 3 }`:

| Вираз | Як він обчислюється | Що потрапляє в елемент |
|-------|---------------------|------------------------|
| `drink.left > 0 ? 'black' : 'gray'` | `3 > 0` дає `true`, вибрано перше значення | `color: 'black'` |
| `fontSize: 18` | число без одиниці | `font-size:18px` |
| `drink.name` | читання поля | текст `Лате` |
| `` `Залишилось: ${drink.left}` `` | шаблонний рядок | `title="Залишилось: 3"` |
| `finalPrice(drink)` | `80 * 75 / 100` | число `60` |
| `drink.discount > 0 && <b>…</b>` | `25 > 0` дає `true`, результатом стає елемент | елемент `<b>` |

Ось розмітка для цього напою і для іншого, у якого знижки немає, а залишок нульовий:

```text
<dt style="color:black;font-size:18px">Лате</dt><dd title="Залишилось: 3">60 грн<b> −25%</b></dd>
<dt style="color:gray;font-size:18px">Какао</dt><dd title="Залишилось: 0">70 грн</dd>
```

Оператор `&&` повертає ліве значення, якщо воно хибне, і праве в іншому разі. У другому випадку ліва частина дала
`false`, а `false` React не показує, тому тега `<b>` немає. Докладно про умовний рендер розповість день 3.

### Що React робить зі значенням у дужках

Вираз може дати що завгодно, і React кожен вид значень обробляє по-своєму. Ось результат запису `<p>{значення}</p>`:

| Значення | Розмітка |
|----------|----------|
| `'Кава'` | `<p>Кава</p>` |
| `25` | `<p>25</p>` |
| `0` | `<p>0</p>` |
| `NaN` | `<p>NaN</p>`, і React додає попередження |
| `''` | `<p></p>` |
| `true`, `false` | `<p></p>` |
| `null`, `undefined` | `<p></p>` |
| `['Кава', ' і ', 'чай']` | `<p>Кава і чай</p>` |
| `{ name: 'Кава' }` | помилка `Objects are not valid as a React child` |
| `new Date(0)` | та сама помилка: `found: [object Date]` |

Звідси випливають дві корисні речі. По-перше, `false` і `null` нічого не показують, тому `&&` і тернарний оператор
зручно ховають частину розмітки. По-друге, `0` показується: якщо ліва частина `&&` є числом, а не порівнянням, на
екрані може з'явитися нуль. Цю пастку докладно розбирає день 3.

## Текст від користувача

### Яку атаку це зупиняє

Уявіть, що на сайті кав'ярні є книга відгуків, і сторінка вставляє кожен відгук у документ як HTML через `innerHTML`.

| Хто | Що робить |
|-----|-----------|
| зловмисник | залишає відгук `<img src=x onerror=...>` із кодом після `onerror` |
| сервер | зберігає цей рядок як звичайний текст відгуку |
| відвідувач | відкриває сторінку відгуків |
| браузер відвідувача | розбирає рядок як HTML, створює `<img>`, не може завантажити адресу `x` і виконує код з `onerror` |
| код зловмисника | працює так, ніби він є частиною сайту кав'ярні |

Така атака називається **XSS** (cross-site scripting), тобто впровадження чужого скрипту через дані. За описом MDN,
код зловмисника може читати й змінювати вміст сторінки, читати локальне сховище й надсилати запити від імені
відвідувача. Коли шкідливий рядок зберігається на сервері, він спрацьовує в кожного, хто відкриє сторінку. Цю атаку ми
в браузері не запускали й описуємо її за MDN.

### Що робить React

Ось той самий рядок із тегами, вставлений через фігурні дужки:

```tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>
}

const comment = '<b>Сашко</b> був тут'
const p = render(<Comment text={comment} />).container.querySelector('p')!
console.log('вузлів усередині <p>:', p.childNodes.length, p.firstChild?.nodeName)
console.log('елементів <b>:', p.querySelectorAll('b').length)
console.log('textContent:', p.textContent)
console.log('innerHTML:', p.innerHTML)
console.log('на сервері:', renderToStaticMarkup(<Comment text={comment} />))
console.log('в атрибуті:', renderToStaticMarkup(<img alt={'"><b>Сашко</b>'} />))
```

```text
вузлів усередині <p>: 1 #text
елементів <b>: 0
textContent: <b>Сашко</b> був тут
innerHTML: &lt;b&gt;Сашко&lt;/b&gt; був тут
на сервері: <p>&lt;b&gt;Сашко&lt;/b&gt; був тут</p>
в атрибуті: <img alt="&quot;&gt;&lt;b&gt;Сашко&lt;/b&gt;"/>
```

Тут працюють два механізми, і обидва зазвичай називають одним словом. **Екранування** означає заміну особливих знаків
так, щоб HTML-парсер прочитав їх як текст: знак `<` стає записом `&lt;`.

**У браузері React нічого не екранує, бо екранувати нема чого.** Він записує рядок у документ як текст, і парсер HTML
у цьому взагалі не бере участі. Вивід це показує: усередині `<p>` лежить один текстовий вузол `#text`, а елемента
`<b>` немає. Запис `&lt;` у виводі `innerHTML` з'явився лише тому, що ця властивість на запит читання перетворила
текст назад на HTML.

**Для сервера React справді екранує**, бо там результатом є рядок HTML, який пізніше розбере браузер. Це видно у
виводі `на сервері` і `в атрибуті`. Лапка в атрибуті теж стала `&quot;`, тому значення не може вийти за межі атрибута.

Отже, React не шукає в рядку небезпечного. Будь-який рядок із дужок стає текстом, нешкідливий `<b>` так само, як `<img
onerror>`. Захист полягає не у фільтрі, а в тому, що дані взагалі не потрапляють туди, де їх розбирають як HTML.

Практика дня бере рядок з `<img onerror>`, а не зі `<script>`, і причина важлива. MDN пояснює, що елемент `<script>`,
вставлений через `innerHTML`, не виконується, а код з `onerror` у тегу `<img>` виконується. Тому думка «якщо в рядку
немає `<script>`, він безпечний» хибна. Це твердження спирається на MDN, бо в справжньому браузері ми цього не
перевіряли. У практиці дня ви самі побачите в браузері захищений випадок: текст на екрані й жодного діалогу.

## Три способи обійти захист

### `dangerouslySetInnerHTML`

Іноді HTML справді потрібен, наприклад коли ваша власна бібліотека перетворила текст у форматі Markdown на розмітку.
Для цього існує проп `dangerouslySetInnerHTML`. Він приймає об'єкт із полем `__html` і записує значення цього поля у
властивість `innerHTML` елемента, тобто саме туди, де браузер розбирає рядок.

Незручна назва й обгортка з об'єкта потрібні для того, щоб цей запис не можна було написати випадково й легко було
знайти в коді. Рядок замість об'єкта React не прийме, а разом із дітьми цей проп не працює:

| Запис | Помилка React |
|-------|---------------|
| `<p dangerouslySetInnerHTML={'<b>a</b>'} />` | `props.dangerouslySetInnerHTML must be in the form {__html: ...}` |
| `<p dangerouslySetInnerHTML={{ __html: '…' }}>текст</p>` | `Can only set one of children or props.dangerouslySetInnerHTML` |

Документація React вимагає давати цьому пропу лише довірені й очищені дані. **Очищення** (sanitization) означає, що
спеціальна бібліотека розбирає HTML і вилучає небезпечне: обробники на кшталт `onerror` і теги `<script>`. MDN радить
бібліотеку DOMPurify, бо написати таке очищення самому важко. Цієї бібліотеки немає в корпусі документації плану, і в
сьогоднішній практиці вона не потрібна: дані користувача показують через `{}`.

### Адреса в `href`

Рядок `javascript:alert(1)` не містить знаків, які треба екранувати, і є правильним значенням атрибута. Екранування
тут не допомагає, бо небезпека виникає пізніше: браузер, перейшовши за такою адресою, виконує написаний там код.

React 19.3 частину таких адрес підміняє сам. Ось що опиняється в `href` після показу під jsdom:

| Значення `href` | Що опинилося в атрибуті |
|-----------------|-------------------------|
| `javascript:alert(1)` | `javascript:throw new Error('React has blocked a javascript: URL…')` |
| ` JavaScript:alert(1)`, з пробілом попереду | те саме |
| `java` + табуляція + `script:alert(1)` | те саме |
| `data:text/html,<b>x</b>` | без змін |
| `vbscript:x` | без змін |
| `https://a.ua` | без змін |

Посилання при цьому лишається на сторінці. За такою адресою браузер мав би показати помилку замість чужого коду, але
клацання в браузері ми не перевіряли, бо jsdom переходів не виконує. Покладатися на цю підміну не можна, бо вона
стосується лише однієї схеми адрес, а в старіших версіях React її немає. Правило плану таке: посилання з даних
пропускайте, лише якщо адреса починається з `http:` або `https:`.

Чому перелічують дозволене, а не заборонене? Запис адреси може бути хитрішим, ніж здається. Ось як читає такі адреси
конструктор `URL`. Цей код запущено в Node, а браузер за стандартом URL розбирає адреси так само, але окремо ми цього
в браузері не перевіряли:

```js
for (const url of ['javascript:alert(1)', ' JavaScript:alert(1)', 'java\tscript:alert(1)']) {
  console.log(JSON.stringify(url), new URL(url).protocol)
}
```

```text
"javascript:alert(1)" javascript:
" JavaScript:alert(1)" javascript:
"java\tscript:alert(1)" javascript:
```

Усі три записи означають ту саму схему. Перевірка «рядок не починається з `javascript:`» пропустила б запис із
пробілом і запис із табуляцією, а список дозволеного їх не пропустить. Є ще одна межа, яку перевіряє практика:
дивитися треба саме на початок рядка, бо слово `http` може стояти й усередині шкідливої адреси.

### Розгортання об'єкта з даних

Запис `{...data}` у тегу передає всі поля об'єкта як пропси. Докладно про нього розповість день 3. Якщо об'єкт прийшов
ззовні, серед його полів може бути будь-що:

```tsx
const data = JSON.parse('{"title":"Кава","dangerouslySetInnerHTML":{"__html":"<img src=x onerror=alert(1)>"}}')
console.log(renderToStaticMarkup(<div {...data} />))
```

```text
<div title="Кава"><img src=x onerror=alert(1)></div>
```

Тому чужий об'єкт не розгортають у тег HTML, а передають окремі поля, які вам потрібні. `tsc` тут мовчить, бо
`JSON.parse` повертає тип `any`, який вимикає перевірку типів.

Сам по собі об'єкт із даних елементом не стане. Елемент має поле `$$typeof`, значенням якого є символ, а формат JSON
передати символ не може. Спроба показати об'єкт `{ type: 'img', props: {…} }` дає вже знайому помилку `Objects are not
valid as a React child`.

## Розмітка після `return`

Розбір читання до вчорашнього дня вже показав цю помилку, а сьогодні вона важлива, бо розмітка стає довшою. Якщо після
`return` стоїть кінець рядка, JavaScript сам ставить там крапку з комою за правилом, яке стандарт ECMAScript називає
автоматичною вставкою крапки з комою. Функція повертає `undefined`, а розмітка нижче стає виразом, до якого виконання
ніколи не дійде.

Компілятор цей код приймає, бо він правильний для мови. React теж мовчить і нічого не показує. Помилку знаходить `tsc`
на рядку, де компонент ужито: `TS2786: … cannot be used as a JSX component`. За документацією TypeScript, недосяжний
код за замовчуванням подається як підказка для редактора, а не як помилка, тому `tsc` на самому рядку з розміткою
мовчить. З параметром `allowUnreachableCode: false` компілятор видає `TS7027: Unreachable code detected`. Правило
просте: відкривна дужка стоїть на одному рядку з `return`.

## Хто яку помилку ловить

| Помилка | Компілятор JSX | `tsc` | React під час роботи |
|---------|----------------|-------|----------------------|
| два сусідні теги без обгортки | `Adjacent JSX elements…` | `TS2657` | до запуску не дійде |
| незакритий `<img>` | `Expected corresponding JSX closing tag…` | `TS17008` | до запуску не дійде |
| `if` у фігурних дужках | `Unexpected token` | `TS1109` | до запуску не дійде |
| `<p class="a" />` | пропускає | `TS2322` | попередження, сторінка працює |
| `<p style="color: red" />` | пропускає | `TS2559` | помилка, компонент не показано |
| `<p>{{ name: 'Кава' }}</p>` | пропускає | `TS2353` | помилка, компонент не показано |
| `return` і розмітка на різних рядках | пропускає | `TS2786` на місці вживання | мовчить, порожньо на екрані |
| `<a href="javascript:…">` | пропускає | мовчить | підміняє адресу, посилання лишається |
| `dangerouslySetInnerHTML` з даними | пропускає | мовчить | виконує те, що сказано |

Рядки про `javascript:` і `dangerouslySetInnerHTML` важливі. Жоден автоматичний інструмент не знає, чи можна довіряти
вашим даним, тому захист у цих випадках пишете ви самі й перевіряєте прикладами.

## Рецепт: приклад на кожну гілку

Рецепт із книжки How to Design Programs не змінюється: опис даних, призначення, сигнатура, приклади, перелік вхідних
даних, тіло, перевірка. Сьогодні в тілі з'являються умови, і кожна умова дає дві гілки. Тому прикладів потрібно
щонайменше два: один для випадку, коли частина розмітки є, і другий для випадку, коли її немає.

```tsx
// Показує назву кав'ярні й посилання на її сайт, якщо сайт відомий.
function CafeLink({ cafe }: { cafe: Cafe }) {
  // Є: cafe.name, cafe.site.
  return null
}

test('CafeLink: без сайту посилання немає', () => {
  render(<CafeLink cafe={{ name: 'Зерно', site: '' }} />)
  expect(screen.queryByRole('link')).toBeNull()
})
```

Цей приклад проходить уже на заглушці `return null`, бо на порожній сторінці посилання справді немає. Приклад не
збрехав, але він нічого не доводить, доки поруч немає прикладу, у якому посилання має бути. Так само заглушка `return
false` проходить приклади, які чекають `false`. Тому в заготовці дня частина перевірок зелена ще до того, як ви щось
написали, і це не ознака готовності. Запит `queryByRole` повертає `null`, якщо елемента немає, а `getByRole` у такому
разі кидає помилку. Докладно їхню різницю пояснює розбір читання.

## Типові хибні уявлення

**«JSX — це HTML усередині JavaScript».** Це запис викликів функцій, який лише схожий на HTML. Тому HTML не можна
вставити без змін, і тому `<div />` означає в них різне.

**«Якщо в рядку є теги, через `{}` вони стануть розміткою».** Значення зі `{}` лягає в проп `children`. Рядок у цьому
пропі React записує як текст, і парсер HTML його не читає.

**«React вирізає небезпечне з рядка».** React нічого не вирізає. Рядок показано знак у знак, разом із `<b>` і `<img>`.

**«Рядок стає текстом ще під час збірки».** Компілятор передає змінну як є і значення рядка не бачить. Рядок стає
текстом під час показу.

**«Немає `<script>`, отже безпечно».** Тег `<script>`, вставлений через `innerHTML`, якраз не виконується, а `onerror`
виконується. За MDN, способів запустити код через HTML багато.

**«React блокує `javascript:`, отже перевірка зайва».** Він блокує одну схему, а посилання лишає на сторінці. Адреси
`data:` проходять без змін.

**«`style` рядком просто не застосується».** Такий запис зупиняє показ компонента помилкою.

## Як це проявиться далі в React

- **День 3, пропси й умовний рендер.** Поле `children`, яке ви сьогодні бачили у виводі компілятора, стане вашим
  інструментом, а записи `{...props}` і `&&` з числом отримають окремий розбір.
- **День 4, списки й ключі.** Масив у дужках уже працює, але React просить ключ: `Each child in a list should have a
  unique "key" prop`. Третій аргумент виклику `jsx` якраз і є цим ключем.
- **День 6, TypeScript у React.** Помилки `tsc` із цієї лекції стануть зрозумілішими, коли ви побачите типи пропсів
  тегів HTML і тип `ReactNode`.
- **День 7, події й стан.** Запис `onClick` отримає функцію, а поле вводу отримає `onChange` замість `readOnly`.

## Перевірте себе

**1. Запис `<li className="drink">{name}</li>` компілюється в який виклик і що він повертає?**

<details><summary>Відповідь</summary>

У виклик `_jsx("li", { className: "drink", children: name })`. Він повертає елемент, тобто простий об'єкт із полями
`type` і `props`. Вузла DOM у цю мить ще немає.

</details>

**2. Чому `if` у фігурних дужках не компілюється, а тернарний оператор компілюється?**

<details><summary>Відповідь</summary>

Вміст дужок стає значенням поля об'єкта або елементом масиву, тому там може стояти лише вираз, тобто запис, який дає
значення. Оператор `if` є інструкцією й значення не дає, а тернарний оператор значення дає.

</details>

**3. Для змінних `a = 'Чорна'` і `b = 'кава'` записи `{a}` і `{b}` стоять на двох сусідніх рядках коду. Що побачить
людина?**

<details><summary>Відповідь</summary>

`Чорнакава`. Компілятор прибирає кінець рядка разом із відступом, тому пробілу між дітьми немає. Пробіл дає запис `{a}
{b}` на одному рядку або окремий вираз `{' '}`.

</details>

**4. Що покаже `<p>{value}</p>` для значень `0`, `false` і `{ a: 1 }`?**

<details><summary>Відповідь</summary>

Для `0` покаже `0`. Для `false` покаже порожній абзац. Для об'єкта React кине помилку `Objects are not valid as a
React child`.

</details>

**5. Рядок `<b>Сашко</b>` вставлено через `{}`. Чому в браузерному DOM React нічого не замінює на `&lt;`, а запис
`&lt;` при цьому можна побачити у властивості `innerHTML`?**

<details><summary>Відповідь</summary>

React записує рядок як текстовий вузол, і парсер HTML у цьому не бере участі. Властивість `innerHTML` на запит читання
перетворює дерево назад на HTML, і саме вона записує знак `<` у тексті як `&lt;`.

</details>

**6. Чому екранування не рятує від `href={site}`, де `site` дорівнює `javascript:alert(1)`?**

<details><summary>Відповідь</summary>

У цьому рядку немає особливих для HTML знаків, тому він є правильним значенням атрибута. Небезпека виникає, коли
браузер переходить за такою адресою й виконує код. Тому адресу перевіряють окремо, пропускаючи лише дозволені схеми.

</details>

**7. Приклад перевіряє `queryByRole('link')` на `null` і проходить на заглушці `return null`. Що це означає?**

<details><summary>Відповідь</summary>

На порожній сторінці посилання справді немає, тому цей приклад сам по собі нічого не доводить. Він набуває сенсу лише
поруч із прикладом, де посилання має бути й перевіряється запитом `getByRole`.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| JSX | запис розмітки всередині JavaScript, який компілятор перетворює на виклики функцій |
| компілятор | програма, яка перетворює текст програми на інший текст ще до запуску |
| `children` | проп, у якому лежить усе, що вкладено між тегами |
| фрагмент | запис `<>…</>`, який об'єднує елементи в один і в документі нічого не лишає |
| вираз | запис, який дає значення |
| інструкція | запис, який щось робить і значення не дає, наприклад `if` |
| екранування | заміна особливих знаків так, щоб парсер HTML прочитав їх як текст |
| XSS | атака, у якій чужий код потрапляє на сторінку через дані й виконується як частина сайту |
| очищення | вилучення небезпечного з рядка HTML спеціальною бібліотекою |
