# Лекція. Фаза 1, день 3. Пропси й умовний рендер

Два попередні дні ви писали компоненти, які щоразу показують одне й те саме. Ця лекція пояснює, як той самий компонент
показує різне: що батько передає йому в дужках тега, чому отримане не можна змінювати, що React показує на екрані, а
що пропускає, і як TypeScript не дає прочитати поле, якого в цьому стані даних немає. Читання займе близько 40 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під
прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0. У справжньому браузері приклади не запускалися,
тому там, де йдеться про браузер, сказано, на чому це твердження тримається.

**Після лекції ви зможете пояснити:**

- що саме отримує функція компонента, коли батько пише атрибути в тегу;
- чим `weight="0"` відрізняється від `weight={0}`;
- чому пропси лише для читання і як тоді на екрані взагалі щось змінюється;
- що лежить у `children` і чому вкладений компонент може ні разу не викликатися;
- якими способами JavaScript вибирають, що показати, і коли який зручніший;
- чому `{count && <Badge />}` показує «0» при нулі, а `{count > 0 && <Badge />}` не показує нічого;
- як TypeScript дізнається, які поля є в кожній гілці, і де ця перевірка закінчується.

## Сторінка з трьома посилками

Ви робите сторінку відстеження посилок. Спершу на ній одна картка, і ви пишете її так, як навчилися вчора:

```tsx
function ParcelCard() {
  return (
    <section>
      <h3>Посилка до міста Одеса</h3>
      <p>Везе кур'єр Ігор</p>
    </section>
  )
}
```

Посилок виявляється три, і тут з'являються три різні потреби.

Перша потреба очевидна: міста й імена в кожної посилки свої, а розмітка однакова. Копіювати функцію тричі з іншими
словами не можна, бо посилок може бути тисяча. Компоненту потрібні вхідні дані, як будь-якій функції.

Друга потреба менш очевидна: картка не просто підставляє інші слова. Посилку, яку ще пакують, ніхто не везе, тому
рядка з кур'єром у неї немає. Отриману посилку хтось підписав, тому в неї інший рядок. Компонент мусить вибирати, що
показати.

Третя потреба з'являється, коли даних стає багато. Хтось напише `delivery.courier` для посилки, яку ще пакують, і на
екрані з'явиться рядок «Везе кур'єр » без імені. Помилки не буде, бо читання неіснуючого поля в JavaScript просто дає
`undefined`. Хочеться, щоб такий код узагалі не проходив перевірку.

Першу потребу задовольняють пропси, другу умовний рендер, а третю розрізнюване об'єднання, яке ви вже бачили в лекції
«TypeScript: основи» саме на цих посилках.

## Пропси: усе, що батько передає компоненту

**Пропси** (props, скорочено від properties, тобто властивості) є вхідними даними компонента. **Батьком** тут
називають компонент, у розмітці якого стоїть тег, а **дитиною** називають компонент, якого цей тег викликає.

### Що саме приходить у функцію

Подивімося на це прямо. Компонент `Label` нічого не показує, а лише друкує свій аргумент. Компонент і тест лежать в
одному файлі, ім'я якого закінчується на `.test.tsx`, наприклад `src/label.test.tsx`. Команда `npx vitest run`
запускає такий файл:

```tsx
// @vitest-environment jsdom
// Цей коментар просить Vitest створити імітацію браузера, бо без документа компонент показати ніде.
import { render } from '@testing-library/react'
import { test } from 'vitest'

function Label(props: { city: string; weight: number; fragile: boolean; tags: string[] }) {
  console.log(props) // друкує все, що функція отримала
  return null
}

test('Label', () => {
  // render показує компонент, тобто React викликає функцію Label.
  render(<Label city="Львів" weight={2} fragile tags={['скло']} />)
})
```

Решта прикладів із React у цій лекції запускаються так само: рядки показу й друку стоять усередині `test`, а перші
рядки файла ми далі не повторюємо. Ось що надрукував цей тест:

```text
{ city: 'Львів', weight: 2, fragile: true, tags: [ 'скло' ] }
```

Функція отримала **один** аргумент, а саме об'єкт, поля якого повторюють атрибути тега. Лекція «JSX» пояснила, звідки
він береться: компілятор перетворює тег на виклик `_jsx(Label, { city: "Львів", ... })`, а React пізніше передає цей
об'єкт у вашу функцію.

Зазвичай об'єкт одразу розкладають на змінні просто в параметрах. Запис `function Label({ city, weight })` називається
**деструктуризацією** й означає те саме, що `const city = props.city` і `const weight = props.weight` на початку
функції. Запис без фігурних дужок, `function Label(city)`, поклав би в змінну `city` увесь об'єкт. Цю помилку розбирав
перший день фази.

Пропсом може бути будь-яке значення JavaScript: рядок, число, масив, об'єкт, функція або елемент розмітки. Теги HTML
приймають лише наперед відомі пропси, а ваш компонент приймає ті, які ви самі оголосили.

### Значення в лапках і значення в дужках

В HTML кожен атрибут є рядком. У JSX лапки дають рядок, а фігурні дужки дають значення будь-якого типу як є. Різниця
стає важливою, коли значення перевіряють на істинність:

```tsx
function Show(props: Record<string, unknown>) {
  console.log(typeof props.weight, props.weight ? 'істинне' : 'хибне')
  return null
}

render(<Show weight="0" />)
render(<Show weight={0} />)
```

```text
string істинне
number хибне
```

Рядок `"0"` є непорожнім рядком, тому він істинний. Число `0` хибне. Запис `fragile` без значення означає
`fragile={true}`, це ви вже бачили у виводі компілятора.

### Типи пропсів

Друга пара дужок у `{ city }: { city: string }` є типом цього об'єкта. Коли компонент оголошено з типом, `tsc`
перевіряє кожен тег, де компонент ужито:

| Запис для `Stamp({ color, text }: { color: string; text: string })` | Що каже `tsc` |
|---------------------------------------------------------------------|---------------|
| `<Stamp color="red" />` | `TS2741: Property 'text' is missing` |
| `<Stamp color="red" text="x" size={3} />` | `TS2322`, зайвого пропа `size` у типі немає |
| `<Stamp color={5} text="x" />` | `TS2322: Type 'number' is not assignable to type 'string'` |

Без типів кожна з цих помилок дала б `undefined` або неправильне значення під час роботи, і помітити її можна було б
лише на екрані.

### Значення за замовчуванням

Пропс можна зробити необов'язковим і дати йому запасне значення. Це той самий запис, що в деструктуризації звичайного
об'єкта:

```tsx
function Box({ size = 100 }: { size?: number | null }) {
  console.log('size =', size)
  return null
}

render(<Box />)
render(<Box size={undefined} />)
render(<Box size={null} />)
render(<Box size={0} />)
```

```text
size = 100
size = 100
size = null
size = 0
```

Запасне значення спрацьовує лише тоді, коли пропса немає або він дорівнює `undefined`. Значення `null` і `0` є
справжніми значеннями, і вони проходять як є.

### Передати все далі: `{...props}`

Іноді компонент лише передає свої пропси дитині. Запис `{...data}` у тегу розгортає всі поля об'єкта в пропси.
Компілятор робить з нього звичайне розгортання об'єкта:

```js
// файл compile.mjs
import { transformWithOxc } from 'vite'
const source = `export const d = <Stamp {...data} color="red" />`
const { code } = await transformWithOxc(source, 'x.jsx', { jsx: { runtime: 'automatic' } })
console.log(code)
```

```text
$ node compile.mjs
import { jsx as _jsx } from "react/jsx-runtime";
export const d = /* @__PURE__ */ _jsx(Stamp, {
	...data,
	color: "red"
});
```

Поля об'єкта записуються по черзі, тому пізніше значення замінює раннє. Порядок записів у тегу вирішує результат:

```tsx
import { renderToStaticMarkup } from 'react-dom/server' // перетворює компонент на рядок HTML без документа

function Stamp({ color, text }: { color: string; text: string }) {
  return <i style={{ color }}>{text}</i>
}
const data = { color: 'blue', text: 'Крихке' }

console.log(renderToStaticMarkup(<Stamp {...data} color="red" />))
console.log(renderToStaticMarkup(<Stamp color="red" {...data} />))
```

```text
<i style="color:red">Крихке</i>
<i style="color:blue">Крихке</i>
```

У другому записі `color="red"` не діє, і `tsc` прямо каже про це: `TS2783: 'color' is specified more than once, so
this usage will be overwritten`.

Документація React радить уживати цей запис стримано. Якщо він трапляється майже в кожному компоненті, сторінка
`Passing Props to a Component` радить поділити компоненти на менші й передавати розмітку через `children`, про який
ідеться нижче. Лекція «JSX» вже показала ще одну межу: чужий об'єкт із даних не можна розгортати в тег HTML, бо серед
його полів може опинитися `dangerouslySetInnerHTML`.

## Чому пропси лише для читання

Пропси належать батькові. Він їх створив, він може передати той самий об'єкт іншим компонентам, і він очікує, що після
показу дитини дані лишаться такими, як були. Тому дитина їх не змінює. Сторінка `Passing Props to a Component` називає
пропси незмінними (immutable) і каже прямо: «Don't try to "change props".»

### Що станеться, якщо спробувати

У режимі розробки React заморожує об'єкт пропсів функцією `Object.freeze` з лекції «Масиви й об'єкти функційно». Запис
поля в заморожений об'єкт у суворому режимі кидає помилку. Суворий режим діє в усіх модулях, тобто й у ваших файлах:

```js
// файл stamp.mjs
import { jsx } from 'react/jsx-runtime'
import { renderToStaticMarkup } from 'react-dom/server'

function Stamp(props) {
  console.log('заморожено?', Object.isFrozen(props))
  try {
    props.text = props.text + '!'
  } catch (error) {
    console.log('помилка:', error.message)
  }
  return jsx('i', { children: props.text })
}
console.log(renderToStaticMarkup(jsx(Stamp, { text: 'Крихке' })))
```

```text
$ node stamp.mjs
заморожено? true
помилка: Cannot assign to read only property 'text' of object '#<Object>'
<i>Крихке</i>
$ NODE_ENV=production node stamp.mjs
заморожено? false
<i>Крихке!</i>
```

Другий запуск важливий. Змінна середовища `NODE_ENV=production` вмикає той варіант пакета `react`, який потрапляє в
збірку для користувачів. Заморожування там немає, тому той самий код мовчки змінює об'єкт. Отже, помилка в режимі
розробки є допомогою, а не захистом. Код, який змінює пропси, не можна залишати в надії, що React його зупинить.

`tsc` такий запис за замовчуванням пропускає, бо звичайний тип `{ text: string }` нічого не каже про заморожування.
Якщо написати тип як `Readonly<{ text: string }>`, компілятор відмовить: `TS2540: Cannot assign to 'text' because it
is a read-only property`.

### Вкладені об'єкти не заморожено

`Object.freeze` заморожує лише один рівень, як пояснювала та сама лекція про об'єкти. Якщо проп є об'єктом, поля цього
об'єкта можна змінити без жодної помилки. Подивіться, що від цього буває. Компонент `Title` хоче показати назву міста
великими літерами й робить це прямо в об'єкті, а компонент `Address` просто показує місто:

```tsx
type Parcel = { city: string; views: number }

function Title({ parcel }: { parcel: Parcel }) {
  parcel.city = parcel.city.toUpperCase()
  return <h3>{parcel.city}</h3>
}
function Address({ parcel }: { parcel: Parcel }) {
  return <p>{parcel.city}</p>
}

const a = { city: 'Львів', views: 0 }
console.log(render(<><Address parcel={a} /><Title parcel={a} /></>).container.innerHTML)
const b = { city: 'Львів', views: 0 }
console.log(render(<><Title parcel={b} /><Address parcel={b} /></>).container.innerHTML)
console.log('у батька:', b.city)
```

```text
<p>Львів</p><h3>ЛЬВІВ</h3>
<h3>ЛЬВІВ</h3><p>ЛЬВІВ</p>
у батька: ЛЬВІВ
```

Результат показу залежить від того, який із компонентів стоїть першим, а в батька дані теж змінилися. Правильний
спосіб обчислити нове значення й не чіпати старе: `const title = parcel.city.toUpperCase()`.

Ще гірше виходить, коли компонент змінює число. Коли саме викликати функцію компонента, вирішує React, а кожен такий
виклик називається **рендером**. Ось компонент, який на кожному рендері додає одиницю:

```tsx
function Views({ parcel }: { parcel: Parcel }) {
  parcel.views = parcel.views + 1
  return <p>{parcel.views}</p>
}

const parcel = { city: 'Львів', views: 0 }
const { container, rerender } = render(<Views parcel={parcel} />)
console.log(container.innerHTML)
rerender(<Views parcel={parcel} />)
console.log(container.innerHTML)
rerender(<Views parcel={parcel} />)
console.log(container.innerHTML)
```

```text
<p>1</p>
<p>2</p>
<p>3</p>
```

Функція `rerender` з Testing Library показує той самий компонент ще раз. Дані на вході не змінилися, а число на екрані
росте. Компонент, який так поводиться, називають нечистим, і день 5 пояснить, чому так писати не можна.

### Як тоді щось змінюється на екрані

Якщо пропси не можна змінювати, звідки на екрані беруться нові дані? Відповідь така: батько передає **нові** пропси.
Кожен рендер батька створює новий об'єкт, а дитина отримує його замість старого:

```tsx
const seen: object[] = []
function Weight(props: { kg: number }) {
  seen.push(props)
  return <p>{props.kg} кг</p>
}

const { container, rerender } = render(<Weight kg={2} />)
console.log(container.innerHTML)
rerender(<Weight kg={3} />)
console.log(container.innerHTML)
console.log("той самий об'єкт?", seen[0] === seen[1], '| перший:', seen[0], '| другий:', seen[1])
```

```text
<p>2 кг</p>
<p>3 кг</p>
той самий об'єкт? false | перший: { kg: 2 } | другий: { kg: 3 }
```

Перший об'єкт лишився таким, яким був. Отже, пропси описують дані на одну конкретну мить, а наступна мить отримує нові
пропси. Сьогодні нові пропси передає тест функцією `rerender`, а з дня 7 це робитиме стан батька. Якщо дитина хоче
щось змінити, вона просить про це батька функцією, яку той передав їй як проп. Про це теж розповість день 7.

## `children`: вкладене теж є пропом

Теги HTML можна вкладати один в одного, і власні компоненти теж. Усе, що стоїть між відкривним і закривним тегами,
компілятор кладе в проп із назвою `children`:

```text
<Panel title="Посилка"><p>Львів</p></Panel>

_jsx(Panel, {
	title: "Посилка",
	children: _jsx("p", { children: "Львів" })
});
```

Коментарі `/* @__PURE__ */` у цьому записі прибрано. Це звичайний проп, і компонент сам вирішує, де його показати.
Завдяки цьому компонент-рамка може не знати, що в ньому лежатиме. Одна рамка однаково обгортає текст, список або іншу
картку.

### Яку форму має `children`

Форма значення залежить від того, що написав батько. Щоб це побачити, зробимо компонент `Panel`, який нічого не
показує, а лише друкує свій проп `children`:

```tsx
import type { ReactNode } from 'react' // ReactNode означає все, що React уміє показати

function Panel({ children }: { children?: ReactNode }) {
  // Перше слово каже, що це за значення, а далі друкується сам вміст.
  console.log(Array.isArray(children) ? 'масив' : typeof children, JSON.stringify(children))
  return null
}

const n = 2
render(<Panel>Просто текст</Panel>)
render(<Panel>Посилок: {n}</Panel>)
render(
  <Panel>
    <p>один</p>
  </Panel>,
)
render(<Panel />)
```

```text
string "Просто текст"
масив ["Посилок: ",2]
object {"type":"p","key":null,"props":{"children":"один"},"_owner":null,"_store":{}}
undefined undefined
```

Кожен виклик `render` надрукував один рядок, у тому самому порядку. У рядку зі словом `object` лежить елемент, тобто
об'єкт із полем `type`, а поля `_owner` і `_store` є службовими полями React. Таблиця збирає цей вивід:

| Що між тегами | Що лежить у `children` |
|---------------|------------------------|
| лише текст | рядок `"Просто текст"` |
| текст і вираз | масив `["Посилок: ", 2]` |
| один тег, навіть на окремому рядку | один елемент, об'єкт із `type: "p"`, а не масив |
| нічого | `undefined` |

Третій рядок випливає з правила про пробіли з лекції «JSX»: кінці рядків і відступи навколо тега компілятор прибирає,
тому дитина лишається одна. З цієї таблиці випливає, що писати `children.map(...)` небезпечно: у трьох випадках із
чотирьох `children` не є масивом. Масив дітей, коли він є, у режимі розробки теж заморожений. Перевіримо це викликом
`push`:

```tsx
function Adds({ children }: { children: ReactNode[] }) {
  try {
    children.push('ще') // спроба дописати значення в отриманий масив
  } catch (error) {
    console.log((error as Error).message)
  }
  return null
}

const n = 2
render(<Adds>Посилок: {n}</Adds>) // між тегами текст і вираз, тому children є масивом
```

```text
Cannot add property 2, object is not extensible
```

Масив `["Посилок: ", 2]` уже має елементи з індексами 0 і 1, тому `push` намагається додати елемент з індексом 2, а
заморожений масив цього не дозволяє. Отже, `children` можна лише читати й показувати, як і решту пропсів. React має
окремий помічник `Children` для таких випадків, але документація називає його вживання нечастим і радить спершу
пошукати інший спосіб.

Тип для пропа `children` зазвичай пишуть `ReactNode`, що означає все, що React уміє показати. Докладно цей тип розбере
день 6. Якщо проп оголошено обов'язковим, то запис `<Panel />` не пройде `tsc`: `TS2741: Property 'children' is
missing`.

### Елемент є лише описом

Є наслідок, який легко пропустити. Запис `<Child />` не викликає функцію `Child`. Він створює елемент, тобто об'єкт з
описом, а React викликає функцію лише тоді, коли цей елемент опиняється в результаті показу:

```tsx
function Child() {
  console.log('Child викликано')
  return <p>дитина</p>
}
function Careless({ title }: { title: string; children?: ReactNode }) {
  return <h3>{title}</h3>
}
function Careful({ title, children }: { title: string; children?: ReactNode }) {
  return <section><h3>{title}</h3>{children}</section>
}

const el = <Child />
console.log('елемент створено, type:', typeof el.type)
console.log(render(<Careless title="без children">{el}</Careless>).container.innerHTML)
console.log(render(<Careful title="з children">{el}</Careful>).container.innerHTML)
```

```text
елемент створено, type: function
<h3>без children</h3>
Child викликано
<section><h3>з children</h3><p>дитина</p></section>
```

`Careless` отримав елемент і не показав його. Функція `Child` не викликалася, вміст зник, і ніхто про це не повідомив.
Так само виглядає типова помилка в рамці, яка забула вивести `{children}`: сама рамка на місці, а всередині порожньо.

## Умовний рендер: окремого запису немає

**Умовним рендером** називають показ різної розмітки залежно від даних. React не додає для цього нічого свого.
Компонент є функцією, тому вибір робить звичайний JavaScript. Ось що залишає від умов компілятор:

```text
<p>{count && <b>нових</b>}</p>

_jsx("p", { children: count && _jsx("b", { children: "нових" }) });

<p>{ok ? <b>так</b> : null}</p>

_jsx("p", { children: ok ? _jsx("b", { children: "так" }) : null });
```

Коментарі `/* @__PURE__ */`, які компілятор додає для мінімізатора, у цьому записі прибрано. Оператори лишилися
такими, як ви їх написали. Отже, щоб зрозуміти результат, треба знати дві речі: що повертає вираз JavaScript і що
React робить із цим значенням.

У вас є чотири способи вибрати, і всі вони видно на сторінці `Conditional Rendering`.

**Інструкція `if` з раннім `return`.** Зручно, коли гілки сильно різняться або коли в одній із гілок решта коду не має
сенсу. Функція повертає результат і далі не виконується.

```tsx
if (parcels.length === 0) {
  return <p>Посилок немає</p>
}
```

**Тернарний оператор `умова ? а : б`.** Цей оператор вибирає одне з двох значень. Він є виразом, тобто дає значення,
тому його можна писати просто в розмітці у фігурних дужках. Зручно, коли відрізняється маленька частина спільної
розмітки: `<p>{paid ? 'Оплачено' : 'Оплата при отриманні'}</p>`.

**Оператор `умова && значення`.** Зручно, коли потрібно показати щось або нічого: `{isFragile && <b>Крихке</b>}`.
Нижче розберемо його єдину пастку.

**Змінна.** Коли умова складна, значення готують перед `return` звичайним `if`, а в розмітку вставляють змінну:

```tsx
let note = null
if (weight > 30) {
  note = <b>Потрібен вантажник</b>
}
return <p>{weight} кг {note}</p>
```

Цей запис найдовший, зате не має обмежень. Інструкцію `if` не можна поставити всередину `{}` у розмітці. Там стоїть
значення поля об'єкта, а `if` значення не дає, тому запис `{if (ok) 'так'}` дає `Unexpected token`, як пояснила лекція
«JSX».

Компонент може також повернути `null`, і тоді він не показує нічого. Сторінка `Conditional Rendering` зауважує, що так
роблять нечасто, бо інший розробник, який вставить такий компонент, може здивуватися. Частіше рішення приймає батько,
який просто не вставляє дитину.

Ще одна властивість спільна для `?:` і `&&`: вони обчислюють лише потрібну частину.

```tsx
function make(name: string) { console.log('обчислено', name); return name }
function Tern({ ok }: { ok: boolean }) {
  return <p>{ok ? make('так') : make('ні')}{ok && make('праворуч')}</p>
}

console.log(render(<Tern ok={false} />).container.innerHTML)
console.log(render(<Tern ok={true} />).container.innerHTML)
```

```text
обчислено ні
<p>ні</p>
обчислено так
обчислено праворуч
<p>такправоруч</p>
```

Тому `{user && <p>{user.name}</p>}` безпечний: при `user === null` запис `user.name` не виконується взагалі.

## Чому `&&` показує нуль

Ось типова ситуація. Картка посилки має показувати напис про невдалі спроби доставки, лише коли такі спроби були.

```tsx
<p>{delivery.attempts && <b>Невдалих спроб: {delivery.attempts}</b>}</p>
```

Виглядає правильно: якщо спроб немає, то нуль хибний, і напису не буде. Напису справді не буде, але на екрані
з'явиться цифра `0`. Простежимо, чому так відбувається.

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | JavaScript | читає `delivery.attempts`, отримує число `0` |
| 2 | JavaScript | перетворює `0` на логічне значення, виходить `false` |
| 3 | JavaScript | повертає **саму ліву частину**, тобто число `0`, а не `false` |
| 4 | виклик `_jsx` | отримує результат виразу, число `0`, у полі `children` |
| 5 | React | показує число як текст, у документі з'являється текстовий вузол `0` |

Вирішальним є третій крок. Багато хто читає `a && b` як логічне «і», результатом якого має бути правда чи неправда. У
JavaScript цей оператор повертає один зі своїх операндів без перетворення. Стандарт ECMAScript описує його так: якщо
ліва частина після перетворення хибна, повернути ліву частину. В інших випадках результатом стає права частина.

Лекція «JSX» вже показувала, що React робить з різними значеннями. Разом із поведінкою `&&` це дає повну таблицю. Щоб
її отримати, покажемо запис `<p>{v && <b>так</b>}</p>` із кожним значенням і надрукуємо абзац, який вийшов:

```tsx
// Тип any стоїть лише для досліду, бо в змінну v потраплять значення різних типів.
function Show({ v }: { v: any }) {
  return <p>{v && <b>так</b>}</p>
}

const cases: [string, unknown][] = [
  ['0', 0], ['-0', -0], ['0n', 0n], ['NaN', NaN], ["''", ''], ['false', false], ['null', null],
  ['undefined', undefined], ['2', 2], ['-1', -1], ["'0'", '0'], ['[]', []], ['{}', {}],
]
for (const [label, v] of cases) {
  const p = render(<Show v={v} />).container.querySelector('p')!
  // childNodes містить усе, що лежить в абзаці: елементи й шматки тексту. Кожен з них називають вузлом.
  console.log(label, '|', p.outerHTML, '| вузлів:', p.childNodes.length)
}
```

```text
0 | <p>0</p> | вузлів: 1
-0 | <p>0</p> | вузлів: 1
0n | <p>0</p> | вузлів: 1
Received NaN for the `children` attribute. If this is expected, cast the value to a string.
NaN | <p>NaN</p> | вузлів: 1
'' | <p></p> | вузлів: 0
false | <p></p> | вузлів: 0
null | <p></p> | вузлів: 0
undefined | <p></p> | вузлів: 0
2 | <p><b>так</b></p> | вузлів: 1
-1 | <p><b>так</b></p> | вузлів: 1
'0' | <p><b>так</b></p> | вузлів: 1
[] | <p><b>так</b></p> | вузлів: 1
{} | <p><b>так</b></p> | вузлів: 1
```

Рядок зі словами `Received NaN` є попередженням, яке друкує сам React. Таблиця групує той самий вивід і пояснює кожну
групу:

| Значення `v` | Розмітка | Вузлів у `<p>` | Чому |
|--------------|----------|----------------|------|
| `0`, `-0`, `0n` | `<p>0</p>` | 1 | хибне число повернулося, а число React показує |
| `NaN` | `<p>NaN</p>` | 1 | те саме, і React ще додає попередження |
| `''` | `<p></p>` | 0 | порожній рядок повернувся, показувати нічого |
| `false`, `null`, `undefined` | `<p></p>` | 0 | значення повернулося, React його пропускає |
| `2`, `-1` | `<p><b>так</b></p>` | 1 | істинне, результатом стала права частина |
| `'0'` | `<p><b>так</b></p>` | 1 | непорожній рядок істинний |
| `[]`, `{}` | `<p><b>так</b></p>` | 1 | будь-який об'єкт істинний, навіть порожній |

Запис `0n` у таблиці означає нуль типу BigInt, окремого типу для великих цілих чисел. З таблиці видно, що пастка
стосується саме чисел. Найчастіше вона трапляється у двох формах: `{count && …}` і `{items.length && …}`. Сторінка
`Conditional Rendering` прямо радить не ставити число ліворуч від `&&`.

Рядок про `-1` нагадує про ще одну відмінність. Перевірка `count > 0` і перевірка на істинність поводяться по-різному
для від'ємних чисел, тому варто написати саме те порівняння, яке означає ваша умова.

**Як виправити.** Умова має бути логічним значенням, тобто `true` або `false`:

| Запис | При `attempts = 0` |
|-------|--------------------|
| `{attempts > 0 && <b>…</b>}` | `false`, нічого не показано |
| `{Boolean(attempts) && <b>…</b>}` | `false`, нічого не показано |
| `{attempts ? <b>…</b> : null}` | `null`, нічого не показано |

**Сусідні оператори.** Той самий принцип «повернути операнд» діє в `||` і `??`, і різниця між ними теж полягає в нулі.
Запис `0 || 'немає'` дає `'немає'`, бо нуль хибний. Запис `0 ?? 'немає'` дає `0`, бо оператор `??` замінює лише `null`
і `undefined`.

**Хто це ловить.** Автоматичні перевірки коду цього не ловлять. Запустимо їх на файлі, який містить цю помилку. Запис
`$?` друкує код виходу попередньої команди:

```tsx
// файл src/Attempts.tsx
export function Attempts({ attempts }: { attempts: number }) {
  return <p>{attempts && <b>Невдалих спроб: {attempts}</b>}</p>
}
```

```text
$ npx tsc --noEmit -p tsconfig.app.json; echo "код виходу tsc: $?"
код виходу tsc: 0
$ npx eslint src/Attempts.tsx; echo "код виходу ESLint: $?"
код виходу ESLint: 0
```

Обидві програми не надрукували жодного зауваження, а код виходу 0 означає, що вони не знайшли помилок. `tsc` пропускає
цей запис, бо тип виразу є «число або елемент», а число є дозволеним умістом розмітки. ESLint із наборами
`typescript-eslint` recommended і `react-hooks` recommended теж мовчить. Сторінка не падає, а лише показує зайвий
символ. Тому цю помилку знаходить лише приклад у тесті, де число дорівнює нулю. Як його написати, розказано нижче, у
розділі про рецепт.

## Варіанти стану: пропс, який описує одну з кількох форм

Тепер третя потреба. У лекції «TypeScript: основи» ви описали етапи доставки **розрізнюваним об'єднанням**, тобто
типом із кількох варіантів, у кожному з яких спільне поле має свій конкретний рядок. Додамо кур'єрові лічильник спроб:

```tsx
type Delivery =
  | { stage: 'packing' }
  | { stage: 'onTheWay'; courier: string; attempts: number }
  | { stage: 'delivered'; signedBy: string }
```

Такий тип добре підходить для пропса: компонент мусить розібрати кожен варіант окремо, а батько не зможе передати
безглуздий об'єкт. Запис `{ stage: 'packing', courier: 'Ігор' }` дає `TS2353`, а запис `{ stage: 'onTheWay' }` дає
`TS2322`.

Ось рамка й сама картка. Рамка отримує місто й вкладений вміст, а картка вибирає вміст за полем `stage`:

```tsx
function Panel({ city, children }: { city: string; children: ReactNode }) {
  return (
    <section className="panel">
      <h3>Посилка до міста {city}</h3>
      {children}
    </section>
  )
}

function ParcelStatus({ city, delivery }: { city: string; delivery: Delivery }) {
  console.log('виклик для міста', city)
  if (delivery.stage === 'packing') {
    return <Panel city={city}><p>Посилку пакують</p></Panel>
  }
  if (delivery.stage === 'delivered') {
    return <Panel city={city}><p>Отримала: {delivery.signedBy}</p></Panel>
  }
  return (
    <Panel city={city}>
      <p>Везе кур'єр {delivery.courier}</p>
      {delivery.attempts > 0 && <p>Невдалих спроб: {delivery.attempts}</p>}
    </Panel>
  )
}
```

### Що знає компілятор у кожному рядку

**Звуженням** називають те, як компілятор після перевірки уточнює тип змінної. На початку функції `delivery` може бути
будь-яким із трьох варіантів, тому читати можна лише `stage`. Усередині першого `if` компілятор знає, що це варіант
`packing`. Спроба написати там `delivery.courier` дає таку помилку:

```text
TS2339: Property 'courier' does not exist on type '{ stage: "packing"; }'.
```

Після цього `if` стоїть `return`, тому код нижче виконується лише для решти варіантів. Компілятор це враховує: варіант
`packing` викреслено. Після другого `if` лишається один варіант, `onTheWay`, тому в останньому `return` читати
`courier` можна без жодної перевірки.

### Де ця перевірка закінчується

**Розкладати об'єкт треба після перевірки.** Запис `const { stage, courier } = delivery` на початку функції дає
`TS2339: Property 'courier' does not exist on type 'Delivery'`, бо поле `courier` є не в усіх варіантах. Той самий
запис усередині гілки `onTheWay` помилки не дає.

**Новий варіант компілятор помітить не завжди.** Додамо четвертий етап, `{ stage: 'lost'; lastSeen: string }`, і
напишемо дві картки, які про нього не знають. Обидві розбирають `packing` і `onTheWay`, а решту віддають останній
гілці. Остання гілка картки `Reads` читає поле, а остання гілка картки `Silent` жодного поля не читає:

```tsx
type Delivery =
  | { stage: 'packing' }
  | { stage: 'onTheWay'; courier: string; attempts: number }
  | { stage: 'delivered'; signedBy: string }
  | { stage: 'lost'; lastSeen: string } // новий варіант

function Reads({ delivery }: { delivery: Delivery }) {
  if (delivery.stage === 'packing') return <p>Посилку пакують</p>
  if (delivery.stage === 'onTheWay') return <p>Везе кур'єр {delivery.courier}</p>
  return <p>Отримала: {delivery.signedBy}</p> // тут лишилися delivered і lost
}
function Silent({ delivery }: { delivery: Delivery }) {
  if (delivery.stage === 'packing') return <p>Посилку пакують</p>
  if (delivery.stage === 'onTheWay') return <p>Везе кур'єр {delivery.courier}</p>
  return <p>Отримано</p> // тут теж лишилися delivered і lost
}

const lost: Delivery = { stage: 'lost', lastSeen: 'Київ' }
console.log(render(<Reads delivery={lost} />).container.innerHTML)
console.log(render(<Silent delivery={lost} />).container.innerHTML)
```

Про картку `Reads` компілятор повідомляє проблему, а про картку `Silent` не повідомляє нічого:

```text
TS2339: Property 'signedBy' does not exist on type '{ stage: "delivered"; signedBy: string; } | { stage: "lost"; lastSeen: string; }'.
```

Vitest не зважає на цю помилку типів, запускає обидві картки для загубленої посилки й друкує таке:

```text
<p>Отримала: </p>
<p>Отримано</p>
```

Перший рядок надрукувала картка `Reads`. Її помилку можна знайти ще до запуску, бо `tsc` про неї повідомив. Другий
рядок надрукувала картка `Silent`. Отже, якщо остання гілка просто показує напис «Отримано» й жодного поля не читає,
помилки не буде, і загублена посилка на екрані стане отриманою. Для таких випадків у лекції «TypeScript: основи» є
прийом із типом `never`, який змушує компілятор перевірити, що всі варіанти розібрано.

**Під час роботи типів немає.** Vitest і Vite лише вирізають типи й запускають код, про що розповідала та сама лекція.
Тому тест пройде по коду з помилкою типів, а результат залежить від глибини читання. Обидві картки нижче читають поле
`courier` у гілці `packing`, де його немає, тому `tsc` скаржиться на обидві:

```tsx
function Soft({ delivery }: { delivery: Delivery }) {
  if (delivery.stage === 'packing') return <p>Везе кур'єр {delivery.courier}</p>
  return null
}
function Hard({ delivery }: { delivery: Delivery }) {
  if (delivery.stage === 'packing') return <p>{delivery.courier.toUpperCase()}</p>
  return null
}

console.log(render(<Soft delivery={{ stage: 'packing' }} />).container.innerHTML)
try {
  render(<Hard delivery={{ stage: 'packing' }} />)
} catch (error) {
  console.log((error as Error).message)
}
```

```text
<p>Везе кур'єр </p>
Cannot read properties of undefined (reading 'toUpperCase')
```

Перший запис читає відсутнє поле, отримує `undefined`, а React його пропускає, тому рядок просто лишається без імені.
Другий запис намагається викликати метод на `undefined` і падає. Отже, таку помилку шукають через `tsc` і підкреслення
в редакторі, а не чекають, поки щось упаде в браузері.

**Необов'язкові поля цього не дають.** Тип `{ stage: string; courier?: string }` компілюється, але компілятор не
пов'язує `stage` із `courier`. На запис `delivery.courier.toUpperCase()` він каже лише `TS18048: 'delivery.courier' is
possibly 'undefined'`, а цю скаргу легко заглушити знаком `!`. Знак `!` є обіцянкою компілятору, що значення є, і
компілятор вірить їй без перевірки.
Документація TypeScript у розділі `Discriminated unions` радить саме такий висновок: зв'язок між полями треба описати
в типі, а не обіцяти його знаком оклику.

## Покроковий приклад: чотири посилки

Покажемо картку з чотирма різними наборами даних і подивимося, що вийшло:

```tsx
const { container } = render(
  <>
    <ParcelStatus city="Львів" delivery={{ stage: 'packing' }} />
    <ParcelStatus city="Одеса" delivery={{ stage: 'onTheWay', courier: 'Ігор', attempts: 0 }} />
    <ParcelStatus city="Київ" delivery={{ stage: 'delivered', signedBy: 'Оксана' }} />
    <ParcelStatus city="Рівне" delivery={{ stage: 'onTheWay', courier: 'Ігор', attempts: 2 }} />
  </>,
)
// Для кожної картки друкуємо вміст її тега section, тобто те, що Panel поклала всередину рамки.
container.querySelectorAll('section').forEach((section) => console.log(section.innerHTML))
```

Перші чотири рядки виводу надрукував `console.log` у тілі `ParcelStatus`, а наступні чотири надрукував останній рядок
цього коду:

```text
виклик для міста Львів
виклик для міста Одеса
виклик для міста Київ
виклик для міста Рівне
<h3>Посилка до міста Львів</h3><p>Посилку пакують</p>
<h3>Посилка до міста Одеса</h3><p>Везе кур'єр Ігор</p>
<h3>Посилка до міста Київ</h3><p>Отримала: Оксана</p>
<h3>Посилка до міста Рівне</h3><p>Везе кур'єр Ігор</p><p>Невдалих спроб: 2</p>
```

Функція одна, а викликів чотири, і кожен виклик отримав власний об'єкт пропсів. Жодна картка нічого не пам'ятає, тому
те саме `delivery` завжди дає ту саму розмітку. Простежимо картку для Одеси:

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | батько | тег стає викликом `_jsx(ParcelStatus, { city: 'Одеса', delivery: {…} })`, створюється елемент |
| 2 | React | викликає `ParcelStatus` і передає об'єкт пропсів |
| 3 | перший `if` | `'onTheWay' === 'packing'` дає `false`, функція йде далі |
| 4 | другий `if` | `'onTheWay' === 'delivered'` дає `false`, функція йде далі |
| 5 | `&&` | `0 > 0` дає `false`, оператор повертає `false`, елемент напису про спроби не створюється |
| 6 | функція | повертає елемент `Panel`, у `children` якого масив із двох значень, абзацу й `false` |
| 7 | React | викликає `Panel`, отримує `section`, для абзацу створює вузол, а для `false` нічого не створює |

Для Рівного п'ятий крок дає інший результат: `2 > 0` дає `true`, оператор повертає праву частину, і картка отримує
другий абзац. Якби ліворуч від `&&` стояло саме `delivery.attempts`, то для Одеси п'ятий крок повернув би `0`, і в
картці з'явилася б цифра.

У завданні дня подібні картки стоять в один рядок. Рядок задає стиль `display: "flex"` на спільному батьку, а сам
вигляд у браузері ми не перевіряли: тести дивляться на текст, ролі й значення `style`.

## Рецепт: приклад на кожен варіант

Рецепт із книжки How to Design Programs не змінюється. Сьогодні уточнюється лише один його крок. У розділах про так
звані **itemizations**, тобто описи даних на зразок «це значення є одним із таких варіантів», книжка наполягає на
зв'язку між даними й кодом. Скільки варіантів в описі даних, стільки гілок у функції й щонайменше стільки прикладів.
Якщо у варіанті є межа, приклад беруть і на межі. Для числа спроб межею є нуль.

| Крок рецепта | Для картки посилки |
|--------------|--------------------|
| опис даних | тип `Delivery`: три варіанти, значення кожного поля пояснено в коментарі |
| призначення й сигнатура | одне речення над функцією й тип пропсів у коді |
| приклади | щонайменше один на варіант, плюс межа: `attempts: 0` і `attempts: 2` |
| перелік вхідних даних | коментар у тілі: що саме доступно в кожній гілці |
| тіло | одна гілка на кожен варіант |
| перевірка | Vitest запускає приклади, а `tsc` перевіряє типи |

### Як перевірити, що нуля немає

Запит `queryByText('0')` повертає `null`, якщо такого елемента немає. Але він шукає елемент, власний текст якого
цілком збігається з рядком, і від цього залежить, чи спіймає приклад пастку:

```tsx
import { cleanup, render, screen } from '@testing-library/react'

const attempts = 0
function A() {
  return <article>{attempts && <b>спроб: {attempts}</b>}<p>Посилку пакують</p></article>
}
function B() {
  return <article><p>Спроб: {attempts && <b>{attempts}</b>}</p></article>
}

const a = render(<A />)
console.log('A:', screen.queryByText('0')?.tagName ?? null, '|', a.container.textContent)
cleanup() // запит шукає в усьому документі, тому перед другим показом прибираємо перший
const b = render(<B />)
console.log('B:', screen.queryByText('0')?.tagName ?? null, '|', b.container.textContent)
```

```text
A: ARTICLE | 0Посилку пакують
B: null | Спроб: 0
```

Рядки виводу друкує `console.log` із результатом запиту й усім текстом картки. Обидва компоненти показують зайвий
нуль. У випадку `A` запит знайшов `<article>`, бо власний текст цього елемента дорівнює `0`, адже текст абзацу
належить абзацу. У випадку `B` власний текст абзацу дорівнює `Спроб: 0`, тому запит нічого не знайшов, і приклад
зелений, хоча помилка є. Отже, якщо нуль стоїть поруч із іншим текстом у тому самому елементі, порівнюйте весь текст,
наприклад методом `toHaveTextContent`.

Такий приклад проходить і на заглушці `return null`, бо на порожній сторінці нуля теж немає. Лекція «JSX» вже
пояснювала, що приклад на відсутність нічого не доводить без пари, де елемент є. Тому поруч потрібен приклад, де
значок справді показано.

### Як заготовка перевіряє, що стану немає

Файл перевірок дня читає текст вашого компонента як рядок, записом `import source from "./StatusCard.tsx?raw"`. Суфікс
`?raw` просить Vite віддати вміст файла рядком, а не виконувати його. Потім перевірка шукає в цьому рядку слова
`useState` і `useReducer`. Так само файл `recipe.test.tsx` читає ваші коментарі над компонентами.

Подивитися на картки можна запуском `npm run dev` за адресою `/f1-d03.html`. Сервер розробки Vite віддає HTML-файл із
кореня проєкту за його іменем. Це можна перевірити програмою `curl`, яка робить запит до сервера й друкує відповідь.
Поки працює `npm run dev`, запустіть в іншому терміналі дві команди. Файл `f1-d03.html` має вже лежати в корені
`spa/`, а програма `grep` залишає з відповіді лише адресу скрипта сторінки:

```bash
curl -s http://localhost:5173/f1-d03.html | grep -o 'src="/src[^"]*"'
curl -s http://localhost:5173/no-such.html | grep -o 'src="/src[^"]*"'
```

```text
src="/src/lessons/f1-d03/preview.tsx"
src="/src/main.tsx"
```

Перший запит повернув саме файл `f1-d03.html`, бо лише він підключає `preview.tsx`. Файла `no-such.html` у проєкті
немає, але сервер не повідомив про помилку, а віддав `index.html`, який підключає `main.tsx`. Отже, якщо за адресою
`/f1-d03.html` ви бачите стартову сторінку проєкту, то файл лежить не в корені `spa/`. Саму сторінку в браузері ми не
відкривали.

## Хто яку помилку ловить

| Помилка | Компілятор JSX | `tsc` | React під час роботи |
|---------|----------------|-------|----------------------|
| `{count && <Badge />}` при нулі | пропускає | мовчить | показує `0` |
| читання `courier` у гілці `packing` | пропускає | `TS2339` | порожнє місце або `TypeError` |
| `props.title = 'x'` | пропускає | мовчить | у розробці `TypeError`, у збірці тихо змінює |
| `props.parcel.city = 'x'`, вкладений об'єкт | пропускає | мовчить | мовчить, дані батька зіпсовано |
| обов'язкового пропа немає | пропускає | `TS2741` | у пропі `undefined` |
| зайвий проп | пропускає | `TS2322` | компонент його не прочитає |
| рамка не виводить `{children}` | пропускає | `TS6133`, якщо проп розкладено в параметрах | мовчить, вміст зникає |
| `{if (ok) 'так'}` | `Unexpected token` | `TS1109` | до запуску не дійде |

Рядок про рамку досі не мав прикладу. Рамка `Frame` розкладає `children` у параметрах, але не виводить його:

```tsx
// файл src/Frame.tsx
import type { ReactNode } from 'react'

export function Frame({ title, children }: { title: string; children: ReactNode }) {
  return <h3>{title}</h3>
}
```

```text
$ npx tsc --noEmit -p tsconfig.app.json
src/Frame.tsx(4,32): error TS6133: 'children' is declared but its value is never read.
```

Числа в дужках означають рядок і позицію в рядку. Отже, забуте `{children}` компілятор знайде лише тоді, коли проп
названо в параметрах. Рамка `Careless` вище не називає `children` у параметрах, тому `tsc` на неї не скаржиться, і
таку помилку може виявити лише приклад у тесті.

Перші чотири рядки показують, що один інструмент цього не закриває. Частину ловить `tsc`, а поведінку закривають
приклади.

## Типові хибні уявлення

**«Пропси приходять рядками, як атрибути HTML».** Рядком є лише значення в лапках. Значення у фігурних дужках
приходить таким, яким воно є: числом, масивом, об'єктом або функцією.

**«`&&` повертає `true` або `false`».** Він повертає один зі своїх операндів. При хибній лівій частині він повертає
саме її.

**«React показує все, що йому віддали».** Числа й рядки він показує. Значення `false`, `true`, `null` і `undefined`
він пропускає. Слова `false` на екрані не буде ніколи, якщо не написати його рядком.

**«Заморожені пропси захищені».** Заморожено один рівень і лише в режимі розробки. Вкладені об'єкти змінюються без
помилки, а у збірці для користувачів заморожування немає взагалі.

**«`<Child />` викликає функцію `Child`».** Цей запис створює лише опис. Функцію викликає React, і лише тоді, коли
опис потрапив у результат показу.

**«`children` завжди масив».** Масив буває лише при кількох дітях. Один елемент приходить сам по собі, а без дітей там
`undefined`.

**«Якщо типи правильні, то показ правильний».** Тип `Delivery` не помітить нуля на екрані й не помітить новий варіант,
коли остання гілка не читає полів. Це завдання прикладів.

## Як це проявиться далі в React

- **День 4, списки й ключі.** Запис `{items.length && <ul>…</ul>}` є тією самою пасткою з нулем, а елементи масиву в
  `children` отримають ключі.
- **День 5, чистота й дерево.** Компонент `Views` із цієї лекції буде прикладом нечистого компонента, а `<StrictMode>`
  покаже таку помилку раніше, бо викличе функцію двічі.
- **День 6, TypeScript у React.** Ви побачите тип `ReactNode` докладно й типи пропсів тегів HTML.
- **День 7, події й стан.** Функція стане пропом, і саме через неї дитина проситиме батька змінити дані. Нові пропси
  приходитимуть не від `rerender`, а зі стану батька.
- **День 10, стан як набір станів екрана.** Те саме розрізнюване об'єднання стане описом стану, а не лише пропа.
- **День 12, спільний стан і скидання стану.** React пов'язує стан компонента з його позицією в дереві, а `false` чи
  `null` теж займають позицію серед дітей. Той день покаже, що від цього залежить, чи збережеться стан.
- **Фаза 3, серверний стан.** Результат `useQuery` у TanStack Query теж є розрізнюваним об'єднанням, тому в гілці
  успіху компілятор знає, що `data` є.

## Перевірте себе

**1. Що отримає функція `Label` для запису `<Label city="Львів" weight={2} fragile />`?**

<details><summary>Відповідь</summary>

Один об'єкт `{ city: 'Львів', weight: 2, fragile: true }`. Значення в лапках прийшло рядком, значення в дужках прийшло
числом, а атрибут без значення дав `true`.

</details>

**2. Компонент оголошено як `function Box({ size = 100 })`. Яким буде `size` для `<Box size={null} />` і чому?**

<details><summary>Відповідь</summary>

`null`. Запасне значення спрацьовує лише тоді, коли пропа немає або він дорівнює `undefined`. Значення `null` є
справжнім значенням.

</details>

**3. Чому компонент не повинен писати `parcel.city = parcel.city.toUpperCase()`, адже помилки не буде?**

<details><summary>Відповідь</summary>

`Object.freeze` заморожує лише сам об'єкт пропсів, а `parcel` лежить уже рівнем нижче, тому запис проходить. Але цей
об'єкт належить батькові, тому зміну побачать сам батько й інші компоненти, а результат показу почне залежати від
порядку компонентів. Нове значення обчислюють у нову змінну.

</details>

**4. Рамка `Careless` не виводить `children`. Чи викликається функція вкладеного компонента?**

<details><summary>Відповідь</summary>

Ні. Запис `<Child />` створив лише елемент. React викликає функцію `Child` тоді, коли елемент потрапляє в результат
показу, а тут він туди не потрапив. Вміст зникає без жодного повідомлення.

</details>

**5. Що покаже `<p>{items.length && <b>є</b>}</p>` для порожнього масиву і для масиву з двох рядків? Як виправити?**

<details><summary>Відповідь</summary>

Для порожнього масиву покаже `0`, бо `&&` повернув ліву частину, а числа React показує. Для двох рядків покаже
`<b>є</b>`. Виправлення: `items.length > 0 && <b>є</b>`, тоді ліворуч стоїть логічне значення, а `false` React
пропускає.

</details>

**6. Чому `const { stage, courier } = delivery` не компілюється на початку функції, а всередині гілки компілюється?**

<details><summary>Відповідь</summary>

На початку `delivery` може бути будь-яким варіантом, а поле `courier` є не в усіх. Після перевірки `stage` компілятор
звужує тип до одного варіанта, у якому `courier` є.

</details>

**7. Приклад перевіряє `queryByText('0')` на `null` і зелений. Чи означає це, що нуля на екрані немає?**

<details><summary>Відповідь</summary>

Ні. Запит шукає елемент, власний текст якого цілком дорівнює `0`. Якщо нуль стоїть поруч із текстом у тому самому
елементі, запит його не знайде. Крім того, такий приклад проходить на заглушці, тому він потребує пари, де значення
справді показано.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| пропси | вхідні дані компонента, один об'єкт-аргумент його функції |
| батько, дитина | компонент, у розмітці якого стоїть тег, і компонент, якого цей тег викликає |
| деструктуризація | запис, який розкладає поля об'єкта на окремі змінні |
| запасне значення | значення пропа, яке діє, коли проп відсутній або дорівнює `undefined` |
| `children` | проп, у якому лежить те, що вкладено між тегами |
| рендер | виклик функції компонента, який дає опис розмітки |
| умовний рендер | показ різної розмітки залежно від даних засобами JavaScript |
| операнд | значення, до якого застосовано оператор |
| розрізнюване об'єднання | тип із кількох варіантів зі спільним полем, яке в кожному варіанті має свій літерал |
| звуження | уточнення типу змінної компілятором після перевірки |
| itemization | у книжці How to Design Programs опис даних на зразок «одне з таких варіантів» |
