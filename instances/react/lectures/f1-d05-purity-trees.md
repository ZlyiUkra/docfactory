# Лекція. Фаза 1, день 5. Чистота й дерево

Досі ви вирішували, що компонент показує. Ця лекція відповідає на інше запитання: що компоненту заборонено робити,
поки він обчислює показ, і чому React так на цьому наполягає. Ви побачите, чому обгортка `<StrictMode>` викликає ваші
функції двічі, куди переносити дії, які справді мають щось змінити, і чому в застосунку є два різні дерева. Читання
займе близько 40 хвилин.

Приклади запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під прикладами
справжній. Перевірку лінтером запущено на ESLint із правилами React. У справжньому браузері приклади не запускалися,
тому біля кожного твердження про браузер сказано, на чому воно тримається.

**Після лекції ви зможете пояснити:**

- які дві умови робить компонент чистим і чому локальний `push` їх не порушує;
- чому нечистий компонент показує правильні числа рівно до першого повторного рендеру;
- що саме `<StrictMode>` викликає двічі, що не викликає двічі й що він робить з ефектами;
- чому на екрані один елемент, хоча тіло компонента виконалося двічі;
- де має стояти дія, яка щось змінює, і чому ефект є останнім варіантом, а не першим;
- чому `<StrictMode>` не можна вимикати заради зручності;
- чим дерево рендеру відрізняється від дерева модулів і на які запитання відповідає кожне.

## Талони в черзі

Ви робите екран для поліклініки. На екрані видно чергу, і кожна людина має талон із номером. Кожен компонент у вас уже
є, а бракує лише номера, тому найпростіше рішення виглядає так: заведемо лічильник і нехай кожен талон бере з нього
наступне число.

```tsx
let nextNumber = 1

function Ticket({ name }: { name: string }) {
  const number = nextNumber
  nextNumber = nextNumber + 1
  return <li>Талон {number}: {name}</li>
}

function Queue({ names }: { names: string[] }) {
  return <ul>{names.map((name) => <Ticket key={name} name={name} />)}</ul>
}
```

Атрибут `key` каже React, який елемент списку який. Докладно його розбирає день «Списки й ключі», а сьогодні він нам
важливий лише тим, що без нього React друкує попередження.

Перевіряємо. Ось три запуски з тими самими трьома іменами. Другий запуск показує той самий компонент із тими самими
пропсами вдруге, а третій починає лічильник спочатку й обгортає застосунок у `<StrictMode>`:

```tsx
const NAMES = ['Оля', 'Ігор', 'Марта']

const first = render(<Queue names={NAMES} />)
console.log('перший показ:  ', first.container.textContent)
first.rerender(<Queue names={NAMES} />)
console.log('другий показ:  ', first.container.textContent)
first.unmount()
nextNumber = 1
const strict = render(<StrictMode><Queue names={NAMES} /></StrictMode>)
console.log('у StrictMode:  ', strict.container.textContent)
```

```text
перший показ:   Талон 1: ОляТалон 2: ІгорТалон 3: Марта
другий показ:   Талон 4: ОляТалон 5: ІгорТалон 6: Марта
у StrictMode:   Талон 2: ОляТалон 4: ІгорТалон 6: Марта
```

Перший рядок виглядає бездоганно, і саме тому такий код доходить до користувачів. Другий рядок показує справжню
проблему: нічого не змінилося, а номери в людей стали іншими. У справжньому застосунку це трапиться, коли батько
перемалюється через будь-яку дрібницю, наприклад через годинник у кутку екрана. Третій рядок показує те саме без
очікування, і далі ми розберемо чому.

Помилка тут не в синтаксисі й не в логіці лічильника. Помилка в тому, що функція, яку ви написали, робить більше, ніж
обчислює розмітку. Назва цієї властивості й правила навколо неї і є темою сьогоднішнього дня.

## Чистий компонент

**Чистою** називають функцію, яка виконує дві умови. Документація React формулює їх дуже коротко, і ось вони своїми
словами.

**Перша умова: функція не змінює нічого, що існувало до її виклику.** Вона не пише в зовнішні змінні й не змінює
об'єктів, які хтось створив раніше.

**Друга умова: ті самі вхідні дані дають той самий результат.** Функція `double(x)`, яка повертає `2 * x`, для числа 3
завжди дає 6. Вона не дасть 7 залежно від часу доби.

React вважає, що кожен ваш компонент є чистою функцією. Це припущення, а не побажання: на ньому побудовано те, як
React планує роботу. Вхідних даних у компонента три. Пропси ви вже знаєте. Стан ви коротко бачили в лекції «Компоненти
й модулі», а контекст, тобто значення, яке компонент читає згори без пропсів, вивчає день 14. Усі три компонент під
час рендеру лише читає.

**Рендером** ми домовилися називати виклик функції компонента. Код усередині цієї функції зверху вниз називають
**тілом** компонента. Тому правило звучить так: тіло компонента лише обчислює розмітку.

`Ticket` порушує обидві умови одразу. Він змінює змінну `nextNumber`, яка існувала до виклику. І він повертає різну
розмітку для того самого імені.

Виправлення полягає не в тому, щоб лічильник працював обережніше. Номер є вхідними даними, тому батько має його
передати:

```tsx
function Ticket({ number, name }: { number: number; name: string }) {
  return <li>Талон {number}: {name}</li>
}

function Queue({ names }: { names: string[] }) {
  return (
    <ul>
      {names.map((name, index) => <Ticket key={name} number={index + 1} name={name} />)}
    </ul>
  )
}
```

```text
перший показ:   Талон 1: ОляТалон 2: ІгорТалон 3: Марта
другий показ:   Талон 1: ОляТалон 2: ІгорТалон 3: Марта
у StrictMode:   Талон 1: ОляТалон 2: ІгорТалон 3: Марта
```

Тепер усі три рядки однакові. Компонент можна викликати скільки завгодно разів, бо кожен виклик лише обчислює розмітку
з того, що йому дали.

### Що саме порушує чистоту

Порушень буває більше, ніж запис у лічильник. Ось типові випадки. Лінтер у цій таблиці означає ESLint із правилами
`react-hooks`, який шаблон проєкту вже підключив, і його результат справжній: ми запустили всі ці рядки в одному
файлі.

| Що робить тіло компонента | Яку умову порушує | Що каже лінтер |
|---------------------------|-------------------|----------------|
| `nextNumber = nextNumber + 1` для зовнішньої змінної | першу | `react-hooks/globals`: Cannot reassign variables declared outside of the component/hook |
| `shown.push(name)` у зовнішній масив | першу | нічого |
| `names.sort()` для масиву з пропсів | першу | нічого |
| `document.title = text` | першу | `react-hooks/immutability`: This value cannot be modified |
| `const now = Date.now()` | другу | `react-hooks/purity`: Cannot call impure function during render |

Дивіться на другий і третій рядки уважно. Запис через метод масиву лінтер не бачить, тому зелений лінтер не доводить,
що компонент чистий. Саме для таких випадків потрібні приклади в тестах і `<StrictMode>`.

Запит у мережу під час рендеру теж порушує першу умову, бо змінює стан сервера чи принаймні витрачає мережу на кожен
виклик. Запис у `console.log` формально теж є дією назовні, але жодні дані програми від нього не залежать. Тому його
вживають для налагодження, а сторінка `<StrictMode>` окремо пояснює, що React DevTools показує рядки другого виклику
блідіше. Цього твердження ми в браузері не перевіряли, воно взяте з документації.

### Читати зовнішнє теж небезпечно

Друга умова стосується читання. Подивімося, що станеться, коли компонент лише читає зовнішню змінну й нічого не пише.
Функція `memo` вчить React пропускати виклик компонента, якщо його пропси не змінилися. Докладно її розбирає фаза 2, а
тут вона показує наслідок дуже наочно. Ліва колонка друкує результат звичайного компонента, а права результат того
самого компонента в `memo`:

```tsx
let rate = 40

function PriceUsual({ uah }: { uah: number }) {
  return <b>{(uah / rate).toFixed(2)}</b>
}
const PriceRemembered = memo(PriceUsual)

// показуємо обидва для 400 гривень, потім міняємо курс і показуємо знову
rate = 50
```

```text
курс 40: 10.00 10.00
курс 50: 8.00 10.00
```

Пропс `uah` дорівнює 400 в обох запусках, тому `memo` вирішив, що результат той самий, і не викликав функцію. Рішення
було правильним для чистого компонента. Але цей компонент читав дані повз вхід, і користувач бачить стару ціну. Курс
треба передати пропом, і тоді `memo` побачить, що вхід змінився.

Це головна причина, чому React наполягає на чистоті: він хоче вирішувати сам, коли викликати ваші функції й коли не
викликати.

### Локальні зміни дозволено

Новачки часто роблять хибний висновок, що чистий компонент не може мати `push` і циклів. Заборона стосується лише
того, що існувало **до** виклику. Те, що ви створили всередині цього самого виклику, ніхто інший ще не бачить:

```tsx
function Numbered({ names }: { names: string[] }) {
  const rows: string[] = []
  for (const name of names) {
    rows.push(`${rows.length + 1}. ${name}`)
  }
  return <p>{rows.join('; ')}</p>
}
```

```text
Numbered у StrictMode: 1. Марта; 2. Ігор; 3. Оля
```

Масив `rows` створюється заново при кожному виклику й зникає разом із ним, тому цей компонент чистий. Такі зміни
називають **локальною мутацією**. Той самий `push` у масив, оголошений рядком вище за функцію, робить компонент
нечистим, хоча текст коду відрізняється лише місцем одного рядка.

Масив із пропсів належить батькові, навіть коли він лежить у вашій змінній. Ось два варіанти сортування. Лекція
«Масиви й об'єкти функційно» вже показувала цю пару методів, а тут видно, чому вона важлива в React:

```tsx
function SortedBad({ names }: { names: string[] }) {
  names.sort()
  return <p>{names.join(', ')}</p>
}

function SortedGood({ names }: { names: string[] }) {
  const sorted = names.toSorted()
  return <p>{sorted.join(', ')}</p>
}
```

```text
після SortedBad, масив батька: [ 'Ігор', 'Марта', 'Оля' ]
після SortedGood, масив батька: [ 'Марта', 'Ігор', 'Оля' ]
```

Компонент `SortedBad` переставив елементи в масиві батька, і тепер кожен інший компонент, який читає цей масив,
отримує новий порядок. Показ обох компонентів виглядає однаково, а різницю видно лише в чужих даних.

Те саме робив компонент `Views` із лекції «Пропси й умовний рендер», який при кожному рендері збільшував
`parcel.views`. Там число росло з кожним `rerender`. Усередині `<StrictMode>` воно одразу стрибає через одиницю:

```text
<p>2</p>
<p>4</p>
```

### Навіщо React це все

Сторінка `Keeping Components Pure` називає три переваги, і кожна пояснює, чому порушення дають такі дивні помилки.

**Перша перевага: той самий компонент може виконуватися в іншому середовищі.** Сервер може викликати компонент, щоб
одразу надіслати готовий HTML. Якщо компонент чистий, його результат не залежить від того, де саме він виконався. Цю
тему вивчає фаза 4.

**Друга перевага: React може пропустити виклик.** Ви щойно бачили це на `memo`: якщо вхід той самий, результат можна
взяти готовий. Фаза 2 у дні про мемоізацію й React Compiler пояснює це докладно. Компілятор сам запам'ятовує
обчислення в компонентах, тому він теж розраховує на те, що компоненти чисті.

**Третя перевага: React може кинути рендер посередині й почати заново.** Якщо дані змінилися, поки React обчислює
глибоке дерево, йому немає сенсу завершувати застарілу роботу. Він викидає результат і починає спочатку. Для чистих
функцій така зупинка нічого не коштує, а нечиста функція вже встигла щось записати, і скасувати цей запис нікому. Цю
поведінку ви побачите у фазі 2, у дні про `useTransition`. Тут ми її не запускали, це переказ документації.

Спільна думка в усіх трьох перевагах одна: **рендер не обов'язково закінчується показом на екрані**, і він може
статися більше разів, ніж ви очікуєте. Тому запис під час рендеру не означає «це зараз показано». Він означає лише, що
React обчислював розмітку.

## Рендер і показ є різними кроками

Щоб зрозуміти, де дозволено щось змінювати, потрібно розрізнити два кроки роботи React. Докладно їх вивчає день 8,
«Рендер, коміт і знімок стану», а тут потрібна лише основна думка.

Спершу React викликає функції компонентів і збирає опис того, що має бути на екрані. Це **рендер**, і під час нього на
сторінці ще нічого не змінилося. Потім React порівнює цей опис із тим, що вже показано, і вносить потрібні зміни в
DOM. Цей другий крок називають **комітом**. Після коміту браузер малює сторінку, як пояснювала лекція «Як браузер
малює».

Тепер розгляньмо три види коду, які всі написано всередині функції компонента, але які виконуються в різний час. Ось
компонент із двома рівнями вкладеності. Батько `Parent` малює дитину `Child`, кожен із них дописує рядок у спільний
журнал `log`, а `Child` ще має кнопку:

```tsx
const log: string[] = []

function Child() {
  log.push('тіло Child')
  useEffect(() => {
    log.push('ефект Child')
    return () => { log.push('прибирання Child') }
  }, [])
  return <button onClick={() => log.push('обробник клацання')}>Далі</button>
}

function Parent() {
  log.push('тіло Parent')
  useEffect(() => {
    log.push('ефект Parent')
    return () => { log.push('прибирання Parent') }
  }, [])
  return <Child />
}
```

Запис у `log` у тілі робить ці компоненти нечистими. Ми пишемо так лише заради досліду, щоб побачити порядок. Ось що
надрукував запуск без `<StrictMode>`:

```text
показ:     тіло Parent → тіло Child → ефект Child → ефект Parent
клацання:  обробник клацання
зникнення: прибирання Parent → прибирання Child
```

Розберімо це за частинами.

**Тіла виконалися першими, згори вниз.** Спершу батько, бо лише він знає, яких дітей малювати, а потім дитина.

**Ефекти виконалися після всіх тіл, знизу вгору.** Ефект дитини пішов раніше за ефект батька.

**Обробник не виконався під час показу.** Стрілка з `onClick` створюється в тілі, але лише створюється. Запустив її
лише клік. Тому обробник не зобов'язаний бути чистим, хоч і написаний усередині компонента. Документація прямо каже,
що побічні дії зазвичай стоять саме в обробниках.

**Прибирання виконалося, коли компонент зник.** Це окрема функція, яку ефект повернув.

### Куди класти дію, яка щось змінює

Дію, яка змінює щось поза компонентом, називають **побічною дією** (side effect). Такі дії потрібні: програма, яка
нічого не змінює, нікому не корисна. Питання лише в тому, де вони стоять.

| Де стоїть код | Коли він виконується | Що там дозволено |
|---------------|----------------------|------------------|
| тіло компонента | під час рендеру, стільки разів, скільки вирішить React | лише обчислення й локальні зміни |
| обробник події | коли людина щось зробила | будь-які зміни, це найкраще місце для них |
| ефект | після коміту, коли компонент з'явився або змінилися його залежності | синхронізація із зовнішньою системою |

Спершу запитайте себе, чи можна обійтися взагалі без дії й просто обчислити результат у розмітці. Якщо дію спричинив
конкретний клік, вона належить обробнику. Ефект лишається для випадку, коли потрібної події просто немає, а щось має
бути правдою весь час, поки компонент показаний. Сторінка `Keeping Components Pure` називає ефект останнім варіантом,
і день 17, «Коли ефект не потрібен», присвячено саме цьому.

## Ефект: скорочено, бо потрібен уже сьогодні

Ефекти докладно вивчає день 16, «Синхронізація ефектами». Лекція «Мережа» вже показувала один приклад, а для
сьогоднішнього завдання потрібні лише основи. **Ефект** є функцією, яку ви передаєте в `useEffect`. React запускає її
після коміту. Вона може повернути ще одну функцію, яку називають **прибиранням**. React викликає прибирання перед
наступним запуском ефекту й коли компонент зникає зі сторінки. Другий аргумент називають **списком залежностей**: це
значення, зміна яких вимагає запустити ефект знову.

Ось приклад справжньої зовнішньої системи. Компонент `Reminder` показує нагадування, а поки він на екрані, працює
таймер браузера, запущений через `setInterval`. Таймером React не керує, тому його й треба синхронізувати вручну.
Лічильник `activeTimers` рахує живі таймери:

```tsx
let activeTimers = 0

function Reminder({ text }: { text: string }) {
  useEffect(() => {
    const timerId = setInterval(() => { /* показати нагадування */ }, 60000)
    activeTimers++
    return () => {
      clearInterval(timerId)
      activeTimers--
    }
  }, [text])
  return <p>Нагадування: {text}</p>
}
```

Розгляньмо рядки по черзі.

- `useEffect(() => { ... }, [text])` оголошує ефект. React сам вирішить, коли його запускати.
- `const timerId = setInterval(...)` запускає таймер і запам'ятовує його номер. Без цього номера таймер не можна
  зупинити.
- `return () => { ... }` повертає прибирання. Функція замикає той самий `timerId`, бо лекція «Функції та замикання»
  пояснила, що функція бачить змінні місця, де її створено.
- `clearInterval(timerId)` зупиняє саме цей таймер.
- `[text]` каже: запустити ефект знову лише тоді, коли змінився `text`.

Без прибирання той самий компонент лишає таймери працювати назавжди. Порівняйте кількість живих таймерів у двох
варіантах:

```text
без прибирання, показ: 1
без прибирання, новий текст: 2
без прибирання, зникнення: 2
```

Компонента вже немає на екрані, а два таймери досі працюють. Ось це й називається витоком: програма тримає те, що
ніхто не використовує. Правило таке: прибирання скасовує рівно те, що зробив цей запуск ефекту.

Є одна поширена описка. Стрілка без фігурних дужок повертає значення виразу, тому запис `useEffect(() =>
setInterval(tick, 60000), [text])` повертає номер таймера, а React вважає все, що повертає ефект, функцією прибирання.
Компілятор каже про це заздалегідь, бо тип результату ефекту дозволяє лише нічого або функцію. Без компілятора запуск
дає `useEffect must not return anything besides a function`, а коли компонент зникає, з'являється `TypeError: destroy
is not a function`.

## Що робить `<StrictMode>`

**`<StrictMode>`** є компонентом React без власної розмітки. Він вмикає додаткові перевірки для всього, що стоїть
усередині нього. Шаблон проєкту вже обгортає ним застосунок у файлі `src/main.tsx`, як показувала лекція «Проєкт:
Vite, лінт, TypeScript». Перевірки працюють лише в режимі розробки. Ось невеликий компонент з ефектом усередині
`<StrictMode>`, запущений без браузера в Node із jsdom. Спершу він працює в режимі розробки, а потім у режимі збірки,
який вмикає змінна середовища `NODE_ENV`:

```text
development → тіло → тіло → ефект → прибирання → ефект
production → тіло → ефект
```

Отже, у режимі збірки `<StrictMode>` не змінює нічого, тому ці перевірки не сповільнюють застосунок користувача.
Vitest запускає React у режимі розробки, тому в тестах подвоєння видно.

### Подвійний виклик

Документація перелічує функції, які `<StrictMode>` викликає двічі. Це ті, що мають бути чистими: тіло компонента,
функція-ініціалізатор у `useState`, функція, передана в функцію встановлення стану, функція в `useMemo` і редюсер у
`useReducer`. Перевіримо все це разом. Компонент `Counter` рахує кожен такий виклик:

```tsx
function Counter() {
  count.body++
  const [n, setN] = useState(() => { count.init++; return 0 })
  const double = useMemo(() => { count.memo++; return n * 2 }, [n])
  const [m, dispatch] = useReducer((state: number) => { count.reducer++; return state + 1 }, 0)
  return (
    <button onClick={() => {
      count.handler++
      setN((old) => { count.update++; return old + 1 })
      dispatch()
    }}>{n} {double} {m}</button>
  )
}
```

| Подія | Режим | тіло | `useState` початок | функція оновлення | `useMemo` | редюсер | обробник |
|-------|-------|------|--------------------|-------------------|-----------|---------|----------|
| показ | без обгортки | 1 | 1 | 0 | 1 | 0 | 0 |
| показ | `<StrictMode>` | 2 | 2 | 0 | 2 | 0 | 0 |
| клацання | без обгортки | 1 | 0 | 1 | 1 | 1 | 1 |
| клацання | `<StrictMode>` | 2 | 0 | 2 | 2 | 2 | **1** |

Останнє число в таблиці найважливіше: обробник виконався один раз. `<StrictMode>` подвоює лише те, що повинно бути
чистим, а обробник не повинен. Тому запит на купівлю в обробнику не піде двічі.

Зверніть увагу на те, чого подвійний виклик не робить. Він не показує компонент на екрані двічі. Обидва виклики тіла
йдуть один за одним ще до коміту, а на екран іде один результат. Запуск вище показує, що це результат другого виклику:
у прикладі з талонами на екрані стоять парні номери. Документація цього порядку не обіцяє, тому не будуйте на ньому
логіку.

### Покроковий приклад: як вийшли номери 2, 4 і 6

Повернімося до першого запуску нечистого `Ticket` у `<StrictMode>`. Ось усі кроки.

| Крок | Хто діє | Що обчислено | `nextNumber` після кроку | Що далі |
|------|---------|--------------|--------------------------|---------|
| 1 | React викликає `Queue` двічі | опис трьох талонів | 1 | у `Queue` немає зовнішніх записів, тому нічого не змінилося |
| 2 | React викликає `Ticket` для Олі вперше | Талон 1 | 2 | результат викинуто |
| 3 | React викликає `Ticket` для Олі вдруге | Талон 2 | 3 | результат лишається |
| 4 | React викликає `Ticket` для Ігоря вперше | Талон 3 | 4 | результат викинуто |
| 5 | React викликає `Ticket` для Ігоря вдруге | Талон 4 | 5 | результат лишається |
| 6 | React викликає `Ticket` для Марти вперше | Талон 5 | 6 | результат викинуто |
| 7 | React викликає `Ticket` для Марти вдруге | Талон 6 | 7 | результат лишається |
| 8 | React робить коміт | три елементи `<li>` | 7 | на екрані номери 2, 4 і 6 |

Чистий компонент у цій таблиці дав би той самий результат на обох викликах, і викидання нічого б не змінило. Подвоєння
не створює помилку. Воно робить видимою ту, яка без нього проявилася б лише при наступному рендері.

### Додатковий цикл для ефектів

Друга перевірка стосується ефектів. Після першого показу React у режимі розробки один раз виконує прибирання й
запускає ефект знову. Тіло при цьому не викликається. Ось той самий `Parent` із `Child`, тепер у `<StrictMode>`:

```text
тіло Parent → тіло Parent → тіло Child → тіло Child → ефект Child → ефект Parent → прибирання Parent → прибирання Child → ефект Child → ефект Parent
```

Перші чотири записи є подвоєними тілами. Далі йдуть звичайні ефекти, а потім повний цикл: усе прибрано й запущено
заново. React таким способом імітує ситуацію, яка в житті трапляється постійно: людина пішла на інший екран і
повернулася. Стан і вузли DOM при цій перевірці зберігаються, змінюються лише запуски ефектів.

Правильне запитання тут звучить не так: «як запустити ефект лише один раз?». Документація ставить його інакше: «як
зробити ефект таким, щоб він витримував повторний запуск?». Подивіться, що дає `<StrictMode>` компонентам із таймером:

```text
без прибирання, StrictMode показ: 2
з прибиранням, StrictMode показ: 1
з прибиранням, новий текст: 1
з прибиранням, зникнення: 0
```

Без прибирання на один компонент уже два живі таймери, і видно це одразу, без жодних кліків. З прибиранням таймер
завжди один, а користувач не може відрізнити цей варіант від одного запуску. Це і є критерій правильного прибирання.

Є випадки, де прибирання не допоможе. Сторінка `Synchronizing with Effects` наводить запит на купівлю товару: якщо він
стоїть в ефекті, то скасувати вже зроблену покупку неможливо. Висновок там такий, що покупку спричиняє клік, а не
показ компонента, тому її місце в обробнику.

### Де діє перевірка

`<StrictMode>` можна поставити навколо частини застосунку, і перевірки діятимуть лише всередині. Але тут є важлива
межа. Ось компонент `A` поза обгорткою й компонент `B` усередині неї, а обгортка стоїть не в корені застосунку:

```tsx
render(<div><Part label="A" /><StrictMode><Part label="B" /></StrictMode></div>)
```

```text
тіло A → тіло B → тіло B → ефект A → ефект B
```

Тіло `B` виконалося двічі, а додаткового циклу ефектів немає. Документація пояснює причину: повторний запуск ефектів
дитини без ефектів батька неможливий у справжній роботі, тому React вмикає цю перевірку лише тоді, коли обгортка
стоїть у корені. Ваш `main.tsx` ставить її саме там, і `render(<StrictMode>...)` у тестах теж.

Третя перевірка стосується посилань, переданих функцією в атрибут `ref`, і працює так само, як цикл ефектів: до неї ми
дійдемо в дні 15. Четверта попереджає про застарілі методи класових компонентів, які в сучасному коді трапляються
рідко.

## Дерево рендеру й дерево модулів

Друга половина дня зовсім про інше. Коли застосунок росте, вам потрібно відповідати на два різні запитання: хто кого
показує, і хто кого імпортує. Відповіді на них виглядають схоже, тому їх легко сплутати.

Ось застосунок черги в кількох файлах. `App` малює обгортку `Shell`, а всередину неї вкладає чергу й підвал. `Queue`
малює талони, а якщо людей немає, то компонент `Empty`.

```tsx
// App.tsx
import { Footer } from './Footer'
import { Queue } from './Queue'
import { Shell } from './Shell'

export function App({ names }: { names: string[] }) {
  return (
    <Shell>
      <Queue names={names} />
      <Footer />
    </Shell>
  )
}
```

```tsx
// Queue.tsx
import { Empty } from './Empty'
import { Ticket } from './Ticket'

export function Queue({ names }: { names: string[] }) {
  if (names.length === 0) return <Empty />
  return <ul>{names.map((name) => <Ticket key={name} name={name} />)}</ul>
}
```

Файл `data.ts` лише зберігає масив імен і не містить жодного компонента, а імпортує його файл входу `main.tsx`.

**Дерево рендеру** показує, який компонент малює якого під час одного рендеру. Кожен вузол цього дерева є компонентом
на своєму місці. Ось порядок викликів із запуску для трьох людей, а нижче він для порожньої черги:

```text
App → Shell → Queue → Ticket «Оля» → Ticket «Ігор» → Ticket «Марта» → Footer
App → Shell → Queue → Empty → Footer
```

З цих викликів складається таке дерево:

```text
App
└── Shell
    ├── Queue
    │   ├── Ticket «Оля»
    │   ├── Ticket «Ігор»
    │   └── Ticket «Марта»
    └── Footer
```

**Дерево модулів** показує, який файл імпортує який. Вузлом є файл, а гілкою рядок `import`. Лекція «Модулі й пакети»
називала цю саму будову графом модулів. Її можна побачити простою командою `grep -n "^import"`:

```text
main.tsx
├── data.ts
└── App.tsx
    ├── Shell.tsx
    ├── Footer.tsx
    └── Queue.tsx
        ├── Empty.tsx
        └── Ticket.tsx
```

У нашому досліді роль `main.tsx` виконував файл тесту. Кожен компонент у досліді ще дописував свою назву в журнал із
допоміжного файла, і цей файл разом із такими рядками тут не показано.

Схожість обманює. Ось чотири відмінності, і кожна видна на цьому прикладі.

| Запитання | Дерево рендеру | Дерево модулів |
|-----------|----------------|----------------|
| Що є вузлом? | компонент на своєму місці | файл |
| Скільки вузлів у `Ticket`? | три, по одному на людину | один файл `Ticket.tsx` |
| Де стоїть `Footer`? | під `Shell`, бо він вкладений у її `children` | під `App.tsx`, бо саме цей файл його імпортує, а `Shell.tsx` про нього не знає |
| Чи є там `data.ts`? | ні, це не компонент | так, якщо його хтось імпортує |
| Що буде для порожньої черги? | замість талонів з'являється `Empty` | нічого не змінюється, файли ті самі |

Рядок про `Footer` особливо важливий. Лекція «Пропси й умовний рендер» пояснювала, що запис `<Footer />` лише створює
елемент, а React викликає функцію тоді, коли цей елемент потрапляє в результат показу. Елемент створив `App`, а в
результат його вставила `Shell`, тому `Shell` малює `Footer`, не маючи жодного рядка `import` про нього.

Рядок про порожню чергу показує ще одну межу: дерево рендеру описує **один** рендер. При іншому пропі воно інше.
Дерево модулів описує файли й не залежить від даних, бо рядки `import` обробляються до запуску коду.

У дереві рендеру немає тегів HTML. Сторінка документації пояснює це тим, що React не прив'язаний до браузера, тому
дерево складається лише з компонентів. Побачити дерево рендеру справжнього застосунку можна у вкладці Components
розширення React DevTools. Цього ми не запускали, бо браузера в нашому досліді немає.

### Навіщо кожне дерево

Дерево рендеру допомагає думати про дані й швидкодію. Компоненти біля кореня впливають на все під собою, а **листки**,
тобто компоненти без дітей, зазвичай перемальовуються найчастіше. Стан зберігається саме в цьому дереві, тому лекція
«Компоненти й модулі» пов'язувала стан із місцем компонента. Фаза 2 використовує це дерево для вимірів у Профайлері.

Дерево модулів допомагає думати про розмір застосунку. Vite використовує його, щоб вирішити, які файли потрапляють у
збірку, а тому файл, якого ніхто не імпортує, до користувача не дійде. Лекція «Проєкт: Vite, лінт, TypeScript»
показувала, що збірка ще й викидає експорти, яких ніхто не використовує. Якщо збірка раптом стала великою, ви шукаєте
причину в цьому дереві, а не в дереві рендеру.

## Рецепт і чистота

Практика дня йде за рецептом книжки How to Design Programs: опис даних, призначення й сигнатура, приклади, перелік
вхідних даних, код, перевірка. Цей рецепт і чистота тісно пов'язані.

Крок «приклади» просить наперед записати очікуваний результат. Це можливо лише тоді, коли той самий вхід завжди дає
той самий вихід, тобто коли функція чиста. Мова BSL, якою написано першу частину книжки, не має присвоєння, тому всі
її функції такі самі й приклади працюють без додаткових умов.

У TypeScript можна написати й функцію, яка змінює переданий масив. Рецепт для неї лишається, але змінюються два кроки.
Призначення має сказати, що саме функція змінює, а приклад перевіряє не повернене значення, а дані після виклику:

```tsx
type Hall = string[]

// Дописує гостя в кінець залу. Функція нічого не повертає, вона змінює переданий масив.
function addGuest(hall: Hall, name: string): void {
  hall.push(name)
}

test('addGuest: новий гість стає в кінець', () => {
  const hall = ['Оля']
  addGuest(hall, 'Ігор')
  expect(hall).toEqual(['Оля', 'Ігор'])
})
```

Масив створено всередині прикладу, тому приклад нічого не ділить з іншими. Якщо ж дані лежать у зовнішній змінній,
вона доживає до наступного тесту, і перед кожним прикладом її доводиться спорожняти. Це ще один наслідок зовнішнього
стану: приклади перестають бути незалежними.

Є й третя думка. Один приклад рідко доводить чистоту, бо нечистий компонент часто проходить перший показ, як `Ticket`
із першого запуску. Потрібні приклади на те, що відбувається далі: другий рендер, рендер у `<StrictMode>`, зникнення
компонента. Сторінка дня перевіряє ці випадки окремо, і кожна перевірка ловить свою частину помилки.

## Типові хибні уявлення

**«`<StrictMode>` ламає мій код, тому його треба прибрати».** Він нічого не ламає, а показує вже наявну помилку. Без
нього номери талонів так само стануть 4, 5 і 6 при другому рендері, лише пізніше й у користувача.

**«Якщо `console.log` надрукувався двічі, компонент показано двічі».** Двічі виконалося тіло. Коміт один, і елемент на
екрані один. Запис у консоль показує кількість викликів, а не кількість показів.

**«`<StrictMode>` подвоює все, зокрема ефекти й обробники».** Обробник виконується один раз. Ефект виконується за
схемою ефект, прибирання, ефект, тобто його запусків два, а між ними стоїть прибирання. Тіло подвоюється до показу, а
цикл ефекту йде після нього.

**«Ефект двічі є помилкою React, тому поставлю прапорець в `useRef`, щоб він спрацював один раз».** Документація
окремо застерігає від цього: прапорець ховає симптом, а прибирання так і лишається ненаписаним. Коли людина піде з
екрана й повернеться, помилка повернеться теж. Та сама сторінка `useRef` забороняє читати й писати `ref.current` під
час рендеру, тому прапорець у тілі компонента робить його ще менш чистим.

**«Запис у `useMemo` виконається один раз, бо результат запам'ятовано».** Функція в `useMemo` теж має бути чистою, і
таблиця вище показує, що `<StrictMode>` викликає її двічі. Запам'ятовування є оптимізацією, а не обіцянкою одного
виклику.

**«Лінтер мовчить, отже компонент чистий».** Ви бачили в таблиці, що запис через `push` у зовнішній масив і `sort` для
пропа лінтер не помічає.

**«Функція оголошена всередині компонента, тому вона теж виконується під час рендеру».** Створення функції і її виклик
є різними діями. Обробник створюється в тілі, а виконується після кліку.

**«Один файл означає один компонент на екрані».** Один файл `Ticket.tsx` дав три вузли в дереві рендеру, і їх може
бути тисяча.

## Як це проявиться далі в React

- **День 7, події й стан.** Обробник стане головним місцем для змін, а функція встановлення стану змінюватиме дані без
  порушення чистоти.
- **День 8, рендер, коміт і знімок стану.** Те, що тут описано двома абзацами, отримає докладний розбір. Ви побачите,
  чому значення стану в межах рендеру не змінюється.
- **День 9, об'єкти й масиви в стані.** Заборона змінювати вхідні дані поширюється на стан: новий об'єкт замість
  зміненого старого.
- **День 13, редюсер.** Редюсер зобов'язаний бути чистим, і `<StrictMode>` викликає його двічі, як показала таблиця.
- **День 15, ref.** Значення в `ref.current` не можна читати й писати під час рендеру з тієї самої причини.
- **Дні 16–19, ефекти.** Прибирання, залежності й ситуації, коли ефект узагалі не потрібен, стануть окремими темами.
- **Фаза 2, мемоізація й React Compiler.** Компілятор запам'ятовує результати в припущенні, що компоненти чисті.
- **Фаза 2, `useTransition`.** React почне переривати рендер, і нечистий код почне давати помилки, які неможливо
  відтворити навмисно.
- **Фаза 4, сервер.** Той самий компонент виконуватиметься на сервері, де ефектів немає: ефект запускається лише в
  браузері.

## Перевірте себе

**1. Які дві умови робить компонент чистим?**

<details><summary>Відповідь</summary>

Перша умова: компонент під час рендеру не змінює нічого, що існувало до його виклику. Друга умова: ті самі пропси,
стан і контекст завжди дають ту саму розмітку.

</details>

**2. Чи чистий компонент, який у тілі створює `const items = []`, у циклі робить `items.push(...)` і показує
результат?**

<details><summary>Відповідь</summary>

Так. Масив створено всередині цього самого виклику, тому його ніхто більше не бачить. Це локальна мутація, і вона
дозволена. Той самий `push` у масив, оголошений поза функцією, чи в масив із пропсів зробив би компонент нечистим.

</details>

**3. Компонент `Ticket` із зовнішнім лічильником показали в `<StrictMode>` для двох людей, починаючи з `nextNumber =
1`. Які номери видно на екрані й чому?**

<details><summary>Відповідь</summary>

Номери 2 і 4. Для кожної людини React виконує тіло двічі. Перша людина забирає номери 1 і 2, а на екрані лишається
результат другого виклику, тобто 2. Друга людина забирає 3 і 4, а на екрані лишається 4.

</details>

**4. У компоненті є `useState`, обробник `onClick` і `useEffect`. Що з цього `<StrictMode>` викличе більше ніж один
раз під час показу й після кліку?**

<details><summary>Відповідь</summary>

При показі двічі виконається тіло й функція-ініціалізатор у `useState`, якщо вона є. Ефект пройде шлях ефект,
прибирання, ефект. Обробник виконається один раз на кожен клік. Якщо в обробнику `setState` отримав функцію, то цю
функцію React викличе двічі, бо вона має бути чистою, а сам обробник не подвоїться.

</details>

**5. Ви бачите в консолі два запити до сервера на один показ. Запит стоїть в ефекті без прибирання. Що робити, якщо це
запит на купівлю, і що, якщо це завантаження даних?**

<details><summary>Відповідь</summary>

Купівлю спричиняє клік, тому її потрібно перенести в обробник, і ефект узагалі прибрати. Для завантаження даних ефект
може бути доречним, і тоді прибирання має скасувати запит чи проігнорувати його результат, як показували лекції
«Асинхронність» і «Мережа». Прибирати `<StrictMode>` не можна в обох випадках, бо він лише показав вже наявну помилку.

</details>

**6. `Shell` показує `{children}`, а `App` пише `<Shell><Footer /></Shell>`. Який файл імпортує `Footer` і хто малює
`Footer` у дереві рендеру?**

<details><summary>Відповідь</summary>

Імпортує `App.tsx`, бо елемент створено там. У дереві рендеру `Footer` стоїть під `Shell`, бо саме `Shell` вставив
його у свою розмітку. Тому два дерева тут розходяться.

</details>

**7. Збірка стала вдвічі більшою після однієї зміни. Яке дерево вам допоможе, і яке дерево допоможе, якщо сторінка
почала повільно реагувати на клік?**

<details><summary>Відповідь</summary>

Розмір збірки залежить від файлів, тому потрібне дерево модулів. Реакцію на клік визначає те, скільки компонентів
перемальовується і як глибоко, тому потрібне дерево рендеру.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| чистий компонент | компонент, який під час рендеру нічого зовнішнього не змінює й для тих самих вхідних даних дає ту саму розмітку |
| тіло компонента | код функції компонента, який виконується під час рендеру |
| рендер | виклик функції компонента, який обчислює опис розмітки |
| коміт | крок, на якому React вносить зміни в DOM |
| побічна дія | будь-яка зміна поза самим обчисленням результату |
| локальна мутація | зміна змінної чи об'єкта, створених у цьому самому виклику |
| обробник події | функція, яку React запускає у відповідь на дію людини |
| ефект | функція, яку React запускає після коміту для синхронізації із зовнішньою системою |
| прибирання | функція, яку повертає ефект, щоб скасувати зроблене ним |
| список залежностей | значення, зміна яких вимагає запустити ефект знову |
| `<StrictMode>` | компонент, який у режимі розробки вмикає додаткові перевірки |
| дерево рендеру | зв'язки «хто кого малює» під час одного рендеру |
| дерево модулів | зв'язки «який файл який імпортує» |
| листок | компонент дерева рендеру без дітей |
