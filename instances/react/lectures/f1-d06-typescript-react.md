# Лекція. Фаза 1, день 6. TypeScript у React

Основи TypeScript ви вивчили у фазі 0, а компоненти вчитеся писати зараз. Ця лекція з'єднує одне з другим: для кожного
місця компонента вона каже, який тип там потрібен, звідки він береться, коли компілятор виведе його сам і що означає
його повідомлення про помилку. Читання займе близько 40 хвилин.

Типи перевірено компілятором `tsc` версії 6.0 із пакетом `@types/react` версії 19.3 і прапорцем `--strict`. Вивід під
прикладами справжній. Код, який мав працювати, запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера
всередині Node. У справжньому браузері приклади не запускалися.

**Після лекції ви зможете пояснити:**

- чому тест проходить, коли проп має неправильний тип, і яка команда це ловить;
- як описати пропси, включно з функцією-пропом і пропсами звичайного тега;
- чим `React.ReactNode` відрізняється від `React.ReactElement`;
- чому винесений обробник потребує типу, а обробник в атрибуті ні, і чим `target` відрізняється від `currentTarget`;
- чому `useState(null)` не приймає нічого, крім `null`, і що означає дивне повідомлення про `(prevState: null) =>
  null`;
- як описати посилання на елемент, дії редюсера й контекст без значення за замовчуванням;
- що робить `@ts-expect-error` і чому пошук слова `any` входить у перевірку дня.

Посилання, редюсер і контекст докладно вивчають пізніші дні. Сьогодні потрібно лише те, що стосується їхніх типів, і
лекція скаже кожного разу, де шукати решту.

## Книжка на сто сторінок

Ви робите каталог бібліотеки. Ось компонент картки книжки й виклик, який написав колега:

```tsx
function BookCard({ title, pages }: { title: string; pages: number }) {
  return <p>{title}, {pages * 2}</p>
}

render(<BookCard title="Кобзар" pages="сто" />)
```

```text
<p>Кобзар, NaN</p>
```

Vitest запускає цей код і не скаржиться, тест зелений, а на екрані стоїть `NaN`. Це той самий поділ, який пояснювала
лекція «TypeScript: основи»: перевірка типів і запуск коду є двома окремими діями. Vitest перед запуском просто
викидає типи й виконує JavaScript, тому він не бачить, що рядок прийшов замість числа. `tsc` нічого не запускає, але
цей рядок не пропустить:

```text
error TS2322: Type 'string' is not assignable to type 'number'.
```

Тому в цьому дні команд дві, і жодна не замінює іншу. У заготовці дня частина тестів уже проходить, бо код працює й
без типів, а `tsc` при цьому друкує двадцять помилок.

Типи в React потрібні в кількох місцях, і в кожному свої правила. Ось усе, про що йтиметься далі.

| Місце в компоненті | Хто пише тип | Головний тип |
|--------------------|--------------|--------------|
| пропси | ви | ваш `type` або `interface` |
| вкладений вміст | ви | `React.ReactNode` |
| обробник в атрибуті | компілятор виводить сам | немає потреби писати |
| винесений обробник | ви | `React.ChangeEvent<HTMLInputElement>` і подібні |
| стан | компілятор, якщо початкове значення каже все, інакше ви | `useState<User \| null>(null)` |
| посилання на елемент | ви | `useRef<HTMLInputElement>(null)` |
| дії редюсера | ви | розрізнюване об'єднання |
| контекст | ви | `createContext<T \| null>(null)` |

## Пропси

Найпростіший спосіб описати пропси ви вже бачили. Коли полів більше двох, тип зручно винести й дати йому назву:

```tsx
type BookCardProps = { title: string; pages: number; rare?: boolean }

export function BookCard({ title, pages, rare = false }: BookCardProps) {
  return <p>{title}, {pages} с.{rare && ' Рідкісна'}</p>
}
```

Замість `type` можна написати `interface BookCardProps { ... }`. Документація React приймає обидва варіанти, і для
пропсів різниці немає. Беріть той, що вже вживається в проєкті.

Тепер компілятор перевіряє кожне місце, де стоїть цей тег. Ось чотири неправильні виклики й те, що сказав `tsc`:

| Виклик | Що сказав `tsc` | Що це означає |
|--------|-----------------|---------------|
| `<BookCard title="Кобзар" pages={320} author="Шевченко" />` | `TS2322: Type '{ title: string; pages: number; author: string; }' is not assignable to type 'IntrinsicAttributes & BookCardProps'` | такого пропа в описі немає |
| `<BookCard titel="Кобзар" pages={320} />` | те саме, плюс `Did you mean 'title'?` | компілятор бачить, що це описка |
| `<BookCard title="Кобзар" pages="320" />` | `TS2322: Type 'string' is not assignable to type 'number'` | тип поля не збігається |
| `<BookCard title="Кобзар" />` | `TS2741: Property 'pages' is missing` | обов'язкове поле відсутнє |

**`IntrinsicAttributes`** є службовим типом із пропсами, які дозволені кожному компоненту. Там є `key`, тому запис
`<BookCard key="1" title="Кобзар" pages={320} />` компілюється, хоча в `BookCardProps` поля `key` немає.

Знак `?` у `rare?: boolean` робить проп необов'язковим. Запасне значення `rare = false` ви вже знаєте з лекції «Пропси
й умовний рендер». Без нього `rare` всередині функції мав би тип `boolean | undefined`.

### Проп-функція

Батько часто передає дитині функцію, щоб дитина могла щось йому повідомити. Її тип записують так само, як тип
будь-якої функції:

```tsx
function Toggle({ onDone }: { onDone: (id: number) => void }) {
  return <button onClick={() => onDone(1)} />
}
```

Запис `(id: number) => void` означає: функція, яка отримує число, а її результат нікого не цікавить. Ось три можливі
виклики цього компонента:

| Виклик | Результат перевірки | Чому |
|--------|---------------------|------|
| `<Toggle onDone={(id) => id * 2} />` | компілюється | результат ігнорують, тому повернути число не заборонено, а тип `id` виведено з опису |
| `<Toggle onDone={() => {}} />` | компілюється | функція може не використовувати аргумент |
| `<Toggle onDone={(id: string) => id} />` | `TS2322`, `Type 'number' is not assignable to type 'string'` | батько очікує рядок, а дитина передасть число |

Другий рядок дивує лише спочатку. Так само `[1, 2].map(() => 0)` працює, хоча `map` передає три аргументи.

### Пропси звичайного тега

Компонент часто є тонкою обгорткою над тегом HTML і має приймати все, що приймає цей тег. Лекція «Пропси й умовний
рендер» показувала, як передати все далі через `{...props}`. Тип для цього теж є: `React.ComponentProps<'button'>`
описує всі пропси тега `<button>`, а знак `&` додає до них ваші.

```tsx
function BusyButton(props: React.ComponentProps<'button'> & { busy: boolean }) {
  const { busy, ...rest } = props
  return <button {...rest} disabled={busy || rest.disabled} />
}

<BusyButton busy onClick={() => {}} type="submit" />
<BusyButton busy href="/x" />
```

Перший виклик компілюється, бо `onClick` і `type` є пропсами кнопки. Другий дає `TS2322`, бо `href` належить
посиланню, а не кнопці. Так само `React.CSSProperties` описує об'єкт для пропа `style`, і запис `{ colour: 'red' }`
дає `TS2561` з підказкою `Did you mean to write 'color'?`.

На роботі ви ще побачите запис `const Card: React.FC<CardProps> = ...`. Сторінка `Using TypeScript` його не
використовує, і нічого нового він не дає: це той самий опис пропсів, записаний інакше. У нього теж немає неявного
`children`, тому `<Fc title="x">текст</Fc>` без оголошеного `children` дає `TS2322`.

## Вкладений вміст: `children`

Лекція «Пропси й умовний рендер» обіцяла докладніше розібрати тип `ReactNode`. Ось його визначення з пакета
`@types/react`, скорочене до того, що вам потрібно:

```ts
type ReactNode =
  | ReactElement
  | string
  | number
  | bigint
  | Iterable<ReactNode>
  | ReactPortal
  | boolean
  | null
  | undefined
  | Promise<AwaitedReactNode>
```

Отже, **`ReactNode`** є об'єднанням усього, що React уміє показати. **`ReactElement`** тут означає результат одного
тега, а `Iterable<ReactNode>` означає масив чи інший перебирний набір таких самих значень. `ReactPortal` і `Promise`
ви зустрінете пізно, і зараз вони неважливі.

Подивимося на компонент `Shelf` із типом `children: React.ReactNode`:

| Виклик | Результат `tsc` |
|--------|-----------------|
| `<Shelf>текст</Shelf>` | компілюється |
| `<Shelf>{7}</Shelf>` | компілюється |
| `<Shelf>{null}{false}{undefined}</Shelf>` | компілюється |
| `<Shelf>{['x', 'y']}</Shelf>` | компілюється |
| `<Shelf />` | `TS2741`, бо поле `children` обов'язкове |
| `<Shelf>{{ title: 'Кобзар' }}</Shelf>` | `TS2353`, бо об'єкт не входить в об'єднання |
| `<Shelf>{new Date()}</Shelf>` | `TS2322: Type 'Date' is not assignable to type 'ReactNode'` |
| `<Shelf>{() => 'x'}</Shelf>` | `TS2322: Type '() => string' is not assignable to type 'ReactNode'` |

Рядок з об'єктом важливий, бо `tsc` тут рятує від справжньої помилки під час роботи:

```text
Error: Objects are not valid as a React child (found: object with keys {title}).
```

Значення, які тип дозволяє, не всі щось показують. Лекція «JSX» уже пояснювала, що `null`, `undefined`, `true` і
`false` на екрані не видно, а число нуль видно. Запуск це підтверджує:
`<Shelf>{null}{false}{undefined}{true}{0}{''}</Shelf>` дає `<section>0</section>`.

Якщо `children` не обов'язковий, пишуть `children?: React.ReactNode`, і тоді `<Shelf />` компілюється.

### Вузький тип `ReactElement`

Другий шлях, який описує документація, є `children: React.ReactElement`. Він приймає лише один елемент. Компонент
`OneOnly` з таким типом поводиться так:

| Виклик | Результат `tsc` |
|--------|-----------------|
| `<OneOnly><div /></OneOnly>` | компілюється |
| `<OneOnly>текст</OneOnly>` | `TS2747`: компонент не приймає текст |
| `<OneOnly><div /><div /></OneOnly>` | `TS2746`: очікується одна дитина, а передано кілька |
| `<OneOnly>{null}</OneOnly>` | `TS2322`: `null` не є елементом |

Беріть цей тип лише тоді, коли компонент справді працює з одним елементом. Обгортка, яка просто показує вміст, не
повинна диктувати, що в неї вкладають, тому там потрібен `ReactNode`.

Є межа, про яку документація каже окремо: TypeScript не вміє вимагати елемент певного тега. Написати, що компонент
приймає лише `<li>`, неможливо, бо тип результату будь-якого тега однаковий.

Старий запис `JSX.Element` тепер дає `TS2503: Cannot find namespace 'JSX'`, бо у `@types/react` 19 глобального
простору імен немає. Якщо він потрібен, пишуть `React.JSX.Element`.

### Звідки береться `React.` без імпорту

Ви побачите в заготовці `React.ReactNode` у файлі без рядка `import React`. Пакет оголошує `React` як глобальну назву,
і для **типів** її можна вживати будь-де. Для значень це не працює. Запис `React.useState(0)` без імпорту в модулі
дає:

```text
error TS2686: 'React' refers to a UMD global, but the current file is a module. Consider adding an import instead.
```

Другий спосіб теж правильний: `import type { ReactNode } from 'react'`. Лекція «TypeScript: дженерики» імпортувала цей
тип так само, лише в одному рядку з `useState`.

## Події

Лекція «DOM і події» пояснювала, що браузер передає обробнику об'єкт події. React загортає цей об'єкт у власний.
Докладно обробники вивчає день 7, а для типів досить знати, що на кожну подію є свій тип у `React`:
`React.ChangeEvent`, `React.MouseEvent`, `React.KeyboardEvent` тощо.

### Коли тип пишуть, а коли ні

Коли стрілка стоїть прямо в атрибуті, компілятор знає, яка подія прийде, бо атрибут `onChange` тега `<input>` має
оголошений тип. Це називають виведенням за контекстом:

```tsx
<input onChange={(e) => setCode(e.target.value)} />
```

Винесена функція оголошена окремо, і в момент оголошення компілятор ще не знає, куди її передадуть. Тому без типу в
суворому режимі буде помилка `TS7006: Parameter 'e' implicitly has an 'any' type`. Сам атрибут нічого не підказує, бо
вона стоїть в іншому місці коду.

```tsx
function handleCode(e: React.ChangeEvent<HTMLInputElement>) {
  setCode(e.target.value)
}

<input onChange={handleCode} />
```

Параметр у кутових дужках називає тег, на якому стоїть обробник. Від нього залежить, які поля доступні: у
`HTMLInputElement` поле `value` є. Цей самий обробник не підійде до тега `<select>`:

```text
error TS2322: Type '(e: ChangeEvent<HTMLInputElement, Element>) => void' is not assignable to type 'ChangeEventHandler<HTMLSelectElement, HTMLSelectElement>'.
```

Якщо ви не пам'ятаєте назву типу, напишіть обробник стрілкою в атрибуті й наведіть курсор на `e` у редакторі.
Документація радить саме так. Це підказка редактора, і запуском ми її не перевіряли.

Весь обробник теж можна описати одним типом, і тоді тип параметра виводиться сам:

```tsx
const handleCode: React.ChangeEventHandler<HTMLInputElement> = (e) => setCode(e.target.value)
```

### `target` і `currentTarget`

Лекція «DOM і події» показала, що `target` є вузлом, на якому подія виникла, а обробник може стояти вище. Для цього є
друге поле: `currentTarget` є вузлом, на якому стоїть обробник. Подивимося, як це описано в типах.

```tsx
function handleClick(e: React.MouseEvent<HTMLButtonElement>) {
  console.log(e.currentTarget.value)
  console.log(e.target.value)
}
```

```text
error TS2339: Property 'value' does not exist on type 'EventTarget'.
```

Перший рядок компілюється, а другий ні. Тип каже правду: клік міг статися на будь-якому вузлі всередині кнопки. Запуск
це показує. Для `<button onClick={...}><b>Видати</b></button>` і кліку по тексту `tagName` дає такі значення:

```text
target: B
currentTarget: BUTTON
```

Для `ChangeEvent` є виняток: поле `target` описано так само, як `currentTarget`. Для поля вводу це правда, бо подія
виникає саме на ньому. Запуск дає `поле: INPUT INPUT`. Але подія зміни спливає, і обробник можна поставити на форму:

```tsx
<form onChange={(e) => e.target.elements.length}>
  <input />
</form>
```

Цей код компілюється, а під час роботи `e.target` є полем вводу, у якого `elements` немає:

```text
форма: INPUT FORM
elements: undefined
```

Коментар у самому файлі типів називає це неправильним описом, який лишено для зворотної сумісності до React 20. Тому
на практиці ставте обробник зміни на сам елемент, і тоді опис правильний. Документація в прикладі читає
`event.currentTarget.value`, а заготовка дня читає `e.target.value`. Для поля вводу з обробником на ньому ці записи
однакові.

### Подія відправлення форми

План називає тип `React.FormEvent<HTMLFormElement>`, і такий обробник компілюється. Але в `@types/react` 19.3 цей тип
позначено `@deprecated`, тобто застарілим, бо такої події насправді немає. Редактор закреслить його. Для відправлення
форми є точніший тип `React.SubmitEvent<HTMLFormElement>`, де `target` завжди є формою, а `submitter` є кнопкою, яка
спричинила відправлення, або `null`. Перевірки дня проходять з обома типами, а примітка на сторінці дня каже, що
змінити в команді `grep`, якщо ви виберете другий.

Метод `preventDefault` ви вже знаєте з лекції «DOM і події». Він скасовує дію браузера, тобто перезавантаження
сторінки після відправлення форми.

### Пастка з назвою без `React.`

Типи `MouseEvent`, `KeyboardEvent` і `SubmitEvent` є ще й у DOM, як глобальні. Якщо забути префікс, то ви опишете іншу
подію:

```tsx
function handleClick(e: MouseEvent) { console.log(e.clientX) }

<button onClick={handleClick}>B</button>
```

```text
error TS2322: Type '(e: MouseEvent) => void' is not assignable to type 'MouseEventHandler<HTMLButtonElement>'.
```

Компілятор друкує майже однакові назви, тому причину легко не помітити. Коли в повідомленні стоять
`MouseEvent<HTMLButtonElement, MouseEvent>` і просто `MouseEvent`, перевірте префікс.

## Стан

Лекція «TypeScript: дженерики» пояснила, що `useState` є дженериком, і тип стану виводиться з початкового значення.
Тут важливо зрозуміти, де цього досить, а де ні. Ось усе разом, а поруч те, що сказав `tsc`:

| Код | Тип стану | Що вийшло |
|-----|-----------|-----------|
| `const [count, setCount] = useState(0)`, потім `setCount('сім')` | `number` | `TS2345`: рядок не підходить |
| `const [wide, setWide] = useState('idle')`, потім `setWide('будь-що')` | `string` | компілюється, хоча ви хотіли лише кілька значень |
| `const [narrow, setNarrow] = useState<Status>('idle')`, потім `setNarrow('будь-що')` | `Status` | `TS2345`: цього значення немає в об'єднанні |
| `const [book, setBook] = useState(null)`, потім `setBook({ title: 'Кобзар', pages: 320 })` | `null` | `TS2353`, розбір нижче |
| `const [good, setGood] = useState<Book \| null>(null)`, потім `good.title` | `Book \| null` | `TS18047: 'good' is possibly 'null'` |
| `const [list, setList] = useState([])`, потім `setList([книжка])` | `never[]` | `TS2322`: `not assignable to type 'never'` |
| `const [books, setBooks] = useState<Book[]>([])` | `Book[]` | компілюється |
| `const [later] = useState<Book>()`, потім `later.title` | `Book \| undefined` | `TS18048: 'later' is possibly 'undefined'` |

Другий рядок найпідступніший. Помилки немає, але перевірки теж немає, бо компілятор вважає тип стану рядком. Коли
значень лише кілька, напишіть їхнє об'єднання явно. Те саме стосується об'єктів зі спільним полем: розрізнюване
об'єднання з лекції «Пропси й умовний рендер» можна покласти прямо в `useState<RequestState>(...)`.

### Читаємо дивне повідомлення

Повідомлення для `useState(null)` виглядає так:

```text
error TS2353: Object literal may only specify known properties, and 'title' does not exist in type '(prevState: null) => null'.
```

Де тут взялася функція? Функція встановлення стану приймає або нове значення, або функцію, яка обчислює нове значення
зі старого. Коли тип стану `null`, вона приймає `null` або `(prevState: null) => null`. Ви передали об'єкт. Компілятор
бачить, що `null` не підходить, тож намагається зіставити об'єкт із другим варіантом і пише про нього. Отже,
повідомлення каже не про функцію: воно каже, що тип стану занадто вузький.

Лікування полягає в тому, щоб одразу сказати, які значення можливі: `useState<Book | null>(null)`. Тоді читання
`good.title` вимагає перевірки, і це правильно, бо книжки може ще не бути. Запис `good ? good.title : '...'` є
звичайним звуженням із лекції «TypeScript: основи».

## Посилання: коротко

**Посилання**, або ref, є об'єктом із полем `current`, значення якого React не показує на екрані й не стежить за його
зміною. Найчастіше в ньому зберігають вузол DOM. Докладно посилання вивчає день 15.

```tsx
const box = useRef<HTMLInputElement>(null)

box.current?.focus()
return <input ref={box} />
```

Запис `useRef<HTMLInputElement>(null)` дає об'єкт із типом поля `HTMLInputElement | null`, бо до показу вузла ще
немає. Тому `box.current.focus()` дає `TS18047: 'box.current' is possibly 'null'`, а запис із `?.` компілюється.

Тип мусить збігатися з тегом. Посилання `useRef<HTMLDivElement>(null)` на тегу `<input>` дає `TS2322`. Аргумент
обов'язковий, бо в React 19 запис `useRef<HTMLInputElement>()` дає `TS2554: Expected 1 arguments, but got 0`.

## Редюсер: коротко

**Редюсер** є чистою функцією, яка отримує поточний стан і дію, а повертає новий стан. Хук `useReducer` викликає її,
коли компонент надсилає дію. Докладно його вивчає день 13. Типи тут дуже корисні, бо дії природно описати
розрізнюваним об'єднанням, яке ви знаєте з лекції «TypeScript: основи».

```tsx
type LoanState = { reader: string | null }
type LoanAction = { type: 'borrow'; reader: string } | { type: 'return' } | { type: 'lost' }

function loanReducer(state: LoanState, action: LoanAction): LoanState {
  switch (action.type) {
    case 'borrow':
      return { reader: action.reader }
    case 'return':
      return { reader: null }
    default: {
      const rest: never = action
      return rest
    }
  }
}
```

У гілці `borrow` компілятор знає, що `reader` є. Гілку `lost` навмисно пропущено, а прийом із `never` з лекції
«TypeScript: основи» це ловить:

```text
error TS2322: Type '{ type: "lost"; }' is not assignable to type 'never'.
```

Виклики теж перевіряються. Після `const [state, dispatch] = useReducer(loanReducer, initial)` тип `dispatch` приймає
лише справжні дії:

| Виклик | Що сказав `tsc` |
|--------|-----------------|
| `dispatch({ type: 'borrow' })` | `TS2345`: `Property 'reader' is missing` |
| `dispatch({ type: 'borow', reader: 'Оля' })` | `TS2820`: `Did you mean '"borrow"'?` |
| `dispatch({ type: 'return', reader: 'Оля' })` | `TS2353`: поля `reader` у цієї дії немає |

Редюсер без цих помилок працює: дія `borrow` з читачкою Олею дала `{ reader: 'Оля' }`, а `return` дав `{ reader: null
}`.

## Контекст: коротко

**Контекст** передає значення вглиб дерева компонентів без пропсів на кожному рівні. Його створює `createContext`,
значення кладе **провайдер**, тобто компонент, який обгортає частину дерева, а читає хук `useContext`. У React 19
провайдером є сам об'єкт контексту, тому пишуть `<LibraryContext value={...}>`. Докладно контекст вивчає день 14.

Проблема для типів така. Контекст має значення за замовчуванням, яке React віддає, коли провайдера немає. Для
бібліотеки розумного значення немає: місто й години роботи неможливо вигадати. Тому створюють контекст із `null` і
прямо кажуть про це в типі:

```tsx
type LibraryValue = { city: string; openUntil: number }

const LibraryContext = createContext<LibraryValue | null>(null)

function useLibrary(): LibraryValue {
  const value = useContext(LibraryContext)
  if (value === null) {
    throw new Error('useLibrary: компонент має бути всередині LibraryContext')
  }
  return value
}
```

Розгляньмо рядки.

- `createContext<LibraryValue | null>(null)` каже, що тут лежить значення або `null`. Без параметра типу
  `createContext(null)` дозволяє лише `null`: запис `<Bare value={{ city: 'Львів' }}>` дає `TS2322: ... not assignable
  to type 'null'`.
- `function useLibrary(): LibraryValue` обіцяє результат без `null`. Це сигнатура в коді, і компілятор перевіряє її
  виконання.
- `useContext(LibraryContext)` повертає `LibraryValue | null`.
- `if (value === null) throw ...` є звичайним звуженням. Після цього рядка лишився лише `LibraryValue`.
- `return value` проходить перевірку лише завдяки попередньому рядку.

Без перевірки компілятор не пропустить таке тіло:

```text
error TS2322: Type 'LibraryValue | null' is not assignable to type 'LibraryValue'.
```

Компоненти, які читають контекст через цей хук, отримують значення без `null` і без жодної своєї перевірки. Компонент,
який читає контекст напряму, дістане `TS18047: 'value' is possibly 'null'`.

### Знак оклику

Перевірку можна обійти коротшим записом: `return useContext(LibraryContext)!`. Знак `!` після виразу називають
**оператором ненульовості**. Він нічого не робить під час роботи, а лише каже компілятору: повір, тут не `null`. Це
така сама обіцянка, як `as` із лекції «TypeScript: основи». Компілятор мовчить, а ось що станеться, коли провайдера
немає, для двох варіантів хука. Варіант зі знаком `!` у досліді називається `usePromise`:

```text
Error: useLibrary: компонент має бути всередині LibraryContext
TypeError: Cannot destructure property 'city' of 'usePromise(...)' as it is null.
```

Перший рядок одразу каже, що зробити. Другий повідомляє про наслідок у чужому рядку коду.

Значення за замовчуванням замість `null` теж прибрало б `null` із типу. Але тоді забутий провайдер перестає бути
помилкою, і компонент мовчки покаже вигадане місто.

Документація пише перевірку як `if (!object)`. Для об'єктів це однаково, але не для кожного значення. Контекст типу
`number | null` зі значенням `0` і перевіркою `if (!value)` кинув помилку попри наявний провайдер:

```text
нуль: Error: немає провайдера
```

Тому порівнюйте з `null` прямо. Причину пояснює таблиця хибних значень із лекції «Пропси й умовний рендер».

Перевірка працює лише під час запуску. Типи не можуть знати, чи стоїть провайдер вище в дереві, бо дерево рендеру
складається під час роботи. Тому в прикладах дня є тест, який запускає хук без провайдера.

## Покроковий приклад: типізуємо форму повернення книжки

Ось компонент, написаний без типів. Він працює: працівник вводить код книжки, форма шукає її й повідомляє батька.

```tsx
export function ReturnForm({ books, onReturn }) {
  const [code, setCode] = useState('')
  const [last, setLast] = useState(null)

  function handleCode(e) {
    setCode(e.target.value)
  }

  function handleSubmit(e) {
    e.preventDefault()
    const book = books.find((b) => b.code === code)
    setLast(book)
    onReturn(book.code)
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={code} onChange={handleCode} />
      <button>Повернути</button>
      {last && <p>Повернуто: {last.title}</p>}
    </form>
  )
}
```

Додаємо типи по одному й щоразу запускаємо `tsc`. Таблиця показує справжню кількість помилок.

| Крок | Що ми дописали | Помилок `tsc` | Що лишилося |
|------|----------------|---------------|-------------|
| початок | нічого | 6 | `TS7031` для `books` і `onReturn`, `TS7006` для двох `e` і для `b`, `TS2339` про `never` для `last.title` |
| опис пропсів | `type Book = { code: string; title: string }`, `ReturnFormProps` | 5 | `b` тепер виведено з масиву, зате з'явилися дві нові помилки про `book` |
| типи подій | `React.ChangeEvent<HTMLInputElement>`, `React.SubmitEvent<HTMLFormElement>` | 3 | дві помилки про `book` і одна про `last.title` |
| тип стану | `useState<Book \| null>(null)` | 2 | `TS2345` для `setLast(book)`, `TS18048: 'book' is possibly 'undefined'` |
| перевірка | `if (book === undefined) return` | 0 | нічого |

Зверніть увагу на другий крок: коли типів стало більше, компілятор побачив те, що раніше ховав `any`. Метод `find`
повертає `Book | undefined`, бо книжки з таким кодом може не бути. Без типів `book.code` впав би під час роботи для
неправильного коду, а тепер цей випадок треба обробити ще до запуску. Компілятор знайшов не описку, а справжню помилку
в логіці.

Цей приклад також пояснює порядок роботи: спершу опис даних, потім сигнатура, і лише тоді решта. Кожен наступний тип
компілятор виводить із попереднього.

## Рецепт: типи є описом даних

Практика дня йде за рецептом книжки How to Design Programs, і типи відповідають двом його крокам.

Крок «опис даних» просить записати, які дані є в програмі. У книжці це коментар, а у вас це `type`. Крок «сигнатура»
просить сказати, що функція отримує й повертає. Книжка пише сигнатуру коментарем, і перевірити її можна лише приклади.
У вас тип пропсів стоїть у самому коді, тому `tsc` перевіряє кожен виклик. Рядок `function useLibrary(): LibraryValue`
є сигнатурою, яка не пропускає неправильне тіло.

Розрізнюване об'єднання є тим самим переліком варіантів, який книжка називає itemization. Умовою рецепта є те, що
гілок у компоненті стільки ж, скільки варіантів у даних. Прийом із `never` перевіряє цю умову автоматично.

### Приклади для компілятора

Рецепт просить писати приклади до коду. Звичайні приклади в тестах перевіряють поведінку. Для типів потрібні свої
приклади, бо типи теж можна зіпсувати: якщо зробити всі поля необов'язковими, код стане працювати, а перевірка зникне.

Коментар `// @ts-expect-error` просить компілятор вважати помилку в наступному рядку очікуваною. Якщо помилки там
немає, компілятор скаржиться:

```tsx
// @ts-expect-error зайвий рядок
export const fine = 5
// @ts-expect-error справжня помилка
export const notFine: number = 'п'
```

```text
error TS2578: Unused '@ts-expect-error' directive.
```

Помилку видав перший коментар, бо під ним помилки немає. Другий коментар своєї роботи досяг, і рядок під ним не
згадано. Тому такий запис є прикладом для компілятора: він падає, коли типи стають занадто вільними.

Vitest читає ці рядки як звичайний код, тому у функцію, яку ніхто не викликає, їх і кладуть.

### Чому шукаємо слово `any`

**`any`** вимикає перевірку для значення й для всього, що з нього взято. Ось три рядки, і `tsc` не сказав про них
нічого:

```tsx
const data: any = { a: 1 }
export const z = data.foo.bar.baz()
export const q: number = data
```

Другий рядок під час роботи впаде. Третій кладе об'єкт у змінну типу `number`, і помилка відкладається до місця, де це
число буде використано. Лекція «TypeScript: основи» пояснювала, чому для даних ззовні правильний тип `unknown`.

Отже, у дня три перевірки, і кожна бачить своє.

| Команда | Що вона бачить | Чого не бачить |
|---------|----------------|----------------|
| `npx vitest run src/lessons/f1-d06` | чи працює код на прикладах | будь-які типи |
| `npx tsc --noEmit -p tsconfig.app.json` | усі типи в проєкті | поведінку під час роботи, забутий провайдер |
| `grep -rnw any src/lessons/f1-d06` | слово `any` в тексті | неявний `any` (його ловить `tsc`) і рядки з `as` чи `!` |

Лінт шаблону ще додає правило `@typescript-eslint/no-explicit-any`, яке для `function X(p: any)` друкує `Unexpected
any. Specify a different type.`

## Типові хибні уявлення

**«Тести зелені, отже типи правильні».** Vitest викидає типи перед запуском. Приклад із `pages="сто"` проходить і
показує `NaN`.

**«`useState(null)` означає, що тип ще невідомий, і компілятор візьме його з наступного `setState`».** Тип стану
береться лише з першого аргументу, і зараз це `null`. Він не змінюється від того, що ви покладете пізніше.

**«`?.` усуває помилку читання для `useState(null)`».** Запис `?.` прибирає `null`, а від типу `null` більше нічого не
лишається, крім `never`. Запис `last && ...` у покроковому прикладі робить те саме, і там видно `TS2339` про `never`.

**«Щоб помилка зникла, зроблю всі поля необов'язковими».** Помилка зникає разом із перевіркою. Тепер компілятор
дозволяє картку без заголовка, а всередині компонента вимагає перевірок, яких раніше не було. Поле, яке потрібне
завжди, має бути обов'язковим, а стани, що виключають один одного, описує розрізнюване об'єднання.

**«`React.ChangeEvent` без параметра теж точний тип».** Без параметра `e.target` є загальним `Element`, у якого немає
`value`. Параметр обов'язковий, і саме він дає поле.

**«Для винесеного обробника тип виведеться з атрибута, де я його вживаю».** Виведення за контекстом працює лише для
стрілки, яка стоїть безпосередньо в атрибуті.

**«Значення за замовчуванням у контексті безпечніше за `null`».** Воно прибирає `null` з типу, але ховає забутий
провайдер, і помилку знайдуть значно пізніше. Перевірка в хуку повідомляє про цю помилку на першому ж показі.

**«`any` у проміжній змінній нічого не псує».** `any` поширюється на все, що з нього отримано, тому без помилок
компілюється навіть `data.foo.bar.baz()`.

## Як це проявиться далі в React

- **День 7, події й стан.** Сьогоднішні типи подій і стану ви вживатимете щодня, і `useState` отримає докладний опис.
- **День 10, стан як набір станів екрана.** Розрізнюване об'єднання стане основним способом описати екран.
- **День 13, редюсер.** Прийом із `never` ви застосуєте для повного `switch`.
- **День 14, контекст.** Провайдер, значення за замовчуванням і причини перемальовування стануть окремою темою.
  Сьогоднішній хук із перевіркою лишиться тим самим.
- **День 15, ref.** Ви побачите, чому `current` може бути `null` і коли React його заповнює.
- **День 19, власні хуки.** Сигнатура власного хука, як у `useLibrary`, стане звичним записом.
- **Фаза 3, форми й дані.** Бібліотеки React Hook Form і TanStack Query виводять типи зі схем і запитів, а їхні
  помилки ви читатимете так само, як сьогоднішні.

## Перевірте себе

**1. Чому `<BookCard title="Кобзар" pages="сто" />` проходить у Vitest і яка команда це знайде?**

<details><summary>Відповідь</summary>

Vitest викидає типи й виконує JavaScript, тому під час роботи він бачить лише рядок і показує `NaN`. Знайде це `npx
tsc --noEmit -p tsconfig.app.json`, і вона надрукує `TS2322: Type 'string' is not assignable to type 'number'`.

</details>

**2. Чим `React.ReactNode` відрізняється від `React.ReactElement`, і який із них брати для обгортки?**

<details><summary>Відповідь</summary>

`ReactNode` є об'єднанням усього, що React уміє показати: рядки, числа, елементи, масиви, `null`, `undefined`, булеві
значення. `ReactElement` є лише результатом одного тега. Обгортка не повинна обмежувати вміст, тому для неї беруть
`ReactNode`.

</details>

**3. Чому `function handle(e) {...}` дає `TS7006`, якщо стоїть окремо, а `onChange={(e) => ...}` помилки не дає?**

<details><summary>Відповідь</summary>

Стрілка в атрибуті отримує тип з оголошеного типу цього атрибута. Винесена функція оголошена окремо, тому в рядку
оголошення компілятор нічого не знає про її використання. Параметр без типу в суворому режимі є помилкою.

</details>

**4. У вас `<button onClick={handle}><b>Видати</b></button>` і обробник `handle(e:
React.MouseEvent<HTMLButtonElement>)`. Чому `e.target.value` не компілюється, а `e.currentTarget.value`
компілюється?**

<details><summary>Відповідь</summary>

`currentTarget` є вузлом, на якому стоїть обробник, і тут це кнопка. `target` є вузлом, де виникла подія, і клік по
тексту дає `<b>`. Тому компілятор описує його лише як загальний `EventTarget`.

</details>

**5. Що означає повідомлення `'title' does not exist in type '(prevState: null) => null'` і як його лікувати?**

<details><summary>Відповідь</summary>

Стан створено через `useState(null)`, тому його тип `null`, а функція встановлення приймає `null` або функцію, яка
повертає `null`. Переданий об'єкт компілятор зіставляє з другим варіантом і пише про нього. Лікування полягає в типі
зі всіма можливими значеннями: `useState<Book | null>(null)`.

</details>

**6. Навіщо хук `useLibrary` кидає помилку, і чому знак `!` тут гірший?**

<details><summary>Відповідь</summary>

Перевірка на `null` дає два результати: зрозуміле повідомлення про забутий провайдер і тип без `null` для всіх, хто
цей хук викликає. Знак `!` дає лише другий результат, бо нічого не перевіряє під час роботи. Без провайдера код упаде
далі, з повідомленням, яке не каже про причину.

</details>

**7. Над рядком стоїть `// @ts-expect-error`, а `tsc` друкує `Unused '@ts-expect-error' directive`. Що це каже про
ваші типи?**

<details><summary>Відповідь</summary>

Рядок, який мав не компілюватися, тепер компілюється. Отже, типи стали занадто вільними: можливо, поле стало
необов'язковим, або в опис потрапив широкий тип на зразок `string` замість об'єднання.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| `type`, `interface` | два способи дати назву опису об'єкта, для пропсів рівнозначні |
| `IntrinsicAttributes` | службовий тип пропсів, дозволених кожному компоненту, зокрема `key` |
| `React.ReactNode` | усе, що React уміє показати |
| `React.ReactElement` | результат одного тега |
| `React.ComponentProps` | тип усіх пропсів вказаного тега |
| виведення за контекстом | компілятор бере тип параметра з місця, де стоїть функція |
| `target` | вузол, на якому виникла подія |
| `currentTarget` | вузол, на якому стоїть обробник |
| посилання, ref | об'єкт із полем `current`, зміна якого не перемальовує компонент |
| редюсер | чиста функція, яка зі стану й дії обчислює новий стан |
| контекст | спосіб передати значення вглиб дерева без пропсів |
| провайдер | компонент, який кладе значення в контекст для всього під собою |
| оператор ненульовості | знак `!` після виразу, обіцянка компілятору без перевірки |
| `@ts-expect-error` | коментар, який вимагає помилки компіляції в наступному рядку |
