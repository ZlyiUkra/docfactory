# Лекція. Фаза 1, день 8. Рендер, коміт і знімок стану

Учора ви навчилися викликати функцію `set`. Ця лекція пояснює, що відбувається після цього виклику: у якому порядку
React викликає ваші функції й змінює документ, чому змінна стану не змінюється в коді, який уже виконується, і що
React робить, коли функцію `set` викликали кілька разів поспіль. Це два найчастіші запитання на співбесіді: чим рендер
відрізняється від коміту і чому стан в обробнику старий. Читання займе близько 50 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під
прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0, а правила лінтера запущено через ESLint із
набором `react-hooks`. У справжньому браузері приклади не запускалися, тому там, де йдеться про браузер, поруч
сказано, на чому це твердження тримається.

**Після лекції ви зможете пояснити:**

- з яких трьох кроків складається зміна на екрані і що робить кожен із них;
- чому рендер не завжди змінює документ;
- чому `console.log(cups)` одразу після `setCups(cups + 1)` друкує старе число і чому `await` тут не допомагає;
- чому три `setCups(cups + 1)` поспіль додають один, а три `setCups(c => c + 1)` додають три;
- коли React об'єднує кілька викликів `set` в один рендер, а коли ні;
- що побачить таймер, запущений з обробника, і чому;
- як перевірити таймер у тесті, не чекаючи кілька секунд.

## Каса, яка рахує не так

Каса в кав'ярні має кнопку «Три чашки». Ви пишете обробник так, як підказує досвід з JavaScript:

```tsx
function addThree() {
  setCups(cups + 1)
  setCups(cups + 1)
  setCups(cups + 1)
  console.log('тепер чашок:', cups)
  setTimeout(() => alert('чашок: ' + cups), 3000)
}
```

Спочатку `cups` дорівнює нулю. Людина клацає один раз, і все виходить не так, як ви чекали. На екрані з'являється 1, а
не 3. У консолі друкується 0. Через три секунди `alert` показує 0, хоча на екрані вже давно 1.

Кожна з цих трьох несподіванок має точну причину, і всі вони випливають з двох фактів. Перший факт: функція `set` не
змінює змінну, а лише просить React викликати компонент ще раз. Другий факт: кожен виклик компонента має власні
змінні, які ніколи не змінюються. Щоб побачити ці факти, треба спершу зрозуміти, що саме робить React після вашого
виклику.

## Три кроки: запуск, рендер, коміт

Сторінка `Render and Commit` ділить будь-яку зміну на екрані на три кроки.

**Запуск** (trigger) є причиною, через яку React починає роботу. Причин дві: перший показ компонента або зміна стану
цього компонента чи одного з його предків.

**Рендер** є викликом функцій ваших компонентів. Сторінка каже це одним реченням: «"Rendering" is React calling your
components». Функція повертає опис розмітки. Якщо в цьому описі є інші компоненти, React викликає і їх, поки не
отримає повний опис.

**Коміт** є записом у документ. React порівнює новий опис із попереднім і змінює в DOM лише те, що відрізняється. При
першому показі він створює всі вузли й додає їх у документ.

Запуск і рендер не відбуваються одночасно. Ось що видно при першому показі, якщо викликати React без допоміжних
функцій Testing Library:

```tsx
Object.assign(globalThis, { IS_REACT_ACT_ENVIRONMENT: false })
function Hello() {
  console.log('React викликав Hello')
  return <p>Вітаємо</p>
}
const box = document.createElement('div')
const root = createRoot(box)
root.render(<Hello />)
console.log('одразу після root.render:', JSON.stringify(box.innerHTML))
await new Promise((resolve) => setTimeout(resolve))
console.log('трохи пізніше:', JSON.stringify(box.innerHTML))
```

```text
одразу після root.render: ""
React викликав Hello
трохи пізніше: "<p>Вітаємо</p>"
```

Виклик `root.render` є запуском. Він лише поставив завдання, а саму роботу React виконав пізніше. Перший рядок
прикладу вимикає режим тестів React. Без нього React друкував би попередження, що оновлення відбулося поза обгорткою
`act`.

### Усі три кроки на одному компоненті

Компонент `Order` показує чек, поле для побажань і нижній рядок, який ні від чого не залежить. Під час рендеру `Order`
читає текст чека прямо з документа, щоб ми побачили, що там лежить у цю мить. Спостерігач `MutationObserver` є засобом
браузера, який записує зміни текстів і вузлів у документі, і jsdom теж його має:

```tsx
function Receipt({ cups }: { cups: number }) {
  console.log('  рендер Receipt, cups =', cups)
  return <p id="receipt">Чашок: {cups}</p>
}
function Footer() {
  console.log('  рендер Footer')
  return <small>Дякуємо!</small>
}
function Order() {
  const [cups, setCups] = useState(1)
  const [, setTick] = useState(0)
  console.log('  рендер Order: cups =', cups, '| у документі зараз:', document.getElementById('receipt')?.textContent)
  return (
    <>
      <Receipt cups={cups} />
      <input aria-label="побажання" />
      <button onClick={() => setCups(cups + 1)}>Ще чашка</button>
      <button onClick={() => setTick((t) => t + 1)}>Рендер без змін</button>
      <Footer />
    </>
  )
}

console.log('Перший показ')
const { container } = render(<Order />)
const input = screen.getByLabelText<HTMLInputElement>('побажання')
await user.type(input, 'без цукру')
const changes: MutationRecord[] = []
const observer = new MutationObserver((list) => changes.push(...list))
observer.observe(container, { subtree: true, childList: true, characterData: true, characterDataOldValue: true })
function report() {
  changes.push(...observer.takeRecords())
  console.log('  змін у документі:', changes.length, changes.map((r) => `${r.oldValue} → ${r.target.textContent}`))
  changes.length = 0
}
console.log('Клацання «Ще чашка»')
fireEvent.click(screen.getByRole('button', { name: 'Ще чашка' }))
report()
console.log('Клацання «Рендер без змін»')
fireEvent.click(screen.getByRole('button', { name: 'Рендер без змін' }))
report()
console.log('те саме поле?', input === screen.getByLabelText('побажання'), '| у полі:', input.value)
```

```text
Перший показ
  рендер Order: cups = 1 | у документі зараз: undefined
  рендер Receipt, cups = 1
  рендер Footer
Клацання «Ще чашка»
  рендер Order: cups = 2 | у документі зараз: Чашок: 1
  рендер Receipt, cups = 2
  рендер Footer
  змін у документі: 1 [ '1 → 2' ]
Клацання «Рендер без змін»
  рендер Order: cups = 2 | у документі зараз: Чашок: 2
  рендер Receipt, cups = 2
  рендер Footer
  змін у документі: 0 []
те саме поле? true | у полі: без цукру
```

Цей вивід варто читати рядок за рядком, бо в ньому є все.

**Рендер відбувається раніше за запис у документ.** Під час другого рендеру `cups` уже дорівнює 2, а в документі ще
лежить «Чашок: 1». Тому під час рендеру не можна покладатися на те, що документ уже новий.

**Рендер іде вниз по дереву.** Батько перемалювався, тому React викликав і `Receipt`, і `Footer`, хоча `Footer` ні від
чого не залежить і пропсів не отримує. Перемальовується той компонент, стан якого змінився, і всі компоненти під ним.
Сторінка каже, що так працює поведінка за замовчуванням, а оптимізацію робити зарано. Цим займається фаза 2.

**Коміт змінює лише різницю.** Після першого клацання в документі змінився один текстовий вузол: `1` став `2`. Весь
абзац React не створював заново.

**Рендер не гарантує зміни в документі.** Друге клацання викликало всі три функції, але опис вийшов таким самим, тому
записано нуль змін.

**Вузли зберігаються.** Поле лишилося тим самим об'єктом, тому набраний текст нікуди не дівся. Сторінка `Render and
Commit` пояснює це так: поле стоїть у тому самому місці JSX, що й минулого разу, тому React його не чіпає. Це поле
некероване, тобто текст тримає сам браузер.

Є одне уточнення, яке помітно лише інструментом. Ми стежили за текстами й складом вузлів. Якщо стежити ще й за
атрибутами, jsdom покаже, що на кожному рендері React ненадовго ставить на полі атрибут `name` і прибирає його.
Значення поля це не зачіпає, і після коміту поле таке саме.

### Що означає слово «рендер»

Лекція «Як браузер малює» описала кроки браузера: стилі, компонування й малювання. У щоденній мові їх теж називають
рендерингом, тому слова легко сплутати. Документація React навмисно називає крок браузера малюванням (painting).

| Крок | Хто виконує | Що відбувається | Що видно в нашому досліді |
|------|-------------|-----------------|---------------------------|
| запуск | ваш виклик `set` | React отримує прохання | нічого |
| рендер | React викликає ваші функції | обчислюється новий опис | рядки «рендер …» |
| коміт | React | записуються зміни в DOM | рядок «змін у документі» |
| малювання | браузер | на екрані з'являється результат | у jsdom цього кроку немає, бо він нічого не малює |

Останній рядок спирається на лекцію «Як браузер малює» й сторінку `Render and Commit`. Запуском його перевірити не
можна.

Сторінка окремо нагадує, що рендер мусить бути чистим обчисленням. Той самий вхід має давати той самий вихід, і
функція не повинна змінювати те, що існувало до неї. Цю тему розглядав день «Чистота й дерево», а тепер видно одну з
причин: React може викликати функцію частіше, ніж ви думаєте.

## Знімок стану

Тепер головне. Подивіться на рядок `const [cups, setCups] = useState(1)`. Слово `const` тут справжнє: змінна `cups` у
межах одного виклику функції ніколи не змінюється. Кожен рендер є окремим викликом функції, а кожен виклик має власну
змінну `cups`. Її значення React видає на початку виклику, і далі воно лишається таким до кінця.

**Знімком стану** називають значення змінної стану в межах одного рендеру. Сторінка `State as a Snapshot` формулює
правило так: «A state variable's value never changes within a render». Обробник створюється під час рендеру, тому
бачить змінні саме цього рендеру. Це звичайне замикання, про яке йшлося в лекції «Функції та замикання», і нічого
особливого React тут не додає.

Це можна побачити прямо. Збережемо обробник кожного рендеру в масив і викличемо старі обробники пізніше:

```tsx
const reports: (() => void)[] = []

function Order() {
  const [cups, setCups] = useState(1)
  function report() {
    console.log('цей обробник бачить cups =', cups)
  }
  reports.push(report)
  return <button onClick={() => setCups(cups + 1)}>Чашок: {cups}</button>
}

render(<Order />)
await user.click(screen.getByRole('button'))
await user.click(screen.getByRole('button'))
console.log('на кнопці:', screen.getByRole('button').textContent, '| рендерів:', reports.length)
reports[0]()
reports[1]()
reports[2]()
```

```text
на кнопці: Чашок: 3 | рендерів: 3
цей обробник бачить cups = 1
цей обробник бачить cups = 2
цей обробник бачить cups = 3
```

Три рендери створили три різні функції з трьома різними змінними. Стан у самому React уже дорівнює 3, а стара функція
й далі бачить 1, бо читає власну змінну, а не комірку всередині React.

### Метод підстановки

Сторінка радить простий прийом: подумки підставте значення стану в код обробника. Якщо в цьому рендері `cups` дорівнює
нулю, обробник із першого прикладу означає те саме, що:

```text
setCups(0 + 1)
setCups(0 + 1)
setCups(0 + 1)
console.log('тепер чашок:', 0)
setTimeout(() => alert('чашок: ' + 0), 3000)
```

Так усі три несподіванки стають очевидними. Друк показує нуль, бо там стоїть нуль. Таймер показує нуль, бо там стоїть
нуль. Функцію `set` тричі просять записати одиницю.

### Чому не допомагає очікування

Перша думка часто така: `set` просто ще не встиг, треба трохи почекати. Це хибна думка, і її можна спростувати
найсильнішим способом. React має функцію `flushSync`, яка змушує його виконати рендер і коміт просто зараз, ще до
наступного рядка. Вона потрібна для рідкісних випадків, коли документ має оновитися негайно. Порівняймо:

```tsx
function Order() {
  const [cups, setCups] = useState(1)
  const text = () => document.getElementById('receipt')!.textContent
  return (
    <>
      <p id="receipt">Чашок: {cups}</p>
      <button onClick={() => {
        setCups(cups + 1)
        console.log('після set:       cups =', cups, '| у документі:', text())
      }}>звичайно</button>
      <button onClick={() => {
        flushSync(() => setCups(cups + 1))
        console.log('після flushSync: cups =', cups, '| у документі:', text())
      }}>flushSync</button>
    </>
  )
}

render(<Order />)
await user.click(screen.getByRole('button', { name: 'звичайно' }))
await user.click(screen.getByRole('button', { name: 'flushSync' }))
```

```text
після set:       cups = 1 | у документі: Чашок: 1
після flushSync: cups = 2 | у документі: Чашок: 3
```

Читайте другий рядок. Рендер і коміт уже завершилися, документ показує 3, а змінна цього обробника так і лишилася 2.
Отже, причина не в часі. Новий рендер створив нову змінну, а стару змінну ніхто не змінював і змінювати не буде. З
тієї самої причини не допомагає і `await`: після нього обробник читає ту саму змінну.

Якщо наступне значення потрібне в тому самому обробнику, обчисліть його самі й покладіть в іншу змінну: `const next =
cups + 1`, потім `setCups(next)`. Довідник `useState` радить саме це в розділі `I've updated the state, but logging
gives me the old value`.

### Навіщо це взагалі так влаштовано

Знімок захищає від помилок із часом. Сторінка `State as a Snapshot` наводить форму, яка надсилає повідомлення із
затримкою п'ять секунд. Людина натискає «Надіслати» адресатові Alice, а поки триває затримка, змінює поле на Bob.
Повідомлення все одно каже про Alice, бо обробник бачить стан на мить натискання. Завдяки цьому вам не треба думати,
чи змінилося щось, поки код чекав.

## Черга оновлень

Тепер про саму функцію `set`. Вона не лише просить новий рендер, а ще й записує, що зробити зі станом. React складає
ці записи в **чергу** й обробляє її під час наступного рендеру. Сторінка `Queueing a Series of State Updates` описує
це так: React чекає, поки виконається весь код обробника, і лише тоді береться за оновлення.

### Пакетування

**Пакетуванням** (batching) називають те, що кілька викликів `set` дають один рендер. Без нього кожен виклик `set`
запускав би окремий рендер, і людина могла б побачити наполовину оновлений екран. Ось як далеко це правило сягає:

```tsx
let parents = 0
let children = 0
function Child({ onDone }: { onDone: () => void }) {
  children = children + 1
  const [paid, setPaid] = useState(0)
  return <button onClick={() => { setPaid(paid + 1); onDone() }}>Оплачено: {paid}</button>
}
function Parent() {
  parents = parents + 1
  const [total, setTotal] = useState(0)
  return <><Child onDone={() => setTotal(total + 1)} /><p>Разом: {total}</p></>
}

render(<Parent />)
console.log('перший показ: батько', parents, '| дитина', children)
await user.click(screen.getByRole('button'))
console.log('після клацання: батько', parents, '| дитина', children)
```

```text
перший показ: батько 1 | дитина 1
після клацання: батько 2 | дитина 2
```

Одне клацання змінило стан у двох різних компонентах, а рендер був один на обох. Наступна таблиця показує межі цього
правила. Кожен рядок ми запустили в jsdom через Testing Library, а в браузері не запускали. Її обгортка `act` змушує
React завершити роботу відразу після події:

| Що зроблено | Рендерів | Чому |
|-------------|----------|------|
| два `set` в обробнику | 1 | обидва виклики стоять в одному обробнику |
| два `set` усередині одного `setTimeout` | 1 | React об'єднує їх і поза обробниками |
| `set`, потім `await`, потім `set` | 2 | код після `await` виконується вже після того, як обробник повернув керування |
| подвійне клацання, по одному `set` на клацання | 2 | кожна подія обробляється окремо |

Останній рядок сторінка пояснює так: React не об'єднує оновлення з різних навмисних подій, наприклад клацань. Якщо
перше клацання вимкнуло кнопку форми, друге вже не надішле її вдруге.

### Що лежить у черзі

Функція `set` приймає два види значень, і вони діють у черзі по-різному.

- **Будь-яке значення, крім функції,** означає «заміни стан на це». Те, що було в черзі перед ним, не має значення.
- **Функція** означає «обчисли наступне значення з попереднього». Таку функцію називають **оновлювачем**. React
  передає їй те, що вийшло перед нею в черзі, а не змінну рендеру.

Тепер три варіанти кнопки «Три чашки», коли `cups` дорівнює нулю:

| Виклик | Що лягає в чергу | Як React проходить чергу | Результат |
|--------|------------------|--------------------------|-----------|
| `setCups(cups + 1)` тричі | заміни на 1, заміни на 1, заміни на 1 | 1, потім 1, потім 1 | 1 |
| `setCups(c => c + 1)` тричі | три оновлювачі | 0 → 1, 1 → 2, 2 → 3 | 3 |

Перший рядок є наслідком знімка: `cups + 1` обчислив JavaScript ще до виклику `set`, і всі три рази вийшла одиниця.
Другий рядок працює тому, що оновлювач не читає `cups`.

### Простежимо мішану чергу

Візьмемо чергу, де є обидва види. Кнопка викликає чотири `set` поспіль, а `cups` спочатку дорівнює 1:

```tsx
function Till() {
  const [cups, setCups] = useState(1)
  function mixed() {
    setCups(cups + 2)
    setCups((c) => c * 2)
    setCups(10)
    setCups((c) => c - 1)
    console.log('наприкінці обробника cups =', cups)
  }
  function swapped() {
    setCups((c) => c * 2)
    setCups(cups + 2)
  }
  return (
    <>
      <p>Чашок: {cups}</p>
      <button onClick={mixed}>мішана</button>
      <button onClick={swapped}>навпаки</button>
    </>
  )
}

render(<Till />)
await user.click(screen.getByRole('button', { name: 'мішана' }))
console.log(screen.getByText(/Чашок/).textContent)
await user.click(screen.getByRole('button', { name: 'навпаки' }))
console.log(screen.getByText(/Чашок/).textContent)
```

```text
наприкінці обробника cups = 1
Чашок: 9
Чашок: 11
```

| Запис у черзі | Що отримує | Що повертає |
|---------------|------------|-------------|
| заміни на `3`, бо `cups + 2` дорівнює `1 + 2` | `1`, не використовується | `3` |
| `c => c * 2` | `3` | `6` |
| заміни на `10` | `6`, не використовується | `10` |
| `c => c - 1` | `10` | `9` |

Кнопка «навпаки» показує, що порядок має значення. Спочатку `cups` дорівнює 9. Оновлювач дає 18, а наступний запис
замінює стан на `9 + 2`, тобто на 11. Якби React просто складав або об'єднував зміни, порядок не мав би значення.

### Коли саме виконується оновлювач

Сторінка каже, що React проходить чергу під час наступного рендеру, коли компонент викликає `useState`. Перевірмо, де
стоять оновлювачі серед інших рядків:

```tsx
function Till() {
  console.log('рендер: початок')
  const [cups, setCups] = useState(0)
  console.log('рендер: cups =', cups)
  function add() {
    console.log('обробник: початок')
    setCups((c) => { console.log('  перший оновлювач, c =', c); return c + 1 })
    setCups((c) => { console.log('  другий оновлювач, c =', c); return c + 1 })
    console.log('обробник: кінець')
  }
  return <button onClick={add}>Чашок: {cups}</button>
}

render(<Till />)
console.log('--- перше клацання')
await user.click(screen.getByRole('button'))
console.log('--- друге клацання')
await user.click(screen.getByRole('button'))
```

```text
рендер: початок
рендер: cups = 0
--- перше клацання
обробник: початок
  перший оновлювач, c = 0
обробник: кінець
рендер: початок
  другий оновлювач, c = 1
рендер: cups = 2
--- друге клацання
обробник: початок
обробник: кінець
рендер: початок
  перший оновлювач, c = 2
  другий оновлювач, c = 3
рендер: cups = 4
```

Друге клацання показує те, що описує сторінка: обробник закінчився, рендер почався, усередині `useState` виконалися
обидва оновлювачі, і лише потім компонент отримав число. Перше клацання показує виняток, про який сторінка не згадує:
перший оновлювач виконався ще всередині виклику `set`. Це внутрішня оптимізація React: коли черга порожня, він може
обчислити результат наперед, щоб перевірити, чи стан узагалі зміниться. Ми спостерігали цей виняток у нашому запуску,
і в документації він не описаний, тому покладатися на нього не можна.

Висновок з цього простий: не робіть в оновлювачі нічого, що залежить від моменту виклику. Сторінка вимагає, щоб
оновлювач був чистим і лише повертав результат. У `StrictMode`, тобто в перевірному режимі розробки, React викликає
кожен оновлювач двічі й один результат відкидає. У нашому запуску кожен оновлювач у цьому режимі виконався двічі. Якщо
оновлювач чистий, ви цього не помітите.

### Коли стан не змінюється

Якщо нове значення збігається зі старим, React пропускає оновлення. Він порівнює значення через `Object.is`, тобто
функцію, яка перевіряє, чи це те саме значення:

```tsx
let renders = 0
function Same() {
  renders = renders + 1
  const [cups, setCups] = useState(1)
  return <><button onClick={() => setCups(1)}>Записати 1</button><button onClick={() => setCups(2)}>Записати 2</button><p>{cups}</p></>
}
const click = async (name: string) => {
  await user.click(screen.getByRole('button', { name }))
  console.log(name, '| рендерів усього:', renders)
}

render(<Same />)
await click('Записати 1')
await click('Записати 2')
await click('Записати 2')
await click('Записати 2')
```

```text
Записати 1 | рендерів усього: 1
Записати 2 | рендерів усього: 2
Записати 2 | рендерів усього: 3
Записати 2 | рендерів усього: 3
```

Запис того самого значення рендеру не дав. Третій рядок показує межу, про яку попереджає довідник `useState`: іноді
React ще раз викликає компонент, а вже потім пропускає його дітей. На екрані нічого не змінюється, і ваш код не
повинен на це зважати.

Через те саме порівняння не працює `order.cups = 5; setOrder(order)`. Об'єкт той самий, тому React вважає, що змін
немає, і рендеру не буде. Це тема дня «Об'єкти й масиви в стані».

### Дві пастки з функціями

Функція `set` вважає будь-яку функцію оновлювачем. Звідси випливають дві помилки, і обидві ми перевірили запуском.

**Оновлювач без `return`.** Запис `setCups((c) => { c + 1 })` має фігурні дужки, тому нічого не повертає. Стан стає
`undefined`, а на екрані лишається «Чашок: » без числа. `tsc` це ловить: `TS2345`, тип `(c: number) => void` не
підходить.

**Функція як значення.** Якщо ви хочете зберегти в стані саму функцію, запис `setHandler(other)` не спрацює: React
викличе `other` і запише результат. Так само поводиться `useState(other)` при першому показі. Довідник радить
дописувати стрілку: `setHandler(() => other)`.

### Чи завжди потрібен оновлювач

Довідник у блоці `Is using an updater always preferred?` каже, що зазвичай різниці немає. React гарантує, що до
наступного клацання стан уже оновлено, тому обробник клацання не бачить застарілого значення на своєму початку.
Оновлювач потрібен у двох випадках: коли в одному обробнику кілька оновлень того самого стану і коли виклик `set`
відкладено. Наступний розділ розбирає другий випадок.

## Таймер: знімок живе довше за рендер

Стрілка в `setTimeout` є замиканням так само, як обробник. Вона бачить змінні рендеру, у якому її створили, навіть
якщо виконується через хвилину. Це дає два наслідки: таймер читає старе значення, а виклик `set` із таймера теж
обчислює нове значення зі старого. Подивімося на другий наслідок, якого немає на сторінці дня. Кнопка відкладає
поповнення на секунду, а людина клацає тричі, поки ця секунда не минула:

```tsx
function Delayed() {
  const [byValue, setByValue] = useState(0)
  const [byUpdater, setByUpdater] = useState(0)
  function later() {
    setTimeout(() => {
      setByValue(byValue + 1)
      setByUpdater((n) => n + 1)
    }, 1000)
  }
  return <button onClick={later}>Числом: {byValue}, оновлювачем: {byUpdater}</button>
}

vi.useFakeTimers({ shouldAdvanceTime: true })
const timedUser = userEvent.setup({ advanceTimers: vi.advanceTimersByTime })
render(<Delayed />)
await timedUser.click(screen.getByRole('button'))
await timedUser.click(screen.getByRole('button'))
await timedUser.click(screen.getByRole('button'))
await act(async () => { vi.advanceTimersByTime(1000) })
console.log(screen.getByRole('button').textContent)
```

```text
Числом: 1, оновлювачем: 3
```

Три клацання не змінювали стану, тому всі три стрілки створено в одному рендері, де `byValue` дорівнює нулю. Усі вони
записали `0 + 1`. Перший запис змінив стан на 1, а наступні два не змінили нічого. Оновлювач не читає змінну рендеру,
тому порахував правильно. Той самий механізм стоїть за вправою `Fix a request counter` на сторінці черги.

### Як перевірити таймер у тесті

Чекати три секунди в кожному тесті незручно. Vitest уміє підміняти таймери: виклик `vi.useFakeTimers()` замінює
`setTimeout` підробкою, яка нічого не виконує сама, а `vi.advanceTimersByTime(3000)` виконує все, що мало спрацювати
за цей час. Такий запис має дві особливості у зв'язці з Testing Library.

**Перша.** Бібліотека `user-event` між діями робить коротку затримку через `setTimeout`, а підроблений таймер сам не
спрацює. Тому `userEvent.setup` отримує параметр `advanceTimers: vi.advanceTimersByTime`, щоб бібліотека сама
пересувала час. Це описано на сторінці `user-event: Options`.

**Друга.** Testing Library після кожної дії чекає на справжній `setTimeout(0)`. Якщо таймери повністю зупинені, цього
не станеться, і тест зависне. Ми перевірили: запис `vi.useFakeTimers()` без параметрів дає `Error: Test timed out`.
Параметр `shouldAdvanceTime: true` змушує підроблений час іти разом зі справжнім, і тест проходить. Звідси побічний
наслідок: підроблений час рухається й сам. У нашому досліді після `vi.advanceTimersByTime(999)` таймер на 1000 мс уже
спрацював, бо підроблений час встиг посунутися разом зі справжнім. Тому не пишіть перевірок «через 999 мс ще не
спрацювало». Перевіряйте лише те, що до проматування виклику не було, а після проматування він є.

Є ще третя особливість, яка стосується лише таймера, що змінює стан. Тоді проматування треба обгорнути в `await
act(async () => { ... })`, як у прикладі вище, інакше React не встигне оновити екран до наступного рядка. У нашому
досліді без `act` кнопка ще показувала старе число. У завданні дня таймер лише викликає функцію `onReport`, тому там
`act` не потрібен.

Чому в завданні дня взагалі стоїть `onReport`, а не `alert`? У jsdom виклик `alert` лише друкує `Not implemented:
Window's alert() method` і нічого не повертає, тому перевірити його в прикладі нічим. Функцію-проп можна замінити
шпигуном. На сторінці `f1-d08.html` проп дорівнює справжньому `alert`, і за описом MDN браузер покаже вікно й
чекатиме, поки людина його закриє. Цей варіант ми в браузері не перевіряли, тому перевірте його самі: клацніть кнопку
й подивіться, яке число стоїть на екрані, коли з'явиться вікно.

## Покроковий приклад: одне клацання від початку до кінця

Зберемо все разом. Компонент `Till` має стан `cups`, початкове значення 1. Обробник робить чотири речі:

```tsx
function Till() {
  const [cups, setCups] = useState(1)
  console.log('рендер: cups =', cups)
  function handleClick() {
    setCups(cups + 2)
    setCups((c) => c * 2)
    console.log('обробник: cups =', cups)
    setTimeout(() => console.log('таймер: cups =', cups), 1000)
  }
  return <button onClick={handleClick}>Чашок: {cups}</button>
}

vi.useFakeTimers({ shouldAdvanceTime: true })
const timedUser = userEvent.setup({ advanceTimers: vi.advanceTimersByTime })
render(<Till />)
await timedUser.click(screen.getByRole('button'))
console.log('на кнопці:', screen.getByRole('button').textContent)
vi.advanceTimersByTime(1000)
```

```text
рендер: cups = 1
обробник: cups = 1
рендер: cups = 6
на кнопці: Чашок: 6
таймер: cups = 1
```

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | React | перший рендер, `useState(1)` дає `cups = 1`, коміт створює кнопку з текстом «Чашок: 1» |
| 2 | людина | клацає, React викликає `handleClick` першого рендеру |
| 3 | JavaScript | обчислює `1 + 2` і викликає `setCups(3)`, у черзі запис «заміни на 3» |
| 4 | JavaScript | викликає `setCups` з функцією, функція лягає в чергу |
| 5 | `console.log` | друкує 1, бо змінна цього рендеру не змінювалася |
| 6 | `setTimeout` | запам'ятовує стрілку, яка замкнула ту саму змінну |
| 7 | React | обробник закінчився, тому починається другий рендер |
| 8 | `useState(1)` | проходить чергу: 3, потім `3 * 2`, повертає 6, аргумент 1 ігнорує |
| 9 | React | коміт змінює лише текст кнопки |
| 10 | таймер | через секунду стрілка друкує 1, хоча екран давно показує 6 |

## Рецепт: перелік варіантів

Сьогодні рецепт із книжки How to Design Programs застосовується до нового виду даних. Функція `set` приймає число або
функцію, тобто оновлення є **itemization**: значення є одним із кількох видів. Розбір читання до дня 3 пояснював, що
книжка вимагає тоді по одній гілці й щонайменше по одному прикладу на кожен варіант.

У файлі `queue.ts` цей опис даних записано типом. Ось той самий шаблон на іншому прикладі: знижка задана або готовою
ціною, або функцією від старої ціни.

```tsx
type Discount = number | ((price: number) => number)

function applyDiscount(price: number, discount: Discount): number {
  if (typeof discount === 'function') {
    return discount(price)
  }
  return discount
}

console.log(applyDiscount(100, 80))
console.log(applyDiscount(100, (p) => p / 2))
```

```text
80
50
```

Перевірка `typeof discount === 'function'` є тим самим звуженням, яке пояснювала лекція «TypeScript: основи»:
усередині гілки компілятор знає, що це функція, а після неї знає, що це число. Що буде, якщо оновлень багато,
вирішуєте вже ви у своєму завданні. Вправа `Implement the state queue yourself` на сторінці черги містить готове
рішення такої задачі, тому відкрийте її лише після своєї функції.

Друга особливість сьогоднішнього рецепта стосується кроку «приклади». Зазвичай приклад записує очікування, яке ви
знаєте. Сьогодні план просить записати очікування, у якому ви, можливо, помиляєтеся. Запишіть його до запуску. Якщо
приклад упаде, це покаже місце, де ваша модель React не збігається з реальною.

## Хто яку помилку ловить

| Помилка | `tsc` | ESLint | Під час роботи |
|---------|-------|--------|----------------|
| читання `cups` після `setCups` | мовчить | мовчить | старе число |
| три `setCups(cups + 1)` | мовчить | мовчить | плюс один замість плюс три |
| `await` після `set`, щоб дочекатися | мовчить | мовчить | те саме старе число |
| `setTimeout` читає `cups` | мовчить | мовчить | число на мить клацання |
| `cups++` | `TS2588`, змінна є константою | мовчить | `TypeError` |
| оновлювач без `return` | `TS2345` | `no-unused-expressions` | стан стає `undefined` |
| `setCups` у тілі компонента | мовчить | `react-hooks/set-state-in-render` | `Too many re-renders` |
| `order.cups = 5; setOrder(order)` | мовчить | `react-hooks/immutability` | екран не змінюється |

Перші чотири рядки є саме темою дня. Ні компілятор, ні лінтер про них нічого не скажуть, бо для типів і правил код
правильний. Такі помилки ловлять лише приклади, тому день і просить їх писати.

## Типові хибні уявлення

**«`set` асинхронний, треба просто почекати».** Чекати немає чого. Навіть `flushSync`, який завершує рендер і коміт
негайно, не змінює змінну в обробнику, бо нове значення лежить у новій змінній нового виклику.

**«Рендер змінює документ».** Рендер лише викликає функції й отримує опис. Документ змінює коміт, і лише там, де є
різниця.

**«Якщо компонент перемалювався, він щось змінив на екрані».** Друге клацання в нашому досліді викликало три функції й
записало нуль змін.

**«Перемальовується лише компонент, стан якого змінився».** Перемальовуються також усі компоненти під ним, навіть якщо
їхні пропси ті самі.

**«React складає всі `set` з одного обробника».** React нічого не складає. Він проходить чергу по порядку: заміна
стирає те, що було, а оновлювач рахує від попереднього. Тому порядок записів має значення.

**«Оновлювач завжди кращий за значення».** Для одного виклику в обробнику клацання різниці немає. Оновлювач потрібен,
коли оновлень кілька або коли виклик відкладено.

**«Таймер покаже поточний стан».** Таймер бачить змінну рендеру, у якому його створили. Щоб прочитати найсвіжіше
значення поза рендером, існує `ref`, про який ітиметься в день «Ref».

## Як це проявиться далі в React

- **День 9, об'єкти й масиви в стані.** Порівняння через `Object.is` пояснить, чому зміна об'єкта не дає рендеру, а
  заміна дає.
- **День 13, редюсер.** Редюсер теж описує зміну стану функцією від попереднього значення, так само як оновлювач.
- **День 15, ref.** Значення в `ref` не є знімком: таймер прочитає найсвіжіше значення, а зміна не викличе рендеру.
- **Дні 16–19, ефекти.** Ефект теж є замиканням одного рендеру, тому застаріле значення в таймері стане головною темою
  залежностей.
- **Фаза 2.** Профайлер покаже, скільки часу займає рендер кожного компонента, а день «Узгодження дерева» пояснить, як
  саме React знаходить різницю.
- **Співбесіда.** Два запитання з вступу тепер мають точні відповіді: рендер є викликом функції, коміт є записом у
  DOM, а стан в обробнику старий, бо це змінна того рендеру, у якому створено обробник.

## Перевірте себе

**1. Компонент перемалювався, але в документі нічого не змінилося. Чи можливо це, і що відбулося?**

<details><summary>Відповідь</summary>

Можливо. Рендер є лише викликом функції компонента. Новий опис збігся з попереднім, тому на кроці коміту React не
записав нічого.

</details>

**2. `cups` дорівнює 4. Що надрукує `console.log(cups)` одразу після `setCups(cups + 1)` і чому не допоможе `await`
між ними?**

<details><summary>Відповідь</summary>

`4`. Функція `set` не змінює цю змінну, вона лише просить новий рендер. Новий рендер створить нову змінну, а цей
обробник читає стару, тому `await` нічого не змінить. Навіть після `flushSync` тут буде 4.

</details>

**3. Яким стане `cups` після `setCups(cups + 1); setCups(cups + 1); setCups(c => c + 1)`, якщо спочатку було 0?**

<details><summary>Відповідь</summary>

`2`. Перші два записи означають «заміни на 1», а оновлювач отримує 1 і повертає 2.

</details>

**4. Яким стане `cups` після `setCups(c => c + 1); setCups(5)`, якщо спочатку було 0?**

<details><summary>Відповідь</summary>

`5`. Оновлювач дав 1, а наступний запис замінив стан на 5. Заміна не дивиться на те, що було перед нею.

</details>

**5. Обробник викликає `setA(1)`, потім `await fetch(...)`, потім `setB(2)`. Скільки рендерів запустить це клацання і
чому не один?**

<details><summary>Відповідь</summary>

Два. Код після `await` виконується вже після того, як обробник повернув керування, тому React встигає обробити першу
чергу окремо. Ми перевірили це на `await` із промісом і таймером у jsdom. Запитів до мережі в досліді не було.

</details>

**6. Кнопка запускає `setTimeout(() => setCups(cups + 1), 1000)`. Людина клацає двічі за секунду. Що покаже екран і як
отримати плюс два?**

<details><summary>Відповідь</summary>

Плюс один. Між клацаннями рендеру не було, тому обидві стрілки бачать те саме `cups`. Плюс два дасть оновлювач:
`setTimeout(() => setCups(c => c + 1), 1000)`.

</details>

**7. Чому в тесті дня стоїть `vi.useFakeTimers({ shouldAdvanceTime: true })`, а не просто `vi.useFakeTimers()`?**

<details><summary>Відповідь</summary>

Testing Library після кожної дії чекає на справжній `setTimeout(0)`. Повністю зупинені таймери цього не дадуть, і тест
зависне. Параметр змушує підроблений час іти разом зі справжнім.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| запуск | причина, з якої React починає роботу: перший показ або зміна стану |
| рендер | виклик функцій компонентів, який дає опис розмітки |
| коміт | запис різниці в документ |
| малювання | крок браузера, який показує результат на екрані; у документації React це painting |
| знімок стану | значення змінної стану, незмінне в межах одного рендеру |
| пакетування | об'єднання кількох викликів `set` в один рендер; англійською batching |
| черга оновлень | список записів, які React проходить під час наступного рендеру |
| оновлювач | функція, передана в `set`, яка обчислює наступне значення з попереднього |
| `flushSync` | функція React, яка змушує виконати рендер і коміт негайно |
| `Object.is` | функція, якою React перевіряє, чи значення те саме |
| підроблені таймери | заміна `setTimeout` у тесті, де час пересуває сам тест |
