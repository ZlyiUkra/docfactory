# Лекція. Фаза 1, день 9. Об'єкти й масиви в стані

Досі в стані лежали здебільшого числа й рядки. Ця лекція пояснює, що змінюється, коли в стані лежить об'єкт або масив:
чому зміна такого значення не оновлює екран і не дає жодної помилки, як правильно будувати нове значення на будь-якій
глибині і як змусити випадкову зміну стану кидати помилку. Читання займе близько 45 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під
прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із тим самим набором
правил `react-hooks`, що й у проєкті `spa`. У справжньому браузері приклади не запускалися, тому там, де йдеться про
браузер, сказано, на чому це твердження тримається.

**Після лекції ви зможете пояснити:**

- що таке мутація і чому змінювати щойно створений об'єкт можна;
- що саме робить функція `set`, коли отримує об'єкт, і чому вона не дивиться всередину;
- чому мутація інколи «наздоганяє» екран після зовсім іншої дії;
- як замінити поле на третьому рівні вкладеності і які об'єкти при цьому лишаються старими;
- чим замінити `push`, `splice`, `sort` і присвоєння за індексом, і де в цих замінах межі;
- чому копія масиву не захищає об'єкти, які в ньому лежать;
- навіщо заморожувати стан у режимі розробки, чому не в збірці й чого заморожування не ловить;
- як із опису даних випливає рекурсивна функція;
- який інструмент яку помилку зі стану знаходить.

## Плеєр, який оновлює екран невчасно

Ви робите музичний плеєр. У стані лежать масив пісень і число, тобто гучність. Кнопка «додати» має дописати пісню, і
ви пишете те, що підказує весь досвід роботи з масивами в JavaScript:

```tsx
function add() {
  songs.push('Плине кача')
  setSongs(songs)
}
```

Ви клацаєте, і нічого не відбувається: лічильник пісень не змінився, а консоль порожня. Потім ви клацаєте «гучніше», і
пісня раптом з'являється. Виглядає так, ніби екран відстає на одну дію, і причини цього не видно ні в коді обробника,
ні в кнопці гучності.

Причина лежить у двох речах, які ви вже знаєте окремо. Лекція «Значення й посилання» пояснила, що змінна зберігає
посилання на об'єкт. Лекція «Масиви й об'єкти функційно» пояснила, що `push` змінює сам масив і нового масиву не
створює. Сьогодні ці дві думки сходяться разом із правилом, за яким працює стан React.

## Що таке мутація

**Мутацією** називають зміну вмісту об'єкта, який уже існує. Запис `songs.push(...)` є мутацією, запис `player.volume
= 60` є мутацією, запис `songs[0] = 'x'` теж. Числа, рядки й логічні значення мутувати неможливо: `setVolume(60)` не
змінює число `50`, а кладе в стан інше число. Об'єкти й масиви мутувати технічно можна, але сторінка `Updating Objects
in State` просить ставитися до них так, ніби вони теж незмінні. Замість мутації стан **замінюють**, тобто передають у
`set` новий об'єкт.

Подивімося, як різні записи поводяться на тому самому компоненті. Масив `seen` запам'ятовує, який масив компонент
бачив на кожному виклику, тому ми зможемо подивитися на попередній стан пізніше:

```tsx
type Variant = 'без set' | 'той самий масив' | 'копія після push' | 'новий масив'
const seen: string[][] = []

function Playlist({ variant }: { variant: Variant }) {
  const [songs, setSongs] = useState(['Щедрик', 'Ой у лузі'])
  const [volume, setVolume] = useState(50)
  seen.push(songs)
  function add() {
    if (variant === 'без set') {
      songs.push('Плине кача')
    } else if (variant === 'той самий масив') {
      songs.push('Плине кача')
      setSongs(songs)
    } else if (variant === 'копія після push') {
      songs.push('Плине кача')
      setSongs([...songs])
    } else {
      setSongs([...songs, 'Плине кача'])
    }
  }
  return (
    <>
      <p>Пісень: {songs.length}</p>
      <p>Гучність: {volume}</p>
      <button onClick={add}>додати</button>
      <button onClick={() => setVolume(volume + 10)}>гучніше</button>
    </>
  )
}
```

Для кожного варіанта тест клацає «додати», записує, що на екрані, а потім клацає «гучніше»:

```text
без set | викликів: 1 | Пісень: 2 | старий масив: 3 | після «гучніше»: Пісень: 3
той самий масив | викликів: 1 | Пісень: 2 | старий масив: 3 | після «гучніше»: Пісень: 3
копія після push | викликів: 2 | Пісень: 3 | старий масив: 3 | після «гучніше»: Пісень: 3
новий масив | викликів: 2 | Пісень: 3 | старий масив: 2 | після «гучніше»: Пісень: 3
```

Прочитаємо цей вивід по рядках.

- **Без `set`.** React не дізнався про зміну, тому не викликав компонент. На екрані лишилося 2, хоча в масиві вже 3.
- **Той самий масив.** Вивід збігається з попереднім рядком до останнього символу. Виклик `setSongs(songs)` тут не
  зробив нічого, бо React отримав той самий масив, який уже зберігає.
- **Копія після `push`.** Екран оновився, і здається, що все гаразд. Але колонка «старий масив» показує 3: масив із
  попереднього стану зіпсовано. Ця помилка найнебезпечніша, бо зовні її не видно.
- **Новий масив.** Екран оновився, а старий масив лишився з двома піснями. Лише цей запис правильний.

Останнє число в кожному рядку однакове, бо «гучніше» викликає компонент, а тіло компонента читає `songs.length` із
того масиву, який лежить у стані зараз. Так і виникає враження, що екран відстає на одну дію. Пісня не з'явилася
пізніше: вона лежала в масиві від самого клацання, а екран показав її лише тоді, коли компонент викликали з іншої
причини.

### Яку мутацію робити можна

Правило забороняє змінювати те, що вже лежить у стані. Об'єкт, який ви створили щойно, ще ніхто не бачив, тому
змінювати його безпечно. Такий запис правильний, хоча в ньому є мутуючий метод:

```tsx
const next = [...songs]
next.reverse()
setSongs(next)
```

Метод `reverse` змінює `next`, а `next` є новим масивом, на який більше ніхто не посилається. Сторінка `Updating
Objects in State` називає це локальною мутацією. Перевірка проста: запитайте себе, чи міг цей об'єкт хтось отримати до
цього рядка. Якщо він прийшов зі стану або з пропсів, відповідь «так», і змінювати його не можна.

## Що робить функція `set`

Тема «Рендер, коміт і знімок стану» пояснює, що функція `set` просить React викликати компонент знову з новим
значенням. Нагадаємо коротко: **рендером** називають виклик функції компонента, а **комітом** називають запис
результату в документ. Тепер додамо одну деталь, від якої залежить увесь сьогоднішній день.

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | React | зберігає для компонента посилання на поточний стан, а компонент отримує це посилання зі `useState` |
| 2 | ваш обробник | викликає `set(наступне)` |
| 3 | React | порівнює наступне значення з поточним функцією `Object.is` |
| 4 | React | якщо `Object.is` дав `true`, ігнорує оновлення й не показує нічого нового |
| 5 | React | якщо `Object.is` дав `false`, планує рендер, а компонент отримає нове посилання |

Лекція «Значення й посилання» показала, що для об'єктів `Object.is` відповідає лише на одне запитання: чи це той самий
об'єкт. Вміст він не читає. Звідси випливають обидва наслідки, які легко переплутати:

- змінений об'єкт, переданий у `set`, для React є тим самим об'єктом, і рендеру немає, хоча вміст інший;
- копія з точно таким самим вмістом для React є іншим об'єктом, і рендер є, хоча вміст той самий.

Чому React порівнює так просто? Порівняти два посилання можна за одну дію, незалежно від розміру стану. Порівняти
вміст означало б обійти обидва об'єкти до найглибшого поля при кожному `set`. Але така дешева перевірка працює лише за
однієї умови: посилання має змінюватися щоразу, коли змінюється вміст. Цю умову забезпечуєте ви, коли не мутуєте стан.
Сторінка `Updating Objects in State` формулює це так: якщо стан ніколи не мутують, то рівність `prevObj === obj`
означає, що всередині нічого не змінилося.

### Коли тіло викликано, а екран лишився старим

Документація в застереженнях до `set` уточнює: інколи React мусить викликати компонент, перш ніж пропустити оновлення.
Подивімося, що це означає на практиці, бо тут спрацьовує пастка для тих, хто шукає помилку лічильником викликів:

```tsx
type Track = { title: string }
const bodies: string[] = []

function Now() {
  const [track, setTrack] = useState<Track>({ title: 'Щедрик' })
  bodies.push(track.title)
  return (
    <>
      <p>Грає: {track.title}</p>
      <button onClick={() => setTrack({ title: 'Ой у лузі' })}>нова</button>
      <button onClick={() => { track.title = track.title + '!'; setTrack(track) }}>мутація</button>
    </>
  )
}
```

```text
перший показ | викликів тіла: 1 | останній виклик прочитав: Щедрик | на екрані: Грає: Щедрик
мутація 1 | викликів тіла: 1 | останній виклик прочитав: Щедрик | на екрані: Грає: Щедрик
новий об’єкт | викликів тіла: 2 | останній виклик прочитав: Ой у лузі | на екрані: Грає: Ой у лузі
мутація 2 | викликів тіла: 3 | останній виклик прочитав: Ой у лузі! | на екрані: Грає: Ой у лузі
мутація 3 | викликів тіла: 3 | останній виклик прочитав: Ой у лузі! | на екрані: Грає: Ой у лузі
```

Перша мутація відбулася одразу після першого показу, і тіло не викликалося. Друга мутація відбулася одразу після
справжнього оновлення, і тіло викликалося: воно навіть прочитало нову назву зі знаком оклику. Але результат цього
виклику React відкинув, і в документ нічого не потрапило, тому екран показує стару назву. Третя мутація знову не
викликала тіло.

Звідси практичний висновок. Лічильник викликів не доводить, що екран оновився, і `console.log` у тілі компонента теж
цього не доводить. Доказом є лише те, що реально стоїть у документі. Цей вивід отримано на React 19.3 під jsdom, а
документація не обіцяє, коли саме буває додатковий виклик, тому на точну кількість викликів покладатися не варто.

## Об'єкт: копія з однією зміною

Запис розгортання `...` ви знаєте з лекції «Значення й посилання». На сторінці дня той самий запис названо
розкладанням, і це те саме. Для стану він дає найкоротший спосіб сказати «те саме, лише одне поле інше»:

```tsx
setPlayer({ ...player, volume: 60 })
```

Порядок важливий: поля записуються зліва направо, тому `volume: 60` має стояти після розгортання. Якщо переставити їх
місцями, то старе значення гучності затре нове.

Новачки часто пишуть лише поле, яке змінилося. Функція `set` нічого не об'єднує, а замінює стан цілком:

```tsx
type Player = { volume: number; shuffle: boolean }

function P() {
  const [player, setPlayer] = useState<Player>({ volume: 50, shuffle: true })
  console.log(player)
  return <button onClick={() => setPlayer({ volume: 60 })}>гучніше</button>
}
```

```text
{ volume: 50, shuffle: true }
{ volume: 60 }
```

Поле `shuffle` зникло. `tsc` такий запис не пропускає: `TS2345`, а в поясненні сказано `Property 'shuffle' is missing
in type '{ volume: number; }'`. Vitest лише вирізає типи й не перевіряє їх, тому під час тесту цей код виконався.

## Вкладений об'єкт: копія на кожному рівні

Розгортання копіює лише один рівень. Візьмемо слухача з трьома рівнями вкладеності, у якого треба змінити назву
пристрою:

```ts
type Device = { id: number; name: string }
type Player = { volume: number; device: Device }
type Listener = { name: string; plan: { tier: string }; player: Player }

const before: Listener = {
  name: 'Оля',
  plan: { tier: 'free' },
  player: { volume: 50, device: { id: 1, name: 'Навушники' } },
}
```

На екрані й у коді це виглядає як один великий об'єкт, але під час роботи програми об'єктів чотири: слухач, тариф,
плеєр і пристрій. Вони не лежать одне в одному. У полі `player` лежить посилання на окремий об'єкт. Сторінка `Updating
Objects in State` окремо наголошує на цьому: «вкладеність» є лише способом записати код.

Щоб змінити назву пристрою без мутації, потрібен новий пристрій. Старий плеєр посилається на старий пристрій, тому
потрібен новий плеєр. Старий слухач посилається на старий плеєр, тому потрібен новий слухач. Отже, ви йдете від місця
зміни вгору до самого верху:

```ts
const after = {
  ...before,
  player: {
    ...before.player,
    device: { ...before.player.device, name: 'Колонка' },
  },
}

console.log('listener:', after === before)
console.log('plan:', after.plan === before.plan)
console.log('player:', after.player === before.player)
console.log('device:', after.player.device === before.player.device)
console.log('старе ім\'я пристрою:', before.player.device.name, '| нове:', after.player.device.name)
```

```text
listener: false
plan: true
player: false
device: false
старе ім'я пристрою: Навушники | нове: Колонка
```

Ось як виглядають обидві версії. Стрілка означає посилання:

```text
before ─┬─► player (volume: 50) ─► device (Навушники)
        └─► plan (free)
              ▲
after  ─┬─────┘
        └─► новий player (volume: 50) ─► новий device (Колонка)
```

Тариф спільний для обох версій, бо його ніхто не міняв, і копіювати його немає потреби. Об'єкти на шляху до зміни
нові. Оптимізації React, про які йтиметься в темі «Мемоізація і React Compiler», спираються саме на це: незмінена
частина даних лишається тим самим об'єктом, і компонент, який показує лише тариф, можна не викликати знову.

### Дві типові помилки з вкладеністю

**Скопіювати лише верх і змінити низ.** Цей запис дає нове посилання, тому екран оновлюється:

```ts
const a = make()
const b = { ...a }
b.player.device.name = 'Колонка'
console.log('лише верхня копія: новий об\'єкт?', a !== b, '| старе ім\'я пристрою:', a.player.device.name)
```

```text
лише верхня копія: новий об'єкт? true | старе ім'я пристрою: Колонка
```

Функція `make` тут створює свіжого слухача, такого самого, як `before`. Новий об'єкт `b` має те саме поле `player`, що
й `a`, тому зміна назви пристрою зіпсувала попередній стан. Це той самий випадок, що й «копія після `push`» на початку
лекції: на екрані все правильно, а старих даних уже немає.

**Записати рівень не цілком.** Запис `player: { volume: 70 }` втрачає поле `device`, бо новий об'єкт складається лише
з того, що ви в ньому написали. Він не бере нічого зі старого автоматично, якщо немає розгортання. `tsc` це помічає,
бо тип вимагає поле `device`. Якби поле було необов'язковим, помилку показав би лише приклад, який порівнює весь
об'єкт.

### Чому не `structuredClone`

Лекція «Значення й посилання» пояснила, що `structuredClone` копіює всі рівні. Він дає правильний результат для старих
даних:

```ts
const c = make()
const d = structuredClone(c)
d.player.device.name = 'Колонка'
console.log('structuredClone: plan той самий?', c.plan === d.plan, '| старе ім\'я:', c.player.device.name)
```

```text
structuredClone: plan той самий? false | старе ім'я: Навушники
```

Старе ім'я вціліло, але тариф тепер теж новий об'єкт, хоча його ніхто не міняв. Для всіх, хто порівнює посилання, це
виглядає так, ніби змінилося все. Крім того, функція працює тим довше, чим більше даних, і падає на значеннях, які не
вміє копіювати, наприклад на функціях.

Якщо копіювання трьох рівнів стає незручним, це часто означає, що стан занадто глибокий. Документація радить зробити
його плоским, і цьому присвячена тема «Структура стану».

## Масив: п'ять дій без мутації

Масив також є об'єктом, тому правило те саме. Сторінка `Updating Arrays in State` дає таблицю, яку варто пам'ятати.
Ось вона на прикладі плейлиста, де `songs` є масивом рядків:

| Дія | Не робіть | Робіть | Результат для `['a', 'b', 'c']` |
|-----|-----------|--------|--------------------------------|
| додати в кінець | `push` | `[...songs, 'x']` | `['a', 'b', 'c', 'x']` |
| додати на початок | `unshift` | `['x', ...songs]` | `['x', 'a', 'b', 'c']` |
| видалити | `splice`, `pop`, `shift` | `songs.filter(s => s !== 'b')` | `['a', 'c']` |
| замінити | `songs[1] = 'x'`, `splice` | `songs.map(s => s === 'b' ? 'x' : s)` | `['a', 'x', 'c']` |
| вставити | `splice` | `[...songs.slice(0, 1), 'x', ...songs.slice(1)]` | `['a', 'x', 'b', 'c']` |
| відсортувати, обернути | `sort`, `reverse` | `[...songs].sort()`, `[...songs].reverse()` | новий масив |

Лекція «Масиви й об'єкти функційно» вже розбирала методи `toSorted`, `toReversed`, `toSpliced` і `with`. Вони теж
повертають новий масив, і в проєкті `spa` вони доступні, бо його шаблон вмикає бібліотеку типів ES2023. Сторінка React
про них не згадує, але запис `songs.toSpliced(1, 0, 'x')` дає той самий результат, що й вставка у таблиці.

### Межі цих записів

**`slice` і `splice`.** Назви відрізняються однією літерою, а поведінка протилежна:

```ts
const slice = ['a', 'b', 'c']
console.log(slice.slice(1, 2), slice)
const splice = ['a', 'b', 'c']
console.log(splice.splice(1, 2), splice)
```

```text
[ 'b' ] [ 'a', 'b', 'c' ]
[ 'b', 'c' ] [ 'a' ]
```

Метод `slice` повертає копію частини й не чіпає масив, а другий аргумент означає кінець. Метод `splice` вирізає
елементи із самого масиву, а другий аргумент означає кількість.

**Позиція вставки поза межами.** Припустимо, вставку записано так, як у таблиці, але з довільною позицією:

```ts
const letters = ['a', 'b', 'c']
const at = (i: number) => [...letters.slice(0, i), 'x', ...letters.slice(i)]
```

```text
at(1): axbc | at(0): xabc | at(3): abcx | at(99): abcx | at(-1): abxc
```

Занадто велика позиція просто дає вставку в кінець. Від'ємна позиція працює інакше: `slice` рахує її від кінця, тому
`-1` поставила елемент перед останнім, і помилки немає.

**Метод `filter` завжди повертає новий масив.** Якщо нічого не видалено, вміст той самий, але посилання нове:

```text
filter без збігу: той самий масив? false | той самий вміст? true
```

Отже, такий `set` викличе рендер, хоча нічого не змінилося. У нашому запуску лічильник викликів зріс із 1 до 2. Це не
помилка, а один зайвий виклик компонента, який зазвичай непомітний. Те саме стосується `map`.

**Метод `sort` повертає той самий масив.** Запис `setSongs(songs.sort())` виглядає як передача результату, але
результатом є `songs`. Тому React не бачить зміни, а масив у стані вже переставлено. Функцію порівняння розбирала
лекція «Масиви й об'єкти функційно», зокрема `localeCompare` для української абетки.

**Два `set` в одному обробнику.** Тема «Рендер, коміт і знімок стану» пояснює, що змінна `songs` не змінюється до
наступного рендеру. Тому копії, зроблені з неї двічі, обидві починаються з того самого стану:

```tsx
setSongs([...songs, 'x'])
setSongs([...songs, 'y'])
// на екрані: a,b,y

setSongs((prev) => [...prev, 'x'])
setSongs((prev) => [...prev, 'y'])
// на екрані: a,b,x,y
```

Другий запис передає **функцію-оновлювач**, яка отримує результат попереднього оновлення.

**Мутація в оновлювачі.** Обгортка `<StrictMode>` змушує React у режимі розробки викликати деякі ваші функції двічі,
щоб виявити нечистий код. Докладно її пояснює тема «Чистота й дерево». Оновлювач є однією з таких функцій. Якщо він
мутує, ефект подвоюється:

```tsx
setSongs((prev) => { runs++; prev.push('x'); return [...prev] })
```

```text
без StrictMode клацання 1 | викликів оновлювача 1 | a,x
без StrictMode клацання 2 | викликів оновлювача 2 | a,x,x
без StrictMode клацання 3 | викликів оновлювача 3 | a,x,x,x
StrictMode клацання 1 | викликів оновлювача 2 | a,x
StrictMode клацання 2 | викликів оновлювача 4 | a,x,x,x
StrictMode клацання 3 | викликів оновлювача 6 | a,x,x,x,x,x
```

Під `<StrictMode>` друге клацання додало не один елемент, а два. Якщо у вашому списку елементи подвоюються лише в
режимі розробки, шукайте мутацію в оновлювачі.

## Об'єкти всередині масиву

Копія масиву є новим масивом із тими самими елементами. Лекція «Масиви й об'єкти функційно» показувала це на `map`, а
в стані наслідок стає особливо неприємним. Два плейлисти, ваш і подруги, стартують з одного й того самого початкового
масиву. Ви ставите лайк пісні у своєму плейлисті:

```tsx
type Song = { id: number; title: string; liked: boolean }
const start = (): Song[] => [
  { id: 1, title: 'Щедрик', liked: false },
  { id: 2, title: 'Ой у лузі', liked: false },
]

function Bad() {
  const [initial] = useState(start)
  const [mine, setMine] = useState(initial)
  const [friend] = useState(initial)
  function like(id: number) {
    const next = [...mine]
    const song = next.find((s) => s.id === id)!
    song.liked = true
    setMine(next)
  }
  // показує обидва плейлисти й кнопку, яка викликає like(1)
}
```

```text
find і присвоєння мій: ♥Щедрик, ·Ой у лузі | подруги: ♥Щедрик, ·Ой у лузі
```

Обробник не викликав жодного `set` для плейлиста подруги, а лайк з'явився і в неї. Масив `next` справді новий, але
`find` повернув той самий об'єкт, який лежить і в масиві подруги. Правильний запис створює новий об'єкт для зміненого
елемента, а решту елементів лишає тими самими:

```tsx
function like(id: number) {
  setMine(mine.map((s) => (s.id === id ? { ...s, liked: true } : s)))
}
```

```text
map із новим об'єктом мій: ♥Щедрик, ·Ой у лузі | подруги: ·Щедрик, ·Ой у лузі
```

Той самий принцип, що й у вкладеному об'єкті: копіюйте на шляху від місця зміни вгору. Масив є верхнім рівнем, а
елемент нижнім. Елементи, яких зміна не стосується, копіювати не треба, і це норма, а не недогляд.

## Покроковий приклад: три дії над плейлистом

Простежимо, які об'єкти створюються. Є три пісні: `A` (Щедрик), `B` (Ой у лузі, ще без лайка) і `C` (Верховино, уже з
лайком). Назвемо версії стану `S0`, `S1`, `S2` і `S3`:

```ts
const S0 = [A, B, C]
const S1 = S0.map((s) => (s.id === 2 ? { ...s, liked: true } : s))
const S2 = [...S1].sort((x, y) => x.title.localeCompare(y.title, 'uk'))
const S3 = S2.filter((s) => s.id !== 1)
```

| Крок | Хто діє | Що створено | Що лишилося тим самим |
|------|---------|-------------|----------------------|
| лайк для `B` | `map` | новий масив `S1` і новий об'єкт `B'` | об'єкти `A` і `C` |
| сортування | розгортання, потім `sort` | новий масив `S2`, порядок `C, B', A` | усі три об'єкти з `S1` |
| видалення `A` | `filter` | новий масив `S3`, елементи `C, B'` | об'єкти `C` і `B'` |

Запуск підтверджує кожен рядок таблиці й показує, що всі попередні версії лишилися цілими:

```text
S1: Щедрик, Ой у лузі ♥, Верховино ♥ | true false true
S2: Верховино ♥, Ой у лузі ♥, Щедрик | S2[0]===C true S2[2]===A true S2[1]===S1[1] true
S3: Верховино ♥, Ой у лузі ♥
S0 далі: Щедрик, Ой у лузі, Верховино ♥
S1 далі: Щедрик, Ой у лузі ♥, Верховино ♥
S2 далі: Верховино ♥, Ой у лузі ♥, Щедрик
```

Три значення в першому рядку відповідають на запитання «чи той самий це об'єкт» для `A`, `B` і `C`. Функція `sort` тут
законно змінює масив, бо це щойно створена копія. Те, що всі чотири версії лежать у пам'яті незайманими, дає
можливість зробити кнопку «скасувати»: досить покласти в стан `S1` замість `S2`.

## Заморожування: помилка замість мовчання

Найгірша властивість мутації в тому, що вона не дає жодного повідомлення. Лекція «Масиви й об'єкти функційно» показала
інструмент, який це змінює: `Object.freeze` забороняє змінювати об'єкт. Сьогодні ви застосовуєте його до стану.

React сам стан не заморожує:

```text
React заморозив стан? false
```

Лекція «Пропси й умовний рендер» показала, що пропси React у режимі розробки заморожує, але на стан це не поширюється.
Тому заморожуємо самі:

```tsx
function F() {
  const [songs, setSongs] = useState(() => freeze(['Щедрик', 'Ой у лузі']))
  function add() {
    console.log('обробник почався')
    songs.push('Плине кача')
    console.log('цей рядок не виконається')
    setSongs(songs)
  }
  return <><p>Пісень: {songs.length}</p><button onClick={add}>додати</button></>
}
```

Тут `freeze` є звичайною обгорткою над `Object.freeze`. Тест слухає подію `error` на `window` і друкує її текст:

```text
обробник почався
помилки: [ 'Cannot add property 2, object is not extensible' ]
Пісень: 2
```

Метод `push` кинув `TypeError`, решта обробника не виконалася, а React передав помилку на рівень `window`. Під jsdom
ми бачили саме це. У браузері цей код не запускався, але подія `error` на `window` є стандартним механізмом для
необроблених помилок, тому в консолі браузера очікуйте таку саму помилку. Те саме відбудеться з присвоєнням у поле:
файли `.ts` і `.tsx` є модулями, модулі виконуються в суворому режимі, а в суворому режимі присвоєння в заморожений
об'єкт кидає `TypeError`. Поза суворим режимом присвоєння не дає помилки, як показувала лекція «Масиви й об'єкти
функційно».

### Що треба знати про заморожування стану

**Заморожується сам об'єкт, а не його копія.** Функція `Object.freeze` повертає той самий об'єкт. Якщо компонент
заморожує початкове значення, яке йому передали, то це значення стає замороженим і для всіх інших:

```tsx
const START = ['Щедрик']
function F({ initial }: { initial: string[] }) {
  useState(() => freeze(initial))
  return null
}

console.log('до показу:', Object.isFrozen(START))
render(<F initial={START} />)
console.log('після показу:', Object.isFrozen(START))
try { START.push('x') } catch (e) { console.log((e as Error).message) }
```

```text
до показу: false
після показу: true
Cannot add property 1, object is not extensible
```

Заморожуйте лише дані, які ви контролюєте. Це також пояснює коментар у файлі `snapshot.test.tsx` практики: цей файл
створює власні початкові дані, бо компонент у режимі розробки заморожує те, що йому передали.

**Запис `useState(() => ...)`.** Такий аргумент називають **ініціалізатором**: React викликає цю функцію лише на
першому рендері. Без обгортки вираз обчислюється на кожному рендері, а його результат React відкидає:

```text
рендерів 3: useState(make()) викликів 3 | useState(() => make()) викликів 1
```

**Копія не заморожена.** Кожне нове значення треба заморожувати окремо, бо заморожування не передається:

```text
копія масиву заморожена? false | елемент копії заморожений? true | новий об'єкт? false | toSorted false
```

З цього виводу випливають два наслідки. Перший наслідок: заморожений масив можна скопіювати й відсортувати копію, бо
копія не заморожена. Другий наслідок: елементи в копії лишаються замороженими, тому `next[0].title = 'x'` кине помилку
навіть після розгортання. А новий масив чи новий об'єкт треба заморозити знову, тому практика загортає в заморожування
і початкове значення, і кожен новий стан.

**Лише в режимі розробки.** Об'єкт `import.meta.env` дає Vite, інструмент збирання вашого проєкту. Поле `DEV` дорівнює
`true`, коли застосунок працює не в збірці для користувачів. Ось три перевірки:

```ts
function guard<T>(value: T): T {
  return import.meta.env.DEV ? Object.freeze(value) : value
}
```

| Де | Що ми побачили |
|----|----------------|
| Vitest | `DEV true PROD false MODE test` |
| `vite`, запит `curl` до модуля | Vite дописав на початок модуля `import.meta.env = {..., "DEV": true, ...}` |
| `vite build`, зібраний файл | `function e(e){return e}`, тобто виклику `Object.freeze` у збірці немає взагалі |

Браузер ми тут не відкривали: ми перевірили те, що сервер розробки й збірка віддають браузеру. Отже, у збірці немає
витрат на заморожування. Але з цього випливає й інше: та сама мутація в збірці вже не кине помилку, а знову
промовчить. Заморожування показує помилки вам під час розробки й не захищає користувачів. Сам обхід коштує небагато:
на нашій машині глибоке заморожування списку зі 100 записів, у кожному з яких лежить ще й масив, зайняло 0,2 мс, з 10
000 записів 8 мс, а зі 100 000 записів 35 мс.

**Обхід повторюється при кожному оновленні.** Заманливо перевіряти на вході `Object.isFrozen` і не заходити всередину
вже замороженого об'єкта. Так робити не можна: об'єкт, заморожений звичайним `Object.freeze`, відповідає `true`, а
його вкладені об'єкти можуть бути незаморожені.

**Що заморожування не ловить.** Дані об'єктів `Map`, `Set` і `Date` лежать не в полях, тому після заморожування їх
можна змінювати, як пояснила лекція «Масиви й об'єкти функційно». Запуск нижче покаже це в рекурсивній функції. Також
рекурсія не закінчиться, якщо об'єкт посилається сам на себе, і про це попереджає MDN у розділі `Deep freezing`.

## Рекурсія за рецептом

Одного рівня заморожування мало, адже в стані вкладені дані. Глибоке заморожування є рекурсією, і рецепт книжки How to
Design Programs показує, звідки вона береться. Глава `Designing with Self-Referential Data Definitions` вчить такого
порядку: спершу опис даних, а форма функції випливає з нього.

**Опис даних посилається сам на себе.** Значення, яке може лежати в стані, є або числом, рядком чи `null`, або масивом
чи об'єктом, усередині яких лежать такі самі значення. Книжка називає такий опис самопосилальним і вимагає двох умов:
варіантів має бути щонайменше два, і хоча б один варіант не посилається на сам опис. Без другої умови значення
неможливо було б створити, а рекурсія ніколи б не закінчувалася.

**Форма функції повторює опис.** Для кожного варіанта є своя гілка. Для кожного самопосилання є рекурсивний виклик.
Книжка показує це на списках, де самопосилання одне, а тому й виклик один. В об'єкті таких полів багато, тому і
викликів стільки, скільки полів. Книжка доходить до цього в главі `The Poetry of S-expressions`, а сьогодні досить
правила «один виклик на кожне вкладене значення».

Подивімося на функцію, яка працює над тим самим описом даних, але робить інше. Практику дня вона не розв'язує, бо лише
перевіряє, чи заморожено значення на всіх рівнях:

```ts
// Чи заморожено значення на всіх рівнях. Примітив і null незмінні самі по собі.
function isDeepFrozen(value: unknown): boolean {
  if (typeof value !== 'object' || value === null) return true
  if (!Object.isFrozen(value)) return false
  return Object.values(value).every(isDeepFrozen)
}
```

Прочитаємо її рядок за рядком.

- Коментар каже, що функція обчислює, а не як вона обходить дані. Книжка окремо просить писати призначення саме так.
- Перша перевірка відповідає варіанту без самопосилання. Запис `value === null` потрібен, бо `typeof null` дає
  `'object'`, а `Object.values(null)` кинув би `TypeError`.
- Запис `Object.isFrozen(value)` перевіряє сам об'єкт.
- Останній рядок є рекурсією. `Object.values` працює і для об'єкта, і для масиву: для `[7, 8]` він дає `[7, 8]`. Тому
  окремої гілки для масивів не потрібно.

Приклади йдуть за порадою книжки: вони кілька разів проходять через самопосилання.

```ts
const inner = Object.freeze({ city: 'Київ' })

console.log(isDeepFrozen(5))                                                // true
console.log(isDeepFrozen(null))                                             // true
console.log(isDeepFrozen({ a: 1 }))                                         // false
console.log(isDeepFrozen(Object.freeze({ a: 1 })))                          // true
console.log(isDeepFrozen(Object.freeze({ a: { b: 1 } })))                   // false
console.log(isDeepFrozen(Object.freeze({ a: inner })))                      // true
console.log(isDeepFrozen(Object.freeze([inner, Object.freeze([inner])])))   // true
```

Значення в коментарях є справжнім виводом. Ось дві межі цієї рекурсії:

```ts
const loop: { self?: object } = {}
loop.self = loop
Object.freeze(loop)
try { isDeepFrozen(loop) } catch (e) { console.log((e as Error).name + ': ' + (e as Error).message) }

const m = Object.freeze(new Map([['a', 1]]))
m.set('b', 2)
console.log('Map після set:', m.size, isDeepFrozen(m))
```

```text
RangeError: Maximum call stack size exceeded
Map після set: 2 true
```

Об'єкт із посиланням на самого себе вичерпав стек викликів. Заморожений `Map` прийняв новий запис, а функція все одно
сказала `true`, бо `Object.values` не бачить записів `Map`. Для стану, описаного об'єктами й масивами, обидві межі
зазвичай не важливі, але знати їх варто.

### Приклади, які ловлять мутацію

Сьогодні кожна функція має два види прикладів, і ось чому потрібні обидва. Функція нижче мутує вхідний масив, а
результат повертає правильний:

```ts
const A: Song = { id: 1, title: 'Щедрик' }
const B: Song = { id: 2, title: 'Ой у лузі' }
const TWO: Song[] = [A, B]

function withoutSong(songs: Song[], id: number): Song[] {
  const at = songs.findIndex((song) => song.id === id)
  songs.splice(at, 1) // вирізає зі вхідного масиву
  return songs
}

test('withoutSong: результат без пісні', () => {
  expect(withoutSong(TWO, 1)).toEqual([B])
})
test('withoutSong: вхідний масив не змінився', () => {
  expect(TWO).toEqual([A, B])
})
test('сусідній приклад, у якому немає помилки', () => {
  expect(TWO.map((song) => song.title)).toEqual(['Щедрик', 'Ой у лузі'])
})
```

```text
 FAIL  lec/w11.test.ts > withoutSong: вхідний масив не змінився
AssertionError: expected [ { id: 2, title: 'Ой у лузі' } ] to deeply equal [ { id: 1, title: 'Щедрик' }, …(1) ]
 FAIL  lec/w11.test.ts > сусідній приклад, у якому немає помилки
AssertionError: expected [ 'Ой у лузі' ] to deeply equal [ 'Щедрик', 'Ой у лузі' ]
```

У виводі показано лише рядки про помилки. Приклад на результат пройшов, тому сам по собі він мутації не ловить. Другий
приклад її зловив. Третій приклад упав, хоча в ньому все написано правильно, бо константа `TWO` спільна для всього
файла. Те саме може трапитися з вами: коли падає приклад, який не має падати, спершу подивіться, чи не зіпсував
спільні дані попередній.

Лекція «Проєкт: Vite, лінт, TypeScript» уже пояснила два матчери, тобто функції перевірки в `expect`. Сьогодні вони
працюють разом: `toEqual` порівнює вміст, а `toBe` порівнює так, як `Object.is`. Запис
`expect(result).not.toBe(input)` є прямою перевіркою того самого, на що дивиться React.

### Рецепт для глибокого заморожування

Функцію `deepFreeze` ви пишете самі. Ось що кожен крок рецепта дає саме для неї, без готового тіла:

| Крок рецепта | Що він дає |
|--------------|------------|
| опис даних | уже записано у файлі `freeze.ts`, і він посилається сам на себе |
| призначення й сигнатура | одне речення про те, що повертає функція, і сигнатура з заготовки |
| приклади | один на примітив, один на вкладений об'єкт, а прихований приклад додає об'єкти всередині масиву |
| перелік вхідних даних | коментар у тілі: що саме доступно в кожній гілці |
| шаблон | гілка без рекурсії для примітива й `null`, а для решти один виклик на кожне вкладене значення |
| перевірка | Vitest запускає приклади, а `tsc` перевіряє типи |

Шаблон у цій таблиці той самий, що й у `isDeepFrozen`. Різниця лише в тому, що функція робить із кожним вкладеним
значенням і що повертає наприкінці.

## Навіщо не мутувати, крім екрана

Може здатися, що досить стежити за оновленням екрана. Запис «копія після `push`» оновлює екран, то чому він поганий?
Сторінка `Updating Objects in State` називає п'ять причин, і ось що кожна означає.

| Причина на сторінці | Що вона означає |
|---------------------|-----------------|
| `Debugging` | значення, яке ви раніше зберегли чи надрукували, не зміниться пізніше, тому можна порівняти стани між рендерами |
| `Optimizations` | React і ваш код можуть пропускати роботу, коли посилання те саме, бо це гарантує, що всередині теж нічого не змінилося |
| `New Features` | нові можливості React вважають стан знімком на певну мить, і мутація минулого стану може їм завадити |
| `Requirement Changes` | кнопка «скасувати», історія змін і повернення форми до старих значень стають простими, бо старі версії лежать у пам'яті цілими |
| `Simpler Implementation` | React не мусить стежити за вашими об'єктами, тому в стан можна класти будь-який об'єкт |

Покроковий приклад із чотирма версіями стану вже показав причину про історію змін: якби кроки мутували масив, версії
`S0` не існувало б.

## Immer: писати як мутацію, отримувати копії

Коли вкладених рівнів багато, запис із розгортаннями стає довгим. Сторінка `Updating Objects in State` радить для
цього бібліотеку Immer. Ви передаєте їй функцію, яка отримує **чернетку** (draft), тобто особливий об'єкт, що записує
ваші зміни. Ви змінюєте чернетку звичайними присвоєннями, а Immer за цим записом будує новий об'єкт:

```js
import { produce } from 'immer'

const after = produce(before, (draft) => {
  draft.player.device.name = 'Колонка'
})
```

```text
Навушники Колонка
listener false | plan true | player false | device false
результат заморожено? true true
```

Це той самий результат, що й у нашого ручного копіювання: нові об'єкти лише на шляху до зміни, а тариф той самий. Ми
запустили цей приклад на `immer` версії 11 в окремій теці, і видно ще одне: Immer сам заморожує результат.

У цьому плані Immer не ставиться. Мета дня полягає в тому, щоб побачити копіювання власноруч, бо без цього
незрозуміло, що саме робить бібліотека. Для компонентів Immer має окремий пакет `use-immer` із хуком `useImmer`. Якщо
ви захочете ним скористатися, це буде ваше окреме рішення поза маршрутом.

## Хто яку помилку ловить

Кожну клітинку перевірено запуском відповідного інструмента. Колонка `freezeInDev` описує функцію з практики дня, яка
заморожує кожен новий стан.

| Запис | `tsc` | ESLint | React без заморожування | `freezeInDev` |
|-------|-------|--------|-------------------------|---------------|
| `songs.push(x); setSongs(songs)` | мовчить | мовчить | рендеру немає | `TypeError` |
| `setSongs(songs.sort())` | мовчить | мовчить | рендеру немає | `TypeError` |
| `player.volume = 60; setPlayer(player)` | мовчить | `react-hooks/immutability` | рендеру немає | `TypeError` |
| `player.device.name = 'x'; setPlayer({ ...player })` | мовчить | `react-hooks/immutability` | рендер є, старий стан зіпсовано | `TypeError` |
| `const next = [...songs]; next[0].title = 'x'; setSongs(next)` | мовчить | мовчить | рендер є, старий стан зіпсовано | `TypeError` |
| `setPlayer({ volume: 60 })`, решти полів немає | `TS2345` | мовчить | поля зникли | не допомагає |

Правило `react-hooks/immutability` знаходить присвоєння в поле значення, отриманого від `useState`, але мутуючі методи
й мутацію через копію в нашому запуску не помітило. Отже, ESLint тут є лише частковою перевіркою. Заморожування ловить
усі п'ять мутацій із таблиці, але лише тоді, коли цей код справді виконується. В останньому рядку мутації немає, тому
заморожування там не допомагає.

TypeScript може допомогти наперед. Якщо написати `useState<readonly Song[]>([])`, то `songs.push(...)` і
`songs.sort()` не компілюються: `TS2339: Property 'push' does not exist on type 'readonly Song[]'`. Але запис
`songs[0].title = 'x'` компілюється, бо `readonly` діє лише на один рівень, так само як `Readonly` з лекції
«TypeScript: дженерики». І ще одна деталь: функція `Object.freeze` у типах повертає `Readonly<T>`, тому `frozen.a =
...` не компілюється, але `frozen.a.b = 2` компілюється.

## Типові хибні уявлення

**«`set` повідомляє React, що дані змінилися».** Функція `set` передає React значення, а React порівнює його з
поточним. Якщо це той самий об'єкт, виклик нічого не робить. Варіанти «без `set`» і «той самий масив» дали однаковий
вивід.

**«React порівнює вміст».** Він порівнює лише посилання. Копія з таким самим вмістом викличе рендер, а змінений вміст
у тому самому об'єкті не викличе.

**«Екран оновився, отже, код правильний».** Варіант «копія після `push`» оновлює екран і псує попередній стан. Помилка
проявиться пізніше і в іншому місці, наприклад у кнопці «скасувати».

**«Мій `map` повертає новий масив, тому мутації немає».** Новий масив містить ті самі об'єкти. Присвоєння в елемент
змінює об'єкт, який лежить і в старому масиві, і, можливо, в іншому стані.

**«Глибока копія надійніша».** Вона правильно зберігає старі дані, але робить новими й ті об'єкти, які не змінилися.
Для кожного, хто порівнює посилання, це виглядає як зміна всього.

**«Копіювати при кожній зміні повільно».** Копіюється лише шлях до зміни, а незмінені об'єкти лишаються спільними.
Сторінка React зазначає, що розгортання копіює один рівень і тому швидке.

**«`Object.freeze` у розробці захищає застосунок».** У збірці цього виклику немає. Заморожування показує помилку
розробнику, а не захищає дані користувача.

**«Мутувати взагалі не можна».** Об'єкт, який ви щойно створили й ніхто ще не бачив, змінювати можна. Заборона
стосується того, що вже лежить у стані або прийшло в пропсах.

## Як це проявиться далі в React

- **День 10, стан як набір станів екрана.** Стан стане об'єктом із варіантами, і перехід між ними буде заміною
  об'єкта.
- **День 11, структура стану.** Там ви побачите, як позбутися глибокого копіювання, зробивши стан плоским, і чому
  обраний елемент зберігають як `selectedId`, а не копією об'єкта.
- **День 13, редюсер.** Редюсер є чистою функцією, яка приймає стан і дію та повертає новий стан. Сьогоднішні функції
  над списком є майже готовими гілками такого редюсера, і перевіряються вони так само, викликом без React.
- **Дні 16–19, ефекти.** React порівнює залежності ефекту через той самий `Object.is`, тому новий об'єкт запускає
  ефект знову, а мутація його не запускає.
- **Фаза 2, день 4, мемоізація.** Функція `memo` пропускає рендер, якщо пропси ті самі за посиланням. Незмінені
  елементи, які ви сьогодні навмисно не копіювали, дають саме це. Лекція «Значення й посилання» вже показувала замір
  на такому списку.
- **Фаза 3, день 7, стор поза React.** Стор повертає знімок даних, і той самий принцип вимагає нового об'єкта, коли
  дані змінилися.

## Перевірте себе

**1. Обробник робить `player.volume = 60` і `setPlayer(player)`. Що буде на екрані, що в об'єкті і чому немає
помилки?**

<details><summary>Відповідь</summary>

В об'єкті вже 60, а на екрані старе значення. React порівняв той самий об'єкт із самим собою через `Object.is` і
проігнорував оновлення. Помилки немає, бо змінювати звичайний об'єкт у JavaScript дозволено.

</details>

**2. Обробник робить `songs.push('x')` і `setSongs([...songs])`. Екран оновився. Що тут неправильно?**

<details><summary>Відповідь</summary>

Масив із попереднього стану зіпсовано, бо `push` змінив його. Якщо хтось тримає посилання на цей масив, наприклад
історія змін або інший стан, він побачить чужу пісню. Правильно створити новий масив без мутації: `setSongs([...songs,
'x'])`.

</details>

**3. Які об'єкти нові після правильної зміни `listener.player.device.name`, а які ті самі?**

<details><summary>Відповідь</summary>

Нові слухач, плеєр і пристрій, тобто все на шляху від зміни до верху. Тариф `listener.plan` лишається тим самим, бо
зміна його не стосується.

</details>

**4. Чому `const next = [...songs]; next.reverse(); setSongs(next)` правильно, а `const next = [...songs];
next[0].liked = true; setSongs(next)` неправильно?**

<details><summary>Відповідь</summary>

У першому випадку змінюється порядок у новому масиві, а новий масив ще ніхто не бачив. У другому випадку змінюється
об'єкт `next[0]`, а це той самий об'єкт, що й у старому масиві: розгортання копіює посилання на елементи, а не самі
елементи.

</details>

**5. Лічильник викликів компонента зріс після `setTrack(track)` із мутованим об'єктом, і `console.log` у тілі показав
нову назву. Чи оновився екран?**

<details><summary>Відповідь</summary>

Не обов'язково. Документація каже, що інколи React викликає компонент, перш ніж пропустити оновлення. У нашому запуску
тіло прочитало нову назву, але результат не потрапив у документ. Перевіряти треба сам документ.

</details>

**6. Чому `useState(() => freezeInDev(initial))` може зламати чужий код?**

<details><summary>Відповідь</summary>

`Object.freeze` заморожує сам об'єкт, а не копію. Значення `initial` належить тому, хто його передав. Якщо він пізніше
спробує його змінити, отримає `TypeError`.

</details>

**7. Приклад `expect(sorted(LIST)).toEqual(...)` зелений. Чому цього мало, щоб довести, що функція нічого не мутує?**

<details><summary>Відповідь</summary>

Функція з `sort` без копії теж повертає правильний результат, просто вона ще й переставляє елементи у вхідному масиві.
Мутацію ловить окремий приклад, який після виклику перевіряє сам вхід.

</details>

**8. Звідки в рекурсивній функції беруться перша гілка й рекурсивний виклик?**

<details><summary>Відповідь</summary>

З опису даних. Варіант без самопосилання, тобто примітив чи `null`, дає гілку без рекурсії. Самопосилання, тобто
вкладене значення в масиві чи об'єкті, дає один рекурсивний виклик на кожне таке значення.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| мутація | зміна вмісту об'єкта, який уже існує |
| заміна стану | передача в `set` нового об'єкта чи масиву замість зміни старого |
| локальна мутація | зміна об'єкта, який щойно створено і якого ще ніхто не отримав |
| рендер | виклик функції компонента, який дає опис розмітки |
| коміт | запис результату рендеру в документ |
| функція-оновлювач | функція, яку передають у `set`; вона отримує попередній стан і повертає новий |
| ініціалізатор | функція, яку передають у `useState`; React викликає її лише на першому рендері |
| заморожування | заборона змінювати об'єкт за допомогою `Object.freeze`, діє на один рівень |
| самопосилальний опис даних | опис, у якому один із варіантів знову посилається на цей самий опис |
| чернетка в Immer | особливий об'єкт, який записує ваші зміни, щоб побудувати з них новий об'єкт |
