# Лекція. Фаза 1, день 10. Стан як набір станів екрана

Досі ви додавали стан тоді, коли компоненту треба було щось запам'ятати: число, рядок, масив. Ця лекція вчить іншого:
спершу описати всі вигляди, які може мати екран, а вже потім вирішувати, які змінні для цього потрібні. Такий порядок
прибирає цілий клас помилок, коли на екрані водночас опиняються речі, які разом бувати не можуть. Читання займе
близько 50 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під
прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0. У справжньому браузері приклади не запускалися,
тому там, де йдеться про браузер, сказано, на чому це твердження тримається.

Застереження про версію компілятора: у перших лекціях про TypeScript команда `tsc` мала версію 7, а в проєкті `spa`
вона має версію 6.0. Це вимушене обмеження через ESLint. ESLint читає файли TypeScript через пакет
`typescript-eslint`, а цей пакет у версії 8.72 працює лише з TypeScript, нижчим за 6.1. Тому версію TypeScript у `spa`
закріплено на 6.0. Коли `typescript-eslint` запрацює з TypeScript 7, обмеження можна буде зняти.

Кожен дослід можна повторити в проєкті шаблону. Для цього створіть окремий файл тесту, наприклад
`src/payment.test.tsx`. Першим рядком напишіть `// @vitest-environment jsdom`. Далі йдуть рядки `import`: функції
`render`, `screen` і `act` приходять із пакета `@testing-library/react`, функція `userEvent` із пакета
`@testing-library/user-event`, функції `test` і `vi` із пакета `vitest`, а хук `useState` із пакета `react`. Лекція не
повторює ці рядки в кожному прикладі. Типи й компоненти залиште зверху файла, а код досліду покладіть усередину
`test('дослід', async () => { ... })`. Запускає файл команда `npx vitest run src/payment.test.tsx
--disable-console-intercept`, а прапорець у ній прибирає службові рядки навколо `console.log`. Кожному досліду дайте
власний файл, щоб екран попереднього досліду не заважав наступному.

**Після лекції ви зможете пояснити:**

- чим опис екрана станами відрізняється від опису діями і що кожен із цих способів вимагає пам'ятати;
- які п'ять кроків радить документація React і що саме робиться на кожному;
- чому п'ять булевих прапорців дають 32 поєднання і коли прапорці все ж нормальні;
- що дає розрізнюване об'єднання понад один рядок `status`;
- навіщо виносити переходи між станами в окрему функцію поза компонентом;
- чому після `await` наступний стан рахують оновлювачем;
- де цей опис перестає захищати і що робити із запізнілою відповіддю;
- як знайти мінімальний стан цілого екрана.

## Оплата, яка показує дві правди

Ви робите кнопку оплати замовлення. Людина натискає «Оплатити», банк якийсь час думає, а потім погоджує оплату або
відмовляє. Ви знаєте DOM, тому пишете те, що найочевидніше: при кожній події кажете кожному елементу, що йому робити.
Нижче звичайний код без React. Функція `bank` повертає проміс, а тест вирішує, коли й що відповість банк:

```ts
document.body.innerHTML = `
  <button id="pay">Оплатити</button>
  <p id="wait" hidden>Банк думає…</p>
  <p id="err" hidden>Банк відмовив</p>
  <p id="ok" hidden>Оплачено</p>`
const pay = document.querySelector<HTMLButtonElement>('#pay')!
const wait = document.querySelector<HTMLElement>('#wait')!
const err = document.querySelector<HTMLElement>('#err')!
const ok = document.querySelector<HTMLElement>('#ok')!

pay.onclick = async () => {
  pay.disabled = true
  wait.hidden = false
  const approved = await bank()
  if (approved) {
    pay.hidden = true
    wait.hidden = true
    ok.hidden = false
  } else {
    err.hidden = false
    pay.disabled = false
  }
}
```

Код виглядає розумно. Тест клацає кнопку, банк відмовляє, тест клацає знову, і банк погоджує. Після кожної події тест
друкує всі видимі елементи:

```ts
// Проміс чекає, а функцію, яка його виконує, тест кладе в answer. Так тест сам вирішує, коли й що відповість банк.
let answer!: (approved: boolean) => void
const bank = () => new Promise<boolean>((resolve) => { answer = resolve })
// Пауза дає обробнику час виконати рядки, що стоять після await.
const pause = () => new Promise((resolve) => setTimeout(resolve))
// Функція збирає текст усіх елементів, у яких немає атрибута hidden.
const visible = () =>
  [...document.body.children]
    .filter((element) => !(element as HTMLElement).hidden)
    .map((element) => element.textContent)
    .join(' + ')

pay.click()
console.log('перша спроба, банк думає:', visible())
answer(false)
await pause()
console.log('банк відмовив:', visible(), '| кнопка вимкнена:', pay.disabled)
pay.click()
console.log('друга спроба, банк думає:', visible())
answer(true)
await pause()
console.log('банк погодив:', visible())
```

```text
перша спроба, банк думає: Оплатити + Банк думає…
банк відмовив: Оплатити + Банк думає… + Банк відмовив | кнопка вимкнена: false
друга спроба, банк думає: Оплатити + Банк думає… + Банк відмовив
банк погодив: Банк відмовив + Оплачено
```

Останній рядок каже людині, що банк відмовив і що оплачено. Причини дві, і обидві дрібні. У гілці відмови забуто
сховати «Банк думає…». На початку другої спроби забуто сховати текст попередньої відмови. Жодна з цих помилок не кидає
винятку.

Такі помилки виникають не через неуважність однієї людини, а через сам спосіб запису. На екрані чотири елементи, а
обробник має три моменти, коли щось змінюється: клацання, згоду банку й відмову банку. Щоб екран був правильним, кожен
момент мусить згадати кожен елемент, хоча на вигляд потрібно змінити лише один чи два. Новий елемент додає рядок у
кожну гілку, а нова гілка вимагає подумати про кожен елемент.

## Два способи описати екран

Код вище називають **імперативним**: він перелічує команди, які треба виконати одну за одною. Сторінка `Reacting to
Input with State` пояснює різницю через аналогію. Імперативний код схожий на поїздку, де ви кажете водієві кожен
поворот. Декларативний код схожий на поїздку на таксі, де ви називаєте лише адресу, а маршрут обирає водій. У цій
аналогії повороти відповідають діям над DOM, адреса відповідає опису того, що має бути на екрані, а водієм є React.

**Декларативний** опис тієї самої оплати складається з двох частин. Перша частина каже, в якому стані зараз оплата.
Друга частина для кожного стану описує весь вигляд екрана. Пізніше ви побачите код цілком, а поки подивімося на
різницю в тому, що треба пам'ятати:

| Запитання | Команди | Стани |
|-----------|---------|-------|
| Де описано, як виглядає екран після відмови? | ніде цілком: це сума всіх команд, виконаних раніше | в одному місці, у гілці для відмови |
| Що залежить від попередньої дії? | вигляд екрана | лише те, який стан настане далі |
| Що треба зробити для нового елемента? | дописати його в кожен обробник | дописати його в опис вигляду |
| Як подивитися на вигляд після відмови? | клацнути й дочекатися відмови банку | передати цей стан у компонент |

Найважливіше запитання в цій таблиці стосується залежності від попередньої дії. Команди змінюють те, що вже є на
екрані, тому результат залежить від усієї історії. Опис стану від історії не залежить: той самий стан завжди дає той
самий вигляд. Лекція «Чистота й дерево» назвала таку властивість компонента чистотою.

## П'ять кроків

Сторінка `Reacting to Input with State` дає порядок роботи з п'яти кроків. Пройдімо їх на оплаті. Ця форма трохи
складніша за попередню: після натискання «Оплатити» людина бачить суму й має підтвердити оплату.

### Перелічити стани екрана

Спершу треба записати все, що людина може побачити, ще до будь-якої логіки. Нам вистачить таблиці:

| Стан | Що на екрані |
|------|--------------|
| `idle`, нічого не почато | кнопка «Оплатити» |
| `confirming`, чекаємо підтвердження | сума й увімкнена кнопка «Підтвердити» |
| `paying`, банк думає | сума, вимкнена кнопка, напис «Банк думає…» |
| `paid`, оплачено | лише чек, без кнопок |
| `declined`, банк відмовив | сума, увімкнена кнопка, текст відмови |

Документація порівнює цей крок із роботою дизайнера, який малює окремий макет для кожного стану, і згадує слово
**скінченний автомат**. Так називають модель, у якій система завжди перебуває в одному стані зі скінченного переліку й
переходить між ними за певними подіями. Цю модель вивчати окремо не треба, досить запам'ятати дві її вимоги: стан
завжди рівно один, а перехід завжди веде до одного наступного стану.

### Показати всі стани поруч

Тепер пишуть компонент, який нічого не вміє робити, але вміє показати будь-який стан, отриманий пропсом. Документація
називає його заглушкою, що керується пропсом. Перелік видів оплати `Payment` докладно пояснено далі, а поки достатньо
бачити, що в кожного виду є поле `kind`:

```tsx
function PaymentView({ payment }: { payment: Payment }) {
  if (payment.kind === 'paid') return <p>Оплачено, чек {payment.receipt}</p>
  if (payment.kind === 'idle') return <button>Оплатити</button>
  return (
    <>
      <p>До сплати: {payment.amount} грн</p>
      <button disabled={payment.kind === 'paying'}>Підтвердити</button>
      {payment.kind === 'paying' && <p>Банк думає…</p>}
      {payment.kind === 'declined' && <p role="alert">{payment.reason}</p>}
    </>
  )
}

const ALL: Payment[] = [
  { kind: 'idle' },
  { kind: 'confirming', amount: 250 },
  { kind: 'paying', amount: 250 },
  { kind: 'paid', receipt: 'A-17' },
  { kind: 'declined', amount: 250, reason: 'Недостатньо коштів' },
]

function Gallery() {
  return (
    <>
      {ALL.map((payment) => (
        <section key={payment.kind}>
          <h2>{payment.kind}</h2>
          <PaymentView payment={payment} />
        </section>
      ))}
    </>
  )
}
```

Тест малює `Gallery` і для кожної секції друкує кнопку й тексти:

```tsx
render(<Gallery />)
for (const section of document.querySelectorAll('section')) {
  const kind = section.querySelector('h2')!.textContent!
  const button = section.querySelector('button')
  const buttonText = button ? button.textContent + (button.disabled ? ' (вимкнена)' : '') : 'немає'
  // Тексти це всі абзаци секції. Якщо абзаців немає, тест друкує тире.
  const texts = [...section.querySelectorAll('p')].map((p) => p.textContent).join(' + ') || '—'
  console.log(`${kind.padEnd(10)} | кнопка: ${buttonText} | текст: ${texts}`)
}
```

```text
idle       | кнопка: Оплатити | текст: —
confirming | кнопка: Підтвердити | текст: До сплати: 250 грн
paying     | кнопка: Підтвердити (вимкнена) | текст: До сплати: 250 грн + Банк думає…
paid       | кнопка: немає | текст: Оплачено, чек A-17
declined   | кнопка: Підтвердити | текст: До сплати: 250 грн + Недостатньо коштів
```

Кожен рядок виводу відповідає одному об'єкту з масиву `ALL`. Рядок `paid` не має кнопки, бо перша перевірка в
`PaymentView` повертає лише абзац із чеком. Рядок `idle` не має тексту, бо друга перевірка повертає лише кнопку. Отже,
щоб побачити будь-який вигляд форми, вам досить додати один об'єкт у масив.

Компонент `Gallery` називають **службовим екраном**, бо його бачить лише розробник. Документація React наводить для
такої сторінки дві назви: `living styleguide` і `storybook`. Такий екран дає три вигоди. Ви бачите всі стани одразу, і
не треба годинами клацати, щоб дійти до рідкісної відмови банку. Стан із помилкою можна показати дизайнерові, хоча
сервера ще немає. А головне, на цьому кроці стає видно стан, який ви забули.

Цей прийом працює лише тому, що `PaymentView` нічого не пам'ятає сам. Тест намалював його двічі з тим самим станом і
порівняв HTML:

```tsx
const state: Payment = { kind: 'declined', amount: 250, reason: 'Недостатньо коштів' }
// Кожен виклик render створює окремий контейнер, тому це два незалежні покази компонента.
const first = render(<PaymentView payment={state} />).container.innerHTML
const second = render(<PaymentView payment={state} />).container.innerHTML
console.log(first === second, first)
```

```text
true <p>До сплати: 250 грн</p><button>Підтвердити</button><p role="alert">Недостатньо коштів</p>
```

Перше слово `true` означає, що два рядки HTML збіглися, а за ним надруковано сам рядок. Якби компонент тримав власний
стан, п'ять копій на службовому екрані показували б різне залежно від того, що в них клацали.

Чому в секції стоїть `key={payment.kind}`? Лекція «Списки й ключі» пояснила, що ключ має однозначно вказувати на
елемент. Поле `kind` тут підходить, бо в переліку кожен вид трапляється один раз.

### Знайти, що перемикає стани

Документація ділить причини змін на дві групи: дії людини й дії комп'ютера. Людина клацає й набирає текст. Комп'ютер
отримує відповідь мережі, дочікується таймера або завантаження картинки. Для цих двох груп потрібен різний код, але
результат однаковий: хтось має записати новий стан.

Для оплати виходить такий перелік переходів. Ліворуч стоїть стан, стрілка називає подію й того, хто її спричинив, а
праворуч стоїть наступний стан:

```text
idle        -- людина: «Оплатити» ------>  confirming
confirming  -- людина: «Підтвердити» --->  paying
confirming  -- людина: «Скасувати» ----->  idle
paying      -- людина: «Скасувати» ----->  idle
paying      -- банк: так --------------->  paid
paying      -- банк: ні ---------------->  declined
declined    -- людина: «Підтвердити» --->  paying
```

Документація радить намалювати такі стрілки хоча б на папері. Цей перелік швидко показує дві проблеми. Стан, у який не
веде жодна стрілка, зайвий. Стан, з якого не виходить жодна стрілка, стає тупиком для людини. Тут тупик один, `paid`,
і він навмисний.

### Записати стан у пам'ять

Третій крок переводить перелік у змінні. Документація чесно каже, що перша спроба рідко буває найкращою, і пропонує
почати з прапорця на кожен стан, якщо ви не знаєте, з чого почати:

```tsx
const [isIdle, setIdle] = useState(true)
const [isConfirming, setConfirming] = useState(false)
const [isPaying, setPaying] = useState(false)
const [isPaid, setPaid] = useState(false)
const [isDeclined, setDeclined] = useState(false)
```

На цьому кроці код ще можна залишити таким, бо наступний крок існує саме для того, щоб його виправити.

### Прибрати зайве

Мета цього кроку документації сформульована просто: прибрати поєднання, для яких немає правильного вигляду екрана.
Кожну змінну перевіряють трьома запитаннями:

- **Чи створює вона парадокс?** Парадоксом документація називає поєднання, яке неможливо показати. `isPaying` і
  `isPaid` можуть обидва дорівнювати `true`, і тоді незрозуміло, що малювати.
- **Чи є та сама інформація в іншій змінній?** Якби ми тримали ще й `isEmpty` для порожнього тексту, цю відповідь
  давав би вираз `text.length === 0`.
- **Чи можна отримати її інверсією іншої?** Якщо є змінна `reason` із текстом помилки або `null`, то прапорець
  `isError` не потрібен, бо його замінює вираз `reason !== null`.

Перше запитання замінює всі п'ять прапорців одним рядком зі значеннями `'idle'`, `'confirming'` тощо. Приклад у
документації зупиняється на трьох змінних: текст відповіді, текст помилки й `status`. Ми підемо на крок далі, і
причину цього пояснює наступний великий розділ.

### Під'єднати обробники

Останній крок пише обробники, які викликають `set`. Код буде довшим за команди DOM із початку лекції, і документація
цього не приховує. Натомість кожен новий вигляд можна додати, не чіпаючи решти, а поєднань, які неможливо показати,
більше немає.

## Скільки поєднань дозволяє опис

Подивімося на прапорці як на арифметику. Кожен булевий прапорець має два значення, і прапорці незалежні, тому
кількість поєднань множиться. Тест перебирає всі поєднання й рахує ті, де істинний рівно один прапорець:

```ts
for (const flags of [2, 3, 4, 5, 6, 8]) {
  let valid = 0
  for (let bits = 0; bits < 2 ** flags; bits++) {
    let ones = 0
    for (let i = 0; i < flags; i++) if (bits & (1 << i)) ones++
    if (ones === 1) valid++
  }
  console.log(`прапорців ${flags}: усього ${2 ** flags}, осмислених ${valid}, зайвих ${2 ** flags - valid}`)
}
```

```text
прапорців 2: усього 4, осмислених 2, зайвих 2
прапорців 3: усього 8, осмислених 3, зайвих 5
прапорців 4: усього 16, осмислених 4, зайвих 12
прапорців 5: усього 32, осмислених 5, зайвих 27
прапорців 6: усього 64, осмислених 6, зайвих 58
прапорців 8: усього 256, осмислених 8, зайвих 248
```

Цикл читає біти числа `bits` як значення прапорців. Запис `bits & (1 << i)` перевіряє, чи встановлено біт номер `i`.
Деталі цього запису сьогодні не важливі, важливі лише числа: кожен новий стан додає один осмислений варіант і подвоює
кількість усіх варіантів. Кожне зайве поєднання є станом, у якому екран опиниться, якщо хоч один виклик `set` забуто.

Перелік значень працює інакше. Одне поле з п'яти значень має рівно п'ять варіантів, а новий стан додає рівно один
варіант. Коротко: незалежні змінні множать варіанти, а один перелік їх додає.

**Прапорці не заборонено.** Ця арифметика стосується лише випадку, коли стани виключають один одного. Поміркуйте про
відеоплеєр із двома прапорцями: `isMuted` (вимкнено звук) і `isFullscreen` (на весь екран). Обидва значення незалежні,
і всі чотири поєднання мають сенс. Об'єднати їх в один перелік означало б вигадати чотири назви там, де вистачало двох
прапорців. Перевірка проста: випишіть поєднання й запитайте, чи для кожного є правильний вигляд екрана. Якщо для
кожного є, змінні справді незалежні.

## Розрізнюване об'єднання як опис стану

Рядок `status` прибирає поєднання прапорців, але лишає інше питання: де лежать дані, які мають сенс лише в деяких
станах? Сума потрібна, поки оплата не завершена. Чек з'являється лише після оплати. Текст відмови існує лише після
відмови. Найпростіший запис кладе все поруч:

```ts
type Status = 'idle' | 'confirming' | 'paying' | 'paid' | 'declined'
type Loose = { status: Status; amount: number | null; receipt: string | null; reason: string | null }

export const f: Loose = { status: 'paid', amount: null, receipt: null, reason: 'Недостатньо коштів' }
```

`tsc` приймає останній рядок мовчки. Цей об'єкт каже, що оплачено, чека немає, а причина відмови є. Документація React
помічає цю саму проблему у згорнутому блоці `Eliminating "impossible" states with a reducer`: навіть після скорочення
до трьох змінних лишаються поєднання без сенсу.

Лекція «TypeScript: основи» вже показала рішення на етапах доставки посилки. **Розрізнюваним об'єднанням** називають
тип із кількох варіантів зі спільним полем, яке в кожному варіанті має власне значення. Кожен вид оплати несе лише
свої дані:

```ts
export type Payment =
  | { kind: 'idle' }
  | { kind: 'confirming'; amount: number }
  | { kind: 'paying'; amount: number }
  | { kind: 'paid'; receipt: string }
  | { kind: 'declined'; amount: number; reason: string }
```

Поле `kind` тут називають **розрізнювачем**. За його значенням TypeScript вирішує, який саме вид перед ним. Покажемо,
що цей тип справді забороняє. Рядок `@ts-expect-error` просить компілятор переконатися, що наступний рядок містить
помилку типу. Якщо помилки немає, компілятор скаржиться вже на цей рядок, тому такий запис є прикладом, який
перевіряється автоматично:

```ts
// @ts-expect-error: у виду paying немає поля reason
export const a: Payment = { kind: 'paying', amount: 250, reason: 'x' }
// @ts-expect-error: у виду paid немає amount
export const b: Payment = { kind: 'paid', receipt: 'A-17', amount: 250 }
// @ts-expect-error: declined без reason
export const c: Payment = { kind: 'declined', amount: 250 }
// @ts-expect-error: такого виду немає
export const d: Payment = { kind: 'refunded' }
```

`tsc` мовчить, тобто всі чотири заборони спрацювали. Об'єкт зі значенням «банк думає й водночас відмовив» записати не
можна, і для цього не потрібна дисципліна розробника.

**Межа цієї заборони.** Зайве поле компілятор ловить лише в об'єкті, записаному прямо в присвоєнні. Таку перевірку
документація TypeScript називає перевіркою зайвих властивостей. Якщо об'єкт спершу лежить в окремій змінній, зайве
поле проходить:

```ts
const raw = { kind: 'paying' as const, amount: 250, reason: 'x' }
export const e: Payment = raw
```

Цей код компілюється без помилок. Вид `paying` вимагає полів `kind` і `amount`, і вони є. Зайве поле `reason` при
цьому лежить в об'єкті, але прочитати його через `e` компілятор не дасть. Отже, об'єднання гарантує дві речі: потрібні
поля є, і код не прочитає чужого поля. Воно не гарантує, що в об'єкті немає нічого зайвого.

### Як компілятор використовує `kind`

Прочитати поле, яке є не в усіх видах, не можна:

```ts
export function wrong(payment: Payment) {
  return payment.reason
}
```

Команда `npx tsc --noEmit -p tsconfig.app.json` перевіряє всі файли теки `src`, зокрема наш файл `src/t2.ts`. Для
кожної помилки вона друкує шлях, рядок і стовпець. У вашому файлі ці числа будуть іншими, бо в нашому файлі перед цією
функцією стоять інші приклади:

```text
src/t2.ts(19,18): error TS2339: Property 'reason' does not exist on type 'Payment'.
  Property 'reason' does not exist on type '{ kind: "idle"; }'.
```

Перший рядок називає місце й саму помилку: у типі `Payment` компілятор не знаходить поля `reason`. Другий рядок
називає причину: поле мусить бути в усіх видах об'єднання, а у виду `idle` його немає. Отже, у своєму коді ви не прочитаєте
поле чужого виду випадково, бо спершу доведеться перевірити `kind`.

Перевірка `kind` **звужує** тип, тобто каже компілятору, що далі можлива лише частина видів. Усередині гілки
`payment.kind === 'declined'` тип уже один, і читати `reason` можна. Читати чуже поле в цій гілці не можна:

```ts
export function wrong2(payment: Payment) {
  if (payment.kind === 'confirming') return payment.receipt
}
```

```text
src/t2.ts(22,53): error TS2339: Property 'receipt' does not exist on type '{ kind: "confirming"; amount: number; }'.
```

Тепер повідомлення називає лише один вид, `confirming`, бо перевірка в цьому рядку вже відкинула всі інші.

У компоненті `PaymentView` вище цей механізм працює непомітно. Після двох перших `return` тип `payment` звужено до
трьох видів, у кожному з яких є `amount`, тому `{payment.amount}` компілюється. А запис `payment.kind === 'declined'
&& <p>{payment.reason}</p>` робить дві справи одним виразом: звужує тип і вирішує, чи малювати абзац.

Звуження не зникає й у стрілці, створеній усередині гілки, якщо змінну ніхто не перепризначає. Функція нижче
компілюється:

```ts
export function late(p: Payment) {
  if (p.kind !== 'declined') return null
  return () => p.reason
}
```

Це зручно для обробників у JSX, адже вони теж є стрілками, а змінні зі `useState` оголошено через `const`.

### Перевірка повноти

Лекція «TypeScript: основи» вже показала тип `never`, якому не належить жодне значення. Якщо в `switch` розібрано всі
види, у гілці `default` не лишається жодного, і тип змінної там `never`. Запишіть цей факт присвоєнням, і компілятор
перевірить його за вас. У функції нижче гілку `declined` забуто навмисно:

```ts
export function title(payment: Payment): string {
  switch (payment.kind) {
    case 'idle':
      return 'Нічого не почато'
    case 'confirming':
      return `Списати ${payment.amount} грн?`
    case 'paying':
      return 'Банк думає…'
    case 'paid':
      return `Чек ${payment.receipt}`
    default: {
      const exhaustive: never = payment
      return exhaustive
    }
  }
}
```

```text
src/t2.ts(13,13): error TS2322: Type '{ kind: "declined"; amount: number; reason: string; }' is not assignable to type 'never'.
```

Повідомлення називає саме той вид, який забуто. Це важливо, коли стан додають через пів року: новий вид одразу стає
помилкою в кожному такому `switch`, і ви отримуєте перелік місць для правки.

### Оператор `in`

Інколи кілька видів мають спільне поле, і перелічувати їх незручно. Оператор `in` перевіряє наявність поля й теж
звужує тип:

```ts
export function viaIn(payment: Payment) {
  if ('amount' in payment) return payment.amount
  return payment.kind
}
```

У першій гілці лишаються три види з `amount`, а в другій лишаються `idle` і `paid`. Це не замінює `kind`, а лише
скорочує запис там, де вас цікавить саме поле, а не вид.

## Функція переходів

Схему зі стрілками тепер можна записати кодом. Звернімо увагу, що подія сама є таким самим переліком видів, бо різні
події несуть різні дані:

```ts
export type PaymentEvent =
  | { type: 'started'; amount: number }
  | { type: 'cancelled' }
  | { type: 'confirmed' }
  | { type: 'approved'; receipt: string }
  | { type: 'refused'; reason: string }

export function nextPayment(payment: Payment, event: PaymentEvent): Payment {
  switch (event.type) {
    case 'started':
      return payment.kind === 'idle' ? { kind: 'confirming', amount: event.amount } : payment
    case 'cancelled':
      return payment.kind === 'confirming' || payment.kind === 'paying' ? { kind: 'idle' } : payment
    case 'confirmed':
      return payment.kind === 'confirming' || payment.kind === 'declined'
        ? { kind: 'paying', amount: payment.amount }
        : payment
    case 'approved':
      return payment.kind === 'paying' ? { kind: 'paid', receipt: event.receipt } : payment
    case 'refused':
      return payment.kind === 'paying'
        ? { kind: 'declined', amount: payment.amount, reason: event.reason }
        : payment
  }
}
```

Прочитаємо гілку `refused`. Відмова банку має сенс лише тоді, коли банк справді думає, тому вираз спершу перевіряє
`payment.kind === 'paying'`. Ця перевірка також звужує тип, і тому `payment.amount` читати дозволено. Новий стан бере
суму зі старого стану, а текст бере з події. В усіх інших станах функція повертає `payment` без змін.

Тест проганяє всі пари стану й події. Масив `ALL` узято зі службового екрана. Крапка означає, що стан не змінився:

```ts
const EVENTS: PaymentEvent[] = [
  { type: 'started', amount: 250 },
  { type: 'cancelled' },
  { type: 'confirmed' },
  { type: 'approved', receipt: 'A-17' },
  { type: 'refused', reason: 'Недостатньо коштів' },
]
console.log(' '.repeat(11) + EVENTS.map((event) => event.type.padEnd(11)).join('').trimEnd())
for (const payment of ALL) {
  const cells = EVENTS.map((event) => {
    const next = nextPayment(payment, event)
    // Той самий об'єкт означає, що подія не на часі.
    return (next === payment ? '·' : next.kind).padEnd(11)
  })
  console.log((payment.kind.padEnd(11) + cells.join('')).trimEnd())
}
```

```text
           started    cancelled  confirmed  approved   refused
idle       confirming ·          ·          ·          ·
confirming ·          idle       paying     ·          ·
paying     ·          idle       ·          paid       declined
paid       ·          ·          ·          ·          ·
declined   ·          ·          paying     ·          ·
```

Перший рядок виводу містить назви подій, а кожен наступний рядок відповідає одному стану. Кожна клітинка, що не
містить крапки, є стрілкою зі схеми вище. Порівняйте цей запис із командами DOM із початку лекції: тут неможливо
наполовину виконати перехід, бо новий стан замінює старий цілком.

Навіщо писати функцію окремо від компонента? Причин три.

**Її легко перевірити.** Для функції не потрібні ні React, ні екран, ні банк. Приклад для неї займає один рядок: стан
і подія на вході, стан на виході.

**Вона не знає про час.** Подія, яка прийшла не вчасно, просто нічого не змінює. Це правило описано в одному місці, і
обробникам кнопок не треба думати, чи можна їм зараз спрацювати.

**Вона повертає той самий об'єкт, коли нічого не сталося.** Лекція «Об'єкти й масиви в стані» пояснила, що React
порівнює новий стан зі старим функцією `Object.is`. Якщо функція повертає те саме посилання, оновлення пропускається.
Перевіримо це лічильником викликів компонента:

```tsx
let calls = 0
let send!: (event: PaymentEvent) => void
function Live() {
  const [payment, setPayment] = useState<Payment>({ kind: 'paying', amount: 250 })
  calls++
  send = (event) => setPayment((p) => nextPayment(p, event))
  return <p>{payment.kind}</p>
}
render(<Live />)
console.log('після першого показу викликів:', calls)
act(() => send({ type: 'started', amount: 999 }))
act(() => send({ type: 'started', amount: 999 }))
console.log('після двох подій не на часі викликів:', calls, '| на екрані:', screen.getByRole('paragraph').textContent)
act(() => send({ type: 'refused', reason: 'x' }))
console.log('після відмови банку викликів:', calls, '| на екрані:', screen.getByRole('paragraph').textContent)
```

```text
після першого показу викликів: 1
після двох подій не на часі викликів: 1 | на екрані: paying
після відмови банку викликів: 2 | на екрані: declined
```

Функція `act` з Testing Library просить React виконати всі заплановані оновлення до наступного рядка. Запис `send =
...` у тілі компонента є лише прийомом цього досліду, щоб викликати `set` із тесту. У робочому коді так не пишуть.
Лекція «Об'єкти й масиви в стані» попереджала, що в окремих випадках React може ще раз викликати компонент, перш ніж
пропустити оновлення. Тут цього не сталося, але покладатися на точну кількість викликів не варто. Покладатися можна на
те, що екран лишається таким самим.

Така функція має власну назву в React. Функцію вигляду «стан і подія на вході, новий стан на виході» називають
редюсером, і окрема тема «Редюсер» покаже хук `useReducer`, який приймає її готовою. Сьогодні ви пишете таку функцію
самі й викликаєте через `useState`.

## Жива форма: один стан і відповідь, яка приходить пізніше

Тепер збираємо все разом. Форма без стану отримує пропс, а батьківський компонент тримає один стан і перетворює події
на переходи:

```tsx
type Answer = { ok: true; receipt: string } | { ok: false; reason: string }

function Live({ charge }: { charge: (amount: number) => Promise<Answer> }) {
  const [payment, setPayment] = useState<Payment>({ kind: 'idle' })
  async function confirm() {
    const next = nextPayment(payment, { type: 'confirmed' })
    if (next.kind !== 'paying') return
    setPayment(next)
    const answer = await charge(next.amount)
    const event = answer.ok
      ? { type: 'approved' as const, receipt: answer.receipt }
      : { type: 'refused' as const, reason: answer.reason }
    setPayment((current) => nextPayment(current, event))
  }
  return (
    <Form
      payment={payment}
      onStart={() => setPayment((p) => nextPayment(p, { type: 'started', amount: 250 }))}
      onConfirm={confirm}
      onCancel={() => setPayment((p) => nextPayment(p, { type: 'cancelled' }))}
    />
  )
}
```

Компонент `Form` влаштований так само, як `PaymentView`, і лише додатково передає обробники кнопкам:

```tsx
type FormProps = { payment: Payment; onStart: () => void; onConfirm: () => void; onCancel: () => void }

function Form({ payment, onStart, onConfirm, onCancel }: FormProps) {
  if (payment.kind === 'paid') return <p>Оплачено, чек {payment.receipt}</p>
  if (payment.kind === 'idle') return <button onClick={onStart}>Оплатити</button>
  return (
    <>
      <p>До сплати: {payment.amount} грн</p>
      <button disabled={payment.kind === 'paying'} onClick={onConfirm}>Підтвердити</button>
      {payment.kind !== 'declined' && <button onClick={onCancel}>Скасувати</button>}
      {payment.kind === 'paying' && <p>Банк думає…</p>}
      {payment.kind === 'declined' && <p role="alert">{payment.reason}</p>}
    </>
  )
}
```

Розберемо функцію `confirm` рядок за рядком, бо в ній зосереджено головну складність дня.

- Запис `const next = nextPayment(...)` питає функцію переходів, що станеться після підтвердження. Сам стан він ще не
  змінює.
- Запис `if (next.kind !== 'paying') return` виходить, якщо підтвердження зараз не веде до стану `paying`. Завдяки
  цьому запит до банку не піде зі стану, де платити не можна. Ця перевірка також звужує тип, тому `next.amount`
  дозволено.
- Виклик `setPayment(next)` записує новий стан, а React планує новий рендер.
- Запис `await charge(...)` чекає на банк. Поки він чекає, компонент може бути показаний знову будь-яку кількість
  разів.
- Останній виклик `setPayment` записує результат оновлювачем.

Чому не можна написати простіше: `setPayment(nextPayment(payment, event))`? Лекція «Рендер, коміт і знімок стану»
пояснила, що змінна стану є знімком рендеру, у якому створено обробник. Цей обробник створено ще тоді, коли стан був
`confirming`. Рядок `setPayment(next)` змінив стан у React, але не змінив змінну `payment` у цьому виклику.
Подивімося, що стається, якщо все ж узяти знімок. Додамо компоненту `Live` пропс `stale`, а останній виклик
`setPayment` у функції `confirm` замінимо такими двома рядками:

```tsx
if (stale) setPayment(nextPayment(payment, event))
else setPayment((current) => nextPayment(current, event))
```

Тест запускає варіант зі знімком, і банк погоджує оплату. Банк тут представлено функцією `deferred`:

```tsx
// deferred створює проміс і віддає назовні функцію resolve, тому тест сам вирішує, коли банк відповість.
function deferred<T>() {
  let resolve!: (value: T) => void
  const promise = new Promise<T>((done) => { resolve = done })
  return { promise, resolve }
}

const bank = deferred<Answer>()
const user = userEvent.setup()
render(<Live charge={() => bank.promise} stale />)
await user.click(screen.getByRole('button', { name: 'Оплатити' }))
await user.click(screen.getByRole('button', { name: 'Підтвердити' }))
console.log('банк думає:', screen.queryByText('Банк думає…') !== null)
// Функція act чекає, поки виконаються рядки після await у confirm і React оновить екран.
await act(async () => bank.resolve({ ok: true, receipt: 'A-17' }))
const button = screen.getByRole<HTMLButtonElement>('button', { name: 'Підтвердити' })
const receipt = screen.queryByText('Оплачено, чек A-17') !== null
console.log('чек на екрані:', receipt, '| кнопка вимкнена:', button.disabled, '| банк думає:', screen.queryByText('Банк думає…') !== null)
```

```text
банк думає: true
чек на екрані: false | кнопка вимкнена: false | банк думає: false
```

Банк погодив оплату, а екран знову просить її підтвердити. Простежимо, чому так сталося. У знімку `payment` лежить
`confirming`. Функція `nextPayment` бачить подію `approved` у стані `confirming` і вважає її не на часі, тому повертає
знімок без змін. Виклик `set` отримує об'єкт `confirming`, який відрізняється від поточного `paying`, і React показує
форму підтвердження. Гроші вже списано, а людина бачить кнопку, яка пропонує списати їх знову.

Оновлювач вирішує цю проблему, бо React передає в нього стан із черги, а не зі знімка. Поточний стан там `paying`,
тому перехід спрацьовує.

Оновлювач теж має обмеження. React може викликати його двічі в суворому режимі, про що казала лекція «Чистота й
дерево», тому функція переходів мусить бути чистою. Запит до банку всередині `nextPayment` у цьому режимі пішов би
двічі. Тому побічні дії лишаються в обробнику, а функція лише рахує наступний стан.

## Покроковий приклад: відмова й повтор

Тест проходить шлях від початку до кінця: оплата, відмова, повтор, успіх. Банк тут знову представлено функцією
`deferred`, яка створює проміс і дає тесту змогу виконати його тоді, коли треба. Компонент записує стан на кожному
своєму виклику, бо в тіло `Live` перед `return` додано рядок `log.push(JSON.stringify(payment))`:

```tsx
// Цей масив стоїть поза тестом, поруч із компонентом Live, бо компонент дописує в нього.
const log: string[] = []
const first = deferred<Answer>()
const second = deferred<Answer>()
// Функція vi.fn рахує свої виклики, а кожен виклик повертає наступний проміс із переліку.
const charge = vi.fn<(amount: number) => Promise<Answer>>()
  .mockReturnValueOnce(first.promise)
  .mockReturnValueOnce(second.promise)
const user = userEvent.setup()
const confirmButton = () => screen.getByRole<HTMLButtonElement>('button', { name: 'Підтвердити' })

render(<Live charge={charge} />)
await user.click(screen.getByRole('button', { name: 'Оплатити' }))
await user.click(confirmButton())
console.log('під час очікування кнопка вимкнена:', confirmButton().disabled, '| запитів:', charge.mock.calls.length)
await user.click(confirmButton())
console.log('після клацання по вимкненій кнопці запитів:', charge.mock.calls.length)
await act(async () => first.resolve({ ok: false, reason: 'Недостатньо коштів' }))
await user.click(confirmButton())
console.log('повтор: запитів', charge.mock.calls.length, '| помилка на екрані:', screen.queryByRole('alert') !== null)
await act(async () => second.resolve({ ok: true, receipt: 'A-17' }))
console.log(log.join('\n'))
```

Останній рядок досліду друкує журнал станів, по одному рядку на кожен виклик компонента:

```text
{"kind":"idle"}
{"kind":"confirming","amount":250}
{"kind":"paying","amount":250}
{"kind":"declined","amount":250,"reason":"Недостатньо коштів"}
{"kind":"paying","amount":250}
{"kind":"paid","receipt":"A-17"}
```

Той самий шлях докладно:

| Крок | Хто діє | Подія | Стан після | Що на екрані |
|------|---------|-------|------------|--------------|
| 1 | React | перший показ | `idle` | кнопка «Оплатити» |
| 2 | людина | «Оплатити» | `confirming`, 250 | сума, кнопка увімкнена |
| 3 | людина | «Підтвердити» | `paying`, 250 | сума, кнопка вимкнена, «Банк думає…» |
| 4 | людина | клацання по вимкненій кнопці | без змін | те саме, запитів і далі один |
| 5 | банк | відмова | `declined`, 250, причина | сума, кнопка увімкнена, текст відмови |
| 6 | людина | «Підтвердити» | `paying`, 250 | текст відмови зник сам |
| 7 | банк | згода | `paid`, чек | лише чек |

Три виклики `console.log`, що стоять посеред того самого досліду, підтверджують клацання по вимкненій кнопці й повтор:

```text
під час очікування кнопка вимкнена: true | запитів: 1
після клацання по вимкненій кнопці запитів: 1
повтор: запитів 2 | помилка на екрані: false
```

Порівняйте повтор із варіантом на командах DOM із початку лекції. Там текст відмови лишився, бо ніхто не наказав його
сховати. Тут ніхто не ховає його спеціально: у виді `paying` поля `reason` немає, тому й малювати нічого.

Клацання по вимкненій кнопці перевірено в jsdom. Бібліотека `user-event` не клацає вимкнені елементи, тому що за
специфікацією HTML вимкнена кнопка не отримує клацань. У справжньому браузері цей код не запускався, але ви можете
перевірити поведінку сторінки `f1-d10.html` зі своєї практики: `npm run dev` і вкладка в браузері.

## Запізніла відповідь: межа цього опису

Функція переходів ігнорує події не на часі, і цього здебільшого досить. Подивімося на випадок, коли цього замало.
Людина скасовує очікування, починає нову оплату на іншу суму, а відповідь банку на першу оплату приходить саме тоді:

```ts
let p: Payment = { kind: 'idle' }
// Функція step застосовує подію й друкує підпис разом із новим станом.
function step(label: string, event: PaymentEvent) {
  p = nextPayment(p, event)
  console.log(label.padEnd(30), JSON.stringify(p))
}
step('почали на 250', { type: 'started', amount: 250 })
step('підтвердили', { type: 'confirmed' })
step('скасували', { type: 'cancelled' })
step('прийшла відповідь на 250', { type: 'approved', receipt: 'A-17' })
step('почали знову, на 400', { type: 'started', amount: 400 })
step('підтвердили', { type: 'confirmed' })
step('запізніла відповідь на 250', { type: 'approved', receipt: 'A-17' })
```

```text
почали на 250                  {"kind":"confirming","amount":250}
підтвердили                    {"kind":"paying","amount":250}
скасували                      {"kind":"idle"}
прийшла відповідь на 250       {"kind":"idle"}
почали знову, на 400           {"kind":"confirming","amount":400}
підтвердили                    {"kind":"paying","amount":400}
запізніла відповідь на 250     {"kind":"paid","receipt":"A-17"}
```

Рядок «прийшла відповідь на 250» показує, що відповідь у стані `idle` проігноровано правильно. Останній рядок показує
проблему: відповідь на оплату 250 гривень закрила оплату на 400 гривень, бо функція бачить лише вид `paying` і не
знає, до якої спроби належить відповідь. Тип не може цього помітити.

Одне з можливих рішень додає номер спроби і в стан `paying`, і в подію, щоб функція порівнювала їх. У вашому завданні
дня цієї проблеми немає, бо там не можна скасувати очікування. Запізнілі відповіді докладно з'являться в темах про
ефекти й у фазі 3, де дані приходять із мережі.

## Рецепт для переліку зі структурами

Практика дня йде за рецептом книжки How to Design Programs, який уже використовували лекції «Події й стан» та «Об'єкти
й масиви в стані». Сьогоднішня глава книжки називається `Itemizations and Structures`, і вона додає один новий
випадок. Досі перелік складався зі значень, а структура складалася з полів. Тепер кожен пункт переліку сам може бути
структурою.

Книжка показує це на грі. Гравець або ще цілиться, і тоді в грі два об'єкти, або вже вистрілив, і тоді об'єктів три.
Це та сама думка, що й у `Payment`: у різних станах існують різні дані. Книжка каже, коли потрібен такий опис: коли в
задачі є різні види інформації, і принаймні деякі з них складаються з кількох частин.

Шаблон функції тепер будують у двох вимірах, і це легко перекласти на TypeScript:

| Що каже рецепт | Як це виглядає у вас |
|----------------|----------------------|
| стільки гілок умови, скільки пунктів у переліку | по `case` на кожен `kind` |
| у кожній гілці умова, яка впізнає цей пункт | сам `case 'declined':` |
| якщо пункт є структурою, у гілці перелічено її поля | `payment.amount`, `payment.reason` у цій гілці |
| приклади: хоча б один на кожен пункт | по прикладу на кожен вид стану |

Шаблон важливий тим, що його пишуть до розв'язку. Ви дивитеся на опис даних і ще до всякої логіки знаєте, скільки
гілок матиме функція й які поля доступні в кожній. Гілка `default` із `never` змушує `tsc` перевіряти одну частину
цього шаблону автоматично.

Книжка також радить ще одне: якщо застрягли на складному випадку, спершу заповніть простий, а для решти лишіть
значення за замовчуванням. Частина прикладів падатиме, але ви бачитимете, як зростає кількість пройдених. На цьому
принципі побудовано ваші заготовки.

## Той самий підхід на цілому екрані

Глава `Thinking in React` застосовує цю саму логіку не до однієї форми, а до всього екрана. Простежимо її кроки на
розкладі потягів. На екрані поле «Куди», галочка «Лише прямі», лічильник і список рейсів.

**Розбити на компоненти.** Розмітка сама підказує межі: `Timetable` охоплює все, `SearchBar` приймає введення,
`TrainTable` показує рейси.

**Написати статичну версію.** Спершу компоненти малюють дані лише через пропси, без стану. Глава наполягає на цьому
порядку: статична версія вимагає багато друку й жодних роздумів, а взаємодія потребує багато роздумів і небагато
друку. Дані йдуть згори вниз, від батька до дітей, і такий рух називають **однобічним потоком даних**.

**Знайти мінімальний стан.** На екрані чотири шматки даних. Глава пропонує для кожного три запитання: чи лишається
воно незмінним, чи приходить від батька пропсом, чи можна його обчислити. Якщо хоч одна відповідь «так», це не стан.

| Дані | Незмінні? | Пропс? | Можна обчислити? | Стан? |
|------|-----------|--------|------------------|-------|
| весь розклад | так | так | ні | ні |
| текст у полі | ні | ні | ні | **так** |
| галочка | ні | ні | ні | **так** |
| відфільтровані рейси | ні | ні | так, з трьох попередніх | ні |
| кількість знайдених | ні | ні | так, це довжина відфільтрованих | ні |

На цілий екран виходить два стани.

**Вирішити, де живе стан.** Для кожного стану треба знайти всі компоненти, які щось малюють на його основі, а потім
їхнього найближчого спільного батька. Текст показує `SearchBar`, а фільтрує за ним `TrainTable`. Спільний батько в них
`Timetable`, тому стан лежить там.

**Додати зворотний потік.** Дані йдуть униз, але людина вводить текст у дитині. Батько передає дитині функції, а
дитина викликає їх. Лекція «Події й стан» уже показала цей прийом у розділі про те, як дитина повідомляє батькові.

```tsx
function Timetable({ trains }: { trains: Train[] }) {
  const [text, setText] = useState('')
  const [onlyDirect, setOnlyDirect] = useState(false)
  const shown = trains.filter((t) => t.to.includes(text) && (!onlyDirect || t.direct))
  return (
    <>
      <SearchBar text={text} onlyDirect={onlyDirect} onTextChange={setText} onOnlyDirectChange={setOnlyDirect} />
      <p>Знайдено: {shown.length}</p>
      <TrainTable trains={shown} />
    </>
  )
}
```

Дочірні компоненти лише малюють пропси й викликають отримані функції. Рейси лежать у звичайному масиві:

```tsx
type Train = { time: string; to: string; direct: boolean }

const TRAINS: Train[] = [
  { time: '07:10', to: 'Київ', direct: true },
  { time: '09:40', to: 'Одеса', direct: true },
  { time: '13:25', to: 'Київ', direct: false },
  { time: '18:05', to: 'Львів', direct: false },
]

type SearchBarProps = {
  text: string
  onlyDirect: boolean
  onTextChange: (text: string) => void
  onOnlyDirectChange: (onlyDirect: boolean) => void
}

function SearchBar({ text, onlyDirect, onTextChange, onOnlyDirectChange }: SearchBarProps) {
  return (
    <form>
      <input aria-label="Куди" value={text} onChange={(event) => onTextChange(event.target.value)} />
      <label>
        <input type="checkbox" checked={onlyDirect} onChange={(event) => onOnlyDirectChange(event.target.checked)} />
        Лише прямі
      </label>
    </form>
  )
}

function TrainTable({ trains }: { trains: Train[] }) {
  return <ul>{trains.map((t) => <li key={t.time}>{t.time} {t.to}</li>)}</ul>
}
```

Тест набирає текст, ставить галочку й після кожної дії друкує лічильник і список:

```tsx
const user = userEvent.setup()
render(<Timetable trains={TRAINS} />)
const report = (label: string) => {
  const found = screen.getByText(/^Знайдено/).textContent
  const list = screen.getAllByRole('listitem').map((item) => item.textContent).join(', ')
  console.log(label.padEnd(22), found, '|', list)
}
report('спочатку')
await user.type(screen.getByLabelText('Куди'), 'Київ')
report('набрали «Київ»')
await user.click(screen.getByLabelText('Лише прямі'))
report('поставили галочку')
```

```text
спочатку               Знайдено: 4 | 07:10 Київ, 09:40 Одеса, 13:25 Київ, 18:05 Львів
набрали «Київ»         Знайдено: 2 | 07:10 Київ, 13:25 Київ
поставили галочку      Знайдено: 1 | 07:10 Київ
```

Змінні `shown` і `shown.length` не лежать у стані, бо обчислюються при кожному рендері. Завдяки цьому лічильник не
може розійтися зі списком. Про зайвий стан докладно говорить наступна лекція, «Структура стану».

Отже, дві глави відповідають на різні запитання. `Reacting to Input with State` питає, у яких станах буває один
компонент і як між ними переходити. `Thinking in React` питає, які дані на екрані справді є станом і в якому
компоненті вони мають лежати.

## Коли стан змінює форму розмітки

Гілки для різних станів можуть повертати різну розмітку, але це має наслідок. Лекція «Списки й ключі» показала, що
текст у некерованому полі лежить у вузлі документа. Подивімося, що станеться з таким полем, якщо стан міняє тег
навколо нього:

```tsx
function Same({ busy }: { busy: boolean }) {
  return <div><input aria-label="Нотатка" /><button disabled={busy}>Так</button></div>
}
function Different({ busy }: { busy: boolean }) {
  if (busy) return <section><input aria-label="Нотатка" /><button disabled>Так</button></section>
  return <div><input aria-label="Нотатка" /><button>Так</button></div>
}
```

Тест набирає «двері» і змінює `busy` на `true`:

```tsx
for (const [name, Note] of [['одне дерево', Same], ['два дерева', Different]] as const) {
  const user = userEvent.setup()
  const { rerender, unmount } = render(<Note busy={false} />)
  await user.type(screen.getByLabelText('Нотатка'), 'двері')
  // Виклик rerender малює той самий компонент із новим пропсом, наче батько змінив свій стан.
  rerender(<Note busy />)
  console.log(`${name}: ${JSON.stringify(screen.getByLabelText<HTMLInputElement>('Нотатка').value)}`)
  unmount()
}
```

```text
одне дерево: "двері"
два дерева: ""
```

У другому компоненті React бачить замість `div` інший тег і створює всю розмітку заново, тому текст зникає. Правило
документація формулює у вправі `Add and remove a CSS class`: одне спільне дерево з обчисленими значеннями зазвичай
краще за два окремі. Кероване поле такої проблеми не має, бо його текст лежить у стані. Докладно поведінку дерева
пояснює тема «Спільний стан і скидання стану».

Гілка для `paid` усе ж повертає зовсім інший вигляд, і це правильно: там зникає вся форма, зберігати нічого.

## Як перевіряти стани в прикладах

Форма переходить через стан, який триває недовго, і цей стан теж треба побачити. Для цього приклади використовують три
засоби.

**Проміс, яким керує тест.** Функцію `deferred` наведено в заготовці вашого файла з прикладами. Вона повертає проміс
разом із функцією, яка його виконує. Поки тест не викликав цю функцію, форма перебуває в стані очікування, і можна
спокійно перевірити екран. Для простих випадків вистачає `vi.fn().mockResolvedValue(true)` з Vitest: це
функція-шпигун, що одразу повертає виконаний проміс.

**Запити `getBy` і `findBy`.** Testing Library має кілька видів запитів. `getBy...` шукає зараз і кидає помилку, якщо
не знайшов. `findBy...` повертає проміс і шукає повторно, поки елемент не з'явиться або не мине одна секунда. Після
асинхронної дії потрібен другий:

```tsx
const d = deferred<Answer>()
const user = userEvent.setup()
render(<Live charge={() => d.promise} />)
await user.click(screen.getByRole('button', { name: 'Оплатити' }))
await user.click(screen.getByRole('button', { name: 'Підтвердити' }))
d.resolve({ ok: true, receipt: 'A-17' })
try { screen.getByText('Оплачено, чек A-17'); console.log('getByText одразу: знайшов') } catch (e) { console.log('getByText одразу:', (e as Error).name) }
const found = await screen.findByText('Оплачено, чек A-17')
console.log('findByText:', found.textContent)
```

```text
getByText одразу: TestingLibraryElementError
findByText: Оплачено, чек A-17
```

Проміс уже виконано, але код після `await` у формі ще не встиг виконатися, тому `getByText` нічого не знайшов.

**Рядки `@ts-expect-error`.** Vitest лише вирізає типи й запускає код, тому такі приклади перевіряє лише `tsc`.

## Хто яку помилку ловить

| Помилка | `tsc` | Приклади Vitest | Очима на службовому екрані |
|---------|-------|-----------------|----------------------------|
| об'єкт виду `paying` із текстом відмови | так | ні | ні |
| забута гілка в `switch` із `never` | так | часто | часто |
| читання поля чужого виду | так | інколи | інколи |
| перехід веде не туди | ні | так | ні |
| знімок замість оновлювача | ні | так, якщо є приклад із відповіддю | ні |
| некрасивий або незрозумілий вигляд | ні | ні | так |
| запізніла відповідь від минулої спроби | ні | лише якщо ви написали такий приклад | ні |

Жоден інструмент не закриває всього. Типи прибирають неможливі стани, приклади перевіряють переходи, а службовий екран
показує вигляд.

## Типові хибні уявлення

**«`await` сам завершує стан очікування».** `await` лише чекає на проміс. Стан очікування закінчується тоді, коли код
запише інший стан. Код із початку лекції показує «Банк думає…», доки команда не сховає цей напис, а компонент показує
його, доки стан не зміниться.

**«Якщо на екрані видно зайве, React ще не домалював».** React показує рівно те, що випливає з поточного стану. Рендер
відбувається у відповідь на зміну стану, тому чекати немає чого. Причину шукайте у значеннях стану.

**«Один `status` усе вирішує, тому прапорці заборонені».** Прапорці є проблемою лише тоді, коли описують стани, що
виключають один одного. Незалежні налаштування, як-от звук і повний екран, цілком нормально зберігати окремо.

**«Досить замінити прапорці рядком».** Рядок прибирає парадокси прапорців, але дані, потрібні лише в деяких станах,
лишаються окремими полями, і вони можуть суперечити рядку. Розрізнюване об'єднання кладе дані всередину відповідного
виду.

**«Тип гарантує, що об'єкт не містить нічого зайвого».** Зайве поле компілятор ловить лише в об'єкті, записаному прямо
в присвоєнні. Тип гарантує наявність потрібних полів і забороняє читати чужі.

**«Заборонена подія має кидати помилку».** Подія, що приходить не вчасно, є нормальною частиною життя форми: людина
клацнула двічі, а відповідь мережі прийшла пізно. Функція переходів спокійно повертає той самий стан, і цього досить.

**«Службовий екран потрібен лише дизайнерам».** Він перевіряє і вашу роботу: якщо вид не можна показати, передавши
один пропс, значить форма тримає частину стану в собі, і вона не є функцією від цього пропса.

## Як це проявиться далі в React

- **Наступний день, «Структура стану».** Сьогодні ви прибрали неможливі поєднання, а завтра приберете значення, які
  можна обчислити, і копії.
- **Тема «Спільний стан і скидання стану».** Там буде пояснено, чому стан зберігається чи зникає, коли змінюється
  дерево компонентів.
- **Тема «Редюсер».** Функція переходів отримає назву й окремий хук `useReducer`, і описані сьогодні види події
  стануть діями редюсера.
- **Теми про ефекти.** Там дані завантажуватимуться тоді, коли компонент з'являється на екрані, а не після клацання, і
  виникне та сама запізніла відповідь, яку ви сьогодні бачили на функції переходів.
- **Фаза 3, «Серверний стан: TanStack Query».** Бібліотека віддає результат запиту теж як стан із переліку, тому
  підхід той самий, а писати переходи вам уже не доведеться.
- **Фаза 3, «Форми в React 19».** Хук `useActionState` тримає результат дії й ознаку очікування, а опис станів форми
  лишається вашою роботою.

## Перевірте себе

**1. Чому в коді на командах DOM після згоди банку екран показує «Банк відмовив + Оплачено»?**

<details><summary>Відповідь</summary>

Вигляд екрана там є сумою всіх виконаних команд. Під час відмови текст показали, а на початку другої спроби й у гілці
згоди ніхто не наказав його сховати. Правильність залежить від того, чи кожна гілка згадала кожен елемент.

</details>

**2. Скільки поєднань дають шість прапорців і скільки з них мають сенс, якщо стани виключають один одного? Чому ця
різниця важлива, навіть поки в коді немає помилок?**

<details><summary>Відповідь</summary>

Шість незалежних булевих змінних дають 64 поєднання, а сенс мають лише шість. Решта 58 дозволені типом, тому код нічим
не захищений: у будь-яке з них можна потрапити одним забутим викликом `set`. Перелік із шести значень має рівно шість
варіантів.

</details>

**3. Коли два булеві прапорці в стані цілком правильні?**

<details><summary>Відповідь</summary>

Коли вони справді незалежні й для кожного з чотирьох поєднань є правильний вигляд екрана. Приклад: `isMuted` і
`isFullscreen` у плеєрі.

</details>

**4. Навіщо функції переходів повертати той самий об'єкт, а не копію, коли подія не на часі?**

<details><summary>Відповідь</summary>

React порівнює старий і новий стан через `Object.is`. Те саме посилання означає, що нічого не змінилося, і оновлення
буде пропущено. Копія з тим самим вмістом дала б зайвий рендер.

</details>

**5. Що станеться, якщо після `await` написати `setPayment(nextPayment(payment, event))`, і чому?**

<details><summary>Відповідь</summary>

Змінна `payment` є знімком рендеру, у якому створено обробник, там стан ще `confirming`. Функція переходів вважає
подію `approved` не на часі й повертає цей знімок. Виклик `set` записує `confirming`, і форма повертається до
підтвердження, хоча банк уже погодив оплату. Оновлювач отримує поточний стан `paying`, і перехід спрацьовує.

</details>

**6. Де функція переходів не допоможе, навіть якщо вона написана правильно?**

<details><summary>Відповідь</summary>

Коли запізніла відповідь на минулу спробу приходить під час нової спроби. Стан знову `paying`, тому подія виглядає
правильною. Функція не знає, до якої спроби належить відповідь, якщо спроби ніяк не позначено.

</details>

**7. Застосуйте три запитання з `Thinking in React`: кошик показує товари, отримані пропсом, поле пошуку, загальну
суму. Що тут стан?**

<details><summary>Відповідь</summary>

Лише текст у полі пошуку. Товари приходять пропсом, а загальну суму можна обчислити. Якщо кошик дозволяє міняти
кількість, тоді стан є й там, але сума все одно обчислюється.

</details>

## Словничок лекції

| Термін | Що це |
|--------|-------|
| імперативний код | код, що перелічує команди одну за одною, наприклад дії над елементами DOM |
| декларативний код | код, що описує потрібний результат, а дії виконує хтось інший |
| стан екрана | один із варіантів того, що може побачити людина |
| скінченний автомат | модель, де система завжди в одному стані зі скінченного переліку й переходить між ними за подіями |
| службовий екран | сторінка для розробника, яка показує всі стани компонента поруч |
| парадокс стану | поєднання значень стану, для якого немає правильного вигляду екрана |
| розрізнюване об'єднання | тип із кількох варіантів зі спільним полем, яке в кожному варіанті має своє значення |
| розрізнювач | спільне поле такого типу, тут `kind` |
| звуження типу | коли після перевірки компілятор вважає можливою лише частину варіантів |
| перевірка повноти | прийом із `never`, який перетворює забутий варіант на помилку компілятора |
| перевірка зайвих властивостей | перевірка компілятора, яка стосується лише об'єкта, записаного прямо в присвоєнні |
| функція переходів | чиста функція, яка зі стану й події рахує наступний стан |
| подія не на часі | подія, для якої в поточному стані немає переходу |
| однобічний потік даних | дані йдуть від батька до дітей лише пропсами |
| зворотний потік | дитина викликає функцію батька, щоб той змінив свій стан |
