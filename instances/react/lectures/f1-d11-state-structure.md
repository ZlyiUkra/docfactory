# Лекція. Фаза 1, день 11. Структура стану

Попередня лекція прибрала зі стану неможливі поєднання. Ця лекція прибирає інше: значення, які можна обчислити, копії
того самого об'єкта й зайву вкладеність. Такі значення не викликають помилок, а лише показують на екрані застарілі
дані, і тому їх важко знайти. Читання займе близько 50 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під
прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із набором правил
`react-hooks`, який використовує ваш проєкт. У справжньому браузері приклади не запускалися.

**Після лекції ви зможете пояснити:**

- чому екран показує застарілі дані, хоча компонент викликано знову;
- за якими правилами вирішують, що зберігати в стані, а що обчислювати;
- чому повторне обчислення зазвичай дешевше за синхронізацію двох змінних;
- чому пропс не можна покласти в `useState`, щоб стежити за ним, і коли `useState(initialValue)` все ж правильний;
- чому обраний елемент зберігають як `id`, і які пастки є в цього запису;
- чому видалення листка в дереві потребує копій усього шляху, а в таблиці вистачає двох копій;
- чому кількість `useState` є лише ознакою, а не метою.

## Телефонна книга, яка розходиться сама з собою

Ви пишете телефонну книгу. У ній є список контактів, лічильник над списком і панель обраного контакта. Ви додаєте стан
для кожної речі, яку показує екран:

```tsx
type Contact = { id: number; name: string }
const START: Contact[] = [{ id: 1, name: 'Ірина' }, { id: 2, name: 'Богдан' }, { id: 3, name: 'Марта' }]

function Phonebook() {
  const [contacts, setContacts] = useState(START)
  const [count, setCount] = useState(START.length)
  const [selected, setSelected] = useState<Contact | null>(null)

  function rename(id: number, name: string) {
    setContacts(contacts.map((c) => (c.id === id ? { ...c, name } : c)))
  }
  function remove(id: number) {
    setContacts(contacts.filter((c) => c.id !== id))
  }
  function add() {
    setContacts([...contacts, { id: 4, name: 'Назар' }])
    setCount(count + 1)
  }
  return (
    <>
      <p>Контактів: {count}</p>
      <ul>
        {contacts.map((c) => (
          <li key={c.id}>
            <input aria-label={`Ім'я ${c.id}`} value={c.name} onChange={(e) => rename(c.id, e.target.value)} />
            <button onClick={() => setSelected(c)}>Обрати {c.id}</button>
            <button onClick={() => remove(c.id)}>Видалити {c.id}</button>
          </li>
        ))}
      </ul>
      <button onClick={add}>Додати</button>
      <p>{selected === null ? 'Нікого не обрано' : `Обрано: ${selected.name}`}</p>
    </>
  )
}
```

Вимоги лекції «Об'єкти й масиви в стані» тут виконано: жодної мутації, усі масиви нові. Тест обирає Ірину, дописує до
її імені дві літери й видаляє двох людей. Після кожної дії тест друкує імена в полях і обидва абзаци:

```text
обрали Ірину           Ірина, Богдан, Марта           | Контактів: 3 | Обрано: Ірина
дописали « К»          Ірина К, Богдан, Марта         | Контактів: 3 | Обрано: Ірина
видалили Богдана       Ірина К, Марта                 | Контактів: 3 | Обрано: Ірина
видалили Ірину         Марта                          | Контактів: 3 | Обрано: Ірина
```

В останньому рядку в книзі лишилася одна людина. Екран каже, що контактів три, а обрано людину, якої немає. Помилки в
консолі немає, типи правильні, і компонент викликався після кожної дії.

Причина одна в обох випадках. Той самий факт записано двічі: кількість людей є і в `contacts`, і в `count`, а ім'я
Ірини є і в `contacts`, і в `selected`. React нічого не знає про зв'язок між цими змінними. Для нього це окремі
значення, тому ви мусите оновлювати їх разом у кожному обробнику. Функцію `add` написано правильно, але функцію
`remove` написано без `setCount`, а `rename` без `setSelected`.

Можна дописати ці виклики, але це лікує лише сьогоднішню помилку. Кожен новий обробник знову мусить пам'ятати про всі
копії. Глава `Choosing the State Structure` пропонує інше рішення: взагалі не тримати другої копії.

## П'ять правил і одна мета

Глава формулює мету так: стан має бути легко оновлювати, не роблячи помилок. Для цього вона дає п'ять принципів.

| Правило | Запитання до коду | Що ламається без нього |
|---------|-------------------|------------------------|
| об'єднувати пов'язане | чи ці змінні завжди змінюються разом? | одну оновили, другу забули |
| уникати суперечностей | чи можуть ці змінні сказати різне? | екран показує стан, якого не буває |
| уникати зайвого | чи можна це обчислити під час рендеру? | обчислене значення застаріває |
| уникати дублювання | чи не лежить той самий об'єкт у двох місцях? | копії розходяться |
| уникати глибокої вкладеності | чи треба копіювати багато рівнів заради однієї зміни? | код оновлення довгий і легко помилитися |

Глава порівнює ці правила з нормалізацією баз даних. Так називають спосіб проєктувати таблиці бази, за якого кожен
факт лежить в одному місці, а все інше посилається на нього за ключем. Ця аналогія лишається корисною до кінця лекції:
стан є маленькою базою даних, а тіло компонента є запитом, який будує з неї екран.

Пройдімо ці правила по черзі.

## Об'єднувати те, що змінюється разом

Товар коштує 4100 гривень, а кнопка перераховує ціну в євро. Поміркуйте про два записи. Суму й валюту можна тримати
окремо або разом:

```tsx
function Two() {
  const [amount, setAmount] = useState(4100)
  const [currency, setCurrency] = useState('грн')
  function toEuro() {
    setCurrency('євро')
  }
  return <button onClick={toEuro}>Два стани: {amount} {currency}</button>
}
function One() {
  const [price, setPrice] = useState({ amount: 4100, currency: 'грн' })
  function toEuro() {
    setPrice({ amount: price.amount / 41, currency: 'євро' })
  }
  return <button onClick={toEuro}>Один стан: {price.amount} {price.currency}</button>
}
```

Тест клацає обидві кнопки:

```text
Два стани: 4100 євро | Один стан: 100 євро
```

В обробнику `Two` забуто `setAmount`, і вийшло 4100 євро. У `One` таку помилку зробити важче, бо `setPrice` вимагає
весь об'єкт. Сума й валюта мають сенс лише разом, адже число 4100 без валюти нічого не означає.

Є й зворотний бік. Функція `set` замінює значення цілком, про що вже казала лекція «Події й стан». Якщо передати лише
частину об'єкта, друге поле зникне. TypeScript тут допомагає:

```tsx
const [price, setPrice] = useState({ amount: 4100, currency: 'грн' })
return <button onClick={() => setPrice({ amount: 100 })}>{price.amount}</button>
```

```text
ts/partial.tsx(4,42): error TS2345: Argument of type '{ amount: number; }' is not assignable to parameter of type 'SetStateAction<{ amount: number; currency: string; }>'.
  Property 'currency' is missing in type '{ amount: number; }' but required in type '{ amount: number; currency: string; }'.
```

Щоб змінити одне поле, копіюють решту: `setPrice({ ...price, amount: 100 })`.

**Коли не об'єднувати.** Це правило стосується змінних, які змінюються разом. Ім'я й прізвище у формі людина набирає
окремо, тому лекція «Події й стан» радила для них окремі `useState`. Об'єднання тут дало б лише більше коду в кожному
обробнику. Є ще один випадок, де об'єкт зручний: коли кількість полів заздалегідь невідома, наприклад людина сама
додає поля у форму.

## Уникати суперечностей

Це правило вам знайоме з лекції «Стан як набір станів екрана». Глава показує його на двох прапорцях `isSending` і
`isSent`, які можуть обидва дорівнювати `true`, і замінює їх одним `status`. Глава додає корисне зауваження: якщо вам
зручно мати прапорець для читабельності, напишіть звичайну константу:

```tsx
const isSending = status === 'sending'
```

Така константа не є станом, тому розійтися зі `status` вона не може. Це вже підводить до наступного правила.

## Не зберігати те, що можна обчислити

Кошик книгарні показує суму й кількість книжок. Сума залежить від ціни й кількості кожної книжки. Порівняємо три
варіанти. У першому сума лежить в окремому стані, у другому її обчислюють, а третій об'єднує список і суму в один
об'єкт, бо хтось вирішив, що тоді `useState` буде менше:

```tsx
function Stored() {
  const [books, setBooks] = useState(BOOKS)
  const [total, setTotal] = useState(1200)
  function inc(id: number) {
    const next = books.map((b) => (b.id === id ? { ...b, qty: b.qty + 1 } : b))
    setBooks(next)
    setTotal(next.reduce((sum, b) => sum + b.price * b.qty, 0))
  }
  function remove(id: number) {
    setBooks(books.filter((b) => b.id !== id))
  }
  return <Cart name="у стані" books={books} total={total} inc={inc} remove={remove} />
}
function Computed() {
  const [books, setBooks] = useState(BOOKS)
  const total = books.reduce((sum, b) => sum + b.price * b.qty, 0)
  function inc(id: number) {
    setBooks(books.map((b) => (b.id === id ? { ...b, qty: b.qty + 1 } : b)))
  }
  function remove(id: number) {
    setBooks(books.filter((b) => b.id !== id))
  }
  return <Cart name="обчислена" books={books} total={total} inc={inc} remove={remove} />
}
function OneObject() {
  const [cart, setCart] = useState({ books: BOOKS, total: 1200 })
  function inc(id: number) {
    const books = cart.books.map((b) => (b.id === id ? { ...b, qty: b.qty + 1 } : b))
    setCart({ books, total: books.reduce((sum, b) => sum + b.price * b.qty, 0) })
  }
  function remove(id: number) {
    setCart({ ...cart, books: cart.books.filter((b) => b.id !== id) })
  }
  return <Cart name="один об'єкт" books={cart.books} total={cart.total} inc={inc} remove={remove} />
}
```

Компонент `Cart` лише показує суму й дві кнопки. Спочатку в кошику книжка за 300 гривень в одному примірнику й книжка
за 450 гривень у двох примірниках. Тест додає ще одну першу книжку, а потім прибирає другу:

```text
у стані: сума 1500, книжок 2
у стані: сума 1500, книжок 1
обчислена: сума 1500, книжок 2
обчислена: сума 600, книжок 1
один об'єкт: сума 1500, книжок 2
один об'єкт: сума 1500, книжок 1
```

Правильна сума в кінці дорівнює 600, бо в кошику лишилося дві книжки за 300 гривень. Її показує лише другий варіант.

Подивимося, що саме робить другий варіант. Рядок із `reduce` стоїть у тілі компонента. Кожен рендер спершу читає
`books` зі стану, а потім рахує суму з цього масиву. Обробникам про суму знати нічого не треба. Сума не може
застаріти, бо вона існує лише протягом одного рендеру.

Третій варіант дуже показовий. У ньому один `useState`, тобто на вигляд стану менше, але помилка та сама. Правило
стосується не кількості викликів `useState`, а кількості незалежних фактів у стані. Сума лишається другим записом того
самого факту, де б вона не лежала.

### Перевірка трьома запитаннями

Лекція «Стан як набір станів екрана» навела три запитання з глави `Thinking in React`. Застосуйте їх до телефонної
книги:

| Дані на екрані | Незмінні? | Пропс? | Можна обчислити? | Рішення |
|----------------|-----------|--------|------------------|---------|
| список контактів | ні | ні | ні | стан |
| кількість контактів | ні | ні | так, довжина списку | обчислити |
| який контакт обрано | ні | ні | ні | стан, але лише `id` |
| дані обраного контакта | ні | ні | так, знайти в списку за `id` | обчислити |

Виходить два стани замість трьох. Як саме лишити від обраного контакта лише `id`, показує розділ про дублювання нижче.

### Чи не дорого обчислювати щоразу

Це перше заперечення, яке виникає: кожен рендер заново обходить список. Виміряємо час `reduce` на масиві різного
розміру. Тест запускає обчислення двадцять разів і друкує медіану, тобто значення посередині впорядкованого ряду:

```ts
const books = Array.from({ length: size }, (_, i) => ({ id: i, price: i % 500, qty: 1 + (i % 3) }))
books.reduce((sum, b) => sum + b.price * b.qty, 0)
```

```text
1000 елементів: 0.009 мс
10000 елементів: 0.073 мс
100000 елементів: 0.806 мс
```

Числа стосуються однієї машини й Node, а не браузера, але порядок величин зрозумілий. Сторінка `You Might Not Need an
Effect` радить виміряти час і думати про кешування, якщо обчислення займає приблизно одну мілісекунду або більше. Для
списку контактів цього порога не досягти. Кешування робить хук `useMemo`, але спершу його слід виміряти, і для цього є
тема фази 2 про мемоізацію. Сьогодні правило просте: спершу обчислюйте в тілі компонента, а кешуйте лише тоді, коли
вимір покаже проблему.

### Чому не ефект

Є спокуса «синхронізувати» значення ефектом. Лекція «Чистота й дерево» коротко пояснила, що **ефект** є функцією, яку
React запускає вже після того, як оновив екран. Докладно ефекти вивчають теми «Синхронізація ефектами» й «Коли ефект
не потрібен», але ця пастка трапляється раніше, тому подивимося на неї зараз. Компонент показує назву міста великими
літерами двома способами:

```tsx
function WithEffect() {
  const [city, setCity] = useState('')
  const [label, setLabel] = useState('')
  useEffect(() => {
    setLabel(city.toUpperCase())
  }, [city])
  log.push(`з ефектом: city=${city} label=${label}`)
  return <input aria-label="Місто" value={city} onChange={(e) => setCity(e.target.value)} />
}
function Direct() {
  const [city, setCity] = useState('')
  const label = city.toUpperCase()
  log.push(`без ефекту: city=${city} label=${label}`)
  return <input aria-label="Місто" value={city} onChange={(e) => setCity(e.target.value)} />
}
```

Тест набирає одну літеру:

```text
з ефектом: city=Р label=
з ефектом: city=Р label=Р
без ефекту: city=Р label=Р
```

З ефектом компонент викликано двічі. Перший виклик бачить нове місто й стару назву, і React записує цей результат на
екран. Лише потім спрацьовує ефект, викликає `set`, і настає другий рендер. Без ефекту все робить один виклик, а дані
в ньому узгоджені. Сторінка `You Might Not Need an Effect` каже те саме: обчислення під час рендеру швидше, простіше й
не дає змінним розійтися.

Цю помилку помічає лінт вашого проєкту. Правило `react-hooks/set-state-in-effect` з пакета `eslint-plugin-react-hooks`
друкує на такому коді:

```text
6:5  error  Error: Calling setState synchronously within an effect can trigger cascading renders
```

## Не класти пропс у стан

Компонент показує одиницю виміру, отриману пропсом. Хтось вирішує покласти її в стан «про всяк випадок»:

```tsx
function Mirror({ unit }: { unit: string }) {
  const [shown] = useState(unit)
  return <p>Дзеркало: {shown}</p>
}
function Direct({ unit }: { unit: string }) {
  return <p>Напряму: {unit}</p>
}
```

Тест показує обидва компоненти з `°C`, а потім передає `°F`:

```text
Дзеркало: °C | Напряму: °F
```

Аргумент `useState` є лише початковим значенням. Довідник каже прямо: цей аргумент ігнорується після першого рендеру.
Компонент викликано знову з новим пропсом, і вираз `useState(unit)` виконано знову, але React дивиться лише на те, що
вже зберігає. Лекція «Події й стан» пояснила, що стан належить екземпляру й живе між рендерами. Тому новий пропс не
змінює збереженого значення.

Якщо вам потрібна просто коротша назва, напишіть звичайну константу: `const shown = unit`. Вона обчислюється щоразу.

**Коли `useState` з пропса правильний.** Буває, що вам якраз і потрібно лише початкове значення. Форма редагування
бере теперішнє ім'я як початок чернетки, а людина потім змінює чернетку незалежно від пропса. Глава просить показати
цей намір назвою: пропс називають `initialName` або `defaultName`, щоб читач коду знав, що подальші зміни цього пропса
ігноруються.

```tsx
function NameDraft({ initialName, onSave }: { initialName: string; onSave: (name: string) => void }) {
  const [draft, setDraft] = useState(initialName)
  return (
    <>
      <input aria-label="Чернетка" value={draft} onChange={(e) => setDraft(e.target.value)} />
      <button onClick={() => onSave(draft)}>Зберегти</button>
    </>
  )
}
```

Але виникає нове питання: що робити, коли людина перейшла до іншого контакта? Перевіримо:

```tsx
const { rerender } = render(<NameDraft initialName="Ірина" onSave={() => {}} />)
await user.type(screen.getByLabelText('Чернетка'), ' К')
console.log('після набору:', value())
rerender(<NameDraft initialName="Богдан" onSave={() => {}} />)
console.log('інший контакт без key:', value())
rerender(<NameDraft key={2} initialName="Богдан" onSave={() => {}} />)
console.log('інший контакт з key:', value())
```

```text
після набору: Ірина К
інший контакт без key: Ірина К
інший контакт з key: Богдан
```

Без `key` у чернетці лишилося ім'я попереднього контакта. Зі зміненим `key` React вважає компонент новим екземпляром і
знову читає початкове значення. Чому так працює, докладно пояснює наступна тема, «Спільний стан і скидання стану».
Сьогодні досить знати, що ефект для цього не потрібен.

**Ще одна копія: `defaultValue`.** Поле вводу теж уміє зберігати копію значення. Лекція «Списки й ключі» пояснила, що
некероване поле тримає текст у вузлі документа. Атрибут `defaultValue` задає лише початковий текст такого поля:

```tsx
function A({ name }: { name: string }) {
  return <input aria-label="defaultValue" defaultValue={name} />
}
function B({ name }: { name: string }) {
  return <input aria-label="value" value={name} onChange={() => {}} />
}
```

Тест показує обидва поля з ім'ям Ірина, а потім передає Богдана:

```text
defaultValue Ірина
value Богдан
```

Це та сама пастка, що й зі `useState`, лише копія лежить у вузлі документа. Керованому полю копія не потрібна.

## Не дублювати: `id` замість копії

Тепер повернемося до телефонної книги. Приберемо обидві зайві змінні: кількість обчислимо, а від обраного контакта
лишимо лише `id`. Зверніть увагу, скільки коду зникло:

```tsx
function Phonebook() {
  const [contacts, setContacts] = useState(START)
  const [selectedId, setSelectedId] = useState<number | null>(null)
  const selected = contacts.find((c) => c.id === selectedId) ?? null
  function rename(id: number, name: string) {
    setContacts(contacts.map((c) => (c.id === id ? { ...c, name } : c)))
  }
  function remove(id: number) {
    setContacts(contacts.filter((c) => c.id !== id))
  }
  return (
    <>
      <p>Контактів: {contacts.length}</p>
      {/* список той самий, лише кнопка викликає setSelectedId(c.id) */}
      <p>{selected === null ? 'Нікого не обрано' : `Обрано: ${selected.name}`}</p>
    </>
  )
}
```

Той самий тест:

```text
обрали Ірину           Ірина, Богдан, Марта           | Контактів: 3 | Обрано: Ірина
дописали « К»          Ірина К, Богдан, Марта         | Контактів: 3 | Обрано: Ірина К
видалили Богдана       Ірина К, Марта                 | Контактів: 2 | Обрано: Ірина К
видалили Ірину         Марта                          | Контактів: 1 | Нікого не обрано
```

Усі рядки правильні, а в обробниках не додалося жодного рядка про панель чи лічильник. Функція `rename` лише змінює
список. Наступний рендер знаходить у новому списку новий об'єкт, і панель показує нове ім'я.

Чому це працює? Значення `id` є не копією контакта, а лише його назвою, тобто посиланням за номером. Воно не може
застаріти щодо імені, бо імені в ньому немає.

### Покроковий приклад із посиланнями

Подивимося, які об'єкти існують на кожному кроці. Тест дає кожному новому об'єкту номер і друкує стан при кожному
виклику компонента:

```text
список: Ірина(об0), Богдан(об1) | selectedId: null | обраний: null
список: Ірина(об0), Богдан(об1) | selectedId: 1 | обраний: Ірина(об0)
список: Іра(об2), Богдан(об1) | selectedId: 1 | обраний: Іра(об2)
список: Богдан(об1) | selectedId: 1 | обраний: null
```

| Дія | Що робить обробник | Що в стані після | Що знаходить `find` |
|-----|--------------------|------------------|---------------------|
| перший показ | нічого | список із двох об'єктів, `selectedId` дорівнює `null` | нічого, бо немає такого `id` |
| «Обрати» | `setSelectedId(1)` | той самий список, `selectedId` дорівнює 1 | `об0` |
| «Перейменувати» | `setContacts(...)` | новий список: новий `об2` замість `об0`, а `об1` той самий | `об2`, тобто вже нове ім'я |
| «Видалити» | `setContacts(...)` | список без `об2`, `selectedId` досі 1 | нічого, тому `null` |

Значення `selectedId` не змінювалося протягом трьох останніх дій. Змінювався лише список, а обраний контакт щоразу
обчислювався з нього заново. Об'єкт `об0` зі старим іменем ніхто вже не тримає. У варіанті з копією його тримав би
`selected`, і панель показувала б старе ім'я.

### П'ять тонкощів цього запису

Тест перевіряє кілька випадків на контактах, де `id` починається з нуля:

```ts
const contacts: Contact[] = [{ id: 0, name: 'Ірина' }, { id: 1, name: 'Богдан' }, { id: 2, name: 'Марта' }]
console.log('find без збігу:', contacts.find((c) => c.id === 9))
const selectedId = 0
const bad = selectedId ? contacts.find((c) => c.id === selectedId) : null
const good = selectedId !== null ? contacts.find((c) => c.id === selectedId) : null
console.log('перевірка істинності при id 0:', bad, '| перевірка на null:', good?.name)
```

```text
find без збігу: undefined
перевірка істинності при id 0: null | перевірка на null: Ірина
```

**Метод `find` повертає `undefined`, коли збігу немає.** Це написано в описі на MDN. Запис `?? null` перетворює його
на `null`. Оператор `??` повертає праве значення лише тоді, коли ліве дорівнює `null` або `undefined`. Така заміна
потрібна, якщо пропс панелі оголошено як `Contact | null`: TypeScript не дасть передати туди `undefined`.

**Нуль хибний.** Умова `if (selectedId)` вважає `id` зі значенням 0 відсутнім, і контакт із цим `id` неможливо обрати.
Лекція «Пропси й умовний рендер» вже показувала, чому нуль в умові дає несподіваний результат. Порівнюйте явно:
`selectedId !== null`.

**Позиція не є назвою.** Підсумок глави каже, що для вибору можна зберігати `id` або індекс, тобто позицію в масиві.
Індекс працює лише тоді, коли позиції не змінюються. Подивімося, що стається після видалення:

```ts
const index = 1
const withoutFirst = contacts.filter((c) => c.id !== 0)
console.log('за позицією до видалення:', contacts[index].name, '| після:', withoutFirst[index].name)
const byId = 1
console.log('за id до видалення:', contacts.find((c) => c.id === byId)?.name, '| після:', withoutFirst.find((c) => c.id === byId)?.name)
```

```text
за позицією до видалення: Богдан | після: Марта
за id до видалення: Богдан | після: Богдан
```

Обрано було Богдана, а після видалення першого контакта обрана вже Марта. Лекція «Списки й ключі» пояснювала ту саму
причину, коли йшлося про ключі.

**Порівнюйте `id`, а не об'єкти.** Так само ламається підсвічування, якщо порівнювати об'єкт із запам'ятованим
об'єктом. Перейменування створює новий об'єкт, тому рівність зникає:

```ts
const obj = contacts[1]
const renamed = contacts.map((c) => (c.id === 1 ? { ...c, name: 'Богдан К' } : c))
console.log('підсвітка за об\'єктом:', renamed.map((c) => c === obj), '| за id:', renamed.map((c) => c.id === 1))
```

```text
підсвітка за об'єктом: [ false, false, false ] | за id: [ false, true, false ]
```

Перший масив каже, що жоден рядок більше не підсвічено. Саме цей випадок розбирає одна з вправ глави, `Fix the
disappearing selection`.

**Застарілий `id` безпечний, поки його не використано вдруге.** Після видалення контакта `selectedId` лишається 1, і
це нормально: `find` нічого не знаходить, панель правдива. Але якщо згодом з'явиться новий контакт із тим самим `id`,
обраність раптом з'явиться на ньому:

```ts
let list = contacts
const stale = 2
list = list.filter((c) => c.id !== 2)
console.log('після видалення:', list.find((c) => c.id === stale)?.name)
list = [...list, { id: 2, name: 'Назар' }]
console.log('новий контакт із тим самим id:', list.find((c) => c.id === stale)?.name)
```

```text
після видалення: undefined
новий контакт із тим самим id: Назар
```

Тому розумно при видаленні обраного скидати `selectedId` у `null`. Це невелика правка, але вона закриває випадок, коли
`id` використовують повторно. Сервер зазвичай видає унікальні `id`, але в прототипі з лічильником таке трапляється
легко.

Глава також показує запис для кількох обраних елементів: `selectedIds` як масив або `Set`. Принцип той самий: у стані
лежать лише номери.

## Не вкладати глибоко

Останнє правило стосується дерев. Структура університету має чотири рівні: університет, факультет, кафедра, група. Її
можна записати двома способами:

```ts
type Tree = { title: string; children: Tree[] }
type Unit = { id: number; title: string; childIds: number[] }

const tree: Tree = {
  title: 'Університет',
  children: [{
    title: 'Факультет',
    children: [{
      title: 'Кафедра',
      children: [{ title: 'Група А', children: [] }, { title: 'Група Б', children: [] }],
    }],
  }],
}
const table: Record<number, Unit> = {
  0: { id: 0, title: 'Університет', childIds: [1] },
  1: { id: 1, title: 'Факультет', childIds: [2] },
  2: { id: 2, title: 'Кафедра', childIds: [3, 4] },
  3: { id: 3, title: 'Група А', childIds: [] },
  4: { id: 4, title: 'Група Б', childIds: [] },
}
```

Перший запис називають **деревом**, бо дочірні об'єкти лежать усередині батьківських. Другий запис називають
**плоским** або **нормалізованим**: усі об'єкти лежать в одній таблиці, а зв'язки записано лише номерами. Тип
`Record<number, Unit>` описує об'єкт, у якому за числовим ключем лежить значення типу `Unit`.

Приберемо групу А. Лекція «Об'єкти й масиви в стані» пояснила, що заради зміни на глибині треба скопіювати кожен
об'єкт на шляху до неї:

```ts
const faculty = tree.children[0]
const department = faculty.children[0]
const nextTree: Tree = {
  ...tree,
  children: [{
    ...faculty,
    children: [{
      ...department,
      children: department.children.filter((g) => g.title !== 'Група А'),
    }],
  }],
}

const parent = table[2]
const nextParent = { ...parent, childIds: parent.childIds.filter((id) => id !== 3) }
const nextTable = { ...table, [parent.id]: nextParent }
```

Запис `[parent.id]: nextParent` підставляє значення змінної як назву поля. Такий запис називається обчислюваним ім'ям
поля, і розбір читання до лекції «Об'єкти й масиви в стані» вже показував його. Подивимося, які об'єкти лишилися
спільними зі старими даними:

```text
дерево: [ 'Група Б' ]
спільні зі старим: Група Б true | кафедра false | факультет false | корінь false
таблиця: [ 'Група Б' ]
спільні зі старим: корінь true | факультет true | кафедра false | сама таблиця false
```

У дереві довелося створити новий об'єкт для кожного предка видаленого запису. У таблиці нові лише два об'єкти: кафедра
й сама таблиця. Це різниця не лише в кількості коду. Чим глибше дерево, тим вона більша:

```text
глибина 2: копій у дереві 2, у таблиці 2
глибина 4: копій у дереві 4, у таблиці 2
глибина 8: копій у дереві 8, у таблиці 2
глибина 16: копій у дереві 16, у таблиці 2
```

### Що треба знати про плоску таблицю

**Видалений запис лишається в таблиці.** Код вище забрав номер із `childIds`, але сам запис лишився:

```text
запис Групи А досі в таблиці: Група А | усього записів: 5
```

На екрані його не видно, бо ніхто на нього не посилається, але він займає пам'ять. Якщо прибрати цілу кафедру, у
таблиці лишаться й усі її групи. Вилучити їх можна рекурсивною функцією, яка спускається за `childIds`. Глава показує
це у згорнутому блоці `Improving memory usage` за допомогою бібліотеки Immer, а тут показано той самий обхід без
бібліотеки:

```ts
const removeSubtree = (t: Record<number, Unit>, id: number): Record<number, Unit> => {
  const { [id]: gone, ...rest } = t
  return gone.childIds.reduce(removeSubtree, rest)
}
const parent = table[1]
const cut = { ...table, 1: { ...parent, childIds: parent.childIds.filter((id) => id !== 2) } }
console.log('записів, якщо лише забрати id у батька:', Object.keys(cut).length)
console.log('записів, якщо прибрати й нащадків:', Object.keys(removeSubtree(cut, 2)).length)
console.log('записів у початковій таблиці:', Object.keys(table).length)
```

```text
записів, якщо лише забрати id у батька: 5
записів, якщо прибрати й нащадків: 2
записів у початковій таблиці: 5
```

Запис `const { [id]: gone, ...rest } = t` кладе запис із цим ключем у `gone`, а решту полів копіює в новий об'єкт
`rest`. Функція `reduce` проходить усіх дітей і щоразу забирає їхні гілки. Початкову таблицю не змінено.

**Запис за номером може бути порожнім, а TypeScript про це не скаже.** Цей код компілюється без помилок, хоча запису з
номером 99 немає:

```ts
const table: Record<number, { title: string }> = { 0: { title: 'Корінь' } }
console.log(table[99].title)
```

```text
TypeError: Cannot read properties of undefined (reading 'title')
```

Тип `Record` обіцяє запис за будь-яким номером. Параметр компілятора `noUncheckedIndexedAccess` змушує TypeScript
додавати `undefined` до типу такого читання. Без нього будьте уважні: посилання на номер, якого вже немає, виявиться
лише під час роботи.

**Не все треба розкладати.** Глава прямо каже, що вкладеність дозволена, а плоска таблиця потрібна тоді, коли
оновлення стає складним. Об'єкт користувача з адресою всередині не варто розкладати на таблицю, бо там два рівні й
немає спільного використання. Ще один прийом: якщо стан стосується лише вигляду одного елемента, наприклад чи наведено
на нього вказівник, цей стан можна тримати в дочірньому компоненті.

## Рецепт: опис даних вирішує наперед

Практика дня йде за рецептом книжки How to Design Programs. Найважливіше рішення дня приймається вже на першому кроці
рецепта, тобто в описі даних. Коли ви записали тип `{ contacts: Contact[]; selectedId: number | null }`, вирішено
майже все: окремого поля для обраного контакта немає, тому писати функції для його оновлення теж не потрібно.

Розділ книжки `5.8 Designing with Structures` описує шаблон функції над структурою: у шаблоні перелічено всі поля цієї
структури, навіть якщо частина з них не знадобиться. Ваші `TODO` з переліком вхідних даних відповідають цьому кроку.
Переклад такий:

| Що каже рецепт | Як це виглядає у вас |
|----------------|----------------------|
| дані, які описують одну річ, збирають у структуру | об'єкт з двома полями: список і `id` обраного |
| у шаблоні функції перелічено поля структури | коментар із переліком полів перед тілом функції |
| функція повертає нове значення структури | нова структура, де змінилося лише потрібне поле |
| похідне значення є окремою функцією | функція, що знаходить обраний контакт у списку |

Останній рядок прямо пов'язаний із сьогоднішньою темою. Обчислене значення стає звичайною функцією від стану, яку
легко перевірити прикладами без React.

## Як рецепт рахує `useState`

Завдання дня перевіряє кількість `useState` у кожному компоненті. Рецепт бере код без коментарів і шукає `useState(`
або `useState<`. Це корисна перевірка, але вона лише ознака. Варіант `OneObject` вище показав, що можна зменшити
кількість викликів і не прибрати проблему. Такий тест на варіанті з одним об'єктом не впав би, а сума все одно
застаріла б. Правильне запитання звучить так: чи лежить кожен факт в одному місці?

Навпаки теж буває. Форма з десятьма незалежними полями може мати десять станів, і нічого поганого в цьому немає.

## Хто яку помилку ловить

| Помилка | `tsc` | Приклади Vitest | ESLint `react-hooks` |
|---------|-------|-----------------|----------------------|
| обчислюване значення лежить у стані й застаріло | ні | так, якщо є приклад із такою дією | ні |
| копія об'єкта в стані розійшлася зі списком | ні | так, якщо є приклад із перейменуванням | ні |
| пропс у стані | ні | так, якщо є приклад із `rerender` | ні |
| похідне значення записують ефектом | ні | часто ні, бо екран у кінці правильний | так, `set-state-in-effect` |
| передано лише частину об'єкта стану | так | інколи | ні |
| читання запису за номером, якого немає | лише з `noUncheckedIndexedAccess` | так, якщо є такий приклад | ні |

Лінт не друкує нічого ні на збереженій копії, ні на компоненті з `useState(unit)`, бо не знає, що два значення мають
бути пов'язаними. Тому в цій темі найцінніші приклади, які роблять дію, а потім перевіряють усе, що показує екран.

## Типові хибні уявлення

**«React перемальовує компонент, тому екран завжди свіжий».** Рендер показує стан таким, яким він є. Якщо копія в
стані застаріла, свіжий рендер покаже застарілу копію.

**«Панель покаже нову назву, бо об'єкт той самий».** Правильне оновлення створює новий об'єкт, тому в списку лежить
новий, а в копії старий. Той самий об'єкт був би лише при мутації, яку забороняє лекція «Об'єкти й масиви в стані».

**«Треба дописати `setSelected` у `rename`».** Це працює до наступного обробника, у якому хтось забуде зробити те
саме. Прибрати копію надійніше, ніж синхронізувати її.

**«Менше `useState` завжди краще».** Об'єднання кількох станів в один об'єкт не прибирає зайвий факт. Правило
стосується кількості незалежних фактів.

**«Більше `useState` завжди гірше».** Незалежні поля форми можуть жити в окремих станах.

**«Зберігати результат швидше, ніж рахувати щоразу».** Для звичайних списків обчислення займає соті частки
мілісекунди, а зайвий ефект додає цілий рендер. Кешування варто робити лише після виміру.

**«`useState(props.value)` оновиться, коли зміниться пропс».** Початкове значення читається лише на першому рендері.
Компонент викликається знову, але React не дивиться на цей аргумент.

**«`id` у стані може вказувати на неіснуючий об'єкт, отже, він небезпечний».** Навпаки: `find` не знаходить такого
об'єкта, і панель каже правду. Копія в такому разі показувала б контакт, якого немає. Небезпека виникає лише при
повторному використанні `id`.

**«Плоска таблиця завжди краща за вкладеність».** Вона корисна там, де оновлення глибоких частин стає складним. Для
двох рівнів без спільних об'єктів вона лише додає роботи.

## Як це проявиться далі в React

- **Тема «Спільний стан і скидання стану».** Стан, потрібний кільком компонентам, підіймають до спільного батька, а
  чернетку скидають через `key`. Сьогодні ви вже бачили `key` у цій ролі.
- **Тема «Редюсер».** Плоский стан і функції над ним природно перетворюються на редюсер, який зібрано в одному місці.
- **Тема «Контекст».** Якщо стан передають глибоко, важливо, щоб він залишався мінімальним, бо кожна його зміна
  зачіпає всіх, хто його читає.
- **Тема «Коли ефект не потрібен».** Сьогоднішнє правило про обчислення під час рендеру стане першим прикладом цілої
  теми.
- **Фаза 2, мемоізація.** `useMemo` кешує похідне значення, і ви вирішуватимете це за виміром, а не наперед.
- **Фаза 3, серверний стан.** Дані з сервера лежать у кеші бібліотеки, а компонент тримає лише `id` обраного.
  Копіювання цих даних у `useState` є тією самою пасткою, що й сьогодні.
- **Фаза 3, глобальний стан.** Сховища часто тримають дані в плоских таблицях із `id`, бо причини ті самі.

## Перевірте себе

**1. Чому панель показує старе ім'я, хоча компонент щойно викликано?**

<details><summary>Відповідь</summary>

Панель читає `selected`, тобто окремий стан. Перейменування створило новий об'єкт у списку, а `selected` тримає
старий. Рендер не оновлює стан, він його показує.

</details>

**2. Застосуйте три запитання до лічильника кількості елементів кошика. Чи є він станом?**

<details><summary>Відповідь</summary>

Ні. Він змінюється і не є пропсом, але його можна обчислити як довжину списку. Третя відповідь «так» означає, що це не
стан.

</details>

**3. Кошик тримає один `useState` з об'єктом `{ books, total }`. Що не так?**

<details><summary>Відповідь</summary>

Сума лишається другим записом того самого факту. Обробник, який змінює `books` і забуває про `total`, дає застарілу
суму. Викликів `useState` менше, але незалежних фактів не менше. Суму треба обчислювати.

</details>

**4. Чому `const [shown] = useState(unit)` не стежить за пропсом і як це виправити?**

<details><summary>Відповідь</summary>

Аргумент `useState` React використовує лише на першому рендері, а далі показує збережене значення. Пропс треба читати
напряму, а якщо потрібна інша назва, написати `const shown = unit`.

</details>

**5. Коли `useState(initialName)` правильний і що станеться під час переходу до іншого контакта?**

<details><summary>Відповідь</summary>

Коли ви навмисно робите чернетку, яка після першого показу живе незалежно від пропса. Під час переходу до іншого
контакта чернетка лишається старою, бо компонент той самий. Зміна `key` створює новий екземпляр, і початкове значення
читається знову.

</details>

**6. Чому `selectedId` кращий за позицію в масиві й що ламається при `if (selectedId)`?**

<details><summary>Відповідь</summary>

Позиція змінюється після видалення чи сортування, і обраним стає сусід, а `id` лишається тим самим. Умова `if
(selectedId)` вважає нуль відсутнім значенням, тому контакт із `id` 0 неможливо обрати. Порівнювати треба з `null`.

</details>

**7. Скільки об'єктів створює видалення листка на глибині 8 у дереві й у плоскій таблиці?**

<details><summary>Відповідь</summary>

У дереві 8 копій, по одній на кожного предка. У таблиці 2: новий батько і нова таблиця. Запис самого листка лишається
в таблиці, якщо його не вилучити окремо.

</details>

## Словничок лекції

| Термін | Що це |
|--------|-------|
| зайвий стан | значення в стані, яке можна обчислити з іншого стану чи пропсів |
| похідне значення | значення, обчислене під час рендеру зі стану чи пропсів |
| дублювання стану | один і той самий об'єкт лежить у стані у двох місцях |
| нормалізація | запис даних, за якого кожен факт лежить в одному місці, а інші місця посилаються на нього за ключем |
| плоска таблиця | об'єкт, де всі записи лежать за номером, а зв'язки записано номерами |
| дзеркалення пропса | копіювання пропса в стан, після якого стан не стежить за пропсом |
| початкове значення | аргумент `useState`, який React читає лише на першому рендері |
| ефект | функція, яку React запускає після оновлення екрана |
| обчислюване ім'я поля | запис `[вираз]: значення`, де назва поля береться зі значення виразу |
