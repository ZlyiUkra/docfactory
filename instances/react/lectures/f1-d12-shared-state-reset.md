# Лекція. Фаза 1, день 12. Спільний стан і скидання стану

Досі кожен компонент сам володів своїм станом. Сьогодні ви побачите дві задачі, де цього мало. Перша: два компоненти
мусять завжди показувати те саме, а кожен рахує своє. Друга: форма мусить очиститися, коли людина перейшла до іншого
запису, а вона зберігає старий текст. Обидві задачі зводяться до одного запитання: де живе стан і коли він зникає.
Читання займе близько 50 хвилин.

Приклади запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під прикладами
справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із тим самим набором правил
`react-hooks`, що й у проєкті `spa`. Один дослід про кадри на екрані запущено в справжньому браузері Chrome, бо jsdom
нічого не малює, і в цьому місці про це сказано окремо.

**Після лекції ви зможете пояснити:**

- чому два компоненти з окремим станом неминуче розходяться і що означає підняти стан;
- до якого саме батька піднімати стан і що стається, якщо підняти зависоко;
- що таке керований і некерований компонент і чим небезпечна копія пропса в стані;
- що React вважає місцем компонента і чому `false` у JSX теж займає місце;
- чому стан зберігся, хоча пропси стали зовсім іншими;
- чому компонент не можна оголошувати всередині іншого компонента;
- що саме робить `key` на одному елементі, який не лежить у списку;
- що зникає разом зі зміною ключа, а що лишається;
- що вибрати ключем і на який компонент його поставити;
- чому скидання ефектом гірше за ключ і коли людина справді побачить старий текст.

## Книгарня з двома незрозумілими помилками

Ви робите сторінку книгарні. Угорі сторінки стоїть значок «У кошику: 0», а нижче стоїть картка книжки з кнопкою
«Купити». Ви написали обидва компоненти окремо, кожен зі своїм лічильником, і клацнули тричі. На кнопці написано
«взято 3», а значок досі показує нуль.

Поруч є друга частина сторінки. Ліворуч лежить перелік книжок, а праворуч стоїть форма відгуку на обрану книжку.
Людина написала кілька слів про «Кобзар», випадково клацнула «Лісову пісню» і натиснула «Надіслати». Відгук на одну
книжку пішов до іншої, хоча в коді обраної книжки все правильно: пропс змінився, і заголовок форми показує нову назву.

Перша помилка виникла, бо стану забагато: одне значення лежить у двох місцях. Друга виникла, бо React зберіг стан там,
де ви очікували нового. Щоб розв'язати обидві, треба точно знати, кому належить стан.

## Частина перша: стан, який мусить бути спільним

### Чому окремий стан розходиться

Лекція «Компоненти й модулі» пояснила, що кожен екземпляр компонента має власний стан. Це правило корисне, поки
компоненти справді незалежні. Подивімося, що воно дає в книгарні:

```tsx
function Badge() {
  const [count] = useState(0)
  return <p>У кошику: {count}</p>
}
function BuyCard() {
  const [count, setCount] = useState(0)
  return <button onClick={() => setCount(count + 1)}>Купити (взято {count})</button>
}
function SplitShop() {
  return <><Badge /><BuyCard /></>
}
```

Тест клацає кнопку тричі й друкує обидва тексти:

```text
окремий стан | У кошику: 0 | Купити (взято 3)
```

Функція `setCount` змінює стан лише свого екземпляра `BuyCard`. Компонент `Badge` не має жодного способу про це
дізнатися, бо компоненти не читають стан одне одного. Дві змінні `count` мають однакову назву, але це два різні
значення в двох різних екземплярах.

### Підняти стан означає забрати його в дітей

**Підняти стан** означає забрати стан у дітей, покласти його в їхнього найближчого спільного батька й передати вниз
пропсами. Сторінка `Sharing State Between Components` називає три кроки.

1. **Прибрати стан із дітей.** Значення стає пропсом.
2. **Передати дані від спільного батька.** Спершу можна передати просто сталі значення, щоб перевірити розмітку.
3. **Додати стан у батька й передати вниз обробник.** Дитина не може сама змінити чужий стан, тому батько дає їй
   функцію.

Лекція «Події й стан» уже показала останній із цих кроків окремо: дитина повідомляє батька про подію через
пропс-функцію. Тепер він стає частиною більшого прийому:

```tsx
function LiftedBadge({ count }: { count: number }) {
  return <p>У кошику: {count}</p>
}
function LiftedCard({ count, onBuy }: { count: number; onBuy: () => void }) {
  return <button onClick={onBuy}>Купити (взято {count})</button>
}
function LiftedShop() {
  const [count, setCount] = useState(0)
  return (
    <>
      <LiftedBadge count={count} />
      <LiftedCard count={count} onBuy={() => setCount(count + 1)} />
    </>
  )
}
```

```text
піднятий стан | У кошику: 3 | Купити (взято 3)
```

Прочитаємо головне.

- Компоненти `LiftedBadge` і `LiftedCard` більше не викликають `useState`. Вони показують те, що їм передали.
- Рядок `const [count, setCount] = useState(0)` стоїть тепер у `LiftedShop`, тому значення одне.
- Запис `onBuy={() => setCount(count + 1)}` передає функцію, а не викликає її. Якщо прибрати стрілку, `setCount`
  виконається під час рендеру, і лекція «Рендер, коміт і знімок стану» пояснила, яка помилка тоді виникає.

Простежимо одне клацання:

| Крок | Хто діє | Що відбувається | `count` у `LiftedShop` |
|------|---------|-----------------|------------------------|
| 1 | людина | клацає кнопку в `LiftedCard` | 0 |
| 2 | `LiftedCard` | викликає пропс `onBuy` і нічого не вирішує сама | 0 |
| 3 | функція з `LiftedShop` | викликає `setCount(1)` | 0, бо це знімок поточного рендеру |
| 4 | React | викликає `LiftedShop` знову | 1 |
| 5 | React | передає обом дітям `count={1}` і викликає їх | 1 |
| 6 | React | записує у два місця документа новий текст | 1 |

Дані рухаються вниз пропсами, а події рухаються вгору викликами функцій. Розійтися двом показам нема як, бо обидва
показують одне значення.

### Підняття часто змінює саме значення

Сторінка каже, що підняття часто змінює те, що ви зберігаєте. Уявімо перелік із трьох жанрів, з яких людина обирає
один. Поки кожен рядок сам пам'ятав, чи його обрано, стан складався з трьох прапорців `true` або `false`. Це вісім
можливих комбінацій, а сенс мають лише чотири: жодного обраного або один із трьох. Решта чотири комбінації означають
помилку, і писати код проти них доведеться вам.

Після підняття батько тримає одне значення: номер обраного рядка або `null`. Таке значення фізично не може сказати
«обрано два», тому помилка зникає разом із зайвими комбінаціями. Тема «Стан як набір станів екрана» будує на цій думці
цілий спосіб описувати стан, а тема «Структура стану» пояснює, чому зберігають номер чи ідентифікатор, а не копію
об'єкта.

### Керований і некерований компонент

Компонент називають **некерованим**, якщо важливу для нього інформацію він тримає у власному стані. Батько не може на
неї вплинути. Компонент називають **керованим**, якщо ця інформація приходить пропсами, тому батько повністю визначає
його поведінку. Ці слова ви вже бачили в лекції «Події й стан» стосовно полів вводу: кероване поле отримує `value` зі
стану. Тепер те саме слово застосовують до ваших компонентів, і сенс той самий: хто вирішує.

Сторінка окремо застерігає, що це не точні технічні терміни, адже більшість компонентів має і пропси, і власний стан.
Вона також порівнює обидва підходи.

| | Некерований | Керований |
|---|-------------|-----------|
| що треба дати компоненту | майже нічого | усі значення й обробники |
| чи може батько скоординувати кілька таких | ні | так |
| коли вибирати | значення цікаве лише самому компоненту | значення залежить від сусідів або потрібне батькові |

Найпідступніша проміжна форма виглядає як керована, але такою не є. Компонент отримує пропс і кладе його у свій стан:

```tsx
function CopyBadge({ count }: { count: number }) {
  const [shown] = useState(count)
  return <p>У кошику: {shown}</p>
}
```

```text
копія пропса у стані | У кошику: 0 | Купити (взято 3)
```

Батько передає значення 3, а значок показує 0. Лекція «Події й стан» пояснює, що аргумент `useState` використовується
лише на першому рендері. Після цього копія живе своїм життям. Компілятор тут мовчить, бо типи правильні. Якщо значення
потрібне лише для показу, читайте сам пропс, а якщо копія справді потрібна, бо людина редагує чернетку, читайте розділ
про початкове значення нижче.

### До якого батька піднімати

Правило таке: до найближчого спільного батька всіх компонентів, яким потрібне це значення. Сторінка називає це
**єдиним джерелом правди**: для кожного значення є один компонент, який ним володіє. Це не означає, що весь стан
лежить в одному місці. Різні значення належать різним компонентам.

Чому не підняти одразу на самий верх? Додамо на сторінку підвал, якому кошик не потрібен, і порівняємо два варіанти:

```tsx
let footer = 0
function Footer() { footer++; return <footer>Контакти</footer> }

function HighApp() {
  const [count, setCount] = useState(0)
  return <><Shop count={count} onBuy={() => setCount(count + 1)} /><Footer /></>
}

function OwnShop() {
  const [count, setCount] = useState(0)
  return <Shop count={count} onBuy={() => setCount(count + 1)} />
}
function LowApp() { return <><OwnShop /><Footer /></> }
```

Після трьох клацань:

```text
стан у App | викликів Footer: 4 | У кошику: 3
стан у спільному батькові | викликів Footer: 1 | У кошику: 3
```

Коли стан лежить у `HighApp`, кожне клацання викликає `HighApp`, а разом із ним усіх його дітей, зокрема `Footer`,
якому нічого не змінилося. На екрані результат однаковий. Для простого підвалу зайвий виклик непомітний, але для
важкого дерева він коштує часу, і про це докладно йдеться у фазі 2 в темі про мемоізацію.

Рішення не остаточне. Сторінка прямо каже, що стан часто переносять униз і назад, доки зрозуміють, де йому місце.

### Рецепт: спершу опис даних

Практика дня йде за рецептом книжки How to Design Programs. Лекція «Пропси й умовний рендер» пояснила головну його
думку для варіантів: скільки варіантів в описі даних, стільки гілок у функції. Сьогодні рецепт показує ще й інше:
рішення про стан записують в описі даних ще до першого рядка тіла.

Заготовка `accordion.ts` уже містить тип `ActiveIndex`: це номер відкритого розділу або `null`. Це і є те саме рішення
«одне значення замість кількох прапорців», записане типом. Ось що кожен крок дає вам без готового тіла функцій:

| Крок рецепта | Що він дає |
|--------------|------------|
| опис даних | готовий: тип каже, що варіантів два, а описи пропсів кажуть, хто що знає |
| призначення й сигнатура | одне речення про те, що функція обчислює чи компонент показує, а сигнатура вже є в заготовці |
| приклади | на кожен варіант `ActiveIndex` і на клацання по відкритому й закритому розділу |
| перелік вхідних даних | коментар у тілі: що доступно функції, а для компонента ще стан і його функція `set` |
| шаблон | випишіть відповідь функції для кожного варіанта клацання, а потім перетворіть цей перелік на тіло |
| перевірка | Vitest запускає приклади, а `tsc` перевіряє типи |

## Частина друга: коли стан зберігається, а коли зникає

Тепер про другу помилку книгарні. Для неї потрібен точний механізм.

### Стан належить місцю в дереві

Лекція «Компоненти й модулі» вже сказала, що React прив'язує стан до місця в дереві, а місце разом зі станом називає
екземпляром. Лекція «Списки й ключі» додала ключі для рядків. Сьогодні це правило стає інструментом, тому сформулюємо
його точно.

Сторінка `Preserving and Resetting State` каже прямо: стан зберігається всередині React, а не в компоненті. React
знає, який стан чий, за **позицією** компонента в дереві рендеру. Позицію зручно уявляти як адресу: «перша дитина
першої дитини кореня». Сама сторінка теж вживає слово «адреса». Після кожного рендеру React порівнює нове дерево зі
старим за такими адресами й на кожній дивиться на дві речі: тип і ключ.

| Що на цій адресі після рендеру | Що робить React | Що зі станом |
|--------------------------------|-----------------|--------------|
| той самий тип, той самий ключ або обидва без ключа | передає нові пропси наявному екземпляру | зберігається |
| інший тип | видаляє старий екземпляр і все під ним, створює новий | новий, початковий |
| той самий тип, інший ключ | видаляє старий екземпляр і все під ним, створює новий | новий, початковий |
| нічого | видаляє екземпляр і все під ним | зникає назавжди |

У цій таблиці немає пропсів. Отже, React не вважає компонент іншим через те, що в нього інші пропси. Також немає рядка
про ваш код: React не знає, скільки в ньому `if`, а бачить лише повернутий результат.

### Десять записів, які виглядають схоже

Ось поле пошуку з власним станом:

```tsx
function Search() {
  const [q, setQ] = useState('')
  return <input aria-label="Пошук" value={q} onChange={(e) => setQ(e.target.value)} />
}
```

Кожен варіант нижче вміє показувати щось різне за прапорцем `on`. Тест при `on={false}` набирає у поле «Шевченко»,
перемикає на `on={true}`, повертає `on={false}` і друкує значення поля. Кожен рядок таблиці є справжнім виводом
запуску.

| Запис | Поле після двох перемикань |
|-------|----------------------------|
| `<div>{on ? <Search /> : <Search />}</div>` | `"Шевченко"` |
| `if (on) return <div><Search /></div>; return <div><Search /></div>` | `"Шевченко"` |
| `<div>{on && <Banner />}<Search /></div>` | `"Шевченко"` |
| `<div>{on ? <Banner /> : null}<Search /></div>` | `"Шевченко"` |
| `<div style={{ display: on ? 'none' : 'block' }}><Search /></div>` | `"Шевченко"` |
| `<div>{on ? <><Search /></> : <Search />}</div>` | `"Шевченко"` |
| `if (on) return <div><Banner /><Search /></div>; return <div><Search /></div>` | `""` |
| `<div>{on ? <section><Search /></section> : <article><Search /></article>}</div>` | `""` |
| `on ? <section><Search /></section> : <div><Search /></div>` | `""` |
| `<div>{on ? null : <Search />}</div>` | `""` |

Розберімо ці записи за групами.

**Умова й два `return` з однаковою будовою.** Тегів `<Search />` у коді два, а адреса одна, тому екземпляр один. Два
`return` нічого не змінюють, бо React бачить лише результат.

**`false` і `null` перед полем.** Ці значення нічого не показують, але займають позицію в JSX. Тому поле завжди
лишається другою дитиною `<div>`, незалежно від банера.

**Два `return`, де в одному є банер.** Цей запис виглядає майже як запис із `null`, але результат протилежний. Коли
`on` істинне, поле є другою дитиною. Коли хибне, воно є першою дитиною. Адреса змінилася, і на старій адресі тепер
стоїть інший тип, тому стан зник. Отже, порожнє місце й відсутність місця для React різні речі. Якщо ви бачите, що
показ повідомлення очищає сусідню форму, шукайте саме це.

**Інша обгортка.** Сам `Search` на вигляд той самий, але змінився тип його батька. Сторінка каже, що інший тип скидає
стан усього **піддерева**, тобто компонента й усього, що лежить під ним. Рівень не важливий: зміна тега на будь-якому
рівні над компонентом знищує і його.

**Поле зникає.** Компонента якийсь час не було на екрані. React знищує стан компонента, коли прибирає його. Сторінка
формулює це так: стан живе, доки компонент показано на цій позиції.

**Поле сховане стилем.** Поле лишається в дереві, тому стан цілий. Це один зі способів зберегти стан прихованого
компонента, і про нього є окремий розділ нижче. У браузері цього запису ми не запускали, але стиль лише ховає вузол і
нічого не каже React, тому на дерево не впливає.

**Фрагмент.** Запис `<>...</>` не дав нової адреси, і стан лишився. Запуск підтверджує це лише для такого випадку:
один фрагмент без ключа стоїть там, де раніше стояв сам компонент. Документація цього випадку не описує, тому не
будуйте на ньому логіку.

### Компонент усередині компонента

З цього самого правила випливає заборона, яку лекція «Компоненти й модулі» вже показала на кімнаті з термостатом. Ось
та сама помилка на полі пошуку:

```tsx
function Page() {
  const [likes, setLikes] = useState(0)
  function Search() {                                     // функція оголошена всередині компонента
    const [q, setQ] = useState('')
    return <input aria-label="Пошук" value={q} onChange={(e) => setQ(e.target.value)} />
  }
  return <><Search /><button onClick={() => setLikes(likes + 1)}>Вподобати: {likes}</button></>
}
```

```text
після набору: "Шевченко"
після «Вподобати»: ""
```

Набір тексту працював, бо він викликав лише `Search`. Клацання викликало `Page`, а кожен виклик `Page` створює нову
функцію `Search`. Функції порівнюються за посиланням, тому для React це інший тип на тій самій адресі. Такі помилки
виглядають дуже дивно, бо поле губить текст через клацання по зовсім іншому елементу. Лінт проєкту тут допомагає:

```text
12:13  error  Error: Cannot create components during render
Components created during render will reset their state each time they are created. Declare components outside of render.
react-hooks/static-components
```

## `key`: назвати екземпляр самому

### Покроковий приклад: відгук на дві книжки

Тепер можна пояснити другу помилку книгарні. Ось форма відгуку:

```tsx
type Book = { id: number; title: string }

function ReviewForm({ book }: { book: Book }) {
  const [text, setText] = useState('')
  return <label>Відгук на «{book.title}»<textarea value={text} onChange={(e) => setText(e.target.value)} /></label>
}

function Shelf() {
  const [id, setId] = useState(1)
  const book = BOOKS.find((b) => b.id === id)!
  return (
    <>
      {BOOKS.map((b) => <button key={b.id} onClick={() => setId(b.id)}>{b.title}</button>)}
      <ReviewForm book={book} />
    </>
  )
}
```

Тест запускає цей код двічі. Другого разу останній рядок розмітки має вигляд `<ReviewForm key={book.id} book={book}
/>`. Він набирає «Сильно» для «Кобзаря», клацає ту саму книжку, а потім іншу. У виводі `вузол` означає елемент
`<textarea>` у документі:

```text
без key | та сама книжка: текст "Сильно" | вузол той самий? true
без key | інша книжка: текст "Сильно" | вузол той самий? true
з key   | та сама книжка: текст "Сильно" | вузол той самий? true
з key   | інша книжка: текст "" | вузол той самий? false
```

Простежимо перехід до другої книжки в обох варіантах.

| Крок | Без ключа | З ключем |
|------|-----------|----------|
| до клацання | на адресі стоїть `ReviewForm`, ключа немає, `text` = «Сильно» | на адресі стоїть `ReviewForm`, ключ `1`, `text` = «Сильно» |
| рендер `Shelf` | опис: `ReviewForm` без ключа, пропс інший | опис: `ReviewForm` із ключем `2`, пропс інший |
| порівняння | тип і ключ ті самі: це той самий екземпляр | ключ інший: це інший екземпляр |
| що зі станом | `text` лишається, новий лише пропс | старий стан знищено, `useState('')` дає порожній рядок |
| що в документі | той самий `<textarea>`, змінився підпис | старий вузол видалено, вставлено новий |
| що бачить людина | підпис нової книжки й старий текст | підпис нової книжки й порожнє поле |

Зверніть увагу на рядок із ключем про ту саму книжку. Коли людина клацає книжку, яка вже обрана, ключ не змінюється,
тому текст лишається. Ключ скидає стан лише тоді, коли сутність справді інша.

### Що додає ключ до адреси

Лекція «Списки й ключі» використовувала ключ, щоб React упізнавав рядок після перестановки. Тут він стоїть на
одному-єдиному елементі, і механізм той самий. Сторінка пояснює це так: ключ стає частиною позиції замість порядку
серед дітей. Тому ключ працює в обидва боки. Він скидає стан, коли змінюється на тій самій позиції, і зберігає стан,
коли елемент із тим самим ключем пересунувся. Ось другий напрямок на двох полях форми, які міняються місцями за
галочкою:

```tsx
function Plain({ rev }: { rev: boolean }) {
  return rev
    ? <div><Field label="Прізвище" /><Field label="Ім'я" /></div>
    : <div><Field label="Ім'я" /><Field label="Прізвище" /></div>
}
```

Тест набирає «Леся» в полі «Ім'я» і перемикає порядок. Варіант із ключами відрізняється записом `key="f"` на полі
імені й `key="l"` на полі прізвища:

```text
без ключів | Ім'я = "" | Прізвище = "Леся"
з ключами | Ім'я = "Леся" | Прізвище = ""
```

Без ключів текст лишився на першій позиції, а підписи помінялися, і ім'я потрапило до прізвища. З ключами React
пересунув екземпляри разом зі станом.

Сторінка наголошує ще на одному: ключі не є глобальними, бо вони діють лише серед дітей одного батька. Лекція «Списки
й ключі» показала це запуском: рядок із тим самим ключем в іншому батькові вважається новим. Тому той самий `id` можна
спокійно вживати як ключ у двох різних місцях сторінки.

### Що зникає разом зі старим ключем

**Весь стан екземпляра й усього під ним.** Це важливо, якщо всередині форми є ще компонент із власним станом. Ми
додали до форми компонент `Stars`, який у власному стані рахує зірочки оцінки. Тест набрав текст, двічі клацнув
зірочки й перейшов до іншої книжки:

```text
key на формі | текст "" | Зірок: 0
```

**Вузли документа.** Елемент видалено, тому зникає все, що лежало в ньому самому: фокус клавіатури, виділений текст,
позиція прокрутки, текст некерованого поля. Перевіримо фокус:

```text
до зміни ключа у фокусі: TEXTAREA
після зміни ключа у фокусі: BODY | старий вузол у документі? false
```

Фокус опинився на `<body>`. Для людини, яка працює з клавіатурою, це означає, що після переходу курсор поля треба
повернути окремо. Цей вивід отримано під jsdom, а в браузері ми цього не запускали. У браузері очікуйте те саме, бо
стандарт HTML описує скидання фокуса, коли елемент із фокусом видаляють. Створення вузлів також потребує більше
роботи, ніж оновлення наявних, тому ключ на великому піддереві не безкоштовний.

**Що лишається.** Усе, що лежить вище за ключ: стан батька, стан сусідів, а також пропси, які передає батько.

### Початкове значення читається знову

Розділ про керований компонент попереджав про копію пропса в стані. Є випадок, коли така копія потрібна: форма
редагування. Людина змінює назву книжки, а книжка в батька лишається старою, доки людина не натисне «Зберегти». Отже,
чернетка має почати зі значення пропса й далі жити окремо:

```tsx
function EditTitle({ book }: { book: Book }) {
  const [title, setTitle] = useState(book.title)
  return <input aria-label="Назва" value={title} onChange={(e) => setTitle(e.target.value)} />
}
```

Тест показує форму для «Кобзаря», а потім передає «Лісову пісню»:

```text
без key: Кобзар
з key: Лісова пісня
```

Без ключа поле показує назву іншої книжки, і збереження записало б її не туди. З ключем створюється новий екземпляр, а
новий екземпляр читає початкове значення знову. Отже, запис `useState(props.x)` разом із ключем не є помилкою:
чернетка свідомо починається зі значення пропса, а ключ каже, коли почати спочатку. У практиці дня чернетка
починається з порожнього рядка, а механізм той самий.

### Що вибрати ключем

Ключем має бути те, що однозначно називає сутність. Це майже завжди її `id`. Дві книжки можуть мати однакову назву:

```text
key={book.title}, інша книжка з тією самою назвою: Кобзар!!!
key={book.id}, та сама інша книжка: Кобзар
```

В обох запусках людина дописала `!!!` до однієї книжки й перейшла до іншої. З ключем-назвою чернетка лишилася, бо ключ
той самий, а з ключем-ідентифікатором поле почало спочатку.

Ключ також має бути **сталим**, тобто однаковим для тієї самої сутності між рендерами. Випадковий ключ дає нову адресу
при кожному рендері батька:

```text
Math.random, набрали: Кобзар!
Math.random, після рендеру батька: Кобзар
```

Набір працював, бо він викликав лише форму, а її батька ніхто не викликав. Перший рендер батька з іншої причини знищив
чернетку. Лінт і тут каже про це, правилом `react-hooks/purity`: `Cannot call impure function during render`.

### Ключ не на тому рівні

Скидається те, на чому стоїть ключ, і все під ним, але не те, що вище. Цю межу легко переплутати:

```tsx
function EditTitle({ book }: { book: Book }) {
  const [title, setTitle] = useState(book.title)
  return <input key={book.id} aria-label="Назва" value={title} onChange={(e) => setTitle(e.target.value)} />
}
```

```text
key на input усередині: Кобзар!!! | вузол той самий? false
```

React чесно створив новий вузол `<input>`. Але стан `title` лежить не в полі, а в компоненті `EditTitle`, який лишився
тим самим екземпляром. Новий вузол одразу отримав старе значення. Правило таке: ключ ставлять на компонент, що тримає
потрібний стан, або вище, і ставить його той, хто малює цей компонент.

## Чому не ефект

### Коротко про `useEffect`

**Ефект** є кодом, який React виконує після того, як записав результат рендеру в документ. Його оголошують хуком
`useEffect`. Другий аргумент є масивом **залежностей**: React порівнює їх із попереднім рендером і виконує ефект
знову, лише якщо хоч одна змінилася. Докладно ефекти вивчають теми «Синхронізація ефектами» й «Коли ефект не
потрібен». Сьогодні досить цього, щоб зрозуміти, чому ефект тут зайвий.

### Що відбувається при скиданні ефектом

Перша думка більшості людей така: «коли змінилася книжка, очистити текст». Записана дослівно, вона дає такий код.
Журнал рядком `log.push` записує кожен рендер, а ефект додатково читає, що зараз у документі:

```tsx
function ByEffect({ book }: { book: Book }) {
  const [text, setText] = useState('')
  log.push(`рендер: «${book.title}», текст ${JSON.stringify(text)}`)
  useEffect(() => {
    log.push(`ефект: у документі зараз ${JSON.stringify(document.querySelector('textarea')!.value)}`)
    setText('')
  }, [book.id])
  return <textarea value={text} onChange={(e) => setText(e.target.value)} />
}
```

Набираємо «Так» і переходимо до іншої книжки. Поруч той самий компонент без ефекту, але з ключем:

```text
ефект
рендер: «Лісова пісня», текст "Так"
ефект: у документі зараз "Так"
рендер: «Лісова пісня», текст ""
key
рендер: «Лісова пісня», текст ""
```

| Що порівнюємо | Ефект | Ключ |
|---------------|-------|------|
| рендерів на один перехід | 2 | 1 |
| чи бачив рендер новий пропс разом зі старим станом | так | ні |
| чи записав React старий текст у документ | так | ні |
| що скидається | лише те, що ви перелічили в ефекті | усе піддерево |
| скільки коду | ефект у кожному компоненті зі станом | один атрибут у батька |

Різницю в тому, що саме скидається, варто побачити. Форма з тим самим компонентом `Stars`, але скинута ефектом, дає:

```text
ефект у формі | текст "" | Зірок: 2
key на формі | текст "" | Зірок: 0
```

Ефект очистив текст, а стан вкладеного компонента лишився від попередньої книжки. Щоб це виправити, довелося б
додавати ефект і туди. Глава `You Might Not Need an Effect` у розділі `Resetting all state when a prop changes`
називає цю ж причину.

Лінт проєкту помічає такий ефект: `Calling setState synchronously within an effect can trigger cascading renders`,
правило `react-hooks/set-state-in-effect`. Натомість `tsc` мовчить, а тести, що дивляться на екран, проходять, бо
Testing Library дочікується ефектів.

### Чи побачить людина старий текст на екрані

Часто кажуть, що людина побачить один кадр зі старим текстом. Це треба уточнити, бо один зайвий рендер стається завжди, а кадр на
екрані ні. Довідник `useEffect` у розділі `Caveats` розрізняє дві ситуації. Якщо ефект викликано не взаємодією людини,
React зазвичай дає браузеру спершу намалювати екран. Якщо його викликано взаємодією, наприклад клацанням, React може
виконати ефект до малювання. Є й третє речення: навіть тоді браузер може встигнути перемалювати екран, перш ніж React
обробить оновлення стану з ефекту.

jsdom нічого не малює, тому ми запустили збірку цього прикладу в Chrome 156 без вікна. Перед кожним кадром функція
`requestAnimationFrame` читала текст у документі. Ми шукали кадр, у якому книжка вже нова, а текст ще старий. Перехід
ми запускали 60 разів клацанням, викликаним кодом через метод `click()`, і 60 разів викликом `set` із таймера.

| Що викликало перехід | Спроб | Спроб, де знайшовся кадр зі старим текстом |
|----------------------|-------|--------------------------------------------|
| клацання | 60 | 0 |
| таймер | 60 | 3 |

Отже, після клацання старого тексту в цьому запуску на кадрах не було, а після таймера він іноді був. За документацією
відповідь мережі потрапляє до тієї самої групи, що й таймер, бо її теж не викликала взаємодія людини, але її ми не
запускали. Це один запуск на одній машині, а документація вживає слово «може», тому покладатися на відсутність кадру
не можна. Незалежно від кадру лишаються зайвий рендер, рендер із чужими даними, запис старого тексту в документ і
вкладений стан, який ефект не скинув.

## Якщо чернетку треба зберегти

Ключ викидає чернетку назавжди. Інколи потрібно навпаки: людина повернулася до книжки й хоче побачити свій текст.
Сторінка `Preserving and Resetting State` у блоці `Preserving state for removed components` пропонує три способи.

**Підняти чернетки в батька.** Сторінка називає цей спосіб найпоширенішим. Батько не зникає, тому стан у ньому
переживає зникнення дитини:

```tsx
function Shelf() {
  const [id, setId] = useState(A.id)
  const [drafts, setDrafts] = useState<Record<number, string>>({})
  const book = id === A.id ? A : B
  return (
    <>
      <button onClick={() => setId(A.id)}>перша</button>
      <button onClick={() => setId(B.id)}>друга</button>
      <Review key={book.id} book={book} draft={drafts[book.id] ?? ''}
        onDraft={(t) => setDrafts({ ...drafts, [book.id]: t })} />
    </>
  )
}
```

Тут `Review` є керованим компонентом без власного стану. Людина набрала «Сильно» для першої книжки й «Ніжно» для
другої, а потім перемикалася:

```text
друга книжка: ""
знову перша: "Сильно"
знову друга: "Ніжно"
```

Запис `{ ...drafts, [book.id]: t }` замінює об'єкт новим, як пояснила лекція «Об'єкти й масиви в стані», а квадратні
дужки дають назву поля з виразу.

**Показати всі форми й сховати зайві стилем.** Вони лишаються в дереві, тому стан цілий, як показав запис із `display:
none`. Сторінка попереджає, що за великих прихованих дерев це повільно.

**Зберігати поза станом React.** Сторінка наводить `localStorage` для випадку, коли чернетка має пережити закриття
вкладки. Ми цього не запускали, а сховище браузера докладніше описано в MDN.

Сторінка окремо зауважує, що ключ потрібен незалежно від вибраного способу, бо чат із однією людиною за змістом
відрізняється від чату з іншою. У прикладі вище ключ і піднята чернетка працюють разом.

Якщо треба скинути лише частину стану, ключ не підходить, бо він скидає все. Глава `You Might Not Need an Effect` у
наступному розділі показує спосіб для цього випадку, а докладно його вивчає тема «Коли ефект не потрібен».

## Типові хибні уявлення

**«Новий пропс означає новий компонент».** Пропси не беруть участі в рішенні. Форма отримала іншу книжку й зберегла
чернетку.

**«Новий тег у JSX означає новий компонент».** Стан не лежить у тегах. Два записи `<Search />` в різних гілках умови
дали той самий екземпляр, бо адреса в них одна.

**«Стан лежить у вузлі документа».** Стан лежить у React. З ключем текст зник, і вузол теж новий, але в записі з `key`
на `<input>` усередині форми вузол новий, а стан той самий. Лише текст некерованого поля справді лежить у вузлі, як
пояснила лекція «Списки й ключі».

**«`key` потрібен лише у списках».** Ключ працює на будь-якому елементі. У списку він просто необхідний, бо без нього
рядки зсуваються.

**«Умовний показ завжди скидає сусідів».** Запис `{on && <Banner />}` тримає місце, тому сусід зберігає стан. Скидає
сусіда лише структура, у якій він опиняється на іншій позиції.

**«Спільний стан варто тримати якомога вище».** Значення належить найближчому спільному батькові. Вище воно змушує
викликати компоненти, яким нічого не змінилося.

**«Ефект робить те саме, що ключ, лише довше».** Ефект дає зайвий рендер із чужими даними, а вкладений стан лишає
старим.

**«Ключ не можна ставити на компонент, який не в масиві, бо це зайве».** Це і є прямий спосіб сказати React, що
сутність інша. Ніякого попередження React тут не дає.

## Як це проявиться далі в React

- **День 13, редюсер.** Коли спільний стан стає складним, логіку його змін зручно винести з батька в одну функцію.
- **День 14, контекст.** Коли піднятий стан треба передавати через багато рівнів, контекст доставляє його без
  проміжних пропсів.
- **День 17, коли ефект не потрібен.** Сьогоднішнє скидання є одним із типових випадків цієї теми, а поруч стоїть
  скидання лише частини стану.
- **Фаза 2, день 2, узгодження дерева.** Там те саме порівняння за типом і ключем розглядається зсередини.
- **Фаза 2, день 4, мемоізація.** Там вимірюється ціна зайвих викликів, які ви сьогодні побачили у `Footer`.

## Перевірте себе

**1. Значок і кнопка мають кожен свій `useState(0)`. Чому значок не бачить клацань, якщо обидва змінні звуться
`count`?**

<details><summary>Відповідь</summary>

Це два окремі значення у двох екземплярах. Функція `set` змінює стан лише свого екземпляра, а компоненти не читають
стан одне одного. Щоб значення було спільним, його піднімають до найближчого спільного батька.

</details>

**2. Батько передає `count`, а дитина пише `const [shown] = useState(count)`. Що покаже дитина після зміни `count`?**

<details><summary>Відповідь</summary>

Старе значення. React використовує аргумент `useState` лише на першому рендері цього екземпляра, а далі живе копія.
Якщо значення потрібне лише для показу, читайте сам пропс.

</details>

**3. Чому `<div>{on && <Banner />}<Search /></div>` зберігає текст у полі, а два `return` з банером і без нього не
зберігають?**

<details><summary>Відповідь</summary>

У першому записі `false` займає позицію, тому поле завжди є другою дитиною. У другому записі поле є то другою, то
першою дитиною, тому на його адресі з'являється інший тип, а стан знищується.

</details>

**4. Текст у полі пропадає після клацання по сусідній кнопці, яка змінює стан батька. Де шукати причину?**

<details><summary>Відповідь</summary>

Найімовірніше, компонент із полем оголошено всередині батька. Кожен рендер батька створює нову функцію, а для React це
інший тип на тій самій адресі. Лінт позначить це правилом `react-hooks/static-components`. Оголошення треба винести на
верхній рівень файла.

</details>

**5. Ви поставили `key={book.id}` на `<input>` усередині форми, а стан `title` лежить у формі. Чому чернетка
лишилася?**

<details><summary>Відповідь</summary>

Ключ створив новий вузол `<input>`, але форма лишилася тим самим екземпляром, і її стан теж. Новий вузол одразу
отримав старе значення. Ключ ставлять на компонент, що тримає стан, або вище.

</details>

**6. Чому `key={book.title}` гірший за `key={book.id}`, а `key={Math.random()}` гірший за обидва?**

<details><summary>Відповідь</summary>

Дві книжки можуть мати однакову назву, і тоді чернетка перейде до іншої книжки. Випадковий ключ змінюється при кожному
рендері батька, тому чернетка зникає через будь-яку зміну вище, навіть якщо сутність та сама.

</details>

**7. Скидання ефектом дало правильний екран у тестах. Назвіть три причини все одно перейти на ключ.**

<details><summary>Відповідь</summary>

Перша: рендерів два, і перший поєднує новий пропс зі старим станом та записує старий текст у документ. Друга: ефект
скидає лише перелічене, а стан вкладених компонентів лишається. Третя: після переходу, викликаного не людиною,
наприклад таймером, браузер може показати кадр зі старим текстом.

</details>

**8. Людина хоче, щоб чернетка поверталася, коли вона повернеться до книжки. Що робити і чи потрібен тоді ключ?**

<details><summary>Відповідь</summary>

Підняти чернетки в батька, наприклад об'єктом від `id` до тексту. Батько не зникає, тому чернетки лишаються. Ключ
сторінка радить лишити, бо за змістом це різні форми, і він скидає решту внутрішнього стану та вузли.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| підняття стану | перенесення стану з дітей до їхнього найближчого спільного батька |
| найближчий спільний батько | найнижчий компонент дерева, під яким лежать усі, кому потрібне значення |
| єдине джерело правди | принцип: кожним значенням володіє один компонент |
| керований компонент | компонент, чию важливу інформацію задають пропси |
| некерований компонент | компонент, який тримає важливу інформацію у власному стані |
| позиція в дереві | адреса компонента в дереві рендеру, за якою React пов'язує стан |
| екземпляр | запис React про компонент на конкретній позиції разом зі станом |
| ключ | атрибут `key`, який стає частиною позиції |
| піддерево | компонент і все, що лежить під ним |
| ефект | код, який React виконує після запису результату рендеру в документ |
