# Лекція. Фаза 1, день 13. Редюсер

Вчора ви зібрали стан в одному батькові. Коли такого стану стає багато, з'являється нова проблема: правила його зміни
розкидано по обробниках, і легко забути одне поле. Ця лекція пояснює редюсер, тобто функцію, у якій стоять усі такі
правила. Ви побачите, коли саме React її викликає, чому вона мусить бути чистою і як перевірити її без браузера.
Читання займе близько 45 хвилин.

Приклади з React запущено на версії 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Приклади без
React запущено в самому Node 24. Вивід під прикладами справжній. Типи перевірено компілятором `tsc` версії 6.0. У
браузері приклади не запускалися, бо редюсер є звичайною функцією, а для цього дня браузер нічого не змінює.

**Після лекції ви зможете пояснити:**

- яку проблему розв'язує редюсер і чому вона видна не одразу;
- що таке дія і чому її називають тим, що сталося;
- у якому порядку працюють обробник, `dispatch`, тіло компонента й редюсер;
- чому редюсер мусить бути чистим і де тоді обчислювати випадкове значення чи час;
- що саме подвоює `<StrictMode>` і що від цього псується;
- як `switch` і об'єднання типів не дають забути дію;
- як перевірити редюсер без React і чим `console.assert` відрізняється від тесту;
- що Node робить із файлом `.ts` і які записи він не приймає;
- коли брати редюсер, а коли досить `useState`.

## Пральна машина, яка забуває час

Ви робите панель керування пральною машиною. Людина обирає програму, а програма задає температуру й час. Кнопка
«Старт» запускає прання, а якщо програму не обрано, панель показує попередження. Кнопка «Стоп» повертає панель у
початковий стан. Полів стану п'ять, і ви пишете те, що вже вмієте:

```tsx
function Panel() {
  const [program, setProgram] = useState('')
  const [degrees, setDegrees] = useState(0)
  const [minutes, setMinutes] = useState(0)
  const [running, setRunning] = useState(false)
  const [warning, setWarning] = useState<string | null>(null)

  function chooseCotton() {
    setProgram('Бавовна')
    setDegrees(60)
    setMinutes(90)
    setWarning(null)
  }
  function start() {
    if (program === '') {
      setWarning('Спершу оберіть програму')
      return
    }
    setRunning(true)
    setWarning(null)
  }
  function stop() {
    setProgram('')
    setDegrees(0)
    setRunning(false)
    setWarning(null)
    // setMinutes(0) тут забуто
  }
  // показує всі п'ять значень і три кнопки
}
```

Тест клацає кнопки в такому порядку й друкує панель після кожного клацання:

```text
спочатку немає, 0°, 0 хв, стоїть
Старт    немає, 0°, 0 хв, стоїть, Спершу оберіть програму
Бавовна  Бавовна, 60°, 90 хв, стоїть
Старт    Бавовна, 60°, 90 хв, пере
Стоп     немає, 0°, 90 хв, стоїть
```

В останньому рядку програми немає, а 90 хвилин є. Компілятор тут мовчить, лінт мовчить, і React не каже нічого, бо
кожен виклик сам по собі правильний. Помилка лежить між викликами: правило «стоп скидає все» не записане ніде цілком.
Воно розсипане на окремі виклики в кількох обробниках, а кожне нове поле доведеться дописувати в усі ці місця.

Подивіться ще раз на код. Щоб зрозуміти, як змінюється стан, треба прочитати всі обробники. Обробник водночас описує
дві речі: що зробила людина і яким має стати стан. Редюсер розділяє ці дві речі.

## Від `useState` до редюсера за три кроки

Сторінка `Extracting State Logic into a Reducer` описує перехід трьома кроками. Пройдемо їх на пральній машині.

### Перший крок: обробник каже, що сталося

Заберемо з обробників усі виклики `set`. Натомість обробник надсилає **дію**, тобто звичайний об'єкт JavaScript, який
описує, що зробила людина. За домовленістю в дії є рядок `type` із назвою події, а в інших полях лежать дані, яких без
події не дізнатися:

```tsx
<button onClick={() => dispatch({ type: 'start_pressed' })}>Старт</button>
```

Сторінка підкреслює різницю: ви більше не кажете React, що робити, а кажете, що щойно зробила людина. Назву обирають
відповідно: `start_pressed` означає «натиснули старт», а не `set_running`. Форму дії React не перевіряє, тому вона
може бути будь-якою, а поле `type` є лише домовленістю.

Чому назва важлива? Порівняймо дві можливі дії: дія «постав `running` у `true`» уже містить рішення і нічого не каже
про те, що робити, коли програму не обрано. Дія «натиснули старт» не містить рішення, тому перевірити умову доведеться
в одному місці, і це місце є редюсером. Теорія дня показує цю різницю на кількості квитків.

### Другий крок: написати редюсер

**Редюсер** є функцією, яка отримує поточний стан і дію, а повертає наступний стан. Ось файл, який ми далі
запускатимемо і в Vitest, і без нього:

```ts
// файл washer.ts
export type Washer = {
  program: string
  degrees: number
  minutes: number
  running: boolean
  warning: string | null
}

// Дія каже, що зробила людина, а не яким має стати стан.
export type WasherAction =
  | { type: 'program_chosen'; program: string; degrees: number; minutes: number }
  | { type: 'start_pressed' }
  | { type: 'stop_pressed' }

export const IDLE: Washer = { program: '', degrees: 0, minutes: 0, running: false, warning: null }

export function washerReducer(washer: Washer, action: WasherAction): Washer {
  switch (action.type) {
    case 'program_chosen': {
      return {
        ...washer,
        program: action.program,
        degrees: action.degrees,
        minutes: action.minutes,
        warning: null,
      }
    }
    case 'start_pressed': {
      if (washer.program === '') return { ...washer, warning: 'Спершу оберіть програму' }
      return { ...washer, running: true, warning: null }
    }
    case 'stop_pressed': {
      return IDLE
    }
    default: {
      const rest: never = action
      return rest
    }
  }
}
```

Прочитаємо рядок за рядком те, що тут нове.

- Тип `WasherAction` є розрізнюваним об'єднанням, яке пояснила лекція «TypeScript: основи». Лекція «TypeScript у
  React» уже показала такий тип для дій, а сьогодні ви бачите його в роботі.
- Функцію оголошено поза компонентом, бо все потрібне вона отримує аргументами. Сторінка радить саме так.
- Запис `switch (action.type)` перевіряє спільне поле. Сторінка `Extracting State Logic` називає `switch` звичайним
  способом писати редюсер, хоча `if` дає той самий результат.
- Кожен `case` обгорнуто фігурними дужками, а всередині є `return`. Про причини йдеться нижче.
- Запис `...washer` переносить решту полів, як пояснила лекція «Об'єкти й масиви в стані». Без нього інші поля
  зникнуть.
- Гілка `default` із типом `never` є перевіркою повноти з лекції «TypeScript: основи». Значення туди не потрапляє, а
  забута дія стане помилкою компіляції.
- Дія `stop_pressed` повертає `IDLE`, тому правило «стоп скидає все» записано одним рядком, і забути поле неможливо.

Зверніть увагу, що `program_chosen` за один раз змінює чотири поля. Це не проблема, а мета: **одна дія описує одну
взаємодію людини, навіть якщо змінює багато даних**. Сторінка наводить приклад: кнопка «Скинути» на формі з п'ятьма
полями надсилає одну дію, а не п'ять окремих.

### Третій крок: під'єднати до компонента

Хук `useReducer` отримує редюсер і початковий стан, а повертає поточний стан і функцію `dispatch`:

```tsx
function Panel() {
  const [washer, dispatch] = useReducer(washerReducer, IDLE)
  return (
    <>
      <p>{washer.program || 'немає'}, {washer.degrees}°, {washer.minutes} хв, {washer.running ? 'пере' : 'стоїть'}{washer.warning && `, ${washer.warning}`}</p>
      <button onClick={() => dispatch({ type: 'program_chosen', program: 'Бавовна', degrees: 60, minutes: 90 })}>Бавовна</button>
      <button onClick={() => dispatch({ type: 'start_pressed' })}>Старт</button>
      <button onClick={() => dispatch({ type: 'stop_pressed' })}>Стоп</button>
    </>
  )
}
```

Той самий тест:

```text
спочатку немає, 0°, 0 хв, стоїть
Старт    немає, 0°, 0 хв, стоїть, Спершу оберіть програму
Бавовна  Бавовна, 60°, 90 хв, стоїть
Старт    Бавовна, 60°, 90 хв, пере
Стоп     немає, 0°, 0 хв, стоїть
```

Останній рядок тепер правильний. Обробники стали по одному рядку, а всі правила лежать в одному місці.

Звідки дані про програму? Температуру й час знає той, хто натиснув кнопку, тому вони приїхали в дії. Правило «обрати
програму значить прибрати попередження» стоїть у редюсері.

## Коли React викликає редюсер

Новачок часто думає, що `dispatch` одразу викликає редюсер. Подивимося на справжній порядок. Компонент нижче записує
кожну подію в масив `steps`, а обробник надсилає дві дії:

```tsx
function reducer(n: number, action: { type: 'plus'; by: number }): number {
  steps.push(`редюсер: стан ${n}, дія ${action.by}`)
  return n + action.by
}
function Load() {
  steps.push('тіло компонента: початок')
  const [n, dispatch] = useReducer(reducer, 0)
  steps.push(`тіло компонента: useReducer дав ${n}`)
  return (
    <button onClick={() => {
      steps.push('обробник: початок')
      dispatch({ type: 'plus', by: 1 })
      steps.push('обробник: перший dispatch повернувся')
      dispatch({ type: 'plus', by: 10 })
      steps.push(`обробник: кінець, n усе ще ${n}`)
    }}>кілограмів: {n}</button>
  )
}
```

Після одного клацання:

```text
обробник: початок
обробник: перший dispatch повернувся
обробник: кінець, n усе ще 0
тіло компонента: початок
редюсер: стан 0, дія 1
редюсер: стан 1, дія 10
тіло компонента: useReducer дав 11
кілограмів: 11
```

| Крок | Хто діє | Що відбувається | `n` у цьому рендері |
|------|---------|-----------------|---------------------|
| 1 | обробник | викликає `dispatch`, а React кладе дію в чергу | 0 |
| 2 | обробник | викликає `dispatch` удруге, і черга має дві дії | 0 |
| 3 | обробник | закінчується, а змінна `n` лишилася старою | 0 |
| 4 | React | викликає тіло компонента | ще не отримано |
| 5 | `useReducer` усередині тіла | проходить чергу й викликає редюсер на кожну дію | ще не отримано |
| 6 | `useReducer` | повертає 11 | 11 |
| 7 | React | записує результат у документ | 11 |

З цього порядку випливають чотири наслідки.

**Редюсер є частиною рендеру.** Сторінка каже це прямо: редюсери виконуються під час рендеру, а дії чекають у черзі до
наступного рендеру. Звідси вся вимога чистоти, про яку йдеться далі.

**Дії проходять по черзі.** Друга дія отримала результат першої. Це той самий механізм, який лекція «Рендер, коміт і
знімок стану» пояснила для функцій-оновлювачів: сторінка `Extracting State Logic` порівнює їх безпосередньо. Отже, два
`dispatch` не потребують запису на зразок `setN((old) => ...)`, бо редюсер завжди отримує найсвіжіший стан.

**Після `dispatch` змінна лишається старою.** Рядок «n усе ще 0» є знімком стану, тим самим, що для `useState`. Якщо
наступне значення потрібне просто в обробнику, довідник `useReducer` радить обчислити його самому: викликати
`reducer(state, action)`. Це можливо лише тому, що редюсер є звичайною чистою функцією.

**Функція `dispatch` одна на весь час життя компонента.** За три рендери ми отримали одну й ту саму функцію:

```text
різних функцій dispatch за три рендери: 1
```

Довідник називає це сталою тотожністю. Це знадобиться в темах про ефекти й контекст, бо таку функцію можна передавати
далі, і посилання не зміниться.

Довідник каже, що дію передають у `dispatch` єдиним аргументом, тому всі дані кладуть у саму дію.

### Той самий стан означає немає оновлення

Якщо редюсер повернув той самий об'єкт, React порівнює його через `Object.is` і пропускає оновлення, як пояснила
лекція «Об'єкти й масиви в стані». Коли дія нічого не змінює, варто повернути отриманий стан без змін. Теорія дня
лічить виклики на такому прикладі.

Але те саме правило робить мутацію небезпечною. Редюсер нижче змінює наявний об'єкт і повертає його, а інша дія
повертає копію. Тип `W` тут є об'єктом із полями `minutes` і `running`, а тип `A` містить дії `more` і `noop`:

```tsx
function mutating(w: W, a: A): W {
  if (a.type === 'more') { w.minutes += 10; return w }
  return { ...w }
}
```

```text
після «ще»: 30 хв
після «інше»: 40 хв
```

Клацання «ще» не оновило екран, бо посилання те саме. Зміна стала видною лише після дії, яка створила копію. Це той
самий ефект, що й у лекції «Об'єкти й масиви в стані», лише тепер помилка сидить у редюсері.

## Чому редюсер мусить бути чистим

Лекція «Чистота й дерево» пояснила, що **чиста функція** від тих самих вхідних даних завжди дає той самий результат і
нічого не змінює ззовні. Редюсер мусить бути таким, бо він виконується під час рендеру, а рендер React може запускати
двічі чи повторювати.

Сторінка називає конкретні заборони: без запитів, без таймерів, без дій, що впливають на щось поза компонентом, а
об'єкти й масиви оновлюються без мутації. Подивімося, що ламається.

### Лічильник усередині редюсера

Припустимо, запису прання треба дати номер, і ви берете звичайну змінну-лічильник. Тип `S` тут є об'єктом зі списком
записів `items`:

```tsx
let nextId = 1
function impure(s: S, a: A): S {
  return { items: [...s.items, { id: nextId++, name: a.name }] }
}
```

Кожне клацання додає один запис. Ось номери після трьох клацань, а поруч та сама логіка, де лічильник стоїть в
обробнику, а номер приїжджає в дії: `dispatch({ type: 'added', id: nextId++, name: 'x' })`.

```text
лічильник у редюсері, без StrictMode: 1,2,3
лічильник у редюсері, StrictMode:    2,4,6
лічильник в обробнику, без StrictMode: 1,2,3
лічильник в обробнику, StrictMode:    1,2,3
```

Обгортка `<StrictMode>` викликає редюсер двічі на кожну дію, як показала лекція «Чистота й дерево». Записів усе одно
три, бо React бере результат одного виклику, а другий відкидає. Але зміну змінної поза функцією відкинути нікому, тому
лічильник зростає подвійно. Обробник він двічі не викликає, бо обробник чистим бути не зобов'язаний, тому в другому
варіанті номери правильні.

Це правило працює для кожного зовнішнього значення.

| Що потрібно | Де обчислити | Що потрапляє в дію |
|-------------|--------------|--------------------|
| новий ідентифікатор | в обробнику | `id` |
| поточний час `Date.now()` | в обробнику | `at` |
| випадкове число `Math.random()` | в обробнику | `value` |
| запит у мережу | в обробнику чи ефекті | лише його відповідь, коли вона прийшла |
| запис у `localStorage` | в ефекті чи обробнику | нічого, бо запис не є частиною стану |

Те, що час не можна читати в редюсері, легко перевірити. Функція `reduce` проганяє той самий журнал дій двічі:

```ts
type T = { at: number }
const r = (_state: T, _action: { type: 'pressed' }): T => ({ at: Date.now() })
const log = [{ type: 'pressed' as const }]
const first = log.reduce(r, { at: 0 })
// минуло кілька мілісекунд
const second = log.reduce(r, { at: 0 })
```

```text
Date.now у редюсері, той самий журнал дав той самий стан? false
```

Цей запис умисно використовує `reduce`, і зараз стане ясно чому.

### Звідки назва

Лекція «Масиви й об'єкти функційно» пояснила, що метод `reduce` згортає масив в одне значення. Функція, яку йому
передають, отримує результат на цей момент і поточний елемент, а повертає наступний результат. Сторінка каже, що
редюсер отримав назву саме звідси: він отримує стан на цей момент і дію, а повертає наступний стан. Отже, редюсер не
«зменшує» код, хоча слово схоже. Він згортає історію дій у стан.

Звідси ще одна вигода: журнал дій і чистий редюсер повністю визначають стан. Теорія дня відтворює екран форми одним
рядком `log.reduce(reducer, INITIAL)`. З нечистим редюсером відтворення не збіглося б.

## Типи: помилки, які знаходить `tsc`

П'ять типових помилок редюсера зручно показати разом. Ми спершу запустили їх, а потім передали компілятору з
налаштуваннями шаблону Vite. Він, зокрема, вмикає `noFallthroughCasesInSwitch`, тобто заборону переходу між гілками
`switch` без `return`.

| Помилка в коді | Що під час роботи | Що каже `tsc` |
|----------------|-------------------|----------------|
| у `return` забуто `...w` | поле зникло: `40 хв, running = undefined` | `TS2741: Property 'running' is missing` |
| `case` без `return` | виконується код наступної гілки | `TS7029: Fallthrough case in switch` |
| немає `default` і не всі дії мають гілку | редюсер повертає `undefined` | `TS2366: Function lacks ending return statement` |
| помилка в назві `'start_presed'` | гілка ніколи не спрацює | `TS2678`: тип не можна порівняти |
| дві `const next` у `case` без дужок | `SyntaxError`, файл не виконується | `TS2451: Cannot redeclare block-scoped variable` |

Останній рядок пояснює фігурні дужки в кожному `case`. Без дужок усі гілки `switch` ділять один блок, тому однакове
ім'я конфліктує. Сторінка радить ставити дужки в кожному `case`.

Коли редюсер без типів отримує дію, якої не знає, він повертає `undefined`, і стан зникає цілком. Ось компонент читає
поле з такого стану:

```text
невідомий type: Cannot read properties of undefined (reading 'minutes')
```

Довідник `useReducer` для такого випадку радить кидати помилку наприкінці функції: тоді повідомлення назве дію, а не
поле, яке випадково виявилось першим. У TypeScript цю роботу виконує перевірка повноти, а для даних, які типи не
контролюють, наприклад дії з мережі, кинути помилку все одно корисно.

Такий самий перелік чекає в обробнику. Лекція «TypeScript у React» показала, які помилки дає виклик `dispatch` із
неіснуючою дією чи без потрібного поля. Перевірку `@ts-expect-error` у вашій заготовці вона теж пояснює: коментар
просить компілятор вважати помилку в наступному рядку очікуваною, а якщо помилки немає, скаржиться.

### Виклик під час рендеру

Той самий запис, що й з `set`, дає ту саму петлю:

```tsx
function Loop() {
  const [n, dispatch] = useReducer((x: number) => x + 1, 0)
  return <button onClick={dispatch()}>{n}</button>
}
```

```text
Too many re-renders. React limits the number of renders to prevent an infinite loop.
```

Запис `onClick={dispatch()}` викликає функцію під час рендеру. Виклик просить новий рендер, а той знову викликає
функцію. Лекція «Рендер, коміт і знімок стану» розбирала це на `set`.

## Перевірка без React

Редюсер не залежить ні від React, ні від браузера, тому перевірити його можна в звичайному файлі:

```ts
// файл check.ts
import { IDLE, washerReducer } from '../lec/washer.ts'

const chosen = washerReducer(IDLE, { type: 'program_chosen', program: 'Бавовна', degrees: 60, minutes: 90 })
console.assert(chosen.minutes === 90, 'програма задала хвилини')

const refused = washerReducer(IDLE, { type: 'start_pressed' })
console.assert(refused.running === false, 'без програми машина не стартує')
console.assert(refused.running === true, 'навмисно хибна перевірка')

console.log('кінець файла')
```

Команда `node check.ts` виконує цей файл. Ми запустили її окремим процесом, як це робить тест `checks.test.ts` у
практиці, і надрукували те, що повернув запуск. **Потоком** називають канал, куди програма пише текст: `stdout` для
звичайного виводу, `stderr` для помилок. У терміналі вони виглядають як один текст, але програма може читати їх
окремо. Поле `status` є **кодом завершення**, тобто числом, яке програма повертає системі:

```text
{
  status: 0,
  stdout: 'кінець файла\n',
  stderr: 'Assertion failed: навмисно хибна перевірка\n'
}
```

### Що робить `console.assert`

Функція отримує умову й повідомлення. Якщо умова істинна, вона мовчить. Якщо умова хибна, вона пише повідомлення.
Вивід вище показує три особливості, які треба знати.

**Програма не зупиняється.** Рядок «кінець файла» надруковано після хибної перевірки. Кожна наступна перевірка теж
виконається.

**Код завершення лишається 0.** Для командного рядка програма пройшла успішно. Саме тому прихований тест у вашому
`checks.test.ts` дивиться не лише на код завершення, а й на порожній `stderr`. Без такого тесту можна не помітити
рядка з повідомленням.

**Текст іде в `stderr`.** Сторінка MDN про цю функцію каже, що вона пише повідомлення про помилку в консоль. У
браузері ми її не запускали, але очікуйте те саме: повідомлення в консолі, а не зупинку.

Отже, `console.assert` є найпростішою перевіркою, але не повноцінним тестом. Тест Vitest падає й друкує, що очікував і
що отримав. Сьогодні ви робите обидва види: перевірки в `checks.ts` доводять незалежність від React, а
`examples.test.tsx` є звичайними прикладами рецепта.

### Як Node виконує TypeScript

Лекція «Проєкт: Vite, лінт, TypeScript» пояснила, що перетворення коду лише вирізає типи й нічого не перевіряє. Node
24 уміє те саме без сторонніх пакетів. Сторінка [Modules: TypeScript](https://nodejs.org/api/typescript.html) називає
це **стиранням типів** (type stripping): Node замінює анотації типів порожнечею й виконує решту як JavaScript. Цю
можливість увімкнено без прапорців, а з Node 24.12 документація називає її стабільною. Звідси випливають чотири межі,
і кожну ми перевірили.

```ts
const n: number = 'не число'
console.log(n, typeof n)
```

```text
не число string
```

**Node не перевіряє типи.** Він їх лише стирає, тому цей файл працює. Перевіряє типи тільки `tsc`.

| Запис | Що каже Node | Як правильно |
|-------|--------------|--------------|
| `import { IDLE } from './washer'` | `ERR_MODULE_NOT_FOUND` | `from './washer.ts'` |
| `import { Washer, IDLE } from './washer.ts'` | `does not provide an export named 'Washer'` | `import { type Washer, IDLE }` |
| `enum Mode { Cotton, Quick }` | `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` | об'єднання рядків |

**Розширення обов'язкове.** Node не вгадує файл, а сторінка каже це прямо. Щоб `tsc` не скаржився на таке розширення,
шаблон Vite вмикає налаштування `allowImportingTsExtensions`.

**Імпорт типу пишуть зі словом `type`.** Без нього Node вважає тип справжнім значенням і не знаходить його, бо у
файлі-джерелі типи вже стерто. Налаштування шаблону `verbatimModuleSyntax` змушує компілятор вимагати це слово
заздалегідь.

**`enum` не підходить.** Йому потрібна заміна запису кодом, а не лише стирання. Налаштування шаблону
`erasableSyntaxOnly` забороняє такі записи вже в `tsc`. Саме тому ваш `checks.ts` може імпортувати `order.ts` напряму:
заготовка не містить нічого, що Node не вміє стерти.

## Рецепт: шаблон випливає з опису дій

Практика дня йде за рецептом книжки How to Design Programs. Лекція «Пропси й умовний рендер» пояснила, що скільки
варіантів в описі даних, стільки гілок у функції. Тип `Action` у вашій заготовці є таким описом: кожен варіант є
об'єктом зі своїми полями. У книжці такі дані описує глава `Itemizations and Structures`, а вся її думка лягає на
`switch` одним реченням: у кожній гілці доступні поля лише цього варіанта.

Функцію `orderReducer` ви пишете самі. Ось що кожен крок рецепта дає саме для неї, без готового тіла:

| Крок рецепта | Що він дає |
|--------------|------------|
| опис даних | готовий: `Order` описує стан, а `Action` перелічує шість дій |
| призначення й сигнатура | одне речення про наступний стан і сигнатура із заготовки |
| приклади | щонайменше один на кожну дію, а для межі окремий приклад, що повернуто те саме посилання |
| перелік вхідних даних | коментар у тілі: у кожній гілці є `order`, а поля дії залежать від варіанта |
| шаблон | `switch (action.type)` з гілкою на кожний варіант і `default` із `never` |
| перевірка | Vitest запускає приклади, `tsc` перевіряє `@ts-expect-error`, а Node виконує `checks.ts` |

## Початкове значення третім аргументом

Хук приймає ще один необов'язковий аргумент. Припустимо, початковий стан треба обчислити функцією `make`. Порівняймо
два записи на компоненті, який показали й двічі клацнули:

```tsx
useReducer(r, make(start))          // другий аргумент є результатом виклику
useReducer(r, start, make)          // третій аргумент є самою функцією
```

```text
make(start) другим аргументом: рендерів 3, викликів 3 | на кнопці 12
make третім аргументом: рендерів 3, викликів 1 | на кнопці 12
make третім аргументом у StrictMode: викликів 2
```

У першому записі `make` виконується на кожному рендері, а результат React відкидає. Це те саме, що лекція «Об'єкти й
масиви в стані» показувала для ініціалізатора `useState`. Різниця лише в тому, що редюсер отримує аргумент окремо:
React викликає `make(start)` сам. Під `<StrictMode>` така функція виконується двічі, тому вона теж мусить бути чистою.
У вашій практиці `INITIAL` є готовою константою, тому третій аргумент не потрібен.

## `useState` чи `useReducer`

Сторінка порівнює їх за кількома ознаками й прямо каже, що вони рівноцінні: один завжди можна переписати на інший.

| Ознака | `useState` | `useReducer` |
|--------|------------|--------------|
| обсяг коду спочатку | менше | більше: редюсер і дії |
| обсяг, коли багато схожих обробників | росте | менше, бо правила спільні |
| читання при простих оновленнях | дуже легко | потрібно перейти до редюсера |
| читання при складних оновленнях | компонент роздувається | що сталося окремо, як оновити окремо |
| пошук помилки | важко сказати, де і чому стан став неправильним | можна надрукувати кожну дію й кожен стан |
| перевірка без компонента | логіка лежить у компоненті | редюсер є окремою функцією |

Практичні ознаки на користь редюсера такі: кілька полів змінюються разом, один і той самий запис про поля повторюється
в кількох обробниках, наступний стан залежить від кількох полів, а ще помилки виникають саме через неправильні
оновлення. Сторінка радить брати редюсер, коли ви часто бачите такі помилки, і додає, що не все треба переписувати.

Для одного прапорця чи одного поля `useState` коротший, і це нормально. В одному компоненті можна мати обидва хуки.
Сторінка це дозволяє. Але поля, які скидаються разом, мають лежати в одному місці, бо інакше дія скидання не знає про
частину з них.

## Типові хибні уявлення

**«`dispatch` викликає редюсер».** Він кладе дію в чергу. Редюсер викликається під час наступного рендеру, усередині
`useReducer`. Журнал порядку це показав.

**«Після `dispatch` стан уже новий».** Змінна в обробнику лишається знімком цього рендеру. Наступне значення можна
обчислити викликом редюсера.

**«Під `<StrictMode>` дія надсилається двічі».** Обробник виконується один раз, а двічі виконується редюсер. Тому
лічильник у редюсері стрибає через одиницю, а лічильник в обробнику ні.

**«Це ламає лише `<StrictMode>`, тому його треба вимкнути».** Він нічого не ламає, а показує помилку, яка вже є.
Лекція «Чистота й дерево» пояснює, чому вимикати його не варто.

**«Дія каже, яким має бути стан».** Дія каже, що сталося. Якщо дія `set_running` несе готове значення, правила
лишаються в обробниках, і редюсер нічого не дає.

**«`console.assert` зупинить програму, якщо щось не так».** Програма йде далі, а код завершення лишається 0.

**«Node перевірив типи, бо запустив `.ts`».** Він їх лише стер. Файл із рядком у числовій змінній виконався без
жодного слова.

**«Редюсер зобов'язаний змінювати стан».** Він може повернути отриманий стан без змін, і тоді React пропустить
оновлення.

**«Редюсер кращий за `useState`».** Він кращий для складних оновлень. Для простих він лише додає код.

## Як це проявиться далі в React

- **День 14, контекст.** Глибоким компонентам можна передати стан і `dispatch` контекстом, не передаючи пропси через
  кожен рівень. Сталість `dispatch` тут дуже доречна.
- **Дні 16–19, ефекти.** Запит у мережу, заборонений у редюсері, живе в обробнику або в ефекті, а його відповідь
  потрапляє в стан як дія. Довідник також каже, що `dispatch` можна не вказувати в залежностях ефекту.
- **Фаза 3, день 7, стор поза React.** Стор повертає новий знімок даних за тим самим правилом: той самий об'єкт
  означає, що нічого не змінилося.
- **Фаза 3, день 11, глобальний стан.** Бібліотека Redux теж будує стан редюсерами й діями, тому сьогоднішня думка
  перейде туди майже без змін.

## Перевірте себе

**1. Обробник надсилає дві дії підряд. Скільки разів викликається редюсер, скільки рендерів і що отримує друга дія?**

<details><summary>Відповідь</summary>

Редюсер викликається двічі, а рендер один. Обидві дії чекають у черзі, і під час рендеру React проходить її. Друга дія
отримує результат першої.

</details>

**2. Обробник після `dispatch` друкує стан. Що він побачить і як дізнатися наступний стан?**

<details><summary>Відповідь</summary>

Старе значення, бо змінна є знімком цього рендеру. Наступний стан можна обчислити самому: `reducer(state, action)`.

</details>

**3. Лічильник `nextId++` стоїть у редюсері, і під `<StrictMode>` номери стрибають через одиницю, а записів правильна
кількість. Чому записів не подвоїлось?**

<details><summary>Відповідь</summary>

React бере результат одного з двох викликів, а другий відкидає, тому до стану потрапляє один запис. Зміна змінної поза
функцією не є результатом, тому її ніхто не відкидає.

</details>

**4. Куди перенести `Date.now()`, якщо час потрібен у стані?**

<details><summary>Відповідь</summary>

В обробник. Він обчислює час і передає в дії: `dispatch({ type: 'started', at: Date.now() })`. Редюсер лише записує
значення з дії, тому лишається чистим.

</details>

**5. Чому після `w.minutes += 10; return w` екран не оновився, а потім «наздогнав»?**

<details><summary>Відповідь</summary>

Посилання те саме, тому `Object.is` дав `true`, і React пропустив оновлення. Дані вже змінилися, тому наступний
справжній рендер їх показав.

</details>

**6. Що робить гілка `default` із `const rest: never = action`?**

<details><summary>Відповідь</summary>

Вона не дає забути дію. Поки всі варіанти розібрано, значення туди не потрапляє, і тип `never` підходить. Якщо гілки
бракує, компілятор повідомить назву забутого варіанта.

</details>

**7. `checks.ts` надрукував `Assertion failed`, але команда завершилася кодом 0. Чому, і як це помічає тест дня?**

<details><summary>Відповідь</summary>

Функція `console.assert` лише пише в `stderr` і не зупиняє програму. Тому `checks.test.ts` запускає файл окремим
процесом і вимагає порожній `stderr`, а не лише нульовий код завершення.

</details>

**8. Чому файл `.ts` із явною помилкою типів виконується в Node?**

<details><summary>Відповідь</summary>

Node стирає анотації типів і виконує решту, а типів не перевіряє. Перевірка належить `tsc`, тому в дні є окрема
команда для нього.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| редюсер | чиста функція, яка отримує стан і дію та повертає наступний стан |
| дія | звичайний об'єкт, який описує, що сталося; за домовленістю має поле `type` |
| `dispatch` | функція, яка кладе дію в чергу й просить новий рендер |
| чиста функція | функція, яка від тих самих даних дає той самий результат і нічого не змінює ззовні |
| перевірка повноти | прийом із типом `never`, який перетворює забутий варіант на помилку компіляції |
| потік `stdout` і `stderr` | канали, куди програма пише звичайний вивід і помилки |
| код завершення | число, яке програма повертає системі; нуль означає успіх |
| стирання типів | спосіб Node виконувати TypeScript: анотації прибираються, решта виконується |
