# Лекція. Фаза 1, день 14. Контекст

Ця лекція пояснює, як компонент отримує значення від далекого батька, коли проміжні компоненти нічого про це значення
не знають. Вона також показує, скільки це коштує: які компоненти React викликає знову, коли значення змінюється, і
чому один великий контекст «для всього» викликає зайву роботу. Читання займе близько 45 хвилин.

Приклади запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під прикладами
справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із набором правил `react-hooks` і
правилом `react-refresh`, які стоять у вашому проєкті `spa`. Розширення React Developer Tools працює лише в браузері,
тому ми його не запускали. У розділі про підсвічування сказано, звідки взято кожне твердження про це розширення.

Практика дня просить зробити тему оформлення. Щоб не показувати готового розв'язку, лекція бере інший об'єкт: прогноз
погоди, у якому користувач вибирає одиницю температури.

**Після лекції ви зможете пояснити:**

- яку проблему розв'язує контекст і чому це не привід відмовитися від пропсів;
- як React знаходить значення для `useContext` і коли спрацьовує значення за замовчуванням;
- чому контекст сам нічого не зберігає і звідки в ньому беруться зміни;
- які дві причини змушують React викликати компонент після перемикання значення;
- чому той самий контекст викликає різну кількість рендерів залежно від того, де стоїть стан;
- чому новий об'єкт у `value` і один великий контекст дають зайві рендери;
- навіщо стан і `dispatch` кладуть у два окремі контексти;
- що саме показує підсвічування в React Developer Tools і чому прямокутник не доводить, що компонент викликано.

## Прогноз, у якому всі передають одиницю далі

Ви робите сторінку прогнозу погоди. Користувач вибирає градуси Цельсія або Фаренгейта. Вибір стоїть нагорі, а
температуру показує компонент `Temperature` на самому дні дерева. Між ними лежать компоненти, яким одиниця не
потрібна, але вони мусять її прийняти й передати:

```tsx
function Temperature({ celsius, unit }: { celsius: number; unit: Unit }) {
  return <b>{formatTemperature(celsius, unit)}</b>
}
function DayCard({ day, celsius, unit }: { day: string; celsius: number; unit: Unit }) {
  return <li>{day}: <Temperature celsius={celsius} unit={unit} /></li>
}
function Forecast({ unit }: { unit: Unit }) {
  return <ul><DayCard day="Пн" celsius={20} unit={unit} /><DayCard day="Вт" celsius={10} unit={unit} /></ul>
}
```

Тут `Unit` є типом `'C' | 'F'`, а `formatTemperature` є звичайною функцією, яка перетворює число на рядок. Компонент
`Forecast` читає `unit` лише для того, щоб передати його в `DayCard`. Компонент `DayCard` робить те саме. Такий запис
працює, і він навіть має перевагу: з коду видно, хто які дані отримує. Незручність з'являється тоді, коли таких рівнів
стає багато або коли одне значення потрібне багатьом компонентам у різних гілках. Документація називає цю ситуацію
**prop drilling**, українською «прокидання пропсів»: значення проходить крізь компоненти, які ним не користуються.

Лекція «Пропси й умовний рендер» пояснила, що пропс завжди передається від батька до прямої дитини. Отже, пропсами
неможливо сказати «дай це значення комусь унизу, хто б це не був». Для цього потрібен інший механізм.

## Три кроки контексту

**Контекст** дозволяє компоненту зробити значення доступним усім компонентам усередині себе, хоч би як глибоко вони
лежали. Тема «TypeScript у React» уже коротко показала контекст із боку типів, а сьогодні ви розберете, як він працює.
Робота складається з трьох кроків: створити контекст, прочитати його там, де значення потрібне, і дати значення там,
де воно відоме.

```tsx
const UnitContext = createContext<Unit>('C')

function Temperature({ celsius }: { celsius: number }) {
  const unit = useContext(UnitContext)
  return <b>{formatTemperature(celsius, unit)}</b>
}

function DayCard({ day, celsius }: { day: string; celsius: number }) {
  return <li>{day}: <Temperature celsius={celsius} /></li>
}

function Forecast() {
  return <ul><DayCard day="Пн" celsius={20} /><DayCard day="Вт" celsius={10} /></ul>
}
```

```tsx
<UnitContext value="F">
  <Forecast />
</UnitContext>
```

```text
Пн: 68°FВт: 50°F
```

Два дні надруковано разом, бо тест читає весь текст контейнера, а елементи `li` не додають проміжків. Перетворення на
Фаренгейти спрацювало на обох.

Прочитаємо це рядок за рядком.

- `createContext<Unit>('C')` створює об'єкт контексту. Аргумент `'C'` є **значенням за замовчуванням**, про яке
  йдеться нижче. Контекст створюють поза компонентами, зазвичай в окремому файлі, щоб той, хто дає значення, і той,
  хто його читає, імпортували один і той самий об'єкт.
- `useContext(UnitContext)` є хуком, тому діють звичайні правила хуків: його викликають на верхньому рівні компонента,
  а не в умові чи циклі. Цей виклик каже React: компонент хоче прочитати `UnitContext`, і його результат залежить від
  цього значення.
- `<UnitContext value="F">` є **провайдером**, тобто компонентом, який дає значення всім усередині себе. У React 19
  провайдером є сам об'єкт контексту. У старому коді ви побачите запис `<UnitContext.Provider>`, і він означає те
  саме.
- `DayCard` і `Forecast` більше не згадують одиницю. Їхні сигнатури стали коротшими, а між провайдером і читачем можна
  вставити скільки завгодно компонентів, і нічого не зламається.

Найважливіше стоїть у довіднику `createContext`: сам об'єкт контексту не містить жодних даних. Він лише позначає, про
який саме контекст ідеться. Значення живе в дереві компонентів, у тому місці, де стоїть провайдер.

Компілятор стежить за обома кінцями. Запис `<UnitContext>` без `value` дає `TS2741: Property 'value' is missing`, а
запис `<UnitContext value="K">` дає `TS2322: Type '"K"' is not assignable to type 'Unit'`.

## Як React знаходить значення

Компонент отримує значення **найближчого провайдера над собою**. Ось цей пошук на чотирьох місцях дерева:

```tsx
function Label({ name }: { name: string }) {
  const unit = useContext(UnitContext)
  return <p>{name}: {unit}</p>
}
```

```tsx
<>
  <Label name="без провайдера" />
  <UnitContext value="F">
    <Label name="у провайдері F" />
    <UnitContext value="C">
      <Label name="у вкладеному C" />
    </UnitContext>
    <Label name="знову в F" />
  </UnitContext>
</>
```

```text
без провайдера: C
у провайдері F: F
у вкладеному C: C
знову в F: F
```

Той самий компонент показав різні значення залежно від того, де він стоїть. Тому контекст не є глобальною змінною:
глобальна змінна має одне значення на весь застосунок, а контекст може мати стільки значень, скільки провайдерів.
Сторінка `Passing Data Deeply with Context` порівнює це з успадкуванням у CSS. Як аналогія це добре працює: колір
тексту успадковується вглиб, поки хтось посередині не задасть інший, а різні властивості не заважають одна одній. Так
само різні контексти повністю незалежні.

### Власний провайдер не діє на того, хто його поставив

Пошук іде лише вгору, а компонент стоїть над тим провайдером, якого сам повертає:

```tsx
function Station() {
  const unit = useContext(UnitContext)
  return (
    <UnitContext value="F">
      <p>Station сам прочитав: {unit}</p>
      <Label name="дитина Station" />
    </UnitContext>
  )
}
```

```text
Station сам прочитав: C
дитина Station: F
```

Рядок із написом «сам прочитав» лежить у розмітці всередині провайдера, але змінну `unit` компонент отримав раніше,
від контексту над собою. Це перша причина, яку довідник `useContext` називає, коли компонент не бачить значення.

### Коли спрацьовує значення за замовчуванням

Значення з `createContext` React бере лише тоді, коли над компонентом немає жодного провайдера цього контексту.
Провайдер без значення вже є провайдером, і запуск це показує:

```text
value={undefined}:
без value:
проп названо theme:
попереджень React: 1 [
  'The `value` prop is required for the `<Context.Provider>`. Did you misspell it or forget to pass it?'
]
```

У всіх трьох випадках компонент отримав `undefined`, а не `C`. Попередження React надрукував один раз на три випадки,
тому покладатися на нього не варто. Компілятор ловить відсутній `value` і ловить неправильну назву пропса.

Лекція «TypeScript у React» уже показала прийом для випадку, коли розумного значення за замовчуванням немає: контекст
створюють із `null`, а читають через власний хук, який кидає помилку, якщо провайдера немає. Значення `'C'` у нашому
прикладі розумне, бо прогноз можна показати в градусах Цельсія, навіть якщо ніхто нічого не вибирав. Для поточного
користувача такого значення немає, тому там потрібен `null` і перевірка.

### Той самий контекст можна читати й давати далі

Компонент може прочитати значення згори й дати своїм дітям інше. Так нитка коментарів дізнається про свій рівень
вкладеності без жодного пропса:

```tsx
type Note = { text: string; replies: Note[] }
const DepthContext = createContext(0)

function Thread({ note }: { note: Note }) {
  const depth = useContext(DepthContext)
  return (
    <>
      <p>рівень {depth}: {note.text}</p>
      <DepthContext value={depth + 1}>
        {note.replies.map((reply) => <Thread key={reply.text} note={reply} />)}
      </DepthContext>
    </>
  )
}
```

```text
рівень 0: Дощ буде?
рівень 1: Вранці так
рівень 2: Звідки дані?
рівень 1: Парасолю візьму
```

Перший виклик не має провайдера над собою, тому отримує значення за замовчуванням `0`. Кожен наступний читає значення
батьківського `Thread` і дає своїм дітям на одиницю більше. Сторінка документації робить те саме із заголовками й
секціями.

## Контекст доставляє, а стан зберігає

У прикладах вище значення було написано прямо в розмітці, тому воно ніколи не змінювалося. Сам контекст не вміє ні
зберігати значення, ні змінювати його. Щоб значення змінювалося, його кладуть у звичайний стан, а провайдеру передають
поточне значення цього стану:

```tsx
function AppInline() {
  hit('App')
  const [unit, setUnit] = useState<Unit>('C')
  return (
    <UnitContext value={unit}>
      <button onClick={() => setUnit(unit === 'C' ? 'F' : 'C')}>одиниця</button>
      <Forecast />
      <Footer />
    </UnitContext>
  )
}
```

Виклик `hit` дописує одиницю до лічильника викликів. У справжньому компоненті так не пишуть, бо це порушує чистоту,
про яку йшлося в темі «Чистота й дерево», але для заміру нам потрібне саме число.

Тепер видно, чому контекст не є **менеджером стану**, тобто інструментом, який сам зберігає дані й керує їхніми
змінами. Дані зберігає `useState` у компоненті `AppInline`, а змінює їх функція `setUnit`. Контекст лише робить
поточне значення видимим унизу. Якщо прибрати контекст, стан нікуди не зникне, хоча компонентам унизу доведеться
отримувати його пропсами. Якщо прибрати стан, контекст показуватиме щось незмінне.

## Хто перемальовується, коли значення змінилося

Спершу уточнимо слово. Коли план каже, що React **перемальовує** компонент, це означає рендер: React викликає функцію
компонента знову. Це не малювання пікселів у браузері, про яке йшлося в лекції «Як браузер малює». Якщо компонент
повернув те саме, документ не зміниться, хоча сам виклик відбувся.

Компонент викликають знову з кількох причин. Сьогодні нас цікавлять дві:

1. **Причина контексту.** Компонент читає контекст, а найближчий провайдер отримав інше значення. Довідник
   `useContext` уточнює, що значення порівнюються функцією `Object.is`. Лекція «Значення й посилання» пояснила, що для
   об'єктів вона перевіряє лише те, чи це той самий об'єкт.
2. **Причина батька.** Лекція «Рендер, коміт і знімок стану» показала, що рендер іде вниз по дереву: коли викликано
   батька, React викликає і його дітей, навіть якщо їхні пропси не змінилися.

Ці причини легко сплутати, тому подивімося на заміри. Ось дерево для першого варіанта, де стан і провайдер стоять у
компоненті `AppInline`. У виводі цей варіант позначено літерою A:

```text
AppInline (стан unit)
└─ UnitContext (провайдер)
   ├─ button
   ├─ Forecast
   │  └─ Day
   │     └─ Temperature (читає контекст)
   └─ Footer
```

Лише `Temperature` читає контекст. Тест клацає кнопку й рахує виклики після клацання:

```text
A до клацання: App 1 | Forecast 1 | Day 1 | Temperature 1 | Footer 1
A після клацання: App 1 | Forecast 1 | Day 1 | Temperature 1 | Footer 1 | на екрані: 68°F
```

Клацання викликало всіх, навіть `Footer`, який жодної температури не показує. Контекст тут ні до чого: `setUnit`
змінив стан компонента `AppInline`, тому React викликав його, а далі спрацювала причина батька для всього під ним.

### Той самий контекст, але стан в обгортці

Тепер винесемо стан і провайдер в окремий компонент, який приймає дітей через `children`. Заодно передамо функцію
зміни в окремому контексті, щоб кнопка могла лежати будь-де. У виводі цей варіант позначено літерою Б:

```tsx
const SetUnitContext = createContext<Dispatch<SetStateAction<Unit>>>(() => {})
function UnitProvider({ children }: { children: ReactNode }) {
  hit('UnitProvider')
  const [unit, setUnit] = useState<Unit>('C')
  return (
    <UnitContext value={unit}>
      <SetUnitContext value={setUnit}>
        {children}
      </SetUnitContext>
    </UnitContext>
  )
}

function UnitSwitch() {
  hit('UnitSwitch')
  const setUnit = useContext(SetUnitContext)
  return <button onClick={() => setUnit((u) => (u === 'C' ? 'F' : 'C'))}>одиниця</button>
}

function AppWrapped() {
  hit('App')
  return (
    <UnitProvider>
      <UnitSwitch />
      <Forecast />
      <Footer />
    </UnitProvider>
  )
}
```

```text
Б до клацання: App 1 | UnitProvider 1 | UnitSwitch 1 | Forecast 1 | Day 1 | Temperature 1 | Footer 1
Б після клацання: UnitProvider 1 | Temperature 1 | на екрані: 68°F
```

Екран показує те саме, але викликів стало два замість п'яти. Простежимо, чому.

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | кнопка | викликає `setUnit`, і стан `UnitProvider` змінюється |
| 2 | React | викликає `UnitProvider`, бо стан належить йому |
| 3 | `UnitProvider` | повертає провайдер із новим `value` і з тим самим `children`, який отримав раніше |
| 4 | React | бачить той самий об'єкт у `children` і не викликає `UnitSwitch`, `Forecast` і `Footer` |
| 5 | React | шукає всередині тих, хто читає `UnitContext`, і викликає `Temperature` |

Крок 3 пояснює лекція «Пропси й умовний рендер»: `children` є звичайним пропсом, у якому лежить уже готовий опис
розмітки. Цей опис створив компонент `AppWrapped`, коли його викликали. Його не викликали знову, тому опис лишився тим
самим об'єктом. Якщо React бачить той самий об'єкт елемента, він не викликає такий компонент, крім випадку, коли той
читає змінений контекст. Цей пропуск ми спостерігаємо в запуску, а окремого правила про нього навчальні сторінки React
не формулюють. Докладно механізм пояснює тема «Узгодження дерева» у фазі 2.

Компонент `Temperature` викликано, хоча і `Forecast`, і `Day` над ним пропущено. Отже, контекст доходить до читача, не
зупиняючись на тих, кого React пропустив. Ось ще один замір, де `Forecast` обгорнуто в `memo`, тобто в функцію React,
яка пропускає виклик компонента, коли пропси не змінилися. Докладно її вивчає тема «Мемоізація і React Compiler»:

```text
memo після клацання: App 1 | Temperature 1 | на екрані: 68°F
```

Компонент `Forecast` пропущено, а `Temperature` все одно отримав нове значення. Довідник `useContext` каже про це
прямо: `memo` не заважає дітям отримувати свіжі значення контексту.

Запис із `UnitSwitch` показує ще одну деталь. Кнопка читає лише `SetUnitContext`, а функція `setUnit` завжди та сама,
тому після клацання кнопку не викликали. Для цього кнопка застосовує функцію-оновлювач із теми «Рендер, коміт і знімок
стану»: їй не треба знати поточну одиницю.

Під `<StrictMode>`, який стоїть у файлі `spa/src/main.tsx` вашого проєкту, усі числа в режимі розробки подвоюються:

```text
Б у StrictMode, після клацання: UnitProvider 2 | Temperature 2
```

Склад компонентів той самий. Тому, коли рахуєте виклики у своїй практиці, дивіться насамперед на те, хто взагалі
з'явився в журналі.

### Новий об'єкт у `value`

Часто в контекст хочеться покласти одразу і значення, і функцію зміни. Тоді з'являється така пастка:

```tsx
type UnitValue = { unit: Unit; setUnit: (u: Unit) => void }
const UnitValueContext = createContext<UnitValue | null>(null)

function Reader() {
  hit('Reader')
  const value = useContext(UnitValueContext)
  return <b>{value?.unit}</b>
}

function NewObjectProvider({ children }: { children: ReactNode }) {
  const [unit, setUnit] = useState<Unit>('C')
  const [checks, setChecks] = useState(0)
  return (
    <UnitValueContext value={{ unit, setUnit }}>
      <button onClick={() => setChecks(checks + 1)}>перевірок: {checks}</button>
      {children}
    </UnitValueContext>
  )
}
```

Стан `checks` не має жодного стосунку до одиниці. Тест двічі клацає кнопку «перевірок», а потім те саме робить для
варіанта, у якому об'єкт загорнуто в хук `useMemo`:

```tsx
const value = useMemo(() => ({ unit, setUnit }), [unit])
```

```text
новий об’єкт | Reader після показу: 1 | після двох клацань: 3
useMemo | Reader після показу: 1 | після двох клацань: 1
```

Запис `{{ unit, setUnit }}` створює новий об'єкт при кожному виклику провайдера. Вміст той самий, але `Object.is`
дивиться на посилання й відповідає, що значення інше. Тому `Reader` викликано двічі без жодної причини. Хук `useMemo`
повертає той самий об'єкт, поки не змінилося `unit`, і зайві виклики зникають. Цей хук вивчає тема «Мемоізація і React
Compiler», а сьогодні досить знати, навіщо він тут. Документація також зазначає, що в невеликому застосунку такі зайві
виклики не є проблемою. Простіший шлях без `useMemo` ви вже бачили: значення й функція лежать у двох окремих
контекстах, і кожен містить значення, яке не створюється заново при кожному виклику.

### Один контекст «для всього»

Тепер про пастку дня. Покладемо в один контекст одиницю й мову інтерфейсу:

```tsx
type Settings = { unit: Unit; lang: Lang }
const SettingsContext = createContext<Settings>({ unit: 'C', lang: 'uk' })

function Temperature() {
  hit('Temperature')
  const { unit } = useContext(SettingsContext)
  return <b>{formatTemperature(20, unit)}</b>
}

function Greeting() {
  hit('Greeting')
  const { lang } = useContext(SettingsContext)
  return <p>{lang === 'uk' ? 'Вітаємо' : 'Hello'}</p>
}
```

Компонент `Greeting` бере лише мову, і запис із деструктуризацією виглядає так, ніби він підписаний лише на неї. Але
кнопка міняє одиницю, а не мову, і заміри кажуть інше. Другий рядок виводу отримано з двома окремими контекстами,
`UnitContext` і `LangContext`:

```text
один контекст | після зміни одиниці: Temperature 1 | Greeting 1 | на екрані: 68°F
два контексти | після зміни одиниці: Temperature 1 | на екрані: 68°F
```

У контексту немає **вибіркової підписки**, тобто способу сказати «викликай мене лише тоді, коли змінилося це поле».
Компонент читає все значення цілком. Нове значення означає виклик для кожного читача, а що той читач робить із
результатом, для React неважливо. Отже, один контекст добре підходить для значень, які змінюються разом або змінюються
рідко, а значення, які змінюються незалежно, краще класти в окремі контексти.

Розділення не допоможе компоненту, який читає обидва контексти: він реагує на кожен із них. Також воно не прибере
причину батька, якщо стан лежить у компоненті, під яким написано всю розмітку.

## Що показує підсвічування в React Developer Tools

Практика дня просить побачити рендери очима, тому поговоримо про розширення браузера **React Developer Tools**.
Сторінка `React Developer Tools` пояснює, де його взяти. Після встановлення в інструментах розробника з'являються
вкладки Components і Profiler. Перемикач підсвічування лежить у налаштуваннях: значок шестерні на вкладці Components,
розділ General, позначка `Highlight updates when components render`.

Для цієї лекції ми цього в браузері не запускали; пізніше практику дня запущено в Chrome без вікна, і підсвічування поводилося так само, але саме вікно розширення там не перевіряли. Назву позначки й те, що написано нижче, прочитано у вихідному коді розширення в
репозиторії React, тому порівняйте це зі своїм екраном.

- Коли компонент викликано, розширення малює рамку навколо **найближчих елементів документа** під цим компонентом. Сам
  компонент не має прямокутника на екрані, тому рамка лягає на те, що він намалював.
- Над рамкою стоїть підпис із назвою компонента, якому належить цей елемент, а запис `x2` означає кількість оновлень.
  Колір змінюється від бірюзового до жовтого, коли оновлень стає більше.
- Рамка реагує на виклик компонента, а не на зміну документа. Компонент, який повернув те саме, все одно
  підсвічується.

З першого пункту випливає важлива незручність. Компонент `UnitProvider` не має власного елемента в документі, тому
його виклик намалює рамки на найближчих елементах у кожній гілці під ним. У варіанті Б за цією логікою очікуємо чотири
рамки: навколо кнопки, навколо `ul`, навколо `b` і навколо `footer`. При цьому заміри показують, що викликано лише
`UnitProvider` і `Temperature`. Рамка навколо `footer` із підписом `Footer` виникає через виклик `UnitProvider` і не
доводить, що викликано `Footer`.

Тому читайте рамки так:

| Що ви бачите | Що це означає |
|--------------|---------------|
| рамка на елементі компонента, який читає контекст | цей компонент майже напевно викликано через причину контексту |
| рамка на верхньому елементі компонента, який контекст не читає | або причина батька, або виклик обгортки без власного елемента |
| рамка на елементі глибоко всередині компонента, який контекст не читає | дитину цього компонента викликано з її власної причини |
| немає жодної рамки | компонент, який малює елемент, не викликано |

Щоб відрізнити два випадки в другому рядку, додайте в тіло підозрілого компонента `console.log`. Якщо журнал мовчить,
то компонент не викликано, а рамка належить обгортці. Точніший інструмент, Profiler, чекає вас у фазі 2, у темі
«Профайлер».

## Редюсер і контекст разом

Тема «Редюсер» пояснює **редюсер**: чисту функцію, яка отримує стан і дію, а повертає новий стан. Хук `useReducer`
зберігає стан і повертає функцію `dispatch`, яка надсилає дію. Коли кошик замовлення показують і шапка, і список, і
кнопки, стан і `dispatch` потрібні багатьом компонентам, і зручно поєднати обидва інструменти:

```tsx
type Item = { id: number; title: string; qty: number }
type CartAction =
  | { type: 'added'; id: number; title: string }
  | { type: 'increased'; id: number }

function cartReducer(items: Item[], action: CartAction): Item[] {
  switch (action.type) {
    case 'added':
      return [...items, { id: action.id, title: action.title, qty: 1 }]
    case 'increased':
      return items.map((it) => (it.id === action.id ? { ...it, qty: it.qty + 1 } : it))
  }
}

const CartContext = createContext<Item[] | null>(null)
const CartDispatchContext = createContext<Dispatch<CartAction> | null>(null)

function CartProvider({ children }: { children: ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, [])
  return (
    <CartContext value={items}>
      <CartDispatchContext value={dispatch}>
        {children}
      </CartDispatchContext>
    </CartContext>
  )
}

function useCart(): Item[] {
  const items = useContext(CartContext)
  if (items === null) throw new Error('useCart: компонент має бути всередині CartProvider')
  return items
}

function useCartDispatch(): Dispatch<CartAction> {
  const dispatch = useContext(CartDispatchContext)
  if (dispatch === null) throw new Error('useCartDispatch: компонент має бути всередині CartProvider')
  return dispatch
}
```

Кожна частина робить одну справу. Функція `cartReducer` вирішує, як змінюється кошик, і її можна перевірити без React.
Компонент `CartProvider` зберігає стан і дає обидва значення вниз. Хуки `useCart` і `useCartDispatch` є власними
хуками, тобто звичайними функціями, назва яких починається з `use` і які всередині викликають інші хуки. Вони
прибирають `null` із типу, як показала лекція «TypeScript у React».

Ось компоненти, які цим користуються. Лише `Header` не читає кошика:

```tsx
function AddButton() {
  hit('AddButton')
  const dispatch = useCartDispatch()
  return <button onClick={() => dispatch({ type: 'added', id: 1, title: 'Кава' })}>додати</button>
}

function CartList() {
  hit('CartList')
  const items = useCart()
  const dispatch = useCartDispatch()
  return (
    <ul>
      {items.map((it) => (
        <li key={it.id}>
          {it.title} × {it.qty}
          <button onClick={() => dispatch({ type: 'increased', id: it.id })}>ще</button>
        </li>
      ))}
    </ul>
  )
}

function Badge() {
  hit('Badge')
  return <p>Позицій: {useCart().length}</p>
}

function Header() {
  hit('Header')
  return <header><Badge /></header>
}
```

```tsx
<CartProvider>
  <Header />
  <AddButton />
  <CartList />
</CartProvider>
```

Лічильники тут ростуть від самого показу, без скидання, а слово «ще» в кінці тексту є написом кнопки:

```text
показ: Header 1 | Badge 1 | AddButton 1 | CartList 1
після «додати»: Header 1 | Badge 2 | AddButton 1 | CartList 2 | Кава × 1ще
після «ще»: Header 1 | Badge 3 | AddButton 1 | CartList 3 | Кава × 2ще | Позицій: 1
```

З цього виводу випливає три висновки.

- **Навіщо два контексти.** Лічильник `AddButton` лишився на одиниці, бо цей компонент читає лише `dispatch`. Довідник
  `useReducer` каже, що ця функція зберігає одну й ту саму ідентичність, тобто лишається тим самим об'єктом між
  рендерами. Її значення ніколи не змінюється. Якби стан і `dispatch` лежали разом в одному об'єкті, `AddButton`
  викликали б при кожній зміні кошика.
- **Вибіркової підписки справді немає.** Клацання «ще» змінило кількість, а не число позицій. `Badge` усе одно
  викликано, бо він читає весь масив, а масив новий.
- **Компонент `Header` після показу більше не викликали.** Він нічого не читає, а `CartProvider` отримав його через
  `children`.

Перевірка в хуку теж працює. Компонент `Badge`, показаний без провайдера, кидає помилку з готовою підказкою:

```text
useCart: компонент має бути всередині CartProvider
```

### В одному файлі чи в кількох

Сторінка `Scaling Up with Reducer and Context` наприкінці збирає контексти, редюсер, провайдер і хуки в один файл. У
вашому проєкті такий файл не пройде лінт, якщо в ньому стоїть компонент. Лекція «Проєкт: Vite, лінт, TypeScript»
пояснила, що файл із компонентами має експортувати лише компоненти, бо так працює гаряча заміна. Ось що сказав лінт на
файлі, який експортує контекст, компонент-провайдер і хук:

```text
4:14  error  Fast refresh only works when a file only exports components. Move your React context(s) to a separate file
11:17  error  Fast refresh only works when a file only exports components. Use a new file to share constants or functions between components
```

Обидві помилки належать правилу `react-refresh/only-export-components`. Лінт перестає скаржитися, коли контекст і хук
лежать у файлі `.ts`, а провайдер лежить в окремому файлі `.tsx`. На поведінку застосунку це не впливає, а гаряча
заміна працює так, як вона має працювати.

## Спершу пропси

Сторінка `Passing Data Deeply with Context` окремо просить не хапатися за контекст щоразу, коли пропс проходить кілька
рівнів. Вона радить такий порядок.

**Спершу передайте пропси.** З них видно, хто які дані отримує. Десяток пропсів крізь кілька компонентів є нудною, але
зрозумілою роботою, а людина, яка читатиме код, побачить увесь шлях даних.

**Потім спробуйте винести компоненти й передати розмітку через `children`.** Якщо проміжний компонент лише передає
пропс далі, часто він не мусить знати про дитину:

```tsx
function Page({ children }: { children: ReactNode }) {
  return <main><h1>Погода</h1>{children}</main>
}
function Week({ unit }: { unit: Unit }) {
  return <p>Середня: {formatTemperature(15, unit)}</p>
}
function CompositionApp({ unit }: { unit: Unit }) {
  return (
    <Page>
      <Week unit={unit} />
    </Page>
  )
}
```

```text
ПогодаСередня: 59°F
```

Компонент `Page` не згадує одиниці, хоча `Week` лежить усередині нього. Значення йде напряму з того компонента, який
знає і про одиницю, і про `Week`.

**Контекст потрібен, коли ні те, ні те не допомагає.** Сторінка називає типові випадки: тема оформлення, поточний
обліковий запис, поточний маршрут і стан, який потрібен далеким компонентам. Спільна ознака така: значення потрібне
компонентам у різних частинах дерева.

## Контекст і рецепт

Практика цього плану йде за рецептом книжки How to Design Programs: спершу опис даних, потім приклади, потім функція.
Контекст цьому не заважає, бо він лише доставляє значення. Опис даних тут є типом `Unit`. Перетворення числа на рядок
є окремою чистою функцією, яку можна перевірити звичайним викликом без React:

```ts
function formatTemperature(celsius: number, unit: Unit): string {
  return unit === 'C' ? `${celsius}°C` : `${Math.round((celsius * 9) / 5 + 32)}°F`
}
```

Приклади проходять обидва варіанти типу й межу, де дві шкали збігаються: `(20, 'C')` дає `20°C`, `(20, 'F')` дає
`68°F`, `(0, 'F')` дає `32°F`, а `(-40, 'F')` дає `-40°F`. Те саме стосується редюсера. Компоненти стають тонкими:
вони лише беруть значення з контексту й викликають чисту функцію.

## Типові хибні уявлення

**«Контекст є менеджером стану».** Він нічого не зберігає й не змінює. Дані лежать у `useState` чи `useReducer`, а
контекст лише робить їх видимими внизу.

**«Коли контекст змінюється, перемальовуються всі, хто всередині провайдера».** Контекст викликає лише тих, хто його
читає. Якщо викликано всіх, причина майже завжди в батьку: стан лежить у компоненті, який написав усю розмітку.
Варіанти A і Б показують різницю на одному дереві.

**«Я взяв лише одне поле через деструктуризацію, тому зміна іншого поля мене не торкнеться».** Деструктуризація є
звичайним читанням змінної вже після того, як `useContext` повернув увесь об'єкт. React нічого про неї не знає.

**«`memo` захистить від зайвих рендерів контексту».** `memo` пропускає виклик через незмінні пропси, але компонент,
який читає контекст, усе одно отримує нове значення. Заміри й довідник кажуть про це однаково.

**«Значення за замовчуванням врятує, якщо `value` виявився `undefined`».** Воно працює, лише коли над компонентом
немає жодного провайдера. Провайдер із `undefined` дає `undefined`.

**«`useContext` бачить провайдер, який компонент сам повертає».** Пошук іде лише вгору, а власний провайдер стоїть
нижче.

**«Контекст є глобальною змінною зручнішого вигляду».** Значення залежить від місця в дереві. Два провайдери дають
двом гілкам різні значення, і саме цим користується нитка коментарів із рівнями.

**«Рамка підсвічування доводить, що цей компонент викликано й документ змінився».** Рамка стоїть на елементі й може
належати виклику батька чи обгортки, а зміна документа тут взагалі ні до чого.

## Як це проявиться далі в React

- **День 15, ref.** Контекст не підходить для значення, зміна якого не повинна запускати рендер. Для такого значення
  існує ref, який ви вивчите в наступний день.
- **Дні 16–19, ефекти.** React порівнює залежності ефекту через `Object.is`, тому об'єкт із контексту, створений
  заново, запускатиме ефект щоразу. Стабільна функція `dispatch` такої проблеми не створює.
- **Фаза 2, день 1, профайлер.** Він покаже кожен коміт і компоненти, які під час нього рендерились, тому там ви
  перевірите висновки сьогоднішнього дня точно, а не за рамками.
- **Фаза 2, день 4, мемоізація.** `memo` і `useMemo` стануть там окремою темою, а новий об'єкт у `value` буде одним із
  випадків, на яких варто робити замір.
- **Фаза 3, дні 1–3, маршрути й серверний стан.** Сторінка документації каже, що більшість маршрутизаторів зберігає
  поточний маршрут у контексті. Провайдери бібліотек, які ви поставите, працюють за тим самим механізмом, який ви
  знаєте сьогодні.
- **Фаза 3, день 7, стор поза React, і день 11, глобальний стан.** Там ви отримаєте те, чого бракує контексту:
  компонент викликається лише тоді, коли змінилася потрібна йому частина даних.

## Перевірте себе

**1. Компонент `DayCard` приймає пропс `unit` лише для того, щоб передати його глибше. Який запис спершу варто
спробувати, перш ніж брати контекст?**

<details><summary>Відповідь</summary>

Спершу варто спробувати передавання розмітки через `children`: компонент, який знає про дані, сам вставляє потрібну
дитину, а проміжний компонент про дані не знає. Контекст потрібен, якщо значення потрібне багатьом компонентам у
різних гілках і цей запис не допомагає.

</details>

**2. Контекст створено так: `createContext<Unit>('C')`. Що поверне `useContext` у трьох випадках: провайдера немає,
над компонентом стоїть `<UnitContext value="F">`, над компонентом стоїть провайдер зі значенням `undefined`?**

<details><summary>Відповідь</summary>

Відповідно `'C'`, `'F'` і `undefined`. Значення за замовчуванням працює лише тоді, коли провайдера немає зовсім.

</details>

**3. Компонент повертає `<UnitContext value="F"><p>{unit}</p></UnitContext>`, а змінну `unit` він прочитав через
`useContext` вище в тому самому тілі. Що покаже абзац, якщо над компонентом провайдера немає?**

<details><summary>Відповідь</summary>

Значення за замовчуванням, тобто `C`. Компонент читає контекст над собою, а провайдер, який він сам повертає, стоїть
нижче. Значення `F` отримають лише компоненти, які стоять усередині цього провайдера й самі викликають `useContext`.

</details>

**4. Стан одиниці лежить у `App`, а `App` прямо в своїй розмітці пише `<Forecast />`, який контексту не читає. Чи
викличе React компонент `Forecast` після зміни одиниці? А якщо стан перенести в `UnitProvider`, який приймає
`children`?**

<details><summary>Відповідь</summary>

У першому випадку так: викликано `App`, а рендер іде вниз по дереву. У другому випадку ні: викликано `UnitProvider`, а
`children` є тим самим описом розмітки, бо `App` не викликали. React викличе лише тих, хто читає змінений контекст.

</details>

**5. Провайдер пише `<UnitValueContext value={{ unit, setUnit }}>`. Батько провайдера перемалювався з іншої причини, а
`unit` той самий. Чи викличе React тих, хто читає цей контекст, і чому?**

<details><summary>Відповідь</summary>

Так. Запис створює новий об'єкт при кожному виклику, а `Object.is` порівнює посилання, а не вміст. Допомагає `useMemo`
або розділення на два контексти зі значеннями, які не створюються заново.

</details>

**6. Навіщо `dispatch` лежить в окремому контексті, якщо можна покласти `{ items, dispatch }` в один?**

<details><summary>Відповідь</summary>

Функція `dispatch` завжди та сама, тому компонент, який лише надсилає дії, не викликається при зміні стану. У замірі
лічильник `AddButton` лишився на одиниці. З одним контекстом цей компонент читав би весь об'єкт і викликався б при
кожній зміні кошика.

</details>

**7. У варіанті з обгорткою ви бачите рамку навколо `footer`, хоча `Footer` контексту не читає. Чи доводить вона, що
`Footer` викликано? Як це перевірити?**

<details><summary>Відповідь</summary>

Ні. За кодом розширення рамка стоїть на найближчих елементах під компонентом, якого викликано, а обгортка не має
власного елемента. Перевірити можна викликом `console.log` у тілі `Footer`: якщо журнал мовчить, компонент не
викликано. Точно те саме покаже Profiler.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| контекст | спосіб зробити значення доступним усім компонентам усередині, без пропсів на кожному рівні |
| провайдер | компонент `<MyContext value={...}>`, який дає значення всім усередині себе |
| значення за замовчуванням | аргумент `createContext`; працює, лише коли над компонентом немає провайдера |
| прокидання пропсів, prop drilling | передавання пропса крізь компоненти, які ним не користуються |
| менеджер стану | інструмент, який сам зберігає дані й керує їхніми змінами; контекст ним не є |
| перемалювати компонент | викликати функцію компонента знову, тобто зробити рендер |
| вибіркова підписка | можливість реагувати лише на зміну одного поля; у контексті її немає |
| власний хук | функція, назва якої починається з `use` і яка всередині викликає інші хуки |
| редюсер | чиста функція, яка отримує стан і дію, а повертає новий стан |
| `dispatch` | функція, яка надсилає дію в редюсер; лишається тією самою між рендерами |
