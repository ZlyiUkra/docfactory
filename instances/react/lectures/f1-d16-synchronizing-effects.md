# Лекція. Фаза 1, день 16. Синхронізація ефектами

Досі компоненти лише обчислювали розмітку й відповідали на клацання. Ця лекція пояснює, що робити, коли компонент має
працювати з чимось поза React весь час, поки він на екрані: тримати з'єднання з сервером, слухати подію вікна, рухати
таймер або завантажувати дані. Читання займе близько 50 хвилин.

Приклади запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під прикладами
справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із тим самим набором правил
`react-hooks`, що й у проєкті `spa`. Частину тверджень jsdom перевірити не може, тому ми запустили їх у Chrome 156 без
вікна на сервері розробки Vite й на зібраному застосунку через `vite preview`. Біля кожного такого твердження сказано,
де воно перевірялося.

Практика дня просить підключитися до кімнати чату й завантажити дані кімнати через вигаданий сервер, який замінює
мережу. Щоб не показувати готового розв'язку, лекція бере інші об'єкти: табло матчу, слайд-шоу, автозбереження чернетки й картку слова зі словника.

**Після лекції ви зможете пояснити:**

- чим ефект відрізняється від коду рендеру й від обробника події;
- у який момент React запускає ефект і що вже є в документі на цей момент;
- чим різняться ефект без списку залежностей, ефект із порожнім списком і ефект зі списком значень;
- коли React викликає функцію прибирання і яке значення вона бачить;
- навіщо `<StrictMode>` у розробці запускає ефект, прибирання й знову ефект, чому вимикати це не треба;
- як прибирання зупиняє таймер, який пережив би компонент;
- чому стара відповідь із мережі може перезаписати нову і як це зупиняє прапорець `ignore`;
- що робить `AbortController` і чому самого його недостатньо;
- чому прапорець не прибирає з екрана старі дані, поки нова відповідь іде;
- що саме побачити в лозі розробки й у лозі збірки.

## Табло, яке має бути підключене

Ви робите табло футбольного матчу. Поки табло на екрані, воно має бути підключене до стрічки подій цього матчу, а коли
табло зникло, стрічку треба закрити. Сервер ми заміняємо маленькою функцією, яка лише записує дії в журнал і рахує
відкриті стрічки:

```tsx
function createFeed(matchId: string) {
  return {
    open() { active++; log.push('open ' + matchId) },
    close() { active--; log.push('close ' + matchId) },
  }
}
```

Де викликати `open()`? Перше, що спадає на думку, це тіло компонента:

```tsx
function FeedInBody({ matchId }: { matchId: string }) {
  const feed = createFeed(matchId)
  feed.open()
  return <h2>Матч {matchId}</h2>
}
```

Показуємо компонент, викликаємо його ще двічі з тим самим матчем і прибираємо з екрана:

```text
у тілі компонента, три рендери й зникнення: open кубок, open кубок, open кубок | відкритих стрічок: 3
```

Три рендери дали три з'єднання, і жодне не закрилося. Лекція «Чистота й дерево» пояснила причину: тіло компонента має
лише обчислювати розмітку, а React вправі викликати його скільки завгодно разів. Відкрити з'єднання означає змінити
щось поза компонентом, тому тіло для цього не годиться.

Другий кандидат це обробник події. Обробник існує саме для дій, але він запускається лише тоді, коли людина щось
зробила. Табло немає на що чекати: людина могла прийти на сторінку за посиланням, повернутися кнопкою «назад» або
відкрити вкладку. Дія потрібна тому, що компонент показано на екрані, і жодного клацання для цього немає.

Для такого випадку існує третій вид коду, який називають **ефектом**. Ефект є кодом, який React запускає після
рендеру, щоб узгодити компонент із системою поза React. Таке узгодження називають **синхронізацією**, а система поза
React є зовнішньою системою: мережа, таймер браузера, подія вікна, сторонній віджет.

| Вид коду | Що його запускає | Що він має право робити |
|----------|------------------|-------------------------|
| тіло компонента | сам рендер | лише обчислювати розмітку |
| обробник події | конкретна дія людини | дії, спричинені цією подією |
| ефект | сам факт показу на екрані й зміна значень, від яких він залежить | синхронізацію із зовнішньою системою |

Запитання для вибору просте: чому цей код має виконатися? Якщо тому, що людина натиснула кнопку, це обробник. Якщо
тому, що компонент видно на екрані, це ефект. Наступна лекція, «Коли ефект не потрібен», присвячена тому, щоб не
писати ефект там, де зовнішньої системи немає.

## Оголошення: коли запускається ефект

Хук `useEffect` приймає функцію й просить React виконати її пізніше. Лекція «Рендер, коміт і знімок стану» поділила
оновлення на два кроки: **рендер**, коли React викликає компоненти, і **коміт**, коли React вносить зміни в документ.
Ефект запускається наприкінці коміту. Цей компонент порівнює, що бачить тіло й що бачить ефект:

```tsx
function WhenRuns() {
  log.push('тіло: заголовок є? ' + (document.querySelector('h2') !== null))
  useEffect(() => {
    log.push('ефект: заголовок є? ' + (document.querySelector('h2') !== null))
  })
  return <h2>Табло</h2>
}
```

```text
тіло: заголовок є? false
ефект: заголовок є? true
```

Запис у журнал у тілі робить компонент нечистим, і так ми робимо лише заради цього досліду. Тіло виконується, поки
React ще не знає, яку розмітку ви повернете, тому заголовка немає. Ефект виконується вже після коміту, і заголовок у
документі є.

Чи встиг браузер намалювати нову сторінку до запуску ефекту, залежить від причини оновлення. Довідник `useEffect` у
розділі `Caveats` каже, що ефект, не спричинений взаємодією, зазвичай запускається після малювання, а ефект,
спричинений клацанням, може запуститися до нього. Лекція «Спільний стан і скидання стану» заміряла цю різницю в
браузері. Для синхронізації досить знати, що документ уже оновлено.

Функцію ефекту не можна робити `async`. Вона має повертати нічого або функцію прибирання, а `async`-функція повертає
проміс. Лекція «Асинхронність» згадувала цю межу, а компілятор її не пропускає. На запис `useEffect(async () => {...},
[word])` він друкує:

```text
error TS2345: Argument of type '() => Promise<void>' is not assignable to parameter of type 'EffectCallback'.
```

Тому асинхронну функцію пишуть усередині ефекту й одразу викликають. Це показано нижче в розділі про мережу.

## Залежності: коли ефект запускається знову

Без другого аргументу ефект запускається після кожного коміту. Для з'єднання це погано: кожна літера в полі нотатки
перепідключала б табло. Другий аргумент називають **списком залежностей**. Це масив значень, які ефект читає. React
порівнює кожне значення зі значенням попереднього рендеру функцією `Object.is` і запускає ефект знову, лише якщо хоч
одне змінилося.

Ось три варіанти одного компонента, який має ще поле нотатки у власному стані. Сценарій однаковий: показати матч
«кубок», ввести дві літери в нотатку, перейти на матч «ліга». Показано варіант зі списком `[matchId]`, а два інші
відрізняються лише останнім рядком ефекту:

```tsx
function WithList({ matchId }: { matchId: string }) {
  const [note, setNote] = useState('')
  useEffect(() => {
    const feed = createFeed(matchId)
    feed.open()
  }, [matchId])
  return <input aria-label="нотатка" value={note} onChange={(e) => setNote(e.target.value)} />
}
```

```text
без списку | open кубок, open кубок, open кубок, open ліга
порожній список | open кубок
[matchId] | open кубок, open ліга
```

| Запис | Коли запускається ефект | Що сталося тут |
|-------|-------------------------|----------------|
| `useEffect(fn)` | після кожного коміту | літери в нотатці запустили ефект ще двічі |
| `useEffect(fn, [])` | лише коли компонент з'явився | новий матч не відкрив нової стрічки, тому табло показує «ліга», а підключене до «кубка» |
| `useEffect(fn, [matchId])` | коли компонент з'явився і коли змінився `matchId` | одне відкриття на кожен матч |

Другий рядок таблиці показує найважливіше: порожній список не є способом сказати «запусти один раз». Це твердження, що
ефект не читає нічого, що може змінитися. Тут воно хибне, бо ефект читає `matchId`. Лінт вашого проєкту повідомляє про
це правилом `react-hooks/exhaustive-deps`, яке показувала лекція «Проєкт: Vite, лінт, TypeScript». Список залежностей
ви не обираєте на власний розсуд: його визначає код ефекту. Що робити, коли зайва залежність заважає, пояснює тема
«Залежності ефекту й власні хуки».

Об'єкт ref і функції `set` у список можна не писати. Сторінка `Synchronizing with Effects` пояснює причину: React
гарантує, що вони лишаються тими самими між рендерами, тому ніколи самі не запустять ефект. Лекція «Ref» показала, що
зміна поля `current` теж не запускає ефект, бо React її не помічає.

### Ефект, який запускає сам себе

Ефект запускається після рендеру, а запис у стан просить новий рендер. Якщо ефект без списку записує стан, виходить
цикл:

```tsx
function Endless() {
  const [count, setCount] = useState(0)
  useEffect(() => {
    if (count < 200) setCount(count + 1)
  })
  return <p>{count}</p>
}
```

```text
цикл | екран: 200 | повідомлень: 3 | перше: Maximum update depth exceeded. This can happen when a component calls setState inside useEffect, but useEffect either doesn't have a dependency array, or one of the dependencies changes on every render.
```

Умова `count < 200` стоїть лише заради досліду. Перша версія нашого досліду була без неї, і тест завис, поки ми його
не зупинили. Отже, React не обриває такий цикл винятком, а лише друкує повідомлення в консоль, і компонент продовжує
рендеритися. У браузері ми цього не запускали. Лінт заздалегідь повідомляє про такий запис двома правилами,
`exhaustive-deps` і `set-state-in-effect`.

## Прибирання: як скасувати зроблене

Додамо до нашого табло перехід на інший матч і зникнення. Спершу ефект без прибирання:

```tsx
function Leaky({ matchId }: { matchId: string }) {
  useEffect(() => {
    const feed = createFeed(matchId)
    feed.open()
  }, [matchId])
  return <h2>Матч {matchId}</h2>
}
```

```text
без прибирання: open кубок, open ліга | відкритих стрічок: 2
```

Компонента вже немає, а обидві стрічки досі відкриті. Програма тримає ресурс, який ніхто не використовує, і таку
помилку називають **витоком**. Лекція «Чистота й дерево» коротко показала це на таймері.

Щоб виправити витік, ефект повертає функцію, яку називають **функцією прибирання**. Вона скасовує те, що зробив цей
запуск ефекту:

```tsx
function Scoreboard({ matchId }: { matchId: string }) {
  useEffect(() => {
    const feed = createFeed(matchId)
    feed.open()
    return () => {
      feed.close()
    }
  }, [matchId])
  return <h2>Матч {matchId}</h2>
}
```

```text
з прибиранням: open кубок, close кубок, open ліга, close ліга | відкритих стрічок: 0
```

Простежимо цей журнал по кроках. Сценарій містить показ, повторний рендер із тим самим матчем, перехід на новий матч і
зникнення.

| Крок | Що зробив React | Що він порівняв | Що опинилося в журналі |
|------|-----------------|-----------------|------------------------|
| показ, матч «кубок» | запустив ефект | порівнювати нема з чим | `open кубок` |
| рендер, той самий матч | не запустив нічого | `кубок` і `кубок` однакові | нічого |
| рендер, матч «ліга» | викликав старе прибирання, потім новий ефект | `ліга` і `кубок` різні | `close кубок`, `open ліга` |
| компонент зник | викликав останнє прибирання | нічого | `close ліга` |

Отже, React викликає прибирання перед кожним наступним запуском ефекту й востаннє тоді, коли компонент зникає. На
третьому кроці зверніть увагу на порядок: спочатку прибирання старого запуску, а потім новий запуск. Тому одночасно
ніколи не живуть дві стрічки.

Чому прибирання закрило саме «кубок», хоч у пропсі вже лежить «ліга»? Лекція «Функції та замикання» пояснила, що
функція бачить змінні місця, де її створено. Кожен рендер створює власну функцію ефекту й власну функцію прибирання, і
вони замикають `feed` та `matchId` свого рендеру. Сторінка `Synchronizing with Effects` у блоці `Each render has its
own Effects` каже про це так: ефект є частиною результату рендеру.

Прибирання має дзеркально скасовувати те, що зробив ефект. Довідник `useEffect` у розділі `Troubleshooting` називає
прибирання без відповідного коду запуску поганою ознакою. Якщо вам хочеться написати «при зникненні зроби щось»,
перевірте, яку саме дію ефекту це скасовує.

## Навіщо `<StrictMode>` запускає ефект двічі

Лекція «Чистота й дерево» уже сказала, що `<StrictMode>` у розробці викликає тіло компонента двічі. З ефектами він
робить іншу перевірку: одразу після першої появи компонента React один раз виконує прибирання й запускає ефект знову.
Стан і вузли документа при цьому лишаються. Ось наші два варіанти табло в `<StrictMode>`:

```text
StrictMode, без прибирання, показ: open кубок, open кубок | відкритих стрічок: 2
StrictMode, з прибиранням, показ: open кубок, close кубок, open кубок | відкритих стрічок: 1
StrictMode, з прибиранням, новий матч: close кубок, open ліга | відкритих стрічок: 1
StrictMode, з прибиранням, зникнення: close ліга | відкритих стрічок: 0
```

Навіщо це потрібно? Уявіть, що людина зайшла на табло, пішла в налаштування й повернулася. Компонент зник і з'явився
знову, тому якщо прибирання немає, відкритих стрічок стане дві. Без перевірки таку помилку треба шукати довгими
переходами вручну. `<StrictMode>` імітує цей самий перехід одразу, тому помилка видна в першому рядку журналу.
Перевірка відбувається лише один раз, відразу після появи: при зміні матчу чи зникненні журнал такий самий, як без
обгортки.

Правило для правильного прибирання сформульоване на сторінці React так: людина не має відрізнити один запуск ефекту
від послідовності «запуск, прибирання, запуск». Тому в журналі з прибиранням число відкритих стрічок дорівнює одиниці,
і це те саме, що дав би один запуск.

Перевіримо це не в jsdom, а в браузері. У Chrome без вікна ми відкрили той самий компонент на сервері розробки Vite і
в зібраному застосунку через `vite preview`. У журнал сторінки потрапили такі рядки:

| Де працює застосунок | Рядки журналу | Чому так |
|----------------------|---------------|----------|
| сервер розробки | `open кубок`, `close кубок`, `open кубок` | React із перевірками розробки |
| `vite preview`, тобто зібраний застосунок | `open кубок` | у збірці React не робить цієї перевірки |

Обгортка `<StrictMode>` в обох випадках стояла навколо застосунку. Лекція «Чистота й дерево» також показала межу цієї
перевірки: цикл ефектів з'являється лише тоді, коли обгортка стоїть у корені застосунку. Сторінка React додає ще одне:
у розробці React запускає ефекти знову й тоді, коли ви зберігаєте файл. Цього ми окремо не перевіряли.

### Чому не варто вимикати перевірку

Подивіться, що станеться, якщо забрати обгортку з варіанта без прибирання:

```text
без StrictMode, без прибирання, показ: open кубок | відкритих стрічок: 1
без StrictMode, без прибирання, зникнення:  | відкритих стрічок: 1
```

Перший рядок виглядає правильно: одне відкриття. Другий рядок показує, що помилка нікуди не зникла, бо компонента
немає, а стрічка відкрита. Обгортка лише робила цю помилку видимою одразу. Вимкнути `<StrictMode>` означає прибрати
повідомлення про помилку, а не саму помилку.

Є й друга спокуса: не вимикати перевірку, а обійти її через ref. Сторінка React показує цей запис у розділі `Don't use
refs to prevent Effects from firing`, а ось він на нашому табло:

```tsx
function Guarded({ matchId }: { matchId: string }) {
  const feedRef = useRef<ReturnType<typeof createFeed> | null>(null)
  useEffect(() => {
    if (feedRef.current === null) {
      feedRef.current = createFeed(matchId)
      feedRef.current.open()
    }
  }, [matchId])
  return <h2>Матч {matchId}</h2>
}
```

```text
запобіжник у ref, показ: open кубок | відкритих стрічок: 1
запобіжник у ref, зникнення:  | відкритих стрічок: 1
запобіжник у ref, повернення: open кубок | відкритих стрічок: 2
запобіжник у ref, новий матч:  | відкритих стрічок: 2
```

Перший рядок задовольняє того, хто дивиться лише на подвійний журнал. Під час перевірки `<StrictMode>` ref
зберігається, тому `open` спрацював один раз. Проте компонент зник, не закривши стрічку, а новий показ створив новий
ref і нову стрічку. Останній рядок ще гірший: матч змінився, а ефект нічого не зробив, тому табло лишилося підключеним
до старого матчу.

## Таймер, який пережив компонент

Практика дня «Ref» лишила відкрите запитання: її секундомір не зупиняється, коли компонент зникає. Подивимося, як це
розв'язує прибирання, на іншому об'єкті. Слайд-шоу має кнопки «пуск» і «стоп» та перемикає слайд щосекунди. Перший
варіант тримає ідентифікатор таймера в ref і нічого більше не робить, як навчила та лекція:

```tsx
function SlidesLeaky() {
  const [slide, setSlide] = useState(0)
  const timerRef = useRef<ReturnType<typeof setInterval> | null>(null)
  function play() {
    timerRef.current = setInterval(() => {
      ticks++
      setSlide((s) => s + 1)
    }, 1000)
  }
  function pause() {
    if (timerRef.current !== null) clearInterval(timerRef.current)
  }
  return (
    <>
      <p role="status">Слайд {slide}</p>
      <button onClick={play}>пуск</button>
      <button onClick={pause}>стоп</button>
    </>
  )
}
```

Є два способи виправити це прибиранням. Перший спосіб змінює саму думку: таймер працює не тому, що натиснули кнопку, а
тому, що компонент на екрані в стані «грає». Кнопки лише змінюють стан, а таймером керує ефект:

```tsx
function SlidesEffect() {
  const [slide, setSlide] = useState(0)
  const [playing, setPlaying] = useState(false)
  useEffect(() => {
    if (!playing) return
    const timerId = setInterval(() => {
      ticks++
      setSlide((s) => s + 1)
    }, 1000)
    return () => {
      clearInterval(timerId)
    }
  }, [playing])
  return (
    <>
      <p role="status">Слайд {slide}</p>
      <button onClick={() => setPlaying(true)}>пуск</button>
      <button onClick={() => setPlaying(false)}>стоп</button>
    </>
  )
}
```

Ref тут не потрібен, бо ідентифікатор лежить у змінній запуску ефекту, а прибирання її замикає. Рядок `if (!playing)
return` виходить без функції прибирання, бо зупиняти нічого. Клацання «стоп» змінює `playing`, тому React викликає
прибирання, а компонент, що зникає, викликає його теж. Запис `setSlide((s) => s + 1)` бере поточне значення з функції
оновлення, тому `slide` не потрапляє в список залежностей, а зміна слайда не перезапускає таймер.

Другий спосіб лишає обробники й ref, а додає ефект, який лише прибирає:

```tsx
function SlidesRefCleanup() {
  const [slide, setSlide] = useState(0)
  const timerRef = useRef<ReturnType<typeof setInterval> | null>(null)
  function play() {
    if (timerRef.current !== null) clearInterval(timerRef.current)
    timerRef.current = setInterval(() => {
      ticks++
      setSlide((s) => s + 1)
    }, 1000)
  }
  function pause() {
    if (timerRef.current !== null) clearInterval(timerRef.current)
  }
  useEffect(() => {
    return () => {
      if (timerRef.current !== null) clearInterval(timerRef.current)
    }
  }, [])
  return (
    <>
      <p role="status">Слайд {slide}</p>
      <button onClick={play}>пуск</button>
      <button onClick={pause}>стоп</button>
    </>
  )
}
```

Перед новим запуском обробник зупиняє попередній таймер: ця пастка показана в лекції «Ref». Тест запускає всі три
варіанти в `<StrictMode>` зі штучними таймерами, клацає «пуск», чекає три секунди, прибирає компонент і чекає ще три
секунди. Змінна `ticks` рахує спрацювання:

```text
лише ref | за 3 с: 3, Слайд 3 | компонент зник, ще за 3 с: 6 | попереджень React: 0
ефект і стан playing | за 3 с: 3, Слайд 3 | компонент зник, ще за 3 с: 3 | попереджень React: 0
ref і прибирання | за 3 с: 3, Слайд 3 | компонент зник, ще за 3 с: 3 | попереджень React: 0
```

Перший рядок є причиною, чому ця помилка так легко лишається. Таймер спрацював іще тричі для компонента, якого немає,
а React не надрукував жодного попередження про виклик `set`. Екран теж нічого не покаже, бо компонента немає. Помилку
видно лише тоді, коли ви рахуєте спрацювання в тесті.

Який спосіб обрати? Перший спосіб кращий, якщо таймер справді описує стан компонента, бо запуск і зупинка лежать поруч
в одному місці й окремий ref не потрібен. Другий спосіб підходить, коли таймером уже керують обробники й ви лише
додаєте зупинку під час зникнення. Вирішуйте самі для свого секундоміра: у ньому є ще й час, який рахують різницею
двох моментів, а цього слайд-шоу не показує.

Якщо ефект запускає таймер сам, без кнопки, `<StrictMode>` викриває відсутнє прибирання одразу, навіть без зникнення
компонента:

```text
автозапуск, без прибирання, StrictMode | за 3 с спрацювань: 6, Слайд 6
автозапуск, з прибиранням, StrictMode | за 3 с спрацювань: 3, Слайд 3
```

Два таймери перемикають слайди вдвічі швидше. Цю саму помилку розбирає вправа `Fix an interval that fires twice` на
сторінці React.

### Кожен рендер має власний таймер

Прибирання дає ще одну корисну поведінку. Автозбереження має записати чернетку через три секунди після останньої
літери, а не після кожної:

```tsx
function AutoSave({ save }: { save: (t: string) => void }) {
  const [text, setText] = useState('')
  useEffect(() => {
    const timerId = setTimeout(() => save(text), 3000)
    return () => {
      clearTimeout(timerId)
    }
  }, [text, save])
  return <textarea aria-label="чернетка" value={text} onChange={(e) => setText(e.target.value)} />
}
```

Людина вводить чотири літери з проміжком пів секунди, а потім чекає:

```text
автозбереження, без прибирання | збережено: "", "к", "ка", "кав", "кава"
автозбереження, з прибиранням | збережено: "кава"
```

Кожна літера змінює `text`, а отже React прибирає попередній таймер, поки той не спрацював. У варіанті без прибирання
кожен таймер спрацював і зберіг значення свого рендеру. Рядок показує, що замикання справді тримає значення рендеру,
який створив ефект, а не найновіше значення.

## Інші зовнішні системи

Майже кожен ефект належить до одного з кількох видів. Сторінка `Synchronizing with Effects` розбирає їх у розділі `How
to handle the Effect firing twice in development`.

| Що робить ефект | Що робить прибирання | Приклад |
|-----------------|----------------------|---------|
| підключається | відключається | наше табло |
| підписується на подію | відписується | подія `resize` вікна |
| запускає таймер | зупиняє таймер | слайд-шоу |
| показує діалог браузера | закриває діалог | `<dialog>` |
| запускає анімацію | повертає початкове значення | прозорість елемента |
| передає значення віджету, і повторна передача нічого не змінює | прибирання не потрібне | рівень масштабу на карті |
| завантажує дані | ігнорує або скасовує відповідь | наступний розділ |

**Підписка.** Функція `removeEventListener` прибирає підписку лише тоді, коли отримала ту саму функцію, яку отримала
`addEventListener`. Ось правильний запис:

```tsx
function WidthGood() {
  const [width, setWidth] = useState(window.innerWidth)
  useEffect(() => {
    function handleResize() {
      calls++
      setWidth(window.innerWidth)
    }
    window.addEventListener('resize', handleResize)
    return () => {
      window.removeEventListener('resize', handleResize)
    }
  }, [])
  return <p role="status">{width}</p>
}
```

Поруч ми запустили варіант, де в обох викликах стоїть стрілка з однаковим текстом. Кожна стрілка створює окрему
функцію, а функція є об'єктом, тому браузер порівнює посилання, як пояснила лекція «Значення й посилання». Посилання
різні, отже, підписка лишається:

```text
підписка, одна функція | викликів на одну подію: 1 | після зникнення: 0
підписка, дві однакові на вигляд функції | викликів на одну подію: 2 | після зникнення: 2
```

Компонент зник, а обидві підписки лишилися, і компілятор та лінт нічого про це не кажуть.

**Вузол документа.** Лекція «Ref» обіцяла місце, де можна прочитати вузол без події. Це ефект, бо на момент його
запуску React уже поклав вузол у `ref.current`. Ось компонент, який показує діалог браузера:

```tsx
function ConfirmDialog({ text }: { text: string }) {
  const dialogRef = useRef<HTMLDialogElement>(null)
  useEffect(() => {
    const dialog = dialogRef.current
    dialog?.showModal()
    return () => {
      dialog?.close()
    }
  }, [])
  return <dialog ref={dialogRef}>{text}</dialog>
}
```

У jsdom немає методу `showModal`, тому ми запустили цей код у Chrome без вікна на сервері розробки з `<StrictMode>`.
Журнал показав таку послідовність: `showModal, open=true`, `close, open=false`, `showModal, open=true`. Після цього
діалог лишився відкритим, тобто людина побачила той самий результат, що й після одного запуску.

Рядок `const dialog = dialogRef.current` стоїть не для краси. Коли компонент зникає, React очищує ref раніше, ніж
викликає прибирання:

```text
прибирання, змінна: P, ref.current: null
```

Цей рядок надрукував інший маленький компонент, який має абзац із ref. Отже, прибирання має користуватися вузлом, який
ефект запам'ятав у своїй змінній, а не читати `ref.current` заново. Лінт нагадує про це правилом
`react-hooks/exhaustive-deps` словами `The ref value 'boxRef.current' will likely have changed by the time this effect
cleanup function runs`. У слайд-шоу вище такої проблеми немає, бо там `timerRef` тримає ваш ідентифікатор, а React
цього поля не чіпає.

Сторінка React пояснює прибирання діалогу тим, що `showModal` кидає виняток, якщо викликати його двічі. У Chrome 156
цього вже не сталося: другий виклик на відкритому модальному діалозі нічого не зробив і не кинув винятку, а виняток
`InvalidStateError` прийшов лише тоді, коли діалог перед цим відкрили методом `show()`. Інших браузерів ми не
запускали. Прибирання все одно лишайте: запуск і скасування стають дзеркальними, а якщо ефект залежить від пропса, без
прибирання діалог не закриється, коли пропс зміниться.

### Що не є ефектом

Прибирання допомагає не завжди, і тоді це підказка, що код стоїть не там. Покупка квитка не скасовується прибиранням,
а лист або платіж не можна «відіслати назад». Порівняємо ефект і обробник:

```tsx
function BuyInEffect({ post }: { post: (u: string) => void }) {
  useEffect(() => {
    post('/api/tickets')
  }, [post])
  return <h2>Квиток</h2>
}
```

```text
купівля в ефекті, показ у StrictMode | запитів: 2
купівля в ефекті, людина повернулася на сторінку | запитів: 4
купівля в обробнику, показ | запитів: 0
купівля в обробнику, клацання | запитів: 1
```

Подвоєння на першому рядку викриває не недолік React, а помилку задуму. Купує людина кнопкою, а не показом сторінки,
тому людина, яка просто повернулася на сторінку, купила б квиток удруге навіть у збірці. Тому запит треба перенести в
обробник.

Сторінка React називає ще два окремі випадки. Звіт про відвідування сторінки може лишитися в ефекті, бо він
спричинений показом сторінки, а подвійний запис у розробці не шкодить людині. Код, який має виконатися один раз за
запуск застосунку, наприклад перевірка токена, стоїть поза компонентами на верхньому рівні модуля. Докладно про такі
випадки говорить лекція «Коли ефект не потрібен».

## Запит у мережу

Лекція «Мережа» пояснила гонку й скасування без React. Тепер поставимо їх в ефект. Картка слова показує значення
слова, яке вибрала людина. Функція `fetchWord` замінює справжній `fetch`: для слова «кіт» відповідь іде 800 мс, для
слова «пес» 100 мс.

```tsx
function WordNoCleanup({ word }: { word: string }) {
  const [entry, setEntry] = useState<Entry | null>(null)
  useEffect(() => {
    fetchWord(word).then(setEntry)
  }, [word])
  return <p role="status">{word}: {entry ? entry.meaning : 'завантаження'}</p>
}
```

Ця картка виглядає правильно, бо ефект запускається при кожній зміні слова. Людина вибирає «кіт», а через 50 мс
вибирає «пес»:

```text
без прибирання | 150 мс: пес: тварина, яка гавкає
без прибирання | 1150 мс: пес: тварина, яка нявкає
```

| Час | Що сталося | Що на екрані |
|-----|------------|--------------|
| 0 мс | вибрано «кіт», пішов запит про кота | `кіт: завантаження` |
| 50 мс | вибрано «пес», пішов запит про пса | `пес: завантаження` |
| 150 мс | прийшла відповідь про пса | `пес: тварина, яка гавкає` |
| 800 мс | прийшла відповідь про кота, і `setEntry` її записав | `пес: тварина, яка нявкає` |

Останній рядок є гонкою: на екрані залишаються дані не того слова, і нічого вже не виправить їх, поки людина не вибере
щось інше. Ми запустили таку саму гонку зі справжнім `fetch` у Chrome без вікна, а сервер відповідав із такими самими
затримками. У журналі після відповіді про пса теж прийшла відповідь про кота, яка перезаписала стан.

### Прапорець `ignore`

Функція прибирання не може забрати відповідь назад, але може сказати цьому запуску ефекту, що його результат більше не
потрібен:

```tsx
function WordIgnore({ word }: { word: string }) {
  const [entry, setEntry] = useState<Entry | null>(null)
  useEffect(() => {
    let ignore = false
    async function load() {
      const found = await fetchWord(word)
      if (!ignore) {
        setEntry(found)
      }
    }
    load()
    return () => {
      ignore = true
    }
  }, [word])
  return <p role="status">{word}: {entry ? entry.meaning : 'завантаження'}</p>
}
```

Розгляньмо рядки по черзі.

- `let ignore = false` створює змінну цього запуску ефекту. Кожен запуск має власну копію, бо ефект є окремим викликом
  функції.
- `async function load()` оголошує асинхронну функцію всередині ефекту, бо сам ефект асинхронним бути не може.
- `if (!ignore)` виконується після `await`, тобто вже тоді, коли прийшла відповідь. На цей момент змінна могла
  змінитися.
- `ignore = true` виконує прибирання. Воно змінює ту змінну, яку замкнула саме ця функція `load`, а інших запусків не
  чіпає.

```text
прапорець ignore | 150 мс: пес: тварина, яка гавкає
прапорець ignore | 1150 мс: пес: тварина, яка гавкає
```

Відповідь про кота так само прийшла на 800 мс, але її запуск ефекту вже мав `ignore === true`, тому `setEntry` не
виконався. Сторінка React робить ще одне зауваження: у розробці ви побачите два запити у вкладці Network, і це
нормально, бо це наслідок тієї самої перевірки `<StrictMode>`:

```text
StrictMode, ignore | запитів: 2 | на екрані: пес: тварина, яка гавкає
```

Сторінка рекомендує не боротися з подвоєнням, а за потреби користуватися рішенням із кешем. Про кеш запитів ідеться у
фазі 3.

### `AbortController`

Прапорець не скасовує самого запиту: браузер далі чекає на відповідь, яка нікому не потрібна. Лекція «Мережа» пояснила
об'єкт `AbortController`: метод `abort()` повідомляє сигнал `signal`, а `fetch`, який отримав цей сигнал, обриває
очікування й відхиляє проміс із помилкою на ім'я `AbortError`. Прибирання є природним місцем для цього виклику:

```tsx
function WordAbort({ word }: { word: string }) {
  const [entry, setEntry] = useState<Entry | null>(null)
  useEffect(() => {
    const controller = new AbortController()
    fetchWord(word, controller.signal)
      .then(setEntry)
      .catch((e) => {
        if (e.name === 'AbortError') {
          log.push('скасовано: ' + word)
        } else {
          throw e
        }
      })
    return () => {
      controller.abort()
    }
  }, [word])
  return <p role="status">{word}: {entry ? entry.meaning : 'завантаження'}</p>
}
```

```text
AbortController | 150 мс: пес: тварина, яка гавкає
AbortController | 1150 мс: пес: тварина, яка гавкає
AbortController | журнал: скасовано: кіт
```

Обробник `.catch` тут обов'язковий. Скасування для промісу є звичайним відхиленням, тому без обробника браузер
повідомляє про невідхоплену помилку. Це ми перевірили в Chrome: компонент зі скасуванням без `.catch` у розробці дав
подію `unhandledrejection` з помилкою `AbortError`, бо перевірка `<StrictMode>` скасувала перший запит одразу.
Справжню помилку мережі, навпаки, ховати не можна, тому обробник відрізняє скасування від неї за назвою.

Лекція «Мережа» попереджала, що скасування не відкочує зробленого на сервері. У нашому запуску в Chrome сервер отримав
запит про кота, хоча клієнт скасував його через 50 мс. Для читання це не страшно, а для запиту, що змінює дані, ця
обставина вирішальна.

### Чому самого контролера недостатньо

Сторінка React у розв'язку вправи `Fix fetching inside an Effect` каже, що `AbortController` сам не захищає від гонки,
бо після запиту можуть іти інші асинхронні кроки. Перевірмо це. Картка тепер після відповіді сервера ще додає приклади
вживання функцією `addExamples`, а ця функція сигналу не отримує:

```tsx
function WordAbortChain({ word }: { word: string }) {
  const [entry, setEntry] = useState<Entry | null>(null)
  useEffect(() => {
    const controller = new AbortController()
    fetchWord(word, controller.signal)
      .then(addExamples)
      .then(setEntry)
      .catch((e) => {
        if (e.name !== 'AbortError') throw e
      })
    return () => {
      controller.abort()
    }
  }, [word])
  return <p role="status">{word}: {entry ? entry.meaning : 'завантаження'}</p>
}
```

Людина вибирає «кіт», чекає 850 мс, поки сервер уже відповів, і вибирає «пес», поки для кота ще підбираються приклади.
Поруч стоїть такий самий ланцюжок із прапорцем замість контролера:

```text
другий крок, лише AbortController | 1100 мс: пес: тварина, яка гавкає (з прикладами)
другий крок, лише AbortController | 2100 мс: пес: тварина, яка нявкає (з прикладами)
другий крок, прапорець ignore | 1100 мс: пес: тварина, яка гавкає (з прикладами)
другий крок, прапорець ignore | 2100 мс: пес: тварина, яка гавкає (з прикладами)
```

Виклик `abort()` прийшов, коли `fetchWord` уже завершився, тому сигнал нікому було слухати, а `addExamples` дійшла до
кінця й передала результат далі. Прапорець перевіряється в останню мить перед записом, тому йому байдуже, скільки
кроків було до цього.

| Що порівнюємо | Прапорець `ignore` | `AbortController` |
|---------------|--------------------|-------------------|
| чи зупиняє запис застарілої відповіді в стан | так, завжди | лише поки сигнал слухає той крок, який зараз виконується |
| чи економить трафік і роботу браузера | ні, відповідь усе одно приходить | так, очікування обривається |
| чи скасовує дію на сервері | ні | ні |
| що ще потрібно | нічого | обробник `.catch` для `AbortError` |

Ці два засоби відповідають на різні запитання, тому практика дня просить обидва: прапорець гарантує, що застаріле не
потрапить у стан, а контролер прибирає непотрібний запит. Як поєднати їх в одному ефекті, вирішіть самі, а цю таблицю
використайте для перевірки.

### Стара відповідь, поки нова в дорозі

Є ще одна пастка, яку прапорець не розв'язує. Прапорець не дає пізній відповіді перезаписати нову, але в стані й далі
лежить попередня відповідь. Вона лежить там увесь час, поки нова ще йде. Ось сценарій: людина дивиться на картку пса,
вибирає кота, а його відповідь іде 800 мс. Рядок записує, що було на екрані через 100 мс після перемикання:

```text
лише ignore | відповідь на екрані: пес: тварина, яка гавкає | через 100 мс після перемикання: кіт: тварина, яка гавкає | коли прийшла нова: кіт: тварина, яка нявкає
порівняння зі словом | відповідь на екрані: пес: тварина, яка гавкає | через 100 мс після перемикання: кіт: завантаження | коли прийшла нова: кіт: тварина, яка нявкає
key | відповідь на екрані: пес: тварина, яка гавкає | через 100 мс після перемикання: кіт: завантаження | коли прийшла нова: кіт: тварина, яка нявкає
```

Перший рядок показує кота, який гавкає. Жодна гонка тут не сталася, і запис `ignore` стоїть правильно, проте екран
показує чужі дані вже 800 мс. Перевірка вашого дня саме про це: під час швидкого перемикання на екрані не мають
з'являтися дані іншої кімнати. Є два способи це виправити, і обидва вже відомі.

Перший спосіб зберігає відповідь разом зі словом, якому вона належить, а під час рендеру порівнює слово. Лекція
«Структура стану» вчила не зберігати те, що можна обчислити, тому окремого стану «завантаження» тут немає:

```tsx
const shown = entry !== null && entry.word === word ? entry : null
```

Другий спосіб передає слово як ключ, щоб кожне слово мало окремий компонент із порожнім станом. Це той самий прийом,
що в лекції «Спільний стан і скидання стану»:

```tsx
function WordPage({ word }: { word: string }) {
  return <WordIgnore key={word} word={word} />
}
```

Під час зміни ключа старий компонент зникає, тому React викликає його прибирання, і прапорець у ньому стає `true`.

Запис стану прямо в тілі ефекту для цього не підходить. Спокуса велика: написати `setLoading(true)` на початку ефекту.
Лінт вашого проєкту таке не пропускає, а сторінка правила `set-state-in-effect` прямо називає цей запис помилкою:

```text
7:5  error  Error: Calling setState synchronously within an effect can trigger cascading renders
```

Запис стану пізніше, у `.then` чи після `await`, правило дозволяє: він спричинений відповіддю зовнішньої системи. У
всіх варіантах вище `setEntry` стоїть саме так, і лінт мовчить.

Лекція «Стан як набір станів екрана» показала запізнілу відповідь як межу свого опису й пообіцяла повернутися до неї.
Тепер ви знаєте механізм: прибирання відсікає таку відповідь. Описи станів екрана з тієї лекції лишаються чинними,
тому помилка мережі й порожня відповідь потребують власних станів.

Сторінка React у блоці `What are good alternatives to data fetching in Effects?` перелічує межі такого завантаження:
ефекти не працюють на сервері, вкладені компоненти чекають один одного, а кешу немає. Для проєктів вона радить готове
рішення. У вашому плані це фаза 3.

## Як побачити різницю між розробкою і збіркою

Лекція «Інструменти браузера» пояснила, чому збірка працює на версії React без перевірок: команда `vite build`
підставляє рядок `"production"` замість `process.env.NODE_ENV`, а мінімізатор викидає гілку розробки. Команда `vite
preview` запускає локальний сервер, який віддає те, що лежить у теці `dist`. Документація Vite застерігає, що це не
сервер для справжньої роботи.

Отже, порівняння складається з двох запусків: `npm run dev` і відкрита сторінка, а потім `npm run build`, `npm run
preview` і та сама сторінка. Звідси випливають дві пастки.

**Збірка не оновлюється сама.** Команда `vite preview` віддає останню збірку. Якщо ви змінили код і не запустили `npm
run build`, то побачите старий журнал і вирішите, що зміна не спрацювала.

**Окрема сторінка уроку не потрапляє в збірку.** За замовчуванням `vite build` збирає лише `index.html`. Практики
цього плану мають окремі сторінки на зразок `/f1-d15.html`, і сервер розробки їх віддає, а збірка ні. Ми це
перевірили: додали до тестового проєкту другий файл сторінки, зібрали проєкт і відкрили цю адресу через `vite
preview`. У теці `dist` лежав лише один файл сторінки:

```text
dist/index.html
```

Сервер не повідомив про помилку, а віддав замість сторінки уроку вміст `index.html`. Журнал тоді належав би зовсім
іншому коду. Документація Vite у розділі `Multi-Page App` описує налаштування `build.rolldownOptions.input`, яке
перелічує всі сторінки для збірки. Ми перевірили його на версії Vite 8, і другий файл з'явився в `dist`. Інший шлях є
простішим: на час порівняння показати компонент дня зі звичайної точки входу `src/main.tsx`. У будь-якому разі
перевірте, що на екрані справді ваш компонент.

Журнал дивіться в консолі браузера, а запити у вкладці Network, яку показала лекція «Інструменти браузера». У нашому
запуску в Chrome тестова сторінка з чотирма компонентами, які роблять запити, у розробці надіслала на сервер 10
запитів, а в збірці 7. Різницю дала перевірка `<StrictMode>`, яка запустила перші запити ще раз.

## Ефекти й рецепт

Практика цього плану йде за рецептом книжки How to Design Programs. Рецепт вимагає прикладів із відомим результатом, а
вони можливі для функцій, які обчислюють значення. Ефект є дією, а не обчисленням, тому його результат не запишеш
рівністю. Лекція «Ref» уже дала правило, яке діє й тут: те, що можна обчислити, виносьте в чисту функцію з прикладами,
а дію перевіряйте тестом компонента.

Для ефекту такий тест перевіряє журнал дій. Функція `render` бібліотеки Testing Library дочікується ефектів, тому
після неї журнал уже заповнений, а виклик `unmount` запускає прибирання. Зовнішню систему ви заміняєте маленьким
об'єктом, як `createFeed` у цій лекції, а час заміняєте штучними таймерами Vitest. Найкорисніший приклад ставить
компонент у `<StrictMode>`, бо там видно відсутнє прибирання. Vitest запускає React у режимі розробки, тому
один-єдиний запуск ефекту в режимі збірки тест у Vitest не покаже, і саме для цього існує ручне порівняння через `vite
preview`.

## Типові хибні уявлення

**«Ефект є кодом, який виконується один раз, коли компонент з'являється».** Ефект описує синхронізацію зі значеннями,
які він читає. Поки компонент на екрані, він може запускатися багато разів, і докладніше про це йдеться в темі
«Життєвий цикл ефекту й події поза ним».

**«Порожній список означає "запустити один раз"».** Це твердження, що ефект нічого реактивного не читає. Якщо читає,
то після зміни значення він лишиться підключеним до старого. У досліді табло показувало один матч, а стрічка була
відкрита до іншого.

**«Подвійний запуск у розробці є помилкою React, тому `<StrictMode>` треба вимкнути».** Перевірка лише показує, де
бракує прибирання. Без неї витік нікуди не дінеться: наш варіант без обгортки показав один `open` і лишив стрічку
відкритою після зникнення.

**«Запобіжник у ref усуває подвійний запуск, отже, проблему розв'язано».** Він прибирає лише рядок у журналі.
Компонент після повернення відкрив другу стрічку, а зміна матчу взагалі не спрацювала.

**«Прибирання виконується, лише коли компонент зникає».** Воно виконується і перед кожним наступним запуском ефекту,
зі значеннями старого рендеру.

**«`AbortController` повністю розв'язує гонку».** Він спрацьовує лише на тому кроці, який слухає сигнал. У нашому
запуску другий крок довів застарілу відповідь до екрана.

**«Прапорець `ignore` гарантує, що екран показує правильні дані».** Прапорець відсікає лише пізні відповіді. Попередня
відповідь лежить у стані, поки не прийде нова, тому без порівняння зі словом чи без `key` екран показує чужі дані.

**«Клієнт скасував запит, отже, сервер нічого не отримав».** Запит про кота в Chrome дійшов до сервера, хоч клієнт
його скасував. Скасування обриває очікування, а не дію на сервері.

**«React попередить мене про таймер, що працює після зникнення компонента».** У нашому запуску таймер спрацював іще
тричі, а React не надрукував жодного попередження.

## Як це проявиться далі в React

- **Тема «Коли ефект не потрібен».** Ви навчилися писати ефект, а наступний день учить його не писати. Перевірка там
  та сама: чи є зовнішня система?
- **Тема «Життєвий цикл ефекту й події поза ним».** Там ви побачите, чому ефект перезапускається лише через значення,
  які читає, і що робити, коли значення треба прочитати, але перезапуск через нього не потрібен.
- **Тема «Залежності ефекту й власні хуки».** Там з'ясується, чому об'єкт, створений у тілі компонента, перезапускає
  ефект на кожному рендері, і як винести повторювану логіку ефекту у власний хук.
- **Фаза 2, заміри.** Вона міряє швидкість лише на збірці, бо розробка повільніша й подвоює роботу через
  `<StrictMode>`. Сьогоднішнє порівняння журналів є першим досвідом такої різниці.
- **Фаза 3, дані.** Там бібліотека бере на себе гонки, кеш і повторні спроби. Ви зможете читати її помилки, бо
  знатимете, яку саме задачу вона розв'язує.

## Перевірте себе

**1. Чому не можна відкривати з'єднання в тілі компонента або в обробнику клацання, якщо воно потрібне весь час, поки
компонент на екрані?**

<details><summary>Відповідь</summary>

Тіло має лише обчислювати розмітку, а React вправі викликати його будь-скільки: у нашому запуску три рендери відкрили
три стрічки. Обробник запускається лише від конкретної дії людини, а компонент може з'явитися без жодного клацання,
наприклад за посиланням. Причиною дії є показ компонента, тому це ефект.

</details>

**2. Ефект читає `matchId`, а список залежностей порожній. Що станеться, коли матч зміниться, і хто про це
попередить?**

<details><summary>Відповідь</summary>

Ефект не запуститься знову, тому компонент лишиться підключеним до старого матчу, а заголовок на екрані вже покаже
новий. Під час виконання помилки не буде. Лінт повідомить про це правилом `react-hooks/exhaustive-deps`.

</details>

**3. Журнал без `<StrictMode>` показав `open кубок`, потім матч змінився на «ліга». Який порядок записів дає ефект із
прибиранням? Чому прибирання закриває саме «кубок»?**

<details><summary>Відповідь</summary>

Порядок такий: `open кубок`, `close кубок`, `open ліга`. React спочатку викликає прибирання старого запуску, а потім
новий ефект. Прибирання замикає змінну `feed` того рендеру, у якому його створено, тому закриває стрічку «кубок», хоч
у новому рендері пропс уже інший.

</details>

**4. Колега каже: «Я прибрав `<StrictMode>`, і подвійний лог зник, тож тепер усе добре». Що ви йому відповісте?**

<details><summary>Відповідь</summary>

Подвійний лог лише показував проблему. Якщо прибирання немає, то після переходу на інший екран і назад з'єднань стане
два, але тепер це видно лише під час ручної перевірки. Потрібно додати прибирання й лишити обгортку. Правильний журнал
у розробці має вигляд «запуск, прибирання, запуск», а в збірці лишається один запуск.

</details>

**5. Слайд-шоу запускається клацанням, ідентифікатор таймера лежить у ref, а компонент зникає. Що станеться і як це
виправити двома способами?**

<details><summary>Відповідь</summary>

Таймер працюватиме далі, бо ним керує браузер, а React не надрукує попередження. Перший спосіб: зберігати в стані, чи
грає показ, і запускати таймер в ефекті зі списком `[playing]`, а прибирання зупинятиме його. Другий спосіб: лишити
обробники й додати ефект із порожнім списком, чиє прибирання зупиняє таймер із ref.

</details>

**6. Навіщо потрібен прапорець `ignore`, якщо є `AbortController`?**

<details><summary>Відповідь</summary>

Контролер скасовує лише той крок, який слухає його сигнал. Якщо після запиту йде ще один асинхронний крок без сигналу,
застарілий результат дійде до запису в стан. Прапорець перевіряють безпосередньо перед записом, тому він спрацьовує
незалежно від кількості кроків. Контролер водночас потрібен, щоб не чекати непотрібної відповіді.

</details>

**7. Ефект має прапорець `ignore`, гонки немає, але після вибору іншого слова екран якийсь час показує нове слово зі
значенням старого. Чому і що з цим робити?**

<details><summary>Відповідь</summary>

Прапорець не очищує стан, тому попередня відповідь лежить там, поки не прийде нова. Можна зберігати відповідь разом зі
словом і під час рендеру порівнювати їх, або передати слово як `key`, щоб кожне слово мало окремий компонент із
порожнім станом. Виклик `setEntry(null)` прямо в тілі ефекту лінт не пропустить.

</details>

**8. Ви запустили `vite preview` і бачите журнал без змін, хоч змінили код. Назвіть дві ймовірні причини.**

<details><summary>Відповідь</summary>

Перша причина: ви не запустили `npm run build`, а `vite preview` віддає останню збірку. Друга причина: ваш компонент
лежить на окремій сторінці, якої немає в збірці, бо за замовчуванням збирається лише `index.html`, і сервер віддає її
замість сторінки уроку.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| ефект | код, який React запускає наприкінці коміту, щоб узгодити компонент із системою поза React |
| зовнішня система | усе, чим React не керує: мережа, таймер, подія вікна, сторонній віджет |
| синхронізація | узгодження зовнішньої системи з поточними пропсами й станом компонента |
| список залежностей | другий аргумент `useEffect`, значення, зміна яких вимагає запустити ефект знову |
| функція прибирання | функція, яку повертає ефект; вона скасовує зроблене цим запуском ефекту |
| витік | ресурс, який програма тримає, хоч його вже ніхто не використовує |
| гонка | ситуація, у якій результат залежить від порядку прибуття відповідей |
| прапорець `ignore` | змінна запуску ефекту, яку прибирання ставить у `true`, щоб результат цього запуску не потрапив у стан |
| `AbortController` | об'єкт браузера, який скасовує очікування на запит через свій сигнал |
| `vite preview` | локальний сервер, який віддає останню збірку з теки `dist` |
