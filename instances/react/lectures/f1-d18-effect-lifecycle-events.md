# Лекція. Фаза 1, день 18. Життєвий цикл ефекту й події поза ним

Тема «Синхронізація ефектами» показала, як написати ефект і прибирання, а ця лекція пояснює, коли React його
перезапускає. Ви побачите, чому ефект не можна уявляти через появу й зникнення компонента, що таке реактивне значення,
і як прочитати в ефекті свіже значення так, щоб ефект через нього не перезапускався. Читання займе близько 45 хвилин.

Приклади запущено на React 19.3 у Vitest під jsdom, тобто в імітації браузера всередині Node. Вивід під прикладами
справжній. Типи перевірено компілятором `tsc` версії 6.0, а лінт перевірено ESLint із тим самим набором правил
`react-hooks`, що й у проєкті `spa`. У справжньому браузері приклади не запускалися, але сьогоднішній механізм
належить React і браузера майже не стосується.

Застереження про версію компілятора: у перших лекціях про TypeScript команда `tsc` мала версію 7, а в проєкті `spa`
вона має версію 6.0. Це вимушене обмеження через ESLint. ESLint читає файли TypeScript через пакет
`typescript-eslint`, а цей пакет у версії 8.72 працює лише з TypeScript, нижчим за 6.1. Тому версію TypeScript у `spa`
закріплено на 6.0. Коли `typescript-eslint` запрацює з TypeScript 7, обмеження можна буде зняти.

Практика дня просить зробити вибір кімнати чату й перемикач теми сповіщень. Щоб не показувати готового розв'язку,
лекція бере інший об'єкт: сторінку, яка стежить за кур'єром, номер замовлення й одиниці відстані.

**Після лекції ви зможете пояснити:**

- чим життєвий цикл компонента відрізняється від життєвого циклу ефекту;
- у якому порядку React виконує рендер, старе прибирання й нове тіло ефекту;
- як React вирішує, чи перезапускати ефект, і що означають відсутній масив, порожній масив і масив зі значеннями;
- які значення реактивні, які ні й чому `ref.current` не можна записати в список залежностей;
- чому два незалежні процеси пишуть двома ефектами;
- чому зміна нереактивної дрібниці перепідключала ефект і чому вимкнений лінт цього не лікує;
- що робить `useEffectEvent`, де його можна викликати й де він ховає помилку;
- коли значення передають у подію ефекту аргументом, а коли читають усередині неї.

## Скарга: «ефект перепідключається, коли не треба»

Сторінка показує, де зараз кур'єр. Вона відкриває канал до служби доставки за номером замовлення, а служба щораз
надсилає відстань у кілометрах. Коли приходить нова відстань, сторінка показує сповіщення, і користувач може обрати
для сповіщень кілометри чи милі.

Служба доставки існує поза React, тому код до неї звертається з ефекту. Функція `createTracking` створює канал, метод
`open` відкриває його, `close` закриває, а `onPosition` задає функцію, яку канал викличе при новій відстані. Методи
`open` і `close` пишуть рядок у журнал, тож ми бачимо кожне підключення.

Усі досліди лекції беруть ці функції з одного файлу. Справжньої мережі в ньому немає, а функція `step` виконує одну дію
тесту й друкує один рядок: назву дії й усе, що за цю дію потрапило в журнал.

```ts
// src/tracking.ts
export type Units = 'km' | 'mi'

export function formatDistance(km: number, units: Units): string {
  return units === 'km' ? `${km} км` : `${(km * 0.621).toFixed(1)} милі`
}

// Журнал збирає дії одного кроку тесту.
let journal: string[] = []

export function say(line: string) {
  journal.push(line)
}

export function notify(text: string) {
  say(`сповіщення «${text}»`)
}

export function logVisit(orderId: string) {
  say(`візит ${orderId}`)
}

type Listener = (km: number) => void

// Тут лежать усі канали, відкриті зараз.
const openChannels = new Set<Listener>()

export function createTracking(orderId: string) {
  let listener: Listener = () => {}
  const deliver: Listener = (km) => listener(km)
  return {
    onPosition(callback: Listener) {
      listener = callback
    },
    open() {
      openChannels.add(deliver)
      say(`відкрито ${orderId}`)
    },
    close() {
      openChannels.delete(deliver)
      say(`закрито ${orderId}`)
    },
  }
}

// Служба надсилає нову відстань усім відкритим каналам.
export function sendPosition(km: number) {
  openChannels.forEach((deliver) => deliver(km))
}

// Очищає журнал, виконує дію, друкує рядок і повертає результат дії.
export function step<T>(name: string, action: () => T): T {
  journal = []
  const result = action()
  console.log(`${name} | ${journal.join(', ')}`)
  return result
}
```

Перша спроба виглядає розумно:

```tsx
function TrackerDeps({ orderId, units }: { orderId: string; units: Units }) {
  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.onPosition((km) => {
      notify(`Кур'єр за ${formatDistance(km, units)}`)
    })
    tracking.open()
    return () => tracking.close()
  }, [orderId, units])
  return <h1>Замовлення {orderId}</h1>
}
```

Тест показує компонент, надсилає відстань, перемикає одиниці й надсилає ще одну відстань. Компоненти лекції й тести
лежать в одному файлі `src/tracker.test.tsx`, а всі наступні приклади дописуються в нього ж:

```tsx
// @vitest-environment jsdom
import { StrictMode, useEffect, useEffectEvent, useRef } from 'react'
import { cleanup, fireEvent, render, screen } from '@testing-library/react'
import { afterEach, test, vi } from 'vitest'
import {
  createTracking, formatDistance, logVisit, notify, say, sendPosition, step, type Units,
} from './tracking'

// Прибирає компонент після кожного тесту, тому його канал не отримає чужих відстаней.
afterEach(cleanup)

test('одиниці в залежностях', () => {
  const view = step('одиниці в залежностях, показ', () =>
    render(<TrackerDeps orderId="A-17" units="km" />),
  )
  step('одиниці в залежностях, 5 км', () => sendPosition(5))
  step('одиниці в залежностях, перемикання на милі', () =>
    view.rerender(<TrackerDeps orderId="A-17" units="mi" />),
  )
  step('одиниці в залежностях, 4 км', () => sendPosition(4))
})
```

Перший рядок файлу просить Vitest запускати його під jsdom. Команда
`npx vitest run src/tracker.test.tsx --disable-console-intercept` запускає файл, а прапорець у кінці прибирає службові
рядки навколо `console.log`. Цей тест друкує таке:

```text
одиниці в залежностях, показ | відкрито A-17
одиниці в залежностях, 5 км | сповіщення «Кур'єр за 5 км»
одиниці в залежностях, перемикання на милі | закрито A-17, відкрито A-17
одиниці в залежностях, 4 км | сповіщення «Кур'єр за 2.5 милі»
```

Сповіщення правильні, але третій рядок показує проблему. Користувач змінив лише спосіб показу числа, а застосунок
закрив канал і відкрив його знову. Поки канал закритий, сповіщення можуть загубитися. Щоб виправити це свідомо, треба
спершу точно зрозуміти, що саме React робить з ефектом.

## Дві різні моделі

### Життєвий цикл компонента

Компонент проходить три етапи. **Монтування** означає, що компонент з'явився на екрані. **Оновлення** означає, що він
отримав нові пропси чи стан і React викликав його знову. **Розмонтування** означає, що компонент зник з екрана. Для
компонента ця модель зручна.

### Життєвий цикл ефекту

Ефект уміє лише дві речі. Його тіло **починає синхронізацію**, тобто узгоджує зовнішню систему з поточними пропсами й
станом, а функція прибирання **зупиняє** цю синхронізацію. Подивімося на ефект без одиниць, який записує ще й кожен
рендер:

```tsx
function TrackerOne({ orderId }: { orderId: string }) {
  say(`рендер ${orderId}`)
  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.open()
    return () => {
      tracking.close()
    }
  }, [orderId])
  return <h1>Замовлення {orderId}</h1>
}
```

Запис під час рендеру порушує чистоту компонента, і ми робимо його лише для цього досліду. Тест проводить компонент
через п'ять подій:

```tsx
test('пʼять подій', () => {
  const view = step('показ A-17', () => render(<TrackerOne orderId="A-17" />))
  step('новий рендер, те саме A-17', () => view.rerender(<TrackerOne orderId="A-17" />))
  step('перехід на B-42', () => view.rerender(<TrackerOne orderId="B-42" />))
  step('перехід на C-05', () => view.rerender(<TrackerOne orderId="C-05" />))
  step('компонент зник', () => view.unmount())
})
```

Вивід такий:

```text
показ A-17 | рендер A-17, відкрито A-17
новий рендер, те саме A-17 | рендер A-17
перехід на B-42 | рендер B-42, закрито A-17, відкрито B-42
перехід на C-05 | рендер C-05, закрито B-42, відкрито C-05
компонент зник | закрито C-05
```

Той самий запуск можна прочитати двома способами.

| Подія | Погляд компонента | Погляд ефекту |
|-------|-------------------|---------------|
| показ A-17 | монтування | почав синхронізацію з A-17 |
| перехід на B-42 | оновлення | зупинив синхронізацію з A-17, почав із B-42 |
| перехід на C-05 | оновлення | зупинив синхронізацію з B-42, почав із C-05 |
| компонент зник | розмонтування | зупинив синхронізацію з C-05 |

Оновлення компонента дало ефекту дві дії одразу, тому погляд компонента тут заважає. Якщо ж дивитися очима ефекту, то
вся історія складається з трьох рівних відрізків часу: ефект був підключений до A-17, потім до B-42, потім до C-05.
Кожен відрізок має початок і кінець, а причина кінця неважлива: ефекту байдуже, чи користувач обрав інше замовлення,
чи пішов зі сторінки.

Звідси випливає правило, яке спрощує весь сьогоднішній день. Пишучи ефект, думайте лише про один такий відрізок: як
почати й як зупинити. Якщо обидві дії написані правильно, React може запускати їх стільки разів, скільки потрібно.

### Порядок дій і старе значення в прибиранні

Рядок `рендер B-42, закрито A-17, відкрито B-42` показує порядок дій при зміні. Спершу React викликає компонент із
новим пропсом. Потім він виконує прибирання від попереднього запуску. Лише потім виконує тіло нового ефекту.

Прибирання закрило саме A-17, хоча компонент уже отримав B-42. Причина в замиканні, яке пояснила лекція «Функції та
замикання». Функцію прибирання створено під час рендеру з A-17, і вона пам'ятає змінні того рендеру. Це правильна
поведінка: зупиняти треба те, що запускав саме цей ефект.

### Перевірка в режимі розробки

Тема «Синхронізація ефектами» показала, що `<StrictMode>` у розробці робить зайвий цикл запуску й зупинки. Цей тест
запускає той самий компонент у цьому режимі:

```tsx
test('TrackerOne під StrictMode', () => {
  const show = (orderId: string) => (
    <StrictMode>
      <TrackerOne orderId={orderId} />
    </StrictMode>
  )
  const view = step('StrictMode, показ A-17', () => render(show('A-17')))
  step('StrictMode, перехід на B-42', () => view.rerender(show('B-42')))
  step('StrictMode, компонент зник', () => view.unmount())
})
```

Вивід такий:

```text
StrictMode, показ A-17 | рендер A-17, рендер A-17, відкрито A-17, закрито A-17, відкрито A-17
StrictMode, перехід на B-42 | рендер B-42, рендер B-42, закрито A-17, відкрито B-42
StrictMode, компонент зник | закрито B-42
```

Подвійний рендер стосується кожного рендеру, а зайвий цикл `відкрито, закрито, відкрито` стається лише при першій
появі компонента. Тепер цей цикл має просте пояснення. React перевіряє саме те, про що йшлося вище: чи вміє ваш ефект
зупинитися й почати знову. Сторінка `Lifecycle of Reactive Effects` каже, що в майбутньому в React можуть з'явитися
інші причини перезапуску ефекту, тому код не повинен розраховувати на певну їх кількість.

## Як React вирішує перезапустити ефект

Після кожного рендеру React бере масив, який ви передали другим аргументом, і порівнює кожен елемент з елементом на
тій самій позиції в масиві попереднього рендеру. Порівнює він функцією `Object.is`, яку показала лекція «Значення й
посилання». Якщо хоч один елемент інший, React запускає прибирання й нове тіло ефекту. Цей масив називають **списком
залежностей**.

Рядок `новий рендер, те саме A-17 | рендер A-17` показав, що компонент викликано, а ефект не чіпали:
`Object.is('A-17', 'A-17')` дає `true`.

| Другий аргумент | Коли ефект перезапускається |
|-----------------|-----------------------------|
| немає масиву | після кожного рендеру |
| `[]` | лише додатковий цикл `<StrictMode>` у розробці |
| `[orderId]` | коли `orderId` змінився |

Перший рядок таблиці дає найгрубішу версію нашої скарги. Той самий ефект без масиву реагує навіть на рендер із
незмінними пропсами:

```tsx
function NoArray({ orderId }: { orderId: string }) {
  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.open()
    return () => tracking.close()
  }) // другого аргументу немає
  return <h1>Замовлення {orderId}</h1>
}

test('без масиву', () => {
  const view = step('без масиву, показ', () => render(<NoArray orderId="A-17" />))
  step('без масиву, новий рендер', () => view.rerender(<NoArray orderId="A-17" />))
})
```

Вивід такий:

```text
без масиву, показ | відкрито A-17
без масиву, новий рендер | закрито A-17, відкрито A-17
```

### Пастка «при монтуванні»

Людина, яка думає категоріями компонента, каже собі: «Мені треба підключитися при монтуванні й відключитися при
розмонтуванні, отже, порожній масив». Перевірмо це:

```tsx
function OnMount({ orderId }: { orderId: string }) {
  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.open()
    return () => tracking.close()
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [])
  return <h1>Замовлення {orderId}</h1>
}
```

Тест показує компонент із A-17, переводить його на B-42 і друкує заголовок з екрана:

```tsx
test('порожній масив', () => {
  const view = step('порожній масив, показ', () => render(<OnMount orderId="A-17" />))
  step('порожній масив, перехід на B-42', () => view.rerender(<OnMount orderId="B-42" />))
  console.log('на екрані:', screen.getByRole('heading').textContent)
})
```

```text
порожній масив, показ | відкрито A-17
порожній масив, перехід на B-42 |
на екрані: Замовлення B-42
```

Екран показує B-42, а канал досі підключений до A-17, бо при переході журнал лишився порожнім. Сповіщення надходитимуть
про чуже замовлення, і жодна помилка про це не повідомить. Коментар у коді вимкнув правило лінту для наступного рядка.

Перевірмо, що каже лінт без коментаря. Покладіть компонент в окремий файл `src/OnMount.tsx` і видаліть рядок із
коментарем. Перед словом `function` допишіть `export`, а над компонентом поставте два рядки імпорту: перший бере
`useEffect` з `react`, другий бере `createTracking` з `./tracking`. Команда
`npx eslint src/OnMount.tsx; echo "код завершення $?"` друкує шлях до файлу, а під ним такі рядки:

```text
  8:6  warning  React Hook useEffect has a missing dependency: 'orderId'. Either include it or remove the dependency array  react-hooks/exhaustive-deps
✖ 1 problem (0 errors, 1 warning)
код завершення 0
```

Запис `8:6` на початку означає восьмий рядок файлу й шосту позицію в ньому, тобто масив `[]`.

Зверніть увагу на останній рядок. Правило `exhaustive-deps` за замовчуванням дає попередження, а не помилку, тому
команда `eslint` завершується успішно, і попередження легко пропустити.

Порожній масив не означає «запустити при монтуванні». Він означає інше: цей ефект не читає жодного реактивного
значення. Це правда, наприклад, для ефекту, який читає лише сталі значення модуля. Тоді компонент справді підключиться
один раз, але ця поведінка випливає з коду ефекту, а ви її не обирали.

## Що таке реактивне значення

**Реактивним** називають значення, яке може змінитися під час нового рендеру. Це пропси, стан і будь-яка змінна в тілі
компонента, обчислена під час рендеру. Значення реактивні, бо React щоразу обчислює їх заново, викликаючи компонент.
Ефект, який читає таке значення, може розійтися з екраном, тому значення має стояти в списку залежностей.

Подивімося, як лінт ставиться до різних значень. Ефект нижче читає чотири значення, а лінт вимагає записати в список
лише одне з них:

```tsx
const BASE = 'https://example.test'
export function Stable({ orderId }: { orderId: string }) {
  const [n, setN] = useState(0)
  const seen = useRef(0)
  const label = orderId + n
  useEffect(() => {
    seen.current = 1
    const id = setTimeout(() => setN(1), 1000)
    console.log(BASE, label)
    return () => clearTimeout(id)
  }, [label])
  return null
}
```

Лінт не знаходить у цьому файлі проблем. Пояснення зібрано в таблиці.

| Значення | Чи реактивне | Чи стоїть у списку | Чому |
|----------|--------------|--------------------|------|
| `BASE` | ні | ні | лежить поза компонентом, рендер його не змінює |
| `orderId`, `n` | так | через `label` | пропс і стан; ефект читає їх лише через `label` |
| `label` | так | так | обчислено під час рендеру з реактивних значень |
| `setN` | ні | можна не писати | React гарантує ту саму функцію на кожному рендері |
| `seen` | ні | можна не писати | React гарантує той самий об'єкт ref на кожному рендері |

Значення `setN` і `seen` оголошено всередині компонента, тому формально вони належать до його тіла. Лінт знає, що їх
повернули `useState` і `useRef`, і тому не вимагає їх. Якщо ви отримали таку саму функцію через пропс, лінт цього вже
не знає й попросить записати її.

### Значення, які не можуть бути залежностями

Деякі значення змінюються без участі React. Лекція «Ref» пояснила, що запис у `ref.current` не викликає рендеру.
Значення `location.pathname` змінює браузер. Спробуймо записати їх у список:

```tsx
export function Mutable() {
  const seen = useRef(0)
  useEffect(() => {
    console.log(seen.current, location.pathname)
  }, [seen.current, location.pathname])
  return null
}
```

Команда `npx eslint` на цьому компоненті серед інших рядків друкує попередження й помилку:

```text
React Hook useEffect has unnecessary dependencies: 'location.pathname' and 'seen.current'. Either exclude them or remove the dependency array. Mutable values like 'seen.current' aren't valid dependencies because mutating them doesn't re-render the component
Error: Cannot access refs during render
```

Лінт має рацію з простої причини. React порівнює список лише після рендеру, а зміна цих значень рендеру не запускає,
тому React цієї зміни не побачить. Читання `seen.current` у списку ще й порушує правило `react-hooks/refs`, бо список
обчислюється під час рендеру. Щоб стежити за зовнішнім значенням, яке змінюється саме по собі, у React є окремий хук
`useSyncExternalStore`, і план до нього дійде у фазі 3, у дні «Стор поза React і перепідключення».

## Кожен ефект синхронізує одну річ

Припустімо, сторінка ще записує відвідування замовлення, і цей запис теж залежить від номера. Спокусливо дописати
виклик в уже наявний ефект, бо його запускає той самий номер. Припустімо також, що згодом адреса сервера каналу стала
змінною:

```tsx
function OneEffect({ orderId, server }: { orderId: string; server: string }) {
  useEffect(() => {
    logVisit(orderId)
    const tracking = createTracking(`${server}/${orderId}`)
    tracking.open()
    return () => tracking.close()
  }, [orderId, server])
  return null
}
```

Той самий код можна записати двома ефектами. Тест запускає обидва варіанти й змінює лише сервер:

```tsx
function TwoEffects({ orderId, server }: { orderId: string; server: string }) {
  // Запис відвідування залежить лише від номера.
  useEffect(() => {
    logVisit(orderId)
  }, [orderId])

  // Канал залежить і від номера, і від сервера.
  useEffect(() => {
    const tracking = createTracking(`${server}/${orderId}`)
    tracking.open()
    return () => tracking.close()
  }, [orderId, server])
  return null
}

test('один ефект і два ефекти', () => {
  const one = render(<OneEffect orderId="A-17" server="s1" />)
  step('один ефект, змінився сервер', () =>
    one.rerender(<OneEffect orderId="A-17" server="s2" />),
  )
  const two = render(<TwoEffects orderId="A-17" server="s1" />)
  step('два ефекти, змінився сервер', () =>
    two.rerender(<TwoEffects orderId="A-17" server="s2" />),
  )
})
```

Показ компонентів стоїть поза `step`, тому у вивід потрапляє лише зміна сервера:

```text
один ефект, змінився сервер | закрито s1/A-17, візит A-17, відкрито s2/A-17
два ефекти, змінився сервер | закрито s1/A-17, відкрито s2/A-17
```

Один ефект записав зайвий візит: користувач нікуди не переходив, а статистика збільшилася. Запис відвідування й канал
є двома незалежними процесами, тому вони мають бути двома ефектами. Сторінка React дає перевірку: якщо видалення
одного ефекту не ламає логіку другого, то ці ефекти синхронізують різні речі. З іншого боку, ділити на кілька ефектів
один цілісний процес лише заради короткого коду не варто.

## Обробник чи ефект: чому цей код виконується

Перед наступним кроком потрібне ще одне розрізнення. Запитайте про кожен рядок коду: **чому** він має виконатися?

| Дія | Чому виконується | Де лежить | Чи реактивна логіка |
|-----|------------------|-----------|---------------------|
| скасувати замовлення | користувач натиснув певну кнопку | обробник | ні |
| тримати канал до замовлення | сторінка показує це замовлення, хоч би як користувач сюди прийшов | ефект | так |

Обробник читає реактивні значення, але не реагує на них: він не запуститься знову, бо значення змінилося, а чекає
наступного клацання. Ефект реагує: якщо він читає значення, то після зміни цього значення він запускається знову. Це і
є причина нашої скарги. Сповіщення лежить усередині ефекту, тому читання одиниць зробило реактивним увесь ефект. Проте
сам показ сповіщення за змістом схожий на обробник: він є реакцією на подію «надійшла відстань», а не на зміну
одиниць.

## Два неправильні виходи й один правильний

Отже, в одному ефекті є дві частини. Відкриття каналу має реагувати на номер замовлення. Показ сповіщення має читати
свіжі одиниці, але не реагувати на них. Перший вихід, тобто запис `units` у список, ми вже бачили: канал
перепідключається.

### Другий вихід: вимкнути лінт

Приберемо `units` зі списку й заглушимо лінт коментарем:

```tsx
function TrackerSilenced({ orderId, units }: { orderId: string; units: Units }) {
  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.onPosition((km) => {
      notify(`Кур'єр за ${formatDistance(km, units)}`)
    })
    tracking.open()
    return () => tracking.close()
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [orderId])
  return <h1>Замовлення {orderId}</h1>
}
```

Тест повторює дії з першого тесту, а показ компонента стоїть поза `step`, тому у вивід не потрапляє:

```tsx
test('вимкнений лінт', () => {
  const view = render(<TrackerSilenced orderId="A-17" units="km" />)
  step('вимкнений лінт, 5 км', () => sendPosition(5))
  step('вимкнений лінт, перемикання на милі', () =>
    view.rerender(<TrackerSilenced orderId="A-17" units="mi" />),
  )
  step('вимкнений лінт, 4 км', () => sendPosition(4))
})
```

```text
вимкнений лінт, 5 км | сповіщення «Кур'єр за 5 км»
вимкнений лінт, перемикання на милі | 
вимкнений лінт, 4 км | сповіщення «Кур'єр за 4 км»
```

Перепідключення зникло, а разом із ним зникла й правильна поведінка. Користувач обрав милі, а сповіщення далі йдуть у
кілометрах. Функцію в `onPosition` створено під час першого рендеру, і вона пам'ятає `units` того рендеру. Ефект не
запускався знову, тому нової функції ніхто не передав. Значення зі старого рендеру називають застарілим, і лекція
«Функції та замикання» вже показала цей механізм на годиннику.

### Правильний вихід: подія ефекту

Хук `useEffectEvent` виносить нереактивну частину з ефекту. Функцію, яку він повертає, називають **подією ефекту**,
англійською Effect Event:

```tsx
function TrackerEvent({ orderId, units }: { orderId: string; units: Units }) {
  const onPosition = useEffectEvent((km: number) => {
    notify(`Кур'єр за ${formatDistance(km, units)}`)
  })

  useEffect(() => {
    const tracking = createTracking(orderId)
    tracking.onPosition((km) => {
      onPosition(km)
    })
    tracking.open()
    return () => tracking.close()
  }, [orderId])

  return <h1>Замовлення {orderId}</h1>
}
```

Розберімо його рядками.

- `useEffectEvent((km: number) => { ... })` викликають на верхньому рівні компонента, як і кожен хук. Він приймає вашу
  функцію й повертає функцію з такими самими параметрами та результатом, тому `onPosition` має тип
  `(km: number) => void`.
- Усередині події ефекту читання `units` не є реактивним, тому `units` не потрапляє до списку залежностей.
- Ефект викликає `onPosition(km)` так само, як викликав би звичайну функцію.
- Список `[orderId]` тепер повний. Ефект справді читає лише `orderId`, а саму `onPosition` у список не пишуть. Лінт не
  знаходить у цьому файлі проблем, і коментар для вимкнення не потрібен.

Тест повторює ті самі дії, а потім ще переводить компонент на інше замовлення, надсилає відстань і прибирає компонент:

```tsx
test('подія ефекту', () => {
  const view = step('подія ефекту, показ', () =>
    render(<TrackerEvent orderId="A-17" units="km" />),
  )
  step('подія ефекту, 5 км', () => sendPosition(5))
  step('подія ефекту, перемикання на милі', () =>
    view.rerender(<TrackerEvent orderId="A-17" units="mi" />),
  )
  step('подія ефекту, 4 км', () => sendPosition(4))
  step('подія ефекту, перехід на B-42', () =>
    view.rerender(<TrackerEvent orderId="B-42" units="mi" />),
  )
  step('подія ефекту, 3 км', () => sendPosition(3))
  step('подія ефекту, компонент зник', () => view.unmount())
})
```

Вивід показує потрібну поведінку:

```text
подія ефекту, показ | відкрито A-17
подія ефекту, 5 км | сповіщення «Кур'єр за 5 км»
подія ефекту, перемикання на милі | 
подія ефекту, 4 км | сповіщення «Кур'єр за 2.5 милі»
подія ефекту, перехід на B-42 | закрито A-17, відкрито B-42
подія ефекту, 3 км | сповіщення «Кур'єр за 1.9 милі»
подія ефекту, компонент зник | закрито B-42
```

Запишімо цей запуск таблицею, де видно ролі кожної частини.

| Крок | Хто діє | Що змінюється |
|------|---------|---------------|
| показ | React запускає ефект | канал до A-17 відкрито |
| надійшло 5 | канал викликає функцію ефекту, вона викликає `onPosition` | сповіщення читає `units` = `km` |
| користувач обрав милі | React викликає компонент | рендер є, список `[orderId]` той самий, ефект не чіпають |
| надійшло 4 | той самий канал, та сама функція ефекту | сповіщення читає вже `units` = `mi`, 4 км показано як 2.5 милі |
| обрано B-42 | React порівнює список і бачить зміну | прибирання закрило A-17, тіло відкрило B-42 |
| надійшло 3 | новий канал | сповіщення читає `mi`, бо одиниці не змінювалися |
| компонент зник | React виконує прибирання | канал до B-42 закрито |

Саме така картина є перевіркою практики дня: зміна кімнати перепідключає канал, а зміна теми не дає в лозі жодного
нового рядка про підключення. Під `<StrictMode>` компонент дав той самий результат, лише з додатковим циклом при
показі:

```tsx
test('подія ефекту під StrictMode', () => {
  const show = (units: Units) => (
    <StrictMode>
      <TrackerEvent orderId="A-17" units={units} />
    </StrictMode>
  )
  const view = step('подія ефекту, StrictMode, показ', () => render(show('km')))
  step('подія ефекту, StrictMode, перемикання', () => view.rerender(show('mi')))
})
```

```text
подія ефекту, StrictMode, показ | відкрито A-17, закрито A-17, відкрито A-17
подія ефекту, StrictMode, перемикання | 
```

Хук `useEffectEvent` стабільний із React 19.2. Допис React про цю версію просить оновити плагін лінту, бо старіші
версії плагіна пропонували записати подію ефекту в список. У вашому проєкті плагін новіший, і запуск вище це
підтверджує.

## Як подія ефекту бачить найновіше

Ефект створено під час першого рендеру, і він пам'ятає функцію `onPosition` саме першого рендеру. Чому ж тоді ця
функція читає `units` останнього рендеру? Ось дослід. Перший ефект зберігає функцію першого рендеру й один раз викликає
її, а другий викликає її при кожній зміні одиниць. Окремо порівняємо самі функції двох рендерів:

```tsx
function FirstFunction({ units }: { units: Units }) {
  const read = useEffectEvent(() => `перша функція бачить ${units}`)
  const first = useRef<() => string>(() => '')

  useEffect(() => {
    first.current = read // ця функція належить першому рендеру
    say(first.current())
  }, [])

  useEffect(() => {
    say(`ефект рендеру ${units}: ${first.current()}`)
  }, [units])
  return null
}

// Сюди кожен рендер кладе свою функцію.
const madeByRender: Array<() => Units> = []

function CompareFunctions({ units }: { units: Units }) {
  const read = useEffectEvent(() => units)
  useEffect(() => {
    madeByRender.push(read)
  })
  return null
}

test('функція першого рендеру', () => {
  const compared = render(<CompareFunctions units="km" />)
  compared.rerender(<CompareFunctions units="mi" />)
  console.log('функція першого рендеру та сама:', madeByRender[0] === madeByRender[1])

  step('функція першого рендеру', () => {
    const view = render(<FirstFunction units="km" />)
    view.rerender(<FirstFunction units="mi" />)
  })
})
```

```text
функція першого рендеру та сама: false
функція першого рендеру | перша функція бачить km, ефект рендеру km: перша функція бачить km, ефект рендеру mi: перша функція бачить mi
```

Кожен рендер отримує нову функцію, але навіть функція першого рендеру виконує код останнього рендеру. Довідник
`useEffectEvent` описує це так: у момент виклику функція бачить значення останнього рендеру, який дійшов до коміту.
**Коміт**, за лекцією «Рендер, коміт і знімок стану», є кроком, де React вносить зміни в документ. Отже, значення з
рендеру, який ще не дійшов до коміту, подія ефекту не прочитає.

Те, що функції різні, зроблено навмисно: подію ефекту не можна використати як залежність. Якщо записати її в список,
ефект перезапускатиметься після кожного рендеру, і помилка буде помітна одразу. Компонент покладено в окремий файл, щоб
перевірити його лінтом:

```tsx
// src/InDeps.tsx
import { useEffect, useEffectEvent } from 'react'
import { say } from './tracking'

export function InDeps({ orderId }: { orderId: string }) {
  const onOpen = useEffectEvent(() => {
    say(`відкрито ${orderId}`)
  })
  useEffect(() => {
    onOpen()
    return () => say('прибрано')
  }, [onOpen]) // подію записано в список, чого робити не можна
  return null
}
```

Тест у файлі `src/tracker.test.tsx` показує компонент і рендерить його ще двічі з тим самим номером:

```tsx
import { InDeps } from './InDeps'

test('подія в залежностях', () => {
  step('подія в залежностях, три рендери', () => {
    const view = render(<InDeps orderId="A-17" />)
    view.rerender(<InDeps orderId="A-17" />)
    view.rerender(<InDeps orderId="A-17" />)
  })
})
```

Перший рядок нижче надрукував тест, а другий надрукувала команда `npx eslint src/InDeps.tsx`:

```text
подія в залежностях, три рендери | відкрито A-17, прибрано, відкрито A-17, прибрано, відкрито A-17
  12:7  warning  Functions returned from `useEffectEvent` must not be included in the dependency array. Remove `onOpen` from the list  react-hooks/exhaustive-deps
```

## Де можна викликати подію ефекту

Подію ефекту можна викликати лише всередині ефекту чи іншої події ефекту того самого компонента. Лінт перевіряє це
правилом `rules-of-hooks`. Файл нижче пробує всі місця виклику:

```tsx
// src/Places.tsx
import { useEffect, useEffectEvent } from 'react'
import { say } from './tracking'

function useAfterMount(callback: () => void) {
  useEffect(() => {
    callback()
  }, [callback])
}

function Child({ onDone }: { onDone: () => void }) {
  return <button onClick={onDone}>Готово</button>
}

export function InEffect() {
  const onPing = useEffectEvent(() => say('подія'))
  useEffect(() => {
    onPing()
  }, [])
  return null
}

export function DuringRender() {
  const onPing = useEffectEvent(() => say('подія'))
  onPing()
  return null
}

export function InClick() {
  const onPing = useEffectEvent(() => say('подія'))
  return <button onClick={() => onPing()}>Пінг</button>
}

export function AsProp() {
  const onPing = useEffectEvent(() => say('подія'))
  return <Child onDone={onPing} />
}

export function InOwnHook() {
  const onPing = useEffectEvent(() => say('подія'))
  useAfterMount(onPing)
  return null
}
```

```text
✖ 4 problems (4 errors, 0 warnings)
```

Рядки 25, 31, 36 і 41 належать компонентам `DuringRender`, `InClick`, `AsProp` і `InOwnHook`. Компонент
`InEffect` лежить вище, і для нього лінт нічого не надрукував. Тест запускає два компоненти, щоб побачити, що станеться під час виконання:

```tsx
import { DuringRender, InClick } from './Places'

test('виклик під час рендеру', () => {
  try {
    render(<DuringRender />)
  } catch (error) {
    console.log('виклик під час рендеру:', (error as Error).message)
  }
})

test('виклик в обробнику', () => {
  step('виклик в обробнику клацання', () => {
    render(<InClick />)
    fireEvent.click(screen.getByRole('button'))
  })
})
```

```text
виклик під час рендеру: A function wrapped in useEffectEvent can't be called during rendering.
виклик в обробнику клацання | подія
```

Ось що дали наші спроби разом.

| Де викликано | Лінт | Під час виконання |
|--------------|------|-------------------|
| в ефекті | мовчить | працює |
| під час рендеру | помилка | кидає помилку |
| в обробнику клацання | помилка | у нашому запуску спрацювала без помилки |
| передано дочірньому компоненту пропсом | помилка | не перевіряли |
| передано у власний хук | помилка | не перевіряли |

Рядок про обробник показує, що покладатися слід саме на лінт: React не зупинить такий виклик. Якщо вам потрібна
функція для обробника, пишіть звичайну функцію.

## Подія ефекту не ховає залежність

Подія ефекту дає спокусу прибирати з ефекту все, що заважає. Тут вона дає ту саму помилку, що й порожній масив, тільки
тепер її не бачить навіть лінт:

```tsx
function Hides({ orderId }: { orderId: string }) {
  const onOpen = useEffectEvent(() => {
    const tracking = createTracking(orderId)
    tracking.open()
  })
  useEffect(() => {
    onOpen()
  }, [])
  return <h1>Замовлення {orderId}</h1>
}
```

Тест робить те саме, що й тест для порожнього масиву:

```tsx
test('сховане замовлення', () => {
  const view = step('сховане замовлення, показ', () => render(<Hides orderId="A-17" />))
  step('сховане замовлення, перехід на B-42', () => view.rerender(<Hides orderId="B-42" />))
  console.log('на екрані:', screen.getByRole('heading').textContent)
})
```

```text
сховане замовлення, показ | відкрито A-17
сховане замовлення, перехід на B-42 |
на екрані: Замовлення B-42
```

Лінт не знаходить у цьому файлі проблем, бо формально ефект не читає нічого реактивного. Довідник `useEffectEvent`
прямо застерігає від такого запису. Обирати допомагає одне запитання: **якщо це значення зміниться, чи має ефект
зробити свою роботу заново?** Якщо замовлення змінилося, канал треба відкрити заново, тому `orderId` належить ефекту.
Якщо змінилися одиниці, каналу це байдуже, тому `units` належить події ефекту.

Глава `Separating Events from Effects` дає правило для імен: називайте подію ефекту тим, що сталося з погляду
користувача, наприклад `onPosition`. Назви `onMount` чи `onUpdate` описують час запуску, а не зміст, і в таку функцію
легко покласти код, який мав лишитися реактивним.

## Аргумент чи найновіше значення

Подія ефекту завжди бачить найновіше, а інколи потрібне значення саме того запуску ефекту. Сторінка показує сповіщення
«стежимо за замовленням» через дві секунди після відкриття. Користувач швидко перейшов з A-17 на B-42. Є два способи
записати подію:

```tsx
function DelayedArg({ orderId, units }: { orderId: string; units: Units }) {
  const onOpened = useEffectEvent((openedId: string) => {
    notify(`Стежимо за ${openedId}, одиниці ${units}`)
  })
  useEffect(() => {
    setTimeout(() => onOpened(orderId), 2000)
  }, [orderId])
  return null
}
```

У першому способі подія не має параметра й читає `orderId` усередині. У другому, який показано вище, ефект передає
номер аргументом. Заради цього досліду ефекти не мають прибирання, тому обидва таймери спрацьовують. Ось перший спосіб і
тест, який перевіряє обидва. Фальшиві таймери Vitest дають тесту перемотати дві секунди без справжнього очікування:

```tsx
function DelayedInside({ orderId }: { orderId: string }) {
  const onOpened = useEffectEvent(() => {
    notify(`Стежимо за ${orderId}`)
  })
  useEffect(() => {
    setTimeout(() => onOpened(), 2000)
  }, [orderId])
  return null
}

test('аргумент чи найновіше значення', () => {
  vi.useFakeTimers()
  step('читає всередині', () => {
    const view = render(<DelayedInside orderId="A-17" />)
    view.rerender(<DelayedInside orderId="B-42" />)
    vi.advanceTimersByTime(2000)
  })
  step('отримує аргументом', () => {
    const view = render(<DelayedArg orderId="A-17" units="km" />)
    view.rerender(<DelayedArg orderId="B-42" units="mi" />)
    vi.advanceTimersByTime(2000)
  })
  vi.useRealTimers()
})
```

Користувач переходить на B-42 раніше, ніж спрацьовують таймери, а при другому способі ще й обирає милі:

```text
читає всередині | сповіщення «Стежимо за B-42», сповіщення «Стежимо за B-42»
отримує аргументом | сповіщення «Стежимо за A-17, одиниці mi», сповіщення «Стежимо за B-42, одиниці mi»
```

Перший спосіб двічі написав про B-42, бо на момент спрацювання першого таймера найновішим номером уже був B-42. Другий
спосіб написав про кожне замовлення окремо: `openedId` прийшов від того запуску ефекту, який поставив таймер. Одиниці
`units` в обох сповіщеннях найновіші, бо їх читає подія.

Правило таке: те, що належить самій події, передавайте аргументом від ефекту, а все інше читайте всередині. У цього є
ще один плюс. Ефект читає `orderId`, щоб передати його аргументом, тому лінт не дасть випадково прибрати номер зі
списку залежностей.

## Ефект і рецепт

Практика цього плану йде за рецептом книжки How to Design Programs. Рецепт вимагає прикладів із відомим результатом, а
вони можливі для функцій, які обчислюють значення. Сьогоднішній код легко поділити за цим принципом. Перетворення
відстані на текст є чистою функцією, яку можна перевірити рівностями:

```ts
export function formatDistance(km: number, units: 'km' | 'mi'): string {
  return units === 'km' ? `${km} км` : `${(km * 0.621).toFixed(1)} милі`
}
```

Наприклад, 5 кілометрів у кілометрах дають `5 км`, а 4 кілометри в милях дають `2.5 милі`. Підключення, сповіщення й
перезапуски є діями, тому результат описати рівністю не вийде. Їх перевіряє журнал дій: у якому порядку що сталося
після якої події. Саме такий журнал ви побачите у своїй перевірці дня.

## Типові хибні уявлення

**«Ефект виконується при монтуванні й прибирається при розмонтуванні».** Ефект починає й зупиняє синхронізацію стільки
разів, скільки змінюються значення, які він читає. У запуску вище один компонент, поки лишався на екрані, підключався
до трьох різних замовлень.

**«Порожній масив означає "один раз"».** Порожній масив означає, що ефект не читає реактивних значень. Якщо читає, то
екран показує одне, а ефект лишився зі старим значенням.

**«Я сам обираю, що писати в списку залежностей».** Список описує код: у ньому кожне реактивне значення, яке читає
ефект. Щоб змінити список, треба змінити код. Цьому присвячена тема «Залежності ефекту й власні хуки».

**«Значення всередині функції, яку ефект передає каналу, не рахується».** Рядок `formatDistance(km, units)` у такій
функції теж читає `units`, тому лінт вимагає записати `units` у список. Сама функція пам'ятає значення рендеру, під
час якого її створено.

**«Лінт можна заглушити, якщо я знаю, що роблю».** Запуск із вимкненим лінтом показав сповіщення в кілометрах після
вибору миль. Заглушений лінт не повідомить і про значення, яке ви допишете в цей ефект через місяць.

**«`useEffectEvent` є способом позбутися залежності».** Він призначений для коду, який справді не має реагувати.
Запуск `Hides` показав канал до чужого замовлення, і лінт при цьому мовчав.

**«Подію ефекту можна викликати звідусіль, бо це звичайна функція».** Її можна викликати лише з ефекту чи іншої події
ефекту того самого компонента. Для обробника пишіть звичайну функцію.

**«`seen.current` чи `location.pathname` можна записати в список, щоб ефект за ними стежив».** React порівнює список
лише після рендеру, а зміна цих значень рендеру не запускає.

## Як це проявиться далі в React

- **Тема «Залежності ефекту й власні хуки».** Ви побачите, що робити, коли в списку опинився об'єкт чи функція, і
  винесете ефект у власний хук, усередині якого подія ефекту працює так само.
- **Фаза 3, день «Стор поза React і перепідключення».** Там з'явиться `useSyncExternalStore` для значень, які
  змінюються поза React, а модель «почати й зупинити» лишиться такою самою.

## Перевірте себе

**1. Компонент оновився з `roomId` = `a` на `roomId` = `b`. У якому порядку виконуються рендер, прибирання й тіло
ефекту? Яке значення бачить прибирання?**

<details><summary>Відповідь</summary>

Спершу рендер із `b`, потім прибирання, потім тіло ефекту з `b`. Прибирання бачить `a`, бо його створено під час
рендеру з `a` і воно пам'ятає змінні того рендеру.

</details>

**2. Що означає порожній список залежностей? Чому формулювання «запустити при монтуванні» неточне?**

<details><summary>Відповідь</summary>

Він означає, що ефект не читає жодного реактивного значення, тому причин для перезапуску немає. Формулювання «при
монтуванні» описує наслідок, а не причину. Якщо ефект читає пропс і стоїть порожній масив, то це помилка: після зміни
пропса екран покаже нове значення, а ефект лишиться зі старим.

</details>

**3. Які з цих значень треба записати в список залежностей, якщо ефект їх читає: стала модуля, пропс, змінна в тілі
компонента, обчислена з пропса, функція `set` від `useState`, об'єкт від `useRef`, `ref.current`?**

<details><summary>Відповідь</summary>

Треба записати пропс і змінну в тілі компонента. Сталу модуля не треба, бо рендер її не змінює. Функцію `set` і об'єкт
ref можна не писати, бо React гарантує, що вони ті самі. Значення `ref.current` записувати не можна, бо його зміна не
запускає рендеру, тому React її не побачить.

</details>

**4. Ефект підключається до сервісу й записує відвідування сторінки. Коли їх варто розділити на два ефекти?**

<details><summary>Відповідь</summary>

Варто розділити, коли це два незалежні процеси, тобто видалення одного не ламає другий. Інакше зміна залежності
підключення запише зайве відвідування, як у нашому запуску при зміні сервера.

</details>

**5. Ефект читає `units`, а зміна `units` не має перепідключати канал. Чому вимкнений лінт дає помилку, а
`useEffectEvent` ні?**

<details><summary>Відповідь</summary>

Без `units` у списку ефект не перезапускається, тому функція першого рендеру назавжди пам'ятає старе значення. Подія
ефекту теж не перезапускає ефект, але при виклику виконує код останнього рендеру, який дійшов до коміту, тому бачить
свіже значення.

</details>

**6. Чому подію ефекту не пишуть у список залежностей і що станеться, якщо написати?**

<details><summary>Відповідь</summary>

Її код не реактивний, тому ефект від неї не залежить. Функція навмисно інша на кожному рендері, тому запис у списку
перезапускатиме ефект після кожного рендеру. Лінт повідомить про це попередженням.

</details>

**7. Подія ефекту читає `orderId` усередині, а ефект викликає її через дві секунди. Користувач за цей час перейшов на
інше замовлення. Про яке замовлення буде сповіщення? Як отримати номер того запуску ефекту?**

<details><summary>Відповідь</summary>

Сповіщення буде про нове замовлення, бо подія бачить найновіше значення. Щоб отримати номер того запуску, ефект
передає його в подію аргументом.

</details>

**8. Як за одним запитанням вирішити, де читати значення: в ефекті чи в події ефекту?**

<details><summary>Відповідь</summary>

Запитайте: якщо це значення зміниться, чи має ефект зробити свою роботу заново? Якщо так, значення читає ефект, і воно
стоїть у списку. Якщо ні, значення читає подія ефекту.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| монтування, оновлення, розмонтування | поява компонента на екрані, його новий рендер і зникнення |
| синхронізація | узгодження зовнішньої системи з поточними пропсами й станом |
| зовнішня система | те, що працює поза React: мережа, сервер, сторонній віджет чи браузерний API |
| реактивне значення | пропс, стан чи змінна в тілі компонента, обчислена під час рендеру |
| список залежностей | другий аргумент `useEffect`, який React порівнює з попереднім через `Object.is` |
| застаріле значення | значення зі старого рендеру, яке читає функція, що пережила цей рендер |
| подія ефекту, Effect Event | функція від `useEffectEvent`, викликана з ефекту, чий код не є реактивним і бачить найновіші значення |
| стабільне значення | значення, про яке React гарантує, що воно те саме на кожному рендері, наприклад функція `set` |
