дасть лише ваш власний застосунок на вашій адресі.

**Після лекції ви зможете пояснити:**

- що лежить у теці `dist` і для чого потрібен кожен файл;
- чому `npm run build` може зупинитися через файл, який ніхто не імпортує;
- який файл є головним JS-файлом і яке число зі звіту збірки йде в журнал;
- чому застосунку на React досить сервісу, який лише роздає файли;
- чого `vite preview` не може показати й де він приховує майбутню проблему;
- чим викладання готової теки відрізняється від підключення репозиторію;
- що саме з вашої збірки може прочитати будь-який відвідувач;
- навіщо потрібні три прогони Lighthouse і чому беруть медіану, а не середнє;
- чому в колонці INP сьогодні стоїть прочерк, а не нуль.

## Застосунок, який бачите лише ви

Ви пишете у відгуку на вакансію: «Ось мій застосунок». Адреса, яку ви бачили весь цей час, має вигляд
`http://localhost:5173`. Слово `localhost` означає «цей самий комп'ютер», тому на комп'ютері роботодавця ця адреса
нічого не відкриє, а на вашому працює лише тоді, коли запущено `npm run dev`. Застосунок існує, але показати його
нікому не можна.

Є й друга проблема. Попередні дні вчили вас, що рендер має причину, а швидкість треба міряти. Режим розробки для цього
не годиться: лекція «Інструменти браузера» пояснила, що він віддає окремі модулі й містить версію React із
перевірками. Справжнє число можна отримати лише на зібраному застосунку, а найкраще на адресі, яку відкривають інші
люди.

Тому план робить **викот**, тобто викладання застосунку в інтернет, рано, а не тоді, коли застосунок «буде готовий».
План оцінює перший викот приблизно в тридцять хвилин. Якщо робити його вперше за день до співбесіди, будь-яка
несподіванка стане проблемою. Якщо зробити його сьогодні, кожна наступна зміна просто оновлюватиме вже працюючу
адресу.

Для цього потрібно відповісти на три запитання: що викладати, куди викладати й як дізнатися, що результат працює і
наскільки швидко. Лекція йде в цьому самому порядку.

## Що створює збірка

Лекція «Проєкт: Vite, лінт, TypeScript» уже показала чотири дії команди `vite build`: вона склеює модулі, викидає
невикористаний код, скорочує код і додає до імен файлів відбиток умісту. Тепер подивімося на результат цілком.

Спершу ось сам застосунок. У файлі `index.html` шаблону ми змінили лише мову й заголовок: `lang="uk"` і
`<title>Чайна крамниця</title>`. Файл `src/main.tsx` лишився таким, яким його створив шаблон. Ось решта файлів:

```tsx
// файл src/App.tsx
import { useState } from 'react'

const TEAS = [
  { name: 'Сенча', price: 240 },
  { name: 'Улун', price: 310 },
  { name: 'Пуер', price: 420 },
]

export default function App() {
  // Стан пам'ятає, який чай обрав відвідувач.
  const [chosen, setChosen] = useState('нічого')
  return (
    <main>
      {/* Назву крамниці збірка візьме з файла .env. */}
      <h1>{import.meta.env.VITE_SHOP_NAME}</h1>
      <ul>
        {TEAS.map((tea) => (
          <li key={tea.name}>
            <button onClick={() => setChosen(tea.name)}>
              {tea.name}, {tea.price} грн
            </button>
          </li>
        ))}
      </ul>
      <p>Обрано: {chosen}</p>
    </main>
  )
}
```

```css
/* файл src/index.css */
body {
  margin: 0;
  font-family: sans-serif;
}

main {
  padding: 16px;
}
```

```text
# файл .env у корені проєкту
VITE_SHOP_NAME=Чайна крамниця
```

Запис `import.meta.env.VITE_SHOP_NAME` читає значення з файла `.env`. Розділ «Що в збірці бачать усі» пояснить, куди
збірка його кладе. Тепер виконаємо `npm run build` і отримаємо такий вивід:

```text

> tsc -b && vite build

transforming...
✓ 16 modules transformed.
```

Команда `ls -l dist dist/assets` показує розмір усього, що з'явилося в теці `dist`:

| Файл | Розмір, байти | Навіщо він |
|------|---------------|------------|
| `index.html` | 477 | сторінка, яку браузер запитує першою |
| `assets/index-B9Arpe-s.js` | 219 940 | весь JavaScript: ваш код і React |
| `assets/index-C7WGSwOu.css` | 56 | усі стилі |
| `favicon.svg` | 9 522 | значок вкладки, скопійований із теки `public` |
| `icons.svg` | 5 031 | значки шаблону, скопійовані із теки `public`; наш код їх не використовує |

Файл JavaScript, у який збірка склала код застосунку, називають **бандлом**. Частина імені `B9Arpe-s` є **хешем**,
тобто коротким рядком, який обчислено із вмісту файла. Ми зібрали той самий код кілька разів і щоразу отримували те
саме ім'я. Після зміни коду ім'я змінюється, і саме це дозволяє браузеру довго зберігати такі файли у своєму кеші:
нова версія завжди матиме нове ім'я. Лекція «Проєкт: Vite, лінт, TypeScript» показала це порівнянням двох збірок.

Файли `favicon.svg` і `icons.svg` хешу не мають. Сторінка Vite про ресурси пояснює, що все з теки `public` копіюється
в корінь `dist` без змін, тому такі файли зберігають свої імена.

Подивімося, як ці файли пов'язані між собою. Зібраний `index.html` виглядає так:

```html
<!doctype html>
<html lang="uk">
  <head>
    <meta charset="UTF-8" />
    <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Чайна крамниця</title>
    <script type="module" crossorigin src="/assets/index-B9Arpe-s.js"></script>
    <link rel="stylesheet" crossorigin href="/assets/index-C7WGSwOu.css">
  </head>
  <body>
    <div id="root"></div>
  </body>
</html>
```

Рядок зі `<script>` називає бандл на ім'я, тому після нової збірки новий `index.html` приведе браузер до нового файла.
Запис `src="/assets/..."` починається з косої риски, отже, браузер шукатиме файл від кореня адреси. Цей дрібний факт
нижче пояснить дві поломки. Елемент `<div id="root">` порожній: вміст сторінки створить React після завантаження
JavaScript. Атрибут `crossorigin` Vite додає сам, і для сьогоднішньої теми він нічого не змінює.

### Збірка щоразу очищає `dist`

Ми поклали в `dist` файл із нотатками й зібрали застосунок знову:

```text
$ echo нотатки > dist/notes.txt
$ npm run build > /dev/null
$ ls -C dist
assets  favicon.svg  icons.svg  index.html
```

Файла немає. Параметр `build.emptyOutDir` за замовчуванням очищає теку перед збіркою, якщо вона лежить усередині
проєкту. Отже, `dist` є результатом команди, а не місцем для зберігання. Журнал вимірів і все інше своє тримайте поза
нею. З тієї самої причини шаблон уже вписав `dist` у файл `.gitignore`, тому в репозиторій ця тека не потрапляє.

### Що входить у бандл і що зупиняє збірку

Команда `npm run build` у вашому проєкті виконує два кроки: `tsc -b && vite build`. Перший крок перевіряє типи, другий
збирає. Ці кроки дивляться на ваші файли по-різному, і це легко перевірити. Ми додали файл уроку, який ніхто не
імпортує і в якому є помилка типу:

```tsx
// файл src/lessons/x/Draft.tsx
export const seats: number = 'двадцять'
export const MARKER = 'МАРКЕР-УРОКУ'
```

```text
$ npm run build; echo "код завершення: $?"

> spa@0.0.0 build
> tsc -b && vite build

src/lessons/x/Draft.tsx(2,14): error TS2322: Type 'string' is not assignable to type 'number'.
код завершення: 2

$ npx vite build | grep -E 'assets.*js|built'
dist/assets/index-B9Arpe-s.js   219.94 kB │ gzip: 68.87 kB
✓ built in 374ms

$ grep -c 'МАРКЕР-УРОКУ' dist/assets/*.js
0
```

Перша команда зупинилася на кроці `tsc -b` з кодом завершення 2, тому рядків збірки у виводі немає. Друга команда
пропустила цей крок і зібрала застосунок. Ім'я й розмір бандла не змінилися, а пошук маркера дав нуль.

Звідси випливають два наслідки для вашого проєкту:

| Хто дивиться | На що дивиться | Що це означає для вас |
|--------------|----------------|------------------------|
| `tsc -b` | на всі файли в `src`, зокрема уроки | незавершена вправа з помилкою типу зупинить `npm run build` |
| `vite build` | лише на те, до чого можна дійти імпортами від `index.html` | файл уроку, який ніхто не імпортує, відвідувач не отримає й не побачить |

Не обходьте першу перевірку прямим викликом `npx vite build`. Ми зробили це лише для досліду. Помилку типу треба
виправити, бо інакше ви викладете код, про який компілятор уже сказав, що він неправильний. Другий наслідок означає
таке: відвідувач побачить те, що рендерить `App`. Тому перед викотом подивіться, що показує ваш `App`.

## Як читати звіт збірки

Кожен рядок звіту містить ім'я файла, його розмір і розмір після стиснення. Позначка `kB` тут означає тисячу байтів:
219 940 байтів показано як `219.94 kB`. Стиснення gzip пояснила лекція «Інструменти браузера»: сервер упаковує текстовий
файл на час передачі, а браузер розпаковує його.

План просить записувати в журнал розмір головного JS-файла після gzip. Для нашого застосунку це число `68.87`, а не
`219.94`. Перше число показує, скільки байтів зазвичай піде мережею, а друге показує, скільки коду браузер мусить
розібрати. Обидва числа важливі, але для порівняння між рядками журналу план обрав перше.

**Який файл є головним.** Поки JS-файл один, запитання не виникає. Лекція «Модулі й пакети» показала динамічний
імпорт, тобто вираз `import("./файл.js")`, який завантажує модуль лише тоді, коли до нього дійшов код. Збірка кладе
такий модуль в окремий файл. Ми додали до застосунку новий модуль і кнопку, яка його завантажує:

```tsx
// файл src/invoice.ts
export const invoiceTitle = 'Рахунок на чай'
```

```tsx
// у файлі src/App.tsx цю кнопку додано відразу під рядком «Обрано»
<button
  onClick={async () => {
    // Браузер завантажить модуль invoice лише після цього клацання.
    const invoice = await import('./invoice')
    setChosen(invoice.invoiceTitle)
  }}
>
  Показати рахунок
</button>
```

```text
$ npm run build | grep '^dist'

dist/assets/index-C7WGSwOu.css     0.05 kB │ gzip:  0.07 kB
dist/assets/invoice-CkRcmuf3.js    0.06 kB │ gzip:  0.08 kB
dist/assets/index-DMji4--J.js    221.60 kB │ gzip: 69.53 kB

$ grep '<script' dist/index.html

```

Тепер у звіті два JS-файли. Головним є той файл, який названо в тезі `<script>` у `dist/index.html`. Браузер завантажує
його завжди, а решту лише за потребою. У цьому прикладі це `index-DMji4--J.js`, тому в журнал пішло б число `69.53`.

**Чому число беруть саме зі звіту.** Ми порівняли кілька способів порахувати той самий файл застосунку без кнопки
рахунку. Цей скрипт ми запустили з кореня проєкту, а останню команду виконали, поки працював `npx vite preview`:

```js
// файл sizes.mjs, запуск: node sizes.mjs
import { readdirSync, readFileSync } from 'node:fs'
import { brotliCompressSync, gzipSync } from 'node:zlib'

// Шукаємо єдиний JS-файл у зібраній теці.
const name = readdirSync('dist/assets').find((file) => file.endsWith('.js'))
const bytes = readFileSync(`dist/assets/${name}`)

console.log('без стиснення:', bytes.length)
console.log('gzip у Node:', gzipSync(bytes).length)
console.log('Brotli у Node:', brotliCompressSync(bytes).length)
```

```text
gzip у Node: 68128
Brotli у Node: 58557

```

Заголовок `Accept-Encoding: gzip` просить сервер стиснути файл, а `%{size_download}` друкує, скільки байтів справді
прийшло мережею. Разом зі звітом збірки маємо таку таблицю:

| Спосіб | Розмір |
|--------|--------|
| без стиснення | 219 940 байтів |
| звіт `vite build` | 68,87 кБ |
| gzip у Node із типовими налаштуваннями | 68 128 байтів |
| що справді передав `vite preview` зі стисненням gzip | 68 128 байтів |
| Brotli у Node, інший алгоритм стиснення | 58 557 байтів |

Числа різняться, бо інструменти стискають із різними налаштуваннями, а хостинг може обрати інший алгоритм. Вам не
потрібно точне число байтів у мережі. Вам потрібне число, яке можна порівнювати саме із собою через тиждень, тому в
журнал щоразу йде значення з того самого місця, тобто зі звіту збірки.

**Що означає перше число.** Ми замінили вміст `src/App.tsx` однією функцією
`export default function App() { return <p>x</p> }` і зібрали застосунок:

```text
$ npm run build | grep 'assets.*js'
dist/assets/index-D9KSjoO6.js   219.53 kB │ gzip: 68.58 kB
```

Майже весь бандл «Чайної крамниці» становлять React і React DOM, а код самої крамниці додав 0,29 кБ після стиснення:
це різниця між 68,87 і 68,58.
Отже, ваш перший рядок майже не говорить про якість вашого коду. Він є точкою відліку, а цінність мають наступні
рядки. Параметр `build.chunkSizeWarningLimit` за документацією Vite додає попередження, якщо файл до стиснення
перевищує 500 кБ.

## Чому не потрібен власний сервер

**Статичний хостинг** є сервісом, який зберігає готові файли й віддає їх за адресою. Він не виконує вашого коду. Він
отримує запит шляху, шукає файл і надсилає його. Подивімося, чому цього досить:

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | браузер відвідувача | запитує `/` |
| 2 | хостинг | надсилає `index.html`, де `<div id="root">` порожній |
| 3 | браузер | читає теги й запитує JS-файл і CSS-файл |
| 4 | хостинг | надсилає обидва файли |
| 5 | браузер | виконує бандл, і React викликає ваші компоненти прямо на пристрої відвідувача |
| 6 | React | записує результат у документ, і сторінка з'являється |

Увесь код вашого застосунку працює в браузері на двох останніх кроках, а сервер лише передав файли. Сервер із власним
кодом знадобиться, коли дані треба зберігати спільно для всіх або коли розмітку має створювати сервер. Другий випадок
вивчає фаза 4, а перший належить плану NestJS.

Чому ж не можна просто надіслати `index.html` файлом і відкрити подвійним клацанням? Ми відкрили цей файл у Chrome за
адресою `file://` і подивилися на документ після завантаження. Змінна `CHROME_PATH` містить шлях до браузера, прапорець
`--headless` запускає його без вікна, а `--dump-dom` друкує документ після виконання скриптів:

```text
$ "$CHROME_PATH" --headless --user-data-dir=$(mktemp -d) --dump-dom file://$PWD/dist/index.html \
    2> /dev/null | grep -o '<div id="root">.*</div>'
<div id="root"></div>
```

Сторінка лишилася порожньою. Запис `/assets/...` за адресою `file://` веде до кореня диска, а не до теки проєкту. Крім
того, сторінка MDN про модулі попереджає, що скрипти-модулі, відкриті через `file://`, зупиняє правило CORS. Тому
зібраному застосунку потрібен сервер, нехай навіть зовсім простий. Ось найпростіший сервер, який ми написали для цієї
лекції. Він шукає файл у теці `dist`, а якщо файла немає, відповідає 404:

```js
// файл static-server.mjs, запуск: node static-server.mjs
import { readFile } from 'node:fs/promises'
import { createServer } from 'node:http'
import { extname, join } from 'node:path'

// Перший аргумент каже, під яким шляхом сервер віддає теку dist.
const PREFIX = process.argv[2] ?? '/'
const TYPES = { '.html': 'text/html', '.js': 'text/javascript', '.css': 'text/css', '.svg': 'image/svg+xml' }

createServer(async (req, res) => {
  const path = new URL(req.url, 'http://x').pathname
  let status = 404
  let body = 'Not found'
  if (path.startsWith(PREFIX)) {
    const rest = path.slice(PREFIX.length) || 'index.html'
    const file = join('dist', rest)
    try {
      body = await readFile(file)
      status = 200
      res.setHeader('Content-Type', TYPES[extname(file)] ?? 'text/plain')
    } catch {
      // Файла немає: лишаємо відповідь 404, як хостинг без окремого правила.
    }
  }
  console.log('GET', path, status)
  res.statusCode = status
  res.end(body)
}).listen(8000)
```

На тій самій теці, відданій цим сервером за адресою `http://`, з'явився весь вміст:

```text
$ "$CHROME_PATH" --headless --user-data-dir=$(mktemp -d) --dump-dom http://localhost:8000/ \
    2> /dev/null | grep -o '<div id="root">.*</div>' | cut -c1-120
<div id="root"><main><h1>Чайна крамниця</h1><ul><li><button>Сенча, 240 грн</button></li><li><button
```

Команда `cut` лише обрізає довгий рядок для лекції. Отже, за адресою `file://` React нічого не намалював, а через сервер
намалював усю сторінку.

## `vite preview`: перевірка перед викладанням

Команда `vite preview` запускає на вашому комп'ютері простий сервер, який роздає `dist`:

```text
$ npx vite preview
  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose
```

Ця команда нічого не збирає, і це її перша пастка. Поки сервер працював, ми змінили код, не запускаючи збірки, і
шукали новий текст у файлі, який віддає сервер:

```text
$ sed -i 's/Сенча/Зелена сенча/' src/App.tsx
$ curl -s http://localhost:4173/assets/index-B9Arpe-s.js | grep -c 'Зелена сенча'
0
```

Нуль означає, що сервер далі віддавав старий файл без нового тексту. Тому порядок завжди такий: спершу збірка, потім
перегляд.

Друга пастка стосується самої теки `dist`. Якщо цієї теки немає, Vite зупиняється з помилкою. Якщо тека є, але порожня,
Vite не скаржиться, друкує ті самі два рядки, а кожен запит отримує відповідь 404:

```text
$ mv dist dist-away
$ npx vite preview 2>&1 | head -2
error when starting preview server:
Error: The directory "dist" does not exist. Did you build your project?

$ mkdir dist
$ npx vite preview
  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4173/
404
```

Отже, якщо сторінка не відкривається, спершу перевірте, чи ви в теці `spa/` і чи є в `dist` файли.

Третя річ важливіша, бо її не видно. Ми порівняли `vite preview` із сервером `static-server.mjs`, який відповідає 404,
коли файла немає. Так поводиться статичний хостинг, якщо на ньому не задано окремого правила. Один і той самий цикл ми
виконали двічі, спершу для порту 4173, де працював `vite preview`, а потім для порту 8000, де працював наш сервер:

```text
$ for p in / /catalog/sencha /assets/nope.js; do
    curl -s -o /dev/null -w "$p %{http_code} %{content_type}\n" http://localhost:4173$p
  done
/ 200 text/html
/catalog/sencha 200 text/html
/assets/nope.js 200 text/html

# той самий цикл для http://localhost:8000
/ 200 text/html
/catalog/sencha 404
/assets/nope.js 404
```

Кожен рядок містить шлях, код відповіді й тип вмісту. Тип `text/html` у відповіді на `/assets/nope.js` показує, що
`vite preview` віддав сторінку, а не JS-файл. Ось підсумок:

| Запит | `vite preview` | сервер, який лише шукає файл |
|-------|----------------|-------------------------------|
| `/` | 200, `index.html` | 200, `index.html` |
| `/catalog/sencha` | 200, `index.html` | 404 |
| `/assets/nope.js` | 200, `index.html` | 404 |

`vite preview` на будь-який незнайомий шлях повертає `index.html`. Така поведінка потрібна **односторінковому
застосунку**, тобто застосунку, де є один `index.html`, а адреси обробляє JavaScript у браузері. Коли у фазі 3
з'явиться маршрутизатор, адреса `/catalog/sencha` існуватиме лише для нього. Якщо людина відкриє таке посилання прямо,
хостинг шукатиме файл `catalog/sencha`, не знайде його й відповість 404, хоча `vite preview` працював. Сьогодні
маршрутів у застосунку ще немає, тому зараз ця проблема вас не торкається. Розбір читання показує, як її розв'язує
кожен хостинг.

Сервер `vite preview` також не повторює інших особливостей хостингу. Команда
`curl -sI http://localhost:4173/assets/index-B9Arpe-s.js | grep -i cache-control` друкує рядок
`Cache-Control: no-cache`, отже, цей сервер просить браузер перевіряти файл із хешем щоразу. Сервер хостингу може
задавати інші правила. Сторінка Vite прямо каже, що ця команда
призначена для перегляду на вашому комп'ютері, а не для обслуговування справжніх відвідувачів.

**Прапорець `--host`.** Команда `npx vite preview --host` друкує ще й адресу вашого комп'ютера в локальній мережі,
наприклад `http://192.168.x.x:4173/`. Телефон у тій самій мережі Wi-Fi зможе її відкрити. Ми цього телефоном не
перевіряли. Це зручний спосіб подивитися на вузький екран, але це не викот: коли ви вимкнете команду або телефон
перейде на мобільний інтернет, адреса перестане працювати.

## Викот: що відбувається

Цей розділ описано за документацією хостингів. Ми нічого не викладали й не перевіряли цих кроків. Кнопки й умови
безкоштовних планів змінюються, тому покрокові дії шукайте на сторінках, які називає розбір читання.

Сторінка Vite `Deploying a Static Site` описує багато хостингів, а план пропонує обрати один із трьох: Netlify, Vercel
або Cloudflare. У кожного з них є два шляхи.

| Що порівнюємо | Викласти готову теку | Підключити репозиторій |
|---------------|----------------------|------------------------|
| Хто запускає збірку | ви, на своєму комп'ютері | хостинг, після кожного оновлення гілки |
| Що отримує хостинг | вміст `dist` | весь код проєкту |
| Звідки беруться змінні `VITE_*` | із вашого файла `.env` під час збірки | із налаштувань проєкту на хостингу |
| Що треба вказати | яку теку викласти | команду збірки, теку результату й підтеку проєкту |
| Як вийде нова версія | ви збираєте й викладаєте ще раз | хостинг збирає сам після `git push` |

Викладання готової теки простіше зрозуміти вперше, бо ви бачите, що передаєте. Підключення репозиторію дає зручність
далі. Для вашого проєкту є одна особливість: застосунок лежить не в корені репозиторію, а в теці `spa/`. У
налаштуваннях збірки такий хостинг просить указати цю підтеку. Netlify називає її `Base directory`, Cloudflare Pages
називає її `Root directory`, а Vercel називає її `Root Directory`. Якщо її не вказати, хостинг шукатиме `package.json`
не там, де він лежить.

У результаті ви отримаєте адресу. Наприклад, документація Vite показує для Cloudflare Pages адресу вигляду
`https://<назва-проєкту>.pages.dev/`. Netlify дозволяє викласти теку навіть без облікового запису, але за її
документацією такий проєкт треба забрати собі протягом години, тому для адреси, яка має лишитися в README, цей шлях не
підходить.

### Коли сторінка порожня: шлях `base`

Найчастіша поломка після викладання виглядає так: сторінка біла, а вкладка Network показує 404 на JS-файл. Причину
легко відтворити. Ми запустили сервер `static-server.mjs` з аргументом `/shop/`, тому він віддає ту саму `dist` за
адресою, вкладеною в цей шлях. Потім ми відкрили в браузері `http://localhost:8000/shop/`, а сервер надрукував запити:

```text
$ node static-server.mjs /shop/
GET /shop/ 200
GET /assets/index-B9Arpe-s.js 404
GET /assets/index-C7WGSwOu.css 404
```

Сторінка знайшлася, а бандл і стилі ні, бо запис `/assets/...` починається від кореня адреси, а файли лежать у
`/shop/assets/`.
Параметр `base` каже збірці, під яким шляхом житиме застосунок:

```text
$ npx vite build --base=/shop/ > /dev/null
$ grep '<script' dist/index.html
    <script type="module" crossorigin src="/shop/assets/index-B9Arpe-s.js"></script>

$ node static-server.mjs /shop/
GET /shop/ 200
GET /shop/assets/index-B9Arpe-s.js 200
GET /shop/assets/index-C7WGSwOu.css 200
```

Якщо ваш застосунок отримає власну адресу без вкладеного шляху, як у трьох названих хостингів, цей параметр не
потрібен. Він потрібен, наприклад, на GitHub Pages, коли адреса містить назву репозиторію. Ім'я файла тут не
змінилося, бо хеш обчислюється з умісту файла, а шлях записано в `index.html`.

## Що в збірці бачать усі

Браузер відвідувача завантажує кожен файл, щоб виконати його, тому все, що лежить у `dist`, є публічним. Скорочення
коду нічого не ховає: імена змінних зникають, а текстові рядки лишаються такими, як були. Щоб побачити це, ми поклали
в `.env` ще два значення, тому тепер там лежать три. Усі три вигадані й ні до чого не дають доступу:

```text
VITE_SHOP_NAME=Чайна крамниця
VITE_DEMO_KEY=demo-key-not-real-111
SERVER_ONLY_VALUE=server-only-not-real-222
```

Спершу код читає лише `import.meta.env.VITE_SHOP_NAME`. Далі ми двічі дописували один рядок у `src/App.tsx` перед
функцією `App`, збирали застосунок і шукали значення в бандлі:

```tsx
// Другий дослід: код читає обидві нові змінні.
console.log(import.meta.env.VITE_DEMO_KEY, import.meta.env.SERVER_ONLY_VALUE)

// Третій дослід: цей рядок стоїть замість рядка вище, тому код друкує весь об'єкт.
console.log(import.meta.env)
```

Для кожного досліду ми виконали ті самі дві команди пошуку. Команда `grep -c` рахує рядки зі збігом, тому 1 означає, що
значення є в бандлі, а 0 означає, що його немає:

```text
$ for v in demo-key-not-real-111 server-only-not-real-222; do grep -c $v dist/assets/*.js; done

# код не читає цих змінних
0
0

# код читає обидві
1
0

# код друкує весь об'єкт
1
0
```

У другому досліді в бандлі можна знайти сам виклик. Запис `void 0` є скороченим записом значення `undefined`:

```text
$ grep -o 'console.log(.\{0,40\}' dist/assets/*.js | grep demo-key
console.log(`demo-key-not-real-111`,void 0);function
```

Ось ці самі результати таблицею:

| Що робить код | `VITE_DEMO_KEY` у бандлі | `SERVER_ONLY_VALUE` у бандлі |
|---------------|--------------------------|------------------------------|
| не читає цих змінних | немає | немає |
| читає обидві через `import.meta.env` | є | немає, у коді вийде `undefined` |
| друкує весь об'єкт `import.meta.env` | є | немає |

Vite підставляє значення змінної з префіксом `VITE_` просто в текст бандла під час збірки. Запис цілого об'єкта вписує
всі такі змінні, навіть ті, про які ви не думали. Третій дослід залишив у бандлі такий текст:

```text
$ grep -o 'BASE_URL.\{0,110\}' dist/assets/*.js
BASE_URL:`/`,DEV:!1,MODE:`production`,PROD:!0,SSR:!1,VITE_DEMO_KEY:`demo-key-not-real-111`,VITE_SHOP_NAME:`Чайна крамн
```

Отже, префікс `VITE_` означає не «налаштування Vite», а дозвіл показати значення всім. Сторінка Vite прямо попереджає,
що такі змінні не повинні містити секретів, наприклад ключів API. Це і є пастка дня: людина кладе ключ у `.env`,
бачить, що він не лежить у репозиторії, і вирішує, що він прихований. Після збірки ключ лежить у публічному файлі.
Запит, якому потрібен ключ, має йти через сервер, бо лише там ключ не передається відвідувачу. Фаза 5 на другому дні
повертається до цієї теми окремою вправою.

Є ще три місця, про які варто знати:

- **Тека `public`.** Ми поклали туди `draft.txt`, і файл з'явився в `dist`. На хостингу такий файл відкриє будь-хто,
  хто знає його ім'я.
- **Карти коду.** Це файли, за якими браузер показує вихідний код замість скороченого. За замовчуванням збірка їх не
  створює. З прапорцем `--sourcemap` поруч із бандлом з'явився файл на 1 046 кБ, і в його полі `sourcesContent` лежить
  вихідний код. Фаза 5 на шостому дні пояснить, куди їх подіти, щоб вони не лежали у відкритому доступі.
- **Файл `.env`.** Шаблон Vite вписав у `.gitignore` записи `*.local` і `dist`, а звичайного `.env` там немає. Ваш
  репозиторій за планом публічний, тому файл `.env`, якщо він є, потрапить у нього після `git add .`, якщо ви не
  додасте його в `.gitignore` самі.

## Замір: три прогони й медіана

Лекція «Інструменти браузера» пояснила, що Lighthouse автоматично завантажує сторінку в заданих умовах і рахує
показники. Сьогодні нам потрібні два. **LCP** показує, коли з'явився найбільший елемент першого екрана. **CLS**
показує, наскільки вміст зсувався під час показу, і не має одиниці виміру.

Режим mobile означає конкретні умови. У полі `configSettings` файла звіту наших запусків стояло: екран 412 на
823 пікселі, затримка мережі 150 мс,
швидкість завантаження приблизно 1,6 Мбіт/с, процесор повільніший у 4 рази. Lighthouse за замовчуванням не гальмує
справжнє завантаження: він завантажує сторінку швидко, а тоді обчислює за моделлю, скільки це тривало б на таких
умовах. Документація Lighthouse називає цей спосіб симульованим уповільненням. Тому результат є оцінкою, а не
секундоміром на справжньому телефоні.

Ось три прогони «Чайної крамниці» на `vite preview` у Lighthouse 13.6. Поки в іншому терміналі працював
`npx vite preview`, ми запустили Lighthouse із командного рядка, а потім прочитали його файли JSON цим скриптом:

```js
// файл report.mjs
import { readFileSync } from 'node:fs'

// Кожен аргумент є іменем файла JSON, який створив Lighthouse.
for (const file of process.argv.slice(2)) {
  const { audits, categories } = JSON.parse(readFileSync(file, 'utf8'))
  console.log(
    file,
    'LCP', Math.round(audits['largest-contentful-paint'].numericValue),
    audits['largest-contentful-paint'].displayValue,
    'CLS', audits['cumulative-layout-shift'].displayValue,
    'TBT', Math.round(audits['total-blocking-time'].numericValue),
    'bytes', audits['total-byte-weight'].numericValue,
    'score', categories.performance.score * 100,
  )
}
```

```text
$ for n in 1 2 3; do
    npx lighthouse http://localhost:4173/ --only-categories=performance --output=json \
      --output-path=prod$n.json --chrome-flags="--headless --no-sandbox" --quiet
  done
$ node report.mjs prod1.json prod2.json prod3.json
prod1.json LCP 770 0.8 s CLS 0 TBT 0 bytes 69642 score 100
prod2.json LCP 756 0.8 s CLS 0 TBT 4 bytes 69642 score 100
prod3.json LCP 767 0.8 s CLS 0 TBT 0 bytes 69642 score 100
```

Режим mobile Lighthouse обирає сам, тому прапорця для нього немає. Прапорець `--no-sandbox` вимикає захисну пісочницю
браузера. Для заміру він не потрібен, бо запуск без нього теж спрацював, тому у своїх командах його не додавайте.
Позначка `TBT` є загальним часом блокування, який
пояснено нижче, а `bytes` є обсягом переданих даних. Звідси беремо два показники дня й оцінку:

| Прогін | LCP, мс | CLS | Оцінка |
|--------|---------|-----|--------|
| перший | 770 | 0 | 100 |
| другий | 756 | 0 | 100 |
| третій | 767 | 0 | 100 |

Звіт Lighthouse показує такий LCP округленим як `0.8 s`. Точні мілісекунди ми взяли з файла JSON, який створює варіант
Lighthouse для командного рядка. У журнал пишіть значення так, як його показує ваш звіт, і щоразу в тих самих
одиницях.

**Медіана** є середнім за порядком значенням: упорядкуйте числа й візьміть те, що посередині. Для трьох значень LCP
упорядкований ряд дає 756, 767, 770, тому медіана дорівнює 767. Медіану кожного показника рахують окремо: число для
LCP і число для CLS можуть належати різним прогонам.

Чому не середнє? У нашому застосунку числа майже однакові, бо сторінка дуже проста, тому розгляньмо показник, який
стрибав. Ми запустили `npm run dev`, а потім той самий цикл із адресою `http://localhost:5173/` і файлами `dev1.json`,
`dev2.json` і `dev3.json`:

```text
$ node report.mjs dev1.json dev2.json dev3.json
dev1.json LCP 757 0.8 s CLS 0 TBT 939 bytes 3712883 score 79
dev2.json LCP 646 0.6 s CLS 0 TBT 416 bytes 3712883 score 90
dev3.json LCP 645 0.6 s CLS 0 TBT 522 bytes 3712883 score 87
```

Колонка `TBT` дає три значення загального часу блокування, тобто часу, коли довгі
задачі заважали сторінці реагувати: 939, 416 і 522 мс. Медіана дорівнює 522, а середнє дорівнює 626, бо один повільний
прогін збільшує середнє. Якби цей прогін тривав не 939, а 9390 мс, медіана лишилася б 522, а середнє виросло б до
3443. Медіані байдуже, наскільки далеко лежить крайнє значення.

Документація Lighthouse пояснює, звідки беруться коливання: інші програми на комп'ютері, розширення браузера, мережа й
сама сторінка. Її приклади беруть п'ять прогонів, бо медіана п'яти прогонів удвічі стабільніша за один прогін. План
бере три, щоб замір лишався коротким, і однакові умови важать тут більше, ніж кількість. Закрийте важкі програми й
міряйте у вікні без розширень, наприклад інкогніто. У панелі Lighthouse у Chrome DevTools потрібен режим Navigation,
тобто замір завантаження сторінки, і мобільний пристрій. Цю панель ми не запускали, бо працювали з командним рядком,
тому назви пунктів уточніть на екрані.

### Не всі показники рухаються однаково

Ось той самий застосунок у двох режимах. У кожній комірці стоїть медіана трьох прогонів:

| Показник | `vite preview` | `npm run dev` |
|----------|----------------|---------------|
| LCP | 767 мс | 646 мс |
| Загальний час блокування | 0 мс | 522 мс |
| Загальний обсяг передачі | 69 642 байти | 3 712 883 байти |

Режим розробки передав у 53 рази більше даних і заблокував сторінку, а LCP у нього вийшов меншим. Це не означає, що
режим розробки швидший. Причини цієї різниці в LCP ми окремо не досліджували, а LCP у цьому випадку є результатом
моделі, а не секундоміра на справжньому телефоні. Висновок простий: одне число не дає вироку, а порівнювати можна лише
заміри з однаковими умовами. Тому заміри в цьому плані ніколи не роблять у режимі розробки, а рядок із `vite preview`
і рядок із викоченої адреси не варто порівнювати між собою.

### CLS: число, яке може бути більшим за нуль

CLS дорівнював нулю, бо наша сторінка нічого не зсуває. Додамо банер, який з'являється через 800 мс нагорі й штовхає
весь вміст униз. Масив `TEAS` у файлі лишається тим самим, а змінюється перший імпорт і функція `App`:

```tsx
// файл src/App.tsx
import { useEffect, useState } from 'react'

export default function App() {
  const [chosen, setChosen] = useState('нічого')
  const [banner, setBanner] = useState(false)
  useEffect(() => {
    // Через 800 мс після показу сторінки стан вмикає банер.
    const id = setTimeout(() => setBanner(true), 800)
    return () => clearTimeout(id)
  }, [])
  return (
    <main>
      {/* Банер стоїть над заголовком, тому штовхає вниз усе, що під ним. */}
      {banner && <p style={{ height: 300, margin: 0, background: '#eee' }}>Знижка на зелений чай</p>}
      <h1>{import.meta.env.VITE_SHOP_NAME}</h1>
      <ul>
        {TEAS.map((tea) => (
          <li key={tea.name}>
            <button onClick={() => setChosen(tea.name)}>
              {tea.name}, {tea.price} грн
            </button>
          </li>
        ))}
      </ul>
      <p>Обрано: {chosen}</p>
    </main>
  )
}
```

Ми зібрали застосунок і знову виконали той самий цикл Lighthouse на `vite preview`, цього разу з файлами `banner1.json`,
`banner2.json` і `banner3.json`:

```text
$ node report.mjs banner1.json banner2.json banner3.json
banner1.json LCP 766 0.8 s CLS 0.098 TBT 0 bytes 69761 score 98
banner2.json LCP 754 0.8 s CLS 0.098 TBT 0 bytes 69761 score 98
banner3.json LCP 755 0.8 s CLS 0.098 TBT 0 bytes 69761 score 98
```

Усі три прогони дали `CLS 0.098` замість нуля й оцінку 98 замість 100. Сайт web.dev називає добрим значення до 0,1 і
поганим понад 0,25, тому один банер уже підвів сторінку майже до межі доброго. Отже, вміст, який з'являється пізно над
іншими елементами, одразу погіршує це число. Ефект у цьому коді ви знаєте з теми «Синхронізація ефектами», а сама
затримка лише імітує дані, які надійшли пізно.

Є важливе обмеження. Сторінка web.dev про CLS каже, що лабораторні інструменти бачать лише зсуви під час завантаження.
Якщо вміст зсувається через хвилину роботи, Lighthouse цього не побачить, а справжні користувачі побачать. Тому нуль у
звіті Lighthouse означає лише «під час завантаження нічого не зсунулося».

### Чому INP сьогодні прочерк

**INP** показує, як швидко сторінка реагує на дії користувача. Щоб його виміряти, хтось має клацати. Lighthouse лише
завантажує сторінку, тому сторінка web.dev прямо каже, що він не може виміряти INP. У файлі звіту наших прогонів
такого показника теж немає: вираз `'interaction-to-next-paint' in audits` у скрипті `report.mjs` дає `false`.
Запис `0` означав би, що відгук миттєвий, а це неправда. Прочерк означає те, що є
насправді: заміру не було. Перше число в цій колонці ви отримаєте у фазі 2 на п'ятому дні, де самі натиснете клавіші
на повільному списку.

Межі показників нагадує така таблиця. Лекція «Інструменти браузера» вже пояснила, що web.dev оцінює за ними дані
справжніх користувачів, а не один лабораторний прогін, тому для вашого заміру це орієнтир, а не вирок.

| Показник | Добре | Погано |
|----------|-------|--------|
| LCP | до 2,5 с | понад 4 с |
| CLS | до 0,1 | понад 0,25 |
| INP | до 200 мс | вивчатиме фаза 2 |

## Журнал вимірів

**Журнал вимірів** є таблицею в README вашого проєкту. Скелет README із розділу плану про репозиторій уже її містить,
разом із рядком «Жива версія» для адреси. Ось звідки беруться числа кожної колонки:

| Колонка | Що в ній | Звідки її взяти |
|---------|----------|-----------------|
| Дата | коли зроблено замір | сьогоднішня дата |
| Що змінили | яку одну зміну оцінює цей рядок | ваші власні слова |
| LCP | медіана трьох прогонів | Lighthouse, режим mobile |
| INP | прочерк до фази 2 | ручний замір у фазі 2 |
| CLS | медіана трьох прогонів | Lighthouse, режим mobile |
| JS, КБ gzip | розмір головного JS-файла після gzip | звіт `vite build` |

Журнал потрібен, бо пам'ять не зберігає чисел. Без нього фраза «після цієї зміни стало швидше» є враженням, а з ним це
можна перевірити. На співбесіді теж запитують число: скільки було, що зробили, скільки стало. Тому нові рядки
дописують, а старі не переписують, навіть якщо число вийшло поганим. Якщо ви змінили хостинг, напишіть про це в
колонці змін, бо наступне число отримане вже за інших умов.

План просить робити кожен замір однаково. Лише тому два рядки взагалі можна порівнювати.

**Сьогоднішній день і рецепт.** Практика цього плану йде за рецептом книжки How to Design Programs, де спершу
записують приклад із відомим результатом, а вже потім пишуть функцію. Збірку, викот і заміри тести не перевірять, бо
результат залежить від мережі, хостингу й браузера. Тому за рецептом ви сьогодні пишете лише маленькі функції журналу
вимірів. Для решти дня працює сама звичка: перед кожною командою скажіть, що ви очікуєте побачити. Якщо перед збіркою ви думаєте про один JS-файл, а бачите два, це вже привід розібратися.

## Типові хибні уявлення

**«Код скорочено, тому секрет важко знайти».** Скорочення змінює імена змінних, а рядки лишає. Пошук `grep` знайшов
наше вигадане значення в бандлі за одну команду.

**«Файл `.env` не в репозиторії, тому ключ у безпеці».** Значення змінної `VITE_*` збірка вписує в публічний файл. Де
лежав сам `.env`, після збірки вже неважливо.

**«`vite preview` працює, отже, на хостингу теж усе буде добре».** Цей сервер на незнайомий шлях відповідає
`index.html`, тому не показує тих поломок, яких варто чекати на хостингу. Він також може задавати інші заголовки, ніж
хостинг.

**«`npx vite build` пройшов, отже, збірка в порядку».** Ця команда не перевіряє типів. Перевіряє їх `tsc -b` усередині
`npm run build`, а він дивиться і на файли, яких бандл не містить.

**«Розмір у журналі дорівнює тому, що піде мережею».** Хостинг може стискати інакше. Наш файл у Brotli мав 58 557
байтів проти 68,87 кБ у звіті. Журнал потребує порівнюваного числа, а не точного.

**«Перший рядок показує, наскільки хороший мій код».** Застосунок із одним абзацом дав 68,58 кБ, бо майже весь бандл
становить React. Цінність мають зміни між рядками.

**«Один прогін Lighthouse дасть правильне число».** Прогони коливаються, а один випадковий результат може бути
крайнім. Медіана трьох прогонів зменшує вплив такого результату.

**«Режим розробки завжди дає гірші числа за всіма показниками».** У нашому замірі LCP у режимі розробки вийшов меншим,
а обсяг передачі в 53 рази більшим. Правило «не міряти в розробці» існує не тому, що там усі числа гірші, а тому, що
там працює інша програма.

**«CLS дорівнює нулю, отже, сторінка ніколи не стрибає».** Лабораторний замір бачить лише зсуви під час завантаження.

**«Адреса `192.168.x.x` відкривається з телефона, отже, застосунок викочено».** Така адреса працює лише у вашій мережі
й лише поки запущена команда на вашому комп'ютері.

## Підсумок фази 1

Двадцять днів тому ви не писали на React нічого. Подивімося, що тепер стоїть за вашими навичками.

**Компоненти й розмітка.** Перші шість днів показали, що компонент є функцією, яка отримує пропси й повертає опис
розмітки. JSX записує цей опис, умови й списки є звичайним JavaScript, ключ каже React, який елемент списку є який, а
чистота означає, що той самий вхід дає той самий опис. TypeScript перевіряє типи цього всього.

**Стан.** Наступні вісім днів пояснили пам'ять компонента. Подія просить новий стан, React викликає компонент знову, а
кожен рендер бачить власний знімок стану. Об'єкти й масиви замінюють, а не змінюють. Стан екрана описують набором
можливих станів, зайвих полів не зберігають, спільний стан піднімають до спільного предка. Складні переходи описує
редюсер, а контекст передає значення глибоко вниз без проміжних пропсів.

**Ref, ефекти й перший викот.** Останні шість днів показали, як компонент працює з тим, що лежить поза React. Ref
зберігає значення, яке не впливає на екран, а ефект синхронізує компонент зі сторонньою системою. Теми «Коли ефект не
потрібен», «Життєвий цикл ефекту й події поза ним» і «Залежності ефекту й власні хуки» показали, як рідко ефект
справді потрібен і чому список його залежностей описує код, а не ваші побажання. Сьогодні застосунок опиняється в
інтернеті.

План ставить дві умови завершення фази. Перша умова: ви можете сказати, чому компонент перемалювався, дивлячись на
код, а не вгадуючи. Якщо компонент перемалювався, то змінився його стан, або рендерився батько, або змінився контекст,
який він читає. Перевірте себе на власному коді: візьміть будь-який компонент і назвіть, що саме запускає його рендер.
Друга умова: застосунок живе в інтернеті, а в журналі є перший рядок. Якщо обидві умови виконано, фазу закрито.

## Як це проявиться далі в React

Фаза 1 навчила писати компоненти, а фаза 2 пояснює, що React робить із ними зсередини. Її головне правило таке: жодної
оптимізації без заміру до неї. Саме тому журнал з'явився раніше за оптимізації.

- **Фаза 2, день 1, профайлер.** Сьогоднішній замір показує, що сторінка завантажується за стільки-то, але не каже,
  який компонент винен. Профайлер називає компонент і мілісекунди. Заміри виконуються на зібраному застосунку або на
  окремій збірці для профілювання, а не в режимі розробки.
- **Фаза 2, дні 2–3, узгодження й пакетування.** Ви дізнаєтеся, за яким алгоритмом React порівнює дерева й чому кілька
  викликів `set` дають один рендер. Це поглибить те, що дали дні про рендер і про збереження стану.
- **Фаза 2, день 4, мемоізація.** Ви вимірюватимете, чи справді `useMemo` дав щось, і запишете результат числом.
- **Фаза 2, день 5, `useTransition`.** У журналі нарешті з'явиться перше число INP замість прочерку, бо ви самі
  натиснете клавіші на штучно повільному списку.
- **Фаза 3, день 1, маршрути.** Ви викотите застосунок із маршрутами й оновите сторінку на вкладеній адресі. У
  `vite preview` це працюватиме, а на хостингу без потрібного правила дасть 404. Розбір читання показує, де кожен
  хостинг задає таке правило.
- **Фаза 5, день 1, розділення коду.** Головний JS-файл стане меншим, а поруч з'являться інші файли, і колонка журналу
  покаже різницю.
- **Фаза 5, день 2, безпека.** Сьогоднішня пастка стане окремою вправою зі змінною `VITE_*` і пошуком її значення в
  `dist`.
- **Фаза 5, день 3, метрики.** Ви збиратимете LCP, INP і CLS від справжніх відвідувачів, а не лише з лабораторного
  заміру.
- **Фаза 5, день 6 і далі, викот.** Сьогоднішній викот є першою версією. Фаза 5 налаштовує кеш і заголовки, а далі
  застосунок працюватиме у вашому власному кластері, і ви продовжите той самий журнал вимірів.

## Перевірте себе

**1. Файл уроку ніхто не імпортує, але в ньому є помилка типу. Що зробить `npm run build` і що зробить
`npx vite build`?**

<details><summary>Відповідь</summary>

`npm run build` спершу виконує `tsc -b`, а той перевіряє всі файли в `src`, тому команда надрукує помилку й
зупиниться, не запустивши збірки. `npx vite build` типів не перевіряє й дивиться лише на те, до чого можна дійти
імпортами, тому збереться без помилки. Цей файл не потрапить у бандл. Правильна дія полягає у виправленні типу.

</details>

**2. Звіт збірки показує два JS-файли. Як визначити, який із них головний, і яке число піде в журнал?**

<details><summary>Відповідь</summary>

Головний файл названо в тезі `<script>` у `dist/index.html`. У журнал іде його розмір після gzip, тобто число зі
стовпця `gzip` у звіті збірки, а не розмір без стиснення.

</details>

**3. `curl` на `/assets/nope.js` у `vite preview` дав відповідь 200. Що там лежить і чому це може ввести в оману?**

<details><summary>Відповідь</summary>

Там лежить `index.html`, бо `vite preview` на незнайомий шлях повертає головну сторінку. Сервер, який просто шукає
файл, відповів би 404. Тому після успіху в `vite preview` пряме посилання на маршрут на хостингу все одно може дати
404, якщо не задано окремого правила.

</details>

**4. Застосунок викладено за адресою `https://example.org/shop/`. Сторінка біла, а у вкладці Network запит
`/assets/index-....js` отримав 404. Що сталося і як це виправити?**

<details><summary>Відповідь</summary>

Шлях у `index.html` починається від кореня адреси, а файл лежить у `/shop/assets/`. Збірка не знала про вкладений
шлях. Потрібно вказати `base: '/shop/'` у налаштуваннях Vite або передати `--base=/shop/` і зібрати застосунок знову.

</details>

**5. У файлі `.env` є `VITE_MAP_KEY`, а код її не читає. Чи є значення в бандлі? Що зміниться, якщо десь у коді
написати `console.log(import.meta.env)`?**

<details><summary>Відповідь</summary>

Поки код не читає змінної, значення в бандлі немає: наш пошук дав нуль збігів. Запис усього об'єкта вписує в бандл усі
змінні з префіксом `VITE_`, тому значення стане публічним. Проте покладатися на те, що його ніхто не прочитає, не
можна. Секрету в такій змінній не місце за жодних умов.

</details>

**6. Три прогони дали LCP 2,1 с, 2,2 с і 4,0 с. Що піде в журнал і чому не середнє?**

<details><summary>Відповідь</summary>

У журнал піде медіана, тобто 2,2 с. Середнє дорівнює приблизно 2,77 с, бо один крайній прогін сильно на нього впливає.
Медіані байдуже, наскільки далеко лежить крайнє значення.

</details>

**7. Чому в колонці INP сьогодні прочерк, а не 0?**

<details><summary>Відповідь</summary>

INP потребує дій користувача, а Lighthouse лише завантажує сторінку, тому заміру не було. Нуль означав би миттєвий
відгук, а це неправда. Перше число з'явиться у фазі 2 на п'ятому дні.

</details>

**8. У нашому замірі LCP у режимі розробки вийшов меншим, ніж на зібраному застосунку. Чому це не підстава міряти в
режимі розробки?**

<details><summary>Відповідь</summary>

Режим розробки є іншою програмою: він передав у 53 рази більше даних і заблокував сторінку на 522 мс, тоді як зібраний
застосунок не заблокував її взагалі. Користувач отримає саме зібраний застосунок. Одне число не описує швидкості, а
порівнювати можна лише заміри з однаковими умовами.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| збірка | робота `vite build`, після якої в `dist` лежать файли для викладання |
| бандл | файл, у який збірка склала код застосунку |
| хеш в імені файла | короткий рядок, обчислений із вмісту файла; новий вміст дає нове ім'я |
| викот | викладання застосунку в інтернет, після якого він доступний за адресою |
| статичний хостинг | сервіс, який зберігає готові файли й віддає їх за адресою, не виконуючи вашого коду |
| односторінковий застосунок | застосунок з одним `index.html`, де адреси обробляє JavaScript у браузері |
| `base` | параметр збірки, який каже, під яким шляхом житиме застосунок |
| `VITE_*` | змінні середовища, значення яких Vite вписує в публічний бандл |
| LCP | коли з'явився найбільший елемент першого екрана |
| CLS | наскільки вміст зсувався під час показу, число без одиниці виміру |
| INP | як швидко сторінка реагує на дії користувача |
| симульоване уповільнення | спосіб Lighthouse обчислити час за моделлю, не гальмуючи справжнього завантаження |
| медіана | середнє за порядком значення в упорядкованому ряду |
| журнал вимірів | таблиця в README, куди дописують числа після кожної зміни |

## Що читати далі

- Lighthouse Variability: чому прогони коливаються.
- JavaScript modules: сторінка MDN, де є попередження про модулі за адресою `file://`.
