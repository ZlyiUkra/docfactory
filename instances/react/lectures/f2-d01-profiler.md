# Лекція. Фаза 2, день 1. Профайлер

Фаза 2 має одне головне правило: жодної оптимізації без заміру до неї. Ця лекція дає інструменти для такого заміру.
Ви побачите, чому React має три різні збірки, що саме рахує число `actualDuration`, чого це число не бачить і чому
замір у режимі розробки може звинуватити не той компонент. Читання займе близько 50 хвилин.

Усі числа нижче отримано запуском. Приклади працювали на React 19.3.1 і Vite 8.3.5 у Chrome 157 без вікна, а час від
кліку до кадру ми додатково перевірили в Chrome 156 з вікном. Усе виміряно на одному ноутбуці під WSL, тому ваші числа
будуть іншими, а порівнювати варто співвідношення. Уповільнення процесора ми задавали командою протоколу інструментів
розробника `Emulation.setCPUThrottlingRate`. Вікно Chrome DevTools і вікно розширення React Developer Tools у цьому
запуску не відкривалися. Кожне твердження про них спирається на документацію чи вихідний код розширення, і поруч із
ним про це сказано.

Практика дня просить налаштувати збірку у вашому проєкті `spa` і заміряти його головний екран. Щоб не показувати
готового розв'язку, лекція бере інший об'єкт: екран складу з таблицею товарів, а псевдонім показує на вигаданому пакеті
платежів.

**Після лекції ви зможете пояснити:**

- чим відрізняються збірка розробки, продакшн-збірка й збірка для профілювання;
- чому `vite build --mode profile` сам по собі нічого не змінює в React і що робить псевдонім;
- чому у зібраному профілі компоненти можуть називатися однією літерою і як це виправити;
- що означають шість аргументів `onRender` і чим `actualDuration` відрізняється від `baseDuration`;
- чого `actualDuration` не бачить;
- як порахувати коміти однієї дії і чому їх буває два;
- чому уповільнений процесор не розтягує цикл, який чекає за годинником;
- як записати результат у журнал вимірів.

## Скарга: «кнопка гальмує»

На екрані складу є кнопка «Наступний склад». Вона показує інші 2000 товарів і підсумок за ними. Користувачі кажуть, що
кнопка гальмує. Ось код екрана:

```tsx
function expensiveTotal(items: Item[]): number {
  let sum = 0
  for (let round = 0; round < 400; round++) {
    for (const it of items) sum = (sum + it.qty * it.price * (round + 1)) % 1000003
  }
  return sum
}

function StockSummary({ items }: { items: Item[] }) {
  return <p>Підсумок: {expensiveTotal(items)}</p>
}

function StockRow({ item }: { item: Item }) {
  return (
    <tr>
      <td>{item.name}</td>
      <td>{item.qty}</td>
      <td>{item.price}</td>
    </tr>
  )
}

function StockTable({ items }: { items: Item[] }) {
  return (
    <table>
      <tbody>
        {items.map((it) => (
          <StockRow key={it.id} item={it} />
        ))}
      </tbody>
    </table>
  )
}

function WarehouseScreen() {
  const [w, setW] = useState(0)
  const items = makeItems(w)
  return (
    <main>
      <Toolbar name={WAREHOUSES[w % 3]} onNext={() => setW((v) => v + 1)} />
      <StockSummary items={items} />
      <StockTable items={items} />
    </main>
  )
}
```

Перш ніж читати далі, спробуйте вгадати, який компонент найдорожчий. Хтось скаже, що винна таблиця, бо рядків дві тисячі.
Хтось скаже, що винен підсумок, бо в ньому вісімсот тисяч кроків циклу. Слово «гальмує» не допомагає обрати між цими
версіями. Потрібні назва компонента й кількість мілісекунд, а інструмент, який їх дає, називають **профайлером**.

Наприкінці лекції буде видно, що режим розробки й збірка для профілювання дають на цьому екрані **різні** відповіді.

## Що саме відбувається між кліком і екраном

Лекція «Рендер, коміт і знімок стану» поділила оновлення на запуск, рендер і коміт, а лекція «Як браузер малює»
пояснила, що після цього браузер рахує розміщення й малює. Профайлер React міряє лише частину цього шляху. Запис одного
кліку на уповільненому в чотири рази процесорі показав такі відрізки:

| Відрізок | Хто працює | Час, мс |
|----------|------------|---------|
| рендер | React викликає ваші компоненти | 76,0 |
| коміт | React змінює документ і виконує `useLayoutEffect` | 28,5 |
| решта ефектів | React виконує `useEffect` | 19,2 |
| від кліку до наступного кадру, усього | усі разом, зокрема браузер | близько 240 |

Перші три рядки взято із запису продуктивності на збірці для профілювання, а цей запис сам додає витрат, тому рендер тут
довший, ніж у вимірах без запису нижче. Останній рядок виміряно окремо, без запису. Уже зараз видно важливе: навіть
ідеальний рендер не зробить кнопку миттєвою, бо більшу частину часу забирає те, що відбувається після нього.

Час від кліку до кадру залежить від того, чи чекає браузер кадру монітора. Chrome без вікна монітора не має, а Chrome
з вікном оновлює екран лише разом із кадром монітора. Тому ми повторили цей екран у Chrome 156 з вікном. Решту екрана
ми дописали самі, бо лекція її не показує, тож рендер там трохи інший. У вікні від кліку до кадру при уповільненні 4×
минуло близько 360 мс, тобто більше, ніж 240 мс без вікна. Висновок від цього не змінюється: більшу частину часу
забирає те, що відбувається після рендеру.

## Три збірки React

Ваш код весь час викликає той самий React, але пакет `react-dom` містить кілька варіантів коду. Подивіться на
перемикач, який лежить у файлі `node_modules/react-dom/profiling.js`:

```js
if (process.env.NODE_ENV === 'production') {
  checkDCE();
  module.exports = require('./cjs/react-dom-profiling.profiling.js');
} else {
  module.exports = require('./cjs/react-dom-profiling.development.js');
}
```

Файл `react-dom/client.js` влаштовано так само, лише імена інших файлів. Лекція «Інструменти браузера» вже пояснила, що
`vite build` підставляє `"production"` замість `process.env.NODE_ENV`, а зайва гілка зникає. Отже, вибір складається з
двох запитань: який вхід імпортовано і яке значення має `NODE_ENV`.

| Збірка | Імпорт | `NODE_ENV` | Чи викликає `onRender` | Чи міряє час кожного компонента | Перевірки розробки |
|--------|--------|------------|------------------------|--------------------------------|--------------------|
| розробка | `react-dom/client` | `development` | так | так | так |
| продакшн | `react-dom/client` | `production` | ні | ні | ні |
| профілювання | `react-dom/profiling` | `production` | так | так | ні |

Ми перевірили цю таблицю в браузері. У продакшн-збірці компонент `<Profiler>` стояв на місці, а `onRender` за
п'ятнадцять кліків не викликався жодного разу. Жодної помилки при цьому не було: `<Profiler>` просто мовчить, і це
легко прийняти за поломку власного коду.

Ще ми підставили маленьку заглушку на місце розширення й прочитали внутрішнє поле React `treeBaseDuration`, бо саме за
ним розширення перевіряє підтримку профілювання у своєму вихідному коді. У збірці розробки та збірці для профілювання
поле є, а у продакшн-збірці немає. Розширення в цьому запуску не встановлювалося. За його вихідним кодом, на збірці без
цього поля вкладка Profiler напише `Profiling not supported`.

Збірка для профілювання трохи важча й трохи повільніша за продакшн-збірку, бо вона міряє час. На нашому екрані:

| Збірка | Розмір JS, байтів | Після gzip, байтів | Клік до кадру, 4×, мс |
|--------|-------------------|--------------------|-----------------------|
| продакшн | 223 950 | 69 059 | 226,5 |
| профілювання | 241 436 | 74 391 | 242,9 |

Звідси два правила. Збірку для профілювання не викладають користувачам. А розмір у колонку журналу «JS, КБ gzip» беруть
лише зі звичайної продакшн-збірки, інакше рядки журналу перестануть порівнюватися.

## Режим збірки й псевдонім

Практика просить зробити окремий режим збірки, у якому React візьме файл для профілювання. Тут є дві окремі дії, і
важливо їх не сплутати.

### Режим сам по собі лише назва

**Режим** у Vite є назвою набору налаштувань. Команда `vite build` за замовчуванням має режим `production`, а параметр
`--mode` задає іншу назву. Режим робить дві речі: визначає, який файл `.env.<режим>` прочитати, і потрапляє в код як
`import.meta.env.MODE`. Значення `NODE_ENV` він не чіпає. Сторінка `Env Variables and Modes` прямо каже, що це два
різні поняття. Ми перевірили це в браузері на збірці `--mode profile`:

```text
import.meta.env.MODE = "profile", import.meta.env.PROD = true, import.meta.env.DEV = false
```

Отже, збірка з режимом `profile` лишається продакшн-збіркою. Звідси випливає помилка, яку легко зробити: якщо додати
лише `--mode profile`, у React нічого не зміниться. Ми зібрали проєкт із цим параметром, але без псевдоніма. Вийшов файл
у 223 897 байтів, тобто майже байт у байт звичайний, а `onRender` у ньому не працює.

### Псевдонім підміняє те, що написано в `import`

**Псевдонім** є правилом для збирача: коли в коді імпортують такий-то шлях, бери натомість інший. Налаштування
`resolve.alias` задає такі правила у файлі `vite.config.ts`. Псевдонім потрібен, щоб не правити імпорти в коді: файл
`main.tsx` лишається незмінним, а заміна живе в одному місці налаштувань. Документація React радить саме цей спосіб.

Покажімо механізм на вигаданому пакеті `pay-sdk`, який має два входи: `pay-sdk/live` для справжніх платежів і
`pay-sdk/sandbox` для пісочниці, де гроші не списуються. Код імпортує лише справжній вхід:

```js
// src/main.js
import { gateway } from 'pay-sdk/live'
console.log(import.meta.env.MODE, import.meta.env.PROD, gateway)
```

Налаштування вмикає заміну лише в режимі `demo`:

```js
// vite.config.js
import { defineConfig } from 'vite'

export default defineConfig(({ mode }) => ({
  resolve:
    mode === 'demo'
      ? { alias: { 'pay-sdk/live': 'pay-sdk/sandbox' } }
      : {},
}))
```

Розберімо цей файл рядками.

- `defineConfig` приймає не об'єкт, а функцію. Vite викликає її й передає об'єкт, у якому є поле `mode` із назвою
  поточного режиму. Без функції налаштування не знало б, який режим зараз запущено.
- Дужки навколо `{ ... }` після стрілки потрібні, щоб JavaScript зрозумів: функція повертає об'єкт, а не починає тіло.
- Умовний вираз обирає, що покласти в `resolve`. У режимі `demo` там лежить псевдонім, а в будь-якому іншому порожній
  об'єкт, тобто звичайна збірка лишається такою, якою була.
- Ключ `'pay-sdk/live'` є тим, що шукається в `import`, а значення `'pay-sdk/sandbox'` є тим, чим його замінюють.
  Значення теж є назвою пакета, тому Vite знаходить файл за полем `exports` цього пакета, як і для звичайного імпорту.

Дві збірки дали такий рядок у готовому файлі:

```text
vite build               → `справжні платежі`
vite build --mode demo   → `пісочниця`
```

Ваше завдання має ту саму будову, а пара назв записана в картці дня.

Запуск показав ще кілька меж цього механізму.

**Ключ замінює і початок довшого шляху.** Якщо записати коротший ключ, наприклад саму назву пакета без другої частини,
Vite замінить початок кожного імпорту. У нашому досліді псевдонім `'react-dom': 'react-dom/profiling'` зупинив збірку,
бо `react-dom/client` перетворився на шлях, якого пакет не має:

```text
"./profiling/client" is not exported under the conditions ["module", "browser", "production", "import"]
```

Такий текст означає, що ключ псевдоніма занадто короткий. Записуйте ключ повністю.

**Перевірка типів не бачить заміни.** Для коду застосунку `tsc -b` не застосовує псевдоніма: він бачить звичайний імпорт
і його типи. Тому хибну назву в значенні псевдоніма виявляє лише збірка.

**Сам файл налаштувань `tsc -b` перевіряє, і форма запису тут важлива.** Ми спробували умову в іншому місці, усередині
`alias`, тобто `resolve: { alias: умова ? { 'назва': 'заміна' } : {} }`. Збірка спрацювала, а `tsc -b` зупинився:

```text
vite.config.ts(3,29): error TS2769: No overload matches this call.
```

Причина в тому, як TypeScript записує тип умовного виразу з двох об'єктів. Для порожнього об'єкта він додає те саме поле
як необов'язкове зі значенням `undefined`, а `resolve.alias` вимагає, щоб усі значення були рядками. Ця помилка підступна:
`npx vite build` типів не перевіряє й проходить, а `npm run build` падає, бо починається з `tsc -b`. Запис із прикладу вище,
де умова обирає весь об'єкт `resolve`, проходить і `tsc -b`, і збірку. Запис із окремою змінною
`const alias: Record<string, string> = умова ? { ... } : {}` теж пройшов обидві перевірки.

**Псевдонім у режимі розробки не робить React швидшим.** Ми запустили `vite --mode profile`. Сторінка працювала, але
`import.meta.env.DEV` дорівнював `true`, а за перемикачем, який ви бачили вище, файл `profiling.js` у розробці бере
`react-dom-profiling.development.js`. Сервер розробки лишається режимом розробки. Міряти треба зібраний файл.

### Куди лягає збірка

Команда `vite build --mode profile` за замовчуванням пише в ту саму теку `dist`, спершу очистивши її. Ми зібрали профіль,
а потім виконали звичайний `npm run build`: файл для профілювання зник. Гірше буває навпаки: якщо викласти теку `dist`
після замірів, користувачі отримають збірку для профілювання. Тому зручно задавати окрему теку параметром
`--outDir dist-profile`, а потім запускати `vite preview --outDir dist-profile`. Ми перевірили обидві команди.

Окрема тека має ще один наслідок. Рядок `dist` у файлі `.gitignore` вашого шаблону закриває лише теку з точно такою
назвою, і запуск `git status` показав файли з `dist-profile` як нові. Цю теку треба дописати в `.gitignore`.

Запис `npm run build -- --mode profile` теж працює: спершу виконується `tsc -b`, а параметр після двох рисок дістається
команді `vite build`. Команда `npx vite build --mode profile` типів не перевіряє.

## Чому компоненти називаються однією літерою

Тут запуск показав те, про що картка дня не згадує. Мінімізатор скорочує імена функцій, а React бере назву компонента з
імені функції. Ось що побачили інструменти на збірці, зробленій лише з псевдонімом:

| Назва в коді | Назва у збірці для профілювання |
|--------------|---------------------------------|
| `WarehouseScreen` | `ee` |
| `Toolbar` | `b` |
| `StockSummary` | `_` |
| `StockTable` | `y` |
| `StockRow` | `v` |

Рядок «найдорожчий компонент: `_`» нічого не каже. Числа при цьому правильні, але невідомо, чиї вони. Мітка `id` у
`<Profiler>` лишається читабельною, бо вона є рядком, а не іменем функції.

Виправлення теж належить лише режиму профілювання. Збирач Rolldown, на якому працює Vite 8, має параметр
`output.keepNames`, який зберігає властивість `name` у функцій. Vite передає такі параметри через `build.rolldownOptions`:

```ts
build: { rolldownOptions: { output: { keepNames: true } } },
```

Цей рядок ставте за тією самою умовою режиму, що й псевдонім, тобто умова обирає весь об'єкт `build`. Такий запис пройшов
`tsc -b` і збірку. Другий спосіб, `build: { minify: false }`, вимикає
мінімізацію взагалі. Порівняння на нашому екрані:

| Збірка для профілювання | Розмір JS, байтів | Назви в інструментах | `actualDuration`, 4×, мс |
|-------------------------|-------------------|----------------------|--------------------------|
| лише псевдонім | 241 436 | одна-дві літери | 55,3 |
| з `keepNames` | 308 178 | справжні | 56,3 |
| з `minify: false` | 631 422 | справжні | не міряли |

Різниця 55,3 і 56,3 менша за коливання між кліками, тому на час рендеру `keepNames` помітно не вплинув. Розмір виріс,
бо зберігати імена доводиться й у всьому коді React, але користувачам цей файл не йде. Параметр перевірено на Vite
8.3.5. Сторінки React про цю проблему не пишуть, тому після оновлення Vite звірте назву параметра з документацією.

## Компонент `<Profiler>`

Розширення браузера показує заміри людині, а компонент `<Profiler>` віддає їх вашому коду. Він не малює нічого на екрані:
він огортає частину дерева й повідомляє, скільки коштувало її оновлення.

```tsx
import { Profiler, type ProfilerOnRenderCallback } from 'react'

const logRender: ProfilerOnRenderCallback = (id, phase, actual, base) => {
  console.log(id, phase, actual.toFixed(1), base.toFixed(1))
}

function Main() {
  return (
    <Profiler id="WarehouseScreen" onRender={logRender}>
      <WarehouseScreen />
    </Profiler>
  )
}
```

- `Profiler` імпортують із `react`, а не з `react-dom`. Саме тому імпорт у коді не змінюється від збірки до збірки.
- `ProfilerOnRenderCallback` є типом функції з пакета `@types/react`. Завдяки йому TypeScript знає типи всіх аргументів.
- Проп `id` є будь-яким рядком, за яким ви потім відрізните цей замір від інших.
- Проп `onRender` є функцією, яку React викличе сам після оновлення дерева всередині. Такі функції називають колбеками.
- `toFixed(1)` обрізає число для читання. Без нього ви побачите щось на кшталт `15.600000000093132`.

Збірка для профілювання надрукувала в консоль такі рядки: перший для першого показу, другий після кліку.

```text
WarehouseScreen mount 34.9 23.5
WarehouseScreen update 16.6 15.4
```

### Шість аргументів `onRender`

| Аргумент | Що це | Приклад значення |
|----------|-------|--------------------|
| `id` | рядок із пропа `id` | `WarehouseScreen` |
| `phase` | `mount` при першому показі, `update` при оновленні, `nested-update` про особливий випадок нижче | `update` |
| `actualDuration` | скільки мілісекунд зайняв рендер цього `<Profiler>` і його нащадків саме цього разу | `16.6` |
| `baseDuration` | оцінка, скільки зайняв би рендер усього піддерева без пропусків | `15.4` |
| `startTime` | мітка часу, коли React почав рендер цього оновлення | `341.7` |
| `commitTime` | мітка часу, коли React завершив цей коміт; вона спільна для всіх `<Profiler>` одного коміту | `342.0` |

Числа мають крок 0,1 мс. Причина в браузері: сторінка MDN про `performance.now()` каже, що в документі без ізоляції від
інших джерел час округлено до 100 мікросекунд. Тому значення `0.0` не означає нуль. Воно означає «менше за крок».

### Коли React викликає `onRender`

Сторінка каже, що React викликає функцію, коли компонент усередині дерева дійшов до коміту. Подивімося, як це працює
в граничних випадках.

**Стан поза деревом.** Кнопка стоїть поруч із `<Profiler>`, тобто не всередині:

```text
клік по сусідній кнопці   → викликів onRender: 0
клік по кнопці всередині  → inner update, actual 0.1
```

Якщо огорнути лише частину екрана, зміни поза нею у замір не потраплять.

**Вкладені заміри й пропущений компонент.** Огорнемо кнопку й важкий компонент у зовнішній `<Profiler>`, а важкий
компонент ще й у внутрішній. Цей компонент обгорнуто в `memo`, тобто React не викликає його заново, поки пропси ті самі.
Обгортку `memo` згадувала лекція «Чистота й дерево», а докладно вона буде на дні 4. Після кліку по кнопці:

```text
inner-memo  update  actual 0.0  base 31.3  commit 342.0
inner-plain update  actual 0.0  base 0.0   commit 342.0
outer       update  actual 0.2  base 31.4  commit 342.0
```

Цей вивід показує три речі.

1. Внутрішні заміри приходять раніше за зовнішні, а `commitTime` у всіх однакове. Отже, це один коміт, хоча рядків три.
   Рахувати коміти кількістю викликів не можна, якщо `<Profiler>` кілька.
2. Значення `actualDuration` у важкого компонента майже нульове, бо React його пропустив, а `baseDuration` пам'ятає,
   скільки він коштував востаннє. Отже, різниця між цими двома числами показує, скільки заощадив пропуск: тут близько
   31 мс. Цим ви скористаєтеся на дні 4, коли питатимете, чи допомогла мемоізація.
3. Запис `update` тут не означає, що компонент викликано. Функцію `onRender` викликано, бо рендер зовнішнього компонента
   дійшов до внутрішнього `<Profiler>`, а сам важкий компонент не виконувався.

Зовнішній `actualDuration` включає внутрішні. Під час першого показу вони дорівнювали 33,1 і 31,4 мс відповідно, тому
рядки вкладених замірів не можна додавати.

### Як знайти найдорожчий компонент кодом

Один `<Profiler>` навколо екрана дає лише одне число на весь екран, а назви компонента не дає. Щоб отримати назву, є
два шляхи: читати вікно розширення, про яке йдеться нижче, або додати тимчасові `<Profiler>` навколо підозрюваних. Ми
зробили другий варіант і огорнули окремо підсумок і таблицю:

```text
StockSummary    actual 37.6
StockTable      actual 20.6
WarehouseScreen actual 59.6
```

Це медіани десяти кліків на збірці для профілювання при уповільненні 4×. Документація нагадує, що кожен `<Profiler>`
додає трохи витрат, тому такі обгортки після заміру прибирають.

## Чого `actualDuration` не бачить

Назва сторінки React каже про вимірювання рендеру, і це буквально так. Ми написали компонент, де ефекти виконують важку
роботу, а саме 3 000 000 кроків циклу, які на цій машині займають 38,4 мс:

```tsx
useLayoutEffect(() => {
  burnSteps(3000000)
}, [t])
useEffect(() => {
  burnSteps(3000000)
}, [t])
```

```text
actualDuration, медіана семи кліків: 0.1 мс
```

Близько 77 мс роботи в ефектах не потрапило в замір. Те саме стосується запису в документ, розміщення й малювання. Тому
число `actualDuration` відповідає лише на запитання «скільки коштували виклики компонентів». Воно не відповідає на
запитання «як довго людина чекала». Таблиця на початку лекції показала, що на нашому екрані людина чекала близько 240 мс,
а `actualDuration` становив 56 мс. На запитання про очікування відповідає показник INP, і його перший замір буде на дні 5
цієї фази.

Ця межа може спотворити й порівняння двох варіантів коду. Лекція «Узгодження дерева» наступного дня міряє скидання великого
піддерева: за `actualDuration` воно виглядає лише вдвічі дорожчим за оновлення, а вся робота, разом зі зміною документа й
компонуванням браузера, вдесятеро дорожча. Тому порівнюючи варіанти, де змінюється кількість вузлів документа, дивіться
ще на час від кліку до кадру чи на доріжки React.

## Скільки комітів дає одна дія

Журнал просить записати кількість комітів на одну дію. Здається, що клік завжди дає один коміт. На екрані складу так і є,
але ось компонент, який після кліку ще раз змінює стан в ефекті:

```tsx
useEffect(() => {
  setLabel(`клік ${t}`)
}, [t])
```

Один клік дає такі виклики `onRender`:

```text
з useEffect:       update (commit 550.2), update (commit 551.7)
з useLayoutEffect: update (commit 539.0), nested-update (commit 539.2)
```

Два різні значення `commitTime` означають два коміти. Користувач зробив одну дію, а React двічі пройшов шлях від рендеру до
коміту. Значення `nested-update` з'являється тоді, коли оновлення запустив код на етапі коміту, як-от `useLayoutEffect`.
Для `useEffect` у нашому запуску було звичайне `update`, тому за самим `phase` такий каскад не впізнати.

Лекція «Коли ефект не потрібен» пояснила, чому такий код зазвичай зайвий, а правило лінту
`react-hooks/set-state-in-effect` позначило обидва варіанти як помилку. Тепер у вас є число, яке показує ціну цього
коду: два коміти замість одного.

Отже, рахуйте коміти одного кореневого `<Profiler>` або рахуйте різні значення `commitTime`.

## Чому `onRender` не можна використовувати для показу на екрані

Хочеться показати `actualDuration` просто на екрані, записавши його у стан компонента, який містить `<Profiler>`. Запустімо
такий код:

```tsx
<Profiler id="loop2" onRender={() => setN((v) => v + 1)}>
  <p>{n}</p>
</Profiler>
```

Зміна стану запускає рендер, рендер запускає `onRender`, а той знову змінює стан. У нашому запуску React зробив 53 виклики,
кинув помилку й прибрав увесь застосунок зі сторінки: елемент `#root` став порожнім. У збірці текст помилки скорочено до
`Minified React error #185`, а в розробницькому файлі React це повідомлення починається словами `Maximum update depth
exceeded`. Виводьте заміри в консоль чи в масив, а не в стан.

## Уповільнення в чотири рази

Лекція «Інструменти браузера» вже пояснила, що ваш ноутбук значно швидший за типовий телефон і що уповільнення рахується
від вашого комп'ютера. За документацією Chrome DevTools його вмикають на вкладці Performance: кнопка налаштувань запису
**Capture Settings**, поле **CPU**, значення **4x slowdown**. Цього вікна ми не відкривали, тому порівняйте назви зі своїм
екраном.

Наш запуск дав результат, який треба знати, перш ніж писати дослідний компонент. Ми порівняли два способи «зробити
компонент повільним»: цикл, який чекає 20 мс за годинником, і цикл зі сталою кількістю кроків.

| Компонент | Як витрачає час | 1×, мс | 4×, мс |
|-----------|-----------------|--------|--------|
| `TimeBurner` | `while (performance.now() < end)` | 20,0 | 20,2 |
| `StepBurner` | 3 000 000 кроків обчислення | 33,9 | 129,3 |

Уповільнення зменшує швидкість виконання, а не змінює годинник. Цикл за годинником зупиняється в той самий момент часу і
просто встигає зробити менше кроків. Цикл зі сталою кількістю кроків справді розтягується, тут у 3,8 раза. Справжні
обчислення поводяться як другий рядок. Тому повільний компонент для досліду пишіть зі сталою кількістю кроків, бо інакше
уповільнення нічого не покаже.

З цього випливає й проста перевірка вашого заміру. Заміряйте ту саму дію без уповільнення й з ним. Якщо `actualDuration`
виріс приблизно вчетверо, то уповільнення справді діє. На нашому екрані у збірці для профілювання було 13,6 і 55,3 мс, тобто
у 4,1 раза. Це важливо, бо ми не змогли перевірити, чи діє значення з вкладки Performance під час запису на вкладці
Profiler розширення. Консольний рядок від `<Profiler>` відповідає на це запитання на вашій машині.

## Покроковий приклад: розробка проти профілювання

Тепер заміряймо екран складу. Порядок дій такий: зібрати, відкрити зібрану сторінку, увімкнути уповільнення,
клацнути 16 разів, відкинути перший клік, бо код ще не «розігрітий», і взяти медіану решти.

| Збірка | `actualDuration`, 1×, мс | `actualDuration`, 4×, мс | Розкид при 4× | Клік до кадру, 4×, мс |
|--------|--------------------------|--------------------------|---------------|-----------------------|
| розробка зі `<StrictMode>` | 61,9 | 761,7 | 704,7–1300,8 | 1068,6 |
| розробка без `<StrictMode>` | 34,8 | 660,0 | 572,0–695,2 | 947,7 |
| профілювання з `keepNames` | 12,4 | 56,3 | 52,1–66,5 | 241,8 |
| профілювання | 13,6 | 55,3 | 49,4–69,3 | 242,9 |
| продакшн | немає | немає | немає | 226,5 |

Колонку «Клік до кадру» ми отримали в Chrome без вікна. У Chrome 156 з вікном на тому самому екрані з нашими даними
медіана при 4× була такою: розробка зі `<StrictMode>` 1357,7 мс, розробка без нього 1272,5 мс, профілювання з
`keepNames` 347,7 мс, профілювання 358,2 мс, продакшн 311,3 мс. У вікні всі числа більші, бо браузер чекає кадру
монітора, але порядок збірок той самий: розробка найповільніша, а продакшн трохи швидший за профілювання.

Без уповільнення режим розробки завищив рендер у 2,6–4,6 раза, а при уповільненні у 12–14 разів. Частину цього дає `<StrictMode>`: лекція «Чистота й дерево»
пояснила, що він викликає компонент двічі, і лічильник це підтвердив, бо `StockSummary` у розробці зі `<StrictMode>`
виконувався двічі на клік, а в зібраному профілі один раз. Проте й без `<StrictMode>` різниця лишається дуже великою.
Множник між 1× і 4× у режимі розробки вийшов не 4, а більше, і числа там коливалися сильно: у попередньому прогоні
значення при 1× становило 132 мс. Причини цього ми не розкладали. Для нас досить висновку, що такі числа не можна брати
за основу.

Гірше за масштаб те, що змінюється **порядок**. Ось власний час кожного компонента, тобто час без його дочірніх
компонентів, при 4×. Рахували його так само, як рахує розширення у своєму вихідному коді, але самого розширення не
запускали.

| Компонент | Розробка зі `<StrictMode>`, мс | Розробка без нього, мс | Профілювання з `keepNames`, мс |
|-----------|--------------------------------|------------------------|------------------|
| `StockRow`, 2000 викликів разом | 358,2 | 406,6 | 7,4 |
| `StockTable` | 229,9 | 100,3 | 1,1 |
| `StockSummary` | 76,3 | 35,8 | 40,5 |
| `WarehouseScreen` | 2,5 | 1,5 | 1,0 |
| `Toolbar` | 0,3 | 0,1 | 0,0 |

Режим розробки каже: винні рядки таблиці, а підсумок майже не важить. Збірка для профілювання каже навпаки: підсумок дорожчий
за всю таблицю в кілька разів. Людина, яка повірила режиму розробки, кинеться загортати рядки в `memo` і майже нічого не
виграє, а справжня причина лишиться. Це і є пастка дня, показана числами. Найімовірніше пояснення таке: у режимі розробки
React робить для кожного елемента додаткову роботу заради налагодження, а чисте обчислення `expensiveTotal` елементів не
створює, тому його час майже не змінюється. Цю частину пояснення ми окремо не вимірювали.

Сума чисел у колонці «Профілювання» менша за 56,3 мс. Решта належить звичайним елементам `tr` і `td`, бо React теж
обробляє їх під час рендеру, а до власного часу компонентів вони не входять. Саме тому заміряний вище `StockTable` разом
із нащадками зайняв 20,6 мс, хоча власні 1,1 і 7,4 мс дають менше.

## Вікно React Developer Tools

Лекція «Контекст» розповіла, де взяти розширення і що показує підсвічування. Сьогодні потрібна друга його вкладка, Profiler.
Весь цей розділ написано за вихідним кодом розширення й давнім дописом React `Introducing the React Profiler`, а вікно ми не
запускали. Тому порівняйте написане зі своїм екраном.

1. Відкрийте зібрану збірку для профілювання адресою від `vite preview`.
2. На вкладці Performance задайте уповільнення. Значення на вкладці Profiler перевірте консольним рядком.
3. На вкладці Profiler натисніть кнопку запису, зробіть **одну** дію й зупиніть запис.

Далі вікно показує таке.

- **Смужки комітів угорі.** Кожна смужка є одним комітом. Кількість смужок на одну дію і є числом для журналу. Вища й жовтіша
  смужка коштувала більше.
- **Вигляд Flamegraph.** Це дерево компонентів, де для кожного написано два числа у форматі `2ms of 5ms`: власний час і час
  разом із дочірніми. Сірий колір означає, що компонент у цьому коміті не рендерився.
- **Вигляд Ranked.** Це той самий коміт, відсортований за власним часом, тому найдорожчий компонент стоїть зверху. Давній допис
  каже, що час у цьому вигляді включає дочірні компоненти, але поточний вихідний код сортує й підписує рядки власним часом.
  Довіряйте вихідному коду.
- **Налаштування `Record why each component rendered while profiling`.** Ця позначка в налаштуваннях вкладки Profiler додає
  блок `Why did this render?`, де видно, які пропси чи стан змінилися.

Документація Chrome радить міряти у вікні інкогніто, бо розширення додають шум. Розширення React теж є розширенням. Тому
число для порівняння «до й після» надійніше брати з консольного рядка `<Profiler>` у вікні без розширень, а вікном
розширення користуватися, щоб дізнатися назву компонента. Скільки саме шуму додає це розширення, ми не міряли.

## Доріжки React на вкладці Performance

Третій інструмент не потребує розширення. Сторінка `React Performance tracks` описує доріжки, які React додає до запису на
вкладці Performance. Ми записали такий запис програмно й прочитали його як дані, а екрана панелі не бачили.

| Збірка | Що є в записі | Компоненти на доріжці `Components ⚛` |
|--------|---------------|--------------------------------------|
| продакшн | жодної мітки React | немає |
| профілювання, стан поза `<Profiler>` | `Scheduler ⚛` | немає |
| профілювання, стан усередині `<Profiler>` | `Scheduler ⚛`, `Components ⚛` | `ee`, `b`, `_`, `y`, `v` |
| профілювання з `keepNames` | те саме | `WarehouseScreen`, `Toolbar`, `StockSummary`, `StockTable`, `StockRow` |

Це збігається зі сторінкою: у збірці для профілювання доріжка компонентів показує лише те, що лежить усередині `<Profiler>`.
Сторінка додає, що з увімкненим розширенням там будуть усі компоненти, цього ми не перевіряли. На доріжці `Scheduler ⚛` у
підрозділі `Blocking` ми побачили мітки `Event: click`, `Update`, `Render`, `Commit` і `Remaining Effects`. Саме звідси взято
таблицю на початку лекції. Перевага цього способу в тому, що рендер, коміт, мережа й малювання видно на одній шкалі часу.

## Як записати результат

Картка просить у журналі рядок із трьома значеннями: найдорожчий компонент, його час і кількість комітів на одну дію.
Таблиця журналу, яку ви завели в темі «Збірка, перший викот і журнал вимірів», має інші колонки: дата, що змінили, LCP, INP,
CLS і розмір JS. Тому запишіть цей результат у колонку «Що змінили», а решту заповніть прочерками, бо Lighthouse ви сьогодні
не запускали, а файл для профілювання не йде користувачам:

```text
| дата | Профіль дії «Наступний склад», збірка для профілювання, 4×: найдорожчий StockSummary 40,5 мс, увесь екран 56,3 мс, 1 коміт | — | — | — | — |
```

Число біля компонента в цьому прикладі є його власним часом, який показало б вікно розширення. Якщо ви огорнули компонент
окремим `<Profiler>`, то запишіть його `actualDuration` разом із нащадками і так і вкажіть. Назвіть у рядку дію, збірку й
уповільнення, бо без цих умов число не можна порівняти з наступним. Лекція про журнал уже
пояснила, чому порівнювати можна лише заміри, зроблені однаково. Це стосується і збірки: число зі збірки для профілювання
порівнюйте лише з числом із такої самої збірки.

Сьогодні не потрібно нічого виправляти. Правило фази каже: спершу замір. Ви отримуєте точку «до», а виправлення прийдуть у
наступні дні.

Рецепт How to Design Programs, за яким іде практика плану, просить записати очікування до написання коду. Тут це працює так:
перед записом профілю напишіть у чернетці, який компонент вважаєте найдорожчим. Якщо вгадали, ви перевірили свою модель. Якщо
ні, ви знайшли те, чого не розуміли.

## Типові хибні уявлення

**«Заміряю в `npm run dev`, бо так зручніше, а порядок компонентів і так збережеться».** На нашому екрані порядок помінявся:
режим розробки ставив на перше місце `StockRow`, а збірка для профілювання `StockSummary`.

**«Параметр `--mode profile` вмикає профілювання».** Режим є лише назвою. Без псевдоніма файл вийшов майже байт у байт такий
самий, як звичайний, а `onRender` не викликався.

**«Якщо `onRender` мовчить, я помилився в коді».** У продакшн-збірці він мовчить завжди, і це задумана поведінка.

**«`actualDuration` показує, скільки людина чекала».** Він рахує лише виклики компонентів. На нашому екрані рендер займав 56 мс
із приблизно 240 мс очікування, а робота в ефектах у нього взагалі не потрапляє.

**«Кількість рядків від `onRender` дорівнює кількості комітів».** При трьох `<Profiler>` один коміт дав три рядки зі спільним
`commitTime`. Рахуйте різні значення `commitTime`.

**«`update` означає, що компонент викликано».** Важкий компонент у `memo` дав `update` із `actualDuration` 0,0, бо React його
пропустив.

**«Щоб зробити компонент повільним для досліду, досить почекати в циклі».** Цикл за годинником під уповільненням не змінюється:
20,0 мс проти 20,2 мс.

**«`npx vite build` пройшов, отже, налаштування правильне».** Ця команда не перевіряє типів. Запис із умовою всередині `alias`
пройшов її, а `npm run build` зупинився на помилці TS2769.

**«Одна літера в назві означає, що замір зіпсований».** Числа правильні, зіпсовано лише імена. Параметр `keepNames` повертає
імена й на нашому екрані не змінив час помітно.

## Як це проявиться далі в React

- **День 2, узгодження дерева.** Ви побачите, що зміна типу обгортки знищує все піддерево, а `actualDuration` показує лише
  частину ціни цього скидання.
- **День 3, пакетування оновлень.** Практика рахує коміти через `onRender`, тому сьогоднішнє правило про `commitTime` стане
  вашим робочим інструментом.
- **День 4, мемоізація й React Compiler.** Порівняння `actualDuration` з `baseDuration` покаже, що дала мемоізація, а збірка
  для профілювання дасть точку «до» й «після».
- **День 5, `useTransition` і перший замір INP.** Там з'явиться показник очікування людини, якого `actualDuration` не бачить.

## Перевірте себе

**1. Ви виконали `vite build --mode profile`, але не додали псевдонім. Що буде з `<Profiler>` і чому?**

<details><summary>Відповідь</summary>

Функція `onRender` не викликатиметься. Режим змінює лише назву й файл `.env`, а `NODE_ENV` лишається `production`, тому
`react-dom/client` бере звичайний продакшн-файл, у якому заміри вимкнено.

</details>

**2. Чому псевдонім у режимі розробки не дає чисел як у зібраній збірці?**

<details><summary>Відповідь</summary>

Файл `react-dom/profiling.js` сам обирає варіант за `NODE_ENV`. У режимі розробки значення не `production`, тому він бере
`react-dom-profiling.development.js` із усіма перевірками розробки. Міряти треба зібраний файл.

</details>

**3. Вкладка показує найдорожчий компонент `_`. Що сталося, чи правильні числа і що зробити?**

<details><summary>Відповідь</summary>

Мінімізатор скоротив ім'я функції, а React бере назву саме з нього. Числа правильні, невідомо лише, чиї вони. У режимі
профілювання треба зберегти імена параметром `output.keepNames` чи вимкнути мінімізацію.

</details>

**4. Внутрішній `<Profiler>` дав `actualDuration` 0,0 і `baseDuration` 31,3. Що це означає?**

<details><summary>Відповідь</summary>

React пропустив виклик цього компонента, тому фактичний рендер майже нічого не коштував. Значення `baseDuration` показує, що
повний рендер коштував би близько 31 мс. Різниця є оцінкою того, що заощадив пропуск.

</details>

**5. Ефект працює 40 мс на кожен клік. Скільки з цього покаже `actualDuration`?**

<details><summary>Відповідь</summary>

Нічого. Це число міряє лише рендер. У нашому запуску компонент із двома важкими ефектами показав 0,1 мс.

</details>

**6. Функція `onRender` за один клік отримала три виклики. Скільки комітів сталося?**

<details><summary>Відповідь</summary>

Цього не можна сказати лише за кількістю викликів. Якщо `<Profiler>` кілька, один коміт дає кілька викликів зі спільним
`commitTime`. Треба порахувати різні значення `commitTime` або читати виклики одного кореневого `<Profiler>`.

</details>

**7. Ви написали дослідний компонент із циклом `while (performance.now() < end)` і увімкнули уповільнення 4×. Час не змінився.
Чому, і чи означає це, що уповільнення не працює?**

<details><summary>Відповідь</summary>

Такий цикл закінчується за годинником, а уповільнення не змінює годинника, лише швидкість виконання. Уповільнення може
працювати цілком нормально. Перевірте його циклом зі сталою кількістю кроків: у нашому запуску він виріс із 33,9 до 129,3 мс.

</details>

**8. Чому результат зі збірки для профілювання не можна порівнювати з результатом режиму розробки, навіть якщо обидва
отримано при 4×?**

<details><summary>Відповідь</summary>

Вони описують різні програми. Режим розробки виконує додаткову роботу для кожного елемента, а `<StrictMode>` у ньому викликає
компоненти двічі. У нашому замірі рендер відрізнявся у 12–14 разів, а порядок компонентів за часом змінився.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| профайлер | інструмент, який показує, що працювало й скільки часу це зайняло |
| збірка для профілювання | варіант React без перевірок розробки, але із замірами часу, вхід `react-dom/profiling` |
| режим у Vite | назва набору налаштувань, яку задає `--mode` |
| `NODE_ENV` | окреме значення, за яким React обирає файл розробки чи продакшн |
| псевдонім | правило для збирача: імпорт одного шляху замінити на інший |
| мінімізатор | програма, яка зменшує файл, зокрема скорочуючи імена |
| `actualDuration` | мілісекунди рендеру піддерева саме цього разу |
| `baseDuration` | оцінка рендеру всього піддерева, якби нічого не було пропущено |
| власний час | час компонента без часу його дочірніх компонентів |
| колбек | функція, яку ви передаєте, а викликає її інший код |
| каскад | оновлення, запущене вже після коміту, через яке одна дія дає кілька комітів |
| медіана | середнє за порядком значення серед відсортованих чисел, менш чутливе до випадкових викидів |
