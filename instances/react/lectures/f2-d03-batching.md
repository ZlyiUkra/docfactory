# Лекція. Фаза 2, день 3. Пакетування оновлень

На співбесіді часто питають: «Скільки разів це відрендериться?». Лекція «Рендер, коміт і знімок стану» вже показала,
що кілька викликів `set` зазвичай дають один рендер. Сьогодні ви побачите, за яким алгоритмом це стається, коли один
пакет розпадається на кілька, що робить `flushSync` і скільки він коштує. Читання займе близько 50 хвилин.

Числа в лекції отримано на React 19.3.1 у браузері `chrome-headless-shell` версії 157, тобто в Chromium без вікна.
Виняток становить замір «Скільки коштує `flushSync` усюди»: час до кадру залежить від монітора, тому цей замір
зроблено в Chrome 156 з вікном. Клацання були справжніми подіями миші, які браузеру надсилав протокол інструментів
розробника. Якщо біля числа не сказано іншого, його отримано на збірці для профілювання (`vite build --mode profile`).
Таблицю про старі версії React отримано в jsdom, і біля неї про це сказано. Вікно розширення React Developer Tools ми
не відкривали, тому жодне число звідти не взято.

Практика дня просить зробити три випадки з трьома `set` і прокручування до нового елемента списку. Щоб не показувати
готового розв'язку, лекція бере інший об'єкт: табло рейсу й панель з умовами перевезення.

**Після лекції ви зможете пояснити:**

- чому рахувати треба коміти, а не рядки `console.log` у тілі компонента;
- що саме робить `set` і де в цьому алгоритмі з'являється пакет;
- чому після клацання React рендерить у мікрозадачі, а після таймера окремою задачею;
- чому `await` сам по собі не розриває пакет, а `set` перед ним і після нього можуть потрапити в різні коміти;
- що змінив React 18 і чому старі статті описують іншу поведінку;
- що робить `flushSync` і коли він додає коміт, а коли ні;
- чому прокручування без `flushSync` не доходить до нового елемента й чим ще можна розв'язати цю задачу;
- скільки коштує `flushSync` усюди й чому одного числа для цієї відповіді мало.

## Запитання, на яке хочеться відповісти числом

Табло рейсу показує вихід на посадку, статус і затримку. Одна кнопка змінює все це одразу:

```tsx
function FlightBoard() {
  console.log('виклик FlightBoard')
  const [gate, setGate] = useState('A1')
  const [status, setStatus] = useState('за розкладом')
  const [late, setLate] = useState(0)

  function change() {
    setGate((g) => (g === 'A1' ? 'B7' : 'A1'))
    setStatus((s) => (s === 'за розкладом' ? 'затримка' : 'за розкладом'))
    setLate((l) => l + 5)
  }

  return (
    <>
      <p id="board">Вихід {gate}, {status}, затримка {late} хв</p>
      <button onClick={change}>Оновити</button>
    </>
  )
}
```

Скільки разів React виконає роботу після одного клацання? Перед відповіддю треба вирішити, чим рахувати, бо простий
спосіб тут дає неправильне число.

## Чим рахувати

Рядок `console.log` у тілі компонента рахує виклики компонента. Коміт є іншою подією: це крок, на якому React вносить
зміни в документ. Лічильник комітів дає компонент `<Profiler>`. Він огортає частину дерева й після кожного коміту цієї
частини викликає функцію з атрибута `onRender`:

```tsx
const logCommit: ProfilerOnRenderCallback = (_id, phase) => {
  console.log('коміт', phase)
}

<Profiler id="flight" onRender={logCommit}>
  <FlightBoard />
</Profiler>
```

Функція отримує шість аргументів. Сьогодні нас цікавлять два з них. Аргумент `phase` називає причину коміту: `mount`
означає перший показ, `update` означає звичайне оновлення, а `nested-update` означає оновлення, викликане під час
коміту. Третій аргумент `actualDuration` каже, скільки мілісекунд зайняв рендер цієї частини дерева. Докладно цей
інструмент вивчає день «Профайлер» цієї фази.

Ось що дало одне клацання на трьох збірках:

| Збірка | Рядків `виклик FlightBoard` | Викликів `onRender` |
|--------|-----------------------------|---------------------|
| режим розробки, `vite`, з `<StrictMode>` | 2 | 1 |
| збірка для профілювання, `vite build --mode profile` | 1 | 1 |
| звичайна продакшн-збірка, `vite build` | 1 | 0 |

Рядок режиму розробки показує, чому `console.log` вводить в оману. Лекція «Чистота й дерево» пояснила, що
`<StrictMode>` у режимі розробки викликає компонент двічі, щоб виявити порушення чистоти. Комітів при цьому один.
Людина бачить два рядки в консолі й помилково вирішує, що пакетування не спрацювало.

Рядок звичайної продакшн-збірки є пасткою для вашого журналу. У звичайній продакшн-збірці React вимикає профілювання,
тому `onRender` мовчить, а екран працює. Нуль у цій таблиці означає не «немає комітів», а «лічильник вимкнено».

Головне правило фази каже: жодної оптимізації без заміру, а міряти треба на продакшн-збірці чи збірці для профілювання
з уповільненням процесора в чотири рази. Це правило стосується часу. Кількість комітів від швидкості не залежала: у
нашому запуску вона однакова без уповільнення й з уповільненням у чотири рази, а також у режимі розробки й на збірці
для профілювання. Отже, коміти можна рахувати й у розробці, а мілісекунди записуйте лише зі збірки для профілювання.

## Що робить `set`: алгоритм

Сторінка `Queueing a Series of State Updates` пояснює пакетування так: React чекає, поки виконається весь код
обробника, і лише тоді береться за оновлення. Для обробника клацання цього опису досить. Проте він не пояснює, звідки
React знає, що код закінчився, і що відбувається поза обробником.

Відповідь видно у вихідному коді пакета `react-dom`. Ми читали файл `react-dom-client.production.js` версії 19.3.1, а
ті самі функції є й у файлі `react-dom-client.development.js`. Те, що описано нижче, є внутрішньою будовою React, а не
обіцянкою документації, тому в наступних версіях деталі можуть змінитися. Документація обіцяє лише результат:
оновлення об'єднуються.

Кожен виклик `set` робить три речі.

1. **Записує оновлення в чергу.** Цю чергу показала лекція «Рендер, коміт і знімок стану».
2. **Визначає пріоритет оновлення.** Функція `resolveUpdatePriority` дивиться на `window.event`, тобто на подію, яку
   браузер обробляє зараз. Якщо події немає, пріоритет звичайний. Якщо подія є, функція `getEventPriority` визначає
   пріоритет за типом цієї події.
3. **Просить запланувати роботу.** Якщо мікрозадачу React ще не заплановано, функція
   `scheduleImmediateRootScheduleTask` ставить одну мікрозадачу. Якщо вже заплановано, нічого не відбувається.

Тут і з'являється пакет. Лекція «Асинхронність» пояснила, що мікрозадача виконується лише після завершення поточного
коду. Тому всі виклики `set`, зроблені синхронно один за одним, встигають лягти в чергу до того, як React почне щось
робити. Другий і третій `set` не планують нової роботи, бо мікрозадача вже стоїть.

Коли мікрозадача нарешті виконується, вона дивиться на пріоритет і обирає один із двох шляхів.

| Де викликано `set` | `window.event` | Пріоритет | Коли React рендерить |
|--------------------|----------------|-----------|----------------------|
| під час `click`, `keydown`, `input`, `submit` | тип цієї події | найвищий, дискретний | просто в цій мікрозадачі |
| під час `mousemove`, `scroll`, `wheel` | тип цієї події | неперервний | окремою задачею планувальника |
| у таймері, після справжнього очікування | `undefined` | звичайний | окремою задачею планувальника |

**Дискретними** називають події, які людина робить свідомо й окремо: клацання чи натискання клавіші. **Неперервними**
називають події, які йдуть потоком, наприклад рух вказівника. **Планувальник** є окремим пакетом `scheduler`, який
React встановлює разом із собою. У браузері він ставить свою роботу через `MessageChannel`, тобто звичайною задачею
циклу подій. Рядок про неперервні події ми прочитали в коді, але окремо не запускали.

### Простежимо одне клацання

| Крок | Хто діє | Що змінюється |
|------|---------|---------------|
| 1 | браузер викликає слухача React, `window.event` має тип `click` | починає виконуватися `change` |
| 2 | `setGate` | запис у чергу, найвищий пріоритет, мікрозадачу заплановано |
| 3 | `setStatus` | запис у чергу, мікрозадача вже є |
| 4 | `setLate` | запис у чергу, мікрозадача вже є |
| 5 | `change` завершилася, стек порожній | виконується мікрозадача React |
| 6 | React викликає `FlightBoard` один раз | проходить три черги, отримує нові значення |
| 7 | коміт | документ змінено, `onRender` записав `коміт update` |
| 8 | браузер малює | людина бачить усі три зміни разом |

Рендер стоїть у мікрозадачі, тому він встигає до наступної задачі, тобто до наступного клацання. Це забезпечує те, що
обіцяє сторінка `Queueing a Series of State Updates`: якщо перше клацання вимкнуло форму, друге вже не надішле її
знову.

### Перевіримо порядок запуском

Щоб побачити ці шляхи, поставимо навколо `set` мітки. Функція `screen` читає текст табло просто з документа.
Властивість `window.event` застаріла, тому у власному коді її не вживають, а тут вона лише показує те, що читає React.
У файлі, який ми запускали, кнопок більше, ніж у коді вище, бо кожен дослід мав свою кнопку:

```tsx
function trace(place: string) {
  console.log(place, '| window.event:', window.event?.type)
  queueMicrotask(() => console.log('мікрозадача до set:', screen()))
  setLate((l) => l + 5)
  queueMicrotask(() => console.log('мікрозадача після set:', screen()))
  setTimeout(() => console.log('таймер 0:', screen()), 0)
  console.log('кінець коду:', screen())
}
```

Спершу викличемо `trace` просто в обробнику клацання. Затримка перед цим уже дорівнювала 15 хв, бо ми натискали інші
кнопки:

```text
клацання | window.event: click
кінець коду: Вихід B7, затримка, затримка 15 хв
мікрозадача до set: Вихід B7, затримка, затримка 15 хв
коміт update
мікрозадача після set: Вихід B7, затримка, затримка 20 хв
таймер 0: Вихід B7, затримка, затримка 20 хв
```

Прочитаймо вивід рядками.

- Рядок `кінець коду` показує 15 хв, бо код обробника ще не закінчився, отже, React не починав роботу.
- Мікрозадача, поставлена до `set`, стоїть у черзі першою, тому вона теж бачить 15 хв.
- Далі йде мікрозадача React, яку запланував `set`, і вона виконує рендер і коміт.
- Мікрозадача, поставлена після `set`, уже бачить 20 хв.
- Таймер є наступною задачею, тому теж бачить 20 хв.

Тепер викличемо `trace` після справжнього очікування, тобто в рядку після `await wait(5)`. Функція `wait` повертає
проміс, який виконується через `setTimeout`:

```text
після wait(5) | window.event: undefined
кінець коду: Вихід B7, затримка, затримка 20 хв
мікрозадача до set: Вихід B7, затримка, затримка 20 хв
мікрозадача після set: Вихід B7, затримка, затримка 20 хв
таймер 0: Вихід B7, затримка, затримка 20 хв
коміт update
```

Подія вже закінчилася, тому `window.event` дорівнює `undefined`, а пріоритет звичайний. Мікрозадача React лише
поставила задачу планувальнику, тому обидві мікрозадачі бачать старе значення. Таймер теж виявився раніше за коміт. Ми
повторили цей дослід десять разів, і всі десять разів таймер випереджав коміт. Виклик усередині `setTimeout` дав такий
самий порядок рядків. У наступних розділах цей порядок пояснить дві несподіванки.

## Межі пакета

Тепер ми можемо передбачати кількість комітів, а не запам'ятовувати її. Правило таке: один пакет складають усі
оновлення, які лягли в чергу до того, як React почав рендерити. Ось випадки, де всі виклики `set` стоять поруч:

| Де стоять виклики `set` | Комітів |
|-------------------------|---------|
| обробник `onClick` | 1 |
| слухач, поставлений через `addEventListener` в ефекті | 1 |
| `Promise.resolve().then(...)` з обробника | 1 |
| `requestAnimationFrame(...)` з обробника | 1 |

Випадки `setTimeout` і `await` залишаємо вашій практиці. Запишіть передбачення до запуску, адже алгоритм уже дає
відповідь.

Цікавіше, коли між викликами `set` є пауза. Ця функція робить паузу між кожними двома викликами, а саму паузу отримує
аргументом:

```tsx
async function steps(pause: () => Promise<unknown>) {
  setGate((g) => (g === 'A1' ? 'B7' : 'A1'))
  await pause()
  setStatus((s) => (s === 'за розкладом' ? 'затримка' : 'за розкладом'))
  await pause()
  setLate((l) => l + 5)
}
```

Викличемо її трьома способами. Запуск кожного рядка ми повторили десять разів, і число не змінювалося.

| Виклик | Комітів | Чому |
|--------|---------|------|
| з обробника клацання, `steps(() => wait(20))` | 3 | між викликами `set` минає 20 мс, і React встигає закінчити роботу |
| з обробника клацання, `steps(async () => {})` | 3 | пауза не чекає нічого, а пріоритет найвищий, тому кожен `set` має власну мікрозадачу з рендером |
| з таймера, `steps(async () => {})` | 1 | пріоритет звичайний, рендер чекає задачі планувальника, і всі мікрозадачі встигають раніше |

Рядки з `steps(async () => {})` містять той самий код, а дають різний результат. Причину показує `trace`, викликаний
після `await null` в обробнику клацання:

```text
після await null | window.event: click
```

Подія ще не закінчилася з погляду браузера. Специфікація DOM описує це так: браузер записує поточну подію, викликає
слухача, а старе значення повертає лише після виклику. Мікрозадачі виконуються наприкінці самого виклику, коли стек
спорожнів, тобто до повернення старого значення. Тому `set` після такого `await` усе ще має найвищий пріоритет.

Ще два запуски показують, де межа нечітка.

- Три окремі таймери з нульовою затримкою, у кожному по одному `set`, дали один коміт у всіх десяти запусках. Це три
  різні задачі, але задача планувальника виконалася вже після них. Сторінки, які ми читали, цього не обіцяють, тому
  будувати на цьому логіку не можна.
- Два окремі клацання дали два коміти. Сторінка `Queueing a Series of State Updates` прямо каже, що React не об'єднує
  оновлення з різних навмисних подій.

Звідси практичний висновок. Сам `await` пакет не розриває: кілька `set`, що стоять разом після нього, дають один
коміт. Але `set` перед `await` і `set` після нього зазвичай потрапляють у різні коміти, і людина може побачити
проміжний стан екрана. Якщо значення мають з'явитися разом, викликайте всі `set` в одному місці, після всіх очікувань.

### Пакет не змінює знімка

Лекція «Рендер, коміт і знімок стану» пояснила, що обробник бачить змінні свого рендеру. Пакетування цього не змінює.
Саме тому наш код викликає `set` з оновлювачем, тобто з функцією `(l) => l + 5`. Якщо написати `setLate(late + 5)`
після `await`, змінна `late` прийде зі старого рендеру. Кількість комітів від цього не зміниться, а значення може бути
неправильним.

### Той самий стан чи нове значення

Пакет може бути й порожнім. Якщо кожен `set` передає те саме значення, що вже є, React порівнює його функцією
`Object.is` і пропускає роботу. Кнопка, яка тричі просила записати те саме, дала нуль комітів і нуль викликів
компонента. Проте одразу після справжньої зміни перше таке клацання дало один виклик і один коміт, а наступні вже
нуль. Довідник `useState` попереджає про це: інколи React має викликати компонент, перш ніж пропустити його дітей.
Отже, поодинокий зайвий рядок у вашій таблиці може мати саме цю причину.

## Що змінив React 18

Сторінки й статті старші за 2022 рік кажуть, що поза обробниками React пакетування не робить. Для тих версій це
правда. Той самий компонент із трьома `set` ми запустили на старих версіях. Цю таблицю отримано в jsdom, тобто в
імітації браузера всередині Node, у збірці для розробки:

| Версія й корінь | Обробник React | Таймер | Після `await` | Власний слухач |
|-----------------|----------------|--------|---------------|----------------|
| 17.0.2, `ReactDOM.render` | 1 | 3 | 3 | 3 |
| 18.3.1, `ReactDOM.render` | 1 | 3 | 3 | 3 |
| 18.3.1, `createRoot` | 1 | 1 | 1 | 1 |

**Корінь** є точкою, де React прикріплюється до документа. Рядок версії 18.3.1 зі старим коренем показує, що
автоматичне пакетування дав не сам номер версії, а новий корінь `createRoot`. Настанова з переходу на React 18 каже те
саме: зі старим `ReactDOM.render` застосунок поводиться як на React 17. У пакеті `react-dom` версії 19.3.1 функції
`render` більше немає, тому сьогодні в браузері працює лише нова поведінка.

Зі старих часів лишилася функція `unstable_batchedUpdates`. Раніше нею вручну об'єднували оновлення поза обробниками.
У версії 19.3.1 вона просто викликає передану функцію, тому в новому коді вона нічого не дає.

## `flushSync`: змусити React працювати зараз

Лекції «Рендер, коміт і знімок стану» та «Ref» уже показали, що функція `flushSync` з пакета `react-dom` виконує
рендер і коміт до наступного рядка коду. Тепер подивимося, як вона це робить. Її код займає кілька рядків. Вона
ставить найвищий пріоритет, викликає вашу функцію, а потім виконує всю термінову роботу. Отже, виклики `set` у
переданій функції теж збираються в пакет, тільки цей пакет закінчується разом із викликом `flushSync`.

З цього випливає, що `flushSync` не завжди додає коміт.

Кожен рядок цього запису описує вміст окремого обробника клацання. Три крапки заміняють ті самі оновлювачі, що стоять
у `change`:

```text
fsOne:    flushSync(() => setLate((l) => l + 5))
fsAll:    flushSync(change)
fsEach:   flushSync(() => setGate(...)); flushSync(() => setStatus(...)); flushSync(() => setLate(...))
fsFirst:  flushSync(() => setGate(...)); setStatus(...); setLate(...)
fsMiddle: setGate(...); flushSync(() => setStatus(...)); setLate(...)
```

| Запис | Комітів | Чому |
|-------|---------|------|
| `fsOne`, один `set` у `flushSync` | 1 | у цьому обробнику немає іншої роботи |
| `fsAll`, усі три `set` в одному `flushSync` | 1 | усі три лягли в один пакет |
| `fsEach`, кожен `set` у своєму `flushSync` | 3 | три примусові пакети |
| `fsFirst`, `set` у `flushSync`, два поза ним | 2 | перший пакет примусовий, другий звичайний |
| `fsMiddle`, `set`, потім `flushSync`, потім `set` | 2 | докладніше нижче |

Тому слова «`flushSync` платить зайвим комітом» треба читати уважно. Зайвий коміт з'являється, коли поза `flushSync`
залишається ще одне оновлення. Якщо код просить лише один `set` у `flushSync`, коміт один, як і без нього.

Запис `fsMiddle` показує застереження довідника. Вивід запуску:

```text
коміт update
після flushSync: Вихід B7, затримка, затримка 75 хв
коміт update
```

Перед цим запуском табло показувало вихід `A1`. Рядок після `flushSync` показує вихід `B7`, хоч `setGate` стояв поза
`flushSync`. Затримка ще не змінилася, бо `setLate` стоїть нижче, і цю зміну застосував другий коміт. Довідник пояснює
цю поведінку: `flushSync` може застосувати й оновлення поза своєю функцією, якщо інакше неможливо застосувати
оновлення всередині неї. Отже, `flushSync` забирає із собою все, що вже чекає в черзі, а також може виконати ефекти,
які ще не виконалися.

### Чого `flushSync` не робить

Він не змінює змінних поточного рендеру. Лекція «Рендер, коміт і знімок стану» показала, що після `flushSync` документ
уже новий, а змінна в обробнику стара. Отже, `flushSync` оновлює документ, а не вашу змінну.

Його також не можна викликати під час рендеру чи в ефекті, бо React у цей момент уже працює. Ми викликали його в
`useEffect`, і в режимі розробки консоль показала таку помилку:

```text
flushSync was called from inside a lifecycle method. React cannot flush when React is already rendering. Consider moving this call to a scheduler task or micro task.
```

Довідник наводить той самий текст зі словом `Warning:` на початку, а у версії 19.3.1 цього слова в консолі немає.
Коміти при цьому мали фази `update` і `nested-update`, тобто робота все одно відбулася, але вже після поточного
коміту.

## Прокручування до нового елемента

Тепер випадок, заради якого `flushSync` існує. Сторінка рейсу довга, а внизу можна розгорнути панель з умовами
перевезення. Кнопка має розгорнути панель і прокрутити до неї. Панель існує в документі лише тоді, коли `open`
дорівнює `true`:

```tsx
function openRules() {
  setOpen(true)
  console.log('вузол панелі:', rulesRef.current)
  rulesRef.current?.scrollIntoView()
  console.log('window.scrollY:', window.scrollY)
}
```

Метод `scrollIntoView` прокручує сторінку так, щоб елемент став видимим, а `window.scrollY` показує, на скільки
пікселів сторінку прокручено. Ось вивід у браузері:

```text
вузол панелі: null
window.scrollY: 0
коміт update
```

Панель з'явилася, але її верхній край лежить на 2029 пікселів нижче верху вікна, а сторінка не зрушила. Алгоритм
пояснює порядок рядків: `set` лише записав оновлення, а коміт станеться в мікрозадачі після кінця обробника. Під час
читання `rulesRef.current` панелі ще немає.

Виправлення займає один рядок. Рядки `console.log` у цьому коді теж були, але тут їх не показано:

```tsx
function openRules() {
  flushSync(() => setOpen(true))
  rulesRef.current?.scrollIntoView()
}
```

```text
коміт update
вузол панелі: SECTION
window.scrollY: 1637
верх панелі у вікні: 392
висота сторінки: 2337 вікна: 700
```

Тепер коміт стоїть першим, а вузол уже є. Панель не дійшла до верху вікна, бо сторінка закінчилася: її висота 2337
пікселів, вікно займає 700, отже, прокрутити можна щонайбільше на 2337 − 700 = 1637 пікселів. Панель стояла на 2029,
тому після прокручування її верх опинився на 2029 − 1637 = 392. Вікно браузера в цьому запуску мало висоту 700
пікселів, тому у вашому вікні числа будуть іншими, але рахуються вони так само.

### У списку помилка тихіша

У панелі вузла не було взагалі, тому помилку легко помітити. У списку елемент завжди є, але це попередній елемент.
Сторінка `Manipulating the DOM with Refs` описує саме таку поведінку: прокручування відстає на один елемент. Ми
перевірили це в браузері на списку заввишки 200 пікселів із рядками по 40 пікселів. Код цього досліду лишаємо вашій
практиці. Без `flushSync` прокручування дійшло до попереднього рядка, а після коміту низ нового рядка опинився на
позиції 240 при висоті видимої частини 200. Отже, новий рядок лишився схованим. Помилки в консолі при цьому немає.

Ось чому перевіряти це треба в браузері. Лекція «Ref» показала, що в jsdom методу `scrollIntoView` немає, бо jsdom не
розташовує елементи на сторінці.

Ще одна деталь стосується плавного прокручування. Із параметром `behavior: 'smooth'` наш список одразу після виклику
лишався на позиції 0, а потрібної позиції досягнув під час перевірки через 1500 мс. Отже, перевіряйте результат
наприкінці анімації, а не наступним рядком коду.

### Інші способи й коли який обирати

Довідник `flushSync` каже, що ця функція потрібна для рідкісних випадків, насамперед для зв'язку зі стороннім кодом і
браузерними API. Прокручування є браузерним API, тому цей випадок є законним, але це не єдиний спосіб.

**Ефект.** Хук `useLayoutEffect` виконується після коміту, але перед малюванням, як пояснила лекція «Як браузер
малює»:

```tsx
useLayoutEffect(() => {
  if (open) {
    rulesRef.current?.scrollIntoView()
  }
}, [open])
```

Цей варіант дав той самий `window.scrollY` 1637 і один коміт. На відміну від `flushSync`, він спрацьовує незалежно від
того, чому `open` змінився. Отже, ефект підходить, коли прокручувати треба після будь-якої зміни, а не лише після
цього клацання. Проте в цьому записі ефект також прокрутить сторінку, якщо `open` став `true` з іншої причини, а це не
завжди потрібно. Тоді причина належить обробнику, і `flushSync` точніше описує намір.

Обережно з `set` усередині ефекту. Ефект, який сам викликає `set`, теж додає коміт: `useLayoutEffect` дав нам фази
`update` і `nested-update`, а `useEffect` дав `update` і `update`.

**`setTimeout` з нулем.** Цей прийом часто трапляється в старому коді, і він працює випадково. Після клацання таймер
бачить новий документ, бо коміт стався раніше, у мікрозадачі. Після `await wait(5)` ми бачили протилежний порядок:
таймер у всіх десяти запусках випереджав коміт. На списку цей дослід у всіх п'яти запусках прокрутив до попереднього
рядка, а новий рядок лишився схованим. Отже, той самий прийом перестає працювати, щойно обробник стає асинхронним.

| Спосіб | Комітів у нашому запуску | Що обрати |
|--------|--------------------------|-----------|
| `flushSync` навколо `set`, інших `set` немає | 1 | прокручування є частиною цієї дії користувача |
| `flushSync` навколо `set`, ще один `set` поза ним | 2 | перенесіть другий `set` усередину, якщо він не заважає |
| `useLayoutEffect` за станом | 1 | прокручування має йти за станом, хоч би що його змінило |
| `setTimeout` з нулем | 1 | не використовуйте: порядок залежить від місця виклику |

## Скільки коштує `flushSync` усюди

Пастка дня звучить так: людина ставить `flushSync` усюди, щоб стан оновився одразу. Головне правило фази вимагає
числа, тому поміряймо. Екран `Departures` показує дві тисячі рядків. Кожен рядок рахує невелику суму й показує три
стани, тому після кожної зміни React викликає всі рядки заново й змінює їхній текст. Повний код досліду стоїть у
файлі `src/main.tsx`, а збирає його команда `vite build --mode profile`:

```tsx
// src/main.tsx
import { Profiler, useState } from 'react'
import { flushSync } from 'react-dom'
import { createRoot } from 'react-dom/client'

const ROWS = 2000
let commits = 0 // Скільки комітів дало поточне клацання.
let render = 0 // Сума actualDuration за ці коміти, мс.

function Row({ i, gate, status, late }: { i: number; gate: number; status: number; late: number }) {
  let sum = 0
  for (let k = 0; k < 40; k++) sum += (i * k + gate + status + late) % 7 // невелика сума в кожному рядку
  return <li>рейс {i}: вихід {gate}, статус {status}, затримка {late}, контроль {sum}</li>
}

function Departures() {
  const [gate, setGate] = useState(0)
  const [status, setStatus] = useState(0)
  const [late, setLate] = useState(0)
  const list = () => document.getElementById('list')!

  function together() {
    setGate(gate + 1)
    setStatus(status + 1)
    setLate(late + 1)
  }
  function separately() {
    flushSync(() => setGate(gate + 1))
    flushSync(() => setStatus(status + 1))
    flushSync(() => setLate(late + 1))
  }
  function separatelyWithReading() {
    flushSync(() => setGate(gate + 1))
    void list().offsetHeight
    flushSync(() => setStatus(status + 1))
    void list().offsetHeight
    flushSync(() => setLate(late + 1))
    void list().offsetHeight
  }

  // Обгортка міряє клацання: від початку обробника до повідомлення, яке надсилає функція кадру.
  const measured = (name: string, handler: () => void) => () => {
    commits = 0
    render = 0
    const start = performance.now()
    handler()
    requestAnimationFrame(() => {
      const channel = new MessageChannel()
      channel.port1.onmessage = () => {
        console.log(JSON.stringify({ name, commits, render: +render.toFixed(1), frame: +(performance.now() - start).toFixed(1) }))
      }
      channel.port2.postMessage(null)
    })
  }

  return (
    <>
      <button onClick={measured('together', together)}>together</button>
      <button onClick={measured('separately', separately)}>separately</button>
      <button onClick={measured('separatelyWithReading', separatelyWithReading)}>separatelyWithReading</button>
      <ul id="list">
        {Array.from({ length: ROWS }, (_, i) => <Row key={i} i={i} gate={gate} status={status} late={late} />)}
      </ul>
    </>
  )
}

createRoot(document.getElementById('root')!).render(
  <Profiler id="departures" onRender={(_id, _phase, actualDuration) => { commits++; render += actualDuration }}>
    <Departures />
  </Profiler>,
)
```

Третій варіант читає `offsetHeight`, тобто висоту списку. Саме заради такого читання `flushSync` зазвичай і пишуть.
Лекція «Як браузер малює» пояснила, що таке читання змушує браузер негайно перерахувати компонування.

Ми міряли дві величини. Перша величина є сумою `actualDuration` за всі коміти одного клацання, тобто часом рендеру.
Друга величина є часом від початку обробника до моменту одразу після наступного кадру: обробник запам'ятовує час на
своєму початку, а кінець записує повідомлення, яке надсилає функція в `requestAnimationFrame`. Цей спосіб дає
наближене значення. Значення є медіаною п'ятнадцяти клацань на збірці для профілювання після трьох прогрівальних.
Уповільнення задано командою протоколу `Emulation.setCPUThrottlingRate`.

| Варіант | Комітів | Рендер, мс, без уповільнення | До кадру, мс, без уповільнення | Рендер, мс, у 4 рази | До кадру, мс, у 4 рази |
|---------|---------|------------------------------|--------------------------------|----------------------|------------------------|
| `together` | 1 | 5.5 | 62.4 | 29.6 | 381.1 |
| `separately` | 3 | 15.2 | 86.9 | 85.6 | 538.7 |
| `separatelyWithReading` | 3 | 15.5 | 142.2 | 80.3 | 894.1 |

Прочитаймо рядки з уповільненням, бо саме їх вимагає правило фази.

- Рендер коштує приблизно втричі дорожче, бо React тричі пройшов дві тисячі рядків. Це прямий наслідок трьох комітів.
- Час до кадру виріс на 158 мс, тобто менш ніж удвічі. Найімовірніша причина така: більшу частину цього часу займає
  робота браузера після вашого коду, а перерахунок і малювання тут відбулися один раз.
- Варіант `separatelyWithReading` має такий самий рендер, як `separately`, а його час до кадру більш ніж удвічі
  більший за час `together`. Причина лежить поза `actualDuration`: це число міряє лише рендер, а не зміни документа й
  перерахунок компонування. Отже, одного `actualDuration` замало, щоб оцінити ціну `flushSync`.

Ці числа належать нашому екрану й нашому комп'ютеру, а запуск ішов у Chrome 156 з вікном. Таблиця показує найгірший
випадок, бо кожен рядок залежить від кожного стану. У вашому застосунку співвідношення буде іншим, тому міряйте свій
екран, а не повторюйте наші цифри.

## Типові хибні уявлення

**«Три `set` дають три рендери».** Три `set`, що стоять поруч, дають один коміт. Це стосується обробника, таймера,
промісу й власного слухача, у нашому запуску всюди один коміт.

**«`await` розриває пакетування».** Сам `await` пакета не розриває. Три `set` разом після `await` дають один коміт.
Окремі коміти дають `set`, розділені очікуванням.

**«Пакетування працює лише в обробниках React».** Так було до React 18 і зі старим коренем, що показала таблиця
версій. Статті того часу описують застарілу поведінку.

**«Я бачу в консолі два рядки, отже, два рендери й пакетування зламано».** У режимі розробки `<StrictMode>` викликає
компонент двічі на один коміт. Рахуйте через `onRender`.

**«`onRender` показує нуль, отже, комітів немає».** У звичайній продакшн-збірці профілювання вимкнено. Потрібна збірка
для профілювання або режим розробки.

**«`flushSync` завжди додає один коміт».** Один `set` у `flushSync` без інших оновлень дає один коміт. Зайвий коміт
дає те, що лишилося поза ним.

**«`flushSync` оновлює змінну стану».** Він оновлює документ. Змінна в поточному обробнику лишається зі старого
рендеру.

**«`setTimeout` з нулем робить те саме, що `flushSync`».** Таймер спрацьовує пізніше коміту лише після дискретної
події. Після справжнього очікування він у наших запусках випереджав коміт.

**«Якщо немає помилки, прокручування працює».** Без `flushSync` у списку метод `scrollIntoView` успішно прокручує до
попереднього елемента, і консоль мовчить.

**«`flushSync` усюди зробить інтерфейс чуйнішим».** Він не пришвидшує роботу, а лише змінює її час і дробить на
частини. У нашому замірі час до кадру зріс з 381.1 мс до 538.7 мс, а з читанням висоти до 894.1 мс.

## Як це проявиться далі в React

- **День «Мемоізація і React Compiler».** Там ви рахуватимете, скільки елементів рендериться на одне клацання.
  Сьогоднішня кількість комітів множиться на кількість рядків, тому зменшувати можна обидва числа.
- **День «`useTransition` і перший замір INP».** Там з'явиться ще один пріоритет. Оновлення всередині
  `startTransition` не вважаються терміновими, тому React може відкласти їхній рендер.
- **День «`<Suspense>` і межі помилок».** Довідник `flushSync` попереджає, що ця функція може змусити межу
  `<Suspense>` знову показати запасний вміст. Там ви побачите, що це означає.
- **Фаза 3, день «Сотні повідомлень на секунду».** Повідомлення WebSocket приходять окремими задачами, тому кожне може
  дати свій коміт. План розв'язує це власним буфером, який раз на кадр передає все разом, а це той самий принцип
  пакета, тільки написаний вами.

## Перевірте себе

**1. Чому один `console.log` у тілі компонента може надрукувати два рядки на одне клацання, а `onRender` викличеться
раз?**

<details><summary>Відповідь</summary>

У режимі розробки `<StrictMode>` викликає компонент двічі, щоб виявити порушення чистоти, а коміт відбувається один.
`console.log` рахує виклики компонента, а `onRender` рахує коміти. У нашому запуску в режимі розробки вийшло 2 і 1, а
на збірці для профілювання 1 і 1.

</details>

**2. Завдяки чому три виклики `set` підряд в обробнику стають одним рендером?**

<details><summary>Відповідь</summary>

Кожен `set` записує оновлення в чергу, а перший із них ще й планує одну мікрозадачу. Мікрозадача виконується лише
після завершення поточного коду, тому всі три записи вже лежать у черзі, коли React починає рендер.

</details>

**3. Обробник клацання робить `setA(1)`, потім `await wait(20)`, потім `setB(1)`, потім `setC(1)`. Скільки комітів ви
очікуєте? А якщо прибрати перший `set` з обробника й викликати всі три після `await`?**

<details><summary>Відповідь</summary>

У першому випадку два коміти: `setA` рендериться в мікрозадачі після обробника, а `setB` і `setC` стоять разом після
очікування й дають один пакет. У другому випадку один коміт, бо всі три оновлення лягли в чергу разом.

</details>

**4. Чому один і той самий код `steps(async () => {})` дав три коміти з клацання й один з таймера?**

<details><summary>Відповідь</summary>

Під час мікрозадач після клацання `window.event` ще вказує на `click`, тому пріоритет найвищий і кожне оновлення
рендериться в своїй мікрозадачі. У таймері події немає, пріоритет звичайний, рендер чекає окремої задачі
планувальника, а всі мікрозадачі виконуються раніше за неї. Тому всі три оновлення встигають у чергу.

</details>

**5. Практичне запитання: `flushSync(() => setItems(next))`, а наступний рядок `setDraft('')`. Скільки комітів? Як
отримати один, зберігши прокручування після `flushSync`?**

<details><summary>Відповідь</summary>

Два: перший примусовий, другий звичайний після обробника. Щоб отримати один, обидва `set` треба покласти в один виклик
`flushSync`, тоді вони утворять один пакет.

</details>

**6. Код викликає `setA` без `flushSync`, а потім `flushSync(() => setB(1))`. Що покаже документ одразу після
`flushSync`?**

<details><summary>Відповідь</summary>

Обидві зміни. Довідник каже, що `flushSync` може застосувати й оновлення поза своєю функцією, і наш запуск це
підтвердив: рядок після `flushSync` показав новий вихід, хоч його `set` стояв поза функцією.

</details>

**7. Чому в нашому замірі варіант `separatelyWithReading` мав такий самий рендер, як `separately`, а час до кадру
значно більший?**

<details><summary>Відповідь</summary>

`actualDuration` міряє лише час рендеру. Читання `offsetHeight` після кожного `flushSync` змушує браузер
перераховувати компонування, а цей час у `actualDuration` не входить, зате входить у час до кадру.

</details>

**8. Людина виправила прокручування через `setTimeout(() => scrollIntoView(), 0)`, і це працювало. Потім обробник став
асинхронним, а виклик опинився після `await`. Що станеться й чому?**

<details><summary>Відповідь</summary>

Прокручування знову приходить до попереднього елемента, як і в наших п'яти запусках на списку. Після справжнього
очікування пріоритет звичайний, тому рендер іде окремою задачею планувальника, а таймер випереджає коміт. Спершу
таймер спрацьовував пізніше лише тому, що після клацання рендер виконується в мікрозадачі.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| пакетування, batching | об'єднання всіх оновлень, що лягли в чергу до початку рендеру, в один рендер і один коміт |
| автоматичне пакетування | пакетування поза обробниками React, яке дає `createRoot` із React 18 |
| коміт | крок, на якому React вносить зміни в документ |
| `onRender` | функція в атрибуті `<Profiler>`, яку React викликає після кожного коміту цієї частини дерева |
| `actualDuration` | мілісекунди рендеру частини дерева за цей коміт, без змін документа й малювання |
| дискретна подія | свідома окрема дія людини, наприклад клацання чи натискання клавіші |
| неперервна подія | подія, що йде потоком, наприклад рух вказівника чи прокручування |
| планувальник | пакет `scheduler`, який виконує роботу React окремими задачами |
| `flushSync` | функція з `react-dom`, яка виконує всю термінову роботу до наступного рядка коду |
| `nested-update` | значення `phase`, коли `set` викликано під час коміту, наприклад у `useLayoutEffect` |
| корінь | точка, де React прикріплюється до документа; `createRoot` створює новий корінь |
