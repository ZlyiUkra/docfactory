# Лекція. Фаза 2, день 4. Мемоізація і React Compiler — один замір

На співбесіді питають: «Коли `useMemo` справді допомагає?». Відповідь «коли обчислення дороге» нічого не каже, поки
немає числа. Хук `useMemo` є одним з інструментів мемоізації. Мемоізацією називають запам'ятовування результату, щоб
не виконувати ту саму роботу вдруге. Сьогодні ви побачите, чому React викликає компоненти, пропси яких не змінилися,
як три інструменти ручної мемоізації це зупиняють, де вони нічого не дають і що робить із тим самим кодом React
Compiler. Кожен крок лекції має замір. Читання займе близько 65 хвилин.

Числа отримано на React 19.3.1, Vite 8.3.6, `@vitejs/plugin-react` 6.2.1 і TypeScript 6.0.3 у браузері
`chrome-headless-shell` версії 157, тобто в Chromium без вікна. Клацання були справжніми подіями миші, які браузеру
надсилав протокол інструментів розробника. Усі заміри часу зроблено на збірці для профілювання, яку завела лекція
«Профайлер» (`vite build --mode profile`). Уповільнення процесора задавала команда протоколу
`Emulation.setCPUThrottlingRate`. Кожне число часу в таблицях є медіаною 45 клацань: три серії по 15 клацань після
чотирьох прогрівальних. Час першого показу є медіаною дев'яти відкриттів сторінки. Вікна розширення React Developer
Tools ми не відкривали, і біля кожного твердження про нього про це сказано.

Застереження про версію компілятора TypeScript: у перших лекціях про TypeScript команда `tsc` мала версію 7, а в
проєкті `spa` вона має версію 6.0. Це вимушене обмеження через ESLint. ESLint читає файли TypeScript через пакет
`typescript-eslint`, а цей пакет у версії 8.72 працює лише з TypeScript, нижчим за 6.1. Тому версію TypeScript у `spa`
закріплено на 6.0. Коли `typescript-eslint` запрацює з TypeScript 7, обмеження можна буде зняти.

Практика дня просить список на дві тисячі елементів із фільтром і лічильником. Щоб не показувати готового розв'язку,
лекція бере інший об'єкт: схему зали кінотеатру, де можна обирати місця.

**Після лекції ви зможете пояснити:**

- чому React викликає дочірні компоненти, хоча їхні пропси не змінилися;
- що запам'ятовує `useMemo` і як поріг в 1 мс перевірити через `console.time`;
- як `memo` порівнює пропси й чому одна нова функція чи об'єкт зводить її нанівець;
- навіщо потрібен `useCallback` і чому він не скасовує створення функції;
- чому перед мемоізацією варто спробувати опустити стан нижче;
- що React Compiler робить із кодом компонента і завдяки чому React пропускає дочірні компоненти без `memo`;
- які пакети вмикають компілятор у шаблоні Vite і за чим видно, що він спрацював;
- де компілятор дав більше за ручну мемоізацію, а де менше;
- що стається з компонентом, який порушує `Rules of React`, і як про це дізнатися.

## Скарга: кнопка «Легенда» відгукується із затримкою

Екран показує залу на 30 рядів по 40 місць, разом 1200 кнопок. Клацання по місцю обирає його. Над залою стоять прогноз
виторгу, сума за обрані місця, кнопка зміни тарифу й кнопка «Легенда», яка показує один абзац пояснення. Користувачі
кажуть, що саме ця остання кнопка спрацьовує не одразу. Ось код:

```tsx
type SeatCellProps = { seat: Seat; picked: boolean; onPick: (id: number) => void }

function SeatCell({ seat, picked, onPick }: SeatCellProps) {
  return (
    <button
      type="button"
      className={picked ? 'seat picked' : 'seat'}
      title={`Ряд ${seat.row}, місце ${seat.place}, ${seat.price} грн`}
      onClick={() => onPick(seat.id)}
    >
      {seat.place}
    </button>
  )
}

export function HallScreen() {
  const [seats] = useState(makeSeats) // 1200 об'єктів { id, row, place, price }
  const [picked, setPicked] = useState<ReadonlySet<number>>(() => new Set())
  const [tariff, setTariff] = useState<Tariff>('day')
  const [legend, setLegend] = useState(false)

  function pick(id: number) {
    setPicked((prev) => toggle(prev, id)) // toggle повертає новий Set із доданим чи прибраним id
  }

  const expected = forecast(seats, tariff) // прогноз виторгу: 480 000 кроків циклу
  const total = totalOf(seats, picked) // сума за обрані місця: один прохід масиву

  return (
    <main>
      <div className="bar">
        <button type="button" onClick={() => setLegend((v) => !v)}>Легенда</button>
        <button type="button" onClick={() => setTariff((t) => (t === 'day' ? 'evening' : 'day'))}>
          Тариф: {tariff === 'day' ? 'денний' : 'вечірній'}
        </button>
        <p>Прогноз виторгу за сеанс: {expected} грн. Обрано місць: {picked.size}, сума {total} грн.</p>
      </div>
      {legend && <Legend />}
      <div className="hall">
        {seats.map((seat) => (
          <SeatCell key={seat.id} seat={seat} picked={picked.has(seat.id)} onPick={pick} />
        ))}
      </div>
    </main>
  )
}
```

Кнопка «Легенда» змінює один булевий стан, а на екрані з'являється один абзац. Скільки роботи React виконує після
одного клацання по ній? Щоб відповісти числом, спершу налаштуємо замір.

## Чим міряти: три числа

Головне правило фази забороняє оптимізувати без заміру. Нам потрібні три числа, і кожне має свій інструмент.

**Скільки компонентів React викликав.** Лекція «Пакетування оновлень» рахувала виклики рядком `console.log` у тілі
компонента. Для 1200 клітинок це 1200 рядків у консолі на кожне клацання, тому ми рахуємо власним хуком:

```tsx
export const renders: Record<string, number> = {}

export function useRenderCount(name: string): void {
  // Ефект без списку залежностей виконується після кожного коміту, у якому React викликав компонент.
  useEffect(() => {
    renders[name] = (renders[name] ?? 0) + 1
  })
}
```

Кожен компонент екрана викликає цей хук першим рядком, наприклад `useRenderCount('SeatCell')`. Якщо React пропустив
компонент, його ефект не виконується, і число не росте. Лічильник навмисно стоїть в ефекті, а не в тілі компонента.
Рядок на кшталт `renders.SeatCell += 1` у тілі компонента порушує чистоту, і далі ви побачите, що через такий рядок
компілятор відмовляється обробляти компонент. У збірках, де ми міряли час, цей хук замінено порожньою функцією, щоб
1200 ефектів не потрапили в результат.

**Скільки тривав рендер.** Це число `actualDuration`, яке `<Profiler>` передає у функцію `onRender` після кожного
коміту. Лекція «Профайлер» пояснила, що воно рахує лише виклики компонентів, без змін документа й малювання. У файлі
`main.tsx` нашого застосунку ці числа складаються в масив, а параметр адреси `?v=` обирає варіант екрана:

```tsx
const commits: { phase: string; actual: number; base: number; commit: number }[] = []

const onRender: ProfilerOnRenderCallback = (_id, phase, actual, base, _start, commit) => {
  commits.push({ phase, actual, base, commit }) // один запис на кожен коміт
}

const screens: Record<string, ComponentType> = { plain: Plain, usememo: UseMemo, manual: Manual /* … */ }
const Screen = screens[new URLSearchParams(location.search).get('v') ?? 'plain'] ?? Plain

Object.assign(window, { lab: { renders, commits } }) // звідси дані читає скрипт заміру

createRoot(document.getElementById('root')!).render(
  <Profiler id="hall" onRender={onRender}>
    <Screen />
  </Profiler>,
)
```

Поруч ми показуємо ще час від клацання до наступного кадру, виміряний так само наближено, як у лекції «Пакетування
оновлень». Код цього заміру стоїть у кінці розділу.

**Скільки коштує одне обчислення.** Для цього консоль браузера має пару функцій. `console.time('назва')` запускає
секундомір, а `console.timeEnd('назва')` зупиняє його й друкує час. Поставимо їх навколо двох обчислень:

```tsx
console.time('forecast')
const expected = forecast(seats, tariff)
console.timeEnd('forecast')

console.time('total')
const total = totalOf(seats, picked)
console.timeEnd('total')
```

Одне клацання по кнопці «Легенда» на збірці для профілювання з уповільненням у чотири рази надрукувало:

```text
forecast: 9.06787109375 ms
total: 0.01416015625 ms
```

Розділ «How to tell if a calculation is expensive?» довідника `useMemo` дає орієнтир: якщо за одну дію на обчислення
набігає помітний час, наприклад 1 мс чи більше, його, можливо, варто мемоізувати. Той самий розділ радить міряти на
продакшн-збірці й з уповільненням процесора, бо ваш комп'ютер швидший за комп'ютер користувача.

### Скрипт, який клацає й рахує медіани

Одне клацання дає одне число, а сусідні клацання розходяться на кілька мілісекунд. Тому клацав скрипт на Node: він
запускає `chrome-headless-shell`, відкриває зібрану сторінку й керує нею через протокол інструментів розробника. Ось
його головні частини. Функція `s` надсилає браузеру команду протоколу, а `ev` виконує вираз на сторінці й повертає
результат:

```js
// Уповільнення процесора: 1 означає звичайну швидкість, 4 означає «учетверо повільніше».
const throttle = (rate) => s('Emulation.setCPUThrottlingRate', { rate })

const click = async (selector) => {
  const box = await ev(`/* центр елемента selector за getBoundingClientRect() */`)
  // Справжнє натискання й відпускання лівої кнопки миші в цій точці.
  await s('Input.dispatchMouseEvent', { type: 'mousePressed', x: box.x, y: box.y, button: 'left', clickCount: 1 })
  await s('Input.dispatchMouseEvent', { type: 'mouseReleased', x: box.x, y: box.y, button: 'left', clickCount: 1 })
  // Чекаємо наступного кадру й ще 60 мс, щоб коміт і ефекти встигли завершитися.
  await ev(`new Promise(r => requestAnimationFrame(() => setTimeout(r, 60)))`)
}

// Час до кадру: слухач на сторінці запам'ятовує момент клацання, а повідомлення MessageChannel
// приходить одразу після найближчого кадру.
document.addEventListener('click', () => {
  const t0 = performance.now()
  requestAnimationFrame(() => {
    const ch = new MessageChannel()
    ch.port1.onmessage = () => window.__frames.push(performance.now() - t0)
    ch.port2.postMessage(0)
  })
}, true)
```

Одна серія вмикає уповільнення, відкриває варіант екрана, робить чотири прогрівальні клацання й п'ятнадцять
записаних. Перед кожним клацанням масиви на сторінці очищуються:

Кожну комбінацію варіанта, дії й уповільнення скрипт проганяв трьома серіями й брав медіану всіх 45 клацань. Варіант
екрана й компілятор змінюються під час збірки. У лабораторному `vite.config.ts` їх вмикають змінні середовища:

```ts

export default defineConfig(({ mode }) => ({
```

Кількість рендерів ми рахували у збірці з `COUNT=1` чотирма записаними клацаннями, а час у збірці без лічильника.
Чотири збірки дали команди такого вигляду:

```bash
COUNT=1 npx vite build --mode profile --outDir dist-p-count   # рахувати рендери, без компілятора
npx vite build --mode profile --outDir dist-p                 # міряти час, без компілятора
RC=1 COUNT=1 npx vite build --mode profile --outDir dist-rc-count
RC=1 npx vite build --mode profile --outDir dist-rc
```

Усі таблиці лекції, де стоять кількість викликів, `actualDuration`, час до кадру чи час першого показу, отримано цим
скриптом. Далі лекція називає лише варіант коду й дію.

### Перший замір

Ось медіани `console.time` для двох обчислень:

| Обчислення | Що воно робить | Без уповільнення, мс | З уповільненням у 4 рази, мс |
|------------|----------------|----------------------|------------------------------|
| `forecast` | 480 000 кроків циклу | 2.3 | 10.3 |
| `totalOf` | один прохід 1200 місць | 0.016 | 0.019 |

Прогноз перевищує поріг у десять разів, а сума менша за нього в п'ятдесят разів. Отже, прогноз є кандидатом на
мемоізацію, а сума ні. Зверніть увагу, що коротке обчислення під уповільненням майже не змінилося. Чому так, ми не
з'ясовували, але висновок практичний: уповільнення не перетворює дешеве обчислення на дороге.

Тепер сама скарга. Скрипт клацав по кнопці «Легенда» в коді з початку лекції, на уповільненому в чотири рази
процесорі:

| Що міряли | Значення |
|-----------|----------|
| викликів `SeatCell` | 1200 |
| `actualDuration`, тобто час рендеру цього коміту | 16.3 мс |
| час від клацання до моменту одразу після наступного кадру | 48.8 мс |

Заради одного абзацу React викликав усі 1200 клітинок і ще раз порахував прогноз. Щоб це виправити, треба спершу
зрозуміти, чому він так робить.

## Чому React викликає всі 1200 клітинок

Стан `legend` живе в `HallScreen`, тому після `setLegend` React викликає `HallScreen`. Ця функція виконується вся, від
першого рядка до останнього. Вона знову викликає `forecast`, знову створює функцію `pick` і знову проходить
`seats.map`, який створює 1200 нових елементів `<SeatCell ... />`.

Далі діє правило, яке довідник `useCallback` записує одним реченням: коли компонент рендериться, React за
замовчуванням рендерить рекурсивно всі його дочірні компоненти. React не перевіряє, чи змінилися їхні пропси. Він
отримав нові елементи й викликає функцію кожного з них.

Причина такого замовчування проста. Перевірка теж коштує роботи, а більшість компонентів рендеряться швидко. Тому
React обирає найпростіший шлях і дає вам інструменти, щоб позначити місця, де перевірка окупиться.

Лекція «Рендер, коміт і знімок стану» пояснила, що рендер не означає зміни документа. Тут це видно добре: React
викликав 1200 функцій, порівняв 1200 результатів із попередніми й не змінив у документі жодної кнопки. Змінився лише
абзац легенди. Отже, 16.3 мс пішли на роботу, результат якої React відкинув.

## `useMemo`: не рахувати вдруге те саме

Лекція «Коли ефект не потрібен» уже показала цей хук. Він приймає функцію обчислення й список залежностей. Під час
першого рендеру React викликає функцію й зберігає результат разом зі списком. Під час наступних рендерів React
порівнює кожну залежність із збереженою через `Object.is`. Якщо всі збіглися, він повертає збережений результат і
функцію не викликає.

```tsx
const expected = useMemo(() => forecast(seats, tariff), [seats, tariff])
```

Масив `seats` і рядок `tariff` не змінюються, коли людина натискає «Легенду», тому прогноз береться зі сховища. Те
саме клацання тепер друкує:

```text
forecast: 0.001953125 ms
total: 0.017822265625 ms
```

Секундомір стоїть навколо виклику `useMemo`, тому рядок `forecast` показує ціну самого порівняння залежностей: дві
мікросекунди замість дев'яти мілісекунд. Час рендеру цього клацання впав із 16.3 мс до 6.3 мс. Клітинок React і далі
викликає 1200, бо `useMemo` стосується лише обчислення.

Три речі хук не робить.

- Він не допомагає, коли залежність змінилася. Клацання по кнопці тарифу чесно перераховує прогноз, і рендер займає
  15.2 мс.
- Він не пришвидшує перший показ, бо тоді обчислення однаково виконується. Без уповільнення перший показ екрана
  зайняв у нас 13.0 мс без мемоізації й 13.3 мс з усією ручною мемоізацією, тобто різниці немає.
- Він не окупається на дешевому обчисленні. Якби ми загорнули `totalOf`, то заощадили б 0.02 мс і додали б рядок
  коду, список залежностей і ще одне місце для помилки.

## `memo`: пропустити компонент, якщо пропси ті самі

Лишилося 1200 викликів `SeatCell`. Функція `memo` з пакета `react` обгортає компонент і повертає новий компонент, який
поводиться так само, але має перевірку на вході:

```tsx
const SeatCell = memo(function SeatCell({ seat, picked, onPick }: SeatCellProps) {
  // тіло компонента те саме
})
```

Коли батько рендериться, React бере старі й нові пропси обгорнутого компонента й порівнює їх. Алгоритм ми прочитали в
пакеті `react-dom` версії 19.3.1, у функції `shallowEqual`. Він перевіряє, що кількість пропсів та сама, а потім
порівнює кожен пропс зі старим значенням через `Object.is`. Довідник `memo` називає таке порівняння поверхневим:
React не заглядає всередину об'єктів. Якщо всі пропси збіглися, а власний стан компонента й контекст, який він читає,
не змінилися, React не викликає його функцію.

Запускаємо замір після обгортання й бачимо, що нічого не змінилося:

| Варіант | Викликів `SeatCell` на клацання «Легенди» | `actualDuration`, мс |
|---------|-------------------------------------------|----------------------|
| `useMemo` на прогнозі, клітинка без `memo` | 1200 | 6.3 |
| `useMemo` на прогнозі, клітинка в `memo` | 1200 | 6.1 |

Різниця 0.2 мс менша за розкид між серіями, який тут сягав 1.3 мс. Це пастка з картки дня, показана числами:
обгортка `memo` є, а користі від неї немає.

Причина лежить у пропсі `onPick`. Функція `pick` оголошена в тілі `HallScreen`, тому кожен рендер створює нову
функцію. Лекція «Значення й посилання» пояснила, що дві функції з однаковим текстом є різними значеннями, і
`Object.is(стара, нова)` дає `false`. Пропси `seat` і `picked` ті самі, але одного нового пропса досить, щоб
порівняння щоразу відповідало «змінилося».

Скільки коштує саме марне порівняння? Ми переписали функцію `shallowEqual` з `react-dom` у файл `shallow-bench.mjs`
і запустили її в Node на 1200 парах об'єктів із тими самими трьома пропсами:

```js
const seats = Array.from({ length: 1200 }, (_, i) => ({ id: i }))
const onPick = () => {}
const make = (fn) => seats.map((seat) => ({ seat, picked: false, onPick: fn }))
for (let run = 0; run < 300; run++) {
  const prev = make(onPick)
  const same = make(onPick) // нові об'єкти пропсів, але кожен пропс той самий
  const other = make(() => {}) // пропс onPick щоразу нова функція
  let t = performance.now()
  for (let i = 0; i < 1200; i++) shallowEqual(prev[i], same[i])
  times.equal.push(performance.now() - t)
  t = performance.now()
  for (let i = 0; i < 1200; i++) shallowEqual(prev[i], other[i])
  times.different.push(performance.now() - t)
}
console.log('1200 порівнянь, усі пропси ті самі, медіана, мс:', median(times.equal).toFixed(3))
console.log('1200 порівнянь, функція щоразу нова, медіана, мс:', median(times.different).toFixed(3))
```

```text
1200 порівнянь, усі пропси ті самі, медіана, мс: 0.126
1200 порівнянь, функція щоразу нова, медіана, мс: 0.127
```

Обидва випадки коштують однаково, близько 0.13 мс, бо в обох порівняння проходить три пропси. На нашому екрані цю ціну
не видно за розкидом. Отже, чесний висновок такий: `memo` з несталим пропсом
не сповільнила екран помітно, але й не дала нічого, крім хибного відчуття, що оптимізацію зроблено.

## `useCallback`: та сама функція між рендерами

Хук `useCallback` приймає функцію й список залежностей і повертає ту саму функцію, поки залежності не змінилися:

```tsx
const pick = useCallback((id: number) => {
  setPicked((prev) => toggle(prev, id))
}, [])
```

Список залежностей порожній, бо функція не читає нічого з рендеру. Це заслуга оновлювача `(prev) => toggle(prev, id)`:
якби ми написали `setPicked(toggle(picked, id))`, у списку мав би стояти `picked`, і функція змінювалася б після
кожного вибору місця. Функцію `setPicked` у список не вносять, бо React гарантує, що вона та сама в усіх рендерах.

Довідник `useCallback` пояснює хук через уже знайомий: запис `useCallback(fn, deps)` працює як
`useMemo(() => fn, deps)`. Хук `useCallback` запам'ятовує саму функцію, а `useMemo` запам'ятовує результат її виклику.
Довідник також застерігає від хибного очікування: стрілкова функція в коді вище створюється в кожному рендері, а React
просто повертає вам попередню.

Тепер усі три пропси клітинки сталі, і `memo` починає працювати:

| Дія | Викликів `SeatCell` | `actualDuration`, мс | До кадру, мс |
|-----|---------------------|----------------------|--------------|
| клацання «Легенди» | 0 | 2.5 | 33.7 |
| вибір одного місця | 1 | 2.4 | 21.1 |
| зміна тарифу | 0 | 12.0 | 26.4 |

Вибір місця викликає рівно одну клітинку, у якої пропс `picked` змінився з `false` на `true`. Зміна тарифу коштує
12.0 мс, бо прогноз справді треба перерахувати, і це потрібна робота.

Рядок «Легенди» показує ще одну межу. Клітинок викликано нуль, а рендер займає 2.5 мс. Ця робота належить батькові:
`HallScreen` щоразу створює 1200 елементів, а React для кожного порівнює пропси. `memo` на дитині не робить дешевшим
батька.

### Одного «завжди нового» пропса досить

Картка називає ще одну причину тієї самої пастки, об'єкт. Замінимо булевий пропс `picked` на об'єкт, створений
просто в розмітці:

```tsx
<SeatCell key={seat.id} seat={seat} look={{ picked: picked.has(seat.id) }} onPick={pick} />
```

Запис `{{ ... }}` створює новий об'єкт для кожної клітинки в кожному рендері. Усе інше лишилося на місці: `memo`,
`useCallback`, `useMemo`. Результат такий:

| Варіант | «Легенда»: клітинок, мс | Вибір місця: клітинок, мс |
|---------|-------------------------|---------------------------|
| булевий пропс `picked` | 0, 2.5 | 1, 2.4 |
| об'єкт у пропсі `look` | 1200, 5.8 | 1200, 6.2 |

Дві пари фігурних дужок повернули всі 1200 викликів. Довідник `memo` радить два виходи: передавати окремі прості
значення, як було спочатку, або зробити об'єкт сталим через `useMemo`. У списку спосіб із `useMemo` не підходить, бо
хук не можна викликати в `map`.

### Що дав кожен крок

| Код | «Легенда»: клітинок, мс | Вибір місця: клітинок, мс | Тариф: клітинок, мс |
|-----|-------------------------|---------------------------|---------------------|
| без мемоізації | 1200, 16.3 | 1200, 16.3 | 1200, 16.0 |
| `useMemo` на прогнозі | 1200, 6.3 | 1200, 5.7 | 1200, 15.2 |
| ще `memo` на клітинці | 1200, 6.1 | 1200, 6.2 | 1200, 16.3 |
| ще `useCallback` на `pick` | 0, 2.5 | 1, 2.4 | 0, 12.0 |

Найбільше дав `useMemo`: 10 мс із 16. Пара `memo` і `useCallback` дала ще близько 4 мс, а кожен із цих двох
інструментів окремо не дав нічого. Як і в лекції «Профайлер», найдорожчим виявилося не те, що впадає в око: 1200
кнопок коштували менше за один цикл.

## Спершу спробуйте обійтися без мемоізації

Довідник `memo` в блоці «Should you add memo everywhere?» радить кілька принципів, які роблять мемоізацію зайвою. Один
із них каже тримати стан якомога нижче в дереві. Стан `legend` потрібен лише кнопці й абзацу, тому перенесемо його до
них:

```tsx
function LegendPanel() {
  const [legend, setLegend] = useState(false)
  return (
    <>
      <button type="button" onClick={() => setLegend((v) => !v)}>Легенда</button>
      {legend && <Legend />}
    </>
  )
}
```

`HallScreen` тепер показує `<LegendPanel />` і про легенду нічого не знає. У цьому варіанті немає ні `memo`, ні
`useMemo`, ні `useCallback`:

| Варіант | Викликів `HallScreen` | Викликів `SeatCell` | `actualDuration`, мс | До кадру, мс |
|---------|-----------------------|---------------------|----------------------|--------------|
| стан у `HallScreen`, без мемоізації | 1 | 1200 | 16.3 | 48.8 |
| стан у `HallScreen`, уся ручна мемоізація | 1 | 0 | 2.5 | 33.7 |
| стан у `LegendPanel`, без мемоізації | 0 | 0 | 0.1 | 17.5 |

Найкращий результат дав варіант без жодного хука мемоізації, бо `HallScreen` узагалі не рендериться. Правило звідси
таке: спершу спитайте, чи стан лежить там, де він потрібен. Мемоізація потрібна тоді, коли стан справді спільний. У
нашій залі таким є вибір місця: його читають і клітинки, і сума.

## React Compiler: те саме робить збірка

Ручна мемоізація має три ціни. Код стає довшим, списки залежностей треба підтримувати, а одна забута функція тихо
скасовує всю роботу. React Compiler знімає ці три ціни. Це інструмент, який працює під час збірки: він читає кожен
компонент і хук і переписує його так, щоб значення запам'ятовувалися самі. Документація називає його стабільним і
перевіреним у продакшні.

### Що компілятор робить із компонентом

Візьмемо малий компонент без жодної мемоізації:

```tsx
export function Summary({ seats, tariff, note }: SummaryProps) {
  const expected = forecast(seats, tariff)
  return (
    <p>
      Прогноз виторгу: {expected} грн. {note}
    </p>
  )
}
```

Щоб побачити результат до перетворення JSX, ми запустили плагін компілятора окремо, через `@babel/core`. Файл
`compile.mjs` читає файл компонента й друкує оброблений код. Параметр `logger` компілятора збирає його повідомлення
про кожну функцію, і вони знадобляться в розділі про пропущені компоненти:

```js
import { transformAsync } from '@babel/core'
import { readFileSync } from 'node:fs'

const file = process.argv[2]
const events = []
const out = await transformAsync(readFileSync(file, 'utf8'), {
  filename: file,
  babelrc: false,
  configFile: false,
  parserOpts: { plugins: ['typescript', 'jsx'] }, // JSX лишається JSX, щоб результат легко читався
  plugins: [['babel-plugin-react-compiler', { logger: { logEvent: (_name, e) => events.push(e) } }]],
})
console.log(out.code)
if (process.argv.includes('--events')) {
  for (const e of events) console.log('ПОДІЯ', e.kind, e.fnName ?? '', e.detail?.reason ?? '')
}
```

Команда `node compile.mjs Summary.tsx` надрукувала такий код. Рядки з описом типу пропсів й імпортом `forecast` тут
пропущено:

```js
import { c as _c } from "react/compiler-runtime";

export function Summary(t0) {
  const $ = _c(6);
  const {
    seats,
    tariff,
    note
  } = t0;
  let t1;
  if ($[0] !== seats || $[1] !== tariff) {
    t1 = forecast(seats, tariff);
    $[0] = seats;
    $[1] = tariff;
    $[2] = t1;
  } else {
    t1 = $[2];
  }
  const expected = t1;
  let t2;
  if ($[3] !== expected || $[4] !== note) {
    t2 = <p>Прогноз виторгу: {expected} грн. {note}</p>;
    $[3] = expected;
    $[4] = note;
    $[5] = t2;
  } else {
    t2 = $[5];
  }
  return t2;
}
```

Прочитаймо цей код частинами.

- `_c(6)` просить у React сховище на шість комірок. Функція `c` лежить у модулі `react/compiler-runtime`, який входить
  у пакет `react` версії 19, і викликає внутрішній хук React. Сховище належить екземпляру компонента, так само як його
  стан, тому два `Summary` на екрані мають два окремі сховища.
- Умова з `seats` і `tariff` охороняє обчислення. Комірки 0 і 1 зберігають значення `seats` і `tariff` з минулого
  разу, а комірка 2 зберігає результат. Якщо обидва значення ті самі, `forecast` не викликається. Це той самий
  `useMemo`, тільки список залежностей компілятор склав сам.
- Умова з `expected` і `note` охороняє елемент. Якщо обидва значення ті самі, функція повертає той самий об'єкт
  елемента, що й минулого разу.
- Порівняння написано оператором `!==`, тобто об'єкти й функції порівнюються за посиланням, як і в `memo`.

### Чому React пропускає дочірні компоненти без `memo`

У цьому коді немає `memo`. Компілятор не обгортає компоненти, а зберігає елементи, і цього досить через правило,
описане в довіднику `useMemo`: якщо батько повертає той самий об'єкт елемента, що й минулого разу, React не рендерить
цей компонент. Перевіримо це правило окремим дослідом. Хук `useMemo` зберігає тут не число, а елемент:

```tsx
function JsxDemo() {
  const [n, setN] = useState(0)
  const kept = useMemo(() => <StampKept />, []) // той самий об'єкт елемента в кожному рендері
  return (
    <main>
      <button type="button" onClick={() => setN(n + 1)}>Натиснуто {n}</button>
      {kept}
      <StampFresh /> {/* новий об'єкт елемента в кожному рендері */}
    </main>
  )
}
```

Обидва компоненти рахують свої рендери хуком `useRenderCount`. Скрипт заміру відкрив цей екран у збірках з
лічильником, без компілятора й із ним, тричі клацнув і надрукував лічильники:

```js
const show = (r) => `StampKept ${r.StampKept}, StampFresh ${r.StampFresh}, JsxDemo ${r.JsxDemo}`
await page.open('?v=jsx')
const before = JSON.parse(await page.ev(`JSON.stringify(window.lab.renders)`))
await page.click('#plus'); await page.click('#plus'); await page.click('#plus')
const after = JSON.parse(await page.ev(`JSON.stringify(window.lab.renders)`))
console.log(`${label}, після показу: ${show(before)}`)
console.log(`${label}, після трьох клацань: ${show(after)}`)
```


```text
без компілятора, після показу: StampKept 1, StampFresh 1, JsxDemo 1
без компілятора, після трьох клацань: StampKept 1, StampFresh 4, JsxDemo 4
з компілятором, після показу: StampKept 1, StampFresh 1, JsxDemo 1
з компілятором, після трьох клацань: StampKept 1, StampFresh 1, JsxDemo 4
```

Без компілятора React пропустив `StampKept`, бо отримав той самий елемент, і тричі викликав `StampFresh`. З
компілятором він пропустив обидва, бо компілятор зберіг і елемент `<StampFresh />`. Практичний наслідок: компілятор
економить там, де батько може повернути той самий елемент. Де батько мусить створити елемент заново, дитину буде
викликано.

### Як увімкнути компілятор у шаблоні Vite

Плагін `@vitejs/plugin-react` шостої версії більше не має параметра `babel`, яким компілятор вмикали раніше, тому
приклади зі старих статей у вашому шаблоні не працюють. Сторінка «`Installation` (React Compiler)» описує чинний
спосіб. Ми виконали його в копії шаблону.

```bash
npm install -D babel-plugin-react-compiler @rolldown/plugin-babel
```

| Пакет | Версія в нашому запуску | Навіщо він |
|-------|-------------------------|------------|
| `babel-plugin-react-compiler` | 1.0.0 | сам компілятор у вигляді плагіна для Babel |
| `@rolldown/plugin-babel` | 0.3.0 | плагін Vite, який пропускає ваші файли через Babel |
| `@babel/core` | 7.29.13 | Babel, тобто програма, яка читає код і переписує його за правилами плагінів |

Пакет `@babel/core` ми не ставили: він уже лежав у `node_modules`, бо його привіз `eslint-plugin-react-hooks`. README
плагіна `@vitejs/plugin-react` радить ставити його явно. Пакет `react-compiler-runtime` потрібен лише для React 17 і
18, а з React 19 збірка працює без нього. Той самий README описує ще дослідний спосіб без Babel, через пакет
`oxc-transform-react`. Його ми не запускали.

Розділ про Vite на сторінці React називає лише `@rolldown/plugin-babel`, а компілятор ставить окремий розділ вище.
Якщо його пропустити, збірка зупиняється. Ми поставили спершу лише `@rolldown/plugin-babel`, дописали налаштування,
показані нижче, і зібрали проєкт:

```bash
npm install -D @rolldown/plugin-babel   # пакета babel-plugin-react-compiler ще немає
npx vite build
```

Шлях до проєкту в цьому виводі замінено трьома крапками:

```text
RolldownError: [BabelError] [BABEL] …/src/main.tsx: Cannot find package 'babel-plugin-react-compiler' imported from …/node_modules/@vitejs/plugin-react/dist/index.js (While processing: "base$0")
```

У файлі налаштувань додаються два імпорти й один запис у списку плагінів:

```ts
// spa/vite.config.ts
import babel from '@rolldown/plugin-babel'
import react, { reactCompilerPreset } from '@vitejs/plugin-react'
import { defineConfig } from 'vitest/config'

export default defineConfig(({ mode }) => ({
  plugins: [react(), babel({ presets: [reactCompilerPreset()] })],
  // resolve, build і test лишаються такими, якими ви зробили їх у темі «Профайлер»
}))
```

Функція `reactCompilerPreset` повертає готовий набір налаштувань Babel із плагіном компілятора, а `babel(...)`
застосовує цей набір до ваших файлів. З таким файлом у нас пройшли `tsc -b`, `npm run build` і збірка для
профілювання. Компілятор діє всюди, де працює Vite: у `npm run dev`, у збірці й у тестах Vitest. Перевіримо це
тестом у jsdom, який показує екран і один раз клацає по «Легенді»:

```tsx
test('клацання по кнопці «Легенда»', () => {
  render(<HallScreen />)
  const afterMount = renders.SeatCell // скільки разів викликано клітинки під час показу
  fireEvent.click(screen.getByText('Легенда'))
  console.log('SeatCell після показу:', afterMount, '| після клацання:', renders.SeatCell)

```

Ми запустили його двічі командою `npx vitest run src/hall/hall.test.tsx --silent=false`, без компілятора й з ним:

Без компілятора клацання додало ще 1200 викликів, а з компілятором жодного. Отже, тести бачать той самий оброблений
код, що й браузер.

**За чим видно, що компілятор спрацював.** Ми перевірили три ознаки, і жодна не потребує розширення браузера.

1. У режимі розробки відкрийте в браузері адресу файла компонента, наприклад `http://localhost:5173/src/App.tsx`. Ми

   команда до сервера без компілятора не знайшла нічого.
2. У зібраному файлі порахуйте рядок `react.memo_cache_sentinel`. Сам React містить його один раз, а оброблений код
   додає його щоразу, коли зберігає значення без залежностей:

   У нас ця команда надрукувала `1` для збірки без компілятора й `32` для збірки з ним.
3. Продакшн-файл став більшим. Команди `npx vite build --outDir dist-prod` і

Ще одну ознаку називає документація: компоненти, які обробив компілятор, мають у вікні розширення React Developer
Tools позначку «Memo ✨», і дивитися її радять у режимі розробки. Вікна розширення ми не відкривали, тому цієї
позначки не бачили. Натомість ми прочитали вихідний код пакета `react-devtools-core` версії 8.0.0, окремого варіанта
тих самих інструментів. Він вважає компонент обробленим, якщо внутрішній запис React про цей компонент має поле
`updateQueue.memoCache`. Це поле ми прочитали на зібраній сторінці. Внутрішній запис React про елемент документа
лежить у властивості з назвою на `__reactFiber$`, а від нього скрипт іде вгору до найближчого компонента:

```js
const fiberOf = (el) => el[Object.keys(el).find((k) => k.startsWith('__reactFiber$'))]
const owner = (el) => {
  let f = fiberOf(el).return
  while (f && typeof f.type !== 'function' && !(f.type && f.type.$$typeof)) f = f.return // пропустити теги
  return f
}
const describe = (f) => ({ name: f.type.name ?? f.type.type.name, memoCache: f.updateQueue?.memoCache != null })
const seat = describe(owner(document.querySelector('.seat')))
const screen = describe(owner(document.querySelector('main')))
JSON.stringify({ seat, screen })
```

```text
dist-p plain {"seat":{"name":"SeatCell","memoCache":false},"screen":{"name":"HallScreen","memoCache":false}}
dist-rc plain {"seat":{"name":"SeatCell","memoCache":true},"screen":{"name":"HallScreen","memoCache":true}}
```

У збірці з компілятором поле мали обидва компоненти, а у збірці без компілятора жоден. Чи показує розширення у
вашому браузері позначку за тим самим полем, ми не перевіряли.

## Три гілки, один замір

Тепер головна таблиця дня. Гілка без мемоізації має код із початку лекції. Гілка з ручною мемоізацією має `memo`,
`useMemo` і `useCallback`. Гілка з компілятором має той самий код, що й гілка без мемоізації, але зібраний із
компілятором. Усі числа дав скрипт із розділу «Скрипт, який клацає й рахує медіани»: збірка для профілювання,
уповільнення в чотири рази, медіана 45 клацань для часу.

| | тариф | 1200 | 16.0 | 9.8 | 36.1 |

медіана першого показу з компілятором була більшою, ніж без нього, на 1–10 мс.

## Де компілятор не замінив ручну мемоізацію

Ось як компілятор переписав місце, де `HallScreen` створює клітинки:

```js
let t10;
if ($[20] !== picked || $[21] !== seats) {
  let t11;
  if ($[23] !== picked) {
    t11 = seat => <SeatCell key={seat.id} seat={seat} picked={picked.has(seat.id)} onPick={pick} />;
    $[23] = picked;
    $[24] = t11;
  } else {
    t11 = $[24];
  }
  t10 = seats.map(t11);
  $[20] = picked;
  $[21] = seats;
  $[22] = t10;
} else {
  t10 = $[22];
}
```

Компілятор зберіг результат `seats.map` як одне ціле, із залежностями `picked` і `seats`. Клацання по «Легенді» не
змінює жодної з них, тому React отримує той самий масив елементів і не викликає жодної клітинки. Вибір місця змінює
`picked`. Тоді `map` виконується знову й створює 1200 нових елементів, а нові елементи React рендерить. Окремого
сховища на кожен прохід `map` компілятор не робить.

Кожен із 1200 викликів дешевий, бо `SeatCell` теж оброблено: 1199 клітинок повертають збережену кнопку. Проте 1200
дешевих викликів коштували 6.6 мс, а один виклик у гілці з `memo` коштував 2.4 мс.

Тепер зберемо з компілятором код, у якому ручна мемоізація лишилася повністю чи частково:

| Код, зібраний із компілятором | Вибір місця: викликів `SeatCell` | `actualDuration`, мс |
|-------------------------------|----------------------------------|----------------------|
| без ручної мемоізації | 1200 | 6.6 |
| лише `useMemo` на прогнозі | 1200 | 6.1 |
| `useMemo` і `memo`, а `pick` звичайна функція | 1 | 3.0 |
| уся ручна мемоізація | 1 | 3.3 |
| уся ручна мемоізація, але об'єкт у пропсі `look` | 1200 | 7.4 |

Таблиця показує три речі.

1. `memo` на елементі списку лишається корисною і з компілятором. Саме вона пропускає 1199 клітинок із 1200.
2. Пастку з новою функцією компілятор виправив. У рядку, де `pick` є звичайною функцією, він сам зробив її сталою, і
   `memo` запрацювала. Без компілятора цей самий код викликав 1200 клітинок.
3. Пастку з новим об'єктом він не виправив. Об'єкт `look` створюється всередині функції, яку викликає `map`, окремо
   для кожного місця, і компілятор не має для нього сховища.

Тепер зрозуміло, що стоїть за порадою сторінки «`Introduction` (React Compiler)». У новому коді вона радить
покладатися на компілятор, а `useMemo` і `useCallback` лишати там, де потрібен точний контроль. Для наявного коду вона
радить або залишити мемоізацію, або ретельно перевірити застосунок, перш ніж її прибирати, бо без неї компілятор може
видати інший код. Довідник `memo` каже сміливіше, що з компілятором `memo` можна безпечно прибрати. На нашому списку
це прибирання збільшило кількість викликів з одного до 1200. Звідси застереження картки про масове видалення: не
видаляйте ручну мемоізацію всю одразу. Прибирайте по одному місцю й після кожного кроку повторюйте замір.

## Коли компілятор пропускає компонент

Компілятор вирішує за вас, які рядки компонента виконати, а які пропустити, і це безпечно лише для чистого коду.
Сторінка `Rules of React` збирає ці вимоги в один перелік: компонент дає той самий результат для тих самих пропсів,
стану й контексту, не змінює нічого зовнішнього під час рендеру, не змінює пропсів і стану, а хуки викликає лише на
верхньому рівні. Лекція «Чистота й дерево» пояснила ці правила на прикладах.

Якщо компілятор бачить порушення, він лишає компонент таким, як ви його написали, і обробляє решту файла. Збірка при
цьому не зупиняється й нічого не друкує. Візьмемо порушення, яке сьогодні легко зробити самому: лічильник рендерів у
тілі компонента.

```tsx
const calls = { screen: 0 }

export function HallScreen() {
  calls.screen += 1 // зміна зовнішнього об'єкта під час рендеру
  const [seats] = useState(makeSeats)
  // далі той самий код, що на початку лекції
}
```

Зберемо цей файл із компілятором і заміряємо клацання по «Легенді»:

| Код, зібраний із компілятором | Викликів `SeatCell` | `actualDuration`, мс | `console.time` прогнозу, мс |
|-------------------------------|---------------------|----------------------|-----------------------------|
| `HallScreen` без лічильника | 0 | 0.9 | 0.001 |
| `HallScreen` з лічильником у тілі | 1200 | 18.6 | 10.3 |

Один рядок повернув екран до стану з початку лекції. Прилад, яким ви хотіли міряти, змінив те, що ви міряли. Саме тому
наш лічильник стоїть в ефекті.

Дізнатися про пропущений компонент можна трьома способами.

**Лінт.** Лінт проєкту показав це місце без жодних додаткових налаштувань:

```bash
npx eslint src/hall/Counted.tsx
```

Вивід скорочено, пропущені рядки позначено трьома крапками:

```text
src/hall/Counted.tsx
  29:3  error  Error: This value cannot be modified

Modifying a variable defined outside a component or hook is not allowed. Consider using an effect.
…
> 29 |   calls.screen += 1
     |   ^^^^^ value cannot be modified
…  react-hooks/immutability
```

Повідомлення каже, що значення, оголошене поза компонентом, змінювати не можна, і радить ефект. Наприкінці стоїть
назва правила, `react-hooks/immutability`. Лічильник у змінній `let` дав у нас інше правило, `react-hooks/globals`, а
читання `ref.current` під час рендеру дало `react-hooks/refs`.

**Оброблений код.** Ось початок двох функцій у файлі `Counted.tsx`, який віддав сервер розробки з компілятором:

```text
8:function SeatCell(t0) {
9-	_s();
10-	const $ = _c(9);
--
88:export function HallScreen() {
89-	_s3();
90-	calls.screen += 1;
```

Рядок `_s()` додає Fast Refresh, тобто оновлення модуля без перезавантаження сторінки в режимі розробки. Функція
`SeatCell` просить сховище, а `HallScreen` одразу переходить до вашого коду: компілятор її не обробив.

**Позначка в інструментах.** За документацією, пропущений компонент не матиме позначки «Memo ✨». Вікна розширення ми
не відкривали. Внутрішнє поле, яке ми читали замість нього, у `HallScreen` з лічильником було відсутнє, а в `SeatCell`
було.

Є ще одна причина пропуску, яку легко принести з фази 1. Якщо в компоненті стоїть коментар, що вимикає правило лінту
React, наприклад `eslint-disable-next-line react-hooks/exhaustive-deps`, компілятор пропускає весь компонент. Про це
сказав сам компілятор через параметр `logger`. Ми передали скрипту `compile.mjs` з розділу «Що компілятор робить із
компонентом» такий файл:

```tsx
export function Forecast({ seats, tariff }: { seats: Seat[]; tariff: Tariff }) {
  // eslint-disable-next-line react-hooks/exhaustive-deps
  const value = useMemo(() => forecast(seats, tariff), [seats]) // tariff навмисно пропущено
  return <p>{value}</p>
}
```

Команда `node compile.mjs BadDeps.tsx --events` надрукувала код без змін і подію `CompileError` з текстом
`React Compiler has skipped optimizing this component because one or more React ESLint rules were disabled`.

### Порушення, яке компілятор не пропустив

Документація каже, що компонент із порушенням компілятор обходить. Наш запуск знайшов виняток, і він небезпечніший за
пропуск. Цей компонент читає годинник під час рендеру:

```tsx
function Clock({ tick }: { tick: number }) {
  const now = Date.now() // нечистий виклик: результат щоразу інший
  return (
    <p id="clock">
      Оновлення {tick}, час {now}
    </p>
  )
}
```

Батько має кнопку, яка збільшує `tick`. Скрипт заміру тричі натиснув її з паузою 300 мс і щоразу читав текст
абзацу:

```js
await page.open('?v=clock')
const texts = [await page.ev(`document.querySelector('#clock').textContent`)]
for (let i = 0; i < 3; i++) {
  await page.ev(`new Promise(r => setTimeout(r, 300))`)
  await page.click('#plus')
  texts.push(await page.ev(`document.querySelector('#clock').textContent`))
}
console.log(`${label}: ${texts.join(' | ')}`)
```


```text
без компілятора: Оновлення 0, час 1793972030295 | Оновлення 1, час 1793972030770 | Оновлення 2, час 1793972031148 | Оновлення 3, час 1793972031532
з компілятором: Оновлення 0, час 1793972032187 | Оновлення 1, час 1793972032187 | Оновлення 2, час 1793972032187 | Оновлення 3, час 1793972032187
```

Без компілятора час росте. З компілятором лічильник оновлень росте, а час застиг. Компілятор вважав `Date.now()`
звичайним обчисленням без залежностей і зберіг його результат назавжди. Лінт при цьому попереджав: правило
`react-hooks/purity` позначило цей рядок словами `Cannot call impure function during render`.

Звідси правило для практики. Помилку правила компілятора в лінті треба виправити, а не сподіватися, що компілятор
обійде це місце. Перш ніж вмикати компілятор, доведіть `npm run lint` до чистого виводу.

Для випадку, коли причину ще не знайдено, є тимчасовий вимикач: рядок `"use no memo"` на початку тіла компонента.
Компілятор такий компонент не чіпає, і параметр `logger` отримав про нього подію `CompileSkip`.

## Лінт: правила компілятора вже у вашому шаблоні


```text
recommended: 16 | лише в recommended-latest: react-hooks/void-use-memo
```

Ці 16 правил складаються з двох давніх, `rules-of-hooks` і `exhaustive-deps`, і чотирнадцяти правил компілятора.
Журнал змін плагіна каже, що в цьому наборі вони з версії 7.0.0. У шостій лінії, за дописом React про версію 19.2, їх
треба було вмикати окремо. Набір `recommended-latest` додає в нашій версії одне дослідне правило, `void-use-memo`, як
і показав вивід вище. Сторінка встановлення компілятора досі радить саме `recommended-latest`, але для сьогоднішніх
правил він не потрібен.

Колонку передбачення заповніть до запуску, як просить рецепт книжки How to Design Programs. Якщо передбачення не

вважали сталим. Назвіть у рядку збірку й уповільнення, бо без них числа не можна порівняти. Число `console.time`
запишіть і тоді, коли воно менше за 1 мс: воно і є відповіддю на запитання, чи варто було мемоізувати фільтр.

Картка також просить назвати місце, де мемоізація нічого не дала. У нашій залі таких місць три: `memo` на клітинці до
появи `useCallback`, `memo` з об'єктом у пропсі й можливий `useMemo` навколо суми, яка коштує 0.02 мс.

## Типові хибні уявлення

**«`memo` робить компонент швидшим».** Вона не пришвидшує рендер, а пропускає його, коли пропси ті самі. Перший показ
без уповільнення зайняв у нас 13.0 мс без мемоізації й 13.3 мс із нею.

**«Я обгорнув компонент у `memo`, отже, зайвих рендерів немає».** З новою функцією в пропсі клітинка в `memo`
викликалася 1200 разів, як і без `memo`. Перевіряйте лічильником.

**«`useCallback` не дає створювати функцію в кожному рендері».** Функція створюється щоразу. Хук лише повертає вам
попередню, якщо залежності ті самі.

**«`useMemo` варто ставити на кожне обчислення».** Сума за обрані місця коштувала 0.02 мс. Тут нічого економити, а
список залежностей додає місце для помилки.

**«Якщо компонент викликано, документ змінився».** Після клацання по «Легенді» React викликав 1200 клітинок і не
змінив жодної кнопки.

**«Компілятор обгортає кожен компонент у `memo`».** Він зберігає значення й елементи всередині компонентів. Клітинки,
створені в `map`, після вибору місця викликалися всі 1200.

**«З компілятором ручну мемоізацію треба видалити».** Документація радить залишити її або прибирати після перевірки. З
компілятором вибір місця коштував у нас 3.3 мс із ручною мемоізацією й 6.6 мс без неї.

**«Лічильник у тілі компонента нічого не змінює».** Через рядок `calls.screen += 1` компілятор не обробив
`HallScreen`, і рендер зайняв 18.6 мс замість 0.9 мс.

**«Якщо код порушує правила, компілятор його просто обійде».** Компонент із `Date.now()` він обробив, і час на екрані
перестав оновлюватися.

## Як це проявиться далі в React

- **Дні «`useTransition` і перший замір INP» і «`useDeferredValue`».** Мемоізація зменшує обсяг роботи, а ці два хуки,
  які ще попереду, керують тим, коли React її виконує.
- **День «Віртуалізація довгих списків».** Мемоізація не пришвидшила перший показ 1200 клітинок. Там ви побачите
  спосіб не створювати більшість клітинок узагалі.
- **Фаза 3, день «Сотні повідомлень на секунду».** Коли дані приходять десятки разів на секунду, кожен зайвий виклик
  рядка множиться на частоту. Там рядок списку отримає `memo` і сталі пропси, щоб React викликав лише змінені рядки.
- **Фаза 3, день «Глобальний стан».** Сховище із селекторами розв'язує сьогоднішню задачу з іншого боку: компонент
  рендериться лише тоді, коли змінилося значення, яке він сам вибрав.

## Перевірте себе

**1. Клацання змінює стан у батька, а пропси дочірнього компонента ті самі. Чому React усе одно викликає дочірній
компонент?**

<details><summary>Відповідь</summary>

Коли компонент рендериться, React за замовчуванням рендерить усі його дочірні компоненти й не перевіряє, чи змінилися
їхні пропси. Батько повертає нові об'єкти елементів, і React викликає функцію кожного з них.

</details>

**2. `console.time` навколо обчислення показує 0.02 мс з уповільненням у чотири рази. Чи варто загортати обчислення в
`useMemo`?**

<details><summary>Відповідь</summary>

Ні. Довідник `useMemo` називає орієнтиром близько 1 мс за одну дію, а це обчислення в п'ятдесят разів дешевше. Хук
додав би код і список залежностей, а заощадив би частку, якої не видно в замірі.

</details>

**3. Ви обгорнули рядок списку в `memo`, а лічильник далі показує, що React викликає всі рядки. Де шукати причину?**

<details><summary>Відповідь</summary>

Серед пропсів рядка є значення, яке батько створює заново в кожному рендері: функція, оголошена в тілі батька, або
об'єкт чи масив, записаний просто в розмітці. `Object.is` для нього щоразу дає `false`, і порівняння пропсів не
проходить.

</details>

**4. Чому список залежностей у `useCallback` для функції `pick` порожній?**

<details><summary>Відповідь</summary>

Функція не читає жодного значення з рендеру. Наступний стан вона обчислює оновлювачем `(prev) => toggle(prev, id)`, а
функція `setPicked` та сама в усіх рендерах. Якби функція читала `picked` напряму, він мав би стояти в списку.

</details>

**5. У коді, який видав компілятор, немає `memo`. Завдяки чому React пропускає дочірні компоненти?**

<details><summary>Відповідь</summary>

Компілятор зберігає створені елементи у сховищі компонента й повертає той самий об'єкт елемента, поки його вхідні
значення ті самі. React, отримавши той самий об'єкт елемента, не рендерить цей компонент.

</details>

**6. З компілятором і без `memo` вибір одного місця викликав 1200 клітинок, а клацання по «Легенді» жодної. Чому?**

<details><summary>Відповідь</summary>

Компілятор зберіг результат `seats.map` як одне ціле із залежностями `picked` і `seats`. «Легенда» їх не змінює, тому
масив елементів той самий. Вибір місця змінює `picked`, `map` виконується знову й створює 1200 нових елементів, а
нові елементи React рендерить.

</details>

**7. Ви додали в тіло компонента рядок `renders.list += 1`, щоб порахувати рендери в гілці з компілятором. Що
станеться і як про це дізнатися?**

<details><summary>Відповідь</summary>

Компілятор побачить зміну зовнішнього значення під час рендеру й лишить цей компонент необробленим, тому число буде як
у гілці без мемоізації. Лінт покаже помилку правила `react-hooks/immutability`, а в обробленому коді цього компонента
не буде рядка з `_c(`. Лічильник слід перенести в ефект.

</details>

**8. Лінт показав `react-hooks/purity` на рядку з `Date.now()`. Чому цю помилку не можна лишити, розраховуючи, що
компілятор обійде компонент?**

<details><summary>Відповідь</summary>

У нашому запуску компілятор такий компонент обробив і зберіг результат `Date.now()` як значення без залежностей. Час
на екрані перестав оновлюватися, хоча інші частини компонента оновлювалися.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| мемоізація | запам'ятовування результату, щоб не виконувати ту саму роботу вдруге |
| `memo` | функція, яка обгортає компонент; React пропускає його виклик, якщо кожен пропс дорівнює попередньому |
| поверхневе порівняння | порівняння кожного пропса через `Object.is`, без погляду всередину об'єктів |
| `useMemo` | хук, який зберігає результат обчислення, поки залежності ті самі |
| `useCallback` | хук, який зберігає саму функцію, поки залежності ті самі |
| `console.time`, `console.timeEnd` | пара функцій консолі, яка друкує час між двома викликами з однаковою назвою |
| React Compiler | інструмент збірки, який переписує компоненти й хуки так, щоб значення запам'ятовувалися самі |
| Babel | програма, яка читає код JavaScript і переписує його за правилами плагінів |
| `react/compiler-runtime` | модуль пакета `react`, з якого оброблений код бере сховище |
| `Rules of React` | правила чистоти компонентів і правила хуків, на які розраховує компілятор |
| `"use no memo"` | рядок на початку компонента, який просить компілятор його не обробляти |
