# Лекція. Фаза 2, день 5. `useTransition` і перший замір INP

Людина друкує в полі, а літери з'являються із запізненням і пачками. Такий екран називають повільним, навіть якщо
решта застосунку працює добре. Сьогодні ви вперше виміряєте цю затримку числом, яке називається INP, а потім приберете
її хуком `useTransition`, не пришвидшивши при цьому жодного компонента. Читання займе близько 80 хвилин, бо поруч із
кожним числом стоїть код, який його дав.

Числа в лекції отримано на React 19.3.1, Vite 8.3.6 і бібліотеці `web-vitals` 6.2.3 у браузері `chrome-headless-shell`
версії 157, тобто в Chromium без вікна, на одному ноутбуці під WSL. Літери набирали справжні події клавіатури, які
браузеру надсилав протокол інструментів розробника командою `Input.dispatchKeyEvent`. Процесор уповільнювала команда
того самого протоколу `Emulation.setCPUThrottlingRate`. Якщо біля числа не сказано іншого, його отримано на збірці для
профілювання (`vite build --mode profile`) з уповільненням у чотири рази, і це медіана семи прогонів. Де прогонів було
менше, про це сказано поруч. У вашому браузері й на вашому комп'ютері числа будуть іншими, тому порівнюйте
співвідношення, а не самі мілісекунди. Вікно Chrome DevTools ми не відкривали. Усе, що сказано про вкладку Performance
та її живі метрики, взято з документації, і біля кожного такого місця про це нагадано.

Практика дня просить зробити повільний список із фільтром. Щоб не показувати готового розв'язку, лекція бере інший
об'єкт: аркуш бейджів для конференції.

**Після лекції ви зможете пояснити:**

- чому поле «замерзає», хоч обробник у ньому складається з одного рядка;
- що саме міряє INP, з яких трьох частин складається час однієї взаємодії і звідки взялися пороги 200 і 500 мс;
- як отримати це число трьома способами і коли функція `onINP` викликає ваш колбек;
- чим термінове оновлення відрізняється від нетермінового і що робить `startTransition`;
- як React перериває рендер переходу і що каже `isPending`;
- чому перехід не робить рендер швидшим, а лише не дає йому блокувати введення;
- за яких двох умов перехід нічого не дає;
- що бачить користувач, коли в перехід загорнуто стан самого поля;
- як записати два числа в журнал вимірів.

## Поле, яке замерзає

Організатори конференції друкують бейджі. У полі вгорі вони набирають назву події, а нижче одразу бачать аркуш із
трьомастами бейджів. На кожному бейджі стоять назва події, ім'я гостя і візерунок. Візерунок є числом, яке
обчислюється з назви та імені, і саме він робить бейдж дорогим.

```tsx
const GUESTS: string[] = Array.from({ length: 300 }, (_, i) => `Гість ${i + 1}`)

// Візерунок бейджа: число, обчислене з тексту сталою кількістю кроків.
function pattern(text: string): string {
  let h = 7
  for (let step = 0; step < 36000; step++) {
    h = (h * 31 + text.charCodeAt(step % text.length) + step) % 1000003
  }
  return h.toString(16).padStart(5, '0')
}

function Badge({ event, guest }: { event: string; guest: string }) {
  return (
    <li className="badge">
      <b>{event === '' ? 'без назви' : event}</b> <span>{guest}</span>{' '}
      <code>{pattern(event + guest)}</code>
    </li>
  )
}

function PlainSheet({ event }: { event: string }) {
  return (
    <ul id="sheet">
      {GUESTS.map((guest) => (
        <Badge key={guest} event={event} guest={guest} />
      ))}
    </ul>
  )
}

const BadgeSheet = memo(PlainSheet)

function UrgentEditor() {
  const [event, setEvent] = useState('')
  return (
    <>
      <label>
        Назва події <input id="event" value={event} onChange={(e) => setEvent(e.target.value)} />
      </label>
      <BadgeSheet event={event} />
    </>
  )
}
```

У цьому коді варто помітити три речі.

- Функція `pattern` робить сталу кількість кроків. Лекція «Профайлер» показала, чому повільність для досліду пишуть
  саме так: цикл, який чекає за годинником, під уповільненням процесора не розтягується. Скільки коштує один бейдж, ми
  поміряємо нижче.
- Аркуш загорнуто в `memo`, який ви вивчали вчора. Зараз він нічого не дає, бо проп `event` змінюється з кожною
  літерою. Він знадобиться далі.
- Поле кероване, як у лекції «Події й стан»: один стан `event` іде і в `value` поля, і в аркуш.

У файлі, який ми запускали, були ще рядки для заміру: лічильники викликів і атрибут `data-event` у списку. Кожен такий
рядок показано там, де лекція вперше бере з нього число.

### Як ми набирали слово

Наберімо слово «форум» так, як друкує вправна людина: одна літера кожні 150 мс. У наших прогонах клавіші натискав
скрипт на Node, який керує браузером через протокол інструментів розробника. Ось його функція набору. Виклик
`page.send` надсилає браузеру одну команду протоколу. Таблицю `KEYS` з кодами клавіш і два рядки, які рахують
тривалість набору, тут пропущено:

```js
async function typeWord(page, word, intervalMs, holdMs = 50) {
  const jobs = []
  ;[...word].forEach((ch, i) => {
    const [code, vk] = KEYS[ch] ?? ['KeyA', ch.toUpperCase().charCodeAt(0)]
    const base = { key: ch, code, windowsVirtualKeyCode: vk, nativeVirtualKeyCode: vk }
    // натискання: браузер створює події клавіші й сам вставляє літеру в поле
    jobs.push(
      sleep(i * intervalMs).then(() =>
        page.send('Input.dispatchKeyEvent', { type: 'keyDown', text: ch, unmodifiedText: ch, ...base }),
      ),
    )
    // відпускання тієї самої клавіші через holdMs мілісекунд
    jobs.push(
      sleep(i * intervalMs + holdMs).then(() => page.send('Input.dispatchKeyEvent', { type: 'keyUp', ...base })),
    )
  })
  await Promise.all(jobs)
}
```

Головне тут у розкладі. Кожна команда чекає свого моменту `i * intervalMs` і не чекає, поки сторінка впорається з
попередньою літерою. Людина теж не чекає, а друкує далі. Перед набором скрипт уповільнює процесор таким рядком, де
`rate` дорівнює 4:

```js
await page.send('Emulation.setCPUThrottlingRate', { rate: Number(rate) })
```

### Що бачить людина

Щоб побачити те саме, що бачить людина, скрипт перед набором виконує на сторінці такий код:

```js
const input = document.getElementById('event')
input.focus() // ставимо курсор у поле без клацання
window.__field = [] // що показувало поле і з якого моменту
window.__keys = [] // коли сторінка отримала кожну клавішу
input.addEventListener('keydown', (e) => window.__keys.push({ key: e.key, at: performance.now() }), true)
let last = null
const tick = () => {
  // раз на кадр порівнюємо вміст поля з попереднім і записуємо лише зміни
  if (input.value !== last) {
    last = input.value
    window.__field.push({ value: last, at: performance.now() })
  }
  requestAnimationFrame(tick)
}
requestAnimationFrame(tick)
```

Функцію `requestAnimationFrame` ви знаєте з лекції «Як браузер малює»: браузер викликає передану функцію перед кожним
кадром. Тому масив `__field` містить те, що могло потрапити на екран. Після набору скрипт читає обидва масиви зі
сторінки в змінну `out` і друкує їх. Час він рахує від моменту, коли сторінка отримала першу клавішу:

```js
const t0 = out.keys[0].at
console.log(`${browser.version.product} | ${variant} | уповільнення ${rate}× | інтервал ${interval} мс`)
console.log('клавіші:', out.keys.map((k) => `${k.key}@${(k.at - t0).toFixed(0)}`).join(' '))
console.log(
  'поле по кадрах:',
  out.field.map((f) => `${JSON.stringify(f.value)}@${(f.at - t0).toFixed(0)}`).join(' '),
)
console.log('наприкінці в полі:', JSON.stringify(out.final))
```

Ось вивід одного прогону. Слово `urgent` у першому рядку є назвою варіанта, у якому оновлення аркуша термінове:

```text
HeadlessChrome/157.0.8103.38 | urgent | уповільнення 4× | інтервал 150 мс
клавіші: ф@0 о@264 р@524 у@754 м@1004
поле по кадрах: ""@-203 "фо"@513 "форум"@1272
наприкінці в полі: "форум"
```

Запис `"фо"@513` означає, що з 513-ї мілісекунди поле показувало «фо». Від'ємне число в першому записі означає момент
до першої клавіші: спостереження почалося за 203 мс до набору.

Рядок `клавіші` показує першу половину проблеми. Скрипт надіслав клавіші на 0, 150, 300, 450 і 600 мс, а сторінка
отримала їх на 0, 264, 524, 754 і 1004 мс. Рядок `поле по кадрах` показує другу половину. Пів секунди поле було
порожнім. Потім у ньому з'явилися одразу дві літери, а ще через три чверті секунди решта три. Людина закінчила
друкувати на 600-й мілісекунді, а слово побачила на 1272-й. Обробник `onChange` при цьому складається з одного виклику
`setEvent`. Що ж триває так довго?

Відповідь дає лекція «Пакетування оновлень». Після натискання клавіші React рендерить у мікрозадачі, тобто одразу
після обробника й до того, як браузер отримає керування. Рендер трьохсот бейджів на цій машині триває близько чверті
секунди, а точне число буде нижче. Увесь цей час головний потік зайнятий: він не може ні намалювати кадр, ні взятися
за наступну клавішу. Лекція «Як браузер малює» пояснила, що довга задача блокує і JavaScript, і малювання разом.

Тепер цю затримку треба виміряти, бо правило фази забороняє оптимізувати без числа.

## Що міряє INP

Лекція «Як браузер малює» вже дала означення. **INP** (Interaction to Next Paint, від взаємодії до наступного
малювання) є часом від дії людини до наступного кадру, який браузер покаже після цієї дії. Там частини цього часу були
показані на вигаданих числах, а сьогодні ви побачите їх на справжніх.

**Взаємодією** стаття web.dev називає групу подій, які браузер надсилає під час одного жесту людини. Для клавіші це
події `keydown`, `keypress` і `keyup`. Рахуються лише клацання, дотики й натискання клавіш, а прокручування й
наведення вказівника не рахуються. Час однієї взаємодії складається з трьох частин.

| Частина | Що це | Хто в ній винен |
|---------|-------|-----------------|
| затримка вводу, input delay | час від дії до початку першого обробника | головний потік зайнятий чимось іншим |
| робота обробників, processing duration | час, поки виконуються всі обробники цієї взаємодії | ваш код і рендер React, запущений із обробника |
| затримка до кадру, presentation delay | час від кінця обробників до показу кадру | стилі, компонування, малювання та все, що встигло вклинитися |

### Записи браузера

Ці три частини можна побачити без жодної бібліотеки. Браузер сам записує час кожної події, яку викликала дія людини.
Цей механізм називається Event Timing API. Записи отримують через `PerformanceObserver`, тобто спостерігача, якому
браузер передає нові записи певного типу:

```ts
type Row = { name: string; id: number; delay: number; work: number; total: number }
const rows: Row[] = []

const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as PerformanceEventTiming[]) {
    if (entry.interactionId === 0) continue // подія не належить до жодної взаємодії
    rows.push({
      name: entry.name,
      id: entry.interactionId,
      delay: Math.round(entry.processingStart - entry.startTime),
      work: Math.round(entry.processingEnd - entry.processingStart),
      total: entry.duration,
    })
  }
})
observer.observe({ type: 'event', durationThreshold: 16, buffered: true })
```

Розберімо цей код рядками.

- `type: 'event'` просить записи про події. Кожен запис є об'єктом `PerformanceEventTiming`.
- `durationThreshold: 16` знижує поріг. Сторінка MDN каже, що без цього параметра надходять лише записи від 104 мс, а
  менше за 16 мс поставити не можна.
- `buffered: true` просить віддати й ті записи, які браузер зібрав до створення спостерігача.
- `startTime` є моментом створення події, тобто приблизно моментом дії людини. `processingStart` і `processingEnd`
  позначають початок і кінець роботи обробників. Тому перша різниця дає затримку вводу, а друга дає роботу обробників.
- `duration` є часом від `startTime` до наступного малювання. Браузер округлює його до 8 мс, тому всі значення в
  колонці `total` кратні восьми.
- `interactionId` однаковий в усіх подій однієї взаємодії. Для подій поза взаємодією він дорівнює нулю.

Цей код працював на сторінці під час набору слова «форум» з інтервалом 150 мс. Це інший прогін, ніж у виводі вище,
тому кадри в ньому настали трохи пізніше. У файлі досліду масив ще записано у `window.__rows`, щоб скрипт міг
прочитати його зі сторінки. Після набору скрипт прочитав цей масив і надрукував його викликом `console.table(rows)`.
Тут показано перші шість рядків із п'ятнадцяти, тобто літери «ф» та «о»:

```text

│ (index) │ name       │ id   │ delay │ work │ total │
├─────────┼────────────┼──────┼───────┼──────┼───────┤
│ 0       │ 'keydown'  │ 6136 │ 1     │ 2    │ 592   │
│ 1       │ 'keypress' │ 6136 │ 3     │ 266  │ 592   │
```

- Три події з однаковим `id` складають одну взаємодію. Її час дорівнює найбільшому `total` серед них, тут 592 мс.
- Уся робота лежить у події `keypress`. У нашому запуску саме під час неї браузер вставляв літеру в поле й повідомляв
  про зміну, а на цю зміну реагує ваш `onChange`.
- Подія `keyup` сама нічого не робить, але теж довго чекає: клавішу відпустили через 50 мс після натискання, коли
  потік ще рендерив.

### Три частини кожної літери

Щоб звести три події клавіші в один рядок, у досліді працював другий такий самий спостерігач. Він складав у масив
чотири числа кожного запису без округлення: `startTime`, `processingStart`, `processingEnd` і `duration`. Скрипт
групував ці записи за `interactionId` і для кожної групи рахував частини. Ось середина цієї функції, а саме групування
в `byId` пропущено. Масив `rows` тут належить цій функції: це не той масив, у який писав спостерігач.

```js
for (const [id, list] of byId) {
  // найдовша подія взаємодії: її duration і є часом усієї взаємодії
  const worst = list.reduce((a, b) => (b.duration > a.duration ? b : a))
  // частини рахуємо за подіями натискання, без keyup
  const down = list.filter((e) => e.name !== 'keyup')
  const src = down.length ? down : list
  const start = Math.min(...src.map((e) => e.startTime))
  const pStart = Math.min(...src.map((e) => e.processingStart))
  const pEnd = Math.max(...src.map((e) => e.processingEnd))
  const dur = Math.max(...src.map((e) => e.duration))
  rows.push({
    id,
    names: list.map((e) => e.name).join('+'),
    start: +start.toFixed(1),
    inputDelay: +(pStart - start).toFixed(1), // затримка вводу
    processing: +(pEnd - pStart).toFixed(1), // робота обробників
    presentation: +(start + dur - pEnd).toFixed(1), // затримка до кадру
    duration: worst.duration,
  })
}
```

Рядки йдуть у порядку літер: «ф», «о», «р», «у», «м». Усі числа подано в мілісекундах. Колонка `start` рахує час від
відкриття сторінки. Якщо відняти від неї 1689.7, натискання припадуть на 0, 149, 299, 449 і 598 мс. Колонки
`inputDelay`, `processing` і `presentation` є трьома частинами, а `duration` є їхньою сумою, тобто часом усієї
взаємодії.

Прочитаймо цю таблицю як розклад головного потоку. Початок обробників дорівнює часу натискання плюс `inputDelay`, а
кінець дорівнює початку плюс `processing`. Наприклад, для літери «о» це 149 + 120.9 = 269.9 і 269.9 + 300.4 = 570.3.

| Час, мс | Що робить головний потік |
|---------|--------------------------|
| 0–269 | обробники літери «ф»: React рендерить аркуш зі словом «ф» |
| 270–570 | обробники літери «о», яка чекала з моменту 149 |
| 570–594 | браузер готує кадр, і в полі з'являється «фо» |
| 594–916 | обробники літери «р», яка чекала з моменту 299 |
| 917–1206 | обробники літери «у», яка чекала з моменту 449 |
| 1208–1481 | обробники літери «м», яка чекала з моменту 598 |
| після 1481 | браузер готує кадр, і в полі з'являється «форум» |

Тепер кожна колонка має пояснення.

- **Робота обробників**, колонка `processing`, майже однакова в усіх літер, від 268 до 322 мс. Це рендер аркуша.
- **Затримка вводу**, колонка `inputDelay`, росте з кожною літерою: 1, 121, 296, 468, 610 мс. Людина натискає клавішу
  кожні 150 мс, а потік звільняється кожні 300 мс, тому черга довшає.
- **Затримка до кадру**, колонка `presentation`, велика там, де браузер після обробників не намалював кадр, а взявся
  за наступну клавішу з черги. Літера «ф» чекала кадру 323 мс, бо перед малюванням браузер опрацював ще й «о». Чому
  браузер намалював кадр саме після «о» і після «м», а не після кожної літери, ми не з'ясовували. В одному з інших
  прогонів рядок `поле по кадрах` мав вигляд `""@-203 "фор"@1102 "форум"@1997`, тобто перший кадр показав три літери.

Найгірше довелося літері «р»: від натискання до кадру минуло 1208 мс.

### Одне число на сторінку

INP сторінки є найгіршою взаємодією за весь візит. Стаття web.dev уточнює: на кожні 50 взаємодій одну найгіршу
відкидають, щоб випадковий збій не псував оцінку. У цьому сеансі взаємодій п'ять, тому INP дорівнює найбільшому
значенню в колонці `duration`, тобто 1208 мс.

Один прогін може бути випадковим. Тому той самий набір ми повторили сім разів, щоразу в новому браузері. Скрипт бере
INP кожного прогону й друкує медіану та межі. Тут `ints` є результатом функції, показаної вище, а `rows` цього разу є
масивом прогонів. Решту полів об'єкта показано далі, там, де лекція бере з них числа:

```js
const median = (xs) => {
  const s = [...xs].sort((a, b) => a - b)
  return s.length % 2 ? s[(s.length - 1) / 2] : (s[s.length / 2 - 1] + s[s.length / 2]) / 2
}
// у циклі прогонів
rows.push({
  inp: ints.length ? Math.max(...ints.map((x) => x.duration)) : 0,
  // ...інші поля
})
// після циклу, для кожного поля k
const num = (k) => rows.map((r) => r[k])
console.log(k.padEnd(15), 'медіана', median(num(k)), '| від', Math.min(...num(k)), 'до', Math.max(...num(k)))
```

```text
inp             медіана 1112 | від 1080 до 1280
```

Отже, число «до» для цього екрана таке: медіана 1112 мс, а в окремих прогонах від 1080 до 1280 мс. Прогін із таблиці
вище до цих семи не входить.

Зверніть увагу, чого INP не міряє. Він не знає, коли оновився аркуш. Його цікавить лише наступний кадр після дії, хоч
би що цей кадр показав. Стаття web.dev каже про це прямо: показник задумано не для всіх наслідків взаємодії, а для
часу, протягом якого було заблоковане наступне малювання. Запам'ятайте це, бо саме на цьому тримається сьогоднішнє
рішення.

### Пороги

| Значення INP | Оцінка web.dev |
|--------------|----------------|
| до 200 мс включно | добре |
| понад 200 мс і до 500 мс включно | потребує поліпшення |
| понад 500 мс | погано |

Стаття `How the Core Web Vitals metrics thresholds were defined` пояснює, звідки ці числа. Дослідження сприйняття
сходяться на тому, що відповідь у межах приблизно 100 мс людина відчуває як наслідок власної дії. Проте поріг має бути
ще й досяжним. За даними, які Chrome зібрав у користувачів у травні 2022 року, в 100 мс вкладалося лише 12 % сайтів на
телефонах, а у 200 мс 56 %. Тому «добре» поставили на 200 мс. Поріг «погано» теж послабили, з 300 до 500 мс, бо за 300
мс поганими виявилися б 55 % із десяти тисяч найпопулярніших сайтів на телефонах.

Із цього випливають два застереження. Значення 200 мс не означає «миттєво», тому число 190 мс ще не привід зупинятися.
А самі пороги web.dev прикладає до 75-го перцентиля візитів справжніх користувачів, як пояснила лекція «Інструменти
браузера». Ваше число походить з одного сеансу на одному комп'ютері, тому для нього пороги є орієнтиром, а не вироком.

## Як отримати число

Картка дня називає два способи: живі метрики й функцію `onINP`. Третій спосіб ви щойно бачили: це записи браузера. Він
не потребує бібліотеки й показує всі три частини, тому таблиці цієї лекції зроблено ним. Тепер два способи з картки.

### Функція `onINP` з бібліотеки `web-vitals`

Бібліотеку `web-vitals` пише команда Chrome. Вона читає ті самі записи й рахує показник так, як його рахує сам Chrome.
Її ставлять командою `npm install web-vitals`. Ми працювали з версією 6.2.3.

```ts
import { onINP } from 'web-vitals'

onINP(
  (metric) => {
    console.log('INP', metric.value, metric.rating)
  },
  { reportAllChanges: true },
)
```

Функція `onINP` приймає колбек, тобто функцію, яку бібліотека викличе сама, коли матиме значення. У файлі досліду той
самий колбек ще складав кожне значення в масив `window.__inp`, щоб скрипт міг порахувати виклики, а параметр
`reportAllChanges` вмикався з адреси сторінки. У прогоні, який ми розбирали вище, консоль показала:

```text
INP 592 poor
INP 1208 poor
```

Колбек викликано двічі: спершу з часом літери «ф», а потім з часом літери «р», який виявився більшим. Літери «о», «у»
та «м» мали менший час, тому про них бібліотека не повідомила. Поле `rating` бібліотека рахує за порогами 200 і 500
мс.

Тепер найважливіше про цю функцію. README каже, що вона викликає колбек, коли значення готове до звіту, і новачок
очікує побачити число одразу. Ми перевірили запуском, коли це стається. Скрипт набирав дві літери, чекав три секунди,
читав довжину масиву `window.__inp`, а потім ховав сторінку. Ось його середина для випадку, коли вікно згортається.
Функція `evaluate` виконує вираз на сторінці й повертає його значення:

```js
// на сторінці: друкуємо кожну зміну видимості й момент, коли сторінку залишають
document.addEventListener('visibilitychange', () => console.log('visibilitychange:', document.visibilityState))
window.addEventListener('pagehide', () => console.log('pagehide'))

// у скрипті: скільки разів колбек викликано до приховування
console.log(
  'перед приховуванням: колбек викликано разів:',
  await evaluate(page, 'window.__inp.length'),
  '| видимість',
  await evaluate(page, 'document.visibilityState'),
)
// згортаємо вікно браузера командою протоколу
const { windowId } = await browser.send('Browser.getWindowForTarget', { targetId: page.targetId })
await browser.send('Browser.setWindowBounds', { windowId, bounds: { windowState: 'minimized' } })
// через півтори секунди читаємо масив знову й друкуємо консоль сторінки
```

Три запуски з викликом `onINP(fn)` без другого аргументу надрукували таке. У першому замість згортання скрипт
відкривав і активував другу вкладку командами `Target.createTarget` і `Target.activateTarget`. У третьому він закривав
сторінку командою `Target.closeTarget`. У другому запуску кінець об'єкта замінено трьома крапками:

```text
перед приховуванням: колбек викликано разів: 0 | видимість visible
activate | помилка: немає | після: {"n":0,"v":"visible","inp":[]}
консоль:

перед приховуванням: колбек викликано разів: 0 | видимість visible
minimize | помилка: немає | після: {"n":1,"v":"hidden","inp":[{"value":560,"rating":"poor", …}]}
консоль: INP 560 poor | visibilitychange: hidden

перед приховуванням: колбек викликано разів: 0 | видимість visible
close | помилка: немає | після: сторінки вже немає
консоль: pagehide | INP 552 poor | visibilitychange: hidden
```

Четвертий запуск мав `reportAllChanges: true`, і його перший рядок був таким:

```text
перед приховуванням: колбек викликано разів: 1 | видимість visible
```

Зведімо все в таблицю.

| Як викликано | Що ми зробили | Скільки разів викликано колбек |
|--------------|---------------|-------------------------------|
| `onINP(fn)` | набрали дві літери й чекали три секунди | 0 |
| `onINP(fn)` | після цього згорнули вікно браузера | 1 |
| `onINP(fn)` | після набору закрили сторінку | 1 |
| `onINP(fn, { reportAllChanges: true })` | набрали дві літери | 1, невдовзі після набору |
| `onINP(fn, { reportAllChanges: true })` | набрали слово «форум» | 1 або 2; у прогоні вище 2: спершу 592, потім 1208 |

Без другого аргументу бібліотека мовчить, поки сторінку видно. Вона повідомляє INP, коли стан видимості сторінки стає
`hidden`: людина перейшла на іншу вкладку, згорнула вікно чи закрила сторінку. Причина в означенні показника: INP
належить усьому візиту, тому остаточне число відоме лише наприкінці. Параметр `reportAllChanges: true` просить
повідомляти й проміжні значення. README попереджає, що й тоді колбек викликається не після кожної взаємодії, а лише
коли значення змінилося.

Вивід показує й особливість браузера без вікна. Функція `onINP` у ньому спрацьовує, проте сховати сторінку вдалося не
кожним способом. Після активації другої вкладки властивість `document.visibilityState` лишилася `visible`, і колбек не
викликався. Згортання вікна дало `hidden` і один виклик. У звичайному Chrome ми цього не перевіряли: README радить
перейти на іншу вкладку й повернутися.

Є ще одна деталь, яка впливає на число «після». Бібліотека просить у браузера лише записи від 40 мс. Окремо вона
завжди отримує запис про першу взаємодію на сторінці. Тому на швидкій сторінці `onINP` повідомляє час першої
взаємодії, навіть якщо пізніша була трохи довшою. Ми бачили це у варіанті з переходом без уповільнення. Скрипт друкує
для кожного прогону два числа поруч: `inp` з нашого спостерігача з порогом 16 мс і `vitals`, тобто значення з масиву
`window.__inp`. В одному прогоні там стояло 16 і 8: наш спостерігач зафіксував третю літеру з часом 16 мс, а
бібліотека повідомила 8 мс, тобто час першої.

### Живі метрики на вкладці Performance

Останній спосіб не потребує коду. За настановою web.dev `Manually diagnose slow interactions in the lab`, вкладка
Performance в інструментах розробника Chrome після відкриття показує екран живих метрик. Під час ваших дій у журналі
`Interactions` з'являються взаємодії, ту з них, яка визначає INP, виділено, а запис можна розгорнути й побачити три
частини. Уповільнення процесора на цій вкладці описала лекція «Профайлер». Цього екрана ми не відкривали, бо браузер
без вікна його не має, тому порівняйте назви зі своїм екраном.

### Від чого залежить число

Перш ніж записати число, подивіться, як воно змінюється від умов. Кожен рядок таблиці отримано з такого самого рядка
`inp`, як у розділі «Одне число на сторінку», тільки для іншої серії прогонів. Код той самий, оновлення аркуша
термінове. Змінювалися лише адреса збірки, уповільнення, інтервал і слово, які скрипт отримує з командного рядка.

| Умови заміру | INP, мс | Розкид | Оцінка |
|--------------|---------|--------|--------|
| збірка для профілювання, уповільнення 4×, літера кожні 150 мс | 1112 | 1080–1280 | погано |
| продакшн-збірка, 4×, 150 мс | 1144 | 1032–1344 | погано |
| збірка для профілювання, 4×, літера кожні 1000 мс | 352 | 328–368 | потребує поліпшення |
| збірка для профілювання, 4×, одна літера | 360 | 312–384 | потребує поліпшення |
| збірка для профілювання, без уповільнення, 150 мс | 80 | 72–128 | добре |
| режим розробки, 4×, 150 мс | 3568 | 3512–3688 | погано |

Рядки зі швидким набором на двох збірках і рядок з однією літерою мають по сім прогонів, рядок без уповільнення п'ять,
а рядки з повільним набором і з режимом розробки по три. Із таблиці випливають чотири правила заміру.

1. **Уповільнення вирішує, чи ви взагалі побачите проблему.** Без нього той самий екран дав 80 мс, тобто «добре». Ваш
   ноутбук швидший за телефон користувача, тому без уповільнення ви міряєте не той пристрій.
2. **Темп набору змінює число втричі.** За повільного набору кожна літера застає вільний потік, і INP дорівнює одному
   рендеру. За швидкого набору літери стають у чергу, і до рендеру додається очікування. Тому «до» і «після» набирайте
   однаково: те саме слово в тому самому темпі.
3. **Режим розробки дав число, утричі більше за збірку.** Лекція «Профайлер» пояснила чому. Таке число не йде в
   журнал.
4. **Продакшн-збірка й збірка для профілювання дали близькі числа.** INP не потребує `<Profiler>`, тому для журналу
   можна брати звичайну продакшн-збірку, яку отримують користувачі.

Є ще одне правило, якого в таблиці не видно: число залежить від того, чим зайнятий комп'ютер. Серія того самого
заміру, зроблена за чверть години до остаточної, дала медіану 1408 мс замість 1112. А в одній із серій варіанта з
переходом, про який ітиметься далі, три прогони з п'яти дали 80–168 мс замість 24–32. Причин ми не шукали. Тому заміри
«до» й «після» робіть поспіль і по кілька разів.

Ще одна порада стосується самого жесту. Клацання в полі, щоб поставити курсор, теж є взаємодією й теж потрапить в INP.
У наших прогонах курсор ставив метод `focus()`, тому рахувалися лише клавіші.

### Штучна повільність і уповільнення процесора

Картка просить, щоб кожен рядок рахував щось одну мілісекунду. Документація React у прикладі з повільною вкладкою
робить це циклом, який чекає одну мілісекунду за годинником. Ми додали такий цикл на початок функції `pattern` і
вмикали його параметром адреси сторінки:

```ts
if (BY_CLOCK) {
  const end = performance.now() + 1
  while (performance.now() < end) {
    // чекаємо за годинником, як у прикладах документації
  }
  return 'clock'
}
```

Скільки триває рендер аркуша, каже функція `onRender` компонента `<Profiler>` з лекції «Профайлер». У файлі досліду
нею огорнуто весь екран, а кожне значення `actualDuration` вона складає в масив:

```tsx
const onRender: ProfilerOnRenderCallback = (_id, phase, actual) => {
  counters.renderMs.push({ phase, actual, at: performance.now() })
}

// у розмітці кореня
<Profiler id="screen" onRender={onRender}>
  <Screen />
</Profiler>
```

Тут `counters` є звичайним об'єктом поза React, у який файл досліду складає заміри. Після набору скрипт читає його зі
сторінки у змінну `b.c`, бере найбільше значення за прогін і друкує медіану так само, як для `inp`. Виклик `slice(1)`
відкидає перший рендер під час відкриття сторінки:

```js
renderMax: +Math.max(0, ...b.c.renderMs.slice(1).map((x) => x.actual)).toFixed(0),
```

Чотири серії термінового варіанта надрукували такі рядки. Вони йдуть у такому порядку: цикл на кроки без уповільнення,
він же з уповільненням у чотири рази, цикл за годинником без уповільнення і він же з уповільненням:

```text
renderMax       медіана 62 | від 58 до 114
renderMax       медіана 256 | від 242 до 330
renderMax       медіана 309 | від 305 до 314
renderMax       медіана 417 | від 369 до 576
```

Зведімо медіани в таблицю:

| Як бейдж витрачає час | Рендер аркуша без уповільнення, мс | З уповільненням 4×, мс | У скільки разів виріс |
|-----------------------|------------------------------------|------------------------|-----------------------|
| цикл на 36 000 кроків | 62 | 256 | 4.1 |
| очікування 1 мс за годинником | 309 | 417 | 1.35 |

Рядок зі сталою кількістю кроків має п'ять прогонів без уповільнення і сім з уповільненням, а рядок з годинником по
три. Із рядка про кроки видно й ціну одного бейджа: 62 мс на триста бейджів дають приблизно 0.2 мс, а 256 мс дають
приблизно 0.85 мс.

Обидва способи годяться для порівняння «до» й «після». Проте з циклом за годинником уповільнення майже не діє, і
список буде повільним навіть без нього. Запишіть у журнал, яким способом зроблено повільність.

## Термінові й нетермінові оновлення

Число «до» є: 1112 мс. Тепер подивімося на причину інакше. Одне натискання клавіші просить екран про дві різні речі.

- Показати літеру в полі. Це **термінове** оновлення: людина дивиться на поле й чекає відповіді саме тут.
- Перемалювати триста бейджів. Це **нетермінове** оновлення: якщо аркуш оновиться на пів секунди пізніше, людина цього
  не помітить, бо ще друкує.

У компоненті `UrgentEditor` обидві речі висять на одному стані `event`. React не має як зробити одну з них раніше за
іншу. Тому спершу стан треба розділити на два, а потім сказати React, який із двох може зачекати. Для другого кроку
існує хук `useTransition`:

```tsx
function TransitionEditor() {
  const [draft, setDraft] = useState('')
  const [event, setEvent] = useState('')
  const [isPending, startTransition] = useTransition()

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    const next = e.target.value
    setDraft(next)
    startTransition(() => {
      setEvent(next)
    })
  }

  return (
    <>
      <label>
        Назва події <input id="event" value={draft} onChange={handleChange} />
      </label>
      <p id="status">{isPending ? 'Оновлюю аркуш…' : 'Аркуш відповідає полю'}</p>
      <BadgeSheet event={event} />
    </>
  )
}
```

- Стан `draft` зберігає те, що стоїть у полі. Стан `event` зберігає те, що показує аркуш. Більшість часу вони
  однакові, а під час набору `event` відстає.
- `useTransition()` не має аргументів і повертає пару. Перший елемент `isPending` каже, чи є незавершений перехід.
  Другий елемент `startTransition` є функцією, якою ви позначаєте оновлення.
- `setDraft(next)` викликано звичайним способом, тому це оновлення термінове.
- `setEvent(next)` викликано всередині функції, переданої в `startTransition`. Таке оновлення React називає
  **переходом** (Transition) і вважає нетерміновим.
- Значення `next` прочитано з події заздалегідь, у звичайну змінну. Обидва виклики `set` отримують одне й те саме
  значення.

### Що робить `startTransition`

Назва підказує, ніби функція щось відкладає, як `setTimeout`. Це не так. Ми перевірили порядок тестом у jsdom, тобто в
імітації браузера всередині Node. Компонент із двома вкладками складає рядки в масив `lines`: один рядок у тілі
компонента й три в обробнику клацання:

```tsx
const lines: string[] = []
function Tabs() {
  const [tab, setTab] = useState('склад')
  const [isPending, startTabChange] = useTransition()
  lines.push(`рендер: tab=${tab} isPending=${isPending}`) // кожен виклик компонента
  return (
    <button
      onClick={() => {
        lines.push('1: перед startTransition')
        startTabChange(() => {
          lines.push('2: усередині функції')
          setTab('звіти')
        })
        lines.push('3: після startTransition')
      }}
    >
      {tab}
    </button>
  )
}
render(<Tabs />)
lines.length = 0 // рядок першого рендеру нам не потрібен
await userEvent.click(screen.getByRole('button'))
console.log(lines.join('\n'))
```

```text
1: перед startTransition
2: усередині функції
3: після startTransition
рендер: tab=склад isPending=true
рендер: tab=звіти isPending=false
```

React викликає вашу функцію одразу. Відкладається не вона, а рендер тих оновлень, які вона запланувала. Довідник
пояснює це спрощеною моделлю: `startTransition` ставить прапорець, викликає функцію і знімає прапорець, а `set`
дивиться на прапорець і вирішує, яким зробити оновлення. Ми прочитали файл `react-dom-client.production.js` версії
19.3.1 і побачили схожу будову: на час виклику React зберігає об'єкт поточного переходу, а функція, яка обирає
пріоритет оновлення, перевіряє, чи цей об'єкт є. Це внутрішня будова React, і в наступних версіях деталі можуть
змінитися.

Рядки виводу, що починаються словом `рендер`, показують другу роботу `startTransition`. Перед викликом вашої функції
React терміново записує `isPending = true`. Тому компонент рендериться двічі: спершу зі старою вкладкою й позначкою
очікування, а потім із новою вкладкою.

Лекція «Пакетування оновлень» дала таблицю пріоритетів. Сьогодні до неї додається рядок.

| Де викликано `set` | Пріоритет | Як React рендерить |
|--------------------|-----------|--------------------|
| в обробнику `click`, `keydown`, `input` | найвищий | одразу в мікрозадачі, без перерв |
| у функції, переданій у `startTransition` | перехід | пізніше, окремими задачами планувальника і з перервами |

### Простежимо одну літеру

Людина натискає «ф» у порожньому полі. Щоб розкласти цю літеру по кроках, потрібні три джерела. Тривалість рендерів
дає `onRender`, код якого показано вище. Час до кадру з літерою дають записи браузера. Момент, коли на екрані з'явився
новий аркуш, записує ще один спостерігач у файлі досліду:

```ts
// коли аркуш у документі справді змінився і коли після цього настав наступний кадр
const sheetWatcher = new MutationObserver((records) => {
  for (const record of records) {
    const el = record.target as HTMLElement
    const row = { event: el.dataset.event ?? '', changed: performance.now(), frame: 0 }
    window.__sheet.push(row)
    requestAnimationFrame(() => {
      const channel = new MessageChannel()
      channel.port1.onmessage = () => {
        row.frame = performance.now()
      }
      channel.port2.postMessage(null)
    })
  }
})
sheetWatcher.observe(document.getElementById('root')!, {
  subtree: true,
  attributes: true,
  attributeFilter: ['data-event'],
})
```

`MutationObserver` викликає передану функцію, коли в документі щось змінилося. Тут він стежить за одним атрибутом. У
файлі досліду список аркуша має вигляд `<ul id="sheet" data-event={event}>`, тому атрибут змінюється саме тоді, коли
React записав у документ новий аркуш. Пара `requestAnimationFrame` і `MessageChannel` дає момент одразу після
наступного кадру: такий самий прийом міряв час до кадру в лекції «Пакетування оновлень».

Скрипт друкує для кожного прогону один рядок. Спершу в ньому стоять взаємодії: затримка вводу, робота обробників,
затримка до кадру та їхня сума. Далі йдуть тривалість і момент кожного коміту, а наприкінці моменти натискань. Час
комітів і натискань відлічено від початку набору: сторінка записує його рядком
`window.__typingStart = performance.now()` перед першою клавішею, і скрипт читає це значення в `b.typingStart`. Масив
`window.__sheet` скрипт читає в `b.sheetLog` і окремо рахує час до кадру з новим аркушем:

```js
details.push(
  ints.map((x) => `${x.inputDelay}+${x.processing}+${x.presentation}=${x.duration}`).join(' | ') +
    '  || onRender: ' +
    b.c.renderMs.slice(1).map((x) => `${x.actual.toFixed(0)}@${(x.at - b.typingStart).toFixed(0)}`).join(' ') +
    ' || клавіші: ' +
    ints.map((x) => (x.start - b.typingStart).toFixed(0)).join(' '),
)
const last = b.sheetLog.at(-1) // остання зміна аркуша, яку бачив sheetWatcher
const lastKey = ints.at(-1) // остання клавіша
rows.push({
  // ...інші поля
  toSheet: last ? +(last.frame - b.typingStart).toFixed(0) : 0, // від початку набору
  lastKeyToSheet: last && lastKey ? +(last.frame - lastKey.start).toFixed(0) : 0, // від останньої клавіші
})
```

У прогоні, де набирали лише літеру «ф», рядок вийшов таким, а поле `lastKeyToSheet` дорівнювало 363:

```text
0 0.3+18.4+5.3=24  || onRender: 2@19 244@314 || клавіші: 3
```

Нуль на початку є номером прогону. Взаємодія одна: 0.3 мс затримки вводу, 18.4 мс роботи обробників, 5.3 мс до кадру,
разом 24 мс. Запис `2@19` означає, що рендер тривав 2 мс, а його коміт стався на 19-й мілісекунді. Другий рендер
тривав 244 мс. Тепер простежимо, що стоїть за цими числами.

| Крок | Хто діє | Що змінюється |
|------|---------|---------------|
| 1 | браузер вставляє літеру, а React викликає `handleChange` | `next` дорівнює `ф` |
| 2 | `setDraft('ф')` | термінове оновлення в черзі |
| 3 | `startTransition` | термінове оновлення `isPending = true` в черзі, далі викликано вашу функцію |
| 4 | `setEvent('ф')` усередині функції | оновлення з пріоритетом переходу в черзі |
| 5 | мікрозадача React, терміновий рендер | `draft` дорівнює `ф`, `isPending` дорівнює `true`, `event` ще порожній |
| 6 | `memo` порівнює пропи аркуша | `event` той самий, аркуш пропущено, рендер зайняв 2 мс |
| 7 | браузер малює кадр через 24 мс після натискання | у полі «ф», під ним «Оновлюю аркуш…» |
| 8 | планувальник, рендер переходу | `event` дорівнює `ф`, React викликає бейджі один за одним, 244 мс |
| 9 | коміт і кадр через 363 мс після натискання | аркуш показує «ф», напис «Аркуш відповідає полю» |

Кадр із літерою настав через 24 мс після натискання, і саме цей час міряє INP: 24 мс замість 360 мс. Крок, на якому
`memo` порівнює пропи аркуша, ще знадобиться нижче: без нього перехід не працює.

## Як React перериває рендер

Одна літера ще не показує головного. Наберімо все слово з інтервалом 150 мс. Рендер аркуша триває близько 250 мс,
отже, наступна клавіша застає React посеред роботи.

Щоб побачити, що тоді стається, у файлі досліду компоненти аркуша рахують власні виклики. Ось ті самі `Badge` і
`PlainSheet`, що на початку лекції, але з рядками заміру:

```tsx
export const counters = {
  sheetCalls: 0, // скільки разів React викликав компонент аркуша
  badgeCalls: 0, // скільки разів React викликав компонент бейджа
  sheetCommits: [] as CommitRecord[], // рендери аркуша, що дійшли до коміту
  pendingLog: [] as string[], // значення isPending у кожному коміті редактора
  renderMs: [] as { phase: string; actual: number; at: number }[], // onRender
}

function Badge({ event, guest }: { event: string; guest: string }) {
  counters.badgeCalls++ // виконується щоразу, коли React викликає компонент
  return (
    <li className="badge">
      <b>{event === '' ? 'без назви' : event}</b> <span>{guest}</span>{' '}
      <code>{pattern(event + guest)}</code>
    </li>
  )
}

export function PlainSheet({ event }: { event: string }) {
  counters.sheetCalls++
  useEffect(() => {
    // ефект без масиву залежностей виконується після кожного коміту, у якому React рендерив аркуш
    counters.sheetCommits.push({ event, at: performance.now() })
  })
  return (
    <ul id="sheet" data-event={event}>
      {GUESTS.map((guest) => (
        <Badge key={guest} event={event} guest={guest} />
      ))}
    </ul>
  )
}
```

Після набору скрипт читає об'єкт `counters` зі сторінки. Він віднімає те, що набігло під час першого показу аркуша:
один виклик аркуша, триста викликів бейджа й один коміт:

```js
rows.push({
  // ...інші поля
  sheetCalls: b.c.sheetCalls - 1,
  badgeCalls: b.c.badgeCalls - mountCalls, // mountCalls дорівнює 300
  sheetCommits: b.c.sheetCommits.length - 1,
  domChanges: b.sheetLog.map((x) => x.event).join(','), // значення data-event, які бачив sheetWatcher
})
```

Сім прогонів варіанта з терміновим оновленням дали такі рядки:

```text
badgeCalls      медіана 1500 | від 1500 до 1500
sheetCalls      медіана 5 | від 5 до 5
sheetCommits    медіана 5 | від 5 до 5
```

Сім прогонів варіанта з переходом дали такі:

```text
badgeCalls      медіана 902 | від 875 до 952
sheetCalls      медіана 5 | від 5 до 5
sheetCommits    медіана 1 | від 1 до 1
```

Поле `domChanges` у кожному прогоні першого варіанта містило `ф,фо,фор,фору,форум`, а в кожному прогоні другого лише
`форум`. Зведімо це в одну таблицю.

| Що рахуємо за одне слово | Термінове оновлення | Оновлення в переході |
|--------------------------|---------------------|----------------------|
| викликів компонента аркуша | 5 | 5 |
| викликів компонента бейджа | 1500 | 902, у різних прогонах від 875 до 952 |
| рендерів аркуша, що дійшли до коміту | 5 | 1 |
| що показував аркуш | «ф», «фо», «фор», «фору», «форум» | лише «форум» |

Стовпець «Оновлення в переході» є доказом. React п'ять разів починав рендерити аркуш і лише раз довів справу до кінця.
З 902 викликів бейджа 300 належать останньому рендеру, а решта 602 належать чотирьом покинутим спробам, приблизно по
150 на кожну.

Ось як це виглядало в часі в одному з прогонів. Це такий самий рядок прогону, як для однієї літери, і друкує його той
самий код. Рядок довгий, тому тут його розірвано на два:

```text
1 0.3+14.4+9.3=24 | 0.7+4.1+11.2=16 | 5.5+5.3+5.2=16 | 5.1+4.1+6.8=16 | 2.8+3.5+9.7=16
  || onRender: 3@15 1@156 0@311 0@460 0@607 259@899 || клавіші: 2 152 302 451 601
```

Перша половина показує п'ять взаємодій, і найдовша з них тривала 24 мс. У другій половині всі числа подано в
мілісекундах, а час відлічено від початку набору. Запис `3@15` означає: рендер тривав 3 мс, а коміт стався на 15-й
мілісекунді. П'ять крихітних комітів ідуть одразу за клавішами, і кожен із них оновлює поле. Один великий коміт на 259
мс настав через 298 мс після останньої клавіші. Поле `badgeCalls` у цьому прогоні дорівнювало 920.

Ще одне поле скрипту каже, скільки найдовше клавіша чекала початку обробників. Ось його рядок і те, що він надрукував
для семи прогонів переходу:

```js
maxDelay: ints.length ? Math.max(...ints.map((x) => x.inputDelay)) : 0,
```

```text
maxDelay        медіана 5.5 | від 3.9 до 5.9
```

Механізм має чотири кроки.

1. **React рендерить перехід частинами.** Цикл рендеру переходу після кожного компонента й кожного елемента питає
   планувальника, чи не час зупинитися. У пакеті `scheduler` версії 0.28.0, який React 19.3.1 ставить разом із собою,
   межа дорівнює 5 мс. Коли час вийшов, React повертає керування браузеру, а решту роботи ставить наступною задачею.
2. **Між частинами браузер робить свою роботу.** Він може намалювати кадр і може передати подію клавіатури. Найдовша
   затримка вводу за прогін мала в цьому варіанті медіану 5.5 мс. Тобто клавіша чекала лише до кінця поточної частини.
3. **Клавіша дає термінове оновлення, і React виконує його першим.** Терміновий рендер редактора тривав від 0 до 3 мс,
   бо аркуш у ньому пропущено.
4. **Розпочатий рендер переходу React покидає й починає заново.** Нове оновлення `setEvent` замінило значення, тому
   доробляти аркуш для слова «ф» немає сенсу. Довідник каже про це в застереженнях: оновлення, позначене як перехід,
   переривають інші оновлення стану.

Значення `isPending` редактор у файлі досліду записував сам. Цей ефект стоїть у компоненті `TransitionEditor` і
виконується після кожного його коміту:

```tsx
useEffect(() => {
  counters.pendingLog.push(`${isPending ? 'pending' : 'ready'} поле="${draft}" аркуш="${event}"`)
})
```

Скрипт друкує масив одним рядком: `console.log('isPending:', b.c.pendingLog.join(' | '))`. Тут слово `isPending:` і
роздільники прибрано, а кожен запис подано з нового рядка:

```text
ready поле="" аркуш=""
pending поле="ф" аркуш=""
pending поле="фо" аркуш=""
pending поле="фор" аркуш=""
pending поле="фору" аркуш=""
pending поле="форум" аркуш=""
ready поле="форум" аркуш="форум"
```

Отже, `isPending` не означає «React зараз рендерить». Він означає «перехід почато, а його результату на екрані ще
немає». Ним показують, що аркуш застарів: написом, як у нас, або напівпрозорістю.

### Перерваний рендер і чистота

Лекція «Чистота й дерево» обіцяла, що в цей день ви побачите, як React кидає рендер посередині. Тепер це видно в
числах: за медіаною 602 виклики бейджа не закінчилися нічим. Якби `Badge` під час рендеру щось надсилав на сервер чи
змінював спільний об'єкт, це сталося б 902 рази заради 300 бейджів на екрані.

Наші лічильники самі є таким порушенням, і лінтер шаблону це бачить. Команда `npx eslint src/badges` для рядка
`counters.sheetCalls++` у компоненті `PlainSheet` надрукувала таке. Шлях до файла й фрагмент коду з вказівником, які
ESLint друкує поруч, тут пропущено:

```text
  16:3  error  Error: This value cannot be modified

Modifying a variable defined outside a component or hook is not allowed. Consider using an effect.
```

Правило, яке це перевіряє, називається `react-hooks/immutability`. У досліді ми порушили його свідомо, бо хотіли
порахувати саме виклики. У коді застосунку такого рядка бути не повинно.

Звідси й межа інструмента з дня «Профайлер». Функція `onRender` бачить лише ті рендери, які дійшли до коміту. У
прогоні вище вона показала 259 мс на останній рендер, а 620 викликів бейджа з 920, тобто дві третини, не потрапили в
жоден `actualDuration`.

## Перехід не робить рендер швидшим

Тепер число «після» і три числа поруч із ним. Усі чотири рядки таблиці є медіанами полів, код яких показано вище. INP
береться з поля `inp`, тривалість рендеру з поля `renderMax`, час після однієї літери з поля `lastKeyToSheet`, а час
для цілого слова з поля `toSheet`.

| Що міряємо | Термінове оновлення | Оновлення в переході |
|------------|---------------------|----------------------|
| INP, слово з інтервалом 150 мс | 1112 мс | 24 мс, розкид 24–32 |
| `actualDuration` одного рендеру аркуша | 256 мс | 260 мс |
| одна літера: від натискання до кадру з новим аркушем | 360 мс | 392 мс |
| слово: від першого натискання до кадру з аркушем «форум» | 1418 мс | 967 мс |

INP зменшився в 46 разів і з оцінки «погано» перейшов в оцінку «добре». Продакшн-збірка дала 1144 мс до і 32 мс після.

Рядки про `actualDuration` і про одну літеру показують, чого перехід не зробив. Рендер аркуша коштує стільки само, 256
і 260 мс. Після однієї літери аркуш з'явився навіть трохи пізніше, через 392 мс замість 360. Різниця менша за розкид
між прогонами, але напрям зрозумілий: робота та сама, а до неї додалися перерви. Перехід змінив не тривалість роботи,
а її місце. Раніше рендер стояв між клавішею і кадром. Тепер він стоїть після кадру й поступається кожній новій
клавіші.

Рядок про ціле слово показує, де перехід таки заощадив час. Слово з'явилося на аркуші на 450 мс раніше, бо React не
довів до кінця чотири проміжні аркуші, яких людина й так не встигла б прочитати.

Це заощадження залежить від темпу. Коли ми набирали літеру раз на секунду, кожен рендер встигав завершитися до
наступної клавіші. Тоді в трьох прогонах обидва варіанти довели до коміту всі п'ять рендерів аркуша й дали по 1500
викликів бейджа, а INP був 352 мс проти 24 мс. Те саме сталося без уповільнення: рендер займав 62 мс, наступна клавіша
приходила через 150 мс, і переривати було нічого, тому до коміту знову дійшли всі п'ять рендерів аркуша. Тобто користь
для INP є завжди, а пропуск проміжних рендерів з'являється лише тоді, коли рендер довший за паузу між діями.

Якщо аркуш потрібен швидше, перехід не допоможе. Тоді треба зменшувати саму роботу: рахувати менше, мемоізувати
обчислення або малювати лише видимі рядки, чим займеться день «Віртуалізація довгих списків».

## Дві умови, без яких перехід не працює

Обидві умови ми знайшли запуском, і перша з них стосується вашої практики.

### Важкий компонент має вміти пропустити рендер

Приберімо `memo`: редактор той самий, але малює `<PlainSheet event={event} />`. Числа в таблиці є медіанами тих самих
полів скрипту: `inp`, `badgeCalls` і `sheetCommits`.

| Варіант | INP, мс | Викликів бейджа | Рендерів аркуша, що дійшли до коміту |
|---------|---------|-----------------|--------------------------------------|
| оновлення термінове, аркуш у `memo` | 1112 | 1500 | 5 |
| перехід, аркуш у `memo` | 24 | 902 | 1 |
| перехід, аркуш без `memo` | 856 | 1800 | 6 |

Без `memo` перехід майже нічого не дав. Причина лежить у тому кроці таблиці про одну літеру, де `memo` порівнює пропи
аркуша. Терміновий рендер викликає компонент редактора, а React за замовчуванням викликає й усіх його дітей. Аркуш
отримує старе значення `event`, але без `memo` React цього не перевіряє й рендерить усі триста бейджів заново. Потім
рендер переходу робить те саме з новим значенням. До коміту дійшли шість рендерів аркуша, і п'ять із них нічого не
змінили в документі.

На списку з фільтром ця помилка б'є ще сильніше. Ми перевірили кроки картки на списку з чотирьохсот рядків, по три
прогони на продакшн-збірці: без переходу INP був 984 мс, з переходом і `memo` 24 мс, а з переходом без `memo` 4688 мс.
Без переходу список скорочувався після першої літери. З переходом без `memo` кожна клавіша рендерила весь
невідфільтрований список, бо стан фільтра ще не встиг змінитися. Коду цього списку тут немає, бо він є вашою
практикою, а міряв його той самий скрипт.

Отже, перехід потребує, щоб терміновий рендер був дешевим. Цього досягають двома способами: загортають важкий
компонент у `memo` або будують дерево так, щоб стан поля жив у компоненті, який не має важких дітей. Якщо у вашій
гілці ввімкнено React Compiler, пропуск може з'явитися сам, але сьогодні ми цього варіанта не запускали. Перевіряйте
лічильником, а не здогадом.

### React перериває лише між компонентами

Тепер зробімо аркуш одним компонентом, який сам у циклі рахує всі триста візерунків і не має компонента `Badge`. Ось
цей компонент із файла досліду разом із лічильниками:

```tsx
function MonolithSheetImpl({ event }: { event: string }) {
  counters.sheetCalls++
  useEffect(() => {
    counters.sheetCommits.push({ event, at: performance.now() })
  })
  const rows = GUESTS.map((guest) => {
    counters.badgeCalls++
    return (
      <li className="badge" key={guest}>
        <b>{event === '' ? 'без назви' : event}</b> <span>{guest}</span>{' '}
        <code>{pattern(event + guest)}</code>
      </li>
    )
  })
  return (
    <ul id="sheet" data-event={event}>
      {rows}
    </ul>
  )
}

export const MonolithSheet = memo(MonolithSheetImpl)
```

Роботи стільки само, `memo` на місці, оновлення в переході. Сім прогонів цього варіанта надрукували для поля
`maxDelay` рядок `maxDelay        медіана 151.7 | від 141.3 до 270.5`. Таблиця порівнює медіани полів `inp`,
`maxDelay` і `sheetCalls` у семи прогонах кожного варіанта.

| Варіант | INP, мс | Найдовша затримка вводу, мс | Викликів компонента аркуша |
|---------|---------|-----------------------------|----------------------------|
| триста компонентів `Badge` | 24 | 5.5 | 5 |
| один компонент на весь аркуш | 208 | 152 | 4 |

Медіана INP виросла до 208 мс і вийшла за поріг «добре», а в найгіршому прогоні було 296 мс. React питає планувальника
про час після кожного компонента, а всередині компонента зупинитися не може, бо це звичайний виклик вашої функції.
Один компонент на 240 мс означає 240 мс без жодної перерви. Клавіша, натиснута в цей час, чекає кінця функції.

Тому в практиці повільний саме кожен рядок, а не список загалом. І тому перехід не рятує компонент, який сам виконує
довге обчислення: таке обчислення треба ділити на компоненти, зменшувати чи виносити з рендеру.

## Пастка: стан поля в переході

Два стани здаються зайвими. Хочеться лишити один і просто загорнути його оновлення в перехід:

```tsx
function TrapEditor() {
  const [event, setEvent] = useState('')
  const [, startTransition] = useTransition()

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    const next = e.target.value
    startTransition(() => {
      setEvent(next)
    })
  }

  return (
    <>
      <label>
        Назва події <input id="event" value={event} onChange={handleChange} />
      </label>
      <BadgeSheet event={event} />
    </>
  )
}
```

Довідник у розділі про типові проблеми каже, що так робити не можна, але не каже, що саме побачить людина. Ми набрали
те саме слово, а скрипт щокадру читав вміст поля тим самим кодом, що й на початку лекції. Варіант у ньому називається
`trap`. Два прогони на екрані з повільним аркушем, з інтервалом 150 і 1000 мс, надрукували таке:

```text
HeadlessChrome/157.0.8103.38 | trap | уповільнення 4× | інтервал 150 мс
клавіші: ф@0 о@152 р@297 у@449 м@598
поле по кадрах: ""@-206 "м"@897
наприкінці в полі: "м"
HeadlessChrome/157.0.8103.38 | trap | уповільнення 4× | інтервал 1000 мс
клавіші: ф@0 о@999 р@1999 у@2999 м@4001
поле по кадрах: ""@-204 "ф"@307 "фо"@1295 "фор"@2313 "фору"@3311 "форум"@4335
наприкінці в полі: "форум"
```

У першому прогоні сторінка отримувала клавіші вчасно, але поле лишалося порожнім 897 мс, а потім показало одну літеру.
Ще один такий самий прогін дав `"м"@981`. У другому прогоні всі літери є, проте кожна запізнюється. Запізнення
дорівнює різниці між записом у рядку `поле по кадрах` і записом у рядку `клавіші`: 307 − 0 = 307, 1295 − 999 = 296,
2313 − 1999 = 314, 3311 − 2999 = 312 і 4335 − 4001 = 334 мс.

Так само ми прогнали ще два варіанти. У першому аркуша немає: замість `<BadgeSheet event={event} />` стоїть абзац із
тим самим текстом. Другий є правильним редактором із двома станами. Зведімо все в таблицю.

| Умови | Що показувало поле | Що в полі наприкінці |
|-------|--------------------|----------------------|
| повільний аркуш, літера кожні 150 мс | порожньо, а через 0.9–1 с після першого натискання одна літера | `м` |
| повільний аркуш, літера кожні 1000 мс | кожна літера з'являлася через 296–334 мс після натискання | `форум` |
| екран без аркуша, літера кожні 150 мс | кожна літера через 27–30 мс | `форум` |
| правильний варіант із двома станами, 150 мс | кожна літера через 8–16 мс | `форум` |

За швидкого набору з п'яти літер лишилася одна. Це гірше за повільність: поле губить те, що людина надрукувала. При
цьому INP у такому прогоні був 24 мс, бо кадр після кожної клавіші наставав швидко: функція `onINP` надрукувала
`INP 24 good`. Показник лишився добрим, а поле перестало працювати. INP міряє час до кадру і нічого не знає про те, чи
правильний цей кадр.

Причину видно в таблиці «Від клавіші до літери» з лекції «Події й стан». Браузер вставляє літеру, React викликає
`onChange`, а потім приводить поле до значення зі стану. У звичайному полі стан на цей момент уже новий. Тут стан
зміниться лише після рендеру переходу, тому React повертає полю старе значення, тобто порожній рядок. Наступна клавіша
вставляє літеру вже в порожнє поле, обробник читає з нього одну літеру, і нове оновлення замінює попереднє. Так до
кінця доживає лише остання літера.

Рядок про екран без аркуша пояснює, чому цю помилку пропускають. На легкому екрані рендер переходу закінчується за
кілька мілісекунд, і поле виглядає справним. Помилка проявиться того дня, коли екран стане важким.

Довідник дає два виходи. Перший ви вже бачили: два стани, з яких стан поля оновлюється звичайним `set`. Другий вихід є
хуком `useDeferredValue`, який ви вивчатимете завтра. Він дає той самий результат, коли функції `set` у вас немає, бо
значення прийшло пропом: ви лишаєте один стан, а хук сам повертає його копію, що відстає.

## Що ще є на сторінках дня

Читання дня згадує дві речі, які лекція не розкривала.

**Окрема функція `startTransition`.** Її імпортують просто з пакета `react`, без хука. Вона так само позначає
оновлення переходом, але не дає `isPending`. Довідник призначає її для місць, де хук викликати не можна, наприклад для
коду поза компонентами. Ми замінили нею функцію з хука в редакторі бейджів. У файлі досліду вона імпортована під іншим
ім'ям, щоб не плутати її з функцією з хука:

```tsx
// useEffect і useTransition у цьому рядку потрібні сусіднім компонентам того самого файла
import { startTransition as startAnyTransition, useEffect, useState, useTransition, type ChangeEvent } from 'react'

export function StandaloneEditor() {
  const [draft, setDraft] = useState('')
  const [event, setEvent] = useState('')

  function handleChange(e: ChangeEvent<HTMLInputElement>) {
    const next = e.target.value
    setDraft(next)
    startAnyTransition(() => {
      setEvent(next)
    })
  }
  // розмітка та сама, що в TransitionEditor, тільки без абзацу зі статусом
}
```

П'ять прогонів цього варіанта надрукували такі рядки:

```text
inp             медіана 24 | від 24 до 24
sheetCommits    медіана 1 | від 1 до 1
```

Отже, INP був 24 мс, а до коміту дійшов один рендер аркуша, як і з хуком. Показати напис «Оновлюю аркуш…» у цьому
варіанті нічим.

**Слово Action.** Починаючи з React 19 сторінка `useTransition` називає функцію, передану в `startTransition`, словом
Action і дозволяє їй бути асинхронною, тобто чекати відповіді сервера. Тоді `isPending` лишається `true`, доки запит
не завершиться. Із цим пов'язане застереження: `set` після `await` треба ще раз загорнути в `startTransition`. Цю
частину вивчає фаза 3 у дні «Форми в React 19», і сьогодні ми її не запускали. Для сьогоднішньої задачі досить
синхронної функції з одним `set`.

4. Наберіть слово й запишіть INP. Повторіть кілька разів і візьміть медіану, як у темі про журнал.
5. Змініть код і повторіть замір тим самим словом у тому самому темпі.
6. Перевірте очима, що поле показує кожну літеру. Число цього не перевіряє.

Вручну ви не втримаєте інтервал 150 мс так рівно, як скрипт. Тому ваші прогони розійдуться сильніше за наші, і одного
заміру замало.

## Типові хибні уявлення

**«Перехід пришвидшує рендер».** Рендер аркуша тривав 256 мс терміново і 260 мс у переході. Перехід лише переносить цю
роботу за кадр і дозволяє її перервати.

**«`startTransition` відкладає мою функцію, як `setTimeout`».** Функція виконується одразу: рядки надрукувалися в
порядку 1, 2, 3. Відкладається рендер оновлень, які вона запланувала.

**«Досить загорнути `set` у `startTransition`, і поле оживе».** Без `memo` на аркуші INP був 856 мс, а на списку з
фільтром 4688 мс проти 984 мс без переходу. Терміновий рендер має оминати важкий компонент.

**«Перехід допоможе з будь-яким повільним компонентом».** React перериває рендер лише між компонентами. Один компонент
на 240 мс дав затримку вводу 152 мс і INP 208 мс.

**«INP показує, як швидко оновився список».** INP міряє час до наступного кадру. У пастці з одним станом він був 24
мс, а поле загубило чотири літери з п'яти.

**«`onINP(console.log)` нічого не друкує, отже, бібліотека не працює».** Без `reportAllChanges` вона повідомляє
значення, коли сторінку приховано. За три секунди на видимій сторінці колбек не викликався жодного разу.

**«На моєму ноутбуці INP 80 мс, тож проблеми немає».** Це число без уповільнення. З уповільненням у чотири рази той
самий код дав 1112 мс.

**«Стан поля теж можна оновлювати в переході, React розбереться».** Кероване поле після кожної клавіші повертається до
значення зі стану. За швидкого набору в полі лишилася одна літера, а за повільного кожна літера чекала близько 300 мс.

**«`isPending` означає, що React зараз рендерить».** Він означає, що перехід почато, а його результат ще не показано.
Під час набору слова він був `true` в п'яти комітах поспіль.

**«Якщо `onRender` показав 259 мс, React стільки й працював».** `onRender` бачить лише рендери, що дійшли до коміту.
Покинуті спроби в нього не потрапляють.

**«200 мс означає миттєво».** Миттєвим дослідження вважають приблизно 100 мс. Поріг 200 мс обрано, бо суворішого
більшість сайтів на телефонах не досягає.

## Як це проявиться далі в React

- **День «`useDeferredValue`».** Той самий список ви зробите іншим хуком і отримаєте третє число INP. Умова про `memo`
  там стоїть прямо в картці дня.
- **День «Віртуалізація довгих списків».** Там ви зменшите саму роботу, а INP набору у фільтр міряєте так, як
  сьогодні.
- **День «`<Suspense>` і межі помилок».** Перехід не дає React сховати вже показаний вміст за запасним, поки нова
  частина завантажується. Про це розділ `Preventing unwanted loading indicators` сторінки `useTransition`.
- **Фаза 3, день «Маршрути».** Довідник радить позначати навігацію між сторінками переходом і каже, що від
  маршрутизаторів із підтримкою Suspense цього очікують.
- **Фаза 3, день «Форми в React 19».** Там функція в переході стане асинхронною, а `isPending` показуватиме, що форма
  ще надсилається.
- **Фаза 5, день «Метрики».** Функцію `onINP` ви поставите на викочену версію й порівняєте сьогоднішнє лабораторне
  число з числами справжніх відвідувачів.

## Перевірте себе

**1. Обробник `onChange` містить один виклик `set`. Чому тоді літера з'являється в полі через пів секунди?**

<details><summary>Відповідь</summary>

Після натискання клавіші React рендерить у мікрозадачі, одразу після обробника. Рендер трьохсот бейджів займає близько
чверті секунди, і весь цей час головний потік не може намалювати кадр. Якщо в черзі вже стоїть наступна клавіша,
браузер може опрацювати й її до малювання. У нашому прогоні перша літера чекала кадру 592 мс.

</details>

**2. Третя літера має затримку вводу 296 мс, роботу обробників 322 мс і затримку до кадру 591 мс. Що означає кожне
число і яка частина зникне першою, якщо людина друкуватиме повільно?**

<details><summary>Відповідь</summary>

296 мс літера чекала, поки потік дорендерить аркуші для двох попередніх літер. 322 мс тривав її власний рендер. 591 мс
минуло до кадру, бо браузер перед малюванням опрацював ще дві клавіші з черги. За повільного набору зникнуть перша й
третя частини, а залишиться рендер: у нашому замірі з літерою раз на секунду INP був 352 мс.

</details>

**3. Ви викликали `onINP(console.log)`, набрали слово, а консоль порожня. Назвіть два способи побачити число.**

<details><summary>Відповідь</summary>

Перший спосіб: сховати сторінку, наприклад перейти на іншу вкладку, бо без параметрів бібліотека повідомляє INP, коли
стан видимості стає `hidden`. Другий спосіб: передати другим аргументом `{ reportAllChanges: true }`, і тоді колбек
викликатиметься щоразу, коли значення зростає.

</details>

**4. За одне слово лічильники показали п'ять викликів компонента аркуша, 902 виклики бейджа й один рендер аркуша, що
дійшов до коміту. Що з цього випливає?**

<details><summary>Відповідь</summary>

React п'ять разів починав рендер аркуша й чотири рази покинув його, коли надходила нова клавіша. Останній рендер дав
300 викликів бейджа, а 602 виклики припали на покинуті спроби. У документ потрапив лише результат останнього рендеру.

</details>

**5. Після переходу INP зменшився з 1112 до 24 мс. Чи став рендер аркуша швидшим? Яким числом це перевірити?**

<details><summary>Відповідь</summary>

Ні. `actualDuration` рендеру аркуша був 256 мс до і 260 мс після, а після однієї літери аркуш з'явився через 392 мс
замість 360. Перехід переніс рендер за кадр і дозволив його переривати, тому зменшився час до кадру, а не час роботи.

</details>

**6. Колега загорнув `setQuery` у `startTransition`, а поле не стало чуйнішим. Що перевірити насамперед?**

<details><summary>Відповідь</summary>

Чи вміє важкий компонент пропускати рендер. Термінове оновлення поля рендерить батьківський компонент і всіх його
дітей. Якщо список не загорнуто в `memo`, він рендериться зі старим значенням на кожну клавішу. У нашому замірі аркуш
без `memo` дав INP 856 мс замість 24.

</details>

**7. Чому перехід не допоміг компоненту, який сам у циклі рахує триста візерунків?**

<details><summary>Відповідь</summary>

React може зупинитися лише між компонентами, а всередині одного виклику функції перерв немає. Такий компонент займає
потік на весь час обчислення, і клавіша чекає його кінця. У нашому замірі найдовша затримка вводу була 152 мс, а INP
208 мс.

</details>

**8. У полі з `value={text}` обробник викликає `startTransition(() => setText(e.target.value))`. Що побачить людина на
важкому екрані за швидкого й за повільного набору?**

<details><summary>Відповідь</summary>

За швидкого набору літери губляться: у нашому прогоні з п'яти лишилася остання. За повільного набору всі літери є, але
кожна з'являється лише після рендеру переходу, у нас приблизно через 300 мс. Причина в тому, що кероване поле після
кожної клавіші повертається до значення зі стану, а стан ще старий.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| INP | час від дії людини до наступного кадру; для сторінки беруть найгіршу взаємодію |
| взаємодія | група подій одного жесту, наприклад `keydown`, `keypress` і `keyup` однієї клавіші |
| затримка вводу | час від дії до початку першого обробника |
| робота обробників | час виконання всіх обробників взаємодії разом із рендером, який вони запустили |
| затримка до кадру | час від кінця обробників до показу кадру |
| Event Timing API | механізм браузера, який записує час подій; записи мають тип `PerformanceEventTiming` |
| `interactionId` | ідентифікатор, спільний для всіх подій однієї взаємодії |
| `onINP` | функція бібліотеки `web-vitals`, яка рахує INP і передає його у ваш колбек |
| `reportAllChanges` | параметр `onINP`: повідомляти значення щоразу, коли воно змінилося |
| термінове оновлення | оновлення стану, яке React рендерить одразу й без перерв |
| перехід, Transition | оновлення стану, позначене як нетермінове; його рендер можна перервати |
| `startTransition` | функція, яка одразу викликає вашу функцію й позначає її оновлення переходами |
| `isPending` | значення з `useTransition`: перехід почато, а його результат ще не показано |
| планувальник | пакет `scheduler`, який виконує роботу React окремими задачами |
