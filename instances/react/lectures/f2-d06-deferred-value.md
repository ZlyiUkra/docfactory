# Лекція. Фаза 2, день 6. `useDeferredValue`

Учора поле перестало гальмувати, коли ви перенесли оновлення списку в перехід. Для цього знадобилася функція `set`
того стану, від якого залежить список. Часто такої функції у вас немає: значення приходить у ваш компонент пропсом
від батька або повертається з чужого хука. Сьогодні ви побачите хук `useDeferredValue`, який дає той самий результат
без доступу до `set`, і поміряєте третє число INP. Читання займе близько 50 хвилин.

Числа в лекції отримано тим самим способом, що й учора: React 19.3.1, Vite 8.3.6, бібліотека `web-vitals` 6.2.3,
браузер `chrome-headless-shell` версії 157, тобто Chromium без вікна, на одному ноутбуці під WSL. Літери набирали
справжні події клавіатури, які скрипт надсилав командою протоколу інструментів розробника `Input.dispatchKeyEvent`, а
процесор уповільнювала команда `Emulation.setCPUThrottlingRate` у чотири рази. Якщо біля числа не сказано іншого, його
отримано на збірці для профілювання (`vite build --mode profile`), і це медіана кількох прогонів, а скільки їх було,
сказано біля кожної таблиці. Вікна Chrome DevTools ми не відкривали. Числа цієї лекції не порівнюйте напряму з
учорашніми: об'єкт інший, і того вечора той самий цикл на комп'ютері рахував майже вдвічі повільніше, ніж напередодні.

Практика дня переробляє ваш учорашній список. Щоб не показувати розв'язку, лекція бере інший об'єкт: аркуш зразків
шрифту.

**Після лекції ви зможете пояснити:**

- чому перехід неможливий, коли значення приходить пропсом, і що тоді робить `useDeferredValue`;
- з якими значеннями React викликає компонент під час одного оновлення і чому таких викликів два;
- чому фоновий рендер переривається так само, як перехід, і як це побачити лічильником;
- навіщо повільній частині `memo` і що стається без нього;
- як показати напівпрозорістю, що дані застаріли;
- чим відкладене значення відрізняється від debounce і throttle;
- що дає параметр `initialValue` з React 19;
- коли брати перехід, а коли відкладене значення.

## Значення, яке ви не змінюєте

Видавництво робить сторінку вибору шрифту. Угорі є поле, куди людина вводить фразу. Нижче стоїть аркуш із трьохсот
зразків: кожен показує назву гарнітури, введену фразу й метрику. **Гарнітурою** називають шрифт разом з усіма його
накресленнями, а метрикою тут буде число, обчислене з фрази та назви гарнітури. Саме метрика робить зразок дорогим.

Аркуш зробила інша команда. Поле й стан фрази живуть у компоненті редактора, а панель зразків отримує фразу пропсом.
Ось дані й аркуш, разом із рядками заміру, які рахують виклики компонентів:

```tsx
// data.ts
export const FONTS: string[] = Array.from({ length: 300 }, (_, i) => `Гарнітура ${i + 1}`)

// Метрика зразка: число, обчислене з тексту сталою кількістю кроків.
export function metric(text: string): string {
  let h = 7
  for (let step = 0; step < 16000; step++) {
    h = (h * 31 + text.charCodeAt(step % text.length) + step) % 1000003
  }
  return h.toString(16).padStart(5, '0')
}
```

```tsx
// Sheet.tsx
function Specimen({ phrase, font }: { phrase: string; font: string }) {
  counters.specimenCalls++ // виконується щоразу, коли React викликає компонент
  return (
    <li className="specimen">
      <span>{font}</span> <q>{phrase}</q> <code>{metric(phrase + font)}</code>
    </li>
  )
}

export function PlainSpecimenSheet({ phrase }: { phrase: string }) {
  counters.sheetCalls++
  useEffect(() => {
    // ефект без масиву залежностей виконується після кожного коміту, у якому React рендерив аркуш
    counters.sheetCommits.push({ phrase, at: performance.now() })
  })
  return (
    <ul id="sheet" data-phrase={phrase}>
      {FONTS.map((font) => (
        <Specimen key={font} phrase={phrase} font={font} />
      ))}
    </ul>
  )
}

export const SpecimenSheet = memo(PlainSpecimenSheet)
```

Тут `counters` є звичайним об'єктом поза React, у який сторінка досліду складає заміри. Рядки, що змінюють його під
час рендеру, порушують чистоту компонента, і лінтер шаблону позначає їх правилом `react-hooks/immutability`, як
показала лекція «`useTransition` і перший замір INP». У досліді ми порушили його свідомо, бо хотіли порахувати саме
виклики. Метрика робить сталу кількість кроків, тому уповільнення процесора розтягує її в чотири рази. Чому
повільність для досліду пишуть саме так, пояснила лекція «Профайлер».

Редактор тримає стан фрази й передає його в панель. Варіант панелі обирає параметр адреси сторінки:

```tsx
// Editor.tsx
export function PhraseEditor({ variant, initial }: { variant: Variant; initial: string }) {
  const [phrase, setPhrase] = useState(initial)
  return (
    <>
      <label>
        Фраза <input id="phrase" value={phrase} onChange={(e) => setPhrase(e.target.value)} />
      </label>
      {variant === 'urgent' && <UrgentPanel phrase={phrase} />}
      {variant === 'deferred' && <DeferredPanel phrase={phrase} memoized />}
      {variant === 'nomemo' && <DeferredPanel phrase={phrase} memoized={false} />}
      {variant === 'debounce' && <DebouncedPanel phrase={phrase} />}
      {variant === 'initial' && <InitialPanel phrase={phrase} />}
    </>
  )
}

// Panels.tsx: перший варіант панелі просто передає фразу аркушу
export function UrgentPanel({ phrase }: { phrase: string }) {
  return <SpecimenSheet phrase={phrase} />
}
```

Решту варіантів панелі лекція покаже там, де вперше бере з них число.

Тепер уявіть, що ви пишете панель. Учорашнє рішення вам недоступне. Щоб загорнути оновлення в перехід, потрібно
викликати `setPhrase` усередині `startTransition`, а `setPhrase` живе в редакторі. Ваш компонент бачить лише готове
значення `phrase`. Довідник каже про це в застереженнях сторінки `useTransition`: оновлення можна загорнути в перехід,
лише якщо у вас є функція `set` цього стану, а для значення з пропса чи власного хука він радить `useDeferredValue`.

### Як ми міряли

Скрипт заміру той самий, що вчора. Функцію набору показано в розділі «Як ми набирали слово» вчорашньої лекції, а
спостерігача записів Event Timing і поле `inp` у розділах «Записи браузера» та «Одне число на сторінку». Ми набирали
слово «атлас» з літерою кожні 150 мс. Поле `inp` дорівнює найдовшій взаємодії прогону, і саме з нього взято кожне
число INP у цій лекції. Решту полів скрипт рахує так. Віднімання прибирає те, що набігло під час першого показу
аркуша: один виклик аркуша, триста викликів зразка й один коміт:

```js
rows.push({
  inp: ints.length ? Math.max(...ints.map((x) => x.duration)) : 0,
  maxDelay: ints.length ? Math.max(...ints.map((x) => x.inputDelay)) : 0, // найдовша затримка вводу
  sheetCalls: b.c.sheetCalls - 1,
  specimenCalls: b.c.specimenCalls - 300,
  sheetCommits: b.c.sheetCommits.length - 1,
  domChanges: b.sheetLog.map((x) => x.phrase).join(','), // які фрази показував аркуш у документі
  toSheet: +(last.frame - b.typingStart).toFixed(0), // від початку набору до кадру з останньою фразою
  renderMax: +Math.max(0, ...b.c.renderMs.slice(1).map((x) => x.actual)).toFixed(0),
})
```

Поле `renderMax` бере найдовший `actualDuration` за прогін з функції `onRender` компонента `<Profiler>`, яким огорнуто
весь екран. Поле `domChanges` заповнює спостерігач `MutationObserver`, який записує кожну зміну атрибута
`data-phrase` в аркуші. Медіану й межі кожного поля скрипт друкує тим самим рядком, що вчора.

Сім прогонів панелі без відкладання надрукували:

```text
inp             медіана 1344 | від 1080 до 1728
maxDelay        медіана 729.9 | від 492.3 до 1202.7
renderMax       медіана 283 | від 229 до 357
specimenCalls   медіана 1500 | від 1500 до 1500
sheetCalls      медіана 5 | від 5 до 5
sheetCommits    медіана 5 | від 5 до 5
```

Отже, число «до» для цієї сторінки: INP 1344 мс, оцінка «погано». Рендер аркуша триває близько 283 мс, і кожна
літера чекає не лише власного рендеру, а й рендерів попередніх літер. Чому так стається, вчора пояснив розділ «Три
частини кожної літери».

## Що робить `useDeferredValue`

Хук приймає значення й повертає його відкладену копію:

```ts
const deferredPhrase = useDeferredValue(phrase)
```

**Відкладене значення** спершу лишається старим, а потім наздоганяє справжнє. Довідник описує це словами «lags
behind», тобто «відстає». Ось панель, яка ним користується:

```tsx
export function DeferredPanel({ phrase, memoized }: { phrase: string; memoized: boolean }) {
  const deferredPhrase = useDeferredValue(phrase)
  const isStale = phrase !== deferredPhrase
  counters.panelRenders.push(`${phrase}/${deferredPhrase}`) // кожен виклик панелі, зокрема покинутий
  useEffect(() => {
    counters.panelCommits.push(`phrase="${phrase}" deferred="${deferredPhrase}" opacity=${isStale ? 0.5 : 1}`)
  })
  return (
    <section style={{ opacity: isStale ? 0.5 : 1 }}>
      {memoized ? <SpecimenSheet phrase={deferredPhrase} /> : <PlainSpecimenSheet phrase={deferredPhrase} />}
    </section>
  )
}
```

Розберімо рядки, які стосуються хука.

- `useDeferredValue(phrase)` викликано на верхньому рівні компонента, як будь-який хук.
- `isStale` порівнює справжнє значення з відкладеним. Поки вони різні, аркуш показує стару фразу.
- Аркуш отримує `deferredPhrase`, а не `phrase`. Поле редактора про хук нічого не знає й далі отримує `phrase`.
- Пропс `memoized` обирає аркуш у `memo` або без нього. Навіщо це, покаже окремий розділ.

### Два виклики на одну літеру

Довідник описує механізм двома кроками у врізці `How does deferring a value work under the hood?`. Спершу React
рендерить з новим значенням `phrase`, але зі старим `deferredPhrase`. Потім у фоні React пробує ще один рендер, у
якому новими є обидва значення.

Масив `panelRenders` показує це прямо. Скрипт склеює обидва масиви останнього прогону в один рядок і друкує його
після медіан:

```js
lastPanel = b.c.panelRenders.join(' ') + '  ||  ' + b.c.panelCommits.join(' | ')
// ...після циклу прогонів
console.log('рендери панелі останнього прогону:', lastPanel)
```

Ось що він надрукував для останнього з семи прогонів панелі з `memo`. Тут слова на початку рядка прибрано, а кожен
коміт подано з нового рядка:

```text
/ а/ а/а ат/ ат/ат атл/ атл/атл атла/ атла/атла атлас/ атлас/атлас
phrase="" deferred="" opacity=1
phrase="а" deferred="" opacity=0.5
phrase="ат" deferred="" opacity=0.5
phrase="атл" deferred="" opacity=0.5
phrase="атла" deferred="" opacity=0.5
phrase="атлас" deferred="" opacity=0.5
phrase="атлас" deferred="атлас" opacity=1
```

Перший запис `/` належить першому показу сторінки: обидва значення порожні. Далі кожна літера дає два виклики панелі.

1. **Терміновий рендер.** Запис `а/` означає, що React викликав панель із `phrase` рівним «а» і `deferredPhrase`
   рівним порожньому рядку. Хук повернув старе значення. Цей рендер дійшов до коміту, і його рядок у списку комітів,
   `phrase="а" deferred="" opacity=0.5`, каже, що поле вже показує «а», а аркуш напівпрозорий.
2. **Фоновий рендер.** Запис `а/а` означає, що React викликав панель удруге, і тепер хук повернув нове значення.
   Аркуш отримав «а» і почав рендерити триста зразків.

Порівняйте кількість викликів панелі з кількістю комітів. Викликів одинадцять, а комітів сім. Фонові рендери для «а»,
«ат», «атл» і «атла» до коміту не дійшли, бо кожен перервала наступна клавіша. Відкладене значення трималося
порожнім, поки людина друкувала, а наздогнало справжнє один раз, після останньої літери.

### Що робить React усередині

Як хук вирішує, яке значення повернути, видно у вихідному коді пакета `react-dom` 19.3.1. Ми читали його версію для
розробки, і на мові лекції він робить таке.

1. Якщо нове значення дорівнює старому за `Object.is`, хук повертає його й нічого не планує.
2. Якщо поточний рендер належить терміновому оновленню, тобто оновленню після клавіші, хук повертає старе значення.
   Водночас він позначає компонент як такий, що має ще одну роботу з окремим пріоритетом. Цей пріоритет React бере з
   групи пріоритетів переходів.
3. Якщо поточний рендер уже нетерміновий, хук повертає нове значення й запам'ятовує його.

Правило для нетермінового рендеру пояснює фоновий рендер: він має пріоритет переходу, тому в ньому хук повертає нове
значення. Правило для термінового рендеру пояснює, чому фоновий рендер поводиться як учорашній перехід. React виконує
його частинами, між частинами віддає потік браузеру, а нова клавіша його перериває. Довідник каже те саме в
застереженнях: фоновий рендер можна перервати, і якщо значення знову змінилося, React починає його спочатку. Правило
для нетермінового рендеру пояснює й інше застереження довідника: якщо оновлення вже є переходом, хук повертає нове
значення одразу й нічого не відкладає.

## Фоновий рендер переривається

Тепер подивімося на ті самі сім прогонів через лічильники. Поля з таблиці взято з рядків медіан, як для `inp`. Для
панелі з відкладеним значенням ці рядки такі:

```text
specimenCalls   медіана 944 | від 680 до 1097
sheetCalls      медіана 5 | від 5 до 5
sheetCommits    медіана 1 | від 1 до 1
```

Поле `domChanges` у кожному прогоні без відкладання містило `а,ат,атл,атла,атлас`, а в кожному прогоні з відкладеним
значенням лише `атлас`. Зведімо це в таблицю.

| Що рахуємо за одне слово | Без відкладання | З відкладеним значенням |
|--------------------------|-----------------|-------------------------|
| викликів компонента аркуша | 5 | 5 |
| викликів компонента зразка | 1500 | 944, у різних прогонах від 680 до 1097 |
| рендерів аркуша, що дійшли до коміту | 5 | 1 |
| що показував аркуш | «а», «ат», «атл», «атла», «атлас» | лише «атлас» |

Стовпець справа є доказом переривання. React п'ять разів починав рендерити аркуш і лише раз довів його до коміту. З
944 викликів зразка 300 належать останньому рендеру, а решта належать чотирьом покинутим спробам.

Компонент аркуша викликано п'ять разів, а не десять, хоча панель React викликав одинадцять разів. У терміновому
рендері аркуш отримує стару фразу, і `memo` бачить ті самі пропси, тому React пропускає аркуш. Аркуш викликають лише
фонові рендери.

Ось як це виглядало в часі в одному з прогонів. Цей рядок друкує для кожного прогону той самий код, що й учора, його
показано в розділі «Простежимо одну літеру» вчорашньої лекції: для кожної взаємодії три частини та їхня сума, потім
усі коміти з `onRender` і моменти клавіш. Запис `4@20` означає, що рендер
тривав 4 мс, а коміт стався на 20-й мілісекунді від початку набору. Рядок довгий, тому тут його розірвано на два:

```text
4 0.6+18.8+20.6=40 | 0.3+5.2+10.5=16 | 3.4+5.5+7.1=16 | 3.2+5.6+7.2=16
  || onRender: 4@20 0@157 1@310 0@460 0@610 228@874 || клавіші: 3 152 302 602
```

Усі взаємодії тривали від 16 до 40 мс. Скрипт записує лише ті, що тривали щонайменше 16 мс, тому їх може бути менше за
п'ять. Маленькі коміти одразу за клавішами є терміновими рендерами: вони оновлюють поле й напівпрозорість. Один
великий коміт настав приблизно через 272 мс після останньої клавіші: це фоновий рендер для «атлас».

Те саме вчора показав перехід. Різниця не в механізмі, а в тому, де ви про нього просите: перехід позначає оновлення
стану, а відкладене значення позначає місце, де значення читають.

## Третє число INP

Ось усі числа поруч. INP береться з поля `inp`, найдовша затримка вводу з поля `maxDelay`, тривалість рендеру з поля
`renderMax`, а час до аркуша з поля `toSheet`. Кожне число є медіаною семи прогонів. Останню літеру скрипт надсилає на
600-й мілісекунді від початку набору, тому все, що в рядку `toSheet` понад 600 мс, людина чекала вже після набору.

| Що міряємо | Без відкладання | З відкладеним значенням |
|------------|-----------------|-------------------------|
| INP, слово з літерою кожні 150 мс | 1344 мс, розкид 1080–1728 | 40 мс, розкид 32–56 |
| найдовша затримка вводу | 729.9 мс | 5 мс |
| `actualDuration` найдовшого рендеру | 283 мс | 228 мс |
| від початку набору до кадру з аркушем «атлас» | 1697 мс | 957 мс |

На продакшн-збірці п'ять прогонів дали медіану INP 1512 мс без відкладання і 72 мс з відкладеним
значенням. Код той самий, змінилася лише адреса збірки.

Читайте таблицю так само, як учорашню.

- **INP впав з оцінки «погано» до оцінки «добре».** Найдовша затримка вводу з відкладеним значенням дорівнює кільком
  мілісекундам: клавіша чекала лише кінця поточної частини фонового рендеру.
- **Рендер аркуша не став швидшим по суті.** Медіани `actualDuration` різняться, але розкиди прогонів, від 229 до 357
  мс і від 216 до 320 мс, перекриваються. Довідник каже прямо: хук не пришвидшує рендер списку, він лише дозволяє
  поставити цей рендер нижче за клавіші.
- **Слово з'явилося на аркуші раніше.** React не доводив до кінця проміжні аркуші для «а», «ат», «атл» і «атла», яких
  людина й так не встигла б прочитати.

Запам'ятайте й межу інструмента з лекції «Профайлер»: функція `onRender` бачить лише рендери, що дійшли до коміту.
Покинуті фонові рендери в `actualDuration` не потрапляють.

## Без `memo` користі немає

Тепер та сама панель з аркушем без `memo`: редактор передає `memoized={false}`, і панель малює `PlainSpecimenSheet`.
Сім прогонів надрукували:

```text
inp             медіана 1136 | від 880 до 1256
specimenCalls   медіана 1800 | від 1800 до 1800
sheetCalls      медіана 6 | від 6 до 6
sheetCommits    медіана 6 | від 6 до 6
```

| Варіант | INP, мс | Викликів аркуша | Викликів зразка | Рендерів аркуша, що дійшли до коміту |
|---------|---------|-----------------|-----------------|--------------------------------------|
| без відкладання, аркуш у `memo` | 1344 | 5 | 1500 | 5 |
| відкладене значення, аркуш у `memo` | 40 | 5 | 944 | 1 |
| відкладене значення, аркуш без `memo` | 1136 | 6 | 1800 | 6 |

Без `memo` відкладене значення майже нічого не дало: 1136 мс проти 1344 мс, і розкиди прогонів перекриваються.
Подивіться, що стається з однією літерою.

1. Клавіша оновлює стан редактора. Терміновий рендер викликає редактор, а за замовчуванням React викликає й усіх його
   дітей, тобто панель.
2. Панель отримує від хука стару фразу й передає її аркушу. Аркуш без `memo` не порівнює пропсів, тому React рендерить
   усі триста зразків зі старою фразою. Цей рендер терміновий і перервати його не можна.
3. Фоновий рендер мав би відрендерити аркуш з новою фразою, але під час швидкого набору він навіть не починався.
   Терміновий рендер тривав понад 200 мс, за цей час надходила наступна клавіша, а термінове оновлення React
   виконує першим.

Рядок рендерів панелі з останнього прогону це показує: `/ а/ ат/ атл/ атла/ атлас/ атлас/атлас`. Записів із новим
відкладеним значенням немає аж до кінця набору. Отже, за слово React п'ять разів відрендерив аркуш з тією самою
порожньою фразою, яку вже показував, і лише раз з новою. Звідси 1800 викликів зразка: 5 разів по 300 у термінових
рендерах і ще 300 у фоновому. Усі шість рендерів аркуша дійшли до коміту, хоча п'ять із них нічого не змінили в
документі.

Довідник пояснює те саме в пересторозі під розділом `Deferring re-rendering for a part of the UI`. Хук не забороняє
React рендерити аркуш. Він лише дає аркушу в терміновому рендері те саме значення, що й минулого разу. Скористатися
цим може тільки компонент, який уміє пропустити рендер з тими самими пропсами, тобто компонент у `memo`.

Картка дня додає, що з React Compiler пропуск відбувається сам. Довідник `memo` каже, що компілятор застосовує до
кожного компонента рівноцінне `memo`, а лекція «Мемоізація і React Compiler — один замір» показала, як він це робить.
Цього досліду з компілятором ми не запускали, тому перевіряйте у своїй гілці лічильником викликів, а не здогадом.

Є ще одна обставина, яку варто знати для практики. Цю помилку видно не завжди. Перший варіант нашої сторінки для
порожньої фрази показував короткий напис, а не триста зразків. Тіло списку в аркуші було таким:

```tsx
{phrase === ''
  ? <li>Введіть фразу, щоб побачити зразки.</li>
  : FONTS.map((font) => <Specimen key={font} phrase={phrase} font={font} />)}
```

Тоді сім прогонів панелі без `memo` дали медіану INP 24 мс, розкид від 24 до 32 мс, і 982 виклики зразка за слово.
Причина в тому, що в терміновому рендері аркуш рендерив стару порожню фразу, а вона нічого не коштувала. Помилка
вилізла, щойно стара фраза стала дорогою. У списку з фільтром порожній фільтр показує весь список, тобто найдорожчий
стан, тому там ви її побачите одразу.

Ми перевірили це на списку з картки дня: чотириста рядків, у кожному штучна повільність, слово «кава», по три прогони
на продакшн-збірці. Коду цього списку тут немає, бо він є вашою практикою, а міряв його той самий скрипт.

| Варіант списку з фільтром | INP, мс |
|---------------------------|---------|
| без відкладання | 1808 |
| відкладене значення, список у `memo`, напівпрозорість | 48 |
| відкладене значення, список без `memo` | 7888 |

## Напівпрозорість: дані застаріли

Хук не дає прапорця на зразок `isPending`. Ознакою того, що аркуш старий, є саме різниця двох значень, і довідник
показує це в розділі `Indicating that the content is stale`:

```tsx
const isStale = phrase !== deferredPhrase
return <section style={{ opacity: isStale ? 0.5 : 1 }}>{/* аркуш */}</section>
```

Рядок комітів панелі вище показує, як поводиться ця умова. Від першої літери до кінця фонового рендеру кожен коміт
мав `opacity=0.5`, і лише останній мав `opacity=1`. Отже, людина бачить напівпрозорий старий аркуш, поки друкує, і
повний новий аркуш, щойно React його дорендерив.

Довідник додає до прикладу властивість CSS `transition`, яка вмикає затемнення з затримкою 0.2 с. Тоді швидкий
фоновий рендер узагалі не дає помітного мерехтіння, бо закінчується раніше, ніж почнеться затемнення. Цього прикладу
ми не міряли.

Зверніть увагу, що напівпрозорість обгортки не змушує React рендерити аркуш. Стиль стоїть на елементі `section`
панелі, а аркуш у `memo` у терміновому рендері пропущено, тому зміна прозорості коштує один дешевий рендер панелі.

## Коли перехід, а коли відкладене значення

Обидва інструменти роблять те саме: просять React відрендерити повільну частину з нетерміновим пріоритетом, щоб
клавіша не чекала. Різниця в тому, де стоїть ваш код.

| Питання | `useTransition` | `useDeferredValue` |
|---------|-----------------|--------------------|
| Що ви позначаєте | оновлення стану | значення, яке читаєте |
| Що вам потрібно | функція `set` того стану | лише саме значення |
| Звідки зазвичай значення | ваш власний стан | пропс, чужий хук, бібліотека |
| Як дізнатися, що результат ще старий | `isPending` | `value !== deferredValue` |
| Чи треба `memo` на повільній частині | так, якщо терміновий рендер її зачіпає | так, завжди |
| Скільки станів для поля | два: стан поля й стан списку | один, бо відкладається вже прочитане значення |

Останній рядок варто помітити. Учора, щоб не зламати поле, ви тримали два стани. З відкладеним значенням стан один:
поле отримує `phrase`, а аркуш отримує відкладену копію того самого рядка. Тому розділ про типові проблеми сторінки
`useTransition` називає `useDeferredValue` другим виходом із пастки зі станом поля в переході.

Правило з картки дня звучить так: якщо ви володієте сеттером, беріть перехід; якщо значення приходить ззовні, беріть
відкладене значення. Якщо ви володієте сеттером, годиться й відкладене значення, і тоді вибір залежить від того, де
зручніше. Перехід позначає одне конкретне оновлення. Відкладене значення діє на будь-яку зміну цього значення, хоч би
звідки вона прийшла.

## Не debounce і не throttle

Перш ніж React мав такі хуки, повільний список після поля розвантажували двома прийомами. **Debounce** чекає, поки
людина перестане друкувати, і лише тоді оновлює список. **Throttle** оновлює список не частіше ніж раз на певний
проміжок. Довідник присвятив порівнянню врізку `How is deferring a value different from debouncing and throttling?` і
називає дві відмінності. Перша: хук не має сталої затримки, тому на швидкому пристрої фоновий рендер стається майже
одразу, а на повільному список відстає пропорційно. Друга: фоновий рендер можна перервати, а рендер після debounce чи
throttle блокує клавішу так само, лише в інший момент.

Обидві відмінності ми перевірили. Для цього зробили панель із debounce на 300 мс:

```tsx
export function DebouncedPanel({ phrase }: { phrase: string }) {
  const [shown, setShown] = useState(phrase)
  useEffect(() => {
    const id = setTimeout(() => setShown(phrase), 300) // показати фразу через 300 мс тиші
    return () => clearTimeout(id) // нова літера скасовує попередній таймер
  }, [phrase])
  return (
    <section style={{ opacity: phrase !== shown ? 0.5 : 1 }}>
      <SpecimenSheet phrase={shown} />
    </section>
  )
}
```

Аркуш тут у `memo`, як і в панелі з відкладеним значенням. Ми запускали обидві панелі в трьох режимах: з уповільненням
і літерою кожні 150 мс, з уповільненням і літерою кожні 400 мс, а також без уповільнення з літерою кожні 150 мс.
Панель без відкладання в тих самих режимах подано для порівняння. Кожне число є медіаною полів `inp`, `maxDelay` і
`toSheet`. Серії першого режиму для панелі без відкладання й панелі з відкладеним значенням є тими самими сімома
прогонами, що й вище. Решта серій мають по п'ять прогонів, а панель без відкладання з літерою кожні 400 мс і без

  чекала його кінця: найдовша затримка вводу 258.9 мс. З відкладеним значенням фоновий рендер тепер часто

  кілька мілісекунд, але коміт, тобто запис готового аркуша в документ, і подальше малювання браузер виконує одним
  шматком. Яку саме частину чекала клавіша, ми не розбирали. INP тут гірший, ніж за швидкого набору, проте вдвічі
  кращий, ніж з debounce.

  на 710-й мілісекунді, а без хука на 697-й. Debounce і тут чекав свої 300 мс, і аркуш з'явився на
  980-й мілісекунді, бо затримку задано числом, а не швидкістю пристрою.

Врізка довідника закінчується тим, коли debounce і throttle лишаються корисними: коли робота відбувається не під час
рендеру. Приклад довідника стосується мережі. Відкладене значення не зменшує кількості запитів, і застереження
сторінки кажуть про це окремо. Якщо на кожну літеру йде запит до сервера, debounce зменшить кількість запитів, а
відкладене значення ні. Обидва прийоми можна поєднувати.

## `initialValue`: перший показ без очікування

Досі хук відкладав лише оновлення. На першому рендері він нічого не відкладає, бо попередньої версії значення ще
немає. Тому сторінка, яка відкривається одразу з фразою, наприклад з адреси, чекає повного аркуша, перш ніж щось
показати.

React 19 додав хуку другий параметр, `initialValue`. Довідник описує його так: це значення для першого рендеру
компонента. Якщо його передати, перший рендер отримає `initialValue`, а рендер зі справжнім значенням React запланує
у фоні.

```tsx
export function InitialPanel({ phrase }: { phrase: string }) {
  const deferredPhrase = useDeferredValue(phrase, '') // перший рендер отримає порожній рядок
  counters.panelRenders.push(`${phrase}/${deferredPhrase}`)
  // Поки відкладена фраза порожня, панель показує лише напис, а не триста зразків.
  if (deferredPhrase === '') return <p>Готую зразки…</p>
  return <SpecimenSheet phrase={deferredPhrase} />
}
```

Сторінку з цією панеллю ми відкривали з фразою «атлас» в адресі. Початкове значення стану редактор отримує з
параметра адреси `phrase`:

```tsx
const params = new URLSearchParams(window.location.search)
// ...
<PhraseEditor variant={variant as Variant} initial={params.get('phrase') ?? ''} />
```

Після відкриття сторінки скрипт чекав чотири секунди, а потім читав зі сторінки момент першого малювання й лічильники
та друкував один рядок на прогін:

```js
const r = await evaluate(
  page,
  `JSON.stringify({
    fcp: performance.getEntriesByName('first-contentful-paint')[0]?.startTime ?? null,
    renders: __counters.panelRenders,
    commits: __counters.sheetCommits.map((c) => c.phrase + '@' + c.at.toFixed(0)),
    specimens: __counters.specimenCalls,
  })`,
)
const o = JSON.parse(r)
console.log(
  `${variant} | FCP ${o.fcp?.toFixed(0)} мс | рендери панелі: ${o.renders.join(' ')} | ` +
    `коміти аркуша: ${o.commits.join(' ')} | викликів зразка: ${o.specimens}`,
)
```

**FCP** (First Contentful Paint, перше змістовне малювання) є моментом, коли браузер уперше намалював текст чи
зображення сторінки. Запис `first-contentful-paint` браузер створює сам. Те саме ми зробили з панеллю
`DeferredPanel`, яка викликає хук без другого параметра. Усі числа в рядках є мілісекундами від початку
завантаження сторінки. По п'ять прогонів з уповільненням у чотири рази надрукували:

```text
initial | FCP 548 мс | рендери панелі: атлас/ атлас/атлас | коміти аркуша: атлас@1161 | викликів зразка: 300
initial | FCP 320 мс | рендери панелі: атлас/ атлас/атлас | коміти аркуша: атлас@842 | викликів зразка: 300
initial | FCP 368 мс | рендери панелі: атлас/ атлас/атлас | коміти аркуша: атлас@896 | викликів зразка: 300
initial | FCP 332 мс | рендери панелі: атлас/ атлас/атлас | коміти аркуша: атлас@844 | викликів зразка: 300
initial | FCP 300 мс | рендери панелі: атлас/ атлас/атлас | коміти аркуша: атлас@784 | викликів зразка: 300
deferred | FCP 916 мс | рендери панелі: атлас/атлас | коміти аркуша: атлас@924 | викликів зразка: 300
deferred | FCP 716 мс | рендери панелі: атлас/атлас | коміти аркуша: атлас@719 | викликів зразка: 300
deferred | FCP 848 мс | рендери панелі: атлас/атлас | коміти аркуша: атлас@858 | викликів зразка: 300
deferred | FCP 1256 мс | рендери панелі: атлас/атлас | коміти аркуша: атлас@1268 | викликів зразка: 300
deferred | FCP 768 мс | рендери панелі: атлас/атлас | коміти аркуша: атлас@771 | викликів зразка: 300
```

| Панель | FCP, медіана, мс | Рендери панелі | Коли аркуш «атлас» дійшов до коміту, медіана, мс |
|--------|------------------|----------------|--------------------------------------------------|
| з `initialValue` `''` | 332 | `атлас/` і `атлас/атлас` | 844 |
| без `initialValue` | 848 | лише `атлас/атлас` | 858 |

З `initialValue` перший рендер повернув порожній рядок, панель показала напис, і браузер намалював сторінку з полем
більш ніж удвічі раніше. Аркуш з'явився приблизно тоді ж, коли й без параметра, але тепер він рендерився після
першого кадру, у фоні, і поле вже можна було бачити. Без параметра перший рендер одразу рахував триста зразків, і до
його кінця сторінка була порожньою.

Цей параметр корисний, коли початкове значення дороге для рендеру, а дешеву заглушку можна показати одразу. Якщо ж
`initialValue` рендериться так само дорого, як справжнє значення, виграшу немає.

## Ще три застереження

Довідник має кілька застережень, які у вашій практиці не з'являться, але зустрінуться пізніше.

- **Передавайте примітиви.** Примітивом називають рядок, число, логічне значення та інші значення, які не є
  об'єктами. Якщо створити об'єкт просто в тілі компонента й передати його в хук, він буде новим на кожному рендері, і
  `Object.is` ніколи не вважатиме його рівним старому. Тоді кожен рендер компонента планує зайвий фоновий рендер.
- **Ефекти фонового рендеру виконуються лише після його коміту.** Покинутий фоновий рендер ефектів не запускає. Наш
  ефект аркуша спрацював за слово один раз: поле `sheetCommits` дорівнювало 1.
- **`<Suspense>`.** Якщо фоновий рендер чекає даних, React не показує запасного вмісту межі, а лишає на екрані старе
  відкладене значення, поки дані не прийдуть. Межі `<Suspense>` ви вивчатимете в дні «`<Suspense>` і межі помилок».

## Третє число в журналі

Журнал вимірів, який ви завели в темі «Збірка, перший викот і журнал вимірів», після вчорашнього дня має два числа
INP. Сьогодні з'являється третє. Умови запишіть так само повно, як учора, щоб рядки можна було порівняти. Ось рядки
для нашої сторінки зразків з числами продакшн-збірки з розділу «Третє число INP». Наш скрипт брав INP із записів Event
Timing, а ви запишіть той спосіб, яким міряли самі:

```text
| дата | «атлас», літера кожні 150 мс, аркуш оновлюється терміново; продакшн, 4×, Event Timing | — | 1512 мс | — | — |
| дата | Те саме, useDeferredValue у панелі, аркуш у memo, напівпрозорість | — | 72 мс | — | — |
```

Порядок дій той самий, що вчора: зібрати застосунок і відкрити зібрану сторінку, увімкнути уповільнення в чотири
рази, записати передбачення, набрати те саме слово в тому самому темпі кілька разів і взяти медіану. Окремо
перевірте очима дві речі, яких число не бачить: поле показує кожну літеру, а список стає напівпрозорим під час набору
й повертається до повної яскравості після нього. Де в інструментах розробника вмикається уповільнення, описала лекція
«Профайлер», а ми того вікна не відкривали.

## Типові хибні уявлення

**«`useDeferredValue` відкладає значення на якийсь час, як `setTimeout`».** Сталої затримки немає. Фоновий рендер
починається одразу після термінового, і без уповільнення аркуш з'являвся на 710-й мілісекунді від початку набору,
майже тоді ж, що й без хука, а з debounce на 300 мс на 980-й.

**«Досить відкласти значення, і список перестане гальмувати».** Без `memo` на аркуші INP був 1136 мс, а викликів
зразка 1800 проти 1500 без хука. Терміновий рендер має пропускати повільний компонент.

**«Хук пришвидшує рендер».** Кожен рендер аркуша, що дійшов до коміту, так само викликав триста зразків, а медіани
`actualDuration`, 283 мс без хука і 228 мс з ним, лежать у розкидах одна одної. Змінилося лише те, коли рендер
відбувається і чи можна його перервати.

**«React рендерить компонент один раз на літеру».** Компонент з хуком React викликав двічі на кожну літеру: спершу зі
старим відкладеним значенням, потім з новим. Під час набору п'яти літер панель викликано одинадцять разів.

**«Debounce робить те саме, тільки простіше».** З літерою кожні 400 мс debounce дав INP 328 мс проти
128 мс, бо рендер після таймера не можна перервати.

**«Щоб показати, що список старий, треба окремий стан `isLoading`».** Досить порівняти `phrase !== deferredPhrase`.
Окремий стан тільки додасть ще один рендер.

**«`useDeferredValue` зменшує кількість запитів до сервера».** Не зменшує, і довідник каже про це окремим
застереженням. Для запитів потрібен debounce або кеш.

**«`initialValue` пришвидшує весь перший показ».** Він пришвидшує перше малювання лише тоді, коли `initialValue`
рендериться дешевше за справжнє значення. Аркуш з фразою все одно рендериться, тільки вже після першого кадру.

## Як це проявиться далі в React

- **День «Віртуалізація довгих списків».** Там ви зменшите саму роботу: малюватимете лише видимі рядки. INP набору у
  фільтр міряєте так само, як сьогодні, і отримаєте ще одне число в журнал.
- **День «`<Suspense>` і межі помилок».** Ви повернетеся до першого розділу сторінки `useDeferredValue`: відкладене
  значення лишає на екрані старі результати замість запасного вмісту, поки нові завантажуються.
- **Фаза 3, день «Маршрути».** Параметри адреси сторінки приходять із хука маршрутизатора, тобто ззовні. Якщо від
  такого параметра залежить повільний список, відкладене значення стане природним вибором.

## Перевірте себе

**1. Ви пишете компонент графіка, який отримує проп `range` від батька. Графік рендериться 300 мс. Чому ви не можете
скористатися `startTransition`, і що робите замість цього?**

<details><summary>Відповідь</summary>

Щоб загорнути оновлення в перехід, потрібна функція `set` стану `range`, а вона живе в батьківському компоненті. Ваш
компонент бачить лише значення. Тому ви викликаєте `useDeferredValue(range)` і передаєте відкладене значення в
повільну частину, загорнуту в `memo`.

</details>

**2. Під час набору слова з п'яти літер панель записала одинадцять викликів і сім комітів. Звідки два виклики на
літеру і чому комітів менше?**

<details><summary>Відповідь</summary>

На кожну літеру React спершу виконує терміновий рендер, у якому хук повертає старе значення, а потім фоновий, у якому
хук повертає нове. Термінові рендери дійшли до коміту всі п'ять. Фонові рендери для перших чотирьох літер перервала
наступна клавіша, тому до коміту дійшов лише останній. Ще один виклик і один коміт належать першому показу сторінки.

</details>

**3. Колега відклав значення, але поле гальмує так само. Лічильник показує 1800 викликів зразка за слово замість
1500. Що сталося?**

<details><summary>Відповідь</summary>

Повільний компонент не загорнуто в `memo`. У терміновому рендері кожної літери він отримує старе значення, але все
одно рендериться, і цей рендер перервати не можна. Фоновий рендер з новим значенням за швидкого набору встиг лише
раз, після останньої літери. Звідси п'ять рендерів по 300 викликів зі старим значенням і ще 300 з новим.

</details>

**4. Чим відкладене значення відрізняється від debounce на 300 мс? Назвіть дві відмінності й число, яке показує
кожну.**

<details><summary>Відповідь</summary>

Перша відмінність: немає сталої затримки. Без уповільнення аркуш з'являвся на 710-й мілісекунді від початку
набору з відкладеним значенням і на 980-й з debounce. Друга відмінність: фоновий рендер можна перервати. З літерою
кожні 400 мс debounce дав INP 328 мс, бо клавіша чекала кінця рендеру, а відкладене значення 128 мс.

</details>

**5. Як показати, що список застарів, якщо хук не дає `isPending`?**

<details><summary>Відповідь</summary>

Порівняти справжнє значення з відкладеним: `phrase !== deferredPhrase`. Поки вони різні, список показує старі дані, і
обгортку роблять напівпрозорою. Щойно фоновий рендер дійшов до коміту, значення збігаються, і прозорість
повертається до 1.

</details>

**6. Сторінка відкривається з фразою в адресі, і порожній екран висить півсекунди. Як допоможе `initialValue` і коли
він не допоможе?**

<details><summary>Відповідь</summary>

З `initialValue` перший рендер отримує задане значення, наприклад порожній рядок, і може показати дешеву заглушку.
Рендер зі справжнім значенням React планує у фоні, після першого кадру. У нашому замірі перше малювання настало на 332
мс замість 848 мс. Він не допоможе, якщо компонент рендерить `initialValue` так само дорого, як справжнє значення.

</details>

**7. Ви володієте сеттером стану фільтра. Що краще: перехід чи відкладене значення?**

<details><summary>Відповідь</summary>

Годиться будь-який з двох, і обидва потребують `memo` на повільному списку. Перехід позначає конкретне оновлення й дає
`isPending`, але вимагає двох станів, щоб не зламати поле. Відкладене значення обходиться одним станом і реагує на
будь-яку зміну значення. Якщо сеттера у вас немає, вибору немає: лише відкладене значення.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| `useDeferredValue` | хук, який повертає відкладену копію значення |
| відкладене значення | значення, яке в терміновому рендері лишається старим, а у фоновому стає новим |
| терміновий рендер | рендер після дії людини; його не можна перервати |
| фоновий рендер | рендер із новим відкладеним значенням; має пріоритет переходу, тому його можна перервати |
| `initialValue` | другий параметр хука: значення для першого рендеру компонента, з React 19 |
| `isStale` | змінна з прикладу довідника: справжнє значення не дорівнює відкладеному |
| debounce | прийом, який оновлює результат лише після паузи в діях людини |
| throttle | прийом, який оновлює результат не частіше ніж раз на заданий проміжок |
| примітив | рядок, число, логічне значення чи інше значення, яке не є об'єктом |
| FCP | First Contentful Paint, момент, коли браузер уперше намалював текст чи зображення сторінки |

## Що читати далі

- [Розбір читання до цього дня](../reading/f2-d06-reading.md): що саме написано на сторінці `useDeferredValue` і де
  що шукати.
- useDeferredValue: сторінка довідника React з застереженнями, трьома способами вжитку й врізкою про debounce.
- useTransition: учорашня сторінка; її застереження пояснює, коли переходу недостатньо.
- memo: сторінка довідника; розділ про React Compiler пояснює, коли `memo` не потрібен.
- React 19: стаття блогу про випуск; розділ про `initialValue`.
