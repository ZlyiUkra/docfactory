# Лекція. Фаза 2, день 7. Віртуалізація довгих списків

У днях 5 і 6 поле фільтра перестало гальмувати, хоча сам список лишився таким самим повільним: перехід і відкладене
значення лише переставляли його рендер нижче за клавіші. Сьогодні ви зробите інакше: зменшите саму роботу. Список на
десять тисяч рядків покаже в документі лише ті рядки, які людина бачить, і ви поміряєте два числа до і після: скільки
елементів має сторінка і яке INP дає набір у фільтр. Читання займе близько 50 хвилин.

Числа в лекції отримано тим самим способом, що в днях 5 і 6: React 19.3.1, Vite 8.3.6, бібліотека `web-vitals` 6.2.3,
браузер `chrome-headless-shell` версії 157.0.8103.38, тобто Chromium без вікна, на одному ноутбуці під WSL. Бібліотеки
віртуалізації взято найновіші стабільні з реєстру npm на день написання: `@tanstack/react-virtual` 3.14.26, яка тягне
ядро `@tanstack/virtual-core` 3.19.11, і `react-window` 2.5.4. Усі числа INP отримано на продакшн-збірці з
уповільненням процесора в чотири рази. Літери набирали справжні події клавіатури, які скрипт надсилав командою
протоколу інструментів розробника `Input.dispatchKeyEvent`, по одній кожні 150 мс. Якщо біля числа не сказано іншого,
це медіана п'яти прогонів. Вікна Chrome DevTools ми не відкривали, а розширення React Developer Tools не запускали.

Практика дня віртуалізує ваш довідник відділень. Щоб не показувати розв'язку, лекція бере інший об'єкт: журнал подій
складу.

**Після лекції ви зможете пояснити:**

- чому десять тисяч рядків гальмують поле навіть тоді, коли кожен рядок дешевий, і чому `memo` цього не виправляє;
- як порахувати елементи сторінки й де в одній клавіші ховається робота браузера;
- як віртуалізація вирішує, які рядки показати, і навіщо їй порожній елемент повної висоти;
- що робить кожна опція `useVirtualizer` у TanStack Virtual: `count`, `getScrollElement`, `estimateSize`, `overscan`,
  `getItemKey`, `measureElement`;
- чим `react-window` відрізняється від TanStack Virtual і що в нього спільного;
- що коштує віртуалізація: пошук браузера, доступність, обмеження верстки, React Compiler;
- коли віртуалізувати не варто.

## Журнал на десять тисяч записів

Склад записує кожну подію: прийом посилки, видачу, помилку сканера. Начальник зміни відкриває сторінку журналу, де
угорі стоїть поле пошуку, а нижче записи за кілька днів. Записів десять тисяч. Кожен запис є рядком із часом, рівнем
важливості й текстом. Ось дані досліду:

```ts
// data.ts: журнал подій складу, вигадані записи для дослідів лекції
export type Level = 'інфо' | 'увага' | 'помилка'
export type LogEntry = { id: number; time: string; level: Level; text: string }

const TEXTS = [
  'Прийнято посилку',
  'Видано посилку',
  'Посилку переміщено на склад',
  'Сканер не прочитав код',
  'Склад заповнено на 90 %',
  'Оновлено адресу',
  "Кур'єр забрав відправлення",
  'Повернення на склад',
]

export function makeLog(count: number): LogEntry[] {
  return Array.from({ length: count }, (_, i) => ({
    id: i + 1,
    time: clock(8 * 3600 + i * 7), // перший запис о 08:00:00, далі кожні 7 секунд
    level: LEVELS[i % 8],
    text: `${TEXTS[i % 8]}, запис № ${10001 + i}`,
  }))
}

export function filterLog(log: LogEntry[], query: string): LogEntry[] {
  const needle = query.trim().toLowerCase()
  if (needle === '') return log
  return log.filter((entry) => entry.text.toLowerCase().includes(needle))
}
```

Функцію `clock`, яка перетворює секунди на рядок `08:00:07`, і масив `LEVELS` з рівнями тут пропущено. Щоб знати,
скільки записів лишає фільтр після кожної літери, ми запустили на `node` такий скрипт:

```ts
// count.ts
import { filterLog, makeLog } from '../spa/src/lab7/data.ts'

const log = makeLog(10000)
console.log('перший запис:', JSON.stringify(log[0]))
for (const q of ['', 'с', 'ск', 'скл', 'скла', 'склад']) {
  console.log(JSON.stringify(q).padEnd(8), filterLog(log, q).length)
}
```

```text
перший запис: {"id":1,"time":"08:00:00","level":"інфо","text":"Прийнято посилку, запис № 10001"}
""       10000
"с"      10000
"ск"     5000
"скл"    3750
"скла"   3750
"склад"  3750
```

Слово «склад» ми набиратимемо в кожному досліді. Перша літера «с» лишає всі десять тисяч записів, бо кожен текст має
слово «запис». Друга літера прибирає половину, третя ще чверть, а далі число не змінюється.

Сторінка тримає текст поля в стані й передає відфільтровані записи в список. Перший варіант списку малює кожен запис:

```tsx
// lists.tsx
export const ROW_HEIGHT = 28
export const VIEW_HEIGHT = 420

// Один рядок журналу: три елементи, <li>, <time> і <b>, плюс текст.
export function LogRow({ entry, style }: { entry: LogEntry; style?: CSSProperties }) {
  return (
    <li style={style}>
      <time>{entry.time}</time> <b>{entry.level}</b> {entry.text}
    </li>
  )
}

// Варіант «до»: усі відфільтровані записи стоять у документі.
export function PlainLog({ entries }: { entries: LogEntry[] }) {
  return (
    <div style={{ height: VIEW_HEIGHT, overflow: 'auto' }} data-count={entries.length}>
      <ul>
        {entries.map((entry) => (
          <LogRow key={entry.id} entry={entry} />
        ))}
      </ul>
    </div>
  )
}
```

Зовнішній `<div>` має сталу висоту 420 пікселів і `overflow: 'auto'`. Така властивість CSS каже браузеру: якщо вміст
вищий за елемент, не розтягувати елемент, а показати смугу прокручування. Елемент, усередині якого вміст
прокручується, називають **областю прокручування**. Атрибут `data-count` нічого не показує людині: його читає скрипт
заміру, щоб знати, що фільтр уже спрацював. Проп `style` рядка тут не використано, він знадобиться далі.

Рядок дешевий. Він нічого не рахує, як рядок із днів 5 і 6, і повертає три елементи з текстом. Повільність сьогодні
дасть не обчислення в рендері, а сама кількість рядків.

Ось сторінка, яка обирає варіант списку за параметром адреси `?v=`:

```tsx
// page.tsx
const params = new URLSearchParams(location.search)
const variant = params.get('v') ?? 'plain'
const LOG = makeLog(Number(params.get('n') ?? 10000))

function LogScreen() {
  const [query, setQuery] = useState('')
  const entries = useMemo(() => filterLog(LOG, query), [query])
  return (
    <>
      <label>
        Пошук <input value={query} onChange={(e) => setQuery(e.target.value)} />
      </label>
      {variant === 'plain' && <PlainLog entries={entries} />}
      {variant === 'memo' && <MemoLog entries={entries} />}
      {variant === 'virtual' && <VirtualLog entries={entries} overscan={overscan} />}
      {variant === 'window' && <WindowLog entries={entries} />}
    </>
  )
}
```

Інші варіанти списку лекція покаже там, де вперше бере з них число. Параметр `?n=` задає довжину журналу, і він
знадобиться наприкінці, коли журнал буде коротким.

## Перше число: скільки елементів має сторінка

Документ, який браузер побудував із HTML і який змінює JavaScript, є деревом об'єктів. Лекція «DOM і події» називала
кожен об'єкт цього дерева вузлом. Вузлом є кожен тег, тобто **елемент**, але також кожен шматок тексту між тегами й
кожен коментар. Стаття web.dev, яку задано на сьогодні, розрізняє ці два слова саме так. Аудит Lighthouse, тобто
автоматична перевірка сторінки в Chrome, рахує вузли, а простий спосіб із тієї самої статті рахує лише елементи:

```js
document.querySelectorAll('*').length
```

Селектор `'*'` відповідає будь-якому елементу, тому метод `querySelectorAll` повертає всі елементи документа, а
`.length` каже, скільки їх. Текстові вузли сюди не потрапляють. Картка дня просить саме цей рядок, тому далі «вузлами
сторінки» ми називатимемо те, що він повертає, і щоразу пам'ятатимемо, що це елементи.

Скрипт заміру виконує цей вираз у сторінці через протокол інструментів розробника, коли сторінка вже показала список,
і ще до першої літери. Ось шматок функції `runOnce` зі скрипту `measure7.mjs`:

```js
const before = JSON.parse(await evaluate(page, `JSON.stringify({
  all: document.querySelectorAll('*').length,
  rows: document.querySelectorAll('#root li, #root [role=listitem]').length,
  probe: ${JSON.stringify(probe)} ? document.body.textContent.includes(${JSON.stringify(probe)}) : null,
})`))
```

Функція `evaluate` надсилає рядок коду в сторінку командою `Runtime.evaluate` і повертає результат. Поле `rows` рахує
рядки списку, а поле `probe` перевіряє, чи є в тексті документа заданий шматок. Друге поле знадобиться в розділі про
пошук браузера. Один прогін сторінки без віртуалізації надрукував:

```text
HeadlessChrome/157.0.8103.38 | http://localhost:4711/lab7.html?v=plain | уповільнення 4× | слово «склад»
до набору: елементів 30014 | рядків у документі 10000 | текст-проба є: true
після набору: поле "склад" | записів 3750 | елементів 11264 | рядків 3750
```

Десять тисяч рядків по три елементи дають 30 000 елементів. Ще 14 належать решті сторінки: `<html>`, `<head>`,
`<body>`, абзац угорі, корінь React, поле з підписом, область прокручування, сам `<ul>` і кілька службових тегів.
Після слова «склад» лишилося 3750 рядків і 11 264 елементи: 3750 × 3 = 11 250, і ще 14.

Стаття web.dev переказує межі Lighthouse так: попередження з'являється, коли вузлів понад 800, а розмір вважається
надмірним понад 1400. Наша сторінка має в двадцять разів більше, і це ще без текстових вузлів.

## Друге число: INP набору

Показник INP, Interaction to Next Paint, лекція «`useTransition` і перший замір INP» описала докладно: це час від дії
людини до наступного кадру, а для сторінки беруть найгіршу взаємодію. Там само описано, як скрипт набирає слово й
групує записи браузера в три частини кожної літери: затримку вводу, роботу обробників і затримку до кадру. Ми взяли
той самий спосіб без змін. Кінець скрипту `measure7.mjs` друкує число від `onINP`, яке сторінка показала в абзаці
нагорі, і таблицю частин кожної літери:

```js
console.log('onINP:', r.inp)
console.table(interactions(r.entries)) // по рядку на взаємодію: три частини й тривалість
```

Рядки йдуть у порядку літер «с», «к», «л», «а», «д». Колонка `processing` є часом обробників події, і в нашій сторінці
вона майже вся належить React: він рендерить список і вносить зміни в документ. Колонка `presentation` є часом від
кінця обробників до кадру, і там працює вже браузер: компонування, підготовка малювання й саме малювання.

Подивіться на першу літеру. Фільтр після «с» лишив усі десять тисяч записів, ті самі об'єкти в тому самому порядку,
тому React не змінив у списку жодного елемента. Проте обробники все одно працювали близько 139 мс: фільтр перебрав
десять тисяч записів, а React викликав `LogRow` десять тисяч разів, щоб дізнатися, що нічого не змінилося. А затримка
до кадру була 379 мс: браузер готував кадр для сторінки з тридцятьма тисячами елементів, хоча в ній змінився лише
текст поля. Це один прогін, і ділити 379 мс між компонуванням і малюванням за цією таблицею не можна. Розподіл часу
дає трасування нижче.

П'ять прогонів дали INP з медіаною 568 мс, від 552 до 640. Це оцінка «погано» за порогами web.dev, які ви вже знаєте:
до 200 мс добре, понад 500 мс погано.

### Де саме йде час

Щоб побачити роботу браузера окремо від роботи React, ми записали трасування, тобто журнал усіх задач головного
потоку, який Chrome веде під час запису профілю на вкладці Performance. Скрипт `trace7.mjs` вмикає такий запис
командою `Tracing.start`, набирає слово й складає час подій за назвами. Події можуть бути вкладеними одна в одну, тому
функція `covered` спершу складає відрізки часу без перекриттів:

```js
const covered = (names) => {
  const spans = onMain.filter((e) => names.includes(e.name)).map((e) => [e.ts, e.ts + (e.dur ?? 0)]).sort((a, b) => a[0] - b[0])
  let total = 0
  let end = -Infinity
  for (const [a, b] of spans) {
    if (a >= end) { total += b - a; end = b } else if (b > end) { total += b - end; end = b }
  }
  return total / 1000 // трасування рахує в мікросекундах
}
```

Масив `onMain` містить лише події головного потоку сторінки, тобто того потоку, де виконувались обробники клавіш. Ось
що надрукував скрипт за все слово «склад», тобто за п'ять літер разом:

```text

├───────────────────────────────────────────┼───────┼───────┤

│ перерахунок стилів (UpdateLayoutTree)     │ 2.4   │ 5     │
```

Етапи, які браузер проходить перед кадром, пояснила лекція «Як браузер малює»: стилі, компонування, малювання.
Компонуванням там названо крок, на якому браузер рахує положення й розмір кожного елемента. **Підготовка малювання**,
у трасуванні PrePaint, є кроком між компонуванням і малюванням: браузер обходить дерево елементів, готує дані для
малювання й позначає, що треба перемалювати. Докладніше цей крок лекція не розбирає: нам досить того, що він теж
обходить кожен елемент.

Читаємо таблицю. JavaScript зайняв 656 мс на п'ять літер. Браузер після цього витратив ще 92 + 161 + 69, тобто близько
322 мс, на компонування, підготовку малювання й малювання. Обидві частини ростуть із кількістю елементів: React
обходить кожен рядок, а браузер обходить кожен елемент документа, хоча на екрані видно лише п'ятнадцять рядків.

Стаття web.dev каже про це прямо: якщо дія змінює документ, браузер робить роботу з компонування, стилів і малювання,
і що більший документ, то дорожча ця робота. Наші числа показують, що це не теорія.

## Чому `memo` не рятує

Перша думка після лекції «Мемоізація і React Compiler — один замір» така: загорнути рядок у `memo`, і React не
викликатиме рядки, чиї пропси не змінилися. Ось цей варіант:

```tsx
const MemoRow = memo(LogRow)

// Той самий список, але кожен рядок загорнуто в memo.
export function MemoLog({ entries }: { entries: LogEntry[] }) {
  return (
    <div style={{ height: VIEW_HEIGHT, overflow: 'auto' }} data-count={entries.length}>
      <ul>
        {entries.map((entry) => (
          <MemoRow key={entry.id} entry={entry} />
        ))}
      </ul>
    </div>
  )
}
```

Об'єкти записів не змінюються між літерами, тому `memo` бачить той самий проп `entry` і пропускає рядок. Ось підсумок
п'яти прогонів, з якого показано чотири рядки з шести:

```text
nodes      медіана 30014 | від 30014 до 30014
inp        медіана 400 | від 360 до 432
proc       медіана 182 | від 176.4 до 218.4
pres       медіана 179.1 | від 174.7 до 217.8
```

Ці рядки друкує скрипт `batch7.mjs`, який п'ять разів викликає `runOnce`. Поле `inp` є найдовшою взаємодією прогону, а
поля `proc` і `pres` є роботою обробників і затримкою до кадру в цій найдовшій взаємодії. Трасування того самого
варіанта надрукувало:

```text
HeadlessChrome/157.0.8103.38 | http://localhost:4711/lab7.html?v=memo | уповільнення 4× | слово «склад»
┌───────────────────────────────────────────┬───────┬───────┐
```

| INP, медіана п'яти прогонів | 568 мс | 400 мс |
| JavaScript за слово, трасування | 656 мс | 384 мс |

`memo` зменшив роботу React: React перестав викликати рядки, які не змінилися. Проте INP лишився з оцінкою «потребує
поліпшення», а робота браузера не зменшилася зовсім. Причина в тому, що `memo` керує лише викликами компонентів. Коли
після літери «к» зникає п'ять тисяч рядків, React однаково мусить видалити з документа п'ять тисяч елементів `<li>`, а
браузер однаково компонує й малює документ, у якому лишилося понад одинадцять тисяч елементів. Саме це має на увазі
картка дня, коли каже, що десять тисяч рядків гальмують браузер, хоч скільки мемоізуйте.

Звідси висновок дня: якщо час іде на документ, зменшувати треба документ.

## Ідея віртуалізації

Людина бачить в області прокручування 420 пікселів. Рядок має висоту 28 пікселів, тому одночасно видно 420 / 28 = 15
рядків. Решта 9985 рядків стоїть у документі, але їх не видно, і саме на них іде майже вся робота.

**Віртуалізація** списку означає, що в документі стоять лише видимі рядки й кілька рядків запасу вище й нижче, а
замість решти стоїть порожнє місце потрібної висоти. Стара документація React називає цей прийом windowing, від слова
«вікно»: список показує лише ту частину, що потрапляє у видиму область. Бібліотеки називають його virtualization.

Щоб людина не помітила підміни, мають виконуватися три умови.

1. **Смуга прокручування має правильну довжину.** Браузер малює смугу за висотою вмісту. Якщо в документі лише
   двадцять рядків, смуга буде короткою, а прокрутити вдасться лише на 560 пікселів. Тому всередині області
   прокручування стоїть порожній внутрішній елемент такої висоти, яку мав би весь список: 10 000 × 28 = 280 000
   пікселів.
2. **Видимі рядки стоять там, де стояли б у повному списку.** Рядок із номером `i` у повному списку починався б на
   висоті `i × 28`. Віртуалізований рядок отримує `position: absolute`, тобто стоїть не в потоці документа, а там,
   куди його поставлено, і зсув `transform: translateY(...)` на цю висоту.
3. **Після прокручування видимі рядки змінюються.** Область прокручування повідомляє про кожне прокручування подією
   `scroll`, а її властивість `scrollTop` каже, на скільки пікселів вміст прокручено. За цим числом бібліотека рахує,
   які рядки тепер видно, і React показує їх замість старих.

Схема для прокручування на 2800 пікселів:

```text
область прокручування, висота 420 px, scrollTop = 2800
┌──────────────────────────────────────────┐
│ внутрішній елемент, висота 280 000 px    │
│   0 px ... 2660 px: порожньо             │  рядків 0–94 у документі немає
│   2660 px: рядок 95  ┐ запас зверху      │
│   ...                │                   │
│   2772 px: рядок 99  ┘                   │
│   2800 px: рядок 100 ┐ видно людині      │ <- верх видимої області
│   ...                │                   │
│   3192 px: рядок 114 ┘                   │ <- низ видимої області, 3220 px
│   3220 px: рядок 115 ┐ запас знизу       │
│   ...                │                   │
│   3332 px: рядок 119 ┘                   │
│   3360 px ... 280 000 px: порожньо       │  рядків 120–9999 у документі немає
└──────────────────────────────────────────┘
```

Так кількість елементів у документі залежить від висоти області прокручування й запасу, а не від довжини списку.

### Рахуємо, які рядки показати

Тепер подивімося, як це рахує справжня бібліотека. Ядро TanStack Virtual, пакет `@tanstack/virtual-core`, не залежить
від React і браузера. Йому можна передати власні функції замість спостерігачів за елементом, і тоді воно працює в
`node`. Ось скрипт, який ми запустили в теці проєкту:

```js
// range.mjs: ядро TanStack Virtual без браузера, які рядки воно покаже при заданому прокручуванні
import { Virtualizer } from '@tanstack/virtual-core'

let report = () => {}
const box = { ownerDocument: { defaultView: {} } } // замість справжнього елемента з прокручуванням

const v = new Virtualizer({
  count: 10000,
  getScrollElement: () => box,
  estimateSize: () => 28,
  overscan: 5,
  observeElementRect: (_, cb) => cb({ width: 600, height: 420 }), // висота видимої області 420 px
  observeElementOffset: (_, cb) => {
    report = cb // запам'ятали, щоб потім «прокрутити»
    cb(0, false)
  },
  scrollToFn: () => {},
  onChange: () => {},
})
v._willUpdate()

function show(label) {
  const items = v.getVirtualItems()
  const first = items[0]
  const last = items.at(-1)
  console.log(
    `${label}: рядків ${items.length}, індекси ${first.index}–${last.index},`,
    `перший start=${first.start}, останній end=${last.end}, getTotalSize=${v.getTotalSize()}`,
  )
}

show('прокручено на 0 px')
report(2800, false)
show('прокручено на 2800 px')
report(2814, false)
show('прокручено на 2814 px')
report(279580, false)
show('прокручено до кінця')
```

Розберемо його.

- Об'єкт `box` удає елемент прокручування. Ядру від нього потрібне лише поле `ownerDocument.defaultView`, тобто вікно,
  якому належить елемент.
- Функція `observeElementRect` у браузері підписується на зміни розміру області. Тут вона одразу каже: ширина 600,
  висота 420.
- Функція `observeElementOffset` у браузері підписується на подію `scroll` і передає ядру `scrollTop`. Тут вона
  запам'ятовує функцію `cb` у змінну `report`, щоб ми могли «прокрутити» викликом `report(2800, false)`. Другий
  аргумент `false` каже, що прокручування вже закінчилося.
- Метод `_willUpdate` у React викликає адаптер бібліотеки після кожного рендеру, а тут ми викликаємо його самі один
  раз. Підкреслення на початку назви означає внутрішній метод, тому в застосунку його самому не викликають.
- `getVirtualItems()` повертає масив рядків, які треба показати. Кожен елемент масиву має поля `index`, `start`,
  `size`, `end` і `key`.

```text
прокручено на 0 px: рядків 20, індекси 0–19, перший start=0, останній end=560, getTotalSize=280000
прокручено на 2800 px: рядків 25, індекси 95–119, перший start=2660, останній end=3360, getTotalSize=280000
прокручено на 2814 px: рядків 26, індекси 95–120, перший start=2660, останній end=3388, getTotalSize=280000
прокручено до кінця: рядків 20, індекси 9980–9999, перший start=279440, останній end=280000, getTotalSize=280000
```

Порахуймо самі кожен рядок виводу.

| Прокручено | Видима область, px | Видимі рядки | Із запасом 5 | Скільки |
|------------|--------------------|--------------|--------------|---------|
| 0 | 0–420 | 0–14 | 0–19, бо вище нульового рядка нічого немає | 20 |
| 2800 | 2800–3220 | 100–114 | 95–119 | 25 |
| 2814 | 2814–3234 | 100–115, верхній і нижній видно частково | 95–120 | 26 |
| 279 580 | 279 580–280 000 | 9985–9999 | 9980–9999, нижче останнього нічого немає | 20 |

Як ядро знаходить перший видимий рядок? У файлі ядра `virtual-core/dist/esm/index.js` функція `calculateRangeImpl`
спершу шукає двійковим пошуком рядок, чий початок найближчий до `scrollTop` знизу. **Двійковий пошук** ділить
упорядкований масив навпіл, дивиться в середину й відкидає половину, де відповіді бути не може. На десять тисяч рядків
йому вистачає чотирнадцяти кроків. Потім функція йде від цього рядка вниз, поки кінець рядка менший за `scrollTop +
420`. Так виходить діапазон видимих рядків. Функція `defaultRangeExtractor` у тому самому файлі додає до нього запас
`overscan` з обох боків і обрізає його межами списку.

Число 279 580 узялося так: прокрутити далі, ніж 280 000 − 420, неможливо, бо тоді під останнім рядком було б порожньо.

Отже, прокручування на 14 пікселів додало один рядок, бо верхній рядок ще частково видно, а знизу вже частково
з'явився наступний. Загальна висота `getTotalSize()` не змінюється, бо всі рядки мають сталу висоту.

## TanStack Virtual у React

TanStack Virtual сама нічого не малює. Сторінка `Introduction` її документації називає бібліотеку headless, тобто
бібліотекою без власної розмітки й стилів: вона лише рахує, які рядки показати й де, а теги пишете ви. Адаптер для
React дає хук `useVirtualizer`. Ось віртуалізований журнал:

```tsx
import { useVirtualizer } from '@tanstack/react-virtual'

// TanStack Virtual: у документі стоять лише видимі рядки й запас.
export function VirtualLog({ entries, overscan = 5 }: { entries: LogEntry[]; overscan?: number }) {
  const scrollRef = useRef<HTMLDivElement>(null)
  const virtualizer = useVirtualizer({
    count: entries.length,
    getScrollElement: () => scrollRef.current,
    estimateSize: () => ROW_HEIGHT,
    getItemKey: (index) => entries[index].id,
    overscan,
  })
  return (
    <div ref={scrollRef} style={{ height: VIEW_HEIGHT, overflow: 'auto' }} data-count={entries.length}>
      <ul style={{ height: virtualizer.getTotalSize(), position: 'relative', margin: 0 }}>
        {virtualizer.getVirtualItems().map((item) => (
          <LogRow
            key={item.key}
            entry={entries[item.index]}
            style={{
              position: 'absolute',
              top: 0,
              left: 0,
              width: '100%',
              height: item.size,
              transform: `translateY(${item.start}px)`,
            }}
          />
        ))}
      </ul>
    </div>
  )
}
```

Пакет ставлять командою `npm install @tanstack/react-virtual`. Розберемо код по рядках.

- `const scrollRef = useRef<HTMLDivElement>(null)`. Хук потребує самого елемента області прокручування, бо він
  читатиме його `scrollTop` і підписуватиметься на його події. Лекція «Ref» пояснила, що React кладе елемент у
  `scrollRef.current` лише під час коміту, а під час першого рендеру там `null`.
- `count: entries.length`. Скільки рядків у списку загалом. Сторінка `Virtualizer` документації називає це загальною
  кількістю елементів для віртуалізації. Коли фільтр змінює довжину масиву, змінюється й `count`.
- `getScrollElement: () => scrollRef.current`. Тут передано функцію, а не сам елемент. Причина та сама: під час
  першого рендеру елемента ще немає, і документація прямо дозволяє функції повертати `null`. Хук викликає її пізніше,
  у своєму ефекті після коміту, коли `scrollRef.current` уже заповнено.
- `estimateSize: () => ROW_HEIGHT`. Функція отримує індекс рядка й повертає його висоту в пікселях. Якщо висоти рядків
  відомі наперед, вона повертає справжню висоту. Якщо ні, вона повертає оцінку, а справжню висоту бібліотека поміряє,
  про що буде окремий розділ.
- `getItemKey: (index) => entries[index].id`. Функція повертає ключ рядка. Без неї ключем є індекс, і документація
  радить замінювати його на ідентифікатор, унікальний в усьому наборі. Чому це важливо саме для фільтра, пояснено
  нижче.
- `overscan`. Скільки рядків запасу малювати вище й нижче видимої області. Документація каже, що за замовчуванням це
  1, і що більший запас довше рендериться, але рідше показує порожні смуги під час швидкого прокручування.
- `virtualizer.getTotalSize()`. Висота всього списку в пікселях, тобто сума висот усіх рядків. Її ставимо внутрішньому
  елементу, тут `<ul>`, щоб смуга прокручування мала правильну довжину.
- `position: 'relative'` на `<ul>`. Абсолютно поставлені рядки рахують свій зсув від найближчого предка з `position`,
  відмінною від `static`. Без цього рядки рахувалися б від іншого елемента й опинилися б не там.
- `virtualizer.getVirtualItems()`. Масив рядків для показу. Поле `item.index` каже, який запис узяти з масиву, поле
  `item.start` каже, на якій висоті рядок починається, а поле `item.size` дає його висоту.
- `transform: translateY(${item.start}px)`. Зсуває рядок униз на `start` пікселів від верху `<ul>`. Приклад
  документації робить так само. Зсув через `transform` не змінює компонування сусідів, бо рядок стоїть поза потоком
  документа.

Порівняйте з прикладом `Example: react/fixed` з документації. Ось його функція для рядків:

```tsx
// Приклад TanStack Virtual, examples/react/fixed/src/main.tsx, MIT
function RowVirtualizerFixed() {
  const parentRef = React.useRef(null)

  const rowVirtualizer = useVirtualizer({
    count: 10000,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 35,
    overscan: 5,
  })

  return (
    <>
      <div
        ref={parentRef}
        className="List"
        style={{
          height: `200px`,
          width: `400px`,
          overflow: 'auto',
        }}
      >
        <div
          style={{
            height: `${rowVirtualizer.getTotalSize()}px`,
            width: '100%',
            position: 'relative',
          }}
        >
          {rowVirtualizer.getVirtualItems().map((virtualRow) => (
            <div
              key={virtualRow.index}
              className={virtualRow.index % 2 ? 'ListItemOdd' : 'ListItemEven'}
              style={{
                position: 'absolute',
                top: 0,
                left: 0,
                width: '100%',
                height: `${virtualRow.size}px`,
                transform: `translateY(${virtualRow.start}px)`,
              }}
            >
              Row {virtualRow.index}
            </div>
          ))}
        </div>
      </div>
    </>
  )
}
```

Будова та сама: область прокручування з висотою, внутрішній елемент висотою `getTotalSize()`, рядки з
`getVirtualItems()`. Різниця в ключі. Приклад бере ключем `virtualRow.index`, і там це безпечно: список ніколи не
змінюється, тому рядок з індексом 7 завжди показує «Row 7». У журналі з фільтром це не так. Після літери «к» запис з
індексом 0 у масиві `entries` вже інший, ніж до неї. Із ключем-індексом React вирішив би, що це той самий рядок, і
передав би йому нові пропси. Для рядка без стану це лише зайві оновлення документа, а для рядка зі станом, наприклад
розгорнутим описом чи позначкою, стан перейшов би до чужого запису. Лекція «Узгодження дерева» пояснила це правило
докладно. Тому ми передаємо `getItemKey`, і поле `item.key` дорівнює `id` запису.

### Що відбувається під час прокручування

Коли людина прокручує, браузер надсилає області подію `scroll`. Спостерігач бібліотеки читає `scrollTop`, ядро
перераховує діапазон, і якщо діапазон змінився, адаптер просить React відрендерити компонент. У коді адаптера
`react-virtual/dist/esm/index.js` для цього є лічильник `useReducer`, а рендер він викликає через `flushSync`, якщо
оновлення прийшло з події прокручування. Що робить `flushSync`, пояснила лекція «Пакетування оновлень»: React виконує
рендер і коміт одразу, ще до повернення з функції. Тут це потрібно, щоб нові рядки з'явилися в тому самому кадрі, що й
прокручування, інакше людина на мить побачила б порожню смугу. Сторінка `React Virtual` описує це опцією
`useFlushSync`, яка за замовчуванням дорівнює `true`.

З версії адаптера 3.14 є ще опція `directDomUpdates`. Коли вона ввімкнена, бібліотека сама записує в документ зсув
рядків і висоту внутрішнього елемента, а React рендерить компонент лише тоді, коли змінюється діапазон рядків. Для неї
внутрішній елемент отримує `ref={virtualizer.containerRef}` і не повинен мати власної висоти в `style`. Приклад
`Example: react/dynamic` її вмикає. Сьогодні вона вам не потрібна, але знайте, звідки в прикладі `containerRef`.

Прокручування ми перевірили в безголовому Chrome, бо в jsdom немає компонування й прокручування. Скрипт `explore7.mjs`
ставить `scrollTop` області, чекає два кадри й рахує рядки:

```js
// Прокручує область списку до y пікселів і чекає два кадри, щоб React устиг показати нові рядки.
const scrollTo = (y) => `new Promise((done) => {
  const box = document.querySelector('#root [data-count]')
  ;(box.scrollHeight > box.clientHeight ? box : box.firstElementChild).scrollTop = ${y}
  requestAnimationFrame(() => requestAnimationFrame(done))
})`
const STATE = `JSON.stringify({
  rows: document.querySelectorAll('#root li, #root [role=listitem]').length,

```

Поле `first` бере номер запису з тексту першого рядка в документі. Запис № 10001 має індекс 0, тому номер мінус 10001
дає індекс. Для варіанта TanStack Virtual скрипт надрукував:

## Замір після віртуалізації

Ті самі п'ять прогонів, те саме слово, та сама продакшн-збірка й те саме уповільнення. Змінилася лише адреса сторінки,
тобто варіант списку:


Перша команда п'ять разів викликає `runOnce` і друкує медіани, друга записує трасування. Слово «склад» і очікувані

Зверніть увагу й на те, чого ми тут не робили: тут немає ні переходу, ні відкладеного значення. Вони не потрібні, бо
кожна літера коштує кілька десятків мілісекунд. Якщо рядок дорогий у рендері, як у днях 5 і 6, віртуалізація й перехід
доповнюють одне одного: віртуалізація зменшує кількість рядків, а перехід ставить рендер нижче за клавіші.

## react-window: той самий результат іншим способом

Друга поширена бібліотека, `react-window`, названа на старій сторінці документації React поруч із `react-virtualized`.
Головна відмінність від TanStack Virtual така: `react-window` є готовим компонентом. Ви не пишете область
прокручування й внутрішній елемент, компонент `List` робить їх сам і передає кожному рядку готовий `style`. Ось журнал
на `react-window` 2.5.4:

```tsx
import { List, type RowComponentProps } from 'react-window'

// react-window 2: компонент List сам рахує видимі рядки й сам ставить їм style.
function WindowRow({ index, style, ariaAttributes, entries }: RowComponentProps<{ entries: LogEntry[] }>) {
  const entry = entries[index]
  return (
    <div style={style} {...ariaAttributes}>
      <time>{entry.time}</time> <b>{entry.level}</b> {entry.text}
    </div>
  )
}

export function WindowLog({ entries }: { entries: LogEntry[] }) {
  return (
    <div data-count={entries.length}>
      <List
        rowComponent={WindowRow}
        rowCount={entries.length}
        rowHeight={ROW_HEIGHT}
        rowProps={{ entries }}
        style={{ height: VIEW_HEIGHT }}
      />
    </div>
  )
}
```

- `rowComponent` є компонентом рядка. `List` передає йому `index`, `style` з положенням рядка й `ariaAttributes`, а
  також усе, що лежить у `rowProps`.
- `rowCount` і `rowHeight` відповідають `count` і `estimateSize` у TanStack Virtual. Висота тут може бути числом, бо
  всі рядки однакові.
- `rowProps={{ entries }}` передає рядкам дані. Приклад міграції на версію 2 у журналі змін каже коментарем, що цей
  об'єкт не треба загортати в `useMemo`, бо `List` сам його запам'ятовує. Типи пакета додають, що `List` рендерить
  рядки заново, коли змінюються значення в цьому об'єкті.
- `style={{ height: VIEW_HEIGHT }}` задає висоту списку. Сторінка `Lists: Fixed row heights` попереджає: без явної
  висоти в пікселях список міряє доступне місце батька через `ResizeObserver`, тож батько повинен мати висоту.
- `ariaAttributes` містить `role="listitem"`, `aria-posinset` і `aria-setsize`. Що це дає, пояснено в розділі про ціну
  віртуалізації. Типи пакета радять розгортати ці атрибути на елемент рядка, як зроблено тут.

Ключем рядка `List` бере індекс. Для рядка без стану, як наш, цього досить. Якщо рядки мають стан, версія 2 дає проп
`rowKey`, і типи пакета радять передавати в нього функцію через `useCallback`.

Замір тим самим способом:

```text
HeadlessChrome/157.0.8103.38 | http://localhost:4711/lab7.html?v=window | уповільнення 4× | слово «склад» | прогонів 5
nodes      медіана 69 | від 69 до 69
inp        медіана 32 | від 24 до 48
```

У документі вісімнадцять рядків: п'ятнадцять видимих і три запасу, бо `overscanCount` у версії 2 за замовчуванням
дорівнює 3. Скрипт прокручування надрукував для цього варіанта:

```text
window   на початку {"rows":18,"first":"10001","found":false,"total":null,"heights":""}
         scrollTop=2800 {"rows":21,"first":"10098","found":false,"total":null,"heights":""}
         scrollTop=251972 {"rows":21,"first":"18997","found":true,"total":null,"heights":""}
```

На 2800 пікселях перший рядок має індекс 97, тобто 100 − 3. Поле `heights` порожнє, бо рядки тут є елементами `<div>`,
а скрипт міряє лише `<li>`. Обидві бібліотеки дали INP з оцінкою «добре», а розкиди прогонів, від 24 до 32 мс і від 24
до 48 мс, перекриваються, тому сказати, яка швидша, ці числа не дозволяють.

### Лінія 1.x: `FixedSizeList`

У старих проєктах і статтях ви зустрінете версію 1.x, де той самий список називався `FixedSizeList`. Ось приклад з її
документації:

```jsx
// Приклад react-window 1.8.11, website/src/routes/examples/FixedSizeList.js, MIT
import { FixedSizeList as List } from 'react-window';

const Row = ({ index, style }) => (
  <div style={style}>Row {index}</div>
);

const Example = () => (
  <List
    height={150}
    itemCount={1000}
    itemSize={35}
    width={300}
  >
    {Row}
  </List>
);
```

Тут `itemCount` став у версії 2 пропом `rowCount`, `itemSize` став `rowHeight`, компонент рядка передавався як дитина,
а не пропом `rowComponent`, а дані йшли через проп `itemData`, а не `rowProps`. Висота й ширина у версії 1 були
обов'язковими. Ми цей приклад не запускали.

| | TanStack Virtual | `react-window` 2 |
|-|------------------|------------------|
| що дає бібліотека | хук, який рахує рядки; розмітку пишете ви | готовий компонент `List` з областю прокручування |
| кількість і висота | `count`, `estimateSize` | `rowCount`, `rowHeight` |
| запас за замовчуванням | `overscan: 1` | `overscanCount: 3` |
| ключ рядка | індекс або `getItemKey` | індекс або `rowKey` |
| рядки різної висоти | `measureElement` | хук `useDynamicRowHeight` |
| прокручування всієї сторінки | `useWindowVirtualizer` | проп `scrollElement="window"` |
| інші фреймворки | Vue, Svelte, Solid, Lit, Angular | лише React |

## Рядки різної висоти

Досі всі рядки мали 28 пікселів. Тепер уявіть, що текст запису довгий і переноситься на кілька рядків тексту. Висоту
такого рядка не знає ніхто, поки браузер його не скомпонує: вона залежить від шрифту, ширини області й самого тексту.

TanStack Virtual розв'язує це так. Функція `estimateSize` дає оцінку для рядків, яких ще ніхто не бачив. Коли рядок
з'являється в документі, бібліотека міряє його справжню висоту, запам'ятовує її й перераховує положення всіх рядків
нижче. Щоб бібліотека могла міряти, рядок отримує два атрибути:

```tsx
// Рядки різної висоти: справжню висоту кожного рядка бібліотека міряє після показу.
export function DynamicLog({ entries }: { entries: LogEntry[] }) {
  const scrollRef = useRef<HTMLDivElement>(null)
  const virtualizer = useVirtualizer({
    count: entries.length,
    getScrollElement: () => scrollRef.current,
    estimateSize: () => ROW_HEIGHT,
    getItemKey: (index) => entries[index].id,
    overscan: 5,
  })
  return (
    <div ref={scrollRef} style={{ height: VIEW_HEIGHT, width: 360, overflow: 'auto' }} data-count={entries.length}>
      <ul data-total={virtualizer.getTotalSize()} style={{ height: virtualizer.getTotalSize(), position: 'relative', margin: 0 }}>
        {virtualizer.getVirtualItems().map((item) => (
          <li
            key={item.key}
            data-index={item.index}
            ref={virtualizer.measureElement}
            style={{ position: 'absolute', top: 0, left: 0, width: '100%', transform: `translateY(${item.start}px)` }}
          >
            <time>{entries[item.index].time}</time> {entries[item.index].text.repeat(1 + (item.index % 3))}
          </li>
        ))}
      </ul>
    </div>
  )
}
```

- `ref={virtualizer.measureElement}`. Тут у `ref` передано функцію, а не об'єкт. Лекція «Ref» пояснила, що React
  викликає таку функцію з елементом після коміту. Метод `measureElement` міряє елемент і, за кодом ядра, стежить за
  ним через `ResizeObserver`, тому зміна висоти пізніше теж буде врахована.
- `data-index={item.index}`. За цим атрибутом бібліотека дізнається, якому рядку належить поміряний елемент. Сторінка
  `Virtualizer` у розділі `measureElement` прямо вимагає його.
- У `style` немає `height`. Висоту тепер визначає вміст, а не бібліотека.
- Атрибут `data-total` потрібен лише скрипту заміру, щоб прочитати `getTotalSize()`.
- Текст повторено один, два або три рази залежно від індексу, а ширину області звужено до 360 пікселів, щоб рядки
  справді мали різну висоту.

Ось що надрукував скрипт прокручування для цього варіанта:

```text
dynamic  на початку {"rows":14,"first":"10001","found":false,"total":"280428","heights":"19,38,57,76"}
         scrollTop=2800 {"rows":19,"first":"10080","found":false,"total":"281049","heights":"19,38,57,76"}
         scrollTop=251972 {"rows":19,"first":"18957","found":false,"total":"281670","heights":"19,38,57,76"}
```

Справжні висоти рядків вийшли 19, 38, 57 і 76 пікселів, тобто від одного до чотирьох рядків тексту, а оцінка була 28.
Тепер прочитайте поле `total`. На початку загальна висота дорівнювала 280 428 пікселям, хоча за оцінкою мала бути
280 000: бібліотека поміряла показані рядки, і вони разом виявилися на 428 пікселів вищими за оцінку. Після кожного
прокручування поміряних рядків ставало більше, і висота росла: 281 049, потім 281 670. Отже, поки людина прокручує,
смуга прокручування трохи змінює довжину, а положення рядків нижче поміряних зсувається. Тому на 251 972 пікселях
перший рядок має індекс 8956, а не 8994, як у списку зі сталою висотою: рядки вище стали вищими.

Звідси дві поради документації. Сторінка `Virtualizer` у розділі `estimateSize` радить, якщо ви міряєте рядки,
оцінювати найбільшу можливу висоту, бо тоді початкові положення будуть точнішими. А сторінка `Lists: Dynamic row
heights` `react-window` попереджає, що поміряні висоти менш ефективні, ніж відомі наперед, і радить задавати висоти
самим, коли їх можна порахувати. Хук `useDynamicRowHeight` у `react-window` робить те саме, що `measureElement`:
передаєте його результат у `rowHeight`, і `List` міряє рядки сам.

## React Compiler і `useVirtualizer`

Лінтер шаблону проєкту має правила `eslint-plugin-react-hooks`, які перевіряють код тими самими правилами, що й React
Compiler. Ми запустили його на файлі з `useVirtualizer`:

```bash
npx eslint src/lab7/lists.tsx
```

Він надрукував таке:

```text
src/lab7/lists.tsx
   48:23  warning  Compilation Skipped: Use of incompatible library

This API returns functions which cannot be memoized without leading to stale UI. To prevent this, by default React Compiler will skip memoizing this component/hook. However, you may see issues if values from this API are passed to other components/hooks that are memoized.

src/lab7/lists.tsx:48:23
  46 | export function VirtualLog({ entries, overscan = 5 }: { entries: LogEntry[]; overscan?: number }) {
  47 |   const scrollRef = useRef<HTMLDivElement>(null)
> 48 |   const virtualizer = useVirtualizer({
     |                       ^^^^^^^^^^^^^^ TanStack Virtual's `useVirtualizer()` API returns functions that cannot be memoized safely
  49 |     count: entries.length,
  50 |     getScrollElement: () => scrollRef.current,
  51 |     estimateSize: () => ROW_HEIGHT,  react-hooks/incompatible-library
```

Тут показано попередження для `VirtualLog`. Таке саме лінтер надрукував для `DynamicLog`. Правило називається
`react-hooks/incompatible-library`. Сторінка цього правила в документації React пояснює: деякі бібліотеки повертають
об'єкт, який змінюється всередині, а не замінюється новим. Об'єкт `virtualizer` якраз такий: між рендерами це той
самий об'єкт, а `getVirtualItems()` повертає щоразу нові рядки. Якби компілятор запам'ятав результат за тим самим
об'єктом, список перестав би оновлюватися під час прокручування. Тому компілятор пропускає компонент, у якому
викликано `useVirtualizer`, і не додає в нього автоматичної мемоізації.

Для вас це означає дві речі. Попередження не є помилкою, і код працює. Але якщо ви покладалися на те, що React
Compiler сам загорне повільні частини цього компонента в мемоізацію, тут він цього не зробить. Тримайте компонент із
віртуалізатором невеликим, а дорогі частини виносьте в окремі компоненти.

## Ціна віртуалізації

### Пошук браузера

Пошук на сторінці, який відкриває `Ctrl+F`, шукає текст у документі. Віртуалізація прибирає з документа рядки, яких не
видно, тому пошук браузера їх не знаходить. Ми не могли перевірити це вікном пошуку, бо в безголовому Chrome його
немає. Перевірити вдалося інше: чи є текст невидимого рядка в документі. Поле `found` у скрипті прокручування шукало
рядок «запис № 19000», тобто запис з індексом 8999. Ось цей рядок зі скрипту `explore7.mjs`, показаного вище:

```js
found: document.body.textContent.includes('запис № 19000'),
```

Властивість `textContent` дає весь текст елемента разом з текстом нащадків, а метод `includes` каже, чи є в ньому
заданий шматок. Скрипт надрукував:

```text
plain    на початку {"rows":10000,"first":"10001","found":true,"total":null,"heights":"19"}
virtual  на початку {"rows":20,"first":"10001","found":false,"total":null,"heights":"28"}
         scrollTop=251972 {"rows":25,"first":"18995","found":true,"total":null,"heights":"28"}
```

Тут показано по рядку з виводу для повного списку й двох станів віртуалізованого. У повному списку текст є завжди. У
віртуалізованому його немає, поки людина не прокрутить до цього місця, і щойно рядок з'явився в документі, текст
знайшовся. Отже, людина, яка натисне `Ctrl+F` і введе «19000», нічого не знайде, хоча запис існує. Те, що вікно пошуку
браузера поводиться саме так, ми виводимо з того, що тексту немає в документі, а не з запуску.

Що з цим робити. У журналі й довіднику вже є власне поле пошуку, і воно шукає в даних, а не в документі. Його й треба
показати людині помітно. Якщо пошук браузера обов'язковий, а рядків кілька сотень, віртуалізація не годиться. Тоді
можна залишити рядки в документі й дати браузерові пропускати роботу з невидимими. Для цього є властивість CSS
`content-visibility: auto`. Сторінка MDN каже, що з таким значенням браузер пропускає вміст, який не стосується
людини, але вміст лишається доступним для пошуку на сторінці й для переходу клавішею Tab. Стаття web.dev теж її
радить. Кількості елементів вона не зменшує, і ми її не міряли.

### Доступність

Програма читання з екрана, якою користуються незрячі люди, оголошує, скільки пунктів у списку. Сторінка MDN про
атрибут `aria-setsize` пояснює, що браузер рахує пункти за тими, що є в документі, тому для віртуалізованого списку з
двадцяти рядків він скаже «двадцять пунктів». Атрибути `aria-setsize` і `aria-posinset` кажуть справжню кількість і
справжній номер пункту. `react-window` 2 дає їх рядку сам у пропі `ariaAttributes`, а з TanStack Virtual їх ставите
ви.

### Обмеження верстки

Віртуалізація вимагає області прокручування з відомою висотою, абсолютно поставлених рядків і внутрішнього елемента з
`position: relative`. Рядки стоять поза потоком документа, тому звичні прийоми верстки, де рядки впливають один на
одного, тут не працюють. З тієї самої причини, з якої їх не бачить пошук, друк сторінки покаже лише рядки, які є в
документі. Друку ми не перевіряли. Для прокручування всієї сторінки, а не окремої області, TanStack Virtual має
окремий хук `useWindowVirtualizer`.

### Короткий список

Картка дня застерігає від віртуалізації короткого списку. Ми поміряли журнал на п'ятдесят записів, адреса `?n=50`.
Слово «склад» лишає з них вісімнадцять, тому останнім аргументом скрипту стоїть очікувана кількість записів 18:

```bash
node batch7.mjs "http://localhost:4711/lab7.html?v=plain&n=50" 5 склад 18
node batch7.mjs "http://localhost:4711/lab7.html?v=virtual&n=50" 5 склад 18
```

```text
HeadlessChrome/157.0.8103.38 | http://localhost:4711/lab7.html?v=plain&n=50 | уповільнення 4× | слово «склад» | прогонів 5
nodes      медіана 164 | від 164 до 164
inp        медіана 24 | від 24 до 144
HeadlessChrome/157.0.8103.38 | http://localhost:4711/lab7.html?v=virtual&n=50 | уповільнення 4× | слово «склад» | прогонів 5
nodes      медіана 74 | від 74 до 74
inp        медіана 16 | від 16 до 24
```

Повний список на п'ятдесят записів має 164 елементи, віртуалізований 74. Медіани INP різняться на 8 мс, тобто на один
крок округлення браузера, і обидва числа мають оцінку «добре». Верхня межа 144 мс у повного списку належить одному
прогону з п'яти, де робота обробників однієї літери тривала 113 мс замість звичних 13–37 мс. Причини ми не шукали: у
інших чотирьох прогонах повного списку INP був від 24 до 48 мс, тому медіана тут чесніша за межу. Виграшу людина не
відчує, а ціну, описану вище, ви платите повністю: пошук браузера, доступність, обмеження верстки й компонент, який
React Compiler пропускає. Тому віртуалізують лише після заміру, коли список має сотні чи тисячі рядків і час справді
йде на документ.

## Орієнтир для практики

Практику ми теж прогнали, щоб перевірити картку. Довідник мав 10 000 відділень, рядок був одним елементом `<li>` без
функції `slowScore`, а набирали ми слово «львів», як у днях 5 і 6. Продакшн-збірка, той самий безголовий Chrome 157,
уповільнення в чотири рази, п'ять прогонів. До віртуалізації сторінка мала 10 013 елементів, а INP мав медіану 368 мс.
Після віртуалізації сторінка мала 39 елементів, а INP 24 мс. Ваші числа будуть іншими, бо інший комп'ютер і інша
розмітка рядка, але порядок має бути той самий: кількість елементів падає з десятків тисяч чи тисяч до кількох
десятків, а INP переходить в оцінку «добре».

Чому рядок без `slowScore`. Якщо лишити рядку вчорашню ціну в одну мілісекунду з уповільненням, повний список на
десять тисяч рядків рендерився б близько десяти секунд на кожну літеру. Такий замір показав би ціну обчислень у
рендері, яку дні 5 і 6 уже міряли, а не ціну документа.

## Дві пари чисел у журналі

Журнал вимірів, який ви завели в темі «Збірка, перший викот і журнал вимірів», отримує сьогодні два рядки. Колонки
журналу ті самі, а кількість елементів запишіть у колонку «Що змінили», бо окремої колонки для неї немає. Ось рядки
для нашого журналу складу:

```text
| дата | Журнал складу, 10 000 записів, «склад», літера кожні 150 мс; 30 014 елементів; продакшн, 4×, onINP | — | 568 мс | — | — |
| дата | Те саме, useVirtualizer, overscan 5; 74 елементи | — | 24 мс | — | — |
```

Порядок дій той самий, що в днях 5 і 6: зібрати застосунок, відкрити зібрану сторінку через `vite preview`, увімкнути
уповільнення в чотири рази, порахувати елементи в консолі, набрати те саме слово в тому самому темпі кілька разів і
взяти медіану. Окремо перевірте очима те, чого числа не бачать: під час прокручування рядки з'являються без порожніх
смуг, а смуга прокручування має таку саму довжину, як у повного списку.

## Типові хибні уявлення

**«Якщо рядок дешевий, довгий список не гальмує».** Рядок нашого журналу нічого не рахував, а INP повного списку був
568 мс. Час ішов на виклик десяти тисяч компонентів і на компонування й малювання тридцяти тисяч елементів.

**«`memo` на рядку розв'язує проблему довгого списку».** `memo` зменшив JavaScript із 656 до 384 мс за слово, але INP
лишився 400 мс, а робота браузера не змінилася. `memo` пропускає виклики компонентів, але не прибирає елементів із
документа.

**«Віртуалізація прискорює фільтр».** Фільтр однаково перебирає всі записи. Віртуалізація зменшує лише кількість
рядків у документі: зі слова «склад» лишилося 3750 записів, а в документі двадцять рядків.

**«Ключем можна взяти `item.index`, як у прикладі документації».** У списку, який змінюється фільтром, індекс 0 після
кожної літери означає інший запис. Ключем має бути ідентифікатор запису через `getItemKey`.

**«Більший `overscan` завжди краще».** Запас зменшує порожні смуги під час швидкого прокручування, але кожен рядок
запасу є ще трьома елементами в документі й ще одним викликом компонента. На 2800 пікселях запас 5 дав двадцять п'ять
рядків замість п'ятнадцяти видимих.

**«`estimateSize` має бути точним, інакше нічого не працює».** Для рядків різної висоти це оцінка: бібліотека міряє
справжню висоту й виправляє положення. Ціна неточності в тому, що загальна висота росте під час прокручування, як
показали числа 280 428, 281 049 і 281 670.

**«Віртуалізація нічого не забирає в людини».** Вона забирає пошук браузера `Ctrl+F` по невидимих рядках, правильну
кількість пунктів для програм читання з екрана без додаткових атрибутів і друк усього списку.

## Як це проявиться далі в React

- **День «`<Suspense>` і межі помилок».** Віртуалізований список часто вантажить дані частинами, коли людина доходить
  до кінця. Поки частина вантажиться, показують запасний вміст, і саме цим займається `<Suspense>`.
- **Фаза 3, день «Маршрути».** Довгий список зазвичай живе на окремій сторінці застосунку. Коли людина повертається на
  нього, вона чекає побачити те саме місце, тому положення прокручування доведеться зберігати й відновлювати, а
  віртуалізатор має для цього метод `scrollToIndex` і опцію `initialOffset`.
- **Таблиці.** Сторінка `Introduction` TanStack Virtual каже, що два віртуалізатори, по рядках і по стовпцях, дають
  сітку. Так будують таблиці з тисячами рядків і стовпців.

## Перевірте себе

**1. Сторінка має список на п'ять тисяч рядків, кожен рядок дешевий. Колега каже, що проблеми немає, бо рядок нічого
не рахує. Які два числа ви поміряєте і де шукатимете час?**

<details><summary>Відповідь</summary>

Кількість елементів через `document.querySelectorAll('*').length` і INP набору чи клацання на продакшн-збірці з
уповільненням процесора. Час шукатиму у двох місцях: у роботі обробників, де React викликає тисячі компонентів, і в
затримці до кадру, де браузер компонує й малює весь документ. У нашому журналі на десять тисяч записів затримка до
кадру першої літери була 379 мс, хоча список не змінився.

</details>

**2. Чому `memo` на рядку зменшив INP з 568 до 400 мс, але не до 24 мс, як віртуалізація?**

<details><summary>Відповідь</summary>

`memo` дозволив React не викликати рядки, чиї пропси не змінилися, тому JavaScript за слово впав із 656 до 384 мс. Але
коли фільтр прибирає тисячі записів, React однаково видаляє тисячі елементів із документа, а браузер однаково компонує
й малює документ з одинадцятьма тисячами елементів. Цю роботу прибирає лише менший документ.

</details>

**3. Область прокручування має висоту 600 пікселів, рядок 30 пікселів, список 2000 рядків, `overscan` дорівнює 3.
Скільки рядків стоїть у документі, коли людина прокрутила на 3000 пікселів, і яку висоту має внутрішній елемент?**

<details><summary>Відповідь</summary>

Видимі рядки займають 3000–3600 пікселів, тобто рядки з індексами від 100 до 119, двадцять рядків. Запас додає по три
з кожного боку: індекси від 97 до 122, двадцять шість рядків. Внутрішній елемент має висоту 2000 × 30 = 60 000
пікселів.

</details>

**4. Навіщо `getScrollElement` є функцією, а не самим елементом?**

<details><summary>Відповідь</summary>

Під час першого рендеру React ще не створив елемент області прокручування, і `scrollRef.current` дорівнює `null`. Хук
викликає функцію пізніше, у своєму ефекті після коміту, коли елемент уже лежить у ref. Документація дозволяє функції
повертати `null`, поки елемента немає.

</details>

**5. У прикладі `react/fixed` ключем рядка є `virtualRow.index`. Чому у списку з фільтром так робити не варто?**

<details><summary>Відповідь</summary>

У фільтрованому списку той самий індекс після кожної літери означає інший запис. Із ключем-індексом React вважатиме
рядок тим самим і передасть йому інші пропси, а стан рядка, якщо він є, перейде до чужого запису. Ключ має бути
ідентифікатором запису, і для цього `useVirtualizer` має опцію `getItemKey`.

</details>

**6. Рядки журналу мають різну висоту. Що треба додати до рядка, щоб TanStack Virtual поміряла його, і що станеться з
загальною висотою під час прокручування?**

<details><summary>Відповідь</summary>

Рядку треба передати `ref={virtualizer.measureElement}` і `data-index={item.index}`, а з `style` прибрати сталу
висоту. Бібліотека міряє кожен показаний рядок, запам'ятовує висоту й перераховує положення рядків нижче. Тому
загальна висота `getTotalSize()` змінюється, поки людина прокручує. Під час прокручування журналу складу вона росла
так: 280 428 пікселів, потім 281 049, потім 281 670.

</details>

**7. Список має п'ятдесят рядків, і колега хоче його віртуалізувати «про запас». Що ви відповісте з числами?**

<details><summary>Відповідь</summary>

На п'ятдесяти записах повний список мав 164 елементи й INP 24 мс, віртуалізований 74 елементи й INP 16 мс, обидва
числа є медіанами. Різниця дорівнює одному кроку округлення браузера, і обидва числа мають оцінку «добре». А ціна
лишається: пошук браузера `Ctrl+F` не знаходить невидимих рядків, програмі читання з екрана потрібні `aria-setsize` і
`aria-posinset`, верстка обмежена, а React Compiler пропускає компонент із `useVirtualizer`. Віртуалізувати варто
після заміру, який показує, що час іде на документ.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| віртуалізація, windowing | спосіб показувати в документі лише видимі рядки списку й невеликий запас |
| область прокручування | елемент зі сталою висотою й `overflow: auto`, усередині якого прокручується вміст |
| внутрішній елемент | порожній елемент висотою всього списку, який дає смузі прокручування правильну довжину |
| `scrollTop` | на скільки пікселів прокручено вміст області |
| запас, overscan | рядки вище й нижче видимої області, які малюють наперед |
| `estimateSize` | функція, яка повертає висоту рядка або її оцінку |
| `getTotalSize()` | висота всього списку в пікселях |
| `getVirtualItems()` | масив рядків для показу з полями `index`, `start`, `size`, `end`, `key` |
| `measureElement` | метод, який міряє справжню висоту показаного рядка |
| headless | бібліотека, яка рахує, але не дає власної розмітки й стилів |
| елемент і вузол | елемент є тегом у документі; вузол є будь-яким об'єктом дерева, зокрема текстом і коментарем |
| підготовка малювання, PrePaint | крок браузера між компонуванням і малюванням, на якому він обходить дерево елементів |
| трасування | журнал усіх задач головного потоку, який Chrome записує для вкладки Performance |
| `content-visibility: auto` | властивість CSS, з якою браузер пропускає роботу з невидимим вмістом, не видаляючи його |
| `aria-setsize`, `aria-posinset` | атрибути, які кажуть програмі читання з екрана справжню кількість пунктів і номер пункту |
