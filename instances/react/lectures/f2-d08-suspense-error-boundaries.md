# Лекція. Фаза 2, день 8. `<Suspense>` і межі помилок

Досі кожен день фази стосувався швидкості: скільки мілісекунд коштує рендер і як не дати повільній частині гальмувати
поле вводу. Сьогодні мова про два інші стани екрана, які людина бачить щодня: частина сторінки ще вантажиться, або
частина сторінки впала з помилкою. Обидва стани React дає описати заздалегідь, а не лишити на волю випадку. Читання
займе близько 70 хвилин.

Числа й вивід у лекції отримано на React 19.3.1, Vite 8.3.6 і TypeScript 6.0.3. Досліди без браузера запускалися у
Vitest 5.1.0 із середовищем jsdom 31.0.0. **jsdom** є бібліотекою, яка імітує документ браузера всередині Node: вона
вміє будувати DOM і надсилати події, але нічого не малює й не завантажує з мережі. Досліди в браузері запускалися в
`chrome-headless-shell` версії 157, тобто в Chromium без вікна, яким скрипт керував через протокол інструментів
розробника. Ми відкривали дві версії тієї самої сторінки: сервер розробки `npx vite` і продакшн-збірку, відкриту через
`npx vite preview`. Біля кожного числа сказано, де його отримано. Вікна Chrome DevTools ми не відкривали, а консоль
читали як дані.

Практика дня робить те саме у вашому застосунку. Щоб не показувати розв'язку, лекція бере інший об'єкт: сторінку
велосипедного маршруту.

**Після лекції ви зможете пояснити:**

- навіщо відкладати завантаження коду компонента і що для цього роблять `lazy` та `<Suspense>`;
- що означає слово «чекати» для компонента і що в цей час показує React;
- чому вже показаний вміст іноді ховається за запасним вмістом і як цього уникнути;
- як записати клас у JavaScript настільки, наскільки цього потребує межа помилок;
- що роблять методи `getDerivedStateFromError` і `componentDidCatch` і в якому порядку їх викликає React;
- які помилки межа ловить, а які ні, і чому помилку в обробнику клацання ловить лише `try/catch`;
- що React друкує в консоль у режимі розробки й у продакшн-збірці і що змінюють `onCaughtError` та `onUncaughtError`;
- що таке стек компонентів і чому в продакшн-збірці в ньому короткі незрозумілі імена.

## Дві неприємності на одній сторінці

Уявіть сторінку маршруту велопрогулянки «Київ — Вишгород». Угорі стоїть заголовок. Нижче йде список зупинок, де кожна
показує кілометр і координати. Під списком є кнопка «Показати графік висот». Графік є важким компонентом, бо його
модуль несе профіль висот із шести тисяч точок. Ще нижче стоїть кнопка «Експортувати GPX», яка мала б зберегти маршрут
у файл. GPX є форматом файла для навігаторів.

Дані маршруту приходять із сервера. Ось як вони виглядають у коді досліду:

```ts
// route.ts
export type Stop = {
  name: string
  km: number
  coords: { lat: number; lon: number } | null
}

export const STOPS: Stop[] = [
  { name: 'Поштова площа', km: 0, coords: { lat: 50.4592, lon: 30.5250 } },
  { name: 'Оболонська набережна', km: 9.4, coords: { lat: 50.5003, lon: 30.5161 } },
  { name: 'Гідропарк Вишгород', km: 17.8, coords: { lat: 50.5748, lon: 30.4887 } },
  { name: 'Межигір’я', km: 24.1, coords: { lat: 50.6198, lon: 30.4620 } },
]

// Ті самі зупинки, але сервер не знайшов координат третьої: поле прийшло як null.
export const BROKEN_STOPS: Stop[] = STOPS.map((s, i) => (i === 2 ? { ...s, coords: null } : s))
```

Список зупинок написав колега, який вважав, що координати є завжди:

```tsx
// StopList.tsx
function StopRow({ stop }: { stop: Stop }) {
  note(`рендер StopRow ${stop.name}`) // рядок заміру: записує кожен виклик у журнал досліду
  // Якщо coords дорівнює null, рядок нижче кидає TypeError під час рендеру.
  const where = `${stop.coords!.lat.toFixed(3)}, ${stop.coords!.lon.toFixed(3)}`
  return (
    <li>
      {stop.km} км, {stop.name} ({where})
    </li>
  )
}

export function StopList({ stops }: { stops: Stop[] }) {
  return (
    <ol>
      {stops.map((s) => (
        <StopRow key={s.name} stop={s} />
      ))}
    </ol>
  )
}
```

Знак оклику після `stop.coords` є записом TypeScript, який каже компілятору: «повір, тут не `null`». Компілятор
вірить і мовчить, але під час виконання значення лишається `null`. Функція `note` дописує рядок у звичайний масив поза
React, а тест наприкінці друкує цей масив. Як і в попередніх днях, такий рядок заміру порушує чистоту компонента, і
ми робимо це свідомо, щоб бачити кожен виклик.

На цій сторінці є дві неприємності.

**Перша неприємність стосується коду.** Збирач кладе весь код, імпортований звичайним `import`, у той файл, який
браузер завантажує першим. Ми зібрали сторінку зі звичайним імпортом графіка командою `vite build`:

```text
dist-lab-static/lab-static.html                  0.26 kB │ gzip:  0.21 kB
dist-lab-static/assets/lab-static-ChzZFTtw.js  304.07 kB │ gzip: 96.84 kB
```

Головний файл важить 304 кілобайти. З них близько 80 кілобайтів займає модуль графіка, який людина, можливо, ніколи
не відкриє. Як читати такий звіт, пояснила лекція «Збірка, перший викот і журнал вимірів».

**Друга неприємність стосується помилки.** Що стається, коли сервер надсилає зупинку без координат? Ми спершу показали
сторінку з правильними даними, а потім з `BROKEN_STOPS`. Тест створив корінь React у jsdom і записав, що лишилося в
документі:

```tsx
const container = document.createElement('div')
const root = createRoot(container)
await act(async () => root.render(<Page stops={STOPS} guarded={false} />))
// ...
try {
  await act(async () => root.render(<Page stops={BROKEN_STOPS} guarded={false} />))
} catch (e) {
  note(`act кинув: ${String(e)}`)
}
note(`документ після: "${container.textContent}", innerHTML="${container.innerHTML}"`)
```

Функція `act` з пакета `react` чекає, поки React виконає всю роботу, заплановану всередині неї. Тести
користуються нею, щоб перевіряти документ уже після рендеру. Компонент `Page` малює заголовок і список зупинок, а
пропс `guarded` поки що дорівнює `false`. Тест надрукував:

```text
рендер StopRow Поштова площа
рендер StopRow Оболонська набережна
рендер StopRow Гідропарк Вишгород
рендер StopRow Поштова площа
рендер StopRow Оболонська набережна
рендер StopRow Гідропарк Вишгород
act кинув: TypeError: Cannot read properties of null (reading 'lat')
документ після: "", innerHTML=""
```

Документ став порожнім. Зникли не лише зупинки, а й заголовок, хоча заголовок ніяк не залежав від координат. Довідник
React описує це правило на сторінці `Component`: якщо під час рендеру виникла помилка, React за замовчуванням прибирає
з екрана весь свій інтерфейс. Чому React двічі пройшов три рядки, покаже розділ «Простежимо одну помилку».

Отже, сторінці бракує двох речей. Код графіка має приходити лише тоді, коли графік потрібен, а поки він іде, людина
має бачити напис «Завантажую графік…». Помилка в одному списку має ламати лише цей список, а решта сторінки має жити
далі. Першу річ дає пара `lazy` і `<Suspense>`, другу дає межа помилок.

## Код, що приходить пізніше

### Динамічний імпорт і `lazy`

Лекція «Модулі й пакети» показала **динамічний імпорт**: вираз `import('./файл')` виконується як звичайний виклик і
повертає обіцянку модуля. Лекція «Збірка, перший викот і журнал вимірів» показала, що збирач кладе такий модуль в
окремий файл. Окремий файл збірки часто називають **чанком**, від англійського chunk, тобто «шматок».

Компонент, проте, не можна просто покласти в обіцянку: React має знати, що малювати, ще до того, як модуль прийшов.
Для цього існує функція `lazy`. Вона приймає функцію завантаження й повертає компонент, який можна рендерити як
звичайний:

```tsx
import { lazy } from 'react'

const ElevationChart = lazy(() => import('./ElevationChart'))
```

Довідник `lazy` у розділі `Reference` описує функцію завантаження, яку він називає `load`, так.

- `load` не приймає аргументів і повертає обіцянку або інший об'єкт з методом `then`. Обіцянка має завершитися
  об'єктом, у якого поле `default` містить компонент. Тому модуль ледачого компонента експортує його як `export
  default`.
- React не викликає `load`, поки ви вперше не спробуєте відрендерити цей компонент.
- Після першого виклику React запам'ятовує і саму обіцянку, і її результат, тому вдруге `load` не викликається.
- Якщо обіцянка відхилена, React кидає причину відхилення найближчій межі помилок.

Сам модуль графіка є звичайним компонентом з експортом за замовчуванням:

```tsx
// ElevationChart.tsx
import { PROFILE } from './profile' // 6000 точок профілю висот: саме вони роблять модуль важким
import { note } from './log'

export default function ElevationChart() {
  note('рендер ElevationChart')
  const step = 20 // кожна двадцята точка, щоб лінія мала 300 вершин
  const points = PROFILE.filter((_, i) => i % step === 0)
    .map(([km, ele]) => `${(km * 10).toFixed(1)},${(260 - ele).toFixed(1)}`)
    .join(' ')
  const top = Math.max(...PROFILE.map(([, ele]) => ele))
  return (
    <figure>
      <svg viewBox="0 0 600 140" width="600" height="140">
        <polyline points={points} fill="none" stroke="currentColor" />
      </svg>
      <figcaption>Найвища точка: {top.toFixed(0)} м</figcaption>
    </figure>
  )
}
```

### Що означає «чекати»

Коли React доходить до ледачого компонента, модуль якого ще не прийшов, він не може викликати цей компонент: функції
компонента ще немає. React зупиняє рендер цієї частини дерева. Довідник називає такий стан словом **suspend**, тобто
«призупинитися». Українською ми кажемо, що компонент **чекає**. Ледачий компонент чекає на свій модуль, а пізніше ви
побачите компоненти, які чекають на дані.

Що показати замість частини, яка чекає? Відповідь дає компонент `<Suspense>`. Він має два пропси.

- `children` містить справжній вміст. Якщо щось усередині чекає, `<Suspense>` показує замість нього запасний вміст.
- `fallback` містить **запасний вміст**, тобто те, що людина бачить, поки справжній вміст не готовий. Зазвичай це
  легкий напис, значок завантаження або сірий макет майбутнього вмісту, який називають скелетом.

Межею `<Suspense>` довідник називає саме місце в дереві, де стоїть цей компонент. Коли компонент чекає, React іде від
нього вгору деревом і шукає найближчу межу. Ця межа показує свій запасний вміст замість усього, що стоїть усередині
неї. Коли модуль приходить, React пробує відрендерити вміст межі ще раз і, якщо все готове, показує його.

### Простежимо одне завантаження

Щоб побачити кожен крок, ми поставили між React і модулем «ворота»: функція завантаження чекає, поки тест не відчинить
їх викликом `open()`. Так тест сам вирішує, коли модуль «прийде з мережі».

```tsx
// lazy.test.tsx
// Ворота: модуль графіка «прийде з мережі» лише тоді, коли тест викличе open().
let open!: () => void
const gate = new Promise<void>((resolve) => (open = resolve))

const ElevationChart = lazy(async () => {
  note('React викликав load')
  await gate
  return import('./ElevationChart')
})

function Loading() {
  note('рендер Loading')
  return <p>Завантажую графік…</p>
}

function RoutePage() {
  note('рендер RoutePage')
  return (
    <main>
      <h1>Київ — Вишгород</h1>
      <Suspense fallback={<Loading />}>
        <ElevationChart />
      </Suspense>
    </main>
  )
}

test('lazy під Suspense', async () => {
  const container = document.createElement('div')
  const root = createRoot(container)
  await act(async () => root.render(<RoutePage />))
  note(`документ: ${container.textContent}`)
  await act(async () => {
    open()
    await pause(300) // чекаємо, поки модуль графіка завантажиться й React повторить рендер
  })
  note(`документ: ${container.textContent}`)
  await act(async () => root.render(<RoutePage />)) // ще один рендер сторінки
  note(`документ: ${container.textContent}`)
  console.log(journal.join('\n'))
})
```

Функція `pause` чекає задану кількість мілісекунд через `setTimeout`. Тест надрукував:

```text
рендер RoutePage
React викликав load
рендер Loading
документ: Київ — ВишгородЗавантажую графік…
рендер ElevationChart
документ: Київ — ВишгородНайвища точка: 235 м
рендер RoutePage
рендер ElevationChart
документ: Київ — ВишгородНайвища точка: 235 м
```

Ось ті самі події таблицею.

| Що сталося | Хто діє | Що в документі |
|------------|---------|----------------|
| перший рендер сторінки | React викликає `RoutePage`, доходить до `ElevationChart` і вперше викликає `load` | ще нічого |
| компонент чекає | React бачить, що модуля немає, і рендерить `fallback` найближчої межі, тобто `Loading` | заголовок і «Завантажую графік…» |
| модуль прийшов | обіцянка `load` завершилася, React повторює рендер вмісту межі й викликає `ElevationChart` | заголовок і графік |
| сторінку рендерять ще раз | React викликає `RoutePage` і `ElevationChart`, але `load` уже не викликає | заголовок і графік |

З виводу видно ще дві речі. Коли модуль прийшов, React не викликав `RoutePage` знову: він повторив рендер лише
вмісту межі. А при новому рендері сторінки рядка «React викликав load» немає, бо React запам'ятав результат першого
завантаження. Цей дослід працював у jsdom, а не в браузері, тому мережі тут не було: модуль імпортував сам Vitest.

### Що показав браузер

Тепер та сама ідея на справжній сторінці. Тут графік з'являється після клацання на кнопку «Показати графік висот»:

```tsx
const ElevationChart = lazy(() => import('./ElevationChart'))

function LazyCase() {
  const [shown, setShown] = useState(false)
  return (
    <main>
      <h1>Київ — Вишгород</h1>
      <button id="show" onClick={() => setShown(true)}>
        Показати графік висот
      </button>
      {shown && (
        <Suspense fallback={<p id="loading">Завантажую графік…</p>}>
          <ElevationChart />
        </Suspense>
      )}
    </main>
  )
}
```

### Що ще змушує межу чекати

Сторінка `<Suspense>` має розділ `What activates a Suspense boundary`, тобто перелік того, що змушує межу чекати.
Сьогодні вам знадобляться перші два пункти.

- **Код ледачого компонента.** Це те, що ви щойно бачили.
- **Обіцянка, яку компонент читає функцією `use`.** Функція `use` з React 19 читає значення обіцянки просто під час
  рендеру. Поки обіцянка не завершилася, компонент чекає. Бібліотеки даних, які довідник називає Suspense-enabled,
  тобто «вміють чекати разом із Suspense», роблять саме це: тримають кеш обіцянок і викликають `use`.

Ось приклад з довідника, де компонент альбомів читає дані через `use`. Він ілюструє, як виглядає таке читання, а не
те, як завантажувати дані у вашому застосунку:

```js
// Albums.js, приклад зі сторінки <Suspense>
import { use } from 'react';
import { fetchData } from './data.js';

export default function Albums({ artistId }) {
  const albums = use(fetchData(`/${artistId}/albums`));
  return (
    <ul>
      {albums.map(album => (
        <li key={album.id}>
          {album.title} ({album.year})
        </li>
      ))}
    </ul>
  );
}
```

Функція `fetchData` у прикладі зберігає обіцянку в `Map` за адресою, тому на кожному рендері `use` отримує ту саму
обіцянку. Сторінка `use` попереджає, що обіцянка, створена просто під час рендеру, щоразу нова, і тоді запасний вміст
показується знову й знову.

Решта пунктів переліку стосується таблиць стилів із пропсом `precedence`, серверного рендеру, шрифтів і зображень під
час анімацій. Їх ви зустрінете у фазі 4.

Важливо й те, чого в переліку немає. Перше застереження сторінки каже, що `<Suspense>` не помічає запитів, зроблених в
ефекті чи в обробнику події. На сторінці є приклад, де альбоми завантажуються в `useEffect`:

```js
// EffectAlbums.js, приклад зі сторінки <Suspense>
useEffect(() => {
  let active = true;
  fetchData(`/${artistId}/albums`).then(result => {
    if (active) {
      setAlbums(result);
    }
  });
  return () => {
    active = false;
  };
}, [artistId]);

// Suspense can't see this fetch, so its fallback never
// shows. The list stays empty until the data arrives.
```

Коментар наприкінці каже, що межа не бачить цього запиту, тому запасний вміст не з'являється, а список лишається
порожнім, поки дані не прийдуть. Компонент тут нічого не чекає: він рендериться одразу з порожнім масивом. Отже,
`<Suspense>` не замінює станів «завантаження» з лекції «Стан як набір станів екрана», якщо дані приходять через ефект.

### Де ставити межі

Межа `<Suspense>` діє на все, що стоїть усередині неї, як на одне ціле. Розділ `Revealing content together at once`
пояснює це так: якщо всередині межі чекає хоч один компонент, запасний вміст заміщує всіх, а коли все готове, усе
з'являється разом. Якщо частина має з'являтися окремо, їй дають власну межу. Розділ `Revealing nested content as it
loads` показує вкладені межі:

```js
// приклад зі сторінки <Suspense>
<Suspense fallback={<BigSpinner />}>
  <Biography />
  <Suspense fallback={<AlbumsGlimmer />}>
    <Panel>
      <Albums />
    </Panel>
  </Suspense>
</Suspense>
```

Поки біографія не готова, зовнішній запасний вміст `BigSpinner` закриває все. Коли біографія готова, вона
з'являється, а на місці альбомів стоїть внутрішній запасний вміст `AlbumsGlimmer`, доки не прийдуть альбоми.

Сторінка радить не ставити межу навколо кожного компонента. Межі мають відповідати тому порядку появи частин, який ви
хочете показати людині, а не структурі файлів. Застереження сторінки додають, що React показує готовий вміст не
частіше ніж раз на 300 мс, тому межі, які стали готовими майже одночасно, з'являються разом. Цього правила ми не
міряли.

### Коли вміст уже показано

Лекції «Пакетування оновлень» та «`useTransition` і перший замір INP» обіцяли пояснити одне явище, і тепер можна
це зробити. Уявіть вкладки «Карта» та «Фото», кожна в окремому лінивому модулі, під однією межею. Карта вже показана.
Людина перемикається на фото, а модуль фото ще не прийшов. Що має бачити людина: стару карту чи запасний вміст?

Ми зробили три кнопки, які перемикають вкладку по-різному:

```tsx
function Tabs() {
  const [tab, setTab] = useState<Tab>('map')
  return (
    <>
      <button id="map" onClick={() => setTab('map')}>Карта</button>
      <button id="photos-urgent" onClick={() => setTab('photos')}>Фото</button>
      <button id="photos-transition" onClick={() => startTransition(() => setTab('photos'))}>
        Фото в переході
      </button>
      <button id="photos-sync" onClick={() => flushSync(() => setTab('photos'))}>
        Фото через flushSync
      </button>
      <Suspense fallback={<p>Завантажую вкладку…</p>}>{tab === 'map' ? <MapTab /> : <PhotosTab />}</Suspense>
    </>
  )
}
```

Модуль фото знову стоїть за воротами, а тест натискає кнопки по черзі й друкує кожен абзац документа. Абзац, схований
стилем, тест позначає словом «[сховано]»:

```tsx
const shown = () =>
  [...container.querySelectorAll('p')]
    .map((p) => (p.style.display ? `[сховано] ${p.textContent}` : p.textContent))
    .join(' + ')
// ...
await click('photos-transition')
note(`фото в переході: ${shown()}`)
await click('map')
await click('photos-urgent')
note(`фото терміново: ${shown()}`)
note(`розмітка: ${container.innerHTML.replace(/<button.*<\/button>/, '')}`)
await click('map')
note(`назад до карти: ${shown()}`)
await click('photos-sync')
note(`фото через flushSync: ${shown()}`)
```

Vitest у jsdom надрукував:

```text
перший показ: Вкладка: карта
React викликав load вкладки фото
фото в переході: Вкладка: карта
фото терміново: [сховано] Вкладка: карта + Завантажую вкладку…
розмітка: <p style="display: none !important;">Вкладка: карта</p><p>Завантажую вкладку…</p>
назад до карти: Вкладка: карта
фото через flushSync: [сховано] Вкладка: карта + Завантажую вкладку…
модуль прийшов: Вкладка: фото
```

Рядки читаються так.

- **У переході карта лишилася на екрані.** Оновлення в `startTransition` нетермінове, тому React може почекати модуля,
  не ховаючи того, що людина вже бачить. Розділ `Preventing already revealed content from hiding` сторінки
  `<Suspense>` описує саме це.
- **Термінове оновлення сховало карту.** Звичайний виклик `setTab` терміновий, а React не відкладає термінового
  рендеру. Тому межа показала запасний вміст. Розмітка показує цікаву річ: React не видалив абзац карти з документа, а
  сховав його стилем `display: none !important`. Коли тест після цього натиснув «Карта», журнал показав рядок `назад
  до карти: Вкладка: карта` без позначки «[сховано]»: React просто зняв стиль, бо абзац увесь час лишався в документі.
- **`flushSync` зробив те саме, що й термінове оновлення.** Лекція «Пакетування оновлень» показала, що `flushSync`
  змушує React виконати оновлення негайно. Негайне оновлення не можна відкласти, тому застереження довідника
  `flushSync` і каже, що ця функція може змусити межу показати запасний вміст.

Довідник додає ще два способи керувати цим. Перший спосіб вам знайомий з лекції «`useDeferredValue`»: якщо межа чекає
через відкладене значення, людина бачить старий вміст, а не запасний. Другий спосіб працює навпаки. Коли людина
переходить до зовсім іншого вмісту, наприклад до профілю іншої людини, старий вміст лишати не треба. Тоді межі дають
інший `key`, і React вважає її новою межею, тож показує запасний вміст. Як `key` скидає стан, пояснила лекція
«Спільний стан і скидання стану».

### Ще три застереження

- **Стан не зберігається до першого показу.** Якщо частина дерева почала чекати ще до того, як її вперше показали,
  React не зберігає для неї жодного стану. Коли все готове, React рендерить її з нуля.
- **`lazy` оголошують на верхньому рівні модуля.** Розділ `Troubleshooting` сторінки `lazy` попереджає: якщо викликати
  `lazy` усередині компонента, кожен рендер створить новий тип компонента. Тоді React вважатиме його іншим компонентом
  і скидатиме весь його стан. Цього випадку ми не відтворили надійно, тому спирайтеся тут на довідник.
- **Ефекти `useLayoutEffect` прибираються, поки вміст схований.** Так називають ефекти, які React виконує ще до того,
  як браузер намалює кадр, і ними зазвичай міряють розміри елементів. Коли React ховає вже показаний вміст, він
  виконує функції прибирання цих ефектів, а коли показує вміст знову, запускає ефекти заново. Так код, який міряє
  розміри, не міряє схованого елемента.

## Клас, без якого не обійтися

Тепер друга неприємність, помилка в списку зупинок. Компонент, який ловить помилки рендеру, React досі дає записати
лише класом. Сторінка `Component` каже прямо, що функцією такий компонент написати поки що не можна. Класів ви в
React ще не писали, а лекція «Значення й посилання» згадала їх лише побіжно, тому почнемо з самої мови.

### Клас у JavaScript у потрібному обсязі

**Клас** є шаблоном, за яким оператор `new` створює об'єкти з однаковими полями й методами. Ось лічильник кілометрів
велосипеда:

```js
// classes.mjs
class Odometer {
  km = 0 // поле класу: у кожного об'єкта своє

  constructor(owner) {
    this.owner = owner // this тут означає об'єкт, який створює new
  }

  ride(distance) {
    this.km += distance // метод бачить свій об'єкт через this
    return this.km
  }

  static fromTrip(owner, trips) {
    // статичний метод належить самому класу, а не об'єктам
    const o = new Odometer(owner)
    for (const t of trips) o.ride(t)
    return o
  }
}

const mine = new Odometer('Оля')
mine.ride(12.5)
mine.ride(9.4)
const yours = Odometer.fromTrip('Петро', [24.1])
console.log(mine.owner, mine.km, '|', yours.owner, yours.km)
console.log('ride у прототипі:', typeof Odometer.prototype.ride, '| fromTrip у класі:', typeof Odometer.fromTrip)
console.log('fromTrip в об’єкта:', typeof mine.fromTrip)
```

```text
$ node classes.mjs
Оля 21.9 | Петро 24.1
ride у прототипі: function | fromTrip у класі: function
fromTrip в об’єкта: undefined
```

Розберімо рядок за рядком.

- `class Odometer { ... }` оголошує клас. Усередині фігурних дужок стоять поля й методи, без ком між ними.
- `km = 0` є **полем класу**. Кожен об'єкт, створений через `new`, отримує власне поле `km` зі значенням 0.
- `constructor(owner)` є функцією, яку `new Odometer('Оля')` викликає першою. Слово **`this`** усередині означає
  об'єкт, що зараз створюється, тому `this.owner = owner` записує в нього поле.
- `ride(distance)` є **методом**. Метод записано без слова `function`. Коли ви викликаєте `mine.ride(12.5)`, `this`
  усередині дорівнює `mine`. Тому `mine.km` після двох поїздок дорівнює 21.9, а `yours.km` має своє окреме значення.
- `static fromTrip(...)` є **статичним методом**. Він належить самому класу: його викликають як `Odometer.fromTrip`, а
  в об'єкта `mine` такого методу немає, і тому `typeof mine.fromTrip` дає `undefined`.

Друга частина того самого файла показує, як один клас продовжує інший:

```js
// extends: новий клас бере все від старого й додає своє. super(...) викликає конструктор батька.
class EbikeOdometer extends Odometer {
  battery = 100

  constructor(owner, capacityKm) {
    super(owner) // до цього рядка this ще не можна чіпати
    this.capacityKm = capacityKm
  }

  ride(distance) {
    this.battery -= (distance / this.capacityKm) * 100
    return super.ride(distance) // метод батька
  }
}

const e = new EbikeOdometer('Ліна', 80)
e.ride(20)
console.log(e.owner, e.km, Math.round(e.battery) + '%', e instanceof Odometer)

// Метод, відірваний від об'єкта, губить this.
const ride = mine.ride
try {
  ride(1)
} catch (err) {
  console.log('відірваний метод:', err.constructor.name, err.message)
}
```

```text
Ліна 20 75% true
відірваний метод: TypeError Cannot read properties of undefined (reading 'km')
```

- `extends Odometer` означає, що `EbikeOdometer` отримує всі поля й методи `Odometer` і може додати свої. Такий
  зв'язок називають **наслідуванням**, а `Odometer` тут є батьківським класом.
- `super(owner)` викликає конструктор батька. У класі з `extends` цей виклик має стояти перед будь-яким звертанням до
  `this`, інакше JavaScript кине помилку.
- `super.ride(distance)` викликає метод батька, коли власний метод має те саме ім'я.
- Останній приклад показує пастку. Коли метод забрали з об'єкта й викликали окремо, `this` усередині вже не вказує
  на об'єкт і дорівнює `undefined`. Тому в класах React обробники подій пишуть як поле зі стрілковою функцією, яка
  запам'ятовує `this` свого об'єкта. Межі помилок обробники зазвичай не потрібні, але ви побачите такий запис у
  прикладах `setState`.

### Компонент-клас у React

React має вбудований клас `Component`. Ваш клас компонента продовжує його через `extends` і має метод `render`, який
повертає JSX. Сторінка `Component` показує найпростіший приклад:

```js
// приклад зі сторінки Component
import { Component } from 'react';

class Greeting extends Component {
  render() {
    return <h1>Hello, {this.props.name}!</h1>;
  }
}
```

У функції-компоненті пропси приходять аргументом, а в класі вони лежать у полі `this.props`. Стан класу лежить у полі
`this.state`, яке має бути об'єктом, а змінюють його методом `this.setState`. Хуки, тобто функції на `use`, у класах
не працюють. Метод `render` має бути чистим, як і функція-компонент: React може викликати його будь-коли й скільки
завгодно разів. Сторінка `Component` радить писати нові компоненти функціями. Межа помилок є винятком, і в плані це
єдине місце, де вам потрібен клас.

У TypeScript клас `Component` приймає два параметри типу: пропси і стан. Запис `class X extends Component<Props,
State>` каже компілятору, які поля мають `this.props` і `this.state`. Як працюють параметри типу, пояснила лекція
«TypeScript: дженерики».

## Межа помилок

### Що робить межа

**Межа помилок** є компонентом-класом, який ловить помилки, кинуті під час рендеру його нащадків, і показує замість
них запасний екран. Нащадками тут називають усі компоненти всередині межі, хоч би як глибоко вони стояли. Межа
ловить помилки лише нижче себе, а частини сторінки поза нею живуть далі.

Межа має два методи, які відрізняють її від звичайного класу.

- **`static getDerivedStateFromError(error)`.** React викликає цей статичний метод, коли нащадок кинув помилку під час
  рендеру. Метод отримує кинуте значення й повертає новий стан межі, після якого її `render` покаже запасний екран.
  Довідник вимагає, щоб цей метод був чистою функцією: жодних запитів, жодного запису в журнал.
- **`componentDidCatch(error, info)`.** React викликає цей метод після того, як межа вже показала запасний екран.
  Тут дозволено побічні дії, наприклад надіслати звіт збирачу помилок. Об'єкт `info` має поле `componentStack`.

Обидва методи отримують `error`. Довідник нагадує, що JavaScript дозволяє кинути будь-що, навіть рядок чи `null`, тому
`error` не завжди є об'єктом `Error`. Через це в TypeScript його тип `unknown`, і перш ніж читати `error.message`,
його звужують перевіркою `error instanceof Error`.

Ось приклад межі зі сторінки `Component`, розділ `Catching rendering errors with an Error Boundary`:

```js
// приклад зі сторінки Component
import * as React from 'react';

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Update state so the next render will show the fallback UI.
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    logErrorToMyService(
      error,
      // Example "componentStack":
      //   in ComponentThatThrows (created by App)
      //   in ErrorBoundary (created by App)
      //   in div (created by App)
      //   in App
      info.componentStack,
      // Warning: `captureOwnerStack` is not available in production.
      React.captureOwnerStack(),
    );
  }

  render() {
    if (this.state.hasError) {
      // You can render any custom fallback UI
      return this.props.fallback;
    }

    return this.props.children;
  }
}
```

Розберімо його за частинами.

- Конструктор викликає `super(props)` і задає початковий стан `{ hasError: false }`. Сучасний запис обходиться без
  конструктора: поле класу `state = { hasError: false }` робить те саме, і сторінка `Component` показує такий варіант
  у розділі про `constructor`.
- `getDerivedStateFromError` повертає `{ hasError: true }`. React зливає цей об'єкт зі станом межі, і наступний виклик
  `render` бачить `hasError`.
- `componentDidCatch` передає помилку й стек компонентів у функцію `logErrorToMyService`, якої в прикладі немає: це
  місце для вашого збирача помилок. Виклик `React.captureOwnerStack()` додає ще один вид стека, про який розповідає
  розділ «Стек компонентів і стек власників».
- `render` повертає `this.props.fallback`, тобто запасний екран, переданий пропсом, або `this.props.children`, тобто
  звичайний вміст.

Межу ставлять навколо частини дерева так само, як `<Suspense>`:

```js
<ErrorBoundary fallback={<p>Something went wrong</p>}>
  <Profile />
</ErrorBoundary>
```

Для досліду ми написали власну межу на TypeScript. Вона робить те саме, але ще записує кожен виклик у журнал досліду:

```tsx
// RouteErrorBoundary.tsx
import { Component, type ErrorInfo, type ReactNode } from 'react'
import { note } from './log'

type Props = { fallback: ReactNode; children: ReactNode }
type State = { hasError: boolean }

export class RouteErrorBoundary extends Component<Props, State> {
  state: State = { hasError: false }

  static getDerivedStateFromError(error: unknown): State {
    note(`getDerivedStateFromError: ${String(error)}`) // лише для досліду: справжній метод має бути чистим
    return { hasError: true }
  }

  componentDidCatch(error: unknown, info: ErrorInfo) {
    note(`componentDidCatch: ${String(error)}`)
    note(`componentStack:${info.componentStack}`)
  }

  render() {
    note(`рендер RouteErrorBoundary, hasError=${this.state.hasError}`)
    if (this.state.hasError) return this.props.fallback
    return this.props.children
  }
}
```

Тип `ErrorInfo` з пакета `react` описує другий аргумент `componentDidCatch`. Тип `ReactNode` означає будь-що, що можна
відрендерити: JSX, рядок, число чи `null`. Виклик `note` у `getDerivedStateFromError` порушує вимогу чистоти, і ми
зробили це лише заради журналу. Лінтер шаблону цей файл пропустив без зауважень.

### Простежимо одну помилку

Тепер компонент `Page` отримує `guarded={true}` і огортає список зупинок межею:

```tsx
function Page({ stops, guarded }: { stops: Stop[]; guarded: boolean }) {
  const list = <StopList stops={stops} />
  return (
    <main>
      <h1>Київ — Вишгород</h1>
      {guarded ? (
        <RouteErrorBoundary fallback={<p>Зупинки не вдалося показати.</p>}>{list}</RouteErrorBoundary>
      ) : (
        list
      )}
    </main>
  )
}
```

Корінь цього разу отримав два параметри, про які докладно розповідає розділ «Куди React повідомляє про помилки».
Зараз досить знати, що `onCaughtError` записує в журнал кожну помилку, яку зловила межа, разом зі стеком компонентів:

```tsx
const root = createRoot(container, {
  onCaughtError: (error, info) => note(`onCaughtError: ${String(error)} | стек: ${stack(info)}`),
  onUncaughtError: (error, info) => note(`onUncaughtError: ${String(error)} | стек: ${stack(info)}`),
})
await act(async () => root.render(<Page stops={BROKEN_STOPS} guarded={true} />))
note(`документ: ${container.textContent}`)
```

Функція `stack` склеює рядки стека через косу риску, щоб вони вмістилися в один рядок журналу. Тест надрукував таке.

Пройдімо журнал по порядку.

1. **Рендер почався звичайно.** React викликав межу з `hasError=false`, і межа повернула свої діти. React викликав

   викликав її `getDerivedStateFromError` і відрендерив її знову, тепер з `hasError=true`, тобто з запасним екраном.
3. **React спробував ще раз.** Друга половина журналу повторює першу: межа знову з `hasError=false`, знову три рядки,
   знову помилка. Так React перевіряє, чи помилка не була випадковою. У вихідному коді `react-dom` 19.3.1 видно, що
   після рендеру, який закінчився помилкою, React ще раз рендерить усе синхронно, тобто без перерв. Якщо друга спроба
   пройде, людина побачить справжній вміст, а React повідомить про помилку як про відновлювану. Таку помилку покаже
   розділ «Помилка, від якої React оговтався». Тут друга спроба теж упала.
4. **React показав запасний екран.** Після другої невдалої спроби React записав у документ межу з запасним екраном.
   Заголовок сторінки лишився, бо він стоїть поза межею.
5. **React повідомив про помилку.** Спершу він викликав `onCaughtError` кореня, а потім `componentDidCatch` межі.
   Обидва отримали ту саму помилку й той самий стек компонентів.

Дві спроби рендеру пояснюють і подвійний прохід у розділі «Дві неприємності на одній сторінці»: там межі не було, але
React так само пробував удруге.

**Стек компонентів** є переліком компонентів від того, що впав, до кореня. Кожен рядок починається словом `at` і
називає компонент, а якщо це ваш компонент, то й файл, рядок та стовпчик. Рядки `at ol` і `at main` належать тегам
HTML, тому файла в них немає. Звичайний **стек викликів** помилки, тобто поле `error.stack`, показує інше: функції
JavaScript, які викликали одна одну, зокрема внутрішні функції React. Стек компонентів відповідає на питання, де в
дереві сталася помилка: у рядку зупинки, всередині списку, всередині межі, на сторінці маршруту.

### Що межа не ловить

Сторінка `Component` має примітку з чотирма винятками. Межа помилок не ловить помилок в обробниках подій, під час
рендеру на сервері, у самій межі та в асинхронному коді, як-от у функціях `setTimeout` чи `requestAnimationFrame`.
Для асинхронного коду там же названо виняток: помилку у функції, переданій у `startTransition` з хука `useTransition`,
межа ловить. Ми перевірили кожен пункт, крім серверного рендеру.

**Помилка в обробнику клацання.** Кнопка експорту кидає помилку просто в `onClick`:

```tsx
function ExportButton() {
  return (
    <button
      id="export"
      onClick={() => {
        throw new Error('GPX: немає координат')
      }}
    >
      Експортувати GPX
    </button>
  )
}
```

Сторінка досліду в браузері ставить кнопку всередину межі разом зі справним списком зупинок і слухає подію `error`
вікна. Це подія, яку браузер надсилає, коли помилку ніхто не перехопив:

```tsx
window.addEventListener('error', (e) => console.log('[window error]', String(e.error)))
// ...
<RouteErrorBoundary fallback={<p id="fallback">Експорт зламався.</p>}>
  <StopList stops={STOPS} />
  <ExportButton />
</RouteErrorBoundary>
```

Скрипт клацнув на кнопку справжніми подіями миші, тобто командою протоколу `Input.dispatchMouseEvent`. І в режимі
розробки, і в продакшн-збірці він надрукував те саме:

```text
console.log: [window error] Error: GPX: немає координат
exception: Uncaught Error: GPX: немає координат
документ наприкінці: "Київ — Вишгород0 км, Поштова площа (50.459, 30.525)9.4 км, Оболонська набережна (50.500, 30.516)17.8 км, Гідропарк Вишгород (50.575, 30.489)24.1 км, Межигір’я (50.620, 30.462)Експортувати GPX"
```

Межа нічого не помітила: запасного екрана немає, сторінка ціла. Помилка дійшла до вікна, і консоль Chrome показала її
як `Uncaught Error`, тобто як помилку, яку ніхто не перехопив. Чому так, видно у вихідному коді `react-dom` 19.3.1.
React викликає ваш обробник у `try/catch`, а в `catch` передає помилку функції браузера `reportError`. Ця функція
повідомляє про помилку так, ніби її ніхто не перехопив, і браузер надсилає подію `error` вікна. Обробник виконується,
коли рендер давно закінчився, тому межі вже нема що показувати: дерево ціле, а зламалася лише дія.

**Помилка в `setTimeout`.** Компонент прогнозу погоди запускає таймер в ефекті, і функція таймера кидає помилку через
100 мс:

```tsx
function Forecast() {
  useEffect(() => {
    const id = setTimeout(() => {
      throw new Error('таймер: прогноз не прийшов')
    }, 100)
    return () => clearTimeout(id)
  }, [])
  return <p>Прогноз погоди</p>
}
```

Сторінка ставить `Forecast` усередину межі із запасним екраном «Прогноз зламався.». У браузері, в обох збірках,
скрипт надрукував:

```text

exception: Uncaught Error: таймер: прогноз не прийшов
документ наприкінці: "Прогноз погоди"
```

Функцію таймера викликає браузер, а не React, тому React про цю помилку навіть не знає. У Vitest той самий компонент
дав інший результат: таймери там належать Node, і Vitest повідомив про помилку як про `Uncaught Exception` поза
тестом. Тому цей випадок ми показуємо з браузера.

розділі `Troubleshooting`, що окрема функція `startTransition`, імпортована з `react` без хука, не пов'язана з жодним
компонентом, тому її помилок межа не зловить.

**Відхилене завантаження `lazy`.** Модуль може не прийти. Після нового викоту на сервері вже немає старих файлів, а
вкладка, відкрита вчора, просить саме їх. Ми імітували це функцією завантаження, яка кидає помилку:

Текст помилки ми взяли такий, який зазвичай дає Chrome, коли не може завантажити динамічний модуль. Справжнього
збою мережі в цьому досліді не було. Тест надрукував, зокрема:

```text

документ: Графік не завантажився.
```

`<Suspense>` не займається помилками, тому помилку завантаження ловить межа помилок над ним. Стек компонентів називає
ледачий компонент словом `Lazy`. Тому `lazy` і межу помилок зазвичай ставлять разом: одна показує очікування, друга
показує збій.

**Помилка в самій межі.** Межа не ловить власних помилок, зокрема помилок свого запасного екрана. Ми поставили одну
межу всередину іншої, а запасний екран внутрішньої межі сам кидає помилку:

```tsx
function Fallback(): ReactNode {
  throw new Error('запасний екран теж зламався')
}
// ...
<RouteErrorBoundary fallback={<p>Зовнішня межа: щось пішло не так.</p>}>
  <section>
    <h2>Зупинки</h2>
    <RouteErrorBoundary fallback={<Fallback />}>
      <StopList stops={BROKEN_STOPS} />
    </RouteErrorBoundary>
  </section>
</RouteErrorBoundary>
```

Ось кінець журналу:

```text
getDerivedStateFromError: TypeError: Cannot read properties of null (reading 'lat')
рендер RouteErrorBoundary, hasError=true
getDerivedStateFromError: Error: запасний екран теж зламався
рендер RouteErrorBoundary, hasError=true
onCaughtError: Error: запасний екран теж зламався | стек: at Fallback (…/spa/src/lab/errors.test.tsx:242:8) / at RouteErrorBoundary (…/spa/src/lab/RouteErrorBoundary.tsx:7:1) / at section (<anonymous>) / at RouteErrorBoundary (…/spa/src/lab/RouteErrorBoundary.tsx:7:1)
componentDidCatch: Error: запасний екран теж зламався
документ: Зовнішня межа: щось пішло не так.
```

Внутрішня межа отримала `TypeError` і спробувала показати свій запасний екран. Запасний екран упав, і помилку зловила
зовнішня межа, тож зник увесь розділ із заголовком «Зупинки». Важливіше інше: у журналі є лише одне повідомлення
`onCaughtError` і один `componentDidCatch`, і обидва про помилку запасного екрана. Про справжню причину, зупинку без
координат, жодного повідомлення немає, бо внутрішня межа так і не показала свого запасного екрана. Висновок для
практики простий: запасний екран має бути найпростішим кодом на сторінці, без звертань до тих самих даних, що
зламалися.

Ось підсумок усіх перевірок.

| Де кинуто помилку | Чи ловить межа | Куди потрапила помилка в нашому запуску |
|-------------------|----------------|-----------------------------------------|
| рендер нащадка | так | запасний екран, `onCaughtError`, `componentDidCatch` (Vitest і браузер) |
| `useEffect` нащадка | так | те саме (Vitest) |
| функція переходу з `useTransition` | так | те саме (Vitest) |
| відхилене завантаження `lazy` | так | те саме, у стеку `Lazy` (Vitest) |
| обробник `onClick` | ні | подія `error` вікна, `Uncaught Error` у консолі (браузер, обидві збірки) |
| функція `setTimeout` | ні | подія `error` вікна, `Uncaught Error` у консолі (браузер, обидві збірки) |
| запасний екран межі | ні, ловить зовнішня межа | зовнішня межа; початкова помилка не потрапила в журнал (Vitest) |
| рендер на сервері | ні, за довідником | не перевіряли |

### `try/catch`: де він працює, а де ні

Перша думка, яка спадає на думку, звучить так: огорнути JSX у `try/catch`. Ми спробували:

```tsx
// TryCatchPage.tsx

  try {
    return <StopList stops={stops} />
  } catch {
    return <p>Зупинки не вдалося показати.</p>
  }
}
```

Тест відрендерив цей компонент із `BROKEN_STOPS`:


`catch` не спрацював, і сторінка знову порожня. Причину пояснила лекція «JSX»: вираз `<StopList stops={stops} />`
лише створює об'єкт-опис елемента. Сам `StopList` React викликає пізніше, коли `TryCatchPage` уже повернув цей опис і
вийшов із `try`. Лінтер шаблону знає цю пастку. Правило `react-hooks/error-boundaries` з пакета
`eslint-plugin-react-hooks` 7.1.1 надрукувало для цього файла:

```text

React does not immediately render components when JSX is rendered, so any errors from this component will not be caught by the try/catch. To catch errors in rendering a given component, wrap that component in an error boundary. (https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).
```

Зате в обробнику події `try/catch` працює звичайно, бо обробник викликає ваш код одразу й повністю:

```tsx
function SafeExport() {
  const [message, setMessage] = useState('')
  return (
    <>
      <button
        onClick={() => {
          try {
            throw new Error('GPX: немає координат')
          } catch (e) {
            note(`catch в обробнику: ${String(e)}`)
            setMessage('Не вдалося експортувати: у маршруті є зупинка без координат.')
          }
        }}
      >
        Експортувати GPX
      </button>
      <p>{message}</p>
    </>
  )
}
```

```text

```

Отже, правило таке. Помилки рендеру ловить межа, бо рендер викликає React, і лише React знає, де межа. Помилки
обробників ловить `try/catch` усередині самого обробника, а повідомлення для людини ви кладете в стан. Якщо в
обробнику є `await`, `try/catch` має охоплювати і його, як показала лекція «Асинхронність».

### Скільки меж і де

Розділ про межі на сторінці `Component` закінчується порадою, яку варто запам'ятати. Огортати кожен компонент окремою
межею не потрібно. Межу ставлять там, де людині має сенс побачити повідомлення про помилку. Довідник наводить приклад
програми повідомлень: межу варто поставити навколо списку розмов і навколо кожного повідомлення, але не навколо
кожного аватара. На нашій сторінці маршруту межа потрібна навколо списку зупинок і навколо графіка, а заголовок і
кнопки лишаються поза ними.

Межа, яка вже показала запасний екран, сама з нього не виходить: її стан `hasError` лишається `true`. Щоб спробувати
ще раз, межі дають новий `key`, і React створює її заново. Інший спосіб полягає в тому, щоб запасний екран мав кнопку,
яка скидає стан межі через `this.setState`. Довідник радить не писати власного класу в кожному проєкті, а написати
один і користуватися ним усюди або взяти готовий пакет `react-error-boundary`. Практика дня просить власний клас, щоб
ви побачили, як він влаштований.

## Куди React повідомляє про помилки

### Три параметри `createRoot`

Функція `createRoot` приймає другим аргументом об'єкт параметрів. Три з них стосуються помилок, і всі три отримують
два аргументи: помилку та об'єкт `errorInfo` з полем `componentStack`.

- **`onCaughtError`** React викликає, коли межа помилок зловила помилку.
- **`onUncaughtError`** React викликає, коли помилку не зловила жодна межа. Після цього React прибирає з екрана весь
  інтерфейс кореня.
- **`onRecoverableError`** React викликає, коли він сам оговтався від помилки, і людина нічого не помітила.

Ці параметри з'явилися в React 19. Посібник з переходу на React 19 пояснює причину в розділі `Errors in render are not
re-thrown`: раніше React ловив помилку рендеру й кидав її ще раз, а в режимі розробки ще й друкував у консоль, і одна
помилка давала кілька записів. Тепер помилку, яку ніхто не зловив, React передає функції `window.reportError`, а
помилку, яку зловила межа, друкує через `console.error`. Хто хоче надсилати помилки збирачу, підключається через ці
три параметри.

### Що друкує React без ваших обробників

### Ваші обробники замість типових

Тепер та сама сторінка, але корінь отримує власні обробники. Сторінка досліду вмикає їх параметром адреси `h=custom`:

```tsx
const options: RootOptions =
  params.get('h') === 'custom'
    ? {
        onCaughtError: (error, info) => {
          console.log('[onCaughtError]', String(error), '\n[componentStack]', info.componentStack)
        },
        onUncaughtError: (error, info) => {
          console.log('[onUncaughtError]', String(error), '\n[componentStack]', info.componentStack)

  <StrictMode>
    <Page />
  </StrictMode>,
)
```

  розшифровують і звичайні стеки викликів.
- **Теги HTML мають справжні імена в обох збірках.** Рядки `at ol` і `at main` збирач не чіпає, бо це назви тегів, а
  не функцій.

### Помилка в обробнику іде повз корінь

Для сторінки з кнопкою експорту власні обробники нічого не змінили. Скрипт відкривав ту саму сторінку з кнопкою
експорту, що й у розділі «Що межа не ловить», тепер із параметром `h=custom`, і клацав на кнопку. Перший аргумент
команди є адресою сервера розробки, а для продакшн-збірки скрипт отримував адресу `vite preview`:

```bash
node run.mjs http://localhost:5281 click custom
node run.mjs http://localhost:5282 click custom
```

В обох збірках скрипт надрукував те саме, що й без обробників:

```text
console.log: [window error] Error: GPX: немає координат
exception: Uncaught Error: GPX: немає координат
```

Рядка `[onUncaughtError]` тут немає. Помилки обробників подій React передає просто в `reportError`, і параметри
кореня їх не бачать. Це той самий шлях, що й для помилки в `setTimeout`. Тому збирачі помилок слухають і подію
`error` вікна, і параметри кореня. Документація Sentry пропонує перевірити підключення саме кнопкою, яка кидає
помилку в `onClick`. Як показав наш дослід, таку помилку бачить подія `error` вікна, а не межа і не параметри
кореня.

### Помилка, від якої React оговтався

Повторна спроба рендеру, яку ви бачили в розділі «Простежимо одну помилку», іноді вдається. Ми зробили значок, який
падає лише на першому виклику:

```tsx
let flaky = 0
function FlakyBadge() {
  flaky++
  note(`рендер FlakyBadge, спроба ${flaky}`)
  if (flaky === 1) throw new Error('значок: перша спроба впала')
  return <p>Значок маршруту</p>
}
```

Корінь цього досліду мав обробник `onRecoverableError`, який друкує помилку і її поле `cause`:

```tsx
onRecoverableError: (error) =>
  note(`onRecoverableError: ${String(error)} | cause: ${String((error as Error).cause)}`),
```

```text
рендер RouteErrorBoundary, hasError=true
рендер RouteErrorBoundary, hasError=false
рендер FlakyBadge, спроба 3
onRecoverableError: Error: There was an error during concurrent rendering but React was able to recover by instead synchronously rendering the entire root. | cause: Error: значок: перша спроба впала
документ: Значок маршруту
```

Людина побачила справжній значок, а не запасний екран. Межа на мить отримала `hasError=true`, але цей рендер не дійшов
до документа, бо повторна синхронна спроба від кореня вдалася. Обробник `onCaughtError` не спрацював. Натомість React
викликав `onRecoverableError` з власною помилкою, яка пояснює, що сталося, а початкову помилку поклав у поле
`cause`. Довідник `createRoot` згадує це поле: деякі відновлювані помилки несуть початкову причину в `error.cause`.
Компонент, який то падає, то ні, найчастіше залежить від чогось змінного поза пропсами й станом, тобто порушує
чистоту. Тому `onRecoverableError` теж варто надсилати збирачу.

### Чому в тестах `onUncaughtError` мовчить

У розділі «Дві неприємності на одній сторінці» корінь мав обробник `onUncaughtError`, але журнал не містить жодного
рядка від нього. Натомість `act` кинув помилку. Причина є у вихідному коді `react-dom` 19.3.1: функція, яка
повідомляє про помилку без межі, перевіряє, чи код виконується всередині `act`. Якщо так, React складає помилку в
окремий список, а `act` кидає її наприкінці, щоб тест упав. Обробник кореня в цьому разі не викликається. Отже,
перевіряти `onUncaughtError` треба в браузері, а в тесті під `act` ви побачите лише кинуту помилку.

### Стек компонентів і стек власників

Приклад межі на сторінці `Component` викликає ще `React.captureOwnerStack()`. **Стек власників** показує не те, де
компонент стоїть у дереві, а те, хто його створив, тобто в якому компоненті написано JSX, що його рендерить. Сторінка
`captureOwnerStack` каже, що ця функція існує лише в режимі розробки, а в продакшн-збірці її немає. У пакеті `react`
19.3.1 її справді немає у файлі продакшн-збірки. Тому код, який іде в обидві збірки, має викликати її лише за умови
режиму розробки, як показує розділ `Troubleshooting` тієї сторінки. Якщо скопіювати приклад межі як є, виклик
`React.captureOwnerStack()` у продакшн-збірці кине `TypeError`, бо `undefined` не можна викликати.

### Куди підключають збирач помилок

**Збирач помилок** є сервісом, який отримує звіти про помилки з браузерів користувачів, групує їх і показує, що впало,
у кого й скільки разів. Сьогодні ви його не підключаєте, це план Next.js, фаза 7, день 9. Але читання дня показує, як
його підключають до тих самих параметрів кореня. Документація Sentry для React 19 радить передати в усі три параметри
`createRoot` функцію `Sentry.reactErrorHandler()`. Межі помилок вона лишає завдання показати запасний екран для своєї
частини сторінки. Розбір читання показує ці приклади докладно. Вам зараз досить помітити, що ваш обробник
`onCaughtError` з практики стоїть саме там, куди пізніше стане обробник збирача.

## Що записати в журнал

Сьогоднішній день не просить нового числа INP. Проте `lazy` є оптимізацією, і головне правило фази каже міряти її до
й після. Найпростіше число для цього — розмір головного JS-файла після gzip зі звіту збірки, як у лекції «Збірка,
перший викот і журнал вимірів». Для нашої сторінки маршруту рядок міг би бути таким:

```text
| дата | Графік висот через lazy під <Suspense>; vite build | головний JS 96.84 → 70.51 kB gzip, окремий чанк 26.46 kB | — | — | — |
```

Колонки журналу у вас можуть бути іншими. Головне, щоб у рядку стояли обидва числа й те, як їх отримано.

## Типові хибні уявлення

**«Межа помилок ловить усі помилки всередині себе».** Помилку в `onClick` межа не зловила ні в режимі розробки, ні в
продакшн-збірці: вона дійшла до події `error` вікна, а сторінка лишилася цілою. Помилку в `setTimeout` межа теж не
зловила.

**«Досить огорнути JSX у `try/catch`».** Компонент усередині JSX React викликає пізніше, коли функція вже вийшла з
`try`. У нашому досліді `catch` не спрацював, документ став порожнім, а лінтер позначив цей код правилом
`react-hooks/error-boundaries`.

**«Межа ловить лише помилки рендеру, тому помилка в ефекті вб'є сторінку».** Помилку з `useEffect` межа в нашому
досліді зловила й показала запасний екран. Не ловить вона помилок у коді, який викликає не React, а браузер:
обробники, таймери, функції після `await`.

**«`<Suspense>` показує запасний вміст, поки ефект завантажує дані».** Межа не бачить запитів з ефектів. Вона реагує
лише на ледачий код і на обіцянки, які читає `use`.

**«Ледачий компонент завжди пришвидшує сторінку».** Виграш є лише тоді, коли важкий модуль потрібен не одразу. У
нашому замірі перше малювання настало приблизно на 130 мс раніше, але графік після клацання чекав ще 545 мс. Для
компонента, який видно на кожному відкритті, це лише зайвий запит.

**«Якщо я передав `onCaughtError`, React далі друкує свою помилку».** Ваш обробник заміняє типовий. З власним
`onUncaughtError` зникли і запис у консолі, і подія `error` вікна.

**«Стек компонентів у продакшн-збірці марний».** Він є, тільки імена стиснуті: `y` замість `StopRow`, `h` замість
межі. Карти коду повертають справжні імена.

**«Запасний екран можна зробити будь-яким».** Якщо він сам упаде, помилку зловить зовнішня межа, а початкова причина
не потрапить у жоден обробник. Запасний екран має бути найпростішим кодом на сторінці.

## Як це проявиться далі в React

- **Фаза 3, день «Маршрути».** Довідник очікує від маршрутизаторів із підтримкою Suspense, що вони загортають
  навігацію в перехід. Тоді стара сторінка лишається на екрані, поки нова завантажується, як вкладка карти в
  сьогоднішньому досліді.
- **Фаза 4, день «Стрімінг на сервері».** Сервер надсилає HTML частинами, і межі `<Suspense>` визначають ці частини:
  спершу йде все, що стоїть над межами, разом із запасним вмістом, а потім вміст кожної межі. Пастка того дня, одна
  межа над усією сторінкою, є продовженням сьогоднішньої поради про те, де ставити межі.
- **Фаза 5, день «Розділення коду».** Там ви розділятимете код за маршрутами, і `lazy` під `<Suspense>` буде одним із
  двох способів.
- **Фаза 5, день «Викот статики як слід».** Стара вкладка після викоту просить чанк, якого вже немає на сервері. Це
  відхилене завантаження `lazy`, яке ловить межа помилок і пропонує оновити сторінку.
- **План Next.js, фаза 7, день 9.** Там до параметрів `createRoot`, які ви сьогодні заповнили власним кодом,
  підключають збирач помилок і карти коду.

## Перевірте себе

**1. Компонент `Report` огорнуто в `lazy`, а вище в дереві немає жодної межі `<Suspense>`. Ви ставите межу навколо
`<App />` у `main.tsx`. Що побачить людина, поки модуль звіту вантажиться, і чому ця межа погана?**

<details><summary>Відповідь</summary>

Найближчою межею буде межа навколо всього застосунку, тому її запасний вміст закриє всю сторінку, хоча чекає лише
звіт. Межу варто поставити безпосередньо навколо `Report` чи навколо тієї частини, яка має з'являтися разом із ним.

</details>

**2. Ви клацаєте на кнопку, яка вперше показує ледачий компонент. Через скільки після клацання браузер просить файл
компонента і що людина бачить до його приходу?**

<details><summary>Відповідь</summary>

Браузер просить файл, щойно React уперше рендерить ледачий компонент, тобто одразу після клацання: у нашому замірі
через 5 мс. Поки файл іде, найближча межа `<Suspense>` показує свій `fallback`. Наступні рендери файла вже не просять,
бо React запам'ятовує результат `load`.

</details>

**3. Вкладка вже показана, а людина перемикається на іншу, ледачу. Як зробити, щоб стара вкладка лишалася на екрані,
поки нова вантажиться, і що станеться, якщо перемикання загорнути у `flushSync`?**

<details><summary>Відповідь</summary>

Перемикання загортають у `startTransition`. Нетермінове оновлення дозволяє React почекати модуля, не ховаючи
показаного вмісту. `flushSync` робить оновлення негайним, а негайне оновлення відкласти не можна, тому межа сховає
стару вкладку стилем `display: none` і покаже запасний вміст.

</details>

**4. Навіщо межі два методи? Чому не можна записати звіт збирачу в `getDerivedStateFromError`?**

<details><summary>Відповідь</summary>

`getDerivedStateFromError` React викликає під час рендеру, щоб отримати новий стан межі. Він має бути чистим, бо
рендер може повторюватися, як у нашому досліді, де React двічі пробував відрендерити зламаний список.
`componentDidCatch` React викликає один раз, коли запасний екран уже в документі, і тут дозволено побічні дії, зокрема
звіт збирачу.

</details>

**5. Кнопка «Зберегти» кидає помилку в `onClick`. Межа навколо кнопки нічого не показала. Чому, і як показати людині
повідомлення?**

<details><summary>Відповідь</summary>

Обробник виконується після рендеру, і React передає його помилку функції `reportError`, тобто вікну, а не межі. Межі
нема чого замінювати, бо дерево ціле. Повідомлення показують так: огортають код обробника в `try/catch`, а в `catch`
кладуть текст повідомлення в стан.

</details>

**6. Ви передали в `createRoot` власний `onUncaughtError`, який лише пише в консоль. Що зникло порівняно з типовою
поведінкою?**

<details><summary>Відповідь</summary>

Зникла передача помилки в `reportError`, тому подія `error` вікна вже не настає і консоль не показує `Uncaught
TypeError`. Зникла й порада React поставити межу. Ваш обробник заміняє типовий повністю, тож тепер ви самі вирішуєте,
куди передати помилку.

</details>

**7. У продакшн-збірці стек компонентів починається рядками `at y`, `at ol`, `at b`. Чому імена такі і як дізнатися
справжні?**

<details><summary>Відповідь</summary>

Збирач стиснув імена функцій, щоб файл був меншим, тому `StopRow` став `y`. Рядок `at ol` має справжнє ім'я, бо це тег
HTML, а не функція. Справжні імена компонентів повертають карти коду, які зберігають відповідність між стиснутим кодом
і вихідним.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| динамічний імпорт | вираз `import('./файл')`, який завантажує модуль, коли до нього дійшов код, і повертає обіцянку |
| чанк | окремий файл збірки, у який збирач кладе динамічно імпортований модуль |
| `lazy` | функція React, яка робить із функції завантаження компонент; модуль вантажиться при першому рендері |
| чекати (suspend) | стан компонента, який не може завершити рендер, бо його код чи дані ще не готові |
| межа `<Suspense>` | місце в дереві, яке показує запасний вміст, поки щось усередині чекає |
| запасний вміст (`fallback`) | те, що межа показує замість справжнього вмісту |
| клас | шаблон, за яким `new` створює об'єкти з однаковими полями й методами |
| поле класу | змінна, яку отримує кожен об'єкт класу, наприклад `state = { hasError: false }` |
| `this` | об'єкт, якому належить метод, що зараз виконується |
| статичний метод | метод, що належить самому класу, а не його об'єктам; позначається словом `static` |
| `extends`, `super` | наслідування від батьківського класу і виклик його конструктора чи методу |
| межа помилок | компонент-клас, який ловить помилки рендеру нащадків і показує запасний екран |
| `getDerivedStateFromError` | статичний метод межі: повертає стан, з яким межа покаже запасний екран; має бути чистим |
| `componentDidCatch` | метод межі для побічних дій, наприклад звіту; отримує `componentStack` |
| стек компонентів | перелік компонентів від того, що впав, до кореня |
| стек власників | перелік компонентів, які створили той, що впав; доступний лише в режимі розробки |
| `onCaughtError`, `onUncaughtError`, `onRecoverableError` | параметри `createRoot` для помилок, які зловила межа, які не зловила жодна, і від яких React оговтався |
| `reportError` | функція браузера, яка повідомляє про помилку як про неперехоплену й надсилає подію `error` вікна |
| карта коду | файл, що зберігає відповідність між стиснутим кодом збірки і вихідним кодом |
| збирач помилок | сервіс, який отримує звіти про помилки з браузерів користувачів і групує їх |
| FCP | First Contentful Paint, момент, коли браузер уперше намалював текст чи зображення сторінки |
