# Лекція. Фаза 3, день 1. Маршрути

З цього дня починається фаза 3. Досі весь ваш застосунок жив на одній адресі, і що показати, вирішував стан. Сьогодні
кожен екран отримає власну адресу: її можна надіслати другові, на неї можна повернутися кнопкою «Назад», і після
оновлення сторінки людина побачить той самий екран. Для цього потрібен **маршрутизатор**, тобто бібліотека, яка
пов'язує адресу в браузері з компонентами на екрані. План бере React Router. Читання займе близько 75 хвилин.

Числа й вивід у лекції отримано на React 19.3.1, React Router 8.5.3, Vite 8.3.6 і TypeScript 6.0.3. Досліди без
браузера запускалися у Vitest 5.1.0 із середовищем jsdom 31.0.0. **jsdom** є бібліотекою, яка імітує документ браузера
всередині Node: вона будує DOM і надсилає події, але нічого не малює й не ходить у мережу. Досліди в браузері
запускалися в `chrome-headless-shell` версії 158, тобто в Chromium без вікна, яким скрипт керував через протокол
інструментів розробника. Сторінки віддавали два сервери: `npx vite preview` з продакшн-збіркою і найпростіший
статичний сервер, який ми написали самі. Біля кожного результату сказано, де його отримано.

Документація React Router у примірнику `react-router` доходить до версії 8.4.0, а в реєстрі npm уже є 8.5.3. Ми
порівняли сторінки, які задано на сьогодні, у двох версіях: їхній текст однаковий, крім абзацу про анімацію посилань
і однієї примітки про експериментальний режим. Обидві відмінності названо в розборі читання.

Практика дня будує екрани вашого застосунку. Щоб не показувати розв'язку, лекція бере інший об'єкт: домашню
бібліотеку з переліком книжок, сторінкою кожної книжки й приватною полицею читача.

**Після лекції ви зможете пояснити:**

- чому екран, вибраний станом, не має адреси і що від цього втрачає людина;
- як браузер змінює адресу без нового запиту до сервера і чому від цього залежить сьогоднішня пастка викоту;
- чим відрізняються три режими React Router і чому план бере режим даних;
- як маршрутизатор зіставляє адресу з деревом маршрутів і як вкладений маршрут потрапляє в `<Outlet>`;
- що таке індексний маршрут, параметр шляху й маршрут `*`;
- чим `<Link>` відрізняється від звичайного посилання і коли потрібен `useNavigate`;
- як лоадер перенаправляє на сторінку входу і чому це не захист даних;
- чому на хостингу пряме посилання спершу дає 404 і яке правило це виправляє на Vercel.

## Три екрани в одному стані

Уявіть застосунок домашньої бібліотеки. У ньому три екрани: головна сторінка, перелік книжок і сторінка однієї
книжки. Найпростіший спосіб перемикати екрани ви вже знаєте з фази 1: покласти назву екрана в стан і показувати
потрібний компонент умовою.

```tsx
// state-vs-url.test.tsx
// @vitest-environment jsdom
import { fireEvent, render, screen } from '@testing-library/react'
import { useState } from 'react'
import { test } from 'vitest'

// Маршрут у стані: екран змінюється, а адреса — ні.
function App() {
  const [screenName, setScreenName] = useState<'home' | 'books'>('home')
  return (
    <>
      <button onClick={() => setScreenName('books')}>Книжки</button>
      {screenName === 'home' ? <h1>Головна</h1> : <h1>Книжки</h1>}
    </>
  )
}

test('екран у стані, адреса стоїть', () => {
  render(<App />)
  console.log('до:   ', location.pathname, '| записів в історії:', history.length, '|', screen.getByRole('heading').textContent)
  fireEvent.click(screen.getByRole('button'))
  console.log('після:', location.pathname, '| записів в історії:', history.length, '|', screen.getByRole('heading').textContent)
})
```

Тест друкує шлях адреси, тобто частину після назви сайту, кількість записів в історії вкладки й заголовок на екрані:

```text
до:    / | записів в історії: 1 | Головна
після: / | записів в історії: 1 | Книжки
```

Заголовок змінився, а адреса й історія лишилися такими самими. Отже, браузер нічого не знає про те, що людина
перейшла на інший екран. З цього випливають чотири незручності:

- кнопка «Назад» не повертає на попередній екран, а виводить із сайту, бо в історії вкладки немає запису для екрана
  «Книжки»;
- посилання на екран не можна надіслати, бо в кожного екрана та сама адреса;
- після оновлення сторінки стан починається спочатку, і людина знову бачить головну;
- коли екранів стане тридцять, умови в одному компоненті перетворяться на заплутаний клубок.

Документація React каже про те саме в дописі про завершення Create React App: маршрут у стані не створює адрес, тому
посиланнями на екрани не можна ділитися. Тому застосунки беруть бібліотеку маршрутизації.

## Як браузер змінює адресу без нового запиту

Перш ніж брати бібліотеку, подивімося, на чому вона стоїть. Кожна вкладка браузера тримає **історію сеансу**, тобто
перелік адрес, які людина відвідала в цій вкладці. Кнопки «Назад» і «Вперед» ходять по цьому переліку. Об'єкт
`history` дає до нього доступ із JavaScript, і цей набір методів документація MDN називає History API.

Головний метод тут `history.pushState(state, unused, url)`. Він додає до історії новий запис з адресою `url` і
одразу показує цю адресу в адресному рядку. Перший аргумент є довільними даними для запису, другий не
використовується. Сторінка MDN про цей метод підкреслює важливе: після `pushState` браузер не намагається завантажити
нову адресу, хоча може зробити це пізніше, наприклад після перезапуску. Коли людина натискає «Назад», браузер
повертається до попереднього запису й надсилає вікну подію `popstate`.

```tsx
// state-vs-url.test.tsx, продовження
test('pushState міняє адресу й додає запис в історію', async () => {
  console.log('до:   ', location.href, '| записів в історії:', history.length)
  history.pushState(null, '', '/books/2')
  console.log('після:', location.href, '| записів в історії:', history.length)
  const seen: string[] = []
  window.addEventListener('popstate', () => seen.push(location.pathname))
  history.back()
  // Подія popstate приходить не одразу після back(), тому трохи чекаємо.
  await new Promise((r) => setTimeout(r, 50))
  console.log('popstate побачив адресу:', seen)
})
```

```text
до:    http://localhost:3000/ | записів в історії: 1
після: http://localhost:3000/books/2 | записів в історії: 2
popstate побачив адресу: [ '/' ]
```

Адресу `http://localhost:3000` jsdom дає документу сам. Виклик `pushState` змінив адресу й додав запис, а `back()`
повернув попередню адресу й викликав `popstate`. Сторінки ніхто не завантажував: у jsdom мережі немає взагалі, а як
поводиться справжній браузер, ми перевіримо нижче, у розділі про переходи.

Тепер видно, що робить маршрутизатор. Він виконує чотири дії:

1. читає адресу з `location`, коли застосунок запускається;
2. за деревом маршрутів вирішує, які компоненти відповідають цій адресі, і рендерить їх;
3. перехоплює клацання на свої посилання і замість завантаження сторінки викликає `pushState`, а потім рендерить
   нові компоненти;
4. слухає `popstate`, щоб кнопки «Назад» і «Вперед» теж міняли екран.

Запам'ятайте з цього розділу одну річ: адреса `/books/2` існує лише для JavaScript у браузері. На сервері немає файла
з такою назвою. Поки людина ходить посиланнями всередині застосунку, сервер про цю адресу не чує. Але коли людина
оновить сторінку чи відкриє посилання з листа, браузер попросить у сервера саме `/books/2`. Від того, що сервер тоді
відповість, залежить сьогоднішня пастка викоту.

## Три режими React Router

React Router можна вживати трьома способами, і документація називає їх **режимами**. Режим визначає, яким компонентом
верхнього рівня ви запускаєте маршрутизатор. Сторінка `Picking a Mode` пояснює, що кожен наступний режим додає
можливості до попереднього, а платите ви тим, що менше вирішуєте самі.

| Режим | Чим запускають | Що дає |
|-------|----------------|--------|
| декларативний (Declarative) | компонент `<BrowserRouter>` | зіставлення адреси з компонентами, посилання, `useNavigate`, `useLocation` |
| режим даних (Data) | функція `createBrowserRouter` і компонент `<RouterProvider>` | усе попереднє, а ще лоадери, дії, стан очікування переходу |
| фреймворк (Framework) | плагін Vite від React Router і файли маршрутів | усе попереднє, а ще власна збірка, розділення коду за маршрутами, рендер на сервері, типи для параметрів |

**Лоадер** є функцією маршруту, яку маршрутизатор викликає до того, як показати сторінку, щоб підготувати для неї
дані. **Дія** є функцією маршруту, яка обробляє надіслану форму. Обидві теми докладно розбирає наступний день, а
сьогодні лоадер знадобиться лише один раз, для приватної полиці.

Чому план бере режим даних? Розділ `Decision Advice` на тій самій сторінці радить новачкам фреймворк. Проте фреймворк
приносить власну збірку й рендер на сервері, а у вашому проєкті збірку вже налаштовано у фазі 1, а сервер план вивчає
окремо, у фазі 4. Режим даних лишає проєкт Vite таким, яким він є, і додає саме те, про що просить документація React:
глава `Build a React app from Scratch` радить завантажувати дані в лоадерах маршрутизатора, а не в компонентах, бо
запити з компонентів вишиковуються в чергу один за одним. Вступ до фази 3 у плані цитує цю пораду.

Якщо ви питаєте сервер `react-router-docs`, передавайте версію `8`, тобто лінію з вашого `package.json`. Сервер знає
версії лише до 8.4.0, тому запит із точною версією 8.5.3 поверне порожній результат.

## Встановлення й перший маршрутизатор

Пакет ставлять однією командою в теці `spa/`:

```text
$ npm install react-router@8.5.3
$ npm ls react-router
spa@0.0.0 /…/spa
└── react-router@8.5.3
```

У `package.json` з'являється рядок `"react-router": "^8.5.3"`. Тепер файл, з якого запускається застосунок, створює
маршрутизатор і віддає його React:

```tsx
// src/library/main.tsx
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import { createBrowserRouter } from 'react-router'
import { RouterProvider } from 'react-router/dom'
import { routes } from './routes'

// Маршрутизатор створюємо один раз, поза деревом React.
const router = createBrowserRouter(routes)

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <RouterProvider router={router} />
  </StrictMode>,
)
```

Пройдімо рядками:

- `createBrowserRouter(routes)` створює **маршрутизатор даних**, тобто об'єкт, який знає дерево маршрутів, тримає
  поточну адресу й стан переходу та слухає історію вкладки. Слово Browser у назві означає, що адресу він бере з
  адресного рядка браузера.
- `routes` є масивом об'єктів маршрутів. Його вміст розбирає наступний розділ.
- `<RouterProvider router={router} />` є компонентом, який показує на екрані те, що вибрав маршрутизатор.
- Компонент `RouterProvider` імпортовано з `react-router/dom`, а не з `react-router`. Довідник пояснює різницю так:
  версія з `react-router/dom` сама передає маршрутизатору функцію `flushSync` з `react-dom`, а версія з
  `react-router` потрібна там, де DOM немає. Сторінка `Installation` імпортує саме з `react-router/dom`, тож і ви
  робіть так.

Маршрутизатор створено на верхньому рівні модуля, а не в компоненті. Сторінка `Installation` прямо каже, що
маршрутизатор даних не можна тримати в стані React, а треба створити один раз поза деревом React. Причина в тому, що
маршрутизатор має власний стан і слухає історію вкладки. Якби компонент створював його при кожному рендері, кожен
рендер давав би новий маршрутизатор із початковим станом.

## Дерево маршрутів

Ось дерево маршрутів бібліотеки:

```tsx
// src/library/routes.tsx
import { redirect, type LoaderFunctionArgs, type RouteObject } from 'react-router'
import { currentReader } from './auth'
import { BookList, BookPage, Home, Layout, Login, NotFound, Shelf } from './pages'

// Лоадер-охоронець: маршрутизатор викликає його до рендеру сторінки полиці.
export function requireReader({ request }: LoaderFunctionArgs) {
  if (!currentReader()) {
    const from = new URL(request.url).pathname
    return redirect(`/login?from=${encodeURIComponent(from)}`)
  }
  return null
}

export const routes: RouteObject[] = [
  {
    path: '/',
    Component: Layout,
    children: [
      { index: true, Component: Home },
      { path: 'books', Component: BookList },
      { path: 'books/:bookId', Component: BookPage },
      { path: 'login', Component: Login },
      { path: 'shelf', loader: requireReader, Component: Shelf },
      { path: '*', Component: NotFound },
    ],
  },
]
```

Кожен елемент масиву є **об'єктом маршруту**. Сьогодні в ньому знадобляться такі поля:

| Поле | Що означає |
|------|------------|
| `path` | шаблон адреси, з яким маршрут збігається; шлях без косої риски на початку дописується до шляху батька |
| `Component` | компонент, який маршрутизатор рендерить, коли маршрут збігся; пишеться з великої літери, і передають саму функцію, а не JSX |
| `children` | дочірні маршрути, тобто маршрути, вкладені в цей |
| `index` | `true` робить маршрут індексним: він показується за адресою батька |
| `loader` | функція, яку маршрутизатор викликає до рендеру цього маршруту |

Поле `Component` можна замінити полем `element` і передати туди JSX, наприклад `element: <Home />`. Сторінки
задані на сьогодні вживають `Component`, і цей запис коротший.

Шляхи дітей тут записано без косої риски на початку: `'books'`, а не `'/books'`. Сторінка `Routing` пояснює, що шлях
батька автоматично входить у шлях дитини. Тому дочірній маршрут `'books/:bookId'` усередині батька `'/'` відповідає
адресі `/books/:bookId`.

### Як маршрутизатор вибирає гілку

Щоб побачити, що саме маршрутизатор знаходить для кожної адреси, ми взяли функцію `matchRoutes` з React Router. Вона
робить ту саму роботу, що й маршрутизатор при кожному переході, але нічого не рендерить. Компоненти для цього не
потрібні, тому в дереві досліду замість них стоять лише назви в полі `id`. Ми навмисно додали маршрут `books/new` і
поставили його після `books/:bookId`.

```ts
// match.test.ts
import { matchRoutes, type RouteObject } from 'react-router'
import { test } from 'vitest'

// Дерево лише з шляхами: компоненти для зіставлення не потрібні.
const routes: RouteObject[] = [
  {
    path: '/',
    id: 'каркас',
    children: [
      { index: true, id: 'головна' },
      { path: 'books', id: 'список' },
      { path: 'books/:bookId', id: 'книжка' },
      { path: 'books/new', id: 'нова книжка' },
      { path: '*', id: 'не знайдено' },
    ],
  },
]

test('які маршрути збігаються з адресою', () => {
  for (const url of ['/', '/books', '/books/2', '/books/new', '/books/2/edit', '/kontakty']) {
    const matches = matchRoutes(routes, url) ?? []
    const chain = matches.map((m) => m.route.id).join(' → ')
    const params = JSON.stringify(matches.at(-1)?.params ?? {})
    console.log(url.padEnd(14), chain.padEnd(26), params)
  }
})
```

Тест друкує адресу, ланцюжок маршрутів, що збіглися, і параметри останнього з них:

```text
/              каркас → головна           {}
/books         каркас → список            {}
/books/2       каркас → книжка            {"bookId":"2"}
/books/new     каркас → нова книжка       {}
/books/2/edit  каркас → не знайдено       {"*":"books/2/edit"}
/kontakty      каркас → не знайдено       {"*":"kontakty"}
```

З цього виводу видно чотири правила.

**Збіг є ланцюжком, а не одним маршрутом.** Для кожної адреси маршрутизатор знаходить шлях деревом від кореня до
листка: спершу каркас, потім дитину. Саме цей ланцюжок він рендерить, і нижче видно, як.

**Адреса `/` дала індексний маршрут.** Індексний маршрут не має власного шляху. Він збігається тоді, коли адреса
дорівнює адресі батька, тобто показує вміст батька за замовчуванням.

**Сегмент із двокрапкою є параметром.** **Сегментом** називають частину адреси між косими рисками: в адресі
`/books/2` два сегменти, `books` і `2`. Шаблон `:bookId` збігається з будь-яким одним сегментом і запам'ятовує його
значення під іменем `bookId`. Тому адреса `/books/2` дала параметр `{"bookId":"2"}`.

**Точний шаблон перемагає параметр, і порядок маршрутів у масиві для цього неважливий.** Адресі `/books/new`
відповідають обидва маршрути, бо `:bookId` збігся б і зі словом `new`. Маршрутизатор вибрав `books/new`, хоча той
стоїть у масиві другим. React Router не бере перший маршрут, що підійшов. Він оцінює кожен шаблон, і сегмент зі
сталим текстом важить більше за параметр. Документація називає це ранжуванням маршрутів.

**Зірочка ловить решту.** Шаблон `*` збігається з будь-якою адресою і кладе в параметр `*` усе, що лишилося. Його
оцінка найнижча, тому він спрацьовує лише тоді, коли жоден інший маршрут не підійшов. Адреса `/books/2/edit` має три
сегменти, а маршрут книжки описує рівно два, тому вона потрапила в `*`.

## Каркас і `<Outlet>`

Тепер подивімося, як ланцюжок маршрутів стає екраном. Перший маршрут дерева має `Component: Layout`. Це **каркас**,
тобто компонент зі спільними частинами всіх сторінок, як-от шапка з навігацією:

```tsx
// src/library/pages.tsx, фрагмент
import { Link, NavLink, Outlet, useNavigate, useParams, useSearchParams } from 'react-router'

// Каркас: шапка з навігацією, яку бачать усі сторінки, і місце для дочірньої сторінки.
export function Layout() {
  return (
    <>
      <header>
        <nav>
          <NavLink to="/" end>Головна</NavLink> <NavLink to="/books">Книжки</NavLink>{' '}
          <NavLink to="/shelf">Моя полиця</NavLink>
        </nav>
      </header>
      <main>
        <Outlet />
      </main>
    </>
  )
}
```

Компонент `<Outlet />` позначає місце, де маршрутизатор покаже наступний маршрут ланцюжка. Для адреси `/books/2`
ланцюжок такий: каркас, потім книжка. Тому React рендерить `Layout`, а там, де в ньому стоїть `<Outlet />`, рендерить
`BookPage`. Якщо батько не має `<Outlet />`, дитина просто не з'явиться на екрані, хоча маршрут і збігся.

Ми відрендерили все дерево в jsdom. У тесті замість `createBrowserRouter` стоїть `createMemoryRouter`. Цей
маршрутизатор тримає історію в масиві, а не в адресному рядку, тому тест сам задає початкову адресу. Решта поводиться
так само.

```tsx
// render.test.tsx
// @vitest-environment jsdom
import { fireEvent, render, screen } from '@testing-library/react'
import { createMemoryRouter, RouterProvider } from 'react-router'
import { test } from 'vitest'
import { routes } from '../routes'

test('каркас, сторінка книжки й активне посилання', async () => {
  const router = createMemoryRouter(routes, { initialEntries: ['/books/2'] })
  render(<RouterProvider router={router} />)
  await screen.findByRole('heading')
  console.log('адреса:', router.state.location.pathname)
  console.log('заголовок:', screen.getByRole('heading').textContent)
  for (const a of screen.getAllByRole('link')) {
    console.log(`посилання «${a.textContent}» href=${a.getAttribute('href')} class="${a.className}" aria-current=${a.getAttribute('aria-current')}`)
  }
  fireEvent.click(screen.getByRole('link', { name: 'Головна' }))
  await screen.findByRole('heading', { name: 'Домашня бібліотека' })
  console.log('після клацання:', router.state.location.pathname, '|', screen.getByRole('heading').textContent)
  console.log('посилань у шапці:', screen.getAllByRole('link').length)
})
```

```text
адреса: /books/2
заголовок: Лісова пісня
посилання «Головна» href=/ class="" aria-current=null
посилання «Книжки» href=/books class="active" aria-current=page
посилання «Моя полиця» href=/shelf class="" aria-current=null
після клацання: / | Домашня бібліотека
посилань у шапці: 3
```

Покроково це виглядає так.

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | маршрутизатор | зіставляє `/books/2` з деревом і отримує ланцюжок «каркас, книжка» з параметром `bookId = "2"` |
| 2 | React | рендерить `Layout`: шапку з трьома посиланнями й `<Outlet />` |
| 3 | React | там, де стоїть `<Outlet />`, рендерить `BookPage`, яка читає параметр і показує «Лісова пісня» |
| 4 | людина | клацає «Головна» |
| 5 | маршрутизатор | змінює адресу на `/`, зіставляє її і отримує ланцюжок «каркас, головна» |
| 6 | React | рендерить той самий `Layout`, а в `<Outlet />` тепер `Home` |

Шапка лишилася на екрані, бо каркас входить в обидва ланцюжки. Змінилася лише частина всередині `<Outlet />`. Саме
для цього вкладають маршрути: спільна частина пишеться один раз у батьківському компоненті.

### Активне посилання: `NavLink`

У виводі посилання «Книжки» має клас `active` й атрибут `aria-current="page"`, хоча адреса `/books/2`, а не `/books`.
Компонент `NavLink` є посиланням, яке знає, чи веде воно на поточну сторінку. Він сам додає клас `active`, щоб CSS міг
виділити пункт меню, і атрибут `aria-current="page"`. Цей атрибут каже програмі читання з екрана, що пункт відповідає
поточній сторінці.

`NavLink` вважає себе активним і тоді, коли адреса довша за його `to`: `/books/2` починається з `/books`. Так
зроблено навмисно, бо пункт «Книжки» має світитися й на сторінці окремої книжки. Якщо потрібен лише точний збіг,
додають проп `end`. Довідник `NavLink` робить виняток для `to="/"`: з цим посиланням збігається будь-яка адреса,
тому маршрутизатор вважає його активним лише на самій `/`, навіть без `end`. У нашому коді `end` біля «Головної»
нічого не змінює, але й не шкодить.

### Індексний маршрут, маршрут без шляху й маршрут без компонента

Індексний маршрут ви вже бачили: `{ index: true, Component: Home }` показується там, де батько поставив
`<Outlet />`, коли адреса дорівнює адресі батька. Сторінка `Routing` додає, що в індексного маршруту не може бути дітей.

Та сама сторінка описує ще дві форми. Перша є **маршрутом каркаса без шляху**. Він має компонент і дітей, але не має
`path`, тому додає спільну обгортку, нічого не дописуючи до адреси:

```tsx
// приклад зі сторінки Routing
createBrowserRouter([
  {
    // no path on this parent route, just the component
    Component: MarketingLayout,
    children: [
      { index: true, Component: Home },
      { path: "contact", Component: Contact },
    ],
  },
]);
```

Тут сторінки `/` і `/contact` отримують каркас `MarketingLayout`, а адреса `/contact` не має жодного зайвого
сегмента. Друга форма є **маршрутом-префіксом**. Він має шлях і дітей, але не має компонента, тому лише дописує
спільний початок адреси до шляхів дітей:

```tsx
// приклад зі сторінки Routing
createBrowserRouter([
  {
    // no component, just a path
    path: "/projects",
    children: [
      { index: true, Component: ProjectsHome },
      { path: ":pid", Component: Project },
      { path: ":pid/edit", Component: EditProject },
    ],
  },
]);
```

Цей запис створює адреси `/projects`, `/projects/:pid` і `/projects/:pid/edit` без спільного компонента. Обидві форми
стануть у пригоді, коли маршрутів побільшає: перша для приватної зони зі своєю шапкою, друга для групи сторінок однієї
сутності.

## Параметри шляху

Сторінка книжки читає параметр хуком `useParams`:

```tsx
// src/library/pages.tsx, фрагмент
export function BookPage() {
  const { bookId } = useParams()
  const book = findBook(Number(bookId))
  if (!book) {
    return <h1>Книжки «{bookId}» немає</h1>
  }
  return (
    <>
      <h1>{book.title}</h1>
      <p>{book.author}</p>
    </>
  )
}
```

Функція `findBook` лежить у файлі з даними бібліотеки:

```ts
// src/library/books.ts
// Книжки домашньої бібліотеки. Справжній застосунок отримав би їх із сервера.
export type Book = { id: number; title: string; author: string }

export const BOOKS: Book[] = [
  { id: 1, title: 'Тіні забутих предків', author: 'Михайло Коцюбинський' },
  { id: 2, title: 'Лісова пісня', author: 'Леся Українка' },
  { id: 3, title: 'Кайдашева сім’я', author: 'Іван Нечуй-Левицький' },
]

export function findBook(id: number): Book | undefined {
  return BOOKS.find((b) => b.id === id)
}
```

Вона шукає книжку за числовим номером і повертає `undefined`, якщо такої немає. Ось що показує сторінка для двох
адрес без книжки, тим самим тестом у jsdom:

```tsx
// render.test.tsx, продовження
test('книжки з таким номером немає', async () => {
  for (const url of ['/books/7', '/books/abc']) {
    const router = createMemoryRouter(routes, { initialEntries: [url] })
    const { unmount } = render(<RouterProvider router={router} />)
    console.log(url, '→', (await screen.findByRole('heading')).textContent)
    unmount()
  }
})
```

```text
/books/7 → Книжки «7» немає
/books/abc → Книжки «abc» немає
```

Разом із попереднім тестом, де `/books/2` дала «Лісова пісня», видно три речі.

**Параметр завжди є рядком.** Адреса складається з тексту, тому `bookId` дорівнює `"2"`, а не `2`. Масив книжок
зберігає номери числами, тому код перетворює рядок через `Number`. Без цього порівняння `b.id === bookId` ніколи не
дало б `true`, бо число не дорівнює рядку при строгому порівнянні.

**Маршрут не перевіряє значення.** Шаблон `:bookId` збігається і з `7`, і з `abc`. Маршрутизатор не знає, які книжки
існують, тому сторінка мусить сама вирішити, що показати, коли книжки немає. Тут вона показує власний заголовок.
Наступного дня ви побачите інший спосіб: лоадер може повідомити маршрутизатору, що запис не знайдено, і тоді сторінку
помилки покаже маршрутизатор.

**TypeScript бачить, що параметра може не бути.** Хук `useParams` повертає об'єкт, у якому кожне значення має тип
`string | undefined`. Ми написали навмисно хибний код:

```tsx
// params.tsx — перевірка типів
import { useParams } from 'react-router'

export function BookTitle() {
  const params = useParams()
  const bookId: string = params.bookId
  const asNumber: number = params.bookId
  return <p>{bookId}{asNumber}</p>
}
```

```text
$ npx tsc -p tsconfig.app.json --noEmit
src/library/tscheck/params.tsx(5,9): error TS2322: Type 'string | undefined' is not assignable to type 'string'.
src/library/tscheck/params.tsx(6,9): error TS2322: Type 'string | undefined' is not assignable to type 'number'.
```

Перша помилка каже, що значення може бути `undefined`. Хук не знає, в якому маршруті його викликали, тому не може
обіцяти, що параметр `bookId` там є. Друга помилка нагадує, що параметр є рядком, а не числом. Код `BookPage` обходить
обидві проблеми: `Number(undefined)` дає `NaN`, а книжки з номером `NaN` немає, тому сторінка покаже повідомлення.

Сторінка `Routing` описує ще два різновиди сегментів. Знак питання після сегмента робить його необов'язковим: шаблон
`':lang?/categories'` збігається і з `/categories`, і з `/uk/categories`. Шаблон, що закінчується на `/*`, збігається
з усім, що стоїть далі, разом із косими рисками, і кладе цей залишок у параметр `*`. Сьогодні вони не потрібні.

### Відносні посилання

Посилання може вести не лише на повну адресу, як `/books`, а й на відносну, без косої риски на початку. Тут легко
помилитися, бо React Router рахує відносний шлях за деревом маршрутів, а не за сегментами адреси. Ми поставили три
посилання на сторінку книжки і відкрили `/books/2` двічі: коли шлях книжки записано одним маршрутом `books/:bookId` і
коли `books` та `:bookId` є двома вкладеними маршрутами.

```tsx
// relative.test.tsx, фрагмент
function Back() {
  return (
    <>
      <Link to="..">назад за деревом</Link>
      <Link to=".." relative="path">назад за адресою</Link>
      <Link to="edit">редагувати</Link>
    </>
  )
}
```

```text
books/:bookId одним маршрутом: «назад за деревом» → /; «назад за адресою» → /books; «редагувати» → /books/2/edit
books і :bookId окремими маршрутами: «назад за деревом» → /books; «назад за адресою» → /books; «редагувати» → /books/2/edit
```

Запис `..` означає «на рівень вище». Без додаткового пропа React Router піднімається на один **маршрут** угору. Коли
`books/:bookId` записано одним маршрутом, батьком є корінь `/`, тому посилання повело на головну, хоча автор,
мабуть, хотів до переліку. Проп `relative="path"` змушує рахувати за сегментами адреси, і тоді `..` прибирає лише
`2`. Довідник `Link` описує обидва значення цього пропа. Запис `edit` без крапок дописується до поточної адреси.

## Сторінка 404

В адресний рядок людина може вписати будь-що. Маршрут `{ path: '*', Component: NotFound }` стоїть останнім серед
дітей каркаса, тому для невідомої адреси ланцюжок буде «каркас, не знайдено», і шапка лишиться на екрані:

```tsx
// render.test.tsx, продовження
test('адреса, якої немає в дереві', async () => {
  const router = createMemoryRouter(routes, { initialEntries: ['/kontakty'] })
  render(<RouterProvider router={router} />)
  console.log('/kontakty →', (await screen.findByRole('heading')).textContent)
})
```

```text
/kontakty → Такої сторінки немає
```

А що буде, якщо маршруту `*` немає? Ми прибрали його й відкрили ту саму адресу:

```tsx
// no-splat.test.tsx, фрагмент
// Те саме дерево, але без маршруту '*'.
const withoutSplat: RouteObject[] = [
  { path: '/', Component: Layout, children: [{ index: true, Component: Home }] },
]

test('без маршруту * і без межі помилок', async () => {
  const router = createMemoryRouter(withoutSplat, { initialEntries: ['/kontakty'] })
  const { container } = render(<RouterProvider router={router} />)
  await new Promise((r) => setTimeout(r, 20))
  console.log('текст сторінки:', container.textContent)
  const err = router.state.errors?.['0']
  console.log('помилка в стані маршрутизатора:', isRouteErrorResponse(err) ? `${err.status} ${err.statusText}` : err)
})
```

```text
Error handled by React Router default ErrorBoundary: ErrorResponseImpl {
  status: 404,
  statusText: 'Not Found',
  data: 'Error: No route matches URL "/kontakty"',
  ...
}
текст сторінки: Unexpected Application Error!404 Not Found💿 Hey developer 👋You can provide a way better UX than this when your app throws errors by providing your own ErrorBoundary or errorElement prop on your route.
помилка в стані маршрутизатора: 404 Not Found
```

Перші рядки React Router надрукував у консоль сам, ми скоротили лише стек. Маршрутизатор не знайшов жодного маршруту
й записав у свій стан помилку зі статусом 404. Цю помилку показала типова сторінка помилки самого React Router з
порадою розробнику. Продакшн-версія цієї сторінки в пакеті поради не містить: ми перевірили це за кодом пакета, а не
запуском.
Людина побачить англійський текст про неочікувану помилку замість зрозумілої сторінки.

Другий спосіб показати свою сторінку є **межею помилок маршруту**. Це поле `ErrorBoundary` в об'єкті маршруту, і воно
працює так само, як межа помилок із лекції «`<Suspense>` і межі помилок» фази 2, але пишеться звичайним компонентом, а
не класом. Компонент читає помилку хуком `useRouteError`, а функція `isRouteErrorResponse` перевіряє, чи це відповідь
зі статусом:

```tsx
// no-splat.test.tsx, продовження
function RootError() {
  const error = useRouteError()
  return <h1>{isRouteErrorResponse(error) ? `Помилка ${error.status}` : 'Щось зламалося'}</h1>
}

test('без маршруту *, але з ErrorBoundary на корені', async () => {
  const routes: RouteObject[] = [{ ...withoutSplat[0], ErrorBoundary: RootError }]
  const router = createMemoryRouter(routes, { initialEntries: ['/kontakty'] })
  const { container } = render(<RouterProvider router={router} />)
  await new Promise((r) => setTimeout(r, 20))
  console.log('текст сторінки:', container.textContent)
})
```

```text
текст сторінки: Помилка 404
```

Чим ці способи відрізняються? Маршрут `*` показує сторінку всередині каркаса, і шапка лишається. Межа помилок на
корені заміняє весь корінь разом із шапкою, зате ловить і інші помилки маршрутів, наприклад кинуті в лоадері.
Практика дня просить сторінку 404, і маршрут `*` дає її найпростіше. Межу помилок на корені варто мати в будь-якому
разі, щоб людина не побачила англійської типової сторінки.

Ще одна річ, про яку варто знати. Сторінку «Такої сторінки немає» малює JavaScript у браузері. Сервер, який віддав
`index.html`, відповів статусом 200. Ми перевірили це на `vite preview`:

```text
$ curl -s -o /dev/null -w '%{http_code} %{content_type}\n' http://localhost:4180/kontakty
200 text/html
```

Тобто з погляду мережі сторінка 404 є успішною відповіддю. Людині це байдуже, а пошуковий робот може вважати таку
сторінку справжньою. Чесний статус 404 від сервера можливий лише тоді, коли сервер знає маршрути, а це тема фази 4.

## Переходи: `Link`, `NavLink`, `useNavigate` і `redirect`

Сторінка `Navigating` перелічує п'ять способів перейти на іншу адресу: `<Link>`, `<NavLink>`, `<Form>`, `redirect` і
`useNavigate`. Форма маршрутизатора належить наступному дню, а решту розгляньмо тут.

### `<Link>` проти звичайного посилання

Компонент `<Link to="/books/2">` рендерить звичайний тег `<a href="/books/2">`, це видно у виводі тесту вище. Чим він
тоді відрізняється від тега `<a>`, написаного вручну? Ми перевірили це в браузері на продакшн-збірці, відданій
`vite preview`. Скрипт відкрив `/books`, записав у змінну `window.marker` слово «живий» і далі по черзі клацнув на
`<Link>`, натиснув «Назад» і клацнув на звичайне посилання `<a href="/books/3">`, яке ми додали в документ. Змінна
`window.marker` живе, поки живе сторінка: якщо браузер завантажить документ заново, змінна зникне.

```js
// nav.mjs, фрагмент: скрипт керує браузером без вікна через протокол інструментів розробника
const state = () =>
  page.evaluate(`JSON.stringify({ адреса: location.pathname, заголовок: document.querySelector('h1')?.textContent, мітка: window.marker ?? null, записів: history.length })`)

await page.goto('http://localhost:4180/books')
await page.evaluate('window.marker = "живий"')
console.log('відкрили /books:      ', await state())

await page.evaluate(`[...document.querySelectorAll('a')].find(a => a.textContent === 'Лісова пісня').click()`)
console.log('клацнули <Link>:      ', await state())

await page.evaluate('history.back()')
console.log('кнопка «Назад»:       ', await state())

await page.evaluate(`(() => { const a = document.createElement('a'); a.href = '/books/3'; document.body.append(a); a.click() })()`)
console.log('звичайне посилання <a>:', await state())
console.log('запити документа:', docs.join(', '))
```

Між кроками скрипт чекав 300–800 мс. Масив `docs` збирає адреси всіх запитів, якими браузер завантажував документ
сторінки:

```text
відкрили /books:       {"адреса":"/books","заголовок":"Книжки","мітка":"живий","записів":2}
клацнули <Link>:       {"адреса":"/books/2","заголовок":"Лісова пісня","мітка":"живий","записів":3}
кнопка «Назад»:        {"адреса":"/books","заголовок":"Книжки","мітка":"живий","записів":3}
звичайне посилання <a>: {"адреса":"/books/3","заголовок":"Кайдашева сім’я","мітка":null,"записів":3}
запити документа: /books, /books/3
```

На початку записів два, бо нова вкладка спершу показувала порожню сторінку `about:blank`. Після клацання на `<Link>`
адреса й заголовок змінилися, записів стало три, а мітка жива. Отже, сторінка не завантажувалась заново, і запиту
документа для `/books/2` немає. Кнопка «Назад» теж обійшлася без запиту: маршрутизатор отримав `popstate` і показав
перелік. Звичайне посилання `<a>` дало новий запит документа `/books/3`, і мітка зникла, бо браузер завантажив
сторінку з нуля: заново завантажив `index.html`, виконав бандл і відрендерив усе. Екран вийшов правильним, бо сервер
віддав `index.html`, але людина чекала довше, а весь стан застосунку пропав.

Висновок: усередині застосунку переходять через `<Link>` чи `<NavLink>`. Вони лишаються справжніми посиланнями в
документі, тому людина бачить адресу при наведенні, а програма читання з екрана оголошує їх посиланнями. Але
звичайне клацання на них React Router перехоплює й обробляє без завантаження сторінки.

### `useNavigate`: перехід із коду

Іноді перейти треба не тому, що людина клацнула посилання, а тому, що щось сталося в коді. Для цього є хук
`useNavigate`, який повертає функцію переходу. Сторінка `Navigating` радить уживати його рідко, лише коли людина
нічого не натискала, наприклад для виходу після довгої бездіяльності. Для переходу після клацання є посилання, а
для переходу після надсилання форми буде форма маршрутизатора з наступного дня.

Наша сторінка входу поки вживає `useNavigate` в обробнику форми, бо форму маршрутизатора ви ще не вивчали:

```tsx
// src/library/pages.tsx, фрагмент
export function Login() {
  const navigate = useNavigate()
  const [params] = useSearchParams()
  return (
    <form
      onSubmit={(e) => {
        e.preventDefault()
        signIn('Оксана')
        navigate(params.get('from') ?? '/', { replace: true })
      }}
    >
      <h1>Вхід</h1>
      <button>Увійти як Оксана</button>
    </form>
  )
}
```

- `e.preventDefault()` просить браузер не надсилати форму звичайним способом, тобто не завантажувати сторінку. Ви
  бачили цей виклик у лекції «DOM і події», розділ «Дія браузера й `preventDefault`».
- `signIn('Оксана')` є фейковим входом: функція записує ім'я в `sessionStorage`, тобто в сховище браузера, яке живе,
  поки відкрита вкладка.
- `useSearchParams` дає параметри після знака питання в адресі. Для адреси `/login?from=%2Fshelf` виклик
  `params.get('from')` повертає `/shelf`: запис `%2F` є закодованою косою рискою.
- `navigate(..., { replace: true })` переходить на збережену адресу і **заміняє** поточний запис історії, а не додає
  новий.

Навіщо заміна? Ми перевірили в браузері, куди веде «Назад» після входу:

```text
початок:             /books | Книжки | записів: 2
клацнули «Моя полиця»: /login?from=%2Fshelf | Вхід | записів: 3
клацнули «Увійти»:   /shelf | Моя полиця, Оксана | записів: 3
«Назад»:             /books | Книжки | записів: 3
```

Після входу записів лишилося три: запис сторінки входу замінено записом полиці. Тому «Назад» повів на перелік
книжок, а не на сторінку входу, яка вже не потрібна людині, що ввійшла.

### `redirect`: перенаправлення з лоадера

Функція `redirect` створює відповідь, яка каже «йди на іншу адресу». Ми перевірили її на Node:

```js
// redirect-check.mjs
import { redirect } from 'react-router'
const r = redirect('/login?from=%2Fshelf')
console.log(r instanceof Response, r.status, r.headers.get('Location'))
```

```text
true 302 /login?from=%2Fshelf
```

Це звичайний об'єкт `Response` з Fetch API, який ви бачили в лекції «Мережа», зі статусом 302 і заголовком `Location`.
Коли лоадер повертає таку відповідь, маршрутизатор не рендерить сторінку цього маршруту, а переходить на адресу з
`Location`. Цим і користується приватна полиця.

## Захищений маршрут

На полицю пускають лише того, хто ввійшов. Вхід у нашій бібліотеці фейковий: справжньої перевірки пароля немає, а
ознакою входу є ім'я в `sessionStorage`.

```ts
// src/library/auth.ts
// Фейковий вхід: ім'я читача лежить у sessionStorage браузера.
// Справжньої перевірки тут немає, і саме про це пастка дня.
const KEY = 'reader'

export function currentReader(): string | null {
  return sessionStorage.getItem(KEY)
}

export function signIn(name: string) {
  sessionStorage.setItem(KEY, name)
}

export function signOut() {
  sessionStorage.removeItem(KEY)
}
```

Маршрут полиці має лоадер `requireReader` з файла `routes.tsx` вище. Пройдімо його рядками:

- маршрутизатор викликає лоадер до рендеру `Shelf` і передає йому об'єкт, де поле `request` є запитом на нову
  адресу;
- `currentReader()` читає ім'я з `sessionStorage`; якщо імені немає, людина не ввійшла;
- `new URL(request.url).pathname` дістає шлях, куди людина хотіла потрапити, тобто `/shelf`;
- `redirect(`/login?from=...`)` відправляє на вхід і передає цей шлях у параметрі `from`; функція
  `encodeURIComponent` кодує косу риску як `%2F`, щоб шлях не змішався з адресою сторінки входу;
- `return null` означає, що людина ввійшла і даних для сторінки лоадер не готує; лоадер мусить щось повернути, і
  `null` тут найпростіше значення.

У jsdom ми відкрили `/shelf` без входу, а потім клацнули «Увійти». Функція `router.subscribe` викликає наш колбек при
кожній зміні стану маршрутизатора:

```tsx
// guard.test.tsx, фрагмент
test('полиця без входу і після входу', async () => {
  sessionStorage.clear()
  const router = createMemoryRouter(routes, { initialEntries: ['/shelf'] })
  router.subscribe((state) => console.log('стан:', state.navigation.state, state.location.pathname + state.location.search))
  render(<RouterProvider router={router} />)
  await screen.findByRole('heading', { name: 'Вхід' })
  console.log('на екрані:', screen.getByRole('heading').textContent, '| адреса:', router.state.location.pathname + router.state.location.search)
  fireEvent.click(screen.getByRole('button', { name: 'Увійти як Оксана' }))
  await screen.findByRole('heading', { name: /Моя полиця/ })
  console.log('на екрані:', screen.getByRole('heading').textContent, '| адреса:', router.state.location.pathname)
})
```

```text
стан: idle /login?from=%2Fshelf
на екрані: Вхід | адреса: /login?from=%2Fshelf
стан: loading /login?from=%2Fshelf
стан: idle /shelf
на екрані: Моя полиця, Оксана | адреса: /shelf
```

Поле `navigation.state` показує, чи триває перехід: `loading` означає, що маршрутизатор уже знає нову адресу і чекає
лоадерів, а `idle` означає, що перехід завершено. Видно, що компонент `Shelf` без входу не рендерився жодного разу:
лоадер перенаправив людину раніше. Після входу маршрутизатор пішов на `/shelf`, знову викликав лоадер, цього разу той
повернув `null`, і полиця з'явилася. У браузері на продакшн-збірці перше відкриття `/shelf` без входу теж закінчилося
на `/login?from=%2Fshelf` із заголовком «Вхід».

### Лоадери батька й дитини працюють одночасно

Коли приватних сторінок кілька, охоронця хочеться поставити один раз, на батьківський маршрут. Тут є підступ. Ми
поставили охоронця на маршрут `/shelf`, а дочірньому маршруту `notes` дали власний лоадер, який нібито завантажує
нотатки. Охоронець навмисно думає 10 мс:

```tsx
// guard.test.tsx, продовження
test('охоронець на батьку, свій лоадер у дитини', async () => {
  sessionStorage.clear()
  const log: string[] = []
  const tree: RouteObject[] = [
    { path: '/login', element: <h1>Вхід</h1> },
    {
      path: '/shelf',
      loader: async () => {
        log.push('охоронець почав')
        await new Promise((r) => setTimeout(r, 10))
        log.push('охоронець: читача немає, перенаправляю')
        return redirect('/login')
      },
      children: [
        {
          path: 'notes',
          loader: () => {
            log.push('лоадер нотаток почав роботу')
            return null
          },
          element: <h1>Нотатки</h1>,
        },
      ],
    },
  ]
  const router = createMemoryRouter(tree, { initialEntries: ['/shelf/notes'] })
  render(<RouterProvider router={router} />)
  await screen.findByRole('heading', { name: 'Вхід' })
  console.log(log.join('\n'))
})
```

```text
охоронець почав
лоадер нотаток почав роботу
охоронець: читача немає, перенаправляю
```

Лоадер нотаток запустився раніше, ніж охоронець вирішив перенаправити людину. Маршрутизатор запускає лоадери всіх
маршрутів ланцюжка одночасно, а не по черзі, щоб сторінка з'явилася швидше. Наступний день розбирає це докладно. Для
охоронця висновок такий: лоадер батька не зупиняє лоадерів дітей. Якби лоадер нотаток справді запитував сервер, запит
пішов би й без входу. Документація лінії 8 описує для перевірки входу окрему властивість маршруту `middleware`: вона
виконується по черзі від батька до дитини і до лоадерів. Сьогодні вона не потрібна, бо практика дня має одну
приватну сторінку.

### Чому це не захист

Тепер головне. Лоадер-охоронець працює в браузері людини, а браузер повністю під її владою. Ми перевірили це двома
способами.

Спершу в браузері, на продакшн-збірці. Скрипт відкрив `/shelf` без входу, потім виконав у сторінці один рядок, який
будь-хто може вписати в консоль інструментів розробника, і відкрив `/shelf` знову:

```js
// guard.mjs, фрагмент
await page.goto('http://localhost:4180/shelf')
await show('відкрили /shelf без входу:')
await page.evaluate(`sessionStorage.setItem('reader', 'хтось чужий')`)
await page.goto('http://localhost:4180/shelf')
await show('після рядка в консолі:  ')
```

```text
відкрили /shelf без входу: /login?from=%2Fshelf | Вхід
після рядка в консолі:   /shelf | Моя полиця, хтось чужий
```

Один рядок відкрив приватну полицю. Потім ми пошукали текст нотатки з полиці в зібраному бандлі:

```text
$ grep -o 'Нотатка: [^`]*' dist/assets/*.js
Нотатка: позичила «Лісову пісню» сусідці
```

Шаблон пошуку бере текст від слова «Нотатка» до найближчого зворотного апострофа, яким збирач обрамив рядок. Текст
лежить у файлі, який отримує кожен відвідувач, бо бандл однаковий для всіх. Охоронець не дає побачити екран, але не
прибирає з браузера ні коду, ні даних.

Отже, захищений маршрут є зручністю: він не показує людині, яка не ввійшла, екрана, яким вона не може
скористатися, і веде її на вхід. Справжній захист стоїть на сервері: дані полиці мають приходити із запиту, а сервер
віддає їх, лише перевіривши, хто питає. Без цієї перевірки той самий запит можна надіслати з консолі чи з `curl`, і
жоден маршрут у браузері цьому не завадить. Сервер із перевіркою входу будує план NestJS, а фаза 5 цього плану
повертається до цієї думки в дні «Оточення й безпека фронтенду».

## Глибоке посилання й оновлення сторінки

**Глибоким посиланням** називають посилання не на головну сторінку сайту, а на внутрішню, як-от `/books/2`. Розберімо,
що відбувається, коли людина оновлює таку сторінку.

| Крок | Хто діє | Що відбувається |
|------|---------|-----------------|
| 1 | браузер | надсилає серверу запит `GET /books/2`, бо оновлення завантажує документ заново |
| 2 | сервер | шукає, що віддати на шлях `/books/2` |
| 3а | сервер із правилом для односторінкового застосунку | файла немає, тому віддає `index.html` |
| 3б | сервер без такого правила | файла немає, тому відповідає 404 |
| 4 | браузер, після кроку 3а | виконує бандл; маршрутизатор читає адресу `/books/2` і показує сторінку книжки |

**Односторінковим застосунком** називають застосунок з одним `index.html`, де адреси обробляє JavaScript у браузері.
Ви вже бачили в лекції «Збірка, перший викот і журнал вимірів», розділ «`vite preview`: перевірка перед викладанням»,
що `vite preview` на будь-який незнайомий шлях повертає `index.html`, а сервер, який лише шукає файл, повертає 404.
Тоді маршрутів ще не було. Тепер перевірмо це на застосунку з маршрутами.

Збірку ми віддали двома серверами. На порту 4180 працював `vite preview`, а на порту 8010 ось цей сервер:

```js
// static-server.mjs
// Найпростіший статичний сервер: шукає файл у dist, а якщо файла немає, відповідає 404.
// Так поводиться хостинг, на якому не задано правила для односторінкового застосунку.
import { readFile } from 'node:fs/promises'
import { createServer } from 'node:http'
import { extname, join } from 'node:path'

const TYPES = { '.html': 'text/html', '.js': 'text/javascript', '.svg': 'image/svg+xml' }

createServer(async (req, res) => {
  const path = new URL(req.url, 'http://x').pathname
  const file = join('dist', path === '/' ? 'index.html' : path)
  try {
    const body = await readFile(file)
    res.setHeader('Content-Type', TYPES[extname(file)] ?? 'text/plain')
    res.end(body)
  } catch {
    res.statusCode = 404
    res.end('Not found')
  }
}).listen(8010)
```

Спершу ми запитали кілька адрес командою `curl` і надрукували код відповіді й тип вмісту:

```text
$ for p in 4180 8010; do for u in / /books/2 /shelf /assets/index-Wjb_VSEm.js /assets/nope.js; do
    curl -s -o /dev/null -w "$p $u %{http_code} %{content_type}\n" http://localhost:$p$u
  done; done
4180 / 200 text/html
4180 /books/2 200 text/html
4180 /shelf 200 text/html
4180 /assets/index-Wjb_VSEm.js 200 text/javascript
4180 /assets/nope.js 200 text/html
8010 / 200 text/html
8010 /books/2 404
8010 /shelf 404
8010 /assets/index-Wjb_VSEm.js 200 text/javascript
8010 /assets/nope.js 404
```

Потім ми повторили це в браузері так, як це робить людина. Скрипт відкрив головну, клацнув «Книжки», потім «Лісова
пісня», а потім оновив сторінку:

```js
// deep.mjs, фрагмент
for (const origin of ['http://localhost:4180', 'http://localhost:8010']) {
  statuses.length = 0
  await page.goto(`${origin}/`)
  await page.evaluate(`[...document.querySelectorAll('a')].find(a => a.textContent === 'Книжки').click()`)
  await page.sleep(300)
  await page.evaluate(`[...document.querySelectorAll('a')].find(a => a.textContent === 'Лісова пісня').click()`)
  await page.sleep(300)
  console.log(origin, 'після клацання:', await body())
  await page.send('Page.reload')
  await page.sleep(800)
  console.log(origin, 'після оновлення:', await body())
  console.log(origin, 'відповіді на запит документа:', statuses.join(', '))
}
```

Функція `body` повертає весь видимий текст сторінки одним рядком, а масив `statuses` збирає коди відповідей на запити
документа:

```text
http://localhost:4180 після клацання: Головна Книжки Моя полиця Лісова пісня Леся Українка
http://localhost:4180 після оновлення: Головна Книжки Моя полиця Лісова пісня Леся Українка
http://localhost:4180 відповіді на запит документа: / 200, /books/2 200
http://localhost:8010 після клацання: Головна Книжки Моя полиця Лісова пісня Леся Українка
http://localhost:8010 після оновлення: Not found
http://localhost:8010 відповіді на запит документа: / 200, /books/2 404
```

Поки людина клацала посилання, обидва сервери поводилися однаково, бо після першого запиту `/` сервер більше не брав
участі. Різниця з'явилася після оновлення. `vite preview` віддав `index.html`, і маршрутизатор показав книжку. Наш
сервер не знайшов файла `books/2` і відповів 404, тому людина побачила лише слова «Not found». Звичайний статичний
хостинг без правила поводиться як наш сервер. Тому практика дня каже: у `vite preview` оновлення працює, а на хостингу
спершу дасть 404.

Зверніть увагу й на рядок `4180 /assets/nope.js 200 text/html`. Правило «усі адреси віддають `index.html`»
спрацьовує й для файла, якого немає. Браузер, який просив скрипт, отримає сторінку HTML. Сьогодні це не заважає, а фаза
5 у днях «Викот статики як слід» і «Сервер: Oracle Cloud, k3s і SPA за HTTP» повернеться до цього: відсутній файл зі
скриптом має отримувати чесний 404.

### Ще одна причина білої сторінки: відносні шляхи

Правило для `index.html` працює лише тоді, коли сторінка називає свої скрипти повним шляхом від кореня сайту. Vite
так і робить за замовчуванням: у `dist/index.html` стоїть `src="/assets/index-Wjb_VSEm.js"`. Параметр `base` з
лекції «Збірка, перший викот і журнал вимірів» можна задати й відносним, `./`. Ми зібрали такий варіант і відкрили
дві адреси:

```text
$ npx vite build --base ./ --outDir dist-rel
$ grep -o '<script[^>]*>' dist-rel/index.html
<script type="module" crossorigin src="./assets/index-Wjb_VSEm.js">
```

```text
  скрипт: /assets/index-Wjb_VSEm.js 200 text/javascript
/ → текст сторінки: "Головна Книжки Моя полиця Домашня бібліотека"
  скрипт: /books/assets/index-Wjb_VSEm.js 404 text/plain
  журнал: Failed to load resource: the server responded with a status of 404 (Not Found)
/books/2 → текст сторінки: ""
```

На головній відносний шлях `./assets/...` дав правильну адресу. На `/books/2` браузер рахував його від теки `/books/`
і попросив `/books/assets/index-Wjb_VSEm.js`, якого немає. Сторінка лишилася білою. Тому застосунку з маршрутами
потрібен `base`, який починається з косої риски: `/` за замовчуванням або `/назва-теки/`, якщо сайт лежить не в
корені.

### Правило на Vercel

Практика плану викочує на Vercel. Цей розділ описано за документацією Vercel: облікового запису ми не мали, тому на
справжньому Vercel не перевіряли жодного кроку.

Сторінка `Vite on Vercel` у розділі `Using Vite to make SPAs` прямо каже, що для односторінкового застосунку на Vite
глибокі посилання одразу не працюють. Vercel сам розпізнає Vite і сам заповнює команду збірки й теку результату,
але не може здогадатися, що адреси обробляє JavaScript. Тому правило задають файлом `vercel.json`:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

Пройдімо цим файлом:

- `$schema` нічого не змінює на сервері. Цей рядок підказує редактору коду, які поля дозволені у файлі, і редактор
  підказуватиме їх під час набору.
- `rewrites` є переліком правил **переписування**. Переписування означає, що сервер віддає вміст іншої адреси, а
  адреса в браузері лишається тією, яку просили. Цим воно відрізняється від перенаправлення, після якого адреса в
  рядку змінюється.
- `source` є шаблоном шляху запиту. Запис `/(.*)` збігається з будь-яким шляхом.
- `destination` є шляхом, вміст якого віддати, тобто `/index.html`.

Чи не віддасть таке правило `index.html` замість бандла? Ні. Довідник `vercel.json` попереджає, що спершу Vercel
шукає справжній файл і лише потім застосовує переписування. Тому `/assets/index-....js` прийде як скрипт, а
`/items/2` отримає `index.html`.

Де лежить файл? Документація каже, що `vercel.json` створюють у кореневій теці проєкту. У вашому репозиторії
застосунок лежить у теці `spa/`, і в налаштуваннях Vercel ця тека записана в поле `Root Directory`, як описано в
розборі читання дня «Збірка, перший викот і журнал вимірів». Сторінка Vercel про монорепозиторії, тобто
репозиторії з кількома застосунками, кладе `vercel.json` у корінь кожного застосунку. Тому файл кладуть у `spa/`,
поруч із `package.json`. Посібник Vercel про помилки 404 пише «корінь репозиторію», бо має на увазі звичайний
випадок, коли застосунок лежить у самому корені. Ми цього не перевіряли, тож якщо правило не діє, спершу перевірте
місце файла. Той самий посібник додає ще два застереження. Файл має бути закомічений у git: якщо його немає в
репозиторії, правило не діє, а Vercel не повідомляє про помилку. І якщо в налаштуваннях вибрано набір `Other` замість
Vite, правило теж може не спрацювати.

Що ви маєте побачити, коли робитимете практику. До появи `vercel.json` головна сторінка відкривається, переходи
посиланнями працюють, а оновлення на адресі `/items/2` дає сторінку помилки 404 від Vercel, а не ваш застосунок.
Після того як файл закомічено й Vercel зібрав нову версію, оновлення на `/items/2` показує ваш екран сутності, а
вкладка «Мережа» показує для запиту документа статус 200.

### Netlify і Cloudflare

Якщо у фазі 1 ви вибрали інший хостинг, правило пишеться інакше. На Netlify його задають рядком
`/*  /index.html  200` у файлі `_redirects`, який має потрапити в теку результату, тобто в `spa/public/`, звідки Vite
копіює його в `dist`. Про це розповідає сторінка документації Netlify `Rewrites and proxies`, розділ `History
pushstate and single-page apps`. Cloudflare Pages окремого правила не потребує: якщо в корені результату немає файла
`404.html`, Pages сам вважає проєкт односторінковим застосунком. Це описує сторінка `Serving Pages`, розділ
`Single-page application (SPA) rendering`. Для Cloudflare Workers потрібен параметр `not_found_handling`, про який
розповідає сторінка `Single Page Application (SPA)` у документації Workers. Ці три сторінки ми лише прочитали, а не
перевіряли запуском.

## Маршрути в тестах

Усі досліди без браузера в цій лекції вживали `createMemoryRouter` замість `createBrowserRouter`. Він приймає те саме
дерево маршрутів і параметр `initialEntries` з початковими адресами. Так тест сам вирішує, з якої адреси почати, і не
залежить від адресного рядка jsdom, який один на весь файл тестів. Тести з маршрутами докладно вивчає день «Тести
з мережею» цієї фази.

Під час тесту полиці Vitest надрукував попередження `No HydrateFallback element provided to render during initial
hydration`. React Router повідомляє так, коли на першому відкритті сторінки маршрут має лоадер, а показувати на час
його роботи нічого. Поле `HydrateFallback` об'єкта маршруту дає компонент для цього часу. У браузері, і в режимі
розробки, і в продакшн-збірці, ми цього попередження в консолі не бачили. Ваш лоадер-охоронець працює миттєво, тому
показувати на цей час нічого не треба.

## Типові хибні уявлення

**«Захищений маршрут захищає дані».** Він лише не показує екрана. Наш один рядок у консолі відкрив полицю, а текст
нотатки лежав у бандлі, який отримує кожен. Дані без входу не має віддавати сервер.

**«Якщо в `vite preview` оновлення працює, на хостингу теж запрацює».** `vite preview` має вбудоване правило для
односторінкового застосунку, а наш простий сервер, як і хостинг без правила, відповів на `/books/2` статусом 404.

**«Порядок маршрутів у масиві вирішує, який спрацює».** Маршрут `books/new` переміг `books/:bookId`, хоча стояв після
нього. React Router ранжує шаблони, і сталий сегмент важить більше за параметр.

**«`useParams` дає число, якщо в адресі цифри».** Параметр завжди є рядком або `undefined`. TypeScript показав тип
`string | undefined`, і порівняння з числом без перетворення ніколи не спрацює.

**«Лоадер на батьківському маршруті зупиняє лоадери дітей».** Лоадер нотаток почав роботу раніше, ніж охоронець
вирішив перенаправити, бо маршрутизатор запускає лоадери ланцюжка одночасно.

**«`<Link>` і `<a>` однакові, бо обидва дають тег `<a>`».** Клацання на `<a>` завантажило сторінку заново, і мітка в
`window` зникла. Клацання на `<Link>` змінило адресу без нового запиту документа.

**«`..` у посиланні означає попередній сегмент адреси».** За замовчуванням `..` піднімається на один маршрут дерева. З
маршрутом `books/:bookId` воно повело на `/`, а на `/books` повело лише з `relative="path"`.

## Як це проявиться далі в React

- **Фаза 3, день 2, лоадери й дії.** Лоадер, який сьогодні лише перенаправляв, почне завантажувати дані сторінки до
  рендеру. Ви побачите одночасний запуск лоадерів не як підступ охоронця, а як спосіб прибрати чергу запитів. Форма
  маршрутизатора замінить `useNavigate` у сторінці входу.
- **Фаза 3, день 4, лоадер плюс кеш.** Лоадер маршруту попросить дані в кеша TanStack Query, і маршрут стане місцем,
  де сходяться адреса, дані й кеш.
- **Фаза 3, день 13, тести з мережею.** Маршрути з лоадерами тестуватимуть через тестовий маршрутизатор, як сьогодні
  `createMemoryRouter`.
- **Фаза 5, день 1, розділення коду.** Властивість `lazy` об'єкта маршруту дозволить вантажити код сторінки окремим
  файлом, лише коли людина на неї перейде. Це продовження `lazy` і `<Suspense>` з фази 2, дня 8. Довідник
  `RouterProvider` каже, що за замовчуванням маршрутизатор загортає свої оновлення в `startTransition`. Лекція фази 2,
  дня 8 показала, що оновлення в переході дозволяє React лишити на екрані вже показаний вміст, поки новий чекає. Як
  це виглядає з лінивими маршрутами, ви перевірите в той день.
- **Фаза 5, день 2, оточення й безпека фронтенду.** Сьогоднішня пастка повернеться прямим текстом: захищений маршрут
  є зручністю, а дані закриває сервер.
- **Фаза 5, дні 6 і 8, викот.** Правило «усі адреси віддають `index.html`» ви запишете для власного сервера nginx і
  відокремите його від файлів зі скриптами, щоб відсутній скрипт отримував чесний 404.

## Перевірте себе

**1. Людина на екрані «Книжки», вибраному через `useState`, натискає «Назад» у браузері. Що станеться і чому?**

<details><summary>Відповідь</summary>

Браузер піде на попередню сторінку в історії вкладки, тобто, найпевніше, піде з сайту. Перемикання стану не додало
запису в історію: наш тест показав, що адреса лишилася `/`, а записів в історії так і лишився один.

</details>

**2. У дереві є маршрути `books/:bookId` і `books/new`. Що покаже адреса `/books/new`, якщо `books/new` стоїть у масиві
другим?**

<details><summary>Відповідь</summary>

Сторінку `books/new`. React Router не бере перший маршрут, що підійшов, а ранжує шаблони, і сегмент зі сталим текстом
важить більше за параметр. Наш запуск `matchRoutes` дав для `/books/new` маршрут «нова книжка» з порожніми параметрами.

</details>

**3. Батьківський компонент маршруту має шапку, але не має `<Outlet />`. Що побачить людина на адресі дочірнього
маршруту?**

<details><summary>Відповідь</summary>

Лише шапку батька. Маршрут дитини збігся, але `<Outlet />` є тим місцем, де React рендерить наступний маршрут
ланцюжка. Без нього дитині немає де з'явитися.

</details>

**4. Сторінка сутності робить `ITEMS.find((i) => i.id === id)`, де `id` взято з `useParams`, а в масиві номери є
числами. Чому сторінка завжди каже, що запису немає?**

<details><summary>Відповідь</summary>

Параметр із `useParams` є рядком, наприклад `"2"`, а строге порівняння `===` числа з рядком завжди дає `false`.
Параметр треба перетворити на число, наприклад через `Number`, і окремо обробити випадок, коли запису з таким
номером немає.

</details>

**5. У `vite preview` оновлення на `/items/2` працює, а після викоту на Vercel дає 404. Що відбувається і що
виправити?**

<details><summary>Відповідь</summary>

Оновлення надсилає серверу запит `GET /items/2`. `vite preview` має вбудоване правило й віддає `index.html`, а
Vercel шукає файл `items/2`, не знаходить і відповідає 404. Виправлення полягає в правилі `rewrites` у `vercel.json`
з `source` `/(.*)` і `destination` `/index.html`. Файл кладуть у кореневу теку застосунку, тобто в `spa/`, поруч із
`package.json`, і комітять у git.

</details>

**6. Охоронець приватної зони стоїть на батьківському маршруті й перенаправляє на вхід. Дочірній маршрут має лоадер,
що запитує список замовлень. Чи піде запит, якщо людина не ввійшла?**

<details><summary>Відповідь</summary>

Піде. Маршрутизатор запускає лоадери всіх маршрутів ланцюжка одночасно, і в нашому досліді лоадер дитини почав
роботу раніше, ніж охоронець вирішив перенаправити. Тому сервер мусить сам перевіряти вхід для кожного запиту, а в
браузері перевірку треба ставити в кожен лоадер або в `middleware`.

</details>

**7. Колега каже: «Сторінка входу ховає адмінку, тож дані адмінки можна віддавати з API без перевірки». Що ви
відповісте?**

<details><summary>Відповідь</summary>

Перевірка в браузері нічого не гарантує. Наш один рядок у консолі, `sessionStorage.setItem('reader', ...)`, відкрив
приватну полицю, а запит до API можна надіслати й без браузера, наприклад командою `curl`. Дані без входу не має
віддавати сервер.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| маршрутизатор | бібліотека, яка пов'язує адресу в браузері з компонентами на екрані |
| історія сеансу | перелік адрес, які людина відвідала в одній вкладці; по ньому ходять «Назад» і «Вперед» |
| `pushState` | метод `history`, який додає запис в історію й міняє адресу без завантаження сторінки |
| `popstate` | подія вікна, яку браузер надсилає, коли людина ходить історією кнопками «Назад» і «Вперед» |
| режим даних | спосіб уживати React Router через `createBrowserRouter` і `<RouterProvider>`, з лоадерами й діями |
| об'єкт маршруту | об'єкт із полями `path`, `Component`, `children`, `index`, `loader`, що описує один маршрут |
| сегмент | частина адреси між косими рисками |
| параметр шляху | сегмент шаблону з двокрапкою, як-от `:bookId`; збігається з будь-яким сегментом і передає його значення рядком |
| ранжування маршрутів | спосіб, яким React Router вибирає найточніший шаблон, коли адресі відповідають кілька |
| каркас | батьківський компонент маршруту зі спільними частинами сторінок і `<Outlet />` |
| `<Outlet />` | місце в каркасі, де React рендерить наступний маршрут ланцюжка |
| індексний маршрут | маршрут з `index: true`, який показується за адресою батька |
| маршрут `*` | маршрут, що збігається з будь-якою адресою, яку не взяв жоден інший; підходить для сторінки 404 |
| межа помилок маршруту | поле `ErrorBoundary` об'єкта маршруту: компонент, який показується замість маршруту, коли сталася помилка |
| `NavLink` | посилання, яке знає, чи веде воно на поточну сторінку, і додає клас `active` та `aria-current="page"` |
| лоадер | функція маршруту, яку маршрутизатор викликає до рендеру сторінки |
| `redirect` | функція, що створює відповідь зі статусом 302 і заголовком `Location`; з лоадера вона веде на іншу адресу |
| захищений маршрут | маршрут, чий лоадер перенаправляє людину на вхід; ховає екран, але не дані |
| глибоке посилання | посилання на внутрішню сторінку застосунку, як-от `/books/2` |
| односторінковий застосунок | застосунок з одним `index.html`, де адреси обробляє JavaScript у браузері |
| переписування (rewrite) | правило сервера, яке віддає вміст іншої адреси, не змінюючи адреси в браузері |
| `createMemoryRouter` | маршрутизатор, що тримає історію в масиві; зручний для тестів |
