# Лекція. Фаза 3, день 2. Лоадери й дії маршруту

Учора кожен екран застосунку отримав адресу, а лоадер маршруту з'явився лише один раз: він не пускав на приватну
сторінку без входу. Сьогодні лоадер робить свою головну роботу, тобто завантажує дані сторінки ще до того, як React її
рендерить. Друга половина дня належить **діям**: дія обробляє форму, яку людина надіслала, і після неї маршрутизатор
сам оновлює дані на екрані. Читання займе близько 80 хвилин.

Числа й вивід у лекції отримано на React 19.3.1, React Router 8.5.3, Vite 8.3.6 і TypeScript 6.0.3. Досліди без
браузера запускалися у Vitest 5.1.0 із середовищем jsdom 31.0.0, тобто в імітації документа браузера всередині Node,
яка не малює й не ходить у мережу. Досліди в браузері запускалися в `chrome-headless-shell` версії 158, тобто в
Chromium без вікна, яким скрипт керував через протокол інструментів розробника. Сторінки віддавав невеликий сервер,
який ми написали самі: він віддає продакшн-збірку і відповідає на запити до API із затримкою 500 мс. Біля кожного
результату сказано, де і як його отримано.

Документація React Router у примірнику `react-router` доходить до версії 8.4.0, а ваш проєкт ставить 8.5.3. Ми
порівняли три сторінки, задані на сьогодні, у сховищі коду React Router за мітками двох версій: їхній текст
однаковий. Що змінилося у 8.5 біля теми дня, сказано в розборі читання. Сервер `react-router-docs` питайте з версією
`8`, бо точної версії 8.5.3 він не знає.

Практика дня будує вкладені екрани прокату спорядження. Щоб не показувати розв'язку, лекція бере інший об'єкт:
домашню бібліотеку з учорашньої лекції. Сьогодні в ній є сторінка автора, а всередині неї перелік його книжок.

**Після лекції ви зможете пояснити:**

- чому два вкладені екрани, які вантажать свої дані в ефектах, змушують людину чекати дві затримки замість однієї;
- коли саме маршрутизатор викликає лоадер і чому лоадери батька й дитини працюють одночасно;
- як компонент отримує дані лоадера через `useLoaderData` і як TypeScript дізнається їхній тип;
- що бачить людина, поки лоадери працюють, і як показати це хуком `useNavigation`;
- як лоадер скасовує запит, коли людина передумала, і як він повідомляє, що запису немає;
- як дія обробляє `<Form>` маршрутизатора і чому після неї лоадери запускаються знову;
- чим `useFetcher` відрізняється від `<Form>`;
- як виміряти водоспад і час до появи вмісту в Chrome з уповільненою мережею;
- чому лоадер разом з ефектом, що вантажить те саме, дає два запити й застарілий екран.

## Сторінка автора, яка з'являється частинами

Сторінка автора в нашій бібліотеці має адресу `/authors/1`. Вона складається з двох маршрутів. Батьківський маршрут
`authors/:authorId` показує ім'я автора й роки життя, а дочірній індексний маршрут показує в `<Outlet />` батька
перелік книжок цього автора. Індексний маршрут, нагадаємо з лекції «Маршрути», розділ «Індексний маршрут, маршрут
без шляху й маршрут без компонента», показується за адресою батька. Обидва маршрути беруть дані з API: автор лежить
за адресою `/api/authors/1`, а книжки за адресою `/api/authors/1/books`.

Найпростіший спосіб завантажити дані ви знаєте з фази 1: кожен компонент сам робить запит в ефекті. Лекція
«Синхронізація ефектами», розділ «Запит у мережу», розбирала цей спосіб разом із прапорцем `ignore`, який не дає
старій відповіді потрапити на екран. Ось обидва екрани, написані так:

```tsx
// src/authors/effect-pages.tsx, фрагмент
import { useEffect, useState } from 'react'
import { Outlet, useParams } from 'react-router'
import { getJson, type Author, type Book } from './api'

// Батьківський екран: сам вантажить автора в ефекті
// і показує дочірній екран лише тоді, коли автор уже є.
export function AuthorWithEffect() {
  const { authorId } = useParams()
  const [author, setAuthor] = useState<Author | null>(null)
  useEffect(() => {
    let ignore = false
    getJson<Author>(`/api/authors/${authorId}`).then((a) => {
      if (!ignore) setAuthor(a)
    })
    return () => {
      ignore = true
    }
  }, [authorId])
  if (!author) return <p>Завантаження автора…</p>
  return (
    <article>
      <h1>{author.name}</h1>
      <p>{author.years}</p>
      <Outlet />
    </article>
  )
}

// Дочірній екран: так само сам вантажить книжки в ефекті.
export function BooksWithEffect() {
  const { authorId } = useParams()
  const [books, setBooks] = useState<Book[] | null>(null)
  useEffect(() => {
    let ignore = false
    getJson<Book[]>(`/api/authors/${authorId}/books`).then((b) => {
      if (!ignore) setBooks(b)
    })
    return () => {
      ignore = true
    }
  }, [authorId])
  if (!books) return <p>Завантаження книжок…</p>
  return (
    <ul className="books">
      {books.map((b) => (
        <li key={b.id}>{b.title}</li>
      ))}
    </ul>
  )
}
```

Функція `getJson` лежить в окремому файлі. Вона робить запит через `fetch`, який ви знаєте з лекції «Мережа», і
повертає розібраний JSON:

```ts
// src/authors/api.ts, фрагмент
export type Author = { id: number; name: string; years: string }
export type Book = { id: number; title: string }

// GET-запит до API: повертає розібраний JSON або кидає помилку зі статусом відповіді.
export async function getJson<T>(path: string, signal?: AbortSignal): Promise<T> {
  const res = await fetch(path, { signal })
  if (!res.ok) throw new Error(`${path}: ${res.status}`)
  return (await res.json()) as T
}
```

Код виглядає правильним, і він справді працює. Подивімося, коли саме йдуть запити. У jsdom мережі немає, тому дослід
підміняє глобальну функцію `fetch` власною. Підмінена функція записує в журнал момент старту запиту, а через заданий
час повертає відповідь і записує момент відповіді. Автор у цьому досліді відповідає за 300 мс, а книжки за 500 мс:
різні числа допоможуть нижче побачити, на яку відповідь чекає маршрутизатор.

```ts
// src/authors/lab/fake-api.ts, фрагмент
export function installFakeApi(delays: { author: number; books: number }) {
  vi.stubGlobal('fetch', (path: string, init?: RequestInit) => {
    const method = init?.method ?? 'GET'
    log.push(`${now()} мс: старт ${method} ${path}`)
    const isBooks = path.endsWith('/books')
    const ms = isBooks ? delays.books : delays.author
    return new Promise<Response>((resolve, reject) => {
      const timer = setTimeout(() => {
        // …тут ще обробка POST-запиту, про неї в розділі про дії
        log.push(`${now()} мс: відповідь ${method} ${path}`)
        resolve(Response.json(isBooks ? books[id] : authors[id]))
      }, ms)
      // …тут ще обробка скасування, про неї в розділі «Людина передумала»
    })
  })
}
```

`vi.stubGlobal` є функцією Vitest, яка на час тесту заміняє глобальну змінну, тут `fetch`. Функція `now` повертає
мілісекунди від початку відліку, округлені до десятків. `Response.json` створює справжній об'єкт `Response` з тілом
JSON, тому код застосунку не помічає підміни.

Сам тест відкриває головну сторінку, клацає посилання «Леся Українка» і чекає, поки на екрані з'явиться назва книжки.
Невелика обгортка `watchRenders` записує в той самий журнал момент, коли React уперше рендерить компонент автора й
компонент книжок:

```tsx
// src/authors/lab/order.test.tsx
// @vitest-environment jsdom
import { fireEvent, render, screen } from '@testing-library/react'
import { createMemoryRouter, RouterProvider, type RouteObject } from 'react-router'
import { test } from 'vitest'
import { effectRoutes, loaderRoutes } from '../routes'
import { installFakeApi, log, now, resetClock } from './fake-api'

// Обгортка записує, коли React уперше рендерить сторінку автора й сторінку книжок.
function watchRenders(routes: RouteObject[]) {
  const author = routes[0].children![1]
  const books = author.children![0]
  for (const r of [author, books]) {
    const Inner = r.Component!
    r.Component = function Watched() {
      log.push(`${now()} мс: перший рендер ${Inner.name}`)
      return <Inner />
    }
  }
  return routes
}

for (const [name, routes] of [['ефекти', effectRoutes], ['лоадери', loaderRoutes]] as const) {
  test(name, async () => {
    installFakeApi({ author: 300, books: 500 })
    const router = createMemoryRouter(watchRenders(structuredClone2(routes)), { initialEntries: ['/'] })
    render(<RouterProvider router={router} />)
    await screen.findByRole('heading', { name: 'Автори бібліотеки' })
    resetClock()
    fireEvent.click(screen.getByRole('link', { name: 'Леся Українка' }))
    await screen.findByText('Камінний господар', {}, { timeout: 2000 })
    log.push(`${now()} мс: книжки на екрані`)
    console.log(`${name}:\n` + log.join('\n'))
  })
}

// Неглибока копія дерева, щоб обгортки не змінювали спільних об'єктів маршрутів.
function structuredClone2(routes: RouteObject[]): RouteObject[] {
  return routes.map((r) => ({ ...r, children: r.children && structuredClone2(r.children) }) as RouteObject)
}
```

Тест проходить двома деревами маршрутів. Дерево `effectRoutes` бере компоненти з ефектами, а `loaderRoutes` бере
лоадери, про які розповідає наступний розділ. `createMemoryRouter` є маршрутизатором, який тримає історію в масиві,
як у вчорашніх тестах. Ось вивід для ефектів:

```text
ефекти:
10 мс: перший рендер AuthorWithEffect
20 мс: старт GET /api/authors/1
320 мс: відповідь GET /api/authors/1
320 мс: перший рендер BooksWithEffect
330 мс: старт GET /api/authors/1/books
830 мс: відповідь GET /api/authors/1/books
830 мс: книжки на екрані
```

Прочитаймо його по кроках.

| Час | Хто діє | Що відбувається |
|-----|---------|-----------------|
| 0 мс | людина | клацає посилання; маршрутизатор змінює адресу на `/authors/1` |
| 10 мс | React | рендерить `AuthorWithEffect`; автора ще немає, тому компонент повертає «Завантаження автора…» без `<Outlet />` |
| 20 мс | ефект батька | після того як React показав рендер на екрані, запускається ефект і починає запит автора |
| 320 мс | ефект батька | відповідь прийшла, `setAuthor` просить новий рендер |
| 320 мс | React | рендерить батька з автором; тепер у ньому є `<Outlet />`, і React уперше рендерить `BooksWithEffect` |
| 330 мс | ефект дитини | лише тепер починається запит книжок |
| 830 мс | ефект дитини | книжки прийшли, перелік з'являється на екрані |

Запит книжок не залежить від відповіді про автора: для нього потрібен лише номер автора з адреси, а номер відомий ще
до першого рендеру. Проте книжки почали вантажитися на 330-й мілісекунді, тобто тоді, коли закінчився запит автора.
Ця черга виникла тому, що компонент книжок узагалі не існував, поки батько чекав на свої дані. Ефект запускається
лише після того, як компонент з'явився на екрані, тому запит дитини не міг початися раніше.

Ви вже бачили таку чергу в лекції «Асинхронність», розділ «Разом чи по черзі: запит починається в момент виклику».
Там два `await` поспіль змусили другий запит чекати на перший, і лекція назвала такі запити **водоспадом**: незалежні
запити, що даремно чекають один одного. Між компонентами водоспад з'являється сам, без жодного `await` поспіль у
коді. Його причина в тому, що дочірній компонент починає свій запит лише після того, як батько отримав свої дані й
показав дитину. Документація React у главі `Build a React app from Scratch`, розділ `Data Fetching`, пише саме про
це: запити з компонентів призводять до мережевих водоспадів, тому радить завантажувати дані в лоадерах маршрутизатора.
Цю пораду цитує вступ до фази 3 у плані.

## Що показав справжній браузер

У jsdom затримки задано числами в коді. У браузері до них додаються мережа, розмір бандла й сам рендер, тому ту саму
сторінку ми відкрили в Chrome. Для цього знадобилися дві речі: сервер, який відповідає на запити до API із затримкою,
і скрипт, який керує браузером і записує час.

### Сервер із затримкою API

Сервер віддає файли продакшн-збірки, тобто результату команди `vite build`. Запити до `/api/...` він обробляє сам:

```js
// lab-server.mjs, фрагмент
// Сервер досліду: віддає зібраний застосунок і відповідає на запити /api/... через 500 мс.
const DELAY = 500

createServer(async (req, res) => {
  const path = new URL(req.url, 'http://x').pathname
  if (path.startsWith('/api/')) {
    await sleep(DELAY) // затримка API: так довго «думає» справжній сервер
    const body = api(path)
    res.writeHead(body ? 200 : 404, { 'Content-Type': 'application/json', 'Cache-Control': 'no-store' })
    return res.end(JSON.stringify(body ?? { error: 'not found' }))
  }
  // …далі файл зі збірки або index.html для будь-якої іншої адреси, стиснутий gzip
}).listen(Number(port))
```

Функція `api` шукає автора чи книжки за адресою запиту. Заголовок `Cache-Control: no-store` забороняє браузеру
зберігати відповідь, тому кожен перехід робить справжній запит. Що означають заголовки кешу, пояснювала лекція
«Проєкт: Vite, лінт, TypeScript». Решта сервера віддає файли так само, як `vite preview`: на будь-яку адресу без файла
він повертає сторінку застосунку, а скрипти стискає gzip, як це робить хостинг.

Важлива деталь: затримка стоїть **на сервері**. Якби код застосунку чекав 500 мс через `setTimeout` перед тим, як
повернути вигадані дані, запиту в мережу не було б зовсім, і вкладка «Мережа» нічого б не показала. Уповільнення
мережі в Chrome теж нічого не змінило б, бо таймер у JavaScript не проходить через мережу.

### Уповільнена мережа

На вашому комп'ютері сервер стоїть поруч із браузером, тому мережа майже не забирає часу. Щоб наблизитися до телефона
на мобільному зв'язку, інструменти розробника Chrome уміють штучно уповільнювати мережу. У вкладці Network є список
Throttling із готовими наборами, і лекція «Мережа» вже згадувала його в розділі «Що ви побачите у вкладці «Мережа»».
Значення наборів ми взяли з коду самих інструментів розробника. Набір Slow 4G задає мінімальну затримку 562,5 мс,
швидкість завантаження 1,6 мегабіта за секунду й швидкість надсилання 0,75 мегабіта за секунду, обидві помножені на
0,9. Скрипт вмикає ті самі значення командою протоколу:

```js
// measure.mjs, фрагмент
// Пресет Slow 4G з коду DevTools: затримка 562,5 мс, 1,6 Мбіт/с униз, 0,75 Мбіт/с угору, з коефіцієнтом 0,9.
const SLOW_4G = { offline: false, latency: 562.5, downloadThroughput: (1.6e6 / 8) * 0.9, uploadThroughput: (750e3 / 8) * 0.9 }

await page.send('Network.setCacheDisabled', { cacheDisabled: true })
await page.send('Network.emulateNetworkConditions', net === 'slow' ? SLOW_4G : NONE)
```

Команда `Network.setCacheDisabled` робить те саме, що прапорець `Disable cache` у вкладці Network: браузер не бере
файлів зі збереженої копії. Команда `Network.emulateNetworkConditions` уповільнює мережу. Опис протоколу каже про
параметр `latency` важливу річ: це **мінімальна** затримка від надсилання запиту до отримання заголовків відповіді.
Тобто Chrome не додає 562,5 мс до кожного запиту, а лише не віддає відповідь раніше. Наш сервер і так думає 500 мс,
тому на запит до API уповільнення додає лише кілька десятків мілісекунд. Зате на великому файлі, як-от бандл,
повільний канал помітний дуже: це видно нижче. В описі протоколу цю команду позначено застарілою на користь новішої
пари команд, але вона працює, і для досліду цього досить.

### Що вимірює скрипт

**Часом до появи вмісту** ми називаємо проміжок від клацання на посилання до моменту, коли в документі є й ім'я
автора, і перелік книжок. Це наше власне визначення для сьогоднішнього досліду, а не стандартна метрика на кшталт LCP
з лекції «Збірка, перший викот і журнал вимірів». Щоб записати цей момент, скрипт до завантаження сторінки вставляє в
неї спостерігача за змінами документа:

```js
// measure.mjs, фрагмент
// Скрипт у сторінці: записує кожну зміну видимого тексту й момент, коли є і автор, і книжки.
const OBSERVER = `
  window.__tl = []; let last = null;
  new MutationObserver(() => {
    const t = (document.getElementById('root')?.innerText ?? '').replace(/\\s+/g, ' ').trim();
    if (t !== last) { last = t; window.__tl.push([performance.now(), t]) }
    if (window.__ready === undefined && document.querySelector('main h1') && document.querySelector('ul.books li'))
      window.__ready = performance.now();
  }).observe(document, { subtree: true, childList: true, characterData: true });`
```

`MutationObserver` є API браузера, яке викликає функцію щоразу, коли змінюється дерево документа. Функція записує в
масив `window.__tl` час і весь видимий текст сторінки, тобто те, що бачила людина, а коли в `<main>` вперше є і
заголовок, і пункт переліку, записує цей час у `window.__ready`. `performance.now()` повертає мілісекунди від
початку завантаження сторінки. Спостерігач бачить зміну документа, а не намальований кадр, тому справжня поява на
екрані може відставати ще на один кадр, тобто приблизно на 16 мс.

Для переходу скрипт відкриває головну сторінку, чекає, поки вона завантажиться, і клацає посилання:

```js
// measure.mjs, фрагмент
t0 = await page.evaluate(`(() => { window.__tl.length = 0; window.__ready = undefined;
  performance.clearResourceTimings(); const t = performance.now();
  [...document.querySelectorAll('a')].find((a) => a.textContent === 'Леся Українка').click(); return t })()`)
await waitReady()
```

Після появи вмісту скрипт читає з браузера `performance.getEntriesByType('resource')`. Це записи Resource Timing,
тобто початок і кінець кожного запиту, які браузер веде сам. Скрипт малює з них смужки так само, як це робить
стовпчик Waterfall у вкладці Network: один знак `█` означає 100 мс. Кожен варіант ми запускали п'ять разів поспіль і
наводимо всі п'ять чисел і медіану, тобто середнє за порядком значення, як у лекції «Збірка, перший викот і журнал
вимірів», розділ «Замір: три прогони й медіана».

## Лоадер: дані до рендеру

**Лоадер** є функцією в об'єкті маршруту, яку маршрутизатор викликає, коли людина переходить на адресу цього маршруту,
і робить це до рендеру його компонента. Що лоадер поверне, те компонент отримає хуком `useLoaderData`. Сторінка
`Data Loading` документації React Router каже саме це: коли людина переходить між маршрутами, лоадери викликаються
раніше, ніж рендериться компонент маршруту.

Ось ті самі два екрани з лоадерами. Функції лоадерів лежать в окремому файлі:

```ts
// src/authors/loaders.ts, фрагмент
import { type LoaderFunctionArgs } from 'react-router'
import { getJson, type Author, type Book } from './api'

// Лоадер батька: маршрутизатор викликає його до рендеру сторінки автора.
export async function authorLoader({ params, request }: LoaderFunctionArgs) {
  return getJson<Author>(`/api/authors/${params.authorId}`, request.signal)
}

// Лоадер дитини: маршрутизатор запускає його одночасно з лоадером батька.
export async function booksLoader({ params, request }: LoaderFunctionArgs) {
  return getJson<Book[]>(`/api/authors/${params.authorId}/books`, request.signal)
}
```

Пройдімо рядками:

- `LoaderFunctionArgs` є типом аргументу лоадера. Маршрутизатор передає лоадеру один об'єкт, і з нього тут узято два
  поля.
- `params` містить параметри шляху, ті самі, що компонент отримав би з `useParams`. Для адреси `/authors/1` поле
  `params.authorId` дорівнює рядку `"1"`.
- `request` є об'єктом `Request` з Fetch API, тобто описом запиту на нову адресу. Учора лоадер-охоронець брав із нього
  `request.url`. Сьогодні знадобилося інше поле, `request.signal`. Це сигнал скасування, такий самий, як у лекції
  «Мережа», розділ «`AbortController` і `AbortSignal`: як зупинити роботу». Маршрутизатор подає цей сигнал, коли
  перехід скасовано, а лоадер передає його у `fetch`. Що це дає, покаже розділ «Людина передумала».
- Лоадер повертає проміс із даними. Маршрутизатор чекає на нього сам, тому `async` і `return` достатньо.

Компоненти тепер не мають ні стану, ні ефектів:

```tsx
// src/authors/loader-pages.tsx, фрагмент
import { Outlet, useLoaderData } from 'react-router'
import type { authorLoader, booksLoader } from './loaders'

export function AuthorRoute() {
  const author = useLoaderData<typeof authorLoader>()
  return (
    <article>
      <h1>{author.name}</h1>
      <p>{author.years}</p>
      <Outlet />
    </article>
  )
}

export function BooksRoute() {
  const books = useLoaderData<typeof booksLoader>()
  return (
    <ul className="books">
      {books.map((b) => (
        <li key={b.id}>{b.title}</li>
      ))}
    </ul>
  )
}
```

`useLoaderData` повертає дані лоадера **свого** маршруту. `AuthorRoute` отримує автора, а `BooksRoute` отримує книжки,
хоча обидва компоненти рендеряться на одній сторінці. Перевірки `if (!author)` більше немає: коли React рендерить
компонент, дані вже є. Запис `<typeof authorLoader>` розбирає розділ «Типи даних лоадера» нижче.

Лишилося пов'язати лоадери з маршрутами в дереві:

```tsx
// src/authors/routes.tsx, фрагмент
import type { RouteObject } from 'react-router'
import { Home, Layout } from './layout'
import { AuthorRoute, BooksRoute } from './loader-pages'
import { authorLoader, booksLoader } from './loaders'

export const loaderRoutes: RouteObject[] = [
  {
    path: '/',
    Component: Layout,
    children: [
      { index: true, Component: Home },
      {
        path: 'authors/:authorId',
        loader: authorLoader,
        Component: AuthorRoute,
        children: [{ index: true, loader: booksLoader, Component: BooksRoute }],
      },
    ],
  },
]
```

Поле `loader` ви бачили вчора в таблиці полів об'єкта маршруту. Кожен маршрут отримує власний лоадер, тому кожен
екран і далі відповідає лише за свої дані, як і з ефектами.

### Чому лоадери в окремому файлі

Спершу ми написали лоадери в тому самому файлі, що й компоненти. Лінт проєкту, який ви налаштували у фазі 0, на це
поскаржився:

```text
$ npx eslint src/authors
src/authors/loader-pages.tsx
  16:23  error  Fast refresh only works when a file only exports components. Use a new file to share constants or functions between components  react-refresh/only-export-components
  21:23  error  Fast refresh only works when a file only exports components. Use a new file to share constants or functions between components  react-refresh/only-export-components
  26:23  error  Fast refresh only works when a file only exports components. Use a new file to share constants or functions between components  react-refresh/only-export-components
```

Правило `react-refresh/only-export-components` стежить за швидким оновленням у режимі розробки, тобто за тим, як Vite
підміняє змінений компонент без перезавантаження сторінки. Підміна працює лише для файлів, які експортують тільки
компоненти. Тому лоадери й дії кладуть в окремий файл, а компоненти імпортують із нього лише тип. Запис
`import type { authorLoader } from './loaders'` бере тільки тип функції: у зібраному коді цього імпорту не буде.

### Той самий журнал із лоадерами

Тест із розділу про ефекти ми вже запускали з другим деревом, `loaderRoutes`. Ось його вивід:

```text
лоадери:
0 мс: старт GET /api/authors/1
0 мс: старт GET /api/authors/1/books
300 мс: відповідь GET /api/authors/1
500 мс: відповідь GET /api/authors/1/books
510 мс: перший рендер AuthorRoute
510 мс: перший рендер BooksRoute
520 мс: книжки на екрані
```

| Час | Хто діє | Що відбувається |
|-----|---------|-----------------|
| 0 мс | людина | клацає посилання |
| 0 мс | маршрутизатор | зіставляє `/authors/1` з деревом, отримує ланцюжок «каркас, автор, книжки» і викликає обидва лоадери; каркас лоадера не має |
| 300 мс | лоадер автора | дані автора готові, але маршрутизатор ще чекає |
| 500 мс | лоадер книжок | готові всі лоадери ланцюжка |
| 510 мс | React | рендерить автора й книжки одним разом, уже з даними |

Обидва запити почалися на нульовій мілісекунді, у момент клацання, і жоден компонент ще не рендерився. Маршрутизатор
дочекався найповільнішого лоадера й лише тоді показав сторінку. Так поводиться `Promise.all` з лекції «Асинхронність»:
він чекає на всі проміси, тож загальний час дорівнює найдовшому з них. Тому сторінка з'явилася на 520-й мілісекунді,
а не на 830-й, і різниця дорівнює якраз затримці автора, яку ефекти ставили в чергу перед книжками.

Учора ви бачили той самий одночасний запуск із неприємного боку: лоадер нотаток почав роботу раніше, ніж охоронець
вирішив перенаправити людину. Сьогодні та сама поведінка прибирає водоспад.

### Водоспад робить умова, а не ефект

Чесно скажемо ще одне. Водоспад у версії з ефектами з'явився через рядок `if (!author) return <p>Завантаження
автора…</p>`: поки автора немає, батько не рендерить `<Outlet />`, і дитина не існує. Ми зібрали третій варіант,
`AuthorWithEffectOpen`, де батько показує `<Outlet />` одразу, а замість імені поки пише «Завантаження автора…».
Дитина з'являється в першому ж рендері й починає свій запит одночасно з батьком:

```text
$ node measure.mjs effects-open 4302 nav slow 5
effects-open nav slow: час до вмісту, мс: 589, 586, 585, 588, 581; медіана 586
  /api/authors/1/books       3–571   ██████
  /api/authors/1             4–580   ██████
  що бачила людина:
      3 мс: Головна Леся Українка Іван Франко Завантаження автора… Завантаження книжок…
    573 мс: Головна Леся Українка Іван Франко Завантаження автора… Лісова пісня Камінний господар Бояриня
    581 мс: Головна Леся Українка Іван Франко Леся Українка 1871–1913 Лісова пісня Камінний господар Бояриня
```

За часом цей варіант не гірший за лоадери: 586 мс проти 583 мс, а на першому відкритті з уповільненням 2287 мс проти
2286 мс. Чому ж план радить лоадери? Подивіться на те, що бачила людина. Протягом 8 мс на екрані були книжки без
автора, а до того два різні повідомлення про завантаження. Чим більше вкладених екранів, тим більше таких проміжних
станів, і кожен компонент сам відповідає за свої гонки й скасування. Крім того, щоб уникнути водоспаду з ефектами,
треба пам'ятати, що жоден батько не може ховати `<Outlet />`, поки чекає. Перша ж така умова, дописана через місяць,
поверне сходинку. Лоадер не залежить від того, що рендерить батько: маршрутизатор знає всі лоадери ланцюжка з дерева
маршрутів і запускає їх у момент переходу. Сторінка з'являється одним разом, коли готові всі дані. А далі в цій лекції
ви побачите, що лоадер ще й сам скасовує застарілі запити й сам оновлює дані після дії.

## Що бачить людина, поки лоадери працюють

З ефектами людина одразу бачить нову сторінку з повідомленням «Завантаження…». З лоадерами маршрутизатор не рендерить
нової сторінки, поки дані не готові. Що тоді на екрані?

Ми перевірили це в jsdom тим самим деревом `loaderRoutes`. Тест клацає посилання й кожні 200 мс друкує стан переходу,
адресу, рядок у шапці, клас посилання й текст у `<main>`:

```tsx
// src/authors/lab/pending.test.tsx, фрагмент
fireEvent.click(screen.getByRole('link', { name: 'Леся Українка' }))
// Кожні 200 мс дивимося на стан переходу, адресу, шапку й вміст <main>.
for (let i = 0; i < 4; i++) {
  await new Promise((r) => setTimeout(r, i === 0 ? 100 : 200))
  const nav = router.state.navigation
  const link = screen.getByRole('link', { name: 'Леся Українка' })
  console.log(
    `${now()} мс: ${nav.state.padEnd(7)} | navigation.location ${nav.location?.pathname ?? '—'} | адреса ${router.state.location.pathname}`,
    `| шапка: ${screen.queryByRole('status')?.textContent ?? '—'} | клас посилання: "${link.className}"`,
    `| main: ${document.querySelector('main')?.textContent}`,
  )
}
```

лишалася `/`. Нова адреса жила окремо, у полі `navigation.location`. Коли всі лоадери закінчили, адреса змінилася,
стара сторінка зникла, а нова з'явилася одразу з даними. Посібник Address Book у документації React Router описує
це так: маршрутизатор лишає стару сторінку, поки вантажаться дані наступної.

Людина при цьому клацнула посилання й пів секунди не бачить жодної зміни. Тому їй треба показати, що перехід триває.
Це роблять двома способами.

**Загальний індикатор через `useNavigation`.** Хук повертає об'єкт поточного переходу. Його поле `state` має одне з
трьох значень: `idle`, коли нічого не відбувається, `loading`, коли маршрутизатор чекає лоадерів, і `submitting`,
коли працює дія. Наш каркас показує рядок у шапці:

```tsx
// src/authors/layout.tsx, фрагмент
import { NavLink, Outlet, useNavigation } from 'react-router'

export function Layout() {
  const navigation = useNavigation()
  return (
    <>
      <header>
        <nav>
          <NavLink to="/" end>Головна</NavLink> <NavLink to="/authors/1">Леся Українка</NavLink>{' '}
          <NavLink to="/authors/2">Іван Франко</NavLink>
        </nav>
        {navigation.state !== 'idle' && <p role="status">Завантаження…</p>}
      </header>
      <main>
        <Outlet />
      </main>
    </>
  )
}
```

Атрибут `role="status"` каже програмі читання з екрана, що в цьому елементі з'являються повідомлення про стан, і вона
прочитає їх уголос. У виводі тесту рядок «Завантаження…» стоїть у шапці, поки `state` дорівнює `loading`.

**Місцевий індикатор через `NavLink`.** Учора `NavLink` додавав клас `active` посиланню на поточну сторінку. Під час
переходу він додає посиланню, на яке клацнули, клас `pending`. У виводі видно обидва: спершу `pending`, після переходу
`active`. CSS може, наприклад, зробити таке посилання сірим.

### Перше відкриття сторінки

немає. Маршрутизатор однаково чекає лоадерів, а React до того нічого не рендерить. Браузерний замір вище показав це
рядком `578 мс: (порожньо)`: до 2286-ї мілісекунди сторінка була білою, хоча бандл завантажився вже до 1697-ї.

## Типи даних лоадера

Звідки компонент знає, що `author` має поле `name`? Запис `useLoaderData<typeof authorLoader>()` передає хуку тип
функції лоадера. Оператор `typeof` у позиції типу бере тип наявного значення. Ви бачили його в лекції «Ref» фази 1, де
запис `ReturnType<typeof setTimeout>` брав тип результату функції `setTimeout`. Хук сам дістає з типу функції те, що
вона повертає, і знімає з нього проміс. Ми навмисно звернулися до поля, якого немає, двічі: з типом і без нього.

```tsx
// src/authors/tscheck/types.tsx
// Перевірка типів: що TypeScript знає про дані лоадера.
import { useLoaderData } from 'react-router'
import type { authorLoader } from '../loaders'

export function Typed() {
  const author = useLoaderData<typeof authorLoader>()
  return <p>{author.name}{author.title}</p>
}

export function Untyped() {
  const author = useLoaderData()
  return <p>{author.name}{author.title}</p>
}
```

```text
$ npx tsc --noEmit -p tsconfig.app.json
src/authors/tscheck/types.tsx(7,34): error TS2339: Property 'title' does not exist on type 'Author'.
```

Помилка одна, у компоненті `Typed`: TypeScript знає, що лоадер повертає `Author`, а в цього типу поля `title` немає.
Компонент `Untyped` пройшов перевірку мовчки, бо без параметра типу `useLoaderData` повертає `any`, тобто тип, з яким
TypeScript дозволяє все. Тому параметр `typeof` варто писати завжди.

Зверніть увагу, що тип узято з `getJson<Author>`. Сервер може прислати що завгодно, а `as T` усередині `getJson` лише
обіцяє TypeScript, що прийшов `Author`. Перевіряти, що дані справді мають потрібну форму, вміє бібліотека zod, яку
план бере в дні «React Hook Form і zod» цієї фази.

## Коли даних немає: помилка з лоадера

Учора сторінка книжки сама показувала «Книжки немає», а лекція обіцяла інший спосіб. Лоадер може **кинути** відповідь
зі статусом, і тоді маршрутизатор не рендерить компонент, а показує межу помилок маршруту, тобто поле
`ErrorBoundary`, з учорашнього розділу «Сторінка 404». Відповідь зручно створити функцією `data` з React Router:

```tsx
// src/authors/lab/error.test.tsx, фрагмент
import { data, isRouteErrorResponse, useLoaderData, useRouteError, type LoaderFunctionArgs } from 'react-router'

const AUTHORS: Record<string, string> = { '1': 'Леся Українка' }

// Лоадер сам каже маршрутизатору, що автора немає.
function authorLoader({ params }: LoaderFunctionArgs) {
  const name = AUTHORS[params.authorId ?? '']
  if (!name) throw data(`Автора ${params.authorId} немає`, { status: 404 })
  return { name }
}

function Author() {
  const { name } = useLoaderData<typeof authorLoader>()
  return <h1>{name}</h1>
}

function AuthorError() {
  const error = useRouteError()
  if (isRouteErrorResponse(error)) return <h1>{error.status}: {error.data}</h1>
  return <h1>Щось зламалося</h1>
}

test('лоадер кидає 404', async () => {
  for (const url of ['/authors/1', '/authors/9']) {
    const router = createMemoryRouter(
      [{ path: '/authors/:authorId', loader: authorLoader, Component: Author, ErrorBoundary: AuthorError }],
      { initialEntries: [url] },
    )
    const { unmount } = render(<RouterProvider router={router} />)
    console.log(url, '→', (await screen.findByRole('heading')).textContent)
    unmount()
  }
})
```

```text
/authors/1 → Леся Українка
/authors/9 → 404: Автора 9 немає
```

`data(значення, { status: 404 })` створює об'єкт із даними й статусом. Коли лоадер його кидає, маршрутизатор
записує помилку в стан і рендерить `ErrorBoundary`. Функція `isRouteErrorResponse` перевіряє, що помилка є саме
такою відповіддю зі статусом, і тоді в неї є поля `status` і `data`. Компонент `Author` тепер завжди отримує
справжнього автора: випадок «немає» обробляє окремий компонент. Лоадер тут не асинхронний, бо дані лежать у пам'яті.
Маршрутизатор приймає і звичайне значення, і проміс.

## Дія: форма маршрутизатора

Досі дані тільки читали. Тепер людина хоче додати книжку до переліку автора. Учора сторінка входу обробляла форму
сама: `onSubmit`, `e.preventDefault()` і `useNavigate`. Маршрутизатор пропонує інший шлях.

**Дія** (action) є функцією в об'єкті маршруту, яку маршрутизатор викликає, коли людина надсилає форму на адресу цього
маршруту методом POST. **Форма маршрутизатора** є компонентом `<Form>` з React Router. Вона рендерить звичайний тег
`<form>`, але, коли людина її надсилає, маршрутизатор не дає браузеру завантажити сторінку, а сам збирає поля форми
й викликає дію. Сторінка `Actions` документації називає ще одну властивість, заради якої все це існує: коли дія
закінчилася, маршрутизатор знову завантажує дані всіх лоадерів на сторінці, тому екран сам показує зміни.

Дія для книжок лежить у тому самому файлі, що й лоадери:

```ts
// src/authors/loaders.ts, фрагмент
import { data, type ActionFunctionArgs } from 'react-router'
import { postJson } from './api'

// Дія дитини: обробляє надіслану форму «Додати книжку».
export async function addBookAction({ params, request }: ActionFunctionArgs) {
  const form = await request.formData()
  const title = String(form.get('title') ?? '').trim()
  if (title === '') {
    return data({ error: 'Впишіть назву книжки' }, { status: 400 })
  }
  await postJson(`/api/authors/${params.authorId}/books`, { title }, request.signal)
  return null
}
```

- Дія отримує той самий об'єкт аргументів, що й лоадер. Тепер `request` є запитом із методом POST і тілом, у якому
  лежать поля форми.
- `request.formData()` читає тіло як `FormData`, тобто набір пар «ім'я поля, значення». MDN описує цей об'єкт на
  сторінці `FormData`. `form.get('title')` повертає значення поля з атрибутом `name="title"`.
- Якщо назва порожня, дія повертає `data(...)` зі статусом 400, тобто «запит неправильний». Що з цим робить
  маршрутизатор, видно нижче.
- Інакше дія надсилає книжку на сервер функцією `postJson`, яка робить `fetch` з методом POST і тілом JSON, і
  повертає `null`, бо нічого показувати не треба.

Компонент книжок отримує форму:

```tsx
// src/authors/loader-pages.tsx, фрагмент
export function BooksRoute() {
  const books = useLoaderData<typeof booksLoader>()
  const result = useActionData<typeof addBookAction>()
  const navigation = useNavigation()
  return (
    <>
      <ul className="books">
        {books.map((b) => (
          <li key={b.id}>{b.title}</li>
        ))}
      </ul>
      <Form method="post">
        <input name="title" aria-label="Назва" />
        <button>{navigation.state === 'submitting' ? 'Додаю…' : 'Додати'}</button>
      </Form>
      {result?.error && <p role="alert">{result.error}</p>}
    </>
  )
}
```

А маршрут книжок отримує поле `action`:

```tsx
// src/authors/routes.tsx, фрагмент
children: [{ index: true, loader: booksLoader, action: addBookAction, Component: BooksRoute }],
```

- `<Form method="post">` не має атрибута `action`. Тоді, як каже довідник `Form`, форма надсилається найближчому
  маршруту, тобто маршруту, у якому її відрендерено. Тут це індексний маршрут книжок.
- Поле введення має `name="title"`. Без атрибута `name` поле не потрапить у `FormData`, і дія його не побачить.
- `useActionData` повертає те, що повернула дія, або `undefined`, поки дія не працювала.
- `navigation.state === 'submitting'` означає, що дія ще працює. Кнопка в цей час каже «Додаю…».

```text
160 мс: старт GET /api/authors/1
160 мс: старт GET /api/authors/1/books
260 мс: відповідь GET /api/authors/1
260 мс: відповідь GET /api/authors/1/books
260 мс: стан idle
270 мс: «Бояриня» в списку; книжок: 3; historyAction PUSH
```

| Час | Стан переходу | Що відбувається |
|-----|---------------|-----------------|
| 50 мс | `submitting` | маршрутизатор зібрав форму й викликав дію; кнопка каже «Додаю…» |
| 60–160 мс | `submitting` | дія надсилає книжку на сервер і чекає відповіді |
| 160 мс | `loading` | дія закінчилася успішно, і маршрутизатор знову запускає **обидва** лоадери сторінки |
| 260 мс | `idle` | лоадери повернули свіжі дані, і в переліку вже три книжки |

Ніде в коді немає рядка «після додавання оновити перелік». Маршрутизатор зробив це сам: після успішної дії він
перезапустив лоадери всіх маршрутів, які зараз на екрані. Документація називає це **повторною перевіркою** даних
(revalidation). Вона перезапустила навіть лоадер автора, хоча автор не змінився. Сторінка `Revalidation Optimization`
показує, як вимкнути це для окремого маршруту полем `shouldRevalidate`, але радить спершу лишити типову поведінку.

У виводі є ще три деталі.

**`formAction` закінчується на `?index`.** Батько й індексний маршрут мають ту саму адресу `/authors/1`. Щоб
маршрутизатор знав, кому з них надіслати форму, форма в індексному маршруті сама дописує до адреси параметр
`?index`. Про це є окрема сторінка документації `Index Query Param`.

**`formMethod POST` великими літерами.** Ви писали `method="post"`, а маршрутизатор зберігає метод так, як його
пишуть у протоколі HTTP.

**`historyAction PUSH`.** Надсилання `<Form>` є переходом, і маршрутизатор додав запис в історію вкладки. Сторінка
`Actions` попереджає про це прямо. Наступний підрозділ показує, коли це важить.

### Помилка перевірки: статус 400

Тепер тест натискає кнопку з порожнім полем:

```tsx

```

```text
10 мс: повідомлення: Впишіть назву книжки
310 мс: стан idle; GET-запитів після дії: 0
actionData: {"0-1-0":{"error":"Впишіть назву книжки"}}
```

Повідомлення з'явилося через `useActionData`. Лоадери цього разу не запускалися жодного разу. Сторінка `Revalidation
Optimization` пояснює чому: у режимі даних надсилання, яке закінчилося статусом 4xx чи 5xx, не перезапускає
лоадерів, бо дані на сервері не змінилися. У стані маршрутизатора результат дії лежить під ідентифікатором маршруту
`0-1-0`. Такі ідентифікатори маршрутизатор складає сам із номерів маршрутів у дереві, якщо ви не задали поле `id`.

Тут варто сказати, чого ця дія не робить. Повідомлення з'являється лише після надсилання, поле не перевіряється під
час набору, а введене значення після помилки не підсвічується. Усе це тема днів про форми React 19 і React Hook Form
цієї фази. Сьогодні досить того, що дія повертає помилку, а компонент її показує.

### Вхід через дію

Учора сторінка входу вживала `useNavigate` лише тому, що форми маршрутизатора ви ще не знали. Ось та сама сторінка з
дією. Тест перевіряє дві функції React Router для перенаправлення з дії, `redirect` і `replace`:

```tsx
// src/authors/lab/login.test.tsx, фрагмент
// Сторінка входу з першого дня, але з формою маршрутизатора замість onSubmit і useNavigate.
const makeLogin = (go: typeof redirect) => async ({ request }: ActionFunctionArgs) => {
  const form = await request.formData()
  sessionStorage.setItem('reader', String(form.get('name')))
  const from = new URL(request.url).searchParams.get('from') ?? '/'
  return go(from)
}

function Login() {
  return (
    <Form method="post">
      <h1>Вхід</h1>
      <input name="name" aria-label="Ім'я" />
      <button>Увійти</button>
    </Form>
  )
}

for (const [name, go] of [['redirect', redirect], ['replace', replace]] as const) test(name, async () => {
  // …маршрути /books, /login з дією makeLogin(go) і /shelf; історія [/books, /login?from=%2Fshelf]
  fireEvent.change(screen.getByLabelText("Ім'я"), { target: { value: 'Оксана' } })
  fireEvent.click(screen.getByRole('button'))
  console.log(`${name}: після входу`, (await screen.findByRole('heading', { name: /Полиця/ })).textContent, '| адреса', router.state.location.pathname, '| historyAction', router.state.historyAction)
  await router.navigate(-1)
  console.log(`${name}: «Назад» після входу веде на`, router.state.location.pathname + router.state.location.search)
})
```

```text
атрибути форми: post /login?from=%2Fshelf
redirect: після входу Полиця, Оксана | адреса /shelf | historyAction PUSH
redirect: «Назад» після входу веде на /login?from=%2Fshelf
replace: після входу Полиця, Оксана | адреса /shelf | historyAction REPLACE
replace: «Назад» після входу веде на /books
```

Перший рядок показує, що `<Form>` відрендерив тег `<form>` зі справжньою адресою дії, разом із параметром `from`.
Тому дія прочитала `from` з `request.url`. `redirect` після дії додав новий запис, і кнопка «Назад» повела людину,
яка вже ввійшла, знову на сторінку входу. `replace` створює таке саме перенаправлення, але заміняє поточний запис
історії, як учорашній `navigate(..., { replace: true })`, і «Назад» повів на перелік книжок.

## Дія без переходу: `useFetcher`

Буває, що форма не повинна бути переходом. Людина позначає книжку прочитаною й лишається на тій самій сторінці, а
запис в історії для цього зайвий. Для цього є `useFetcher`. Хук повертає об'єкт **фетчера**, тобто окремого
виконавця запитів із власним станом. Його форма `<fetcher.Form>` викликає ту саму дію маршруту, але не змінює
`navigation` і не додає запису в історію. Сторінка `Actions` описує це одним реченням, і ми перевірили його:

```tsx
// src/authors/lab/fetcher.test.tsx, фрагмент
function Book() {
  const book = useLoaderData<{ title: string; read: boolean }>()
  const fetcher = useFetcher()
  // Оптимістичний показ: поки дія працює, беремо значення з надісланої форми.
  const shown = fetcher.formData ? fetcher.formData.get('read') === 'yes' : book.read
  return (
    <fetcher.Form method="post">
      <h1>{book.title}</h1>
      <button name="read" value={shown ? 'no' : 'yes'}>{shown ? 'Прочитано' : 'Не прочитано'}</button>
      <span>fetcher.state={fetcher.state}</span>
    </fetcher.Form>
  )
}
```

Лоадер маршруту `/books/:id` повертає книжку через 100 мс і рахує свої виклики, а дія через 100 мс записує позначку.
Тест друкує стан до клацання і в три моменти після нього:

```text
до клацання:     кнопка «Не прочитано» | fetcher.state=idle | navigation.state=idle | лоадер викликано 1 р. | адреса /books/11 | historyAction POP
через 10 мс:     кнопка «Прочитано» | fetcher.state=submitting | navigation.state=idle | лоадер викликано 1 р. | адреса /books/11 | historyAction POP
через 150 мс:    кнопка «Прочитано» | fetcher.state=loading | navigation.state=idle | лоадер викликано 2 р. | адреса /books/11 | historyAction POP
через 300 мс:    кнопка «Прочитано» | fetcher.state=idle | navigation.state=idle | лоадер викликано 2 р. | адреса /books/11 | historyAction POP
```

Стан змінювався в самого фетчера: `submitting`, потім `loading`, потім `idle`. А `navigation.state` весь час лишався
`idle`, адреса не змінилася, і `historyAction` лишився `POP`, тобто значенням від першого відкриття. Лоадер після дії
все одно перезапустився: фетчер теж запускає повторну перевірку.

Напис на кнопці змінився вже через 10 мс, хоча дія ще працювала. Це **оптимістичний показ**: поки дія не закінчилася,
компонент бере значення з `fetcher.formData`, тобто з форми, яку людина щойно надіслала, і показує результат
заздалегідь. Розділ `Optimistic UI` сторінки `Pending UI` показує той самий прийом.

А якщо сервер відповів помилкою? Ми змінили дію так, щоб вона через 100 мс повертала статус 500, тобто «помилка
сервера», а лоадер завжди казав, що книжку не прочитано:

```tsx

console.log('через 210 мс:', screen.getByRole('button').textContent, '| лоадер викликано', loaderCalls, 'р.')
```


Поки дія працювала, кнопка оптимістично казала «Прочитано». Коли дія закінчилася помилкою, `fetcher.formData` зник, а
лоадер не перезапускався, бо статус 500 не запускає повторної перевірки. Тому кнопка повернулася до значення з
лоадера. Людина побачила, що позначка не вдалася, але не дізналася чому. Як показати причину й поєднати все це з
кешем, розбирає день «Мутації й оптимістичні оновлення» цієї фази.

## Пастка: лоадер і ефект з тим самим запитом

Коли код переписують з ефектів на лоадери, легко лишити старий ефект на місці. Ось компонент книжок після такого
недбалого переписування:

```tsx
// src/authors/loader-pages.tsx, фрагмент
// Пастка: лоадер уже приніс книжки, а компонент вантажить їх ще раз в ефекті.
export function BooksRouteTwice() {
  const fromLoader = useLoaderData<typeof booksLoader>()
  const { authorId } = useParams()
  const [books, setBooks] = useState<Book[]>(fromLoader)
  useEffect(() => {
    let ignore = false
    getJson<Book[]>(`/api/authors/${authorId}/books`).then((b) => {
      if (!ignore) setBooks(b)
    })
    return () => {
      ignore = true
    }
  }, [authorId])
  return (
    <ul className="books">
      {books.map((b) => (
        <li key={b.id}>{b.title}</li>
      ))}
    </ul>
  )
}
```

Екран виглядає правильно, тести на вміст проходять. Порахуймо запити. Тест відкриває `/authors/1` двічі, без
`<StrictMode>` і з ним, і рахує старти запиту книжок:

ще й тримає власну копію в стані. Тест викликає `router.navigate` з методом POST, і маршрутизатор поводиться так, ніби
людина надіслала `<Form>` на індексному маршруті:

```tsx
const loaderBooks = (router.state.loaderData['0-0'] as { title: string }[]).map((b) => b.title)
```


Лоадер після дії приніс нову книжку в обох випадках. Але компонент із власним станом показав старий перелік.
Значення `fromLoader` потрапило в `useState` лише як початкове, а ефект залежить тільки від `authorId`, який не
змінився. Отже, копія даних лоадера в стані перестала оновлюватися разом із лоадером. Наступного дня ви зустрінете ту
саму помилку з даними TanStack Query.

Як уникнути пастки: після переходу на лоадер приберіть з компонента і ефект, і стан для цих даних. Компонент читає
дані лише через `useLoaderData`. Перевірити легко: у вкладці Network на один перехід має бути рівно один запит на
кожні дані.

## Як виміряти самому

Ось що побачите ви, коли повторите заміри в Chrome з вікном. Самі ми працювали без вікна, тому опис вкладки нижче
спирається на документацію Chrome і на числа, які той самий браузер віддав скрипту.

1. Зберіть продакшн-збірку й відкрийте її. Режим розробки не годиться для замірів, як пояснює лекція «Інструменти
   браузера», розділ «Чому швидкість не міряють у режимі розробки», а `<StrictMode>` там ще й подвоює ефекти.
2. Відкрийте інструменти розробника, вкладку Network, поставте прапорець `Disable cache` і виберіть у списку
   Throttling набір `Slow 4G`.
3. Перейдіть на сторінку з вкладеними екранами. У стовпчику Waterfall запити до API стоятимуть сходинкою, якщо екрани
   вантажать дані в ефектах і батько ховає `<Outlet />`, і одне під одним, якщо дані вантажать лоадери.
4. Рядок унизу вкладки показує, скільки запитів зроблено. На один перехід із лоадерами запитів до API має бути
   стільки, скільки маршрутів з лоадерами в ланцюжку.

Затримка 562,5 мс у наборі Slow 4G є мінімальною, а не доданою, тому на запиті до API, який сервер і так тримає
500 мс, уповільнення майже не видно. На першому відкритті сторінки воно помітне на бандлі. Записуючи числа в журнал
вимірів, пишіть поруч умови: яка збірка, який набір уповільнення, перехід чи перше відкриття. Без цього числа з різних
днів не можна порівнювати, про що вже йшлося в лекції «Збірка, перший викот і журнал вимірів», розділ «Журнал
вимірів».

## Типові хибні уявлення

**«Водоспад з'являється через `useEffect`».** Водоспад з'являється тоді, коли дочірній компонент починає свій запит
лише після даних батька. Варіант, у якому батько показує `<Outlet />` одразу, дав 586 мс, так само як лоадери. Але
одна умова `if (!data) return …` у батька повертає сходинку, а лоадер від цього не залежить.

**«Лоадер батька завантажується першим, потім лоадер дитини».** Обидва лоадери почали роботу на нульовій мілісекунді,
і маршрутизатор показав сторінку, коли закінчився найповільніший.

**«Поки лоадери працюють, людина бачить нову сторінку з повідомленням про завантаження».** Під час переходу на екрані
лишається стара сторінка, а нова адреса живе в `navigation.location`. Показати, що перехід триває, мусите ви самі:
`useNavigation` чи клас `pending` у `NavLink`.

**«Після дії перелік треба оновити вручну».** Маршрутизатор сам перезапускає лоадери сторінки після успішної дії.
Після відповіді зі статусом 4xx чи 5xx він їх не запускає.

**«Без `request.signal` у лоадері стара відповідь потрапить на екран».** Не потрапить: маршрутизатор відкидає
результат скасованого переходу. Сигнал потрібен, щоб скасувати сам запит і не навантажувати мережу й сервер.

**«Якщо лишити ефект поруч із лоадером, гірше не буде, просто дані прийдуть двічі».** Окрім другого запиту, копія в
стані перестає оновлюватися: після дії лоадер приніс нову книжку, а екран показав старий перелік.

**«`useLoaderData()` без параметра типу перевіряє поля».** Без параметра хук повертає `any`, і TypeScript мовчки
пропустив звернення до поля, якого немає.

## Як це проявиться далі в React

- **Фаза 3, день 3, TanStack Query.** Лоадер вантажить дані щоразу, коли людина приходить на сторінку. Бібліотека
  TanStack Query додасть кеш, тобто збереже відповідь і віддасть її одразу, коли людина повернеться.
- **Фаза 3, день 4, лоадер плюс кеш.** Лоадер не робитиме запиту сам, а попросить дані в кеша, і компонент читатиме ті
  самі дані з того самого кеша. Сьогоднішній урок про одне джерело даних для компонента стане там правилом про
  однакові ключі.
- **Фаза 3, день 5, мутації й оптимістичні оновлення.** Сьогоднішня дія й оптимістичний показ через
  `fetcher.formData` отримають продовження: відкат при помилці й оновлення кешу.
- **Фаза 3, дні про форми.** Форми React 19 і React Hook Form розберуть перевірку полів під час набору й показ помилок
  біля кожного поля.
- **Фаза 3, день 13, тести з мережею.** Сьогоднішній підмінений `fetch` замінить бібліотека MSW, яка перехоплює
  справжні запити.
- **Фаза 5, день 1, розділення коду.** Властивість `lazy` дозволить почати лоадер, поки вантажиться код сторінки, і
  скоротить перше відкриття.

## Перевірте себе

**1. Батько й дитина вантажать дані в ефектах, кожен запит триває 500 мс, а батько, поки чекає, показує
«Завантаження…» без `<Outlet />`. Скільки людина чекає на всю сторінку і чому?**

<details><summary>Відповідь</summary>

Близько 1000 мс. Дитина з'являється лише після даних батька, тому її ефект і запит починаються тоді, коли запит
батька закінчився. Наш замір без уповільнення дав 1012 мс, а з уповільненням Slow 4G 1153 мс.

</details>

**2. Ті самі екрани переписали на лоадери. Лоадер батька триває 300 мс, лоадер дитини 500 мс. Коли React рендерить
батька?**

<details><summary>Відповідь</summary>

Приблизно на 500-й мілісекунді, разом із дитиною. Маршрутизатор запускає обидва лоадери в момент переходу й рендерить
сторінку, коли готові всі лоадери ланцюжка. У нашому досліді обидва компоненти вперше рендерилися на 510-й
мілісекунді.

</details>

**3. Людина клацнула посилання, а лоадери працюють ще секунду. Що вона бачить і як їй показати, що перехід триває?**

<details><summary>Відповідь</summary>

Вона бачить стару сторінку: маршрутизатор не рендерить нової, поки дані не готові. Показати перехід можна хуком
`useNavigation`, коли його `state` не дорівнює `idle`, або класом `pending`, який `NavLink` додає посиланню, на яке
клацнули. На першому відкритті старої сторінки немає, тому там потрібен `HydrateFallback`.

</details>

**4. Після успішної дії «Додати книжку» на екрані старий перелік. Компонент читає `useLoaderData`, кладе результат у
`useState` і ще вантажить книжки в ефекті із залежністю `[authorId]`. Що сталося?**

<details><summary>Відповідь</summary>

Маршрутизатор після дії перезапустив лоадер, і `useLoaderData` повернув новий перелік. Але компонент показує свій
стан, а `useState` бере аргумент лише як початкове значення. Ефект теж не перезапустився, бо `authorId` не змінився.
Треба прибрати стан і ефект і показувати те, що повертає `useLoaderData`.

</details>

**5. Дія повернула `data({ error: '…' }, { status: 400 })`. Чи перезапустяться лоадери сторінки?**

<details><summary>Відповідь</summary>

Ні. У режимі даних надсилання, яке закінчилося статусом 4xx чи 5xx, не перезапускає лоадерів. Наш тест після такої
дії не побачив жодного GET-запиту, а помилку компонент отримав через `useActionData`.

</details>

**6. Після входу через `<Form>` і дію, яка повертає `redirect(from)`, людина натискає «Назад» і знову бачить сторінку
входу. Чому і що змінити?**

<details><summary>Відповідь</summary>

Надсилання `<Form>` є переходом, і `redirect` після дії додав новий запис в історію, тож запис сторінки входу лишився
позаду. Функція `replace` створює таке саме перенаправлення, але заміняє поточний запис. У нашому тесті з `replace`
«Назад» повів на попередню сторінку, а не на вхід.

</details>

**7. Чим `<fetcher.Form>` відрізняється від `<Form>`?**

<details><summary>Відповідь</summary>

Обидві форми викликають дію маршруту, і після обох маршрутизатор перезапускає лоадери. Але `<Form>` є переходом: він
змінює `navigation.state` і додає запис в історію. Фетчер має власний `fetcher.state`, не змінює `navigation` і
адреси та не додає запису в історію. Тому фетчер зручний для дрібних дій на тій самій сторінці, як-от позначка
«прочитано».

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| водоспад | незалежні запити, що даремно чекають один одного; між компонентами виникає, коли дитина починає запит після даних батька |
| лоадер | функція маршруту, яку маршрутизатор викликає в момент переходу, до рендеру компонента, щоб завантажити дані |
| `useLoaderData` | хук, що повертає дані лоадера свого маршруту |
| `LoaderFunctionArgs` | тип аргументу лоадера з полями `params` і `request` |
| `request.signal` | сигнал скасування, який маршрутизатор подає, коли перехід скасовано |
| час до появи вмісту | у цій лекції: від клацання до моменту, коли в документі є всі дані сторінки |
| уповільнення мережі | штучне обмеження швидкості й мінімальна затримка, які задає Chrome, наприклад набір Slow 4G |
| `useNavigation` | хук зі станом переходу: `idle`, `loading` або `submitting`, і новою адресою в `location` |
| `HydrateFallback` | компонент, який маршрутизатор показує на першому відкритті, поки працюють лоадери |
| `data` | функція React Router, що створює дані зі статусом для лоадера чи дії |
| дія (action) | функція маршруту, яку маршрутизатор викликає, коли на адресу маршруту надіслано форму методом POST |
| `<Form>` | форма маршрутизатора: надсилання стає переходом, а поля приходять у дію як `FormData` |
| `useActionData` | хук, що повертає результат останньої дії свого маршруту |
| повторна перевірка (revalidation) | повторний запуск лоадерів сторінки після успішної дії |
| `?index` | параметр, яким форма в індексному маршруті позначає, що дію треба взяти в індексного маршруту, а не в батька |
| `replace` | функція, що перенаправляє з дії чи лоадера й заміняє поточний запис історії |
| фетчер (`useFetcher`) | окремий виконавець запитів до лоадерів і дій, який не змінює адреси й не додає запису в історію |
| оптимістичний показ | показ результату дії ще до відповіді сервера, на основі надісланої форми |
