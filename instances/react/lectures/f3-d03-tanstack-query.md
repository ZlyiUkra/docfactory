# Лекція. Фаза 3, день 3. Серверний стан: TanStack Query

Учора лоадери маршрутів навчилися вантажити дані сторінки ще до її рендеру. Проте лоадер нічого не пам'ятає: щоразу,
коли людина повертається на сторінку, він знову йде на сервер, а відповідь забуває одразу після рендеру. Сьогодні в
застосунку з'являється **кеш**, тобто збережена на боці браузера копія відповідей сервера, яку можна показати одразу,
без нового очікування. Цей кеш дає бібліотека TanStack Query. Вона ж бере на себе роботу, яку у фазі 1 ви писали
вручну в кожному ефекті: захист від гонок відповідей, скасування запитів, повтори після помилки. Читання займе близько
80 хвилин.

Числа й вивід у лекції отримано на React 19.3.1, React Router 8.5.3, TanStack Query 5.108.4 (пакети
`@tanstack/react-query` і `@tanstack/react-query-devtools`), Vite 8.3.6 і TypeScript 6.0.3. Досліди без браузера
запускалися у Vitest 5.1.0 із середовищем jsdom 31.0.0, тобто в імітації документа браузера всередині Node, яка не
малює й не ходить у мережу. Досліди в браузері запускалися в `chrome-headless-shell` версії 158, тобто в Chromium без
вікна, яким скрипт керував через протокол інструментів розробника. Сторінки віддавав той самий невеликий сервер, що й
учора: він віддає продакшн-збірку і відповідає на запити до API із затримкою 500 мс. Біля кожного результату сказано,
де і як його отримано.

Документація TanStack Query у примірнику `tanstack-query` доходить до версії 5.103.3, а ваш проєкт ставить 5.108.4.
Ми порівняли шість сторінок, заданих на сьогодні, у сховищі коду TanStack Query за мітками двох версій. Сторінки
`Queries` і `Query Keys` однакові, а в `Overview`, `Quick Start`, `Important Defaults` і `Devtools` змінилися приклади
й опис кількох параметрів панелі. Що саме змінилося і що з цього важливо, сказано в розборі читання. Сервер
`tanstack-query-docs` питайте з версією `5`.

Практика дня переводить екрани прокату спорядження на TanStack Query. Щоб не показувати розв'язку, лекція бере інший
об'єкт: домашню бібліотеку з двох попередніх лекцій. Сьогодні на її головній сторінці є перелік авторів, який
приходить із сервера, а сторінка автора показує його ім'я й книжки.

**Після лекції ви зможете пояснити:**

- чим серверний стан відрізняється від стану, який компонент тримає в `useState`;
- що роблять `QueryClient`, `QueryClientProvider` і `useQuery` і що повертає `useQuery`;
- чим `status` відрізняється від `fetchStatus` і чому дані можуть бути на екрані, поки йде запит;
- як ключ запиту стає адресою запису в кеші і чому в ключі має бути кожна змінна, від якої залежить запит;
- чому кілька компонентів з одним ключем роблять один запит і що відбувається у `<StrictMode>`;
- що означають `staleTime` і `gcTime` і чим вони відрізняються;
- що саме змушує TanStack Query піти на сервер знову: повернення на екран, повернення на вкладку, відновлення мережі;
- як бібліотека повторює невдалий запит і скільки людина чекає на повідомлення про помилку;
- що показує панель Devtools і чому її немає в продакшн-збірці;
- чому копія `data` у `useState` перестає оновлюватися.

## Перелік, який щоразу вантажиться заново

Головна сторінка нашої бібліотеки показує перелік авторів. Перелік лежить на сервері за адресою `/api/authors`.
Спершу напишемо його так, як ви вже вмієте, з ефектом і прапорцем `ignore` з лекції «Синхронізація ефектами», розділ
«Запит у мережу»:

```tsx
// src/library/effect-list.tsx
import { useEffect, useState } from 'react'
import { getJson, type Author } from './api'

// Для порівняння: той самий перелік, завантажений в ефекті, як у фазі 1.
export function AuthorsListEffect() {
  const [authors, setAuthors] = useState<Author[] | null>(null)
  useEffect(() => {
    let ignore = false
    getJson<Author[]>('/api/authors').then((a) => {
      if (!ignore) setAuthors(a)
    })
    return () => {
      ignore = true
    }
  }, [])
  if (!authors) return <p>Завантаження авторів…</p>
  return (
    <>
      <h1>Автори бібліотеки</h1>
      <ul className="authors">
        {authors.map((a) => (
          <li key={a.id}>{a.name}</li>
        ))}
      </ul>
    </>
  )
}
```

Функція `getJson` та сама, що й учора: вона робить `fetch`, кидає помилку, якщо статус відповіді не успішний, і
повертає розібраний JSON. Типи `Author` і `Book` описують автора й книжку:

```ts
// src/library/api.ts
export type Author = { id: number; name: string; years: string }
export type Book = { id: number; title: string }

// GET-запит до API: повертає розібраний JSON або кидає помилку зі статусом відповіді.
export async function getJson<T>(path: string, signal?: AbortSignal): Promise<T> {
  const res = await fetch(path, { signal })
  if (!res.ok) throw new Error(`${path}: ${res.status}`)
  return (await res.json()) as T
}
```

Людина відкриває головну, переходить на сторінку Лесі Українки й повертається назад. Ми зібрали застосунок у
продакшн-збірку з цим переліком і повторили такий маршрут у Chrome без вікна. Мережу уповільнено набором Slow 4G, а
збережені копії файлів вимкнено, як учора в розділі «Уповільнена мережа». Людина повертається на головну через 10 і

Три крапки заміняють рядки про сторінку автора: про них нижче. Кожне повернення коштувало людині повної затримки
API, близько 580 мс, хоча перелік за ці секунди не змінився. Причина в тому, як ефект зберігає дані. Відповідь
лежить у стані компонента `AuthorsListEffect`. Коли людина йде на сторінку автора, React прибирає цей компонент з
екрана разом з усім його станом. Коли людина повертається, React створює новий екземпляр компонента з порожнім станом,
і ефект іде на сервер заново.

Ця втрата пам'яті не єдина проблема ефекту. Ось що він не робить або робить лише тому, що ви написали це вручну:

- **Кеш.** Відповідь живе лише поки живе компонент. Інший компонент, якому потрібен той самий перелік, піде на сервер
  удруге.
- **Один запит на всіх.** Два компоненти, які одночасно показують перелік авторів, роблять два однакові запити.
- **Гонки відповідей.** Прапорець `ignore` і `AbortController` ви пишете в кожному ефекті самі, як показала лекція
  «Синхронізація ефектами» в розділах «Прапорець `ignore`» і «`AbortController`».
- **Повтори.** Якщо сервер на мить відповів помилкою, ефект одразу показує помилку.
- **Оновлення.** Якщо людина залишила вкладку на годину й повернулася, вона бачить годинної давнини перелік, поки
  сама не оновить сторінку.

Учорашні лоадери розв'язали проблему водоспаду, тобто черги запитів, які могли б іти разом. Кешу вони не дали: лоадер
так само вантажить усе щоразу, коли людина приходить на сторінку. Перші три пункти TanStack Query виконує сам, а для
двох останніх має налаштування з розумними значеннями за замовчуванням.

## Серверний стан

Перш ніж писати код, варто зрозуміти, чим дані з сервера відрізняються від звичайного стану компонента. Сторінка
`Overview` документації TanStack Query пояснює це в розділі `Motivation`.

Стан, який ви досі тримали в `useState`, належить вашому застосунку. Текст у полі пошуку, відкрите вікно, вибрана
вкладка існують лише в браузері людини. Ніхто інший не може їх змінити, і вони завжди правильні, бо ваш код і є
єдиним джерелом правди про них. Такий стан документація називає **клієнтським станом**.

Перелік авторів поводиться інакше. Справжній перелік лежить на сервері, а браузер має лише копію, отриману в певну
мить. Сторінка `Overview` перелічує, чим такий **серверний стан** відрізняється. Своїми словами:

- він зберігається десь далеко, у місці, яким ви, можливо, не керуєте;
- прочитати чи змінити його можна лише асинхронно, тобто запитом, відповідь на який прийде пізніше;
- ним володієте не лише ви: інші люди можуть змінити його без вашого відома;
- тому копія в браузері може застаріти, якщо за нею не стежити.

Звідси випливають задачі, які та сама сторінка називає складними: кешувати, поєднувати однакові запити в один,
оновлювати застарілі дані у фоні, знати, коли дані застаріли, звільняти пам'ять від даних, які вже ніхто не показує.
TanStack Query є бібліотекою саме для серверного стану. Клієнтський стан лишається в `useState`, `useReducer` і
контексті, як і було.

## Клієнт, провайдер і `useQuery`

Бібліотека ставиться одним пакетом:

```bash
npm install @tanstack/react-query@5.108.4
```

Далі потрібні три речі. Сторінка `Quick Start` показує їх в одному прикладі, а ось як вони виглядають у нашій
бібліотеці.

**Клієнт запитів.** `QueryClient` є об'єктом, у якому живе кеш і налаштування за замовчуванням. Застосунку потрібен
один такий об'єкт, тому його створюють один раз, на верхньому рівні модуля, так само як учорашній маршрутизатор:

```tsx
// src/library/main.tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { ReactQueryDevtools } from '@tanstack/react-query-devtools'
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import { createBrowserRouter } from 'react-router'
import { RouterProvider } from 'react-router/dom'
import { routes } from './routes'

// Один клієнт на весь застосунок: у ньому живе кеш.
const queryClient = new QueryClient()
const router = createBrowserRouter(routes)

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
      <ReactQueryDevtools initialIsOpen={import.meta.env.VITE_DEVTOOLS_OPEN === '1'} />
    </QueryClientProvider>
  </StrictMode>,
)
```

**Провайдер.** `QueryClientProvider` передає клієнт усім компонентам усередині себе. Це звичайний контекст React, як
у лекції «Контекст»: провайдер ставлять високо в дереві, а хуки бібліотеки знаходять клієнт найближчого провайдера
над собою. Маршрутизатор стоїть усередині провайдера, тому кожна сторінка бачить той самий кеш. Рядок
`<ReactQueryDevtools … />` додає панель для розробника, про неї окремий розділ наприкінці. Змінна
`VITE_DEVTOOLS_OPEN` потрібна лише нашим дослідам.

**Хук `useQuery`.** Компонент оголошує, які дані йому потрібні, і отримує їх разом зі станом завантаження. Ось перелік
авторів, переписаний з ефекту:

```tsx
// src/library/pages.tsx, фрагмент
import { useQuery } from '@tanstack/react-query'
import { getJson, type Author } from './api'

// Скільки мілісекунд перелік авторів вважається свіжим. Збірка досліду може змінити це число.
const AUTHORS_STALE_MS = Number(import.meta.env.VITE_AUTHORS_STALE ?? 30_000)

// Головна: перелік авторів із сервера.
export function AuthorsList() {
  const { isPending, isError, error, data, isFetching } = useQuery({
    queryKey: ['authors'],
    queryFn: ({ signal }) => getJson<Author[]>('/api/authors', signal),
    staleTime: AUTHORS_STALE_MS,
  })
  if (isPending) return <p>Завантаження авторів…</p>
  if (isError) return <p role="alert">Не вдалося: {error.message}</p>
  return (
    <>
      <h1>Автори бібліотеки {isFetching && <small>оновлюю…</small>}</h1>
      <ul className="authors">
        {data.map((a) => (
          <li key={a.id}>{a.name}</li>
        ))}
      </ul>
    </>
  )
}
```

Пройдімо рядками.

- `queryKey: ['authors']` є **ключем запиту**, тобто масивом, який називає дані. За цим ключем бібліотека шукає й
  зберігає запис у кеші. Ключам присвячено окремий розділ нижче.
- `queryFn` є **функцією запиту**, тобто функцією, яка йде по дані й повертає проміс. Сторінка `Queries` ставить їй
  одну вимогу: проміс має або дати дані, або кинути помилку. Наш `getJson` кидає помилку, коли статус не успішний.
  Це важливо, бо сам `fetch` на статус 500 помилки не кидає, як пояснювала лекція «Мережа», розділ «Коли проміс від
  `fetch` відхиляється».
- Функція запиту отримує аргумент від бібліотеки, і з нього тут узято `signal`. Це сигнал скасування, такий самий,
  як у лекції «Мережа» і в учорашніх лоадерах. Бібліотека подає його, коли запит більше нікому не потрібен. Що це дає,
  покажуть розділи про гонки й про `<StrictMode>`.
- `staleTime` каже, скільки мілісекунд дані вважаються свіжими. Ми ставимо 30 секунд. Це найважливіше налаштування
  дня, і йому присвячено окремий розділ.
- `useQuery` повертає об'єкт із кількома полями. `isPending` дорівнює `true`, поки даних ще немає. `isError` дорівнює
  `true`, коли запит закінчився помилкою, а сама помилка лежить в `error`. `data` містить дані. `isFetching` дорівнює
  `true`, поки функція запиту працює, і тут ми показуємо поруч із заголовком напис «оновлюю…».

У компоненті немає ні `useState`, ні `useEffect`, ні прапорця `ignore`. Компонент лише каже, які дані йому потрібні, а
коли їх вантажити, вирішує бібліотека.

### Що повертає `useQuery` у кожному рендері

Щоб побачити, як змінюються ці поля, ми написали тест у jsdom. У jsdom мережі немає, тому дослід, як і вчора,
підміняє глобальний `fetch` функцією `installFakeApi`. Підмінена функція відповідає через заданий час і записує в
журнал старт і відповідь кожного запиту. Компонент записує в той самий журнал кожен свій рендер:

```tsx
// src/library/lab/basic.test.tsx
// @vitest-environment jsdom
import { QueryClient, QueryClientProvider, useQuery } from '@tanstack/react-query'
import { render, screen } from '@testing-library/react'
import { test } from 'vitest'
import { getJson, type Author } from '../api'
import { installFakeApi, log, now, resetClock } from './fake-api'

// Компонент записує в журнал кожен свій рендер: status, fetchStatus і скільки авторів у data.
function Authors() {
  const q = useQuery({
    queryKey: ['authors'],
    queryFn: ({ signal }) => getJson<Author[]>('/api/authors', signal),
  })
  log.push(`${now()} мс: рендер status=${q.status} fetchStatus=${q.fetchStatus} data=${q.data ? q.data.length + ' авторів' : 'undefined'}`)
  if (q.isPending) return <p>Завантаження авторів…</p>
  if (q.isError) return <p>Помилка: {q.error.message}</p>
  return <ul>{q.data.map((a) => <li key={a.id}>{a.name}</li>)}</ul>
}

test('перший запит', async () => {
  installFakeApi(500)
  const client = new QueryClient()
  resetClock()
  render(<QueryClientProvider client={client}><Authors /></QueryClientProvider>)
  await screen.findByText('Іван Франко', {}, { timeout: 2000 })
  console.log(log.join('\n'))
})
```

```text
$ npx vitest run src/library/lab/basic.test.tsx --disable-console-intercept
10 мс: рендер status=pending fetchStatus=fetching data=undefined
20 мс: старт /api/authors
520 мс: відповідь /api/authors
520 мс: рендер status=success fetchStatus=idle data=2 авторів
```

У тесті ми самі створюємо `new QueryClient()`, щоб кожен тест мав порожній кеш. Компонент відрендерився двічі. У
першому рендері даних ще немає, а запит лише збирається піти: він почався на 20-й мілісекунді, після того як React
показав перший рендер. Бібліотека підписує компонент на запис кешу вже після рендеру, так само як ефект запускається
після рендеру, тому запит і стартує трохи пізніше. Коли через 500 мс прийшла відповідь, бібліотека попросила React
відрендерити компонент знову, уже з даними.

### `status` і `fetchStatus`: два різні запитання

У журналі видно два поля стану, і сторінка `Queries` пояснює, навіщо їх два. Поле `status` відповідає на запитання
«чи є дані?». Воно має три значення: `pending`, коли даних ще немає, `error`, коли запит закінчився помилкою, і
`success`, коли дані є. Поля `isPending`, `isError` і `isSuccess` є скороченнями для цих трьох значень.

Поле `fetchStatus` відповідає на інше запитання: «чи працює зараз функція запиту?». Значення `fetching` означає, що
запит іде, `idle` означає, що нічого не відбувається, а `paused` означає, що запит хотів піти, але бібліотека
поставила його на паузу, бо немає мережі. Поле `isFetching` дорівнює `true`, коли `fetchStatus` дорівнює `fetching`.

Ці два поля незалежні, і будь-яке поєднання можливе. Найважливіше для сьогоднішнього дня поєднання таке: `status`
дорівнює `success`, а `fetchStatus` дорівнює `fetching`. Це означає, що дані вже є й показані, а бібліотека тим часом
перевіряє на сервері, чи вони не змінилися. Таке оновлення називають **фоновим запитом**, бо людина бачить дані й не
чекає на нього. Саме тому `AuthorsList` перевіряє `isPending`, а не `isFetching`: напис «Завантаження авторів…»
замість переліку має з'являтися лише тоді, коли показати справді нічого.

| `status` | `fetchStatus` | Що це означає |
|----------|---------------|---------------|
| `pending` | `fetching` | даних немає, перший запит іде; людина бачить «Завантаження…» |
| `success` | `idle` | дані є, запиту немає |
| `success` | `fetching` | дані показано, а у фоні йде перевірка; у нашій бібліотеці поруч напис «оновлюю…» |
| `pending` | `paused` | даних немає, і запит чекає на мережу |
| `error` | `idle` | усі спроби закінчилися помилкою, вона лежить в `error` |

### Що знає TypeScript про `data`

Поки `status` дорівнює `pending`, поля `data` ще немає. TypeScript це знає: тип `data` для нашого запиту дорівнює
`Author[] | undefined`. Тип узято з того, що повертає функція запиту, тобто з `getJson<Author[]>`. Ми навмисно
звернулися до `data.length` без жодної перевірки, а в другому компоненті з перевірками:

```tsx
// src/library/tscheck/types.tsx
// Перевірка типів: що TypeScript знає про data.
import { useQuery } from '@tanstack/react-query'
import { getJson, type Author } from '../api'

export function NoCheck() {
  const { data } = useQuery({ queryKey: ['authors'], queryFn: () => getJson<Author[]>('/api/authors') })
  return <p>{data.length}</p>
}

export function WithCheck() {
  const { isPending, isError, error, data } = useQuery({
    queryKey: ['authors'],
    queryFn: () => getJson<Author[]>('/api/authors'),
  })
  if (isPending) return <p>Завантаження…</p>
  if (isError) return <p>{error.message}</p>
  return <p>{data.length}</p>
}
```

```text
$ npx tsc --noEmit -p tsconfig.app.json
src/library/tscheck/types.tsx(7,14): error TS18048: 'data' is possibly 'undefined'.
```

Помилка одна, у компоненті `NoCheck`. У `WithCheck` TypeScript після двох `return` знає, що лишився тільки випадок
`success`, і звужує тип `data` до `Author[]`. Так само звужувалися розрізнювані об'єднання в лекції «Стан як набір
станів екрана», розділ «Розрізнюване об'єднання як опис стану»: перевірка одного поля каже компілятору, яка форма в
усього об'єкта. Сторінка `Queries` радить саме такий порядок: спершу `isPending`, потім `isError`, а далі вважати, що
дані є.

## Кеш за ключем

Тепер сторінка автора. Вона показує ім'я автора й перелік його книжок, тобто робить два запити:

```tsx
// src/library/pages.tsx, фрагмент
import { useQuery } from '@tanstack/react-query'
import { useParams } from 'react-router'
import { getJson, type Author, type Book } from './api'

// Сторінка автора: два запити з різними ключами.
export function AuthorPage() {
  const { authorId } = useParams()
  const author = useQuery({
    queryKey: ['authors', authorId],
    queryFn: ({ signal }) => getJson<Author>(`/api/authors/${authorId}`, signal),
  })
  const books = useQuery({
    queryKey: ['authors', authorId, 'books'],
    queryFn: ({ signal }) => getJson<Book[]>(`/api/authors/${authorId}/books`, signal),
  })
  return (
    <article>
      <h1>{author.data ? author.data.name : 'Завантаження автора…'}</h1>
      {books.data ? (
        <ul className="books">
          {books.data.map((b) => (
            <li key={b.id}>{b.title}</li>
          ))}
        </ul>
      ) : (
        <p>Завантаження книжок…</p>
      )}
    </article>
  )
}
```

Номер автора `authorId` приходить з адреси через `useParams`, як у лекції «Маршрути». Обидва запити мають його в
ключі. Сторінка `Query Keys` пояснює правило: ключ має однозначно описувати дані, тому кожна змінна, від якої
залежить функція запиту, мусить стояти в ключі. Ключ `['authors', '1']` означає «автор номер 1», а
`['authors', '1', 'books']` означає «книжки автора номер 1». Для бібліотеки це два різні записи кешу.

Дерево маршрутів звичайне, як у лекції «Маршрути», і лоадерів тут немає: сьогодні дані вантажать компоненти, а
поєднати лоадер із кешем план вчить завтра.

```tsx
// src/library/routes.tsx, фрагмент
export const routes: RouteObject[] = [
  {
    path: '/',
    Component: Layout,
    children: [
      { index: true, Component: AuthorsList },
      { path: 'authors/:authorId', Component: AuthorPage },
    ],
  },
]
```

### Кожен автор у своєму записі

За цей час маршрутизатор змінює адресу, React рендерить нову сторінку, і лише після рендеру бібліотека запускає
запит. Учора лоадери починали запит у саму мить клацання. Об'єднати обидві переваги вчить завтрашній день.

### Ключ, у якому бракує змінної

Що буде, якщо номер автора стоїть у функції запиту, але не в ключі? Ми написали таку сторінку книжок:

```tsx
// src/library/lab/keys.test.tsx, фрагмент
// Помилка: номер автора є в queryFn, але не в ключі.
function BooksWrongKey() {
  const { authorId } = useParamsSafe()
  const books = useQuery({
    queryKey: ['books'],
    queryFn: ({ signal }) => getJson<Book[]>(`/api/authors/${authorId}/books`, signal),
  })
  return (
    <>
      <h1>Автор {authorId}</h1>
      <ul>{books.data?.map((b) => <li key={b.id}>{b.title}</li>)}</ul>
    </>
  )
}
```

`useParamsSafe` у тесті просто викликає `useParams`. Тест відкриває автора 1, а потім клацає «Іван Франко» і чекає
секунду:

```text
1010 мс: на екрані: Автор 2 | Лісова пісня, Камінний господар
записи кешу: ["books"]
```

За секунду не пішло жодного запиту, і на сторінці автора 2 лишилися книжки Лесі Українки. Для бібліотеки ключ не
змінився, тому й запис кешу той самий, а дані в ньому вже є. Те, що функція запиту тепер звертається за іншою адресою,
бібліотека не бачить, бо порівнює лише ключі. Сторінка `Query Keys` каже про це так: ключ працює як залежності функції
запиту, і коли змінна в ключі змінюється, запит повторюється сам. Це те саме правило, що й зі списком залежностей
ефекту в лекції «Залежності ефекту й власні хуки». Для залежностей ефекту лінт мав правило
`react-hooks/exhaustive-deps`, а для ключів TanStack Query існує окремий додаток до ESLint
`@tanstack/eslint-plugin-query` з правилом під тією самою назвою. Ми його не ставили, бо це нова залежність проєкту.

### Як ключ стає рядком

Бібліотека перетворює ключ на рядок функцією `hashKey` і порівнює вже рядки. Сторінка `Query Keys` каже, що порядок
полів в об'єкті всередині ключа значення не має, а порядок елементів масиву має. Ми перевірили це, викликавши
`hashKey` напряму:

```tsx
// src/library/lab/keys.test.tsx, фрагмент
test('хеш ключа', () => {
  console.log(hashKey(['books', { page: 2, sort: 'title' }]))
  console.log(hashKey(['books', { sort: 'title', page: 2 }]))
  console.log(hashKey(['books', 2, 'title']))
  console.log(hashKey(['books', 'title', 2]))
  console.log(hashKey(['authors', '1']), hashKey(['authors', 1]))
})
```

```text
["books",{"page":2,"sort":"title"}]
["books",{"page":2,"sort":"title"}]
["books",2,"title"]
["books","title",2]
["authors","1"] ["authors",1]
```

Перші два ключі дали той самий рядок, бо бібліотека впорядковує поля об'єкта перед перетворенням. Наступні два
різні, бо в масиві порядок зберігається. Останній рядок варто запам'ятати. Рядок `"1"` і число `1` дають різні
ключі, а отже, різні записи кешу. `useParams` завжди повертає рядки, тому якщо в одному місці ключ збирається з
`useParams`, а в іншому з числа, вийде два записи на ті самі дані. Завтрашній день саме про таку пастку.

## Гонка відповідей

Лекція «Синхронізація ефектами» розбирала гонку: людина швидко перемикає записи, стара відповідь приходить пізніше за
нову й перезаписує екран. Ефект захищався від цього прапорцем `ignore`. Повторимо той самий сценарій з `useQuery`.
Леся Українка тепер відповідає за 900 мс, а Іван Франко за 200 мс. Тест клацає Лесю, через 100 мс клацає Франка і
записує, що на екрані. Сторінку взято у двох варіантах: справжня `AuthorPage`, яка передає `signal` у запит, і
спрощена сторінка без сигналу:

`['authors', '2']`. Хоч би коли прийшла стара відповідь, вона потрапить у свій запис і не торкнеться чужого.

Різниця між варіантами в долі старого запиту. Сторінка `Query Cancellation` документації описує правило: за
замовчуванням бібліотека не скасовує запит, коли компонент пішов, і відповідь лягає в кеш, щоб пригодитися пізніше.
Але якщо функція запиту взяла `signal`, бібліотека вважає, що запит уміє зупинятися, і скасовує його, щойно запис
лишився без жодного компонента, який його читає. У варіанті із сигналом обидва запити Лесі зупинилися на 170-й
мілісекунді, а записи повернулися до попереднього стану `pending`. У варіанті без сигналу запит Лесі дійшов до кінця
на 910-й мілісекунді, і його відповідь лягла в запис `['authors', '1']` зі станом `success`. Якщо людина зараз
повернеться до Лесі, ім'я з'явиться одразу. Обидві поведінки правильні, і вибір залежить від того, що дорожче:
мережа чи швидке повернення.

Пройдімо результати по черзі.

**Два компоненти з одним ключем роблять один запит.** Бібліотека зберігає не лише дані, а й запит, який зараз іде.
Коли другий компонент просить той самий ключ, вона бачить, що запит уже в дорозі, і просто чекає на нього разом з
першим. Сторінка `Overview` називає це поєднанням однакових запитів в один (deduping). З ефектами кожен компонент
зробив би власний запит.

**`<StrictMode>` і ефект: дві відповіді.** Лекція «Синхронізація ефектами», розділ «Навіщо `<StrictMode>` запускає
ефект двічі», пояснила, що в режимі розробки React монтує компонент, одразу прибирає його й монтує знову. Ефект без
скасування зробив два повні запити й отримав дві відповіді. Тест кладе `<StrictMode>` у корінь дерева, як у вашому
`main.tsx`, бо довідник `<StrictMode>` у примітці до розділу «Enabling Strict Mode for a part of the app» каже: якщо
`<StrictMode>` стоїть не в корені, React не повторює ефектів під час першого монтування. Ми спершу поставили його
всередину провайдера й отримали один запит для ефекту, а в корені отримали два.

**`<StrictMode>` і `useQuery` із сигналом: старт, скасування, старт.** Під час першого монтування компонент
підписався на запис, і запит пішов. Потім React прибрав компонент, і запис на мить лишився без жодного читача.
Функція запиту бере `signal`, тому бібліотека, як описано в розділі про гонку, скасувала запит. Друге монтування
знайшло запис без даних і почало запит знову. Відповідь прийшла одна, тому сервер майже не відчув різниці, але у
вкладці Network режиму розробки ви побачите два рядки `authors`, і один із них скасований. Ми перевірили це в Chrome
на сервері розробки Vite, тобто з командою `npx vite`:

запит один: це видно в замірах браузера нижче.

**`<StrictMode>` і `useQuery` без сигналу: один запит.** Без сигналу бібліотека не скасовує запиту, коли компонент
пішов. Друге монтування застало запит у дорозі й приєдналося до нього. Отже, рядок `(canceled)` у режимі розробки не
означає помилки: він лише показує, що функція запиту вміє скасовуватися.

## Свіжі й застарілі дані: `staleTime`

У розділі про ключі повернення до Лесі показало дані одразу, але запит однаково пішов. Сторінка `Important Defaults`
пояснює чому. Її перше правило каже, що за замовчуванням бібліотека вважає збережені дані **застарілими** (stale)
одразу після того, як вони прийшли. Застарілі дані бібліотека показує, але при нагоді перевіряє на сервері.

Налаштування `staleTime` змінює це правило. Воно задає, скільки мілісекунд після отримання дані вважаються
**свіжими** (fresh). Поки дані свіжі, бібліотека бере їх із кешу й не робить жодного запиту. Коли `staleTime` минув,
дані стають застарілими. За замовчуванням `staleTime` дорівнює 0. Сторінка називає ще два особливі значення:
`Infinity` означає «не перезапитувати, доки запис не позначать застарілим вручну», а `'static'` означає «не
перезапитувати ніколи». Як позначати записи вручну, тобто інвалідацію, план вчить завтра й у день про мутації.

Те саме правило перелічує, коли саме бібліотека перезапитує застарілі дані у фоні:

1. коли монтується новий екземпляр запиту, тобто новий компонент з `useQuery` для цього ключа;
2. коли вікно знову отримує фокус, тобто людина повертається на вкладку;
3. коли мережа відновилася після обриву.

Кожну з цих подій можна вимкнути окремим налаштуванням: `refetchOnMount`, `refetchOnWindowFocus` і
`refetchOnReconnect`. Сторінка радить замість цього насамперед збільшувати `staleTime`. Ще одне налаштування,
`refetchInterval`, перезапитує дані за таймером незалежно від свіжості, а сьогодні воно нам не потрібне.

### Повернення на екран є новим монтуванням

Перша подія потребує пояснення. Коли людина переходить із головної на сторінку автора, маршрутизатор перестає
рендерити `AuthorsList`, і React прибирає цей компонент. Разом із ним зникає його **спостерігач**, тобто внутрішній
об'єкт бібліотеки, який `useQuery` створює, щоб стежити за записом кешу й повідомляти компонент про зміни. Запис
`['authors']` при цьому лишається в кеші, але без жодного спостерігача. Коли людина повертається, React створює новий
екземпляр `AuthorsList`, а його `useQuery` створює нового спостерігача. Для бібліотеки це і є «монтується новий
екземпляр запиту». Спостерігач дивиться на запис: дані є, тому `status` одразу дорівнює `success`, а якщо дані
застарілі, він ще й запускає фоновий запит.

Ми перевірили це в jsdom із двома значеннями `staleTime`. Тест відкриває головну, переходить на сторінку «Про

### Що показав справжній браузер

Тепер той самий маршрут у Chrome на продакшн-збірці, з уповільненням Slow 4G і вимкненими збереженими копіями файлів,
як у першому розділі. Людина відкриває головну, за 3 секунди до повернення переходить на сторінку Лесі Українки й
повертається на головну через 10 і через 35 секунд після першого завантаження переліку. Час тут справжній, без
пересування годинника: скрипт чекає ці секунди. Ось фрагмент скрипта, який клацає «Головна» і чекає на перелік:

```js
// back.mjs, фрагмент

const start = await page.evaluate(`(async () => { const t = performance.now();
  [...document.querySelectorAll('a')].find((a) => a.textContent === 'Головна').click();
  while (!document.querySelector('ul.authors li')) await new Promise((r) => setTimeout(r, 5));
  return Math.round(performance.now() - t) })()`)
events.push(`${sec()} с  перелік на екрані через ${start} мс після клацання`)
await page.sleep(100)
events.push(`${sec()} с  на екрані: «${await text()}»`)
```

Скрипт перевіряє наявність переліку кожні 5 мс, тому точність числа приблизно 5 мс. Запити скрипт бере з подій
протоколу `Network.requestWillBeSent` і `Network.loadingFinished`, тобто з тих самих подій, з яких Chrome будує рядки

## Повернення на вкладку: `refetchOnWindowFocus`

Друга подія з `Important Defaults` стається, коли людина перемикається на іншу вкладку браузера чи на іншу програму, а
потім повертається. Браузер повідомляє сторінку про це подією `visibilitychange` на документі: поле
`document.visibilityState` стає `hidden`, коли сторінку не видно, і `visible`, коли її знову видно. Сторінка
`Window Focus Refetching` документації показує, що бібліотека слухає саме цю подію. Коли сторінка знову стає видимою,
бібліотека перезапитує всі застарілі запити, у яких є спостерігачі. Свіжих вона не чіпає. Налаштування
`refetchOnWindowFocus: false` вимикає цю поведінку для одного запиту чи для всіх.

Без вікна вкладку не перемкнеш: у безголовому Chrome усі сторінки вважаються видимими, і перемикання між ними нічого
не змінило, ми це перевірили. Тому скрипт `tab.mjs` попросив Chrome через протокол сховати сторінку й показати знову.
Команда `Page.setWebLifecycleState` зі станом `frozen` робить сторінку схованою, а команда
`Emulation.setFocusEmulationEnabled` повертає її у видимий стан. Події `visibilitychange` при цьому подає сам
браузер, а не наш код:

```js
// tab.mjs, фрагмент
```

маршрутизатор, коли людина переходить сторінками вашого застосунку. Повернення на вкладку є подією
`visibilitychange`: його викликає браузер, коли людина повертається з іншої вкладки чи програми, а компонент увесь цей
час лишався на екрані.

Сторінка `Window Focus Refetching` має розділ `Troubleshooting` про пастку для розробника. В інструментах розробника
Chrome, на панелі Rendering, є прапорець «Emulate a focused page». Коли він увімкнений, сторінка завжди вважається
видимою, події `visibilitychange` не приходять, і повернення на вкладку нічого не перезапитує. Це та сама функція
протоколу `Emulation.setFocusEmulationEnabled`, якою скрипт повертав сторінку у видимий стан.

У jsdom подію можна подати вручну, і це зручно для тестів. Пастка дня нижче використовує саме такий спосіб.

## Неактивні дані: `gcTime`

Коли в запису кешу не лишилося жодного спостерігача, `Important Defaults` називає його **неактивним** (inactive).
Неактивний запис не зникає одразу: він лежить у кеші на випадок, якщо знадобиться знову. Скільки він лежить, задає
налаштування `gcTime`, за замовчуванням 5 хвилин. Коли час минув, бібліотека видаляє запис і звільняє пам'ять. Ця
дія називається збиранням сміття (garbage collection), звідси й скорочення в назві налаштування.

Тест скорочує `gcTime` до 1 секунди, щоб не чекати 5 хвилин. Він відкриває перелік, прибирає компонент і монтує його
знову: перший раз через пів секунди, другий раз через півтори:

```tsx
// src/library/lab/gc.test.tsx, фрагмент
// gcTime скорочено до 1 с, щоб тест не чекав 5 хвилин.
function Authors() {
  const q = useQuery({
    queryKey: ['authors'],
    queryFn: ({ signal }) => getJson<Author[]>('/api/authors', signal),
    gcTime: 1000,
  })
  log.push(`${now()} мс: рендер status=${q.status} isFetching=${q.isFetching}`)
  return <p>{q.data ? q.data.map((a) => a.name).join(', ') : 'Завантаження авторів…'}</p>
}

test('gcTime', async () => {
  installFakeApi(300)
  const client = new QueryClient()
  const ui = <QueryClientProvider client={client}><Authors /></QueryClientProvider>
  let view = render(ui)
  await screen.findByText(/Леся/)
  for (const pause of [500, 1500]) {
    view.unmount() // людина пішла з екрана: спостерігачів немає, запис став неактивним
    await new Promise((r) => setTimeout(r, pause))
    resetClock()
    log.push(`після паузи ${pause} мс записів у кеші: ${client.getQueryCache().getAll().length}`)
    view = render(ui)
    await screen.findByText(/Леся/)
    await new Promise((r) => setTimeout(r, 400))
    console.log(log.join('\n'))
  }
})
```

```text
після паузи 500 мс записів у кеші: 1
0 мс: рендер status=success isFetching=true
10 мс: старт /api/authors
310 мс: відповідь /api/authors
310 мс: рендер status=success isFetching=false
після паузи 1500 мс записів у кеші: 0
0 мс: рендер status=pending isFetching=true
0 мс: старт /api/authors
300 мс: відповідь /api/authors
300 мс: рендер status=success isFetching=false
```

Після пів секунди запис ще був у кеші, тому компонент одразу отримав `success` і дані, а запит пішов фоном. Після
півтори секунди запису вже не було, і компонент почав із `pending`, тобто людина знову дивилася на «Завантаження
авторів…».

`staleTime` і `gcTime` легко сплутати, тому порівняємо їх прямо. `staleTime` каже, чи йти на сервер: свіжі дані не
перезапитуються. `gcTime` каже, чи є що показати: поки запис у кеші, людина бачить дані одразу, навіть застарілі.
Обидва числа працюють незалежно. Зі `staleTime` 30 секунд і `gcTime` 5 хвилин дані протягом перших 30 секунд
показуються без запитів, а потім до 5 хвилин після того, як їх перестали показувати, показуються одразу з фоновим
запитом.

## Повтори після помилки

Ще одне правило `Important Defaults`: запит, який закінчився помилкою, бібліотека мовчки повторює 3 рази із
затримкою, яка щоразу подвоюється, і лише потім показує помилку. Сторінка `Query Retries` уточнює, що затримка
починається з 1000 мс і не перевищує 30 секунд. Тест просить автора 9, а підмінений сервер щоразу відповідає
статусом 500:

```tsx
// src/library/lab/retry.test.tsx, фрагмент
function Author9() {
  const q = useQuery({
    queryKey: ['authors', '9'],
    queryFn: ({ signal }) => getJson<Author>('/api/authors/9', signal),
  })
  log.push(`${now()} мс: рендер status=${q.status} failureCount=${q.failureCount}`)
  if (q.isPending) return <p>Завантаження…</p>
  if (q.isError) return <p role="alert">Помилка: {q.error.message}</p>
  return <h1>{q.data.name}</h1>
}

test('повтори за замовчуванням', async () => {
  installFakeApi(100)
  server.failing.add('/api/authors/9') // сервер щоразу відповідає 500
  resetClock()
  render(<QueryClientProvider client={new QueryClient()}><Author9 /></QueryClientProvider>)
  await screen.findByRole('alert', {}, { timeout: 12_000 })
  console.log(log.join('\n'))
  console.log('на екрані:', screen.getByRole('alert').textContent)
}, 15_000)
```

```text
10 мс: рендер status=pending failureCount=0
20 мс: старт /api/authors/9
120 мс: відповідь /api/authors/9
130 мс: рендер status=pending failureCount=1
1120 мс: старт /api/authors/9
1220 мс: відповідь /api/authors/9
1230 мс: рендер status=pending failureCount=2
3220 мс: старт /api/authors/9
3320 мс: відповідь /api/authors/9
3330 мс: рендер status=pending failureCount=3
7330 мс: старт /api/authors/9
7430 мс: відповідь /api/authors/9
7430 мс: рендер status=error failureCount=4
на екрані: Помилка: /api/authors/9: 500
```

Чотири спроби: перша й три повтори. Між ними 1, 2 і 4 секунди, тому помилку людина побачила лише на 7,4 секунді. Весь
цей час `status` лишався `pending`, а поле `failureCount` рахувало невдалі спроби. Повтори добре допомагають, коли
сервер на мить перевантажений чи мережа на мить зникла. Але якщо сервер чесно каже, що запису немає, сім секунд
очікування зайві. Налаштування `retry` дозволяє змінити кількість повторів або вирішувати за помилкою, чи
повторювати. Сьогоднішня практика цього не вимагає.

Без того, що `getJson` кидає помилку для статусу 500, повторів не було б зовсім: `fetch` вважав би відповідь 500
успішною, функція запиту повернула б тіло з полем `error`, і бібліотека поклала б його в `data`. Тому функція запиту
завжди мусить перевіряти `res.ok`. Приклад на сторінці `Overview` у документації версії 5.108.4 отримав саме таку
перевірку, а в 5.103.3 її ще не було.

## Devtools: що бачить розробник

Кеш живе всередині JavaScript, і його не видно ні на екрані, ні у вкладці Network. Для цього є окремий пакет:

```bash
npm install @tanstack/react-query-devtools@5.108.4
```

Компонент `ReactQueryDevtools` ставлять усередину `QueryClientProvider`, як у нашому `main.tsx` вище. Сторінка
`Devtools` радить ставити його якомога ближче до кореня. Властивість `initialIsOpen` каже, чи відкрита панель із
самого початку. Поки панель закрита, у правому нижньому куті сторінки стоїть кнопка з логотипом TanStack, яка її
відкриває. Чи відкрита панель, бібліотека запам'ятовує в `localStorage` браузера, тому після оновлення сторінки панель
лишається такою, як ви її залишили.

**Панель є лише в режимі розробки.** Сторінка `Devtools` каже, що пакет потрапляє в бандл лише тоді, коли
`process.env.NODE_ENV` дорівнює `'development'`. У коді пакета це записано прямо: в інших режимах `ReactQueryDevtools`
є функцією, яка повертає `null`. Vite підставляє `production` у продакшн-збірці, тому ми пошукали в зібраному файлі
слова, характерні для панелі, і не знайшли жодного. У Vitest змінна дорівнює `test`, тому в тестах панель теж нічого
не рендерить. Отже, щоб побачити панель, запускайте `npx vite`, а запити й час рахуйте на продакшн-збірці.

**Що показує панель.** Ми відкрили застосунок на сервері розробки в Chrome без вікна розміром 1100 на 760 точок і
зробили знімки екрана. Ось що на них видно; у вашому вікні розмір і тема можуть бути іншими.

- Угорі панелі стоїть перемикач `Queries` і `Mutations`. Мутації, тобто запити, які змінюють дані, вивчає день 5.
- Праворуч ряд лічильників із кольоровими крапками: `Fresh`, `Fetching`, `Paused`, `Stale` і `Inactive`. Вони
  рахують записи кешу в кожному стані. На головній одразу після завантаження лічильник `Fresh` показував 1.
- Нижче поле `Filter` для пошуку записів за ключем і список сортування `Sort by status`.
- Далі по рядку на кожен запис кешу. Ліворуч у рядку число спостерігачів, тобто скільки змонтованих компонентів
  зараз читають цей запис, а поруч ключ, наприклад `["authors"]`. Колір поля з числом відповідає стану запису.
- Через 150 мс після клацання на Лесю Українку панель показувала `Fetching 2` і `Inactive 1`. Два записи сторінки
  автора вантажилися й мали по одному спостерігачу, а запис `["authors"]` мав 0 спостерігачів, бо головну прибрано.
- Коли відповіді прийшли, ті самі два записи перейшли в `Stale 2`: їхній `staleTime` дорівнює 0, тому вони застаріли
  одразу. Запис `["authors"]` лишився неактивним.
- Клацання на рядок відкриває праворуч деталі запису. Розділ `Query Details` показує ключ, позначку стану (для
  `["authors"]` це було `inactive`), кількість спостерігачів `Observers` і час `Last Updated`, коли прийшли дані.
  Розділ `Actions` має кнопки `Refetch`, `Invalidate`, `Reset`, `Remove`, `Trigger Loading` і `Trigger Error`: ними
  можна перезапитати запис, позначити його застарілим, видалити чи на час показати екран завантаження або помилки.
  Розділ `Data Explorer` показує збережені дані деревом, а `Query Explorer` показує налаштування запису, серед яких
  `gcTime: 300000`.

Під час досліду ми випадково натиснули кнопку `Open in picture-in-picture mode`, і панель переїхала в окреме вікно.
Бібліотека запам'ятала й це в `localStorage`, тому після оновлення сторінки панель не з'явилася на своєму місці. Якщо
таке станеться у вас, закрийте окреме вікно кнопкою панелі або очистіть `localStorage` для сторінки.

## Пастка: копія `data` у `useState`

Часом хочеться покласти дані запиту в стан, наприклад, щоб потім їх редагувати. Ось два способи це зробити. Перший
кладе `data` у `useState` того самого компонента. Другий передає готові дані дочірньому компоненту, а той кладе їх у
свій стан. Третій компонент показує `data` напряму:

```tsx
// src/library/lab/focus.test.tsx, фрагмент
const authorsQuery = (staleTime: number) => ({
  queryKey: ['authors'],
  queryFn: ({ signal }: { signal: AbortSignal }) => getJson<Author[]>('/api/authors', signal),
  staleTime,
})

// Показує data напряму.
function Direct({ staleTime }: { staleTime: number }) {
  const { data } = useQuery(authorsQuery(staleTime))
  return <p>напряму: {data ? data.map((a) => a.name).join(', ') : '…'}</p>
}

// Пастка, перший варіант: data прямо в useState того самого компонента.
function CopyHere({ staleTime }: { staleTime: number }) {
  const { data } = useQuery(authorsQuery(staleTime))
  const [authors] = useState(data)
  return <p>копія тут: {authors ? authors.map((a) => a.name).join(', ') : '…'}</p>
}

// Пастка, другий варіант: дочірній компонент отримує готові дані й кладе їх у свій стан.
function CopyInChild({ staleTime }: { staleTime: number }) {
  const { data } = useQuery(authorsQuery(staleTime))
  if (!data) return <p>копія в дитині: …</p>
  return <EditableList initial={data} />
}
function EditableList({ initial }: { initial: Author[] }) {
  const [authors] = useState(initial)
  return <p>копія в дитині: {authors.map((a) => a.name).join(', ')}</p>
}
```

Функція `authorsQuery` збирає однакові налаштування запиту для всіх трьох компонентів, щоб ключ і функція запиту
напевно збігалися. Тест показує три компоненти, чекає на дані, а потім змінює «базу» підміненого сервера, ніби інша
людина додала авторку. Після цього тест подає подію `visibilitychange`, тобто імітує повернення на вкладку:

```tsx
// src/library/lab/focus.test.tsx, фрагмент
// Людина пішла на іншу вкладку й повернулася: браузер подає подію visibilitychange.
function returnToTab() {
  window.dispatchEvent(new Event('visibilitychange'))
}

for (const staleTime of [0, 30_000]) {
  test(`повернення на вкладку, staleTime ${staleTime}`, async () => {
    installFakeApi(300)
    render(
      <QueryClientProvider client={new QueryClient()}>
        <Direct staleTime={staleTime} />
        <CopyHere staleTime={staleTime} />
        <CopyInChild staleTime={staleTime} />
      </QueryClientProvider>,
    )
    await screen.findByText(/напряму: Леся/)
    // …друкуємо рядок «до»
    server.authors.push({ id: 3, name: 'Ольга Кобилянська', years: '1863–1942' }) // хтось додав автора
    resetClock()
    returnToTab()
    await new Promise((r) => setTimeout(r, 500))
    // …друкуємо журнал і рядок «після»
  })
}
```

```text
staleTime 0, visibilityState visible
  до:    напряму: Леся Українка, Іван Франко | копія тут: … | копія в дитині: Леся Українка, Іван Франко
  0 мс: старт /api/authors
  300 мс: відповідь /api/authors
  після: напряму: Леся Українка, Іван Франко, Ольга Кобилянська | копія тут: … | копія в дитині: Леся Українка, Іван Франко
staleTime 30000, visibilityState visible
  до:    напряму: Леся Українка, Іван Франко | копія тут: … | копія в дитині: Леся Українка, Іван Франко
  після: напряму: Леся Українка, Іван Франко | копія тут: … | копія в дитині: Леся Українка, Іван Франко
```

Зі `staleTime: 0` повернення на вкладку зробило один запит, і кеш отримав три авторки й автора. Компонент `Direct`
показав нову авторку. Обидві копії її не показали, і з різних причин.

Копія в тому самому компоненті не показала **нічого**, навіть першого переліку. Під час першого рендеру даних ще не
було, тому `useState(data)` запам'ятав `undefined`. Лекція «Структура стану», розділ «Не класти пропс у стан»,
пояснила, що аргумент `useState` є лише початковим значенням, і React дивиться на нього лише в першому рендері. Коли
дані прийшли, `data` змінилося, а стан ні.

Копія в дитині спершу виглядала правильно, бо `EditableList` з'явився вже з даними. Але після фонового запиту вона
лишилася зі старим переліком: дочірній компонент той самий, його стан той самий, а новий пропс `initial` стан не
змінює. Це та сама помилка, яку вчора розбирала пастка з лоадером, тільки джерело даних тепер кеш.

Зі `staleTime` 30 секунд дані були свіжі, тому повернення на вкладку не зробило запиту, і всі три компоненти
лишилися як були. Пастка з копією від цього не зникає: вона просто проявиться пізніше, коли дані застаріють.

Як уникнути пастки: читайте `data` з `useQuery` там, де показуєте дані, і не кладіть його в `useState`. Якщо дані
потрібні в дочірньому компоненті, передавайте їх пропсом і показуйте пропс напряму. Справжня чернетка для
редагування, яка свідомо не стежить за сервером, буває потрібна у формах. Тоді назвіть пропс `initial…`, як радила
лекція «Структура стану», щоб читач коду бачив, що зміни на сервері до чернетки не доходять. Форми план вивчає в днях
9 і 10 цієї фази.

## Як перевірити самому

Ось що побачите ви, коли повторите сьогоднішні досліди в Chrome з вікном. Самі ми працювали без вікна, тому опис
вкладки Network нижче спирається на документацію Chrome і на події, які той самий браузер надсилав скрипту.

1. **Devtools у режимі розробки.** Запустіть `npx vite`, відкрийте застосунок і клацніть кнопку з логотипом TanStack
   у куті сторінки. Перейдіть між сторінками й подивіться, як записи переходять між `Fresh`, `Fetching`, `Stale` і
   `Inactive`, а число спостерігачів падає до 0, коли ви йдете з екрана.
2. **Мережа на продакшн-збірці.** Зберіть застосунок і відкрийте його через `npx vite preview`. Режим розробки для
   підрахунку запитів не годиться: `<StrictMode>` там додає скасований рядок для кожного запиту із сигналом.
3. У вкладці Network поставте прапорець `Disable cache`. Набір уповільнення не обов'язковий: кількість запитів від
   нього не залежить, а з набором `Slow 4G` різниця між переліком з кешу й переліком із сервера помітніша.
4. Відкрийте екран із запитом, якому ви задали `staleTime` 30 секунд, перейдіть на інший екран і поверніться до 30
   секунд після завантаження. Нових рядків для цього запиту не буде. Повторіть після 30 секунд: з'явиться один рядок,
   а дані на екрані будуть видні ще до його кінця.
5. Перевіряючи повернення на вкладку, переконайтеся, що на панелі Rendering вимкнено «Emulate a focused page».

Записуючи результат, пишіть поруч умови: яка збірка, скільки секунд минуло від завантаження і яке значення
`staleTime` має кожен запит на екрані.

## Типові хибні уявлення

**«`staleTime` каже, скільки дані лежать у кеші».** Скільки лежить неактивний запис, каже `gcTime`. `staleTime` каже,
скільки дані вважаються свіжими й не перезапитуються.

**«Застарілі дані не показуються, поки не прийдуть нові».** Застарілі дані показуються одразу, а перевірка йде у фоні.
У браузері перелік зі `staleTime: 0` з'являвся при поверненні за 6–8 мс, а запит закінчувався через пів секунди.

**«30 секунд рахуються від моменту, коли я пішов з екрана».** Вони рахуються від моменту, коли прийшли дані. Дані,
отримані о 10:00:00, о 10:00:31 уже застарілі, навіть якщо ви бачили їх секунду тому.

**«Повернення на екран і повернення на вкладку є тим самим».** Перше є новим монтуванням компонента в межах
застосунку, друге є подією браузера `visibilitychange`. Кожне має власне налаштування: `refetchOnMount` і
`refetchOnWindowFocus`.

**«Ключ є просто назвою запиту».** Ключ є адресою запису в кеші й списком залежностей. Сторінка з ключем `['books']`
без номера автора показала книжки Лесі Українки на сторінці Франка і не зробила жодного запиту.

**«`useQuery` захищає від гонок, бо скасовує старі запити».** Захищає ключ: стара відповідь лягає у свій запис і не
потрапляє на чужу сторінку. Скасування відбувається лише тоді, коли функція запиту взяла `signal`.

**«Рядок `(canceled)` у вкладці Network означає помилку».** У режимі розробки його дає `<StrictMode>`, коли функція
запиту бере `signal`. У продакшн-збірці на кожен запит один рядок.

**«Помилка сервера одразу з'являється на екрані».** За замовчуванням бібліотека робить три повтори через 1, 2 і 4
секунди, тому людина бачить помилку приблизно через 7 секунд.

**«Devtools треба прибирати перед викотом».** Пакет сам повертає порожній компонент поза режимом розробки, і в
продакшн-збірці його коду немає.

**«Копія `data` у стані зручніша, бо її можна змінювати».** Копія перестає оновлюватися разом із кешем, а якщо її
зробити в тому самому компоненті, вона може взагалі лишитися порожньою.

## Як це проявиться далі в React

- **Фаза 3, день 4, лоадер плюс кеш.** Сьогодні запит починався лише після рендеру сторінки, а вчорашній лоадер
  починав його в мить клацання. Завтра лоадер попросить дані в кеша, а компонент читатиме той самий запис через
  `useQuery`. Ключі в лоадері й компоненті мусять збігатися до символу, і сьогоднішній рядок
  `["authors","1"] ["authors",1]` пояснює чому.
- **Фаза 3, день 5, мутації й оптимістичні оновлення.** Кнопки `Invalidate` і вкладка `Mutations` у Devtools
  знадобляться, коли застосунок почне змінювати дані на сервері й позначати записи застарілими.
- **Фаза 3, дні 6–8, живі дані.** Список монет користувача ходитиме через той самий фейковий API і TanStack Query, а
  живі ціни прийдуть окремим каналом.
- **Фаза 3, день 13, тести з мережею.** Сьогоднішній підмінений `fetch` замінить бібліотека MSW, яка перехоплює
  справжні запити.

## Перевірте себе

**1. Перелік має `staleTime: 30_000`. Дані прийшли о 12:00:00. Людина пішла з екрана о 12:00:20 і повернулася о
12:00:40. Що вона побачить і скільки запитів піде?**

<details><summary>Відповідь</summary>

Перелік з'явиться одразу з кешу, бо запис ще не видалено: `gcTime` за замовчуванням 5 хвилин. Дані на 40-й секунді
вже застарілі, бо 30 секунд рахуються від 12:00:00, тому новий спостерігач запустить один фоновий запит. Поки він
іде, `status` дорівнює `success`, а `isFetching` дорівнює `true`.

</details>

**2. Чим відрізняються `status` і `fetchStatus`? Наведіть поєднання, у якому людина бачить дані, а запит іде.**

<details><summary>Відповідь</summary>

`status` каже, чи є дані: `pending`, `error` або `success`. `fetchStatus` каже, чи працює функція запиту: `fetching`,
`idle` або `paused`. Дані на екрані під час запиту означають `status: 'success'` і `fetchStatus: 'fetching'`: це
фоновий запит. У нашому браузерному досліді в цей час поруч із заголовком стояв напис «оновлюю…».

</details>

**3. Сторінка автора має `queryKey: ['books']`, а функція запиту бере номер автора з адреси. Що побачить людина,
перейшовши від автора 1 до автора 2?**

<details><summary>Відповідь</summary>

Книжки автора 1. Ключ не змінився, тому бібліотека бере той самий запис кешу, у якому вже є дані, і запиту не робить.
У нашому тесті за секунду не пішло жодного запиту. Номер автора треба покласти в ключ: `['authors', authorId,
'books']`.

</details>

**4. У режимі розробки вкладка Network показує на першому відкритті два запити `authors`, і один із них скасовано. Це
помилка в коді?**

<details><summary>Відповідь</summary>

Ні. `<StrictMode>` у режимі розробки монтує компонент, прибирає й монтує знову. Коли компонент прибрано, запис лишився
без спостерігачів, а функція запиту бере `signal`, тому бібліотека скасувала запит. Друге монтування почало його
знову. Без сигналу запит був би один, а в продакшн-збірці він один і з сигналом.

</details>

**5. Чим повернення на екран відрізняється від повернення на вкладку з погляду TanStack Query?**

<details><summary>Відповідь</summary>

Повернення на екран є новим монтуванням компонента з `useQuery`, тобто появою нового спостерігача: це перевіряє
`refetchOnMount`. Повернення на вкладку є подією браузера `visibilitychange`, коли компонент увесь час був на екрані:
це перевіряє `refetchOnWindowFocus`. В обох випадках фоновий запит іде лише для застарілих даних.

</details>

**6. Сервер щоразу відповідає статусом 500. Через скільки людина побачить повідомлення про помилку за налаштувань за
замовчуванням і що вона бачитиме до того?**

<details><summary>Відповідь</summary>

Приблизно через 7 секунд плюс час чотирьох відповідей сервера: у нашому тесті на 7,4 секунді. Бібліотека робить
першу спробу й три повтори з паузами 1, 2 і 4 секунди. Весь цей час `status` дорівнює `pending`, тож людина бачить
повідомлення про завантаження.

</details>

**7. Компонент робить `const [authors] = useState(data)` одразу після `useQuery`. Чому на екрані може не з'явитися
навіть перший перелік?**

<details><summary>Відповідь</summary>

Під час першого рендеру даних ще немає, тому `useState` запам'ятовує `undefined`. Аргумент `useState` є лише
початковим значенням, і коли `data` прийде, стан не зміниться. Треба показувати `data` напряму.

</details>

## Словничок лекції

| Слово | Що означає |
|-------|------------|
| серверний стан | дані, справжня версія яких лежить на сервері, а браузер має лише копію, що може застаріти |
| клієнтський стан | дані, які існують лише в браузері й належать тільки вашому коду |
| кеш | збережені в браузері відповіді сервера, які можна показати одразу |
| `QueryClient` | об'єкт, у якому живуть кеш і налаштування; створюється один раз на застосунок |
| `QueryClientProvider` | компонент-провайдер, що передає клієнт усім компонентам усередині |
| `useQuery` | хук, що оголошує потрібні дані за ключем і повертає їх разом зі станом |
| ключ запиту (`queryKey`) | масив, що називає дані; бібліотека перетворює його на рядок і шукає за ним запис кешу |
| функція запиту (`queryFn`) | функція, що йде по дані й повертає проміс із даними або кидає помилку |
| `status` | чи є дані: `pending`, `error` або `success` |
| `fetchStatus` | чи працює функція запиту: `fetching`, `idle` або `paused` |
| фоновий запит | перевірка на сервері, поки людина вже бачить дані з кешу |
| спостерігач | внутрішній об'єкт, яким `useQuery` стежить за записом кешу; з'являється під час монтування компонента |
| свіжі дані (fresh) | дані, з моменту отримання яких минуло менше за `staleTime`; не перезапитуються |
| застарілі дані (stale) | дані, для яких `staleTime` минув; показуються, але при нагоді перевіряються |
| `staleTime` | скільки мілісекунд після отримання дані вважаються свіжими; за замовчуванням 0 |
| неактивний запис | запис кешу без жодного спостерігача |
| `gcTime` | скільки неактивний запис лежить у кеші, перш ніж його видалять; за замовчуванням 5 хвилин |
| `refetchOnWindowFocus` | чи перезапитувати застарілі дані, коли сторінка знову стає видимою |
| `visibilitychange` | подія браузера, коли сторінка стає видимою чи схованою |
| поєднання запитів (deduping) | один запит на всі компоненти, які одночасно просять той самий ключ |
| `failureCount` | скільки спроб запиту вже закінчилися помилкою |
| Devtools | панель TanStack Query для розробника, що показує записи кешу; є лише в режимі розробки |
