### Вступний абзац

Сторінка починається з означення: замикання є поєднанням функції й посилань на стан навколо неї. Цей стан MDN називає
**lexical environment** (лексичне оточення), а лекція називає оточенням. Друга важлива думка стоїть у кінці абзацу:
замикання створюється щоразу, коли створюється функція, і саме в цю мить. Отже, замикання не є рідкісним прийомом, а
властивістю кожної функції.

| Вираз | Що означає |
|-------|------------|
| bundled together, enclosed | функція й оточення існують разом, звідси й назва «замикання» |
| outer scope | область видимості навколо функції |

### `Lexical scoping`

Розділ починається з такого коду:

```js
function init() {
  var name = "Mozilla"; // name is a local variable created by init
  function displayName() {
    // displayName() is the inner function, that forms a closure
    console.log(name); // use variable declared in the parent function
  }
  displayName();
}
init();
```

У Node 24 цей код друкує:

```text
Mozilla
```

Функція `init` створює змінну `name` і функцію `displayName`. Функцію `displayName` оголошено всередині `init`, тому
викликати її можна лише в тілі `init`. Власних змінних функція `displayName` не має, але рядок `console.log(name)` у
ній однаково друкує `Mozilla`. Це відбувається тому, що `displayName` записано всередині `init`, і змінна `name` з
`init` для неї доступна. MDN використовує цей приклад, щоб показати просте правило: вкладена функція бачить змінні
зовнішньої. Потім MDN пояснює слово **lexical**: місце, де змінну оголошено в тексті програми, визначає, де вона
доступна.

Слово **parser** у цьому розділі означає частину рушія, яка читає текст програми й розбирає його будову. **Рушій** —
це програма, яка виконує JavaScript.

**Навіщо в React.** Компонент часто містить обробники, оголошені всередині нього. Обробник бачить пропси та стан
компонента, бо він вкладений у функцію компонента. Це те саме правило.

### `Scoping with let and const`

Раніше JavaScript мав лише дві області видимості для змінних: функцію й увесь скрипт. Ключове слово `var` не зважає на
фігурні дужки блока, тому змінна, оголошена в `if`, видна й після нього. Розділ показує це таким кодом:

```js
if (Math.random() > 0.5) {
  var x = 1;
} else {
  var x = 2;
}
console.log(x);
```

Функція `Math.random()` повертає випадкове число від 0 до 1. Тому `if` у половині випадків виконує першу гілку й
записує в `x` число 1, а в іншій половині виконує гілку `else` і записує в `x` число 2. Обидва рядки `var x`
оголошують ту саму змінну, і ця змінна видна й після закритої фігурної дужки. Тому рядок `console.log(x)` друкує 1
або 2. Ми запустили цей код у Node 24 десять разів: сім запусків надрукували `1`, а три запуски надрукували `2`.
Людина, яка прийшла з мови C чи Java, чекала б тут помилки, бо в цих мовах змінна, оголошена в блоці, поза блоком не
видна.

Другий фрагмент розділу відрізняється лише словом `const`:

```js
if (Math.random() > 0.5) {
  const x = 1;
} else {
  const x = 2;
}
console.log(x); // ReferenceError: x is not defined
```

Тепер кожна гілка створює власну змінну `x`, яка існує лише всередині своїх фігурних дужок. Рядок `console.log(x)`
стоїть поза обома блоками, тому JavaScript не знаходить там жодної змінної `x`. Node зупиняє програму з помилкою
`ReferenceError: x is not defined`, як і написано в коментарі MDN.

Ось та сама думка без випадковості:

```js
function withVar() {
  if (true) {
    var size = "великий";
  }
  return size;
}
console.log(withVar());

function withLet() {
  if (true) {
    let size = "великий";
  }
  return typeof size;
}
console.log(withLet());
```

```text
великий
undefined
```

MDN пише, що `var` у першому фрагменті створює глобальну змінну. Це правда лише для його випадку, коли код стоїть на
верхньому рівні звичайного скрипта. У функції `var` створює змінну цієї функції, як у `withVar` вище.

Розділ згадує **temporal dead zones**. Їх розібрано нижче, у сторінці `let`. Згадано й **ES6**: так називають версію
мови 2015 року, у якій з'явилися `let`, `const` і модулі.

**Навіщо в React.** Сучасний код на React не використовує `var`. Проте старі приклади й чужий код його містять, тому
варто знати, чому змінна виходить за межі блока.

### `Closure`

Це головний розділ сторінки. Він бере попередній приклад і змінює одне: зовнішня функція, яку тепер звуть
`makeFunc`, не викликає внутрішню функцію, а повертає її:

```js
function makeFunc() {
  const name = "Mozilla";
  function displayName() {
    console.log(name);
  }
  return displayName;
}

const myFunc = makeFunc();
myFunc();
```

```text
Mozilla
```

Рядок `const myFunc = makeFunc()` викликає `makeFunc`. Функція `makeFunc` створює змінну `name` і функцію
`displayName`, повертає `displayName` і на цьому закінчує роботу. Повернена функція потрапляє в змінну `myFunc`.
Наступний рядок викликає `myFunc`, тобто ту саму функцію `displayName`, і вона друкує `Mozilla`. MDN зауважує, що це
може здатися дивним. У деяких мовах локальні змінні функції існують лише доти, доки функція виконується, тому після
завершення `makeFunc` можна було б чекати, що змінної `name` вже немає. MDN пояснює, чому в JavaScript інакше:
екземпляр внутрішньої функції тримає посилання на своє оточення, а в оточенні лежить змінна `name`.

Слово **instance** (екземпляр) тут важливе. Текст функції один, але кожне виконання коду, який її створює, дає новий
об'єкт:

```js
function makeHandler() {
  return () => {};
}
console.log(makeHandler() === makeHandler());
```

```text
false
```

Другий приклад розділу — функція `makeAdder`:

```js
function makeAdder(x) {
  return function (y) {
    return x + y;
  };
}

const add5 = makeAdder(5);
const add10 = makeAdder(10);

console.log(add5(2)); // 7
console.log(add10(2)); // 12
```

```text
7
12
```

Функція `makeAdder` приймає число `x` і повертає нову функцію. Повернена функція приймає число `y` і повертає суму
`x + y`. Виклик `makeAdder(5)` створює оточення, у якому `x` дорівнює 5, створює в ньому нову функцію, і ця функція
потрапляє в `add5`. Виклик `makeAdder(10)` створює інше оточення, у якому `x` дорівнює 10, і ще одну нову функцію,
яка потрапляє в `add10`. Тому `add5(2)` повертає 5 + 2 = 7, а `add10(2)` повертає 10 + 2 = 12. Отже, `add5` і
`add10` мають спільний текст функції, але різні оточення. Функцію, яка створює й повертає інші функції, MDN називає
фабрикою функцій (**function factory**), і `makeAdder` є саме такою фабрикою. Лекція показує той самий механізм на
прикладі податків, з кожним кроком у таблиці.

**Навіщо в React.** Кожен рендер створює нові екземпляри обробників. Вони виглядають однаково, але це інші об'єкти, і
кожен тримає змінні свого рендеру.

### `Practical closures`

Замикання дає змогу зв'язати дані з функцією, яка з ними працює. Об'єкт робить те саме, тому замикання можна
використати всюди, де ви створили б об'єкт із одним методом.

Приклад розділу змінює розмір тексту на сторінці. Стилі цього прикладу задають розмір шрифту елемента `body` у
пікселях, а розмір заголовків задають в одиницях `em`, тобто відносно розміру шрифту `body`. Тому досить змінити
розмір шрифту `body`, і заголовки зміняться разом із ним. Ось код JavaScript із розділу:

```js
function makeSizer(size) {
  return () => {
    document.body.style.fontSize = `${size}px`;
  };
}

const size12 = makeSizer(12);
const size14 = makeSizer(14);
const size16 = makeSizer(16);
```

Функція `makeSizer` приймає число пікселів `size` і повертає стрілкову функцію. Ця стрілкова функція складає рядок на
зразок `12px` і записує його у властивість `fontSize` стилю елемента `body`, тобто задає розмір шрифту всієї
сторінки. Три виклики `makeSizer` створюють три функції, і кожна тримає власне оточення. У функції `size12` змінна
`size` дорівнює 12, у функції `size14` вона дорівнює 14, а у функції `size16` вона дорівнює 16. Далі розділ прикріплює
ці три функції до трьох кнопок:

```js
document.getElementById("size-12").onclick = size12;
document.getElementById("size-14").onclick = size14;
document.getElementById("size-16").onclick = size16;
```

```html
<button id="size-12">12</button>
<button id="size-14">14</button>
<button id="size-16">16</button>
<p>This is some text that will change size when you click the buttons above.</p>
```

Метод `document.getElementById` знаходить на сторінці елемент, у якого атрибут `id` має задане значення. Властивість
**`onclick`** — це властивість елемента, у яку кладуть функцію, що спрацює при натисканні. Тому натискання кнопки з
написом `12` викликає функцію `size12`, і вона ставить шрифт розміром 12 пікселів. Код потребує сторінки, тому не
запускається в Node. На самій сторінці MDN є робочий приклад: натисніть кнопки, і текст змінить розмір.

Вираз **event-based** означає, що код не йде від початку до кінця, а реагує на події, наприклад на натискання.

**Навіщо в React.** Уявіть компонент, у якому `setSize` є функцією, що змінює стан із розміром шрифту. Запис
`onClick={() => setSize(12)}` у такому компоненті робить те саме, що й `makeSizer`: створює функцію, яка спрацює
пізніше й тримає потрібні дані.

### `Emulating private methods with closures`

Деякі мови мають позначку `private`, яка забороняє викликати метод зовні. До появи класів у JavaScript такого не було,
але те саме давали замикання. Приклад створює об'єкт `counter` із трьома функціями навколо приватної змінної та
приватної функції:

```js
const counter = (function () {
  let privateCounter = 0;
  function changeBy(val) {
    privateCounter += val;
  }

  return {
    increment() {
      changeBy(1);
    },

    decrement() {
      changeBy(-1);
    },

    value() {
      return privateCounter;
    },
  };
})();

console.log(counter.value()); // 0.

counter.increment();
counter.increment();
console.log(counter.value()); // 2.

counter.decrement();
console.log(counter.value()); // 1.
```

```text
0
2
1
```

Змінна `privateCounter` і функція `changeBy` лежать усередині безіменної функції, яку викликано один раз. Ця функція
повертає об'єкт із трьома методами, і цей об'єкт потрапляє в змінну `counter`. Запис `increment() { ... }` усередині
об'єкта є коротким способом записати поле `increment`, значенням якого є функція. Метод `increment` викликає
`changeBy(1)` і так додає 1 до `privateCounter`. Метод `decrement` викликає `changeBy(-1)` і віднімає 1. Метод
`value` повертає поточне значення `privateCounter`. Тому код друкує спершу 0, після двох викликів `increment` друкує
2, а після одного виклику `decrement` друкує 1. Код зовні може викликати лише ці три методи. До `privateCounter` і
`changeBy` він дістатися не може, бо ці імена існують лише в оточенні безіменної функції.

У цьому коді є незнайомий запис. **IIFE** (immediately invoked function expression) — це функція, яку викликають
одразу після створення: `(function () { ... })()`. Вона потрібна, щоб отримати власне оточення один раз. Зовнішні
дужки потрібні для того, щоб рушій прочитав запис як вираз, а не як оголошення функції.

Другий приклад розділу перетворює безіменну функцію на звичайну функцію з ім'ям `makeCounter` і викликає її двічі:

```js
function makeCounter() {
  let privateCounter = 0;
  function changeBy(val) {
    privateCounter += val;
  }
  return {
    increment() {
      changeBy(1);
    },

    decrement() {
      changeBy(-1);
    },

    value() {
      return privateCounter;
    },
  };
}

const counter1 = makeCounter();
const counter2 = makeCounter();

console.log(counter1.value()); // 0.

counter1.increment();
counter1.increment();
console.log(counter1.value()); // 2.

counter1.decrement();
console.log(counter1.value()); // 1.
console.log(counter2.value()); // 0.
```

```text
0
2
1
0
```

Кожен виклик `makeCounter` створює нове оточення з власною змінною `privateCounter`. Методи об'єкта `counter1`
тримають перше оточення, а методи об'єкта `counter2` тримають друге. Три виклики методів `counter1` змінюють лише
змінну з першого оточення. Тому останній рядок друкує 0: змінну `privateCounter` лічильника `counter2` ніхто не
змінював.

Запам'ятайте різницю між двома прикладами розділу. У першому три функції мають спільне оточення, бо створені в одному
виклику. У другому прикладі `makeCounter` викликано двічі, тому два лічильники незалежні. Лекція показує цю ж різницю
на гаманці.

| Вираз | Що означає |
|-------|------------|
| Module Design Pattern | прийом, коли функція приховує змінні й віддає назовні лише кілька функцій |
| global namespace | спільний простір імен усього скрипта, який легко засмітити |
| data hiding, encapsulation | приховання даних, до яких код зовні може дістатися лише через дозволені функції |

**Навіщо в React.** Власні хуки працюють схожим способом: функція приховує деталі, а назовні віддає значення й функції
для роботи з ними. **Хук** — це функція React з префіксом `use`. Їх ви вивчатимете у фазі 1.

### `Closure scope chain`

Функція бачить не лише зовнішню функцію, а й усе, що навколо неї, аж до верхнього рівня. MDN показує це таким кодом:

```js
// global scope
const e = 10;
function sum(a) {
  return function (b) {
    return function (c) {
      // outer functions scope
      return function (d) {
        // local scope
        return a + b + c + d + e;
      };
    };
  };
}

console.log(sum(1)(2)(3)(4)); // 20
```

```text
20
```

Функція `sum` повертає функцію, та повертає ще одну функцію, і так до четвертого рівня вкладення. Запис
`sum(1)(2)(3)(4)` означає: виклич `sum` з аргументом 1, потім виклич з аргументом 2 те, що вона повернула, і так
далі. Функція четвертого рівня отримує лише `d`, але додає до нього `a`, `b` і `c` з трьох зовнішніх функцій і `e` з
верхнього рівня файла: 1 + 2 + 3 + 4 + 10 = 20. Далі сторінка записує той самий код, дає внутрішнім функціям імена
`sum2`, `sum3` і `sum4` і кладе кожен проміжний результат в окрему змінну. Результат лишається тим самим, 20. Ось
такий самий ланцюг на прикладі ціни:

```js
const delivery = 50;
function total(price) {
  return function (qty) {
    return function (discount) {
      return price * qty - discount + delivery;
    };
  };
}
console.log(total(100)(2)(30));
const forTea = total(100);
const twoTeas = forTea(2);
console.log(twoTeas(0), twoTeas(30));
```

```text
220
250 220
```

Найглибше вкладена функція читає `discount` зі свого оточення, `qty` і `price` із зовнішніх, а `delivery` з верхнього
рівня файла. Перший виклик дає 100 × 2 − 30 + 50 = 220. Проміжні результати `forTea` і `twoTeas` можна зберегти й
використати кілька разів, бо кожен із них пам'ятає свої змінні.

Далі розділ показує, що замикання тримає й змінну блока. Код нижче повторює приклад MDN, лише змінну `y` зі значенням
6 тут названо `code` і дано їй значення 42:

```js
function outer() {
  let getCode;
  {
    const code = 42;
    getCode = () => code;
  }
  console.log(typeof code);
  console.log(getCode());
}
outer();
```

```text
undefined
42
```

Змінна `code` існує лише всередині фігурних дужок, тому `typeof code` поза ними повертає рядок `undefined`. Стрілкова
функція, яку створили всередині дужок, тримає оточення цього блока. Тому виклик `getCode()` після виходу з блока
однаково повертає 42.

Наприкінці йдеться про **модулі**, тобто файли зі своєю областю видимості, з яких код явно експортують через `export`.
Модуль сам створює оточення, і функції модуля можуть його тримати. MDN показує це на прикладах із файлами
`myModule.js` і `closureCreator.js`. Нижче ті самі приклади зібрано у два файли, запущені на Node як `.mjs`:

```js
// settings.mjs
let theme = "світла";
export const getTheme = () => theme;
export const setTheme = (next) => {
  theme = next;
};
export let language = "uk";
export const setLanguage = (next) => {
  language = next;
};
```

```js
// use.mjs
import { getTheme, setTheme, language, setLanguage } from "./settings.mjs";

console.log(getTheme());
setTheme("темна");
console.log(getTheme());

const readLanguage = () => language;
console.log(readLanguage());
setLanguage("en");
console.log(readLanguage());
```

```text
світла
темна
uk
en
```

Змінна `theme` не експортована, тому прочитати її можна лише через дві функції. Імпорт `language` не копіює значення:
MDN називає імпортоване ім'я **live binding**, тобто «живою прив'язкою» до змінної в іншому модулі. Тому
`readLanguage` бачить нове значення.

Модулі докладно розбирає день 4 цієї фази.

**Навіщо в React.** Обробник у компоненті читає одразу кілька рівнів: власні змінні, пропси й стан компонента, імпорти
модуля. Весь цей ланцюг працює за описаним тут правилом.

### `Creating closures in loops: A common mistake`

Це розділ про помилку, яка стоїть за завданням із циклом. Сторінка прикладу має абзац для підказки й три поля вводу:

```html
<p id="help">Helpful notes will appear here</p>
<p>Email: <input type="text" id="email" name="email" /></p>
<p>Name: <input type="text" id="name" name="name" /></p>
<p>Age: <input type="text" id="age" name="age" /></p>
```

Код JavaScript призначає кожному полю функцію, яка показує підказку:

```js
function showHelp(help) {
  document.getElementById("help").textContent = help;
}

function setupHelp() {
  var helpText = [
    { id: "email", help: "Your email address" },
    { id: "name", help: "Your full name" },
    { id: "age", help: "Your age (you must be over 16)" },
  ];

  for (var i = 0; i < helpText.length; i++) {
    // Culprit is the use of `var` on this line
    var item = helpText[i];
    document.getElementById(item.id).onfocus = function () {
      showHelp(item.help);
    };
  }
}

setupHelp();
```

Функція `showHelp` записує переданий текст в абзац, у якого `id` дорівнює `help`. Функція `setupHelp` заводить масив
`helpText` із трьох об'єктів, і кожен об'єкт містить `id` поля й текст підказки для цього поля. Цикл проходить масив,
кладе поточний об'єкт у змінну `item` і записує у властивість `onfocus` відповідного поля нову функцію. Властивість
**`onfocus`** містить функцію, що спрацьовує, коли поле отримує фокус, тобто коли курсор ставлять у поле. Кожна з
трьох нових функцій викликає `showHelp(item.help)`. Коментар MDN у циклі прямо називає винуватцем слово `var` у рядку
з `item`. Код потребує сторінки, тому не запускається в Node. У робочому прикладі на сторінці MDN ви побачите: хоч
яке поле вибрати, підказка завжди про вік.

Причина така. Три функції мають спільне оточення, бо `var item` оголошена один раз на всю функцію `setupHelp`. Коли
користувач ставить курсор у поле, цикл уже завершився, і `item` вказує на останній елемент. MDN пояснює це через
**hoisting**. Цим словом називають те, що оголошення `var` діє у всій функції, навіть якщо рядок оголошення стоїть
нижче або всередині циклу.

MDN дає кілька виправлень, і всі вони створюють окрему змінну для кожного проходу. Решта коду в них лишається майже
тією самою, тому нижче наведено лише частини, які змінилися.

Перше виправлення додає фабрику функцій `makeHelpCallback`:

```js
function makeHelpCallback(help) {
  return function () {
    showHelp(help);
  };
}
```

У циклі полю присвоюють те, що повертає ця фабрика:

```js
document.getElementById(item.id).onfocus = makeHelpCallback(item.help);
```

Кожен виклик `makeHelpCallback` створює нове оточення, у якому параметр `help` містить текст підказки саме цього
проходу. Повернена функція тримає це оточення, тому кожне поле показує свою підказку.

Друге виправлення загортає тіло циклу в IIFE, тобто у функцію, яку викликають одразу після створення. Цей запис
докладно пояснено вище, у розділі `Emulating private methods with closures`:

```js
for (var i = 0; i < helpText.length; i++) {
  (function () {
    var item = helpText[i];
    document.getElementById(item.id).onfocus = function () {
      showHelp(item.help);
    };
  })(); // Immediate event listener attachment with the current value of item (preserved until iteration).
}
```

Тепер `var item` оголошено всередині IIFE. Кожен прохід циклу викликає IIFE заново, і кожен виклик створює нове
оточення з новою змінною `item`.

Третє виправлення замінює `var` на `let` і `const`:

```js
for (let i = 0; i < helpText.length; i++) {
  const item = helpText[i];
  document.getElementById(item.id).onfocus = () => {
    showHelp(item.help);
  };
}
```

Змінна `const item` належить блоку тіла циклу, а кожен прохід виконує цей блок заново й отримує нову змінну `item`.
MDN зазначає, що тут уже не потрібні додаткові замикання. У цьому варіанті сторінка оголошує й масив `helpText` через
`const`, а не через `var`.

Четверте виправлення обходиться без звичайного циклу `for`:

```js
for (const item of helpText) {
  document.getElementById(item.id).onfocus = () => {
    document.getElementById("help").textContent = item.help;
  };
}

helpText.forEach((item) => {
  document.getElementById(item.id).onfocus = () => {
    showHelp(item.help);
  };
});
```

Цикл `for...of` по черзі кладе в змінну `item` кожен елемент масиву й на кожному проході створює нову змінну. Метод
`forEach` викликає передану функцію для кожного елемента, і `item` у ньому є параметром цієї функції, тобто новою
змінною кожного виклику.

Таблиця підсумовує ці чотири способи:

| Спосіб | Що він робить |
|--------|---------------|
| Фабрика `makeHelpCallback` | кожен виклик створює нове оточення з власним параметром |
| IIFE в тілі циклу | кожен прохід викликає функцію й отримує нове оточення |
| `let` або `const` | блок циклу отримує нову змінну на кожному проході |
| `for...of` або `forEach` | кожен прохід має власну змінну, а для `forEach` це власний параметр функції |

Перевіримо всі ідеї на прикладі без сторінки:

```js
const items = ["чай", "кава"];
const viaFactory = [];
function makeLabel(text) {
  return () => "товар: " + text;
}
for (var i = 0; i < items.length; i++) {
  viaFactory.push(makeLabel(items[i]));
}
console.log(viaFactory[0](), viaFactory[1]());

const viaIife = [];
for (var j = 0; j < items.length; j++) {
  (function () {
    var text = items[j];
    viaIife.push(() => "товар: " + text);
  })();
}
console.log(viaIife[0](), viaIife[1]());

const viaForEach = [];
items.forEach((text) => {
  viaForEach.push(() => "товар: " + text);
});
console.log(viaForEach[0](), viaForEach[1]());
```

```text
товар: чай товар: кава
товар: чай товар: кава
товар: чай товар: кава
```

Зверніть увагу, що виклик IIFE читає `items[j]` одразу, під час проходу. Тому `var text` усередині неї отримує
правильний елемент, хоча `j` одна на всі проходи.

**Навіщо в React.** Списки в React зазвичай будують через `map`, а функція в `map` має власний параметр на кожен
елемент. Тому `items.map((item) => <button onClick={() => pick(item)} />)` не має цієї помилки.

### `Performance considerations`

Кожен екземпляр функції займає пам'ять, тому не варто створювати функції всередині функцій без потреби. MDN показує це
на **конструкторі**, тобто функції, яку викликають через `new`, щоб отримати новий об'єкт. Перший варіант на сторінці
створює методи всередині конструктора:

```js
function MyObject(name, message) {
  this.name = name.toString();
  this.message = message.toString();
  this.getName = function () {
    return this.name;
  };

  this.getMessage = function () {
    return this.message;
  };
}
```

Кожен виклик `new MyObject(...)` виконує тіло цієї функції заново. Тому кожен новий об'єкт отримує дві нові функції
`getName` і `getMessage`, хоча ці функції не користуються жодною змінною з оточення конструктора. Метод `toString` у
цьому коді перетворює аргумент на рядок. Останній варіант на сторінці кладе ці методи в прототип:

```js
function MyObject(name, message) {
  this.name = name.toString();
  this.message = message.toString();
}
MyObject.prototype.getName = function () {
  return this.name;
};
MyObject.prototype.getMessage = function () {
  return this.message;
};
```

Між цими двома варіантами сторінка показує ще один, який замінює прототип цілим новим об'єктом, і одразу каже, що
так робити не радять. Ці приклади нічого не друкують, тому нижче різницю показано на власному прикладі. Якщо метод
створюється в конструкторі, кожен об'єкт отримає власну копію методу. Якщо метод покласти в **прототип**, тобто
об'єкт, спільний для всіх об'єктів цього конструктора, копія буде одна:

```js
function PerObject(name) {
  this.name = name;
  this.hello = function () {
    return "привіт, " + this.name;
  };
}
function Shared(name) {
  this.name = name;
}
Shared.prototype.hello = function () {
  return "привіт, " + this.name;
};

const a1 = new PerObject("а");
const a2 = new PerObject("б");
const b1 = new Shared("а");
const b2 = new Shared("б");
console.log(a1.hello === a2.hello, a1.hello());
console.log(b1.hello === b2.hello, b1.hello());
```

```text
false привіт, а
true привіт, а
```

Цей приклад також показує межу замикання. Слово `this` не береться із замикання: у звичайної функції його значення
визначається під час кожного виклику. Якщо функцію викликали як `b1.hello()`, то `this` дорівнює об'єкту перед
крапкою, тобто `b1`. Тому метод `hello` на прототипі працює для обох об'єктів. Стрілкова функція власного `this` не
має, тому бере його з оточення, у якому її створили.

**Навіщо в React.** Порада стосується методів, які можна зробити спільними. Обробник у компоненті мусить читати змінні
свого рендеру, тому створювати його в кожному рендері є звичайним кодом. Повторний рендер компонента часто називають
**перерендером**. Прийоми для уникнення зайвих перерендерів, зокрема `useCallback`, з'являться в плані пізніше.

## MDN: `let`

**Де читати:** [let на MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/let).

**Що там є:** точна довідка про оголошення `let`: де змінна видна, коли її можна читати, що заборонено.

**Якщо часу мало,** прочитайте `Description`, `Temporal dead zone (TDZ)` і `Scoping rules`.

Ця сторінка не пояснює нову змінну на кожен прохід циклу. Це пояснення лежить на іншій сторінці, і наприкінці цього
розділу є окремий підрозділ про неї.

### `Try it` і `Syntax`

`Try it` дає вікно з кодом, яке можна змінювати просто на сторінці. У вікні стоїть такий приклад:

```js
let x = 1;

if (x === 1) {
  let x = 2;

  console.log(x);
  // Expected output: 2
}

console.log(x);
// Expected output: 1
```

```text
2
1
```

Рядок `let x = 2` усередині `if` створює нову змінну `x`, яка існує лише в блоці `if`. Тому `console.log(x)` у блоці
друкує 2. Рядок `console.log(x)` після блока бачить зовнішню змінну `x` і друкує 1, бо рядок `let x = 2` зовнішньої
змінної не змінював.

`Syntax` показує всі форми запису:

```js
let name1;
let name1 = value1;
let name1 = value1, name2 = value2;
let name1, name2 = value2;
let name1 = value1, name2, /* …, */ nameN = valueN;
```

Ці рядки не призначені для запуску, вони лише показують форму запису. З них видно, що одним `let` можна оголосити
кілька змінних через кому, а значення можна не задавати. Розділ `Parameters` пояснює, що змінна без заданого значення
отримує `undefined`.

У `Parameters` слово **binding pattern** означає запис, який витягує кілька значень одразу. Ви бачите його щодня:
`const [qty, setQty] = useState(0)`. **Identifier** означає правильне ім'я змінної.

### `Description`

Цей розділ спершу перелічує місця, які обмежують змінну `let`: блок, `switch`, `try...catch`, тіло `for`, якщо `let` у
заголовку, тіло функції, статичний блок класу. **Блоком** тут називають будь-який код у фігурних дужках. **Статичний
блок класу** — це блок зі словом `static` усередині оголошення класу, код якого виконується під час створення самого
класу. Якщо нічого з цього немає, змінна належить модулю, коли код виконується як модуль, або всьому скрипту, коли код
виконується як звичайний скрипт.

Далі йдуть чотири відмінності від `var`:

| Відмінність | Що це дає |
|-------------|-----------|
| Діє в блоці, а не лише у функції | Змінна не виходить за фігурні дужки |
| Доступна лише після рядка оголошення | Спроба прочитати раніше дає помилку, а не тихе `undefined` |
| Не створює властивості в `globalThis` | Верхній рівень скрипта не засмічує глобальний об'єкт, тобто об'єкт, доступний з будь-якого місця |
| Не можна оголосити двічі в одній області | Помилка з'являється ще до запуску |

Наступне речення розрізняє два види записів. **Інструкцією** (statement) називають запис, який виконує дію, наприклад
`if`, цикл чи виклик функції. **Оголошенням** (declaration) називають запис, який створює нове ім'я, наприклад `let`,
`const`, `function` чи `class`. Граматика мови дозволяє ставити в тіло `if` без фігурних дужок лише інструкцію.
Сторінка каже, що `let` починає оголошення, а не інструкцію, тому `let` не може стояти сам як тіло `if`. MDN додає, що
такий запис і не мав би сенсу, бо прочитати цю змінну ніде не вдалося б:

```js
if (true) let a = 1;
```

Цей файл Node не запускає й пише: `SyntaxError: Lexical declaration cannot appear in a single-statement context`.

Сторінка також каже, що багато посібників радять брати `const`, якщо змінну не присвоюють заново. У коді React так і
роблять: `const [qty, setQty]` створює нову змінну на кожен рендер, і запису в неї ніхто не робить. Тому змінна стану
не може змінитися, і функції цього рендеру завжди бачать те саме значення.

### `Temporal dead zone (TDZ)`

**Тимчасова мертва зона** — це час від початку блока до рядка, де змінну оголошено. Змінна вже існує в оточенні, але
не має значення, і читання кидає `ReferenceError`. Змінна `var` у цей час мала б значення `undefined`:

```js
console.log(early);
var early = 1;
console.log(early);
try {
  console.log(late);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
let late = 2;
```

```text
undefined
1
ReferenceError: Cannot access 'late' before initialization
```

Слово **temporal** означає «часова»: зона залежить від порядку виконання, а не від порядку рядків у файлі. Ця різниця
важлива для замикань. Функцію, яка читає змінну, можна створити вище за оголошення, якщо викликати її нижче:

```js
function setup() {
  const report = () => "ліміт " + limit;
  try {
    console.log(report());
  } catch (error) {
    console.log(error.name + ": " + error.message);
  }
  const limit = 5;
  console.log(report());
}
setup();
```

```text
ReferenceError: Cannot access 'limit' before initialization
ліміт 5
```

Також `typeof` тут поводиться інакше, ніж зазвичай. Для неоголошеного імені він повертає `undefined`, а для змінної в
мертвій зоні кидає помилку:

```js
console.log(typeof neverDeclared);
try {
  console.log(typeof soon);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
let soon = 1;
```

```text
undefined
ReferenceError: Cannot access 'soon' before initialization
```

**Навіщо в React.** Обробник, оголошений через `const` вище за змінну, яку він читає, працює, бо спрацює пізніше.
Натомість виклик такої функції під час рендеру, до оголошення змінної, дасть цю помилку.

### `Redeclarations`

Два `let` з одним ім'ям в одній області заборонені, як і `let` з ім'ям параметра:

```js
function f(a) {
  let a = 1;
}
```

Node не запускає цей файл і пише: `SyntaxError: Identifier 'a' has already been declared`. Розділ попереджає про дві
ситуації:

- **Консоль.** Команди, введені окремо в консолі браузера, працюють із тією самою областю, тому Firefox може видати цю
  помилку, а Chrome дозволяє оголосити ім'я знову.
- **`switch`.** Усі варіанти `case` лежать в одному блоці, тому два `let` з одним ім'ям у різних `case` конфліктують.
  Виправлення таке: загорнути кожен `case` у власні фігурні дужки.

```js
const kind = 1;
switch (kind) {
  case 0: {
    let label = "нуль";
    console.log(label);
    break;
  }
  case 1: {
    let label = "один";
    console.log(label);
    break;
  }
}
```

```text
один
```

### `Scoping rules`

Перший приклад розділу порівнює `var` і `let` у вкладеному блоці:

```js
function varTest() {
  var x = 1;
  {
    var x = 2; // same variable!
    console.log(x); // 2
  }
  console.log(x); // 2
}

function letTest() {
  let x = 1;
  {
    let x = 2; // different variable
    console.log(x); // 2
  }
  console.log(x); // 1
}
```

Сторінка лише оголошує ці дві функції й не викликає їх. Ми дописали в кінець рядки `varTest();` і `letTest();` і
запустили файл у Node 24:

```text
2
2
2
1
```

Перші два рядки надрукувала `varTest`. Рядок `var x = 2` у блоці не створює нової змінної, а змінює ту саму змінну `x`
усієї функції, тому й після блока `x` дорівнює 2. Останні два рядки надрукувала `letTest`. Рядок `let x = 2` створює
нову змінну, яка існує лише в блоці, тому після блока видно зовнішню `x`, що дорівнює 1. Ось та сама різниця на
власному прикладі:

```js
let level = "зовнішній";
{
  let level = "внутрішній";
  console.log(level);
}
console.log(level);
var total = 1;
{
  var total = 2;
}
console.log(total);
```

```text
внутрішній
зовнішній
2
```

Другий приклад розділу показує, що `let` на верхньому рівні програми не створює властивості глобального об'єкта:

```js
var x = "global";
let y = "global";
console.log(this.x); // "global"
console.log(this.y); // undefined
```

Вивід із коментарів, `"global"` і `undefined`, сторінка обіцяє для звичайного скрипта браузера. На верхньому рівні
такого скрипта `this` дорівнює глобальному об'єкту. Рядок `var x` створює в глобальному об'єкті властивість `x`, а
рядок `let y` такої властивості не створює. Тому цей приклад треба запускати у звичайному скрипті браузера. У файлі
Node результат інший, бо Node загортає такий файл у функцію, і `var` на верхньому рівні файла не створює глобальної
властивості. Ми запустили цей фрагмент у Node 24, і обидва рядки надрукували `undefined`. Власний приклад нижче
перевіряє те саме ще й через `globalThis`:

```js
var viaVar = "var";
let viaLet = "let";
console.log(this.viaVar, this.viaLet, globalThis.viaVar, globalThis.viaLet);
```

```text
undefined undefined undefined undefined
```

### `TDZ combined with lexical scoping`

Цей розділ показує наслідок затінення. Як пояснювала лекція, затінення трапляється тоді, коли внутрішнє оголошення має
те саме ім'я, що й зовнішня змінна, і пошук імені знаходить внутрішню змінну першою. Перший приклад розділу такий:

```js
function test() {
  var foo = 33;
  if (foo) {
    let foo = foo + 55; // ReferenceError
  }
}
test();
```

Node зупиняє цю програму з помилкою `ReferenceError: Cannot access 'foo' before initialization` у рядку з `let`. Блок
`if` виконується, бо зовнішня змінна `foo` дорівнює 33. Рядок `let foo = foo + 55` усередині блока здається читанням
зовнішнього `foo`. Проте оточення блока вже містить нове ім'я `foo`, і пошук зупиняється на ньому, а воно ще в мертвій
зоні. Ось той самий випадок на власному прикладі, де помилку перехоплено:

```js
function test() {
  const price = 10;
  if (price) {
    try {
      let price = price + 5;
      console.log(price);
    } catch (error) {
      console.log(error.name + ": " + error.message);
    }
  }
}
test();
```

```text
ReferenceError: Cannot access 'price' before initialization
```

Другий приклад розділу падає з тієї самої причини:

```js
function go(n) {
  // n here is defined!
  console.log(n); // { a: [1, 2, 3] }

  for (let n of n.a) {
    //          ^ ReferenceError
    console.log(n);
  }
}

go({ a: [1, 2, 3] });
```

Node спершу друкує `{ a: [ 1, 2, 3 ] }`, а потім зупиняє програму з помилкою `ReferenceError: Cannot access 'n'
before initialization` у заголовку циклу. Перший `console.log(n)` бачить параметр `n` функції `go`, тобто переданий
об'єкт. Цикл `for...of` мав би по черзі класти в нову змінну `n` кожен елемент масиву `n.a`. Але заголовок циклу вже
належить новій області, де `let n` оголошує нову змінну `n`. Тому запис `n.a` у тому самому заголовку читає нову `n`,
а ця змінна ще не має значення.

### `Other situations` і `Declaration with destructuring`

`Other situations` показує, що `var` у блоці належить зовнішній області, а `let` у блоці належить блоку:

```js
var a = 1;
var b = 2;

{
  var a = 11; // the scope is global
  let b = 22; // the scope is inside the block

  console.log(a); // 11
  console.log(b); // 22
}

console.log(a); // 11
console.log(b); // 2
```

```text
11
22
11
2
```

Рядок `var a = 11` у блоці змінює ту саму змінну `a`, що й перший рядок, тому після блока `a` дорівнює 11. Рядок
`let b = 22` створює нову змінну `b` лише для блока, тому після блока видно зовнішню `b`, що дорівнює 2.

Звідси випливає другий фрагмент розділу:

```js
let x = 1;

{
  var x = 2; // SyntaxError for re-declaration
}
```

Node цей файл не запускає й пише: `SyntaxError: Identifier 'x' has already been declared`. Рядок `var x` у блоці
належить не блоку, а зовнішній області. Тому `let x` зовні і `var x` у блоці потрапляють в одну область і
конфліктують.

`Declaration with destructuring` показує **деструктуризацію**, тобто витягання кількох значень одним записом. Приклад
сторінки такий:

```js
const result = /(a+)(b+)(c+)/.exec("aaabcc");
let [, a, b, c] = result;
console.log(a, b, c); // "aaa" "b" "cc"
```

```text
aaa b cc
```

Регулярний вираз `/(a+)(b+)(c+)/` шукає в рядку одну чи більше літер `a`, за ними одну чи більше літер `b` і за ними
одну чи більше літер `c`. Кожна пара круглих дужок у ньому утворює **групу захоплення**, тобто частину шаблону, збіг
якої запам'ятовується окремо. Метод `exec` повертає масив, у якому першим елементом стоїть увесь знайдений текст
`aaabcc`, а за ним стоїть по елементу на кожну групу, тобто `aaa`, `b` і `cc`. Запис `let [, a, b, c]` починається з
коми, тому перший елемент масиву пропускається, а наступні три елементи потрапляють у змінні `a`, `b` і `c`.

Нові змінні не пов'язані з масивом, із якого їх узяли:

```js
const pair = ["Київ", 3];
let [town, days] = pair;
days = days + 1;
console.log(town, days, pair[1]);
```

```text
Київ 4 3
```

Кінець сторінки містить таблицю підтримки браузерами й посилання. Для цього дня вони не потрібні.

**Навіщо в React.** Рядок `const [qty, setQty] = useState(0)` є саме такою деструктуризацією: він витягує зі значення,
яке повернула функція, дві нові змінні цього рендеру.

### Чого немає на цій сторінці: цикл `for`

Нова змінна на кожен прохід описана на сторінці
[`for`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/for), у розділі `Lexical
declarations in the initialization block`. Там сказано, що після кожного проходу цикл створює нову область, копіює
туди значення й лише потім виконує **afterthought**, тобто третю частину заголовка, наприклад `i++`.

Розділ показує й незвичний наслідок. Функція, створена в самому заголовку, тримає початкову змінну, яка не належить
жодному проходу. На сторінці це показано таким кодом:

```js
for (let i = 0, getI = () => i; i < 3; i++) {
  console.log(getI());
}
```

```text
0
0
0
```

Функцію `getI` створено один раз, у заголовку циклу, і вона тримає змінну `i`, яку цикл завів ще до першого проходу.
Кожен прохід отримує нову змінну `i`, і запис `i++` збільшує вже цю нову змінну. Початкової змінної, яку тримає
`getI`, ніхто не змінює, тому `getI()` щоразу повертає 0. Власний приклад нижче друкує поруч і `getI()`, і змінну
проходу:

```js
for (let i = 0, getI = () => i; i < 2; i++) {
  console.log("функція із заголовка:", getI(), "змінна проходу:", i);
}
```

```text
функція із заголовка: 0 змінна проходу: 0
функція із заголовка: 0 змінна проходу: 1
```

## Як читати специфікації, на які посилається теорія дня

Цей розділ необов'язковий. Теорія дня посилається на ECMA-262 і стандарт HTML, тому варто знати, що там написано.
**ECMA-262** — це специфікація мови JavaScript, а **стандарт HTML** описує, зокрема, таймери браузера. Обидва описують
поведінку як покрокові алгоритми. Вони не показують коду рушія й не є посібниками. Рушій може бути влаштований як
завгодно, якщо результат збігається.

Номери розділів змінюються між версіями. Посилання нижче ведуть на чернетку ECMA-262 станом на листопад 2026 року,
тому шукайте розділи за назвою, а не за номером.

| Запис в алгоритмі | Що означає |
|-------------------|------------|
| abstract operation | внутрішня процедура зі специфікації, яку не можна викликати з коду |
| `[[Environment]]` | внутрішнє поле об'єкта, яке недоступне з коду |
| `Let x be ...` | завести змінну самого алгоритму |
| `Set x to ...` | записати значення |
| `?` перед викликом | якщо виклик дав помилку, зупинитися й передати її далі |
| `!` перед викликом | цей виклик ніколи не дає помилки |
| Note | пояснення для читача, а не частина правил |

### ECMA-262: `Environment Records` (9.1)

[Цей розділ](https://tc39.es/ecma262/#sec-environment-records) визначає те, що лекція називає оточенням. Новий запис
з'являється щоразу, коли виконується код функції чи блока. Кожен запис має поле `[[OuterEnv]]`, яке посилається на
зовнішній запис або дорівнює `null`. Наприкінці розділ каже, що ці записи існують лише в описі мови, і програма не
може дістатися до них напряму.

Записи бувають різних видів. [`Declarative Environment
Records`](https://tc39.es/ecma262/#sec-declarative-environment-records) зберігають імена з оголошень. [`Function
Environment Records`](https://tc39.es/ecma262/#sec-function-environment-records) є їхнім різновидом для верхнього
рівня функції й додатково описують `this`. Для стрілкової функції специфікація робить виняток: її запис оточення не
описує `this`, бо стрілкова функція власного `this` не має й бере його із зовнішнього оточення.

### ECMA-262: `OrdinaryFunctionCreate` (10.2.3)

[Ця операція](https://tc39.es/ecma262/#sec-ordinaryfunctioncreate) створює об'єкт функції. Майже всі її кроки
записують у поля об'єкта різні дані: текст функції, параметри, режим роботи `this`. Для нас важливий один рядок: `Set
func.[[Environment]] to envRecord`. Значення `envRecord` цій операції передає інша операція, яка її викликає. Для
стрілкової функції це робить
[`InstantiateArrowFunctionExpression`](https://tc39.es/ecma262/#sec-runtime-semantics-instantiatearrowfunctionexpression).
Вона виконує рядок `Let envRecord be the LexicalEnvironment of the running execution context`. Щоб зрозуміти цей
рядок, потрібне ще одне поняття. **Контекст виконання** (execution context) — це запис, яким специфікація стежить за
кодом, що виконується. Контекст того коду, який виконується саме зараз, специфікація називає **running execution
context**, а його поле `LexicalEnvironment` містить оточення цього коду. Отже, стрілкова функція отримує оточення того
місця, де рушій саме виконує її запис. Звідси висновок: запам'ятовування оточення і є дією при створенні функції.

### ECMA-262: `NewFunctionEnvironment` (9.1.2.4)

[Ця операція](https://tc39.es/ecma262/#sec-newfunctionenvironment) працює при кожному виклику. Вона створює порожній
запис і виконує рядок `Set envRecord.[[OuterEnv]] to func.[[Environment]]`. У цьому рядку немає жодної згадки про
того, хто викликав функцію, і саме тому пошук іде від місця створення.

### ECMA-262: `GetIdentifierReference` (9.1.2.1)

[Ця операція](https://tc39.es/ecma262/#sec-getidentifierreference) шукає ім'я. Своїми словами її можна записати так:

| Крок | Що робить алгоритм |
|------|--------------------|
| Запису немає, отримано `null` | повертає результат «ім'я не знайдено» |
| Запис має таке ім'я | повертає посилання на цю змінну в цьому записі |
| Запис не має такого імені | викликає сам себе із зовнішнім записом `[[OuterEnv]]` |

Цей алгоритм повертає посилання на змінну, а значення читає окремий крок. Тому читання змінної завжди дає те, що
лежить у ній у цю мить.

### ECMA-262: `ForBodyEvaluation` (14.7.4.3) і `CreatePerIterationEnvironment` (14.7.4.4)

[Перша операція](https://tc39.es/ecma262/#sec-forbodyevaluation) описує порядок дій циклу: створити оточення проходу,
перевірити умову, виконати тіло, створити нове оточення проходу, виконати третю частину заголовка, повторити. [Друга
операція](https://tc39.es/ecma262/#sec-createperiterationenvironment) створює нове оточення, заводить у ньому ті самі
імена й копіює значення з попереднього проходу. Якщо цикл не має `let` у заголовку, список імен порожній, і нічого не
створюється. Так специфікація пояснює різницю між `let` і `var`.

### Стандарт HTML: `Timers` (8.7)

[Цей розділ](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers) описує `setTimeout` як
алгоритм. Основні кроки такі:

1. Від'ємна затримка стає нулем.
2. Вкладеним називають таймер, який поставила функція іншого таймера. Якщо таймери вкладені понад п'ять разів, а
   затримка менша за 4 мілісекунди, вона стає 4 мілісекундами.
3. Алгоритм готує задачу, яка викличе вашу функцію з переданими аргументами.
4. Алгоритм запускає очікування паралельно, тобто окремо від вашого коду, і ваш код тим часом виконується далі. Сам
   `setTimeout` одразу повертає номер таймера. Цей номер можна передати в `clearTimeout`, щоб скасувати таймер.
5. Коли час минув, задача потрапляє в чергу задач.

Браузер має право чекати довше, наприклад щоб заощадити заряд батареї, тому затримка є нижньою межею, а не точним
часом. Node має власну реалізацію, описану в [документації таймерів](https://nodejs.org/api/timers.html): затримку,
меншу за 1, він замінює на 1 і не обіцяє точного часу спрацювання.

<details><summary>Відповідь</summary>

Коли функцію викликають там само, де створили, вона й без пояснень здається такою, що просто бачить сусідні змінні.
Повернена функція переживає свій виклик, і саме тоді стає помітно, що вона тримає оточення.

</details>

**2. Чому в прикладі MDN з `onfocus` підказка завжди про вік?**

<details><summary>Відповідь</summary>

Усі три функції тримають спільне оточення з однією змінною `item`, бо вона оголошена через `var`. Функції спрацьовують
після завершення циклу, коли `item` вказує на останній елемент списку.

</details>

**3. Назвіть два виправлення цієї помилки, які не потребують `let` чи `const`. Що в них спільного?**

<details><summary>Відповідь</summary>

Фабрика функцій і IIFE в тілі циклу. Обидві викликають функцію на кожному проході, а кожен виклик створює нове
оточення з власною змінною.

</details>

**4. Що повертає `typeof` для неоголошеного імені і для змінної `let` до рядка її оголошення?**

<details><summary>Відповідь</summary>

Для неоголошеного імені він повертає рядок `undefined`. Для змінної в тимчасовій мертвій зоні він кидає
`ReferenceError`.

</details>

**5. Чому рядок `let price = price + 5` у блоці кидає помилку, хоча зовні є змінна `price`?**

<details><summary>Відповідь</summary>

Оточення блока вже містить ім'я `price`, і пошук зупиняється на ньому. Ця змінна ще не отримала значення, бо рядок
оголошення ще не завершився, тому читання кидає `ReferenceError`.

</details>

**6. Який рядок специфікації пояснює, що функція шукає змінні за місцем створення, а не за місцем виклику?**

<details><summary>Відповідь</summary>

Рядок `Set envRecord.[[OuterEnv]] to func.[[Environment]]` в операції `NewFunctionEnvironment`. Зовнішнім для нового
оточення виклику стає оточення, записане у функцію при створенні, а про місце виклику рядок нічого не каже.

</details>
