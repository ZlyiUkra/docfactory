# Розбір читання. День 3. Функції та замикання

Лекція пояснює саму тему, а цей файл допомагає прочитати задані сторінки: показує, де що шукати, що означають
незнайомі слова й навіщо кожна думка потрібна в React. Обидві сторінки написані англійською, і розбір їх не
перекладає, а переказує своїми словами. Назви розділів наведено мовою оригіналу, щоб ви легко їх знайшли.

Читайте в такому порядку: лекцію, потім `Closures` (близько 30 хвилин), потім `let` (близько 20 хвилин). Окремий
розділ наприкінці пояснює, як читати специфікації, на які посилається теорія дня. Він необов'язковий.

**Перед читанням зробіть завдання або хоча б спробуйте.** Сторінка `Closures` містить власну версію лічильника, а
сторінка `for`, на яку ми посилаємось нижче, містить цикл із таймерами. Вони не збігаються із завданнями дня дослівно,
але якщо прочитати їх першими, завдання вже не перевірить вашого розуміння.

### Вступний абзац

Сторінка починається з означення: замикання є поєднанням функції й посилань на стан навколо неї. Цей стан MDN називає
**lexical environment** (лексичне оточення), а лекція називає оточенням. Друга важлива думка стоїть у кінці абзацу:
замикання створюється щоразу, коли створюється функція, і саме в цю мить. Отже, замикання не є рідкісним прийомом, а
властивістю кожної функції.

| Вираз | Що означає |
|-------|------------|
| bundled together, enclosed | функція й оточення існують разом, звідси й назва «замикання» |
| outer scope | область видимості навколо функції |

### `Lexical scoping`

Функція `displayName` лежить усередині функції `init`, не має власних змінних і все одно друкує змінну `name` з
`init`. MDN використовує цей приклад, щоб показати просте правило: вкладена функція бачить змінні зовнішньої. Потім
він пояснює слово **lexical**: місце, де змінну оголошено в тексті програми, визначає, де вона доступна.

Слово **parser** у цьому розділі означає частину рушія, яка читає текст програми й розбирає його будову. **Рушій** —
це програма, яка виконує JavaScript.

**Навіщо в React.** Компонент часто містить обробники, оголошені всередині нього. Обробник бачить пропси та стан
компонента, бо він вкладений у функцію компонента. Це те саме правило.

### `Scoping with let and const`

Раніше JavaScript мав лише дві області видимості для змінних: функцію й увесь скрипт. Ключове слово `var` не зважає на
фігурні дужки блока, тому змінна, оголошена в `if`, видна й після нього. Людина, яка прийшла з мови C чи Java, чекала
б там помилки. Розділ показує це через `Math.random()`, а ось та сама думка без випадковості:

```js
function withVar() {
  if (true) {
    var size = "великий";
  }
  return size;
}
console.log(withVar());

function withLet() {
  if (true) {
    let size = "великий";
  }
  return typeof size;
}
console.log(withLet());
```

```text
великий
undefined
```

MDN пише, що `var` у його прикладі створює глобальну змінну. Це правда лише для його випадку, коли код стоїть на
верхньому рівні звичайного скрипта. У функції `var` створює змінну цієї функції, як у `withVar` вище.

Розділ згадує **temporal dead zones**. Їх розібрано нижче, у сторінці `let`. Згадано й **ES6**: так називають версію
мови 2015 року, у якій з'явилися `let`, `const` і модулі.

**Навіщо в React.** Сучасний код на React не використовує `var`. Проте старі приклади й чужий код його містять, тому
варто знати, чому змінна виходить за межі блока.

### `Closure`

Це головний розділ сторінки. Він бере попередній приклад і змінює одне: `makeFunc` не викликає внутрішню функцію, а
повертає її. Функцію викликають уже після завершення `makeFunc`, і вона все одно друкує `name`. MDN пояснює це так:
екземпляр внутрішньої функції тримає посилання на своє оточення, а в оточенні лежить змінна.

Слово **instance** (екземпляр) тут важливе. Текст функції один, але кожне виконання коду, який її створює, дає новий
об'єкт:

```js
function makeHandler() {
  return () => {};
}
console.log(makeHandler() === makeHandler());
```

```text
false
```

Другий приклад розділу — `makeAdder`, де `add5` і `add10` мають спільний текст функції й різні оточення. MDN називає
`makeAdder` фабрикою функцій (**function factory**). Лекція показує той самий механізм на прикладі податків, з кожним
кроком у таблиці.

**Навіщо в React.** Кожен рендер створює нові екземпляри обробників. Вони виглядають однаково, але це інші об'єкти, і
кожен тримає змінні свого рендеру.

### `Practical closures`

Замикання дає змогу зв'язати дані з функцією, яка з ними працює. Об'єкт робить те саме, тому замикання можна
використати всюди, де ви створили б об'єкт із одним методом.

Приклад розділу змінює розмір тексту на сторінці. Функція `makeSizer` приймає число пікселів і повертає функцію, яка
записує це число в стиль `body`. Три виклики дають три функції, і кожну присвоєно властивості `onclick` окремої
кнопки. **`onclick`** — це властивість елемента, у яку кладуть функцію, що спрацює при натисканні. Код потребує
сторінки, тому не запускається в Node. На самій сторінці MDN є робочий приклад: натисніть кнопки, і текст змінить
розмір.

Вираз **event-based** означає, що код не йде від початку до кінця, а реагує на події, наприклад на натискання.

**Навіщо в React.** Запис `onClick={() => setSize(12)}` робить те саме, що й `makeSizer`: створює функцію, яка спрацює
пізніше й тримає потрібні дані.

### `Emulating private methods with closures`

Деякі мови мають позначку `private`, яка забороняє викликати метод зовні. До появи класів у JavaScript такого не було,
але те саме давали замикання. Приклад створює об'єкт `counter` із трьома функціями навколо приватної змінної та
приватної функції.

Тут є незнайомий запис. **IIFE** (immediately invoked function expression) — це функція, яку викликають одразу після
створення: `(function () { ... })()`. Вона потрібна, щоб отримати власне оточення один раз. Зовнішні дужки потрібні
для того, щоб рушій прочитав запис як вираз, а не як оголошення функції.

Запам'ятайте різницю між двома прикладами розділу. У першому три функції мають спільне оточення, бо створені в одному
виклику. У другому прикладі `makeCounter` викликано двічі, тому два лічильники незалежні. Лекція показує цю ж різницю
на гаманці.

| Вираз | Що означає |
|-------|------------|
| Module Design Pattern | прийом, коли функція приховує змінні й віддає назовні лише кілька функцій |
| global namespace | спільний простір імен усього скрипта, який легко засмітити |
| data hiding, encapsulation | приховання даних, до яких код зовні може дістатися лише через дозволені функції |

**Навіщо в React.** Власні хуки працюють схожим способом: функція приховує деталі, а назовні віддає значення й функції
для роботи з ними. **Хук** — це функція React з префіксом `use`. Їх ви вивчатимете у фазі 1.

### `Closure scope chain`

Функція бачить не лише зовнішню функцію, а й усе, що навколо неї, аж до верхнього рівня. MDN показує це ланцюгом
`sum(1)(2)(3)(4)`. Запис із кількома дужками означає: виклич функцію, виклич те, що вона повернула, і так далі. Ось
такий самий ланцюг на прикладі ціни:

```js
const delivery = 50;
function total(price) {
  return function (qty) {
    return function (discount) {
      return price * qty - discount + delivery;
    };
  };
}
console.log(total(100)(2)(30));
const forTea = total(100);
const twoTeas = forTea(2);
console.log(twoTeas(0), twoTeas(30));
```

```text
220
250 220
```

Найвнутрішня функція читає `discount` зі свого оточення, `qty` і `price` із зовнішніх, а `delivery` з верхнього рівня
файла. Перший виклик дає 100 × 2 − 30 + 50 = 220. Проміжні результати `forTea` і `twoTeas` можна зберегти й
використати кілька разів, бо кожен із них пам'ятає свої змінні.

Далі розділ показує, що замикання тримає й змінну блока:

```js
function outer() {
  let getCode;
  {
    const code = 42;
    getCode = () => code;
  }
  console.log(typeof code);
  console.log(getCode());
}
outer();
```

```text
undefined
42
```

Наприкінці йдеться про **модулі**, тобто файли зі своєю областю видимості, з яких код явно експортують через `export`.
Модуль сам створює оточення, і функції модуля можуть його тримати. Ось два файли, запущені на Node як `.mjs`:

```js
// settings.mjs
let theme = "світла";
export const getTheme = () => theme;
export const setTheme = (next) => {
  theme = next;
};
export let language = "uk";
export const setLanguage = (next) => {
  language = next;
};
```

```js
// use.mjs
import { getTheme, setTheme, language, setLanguage } from "./settings.mjs";

console.log(getTheme());
setTheme("темна");
console.log(getTheme());

const readLanguage = () => language;
console.log(readLanguage());
setLanguage("en");
console.log(readLanguage());
```

```text
світла
темна
uk
en
```

Змінна `theme` не експортована, тому прочитати її можна лише через дві функції. Імпорт `language` не копіює значення:
MDN називає імпортоване ім'я **live binding**, тобто «живою прив'язкою» до змінної в іншому модулі. Тому
`readLanguage` бачить нове значення.

Модулі докладно розбирає день 4 цієї фази.

**Навіщо в React.** Обробник у компоненті читає одразу кілька рівнів: власні змінні, пропси й стан компонента, імпорти
модуля. Весь цей ланцюг працює за описаним тут правилом.

### `Creating closures in loops: A common mistake`

Це розділ про помилку, яка стоїть за завданням із циклом. Сторінка має три поля вводу. Цикл із `var` призначає кожному
полю функцію `onfocus`, яка показує підказку. Властивість **`onfocus`** містить функцію, що спрацьовує, коли поле
отримує фокус, тобто коли курсор ставлять у поле. У робочому прикладі на сторінці MDN ви побачите: хоч яке поле
вибрати, підказка завжди про вік.

Причина така. Три функції мають спільне оточення, бо `var item` оголошена один раз на всю функцію `setupHelp`. Коли
користувач ставить курсор у поле, цикл уже завершився, і `item` вказує на останній елемент. MDN пояснює це через
**hoisting**. Цим словом називають те, що оголошення `var` діє у всій функції, навіть якщо рядок оголошення стоїть
нижче або всередині циклу.

MDN дає кілька виправлень, і всі вони створюють окрему змінну для кожного проходу:

| Спосіб | Що він робить |
|--------|---------------|
| Фабрика `makeHelpCallback` | кожен виклик створює нове оточення з власним параметром |
| IIFE в тілі циклу | кожен прохід викликає функцію й отримує нове оточення |
| `let` або `const` | блок циклу отримує нову змінну на кожному проході |
| `for...of` або `forEach` | кожен прохід має власну змінну, а для `forEach` це власний параметр функції |

Перевіримо всі ідеї на прикладі без сторінки:

```js
const items = ["чай", "кава"];
const viaFactory = [];
function makeLabel(text) {
  return () => "товар: " + text;
}
for (var i = 0; i < items.length; i++) {
  viaFactory.push(makeLabel(items[i]));
}
console.log(viaFactory[0](), viaFactory[1]());

const viaIife = [];
for (var j = 0; j < items.length; j++) {
  (function () {
    var text = items[j];
    viaIife.push(() => "товар: " + text);
  })();
}
console.log(viaIife[0](), viaIife[1]());

const viaForEach = [];
items.forEach((text) => {
  viaForEach.push(() => "товар: " + text);
});
console.log(viaForEach[0](), viaForEach[1]());
```

```text
товар: чай товар: кава
товар: чай товар: кава
товар: чай товар: кава
```

Зверніть увагу, що виклик IIFE читає `items[j]` одразу, під час проходу. Тому `var text` усередині неї отримує
правильний елемент, хоча `j` одна на всі проходи.

**Навіщо в React.** Списки в React зазвичай будують через `map`, а функція в `map` має власний параметр на кожен
елемент. Тому `items.map((item) => <button onClick={() => pick(item)} />)` не має цієї помилки.

### `Performance considerations`

Кожен екземпляр функції займає пам'ять, тому не варто створювати функції всередині функцій без потреби. MDN показує це
на **конструкторі**, тобто функції, яку викликають через `new`, щоб отримати новий об'єкт. Якщо метод створюється в
конструкторі, кожен об'єкт отримає власну копію методу. Якщо метод покласти в **прототип**, тобто об'єкт, спільний для
всіх об'єктів цього конструктора, копія буде одна:

```js
function PerObject(name) {
  this.name = name;
  this.hello = function () {
    return "привіт, " + this.name;
  };
}
function Shared(name) {
  this.name = name;
}
Shared.prototype.hello = function () {
  return "привіт, " + this.name;
};

const a1 = new PerObject("а");
const a2 = new PerObject("б");
const b1 = new Shared("а");
const b2 = new Shared("б");
console.log(a1.hello === a2.hello, a1.hello());
console.log(b1.hello === b2.hello, b1.hello());
```

```text
false привіт, а
true привіт, а
```

Цей приклад також показує межу замикання. Слово `this` не береться із замикання: у звичайної функції його значення
визначається під час кожного виклику. Тому метод `hello` на прототипі працює для обох об'єктів. Стрілка власного
`this` не має й шукає його назовні.

**Навіщо в React.** Порада стосується методів, які можна зробити спільними. Обробник у компоненті мусить читати змінні
свого рендеру, тому створювати його в кожному рендері є звичайним кодом. Прийоми для уникнення зайвих перерендерів,
зокрема `useCallback`, з'являться в плані пізніше.

## MDN: `let`

**Де читати:** [let на MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/let).

**Що там є:** точна довідка про оголошення `let`: де змінна видна, коли її можна читати, що заборонено.

**Якщо часу мало,** прочитайте `Description`, `Temporal dead zone (TDZ)` і `Scoping rules`.

Ця сторінка не пояснює нову змінну на кожен прохід циклу. Це пояснення лежить на іншій сторінці, і наприкінці цього
розділу є окремий підрозділ про неї.

### `Try it` і `Syntax`

`Try it` дає вікно з кодом, яке можна змінювати просто на сторінці. У прикладі змінна `x` усередині `if` є іншою
змінною, ніж `x` зовні. `Syntax` показує, що одним `let` можна оголосити кілька змінних через кому, а значення можна
не задавати: тоді в змінній буде `undefined`.

У `Parameters` слово **binding pattern** означає запис, який витягує кілька значень одразу. Ви бачите його щодня:
`const [qty, setQty] = useState(0)`. **Identifier** означає правильне ім'я змінної.

### `Description`

Цей розділ спершу перелічує місця, які обмежують змінну `let`: блок, `switch`, `try...catch`, тіло `for`, якщо `let` у
заголовку, тіло функції, статичний блок класу. Якщо нічого з цього немає, змінна належить модулю або всьому скрипту.

Далі йдуть чотири відмінності від `var`:

| Відмінність | Що це дає |
|-------------|-----------|
| Діє в блоці, а не лише у функції | Змінна не виходить за фігурні дужки |
| Доступна лише після рядка оголошення | Спроба прочитати раніше дає помилку, а не тихе `undefined` |
| Не створює властивості в `globalThis` | Верхній рівень скрипта не засмічує глобальний об'єкт, тобто об'єкт, доступний з будь-якого місця |
| Не можна оголосити двічі в одній області | Помилка з'являється ще до запуску |

Наступне речення каже, що `let` починає оголошення, а не інструкцію, тому не може стояти сам як тіло `if`:

```js
if (true) let a = 1;
```

Цей файл Node не запускає й пише: `SyntaxError: Lexical declaration cannot appear in a single-statement context`.

Сторінка також каже, що багато посібників радять брати `const`, якщо змінну не присвоюють заново. У коді React так і
роблять: `const [qty, setQty]` створює нову змінну на кожен рендер, і запису в неї ніхто не робить. Тому змінна стану
не може змінитися, і функції цього рендеру завжди бачать те саме значення.

### `Temporal dead zone (TDZ)`

**Тимчасова мертва зона** — це час від початку блока до рядка, де змінну оголошено. Змінна вже існує в оточенні, але
не має значення, і читання кидає `ReferenceError`. Змінна `var` у цей час мала б значення `undefined`:

```js
console.log(early);
var early = 1;
console.log(early);
try {
  console.log(late);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
let late = 2;
```

```text
undefined
1
ReferenceError: Cannot access 'late' before initialization
```

Слово **temporal** означає «часова»: зона залежить від порядку виконання, а не від порядку рядків у файлі. Ця різниця
важлива для замикань. Функцію, яка читає змінну, можна створити вище за оголошення, якщо викликати її нижче:

```js
function setup() {
  const report = () => "ліміт " + limit;
  try {
    console.log(report());
  } catch (error) {
    console.log(error.name + ": " + error.message);
  }
  const limit = 5;
  console.log(report());
}
setup();
```

```text
ReferenceError: Cannot access 'limit' before initialization
ліміт 5
```

Також `typeof` тут поводиться інакше, ніж зазвичай. Для неоголошеного імені він повертає `undefined`, а для змінної в
мертвій зоні кидає помилку:

```js
console.log(typeof neverDeclared);
try {
  console.log(typeof soon);
} catch (error) {
  console.log(error.name + ": " + error.message);
}
let soon = 1;
```

```text
undefined
ReferenceError: Cannot access 'soon' before initialization
```

**Навіщо в React.** Обробник, оголошений через `const` вище за змінну, яку він читає, працює, бо спрацює пізніше.
Натомість виклик такої функції під час рендеру, до оголошення змінної, дасть цю помилку.

### `Redeclarations`

Два `let` з одним ім'ям в одній області заборонені, як і `let` з ім'ям параметра:

```js
function f(a) {
  let a = 1;
}
```

Node не запускає цей файл і пише: `SyntaxError: Identifier 'a' has already been declared`. Розділ попереджає про дві
ситуації:

- **Консоль.** Команди, введені окремо в консолі браузера, працюють із тією самою областю, тому Firefox може видати цю
  помилку, а Chrome дозволяє оголосити ім'я знову.
- **`switch`.** Усі варіанти `case` лежать в одному блоці, тому два `let` з одним ім'ям у різних `case` конфліктують.
  Виправлення таке: загорнути кожен `case` у власні фігурні дужки.

```js
const kind = 1;
switch (kind) {
  case 0: {
    let label = "нуль";
    console.log(label);
    break;
  }
  case 1: {
    let label = "один";
    console.log(label);
    break;
  }
}
```

```text
один
```

### `Scoping rules`

Цей приклад порівнює `var` і `let` у вкладеному блоці. Рядок `var x = 2` змінює ту саму змінну, а `let x = 2` створює
нову:

```js
let level = "зовнішній";
{
  let level = "внутрішній";
  console.log(level);
}
console.log(level);
var total = 1;
{
  var total = 2;
}
console.log(total);
```

```text
внутрішній
зовнішній
2
```

Другий приклад розділу, з `this.x`, треба запускати у звичайному скрипті браузера. У файлі Node результат інший, бо
Node загортає такий файл у функцію, і `var` на верхньому рівні файла не створює глобальної властивості:

```js
var viaVar = "var";
let viaLet = "let";
console.log(this.viaVar, this.viaLet, globalThis.viaVar, globalThis.viaLet);
```

```text
undefined undefined undefined undefined
```

### `TDZ combined with lexical scoping`

Цей розділ показує наслідок затінення. Рядок `let foo = foo + 55` усередині блока здається читанням зовнішнього `foo`.
Проте оточення блока вже містить нове ім'я `foo`, і пошук зупиняється на ньому, а воно ще в мертвій зоні:

```js
function test() {
  const price = 10;
  if (price) {
    try {
      let price = price + 5;
      console.log(price);
    } catch (error) {
      console.log(error.name + ": " + error.message);
    }
  }
}
test();
```

```text
ReferenceError: Cannot access 'price' before initialization
```

Другий приклад розділу, `for (let n of n.a)`, падає з тієї самої причини: заголовок циклу вже належить новій області,
де `n` ще не має значення.

### `Other situations` і `Declaration with destructuring`

`Other situations` показує, що `var` у блоці належить зовнішній області, а `let` у блоці належить блоку. Тому `let x`
зовні і `var x` у блоці конфліктують: обидва потрапляють в одну область.

`Declaration with destructuring` показує **деструктуризацію**, тобто витягання кількох значень одним записом. Нові
змінні не пов'язані з масивом, із якого їх узяли:

```js
const pair = ["Київ", 3];
let [town, days] = pair;
days = days + 1;
console.log(town, days, pair[1]);
```

```text
Київ 4 3
```

Кінець сторінки містить таблицю підтримки браузерами й посилання. Для цього дня вони не потрібні.

**Навіщо в React.** Рядок `const [qty, setQty] = useState(0)` є саме такою деструктуризацією: він витягує зі значення,
яке повернула функція, дві нові змінні цього рендеру.

### Чого немає на цій сторінці: цикл `for`

Нова змінна на кожен прохід описана на сторінці
[`for`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/for), у розділі `Lexical
declarations in the initialization block`. Там сказано, що після кожного проходу цикл створює нову область, копіює
туди значення й лише потім виконує **afterthought**, тобто третю частину заголовка, наприклад `i++`.

Розділ показує й незвичний наслідок. Функція, створена в самому заголовку, тримає початкову змінну, яка не належить
жодному проходу:

```js
for (let i = 0, getI = () => i; i < 2; i++) {
  console.log("функція із заголовка:", getI(), "змінна проходу:", i);
}
```

```text
функція із заголовка: 0 змінна проходу: 0
функція із заголовка: 0 змінна проходу: 1
```

## Як читати специфікації, на які посилається теорія дня

Цей розділ необов'язковий. Теорія дня посилається на ECMA-262 і стандарт HTML, тому варто знати, що там написано.
**ECMA-262** — це специфікація мови JavaScript, а **стандарт HTML** описує, зокрема, таймери браузера. Обидва описують
поведінку як покрокові алгоритми. Вони не показують коду рушія й не є посібниками. Рушій може бути влаштований як
завгодно, якщо результат збігається.

Номери розділів змінюються між версіями. Посилання нижче ведуть на чернетку ECMA-262 станом на листопад 2026 року,
тому шукайте розділи за назвою, а не за номером.

| Запис в алгоритмі | Що означає |
|-------------------|------------|
| abstract operation | внутрішня процедура зі специфікації, яку не можна викликати з коду |
| `[[Environment]]` | внутрішнє поле об'єкта, яке недоступне з коду |
| `Let x be ...` | завести змінну самого алгоритму |
| `Set x to ...` | записати значення |
| `?` перед викликом | якщо виклик дав помилку, зупинитися й передати її далі |
| `!` перед викликом | цей виклик ніколи не дає помилки |
| Note | пояснення для читача, а не частина правил |

### ECMA-262: `Environment Records` (9.1)

[Цей розділ](https://tc39.es/ecma262/#sec-environment-records) визначає те, що лекція називає оточенням. Новий запис
з'являється щоразу, коли виконується код функції чи блока. Кожен запис має поле `[[OuterEnv]]`, яке посилається на
зовнішній запис або дорівнює `null`. Наприкінці розділ каже, що ці записи існують лише в описі мови, і програма не
може дістатися до них напряму.

Записи бувають різних видів. [`Declarative Environment
Records`](https://tc39.es/ecma262/#sec-declarative-environment-records) зберігають імена з оголошень. [`Function
Environment Records`](https://tc39.es/ecma262/#sec-function-environment-records) є їхнім різновидом для верхнього
рівня функції й додатково описують `this`. Стрілка позначена окремо, бо власного `this` не має.

### ECMA-262: `OrdinaryFunctionCreate` (10.2.3)

[Ця операція](https://tc39.es/ecma262/#sec-ordinaryfunctioncreate) створює об'єкт функції. Майже всі її кроки
записують у поля об'єкта різні дані: текст функції, параметри, режим роботи `this`. Для нас важливий один рядок: `Set
func.[[Environment]] to envRecord`. Значення `envRecord` передає той, хто створює функцію. Для стрілки це робить
[`InstantiateArrowFunctionExpression`](https://tc39.es/ecma262/#sec-runtime-semantics-instantiatearrowfunctionexpression),
який бере поточне оточення виконання. Отже, запам'ятовування оточення і є дією при створенні функції.

### ECMA-262: `NewFunctionEnvironment` (9.1.2.4)

[Ця операція](https://tc39.es/ecma262/#sec-newfunctionenvironment) працює при кожному виклику. Вона створює порожній
запис і виконує рядок `Set envRecord.[[OuterEnv]] to func.[[Environment]]`. У цьому рядку немає жодної згадки про
того, хто викликав функцію, і саме тому пошук іде від місця створення.

### ECMA-262: `GetIdentifierReference` (9.1.2.1)

[Ця операція](https://tc39.es/ecma262/#sec-getidentifierreference) шукає ім'я. Своїми словами її можна записати так:

| Крок | Що робить алгоритм |
|------|--------------------|
| Запису немає, отримано `null` | повертає результат «ім'я не знайдено» |
| Запис має таке ім'я | повертає посилання на цю змінну в цьому записі |
| Запис не має такого імені | викликає сам себе із зовнішнім записом `[[OuterEnv]]` |

Цей алгоритм повертає посилання на змінну, а значення читає окремий крок. Тому читання змінної завжди дає те, що
лежить у ній у цю мить.

### ECMA-262: `ForBodyEvaluation` (14.7.4.3) і `CreatePerIterationEnvironment` (14.7.4.4)

[Перша операція](https://tc39.es/ecma262/#sec-forbodyevaluation) описує порядок дій циклу: створити оточення проходу,
перевірити умову, виконати тіло, створити нове оточення проходу, виконати третю частину заголовка, повторити. [Друга
операція](https://tc39.es/ecma262/#sec-createperiterationenvironment) створює нове оточення, заводить у ньому ті самі
імена й копіює значення з попереднього проходу. Якщо цикл не має `let` у заголовку, список імен порожній, і нічого не
створюється. Так специфікація пояснює різницю між `let` і `var`.

### Стандарт HTML: `Timers` (8.7)

[Цей розділ](https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html#timers) описує `setTimeout` як
алгоритм. Основні кроки такі:

1. Від'ємна затримка стає нулем.
2. Якщо таймери вкладені понад п'ять разів, а затримка менша за 4 мілісекунди, вона стає 4 мілісекундами.
3. Алгоритм готує завдання, яке викличе вашу функцію з переданими аргументами.
4. Алгоритм запускає очікування паралельно й одразу повертає номер таймера.
5. Коли час минув, завдання потрапляє в чергу.

Браузер має право чекати довше, наприклад щоб заощадити заряд батареї, тому затримка є нижньою межею, а не точним
часом. Node має власну реалізацію, описану в [документації таймерів](https://nodejs.org/api/timers.html): затримку,
меншу за 1, він замінює на 1 і не обіцяє точного часу спрацювання.

## Запитання до читання

**1. MDN каже, що замикання створюється щоразу, коли створюється функція. Чому ж тоді його зазвичай пояснюють на
функції, яку повернули з іншої функції?**

<details><summary>Відповідь</summary>

Коли функцію викликають там само, де створили, вона й без пояснень здається такою, що просто бачить сусідні змінні.
Повернена функція переживає свій виклик, і саме тоді стає помітно, що вона тримає оточення.

</details>

**2. Чому в прикладі MDN з `onfocus` підказка завжди про вік?**

<details><summary>Відповідь</summary>

Усі три функції тримають спільне оточення з однією змінною `item`, бо вона оголошена через `var`. Функції спрацьовують
після завершення циклу, коли `item` вказує на останній елемент списку.

</details>

**3. Назвіть два виправлення цієї помилки, які не потребують `let` чи `const`. Що в них спільного?**

<details><summary>Відповідь</summary>

Фабрика функцій і IIFE в тілі циклу. Обидві викликають функцію на кожному проході, а кожен виклик створює нове
оточення з власною змінною.

</details>

**4. Що повертає `typeof` для неоголошеного імені і для змінної `let` до рядка її оголошення?**

<details><summary>Відповідь</summary>

Для неоголошеного імені він повертає рядок `undefined`. Для змінної в тимчасовій мертвій зоні він кидає
`ReferenceError`.

</details>

**5. Чому рядок `let price = price + 5` у блоці кидає помилку, хоча зовні є змінна `price`?**

<details><summary>Відповідь</summary>

Оточення блока вже містить ім'я `price`, і пошук зупиняється на ньому. Ця змінна ще не отримала значення, бо рядок
оголошення ще не завершився, тому читання кидає `ReferenceError`.

</details>

**6. Який рядок специфікації пояснює, що функція шукає змінні за місцем створення, а не за місцем виклику?**

<details><summary>Відповідь</summary>

Рядок `Set envRecord.[[OuterEnv]] to func.[[Environment]]` в операції `NewFunctionEnvironment`. Зовнішнім для нового
оточення виклику стає оточення, записане у функцію при створенні, а про місце виклику рядок нічого не каже.

</details>
