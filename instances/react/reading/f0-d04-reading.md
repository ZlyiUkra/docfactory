## JavaScript modules (MDN)

**Де читати:** [JavaScript modules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules).

**Що це за текст.** Це довгий посібник MDN про модулі в браузері. Приклад у ньому малює фігури на елементі `<canvas>`.
Цей елемент сторінки є полотном, на якому код JavaScript може малювати. Саме малювання для дня не важливе: автори
взяли його лише як простий код, який зручно розкласти на кілька модулів. Посібник написано для браузера, тому про Node
там майже нічого немає. Node описано в лекції.

**Якщо часу мало,** прочитайте `Exporting module features`, `Importing features into your script`, `Default exports
versus named exports`, `Other differences between modules and classic scripts` і `Dynamic module loading`.

### A background on modules

Автори пояснюють, що JavaScript починав із маленьких скриптів, а тепер на ньому пишуть великі застосунки. Спершу
модулі давали сторонні бібліотеки й інструменти, а тепер браузери підтримують їх самі. Проте бандлери, тобто програми,
які збирають код модулів у файли для браузера (лекція пояснює це слово), лишаються корисними. MDN пояснює чому: вони
вміють кілька речей, яких браузер сам не робить. Тут трапляються три слова. **Chunking** означає, що бандлер ділить
код на частини розумного розміру. **Minification** означає, що бандлер стискає текст коду, щоб файл став меншим.
**Tree-shaking** означає, що бандлер не включає у збірку експорти, які ніхто не імпортує. Лекція показала це запуском
Vite.

### Introducing an example, Basic example structure

Тут описано файли першого прикладу. Сторінка показує їх так:

```plain
index.html
main.js
modules/
    canvas.js
    square.js
```

Файл `index.html` є сторінкою, а `main.js` є головним модулем, який бере код з двох модулів у теці `modules/`. Модуль
`canvas.js` має функції, які створюють полотно на сторінці й список для звіту. Модуль `square.js` містить константу
`name` з рядком `'square'` і три функції: `draw()` малює квадрат, `reportArea()` записує у звіт його площу, а
`reportPerimeter()` записує його периметр. Ці імена ви далі побачите в усіх прикладах сторінки.

Автори одразу попереджають, що приклади треба запускати через локальний вебсервер, а не відкривати файл із диска.
Локальний вебсервер — це сервер, який працює на вашому ж комп'ютері й віддає браузеру файли з вашої теки. Причину
пояснює розділ про відмінності модулів.

### Aside — .mjs versus .js

Це відступ про розширення файлів. Слово «рушій» пояснювала лекція дня 2: це програма, яка виконує JavaScript.
Документація рушія V8, який працює в Chrome і в Node, радить для модулів розширення `.mjs`, щоб одразу було видно,
який файл є модулем. MDN лишає `.js`, бо сервери не завжди правильно віддають `.mjs`.

Що означає «правильно віддають», пояснює одне нове слово. Разом із файлом сервер надсилає позначку, яка каже, що
лежить у файлі. Цю позначку називають **MIME-тип**, і для JavaScript вона дорівнює `text/javascript`. Якщо сервер
надіслав модуль з іншою позначкою, браузер не виконає цей код. MDN пише, що більшість серверів уже правильно
позначають файли `.js`, а файли `.mjs` ще ні. Сам браузер дивиться не на розширення, а на цю позначку й на атрибут
`type="module"` у тегу `<script>`. У проєктах на Vite про це думати не треба.

### Exporting module features

Розділ показує два способи. Перший спосіб ставить слово `export` перед оголошенням. Ось код із файла `square.js`:

```js
export const name = "square";

export function draw(ctx, length, x, y, color) {
  ctx.fillStyle = color;
  ctx.fillRect(x, y, length, length);

  return { length, x, y, color };
}
```

Константа `name` і функція `draw` тепер доступні іншим файлам. Що робить тіло `draw`, для дня не важливо: воно малює
квадрат на полотні. Другий спосіб оголошує все без `export`, а наприкінці файла перелічує імена одним рядком:

```js
export { name, draw, reportArea, reportPerimeter };
```

Експорт має стояти на верхньому рівні файла, тобто поза будь-якою функцією, тому всередині функції він неможливий.
Експортувати можна функції, змінні й класи.

### Importing features into your script

Файл `main.js` бере експорти з `square.js` таким рядком:

```js
import { name, draw, reportArea, reportPerimeter } from "./modules/square.js";
```

У фігурних дужках перелічено імена, які файл бере, а після слова `from` стоїть рядок, за яким шукають файл модуля.
Лекція називає такий рядок вказівником. Далі `main.js` викликає `draw(...)` так, ніби функцію оголошено в ньому
самому.

Тут є дві важливі думки. Перша: `./` у шляху означає «ця тека», тобто тека, де лежить файл з цим `import`. Тому шлях
працює незалежно від того, де лежить весь проєкт.

Друга думка стосується того, що саме отримує файл, який імпортує. MDN називає імпортоване ім'я «поданням лише для
читання» (read-only view). Це означає, що ім'я у вашому файлі не є копією значення. Воно показує ту саму змінну, яку
оголосив модуль-експортер, і ваш файл може лише читати її. Присвоїти цьому імені нове значення ваш файл не може, так
само як змінній, оголошеній через `const`. Якщо ж у змінній лежить об'єкт, поля цього об'єкта змінити можна. Нове
значення самій змінній може дати лише модуль, який її експортує. Лекція в розділі «Що саме приходить через `import`»
показує спільний об'єкт, а теорія дня перевіряє цю думку на лічильнику.

### Importing modules using import maps

**Карта імпортів** (import map) — це блок `<script type="importmap">` на сторінці, де записано, якій назві яка адреса
відповідає. Вона потрібна, щоб у браузері без бандлера працював голий вказівник, тобто назва без шляху, наприклад
`from "shapes"`. Без карти браузер кидає `TypeError`. Сторінка показує таку карту:

```html
<script type="importmap">
  {
    "imports": {
      "shapes": "./shapes/square.js",
      "shapes/square": "./modules/shapes/square.js",
      "https://example.com/shapes/square.js": "./shapes/square.js",
      "https://example.com/shapes/": "/shapes/square/",
      "../shapes/square": "./shapes/square.js"
    }
  }
</script>
```

Ліворуч у кожному рядку стоїть те, що можна написати після `from`, а праворуч стоїть адреса, яку браузер підставить
замість цього. Після цієї карти рядок `import { name as squareNameOne } from "shapes";` працює, бо браузер знаходить у
карті ключ `"shapes"` і завантажує файл `./shapes/square.js`. Слово `as` у цьому рядку дає імпортованому імені `name`
нове ім'я `squareNameOne`, і про цей запис розповідає розділ `Renaming imports and exports`. Підрозділи `Feature
detection`, `Importing modules as bare names`, `Remapping module paths`, `Packages of modules`, `General URL
remapping`, `Scoped modules for version management` і `Improve caching by mapping away hashed filenames` описують
варіанти цього запису. У проєкті на Vite переписуванням назв займається сам Vite, тому ці підрозділи можна лише
переглянути. Запам'ятайте сам факт: гола назва не працює в браузері сама по собі, і вона працює в Node, бо Node шукає
в `node_modules`.

### Loading non-JavaScript resources

Розділ показує **атрибути імпорту**. Це запис `with { ... }` у кінці рядка `import`, який каже браузеру, що за файл
імпортують. Ось приклад зі сторінки:

```js
import colors from "./colors.json" with { type: "json" };
import styles from "./styles.css" with { type: "css" };
```

Перший рядок імпортує дані у форматі JSON, і змінна `colors` отримує звичайний об'єкт JavaScript. Другий рядок
імпортує стилі CSS як об'єкт таблиці стилів. Без такого запису браузер вважає, що файл містить JavaScript, і кидає
помилку, якщо там щось інше. Браузер також перевіряє, чи файл справді має названий тип, і відмовляє, якщо ні. MDN
пояснює, навіщо це: так браузер не виконає код випадково там, де ви хотіли взяти лише дані. Не плутайте це із записом
`import "./App.css"` у проєкті на Vite: той запис обробляє бандлер, а не сам браузер.

### Applying the module to your HTML

Модуль підключають тегом `<script type="module" src="main.js">`. Слова `import` і `export` працюють лише в модулях.
Звичайним скриптом MDN називає файл, який підключено тегом `<script>` без атрибута `type="module"`. У такому файлі ці
слова дають `SyntaxError`, і сторінка наводить такий текст помилки: `import declarations may only appear at top level
of a module`. Саме такий тег стоїть в `index.html` кожного проєкту на Vite.

### Other differences between modules and classic scripts

Це короткий і дуже корисний перелік:

| Що сказано | Що це означає |
|------------|---------------|
| Завантаження з `file://` дає помилку **CORS** | CORS — це правила браузера щодо доступу до чужих джерел. Сторінка, відкрита прямо з диска, не може завантажити модуль, тому потрібен сервер. Ви побачите помилку в консолі браузера |
| Суворий режим вмикається сам | Суворий режим пояснювала лекція дня 2. У модулі писати `"use strict"` не треба, а помилки на кшталт присвоєння неоголошеній змінній зупиняють програму |
| Атрибут `defer` не потрібен | Атрибут `defer` у тегу `<script>` каже браузеру виконати звичайний скрипт лише після того, як браузер прочитає всю сторінку до кінця. Модуль і так чекає цієї миті, тому атрибут йому не потрібен |
| Модуль виконується один раз | Модуль виконується один раз навіть тоді, коли на нього посилаються кілька тегів |
| Імена модуля не глобальні | Глобальним називають ім'я, яке видно з будь-якого скрипта сторінки й з консолі браузера. Імена модуля видно лише в самому модулі, тому в консолі їх не буде, і налагоджувати через консоль незвично |

### Default exports versus named exports

Тут описано `export default` і пояснено, що на модуль дозволено один такий експорт. У файлі `square.js` є функція
`randomSquare()`, яка малює квадрат випадкового кольору, розміру й положення. Автори роблять її типовим експортом,
дописавши наприкінці файла такий рядок:

```js
export default randomSquare;
```

Файл `main.js` імпортує її так:

```js
import randomSquare from "./modules/square.js";
```

Фігурних дужок тут немає. Вони не потрібні, бо типовий експорт у модулі лише один, і рушій знає, яку річ ви берете.
Сторінка пояснює, що цей рядок по суті є скороченням для такого запису:

```js
import { default as randomSquare } from "./modules/square.js";
```

Отже, типовий експорт є звичайним експортом з іменем `default`, а `as` дає йому ім'я у вашому файлі. Лекція показує це
власним запуском.

### Avoiding naming conflicts, Renaming imports and exports

Автори додають до прикладу модулі `circle.js` і `triangle.js`. Кожен із них експортує ті самі імена, що й `square.js`:
`name`, `draw`, `reportArea` і `reportPerimeter`. Якщо взяти їх в один файл без змін, вийде такий код. Ми відтворили
ці три модулі, запустили файл `main.js` із цим кодом у Node 24, і під кодом наведено головний рядок того, що
надрукував Node:

```js
import { name, draw, reportArea, reportPerimeter } from "./modules/square.js";
import { name, draw, reportArea, reportPerimeter } from "./modules/circle.js";
import { name, draw, reportArea, reportPerimeter } from "./modules/triangle.js";
```

```text
SyntaxError: Identifier 'name' has already been declared
```

Кожен рядок `import` оголошує у файлі імена `name`, `draw` і решту. Другий рядок намагається оголосити ті самі імена
вдруге, а одне ім'я в одному файлі можна оголосити лише раз. Тому виникає помилка повторного оголошення, і Node
зупиняється ще до того, як виконає хоч один рядок. Браузер поводиться так само. MDN наводить текст цієї помилки з
Firefox: `SyntaxError: redeclaration of import name`.

Автори показують два місця для `as`: під час експорту й під час імпорту. Під час імпорту запис має такий вигляд:

```js
import {
  name as squareName,
  draw as drawSquare,
  reportArea as reportSquareArea,
  reportPerimeter as reportSquarePerimeter,
} from "./modules/square.js";
```

Тепер функція `draw` з файла `square.js` має у вашому файлі ім'я `drawSquare`. Так само сторінка перейменовує імена з
`circle.js` і `triangle.js`, і конфлікту більше немає. Автори радять перейменовувати під час імпорту, бо чужий модуль
ви змінити не можете.

### Creating a module object

Запис `import * as Square from "./square.js"` збирає всі експорти в один об'єкт, і далі ви пишете `Square.draw()`. Це
ще один спосіб уникнути конфлікту імен.

### Modules and classes

Клас експортують так само, як функцію, і створюють його через `new`. Цей розділ можна пропустити: у сучасному React
компоненти пишуть функціями.

### Aggregating modules

**Агрегація** — це передавання чужих експортів далі. Записи `export * from "x.js"` і `export { name } from "x.js"`
дозволяють зібрати всю теку в одному файлі. У прикладі сторінки модулі фігур лежать у теці `modules/shapes/`, і кожен
із них експортує клас своєї фігури: `square.js` експортує `Square`, `circle.js` експортує `Circle`, а `triangle.js`
експортує `Triangle`. Поруч із цією текою автори створюють файл `shapes.js` із трьома рядками:

```js
export { Square } from "./shapes/square.js";
export { Triangle } from "./shapes/triangle.js";
export { Circle } from "./shapes/circle.js";
```

Файл `shapes.js` сам нічого не оголошує. Він лише бере кожен клас з його модуля й експортує далі. Завдяки цьому файл
`main.js` замість трьох рядків `import` пише один:

```js
import { Square, Circle, Triangle } from "./modules/shapes.js";
```

Файл `shapes.js` має той самий зміст, що й файл `index.js`, який збирає експорти цілої теки компонентів у великих
проєктах. Про такий файл розповідає лекція.

### Dynamic module loading

Вираз `import()` завантажує модуль під час виконання, а не до нього, як рядок `import`. Він одразу повертає проміс,
тобто об'єкт, який представляє ще не завершену роботу. Коли модуль завантажено, проміс виконується, і його значенням
стає об'єкт модуля. Це той самий об'єкт з усіма експортами, який дає запис `import * as`. Сторінка показує загальний
вигляд такого виклику:

```js
import("./modules/myModule.js").then((module) => {
  // Do something with the module.
});
```

Метод `then` приймає функцію, і цю функцію викликають тоді, коли модуль завантажився. Вона отримує об'єкт модуля в
параметрі `module`. У прикладі сторінки кожна фігура завантажується лише після клацання на її кнопку, тому код фігури,
на яку ніхто не клацнув, браузер так і не завантажує. На цьому побудовано функцію React `lazy`. Документація React
показує її так:

```js
const MarkdownPreview = lazy(() => import('./MarkdownPreview.js'));
```

React викличе цю функцію й завантажить код компонента `MarkdownPreview` лише тоді, коли компонент уперше треба буде
показати. Детально проміси й метод `then` пояснює день 5.

### Top level await

Слово `await` стоїть перед промісом і чекає, доки проміс виконається, а потім дає його значення. Детально `await`
пояснює день 5. У модулі `await` можна писати поза функцією. Тоді файл, який імпортує такий модуль, чекає його
завершення, а незалежні модулі завантажуються далі. У прикладі модуль `getColors.js` завантажує файл кольорів
`colors.json` і експортує результат:

```js
// fetch request
const colors = fetch("../data/colors.json").then((response) => response.json());

export default await colors;
```

Функція `fetch` просить файл з мережі й одразу повертає проміс, який виконується, коли прийшла відповідь. Метод
`response.json()` читає тіло відповіді як JSON і повертає проміс зі звичайним об'єктом. Отже, у константі `colors`
лежить проміс, значенням якого стане об'єкт кольорів. Останній рядок чекає цей проміс і робить його значення типовим
експортом. Файл `main.js` бере цей експорт рядком `import colors from "./modules/getColors.js";`. Сторінка пояснює
наслідок: код `main.js` не почне виконуватися, доки не відпрацює `getColors.js`, а модуль `canvas.js` тим часом
завантажується далі.

### Import declarations are hoisted

Оголошення імпорту спрацьовують раніше за решту коду, тому імпортоване ім'я доступне навіть вище за рядок `import`.
Сторінка показує це на такому фрагменті `main.js`:

```js
// …
const myCanvas = new Canvas("myCanvas", document.body, 480, 320);
myCanvas.create();
import { Canvas } from "./modules/canvas.js";
myCanvas.createReportList();
// …
```

Клас `Canvas` використано у першому рядку, а імпортовано лише в третьому, і код усе одно працює. Причину пояснювала
лекція: рушій обробляє всі рядки `import` ще до виконання коду, тому до першого рядка ім'я `Canvas` уже зв'язане з
експортом. MDN додає, що й код імпортованого модуля виконується раніше за решту коду файла. Автори все одно радять
писати імпорти вгорі, бо так видно залежності.

### Cyclic imports

**Циклічний імпорт** виникає, коли `a` імпортує `b`, а `b` прямо чи через інші файли залежить від `a`. Такий цикл не
завжди ламається, бо значення імпортованої змінної читається лише в момент використання. Сторінка показує цикл, який
працює. Тут в одному блоці записано два файли. Ми поклали їх у порожню теку, запустили `node a.js` у Node 24, і під
кодом наведено те, що він надрукував:

```js
// -- a.js --
import { b } from "./b.js";

setTimeout(() => {
  console.log(b); // 1
}, 10);

export const a = 2;

// -- b.js --
import { a } from "./a.js";

setTimeout(() => {
  console.log(a); // 2
}, 10);

export const b = 1;
```

```text
2
1
```

Розберемо, що тут відбувається. Ви запустили `a.js`, але першим виконується його залежність `b.js`. Файл `b.js` не
читає `a` одразу. Він лише ставить таймер, тобто просить виконати функцію через 10 мілісекунд, а потім створює
константу `b`. Далі виконується `a.js`: він теж ставить таймер і створює константу `a`. Коли таймери спрацьовують,
обидві константи вже мають значення. Першим спрацьовує таймер файла `b.js`, бо його поставили раніше, тому спершу
друкується `2`, а потім `1`.

Якщо код читає змінну до її ініціалізації, тобто до рядка, який дає їй значення, виникає `ReferenceError`. Такий
випадок, коли `b.js` читає `a` одразу, показує лекція. Автори дають три поради: об'єднати модулі, винести спільний код
у третій файл або перенести частину коду. У React цикли часто виникають, коли два компоненти імпортують один одного.

### Authoring "isomorphic" modules

**Ізоморфний модуль** працює і в браузері, і в Node. Браузер дає кожному скрипту глобальну змінну `window`, яка
представляє вікно зі сторінкою, а Node дає змінну `process`, яка описує запущену програму. У Node немає `window`, а в
браузері немає `process`. Тому такий модуль не повинен звертатися до цих змінних, поки не перевірив, що вони існують.
Сторінка показує таку перевірку:

```js
// myModule.js
let password;
if (typeof process !== "undefined") {
  // We are running in Node.js; read it from `process.env`
  password = process.env.PASSWORD;
} else if (typeof window !== "undefined") {
  // We are running in the browser; read it from the input box
  password = document.getElementById("password").value;
}
```

Оператор `typeof` повертає рядок `"undefined"`, якщо такої змінної немає, і не кидає помилки. Тому модуль спершу
з'ясовує, де він працює. У браузері він бере пароль з поля на сторінці. У Node він бере пароль зі змінної середовища
`PASSWORD`. **Змінна середовища** — це пара з назви й значення, яку операційна система передає запущеній програмі, а в
Node усі такі пари лежать в об'єкті `process.env`. Для фази 0 цей розділ можна пропустити, а до думки про код на
сервері ви повернетеся пізніше.

### Troubleshooting

Тут зібрано три типові збої: сервер віддає `.mjs` із неправильним MIME-типом, сторінка відкрита через `file://`, а
операційна система сховала чи змінила розширення файла. На перші два ви натрапите, лише якщо відкриватимете сторінку
без Vite.

## package.json (npm)

**Де читати:** [package.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-json), розділи
[dependencies](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#dependencies) і
[devDependencies](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#devdependencies).

**Що це за текст.** Це довідник, де кожне поле описано окремим розділом. Читати його від початку до кінця не треба.
Значна частина полів стосується авторів бібліотек, які публікують пакети в реєстрі. У застосунку на React потрібні
лише кілька полів.

**Якщо часу мало,** прочитайте лише `dependencies` і `devDependencies`.

### dependencies

У цьому полі записано, які пакети потрібні і яких версій. Сторінка перелічує всі дозволені форми запису:

| Запис | Що означає |
|-------|------------|
| `"2.0.1"` | лише ця версія |
| `">=1.0.0 <2.0.0"` | умови порівняння версій |
| `"~1.2"`, `"^1.2.3"` | діапазони, записані тильдою `~` і дашком `^`. Що саме вони дозволяють, пояснює розділ `About semantic versioning` нижче |
| `"1.2.x"` | версія 1.2 з будь-яким останнім числом |
| `"1.0.0 - 2.0.0"` | від і до, включно |
| `"<1.0.0 \|\| >=2.3.1"` | один або другий діапазон |
| `"*"` або `""` | будь-яка версія |
| `"latest"` | **дист-тег**, тобто назва, яку автор пакета прив'язав до певної версії |
| `"https://…/x.tgz"` | архів за адресою |
| `"git+https://…#v1.0"`, `"user/repo"` | сховище git або скорочення для GitHub |
| `"file:../my-lib"` | тека на вашому диску |
| `"npm:other@1.0.0"` | **псевдонім**: під цим іменем встановлюється інший пакет |

Сторінка окремо застерігає: не кладіть у цей розділ тестові бібліотеки, транспайлери й інші інструменти для розробки.
**Транспайлер** — це програма, яка перекладає код з однієї форми мови в іншу, наприклад з TypeScript у JavaScript.

### devDependencies

Сюди записують те, що потрібно для розробки, а не для роботи пакета в кінцевого користувача. Сторінка написана з
погляду автора бібліотеки. Той, хто встановить бібліотеку у свій проєкт, не отримає пакетів з її `devDependencies`.
Ці пакети npm встановлює лише тоді, коли `npm install` запущено в корені самої бібліотеки, тобто в теці, де лежить її
власний `package.json`. Для застосунку на Vite, як показує лекція, поділ на розділи не впливає на зібраний файл.
Команда `npm ci --omit=dev` пропускає цей розділ.

### Інші поля, які ви побачите

Ці поля не входять у завдане читання, але вони часто трапляються в `package.json`:

| Поле | Що каже сторінка |
|------|------------------|
| `name`, `version` | Це назва й версія пакета. Вони обов'язкові лише тоді, коли пакет публікують у реєстрі |
| `scripts` | Тут записано короткі команди, які запускає `npm run` |
| `bin` | Тут записано, яку команду для термінала дає пакет |
| `main` | Тут записано вхідний файл пакета, тобто файл, який отримує той, хто імпортує пакет за назвою. Якщо поля немає, вхідним файлом вважається `index.js` |
| `exports` | Це сучасна заміна `main`. Поле перелічує файли, які пакет дозволяє імпортувати ззовні, а файли, яких у переліку немає, імпортувати ззовні не можна |
| `type` | Поле каже Node, як читати файли `.js` пакета, наприклад значення `"module"` робить їх модулями. Сторінка прямо каже, що сам npm це поле не використовує |
| `private` | Якщо поле дорівнює `true`, npm відмовиться публікувати такий пакет |
| `peerDependencies` | Поле каже, з якими версіями головного пакета сумісний ваш пакет. Приклад розібрано під таблицею |
| `overrides` | Поле примусово замінює версію пакета, від якого залежать ваші залежності. npm враховує це поле лише в `package.json` самого проєкту, а в пакетах, які проєкт встановив, ігнорує |

Поле `peerDependencies` потребує прикладу. Буває пакет-доповнення, який працює разом з іншим, головним пакетом, але
сам цей головний пакет не обов'язково імпортує. Сторінка називає такий пакет плагіном і показує його `package.json`:

```json
{
  "name": "@npm/tea-latte",
  "version": "1.3.5",
  "peerDependencies": {
    "@npm/tea": "2.x"
  }
}
```

Цей запис каже, що плагін `@npm/tea-latte` можна встановити лише поруч із головним пакетом `@npm/tea` версії 2.
Сторінка пише, що в npm версій 3–6 такі пакети не встановлювалися самі, а з npm 7 npm встановлює їх автоматично.

**Навіщо це в React.** Розділ `peerDependencies` пояснює, як `react-dom` і бібліотеки компонентів домовляються про
версію React. Перевірте самі командою `npm view react-dom peerDependencies`. Команда `npm view` читає з реєстру опис
пакета, а назва поля після назви пакета просить надрукувати лише це поле.

## package-lock.json (npm)

**Де читати:** [package-lock.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json).

**Що це за текст.** Сторінка описує файл блокування. Перший розділ пояснює, навіщо він потрібен, а решта описує
формат. Формат потрібен рідко, бо файл пише сам npm. Вручну його не редагують.

**Якщо часу мало,** прочитайте `Description`.

### Description

npm створює цей файл щоразу, коли змінює `node_modules` або `package.json`. Файл описує точне дерево залежностей, яке
вийшло, щоб наступні встановлення дали таке саме дерево. Файл треба комітити. Сторінка називає п'ять причин:

- Усі учасники команди, сервери й сервер збирання гарантовано встановлюють точно ті самі залежності.
- Можна повернутися до старого стану `node_modules`, не зберігаючи саму теку `node_modules` у git.
- Зміни дерева стає видно в різниці git, тобто в переліку рядків, які змінилися між двома комітами.
- Встановлення йде швидше, бо npm не перепитує реєстр про пакети, які вже встановлювалися раніше.
- Починаючи з npm 7, файл містить повну картину дерева, тому npm рідше читає окремі файли `package.json`.

### package-lock.json vs npm-shrinkwrap.json

**npm-shrinkwrap.json** має той самий формат, але його можна опублікувати разом із пакетом. Файл `package-lock.json`
не публікується і працює лише в кореневому проєкті. Отже, файл блокування бібліотеки не впливає на ваш проєкт: вирішує
лише ваш власний. У застосунку вам потрібен саме `package-lock.json`.

### Hidden Lockfiles

npm також тримає прихований файл `node_modules/.package-lock.json`, щоб не обходити всю теку щоразу. Комітити його не
треба, бо він лежить у `node_modules`. Якщо ви вручну правили щось у `node_modules`, npm може цього не помітити, і
сторінка радить видалити прихований файл.

### Handling Old Lockfiles

Коли npm бачить файл блокування від старої версії npm 6 чи раніших, він сам оновлює його формат. Тому після `npm
install` у старому проєкті файл блокування може раптом сильно змінитися.

### File Format

Це довідкова частина. Ось поля, які варто впізнавати:

| Поле | Значення |
|------|----------|
| `lockfileVersion` | Це версія формату файла: 1 для npm 5 і 6, 2 для npm 7 і 8, 3 для npm 9 і новіших |
| `packages` | Це об'єкт, де ключ є розташуванням пакета, а порожній рядок `""` позначає сам проєкт |
| `version` | Це точна версія встановленого пакета |
| `resolved` | Це адреса, з якої npm завантажив архів пакета |
| `integrity` | Це **хеш** вмісту архіву, тобто коротке значення, обчислене з вмісту, як пояснює лекція. Його записано у стандартному форматі Subresource Integrity: спершу назва алгоритму `sha512` чи `sha1`, потім дефіс і саме значення |
| `dev`, `optional` | Поле `dev` позначає пакет, потрібний лише для розробки, а `optional` позначає необов'язковий пакет |
| `hasInstallScript` | Поле позначає пакет, який запускає власний скрипт під час встановлення |
| `dependencies` на верхньому рівні | Це застаріле поле, яке потрібне лише старим версіям npm |

Ключі в `packages` мають вигляд шляху, наприклад `node_modules/debug/node_modules/ms`. Отже, файл блокування записує
не лише версії, а й те, де кожен пакет лежатиме на диску.

**Навіщо це в React.** Щоразу, коли ви бачите великий рядок змін у цьому файлі, ви можете прочитати, які саме пакети
змінили версію.

## npm-ci (npm)

**Де читати:** [npm-ci](https://docs.npmjs.com/cli/v11/commands/npm-ci).

**Що це за текст.** Сторінка команди має сталий вигляд: `Synopsis` показує, як її викликати, `Description` пояснює, що
вона робить, `Configuration` перелічує прапорці. Назва походить від CI, continuous integration: так називають сервер,
який автоматично збирає проєкт і запускає тести після кожного коміту.

**Якщо часу мало,** прочитайте `Description`.

### Description

Сторінка перелічує п'ять відмінностей від `npm install`:

| Що написано | Що це означає на практиці |
|-------------|---------------------------|
| Проєкт мусить мати файл блокування | Без нього команда зупиняється з помилкою `EUSAGE` |
| Якщо файл блокування й `package.json` розходяться, команда виходить із помилкою | Вона нічого не вирішує за вас |
| Встановлює лише весь проєкт | Додати окремий пакет цією командою неможливо |
| Видаляє наявну `node_modules` | Не кладіть туди нічого свого |
| Ніколи не пише в `package.json` і файл блокування | Після неї в git немає змін |

Є ще одне застереження. Деякі прапорці `npm install` змінюють те, яким вийде дерево залежностей. Наприклад, прапорець
`--legacy-peer-deps` змушує npm повністю ігнорувати `peerDependencies`, як це робили npm версій 3–6. Якщо файл
блокування створено з таким прапорцем, той самий прапорець треба передати й `npm ci`, інакше він, імовірно,
завершиться помилкою.

### Example

Приклад порівнює час двох команд на тому самому проєкті з 154 пакетами. Сторінка показує їх разом із тим, що вони
надрукували:

```bash
$ cd ./my/npm/project
$ npm install
added 154 packages in 10s
$ ls | grep package-lock
```

```bash
$ npm ci
added 154 packages in 5s
```

Команда `npm install` зайняла 10 секунд, а `npm ci` зайняла 5 секунд. Це цифри з прикладу на сторінці, а не обіцянка.
Рядок `ls | grep package-lock` лише перевіряє, що в теці з'явився файл блокування. Далі наведено налаштування сервера
Travis CI, тобто однієї зі служб, які автоматично збирають проєкти:

```bash
# .travis.yml
install:
- npm ci
# keep the npm cache around to speed up installs
cache:
  directories:
  - "$HOME/.npm"
```

Рядок `- npm ci` під словом `install` каже серверу встановлювати залежності саме командою `npm ci`. Розділ `cache`
просить сервер зберігати між запусками теку `$HOME/.npm`, тобто кеш npm, щоб наступні встановлення йшли швидше. Сама
служба Travis для вас не важлива, а важлива думка: у вашому налаштуванні `npm ci` стоїть замість `npm install`.

### Configuration

Цей довгий перелік варто лише проглянути. Знадобляться три прапорці:

- `omit` пропускає вказані види залежностей, наприклад `--omit=dev`. Що таке змінна середовища, пояснено вище, у
  розділі про ізоморфні модулі. Якщо змінна середовища `NODE_ENV` дорівнює `production`, цей прапорець типово дорівнює
  `dev`. Через це на сервері можуть несподівано зникнути інструменти збирання.
- `ignore-scripts` забороняє npm запускати скрипти, записані в `package.json` пакетів. Деякі пакети мають скрипти
  `preinstall`, `install` чи `postinstall`, які npm запускає сам під час встановлення. Цей прапорець не дає їм
  запуститися, і тому він додає безпеки.
- `dry-run` показує, що зміниться, нічого не змінюючи.

## npx (npm)

**Де читати:** [npx](https://docs.npmjs.com/cli/v11/commands/npx).

**Якщо часу мало,** прочитайте `Description` і `Examples`.

### Description

Команда запускає програму з пакета, який або вже стоїть у проєкті, або завантажується спеціально для запуску. Основні
правила:

| Що написано | Що це означає |
|-------------|---------------|
| Параметри після назви пакета йдуть до програми | Команда `npx tool --flag` передає `--flag` самій програмі `tool`, а не `npx` |
| Якщо пакета немає в залежностях проєкту, npm встановлює його в кеш npm | У вашому проєкті нічого не змінюється |
| Назва без версії збігається з тією версією, яка вже стоїть у проєкті | Якщо в проєкті стоїть 1.0, запуститься 1.0 |
| Назва з версією збігається з пакетом проєкту лише тоді, коли назва й версія однакові. Інакше npm завантажує потрібну версію | Команда `npx tool@latest` може запустити іншу версію, ніж стоїть у проєкті |
| Перед встановленням npm друкує запитання | Прапорець `--yes` заздалегідь відповідає «так», а `--no` відповідає «ні» |

**Як вибирається програма.** Пакет описує програми в полі `bin`. Якщо запис один, запускається він. Якщо їх кілька,
запускається той, що збігається з назвою пакета без області. **Область** (scope) — це префікс назви на кшталт
`@vitejs/`. Якщо вибрати не вдається, npm виходить із помилкою. Прапорець `--package` (`-p`) вказує пакет, коли
потрібна програма називається інакше.

### npx vs npm exec

Обидві команди роблять одне й те саме, але `npx` вважає всі прапорці після назви пакета прапорцями програми.
Сторінка показує це на такій команді:

```
$ npx foo@latest bar --package=@npmcli/foo
```

Прапорець `--package` стоїть після назви `foo@latest`, тому npm не читає його сам, а передає програмі. У результаті
npm запускає таку команду:

```
$ foo bar --package=@npmcli/foo
```

У `npm exec` межу ставлять двома дефісами: `npm exec -- tool --flag`. Усе, що стоїть після `--`, npm не читає, а
передає програмі. Сторінка радить писати `--`, якщо є сумніви.

### Examples

Розділ має три приклади, і кожен записано двома рівнозначними способами, через `npm exec` і через `npx`. Перший
приклад запускає пакет `tap`, який уже стоїть у залежностях проєкту, і передає йому аргументи:

```
$ npm exec -- tap --bail test/foo.js
$ npx tap --bail test/foo.js
```

Другий приклад запускає з пакета `foo` програму `bar`, тобто програму, назва якої не збігається з назвою пакета.
Тому пакет вказано окремо прапорцем `--package`:

```
$ npm exec --package=foo -- bar --bar-argument
# ~ or ~
$ npx --package=foo bar --bar-argument
```

Третій приклад передає прапорцем `-c` цілий рядок команд, як його набрали б у терміналі. Ці команди виконуються в
межах поточного проєкту:

```
$ npm x -c 'eslint && say "hooray, lint passed"'
$ npx -c 'eslint && say "hooray, lint passed"'
```

Запис `npm x` є коротшою назвою `npm exec`.

### Compatibility with Older npx Versions

Цей розділ пояснює, що `npx` переписано в npm 7. Старі статті можуть згадувати прапорці `--ignore-existing` чи
`--no-install`: перший вилучено, а другий застарів. Якщо приклад із чужої статті не працює, причина може бути тут.

**Навіщо це в React.** Команда `npm create vite@latest`, яка створює проєкт, працює так само. Лекція пояснює, що
`npm create` є іншою назвою `npm init`. Сторінка команди `npm init` пише, що `npm init foo` перетворюється на
`npm exec create-foo`. Тому `npm create vite@latest` запускає `npm exec create-vite@latest`, тобто програму з пакета
`create-vite` останньої версії.

## About semantic versioning (npm)

**Де читати:** [About semantic versioning](https://docs.npmjs.com/about-semantic-versioning). Сторінка коротка, тому
читати її можна повністю.

### Incrementing semantic versions in published packages

Таблиця каже, яке число збільшити:

| Стан коду | Назва випуску | Правило | Приклад |
|-----------|---------------|---------|---------|
| Перший випуск | новий продукт | почати з 1.0.0 | `1.0.0` |
| Виправлено помилки, сумісність є | patch | збільшити останнє число | `1.0.1` |
| Нові можливості, сумісність є | minor | збільшити середнє, останнє обнулити | `1.1.0` |
| Зміни, що ламають сумісність | major | збільшити перше, решту обнулити | `2.0.0` |

Слово **backward compatible** означає «зворотно сумісний»: код, який працював зі старою версією, працює й з новою.

### Using semantic versioning to specify update types your package can accept

Для версії `1.0.4` сторінка наводить такі записи:

| Що дозволяємо оновлювати | Запис |
|--------------------------|-------|
| лише patch | `1.0`, `1.0.x`, `~1.0.4` |
| patch і minor | `1`, `1.x`, `^1.0.4` |
| усе, включно з major | `*`, `x` |

### Example

Приклад показує два записи в `dependencies`: `"my_dep": "^1.0.0"` і `"another_dep": "~2.2.0"`.

**Чого на сторінці немає.** Вона не каже про версії `0.x`, у яких дашок поводиться вужче. Це описано в [README пакета
semver](https://github.com/npm/node-semver#caret-ranges-123-025-004) у розділі про дашок: `^0.2.3` означає від `0.2.3`
до `0.3.0`, не включно, а `^0.0.3` означає лише `0.0.3`. Там само пояснено, чому версії з дефісом, тобто передрелізи,
про які розповідала лекція, не підходять під звичайний діапазон.

**Навіщо це в React.** За номерами версій ви вирішуєте, наскільки ризиковане оновлення. Перехід `19.2` → `19.3` має
бути сумісним, а перехід на 20 потребує читання статті про зміни.

## How to Design Programs, розділ 3

**Де читати:** [частина I, розділ 3](https://htdp.org/2024-11-6/Book/part_one.html#%28part._ch~3ahtdp%29) книжки How
to Design Programs, друге видання. Автори: Matthias Felleisen, Robert Bruce Findler, Matthew Flatt і Shriram
Krishnamurthi. Текст книжки не можна поширювати, тому тут є лише короткий переказ. Сервер `htdp-book` відповідає на
запитання за книжкою.

**Що це за текст.** Книжка вчить проєктувати програми, тобто продумувати функцію за сталими кроками ще до того, як
писати її код. Приклади книжки написано мовою BSL. Це спрощена мова для новачків, і її назва розшифровується як
Beginning Student Language. Програми цією мовою пишуть і запускають у DrRacket, тобто в окремій програмі для роботи з
кодом. Ви пишете на JavaScript, тому важливі кроки, а не синтаксис.

На початку розділу автори описують «програмування в гаражі» (garage programming). Так вони називають роботу навмання:
людина пробує то одне, то інше й зупиняється, коли результат виглядає прийнятно. Такою програмою можуть користуватися
лише її автори та їхні друзі. Добра програма, за словами книжки, має короткий опис того, що вона робить, які дані
приймає й що повертає, а також якесь підтвердження, що вона працює. Тоді інші люди можуть її читати й підтримувати.

**Якщо часу мало,** прочитайте перелік кроків у `3.1 Designing Functions`.

### 3.1 Designing Functions

Автори починають з думки, що програма перекладає інформацію з реального світу в дані, обробляє їх і перекладає
результат назад. Далі вони дають рецепт, тобто сталий перелік кроків, за яким проєктують кожну функцію.

У другому кроці рецепта є три нові слова. **Сигнатура** — це коментар, який каже, скільки даних функція приймає, якого
вони виду й що функція повертає. У книжці він має вигляд `; String -> Number`: ліворуч від стрілки стоїть те, що
функція приймає, а праворуч стоїть те, що вона повертає. **Призначення** (purpose statement) — це коментар з одного
рядка, який відповідає на запитання «що функція обчислює?». **Заголовок** (header), який книжка ще називає
**заглушкою** (stub), — це найпростіше оголошення функції, тіло якого просто повертає будь-яке значення потрібного
виду. Заглушка ще нічого не обчислює, але програму з нею вже можна запустити.

Рецепт має шість кроків:

| Крок книжки | Що ви робите | Запис у JavaScript у цьому курсі |
|-------------|--------------|----------------------------------|
| Опис даних | вирішуєте, як записати інформацію даними | коментар над даними |
| Сигнатура, призначення, заголовок | кажете, що функція бере й повертає, одним реченням пояснюєте її роботу, пишете заглушку | два рядки коментаря й `return` значення потрібного типу |
| Функціональні приклади | для вибраних вхідних даних вираховуєте результат самі | тести `node --test` |
| Перелік вхідних даних | виписуєте, з яких даних функція обчислюватиме результат. Поки що це лише її параметри | коментар у тілі функції |
| Тіло функції | замінюєте заглушку справжнім кодом | код |
| Перевірка | запускаєте приклади | `node --test` |

У книжці є покроковий приклад із площею квадрата, і приклад функції, яка додає текст на картинку. Ось той самий хід
думок на іншому прикладі в JavaScript. Нехай функція лежить у файлі `price.js`. Перший рядок коментаря є сигнатурою,
другий рядок є призначенням, а сама функція поки що є заглушкою. Заглушка навмисно повертає 0, щоб файл запускався ще
до написання тіла.

```js
// number -> number
// Ціна з податком 20 %, округлена до цілих гривень.
export function priceWithVat(price) {
  return 0;
}
```

Функціональні приклади записано тестами в окремому файлі `price.test.js`. Перший приклад каже, що `priceWithVat(100)`
має дати 120, а другий каже, що `priceWithVat(0)` має дати 0. Функція `test` з модуля `node:test` отримує назву
прикладу й функцію, яка цей приклад перевіряє. Функція `assert.equal` порівнює те, що повернула `priceWithVat`, з
очікуваним числом і кидає помилку, якщо вони різні. Команда `node --test` сама знаходить і запускає файли, назви яких
закінчуються на `.test.js`. Ось файл з тестами і те, що надрукувала ця команда в Node 24. Вивід скорочено: Node
друкує ще час кожного тесту, кілька рядків підсумку й подробиці помилки.

```js
import { test } from "node:test";
import assert from "node:assert/strict";
import { priceWithVat } from "./price.js";

test("priceWithVat: 100 грн", () => {
  assert.equal(priceWithVat(100), 120);
});

test("priceWithVat: безкоштовний товар", () => {
  assert.equal(priceWithVat(0), 0);
});
```

```text
$ node --test
✖ priceWithVat: 100 грн
✔ priceWithVat: безкоштовний товар
ℹ tests 2
ℹ pass 1
ℹ fail 1
```

Позначка `✖` означає, що приклад не пройшов, а `✔` означає, що пройшов. Другий приклад пройшов випадково, бо
заглушка повертає те саме значення. Перший упав, бо заглушка повернула 0 замість 120, і це правильно, бо тіла ще
немає. Книжка каже, що робити, коли приклад падає. Спершу перевірте, чи правильно ви вирахували очікуване значення.
Якщо так, шукайте помилку у функції. Буває й третій, рідший випадок: помилилися і там, і там.

### 3.3 Domain Knowledge

**Domain knowledge** означає знання предметної галузі. Щоб написати тіло функції, потрібні знання двох видів. Перший
вид стосується самої галузі: математики, бухгалтерії, медицини. Такі знання часто отримують від людей із цієї галузі.
Другий вид стосується бібліотек: треба знати, що мова й підключені бібліотеки вже вміють. Саме тому завдання дня
пропонує підключити готову зовнішню бібліотеку, а не писати самому те, що вона вже вміє.

### 3.4 From Functions to Programs

Програма зазвичай складається з багатьох функцій. Автори радять вести **список бажань** (wish list). Це перелік
функцій, які ще треба написати, і для кожної з них у ньому записано назву, сигнатуру й призначення. Функції зі списку
проєктуйте по одній за тим самим рецептом. Якщо під час роботи стало потрібно ще щось, допишіть до списку. Програма
готова, коли список порожній. Для простої програми першим до списку йде головна функція, а для інтерактивної туди
йдуть обробники подій. Сталі значення, які використовує функція, автори радять дописувати до переліку вхідних даних.

**Навіщо це в React.** Функцію з `export` викликають інші файли, і вони розраховують, що вона приймає й повертає саме
те, що про неї сказано. Сигнатура записує, що функція приймає й що повертає, а в дні 9 цей запис перевірятиме
TypeScript. Приклади-тести працюватимуть так само з компонентами й хуками.

## Запитання до читання

**1. MDN пише, що приклади треба запускати через вебсервер. Чому не можна відкрити `index.html` подвійним клацанням?**

<details><summary>Відповідь</summary>

Сторінка, відкрита за адресою `file://`, не може завантажити модуль через правила CORS, і в консолі браузера з'явиться
помилка. Звичайні скрипти таке обмеження не зачіпає.

</details>

**2. Чому в проєкті на Vite вам майже не потрібні карти імпортів?**

<details><summary>Відповідь</summary>

Карта потрібна, щоб браузер зрозумів голу назву пакета. Vite сам переписує такі назви на адреси, тому браузер отримує
вже правильний шлях.

</details>

**3. Де в `package.json` записати бібліотеку тестів і чому сторінка радить не класти її в `dependencies`?**

<details><summary>Відповідь</summary>

У `devDependencies`. Кінцевому користувачеві пакета вона не потрібна. Команда `npm install --save-dev` запише її туди,
а `--omit=dev` її пропустить.

</details>

**4. Які п'ять відмінностей `npm ci` від `npm install` називає документація?**

<details><summary>Відповідь</summary>

Вимагає файл блокування. Завершується помилкою при розбіжності. Встановлює лише весь проєкт. Видаляє `node_modules`
перед встановленням. Нічого не пише в `package.json` і файл блокування.

</details>

**5. Чому файл блокування бібліотеки не визначає версії у вашому проєкті?**

<details><summary>Відповідь</summary>

`package-lock.json` не публікується і враховується лише в кореневому проєкті. Версії залежностей бібліотеки у вашому
проєкті визначає ваш власний файл блокування в межах діапазонів, які бібліотека записала в `package.json`.

</details>

**6. Навіщо книжка радить писати заглушку до справжнього тіла функції?**

<details><summary>Відповідь</summary>

Заглушка робить програму правильною за формою, тому приклади можна запустити одразу. Приклад, який проходить на
заглушці випадково, показує, що цього прикладу мало, а приклад, який падає, показує, що попереду ще робота.

</details>
