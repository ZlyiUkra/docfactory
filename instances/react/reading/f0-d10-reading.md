## Generics

**Де читати:** [Generics](https://www.typescriptlang.org/docs/handbook/2/generics.html) у посібнику TypeScript
Handbook, який пишуть автори самої мови. У примірнику `typescript` це `handbook-v2/Type Manipulation/Generics`.

**Що там є.** Це основний текст дня. На початку автори кажуть, що дженерики дозволяють будувати частини програми, які
працюють із багатьма типами, а не з одним. Вони зазначають, що подібний механізм є в C# і Java. Параметр типу в цьому
тексті називається `Type`, а в сторінці дня й у коді React частіше `T`. Різниці немає, бо це лише назва.

**Якщо часу мало,** прочитайте `Hello World of Generics`, `Generic Types`, `Generic Constraints` і `Using Type
Parameters in Generic Constraints`.

### Hello World of Generics

Тут усе пояснено на найпростішій функції: `identity` повертає те, що отримала. Автори проходять той самий шлях, що й
лекція. Функцію можна написати для `number`, але тоді вона годиться лише для чисел. Її можна написати через `any`, але
тоді тип результату втрачено. Запис `identity<Type>(arg: Type): Type` запам'ятовує тип аргументу й передає його в
результат.

Далі показано два способи виклику. Перший пише тип явно: `identity<string>("myString")`. Другий покладається на
**виведення аргументу типу** (type argument inference): компілятор дивиться на значення й сам визначає `Type`. Автори
радять другий спосіб, бо він коротший, а явний запис лишають для випадків, коли виведення не вдається. Такий випадок
ви вже знаєте: початкове значення `null`.

### Working with Generic Type Variables

Автори показують помилку, яку робить кожен новачок. Функція `loggingIdentity<Type>(arg: Type)` читає `arg.length`, і
компілятор відповідає `Property 'length' does not exist on type 'Type'`. Причина проста: замість `Type` можуть
підставити число, а в числа довжини немає. Компілятор вимагає, щоб код був правильним для будь-якого типу.

Перше виправлення змінює параметр на масив, `arg: Type[]`, і тоді `length` законний. Запис `Array<Type>` означає те
саме.

### Generic Types

Тут автори записують сам тип дженерик-функції: `<Type>(arg: Type) => Type`. Читайте цей запис так: функція, яка має
власний параметр типу. Далі показано, що той самий тип можна винести в інтерфейс двома способами.

| Де стоїть параметр | Запис | Що це означає |
|--------------------|-------|---------------|
| на сигнатурі виклику | `interface F { <Type>(arg: Type): Type; }` | функція лишається дженериком, і кожен виклик добирає тип окремо |
| на самому інтерфейсі | `interface F<Type> { (arg: Type): Type; }` | тип задають один раз, `F<number>`, і далі функція працює лише з числами |

Для завдання дня важливий другий варіант. Коли ви пишете `interface Store<T>`, параметр стоїть на інтерфейсі, тому
`get`, `set` і `subscribe` говорять про той самий тип. Запис `Store<number>` закріплює його для всіх методів.

### Generic Classes

Клас теж може мати параметр типу, і приклад `GenericNumber` показує це для чисел і рядків. Статичні поля класу, тобто
ті, що належать самому класу, а не об'єкту, параметра не бачать.

**Застереження.** Приклад у тексті оголошує поля без початкових значень. Ми перевірили цей код на TypeScript 6.0.3 з
`--strict`: компілятор відповідає `TS2564: Property 'zeroValue' has no initializer`. Сторінка написана для м'якого
режиму, тому якщо ви спробуєте приклад у себе, ця помилка стосується не дженериків, а суворого режиму. У фазі 0 класи
не потрібні.

### Generic Constraints

Друге виправлення `loggingIdentity` додає **обмеження**. Автори описують інтерфейс `Lengthwise` із полем `length` і
пишуть `Type extends Lengthwise`. Відтепер функція приймає масиви, рядки й об'єкт `{ length: 10, value: 3 }`, а виклик
`loggingIdentity(3)` відхиляє. Слово `extends` тут не означає наслідування: воно каже, що тип має відповідати цьому
опису.

### Using Type Parameters in Generic Constraints

Це найкорисніший розділ для завдання дня. Один параметр типу може обмежувати інший. Запис `getProperty<Type, Key
extends keyof Type>(obj: Type, key: Key)` дозволяє лише ключі цього об'єкта. Автори беруть об'єкт із полями `a`, `b`,
`c`, `d`. Виклик із ключем `"a"` проходить, а виклик із ключем `"m"` дає помилку.

Порядок обчислення такий: спершу компілятор визначає `Type` з об'єкта, потім обчислює `keyof Type`, а потім перевіряє
`Key`. Той самий механізм стоїть за обмеженням у `pick` із завдання дня й за функцією `pluck` із лекції.

### Using Class Types in Generics

Тут показано, як передати у функцію сам клас, щоб вона створила його об'єкт. Запис `{ new (): Type }` означає «щось,
що можна викликати через `new` і отримати `Type`». Приклади з `BeeKeeper` і `Lion` ускладнюють цю ідею. У фазі 0 цей
розділ можна пропустити.

### Generic Parameter Defaults

Параметр типу може мати значення за замовчуванням: `<T = HTMLDivElement>`. Якщо тип не вказано й вивести його нема з
чого, компілятор бере це значення. Автори порівнюють такий запис із кількома перевантаженими оголошеннями функції
`create`, а потім перелічують правила. Найважливіші з них такі: параметр зі значенням за замовчуванням стає
необов'язковим, обов'язкові параметри не можуть іти після нього, а значення має відповідати обмеженню.

У React цей прийом теж є. У пакеті `@types/react` є оголошення `function useState<S = undefined>()`, яке спрацьовує,
коли `useState` викликають без аргументу.

### Variance Annotations

**Варіантність** описує, чи можна підставити `Producer<Cat>` там, де очікують `Producer<Animal>`. Компілятор сам
обчислює це за формою типу. Запис `in` і `out` у кутових дужках дозволяє вказати це явно, але автори прямо кажуть, що
такі позначки майже ніколи не потрібні. Цей розділ можна пропустити.

## Keyof Type Operator

**Де читати:** [Keyof Type Operator](https://www.typescriptlang.org/docs/handbook/2/keyof-types.html). У примірнику
`typescript` це `handbook-v2/Type Manipulation/Keyof Type Operator`.

**Що там є.** Це дуже коротка сторінка, яку легко прочитати цілком.

### The `keyof` type operator

Головне сказано одним прикладом: для типу `Point` із полями `x` і `y` запис `keyof Point` дорівнює `"x" | "y"`. Отже,
результат є об'єднанням літеральних типів, про які йшлося вчора. Оператор працює лише з типами: ви не можете
застосувати його до значення під час роботи програми.

Далі автори розбирають **індексну сигнатуру**. Так називають запис `{ [k: string]: boolean }`, який означає об'єкт із
будь-якими рядковими ключами. Для нього `keyof` дає `string | number`, і це дивує. Причина в JavaScript: ключі об'єкта
завжди перетворюються на рядки, тому `obj[0]` і `obj["0"]` означають те саме. Для `{ [n: number]: unknown }`
результатом буде просто `number`.

Наприкінці сторінка згадує, що `keyof` особливо корисний разом зі зіставленими типами. Прикладу тут немає, але ви
бачили один у лекції: так оголошено `Partial`.

Ще два випадки текст не розбирає. Вони корисні для читання повідомлень компілятора.

Файл `keys.ts`:

```ts
type Product = { id: number; name: string };
type Parcel = { id: number; weight: number };

const common: keyof (Product | Parcel) = "name";

const tea: Product = { id: 1, name: "Чай" };
for (const key of Object.keys(tea)) {
  console.log(tea[key]);
}
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false keys.ts
keys.ts(4,7): error TS2322: Type '"name"' is not assignable to type '"id"'.
keys.ts(8,15): error TS7053: Element implicitly has an 'any' type because expression of type 'string' can't be used to index type 'Product'.
  No index signature with a parameter of type 'string' was found on type 'Product'.
```

Для об'єднання типів `keyof` дає лише спільні ключі, бо лише вони є в кожному варіанті. Метод `Object.keys` повертає
`string[]`, бо в значення можуть бути й не описані поля.

## Utility Types

**Де читати:** [Utility Types](https://www.typescriptlang.org/docs/handbook/utility-types.html) у довіднику
TypeScript. У примірнику `typescript` це `reference/Utility Types`.

**Що там є.** Це довідник, а не розповідь. Кожен розділ містить один службовий тип, рядок із версією, коли він
з'явився (`Released`), опис і приклад. Читати його варто частинами.

**Якщо часу мало,** прочитайте `Partial`, `Pick`, `Omit` і `Record`. Для завдання дня цього досить.

Оголошення цих типів можна подивитися у файлі `node_modules/typescript/lib/lib.es5.d.ts`. Цей файл читається легко, бо
кожне оголошення займає кілька рядків.

### `Awaited<Type>`

Цей тип показує, що дасть `await`. Він розгортає вкладені проміси: `Awaited<Promise<Promise<number>>>` дорівнює
`number`.

### `Partial<Type>`

Усі поля стають необов'язковими. Приклад `updateTodo` показує типове застосування: функція приймає об'єкт і часткові
зміни, а повертає об'єднаний об'єкт через `...`. Завдання дня містить таку функцію, `applyEdit`, готовою.

### `Required<Type>`

Це протилежне до `Partial`: усі поля стають обов'язковими.

### `Readonly<Type>`

Поля не можна переприсвоїти, і компілятор дає `Cannot assign to 'title' because it is a read-only property`. Підрозділ
`Object.freeze` показує зв'язок із JavaScript: опис цього методу повертає `Readonly<Type>`. Лише сам метод заморожує
об'єкт під час роботи, а тип лише забороняє присвоєння в коді.

### `Record<Keys, Type>`

Цей тип описує об'єкт із ключами `Keys` і значеннями `Type`. У прикладі `CatName` є об'єднанням трьох імен, тому
компілятор вимагає всі три. Ми перевірили наслідок: якщо пропустити ключ, компілятор повідомляє, що цього поля бракує.
Запис `Record<string, number>` поводиться інакше, бо ключів безліч, і лекція показує пов'язану з цим пастку.

### `Pick<Type, Keys>`

Цей тип лишає лише названі поля. Приклад `TodoPreview` є короткою версією `Todo` для перегляду списку. Другий параметр
обмежено як `K extends keyof T`, тому компілятор перевіряє назви. Завдання дня використовує цей тип у типі результату
своєї функції.

### `Omit<Type, Keys>`

Цей тип прибирає названі поля. Оголошення показує цікаву річ: `type Omit<T, K extends keyof any> = Pick<T,
Exclude<keyof T, K>>`. Отже, `Omit` складено з двох інших типів. Запис `keyof any` означає будь-який можливий ключ,
тому описка в назві поля компілятора не турбує. Те саме сказано в лекції.

### `Exclude<UnionType, ExcludedMembers>`

Цей тип прибирає варіанти з об'єднання: `Exclude<"a" | "b" | "c", "a">` дає `"b" | "c"`. Приклад із `Shape` показує,
що так можна прибрати цілий варіант розрізнюваного об'єднання. Не плутайте його з `Omit`: `Exclude` працює з
варіантами об'єднання, а `Omit` з полями об'єкта.

### `Extract<Type, Union>`

Це протилежне до `Exclude`: лишаються лише варіанти, які підходять під другий параметр.

### `NonNullable<Type>`

Цей тип прибирає з об'єднання `null` і `undefined`.

### `Parameters<Type>` і `ConstructorParameters<Type>`

`Parameters<typeof f>` дає кортеж типів аргументів функції `f`. Запис `typeof f` тут означає тип функції, а не
оператор JavaScript. Другий тип робить те саме для конструктора класу.

### `ReturnType<Type>` і `InstanceType<Type>`

`ReturnType<typeof f>` дає тип результату функції `f`. Він зручний, коли функцію написав хтось інший, а окремої назви
для її результату немає. Другий тип дає тип об'єкта, який створює клас.

### `NoInfer<Type>`

Цей тип з'явився у версії 5.4. Він забороняє компілятору брати цей аргумент як підказку для параметра типу. У прикладі
`createStreetLight` список кольорів задає допустимі значення, а колір за замовчуванням лише перевіряють за цим
списком. Сьогодні він не потрібен.

### `ThisParameterType<Type>`, `OmitThisParameter<Type>` і `ThisType<Type>`

Ці три типи працюють із параметром `this` у функціях. У цьому плані вони не знадобляться, тому розділи можна
пропустити.

### Intrinsic String Manipulation Types

`Uppercase`, `Lowercase`, `Capitalize` і `Uncapitalize` змінюють літеральні рядки на рівні типів: `Uppercase<"чай">`
дорівнює `"ЧАЙ"`. Докладніше про них сказано на сторінці Template Literal Types. У цьому плані вони не потрібні.

Файл нижче перевіряє кілька наведених вище тверджень. Кожна помилка показує, який тип вийшов насправді.

Файл `utility.ts`:

```ts
function total(price: number, count: number): string {
  return String(price * count);
}

const a: Awaited<Promise<Promise<number>>> = "x";
const b: Exclude<"a" | "b" | "c", "a"> = "a";
const c: Parameters<typeof total> = [80];
const d: ReturnType<typeof total> = 5;
const e: Uppercase<"чай"> = "чай";
```

```text
$ npx tsc --noEmit --strict --target es2022 --pretty false utility.ts
utility.ts(5,7): error TS2322: Type 'string' is not assignable to type 'number'.
utility.ts(6,7): error TS2322: Type '"a"' is not assignable to type '"b" | "c"'.
utility.ts(7,7): error TS2322: Type '[number]' is not assignable to type '[price: number, count: number]'.
  Source has 1 element(s) but target requires 2.
utility.ts(8,7): error TS2322: Type 'number' is not assignable to type 'string'.
utility.ts(9,7): error TS2322: Type '"чай"' is not assignable to type '"ЧАЙ"'.
```

## How to Design Programs: 3.1 Designing Functions

**Де читати:** [розділ 3.1 книжки](https://htdp.org/2024-11-6/Book/part_one.html#%28part._sec~3adesign-func%29). У
примірнику `htdp` це розділ `3.1 Designing Functions`. Вчорашній розбір уже переказав цей розділ, тому тут важливо
лише, що змінюється для дженериків. Текст книжки тут лише коротко переказано.

**Якщо часу мало,** досить згадати таблицю нижче.

### The Design Process

Шість кроків лишаються тими самими. Кожен із них отримує параметр типу, якщо функція працює з багатьма типами.

| Крок книжки | Що змінюється сьогодні |
|-------------|------------------------|
| Подати інформацію як дані | опис даних сам може мати параметр: `Store<T>` |
| Сигнатура, призначення, заголовок | сигнатура отримує кутові дужки, а призначення каже, що саме зв'язує параметр |
| Приклади | потрібні приклади для різних типів і приклади для компілятора під `@ts-expect-error`, наприклад неправильна назва поля |
| Перелік вхідних даних | крім параметрів, сюди входить те, що живе між викликами, наприклад значення в замиканні |
| Код | тіло не залежить від конкретного типу, бо заздалегідь його не знає |
| Перевірка | `tsc` перевіряє типи, а `node --test` перевіряє поведінку; один не замінює іншого |

Сама книжка повертається до цієї теми пізніше, у частині про абстракцію. Розділ [14.3 Similarities in Data
Definitions](https://htdp.org/2024-11-6/Book/part_three.html) показує два майже однакові означення списку, для чисел і
для рядків. Вони відрізняються лише одним місцем, і це місце автори роблять параметром. Це та сама думка, що лежить в
основі `Array<T>`. За змістом до дженериків близький і розділ `15.2 Similarities in Signatures`. Вони не входять у
завдання дня.

## Додатково: Guidelines for Writing Good Generic Functions

**Де читати:** однойменний розділ сторінки [More on
Functions](https://www.typescriptlang.org/docs/handbook/2/functions.html). Його немає в обов'язковому списку, але саме
він підтримує пастку цього дня. Він містить три короткі правила.

| Назва правила | Що воно каже | Приклад із тексту |
|---------------|--------------|-------------------|
| `Push Type Parameters Down` | беріть сам параметр, а не обмеження на цілому масиві, інакше результат стає надто широким | `firstElement2<Type extends any[]>` дає `any` |
| `Use Fewer Type Parameters` | не додавайте параметр, який нічого не зв'язує | зайвий `Func` у `filter2` |
| `Type Parameters Should Appear Twice` | параметр, який трапляється один раз, майже завжди зайвий | `greet<Str extends string>` |

На цій самій сторінці є розділ `Working with Constrained Values`. Там показано помилку, про яку часто запитують:
функція обіцяє повернути `Type`, а повертає `{ length: minimum }`. Об'єкт підходить під обмеження, але не є саме тим
типом, який передали, тому компілятор його відхиляє.

## Запитання для самоперевірки

**1. Що означає «виведення аргументу типу» і коли його не вистачає?**

<details><summary>Відповідь</summary>

Компілятор сам визначає параметр типу з аргументів виклику. Його не вистачає, коли з аргументу не видно задуму,
наприклад початкове значення `null`, або коли аргументів немає взагалі. Тоді тип пишуть у кутових дужках.

</details>

**2. Чим відрізняються `interface F { <Type>(arg: Type): Type; }` і `interface F<Type> { (arg: Type): Type; }`?**

<details><summary>Відповідь</summary>

У першому випадку кожен виклик добирає тип окремо. У другому тип задають один раз, коли пишуть `F<number>`, і далі він
закріплений. Для сховища з кількома методами потрібен другий варіант, бо всі методи говорять про той самий тип.

</details>

**3. Чому `keyof { [k: string]: boolean }` дорівнює `string | number`?**

<details><summary>Відповідь</summary>

Ключі об'єкта в JavaScript завжди стають рядками, тому `obj[0]` означає те саме, що `obj["0"]`. Отже, числовий ключ
теж законний для рядкової індексної сигнатури.

</details>

**4. Чому `Pick` перевіряє назву поля, а `Omit` ні?**

<details><summary>Відповідь</summary>

`Pick` оголошено з обмеженням `K extends keyof T`, а `Omit` з обмеженням `K extends keyof any`, тобто будь-який ключ.
Опис `Omit` не вимагає, щоб ключ належав типу `T`.

</details>

**5. Чим `Exclude` відрізняється від `Omit`?**

<details><summary>Відповідь</summary>

`Exclude` прибирає варіанти з об'єднання, а `Omit` прибирає поля з об'єктного типу. `Omit` якраз і використовує
`Exclude` над об'єднанням ключів.

</details>

**6. Чому приклад `GenericNumber` із посібника може дати помилку у вас, хоча в тексті її немає?**

<details><summary>Відповідь</summary>

Сторінка написана для м'якого режиму. З `--strict` компілятор вимагає початкових значень для полів класу й друкує
`TS2564`. Ця помилка стосується суворого режиму, а не дженериків.

</details>

**7. Яке правило допомагає вирішити, чи потрібен параметр типу?**

<details><summary>Відповідь</summary>

Параметр має траплятися принаймні у двох місцях і зв'язувати їх, наприклад вхід і вихід. Якщо він є лише в одному
місці, його майже завжди можна прибрати.

</details>
