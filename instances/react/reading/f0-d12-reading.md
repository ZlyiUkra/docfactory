### Вступ

Великі вебзастосунки почали заважати власним інструментам: сервер розробки довго запускався, гаряча заміна
спрацьовувала із затримкою, а збірка тривала довго. Що таке гаряча заміна, пояснює лекція дня 11, розділ «Гаряча
заміна: як змінити код, не втративши стан». Попередні покоління інструментів поступово поліпшували роботу, але суть
проблеми лишалася. Vite створено, щоб змінити сам спосіб віддавати код під час розробки.

### `The Origins`

Це головний розділ. Коли браузери навчилися завантажувати модулі самі, стало можливо віддавати JavaScript без
склеювання. До того працювали **бандлери**, тобто програми, які склеюють модулі проєкту в кілька файлів (лекція дня 4,
розділ «Як завантажується програма з модулів»). Бандлер обробляв увесь застосунок, перш ніж щось показати, тому
більший застосунок означав довше чекання.

Vite поділив код на дві групи й обходиться з ними по-різному. Перша група — це **залежності**, тобто бібліотеки з
`node_modules`. Вони змінюються рідко, тому Vite один раз склеює кожну з них заздалегідь. Склеює він інструментом,
написаним мовою, яку перекладають у машинний код, і тому такий інструмент працює набагато швидше за написаний на
JavaScript. Навіщо взагалі склеювати бібліотеки, пояснює вчорашній розбір, розділ `npm Dependency Resolving and
Pre-Bundling`. Друга група — це ваш код. Він змінюється постійно, тому Vite нічого не готує наперед: браузер запитує
файл, і лише тоді Vite перетворює саме цей файл. Як це виглядає крок за кроком, показує лекція дня 11, розділ «Робота
перша: сервер розробки віддає файли на вимогу».

Звідси два наслідки, про які говорить сторінка. Сервер запускається майже миттєво незалежно від розміру застосунку,
бо на старті він ще нічого не перетворив. А гаряча заміна оновлює лише змінений модуль, і для цього не потрібно ні
перезавантажувати сторінку, ні збирати все заново.

На сторінці є дві схеми, і їх варто роздивитися. Перша показує сервер на основі бандлера: спершу склеювання всього
застосунку, потім показ. Друга показує сервер на модулях: сервер готовий одразу, а модулі вантажаться, коли браузер
про них просить.

**Найважливіше для сьогоднішніх чисел.** Наприкінці розділу сказано, що для продакшну такий спосіб неефективний,
бо кожен вкладений `import` додає ще один **обмін** (round trip). Обмін — це шлях запиту від браузера до сервера й
відповіді назад (розбір дня 8, розділ `TCP handshake`). Обмін не можна почати раніше, ніж браузер дізнається про
файл, а дізнається він про нього, лише прочитавши файл, що його імпортує. Тому вкладені імпорти вантажаться не
одночасно, а по черзі, сходинками. Таку драбинку лекція називає каскадом (розділ «Один запит за кроками», абзац «Як
читати водоспад цілком»). Саме через каскад збірка існує як окремий крок.

Подивимося на каскад у браузері. Візьмемо приклад, де `main.js` імпортує `App.js`, а той імпортує ще чотири файли.
Маленький сервер на Node віддає кожен файл `.js` із затримкою 100 мс, ніби сервер стоїть далеко. Друга сторінка,
`bundle.html`, має той самий код, уже склеєний в один файл:

```js
// файл cascade.mjs, перша половина: сторінки й сервер
const FILES = {
  "/index.html": '<!doctype html><script type="module" src="/main.js"></script>',
  "/main.js": 'import "./App.js"\nconsole.log("main.js виконано")',
  "/App.js": 'import "./a.js"\nimport "./b.js"\nimport "./c.js"\nimport "./d.js"',
  "/a.js": "", "/b.js": "", "/c.js": "", "/d.js": "",
  "/bundle.html": '<!doctype html><script type="module" src="/bundle.js"></script>',
  "/bundle.js": 'console.log("bundle.js виконано")',
}
const server = createServer(async (req, res) => {
  if (req.url.endsWith(".js")) await new Promise((r) => setTimeout(r, 100))
  const type = req.url.endsWith(".html") ? "text/html" : "text/javascript"
  res.writeHead(200, { "Content-Type": type, "Cache-Control": "no-store" })
  res.end(FILES[req.url] ?? "")
})
```

Друга половина скрипта відкриває сторінку в Chrome без вікна й друкує для кожного запиту час початку, час кінця та
причину запиту, тобто файл, який його спричинив. Вкладка Network показує цю причину в стовпчику Initiator. Chrome 158
без вікна надрукував:

```text
сторінка /index.html
  /index.html  почався    0 мс, закінчився   32 мс, причина: other
  /main.js     почався   37 мс, закінчився  142 мс, причина: /index.html
  /App.js      почався  143 мс, закінчився  245 мс, причина: /main.js
  /a.js        почався  245 мс, закінчився  346 мс, причина: /App.js
  /b.js        почався  245 мс, закінчився  347 мс, причина: /App.js
  /c.js        почався  246 мс, закінчився  348 мс, причина: /App.js
  /d.js        почався  246 мс, закінчився  348 мс, причина: /App.js
  DOMContentLoaded  350 мс, load  350 мс

сторінка /bundle.html
  /bundle.html почався    0 мс, закінчився   27 мс, причина: other
  /bundle.js   почався   31 мс, закінчився  136 мс, причина: /bundle.html
  DOMContentLoaded  137 мс, load  137 мс
```

Запит `App.js` почався лише тоді, коли закінчився `main.js`, а чотири останні файли почалися разом, щойно прийшов
`App.js`. Отже, сторінка пройшла три сходинки по 100 мс. Склеєний файл прийшов за одну сходинку, і подія
`DOMContentLoaded` настала на 213 мс раніше. Що означають `DOMContentLoaded` і `load`, пояснено нижче, у розділі про
довідкову сторінку Network. На вашому комп'ютері сервер розробки відповідає швидко, тому сходинки короткі. На
реальній мережі кожна сходинка коштує цілий обмін, тому продакшн отримує склеєні файли.

Назви `Snowpack`, `WMR` і `@web/dev-server` у цьому розділі це попередники Vite. Запам'ятовувати їх не потрібно.

### `Growing with the Ecosystem`

Фреймворки, серед них React Router, SvelteKit і Astro, використовують Vite як основу. Інструменти Vitest і Storybook
теж на ньому побудовані. Для вас важливо одне: Vitest перетворює код тим самим способом, що й сервер розробки (лекція
дня 11, розділ «Vitest: приклади стають перевірками»). Перевірка `vite-ecosystem-ci` означає, що команда запускає
тести великих проєктів на кожній зміні Vite.

### `A Unified Toolchain`

Раніше Vite мав два інструменти: esbuild для розробки й Rollup для збірки. Вони перетворювали код трохи по-різному й
мали різні плагіни. Тепер обидві роботи виконує Rolldown, написаний мовою Rust, яку перекладають у машинний код. Він
використовує Oxc. Сторінка називає три роботи Oxc. Перша — **розбір**: програма читає текст коду й будує з нього
структуру, з якою далі можна працювати. Друга — перетворення, наприклад вирізання типів TypeScript. Третя —
мінімізація, тобто переписування коду коротше (лекція дня 11, розділ «Робота друга: збірка для користувачів»).

Якщо старий туторіал згадує esbuild чи Rollup у налаштуваннях, це означає, що він написаний для старшої версії Vite.
Назви `rollupOptions` або `esbuild` у такому туторіалі звіряйте з документацією для вашої версії.

### `Where Vite is Heading`

Сторінка називає три напрямки.

`Full bundle mode` означає режим розробки зі склеюванням. У дуже великих застосунках кількість окремих запитів сама
стає проблемою: сторінка вантажиться повільно, бо запитів тисячі. Rolldown настільки швидкий, що склеювання стало
можливим і в розробці. Цей напрямок поки що досліджується, тому ваші заміри сьогодні покажуть окремі запити.

`Environment API` стосується того, де виконується код. Досі Vite знав дві цілі: клієнт, тобто браузер, і **SSR**
(server-side rendering), тобто сервер, який сам будує HTML сторінки. Новий інтерфейс дозволяє фреймворкам описати
власні середовища, наприклад сервери поблизу користувача чи сервіс-воркери (про них нижче). Кожне таке середовище має
свої правила пошуку модулів і виконання коду.

Третій напрямок стосується швидкого прийняття нових можливостей мови: Vite, Rolldown і Oxc розвиваються разом, тому
їм не треба чекати на чужі інструменти.

**Навіщо це в React.** Склеєні залежності видно у водоспаді прямо. Ось найменший застосунок React у режимі розробки,
Vite 8.3 і React 19.3:

```jsx
// файл src/main.jsx
import { StrictMode } from "react"
import { createRoot } from "react-dom/client"
import { App } from "./App.jsx"

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

```jsx
// файл src/App.jsx
import { useEffect, useState } from "react"

export function App() {
  const [text, setText] = useState("завантаження…")
  useEffect(() => {
    fetch("/hello.json")
      .then((response) => response.json())
      .then((data) => setText(data.text))
  }, [])
  return <p>{text}</p>
}
```

Файл `public/hello.json` містить `{"text":"привіт"}`. Ми запустили сервер розробки Vite, тобто те саме, що робить
`npm run dev` у вашому проєкті. Програма відкрила сторінку в Chrome 158 без вікна з вимкненим кешем і надрукувала
кожен запит: адресу, а після стрілки причину запиту.

```text
/  <-  other
/@vite/client  <-  /
/src/main.jsx  <-  /
/@react-refresh  <-  /
/node_modules/.vite/deps/react.js  <-  /src/main.jsx
/node_modules/.vite/deps/react-dom_client.js  <-  /src/main.jsx
/src/App.jsx  <-  /src/main.jsx
/node_modules/.vite/deps/react_jsx-dev-runtime.js  <-  /src/main.jsx
/node_modules/.vite/deps/react-DgVJeC5g.js  <-  /node_modules/.vite/deps/react.js
/node_modules/vite/dist/client/env.mjs  <-  /@vite/client
WebSocket /
/node_modules/.vite/deps/react-dom-CFuoV50Q.js  <-  /node_modules/.vite/deps/react-dom_client.js
/hello.json  <-  /src/App.jsx
/hello.json  <-  /src/App.jsx
текст сторінки: привіт
```

Пакети React і React DOM прийшли п'ятьма файлами з теки `.vite/deps`, тобто вже склеєними. Три з них відповідають
тому, що імпортує ваш код: `react`, `react-dom/client` і модуль для JSX, який дописало перетворення (лекція дня 11
показувала виклик `_jsxDEV`). Два файли з набором літер у назві є спільними шматками: стовпчик причини показує, що
`react.js` сам запитав `react-DgVJeC5g.js`. Рядки `/@vite/client`, `/@react-refresh`, `env.mjs` і `WebSocket`
є службовим кодом режиму розробки (лекція, розділ «Чому швидкість не міряють у режимі розробки»). Ваш код,
`main.jsx` і `App.jsx`, прийшов окремими запитами, по одному на файл. У справжньому проєкті таких файлів десятки,
тому в розробці запитів у рази більше, ніж у збірці. Чому `/hello.json` стоїть двічі, пояснено в розділі «Навіщо це
в React» про вкладку Network.

## Документація Chrome DevTools про вкладку Network

Тут дві сторінки: навчальна з покроковими діями й довідкова з усіма можливостями. Почніть із навчальної, а довідкову
використовуйте як пошук.

### Навчальна сторінка `Inspect network activity`

**Де читати:** [developer.chrome.com/docs/devtools/network](https://developer.chrome.com/docs/devtools/network).

**Якщо часу мало,** прочитайте `Log network activity`, `Simulate a slower network connection` і `Inspect a resource's
details`.

- **`When to use the Network panel`.** Ця вкладка потрібна, щоб перевірити, що файли завантажуються як слід, і
  подивитися їхні заголовки, вміст і розмір. Для загальної швидкості завантаження сторінка радить починати з
  Lighthouse, бо багато проблем не пов'язані з мережею. Що таке Lighthouse, пояснює лекція, розділ «Lighthouse і дані
  справжніх користувачів».
- **`Open the Network panel`.** Вкладка порожня, поки ви її не відкрили, бо записує лише те, що сталося при відкритих
  інструментах.
- **`Log network activity`.** Пояснює стовпчики за замовчуванням: Status, Type, Initiator, Size, Time. Більшість із
  них пояснює лекція, розділ «Вкладка Network: один рядок на один запит». Стовпчик Type показує вид ресурсу,
  наприклад документ, скрипт чи стиль. Графік над списком називається Overview. Його можна сховати.
- **`Show more information`.** Правий клік на заголовках таблиці додає стовпчики, наприклад Domain.
- **`Simulate a slower network connection`.** Меню Throttling уповільнює мережу, а довге натискання на кнопку
  перезавантаження дає пункт Empty Cache And Hard Reload, тобто перезавантаження з порожнім кешем. Це імітація нового
  відвідувача.
- **`Capture screenshots`.** Показує вигляд сторінки в різні моменти завантаження, поруч із запитами, що в той час
  тривали.
- **`Inspect a resource's details`.** Клік на рядку відкриває вкладки Headers, Preview, Response, Initiator і Timing.
  Headers містить заголовки запиту й відповіді, тобто службові пари «назва й значення» (лекція дня 6, розділ «Що таке
  запит і відповідь»). Response містить саме тіло відповіді. Кнопка Format у Response робить мінімізований файл
  читабельним.
- **`Search network headers and responses`.** Пошук шукає в заголовках і тілах. Спробуйте знайти `Cache-Control`:
  що означає значення `no-cache` у відповідях сервера розробки, пояснює лекція, розділ «Вкладка Network: один рядок
  на один запит», абзац «Статус 304».
- **`Filter resources`.** Фільтр приймає звичайний текст, регулярний вираз і виключення через мінус, а також
  `domain:...`. Регулярний вираз є шаблоном для пошуку в тексті (лекція дня 3, розділ «Як це проявиться в React»).
  Кнопки над списком залишають лише CSS, JS тощо. Для заміру дня фільтр має стояти на All, щоб у списку й у
  підсумковому рядку були всі запити.
- **`Block requests`.** Блокує вибрані файли. Так зручно перевірити, що станеться, якщо файл не завантажиться.

### Довідкова сторінка `Network features reference`

**Де читати:**
[developer.chrome.com/docs/devtools/network/reference](https://developer.chrome.com/docs/devtools/network/reference).

**Якщо часу мало,** прочитайте `Emulate a first-time visitor by disabling the browser cache`, `View the timing
breakdown of a request`, `View the total size of transferred and loaded resources`, `View the uncompressed size of a
resource` і `Use big request rows`.

Сторінка поділена на великі розділи. Ось що в них важливе для плану.

**`Record network requests`.** `Save requests across page loads` описує галочку Preserve log: вона зберігає запити між
завантаженнями сторінки. Без неї список очищається під час переходу на іншу адресу. `Capture screenshots during page
load` повторює навчальну сторінку.

**`Change loading behavior`.** Тут є найважливіша для сьогодні дія: `Emulate a first-time visitor by disabling the
browser cache`, тобто галочка Disable cache. Поруч розташовано `Emulate offline`, щоб перевірити, що станеться без
мережі, і `Emulate slow network connections` з готовими профілями мережі й власним. Розділ `Override HTTP response
headers` дозволяє підмінити заголовки відповіді сервера просто в браузері. Це знадобиться пізніше для **заголовків
безпеки**, тобто заголовків, якими сервер обмежує браузер. Наприклад, за довідником MDN заголовок
`Content-Security-Policy` каже, з яких адрес сторінці дозволено вантажити скрипти та інші ресурси.

**`Filter requests`.** Пошук за властивостями, наприклад `status-code:404`, і пункти `Hide data URLs` та `Hide
extension URLs`. Другий прибирає запити розширень браузера, які заважають рахувати.

**`Sort requests`.** `Sort by activity phase` у стовпчику Waterfall сортує за вибраним етапом. Так легко знайти,
наприклад, найдовше очікування першого байта.

**`Analyze requests`.** Це головний розділ сторінки.

- `View the timing of requests in relation to one another` описує водоспад: смужки впорядковано за часом початку,
  світліша частина означає очікування, темніша означає завантаження. Як читати сходинки водоспаду, показує дослід із
  каскадом у розділі `The Origins` вище.
- `Analyze the messages of a WebSocket connection` показує, як читати повідомлення WebSocket, тобто постійного
  з'єднання, яким сервер може надсилати повідомлення сам (лекція дня 11, розділ «Гаряча заміна: як змінити код, не
  втративши стан»). На вкладці Messages рядка гарячої заміни Vite ви побачите ті самі повідомлення `update` і
  `full-reload`, які лекція дня 11 отримувала окремим скриптом.

  Ми перевірили, що браузер отримує саме їх. Програма відкрила застосунок React із розділу `Why Vite` у Chrome без
  вікна й друкувала кожне повідомлення, яке сторінка отримала через WebSocket. Тим часом вона дописала коментар у
  `App.jsx`, потім повернула файл, а далі зробила те саме з `main.jsx`:

  ```js
  // файл wsframes.mjs, головні рядки
  chrome.on("Network.webSocketFrameReceived", (p) => console.log("отримано:", p.response.payloadData))
  // ...
  for (const file of ["app/src/App.jsx", "app/src/main.jsx"]) {
    const text = readFileSync(file, "utf8")
    writeFileSync(file, text + "// змінено\n")      // дописуємо коментар, як під час правки
    await wait(1500)
    writeFileSync(file, text)                        // повертаємо файл
    await wait(1500)
  }
  ```

  Chrome 158 без вікна отримав такі повідомлення. Довгий шлях до файла ми скоротили до `…`, а решта рядків справжня:

  ```text
  отримано: {"type":"connected"}
  отримано: {"type":"update","updates":[{"type":"js-update","timestamp":1795405792286,"path":"/src/App.jsx","acceptedPath":"/src/App.jsx","explicitImportRequired":false,"isWithinCircularImport":false}]}
  отримано: {"type":"update","updates":[{"type":"js-update","timestamp":1795405793787,"path":"/src/App.jsx","acceptedPath":"/src/App.jsx","explicitImportRequired":false,"isWithinCircularImport":false}]}
  отримано: {"type":"full-reload","triggeredBy":"…/app/src/main.jsx","path":"*"}
  отримано: {"type":"connected"}
  отримано: {"type":"full-reload","triggeredBy":"…/app/src/main.jsx","path":"*"}
  отримано: {"type":"connected"}
  ```

  Дві правки `App.jsx` дали два повідомлення `update`, і сторінка лишилася тією самою. Дві правки `main.jsx` дали
  `full-reload`, тобто перезавантаження сторінки. Після кожного перезавантаження сторінка заново відкриває з'єднання,
  тому знову приходить `connected`. Чому файли поводяться по-різному, пояснює лекція дня 11, розділ «Гаряча заміна:
  як змінити код, не втративши стан», абзац «Чому файли поводяться по-різному».
- `View the timing breakdown of a request` пояснює етапи одного запиту. Головні з них, а саме чергу, DNS,
  з'єднання, надсилання, очікування першого байта й завантаження тіла, пояснює лекція, розділ «Один запит за
  кроками». Тут лише те, чого в лекції немає.

  **Queueing і Stalled.** Сторінка розрізняє два види очікування. Queueing означає, що запит стоїть у черзі в самому
  браузері ще до початку з'єднання. Stalled означає, що запит затримався з тих самих причин, але вже після початку
  з'єднання. Причин у черги три: є важливіші запити, браузер виділяє місце в дисковому кеші, або з цим сервером уже
  відкрито шість з'єднань. Останнє правило діє лише для HTTP/1.0 і HTTP/1.1. Довідник MDN пояснює його так: у HTTP/1.1
  одне з'єднання передає відповіді по одній, тому браузери відкривають до кожного сайту кілька з'єднань паралельно, і
  зазвичай їх шість.

  Це правило стосується вашого проєкту прямо. Сервер розробки Vite без налаштування `server.https` працює на
  HTTP/1.1: програма відкрила застосунок React вище й надрукувала протокол усіх відповідей, і Chrome 158 без вікна
  показав лише `http/1.1`. Ось що буває, коли `main.js` імпортує дванадцять файлів одразу, а сервер віддає кожен
  файл за 100 мс:

  ```js
  // файл six.mjs, перша половина: сторінки й сервер
  const names = Array.from({ length: 12 }, (_, i) => `m${i + 1}.js`)
  const FILES = {
    "/index.html": '<!doctype html><script type="module" src="/main.js"></script>',
    "/main.js": names.map((n) => `import "./${n}"`).join("\n"),
  }
  const server = createServer(async (req, res) => {
    if (req.url !== "/index.html" && req.url !== "/main.js") await new Promise((r) => setTimeout(r, 100))
    res.writeHead(200, { "Content-Type": req.url.endsWith(".html") ? "text/html" : "text/javascript" })
    res.end(FILES[req.url] ?? "")
  })
  ```

  Друга половина скрипта друкує для кожного файла три моменти: коли браузер поставив запит у чергу, коли справді
  надіслав його серверу й коли отримав відповідь повністю. Ще вона друкує номер з'єднання, яким пройшов запит. Chrome
  158 без вікна надрукував:

  ```text
  /m1.js   у черзі з   35 мс, надіслано   35 мс, готово  138 мс, з'єднання 18
  /m2.js   у черзі з   35 мс, надіслано   37 мс, готово  139 мс, з'єднання 32
  /m3.js   у черзі з   35 мс, надіслано   37 мс, готово  139 мс, з'єднання 38
  /m4.js   у черзі з   35 мс, надіслано   37 мс, готово  139 мс, з'єднання 44
  /m5.js   у черзі з   35 мс, надіслано   38 мс, готово  140 мс, з'єднання 50
  /m6.js   у черзі з   36 мс, надіслано   38 мс, готово  140 мс, з'єднання 56
  /m7.js   у черзі з   36 мс, надіслано  139 мс, готово  239 мс, з'єднання 18
  /m8.js   у черзі з   36 мс, надіслано  139 мс, готово  241 мс, з'єднання 32
  /m9.js   у черзі з   36 мс, надіслано  139 мс, готово  241 мс, з'єднання 38
  /m10.js  у черзі з   36 мс, надіслано  140 мс, готово  241 мс, з'єднання 44
  /m11.js  у черзі з   36 мс, надіслано  140 мс, готово  241 мс, з'єднання 50
  /m12.js  у черзі з   36 мс, надіслано  140 мс, готово  242 мс, з'єднання 56
  ```

  Браузер дізнався про всі дванадцять файлів одночасно, на 35–36 мс. Перші шість пішли одразу, кожен своїм
  з'єднанням. Решта шість чекали близько 100 мс, доки звільниться з'єднання, і пішли тими самими шістьма. Ці 100 мс
  вкладка Timing показала б як Queueing або Stalled. У проєкті з десятками файлів ви побачите в режимі розробки такі
  самі довгі черги, і вони теж є причиною, чому заміри в режимі розробки нічого не кажуть про продакшн.

  **Proxy negotiation** означає, що браузер домовляється з **проксі**, тобто проміжним сервером між вами й сайтом,
  якщо такий налаштовано. **ServiceWorker Preparation** і **Request to ServiceWorker** означають, що браузер запускає
  сервіс-воркер і передає йому запит. Сервіс-воркер, за довідником MDN, є скриптом, що стоїть між сторінкою й мережею,
  як проміжний сервер: він може перехопити запит і, наприклад, віддати відповідь без мережі. У вашому проєкті його
  немає, тому ці рядки будуть порожні.
- `View initiators and dependencies` дуже корисний сьогодні. Утримуючи Shift і наводячи на запит, ви бачите зеленим
  того, хто його спричинив, і червоним тих, кого спричинив він. Так видно дерево імпортів у режимі розробки. Кольорів
  ми не перевіряли, бо їх видно лише в інтерфейсі. Самі зв'язки браузер повідомляє в кожній події запиту: стовпчик
  «причина» в досліді з каскадом надруковано саме з них.
- `View load events` пояснює дві мітки. Довідник MDN уточнює, коли вони настають. Подія `DOMContentLoaded` настає,
  коли браузер розібрав увесь HTML і виконав відкладені скрипти, а скрипти з `type="module"` теж відкладені. Тому в
  досліді з каскадом `DOMContentLoaded` настала на 350 мс, лише після останнього модуля. Картинок і фреймів ця подія
  не чекає. Подія `load` настає, коли завантажилося все, разом зі стилями й картинками. На сторінці Chrome сказано,
  що першу мітку позначено синім, а другу червоним; цього ми не перевіряли.
- `View the total number of requests` і `View the total size of transferred and loaded resources` описують підсумковий
  рядок, з якого ви берете числа. Обидва числа враховують лише запити, записані від часу відкриття інструментів.
- `View the uncompressed size of a resource` пояснює нижнє число в стовпчику Size. Його видно лише тоді, коли
  увімкнено `Big request rows`, тому без цього параметра в кожному рядку є лише одне число. Чим відрізняються два
  розміри, пояснює лекція, розділ «Розмір: скільки передано й скільки розпаковано».

**`Export requests data`.** Файл HAR (HTTP Archive) зберігає весь список запитів разом із заголовками й часом, і ним
зручно ділитися, наприклад, у повідомленні про помилку. За словами сторінки, за замовчуванням із файла прибрано
заголовки `Cookie`, `Set-Cookie` і `Authorization`, бо в них бувають дані входу. Цього ми не перевіряли.

**`Change the layout of the Network panel`.** `Use big request rows` перемикає на високі рядки з двома числами в Time
і Size.

**Навіщо це в React.** Список запитів показує те, чого не видно в коді. Подивіться ще раз на вивід у розділі
`Why Vite`: компонент `App` один раз викликає `fetch("/hello.json")` в ефекті, а в списку два рядки `/hello.json`.
Причина в `StrictMode`: у режимі розробки він навмисно запускає ефект двічі, щоб знайти ефекти без функції очищення
(лекція дня 6, розділ «Як це проявиться в React»). Ту саму сторінку ми зібрали командою `vite build`, відкрили через
`vite preview` і залишили з виводу лише рядки з `hello`. Chrome 158 без вікна надрукував:

```text
/hello.json  <-  /assets/index-BHQomYyD.js
```

У збірці запит один, бо додаткові перевірки `StrictMode` працюють лише в режимі розробки. Тому подвійний запит у
розробці є очікуваним. Якщо ж запит повторюється й у збірці, шукайте помилку у власному коді. Так само в наступних
днях ви дивитиметесь на список, щоб побачити, чи не з'явився каскад і чи справді файл узято з кешу.

## Документація Chrome DevTools про вкладку Performance

### Навчальна сторінка `Analyze runtime performance`

**Де читати:**
[developer.chrome.com/docs/devtools/performance](https://developer.chrome.com/docs/devtools/performance).

**Що це за текст.** Сторінка веде вас через демонстрацію з квадратами, які рухаються. Кроки дня цієї вкладки не
вимагають, але лекція пояснює її, а в наступних фазах вона знадобиться. Читайте, виконуючи кроки на демонстрації.

**Якщо часу мало,** прочитайте `Simulate a mobile CPU`, `Analyze frames per second` і `Find the bottleneck`.

- **`Get started`.** Сторінка радить вікно інкогніто, щоб Chrome працював у чистому стані й розширення не додавали
  шуму.
- **`Simulate a mobile CPU`.** У налаштуваннях запису вибирають `4x slowdown`, і процесор працює вчетверо повільніше.
  Сторінка каже, що дешеві телефони краще відтворює `20x`, але демонстрація з таким уповільненням працює надто погано,
  тому для навчання взято 4x. Отже, число 4 тут є прикладом, а не точним описом середнього телефона. Як поводиться
  уповільнення насправді, показує дослід нижче, у розділі `Throttle the CPU while recording`.
- **`Set up the demo`.** Кнопка Add 10 додає квадрати, доки анімація не почне гальмувати. Кнопка Optimize вмикає
  швидший код.
- **`Record runtime performance`.** Кнопка Record починає запис, Stop завершує його. Кількох секунд досить.
- **`Analyze frames per second`.** FPS означає кількість кадрів на секунду. Що таке кадр, пояснює лекція дня 8,
  розділ «Коли браузер це робить: кадри». Червона смужка над графіком FPS означає, що кадрів стало так мало, що
  користувач це відчуває. Графік CPU, повністю заповнений кольором, означає, що процесор зайнятий на максимумі.
  Наведіть мишу на графіки, щоб побачити знімки екрана в цей момент.
- **`Bonus: Open the FPS meter`.** Показує кількість кадрів наживо поверх сторінки.
- **`Find the bottleneck`.** Це головна частина сторінки. Вкладка Summary показує, на що пішов час. Доріжку Main,
  полум'яний графік і червоний трикутник довгої задачі пояснює лекція, розділ «Вкладка Performance: що робив
  браузер». Клік на смужці веде до рядка коду. У демонстрації причиною гальмування є **примусове компонування**: код
  у кожному кадрі змінює стилі й одразу читає позиції елементів, тому браузер мусить знову й знову рахувати
  компонування. Цей механізм докладно розібрано в лекції дня 8, розділи «Позначка замість негайної роботи» та «Коли
  чергування стає дорогим».
- **`Bonus: Analyze the optimized version`.** Показує, що в кращій версії менше подій і вищий FPS. Сторінка додає, що
  властивості `transform` і `opacity` були б ще кращими, бо їх браузер змінює без компонування. Чому так, пояснює
  лекція дня 8, розділ «Чому `transform` плавніший за `left`».

### Довідкова сторінка `Performance features reference`

**Де читати:**
[developer.chrome.com/docs/devtools/performance/reference](https://developer.chrome.com/docs/devtools/performance/reference).

**Якщо часу мало,** прочитайте `Live metrics screen`, `Record load performance`, `Throttle the CPU while recording` і
`Read the flame chart`.

**`Live metrics screen`.** Щойно ви відкрили вкладку, вона показує три показники Core Web Vitals вашої сторінки: LCP,
CLS та INP. LCP пояснює лекція, розділ «Lighthouse і дані справжніх користувачів», а INP і CLS пояснює лекція дня 8,
розділ «Метрики INP і CLS». Можна підключити польові дані з CrUX, тобто загальнодоступного звіту Chrome про реальних
відвідувачів, і побачити різницю. Для сайту на `localhost` польових даних немає, бо справжніх відвідувачів у нього
немає.

**`Record performance`.** Тут зібрано налаштування запису. Ось короткий підсумок розділів:

| Розділ | Що він дає |
|--------|------------|
| `Record runtime performance` | запис роботи вже завантаженої сторінки, наприклад кліків |
| `Record load performance` | кнопка Record and reload записує завантаження й сама зупиняється невдовзі після нього |
| `Capture screenshots while recording` | знімки кожного кадру |
| `Force garbage collection while recording` | кнопка, яка просить збирач сміття (лекція дня 3) звільнити пам'ять негайно |
| `Disable JavaScript samples` | прибирає стеки викликів (лекція дня 4) із доріжки Main; запис коротший, але менш докладний |
| `Throttle the network while recording` | уповільнення мережі під час запису |
| `Throttle the CPU while recording` | уповільнення процесора |
| `Show Custom Tracks` | вмикає додаткові доріжки, зокрема доріжки React |

У розділі `Throttle the CPU while recording` сказано важливе: уповільнення рахується від можливостей вашого
комп'ютера, тому справді відтворити процесор телефона інструмент не може. Перевіримо це. Програма дала Chrome без
вікна ту саму обчислювальну задачу при уповільненні 1x, 4x і 20x, по три рази для кожного:

```js
// файл throttle.mjs
import { launch } from "./cdp.mjs"

const TASK = `(() => {
  const start = performance.now()
  let sum = 0
  for (let i = 0; i < 20_000_000; i++) sum += i % 7   // фіксований обсяг роботи
  return Math.round(performance.now() - start)
})()`

const chrome = await launch()
await chrome.send("Runtime.evaluate", { expression: TASK })          // розігрів, результат не беремо
for (const rate of [1, 4, 20]) {
  await chrome.send("Emulation.setCPUThrottlingRate", { rate })
  const times = []
  for (let run = 0; run < 3; run++) {
    const { result } = await chrome.send("Runtime.evaluate", { expression: TASK })
    times.push(result.value)
  }
  console.log(`уповільнення ${String(rate).padStart(2)}x: ${times.join(", ")} мс`)
}
await chrome.close()
```

Команда `Runtime.evaluate` виконує рядок `TASK` усередині сторінки так, ніби ви ввели його в консолі. Команда
`Emulation.setCPUThrottlingRate` вмикає уповільнення в задану кількість разів. Що меню CPU у вкладці Performance
користується саме цією командою, ми не перевіряли. Chrome 158 без вікна надрукував:

```text
уповільнення  1x: 31, 31, 31 мс
уповільнення  4x: 146, 126, 143 мс
уповільнення 20x: 654, 644, 630 мс
```

Без уповільнення задача тривала 31 мс, з уповільненням 4x близько 125–146 мс, з 20x близько 640 мс. Отже, Chrome не
підставляє процесор якогось телефона, а розтягує роботу саме вашого комп'ютера. На ноутбуці, де та сама задача
триває 15 мс, уповільнення 4x дасть близько 60 мс, і жоден із цих двох результатів не є «часом на телефоні». Для
кращого наближення до дешевих і середніх телефонів є пункт Calibrate у меню CPU: він вимірює ваш комп'ютер і сам
підбирає числа уповільнення під нього.

**`Analyze a performance recording`.** Це найдовша частина сторінки, читайте її як довідник.

- `Get actionable insights` описує готові поради, які Chrome виводить за записом.
- `View main thread activity` і `Read the flame chart` пояснюють доріжку Main так само, як лекція. Сторінка додає
  кольори: темно-жовтий означає виконання скриптів, фіолетовий означає обчислення стилів і компонування. Кольорів ми
  не перевіряли.
- `Distinguish between first- and third-party events` допомагає відрізнити ваш код, тобто код першої сторони, від
  коду третіх сторін, тобто сторонніх сервісів на кшталт аналітики чи реклами, що вантажаться з чужих адрес.
- `View activities in a table` описує три вкладки. Bottom-Up показує, які дії самі забрали найбільше часу. Call Tree
  показує, які верхні дії спричинили найбільше роботи. Event Log показує дії за порядком. Різниця між першими двома
  тримається на двох числах. **Власний час** (Self Time) функції — це час, коли виконувався код самої функції, а не
  викликаних нею. **Загальний час** (Total Time) — це власний час плюс час усіх функцій, які вона викликала.

  Ось як ці числа отримує браузер. Функція `outer` 30 мс працює сама, а потім викликає `inner`, яка працює ще 70 мс:

  ```js
  // код сторінки з файла selftime.mjs
  function inner() {                      // 70 мс власної роботи
    let x = 0
    const end = Date.now() + 70
    while (Date.now() < end) x++
    return x
  }
  function outer() {                      // 30 мс власної роботи, потім виклик inner
    let x = 0
    const end = Date.now() + 30
    while (Date.now() < end) x++
    return x + inner()
  }
  outer()
  ```

  Програма вмикає **профайлер** процесора, тобто частину браузера, яка кожні 0,1 мс записує, які функції зараз у
  стеку викликів. Такі знімки стека вкладка Performance і називає JavaScript samples (див. таблицю вище). Потім
  програма рахує. Власний час функції складається з тих знімків, де вона стоїть на самому верху стека. Загальний час
  додає ще знімки, де над нею стоять викликані нею функції. Chrome 158 без вікна надрукував:

  ```text
  outer: власний час 30 мс, загальний 97 мс
  inner: власний час 67 мс, загальний 67 мс
  діти outer: inner
  ```

  У `outer` власний час 30 мс, а загальний 97 мс, бо до нього додано час `inner`. Функція `inner` нічого не викликає,
  тому обидва її числа однакові. Замість задуманих 70 мс вийшло 67, бо профайлер бачить роботу лише в моменти своїх
  записів. За описом сторінки Bottom-Up поставив би вгорі `inner`, бо в неї найбільший власний час, а Call Tree
  поставив би вгорі `outer`, бо з неї почалася вся робота.
- `View performance markers` показує вертикальними лініями мітки FCP і LCP, тобто моменти першого вмісту й
  найбільшого елемента (лекція, розділ «Lighthouse і дані справжніх користувачів»). `View custom timings` показує ваші
  власні мітки `performance.mark()` і виміри `performance.measure()`. Виклик `performance.mark()` ставить мітку з
  назвою в момент виклику, а `performance.measure()` рахує час між двома мітками. Ось приклад зі сторінки MDN
  `Performance: measure() method` (код MDN має ліцензію CC0). Рядки з позначкою «Дописано» ми додали, щоб між мітками
  минув час:

  ```js
  performance.mark("login-started")                 // Дописано: початок умовного входу
  setTimeout(() => {                                // Дописано: вхід триває 120 мс
    performance.mark("login-finished")              // Дописано: кінець входу
    // Приклад MDN:
    const loginMeasure = performance.measure(
      "login-duration",
      "login-started",
      "login-finished",
    );
    console.log(loginMeasure.duration);
  }, 120)
  ```

  Програма виконала цей код у сторінці під час запису профілю, а потім надрукувала вивід консолі сторінки й назви
  записів у профілі з групи, де браузер зберігає мітки користувача. Chrome 158 без вікна надрукував:

  ```text
  консоль сторінки: 120.90000000223517
  у профілі є записи: login-started, login-finished, login-duration
  ```

  Вимір тривав трохи більше за 120 мс, бо таймер ніколи не спрацьовує раніше заданого часу. Обидві мітки й вимір
  потрапили в профіль, тобто саме їх DevTools покаже на доріжці Timings. Як вони виглядають на екрані, ми не
  перевіряли.
- `View interactions` і `View layout shifts` показують кліки та стрибки вмісту, тобто те, що стоїть за INP і CLS
  (лекція дня 8, розділ «Метрики INP і CLS»).
- `Analyze frames per second (FPS)` і `View network requests` показують кадри й водоспад прямо в запису. Червоний
  трикутник на запиті в цій доріжці означає, що запит **блокує рендер**: браузер не покаже сторінку, доки цей файл не
  прийде. Так поводиться, наприклад, звичайний скрипт без `async` чи `defer` у `<head>`: розбір HTML зупиняється,
  доки скрипт не завантажиться й не виконається (розбір дня 8, розділ `Parsing`). Стаття web.dev `Optimize Largest
  Contentful Paint` тому й радить майже ніколи не ставити таких скриптів у `<head>`. Значка ми не перевіряли.
- `View the duration of a portion of a recording` дає тривалість виділеного відрізка.

**`Analyze rendering performance with the Rendering tab`.** Вкладка Rendering має FPS-метр і Paint Flashing, який
зеленим підсвічує все, що браузер перемальовує. Кроки від коду до малювання пояснює лекція дня 8, розділ «Чотири кроки
від коду до екрана». Це наочний спосіб побачити зайві перемальовування.

**Навіщо це в React.** У фазі 2 ви записуватимете профіль рендеру з уповільненням процесора, а у фазі 3 шукатимете,
чому сотні повідомлень на секунду не встигають показуватись. React додає до запису власні доріжки, їх описує окрема
сторінка [React Performance tracks](https://react.dev/reference/dev-tools/react-performance-tracks). Доріжка Scheduler
має чотири піддоріжки за пріоритетом роботи: Blocking для термінових оновлень, наприклад після кліку, Transition для
оновлень у `startTransition`, Suspense і Idle. Доріжка Components показує час кожного компонента. За документацією
React, у розробницькій версії ці доріжки ввімкнені, а у звичайній продакшн-збірці вимкнені, бо додають накладні
витрати.

Ми записали профіль завантаження застосунку React із розділу `Why Vite` у режимі розробки й надрукували без повторів
усі записи, які React поклав на свої доріжки. Записи йдуть у форматі «група / доріжка: назва». Chrome 158 без вікна
надрукував:

```text
Scheduler ⚛ / Blocking: Blocking Track
Scheduler ⚛ / Transition: Transition Track
Scheduler ⚛ / Suspense: Suspense Track
Scheduler ⚛ / Idle: Idle Track
Scheduler ⚛ / Blocking: Render
Scheduler ⚛ / Blocking: Commit
Scheduler ⚛ / Blocking: Waiting for Paint
 / Components ⚛: App
Scheduler ⚛ / Blocking: Remaining Effects
усього записів на доріжках React: 26
```

Перші чотири рядки створюють піддоріжки Scheduler. Далі видно, як пройшов перший показ: рендер, коміт, очікування
малювання й решта ефектів, усе з пріоритетом Blocking. Доріжка Components має запис для `App`. Той самий запис для
збірки через `vite preview` надрукував `усього записів на доріжках React: 0`, тобто у звичайній збірці доріжок
немає. Тому ці доріжки показують, що відбувається, а не скільки це триває в продакшні: для заміру без розробницьких
перевірок є окрема збірка для профілювання (лекція, розділ «Як це проявиться в React»).

## How to Design Programs, `3.1 Designing Functions`

**Де читати:** [розділ у книжці](https://htdp.org/2023-8-14/Book/part_one.html#%28part._sec~3adesign-func%29).
Вчорашній розбір уже провів вас кроками рецепта (розбір дня 11, розділ «Кроки рецепта й ваш TypeScript»). Там же
пояснено, що таке заглушка і як книжка радить поводитися, коли приклад не збігся. Тут лише те, що особливо стане в
пригоді сьогодні. Текст книжки розбір лише коротко переказує.

### Опис даних

Перший крок рецепта просить вирішити, що чим буде подано. Сьогодні це незвичне завдання: інформацією стає те, що ви
бачите в браузері, а даними стає об'єкт із числами. Ваше рішення про одиниці важить багато. Кілобайт буває
десятковим, тобто 1000 байтів, а буває двійковим, тобто 1024 байти, і тоді його позначають KiB. Це має бути записано
в описі даних, інакше порівняння двох замірів не матимуть сенсу. Як рахує вкладка Network, ми не перевіряли:
документації Chrome серед наших серверів немає. Звірте самі на одному файлі збірки. Команда `ls -l dist/assets`
друкує його розмір у байтах. Поділіть це число на 1000 і на 1024 і подивіться, який результат збігається з нижнім,
розпакованим числом у стовпчику Size при ввімкнених `Big request rows`.

### Сигнатура, призначення й заголовок

Книжка наполягає, що призначення має коротко відповідати на запитання, що саме обчислює функція. Для функції, яка
рахує відношення двох чисел, корисно записати в призначенні, що на що ділимо. Число запитів у розробці, поділене на
число запитів у збірці, більше за одиницю, а навпаки менше, і без запису легко сплутати одне з другим.

### Приклади

Книжка просить визначити очікуваний результат наперед. Для вимірювань це важливо вдвічі: ви заздалегідь обчислюєте
результат на круглих числах, а не підганяєте його під вивід функції. Також варто взяти приклад на межі, наприклад два
однакові заміри.

### Опис того, що є, код і перевірка

Перелік вхідних даних нагадує, з чого можна рахувати. Тіло функції збирається з цього переліку. Перевірка запускає
приклади через Vitest.

**Навіщо це в React.** Числа зі сторінки стають даними, а висновок стає функцією з прикладами. Такий самий підхід ви
застосуєте до будь-якого показника у фазі 5.

## Перевірте себе

**1. Чому сторінка `Why Vite` каже, що модулі без склеювання неефективні для продакшну, хоч вони такі зручні в
розробці?**

<details><summary>Відповідь</summary>

Кожен вкладений `import` додає ще один обмін, тобто шлях запиту до сервера й відповіді назад. Браузер дізнається про
наступний файл, лише прочитавши попередній, тому запити йдуть каскадом. У досліді з каскадом три сходинки по 100 мс
дали 350 мс до `DOMContentLoaded`, а склеєний файл дав 137 мс. У розробці сервер стоїть на вашому комп'ютері, тому
сходинки короткі й це терпимо, а для користувача на реальній мережі ні.

</details>

**2. Який етап вкладки Timing ви подивитесь, щоб зрозуміти, чи винен сервер?**

<details><summary>Відповідь</summary>

`Waiting (TTFB)`, бо він охоплює обмін із сервером і підготовку відповіді. `Content Download` стосується вже передачі
тіла.

</details>

**3. У стовпчику Size стоїть одне число, а в документації описано два. Що зробити?**

<details><summary>Відповідь</summary>

Увімкнути в налаштуваннях вкладки параметр `Big request rows`. Тоді верхнє число є переданим розміром, а нижнє є
розміром після розпакування.

</details>

**4. Чим Bottom-Up відрізняється від Call Tree?**

<details><summary>Відповідь</summary>

Bottom-Up підсумовує, які дії самі забрали найбільше власного часу, а Call Tree показує, які верхні дії спричинили
найбільше роботи разом із вкладеними. У досліді з `outer` і `inner` Bottom-Up поставив би вгорі `inner` з 67 мс
власного часу, а Call Tree поставив би вгорі `outer` з 97 мс загального.

</details>

**5. Ви вибрали уповільнення 4x і отримали певний час задачі. Чи можна сказати, що саме стільки вона триватиме на
середньому телефоні?**

<details><summary>Відповідь</summary>

Ні. Уповільнення розтягує роботу вашого комп'ютера: у досліді задача на 31 мс при 4x тривала 125–146 мс, а на
швидшому комп'ютері той самий код дасть менше. Справжнього процесора телефона воно не відтворює. Це орієнтир для
порівняння, точніше наближення дає калібрування, а найточніше дає вимір на справжньому пристрої.

</details>

**6. Навіщо шукати запити через Shift і наведення миші у списку Network у режимі розробки?**

<details><summary>Відповідь</summary>

Так видно, який файл спричинив який запит, тобто дерево імпортів. Воно пояснює, чому в розробці запити йдуть каскадом
і звідки береться їхня кількість.

</details>

**7. У режимі розробки рядок модуля має довгий Queueing, хоча сервер відповідає швидко. Що могло статися?**

<details><summary>Відповідь</summary>

Сервер розробки Vite працює на HTTP/1.1, а браузер відкриває до одного сервера лише шість з'єднань. Якщо сторінка
одночасно просить більше шести файлів, решта чекає в черзі браузера, доки звільниться з'єднання. У досліді з
дванадцятьма модулями сьомий і наступні чекали близько 100 мс саме тому.

</details>
