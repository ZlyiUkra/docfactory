## `Your First Component`

**Де читати:** [react.dev/learn/your-first-component](https://react.dev/learn/your-first-component).

**Що це за текст.** Це сторінка команди React, яка вперше показує компонент. Вона коротка, має кілька вбудованих вікон
із кодом, які можна правити просто на сторінці, і завершується вправами.

**Якщо часу мало,** прочитайте `Defining a component` і підрозділ `Nesting and organizing components`, а решту
перегляньте.

### `Components: UI building blocks`

Сторінка нагадує, що тегами HTML на кшталт `<article>`, `<h1>` чи `<ol>` будують будь-яку сторінку в інтернеті. React
дозволяє об'єднати розмітку, стилі й код у власні блоки, які називаються компонентами, і вживати їх як нові теги.
Сторінка показує великий приклад, де `<PageLayout>` містить `<NavigationHeader>`, `<Sidebar />` і `<PageContent>`. Цей
приклад показує лише форму запису: такі компоненти в нього ніде не оголошено.

Незнайомі слова тут такі:

- **UI** (user interface) означає інтерфейс користувача, тобто все, що людина бачить на екрані й чого торкається.
- **Reusable** означає «придатний для повторного вжитку»: написаний один раз компонент стоїть у багатьох місцях.
- **Компонувати** (compose) означає складати більші блоки з менших.

Наприкінці сторінка згадує готові набори компонентів `Chakra UI` і `Material UI`. Вони вам зараз не потрібні.

**Навіщо це вам.** Сьогодні ви складете екран із трьох компонентів, і великий приклад показує, куди цей спосіб веде
надалі.

### `Defining a component`

Сторінка дає таке визначення: компонент React — це функція JavaScript, у яку можна вписати розмітку. Вона показує
функцію `Profile`, яка повертає тег `<img>`, і розбирає її за кроками.

**`Step 1: Export the component`.** Префікс `export default` належить до стандартного JavaScript, а не до React. Він
позначає головну функцію файла, щоб інший файл міг її імпортувати. Механізм ви вже бачили в лекції «Модулі й пакети».

**`Step 2: Define the function`.** Запис `function Profile() { }` оголошує звичайну функцію. Тут стоїть перше з двох
застережень сторінки: назва компонента мусить починатися з великої літери, інакше він не працюватиме. Лекція показує
причину: запис із малої літери компілюється в рядок, а не в посилання на вашу функцію.

**`Step 3: Add markup`.** Функція повертає розмітку, а сам запис називається **JSX**, і докладно його вивчає наступний
день. Розмітку в один рядок можна написати одразу після `return`, а розмітку в кілька рядків треба взяти в круглі
дужки. Тут стоїть друге застереження: без дужок усе, що стоїть у рядках після `return`, буде проігноровано.

Причина в JavaScript, а не в React. Коли після слова `return` стоїть кінець рядка, мова сама ставить там крапку з
комою, і цей механізм називають автоматичною вставкою крапки з комою (automatic semicolon insertion). Функція
завершується, нічого не повернувши. Ось дослід:

```tsx
function Broken() {
  return
    <p>Вітер: 5 м/с</p>
}

test('return', () => {
  console.log('Broken():', Broken())
  const { container } = render(<Broken />)
  console.log('розмітка:', JSON.stringify(container.innerHTML))
})
```

```text
Broken(): undefined
розмітка: ""
```

React мовчить і нічого не показує, бо компонент може нічого не повертати. Помилку знаходить `tsc`:
`error TS2786: 'Broken' cannot be used as a JSX component`, бо ця функція повертає `void`, тобто нічого. Ось тому в
усіх прикладах круглі дужки стоять у тому самому рядку, що й `return`.

**Навіщо це вам.** Цей розділ дає форму, у якій ви сьогодні пишете всі компоненти. Заглушка рецепта `return null` теж
законна: компонент, який повертає `null`, нічого не показує.

### `Using a component`

Сторінка показує компонент `Gallery`, який уживає `Profile` тричі. Для цього вона вперше кладе два компоненти в один
файл.

**`What the browser sees`.** Цей підрозділ пояснює, що означає регістр літер. `<section>` написано з малої літери,
тому React вважає його тегом HTML. `<Profile />` написано з великої літери, тому React шукає функцію `Profile`.
Браузер отримує вже звичайний HTML, де всередині `<section>` стоять заголовок і три теги `<img>`. Слова «компонент»
браузер не знає зовсім.

**`Nesting and organizing components`.** Цей підрозділ головний для вашого дня. Він вводить слова **батько** (parent)
і **дитина** (child): `Gallery` тут батько, а `Profile` тут дитина, і її можна вжити скільки завгодно разів. Далі
стоїть застереження: компоненти можуть показувати інші компоненти, але їхні оголошення вкладати не можна. Сторінка дає
два короткі фрагменти, неправильний із функцією `Profile` усередині `Gallery` і правильний, де обидві функції стоять
на верхньому рівні файла.

Сторінка лише каже, що вкладене оголошення дуже повільне й породжує помилки, і не пояснює чому. Пояснення лежить в
іншій главі, `Preserving and Resetting State`, а лекція цього дня переказує його докладно. Там само сторінка радить:
якщо дитині потрібні дані батька, передайте їх пропсами. Це та сама порада, яку дає сторінка лінтера для правила
`static-components`.

**Навіщо це вам.** Навмисна помилка в практиці дня порушує саме це застереження, тому прочитайте цей підрозділ до неї.

### `Components all the way down`

Це згорнутий блок із додатковою думкою, англійською такий блок документація називає deep dive. Вираз у заголовку
означає, що компоненти стоять на всіх рівнях застосунку, від кнопки до цілої сторінки. Блок повідомляє чотири речі:

- Застосунок починається з **кореневого компонента** (root). Деякі інструменти створюють його самі.
- Більшість застосунків складаються з компонентів на всіх рівнях, навіть якщо компонент уживається лише один раз.
- Фреймворки на React можуть заздалегідь створити HTML із компонентів на сервері, щоб текст з'явився ще до
  завантаження JavaScript. Цю тему ви зустрінете набагато пізніше в плані.
- Деякі сайти вживають React лише для окремих частин наявної сторінки, і тоді коренів кілька.

Ваш проєкт належить до першого випадку: шаблон Vite створив файл `src/App.tsx`, і `App` у ньому є кореневим
компонентом.

### `Recap` і `Challenges`

`Recap` у кінці сторінки стисло повторює головне: компонент відрізняється від звичайної функції двома рисами, назвою з
великої літери й тим, що повертає розмітку. Далі йдуть чотири вправи, які варто зробити просто на сторінці, бо вони
займають кілька хвилин:

| Вправа | Що вона тренує |
|--------|----------------|
| `Export the component` | компонент без `export` не видно ззовні |

## `Importing and Exporting Components`

**Де читати:**
[react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components).

**Що це за текст.** Ця сторінка продовжує попередню. Вона бере ті самі компоненти `Profile` і `Gallery` та рознімає їх
по файлах.

**Якщо часу мало,** прочитайте таблицю в `Default vs named exports` і розділ
`Exporting and importing multiple components from the same file`.

### `The root component file`

Сторінка називає файл із кореневим компонентом **root component file**. У прикладах це `App.js`, а у вас це
`src/App.tsx`. Сторінка застерігає, що розташування залежить від інструмента, а у фреймворках із маршрутами за файлами
кореневий компонент має кожна сторінка.

### `Exporting and importing a component`

Сторінка описує три кроки: створити новий файл, експортувати компонент і імпортувати його там, де він потрібен.
Приклад переносить `Profile` і `Gallery` у файл `Gallery.js`. `Gallery` стає типовим експортом, а `Profile` лишається
без `export`, тому цей компонент видно лише в цьому файлі.

Поруч стоїть примітка про розширення: документація пише то `'./Gallery.js'`, то `'./Gallery'`, і обидва записи
працюють у React-проєктах. Перший ближчий до того, як працюють модулі в самому браузері. Лекція «Модулі й пакети»
пояснювала, що дописує пропущене розширення саме Vite. У вашому проєкті шукайте файли `.tsx`, а в імпорті розширення
не пишіть, як у заготовках дня.

### `Default vs named exports`

Це розгорнутий блок і головна таблиця сторінки. Там сказано, що файл може мати щонайбільше один типовий експорт і
скільки завгодно іменованих, а вид експорту визначає, як імпортувати. Переказуємо таблицю прикладом на іншому об'єкті:

| Вид | Експорт | Імпорт |
|-----|---------|--------|
| типовий | `export default function Title() {}` | `import Title from './Title'` |
| іменований | `export function Note() {}` | `import { Note } from './Note'` |

Сторінка додає три думки:

- **Типовий імпорт можна назвати як завгодно.** Запис `import Banana from './Button.js'` дасть той самий типовий
  експорт. Іменований імпорт мусить збігатися за назвою.
- **Є поширена домовленість.** Якщо файл віддає один компонент, беруть типовий експорт. Якщо компонентів чи значень
  кілька, беруть іменовані.
- **Не залишайте компонент без імені.** Сторінка не радить запис `export default () => {}`, бо він ускладнює пошук
  помилок. Ось чому: така функція отримує ім'я `default`, і ми це перевірили в Node, де `name` такої функції дав
  `"default"`.

Тут варто бути уважним до одного речення. Сторінка каже, що запис імпорту не того виду дасть помилку. Це правда не
завжди. Якщо у файлі є і типовий експорт, і потрібний вам іменований, а ви написали типовий імпорт, помилки не буде:
ви просто отримаєте інший компонент. Лекція показує цей випадок із `Title` і `Note`.

### `Exporting and importing multiple components from the same file`

Коли файл має віддати ще один компонент, він уже не може бути типовим, бо типовий один. Сторінка робить `Profile`
іменованим експортом поруч із типовим `Gallery`, а потім показує два рядки імпорту: окремо типовий, окремо іменований.
Обидва можна написати й одним рядком, `import Gallery, { Profile } from './Gallery.js'`. Сторінка цього не показує,
але це звичайний запис мови, який уже стояв у лекції «Модулі й пакети».

Поруч є примітка, що частина команд вибирає лише один вид експорту чи не змішує їх в одному файлі, і що вибирати вам.
У вашому завданні `Header` і `List` типові, а `Card` іменований, щоб ви один раз написали обидва варіанти. Це
навчальний вибір, а не правило.

### `Recap` і `Challenges`

`Recap` перелічує головні тези сторінки. Єдина вправа, `Split the components further`, просить винести `Profile` в
окремий файл і зробити це двічі: один раз з іменованим експортом, другий раз із типовим. Це хороша розминка перед тим,
як розкладати компоненти дня по файлах, бо вправа дає ту саму дію на чужому прикладі.

**Навіщо це вам.** Практика дня розкладає три компоненти по трьох файлах. Заготовка `List.tsx` залишає вам написати
рядок імпорту для `Card` самостійно, тому перед цим рядком перевірте вид експорту в `Card.tsx`.

## `Queries: About` у Testing Library

**Де читати:** [testing-library.com/docs/queries/about](https://testing-library.com/docs/queries/about). Сервер цього
матеріалу — `testing-library-docs`.

**Що це за текст.** Testing Library — це бібліотека, яка шукає елементи на сторінці так, як їх знаходить людина: за
написом, роллю, підписом поля. Вона існує для того, щоб тест не залежав від класів і внутрішньої будови компонента.
Запит (query) — це її функція, яка знаходить елемент. Ви поставили цю бібліотеку в день 11 фази 0.

**Якщо часу мало,** прочитайте таблицю в `Types of Queries` і список у `Priority`.

Приклади нижче працюють на такому екрані:

```tsx
function Reading({ label, value }: { label: string; value: string }) {
  return <p>{label}: {value}</p>
}
function Station({ city, wind }: { city: string; wind: number }) {
  return <section aria-label={city}><h2>{city}</h2><Reading label="Вітер" value={`${wind} м/с`} /></section>
}
function Page() {
  return <div><h1>Погода</h1><Station city="Львів" wind={5} /><Station city="Одеса" wind={9} /></div>
}
```

### `Types of Queries`

Назва запиту складається з двох частин. Перша частина каже, що робити, якщо знайдено не один елемент, а друга каже, за
чим шукати: `ByRole`, `ByText`, `ByLabelText` тощо. Ось переказ головної таблиці сторінки:

| Початок назви | Нічого не знайдено | Один елемент | Кілька елементів | Чекає появи |
|---------------|--------------------|--------------|------------------|-------------|
| `getBy` | кидає помилку | повертає його | кидає помилку | ні |
| `queryBy` | повертає `null` | повертає його | кидає помилку | ні |
| `findBy` | відхиляє проміс | виконує проміс цим елементом | відхиляє проміс | так, до 1000 мс |
| `getAllBy` | кидає помилку | масив з одного | масив | ні |
| `queryAllBy` | порожній масив | масив з одного | масив | ні |
| `findAllBy` | відхиляє проміс | масив з одного | масив | так, до 1000 мс |

Як вибрати. Беріть `getBy`, коли елемент має бути на сторінці, бо помилка одразу покаже, чого бракує. Беріть
`queryBy`, лише коли перевіряєте, що елемента **немає**, бо він не кидає помилки. Варіант `findBy` потрібен тоді, коли
елемент з'явиться пізніше, наприклад після запиту до сервера, і це тема наступних днів. Ось дослід на нашому екрані:

```tsx
console.log(screen.getAllByRole('heading', { level: 2 }).map((h) => h.textContent))
console.log(screen.queryByRole('heading', { name: 'Київ' }))
console.log(screen.getAllByText(/^Вітер/).length)
```

```text
[ 'Львів', 'Одеса' ]
null
2
```

А ось дві типові помилки `getBy`. Перший рядок ми отримали, коли на сторінці було два вузли, що підходять, а другий,
коли не було жодного:

```text
Found multiple elements with the text: /^Вітер/
Unable to find an accessible element with the role "heading" and name "Київ"
```

Під таким повідомленням бібліотека ще друкує знімок розмітки сторінки. Прочитайте його першим: він показує, що
насправді є на сторінці.

### `Priority`

Цей розділ каже, який запит вибрати, якщо підходять кілька. Порядок відбиває те, як сторінку сприймає людина, зокрема
людина з екранним читачем, тобто програмою, яка промовляє вміст сторінки вголос.

| Група | Запити | Коли брати |
|-------|--------|------------|
| доступні всім | `getByRole` | перший вибір, майже для всього |
| | `getByLabelText` | поля форми з підписом |
| | `getByPlaceholderText` | лише якщо підпису немає, бо підказка в полі його не замінює |
| | `getByText` | звичайний текст поза формами |
| | `getByDisplayValue` | поле, де вже введено значення |
| семантичні | `getByAltText`, `getByTitle` | зображення з `alt`; атрибут `title` екранні читачі читають не завжди |
| тестові ідентифікатори | `getByTestId` | лише тоді, коли нічого іншого не підходить |

Тому в заготовках дня стоять `getByRole` і `getByText`, а не пошук за класом.

### `Using Queries`

Цей розділ пояснює, звідки запит знає, де шукати. Базова версія запиту вимагає першим аргументом вузол. Зручна версія
вже прив'язана до `document.body` і лежить в об'єкті **`screen`**. Сторінка радить брати саме його, тому в заготовках
ви всюди бачите `screen.getByRole(...)`. Підрозділ `queryOptions` пояснює другий аргумент, об'єкт із налаштуваннями
пошуку, наприклад `{ level: 1 }`.

`screen` працює лише там, де є глобальний `document`. У вашому проєкті це забезпечує `environment: 'jsdom'` у
налаштуваннях Vitest, про які йшлося в день 11 фази 0.

### `getByRole`, `level` і `name`

Цього запиту докладно немає на сторінці `About`. Він описаний на сусідній сторінці
[`ByRole`](https://testing-library.com/docs/queries/byrole), а план згадує його окремо, тому пояснюємо його тут.

**Роль** (role) — це те, чим елемент є для програм, які читають сторінку за людину: кнопка, заголовок, список. Багато
тегів мають роль без жодного атрибута, і таку роль називають неявною (implicit). Ось що ми отримали у своєму досліді в
jsdom:

| Тег | Роль |
|-----|------|
| `<h1>`…`<h6>` | `heading` |
| `<button>` | `button` |
| `<ul>`, `<li>` | `list`, `listitem` |
| `<main>` | `main` |
| `<article>` | `article` |
| `<header>` | `banner` |
| `<input>` | `textbox` |
| `<section aria-label="Одеса">` | `region` |
| `<section>` без підпису | ролі немає |

Останній рядок важливий: той самий тег отримує роль лише тоді, коли має ім'я. Поруч стоять два налаштування, які
потрібні вам сьогодні:

- **`level`** працює лише з роллю `heading` і вибирає рівень заголовка. Запит `getByRole('heading', { level: 3 })`
  шукає `<h3>`. З іншою роллю це налаштування кидає помилку.
- **`name`** шукає за **доступним іменем** (accessible name), тобто текстом, який елемент називає програмі для
  читання. У простому випадку це текст усередині кнопки чи заголовка, значення `aria-label` або підпис поля.

```tsx
console.log(screen.getByRole('heading', { level: 1 }).textContent)
console.log(screen.getByRole('heading', { name: 'Одеса' }).nodeName)
```

```text
Погода
H2
```

### `within`

Функції `within` теж присвячена окрема сторінка,
[`within`](https://testing-library.com/docs/dom-testing-library/api-within), а на `About` вона лише згадана. Вона бере
вузол і повертає ті самі запити, але обмежені цим вузлом. Вона потрібна тоді, коли той самий текст є в кількох місцях
і важливо, у якому саме.

```tsx
const odesa = screen.getByRole('region', { name: 'Одеса' })
console.log(within(odesa).getByText('Вітер: 9 м/с').nodeName)
```

```text
P
```

### `TextMatch`

Більшість запитів приймають рядок, регулярний вираз або функцію. Таке значення сторінка називає `TextMatch`. Рядок за
замовчуванням має збігтися **повністю** й з урахуванням регістру, тому `getByText('Вітер')` не знайде абзац
`Вітер: 5 м/с`. Регулярний вираз `/^Вітер/` його знайде.

Підрозділ `Precision` описує налаштування `exact: false`, яке дозволяє шукати частину рядка без урахування регістру.
Сторінка натякає, що для нечіткого пошуку регулярний вираз часто кращий. Підрозділ `Normalization` повідомляє, що
перед порівнянням бібліотека обрізає пробіли на краях і замінює кілька пробілів поспіль одним. Тому зайві пробіли в
розмітці не заважають.

Є важлива межа: `getByText` порівнює текст одного вузла. Якщо частину тексту обгорнуто в окремий тег, наприклад
`<p><b>Вітер:</b> 5 м/с</p>`, то рядок `'Вітер: 5 м/с'` не знайдеться, і повідомлення про помилку прямо каже, що
текст, можливо, розбито на кілька елементів.

### `Manual Queries`, `Browser extension` і `Playground`

`Manual Queries` каже, що можна вжити звичайний `querySelector`, але радить цього уникати, бо класів та
ідентифікаторів користувач не бачить. Останні два розділи описують розширення для браузера й пісочницю, у якій можна
підбирати запити на власному HTML. Вони вам не обов'язкові.

**Навіщо це вам.** Рецепт просить приклади до тіла, а приклад для компонента складається саме з таких запитів.
Заготовка `examples.test.tsx` дає вам кілька готових прикладів і лишає написати решту.

**Що це за текст.** Це книжка How to Design Programs, друге видання, авторів Matthias Felleisen, Robert Bruce Findler,
Matthew Flatt і Shriram Krishnamurthi, видавництва MIT Press, 2018 року. Її приклади написано навчальною мовою BSL,

**Якщо часу мало,** цей розділ ви вже читали у фазі 0, тому перечитайте лише `The Design Process` і зверніть увагу на
таблицю нижче.

### `Information and Data`

Програма отримує інформацію зі світу й видає нову. Щоб працювати з інформацією, вона подає її даними мови
програмування. Книжка показує, що число 42 саме по собі нічого не означає: воно може бути кількістю пікселів,
температурою чи кількістю символів. Тому програміст записує в коментарі **опис даних** (data definition): як
називається цей набір даних і що означає кожне значення.

Для компонента цю роботу робить тип пропсів, а значення полів пояснює коментар. Приклад із заготовок дня: коментар над
типом `Coin` пояснює, що `id` — це число, за яким React розрізняє елементи списку.

### `The Design Process`

Книжка пропонує кроки в певному порядку.

| Крок у книжці | Що він просить | Що це для компонента |
|---------------|----------------|----------------------|
| подати інформацію даними | записати опис даних | тип пропсів, наприклад `type ReadingProps` |
| сигнатура, призначення, заголовок | сказати, що функція отримує й повертає; одним реченням сказати, що вона робить; написати заглушку | параметр із типом у коді, коментар над функцією, тіло `return null` |
| приклади | вибрати вхідні дані й наперед визначити результат | файл тестів, де `render` показує компонент, а запит шукає очікуваний вміст |
| опис того, що є | перелічити, з яких даних треба будувати результат | коментар із переліком пропсів у тілі |
| код | замінити заглушку | розмітка в `return` |
| перевірка | запустити приклади | `npx vitest run` |

Головні думки розділу такі. Призначення має бути настільки коротким і точним, щоб читачеві не довелося читати саму
функцію. Заглушка дозволяє запустити приклади до написання коду, і вони мають упасти.

Коли результат не збігся, книжка радить не поспішати. Можливі три варіанти: неправильно обчислено очікуваний
результат, неправильний код або помилка і там, і там. Спершу перевірте очікуваний результат, а вже потім правте
функцію. На сторінці дня є окрема пастка саме про такий випадок, де приклад шукає заголовок не того рівня, а компонент
правильний.

**Навіщо це вам.** Файл `recipe.test.tsx` перевіряє рецепт автоматично: він шукає коментар із призначенням над кожним
компонентом і рахує ваші приклади. Рецепт не змінився, змінилося лише те, як виглядає приклад.

## Перевірте себе

**1. Що станеться, якщо після `return` розмітка стоїть у наступному рядку без дужок?**

<details><summary>Відповідь</summary>

JavaScript сам поставить крапку з комою після `return`, і функція поверне `undefined`. React нічого не покаже й не
повідомить про помилку. `tsc` скаже, що таку функцію не можна вживати як компонент.

</details>

**2. Сторінка `Your First Component` каже, що оголошення компонента всередині іншого компонента повільне й веде до
помилок. Де шукати причину?**

<details><summary>Відповідь</summary>

У главі `Preserving and Resetting State`, у розділі `Different components at the same position reset state`, а також у
лекції цього дня. Причина в тому, що при кожному рендері батька створюється нова функція, тобто новий тип на тому
самому місці, і React замінює старий екземпляр новим.

</details>

**3. Файл має `export default function Gallery` і `export function Profile`. Як отримати обидва в одному рядку
імпорту?**

<details><summary>Відповідь</summary>

`import Gallery, { Profile } from './Gallery'`. Типовий експорт стоїть без дужок і першим, а іменований стоїть у
дужках.

</details>

**4. Яким запитом перевірити, що заголовка на сторінці немає, і чому не `getByRole`?**

<details><summary>Відповідь</summary>

`queryByRole`. Він повертає `null`, якщо елемента немає, і цей результат можна перевірити. `getByRole` у цьому випадку
кине помилку, і тест упаде ще до перевірки.

</details>

**5. Чому `getByText('Вітер')` не знаходить абзац `Вітер: 5 м/с`?**

<details><summary>Відповідь</summary>

Рядок за замовчуванням має збігтися повністю. Щоб знайти частину тексту, беруть регулярний вираз `/^Вітер/` або
налаштування `exact: false`.

</details>

**6. Який запит сторінка `Priority` радить першим і чому?**

<details><summary>Відповідь</summary>

`getByRole`. Він шукає так, як сторінку сприймає людина, зокрема через екранний читач. Такий тест перевіряє ще й те,
що елементи мають правильні ролі, і він не ламається, коли змінюються класи.

</details>
