### `Components: UI building blocks`

Сторінка нагадує, що тегами HTML на кшталт `<article>`, `<h1>` чи `<ol>` будують будь-яку сторінку в інтернеті. React
дозволяє об'єднати розмітку, стилі й код у власні блоки, які називаються компонентами, і вживати їх як нові теги. Ось
великий приклад сторінки: так, за її словами, побудовано саму документацію.

```js
<PageLayout>
  <NavigationHeader>
    <SearchBar />
    <Link to="/docs">Docs</Link>
  </NavigationHeader>
  <Sidebar />
  <PageContent>
    <TableOfContents />
    <DocumentationText />
  </PageContent>
</PageLayout>
```

Код зі сторінки react.dev `Your First Component`, розділ `Components: UI building blocks`.

Цей фрагмент не запускається, бо жоден із цих компонентів на сторінці не оголошено. Він показує лише форму запису:
компоненти вкладаються один в одного так само, як теги HTML. Наприклад, `<PageLayout>` охоплює весь макет сторінки, а
всередині нього стоять шапка `<NavigationHeader>`, бічна панель `<Sidebar />` і вміст `<PageContent>`.

Незнайомі слова тут такі:

- **UI** (user interface) означає інтерфейс користувача, тобто все, що людина бачить на екрані й чого торкається.
- **Reusable** означає «придатний для повторного вжитку»: компонент пишуть один раз, а вживають у багатьох місцях.
- **Compose** означає складати більші блоки з менших.

Наприкінці цього розділу сторінка згадує `Chakra UI` і `Material UI`. Це готові набори компонентів, тобто бібліотеки з
кнопками, вікнами й полями, які написали інші люди. Вони вам зараз не потрібні.

**Навіщо це вам.** Сьогодні ви складете екран `Screen` із шапки, списку й картки. Великий приклад показує, що так само
складаються й цілі сторінки.

### `Defining a component`

Сторінка дає таке визначення: компонент React — це функція JavaScript, у яку можна вписати розмітку. Ось її приклад:

```js
export default function Profile() {
  return (
    <img
      src="https://react.dev/images/docs/scientists/MK3eW3Am.jpg"
      alt="Katherine Johnson"
    />
  )
}
```

Код зі сторінки react.dev `Your First Component`, розділ `Defining a component`.

Тег `<img>` показує картинку. Атрибут `src` каже, звідки її завантажити, а атрибут `alt` дає текстовий опис картинки
для тих, хто її не бачить. Далі сторінка розбирає цей код за трьома кроками.

**`Step 1: Export the component`.** Префікс `export default` належить до стандартного JavaScript, а не до React. Він
позначає головну функцію файла, щоб інший файл міг її імпортувати. Цей механізм пояснює лекція дня 4 фази 0 «Модулі
й пакети», підрозділ «Типовий експорт».

**`Step 2: Define the function`.** Запис `function Profile() { }` оголошує звичайну функцію. Тут стоїть перше з двох
застережень сторінки: назва компонента мусить починатися з великої літери, інакше він не працюватиме. Сторінка не
пояснює чому, а лекція цього дня пояснює це в розділі «Велика літера вирішує, що це»: запис із малої літери компілятор
JSX перетворює на рядок із назвою тега, а не на посилання на вашу функцію.

**`Step 3: Add markup`.** Функція повертає розмітку. Запис розмітки всередині JavaScript називається **JSX**, і
докладно його вивчає наступний день. Сторінка показує два правильні способи записати `return`. Розмітку в один рядок
пишуть одразу після слова `return`. Розмітку в кілька рядків беруть у круглі дужки, і відкривна дужка стоїть у тому
самому рядку, що й `return`:

```js
return <img src="https://react.dev/images/docs/scientists/MK3eW3As.jpg" alt="Katherine Johnson" />;
```

```js
return (
  <div>
    <img src="https://react.dev/images/docs/scientists/MK3eW3As.jpg" alt="Katherine Johnson" />
  </div>
);
```

Код зі сторінки react.dev `Your First Component`, розділ `Step 3: Add markup`.

Тут стоїть друге застереження: без дужок усе, що стоїть у рядках після `return`, буде проігноровано.

Причина в JavaScript, а не в React. Якщо крапку з комою в кінці інструкції пропущено, JavaScript у багатьох місцях
ставить її сам. Цей механізм називають автоматичною вставкою крапки з комою (automatic semicolon insertion). Для
`return` правило суворе: між словом `return` і значенням, яке він повертає, не можна переносити рядок. Тому коли після
`return` стоїть кінець рядка, мова ставить крапку з комою одразу після `return`. Функція завершується й повертає
`undefined`, а розмітка в наступному рядку вже ніколи не виконується. Перевіримо це файлом `src/broken.test.tsx`:

```tsx
import { render } from '@testing-library/react'
import { test } from 'vitest'

function Broken() {
  return
    <p>Вітер: 5 м/с</p>
}

test('return', () => {
  console.log('Broken():', Broken())
  const { container } = render(<Broken />)
  console.log('розмітка:', JSON.stringify(container.innerHTML))
})
```

```text
Broken(): undefined
розмітка: ""
```

Перший рядок виводу показує, що сама функція повернула `undefined`. У другому рядку `container` — це порожній блок
`<div>`, у який `render` показує компонент, а `innerHTML` дає розмітку всередині нього. Розмітка порожня, отже,
React нічого не поставив у документ. При цьому React не кинув помилки й нічого не надрукував у консоль. Починаючи з
React 18, компонент має право повернути `undefined`, і це означає «нічого не показувати». Про це пише журнал змін
React 18, і там же радять ловити забутий `return` лінтером.

Тест проходить, тому помилку видно лише в TypeScript. Команда `npx tsc --noEmit -p tsconfig.app.json` друкує:

```text
src/broken.test.tsx(11,33): error TS2786: 'Broken' cannot be used as a JSX component.
  Its type '() => void' is not a valid JSX element type.
    Type '() => void' is not assignable to type '(props: any) => ReactNode | Promise<ReactNode>'.
      Type 'void' is not assignable to type 'ReactNode | Promise<ReactNode>'.
```

Тип `void` означає, що функція нічого не повертає. Типи React описують, що компонент мусить повертати: розмітку,
рядок, `null` тощо, і цей перелік у них називається `ReactNode`. Тип `void` у цей перелік не входить, хоча під час
запуску React приймає `undefined`. Тому TypeScript не дозволяє вжити `Broken` як тег у рядку 11. Лінтер за
налаштуваннями шаблону про цей файл не каже нічого. Правило `no-unreachable`, яке шукає код після `return`, пресет
для TypeScript вимикає, бо покладає таку перевірку на сам TypeScript. Тому в усіх прикладах відкривна кругла дужка
стоїть у тому самому рядку, що й `return`.

**Навіщо це вам.** Цей розділ дає форму, у якій ви сьогодні пишете всі компоненти. Заглушка рецепта `return null` у
заготовках дня теж допустима: компонент, який повертає `null`, нічого не показує, і TypeScript такий запис пропускає.

### `Using a component`

Сторінка показує компонент `Gallery`, який уживає `Profile` тричі. Для цього вона вперше кладе два компоненти в один
файл:

```js
function Profile() {
  return (
    <img
      src="https://react.dev/images/docs/scientists/MK3eW3As.jpg"
      alt="Katherine Johnson"
    />
  );
}

export default function Gallery() {
  return (
    <section>
      <h1>Amazing scientists</h1>
      <Profile />
      <Profile />
      <Profile />
    </section>
  );
}
```

Код зі сторінки react.dev `Your First Component`, розділ `Using a component`.

**`What the browser sees`.** Цей підрозділ пояснює, що означає регістр літер. `<section>` написано з малої літери,
тому React вважає його тегом HTML. `<Profile />` написано з великої літери, тому React шукає функцію `Profile`. У
документ потрапляє вже звичайний HTML, де всередині `<section>` стоять заголовок і три теги `<img>`, а слова
«компонент» там немає зовсім. Ми показали той самий код у Vitest і надрукували розмітку, яку React поставив у
документ. Щоб кожен тег стояв в окремому рядку, тест друкує `container.innerHTML.replaceAll('><', '>\n<')`:

```text
<section>
<h1>Amazing scientists</h1>
<img alt="Katherine Johnson" src="https://react.dev/images/docs/scientists/MK3eW3As.jpg">
<img alt="Katherine Johnson" src="https://react.dev/images/docs/scientists/MK3eW3As.jpg">
<img alt="Katherine Johnson" src="https://react.dev/images/docs/scientists/MK3eW3As.jpg">
</section>
```

Вивід збігається з тим, що показує сторінка. Різниця лише в порядку атрибутів і в тому, що `<img>` надруковано без
скісної риски в кінці: у HTML вона для цього тега не потрібна.

**`Nesting and organizing components`.** Цей підрозділ головний для вашого дня. Він вводить слова **батько** (parent)
і **дитина** (child): `Gallery` тут батько, а `Profile` тут дитина, і її можна вжити скільки завгодно разів. Далі
стоїть застереження: компоненти можуть показувати інші компоненти, але їхні оголошення вкладати не можна. Сторінка дає
два короткі фрагменти. Перший неправильний, бо функцію `Profile` оголошено всередині `Gallery`:

```js
export default function Gallery() {
  // 🔴 Never define a component inside another component!
  function Profile() {
    // ...
  }
  // ...
}
```

Другий правильний, бо обидві функції стоять на верхньому рівні файла:

```js
export default function Gallery() {
  // ...
}

// ✅ Declare components at the top level
function Profile() {
  // ...
}
```

Код зі сторінки react.dev `Your First Component`, розділ `Nesting and organizing components`.

Сторінка лише каже, що перший варіант дуже повільний і породжує помилки, і не пояснює чому. Пояснення лежить в іншій
главі, `Preserving and Resetting State`, а лекція цього дня переказує його в розділі «Компонент усередині
компонента». Там само сторінка радить: якщо дитині потрібні дані батька, передайте їх пропсами. Ту саму пораду дає
сторінка правила лінтера `static-components`, яке ловить цю помилку (лекція, розділ «Хто ловить цю помилку»).

**Навіщо це вам.** Навмисна помилка в практиці дня порушує саме це застереження, тому прочитайте цей підрозділ до неї.

### `Components all the way down`

Це згорнутий блок із додатковою думкою, і документація називає такі блоки deep dive. Щоб його прочитати, на нього
треба клацнути. Вираз у заголовку означає, що компоненти стоять на всіх рівнях застосунку, від кнопки до цілої
сторінки. Блок повідомляє чотири речі:

- Застосунок починається з **кореневого компонента** (root). Зазвичай його створює сам інструмент, яким ви почали
  проєкт. Сторінка наводить приклад фреймворку Next.js, де кореневий компонент лежить у файлі `pages/index.js`.
  Фреймворком називають готовий каркас застосунку, який, крім React, бере на себе ще й адреси сторінок і збирання.
- Більшість застосунків складаються з компонентів на всіх рівнях, навіть якщо компонент уживається лише один раз.
- Фреймворки на React ще й самі будують HTML із ваших компонентів, тому частина сторінки з'являється ще до того, як
  завантажиться JavaScript. Цю тему ви зустрінете набагато пізніше в плані.
- Деякі сайти вживають React лише для окремих частин наявної сторінки, і тоді коренів кілька.

Ваш проєкт має один корінь: шаблон Vite створив файл `src/App.tsx`, і `App` у ньому є кореневим компонентом. Файл
`src/main.tsx` просить React показати `App` на сторінці.

## `Importing and Exporting Components`

**Де читати:**
[react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components).

**Що це за текст.** Ця сторінка продовжує попередню. Вона бере ті самі компоненти `Profile` і `Gallery` та розкладає
їх по файлах.

**Якщо часу мало,** прочитайте таблицю в `Default vs named exports` і розділ
`Exporting and importing multiple components from the same file`.

### `The root component file`

Сторінка називає файл із кореневим компонентом **root component file**. У прикладах це `App.js`, а у вас це
`src/App.tsx`. Сторінка застерігає, що розташування цього файла залежить від інструмента.

Далі вона згадує фреймворки з маршрутами за файлами. **Маршрутом** називають відповідність між адресою в рядку
браузера й екраном, який за цією адресою показують. Деякі фреймворки, наприклад Next.js, будують маршрути з файлів:
кожен файл у спеціальній теці стає окремою сторінкою зі своєю адресою. Тоді кореневий компонент має кожна така
сторінка.

### `Exporting and importing a component`

Сторінка описує три кроки: створити новий файл, експортувати з нього компонент і імпортувати його там, де він
потрібен. Приклад переносить `Profile` і `Gallery` у файл `Gallery.js`, а в `App.js` лишається лише імпорт:

```js
import Gallery from './Gallery.js';

export default function App() {
  return (
    <Gallery />
  );
}
```

Код зі сторінки react.dev `Importing and Exporting Components`, розділ `Exporting and importing a component`.

У файлі `Gallery.js` функція `Gallery` має `export default`, тобто це типовий експорт. Функція `Profile` лишається без
`export`, тому цей компонент видно лише всередині `Gallery.js`.

Поруч стоїть примітка про розширення: документація пише то `'./Gallery.js'`, то `'./Gallery'`, і обидва записи
працюють у React-проєктах. Перший запис ближчий до того, як працюють модулі в самому браузері: без Vite браузер
запитує в сервера точну адресу файла й сам розширення не дописує. Лекція дня 4 фази 0 «Модулі й пакети» в розділі «Як
за рядком у лапках знаходять файл» пояснювала, що пропущене розширення дописує саме Vite. У вашому проєкті файли мають
розширення `.tsx`, а в рядках імпорту заготовок дня розширення не пишуть.

### `Default vs named exports`

Це теж згорнутий блок deep dive, і в ньому лежить головна таблиця сторінки. Там сказано, що файл може мати щонайбільше
один типовий експорт і скільки завгодно іменованих, а вид експорту визначає, як імпортувати. Таблиця сторінки
показує те саме, що таблиця лекції в розділі «Файли: компонент у своєму модулі», лише на компоненті `Button`:
`export default function Button() {}` імпортують як `import Button from './Button.js'`, а
`export function Button() {}` імпортують як `import { Button } from './Button.js'`.

Сторінка додає три думки:

- **Типовий імпорт можна назвати як завгодно.** Запис `import Banana from './Button.js'` дасть той самий типовий
  експорт. Іменований імпорт мусить збігатися за назвою з експортом.
- **Є поширена домовленість.** Якщо файл віддає один компонент, беруть типовий експорт. Якщо компонентів чи значень
  кілька, беруть іменовані.
- **Не залишайте компонент без імені.** Сторінка не радить запис `export default () => {}`, бо він ускладнює пошук
  помилок, але не пояснює чому. Причину видно в такому досліді на Node.

```js
// файл anonymous.mjs
export default () => {
  throw new Error('щось зламалося')
}

// файл named.mjs
export default function Forecast() {
  throw new Error('щось зламалося')
}

// файл main.mjs
import Anonymous from './anonymous.mjs'
import Named from './named.mjs'

for (const component of [Anonymous, Named]) {
  console.log('name:', JSON.stringify(component.name))
  try {
    component()
  } catch (error) {
    console.log(error.stack.split('\n')[1].trim()) // перший рядок стека: хто кинув помилку
  }
}
```

Команда `node main.mjs` друкує таке. Довгий шлях до файлів ми замінили трьома крапками:

```text
name: "default"
at default (file:///…/anonymous.mjs:2:9)
name: "Forecast"
at Forecast (file:///…/named.mjs:2:9)
```

Функція без власного імені отримує ім'я `default`. Це ім'я Node показує в **стеку викликів**, тобто в переліку
функцій, які виконувалися в момент помилки. Якщо таких функцій у проєкті десяток, рядок `at default` не скаже, яка з
них зламалася, а рядок `at Forecast` скаже одразу.

Тут варто уважно прочитати одне речення. Сторінка каже, що ви отримаєте помилку, якщо імпортуєте типовий експорт так,
як іменований: наприклад, напишете `import { Title } from './parts'`, коли у файлі стоїть
`export default function Title`. Для цього напрямку це правда, але хто саме повідомить про помилку, залежить від
інструмента. Лекція в розділі «Файли: компонент у своєму модулі» показує, що Node не запускає такий модуль зовсім, а у
Vitest помилку кидає React. Зворотний напрямок сторінка не згадує, а він підступніший. Якщо файл має типовий експорт
`Title` й іменований `Note`, а ви написали `import Note from './parts'`, то помилки не буде ніде: у змінну `Note`
потрапить `Title`. Цей випадок лекція теж показує.

### `Exporting and importing multiple components from the same file`

Коли файл має віддати ще один компонент, він уже не може бути типовим, бо типовий експорт один. Сторінка робить
`Profile` іменованим експортом поруч із типовим `Gallery`, а потім імпортує обидва двома рядками:

```js
import Gallery from './Gallery.js';
import { Profile } from './Gallery.js';
```

Код зі сторінки react.dev `Importing and Exporting Components`, розділ
`Exporting and importing multiple components from the same file`.

Обидва імпорти можна написати й одним рядком: `import Gallery, { Profile } from './Gallery.js'`. Сторінка цього не
показує, але це звичайний запис мови: такий самий рядок `import makeTitle, { SEPARATOR } from "./title.js"` стоїть у
лекції «Модулі й пакети», підрозділ «Типовий експорт».

Поруч є примітка, що частина команд вибирає лише один вид експорту або не змішує обидва види в одному файлі, щоб їх не
плутати, і що вибір за вами. У вашому завданні `Header`, `List` і `Screen` експортовано типово, а `Card` іменовано,
щоб ви один раз написали обидва варіанти. Це навчальний вибір, а не правило.

### `Recap` і `Challenges`

`Recap` перелічує головні тези сторінки. Єдина вправа, `Split the components further`, просить винести `Profile` в
окремий файл і зробити це двічі: один раз з іменованим експортом, другий раз із типовим. Це добра розминка перед тим,
як розкладати компоненти дня по файлах, бо вправа дає ту саму дію на чужому прикладі.

**Навіщо це вам.** Практика дня розкладає компоненти по окремих файлах. Заготовка `List.tsx` залишає вам написати
рядок імпорту для `Card` самостійно, тому перед цим рядком перевірте вид експорту в `Card.tsx`.

## `Queries: About` у Testing Library

**Де читати:** [testing-library.com/docs/queries/about](https://testing-library.com/docs/queries/about). Сервер цього
матеріалу — `testing-library-docs`.

**Що це за текст.** Testing Library — це бібліотека, яка шукає елементи на сторінці так, як їх знаходить людина: за
написом, роллю, підписом поля. Вона існує для того, щоб тест не залежав від класів і внутрішньої будови компонента.
**Запит** (query) — це її функція, яка знаходить елемент. Ви поставили цю бібліотеку в практиці дня 11 фази 0 разом
із Vitest і jsdom.

**Якщо часу мало,** прочитайте таблицю в `Types of Queries` і список у `Priority`.

Приклади нижче працюють на маленькому екрані погоди. Ось файл `src/queries.test.tsx`, у тіло тесту якого ми по черзі
вставляли рядки дослідів:

```tsx
import { render, screen, within } from '@testing-library/react'
import { test } from 'vitest'

function Reading({ label, value }: { label: string; value: string }) {
  return <p>{label}: {value}</p>
}
function Station({ city, wind }: { city: string; wind: number }) {
  return <section aria-label={city}><h2>{city}</h2><Reading label="Вітер" value={`${wind} м/с`} /></section>
}
function Page() {
  return <div><h1>Погода</h1><Station city="Львів" wind={5} /><Station city="Одеса" wind={9} /></div>
}

// Виконує запит і повертає перший рядок помилки, якщо запит її кинув.
function firstLine(query: () => unknown) {
  try {
    query()
    return 'без помилки'
  } catch (error) {
    return (error as Error).message.split('\n')[0]
  }
}

test('запити', () => {
  render(<Page />)
  // сюди вставляйте рядки дослідів
})
```

Атрибут `aria-label` дає блоку `<section>` підпис. На екрані цього підпису не видно, але його читають програми, які
промовляють сторінку вголос. Навіщо він тут, пояснює розділ про `getByRole` нижче. Функція `firstLine` потрібна тому,
що запит, який нічого не знайшов, кидає помилку, а повідомлення в неї довге. Функція перехоплює помилку й повертає
лише її перший рядок.

### `Types of Queries`

Назва кожного запиту складається з двох частин. Початок назви, наприклад `getBy` чи `queryAllBy`, визначає поведінку
запиту: скільки елементів він чекає, що робить, коли знайшов нуль чи кілька, і чи чекає, поки елемент з'явиться.
Кінець назви визначає, за чим шукати: `ByRole` шукає за роллю, `ByText` за текстом, `ByLabelText` за підписом поля.
Будь-який початок поєднується з будь-яким кінцем, тому є `getByText`, `queryByRole`, `findAllByLabelText` тощо. Ось
переказ підсумкової таблиці сторінки:

| Початок назви | Нічого не знайдено | Один елемент | Кілька елементів | Чекає появи |
|---------------|--------------------|--------------|------------------|-------------|
| `getBy` | кидає помилку | повертає його | кидає помилку | ні |
| `queryBy` | повертає `null` | повертає його | кидає помилку | ні |
| `findBy` | відхиляє проміс | виконує проміс цим елементом | відхиляє проміс | так, до 1000 мс |
| `getAllBy` | кидає помилку | масив з одного | масив | ні |
| `queryAllBy` | порожній масив | масив з одного | масив | ні |
| `findAllBy` | відхиляє проміс | масив з одного | масив | так, до 1000 мс |

Як вибрати. Беріть `getBy`, коли елемент має бути на сторінці, бо помилка одразу покаже, чого бракує. Беріть
`queryBy`, лише коли перевіряєте, що елемента **немає**, бо він не кидає помилки. Варіант `findBy` потрібен тоді, коли
елемент з'явиться пізніше, наприклад після запиту до сервера, і це тема наступних днів. Ось дослід на нашому екрані:

```tsx
console.log(screen.getAllByRole('heading', { level: 2 }).map((h) => h.textContent))
console.log(screen.queryByRole('heading', { name: 'Київ' }))
console.log(screen.getAllByText(/^Вітер/).length)
```

```text
[ 'Львів', 'Одеса' ]
null
2
```

Перший рядок знайшов обидва заголовки `<h2>` і надрукував їхній текст. Другий рядок шукав заголовок «Київ», не знайшов
його й повернув `null` без помилки. Третій рядок шукав регулярним виразом `/^Вітер/`, тобто «текст починається словом
Вітер», і знайшов два абзаци, по одному в кожному місті.

А ось дві типові помилки `getBy`. Перший запит знаходить два абзаци, а другий не знаходить жодного заголовка:

```tsx
console.log(firstLine(() => screen.getByText(/^Вітер/)))
console.log(firstLine(() => screen.getByRole('heading', { name: 'Київ' })))
```

```text
Found multiple elements with the text: /^Вітер/
Unable to find an accessible element with the role "heading" and name "Київ"
```

Під першим рядком такого повідомлення бібліотека ще друкує знімок розмітки сторінки. Прочитайте його першим: він
показує, що насправді є на сторінці. Приклад такого знімка є в лекції, розділ «Рецепт: компонент проєктують як
функцію».

### `Priority`

Цей розділ каже, який запит вибрати, якщо підходять кілька. Сторінка пояснює порядок так: тест має шукати елементи
так, як їх шукає людина. Людина, яка бачить екран, знаходить кнопку за написом. Людина, яка не бачить екрана,
користується **екранним читачем** (screen reader). Так називають програму, яка промовляє вміст сторінки вголос і для
кожного елемента називає, що це таке й як він підписаний, наприклад «кнопка, Оновити». Те, наскільки сторінкою можуть
користуватися всі люди, зокрема й ці, називають **доступністю** (accessibility). Запити першої групи шукають так, як
шукають обидві людини, тому сторінка називає їх доступними всім. Наприкінці списку стоять запити за тим, чого людина
не бачить і не чує зовсім.

| Група | Запити | Коли брати |
|-------|--------|------------|
| доступні всім | `getByRole` | перший вибір, майже для всього |
| | `getByLabelText` | поля форми з підписом |
| | `getByPlaceholderText` | лише якщо підпису немає, бо підказка в порожньому полі його не замінює |
| | `getByText` | звичайний текст поза формами |
| | `getByDisplayValue` | поле, де вже введено значення |
| семантичні | `getByAltText` | картинка з атрибутом `alt` |
| | `getByTitle` | елемент з атрибутом `title` |
| тестові ідентифікатори | `getByTestId` | лише тоді, коли нічого іншого не підходить |

**Семантичними** сторінка називає запити за атрибутами HTML, які описують значення елемента. Атрибут `alt` дає
текстовий опис картинки. Атрибут `title` дає підказку, яка з'являється, коли навести на елемент мишу. Без миші її не
видно, а екранні читачі читають її не завжди, тому цей запит стоїть нижче. **Тестовий ідентифікатор** — це атрибут
`data-testid`, який дописують у розмітку лише заради тестів. Людина його не бачить і не чує, тому він останній.

Тому в заготовках дня стоять `getByRole` і `getByText`, а не пошук за класом.

### `Using Queries`

Цей розділ пояснює, звідки запит знає, де шукати. Базові запити з пакета `@testing-library/dom` першим аргументом
беруть вузол, усередині якого шукати, і сторінка називає цей вузол `container`. Об'єкт **`screen`** містить ті самі
запити, уже прив'язані до `document.body`, тобто до всієї сторінки. Сторінка показує обидва способи на одному полі.
Ми запустили цей фрагмент у тілі тесту Vitest, у файлі `src/container.test.ts`. Перед ним ми поставили в документ
розмітку, яку сторінка дає трохи вище, а після нього дописали рядок із `console.log`:

```ts
import { getByLabelText, screen } from '@testing-library/dom'

document.body.innerHTML = `
  <div id="app">
    <label for="username-input">Username</label>
    <input id="username-input" />
  </div>`
// With screen:
const inputNode1 = screen.getByLabelText('Username')
// Without screen, you need to provide a container:
const container = document.querySelector<HTMLElement>('#app')!
const inputNode2 = getByLabelText(container, 'Username')
console.log(inputNode1 === inputNode2, inputNode1.id)
```

Код зі сторінки Testing Library `Queries: About`, розділ `Using Queries`. Присвоєння `document.body.innerHTML`, тип
`<HTMLElement>`, знак `!` і останній рядок дописали ми.

```text
true username-input
```

`true` означає, що обидва способи знайшли той самий вузол. Запис `querySelector<HTMLElement>` каже TypeScript, який
вузол повернеться, а знак `!` обіцяє, що вузол точно знайдеться і `null` там не буде. Сторінка радить брати `screen`,
тому в заготовках ви всюди бачите `screen.getByRole(...)`. Підрозділ `queryOptions` пояснює другий аргумент запиту:
об'єкт із налаштуваннями пошуку, наприклад `{ level: 1 }`.

`screen` працює лише там, де є глобальний `document`. У вашому проєкті його дає рядок `environment: 'jsdom'` у файлі
`vite.config.ts`, який ви записали в практиці дня 11 фази 0.

### `getByRole`, `level` і `name`

Цього запиту докладно немає на сторінці `About`. Він описаний на сусідній сторінці
[`ByRole`](https://testing-library.com/docs/queries/byrole), а план згадує його окремо, тому пояснюємо його тут.

**Роль** (role) — це відповідь на запитання «що це за елемент» для програм, які читають сторінку замість людини:
кнопка, заголовок, список. Браузер будує поруч із деревом DOM ще одне дерево, **дерево доступності** (accessibility
tree). У ньому кожен вузол має роль та ім'я, і саме це дерево читає екранний читач. Більшість тегів отримують роль без
жодного атрибута, і таку роль називають неявною (implicit). Ось дослід, який друкує ролі, які Testing Library обчислює
в jsdom. Функція `getRoles` із пакета `@testing-library/dom` повертає об'єкт, у якому кожній ролі відповідає масив
вузлів із цією роллю. Тест друкує роль і перші 40 символів розмітки кожного вузла:

```tsx
import { getRoles } from '@testing-library/dom'
import { render } from '@testing-library/react'
import { test } from 'vitest'

test('ролі', () => {
  const { container } = render(
    <>
      <header>Шапка сторінки</header>
      <main>
        <h1>Погода</h1>
        <h3>Прогноз</h3>
        <button>Оновити</button>
        <input />
        <ul><li>Львів</li></ul>
        <article><header>Шапка картки</header></article>
        <section aria-label="Одеса">з підписом</section>
        <section>без підпису</section>
      </main>
    </>,
  )
  const roles = getRoles(container)
  for (const [role, nodes] of Object.entries(roles)) {
    console.log(role.padEnd(9), nodes.map((n) => n.outerHTML.slice(0, 40)).join(' | '))
  }
})
```

```text
generic   <div><header>Шапка сторінки</header><mai | <section>без підпису</section>
banner    <header>Шапка сторінки</header> | <header>Шапка картки</header>
main      <main><h1>Погода</h1><h3>Прогноз</h3><bu
heading   <h1>Погода</h1> | <h3>Прогноз</h3>
button    <button>Оновити</button>
textbox   <input>
list      <ul><li>Львів</li></ul>
listitem  <li>Львів</li>
article   <article><header>Шапка картки</header></
region    <section aria-label="Одеса">з підписом</
```

Більшість рядків очевидні: `<h1>` і `<h3>` мають роль `heading`, `<button>` має роль `button`, `<ul>` і `<li>` мають
ролі `list` і `listitem`. Перший рядок потребує пояснення. Роль `generic` означає «звичайний блок без особливого
значення», як у `<div>`. Її отримав `container`, тобто блок `<div>`, у який `render` показує компонент, а також
`<section>` без підпису. Отже, той самий тег `<section>` отримує роль `region` лише тоді, коли має ім'я, тут із
`aria-label`. Саме тому в нашому екрані погоди кожен `Station` має `aria-label`.

Рядок `banner` показує розбіжність між jsdom і браузером. За стандартом ARIA in HTML тег `<header>` має роль `banner`
лише тоді, коли він не лежить усередині `<article>`, `<aside>`, `<main>`, `<nav>` чи `<section>`. Ми показали ту саму
розмітку в Chrome 158 без вікна й прочитали його дерево доступності. Chrome дав роль `banner` лише першій шапці, а
шапці всередині `<article>` дав іншу роль, `sectionheader`. Testing Library 10.4 цього правила не враховує і дала
`banner` обом. Для вашого дня це важливо в одному місці. Перевірка в `screen.test.tsx` показує `Header` окремо, тому
`<header>` стоїть просто на сторінці, і роль `banner` правильна і в тесті, і в браузері. А в `Screen` шапка лежить
усередині `<main>`. Таку розмітку ми теж показали в Chrome, і він дав шапці роль `sectionheader`, а не `banner`.
Отже, у тесті запит `getByRole('banner')` знайде шапку `Screen`, а екранний читач у браузері не назве її шапкою
сторінки.

Поруч із роллю стоять два налаштування, які потрібні вам сьогодні:

- **`level`** працює лише з роллю `heading` і вибирає рівень заголовка. Запит `getByRole('heading', { level: 3 })`
  шукає `<h3>`. З іншою роллю це налаштування кидає помилку.
- **`name`** шукає за **доступним іменем** (accessible name), тобто текстом, яким елемент називає себе в дереві
  доступності. У простому випадку це текст усередині кнопки чи заголовка, значення `aria-label` або підпис поля.

```tsx
console.log(screen.getByRole('heading', { level: 1 }).textContent)
console.log(screen.getByRole('heading', { name: 'Одеса' }).nodeName)
console.log(firstLine(() => screen.getByRole('region', { level: 2 })))
```

```text
Погода
H2
Role "region" cannot have "level" property.
```

Перший рядок знайшов єдиний `<h1>`, другий знайшов заголовок з текстом «Одеса» і надрукував назву його тега, а третій
показує помилку, яку дає `level` з роллю `region`.

### `within`

Функції `within` теж присвячена окрема сторінка,
[`within`](https://testing-library.com/docs/dom-testing-library/api-within), а на `About` вона лише згадана. Вона бере
вузол і повертає ті самі запити, але обмежені цим вузлом. Вона потрібна тоді, коли той самий текст є в кількох місцях
і важливо, у якому саме.

```tsx
const odesa = screen.getByRole('region', { name: 'Одеса' })
console.log(within(odesa).getByText(/^Вітер/).textContent)
```

```text
Вітер: 9 м/с
```

На всій сторінці той самий запит `getByText(/^Вітер/)` кинув помилку `Found multiple elements`, бо абзаців про вітер
два. Усередині блока Одеси такий абзац один, тому `within` знайшов його без помилки.

### `TextMatch`

Більшість запитів приймають рядок, регулярний вираз або функцію. Таке значення сторінка називає `TextMatch`. Рядок за
замовчуванням має збігтися **повністю** й з урахуванням регістру. Підрозділ `Precision` описує налаштування
`exact: false`, яке дозволяє шукати частину рядка без урахування регістру:

```tsx
console.log(firstLine(() => screen.getByText('Вітер')))
console.log(screen.getAllByText('вітер', { exact: false }).length)
```

```text
Unable to find an element with the text: Вітер. This could be because the text is broken up by multiple elements. In this case, you can provide a function for your text matcher to make your matcher more flexible.
2
```

Рядок `'Вітер'` не знайшов абзацу `Вітер: 5 м/с`, бо текст абзацу довший. Друге речення помилки радить перевірити,
чи не розбито текст на кілька елементів. Ця підказка стоїть у кожному такому повідомленні, і тут вона не про нашу
причину. З `exact: false` рядок `'вітер'` з малої літери знайшов обидва абзаци. Сторінка радить для неточного пошуку
частіше брати регулярний вираз, бо ним точніше видно, що саме ви шукаєте. Підрозділ `Normalization` повідомляє, що
перед порівнянням бібліотека обрізає пробіли на краях і замінює кілька пробілів поспіль одним. Тому зайві пробіли в
розмітці пошуку не заважають.

Є важлива межа: `getByText` порівнює лише той текст, що лежить безпосередньо в елементі, без тексту вкладених тегів.
Якщо частину тексту обгорнуто в окремий тег, рядок не знайдеться:

```tsx
import { render, screen } from '@testing-library/react'
import { test } from 'vitest'

test('частина тексту в окремому тезі', () => {
  render(<p><b>Вітер:</b> 5 м/с</p>)
  try {
    screen.getByText('Вітер: 5 м/с')
  } catch (error) {
    console.log((error as Error).message.split('\n')[0])
  }
})
```

```text
Unable to find an element with the text: Вітер: 5 м/с. This could be because the text is broken up by multiple elements. In this case, you can provide a function for your text matcher to make your matcher more flexible.
```

Безпосередньо в `<p>` лежить лише текст ` 5 м/с`, а `Вітер:` належить тегу `<b>`. Тому ні `<p>`, ні `<b>` не має
повного рядка, і тут підказка про розбитий текст якраз влучна. Чому ж тоді компонент `Reading` знаходиться? Запис
`<p>{label}: {value}</p>` теж створює кілька шматків тексту. Ось що лежить в абзаці Львова:

```tsx
const paragraph = screen.getByText('Вітер: 5 м/с')
console.log(Array.from(paragraph.childNodes).map((node) => node.nodeName + ' ' + JSON.stringify(node.textContent)))
```

```text
[ '#text "Вітер"', '#text ": "', '#text "5 м/с"' ]
```

React поставив в абзац три текстові вузли, а `#text` — це назва, якою DOM позначає текстовий вузол. Усі три лежать
безпосередньо в `<p>`, без проміжного тега, тому бібліотека склеює їх в один рядок `Вітер: 5 м/с`.

### `Manual Queries`, `Browser extension` і `Playground`

`Manual Queries` каже, що можна вжити звичайний `querySelector` із лекції «DOM і події», але радить так не шукати за
класом чи `id`, бо їх користувач не бачить. Якщо інакше ніяк, сторінка радить узяти тестовий ідентифікатор, щоб було
видно, що це свідомий виняток. Останні два розділи описують розширення для браузера й пісочницю, у якій можна
підбирати запити на власному HTML. Вони вам не обов'язкові.

**Навіщо це вам.** Рецепт просить приклади до тіла, а приклад для компонента складається саме з таких запитів.
Заготовка `examples.test.tsx` дає вам кілька готових прикладів і лишає написати решту.

## How to Design Programs, `3.1 Designing Functions`

**Де читати:** [розділ у книжці](https://htdp.org/2023-8-14/Book/part_one.html#%28part._sec~3adesign-func%29). Сервер
цього матеріалу — `htdp-book`.

**Що це за текст.** Це книжка How to Design Programs, друге видання, авторів Matthias Felleisen, Robert Bruce Findler,
Matthew Flatt і Shriram Krishnamurthi, видавництва MIT Press, 2018 року. Її приклади написано навчальною мовою BSL,
схожою на Lisp. Розбір лише коротко переказує цей розділ, а оригінал читайте за посиланням.

**Якщо часу мало,** перечитайте лише `The Design Process`. Цей розділ ви вже розбирали у фазі 0: його кроки переказує
розбір дня 4 у розділі «3.1 Designing Functions», а розбір дня 9 у розділі «How to Design Programs: 3.1 Designing
Functions» показує, чим кожен крок став у TypeScript. Тут ми не повторюємо цей переказ, а показуємо лише, що нового
дає розділ сьогодні, коли функцією стає компонент.

### `Information and Data`

Книжка показує, що число 42 саме по собі нічого не означає: воно може бути кількістю пікселів, температурою чи
кількістю символів. Тому програміст записує **опис даних** (data definition): коментар, який пояснює, що означає
кожне значення.

Для компонента опис даних — це тип пропсів разом із коментарем до його полів. Приклад із заготовок дня: тип `Coin` у
файлі `List.tsx` має поле `id`, і саме з типу не зрозуміло, навіщо воно. Коментар над типом пояснює, що `id` — це
число, за яким React розрізняє елементи списку.

### `The Design Process`

Книжка пропонує шість кроків: опис даних; сигнатура, призначення й заглушка; приклади; перелік того, з чого
обчислювати результат; код; перевірка. Як кожен із цих кроків виглядає для компонента, показує таблиця в лекції цього
дня, розділ «Рецепт: компонент проєктують як функцію». Нового сьогодні лише одне: приклад для компонента не порівнює
результат зі значенням, а показує компонент через `render` і шукає на сторінці очікуваний вміст запитами з
попереднього розділу.

Наприкінці розділу книжка радить, що робити, коли приклад не пройшов. Можливі три причини: ви неправильно визначили
очікуваний результат, функція рахує неправильно, або помилка є і там, і там. Спершу перевірте очікуваний результат, а
вже потім правте функцію. На сторінці дня є окрема пастка саме про такий випадок: приклад шукає заголовок не того
рівня, а компонент правильний.

**Навіщо це вам.** Файл `recipe.test.tsx` перевіряє рецепт автоматично: він шукає коментар із призначенням над кожним
компонентом і рахує ваші приклади. Рецепт не змінився, змінилося лише те, як виглядає приклад.

## Перевірте себе

**1. Що станеться, якщо після `return` розмітка стоїть у наступному рядку без дужок?**

<details><summary>Відповідь</summary>

JavaScript сам поставить крапку з комою після `return`, і функція поверне `undefined`. React нічого не покаже й не
повідомить про помилку, бо з React 18 компонент має право повернути `undefined`. `tsc` скаже, що таку функцію не
можна вживати як компонент.

</details>

**2. Сторінка `Your First Component` каже, що оголошення компонента всередині іншого компонента повільне й веде до
помилок. Де шукати причину?**

<details><summary>Відповідь</summary>

У главі `Preserving and Resetting State`, у розділі `Different components at the same position reset state`, а також у
лекції цього дня, розділ «Компонент усередині компонента». Причина в тому, що при кожному рендері батька створюється
нова функція, тобто новий тип на тому самому місці, і React замінює старий екземпляр новим.

</details>

**3. Файл має `export default function Gallery` і `export function Profile`. Як отримати обидва в одному рядку
імпорту?**

<details><summary>Відповідь</summary>

`import Gallery, { Profile } from './Gallery'`. Типовий експорт стоїть без дужок і першим, а іменований стоїть у
дужках.

</details>

**4. Яким запитом перевірити, що заголовка на сторінці немає, і чому не `getByRole`?**

<details><summary>Відповідь</summary>

`queryByRole`. Він повертає `null`, якщо елемента немає, і цей результат можна перевірити. `getByRole` у цьому випадку
кине помилку, і тест упаде ще до перевірки.

</details>

**5. Чому `getByText('Вітер')` не знаходить абзац `Вітер: 5 м/с`?**

<details><summary>Відповідь</summary>

Рядок за замовчуванням має збігтися повністю. Щоб знайти частину тексту, беруть регулярний вираз `/^Вітер/` або
налаштування `exact: false`.

</details>

**6. Який запит сторінка `Priority` радить першим і чому?**

<details><summary>Відповідь</summary>

`getByRole`. Він шукає так, як сторінку сприймає людина, зокрема через екранний читач. Такий тест перевіряє ще й те,
що елементи мають правильні ролі, і він не ламається, коли змінюються класи.

</details>
