## `Rendering Lists`

**Де читати:** [react.dev/learn/rendering-lists](https://react.dev/learn/rendering-lists). Сервер цього матеріалу
називається `react-docs`.

**Що це за текст.** Це сторінка команди React про те, як показати масив даних. Сторінка містить вікна з кодом, які
можна правити просто в браузері, і чотири вправи. Основні приклади стоять на одному наборі даних: список науковців із
професіями, а у вправах з'являються рецепти й вірш.

**Якщо часу мало,** прочитайте `Keeping list items in order with key`, обидва підрозділи про ключі та застереження
`Pitfall` наприкінці розділу `Why does React need keys?`.

### `Rendering data from arrays`

Сторінка починає зі списку п'яти імен, написаного вручну, і показує три кроки. Дані переносять у масив `people`,
методом `map` перетворюють кожне ім'я на `<li>`, і результат ставлять у дужки всередині `<ul>`.

Цей приклад навмисно не має ключа, тому у вікні з кодом видно попередження `Each child in a list should have a unique
"key" prop`. Сторінка обіцяє полагодити його нижче. Ви побачите те саме в консолі.

### `Filtering arrays of items`

Тепер кожен науковець є об'єктом із полями `id`, `name` і `profession`. Завдання полягає в тому, щоб показати лише
хіміків. Сторінка додає перед `map` виклик `filter`, а його результат кладе в змінну `chemists`. Функція `getImageUrl`
із файла `utils.js` лише збирає адресу картинки, і для теми вона не важлива.

**Застереження `Pitfall` про стрілкові функції.** Сторінка пояснює те саме, що лекція «Масиви й об'єкти функційно»:
вираз одразу після `=>` повертається сам, а після `=> {` потрібен `return`. Записи `=> (` на цій сторінці є просто
виразом у дужках. Ось перевірка на нашому прикладі:

```tsx
const rows = [{ id: 1, name: 'Чай' }]
const a = rows.map((row) => <li key={row.id}>{row.name}</li>)
const b = rows.map((row) => { <li key={row.id}>{row.name}</li> })
console.log(a.length, a[0]?.type, '|', b.length, b[0])
```

```text
1 li | 1 undefined
```

Масив `b` має ту саму довжину, але в ньому лежить `undefined`, тому React нічого не покаже.

### `Keeping list items in order with key`

Сторінка додає `key={person.id}` до кожного `<li>` і попередження зникає. Вона пояснює коротко: ключ потрібен, щоб
React знав, який рядок який, коли масив можуть відсортувати, додати рядок чи видалити рядок. Ключ, вибраний добре,
дозволяє React зрозуміти, що саме сталося, і правильно оновити дерево вузлів. Сторінка також радить брати ключ із
самих даних, а не створювати під час рендеру.

### `Displaying several DOM nodes for each list item`

Це згорнутий блок із додатковою думкою. Запитання таке: що робити, коли рядок має дати кілька вузлів, наприклад `<h1>`
і `<p>`? Скорочений запис `<>…</>` не приймає ключа, тому сторінка показує два виходи: обгорнути в `<div>` або
написати повний запис `<Fragment key={person.id}>`. Фрагмент зникає з документа, і вийде плаский ряд `<h1>`, `<p>`,
`<h1>`, `<p>`.

Цю можливість докладно описує [сторінка `Fragment`](https://react.dev/reference/react/Fragment) у розділі `Rendering a
list of Fragments`. Сьогодні вона вам не потрібна в завданні, але лекція показує її запуском.

### `Where to get your key`

Сторінка називає два джерела.

- **Дані з бази.** Беруть її ключі чи ідентифікатори, бо вони унікальні за своєю природою.
- **Дані, створені й збережені локально,** наприклад нотатки в застосунку для нотаток. Тут беруть лічильник, виклик
  `crypto.randomUUID()` або пакет на зразок `uuid`, і важливі слова стоять наприкінці речення: «when creating items»,
  тобто коли запис створюють.

**UUID** означає універсальний унікальний ідентифікатор, рядок із 36 символів, для якого збіг практично неможливий.
Ось як виглядає результат запуску в Node, у браузері метод той самий:

```js
const a = crypto.randomUUID()
console.log(a.length, a === crypto.randomUUID())
```

```text
36 false
```

Сторінка [MDN про `randomUUID`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) додає, що в
браузері метод доступний лише в захищеному контексті, тобто на HTTPS. Ми цього в браузері не перевіряли. У вашому
завданні цей метод не потрібен, бо `id` уже є в даних.

### `Rules of keys`

Правил лише два, і кожне варто прочитати буквально.

**Перше.** Ключі мають бути унікальними серед сусідів, але в різних масивах можуть збігатися. Лекція перевіряє це
двома `map` в одному батьку.

**Друге.** Ключі не повинні змінюватися, і сторінка каже прямо: «Don't generate them while rendering.» Сторінка не
каже, що саме стається при порушенні, тобто що для `Math.random()` усі вузли створюються заново. Це сказано трохи
нижче, у застереженні.

### `Why does React need keys?`

Сторінка дає аналогію з файлами на робочому столі. Якби файли мали не назви, а лише порядок, ви казали б «перший
файл», «другий файл». Коли файл видалено, «другий файл» раптом стає іншим файлом. У цій аналогії назва файла
відповідає ключу, а порядок файлів відповідає індексу. Лекція показує те саме на числах.

Сторінка підсумовує це так: ключ дає більше інформації, ніж позиція в масиві, і дозволяє React упізнавати запис
упродовж усього його життя, навіть коли позиція змінилася.

**Застереження `Pitfall`** є найважливішим місцем сторінки. Воно містить три думки.

- **Індекс.** Сторінка каже, що індекс є саме тим, чим React скористається, якщо ключа немає, і що він часто дає
  неочевидні помилки при вставці, видаленні чи зміні порядку. Лекція показує шість дій і ті дві, де індекс не
  ламається. На самій сторінці цього поділу немає.
- **Випадковий ключ.** Запис `key={Math.random()}` дає ключі, які не збігаються між рендерами, тому всі компоненти й
  вузли створюються щоразу заново. Сторінка називає два наслідки: це повільно, і втрачається все введене в рядках. Це
  і є пастка вашого дня.
- **Ключ не є пропом.** Компонент не отримує `key`. Якщо йому потрібне те саме значення, передайте його окремо:
  `<Profile key={id} userId={id} />`.

Перевірка останньої думки:

```tsx
function Profile(props: { userId: number }) {
  console.log(Object.keys(props))
  return null
}

render(<Profile key={7} userId={7} />)
```

```text
[ 'userId' ]
```

### `Recap` і `Challenges`

`Recap` повторює сказане: дані виносять із компонента в масиви й об'єкти, `map` створює схожі компоненти, `filter`
вибирає частину, а кожен компонент у колекції отримує `key`.

| Вправа | Що вона тренує | Чи робити сьогодні |
|--------|----------------|--------------------|
| `Splitting a list in two` | два списки з одного масиву | так, це швидка вправа на `filter` і `map` |
| `Nested lists in one component` | вкладені `map` і різні ключі на кожному рівні | так |
| `Extracting a list item component` | ключ на тегу компонента, а не всередині | обов'язково, бо це типова помилка |
| `List with a separator` | кілька вузлів на рядок і `Fragment` з ключем | за бажанням |

У вправі `Nested lists` внутрішнім ключем є сам інгредієнт, бо в одному рецепті інгредієнти не повторюються. Це
приклад правила «унікальний серед сусідів». У вправі `List with a separator` сторінка вживає індекс, і пояснює це тим,
що рядки вірша ніколи не змінять порядку. Тобто заборона індексу не є абсолютною.

**Навіщо це вам.** Застереження `Pitfall` є точним описом двох варіантів ключа й пастки вашого завдання. Перевірка
«однакові назви не ламають ключі» в `FieldList.test.tsx` існує через правило `Rules of keys`.

## `user-event: Introduction` у Testing Library

**Де читати:** [testing-library.com/docs/user-event/intro](https://testing-library.com/docs/user-event/intro). Сервер
цього матеріалу називається `testing-library-docs`.

**Що це за текст.** Це вступ до бібліотеки, яка в тестах відтворює дії людини. Сторінка коротка й містить лише
приклади запису. Самі методи `type` і `click` описано на інших сторінках, тому нижче вони мають власні підрозділи.
Сторінка описує версію 14, а для версії 13 є окрема документація. Проєкт ставить останню версію, і під час нашої
перевірки це була 14.6.

**Якщо часу мало,** прочитайте `Differences from fireEvent` і перший приклад у `Writing tests with userEvent`.

### `Differences from fireEvent`

Функція `fireEvent` є тонкою обгорткою над методом браузера `dispatchEvent`: вона надсилає одну подію й нічого більше.
Сторінка пояснює, що справжня дія людини складається з багатьох подій. Коли людина набирає текст, змінюються фокус,
виділення й значення поля, і кожну літеру супроводжує кілька подій. Лекція показує список цих подій запуском. Формула
сторінки звучить так: «`fireEvent` dispatches _DOM events_, whereas `user-event` simulates full _interactions_».

Сторінка називає ще одну різницю: `user-event` робить перевірки, яких не робила б подія. Він не натисне на прихований
елемент і не набере текст у вимкнене поле. Для дій, яких бібліотека ще не вміє, сторінка радить `fireEvent` із
застереженням, що тест тоді залежить від того, які саме події ви надіслали.

### `Writing tests with userEvent`

Сторінка радить викликати `userEvent.setup()` перед показом компонента, усередині самого тесту або в допоміжній
функції. Вона застерігає від виклику поза тестом, наприклад у `beforeEach`.

Другий приклад на сторінці є допоміжною функцією, яка повертає разом `user` і результат `render`. У вашому завданні
вона не потрібна, але запис коротший, коли тестів багато:

```tsx
function setup(jsx: ReactNode) {
  return { user: userEvent.setup(), ...render(jsx) }
}

const { user: person, container } = setup(<input aria-label="поле" />)
await person.type(screen.getByLabelText('поле'), 'так')
console.log(container.querySelector('input')?.value)
```

```text
так
```

Сторінка згадує й прямий виклик `userEvent.click(...)` без `setup`. Він працює у версії 14, але існує здебільшого для
переходу зі старої версії, тому сторінка радить виклик на об'єкті `user`.

### `setup`: окрема сторінка опцій

**Де читати:** [testing-library.com/docs/user-event/setup](https://testing-library.com/docs/user-event/setup). На
сторінці `Introduction` цей виклик лише показано.

Сторінка пояснює, що виклик створює об'єкт, методи якого ділять між собою стан пристроїв введення, тому затиснута
клавіша лишається затиснутою для наступної дії. Сьогодні вам не потрібна жодна опція, тому запам'ятайте лише форму:
`const user = userEvent.setup()` на початку кожного тесту, який щось натискає або набирає. Методи цього об'єкта
повертають проміси, тому такий тест оголошують `async`.

### `type`: окрема сторінка

**Де читати:** [testing-library.com/docs/user-event/utility](https://testing-library.com/docs/user-event/utility),
розділ `type()`.

Метод вставляє текст у поле й повертає проміс. Сторінка перелічує чотири дії в такому порядку: натиснути на елемент,
за потреби встановити виділення, набрати текст, відпустити натиснуті клавіші. Перша дія пояснює, чому поле після
`user.type` має фокус. Опції `skipClick` і `initialSelectionStart` можуть змінити цю послідовність:

```tsx
render(<input aria-label="поле" defaultValue="XY" />)
const field = screen.getByLabelText<HTMLInputElement>('поле')
await user.type(field, 'a')
console.log(field.value)
await user.type(field, 'b', { initialSelectionStart: 0 })
console.log(field.value)
```

```text
XYa
bXYa
```

Без опції текст додається в кінець, а з опцією `initialSelectionStart: 0` на початок. Сьогодні опції не потрібні.
Сторінка також показує метод `clear`, який очищує поле, і `upload`, який імітує вибір файла. Вони знадобляться
пізніше.

### `click`: окрема сторінка

**Де читати:**
[testing-library.com/docs/user-event/convenience](https://testing-library.com/docs/user-event/convenience), розділ
`click()`.

Сторінка пояснює, що цей метод є скороченням для двох дій вказівником: перемістити вказівник на елемент і натиснути та
відпустити ліву кнопку. Вона перелічує поруч `dblClick`, `tripleClick`, `hover`, `unhover` і `tab`. Перевірка про
вимкнену кнопку:

```tsx
const log: string[] = []
render(<button disabled onClick={() => log.push('натиснуто')}>Видалити</button>)
await user.click(screen.getByRole('button', { name: 'Видалити' }))
console.log(log.length)
```

```text
0
```

**Навіщо це вам.** Ваші приклади в `examples.test.tsx` вживають саме `userEvent.setup()`, `user.type` і `user.click`.
Значення поля там перевіряє `toHaveValue`, а цей метод належить не до цієї сторінки, а до бібліотеки `jest-dom`, яку
ви поставили в день 11 фази 0.

### `The Design Process`

Книжка пропонує кроки в певному порядку. Ось де кожен із них стоїть у сьогоднішній заготовці:

| Крок у книжці | Що він просить | Де це в заготовці дня |
|---------------|----------------|-----------------------|
| подати інформацію даними | записати опис даних | типи `Item` і `KeyBy`, приклад `FRUITS` у `FieldList.tsx` |
| сигнатура, призначення, заголовок | сказати, що функція отримує й повертає, одним реченням сказати, що вона робить, написати заглушку | сигнатура в коді, коментар над функцією, заглушки `return items` і `return null` |
| приклади | наперед записати очікуваний результат | `examples.test.tsx` |
| перелік вхідних даних | записати те, з чого будується результат | коментар `// Вхідні дані: …` у тілі |
| код | замінити заглушку | ваш код за підказками в коментарях |
| перевірка | запустити приклади | `npx vitest run src/lessons/f1-d04` і `npx tsc --noEmit -p tsconfig.app.json` |

Зразком усіх кроків сьогодні є функція `rowKey`, а функцію `without` і компонент `FieldList` ви доводите самі. Файл
`recipe.test.tsx` перевіряє саме цю будову.

### Як лягає на сьогоднішнє завдання

Функція `without` є саме таким випадком, для якого написано цей розділ. Вона отримує значення й повертає нове, не
змінюючи старого, і приклади перевіряє простий `expect` без сторінки.

Компонент `FieldList` рецепт теж описує, хоча в нього є стан і користувач. Книжка в цьому розділі ще не говорить про
стан, тому два кроки мають іншу форму. Перелік вхідних даних тут містить не лише пропси, а ще й значення стану,
функцію його зміни й допоміжні функції. Приклади записано не як пари «вхід і результат», а як послідовність дій
користувача й перевірку екрана після них.

Коли результат не збігся, порада книжки стає особливо важливою. Для вас є два очікуваних результати: `bbb` у рядку
«Сливи» для ключа-індексу і `ccc` для ключа-`id`. Обидва правильні для свого ключа, тому перед виправленням коду
спершу перевірте, який ключ стоїть у прикладі.

**Навіщо це вам.** Файл `recipe.test.tsx` шукає призначення над кожною функцією й рахує ваші приклади. Рецепт не
змінився, змінилося лише те, що сьогодні частина прикладів є послідовністю дій.

## Перевірте себе

**1. Сторінка `Rendering Lists` застерігає від `=> {` без `return`. Що лежатиме в масиві, який поверне такий `map`?**

<details><summary>Відповідь</summary>

Значення `undefined` у кожній позиції, тобто масив потрібної довжини, але без елементів. React нічого не покаже, а
`tsc` скаже `TS2322` про `void[]`.

</details>

**2. Яка аналогія в `Why does React need keys?`, і що в ній чому відповідає?**

<details><summary>Відповідь</summary>

Файли на робочому столі без назв, лише з порядком. Назва відповідає ключу, а порядок відповідає індексу. Коли файл
видалено, порядковий номер починає означати інший файл.

</details>

**3. Що сторінка каже про індекс і чому це не абсолютна заборона?**

<details><summary>Відповідь</summary>

Вона каже, що саме індекс React бере, коли ключа немає, і що при вставці, видаленні чи зміні порядку він дає
неочевидні помилки. У вправі `List with a separator` сторінка сама вживає індекс, бо рядки вірша ніколи не змінюють
порядку.

</details>

**4. Чому сторінка радить `crypto.randomUUID()`, але застерігає від `Math.random()`?**

<details><summary>Відповідь</summary>

Вона радить викликати `crypto.randomUUID()` один раз, коли запис створюють, і зберігати результат. Застереження
стосується виклику під час рендеру. Проблему дає не саме випадкове значення, а те, що воно щоразу нове.

</details>

**5. Чим `fireEvent` відрізняється від `user-event`?**

<details><summary>Відповідь</summary>

`fireEvent` надсилає одну подію. `user-event` відтворює цілу дію людини: фокус, натискання й усі події клавіш. Він
також не дає натиснути на вимкнену кнопку або набрати текст у вимкнене поле.

</details>

**6. Що робить `user.type` першою дією, і який наслідок цього бачать ваші перевірки?**

<details><summary>Відповідь</summary>

Спершу він натискає на поле, тому поле отримує фокус. Перевірка «перемалювання не стирає текст і не губить фокус»
розраховує на це.

</details>

**7. У чому відмінність прикладів для `without` і для `FieldList`?**

<details><summary>Відповідь</summary>

Приклад для `without` є парою «вхід і результат» через `expect`, і він не потребує сторінки. Приклад для `FieldList`
показує компонент, виконує дії через `userEvent` і перевіряє екран.

</details>
