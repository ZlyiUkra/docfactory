## `lazy`

**Де читати:** [react.dev/reference/react/lazy](https://react.dev/reference/react/lazy).

**Що це за текст.** Це коротка сторінка довідника про одну функцію. Перше речення каже, що `lazy` дає змогу відкласти
завантаження коду компонента, доки його вперше не відрендерять.

**Якщо часу мало,** прочитайте `Reference` і розділ `Troubleshooting`.

### `Reference` › `lazy(load)`

Функцію `lazy` викликають поза компонентами, на верхньому рівні модуля. Вона повертає компонент React, який можна
рендерити як звичайний. Пункт `Returns` додає головне: поки код ще вантажиться, спроба відрендерити такий компонент
змушує його **призупинитися**, англійською suspend. Лекція перекладає це словом «чекати». Щоб показати щось на час
очікування, потрібна межа `<Suspense>`.

### `Parameters`

Параметр один, `load`. Це функція, яка повертає обіцянку або інший **thenable**, тобто об'єкт, схожий на обіцянку,
бо в нього є метод `then`. Сторінка каже чотири речі про те, як React поводиться з `load`.

| Що каже сторінка | Що це означає для вас |
|------------------|------------------------|
| React не викликає `load`, поки компонент уперше не спробують відрендерити | модуль не завантажиться, якщо людина до нього не дійшла |
| після першого виклику React чекає завершення й рендерить поле `.default` результату | модуль має експортувати компонент як `export default` |
| і обіцянку, і її результат React запам'ятовує | `load` викликається один раз; наш запуск показав рядок «React викликав load» лише при першому рендері |
| якщо обіцянка відхилена, React кидає причину найближчій межі помилок | збій завантаження ловить межа помилок, а не `<Suspense>`; наш запуск показав у стеку компонентів рядок `at Lazy` |

### `load` function › `Returns`

Тут уточнено, чим має завершитися обіцянка: об'єктом, у якого поле `.default` містить коректний тип компонента.
Сторінка називає три приклади такого типу: функцію, компонент у `memo` і компонент у `forwardRef`. Функцію
`forwardRef` ви не вивчали, і сьогодні вона не потрібна.

### `Usage` › `Lazy-loading components with Suspense`

Розділ показує заміну звичайного імпорту:

```js
// приклад зі сторінки lazy
import { lazy } from 'react';

const MarkdownPreview = lazy(() => import('./MarkdownPreview.js'));
```

Сторінка нагадує, що вираз `import()` є динамічним імпортом і може потребувати підтримки збирача. Vite його підтримує:
лекція показала, що збірка поклала лінивий модуль в окремий файл. Далі сторінка ставить лінивий компонент усередину
`<Suspense>`:

```js
<Suspense fallback={<Loading />}>
  <h2>Preview</h2>
  <MarkdownPreview />
</Suspense>
```

Зверніть увагу: заголовок `<h2>Preview</h2>` теж стоїть усередині межі. Тому поки попередній перегляд вантажиться,
запасний вміст заміщує і його. Повний приклад сторінки має прапорець «Show preview» і функцію `delayForDemo`, яка
штучно затримує завантаження на дві секунди, щоб запасний вміст було видно. У вашому застосунку такої затримки немає,
тому на швидкій мережі запасний вміст може промайнути непомітно. Наш запуск у продакшн-збірці з уповільненою мережею
показав запасний вміст через 5 мс після клацання, а графік через 545 мс.

### `Troubleshooting` › `My lazy component's state gets reset unexpectedly`

Єдиний розділ про типову проблему. Не оголошуйте ледачий компонент усередині іншого компонента. Тоді кожен рендер
батька створює новий виклик `lazy`, тобто новий тип компонента, і React скидає весь стан усередині. Оголошуйте його на
верхньому рівні модуля. Цього випадку ми не відтворили надійно, тому тут покладайтеся на сторінку.

## `<Suspense>`

**Де читати:** [react.dev/reference/react/Suspense](https://react.dev/reference/react/Suspense).

**Що це за текст.** Це довга сторінка довідника з багатьма живими прикладами. Перше речення каже, що `<Suspense>`
показує запасний вміст, доки його діти не завантажаться. Більшість прикладів завантажує дані через функцію `use`, яку
ви сьогодні лише впізнаєте. Частина розділів стосується серверного рендеру, і до них ви повернетеся у фазі 4.

**Якщо часу мало,** прочитайте `Props`, `Caveats`, `What activates a Suspense boundary`, `Displaying a fallback while
content is loading`, `Revealing content together at once` і `Preventing already revealed content from hiding`.

### `Reference` › `<Suspense>` › `Props`

Сторінка описує пропси.

- `children` є справжнім вмістом. Якщо щось усередині чекає, межа перемикається на `fallback`.
- `fallback` є запасним вмістом. Сторінка радить робити його легким: значок завантаження чи **скелет**, тобто сірий
  макет майбутнього вмісту. Коли діти готові, межа сама повертається до них. Окреме речення каже, що коли чекає сам
  `fallback`, спрацьовує найближча межа вище.
- `defer` є необов'язковим логічним пропсом: з ним React може спершу показати запасний вміст і відрендерити дітей
  пізніше, навіть якщо ніщо в них не чекає. Сторінка радить його для вмісту, який дорого рендерити. У типах
  `@types/react` 19.3, які стоять у шаблоні проєкту, такого пропса немає, а є пропс `name`, який підписує межу в
  React Developer Tools. Ні того, ні іншого ми не перевіряли.

### `Caveats`

Застереження варто прочитати всі. Таблиця каже, що означає кожне і що ми бачили.

| Застереження | Що воно означає | Що ми бачили |
|--------------|-----------------|--------------|
| межа не помічає запитів з ефекту чи обробника події | дані з `useEffect` не вмикають запасного вмісту | не перевіряли запуском; приклад сторінки `EffectAlbums` показує те саме |
| стан частини, яка почала чекати до першого показу, не зберігається | коли все готове, React рендерить її з нуля | не перевіряли |
| якщо показаний вміст знову почав чекати, межа покаже `fallback`, якщо оновлення не позначено `startTransition` чи `useDeferredValue` | термінове оновлення ховає показаний вміст | наш запуск: у переході стара вкладка лишилася, термінове оновлення й `flushSync` сховали її |
| React показує готовий вміст не частіше ніж раз на 300 мс | межі, які стали готовими майже одночасно, з'являються разом | не перевіряли |
| коли показаний вміст ховається, React прибирає його ефекти `useLayoutEffect` і запускає знову при показі | код, що міряє розміри, не міряє схованого | не перевіряли; наш запуск показав, що схований вміст лишається в документі зі стилем `display: none !important` |
| серверний рендер частинами й вибіркова гідратація пов'язані з Suspense | про це фаза 4 | не перевіряли |

### `Reference` › `What activates a Suspense boundary`

Розділ перелічує, що змушує межу чекати. Ось кожен пункт своїми словами.

- **Код ледачого компонента**, завантажений через `lazy`.
- **Обіцянка, прочитана функцією `use`.** Сюди належать і дані, які надсилають серверні компоненти, і дані з бібліотек
  із підтримкою Suspense.
- **Таблиця стилів** у тезі `<link rel="stylesheet">` із пропсом `precedence`. React чекає її завантаження, але не
  довше за певний час.
- **HTML великої межі під час серверного рендеру частинами.** Пересилання займає час, тому межа з великим вмістом
  чекає навіть тоді, коли в ній ніщо не призупинилося.
- **Шрифти й зображення.** Типово межа їх не чекає. Але коли появу межі анімує компонент `<ViewTransition>`, React
  чекає нових шрифтів і видимих зображень до 500 мс.
- **Важкий рендер** усередині межі з пропсом `defer`.

Підрозділ `Suspense-enabled frameworks` пояснює слова «бібліотека, що вміє чекати разом із Suspense» з картки дня.
Така бібліотека тримає кеш обіцянок і всередині викликає `use`. Без бібліотеки можна викликати `use` самому, якщо
обіцянка лежить у кеші й на кожному рендері та сама.

### `Usage` › `Displaying a fallback while content is loading`

Перший приклад показує сторінку виконавця, де альбоми завантажуються через `use`. Межа показує «Loading...», поки дані
не прийдуть. Функція `fetchData` у файлі `data.js` тримає обіцянки в `Map`, а коментар над нею прямо каже, що
справжній спосіб завантаження залежить від бібліотеки чи фреймворку. Приклад показує механізм, а не те, як писати
запити у вашому застосунку.

Далі в тому самому розділі стоїть протилежний приклад, `EffectAlbums`. Той самий список вантажиться в `useEffect`, і
коментар у коді каже, що межа цього запиту не бачить і запасного вмісту не покаже. Список просто порожній, поки дані
не прийдуть. Це відповідає першому застереженню сторінки.

Кінець розділу показує те саме під час серверного рендеру частинами. Цей приклад потрібен у фазі 4.

### `Usage` › `Revealing content together at once`

Усе всередині однієї межі React вважає одним цілим. Якщо чекає хоч один компонент, запасний вміст заміщує всіх, а коли
все готове, усе з'являється разом. Сторінка додає, що компоненти, які чекають, не мусять бути прямими дітьми межі:
якщо перенести їх у проміжний компонент `Details`, поведінка не зміниться, бо найближча межа та сама.

### `Usage` › `Revealing nested content as it loads`

Тут межі вкладено одна в одну. Сторінка розписує послідовність кроків: поки біографія не готова, зовнішній
`BigSpinner` закриває все; коли біографія готова, вона з'являється, а на місці альбомів стоїть внутрішній
`AlbumsGlimmer`; коли готові й альбоми, вони заміщують `AlbumsGlimmer`. Наприкінці стоїть порада: не ставте межу
навколо кожного компонента, а ставте там, де дизайн передбачає окремий стан завантаження.

### `Usage` › `Showing stale content while fresh content is loading`

Цей розділ ви вже бачили з іншого боку на сторінці `useDeferredValue`. Без хука кожна нова літера пошуку ховає старі
результати за запасним вмістом. З `useDeferredValue` межа лишає на екрані старі результати, а напівпрозорість показує,
що вони застарілі.

### `Usage` › `Preventing already revealed content from hiding`

Головний розділ для теми «показаний вміст». Сторінка спершу показує маршрутизатор, у якому натискання кнопки одразу
ховає всю сторінку за `BigSpinner`, бо нова сторінка чекає даних. Потім вона загортає навігацію в `startTransition`, і
стара сторінка лишається, поки нова не готова. Наш запуск зробив те саме з двома лінивими вкладками: у переході стара
вкладка лишилася на екрані, а звичайне оновлення сховало її.

### `Usage` › `Indicating that a Transition is happening`

Продовження попереднього розділу. Щоб людина бачила, що навігація триває, сторінка бере `useTransition` замість
окремої функції `startTransition` і змінює стиль шапки, поки `isPending` дорівнює `true`.

### `Usage` › `Resetting Suspense boundaries on navigation`

Іноді старого вмісту лишати не треба: людина перейшла до профілю іншої людини. Тоді межі або компоненту над нею дають
`key` з ідентифікатором профілю. Новий `key` змушує React вважати межу новою, і вона показує запасний вміст. Сторінка
додає, що маршрутизатори з підтримкою Suspense мають робити це самі.

### `Usage` › `Providing a fallback for server errors and client-only content`

Розділ про серверний рендер. Якщо компонент упав на сервері, React не зупиняє рендеру, а кладе в HTML запасний вміст
найближчої межі `<Suspense>` і пробує ще раз уже в браузері. Якщо в браузері знову помилка, її отримує найближча межа
помилок. Сьогодні досить знати, що такий зв'язок є, а потрібен він у фазі 4.

### `Troubleshooting` › `How do I prevent the UI from being replaced by a fallback during an update?`

Відповідь коротка: позначте оновлення як нетермінове через `startTransition`. Сторінка підкреслює, що React запобігає
небажаному запасному вмісту лише в нетермінових оновленнях, і термінового рендеру він не відкладає. Межі, які
з'явилися в цьому оновленні вперше, однаково покажуть свій запасний вміст одразу. Окреме речення каже, що
маршрутизатор із підтримкою Suspense має сам загортати свої оновлення в `startTransition`.

## `Component`, розділ `Catching rendering errors with an Error Boundary`

**Де читати:** [react.dev/reference/react/Component](https://react.dev/reference/react/Component), розділ [Catching
rendering errors with an Error
Boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).

**Що це за текст.** Це сторінка довідника про базовий клас `Component`, тобто про компоненти-класи. Сторінка
починається з пересторогу: нові компоненти радять писати функціями, а класи React підтримує заради старого коду. Межа
помилок є винятком, тому сьогодні з цієї сторінки потрібні лише розділ про межі й довідка про два методи. Класів ви ще
не писали, тому корисно переглянути й розділ `Defining a class component`.

**Якщо часу мало,** прочитайте розділ `Catching rendering errors with an Error Boundary` і довідку про
`static getDerivedStateFromError` та `componentDidCatch`.

### `Usage` › `Defining a class component`

Компонент-клас продовжує вбудований клас `Component` через `extends` і має метод `render`, який повертає JSX. Пропси
лежать у полі `this.props`, тому замість `name` пишуть `this.props.name`. Сторінка наголошує, що хуки в класах не
працюють. Синтаксис класу, тобто `class`, `extends`, `this`, поля й статичні методи, пояснює лекція в розділі «Клас у
JavaScript у потрібному обсязі».

### `Usage` › `Catching rendering errors with an Error Boundary`

Перший абзац пояснює проблему. Якщо під час рендеру виникла помилка, React за замовчуванням прибирає з екрана свій
інтерфейс. Наш запуск це підтвердив: після помилки в одному рядку списку документ став порожнім разом із заголовком.
**Межа помилок**, англійською Error Boundary, є особливим компонентом, який показує запасний інтерфейс замість
частини, що впала.

Під цим стоїть примітка про те, чого межа не ловить. Таблиця зводить її з нашими запусками.

| Що не ловить межа | Наш запуск |
|-------------------|------------|
| помилки в обробниках подій | помилка в `onClick` дійшла до події `error` вікна, межа нічого не показала, в обох збірках |
| помилки серверного рендеру | не перевіряли |
| помилки в самій межі, а не в її дітях | помилку запасного екрана зловила зовнішня межа, а початкова помилка не потрапила в журнал |
| асинхронний код, як-от `setTimeout` чи `requestAnimationFrame` | помилка в `setTimeout` дійшла до події `error` вікна, межа нічого не показала |
| виняток: помилки функції, переданої в `startTransition` з хука `useTransition`, межа ловить | межа показала запасний екран |

Далі сторінка пояснює, що межа потребує методу `static getDerivedStateFromError`, а метод `componentDidCatch` додають,
якщо треба записати помилку кудись, наприклад у сервіс аналітики. Останнє речення абзацу згадує функцію
`captureOwnerStack`, яка в режимі розробки додає стек власників.

Потім іде приклад класу `ErrorBoundary`. Лекція наводить його повністю й розбирає за частинами. Тут варто помітити три
речі.

- Коментар у `componentDidCatch` показує, як виглядає стек компонентів: рядки на кшталт «in ComponentThatThrows
  (created by App)». У React 19.3.1 наш запуск показав інший запис: рядки починаються словом `at`, а замість «created
  by» стоїть файл із номером рядка, наприклад `at StopRow (…/StopList.tsx:7:20)`.
- Виклик `React.captureOwnerStack()` позначено коментарем-попередженням: у продакшн-збірці цієї функції немає. Якщо
  скопіювати приклад як є, продакшн-збірка кине `TypeError` уже під час обробки помилки.
- `render` повертає `this.props.fallback`, тому запасний екран передають пропсом, як показує наступний фрагмент
  сторінки з `<ErrorBoundary fallback={<p>Something went wrong</p>}>`.

Розділ закінчується порадою, де ставити межі. Огортати кожен компонент не треба. Межу ставлять там, де людині має сенс
побачити повідомлення про помилку: у програмі повідомлень навколо списку розмов і навколо кожного повідомлення, але не
навколо кожного аватара. Остання примітка каже, що функцією межу поки написати не можна, а замість власного класу
можна взяти пакет `react-error-boundary`. Практика дня просить власний клас.

### `Reference` › `static getDerivedStateFromError(error)`

Цей метод описано на тій самій сторінці, але в розділі `Reference`, далеко від прикладу. React викликає його, коли
дочірній компонент, хоч би як глибоко він стояв, кинув помилку під час рендеру. Метод має повернути стан, з яким межа
покаже повідомлення про помилку.

- **`Parameters`.** Метод отримує кинуте значення. Сторінка нагадує, що здебільшого це об'єкт `Error`, але JavaScript
  дозволяє кинути будь-що, навіть рядок чи `null`. Тому в TypeScript параметр має тип `unknown`.
- **`Returns`.** Метод повертає стан, який каже межі показати запасний екран.
- **`Caveats`.** Метод має бути чистою функцією. Для побічних дій, наприклад виклику аналітики, потрібен
  `componentDidCatch`. Наш запуск показав, чому чистота тут важлива: React викликав цей метод двічі на одну помилку,
  бо після невдалого рендеру робить ще одну синхронну спробу.

Примітка наприкінці каже, що відповідника цього методу для функцій поки немає, і повторює пораду про один спільний
клас межі або пакет `react-error-boundary`.

### `Reference` › `componentDidCatch(error, info)`

React викликає цей метод, коли дочірній компонент кинув помилку під час рендеру. Сторінка радить ним записувати
помилку в сервіс звітів у продакшн-збірці. Клас, який має обидва методи, сторінка й називає межею помилок.

- **`Parameters`.** Перший параметр той самий, що в `getDerivedStateFromError`. Другий, `info`, має поле
  `componentStack`, тобто стек компонентів: компонент, що кинув помилку, і всі його батьки з назвами та місцями у
  вихідному коді. Сторінка попереджає, що в продакшн-збірці назви стиснуті, і радить розшифровувати стек картами коду
  так само, як звичайні стеки помилок. Наш запуск у продакшн-збірці показав рядки `at y`, `at b`, `at h` замість
  `StopRow`, `StopList` і межі.
- **`Returns`.** Метод нічого не повертає.
- **`Caveats`.** Тут два пункти. Перший каже, що раніше запасний екран показували, викликаючи `setState` усередині
  `componentDidCatch`, і що тепер для цього є `getDerivedStateFromError`. Другий каже, що в режимі розробки помилки,
  зловлені `componentDidCatch`, доходять до `window`, а в продакшн-збірці ні. Наш запуск на React 19.3.1 цього не
  підтвердив: зловлена помилка не дала події `error` вікна ні в режимі розробки, ні в продакшн-збірці. Посібник з
  переходу на React 19 пояснює, що React більше не кидає зловлену помилку вдруге, а друкує її через `console.error`.
  Схоже, що другий пункт описує поведінку старших версій.

## `createRoot`, розділ `Error logging in production`

**Де читати:**
[react.dev/reference/react-dom/client/createRoot](https://react.dev/reference/react-dom/client/createRoot), розділ
[Error logging in production](https://react.dev/reference/react-dom/client/createRoot#error-logging-in-production).

**Що це за текст.** Це сторінка довідника про функцію, яка створює корінь React у DOM-елементі. Ваш `main.tsx` уже
викликає її. Сьогодні з неї потрібні опис параметрів і розділ про журнал помилок.

**Якщо часу мало,** прочитайте `Parameters` і `Error logging in production`.

### `Reference` › `createRoot(domNode, options?)` › `Parameters`

Перший параметр, `domNode`, є DOM-елементом, у якому React малюватиме. Другий, `options`, є необов'язковим об'єктом
параметрів кореня. Три з них стосуються помилок, і всі три отримують помилку та об'єкт `errorInfo` з полем
`componentStack`.

| Параметр | Коли React його викликає | Наш запуск |
|----------|--------------------------|------------|
| `onCaughtError` | межа помилок зловила помилку | викликано один раз, перед `componentDidCatch` межі |
| `onUncaughtError` | помилку не зловила жодна межа | у браузері викликано, документ порожній; у Vitest під `act` не викликано, бо `act` кидає помилку сам |
| `onRecoverableError` | React сам оговтався від помилки | компонент упав лише на першій спробі; React показав справжній вміст і передав власну помилку з початковою в полі `cause` |

Четвертий параметр, `identifierPrefix`, стосується хука `useId` і сьогодні не потрібен. Окремий розділ
`Troubleshooting` нагадує типову помилку: параметри передають у `createRoot`, а не другим аргументом у `root.render`.

### `Usage` › `Error logging in production`

Перше речення каже, що за замовчуванням React друкує всі помилки в консоль. Щоб зробити власний звіт, передають три
параметри з розділу вище. Перший приклад передає лише `onCaughtError`, який надсилає звіт функцією
`reportCaughtError`, крім помилки з текстом «Known error». Такий фільтр показує, що в обробнику можна відкинути
помилки, про які ви вже знаєте.

Другий приклад складається з двох файлів. Файл `reportError.js` має функцію `reportError`, яка друкує тип помилки,
саму помилку й стек компонентів через `console.error`, і три обробники, які її викликають. Коментар у ній каже, що
`console.error` стоїть тут лише для показу, а справжня реалізація залежить від вас. Файл з `createRoot` передає ці три
обробники в корінь. Над ними стоїть важливий коментар: у режимі розробки ці параметри варто прибрати, щоб лишалися
типові обробники React, або зробити власне вікно для помилок. У прикладі їх передано завжди лише для показу.

Наш запуск пояснює, навіщо цей коментар. Без ваших обробників React у режимі розробки друкує, у якому компоненті
сталася помилка і яка межа її зловила, а для помилки без межі ще й радить поставити межу. З вашими обробниками цих
повідомлень немає, бо ваш код заміняє типовий. Для помилки без межі зникає навіть подія `error` вікна, бо типовий
обробник передавав помилку функції `reportError`, а ваш цього не робить.

Третій файл прикладу, `App.js`, має компонент `Boom`, який падає, бо звертається до неіснуючої змінної, і дві кнопки:
одна показує `Boom` без межі, друга показує його всередині `ErrorBoundary`. Перша кнопка дає помилку без межі, друга
дає помилку, яку зловила межа. Практика дня робить те саме з помилкою, кинутою в рендері.

## `Sentry for React`, розділ `Capture React Errors (React 19+)`

**Де читати:**
[docs.sentry.io/platforms/javascript/guides/react](https://docs.sentry.io/platforms/javascript/guides/react/).

**Що це за текст.** Це сторінка документації Sentry з першим підключенням SDK для React. **SDK**, тобто software
development kit, тут означає пакет `@sentry/react`, який ставлять у застосунок, щоб він надсилав помилки в Sentry.
Сторінка покрокова: встановити пакет, налаштувати, перевірити. Розбір переказує її своїми словами й не наводить коду,
бо умови цієї документації відрізняються від умов документації React.

**Якщо часу мало,** прочитайте лише `Capture React Errors (React 19+)`.

### `Install`

Пакет ставлять командою `npm install @sentry/react`. Сьогодні ви його не ставите.

### `Configure` › `Initialize the Sentry SDK` і `Apply Instrumentation to Your App`

Налаштування Sentry кладуть в окремий файл, у прикладі він називається `instrument.js`. Сторінка двічі наголошує, що
цей файл імпортують першим рядком у точці входу застосунку, ще до інших імпортів. Причини сторінка не пояснює.
Найпростіше пояснення таке: модулі виконуються в порядку імпортів, тому лише перший імпорт гарантує, що SDK почне
слухати помилки раніше за будь-який інший код. У вашому проєкті точкою входу є `main.tsx`.

### `Configure` › `Capture React Errors (React 19+)`

Розділ, заданий на сьогодні. Перше речення каже, що React 19 додав хуки помилок, які поєднуються з Sentry. Під хуками
тут мають на увазі не хуки React на кшталт `useState`, а три параметри `createRoot` з читання вище. Приклад передає в
кожен із них функцію `Sentry.reactErrorHandler()`. Для `onUncaughtError` вона ще отримує власну функцію, яка друкує
попередження з помилкою і стеком компонентів, тобто Sentry дає змогу і надіслати звіт, і додати свою дію.

Під прикладом стоїть згорнута примітка для React 18 і старших версій. Там хуків помилок немає, тому помилки рендеру
ловлять компонентом `Sentry.ErrorBoundary`, який і показує запасний екран, і надсилає звіт.

Навіщо це сьогодні. Ваш обробник `onCaughtError` з практики стоїть саме там, де пізніше стане
`Sentry.reactErrorHandler()`. Якщо ви колись підключите Sentry, міняти доведеться один рядок `createRoot`, а не межі.

Сторінка називає карти коду обов'язковими для помилок з продакшн-збірки, бо без них стек вказує на стиснутий код. Наш
запуск показав, як це виглядає: `at y` замість `at StopRow`. Налаштовують це майстром Sentry, і цей крок належить
плану Next.js.

### `Verify Your Setup`

Сторінка пропонує перевірити підключення кнопкою, яка кидає помилку в `onClick`, і окремо попереджає, що помилки,
викликані з консолі інструментів розробника, Sentry не бачить. Наш запуск показав, що помилку з `onClick` межа й
параметри кореня не отримують, вона доходить лише до події `error` вікна. Отже, таку помилку SDK може отримати лише
через загальний обробник вікна, а не через межу.

## `React Error Boundary`, розділ `Error Hooks vs ErrorBoundary`

**Де читати:**
[docs.sentry.io/platforms/javascript/guides/react/features/error-boundary](https://docs.sentry.io/platforms/javascript/guides/react/features/error-boundary/).

**Що це за текст.** Це сторінка документації Sentry про її власний компонент межі помилок і про те, коли брати його, а
коли параметри `createRoot`. Як і попередню, розбір її лише переказує.

**Якщо часу мало,** прочитайте `Quick Reference` і `Error Hooks vs ErrorBoundary`.

### `Quick Reference`

Таблиця з п'яти рядків: ситуація і рішення. Для React 19 загальний звіт про всі помилки дають параметри `createRoot` з
`reactErrorHandler()`. Обробку помилки в окремій частині сторінки із запасним екраном дає `Sentry.ErrorBoundary`.
Позначити, з якої частини застосунку прийшла помилка, допомагає пропс `beforeCapture`. Для власного класу межі є
функція `captureReactException`, яку викликають у `componentDidCatch`.

### `Basic Usage`

Компонент `Sentry.ErrorBoundary` огортає частину сторінки й отримує пропс `fallback`, як межа з довідника React.
Сторінка перелічує, що стається, коли всередині впала помилка: Sentry отримує помилку разом зі стеком компонентів,
замість частини з'являється запасний екран, а решта застосунку працює далі.

### `Error Hooks vs ErrorBoundary`

Розділ, заданий на сьогодні. Сторінка порівнює два підходи таблицею.

| Підхід | Що охоплює | Що робить |
|--------|------------|-----------|
| `reactErrorHandler()` у параметрах `createRoot`, React 19 і новіші | увесь застосунок | лише надсилає звіт, інтерфейсу не змінює |
| `Sentry.ErrorBoundary` | лише огорнуту частину | надсилає звіт і показує запасний екран для цієї частини |

Далі сторінка каже, що в React 19 ці підходи доповнюють один одного. Параметри кореня є загальною страховкою для
звітів, а межі дають запасні екрани для окремих частин. У React 18 і старших межа є головним інструментом і для
звітів, і для запасного екрана. Приклад під таблицею показує саме таку пару: три параметри кореня з
`reactErrorHandler()` і окрему межу навколо панелі `Dashboard`.

Для вашої практики висновок той самий, що й з довідника React. Межа відповідає за те, що людина бачить, коли частина
впала, а параметри кореня відповідають за те, куди піде повідомлення про помилку.

### `Multiple Boundaries`, `Custom Error Boundaries` і `Fallback UI Options`

Решту сторінки сьогодні досить переглянути.

- **`Multiple Boundaries`.** Окремі межі для бічної панелі й основного вмісту, щоб збій однієї частини не зачіпав
  іншої. Пропс `beforeCapture` додає до звіту позначку частини сторінки.
- **`Custom Error Boundaries`.** Власний клас межі, у якому `componentDidCatch` викликає
  `Sentry.captureReactException`. Сторінка окремо підкреслює, що власна межа мусить бути класом і що це вимога React,
  а не Sentry. Функція потребує SDK версії 9.8.0 чи новішої.
- **`Fallback UI Options`.** Пропс `fallback` може бути не лише елементом, а й функцією, яка отримує помилку, стек
  компонентів і функцію `resetError`. Остання скидає межу й пробує відрендерити вміст ще раз, тобто робить те, що в
  лекції описано як скидання стану межі.

## Запитання для перевірки

**1. Модуль ледачого компонента експортує його так: `export function Chart() {...}`. Що піде не так?**

<details><summary>Відповідь</summary>

Сторінка `lazy` вимагає, щоб обіцянка `load` завершилася об'єктом, у якого поле `.default` містить компонент.
Іменований експорт `Chart` не потрапляє в `.default`, тому React не знайде компонента. Модуль має експортувати
компонент як `export default`.

</details>

**2. Компонент завантажує дані в `useEffect`, а навколо стоїть `<Suspense>`. Чому запасний вміст не з'являється?**

<details><summary>Відповідь</summary>

Перше застереження сторінки `<Suspense>` каже, що межа не помічає запитів з ефектів і обробників. Компонент нічого не
чекає: він одразу рендериться з порожніми даними. Межу вмикають лише лінивий код, обіцянка, прочитана через `use`, і
кілька випадків серверного рендеру.

</details>

**3. Чому `getDerivedStateFromError` має бути чистим, а `componentDidCatch` ні?**

<details><summary>Відповідь</summary>

`getDerivedStateFromError` React викликає під час рендеру, щоб отримати новий стан межі, а рендер може повторюватися:
наш запуск показав два виклики на одну помилку. `componentDidCatch` React викликає, коли запасний екран уже показано,
і там дозволено побічні дії, наприклад звіт збирачу.

</details>

**4. Примітка на сторінці `Component` перелічує, чого межа не ловить. Назвіть пункти й виняток.**

<details><summary>Відповідь</summary>

Межа не ловить помилок в обробниках подій, під час серверного рендеру, у самій межі та в асинхронному коді на кшталт
`setTimeout`. Виняток стосується функції, переданої в `startTransition` з хука `useTransition`: її помилки межа
ловить.

</details>

**5. Чому приклад на сторінці `createRoot` радить прибрати власні обробники в режимі розробки?**

<details><summary>Відповідь</summary>

Власний обробник заміняє типовий. Типовий у режимі розробки друкує назву компонента, що впав, і назву межі, а для
помилки без межі радить її поставити. З власним обробником ці підказки зникають, тому для розробки або лишають типові
обробники, або роблять власне вікно для помилок.

</details>

**6. Документація Sentry для React 19 радить і параметри `createRoot`, і `Sentry.ErrorBoundary`. Навіщо обидва?**

<details><summary>Відповідь</summary>

Параметри кореня з `reactErrorHandler()` надсилають звіти про всі помилки застосунку, але інтерфейсу не змінюють. Межа
показує запасний екран для своєї частини сторінки й може позначити, з якої частини прийшла помилка. Одне відповідає за
звіт, друге за те, що бачить людина.

</details>

**7. Застереження до `componentDidCatch` каже, що в режимі розробки зловлені помилки доходять до `window`. Що показав
наш запуск і чим це пояснюється?**

<details><summary>Відповідь</summary>

На React 19.3.1 зловлена помилка не дала події `error` вікна ні в режимі розробки, ні в продакшн-збірці: React
надрукував її через `console.error`, і все. Посібник з переходу на React 19 каже, що React більше не кидає зловлену
помилку вдруге. Отже, застереження, схоже, описує старші версії.

</details>
