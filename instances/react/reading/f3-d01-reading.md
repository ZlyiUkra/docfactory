## `Picking a Mode`

**Де читати:** [reactrouter.com/start/modes](https://reactrouter.com/start/modes).

**Що це за текст.** Це сторінка розділу Getting Started, яка допомагає вибрати, як уживати React Router. Вона
коротка, а половину її займає таблиця.

**Якщо часу мало,** прочитайте вступ і розділ `Decision Advice`.

### Вступ

Сторінка називає React Router маршрутизатором з кількома стратегіями і каже, що вживати його можна в трьох **режимах**.
Можливості режимів складаються: декларативний режим дає найменше, режим даних додає до нього нове, а фреймворк додає
ще більше. Платою за кожен крок вгору сторінка називає менший контроль над архітектурою, тобто ви менше вирішуєте самі.
Режим визначає API верхнього рівня, тобто той компонент чи функцію, якою ви запускаєте маршрутизатор. Сторінка
пояснює також значки, які стоять на інших сторінках документації: значок показує, для якого режиму написано текст.
Сьогодні вам потрібні сторінки зі значком `data`.

### `Declarative`

Декларативний режим дає основне: зіставити адресу з компонентами, переходити між сторінками й показувати активне
посилання. Сторінка називає `<Link>`, `useNavigate` і `useLocation`. Запускають його компонентом `<BrowserRouter>`, яким
огортають увесь застосунок:

```tsx
// приклад зі сторінки Picking a Mode
import { BrowserRouter } from "react-router";

ReactDOM.createRoot(root).render(
  <BrowserRouter>
    <App />
  </BrowserRouter>,
);
```

Маршрути в цьому режимі описують JSX-компонентами `<Routes>` і `<Route>` прямо в дереві React. Ви їх сьогодні не
пишете.

### `Data`

Тут сторінка пояснює головну відмінність режиму даних: опис маршрутів винесено з рендеру React. Маршрути описані
звичайним масивом об'єктів ще до того, як React щось рендерить. Тому маршрутизатор може завантажити дані, обробити
форму й показати стан очікування до рендеру сторінки. Сторінка називає `loader`, `action` і `useFetcher`. Приклад
показує той самий запуск, що й у лекції:

```tsx
// приклад зі сторінки Picking a Mode
let router = createBrowserRouter([
  {
    path: "/",
    Component: Root,
    loader: loadRootData,
  },
]);

ReactDOM.createRoot(root).render(
  <RouterProvider router={router} />,
);
```

Слово `let` тут не має особливого змісту: автори документації просто так пишуть змінні. У вашому коді буде `const`.

### `Framework`

Фреймворк огортає режим даних плагіном Vite. Сторінка перелічує, що він додає: функцію `href` і модулі маршрутів з
перевіркою типів, розумне розділення коду, рендер на сервері, статичний рендер і режим односторінкового застосунку.
Маршрути тут лежать в окремих файлах, а кожен файл експортує лоадер і компонент. Слова «модуль маршруту» означають
саме такий файл. План цього режиму не бере: рендер на сервері вивчає фаза 4 цього плану, а фреймворк із серверним
рендером ви побачите в плані Next.js.

### `Decision Advice`

Цей розділ починається з думки, яку варто запам'ятати: кожен режим підтримує будь-яку архітектуру й будь-яке місце
викоту, тож питання не в тому, чи потрібен вам рендер на сервері, а в тому, скільки ви хочете робити самі. Далі йдуть
три переліки.

| Режим | Кому сторінка радить його |
|-------|----------------------------|
| фреймворк | тим, хто ще не має власної думки; хто порівнює Next.js, SvelteKit, Astro та інші; хто, можливо, захоче рендер на сервері; хто переходить з Next.js |
| режим даних | тим, хто хоче можливостей роботи з даними, але сам керує збіркою, даними й сервером; хто вже вживає маршрутизатор даних з версії 6.4 |
| декларативний | тим, хто хоче найпростішого; хто прийшов зі старих версій і задоволений `<BrowserRouter>`; у кого власний шар даних; хто переходить із Create React App |

Може здатися, що план суперечить сторінці, адже ви новачок у React Router, а сторінка радить новачкам фреймворк. Але
ваш випадок описує другий рядок: збірку Vite ви налаштували у фазі 1 й керуєте нею самі, а дані план хоче
завантажувати в лоадерах, як радить документація React. Лекція в розділі «Три режими React Router» пояснює цей вибір
докладніше.

### `API + Mode Availability Table`

Сторінка сама жартує, що таблиця написана переважно для мовних моделей. Це довгий перелік компонентів і хуків із
позначками, у якому режимі кожен доступний. Читати його цілком не треба, але він зручний як довідка. З нього видно,
що `Link`, `NavLink`, `Outlet`, `useParams` і `useNavigate` є в усіх трьох режимах, а `useLoaderData`, `useNavigation`
і `useRouteError` з'являються лише в режимі даних і у фреймворку. Рядки `Links`, `Meta` і `Scripts` позначено лише для
фреймворку, бо ці компоненти малюють сторінку на сервері.

## `Installation`

**Що це за текст.** Перша сторінка розділу Data Mode. Вона займає один екран і показує, як запустити маршрутизатор
даних.

**Якщо часу мало,** прочитайте розділ `Create a Router and Render` і примітку під ним.

### `Bootstrap with a Bundler Template`

Сторінка пропонує почати з шаблону Vite і вибрати React або зібрати застосунок будь-яким іншим збирачем. Ваш проєкт
уже створено з шаблону Vite у фазі 0, тому цей крок ви пропускаєте.

### `Install React Router`

Тут одна команда, `npm i react-router`. Скорочення `i` означає `install`. Без номера версії npm поставить найновішу
стабільну, тобто ту, що позначена в реєстрі як `latest`. Наш запуск `npm view react-router dist-tags` показав, що 24
листопада 2026 року це 8.5.3. Щоб у вас стояла та сама версія, що й у лекції, пишіть `npm install react-router@8.5.3`.
Старі посібники ставлять ще пакет `react-router-dom`, але лінії 8 цього пакета немає: наш запуск
`npm view react-router-dom version` показав 7.18.7. Усе, що треба для браузера, лежить у пакеті `react-router` і в
його вході `react-router/dom`.

### `Create a Router and Render`

Розділ показує повний файл запуску:

```tsx
// приклад зі сторінки Installation
import React from "react";
import ReactDOM from "react-dom/client";
import { createBrowserRouter } from "react-router";
import { RouterProvider } from "react-router/dom";

const router = createBrowserRouter([
  {
    path: "/",
    element: <div>Hello World</div>,
  },
]);

const root = document.getElementById("root");

ReactDOM.createRoot(root).render(
  <RouterProvider router={router} />,
);
```

Тут три речі варто помітити.

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `createBrowserRouter` імпортовано з `react-router`, а `RouterProvider` з `react-router/dom` | версія `RouterProvider` з `react-router/dom` сама підключає функцію `flushSync` з `react-dom`, як каже довідник `RouterProvider`; так і пишіть |
| маршрут має поле `element` з JSX | на сторінці `Routing` ті самі маршрути записано полем `Component` з функцією компонента; обидва записи робочі |
| `getElementById("root")` без знака оклику | у TypeScript зі строгою перевіркою ця функція може повернути `null`, тому в шаблоні Vite стоїть `document.getElementById('root')!`; приклад написано так, ніби це JavaScript |

Імпорт `React` у першому рядку для React 19 з налаштуваннями шаблону Vite не потрібен: JSX перетворюється без нього.
У вашому `main.tsx` уже є `StrictMode` і `createRoot`, тож ви лише заміняєте `<App />` на
`<RouterProvider router={router} />`.

**Примітка `docs-info`.** Під кодом стоїть рамка з важливим правилом: маршрутизатор даних не можна тримати в стані
React. Його створюють один раз поза деревом React і передають у `<RouterProvider>`. Рамка також називає параметр
`patchRoutesOnNavigation`, через який маршрути можна додавати пізніше. Сьогодні він не потрібен.

## `Routing`

**Де читати:** [reactrouter.com/start/data/routing](https://reactrouter.com/start/data/routing).

**Що це за текст.** Головна сторінка дня. Вона показує, як описати дерево маршрутів масивом об'єктів, і перелічує всі
види маршрутів і сегментів адреси.

**Якщо часу мало,** прочитайте `Configuring Routes`, `Nested Routes`, `Index Routes` і `Dynamic Segments`.

### `Configuring Routes`

Маршрути передають першим аргументом у `createBrowserRouter`. Мінімум для маршруту, як каже сторінка, це шлях і
компонент. Більший приклад на сторінці варто розібрати, бо він показує одразу кілька видів маршрутів:

```ts
// приклад зі сторінки Routing
createBrowserRouter([
  {
    path: "/",
    Component: Root,
    children: [
      { index: true, Component: Home },
      { path: "about", Component: About },
      {
        path: "auth",
        Component: AuthLayout,
        children: [
          { path: "login", Component: Login },
          { path: "register", Component: Register },
        ],
      },
      {
        path: "concerts",
        children: [
          { index: true, Component: ConcertsHome },
          { path: ":city", Component: ConcertsCity },
          { path: "trending", Component: ConcertsTrending },
        ],
      },
    ],
  },
]);
```

| Маршрут | Яку адресу дає | Що показує |
|---------|----------------|------------|
| `index: true, Component: Home` | `/` | `Home` усередині `Root` |
| `path: "about"` | `/about` | `About` усередині `Root` |
| `path: "auth"` з дітьми | `/auth/login`, `/auth/register` | сторінку входу чи реєстрації всередині `AuthLayout`, а той усередині `Root` |
| `path: "concerts"` без компонента | `/concerts`, `/concerts/:city`, `/concerts/trending` | дітей одразу всередині `Root`, без спільної обгортки |

Зверніть увагу на `:city` і `trending` поруч. Адреса `/concerts/trending` підходить до обох, і лекція в розділі «Як
маршрутизатор вибирає гілку» показала на нашому запуску, що виграє сталий сегмент, незалежно від порядку в масиві.

### `Route Objects`

Тут сторінка лише називає **об'єкт маршруту**, тобто кожен елемент масиву, і каже, що він описує не тільки шлях і
компонент, а й завантаження даних та дії. Приклад показує лоадер, який читає параметр `params.teamId`, і компонент, що
бере результат через `useLoaderData`. Це матеріал наступного дня. Повний перелік полів дає окрема сторінка
`Route Object`.

### `Nested Routes`

Маршрут вкладають у батька через поле `children`. Сторінка каже дві речі:

- шлях батька автоматично входить у шлях дитини, тому маршрут `settings` під `/dashboard` дає адресу
  `/dashboard/settings`;
- дочірній маршрут рендериться там, де батько поставив `<Outlet/>`.

Приклад компонента `Dashboard` показує заголовок і `<Outlet />` з коментарем, що на цьому місці буде або `Home`, або
`Settings`. Наш запуск у лекції, розділ «Каркас і `<Outlet>`», показав те саме: при переході шапка лишилася, а
змінився лише вміст `<Outlet />`.

### `Layout Routes`

**Маршрут каркаса без шляху** має компонент і дітей, але не має `path`. Він додає спільну обгортку для дітей, не
додаючи сегмента до адреси. У прикладі сторінки `Home` і `Contact` рендеряться в `<Outlet />` компонента
`MarketingLayout`. Другий приклад цікавіший: усередині префікса `projects` є такий маршрут каркаса з дітьми `:pid` і
`:pid/edit`. Тому сторінки проєкту й редагування отримують каркас `ProjectLayout`, а сторінка `ProjectsHome` з адресою
`/projects` його не отримує. Так одна група адрес може мати різні обгортки.

### `Index Routes`

**Індексний маршрут** позначають `index: true`, і він не має шляху. Сторінка порівнює його з дочірнім маршрутом за
замовчуванням: він рендериться в `<Outlet>` батька за адресою самого батька. У прикладі `DashboardHome` показується
на `/dashboard`, а `DashboardSettings` на `/dashboard/settings`. Наостанок сторінка каже, що індексний маршрут не може
мати дітей. Це логічно: у нього немає власного шляху, до якого діти могли б дописати свій.

### `Prefix Route`

**Маршрут-префікс** має шлях і дітей, але не має компонента. Він створює групу адрес зі спільним початком і не додає
обгортки. Приклад сторінки дає адреси `/projects`, `/projects/:pid` і `/projects/:pid/edit`. Лекція наводить цей
приклад повністю в розділі «Індексний маршрут, маршрут без шляху й маршрут без компонента».

### `Dynamic Segments`

**Динамічний сегмент** починається з двокрапки. Коли маршрут збігається з адресою, значення цього сегмента
маршрутизатор передає як `params` в інші свої API. Сторінка показує два місця, де їх читають: лоадер отримує
`params` в аргументі, а компонент викликає хук `useParams`. В одному шляху може бути кілька параметрів, як у
`c/:categoryId/p/:productId`.

Сторінка не каже прямо, якого типу значення параметра. Наш запуск у лекції, розділ «Параметри шляху», показав, що це
завжди рядок, а TypeScript дає тип `string | undefined`. Тому номер із адреси перетворюють на число самі.

### `Optional Segments`

Знак питання в кінці сегмента робить його необов'язковим. Шаблон `:lang?/categories` збігається і з адресою з мовою,
і без неї. Необов'язковим може бути й сталий сегмент: `users/:userId/edit?` збігається і з `/users/5`, і з
`/users/5/edit`.

### `Splats`

Шаблон, який закінчується на `/*`, збігається з усім, що стоїть після косої риски, разом з іншими косими рисками.
Сторінка каже, що такий сегмент ще називають «catchall» і «star», тобто «ловить усе» і «зірочка». Залишок адреси
лежить у `params["*"]`. Оскільки ім'я `*` не можна написати змінною напряму, сторінка показує, як дати йому інше ім'я
при деструктуризації: `const { "*": splat } = params`. Маршрут `path: '*'` для сторінки 404 є окремим випадком
цього шаблону: наш запуск `matchRoutes` для адреси `/kontakty` поклав у параметр `*` значення `kontakty`.

## `Navigating`

**Де читати:** сторінка розділу Data Mode
[reactrouter.com/start/data/navigating](https://reactrouter.com/start/data/navigating) має одне речення: у режимі
даних переходи такі самі, як у фреймворку. Тому читайте сторінку фреймворку
[reactrouter.com/start/framework/navigating](https://reactrouter.com/start/framework/navigating).

**Що це за текст.** Огляд способів перейти на іншу адресу. Значок на сторінці каже `framework`, але все, що тут
описано, працює й у режимі даних.

**Якщо часу мало,** прочитайте `NavLink`, `Link` і `useNavigate`.

### `Introduction`

Сторінка перелічує п'ять способів: `<Link>`, `<NavLink>`, `<Form>`, `redirect` і `useNavigate`.

### `NavLink`

Цей компонент потрібен для посилань, яким треба показувати активний стан і стан очікування. Приклад будує меню з
чотирьох пунктів. Два перші мають проп `end`, бо інакше пункт «Home» з `to="/"` чи «Trending Concerts» світився б на
глибших адресах. Наш запуск показав, що без `end` посилання «Книжки» активне й на `/books/2`. Довідник `NavLink` додає
виняток для `to="/"`: такий пункт і без `end` активний лише на самій `/`.

Далі сторінка показує класи, які `NavLink` додає сам: `active`, коли адреса збігається, і `pending`, коли маршрутизатор
уже йде на цю адресу, але ще чекає лоадерів. Наш запуск показав і третю річ, про яку ця сторінка не пише: активне
посилання отримує атрибут `aria-current="page"` для програм читання з екрана.

Пропи `className`, `style` і `children` можуть бути функціями. React Router викликає їх з об'єктом, у якому є поля
`isActive` і `isPending`, і бере результат:

```tsx
// приклад зі сторінки Navigating
<NavLink
  to="/messages"
  className={({ isActive, isPending }) =>
    [
      isPending ? "pending" : "",
      isActive ? "active" : "",
    ].join(" ")
  }
>
  Messages
</NavLink>
```

**Що змінилося у 8.5.** У версії 8.4.0 ці функції отримували ще поле `isTransitioning`, а приклад мав клас
`transitioning`. У 8.5.3 сторінка прибрала їх і додала речення: старий проп і клас застарілі, і для анімації переходів
тепер радять компонент React `<ViewTransition>`. Журнал змін пакета для 8.5.0 каже те саме: усі API анімації переходів
React Router позначено застарілими на користь компонента React, доступного з React 19.3, а стара поведінка поки
працює. Сервер `react-router-docs` знає лише 8.4.0, тож покаже старий варіант.

### `Link`

`<Link>` радять тоді, коли активний стан не потрібен. Приклад показує повідомлення «You've been logged out» з
посиланням на вхід. Наш запуск у браузері, лекція, розділ «`<Link>` проти звичайного посилання», показав, чим він
кращий за ручний `<a>`: клацання змінює адресу без нового запиту документа, і стан сторінки зберігається.

### `Form`

Форма маршрутизатора теж переходить на іншу адресу. Форма з методом GET збирає поля в параметри після знака питання:
приклад перетворює слово «journey» в адресу `/search?q=journey`. Форма з `method="post"` надсилає дані як `FormData`
дії маршруту. Сторінка додає, що для надсилання форми частіше вживають `useFetcher`. Обидві теми належать наступному
дню.

### `redirect`

У лоадерах і діях можна повернути `redirect` на іншу адресу. Перший приклад сторінки показує саме охоронця: якщо
користувача немає, лоадер повертає `redirect("/login")`. Другий приклад перенаправляє після створення запису на його
сторінку. Наш запуск показав, що `redirect` повертає звичайний об'єкт `Response` зі статусом 302 і заголовком
`Location`.

Перший приклад читає користувача із запиту функцією `getUser(request)`. На сервері так перевіряють куку сесії. У
вашому застосунку лоадер працює в браузері, тому перевірка в ньому лише ховає екран. Це і є пастка дня, а лекція в
розділі «Чому це не захист» показує, як один рядок у консолі її обходить.

### `useNavigate`

Хук дає функцію переходу з коду, без дії людини. Сторінка радить уживати його рідко і лише тоді, коли людина нічого не
натискала: для виходу після бездіяльності чи для тестів з обмеженим часом. Для всього іншого краще підходять інші
способи зі сторінки. Наша сторінка входу вживає `useNavigate` в обробнику форми лише тому, що форму маршрутизатора ви
вивчите завтра.

## `Single Page App (SPA)`, крок `4. Direct all URLs to index.html`

**Де читати:** [reactrouter.com/how-to/spa](https://reactrouter.com/how-to/spa).

**Що це за текст.** Посібник з розділу How-To. Значок каже `framework`, і майже вся сторінка про фреймворк. Перша
рамка прямо каже, що в режимі даних ви будуєте односторінковий застосунок так, як вважаєте за потрібне. Вам потрібен
лише крок 4, на який посилається перевірка дня.

**Якщо часу мало,** прочитайте лише крок 4.

### Кроки 1–3

Вони вимикають рендер на сервері в налаштуваннях фреймворку, додають компонент `HydrateFallback` для екрана
завантаження й переносять лоадери в `clientLoader`. Вашому проєкту це не потрібно. У версії 8.5.3 тут з'явилася
додаткова рамка про експериментальний режим, де односторінковий застосунок отримує дані від серверних лоадерів. Вона
теж стосується лише фреймворку.

### `4. Direct all URLs to index.html`

Це загальне правило для будь-якого односторінкового застосунку, незалежно від режиму. Хостинг треба налаштувати так,
щоб на будь-яку адресу він віддавав `index.html` зібраного застосунку. Сторінка каже, що деякі хостинги роблять це
самі, а деякі ні, і як приклад показує рядок для файла `_redirects`:

```text
/*    /index.html   200
```

Такий файл розуміє Netlify. Остання фраза кроку стисло описує симптом: якщо правильні адреси вашого застосунку дають
404, найпевніше, хостинг не налаштовано. Лекція в розділі «Глибоке посилання й оновлення сторінки» показала це
запуском: `vite preview` віддав сторінку книжки після оновлення, а наш простий сервер без правила відповів 404.

## `Vite on Vercel`, розділ `Using Vite to make SPAs`

**Де читати:** [vercel.com/docs/frameworks/frontend/vite](https://vercel.com/docs/frameworks/frontend/vite),
розділ `Using Vite to make SPAs`. Сервер `vercel-docs` знаходить цей розділ на запит «Using Vite to make SPAs».

**Що це за текст.** Сторінка документації Vercel про проєкти на Vite. Вона коротка, а вам потрібен один розділ. Ми
нічого не викочували на Vercel, тому все нижче описано за документацією, а не перевірено запуском.

**Якщо часу мало,** прочитайте лише розділ `Using Vite to make SPAs`.

### `Getting started`

Розділ каже, що проєкт на Vite можна викласти командою `vercel` з кореня проєкту або підключити репозиторій, і тоді
кожен запит на злиття отримає окрему адресу для перегляду. Обидва шляхи розбирав розбір читання дня «Збірка, перший
викот і журнал вимірів».

### `Using Vite to make SPAs`

Розділ починається з прямого попередження: якщо застосунок на Vite викочено як односторінковий, глибокі посилання
одразу не працюють. Далі він просить створити файл `vercel.json` у корені проєкту з правилом `rewrites`:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

| Що на сторінці | Що це означає для вас |
|----------------|------------------------|
| `rewrites` | **переписування**: Vercel віддає вміст `destination`, а адреса в браузері лишається тією, яку просили |
| `"source": "/(.*)"` | шаблон, що збігається з будь-яким шляхом |
| «у корені проєкту» | ваш застосунок лежить у `spa/`, і ця тека записана в поле `Root Directory`; сторінка Vercel про монорепозиторії кладе `vercel.json` у корінь кожного застосунку, тож файл кладуть у `spa/` поруч із `package.json` і комітять у git; ми цього не перевіряли |
| примітка про `cleanUrls` | якщо в тому самому файлі ввімкнено `cleanUrls`, шлях пишуть без `.html`, тобто `/`; у вашому файлі цього параметра немає |
| фраза про режим кількох сторінок | сторінка радить для продакшну режим Vite з кількома HTML-файлами, але не пояснює чому; план будує односторінковий застосунок, тому ця порада вам зараз не потрібна |

Довідник `Static Configuration with vercel.json` у розділі `rewrites` додає важливу річ, якої немає на цій сторінці:
спершу Vercel шукає справжній файл і лише потім застосовує переписування. Тому правило `/(.*)` не заміняє вашого
бандла сторінкою: файл `/assets/index-....js` існує й прийде як скрипт. Посібник Vercel `Why is my deployed project
giving a 404?` пояснює, чому правило не ввімкнено саме: Vercel за замовчуванням вважає кожну адресу шляхом до файла,
бо так працюють фреймворки на кшталт Next.js, і не може здогадатися, що ваш застосунок обробляє адреси сам. Там само
названо дві пастки: незакомічений `vercel.json` не діє, і Vercel про це не повідомляє, а набір налаштувань `Other`
замість Vite може завадити правилу.

Що ви маєте побачити. До появи файла оновлення на `/items/2` дає сторінку помилки 404 від Vercel. Після коміту файла
й нової збірки оновлення на `/items/2` показує екран вашого застосунку.

## Запитання для перевірки

**1. Сторінка `Picking a Mode` радить новачкам фреймворк. Чому план бере режим даних?**

<details><summary>Відповідь</summary>

Розділ `Decision Advice` радить режим даних тим, хто хоче лоадерів і дій, але сам керує збіркою й сервером. Збірку Vite
ви налаштували у фазі 1, сервер план вивчає окремо, а документація React радить завантажувати дані в лоадерах
маршрутизатора. Режим даних дає саме це, не міняючи збірки.

</details>

**2. Звідки імпортують `RouterProvider` і чому?**

<details><summary>Відповідь</summary>

З `react-router/dom`, як на сторінці `Installation`. Ця версія сама передає маршрутизатору `flushSync` з `react-dom`.
Версія з `react-router` потрібна там, де DOM немає.

</details>

**3. Що станеться з маршрутизатором, якщо створити його через `createBrowserRouter` усередині компонента?**

<details><summary>Відповідь</summary>

Кожен рендер компонента створить новий маршрутизатор із початковим станом, і стан переходів загубиться. Примітка на
сторінці `Installation` каже створювати маршрутизатор один раз поза деревом React і не тримати його в стані.

</details>

**4. Чим маршрут каркаса без шляху відрізняється від маршруту-префікса?**

<details><summary>Відповідь</summary>

Маршрут каркаса має компонент, але не має шляху: він додає обгортку, нічого не дописуючи до адреси. Маршрут-префікс
має шлях, але не має компонента: він дописує спільний початок адреси, не додаючи обгортки.

</details>

**5. Чому індексний маршрут не може мати дітей?**

<details><summary>Відповідь</summary>

Індексний маршрут не має власного шляху і показується за адресою батька. Діти дописують свій шлях до шляху батька,
тому їм нема до чого дописуватися саме в індексного маршруту. Їх кладуть поруч з ним, у самого батька.

</details>

**6. Сторінка `Navigating` радить уживати `useNavigate` рідко. Для яких випадків вона його лишає?**

<details><summary>Відповідь</summary>

Для переходів, які стаються без дії людини: вихід після бездіяльності, тест з обмеженим часом. Для клацань є
`<Link>` і `<NavLink>`, для форм є `<Form>`, а в лоадерах і діях є `redirect`.

</details>

**7. Ви поклали `vercel.json` з правилом `rewrites` у корінь репозиторію, а застосунок лежить у `spa/`, і ця тека
записана в `Root Directory`. Оновлення на `/items/2` досі дає 404. Що перевірити?**

<details><summary>Відповідь</summary>

Документація Vercel просить класти `vercel.json` у корінь проєкту, а сторінка про монорепозиторії кладе його в
корінь кожного застосунку, тобто в теку з `Root Directory`. Перенесіть файл у `spa/`, поруч із `package.json`,
перевірте, що його закомічено, і що набір налаштувань проєкту вказує Vite, а не `Other`. Потім дочекайтеся нової
збірки. Ми цього на Vercel не перевіряли.

</details>
