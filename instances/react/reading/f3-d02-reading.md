## `Data Loading`

**Що це за текст.** Четверта сторінка розділу Data Mode, одразу після `Route Object`. Вона має два розділи й займає
пів екрана: що повертає лоадер і як компонент отримує результат.

**Якщо часу мало,** прочитайте всю сторінку, це займе хвилину. Важливіше прочитати її уважно, ніж швидко.

### `Providing Data`

Розділ каже одним реченням, що дані потрапляють у компоненти маршрутів з лоадерів, і показує маршрут:

```tsx
// приклад зі сторінки Data Loading
createBrowserRouter([
  {
    path: "/",
    loader: async () => {
      // return data from here
      return { records: await getSomeRecords() };
    },
    Component: MyRoute,
  },
]);
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `loader: async () => { … }` | лоадер записано стрілковою функцією прямо в об'єкті маршруту; у лекції лоадери винесено в окремий файл, бо цього вимагає правило лінту `react-refresh/only-export-components` |
| `getSomeRecords()` | вигадана функція, яка стоїть замість справжнього запиту; на її місці у вас буде `fetch` до API |
| `return { records: … }` | лоадер може повернути будь-яке значення; тут дані загорнуто в об'єкт із полем `records` |
| коментар `return data from here` | «повертайте дані звідси» |

Сторінка не каже, що лоадер отримує аргумент. Лоадер у прикладі не має параметрів, бо йому нічого не треба знати.
Справжньому лоадеру майже завжди потрібні `params`, тобто параметри шляху, і `request` із сигналом скасування.
Їх описує довідник `LoaderFunctionArgs`, а лекція розбирає в розділі «Лоадер: дані до рендеру».

### `Accessing Data`

Компонент отримує дані хуком `useLoaderData`:

```tsx
// приклад зі сторінки Data Loading
import { useLoaderData } from "react-router";

function MyRoute() {
  const { records } = useLoaderData();
  return <div>{records.length}</div>;
}
```

Під кодом стоїть головне речення сторінки: коли людина переходить між маршрутами, лоадери викликаються раніше, ніж
рендериться компонент маршруту. Наш запуск показав це журналом: обидва запити почалися в момент клацання, а компоненти
вперше рендерилися лише тоді, коли закінчився найповільніший лоадер.

Що сторінка лишає поза увагою:

- **Тип даних.** У прикладі `useLoaderData()` викликано без параметра типу. У TypeScript такий виклик повертає `any`,
  і наш запуск `tsc` мовчки пропустив звернення до поля, якого немає. Пишіть `useLoaderData<typeof loader>()`, тоді
  TypeScript знає тип даних лоадера.
- **Вкладені маршрути.** Сторінка не каже, що лоадери всіх маршрутів ланцюжка запускаються одночасно. Про це пише
  сторінка фреймворку `Data Loading` у версії 8.5.3, у новому розділі `Authentication and Authorization`, про який
  нижче. Наш запуск це підтвердив: лоадер автора й лоадер книжок почали роботу на тій самій мілісекунді.
- **Що на екрані, поки лоадер працює.** Про це сторінка `Pending UI` нижче.
- **Помилки.** Як лоадер повідомляє, що запису немає, сторінка не показує. Лекція в розділі «Коли даних немає:
  помилка з лоадера» кидає з лоадера `data(..., { status: 404 })`, і маршрутизатор показує `ErrorBoundary`.

**Навіщо це у вашому проєкті.** Сьогоднішня практика просить переписати два екрани з ефектів на лоадери. Ця сторінка
показує обидві половини такого переписування: лоадер у маршруті й `useLoaderData` у компоненті замість стану й
ефекту.

### `Introduction`

Вступ ставить вимогу: коли людина переходить на нову адресу або надсилає форму, інтерфейс має одразу відповісти
станом очікування або оптимістичним станом. Друге речення важливе: за це відповідає код застосунку. Тобто
маршрутизатор сам нічого не показує, він лише дає вам стан, з якого можна побудувати індикатор.

**Стан очікування** (pending state) означає, що на екрані видно, що робота триває: напис, крутилка, сіре посилання.
**Оптимістичний стан** означає, що на екрані вже показано очікуваний результат, хоча сервер ще не відповів.

### `Global Pending Navigation`

Розділ пояснює, що під час переходу маршрутизатор чекає лоадерів наступної сторінки й лише потім її рендерить. Стан
очікування дає хук `useNavigation`:

```tsx
// приклад зі сторінки Pending UI
import { useNavigation } from "react-router";

export default function Root() {
  const navigation = useNavigation();
  const isNavigating = Boolean(navigation.location);

  return (
    <html>
      <body>
        {isNavigating && <GlobalSpinner />}
        <Outlet />
      </body>
    </html>
  );
}
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `<html>` і `<body>` у компоненті | у фреймворку кореневий компонент малює весь документ; у режимі даних документом є ваш `index.html`, тому індикатор кладуть у каркас, як `Layout` у лекції |
| `Boolean(navigation.location)` | поле `location` є лише під час переходу і містить адресу, куди людина йде; без переходу воно `undefined` |
| `<GlobalSpinner />` | вигаданий компонент із крутилкою; на його місці може бути будь-яке повідомлення |
| `export default function` | у фреймворку кожен файл маршруту експортує компонент за замовчуванням; вам цього не треба |

Наш запуск показав, що під час переходу `navigation.location` містить `/authors/1`, а поточна адреса маршрутизатора
ще лишається `/`. На екрані в цей час стара сторінка. Лекція в розділі «Що бачить людина, поки лоадери працюють»
перевіряє стан не через `location`, а через `navigation.state !== 'idle'`. Обидва записи для переходу посиланням
дають однаковий результат.

### `Local Pending Navigation`

Індикатор можна показати не на всій сторінці, а біля посилання. Учорашнє читання `Navigating` показувало, що пропи
`children`, `className` і `style` компонента `NavLink` можуть бути функціями. Тут вони отримують поле `isPending`:

```tsx
// приклад зі сторінки Pending UI
<NavLink to="/home">
  {({ isPending }) => (
    <span>Home {isPending && <Spinner />}</span>
  )}
</NavLink>
<NavLink
  to="/about"
  style={({ isPending }) => ({
    color: isPending ? "gray" : "black",
  })}
>
  About
</NavLink>
```

Перше посилання показує крутилку поруч із текстом, друге фарбує текст сірим, поки перехід триває. Наш запуск показав
ще простіший спосіб, про який сторінка тут не пише, але згадує сторінка `Navigating`: `NavLink` сам додає клас
`pending` посиланню, на яке клацнули, а після переходу заміняє його на `active`.

### `Pending Form Submission`

Тепер про форми. Сторінка радить для форми, яка має показати стан очікування, насамперед фетчер, бо він має власний
незалежний стан, тоді як звичайна форма запускає загальний перехід:

```tsx
// приклад зі сторінки Pending UI
function NewProjectForm() {
  const fetcher = useFetcher();

  return (
    <fetcher.Form method="post">
      <input type="text" name="title" />
      <button type="submit">
        {fetcher.state !== "idle"
          ? "Submitting..."
          : "Submit"}
      </button>
    </fetcher.Form>
  );
}
```

Для звичайної `<Form>` стан бере `useNavigation`:

```tsx
// приклад зі сторінки Pending UI
function NewProjectForm() {
  const navigation = useNavigation();

  return (
    <Form method="post" action="/projects/new">
      <input type="text" name="title" />
      <button type="submit">
        {navigation.formAction === "/projects/new"
          ? "Submitting..."
          : "Submit"}
      </button>
    </Form>
  );
}
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `fetcher.state !== "idle"` | у фетчера свій стан: `submitting`, поки працює дія, `loading`, поки перезапускаються лоадери, потім `idle` |
| `navigation.formAction === "/projects/new"` | перевіряє, що триває надсилання саме цієї форми, а не якоїсь іншої на сторінці |
| `"Submitting..."` | «Надсилаю…» |

Друга перевірка має підступ, про який сторінка не пише. Наш запуск показав, що форма в **індексному** маршруті
дописує до адреси параметр `?index`, тож `navigation.formAction` дорівнював `/authors/1?index`, а не `/authors/1`.
Порівняння з адресою без `?index` у такій формі ніколи не спрацювало б. У лекції кнопка перевіряє
`navigation.state === 'submitting'`, і цього досить, коли форма на сторінці одна.

Ще одна відмінність, яку видно з нашого запуску. Під час роботи фетчера `navigation.state` весь час лишався `idle`,
тож загальний індикатор у шапці не з'являвся. Під час роботи `<Form>` стан ішов шляхом `submitting`, `loading`,
`idle`, і шапка показувала «Завантаження…».

### `Optimistic UI`

Останній розділ показує оптимістичний стан. Коли з надісланої форми вже відомо, яким стане результат, його можна
показати одразу:

```tsx
// приклад зі сторінки Pending UI
function Task({ task }) {
  const fetcher = useFetcher();

  let isComplete = task.status === "complete";
  if (fetcher.formData) {
    isComplete =
      fetcher.formData.get("status") === "complete";
  }

  return (
    <div>
      <div>{task.title}</div>
      <fetcher.Form method="post">
        <button
          name="status"
          value={isComplete ? "incomplete" : "complete"}
        >
          {isComplete ? "Mark Incomplete" : "Mark Complete"}
        </button>
      </fetcher.Form>
    </div>
  );
}
```

Рядок за рядком:

- `task.status` береться з даних лоадера: так сервер бачить завдання зараз.
- `fetcher.formData` є лише тоді, коли фетчер надсилає форму. Це `FormData`, тобто набір полів форми, як у лекції.
- Кнопка має `name` і `value`. Коли людина натискає кнопку, браузер кладе її `name` і `value` у дані форми, тому дія
  дізнається, яке значення вибрала людина, а компонент може прочитати те саме значення з `fetcher.formData`.
- Поки дія працює, `isComplete` береться з надісланої форми, тому кнопка одразу показує новий стан. Коли дія й
  повторні лоадери закінчаться, `fetcher.formData` зникне, і стан знову візьметься з `task.status`, але вже свіжого.

Наш запуск у лекції, розділ «Дія без переходу: `useFetcher`», зробив те саме з позначкою «прочитано»: напис на кнопці
змінився через 10 мс, хоча дія ще працювала. Що буде, якщо сервер відповість помилкою, сторінка не каже. Наш запуск
у тому самому розділі лекції показав: коли дія повернула статус 500, `fetcher.formData` зник, лоадер не
перезапустився, і кнопка повернулася до старого значення з лоадера. Повідомлення про помилку й роботу з кешем
розбирає день «Мутації й оптимістичні оновлення» цієї фази.

## `Actions`

**Де читати:** [reactrouter.com/start/data/actions](https://reactrouter.com/start/data/actions).

**Що це за текст.** П'ята сторінка розділу Data Mode. Вона показує, як оголосити дію, трьома способами викликати її і
як прочитати результат.

**Якщо часу мало,** прочитайте `Defining Actions`, `Calling actions with a Form` і `Accessing Action Data`.

### `Defining Actions`

Розділ дає визначення: зміни даних (mutations) роблять дії, тобто поле `action` об'єкта маршруту. Друге речення
містить головну думку сторінки: коли дія закінчилася, усі дані лоадерів на сторінці перевіряються знову, щоб
інтерфейс збігався з даними без жодного вашого коду. Слово revalidated тут означає повторний запуск лоадерів. Третє
речення посилається на посібник `Revalidation Optimization` для випадків, коли частину перезапусків треба пропустити.

```tsx
// приклад зі сторінки Actions
let router = createBrowserRouter([
  {
    path: "/projects/:projectId",
    Component: Project,
    action: async ({ request }) => {
      let formData = await request.formData();
      let title = formData.get("title");
      let project = await someApi.updateProject({ title });
      return project;
    },
  },
]);
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `action: async ({ request }) => …` | дія отримує той самий об'єкт аргументів, що й лоадер; тут узято лише `request` |
| `await request.formData()` | тіло запиту читається як `FormData`; метод повертає проміс, бо тіло може бути великим і приходить потоком, як ви бачили в лекції «Мережа», розділ «Тіло відповіді — це потік» |
| `formData.get("title")` | значення поля з `name="title"`; тип у TypeScript `FormDataEntryValue \| null`, тому в лекції його перетворено на рядок через `String(...)` |
| `someApi.updateProject` | вигаданий клієнт API |
| `return project` | результат дії стане доступним через `useActionData` |

Наш запуск підтвердив головне речення: після успішної дії «Додати книжку» маршрутизатор знову запустив обидва лоадери
сторінки, і перелік оновився сам. Посібник `Revalidation Optimization` додає важливе уточнення для режиму даних:
надсилання, яке закінчилося статусом 4xx чи 5xx, лоадерів не перезапускає. Наш запуск із порожньою назвою, коли дія
повернула статус 400, це підтвердив: жодного запиту лоадерів після дії.

### `Calling Actions`

Дію викликають двома способами: декларативно, тобто описом у розмітці через `<Form>`, і імперативно, тобто викликом
функції в коді через `useSubmit`. Ще є варіант із фетчером: `<fetcher.Form>` і `fetcher.submit`. В усіх випадках
дію знаходять за шляхом маршруту й методом `"post"`.

#### `Calling actions with a Form`

```tsx
// приклад зі сторінки Actions
import { Form } from "react-router";

function SomeComponent() {
  return (
    <Form action="/projects/123" method="post">
      <input type="text" name="title" />
      <button type="submit">Submit</button>
    </Form>
  );
}
```

Тут атрибут `action` вказує адресу маршруту, чию дію викликати. Якщо його немає, як у лекції, форма надсилається
найближчому маршруту, тобто тому, у якому її відрендерено. Так каже довідник `Form`. Під кодом сторінка попереджає:
надсилання спричиняє перехід, і в історію браузера додається новий запис. Наш запуск показав `historyAction PUSH`
після надсилання форми. Лекція в розділі «Вхід через дію» показує, коли це важить: після `redirect` з дії кнопка
«Назад» повела на сторінку входу, а `replace` замість `redirect` цього уникає.

#### `Calling actions with useSubmit`

```tsx
// приклад зі сторінки Actions
import { useCallback } from "react";
import { useSubmit } from "react-router";
import { useFakeTimer } from "fake-lib";

function useQuizTimer() {
  let submit = useSubmit();

  let cb = useCallback(() => {
    submit(
      { quizTimedOut: true },
      { action: "/end-quiz", method: "post" },
    );
  }, []);

  let tenMinutes = 10 * 60 * 1000;
  useFakeTimer(tenMinutes, cb);
}
```

Приклад описує тест на час: через десять хвилин форма надсилається сама, без натискання. `useSubmit` повертає функцію
`submit`, яка приймає дані й ті самі параметри, що атрибути форми. Пакета `fake-lib` і хука `useFakeTimer` не існує:
це вигадка, яка стоїть замість будь-якого таймера. `useCallback` з порожнім масивом залежностей тримає ту саму
функцію між рендерами. Лінт вашого проєкту на такому коді попереджає: наш запуск ESLint надрукував для правила
`react-hooks/exhaustive-deps` попередження `React Hook useCallback has a missing dependency: 'submit'`, тобто
просить додати `submit` до масиву.
Сторінка знову додає, що це перехід із новим записом в історії. Сьогодні `useSubmit` вам не потрібен: для форми, яку
надсилає людина, є `<Form>`.

#### `Calling actions with a fetcher`

```tsx
// приклад зі сторінки Actions
import { useFetcher } from "react-router";

function Task() {
  let fetcher = useFetcher();
  let busy = fetcher.state !== "idle";

  return (
    <fetcher.Form method="post" action="/update-task/123">
      <input type="text" name="title" />
      <button type="submit">
        {busy ? "Saving..." : "Save"}
      </button>
    </fetcher.Form>
  );
}
```

Розділ каже, що фетчери надсилають дані діям і лоадерам без переходу, тобто без нових записів в історії. Імперативний
варіант пишеться так:

```tsx
// приклад зі сторінки Actions
fetcher.submit(
  { title: "New Title" },
  { action: "/update-task/123", method: "post" },
);
```

Наш запуск показав три речі: адреса не змінилася, `historyAction` лишився `POP` від першого відкриття, а
`navigation.state` весь час був `idle`. Лоадер сторінки після дії фетчера все одно перезапустився. Посилання в кінці
розділу веде на посібник `Using Fetchers` з усіма подробицями.

### `Accessing Action Data`

```tsx
// приклад зі сторінки Actions
function Project() {
  let actionData = useActionData();
  return (
    <div>
      <h1>Project</h1>
      <Form method="post">
        <input type="text" name="title" />
        <button type="submit">Submit</button>
      </Form>
      {actionData ? (
        <p>{actionData.title} updated</p>
      ) : null}
    </div>
  );
}
```

Те, що повернула дія, компонент маршруту отримує через `useActionData`, а фетчер отримує через `fetcher.data`. Поки
дія не працювала, `actionData` дорівнює `undefined`, тому код перевіряє його перед показом. У TypeScript пишіть
`useActionData<typeof action>()`, як і для лоадера. Лекція повертає з дії `data({ error: … }, { status: 400 })` і
показує повідомлення з `actionData.error`: так дія повідомляє людині, що з формою не так, і при цьому не перезапускає
лоадерів.

**Навіщо це у вашому проєкті.** Практика дня дій не вимагає: вона про лоадери й водоспад. Але після переходу на
лоадери перша ж форма у вашому застосунку, як-от учорашня сторінка входу, природно стає `<Form>` з дією. День «Мутації
й оптимістичні оновлення» цієї фази зробить те саме вже з кешем TanStack Query.

## Що змінилося у 8.5

Тексти трьох сьогоднішніх сторінок у версіях 8.4.0 і 8.5.3 однакові. Зміни є поруч із ними.

-  **Довідник `useNavigation`.** У версії 8.4.0 його сторінку зіпсувало автоматичне збирання з коментарів у коді:
  замість опису там опинилися сотні рядків вихідного коду. Сервер `react-router-docs` знає саме 8.4.0, тому на запит
  про `useNavigation` може повернути шматки коду. У версії 8.5.3 сторінку виправлено: хук повертає поточний перехід, а
  без переходу повертає стан `idle`.
- **`Form` і `useSubmit`.** Параметр `viewTransition` позначено застарілим. Журнал змін 8.5.0 пояснює, що всі API
  анімації переходів React Router тепер радять замінювати компонентом React `<ViewTransition>`, доступним з
  React 19.3. Учорашній розбір говорив про те саме для `NavLink`.
- **Сторінка фреймворку `Data Loading`.** У 8.5.3 з'явився розділ `Authentication and Authorization`. Він каже, що
  маршрутизатор запускає лоадери ланцюжка одночасно, а лоадер може бути викликаний і окремо, наприклад фетчером. Тому
  лоадер батька не може захистити лоадери дітей. Це те саме, що показав учорашній дослід з охоронцем.
- **Журнал змін пакета.** Біля теми дня є такі виправлення. У 8.5.3 результат дії поточного маршруту, тобто
  `actionData`, більше не зникає, поки триває надсилання форми на інший маршрут, а атрибут `encType` форми читається
  без огляду на великі й малі літери. У 8.5.2 стан переходу лишається узгодженим, якщо дія кинула помилку, а
  `redirect()` більше не змінює об'єкт параметрів, який йому передали. У 8.5.1 надсилання `<Form>` на поточну адресу,
  у якій є символи, що кодуються через `%`, більше не дублює запису в історії. Там само виправлено кілька випадків
  із фетчерами: помилка повторної перевірки після дії фетчера тепер іде до найближчої межі помилок, а не до кореневої,
  а нові дані фетчера не перезаписуються старішими відповідями. У 8.5.0 фетчер після `fetcher.reset()` більше не
  перевіряється знову.

Жодна з цих змін не змінює поведінки, яку ви побачите в сьогоднішній практиці.

## Запитання для перевірки

**1. Сторінка `Data Loading` каже, що лоадери викликаються до рендеру компонента. Що з цього випливає для перевірки
`if (!data)` у компоненті?**

<details><summary>Відповідь</summary>

Вона не потрібна. Коли React рендерить компонент маршруту, маршрутизатор уже дочекався його лоадера, тому
`useLoaderData` повертає готові дані. Випадок «запису немає» лоадер обробляє сам, кидаючи відповідь зі статусом, і
тоді маршрутизатор показує `ErrorBoundary` замість компонента.

</details>

**2. Приклад на сторінці `Pending UI` кладе індикатор у `<html>` і `<body>`. Куди його покласти у вашому застосунку?**

<details><summary>Відповідь</summary>

У каркас, тобто в компонент кореневого маршруту зі спільною шапкою й `<Outlet />`. У режимі даних документ дає ваш
`index.html`, а React рендерить усе всередині `#root`.

</details>

**3. Форма стоїть в індексному маршруті, а кнопка перевіряє `navigation.formAction === "/authors/1"`. Чому напис
«Надсилаю…» ніколи не з'являється?**

<details><summary>Відповідь</summary>

Форма в індексному маршруті дописує до адреси `?index`, щоб маршрутизатор відрізнив її від форми батька з тією самою
адресою. Наш запуск показав `formAction /authors/1?index`. Треба порівнювати з повною адресою або перевіряти
`navigation.state === 'submitting'`.

</details>

**4. Сторінка `Actions` каже, що після дії перевіряються всі дані лоадерів. Ваша дія повернула статус 400. Чи
перезапустяться лоадери?**

<details><summary>Відповідь</summary>

Ні. Посібник `Revalidation Optimization` уточнює, що в режимі даних надсилання зі статусом 4xx чи 5xx лоадерів не
перезапускає. Наш запуск це підтвердив.

</details>

**5. Чим «Calling actions with a fetcher» відрізняється від «Calling actions with a Form» з погляду кнопки «Назад»?**

<details><summary>Відповідь</summary>

Надсилання `<Form>` є переходом і додає запис в історію, тому «Назад» поверне людину на стан до надсилання. Фетчер не
робить переходу й не додає запису, тому «Назад» поведе туди, де людина була до цієї сторінки.

</details>

**6. У прикладі `Optimistic UI` кнопка має `name="status"` і `value`. Навіщо їй ці атрибути?**

<details><summary>Відповідь</summary>

Браузер кладе `name` і `value` натиснутої кнопки в дані форми. Тому дія дізнається, яке значення вибрала людина, а
компонент може прочитати те саме значення з `fetcher.formData` і показати результат, не чекаючи відповіді сервера.

</details>
