## `Overview`

найпростіший приклад. Сторінку написано рекламним тоном, тому кілька речень про те, яка бібліотека чудова, можна

**Якщо часу мало,** прочитайте розділ `Motivation`: він пояснює слово «серверний стан», на якому стоїть увесь день.

### Вступ сторінки

Перший абзац каже, що бібліотеку раніше називали React Query, і що вона робить чотири речі з **серверним станом**:
отримує, кешує, синхронізує й оновлює. Слово **синхронізувати** тут означає підтримувати копію в браузері
відповідною тому, що лежить на сервері. Стару назву React Query ви ще зустрінете в статтях і в назві пакета для
Devtools.

### `Motivation`

Розділ починається з того, що більшість фреймворків не має готового способу отримувати й змінювати дані. Тому
розробники або будують власні обгортки, або поєднують стан компонентів з ефектами, тобто роблять те саме, що ви
робили у фазі 1, або кладуть дані з сервера в загальні бібліотеки стану.

Далі головна думка: загальні бібліотеки стану добре працюють із **клієнтським станом**, а з серверним погано, бо
серверний стан зовсім інший. Розділ перелічує чотири відмінності. Своїми словами: серверний стан лежить там, де ви не
керуєте; читається й змінюється лише асинхронно; ним володієте не лише ви, тому інші можуть змінити його без вашого
відома; і тому копія в застосунку може застаріти. Слова «out of date» на сторінці означають саме «застаріла копія».

Другий перелік називає задачі, що з'являються слідом:

| Що написано | Що це означає |
|-------------|---------------|
| Caching | зберігати відповіді, щоб показувати їх без нового запиту; автор жартома називає це найважчою задачею програмування |
| Deduping multiple requests for the same data into a single request | якщо кілька компонентів одночасно просять ті самі дані, піти на сервер один раз; лекція показала це в розділі «Один запит на кількох читачів» |
| Updating "out of date" data in the background | оновлювати застарілі дані, поки людина бачить старі; лекція називає це фоновим запитом |
| Knowing when data is "out of date" | знати, коли дані застаріли; це робить `staleTime` |
| Reflecting updates to data as quickly as possible | швидко показувати зміни; про це дні 4 і 5 |
| Performance optimizations like pagination and lazy loading data | сторінки й дозавантаження; план до них сьогодні не доходить |
| Managing memory and garbage collection of server state | звільняти пам'ять від даних, які вже ніхто не показує; це робить `gcTime` |
| Memoizing query results with structural sharing | не створювати нових об'єктів, якщо дані не змінилися; про це розділ `Important Defaults` нижче |

Наприкінці розділу обіцянки: менше коду, легше підтримувати, швидший для людини застосунок і менше трафіку. Наш
браузерний запуск дав цим обіцянкам числа: перелік авторів з ефектом з'являвся при поверненні через 579–584 мс, а з
`useQuery` через 6–8 мс.

### `Enough talk, show me some code already!`

Приклад отримує з API GitHub відомості про сховище коду TanStack Query і показує назву, опис і кількість зірок:

```tsx
// приклад зі сторінки Overview, версія 5.108.4
import {
  QueryClient,
  QueryClientProvider,
  useQuery,
} from '@tanstack/react-query'

const queryClient = new QueryClient()

export default function App() {
  return (
    <QueryClientProvider client={queryClient}>
      <Example />
    </QueryClientProvider>
  )
}

function Example() {
  const { isPending, error, data } = useQuery({
    queryKey: ['repoData'],
    queryFn: async () => {
      const response = await fetch(
        'https://api.github.com/repos/TanStack/query',
      )
      if (!response.ok) throw new Error('Failed to fetch repo data')
      return response.json()
    },
  })

  if (isPending) return 'Loading...'

  if (error) return 'An error has occurred: ' + error.message

  return (
    <div>
      <h1>{data.name}</h1>
      <p>{data.description}</p>
      <strong>👀 {data.subscribers_count}</strong>{' '}
      <strong>✨ {data.stargazers_count}</strong>{' '}
      <strong>🍴 {data.forks_count}</strong>
    </div>
  )
}
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| `const queryClient = new QueryClient()` поза компонентом | клієнт із кешем створюють один раз, на рівні модуля; лекція робить так само в `main.tsx` |
| `<QueryClientProvider client={queryClient}>` | провайдер контексту, як у лекції «Контекст»; усі хуки всередині бачать цей клієнт |
| `queryKey: ['repoData']` | ключ запису кешу; тут сталий, бо запит ні від чого не залежить |
| `if (!response.ok) throw …` | функція запиту кидає помилку на неуспішний статус; без цього рядка відповідь 404 потрапила б у `data` |
| `return response.json()` | повертає проміс із розібраним JSON; `useQuery` дочекається його сам |
| `if (isPending) …`, `if (error) …` | спершу випадок «даних ще немає», потім «помилка», а далі дані точно є |

Рядок з `response.ok` з'явився в документації версії 5.108.4, а в 5.103.3, яку тримає сервер, його ще немає. Лекція
пояснює в розділі «Повтори після помилки», чому він важливий: без нього бібліотека не дізнається про помилку й не
повторить запит.

Без типів `data` у прикладі має тип `any`, тому звернення `data.name` проходить перевірку. У вашому проєкті функція
запиту має повертати тип, наприклад через `getJson<Author[]>` з лекції. Тоді TypeScript, як показав наш запуск
`tsc`, не дає звернутися до `data`, поки ви не перевірили `isPending` і `isError`.

## `Quick Start`

**Де читати:** [tanstack.com/query/latest/docs/framework/react/quick-start](https://tanstack.com/query/latest/docs/framework/react/quick-start).

**Що це за текст.** Один приклад, який показує три головні поняття бібліотеки: запити, мутації й інвалідацію. Сторінка
займає один екран і не має розділів.

**Якщо часу мало,** прочитайте приклад і зупиніться на рядку `useQuery`: мутації й інвалідація прийдуть у днях 4 і 5.

Ось приклад:

```tsx
// приклад зі сторінки Quick Start, версія 5.108.4
import {
  useQuery,
  useMutation,
  useQueryClient,
  QueryClient,
  QueryClientProvider,
} from '@tanstack/react-query'
import { createRoot } from 'react-dom/client'
import { getTodos, postTodo } from '../my-api'

// Create a client
const queryClient = new QueryClient()

function App() {
  return (
    // Provide the client to your App
    <QueryClientProvider client={queryClient}>
      <Todos />
    </QueryClientProvider>
  )
}

function Todos() {
  // Access the client
  const queryClient = useQueryClient()

  // Queries
  const query = useQuery({ queryKey: ['todos'], queryFn: getTodos })

  // Mutations
  const mutation = useMutation({
    mutationFn: postTodo,
    onSuccess: () => {
      // Invalidate and refetch
      queryClient.invalidateQueries({ queryKey: ['todos'] })
    },
  })

  return (
    <div>
      <ul>
        {query.data?.map((todo) => (
          <li key={todo.id}>{todo.title}</li>
        ))}
      </ul>

      <button
        onClick={() => {
          mutation.mutate({
            id: Date.now(),
            title: 'Do Laundry',
          })
        }}
      >
        Add Todo
      </button>
    </div>
  )
}

createRoot(document.getElementById('root')).render(<App />)
```

| Що в коді | Що це означає для вас |
|-----------|------------------------|
| коментар `Create a client` | «створіть клієнт» |
| коментар `Provide the client to your App` | «надайте клієнт застосунку», тобто покладіть його в провайдер |
| `useQueryClient()` | хук, що повертає клієнт із найближчого провайдера; потрібен, щоб викликати методи клієнта з компонента |
| `useQuery({ queryKey: ['todos'], queryFn: getTodos })` | запит переліку справ; `getTodos` є функцією, яка повертає проміс |
| `query.data?.map(…)` | оператор `?.` потрібен, бо поки даних немає, `data` дорівнює `undefined`; приклад не показує «Завантаження…», а просто малює порожній список |
| `useMutation`, `mutation.mutate(…)` | мутація, тобто запит, що змінює дані на сервері; це тема дня 5, сьогодні її не пишіть |
| `invalidateQueries({ queryKey: ['todos'] })` | позначити запис застарілим і перезапитати його; це тема днів 4 і 5 |
| `createRoot(…).render(<App />)` | звичайний вхід застосунку React 19 |

Останній рядок у версії 5.108.4 оновили: у 5.103.3 там стояв старий виклик `render(<App />, …)` з React 17, який у
React 19 уже не існує. Якщо сервер покаже вам старий рядок, пишіть `createRoot`, як у вашому `main.tsx`.

Після прикладу сторінка каже, що ці три поняття становлять більшу частину бібліотеки, і наступні сторінки розбирають
кожне докладно.

**Навіщо це у вашому проєкті.** Приклад дає порядок обв'язки: клієнт на рівні модуля, провайдер навколо застосунку,
`useQuery` у компоненті. У практиці дня провайдер обгортає маршрутизатор, як у лекції, щоб усі сторінки бачили один
кеш.

### `Query Basics`

Перше речення дає визначення: **запит** (query) є декларативною залежністю від асинхронного джерела даних,
прив'язаною до унікального ключа. Слово **декларативна** означає, що компонент описує, які дані йому потрібні, а коли
й як їх отримати, вирішує бібліотека. Так само JSX описує, що має бути на екрані, а React вирішує, як це намалювати.

Далі уточнення: запит можна робити будь-яким методом, що повертає проміс, навіть POST. Але якщо метод змінює дані на
сервері, сторінка радить мутації, тобто тему дня 5.

Щоб підписати компонент на запит, `useQuery` отримує щонайменше дві речі: **унікальний ключ** і функцію, яка повертає
проміс, що або дає дані, або кидає помилку. Ключ, каже сторінка, бібліотека використовує, щоб перезапитувати,
кешувати й ділити запит між частинами застосунку.

Потім сторінка перелічує три основні стани запиту:

| Що написано | Що це означає |
|-------------|---------------|
| `isPending` або `status === 'pending'` | даних ще немає |
| `isError` або `status === 'error'` | запит закінчився помилкою |
| `isSuccess` або `status === 'success'` | запит успішний, дані є |

І три додаткові поля: `error` з помилкою, `data` з даними й `isFetching`, яке дорівнює `true` щоразу, коли запит іде,
зокрема у фоні.

Третій приклад показує рекомендований порядок перевірок:

```tsx
// приклад зі сторінки Queries
function Todos() {
  const { isPending, isError, data, error } = useQuery({
    queryKey: ['todos'],
    queryFn: fetchTodoList,
  })

  if (isPending) {
    return <span>Loading...</span>
  }

  if (isError) {
    return <span>Error: {error.message}</span>
  }

  // We can assume by this point that `isSuccess === true`
  return (
    <ul>
      {data.map((todo) => (
        <li key={todo.id}>{todo.title}</li>
      ))}
    </ul>
  )
}
```

Коментар в останньому блоці каже: «тут уже можна вважати, що `isSuccess === true`». Речення під четвертим прикладом
додає, що TypeScript теж звужує тип `data`, якщо ви перевірили `pending` і `error`. Наш запуск `tsc` це підтвердив:
без перевірок звернення `data.length` дало помилку `'data' is possibly 'undefined'`, а з ними пройшло.

Четвертий приклад робить те саме через `status === 'pending'` і `status === 'error'`. Це справа смаку.

### `FetchStatus`

Розділ вводить друге поле стану, `fetchStatus`, з трьома значеннями:

| Що написано | Що це означає |
|-------------|---------------|
| `fetchStatus === 'fetching'` | функція запиту зараз працює |
| `fetchStatus === 'paused'` | запит хотів піти, але стоїть на паузі; посилання веде на посібник `Network Mode`, де пояснено, що бібліотека чекає на мережу |
| `fetchStatus === 'idle'` | запит нічого не робить |

### `Why two different states?`

Розділ пояснює, навіщо два поля. Фонові перезапити й логіка **stale-while-revalidate** роблять можливими будь-які
поєднання. Stale-while-revalidate є назвою підходу «показуй застаріле, поки перевіряєш», тобто віддавай збережені дані
одразу й водночас питай сервер про нові. Сторінка дає два приклади. Запит у стані `success` зазвичай `idle`, але
буває `fetching`, коли йде фоновий запит. Запит без даних зазвичай `pending` і `fetching`, але буває `paused`, коли
немає мережі.

Наприкінці правило, яке варто запам'ятати дослівно за змістом: `status` розповідає про `data`, тобто чи є дані, а
`fetchStatus` розповідає про `queryFn`, тобто чи працює функція. Наш браузерний запуск показав поєднання `success` і
`fetching`: при поверненні на головну зі `staleTime` 0 перелік був на екрані за 8 мс, а поруч пів секунди стояв напис
«оновлюю…», який показує `isFetching`.

TypeScript перевіряє, що ви не забули жодного.

## `Query Keys`

**Де читати:** [tanstack.com/query/latest/docs/framework/react/guides/query-keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).

**Що це за текст.** Посібник про ключі запиту: якими вони бувають і як бібліотека їх порівнює. Тексти у версіях
5.103.3 і 5.108.4 однакові.

**Якщо часу мало,** прочитайте вступ і розділ `If your query function depends on a variable, include it in your query
key`.

### Вступ сторінки

Вступ каже головне: бібліотека кешує запити за ключами. Ключ мусить бути масивом на верхньому рівні. Він може бути
простим, як масив з одним рядком, або складним, з кількома рядками й вкладеними об'єктами. Дві вимоги: ключ можна
перетворити на рядок функцією `JSON.stringify`, і ключ **унікальний для даних запиту**, тобто різні дані мають різні
ключі.

### `Simple Query Keys`

Найпростіший ключ складається зі сталих значень. Сторінка радить його для загальних переліків і для даних без
ієрархії:

```tsx
// приклад зі сторінки Query Keys
// A list of todos
useQuery({ queryKey: ['todos'], ... })

// Something else, whatever!
useQuery({ queryKey: ['something', 'special'], ... })
```

Три крапки в прикладі заміняють решту налаштувань. Наш перелік авторів має такий ключ: `['authors']`.

### `Array Keys with variables`

Коли для опису даних потрібно більше, у масив додають змінні. Сторінка називає два випадки: ієрархічні чи вкладені
ресурси, де зазвичай додають номер запису, і запити з додатковими параметрами, де зазвичай додають об'єкт:

```tsx
// приклад зі сторінки Query Keys
// An individual todo
useQuery({ queryKey: ['todo', 5], ... })

// An individual todo in a "preview" format
useQuery({ queryKey: ['todo', 5, { preview: true }], ...})

// A list of todos that are "done"
useQuery({ queryKey: ['todos', { type: 'done' }], ... })
```

Слово **ресурс** тут означає річ, яку повертає API за своєю адресою: справу, автора, книжку. У лекції ключ
`['authors', authorId, 'books']` описує вкладений ресурс, тобто книжки конкретного автора.

### `Query Keys are hashed deterministically!`

**Хешувати** тут означає перетворювати ключ на рядок, за яким бібліотека шукає запис. **Детерміновано** означає, що
той самий ключ завжди дає той самий рядок. Сторінка показує, що порядок полів в об'єкті значення не має, і всі три
такі запити однакові:

```tsx
// приклад зі сторінки Query Keys
useQuery({ queryKey: ['todos', { status, page }], ... })
useQuery({ queryKey: ['todos', { page, status }], ...})
useQuery({ queryKey: ['todos', { page, status, other: undefined }], ... })
```

А порядок елементів масиву має значення, тому ці три запити різні:

```tsx
// приклад зі сторінки Query Keys
useQuery({ queryKey: ['todos', status, page], ... })
useQuery({ queryKey: ['todos', page, status], ...})
useQuery({ queryKey: ['todos', undefined, page, status], ...})
```

Наш запуск перевірив це функцією `hashKey`, якою бібліотека перетворює ключі. Ключі `['books', { page: 2, sort:
'title' }]` і `['books', { sort: 'title', page: 2 }]` дали однаковий рядок, а `['books', 2, 'title']` і
`['books', 'title', 2]` різні. Сторінка не каже ще одного, що ми побачили там само: рядок `'1'` і число `1` дають
різні ключі, `["authors","1"]` і `["authors",1]`. Хук `useParams` завжди повертає рядки, тому стежте, щоб в усіх
місцях ключ збирався однаково.

### `If your query function depends on a variable, include it in your query key`

Заголовок і є правилом: якщо функція запиту залежить від змінної, покладіть цю змінну в ключ. Ключ однозначно описує
дані, тому в ньому мусить бути кожна змінна, яка змінюється:

```tsx
// приклад зі сторінки Query Keys
function Todos({ todoId }) {
  const result = useQuery({
    queryKey: ['todos', todoId],
    queryFn: () => fetchTodoById(todoId),
  })
}
```

Після прикладу сторінка порівнює ключ із залежностями: ключ працює як залежності функції запиту. Коли змінна в ключі
змінюється, запит виконується знову сам, а кожне значення змінної отримує власний запис кешу. Слова «depending on
your `staleTime` settings» означають, що для значення, яке вже є в кеші й ще свіже, нового запиту не буде. Посилання
`exhaustive-deps` веде на правило додатка до ESLint `@tanstack/eslint-plugin-query`, яке перевіряє це автоматично,
так само як `react-hooks/exhaustive-deps` перевіряє залежності ефекту. У вашому проєкті цього додатка немає.

Наш запуск показав, що буває без цього правила. Сторінка з ключем `['books']`, функція запиту якої бере номер автора
з адреси, після переходу від автора 1 до автора 2 за секунду не зробила жодного запиту й показала книжки Лесі
Українки під заголовком «Автор 2».

### `Further reading`

Посилання на статтю «Effective React Query Keys» і пакет Query Key Factory для впорядкування ключів у великих
застосунках. Сьогодні не обов'язково, але стаття знадобиться завтра, коли ключ треба буде однаково зібрати в лоадері
й у компоненті.

**Навіщо це у вашому проєкті.** Сторінка речі прокату показує одну річ і її відгуки. Номер речі приходить з адреси,
тому він має стояти в ключах обох запитів, і ці ключі мають відрізнятися між собою.

## `Important Defaults`

**Де читати:** [tanstack.com/query/latest/docs/framework/react/guides/important-defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

**Що це за текст.** Перелік налаштувань за замовчуванням, які, як попереджає вступ, часто дивують новачків. Сторінка
не має розділів, лише список пунктів із примітками. Це найважливіша сторінка дня: практика й перевірка будуються на
трьох її пунктах.

**Якщо часу мало,** прочитайте перші чотири пункти: про застарілі дані, про `staleTime`, про події, після яких
застарілі дані перезапитуються, і про неактивні запити.

Вступ називає налаштування **агресивними, але розумними** (aggressive but sane). Агресивні вони тому, що бібліотека
часто ходить на сервер. Розумні тому, що людина завжди бачить якомога свіжіші дані. Розберемо пункти по черзі.

### Дані застарілі одразу

Перший пункт: екземпляри запиту через `useQuery` за замовчуванням вважають збережені дані **застарілими** (stale).
Примітка під ним каже, що змінити це можна налаштуванням `staleTime` для всіх запитів або для одного, і що більший
`staleTime` означає рідші перезапити.

Налаштування для всіх запитів задають у клієнті, у полі `defaultOptions.queries`. Сторінка `Window Focus Refetching`
показує, як це записати: `new QueryClient({ defaultOptions: { queries: { … } } })`. Для одного запиту налаштування
пишуть прямо в `useQuery`, як у лекції.

### `staleTime` і свіжі дані

Другий пункт: запит зі `staleTime` вважається **свіжим** (fresh), поки `staleTime` не минув. Під ним три варіанти:

| Що написано | Що це означає |
|-------------|---------------|
| `staleTime` дорівнює, наприклад, `2 * 60 * 1000` | 2 хвилини дані беруться з кешу без жодних перезапитів, або доки запис не інвалідують вручну |
| `staleTime: Infinity` | не перезапитувати ніколи, доки запис не інвалідують вручну |
| `staleTime: 'static'` | не перезапитувати ніколи, навіть після ручної інвалідації |

**Інвалідувати** запис означає позначити його застарілим методом `invalidateQueries`, щоб бібліотека перезапитала
його. Це тема днів 4 і 5. Примітка під списком пояснює різницю між `Infinity` і `'static'`: `'static'` суворіше, його
не пробиває ні інвалідація, ні значення `"always"` у налаштуваннях перезапитів. `'static'` сторінка радить для даних,
які не змінюються, поки застосунок працює, а `Infinity` для даних, які ви хочете оновлювати вручну.

Час `staleTime` рахується від моменту, коли прийшли дані. Сторінка цього не пише прямо, а наш запуск показав: дані,
отримані о 10:00:00, при `staleTime` 30 секунд о 10:00:31 вже перезапитувалися, хоча людина пішла з екрана лише 21
секунду тому.

### Коли застарілі дані перезапитуються

Третій пункт перелічує три події, після яких застарілі запити перезапитуються у фоні:

| Що написано | Що це означає | Як вимкнути |
|-------------|---------------|-------------|
| New instances of the query mount | змонтувався новий компонент з `useQuery` для цього ключа, наприклад людина повернулася на екран | `refetchOnMount: false` |
| The window is refocused | сторінка знову стала видимою, наприклад людина повернулася на вкладку | `refetchOnWindowFocus: false` |
| The network is reconnected | мережа відновилася після обриву | `refetchOnReconnect: false` |

Примітка під пунктом радить спершу збільшувати `staleTime`, а не вимикати події. Наш браузерний запуск показав обидві
перші події. Зі `staleTime` 30 секунд повернення на екран через 10 секунд не дало запиту, а через 35 секунд дало
один. Повернення на вкладку через 5 секунд не дало запиту, а через 35 секунд дало один. Зі `staleTime` 0 кожне
повернення давало запит. Третю подію, відновлення мережі, ми не перевіряли.

Що саме означає «window is refocused», уточнює сусідня сторінка `Window Focus Refetching`: бібліотека слухає подію
`visibilitychange`, яку браузер подає, коли сторінка стає видимою чи схованою. У розділі `Troubleshooting` там є
попередження: прапорець «Emulate a focused page» на панелі Rendering інструментів розробника Chrome тримає сторінку
завжди видимою, і тоді повернення на вкладку нічого не перезапитує.

### `refetchInterval`

Четвертий пункт: запит можна перезапитувати за таймером налаштуванням `refetchInterval`, незалежно від `staleTime`.
Посилання веде на посібник `Polling`. Сьогодні не потрібно: живі дані план бере в блоці B через WebSocket.

### Неактивні запити й `gcTime`

П'ятий і шостий пункти разом. Запит, у якого не лишилося жодного активного `useQuery` чи іншого спостерігача, стає
**неактивним** (inactive) і лишається в кеші на випадок, якщо знадобиться знову. Неактивні запити видаляються через
**5 хвилин**. Примітка радить змінити це налаштуванням `gcTime`, значення за замовчуванням записано як
`5 * 60 * 1000` мілісекунд. **Збирання сміття** (garbage collection) означає саме це видалення даних, які вже ніхто
не використовує.

Наш запуск зі скороченим до 1 секунди `gcTime` показав обидва випадки: після пів секунди без спостерігачів компонент
одразу отримав дані з кешу, а після півтори секунди запису вже не було, і компонент почав зі стану `pending`. На
знімку панелі Devtools ми бачили в налаштуваннях запису `gcTime: 300000`, тобто ті самі 5 хвилин.

### Повтори після помилки

Сьомий пункт: невдалий запит бібліотека **мовчки повторює 3 рази** із затримкою, що експоненційно зростає, і лише
потім показує помилку. **Експоненційно** тут означає, що кожна наступна пауза вдвічі довша за попередню. Змінити
кількість і паузи можна налаштуваннями `retry` і `retryDelay`.

Наш запуск з API, що щоразу відповідає статусом 500, дав чотири спроби: на 20-й, 1120-й, 3220-й і 7330-й мілісекунді.
Паузи між ними 1, 2 і 4 секунди, а помилка з'явилася на екрані на 7,4 секунді. Поле `failureCount` за цей час
зросло від 0 до 4.

### Структурне спільне використання

Восьмий пункт найтехнічніший. Результати запиту за замовчуванням **структурно спільні** (structurally shared). Це
означає, що бібліотека порівнює нові дані зі старими, і якщо якась частина не змінилася, лишає старий об'єкт для цієї
частини. Тоді посилання на незмінені дані лишається тим самим, і `useMemo`, `useCallback` чи `memo` з лекції фази 2
«Мемоізація і React Compiler» не перераховують зайвого. Сторінка жартує, що в 99,9 % випадків про це можна не
думати.

Наш запуск перевірив це методами клієнта `fetchQuery`, який виконує запит і кладе результат у кеш, і
`getQueryData`, який читає дані з кешу так, як їх отримує компонент:

```tsx
// src/library/lab/sharing.test.tsx, фрагмент
// Дані беремо з кешу: саме їх отримує компонент як data.
const read = () => client.getQueryData<Author[]>(['authors'])!
await client.fetchQuery(options)
const first = read()
await client.fetchQuery({ ...options, staleTime: 0 })
const same = read()
console.log('ті самі дані з сервера: той самий масив?', same === first)
server.authors[1] = { ...server.authors[1], years: '1856–1916 (уточнено)' }
await client.fetchQuery({ ...options, staleTime: 0 })
const changed = read()
console.log('змінено Франка: той самий масив?', changed === first,
  '| той самий об’єкт Лесі?', changed[0] === first[0], '| той самий об’єкт Франка?', changed[1] === first[1])
```

```text
ті самі дані з сервера: той самий масив? true
змінено Франка: той самий масив? false | той самий об’єкт Лесі? true | той самий об’єкт Франка? false
```

Сервер щоразу надсилав новий JSON, тобто нові об'єкти. Проте коли відповідь не змінилася, кеш лишив старий масив. А
коли змінився лише Франко, кеш створив новий масив і новий об'єкт Франка, але об'єкт Лесі лишив старим. Примітка під
пунктом каже, що це працює лише для значень, сумісних із JSON, і що для дуже великих відповідей функцію можна вимкнути
налаштуванням `structuralSharing`.

**Що це за текст.** Сторінка про панель для розробника: як її поставити, у яких двох режимах вона буває, що вміє і як

Вступ радить тримати панель під рукою з першого дня роботи з бібліотекою. Далі три примітки. Перша каже, що для

мутації.

### `Install and Import the Devtools`

Панель є окремим пакетом, і сторінка показує команди для npm, pnpm, yarn і bun. У вашому проєкті це
`npm install @tanstack/react-query-devtools@5.108.4`. Речення про Next.js 13 вас не стосується.

Головне речення розділу: за замовчуванням панель потрапляє в бандл лише тоді, коли `process.env.NODE_ENV` дорівнює
`'development'`, тому окремо прибирати її з продакшн-збірки не треба. Ми подивилися в код пакета: поза режимом
розробки `ReactQueryDevtools` є функцією, яка повертає `null`. У зібраному продакшн-файлі нашої бібліотеки слів,
характерних для панелі, не знайшлося. У Vitest змінна дорівнює `test`, тому в тестах панель теж нічого не рендерить.

### `Floating Mode`

**Плаваючий режим** означає, що панель живе поверх застосунку й відкривається кнопкою в куті екрана. Чи відкрита
панель, бібліотека запам'ятовує в `localStorage`. Сторінка радить ставити компонент якомога ближче до кореня:

```tsx
// приклад зі сторінки Devtools
import { ReactQueryDevtools } from '@tanstack/react-query-devtools'

function App() {
  return (
    <QueryClientProvider client={queryClient}>
      {/* The rest of your application */}
      <ReactQueryDevtools initialIsOpen={false} />
    </QueryClientProvider>
  )
}
```

Коментар `The rest of your application` означає «решта вашого застосунку»: у вас на цьому місці стоїть
`<RouterProvider>`. Головне, щоб панель була всередині провайдера, бо вона бере клієнт із контексту.

### `Options` плаваючого режиму

| Параметр | Що робить |
|----------|-----------|
| `initialIsOpen` | `true`, якщо панель має бути відкрита з самого початку |
| `buttonPosition` | де стоїть кнопка з логотипом; за замовчуванням `bottom-right`, тобто правий нижній кут |
| `position` | з якого боку з'являється панель; за замовчуванням `bottom`, тобто знизу |
| `client` | інший клієнт замість того, що в контексті |
| `errorTypes` | заготовлені помилки, які можна ввімкнути для запиту з панелі |
| `styleNonce` | у 5.108.4 застарів і нічого не робить |
| `shadowDOMTarget` | тіньовий корінь, куди додати стилі панелі; потрібен лише в рідкісних випадках |
| `trustedTypesPolicy` | новий у 5.108.4; потрібен сторінкам із суворою політикою безпеки Trusted Types |
| `hideDisabledQueries` | ховати з панелі вимкнені запити |
| `theme` | світла, темна чи системна тема; у 5.108.4 за замовчуванням береться тема з меню налаштувань панелі |

Більшість цих параметрів вам сьогодні не знадобиться, крім `initialIsOpen`.

### `Embedded Mode`

**Вбудований режим** показує ту саму панель як звичайний компонент `ReactQueryDevtoolsPanel`, який ви ставите туди, де
хочете, і відкриваєте власною кнопкою. Приклад зберігає відкритість панелі в `useState`. Сьогодні вистачить
плаваючого режиму.

### `Filter queries and mutations`

Новий розділ у 5.108.4. Поле `Filter` над списком записів за замовчуванням шукає за ключем. Кнопка всередині поля
перемикає область пошуку: `Key` шукає за ключем, `Data` за даними запису, `All` за обома. На нашому знімку в полі
фільтра справді стояла позначка `Key`.

### `Search query and mutation data`

Теж новий розділ. Коли ви вибрали запис, у його `Data Explorer` є поле `Search data` для пошуку всередині даних:
назви полів і значення, без урахування регістру. Знайдене підсвічується, а гілки з ним розгортаються.

### `Devtools in production`

Розділ показує, як за бажанням вантажити панель і в продакшні: окремим імпортом `…/production` через `React.lazy`, а
відкривати функцією `window.toggleDevtools()` з консолі. Підрозділ `Modern bundlers` дає коротший шлях імпорту для
збирачів, які розуміють поле `exports` у `package.json`. Vite його розуміє. Сьогодні цього не потрібно.

### Що ви побачите в панелі

Сторінка не описує вигляду самої панелі, тому ось що ми побачили на знімках екрана застосунку в режимі розробки,
зроблених у Chrome без вікна. У вашому вікні розмір і тема можуть відрізнятися.

- Угорі назва, перемикач `Queries` і `Mutations` і лічильники станів `Fresh`, `Fetching`, `Paused`, `Stale` і
  `Inactive`.
- Під ними поле `Filter`, список `Sort by status` і кнопки, серед яких очищення кешу, імітація роботи без мережі,
  окреме вікно «картинка в картинці» і меню налаштувань. Підписи кнопок ми взяли з атрибутів `aria-label`.
- Далі рядок на кожен запис кешу: ліворуч число спостерігачів, поруч ключ.
- Клацання на рядок відкриває праворуч `Query Details` з ключем, станом, `Observers` і `Last Updated`, `Actions` з
  кнопками `Refetch`, `Invalidate`, `Reset`, `Remove`, `Trigger Loading`, `Trigger Error`, а також `Data Explorer` і
  `Query Explorer`.

Не натискайте кнопку окремого вікна, якщо не хочете: панель переїде туди й після оновлення сторінки там і лишиться,
бо бібліотека запам'ятовує й це.

**Навіщо це у вашому проєкті.** Крок практики «підключити Devtools» просить поставити `ReactQueryDevtools` у
провайдер. Панель покаже вам, як записи сторінки речі переходять між станами й скільки компонентів читають кожен.
Запускайте застосунок у режимі розробки, щоб її бачити, а запити рахуйте на продакшн-збірці.

## Що змінилося між 5.103.3 і 5.108.4

Сервер `tanstack-query-docs` знає документацію до 5.103.3, а ваш проєкт ставить 5.108.4. Ми порівняли шість сторінок
дня у сховищі коду за мітками двох версій і прочитали журнали змін пакетів `@tanstack/query-core`,
`@tanstack/react-query` і `@tanstack/react-query-devtools` за цей проміжок.

**Сторінки дня.**

- `Queries` і `Query Keys` не змінилися.
- `Overview`: приклад отримав перевірку `if (!response.ok) throw new Error(…)` у функції запиту.
- `Quick Start`: останній рядок прикладу тепер `createRoot(…).render(<App />)` замість старого `render(<App />, …)`.
- `Important Defaults`: змінився лише запис числа, `5 * 60 * 1000` замість `1000 * 60 * 5`.
- `Devtools`: `styleNonce` застарів і нічого не робить; `shadowDOMTarget` описано інакше; з'явилися параметри
  `trustedTypesPolicy` і `hideDisabledQueries`; тема за замовчуванням береться з меню налаштувань панелі; вбудована
  панель тепер заповнює висоту контейнера; додано розділи `Filter queries and mutations` і `Search query and mutation
  data`.

**Пакети.** За журналами змін нові версії не змінили поведінки, на якій стоїть сьогоднішній день: значення за
замовчуванням для `staleTime`, `gcTime`, `retry` і подій перезапиту ті самі. Більшість змін виправляє рідкісні випадки
з нескінченними запитами, мутаціями, `useQueries` і `select`, які план сьогодні не бере. Біля теми дня стоять такі:

- 5.104.0: пакети збираються Vite 8, тим самим, що й ваш проєкт.
- 5.104.4: панель Devtools створюється один раз, а не на кожен рендер.
- 5.105.2: перед підпискою спостерігач спершу оновлює налаштування, тому дерево всередині `<Activity>`, ключ якого
  змінився, поки дерево було сховане, більше не вантажить старий ключ.
- 5.105.3: статичний запит без даних тепер може перезапитатися після скидання чи інвалідації.
- 5.106.0 і 5.107.0: у Devtools з'явилися пошук у даних, перемикач області фільтра, а великі списки записів
  відображаються швидше.
- 5.108.2: Devtools більше не додають елемент `<style>` у `<head>`, а стилі підключаються інакше; тому `styleNonce`
  застарів.
- 5.108.4: таймери збирання сміття очищаються, коли запис видалено з кешу.

## Запитання для перевірки

**1. Сторінка `Overview` перелічує, чим серверний стан відрізняється від клієнтського. Назвіть дві відмінності, через
які копія в браузері може застаріти.**

<details><summary>Відповідь</summary>

Серверний стан лежить там, де ви не керуєте, і ним володієте не лише ви: інші люди можуть змінити його без вашого
відома. Тому копія, отримана хвилину тому, вже може не відповідати серверу.

</details>

**2. За сторінкою `Queries`, що каже поле `status`, а що поле `fetchStatus`?**

<details><summary>Відповідь</summary>

`status` розповідає про `data`: чи є дані. `fetchStatus` розповідає про `queryFn`: чи працює функція запиту. Тому
можливе поєднання `success` і `fetching`, коли дані показано, а у фоні йде перевірка.

</details>

**3. Ключі `['todos', { page, status }]` і `['todos', { status, page }]` дають один запис кешу чи два? А
`['todos', page, status]` і `['todos', status, page]`?**

<details><summary>Відповідь</summary>

Перші два дають один запис, бо бібліотека впорядковує поля об'єкта перед перетворенням ключа на рядок. Другі два дають
два записи, бо в масиві порядок елементів зберігається.

</details>

**4. За сторінкою `Important Defaults`, після яких трьох подій застарілий запит перезапитується у фоні? Яка з них
спрацьовує, коли людина повертається на екран вашого застосунку?**

<details><summary>Відповідь</summary>

Коли монтується новий екземпляр запиту, коли вікно знову отримує фокус і коли відновлюється мережа. Повернення на
екран є першою подією: маршрутизатор знову рендерить компонент, і його `useQuery` створює нового спостерігача.

</details>

**5. Чим `staleTime: Infinity` відрізняється від `staleTime: 'static'`?**

<details><summary>Відповідь</summary>

Обидва не дають перезапитувати дані через застарілість. Але запис з `Infinity` можна інвалідувати вручну, і тоді він
перезапитається, а запис зі `'static'` не перезапитується навіть після інвалідації.

</details>

**6. Ви поставили `ReactQueryDevtools` у провайдер, зібрали застосунок і відкрили `vite preview`. Панелі немає.
Чому?**

<details><summary>Відповідь</summary>

Сторінка `Devtools` каже, що панель потрапляє в бандл лише в режимі розробки, коли `process.env.NODE_ENV` дорівнює
`'development'`. У продакшн-збірці компонент повертає `null`. Щоб побачити панель, запустіть `npx vite`.

</details>

**7. Сервер `tanstack-query-docs` показує приклад `Quick Start` з рядком
`render(<App />, document.getElementById('root'))`. Чи писати так у вашому проєкті?**

<details><summary>Відповідь</summary>

Ні. Сервер тримає документацію версії 5.103.3, де стояв старий виклик з React 17. У версії 5.108.4 приклад уже
використовує `createRoot(…).render(<App />)`, як ваш `main.tsx`, а в React 19 старого `render` немає.

</details>
