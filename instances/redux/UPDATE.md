# Оновлення корпусу redux

Дві різні роботи: звичайне оновлення (вийшли нові релізи бібліотек) і нова бібліотека поруч із Redux. Порядок
усередині кожної важливіший за самі команди.

Головне правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Сторінка, що зникла з документації, чи версія, прибрана з реєстру, лишається в `corpus/`; прибрати — рішення людини.

## 1. Звичайне оновлення

**Крок 1. Нові теги.** Документація береться з тегів, перелічених у полі `tags` джерел `*-docs` у `sources.json`
(«тег → версія», від найновішого). Новий реліз — новий рядок нагорі цього поля: `"v2.14.0": "2.14.0"`. У
монорепозиторіях — лише теги свого пакета: у redux-toolkit `v…` (не `@rtk-query/…`), у redux-saga `v…` і
`redux-saga@…` (не `@redux-saga/…`). Нотатки релізів, README і реєстр npm нові версії підхоплюють самі.

**Крок 2. Завантаження й решта.**

```
./df redux sources --why
./df redux refresh --missing      # лише нове; повний refresh — ~1,5 години
./df redux manifest
./df redux vectors
./df redux smoke
# Ctrl+C у терміналі з serve, і знову: ./df redux serve
```

`--missing` докачує документи, яких ще немає, і не чіпає наявних. Цього досить для нових тегів і релізів. Повний
`refresh` потрібен, коли змінився перелік версій уже наявного тексту: документ пам'ятає всі версії, де текст був
таким, і з новим тегом цей перелік росте. З Claude Code довгі кроки запускати окремим процесом
(`setsid nohup …`), інакше оболонка обірве їх через 30 хвилин.

Корпус комітити логічними частинами до ~700 файлів: кожна бібліотека окремо (Redux і Toolkit — двома частинами),
нотатки релізів, README, реєстр npm.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Нова бібліотека поруч із Redux

**Документація** — джерело `ghdocs-history` за зразком `saga-docs`: префікс дерев репозиторію, теки документації,
теги релізів пакета з версіями. Якщо документація живе в монорепозиторії, — лише теги цього пакета.

**README** — лише якщо README пакета є документацією, а не посиланням на сайт; дивитися на README в опублікованих
пакетах старих ліній. Джерело `npm-readme` за зразком `readme-redux-saga`.

**Нотатки релізів** — `ghreleases` за зразком `saga-releases`; `skip` — вираз тегів чужих пакетів монорепозиторію.

**Реєстр** — `npm-versions` за зразком `npm-redux-saga`.

Потім `refresh --missing`, `manifest`, `vectors`, `smoke`, як у розділі 1, і рядок у таблиці бібліотек README.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df redux quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточні лінії:** Toolkit 2, Redux 5, React Redux 9, Reselect 5, Immer 11. `prompts/search.txt` (абзац «Which
  version to search first») і `prompts/agent.txt` велять шукати з лінією тієї бібліотеки, про яку питання; нова
  мажорна версія — правка цих двох абзаців і `quality_model` у `checks.json`.
- **Правила промпту, що вже є:** запит — назвами API англійською; без версії — історія, міграції й сумісність;
  номери версій — свої в кожної бібліотеки; кожна відповідь каже бібліотеку й версію; на старий стиль Redux — ще й
  як це робить Toolkit.
- **Останній результат:** у README, абзац «Замір `quality`».
