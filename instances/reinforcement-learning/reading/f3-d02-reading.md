у float32. Потік (stream) у коментарях `pine` — одна модель одного терміну. Запас (margin) у цьому файлі має два
значення, і їх треба розрізняти: `margin32` — це сума листків до сигмоїди, а запас над порогом рахується пізніше, у
`board.js`.

### Функція `parseTree`

Функція отримує одне дерево з файла моделі й перекладає п'ять його списків у типізовані масиви JavaScript.

| Поле дерева у файлі | Масив у `score.js` | Що в ньому |
|---------------------|--------------------|-------------|
| `left_children` | `left`, `Int32Array` | для кожного вузла номер вузла, куди йти ліворуч; `-1` означає, що вузол — листок |
| `right_children` | `right`, `Int32Array` | номер вузла, куди йти праворуч |
| `split_indices` | `feat`, `Int32Array` | номер ознаки, про яку питає вузол |
| `split_conditions` | `cond`, `Float32Array` | у вузлі з запитанням — поріг; у листку — значення листка |
| `default_left` | `defLeft`, `Uint8Array` | куди йти, якщо ознаки немає: 1 — ліворуч |

Коментар над функцією пояснює, чому поріг і значення листка лежать в одному масиві: у самій бібліотеці це одне поле
пам'яті, яке читається по-різному залежно від того, листок це чи ні. Типізований масив `Float32Array` тут не лише для
швидкості: запис числа в нього вже є округленням до float32.

### Функція `loadModels`

Функція отримує теку моделей `mlDir`, спільну частину назви `prefix`, список термінів `exps` і, за бажанням, список
порогів `cuts`. Для кожного терміну вона читає файл `<prefix>-exp<термін>.json`.

| Що робить код | Що це означає |
|---------------|---------------|
| `learner.learner_model_param.num_feature` | скільки ознак чекає модель; у чинних моделях 59 |
| `Number(String(base_score).replace(/[[\]]/g, ''))` | `base_score` у файлі записано рядком у квадратних дужках, наприклад `[4.8474342E-1]`; код знімає дужки |
| `learner.gradient_booster.model.trees.map(parseTree)` | усі дерева моделі |
| `if (cuts) cut = Number(cuts[k]); else` читати файл `<prefix>-exp<термін>.cut` | поріг береться зі списку, якщо його передано, інакше з файла `.cut` поруч із моделлю |
| `if (!(cut > 0 && cut < 1)) throw` | поріг мусить бути ймовірністю |
| `base32: Math.fround(logit(baseScore))` | стартове значення суми: логарифм шансів числа `base_score`, округлений до float32 |
| `cutM: logit(cut)` | поріг у логарифмі шансів, у звичайній точності float64 |
| `cutM0`, коли передано `cuts0` | поріг до підняття `--cut-raise`; потрібен лише, щоб показати сигнали, які підняття відсікло |

Список `cuts` приходить із файла дошки. Наприклад, у `live/orchestra/x3-1.json` для моделей `ll1-rt9x-A-r400` записано
терміни `[2, 3, 4]` і три пороги. Тобто чинний запуск файли `.cut` не читає: його пороги лежать у файлах дощок.

### Функція `margin32`

```javascript
export function margin32(model, row, off = 0) {
    let psum = 0;
    const trees = model.trees;
    for (let k = 0; k < trees.length; k++) {
        const t = trees[k];
        let nid = 0;
        for (;;) {
            const l = t.left[nid];
            if (l === -1) break;
            const v = row[off + t.feat[nid]];
            if (v !== v) nid = t.defLeft[nid] ? l : t.right[nid];          // NaN: the default branch
            else nid = v < t.cond[nid] ? l : t.right[nid];
        }
        psum = Math.fround(psum + t.cond[nid]);
    }
    return Math.fround(model.base32 + psum);
}
```

- `row` — один довгий масив, у якому рядки ознак лежать один за одним. `off` — місце, з якого починається потрібний
  рядок. Ознака з номером `j` цього рядка лежить у `row[off + j]`.
- `nid = 0` — прохід починається з кореня дерева.
- `if (l === -1) break` — якщо лівого сусіда немає, вузол є листком, і прохід закінчено.
- `v !== v` — перевірка на `NaN`: це єдине значення, яке не дорівнює саме собі. Для нього вузол має записаний наперед
  напрямок.
- `v < t.cond[nid] ? l : t.right[nid]` — правило вузла. Порівняння строге.
- `psum = Math.fround(psum + t.cond[nid])` — після виходу з циклу `nid` вказує на листок, і `t.cond[nid]` є значенням
  листка. Сума після кожного дерева округлюється до float32.
- Останній рядок додає стартове значення `base32`. Порядок важить: спершу всі листки, потім стартове значення. У
  float32 інший порядок додавання може дати інше останнє число.

**Порівняння: каса, яка округлює після кожної позиції.** Якщо ціну кожної позиції чека округлити до копійки й додати,
сума може на копійку відрізнятися від суми точних цін, округленої один раз наприкінці.

| У порівнянні | У `margin32` |
|--------------|--------------|
| ціна однієї позиції | значення листка одного дерева |
| округлення до копійки після кожної позиції | `Math.fround` після кожного дерева |
| сума на чеку | сума листків, яку повертає функція |

Порівняння перестає працювати в наслідках. На касі копійка нічого не вирішує. Тут різниця в сьомому знаку вирішує лише
тоді, коли оцінка стоїть точно на порозі, але саме такі рядки й відрізняють «сигнал» від «не сигнал».

### Функції `sigmoid32`, `logit32` і `scoreRows`

`sigmoid32(m)` рахує `1 / (1 + exp(-m))` і округлює до float32 після кожної дії. Це оцінка: число від 0 до 1.
`logit32(p)` рахує логарифм шансів оцінки, теж у float32, і перед цим обрізає оцінку до проміжку від `1e-9` до `1 −
1e-9`, щоб не ділити на нуль. `scoreRows(model, X, nRows, f)` викликає `sigmoid32(margin32(...))` для кожного з
`nRows` рядків шириною `f` ознак.

Запас над порогом у цьому файлі не рахується. Його рахує `live/board.js`: для кожної пари він оцінює два рядки ознак,
«вгору» і «вниз», бере більшу з двох оцінок і рахує `g = logit32(p) - mdl.cutM`. Сигнал є, коли найбільший із запасів
моделей системи не менший за нуль: `fired: bestG >= 0`.

Кінець файла — службовий запуск `node live/score.js --rows <файл>` для програми звірки. Типові значення в ньому,
`ll1-d4y6-250x4x0.05` і терміни `3,4,5,7,9,13`, лишилися від вересневих моделей і до чинного запуску не стосуються.

**Навіщо це в проєкті `po-rl`.** Ваш читач оцінок у Python має повторити саме ці дії в тому самому порядку: строге
порівняння, `NaN` у записаний напрямок, сума листків у float32, стартове значення останнім, сигмоїда у float32. Тоді
його можна звірити з числами, які `pine` уже зберіг.

### `dataset.js`: функція `labelAt` і горизонт

```javascript
const labelAt = (bf, i, side, horizon) => {
    const j = i + horizon - 1;
    if (j >= bf.n) return null;
    const d = bf.close[j] - bf.open[i];
    return { win: side > 0 ? d > 0 : d < 0, decisive: d !== 0 };
};
```

Вхід вирішується на відкритті бара `i`. Результат береться із закриття бара `i + horizon − 1`: той самий відлік, що в
лекції «Стан, дія і винагорода», тільки термін тут названо горизонтом. `d > 0` для угоди «вгору» і `d < 0` для угоди
«вниз» — строгі порівняння, тож рівні ціни дають `win: false`. Коментар над функцією пояснює, навіщо горизонт: на
одній хвилині модель з 32 ознаками мала частку виграшів `48,8 %` проти потрібних `58,8 %`, і з довшим терміном нічиїх
стає менше. Там само стоїть речення `FEATURES DO NOT MOVE`: ознаки завжди читаються на барі `i − 1`, хоч би який був
горизонт.

Решта файла збирає рядки. `rowsForPair` для кожного сигналу викликає `fillRow` з `features.js` і `labelAt`. Блок
запуску ділить рядки датою `--split`, типово `2025-08-22`, і пише `data/ml/train-m1.bin`, `test-m1.bin` і
`features.json`. Файл `data/ml/features.json` у вас на диску — саме від цього запуску: 52 ознаки, дата поділу
22.08.2025, горизонт 1.

### `Introduction to Boosted Trees`: `Decision Tree Ensembles`

| Що написано | Що це означає |
|-------------|---------------|
| модель — набір дерев класифікації та регресії, CART | кожне дерево ділить рядки на групи запитаннями до ознак |
| у CART у кожному листку лежить дійсне число, а не лише рішення | листок не каже «так» чи «ні»; він каже, скільки додати |
| одного дерева замало, тому беруть ансамбль, який додає прогнози багатьох дерев | прогноз бустера — сума |
| у прикладі два дерева доповнюють одне одного | друге дерево вчиться на тому, чого не вловило перше |
| формула `\hat{y}_i = \sum_{k=1}^K f_k(x_i)` | прогноз для рядка `i`: пройти рядком `x_i` кожне з `K` дерев і додати значення листків |
| випадковий ліс і бустер — та сама модель, різниця лише в навчанні | прохід деревами той самий; тому `score.js` читає і бустери `pine`, і його ліс `rf` тим самим кодом |

Останнє твердження видно у файлах `pine`. Модель `ll1-rt9x-rf-r1-exp5.json` має 100 дерев глибини до 12 і поле
`num_parallel_tree: 100`: це ліс, навчений за один крок. Модель `ll1-rt9x-A-r400-exp2.json` має 400 дерев глибини до 6
і `num_parallel_tree: 1`: це бустер. Функція `margin32` проходить обидві однаково.

Одна відмінність усе ж є, і її видно в записі з `live-config.md` про навчання лісу: `eta 1 (the sum of the trees is
their average)`. Ліс має усереднювати дерева, а код їх додає. Це узгоджено під час навчання: значення листків лісу вже
поділені на кількість дерев.

### `Introduction to Boosted Trees`: `Tree Boosting`

Ця частина пояснює навчання. Для читання прогнозу вона не потрібна, але з неї походять назви налаштувань. Дерева
додаються по одному: `\hat{y}_i^{(t)} = \hat{y}_i^{(t-1)} + f_t(x_i)`. Нове дерево вибирають так, щоб якнайбільше
зменшити мету навчання, яка складається з двох частин: втрати на навчальних даних і штрафу за складність. Штраф за
складність дерева записано як `\omega(f) = \gamma T + \frac{1}{2}\lambda \sum_{j=1}^T w_j^2`: тут `T` — кількість
листків, `w_j` — значення листків. Найкраще значення листка дорівнює `w_j^* = -G_j / (H_j + \lambda)`: сума похідних
втрати за рядками листка, поділена на суму других похідних плюс `\lambda`.

| Слово документа | Що це означає |
|-----------------|---------------|
| objective function | мета навчання: число, яке навчання зменшує |
| training loss | втрата: наскільки прогнози розходяться з відповідями навчальних рядків |
| regularization | штраф за складність: що більше листків і що більші їхні значення, то більший штраф |
| overfitting | перенавчання: модель запам'ятала навчальні рядки разом з їхніми випадковостями |
| additive training | дерева додаються по одному, а вже додані не змінюються |

Останній рядок пояснює, чому в `pine` є моделі з `r400` у назві. Якщо дерева додаються по одному й старі не
змінюються, перші 400 дерев моделі з 800 дерев самі є готовою моделлю. Файл `ll1-rt9x-A-r400-exp2.summary.json` так і
каже: джерело `ll1-rt9x-a-800x6x0.05-exp2.json`, `rounds: 400`. Документ `Prediction` називає це `iteration_range` і
порівнює з розрізанням моделі.

### `Intercept`

Документ пояснює число `base_score`, з якого починається сума.

| Що написано | Що це означає |
|-------------|---------------|
| з версії 2.0.0 XGBoost сам оцінює `base_score` з відповідей навчальних рядків | у моделях `pine` це число ніхто не задавав; для терміну 2 воно дорівнює `0,48474342`, тобто частці виграшів у навчальних рядках |
| число `0,5` тут — значення після зворотної функції зв'язку | `base_score` записано як імовірність, а не як доданок до суми |
| для логістичної регресії з `base_score = 0,5` до сирого виходу моделі додається `logit(0,5) = 0` | у суму йде логарифм шансів числа `base_score` |
| формула `E[y_i] = g^{-1}(F(x_i) + g(intercept))` | оцінка дорівнює сигмоїді від суми листків плюс логарифм шансів `base_score` |

У формулі `F(x_i)` — сума листків усіх дерев, `g` — функція зв'язку, для мети `binary:logistic` це логарифм шансів, а
`g^{-1}` — зворотна до неї функція, сигмоїда. Саме цю формулу виконує `score.js`: `base32 = fround(logit(baseScore))`,
потім `margin32`, потім `sigmoid32`.

**Незнайомі слова.** Intercept, або global bias, — стартове значення, однакове для всіх рядків. Link function —
функція зв'язку: перетворення, яке переводить імовірність у число без меж. Raw prediction, або margin, — сума до
зворотного перетворення. Base margin — стартове значення, задане окремо для кожного рядка; у `pine` його немає.

### `Prediction` і `XGBoost Parameters`

Документ `Prediction` здебільшого про форму масиву, який повертає функція `predict`. Для цього дня з нього потрібні
три місця.

| Що написано | Що це означає |
|-------------|---------------|
| `output_margin` дає прогноз без перетворення | суму листків разом зі стартовим значенням, до сигмоїди; це те, що повертає `margin32` |
| `base_score` і `base_margin` задають глобальний зсув моделі | див. документ `Intercept` |
| `iteration_range` повертає прогноз лише від дерев із заданого проміжку кроків | так `pine` міряв ту саму модель на 100, 200, 300, 400, 600 і 800 деревах, не навчаючи її шість разів |

У документі `XGBoost Parameters` знайдіть налаштування, якими навчено моделі `pine`. Для моделі `A` їх записано у

означає 800 кроків, глибину 6 і крок навчання `0,05`.

| Налаштування | Що каже документація | Значення в моделі `ll1-rt9x-a-800x6x0.05` |
|--------------|----------------------|-------------------------------------------|
| `objective`: `binary:logistic` | логістична регресія для двох класів, на виході ймовірність | так записано в кожному файлі моделі |
| `max_depth` | найбільша глибина дерева; що вона більша, то складніша модель і то ймовірніше перенавчання | 6 |
| `eta`, або `learning_rate` | на це число множиться внесок кожного нового дерева, щоб навчання було обережнішим | `0,05` |
| `base_score` | стартовий прогноз для всіх рядків; оцінюється сам | `0,48474342` для терміну 2 |

Число дерев у назві, 800, — не налаштування з цього документа, а кількість кроків навчання. Ще одне число з файла
`summary.json`, `min_leaf: 1600`, каже, що листок не може спиратися менш ніж на 1600 навчальних рядків. Це головний
захист моделей `pine` від запам'ятовування окремих хвилин.

## López de Prado — `7 Cross-Validation in Finance`

**Де читати.** Сервер `tree-models-docs`, документ `7 Cross-Validation in Finance`. Це глава 7 книжки López de Prado,
Advances in Financial Machine Learning (Wiley, 2018).

**Хто написав і навіщо.** Автор пише для людей, які будують торгові моделі. Глава починається з твердження, що
стандартна перевірка моделей на фінансових даних не працює: перенавчання станеться, і перевірка його не помітить.

**Якщо часу мало.** Прочитайте розділи `7.1`, `7.2` і `7.3` та вправу `7.5`. Розділи `7.4` і `7.5` — код для бібліотек
pandas і scikit-learn, яких у `po-rl` немає.

### `7.1 Motivation` і `7.2 The Goal of Cross-Validation`

| Що написано | Що це означає |
|-------------|---------------|
| мета перехресної перевірки — визначити похибку узагальнення, щоб не допустити перенавчання | перевірка відповідає на запитання, як модель поводитиметься на даних, яких вона не бачила |
| перехресна перевірка сама сприяє перенавчанню через підбір налаштувань | якщо за результатом перевірки щось вибирають, цей результат перестає бути чесним |
| модель, перевірена на тих самих даних, на яких її навчено, показує блискучі результати | це і є пастка дня |
| такі алгоритми не відрізняються від стискання файлів із втратами: вони дуже точно переказують дані й нічого не передбачають | модель може бути добрим конспектом минулого і поганим прогнозом |
| перевірка ділить спостереження на навчальну й перевірну множини, і кожне належить рівно одній | жоден рядок не можна і вчити, і перевіряти |
| у схемі k-fold дані ділять на `k` частин; модель по черзі навчають на всіх, крім однієї, і перевіряють на ній | стандартна схема, яку далі автор розбирає |
| двійковий класифікатор чогось навчився, якщо його точність на перевірці вища за 1/2 | для бінарного опціону ця межа інша: `58,8 %` за виплати 70 % |

**Незнайомі слова.** Cross-validation, скорочено CV, — перехресна перевірка. Generalization error — похибка
узагальнення: похибка на нових даних. Hyper-parameter — налаштування, яке задають до навчання, наприклад глибина
дерева. IID, independent and identically distributed, — незалежні й однаково розподілені спостереження: кожне нічого
не каже про сусіднє. Backtesting — перевірка торгової стратегії на історії.

### `7.3 Why K-Fold CV Fails in Finance`

| Що написано | Що це означає |
|-------------|---------------|
| перша причина: спостереження не можна вважати незалежними | сусідні хвилини однієї пари схожі |
| друга причина: перевірну множину використовують багато разів, поки розробляють модель, і це дає множинні перевірки й упередження відбору | цю причину автор відкладає до глав 11–13 |
| ознака зі зв'язком у часі: `X_t ≈ X_{t+1}` | ознаки сусідніх хвилин майже однакові: вони рахуються з вікон, які перекриваються |
| мітки з даних, що перекриваються: `Y_t ≈ Y_{t+1}` | результат угоди на п'ять хвилин із хвилини `t` і з хвилини `t + 1` визначають майже ті самі бари |
| якщо `t` і `t + 1` потрапили в різні множини, інформація просочується | модель на перевірці «впізнає» рядок, майже копію якого бачила в навчанні |
| просочування небезпечне саме з марними ознаками: воно веде до хибних відкриттів | модель без жодної сили виглядатиме сильною |
| для просочування треба, щоб були схожі і ознаки, і мітка: `(X_i, Y_i) ≈ (X_j, Y_j)`; самих лише схожих ознак мало | якщо ознаки перевірного рядка читають бари з навчального періоду, це ще не витік |

**Порівняння: два кадри однієї серії.** Фотограф зробив два знімки з різницею в секунду. Якщо перший покласти в альбом
для навчання, а другий дати на іспит, учень «упізнає» знімок, якого начебто не бачив.

| У порівнянні | У наборі даних |
|--------------|----------------|
| кадр | рядок: ознаки хвилини й результат угоди |
| серія кадрів | сусідні хвилини однієї пари |
| альбом для навчання й іспит | навчальна й перевірна множини |

Порівняння перестає працювати в тому, наскільки це видно. Два кадри серії схожі на око. Два сусідні рядки набору
схожими не виглядають: це два довгі ряди чисел, і схожість треба вивести з того, як вони пораховані.

Прикладіть це до набору `ll1rt9x`. Мітка рядка з терміном `exp` читає бари від `i` до `i + exp − 1`. Мітка наступної
хвилини читає бари від `i + 1` до `i + exp`. Для терміну 5 чотири бари з п'яти спільні. Ознаки обох рядків рахуються з
вікон по 14, 60 і 240 барів, які зсунуті на один бар. Отже, сусідні рядки — саме те, що автор записує як `(X_i, Y_i) ≈
(X_j, Y_j)`, а коментар у `dataset.js` — як майже ту саму подію. Якби такі рядки розкидали навмання між навчанням і
перевіркою, перевірка нічого б не коштувала.

### `7.4 A Solution: Purged K-Fold CV`

Автор пропонує два прийоми. Очищення (purging): із навчальної множини прибирають кожне спостереження, мітка якого
перекривається в часі з якоюсь міткою перевірної множини. Ембарго (embargo): додатково прибирають навчальні
спостереження, які йдуть одразу після перевірної множини, на відрізку приблизно в одну соту всієї довжини даних.

Умову перекриття записано трьома нерівностями. Нехай перевірна мітка залежить від барів у проміжку від `t_{j,0}` до
`t_{j,1}`, а навчальна — від барів у проміжку від `t_{i,0}` до `t_{i,1}`. Мітки перекриваються, якщо навчальна
починається всередині перевірної, або закінчується всередині неї, або повністю її накриває.

```python
def getTrainTimes(t1, testTimes):
    trn = t1.copy(deep=True)
    for i, j in testTimes.iteritems():
        df0 = trn[(i <= trn.index) & (trn.index <= j)].index   # train starts within test
        df1 = trn[(i <= trn) & (trn <= j)].index               # train ends within test
        df2 = trn[(trn.index <= i) & (j <= trn)].index         # train envelops test
        trn = trn.drop(df0.union(df1).union(df2))
    return trn
```

Це `SNIPPET 7.1`, записаний заново: на сервері його рядки злито. Код написано для бібліотеки pandas, якої в плані
немає, тому читайте його як опис.

- `t1` — таблиця з одним стовпчиком: для кожного спостереження індекс є часом його початку, а значення — часом, коли
  стає відомою його мітка.
- `testTimes` — такі самі пари «початок, кінець» для перевірної множини. Цикл бере кожну пару як `i, j`.
- `df0` — навчальні спостереження, які почалися між `i` та `j`. `df1` — ті, які закінчилися між `i` та `j`. `df2` —
  ті, які почалися до `i` й закінчилися після `j`.
- `trn.drop(...)` прибирає всі три групи. Функція повертає те, що лишилося.

У `pine` такого коду немає, і ось чому він не знадобився. Навчальна половина закінчується 31.12.2022, перевірна
починається 01.01.2023, і межа одна. Останній вхід торгового дня — о 20:00, найдовший термін — 10 хвилин, а наступний
вхід — о 08:00 наступного торгового дня. Мітка останнього навчального рядка стає відомою задовго до першого
перевірного рядка, тож через межу не перекривається жодна пара міток. Очищення потрібне там, де меж багато, як у
k-fold; за одного розрізу по ночі воно виконується саме.

Розділ `7.5` описує дві вади бібліотеки scikit-learn 2018 року й до `po-rl` не стосується.

### Вправа `7.5`: упередження відбору

Вправу варто прочитати, хоч вона стоїть наприкінці. Автор пропонує уявити тисячу варіантів однієї стратегії, кожен із
яких перевірено. Частина з них виглядатиме добре просто від везіння, і якщо показати лише їх, ніхто не відрізнить
удачу від сили. Далі автор питає: що, як поділити дані на три частини — навчальну, перевірну для вибору й тестову, яку
читають один раз для єдиного вибраного варіанта, — і в якому випадку навіть це не рятує.

Саме цю схему записано в `year-roles.json`, і `pine` сам рахує, скільки варіантів він перебрав. Файл
`data/runs/rt9-features/fverdict.txt` починається рядком `k 1102, luck floor 3.74 se`: на 2024 році порівняно 1102
варіанти, і тому перевагу меншу за 3,74 стандартної похибки вирішено вважати везінням. Відповідь на запитання автора:
схема перестає працювати, щойно тестову частину читають удруге й за результатом щось змінюють. У `pine` про це подбано
файлами-позначками `read-2025.stamp` і `read-2025-features3.stamp` у теці `data/runs/rt9-features`. У кожному
записано, коли й для яких моделей прочитано 2025 рік, і слова власника, що за побаченим на 2025 і 2026 роках нічого не
вибирається. Опис даних у `data-model.md` тієї самої специфікації додає, що друге читання відхиляється.

**Навіщо це в проєкті `po-rl`.** Глава дає мову для розділу «Періоди» у вашому `DATA.md` і для дня 5 цієї фази, де ви
ділите на три частини вже свої дані. Для агента діє те саме, що для бустера: період, на якому щось вибирали, не
годиться для чесної оцінки вибраного.

## Що взяти собі

- Оцінку в `pine` рахує `margin32` плюс `sigmoid32`: строге порівняння у вузлі, сума листків у float32, стартове
  значення останнім.
- Запас над порогом рахує `board.js`, а пороги чинного запуску лежать у файлах дощок, а не у файлах `.cut`.
- Назв полів дерева в документації на сервері немає; їх узято з файлів моделей і з `score.js`.
- Чинні моделі навчено на наборі з `ll1-dataset.js`: рядок на хвилину, пару й напрямок, мітка на кожен термін.
  `dataset.js` описує попередній набір.
- Формула оцінки з документації: сигмоїда від суми листків плюс логарифм шансів `base_score`. Число `base_score`
  бібліотека оцінила сама, і воно дорівнює частці виграшів у навчальних рядках.
- Перші 400 дерев бустера з 800 — готова модель, бо дерева додаються по одному.
- Сусідні хвилини мають майже ті самі ознаки й майже ту саму мітку. Тому ділити можна лише за часом.
- Період, на якому вибирали налаштування чи пороги, вже не є чесною перевіркою того, що вибрали.

## Запитання до читання

**1. Що зробить `margin32`, якщо значення ознаки точно дорівнює порогові вузла, і що — якщо ознака дорівнює `NaN`?**

<details><summary>Відповідь</summary>

За рівності піде праворуч: правило вузла `v < t.cond[nid]` строге, а рівність його не виконує. За `NaN` піде туди,
куди каже `defLeft` цього вузла: ліворуч, якщо там 1, і праворуч, якщо 0.

</details>

**2. Чому `score.js` після кожного додавання викликає `Math.fround`?**

<details><summary>Відповідь</summary>

Бібліотека XGBoost додає листки у float32, а числа JavaScript мають точність float64. Без округлення сума відрізнялася
б в останніх знаках, і оцінка, що стоїть майже на порозі, могла б опинитися з іншого боку. Коментар у файлі називає
мету прямо: запас, який Python друкує як `+0.0000`, має стояти по той самий бік нуля.

</details>

**3. План радить читати `dataset.js`. На якому наборі насправді навчено чинні моделі й чим його рядок відрізняється?**

<details><summary>Відповідь</summary>

На наборі `ll1rt9x`, який написав `ll1-dataset.js`. У `dataset.js` рядок — один сигнал стратегії MAR1 з міткою за одну
хвилину. У `ll1-dataset.js` рядок — кожна хвилина сесії кожної пари в кожному з двох напрямків, і міток стільки,
скільки термінів: від 2 до 10 хвилин.

</details>

**4. У файлі моделі `base_score` дорівнює `0,48474342`. Звідки це число і що з ним робить оцінювач?**

<details><summary>Відповідь</summary>

Бібліотека оцінила його сама з відповідей навчальних рядків: це частка виграшів у навчальній половині для терміну 2, і
журнал побудови набору друкує те саме `0,4847`. Оцінювач бере його логарифм шансів, приблизно `−0,061`, і додає до
суми листків перед сигмоїдою.

</details>

**5. Чому випадковий поділ рядків на навчальні й перевірні не годиться для хвилинних даних?**

<details><summary>Відповідь</summary>

Сусідні хвилини однієї пари мають майже ті самі ознаки, бо вікна ознак зсунуті на один бар, і майже ту саму мітку, бо
результат угоди на кілька хвилин визначають майже ті самі бари. Випадковий поділ покладе один із таких рядків у
навчання, а другий у перевірку, і модель на перевірці впізнаватиме вже бачене.

</details>

**6. У `pine` дані поділено на навчання, два роки для вибору й рік, прочитаний один раз. Коли така схема перестає бути
чесною?**

<details><summary>Відповідь</summary>

Коли період для єдиного читання читають ще раз і за результатом щось змінюють. Після цього він стає ще одним періодом
для вибору. У `pine` від цього захищають файли-позначки про єдине читання 2025 року, а 2026 рік у `year-roles.json`
прямо названо слабкою перевіркою, бо його вже читали кілька разів.

</details>
