Search the documentation of Resend -- the email API for developers, and of its official Node.js SDK, the npm package
`resend` (site resend.com/docs, repository resend/resend-node, the npm registry). The corpus holds every page of the
site: getting started and sending with Node.js, Next.js, Express and other runtimes; the REST API reference
(emails: send, batch send, schedule, update, cancel, retrieve, attachments; received emails; domains; API keys;
audiences, segments and contacts; broadcasts; templates; topics; webhooks) with the Node.js, cURL and CLI examples
and the JSON responses; webhooks and their event types, signature verification, retries and replays; the dashboard
(emails, idempotency keys, attachments, scheduling, tags, domains and DNS, DMARC, inbound receiving, automations,
broadcasts, contacts); the knowledge base on deliverability (SPF, DKIM, DMARC, bounces, spam); and guides. It also
holds the README of every stable `resend` version from npm, 0.1 to 6.34, the npm registry entry with release dates,
and the release notes of every stable resend-node release. Returns the matching excerpts with the versions each one
belongs to.

Call this when a question is about Resend as it describes itself -- how to send an email with `resend.emails.send()`
and which fields it takes (`from`, `to`, `subject`, `html`, `text`, `react`, `cc`, `bcc`, `replyTo`, `attachments`,
`tags`, `headers`, `scheduledAt`), how batch sending, scheduling and idempotency keys work, how to add and verify a
domain and which DNS records it needs, how to receive and verify webhooks, what the rate limits and quotas are, what
an error code means -- and history: since which SDK version a method or option exists, what changed between versions
(the release notes list it).

Do not call this for React Email itself -- its components, `render()` and CLI are the react-email documentation
(react-email-docs) -- nor for Next.js, Node.js, nodemailer, SMTP servers or DNS providers as their own projects:
their documentation is not here -- these pages only show how Resend is used with them -- and the search will return
excerpts that merely mention them, with confident-looking titles. The PHP, Python, Ruby, Go, Rust, Java, .NET and
Elixir examples of the site are not kept; only Node.js, cURL and the CLI are.

`version` narrows the search to one release line of the npm package `resend`: a line of one number keeps every
document of that major ("6" keeps 6.x), two numbers keep a minor ("6.34"), three an exact version ("4.8.0"). The pages
of the site carry no version -- the API is one live service -- so leave `version` empty for anything about the API,
the dashboard or deliverability. Every excerpt comes back with `versions`: each version whose documents contain this
exact text, newest first.

Write the query in English, with the names the documentation itself uses ("send email", "batch", "scheduledAt",
"idempotency key", "attachments", "tags", "domains", "DNS records", "SPF", "DKIM", "DMARC", "webhooks", "verify
webhook", "event types", "rate limit", "API keys", "audiences", "contacts", "broadcasts", "templates", "react"), not
in the user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike --
and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація Resend". Identifiers, parameters and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By npm downloads in the week before 25 October 2026 the line 6 of `resend` holds 81 %
(6.34.1 of 16 October 2026 is the newest), the line 4 -- 15 %. Answer SDK questions for 6.x: search without
`version` first (the site describes the current API and SDK), then with "6" for the README and the release notes;
when the user's code uses an older line, search it as well and say what changed. Every answer about the SDK says
which version it is for.
