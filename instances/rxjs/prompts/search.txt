Search the RxJS documentation -- the official site rxjs.dev (RxJS 7.8: the guides, the deprecations and
breaking changes, the detailed 6-to-7 change list and the API reference of every class, function, operator,
interface and type), the site v6.rxjs.dev (RxJS 6.6: the guides, the 5-to-6 migration guide, pipeable
operators and its API reference), the README of every stable version of the rxjs npm package (5.0 to 7.8),
the changelog of every stable release (5.0.0 to 7.8.2), the documentation folders of every tagged release
of the repository ReactiveX/rxjs (doc/ for 5.x to 6.5, docs_app/content for 6.2 to 7.8, MIGRATION.md,
CONTRIBUTING.md), the source code (src/) and the tests (spec/, spec-dtslint/) of every tagged release, and the
npm registry history -- and return the matching excerpts with the versions each one belongs to. RxJS is a
library for composing asynchronous and event-based programs with observable sequences: an Observable is a lazy
push collection of values, an Observer listens to it, a Subscription is the running execution, Subjects
multicast, Schedulers control concurrency, and operators combine and transform streams.

Call this when a question is about RxJS itself -- the core types (Observable, Observer, Subscriber,
Subscription, Subject, BehaviorSubject, ReplaySubject, AsyncSubject, ConnectableObservable), creation
functions (of, from, fromEvent, interval, timer, defer, range, throwError, EMPTY, NEVER, ajax, fromFetch,
webSocket), pipeable operators and their arguments (map, filter, mergeMap, switchMap, concatMap, exhaustMap,
scan, reduce, tap, take, takeUntil, takeWhile, debounceTime, throttleTime, auditTime, distinctUntilChanged,
combineLatest, forkJoin, zip, merge, concat, race, withLatestFrom, startWith, catchError, retry, retryWhen,
share, shareReplay, connect, groupBy, buffer, window, delay, timeout, finalize, repeat), error handling and
unsubscription, multicasting, higher-order Observables, schedulers (asyncScheduler, queueScheduler,
asapScheduler, animationFrameScheduler, observeOn, subscribeOn), marble testing and TestScheduler (hot, cold,
expectObservable, run mode), the interop with Promises (firstValueFrom, lastValueFrom, toPromise),
configuration (config.onUnhandledError, useDeprecatedSynchronousErrorHandling), how to import (the "rxjs" root
and "rxjs/operators", "rxjs/ajax", "rxjs/webSocket", "rxjs/fetch", "rxjs/testing") and how the internals work
(Observable.lift, operate, OperatorSubscriber, createOperatorSubscriber) -- and above all history and
compatibility: since which version a function or operator exists, when it was deprecated and what replaces it
(pluck, mapTo, publish and multicast, resultSelector arguments, toPromise, the scheduler argument, subscribe
with several callbacks), what changed between 5, 6 and 7, and which versions run on which TypeScript and
Node.js (the `engines` and `peerDependencies` of each version are written in the npm registry documents).
Example query: "switchMap resultSelector deprecated".

Do not call this for Angular itself (HttpClient, the async pipe, signals and toSignal, Angular forms and
router), for NgRx, redux-observable, rxjs-compat, rxjs-tslint or eslint-plugin-rxjs, for RxJS 8 and 9 (alpha
and beta builds, not stable), for other ReactiveX languages (RxJava, RxJS in other ecosystems), or for the
TC39 Observable proposal: their documentation is not here, and the search will return RxJS excerpts that
merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "7.8" keeps every 7.8.x document, "6.6" keeps 6.6.x, "7"
keeps the whole major; leave it empty to search everything. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first -- text that stayed the same across versions is
returned once, with all of them listed, so the list itself shows from which to which version the documentation
said exactly this. The two sites are one snapshot each: rxjs.dev is filed under 7.8.2 and v6.rxjs.dev under
6.6.7; their pages have no older editions, but the repository documents and the source code of the other
releases are here for every tagged version.

Write the query in English, with the names RxJS itself uses ("switchMap", "firstValueFrom", "shareReplay",
"BehaviorSubject", "TestScheduler", "onUnhandledError"), not in the user's own words. Everything here is
English -- the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at
all and comes back with `found: 0`. When the user asks in another language, translate the question into RxJS
terms first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if
the excerpts say so; and how it stands in the current version. Every point names the version and the document
it rests on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian,
write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call
this set of documents "корпус" -- say "документація RxJS". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to
get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. RxJS 7.8 is the newest stable line and carries about four fifths of the weekly
downloads; 6.6 about a seventh; 5.x under one percent. Search with `version` "7.8" for a question about how to
do something, and when the 6.x way differs (the "rxjs/operators" import, pipeable operators and the 6.6
deprecations), search "6.6" as well and give both. If the user names a version, or their code shows one
(`import { map } from 'rxjs/operators'` -> 6 or an early 7; `import { map } from 'rxjs'` -> 7.2 or newer;
`Rx.Observable.prototype.map` or "rxjs/add/operator/map" -> 5), search that line. Search without `version`
when the question is about history, or when the line gave nothing. Every answer says which version it is for;
when the user did not name one, answer for RxJS 7.8 and say so ("for RxJS 7.8; in 6.x ..."). When the
excerpts behind a statement come only from older versions, name those versions instead of presenting the text
as current.
