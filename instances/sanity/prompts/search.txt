Search the documentation of Sanity -- the content platform: Sanity Studio (the editing app, npm package `sanity`),
the Content Lake (the hosted datastore), the query language GROQ and the JavaScript libraries around them (sites
www.sanity.io/docs and reference.sanity.io, repositories sanity-io/* on GitHub, the npm registry). The corpus holds
every page of www.sanity.io/docs: Studio configuration, schema types and fields, structure and document actions,
plugins, the Content Lake (documents, datasets, references, drafts and versions, releases, assets and images,
webhooks, CORS, tokens and roles), GROQ and its functions, the HTTP API reference (query, mutate, listen, history,
export), the CLI reference, Visual Editing and the Presentation tool, Live Content, Functions, Blueprints, Canvas,
Media Library, Build with AI, the framework guides (Next.js, Astro, Nuxt, Remix and others) and the help articles. It
also holds the TypeDoc API reference reference.sanity.io (classes, functions, types and options of `sanity`,
`@sanity/client`, `next-sanity`, `@sanity/sdk`, `@sanity/sdk-react`, `@sanity/visual-editing`, `@sanity/blueprints`,
`@sanity/functions` and others), the README of every stable version of the npm packages `sanity`, `groq`,
`@sanity/vision`, `@sanity/cli`, `@sanity/client`, `next-sanity`, `@sanity/image-url`, `@sanity/visual-editing` and
`@portabletext/react`, their npm registry entries with release dates, and the release notes of the GitHub releases of
sanity, client, next-sanity, cli, image-url, visual-editing and react-portabletext. Returns the matching excerpts with
the versions each one belongs to.

Call this when a question is about Sanity as it describes itself -- how to define a schema with `defineType` and
`defineField`, which options a field type takes, how to configure `sanity.config.ts`, the structure tool and
document actions, how to write a GROQ query or projection, how references, drafts, perspectives and releases work,
how to query with `createClient` and `client.fetch`, how to set up `next-sanity`, Visual Editing, `defineLive` or
image URLs with `urlFor`, which CLI command does what, what an HTTP API endpoint takes and returns -- and history:
since which version a feature or option exists, what changed between versions (the README and the release notes
list it).

Do not call this for Next.js, React, Astro, Nuxt, Vercel or Portable Text editors of other projects as their own
projects: their documentation is not here -- these pages only show how Sanity is used with them -- and the search
will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line. The README, registry and release notes of `sanity` carry the plain
version of the Studio release ("6.20.0", "3.99.0"), and so do `groq` and `@sanity/vision`, which ship together with
it: a line of one number keeps every document of that major ("6" keeps 6.x), two numbers keep a minor ("6.20"). The
other packages carry their name before their own number: "client-8" keeps `@sanity/client` 8.x, then "cli-",
"next-sanity-", "image-url-", "visual-editing-", "portabletext-react-". The pages of www.sanity.io/docs and of
reference.sanity.io carry no version -- they describe the current release -- so leave `version` empty for those.
Every excerpt comes back with `versions`: each version whose documents contain this exact text, newest first.

Write the query in English, with the names the documentation itself uses ("schema types", "defineField",
"reference", "array of objects", "validation", "structure builder", "document actions", "GROQ", "projection",
"perspectives", "drafts", "releases", "createClient", "useCdn", "apiVersion", "next-sanity", "defineLive",
"visual editing", "presentation tool", "image url", "hotspot", "portable text", "webhooks", "CLI"), not in the user's
own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word
index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the
question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус"
-- say "документація Sanity". Identifiers, parameters and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was
cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By npm downloads in the week before 25 October 2026 the line 6 of `sanity` holds 52 %
(6.20.0 is the newest), the line 5 -- 24 %, the line 3 -- 14 %; `@sanity/client` 7 holds 51 % and 8 -- 35 %;
`next-sanity` 13 holds 53 %. Answer for the current lines: search without `version` first (the site and the
reference describe the current release), then with the line for the README and the release notes; when the user's
code uses an older line, search it as well and say what changed. Every answer about a package says which version it
is for.
