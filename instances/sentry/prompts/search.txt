docs.sentry.io -- the browser SDK and the guide of every JavaScript framework and runtime
(Next.js, React, React Router, Remix, TanStack Start, Vue, Nuxt, Angular, Svelte, SvelteKit,
Solid, SolidStart, Astro, Gatsby, Ember, Node.js, Express, Fastify, Koa, Hapi, Hono, NestJS,
Elysia, Nitro, Bun, Deno, Cloudflare, AWS Lambda, Azure Functions, Google Cloud Functions,
Firebase, Electron, Capacitor, Cordova, Effect, Mastra, Wasm and others): installation and
manual setup, Sentry.init options, capturing errors, error boundaries, tracing and sampling,
distributed tracing, Session Replay, profiling, logs, metrics, cron monitoring, user feedback,
enriching events (scopes, tags, context, breadcrumbs, fingerprinting, event processors),
filtering and data scrubbing, integrations, source maps and their upload, OpenTelemetry, the
migration guides between major versions and the pages kept for older SDK lines; the general
sections of docs.sentry.io -- the product (Issues, Traces, Replays, Alerts, Dashboards, Releases,
Crons, Uptime, Explore), concepts (DSN, keys, quotas, search syntax, data), sentry-cli,
organization and account settings with auth tokens, security, legal and PII; the integrations
(GitHub, GitLab, Slack, Jira, Vercel, Netlify and others) and the REST API of Sentry, one page per
endpoint. Also: the README, the migration guides and the changelog of every release of the
JavaScript SDK (lines 4 to 11, repository getsentry/sentry-javascript); the README with every
option of the bundler plugins (@sentry/vite-plugin, webpack-plugin, rollup-plugin,
esbuild-plugin), their migration guide and changelog; the README and changelog of sentry-cli;
and the npm registry record of every @sentry/* SDK package, of the bundler plugins and of
@sentry/cli -- every version with its date, its dist-tags and what changed in exports,
dependencies, peer dependencies and Node requirements. Returns the matching excerpts with the
versions each one belongs to.

Call this when a question is about Sentry in a JavaScript or TypeScript project: adding the SDK
to a framework, what an option of Sentry.init or of withSentryConfig does, why errors or traces
do not arrive, sampling, source maps and readable stack traces, releases and environments,
privacy and masking in Session Replay, alerts and issue grouping, auth tokens and CI, sentry-cli
commands, the REST API, which @sentry/* version supports a given framework version, and what
changed between SDK versions or how to migrate. Example query: "withSentryConfig sourcemaps
deleteSourcemapsAfterUpload".

Do not call this for Sentry SDKs of other platforms (Python, Go, Java, .NET, PHP, Ruby, Rust,
Android, Apple, Flutter, React Native, Unity), for self-hosting the Sentry server, for other
monitoring tools (Datadog, New Relic, Grafana, Prometheus, OpenTelemetry Collector) or for the
frameworks themselves -- React, Next.js, NestJS, Node.js, Vite, Express have their own
instances: their documentation is not here, and the search will return Sentry excerpts that
merely mention them, with confident-looking titles.

Frameworks. Most pages exist once per framework, with the same title and nearly the same text
("Source Maps for Next.js", "Source Maps for React", "Source Maps for Browser JavaScript"). Name
the framework in the query ("Next.js", "React", "NestJS", "Node.js", "Express", "SvelteKit") and
the result will take that framework's copy of the page; without a name the copy may belong to
any framework, so read the document title before answering. The browser SDK pages (Browser
JavaScript, @sentry/browser) have no framework name.

`version` narrows the search. Pages of the JavaScript section carry the SDK line they describe:
"11" is the current line, and a page kept for an older line carries its number ("10", "9", "8",
"7"). The general sections, the integrations and the REST API carry no version -- they describe
sentry.io as it is now. Changelog entries carry the exact version of the SDK ("10.75.2"), of the
bundler plugins ("5.4.1") or of sentry-cli ("3.8.0"), and npm registry documents carry every
version of the package they describe; since these numbers belong to different products, a version
filter alone mixes them -- name the product in the query too ("sentry-cli", "vite-plugin",
"@sentry/nextjs"). Leave `version` empty to search everything. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- text that
stayed the same across versions is returned once, with all of them listed.

Which version to answer for. When the user names no SDK version, answer for the current line 11
and say from which version a change applies; when the user names an older line, search with that
`version` -- a page for the old line exists only where it differs, otherwise the current page
applies and the changelog and the migration guides say what changed.

Where the documentation lives. Site pages are named by their path on docs.sentry.io
(platforms-javascript-guides-nextjs-sourcemaps, platforms-javascript-configuration-options,
platforms-javascript-migration-v10-to-v11, product-issues-…, concepts-key-terms-…, cli-…,
api-…, integrations-…); changelog documents are named by their version, npm documents by the
package and its version line (sentry-nextjs-line-11).

Write the query in English, with the names the documentation uses (Sentry.init, dsn,
tracesSampleRate, tracesSampler, tracePropagationTargets, replaysSessionSampleRate,
replaysOnErrorSampleRate, beforeSend, ignoreErrors, sendDefaultPii, environment, release,
captureException, captureMessage, ErrorBoundary, onRequestError, instrumentation.ts,
withSentryConfig, sentryVitePlugin, authToken, SENTRY_AUTH_TOKEN, debug IDs, sourcemaps upload,
tunnel, startSpan, setUser, setTag, withScope, breadcrumbs, fingerprint, maskAllText, Crons
monitor, Sentry logger, sentry-cli releases). Everything here is English -- the excerpts, the
word index and the meaning index alike -- and the word index keeps only latin letters and
digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing
at all and comes back with `found: 0`. When the user asks in another language, translate the
question into Sentry terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. When the question is about a change between SDK
versions, a deprecation or a migration, answer point by point: since which version; what
changed; what the migration requires; how it stands now -- each point with the document it rests
on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain
technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"помилка", "подія", "трасування", "вибірка", "карти коду", "реліз", "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація Sentry".
Identifiers, options, package names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
