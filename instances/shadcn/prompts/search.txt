Search the documentation of shadcn/ui and Radix UI, in English: the shadcn/ui documentation of
every minor release of its CLI (0.1 to 4.21) -- every component page with its examples and the
component source code, installation for each framework, theming and CSS variables, dark mode,
forms, the registry, the CLI, monorepo, RTL and the changelog -- both on the current site and on
the site for Tailwind CSS v3; and Radix UI -- Primitives (every part of every component with its
props, data attributes, CSS variables and keyboard interactions; utilities; guides on styling,
animation, composition and server-side rendering; the release notes of every package), Radix
Themes and Radix Colors. Returns the matching excerpts with the versions each one belongs to.

shadcn/ui is a set of components copied into your project; most of them wrap Radix Primitives,
and from 3.x each component also exists on Base UI and on React Aria. The shadcn page says how
to install and use a component and shows examples; the props, events, `data-*` attributes and
keyboard behaviour of the parts underneath (`open`, `onOpenChange`, `asChild`, `data-state`)
are on the Radix page of the same component. A question about controlling or customising a
shadcn component usually needs both.

Call this when a question is about shadcn/ui or Radix: adding a component (`npx shadcn add`),
`components.json`, theming with CSS variables, Tailwind CSS v4 vs v3 setup, dark mode, forms
with React Hook Form and zod, data tables, sidebars, charts, the registry, Radix props and
events, controlled vs uncontrolled state, `asChild`, portals, focus management, animation with
`data-state`, accessibility and keyboard navigation, Radix Themes components and tokens, Radix
Colors scales. Example query: "Dialog onOpenChange controlled open state".

Do not call this for other component libraries (Material UI, Chakra, Mantine, Headless UI,
Ark UI have no documentation here), for Tailwind CSS itself (the tailwind instance), for React
Hook Form or zod themselves (their own instances), or for React itself (the react instance): the
search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search. shadcn/ui pages carry the minor release of the CLI they were published
with: "shadcn-4.21" ... "shadcn-2.6" for the current site (ui.shadcn.com, Tailwind CSS v4), and
"shadcn-tw3-3.8" ... "shadcn-tw3-0.1" for the site for Tailwind CSS v3, which up to 2.5 was the
whole documentation. A major takes every minor of it: "shadcn-4" is every 4.x, "shadcn-tw3-3" every
3.x of the Tailwind v3 site, "shadcn-tw3-0" every 0.x. Radix Primitives pages carry "radix-ui-1.7"
... "radix-ui-1.1" (the single `radix-ui` package, 2025 on) and, for the years when every component
was a package of its own, the component and its version: "radix-dialog-1.1.2", "radix-dialog-0.1.7"
("radix-dialog-1" is every 1.x of the Dialog package). Radix Themes carry "radix-themes-3.3" ...
"radix-themes-1.0", Radix Colors "radix-colors-3.0" ... "radix-colors-0.1". Leave `version` empty to
search everything. Every excerpt comes back with `versions`: each version whose documents contain
this exact text, newest first.

Which version to answer for. Unless the user names a version, answer from the current site
("shadcn-4.21" and "radix-ui-1.7"). When the project uses Tailwind CSS v3 or an old CLI, filter
by the major of its CLI on the Tailwind v3 site ("shadcn-tw3-3", "shadcn-tw3-2", "shadcn-tw3-0");
when it imports `@radix-ui/react-dialog` and the like (one package per
component), filter by that component and its major ("radix-dialog-1"). Say which primitives
library a shadcn page is for when it matters: components/radix, components/base (Base UI) and
components/aria (React Aria) are three pages with different props.

Where the documentation lives. shadcn/ui pages are named by their path (shadcn-components-dialog
for the Radix variant, shadcn-components-base-dialog, shadcn-components-aria-dialog,
shadcn-installation-next, shadcn-theming, shadcn-forms-react-hook-form, shadcn-cli,
shadcn-registry-index; shadcn-tw3-components-dialog on the Tailwind v3 site); Radix pages by
the product and the component (radix-dialog, radix-overview-releases, radix-guides-styling,
radix-themes-components-button, radix-colors-overview-installation).

Write the query in English, with the names the documentation uses (Dialog, DialogTrigger,
DialogContent, Sheet, Drawer, DropdownMenu, Popover, Tooltip, Select, Combobox, Command, Form,
Field, DataTable, Sidebar, Chart, Toast, Sonner, components.json, cn, CSS variables,
--background, --primary, dark mode, ThemeProvider, open, defaultOpen, onOpenChange, asChild,

is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into shadcn and Radix terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Answer in the language the user wrote in. When the question is about a change between versions
or a migration (Tailwind v3 to v4, `@radix-ui/react-*` to `radix-ui`, Radix to Base UI), answer
point by point: since which version; what changed; what the migration requires; how it stands
now -- each point with the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as
a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "компонент", "проп", "подія", "стан", "тема", "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація shadcn/ui" or
"документація Radix". Component, prop, attribute and variable names stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
