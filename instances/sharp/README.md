# sharp — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про sharp, libvips і pyvips за їхньою документацією. sharp — модуль
Node.js для обробки зображень: він змінює розмір, перетворює формати й накладає одне зображення на інше. libvips —
бібліотека мовою C, яка виконує цю роботу всередині sharp. pyvips — прив'язка libvips до Python, тобто пакет, через
який ту саму бібліотеку викликають із коду Python.

## Навіщо три бібліотеки в одному примірнику

sharp сам зображень не обробляє: кожен його метод збирає ланцюжок операцій libvips і запускає його. Тому питання про
sharp часто має відповідь у документації libvips. Чому `resize()` дає саме таку різкість, пояснює опис функції
`vips_resize()`. Які значення приймає параметр `effort` для AVIF, описано у `vips_heifsave()`. Скільки пам'яті піде на
велике зображення, пояснює сторінка libvips про те, як вона відкриває файли. pyvips викликає ті самі операції під тими
самими іменами. В одному примірнику один пошук бачить усі три місця.

| Що питають | Де відповідь у цьому примірнику |
|------------|----------------------------------|
| Який метод sharp викликати і які в нього параметри | довідник API sharp і файл типів TypeScript |
| Як поставити sharp на Linux, у Docker, на AWS Lambda | сторінка встановлення sharp |
| З якої версії є параметр і що зламав реліз | журнал змін sharp, релізи, історія npm |
| Яку версію libvips і яких бібліотек форматів вкладено в готову збірку | журнал змін sharp і релізи sharp-libvips |
| Що робить операція всередині і які в неї необов'язкові аргументи | довідник C API libvips з коментарів у коді |
| Як користуватися командами `vips` і `vipsthumbnail` | посібник libvips і сторінки man |
| Як зробити те саме в Python | документація pyvips: клас `Image` з розділом на кожен метод |

**Що є що.** **Операція** — одна дія libvips над зображенням: зміна розміру, розмиття, запис у JPEG. Кожна операція
має три написання: функція C `vips_resize()`, команда `vips resize` і метод pyvips `Image.resize()`. **Необов'язкові
аргументи** — іменовані параметри операції, які можна не передавати (`kernel`, `gap`); у C вони йдуть парами «ім'я,
значення» наприкінці виклику. **Готова збірка** — уже скомпільована libvips разом із бібліотеками форматів, яку sharp
ставить пакетом npm `@img/sharp-libvips-*`, щоб нічого не компілювати на машині користувача. **Коментар gtk-doc** —
коментар особливого вигляду над функцією в коді C, з якого збирається довідник: ім'я функції, параметри, опис.
**Послідовний доступ** — спосіб читати файл зверху вниз один раз, без завантаження всього зображення в пам'ять.

## Звідки документація

- **Документація sharp — з репозиторію.** Сайт sharp.pixelplumbing.com збирається з теки `docs` репозиторію
  `lovell/sharp`, а сторінки API в ній згенеровано з коментарів у коді sharp. Узято останній тег кожної лінії
  0.11–0.35. З лінії 0.34 сторінки лежать у теці `docs/src/content/docs`, до того — просто в `docs`; поле
  `slug_rewrite` у `config.json` зводить імена тих самих сторінок до одного, щоб сторінка `api-resize` різних ліній
  займала у видачі одне місце.
- **Журнал змін sharp — файл на версію.** У теці `changelog` лежить окремий файл на кожен реліз, а версія є лише в
  імені файла. Читач `ghdocs-filever` бере версію з імені й додає до неї префікс `sharp-`.
- **Довідник функцій libvips — з коментарів у коді.** Текстом цей довідник ніде не лежить: сайт libvips.org/API
  збирається з коментарів над функціями в коді C і віддає лише три останні лінії. Читач `ghcode-history-gtkdoc` бере з
  кожного файла `.c` і `.h` лише ці коментарі й робить із кожного розділ: назва — ім'я функції («vips_resize()»), під
  нею оголошення, перелік параметрів і опис. Розмітку посилань він переводить у звичайні імена: «@scale» стає
  «`scale`», «[enum@Vips.Kernel.LANCZOS3]» — «`VIPS_KERNEL_LANCZOS3`». Файл, у якому між версіями мінялася лише
  реалізація, лежить одним документом: із 3 517 неповторних файлів коду вийшло 1 272 документи.
- **Посібник libvips — у трьох макетах.** У лініях 8.17–8.18 це сторінки markdown для засобу gi-docgen, у лініях
  8.5–8.16 — markdown зі службовим блоком XML на початку, а частина сторінок до 8.16 написана у форматі DocBook. Перші
  два макети читає `ghdocs-history-gidocgen`, третій — `docbook-gh`. Імена сторінок зведено правилами `slug_rewrite`:
  сторінка про командний рядок називалася `using-command-line.xml`, а тепер `using-the-cli.md`.
- **Дописи «What's new in libvips»** лежать у гілці `gh-pages` репозиторію libvips, з якої збирається сайт
  libvips.org. Це найдокладніший опис того, що принесла кожна лінія 8.5–8.18. Версії ці дописи не несуть: лінію
  названо в заголовку.
- **Документація pyvips.** Сторінку класу `Image` у репозиторії pyvips згенеровано з опису операцій libvips: кожен
  метод записано директивою Sphinx. Читач `ghdocs-history-pydomain` робить кожен метод розділом. Методи, написані
  руками (`new_from_file`, `write_to_buffer`, `new_from_array`), описано рядками документації в коді пакета, тому
  взято й файли `pyvips/*.py`.
- **Релізи sharp-libvips.** Кожен реліз несе таблицю «бібліотека — версія»: libvips, libheif, libwebp, mozjpeg,
  librsvg, libtiff та інші. Це відповідь на питання, яку версію кодека вкладено в готову збірку sharp.

## Межі, про які треба пам'ятати

- Довідник libvips узято з коментарів у коді, а не з сайту, тому його сторінки ведуть на файл коду в GitHub, а не на
  сторінку функції на libvips.org.
- У довіднику libvips ліній 8.17 і 8.18 текст називає інші функції так, як їх пише gi-docgen: «`Image.shrink()`»
  замість «vips_shrink()». Назва розділу — завжди ім'я C. У лініях до 8.16 і текст називає функції іменами C.
- Функція libvips потрапляє в довідник, лише коли над нею стоїть коментар gtk-doc. Параметри операцій, оголошені в
  коді макросами `VIPS_ARG_*`, сюди не входять: у довіднику вони є тою мірою, якою їх перелічує коментар функції.
- Записи файла `ChangeLog` до версії 7.9.1 не мають номера версії, тому всі вони лежать в одному документі цієї
  версії.
- Дописи «What's new in libvips» і сторінка встановлення libvips не мають версії, тому пошук із параметром `version`
  їх не бачить.
- Документації sharp ліній до 0.11 окремими сторінками не було: для них є README з повним описом API.
- Журнал змін sharp починається з версії 0.10.0.
- Сторінки документації sharp ведуть на адреси сайту sharp.pixelplumbing.com, тобто на найновішу версію сторінки, а не
  на версію документа; так само посібник libvips веде на `libvips.org/API/current`.
- Передрелізи не беруться.
- Інших прив'язок libvips (ruby-vips, php-vips, NetVips, C++ API окремим довідником) тут немає. Формат SVG — у
  примірнику `svg`, оптимізація SVG — у `svgo`. Інших інструментів для зображень (ImageMagick, Pillow, OpenCV, jimp)
  немає ніде.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/sharp-corpus-2026-11-21.tar.gz` (тексти, паспорт і сховище сирого
`raw/`; перед видаленням текстів розпакований окремо й звірений із диском), копія —
`C:\Distr\sharp-corpus-2026-11-21.tar.gz` (`/mnt/c/Distr/…` з WSL), SHA-256 обох звірено. В історії git текстів немає
ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/sharp/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/sharp-corpus-РРРР-ММ-ДД.tar.gz -C instances/sharp corpus raw
find instances/sharp/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/sharp/raw
gzip -9 -c instances/sharp/index/passages.json > instances/sharp/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Новий архів копіюють у `C:\Distr` і звіряють за SHA-256 (`tools/mirror-archives.sh --apply`),
і лише тоді видаляють попередній з обох місць, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/sharp-corpus-2026-11-21.tar.gz -C instances/sharp
./df sharp smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/sharp/index/passages.json.gz`, далі
`./df sharp vectors` заллє колекцію Qdrant.

## Установка venv

Власний venv цьому примірнику не потрібен: `./df sharp …` бере спільне середовище з кореня репозиторію (`.venvs/cpu`
або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md, розділ «Спільне
середовище». Ключ для кроку `ask` і токен GitHub лежать у кореневому `.env`.

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df sharp sources --why    # перелік джерел і білий список
./df sharp refresh          # усе: близько 50 хвилин мережею, з них пів години — код libvips
./df sharp refresh libvips-news libvips-install   # два заморожені джерела називають окремо
./df sharp manifest         # оновити паспорт
./df sharp setup            # Qdrant чи пошук лише по словах
./df sharp vectors          # залити корпус у docs-sharp
./df sharp smoke            # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df sharp serve   # порт 8999
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8999/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user sharp-docs http://127.0.0.1:8999/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.
