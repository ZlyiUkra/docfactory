# Оновлення корпусу sharp

Історія npm (`npm-sharp`, `npm-sharp-libvips`), README версій (`sharp-readme`) та історія PyPI (`pypi-pyvips`) беруть
версії з опису пакета в реєстрі, тож новий реліз потрапляє туди сам. Релізи GitHub (`sharp-releases`,
`sharp-libvips-releases`, `libvips-releases`) читаються щоразу заново з API, журнал змін pyvips (`pyvips-changelog`) —
з основної гілки репозиторію. Передрелізи відсіюються.

Руками оголошено:

- **Документація і код на тегах** (`sharp-docs`, `sharp-types`, `libvips-api`, `libvips-guide`, `libvips-man`,
  `pyvips-docs`, `pyvips-code`): поле `tags` — об'єкт «тег → мітка версії з префіксом», від найновішого, по одному
  тегу на лінію. Коли в лінії виходить новий патч, тег лінії заміняють новішим; коли виходить нова лінія, дописують
  рядок нагорі. У sharp і libvips лінія — два числа (`0.35`, `8.18`), тег — три (`v0.35.5`, `v8.18.7`).
- **Журнал змін sharp** (`sharp-changelog`): адреса дерева теки `docs/src/content/docs/changelog` на тегу останнього
  релізу, файл на версію. Після нового релізу тег в адресі `url` і в полі `within` заміняють новим. Основну гілку не
  беруть: там уже лежить файл ще не випущеної версії.
- **Журнал змін libvips** (`libvips-changelog`): файл `ChangeLog` на закріпленому коміті основної гілки. Після нового
  релізу хеш коміту в `url`, `within` заміняють новим. Записи без дати на початку файла («date-tbd 8.19.0») — версії,
  що ще не вийшли; читач їх не бере, бо вони стоять перед першим заголовком із датою.
- **Старі макети** (`sharp-docs-old`, `libvips-guide-md`, `libvips-guide-docbook`) оголошено на тегах закритих ліній,
  і міняти їх не треба.
- **Дописи «What's new» і сторінка встановлення libvips** (`libvips-news`, `libvips-install`): гілка `gh-pages`
  репозиторію libvips на закріпленому коміті. Ці два джерела позначено `frozen`, тож `refresh` без назви їх не питає.
  Коли виходить нова лінія libvips, хеш коміту заміняють новим і називають обидва джерела в команді.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описано в README, розділ «Архівний режим».

## Вийшла нова версія sharp, libvips чи pyvips

```
./df sharp refresh sharp-docs sharp-changelog sharp-types sharp-releases   # приклад для sharp, після правки tags і url
./df sharp refresh --missing    # джерела, яких не названо, лише докачуються
./df sharp manifest
./df sharp vectors
./df sharp smoke
# Ctrl+C у терміналі з serve, і знову: ./df sharp serve
```

Для libvips названі джерела — `libvips-api libvips-guide libvips-man libvips-changelog libvips-releases`, а з новою
лінією ще й `libvips-news libvips-install`. Для pyvips — `pyvips-docs pyvips-code pyvips-changelog pypi-pyvips`.

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (файл коду з незмінними описами дописує нову версію в рядок `# версія:`).

Джерело `libvips-api` складає перелік довше за інші: щоб знати, в яких файлах коду є описи функцій, читач читає кожен
файл уже під час складання переліку. Перший прогін звертається по кожен неповторний файл усіх ліній, наступні питають
сервер умовним запитом і беруть незмінне зі сховища сирого.

Ім'я файла містить початок хеша його вмісту, тому змінена сторінка лягає новим файлом поруч зі старим. Після заміни
тегу в `tags` файли, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш ніж запускати
`manifest`: інакше в корпусі лишиться редакція патча, якого в `tags` уже немає.

Якщо вийшла нова лінія:

- у `prompts/search.txt` (абзаци про `version` і «Which version to search first») та `prompts/agent.txt` замінити
  номер найновішої лінії, частки завантажень і перелік того, що змінив реліз; коли сайт sharp чи посібник libvips
  змінить розкладку файлів, додати правило в `slug_rewrite` файла `config.json`, щоб нові імена сторінок зводилися до
  старих;
- у таблиці «Пакети й версії» README оновити версію й частки завантажень;
- у `checks.json`, у десятці `quality_model`, замінити мітку лінії й звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторіїв і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального
довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей): `./df sharp quality --show`, порівняння обох
десяток з попереднім результатом, розбір промахів, правка промптів чи цілей. Головна мета — «як модель» 10 із 10.
