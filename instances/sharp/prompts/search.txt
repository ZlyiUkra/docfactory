Search the documentation of sharp, libvips and pyvips and return the matching excerpts with the versions each one
belongs to. sharp is the Node.js image processing module (the npm package sharp): it resizes, converts and composites
JPEG, PNG, WebP, AVIF, GIF, TIFF and SVG images. libvips is the C library that does the work underneath it, with the
command line tools vips and vipsthumbnail. pyvips is the Python binding of libvips.

What is here. sharp: the documentation of sharp.pixelplumbing.com as it stood at the last release of every line
0.11-0.35 -- the API reference (the constructor and its options, input and metadata, output and the options of every
format, resizing, compositing, image operations, colour, channels, utilities), installation and performance; the
change log, one entry per release since 0.10.0; the TypeScript declarations lib/index.d.ts of the lines 0.32-0.35 with
the exact option types (ResizeOptions, JpegOptions, WebpOptions, AvifOptions, Metadata, OutputInfo); the README of
every stable release; the npm history; the GitHub release notes; and the releases of sharp-libvips, each with a table
of the libvips version and of every dependency (libheif, libwebp, mozjpeg, librsvg, libtiff ...) bundled in the
prebuilt @img/sharp-libvips-* packages. libvips: the C API reference of every line 8.1-8.18, taken from the
documentation comments in the source code -- a section per function, type, enum and macro (vips_resize,
vips_thumbnail, vips_jpegsave, vips_image_new_from_file, VipsKernel, VipsInterpretation) with the declaration, the
parameters, the optional arguments and the description; the guide of the lines 8.1-8.18 (the vips command line,
vipsthumbnail, using libvips from C, threads, multipage and animated images, image pyramids, UltraHDR, how libvips
works and how it opens files, the function list, the file format, extending and binding); the man pages; the
ChangeLog; the GitHub release notes; the "What's new in libvips" posts for 8.5-8.18; and the install page. pyvips: the
documentation of the lines 2.0-3.2 (the introduction and the Image class with a section per method), the
docstrings of the package code, the examples, the change log and the PyPI history with the README.

Call this when a question is about processing images with sharp in Node.js, with libvips from C or from the command
line, or with pyvips in Python: how to resize, crop, rotate, flip, blur, sharpen or composite an image; how to convert
between formats and which options a format takes (quality, lossless, effort, chroma subsampling, progressive, bit
depth); how to read or keep metadata, EXIF and ICC profiles; how to work with animated and multipage images; how to
use streams and buffers; how to install sharp on a platform, in Docker, on AWS Lambda or with WebAssembly; how to tune
concurrency, the cache and memory use; why an operation behaves as it does underneath -- and history: since which
version a method, option or operation exists, what a release changed, which libvips a sharp release carries. Example
query: "resize fit cover position withoutEnlargement".

Do not call this for the image file formats themselves (the SVG specification is in the svg-docs server), for SVG
optimisation (svgo-docs), for other image tools (ImageMagick, Pillow, OpenCV, jimp), for the other language bindings
of libvips (ruby-vips, php-vips, NetVips, the C++ API) or for Node.js, Python and C themselves: their documentation is
not here, and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line of one product. Each product carries its own numbering behind a
prefix: "sharp-0.35", "sharp-0.34", "sharp-0.33", "libvips-8.18", "libvips-8.17", "libvips-8.15", "pyvips-3.2",
"pyvips-2.2", "sharp-libvips-1.3". A longer value narrows further ("sharp-0.35.5", "libvips-8.18.7"). Leave it empty
to search every version at once. Every excerpt comes back with `versions`: each version whose documents contain this
exact text, newest first. The "What's new in libvips" posts and the install page carry no version and are found only
by a search without `version`.

Which version to search first. When the user names no version, answer for the newest line and say which one: sharp
0.35, libvips 8.18, pyvips 3.2. In the week before 21 November 2026 the line 0.35 had 75% of the npm downloads of
sharp, 0.34 had 18.5% and 0.33 had 4.7%, so when an answer differs between 0.35 and 0.34, give both. Things that
changed and are worth checking before an answer: 0.35.0 requires Node.js >= 20.9.0, removed the `install` script, the
`failOnError` option and `paletteBitDepth`, and renamed `format.jp2k` to `format.jp2`; 0.34.0 added `autoOrient` and
accepts an array of input images to join or animate; 0.33.0 moved the prebuilt binaries into npm packages
(@img/sharp-*) installed by the package manager, requires Node.js ^18.17.0 or >= 20.3.0 and partially deprecated
`withMetadata()` in favour of `withExif()` and `withIccProfile()`; 0.32.0 began to ship its own TypeScript
definitions, replacing @types/sharp; `failOn` replaced `failOnError` in 0.30.4. Each sharp release carries one
libvips version, named in its change log entry: 0.35.0 upgraded to libvips 8.18.3, 0.34.3-0.34.5 to 8.17.1-8.17.3,
0.33.2-0.33.5 to 8.15.1-8.15.3, 0.32.4-0.32.6 to 8.14.3-8.14.5. Search the libvips reference of that line when the
question is about what happens underneath.

How the three name the same thing. One libvips operation has three spellings: the C function `vips_resize()`, the
command `vips resize` and the pyvips method `Image.resize()`; sharp wraps several operations behind one method
and names its options differently. In the libvips reference of 8.17 and 8.18 the text refers to
other functions as `Image.shrink()`; the section title is always the C name, "vips_shrink()".

How the text is laid out. Documents are named by source: sharp-docs (a page per group of methods; a section per
method, titled with its name -- "resize", "jpeg", "composite"), sharp-changelog, sharp-types, sharp-readme, npm-sharp,
sharp-release, sharp-libvips-release, libvips (one document per source file; a section per documented function or
type), libvips-doc (the guide), libvips-man, libvips-changelog, libvips-release, pyvips-doc, pyvips (code and
examples), pyvips-changelog, pypi-pyvips.

Write the query in English, with the names the libraries use ("resize fit cover withoutEnlargement", "jpeg quality
mozjpeg progressive", "webp lossless effort", "avif quality chromaSubsampling", "composite blend gravity", "metadata
orientation exif", "withMetadata keepIccProfile", "sharp.cache concurrency", "vips_thumbnail", "vips_jpegsave Q
optimize_coding", "vipsthumbnail --size", "Image.new_from_file access sequential", "Image.thumbnail"), not in the
user's own words. Everything here is English -- the excerpts, the word index and the meaning index alike -- and the
word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the question
into the terms of the libraries first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a method, option or
operation, answer point by point: since which version it exists; what changed in later versions; what prompted the
change, if the excerpts say so; and how it stands in the current version. Every point names the product, the version
and the document it rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set
of documents "корпус" -- say "документація sharp, libvips і pyvips". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back, not
out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass
the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.
