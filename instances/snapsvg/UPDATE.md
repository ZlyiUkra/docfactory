# Оновлення корпусу snapsvg

Snap.svg не має нових релізів з лютого 2017 року, тому оновлювати тут майже нічого: реєстр npm (`npm-*`) і README
`snapsvg-cjs` читаються з реєстру щоразу заново, а журнал змін (`changelog`) — з гілки `master`. Якщо проєкт таки
випустить нову версію, руками оголошують таке:

- **Довідник і README** (`api`, `readme`): поле `tags` — об'єкт «тег → версія», від найновішого. Новий тег
  дописують першим рядком в обох джерелах. Файл довідника — `doc/reference.html`; якщо він переїхав, новий шлях
  додають у `files`.
- **Демонстрації** (`demos`): поле `tags` тримає один тег останньої версії; його замінюють.
- **Сайт** (`site`): поле `tags` — «SHA коміту → версія». Репозиторій `adobe-webplatform/snapsvg-site` тегів не
  має, тому беруть SHA найновішого коміту (`git ls-remote https://github.com/adobe-webplatform/snapsvg-site master`)
  і версію, що вийшла на той день.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df snapsvg refresh api readme demos changelog npm-snapsvg   # після правки sources.json
./df snapsvg refresh --missing    # джерела, яких не названо, лише докачуються
./df snapsvg manifest
./df snapsvg vectors
./df snapsvg smoke
# Ctrl+C у терміналі з serve, і знову: ./df snapsvg serve
```

Ім'я файла довідника містить початок хеша його вмісту, тому довідник нового тегу лягає новим файлом поруч зі
старими. Сховище сирого `raw/` повертається з архіву разом із текстами, тож після правки читача тексти
перебудовуються без мережі: `./df snapsvg build <id>`.

Після нової версії:

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` замінити версію за
  замовчуванням і дату останнього релізу;
- у `checks.json`, у десятці `quality_model`, замінити `"0.5"` і звірити цілі: ціль — це розділ довідника
  (`api-reference#element-attr`), і з новою сигнатурою методу його ключ зміниться.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторію: без нього API GitHub дає 60
звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df snapsvg quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
