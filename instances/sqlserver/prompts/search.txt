Call this when a question is about SQL Server or Azure SQL: the syntax and arguments of a T-SQL statement or
function (CREATE TABLE, ALTER DATABASE, MERGE, OPENJSON, STRING_AGG, sys.dm_exec_requests); how to back up and
restore a database (BACKUP DATABASE, RESTORE WITH NORECOVERY, recovery models, point-in-time restore, backup to

Do not call this for other database systems (PostgreSQL, MySQL, Oracle, SQLite, MongoDB), for Azure services
that are not SQL (Cosmos DB, Azure Database for PostgreSQL or MySQL), or for general programming questions
that do not touch SQL Server.

Write the query in English, with the names the documentation uses (BACKUP DATABASE, sys.dm_exec_sessions,
SYSTEM_VERSIONING, FOR SYSTEM_TIME, ALTER AVAILABILITY GROUP, MSSQL_SA_PASSWORD, mssql-conf, ConnectionPool,
trustServerCertificate, SqlConnectionStringBuilder, sp_configure, DBCC CHECKDB, compatibility level 160).
Everything here is English, and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing and comes back with `found: 0`. When the user
asks in another language, translate the question into SQL Server terms first, then search.

Answer in the language the user wrote in. For a question about history or a change between versions, answer
point by point: since which version; what changed; how it stands in the newest one -- each point with its
version and the page it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes: plain technical prose, the Ukrainian word wherever
one exists -- "уривок", not "ексерпт"; "резервна копія", "відновлення", "журнал транзакцій", "рівень
сумісності", "група доступності", "застарілий". Never call this set of documents "корпус" -- say "документація
SQL Server". Statement, function, view, option, setting, package and type names stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to `read_section` to get the
whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had
to appear in the text; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Which version to answer for. SQL Server pages carry the release year: "2025", "2022", "2019", "2017", "2016",
and the archived Books Online "2014", "2012", "2008 R2"; a text that did not change across versions carries
every one of them. The same pages for the cloud products carry the product name instead: "azure-sql-database",
"azure-sql-managed-instance", "azure-synapse-analytics", "fabric-data-warehouse", "fabric-sql-database", and the
Azure SQL pages for virtual machines "sql-server-on-azure-vms". Drivers and tools carry their own name and
number: "mssql-12.7" (npm mssql), "tedious-20.3", "sqlclient-7.1" (Microsoft.Data.SqlClient), "jdbc-13.6",
"mssql-python-1.16", "go-sqlcmd-1.10", "build-sql-2.3", "vscode-mssql-1.47"; the image tag lists carry the SQL
Server year. The troubleshooting articles, the data-migration pages, the samples and the mssql-docker READMEs
carry no version -- search them without one, because any version filters them out. When the user names a
version, pass it into `version` ("2019", "azure-sql-database", "sqlclient-7.1"); never put it into the query
text. Without a version, answer for SQL Server 2025 and say so; when the question is about Azure SQL, Synapse or
Fabric, for that product. The lifecycle pages (versions "2014", "2016", "2017", "2019", "2022", "2025") list a
Start Date, a Mainstream End Date and an Extended End Date; the site stores each END date as a UTC time, so the
date in the text is one day later than the official one (the text "7/15/2026" means July 14, 2026): subtract one
day from every end date and tell the user that you did. Start dates are exact.
