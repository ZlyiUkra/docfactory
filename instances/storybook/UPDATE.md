# Оновлення корпусу storybook

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи Storybook, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версія сторінок — це гілка.** Джерело `storybook-docs` бере теку `docs/` репозиторію
storybookjs/storybook з п'яти гілок, оголошених у полі `refs` («гілка → версія»): `main` — поточна лінія 10.x,
`release-9-1`, `release-8-6`, `release-7-6`, `release-6-5` — остання мінорна кожної старшої лінії. Нова мінорна чи
мажорна версія сама в корпус не потрапляє: її мітку й гілку дописують руками (крок 1). Журнали змін, посібник з
переходу MIGRATION.md, рецепти й реєстр npm читаються з `main` і сайту цілком — вони підтягують нове самі.

Друге правило: **нова версія змінює й старі документи.** Однаковий текст сторінки в кількох версіях лежить у корпусі
одним фрагментом із переліком усіх версій. Тож після оновлення корпус перезаписують цілком (`refresh` без
`--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Мітка поточної лінії.** У `refs` джерела `storybook-docs` гілка `main` має мітку поточної мінорної
(`"main": "10.6"`). Вийшла 10.7 — мітку міняють на `"10.7"`. Номер — з `code/package.json` гілки `main` або з мітки
`latest` реєстру npm:

```
curl -s https://registry.npmjs.org/storybook | python3 -c "import json,sys; print(json.load(sys.stdin)['dist-tags'])"
```

**Крок 2. Якщо вийшла нова мажорна лінія** (11.0):

- гілку попередньої лінії дописати в `refs` з міткою її останньої мінорної: `"release-10-6": "10.6"` (ім'я гілки —
  у переліку гілок репозиторію, `release-<мажорна>-<мінорна>`), а `main` — з міткою нової: `"main": "11.0"`;
- у полі `site` гілці `main` дати шаблон нової лінії (`https://storybook.js.org/docs/11/{path}`), а нову гілку
  попередньої лінії — з її номером (`…/docs/10/{path}`). Лінію, яку сайт перестав віддавати (зараз це 6.5 і 7.6),
  з `site` прибирають: тоді адресою стає файл на GitHub;
- журнал змін нової лінії: якщо його винесли в окремий файл (як `CHANGELOG.v6.md`), дописати джерело `changelog-v`
  на цей файл; поле `skip` у джерелі `storybook-releases` перелічує латки, яких немає в жодному журналі, — нові
  такі латки дописати туди;
- у промптах замінити поточну лінію: `prompts/search.txt` (абзаци «Which version to search first» і «Every answer
  says which version it is for») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "10"`;
- лінію за замовчуванням вибирають за завантаженнями з npm за тиждень, а не за номером: поки 10.x завантажують більше,
  вона лишається основною;
- у `checks.json`, у десятці `quality_model`, замінити `"10"` на нову лінію там, де питання про поточну поведінку.

**Крок 3. Завантажити.**

```
./df storybook sources --why
./df storybook refresh        # ~30 хвилин: сторінки п'яти гілок і кожен файл прикладу
./df storybook manifest
./df storybook vectors
./df storybook smoke
./df storybook quality
# Ctrl+C у терміналі з serve, і знову: ./df storybook serve
```

Перші ~5 хвилин `refresh` журнал мовчить: читач проходить дерева п'яти гілок і читає кожну сторінку, щоб відкинути
чернетки (`draft: true`) і сторінки розділів без тексту. Приклади коду тягнуться вже під час запису — раз на вміст
файла, тож однаковий приклад кількох гілок завантажується один раз.

`smoke` порівнює число фрагментів з `expected_passages` у `checks.json`; після оновлення число зміниться — вписати
нове разом із датою в `expected_note`, а в README — у таблицю «Скільки цього». `quality` порівняти з попереднім
заміром (README): «як модель» має лишитися 10 із 10.

**Крок 4. Винести тексти в архів** — як у README, розділ «Архівний режим»: новий архів під новою датою, звірка з
диском, видалення текстів і попереднього архіву, нове ім'я архіву в README.

## 2. Збирання з нуля

На новій машині чи після втрати корпусу:

```
cd instances/storybook
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # GITHUB_TOKEN бажаний: дерева п'яти гілок і релізи — звернення до API
cd ../..
./df storybook refresh        # ~30 хвилин
./df storybook manifest
./df storybook setup
./df storybook vectors        # ~20 хвилин
./df storybook smoke
```

Сирі файли йдуть з `raw.githubusercontent.com` і ліміту API не витрачають; токен потрібен деревам гілок (по одному
рекурсивному зверненню на гілку) і переліку релізів.
