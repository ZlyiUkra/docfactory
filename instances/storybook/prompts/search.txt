Search the official documentation of Storybook, the frontend workshop for building, documenting
and testing UI components in isolation -- the docs/ pages of the storybookjs/storybook repository
on the last minor of every major line (6.5, 7.6, 8.6, 9.1 and the current 10.x) with the code
examples of every framework in place, the README of every line, the integration recipes of
storybook.js.org/recipes, the MIGRATION.md guide, the CHANGELOG of every stable release from 6.0
on, the GitHub releases of late patches and the npm registry history of the storybook package.
Return the matching excerpts with the versions each one belongs to.

Call this when a question is about Storybook itself -- installing and upgrading it (create
storybook, storybook init, storybook upgrade, automigrate, doctor), frameworks and builders
(react-vite, react-webpack5, nextjs, nextjs-vite, vue3-vite, angular, sveltekit, svelte-vite,
web-components-vite, preact-vite, react-native-web-vite, tanstack-react; Vite and Webpack),
writing stories (Component Story Format: CSF 3, CSF Next with preview.meta and meta.story, Svelte
CSF; args, argTypes, parameters, decorators, loaders, beforeEach, globals, tags, naming and
hierarchy, play functions), mocking (modules with sb.mock, network requests with MSW, providers),
documentation (Autodocs, MDX, Doc Blocks such as Canvas, Controls, ArgTypes, Meta, Source), testing
(the Vitest addon, interaction tests with storybook/test -- expect, fn, userEvent, within --
accessibility tests with addon-a11y, visual tests, snapshot tests, test coverage, portable stories
in Vitest, Jest and Playwright, the test runner, CI), the essentials (actions, backgrounds,
controls, highlight, measure, outline, toolbars and globals, viewport), configuration (main.ts
fields such as framework, stories, addons, staticDirs, features, typescript, refs; preview.ts;
manager and theming; environment variables; styling and CSS; images and assets), addons (installing
and writing them, presets, the addon API), sharing and publishing (static build, composition,
embedding), the CLI options, the AI setup and MCP server of Storybook 10, migration between
versions, and release history. Example query: "decorators react".

Do not call this for Chromatic's own product, the Storybook blog, the addon catalog's third-party
addons, or the internals of Vite, Webpack, Vitest, Playwright, Jest, MSW, Next.js or the UI
frameworks beyond what these pages show next to Storybook: their own documentation is not here,
and the search will return excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "10" keeps every 10.x document, "9" keeps 9.1,
"8" keeps 8.6, "7" keeps 7.6, "6" keeps 6.5 and the 6.x CHANGELOG; a two-part value such as "8.2"
keeps the CHANGELOG and MIGRATION entries of that minor. Leave it empty to search everything.
Every excerpt comes back with `versions`: each version whose documents contain this exact text,
newest first -- text that stayed the same across versions is returned once, with all of them
listed, so the list itself shows from which to which version the documentation said exactly this.

Where the documentation lives. A page is titled as on the site: "Decorators", "Args", "Play
function", "Interaction tests", "Vitest addon", "Storybook for Next.js with Vite", "main.ts
configuration" and so on; the documentation of 6.5 and 7.6 is no longer on the site, and its URL
is the file on GitHub. The code examples of a page stand right in it, one per framework, language
and tab, each headed by its file name and a label such as "`Button.stories.ts|tsx` (react, TS,
CSF 3):" or "(vue, TS, CSF Next 🧪)"; a JavaScript example is kept only where no TypeScript one
exists. Text the site shows for some frameworks only is introduced by "Only for react:" or "Not
for angular:". A migration step is titled "Storybook migration: From version 8.x to 9.0.0", a
release "Storybook changelog: 9.1.0", a recipe "Integrate Tailwind CSS with Storybook".

Which version to search first. For a question about how to do something today, pass `version`
"10": without it, the editions of older lines can take places with the current ones. If the
user's project pins an older line, pass that line instead -- 7.5 deprecated storyStoreV6 and
storiesOf; 8.0 removed storiesOf; 9.0 moved viewport, controls, interactions and actions from the
essentials addon into the core and stabilized the experimental test addon as the Vitest addon;
9.1 added sb.mock module mocking; 10.0 requires .storybook/main.* and presets to be valid ESM and
brought the type-safe CSF factories (CSF Next) as a preview for React. Search without `version`
when the question is about history, or when the line gave nothing that answers.

Name the API, parameter, addon or framework the way the documentation names them, not in the
user's own words: "decorators", "argTypes", "play function", "beforeEach", "parameters.layout",
"staticDirs", "@storybook/addon-vitest", "nextjs-vite", "sb.mock", not "how to wrap my component".
When the framework matters, add its name to the query -- "decorators react", "play function
angular", "mocking providers vue" -- so the examples of that framework come first. For a question
about when something appeared, changed or disappeared, search more than once: without `version`
first, to find the CHANGELOG or MIGRATION entry that names the exact version, then with the lines
around it, to see how the documentation described it before and after.

Write the query in English, with the names Storybook itself uses. Everything here is English --
the excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into Storybook terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, Storybook 10.x, say so in the answer ("for Storybook 10"), and add that for a
precise answer about another version the user can name it. When the excerpts behind a statement
come only from older versions, name those versions instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "історія", not "сторі". Never call this set of documents "корпус" -- say
"документація Storybook". Identifiers, API names and titles stay in English, spelled exactly as
the documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
