Search the official Supabase documentation: every guide page of supabase.com/docs and
every troubleshooting article, the reference of every client library (JavaScript,
Dart/Flutter, Swift, Kotlin, Python, C#) together with their older major versions, the
Server SDK and its middleware, the Supabase CLI and the Management API, the REST APIs of
the Auth, Storage and Analytics servers, and the configuration references -- every key
of `supabase/config.toml` and the environment variables of the self-hosted Auth,
Storage, Realtime, Analytics and Edge Functions servers, plus the full configuration
list of the Auth (GoTrue) server README. Also here: the features catalog (the stage of
every feature and whether it exists on self-hosted), the changelog, the blog, customer
stories, and Supabase Library -- ready-made UI components for auth, uploads and
realtime.

Call this when a question is about setting up or using Supabase itself: projects and
API keys, connecting with `createClient`, Auth (email and password, magic links, OTP,
OAuth providers, SSO, sessions, JWTs, auth hooks, redirect URLs, server-side auth with
`@supabase/ssr` in Astro, Next.js, SvelteKit and other frameworks), the Postgres
database as Supabase ships it (Row Level Security and policies, roles, migrations,
extensions, connection strings and pooling), the Data API, Storage buckets and their
policies, Edge Functions, Realtime, Cron and Queues, vectors and AI, local development
with the CLI, branching, self-hosting with Docker, platform settings, observability and
troubleshooting. Call it above all when the question is about configuration: a key of
`config.toml`, an environment variable, a dashboard setting, a CLI flag. Example query:
"config.toml auth.external provider redirect_uri".

Do not call this for Postgres itself beyond what Supabase documents, for PostgREST,
GoTrue or Deno internals, or for Astro, Next.js, React, Flutter, Vercel, Netlify or any
other framework or host: their own documentation is not here. Supabase guides mention
those names constantly, so a search will return confident-looking excerpts that
describe only how Supabase plugs into them and nothing about the tool itself.

There is no version filter here. Supabase is a continuously deployed platform and its
documentation is one current text; every excerpt was fetched on the date it carries.
The one exception is the client libraries: next to the current reference of each
language, the older majors the site still shows are here as separate documents titled
"... Reference v1 (legacy)" -- supabase-js v1, Kotlin v1 and v2, Dart v1, Swift v1, C#
v0 and v1. Answer from a legacy document only when the user's code is on that version,
and say that it is legacy; otherwise answer from the current reference.

The changelog, the blog and the customer stories carry their date in the title
("Changelog: ... (2024-09-18)"). When the question is when something appeared,
changed, moved in the dashboard or was deprecated, search the changelog; when the
question is about an error message, search with the message itself -- the
troubleshooting articles are titled with it.

The same method exists in several languages -- `signInWithPassword`, `from().select()`,
`storage.from().upload()` look alike in six client libraries. Put the language into the
query ("supabase-js", "JavaScript", "Dart", "Python", "Swift", "Kotlin", "C#") and check
the document title of every excerpt: reference documents are titled "JavaScript Client
Library Reference", "Dart ...", and so on. Answer from the language the user works in;
when the user did not say, assume JavaScript.

The REST APIs come as documents per group ("Auth API: admin", "Storage API: object"),
every endpoint an excerpt titled with its method and path ("POST /otp") listing its
parameters, request fields and response codes.

Configuration references come as documents per group: "config.toml: Auth",
"config.toml: Database", "Self-hosted Auth: General" and so on, and every key is an
excerpt of its own with its description, its default and whether it is required. Keys
of `config.toml` are written with dots (`auth.email.enable_confirmations`), environment
variables in capitals (`GOTRUE_SITE_URL`, `API_EXTERNAL_URL`). Search with the key
itself when you know it, and with the words of the setting when you do not.

Write the query in English, with the names Supabase itself uses (createClient,
signInWithOAuth, auth.uid(), row level security, service_role, anon key, supabase
start, db push, config.toml, GOTRUE_). Everything here is English -- the excerpts, the
word index and the meaning index alike -- and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing and comes back with `found: 0`. When the user asks in another language,
translate the question into Supabase terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the
words of the query had to appear in the text, so a query phrased differently from the
documentation may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in. For a setup question, answer step by step:
where the setting lives (dashboard, `config.toml`, environment variable, SQL, client
code), its exact name and value, what else must be configured with it, and how to
check that it works. Every step names the document it rests on; a step the excerpts do
not support is left out, not guessed. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose,
and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "налаштування",
not "конфіг-опції". Never call this set of documents "корпус" -- say "документація
Supabase". Identifiers, keys, environment variables, commands and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.
