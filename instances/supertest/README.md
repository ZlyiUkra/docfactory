# supertest — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про пакет npm `supertest` (перевірка HTTP-серверів Node.js зручним
ланцюжком викликів поверх superagent, репозиторій forwardemail/supertest) — за документацією усіх його стабільних версій:
README кожної версії, History.md ранніх версій, нотатки релізів GitHub та історія версій у реєстрі npm.
Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний
устрій фабрики — у [../../README.md](../../README.md).

## Навіщо окремий примірник

`supertest` — стандартний спосіб перевірити API без запуску справжнього сервера на порту: `request(app).get('/users')
.expect(200)` підіймає застосунок на тимчасовому порту й перевіряє відповідь. У NestJS він стоїть у документації
розділу Testing (наскрізні тести), а в плані NestJS — у фазі тестів. Пакет має довгу історію, і вона записана в трьох
місцях: History.md у репозиторії (до 3.4.1), нотатки релізів GitHub (з 1.2.0) і реєстр npm. Репозиторій тричі змінював
власника (visionmedia → ladjs → forwardemail), через що старі нотатки посилаються на старі адреси. У версії 7.2.0
з'явилися перевірки cookies, у 6.3.0 — підтримка HTTP/2, у 7.0.0 відкинуто Node.js до 14.16 (тепер `engines` вимагає
14.18), а залежність superagent за цей час змінилася від 0.21 до 10. Усе це — в одному місці й з номером версії біля
кожного уривка.

Офіційного сайту в пакета немає: поле `homepage` у npm веде на репозиторій GitHub (заголовок README посилається на сайт
superagent — це інший пакет). Тому примірник складається з пакета npm і репозиторію.

v3.4.2 (його запис про 3.4.2 порожній, найновіший запис — 3.4.1). Чому немає релізів 1.0.0, 1.0.1 і 1.1.0: на GitHub вони

джерелом `ghcode-history`, як у примірнику `passport`.

Запит про «з якої версії є перевірки cookies» вважає відповіддю і реліз 7.2.0 («feat(cookies): add cookie
assertions»), і розділ README «Cookies»: його поле `versions` починається з 7.2.0.

## Що в цій теці

- `corpus/` — паспорт `index.json`, тобто опис копії: адреса, дата завантаження й сума тексту кожного документа.
  Самих текстів тут немає: корпус в архіві (розділ «Архівний режим» нижче).
- `index/` — кеш фрагментів, з якого сервер підіймається: у git — стиснений `passages.json.gz`, розпакований
  `passages.json` лежить поруч і в git не потрапляє.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями, правила `redact` і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.mcp.json` — запис HTTP-сервера для Claude Code. `ANTHROPIC_API_KEY` (лише для кроку `ask`) і `GITHUB_TOKEN` (лише для
  завантаження корпусу) беруться з кореневого `.env`.

Кроки нижче запускаються з кореня фабрики (`docfactory/`) через `./df supertest <крок>`.

## Версії

Версія — номер випуску. Фільтр `version` бере мажор (`"7"`), мінор (`"7.2"`, `"0.15"`) або точну версію (`"7.2.2"`). Без
названої версії промпт велить шукати для лінії 7 — на неї за тиждень до 20.10.2026 припадало близько 77 % завантажень
(7.2.2 — 44 %, 7.3.1 — 14 %, 7.1.4 — 7 %), а на лінію 6 близько 20 % (6.3.4 — 13 %); де 6.x відрізняється (Node.js
старіший за 14.18, старіший superagent, немає перевірок cookies), модель згадує й її. Вимога до Node.js (поле `engines`)
записана в документах реєстру: 7.x — `>=14.18.0`, 6.x — `>=6.4.0`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/supertest-corpus-2026-10-20.tar.gz` (125 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском). В історії git текстів немає ніде.
Архів лежить лише на цій машині. Сховище `raw/` після звірки теж видалено з диска.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/supertest/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/supertest-corpus-РРРР-ММ-ДД.tar.gz -C instances/supertest corpus raw
find instances/supertest/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/supertest/raw
gzip -9 -c instances/supertest/index/passages.json > instances/supertest/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Тоді ж видаляють попередній архів, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/supertest-corpus-2026-10-20.tar.gz -C instances/supertest
./df supertest smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/supertest/index/passages.json.gz`,
далі `./df supertest vectors` заллє колекцію Qdrant (близько секунди на відеокарті, хвилина на процесорі).

## Установка venv

Власний venv цьому примірнику не потрібен: `./df supertest …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище».

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df supertest sources --why   # перелік джерел і білий список
./df supertest refresh         # завантажити все задеклароване (близько хвилини)
./df supertest manifest        # оновити паспорт
./df supertest setup           # Qdrant чи пошук лише по словах
./df supertest vectors         # залити корпус у docs-supertest
./df supertest smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df supertest serve          # порт 8876
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8876/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user supertest-docs http://127.0.0.1:8876/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `supertest-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
