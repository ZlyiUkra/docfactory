Search the supertest documentation -- the README of every stable version of the npm package `supertest`
(testing of Node.js HTTP servers with a fluent API on top of superagent, now maintained by Forward Email), the
History.md of its early versions, the GitHub release notes of later ones and the npm registry history of the
package -- and return the matching excerpts with the versions each one belongs to.

Call this when a question is about supertest as it describes itself -- request(app) and request(url), the methods
.get(), .post(), .put(), .patch(), .delete(), the assertions .expect(status), .expect(body), .expect(field, value),
.expect(function) and .end(fn), the request methods inherited from superagent (.set(), .send(), .query(), .field(),
.attach(), .auth(), .type(), .accept(), .buffer(), .parse(), .redirects()), promises and async/await instead of
callbacks, request.agent(app) with persistent cookies, the cookie assertions (.cookies, .set, .reset, .new, .renew,
.contain, .not -- added in 7.2.0), how a server is started on an ephemeral port, HTTP/2 support, HTTPS and
certificates, error stack traces of failed assertions, and the requirements on the Node.js version -- and above all
history and compatibility: since which version a method or option exists, what changed between versions, which
version of superagent stands behind a release, which versions require which Node.js (the `engines` field of every
version is written in the npm registry documents), and when every version came out. The dependencies of every
version (superagent, methods, cookie-signature) are written in the registry documents too.

Do not call this for superagent itself (its own API, its browser build), for Jest, Mocha, Vitest, Express, NestJS
or any test framework or web framework, for the `@types/supertest` typings, nor for HTTP mocking libraries such as
nock or msw: their documentation is not here, and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line. The package is numbered 0.x to 7.x: the lines are 0.0 to 0.15
(minor numbers), then 1, 2, 3, 4, 5, 6 and 7 (77 stable versions, 0.0.1 to 7.3.1). A line of one number keeps every
document of that major ("7" keeps 7.0.0 to 7.3.1, "6" keeps 6.0.0 to 6.3.4), two numbers keep a minor ("7.2" or
"0.15"), three an exact version ("7.2.2"). The versions 5.0.0-0 and 5.0.0-1 are not stable releases: only the
registry lists them. The History.md of the repository ends at 3.4.1; releases 1.0.0, 1.0.1 and 1.1.0 have no notes.
Leave `version` empty to search everything, including text that carries no version. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- text that stayed the same across
versions is returned once, with all of them listed, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names the documentation itself uses ("expect", "agent", "cookies", "set",
"send", "end", "attach", "field"), not in the user's own words. Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When the
user asks in another language, translate the question into the terms of the documentation first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the excerpts say
so; and how it stands in the current version. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer
writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "перевірка", "запит", "застарілий". Never call this set of documents "корпус" -- say
"документація supertest". Identifiers, method names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional, see
above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated: true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to appear
in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words" means a second,
meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. By weekly downloads the line 7 leads with about 77 % (7.2.2 about 44 %, 7.3.1 about
14 %, 7.1.4 about 7 %), and the line 6 follows with about 20 % (6.3.4 about 13 %). Pass `version` "7" for how things
are done today, and mention 6.x when it differs (Node.js older than 14.18, an older superagent, no cookie assertions).
Search without `version` when the question is about history, or when the line gave nothing. Every answer says which
version it is for; when the excerpts behind a statement come only from older versions, name those versions instead of
presenting the text as current.
