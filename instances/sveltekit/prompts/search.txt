Search the SvelteKit documentation and return the matching excerpts with the versions each one belongs to. What
is here: the documentation and FAQ of SvelteKit (svelte.dev/docs/kit, repository sveltejs/kit) at the last release
of every minor line 1.0 to 3.1 -- routing, loading data, form actions, page options, state management, hooks,
errors, link options, service workers, server-only modules, adapters and deployment, configuration, the
reference of $app, $env and $lib modules and types, and the migration guides; the SvelteKit part of the
svelte.dev tutorial (Basic and Advanced SvelteKit, without a version); the documentation of Sapper, the
predecessor of SvelteKit, at the last release of every minor line; the changelogs of @sveltejs/kit, the adapters
(auto, node, static, vercel, netlify, cloudflare, bun), @sveltejs/package, @sveltejs/enhanced-img and Sapper; the
README of every stable version and the npm registry history (versions, dates, dist-tags, peer dependencies,
exports) of @sveltejs/kit, those adapters and packages, create-svelte and sapper.

Call this when a question is about SvelteKit: routes and files (+page.svelte, +page.js, +page.server.js,
+layout, +server.js, +error.svelte), load functions and their data, form actions and use:enhance, page options
(prerender, ssr, csr, trailingSlash), hooks (handle, handleFetch, handleError, reroute, init), errors and
redirects (error, redirect), $app/navigation (goto, invalidate, preloadData), $app/state and $app/stores,
$app/forms, $app/paths, $env/static and $env/dynamic, server-only modules, remote functions, snapshots, shallow
routing, service workers, svelte.config.js, adapters and deployment to Node, static hosting, Vercel, Netlify,
Cloudflare and Bun, packaging libraries with @sveltejs/package, images with @sveltejs/enhanced-img, migration
between SvelteKit majors and from Sapper; and Sapper itself -- and history: since which version a feature exists,
what changed in a release.

Do not call this for Svelte itself (runes, components, template syntax, transitions, stores, the compiler) or the
sv CLI -- they are in the svelte-docs server of the same family -- nor for Vite itself, other frameworks or
third-party libraries, or for TypeScript or JavaScript language questions: their documentation is not here, and
the search will return SvelteKit excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "2.70" keeps every 2.70.x document of @sveltejs/kit, "2" every
2.x, "3.1" the newest line; leave it empty to search everything. The other packages carry their own numbering
with a prefix, so they never mix with SvelteKit: "adapter-node-5", "adapter-vercel-6", "package-2",
"enhanced-img-0", "create-svelte-6", "sapper-0.29". Every excerpt comes back with `versions`: each version whose
documents contain this exact text, newest first, so the list itself shows from which to which version the
documentation said exactly this.

Write the query in English, with the names SvelteKit itself uses ("+page.server.js", "load", "form actions",
"handle", "goto", "$env/static/private", "adapter-node"), not in the user's own words. Everything here is English
-- the excerpts, the word index and the meaning index alike -- and the word index keeps only latin letters and
digits, so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all and comes
back with `found: 0`. When the user asks in another language, translate the question into SvelteKit terms
first, then search.

Answer in the language the user wrote in. When the question is about a feature's history or support, answer
point by point: since which version it exists; what changed in later versions; what prompted the change, if the
excerpts say so; and how it stands in the current version. Every point names the version and the document it
rests on; a point the excerpts do not support is left out, not guessed. When that language is Ukrainian, write
as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word
wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація SvelteKit". Identifiers, option names and titles stay in English,
spelled exactly as the documentation spells them. Build the answer out of the excerpts that came back, not out
of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. SvelteKit 2 carries most of the weekly downloads (2.70 alone about 40%), the
newest major 3 about 20% (3.1 14%, 3.0 6%). Search with `version` "2.70" for a question about how to do
something; when the user names SvelteKit 3 or the 3.x documentation differs for the feature asked about, search
"3.1" as well and answer for both, saying which is which. Search without `version` when the question is about
history, about an adapter or another package (their versions carry a prefix), about Sapper, about the tutorial
(no version), or when the line gave nothing. Every answer says which version it is for. When the excerpts behind
a statement come only from older versions, name those versions instead of presenting the text as current.
