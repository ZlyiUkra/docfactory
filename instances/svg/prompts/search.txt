Search the SVG specifications and return the matching excerpts with the editions each one belongs to. What is
here: Scalable Vector Graphics (SVG) 2 in two editions -- the W3C Candidate Recommendation Snapshot of 6 October
2026 and the current editor's draft --, one document per chapter: rendering model, basic data types and
interfaces, document structure (svg, g, defs, symbol, use, switch, title, desc), styling, geometry properties,
coordinate systems, transformations and units (viewBox, preserveAspectRatio), paths, basic shapes, text,
embedded content (image, foreignObject), painting (fill, stroke, markers, paint-order), paint servers
(gradients and patterns), scripting and interactivity (events, pointer-events, script), linking (href, a,
view), conformance, implementation notes (the arc conversion formulas), accessibility support, the attribute
index, the property index and the list of changes from SVG 1.1; SVG 1.1 (Second Edition), the W3C
Recommendation of 16 August 2011, with the chapters SVG 2 no longer has: Filter Effects, Clipping, Masking and
Compositing, Animation, Fonts, Color, Scripting, Metadata, Extensibility, Concepts, Backwards Compatibility; the
modules SVG 2 hands those subjects to, each as the latest W3C publication and as the editor's draft -- Filter
Effects Module Level 1, CSS Masking Module Level 1, Compositing and Blending Level 1, CSS Transforms Module
Level 1, Motion Path Module Level 1 --, and SVG Animations Level 2 (editor's draft only); the working group's
drafts SVG Strokes, SVG Markers, SVG Paths, SVG Integration, SVG Native and CSS Fill and Stroke Module Level 3;
and the accessibility specifications SVG Accessibility API Mappings 1.0 and the WAI-ARIA Graphics Module 1.0.

Call this when a question is about what the SVG format itself requires -- the rule, not a tutorial: what an
element is, where it may appear and which attributes it takes; the grammar and meaning of path data; how
viewBox and preserveAspectRatio map a drawing into its viewport; how units, percentages and bounding boxes are
computed; how fill, stroke, dashes, line joins, markers and paint-order work; how a use element builds its
shadow tree; how text is laid out, wrapped and placed on a path; how gradients and patterns are defined; which
element receives a pointer event; how presentation attributes interact with CSS; the IDL of an SVG DOM
interface; the filter primitives (feGaussianBlur, feColorMatrix, feComposite and the rest); clipPath and mask;
the transform attribute and transform functions; the animation elements animate, set, animateMotion and
animateTransform; how an SVG element is exposed to assistive technology -- and what changed between SVG 1.1
and SVG 2. Example query: "elliptical arc large-arc-flag sweep-flag".

Do not call this for which browser implements what and since when, or for tutorials -- that is in the mdn-docs
server --; for the libraries that draw or animate SVG (the svgjs-docs, snapsvg-docs, paperjs-docs, d3-docs
servers); for shrinking SVG files (svgo-docs); for HTML, DOM, Fetch or WAI-ARIA themselves (webstandards-docs);
or for CSS specifications other than the five modules named above: their text is not here, and the search
will return SVG excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one generation of the format. "2" keeps everything of the SVG 2 generation:
the SVG 2 snapshot, its editor's draft, the modules, the working group's drafts and the accessibility
specifications. "2.draft" keeps only the editors' drafts: the SVG 2 draft, the drafts of the five modules, SVG
Animations and the working group's drafts. "1.1" keeps SVG 1.1 (Second Edition) alone. Leave it empty to
search everything. Every excerpt comes back with `versions`: each edition whose text contains this exact
excerpt. An excerpt marked "2" and "2.draft" reads the same in the publication and in the draft; one marked
only "2.draft" is text the draft has changed or added, and an answer resting on it must say so; one marked
only "2" is text the draft no longer has in that form.

Which edition to search first. Search with `version` "2" and say the answer is for SVG 2: it is the edition
browsers follow for current features, and it is the only one that describes href without the xlink prefix,
paint-order, the use-element shadow tree and text wrapping. SVG 2 is a Candidate Recommendation, not yet a
Recommendation; SVG 1.1 (Second Edition) is the last full Recommendation. Search "1.1" when the user names SVG
1.1, shows markup with xlink:href, a DOCTYPE, the version or baseProfile attribute, or asks about something SVG
2 dropped -- SVG fonts (font, glyph, hkern), animateColor, tref, the cursor element, feature strings. For
filters, clipping and masking and animation, SVG 2 itself only points to the modules: the rules are in Filter
Effects, CSS Masking and SVG Animations (found with "2") and, in their original form, in the SVG 1.1 chapters
(found with "1.1"). When the user asks what changed, read "Changes from SVG 1.1" (document svg2--changes) and
compare the same section under "1.1" and under "2". The working group's drafts SVG Strokes, SVG Markers, SVG
Paths, SVG Native and CSS Fill and Stroke describe proposals: say plainly that such a feature is a draft.

How the text is laid out. One document per chapter of each edition, titled with the edition and the chapter
number: "SVG 2: 9 Paths", "SVG 2 Editor's Draft: 9 Paths", "SVG 1.1: 8 Paths", "Filter Effects Module Level 1:
9 Filter primitives". Document names are svg2--paths, svg2-draft--paths, svg11--paths,
filter-effects--filter-effects-filter-primitives, css-masking--css-masking-clipping-paths,
svg-animations--svg-animations-animation-elements. Headings inside a chapter carry no section numbers, because
numbering differs between editions: cite a section by its title and the URL of the excerpt. The same section
of several editions takes one place in the results and shows the newest edition found. Formulas are written
out as text: "x_1" is a subscript, "r_x^2" a power, "(a) / (b)" a fraction, "sqrt(...)" a root, and a matrix
or vector is a bracketed table with rows separated by ";", as in "[cos φ, - sin φ; sin φ, cos φ]". Element,
attribute and property definitions come as lists (Categories, Content model, Attributes, DOM Interfaces) and
tables (Value, Initial, Applies to, Inherited, Computed value, Animation type).

Write the query in English, with the names the specification uses ("viewBox preserveAspectRatio meet slice",
"stroke-dasharray stroke-dashoffset", "use element shadow tree", "textPath startOffset", "feGaussianBlur
stdDeviation", "clipPathUnits objectBoundingBox", "pointer-events hit-testing"), not in the user's own words.
Everything here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language, translate the
question into the terms of the specification first, then search.

Answer in the language the user wrote in. When the question asks what the specification requires, answer
point by point, each point with the edition, the chapter and the section title it rests on (SVG 2, Paths,
"The elliptical arc curve commands"); a point the excerpts do not support is left out, not guessed. Keep the
requirement keywords as the text has them -- "must", "should", "may" carry the weight of the rule, and a
"must" retold as "recommended" is a wrong answer. When that language is Ukrainian, write as a Ukrainian
engineer writes, not as a translation from English: plain technical prose, and the Ukrainian word wherever one
exists -- "уривок", not "ексерпт"; "вимога", not "реквайрмент". Never call this set of documents "корпус" --
say "тексти специфікацій". Element, attribute, property and interface names stay in English, spelled exactly as
the specification spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the specification uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.
