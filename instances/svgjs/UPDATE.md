# Оновлення корпусу svgjs

README (`npm-readme-*`) і реєстр (`npm-*`) беруть версії з опису пакетів у реєстрі npm, тож новий реліз ядра чи
додатка потрапляє туди сам. Журнали змін (`changelog`, `changelog-svgdom`) і релізи GitHub (`releases-*`) читаються
щоразу заново з гілки `master` і з API. Передрелізи README і релізів не беруться (`skip_versions: "-"` у README,
`"stable": true` і `skip` у релізах).

Руками оголошено:

- **Сайт** (`site`): поле `tags` тримає по рядку «SHA коміту → лінія» на кожну гілку `source-*` репозиторію
  `svgdotjs/svgdotjs.github.io`. Щоб оновити лінію, беруть SHA найновішого коміту її гілки
  (`git ls-remote https://github.com/svgdotjs/svgdotjs.github.io source-3.2`) і заміняють рядок. Нова лінія
  документації (скажімо, гілка `source-3.3`) — новий рядок нагорі, бо `tags` оголошено від найновішого. Після
  оновлення звіряють адреси: `{version}` у полі `site` стає міткою лінії, і сторінка має відповідати за адресою
  `https://svgjs.dev/docs/<лінія>/<сторінка>/`.
- **Новий додаток** — джерела `npm-readme`, `npm-versions` і, якщо є релізи, `ghreleases` за зразком наявних, з
  префіксом версії `<додаток>-`; у таблицю «Додатки і їхні ядра» README і в абзаци про префікси обох промптів
  дописують, з яким ядром працює кожна його лінія (за залежностями в реєстрі npm).

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df svgjs refresh npm-readme-svgjs3 npm-svgjs3 changelog releases-svgjs   # або джерела додатка
./df svgjs refresh --missing    # джерела, яких не названо, лише докачуються
./df svgjs manifest
./df svgjs vectors
./df svgjs smoke
# Ctrl+C у терміналі з serve, і знову: ./df svgjs serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі README стоять усі версії, де текст був таким, тож
новий реліз змінює й старі документи (незмінний README дописує нову версію в рядок `# версія:`).

## Оновився сайт

```
./df svgjs refresh site   # після заміни SHA в sources.json
./df svgjs manifest
./df svgjs vectors
./df svgjs smoke
```

Ім'я файла сторінки містить початок хеша її тексту, тому змінена сторінка лягає новим файлом поруч зі старим. Файли
попереднього знімка, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш ніж рахувати
вектори: інакше пошук знаходив би обидві редакції сторінки. Сховище сирого `raw/` повертається з архіву разом із
текстами, тож після правки читача тексти перебудовуються без мережі: `./df svgjs build <id>`.

Якщо змінилися найпоширеніші лінії (на 20.11.2026 — `@svgdotjs/svg.js` 3.2 і `svg.js` 2.7.1, близько 1,1 млн
завантажень на тиждень кожен):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінії за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"3"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторію і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df svgjs quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
