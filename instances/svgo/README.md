# svgo — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про SVGO (SVG Optimizer) — бібліотеку Node.js і команду `svgo`, що
зменшує файли SVG без видимої зміни малюнка, — і про пакети, якими SVGO запускають з інших інструментів:
`svgo-loader`, `postcss-svgo`, `@svgr/plugin-svgo`, `imagemin-svgo`, `gulp-svgmin`, `vite-plugin-svgo`. Документація
— сайт svgo.dev з останнього тегу кожної лінії 3.0–4.1, README кожної стабільної версії 0.0.1–4.1.0, журнал змін,
релізи GitHub і README з реєстром npm шести обгорток; лише англійською. Код спільний і лежить у `../../engine/`,
`../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо окремий примірник

Файл SVG, збережений з векторного редактора, несе багато зайвого: метадані редактора, коментарі, приховані
елементи, типові значення атрибутів, координати з десятьма знаками після коми. Браузеру це не потрібно, а файл від
цього в кілька разів більший. SVGO читає файл, проганяє його через ланцюжок **плагінів** і записує назад. Кожен
плагін робить одну дію: `removeComments` прибирає коментарі, `convertPathData` скорочує запис контурів,
`cleanupIds` скорочує ідентифікатори. Типовий набір плагінів зветься `preset-default`.

Питання про SVGO майже завжди про плагіни: що саме робить плагін, які в нього параметри, чому після оптимізації
малюнок перестав масштабуватися (плагін `removeViewBox`) або дві іконки на сторінці зламали одна одну (однакові
скорочені ідентифікатори після `cleanupIds`). Відповідь залежить від версії: у вжитку одразу чотири лінії, і
конфігурація між ними не переноситься без змін.

| Лінія | Що змінилося для користувача |
|-------|------------------------------|
| 2 | налаштування у `svgo.config.js` з масивом `plugins`; типовий набір міняли через `extendDefaultPlugins`, а від 2.4.0 — плагіном `preset-default` з `overrides` |
| 3 | потрібен Node.js 14; `sortAttrs` увімкнено типово; `cleanupIDs` перейменовано на `cleanupIds`, його параметр `prefix` замінив плагін `prefixIds` |
| 4 | потрібен Node.js 16; `removeViewBox` і `removeTitle` прибрано з `preset-default`; `removeScriptElement` перейменовано на `removeScripts`; імпортувати можна лише публічний API |

**Що є що.** **Плагін** — одна дія над деревом SVG з власними параметрами; **preset-default** — типовий набір
плагінів у порядку виконання; **overrides** — параметр цього набору, яким вимикають чи налаштовують окремий
плагін; **multipass** — режим, у якому SVGO проганяє файл через плагіни кілька разів, доки той зменшується;
**optimize** — функція бібліотеки, що приймає рядок SVG і повертає оптимізований; **обгортка** — пакет, що викликає
SVGO зсередини іншого інструмента (webpack, PostCSS, gulp).

## Звідки документація

- **Сайт — з репозиторію, з тегу кожної лінії.** Сайт svgo.dev (Docusaurus) збирається з теки `docs` основного
  репозиторію `svg/svgo`. Тека з'явилася в лінії 3.0, тому документацію взято з останнього тегу кожної лінії
  3.0–3.3 і 4.0–4.1. Сайт показує лише найновішу версію, тож адреса в цитаті сторінки старішої версії веде на
  сьогоднішню сторінку того самого плагіна.
- **Параметри плагіна — із шапки файла.** Сторінка плагіна — це два абзаци опису, а перелік параметрів з описами
  й типовими значеннями лежить у службовій шапці YAML файла (блок `svgo:`); сайт малює з неї таблицю. Спільний
  читач шапку відкидає. Читач `ghdocs-history-svgo` переносить її в текст: під назвою стоїть ідентифікатор
  плагіна, наприкінці — розділ «Parameters» з рядком на параметр. Якщо рядок шапки не вкладається у відому
  форму, читач зупиняється з помилкою, а не пропускає параметр мовчки.
- **Імена файлів плагінів мінялися.** У 3.0 і 3.1 файл звався через дефіс (`cleanup-ids.mdx`), далі — іменем
  плагіна (`cleanupIds.mdx`), а тека переїхала з `03-plugins` у `04-plugins`. Правила `slug_rewrite` у
  `config.json` зводять обидві форми до одного ключа, тож однаковий розділ двох версій — один фрагмент.
- **README — головна документація старих ліній.** До лінії 3 сайту не було: таблиця плагінів, опис командного
  рядка й конфігурації стоять у README. Реєстр npm віддає README лише найновішої версії, тому README кожної
  версії читається з репозиторію на коміті її публікації (`gitHead`), а де реєстр коміту не записав — з тегу.
  README є в усіх 107 стабільних версіях.
- **README обгорток — із самого пакета.** Обгортки живуть у чужих репозиторіях, частина — у монорепозиторіях
  (`postcss-svgo` у cssnano, `@svgr/plugin-svgo` у svgr). Тому їхній README читач `npm-tarball-files` бере з
  пакета кожної версії: це рівно той текст, що приходить з `npm install`.
- **Журнал змін і релізи.** Файлом журнал вели до 1.3.2; від 2.0 зміни описують релізи GitHub. `CHANGELOG-old.md`
  узято на тегу `v3.3.5`, бо в лінії 4 файл прибрано з репозиторію; заголовок запису там нестандартний, і його
  розбирає `changelog-regex`.

## Межі, про які треба пам'ятати

- Сторінок плагінів для ліній 1 і 2 немає: про плагіни цих ліній кажуть таблиця в README, журнал змін і релізи.
- Речення «плагін увімкнено типово» є на сторінках плагінів ліній 3.0–4.0: у 4.1 позначку з шапки файла прибрали.
  Для будь-якої версії перелік типових плагінів дає сторінка «Preset Default».
- Документацію взято з останнього тегу кожної лінії, а не з кожної версії: що змінилося між 3.3.0 і 3.3.5, кажуть
  релізи.
- Обгортки представлено лише їхнім README і реєстром. Документації самих webpack, PostCSS, cssnano, SVGR,
  imagemin, gulp і Vite тут немає.
- Корейський і російський переклади посібника «how it works» не беруться. У кількох старих README і в одному
  записі журналу змін є слова кирилицею (посилання на російський переклад); пошук їх не індексує.
- Код плагінів не входить: є лише їхні сторінки документації.
- Сам формат SVG — у примірнику `mdn`. Бібліотеки, що малюють SVG, мають власні примірники: `svgjs`, `snapsvg`,
  `paperjs`, `d3`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/svgo-corpus-2026-11-20.tar.gz` (тексти, паспорт і сховище сирого
`raw/`; перед видаленням текстів розпакований окремо й звірений із диском), копія —
`C:\Distr\svgo-corpus-2026-11-20.tar.gz` (`/mnt/c/Distr/…` з WSL), SHA-256 обох звірено. В історії git текстів
немає ніде.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/svgo/index/passages.json  # кеш має бути на місці й свіжий
tar --sort=name -czf ~/archives/docfactory/svgo-corpus-РРРР-ММ-ДД.tar.gz -C instances/svgo corpus raw
find instances/svgo/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/svgo/raw
gzip -9 -c instances/svgo/index/passages.json > instances/svgo/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском. Новий архів копіюють у `C:\Distr` і звіряють за SHA-256 (`tools/mirror-archives.sh --apply`),
і лише тоді видаляють попередній з обох місць, а ім'я нового пишуть у «Де тексти».

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/svgo-corpus-2026-11-20.tar.gz -C instances/svgo
./df svgo smoke
```

**Що перестає працювати.** `check`, `refresh` і `manifest` читають файли, і без текстів їм нема з чим працювати. Дві
перевірки `smoke` чесно пропускаються («корпус в архіві»).

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/svgo/index/passages.json.gz`,
далі `./df svgo vectors` заллє колекцію Qdrant.

## Установка venv

Власний venv цьому примірнику не потрібен: `./df svgo …` бере спільне середовище з кореня репозиторію
(`.venvs/cpu` або `.venvs/gpu`). Як його збудувати один раз і як `df` обирає між ними — у кореневому README.md,
розділ «Спільне середовище». Свій `.env` примірник тримає в `instances/svgo/.env` (`cp .env.example .env`; для
кроку `ask` потрібен `ANTHROPIC_API_KEY`); `GITHUB_TOKEN`, якого немає в цьому `.env`, береться з кореневого.

## Збирання корпусу

Корпус в архіві: щоб оновити чи перезібрати його, тексти спершу повертають (розділ «Архівний режим»). Для роботи
сервера збирати нічого не треба — потрібен лише `vectors`, якщо колекції ще немає.

```
./df svgo sources --why    # перелік джерел і білий список
./df svgo refresh          # усе: близько 5 хвилин мережею (паузи 0,2 с)
./df svgo manifest         # оновити паспорт
./df svgo setup            # Qdrant чи пошук лише по словах
./df svgo vectors          # залити корпус у docs-svgo
./df svgo smoke            # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df svgo serve   # порт 8995
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8995/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user svgo-docs http://127.0.0.1:8995/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `svgo-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
