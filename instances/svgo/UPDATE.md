# Оновлення корпусу svgo

README `svgo` (`npm-readme-svgo`), README обгорток (`readme-*`) і реєстр (`npm-*`) беруть версії з опису пакетів у
реєстрі npm, тож новий реліз потрапляє туди сам. Релізи GitHub (`releases`) читаються щоразу заново з API.
Передрелізи не беруться (`skip_versions: "-"`, у релізах — `"stable": true` і `skip`).

Руками оголошено:

- **Документація сайту** (`docs`): поле `tags` — об'єкт «тег → версія», від найновішого, по одному тегу на лінію.
  Нову версію тієї самої лінії ставлять замість старої (v4.1.1 замість v4.1.0), нову лінію дописують першим
  рядком. Після оновлення дивляться, чи не з'явилася в шапці сторінок плагінів нова форма: читач
  `ghdocs-history-svgo` зупиняється з помилкою на рядку блоку `svgo:`, якого не розуміє, і тоді його доповнюють.
- **Адреси сторінок сайту** (поле `site` джерела `docs`): вирази шляхів з номером теки (`04-plugins`). Якщо тека
  змінила номер чи з'явився новий розділ, адресу звіряють із `https://svgo.dev/sitemap.xml`.
- **Посібник старих ліній** (`docs-old`) і **журнал змін** (`changelog-old`) заморожені: ліній 1 і 2 більше не
  розвивають, а файл журналу закріплено на тегу `v3.3.5`.
- **Нова обгортка** — джерела `npm-tarball-files` і `npm-versions` за зразком наявних, з префіксом версії
  `<пакет>-`; у таблицю обгорток README дописують, від якої лінії `svgo` вона залежить.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df svgo refresh docs npm-readme-svgo npm-svgo releases   # після правки tags у sources.json
./df svgo refresh --missing    # джерела, яких не названо, лише докачуються
./df svgo manifest
./df svgo vectors
./df svgo smoke
# Ctrl+C у терміналі з serve, і знову: ./df svgo serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінна сторінка дописує нову версію в рядок `# версія:`). Для обгортки так само:
`./df svgo refresh readme-postcss-svgo npm-postcss-svgo`.

Ім'я файла сторінки містить початок хеша її тексту, тому змінена сторінка лягає новим файлом поруч зі старим. Після
заміни тегу в `tags` файли, яких новий прогін не записав, переносять в окрему теку поза корпусом руками, перш ніж
рахувати вектори: інакше пошук знаходив би сторінку версії, якої в переліку вже немає. Сховище сирого `raw/`
повертається з архіву разом із текстами, тож після правки читача тексти перебудовуються без мережі:
`./df svgo build <id>`.

Якщо змінилися найпоширеніші лінії (на 20.11.2026 — лінія 4, близько 42 % завантажень; лінія 3 — 31 %; лінія 2 —
17 %; лінія 1 — 9 %) або вийшла нова мажорна версія:

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінію за
  замовчуванням і дописати, що нова лінія змінила для користувача (за її посібником переходу);
- у таблицю ліній README дописати рядок;
- у `checks.json`, у десятці `quality_model`, замінити `"4"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) потрібен для дерев репозиторію і сторінок релізів: без нього API
GitHub дає 60 звернень на годину.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df svgo quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
