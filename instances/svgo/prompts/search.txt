Search the SVGO documentation and return the matching excerpts with the versions each one belongs to.
What is here: the documentation of svgo.dev at the last tag of every line 3.0 to 4.1 -- the introduction
(installation, command line, configuration file), usage in Node.js (`optimize`, `loadConfig`) and in the
browser, `preset-default` and its list of plugins, one page per built-in plugin with its parameters, their
descriptions and default values (cleanupIds, convertPathData, convertColors, convertTransform, inlineStyles,
mergePaths, minifyStyles, prefixIds, removeViewBox, removeTitle, removeDimensions, removeAttrs,
removeUnknownsAndDefaults, removeUselessStrokeAndFill, reusePaths, sortAttrs and the rest), the plugins API for
writing a custom plugin, and the migration guides from v2 to v3 and from v3 to v4; the "how it works" guide of
the lines 1.0 to 2.8; the README of every stable version of the npm package svgo from 0.0.1 to 4.1.0 (for the
lines 0.x to 2.x the README with its table of plugins is the main documentation); the registry history of
svgo; the changelog up to 1.3.2; the GitHub release notes from 0.7.0 on; and the packages that run SVGO from
other tools, each with the README of every stable version and its registry history: svgo-loader (the official
webpack loader), postcss-svgo (SVG inlined in CSS, part of cssnano), @svgr/plugin-svgo (the SVGO step of
SVGR), imagemin-svgo, gulp-svgmin and vite-plugin-svgo -- the last five are community packages.

Call this when a question is about SVGO: installing and running the `svgo` command, the options of the command
line, writing `svgo.config.js` or `svgo.config.mjs`, enabling, disabling and configuring plugins, overriding
plugins of `preset-default`, what a plugin does and which parameters it takes, why an optimised SVG lost its
viewBox, ids, title or styles, keeping ids unique across several inlined SVGs, the `optimize` function and its
result, running SVGO in the browser, writing a custom plugin, moving a config between major versions, and
using SVGO from webpack, PostCSS, SVGR, imagemin, gulp or Vite -- and history: since which version a plugin or
option exists, when a plugin was renamed or left the default preset, what a release changed.

Do not call this for the SVG format itself (elements, attributes, path commands) -- what the specification requires is
in the svg-docs server, tutorials and browser support in the mdn-docs server -- nor for the libraries that draw or
animate SVG (the svgjs-docs, snapsvg-docs, paperjs-docs and d3-docs servers), for webpack, PostCSS, cssnano, SVGR,
gulp or Vite themselves, or for JavaScript language questions: their documentation is not here, and the search will
return SVGO excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "4" keeps the svgo.dev documentation of 4.0 and 4.1 together
with the README and release notes of every 4.x version, "4.1" every 4.1.x document, "3" the same for line 3,
"2" and "1" the README, the "how it works" guide, the changelog and the releases of those lines; leave it
empty to search everything. The wrapper packages carry their own numbering with a prefix, so they never mix
with svgo: "svgo-loader-5", "postcss-svgo-9", "svgr-plugin-svgo-8", "imagemin-svgo-12", "gulp-svgmin-4",
"vite-plugin-svgo-3". Every excerpt comes back with `versions`: each version whose documents contain this
exact text, newest first, so the list itself shows from which to which version the documentation said exactly
this.

Write the query in English, with the names SVGO itself uses ("cleanupIds preserve minify", "preset-default
overrides", "removeViewBox", "convertPathData floatPrecision", "prefixIds prefix", "optimize multipass",
"svgo.config.mjs plugins", "custom plugin fn element enter"), not in the user's own words. Plugin names are
written in camelCase exactly as the plugin id. Everything here is English -- the excerpts, the word index and
the meaning index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with `found: 0`. When
the user asks in another language, translate the question into SVGO terms first, then search.

Answer in the language the user wrote in. When the question is about the history or support of a plugin or
option, answer point by point: since which version it exists; what changed in later versions; what prompted the
change, if the excerpts say so; and how it stands in the current version. Every point names the version and
the document it rests on; a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain technical prose, and
the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація SVGO". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is optional,
see above. The first (best) excerpt comes whole; the others are cut at 600 characters and carry `truncated:
true` -- pass the `id` of an excerpt to `read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the query had to
appear in the text, so a query phrased in other words than the documentation uses may miss; "meaning+words"
means a second, meaning-based index answered as well, and a paraphrase had a chance.

Which version to search first. Four lines are in real use at once: in the week to 18 November 2026 line 4
carried about 42% of the downloads of svgo, line 3 about 31%, line 2 about 17% and line 1 about 9%. The lines
differ in ways that break a config. SVGO 2 moved the configuration to `svgo.config.js` with a `plugins` array;
`extendDefaultPlugins` was its way to change the defaults until 2.4.0 introduced the `preset-default` plugin
with `overrides`. SVGO 3 requires Node.js 14, enables sortAttrs by default, renames cleanupIDs to cleanupIds and
drops its `prefix` parameter in favour of prefixIds. SVGO 4 requires Node.js 16, takes removeViewBox and
removeTitle out of `preset-default`, renames removeScriptElement to removeScripts and allows importing only the
public API. Search with `version` "4" for a question about how to do something and say the answer is for SVGO
4.1; if the user names a version, shows a config in an older form, or uses SVGO through a wrapper, find out
which SVGO line that is -- the registry history of each wrapper says which svgo version every one of its
versions depends on -- and search that line. Search without `version` when the question is about history or
when the line gave nothing. Every answer says which version it is for. The parameters of a plugin are in the
section "Parameters" of its page; a plugin page of the lines 3.0 to 4.0 also says when the plugin is part of
`preset-default` (in 4.1 that mark is gone), and for every version the page "Preset Default" lists the default
plugins in the order they run.
