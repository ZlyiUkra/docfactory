# Оновлення корпусу swr

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи SWR, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версії приходять самі, з реєстру npm.** Сайт swr.vercel.app тегів не має, тож читач
`ghsite-dated` бере перелік версій і їхні дати з https://registry.npmjs.org/swr і на кожну стабільну версію робить
знімок гілки `main` репозиторію vercel/swr-site — вершину гілки перед виходом наступної версії тієї ж лінії. README,
релізи й реєстр npm так само читають актуальний перелік. Руками нічого дописувати не треба, окрім прикладів (крок 3).

Друге правило: **нова версія змінює й старі документи.** Документ — неповторний текст сторінки, а в рядку
`# версія:` стоять усі версії, де сторінка була саме такою. Тож після нового релізу корпус перезаписують цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх не
знайде. Для найновішої версії знімок — сьогоднішній стан гілки, тож навіть без нового релізу правка сайту змінює
корпус.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Чи змінилася розкладка сайту.** Сайт уже тричі переносив файли: `docs/index.md` (весна 2020),
`pages/**/*.md(x)` (з 02.2021 англійські файли — `*.en-US.mdx`), `content/**/*.mdx` (з 10.12.2025). Кожна розкладка
— окрема епоха в полі `eras` джерела `swr-site`. Якщо сайт знову переїхав, у переліку нових версій не з'явиться
жодної сторінки сайту: тоді останній епосі дописують `before` (дата коміту переїзду), додають нову епоху з новими
шляхами, а в `config.json` — правило `slug_rewrite`, що зводить нові імена сторінок до тих самих ключів (`docs-…`).

**Крок 2. Якщо вийшла нова мажорна лінія** (3.0):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзаци «Which version to search first» і «Every answer
  says which version it is for») та `prompts/agent.txt` велять на питання «як зараз» шукати з `version "2"` —
  інакше модель і далі шукатиме в старій лінії, а нова документація у видачу не потрапить;
- лінію за замовчуванням вибирають за завантаженнями з npm за тиждень, а не за номером: поки 2.x завантажують більше,
  вона лишається основною;
- у `checks.json`, у десятці `quality_model`, замінити `"2"` на нову лінію там, де питання про поточну поведінку.

**Крок 3. Приклади.** Приклади беруться на останньому тезі кожної лінії: `swr-examples-v2` — `v2.5.1`,
`swr-examples-v1` — `1.3.0`, `swr-examples-v0` — коміт версії 0.5.7. Новий реліз лінії 2.x — замінити тег у `url`,
`version` і `title` джерела `swr-examples-v2`; нова лінія — нове джерело `swr-examples-v3` за тим самим зразком.
Теги репозиторію vercel/swr мають два вигляди: 0.x, 1.x і 2.0.0 — без «v», з 2.0.1 — з «v». Список, без жодного
звернення до API:

```
git ls-remote --tags https://github.com/vercel/swr.git | grep -v '\^{}' | sed 's#.*refs/tags/##' | grep -v -- -
```

**Крок 4. Завантажити.**

```
./df swr sources --why
./df swr refresh
./df swr manifest
./df swr vectors
./df swr smoke
# Ctrl+C у терміналі з serve, і знову: ./df swr serve
```

`refresh` без назв — повне перезавантаження: перелік комітів сайту, дерева знімків, потім файли. Корпус не
комітиться: після оновлення пишуть новий архів і знову виносять тексти (README, розділ «Архівний режим»), а в git
ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Особливі версії

- **0.1.0 — чужий пакет.** Його опубліковано 06.04.2018, за півтора року до SWR, іншим автором, що раніше володів
  ім'ям `swr`. Його відкидають усі джерела (`only`, `skip_versions`); версії 0.1.1 не існує, SWR починається з 0.1.2.
- **README без коміту в реєстрі.** Для 2.0.0–2.1.3 реєстр npm не записав `gitHead`; README тоді береться з тегу:
  спершу `v{версія}`, а коли такого немає (2.0.0) — тег без «v». Обидва шаблони стоять у полі `files` джерела
  `swr-readme`.
- **Тегів 0.1.2, 0.1.5, 0.5.2, 0.5.5, 0.5.7 немає**, але реєстр записав їхні коміти, тож README цих версій є.
- **Тег `remove`** у репозиторії є, але він не випуск; джерело релізів його пропускає.

## 3. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього перелік ~90 дерев і ~440 комітів іде
годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
setsid nohup ./df swr refresh > instances/swr/out/refresh.log 2>&1 &
```

Перші ~4 хвилини журнал мовчить, а `corpus/` порожній: читач проходить коміти й дерева сайту. Стан видно за
кількістю файлів: `ls instances/swr/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df swr quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Що це означає тут:

- **Поточна лінія — 2.** Що міняти з новою мажорною лінією — крок 2 розділу «1. Вийшли нові релізи» вище.
- **Правила промпту, що вже є:** спершу лінія 2; запит — назвою хука, опції чи поняття, а не описом; питання про
  історію — нотатки релізу й допис у блозі про 1.0 чи 2.0; кожна відповідь каже, для якої версії вона, а без
  названої версії — відповідає для 2.x і пропонує назвати свою.
- **Останній результат** — у README, абзац «Замір `quality`».
