Search the official documentation of SWR, the React Hooks library for data fetching -- the site
swr.vercel.app on every stable release from 0.2 to the current 2.x line, the README of every
stable version from 0.1.2 on (for 0.x it was the main documentation), the GitHub release notes of
every stable release, the npm registry history of the swr package and the example applications
of the repository for the 0.x, 1.x and 2.x lines. Return the matching excerpts with the versions
each one belongs to.

Call this when a question is about SWR itself -- useSWR and its arguments (key, fetcher, options),
the options and their defaults (revalidateOnFocus, revalidateOnReconnect, refreshInterval,
dedupingInterval, fallbackData, fallback, keepPreviousData, suspense, shouldRetryOnError,
errorRetryCount, onSuccess, onError, compare, isPaused, use), the returned values (data, error,
isLoading, isValidating, mutate), SWRConfig and global configuration, conditional and dependent
fetching, arguments and multiple arguments, data fetching with fetch, axios and GraphQL, error
handling and retry, automatic revalidation, mutation and revalidation (global mutate, bound
mutate, useSWRMutation and trigger, optimistic updates, rollbackOnError, populateCache,
revalidate), pagination and infinite loading (useSWRInfinite, size, setSize, getKey), prefetching
and preload, subscriptions (useSWRSubscription), Suspense, middleware, the cache provider and its
API, performance (deduplication, deep comparison, dependency collection), Next.js (SSG, SSR, the
App Router, React Server Components), React Native, TypeScript, DevTools, and the blog posts
announcing 1.0 and 2.0. Example query: "useSWRMutation trigger".

Do not call this for TanStack Query, Apollo, RTK Query, Relay or other data-fetching libraries,
nor for React or Next.js in general, beyond what the SWR documentation says about them: their own
documentation is not here, and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line: "2" keeps every 2.x document, "2.2" keeps
2.2.x, "1" keeps 1.x, "0.5" keeps 0.5.x; leave it empty to search everything. Every excerpt comes
back with `versions`: each version whose documents contain this exact text, newest first -- text
that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lived. Up to 0.2 (spring 2020) the README of the repository vercel/swr was
the whole documentation, and it stayed the fullest reference for all of 0.x: titles "SWR README
0.3.0 ... 0.5.7". From May 2020 the site swr.vercel.app had a single docs page ("docs/index"), from
July 2020 a Nextra site of separate pages titled by their path -- "docs/options",
"docs/mutation", "docs/pagination", "getting-started"; from February 2021 the same pages carry the
suffix ".en-US" in the title ("docs/mutation.en-US", "docs/advanced/cache.en-US",
"blog/swr-v2.en-US"); from December 2025 the site moved to new files, titled again without the
suffix ("docs/mutation", "docs/api"). The release notes are titled "SWR release: v2.3.0"; there is
no CHANGELOG file -- the release notes are the change log. The examples are titled
"Example: basic", "Example: infinite-scroll" and hold the code of each example application.

Which version to search first. For a question about how to do something today, pass `version`
"2": without it, the many editions of older pages can take places with the current ones. If the
user's project runs 1.x or 0.x, pass that line instead -- the API changed a lot between them
(1.0 moved useSWRInfinite to swr/infinite, renamed initialData to fallbackData, dropped the
default fetcher and added cache providers and middleware; 2.0 added useSWRMutation, isLoading,
keepPreviousData and preload, and the fetcher no longer takes multiple arguments). Search without
`version` when the question is about history, or when the line gave nothing that answers.

Name the hook, option or concept the way the documentation titles it, not in the user's own
words: "dedupingInterval", "fallbackData", "useSWRInfinite", "optimisticData", "cache provider",
"revalidateOnFocus", not "how to stop it refetching". For a question about when something
appeared, changed or disappeared, search more than once: without `version` first, to find the
release note or blog post that names the exact version, then with the versions around it, to see
how the documentation described it before and after.

Write the query in English, with the names SWR itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into SWR terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for the
default line, SWR 2.x, say so in the answer ("for SWR 2.x"), and add that for a precise answer
about another version the user can name it. When the excerpts behind a statement come only from
older versions, name those versions instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists and which release introduced it;
what changed in later versions; what prompted the change, if the excerpts say so; and how it
stands in the current version -- recommended, deprecated, or removed and replaced by what. Every
point names the version and the document it rests on; a point the excerpts do not support is left
out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація SWR". Identifiers, API names and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came back,
not out of memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
