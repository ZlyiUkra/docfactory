# tailwind — примірник фабрики docfactory

П'ятнадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Tailwind CSS за офіційною
документацією всіх його версій — v4.3, v3.4, v2.2, v1.9 і v0.7 — з посібниками встановлення під кожен фреймворк,
журналом змін від 0.1.0 і реєстром версій npm самого `tailwindcss` та пакетів, з якими його використовують. Код
спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний
устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

Tailwind між мажорними версіями змінюється не косметично. У v3 і раніше налаштування живе в `tailwind.config.js`,
стилі підключаються директивами `@tailwind base; @tailwind components; @tailwind utilities;`, а у фреймворк Tailwind
заходить через PostCSS; у v4 конфігурація переїхала в CSS (`@theme`, `@import "tailwindcss"`), а для Vite є власний
плагін `@tailwindcss/vite`. Проєкти на старих версіях фреймворків живуть зі старим Tailwind і старими версіями
бібліотек навколо нього, тож питання «як це налаштувати саме тут» має відповідь лише в документації тієї версії.

Друге питання — сумісність: яка версія `flowbite-react`, `daisyui` чи `@astrojs/tailwind` працює з якою версією
Tailwind і фреймворку. Цього не пише жодна сторінка документації, але це записано в реєстрі npm: peer-залежності
(«пакет чекає поруч такої-то версії іншого пакета») кожної опублікованої версії. Тому реєстр тут — окремий шар.

Разом 1 800 документів; фрагментів в індексі — 15 922 (`expected_passages` у `checks.json`). Фрагменти — це
шматки документів між заголовками, по яких іде пошук; однаковий текст різних версій зливається в один з усіма
версіями.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 5 із 10, за
змістом 6, разом 6; друга, «як модель» (назви класів, директив і сторінок, з `version`, як велить промпт), — 10 із 10.
Цілі — розділи всіх версій, бо для проєкту на старшому Tailwind правильна відповідь саме там. Промахи першої
десятки:

- **Своїми словами без термінів.** «Змінити стиль, коли над елементом миша» знаходить довідку псевдокласу `hover` у
  додатку сторінки, а не розділ «Hover, focus, and active»; «власний колір бренду в палітрі» — палітру кольорів за
  замовчуванням, а не її налаштування. Слова питання й документації не збігаються, тож промпт велить писати запит
  назвами; друга десятка з ними влучає щоразу.
- **Без версії місця займають README.** Питання «що зламається при переході з 3 на 4» без версії приносить розділи
  «Versioning» з README пакетів, а «перевикористати набір класів у своєму CSS-класі» — API `createTailwindMerge`. З
  README тут 6 671 фрагмент із 15 914, з них 2 685 — daisyUI (265 різних текстів README). Тому промпт велить
  шукати без `version` лише сумісність пакетів та історію.

**Версія у відповіді.** Кожна відповідь каже, якої версії Tailwind вона стосується; без названої — за v4, а де v3
робить це інакше (конфігурація, директиви, встановлення), — і спосіб v3.

## Пакети поруч із Tailwind

Для кожного — реєстр версій npm; README всіх версій — там, де README є документацією, а не посиланням на сайт.

| Пакет | Для чого | README |
|-------|----------|:------:|

cva, daisyUI, flowbite-react і flowbite-angular README на GitHub сьогодні теж короткий, але в опублікованих
пакетах старих ліній він був повною документацією (у Headless UI 0.x — до 50 КБ), тому взято всі версії.

### Що таке insiders і нічні збірки

У реєстрі npm трапляються версії, які релізами не є:

- **`0.0.0-insiders.<коміт>`** — Tailwind (і Headless UI) публікує збірку з кожного коміту в основну гілку з міткою
  `insiders`. Це спосіб спробувати виправлення до офіційного релізу — наприклад, перевірити, що баг закрито. Номер
  не каже, якій версії Tailwind вона відповідає; для роботи вона не призначена. У `tailwindcss` таких 2 272 з 2 661
  версії.
- **`0.0.0-development.N`** — ранні технічні публікації того самого роду.
- **Збірки з хешем коміту в номері** (`0.3.1-8de0114` у Headless UI) і нічні (`nightly`) — те саме під іншою назвою.

Їхній README — просто README репозиторію того дня, тож для README вони не беруться. У реєстрі версій вони лишаються:
якщо така версія трапиться у вашому `package.json` чи lock-файлі, документ реєстру покаже її дату й мітку.
Передрелізи (`4.0.0-alpha.1`, `-beta`, `-rc`) — інша річ: це версії на шляху до релізу, вони беруться всюди.

## Що в цій теці

- `corpus/` — документи звичайними текстовими файлами; поруч `index.json` — паспорт: адреса, дата завантаження й
  сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df tailwind <крок>`.

Два нові читачі:

- **`html-pages`** — зібраний HTML сторінок сайту; перелік — посилання бічного меню зі сторінок-змістів, текст — від
  заголовка сторінки до кінця статті. Вихідники сайту (MDX) тут не годяться: таблиця класів сторінки («`p-4` |
  `padding: 1rem`») у v1–v3 генерується з коду самого tailwindcss під час збирання, у v4 — обчислюється виразом JS у
  розмітці, а спільні блоки («Responsive design», «Using a custom value») — окремі компоненти. Усе це є лише в
  готовому HTML.
- **`guide-steps`** — посібники v3 з модулів JS: вкладка — розділом («Using Vue»), крок — підрозділом, код — блоком з
  ім'ям файла. Зібраний сайт v3 показує лише першу вкладку: Vue і Svelte у посібнику Vite, Laravel Mix у посібнику
  Laravel в HTML не потрапляють. У v4 кожна вкладка — окрема адреса, тож там вистачає `html-pages`.

Особливості, які варто знати:

- **Мітки версій документації:** `4.3`, `3.4`, `2.2`, `1.9`, `0.7`; журнал змін — точний номер релізу. Фільтр `"3"`
  бере v3.4 разом із записами журналу 3.x.
- **Номери в реєстрі й README — свого пакета.** З `version "3"` знайдуться і daisyUI 3, і tailwind-merge 3; назва
  документа каже, про який пакет мова.
- **v0.7 — без таблиць класів:** їх вставляв шаблон Blade, у markdown лишився рядок `@include(...)`.
- **Кілька ранніх версій без README:** alpha 4.0 плагінів Vite і PostCSS, preline 1.0.x — ні коміту публікації, ні
  тегу для них у репозиторії немає.
- **Лише англійська.**

Тут немає документації самих фреймворків (React, Vue, Angular, Astro — окремі примірники там, де вони є) і

## Установка venv

```
cd instances/tailwind
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df tailwind sources --why   # перелік джерел і білий список
./df tailwind refresh         # завантажити все задеклароване (~50 хвилин, переважно README)
./df tailwind manifest        # оновити паспорт
./df tailwind setup           # Qdrant чи пошук лише по словах
./df tailwind vectors         # залити корпус у docs-tailwind
./df tailwind smoke           # перевірки
```

`refresh` з іменами джерел без `--missing` однаково проходить усі джерела; щоб довантажити лише названі, —
`./df tailwind refresh --missing <id…>`.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df tailwind serve          # порт 8775
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8775/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user tailwind-docs http://127.0.0.1:8775/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `tailwind-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df tailwind setup --vectors      # з Qdrant: потрібен Docker
./df tailwind setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

**4. Перевірка, сервер, клієнт.**

```
./df tailwind smoke          # усі перевірки мають бути ok
./df tailwind serve          # порт 8775, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
