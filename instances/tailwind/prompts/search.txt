Search the official Tailwind CSS documentation -- every major version of it: v4.3
(tailwindcss.com), v3.4 (v3.tailwindcss.com), v2.2, v1.9 and v0.7 -- including the class
tables of every utility page, the "Install Tailwind CSS with ..." guide for each framework
(Vite, Next.js, Astro, Angular, Nuxt, SvelteKit, React Router, Remix, Laravel, Create React
App, Gatsby and others, with every tab such as "Using Vue" or "Using Laravel Mix"), the
upgrade guides, the CHANGELOG entry of every release from 0.1.0 to today, and the npm
registry list of every published version of tailwindcss and of the packages used with it
(date, dist-tag, dependencies and peer dependencies), and return the matching excerpts with
the versions each one belongs to.

Call this when a question is about Tailwind CSS itself -- utility classes and their CSS
(padding, grid-template-columns, text-color), variants (hover:, focus:, dark:, md:, group-*,
peer-*), responsive design, dark mode, theme and configuration (tailwind.config.js in v3 and
older, @theme and CSS-first configuration in v4), directives and functions (@tailwind,
@apply, @layer, @import "tailwindcss", @config, @plugin, @source, theme()), preflight,
content detection, plugins, installation with a framework or a build tool (Vite, PostCSS,
the CLI, the Play CDN), an upgrade from one major version to the next -- and above all when
it is about version compatibility: which version of tailwindcss, @tailwindcss/vite,
@tailwindcss/postcss, @astrojs/tailwind, Headless UI, tailwind-merge, daisyUI, Flowbite
(flowbite-react, flowbite-vue, flowbite-angular), Preline, shadcn, shadcn-vue or spartan/ui
fits which version of another -- the peer dependencies of each version answer that. Example
query: "grid-cols arbitrary value".

Do not call this for the documentation of the frameworks themselves (React, Vue, Angular,
Astro, Next.js), of the component libraries (their component APIs, props and examples) or of
CSS itself: here are only Tailwind's own documentation and the npm registry facts about those
packages, and the search will return excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line: "4" keeps the v4.3 documentation and the
4.x changelog entries, "3" keeps v3.4, "2", "1" and "0" the older lines; leave it empty to
search everything. The npm registry documents carry the version numbers of their own package:
with `version` "3" a registry excerpt may be about daisyUI 3 or tailwind-merge 3, not
Tailwind CSS 3 -- its title names the package. Every excerpt comes back with `versions`: each
version whose documents contain this exact text, newest first.

How the text is laid out. Documentation pages are titled as on the site ("Padding",
"Install Tailwind CSS with Astro", "Upgrade guide"); a class table reads as rows
"p-4 | padding: calc(var(--spacing) * 4);" (v4) or "p-4 | padding: 1rem;" (v3 and older). A
guide is a list of steps, each with its code block and the file name above it. Changelog
entries are titled "Tailwind CSS changelog <version>". Registry documents are titled by the
package: an overview (dist-tags, release lines, import paths) and one document per major
line, listing every version with its date and what changed in its dependencies and peer
dependencies.

Which version to search first. For a question about how to do something today, pass
`version` "4": without it, five editions of the same page, which differ in details, fill
every place. When the user's project is on an older Tailwind (a tailwind.config.js, @tailwind
directives, an older framework), search that line: "3" for most projects before 2025. Search
without `version` for compatibility between packages and for history.

For a question about when something appeared, changed or disappeared, search more than
once: the changelog and the upgrade guide name the exact version; then search the lines
before and after it to see how the documentation described it. For a question about which
versions of two packages work together, search the registry document of the package that
depends on the other, and read the peer dependencies of its versions.

Write the query in English, with the names Tailwind itself uses (class names, directive
names, config keys, package names). Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits,
so a query written in Ukrainian, Russian or any other non-latin script matches nothing at
all and comes back with `found: 0`. When the user asks in another language, translate the
question into Tailwind terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer
for v4 -- the current line -- say so ("in Tailwind CSS v4"), and when v3 does it differently
(configuration, directives, installation), give the v3 way too: many projects are still on
it. When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about setting Tailwind up or
about compatibility, answer point by point: which packages and which versions; the steps and
the files they change; what differs for the other major version. Every point names the
version and the document it rests on; a point the excerpts do not support is left out, not
guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists
-- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація Tailwind CSS". Class names, directives, package
names and titles stay in English, spelled exactly as the documentation spells them. Build the
answer out of the excerpts that came back, not out of memory: if an excerpt was cut, read the
whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
