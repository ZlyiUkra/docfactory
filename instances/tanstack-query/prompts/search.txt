Search the official TanStack Query documentation (React Query before v4) -- every published
version of it, from 0.x to the current 5.x line, including alpha, beta and release candidate
builds -- together with the API reference of every framework adapter, the example apps, the
changelogs of all @tanstack/*-query packages, the GitHub release notes and the TanStack blog
posts about Query, and return the matching excerpts with the versions each one belongs to.

Call this when a question is about TanStack Query itself -- useQuery, useMutation,
useInfiniteQuery, useSuspenseQuery, queryOptions, QueryClient and QueryCache, query keys,
staleTime and gcTime (cacheTime before v5), invalidation and refetching, optimistic updates,
prefetching, SSR and hydration, persisters, devtools, the ESLint plugin, the adapters for
React, Preact, Vue, Angular, Solid, Svelte and Lit, an upgrade between major versions -- and
above all when it is about history: since which version something exists, what changed
between versions, what was renamed or removed and what replaced it. Example query:
"useQuery staleTime gcTime".

Do not call this for React, Vue or the other frameworks themselves, for TanStack Router,
Start, Table, Form or DB (only two blog posts about DB are here), for SWR, Apollo or RTK
Query: their documentation is not here, and the search will return TanStack Query excerpts
that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "5" keeps every 5.x document, "4.29" keeps
4.29.x, "0.3" keeps 0.3.x; leave it empty to search everything. Pre-releases belong to their
line: "5" also keeps 5.0.0-beta.1. Every excerpt comes back with `versions`: each version
whose documents contain this exact text, newest first -- text that stayed the same across
versions is returned once, with all of them listed, so the list itself shows from which to
which version the documentation said exactly this. Versions after 5.90.3 are the versions of
@tanstack/query-core; changelog and release entries of an adapter carry that package's own
version (svelte-query is on its own 6.x line, solid-query has 6.0 release candidates).

Where the documentation lived. Up to 1.x the whole documentation was the README of the
repository; from 2.x it is the docs/ folder, and from 4.x each framework has its own pages.
In the current line a page that exists for several frameworks is a separate document per
framework (docs/framework/react/..., docs/framework/vue/...): name the framework in the
query ("useQuery vue"), and the search fills the place with that framework's page; a query
that names no framework gets whichever ranked highest, often not the user's. Example apps
are documents titled "Example: react/simple" with their package.json and source files.

Which version to search first. For a question about how to do something today, pass
`version` "5" and name the framework of the project in the query ("invalidateQueries after
mutation react"): without it, the many editions of the old 0.x-1.x README, which differ by
a line or two, fill every place with the API of 2020, and the current guide does not make
it into the results. If the user's project runs an older line, pass that line instead ("3",
"4"). Search without `version` when the question is about history, or when the line gave
nothing that answers.

Name the feature the way the documentation titles it, not in the user's own words: "dependent
queries enabled", "paginated queries placeholderData", "important defaults staleTime", not
"run a query after another one returned". A description without these names matches the
API reference pages, which list every option, and misses the guide that explains the
feature. When every excerpt that came back is an API reference page (an id with
"-reference-" in it) and the question is how to do something, search again with the name of
the guide.

For a question about when something appeared, changed or disappeared, search more than
once: without `version` first, to find the changelog entry, the release notes and the
migration guide that name the exact version, then with the versions around it, to see how
the documentation described it before and after.

Write the query in English, with the names TanStack Query itself uses (useQuery,
queryClient.invalidateQueries, placeholderData, keepPreviousData, isPending). Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word
index keeps only latin letters and digits, so a query written in Ukrainian, Russian or any
other non-latin script matches nothing at all and comes back with `found: 0`. When the user
asks in another language, translate the question into TanStack Query terms first, then
search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer
for the default line, 5.x -- the line most projects use -- say so in the answer ("for
TanStack Query 5.x"), and add that for a precise answer about another version the user can
name it. When the excerpts behind a statement come only from older versions, name those
versions instead of presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history
or support, answer point by point: since which version it exists and which release
introduced it; what changed in later versions; what prompted the change, if the excerpts
say so; and how it stands in the current version -- recommended, deprecated, or removed and
replaced by what. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. A text found only in alpha, beta or rc
builds may never have shipped in a release: say so. When that language is Ukrainian, write
as a Ukrainian engineer writes, not as a translation from English: plain technical prose,
and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація TanStack
Query". Identifiers, API names and titles stay in English, spelled exactly as the
documentation spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
