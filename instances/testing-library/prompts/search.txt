Search the documentation of Testing Library, in English: the whole site testing-library.com
(the core DOM Testing Library -- queries, the ByRole query and the priority of queries,
waitFor and findBy, fireEvent, configuration, debugging; user-event 14 -- setup(), click,
type, keyboard, pointer, clipboard, options; the guides -- guiding principles, appearance and
disappearance, events, fake timers; the examples; the ecosystem -- jest-dom, the eslint
plugins, query extensions) together with the page of every framework wrapper: React Testing
Library, React Native, Vue, Angular, Svelte, Preact, Solid, Qwik, Marko, Cypress, Puppeteer,
Nightwatch, TestCafe and WebdriverIO -- as it stands now and in four older snapshots of the
site (2020-02, 2022-02, 2023-01, 2024-04) for code that still runs old versions; the rule
pages and migration guides of eslint-plugin-testing-library (majors 3 to 7) and
eslint-plugin-jest-dom (majors 3 to 5); the docs of the deprecated
@testing-library/react-hooks (majors 1 to 8); for the React line also the README of every
published version of @testing-library/react, @testing-library/dom,
@testing-library/user-event, @testing-library/jest-dom, @testing-library/react-hooks and both
eslint plugins, plus the README on the main branch with changes not released yet, their
GitHub release notes, and the npm registry list of every published version (date, dist-tag,
dependencies and peer dependencies). Returns the matching excerpts.

Call this when a question is about testing a user interface the way a user sees it: render
and screen, getByRole, getByLabelText, findBy and queryBy, within, waitFor and
waitForElementToBeRemoved, user-event and why it is preferred over fireEvent, renderHook,
act and "not wrapped in act(...)" warnings, cleanup, jest-dom matchers (toBeInTheDocument,
toBeVisible, toHaveAccessibleName), setup with Jest or Vitest, accessible queries, common
lint rules (prefer-screen-queries, no-node-access, await-async-queries) -- and when it is
about versions of the React line: what changed between React Testing Library 12, 13, 14, 15
and 16, user-event 13 and 14, jest-dom 5, 6 and 7, and which versions of React and
@testing-library/dom each one needs -- the peer dependencies answer that. Example query:
"React Testing Library getByRole name option".

Always name the framework in the query. The site has a page for every framework, and render,
screen, setup and options differ between them: "React Testing Library render wrapper",
"Angular Testing Library render componentProperties", "Vue Testing Library render props".
The queries, waitFor, user-event and jest-dom are shared by every framework and come from
the DOM Testing Library pages; for those the framework need not be named. When the user
works with React -- the default here -- say "React Testing Library" in the query and prefer
excerpts from the react-testing-library pages and the React packages; an excerpt from
another framework's page answers a question about that framework only.

Do not call this for the test runners themselves (Jest, Vitest, Mocha, Playwright Test), for
MSW or Supertest, or for React itself: their documentation is not here, and the search will
return Testing Library excerpts that merely mention them, with confident-looking titles. For
the npm packages of wrappers other than React -- their README, versions and release notes --
nothing is here yet; only their pages on the site.

There is no version filter here. The header of every excerpt says which versions it belongs
to: a site page says "current" or the month of an older snapshot (an old snapshot describes
the API of that time -- wait and waitForElement before waitFor, user-event 13 before 14);
the README of each version of a React-line package names its versions; "main" marks text not
released yet; and the registry documents list every version with its peer dependencies. Put
the version into the query when it matters ("user-event 14 type", "user-event 13 type"), and
do not answer a question about the current version from an old snapshot. When the user did not name
a version, answer for the most downloaded line on npm and say so: React Testing Library 16,
@testing-library/dom 10, user-event 14, jest-dom 6 (jest-dom 7 is the newest release, but
6 is still downloaded far more -- mention both when they differ).

Where the documentation lives. Site pages are named by their path in the docs folder:
site-docs--docs-queries-byrole-..., site-docs--docs-react-testing-library-api-...,
site-docs--docs-user-event-..., site-docs--docs-angular-testing-library-..., guides as
docs-guide-... and docs-guides-.... Lint rules are named by their path in the plugin
repository (docs-rules-prefer-screen-queries). README documents, release notes and registry
documents are titled by package.

Write the query in English, with the names the documentation uses (getByRole, findByText,
screen, within, waitFor, userEvent.setup, renderHook, toBeInTheDocument, configure,
testIdAttribute). Everything here is English -- the excerpts, the word index and the meaning
index alike -- and the word index keeps only latin letters and digits, so a query written in
Ukrainian, Russian or any other non-latin script matches nothing at all and comes back with
`found: 0`. When the user asks in another language, translate the question into Testing
Library terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Answer in the language the user wrote in. Every answer says which framework, which package
and which version it is for. When the question is about a version change, a migration or
compatibility, answer point by point: which package and since which version; what changed;
what the migration requires; how it stands now -- each point with the document it rests on;
a point the excerpts do not support is left out, not guessed. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain
technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"запит", not "квері"; "застарілий", not "депрекейтнутий". Never call this set of documents
"корпус" -- say "документація Testing Library". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.
