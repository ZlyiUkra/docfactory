# typeorm — примірник фабрики docfactory

Захищений MCP-сервер, що відповідає на питання про TypeORM — ORM для TypeScript і JavaScript (PostgreSQL, CockroachDB,
MySQL, MariaDB, SQLite, Microsoft SQL Server, Oracle, SAP HANA, Google Spanner, MongoDB, sql.js, Capacitor, Cordova,
Expo, React Native): сутності й колонки, зв'язки, `DataSource` і його параметри, `EntityManager` і `Repository`,
параметри `find`, QueryBuilder, міграції й CLI, транзакції, підписники, драйвери кожної бази й перехід з 0.3 на 1.0.
Джерела — головний репозиторій typeorm/typeorm на кожному стабільному тезі (документація, код і тести), його
`CHANGELOG.md` і релізи GitHub та реєстр npm, лише англійською й лише стабільні версії. Код спільний і лежить у
`../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо

План NestJS (фаза 3, дні 1–10) будує шар даних на TypeORM. А TypeORM у травні 2026 вийшов з лінії 0.x: 1.0 прибрала
`Connection`, `findByIds`, `@EntityRepository`, налаштування змінними `TYPEORM_*` і `ormconfig.env`, змінила хеш
стратегії іменування й поведінку `where` з `null` чи `undefined` і ще десятки речей. Сайт typeorm.io тепер показує
лише 1.x, v0.typeorm.io — лише останню 0.3, а більшість проєктів досі на 0.3 (78 % завантажень npm за тиждень до
19.10.2026) і частина — на 0.2. Тож потрібен текст документації саме тієї версії, з якою працюєш, а не пам'ять моделі,
яка змішує обидві лінії. Код `src/` з JSDoc і тести кожного тегу відповідають на те, чого в документації немає: повний
перелік параметрів декоратора чи драйвера, що саме робить метод і з якої версії.

**Що є що.** **ORM** — бібліотека, що дає працювати з таблицями як з об'єктами. **Сутність** (entity) — клас із
декоратором `@Entity()`, що відповідає таблиці; її поля з `@Column()` — колонки, `@ManyToOne`/`@OneToMany` та інші —
зв'язки. **DataSource** (до 0.3 — `Connection`) — підключення до бази з параметрами драйвера; через нього беруть
**EntityManager** (операції з будь-якими сутностями) і **Repository** (операції з однією). **QueryBuilder** — побудова
SQL ланцюжком викликів (`createQueryBuilder().leftJoinAndSelect().where()`). **Міграція** — клас із методами
`up`/`down`, що змінює схему бази; CLI порівнює сутності з базою й генерує його сам (`migration:generate`).
**Codemod** (`@typeorm/codemod`) — програма, що переписує код 0.3 під 1.0.

У яких фазах і днях планів навчання він потрібен — див. [../../docs/learning-map.md](../../docs/learning-map.md).

версії, де він був саме таким; однаковий текст різних версій лягає одним фрагментом з усіма цими версіями. 94 %
фрагментів — код і тести.

Замір `quality`: перша десятка (питання своїми словами, без версії) — по словах 6 із 10, за змістом 4, разом 7; друга,
«як модель» (назви TypeORM разом зі словами теми сторінки, як велить промпт), — 10 із 10, і так само з версією
`"1.1"`; з версією `"0.3"` — 9: посібника переходу на 1.0 у лінії 0.3 немає, і так має бути. Перший замір дав «як
модель» 7 із 10: код і тести — дев'ять фрагментів із десяти, і запит самими іменами (`@Column options nullable default
unique length`, `createQueryBuilder leftJoinAndSelect`, `MongoDB @ObjectIdColumn entity`) приносив сутності з тестів і
файли коду замість сторінки документації. Промпт тепер радить ставити поруч з іменами слова теми сторінки чи її
розділу («Column options», «Select using Query Builder joining relations», «MongoDB defining entities and columns»), а
для коду — ім'я класу й методу. Цілі доповнено справжніми відповідями: сторінкою Pagination (питання про offset і
limit — дослівно про неї) і розділами «Supported isolation levels» та «Default isolation level» сторінки Transactions.
Пошук за змістом у першій десятці слабкий з тієї самої причини: на переказ без жодного слова зі сторінки модель
векторів приносить найближчий код. `max_per_doc` 0, 2 і 3 дають ту саму видачу, 1 — гіршу; `fusion_depth` 10 нічого не
змінює; обидва не ввімкнені.

## Що в цій теці

- `corpus/` — лише паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа (тексти — в архіві,
  див. нижче).
- `index/passages.json.gz` — стиснений кеш фрагментів, з якого підіймається сервер.
- `sources.json` — звідки корпус будується (15 джерел), і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, родини джерел (`families`), спільні ключі перейменованих
  сторінок (`slug_rewrite`), глибина лінії версій і профіль домену; `max_per_doc` не потрібен (замір нижче).
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — токен GitHub (дерева тегів, релізи) і, для кроку `ask`, ключ Anthropic; `.mcp.json` — запис HTTP-сервера
  для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад (без GPU: вектори рахує процесор).

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df typeorm <крок>`.

Особливості, які варто знати:

- **Три розкладки документації.** До 0.3.24 — плоска тека `docs/*.md` (≈50 сторінок), з 0.3.25 — Docusaurus
  (`docs/docs/<розділ>/<N>-<сторінка>.md`), а з 1.0 сторінки ще й переставлено (`advanced-topics/3-indices` →
  `indexes`, `guides/2-mongodb` → `drivers/mongodb`, міграції — окремий розділ із одинадцяти сторінок з 0.3.28). Поле
  `slug_rewrite` у `config.json` дає сторінці спільний ключ у всіх розкладках (56 пар знайдено перейменуваннями git
  між сусідніми тегами — `git diff -M` — і звірено назвами сторінок; міграції 0.3.24 однією сторінкою і «Performance
  optimizing» до розбиття лишаються окремими), а родина `docs` — одне місце у видачі на розділ. Спільних ключів між
  джерелами різних родин немає.
- **Адреси.** Сторінка 1.x веде на typeorm.io, сторінка 0.3.25–0.3.31 — на v0.typeorm.io (обидва набори адрес звірено:
  77 і 66 сторінок відповідають 200), решта — на файл GitHub на тезі. Номери на початку імен файлів (`1-entities.md`)
  Docusaurus в адресах не показує: `/docs/entity/entities/`.
- **Вкладки баз.** З 1.0 рівні ізоляції транзакцій і план запиту показано вкладками власного компонента
  `<DatabaseTabs>`; новий читач `ghdocs-history-typeorm` дає кожній вкладці назву бази («PostgreSQL:», «MySQL:»,
  «SQLite:»), бо `docusaurus_tabs` знає лише `<Tabs>`/`<TabItem>`, і знімає імпорт MDX на кількох рядках, через який
  назвою сторінки ставало ім'я файла.
- **Зміст плоских сторінок.** Сторінки 0.1–0.3.24 починаються переліком посилань на власні розділи (у `entities.md` —
  25 пунктів); він знімається (`drop_toc`), інакше вступом документа ставав короткий фрагмент з назвами всіх розділів.
- **Код поділено на методи.** Код TypeORM має відступ у чотири пробіли й рядки без «;». Нові поля читача
  `ghcode-history-ts`: `indent: 4` — член класу на чотирьох пробілах стає розділом («EntityManager.findOne()»),
  `join_same` — перевантаження (`export function Column(): PropertyDecorator`, `async transaction<T>(…)`) зливаються з
  реалізацією в один розділ. Без них клас EntityManager був одним розділом на сотні рядків. Файли до 400 КБ
  (`max_file`): `PostgresQueryRunner.ts` у 1.1.2 має 205, найбільший — 351 (`driver/mongodb/typings.ts`, копія типів
  драйвера mongodb).
- **Переїзд у монорепозиторій.** З 1.1.2 код і тести лежать у `packages/typeorm/src` і `packages/typeorm/test`;
  правило `slug_rewrite` `^packages-typeorm-` дає їм ті самі ключі, що й до переїзду.
- **Журнал змін.** Записи 0.2.23 і 0.2.24 стоять під одним заголовком («## [0.2.23](…), [0.2.24](…)»): нова група `w`
  читача `changelog-regex` дає документу обидві версії. 0.3.31 вийшла з гілки 0.3 після 1.0.0, і в журналі `master` її
  немає — її зміни дають реліз GitHub. Релізи на GitHub ведуться з 0.2.35.
- **README з тегу, а не з tarball.** Tarball typeorm важить 2–3 МБ, усіх 115 — понад 300 МБ заради одного файла.
  README кореня репозиторію на коміті публікації — той самий текст: збирання пакета лише міняє мову блоків коду з
  typescript на javascript. Чотири версії без тегу й без `gitHead` (0.0.1, 0.1.11, 0.1.20, 0.1.21) — з tarball;
  `slug_rewrite` дає їм той самий ключ.

## Версії у відповіді

Фільтр `version` бере лінію: `"0.3"` — усе 0.3.x, `"1.1"` — 1.1.x, `"0.2.45"` — один випуск (`version_line_depth` 2).
Документація, README, код, тести, журнал і релізи несуть кожен випуск, де текст був саме таким. `@typeorm/codemod` має
мітку `codemod-` (`"codemod-1.0.3"`: на всіх тегах 1.x пакет має версію 1.0.3), `@typeorm/legacy-naming-strategies` —
`legacy-naming-strategies-`; голе `"1.0"` їх не бере. Без фільтра сторінка, що є в кількох версіях, показується один
раз — найновішою редакцією.

Без названої версії промпт велить відповідати для обох ліній: 0.3 (0.3.31 — найпопулярніша за завантаженнями npm) і
1.1 (1.1.2 — найновіша), і казати, де вони розходяться: між ними несумісні зміни 1.0.

## Сховище сирого

Під час оновлення примірник тримає ще й сирі відповіді — у теці `raw/`, поза git (сховище ввімкнене за замовчуванням).
Правка читача тоді не вимагає нового завантаження: `./df typeorm build` збирає тексти зі сховища без мережі. Код і
тести кладуть у сховище з голого клону (`tools/seed_git_store.py`), а не тягнуть мережею: 18 714 файлів — за хвилину.
Між оновленнями сховище, як і тексти, лежить лише в архіві: серверу воно не потрібне. Устрій — у
[../../UPDATE.md](../../UPDATE.md), розділ про `refresh`.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку: у `corpus/` лежить лише паспорт `index.json`, а сервер підіймається з
кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш тримає повний текст
кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/typeorm-corpus-2026-10-19.tar.gz` (19 759 текстів, паспорт і сховище
сирого `raw/`; перед видаленням текстів розпакований окремо й звірений із диском — нуль розбіжностей). В історії git
текстів немає ніде. Архів лежить лише на цій машині. Сховище `raw/` після звірки теж видалено з диска.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/typeorm/index/passages.json  # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/typeorm-corpus-РРРР-ММ-ДД.tar.gz -C instances/typeorm corpus raw
find instances/typeorm/corpus -maxdepth 1 -name '*.txt' -delete
rm -rf instances/typeorm/raw
gzip -9 -c instances/typeorm/index/passages.json > instances/typeorm/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти й сховище — лише після того, як
архів звірено з диском.

**Як повернути тексти** — перед будь-яким оновленням корпусу; разом із ними повертається й сховище `raw/`:

```
tar -xzf ~/archives/docfactory/typeorm-corpus-2026-10-19.tar.gz -C instances/typeorm
./df typeorm smoke
```

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/typeorm/index/passages.json.gz`, далі
`./df typeorm vectors` заллє колекцію Qdrant (півтори години на процесорі: 5 281 с).

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df typeorm serve       # порт 8868
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8868/mcp`. Сервер тримає в пам'яті
близько 1 ГБ і підіймається з кешу за пів хвилини.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно. У WSL:

```
claude mcp add --transport http --scope user typeorm-docs http://127.0.0.1:8868/mcp
```

У Windows — та сама команда в PowerShell: Claude Code тримає окремі налаштування для WSL і для Windows (вікно VS Code
на боці Windows читає `C:\Users\<ім'я>\.claude.json`); або кнопка «Add server» у вікні `/mcp` (тип HTTP, рівень User).
Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт. Інший шлях — запис `.mcp.json` цієї теки: Claude
Code, відкритий у ній, побачить сервер сам.

**3. Перевірити.** `/mcp` — має бути `typeorm-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію Claude
Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і «Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Якщо порт 8868 зайнятий, `serve` падає з «address already in use»: значить,
сервер уже піднято в іншому терміналі. Решта — scope запису — так само, як у [README примірника
nestjs](../nestjs/README.md#спосіб-б--сервер-під-claude-code-http).
