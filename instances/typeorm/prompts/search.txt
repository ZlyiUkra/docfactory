CockroachDB, MySQL, MariaDB, SQLite, better-sqlite3, Microsoft SQL Server, Oracle, SAP HANA, Google
Spanner, MongoDB, sql.js, Capacitor, Cordova, Expo and React Native -- and return the matching excerpts
with the versions each one belongs to. Here: the documentation of every stable release, taken from the
repository at each release tag -- the typeorm.io site of 1.0.0-1.1.2, the v0.typeorm.io site of
0.3.25-0.3.31 and the docs/*.md pages of 0.1.0-0.3.24 (entities and columns, embedded entities,
inheritance, tree and view entities, EntitySchema, relations, eager and lazy relations, DataSource and
its options for every driver, Connection and ormconfig before 0.3, multiple data sources and
replication, EntityManager and Repository with their full API, find options, custom repositories,
the select, insert, update, delete and relation query builders, caching, migrations and the CLI,
transactions and isolation levels, indexes, listeners and subscribers, logging, naming strategies,
the per-database driver pages, performance, the decorator reference, FAQ, the 1.0 release notes and
the upgrading guide from 0.3, the roadmap and the blog); the README of every stable npm release from
0.0.1; CHANGELOG.md and the GitHub release notes; the source code src/ with its JSDoc and the tests of
every stable tag from 0.0.2 to 1.1.2; the @typeorm/codemod package that rewrites 0.3 code for 1.0 and
@typeorm/legacy-naming-strategies; the npm version table of each package.

Call this when a question is about TypeORM itself -- how to declare an entity, a column type and its
options (nullable, default, unique, length, transformer, generated), primary and generated columns,
relations (@OneToOne, @ManyToOne, @OneToMany, @ManyToMany, @JoinColumn, @JoinTable, cascade,
onDelete), DataSource options, find and findOne with where, relations, select, order, skip and take,
FindOperators (In, Like, ILike, Between, IsNull, Raw), createQueryBuilder with joins, subqueries and
getRawMany, upsert, soft delete, transactions, QueryRunner, migrations (migration:generate,
migration:run, migration:revert), synchronize, subscribers, what a decorator or method does in a
version, what an error means -- and above all history: since which version something exists, what
changed, what was renamed or removed in 1.0 and how to upgrade.
Example query: "createQueryBuilder leftJoinAndSelect".

Do not call this for the database servers themselves (postgresql-docs, sqlserver-docs, mongodb-docs),
for raw client drivers (node-postgres-docs), for other ORMs (prisma-docs, drizzle-docs, mongoose-docs),
or for the NestJS integration module @nestjs/typeorm (nestjs-docs).

Write the query in English, with the names TypeORM uses (DataSource, EntityManager, Repository,
createQueryBuilder, leftJoinAndSelect, findOneBy, @Entity, @Column, @PrimaryGeneratedColumn,
@ManyToOne, @JoinColumn, migration:generate, QueryRunner, Transaction). Everything here is English,
and the word index keeps only latin letters and digits, so a query written in Ukrainian, Russian or
any other non-latin script matches nothing and comes back with `found: 0`. When the user asks in
another language, translate the question into TypeORM's terms first, then search.

Which version to answer for. Every answer says which version it is for. When the user did not name a
version, answer for both lines in use: 0.3 (0.3.31, the most downloaded) and 1.1 (1.1.2, the newest)
-- search each of them (`version` "0.3", then "1.1") and say where they differ: 1.0 (May 2026)
removed and renamed much of 0.3 (Connection, ormconfig, findByIds, the old naming of constraints and
more; see the upgrading guide), so an answer for one line can be wrong for the other. When the
excerpts behind a statement come only from older versions, name those versions instead of
presenting the text as current. Put a version only into `version`, never into the query text: "0.3"
keeps the whole 0.3 line, "0.3.20" one release. Documentation, README, code, tests, CHANGELOG and
release notes are marked by every release they belong to; @typeorm/codemod carries the prefix
"codemod-" ("codemod-1.0.3") and @typeorm/legacy-naming-strategies "legacy-naming-strategies-", so
their numbers are never confused with TypeORM's. A site page is named after its path
("docs-docs-entity-1-entities", "docs-docs-working-with-entity-manager-3-find-options"), a page of
0.1-0.3.24 the same way once renamed ("docs-entities" became the first), a source file after its
path ("src-entity-manager-entitymanager-ts"), a test after its path, a CHANGELOG entry by version
("changelog-0.3.0"). Pages that differ per database show each database under its own label
(PostgreSQL:, MySQL:, SQLite:): give the one the user asked about.

Answer in the language the user wrote in. When the question is about a feature's history or support,
answer point by point: since which version it exists; what changed in later versions; and how it
stands now -- recommended, deprecated, or removed and replaced by what. Every point names the version
and the document it rests on; a point the excerpts do not support is left out, not guessed. When
that language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from English:
plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"сутність", "зв'язок", "міграція схеми", not "мігрейшн"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація TypeORM". Identifiers, decorators, options
and titles stay in English, spelled exactly as the documentation spells them. Build the answer out of
the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before
describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version` is
optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text; "meaning+words" means a second, meaning-based index answered as
well, and a paraphrase had a chance.
