# typescript — примірник фабрики docfactory

Дванадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про TypeScript за офіційною
документацією всіх його версій — текстом сайту typescriptlang.org на кожен стабільний реліз від 1.4 (2015) до поточної
7.x, README кожної версії npm (зокрема нічних збірок, beta, rc й insiders), нотатками релізів, README й `CHANGES.md`
нативного порту `typescript-go` і реєстром версій npm. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо вся історія

TypeScript щомісяця-два випускає мінорну версію, і кожна щось додає до мови чи компілятора: `satisfies` — у 4.9,
декоратори стандарту — у 5.0, `moduleResolution: bundler` — у 5.0, `isolatedDeclarations` — у 5.5. У 6.0 частину
старих опцій прибрано, а 7.0 — це вже компілятор, переписаний на Go. Проєкти ж живуть на різних лініях: 28.09.2026
лінія 5 тримає 62,5% завантажень, 6 — 17,4%, 7 — 11,8%, 4 — 5,6%. Тож питання звучить «чи є це в моїй версії», «з
якої версії», «що замінило» — і відповідь дає лише документація саме тієї версії та release notes, що називають
версію точно.

| Шар | Документів | Звідки |
|-----|-----------:|--------|
| Текст сайту на кожен стабільний реліз: кожен неповторний текст файла один раз, з усіма версіями, де він був таким | 1 886 | `microsoft/TypeScript-Handbook` (566), далі `microsoft/TypeScript-Website` (1 320) |
| README кожної версії npm, зокрема нічних, beta, rc й insiders; однакові тексти зведено | 55 | README репозиторію на коміті публікації |
| Нотатки релізів | 218 | GitHub API, `microsoft/TypeScript` |
| Реєстр версій npm: огляд і по документу на лінії 0–7 | 9 | `registry.npmjs.org/typescript` |
| `typescript-go`: останній коміт з README і `CHANGES.md`, нотатка релізу 7.0.2 | 2 | GitHub API, `microsoft/typescript-go` |

Разом 2 170 документів; фрагментів в індексі — 8 874 (`expected_passages` у `checks.json`). Фрагменти — це
шматки документів між заголовками, по яких іде пошук; незмінні розділи різних редакцій зливаються в один
(`revision_suffix`).

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 2 із 10, за
змістом 5, разом 4; друга, «як модель» (назвами з документації, з `version "5"`, для порту на Go — `"7"`, як велить
промпт), — 9 із 10. Цілі — сторінки обох епох сайту: і `packages-documentation-copy-en-…`, і `pages-…` з
TypeScript-Handbook, бо для старшої версії правильна відповідь саме там. Промахи:

- **Своїми словами без назв.** «Розбити кодову базу на частини, що збираються окремо» не знаходить project
  references, «що поводиться інакше в компіляторі на Go» — `CHANGES.md` порту: слова питання й документації не
  перетинаються. Тому промпт велить писати запит назвами; друга десятка з ними влучає 9 разів.
- **Єдиний промах другої десятки** — «declaration files d.ts library»: місця зайняли шаблони `.d.ts` для бібліотек
  різної будови (`declaration-files-templates-…`). Вони теж про declaration files, але ціллю їх не дописано: це
  була б підгонка заміру під видачу.
- **Сторінки опцій tsconfig не можуть бути ціллю.** Сторінка на опцію не має жодного заголовка, тож в індексі вона —
  один розділ без назви, а `smoke` рахує ціллю лише розділ із назвою. Шукаються такі сторінки нормально (на
  `strictNullChecks` вона перша у видачі); ціль для опції — розділи handbook і release notes, що її описують.

**Версія у відповіді.** Кожна відповідь каже, для якої версії вона. Якщо користувач версії не назвав, модель
відповідає для лінії за замовчуванням 5.x, пише це прямо й пропонує назвати свою версію; якщо для 6 чи 7 відповідь
інша — дає і її. Текст, знайдений лише в старших версіях, подає з цими версіями.

## Що в цій теці

- `corpus/` — документація звичайними текстовими файлами; поруч `index.json` — паспорт, тобто опис копії: адреса,
  дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Епохи сайту лежать тут, у полі
  `eras` джерела `ts-site`; версії для знімків, README й реєстру приходять з реєстру npm.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df typescript <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| текст сайту на кожен стабільний реліз | гілка репозиторію сайту на мить перед наступним релізом, текст — `raw.githubusercontent.com` | `ghsite-dated` |
| README усіх версій npm | реєстр npm (версії й коміти публікації), текст — `raw.githubusercontent.com` | `npm-readme` |
| нотатки релізів TypeScript і typescript-go | GitHub API | `ghreleases` |
| реєстр версій | опис пакета в реєстрі npm | `npm-versions` |
| README і `CHANGES.md` typescript-go | останній коміт репозиторію через GitHub API | `ghcommit` |

Нових читачів цей примірник не додав. Читач `ghsite-dated` дістав необов'язкове поле `only` — вираз версій, на які
робляться знімки: без нього пакет з ~3 500 нічними збірками дав би знімок сайту на кожну ніч.

Особливості, які варто знати:

- **Сайт не має версійних тегів.** Документація живе окремо від компілятора, тож на кожен стабільний реліз npm
  береться стан гілки сайту на мить перед наступним релізом тієї ж лінії. Нічні збірки, beta, rc й insiders знімків
  не мають — їх несуть README і реєстр npm.
- **Дві епохи сайту.** До 01.08.2020 — репозиторій `microsoft/TypeScript-Handbook`, тека `pages/` (нині архівний),
  назви документів `pages-…`. Далі — `microsoft/TypeScript-Website`, гілка `v2`: handbook (v1 і v2), reference,
  modules reference, declaration files, project config, release notes, tutorials, довідник опцій tsconfig (сторінка
  на опцію), handbook пісочниці й глосарій; назви `packages-documentation-copy-en-…`,
  `packages-tsconfig-reference-copy-en-options-…`.
- **Релізи 0.8–1.4.0 знімка сайту не мають:** вони вийшли до квітня 2015, коли репозиторію Handbook ще не було.
  Перша версія зі знімком — 1.4.1. Що змінилося в тих версіях, розповідають release notes.
- **Release notes — головне джерело «з якої версії».** Сторінка на кожну мінорну версію від 1.1, у обох епохах.
- **README — з коміту публікації.** Реєстр npm для кожної версії пише коміт, з якого її опубліковано (`gitHead`), і
  README береться з репозиторію на цьому коміті, а де коміту в реєстрі нема — з тегу релізу. Версії 7.0.1-rc, 7.0.2
  і нічні 7.1 за 07–19.08.2026 опубліковано з комітів `typescript-go`, тож їхній README — з того репозиторію.
  Без README лишилися 56 версій: beta й rc 3.4–5.4 (реєстр не записав коміт, а теги `v5.0-beta` на шаблон
  `v{version}` не лягають) і 0.8–1.0.1 — їхній текст майже напевно той самий, що в сусідніх релізів.
- **Версія нотатки релізу — з тегу.** Теги TypeScript бувають без третього числа: `v5.0-beta` дає версію
  `5.0-beta`, `v1.4` — `1.4`. Фільтр `version: "5"` їх знаходить, а `"5.0"` — ні: межа сегмента там «5.0.».
  Тестовий реліз `vsix-test/v0.0.0` з `typescript-go` відкинуто полем `skip`.
- **TypeScript 7 і `typescript-go`.** Нативний порт на Go розробляли в окремому репозиторії; після релізу 7.0
  розробка повернулася в `microsoft/TypeScript`, а `typescript-go` закрито й архівовано. Звідти взято README
  (прев'ю `@typescript/native-preview`, `tsgo`) і `CHANGES.md` — чим порт відрізняється від 5.x/6.x. Джерело
  заморожене (`frozen`). Дерево цього репозиторію GitHub віддає обрізаним, тому читач — `ghcommit`, а не `ghdocs`.
- **Лише англійська.** Переклади сайту не беруться.
- **Редакції того самого файла зливаються (`revision_suffix`)**: ім'я документа несе хеш вмісту, і без поля
  незмінний розділ двох редакцій лишався б двома фрагментами.

## Межі, про які треба пам'ятати

Тут немає документації JavaScript (для мови — примірник `ecmascript`), Node.js, фреймворків і збирачів,
typescript-eslint і пакетів типів DefinitelyTyped (`@types/…`). Блог devblogs.microsoft.com/typescript і Bluesky
свідомо не взято: анонси повторюють release notes. Нічні збірки, beta, rc й insiders — не релізи: текст, що є лише в
них, міг так і не вийти, і промпт велить моделі казати про це прямо.

## Установка venv

```
cd instances/typescript
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df typescript sources --why   # перелік джерел і білий список
./df typescript refresh         # завантажити все задеклароване (кілька годин, див. UPDATE.md)
./df typescript manifest        # оновити паспорт
./df typescript setup           # Qdrant чи пошук лише по словах
./df typescript vectors         # залити корпус у docs-typescript
./df typescript smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df typescript serve          # порт 8772
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8772/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user typescript-docs http://127.0.0.1:8772/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `typescript-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df typescript setup --vectors      # з Qdrant: потрібен Docker
./df typescript setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

Без векторів сервер працює так само, лише перефразоване питання, що не має спільних слів із документацією, може не
знайтися. Перейти на вектори можна будь-коли тією самою командою з `--vectors`.

**4. Перевірка, сервер, клієнт.**

```
./df typescript smoke          # усі перевірки мають бути ok
./df typescript serve          # порт 8772, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
