# Оновлення корпусу typescript

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **усі версії приходять із npm самі.** Перелік версій для знімків сайту (`ts-site`), README
(`ts-readme`) і реєстру (`ts-npm`) береться з реєстру npm на кожному прогоні: новий стабільний реліз дістає свій
знімок сайту, а нова нічна збірка, beta чи rc — свій README і рядок у реєстрі, без правки `sources.json`.

Друге правило: **новий реліз змінює й старі документи.** Документ — неповторний текст файла, а в рядку `# версія:`
стоять усі версії, де файл був саме таким. Тому `ts-site`, `ts-readme` і `ts-npm` перезаписуються цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх
не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Документ, що після нового релізу вже нікому не належить, лишається в `corpus/`; прибрати його — рішення людини.

Четверте: **`list` і `refresh` з назвами джерел однаково складають перелік усіх джерел** — назви обмежують лише
запис. Перелік `ts-site` гортає всю історію комітів сайту, а `ts-readme` читає README кожної з ~3 800 версій, тож
навіть «перевірити одне дрібне джерело» так триває годину. Щоб звернутися лише до названих джерел, є
`refresh --missing <id>`: він і перелік складає тільки для них.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Якщо вийшла нова мажорна лінія, що стане основною** (скажімо, 7.x обійде 5.x за завантаженнями):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзац «Which version to search first») та
  `prompts/agent.txt` велять на питання «як зараз» шукати з `version "5"`;
- у `checks.json`, у десятці `quality_model`, замінити `"5"` на нову лінію там, де питання про поточну поведінку.

**Крок 2. Якщо документація сайту переїхала** в іншу теку чи репозиторій — додати новий вираз у `include` останньої
епохи джерела `ts-site`, або нову епоху (попередній дописати `before`); якщо README пакета переїхав — додати шаблон
шляху в поле `files` джерела `ts-readme`.

**Крок 3. Завантажити.** Одне джерело за раз — машина важко переносить паралельні прогони:

```
./df typescript sources --why
./df typescript refresh ts-releases ts-npm       # хвилини, але перелік складається для всіх джерел
./df typescript manifest
./df typescript vectors
./df typescript smoke
# Ctrl+C у терміналі з serve, і знову: ./df typescript serve
```

`refresh` без назв — повне перезавантаження, кілька годин. Корпус не комітиться: після оновлення пишуть новий архів
і знову виносять тексти (README, розділ «Архівний режим»), а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього історія комітів сайту й дерева
знімків ідуть годинними вікнами по 60 звернень.

**Крок 2. По джерелу, від легкого до важкого,** з `--missing` і журналом без буфера — інакше журнал мовчить до
кінця:

```
PYTHONUNBUFFERED=1 ./df typescript refresh --missing ts-releases ts-npm tsgo-docs tsgo-releases > /tmp/ts-1.log 2>&1
PYTHONUNBUFFERED=1 ./df typescript refresh --missing ts-site   > /tmp/ts-site.log 2>&1     # ~50 хвилин
PYTHONUNBUFFERED=1 ./df typescript refresh --missing ts-readme > /tmp/ts-readme.log 2>&1   # ~1,5 години
```

Спершу `ts-site` мовчить, а файлів не прибуває: читач гортає історію комітів обох репозиторіїв сайту й дерева
знімків, і лише потім пише. Стан видно за кількістю файлів: `ls instances/typescript/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть ту саму команду: з `--missing` уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df typescript quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія — 5.** `prompts/search.txt` (абзац «Which version to search first») і `prompts/agent.txt` велять
  на питання «як зараз» шукати з `version "5"`. Лінію за замовчуванням звірити із завантаженнями `typescript` (пункт
  3 кроку 7): 28.09.2026 лінія 5 — 62,5%, 6 — 17,4%, 7 — 11,8%, 4 — 5,6%. Поки 6 і 7 тримають помітну частку,
  промпт велить при різних відповідях давати і їх.
- **Правила промпту, що вже є:** спершу лінія 5, без версії — лише історія; запит — назвами, як їх називає
  документація; кожна відповідь каже, для якої версії вона, а без названої версії — відповідає для 5.x і пропонує
  назвати свою; текст, що є лише в нічних, beta, rc чи insiders, міг не вийти релізом — казати про це.
- **Останній результат:** у README, абзац «Замір `quality`».
