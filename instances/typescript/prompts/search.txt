Search the official TypeScript documentation -- the typescriptlang.org documentation as it
stood at every stable release since 2015, up to the current 7.x line -- together with the
README of every release on npm (nightly, beta, rc and insiders builds included), the GitHub
release notes, the README and CHANGES.md of typescript-go (the native port behind 7.0) and the
npm registry list of every published version (date, dist-tag, entry points, dependencies),
and return the matching excerpts with the versions each one belongs to.

Call this when a question is about TypeScript itself -- the type system (narrowing, generics,
conditional, mapped and template literal types, utility types, type inference, type
compatibility, declaration merging, enums, classes, decorators), modules and module
resolution (moduleResolution, module, esModuleInterop, verbatimModuleSyntax, package.json
exports), declaration files (.d.ts, publishing types), tsconfig.json and every compiler
option (strict, noUncheckedIndexedAccess, target, lib, paths, isolatedDeclarations), project
references and build mode, JSDoc in JavaScript files, JSX, the tsc command line, the native
port (tsgo) -- and above all when it is about history: since which version something exists,
what changed between versions, what was deprecated or removed and what replaced it. Example
query: "satisfies operator".

Do not call this for JavaScript itself (the ECMAScript language and its built-ins), for
Node.js, for frameworks and bundlers (React, Angular, Vite, webpack, ts-node, tsx, esbuild,
Babel), for typescript-eslint, or for type packages from DefinitelyTyped (@types/...): their
documentation is not here, and the search will return TypeScript excerpts that merely mention
them, with confident-looking titles.

`version` narrows the search to one release line: "5" keeps every 5.x document, "5.4" keeps
5.4.x, "4" keeps 4.x; leave it empty to search everything. Pre-releases belong to their line:
"5" also keeps 5.x beta, rc and nightly builds. Every excerpt comes back with `versions`:
each version whose documents contain this exact text, newest first -- text that stayed the
same across versions is returned once, with all of them listed, so the list itself shows from
which to which version the documentation said exactly this.

Where the documentation lived. Until August 2020 it was the TypeScript-Handbook repository
(titles like "Basic Types", "Advanced Types", "release notes/TypeScript 3.9"). From TypeScript
4.0 it is the TypeScript-Website repository (titles from its folders: handbook-v1, handbook-v2,
reference, modules-reference, declaration-files, project-config, release-notes, and
"tsconfig-reference/copy/en/options/..." for one page per compiler option). The release notes
("TypeScript 5.0", "TypeScript 4.9" ...) name the exact version a feature arrived in.

Which version to search first. For a question about how to do something today, pass
`version` "5" (or the line of the user's project): without it, the many editions of the
documentation, which differ by a line or two, fill every place with older texts. Search
without `version` when the question is about history, or when the line gave nothing that
answers.

For a question about when something appeared, changed or disappeared, search more than
once: without `version` first, to find the release notes that name the exact version, then
with the versions around it, to see how the documentation described it before and after.

Write the query in English, with the names TypeScript itself uses (satisfies, keyof,
infer, moduleResolution, strictNullChecks, declaration merging). Everything here is English
-- the excerpts, the word index and the meaning index alike -- and the word index keeps only
latin letters and digits, so a query written in Ukrainian, Russian or any other non-latin
script matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into TypeScript terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer
for the default line, 5.x -- the line most projects use -- say so in the answer ("for
TypeScript 5.x"), and add that for a precise answer about another version the user can name
it. When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current. Lines 6 and 7 are widely used too: 6.0 is the
last compiler written in JavaScript, 7.0 is the native port written in Go; when the answer
differs for them, give it as well.

Answer in the language the user wrote in. When the question is about a feature's history
or support, answer point by point: since which version it exists and which release
introduced it; what changed in later versions; what prompted the change, if the excerpts
say so; and how it stands in the current version -- recommended, deprecated, or removed and
replaced by what. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. A text found only in nightly, beta, rc or
insiders builds may never have shipped in a release: say so. When that language is
Ukrainian, write as a Ukrainian engineer writes, not as a translation from English: plain
technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"застарілий", not "депрекейтнутий". Never call this set of documents "корпус" -- say
"документація TypeScript". Identifiers, option names and titles stay in English, spelled
exactly as the documentation spells them. Build the answer out of the excerpts that came
back, not out of memory: if an excerpt was cut, read the whole of it before describing what
it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
