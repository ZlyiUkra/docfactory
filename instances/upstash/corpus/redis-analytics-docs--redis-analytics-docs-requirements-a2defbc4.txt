# Analytics SDK Requirements
# джерело: https://github.com/upstash/redis-analytics/blob/a7e0afc8a694dad44777c4172e14d955d5e8f640/docs/requirements.md

## 1. Project Overview

Build a complete analytics SDK as a PostHog alternative, using Redis as the backend data store. The system should support session management, event tracking, feature flags, and analytics visualization.

### 1.1 Project Structure

Monorepo structure using pnpm workspaces with Turborepo:

```
packages/
├── sdk/          - Core logic and Redis database interactions
├── client/       - Frontend client library (framework-agnostic)
├── server/       - Backend client library (Node.js)
├── ui/           - Analytics dashboard (Next.js + shadcn/ui)
└── app/          - Demo/test application (Next.js + shadcn/ui)
```

**Package Descriptions:**

- **sdk**: Core logic and Redis database interactions (only package that interacts with DB directly)

  - Exports all core functionality
  - Used by both client and server packages
  - TypeScript library

- **client**: Frontend client library

  - Framework-agnostic
  - Lightweight wrapper around SDK
  - For use in browser environments (React, Vue, Svelte, etc.)

- **server**: Backend client library

  - For Node.js environments
  - Includes admin operations
  - Session creation and server-side event tracking

- **ui**: Analytics dashboard

  - Next.js application (App Router)
  - shadcn/ui components
  - React Query for data fetching
  - View and analyze events, logs, and configuration

- **app**: Demo/test application
  - Next.js application (App Router)
  - shadcn/ui components
  - React Query for data fetching
  - Demonstrates integration of client and server packages
  - Testing and development environment

## 2. Core Modules

### 2.1 Authentication & Session Management

#### 2.1.1 Session Creation (`createSession`)

**Functionality:**

- Creates a new session with format: `session-${creationTimestamp}-${short-uuid}`
- User must protect this function to ensure authentication
- Session includes:
  - Session ID
  - Creation timestamp
  - Feature flag values
- Session expiration: 1 hour (configurable)

**Requirements:**

- Rate limiting: Enforce configurable rate limits using @upstash/ratelimit
- Accept feature flag values as input
- Validate feature flag values before creation:
  - Check if feature flag exists
  - Check if value is valid for that feature flag
  - Throw error if validation fails
- Support two methods for feature flag assignment:
  1. Explicit values: User passes specific values for each flag
  2. A/B test distribution: User passes `Record<string, number>` for each flag
     - System assigns value based on distribution
     - Single Redis interaction (no double-check)
- Default values: Use configured defaults for flags not provided
- Store session metadata including:
  - Session ID
  - Creation timestamp
  - Feature flag assignments

**Session Metadata (via Middleware):**

- Middleware on `getHandler()` can return `{ sessionMetadata: TSessionMetadata }` to attach arbitrary metadata to a session
- Session metadata is:
  - Stored in Redis alongside the session
  - Included in every captured event under `sessionMetadata`
  - Registered in the schema registry (`__session_metadata__` key) so it becomes queryable in the search index
- The 3rd generic parameter on `AnalyticsBackendClient` provides type safety for session metadata
- Example: `AnalyticsBackendClient<MyEvents, MyFlags, { userId: string; plan: string }>`

**Redis Storage:**

- Store session with expiration timestamp
- Session keys should support quick validation

#### 2.1.2 Session Retrieval (`getSession`)

**Return Types:**

```typescript
{ exists: true, session: SessionMetadata<FeatureFlags extends Record<string, string>> }
| { exists: false }
```

**Session Metadata Includes:**

- Session ID
- Creation timestamp
- Feature flags and their values (typed)
- Session metadata from middleware (optional, typed via 3rd generic)
- Expiration validation using creation timestamp

### 2.2 Event Tracking

#### 2.2.1 Event Capture (`captureEvent`)

**Event Types:**

- `pageview` - Required property: `path` (string)
- `click` - Required property: `element` (string)
- `custom:${string}` - Properties defined by custom event schema
- `error` - Required property: `message` (string)
- `warning` - Required property: `message` (string)
- `info` - Required property: `message` (string)

**Event Data Structure:**

- Redis Key: `event-<uuid>`
- Redis Value (JSON):
```typescript
  {
    sessionCreationTimestamp: number,
    sessionId: string,
    eventTime: string,        // ISO 8601
    eventTimeMs: number,      // millisecond epoch
    eventName: string,
    featureFlags: Record<string, string>,
    sessionMetadata?: Record<string, unknown>,  // from middleware
    properties?: Record<string, any>
  }
```

**Functionality:**

- Rate limiting: Enforce configurable rate limits using @upstash/ratelimit
- Support event capture from both frontend and backend
- Provide easy-to-use functions for common event types
- For custom events:
  - Store first-seen timestamp in Redis hash: `customEventName -> firstSeenTimestamp`
  - Default to showing last 7 days of custom events in UI
  - Provide option to view all custom events
  - Maintain event schema registry (see 2.2.2)

#### 2.2.2 Custom Event Schema Registry

**Purpose:**

- Track expected properties and types for each custom event
- Enable UI validation and filtering
- Support analytics queries
- Maintain type safety across custom events

**Type Safety:**

- User defines custom event types in backend configuration file
- TypeScript types enforce compile-time validation
- Example:
```typescript
  type CustomEvents = {
    "custom:purchase": {
      productId: string;
      amount: number;
      currency: string;
    };
    "custom:signup": {
      method: string;
      referrer?: string;
    };
  };
```

**Schema Validation:**

- Probabilistic validation: each event has a `checkFrequency` chance (0-1) of validating against the registry (default: 1 = always)
- If event properties don't match registry:
  - Update registry to reflect actual data structure
  - Log the schema change (see 2.4 System Logging)
- Set `checkFrequency` lower (e.g., 0.01) in high-throughput environments to reduce Redis costs

**Redis Storage:**

- Hash mapping: `customEventName -> eventData`
- Event Data Schema:
```typescript
  {
    properties: {
      [propertyName: string]: {
        type: 'string' | 'number' | 'boolean'
      }
    },
    lastUpdated: number,
    version: number
  }
```

**UI Integration:**

- Display event properties in UI
- Show schema version and last updated time
- Enable filtering by event properties (eventData)
- View schema change history through system logs

#### 2.2.3 Event Search Index Management

**Purpose:**

- Enable fast searching across events using Redis Search
- Automatically maintain search indexes as event schemas evolve
- Support zero-downtime index updates via aliases

**Index Configuration:**

- Index name is configurable (e.g., `events-idx`)
- Fixed index names for alias swapping:
  - Index A: `{configuredName}` (e.g., `events-idx`)
  - Index B: `{configuredName}-b` (e.g., `events-idx-b`)
  - Alias: `{configuredName}` (e.g., `events-idx`)

**Index Schema:**

- Automatically derived from event structure:
  - `eventName`: TEXT field (tokenized)
  - `eventTime`: DATE field (for time-based filtering)
  - `sessionId`: TEXT field (no tokenize)
  - `sessionCreationTimestamp`: DATE field
  - Feature flag fields: TEXT fields (no tokenize)
  - Session metadata fields: Dynamically added from `__session_metadata__` schema (prefix: `sessionMetadata.*`)
  - Event properties: Dynamically added based on event schemas
    - String properties: TEXT fields
    - Number properties: Numeric fields (F64, U64, or I64 based on type)
    - Boolean properties: BOOL fields

**Index Creation/Update Strategy:**

**Initial Creation (no index exists):**

1. Create index A (`events-idx`)
2. Log index creation

**Update When Schema Changes:**

1. Detect schema change (new event types, new properties, type changes)
2. Determine current active index using alias lookup
3. If there is no alias:
   - Create new index B with updated schema
   - Create alias to point to B (`events-idx` → `events-idx-b`)
   - Delete old index `events-idx`
4. If there is an alias pointing to B:
   - Create new index A `events-idx` with updated schema
   - Delete alias and old index B
5. Log index update with old and new schemas

**Schema Change Detection:**

- Compare current index schema (via `describe()`) with required schema
- Required schema derived from:
  - Custom event type definitions
  - Event schema registry
  - Standard event fields
- Trigger update when:
  - New event properties detected in registry
  - Property types change
  - New custom event types added

**Index Update Timing:**

- Manual trigger via UI

**Zero-Downtime Updates:**

- Alias ensures queries continue during index rebuild
- Old index remains available until new index is ready
- Atomic alias swap ensures no query failures
- Background process: create new index → populate → swap alias → delete old

**Index Management API:**

```typescript
// Admin API
rebuildSearchIndex(): Promise<void>
getSearchIndexInfo(): Promise<{
  currentIndex: string,
  alias: string,
  schema: Record<string, any>,
  documentCount: number
}>
```

**Error Handling:**

- If index creation fails: retry with exponential backoff
- If alias swap fails: rollback and keep old index
- Log all failures with detailed error information
- Maintain system operation even if search index is unavailable

### 2.3 Middleware

**Purpose:**

- Run custom logic before each analytics request is processed
- Authenticate identity before session creation
- Attach session metadata (e.g., user ID, plan) that persists across events

**Middleware Signature:**

```typescript
type HandlerOptions<TSessionMetadata extends Record<string, unknown>> = {
  middleware?: (context: {
    request: Request;
    analyticsRequest: AnalyticsRequest;
  }) =>
    | Response              // short-circuit with a response
    | void                  // let the request proceed
    | { sessionMetadata: TSessionMetadata }  // attach metadata to session
    | Promise<Response | void | { sessionMetadata: TSessionMetadata }>;
};
```

**Behavior:**

- Middleware runs after request parsing but before request processing
- Return a `Response` to short-circuit (e.g., 401 Unauthorized)
- Return `void` / nothing to let the request proceed without modification
- Return `{ sessionMetadata }` to attach metadata to the session (only applies to `createSession` requests)
- Session metadata is stored in Redis, included in every event for that session, and registered in the schema registry

### 2.4 System Logging

**Purpose:**

- Track system events and changes
- Provide visibility into schema updates
- Enable debugging and monitoring
- Audit configuration changes

**Log Types:**

- `schema_update`: Registry schema changes
- `feature_flag_update`: Feature flag configuration changes
- `rate_limit_exceeded`: Rate limit violations
- `validation_error`: Event validation failures
- `system_error`: Internal system errors
- `index_update`: Search index creation/update/deletion

**Log Storage:**

- Redis Key: `system-log-<timestamp>-<uuid>`
- Redis Value (JSON):
```typescript
  {
    logType: string,
    timestamp: number,
    eventName?: string,
    changes?: {
      before: any,
      after: any
    },
    metadata?: Record<string, any>
  }
```

**Schema Update Logs:**

- Capture when registry is updated during validation checks
- Show before/after comparison of schema
- Include event name and property changes
- Example:
```typescript
  {
    logType: 'schema_update',
    timestamp: 1234567890,
    eventName: 'custom:purchase',
    changes: {
      before: {
        properties: { productId: { type: 'string' } }
      },
      after: {
        properties: {
          productId: { type: 'string' },
          amount: { type: 'number' }
        }
      }
    }
  }
```

**Index Update Logs:**

- Capture when search index is created, updated, or deleted
- Show before/after comparison of index schema
- Include document count before and after
- Track which index (A or B) is active
- Example:
```typescript
  {
    logType: 'index_update',
    timestamp: 1234567890,
    action: 'update', // 'create' | 'update' | 'delete'
    indexName: 'events-idx',
    changes: {
      before: {
        activeIndex: 'events-idx-a',
        documentCount: 10000,
        schema: {
          eventName: { type: 'TEXT' },
          eventTime: { type: 'DATE' },
          'properties.amount': { type: 'F64' }
        }
      },
      after: {
        activeIndex: 'events-idx-b',
        documentCount: 10000,
        schema: {
          eventName: { type: 'TEXT' },
          eventTime: { type: 'DATE' },
          'properties.amount': { type: 'F64' },
          'properties.currency': { type: 'TEXT' }
        }
      }
    }
  }
```

**UI Integration:**

- Dedicated logs/activity tab in UI
- Filter logs by type
- Search logs by event name, timestamp, or content
- Real-time log streaming
- Export logs for analysis

### 2.5 Feature Flags

#### 2.5.1 Feature Flag Configuration

**Storage:**

- Redis key containing all possible feature flags
- Configurable via server and UI

**Flag Definition:**

```typescript
{
  flagName: {
    possibleValues: string[],
    defaultValue: string,
    description?: string
  }
}
```

#### 2.5.2 Flag Assignment in Sessions

**Requirements:**

- Each session stores assigned feature flag values
- Assignment methods:
  1. **Explicit**: User provides specific values
  2. **Distribution-based**: User provides distribution weights
     - Example: `{ control: 50, variant: 50 }`
     - System randomly assigns based on weights
- Validation:
  - Verify flag exists in configuration
  - Verify value is valid for that flag
  - Throw descriptive errors on validation failure
- Default assignment: Use configured defaults for unspecified flags

## 4. Configuration Architecture

### 4.1 Centralized Configuration

**Requirement:**
All configuration should be defined in a single TypeScript file that:

- Exports backend client configuration
- Exports types for frontend clients
- Can be imported by both frontend and backend
- Ensures type safety across the stack

**Configuration Elements:**

- Session expiration time
- Default feature flag values
- Feature flag definitions
- Custom event type definitions (for type safety)
- Redis connection settings
- UI defaults (time ranges, etc.)
- Search index configuration:
  - Index name
  - Auto-update enabled/disabled
  - Index rebuild on startup
- Rate limiting configuration:
  - Session creation rate limits
  - Event capture rate limits
  - Rate limit windows and maximums
- Schema validation configuration:
  - Validation frequency (probability 0-1, default 1 = always validate)
- System logging configuration:
  - Log retention period
  - Enabled log types

**Example Structure:**

```typescript
// config.ts
export const CONFIG = {
  session: {
    expirationMs: 3600000, // 1 hour
  },
  featureFlags: {
    theme: {
      possibleValues: ["light", "dark"],
      defaultValue: "light",
    },
  },
  events: {
    customEventRetentionDays: 7,
  },
  rateLimit: {
    sessionCreation: {
      requests: 10,
      window: "60s",
    },
    eventCapture: {
      requests: 100,
      window: "60s",
    },
  },
  schemaValidation: {
    checkFrequency: 1, // probability 0-1, default 1 = always validate
  },
  logging: {
    retentionDays: 30,
    enabledTypes: ["schema_update", "feature_flag_update", "rate_limit_exceeded", "index_update"],
  },
  search: {
    indexName: "events-idx",
    autoUpdate: true, // Automatically update index when schema changes
    rebuildOnStartup: false, // Check and rebuild index on startup if needed
  },
} as const;

// Export Config type for SDK consumers
export type Config = typeof CONFIG;

export type FeatureFlags = typeof CONFIG.featureFlags;

// Custom event types for type safety
export type CustomEvents = {
  "custom:purchase": {
    productId: string;
    amount: number;
    currency: string;
  };
  "custom:signup": {
    method: string;
    referrer?: string;
  };
};

// Usage with clients
// import { AnalyticsClient } from '@your-org/analytics-client';
// import { AnalyticsServer } from '@your-org/analytics-server';
// import type { CustomEvents } from './config';
//
// const client = new AnalyticsClient<CustomEvents>({ ... });
// const server = new AnalyticsServer<CustomEvents>({ ... });
```

### 4.2 Type Safety

**Requirements:**

- Frontend imports types from configuration file
- Backend imports configuration and types
- TypeScript ensures compile-time type checking
- SDK exports `Config` type for type-safe configuration
- Feature flag types are inferred from configuration
- Custom event types are defined in configuration and enforced at compile time
- Client APIs (frontend and backend) accept `CustomEvents` as a generic parameter:
  - `AnalyticsClient<CustomEvents>` for frontend
  - `AnalyticsServer<CustomEvents>` for backend
  - `captureEvent` method uses generic type parameter to enforce correct properties
  - TypeScript autocomplete shows available event names and their required properties
  - Compile-time errors for mismatched event data
  - No runtime overhead - all type checking happens at compile time
- Event data is validated against schemas at runtime (periodic checks)
- Schema registry automatically updates to match actual usage

```typescript
class AnalyticsServer<TCustomEvents extends Record<string, any>> {
  // Type-safe event capture
  captureEvent<T extends keyof TCustomEvents>(event: {
    sessionId: string;
    eventName: T;
    properties: TCustomEvents[T];
  }): Promise<void>;

  // Standard events
  capturePageView(sessionId: string, path: string): Promise<void>;
  captureClick(sessionId: string, element: string): Promise<void>;
  captureError(sessionId: string, message: string): Promise<void>;
  captureWarning(sessionId: string, message: string): Promise<void>;
  captureInfo(sessionId: string, message: string): Promise<void>;

  // Session management
  createSession(options: {
    featureFlags?: Record<string, string> | Record<string, Record<string, number>>;
  }): Promise<Session>;
  getSession(sessionId: string): Promise<SessionResult>;

  // Feature flags
  getFeatureFlag(sessionId: string, flagName: string): Promise<string>;
  getAllFeatureFlags(sessionId: string): Promise<Record<string, string>>;

  // Admin operations
  defineFeatureFlag(config: FeatureFlagConfig): Promise<void>;
  updateFeatureFlag(name: string, config: Partial<FeatureFlagConfig>): Promise<void>;
  rebuildSearchIndex(): Promise<void>;
  getSearchIndexInfo(): Promise<SearchIndexInfo>;
}
```

**Type Safety Notes:**

- Both clients accept `CustomEvents` type as a generic parameter during instantiation
- `AnalyticsClient<CustomEvents>` and `AnalyticsServer<CustomEvents>` provide complete type safety
- TypeScript provides autocomplete for event names and their properties
- Compile-time errors prevent mismatched event data
- Generic parameter ensures `captureEvent` only accepts events defined in `CustomEvents`
- Standard events (pageview, click, error, etc.) have their required properties enforced
- IDE shows type errors immediately when properties are missing or have wrong types
