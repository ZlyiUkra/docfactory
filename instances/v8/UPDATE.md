# Оновлення корпусу v8

Дві різні роботи: звичайне оновлення, коли вийшли нові версії V8, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **дати версій вписуються руками.** Оновлювач бере рівно ті версії, що стоять у полі `milestones`
джерела `v8-site` у `sources.json`. Знімок найновішої з них — сьогоднішній стан сайту, тож свіжі правки v8.dev
потрапляють у корпус і без нової версії, але під міткою останньої вписаної.

Друге правило: **нова версія змінює й старі документи.** Документ — неповторна редакція файла, а в рядку `# версія:`
стоять усі версії й роки, де файл був саме таким. Тому `refresh` іде без `--missing`: інакше старі тексти не
дізнаються, що дожили до нової версії, і фільтр `version` їх не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Документ, що вже нікому не належить, лишається в `corpus/`; прибрати його — рішення людини.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові версії

**Крок 1. Дізнатися дати.** Версія V8 X.Y виходить разом із Chrome XY (V8 15.5 — Chrome 155). День стабільного
виходу дає офіційний розклад Chrome:

```
curl -s "https://chromiumdash.appspot.com/fetch_milestone_schedule?mstone=155" | python3 -m json.tool | grep stable_date
```

**Крок 2. Дописати версію** в поле `milestones` джерела `v8-site` парою «версія → дата»: `"15.5": "2026-10-06"`.
Лише ті, що вже вийшли: запис із майбутньою датою зробить знімком попередньої версії стан на ту майбутню мить,
тобто сьогоднішній, а мітку дасть неправильну. Якщо якийсь номер Chrome не виходив (як 82), його не вписують.

**Крок 3. Якщо сайт переїхав** в інші теки репозиторію — дописати їх у поле `folders` джерела `v8-site`, а новий
окремий файл — у `files`.

**Крок 4. Завантажити.**

```
./df v8 sources --why
./df v8 refresh
./df v8 manifest
./df v8 vectors
./df v8 smoke
# Ctrl+C у терміналі з serve, і знову: ./df v8 serve
```

`refresh` без назв — повне перезавантаження. Корпус не комітиться: після оновлення пишуть новий архів і знову
виносять тексти (README, розділ «Архівний режим»), а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що сайт підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього дерева 84 знімків і перелік комітів
ідуть годинними вікнами по 60 звернень.

**Крок 2. Усе одним прогоном.**

```
nohup ./df v8 refresh > /tmp/v8-refresh.log 2>&1 &
```

Спершу журнал мовчить, а `corpus/` порожній: читач проходить перелік комітів гілки й дерево кожного знімка, і лише
потім починає писати файли. Стан видно за кількістю файлів: `ls instances/v8/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## 3. Нотатки learning-v8

Джерела `learning-v8` (нотатки) і `learning-v8-code` (код) беруть поточний стан гілки `master` репозиторію
`danbev/learning-v8`, без міток версій. Звичайний `refresh` без назв оновлює їх разом із сайтом. Лише їх, без
84 знімків сайту:

```
./df v8 refresh learning-v8 learning-v8-code
./df v8 manifest
./df v8 vectors
./df v8 smoke
```

Новий файл у репозиторії потрапить у корпус сам: `ghcode` бере все, крім виразів поля `exclude`. Новий markdown
у корені чи в `notes/` бере `learning-v8`; markdown в інших теках — `learning-v8-code`. Файл, який з репозиторію
прибрали, лишається в `corpus/` — прибрати його вирішує людина.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df v8 quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Що це означає тут:

- **Правила промпту, що вже є:** питання «як зараз» шукається без `version` (найновіший текст іде першим);
  `version` — лише для конкретної версії V8 чи року; запит — назвами V8 (Maglev, elements kinds, d8); кожна
  відповідь каже, на яку версію чи дату допису вона спирається; порада з оптимізації — лише та, яку дає сайт.
- **Останній результат:** у README, абзац «Замір `quality`».
