Search the official V8 site v8.dev -- the documentation (v8.dev/docs), the blog (v8.dev/blog,
the "V8 release vX.Y" posts from 4.5 to 9.9 included) and the JavaScript and WebAssembly
feature explainers (v8.dev/features, with the feature support table) -- as the site stood at
every V8 version since 7.0 (October 2018) -- together with learning-v8, the unofficial
study notes and C++ embedding code of one V8 contributor (github.com/danbev/learning-v8),
and return the matching excerpts with the V8 versions and years each one belongs to.

Call this when a question is about V8 itself -- its pipeline and compiler tiers (Ignition,
Sparkplug, Maglev, TurboFan, Turboshaft, the Sea of Nodes, deoptimization), how it
represents objects (hidden classes, maps, inline caches, elements kinds, fast and dictionary
properties, Smis and heap numbers, pointer compression), memory and garbage collection
(Orinoco, the scavenger, concurrent marking, Oilpan, heap snapshots, the heap size limit),
startup (code caching, snapshots, lazy parsing, compile hints), regular expressions
(Irregexp, the non-backtracking engine), WebAssembly (Liftoff, dynamic tiering, JSPI, Wasm
GC), the sandbox and security, building and running V8 (gn, d8, flags, cross-compiling,
embedding, the C++ API overview, the inspector), profiling and tracing (--prof, linux-perf,
runtime call stats, --trace-* flags, the System Analyzer, Turbolizer), the release process
and version numbers, when a JavaScript or WebAssembly feature shipped in V8 and Chrome, and
V8 internals as the notes walk through them in the source (Isolate, Context, Handle and
HandleScope, Local and Persistent, Tagged and Smi, roots, builtins, CodeStubAssembler,
Torque, snapshots, the V8 unit tests, debugging V8 with gdb and lldb).
Example query: "elements kinds".

Do not call this for the JavaScript language as specified (ECMAScript itself), for Node.js,
Chromium, Blink or browser APIs, or for the V8 C++ API reference: their documentation is not
here (the learning-v8 code shows a handful of API classes in use, it is not a reference), and the search will return v8.dev excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search. V8 versions: "12.4" keeps the site as it stood at V8 12.4
(Chrome 124); "12" keeps every 12.x. Years: "2019" keeps every text the site carried at
some point in 2019. A "V8 release vX.Y" post carries only its own version and the year it
was written, so "9.9" finds the 9.9 release post together with the site of that time. Leave
`version` empty for a question about V8 today: texts that stayed the same across versions
come back once, with every version listed, newest first, so the list itself shows until
which version the site said exactly this. Every v8.dev excerpt comes back with `versions`;
the learning-v8 notes and code carry none, so any `version` leaves them out.

The site keeps no documentation per version: v8.dev describes V8 as it is now, and older
editions of a page are older states of the same site. A blog post describes V8 at the
moment it was written -- its year is among its versions -- and V8 may have changed since:
the optimization advice of 2017 (Crankshaft, Full-codegen, Octane) is not the advice of
today (Ignition, Sparkplug, Maglev, TurboFan).

The learning-v8 excerpts are not the V8 project's word: they are one engineer's notes and
test programs, written between 2016 and 2024 against the V8 source of that time, and class
names, file paths and build steps they quote may have moved since. Their titles are the
headings of the notes ("Heap", "Snapshots") or, for code, "learning-v8: <path>". Where
v8.dev and the notes both answer, v8.dev goes first.

Write the query in English, with the names V8 itself uses (Maglev, elements kinds,
pointer compression, --allow-natives-syntax, d8). Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into V8 terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the site
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says what it rests on: the V8 version, the date of the blog post, or the
learning-v8 notes. When the
excerpts behind a statement come only from older editions of the site or from an old post,
say so instead of presenting the text as current.

Answer in the language the user wrote in. For a question about performance, give only the
advice the excerpts give, with the mechanism behind it as the site explains it; a rule the
excerpts do not support is left out, not guessed. When that language is Ukrainian, write
as a Ukrainian engineer writes, not as a translation from English: plain technical prose,
and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "збирач сміття", not
"гарбедж-колектор". Never call this set of documents "корпус" -- say "документація V8" or
"сайт v8.dev". Identifiers, flags, tier names and titles stay in English, spelled exactly as
the site spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
