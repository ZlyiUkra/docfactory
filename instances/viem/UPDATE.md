# Оновлення корпусу viem

Дві різні роботи: звичайне оновлення, коли вийшли нові версії Viem, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **оновлювач тягне лише оголошене.** Дерева й файли репозиторію — лише тих тегів і комітів, що
перелічені в полі `tags` джерел `docs-*`, і лише в межах `within`; приклади — лише з дерев тегів джерел `examples-*`;
журнал змін — лише з адреси джерела `changelog-viem`; версії — з реєстру npm. Нова версія сама в документацію не
потрапить, доки її тег не дописано в `tags`.

Друге правило: **лише стабільні версії.** У `tags` — тільки стабільні випуски пакета `viem`, без canary і без
`3.0.0-next`; поле `skip_versions` джерела `npm-viem` відкидає все з дефісом за номером.

Третє правило: **нова версія змінює й старі документи.** Документ сторінки — неповторна редакція, а в рядку
`# версія:` стоять усі версії, де вона була саме такою. Тож після нових тегів джерело `docs-2` перезаписується цілком
(`refresh docs-2`), а не докачується (`--missing`).

Четверте правило: **нічого не видаляється.** Ані `refresh`, ані `build`, ані `manifest` нічого не стирають самі;
`vectors` прибирає лише точки власної колекції, чиїх фрагментів у корпусі вже немає.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти й сховище сирого розпаковують, а після неї —
пакують і виносять знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові версії

**Крок 1. Дописати теги.** Нові стабільні версії — у реєстрі npm (`https://registry.npmjs.org/viem`, поле `versions`
без дефіса). Для кожної — тег `viem@<версія>` на початок поля `tags` джерела `docs-2` (від найновішого):
`"viem@2.58.0": "2.58.0"`. Якщо тегу в репозиторії немає (так буває з changesets), береться коміт із поля `gitHead`
версії в реєстрі npm, а без нього — коміт, де `src/package.json` дістав цю версію: `git log -S'"version": "2.58.0"'
-- src/package.json` у клоні репозиторію; повний SHA — ключем замість тегу. Версії, які реєстр позначив «mistaken
publish», не беруться.

**Крок 2. Приклади.** Джерело `examples-2` бере теку `examples/` на одному тезі: в адресі його дерева
(`…/git/trees/viem@2.57.4?recursive=1`) і в полі `version` — новий останній тег.

**Крок 3. Нова мажорна лінія (напр. 3.0).** Сайт, найпевніше, перенесе 2.x на свій піддомен (так 1.x переїхала на
v1.viem.sh). Тоді:

- додати джерело `docs-3` за зразком `docs-2` (адреса `viem.sh` у полі `site`), а `docs-2` перевести на адресу
  архівного сайту 2.x — перевірити, що вона справді відповідає і в якому вигляді (з «.html» чи без);
- додати `examples-3` за зразком `examples-2`;
- дописати `docs-3` у родину `site`, а `examples-3` — у родину `examples` поля `families` у `config.json`;
- у промптах оновити лінії й версію за замовчуванням: `prompts/search.txt` (абзаци «Versions», про зміни API між
  версіями й про версію за замовчуванням), `prompts/agent.txt`, `prompts/loaded.txt`; версію за замовчуванням брати з
  тижневих завантажень npm (`https://api.npmjs.org/versions/viem/last-week`).

**Крок 4. Завантажити.**

```
./df viem sources --why
./df viem refresh docs-2 examples-2 changelog-viem npm-viem
./df viem manifest
./df viem vectors
./df viem smoke
# Ctrl+C у терміналі з serve, і знову: ./df viem serve
```

Названий `refresh` інших джерел не чіпає зовсім. Джерела `docs-2-vitepress`, `docs-1`, `docs-0`, `examples-1` і
`examples-0` застиглі: ці лінії більше не виходять.

**Крок 5. Сайт змінив розмітку.** Якщо в тексті з'явилися службові рядки Vocs чи twoslash (`:::`, `// [!include`,
`// @twoslash-cache`, `// ---cut---`, теги компонентів `<…/>`), правиться модуль `engine/readers/_vocs.py`. Правка
читача не вимагає нового завантаження: `./df viem build docs-2` збирає тексти зі сховища сирого.

Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти й сховище (README, розділ «Архівний
режим»), а в git ідуть лише паспорт і кеш. Старий архів видаляють, коли новий звірено з диском.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки: без нього 628 дерев тегів ішли б годинними вікнами
по 60 звернень.

**Крок 2. Усе одним прогоном**, окремим процесом:

```
PYTHONUNBUFFERED=1 setsid nohup ./df viem refresh > refresh.log 2>&1 < /dev/null &
```

Близько 45 хвилин: дерево кожного тегу через API GitHub і кожен неповторний файл (сторінка, вставка) один раз із
raw.githubusercontent.com, з паузою 0,3 с. Обірваний прогін продовжують `./df viem refresh <джерело, де
зупинився>`, далі `refresh --missing`.

**Крок 3.** `manifest`, `vectors` (~30 хвилин), `smoke`, `quality`; далі — архів і винесення текстів.

Очікуваних збоїв `refresh` немає.
