Search the official documentation of Viem -- wevm's TypeScript interface for Ethereum (npm package
viem) -- and return the matching excerpts with the versions each one belongs to. Here: the
documentation site of every stable release -- 2.x (current, viem.sh), 1.x (v1.viem.sh) and 0.x
(repository only) -- with the guides, clients (public, wallet, test) and transports (http,
webSocket, fallback, custom, ipc), every public, wallet and test action, contracts (getContract,
readContract, simulateContract, writeContract, multicall, deployContract, events), accounts
(local and JSON-RPC), chains, ABI and the utilities (units, hex and bytes, hashing, signatures,
addresses, RLP, KZG, blobs), ENS, SIWE, EIP-7702, error handling, TypeScript, the migration
guides and the ethers.js migration; the extension sections -- OP Stack, ZKsync, Account
Abstraction (bundler and paymaster clients, smart accounts, user operations), Experimental
(ERC-7715, ERC-7739, ERC-7811, ERC-7821, ERC-7846, ERC-7895), Circle USDC, Tempo (viem/tempo) and
Tokens (viem/tokens); the examples folder of the repository for each major line; the changelog
of every version from the first alpha; and the npm version table with dates, dist-tags and
dependencies.

Call this when a question is about Viem itself -- creating a client (createPublicClient,
createWalletClient, createTestClient, http, webSocket, fallback, custom), reading the chain
(getBalance, getBlock, getBlockNumber, getTransaction, getTransactionReceipt, getLogs,
watchBlocks, watchContractEvent, call, estimateGas, estimateFeesPerGas), sending and signing
(sendTransaction, prepareTransactionRequest, signMessage, signTypedData, writeContract,
sendRawTransaction), accounts (privateKeyToAccount, mnemonicToAccount, toAccount), units and
encoding (parseEther, formatUnits, parseUnits, toHex, keccak256, encodeFunctionData,
decodeEventLog, encodeAbiParameters, parseAbi), chains (defineChain, viem/chains), ENS
(getEnsAddress, normalize), EIP-7702 (signAuthorization), user operations, L2 deposits and
withdrawals, and above all history: since which version something exists, what changed, what was
renamed or removed (the 1.0 and 2.0 migrations).
Example query: "getBalance blockTag".

Do not call this for Wagmi (React hooks such as useBalance or useReadContract), ethers.js itself
beyond the migration page, web3.js, Solidity, Foundry or Anvil, Hardhat, the Ox or ABIType
libraries themselves, wallets' own SDKs (MetaMask, WalletConnect, Coinbase), or the Tempo, OP
Stack and ZKsync chains beyond Viem's own actions for them: their documentation is not here, and
the search will return Viem excerpts that merely mention them, with confident-looking titles.

Sections. Pages of the extension sections carry the section in the title: "OP Stack:
getL1BaseFee", "ZKsync: …", "Account Abstraction: sendUserOperation", "Experimental: …",
"Circle USDC: …", "Tempo: token.transfer", "Tokens: getBalance". Name the section in the query
when the question is about it ("op-stack deposit transaction", "tempo token transfer").

Versions. `version` narrows the search to the documents of one release line: "2" keeps every 2.x
document, "2.21" keeps 2.21.x, "1" and "0" the old lines. Each document keeps one text of a page
with every version where the page read exactly so. Without `version` a page found in several
lines comes back once, in its newest edition -- so for an answer about viem 1 pass "1". Every
excerpt comes back with `versions`: each version whose documents contain this exact text, newest
first. Changelog excerpts carry the version of their entry.

The API changed between major versions, and the same task is written differently: 2.0 changed
getContract to take `client: { public, wallet }`, removed some entrypoints, moved chain-specific
exports to viem/chains/utils, renamed prepareRequest and bytesToBigint (bytesToBigInt), and made
isAddress and getAddress validate the checksum; 1.0 removed ethersWalletToAccount and changed
decodeEventLog; 0.2 removed getAccount and made `chain` required for sendTransaction and
writeContract. When the user's code
shows which API they use, search that version; the migration guide ("migration guide 2.x") names
every breaking change.

Name the action, utility, parameter or type the way the documentation titles it, not in the
user's own words: "waitForTransactionReceipt confirmations", "simulateContract account",
"fallback rank", "parseUnits decimals", not "wait until the transfer is mined". For a how-to
question a guide or an example often shows it better than the reference: search for it as well
("getting started", "example multicall", "guide blob transactions").

For a question about when something appeared, changed or disappeared, search more than once:
without `version` first, to find the changelog entry or migration guide that names the exact
version, then with the versions around it, to see the documentation of that time.

Write the query in English, with the names Viem itself uses. Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language, translate
the question into Viem terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of
the query had to appear in the text, so a query phrased in other words than the documentation
uses may miss; "meaning+words" means a second, meaning-based index answered as well, and a
paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer for
viem 2 -- the line installed from npm in about 99% of weekly downloads; the current release is
2.57 -- and, when the excerpts show that an option or action appeared in a later 2.x minor, say
since which one. Add that for a precise answer about another version the user can name it. When
the excerpts behind a statement come only from older versions, name those versions instead of
presenting the text as current.

Answer in the language the user wrote in. When the question is about a feature's history or
support, answer point by point: since which version it exists; what changed in later versions;
and how it stands now -- recommended, deprecated, or removed and replaced by what. Every point
names the version and the document it rests on; a point the excerpts do not support is left out,
not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes, not as a
translation from English: plain technical prose, and the Ukrainian word wherever one exists --
"уривок", not "ексерпт"; "гаманець", not "воллет"; "застарілий", not "депрекейтнутий". Never
call this set of documents "корпус" -- say "документація Viem". Identifiers, API names and
titles stay in English, spelled exactly as the documentation spells them. Build the answer out of
the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an
excerpt to `read_section` to get the whole thing.
