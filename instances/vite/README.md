# vite — примірник фабрики docfactory

Вісімнадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Vite і його офіційні плагіни —
React (Babel, SWC, Oxc), React Server Components, Vue, Vue JSX, legacy, basic-ssl — і про create-vite за офіційною
документацією всіх версій, README кожної опублікованої версії пакетів, нотатками релізів і реєстром версій npm. Код
спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний
устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

Vite за п'ять років змінив вісім мажорних версій, і кожна щось переставляла: типові браузери збірки, формат
`vite.config` (CommonJS, потім лише ESM), API для SSR (`ssrLoadModule`, потім Module Runner і Environment API),
а у 8 — і сам збирач (Rollup та esbuild замінив Rolldown з Oxc). Проєкт може стояти на будь-якій із цих версій, і
відповідь «як це налаштувати» залежить від того, на якій саме.

Тому тут документація кожної версії, а не лише поточна: один і той самий текст, що не змінювався між версіями,
лежить один раз із переліком усіх версій, де він був таким. А для питань «що з чим сумісне» (Vite 8 і
plugin-react 6, Node 20 чи 22, Vue 3, TypeScript) — реєстр npm з peer-залежностями кожної версії.

Разом 2 821 документ; фрагментів в індексі — 4 904 (`expected_passages` у `checks.json`). Фрагменти — це шматки
документів між заголовками, по яких іде пошук; однаковий текст різних версій зливається в один з усіма версіями.
Сторінок небагато, зате кожна — у десятках редакцій: `docs/config/index` має 303 фрагменти, `docs/guide/features` —
225, `docs/guide/migration` — 180.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 1 із 10, за
змістом 5, разом 6; друга, «як модель» (назви опцій і API, з `version: "8"`, як велить промпт), — 10 із 10. Цілі —
сторінки всіх версій. Промахи першої десятки показують, чому промпт велить шукати з версією:

- **Без версії місця займають редакції.** Та сама сторінка лежить у десятках версій, і по словах перші п'ять місць
  беруть п'ять редакцій сусідньої сторінки, а не цільова: на «render pages on the server» — п'ять варіантів
  «Static Deploy», на «apply a code change without reloading» — «Why Vite → Slow Updates». За змістом цілі
  знаходяться, і злиття їх підіймає — звідси 6 проти 1.
- **Два промахи — не порожні.** «Why the first start takes long» приносить «Why Vite → Slow Server Start» замість
  «Dependency Pre-Bundling», а «apply a code change without reloading» за змістом — застереження (`caveats`) з
  README plugin-react-swc про межі Fast Refresh: обидва тексти відповідають на питання, лише з іншої сторінки.
- **Друга десятка влучає щоразу**, бо `version: "8"` лишає одну редакцію кожної сторінки, і місця дістаються різним
  сторінкам.

**Версія у відповіді.** Кожна відповідь каже, якого пакета й версії вона стосується; без названої — для
найпопулярнішої лінії за завантаженнями npm (на день збирання — Vite 8, 46% завантажень за тиждень), а де поширені
дві — для обох. Текст, знайдений лише в alpha, beta чи rc, міг так і не вийти релізом — відповідь каже про це.

### Проміжні збірки в реєстрі

У реєстрі npm трапляються версії, які релізами не є: збірки з хешем коміту чи номером pull request у номері
(`1.2.0-pr.123`, `0.3.1-8de0114`) і `0.0.0-…`. Це збірки для перевірки змін до релізу; README таких версій не
береться, але в реєстрі вони лишаються — якщо така версія трапиться в lock-файлі, документ реєстру покаже її дату й
мітку. Передрелізи (`-alpha`, `-beta`, `-rc`) — інша річ: це версії на шляху до релізу, вони беруться всюди.

## Що в цій теці

- `corpus/` — документи звичайними текстовими файлами; поруч `index.json` — паспорт: адреса, дата завантаження й
  сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df vite <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація Vite | тека `docs/` vitejs/vite на кожному тегу релізу | `ghdocs-history` |
| нотатки релізів монорепозиторіїв | GitHub API, лише теги свого пакета | `ghreleases-tagged` |
| нотатки релізів plugin-basic-ssl | GitHub API | `ghreleases` |
| README пакетів | коміт публікації (`gitHead`) або тег релізу на GitHub | `npm-readme` |
| версії пакетів | реєстр npm | `npm-versions` |

Нових читачів немає. Сайт vite.dev (VitePress) збирається з тієї самої теки `docs/`, і весь його текст лежить у
markdown, тож знімки репозиторію на тегах дають і поточну документацію, і всю її історію — зокрема архівні сайти
v2.vite.dev … v7.vite.dev, що відповідають гілкам `v2` … `v7`.

Особливості, які варто знати:

- **Мітка — точна версія свого пакета** (`8.3.2`, `6.1.1`); фільтр `"8"` бере всю лінію 8.x. Номери в пакетів
  свої: з `version "8"` знайдуться і Vite 8, і plugin-legacy 8 — назва й шлях документа кажуть, чий він.
- **Лінія 1.x — лише README.** На тегах `v1.0.0-rc.*` теки `docs/` ще не було; документація починається з
  `v2.0.0-alpha.1`.
- **Релізи Vite на GitHub — з 2.7.0-beta.10** (грудень 2021). Для 2.0–2.6 є документація, README і реєстр, а
  журнал змін тих версій (`CHANGELOG.md` на старих тегах) не взято: заголовок версії там — посилання на
  порівняння тегів, загорнуте в `<small>`, а не `## 2.6.14 (дата)`, і його не впізнає жоден із чинних читачів;
  нового заради семи мінорних версій вирішено не писати.
- **Плагіни переїздили.** plugin-react, plugin-vue і plugin-vue-jsx до кінця 2022 жили в vitejs/vite, а потім — у
  власних репозиторіях; plugin-react-swc спершу жив у vitejs/vite-plugin-react-swc. Релізи старого місця — окремі
  джерела `releases-*-old`, а README пробує обидва репозиторії по черзі.
- **Теги монорепозиторію.** У vitejs/vite документація береться лише з тегів `v…` самого Vite; теги
  `create-vite@…`, `plugin-legacy@…` та старі `plugin-react@…`, `plugin-vue@…` мають ту саму теку документації.
- **Кілька версій без README:** у Vite — 95 ранніх (`1.0.0-beta.*` і частина `1.0.0-rc.*` без тегу й коміту
  публікації), перші 1.0.x plugin-vue, 2.5.x create-app і 1.x plugin-react-refresh. Тексти ті самі, що в сусідніх
  версіях, тож у корпусі вони є, бракує лише мітки цих версій.
- **Лише офіційне й лише англійською.** Плагіни інших команд (`@sveltejs/vite-plugin-svelte`, Analog для Angular)
  і переклади документації (`docs-cn`, `docs-ja`, …) не взято.

## Установка venv

```
cd instances/vite
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df vite sources --why   # перелік джерел і білий список
./df vite refresh         # завантажити все задеклароване (~1,5 години)
./df vite manifest        # оновити паспорт
./df vite setup           # Qdrant чи пошук лише по словах
./df vite vectors         # залити корпус у docs-vite (~25 хвилин)
./df vite smoke           # перевірки
```

`refresh` довший за 30 хвилин: із Claude Code його треба запускати окремим процесом (`setsid nohup …`), інакше
фонову задачу обірве оболонка. Обірваний `refresh` продовжується з `--missing`: уже записане він не тягне вдруге.
Імена джерел без `--missing` прогін не звужують. Перші пів години `refresh` мовчить: читач документації спершу
обходить дерева всіх тегів і лише потім записує.

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df vite serve           # порт 8778
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8778/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user vite-docs http://127.0.0.1:8778/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `vite-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df vite setup --vectors      # з Qdrant: потрібен Docker
./df vite setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

**4. Перевірка, сервер, клієнт.**

```
./df vite smoke           # усі перевірки мають бути ok
./df vite serve           # порт 8778, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
