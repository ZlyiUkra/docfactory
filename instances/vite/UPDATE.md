# Оновлення корпусу vite

Дві різні роботи: звичайне оновлення (вийшли нові релізи Vite чи плагінів) і новий офіційний плагін. Порядок
усередині кожної важливіший за самі команди.

Головне правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Сторінка, що зникла з документації, чи версія, прибрана з реєстру, лишається в `corpus/`; прибрати — рішення людини.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Звичайне оновлення

**Крок 1. Нові теги.** Документація береться з тегів, перелічених у полі `tags` джерела `vite-docs` у
`sources.json` («тег → версія», від найновішого). Новий реліз Vite — новий рядок нагорі цього поля:
`"v8.4.0": "8.4.0"`. Передрелізи (`v9.0.0-beta.1`) теж беруться: у них документація вже змінена. Репозиторій
vitejs/vite — монорепозиторій, і теги в ньому є й у інших пакетів (`create-vite@…`, `plugin-legacy@…`, старі
`plugin-react@…`, `plugin-vue@…`); у `tags` ідуть лише теги самого Vite, `v…` — тека `docs/` належить йому.
Нотатки релізів, README і реєстр npm нові версії підхоплюють самі, зокрема й у плагінів.

**Крок 2. Завантаження й решта.**

```
./df vite sources --why
./df vite refresh --missing      # лише нове; повний refresh — ~1,5 години
./df vite manifest
./df vite vectors
./df vite smoke
# Ctrl+C у терміналі з serve, і знову: ./df vite serve
```

`--missing` докачує документи, яких ще немає, і не чіпає наявних. Цього досить для нових тегів і релізів. Повний
`refresh` потрібен, коли змінився перелік версій уже наявного тексту: документ пам'ятає всі версії, де текст був
таким, і з новим тегом цей перелік росте. З Claude Code довгі кроки запускати окремим процесом
(`setsid nohup …`), інакше оболонка обірве їх через 30 хвилин.

Корпус не комітиться: після оновлення пишуть новий архів і знову виносять тексти (README, розділ «Архівний режим»),
а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Новий офіційний плагін

Беруться лише пакети організації vitejs (`@vitejs/*` і `create-vite`). У плагінів немає теки документації —
документацією є README пакета, тож джерел три:

**README** — `npm-readme` за зразком `readme-plugin-vue`: опис пакета в реєстрі, шаблон адреси README з `{ref}`
(коміт публікації або тег), шаблон тегу. Якщо плагін переїздив між репозиторіями (так було з plugin-react і
plugin-vue — із vitejs/vite у власні), шаблонів кілька, і пробуються вони по черзі.

**Нотатки релізів** — `ghreleases-tagged` за зразком `releases-plugin-vue`: потік релізів монорепозиторію спільний,
тож `tag_prefix` (`plugin-vue@`) лишає релізи лише цього пакета, а версією стає решта тегу. Якщо плагін раніше
жив у vitejs/vite, його старі релізи лежать там — друге джерело за зразком `releases-plugin-vue-old`.

**Реєстр** — `npm-versions` за зразком `npm-plugin-vue`.

Потім `refresh --missing`, `manifest`, `vectors`, `smoke`, як у розділі 1, рядок у таблиці пакетів README і
назва пакета в `prompts/search.txt` та `prompts/loaded.txt`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df vite quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточна лінія:** Vite 8. `prompts/search.txt` (абзац «Which version to search first») і `prompts/agent.txt`
  велять шукати з нею; нова мажорна версія — правка цих двох абзаців і `quality_model` у `checks.json`.
- **Правила промпту, що вже є:** запит — назвами опцій і API англійською; без версії — історія, міграції й
  сумісність; номери версій — свої в кожного пакета; кожна відповідь каже пакет і версію; текст лише з alpha, beta
  чи rc міг не вийти релізом.
- **Останній результат:** у README, абзац «Замір `quality`».
