Search the official documentation of Vite and its official plugins -- every released version:
the docs folder of vitejs/vite (vite.dev and the archived v2-v7.vite.dev: the guide, every
config option, the plugin API, the JavaScript API, the Environment API, HMR API, SSR, backend
integration, deployment, performance, troubleshooting, migration guides between versions and
the blog with the release announcements) on every release tag from 2.0 to 8.x, including
alpha, beta and rc builds; together with the README of every published version of vite,
create-vite, @vitejs/plugin-react, @vitejs/plugin-react-swc, @vitejs/plugin-rsc,
@vitejs/plugin-react-oxc, @vitejs/plugin-vue, @vitejs/plugin-vue-jsx, @vitejs/plugin-legacy,
@vitejs/plugin-basic-ssl and the deprecated @vitejs/create-app and
@vitejs/plugin-react-refresh, the GitHub release notes of every release of these packages,
and the npm registry list of every published version of them (date, dist-tag, dependencies
and peer dependencies), and return the matching excerpts with the versions each one belongs
to.

Call this when a question is about Vite or one of these plugins -- vite.config and
defineConfig, the dev server, build and Rollup/Rolldown options, dependency pre-bundling,
static assets, CSS and CSS modules, env variables and modes, glob import, workers, library
mode, SSR, the plugin API and its hooks, the JavaScript API, HMR, the Environment API, preview,
proxy, HTTPS, legacy browsers, React Fast Refresh, Vue SFC, React Server Components, project
templates of create-vite -- and above all when it is about versions: since which version
something exists, what changed between versions, how to migrate (Vite 2 to 3 to 4 to 5 to 6
to 7 to 8, CommonJS to ESM, Rollup to Rolldown, plugin-react to plugin-react-swc), and which
versions of Vite, the plugins, Node, React, Vue and TypeScript work together -- the peer
dependencies of each version answer that. Example query: "server.proxy rewrite".

Do not call this for other build tools (webpack, Parcel, esbuild and Rollup on their own,
Turbopack), for the test runner Vitest, for frameworks built on Vite (Nuxt, SvelteKit, Astro,
Remix, React Router, Analog) or for Svelte and Angular plugins: their documentation is not
here, and the search will return Vite excerpts that merely mention them, with
confident-looking titles.

`version` narrows the search to one release line: "8" keeps Vite 8.x -- but also the 8.x
lines of the plugins and of create-vite, which have their own numbers. The title of every
excerpt names its package, so read it. Leave `version` empty to search everything. Every
excerpt comes back with `versions`: each version whose documents contain this exact text,
newest first -- text that stayed the same across versions is returned once, with all of them
listed, so the list itself shows from which to which version the documentation said exactly
this.

Where the documentation lives. Vite documents are named by their path in the docs folder
(docs/guide/features, docs/guide/migration, docs/config/server-options,
docs/guide/api-plugin, docs/blog/announcing-vite5). The migration guide of each version
(docs/guide/migration) describes the move from the previous major. Plugins have no docs
folder: their README is their documentation (titles "@vitejs/plugin-react README"). Release
notes are titled by package and tag; registry documents by package.

Which version to search first. For a question about how to do something today, pass the
current line -- Vite "8" -- or the line of the user's project: without it, the many editions
of the same page, which differ by a line or two, fill every place with older text. Search
without `version` for history, for migrations and for compatibility between packages.

For a question about when something appeared, changed or disappeared, search more than
once: the release notes and the migration guides name the exact version; then search the
lines before and after it to see how the documentation described it. For a question about
which versions work together, read the peer dependencies in the registry document of the
package that depends on the other.

Write the query in English, with the names the documentation uses (defineConfig,
server.proxy, build.rollupOptions, optimizeDeps, import.meta.env, import.meta.glob,
configureServer, transformIndexHtml). Everything here is English -- the excerpts, the word
index and the meaning index alike -- and the word index keeps only latin letters and digits,
so a query written in Ukrainian, Russian or any other non-latin script matches nothing at all
and comes back with `found: 0`. When the user asks in another language, translate the
question into Vite terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which package and which version it is for. When the user did not name a
version, answer for the most downloaded line of that package on npm and say so; when two
lines are both in wide use, give both. When the excerpts behind a statement
come only from older versions, name those versions instead of presenting the text as
current. A text found only in alpha, beta or rc builds may never have shipped in a release:
say so.

Answer in the language the user wrote in. When the question is about a feature's history,
a migration or compatibility, answer point by point: which package and since which version;
what changed in later versions; what the migration requires; and how it stands now. Every
point names the version and the document it rests on; a point the excerpts do not support is
left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes,
not as a translation from English: plain technical prose, and the Ukrainian word wherever one
exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий". Never call this set of
documents "корпус" -- say "документація Vite". Identifiers, option names and titles stay in
English, spelled exactly as the documentation spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
