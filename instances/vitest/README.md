# vitest — примірник фабрики docfactory

Двадцять третій примірник фабрики: захищений MCP-сервер, що відповідає на питання про тестовий фреймворк Vitest, його
пакети (UI, браузерний режим і провайдери, покриття v8 та istanbul, web-worker, vite-node) і правила лінтера
`@vitest/eslint-plugin` за офіційною документацією всіх версій, README кожної опублікованої версії пакетів, нотатками
релізів і реєстром версій npm. Код спільний і лежить у `../../engine/`, `../../server/` та `../../common/`; ця тека
тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо

Vitest за чотири роки пройшов шлях від 0.x до 5.x, і кожна мажорна версія щось переставляла: робочі простори
(`workspace`) замінили проєкти (`projects`), браузерний режим із експериментального став стабільним і розділився на
окремі пакети провайдерів, `coverage-c8` поступився `coverage-v8`, vite-node пішов з монорепозиторію. Тести в проєкті
пишуться під конкретну версію, і відповідь «як замокати модуль» чи «як увімкнути покриття» залежить від неї.

Тому тут документація кожної версії, а не лише поточна: один і той самий текст, що не змінювався між версіями, лежить
один раз із переліком усіх версій, де він був таким. А для питань «що з чим сумісне» (Vitest і Vite, Node, Playwright)
— реєстр npm з peer-залежностями кожної версії.

Vitest вивчається в плані React (фаза 3, дні 12–13), у плані NestJS (фаза 5) і в плані Next.js (фаза 4, день 13) —
див. [../../docs/learning-map.md](../../docs/learning-map.md).

## Що в цій теці

- `corpus/` — лише паспорт `index.json`: адреса, дата завантаження й сума тексту кожного документа (тексти — в архіві,
  див. нижче).
- `index/passages.json.gz` — стиснений кеш фрагментів, з якого підіймається сервер.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df vitest <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація Vitest | тека `docs/` vitest-dev/vitest на кожному тегу релізу | `ghdocs-history` |

| нотатки релізів | GitHub API | `ghreleases` |

| версії пакетів | реєстр npm | `npm-versions` |

Нових читачів немає. Сайт vitest.dev (VitePress) збирається з тієї самої теки `docs/`, тож знімки репозиторію на
тегах дають і поточну документацію, і всю її історію.

Особливості, які варто знати:

- **Мітка — точна версія свого пакета** (`4.1.11`, `1.6.27`); фільтр `"4"` бере всю лінію 4.x. Пакети монорепозиторію
  мають ті самі номери, що й Vitest, а `@vitest/eslint-plugin` і `vite-node` — свої: з `version "1"` знайдуться і
  Vitest 1, і eslint-plugin 1.x — назва документа каже, чий він.
- **Документація — з 0.1.** На тегах 0.0.x теки `docs/` ще не було.
- **README пакета `vitest`** у монорепозиторії — заглушка на кількасот байтів, тож береться кореневий README
  репозиторію (поріг `min_chars`).
- **`@vitest/coverage-c8` README не мав ніколи**, тож для нього є лише реєстр.
- **vite-node** з 4.x веде окремий репозиторій antfu-collective/vite-node, а **`@vitest/browser-webdriverio`** з 5.x —
  vitest-community/vitest-webdriverio. Це вже не офіційні репозиторії vitest-dev, тож README їхніх новіших версій не
  взято; записи реєстру є.
- **Лише офіційне й лише англійською.** Розширення для VS Code, переклади документації, Testing Library і MSW не
  взято.

## Архівний режим: сервер без корпусу

Корпус примірника в архіві від самого початку, як у kubernetes і linux: у `corpus/` лежить лише паспорт `index.json`,
а сервер підіймається з кешу фрагментів (`index/passages.json`) і колекції Qdrant; відповіді ті самі до символа — кеш
тримає повний текст кожного фрагмента.

**Де тексти.** В архіві `~/archives/docfactory/vitest-corpus-2026-10-06-prefixed.tar.gz` (5,4 МБ, 3 679 текстів і паспорт;
перед видаленням розпакований окремо й звірений із диском — нуль розбіжностей). В історії git текстів немає ніде.
Архів лежить лише на цій машині.

**Як винести знову** — після оновлення, коли `vectors` і `smoke` пройшли:

```
ls -l instances/vitest/index/passages.json                 # кеш має бути на місці й свіжий
tar -czf ~/archives/docfactory/vitest-corpus-РРРР-ММ-ДД.tar.gz -C instances/vitest corpus
find instances/vitest/corpus -maxdepth 1 -name '*.txt' -delete
gzip -9 -c instances/vitest/index/passages.json > instances/vitest/index/passages.json.gz
```

і закомітити паспорт `corpus/index.json` та `index/passages.json.gz`. Видаляти тексти — лише після того, як архів
звірено з диском.

**Як повернути тексти** — перед будь-яким оновленням корпусу:

```
tar -xzf ~/archives/docfactory/vitest-corpus-РРРР-ММ-ДД.tar.gz -C instances/vitest
./df vitest smoke
```

**На іншій машині** після клонування кеш треба розпакувати: `gunzip -k instances/vitest/index/passages.json.gz`, далі
`./df vitest vectors` заллє колекцію Qdrant (33 хвилини на цій машині).

## Установка venv

```
cd instances/vitest
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

```
./df vitest sources --why   # перелік джерел і білий список
./df vitest refresh         # завантажити все задеклароване (~2,5 години)
./df vitest manifest        # оновити паспорт
./df vitest setup           # Qdrant чи пошук лише по словах
./df vitest vectors         # залити корпус у docs-vitest (~35 хвилин)
./df vitest smoke           # перевірки
```

`refresh` довший за 30 хвилин: із Claude Code його треба запускати окремим процесом (`setsid nohup …`), інакше
фонову задачу обірве оболонка. Обірваний `refresh` продовжується з `--missing`: уже записане він не тягне вдруге.
Перші пів години `refresh` мовчить: читач документації спершу обходить дерева всіх тегів і лише потім записує.
Найдовша частина — README: реєстр npm віддає текст лише найновішої версії, тож кожна з майже трьох тисяч версій читається
окремо.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df vitest serve           # порт 8783
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8783/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user vitest-docs http://127.0.0.1:8783/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server» у
вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `vitest-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію Claude
Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і «Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).
