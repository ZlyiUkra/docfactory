Search the official documentation of the test framework Vitest and its packages -- every
released version: the docs folder of vitest-dev/vitest (vitest.dev: the guide, every config
option, the test API, expect and its matchers, the vi utilities for mocks, spies, timers and
globals, snapshots, coverage, browser mode and its providers, workspaces and projects, test
environments, in-source testing, type testing, reporters, the CLI, the Node API for
extensions, migration guides between versions and from Jest, and the blog with the release
announcements) on every release tag from 0.1 to 5.x, including beta and rc builds; the rule
pages and README of @vitest/eslint-plugin on every tag; the README of every published
version of vitest, @vitest/ui, @vitest/browser and its providers (playwright, webdriverio,
preview), @vitest/coverage-v8, @vitest/coverage-istanbul, @vitest/web-worker,
@vitest/snapshot, @vitest/expect, @vitest/mocker, @vitest/pretty-format and vite-node; the
GitHub release notes of every release of Vitest and of @vitest/eslint-plugin; and the npm
registry list of every published version of these packages and of the deprecated
@vitest/coverage-c8 (date, dist-tag, dependencies and peer dependencies), and return the
matching excerpts with the versions each one belongs to.

Call this when a question is about Vitest -- vitest.config and defineConfig, test, describe,
it, test.each, beforeEach and the other hooks, expect and its matchers, expect.poll,
expect.soft, custom matchers, vi.fn, vi.spyOn, vi.mock and module mocking, fake timers,
snapshots and inline snapshots, coverage with v8 or istanbul, browser mode with Playwright or
WebdriverIO, test environments (node, jsdom, happy-dom), pools and parallelism, sharding,
filtering, watch mode, the UI, reporters, typecheck and expectTypeOf, in-source testing,
workspaces and projects, setup files, globals, the lint rules of @vitest/eslint-plugin --
and above all when it is about versions: since which version something exists, what changed
between versions, how to migrate (Vitest 0.x to 1 to 2 to 3 to 4 to 5, Jest to Vitest,
workspace to projects, coverage-c8 to coverage-v8), and which versions of Vitest, its
packages, Vite, Node and the browser providers work together -- the peer dependencies of
each version answer that. Example query: "vi.mock factory hoisting".

Do not call this for other test runners (Jest, Mocha, Jasmine, Node's own test runner,
Playwright Test, Cypress), for the libraries used inside tests (Testing Library, MSW,
Supertest), or for Vite itself: their documentation is not here, and the search will return
Vitest excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "4" keeps Vitest 4.x -- but also every
@vitest/* package 4.x, which share Vitest's numbers, and the 4.x line of vite-node if there
is one; @vitest/eslint-plugin has its own numbers (1.x). The title of every excerpt names its
package, so read it. Leave `version` empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first -- text
that stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lives. Vitest documents are named by their path in the docs folder
(docs/guide/mocking, docs/api/vi, docs/api/expect, docs/config/index, docs/guide/browser,
docs/guide/coverage, docs/guide/migration, docs/blog/vitest-3). The migration guide
(docs/guide/migration) describes the move from the previous major and from Jest. Lint rules
are named by their path in the plugin repository (docs/rules/no-focused-tests). Packages
without pages of their own are documented by their README. Release notes are titled by
package and tag; registry documents by package.

Which version to search first. For a question about how to do something today, pass the
line of the user's project or the most downloaded line -- Vitest "4": without it, the many
editions of the same page, which differ by a line or two, fill every place with older text.
Search without `version` for history, for migrations and for compatibility between packages.

For a question about when something appeared, changed or disappeared, search more than
once: the release notes and the migration guides name the exact version; then search the
lines before and after it to see how the documentation described it. For a question about
which versions work together, read the peer dependencies in the registry document of the
package that depends on the other.

Write the query in English, with the names the documentation uses (vi.mock, vi.fn,
vi.useFakeTimers, expect.poll, toMatchInlineSnapshot, test.each, defineConfig,
coverage.provider, browser.instances, environment jsdom). Everything here is English -- the
excerpts, the word index and the meaning index alike -- and the word index keeps only latin
letters and digits, so a query written in Ukrainian, Russian or any other non-latin script
matches nothing at all and comes back with `found: 0`. When the user asks in another
language, translate the question into Vitest terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which package and which version it is for. When the user did not name a
version, answer for the most downloaded line of that package on npm and say so; when two
lines are both in wide use, give both. When the excerpts behind a statement come only from
older versions, name those versions instead of presenting the text as current. A text found
only in beta or rc builds may never have shipped in a release: say so.

Answer in the language the user wrote in. When the question is about a feature's history,
a migration or compatibility, answer point by point: which package and since which version;
what changed in later versions; what the migration requires; and how it stands now. Every
point names the version and the document it rests on; a point the excerpts do not support is
left out, not guessed. When that language is Ukrainian, write as a Ukrainian engineer writes,
not as a translation from English: plain technical prose, and the Ukrainian word wherever one
exists -- "уривок", not "ексерпт"; "застарілий", not "депрекейтнутий"; "мок" and "знімок"
are fine. Never call this set of documents "корпус" -- say "документація Vitest".
Identifiers, option names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
