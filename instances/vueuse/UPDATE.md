# Оновлення корпусу vueuse

Реєстр (`npm-vueuse-*`), README (`npm-readme-vueuse-core`) і сторінки ліній 2.x/3.x (`docs-2020`) беруть версії з
опису пакетів у реєстрі npm, а релізи GitHub читаються з API щоразу заново: новий реліз потрапляє туди сам. Передрелізи
не беруться (`skip_versions: "-"` у README, `only` у `docs-2020`, `ghreleases-stable` — без дефіса в номері).

Руками оголошено:

- **Сайт vueuse.org** (`docs`): поле `tags` — останній тег кожної мінорної, найновіший першим (`"v15.0.0": "15.0.0"`).
  Нова мінорна — новий рядок на початку `tags`; новий латковий реліз тієї самої мінорної — заміна тегу в її рядку.
- **Новий пакет `@vueuse/*`** у монорепозиторії — нове джерело `npm-vueuse-<ім'я>` за зразком наявних; сторінки його
  функцій `docs` підхопить сам (тека `packages/`).
- **Лінії 2.x/3.x** (`docs-2020`) більше не виходять.
- **Окремі проєкти** (`motion-docs`, `gesture-docs`): поле `tags` — тег або повний SHA коміту публікації (`gitHead`
  у реєстрі npm) останньої версії кожної мінорної, з версією під префіксом (`"v3.0.3": "motion-3.0.3"`). Нова мінорна —
  новий рядок на початку `tags`. Якщо motion знову перекладе теки, — правило в `slug_rewrite`. README, реєстр, журнал
  motion і релізи head беруть нові версії самі.

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

```
./df vueuse refresh docs releases npm-readme-vueuse-core npm-vueuse-core   # і решту npm-vueuse-*
# вийшов окремий проєкт: motion-docs changelog-motion npm-readme-vueuse-motion npm-vueuse-motion тощо
./df vueuse refresh --missing    # джерела, яких не названо, лише докачуються
./df vueuse manifest
./df vueuse vectors
./df vueuse smoke
# Ctrl+C у терміналі з serve, і знову: ./df vueuse serve
```

Названі джерела оновлюються повністю, не `--missing`: у документі стоять усі версії, де текст був таким, тож новий
реліз змінює й старі документи (незмінна сторінка дописує нову версію в рядок `# версія:`). Документи редакцій, яких
у новому прогоні вже немає, лишаються в теці — їх переносять в окрему теку поза корпусом руками, перш ніж рахувати
вектори. Повний `refresh` — близько 25 хвилин мережею; сховище сирого `raw/` повертається з архіву разом із текстами,
тож після правки читача тексти перебудовуються без мережі: `./df vueuse build <id>`.

Якщо змінилися найпоширеніші лінії (на 29.10.2026 — 10.11 і 14.4, близько 29 % і 28 % завантажень `@vueuse/core`
за мажорами 10 і 14):

- у `prompts/search.txt` (абзац «Which version to search first») та `prompts/agent.txt` переглянути лінії за
  замовчуванням;
- у `checks.json`, у десятці `quality_model`, замінити `"14.4"` і `"10.11"` і звірити цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у `.env`) потрібен для дерев 99 тегів та історії комітів (кілька сотень звернень на
повний прогін).

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df vueuse quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
