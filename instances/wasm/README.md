# wasm — примірник фабрики docfactory

Чотирнадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про WebAssembly за офіційною
специфікацією всіх її видань — Core Specification, JavaScript Interface і Web API у виданнях 1.0, 2.0, 3.0 та в
поточній чернетці — і за обговореннями в issues репозиторію WebAssembly/spec. Код спільний і лежить у
`../../engine/`, `../../server/` та `../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у
[../../README.md](../../README.md).

## Навіщо

WebAssembly у браузері — це три специфікації разом: core каже, що таке модуль, коли він коректний і що робить кожна
інструкція; JavaScript Interface — як модуль компілюється, інстанціюється й викликається з JS (`WebAssembly.Module`,
`Instance`, `Memory`, перетворення значень); Web API — потокова компіляція (`compileStreaming`,
`instantiateStreaming`). Саме тут WebAssembly стикується з V8, тож примірник доповнює `v8` і `ecmascript`. Видання
помітно різняться: 2.0 додало multi-value, reference types, bulk memory і SIMD, 3.0 — GC, tail calls, exception
handling, memory64 і кілька пам'ятей. Питання «чи є це у виданні, яке підтримує мій рушій» відповідає лише текст
саме того видання, а «чому правило саме таке» — часто лише issues.

## Скільки цього

| Шар | Документів | Звідки |
|-----|-----------:|--------|
| Core, JS API і Web API видань 1.0, 2.0, 3.0 і поточної чернетки: документ на розділ верхнього рівня | 87 | w3.org (1.0, 2.0), гілка `gh-pages` репозиторію (3.0), webassembly.github.io (чернетка) |
| Issues репозиторію WebAssembly/spec, відкриті й закриті, з усіма коментарями (693 із коментарями) | 759 | GitHub API |

Разом 846 документів; фрагментів в індексі — 6 923 (`expected_passages` у `checks.json`). Фрагменти — це шматки
документів між заголовками, по яких іде пошук; однаковий розділ різних видань зливається в один з усіма виданнями.

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 1 із 10, за
змістом 4, разом 4; друга, «як модель» (терміни специфікації, з `version "3"`, як велить промпт), — 10 із 10. Цілі —
розділи всіх видань, бо для старшого видання правильна відповідь саме там. Промахи першої десятки:

- **Своїми словами без термінів.** «Таблиця переходів» не знаходить `br_table`, «виклик, що замінює кадр» —
  `return_call`: слова питання й специфікації не перетинаються. Тому промпт велить писати запит термінами; друга
  десятка з ними влучає щоразу.
- **Без версії місця займають issues.** Про `memory.grow` чи `call_indirect` сотні реплік в обговореннях, і пошук
  без `version` віддає їх поруч із нормою. Issues версії не мають, тож з `version "3"` вони не заважають; без версії
  промпт велить шукати лише історію й мотивацію правил.
- **Web API не може бути ціллю заміру.** Його розділи не мають підзаголовків, тож в індексі кожен — один розділ без
  назви, а `smoke` рахує ціллю лише розділ із назвою. Шукаються вони нормально.

**Видання у відповіді.** Кожна відповідь каже, якого видання вона стосується; без названого — за 3.0. Текст, що є
лише в чернетці, ще не став частиною випущеного видання; issue — обговорення, а не норма, і подається з номером.

## Що в цій теці

- `corpus/` — документи звичайними текстовими файлами; поруч `index.json` — паспорт: адреса, дата завантаження й
  сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження issues); `.mcp.json` — запис
  HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df wasm <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| видання 1.0 | W3C Recommendation 05.12.2019, w3.org | `bikeshed` |
| видання 2.0 | W3C Candidate Recommendation 17.12.2024, w3.org | `bikeshed` |
| видання 3.0 | зібраний сайт на коміті `0f70bfa4` гілки `gh-pages` — деплої тегу `wg-3.0` | `bikeshed` |
| поточна чернетка | webassembly.github.io/spec | `bikeshed` |
| issues з коментарями | GitHub API | `ghissues` |

Два нові читачі:

- **`bikeshed`** — специфікація, зібрана Bikeshed, однією сторінкою. Документ на нумерований розділ верхнього рівня
  (і на додаток «A Appendix»), підрозділи — заголовками з номерами видання («### 4.4.5 Memory Instructions»).
  Формули на сторінці вже відрендерено KaTeX-ом, вихідного TeX немає, тож читач збирає їх назад у рядок за
  розкладкою: індекси (`t_1*`), правила виведення («засновки ⟹ висновок»), граматики
  («numtype ::= i32 ∣ i64 ∣ f32 ∣ f64»), кроки алгоритмів — нумерованими вкладеними списками.
- **`ghissues`** — issues репозиторію з усіма коментарями: документ на issue, коментар — окремим розділом
  «Comment by АВТОР, ДАТА»; pull request-и відкидаються.

Особливості, які варто знати:

- **Мітки видань:** `1.0`, `2.0`, `3.0` і `3.0.draft` для чернетки. Фільтр `"3"` (чи `"3.0"`) бере 3.0 разом із
  чернеткою, `"3.0.draft"` — лише чернетку. Issues мітки не мають і знаходяться лише без `version`.
- **2.0 — лише датована адреса.** Під недатованою `w3.org/TR/wasm-core-2/` W3C тепер виставляє поточну чернетку
  робочої групи — вже з GC, tail calls, memory64 і `try_table`. Тому 2.0 — це Candidate Recommendation від
  17.12.2024, де жодної фічі 3.0 немає.
- **3.0 не має окремої сторінки** (лише PDF), тож береться зібраний сайт із гілки `gh-pages` на деплої тегу.
- **Номери розділів зсуваються між виданнями:** `br_table` у валідації — 3.3.5.8 в 1.0, 3.3.8.8 у 2.0, 3.4.2.6 у
  3.0. Тому однаковий текст зливається лише там, де збігся й номер (зазвичай 3.0 і чернетка).
- **Імена документів несуть специфікацію:** `core-3-validation`, `js-5-the-webassembly-namespace`,
  `web-2-streaming-module-compilation-and-instantiation`; у JS API і Web API номери розділів верхнього рівня теж
  різні між виданнями (у 2.0 з'явився розділ Introduction).
- **Лише англійська.** Видання 1.0, 2.0 і 3.0 заморожені (`frozen`): їхній текст не змінюється.

## Межі, про які треба пам'ятати

Тут немає реалізацій (V8 — окремий примірник `v8`, SpiderMonkey, Wasmtime), інструментів (Emscripten,
wasm-bindgen, wabt, Binaryen), WASI і пропозицій, ще не злитих у специфікацію (репозиторій WebAssembly/proposals).
Pull request-и репозиторію специфікації свідомо не взято. Додатки Metadata і Legacy Exceptions з того ж сайту не
взято: це не частина видань.

## Установка venv

```
cd instances/wasm
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df wasm sources --why   # перелік джерел і білий список
./df wasm refresh         # завантажити все задеклароване (~25 хвилин, переважно issues)
./df wasm manifest        # оновити паспорт
./df wasm setup           # Qdrant чи пошук лише по словах
./df wasm vectors         # залити корпус у docs-wasm (~20 хвилин)
./df wasm smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd /mnt/c/Projects/fwdays/docfactory
./df wasm serve          # порт 8774
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8774/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user wasm-docs http://127.0.0.1:8774/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `wasm-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df wasm setup --vectors      # з Qdrant: потрібен Docker; вектори рахуються ~20 хвилин
./df wasm setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

**4. Перевірка, сервер, клієнт.**

```
./df wasm smoke          # усі перевірки мають бути ok
./df wasm serve          # порт 8774, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
