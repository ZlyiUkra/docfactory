# Оновлення корпусу wasm

Дві різні роботи: звичайне оновлення (чернетка змінилася, з'явилися нові issues) і нове видання специфікації.
Порядок усередині кожної важливіший за самі команди.

Головне правило: **видання 1.0, 2.0 і 3.0 заморожені.** Їхні джерела позначено `frozen`, і `refresh` без назв їх
не чіпає: текст випущеного видання не змінюється. Живі лише два джерела на кожну специфікацію — чернетка
(`core-draft`, `js-draft`, `web-draft`) — і `issues`.

Друге правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Розділ, що зник із чернетки, чи issue, прибраний з GitHub, лишається в `corpus/`; прибрати — рішення людини.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Звичайне оновлення

```
./df wasm sources --why
./df wasm refresh                 # чернетки трьох специфікацій і всі issues (~25 хвилин)
./df wasm manifest
./df wasm vectors
./df wasm smoke
# Ctrl+C у терміналі з serve, і знову: ./df wasm serve
```

Issues перезаписуються цілком: у старий тред могли дописати коментар. Корпус не комітиться: після оновлення пишуть
новий архів і знову виносять тексти (README, розділ «Архівний режим»), а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що корпус підріс. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Вийшло нове видання

Скажімо, 4.0 — тег `wg-4.0` у репозиторії WebAssembly/spec.

**Крок 1. Знайти деплой тегу.** Коміт тегу:

```
git ls-remote https://github.com/WebAssembly/spec.git refs/tags/wg-4.0
```

Далі — перший коміт гілки `gh-pages` з повідомленням `deploy: <цей коміт>`; саме в ньому лежить зібраний сайт
видання. Для 3.0 це `0f70bfa4` (деплой `9d360199`, 26.09.2025).

**Крок 2. Дописати джерела** `core-4.0`, `js-4.0`, `web-4.0` за зразком `core-3.0`: адреса
`…/<коміт>/core/bikeshed/index.html` (для JS API — `js-api/index.html`, для Web API — `web-api/index.html`),
`version: "4.0"`, `frozen: true`. Якщо
W3C опублікував видання окремою датованою сторінкою — краще вона. Недатовані адреси w3.org (`/TR/wasm-core-2/`) не
годяться: під ними W3C виставляє поточну чернетку.

**Крок 3. Мітка чернетки.** Чернетка після 4.0 — `4.0.draft` у полі `version` джерел `*-draft`; у промптах
(`prompts/search.txt`, `prompts/agent.txt`) і в `checks.json` (`quality_model`) поточне видання `"3"` замінити на
`"4"`.

**Крок 4.** `refresh <нові id>`, `manifest`, `vectors`, `smoke`, як у розділі 1.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df wasm quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Що це означає тут:

- **Поточне видання — 3.0.** `prompts/search.txt` (абзац «Which edition to search first») і `prompts/agent.txt`
  велять на питання «як зараз» шукати з `version "3"`, що бере 3.0 разом із чернеткою.
- **Правила промпту, що вже є:** запит — термінами специфікації англійською; без версії — лише історія й мотивація
  (issues); кожна відповідь каже видання; текст лише з чернетки — ще не видання; issue — обговорення, не норма.
- **Останній результат:** у README, абзац «Замір `quality`».
