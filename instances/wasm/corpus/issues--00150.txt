# WebAssembly spec issue #150: Tail recursion optimization not trapping
# джерело: https://github.com/WebAssembly/spec/issues/150
# отримано: 2026-09-30

Issue #150, opened by jcbeyler on 2015-10-23, closed (completed) on 2015-11-05.

In the fac.wast there is an assert_trap:

(assert_trap (invoke "fac-rec" (i64.const 1073741824)) "runtime: callstack exhausted")

However, in my wasm-to-llvm-prototype code, LLVM removes the tail recursion and therefore this no longer traps.

Now I've seen here and there some comments about testing that we are not optimizing things away. So my first question relates directly to this test:
- Are we not going to allow that the Wasm compiler performs optimizations such as tail recursion if it wants to?
  - Is that true only for Web browser case or also the AOT case?
- What about the other tests then? Should we not allow the compiler to optimize things away if possible?
  - If for testing purposes, we could perhaps flag the module in a way to say: don't optimize this, we are testing something and, without that flag, be able to optimize away...

Ps: now that we have the awesome mirror: https://github.com/WebAssembly/testsuite; should these questions go there or is it simpler to keep them here?

## Comment by titzer, 2015-10-23

We have discussed tail call optimizations and the general consensus was that engines should not perform tail call optimization if it can change the space complexity of a program. Concretely an engine should not optimize infinite recursion to an infinite loop. However, an engine dropping a frame or two in the middle (when it can prove that doesn't eliminate a stack overflow situation) seems fine.

We want to add explicit proper tail call support to WebAssembly in the future.

If this is a case of LLVM optimizing a C program, that's a layer above WASM.

## Comment by jfbastien, 2015-10-23

This is about wasm _to_ LLVM (then to x86 or w/e), where LLVM optimizes the tail call.

I think as spec'd today LLVM is allowed to do this, as long as there's _some_ limit (where there was none before). i.e. it can transform to a loop, but needs to add an arbitrary limit to the number of iterations.

I like C++'s approach of saying that infinite loops are UB :-)
I think wasm could do something along those lines, but with the usual limited local nondeterminism.

## Comment by ghost, 2015-10-23

I think everyone agrees with making optimized tail call support explicit.

But I for one disagree with making it a requirement that implements not apply a tail call optimization when not explicit. It might even cost performance for some implementations to have to push to the stack to meet the requirement - implementations that naturally store a return address in a register. It affects them even for functions that do not make an tail call to themselves because there might be a chain A->B->C->A etc, so implementations are effectively required to have every function push to the stack. It's another ARM-blind decision.

Developers should not be writing code that depends on the stack being pushed for each function either.  Making the behaviour undefined in the spec. has this effect.

In practice I expect an implementations can just ignore the requirement, and I doubt any app is going to depend on the stack overflowing, so it's not a big mistake.

## Comment by sunfishcode, 2015-10-23

@jcbeyler The easiest way for LLVM-based implementations to implement this requirement is to apply the "disable-tail-calls" function attribute to functions generated from wasm. That way, you can always run the full optimizer, and it will automatically do the right thing.

@JSStats An implementation that ignores this requirement will fail the testsuite. Portability will be weakened if implementations ignore testsuite failures.

> I doubt any app is going to depend on the stack overflowing

There are many developers who are greatly motivated to depend on tail recursion optimizations and having the stack _not_ overflow. If we let implementations provide this feature implicitly and opportunistically (that is to say, unreliably), there's not just a risk that applications will start depending on particular implementations, there's a significant likeliness.

## Comment by sunfishcode, 2015-10-24

@JSStats Requiring tail call optimization to be explicit has the following advantages:
- The rules for deciding when a call is a tail call can be explicitly designed, rather than just being left up to whatever the first engines to implement it happen to do. For example, if we just let LLVM backends optimize tail calls whenever they feel like it, they're likely to do so in some situations which are not syntactic tail calls at the WebAssembly level, and decline to do so in some situations which are syntactic tail calls at the WebAssembly level.
- Interactions between tail calls and other possible future language features, such as stack introspection, can similarly be explicitly designed.
- Applications which depend on tail calls (eg. Scheme programs not translated out of tail-call style) wouldn't use a layer that falls back to non-tail calls because that would cause them to just crash; they would instead just do the feature test and then (hopefully) politely inform the user of this circumstance.

## Comment by sunfishcode, 2015-11-05

WebAssembly is an as-if platform; implementations are encouraged to optimize, and need not implement the semantics literally in the manner described in the spec, as long as they preserve the observable behavior, however tail call optimization is effectively very observable in practice.
