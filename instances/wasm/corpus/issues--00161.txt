# WebAssembly spec issue #161: address.wast testcase constants
# джерело: https://github.com/WebAssembly/spec/issues/161
# отримано: 2026-09-30

Issue #161, opened by kripken on 2015-11-04, closed (completed) on 2015-11-11.

That testcase has

```
    (func $bad1 (param $i i32) (i32.load offset=4294967296 (get_local $i)))
```

and it tests that that traps on loads of 0 and 1.
1. The offset seems odd - that isn't a 32-bit unsigned. Is it internally represented as a larger number?
2. If it's a 32-bit unsigned, shouldn't that  first turn into a 0, and so there is no fault?

## Comment by binji, 2015-11-04

https://github.com/WebAssembly/design/blob/master/AstSemantics.md#addressing mentions that the sum of address and offset is specified as being infinite precision.

## Comment by jcbeyler, 2015-11-05

Interesting to have an infinite precision, is there a rationale behind that?

## Comment by kripken, 2015-11-05

The _sum_ is treated that way for offset bounds checking. But it seems silly, at least to me, to allow infinite precision integers for the offset :) e.g. would we actually ensure that the binary format can pack an i512 in there? ;) seems like it should just be a uint32 field for 32-bit pointers, uint64 for 64-bit.

## Comment by sunfishcode, 2015-11-05

I agree. The sum is infinite precision because we don't want to worry about an offset causing an address computation to wrap around the address space and end up back in bounds. And the offset has the type of the address in the design repo so it looks like we just need to enforce that in the spec repo.

## Comment by titzer, 2015-11-05

Technically the offset is (or should be) a 32-bit unsigned constant and the
index is a 32-bit unsigned integer, so 33 bit precision is enough :-)

Obviously, we only bounds check against (mem_size - offset), which can be
computed at compile time and no 33-bit arithmetic is done at runtime.

## Comment by sunfishcode, 2015-11-10

I think there's a misunderstanding here. The 33-bit type is only a theoretical consequence of being the minimal result type of adding two 32-bit values without overflow. It doesn't actually exist anywhere in either the text or binary formats. We just have 32-bit values. I believe the ml-proto parser is incorrectly accepting an offset constant which is outside the 32-bit unsigned range.

## Comment by lukewagner, 2015-11-10

Agreed that the test case in the OP should be `assert_invalid` instead.  `Memory.offset` is an `int64` mostly just for simplicity (and lack of `uint32`).  `check.ml` already rejects negative values; it'd be easy to reject values > UINT32_MAX.
