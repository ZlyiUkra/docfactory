# WebAssembly spec issue #213: Strings - Unicode or C
# джерело: https://github.com/WebAssembly/spec/issues/213
# отримано: 2026-09-30

Issue #213, opened by ghost on 2016-01-21, closed (completed) on 2016-02-25.

I cannot locate any specification within the spec regarding strings. So, my questions are:
1. Is the zero-terminated string baked into wasm? (If so, why?)
2. What about Unicode? What is the semantics of a string literal, of a block of memory interpreted as a string?

If this question has already been answered, please point me to the spec.

## Comment by kg, 2016-01-21

Null terminated strings are smaller, even after stream compression. However, that really only matters if you have a bunch of them. So it would be perfectly reasonable to encode length values for import/export names and most other names in a module.

## Comment by ghost, 2016-01-21

If imports/exports have null termination, this must be only a property of the binary encoding of wasm files.

However, I have seen at least one unit test (https://github.com/WebAssembly/testsuite/blob/master/address.wast) where there are string literals in main code; and the assumption that it was ASCII (i.e., one byte/char) and null-terminated is part of the test.

Either strings _are_ permitted in wasm files’ memory sections, in which case string representation _must_ be decided, or they should _not_ be permitted. There is no middle ground here.

Personally, I can see arguments on all sides. As it happens, I think that a ‘common’ string format is more-or-less inevitable; so it would be better to get in front of that issue.

## Comment by kg, 2016-01-21

That's a misunderstanding of the test case, so thanks for citing the example: The strings in that test case are not null-terminated. The test case defines the size of the heap and then initializes the _start_ of the heap with a string literal. The remainder of the heap remains zero-filled as it would if it had no initializer data whatsoever.

So the string isn't terminated at all, it just happens to be followed by zeroes.

## Comment by rossberg, 2016-01-22

Just to clarify what others already said: the S-expression format intentionally is completely agnostic to any specific interpretation of string literals. As far as the implementation is concerned, it's just a sequence of random bytes, including 0-bytes, enclosed in ASCII quotes (and with a special meaning assigned to ASCII backslash values). No 0-byte is implicitly appended. The host can interpret these byte sequences in whatever way it sees fit, be it ASCII or Unicode or EBCDIC.

The `print` function cannot actually print strings, only ints or floats. So not even that currently commits to any specific interpretation.

## Comment by titzer, 2016-01-23

For the binary format, I just did the simplest thing, which was
null-terminated strings. I think we should take the suggestion from
@JSStats to use an LEB128-encoding length first. Then strings can be
uninterpreted sequences of bytes from the point of view of the
decoder/engine.
