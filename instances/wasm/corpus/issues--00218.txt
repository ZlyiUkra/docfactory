# WebAssembly spec issue #218: Formalize S-Expression Syntax grammar.
# джерело: https://github.com/WebAssembly/spec/issues/218
# отримано: 2026-09-30

Issue #218, opened by mbebenita on 2016-01-26, closed (completed) on 2016-02-25.

I've been prototyping a Bison grammar (which is LR(1)) for the S-Expression Syntax. As far as I can tell, there are situations when the current informal grammar is not LR(1) and needs two tokens of lookahead. For instance, sequences of optional lists of non-terminals cause problems. Here is a snippet of the grammar:

```
local
  : '(' LOCAL type_list ')'
  | '(' LOCAL NAME type ')'
  ;

local_list
  : local
  | local_list local
  ;

local_list_option
  : /* Nothing */
  | local_list
  ;

expression
  : '(' NOP ')'
  ;

expression_list
  : expression
  | expression_list expression
  ;

expression_list_option
  : /* Nothing */
  | expression_list
  ;

func
  : '(' FUNC name_option type_name_option param_list_option
    result_option local_list_option expression_list_option ')'
                  ^
  ;
```

When the parser is at the `^` location above, it can't determine whether the look-ahead token, `(` in this case, is part of the optional local_list or the expression_list. The parser can either shift and drop down into the `local_list` rule, or reduce `local_list_option` to `Nothing` and move on to `expression_list_option`, thus leading to a shift/reduce error.

In my opinion the AST text format should be really easy to parse and write grammars for. I'm not quite sure how to fix this. One way would be to make the tokens include their opening parenthesis, so `(LOCAL` would be just one token, instead of two `(` and `LOCAL`. This makes the grammar kind of ugly, but would fix a lot of the shift/reduce errors. The other approach would be to avoid optional non-terminals, or include delimiters of some sort.

Ideas?

## Comment by mbebenita, 2016-01-26

This is actually a good description of the problem:

From the example in the book:

```
statement
  : command optional_keyword '(' identifier_list ')'  // Rule 0
  ;

optional_keyword
  : /* blank / epsilon */ // Rule 1
  | '(' keyword ')'       // Rule 2
```

With one token of look-ahead `(`, you can't tell if you should take Rule 1 (since you are now seeing the `(` token before the identifier_list) or Rule 2 because it's the beginning of the optional_keyword production.

Bison usually picks either to reduce or shift if there is a conflict, however left unresolved this usually confuses the parser. For example, it can't parse:

```
(module
  (func (param $i i32))
)
```

I think adjusting the grammar to fix and group the position of optional non-terminals would solve this problem.
