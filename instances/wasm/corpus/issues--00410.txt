# WebAssembly spec issue #410: [test] JS: make top-level calls to call() compatible with async
# джерело: https://github.com/WebAssembly/spec/issues/410
# отримано: 2026-09-30

Issue #410, opened by bnjbvr on 2017-01-24, closed (completed) on 2017-05-23.

After the recent changes to the wast-to-JS converter, `call()` will return a `Promise`; for testing non-canonical NaNs and `i64`, temporary modules are created that emulate the behavior of `assert_return`, but these modules do create top-level `call()`. In an async context, this may create an unhandled rejected Promise, generating a warning in the developers console but there's no way a test harness could catch this; a test harness doesn't know if the Promise returned by `call()` will be used or not, and if it expects to be resolved or rejected.

Could we just add a check that they return `undefined` (that is, wrap these top level calls in `assert_return`), or have a dedicated `top_level_call` function in the generated JS harness, please?

## Comment by bnjbvr, 2017-01-30

`instance()` returns a Promise that's completed when the binary code is compiled and instantiated, so the variables are bound to `Promises`. If they're not explicitly handled by the harness, they won't be handled at all and the unhandled callback will be invoked, at the top level. Since `instance()` is used in situations where it is supposed to fail (`assert_unlinkable` for instance) and in others it is supposed to succeed (e.g. `call`), we can't assume in the impl of `instance()` that it will succeed or fail. Does it make sense?

I think the top level calls could just be as simple as `run(() => instance(...));`.

## Comment by rossberg, 2017-01-30

All uses of `instance` in the generated JS are supposed to succeed. The uses inside `assert_unlinkable` and friends are internal to the harness, you can implement them differently in the async variant (i.e., not go through the error-checking wrapper).
