## Comment by littledan, 2017-10-09

It's great to see so much attention to testing and encouraging the most welcoming environment for adding tests. This makes me really optimistic about the Wasm feature development process.

I think a two-way sync system could help with these goals. This technique has been used successfully in web-platform-tests for Chrome and Mozilla. With two-way sync, you can check in a change to tests either in an implementation repository, or in the upstream repository, and all repos are automatically synchronized with each other very frequently.

It looks like V8 currently maintains Wasm spec tests by pulling down a compressed archive, and in the SpiderMonkey source tree, I see generated tests in JavaScript which are based on the Wasm spec tests with a minimal wrapper template. Both of these processes seem to be "one way"--you add tests upstream, and then periodically pull them down. With either of these processes, I don't see a way that you can easily make a single patch which, e.g., fixes a bug, and in the same patch adds a regression test. It would be great if regression tests, added in a light-weight way, could be shared between implementations.

What would you think about using two-way sync for Wasm tests?

If we have two-way sync, maybe it would make sense to take advantage of web-platform-tests' infrastructure, or, maybe it would make sense to build parallel infrastructure. That's a narrower technical question; I wanted to talk about the project goals first.

## Comment by jgraham, 2017-10-10

> We should optimise for making the process of adding tests and creating proposals simple and uniform, because that has the best chance of encouraging as many tests as possible.

I strongly agree with this premise.

> It would be infeasible from my perspective to move the 95% of (web-agnostic) core Wasm tests away from the spec and the reference interpreter that is used to process them. And given that, it seems to make most sense to keep the other tests here as well.

From my "generic" (i.e. without being focused on wasm specifically) browser-vendor perspective, I would come to the exact opposite conclusion. Keeping tests with a spec is a local optimum for people directly working on that spec. But there is evidence (for example in @foolip's comment above) that having a central repository for testing that allows vendors to contribute to, run, and sync, tests across the entire platform in a uniform way is more effective in getting vendors to contribute to the tests and to run an up-to-date copy of the testsuite.

Yes, in some ideal world we might be able to create a uniform contribution and sync pipeline that worked across multiple test repositories. But that isn't the world we live in. On the other hand, I expect we could solve technical issues around wasm in wpt specifically is there's some need to e.g. run travis jobs that depend on something in the spec repo. I don't know what the current setup you have is, so it's hard to make specific technical promises, but it certainly seems to me to be worth looking at the detailed requirements and assessing them for feasibility.

## Comment by foolip, 2017-10-13

I commented on the framing of the agenda in https://github.com/WebAssembly/meetings/pull/80, but @jfbastien suggested I paste it here instead:

To clarify "the WPT effort would like to incorporate as many WASM tests as possible": while tests for any web-exposed features are welcome in WPT, it's not a goal to subsume all other test suites, what matters is that shared test suites exist, are well maintained, and that there's good infrastructure around them.

I have no involvement in wasm, but I think these are the important questions:
 1. Would implementers like to add/change shared tests together with their code changes? (IMHO, this is very important, as otherwise using shared tests always comes with an overhead. See this email for how much of a difference it seems to make.)
 1. If yes, how do you enable two-way sync between the repos involved?
 1. How do you get an always-fresh view of the state of the test suite, by which implementers can prioritize their work?

If merging into wpt and using wpt.fyi is the best answer, that'd be OK, and I don't anticipate you'd meet with any resistance. The build step could perhaps happen at runtime, looks like it's a python script already.

As for a one-way sync in order to get results into wpt.fyi, someone would need to keep that always running and make sure that the special directory can't be changed in wpt and that people can immediately discover why. A separate wasm.fyi would feel cleaner, but that's a lot of work.

It would be nice if the outcome is all wasm tests in one place, not split over spec/test and wpt/wasm as currently.
