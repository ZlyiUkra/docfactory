# WebAssembly spec issue #584: Memory allocation/growth failure
# джерело: https://github.com/WebAssembly/spec/issues/584
# отримано: 2026-09-30

Issue #584, opened by littledan on 2017-10-16, closed (completed) on 2017-10-18.

I'm probably reading the specification wrong, but it seems like allocating memory is specified to be infallable, but growing memory is specified to allow failure. Is this intentional?

If memory allocation fails during module instantiation, should the generated exception be LinkError, the browser-specific OOM error/crash, or RangeError?

If memory growth triggered by the Wasm executable code fails, should the generated JavaScript exception be RuntimeError, the browser-specific OOM error/crash, or RangeError?

(I was expecting all of these to be the browser-specific OOM error, but I see different things in the spec documents. I'm not sure if this is intentional or not.)

## Comment by lukewagner, 2017-10-17

Memory allocation during instantiation is fallible and should throw.  `WebAssembly.Memory.prototype.grow` throws a `RangeError` and IIRC that was chosen intentionally for symmetry with other JS builtins, so I think instantiation should throw a `RangeError`.  (FF gets that wrong, atm, but easy to fix.)

> If memory growth triggered by the Wasm executable code fails, should the generated JavaScript
> exception be RuntimeError, the browser-specific OOM error/crash, or RangeError?

 `grow_memory` in executable code never throws, but is defined to return -1 (so that wasm can test and handle).

## Comment by lukewagner, 2017-10-17

Actually, I could see the argument for either `RangeError` or whatever the engine normally does for a failed GC allocation (e.g., when `new WebAssembly.Memory(x)` fails) which seems to be different in FF.

## Comment by rossberg, 2017-10-17

The fallibility of allocating memory is supposed to be covered by the Appendix on implementation limitations. The grow_memory instruction is special because as @lukewagner mentions, it does not actually cause failure but returns regularly in that case. So that's why it has to make that case explicit (in the form of non-determinism).

## Comment by rossberg, 2017-10-18

All memory exhaustion conditions reported on the JS side are supposed to materialise as consistent exceptions (including Memory#grow). The grow_memory instruction does not cause an error, however, to enable handling the condition inside Wasm code. What alternative do you see without Wasm having exception handling?

## Comment by littledan, 2017-10-18

I was being sloppy when I said grow_memory above. I meant, Memory.prototype.grow vs instantiating a module. I was wondering wither this divergence was intended, and if not, which of the two behaviors should apply for both?

## Comment by rossberg, 2017-10-18

I see, fair question. I agree that they should behave consistently on OOM. I think as long as EcmaScript specifies a RangeError for similar cases we should follow that. Should TC39 decide to change that because it does not match web reality then we should move along.

However, Memory#grow has another, more explicit failure case, which is when the grow exceeds a user-specified maximum for the memory. I think that should throw a RangeError regardless.
