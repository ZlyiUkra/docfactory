# WebAssembly spec issue #590: Split up instantiation for better integration with JS spec?
# джерело: https://github.com/WebAssembly/spec/issues/590
# отримано: 2026-09-30

Issue #590, opened by littledan on 2017-10-20, closed (completed) on 2018-01-09.

JS.md has some steps that it executes to set up the JS representation of table objects, which occurs after most of instantiation but before the start function is executed. Error reporting of the start function also differs from previous error handling. Would it be reasonable to split off start function execution from the rest of instantiation, so that the integration can be cleaner here? For now, I can use rough language to express the same thing (as JS.md does now), but it's a little sub-optimal given how precise everything else is.

## Comment by rossberg, 2017-10-23

I now recall the problem: element segments can mutate *imported* tables before the start function runs. Becasue the start function can call back into JS and observe these through Table#get, these mutations have to be reflected properly on the JS side _before_ start, but _after_ the table segments have been executed (because that's when you know them). Step 20.3.3 in the current draft is the key piece.

Of course, the problem with that setup is that it won't extend to Wasm-internal ways of mutating the table anyway. So maybe the right way to deal with table.[[Values]] is to do the update lazily as part of Table#get. Then it always works, and the logic for updating tables early during instantiation is unnecessary. However, that would require keeping a more global funcaddr->JSFunction mapping around.
