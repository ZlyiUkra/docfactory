# WebAssembly spec issue #622: Multiple exports under same name
# джерело: https://github.com/WebAssembly/spec/issues/622
# отримано: 2026-09-30

Issue #622, opened by pepyakin on 2017-12-12, closed (completed) on 2018-05-03.

Spec states that each export should have a different name.

However, it looks like spec tests are relying on that module `spectest` publishes several functions with different signatures under the same name.

https://github.com/WebAssembly/spec/blob/fb7e7e1e381ffc283c923a87fdfea5ebbd213737/test/core/imports.wast#L36-L39

Why is that? Is `spectest` module is sort of magic?

## Comment by binji, 2017-12-12

It's only as magic as JavaScript :-)

`spectest.print` is just one export, but it happens to be a function that can print as many arguments as it is given with whichever types it is given. You could provide it in the import object as:

```
let importObj = {spectest: {print: console.log}};
```

## Comment by eholk, 2017-12-12

You can only have one export of a given name, but you can something as many times as you want.

This is useful especially in the case of importing JavaScript functions, as these will accept values of different types. For example, `console.info` can log any type object, but Wasm requires the types to match when you call a function. That means if you want to call `console.info` at different types, you must import it for each type you want.

That's what's going on here with `spectest` as well.

## Comment by eholk, 2017-12-22

@pepyakin For you example to work, you'd have to give a different name to each imported version of the function. For example:

```
(module
  (import "env" "derp" (func $derp))
  (import "env" "derp" (func $derp_i32 (param i32)))
)
```

I think the spec is still technically correct, because the names `$derp` and `$derp_i32` aren't really names, but get translated to numeric indices instead (so `$derp` is shorthand for 0 here, and `$derp_i32` for 1).

## Comment by rossberg, 2017-12-23

The spec only requires *export* names to be unique. It does not require *import* names to be unique. What that means is that you can import the same entity several times. If the host environment is loose with typing (like JavaScript) that also implies that you can import e.g. the same function under different types. However, it still conceptually is the same function. (Strictly speaking, though, it is up to the embedder to resolve imports, so other embeddings might handle that slightly differently and perform type-dependent resolution.)

## Comment by sunfishcode, 2018-02-13

I agree. I believe this sentence in the spec is incorrect:

> Each import is identified by a two-level name space, consisting of a module name and a unique name for an entity within that module.

Specifically, the word "unique" here seems incorrect. The same name can be resolved to two different entities within the same module, with or without different signatures, as discussed in #650 etc., and two imports within a module can have the same names.
