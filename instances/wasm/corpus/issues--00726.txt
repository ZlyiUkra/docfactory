## Comment by dschuff, 2018-04-07

* § 2.1.1 Many productions use the syntax "sym := \dots | A | B" to indicate adding additional cases to a previously-described production. A note about that convention could probably be added in this section.

* § 2.1.2 The rendering of replacement notation, e.g. `:s \with [i \slice n]` in the multipage version is a link to the correct `#notation-replace` anchor; however in the editor's draft it doesn't get special handling and renders more or less as *swith[i]* which is hard to read.

* § 2.2.4 "lengths of a name" should be "length of a name"

* § 2.4  "consuming (popping) argument values and producing (pushing) result values." This section uses "produce" and "return" fairly interchangeably when talking about result types or values of instructions. So this sentence should maybe mention that, e.g. "producing/returning (pushing) result values"

* § 2.4.1 "flavours" It looks like American spelling is used elsewhere in this document, so this should be "flavors" for consistency.

* § 2.4.2 "The drop operator simply throws away a single operand": could be more precise as something like "consumes a single operand and produces no result".

* § 2.4.3 "Variable instructions are concerned with the access to local or global variables." Drop the "the". It's cleaner.

* § 2.4.5 nop is listed with the control instructions. But it's a (non)-arithmetic instruction just as much as it's a (non)-control-flow-affecting instruction. I'd vote to put it with the parametric instructions since it takes 0 operands of any type :D

* § 2.4.5 "unlike other index spaces" I believe this is the first mention of the term "index space"; it should probably link forward to where index spaces are discussed (§ 2.5.1)

* § 2.5.1 "The index space for locals ... includes the parameters and local variables of that function, which precede the other locals." Should be something like "includes the parameters of the function, which precede the local variables"

* § 2.5.1.1 "The meta variables x,y ranges" should be "range"

* § 2.5.2 "All function types used in a module must be defined " It might be worth calling out that this includes types of imported functions?

* § 2.5.3 It might be worth calling out that function parameters are mutable too. Or just drop the statement that locals are mutable, if the purpose of this section is just to describe indexing?

* § 2.5.5 "The mems component" Given the outcome of https://github.com/WebAssembly/spec/issues/627 this component should probably be called "memories" (which I like better anyway). I believe this particular "mems" is really only reflected in parts of the abstract  grammar and doesn't appear e.g. anywhere in the text format. But I guess that probably means that the **mem** terminal symbol in the grammar should be "memory" as well?

* § 2.5.7 "initialize a subrange of a table at a given offset from a static vector of elements." It might be better as "initialize a subrange of a table (at a given offset) from a static vector of elements." so that the association of "from" is more clear.

* § 2.5.8 "The initial contents of a memory are zero bytes." might be better as "The initial contents of a memory are zero-valued bytes" or "zero-bytes" something to indicate that zero is the value and not the count. Also, same comment as 2.5.7 wrt "offset from"

* § 2.5.9 "The start component of a module optionally declares" I think we can drop "optionally". If present the component always declares the start function index (and all components are optional).

## Comment by rossberg, 2023-02-15

@binjune, it might have been answered at one of the in-person meetings, I don't remember. But the answer is that they are defined as part of the syntax for result types here. Note that the convention section merely defines "meta" syntax, i.e., notation to specify the actual syntax. The result brackets do not belong there, because they are part of the actual syntax being defined.

I have in fact considered dropping the brackets in the past, since they cause some clutter. But they also help clarity in some cases, especially for empty result types.
