# WebAssembly spec issue #983: The WASM specification is not human-readable
# джерело: https://github.com/WebAssembly/spec/issues/983
# отримано: 2026-09-30

Issue #983, opened by nta on 2019-03-12, closed (completed) on 2019-05-17.

Hi,

I've been trying to understand the WebAssembly specification, however was completely baffled by the use of mathematical notation and all the 'weird symbols' to define behavior of the specification.

Take for example this section (and it's not even one of the worst):

image

To me, as a human being with experience in computer programming, but who hasn't had the luck of having had a formal education in mathematics and related.. things, I feel excluded by the fact that practically every sentence in the specification is human-readable, except for the actual definitions of 'what is supposed to happen'.

I don't think it is a valid use case to write a specification for the presumably <10% of the world population that knows high-level mathematics, especially seeing that it is perfectly possible to have an interest (and knowledge) in software development without being a 'math genius'.

Other specifications I've seen write things like this in human-readable pseudocode using plain English characters, and not having to resort to this unreadable jumble of math symbols and two-dimensional notation.

## Comment by bitwalker, 2019-03-12

I'm not trying to suggest that you may not have a point, but what part of your example is high-level mathematics? The paragraph before defines `N` (i.e. the bit width of the integer), and the rest is a simple formula for calculating the value, with two possibilities depending on which predicate is satisfied first (i.e. the part in parentheses), and even explains that it is a two's complement representation for additional clarity.

I agree if there are unfamiliar operators or symbols in the spec, that they should absolutely be defined, but I'm not sure it is valid criticism to say that symbols/operators which see extremely broad use are not "human readable" (e.g. the symbols/operators in your example).

Perhaps there is a better example to make the argument with?

EDIT: As an aside, I find the example easy to read (and I have no math background beyond high school calculus, which was years ago); _but_, pseudo-code might be more grokkable. The problem is that pseudo-code rarely has any defined semantics, where math notation does. When you are trying to define a spec, the semantics are very important, so I don't think it is viable to replace the math with code (for example). Human readable text without any clear representation of what the text describes is difficult to parse in my opinion, I like to have both, and from my reading of the spec, generally speaking there is always text which explains in plain English what is shown in the notation.

## Comment by bitwalker, 2019-03-12

@nta That notation is explained in plain english right above:

- The function type functype must be valid.
- Let [t1∗​]→[t2∗​] be the function type functype.
- For every valid store S1​ extending S and every sequence val∗ of values whose types coincide with t1∗​:
  - Executing hf in store S1​ with arguments val∗ has a non-empty set of possible outcomes.
  - For every element R of this set:
    - Either R must be ⊥ (i.e., divergence).
    - Or R consists of a valid store S2​ extending S1​ and a result result whose type coincides with [t2∗​].
- Then the function instance is valid with function type functype.
