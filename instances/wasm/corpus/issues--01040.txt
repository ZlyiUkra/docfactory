# WebAssembly spec issue #1040: Malformed vs invalid test assertions
# джерело: https://github.com/WebAssembly/spec/issues/1040
# отримано: 2026-09-30

Issue #1040, opened by AndrewScheidecker on 2019-07-01, closed (completed) on 2022-08-04.

Some spec tests rely on implementations precisely distinguishing malformed vs invalid modules, but use modules that are both malformed and invalid. As an example: https://github.com/WebAssembly/spec/blob/master/test/core/if.wast#L894

In this case, the `if`/`end` labels don't match, but the `if` instruction also doesn't validate because the stack is empty.

This means that conforming implementations must strictly observe the error priority of the reference interpreter: it must parse the whole module and find any malformed syntax, even if it realizes that the module is invalid before it encounters malformed syntax.

Is it valuable to require implementations to find the syntax error instead of the validation error? I don't think it is: what matters is that the module is rejected. It simplifies the spec to factor parsing and validation into separate stages, but I imagine most implementations will be doing them simultaneously.

Note that the code to convert the tests to JavaScript currently doesn't distinguish between `assert_invalid` and `assert_malformed`: https://github.com/WebAssembly/spec/blob/master/interpreter/script/js.ml#L76

IMO the test scripts should just use the equivalent of `assert_malformed_or_invalid`.

## Comment by rossberg, 2019-07-01

Yeah, I'm not surprised such tests exists, since it's easy to make such mistakes in negative tests. But they should be considered a bug in the test suite. If you discover such cases, fixes are most welcome. ;)

But this problem is not really related to the malformed vs invalid distinction -- a module may also be malformed (or invalid) alone for multiple reasons, and it's not specified which one fires in such a case either. So making the two kinds indistinguishable would not really improve anything fundamental. Either way, you are always free to ignore the difference.

The relevant difference between malformed and invalid is that the latter conceptually is a type error independent of the format (binary vs text) and programs that are merely invalid can still be converted between the two. The former is a format-dependent syntax error.

## Comment by AndrewScheidecker, 2019-07-05

One more test I'm a little skeptical of: https://github.com/WebAssembly/spec/blob/666dc4cb8d4a81d386a7a716000bb85fbbbd06a2/test/core/binary.wast#L740

The spec interpreter calls this malformed because the `br_table` eats one of the `end` opcodes in place of a label index, so there isn't a `end` corresponding to the `func`.

However, the `end` opcode is an invalid label index, so many reasonable implementations will just fail the module as invalid.

AFAICT there isn't a way to write this test that isn't just testing some other part of parsing/validation.
