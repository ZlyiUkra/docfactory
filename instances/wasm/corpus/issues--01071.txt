# WebAssembly spec issue #1071: [spec] on the use of result type
# джерело: https://github.com/WebAssembly/spec/issues/1071
# отримано: 2026-09-30

Issue #1071, opened by Huxpro on 2019-09-16, closed (completed) on 2019-09-26.

The use of `resulttype` in the current spec is somewhat contrived, inconsistent, and uncomfortable. It could occur in at least 3 forms:

1. it's written as the non-terminal explicitly, e.g. Structure - control instr,
2. it's written as the optional occurrence explicitly e.g. Validation - control instr
3. it's implicitly used as a constraint on the star in the "Note". e..g. Validation - function type

The coercion between them happens often and often happened implicitly as well.

This is also inconsistent with the PLDI formalization and reference interpreter implementation. I understood the fact that multi-value proposal is postponed. But could we formalize this _temporary_ constraint better?

One idea is to generalize all occurrence of this notion of the result type and only attach the constraint once and for all during the validation (keep the full generality of un-typed dynamics)?

## Comment by rossberg, 2019-09-16

Yeah, the reason may be somewhat non-obvious, but these differences reflect what is expressible in the binary format, which has different representations of function types (which include n-ary results syntactically) and block's resulttypes (which currently cannot). Hence it's a typing restriction on the former but a syntactic restriction on the latter.

The cause of this difference was the desire to compress the common case of block types in the binary format. Unfortunately, that ad-hoc representation remains ugly even with the multi-value extensions, where it is confined to a new blocktype, though.

The more uniform representation in the interpreter predates the ad-hoc block type encoding. I should perhaps have changed it.

The PLDI paper abstracted away from the indirection through typeidx's to express function types, so could ignore this nuisance.
