Since MathJax 3, MathML output is no longer supported because browsers' implementations were too incomplete/buggy. So there is nothing we can do here.

## Comment by BenjaminAster, 2023-04-06

Since January, MathML is now supported in all browsers (including Chrome and all other Chromium-based browsers!). Instead of MathJax (which, as already mentioned, doesn't support MathML anymore), LaTeXML can be used, which is a tool that converts LaTeX directly to static MathML, eliminating the need for any JavaScript or SVGs. The NIST Digital Library of Mathematical Functions is a wonderful example of a site that uses LaTeXML to render all of its mathematical expressions as MathML.

## Comment by BenjaminAster, 2023-04-08

Chromium supports a subset of MathML called MathML Core which should, in theory, cover most use cases for math rendering.

- **Hyperlinks** can be embedded via an HTML `<a>` element inside of a MathML element, so `<mi><a href="https://en.wikipedia.org/wiki/Pi">&pi;</a></mi>` instead of `<mi href="https://en.wikipedia.org/wiki/Pi">&pi;</mi>` should do the job.
- **Fonts** should definitely work in Chromium, I don't know what went wrong here.
- **Alignment** should be possible in Chromium with CSS. Is MathJax maybe generating old alignment HTML attributes that are not part of MathML Core?

Would you perhaps mind copy-pasting the generated HTML/MathML code of the example section above, I might be able to get it working in Chrome. If not, I'm sure Frédéric Wang can help us here, he is the person who mostly wrote the MathML Core specification **and** the person behind Chromium's MathML implementation.

The Sphinx people definitely seem to be interested in direct MathML generation but didn't implement it because of the lack of browser support. Now that MathML is supported, I hope they might re-consider it. See https://github.com/sphinx-doc/sphinx/issues/6092

Btw, with this excessive size profile, we probably don't want to ship these pages in native MathML even if we could. If this one figure already takes ~600 KB, than the full spec would surely come in at 100 MB or more. For perspective, the same figure is <2KB in Latex.

## Comment by BenjaminAster, 2023-04-08

Ok, I could get most MathML layout to work (including hyperlinks in `<a>`s), but yeah, it is a bit clunky; Chromium needs a -webkit prefix for `text-align: -webkit-right` in an `<mtable>`, and `vertical-align: top` to get the `moduleinst = {` to the top just doesn't do what it is supposed to. Fonts do work, they just need to be specified via CSS and not the `mathvariant` HTML attributes. So I guess it does make sense to wait some more time until Chromium's `<mtable>` implementation gets better; I might open some issues for Chromium in the meantime.

The big file size is mostly due to all the formatting and attributes that MathJax is adding; if you strip them away and minify the MathML, it becomes a lot smaller. Especially for the multipage spec where the pages aren't that extremely long, I think the user experience would be much improved if it would be rendered instantly by the browser instead it of taking 10 seconds to load all the MathJax.

## Comment by ericprud, 2023-04-10

It sounds like there are two prongs  of attack for long-term and immediate publication:

**long-term:** lean on/entice sphinx devs to:
* use recent MathML spec
* minimize superfluous markup, with the goal of getting closer to the Latex payload size.

**immediate:** use MathJax to render as MathML;
* pick a representative subset of the spec and side-by-side it with the current MathJax rendering.

## Comment by rossberg, 2023-04-10

I'm not really convinced that the size of the MML can be reduced significantly. The above does not actually look unreasonably bloated, and stripping it of some MJX artefacts will probably save 20% at best.

AFAICS, the size difference comes from two factors: For one, the MML contains plenty of cross-links and font tags, which take up significant space. In the Latex representation, these are all abstracted into macros, so don't take up wire space repeatedly. Second, HTML/SGML simply is an inherently space-inefficient format, and the markup-heavy use case of math is a kind of worst-case scenario for it.

Anyway, thanks @BenjaminAster for looking into this! I think being able to configure MathJax to use MML for rendering would already be a big improvement.
