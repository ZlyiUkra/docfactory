# WebAssembly spec issue #1182: Binary integer format
# джерело: https://github.com/WebAssembly/spec/issues/1182
# отримано: 2026-09-30

Issue #1182, opened by verbessern on 2020-04-22, closed (completed) on 2020-04-23.

Hi, the definition of `uN` in 5.2.2 does allow **only** one training zero, no zero**s** as written in the note down. That is correct, because if the zeroes are many, the second alternative of `uN` must be changed, to reflect it, but that is 'bad', because it will introduce ambiguity. For `sN` also.

## Comment by binji, 2020-04-22

It's intended to allow multiple trailing zeros, for example these are all of the valid u32 encodings of 3:
```
0x03
0x83 0x00
0x83 0x80 0x00
0x83 0x80 0x80 0x00
0x83 0x80 0x80 0x80 0x00
```

So there is already ambiguity in encoding. I don't understand how does the definition for `uN` needs to change for decoding, however.

## Comment by rossberg, 2020-04-23

The definition is working as intended. Here is the derivation for representing the value 4 in 3 bytes
```
4:u32
|
0x84:byte 0:u25 => 2^7*0 + 0x84-2^7 = 4  (0x84 >= 2^7 /\ 32 > 7)
          |
          0x80:byte 0:u18 => 2^7*0 + 0x80-2^7 = 0  (0x80 >= 2^7 /\ 25 > 7)
                    |
                    0x00:byte => 0  (0x00 < 2^7 /\ 0x00 < 2^18)
```
Similarly, you can derive an encoding up to 5 bytes. Longer sequences will be rejected by the side condition `N > 7` and because uN doesn't allow negative length.

## Comment by verbessern, 2020-04-23

I see. For me that are not trailing zeroes, that are 0x80 and one trailing zero. If the meaning is for the usable bits then yes, no issue.

ps. For the protocol, the grammar rule uN is not ambiguous now. Its nondeterministic with one byte of look ahead.
