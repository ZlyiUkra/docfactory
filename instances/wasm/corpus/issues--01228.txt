# WebAssembly spec issue #1228: Clarify binary encoding of prefixed opcodes
# джерело: https://github.com/WebAssembly/spec/issues/1228
# отримано: 2026-09-30

Issue #1228, opened by bnjbvr on 2020-07-28, closed (completed) on 2021-10-07.

Some opcodes are prefixed by a single opcode byte, but it's unclear how to encode the "sub"opcodes that are following (e.g: i32 signed saturated truncation from f32, 0xfc is the prefix, 0x00 is the subopcode byte). My reading of https://webassembly.github.io/spec/core/binary/instructions.html seems to tend towards "it's a single byte", but some implementations (namely Binaryen, WABT, Spidermonkey) seem to allow a variable-length u32 there. In addition to this, the upcoming SIMD spec will introduce variable-length u32 subopcodes, and since there might be a lot of them, it makes sense to use variable-length encoding there. So two questions here:

1. Do we want to uniformize subopcodes encoding, that is, follow SIMD's way and use variable-length u32 encoding for all the prefixes?
2. If not, would it make sense to precise in the spec text that these should be a fixed (as opposed to variable-length) single byte?

## Comment by binji, 2020-07-28

There was a CG decision in 2017 to say that all prefixed instructions would be a prefix byte followed by a LEB128. It's unfortunate that the spec doesn't implement it this way. For now, I think we should go one of two directions:

1) Keep the spec as it is, and fix existing implementations to require a single byte for the math prefix. (This is the only prefix byte currently in phase 5). We can extend this to LEB128 later, as we've done for other fields.
2) Consider this a mistake in the spec, and update it to LEB128 now. Similarly, update all upcoming proposals.

Personally, I'd prefer to do the second.

## Comment by ngzhian, 2020-07-29

Yea agree it's not a big factor, I don't know how many proposals will fall into that magic range between 0x80 and 0xff number of instructions, it looks like either they have very little instructions that they fit in 0x80, or that they have so many that they need SIMD.

Besides encoding size, we found some slowdown in compilation speed due to using LEB encoding. It could be due to the branching (checking if byte or LEB), so if we make everything LEB, we can probably gain that back.

## Comment by binji, 2020-08-05

We agreed in the meeting that to change the spec (and all proposals) to use a single prefix byte followed by an leb128-encoded opcode. See https://github.com/WebAssembly/spec/pull/1235 for the spec change.
