# WebAssembly spec issue #1292: [js-api] Integration with the ResizableArrayBuffer and GrowableSharedArrayBuffer proposal
# джерело: https://github.com/WebAssembly/spec/issues/1292
# отримано: 2026-09-30

Issue #1292, opened by syg on 2021-03-02, open.

The ResizableArrayBuffer and GrowableSharedArrayBuffer proposal is a TC39 proposal that is currently stage 2.

There was some discussion of how the proposal might integrate with the Wasm/JS API. It seems better to move the discussion here to get a concrete plan and to get more Wasm eyes on the issue.

As a starting point, I suggest the following changes to the WebAssembly.Memory API:

- `Memory` will have a new `resizableBuffer` attribute.
    - Returns a `ResizableArrayBuffer` or `GrowableSharedArrayBuffer` instance.
    - If an `ArrayBuffer` was vended by the `buffer` attribute on the same instance, that `ArrayBuffer` instance will be detached. `SharedArrayBuffers` and `GrowableSharedArrayBuffer` will alias the same memory.
    - If the `Memory` was created with a maximum size, that size will be reflected on the `ResizableArrayBuffer` or `GrowableSharedArrayBuffer` instance.
    - Otherwise, the maximum size is `2^32`.
- `Memory`'s `buffer` attribute will detach any `ResizableArrayBuffer` buffers vended by the `resizableBuffer` attribute.
- `ResizableArrayBuffer`s gotten via `Memory`'s `resizableBuffer` attribute will:
    - Throw on `transfer()`, since they can't be detached.
    - Throw on `resize()` calls that are shrinks.
    - Throw on `resize()` calls that are not in multiples of the wasm page size. (Thanks @conrad-watt)
- `GrowableArrayBuffer`s gotten via `Memory`'s `resizableBuffer` attribute will:
    - Throw on `grow()` calls that are not in multiples of the wasm page size.

Thoughts welcome.

(Also, what is the process for bringing such a "normative PR" that's not a full proposal to the CG? Is it just an agenda item?)

@conrad-watt Been a while, restarting an inquiry here. So I recently learned it _is_ possible for a WebAssembly.Memory grow to incur a copy, i.e. the underlying data pointer changes a la `realloc` + copy. JS resizable ArrayBuffers were designed to require in-place growth.

So that leaves us with the question of, if a WebAssembly.Memory's buffer is exposed as a resizable buffer, and in-place growth fails, what should happen?

I see at least a few options:

1. Fail. After all, memory growth can fail for any number of reasons. This is analogous to failing to grow shared memories, which must always be in-place.
    1. Slight variation: fail with a message saying, if the user really wants, go back to a fixed-length buffer and try again. Maybe a copy will succeed.
1. Refuse to expose memories without a provided `maximum` as resizable buffers.
1. Silently convert the buffer back to a fixed-length buffer and try again.

Both 1 or 2 seem reasonable to me. I'm not _really_ considering option 3, which is extremely gross.

## Comment by syg, 2025-02-26

> @syg Can you elaborate on this? That sounds like an implementation detail, but I'm not sure if that shows up somewhere.

It's true that it's not required for spec compliance, but the design was informed by a security constraint that a ArrayBuffer's data pointer should not change, except via detaching. So while the design doesn't preclude an engine from copying under the hood, it allows for the possibility of not copying.

So for engines that do not copy, growing a Memory that's reflected as *non-resizable* buffer is fine today because the security constraint above isn't violated: you detach the old buffer, and e.g. invalidate all JIT code that might've baked in the data pointer as a constant. Detaching is pretty safe since it's one-way and can't be undone. For those engines, if growing a resizable cannot be done in-place, we still don't want to run afoul of that security constraint. For JS resizable buffers, that's done by always requiring a maximum length: if the implementation can't reserve the virtual memory up front, fail early.

## Comment by syg, 2025-03-14

> Does this mean that on current 32-bit platforms, it's expected that we can successfully instantiate a Wasm module with a memory that has 2^16 pages set as its max size, but attempting to create a ResizeableArrayBuffer in pure JS with analogous max size (2^32 bytes) would always throw? I might have thought naively that they'd both succeed and fail under the same circumstances - would the Wasm memory use a different implementation strategy (like relocating/copying grows)?

Yeah it does. Wasm succeeds but JS will fail.

The engine interpretation of "maximum" between Wasm memories and JS RABs kind of diverged over time.

Wasm memory maximums passed in to the constructor (which I'll refer to as "requested maximum") are like true hints. If the engine can't allocate virtual memory up to the requested maximum, it backs off and tries until it gets a successful allocation. This lower, internal maximum is the true maximum and not exposed to users. This is a "fail late" strategy wrt in-place growing.

RAB maximums passed to the constructor are like demands. If the engine can't allocate virtual memory up to the requested maximum, it throws at construction. IOW, if the internal maximum can't be the requested maximum, allocation fails. This is a "fail early" strategy wrt in-place growing.

This difference in interpretation is kind of moot though for V8. Even if RABs adopted Wasm's "fail late" strategy, we still can't expose 2^32 without widening all length fields on 32bit, which isn't worth it for this edge case.

Edit: And presumably it's also risky to do the flip side thing and make Wasm memories fail to allocate with 2^16 pages on 32bit, since that succeeds today.
