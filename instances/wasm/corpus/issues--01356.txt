# WebAssembly spec issue #1356: If a module's start function fails, is the module instantiated?
# джерело: https://github.com/WebAssembly/spec/issues/1356
# отримано: 2026-09-30

Issue #1356, opened by TonyGuil on 2021-09-06, closed (completed) on 2022-08-04.

If a module's start function fails, is the module instantiated? I would assume not. But that invalidates the very last test in linking.wast. The module's start function executes an unreachable instruction, and traps. So according to my interpreter, the module has not been instantiated. But then we get (Line 388):
(assert_return (invoke $Ms "get table[0]") (i32.const 0xdead))
and this is supposed to call function $f in the uninstantiated module, via a table element in a previously instantiated module $Ms. My interpreter accordingly generates an uninitialized error, but the test suite expects the call to succeed.

Is this right? Or have I missed something?

## Comment by rossberg, 2021-09-07

Well, since there is an explicit test for this you can assume it is intentional.

Conceptually, the start function is just a function that is called automatically after the module has been initialised. At this point, imported memories and tables have already been updated, potentially with functions from the modules. It would complicate both semantics and implementations if there was a requirement to roll that back: semantically, there either would have be some implicit mutation to tables, or function values themselves would have to be defined to be mutable and go through state changes. Both are rather undesirable properties and complications.

## Comment by TonyGuil, 2021-09-07

I am not suggesting that changes to memories and tables be rolled back. As you say, that would be problematic. But according to the spec (page 18):
The start function is intended for initializing the state of a module. The module and its exports are not
accessible before this initialization has completed.
So, although memories and tables have been initialized, the module itself has not, if the start function traps. Hence (presumably) its functions can't be called. I think the test would make more sense if the module's table was initialized with an imported function, that could safely be called, instead of with $f from the uninitialized module.

## Comment by conrad-watt, 2021-09-07

The phase "initializing the state" in that note is intended to be read as meaning initializing the _programmatic_ state of the compiled code, rather than the Wasm-language-level state (i.e. the allocation of functions/memories etc). I agree there's some ambiguity here, but only in the explanatory note - the normative text describes the intended behaviour precisely.

For example, you could imagine a compiled C++ runtime using the start function to set up the initial state of the memory allocator as a struct laid out in linear memory. This can be considered "initialization" in the sense that the work needs to be done before any regular compiled code is run, but it can only occur _after_ the state of the module has been "initialized" in a Wasm-language-level sense (i.e. the memory allocated with 0-bytes and made available for access, any helper functions have been allocated, active data and element segments have been executed etc).

The test is checking that the effect of an active element segment executed during instantiation is observable (and moreover that the referenced function has been correctly allocated) even if the start function subsequently fails part-way.

## Comment by TonyGuil, 2021-09-07

@conrad-watt, you are strenthening my case! If the start function fails, then (in your example) the memory allocator might be in an invalid state. So we can't call any functions in the module, because who knows what might happen?

I agree that the entry in the imported table should be initialized to $f. What I am saying is that when this function is _called_ indirectly by get table[0] in the assert_return test on line 388, this call should fail. Imagine what might happen if $f tried to allocate memory!

So there should in fact be _two_ tests: the original test, but altered to expect an error "uninstantiated module" or some such; and a new test, which initializes the table entry to an _imported_ function from a different module, that can safely be called.

## Comment by conrad-watt, 2021-09-07

>  If the start function fails, then (in your example) the memory allocator might be in an invalid state. So we can't call any functions in the module, because who knows what might happen?

There would be an error in the functional behaviour of the compiled program, but nothing unsafe would happen from the perspective of the Wasm VM. It's not the Wasm language's responsibility to mitigate against these logic bugs - hardening can be inserted by the source language compilation scheme if it's deemed appropriate (e.g. programmatically checking that the start function successfully executed).

> What I am saying is that when this function is called indirectly by `get table[0]` in the `assert_return` test on line 388, this call should fail.

It is very unlikely that this behaviour will be changed now, because it would cause a web compat issue. In any case, I believe the current behaviour is preferable (edit: because the error-on call semantics would likely increase engine complexity and penalise the performance of compiled modules that handle their start function correctly).

## Comment by rossberg, 2021-09-07

I agree that the current behaviour is preferable, for the reasons mentioned above. Specifically, it avoids inducing stateful semantics into values that do not otherwise have state (esp function and module instances).
