# WebAssembly spec issue #1902: [interpreter] Support JS test wrappers for calls with non-flat function types
# джерело: https://github.com/WebAssembly/spec/issues/1902
# отримано: 2026-09-30

Issue #1902, opened by f52985 on 2025-05-09, closed (completed) on 2025-05-10.

Here is a test case written in `wast` format:

```wast
;; sample.wast
(module
  (type $t (sub (func (result f32))))
  (func (export "f") (type $t)
    (f32.const 0)
  )
)
(assert_return (invoke "f") (f32.const 0))
```

This defines a function with a non-final float (`f32`) as its return type.

When this `wast` file is converted into a JavaScript test case using the `./wasm` binary (built from the `wasm-3.0` branch) with the following command:

```
./wasm sample.wast -o sample.js
```

and then executed using a JavaScript engine such as V8:

```
./d8 sample.js
```

it results in the following unexpected `LinkError`:

```sh
LinkError: WebAssembly.Instance(): Import #0 "module" "f": imported function does not match the expected type
  return new WebAssembly.Instance(mod, imports);
         ^
LinkError: WebAssembly.Instance(): Import #0 "module" "f": imported function does not match the expected type
    at instance (sample.js:65:10)
    at sample.js:209:16
    at run (sample.js:82:3)
    at sample.js:209:1
```

I'm not sure whether the issue lies in the generated JavaScript test case or the behavior of the browser engines.
However, since the same error occurs across all major engines (V8, SpiderMonkey, and JavaScriptCore),
it seems likely that the issue originates from the JS code generator (harness).

I'm not very familiar with this area—could someone take a look?

## Comment by rossberg, 2025-05-09

Yeah, this is a limitation of the interpreter, whose JS converter currently only supports `invoke` assertions requiring Wasm wrappers (as for floats) over functions that have "flat" function types (no subtyping, no recursion). I can look into extending that, but it's not entirely straightforward.
