## Comment by rossberg, 2025-06-19

Hm, can you elaborate why you believe that it should not be valid? Because struct is not a supertype of array?

The implicit source doesn't need to be a supertype of the target type of a cast, they only need to have a common supertype (i.e., be in the same subtype hierarchy). As a general rule, we must always allow a value of subtype to be legal where a supertype is expected. That e.g. is to enable certain code transformations (like inlining) that might lift more tightly typed code into casts where they result in such a case. Technically, that's also needed for soundness, since type preservation of reduction would fail otherwise.

Consider e.g. this example:
```
(func $f (param $x anyref) ... (if ... (ref.cast arrayref (local.get $x))) ...)
(func $g (param $y structref) ...)
(func $h (param $z structref) (call $g (local.get $z)) (call $f (local.get $z)))
```
The call to $f in $h is perfectly legal. And it should be fine to inline $f without making it impossible to type the resulting code.

## Comment by rossberg, 2025-06-19

I just used anyref and friends for brevity, it is no different for non-null types.

In the typing rule for ref.cast, rt' can be any supertype of "what is on the stack", since subsumption can always be applied (per the third of the rules for instruction sequences).

Concretely, in your example, (local.get 0) has principal type ε → (ref struct), but by subsumption, can also be given a supertype like ε → (ref any). And with that, the sequence (local.get 0) (ref.cast (ref array)) is perfectly well-typed according to the rule for casts.

Note how the linear validation algorithm handles that (or rather, the analogous case for ref.test) by simply checking the operand type against the top type of the hierarchy.

The type `none` indeed is uninhabited, i.e., there are no values with that type. So in my inlining example above, assuming $f isn't buggy, the if leading to the cast presumably cannot be reached for the call site in $h and becomes dead code after inlining and specialising the parameter type. If reached, the cast would unconditionally fail, but that's fine as far as Wasm is concerned.

## Comment by rossberg, 2025-06-20

> I thought extern is an external compatible representation of a wasm reference.

The opposite. It is a host pointer/value represented inside Wasm, in its most efficient representation (which may or may not point to a Wasm object). The type already existed in Wasm 2.0, before Wasm even had its own reference values.

> Or do you need a non-webassembly "type" code which is not accessible from wasm (i.e. it can be converted to any, but all casts must fail, since its representation is unknown.

Yes. In an implementation where Wasm and host pointers have different representations or live in different heaps, this essentially boxes the external pointer into an internal Wasm heap object.

> I can understand the concept of a value outside the scope of wasm (extern value), but converting it to any type is a strange operation for me.

This is so that one can define module import interfaces whose functions operate on some abstract reference (of type any), in such a way that they can be implemented as either a Wasm or a host module. Important for polyfilling or self-hosting scenarios.
