# WebAssembly spec issue #1990: [spec] Latest spec does not properly define the semantics of `all_true`
# джерело: https://github.com/WebAssembly/spec/issues/1990
# отримано: 2026-09-30

Issue #1990, opened by d0sboots on 2025-09-28, closed (completed) on 2025-10-01.

I am looking at the current version of https://webassembly.github.io/spec/core/bikeshed/, dated "Editor’s Draft, 26 September 2025" and documented as release 3.0.

In it, there are 18 hits for "all_true", but none in the execution section. The semantics for `shape.vtestop` are defined based on vtestop_sh where vtestop is instantiated as all_true, but there is no all_true numeric defined. (I'm also not sure if all_true can be defined implicitly as a lanes-expansion of a numeric this way; at the very least, it's not the most understandable way to do it.)

In contrast, https://www.w3.org/TR/wasm-core-2/ explicitly defines `shape.all_true` in 4.4.3.15.

## Comment by d0sboots, 2025-10-01

AFAICT, this is still not fixed. The new "iall_true" numeric will return a value of size N, the same size as its input. (I think - the numerics aren't explicit about this, especially when using the bool helper, so it's confusing.) Regardless, the way this is currently specced vtestop will definitely work the same way as vrelop, which is to perform the underlying op lanewise. But the types are mismatched - the return type would need to be v128 for that. Also (more importantly), that's not how all_true works - there's an extra global "and" step that is missing.

I'm not sure why there's this desire to define it in terms of a numeric when that's fundamentally not how it operates - it's much more straightforward to just define the semantics in the instruction, similar to any_true.

An additional factor in this is that, taken in isolation, the iall_true numeric is *extremely* confusing, to the point of looking like a bug. The name is "all_true", but it returns 1 if *any* bits are true, so from the perspective of the operation itself it seems like it should be called "iany_true". This would also be a terrible name though, given the existence of v128.any_true and how this is used for all_true. That is why the original name of ineqz was the best, and using it explicitly instead of implicitly.
