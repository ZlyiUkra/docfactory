# WebAssembly spec issue #2072: Should importing or exporting a function count as declaring it for ref.func?
# джерело: https://github.com/WebAssembly/spec/issues/2072
# отримано: 2026-09-30

Issue #2072, opened by eqrion on 2026-02-04, open (reopened).

A function must be 'declared' by use outside of the function section in order to be allowed to be used with `ref.func`.

I recently discovered that just importing a function doesn't count:
```
(module
  (import "" "" (func $f))
  (func
    ref.func $f
    drop
  )
)
```
This code fails to validate in V8, SM, and JSC complaining that $f wasn't pre-declared.

This seems odd to me, and I can't think of any reason we shouldn't consider it valid. But maybe I'm missing something?

I then double checked the spec here, and I believe this is the relevant rule in module validation:

The `refs` field on `C` is the set of valid targets for ref.func. If I'm reading it right, that means that both exports and imports aren't included in `refs`.

SM and V8 treat exporting a function as declaring it, while it looks like JSC does not do that. So there's inconsistent handling on exports.

I personally think that exporting/importing a function should count as declaring it. I'm pretty sure imports/exports and declaring was discussed a long time ago, but can't find anything relevant.

## Comment by tlively, 2026-02-05

Looks like this was initially discussed here: https://github.com/WebAssembly/reference-types/issues/76. I didn't see any mentions of import or export sections there, though. I believe the original idea was that only instances of `ref.func` instructions are counted, but that contradicts the descriptions of `refs` in the typing context: "References: the list of function indices that occur in the module outside functions and can hence be used to form references inside them." That description would seem to include imported and and exported functions.

Given that the real motivation is allowing engines to emit different prologues and epilogues for indirectly callable functions, we should certainly include imported and exported functions as being referencable; there's no telling whether some other module that may import an exported function will call it indirectly, so the engine has to be prepared for that. I would support updating the spec to reflect this.

## Comment by fitzgen, 2026-02-05

> How does Wasmtime handle imports?

We reject the OP module and do not treat imported functions as declared in our validator:

```shell-session
$ wasm-tools validate ~/scratch/import-declared.wat
error: func 1 failed to validate

Caused by:
    0: undeclared function reference (at offset 0x1e)
```

(Note: `wasm-tools validate` is the same validator used in Wasmtime)

However, in the engine, after the module has been validated and assuming it was not rejected as invalid, we will mark all imported functions as "escaping" (~= spec's "declared") and therefore generate the same set of trampolines and such for imported functions that we will for functions that are exported or declared in a passive element segment. (And these trampolines are required in both cases.)

---------

Anyways, to be clear: I am in favor of clarifying/updating the spec to make both imports and exports explicitly declared.

## Comment by rossberg, 2026-02-06

Interestingly, the test suite even has a test for exports (see ref_func.wast), so that is an oversight in the spec, which is trivial to fix. (It's somewhat surprising that JSC fails an official test. ;) )

For imports, the story is different, though. The whole mechanism is based on checking which function indices appear where. But function imports have the same status as function definitions: neither has an occurrence of a function index, so naturally neither can contribute to the set of refs. I would prefer not to hack that further.

## Comment by rossberg, 2026-02-06

Well, as currently spec'ed, a declaration doesn't (and never needs to) know "its" index. Technically, indices are never "added" to a name space, they are just that, indices into a given array. That's certainly a technicality that can be changed, but given that the whole check already is such a wart, I would prefer to keep it simple and not grow that wart further if it hardly matters in practice.

Maybe a practical factor to consider is that implicit declaration on imports also creates more complexity for tools like module mergers, which will then have to identify all uses of an import and possibly synthesise new element segments.

## Comment by rossberg, 2026-02-06

@eqrion, a merger statically links two (or N) modules by resolving export/import pairs between them and then "concatenating" the module bodies. Beyond that, it shouldn't have to do more than shifting indices accordingly. It could keep resolved exports, but it certainly can't keep resolved imports, which is why imports are the bigger issue.

That said, even for exports, multiple "resolved" exports from different modules (when merging more than two) could happen to have a name clash. Or you don't want to expose what becomes an implementation detail of the combined module. So in fact it would be preferable if exports didn't have implicit extra meaning either (and I'd like to shift away a bit from my earlier statement about exports).

Wrt modules, it always comes down to the same observation: attaching any implicit meaning to imports, exports, or module boundaries conflicts with inter-module composability/transformability, notwithstanding intra-module convenience.
