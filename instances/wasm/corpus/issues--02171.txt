# WebAssembly spec issue #2171: [spectec] Reftype subtyping premises in opsem
# джерело: https://github.com/WebAssembly/spec/issues/2171
# отримано: 2026-09-30

Issue #2171, opened by raoxiaojia on 2026-05-21, closed (completed) on 2026-05-26.

I noticed that the reference instructions allow an additional `reftype_sub` at their premises, e.g.: https://github.com/WebAssembly/spec/blob/d34a973e70ab127476b5d8591c6f558be289b929/specification/wasm-3.0/4.3-execution.instructions.spectec#L149-153. But `Ref_ok` already has a `sub` rule that allows the same subtyping.

It seems that the idea is to making subtyping the responsibility of `Ref_ok`, as I see that other uses of `Ref_ok` such as `elem/tableinst_ok` no longer has a separate subtyping step. There are also inlined TODO comments suggesting the version without the rules, which seems fine to me.

I wonder if the extra subtyping premise in the opsem rules can be dropped -- unless there's a pass in spectec that requires them to be explicitly present in the rules?

## Comment by raoxiaojia, 2026-05-22

> Backend-interpreter manually defines $Ref_ok as a function that returns the most specific type for the given ref, so it requires the explicit variable that will store the return of the function.
>
> I think it might be possible to refactor this behavior by making $Ref_ok as a predicate function that requires a ref and a reftype, and returns a boolean value to be directly used in the if instruction.

I agree that the implementation is correct. The decision here is more about the design principles, on whether it is the duty of the typing predicate to allow subtyping, or if the use sites have to explicit state that matching is allowed.

There are several different instances of this decision in the spec, and I think what feels 'right' can be different per instance. E.g. stack types/function types certainly want the subtyping rules to be part of the relation as well (else the definition needs a lot of boilerplate `<:` in many places), where as for import matching it feels right that the imports simply have whatever type it 'declares' to have, and the importing module should perform the matching check. For this particular instance, it seems that the decision was to move the subtyping obligation to the predicate (given the TODOs)?

Having redundant checks used to be fine, because matching is supposed to be transitive anyway. But with Wasm 3.0 where types themselves can be invalid, this becomes more subtle, as the double subtyping by `Ref_ok/sub` and the explicit matching in the opsem rule allows transitivity without the validity of the intermediate type (basically, the existential in the opsem rule), which is a requirement in `heaptype_sub/trans`. So having a double matching here would appear more permissive than what the relational rules actually define.

Incidentally, it is actually not more permissive for now, because it happens that the set of types that can be returned by `ref_ok` seems to be disjoint with the valid LHS of counterexamples for heaptype_sub/trans without validity of the intermediate.

## Comment by raoxiaojia, 2026-05-22

(removing a previous comment as it was incorrect)
Actually, I realised that this is an issue of the `Ref_ok` relation itself, as `Ref_ok/sub` itself can be applied recursively to permit transitivity with invalid intermediate type, even in a valid store, because there's no validity guard on the RHS. Compared to `Instrs_ok/sub` which has a RHS validity guard:
```
rule Instrs_ok/sub:
  C |- instr* : it'
  -- Instrs_ok: C |- instr* : it
  -- Instrtype_sub: C |- it <: it'
  -- Instrtype_ok: C |- it' : OK
```
Compared to `Ref_ok/sub`:
```
rule Ref_ok/sub:
  s |- ref : rt
  -- Ref_ok: s |- ref : rt'
  -- Reftype_sub: {} |- rt' <: rt
```

Note also that `rt` is fully arbitrary via this rule, so store validity doesn't prove that it is valid.

So dropping the redundant side condition in the opsem rule wouldn't fix this. If `Ref_ok/sub` is intended to be part of the relation itself, then it seems correct to similarly add a RHS validity guard, similar to what `instrs_ok/sub` does. But that seems verbose; perhaps in this case it's better if `Ref_ok/sub` isn't part of the `Ref_ok` relation to avoid this unwanted transitivity issue, and make it the duty of the use site to state the matching premises?

I noticed that there are potentially other places which is missing such a guard that allows unrestricted transitivity, such as `externaddr_ok/sub`; they might need to be addressed similarly.

## Comment by raoxiaojia, 2026-05-24

I thought `Val_ok` would be fine, as it simply uses `Ref_ok` in the `ref` arm, which should allow subtyping in my suggested version. Maybe there's something I missed when you said a similar duplication is required for `Val_ok`?

More concretely, I was suggesting factoring out the base cases of `Ref_ok` into a function, something like the following:
```
def $canonical_reftype (store, ref) : reftype
def $canonical_reftype (REF.NULL_ADDR) = (REF NULL BOT)
def $canonical_reftype (REF.I31_NUM) = (REF I31)
(etc)
```
and then `Ref_ok` becomes a single subtype matching:
```
relation Ref_ok: store |- ref: reftype

rule Ref_ok/match:
  s |- ref : rt
  -- if $canonical_reftype (s, ref) = rt'
  -- Reftype_sub: {} |- rt' <: rt
```
This preserves the semantics of `Ref_ok` completely (both versions allow matching), so downstream uses of `Ref_ok` do not have to state the matching. The RHS guard can be avoided in this way, as there's no recursive application of `Ref_ok` in the premise now.

One genuine question though: should `Num_ok/Vec_ok` be interpreted as stating the principal type or the subtyping-agnostic rule in this case?
