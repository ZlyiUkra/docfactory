# WebAssembly spec issue #2182: [spec] Missing/over-lenient context for resulttype validity for admin `frame` block
# джерело: https://github.com/WebAssembly/spec/issues/2182
# отримано: 2026-09-30

Issue #2182, opened by raoxiaojia on 2026-06-08, closed (completed) on 2026-06-08.

In the typing rule of `frame`, the current two different versions of it (formulated slightly differently in the spectec source and spec's soundness appendix) are both slightly too lenient (copied below).
```
rule Instr_ok2/frame:
  s; C |- FRAME_ n `{f} instr* : eps -> t^n
  -- Frame_ok: s |- f : C'
  -- Expr_ok2: s; C' |- instr* : t^n
```

The spectec version doesn't check the validity of the result type `t^n`. Note that this does not outright allow ill-formed resulttype `t^n`, because each individual `instr_ok` does carry a guard on the validity of the produced type.

The actual issue is in the lifting of the body type to the `frame` block itself, which used to be fine in pre-3.0 but is too lenient now, since `t^n` can carry context-aware indices such as `IDX` that can mean different things inside the body's context (C') and the outer context (C). This allows a closed struct reference to be re-described as an `IDX` type under the inner context, smuggled across the frame, and then re-interpreted as a different type under the outer context.

The prose version does the validity check, but it checks `t^n` under `C`, which does not prevent the above issue. Adding a validity check for `t^n` under the inner context `C'` doesn't help either, as the same smuggling goes through.

imo the fix should be to require `resulttype_ok: {} |- t^n : OK` under an empty context, which forces the body to type itself with a closed type. This seems correct design-wise as well, as a function's result type should be context-agnostic when used by other entities.

(I didn't create a PR as I didn't actually find where to fix the prose only.)
