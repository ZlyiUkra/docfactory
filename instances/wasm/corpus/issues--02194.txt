# WebAssembly spec issue #2194: [spec] instrs_ok/seq's principality requirement is slightly over-restrictive
# джерело: https://github.com/WebAssembly/spec/issues/2194
# отримано: 2026-09-30

Issue #2194, opened by raoxiaojia on 2026-06-22, closed (completed) on 2026-06-23.

There seems to be an issue in the structural rules of `instrs_ok` that actually prevents `instrs_ok/seq` to be applied because it requires the principal typing form (i.e. `instr_ok`) for the head instruction: https://github.com/WebAssembly/spec/blob/869387d57e9a6f6fd65554a7593bd7e4e921787d/specification/wasm-3.0/2.3-validation.instructions.spectec#L613-L633

For example, `[nop; drop]` should be typeable under `[t] ->_(locs) []` (locs is irrelevant here). However, `instr_ok` only permits `nop` to be typed under `[] -> []`, and `instrs_ok/seq` strictly requires sticking the principal type of `nop` with the rest, which makes the derivation impossible. `instrs_ok/frame/sub` can't be applied preemptively as a setup step either since none of them is applicable/useful.

Note that adding an `instrtype_sub` to `instrs_ok/seq` will not resolve this issue, since `instrtype_sub` only allow subtyping instead of framing (like `instrs_ok/frame` does). imo the correct fix needs 2 changes: change `instr_ok instr_1` to `instrs_ok [instr_1]` in `instrs_ok/seq`, and then separately add a `instrs_ok/lift` that simply lifts `instr_ok` to `instrs_ok` of the same signature -- or equivalently, compress these into `instrs_ok/seq`, which will then need to handle both frame and subtyping. This permits the principal type of `[instr_1]` to be pre-weakened (to [t] -> [t]) to fit the rest of the stack.

This fix might need to be backported to the 1.0/2.0 spec as well.

## Comment by rossberg, 2026-06-22

Hm, I think you're right. I can see two possible fixes:

1. Add
```
rule Instrs_ok/instr:
  C |- instr : t_1* -> t_2*
  -- Instr_ok: C |- instr : t_1* -> t_2*
```
and change Instrs_ok/seq to operate on `instr_1* instr_2*`.

2. Move /sub and /frame from Instrs_ok to Instr_ok.

I have to sleep over which one I prefer. WDYT?

## Comment by raoxiaojia, 2026-06-22

For proofs I'd strongly prefer 1 (I was suggesting it as well in my comment) -- having an `instr_ok` that somewhat captures the 'principal type' of each instruction is really convenient for a large part of the proofs, and moving `/sub` and `/frame` into `instr_ok` would annihilate that nice relation. This also restricts the need of cut-elimination entirely within `instrs_ok` only (instead of entangled between the two relations).

I can see how option 2 allows it to use one fewer rules though, so there's some point in that as well.
