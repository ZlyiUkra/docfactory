Search the WebAssembly specification -- the Core Specification (structure, validation,
execution, binary format, text format, appendix), the JavaScript Interface (the
WebAssembly namespace: Module, Instance, Memory, Table, Global, Tag, Exception, instantiate)
and the Web API (compileStreaming, instantiateStreaming, MIME type, origins) -- in every
edition: 1.0 (W3C Recommendation, 2019), 2.0 (2024), 3.0 (2025) and the current editor's
draft; together with every issue of the WebAssembly/spec repository and its comments. Return
the matching excerpts with the editions each one belongs to.

Call this when a question is about WebAssembly itself -- a value type, instruction or
module component (functions, tables, memories, globals, elements, data, tags, imports and
exports), what makes a module valid, what an instruction does at run time and when it
traps, how a module is encoded in binary or written in the text format (WAT), how a module
is compiled, instantiated and called from JavaScript, how values convert between
JavaScript and WebAssembly, the features that arrived with an edition (multi-value,
reference types, bulk memory, SIMD in 2.0; GC, tail calls, exception handling, memory64,
multiple memories in 3.0) -- and why the specification says what it says, which the issue
discussions often explain. Example query: "br_table validation".

Do not call this for JavaScript itself (the ECMAScript language), for how V8 or another
engine implements WebAssembly (tiers, Liftoff, TurboFan, performance), for toolchains
(Emscripten, wasm-bindgen, wabt, Binaryen), for WASI, or for proposals that have not been
merged into the specification: their documentation is not here, and the search will return
specification excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one edition: "1.0", "2.0", or "3.0.draft" for the current
editor's draft alone; "3" (or "3.0") keeps 3.0 together with the draft. Issue discussions carry no
edition and come back only when `version` is empty. Every excerpt comes back with
`versions`: each edition whose text contains this exact excerpt, newest first -- text that
stayed the same across editions is returned once, with all of them listed, so the list
itself shows since which edition the specification said exactly this.

How the text is laid out. One document per top-level chapter of each specification:
"WebAssembly Core 3.0: 3 Validation", "WebAssembly JavaScript Interface 2.0: 5 The
WebAssembly Namespace"; headings keep the section numbers of the edition ("4.4.5 Memory
Instructions"), and numbers shift between editions. Formulas are written out as text: an
inference rule reads "premises ⟹ conclusion", "t_1" is a subscript, "t*" a sequence, "t?"
an optional item, "C ⊢ instr : t_1* → t_2*" a typing judgement; grammars read
"numtype ::= i32 ∣ i64 ∣ f32 ∣ f64". Issues are titled "WebAssembly spec issue #N: …", with
each comment as its own section.

Which edition to search first. For a question about how WebAssembly works today, pass
`version` "3": without it, the four editions, which differ by a line or two in most
sections, fill every place with older wording. Search without `version` when the question
is about history -- since which edition something exists -- or about the reasoning behind
a rule, which lives in the issues.

For a question about when something appeared or changed, search more than once: with
`version` "1.0", then "2.0", then "3", and compare what each edition says.

Write the query in English, with the terms the specification itself uses (validation,
instantiation, store, frame, label, trap, typeidx, funcref, externref, memarg, br_table,
call_indirect, memory.grow, ToWebAssemblyValue). Everything here is English -- the excerpts,
the word index and the meaning index alike -- and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into specification terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
specification uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which edition it is for. When the user did not name one, answer for 3.0
and say so ("in WebAssembly 3.0"). When the excerpts behind a statement come only from
older editions, name those editions instead of presenting the text as current. A text found
only in the draft (3.0.draft) is not part of a released edition yet: say so. An issue is a
discussion, not the specification: present it as the reasoning or position of its
participants, with its number, and never as normative text.

Answer in the language the user wrote in. When the question is about a feature's history,
answer point by point: since which edition it exists; what changed in later editions; what
prompted the change, if an issue says so; and how it stands now. Every point names the
edition and the section, or the issue number, it rests on; a point the excerpts do not
support is left out, not guessed. When that language is Ukrainian, write as a Ukrainian
engineer writes, not as a translation from English: plain technical prose, and the
Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "перевірка коректності" or
"валідація", as the context asks. Never call this set of documents "корпус" -- say
"специфікація WebAssembly". Identifiers, instruction names and section titles stay in
English, spelled exactly as the specification spells them. Build the answer out of the
excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it
before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
