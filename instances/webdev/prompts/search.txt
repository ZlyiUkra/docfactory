Search web.dev and the documentation of the web-vitals library, in English. web.dev is the site
of the Chrome team on building for the web: its Learn courses (CSS, JavaScript, HTML,
Accessibility, Forms, Images, Performance, Progressive Web Apps, Design, Testing, Privacy, AI), its
articles -- Core Web Vitals and the other metrics (LCP, INP, CLS, FCP, TTFB, TBT, the retired FID)
with their thresholds and how those were chosen, measuring in the field and in the lab, optimizing
each metric, loading and rendering performance, images and fonts, caching, service workers and
offline, installable apps, accessibility, forms, security headers, Baseline and browser
compatibility -- and its blog. web-vitals is the small JavaScript library that measures these
metrics in real browsers: the README of every stable release from 0.1.0 to 6.2.3 (onLCP, onINP,
onCLS, onFCP, onTTFB, onFID before 5.0, the attribution build, sending the data to analytics,
thresholds, browser support), its changelog, one entry per release, and the guides for upgrading to
v4, v5 and v6. Returns the matching excerpts with the versions each one belongs to.

Call this when a question is about web performance and its metrics (what counts as a good LCP, INP
or CLS, why a page is slow, how to find and fix a slow interaction or a layout shift, how to
measure real users), about loading images and fonts, lazy loading, preloading and priorities,
caching and service workers, making a site installable or working offline, accessibility (focus,
keyboard, ARIA, contrast, forms), responsive layout and modern CSS as web.dev teaches it, and about
using the web-vitals library or upgrading it. Example query: "INP good threshold 200 milliseconds
75th percentile".

Do not call this for the reference of an HTML element, a CSS property or a Web API (the mdn
instance has MDN), for the specifications themselves (the webstandards instance), for React or
Next.js specifics (the react and nextjs instances), or for Chrome DevTools, Lighthouse and Chrome
extensions, whose documentation is not here: the search will return web.dev excerpts that merely
mention them, with confident-looking titles.

`version` narrows the search to the web-vitals library and nothing else: web.dev pages have no
version and are left out by any filter. The README of web-vitals carries every release that had
exactly that text ("6.2.3", "6.2.2" ...), a changelog entry its release, an upgrade guide the major
it leads to ("6.0.0"). A shorter version takes every release under it: "6" is every 6.x, "6.2"
every 6.2.x, "0.2" every 0.2.x. Leave `version` empty to search everything. Every excerpt comes back
with `versions`: each version whose documents contain this exact text, newest first.

Which version to answer for. web.dev pages are the current site; each one says when it was
published and last updated -- say so when the advice may have aged (a page from 2019 about FID or
about a tool that has changed). For web-vitals, unless the user names a version, answer from the
newest release (6.2); when the project uses an older one (onFID exists up to 4.x, the attribution
fields were renamed in 4.0), filter by its major and say what changed since.

Where the documentation lives. web.dev pages are named by their path: articles-vitals,
articles-lcp, articles-inp, articles-cls, articles-defining-core-web-vitals-thresholds,
articles-optimize-lcp, articles-optimize-inp, articles-optimize-cls, learn-performance-welcome,
learn-css-box-model, learn-accessibility-focus, blog-interop-2025. The web-vitals README is
web-vitals, its changelog entries web-vitals-changelog-6.2.0 and so on, the upgrade guides
web-vitals-upgrading-to-v4, -v5 and -v6.

Write the query in English, with the names the documentation uses (Core Web Vitals, Largest
Contentful Paint, Interaction to Next Paint, Cumulative Layout Shift, First Contentful Paint, Time to
First Byte, Total Blocking Time, 75th percentile, field data, lab data, CrUX, PageSpeed Insights,
long tasks, Long Animation Frames, scheduler.yield, requestIdleCallback, fetchpriority, preload,
preconnect, loading lazy, srcset, sizes, font-display, content-visibility, bfcache, service worker,
Workbox, web app manifest, onINP, onLCP, onCLS, attribution, reportAllChanges, sendBeacon, ARIA,
aria-label, focus, tabindex, prefers-reduced-motion, container queries, :has(), Baseline). Everything
here is English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks in
another language, translate the question into these terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words of the
query had to appear in the text, so a query phrased in other words than the documentation uses may
miss; "meaning+words" means a second, meaning-based index answered as well, and a paraphrase had a
chance.

Answer in the language the user wrote in. When the question is about a change between versions of
web-vitals or about a metric that replaced another (FID to INP), answer point by point: since which
version or date; what changed; what the migration requires; how it stands now -- each point with
the document it rests on; a point the excerpts do not support is left out, not guessed. When that
language is Ukrainian, write as a Ukrainian engineer writes, not as a translation from English:
plain technical prose, and the Ukrainian word wherever one exists -- "уривок", not "ексерпт";
"метрика", "поріг", "взаємодія", "зсув макета", "застарілий", not "депрекейтнутий". Never call this
set of documents "корпус" -- say "web.dev" or "документація web-vitals". Metric, API and property
names stay in English, spelled exactly as the documentation spells them. Build the answer out of
the excerpts that came back, not out of memory: if an excerpt was cut, read the whole of it before
describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3; `version`
is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.
