Search the texts of the web standards themselves, in English: the WHATWG living standards
(HTML -- the event loop, navigation and history, scripting and modules, Web Workers,
server-sent events, Web Storage, postMessage, parsing; DOM -- events, AbortController and
AbortSignal, nodes, MutationObserver; Fetch -- requests, responses, the fetch algorithm,
CORS and preflight, credentials; URL; Streams; WebSockets; Infra; Web IDL; Encoding; MIME
Sniffing; Storage; XMLHttpRequest; Cookie Store API; Notifications; Fullscreen; Console;
Compression), the W3C specifications Content Security Policy Level 3, Fetch Metadata,
Referrer Policy, Permissions Policy, Secure Contexts, Mixed Content, Service Workers, Web
Application Manifest, Push API, WAI-ARIA 1.2, ARIA in HTML and WCAG 2.2 together with
Understanding WCAG 2.2, Techniques for WCAG 2.2 and the ARIA Authoring Practices Guide
(patterns and practices), the IETF texts RFC 9110 (HTTP semantics), RFC 9111 (caching),
RFC 9112 (HTTP/1.1), RFC 6265 and the 6265bis draft (cookies, SameSite), RFC 6455
(WebSocket), RFC 6585 (429 Too Many Requests), RFC 6797 (HSTS), RFC 9457 (problem
details), RFC 7519, 7515, 7517, 7518 and 8725 (JWT, JWS, JWK, JWA and their best current
practices), RFC 6749, 6750, 7636 and 9700 (OAuth 2.0, bearer tokens, PKCE, OAuth security
best current practice) and RFC 9106 (Argon2), OpenID Connect Core and Discovery, the
OpenAPI Specification 3.1.1, JSON Schema 2020-12 (core and validation), and ERC-20,
ERC-721 and ERC-4361 (Sign-In with Ethereum). Returns the matching excerpts.

Call this when the question is about what a standard actually requires -- the normative
rule, not a tutorial: the steps of an algorithm (main fetch, the CORS check, the event
loop processing model, URL parsing, structured clone), when a CORS preflight is sent and
what it must contain, how SameSite and the __Host- prefix are defined, what a cache may
store and for how long, what a status code means and which headers go with it, the close
codes and framing of the WebSocket protocol, which claims a JWT must validate, how refresh
token rotation and PKCE are specified, what a CSP directive allows, what a WCAG success
criterion demands and at which level, which ARIA role and keyboard behaviour a widget
pattern needs, what an OpenAPI field or a JSON Schema keyword means. Example query:
"CORS preflight request Access-Control-Request-Method".

Do not call this for frameworks and libraries (React, Next.js, NestJS, Express, Node.js
APIs, Passport, Auth.js, socket.io), for tutorials and browser support -- which browser
implements what and since when is not in a standard; that answer lives in MDN Web Docs, a
separate documentation set -- or for standards that are not listed above (HTTP/2, HTTP/3,
TLS, CSS specifications, ECMAScript): their text is not here, and the search will return
excerpts that merely mention them, with confident-looking titles.

There is no version filter here. Each standard is present in one edition: the WHATWG
standards and the W3C editor's drafts as they stand today (living standards change
continuously), the W3C Recommendations and the RFCs as published. Two texts are not final:
RFC 6265bis is an Internet-Draft (draft 22) and JSON Schema 2020-12 was published as
Internet-Drafts -- when an answer rests on them, say that the text is a draft.

Where the documentation lives. Documents are named by the standard and the top-level
section: whatwg-fetch--4-fetching, whatwg-html--webappapis (one document per page of the
HTML standard), w3c-csp--6-content-security-policy-directives, w3c-wcag--2-operable,
rfc9110--15-status-codes, rfc6265bis--5-user-agent-requirements, oidc-core--3-authentication,
openapi-3.1--4-specification, json-schema-core--8-the-json-schema-core-vocabulary. The pages
of Understanding WCAG, Techniques for WCAG and the APG are named by their path:
wai-wcag-understanding--..., wai-wcag-techniques--..., wai-apg-patterns--...,
wai-apg-practices--.... Headings keep the numbers of the standard ("4.1 Main fetch",
"Success Criterion 2.4.11"), so a section can be cited by number.

Write the query in English, with the terms the standards use (main fetch, CORS-preflight
fetch, credentials mode, SameSite, Strict-Transport-Security, refresh token rotation,
code_challenge, Success Criterion, aria-expanded, Problem Details). Everything here is
English -- the excerpts, the word index and the meaning index alike -- and the word index
keeps only latin letters and digits, so a query written in Ukrainian, Russian or any other
non-latin script matches nothing at all and comes back with `found: 0`. When the user asks
in another language, translate the question into the terms of the standard first, then
search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
standard uses may miss; "meaning+words" means a second, meaning-based index answered as
well, and a paraphrase had a chance.

Answer in the language the user wrote in. When the question asks what a standard requires,
answer point by point, each point with the standard and the section number it rests on
(RFC 9110, 15.5.21; Fetch, 4.1 step 12); a point the excerpts do not support is left out,
not guessed. Keep the requirement keywords as the text has them -- MUST, SHOULD, MAY in
RFCs, "must" and "should" in WHATWG and W3C texts carry the weight of the rule, and a
MUST retold as "recommended" is a wrong answer. When that language is Ukrainian, write as a
Ukrainian engineer writes, not as a translation from English: plain technical prose, and
the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "вимога", not
"реквайрмент". Never call this set of documents "корпус" -- say "тексти стандартів".
Identifiers, header names, field names and titles stay in English, spelled exactly as the
standard spells them. Build the answer out of the excerpts that came back, not out of
memory: if an excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default
3. Excerpt text is cut at 600 characters -- pass the `id` of an excerpt to
`read_section` to get the whole thing.
