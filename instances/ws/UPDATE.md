# Оновлення корпусу ws

Перелік версій тут не оголошується руками: читач README і реєстру бере його з опису пакета в реєстрі npm
(`https://registry.npmjs.org/ws`), тож нова версія потрапляє в корпус сама, коли вийде в npm. Релізи беруться з
GitHub (`websockets/ws`) і теж підхоплюють нову версію самі. Руками прив'язано дві речі: адреса `History.md` у джерелі
`ws-history` (тег `0.6.5`: файл на новіших тегах репозиторій не вів, тож оновлювати її не треба) і перелік тегів у полі
`tags` джерела `ws-api` (нижче).

Супутні пакети `bufferutil`, `utf-8-validate` і `wscat` підхоплюють нові версії самі, так само як `ws`: їхні README й
реєстр беруться з npm, тегів і релізів вони не мають (нотатки релізів на GitHub порожні).

Правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед роботою нижче тексти розпаковують, а після неї — пакують і виносять знову;
обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## Вийшла нова версія

Спершу додати тег нової версії в поле `tags` джерела `ws-api` у `sources.json` (на початок, бо перелік іде від
найновішого): `"8.23.0": "8.23.0"`. Тег збігається з номером версії; список тегів — `https://github.com/websockets/ws/tags`.
Без цього довідник `doc/ws.md` нової версії в корпус не потрапить, хоч README, реліз і реєстр підхопляться самі.

```
./df ws check                 # чи змінилося щось нагорі за джерелом
./df ws refresh               # повне перезавантаження, близько 10 хвилин
./df ws manifest
./df ws vectors
./df ws smoke
# Ctrl+C у терміналі з serve, і знову: ./df ws serve
```

`refresh` повний, не `--missing`: у документі стоять усі версії, де текст був таким, тож нова версія змінює й старі
документи (README, що не змінився, дописує нову версію в рядок `# версія:`).

Якщо вийшла нова мажорна лінія (9.0) або нова мінорна 8.x:

- у `prompts/search.txt` (абзац «Which version to search first» і перелік ліній) та `prompts/agent.txt` замінити
  поточну лінію на нову, а версію за замовчуванням звірити з числом завантажень
  (`https://api.npmjs.org/versions/ws/last-week`): відповідь іде для найпопулярнішої лінії, а коли дві
  майже рівні — для обох; на 20.10.2026 лінія 8 мала 78 %, лінія 7 — 17 %, лінія 6 — 3,5 %;
- у `checks.json`, у десятках `quality` і `quality_model`, замінити лінію там, де питання про поточну поведінку, і звірити
  цілі.

Якщо `smoke` скаржиться на число фрагментів — корпус підріс; нове число записують у `checks.json` полем
`expected_passages`, а в `expected_note` — коли й чому його знято.

Токен GitHub (`GITHUB_TOKEN` у кореневому `.env`) не обов'язковий, але без нього звернення до API GitHub (дерева тегів
і релізи) ідуть годинними вікнами по 60, а 158 дерев тегів їх вичерпують одразу.

Передрелізи (`0.3.4-2`, `2.0.0-beta.*`) пропускаються полем `skip_versions` у README і `stable` у релізах. Порожній
запис «v0.4.26 - Skipped» у `History.md` пропускає поле `skip` джерела `ws-history`.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df ws quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту,
знову замір. Останній результат — у README, розділ «Скільки цього».
