# Оновлення корпусу xgboost

Корпус живе нагорі: репозиторій `dmlc/xgboost`, сайт Read the Docs і реєстр PyPI. Теги вже вийшлих версій не змінюються, а нова
мінорна лінія потребує правки `sources.json`.

Правило: **нічого не видаляється.** Ані `refresh`, ані `manifest` нічого не видаляють. Лише `vectors` прибирає точки своєї колекції,
чиїх фрагментів у корпусі вже немає.

**Спершу — повернути тексти.** Корпус примірника в архіві, а `check`, `refresh` і `manifest` читають файли. Тому перед роботою нижче
тексти розпаковують, а після неї виносять знову: обидві дії описано в
[README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

```
./df xgboost refresh <id джерела>   # лише те, що змінилося
./df xgboost manifest
./df xgboost vectors
./df xgboost smoke
# Ctrl+C у терміналі з serve, і знову: ./df xgboost serve
```

Що міняти, коли вийшла нова лінія:

- **Тексти `doc/`:** дописати новий тег у поле `tags` джерела `xgboost-docs`, найновіший першим. Нотатки релізу нової лінії лежать у
  `doc/changes/` і прийдуть разом із текстами.
- **Довідник API:** тека `stable` на сайті тепер означає нову лінію. Попередню лінію додати в `versions` джерела `xgboost-api` як
  `release_<номер>.0`, а в `version_labels` записати, який номер означає `stable`.
- Релізи GitHub і PyPI підтягуються самі.

Повне перезавантаження всіх джерел триває кілька хвилин двома блоками: `xgboost-api` окремо, решта разом.

Якщо `smoke` скаржиться на число фрагментів, корпус підріс: нове число записують в `expected_passages`, а в `expected_note` — коли й
чому його знято.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу треба виконати `./df xgboost quality --show`, переглянути запити зі знаком «-» і перевірити, чи справді
відповідь змінилася. Ціль розширюють лише тоді, коли знайдена сторінка справді відповідає на запит.
