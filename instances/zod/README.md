# zod — примірник фабрики docfactory

Десятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Zod за офіційною документацією всіх
його версій — від 1.0.0 (березень 2020) до поточної 4.x, разом з alpha, beta й canary, — за README кожної версії
npm, нотатками релізів і реєстром версій npm. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо вся історія

Zod двічі круто міняв API. У 3.x документацією був сам README, у 4.0 з'явився сайт zod.dev, а API змінився:
`z.string().email()` став `z.email()`, `message` — `error`, `ZodError.errors` — `issues`, з'явилися `zod/mini` і
`zod/v4/core`. Перехід розтягнувся: з 3.25 пакет несе обидві версії одразу (`zod/v3` і `zod/v4`), і близько 40%
завантажень досі припадає на лінію 3. Тож питання звучить «як це в моїй версії», «з якої версії є
`z.discriminatedUnion`», «чим замінили» — і відповідь дає лише документація саме тієї версії.

## Скільки цього

| Шар | Документів | Звідки |
|-----|-----------:|--------|
| Документація на кожному з 208 тегів: кожен неповторний текст файла один раз, з усіма версіями, де він був таким | 293 | репозиторій `colinhacks/zod` |
| README кожної версії npm, зокрема canary; однакові тексти зведено | 187 | README репозиторію на коміті публікації |
| Нотатки релізів | 216 | GitHub API |
| Реєстр версій npm: огляд і по документу на лінії 1–4 | 5 | `registry.npmjs.org/zod` |

Разом 701 документ; фрагментів в індексі — 3 446 (`expected_passages` у `checks.json`). Фрагменти — це шматки
документів між заголовками, по яких іде пошук; незмінні розділи різних редакцій зливаються в один
(`revision_suffix`).

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 3 із 10, за
змістом 2, разом 4; друга, «як модель» (назвами API, з `version "4"`, як велить промпт), — 9 із 10. Цілі першої
десятки — сторінки сайту zod.dev і ті самі розділи документації v3 (`packages-docs-v3-home`). Промахи:

- **Без версії видачу займають README старих версій.** На «отримати тип TypeScript зі схеми» перші місця беруть
  розділи README 1.2.x і 3.8–3.14 — для тих версій це правильна відповідь, але замір її ціллю не рахує. Тому
  промпт велить на питання «як зараз» шукати з `version "4"`.
- **Лінія 4 несе й документацію v3.** З 3.25 документація v3 лежить у тому самому репозиторії
  (`packages/docs-v3`), тож її тексти належать і тегам 4.x, і фільтр `version: "4"` їх знаходить. Звідси єдиний
  промах другої десятки: на «z.discriminatedUnion» перші місця — розділ про оновлений `z.discriminatedUnion` з
  огляду v4 і сторінки v3, а `api#discriminated-unions` у п'ятірку не потрапляє. Відрізнити документацію v3 від v4
  всередині тегу 4.x фільтр версії не вміє; розрізняє її шлях (`packages-docs-v3-…`), і модель бачить його у
  видачі.

**Версія у відповіді.** Кожна відповідь каже, для якої версії вона. Якщо користувач версії не назвав, модель
відповідає для лінії за замовчуванням 4.x, пише це прямо й пропонує назвати свою версію; якщо для 3 і 4 відповідь
різна — дає обидві й питає, на якій лінії проєкт. Текст, знайдений лише в старших версіях, подає з цими версіями.

## Що в цій теці

- `corpus/` — документація звичайними текстовими файлами; поруч `index.json` — паспорт, тобто опис копії: адреса,
  дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Теги документації лежать тут, у
  полі `tags` джерела `zod-docs`; версії для README приходять з реєстру npm.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df zod <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація всіх версій | дерево репозиторію на кожному тезі, текст — `raw.githubusercontent.com` | `ghdocs-history` |
| README усіх версій npm | реєстр npm (версії й коміти публікації), текст — `raw.githubusercontent.com` | `npm-readme` |
| нотатки релізів | GitHub API | `ghreleases` |
| реєстр версій | опис пакета в реєстрі npm | `npm-versions`, новий |

Особливості, які варто знати:

- **Дві епохи документації.** До 3.25 документація — це кореневий README (він у джерелі `zod-readme`) і файли
  поруч: `ERROR_HANDLING.md`, `MIGRATION.md`, `CHANGELOG.md`, теки `docs/` і `blog/`. З 3.25 — сайт zod.dev у
  `packages/docs/content` (MDX), а документація v3 — у `packages/docs-v3`. Назва документа — шлях файла:
  `packages-docs-content-basics`, `packages-docs-v3-home`, `ERROR_HANDLING`.
- **Теги — точні версії.** «Лінійні» теги (`v3.25`, `v1.9`), що дублюють точні, не беруться. Серед тегів є кілька
  передрелізів (`4.0.0-beta`, `3.0.0-beta3`, `3.0.0-snapshot-2021-01-21`); canary тегів не мають.
- **README — з коміту публікації.** Реєстр npm для кожної версії пише коміт, з якого її опубліковано (`gitHead`), і
  README береться з репозиторію на цьому коміті, а де коміту в реєстрі нема (115 версій) — з тегу релізу. З v4 це
  `packages/zod/README.md`, бо в корені лишилася заглушка; тексти коротші за 500 знаків (заглушки) не беруться. У
  119 версій README так і не знайшовся; серед стабільних — лише 1.2.3 і 1.11.7.
- **Лінія 2 — лише передрелізи.** 43 версії alpha і beta, стабільного релізу не було; її текст — тільки в README.
- **Canary — повноправні версії.** Їх теж встановлюють, тож і README, і рядки реєстру для них є. Canary — не
  релізи: текст, що є лише в них, міг так і не вийти, і промпт велить моделі казати про це прямо.
- **Реєстр версій npm (`npm-versions`).** Огляд пакета — поточні мітки (`latest`, `beta`, `canary`…), лінії з
  першою й останньою версією, і для кожного шляху імпорту (`zod/v4`, `zod/mini`) — з якої й до якої версії він був.
  Документ лінії — кожна версія з датою, видом і тим, що змінилося відносно попередньої: шляхи імпорту, залежності,
  вимоги до Node. Це відповідає на «з якої версії» й «що встановити», чого текст документації прямо не каже.
- **MDX.** Рядки `import`/`export` сторінок сайту відкидаються, але лише поза блоками коду: у прикладах вони
  лишаються.
- **Лише англійська.** Переклади README (KO, ZH) не беруться.
- **Редакції того самого файла зливаються (`revision_suffix`)**, як у `react-router`: ім'я документа несе хеш
  вмісту, і без поля незмінний розділ двох редакцій лишався б двома фрагментами.

## Межі, про які треба пам'ятати

Бібліотек довкола Zod тут немає: `@hookform/resolvers`, `zod-to-json-schema`, tRPC та інших. Документація `zod/v3`
у пакетах 4.x — та сама, що в `packages/docs-v3`, окремо не збиралася.

## Установка venv

```
cd instances/zod
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df zod sources --why   # перелік джерел і білий список
./df zod refresh         # завантажити все задеклароване
./df zod manifest        # оновити паспорт
./df zod setup           # Qdrant чи пошук лише по словах
./df zod vectors         # залити корпус у docs-zod (~80 хвилин)
./df zod smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df zod serve          # порт 8770
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8770/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user zod-docs http://127.0.0.1:8770/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `zod-docs` і два інструменти `search_docs`, `read_section`.

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df zod setup --vectors      # з Qdrant: потрібен Docker; вектори рахуються ~80 хвилин
./df zod setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

Без векторів сервер працює так само, лише перефразоване питання, що не має спільних слів із документацією, може не
знайтися. Перейти на вектори можна будь-коли тією самою командою з `--vectors`.

**4. Перевірка, сервер, клієнт.**

```
./df zod smoke          # усі перевірки мають бути ok
./df zod serve          # порт 8770, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
