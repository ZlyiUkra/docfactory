# Оновлення корпусу zod

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версії README й реєстру приходять із npm, а теги документації — руками.** Перелік версій для
`zod-readme` і `zod-npm` береться з реєстру npm на кожному прогоні: новий реліз, зокрема canary, потрапляє в корпус
сам. Інакше з `zod-docs`: там, як у `react-router`, оновлювач бере рівно теги з поля `tags` у `sources.json`, і
новий тег треба дописати.

Друге правило: **новий реліз змінює й старі документи.** Документ — неповторний текст файла, а в рядку `# версія:`
стоять усі версії, де файл був саме таким. Тому `zod-docs`, `zod-readme` і `zod-npm` перезаписуються цілком
(`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version` їх
не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Документ, що після нового релізу вже нікому не належить, лишається в `corpus/`; прибрати його — рішення людини.

**Спершу — повернути тексти.** Корпус примірника в архіві: у `corpus/` лежить лише паспорт, а `check`, `refresh` і
`manifest` працюють із файлами. Перед будь-якою роботою нижче тексти розпаковують, а після неї — пакують і виносять
знову; обидві дії описані в [README, розділ «Архівний режим»](README.md#архівний-режим-сервер-без-корпусу).

## 1. Вийшли нові релізи

**Крок 1. Дописати теги для `zod-docs`.** Список, без жодного звернення до API:

```
git ls-remote --tags https://github.com/colinhacks/zod.git | grep -v '\^{}' \
  | sed 's#.*refs/tags/##' | sort -V | tail
```

Кожен новий тег дописується на початок поля `tags` джерела `zod-docs` парою «тег → версія»
(`"v4.7.0": "4.7.0"`). Перелік іде від найновішого за датою публікації в npm. «Лінійні» теги (`v4.7` без
третього числа), що дублюють точні, не дописуються.

**Крок 2. Якщо вийшла нова мажорна лінія** (скажімо, 5.0.0 як реліз, а не beta чи canary):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзац «Which version to search first») та
  `prompts/agent.txt` велять на питання «як зараз» шукати з `version "4"`;
- у `checks.json`, у десятці `quality_model`, замінити `"4"` на нову лінію там, де питання про поточну поведінку.

**Крок 3. Якщо документація переїхала** в іншу теку репозиторію — дописати її в поле `folders` джерела `zod-docs`;
якщо README пакета переїхав — додати шаблон шляху в поле `files` джерела `zod-readme` (перелік іде за пріоритетом).

**Крок 4. Завантажити.**

```
./df zod sources --why
./df zod refresh
./df zod manifest
./df zod vectors
./df zod smoke
# Ctrl+C у терміналі з serve, і знову: ./df zod serve
```

`refresh` без назв — повне перезавантаження. Корпус не комітиться: після оновлення пишуть новий архів і знову
виносять тексти (README, розділ «Архівний режим»), а в git ідуть лише паспорт і кеш.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього дерева 208 тегів ідуть годинними
вікнами по 60 звернень.

**Крок 2. Усе одним прогоном.**

```
nohup ./df zod refresh > /tmp/zod-refresh.log 2>&1 &
```

Спершу журнал мовчить, а `corpus/` порожній: читачі проходять дерево кожного тегу й README кожної з понад тисячі
версій npm, і лише потім починають писати файли. Стан видно за кількістю файлів: `ls instances/zod/corpus | wc -l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df zod quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Що це означає тут:

- **Поточна лінія — 4.** `prompts/search.txt` (абзац «Which version to search first») і `prompts/agent.txt` велять
  на питання «як зараз» шукати з `version "4"`. Лінію за замовчуванням звірити із завантаженнями `zod` (пункт 3
  кроку 7): 28.09.2026 лінія 4 — близько 60%, лінія 3 — близько 40%. Поки лінія 3 тримає таку частку, промпт велить
  при різних відповідях для 3 і 4 давати обидві.
- **Правила промпту, що вже є:** спершу лінія 4, без версії — лише історія; запит — назвами API, як їх називає
  документація; кожна відповідь каже, для якої версії вона, а без названої версії — відповідає для 4.x і пропонує
  назвати свою; текст, що є лише в alpha, beta чи canary, міг не вийти релізом — казати про це.
- **Останній результат:** у README, абзац «Замір `quality`».
