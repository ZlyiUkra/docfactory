# zustand — примірник фабрики docfactory

Одинадцятий примірник фабрики: захищений MCP-сервер, що відповідає на питання про Zustand за офіційною документацією
всіх його версій — від 0.0.1 (квітень 2019) до поточної 5.x, разом з alpha, beta й rc, — за README кожної версії
npm, нотатками релізів і реєстром версій npm. Код спільний і лежить у `../../engine/`, `../../server/` та
`../../common/`; ця тека тримає самі дані домену. Загальний устрій фабрики — у [../../README.md](../../README.md).

## Навіщо вся історія

Zustand маленький, але його API помітно змінювався з мажорною версією. У 4.0 документація переїхала з README в
окрему теку, а `zustand/context` лишився тільки в 4.x; у 5.0 прибрали імпорт за замовчуванням, `create` більше не
приймає функцію порівняння (для цього тепер `createWithEqualityFn` з `zustand/traditional`), а замість `shallow` у
селекторі радять хук `useShallow`. Лінія 4 досі тримає близько 40% завантажень, тож питання звучить «як це в моїй
версії», «з якої версії є `useShallow`», «чим замінили» — і відповідь дає лише документація саме тієї версії.

## Скільки цього

| Шар | Документів | Звідки |
|-----|-----------:|--------|
| Тека `docs/` на кожному з 137 тегів: кожен неповторний текст файла один раз, з усіма версіями, де він був таким | 374 | репозиторій `pmndrs/zustand` |
| README кожної версії npm, зокрема alpha, beta й rc; однакові тексти зведено | 85 | README репозиторію на коміті публікації |
| Нотатки релізів | 105 | GitHub API |
| Реєстр версій npm: огляд і по документу на лінії 0–5 | 7 | `registry.npmjs.org/zustand` |

Разом 571 документ; фрагментів в індексі — 2 191 (`expected_passages` у `checks.json`). Фрагменти — це
шматки документів між заголовками, по яких іде пошук; незмінні розділи різних редакцій зливаються в один
(`revision_suffix`).

Замір `quality` на першому корпусі: перша десятка (питання своїми словами, без версії) — по словах 4 із 10, за
змістом 4, разом 5; друга, «як модель» (назвами API, з `version "5"`, як велить промпт), — 9 із 10. Теми обох
десяток однакові, а цілі — і сторінки нинішньої розкладки сайту (`learn/`, `reference/`), і ті самі сторінки старших
розкладок (`guides/`, `middlewares/`, `integrations/`): для старшої версії це правильна відповідь. Промахи:

- **Своїми словами без назв API.** «Спостерігати зміни стану в розширенні браузера» не знаходить `devtools`,
  «стор без React» — `createStore`, «змінювати вкладений стан на місці» — `immer`: слова питання й документації не
  перетинаються. Тому промпт велить писати запит назвами API; друга десятка з ними влучає 9 разів.
- **Єдиний промах другої десятки** — «persist middleware localStorage»: місця зайняли розділ «persist middleware» у
  README версій 5.0.x і такий самий розділ гайду TypeScript для початківців. Обидва описують persist, але сторінками
  persist не є, тож ціллю їх не дописано: це була б підгонка заміру під видачу.

**Версія у відповіді.** Кожна відповідь каже, для якої версії вона. Якщо користувач версії не назвав, модель
відповідає для лінії за замовчуванням 5.x, пише це прямо й пропонує назвати свою версію; якщо для 4 і 5 відповідь
різна — дає обидві й питає, на якій лінії проєкт. Текст, знайдений лише в старших версіях, подає з цими версіями.

## Що в цій теці

- `corpus/` — документація звичайними текстовими файлами; поруч `index.json` — паспорт, тобто опис копії: адреса,
  дата завантаження й сума тексту кожного документа.
- `sources.json` — звідки корпус будується, і водночас білий список для оновлювача. Теги документації лежать тут, у
  полі `tags` джерела `zustand-docs`; версії для README приходять з реєстру npm.
- `config.json` — порт, колекція Qdrant, модель векторів, пауза між зверненнями і профіль домену.
- `prompts/` — описи інструментів для моделі, системний промпт власного агента, текст відмови.
- `checks.json` — чим `smoke` і `quality` перевіряють саме цей корпус.
- `.env` — ключ Anthropic (лише для кроку `ask`) і токен GitHub (лише для завантаження корпусу); `.mcp.json` —
  запис HTTP-сервера для Claude Code.
- `.venv/` — власний venv примірника; `requirements.txt` — його склад.

Кроки нижче, окрім установки venv, запускаються з кореня фабрики (`docfactory/`) через `./df zustand <крок>`.

## Звідки документація

| Що | Джерело | Читач |
|----|---------|-------|
| документація всіх версій | тека `docs/` на кожному тезі, текст — `raw.githubusercontent.com` | `ghdocs-history` |
| README усіх версій npm | реєстр npm (версії й коміти публікації), текст — `raw.githubusercontent.com` | `npm-readme` |
| нотатки релізів | GitHub API | `ghreleases` |
| реєстр версій | опис пакета в реєстрі npm | `npm-versions` |

Нових читачів цей примірник не додав: усі чотири вже були.

Особливості, які варто знати:

- **Три розкладки документації.** До 4.0 документація — це README (він у джерелі `zustand-readme`). У 4.0 з'явилася
  тека `docs/`, згодом поділена на `getting-started`, `guides`, `integrations`, `migrations`, а в 5.0 — ще й
  `apis`, `hooks`, `middlewares`. З 5.0.15 сайт zustand.docs.pmnd.rs перейшов на розділи `learn/` і `reference/`.
  Назва документа — шлях файла: `docs-guides-slices-pattern`, `docs-learn-guides-slices-pattern`,
  `docs-reference-middlewares-persist`. Та сама сторінка в різних розкладках — різні документи.
- **Теги — точні версії.** Частина тегів без префікса `v` (`4.5.7`), решта з ним; кожен відповідає версії npm.
- **README — з коміту публікації.** Реєстр npm для кожної версії пише коміт, з якого її опубліковано (`gitHead`), і
  README береться з репозиторію на цьому коміті, а де коміту в реєстрі нема — з тегу релізу. У 10 версій немає ні
  коміту, ні тегу — їхнього README в корпусі нема: 4.0.0-alpha.0–4, 3.1.0-beta.0, 3.0.0-beta.0, 2.2.3,
  1.0.0-beta.0 і 1.0.0-beta.1.
- **Шляхи імпорту в 5.x.** Пакет 5.x публікує підшляхи шаблоном `zustand/*`, тож явні `zustand/middleware`,
  `zustand/shallow` в огляді реєстру закінчуються на 4.5.7. Імпорт при цьому працює й далі — через шаблон; огляд
  це прямо застерігає.
- **Лише англійська.**
- **Редакції того самого файла зливаються (`revision_suffix`)**, як у `react-router`: ім'я документа несе хеш
  вмісту, і без поля незмінний розділ двох редакцій лишався б двома фрагментами.

## Межі, про які треба пам'ятати

Бібліотек довкола Zustand тут немає: `zustand-x`, `zundo`, `use-context-selector`, як і документації Jotai чи Valtio
з того ж pmndrs. Alpha, beta й rc — не релізи: текст, що є лише в них, міг так і не вийти, і промпт велить моделі
казати про це прямо.

## Установка venv

```
cd instances/zustand
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env          # впишіть GITHUB_TOKEN і, якщо потрібен крок ask, ANTHROPIC_API_KEY
cd ../..
```

## Збирання корпусу

Якщо корпус уже лежить у `corpus/`, потрібен лише `vectors`, якщо колекції ще немає.

```
./df zustand sources --why   # перелік джерел і білий список
./df zustand refresh         # завантажити все задеклароване (~15 хвилин)
./df zustand manifest        # оновити паспорт
./df zustand setup           # Qdrant чи пошук лише по словах
./df zustand vectors         # залити корпус у docs-zustand (~25 хвилин)
./df zustand smoke           # перевірки
```

Порядок оновлення — у [UPDATE.md](UPDATE.md). Після будь-якого оновлення корпусу `serve` треба перезапустити.

## Сервер під Claude Code

**1. Підняти сервер** в окремому терміналі WSL і лишити жити:

```
cd ~/Projects/docfactory
./df zustand serve          # порт 8771
```

Готовий він тоді, коли надрукував кількість фрагментів і адресу `http://127.0.0.1:8771/mcp`.

**2. Додати сервер у Claude Code** — у тому середовищі, де відкрито вікно:

```
claude mcp add --transport http --scope user zustand-docs http://127.0.0.1:8771/mcp
```

У WSL і у Windows Claude Code тримає окремі налаштування: вікно VS Code на боці Windows читає
`C:\Users\<ім'я>\.claude.json`, тож команду треба виконати в PowerShell, або додати сервер кнопкою «Add server»
у вікні `/mcp` (тип HTTP, рівень User). Сам сервер з Windows доступний за тією ж адресою: WSL2 прокидає порт.

**3. Перевірити.** `/mcp` — має бути `zustand-docs` і два інструменти `search_docs`, `read_section`. Якщо сесію
Claude Code відкрито раніше, ніж піднято сервер, вона покаже його як недоступний: у `/mcp` виберіть сервер і
«Reconnect».

Зупинка — Ctrl+C у терміналі сервера. Решта — scope запису, «address already in use» — так само, як у
[README примірника react-router](../react-router/README.md#спосіб-б--сервер-під-claude-code-http).

## На іншій машині

Інше вікно VS Code на тій самій машині нічого, крім кроків 1–3 вище, не потребує: сервер один, клієнтів скільки
завгодно. На іншій машині (теж WSL) бракує трьох речей, яких немає в git: venv примірника, `.env` і векторів у
Qdrant.

**1. Код і корпус.** Корпус лежить у git, тож досить отримати репозиторій зі свіжими комітами (`git clone` або
`git pull` після того, як їх запушено) і перейти в його корінь.

**2. Venv примірника** — за розділом «Установка venv» вище. `.env` для пошуку не потрібен: токен GitHub треба лише
для `refresh`, ключ Anthropic — лише для `ask`.

**3. Спосіб пошуку.** Два варіанти:

```
./df zustand setup --vectors      # з Qdrant: потрібен Docker; вектори рахуються ~25 хвилин
./df zustand setup --no-vectors   # лише пошук по словах: без Docker, одразу
```

Без векторів сервер працює так само, лише перефразоване питання, що не має спільних слів із документацією, може не
знайтися. Перейти на вектори можна будь-коли тією самою командою з `--vectors`.

**4. Перевірка, сервер, клієнт.**

```
./df zustand smoke          # усі перевірки мають бути ok
./df zustand serve          # порт 8771, лишити жити
```

і далі — кроки 2–3 розділу «Сервер під Claude Code» на тій машині, де відкрито VS Code.
