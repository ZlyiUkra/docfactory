# Оновлення корпусу zustand

Дві різні роботи: звичайне оновлення, коли вийшли нові релізи, і збирання з нуля. Порядок усередині кожної
важливіший за самі команди.

Головне правило: **версії README й реєстру приходять із npm, а теги документації — руками.** Перелік версій для
`zustand-readme` і `zustand-npm` береться з реєстру npm на кожному прогоні: новий реліз, зокрема alpha, beta й rc,
потрапляє в корпус сам. Інакше з `zustand-docs`: там, як у `react-router`, оновлювач бере рівно теги з поля `tags` у
`sources.json`, і новий тег треба дописати.

Друге правило: **новий реліз змінює й старі документи.** Документ — неповторний текст файла, а в рядку `# версія:`
стоять усі версії, де файл був саме таким. Тому `zustand-docs`, `zustand-readme` і `zustand-npm` перезаписуються
цілком (`refresh` без `--missing`): інакше старі тексти не дізнаються, що дожили до нової версії, і фільтр `version`
їх не знайде.

Третє правило: **нічого не видаляється.** Ані `refresh`, ані `vectors`, ані `manifest` нічого не стирають самі.
Документ, що після нового релізу вже нікому не належить, лишається в `corpus/`; прибрати його — рішення людини.

## 1. Вийшли нові релізи

**Крок 1. Дописати теги для `zustand-docs`.** Список, без жодного звернення до API:

```
git ls-remote --tags https://github.com/pmndrs/zustand.git | grep -v '\^{}' \
  | sed 's#.*refs/tags/##' | sort -V | tail
```

Кожен новий тег дописується на початок поля `tags` джерела `zustand-docs` парою «тег → версія» (`"v5.1.0": "5.1.0"`).
Перелік іде від найновішого за датою публікації в npm. Префікс `v` у тегах Zustand є не завжди (`4.5.7`): ключ — тег
як він є, значення — версія npm.

**Крок 2. Якщо вийшла нова мажорна лінія** (скажімо, 6.0.0 як реліз, а не alpha, beta чи rc):

- у промптах замінити поточну лінію: `prompts/search.txt` (абзац «Which version to search first») та
  `prompts/agent.txt` велять на питання «як зараз» шукати з `version "5"`;
- у `checks.json`, у десятці `quality_model`, замінити `"5"` на нову лінію там, де питання про поточну поведінку.

**Крок 3. Якщо документація переїхала** в іншу теку репозиторію — дописати її в поле `folders` джерела `zustand-docs`;
якщо README пакета переїхав — додати шаблон шляху в поле `files` джерела `zustand-readme` (перелік іде за
пріоритетом).

**Крок 4. Завантажити.**

```
./df zustand sources --why
./df zustand refresh
./df zustand manifest
./df zustand vectors
./df zustand smoke
# Ctrl+C у терміналі з serve, і знову: ./df zustand serve
```

`refresh` без назв — повне перезавантаження. Корпус комітити частинами до ~700 файлів.

Якщо `smoke` скаржиться на число фрагментів — це наслідок того, що документація підросла. Нове число записують у
`checks.json` полем `expected_passages`, а в `expected_note` — коли й чому його знято.

## 2. Збирання з нуля

**Крок 1. Токен.** Покладіть `GITHUB_TOKEN=…` у `.env` цієї теки. Без нього дерева 137 тегів ідуть годинними
вікнами по 60 звернень.

**Крок 2. Усе одним прогоном.**

```
nohup ./df zustand refresh > /tmp/zustand-refresh.log 2>&1 &
```

Спершу журнал мовчить, а `corpus/` порожній: читачі проходять дерево кожного тегу й README кожної з півтори сотні
версій npm, і лише потім починають писати файли. Стан видно за кількістю файлів: `ls instances/zustand/corpus | wc
-l`.

**Крок 3. Якщо прогін урвався** — повторіть його з `--missing`: уже записані файли не перекачуються.

## Уточнення відповідей після оновлення

Після кожного оновлення корпусу — цикл із [кроку 7 загального довідника](../../UPDATE.md#крок-7--відновити-уточнення-відповідей):
`./df zustand quality --show`, порівняння обох десяток з попереднім результатом, розбір промахів, правка промпту, знову
замір. Що це означає тут:

- **Поточна лінія — 5.** `prompts/search.txt` (абзац «Which version to search first») і `prompts/agent.txt` велять
  на питання «як зараз» шукати з `version "5"`. Лінію за замовчуванням звірити із завантаженнями `zustand` (пункт
  3 кроку 7): 28.09.2026 лінія 5 — 55,9%, лінія 4 — 39,0%, лінія 3 — 5,0%. Поки лінія 4 тримає таку частку, промпт
  велить при різних відповідях для 4 і 5 давати обидві.
- **Правила промпту, що вже є:** спершу лінія 5, без версії — лише історія; запит — назвами API, як їх називає
  документація; кожна відповідь каже, для якої версії вона, а без названої версії — відповідає для 5.x і пропонує
  назвати свою; текст, що є лише в alpha, beta чи rc, міг не вийти релізом — казати про це.
- **Останній результат:** у README, абзац «Замір `quality`».
