Search the official Zustand documentation -- every released version of it, from 0.x (2019) to
the current 5.x line, including alpha, beta and rc builds -- together with the README of every
release, the GitHub release notes and the npm registry list of every published version
(date, dist-tag, import paths such as zustand/middleware or zustand/shallow, dependencies),
and return the matching excerpts with the versions each one belongs to.

Call this when a question is about Zustand itself -- creating a store (create, createStore,
the vanilla store, useStore), selectors and re-renders (useShallow, shallow, equality
functions, createWithEqualityFn), updating state (set, get, replace, immutable updates,
the immer middleware), middlewares (persist, devtools, subscribeWithSelector, combine,
redux), the slices pattern, TypeScript types for stores and middlewares, React context,
SSR and Next.js, testing, an upgrade from v3 to v4 or from v4 to v5 -- and above all when it
is about history: since which version something exists, what changed between versions, what
was renamed or removed and what replaced it. Example query: "persist middleware storage".

Do not call this for React itself, for Redux, Jotai, Valtio, MobX or Recoil, or for
libraries built on Zustand: their documentation is not here, and the search will return
Zustand excerpts that merely mention them, with confident-looking titles.

`version` narrows the search to one release line: "5" keeps every 5.x document, "4.5"
keeps 4.5.x, "3" keeps 3.x; leave it empty to search everything. Pre-releases belong to
their line: "5" also keeps 5.0.0-alpha, -beta and -rc builds. Every excerpt comes back with
`versions`: each version whose documents contain this exact text, newest first -- text that
stayed the same across versions is returned once, with all of them listed, so the list
itself shows from which to which version the documentation said exactly this.

Where the documentation lived. Up to 3.x the whole documentation was the README of the
package (titles "Zustand README …"). From 4.0 it is the docs/ folder of the repository, the
source of the zustand.docs.pmnd.rs site (titles from docs/…): guides, recipes, integrations
and migrations at first, API, hooks and middleware reference pages from 5.0, and from 5.0.15
the learn/ and reference/ sections of the current site.

Which version to search first. For a question about how to do something today, pass
`version` "5" (or the line of the user's project): without it, the many editions of the
older README and docs, which differ by a line or two, fill every place with older APIs.
Search without `version` when the question is about history, or when the line gave nothing
that answers.

For a question about when something appeared, changed or disappeared, search more than
once: without `version` first, to find the release notes and the migration guide that name
the exact version, then with the versions around it, to see how the documentation described
it before and after.

Write the query in English, with the names Zustand itself uses (create, useShallow,
persist, devtools, createStore, StateCreator). Everything here is English -- the excerpts,
the word index and the meaning index alike -- and the word index keeps only latin letters
and digits, so a query written in Ukrainian, Russian or any other non-latin script matches
nothing at all and comes back with `found: 0`. When the user asks in another language,
translate the question into Zustand terms first, then search.

The `search` field of the result says how the excerpts were found: "words" means the words
of the query had to appear in the text, so a query phrased in other words than the
documentation uses may miss; "meaning+words" means a second, meaning-based index answered
as well, and a paraphrase had a chance.

Every answer says which version it is for. When the user did not name a version, answer
for the default line, 5.x -- the line most projects use -- say so in the answer ("for
Zustand 5.x"), and add that for a precise answer about another version the user can name
it. When the excerpts behind a statement come only from older versions, name those versions
instead of presenting the text as current. Line 4 is still widely used (about 40% of
downloads): when the answer differs between 4 and 5, give both and ask which one the project
is on.

Answer in the language the user wrote in. When the question is about a feature's history
or support, answer point by point: since which version it exists and which release
introduced it; what changed in later versions; what prompted the change, if the excerpts
say so; and how it stands in the current version -- recommended, deprecated, or removed and
replaced by what. Every point names the version and the document it rests on; a point the
excerpts do not support is left out, not guessed. A text found only in alpha, beta or rc
builds may never have shipped in a release: say so. When that language is Ukrainian, write
as a Ukrainian engineer writes, not as a translation from English: plain technical prose,
and the Ukrainian word wherever one exists -- "уривок", not "ексерпт"; "застарілий", not
"депрекейтнутий". Never call this set of documents "корпус" -- say "документація Zustand".
Identifiers, API names and titles stay in English, spelled exactly as the documentation
spells them. Build the answer out of the excerpts that came back, not out of memory: if an
excerpt was cut, read the whole of it before describing what it says.

Arguments: `query` is free text; `k` is how many excerpts to return, 1 to 10, default 3;
`version` is optional, see above. Excerpt text is cut at 600 characters -- pass the `id` of
an excerpt to `read_section` to get the whole thing.
